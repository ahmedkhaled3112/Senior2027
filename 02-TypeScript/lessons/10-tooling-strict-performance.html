Why this matters · ليه ده مهم

English

Writing good types is half the job. The other half is the system around them: a lint rule that catches the floating promise tsc is happy with, a flag that catches items[0].sku on an empty cart, a plan to turn those flags on in a 200,000-line codebase without stopping the team, and the ability to answer "why does CI take 12 minutes?" with data. That's Senior ownership, and it's what interviewers probe with "how would you migrate this to strict?"

The ground also moved in 2026. npm i typescript now gives you TS 7, the native compiler, and the type-aware lint tooling can't run on it yet. This lesson shows the setup that works, and every number in it comes from a real run on both compilers. Timings are from a busy Windows machine with other jobs running, so treat them as approximate (≈) and trust the ratios and the counts.

بالعامية

إنك تكتب types كويسة ده نص الشغل. النص التاني هو السيستم اللي حواليها: lint rule بتمسك الـ floating promise اللي tsc راضي عنها، وflag بيمسك items[0].sku على cart فاضية، وخطة تفعّل بيها الـ flags دي في codebase فيه 200 ألف سطر من غير ما توقف الفريق، وإنك تعرف ترد على "ليه الـ CI بياخد 12 دقيقة؟" بأرقام. ده اللي بيتسمى Senior ownership، وده اللي الـ interviewer بيدوّر عليه لما يسألك "هتحوّل المشروع ده لـ strict إزاي؟".

وكمان الأرض اتحركت في 2026: npm i typescript بقى بيجيب TS 7، الـ compiler الـ native، وأدوات الـ type-aware lint لسه مش بتشتغل عليه. الدرس ده بيوريك الـ setup اللي شغال، وكل رقم فيه طالع من تشغيل حقيقي على الـ compiler الاتنين. الأوقات من جهاز Windows مشغول وعليه شغل تاني، فاعتبرها تقريبية (≈)، واعتمد على النسب والأعداد.

Part 1 — typescript-eslint, and why it can't use TS 7 yet 🟡 Intermediateالجزء 1 — typescript-eslint، وليه لسه مش بيشتغل على TS 7

English

tsc asks "do the types line up?" Type-aware lint rules ask "is this code doing something dangerous, given the types?" The file below has five real production bugs and tsc reports zero errors on both TS 6 and TS 7. A dropped promise is valid TypeScript, and so is a default branch that swallows a new status. no-floating-promises, no-explicit-any, strict-boolean-expressions and switch-exhaustiveness-check catch them because they read type information from the compiler.

That dependency is exactly the problem today. typescript-eslint 8.72 declares "typescript": ">=4.8.4 <6.1.0" as its peer range, so npm refuses to install it next to TS 7 (ERESOLVE). Forcing it with --legacy-peer-deps only moves the failure: ESLint crashes at startup with typescript-eslint does not support TS 7.0. The reason is architectural. require("typescript") on TS 7 exports only version and versionMajorMinor; there's no createProgram, because 7.0 ships without the JS compiler API that the lint tooling reads types through. Microsoft says it expects 7.1 to ship a new and different API, and typescript-eslint tracks its support in issue #10940. Other tools lag too: openapi-typescript 7.13 still peers on typescript ^5.x.

The way teams deal with this is the side-by-side setup from Microsoft's announcement, using two npm aliases. typescript points at @typescript/typescript6, so every tool that does require("typescript") gets the TS 6 API. @typescript/native points at TS 7, which provides the tsc binary. You get a fast type-check and a working linter from one install. The cost is that two compilers now read your code, so keep the code valid on both: run tsc6 --stableTypeOrdering in CI, and remove the alias once your tools support the new API.

Two of the four rules aren't in any preset. recommendedTypeChecked includes no-floating-promises and no-explicit-any, but strict-boolean-expressions and switch-exhaustiveness-check are in neither recommended nor strict, so you must switch them on yourself, as the config below does.

type OrderStatus = "pending" | "paid" | "refunded";

  id: string;
  status: OrderStatus;
  coupon: string | null;
  totalCents: number;
}

  await Promise.resolve(order.id);
}

}

// (2) الـ any بيقفل الـ type-checker على كل اللي بعده
export function parseOrder(json: string): Order {
  const data: any = JSON.parse(json);
  return data;
}

// (3) الشرط ده بيعدّي ⁦""⁩ و 0 كإنهم مفيش قيمة
export function discountLabel(order: Order): string {
  if (order.coupon) return `coupon: ${order.coupon}`;

}

// (4) حد ضاف refunded في الـ union ونسي الـ switch ده

      return "Waiting for payment";

      return "Unknown";
  }
}

  orders.forEach(async (order) => {
    await saveOrder(order);
  });
}

tsc بيسأل "الـ types راكبة على بعض؟"، والـ type-aware lint rules بتسأل "الكود ده بيعمل حاجة خطر، بالنظر للـ types؟". الملف فوق فيه 5 bugs حقيقية بتاعة production، وtsc بيطلّع صفر errors على TS 6 وTS 7. الـ promise الضايعة TypeScript سليم، وكمان الـ default اللي بيبلع status جديد. no-floating-promises وno-explicit-any وstrict-boolean-expressions وswitch-exhaustiveness-check بيمسكوهم لإنهم بيقروا الـ type information من الـ compiler.

والاعتماد ده هو المشكلة النهارده. typescript-eslint 8.72 معلن "typescript": ">=4.8.4 <6.1.0" كـ peer range، فـ npm بيرفض يسطّبه جنب TS 7 (ERESOLVE). ولو غصبته بـ --legacy-peer-deps الغلطة بتتنقل بس: ESLint بيقع أول ما يبدأ برسالة typescript-eslint does not support TS 7.0. والسبب في الـ architecture: require("typescript") على TS 7 بيرجّع version وversionMajorMinor بس، ومفيش createProgram، لإن 7.0 نازل من غير الـ JS compiler API اللي الـ lint بيقرا منها الـ types. Microsoft بتقول إنها متوقعة إن 7.1 ينزل بـ API جديدة ومختلفة، وtypescript-eslint بيتابع الدعم في issue #10940. وأدوات تانية متأخرة كمان: openapi-typescript 7.13 لسه peer بتاعها typescript ^5.x.

والفرق بتتعامل مع ده بالـ side-by-side setup اللي في إعلان Microsoft، بـ npm aliases اتنين. typescript بيشاور على @typescript/typescript6، فأي tool بتعمل require("typescript") بتاخد TS 6 API. و@typescript/native بيشاور على TS 7، وهو اللي بيدّيك الـ tsc. فبتاخد type-check سريع وlinter شغال من install واحد. التكلفة إن فيه 2 compilers بيقروا الكود، فلازم يفضل سليم على الاتنين: شغّل tsc6 --stableTypeOrdering في الـ CI، وشيل الـ alias لما الأدوات تدعم الـ API الجديدة.

واتنين من الأربع rules مش في أي preset. recommendedTypeChecked فيها no-floating-promises وno-explicit-any، إنما strict-boolean-expressions وswitch-exhaustiveness-check مش في recommended ولا strict، فلازم تفعّلهم بإيدك زي الـ config اللي فوق.

Part 2 — tsc --noEmit in CI & project references 🟡 Intermediateالجزء 2 — tsc --noEmit في الـ CI والـ project references

English

Type-checking and transpiling are separate jobs (lesson 01 introduced this). esbuild, SWC and tsx strip types without looking at them, so a build can succeed and run with a type error in it: below, esbuild exits 0 and the program prints 15050 instead of adding two numbers. So CI must run tsc --noEmit as its own required step. With TS 7 the old reason for the split, speed, has weakened: a full type-check of 301 files took ≈0.7 s, while esbuild took ≈1–1.5 s to write them on this machine. Keep the split anyway, because your dev server shouldn't refuse to reload over a type error, and bundling is a different job.

In a monorepo, project references split the type-check along package lines. A package sets composite: true (which turns on declaration), and dependents list it under references. tsc -b then builds in dependency order and stores state in .tsbuildinfo. The important behaviour is in the logs below. With nothing changed, it skips everything. Change a function body in shared and only shared rebuilds, because api depends on the emitted .d.ts, which didn't change. Change a public signature and api rebuilds and reports the real break.

Dependents type-check against the .d.ts rather than re-checking source, which is what makes this scale. The price is config: every package needs a tsconfig.json and correct references, and you must commit to tsc -b as the entry point. Importing another package without a reference fails with TS6059 and TS6307.

Part 3 — noUncheckedIndexedAccess & exactOptionalPropertyTypes 🔴 Advancedالجزء 3 — noUncheckedIndexedAccess و exactOptionalPropertyTypes

English

These two aren't part of strict, yet they close its biggest remaining holes. By default items[0] has type OrderItem even when the array is empty, and FX_RATES[currency] has type number even for a currency that isn't there. noUncheckedIndexedAccess adds | undefined to every index access, which forces you to decide what an empty cart or an unknown currency means. The unknown-currency case is the nastier one: nothing crashes, a NaN just flows into your database.

The cost is noise in code that already checks bounds: a classic for (let i...) loop gets flagged even though i is in range. Prefer for...of, which doesn't get undefined, and use ! only where the bound is genuinely proven. Narrowing still works on a literal or const key. Also, the flag needs strictNullChecks: without it, it does nothing and reports nothing, because | undefined vanishes. On TS 7 it passes with no message at all.

exactOptionalPropertyTypes separates two things JavaScript treats differently: a key that's absent and a key that's present with the value undefined. Without the flag, name?: string accepts { name: undefined }. That breaks PATCH semantics, because { ...user, ...patch } copies the key and wipes the value, leaving updated.name typed string and actually undefined. With the flag, name?: string means "absent or a string", and if you really mean to allow undefined, you write name?: string | undefined. This one does refuse to run without strictNullChecks (TS5052).

Worth knowing: tsc --init on both TS 6 and TS 7 now writes noUncheckedIndexedAccess: true and exactOptionalPropertyTypes: true into new configs, so new projects get them whether they know it or not. Both flags behaved identically on 6.0.3 and 7.0.2 in every test here.

Interview question: "What's the difference between prop?: string and prop: string | undefined?" The first lets the key be absent; the second requires the key but allows the value undefined. Without exactOptionalPropertyTypes, the first also accepts an explicit undefined, which is how a PATCH wipes a field through a spread. With the flag, an explicit undefined is rejected unless you add | undefined.
السؤال: "إيه الفرق بين prop?: string وprop: string | undefined؟" الأول بيسمح إن الـ key مايبقاش موجود، والتاني لازم الـ key بس القيمة ممكن تبقى undefined. من غير exactOptionalPropertyTypes الأول بيقبل undefined صريحة كمان، وده اللي بيخلي PATCH يمسح field من خلال spread. ومع الـ flag الـ undefined الصريحة بتترفض، إلا لو ضفت | undefined.

Part 4 — The other strict flags 🔴 Advancedالجزء 4 — باقي الـ strict flags

English

Each flag below prevents one specific bug, shown with its real run. All were tested on TS 7.0.2 and TS 6.0.3 with identical diagnostics.

  • noImplicitOverride (not in strict): every overriding member must say override. On its own the flag doesn't catch an orphaned method. It flags capture, the one that really overrides. Its value comes next: once everything is marked, renaming the base method turns override refund into TS4113. That check runs even without the flag, so the keyword is worth writing either way.
  • noPropertyAccessFromIndexSignature (not in strict): dot access is reserved for known properties, so a key from an index signature needs limits["maxRetires"]. It doesn't detect the typo by itself. It makes "this key is unchecked" visible, and the real fix is a type with known keys.
  • noFallthroughCasesInSwitch (not in strict): a non-empty case must end in break, return or throw. Empty cases that deliberately share a body are still fine.
  • useUnknownInCatchVariables (in strict): e in catch is unknown rather than any. Anything can be thrown, and a handler that assumes e.response.status crashes inside the catch and hides the original error. Remember that strict has been the default since TS 6, so with no setting at all, this is on.

  • noImplicitOverride (مش في strict): أي member بيعمل override لازم يقول override. الـ flag لوحده مش بيمسك الـ method اليتيمة، هو بيعلّم capture، اللي بتعمل override فعلًا. قيمته في الخطوة اللي بعدها: لما كله يبقى متعلّم، أي rename في الـ base بيخلي override refund تطلع TS4113. والفحص ده شغال حتى من غير الـ flag، فالكلمة تستاهل تتكتب في الحالتين.
  • noPropertyAccessFromIndexSignature (مش في strict): الوصول بالنقطة للـ properties المعروفة بس، فالـ key اللي جاي من index signature لازم يتكتب limits["maxRetires"]. هو مش بيكتشف الغلطة الإملائية لوحده، بس بيوضّح إن "الـ key ده مش متفحص"، والحل الحقيقي type بـ keys معروفة.
  • noFallthroughCasesInSwitch (مش في strict): الـ case اللي فيه كود لازم يخلص بـ break أو return أو throw. والـ cases الفاضية اللي بتشارك نفس الكود قصدًا لسه مقبولة.
  • useUnknownInCatchVariables (في strict): الـ e في catch نوعها unknown مش any. أي حاجة ممكن تترمي، والـ handler اللي بيفترض e.response.status بيقع جوه الـ catch نفسها وبيخبي الـ error الأصلي. وافتكر إن strict بقى الـ default من TS 6، فمن غير أي إعداد ده شغال.
فين هستخدمه في شغلي؟ noImplicitOverride: base class لـ payment providers، وحد عمل rename لـ refund، فـ Stripe بقى بيرد "not supported" والعملاء مش بياخدوا فلوسهم. noFallthroughCasesInSwitch: عميل دفع فجاله إيميل refund. useUnknownInCatchVariables: الـ gateway رمت string، فالـ catch وقعت وضاع الـ log بتاع الـ timeout الأصلي وقت الـ incident. وnoPropertyAccessFromIndexSignature: process.env.DATABSE_URL بغلطة إملائية بتعدّي من غير الـ flag، والحل الدائم validation بـ schema زي الدرس 08.
Trade-off: noPropertyAccessFromIndexSignature is the least valuable of the four It adds bracket noise and doesn't catch the typo; it only makes unchecked access visible. Turn it on last, or skip it if you've already replaced index signatures with known keys and validated env vars at startup.

Part 5 — Adopting strictness on an old codebase 🔴 Advancedالجزء 5 — إزاي تفعّل الـ strict على codebase قديم

English

Don't fix everything in one PR. It'll conflict with every open branch, it can't be reviewed, and the shortcuts people take under pressure (as any, !) leave you with the same bugs and less honest types. Instead, make the debt visible and stop it from growing. Here's the plan:

  1. Pin the starting point. strict has defaulted to true since TS 6, so an old project upgrading must set "strict": false explicitly and then flip each flag on purpose.
  2. Count errors per flag with a ladder, where each flag is added on top of the previous ones and only the increase is charged to it. Order matters: noUncheckedIndexedAccess shows nothing without strictNullChecks, so counting it alone gives a false zero.
  3. Add a ratchet. Save the current errors in a baseline file, keyed by file and error code rather than by line number, so unrelated edits don't invalidate it. CI fails on any new error, and the baseline only moves down.
  4. Turn on one flag at a time, starting with the cheapest and the most valuable, in small PRs by folder. A flag leaves the ladder once its count reaches zero, and goes into tsconfig.json for good.
  5. Use a per-folder config for new code so src/payments can be strict before the rest. The catch is real: tsc also reports errors in files that the folder imports, so below the strict payments config reports errors in orders. Either fix dependencies from the bottom up, or filter the report by path in your ratchet.
  6. Prefer @ts-expect-error over @ts-ignore when you must suppress. It fails with TS2578 once the error is gone, so stale suppressions can't pile up, whereas @ts-ignore stays silent forever and hides any future error on that line. Add a ticket number. typescript-eslint's ban-ts-comment (in the recommended set) rejects @ts-ignore.

Part 6 — Why tsc is slow, measured on TS 6 and TS 7 🔴 Advancedالجزء 6 — ليه الـ tsc بطيء، بالقياس على TS 6 و TS 7

English

Start with --extendedDiagnostics, which works on both compilers. Check time usually dominates. Read the counts before the times: Instantiations is how many times generic types were expanded, and in every run here it was identical on TS 6 and TS 7, on any checker count and under any load. That makes it the best number to track. Timings move with the machine.

To compare the compilers, a script generated 6,000 blocks of realistic code (interfaces, discriminated unions, mapped types, generics): 174,004 lines, 6.5 MB. It was then type-checked two ways, as one huge file and split into 300 files, with every scenario run in turn for 7 rounds so background load hit them equally. TS 7 was ≈3.2× faster on the single file and ≈7.5× on the same code split into files, ≈9× with --checkers 8. Microsoft reports 8–12× on real projects, and the split-file result lands near that. The lesson in the difference is about shape: TS 7 runs parallel checkers across files, so one giant generated file gets almost nothing from them. Here --singleThreaded barely changed the single-file time but made the multi-file run ≈2.5× slower. Memory dropped too, from ≈680 MB to ≈400–450 MB, as each compiler reports it.

What costs most in the checker is deep conditional types and large unions, covered with a real example in Part 7. Next comes the classic question of interface versus intersection, where the honest answer has two halves. On flat types the difference is small in time, even though the counts are clearly worse: +50% types, +63% assignability checks, about 5% more check time on TS 6. On deep chains, where each type builds on the last, intersections blow up: 80× more assignability entries, and check time ≈6× worse on TS 6 and ≈9× worse on TS 7. So don't rewrite your codebase over flat A & B, but do use interface extends for type hierarchies.

Two settings give big wins for free. skipLibCheck skips checking all .d.ts files, and on a small app importing Express, Fastify, Zod and React it cut the run ≈3× on TS 6 and ≈7× on TS 7, with Types dropping from 149,587 to 2,403 on TS 6. Its danger is that it covers your own .d.ts files too: an undefined type there silently becomes any. So keep your own types in .ts files. incremental stores state in .tsbuildinfo, so a no-change run does zero checking.

English

Here's a file of only 48 lines, a permission system. It builds a union of 23,040 strings and scans that union with a distributive conditional type (lesson 11) on every call to can(). --extendedDiagnostics raises the alarm: 8.8 million instantiations from one short file. --generateTrace <dir> then tells you where. It works on both compilers with different output: TS 6 writes trace.json and types.json, while TS 7 writes trace.json, one types_N.json per checker, and a legend.json. It slows the run down, so use it to investigate rather than in everyday CI.

trace.json is in Chrome's trace format, so you can open it in chrome://tracing or Perfetto. For a quick answer, either run @typescript/analyze-trace or read the JSON with a few lines of code as below. Both name the same spot: all the time is inside export const checks, at roughly the same cost for each can() call, and the biggest union in the types file has 23,040 members. That's the hot type.

Watch out for one TS 7 difference: in the trace, pos is a UTF-16 character offset on TS 6 but a UTF-8 byte offset on TS 7. analyze-trace 0.11 assumes characters, so on a file with non-ASCII text, such as your Arabic comments, it reports the wrong line on TS 7 traces: line 33 instead of 30. On an ASCII-only copy of the file it's correct. The script below handles both.

The fix isn't a smarter conditional type. It's a different data structure: a lookup table instead of a flat union, so PermissionTable[R][A] is one indexed access rather than a scan of 23,040 members. Same call sites, same errors caught, and instantiations go from 8,849,479 to 185. Note what TS 7 did not fix: on the slow file it was only ≈1.7× faster at the median. Everything happens in one file, so one checker does all the work. Native speed doesn't rescue a bad type; the fix was worth vastly more than the compiler upgrade.

// صلاحيات النظام: resource × action × scope = union ضخم
type Resource =
  | "orders" | "payments" | "invoices" | "users" | "tenants" | "products" | "carts" | "shipments"
  | "refunds" | "coupons" | "reports" | "webhooks" | "apiKeys" | "auditLogs" | "notifications" | "jobs";
type Action =
  | "read" | "create" | "update" | "delete" | "export" | "import" | "approve" | "reject"
  | "archive" | "restore" | "assign" | "share";
type Scope = "own" | "team" | "tenant" | "region" | "global" | "support" | "billing" | "sandbox";
type Env = "dev" | "staging" | "prod";
type Version = "v1" | "v2" | "v3" | "v4" | "v5";

// (1) الـ template literal بيضرب كل الاحتمالات في بعض: ⁦16 × 12 × 8 × 3 × 5 = 23,040 member⁩
export type Permission = `${Version}:${Env}:${Resource}:${Action}:${Scope}`;

// (2) بنعدّي على كل member في الـ union بـ infer: شغل تقيل لكل مرة بنستخدمها
type ActionsOf<R extends Resource, P extends string = Permission> =
  P extends `${string}:${string}:${R}:${infer A}:${string}` ? A : never;
type ScopesOf<R extends Resource, A extends Action, P extends string = Permission> =
  P extends `${string}:${string}:${R}:${A}:${infer S}` ? S : never;

// (3) الـ helper اللي بيتنادى في كل route
export function can<R extends Resource, A extends ActionsOf<R>>(
  resource: R,
  action: A,
  scope: ScopesOf<R, A>,
): string {
  return `${resource}:${action}:${scope}`;
}

Interview question: "The type-check got slow after a recent merge. How do you investigate?" Compare --extendedDiagnostics before and after, focusing on Instantiations and Types, since those don't depend on the machine. A big jump means a type problem rather than a code-size problem. Run --generateTrace, find the hot spot with analyze-trace or the JSON, and look at the biggest unions in the types file. Fix by changing the data structure, usually a lookup instead of a scan. Then add an instantiation budget in CI so it can't return.
السؤال: "الـ type-check بقى بطيء بعد merge قريب. هتحقق إزاي؟" قارن --extendedDiagnostics قبل وبعد، وركّز على Instantiations وTypes، لإنهم مش بيعتمدوا على الجهاز. لو فيه قفزة كبيرة يبقى المشكلة في type مش في حجم الكود. شغّل --generateTrace، ووصل للـ hot spot بـ analyze-trace أو الـ JSON، وبص على أكبر unions في ملف الـ types. الإصلاح بتغيير الـ data structure، غالبًا lookup بدل scan. وبعدها حط instantiation budget في الـ CI عشان ماترجعش.

Cheat sheet · الخلاصة

  • tsc and type-aware lint catch different bugs: 5 real bugs here, 0 tsc errors, 8 lint problems. strict-boolean-expressions and switch-exhaustiveness-check must be enabled by hand.
  • typescript-eslint 8.72 peers on typescript <6.1 and throws on TS 7, because 7.0 has no JS API. Setup: typescript → npm:@typescript/typescript6, @typescript/native → npm:typescript@7. Then tsc is TS 7 and tsc6 is TS 6.
  • esbuild/SWC/tsx don't check types: CI needs tsc --noEmit as a required step, plus tsc6 --stableTypeOrdering while you run both.
  • Project references: composite + references + tsc -b. An internal change doesn't rebuild dependents; a .d.ts change does.
  • noUncheckedIndexedAccess needs strictNullChecks or silently does nothing. exactOptionalPropertyTypes stops { ...user, ...patch } from wiping fields. tsc --init now enables both.
  • noImplicitOverride, noFallthroughCasesInSwitch and noPropertyAccessFromIndexSignature are outside strict; useUnknownInCatchVariables is inside. strict is the default since TS 6.
  • Old codebase: cumulative ladder, ratchet keyed by file + code, one flag at a time, small PRs. A folder config also reports errors in what it imports. @ts-expect-error, never @ts-ignore.
  • Track Instantiations rather than time: identical on TS 6 and TS 7 here, on any machine load.
  • TS 7 vs TS 6 on the same code: ≈3.2× as one huge file, ≈7.5× as 300 files. Parallelism is per file, so split giant generated files. A slow type gains only ≈1.7×.
  • Flat intersections cost little (≈5–20% check time); deep chains ≈6–9×. Use interface extends for hierarchies.
  • skipLibCheck: ≈3–7× faster, but your own .d.ts errors become silent any. incremental: a no-change run does zero checking.
  • --generateTrace works on both, with different files. On TS 7, pos is in bytes, so analyze-trace 0.11 gets lines wrong on non-ASCII files. Fix the data structure: lookup, not scan.

  • الـ intersections الـ flat تكلفتها قليلة (≈5–20% check time)، والسلاسل العميقة ≈6–9×. استخدم interface extends في الـ hierarchies.
  • skipLibCheck: أسرع ≈3–7×، بس errors ملفات .d.ts بتاعتك بتبقى any ساكتة. وincremental: التشغيل من غير تغيير مش بيعمل أي check.
  • --generateTrace شغال على الاتنين بملفات مختلفة. وعلى TS 7 الـ pos بالـ bytes، فـ analyze-trace 0.11 بيغلط في السطور على الملفات اللي فيها non-ASCII. وصلّح الـ data structure: lookup مش scan.
