Why this matters · ليه ده مهم

English

Every API contract, DTO, handler signature and React prop you write is built from the pieces in this lesson, and each piece has a sharp edge. A Record<string, number> price lookup hides an undefined that becomes NaN on an invoice. readonly stops less than people assume. An intersection silently turns a field into never. Overloads get written where a union would do, and optional fields get used where a discriminated union would make bad states impossible. "What's the real difference between interface and type?" is also on almost every TypeScript interview, and "they're basically the same" is the answer that fails.

بالعامية

كل API contract و DTO و handler signature و React prop بتكتبهم مبنيين من الحاجات اللي في الدرس ده، وكل حاجة فيهم ليها حرف حاد. الـ Record<string, number> بتاع الأسعار بيخبّي undefined بيتحول لـ NaN في الفاتورة. والـ readonly بيمنع أقل بكتير مما الناس فاكرة. والـ intersection ممكن يحوّل حقل لـ never من غير صوت. وناس بتكتب overloads في مكان union كفاية، وبتستخدم optional fields في مكان discriminated union كان هيخلي الحالات الغلط مستحيلة. وسؤال "إيه الفرق الحقيقي بين interface و type؟" موجود في أغلب الـ interviews بتاعة TypeScript، وإجابة "هما تقريبًا زي بعض" هي الإجابة اللي بتسقّط.

Part 1 — interface vs type, for real 🟢 Basicالجزء 1 — الـ interface والـ type: الفرق بجد

English

For a plain object shape the two are interchangeable: both describe the same values, both can be extended, and a class can implements either. The differences that matter in practice are these.

  • Declaration merging. Two interface Order blocks merge into one type; two type Invoice declarations are TS2300. Merging is the mechanism behind module augmentation, such as adding req.user to Express (lesson 07). It's also a trap: Notification already exists in the DOM lib, so reopening it globally adds your field to the browser's type, and your object is suddenly missing 17 properties.
  • extends vs &. extends checks compatibility at the declaration, so a conflicting field is TS2430 right there. & doesn't check anything at the declaration. The field quietly becomes number & string, which is never, and you find out at first use from a message that doesn't mention the cause.
  • Error messages. Interface errors tend to be shorter. In the code below, the same missing field gives one line for the extends version and two for the intersection.
  • What only type can do. Unions, tuples, aliases of primitives, template literal types, mapped and conditional types. An interface can't extend a union (TS2312), a class can't implement one (TS2422), and [K in ...] inside an interface is a cascade of errors starting at TS1169.
  • A subtle one. An object type alias is assignable to Record<string, string>; an interface with the same shape isn't (TS2345, "Index signature ... is missing"). Interfaces can gain members later through merging, so the compiler won't assume the shape is closed. You'll hit this when passing a typed object to a generic logger.
  • Performance. The TypeScript team's performance wiki recommends interfaces over intersections: relationships between named interfaces get cached, while intersections are rechecked constituent by constituent. It shows up in large codebases, not in a ten-file service. Lesson 10 measures it.

The practical rule: use interface for objects and classes that may be extended, and type for unions and everything else. Many teams use type by default and that works too. What matters is picking one and enforcing it, which the consistent-type-definitions rule in typescript-eslint can do.

بالعامية

في شكل object عادي الاتنين بيعملوا نفس الشغل: بيوصفوا نفس القيم، والاتنين بيتمدوا، والـ class تقدر تعمل implements لأي واحد فيهم. الفروق اللي بتفرق فعلًا هي دي:

  • الـ declaration merging. لو كتبت interface Order مرتين بيتدمجوا في نوع واحد؛ إنما type Invoice مرتين يبقى TS2300. والـ merging هو الآلية اللي وراها الـ module augmentation، زي إنك تضيف req.user على Express (الدرس 07). وهو كمان فخ: Notification موجودة أصلًا في الـ DOM lib، فلما تفتحها global إنت بتزوّد حقلك على نوع الـ browser، والـ object بتاعك فجأة ناقصه 17 property.
  • extends ضد &. الـ extends بيفحص التوافق عند التعريف، فالحقل المتعارض بيطلّع TS2430 في مكانه. الـ & مبيفحصش أي حاجة عند التعريف: الحقل بيبقى number & string يعني never من غير صوت، وبتعرف عند أول استخدام برسالة مش بتذكر السبب.
  • الـ error messages. رسايل الـ interface غالبًا أقصر. في الكود فوق، نفس الحقل الناقص طلّع سطر واحد مع extends وسطرين مع الـ intersection.
  • اللي الـ type بس بيعمله. الـ unions والـ tuples والـ aliases للـ primitives والـ template literal types والـ mapped والـ conditional types. الـ interface مبيعرفش يمد union (TS2312)، والـ class مبتعرفش تعمل implement لـ union (TS2422)، و [K in ...] جوه interface بتطلّع سلسلة errors أولها TS1169.
  • فرق خفي. الـ type alias لـ object بيدخل في Record<string, string>، إنما interface بنفس الشكل مش بيدخل (TS2345، "Index signature ... is missing"). السبب إن الـ interface ممكن ياخد members زيادة بعدين عن طريق الـ merging، فالـ compiler مش بيفترض إن شكله مقفول. وده هيقابلك لما تبعت object متنوّع لـ logger عام.
  • الـ performance. الـ wiki بتاع performance من فريق TypeScript بينصح بالـ interfaces بدل الـ intersections: العلاقات بين الـ interfaces المتسمية بتتعمل لها cache، أما الـ intersections فبتتفحص جزء جزء كل مرة. الفرق ده بيبان في الـ codebases الكبيرة، مش في service فيها 10 ملفات. الدرس 10 بيقيسه بالأرقام.

القاعدة العملية: interface للـ objects والـ classes اللي ممكن تتمد، و type للـ unions وكل حاجة تانية. فرق كتير بتستخدم type by default وده شغال برضه. المهم تختار واحدة وتطبقها، و rule اسمها consistent-type-definitions في typescript-eslint بتعمل ده.

فين هستخدمه في شغلي؟ User و Order والـ repository contracts: interface. و PaymentMethod و ApiResult و OrderStatus: type. ولما تعمل DTO بيغيّر نوع حقل، زي total من number لـ string، متعملش Order & { total: string } لأنه بيطلّع never. ولما يبان إن نوع عندك فيه حقول غريبة مش فاكر إنك كتبتها، دوّر على interface بنفس الاسم في .d.ts global. وسمّي أنواعك أسماء من الـ domain زي PushNotification بدل Notification عشان متخبطش في الـ DOM lib.

Part 2 — Index signatures, optional & readonly 🟢 Basicالجزء 2 — الـ index signatures والـ optional والـ readonly

English

Index signatures. { [sku: string]: number } and Record<string, number> are the same type, and it says something false: "every string is a key with a number". So prices["NOPE"] is typed number and is undefined at runtime. undefined * 2 is NaN, with no exception, and it flows to the invoice. strict does not catch this. noUncheckedIndexedAccess does, by making the read number | undefined (lesson 10).

A plain object has a second problem: it inherits from Object.prototype. With a client-supplied SKU, prices["constructor"] returns a function and passes an === undefined check. Map has neither problem: get() is honestly typed number | undefined, and there's no prototype to hit.

Two related rules. Record<OrderStatus, string> with a union key is the opposite of the lie above: every key is required (TS2741), which forces you to add a label whenever you add a status. And named properties alongside an index signature must fit it (TS2411).

Optional vs | undefined. couponCode?: string may be left out. couponCode: string | undefined must be written, even if the value is undefined. Use the second form when every construction site should make a decision: adding the field breaks each one at compile time. They differ at runtime too: in and Object.keys see an explicit undefined, JSON.stringify drops it, and spreading it overwrites. { ...saved, ...{ couponCode: undefined } } wipes the saved coupon, a real PATCH bug. exactOptionalPropertyTypes rejects the explicit undefined on a ? property.

readonly is shallow and compile-time only. It rejects order.total = 0, but order.customer.name = "..." and order.tags.push() compile. It also isn't checked on assignment: a readonly total object passes to a parameter typed { total: number }, and that function can mutate it. For a runtime guarantee use Object.freeze, which is also shallow (JS lesson 06). A recursive DeepReadonly comes in lesson 11.

Part 3 — Function types 🟢 Basicالجزء 3 — الـ function types

English

Parameters and returns. Parameter types are required; return types are inferred unless you write them (lesson 01, Part 7). dueDays = 30 is a default parameter: its type is inferred from the value, and callers may skip it or pass undefined to get the default. note?: string is optional, so it's string | undefined inside the function. ...tags: string[] collects the rest. A required parameter can't follow an optional one (TS1016).

Function type aliases. type PriceRule = (priceCents: number) => number names a signature. Any function assigned to it gets its parameter types from context, so you don't repeat them. A function with fewer parameters is accepted, the same reason arr.map((x) => ...) doesn't have to declare the index. A wrong parameter or return type is rejected.

Call signatures. Functions are objects and can have properties. interface RateLimiter { (userId: string): boolean; readonly limit: number } describes a function you can call that also has a .limit. Object.assign(fn, { limit }) is a clean way to build one.

void vs undefined. On a function declaration, : void forbids returning a value (TS2322). But a contextual () => void type accepts a function that returns anything. That's deliberate: otherwise ids.forEach((id) => out.push(id)) wouldn't compile, because push returns a number. void there means "the caller won't use the result", not "there is no result". The value really does come back at runtime, and the compiler stops you relying on it (TS1345, TS2322). undefined as a return type is stricter: the function really must return undefined, and since TS 5.1 it doesn't need a return statement.

Interview question "Why does a callback typed () => void accept a function that returns a number, when function f(): void { return 1 } is an error?" → Model answer: "In a contextual function type, void means the caller ignores the return value, so returning something is harmless. That keeps common code like forEach((x) => arr.push(x)) compiling. On a declaration, : void is a statement about that function's own body, so returning a value is a contradiction. The value still exists at runtime, and the type stops you using it."
السؤال: "ليه callback نوعه () => void بيقبل function بترجّع رقم، مع إن function f(): void { return 1 } error؟" ← الإجابة النموذجية: "في الـ contextual function type، الـ void معناها إن الـ caller بيتجاهل القيمة الراجعة، فرجوع حاجة مش بيضر. وده اللي بيخلي كود شائع زي forEach((x) => arr.push(x)) يتكمبل. إنما على الـ declaration، : void كلام عن body الـ function نفسها، فرجوع قيمة تناقض. والقيمة لسه موجودة في الـ runtime، والـ type بيمنعك تستخدمها."

Part 4 — Overloads & this typing 🟢 Basicالجزء 4 — الـ overloads وتحديد نوع الـ this

English

Overloads are several signatures for one implementation. They're worth it when the return type depends on the arguments: getOrders("id") returns one Order, getOrders(["a", "b"]) returns an array, and the caller needs no as and no narrowing. Only the overload signatures are visible to callers; the implementation signature is hidden and must cover all of them.

They have three limits. First, overloads don't distribute over a union: passing a string | string[] is TS2769, because no single signature accepts it. Second, the compiler only checks that the implementation is broadly compatible with each overload, not that it keeps each promise: parseAmount below claims to return number for a string and returns a string, with no error. Third, the first matching overload wins, so a general one placed first swallows the specific ones.

When a union is simpler. If the return type is the same whatever the input, overloads add nothing. formatPrice(amount: number | string): string is shorter and also accepts a value that is already number | string. Default to a union. Lesson 14 compares overloads with conditional return types.

this typing. A function can declare this as a fake first parameter: function markPaid(this: Order). It's erased from the emitted JS and takes no argument slot. It turns the lost-this bug (JS lesson 04) into a compile error, TS2684. Without it, a plain function using this is TS2683 under strict. Class methods don't get this protection by default: const f = service.label; f() compiles and crashes. Declaring this: CheckoutService on the method closes that hole, and in callbacks the practical fix is an arrow function.

interface Order {
  id: string;
}

  return typeof arg === "string" ? { id: arg } : arg.map((id) => ({ id }));
}

الـ overloads يعني كذا signature لـ implementation واحدة. بتستاهل لما الـ return type يكون تابع للـ arguments: getOrders("id") بترجّع Order واحد، و getOrders(["a", "b"]) بترجّع array، والـ caller مش محتاج as ولا narrowing. الـ caller بيشوف الـ overload signatures بس؛ والـ implementation signature مخفية ولازم تغطي كلهم.

ليهم 3 حدود. الأول: الـ overloads مش بتتوزع على union، فلو بعت string | string[] يبقى TS2769، لأن مفيش signature واحدة بتقبلها. التاني: الـ compiler بيتأكد بس إن الـ implementation متوافقة عمومًا مع كل overload، مش إنها بتنفذ كل وعد: parseAmount اللي فوق بتدّعي إنها بترجّع number لو دخلها string، وهي بترجّع string، ومفيش error. التالت: أول overload بيطابق هو اللي بيكسب، فلو حطيت العام الأول هيبلع الأنواع المحددة، زي describe اللي نوعها "something" وقيمتها الحقيقية text.

إمتى الـ union أبسط. لو الـ return type واحد مهما كان الـ input، الـ overloads مش بتضيف حاجة. formatPrice(amount: number | string): string أقصر، وبتقبل كمان قيمة نوعها number | string أصلًا. خلي الـ union هو الافتراضي. و الدرس 14 بيقارن الـ overloads بالـ conditional return types.

نوع الـ this. الـ function تقدر تعلن this كأول parameter وهمي: function markPaid(this: Order). بيتشال من الـ JS خالص ومش بياخد مكان في الـ arguments. وبيحوّل bug الـ lost this (درس JS رقم 04) لـ compile error اسمه TS2684. ومن غيره، function عادية بتستخدم this بتطلّع TS2683 تحت strict. والـ class methods مش بتاخد الحماية دي by default: const f = service.label; f() بيتكمبل ويقع. لما تكتب this: CheckoutService على الـ method الثغرة بتتقفل، والحل العملي في الـ callbacks هو arrow function.

فين هستخدمه في شغلي؟
  • الـ overloads: repository فيه findById(id) بترجّع User | null و findById(ids) بترجّع User[]. أو helper زي createElement("input") الـ return بتاعه تابع للـ tag. غير كده خليها union.
  • الـ this: Mongoose methods: schema.methods.fullName = function (this: UserDoc) { ... }، و Fastify handlers العادية اللي this فيها الـ instance.
  • الـ lost this: app.post("/checkout", service.handle) بيتكمبل وبيقع في أول request. اكتب (req, res) => service.handle(req, res)، أو أعلن this على الـ method فالـ compiler يمسكها.
Trade-off: overloads hide the implementation from the checker Overloads give callers a precise API, but the body is typed against the wide implementation signature, so a wrong branch won't be caught. Keep the body small and cover each overload with a test. If callers often hold a union, offer a union signature as well, or switch to one object parameter with a discriminated union (Part 7).
الـ overloads بتخبّي الـ implementation عن الـ checker: بتدي الـ caller واجهة دقيقة، بس الـ body بيتفحص على الـ implementation signature الواسعة، ففرع غلط مش هيتمسك. خلي الـ body صغير واكتب test لكل overload. ولو الـ callers غالبًا معاهم union، ضيف signature بـ union كمان، أو حوّلها لـ object parameter واحد بـ discriminated union (الجزء 7).

Part 5 — Union types 🟢 Basicالجزء 5 — الـ union types

English

A union A | B says the value is one of these types, and you don't know which yet. So until you narrow, you can only use what all members have: toString() works on string | number, toFixed() doesn't (TS2339). Inside if (typeof amount === "string") the compiler knows which one you have, and in the code after that branch it knows it's the other. Lesson 04 covers narrowing properly.

The union you'll write most is string | null, the result of a lookup. It forces a decision (TS18047 otherwise), and there are three standard answers: an early return or throw when "not found" means a 404, ?. when it's fine for the result to stay empty, and ?? when you have a fallback. Don't use || for that: it also replaces 0 and "", so a stored discount of 0 becomes 10 (JS lesson 01).

Array of a union vs union of arrays. (string | number)[] means each element may be either, so pushing either is fine. string[] | number[] means the whole array is one kind and you don't know which. Reading is safe: map, filter and length all work, and elements are string | number. Writing isn't: push would need a value that fits both, which is never (TS2345). When you meet the second form, normalize to one representation at the boundary.

type Amount = string | number;

  return amount.toString();

  return amount.toFixed(2);

الـ union A | B معناه القيمة واحدة من الأنواع دي، ولسه مش عارف أنهي واحدة. فلحد ما تعمل narrowing، مش هتقدر تستخدم غير اللي موجود في كل الأنواع: toString() شغالة على string | number، و toFixed() لأ (TS2339). وجوه if (typeof amount === "string") الـ compiler بيعرف إنت معاك إيه، وفي الكود اللي بعد الفرع ده بيعرف إنها التانية. الدرس 04 بيشرح الـ narrowing بالتفصيل.

أكتر union هتكتبها هي string | null، نتيجة أي بحث. بتجبرك تاخد قرار (وإلا TS18047)، وليها 3 إجابات معروفة: early return أو throw لما "مش موجود" معناها 404، و ?. لما عادي النتيجة تفضل فاضية، و ?? لما يكون عندك قيمة بديلة. ومتستخدمش || هنا: بتبدّل 0 و "" كمان، فخصم متخزن قيمته 0 بيبقى 10 (درس JS رقم 01).

array من union ضد union من arrays. (string | number)[] معناها كل عنصر ممكن يبقى أي واحد، فالـ push لأي نوع منهم تمام. إنما string[] | number[] معناها الـ array كلها نوع واحد ومش عارف أنهي واحد. القراية آمنة: map و filter و length كلهم شغالين، والعناصر نوعها string | number. الكتابة لأ: push محتاجة قيمة تركب على الاتنين، وده never (TS2345). ولما تقابل الشكل التاني، وحّد الشكل على الحدود.

فين هستخدمه في شغلي؟ const user = await users.findById(id) نوعها User | null: السطر اللي بعده if (!user) return res.status(404)...، وكل اللي تحته user نوعه User من غير !. وفي migration من IDs رقمية لـ UUIDs ممكن الـ API يرجّع string[] | number[]: حوّل كله لـ string[] في الـ client عند الباب، بدل ما كل الكود يتعامل مع الاحتمالين. وفي الـ code review، أي || على قيمة ممكن تبقى 0 أو string فاضية بصلها مرتين.

Part 6 — Intersection types 🟢 Basicالجزء 6 — الـ intersection types

English

A & B says the value is all of these types at once. For object types that combines the fields: Order & Timestamped has id, total, createdAt and updatedAt. It's how you add a capability to any type without changing it, and it's the natural return type of a helper like withTimestamps<T>(entity: T): T & Timestamped (generics are in lesson 05). The & is type-level only; merging the actual objects is the spread's job.

Conflicts don't produce an error at the declaration, and the result depends on what conflicts:

  • Primitives: string & number is never, because no value can be both.
  • The same field with two types: { total: number } & { total: string } keeps the object, and total alone becomes never.
  • The same field with conflicting literals: { status: "paid" } & { status: "pending" } reduces the whole object to never, since no such object can exist. That's the one case where the compiler explains itself: "The intersection ... was reduced to 'never' because property 'status' has conflicting types".

To change a field's type, remove it first: Omit<Order, "total"> & { total: string } (lesson 06).

interface Order {
  id: string;
  total: number;
}

interface Timestamped {
  createdAt: Date;
  updatedAt: Date;
}

// (1) الاستخدام الطبيعي: تضيف قدرة لأي نوع من غير ما تغيّره
type StoredOrder = Order & Timestamped;

// الـ & في الـ types بس: الدمج الفعلي في الـ runtime شغل الـ spread
function withTimestamps<T extends object>(entity: T, now: Date): T & Timestamped {
  return { ...entity, createdAt: now, updatedAt: now };
}

const stored: StoredOrder = withTimestamps({ id: "ord_1", total: 100 }, new Date("2026-11-01"));
console.log(stored.id, stored.createdAt.getUTCFullYear());
// → ord_1 2026

// (2) الـ primitives المتعارضة: مفيش قيمة تبقى string و number مع بعض
type Impossible = string & number;
// ✗ TS2322: Type '"ord_1"' is not assignable to type 'never'.
const nothing: Impossible = "ord_1";

// (3) نفس الحقل بنوعين: الحقل نفسه بس هو اللي بيبقى never
type TotalConflict = { total: number } & { total: string };
// ✗ TS2322: Type 'number' is not assignable to type 'never'.
const conflict: TotalConflict = { total: 100 };

// (4) الـ literals المتعارضة في حقل discriminant: الـ object كله بيبقى never
type PaidState = { status: "paid"; paidAt: Date };
type PendingState = { status: "pending"; dueAt: Date };
type BothStates = PaidState & PendingState;

// ✗ TS2339: Property 'status' does not exist on type 'never'.
//     The intersection 'BothStates' was reduced to 'never' because property 'status' has conflicting types in some constituents.
const readStatus = (state: BothStates) => state.status;
بالعامية

A & B معناه القيمة كل الأنواع دي مع بعض. في الـ object types ده بيجمع الحقول: Order & Timestamped فيه id و total و createdAt و updatedAt. وده الطريقة اللي بتضيف بيها قدرة لأي نوع من غير ما تغيّره، وهو الـ return type الطبيعي لـ helper زي withTimestamps<T>(entity: T): T & Timestamped (الـ generics في الدرس 05). والـ & موجودة في الـ types بس؛ دمج الـ objects نفسها شغل الـ spread.

التعارض مش بيطلّع error عند التعريف، والنتيجة بتعتمد على إيه اللي متعارض:

  • الـ primitives: string & number بتبقى never، لأن مفيش قيمة تبقى الاتنين.
  • نفس الحقل بنوعين: { total: number } & { total: string } الـ object بيفضل، و total لوحده بيبقى never.
  • نفس الحقل بـ literals متعارضة: { status: "paid" } & { status: "pending" } بيحوّل الـ object كله لـ never، لأن مفيش object كده ممكن يتوجد. ودي الحالة الوحيدة اللي الـ compiler بيشرح فيها نفسه: "The intersection ... was reduced to 'never' because property 'status' has conflicting types".

عشان تغيّر نوع حقل، شيله الأول: Omit<Order, "total"> & { total: string } (الدرس 06).

فين هستخدمه في شغلي؟ صف جاي من الـ DB: type OrderRow = Order & Timestamped & { tenantId: string }، فكل الجداول بتشارك نفس حقول الـ audit من غير تكرار. وفي Next، Props & { params: Promise<{ id: string }> } بيضيف على props موجودة. والغلطة المعتادة لما حد يدمج نوع API مع نوع DB: ApiOrder & DbOrder وفي واحد total نوعها string وفي التاني number؛ التعريف بيعدّي، والـ error بيطلع بعدين "not assignable to never". لما تشوف never في رسالة زي دي، دوّر على &.
What breaks: a never you didn't plan never in an error message on a plain assignment nearly always means an intersection conflict somewhere up the chain. In the editor, hover over the type alias and each field to find which one collapsed. If you're merging two independent shapes, prefer an interface ... extends, because then the conflict is reported where it was created.
إيه اللي بيكسر: لما تلاقي never في رسالة error على assignment عادي، ده غالبًا معناه تعارض intersection في مكان فوق في السلسلة. في الـ editor اعمل hover على الـ type alias وعلى كل حقل عشان تعرف مين اللي اتحوّل. ولو بتدمج شكلين مستقلين، الأحسن interface ... extends، لأن التعارض ساعتها بيتبلّغ في المكان اللي اتعمل فيه.
Interview question "A | B looks like it should have more properties than A & B. Why is it the other way round?" → Model answer: "Types are sets of values. A union is a bigger set, so I know less about any one value, and only shared members are safe until I narrow. An intersection is a smaller set: a value must satisfy both, so everything from both is available. That's also why string & number is never: the set is empty."

Part 7 — Discriminated unions, first look 🟢 Basicالجزء 7 — الـ discriminated unions: أول نظرة

English

A discriminated union is a union of object types that share one literal field, the discriminant. In { kind: "card"; last4: string } | { kind: "wallet"; phone: string }, the field kind tells the compiler which variant it has. switch (method.kind) narrows each branch, so method.last4 is only available under case "card". Before narrowing it's TS2339, and the message names the variant lacking it.

Compare the common alternative: one interface with kind and every other field optional. It compiles { kind: "card" } with no card data, and { kind: "wallet", last4, phone } with both. Every reader then needs a check, or a !, for a field that "should" be there. The discriminated union makes those states unrepresentable: a card with a phone doesn't compile (TS2353). This is the most useful pattern in TypeScript, and lesson 04 takes it further with full event unions and exhaustive checks.

// الحقل المشترك kind هو الـ discriminant: literal مختلف في كل variant
type PaymentMethod =
  | { kind: "card"; last4: string; expiry: string }
  | { kind: "wallet"; phone: string };

function describe(method: PaymentMethod): string {
  switch (method.kind) {
    case "card":
      // هنا الـ compiler عارف إنها card، فالـ last4 موجودة
      return `card ending ${method.last4}`;
    case "wallet":
      return `wallet ${method.phone}`;
  }
}

console.log(describe({ kind: "card", last4: "4242", expiry: "12/28" }));
// → card ending 4242
console.log(describe({ kind: "wallet", phone: "01000000000" }));
// → wallet 01000000000

// ✗ TS2339: Property 'last4' does not exist on type 'PaymentMethod'.
//     Property 'last4' does not exist on type '{ kind: "wallet"; phone: string; }'.
const beforeNarrowing = (method: PaymentMethod): string => method.last4;

// الحالة الغلط مش ممكن تتكتب أصلًا
// ✗ TS2353: Object literal may only specify known properties, and 'phone' does not exist in type '{ kind: "card"; last4: string; expiry: string; }'.
const invalid: PaymentMethod = { kind: "card", last4: "4242", expiry: "12/28", phone: "010" };

// ❌ البديل الشائع: كل حاجة optional في object واحد
interface PaymentLoose {
  kind: "card" | "wallet";
  last4?: string;
  expiry?: string;
  phone?: string;
}

// الحالتين دول غلط، والـ compiler ساكت
const noCardData: PaymentLoose = { kind: "card" };
const everything: PaymentLoose = { kind: "wallet", last4: "4242", phone: "010" };

function describeLoose(method: PaymentLoose): string {
  if (method.kind === "card") {
    // ✗ TS18048: 'method.last4' is possibly 'undefined'.
    return `card ending ${method.last4.slice(-4)}`;
  }
  return `wallet ${method.phone}`;
}

try {
  console.log(describeLoose(noCardData));
} catch (err) {
  console.log((err as Error).message);
  // → Cannot read properties of undefined (reading 'slice')
}
console.log(describeLoose(everything));
// → wallet 010

بالعامية

الـ discriminated union هو union من object types كلهم فيهم حقل literal مشترك اسمه الـ discriminant. في { kind: "card"; last4: string } | { kind: "wallet"; phone: string }، الحقل kind بيقول للـ compiler إحنا في أنهي variant. و switch (method.kind) بيضيّق كل فرع، فـ method.last4 متاحة تحت case "card" بس. وقبل الـ narrowing بتبقى TS2339، والرسالة بتذكر الـ variant اللي ناقصه الحقل.

قارن بالبديل الشائع: interface واحد فيه kind وكل الحقول التانية optional. ده بيتكمبل مع { kind: "card" } من غير بيانات كارت، ومع { kind: "wallet", last4, phone } والاتنين موجودين. وبعدين كل حد بيقرا لازم يعمل check أو يكتب ! على حقل "المفروض" يكون موجود، وفي الكود فوق ده وقع بـ TypeError. الـ discriminated union بيخلي الحالات دي مش ممكن تتكتب أصلًا: card فيها phone مش بتتكمبل (TS2353). وده أفيد pattern في TypeScript، و الدرس 04 بيكمّل فيه بـ event unions كاملة و exhaustive checks.

فين هستخدمه في شغلي؟ API response: { ok: true; data: Order } | { ok: false; error: string } بدل { data?: Order; error?: string }. Webhook من payment provider: كل type ليه payload مختلف. و Notifications: { channel: "sms"; phone } | { channel: "email"; address; subject } تتخزن في queue، والـ worker يعمل switch عليها. وفي Postgres بيقابله عمود kind و CHECK constraints، أو jsonb بنفس الشكل. ولما تشوف في review نوع فيه 5 حقول optional وكلها مربوطة بـ status، اقترح التحويل ده.

❌ Changing a field's type with &

❌ الـ & مش بيستبدل الحقل، بيدوّر على قيمة تبقى number و string مع بعض، فالحقل بيبقى never والـ error بيطلع بعيد عن السبب. ✅ Omit بيشيل الحقل القديم، وبعدها تعرّفه بالنوع الجديد، و extends بيتأكد إن مفيش تعارض تاني.

}
بالعامية

❌ 3 سطور signatures مش بتقول أي معلومة زيادة، وكمان بترفض قيمة نوعها number | string (TS2769). ✅ signature واحدة بـ union أقصر وبتقبل كل الحالات. الـ overloads تستاهل بس لما الـ return يتغيّر حسب الـ input.

❌ Optional fields for variants 
// الحقول optional: مين يضمن إن الـ card معاها last4؟
interface Payment {
  kind: "card" | "wallet";
  last4?: string;
  phone?: string;
}
const bad: Payment = { kind: "card", phone: "010" };
✅ A discriminated union 
// كل variant معاه حقوله بس، والتركيبة الغلط مش بتتكتب
type Payment =
  | { kind: "card"; last4: string }
  | { kind: "wallet"; phone: string };
// ✗ TS2353: Object literal may only specify known properties, and 'phone' does not exist in type '{ kind: "card"; last4: string; }'.
const bad: Payment = { kind: "card", phone: "010" };

Try it yourself · جرّب بنفسك

1. Where does the error appear? 🟢 easy Starting from the Refund interface below, write a version where amountCents is a string in three ways: with interface ... extends, with &, and one that actually works. Note exactly where each error appears and what it says.
من الـ Refund اللي تحت، اكتب نسخة فيها amountCents نوعها string بتلات طرق: بـ interface ... extends، وبـ &، وواحدة شغالة فعلًا. واكتب الـ error بيطلع فين بالظبط وبيقول إيه في كل حالة.
// عايزين نسخة من Refund فيها amountCents نوعها ⁦string (⁩زي اللي بيرجع من API قديم)
interface Refund {
  id: string;
  amountCents: number;
}

// (أ) اكتبها بـ interface ... extends Refund
// (ب) اكتبها بـ ⁦type ... = Refund & { ... }⁩
// (ج) اكتب نسخة شغالة فعلًا
Solution · الحل 
interface Refund {
  id: string;
  amountCents: number;
}

// (أ⁦) extends⁩: الـ error عند التعريف على طول
// ✗ TS2430: Interface 'PartialRefundA' incorrectly extends interface 'Refund'.
//     Types of property 'amountCents' are incompatible.
//     Type 'string' is not assignable to type 'number'.
interface PartialRefundA extends Refund {
  amountCents: string;
}

// (ب⁦) &:⁩ التعريف عدّى، والـ error بعدين عند الاستخدام
type PartialRefundB = Refund & { amountCents: string };
// ✗ TS2322: Type 'string' is not assignable to type 'never'.
const b: PartialRefundB = { id: "r_1", amountCents: "100" };

// (ج) لو عايز تغيّر نوع الحقل فعلًا: شيله الأول بـ Omit وبعدين ضيفه
type PartialRefundC = Omit<Refund, "amountCents"> & { amountCents: string };
const c: PartialRefundC = { id: "r_1", amountCents: "100" };
console.log(c);
// → { id: 'r_1', amountCents: '100' }
الـ (أ) بتطلّع TS2430 عند التعريف. والـ (ب) التعريف بيعدّي، والـ error عند أول object وبيقول never. والـ (ج) بـ Omit هي اللي بتغيّر النوع فعلًا.
2. A lookup that can't lie 🟡 medium Write reserve(sku: string, qty: number): number over a stock table where A1 has 3 units and B2 has 0. It returns the remaining stock. It must throw for "NOPE" and for "constructor", and it must report B2 as out of stock, not as an unknown SKU.
اكتب reserve(sku: string, qty: number): number على جدول مخزون فيه A1 رصيدها 3 و B2 رصيدها 0. بترجّع الرصيد الباقي. لازم ترمي مع "NOPE" ومع "constructor"، ولازم تقول إن B2 خلصت، مش إنها SKU مش معروفة.
Hint · تلميح Use a Map, and compare with === undefined. What would if (!stock) do with B2?
استخدم Map، وقارن بـ === undefined. طب if (!stock) هتعمل إيه مع B2؟
Solution · الحل 
const stockBySku = new Map<string, number>([
  ["A1", 3],
  ["B2", 0],
]);

function reserve(sku: string, qty: number): number {
  const stock = stockBySku.get(sku);
  // الـ ⁦=== undefined⁩ مهم: الـ B2 رصيدها 0 وده مش معناه إنها مش موجودة
  if (stock === undefined) throw new Error(`unknown sku: ${sku}`);
  if (stock < qty) throw new Error(`insufficient stock for ${sku}: ${stock}`);
  return stock - qty;
}

console.log(reserve("A1", 2));
// → 1

for (const sku of ["NOPE", "constructor", "B2"]) {
  try {
    reserve(sku, 1);
  } catch (err) {
    console.log((err as Error).message);
  }
}
// → unknown sku: NOPE
// → unknown sku: constructor
// → insufficient stock for B2: 0
لو كتبت if (!stock) كانت B2 هتطلع "unknown sku" لأن 0 قيمته falsy. و "constructor" بتترفض لوحدها لأن الـ Map مفيهاش prototype keys.
3. Overloads or a union? 🟡 medium Write a notification sender where "sms" requires a phone, and "email" requires an address and a subject. Do it twice: once as notify(channel, ...) with overloads, once as send(message) taking a discriminated union. Then call each one with a value whose channel is only known at runtime, and see which still compiles.
اكتب function بتبعت notifications: الـ "sms" لازم معاها phone، والـ "email" لازم معاها address و subject. اعملها مرتين: مرة notify(channel, ...) بـ overloads، ومرة send(message) بتاخد discriminated union. وبعدين ناد كل واحدة بقيمة الـ channel بتاعها معروف في الـ runtime بس، وشوف مين لسه بيتكمبل.
Solution · الحل 
// الحل 1: overloads، كل قناة ليها parameters مختلفة
function notify(channel: "sms", phone: string): string;
function notify(channel: "email", address: string, subject: string): string;
function notify(channel: "sms" | "email", to: string, subject?: string): string {
  return channel === "sms" ? `sms to ${to}` : `email to ${to}: ${subject}`;
}

console.log(notify("sms", "0100"));
// → sms to 0100
console.log(notify("email", "sara@shop.eg", "Invoice"));
// → email to sara@shop.eg: Invoice

// ✗ TS2345: Argument of type '"sms"' is not assignable to parameter of type '"email"'.
const wrong = notify("sms", "0100", "Invoice");

// الحل 2: discriminated union كـ parameter واحد: أقرب للـ JSON وبيتركّب أحسن
type Notification =
  | { channel: "sms"; phone: string }
  | { channel: "email"; address: string; subject: string };

function send(message: Notification): string {
  switch (message.channel) {
    case "sms":
      return `sms to ${message.phone}`;
    case "email":
      return `email to ${message.address}: ${message.subject}`;
  }
}

// الفرق: قيمة نوعها union بتعدّي هنا عادي، ومع الـ overloads كانت هتترفض
function fromQueue(job: Notification): string {
  return send(job);
}
console.log(fromQueue({ channel: "email", address: "sara@shop.eg", subject: "Paid" }));
// → email to sara@shop.eg: Paid
الاتنين بيمنعوا التركيبة الغلط. بس الـ discriminated union بيقبل قيمة نوعها Notification جاية من queue، أما الـ overloads فمحتاجة تعرف الـ channel وقت الـ compile. ولأن الـ job بتيجي كـ union، الحل التاني هو الأنسب في الـ worker.
4. In your project: remove the optional soup 🔴 project Find a type in your side project or at work with several optional fields tied to a status (Payment, Notification, Job). Rewrite it as a discriminated union, add a never check in the default branch, and fix what the compiler then flags. Count how many ?, ! and runtime checks disappeared.
دوّر على type في مشروعك الجانبي أو في الشغل فيه كذا حقل optional مربوطين بـ status (Payment أو Notification أو Job). اكتبه من جديد كـ discriminated union، وضيف فحص never في فرع default، وصلّح اللي الـ compiler هيطلّعه. وعدّ كام ? و ! و runtime check اختفوا.
Solution · الحل 
// قبل: ⁦{ status; paidAt?; failureReason?; refundedAt? }⁩ وكل الحقول ممكن تتجمع غلط
// بعد: كل حالة معاها الحقول بتاعتها بس
type Payment =
  | { status: "pending"; createdAt: Date }
  | { status: "paid"; createdAt: Date; paidAt: Date }
  | { status: "failed"; createdAt: Date; failureReason: string }
  | { status: "refunded"; createdAt: Date; paidAt: Date; refundedAt: Date };

function paymentLabel(payment: Payment): string {
  switch (payment.status) {
    case "pending":
      return "waiting for confirmation";
    case "paid":
      return `paid on ${payment.paidAt.toISOString().slice(0, 10)}`;
    case "failed":
      return `failed: ${payment.failureReason}`;
    case "refunded":
      return `refunded on ${payment.refundedAt.toISOString().slice(0, 10)}`;
    default: {
      // حالة جديدة من غير case هتبقى compile error هنا
      const unhandled: never = payment;
      return unhandled;
    }
  }
}

const now = new Date("2026-11-01T10:00:00Z");
console.log(paymentLabel({ status: "failed", createdAt: now, failureReason: "card_declined" }));
// → failed: card_declined
console.log(paymentLabel({ status: "refunded", createdAt: now, paidAt: now, refundedAt: now }));
// → refunded on 2026-11-01

// ✗ TS2353: Object literal may only specify known properties, and 'paidAt' does not exist in type '{ status: "pending"; createdAt: Date; }'.
const impossible: Payment = { status: "pending", createdAt: now, paidAt: now };
ده مثال على Payment. كل حالة بقى معاها الحقول اللي ليها معنى فيها بس، و paidAt على حالة pending مبقتش بتتكتب. ولو حد ضاف حالة جديدة، سطر الـ never هيطلّع compile error لحد ما يكتب لها case.

Cheat sheet · الخلاصة

  • interface merges and reports conflicts at the declaration; type does unions, tuples, mapped and conditional types. Rule: interface for extendable objects, type for the rest.
  • A type alias fits Record<string, T>; an interface doesn't. Avoid global names that exist in the DOM lib.
  • Record<string, T> lies: reads are typed T but may be undefined. Use Map or noUncheckedIndexedAccess. Plain objects also expose constructor.
  • Record<Union, T> is the opposite: every key is required. Use it for status labels.
  • x?: T may be absent; x: T | undefined must be written. An explicit undefined overwrites in a spread.
  • readonly is shallow, compile-time only, and not checked on assignment to a mutable type.
  • Contextual () => void may return anything; : void on a declaration can't. () => undefined must really return undefined.
  • Use overloads only when the return type depends on the arguments. They don't accept unions and don't verify the implementation. The general overload goes last.
  • this: T is a fake parameter that turns lost-this into TS2684. Class methods need it declared.
  • A | B: more values, fewer members. A & B: fewer values, more members. Conflicts become never.
  • Variants with optional fields become discriminated unions, and switch on the literal field narrows each branch.
بالعامية
  • الـ interface بيتدمج وبيطلّع التعارض عند التعريف؛ والـ type بيعمل unions و tuples و mapped و conditional types. القاعدة: interface للـ objects اللي ممكن تتمد، و type للباقي.
  • الـ type alias بيدخل في Record<string, T>، والـ interface لأ. وابعد عن الأسامي الـ global الموجودة في الـ DOM lib.
  • Record<string, T> بيكذب: القراية نوعها T وممكن تكون undefined. استخدم Map أو noUncheckedIndexedAccess. والـ objects العادية كمان فيها constructor.
  • Record<Union, T> العكس: كل key لازم يكون موجود. استخدمها لـ labels الـ status.
  • x?: T ممكن تتساب؛ و x: T | undefined لازم تتكتب. والـ undefined المكتوب بيمسح القديم في الـ spread.
  • الـ readonly سطحي، و compile-time بس، ومش بيتفحص لما تحطه في نوع mutable.
  • () => void الجاية من الـ context ممكن ترجّع أي حاجة؛ و : void على declaration لأ. و () => undefined لازم ترجّع undefined بجد.
  • الـ overloads بس لما الـ return يتغيّر حسب الـ arguments. مش بتقبل unions، ومش بتتأكد من الـ implementation. والـ overload العام في الآخر.
  • this: T parameter وهمي بيحوّل الـ lost this لـ TS2684. والـ class methods لازم تكتبه عليها.
  • A | B: قيم أكتر و members أقل. A & B: قيم أقل و members أكتر. والتعارض بيبقى never.
  • الـ variants اللي بـ optional fields تتحول لـ discriminated unions، و switch على الحقل الـ literal بيضيّق كل فرع.
