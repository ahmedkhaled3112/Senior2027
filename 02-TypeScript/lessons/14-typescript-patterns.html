Why this matters · ليه ده مهم

English

This lesson is where the type system stops being a topic and becomes design. The incidents these patterns prevent are ordinary ones: a password_hash in a JSON response because a row was returned directly, a shipped order with no payment because status was a loose string, a query that returns nothing because a shared builder was mutated, a process that dies after sending the response because an async listener rejected, a 500 where the customer should have seen "card declined". Senior interviews test the same thing: "make illegal states unrepresentable", "design a type-safe builder", "when would you use a Result over an exception?".

الدرس ده هو المكان اللي الـ type system بيبطل فيه يبقى موضوع بتذاكره، ويبقى design. والـ incidents اللي الـ patterns دي بتمنعها عادية جدًا: password_hash طلع في JSON response لأن row رجع زي ما هو، order اتشحن من غير دفع لأن الـ status كان string سايب، query بيرجع فاضي لأن builder مشترك اتعدّل، process بيموت بعد ما بعت الـ response لأن async listener رمى rejection، و500 في مكان المفروض العميل يشوف فيه "الكارت اترفض". وinterviews السنيور بتختبر نفس الحاجة: "make illegal states unrepresentable"، "صمّم type-safe builder"، "إمتى تستخدم Result بدل exception؟".

Part 1 — The API layer: rows, domain, DTOs, OpenAPI 🔴 Advancedالجزء 1 — الـ API layer: الـ rows والـ domain والـ DTOs و OpenAPI

English

An API has three shapes that look alike and change for different reasons. The row is what the database driver returns: snake_case, BIGINT as a string, internal columns included. The domain model is what your logic thinks in: bigint cents, a Date, camelCase. The DTO is your public contract: only JSON-safe types, only fields clients may see. Explicit mappers between them mean a migration doesn't change your API, and an API version doesn't touch your queries.

Why not return the row? Because structural typing lets you. UserRow has everything PublicUser has, so returning it from a function declared to return PublicUser compiles. The excess-property check only applies to fresh object literals, and JSON.stringify serializes what's there, not what the type says. The example below sends password_hash with no error anywhere. A mapper naming each field is the fix, because a new column can't leave without a decision. Domain objects leak differently: JSON.stringify throws on a bigint, and turns a Date into a string that the client's type still calls Date.

When the contract is an OpenAPI spec, openapi-typescript generates the types so that server and client can't drift apart silently. The output is plain .d.ts: an enum becomes a union, and format: date-time stays string, which is honest about what JSON delivers. openapi-fetch then types the path, params and response from those generated types. Generated types describe the contract; they don't check that a server keeps it, so validate at the boundary where it matters.

The real-world catch on TS 7: openapi-typescript 7.13 declares typescript: ^5.x and calls the old compiler API at runtime. With TS 7 next to it, npm i fails with ERESOLVE, and forcing it with --legacy-peer-deps crashes on ts.factory, because TS 7's main entry only exports the version (its new API lives under typescript/unstable/*). What works: run the generator with its own TS 5 through npx -p, commit the output, and type-check that output with TS 7. It also ran with TS 6.0.3 installed next to it, producing an identical file.

// (1) الـ row زي ما pg بيرجعه: snake_case، والـ BIGINT جاي string
interface OrderRow {
  id: string;
  customer_id: string;
  total_cents: string;
  currency: "EGP" | "USD";
  status: "placed" | "paid" | "refunded";
  created_at: Date;
  internal_note: string | null;
  stripe_charge_id: string | null;
}

// (2) الـ domain: الأنواع اللي البيزنس لوجيك بيفكر بيها
interface Money { readonly cents: bigint; readonly currency: "EGP" | "USD" }
interface Order {
  id: string;
  customerId: string;
  total: Money;
  status: OrderRow["status"];
  createdAt: Date;
  internalNote: string | null;
}

// (3) الـ DTO: الـ contract مع الـ client، وكل حاجة فيه JSON-safe
interface OrderDto {
  id: string;
  total: { amount: string; currency: Money["currency"] };
  status: OrderRow["status"];
  createdAt: string;
}

// الـ mapper الأول: من شكل الـ DB لشكل الـ domain
function toDomain(row: OrderRow): Order {
  return {
    id: row.id,
    customerId: row.customer_id,
    total: { cents: BigInt(row.total_cents), currency: row.currency },
    status: row.status,
    createdAt: row.created_at,
    internalNote: row.internal_note,
  };
}

// الـ mapper التاني: كل field طالع مكتوب بالاسم، فمفيش حاجة تتسرب بالغلط
function toDto(order: Order): OrderDto {
  const whole = order.total.cents / 100n;
  const fraction = (order.total.cents % 100n).toString().padStart(2, "0");
  return {
    id: order.id,
    total: { amount: `${whole}.${fraction}`, currency: order.total.currency },
    status: order.status,
    createdAt: order.createdAt.toISOString(),
  };
}

const row: OrderRow = {
  id: "ord_1", customer_id: "cus_9", total_cents: "15000", currency: "EGP", status: "paid",
  created_at: new Date("2026-11-01T10:00:00Z"), internal_note: "VIP refund risk", stripe_charge_id: "ch_123",
};

console.log(JSON.stringify(toDto(toDomain(row))));
// → {"id":"ord_1","total":{"amount":"150.00","currency":"EGP"},"status":"paid","createdAt":"2026-11-01T10:00:00.000Z"}

// الـ domain لو طلع مباشرة على الـ response: الـ bigint بيوقّع JSON.stringify
try {
  JSON.stringify(toDomain(row));
} catch (e) {
  console.log(String(e));
}

import type { components, paths } from "./api-types.d.ts";

type Order = components["schemas"]["Order"];
type GetOrder = paths["/orders/{id}"]["get"];
type OrderOk = GetOrder["responses"][200]["content"]["application/json"];
type OrderNotFound = GetOrder["responses"][404]["content"]["application/json"];
type OrderPathParams = GetOrder["parameters"]["path"];

type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

// الـ enum في الـ spec بقى union، والـ date-time فضل string زي ما بييجي في JSON
type _1 = Expect<Equal<Order["status"], "placed" | "paid" | "refunded">>;
type _2 = Expect<Equal<Order["createdAt"], string>>;
type _3 = Expect<Equal<OrderOk, Order>>;
type _4 = Expect<Equal<OrderPathParams, { id: string }>>;

// مفيش validation هنا: الـ types بتوصف الـ contract، مش بتتأكد إن الـ server ملتزم بيه
async function getOrder(baseUrl: string, id: OrderPathParams["id"]): Promise<OrderOk | OrderNotFound> {
  const res = await fetch(`${baseUrl}/orders/${encodeURIComponent(id)}`);
  return (await res.json()) as OrderOk | OrderNotFound;
}

بالعامية

أي API فيه 3 أشكال شبه بعض وبيتغيروا لأسباب مختلفة. الـ row هو اللي الـ DB driver بيرجّعه: snake_case، وBIGINT كـ string، ومعاه الـ columns الداخلية. الـ domain model هو اللي البيزنس لوجيك بيفكر بيه: cents بـ bigint، وDate، و camelCase. الـ DTO هو الـ contract العام: JSON-safe types بس، والـ fields اللي الـ client مسموحله يشوفها بس. والـ mappers الصريحة بينهم معناها إن الـ migration مش بتغيّر الـ API، و version جديد من الـ API مش بيلمس الـ queries.

طب ليه متبعتش الـ row وخلاص؟ لأن الـ structural typing بيسمحلك. UserRow فيه كل اللي في PublicUser، فلما ترجّعه من function نوعها PublicUser بيتـ compile. الـ excess-property check بيشتغل على object literal طازة بس، وJSON.stringify بيطلّع الموجود مش اللي الـ type قاله. المثال فوق بعت password_hash من غير أي error في أي حتة. الحل mapper بيكتب كل field بالاسم، فأي column جديد مش هيخرج من غير قرار. والـ domain objects بتسرّب بطريقة تانية: JSON.stringify بيرمي error على bigint، وبيحوّل Date لـ string والـ type عند الـ client لسه بيقول Date.

ولما الـ contract يبقى OpenAPI spec، openapi-typescript بيولّد الـ types، فالـ server والـ client مش بيبعدوا عن بعض في صمت. الناتج .d.ts عادي: الـ enum بيبقى union، وformat: date-time بيفضل string، وده صادق مع اللي JSON بيوصّله فعلًا. وبعدين openapi-fetch بيدّي types للـ path والـ params والـ response من نفس الملف. الـ types المتولّدة بتوصف الـ contract، بس مش بتتأكد إن الـ server ملتزم بيه، فاعمل validation عند الحدود في الأماكن المهمة.

المشكلة الحقيقية على TS 7: openapi-typescript 7.13 كاتب typescript: ^5.x وبينادي الـ compiler API القديم في الـ runtime. لو TS 7 جنبه، npm i بيفشل بـ ERESOLVE، ولو جبرته بـ --legacy-peer-deps بيقع على ts.factory، لأن الـ main entry بتاع TS 7 بيطلّع الـ version بس (الـ API الجديد موجود تحت typescript/unstable/*). اللي بينفع: شغّل الـ generator بـ TS 5 خاص بيه عن طريق npx -p، واعمل commit للناتج، واعمله type-check بـ TS 7. وكمان اشتغل مع TS 6.0.3 متسطب جنبه وطلّع نفس الملف بالظبط.

فين هستخدمه في شغلي؟ في أي GET /users/:id في Express أو Next route handler: الـ repository بيرجّع row، والـ service بيشتغل على domain، والـ controller بينادي toUserDto قبل res.json. وبكده لما زميلك يضيف reset_token في migration، مش هيطلع للـ client. ولو الفرونت والباك في repos منفصلة، حط خطوة في CI: npx -y -p typescript@5 -p openapi-typescript@7.13 openapi-typescript openapi.yaml -o api-types.d.ts وبعدها git diff --exit-code، فأي تغيير في الـ spec من غير ما الـ types تتحدث هيوقّف الـ PR. الغلطة الشائعة: res.json(row) عشان "الـ type مظبوط"، وهو فعلًا مظبوط، والـ data هي اللي بتتسرب.
Trade-off: three types for every entity Mappers are boilerplate, and for an internal admin CRUD with one consumer they rarely pay off. Keep them where the cost of a leak or a coupled migration is real: public APIs, money, PII. A cheaper middle ground: a Zod response schema also strips unknown keys (UserDto.parse(row) printed only id and email when run), at the price of a runtime parse per response.
الـ mappers كود زيادة، وفي admin CRUD داخلي ليه consumer واحد غالبًا مش بتجيب تمنها. خليها في الأماكن اللي التسريب أو الـ migration المربوطة بتكلّف فيها بجد: الـ public APIs، والفلوس، والـ PII. وفيه حل وسط أرخص: Zod response schema بيشيل الـ keys اللي مش معروفة برضه (UserDto.parse(row) طبع id وemail بس لما اتشغّل)، وتمنه parse في الـ runtime مع كل response.

Part 2 — State machines with discriminated unions 🔴 Advancedالجزء 2 — الـ state machines بالـ discriminated unions

English

Model state as flags and you get every combination, including nonsense. { isLoading: boolean; data?: Order; error?: string } has 8 combinations and only 4 mean anything, and { isLoading: true, data, error } compiles. Every consumer then has to guess which combinations can really happen. A discriminated union makes the illegal ones unrepresentable: each state carries exactly its own data, state.data exists only after narrowing to "success", and there's no ? or !. If you want stale data on screen during a reload, that's a new state with its own name (exercise 1), not another optional field.

The same idea scales to domain lifecycles. Give each status its own type, and write each transition as a function whose parameter is the allowed source state: ship(o: PaidOrder). Shipping a draft is then a compile error, and fields like paymentId are required from the moment they exist. A TRANSITIONS table declared with as const satisfies gives one definition for both the type (NextOf<S>) and the runtime check.

Know where this stops. An order loaded from the database is a wide AnyOrder, so you must narrow before a transition, and that status column should itself be validated at the boundary. Types also can't see concurrency: two requests can both load a placed order and both pay it. That's solved in the database, with a conditional UPDATE … WHERE status = 'placed' and a check on the affected row count. That statement wasn't executed for this lesson, since there's no Postgres on this machine.

type Status = "draft" | "placed" | "paid" | "shipped" | "cancelled";

  placed: ["paid", "cancelled"],
  paid: ["shipped", "cancelled"],

  cancelled: [],

لو عملت الـ state بـ flags هتاخد كل التركيبات، ومنها الكلام الفاضي. { isLoading: boolean; data?: Order; error?: string } فيه 8 تركيبات و4 بس ليهم معنى، و{ isLoading: true, data, error } بيتـ compile. وبعدها كل consumer لازم يخمّن أنهي تركيبة ممكن تحصل فعلًا. الـ discriminated union بيخلي الحالات الغلط مستحيل تتكتب: كل حالة شايلة الـ data بتاعتها بس، وstate.data موجودة بعد التضييق لـ "success" بس، ومفيش ? ولا !. ولو عايز تعرض data قديمة وإنت بتعمل reload، دي حالة جديدة باسمها (تمرين 1)، مش field optional زيادة.

ونفس الفكرة بتكبر مع دورة حياة الـ domain. ادّي كل status نوع خاص بيه، واكتب كل transition كـ function الـ parameter بتاعها هو الحالة المسموح تبدأ منها: ship(o: PaidOrder). كده شحن draft بقى compile error، و fields زي paymentId بقت required من أول لحظة موجودة فيها. وجدول TRANSITIONS المكتوب بـ as const satisfies بيدّيك تعريف واحد للنوع (NextOf<S>) وللفحص في الـ runtime.

واعرف ده بيقف فين. الـ order اللي جاي من الـ DB نوعه AnyOrder الواسع، فلازم تضيّق قبل أي transition، وعمود status نفسه لازم يتعمله validation عند الحدود. والـ types كمان مش شايفة الـ concurrency: اتنين requests ممكن يحمّلوا نفس الـ order وهو placed ويدفعوه الاتنين. وده بيتحل في الـ DB، بـ UPDATE … WHERE status = 'placed' مشروط مع فحص عدد الصفوف. والجملة دي متشغّلتش في الدرس ده، لأن مفيش Postgres على الجهاز.

فين هستخدمه في شغلي؟ في Next: أي component بيجيب data، بدل 3 useState لـ loading و data و error اعمل useReducer بـ RemoteData<Order>، ومفيش spinner هيفضل شغال جنب error message. وفي الباك: endpoint POST /orders/:id/ship بيحمّل الـ order، يضيّق بـ if (order.status !== "paid") return conflict، وبعدها ship(order, trackingNo). وبكده الغلطة الشائعة، إن حد ينادي ship من job تانية من غير ما يفحص، بقت compile error. وفي الـ DB نفسه حط الـ WHERE status = 'paid' عشان الـ race.

Part 3 — A type-safe query builder 🔴 Advancedالجزء 3 — query builder آمن بالـ types

English

A builder's type can carry state that accumulates as you chain. Here two pieces of state do the work. The first is the phase: EmptyQuery<DB> has only from(), so execute() doesn't exist until a table is chosen. The second is what's been selected: Query<Row, Sel> where each select returns Query<Row, Sel | C>, so the selection grows as a union. execute() computes its result from that: never means SELECT * and the whole row, anything else means Pick<Row, Sel>. The [Sel] extends [never] wrapper stops distribution.

where<C extends keyof Row & string>(column: C, op: OpsFor<Row[C]>, value: Row[C]) links all three arguments to the column. TS infers C from the first argument, then the operator and value types follow, so where("status", "=", "cancelled") and where("status", ">", "paid") fail for precise reasons.

Compile-time safety ends at the process boundary, so the runtime still has work to do. Values always go as $n parameters, and identifiers are always quoted, because a cast can bring a URL parameter past the types: the run below shows a DROP TABLE attempt turned into a harmless, odd column name. The single as in execute() is an honest trust point between the Schema type and the real table, which is why that type should be generated from the database.

Type-level code needs tests like any other code, and they run under tsc --noEmit. Expect<Equal<…>> pins the result types, and @ts-expect-error pins the invalid uses. If an invalid call starts compiling, the directive itself becomes an error (TS2578: Unused '@ts-expect-error' directive.), so the suite fails. A directive only proves that some error occurred, so the messages below were also checked once by removing the directives and comparing real output. Vitest's expectTypeOf also compiled under tsc on TS 7, as an alternative (only the type check was tried, not a Vitest run).

// الـ driver: الـ builder مش عارف Postgres، بياخد أي حاجة بتنفّذ SQL
export interface Driver {
  query(sql: string, params: readonly unknown[]): Promise<readonly unknown[]>;

// الـ operators حسب نوع الـ column: مفيش > على string
type OpsFor<V> = [V] extends [string] ? "=" | "!=" | "like"
  : [V] extends [number | Date] ? "=" | "!=" | ">" | ">=" | "<" | "<="
  : "=" | "!=";

// بيفرد Pick عشان الـ hover يبقى مقروء
type Prettify<T> = { [K in keyof T]: T[K] } & {};

// من غير select يبقى ⁦SELECT *⁩ والنتيجة الـ row كله
type ResultOf<Row, Sel extends keyof Row> = [Sel] extends [never] ? Row : Prettify<Pick<Row, Sel>>;

interface QueryState {
  readonly table: string;
  readonly columns: readonly string[];
  readonly wheres: readonly { column: string; op: string; value: unknown }[];
  readonly order: { column: string; dir: "asc" | "desc" } | null;
  readonly limit: number | null;
}

// الـ types مش موجودة في الـ runtime: اقفل الـ identifier بالـ quoting دايمًا
const quote = (name: string) => `"${name.replaceAll('"', '""')}"`;

// المرحلة 1: لسه مفيش table، فمفيش غير from أصلًا
export class EmptyQuery<DB> {
  readonly #driver: Driver;
  constructor(driver: Driver) {
    this.#driver = driver;
  }
  from<T extends keyof DB & string>(table: T): Query<DB[T], never> {
    return new Query<DB[T], never>(this.#driver, { table, columns: [], wheres: [], order: null, limit: null });
  }
}

// المرحلة 2: Row هو شكل الجدول، و Sel الـ columns اللي اتجمعت لحد دلوقتي
export class Query<Row, Sel extends keyof Row & string> {
  readonly #driver: Driver;
  readonly #state: QueryState;
  constructor(driver: Driver, state: QueryState) {
    this.#driver = driver;
    this.#state = state;
  }

  // كل select بيرجع type جديد: Sel بيكبر، و instance جديد خالص
  select<C extends keyof Row & string>(...columns: C[]): Query<Row, Sel | C> {
    return new Query<Row, Sel | C>(this.#driver, { ...this.#state, columns: [...this.#state.columns, ...columns] });
  }

  // نوع الـ value والـ op جايين من الـ column نفسه
  where<C extends keyof Row & string>(column: C, op: OpsFor<Row[C]>, value: Row[C]): Query<Row, Sel> {
    return new Query<Row, Sel>(this.#driver, { ...this.#state, wheres: [...this.#state.wheres, { column, op, value }] });
  }

  orderBy<C extends keyof Row & string>(column: C, dir: "asc" | "desc" = "asc"): Query<Row, Sel> {
    return new Query<Row, Sel>(this.#driver, { ...this.#state, order: { column, dir } });
  }

  limit(n: number): Query<Row, Sel> {
    return new Query<Row, Sel>(this.#driver, { ...this.#state, limit: n });
  }

  toSql(): { sql: string; params: unknown[] } {
    const { table, columns, wheres, order, limit } = this.#state;
    const params: unknown[] = [];
    const cols = columns.length ? columns.map(quote).join(", ") : "*";
    let sql = `SELECT ${cols} FROM ${quote(table)}`;
    if (wheres.length) {
      // الـ values دايمًا parameters: عمرها ما بتتلزق في الـ SQL
      const parts = wheres.map((w) => `${quote(w.column)} ${w.op} $${params.push(w.value)}`);
      sql += ` WHERE ${parts.join(" AND ")}`;
    }
    if (order) sql += ` ORDER BY ${quote(order.column)} ${order.dir === "desc" ? "DESC" : "ASC"}`;
    if (limit !== null) sql += ` LIMIT $${params.push(limit)}`;
    return { sql, params };
  }

  async execute(): Promise<ResultOf<Row, Sel>[]> {
    const { sql, params } = this.toSql();
    const rows = await this.#driver.query(sql, params);
    // الـ cast الوحيد: ثقة بين الـ Schema type والجدول الحقيقي، فخلي الـ type متولّد من الـ DB
    return rows as ResultOf<Row, Sel>[];
  }
}

Part 4 — Fluent APIs: this vs a new generic instance 🔴 Advancedالجزء 4 — الـ Fluent APIs: الـ this ضد instance جديد بـ generic جديد

English

There are two ways to type a chain. Returning this uses the polymorphic this type: a subclass method called mid-chain keeps the subclass type, whereas a hard-coded return type loses it and the next call fails (TS2339). It's the right choice when a call doesn't change what the object is: setting a header, adding a check. It can't express state changes, because this always has the same type arguments.

Returning a new generic instance is required when the type changes, as with select() in Part 3. It also buys immutability, and that's a runtime bug fix as well as a style choice. In the mutable version below, paid and refunded are the same object as the tenant base, so the query ends up asking for two statuses at once and returns nothing. The immutable builder has no such bug. The cost is an allocation per call, negligible next to a database round trip.

Reading the real libraries in node_modules shows both techniques, plus a third. Zod 4.6.7 mixes them: check() returns this because the output type doesn't change, while optional() returns ZodOptional<this>, a wrapper type around the current one. At runtime it clones: check calls this.clone(…) and optional calls optional(this). Drizzle 0.45.4 does something different: where() returns PgSelectWithout<this, TDynamic, 'where'>, an Omit that removes the method from the type, so calling it twice is a compile error, unless you opt out with $dynamic(). At runtime it mutates and returns this, so the type says one thing and the object does another. The run below proves it: limited === base is true, and base gained the limit.

Part 5 — Typed event emitters & typed config 🔴 Advancedالجزء 5 — الـ typed event emitters والـ typed config

English

A typed emitter is one mapped lookup: on<K extends keyof Events & string>(event: K, handler: (payload: Events[K]) => void). K is inferred from the event name, and Events[K] gives the handler its payload. Wrong names, incomplete payloads, and handlers that read a field from the wrong event are all compile errors. @types/node now supports this directly too: new EventEmitter<{ "order.paid": [Payload] }>(), with arguments as a tuple. Reach for a wrapper when you want a smaller API, such as a single payload or an on that returns an unsubscribe function. One trap: an interface doesn't satisfy Record<string, unknown> because interfaces have no implicit index signature (TS2344). Use a type alias or a wider constraint.

The types say nothing about runtime behaviour, and that's where emitters hurt. emit is synchronous: a throwing listener throws into the code that called emit (your checkout) and skips the remaining listeners. An async listener is accepted where void is expected, and if it rejects, nobody catches it: the process dies with an unhandled rejection after the response went out, as the transcript shows. Fix it with captureRejections: true and an error listener, or by catching inside the handler, and let @typescript-eslint/no-misused-promises flag the pattern. Also, this typing only covers one process: events crossing Redis or Kafka need a schema at the boundary.

Typed config combines Lesson 13's tools. as const satisfies Record<string, FeatureFlag> checks every entry against the shape, while keyof typeof FLAGS stays a real union, so isEnabled("newChekout") is a compile error. The order matters: as const goes on the literal and satisfies comes after it (the other way gives TS1355). Inline arrays stay assignable even to a mutable string[] in the config type, where they become a mutable tuple. A tuple already declared as const in a variable is readonly and fails with TS4104, so declare config types as readonly string[]. Combined with template literal parsing, even URL params are derived from the route table.

// الـ map: اسم الـ event وشكل الـ payload بتاعه، في مكان واحد
type OrderEvents = {
  "order.paid": { orderId: string; amountCents: number };
  "order.refunded": { orderId: string; reason: string };

// الـ wrapper: طبقة types رفيعة فوق EventEmitter الأصلي، ومفيش logic جديد
class TypedEmitter<Events extends Record<string, unknown>> {
  readonly #inner = new EventEmitter();

  // الـ K بيتـ infer من اسم الـ event، و ⁦Events[K]⁩ بيدي الـ handler الـ payload الصح
  on<K extends keyof Events & string>(event: K, handler: (payload: Events[K]) => void): () => void {
    const listener = handler as (payload: unknown) => void;
    this.#inner.on(event, listener);
    // بيرجّع unsubscribe: أسهل من إنك تحتفظ بالـ reference عشان off
    return () => this.#inner.off(event, listener);
  }

  emit<K extends keyof Events & string>(event: K, payload: Events[K]): boolean {
    return this.#inner.emit(event, payload);
  }
}

Part 6 — Overloads vs conditional return types 🔴 Advancedالجزء 6 — الـ overloads ضد الـ conditional return types

English

When a return type depends on an argument, you have two tools. Here's the same API, findOrder(id, { required }), written both ways. Overloads list each call shape and read well in the editor, one signature per use with its own JSDoc. A conditional return type is one generic signature that computes the answer: Found<R>.

Implementation pain. Neither is fully checked. In a conditional return, TS doesn't narrow the type parameter from a runtime check: after if (required) throw, return null still fails with TS2322, because R stays unresolved, so you need one honest as. (return order passes there only because Order fits both branches.) Overloads look safer since there's no cast, but the body is checked only loosely against them. The overload-lie example promises Order when required: true, returns null, compiles cleanly and crashes. Either way the promise is yours to keep, so test it.

Callers. This is where they differ. A boolean from a variable matches no overload (TS2769) unless you add a third, while the conditional distributes and gives the correct, safe Order | null. A generic wrapper can forward R through a conditional but can't forward through overloads. ReturnType on an overloaded function sees only the last signature. And for a wrong argument, the overload error reports only "the last overload", which here complains about false, while the conditional names the real requirement, boolean | undefined. Overloads scale badly too: n independent options can need up to 2n signatures.

لما نوع الرجوع يعتمد على argument، عندك أداتين. فوق نفس الـ API، findOrder(id, { required })، مكتوبة بالطريقتين. الـ overloads بتكتب كل شكل call لوحده وبتبقى مقروءة في الـ editor، signature لكل استخدام ومعاها JSDoc بتاعها. والـ conditional return type signature واحدة generic بتحسب الإجابة: Found<R>.

وجع الـ implementation. الاتنين مش مفحوصين بالكامل. في الـ conditional، TS مش بيضيّق الـ type parameter من فحص في الـ runtime: بعد if (required) throw، الـ return null لسه بتفشل بـ TS2322، لأن R فاضل مش محسوم، فلازم as واحد صريح. الـ callers. هنا الفرق الحقيقي. الـ boolean الجاي من متغير مش بيمشي مع أي overload (TS2769) إلا لو ضفت تالت، أما الـ conditional فبيتوزع وبيدّيك الإجابة الصح والآمنة Order | null. والـ wrapper الـ generic يقدر يعدّي R من خلال conditional، ومش هيقدر من خلال overloads. وReturnType على function فيها overloads بيشوف آخر signature بس. ولو الـ argument غلط، error الـ overload بيتكلم عن "آخر overload" بس، واللي هنا بيشتكي من false، بينما الـ conditional بيسمّي المطلوب الحقيقي boolean | undefined. والـ overloads كمان مش بتكبر كويس: n options مستقلين ممكن يحتاجوا لحد 2n signature.

Part 7 — Result types vs exceptions 🔴 Advancedالجزء 7 — الـ Result types ضد الـ exceptions

English

A throw doesn't appear in a function's type, so a caller can't see which failures to expect. A Result puts them in the signature: Promise<Result<Receipt, CheckoutError>>, where CheckoutError is a discriminated union in which each variant carries the data its caller needs (declineCode, available). The compiler then forces you to check ok before reading value, and an exhaustive switch at the HTTP edge turns each variant into a status code in one place. Add a variant and the assertNever line stops compiling until someone decides its status.

The dividing line: Result for expected domain outcomes where the caller has a distinct response, such as a declined card or missing stock. Exceptions for bugs and infrastructure failures, like a TypeError or a reset connection, where no caller nearby can do anything useful and the right behaviour is to log, alert and return a generic 500. chargeCard below shows the boundary technique: catch what the SDK throws, convert the known error to a Result, and rethrow everything else. In the run, tok_declined gets a 402 with a useful message, while tok_network and the null-deref bug reach the error middleware as 500s without leaking details.

A Result has real costs, and the examples show two that are easy to miss. First, it can be ignored: a forgotten await charge() compiles and the order gets marked paid. An exception can't be forgotten that way. The defence is to make the next step require the proof: markPaid(orderId, receipt) can't be called without the Receipt that only a checked ok provides. Second, transactions roll back on throw: returning a failed Result from a transaction callback is a normal return, so it commits the partial writes. Drizzle's tx.rollback() is itself just a throw. Inside a transaction, throw, and convert to a Result outside it.

The third cost is noise: if (!r.ok) return r at every layer. It pays off when callers really branch on the error type. If every layer just forwards it to a generic 500, that's an exception written the long way.

    return await withTx(async () => {
      const r = await work();
      if (!r.ok) throw new RollbackWith(r.error);

    });

    throw e;

بالعامية

الـ throw مش بيبان في نوع الـ function، فالـ caller مش شايف إيه الفشل المتوقع. الـ Result بيحطهم في الـ signature: Promise<Result<Receipt, CheckoutError>>، وCheckoutError عبارة عن discriminated union كل variant فيه شايل الـ data اللي الـ caller محتاجها (declineCode، available). وبعدها الـ compiler بيجبرك تفحص ok قبل ما تقرا value، وswitch exhaustive عند الـ HTTP edge بيحوّل كل variant لـ status code في مكان واحد. تضيف variant، وسطر assertNever يبطل يتـ compile لحد ما حد يقرر الـ status بتاعه.

الخط الفاصل: Result للنتايج المتوقعة في الـ domain اللي الـ caller عنده رد مختلف ليها، زي كارت مرفوض أو مخزون خلص. وexceptions للـ bugs ومشاكل الـ infrastructure، زي TypeError أو connection اتقطع، لأن مفيش caller قريب يقدر يعمل حاجة مفيدة، والصح إنك تعمل log و alert وترجّع 500 عامة. وchargeCard فوق بتوريك التكنيك عند الحدود: امسك اللي الـ SDK بيرميه، حوّل المعروف لـ Result، وارمي الباقي تاني. وفي التشغيل، tok_declined خد 402 برسالة مفيدة، وtok_network وباج الـ null وصلوا الـ error middleware كـ 500 من غير ما يسرّبوا تفاصيل.

والـ Result ليه تمن حقيقي، والأمثلة بتوريك حاجتين سهل تفوتهم. الأولى: ممكن يتساب من غير ما يتقرا: await charge() من غير فحص بيتـ compile والـ order بيتعلّم paid. والـ exception مش بيتنسي بالشكل ده. والحماية إن الخطوة اللي بعدها تطلب الإثبات: markPaid(orderId, receipt) مش هتتنادى من غير الـ Receipt اللي مبيجيش غير بعد فحص ok. التانية: الـ transactions بتعمل rollback على الـ throw: رجوع Result فاشل من transaction callback هو return عادي، فبيعمل commit للكتابة الجزئية. وحتى tx.rollback() بتاع Drizzle هو نفسه throw مش أكتر. فجوه الـ transaction ارمي، وحوّل لـ Result بره.

والتمن التالت هو الدوشة: if (!r.ok) return r في كل layer. بيجيب تمنه لما الـ callers يبقوا فعلًا بيتصرفوا حسب نوع الـ error. ولو كل layer بتعدّيه وخلاص لحد 500 عامة، يبقى ده exception مكتوب بالطريقة الطويلة.

فين هستخدمه في شغلي؟ الـ checkout هو المثال النموذجي: checkout() بترجّع Result، والـ controller بينادي toHttp، والفرونت بيفرّق بين "الكارت اترفض، جرّب كارت تاني" و"حصلت مشكلة". ولو الـ job في queue بتعمل charge، نوع الـ error بيحدد تعمل retry ولا لأ: card_declined مفيهاش retry، وECONNRESET تعدّي كـ exception والـ queue تعيدها. الغلطة الشائعة: catch (e) { return err({ type: "unknown" }) }، وده بيبلع الـ bugs جوه Result فالـ alerts متوصلش، والمشكلة تتكشف من شكاوى العملاء.
Interview question "Result types or exceptions?" → Both, for different things. Use Result for expected domain outcomes where the caller branches on the error, since they belong in the signature and can be handled exhaustively at the edge. Use exceptions for bugs and infrastructure failures, which should reach central logging. Convert at the boundary: catch known SDK errors into a Result and rethrow the rest. Watch two traps: an unchecked Result compiles, so make the next step require its value, and returning a failed Result inside a transaction commits, so throw inside the transaction.
"Result types ولا exceptions؟" ← الاتنين، كل واحد لحاجة. الـ Result للنتايج المتوقعة في الـ domain لما الـ caller يتصرف حسب الـ error، لأنها مكانها الـ signature وتتعالج exhaustive عند الـ edge. والـ exceptions للـ bugs ومشاكل الـ infrastructure، ولازم توصل للـ logging المركزي. والتحويل عند الحدود: امسك errors الـ SDK المعروفة وحوّلها لـ Result، وارمي الباقي تاني. وخد بالك من فخين: Result من غير فحص بيتـ compile، فخلي الخطوة اللي بعده تطلب قيمته. ورجوع Result فاشل جوه transaction بيعمل commit، فارمي جوه الـ transaction.

Solution · الحل 
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

// الـ Date بتتحول string زي ما JSON.stringify بيعمل، والـ bigint بيبقى never عشان بيوقّعه
type Jsonified<T> =
  T extends Date ? string
  : T extends bigint ? never
  : T extends readonly (infer U)[] ? Jsonified<U>[]
  : T extends object ? { [K in keyof T]: Jsonified<T[K]> }
  : T;

interface Order {
  id: string;
  createdAt: Date;
  total: { cents: bigint };
  items: { sku: string; shippedAt: Date | null }[];
}

type OrderJson = Jsonified<Order>;
type _1 = Expect<Equal<OrderJson["createdAt"], string>>;
type _2 = Expect<Equal<OrderJson["total"]["cents"], never>>;
type _3 = Expect<Equal<OrderJson["items"][number]["shippedAt"], string | null>>;

// الـ client كده مش هيقدر ينادي getTime على string
declare const fromApi: OrderJson;
// @ts-expect-error
fromApi.createdAt.getTime();

export type { _1, _2, _3 };
الـ conditional type بيتوزع على Date | null، فـ shippedAt بقت string | null. وترتيب الفحص مهم: لو الـ object جه قبل Date، الـ Date كان هيتحول لـ object مليان methods.

Cheat sheet · الخلاصة

  • Row, domain and DTO are three types with explicit mappers. Structural typing lets a row pass as a DTO, and JSON.stringify then sends every field.
  • openapi-typescript needs TS 5: on a TS 7 project, run npx -y -p typescript@5 -p openapi-typescript openapi-typescript …, commit the output, and type-check it with TS 7.
  • Replace flag combinations with a discriminated union. Each state carries its own data, and a stale-data reload is a new state, not a new optional field.
  • Lifecycle: one type per status, one function per allowed transition. Concurrency still needs a guarded UPDATE … WHERE status = ….
  • Builder: a separate type per phase, a generic that accumulates (Sel | C), and a result computed from it. At runtime, parameterize values and quote identifiers.
  • Test types with tsc --noEmit: Expect<Equal<…>> plus @ts-expect-error. Never assert on message text: TS 7 sorts unions differently from TS 6.
  • Return this when the type doesn't change; return a new generic instance when it does. Immutable builders are safe to reuse. Drizzle's aren't: it mutates and returns this.
  • Typed emitter: on<K extends keyof Events & string>, or new EventEmitter<Map>() from @types/node. emit is sync, a listener's throw reaches the caller, and async rejections crash the process.
  • Config: {…} as const satisfies Record<string, Config>, in that order. keyof typeof gives a real union.
  • Overloads for a few distinct shapes and per-shape docs. Conditional types for computed results, non-literal values and wrappers. Both trust the body, so test it. Consider two named functions first.
  • Result for expected domain errors with distinct responses. Exceptions for bugs and infrastructure. Convert at the boundary and rethrow the unknown.
  • Result traps: it can be ignored (make the next step require its value), and returning a failed one inside a transaction commits (throw inside, convert outside).
بالعامية
  • الـ row والـ domain والـ DTO يبقوا 3 types بـ mappers صريحة. الـ structural typing بيعدّي الـ row كـ DTO، وJSON.stringify بعدها بيبعت كل الـ fields.
  • openapi-typescript محتاج TS 5: في مشروع على TS 7، شغّل npx -y -p typescript@5 -p openapi-typescript openapi-typescript …، واعمل commit للناتج، واعمله type-check بـ TS 7.
  • بدّل تركيبات الـ flags بـ discriminated union. كل حالة شايلة الـ data بتاعتها، والـ reload بـ data قديمة حالة جديدة، مش optional field جديد.
  • دورة الحياة: type لكل status، و function لكل transition مسموح. والـ concurrency لسه محتاجة UPDATE … WHERE status = … مشروط.
  • الـ builder: type منفصل لكل مرحلة، و generic بيتجمع (Sel | C)، والنتيجة بتتحسب منه. وفي الـ runtime خلي الـ values parameters واعمل quoting للـ identifiers.
  • اختبر الـ types بـ tsc --noEmit: Expect<Equal<…>> مع @ts-expect-error. ومتعملش assert على نص الرسايل: TS 7 بيرتّب الـ unions غير TS 6.
