Why this matters · ليه ده مهم

English

Almost every screen you ship loads something from an API, and most production UI bugs live in the gap between "request sent" and "data on screen": a customer sees another customer's invoice because a slow response landed last, a "No orders" page appears during a 500, a single bad payload turns the whole app into a white page, a table jumps under the user's cursor. Next lesson hands most of the fetching to a library. This one writes it by hand first, because that's how you learn what the library actually solves and what stays your job: boundaries, loading UX and error UX are yours no matter which library you pick. The stale-response question and "what can't an error boundary catch?" are also standard interview questions.

بالعامية

تقريبًا كل شاشة بتطلّعها بتحمّل حاجة من API، ومعظم bugs الـ UI في production عايشة في المسافة بين "الـ request اتبعت" و"الـ data ظهرت": عميل بيشوف فاتورة عميل تاني عشان response بطيء وصل في الآخر، صفحة "No orders" بتظهر وقت 500، payload واحد بايظ بيقلب الـ app كله صفحة بيضا، جدول بيتنطر تحت الـ cursor بتاع اليوزر. الدرس الجاي هيسلّم معظم الـ fetching لمكتبة. الدرس ده بيكتبه بإيدك الأول، لأن كده بس هتعرف المكتبة بتحل إيه بالظبط، وإيه اللي هيفضل شغلك إنت: الـ boundaries والـ loading UX والـ error UX بتوعك أيًا كانت المكتبة. وسؤال الـ stale response وسؤال "الـ error boundary مبتمسكش إيه؟" بييجوا كتير في الـ interviews.

Part 1 — fetch in useEffect: what you build yourself 🟡 Intermediateالجزء 1 — الـ fetch جوه useEffect: اللي لازم تبنيه بإيدك

English

Write the hook once by hand. useOrders below is what most codebases start with: three useState calls and a promise chain, about 17 lines, to answer one question ("where is this request?"), and then every consumer repeats the same two ifs. The res.ok line is there because fetch only rejects on network failure and a 500 resolves normally; that trap is covered in JS lesson 14.

It works on a happy path, and that's the problem. It also has a bug you can't see in a demo: when url changes, isLoading never goes back to true, so the old rows stay on screen with no indicator. The obvious fix, setIsLoading(true) at the top of the effect, is now flagged by the react-hooks/set-state-in-effect rule from eslint-plugin-react-hooks 7. Part 3 shows a version that derives loading instead of storing it.

Then there's what the hook doesn't do at all. To measure that instead of guessing, this lesson uses a small lab script: it bundles a .tsx with esbuild, starts a real HTTP API on a free port, opens your installed Chrome headless through Playwright (channel: "chrome", so no browser download), runs a driver and shuts everything down. Each experiment is a name.tsx and a name.lab.mjs that exports entry, api and drive. The run below counts requests on the server: going back to a page refetches it and shows the loading text again, 3 widgets that need the same data make 3 requests, and one transient 503 leaves the user on an error screen because nothing retries.

import { useEffect, useState } from "react";

type Order = { id: string; total: number };

// الـ hook بإيدك: 3 useState عشان سؤال واحد بس هو "الـ request وصل فين؟"
function useOrders(url = "/api/orders") {
  const [orders, setOrders] = useState<Order[] | null>(null);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<Error | null>(null);

  useEffect(() => {
    fetch(url)
      .then((res) => {
        // الـ fetch مبيرفضش على 500، فلازم تشيك بنفسك
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json() as Promise<Order[]>;
      })
      .then(setOrders)
      .catch(setError)
      .finally(() => setIsLoading(false));
  }, [url]);

  return { orders, isLoading, error };
}

function OrdersTable({ url }: { url?: string }) {
  const { orders, isLoading, error } = useOrders(url);
  if (isLoading) return <p>Loading orders…</p>;
  if (error) return <p role="alert">Could not load orders: {error.message}</p>;
  return <p>{orders?.length} orders</p>;
}

export function api(req, res, url) {
  res.setHeader("content-type", "application/json");
  if (url.searchParams.has("flaky")) {
    // أول request بس بيقع بـ 503: حاجة عابرة، وretry واحد كان هيحلها

}

اكتب الـ hook بإيدك مرة. useOrders اللي فوق هو اللي معظم الـ codebases بتبدأ بيه: 3 useState وسلسلة promises، حوالي 17 سطر، عشان تجاوب على سؤال واحد ("الـ request وصل فين؟")، وبعدها كل consumer بيكرر نفس الـ 2 if. سطر res.ok موجود لأن fetch مبيرفضش غير لما الشبكة تقع، والـ 500 بترجع عادي؛ الفخ ده اتشرح في درس JS رقم 14.

Part 2 — Race conditions: the stale response wins 🟡 Intermediateالجزء 2 — الـ race conditions: الرد القديم هو اللي بيكسب

English

Every keystroke changes query, so every keystroke starts an effect and a request. The network doesn't promise that responses arrive in the order you sent them: a short prefix can be the slow one because it matches more rows. Each response calls setResult, so the last one to arrive wins, not the last one you asked for.

In the run below the backend takes 900 ms for in and 100 ms for everything else. Typing inv sends three requests, and the input ends on inv while the screen says in, permanently. Nothing logs an error, and no test that returns instantly will ever catch it.

The fix is a flag per effect run. Each effect has its own closure, and React runs the previous effect's cleanup before starting the next one, so setting ignore = true in the cleanup turns off exactly the request that's now out of date. That's the React shape of the general "only the latest wins" pattern from JS lesson 10, where it's a sequence number. The flag protects the screen only: the request still runs to the end and the server still does the work. Part 3 deals with that.

import { useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

type SearchResult = { query: string; invoices: string[] };

// ❌ مفيش حاجة بتمنع رد قديم إنه يكتب فوق رد أحدث
function useSearchRacy(query: string) {
  const [result, setResult] = useState<SearchResult | null>(null);
  useEffect(() => {
    if (!query) return;
    fetch(`/api/invoices?q=${encodeURIComponent(query)}`)
      .then((res) => res.json() as Promise<SearchResult>)
      .then(setResult);
  }, [query]);
  return result;
}

// ✅ كل effect عنده flag بتاعه، والـ cleanup بيقفله أول ما الـ query تتغير
function useSearchSafe(query: string) {
  const [result, setResult] = useState<SearchResult | null>(null);
  useEffect(() => {
    if (!query) return;
    let ignore = false;
    fetch(`/api/invoices?q=${encodeURIComponent(query)}`)
      .then((res) => res.json() as Promise<SearchResult>)
      .then((data) => {
        if (!ignore) setResult(data);
      });
    return () => {
      ignore = true;
    };
  }, [query]);
  return result;
}

const useSearch = location.search === "?fixed" ? useSearchSafe : useSearchRacy;

function SearchBox() {
  const [query, setQuery] = useState("");

      <p id="shown">results for: {result?.query ?? "-"}</p>
    </main>
  );
}

// الـ backend: حرفين "in" بياخدوا 900ms (scan تقيل)، وأي query تانية 100ms
export function api(req, res, url) {
  const q = url.searchParams.get("q");
  const delay = q === "in" ? 900 : 100;
  setTimeout(() => {
    res.setHeader("content-type", "application/json");
    res.end(JSON.stringify({ query: q, invoices: [`INV-${q}-1`] }));
  }, delay);
}

بالعامية

كل حرف بيغيّر query، يعني كل حرف بيشغّل effect وrequest. والشبكة مش بتوعدك إن الردود هتوصل بنفس ترتيب الطلبات: prefix قصير ممكن يبقى هو البطيء لأنه بيطابق صفوف أكتر. وكل رد بينده setResult، فاللي بيكسب هو آخر واحد وصل، مش آخر واحد إنت طلبته.

في الـ run اللي فوق الـ backend بياخد 900ms لـ in و100ms لأي حاجة تانية. كتابة inv بتبعت 3 requests، والـ input بينتهي على inv والشاشة بتقول in وتفضل كده. مفيش error في أي log، ومفيش test بيرد فورًا هيمسكها أبدًا.

الحل flag لكل تشغيلة effect. كل effect ليه closure بتاعته، وReact بيشغّل الـ cleanup بتاع الـ effect اللي فات قبل ما يبدأ اللي بعده، فلما تعمل ignore = true في الـ cleanup بتقفل بالظبط الـ request اللي بقى قديم. ده شكل React لنفس pattern "آخر طلب بس هو اللي يكسب" من درس JS رقم 10، اللي كان بـ sequence number هناك. الـ flag بيحمي الشاشة بس: الـ request بيكمّل لآخره والسيرفر بيعمل الشغل برضه. الجزء 3 بيتعامل مع ده.

فين هستخدمه في شغلي؟ مش في الـ search بس. أخطر مكان هو صفحة التفاصيل: admin panel فيه قايمة عملاء، اليوزر ضغط على عميل A وبعدين B بسرعة، ورد A وصل في الآخر. دلوقتي العنوان فيه اسم B والفواتير بتاعة A، ولو ضغط "Refund" هيعمله على الفاتورة الغلط. نفس الكلام في الـ pagination والـ tabs وأي tenantId بيتغير. أي effect بيعمل fetch وليه dependency بتتغير لازم يكون فيه الـ cleanup ده؛ لو شفت واحد من غيره في code review، ده تعليق blocking.

Part 3 — AbortController in the cleanup 🟡 Intermediateالجزء 3 — الـ AbortController في الـ cleanup

English

Create a controller in the effect, pass controller.signal to fetch, and call controller.abort() in the cleanup. Now the outdated request actually stops on the client: the connection closes, no more bytes are downloaded, the response is never parsed, and on HTTP/1.1 it frees one of the browser's 6 connections per host.

The trap: an aborted fetch rejects with a DOMException named AbortError, so a plain .catch(setError) shows your own cancellation to the user as a failure. In the run below the naive hook ends with correct results and Error: signal is aborted without reason on screen, because the rejection of the old request lands right after the new effect cleared the error. An abort isn't an error state: filter it by name and ignore it. The fixed hook also stops storing isLoading and setError(null) separately. It stores each result together with the query it belongs to, and anything that doesn't match the current query counts as "still loading". That's derived state, and it's also what satisfies the set-state-in-effect rule.

StrictMode gives you a free test of all this. In development React runs mount, cleanup, mount, so you get 2 fetches and 1 abort, and the UI must still end up correct. The server received 2 requests in every run here: the abort happens right after fetch starts, but the request can already be on its way. In production it's 1 fetch and 0 aborts.

Abort saves the client. The server keeps working unless it watches for the disconnect, and a POST that already reached the server isn't undone. After an aborted POST, the client doesn't know whether it happened, which is why writes need idempotency keys (JS lesson 10 covers cancellation on both sides, and next lesson applies the key to a mutation). If your code does more awaits after fetch, check signal.aborted before setting state, because abort can't reach into your own async steps.

بالعامية

اعمل controller جوه الـ effect، باصي controller.signal لـ fetch، ونادي controller.abort() في الـ cleanup. كده الـ request القديم بيقف فعلًا على الـ client: الـ connection بيتقفل، مفيش bytes زيادة بتتحمل، الرد مبيتعملوش parse، وعلى HTTP/1.1 بيفضّي واحد من الـ 6 connections اللي المتصفح بيسمح بيهم لكل host.

الفخ: الـ fetch الملغي بيرفض بـ DOMException اسمها AbortError، فـ .catch(setError) العادية بتعرض الإلغاء بتاعك إنت لليوزر على إنه فشل. في الـ run اللي فوق الـ hook الساذج خلص بنتايج صح ومعاها Error: signal is aborted without reason على الشاشة، لأن رفض الـ request القديم بيوصل مباشرة بعد ما الـ effect الجديد مسح الـ error. الـ abort مش حالة error: فلتره بالاسم وتجاهله. والـ hook المتصلّح كمان بطّل يخزّن isLoading ويعمل setError(null) لوحدهم: بيخزّن كل نتيجة مع الـ query بتاعتها، وأي حاجة مش مطابقة للـ query الحالية بتتحسب "لسه بيحمّل". ده derived state، وده كمان اللي بيرضّي rule الـ set-state-in-effect.

الـ StrictMode بيديك test ببلاش للكلام ده. في الـ development، React بيعمل mount ثم cleanup ثم mount، فبتاخد 2 fetches و1 abort، والـ UI لازم يخلص صح برضه. السيرفر استلم 2 requests في كل run هنا: الـ abort بيحصل بعد ما fetch يبدأ بلحظة، بس الـ request ممكن يكون طلع خلاص. في الـ production بيبقى fetch واحد ومفيش abort.

الـ abort بينقذ الـ client. السيرفر بيكمّل شغله إلا لو بيراقب قفل الـ connection، والـ POST اللي وصل السيرفر خلاص مبيترجعش. بعد POST ملغي، الـ client مش عارف هو اتنفذ ولا لأ، وعشان كده الـ writes محتاجة idempotency keys (درس JS رقم 10 بيغطي الإلغاء من الناحيتين، والدرس الجاي بيطبّق الـ key على mutation). ولو الكود بتاعك فيه awaits زيادة بعد fetch، شيّك على signal.aborted قبل ما تعمل set للـ state، لأن الـ abort مبيدخلش جوه خطواتك الـ async إنت.

فين هستخدمه في شغلي؟ صفحة تقارير: اليوزر طلب تقرير سنة كاملة بياخد 30 ثانية من Postgres، زهق ورجع غيّر الفلتر. من غير abort الـ query القديم بيفضل شغال وماسك connection من الـ pool، ومن الـ UI بتيجي تانية فوقه. مع abort من الـ client + res.on("close") في Fastify أو Express اللي بيلغي الـ query، الـ pool بيفضل فاضي. والغلطة الشائعة: تفتكر إن abort على POST /payments معناه إن الدفع اتلغى. مش كده: اعرض "جاري التأكد" واسأل السيرفر عن الحالة بالـ idempotency key.

Part 4 — Error boundaries 🟡 Intermediateالجزء 4 — الـ error boundaries

English

When a component throws during rendering and nothing catches it, React unmounts the whole tree (Part 5 shows the white page). An error boundary is a class component that catches errors from the tree below it. It has two methods with different jobs: static getDerivedStateFromError runs during the render phase, must be pure, and returns the state that shows the fallback; componentDidCatch runs during the commit phase and is where side effects like reporting go. There is still no hook equivalent: React 19.3 exports nothing for this, so it's the one place a modern codebase still has a class, or uses a library.

try/catch around JSX doesn't work, because <BrokenOrders /> only creates an object; the component runs later, when React renders it, long after your try has finished. The react-hooks/error-boundaries lint rule flags exactly this with "Avoid constructing JSX within try/catch".

Boundaries catch errors during render, in effects and in lifecycle methods below them, and in React 19 also errors thrown inside startTransition (lesson 19). They don't catch errors in event handlers, in async code such as setTimeout or a promise, during server rendering, or in the boundary itself. For handlers and async code you pass the error in yourself: store it in state and throw it during render, or use showBoundary from the library. On the server only a Suspense boundary catches: it sends the fallback and lets the client retry (lesson 21).

react-error-boundary 6 is the standard wrapper: FallbackComponent receives error and resetErrorBoundary (error is typed unknown, with a getErrorMessage helper), onError reports, resetKeys resets the boundary when a value changes, onReset tells you why it reset, and useErrorBoundary gives you showBoundary. Resetting remounts the children, so their effects run again and refetch. In the dashboard run below, one widget gets a broken payload and throws during render, another gets a 500 and uses showBoundary, and Revenue never notices. Retry fixes Orders, and switching tenants resets Payments through resetKeys.

import { Component, useEffect, useState, useTransition, type ErrorInfo, type ReactNode } from "react";

type State = { hasError: boolean; message: string };

// الـ class ده لسه الطريقة الوحيدة في React نفسها: مفيش hook بيعمل نفس الشغل
class ErrorBoundary extends Component<Props, State> {
  state: State = { hasError: false, message: "" };

  // الدالة دي بتتنده في الـ render phase: لازم تكون pure وترجّع الـ state الجديد بس
  static getDerivedStateFromError(error: unknown): State {
    return { hasError: true, message: error instanceof Error ? error.message : String(error) };
  }

  // الدالة دي بتتنده في الـ commit phase: مكان الـ side effects زي الـ logging
  componentDidCatch(error: unknown, info: ErrorInfo) {
    const frame = info.componentStack?.trim().split("\n")[0]?.trim().split(" (")[0];
    console.log(`[report] ${this.props.name}: ${String(error)} | ${frame}`);
  }

  render() {
    if (this.state.hasError) return <p role="alert">fallback: {this.state.message}</p>;
    return this.props.children;
  }
}

الـ try/catch حوالين JSX مبيشتغلش، لأن <BrokenOrders /> بيعمل object بس؛ الـ component بيتنفذ بعدين لما React يعمله render، بعد ما الـ try بتاعك يكون خلص من بدري. الـ lint rule اللي اسمها react-hooks/error-boundaries بتعلّم على ده بالظبط وبتقول "Avoid constructing JSX within try/catch".

الـ boundaries بتمسك الـ errors اللي في الـ render والـ effects والـ lifecycle methods تحتها، وفي React 19 كمان اللي بيترمي جوه startTransition (درس 19). بس مبتمسكش الـ errors في الـ event handlers، ولا في الـ async code زي setTimeout أو promise، ولا في الـ server rendering، ولا في الـ boundary نفسها. الـ handlers والـ async إنت اللي بتوصّل الـ error بتاعهم: تحطه في state وترميه في الـ render، أو تستخدم showBoundary من المكتبة. وعلى السيرفر الـ Suspense boundary بس هي اللي بتمسك: بتبعت الـ fallback وبتسيب الـ client يحاول تاني (درس 21).

Part 5 — Where boundaries go, and reporting 🟡 Intermediateالجزء 5 — الـ boundaries تتحط فين، والـ reporting

English

Place a boundary by asking "if this part dies, what can the user still do?" There are three useful levels. A root boundary is the last resort: a plain full-page message with a reload button. A route boundary keeps the header and navigation alive when a page fails, and should reset when the path changes (resetKeys={[pathname]}). A widget boundary isolates a non-critical card on a dashboard so a failing chart doesn't take the invoices with it. Fallbacks must be simple: an error thrown inside the fallback goes to the next boundary up, so a root fallback that depends on the broken auth context defeats the point.

With no boundary at all, React removes everything. The run below proves it: after one component throws, #root has length 0 and the user sees nothing, not even your header. With a boundary around the page, the header and navigation survive.

React 19 gives createRoot three reporting hooks, which is the right single place to connect your error tracker: onCaughtError (a boundary caught it; the default logs with console.error), onUncaughtError (no boundary, the tree is gone; the default calls reportError), and onRecoverableError (React recovered by itself; the default calls reportError). We triggered the last one two ways: a component that throws once during a concurrent render, which React re-renders synchronously, and a hydration mismatch, which makes React regenerate the tree on the client. If you also report from each boundary's onError, you'll count the same error twice, so pick one.

info.componentStack follows the tree, including DOM parents like section. captureOwnerStack() follows who rendered whom, which is usually what you want when debugging: here it points at InvoicePage. It's development only: in the production build of React the export is undefined (checked), so guard it with NODE_ENV or the error handler itself will crash.

  const message = error instanceof Error ? error.message : String(error);
  const stack = info.componentStack?.trim().split("\n").slice(0, 2).map((line) => line.trim().split(" (")[0]);

  if (process.env.NODE_ENV !== "production") {
    const owner = captureOwnerStack()?.trim().split("\n")[0]?.trim().split(" (")[0];
    console.log(`  ownerStack: ${owner ?? "null"}`);
  }
}

Trade-off: how granular? One boundary around everything means any small failure costs the whole page. A boundary around every table cell means dozens of tiny error messages and a repeated retry UI. Part 6 — Loading states without layout shift 🟡 Intermediateالجزء 6 — حالات الـ loading من غير layout shift

English

A spinner says "wait" and takes up almost no space; when the content arrives, everything below it jumps. A skeleton reserves the space the content will take, so nothing moves. We measured this in Chrome with a PerformanceObserver on layout-shift, using the same page and the same 500 ms API. Spinner then table: one shift, CLS 0.0943, almost the whole budget (web.dev calls 0.1 or less "good") from a single element. Fixed-size skeleton: 0. The number isn't magic: score = impact fraction × distance fraction. The footer (1264 × 100 px) moves 440 px in a 1280 × 720 viewport, so it touches 200 px of height before and after: (1264 × 200) / (1280 × 720) × 440 / 1280 = 0.0943.

A skeleton only works if it matches. Ours first had a 1 px border on each 48 px row with the default content-box, so each row was 49 px, the footer moved 10 px, and CLS was 0.0012: box-sizing: border-box took it to 0. If the skeleton shows 10 rows and the API returns 3, the footer jumps up: CLS 0.0720. Reserving the space with min-height on the container brings it back to 0. Lesson 24 covers CLS and the other vitals in depth.

Two more rules. Delay the spinner about 200 ms, because a spinner that flashes for 80 ms makes a fast app feel slow and jittery: with the delay, an 80 ms response shows no spinner and an 800 ms response shows it once. Keep the previous data on page change rather than blanking the table. In our run, blanking moved the Next button 438 px up under the user's cursor with a total shift of 0.4703; keeping the old rows with reduced opacity moved nothing. Note that official CLS excludes shifts within 500 ms of user input (hadRecentInput), which is why this script counts them all: the button still moved, whatever the metric says.

For accessibility, mark the updating region with aria-busy, hide decorative skeleton bars with aria-hidden, and give a spinner role="status". Screen reader support for aria-busy varies, so test it (lesson 16).

    console.log(`${mode.padEnd(15)} shifts=${shifts}  CLS=${total.toFixed(4)}`);
  }

Part 7 — Empty states and error UX 🟡 Intermediateالجزء 7 — الـ empty states وتجربة الأخطاء

English

Three booleans (isLoading, isError, isEmpty) give you 8 combinations and only 4 of them mean anything. A discriminated union makes the other 4 impossible to represent, and assertNever makes the render exhaustive: add a fifth status and tsc stops with TS2345 until you handle it. The technique is covered in TS lesson 04; here it becomes a small reusable DataView.

Empty isn't error, and empty isn't one thing. Zero orders because of a filter needs "Clear filter". Zero orders on a new account needs "Create your first order". Showing the same "No data" for both wastes the one moment the user is ready to act.

Map failures to what the user can do. The status code is for you; the user needs an action. Note how the failures reach you: an HTTP error resolves and you throw it yourself after checking res.ok, a timeout from AbortSignal.timeout rejects with a TimeoutError, and being offline rejects with TypeError: Failed to fetch (all confirmed in the run below). navigator.onLine === false reliably means offline, but true only means there's a network interface, not that your API is reachable.

Partial failure and honesty. When a panel fails, the others should keep working, which is why each panel owns its state here. Never swallow an error into an empty result: catch(() => []) tells the customer they have no orders during your outage, which is worse than an error message. Use role="alert" so screen readers announce the failure when it appears, and include a reference such as the request id so support can find it.

export class HttpError extends Error {
  status: number;
  body: unknown;
  requestId: string | null;
  constructor(status: number, body: unknown, requestId: string | null) {
    super(`HTTP ${status}`);
    this.name = "HttpError";
    this.status = status;
    this.body = body;
    this.requestId = requestId;
  }
}

export async function fetchJson<T>(url: string, init?: RequestInit): Promise<T> {
  const res = await fetch(url, init);
  if (!res.ok) {
    const body = await res.json().catch(() => null);
    throw new HttpError(res.status, body, res.headers.get("x-request-id"));
  }
  return res.json() as Promise<T>;
}

// الـ action هو اللي اليوزر يقدر يعمله: ده أهم من نص الـ error نفسه
export type UserAction = "sign-in" | "request-access" | "go-back" | "fix-fields" | "retry" | "wait-for-network";
export type UserError = {
  kind: "session" | "forbidden" | "not-found" | "validation" | "server" | "offline" | "timeout" | "unknown";
  message: string;
  action: UserAction;
  requestId?: string;
  fields?: Record<string, string>;
};

export function toUserError(err: unknown): UserError {
  // الـ AbortSignal.timeout بيرفض بـ DOMException اسمها TimeoutError
  if (err instanceof DOMException && err.name === "TimeoutError") {
    return { kind: "timeout", message: "This is taking longer than usual.", action: "retry" };
  }
  // الـ fetch بيرفض بـ TypeError لما الشبكة تقع أو الـ server ميتوصلش
  if (err instanceof TypeError) {
    return navigator.onLine
      ? { kind: "server", message: "We can't reach the server right now.", action: "retry" }
      : { kind: "offline", message: "You're offline. We'll retry when you're back.", action: "wait-for-network" };
  }
  if (err instanceof HttpError) {
    const requestId = err.requestId ?? undefined;
    if (err.status === 401) return { kind: "session", message: "Your session expired.", action: "sign-in" };
    if (err.status === 403) return { kind: "forbidden", message: "You don't have access to this.", action: "request-access" };
    if (err.status === 404) return { kind: "not-found", message: "This invoice no longer exists.", action: "go-back" };
    if (err.status === 422) {
      const fields = (err.body as { fields?: Record<string, string> } | null)?.fields;
      return { kind: "validation", message: "Please fix the highlighted fields.", action: "fix-fields", fields };
    }
    if (err.status >= 500) return { kind: "server", message: "Something went wrong on our side.", action: "retry", requestId };
  }
  return { kind: "unknown", message: "Something went wrong.", action: "retry" };
}

export type ViewState<T> =
  | { status: "loading" }
  | { status: "error"; error: UserError }
  | { status: "empty" }
  | { status: "ready"; data: T };

function assertNever(value: never): never {
  throw new Error(`Unhandled state: ${JSON.stringify(value)}`);
}

type DataViewProps<T> = {
  state: ViewState<T>;
  skeleton: ReactNode;
  empty: ReactNode;
  onRetry: () => void;
  children: (data: T) => ReactNode;
};

export function DataView<T>({ state, skeleton, empty, onRetry, children }: DataViewProps<T>) {
  switch (state.status) {
    case "loading":
      return <div aria-busy="true">{skeleton}</div>;
    case "error":
      return (
        <div role="alert">
          <p>{state.error.message}</p>
          {state.error.requestId && <p><small>Reference: {state.error.requestId}</small></p>}
          {state.error.action === "retry" && <button onClick={onRetry}>Try again</button>}
        </div>
      );
    case "empty":
      return <>{empty}</>;
    case "ready":
      return <>{children(state.data)}</>;
    default:
      // لو زوّدت حالة خامسة ونسيت الـ case بتاعها، الـ tsc بيقف هنا
      return assertNever(state);
  }
}

// الـ hook بيرجّع ViewState جاهزة، والـ reload بيغيّر الـ attempt فالـ effect يشتغل تاني
function useListResource<T>(url: string) {
  const [attempt, setAttempt] = useState(0);
  const [settled, setSettled] = useState<{ key: string; state: ViewState<T[]> } | null>(null);
  const key = `${url}#${attempt}`;

  useEffect(() => {
    const controller = new AbortController();
    fetchJson<T[]>(url, { signal: controller.signal })
      .then((data) => setSettled({ key, state: data.length === 0 ? { status: "empty" } : { status: "ready", data } }))
      .catch((err: Error) => {
        if (err.name !== "AbortError") setSettled({ key, state: { status: "error", error: toUserError(err) } });
      });
    return () => controller.abort();
  }, [url, key]);

  const reload = useCallback(() => setAttempt((n) => n + 1), []);
  const state: ViewState<T[]> = settled?.key === key ? settled.state : { status: "loading" };
  return { state, reload };
}

import { useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

type SearchResult = { query: string };

// الـ debounce بيقلل عدد الـ requests، بس مبيضمنش ترتيب الردود
function useDebounced(value: string, delayMs: number) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(timer);
  }, [value, delayMs]);
  return debounced;
}

function SearchBox() {
  const [text, setText] = useState("");
  const query = useDebounced(text, 300);
  const [result, setResult] = useState<SearchResult | null>(null);

  useEffect(() => {
    if (!query) return;
    fetch(`/api/invoices?q=${encodeURIComponent(query)}`)
      .then((res) => res.json() as Promise<SearchResult>)
      .then(setResult);
  }, [query]);

  return (
    <main>
      <input aria-label="Search invoices" value={text} onChange={(e) => setText(e.target.value)} />
      <p id="shown">results for: {result?.query ?? "-"}</p>
    </main>
  );
}

createRoot(document.getElementById("root")!).render(<SearchBox />);

export function api(req, res, url) {
  const q = url.searchParams.get("q");
  const delay = q === "in" ? 900 : 100;
  setTimeout(() => res.setHeader("content-type", "application/json").end(JSON.stringify({ query: q })), delay);
}

}

Cheat sheet · الخلاصة

  • By hand you get 3 useState and no cache, no dedup, no retry (measured: back navigation 2 hits, 3 widgets 3 hits, one 503 stays an error).
  • Any effect that fetches and has a changing dependency can show a stale response. Fix it with an ignore flag or abort in the cleanup. Debounce doesn't fix it.
  • AbortError isn't an error state: filter it by name. In Chrome the message is signal is aborted without reason.
  • Abort saves the client. The server keeps going unless it watches res.on("close"), and a POST isn't undone: writes need an idempotency key.
  • Store the result with its key and derive loading from it, instead of setLoading(true) in the effect (react-hooks/set-state-in-effect flags that).
  • Boundaries catch render, effects, lifecycle and startTransition. They don't catch handlers, async code, SSR or themselves. Use showBoundary, or set state and throw.
  • Levels: root, route (resetKeys={[pathname]}), widget. No boundary means #root is empty.
  • Report once, from createRoot: onCaughtError, onUncaughtError, onRecoverableError. captureOwnerStack is development only.
  • Spinner then table: CLS 0.0943. Matching skeleton: 0. Reserve space with min-height when the count varies.
  • Delay spinners about 200 ms. Keep previous data on page change and set aria-busy.
  • Four states in a union, rendered exhaustively. Empty because of a filter differs from empty on a new account. Map every failure to a user action, use role="alert", and never catch(() => []).
