Why this matters · ليه ده مهم

English

Server Components change where the line between backend and frontend sits. As a full-stack engineer that's your line to design: which code ships to the browser, what data crosses the network, and which functions become public endpoints. Get it right and heavy libraries stay off the client. Get it wrong and a passwordHash lands in the page source, or any logged-in user can delete another tenant's invoices.

This also has a production history. In December 2025 a CVSS 10.0 remote code execution hit this exact layer, followed by more patches through January 2026. So this lesson reads the real wire format, attacks a real Server Function, and treats patching as part of the job.

بالعامية

الـ Server Components بتغيّر مكان الخط اللي بين الـ backend والـ frontend. وإنت كـ full-stack ده الخط اللي إنت اللي بتصممه: أنهي كود بيروح للـ browser، وأنهي data بتعدّي الشبكة، وأنهي functions بتبقى public endpoints. لو عملتها صح، المكتبات التقيلة بتفضل بعيد عن الـ client. ولو غلط، passwordHash بيبان في الـ page source، أو أي مستخدم عامل login يقدر يمسح فواتير tenant تاني.

وليها تاريخ في production كمان. في ديسمبر 2025 حصل remote code execution بـ CVSS 10.0 في الطبقة دي بالظبط، وبعده patches تانية لحد يناير 2026. عشان كده الدرس بيقرا الـ wire format الحقيقي، وبيهاجم Server Function حقيقية، وبيتعامل مع الـ patching كجزء من الشغل.

Part 1 — The mental model 🔴 Advancedالجزء 1 — الـ mental model

English

The server renders a tree of components into a payload, not HTML. Where the tree contains a Client Component, the payload holds a reference: which file, which chunk, which export, plus its props. The client reads the payload, reconciles it into the React tree, loads the referenced chunks and hydrates those interactive parts. So: the server renders a tree, the client completes the interactive parts.

RSC isn't SSR. SSR (lesson 21) turns components into HTML so the first paint is fast, and every component's code still ships for hydration. RSC decides which components ship at all. They work together: Next.js produces the payload, renders HTML from it, and sends both.

'use client' marks a module boundary in the import graph, not a single component. That file and everything it imports become client code. The run shows it: format-price.ts has no directive but it's imported from add-to-cart.tsx, so its string is in .next/static. pricing-rules.ts also has no directive, but only a Server Component imports it, so it isn't.

Next.js 16.4 is the host here, and section 06 covers its framework details. The lab ran next build with TypeScript 6.0.3, and the same code also type-checks on TypeScript 7.

بالعامية

السيرفر بيعمل render لـ tree من الـ components وبيحولها لـ payload مش HTML. ولو في الـ tree فيه Client Component، الـ payload بيبقى فيه reference: أنهي ملف، وأنهي chunk، وأنهي export، ومعاهم الـ props. الـ client بيقرا الـ payload، ويعمل reconcile للـ React tree، ويحمّل الـ chunks المطلوبة، ويعمل hydrate للأجزاء الـ interactive دي. يعني: السيرفر بيعمل render لـ tree، والـ client بيكمّل الأجزاء الـ interactive.

الـ RSC مش SSR. الـ SSR (الدرس 21) بيحوّل الـ components لـ HTML عشان أول paint يبقى سريع، وكود كل component بيتبعت برضه للـ hydration. الـ RSC بيقرر أنهي components تتبعت أصلًا. والاتنين بيشتغلوا مع بعض: Next.js بيطلّع الـ payload، ويعمل منه HTML، ويبعت الاتنين.

'use client' بيحدد module boundary في الـ import graph، مش component واحد. الملف ده وكل اللي بيستورده بيبقوا client code. والـ run بيوريك ده: format-price.ts مفيهوش directive بس مستورد من add-to-cart.tsx، فالنص بتاعه موجود في .next/static. وpricing-rules.ts برضه مفيهوش directive، بس اللي بيستورده Server Component بس، فمش موجود.

الـ Next.js 16.4 هو الـ host هنا، والقسم 06 فيه تفاصيل الـ framework. والـ lab شغّل next build بـ TypeScript 6.0.3، ونفس الكود بيعدّي الـ type-check على TypeScript 7 كمان.

فين هستخدمه في شغلي؟ صفحة منتج فيها سعر وهامش ربح داخلي وزرار "أضف للسلة". الهامش محسوب بـ pricing-rules.ts فيه معادلة الشركة: لو الملف ده اتستورد من Server Component بس، المعادلة مش هتوصل للـ browser أبدًا. بس لو حد في الـ code review استورده من add-to-cart.tsx عشان يعرض رقم، المعادلة كلها هتروح الـ client bundle من غير أي error. عشان كده لما تراجع PR فيه 'use client'، بص على الـ imports بتاعة الملف مش الملف لوحده.
Interview question "What's the difference between SSR and Server Components?" → SSR makes HTML for the first paint, and all component code still ships to hydrate. Server Components never ship their code: they produce a payload with references to the Client Components that do ship. They're independent, and frameworks combine them.
"إيه الفرق بين SSR و Server Components؟" ← الـ SSR بيعمل HTML لأول paint، وكود كل الـ components بيتبعت برضه عشان الـ hydration. الـ Server Components الكود بتاعهم مبيتبعتش أبدًا: بيطلّعوا payload فيه references للـ Client Components اللي بتتبعت. الاتنين مستقلين، والـ frameworks بتجمعهم.

Part 2 — The boundary and serialization 🔴 Advancedالجزء 2 — الـ boundary والـ serialization

English

Props going from a Server Component to a Client Component cross the network, so they must be serializable. What crosses: JSON values, Date, Map, Set, BigInt, undefined, typed arrays, promises, React elements and Server Functions. What doesn't: plain functions and class instances. All eight props below reached the browser with the right type, including instanceof Date.

Everything you pass is public. A Client Component that only reads user.name still receives the whole object, because serialization can't know what the component will read. The run found passwordHash in both the payload and the HTML. The fix is a DTO: a function that names each field allowed to leave the server, so a new column can't leak by accident. React's taint APIs aimed at this are experimental, and they aren't exported from stable react 19.3.1 (ran).

The boundary has one more rule. A server module sees a 'use client' export as an opaque reference, so it can't reach inside. Select.Option is undefined on the server. Compound components with dots (lesson 15) therefore fail with the build error below. Use named exports such as SelectOption, or build the composed tree inside a Client Component.

Part 3 — No re-render, no state, smaller bundle 🔴 Advancedالجزء 3 — مفيش re-render ولا state، و bundle أصغر

English

A Server Component is a function that runs on the server and whose result is sent as data. It has no instance in the browser, so nothing can re-render it there: it has no state, no effects and no event handlers. It can be async and read a database directly. It only runs again when the server is asked for a new payload, through navigation, router.refresh() or revalidation.

That's why it shrinks the bundle: code that never re-renders in the browser doesn't need to be there. Using a hook in one is a real build error rather than a warning. The measurement below uses the same two libraries, marked and sanitize-html, on the same text. In a Server Component the page loaded 447 KB of JS, or 132 KB on the wire. In a Client Component it loaded 672 KB, or 210 KB on the wire: 225 KB more to parse and 78 KB more to download, for identical output.

The trade-off: every navigation becomes a server round trip. Clicking a link to a dynamic route fired a GET /promise?_rsc=…, and the links on the page also prefetched on load (4 requests before any click). You pay in server CPU and latency, you depend on the network, and a click can feel slower than a client-side route. Client state, in contrast, updates with no round trip at all.

Part 4 — Composition 🔴 Advancedالجزء 4 — الـ composition

English

A Client Component can't import a server module and keep it on the server: the import pulls that module into the client graph. It can receive a Server Component as children, because the parent Server Component renders it first and passes along the finished result. The Client Component just places it. So who imports decides where code runs, not who renders whom.

The run compares both on one page. With children, ShippingQuote stayed on the server: five clicks changed the button, the timestamp never changed, and there were zero requests. With a direct import, the timestamp changed on every click because the component now runs in the browser, its key landed in .next/static, and the page got a hydration error from Date.now(). Add import "server-only" to a sensitive module and this becomes a build error instead of a silent leak.

A warning on checking leaks by searching: my first version of this test used the key only in key.length > 0, and the minifier folded that to true, so the string vanished from the bundle. The search found nothing, yet the module was in the client graph. Treat the import graph as the truth, and use server-only as the guard.

Three patterns follow. Push 'use client' to the leaves: mark the small interactive part, not the page. Providers: a 'use client' wrapper takes children, so a Server Component layout can wrap the app without becoming a client tree. React 19.3 also lets a Server Component render <TenantContext value="acme"> directly, imported from a 'use client' module. The older .Provider form fails there, because .Provider is a dot into a client reference, as in Part 2. Passing a promise: don't await, pass the promise as a prop, and call use on the client. The shell goes out at ≈9 ms, and the data follows at ≈411 ms in the same response.

Part 5 — The RSC payload 🔴 Advancedالجزء 5 — الـ RSC payload

English

The payload format is called Flight: a stream of rows, each id:value, where values refer to other rows. This lets a slow part of the tree arrive later. You can produce it with no framework by using react-server-dom-webpack directly. It needs node --conditions react-server; without that flag react refuses to load in this mode and throws the error below.

Reading the production output from top to bottom: 1:"$Sreact.suspense" is a symbol. 4:I["$3",["cart-chunk","cart-chunk.js"],"AddToCart"] is a client reference: the module, the chunks to load, and the export name, with no code. Row 0 is the tree as React elements in the form ["$", type, key, props]. $L2 is a lazy hole to be filled by row 2, and $L4 is a lazy reference to the client component. $D… is a date. Row 2 arrives in a second chunk, about 100 ms later, when Items finishes. That's how Suspense streams without HTML.

Dev builds add debug rows with component names, stacks and timings, which is why the same output took 3542 bytes in dev and 445 in production. So read production output when you audit. In Next.js a request with the header RSC: 1 returns text/x-component. The HTML response carries the same payload inside self.__next_f.push(…) scripts, so the data sits in the page twice, as with hydration data in lesson 21: "Internal margin" appeared twice in the HTML.

This format is internal and has no version guarantee. Reading it is a debugging and audit skill. Don't parse it in your own code, and don't build on these row prefixes. The React docs say the underlying bundler APIs don't follow semver and may break between 19.x minors.

Part 6 — Server Functions 🔴 Advancedالجزء 6 — الـ Server Functions

English

Naming first. Until September 2024, React called all of these "Server Actions". They're now Server Functions, and a Server Action is a Server Function passed to an action prop or called from inside an action. So not every Server Function is an action. Older articles, and Next.js in many places, still say Server Actions. The next-action header below keeps the old word.

'use server' at the top of a file turns every export into an endpoint. Inside a function, it does that for one function. The client bundle never receives the function's code, only a reference: an id. Calling it from the client is an RPC over HTTP POST, as the log below shows: POST /notes with a next-action header holding the id, the arguments in the body, and a text/x-component response. Results use the same serialization as Part 2, and arguments use nearly the same one, without JSX.

Three things come with it. Forms work without JavaScript: with a Server Function in action, React renders hidden $ACTION_… inputs, so the form posts natively. With JS turned off, the note was saved and the page returned as text/html. Revalidation: revalidatePath makes the same response carry the updated page, so one round trip does both the mutation and the refresh. useActionState (lesson 19) gives you the returned state and a pending flag, in both modes.

One behaviour shapes how you use them. In Next.js, three parallel calls to a 200 ms function took ≈651 ms, with POSTs ≈219 and ≈433 ms apart: they run one after another. Combined with being uncacheable POSTs, that makes Server Functions a poor fit for reads. Read data in a Server Component, or a GET route if the client must fetch.

"use server";

الأسامي الأول. لحد سبتمبر 2024، React كان بيسميهم كلهم "Server Actions". دلوقتي اسمهم Server Functions، والـ Server Action هو Server Function بتتبعت لـ action prop أو بتتنادى من جوه action. يعني مش كل Server Function تبقى action. والمقالات القديمة و Next.js في حتت كتير لسه بيقولوا Server Actions. والـ header بتاع next-action اللي فوق لسه بالاسم القديم.

'use server' في أول الملف بيحوّل كل export لـ endpoint، وجوه function بيعمل ده للـ function دي بس. والـ client bundle عمره ما بياخد كود الـ function، بياخد reference بس: id. وندائها من الـ client هو RPC على HTTP POST، زي ما الـ log بيوريك: POST /notes ومعاه header next-action فيه الـ id، والـ arguments في الـ body، والرد text/x-component. والنتايج بتستخدم نفس الـ serialization بتاع الجزء 2، والـ arguments تقريبًا نفسه بس من غير JSX.

فيه 3 حاجات بتيجي معاها. الـ forms بتشتغل من غير JavaScript: لما تحط Server Function في action، React بيطلّع hidden inputs بتاعة $ACTION_…، فالـ form بيعمل POST عادي. ولما قفلنا الـ JS، الـ note اتحفظت والصفحة رجعت text/html. الـ revalidation: revalidatePath بيخلي نفس الـ response يجيب الصفحة المحدّثة، فـ round trip واحد بيعمل الـ mutation والتحديث مع بعض. useActionState (الدرس 19) بيديك الـ state اللي رجع و pending flag، في الحالتين.

وفيه سلوك بيحدد هتستخدمها إزاي. في Next.js، 3 calls بالتوازي لـ function بتاخد 200ms أخدوا ≈651ms، والـ POSTs بينهم ≈219 و≈433ms: بيشتغلوا ورا بعض. ومع إنهم POSTs مش بتتعمل cache، ده بيخلي الـ Server Functions اختيار وحش للقراية. اقرا الـ data في Server Component، أو GET route لو الـ client لازم يجيبها.

فين هستخدمه في شغلي؟ زرار "حفظ ملاحظة على الفاتورة" أو form لتعديل بيانات العميل: Server Function تحفظ الـ DB وتعمل revalidate، من غير ما تكتب API route و fetch و loading state بإيدك. بس لو عندك mobile app أو partner بيستخدم نفس الـ endpoint، اعمل REST API عادي (القسم 06 فيه الـ decision table)، لأن الـ id بيتغير مع كل build ومش contract ثابت. ولو حد استخدم Server Function عشان يجيب autocomplete results، هتلاقي الـ requests واقفة ورا بعض والبحث بطيء: دي غلطة شائعة في الـ code review.

Part 7 — Security 🔴 Advancedالجزء 7 — الـ security

English

Every Server Function is a public HTTP endpoint. It looks like a local function call, which is exactly why people forget. The React docs say arguments are fully client-controlled and must be treated as untrusted, and that each function must check that the logged-in user may perform the action. The UI showing only your own invoices doesn't protect anything, because the attacker doesn't use your UI.

The attack below needs no special tooling. The action id sits in public JavaScript. Alice, logged in to tenant acme, sends a plain fetch with that id and [201], which is another tenant's invoice, and it's deleted. It worked with no cookie at all too. The fix has a fixed order in every function: authenticate from the server-side session, validate with a schema on unknown input, and authorize by putting the tenant in the query itself. All four attacks then failed, and the owner's own delete still worked.

Next.js adds a CSRF check by comparing Origin with Host: a request from evil.test got a 500 here. That stops other websites, not a logged-in user with a script. Closed-over variables in an inline Server Function travel through the client encrypted, and the marker string wasn't in the payload; multiple instances need a shared key. Encryption hides the values but doesn't authorize anything.

Real incidents. Flight decoding is itself attack surface, because it parses attacker-controlled bytes on your server. The table lists what was published. Apps with no server, or with no framework or bundler supporting RSC, weren't affected. The React team warned that an app may be vulnerable even with no Server Functions of its own, if it supports Server Components. The first fixes for the denial of service were incomplete, so there were three patch rounds in eight weeks. Versions 19.0.4, 19.1.5 and 19.2.4 are the final safe ones for all five.

The ops lesson is patch speed, and knowing what to check. npm ls react-server-dom-turbopack printed (empty) in a Next.js app, because Next.js carries its own copy in next/dist/compiled: here React 19.3.0-canary-278794d7-20261002, while the installed react is 19.3.1. So for Next.js you check and upgrade next. For other setups you run npm ls react-server-dom-webpack react-server-dom-parcel react-server-dom-turbopack.

بالعامية

كل Server Function هي public HTTP endpoint. شكلها function call عادي، وده بالظبط اللي بيخلي الناس تنسى. docs بتاعة React بتقول إن الـ arguments في إيد الـ client بالكامل ولازم تتعامل معاها كـ untrusted، وإن كل function لازم تتأكد إن المستخدم اللي عامل login مسموح له بالـ action ده. وإن الـ UI بيعرض فواتيرك بس، ده مش بيحمي حاجة، لأن المهاجم مش بيستخدم الـ UI بتاعك.

الهجوم اللي فوق مش محتاج أي أدوات. الـ action id موجود في JavaScript عام. Alice، عاملة login في tenant acme، بتبعت fetch عادي بالـ id ده و[201]، وده فاتورة tenant تاني، فبتتمسح. واشتغل كمان من غير cookie خالص. والحل ليه ترتيب ثابت في كل function: authenticate من الـ session اللي على السيرفر، وvalidate بـ schema على input نوعه unknown، وauthorize بإن الـ tenant يبقى جوه الـ query نفسها. وبعدها الـ 4 هجمات فشلوا، والمالك قدر يمسح فاتورته عادي.

Next.js بيضيف CSRF check بيقارن Origin بـ Host: request من evil.test طلّع 500 هنا. ده بيوقف المواقع التانية، مش مستخدم عامل login ومعاه script. والمتغيرات اللي الـ inline Server Function ماسكاها بتعدّي من الـ client مشفّرة، والنص المميز مكانش في الـ payload، والـ instances الكتير محتاجة key مشترك. والتشفير بيخبّي القيم بس، ومش بيعمل authorization.

حوادث حقيقية. فك الـ Flight نفسه attack surface، لأنه بيفك bytes في إيد المهاجم على سيرفرك. الجدول فيه اللي اتنشر. الـ apps اللي مفيهاش سيرفر، أو مفيهاش framework أو bundler بيدعم RSC، متأثرتش. وفريق React حذّر إن الـ app ممكن يبقى vulnerable حتى لو مفيش Server Functions بتاعته، طالما بيدعم Server Components. وأول fixes للـ DoS مكانتش كاملة، فبقوا 3 جولات patches في 8 أسابيع. والإصدارات 19.0.4 و19.1.5 و19.2.4 هي الآمنة نهائيًا من الـ 5 كلهم.

الدرس في الـ ops هو سرعة الـ patch، وإنك تعرف تبص على إيه. npm ls react-server-dom-turbopack طلّع (empty) في Next.js app، لأن Next.js معاه نسخته في next/dist/compiled: هنا React 19.3.0-canary-278794d7-20261002، وreact المتسطب 19.3.1. فلـ Next.js بتبص على next وترقّيه. ولأي setup تاني بتشغّل npm ls react-server-dom-webpack react-server-dom-parcel react-server-dom-turbopack.

فين هستخدمه في شغلي؟ في أي PR فيه 'use server'، راجع زي ما بتراجع Express route جديد: مين بينادي؟ الـ input متفحوص؟ الـ tenant جاي من الـ session ولا من الـ args؟ والـ tenantId جاي من الـ client عمره ما يتصدق (قسم Node والقسم 06 فيهم التفاصيل). وللـ ops: Renovate أو Dependabot على next و pipeline يقدر يعمل deploy في نفس اليوم، لأن الـ RCE لما اتعلن كان الوقت بيتحسب بالساعات. وخلي الـ secrets في process.env مش مكتوبة في كود الـ function.
What breaks at scale Rate limits and audit logs from your API gateway don't automatically cover Server Functions, because they're POSTs to page URLs rather than to /api/*. A rule on /api/* misses them. Add rate limiting and audit logging inside the shared wrapper from exercise 3, or at a proxy level that matches on the next-action header.
الـ rate limits والـ audit logs اللي على الـ API gateway مش بتغطي الـ Server Functions لوحدها، لأنها POSTs على URLs بتاعة صفحات مش على /api/*. أي rule على /api/* مش هتشوفها. ضيف الـ rate limit والـ audit log جوه الـ wrapper المشترك بتاع تمرين 3، أو في proxy بيشوف الـ header next-action.
Interview question "A teammate says a Server Function is safe because the button only appears for admins. What do you say?" → The button is UI. The function is a public POST endpoint whose id is in public JS. Authenticate from the session, validate arguments with a schema, and scope the write to the tenant inside the function. I showed a cross-tenant delete with plain fetch, and it even worked with no cookie. Hiding a button is UX, not authorization.
"زميلك بيقول إن الـ Server Function آمنة عشان الزرار بيظهر للـ admins بس. هترد تقول إيه؟" ← الزرار ده UI. الـ function هي public POST endpoint والـ id بتاعها في JS عام. اعمل authenticate من الـ session، و validate للـ arguments بـ schema، وخلي الكتابة مربوطة بالـ tenant جوه الـ function. وريته cross-tenant delete بـ fetch عادي، واشتغل حتى من غير cookie. إخفاء الزرار UX مش authorization.

Common mistakes · غلطات شائعة

❌ Passing a database row as a prop 
// ❌ الـ passwordHash ظهر في الـ payload وفي الـ HTML
const user = await getUserById(1);
return <UserMenu user={user} />;
✅ Name the fields that may leave 
// ✅ الصف بقى ⁦{"name":"Alice"}⁩ بس
const user = await getUserById(1);
return <UserMenu user={{ name: user.name }} />;
بالعامية

❌ الـ serialization مش عارف الـ component هيقرا إيه، فبيبعت الـ object كله، وأي حد يقدر يشوفه بـ View Source. والـ TypeScript مش هيشتكي. ✅ حدد الحقول بالاسم في DTO، فأي column جديد في الـ DB مش هيخرج لوحده.

❌ 'use client' on the whole page 
// ❌ الصفحة كلها ومكتباتها راحوا الـ browser عشان زرار واحد
"use client";
import { marked } from "marked";

✅ Only the interactive leaf 
// ✅ الصفحة server، والزرار بس client

بالعامية

❌ 'use client' بيجر الملف وكل اللي بيستورده، والقياس في الجزء 3 كان 225KB زيادة لنفس الناتج. وغالبًا حد بيحطها عشان error بتاع useState ويكمّل. ✅ طلّع الجزء اللي فيه state لملف صغير، والباقي يفضل server.

}

// ✅ أي client import هيبقى build error

بالعامية

❌ الـ import هو اللي بيحدد مكان الكود، فالـ module كله بيروح الـ browser ومعاه أي secret، من غير أي error. ✅ الـ Server Component هو اللي يجمّع الاتنين ويبعت النتيجة كـ children، وserver-only بيحول أي غلطة مستقبلية لـ build error.

3. A factory nobody can forget 🔴 hard Write createAction(schema, handler) so that authentication and validation can't be skipped: the handler only runs with parsed input and a real user. Rewrite deleteInvoice with it and rerun the four attacks with plain fetch.

Solution · الحل 
import "server-only";

import { cookies } from "next/headers";
import type { z } from "zod";
import { userFromSession, type UserRow } from "./db";

export type ActionResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: "UNAUTHENTICATED" | "INVALID_INPUT" | "NOT_FOUND" };

// مصنع واحد لكل Server Function: الـ auth والـ validation مش ممكن حد ينساهم
export function createAction<S extends z.ZodType, T>(
  schema: S,
  handler: (input: z.output<S>, user: UserRow) => Promise<T | null>,
) {
  return async (raw: unknown): Promise<ActionResult<T>> => {
    const user = userFromSession((await cookies()).get("session")?.value);
    if (!user) return { ok: false, error: "UNAUTHENTICATED" };

    const parsed = schema.safeParse(raw);
    if (!parsed.success) return { ok: false, error: "INVALID_INPUT" };

    const data = await handler(parsed.data, user);
    return data === null ? { ok: false, error: "NOT_FOUND" } : { ok: true, data };
  };
}

Cheat sheet · الخلاصة

  • The server renders a tree into a payload, and the client reconciles it and hydrates the interactive parts. RSC isn't SSR: SSR makes HTML, RSC decides which code ships.
  • 'use client' marks a module boundary in the import graph: the file and all its imports. Who imports decides, not who renders.
  • Props cross as: JSON, Date, Map, Set, BigInt, promises, elements, Server Functions. Not plain functions or class instances.
  • Every prop is public. Use a DTO: passwordHash showed up in both payload and HTML.
  • Dots on a client export are undefined on the server. Use named exports. <Ctx value> works from the server on 19.3; .Provider doesn't.
  • Server Components have no state, effects or re-render. Measured: 447 KB vs 672 KB of JS for identical output. Cost: each navigation is a round trip.
  • Composition: pass a Server Component as children. Guard sensitive modules with import "server-only".
  • Flight: rows of id:value. I client reference, $L lazy, $S symbol, $D date. Internal and unversioned. It's also embedded in the HTML.
  • Server Function: 'use server', the client holds an id, a call is a POST. Forms work without JS. In Next.js calls run one at a time, so use them for mutations.
  • Every Server Function is a public endpoint: authenticate, validate, authorize inside each one, or through one shared wrapper.
  • CVE-2025-55182 (10.0 RCE) and the follow-ups: final fixes 19.0.4, 19.1.5, 19.2.4. In Next.js check next, because npm ls doesn't see its bundled copy.
  • Skip RSC for offline-first, static hosting and highly interactive apps. Keep a real API for other clients.
بالعامية
  • السيرفر بيعمل render لـ tree ويحولها لـ payload، والـ client بيعمل reconcile وبيعمل hydrate للأجزاء الـ interactive. الـ RSC مش SSR: الـ SSR بيعمل HTML، والـ RSC بيقرر أنهي كود يتبعت.
  • 'use client' بيحدد module boundary في الـ import graph: الملف وكل اللي بيستورده. مين بيستورد هو اللي بيقرر، مش مين بيعمل render.
  • الـ props بتعدّي لو: JSON، Date، Map، Set، BigInt، promises، عناصر، Server Functions. ومش بتعدّي لو functions عادية أو class instances.
  • كل prop بيبقى public. استخدم DTO: passwordHash ظهر في الـ payload وفي الـ HTML.
  • النقطة على client export قيمتها undefined على السيرفر، فاستخدم named exports. و<Ctx value> بيشتغل من السيرفر على 19.3، و.Provider لأ.
  • الـ Server Components مفيهاش state ولا effects ولا re-render. القياس: 447KB ضد 672KB من الـ JS لنفس الناتج. والتكلفة: كل navigation بقى round trip.
  • الـ composition: ابعت Server Component كـ children، واحمي الـ modules الحساسة بـ import "server-only".
  • الـ Flight: صفوف id:value. I هو client reference، و$L lazy، و$S symbol، و$D تاريخ. داخلي ومن غير version، وموجود كمان جوه الـ HTML.
  • الـ Server Function: 'use server'، والـ client ماسك id، والنداء POST. الـ forms بتشتغل من غير JS. وفي Next.js الـ calls بتمشي ورا بعض، فاستخدمها للـ mutations.
  • كل Server Function هي public endpoint: اعمل authenticate و validate و authorize جوه كل واحدة، أو في wrapper واحد مشترك.
  • CVE-2025-55182 (RCE بـ 10.0) واللي بعدها: الحل النهائي 19.0.4 و19.1.5 و19.2.4. وفي Next.js بص على next، لأن npm ls مش بيشوف النسخة اللي جواه.
  • سيب الـ RSC للـ offline-first والـ static hosting والـ apps التفاعلية جدًا. وخلي عندك API حقيقي للـ clients التانية.
