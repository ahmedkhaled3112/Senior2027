Why this matters · ليه ده مهم

English

Every Next.js page you ship runs this machinery, and the framework hides it until something breaks. Then you get a production log full of Minified React error #418, a form that loses what the user typed, a dark-mode flash, or one customer seeing another customer's balance. All of these come from one fact: the same component runs twice, on two machines, with different clocks, locales and globals.

This lesson builds it with no framework: node:http, renderToString, hydrateRoot, then renderToPipeableStream with real chunks over a real socket. Next.js is section 06; here you learn the layer it stands on. It also answers exit-test question 6: what a hydration error actually is.

بالعامية

أي صفحة Next.js بتطلعها بتشغّل الماكينة دي، والـ framework بيخبّيها عنك لحد ما حاجة تقع. وقتها هتلاقي الـ production logs مليانة Minified React error #418، أو form بيضيّع اللي المستخدم كتبه، أو flash في الـ dark mode، أو عميل شايف رصيد عميل تاني. كل دول جايين من حقيقة واحدة: نفس الـ component بيتنفّذ مرتين، على جهازين، بساعة و locale و globals مختلفين.

الدرس ده بيبني ده كله من غير framework: node:http وrenderToString وhydrateRoot، وبعدين renderToPipeableStream بـ chunks حقيقية على socket حقيقي. الـ Next.js في القسم 06، وهنا بتتعلم الطبقة اللي هو واقف عليها. وكمان الدرس بيجاوب على سؤال 6 في اختبار الخروج: يعني إيه hydration error بالظبط.

Part 1 — SSR vs hydration, by hand 🔴 Advancedالجزء 1 — الـ SSR والـ hydration بإيدك

English

SSR runs your components on the server and sends the result as HTML, so the browser can paint real content before any of your JavaScript arrives. That HTML is inert: there are no event handlers and no state behind it. Hydration is the second step: hydrateRoot renders the same tree in the browser, walks the existing DOM instead of creating new nodes, and attaches React to it. Only then does a click do anything.

Hydration needs the same inputs the server used, so the data travels twice: once as markup and once as JSON for the second render. In the run below USB-C cable appears in both. Embedding that JSON is also a security boundary. A bare JSON.stringify inside a <script> tag lets a customer named </script><script>… run code on your page. HTTP itself is in section 01; React's part starts once the bytes arrive.

The gap between the two steps is real. With the bundle delayed by 1500 ms, the button was visible after ≈114 ms and hydrated after ≈1600 ms. A click inside that window was lost: before hydrateRoot runs, React has no listener on the page, so there is nothing to catch or replay the event. Part 5 shows the narrower case where React does replay a click.

There's a cost on the server too. renderToString holds the event loop for the whole render, so every other request waits. If your API and a huge SSR page share a process, that page stalls the API.

بالعامية

الـ SSR معناه إن الـ components بتتنفّذ على السيرفر والنتيجة بتتبعت HTML، فالـ browser يقدر يرسم محتوى حقيقي قبل ما أي JavaScript بتاعك يوصل. بس الـ HTML ده ميت: مفيش event handlers ولا state وراه. الـ hydration هو الخطوة التانية: hydrateRoot بيعمل render لنفس الـ tree في الـ browser، وبيمشي على الـ DOM الموجود بدل ما يعمل nodes جديدة، وبيربط React بيه. ساعتها بس الدوسة بتعمل حاجة.

الـ hydration محتاج نفس الـ inputs اللي السيرفر استخدمها، فـالـ data بتسافر مرتين: مرة كـ markup ومرة كـ JSON للـ render التاني. في الـ run اللي فوق USB-C cable موجودة في الاتنين. وحط الـ JSON ده في الصفحة هو كمان حدود أمان: JSON.stringify لوحده جوه <script> بيخلي عميل اسمه </script><script>… يشغّل كود على صفحتك. والـ HTTP نفسه في القسم 01، وشغل React بيبدأ لما البايتات توصل.

الفترة اللي بين الخطوتين دي حقيقية. لما أخّرنا الـ bundle بـ 1500ms، الزرار ظهر بعد ≈114ms واتعمله hydrate بعد ≈1600ms. والدوسة في الفترة دي ضاعت: قبل ما hydrateRoot يشتغل، React ملوش أي listener على الصفحة، فمفيش حد يمسك الـ event أو يعيده. الجزء 5 هيوريك الحالة الأضيق اللي React بيعيد فيها الدوسة فعلًا.

وفيه trade-off على السيرفر: renderToString بتمسك الـ event loop طول الـ render، فأي request تاني بيستنى. ده اللي بيخلي SSR لصفحة ضخمة يوقف الـ API كله لو الاتنين في نفس الـ process.

فين هستخدمه في شغلي؟ صفحة تفاصيل order في dashboard على موبايل 3G: الـ Approve ظاهر من أول ثانية والـ JS بياخد 4 ثواني، فالموظف بيدوس ومفيش حاجة بتحصل ويفتكر إن النظام واقف. الحل مش "نسرّع السيرفر" بس: تقلل الـ JS، وتدي الزرار شكل disabled لحد الـ hydration، أو تخليه <form> حقيقي يشتغل من غير JS. ولو عندك renderToString لتقرير فيه 50 ألف صف، هيوقف كل الـ requests التانية ثانية كاملة: حطه في streaming أو pagination.

Part 2 — Hydration errors 🔴 Advancedالجزء 2 — الـ hydration errors

English

A hydration error means the tree the client rendered doesn't match the HTML the server sent. React can't safely attach to DOM that disagrees with it, so it throws that DOM away and re-renders on the client up to the nearest <Suspense> boundary, or the whole root if there is none. It reports this through onRecoverableError. The page ends up correct, which is why these bugs survive for months: nothing looks broken in a quick manual check.

Each cause below ran in real Chrome (locale ar-EG, zone Africa/Cairo) against a Node server in UTC. Two results deserve attention. <div> inside <p> is an HTML parser rule: the parser closes the <p> before the <div>, so the DOM has 3 nodes where React expects 2. Attribute mismatches aren't repaired at all: React logs "This won't be patched up" in dev, logs nothing in production, and the wrong class stays on the element.

Browser extensions change the DOM before React loads, and you can't reproduce a user's extension simply. I simulated one with a script that edits the DOM before hydrateRoot: an injected node or edited text causes a mismatch, an extra attribute causes none. That matches what you see in the wild, and it means a low rate of #418 from a few users may be noise. Check the browser and the page before chasing it.

Part 3 — Client-only content and server-side traps 🔴 Advancedالجزء 3 — المحتوى اللي للـ client بس وفخاخ السيرفر

English

Some content can't exist on the server: a cart in localStorage, a saved draft, the user's time zone. React 19.3 added browser() in react-dom for this. use(browser(reason)) stops the component during server rendering and leaves the closest <Suspense> fallback in the HTML. In the browser it returns undefined, so the component renders normally. It has three rules from the docs, and I ran the first: it must sit inside a Suspense boundary, it must be called from a Client Component, and it must go through use rather than being thrown.

Compared with the older isClient effect, the difference shows up in render counts: browser() rendered once in Chrome and the effect version rendered twice, because it has to match the server first and then update. Neither reported an error. browser() also reports to a server callback, onBrowserBailout, so you can see which components opt out. It doesn't reach onError or onRecoverableError.

Neither approach solves a theme flash, because both wait for JavaScript. The page paints white, then the bundle arrives and turns it dark. The fix is a small inline script in <head> that runs before the first paint. It changes <html> before hydration, so that one element needs suppressHydrationWarning. If the theme lives in a cookie, the server can send the right HTML with no script, but then the page is harder to cache.

The worst trap is on the server. A Node process serves many requests at once, so a module-level variable is shared between users. Streaming makes this easy to hit: a component suspends, another request overwrites the variable, and the first request resumes and reads the second user's data. The run below shows Alice's page with Bob's email. The fix is state created per request and passed down through Context, or AsyncLocalStorage for server-only values.

فيه محتوى مينفعش يتعمل على السيرفر أصلًا: cart في localStorage، أو draft متسجّل، أو الـ time zone بتاع المستخدم. React 19.3 ضاف browser() من react-dom عشان كده. use(browser(reason)) بيوقف الـ component أثناء الـ server rendering ويسيب الـ fallback بتاع أقرب <Suspense> في الـ HTML. وفي الـ browser بيرجّع undefined فالـ component بيتعمله render عادي. وليه 3 قواعد من الـ docs، وأنا شغّلت الأولى: لازم يبقى جوه Suspense boundary، ولازم يتنادى من Client Component، ولازم يعدّي من use مش يتعمله throw.

لو قارنته بالـ isClient effect القديم، الفرق بيبان في عدد الـ renders: browser() عمل render مرة واحدة في Chrome، ونسخة الـ effect عملت مرتين، لأنها لازم تطابق السيرفر الأول وبعدين تتحدّث. والاتنين مبلّغوش عن أي error. وكمان browser() بيبلّغ callback على السيرفر اسمه onBrowserBailout، فتقدر تعرف أنهي components بتهرب من الـ SSR. وده مش بيوصل لـ onError ولا onRecoverableError.

ولا واحدة من الطريقتين بتحل الـ theme flash، لأن الاتنين مستنيين الـ JavaScript: الصفحة بتترسم بيضا، وبعدين الـ bundle يوصل ويقلبها سودا. الحل سكريبت inline صغير في الـ <head> بيشتغل قبل أول paint. وهو بيغيّر الـ <html> قبل الـ hydration، فالعنصر ده بالذات محتاج suppressHydrationWarning. ولو الـ theme في cookie، السيرفر يقدر يبعت الـ HTML صح من الأول من غير سكريبت، بس كده الصفحة مش هتتعمل cache بنفس السهولة.

أخطر فخ موجود على السيرفر. الـ Node process بيخدم requests كتير في نفس الوقت، فـأي متغير على مستوى الـ module بيبقى مشترك بين المستخدمين. والـ streaming بيخلي الغلطة دي سهلة: component بيعمل suspend، و request تاني يكتب فوق المتغير، والأول يرجع يكمّل ويقرا بيانات المستخدم التاني. الـ run اللي فوق بيوريك صفحة Alice وعليها إيميل Bob. الحل state بيتعمل لكل request وينزل من خلال Context، أو AsyncLocalStorage للقيم اللي للسيرفر بس (اتشرح في قسم Node).

فين هستخدمه في شغلي؟ لو عندك Zustand أو Redux store معمول create() في ملف ومستورد في كل حتة، وبتعمل SSR، فده بالظبط الفخ ده: الـ store واحد لكل المستخدمين. مراجعة واحدة في الـ code review هتمنع incident من النوع اللي بيتبلّغ عنه رسميًا: عميل شايف بيانات عميل تاني. القاعدة: على السيرفر مفيش state بيخص مستخدم في متغير عام. واعمل store جوه useState أو Context لكل request، وخلي عندك test بيبعت طلبين متزامنين لمستخدمين مختلفين ويتأكد إن مفيش تسريب.
Trade-off: browser() or an effect? Use browser() on React 19.3+ when a Suspense fallback is an acceptable placeholder: one render and a server-side report. Use the effect when you need to support older React, or when the component should render meaningful server HTML first and only refine it later, as in the ISO date in Part 2. Neither gives you SEO for that content, because the crawler's HTML holds only the fallback.

Part 4 — Streaming SSR 🔴 Advancedالجزء 4 — الـ Streaming SSR

English

renderToString sends nothing until everything is done, so one slow query delays the whole page. renderToPipeableStream sends the shell (everything outside <Suspense>, with fallbacks in place) as soon as it's ready, keeps the connection open, and sends each boundary's HTML when its data arrives. In the run, an order page with a 300 ms and a 900 ms boundary sent three chunks at ≈10, ≈309 and ≈923 ms.

The late HTML has to land in the right place without any bundle. Each chunk carries it in a <div hidden id="S:0"> plus an inline script calling $RC("B:0","S:0"), which finds the <template id="B:0"> marker and moves the content over the fallback. That's why the page updates with no client bundle at all, and why it stays on the fallback when JavaScript is off.

Four production consequences follow. Crawlers: use onAllReady for bots so they get complete HTML in one chunk (≈908 ms in the run). Since a bot's response starts after everything has settled, its status can be honest: with the invoice down the bot got 500 and the user 200. Status codes: the status goes out with the shell, so a later failure stays 200 and only onError and an inline $RX know about it; only an error in the shell can still return a real 500. Proxies: a buffering proxy merges everything into one chunk at ≈910 ms, and streaming silently stops working (nginx's proxy_buffering is the classic case; I used a small Node proxy here, nginx wasn't run). Compression is safe in the run: React's stream calls destination.flush() when that method exists, and a gzip stream has it, so chunks still came at ≈312 and ≈911 ms.

renderToReadableStream is the same engine for Web Streams, for Workers, Deno and Bun. It ran with the same three chunks on Node. Node streams vs Web Streams is in section 04.

You will also see The destination stream closed early. in onError. It means the client closed the connection before the stream finished, for example by closing the tab. React stops the work and reports it, so don't treat it as a bug in your alerts.

function load(cache: RequestCache, key: string, ms: number, fail = false) {
  if (!cache.has(key)) {

      if (fail) throw new Error(`${key} service is down`);

}

Part 5 — Selective hydration 🔴 Advancedالجزء 5 — الـ selective hydration

English

Each <Suspense> boundary in server HTML can hydrate on its own. So React doesn't have to finish the whole page before responding, and it can pick what to work on next. If the user clicks inside a boundary that hasn't hydrated yet, React hydrates that boundary first, synchronously, then replays the click. This is the narrow case Part 1 promised: it works only once hydrateRoot has run, because that is when React's root listeners exist.

Three widgets that each burn 200 ms prove it. With no click they hydrate in document order and finish at ≈627 ms. With a click on the last widget, it hydrates first at ≈212 ms, its handler runs a millisecond later, and the other two finish at ≈818 ms. A click before hydrateRoot is lost, as before.

Boundaries also limit damage. A render crash in one widget goes to its error boundary while the others keep working. A server-side failure in a boundary comes through as React error #419 in onRecoverableError, the client renders that boundary itself, and the DOM outside it stays. Part 2's measurement is the same idea: a mismatch inside a boundary cost 1 node instead of 5003.

Two recent changes matter. React 19.2 batches reveals: $RC queues boundaries in $RB and reveals them together, at most once per 300 ms (the $RT+300 in the runtime above). React 19.3 double-invokes effects under StrictMode during hydration, in dev, to match client-rendered roots, so cleanup bugs that only showed up on client navigation now show up on first load too. Keep <StrictMode> at the top of the tree: when my first test nested it inside a component, effects ran only once on first mount.

prerender and resume are the APIs behind Partial Pre-rendering: prerender at build time, abort to keep a static shell plus a serializable postponed state, then resume at request time and send only the dynamic part. In the run, the dynamic part didn't repeat the shell. Section 06 shows how Next.js uses this; you won't usually call these APIs directly.

بالعامية

كل <Suspense> boundary في HTML السيرفر يقدر يتعمله hydrate لوحده. فـ React مش لازم يخلص الصفحة كلها عشان يستجيب، ويقدر يختار يشتغل على إيه الأول. لو المستخدم داس جوه boundary لسه متعملوش hydrate، React بيعمل hydrate لـالـ boundary ده الأول بشكل sync، وبعدين يعيد الدوسة. دي الحالة الضيقة اللي وعدتك بيها في الجزء 1: بتشتغل بس بعد ما hydrateRoot يشتغل، لأن وقتها بس الـ root listeners بتوع React بيبقوا موجودين.

3 widgets كل واحد بيستهلك 200ms بيثبتوا ده. من غير دوسة بيتعملهم hydrate بترتيب الصفحة ويخلصوا عند ≈627ms. ولو دوست على آخر widget، بيتعمله hydrate الأول عند ≈212ms، والـ handler بتاعه بيشتغل بعدها بـ millisecond، والاتنين التانيين يخلصوا عند ≈818ms. والدوسة قبل hydrateRoot بتضيع زي ما قلنا.

والـ boundaries كمان بتحدد حجم الضرر. لو widget وقع في الـ render، الغلطة بتروح للـ error boundary بتاعه والباقي بيفضل شغال. ولو boundary وقع على السيرفر، بييجي #419 في onRecoverableError، والـ client بيعمل render للـ boundary ده بنفسه، والـ DOM اللي بره بيفضل زي ما هو. وقياس الجزء 2 هو نفس الفكرة: mismatch جوه boundary كلّف node واحد بدل 5003.

فيه تغييرين جداد مهمين. React 19.2 بيجمّع الـ reveals: $RC بيحط الـ boundaries في $RB ويظهرهم مع بعض، بحد أقصى مرة كل 300ms (ده الـ $RT+300 في الـ runtime اللي فوق). وReact 19.3 بيعمل double-invoke للـ effects تحت StrictMode أثناء الـ hydration، في dev، عشان يبقى زي الـ client-rendered roots. فالـ cleanup bugs اللي كانت بتظهر بس في الـ client navigation، دلوقتي هتظهر من أول load كمان. وخلي <StrictMode> في أعلى الـ tree: لما أول تجربة حطيته فيها جوه component، الـ effects اتنفذت مرة واحدة بس في أول mount. والـ StrictMode نفسه اتشرح في الدرس 03.

prerender وresume هم الـ APIs اللي ورا Partial Pre-rendering: بتعمل prerender وقت الـ build، وتوقفه بـ abort فتحتفظ بـ shell ثابت ومعاه postponed state ينفع يتحفظ، وبعدين resume وقت الـ request وتبعت الجزء الديناميكي بس. وفي الـ run، الجزء الديناميكي مكررش الـ shell. القسم 06 بيوريك Next.js بيستخدم ده إزاي، وغالبًا مش هتنادي الـ APIs دي بنفسك.

فين هستخدمه في شغلي؟ صفحة order فيها زرار Refund تحت، وفوقه reviews و recommendations تقال. لو كل حاجة في boundary واحد، الزرار مش هيستجيب غير لما كل التقيل يخلص. لو الـ widgets التقيلة كل واحد في Suspense لوحده، الموظف يدوس Refund و React ينط له الأول. ولو عندك socket في useEffect من غير cleanup سليم، بعد الترقية لـ 19.3 هتلاقي اتصالين في dev من أول load: ده مش bug في React، ده الـ cleanup بتاعك.
Trade-off: how many boundaries? More boundaries mean smaller hydration tasks, smaller mismatch damage and click priority. They also mean more fallback states to design, and more markup in the stream. Group what belongs together (boundary design is in lesson 20), and put a boundary around anything heavy that isn't the page's main action.
boundaries أكتر معناها hydration tasks أصغر، وضرر أقل من الـ mismatch، وأولوية للدوسة. وكمان معناها fallback states أكتر تصممها، و markup أكتر في الـ stream. جمّع الحاجات اللي مكانها مع بعض (تصميم الـ boundaries في الدرس 20)، وحط boundary حوالين أي حاجة تقيلة ومش هي الـ action الأساسي في الصفحة.

Cheat sheet · الخلاصة

  • SSR paints content; hydrateRoot makes it alive. A click before hydrateRoot is lost. Data travels twice, so escape < in embedded JSON.
  • A hydration error means the client's first render differs from the server HTML. React rebuilds up to the nearest Suspense boundary and reports through onRecoverableError.
  • Causes: time, randomness, window branches, locale and time zone, invalid nesting, extensions. In production it's #418.
  • Attribute mismatches aren't repaired, and don't reach onRecoverableError.
  • Cost measured: 5003 nodes dropped without a boundary, 1 with one, and typed input is lost.
  • Fixes: value as a prop, useId, useSyncExternalStore, effect, fixed formatter. suppressHydrationWarning is one level deep and doesn't patch.
  • use(browser()) (19.3): the server sends the fallback, one client render, needs Suspense, reports to onBrowserBailout.
  • Theme flash: inline script in <head> plus suppressHydrationWarning on <html>.
  • Module-level state on the server leaks between users. Create state per request: Context or AsyncLocalStorage.
  • Streaming: shell, then each boundary with $RC. onAllReady for bots. Status goes out with the shell. Report from onError, set a timeout with abort().
  • Buffering proxies kill streaming silently. Read chunk arrival times at each hop.
  • Selective hydration: a click on an unhydrated boundary jumps the queue and is replayed. 19.2 batches reveals at most once per 300 ms. 19.3 StrictMode double-invokes effects during hydration.
بالعامية
  • الـ SSR بيرسم المحتوى، وhydrateRoot بيخليه عايش. الدوسة قبل hydrateRoot بتضيع. والـ data بتسافر مرتين، فهرّب الـ < في الـ JSON اللي في الصفحة.
  • الـ hydration error معناه إن أول render في الـ client مختلف عن HTML السيرفر. React بيبني من جديد لحد أقرب Suspense boundary ويبلّغ من خلال onRecoverableError.
  • الأسباب: الوقت، الأرقام العشوائية، فروع window، الـ locale والـ time zone، الـ nesting الغلط، والـ extensions. وفي production اسمها #418.
  • الـ attribute mismatch مش بيتصلّح، ومش بيوصل لـ onRecoverableError.
  • التكلفة اللي اتقاست: 5003 nodes اترموا من غير boundary، وواحد بس مع boundary، واللي المستخدم كتبه بيضيع.
  • الحلول: القيمة كـ prop، useId، useSyncExternalStore، effect، formatter ثابت. وsuppressHydrationWarning مستوى واحد ومش بيصلّح.
  • use(browser()) (19.3): السيرفر بيبعت الـ fallback، و render واحد في الـ client، ومحتاج Suspense، وبيبلّغ onBrowserBailout.
  • الـ theme flash: سكريبت inline في الـ <head> ومعاه suppressHydrationWarning على الـ <html>.
  • الـ state اللي على مستوى الـ module على السيرفر بيسرّب بين المستخدمين. اعمل state لكل request: Context أو AsyncLocalStorage.
  • الـ streaming: الـ shell، وبعدين كل boundary بـ $RC. onAllReady للبوتات. الـ status بيتبعت مع الـ shell. بلّغ من onError، وحط timeout بـ abort().
