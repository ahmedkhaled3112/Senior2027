Why this matters · ليه ده مهم

English

Nobody plans a tangled frontend. It happens one reasonable import at a time, until changing billing breaks orders, the test suite takes minutes because one file pulls in 300 modules, and nobody dares delete anything. Structure decides how month 24 feels, and seniors get asked to design it, defend it and enforce it with tools rather than a wiki page.

This lesson doesn't argue from taste. It builds the same app both ways and counts, measures what barrels really cost, reproduces a circular-import crash and a secret leaking into a browser chunk, runs real Module Federation in Chrome, and builds a working design-system package. Everything ran here on Windows, so counts and sizes are solid and timings are marked ≈.

بالعامية

محدش بيخطط يعمل frontend متلخبط. بيحصل import ورا import، كل واحد شكله منطقي، لحد ما تغيير في billing يكسر orders، والـ tests تاخد دقايق عشان ملف واحد بيسحب 300 module، ومحدش يجرؤ يمسح حاجة. الـ structure هو اللي بيحدد الشهر الـ 24 هيبقى عامل إزاي، والسنيور هو اللي بيتطلب منه يصممه ويدافع عنه ويفرضه بـ tools مش بصفحة wiki.

الدرس ده مش بيتكلم بالذوق. بنبني نفس الـ app بالطريقتين ونعدّ، ونقيس الـ barrels بتكلف كام بجد، ونكرر crash حقيقي من circular import وسر بيتسرب لـ chunk في الـ browser، ونشغّل Module Federation حقيقي في Chrome، ونبني design system package شغالة. كل حاجة اتشغلت هنا على Windows، فالأعداد والأحجام ثابتة، والأزمنة معلّم عليها بـ ≈.

Part 1 — Feature-based vs type-based 🔴 Advancedالجزء 1 — الـ feature-based قصاد الـ type-based

English

A type-based tree groups files by what they are: components/, hooks/, utils/, api/. A feature-based tree groups them by what they're for: features/orders, features/billing. I generated the same app both ways, and both compile on TS 7. Then I took one real change, partial refunds on orders, and counted.

The honest result: the number of files changed is the same, 6 and 6. Feature folders don't make a change smaller. They make it less scattered: 6 folders against 1, with 17 files from other domains sitting beside your work against 0. That's what you feel in a pull request, in a review, and when a new hire asks where billing lives.

The stronger test is deleting a feature. Remove features/billing and tsc reports exactly one error, in src/app/App.tsx, the one place that composes it. In the type-based tree there's no folder to delete: you search by name, hope the names are consistent, and collect 7 files from 6 folders. A feature you can delete as a folder has real boundaries, and it's also a natural unit for CODEOWNERS and route-level code splitting (lesson 13).

Type-based is still fine for a small app with one domain, a prototype, or a component library where everything really is a component. The structure pays off once you have several domains and several people. Migrate gradually: new features go in features/, and old code moves when you touch it.

الاختبار الأقوى هو مسح feature. امسح features/billing وtsc هيطلّع error واحد بس في src/app/App.tsx، المكان الوحيد اللي بيركّبها. في الشجرة الـ type-based مفيش فولدر تمسحه: بتدوّر بالاسم، وتتمنى الأسماء تكون متسقة، وتلم 7 ملفات من 6 فولدرات. الـ feature اللي تقدر تمسحها كفولدر ليها حدود حقيقية، وكمان وحدة طبيعية لـ CODEOWNERS وللـ code splitting على مستوى الـ route (درس 13).

الـ type-based لسه كويس في app صغير بـ domain واحد، أو prototype، أو component library كل حاجة فيها component فعلًا. الـ structure بيدفع تمنه لما يبقى عندك كذا domain وكذا حد. وانقل بالتدريج: الـ features الجديدة تدخل features/، والقديم يتنقل لما تلمسه.

فين هستخدمه في شغلي؟ الـ Next app بتاع شركتك فيه components/ بـ 200 ملف، وأي PR بيلمس 6 فولدرات، والـ reviewer مش عارف إيه اللي يخص إيه. متعملش PR ضخم ينقل كل حاجة. ابدأ بالـ feature الجاية في features/، وحط CODEOWNERS عليها، واستخدم اختبار المسح كمقياس: لو مسحت الفولدر والـ errors طلعت في مكان واحد، يبقى الحدود سليمة.
Trade-off Feature folders make cross-cutting changes slightly harder: renaming a prop on every list means opening many features instead of one components/ folder. And some code really has no home yet. That's a fair price when most changes follow a product feature, which is true of most product work. If most of your changes are cross-cutting, as in a component library, type-based is the better fit.
فولدرات الـ features بتخلي التغييرات اللي بتعدّي على كل حاجة أصعب شوية: تغيير اسم prop في كل list معناه تفتح features كتير بدل فولدر components/ واحد. وفيه كود ملوش بيت لسه. ده تمن معقول لما أغلب التغييرات ماشية مع feature في المنتج، وده حال أغلب شغل المنتجات. لو أغلب تغييراتك عابرة زي component library، يبقى الـ type-based أنسب.

Part 2 — Colocation and import paths 🔴 Advancedالجزء 2 — الـ colocation ومسارات الـ imports

English

Colocation means keeping things that change together close together. The test, styles, hook and story sit beside the component, so moving or deleting it takes them along and nothing is orphaned in a distant __tests__ folder. It costs the bundle nothing, because app code never imports a test or a story. The build below has zero files containing their marker strings.

A promotion rule stops shared/ from becoming a junk drawer. Code starts inside its feature. When a second feature needs it, first ask whether the app layer can pass it in (Part 4). Promote it only if it has no domain word in it: formatMoney yes, orderTotal no. And demote too: shared code used by one feature goes back home. The report below computes both from dependency-cruiser's JSON, so it can run in CI.

Then import paths. Deep ../../../ hurts, so people alias. baseUrl is gone in TS 7 (TS5102) and deprecated in TS 6 (TS5101), so paths entries are written relative to the tsconfig (TS lesson 07, part 2, and lesson 10). But paths only teaches the compiler. Plain node fails. Vite dev and Vitest fail unless you set resolve.tsconfigPaths: true. And vite build passes without it, because Rolldown finds the tsconfig itself (with the tsconfig removed, the same build failed to resolve the import), so CI can stay green while npm run dev is broken.

Subpath imports avoid all of that. "imports": { "#shared/*": "./src/shared/*" } in package.json is a Node feature, and it worked in every tool with no config. One catch: a bare #/* pattern fails on Node 22.19 with ERR_INVALID_MODULE_SPECIFIER even though TS 7 accepts it, so give the prefix a name.

// تقرير بيطبّق قاعدة الـ promotion: مين لازم يطلع لـ shared ومين لازم ينزل منه
import { execFileSync } from "node:child_process";

const depcruise = process.argv[2];
const json = execFileSync(process.execPath, [depcruise, "src", "--no-config", "--ts-config", "tsconfig.json", "--ts-pre-compilation-deps", "--output-type", "json"], { encoding: "utf8", maxBuffer: 1 << 28 });
const { modules } = JSON.parse(json);

const featureOf = (p) => p.match(/^src\/features\/([^/]+)\//)?.[1];
const users = new Map();
for (const mod of modules) {
  const from = featureOf(mod.source) ?? (mod.source.startsWith("src/app/") ? "app" : "shared");
  for (const dep of mod.dependencies) {
    if (dep.resolved.includes("node_modules") || !dep.resolved.startsWith("src/")) continue;
    if (!users.has(dep.resolved)) users.set(dep.resolved, new Set());
    if (from !== featureOf(dep.resolved)) users.get(dep.resolved).add(from);
  }
}

for (const [file, who] of [...users].sort()) {
  const feature = featureOf(file);
  const others = [...who];
  // جوه feature ومستخدم من feature تانية: مرشّح يطلع لـ shared
  if (feature && !file.endsWith("/index.ts") && others.some((w) => w !== "app")) {
    console.log(`PROMOTE  ${file}  used by ${others.join(", ")}`);
  }
  // في shared ومستخدم من feature واحدة بس: رجّعه لمكانه
  if (file.startsWith("src/shared/") && others.filter((w) => w !== "shared").length === 1) {
    console.log(`DEMOTE   ${file}  used only by ${others.join(", ")}`);
  }
}

Part 3 — A public API per feature, and what barrels cost 🔴 Advancedالجزء 3 — public API لكل feature وتكلفة الـ barrels

English

A public API means features/orders/index.ts exports what others may use, and everything else is private, by convention and by the rule in Part 4. You can rename or move internals without touching a consumer, exactly as with exports in a package. The cost is that index.ts is a barrel, so measure it. On a generated 300-module feature:

  • Dev server: 2 modules requested when importing the file directly, 302 through the barrel. There's no tree shaking in dev, so every re-exported file is served.
  • Tests: ≈ 388 ms against ≈ 3.73 s for the same one-line test in Vitest, on this loaded Windows machine. About 10 times slower, and it's nearly all transform time.
  • Production, pure modules: 215.2 KB both ways. Rolldown tree-shakes them, so "barrels bloat the bundle" isn't automatically true.
  • Production, one top-level call per module: 485.9 KB against 215.2 KB. registerReport(...) is a side effect, so the bundler must keep all 300.
  • "sideEffects": false: back to 215.2 KB, and it's a promise. Those registrations are now dropped, so a registry that depended on them would silently be missing entries.

So keep feature barrels small and explicit: the few things outsiders need, not export * of every file. Then the module cost is tiny and the bundle is safe. A barrel at a feature boundary is fine. A barrel over 300 icons in shared/ isn't.

Barrels also make cycles easy. A file inside a feature importing its own barrel creates index → format → index (JS lesson 12, part 4). Whether it crashes depends on the order of the export lines: with statuses first it works, and sorted alphabetically it throws a TDZ ReferenceError in Node and in the Vite dev server. Production reports the same bug differently, TypeError: Cannot read properties of undefined, because Rolldown turned the top-level const into var. A formatter that sorts exports can trigger it. Both detectors found it: madge 8.0.0 peers on typescript ^5.4.4, so a plain npm i next to TS 6 fails with ERESOLVE (it ran with --legacy-peer-deps), and dpdm 4.3 installs cleanly. dpdm -T ignores type-only cycles, which are erased and harmless, while madge flagged them too. The fix: inside a feature, import the file directly. The barrel is for outsiders.

On the server side, a barrel can be a security bug. 'use client' marks a boundary (lesson 22, part 1), and a client component importing from a barrel pulls everything the barrel re-exports into its graph. I ran three versions on Next 16.4. With import "server-only", the build fails, which is what you want. Without it and with a pure function, tree shaking happened to save us. Without it and with a top-level connect(url), next build succeeds and the connection string lands in .next/static, served to every visitor. The fix is two entry points, index.ts for the browser and server.ts for the server, plus the server-only guard.

English

Imports point one way: app → features → shared. Features never import each other, and shared knows nothing above it. That's what keeps the delete test from Part 1 passing. One import from billing into orders and you can no longer delete, split or own either one alone. A rule on a wiki doesn't hold under deadline pressure, so enforce it with tools. Both of these ran here.

ESLint's core no-restricted-imports, in flat config on ESLint 10, gives instant feedback in the editor with your own message. It matches the import string, not the resolved file. A naive **/features/orders/** misses both ../orders/orderTotal and ../../features/orders, so it reported 2 of 4 violations in the run below. List the relative forms too.

dependency-cruiser resolves real paths, so it can't be fooled by spelling. It found 5 violations, with one import breaking two rules, and $1 back-references express "any feature but this one". It's what I'd run in CI. Its trap: it supports typescript >=2.0.0 <7.0.0. Part 5 — Micro-frontends 🔴 Advancedالجزء 5 — الـ micro-frontends

English

Micro-frontends split one UI into apps that are built and deployed separately. With Module Federation, a host loads code from a remote at runtime: import("billing/InvoiceWidget") resolves from a URL, not at build time. I built one with @module-federation/vite 1.23.9 on Vite 8.3 and ran it in Chrome. It works. Here's what it costs, measured on one button:

  • Performance: 26 JS requests and 137.4 KB gzip, against 2 requests and 67.1 KB for the same screen as one build.
  • The React singleton: a remote that bundles its own React crashes in the host with Cannot read properties of null (reading 'useState'), because the hook reads a dispatcher from a copy that isn't rendering. shared: { react: { singleton: true } } fixes it, and now every team must agree on React.
  • Version skew: a remote asking for ^18.3.0 against a host on 19.3.1 still ran on 19, with 7 console warnings and no failed build. The combination reaches production untested.
  • Runtime dependencies: with the remote down and no error boundary, the whole shell went blank. One team's bad deploy takes down another team's page, unless every remote sits behind a boundary. With one, the shell survived.
  • CSS and contracts: global styles and per-app Tailwind builds can collide or duplicate, and the remote's types need generating across deploys (dts, which I turned off here). I didn't measure these two.

The valid case is organizational, not technical: many teams blocked by each other's release cycle, or a legacy app being replaced piece by piece. If one team owns the app, you pay all of this for nothing.

The usual alternative is a monorepo with route-level deploys. Each app owns a URL prefix, a reverse proxy routes by path, packages/ui keeps them looking the same, and crossing a prefix is a full page load. You get independent deploys with no runtime sharing and no singleton problem, and a bad billing deploy only breaks /billing. Next.js calls this Multi-Zones. This one is not run here: it needs a real reverse proxy such as nginx, which isn't available on this machine.

الـ micro-frontends بتقسم UI واحد لـ apps بتتبني وتتعمل deploy لوحدها. مع Module Federation، الـ host بيحمّل كود من remote وقت التشغيل: import("billing/InvoiceWidget") بيتحل من URL مش وقت الـ build. بنيت واحد بـ @module-federation/vite 1.23.9 على Vite 8.3 وشغّلته في Chrome، واشتغل. ودي التكلفة، متقاسة على زرار واحد:

  • الـ performance: 26 JS request و137.4 KB gzip، قصاد 2 request و67.1 KB لنفس الشاشة في build واحد.
  • الـ React singleton: remote معاه نسخته من React بيقع جوه الـ host بـ Cannot read properties of null (reading 'useState')، لأن الـ hook بيقرا الـ dispatcher من نسخة مش هي اللي بترندر. shared: { react: { singleton: true } } بيحلها، وساعتها كل الفرق لازم تتفق على React.

  • الـ runtime dependencies: لما الـ remote وقع ومفيش error boundary، الـ shell كله فضي. deploy غلط من فريق بيوقّع صفحة فريق تاني، إلا لو كل remote ورا boundary. ومع الـ boundary الـ shell فضل شغال.
  • الـ CSS والـ contracts: الـ global styles وبناء Tailwind لكل app ممكن يتعارضوا أو يتكرروا، وtypes بتاعة الـ remote لازم تتولد عبر الـ deploys (dts، وقفلته هنا). الاتنين دول ماقستهمش.

الحالة اللي تستاهل حالة تنظيمية مش تقنية: فرق كتير كل واحد واقف على release التاني، أو app قديم بيتبدل حتة حتة. لو فريق واحد ماسك الـ app، إنت بتدفع كل ده على الفاضي.

البديل المعتاد مونوريبو مع deploys على مستوى الـ route. كل app ماسك URL prefix، وreverse proxy بيوزّع حسب المسار، وpackages/ui بتخلي الشكل واحد، والانتقال بين prefixes عبارة عن full page load. بتاخد deploys مستقلة من غير مشاركة وقت التشغيل ومن غير مشكلة الـ singleton، وdeploy غلط في billing بيكسر /billing بس. Next.js بيسمي ده Multi-Zones. ودي ما اتشغلتش هنا: محتاجة reverse proxy حقيقي زي nginx، ومش متاح على الجهاز ده.

Part 6 — A design system package 🔴 Advancedالجزء 6 — الـ design system كـ package

English

packages/ui in a workspace gives a design system one home and one version. npm workspaces link node_modules/@shop/ui to the folder. I built the two-package workspace below, consumed it from a Vite app with Tailwind 4, and ran it in Chrome. Tokens, cva and component APIs are in lesson 15, part 6. This part is about the package.

Source or built exports. An internal package can export source: ".": "./src/index.ts". There's no build step and HMR is instant, and every consumer must compile it, so it can't be published as is. Built exports point at dist with types first (TS lesson 07, part 7), which publishing requires, and which needs a watch build in development. Start with source. Build when consumers live outside the repo.

React is a peer dependency, plus a dev dependency for local tests. A UI package with "dependencies": { "react": "19.2.0" } gave two copies in npm ls react and a blank page with the same useState error as Part 5. Vite's resolve.dedupe hid it and the peer dependency fixes it. In built mode, mark both react and react/jsx-runtime external: 342 bytes against 44,298.

CSS delivery. Tailwind 4 scans the app, not sibling packages, so the app's CSS needs @source "../../../packages/ui/src";. Without it the HTML has bg-rose-700 and the CSS has 0 rules for it: an unstyled button and no error. There's a nasty twist. Tailwind respects .gitignore, so with no .gitignore the second build scans the previous dist/, finds the class names there, and "works". It's fine on your laptop and broken on a clean CI.

بالعامية

packages/ui في workspace بيدي الـ design system بيت واحد ونسخة واحدة. npm workspaces بتربط node_modules/@shop/ui بالفولدر. بنيت الـ workspace اللي فوق بالـ 2 packages، واستخدمته من Vite app مع Tailwind 4، وشغّلته في Chrome. الـ tokens والـ cva وتصميم الـ components في الجزء 6 من درس 15، والجزء ده عن الباكدج نفسها.

source ولا built exports. الباكدج الداخلية ممكن تصدّر الـ source: ".": "./src/index.ts". مفيش build step والـ HMR فوري، بس كل مستخدم لازم يعمل compile، فمينفعش تتنشر كده. الـ built exports بتشاور على dist والـ types الأول (الجزء 7 من درس TS رقم 07)، وده مطلوب للنشر، ومحتاج watch build في dev. ابدأ بالـ source، وابني لما المستخدمين يبقوا بره الـ repo.

React يبقى peer dependency، ومعاها dev dependency للـ tests المحلية. باكدج UI فيها "dependencies": { "react": "19.2.0" } طلّعت نسختين في npm ls react وصفحة فاضية بنفس error الـ useState بتاع الجزء 5. الـ resolve.dedupe في Vite خبّى المشكلة، والـ peer dependency هو اللي بيحلها. وفي الـ built mode، خلّي react وreact/jsx-runtime الاتنين external: 342 byte قصاد 44,298.

توصيل الـ CSS. Tailwind 4 بيفحص الـ app مش الـ packages اللي جنبه، فالـ CSS بتاع الـ app محتاج @source "../../../packages/ui/src";. من غيره الـ HTML فيه bg-rose-700 والـ CSS فيه 0 rules ليه: زرار من غير ستايل ومن غير error. وفيه لفّة وحشة: Tailwind بيحترم .gitignore، فلو مفيش .gitignore الـ build التاني بيفحص dist/ القديم، ويلاقي الأسماء هناك، و"يشتغل". يعني تمام على اللابتوب بتاعك وبايظ على CI نضيف.

الـ versioning بـ Changesets. الـ PR بيبقى فيه ملف markdown صغير بيحدد الباكدج وحجم الـ bump. changeset version بياكل الملفات دي، ويزوّد النسخة، ويكتب الـ changelog: من 1.2.0 لـ 1.3.0 فوق. والنشر ما اتشغلش هنا. وفي الآخر، نسخ الـ components جوه الـ repo على طريقة shadcn هو الموديل التاني: الكود بتاعك والـ upgrades يدوي، والجدول بيقارن بينهم.

فين هستخدمه في شغلي؟ عندك admin dashboard وcustomer app في نفس الـ repo، وزرار الـ danger شكله مختلف في الاتنين. اعمل packages/ui بـ source exports، وحط React فيها peer، وضيف @source في كل app، وتأكد إن .gitignore فيه dist. وفي CI ابني من checkout نضيف، عشان حكاية الـ dist/ القديم متخبيش الـ bug. ولو مش محتاج أكتر من app، shadcn جوه الـ repo كفاية، ومتعملش باكدج لحد ما يبقى فيه مستخدم تاني. ولما تضيف component، ده الـ artifact رقم 2 بتاع القسم.

Cheat sheet · الخلاصة

  • Feature folders don't shrink a change (6 files either way). They reduce scatter: 1 folder against 6, 0 foreign neighbours against 17.
  • The delete test: remove a feature's folder, and tsc should complain only in the app layer.
  • Colocate test, styles, hook and story. They add 0 bytes to the bundle.
  • Promote to shared only with no domain word in the name, and demote what one feature uses.
  • No baseUrl in TS 7. paths needs resolve.tsconfigPaths: true in Vite dev and Vitest and fails in plain node. #shared/* works everywhere; #/* fails on Node 22.19.
  • Barrels: 302 modules against 2 in dev, about 10 times slower in tests. Production is equal for pure modules, 485.9 KB against 215.2 KB with top-level calls.
  • Inside a feature, import files directly. Own-barrel cycles crash by export order: ReferenceError in dev, TypeError in production. Gate with dpdm -T --exit-code circular:1.
  • Never mix client and server exports in a barrel. It can leak secrets into .next/static. Use server.ts plus server-only.
  • app → features → shared. Features talk through slots, callbacks and the URL.
  • no-restricted-imports matches strings, so list relative forms. dependency-cruiser resolves files, but it needs TS 6 beside TS 7 or it passes on 0 modules.
  • Module Federation ran: 26 requests and 137.4 KB against 2 and 67.1 KB, singleton React, skew only warns, a dead remote blanks the shell. Usually use a monorepo with route-level deploys.
  • packages/ui: source exports first, React as a peer, @source in each app, dist in .gitignore, Changesets for versions.

  • فولدرات الـ features مش بتصغّر التغيير (6 ملفات في الحالتين). هي بتقلل التفرق: فولدر واحد قصاد 6، وصفر جيران من domains تانية قصاد 17.
  • اختبار المسح: امسح فولدر الـ feature، وtsc المفروض يشتكي في الـ app layer بس.
