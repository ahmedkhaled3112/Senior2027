Why this matters · ليه ده مهم

English

useEffect is where most React production bugs live: a duplicate charge from a POST behind a flag, a tab hammering your API in a silent loop, a socket still subscribed to the previous tenant, a drawer that leaks a listener each time it opens. None of these throws. They show up as load on your backend, wrong numbers and a heap that keeps growing. As the person who owns both sides of the API, you're the one who gets paged for them, and "give me three wrong effects and the right alternative" is on this section's exit test.

Part 1 — The effect lifecycle 🟡 Intermediateالجزء 1 — دورة حياة الـ effect

English

An effect isn't "code that runs on mount". It describes how to keep the component synchronized with something outside React: a socket, a subscription, a timer, a browser API. Its shape is a setup plus a cleanup, and it reads as a sentence: while tenantId is X, stay connected to X; when it changes, leave the old one and join the new one. Thinking in lifecycle events ("on mount", "on update") is what produces most of the bugs in this lesson. The two questions to ask are: what am I syncing with, and which values does that sync depend on?

The dependency array decides when React re-synchronizes, and it has exactly three forms:

  • No array: setup runs after every commit.
  • []: setup runs once after mount, cleanup once on unmount.
  • [a, b]: setup runs after mount, then whenever any entry differs from the previous render. Entries are compared one by one with Object.is, never deeply.

The order on a change matters: render with the new props, commit to the DOM, cleanup from the previous render, setup from the new render. The cleanup is a closure, so it still sees the old tenantId, which is exactly what you want when closing the old socket. Unmount runs the cleanup only. A re-render with equal deps runs neither.

import { useEffect } from "react";
import { createRoot } from "react-dom/client";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
const runs = { noArray: 0, empty: 0, tenant: 0, nan: 0, zero: 0, filters: 0 };

type Props = { tenantId: string; nan: number; zero: number; filters: { status: string } };

function Probe({ tenantId, nan, zero, filters }: Props) {
  // من غير array: بعد كل commit
  useEffect(() => { runs.noArray++; });
  // الـ array الفاضية: مرة واحدة بعد الـ mount
  useEffect(() => { runs.empty++; }, []);
  // الـ array اللي فيها قيم: لما قيمة منهم تتغير حسب Object.is
  useEffect(() => { runs.tenant++; }, [tenantId]);
  useEffect(() => { runs.nan++; }, [nan]);
  useEffect(() => { runs.zero++; }, [zero]);
  useEffect(() => { runs.filters++; }, [filters]);
  return null;
}

const root = createRoot(document.getElementById("root")!);

// نفس الـ tenant في أول 3 renders، وكل مرة object جديد بنفس المحتوى
for (const tenantId of ["acme", "acme", "acme", "globex"]) {
  const zero = tenantId === "globex" ? -0 : 0;
  root.render(<Probe tenantId={tenantId} nan={NaN} zero={zero} filters={{ status: "paid" }} />);
  await sleep(30);
}

بالعامية

الـ effect مش "كود بيشتغل على الـ mount". هو وصف لإزاي الـ component يفضل متزامن مع حاجة برّه React: socket، subscription، timer، browser API. شكله setup و cleanup، وبيتقري كأنه جملة: طول ما tenantId هو X خليك متوصل بـ X، ولما يتغير سيب القديم وادخل على الجديد. لما تفكر بـ lifecycle events زي "on mount" و "on update"، ده اللي بيطلّع معظم الـ bugs في الدرس ده. السؤالين اللي تسألهم: إنت بتعمل sync مع إيه؟ وإيه القيم اللي الـ sync ده معتمد عليها؟

الـ dependency array هي اللي بتحدد إمتى React يعيد الـ sync، وليها 3 أشكال بس:

  • من غير array: الـ setup بيشتغل بعد كل commit.
  • []: الـ setup مرة واحدة بعد الـ mount، والـ cleanup مرة واحدة على الـ unmount.
  • [a, b]: الـ setup بعد الـ mount، وبعدين كل ما أي قيمة تختلف عن الـ render اللي فات. المقارنة قيمة قيمة بـ Object.is، ومفيش مقارنة deep أبدًا.

الترتيب وقت التغيير مهم: render بالـ props الجديدة، بعدين commit على الـ DOM، بعدين cleanup بتاع الـ render اللي فات، بعدين setup بتاع الـ render الجديد. الـ cleanup ده closure، فلسه شايف tenantId القديم، وده بالظبط اللي إنت عايزه وإنت بتقفل الـ socket القديم. الـ unmount بيشغّل الـ cleanup بس. وأي re-render والـ deps زي ما هي مش بيشغّل حاجة منهم.

English

"Effects run after paint" is only roughly true. You saw the commit order in lesson 03; the react.dev reference is more careful about paint: "If your Effect wasn't caused by an interaction (like a click), React will generally let the browser paint the updated screen first", and "If your Effect is caused by an interaction (like a click), React may run your Effect before the browser paints the updated screen." I measured it with 40 updates of each kind, scheduling a requestAnimationFrame from the layout effect, since that callback runs right before the frame's paint.

A click is deterministic: the effect ran before the frame every time, because React flushes effects from discrete events synchronously. A timer gives a mix, because React only yields: it runs the effect in a separate task, and whether a frame comes first depends on whether one is due. The rule to code against: useEffect runs after commit, and it may land on either side of paint. If the work has to happen before paint, that's useLayoutEffect (Part 5).

import { useEffect, useLayoutEffect, useState } from "react";
import { createRoot } from "react-dom/client";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
const log: string[] = [];
let bumpFromTimer = () => {};

function UnreadBadge() {
  const [count, setCount] = useState(0);
  bumpFromTimer = () => setCount((c) => c + 1);
  useLayoutEffect(() => {
    log.push("layout effect");
    // الـ rAF بييجي قبل الـ paint مباشرة في نفس الـ frame
    requestAnimationFrame(() => log.push("frame"));
  }, [count]);
  useEffect(() => { log.push("effect"); }, [count]);
  return <button id="bump" onClick={() => setCount((c) => c + 1)}>{count}</button>;
}

createRoot(document.getElementById("root")!).render(<UnreadBadge />);
await sleep(200);

const tally = new Map<string, number>();
async function trial(name: string, update: () => void) {
  for (let i = 0; i < 40; i++) {
    log.length = 0;
    update();
    await sleep(60);
    const key = `${name}: ${log.join(" -> ")}`;
    tally.set(key, (tally.get(key) ?? 0) + 1);
  }
}

// تحديث جاي من timer أو response: مش user interaction
await trial("timer", () => setTimeout(bumpFromTimer, 0));
// تحديث جاي من click: ده discrete event
await trial("click", () => document.getElementById("bump")!.click());

for (const [k, v] of tally) console.log(`${v}x ${k}`);
console.log("--- done");

بالعامية

جملة "الـ effects بتشتغل بعد الـ paint" صح تقريبًا بس. الترتيب بتاع الـ commit شفته في الدرس 03، بس reference بتاع react.dev أدق في موضوع الـ paint: بيقول لو الـ effect مش جاي من interaction زي click، React في العادة بيسيب الـ browser يرسم الأول. ولو جاي من interaction زي click، ممكن React يشغّل الـ effect قبل ما الـ browser يرسم. قسته بـ 40 update من كل نوع، و requestAnimationFrame من جوه الـ layout effect، لأن الـ callback بتاعه بيشتغل قبل paint الـ frame على طول.

الـ click ثابت: الـ effect قبل الـ frame كل مرة، لأن React بيعمل flush للـ effects بتاعة الـ discrete events بشكل sync. الـ timer نتيجته متلخبطة، لأن React بس بيسيب مساحة: بيشغّل الـ effect في task لوحده، وإذا كان frame هييجي الأول ولا لأ ده حسب إذا كان فيه frame مستحق. القاعدة اللي تبني عليها: useEffect بيشتغل بعد الـ commit، وممكن ييجي قبل الـ paint أو بعده. ولو الشغل لازم يحصل قبل الـ paint، يبقى useLayoutEffect (الجزء 5).

فين هستخدمه في شغلي؟ dashboard فيها tenants كتير والمستخدم بيبدّل بينهم من dropdown: الـ [tenantId] هي اللي بتضمن إن الـ socket القديم يتقفل قبل الجديد ما يتفتح، فمفيش event من acme يظهر تحت globex. وفي code review لو شفت useEffect(() => { connect(tenantId) }, [])، ده bug مش style: المستخدم هيبدّل الـ tenant والـ socket هيفضل على القديم، وهيشوف orders مش بتاعته. الغلطة الشائعة هنا إنك تفكر "عايزها تشتغل مرة واحدة" بدل "متزامنة مع إيه".
Interview question "When does the cleanup run, and which values does it see?" → Before the next setup, when a dependency changed, and on unmount. It runs after the new render has been committed, and it sees the values from the render that created it, because it's a closure. That's why closing socket for the old tenant works with no extra bookkeeping.
"الـ cleanup بيشتغل إمتى، وبيشوف قيم إيه؟" ← قبل الـ setup الجاي لما dependency تتغير، وعلى الـ unmount. بيشتغل بعد ما الـ render الجديد اتعمله commit، وبيشوف قيم الـ render اللي عمله، لأنه closure. وعشان كده قفل socket بتاع الـ tenant القديم بيشتغل من غير أي حسابات زيادة.

Part 2 — The three classic bugs 🟡 Intermediateالجزء 2 — الـ 3 bugs الكلاسيكية

English

These three are the answer to exit-test question 3, and you'll meet all of them in real code.

1. Fetch without cleanup: a race. Responses arrive in network order, not request order. Type pa then paid; if the short query is slower, its response lands last and overwrites the right results. The fix is a cleanup that shuts the door on the old request. This is the short version: the full treatment with AbortController is in lesson 09.

import { useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

// الـ backend المتخيل: الـ query القصيرة أبطأ لأنها بترجع rows أكتر
const LATENCY: Record<string, number> = { pa: 300, paid: 50 };
async function searchOrders(query: string): Promise<string[]> {
  await sleep(LATENCY[query] ?? 10);
  return [`results for "${query}"`];
}

function BadSearch({ query }: { query: string }) {
  const [results, setResults] = useState<string[]>([]);
  useEffect(() => {
    // مفيش cleanup: اللي يوصل آخر هو اللي يكسب، مش اللي اتطلب آخر
    searchOrders(query).then(setResults);
  }, [query]);
  return <p id="bad">{results.join()}</p>;
}

function GoodSearch({ query }: { query: string }) {
  const [results, setResults] = useState<string[]>([]);
  useEffect(() => {
    let ignore = false;
    searchOrders(query).then((rows) => {
      if (!ignore) setResults(rows);
    });
    // الـ cleanup بيقفل الباب على الـ request القديم
    return () => {
      ignore = true;
    };
  }, [query]);
  return <p id="good">{results.join()}</p>;
}

function App({ query }: { query: string }) {
  return (
    <>
      <BadSearch query={query} />
      <GoodSearch query={query} />
    </>
  );
}

const root = createRoot(document.getElementById("root")!);
root.render(<App query="pa" />);
await sleep(20);
root.render(<App query="paid" />);
await sleep(500);

console.log("input shows: paid");
console.log("bad :", document.getElementById("bad")!.textContent);
console.log("good:", document.getElementById("good")!.textContent);
console.log("--- done");

bad : results for "pa"
good: results for "paid"
المستخدم كاتب paid، والـ bad عارض نتايج pa لأن الـ response بتاعها وصل آخر واحد. والـ good عارض النتايج الصح لأن الـ cleanup قفل على الـ request القديم.

الـ 3 دول هما إجابة السؤال 3 في اختبار الخروج، وهتقابلهم كلهم في كود حقيقي.

1. fetch من غير cleanup: race. الـ responses بتوصل بترتيب الشبكة، مش بترتيب الطلب. لو كتبت pa وبعدها paid والـ query القصيرة أبطأ، الـ response بتاعها هيوصل آخر واحد ويكتب فوق النتايج الصح. الحل cleanup يقفل الباب على الـ request القديم. ده الملخص بس، والشرح الكامل مع AbortController في الدرس 09.

English

2. Syncing state from props: a wrong commit. Copying a prop-derived value into state through an effect means the value is always one commit late. Switching from order A to order B commits B-2 total=300 first: B's id with A's total. That's twice the renders, and a window where the DOM holds a number that was never true. On an invoice page, that number can be painted.

import { useEffect, useLayoutEffect, useRef, useState } from "react";
import { createRoot } from "react-dom/client";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

type Order = { id: string; items: { price: number; qty: number }[] };
const orderA: Order = { id: "A-1", items: [{ price: 100, qty: 3 }] };
const orderB: Order = { id: "B-2", items: [{ price: 50, qty: 1 }] };
const totalOf = (order: Order) => order.items.reduce((sum, i) => sum + i.price * i.qty, 0);

const commits: string[] = [];

// كل commit بنسجّل اللي اتكتب في الـ DOM فعلًا
function useLogCommit(ref: React.RefObject<HTMLParagraphElement | null>) {
  useLayoutEffect(() => {
    commits.push(ref.current!.textContent!);
  });
}

function BadSummary({ order }: { order: Order }) {
  const ref = useRef<HTMLParagraphElement>(null);
  const [total, setTotal] = useState(0);
  // الغلط: state بنسخة من props، بتتأخر commit كامل
  useEffect(() => {
    setTotal(totalOf(order));
  }, [order]);
  useLogCommit(ref);
  return <p ref={ref}>{order.id} total={total}</p>;
}

function GoodSummary({ order }: { order: Order }) {
  const ref = useRef<HTMLParagraphElement>(null);
  // الصح: قيمة محسوبة في الـ render، مفيش حاجة تتأخر
  const total = totalOf(order);
  useLogCommit(ref);
  return <p ref={ref}>{order.id} total={total}</p>;
}

const root = createRoot(document.getElementById("root")!);

async function run(name: string, Summary: typeof BadSummary) {
  commits.length = 0;
  root.render(<Summary order={orderA} />);
  await sleep(300);
  root.render(<Summary order={orderB} />);
  await sleep(300);
  console.log(`${name}: ${commits.length} commits`);
  for (const c of commits) console.log(`  ${c}`);
  root.render(null);
  await sleep(50);
}

await run("bad", BadSummary);
await run("good", GoodSummary);

Part 4 — useEffectEvent 🟡 Intermediateالجزء 4 — useEffectEvent

English

This one isn't in the README, because it became stable in React 19.2 (October 2025). It solves a real conflict: inside an effect, some values should re-synchronize it and others should just be read at their latest value. A support chat must reconnect when orderId changes, but its "connected" toast only wants the current theme. Before this hook you had two bad options: put theme in the deps and reconnect on each toggle, or silence the linter and read a stale value.

useEffectEvent wraps the non-reactive part. The result can be called from the effect, always sees the latest props and state, and doesn't go in the deps. Below, a handshake is still in flight when the theme changes, and then the theme changes three more times:

import { useEffect, useEffectEvent } from "react";
import { createRoot } from "react-dom/client";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

let connects = 0;
const toasts: string[] = [];

// اتصال متخيل: الـ handshake بياخد 20ms، زي WebSocket أو SSE
function createConnection(orderId: string, onConnected: () => void) {
  let timer = 0;
  return {
    connect() {
      connects++;
      timer = window.setTimeout(onConnected, 20);
    },
    disconnect() {
      clearTimeout(timer);
    },
  };
}

type Props = { orderId: string; theme: "light" | "dark" };

// الغلط 1: theme في الـ deps، فكل تغيير theme بيقطع الاتصال ويفتحه تاني
function Reconnects({ orderId, theme }: Props) {
  useEffect(() => {
    const conn = createConnection(orderId, () => toasts.push(`${orderId}:${theme}`));
    conn.connect();
    return () => conn.disconnect();
  }, [orderId, theme]);
  return null;
}

// الغلط 2: شيلنا theme من الـ deps، فالـ toast بيقرا قيمة قديمة
function StaleTheme({ orderId, theme }: Props) {
  useEffect(() => {
    const conn = createConnection(orderId, () => toasts.push(`${orderId}:${theme}`));
    conn.connect();
    return () => conn.disconnect();
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [orderId]);
  return null;
}

// الصح: الاتصال reactive على orderId بس، والـ toast بيقرا آخر theme
function Fixed({ orderId, theme }: Props) {
  const onConnected = useEffectEvent(() => toasts.push(`${orderId}:${theme}`));
  useEffect(() => {
    const conn = createConnection(orderId, onConnected);
    conn.connect();
    return () => conn.disconnect();
  }, [orderId]);
  return null;
}

async function run(name: string, Chat: typeof Fixed) {
  connects = 0;
  toasts.length = 0;
  const root = createRoot(document.getElementById("root")!);
  root.render(<Chat orderId="o-1" theme="light" />);
  await sleep(5);
  // المستخدم غيّر الـ theme والـ handshake لسه شغال
  root.render(<Chat orderId="o-1" theme="dark" />);
  await sleep(50);
  // تلات تغييرات theme كمان على نفس الـ order
  for (const theme of ["light", "dark", "light"] as const) {
    root.render(<Chat orderId="o-1" theme={theme} />);
    await sleep(50);
  }
  console.log(`${name}: connects=${connects} toasts=${toasts.join(" ")}`);
  root.unmount();
}

await run("deps [orderId], lint off", StaleTheme);
await run("useEffectEvent", Fixed);

English

The rules, checked by running them:

  • Not in the deps array. The docs say it has no stable identity, and I counted 3 identities in 3 renders. The linter warns if you add it.
  • Only called from effects or other Effect Events. Calling it during render throws. Calling it from a click handler is not caught at runtime on 19.3.1: only the linter stops you, so keep the rule on.
  • Don't pass it to other components or hooks.
  • Not a way to silence deps. This is the trap. Hiding tenantId inside an Effect Event gives the same bug as [], and now the linter says nothing. Ask: if this value changes, should the sync restart? If yes, it's a dep.

Part 5 — useLayoutEffect and useInsertionEffect 🟡 Intermediateالجزء 5 — useLayoutEffect و useInsertionEffect

English

useLayoutEffect has the same API as useEffect but runs right after the DOM mutations and blocks paint, and any setState inside it re-renders synchronously before the browser draws. The classic case is a tooltip above its anchor: you can only compute its position after measuring its height, which needs it in the DOM. With useEffect, the browser can paint it in the wrong place first.

To prove it, I sample the tooltip's position in requestAnimationFrame, which runs right before each paint, across 40 opens per variant. Note that the flicker is intermittent. That's why it "works on my machine" and shows up on a slow phone.

import { useEffect, useLayoutEffect, useRef, useState } from "react";
import { createRoot } from "react-dom/client";

function makeTooltip(useMeasure: typeof useEffect) {
  return function Tooltip() {
    const ref = useRef<HTMLDivElement>(null);
    const [height, setHeight] = useState(0);
    useMeasure(() => {
      setHeight(ref.current!.getBoundingClientRect().height);
    }, []);
    return (
      <div ref={ref} id="tip" style={{ position: "fixed", left: 40, top: ANCHOR_TOP - height - 8, padding: 12 }}>
        Refund will reach the customer in 5 days
      </div>
    );
  };
}

So 200 rows doing read-then-write in a layout effect become read, write, read, write. Every read after a write forces a new layout: LayoutCount from Chrome goes up by 201, one per row plus the frame's own. There are three fixes, and the cheapest one to reach for is the last:

  • Batch in the parent. The parent's layout effect runs after all children are in the DOM, so read everything, then write everything.
  • ResizeObserver (taught here). It delivers sizes after layout, once per frame, with no forced read. It's also the right tool when sizes change later. Stop observing, or avoid changing the observed size, to prevent its loop error.
  • Solve it in CSS. If it can be expressed as padding, grid or flex, no measurement is needed at all.

function ObservedTable() {

English

How to find a leak with heap snapshots is in the JavaScript section. The React-specific part is where they come from: anything you open in an effect and don't close in its cleanup. A store subscription, a window listener and a setInterval are the usual three. Unmounting doesn't undo any of them, since React doesn't know they exist.

React 18 also removed the old "setState on an unmounted component" warning, so leaks are now silent. The demo mounts and unmounts each widget 1000 times, then reads live subscribers plus JSEventListeners, Nodes and JSHeapUsedSize from Chrome, after a forced GC.

import { useEffect, useRef, useState } from "react";

// ده store بسيط زي أي store خارجي: مجموعة subscribers
const cartStore = {
  subscribers: new Set<() => void>(),
  subscribe(fn: () => void) {
    this.subscribers.add(fn);
    return () => {
      this.subscribers.delete(fn);
    };
  },
};

let liveIntervals = 0;

// الغلط: 3 subscriptions ومفيش ولا cleanup
function LeakyWidget() {
  const [, setCount] = useState(0);
  const [lines] = useState(() => new Array(1000).fill("order line"));
  useEffect(() => {
    cartStore.subscribe(() => setCount(lines.length));
    window.addEventListener("resize", () => setCount(lines.length));
    liveIntervals++;
    setInterval(() => setCount(lines.length), 60_000);
  }, [lines]);
  return <div>cart widget</div>;
}

// أسوأ: الـ closure ماسك DOM node، فالـ node بيفضل عايش بعد الـ unmount
function LeakyDomWidget() {
  const ref = useRef<HTMLDivElement>(null);
  useEffect(() => {
    const el = ref.current!;
    cartStore.subscribe(() => {
      el.textContent = "updated";
    });
  }, []);
  return <div ref={ref}>cart widget</div>;
}

// الصح: كل حاجة اتفتحت بتتقفل في الـ cleanup
function CleanWidget() {
  const [, setCount] = useState(0);
  const [lines] = useState(() => new Array(1000).fill("order line"));
  useEffect(() => {
    const unsubscribe = cartStore.subscribe(() => setCount(lines.length));
    const onResize = () => setCount(lines.length);
    window.addEventListener("resize", onResize);
    liveIntervals++;
    const id = setInterval(() => setCount(lines.length), 60_000);
    return () => {
      unsubscribe();
      window.removeEventListener("resize", onResize);
      clearInterval(id);
      liveIntervals--;
    };
  }, [lines]);
  return <div>cart widget</div>;
}

// الأنضف للـ listeners: AbortController واحد بيقفلهم كلهم
function AbortWidget() {
  const [, setCount] = useState(0);
  const [lines] = useState(() => new Array(1000).fill("order line"));
  useEffect(() => {
    const controller = new AbortController();
    const { signal } = controller;
    const refresh = () => setCount(lines.length);
    window.addEventListener("resize", refresh, { signal });
    window.addEventListener("online", refresh, { signal });
    document.addEventListener("visibilitychange", refresh, { signal });
    return () => controller.abort();
  }, [lines]);
  return <div>cart widget</div>;
}

English

Read those lines closely, since they tell you what a leak actually retains:

  • The closure's captures are what stay alive. leaky holds about 5 MB, which matches 1000 arrays of 1000 entries captured by the callbacks.
  • DOM nodes depend on what you captured. leaky retains 0 nodes even though it calls setCount, because React detaches a fiber from its DOM on unmount, which limits the damage. dom captures the element directly, and 2000 nodes stay alive, each a div plus its text.
  • Timers keep running. Each leaked setInterval wakes up the main thread forever, for a component that doesn't exist.
  • AbortController is the cleanest cleanup for listeners. Pass one signal to every addEventListener and call abort() once. The same signal also cancels a fetch.

English

Stale closures are the other half of this README item. A function captures the variables of the render that created it (closures, in the JavaScript section). An interval created in an effect with [] keeps the closure of the first render forever, so seconds is 0 inside it, always. Hiding the warning with eslint-disable is how this reaches production. There are four fixes, and the choice depends on what the callback needs:

  • Deps [seconds]: correct but it recreates the interval on each tick, so a slow render can stretch the period.
  • Updater setSeconds((s) => s + 1): the best fix when the new state depends only on the old state.
  • useEffectEvent: when the callback must read a different latest value.
  • A ref written in an effect: the older way, and still what you need below React 19.2. Writing ref.current during render fails react-hooks/refs ("Cannot access refs during render"), so write it in an effect.
import { useEffect, useEffectEvent, useRef, useState } from "react";
import { createRoot } from "react-dom/client";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

let intervalsCreated = 0;

// الغلط: الـ closure اتعمل في أول render، فـ seconds جواه صفر للأبد
function StaleTimer() {
  const [seconds, setSeconds] = useState(0);
  useEffect(() => {
    intervalsCreated++;
    const id = setInterval(() => setSeconds(seconds + 1), 20);
    return () => clearInterval(id);
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, []);
  return <p>{seconds}</p>;
}

// الحل 1: حط seconds في الـ deps، بس الـ interval بيتعمل من أول وجديد كل tick
function DepsTimer() {
  const [seconds, setSeconds] = useState(0);
  useEffect(() => {
    intervalsCreated++;
    const id = setInterval(() => setSeconds(seconds + 1), 20);
    return () => clearInterval(id);
  }, [seconds]);
  return <p>{seconds}</p>;
}

// الحل 2: updater function، مش محتاج يقرا الـ state أصلًا
function UpdaterTimer() {
  const [seconds, setSeconds] = useState(0);
  useEffect(() => {
    intervalsCreated++;
    const id = setInterval(() => setSeconds((s) => s + 1), 20);
    return () => clearInterval(id);
  }, []);
  return <p>{seconds}</p>;
}

// الحل 3: لازم تقرا قيمة تانية من غير ما تعيد الـ interval: useEffectEvent
function EventTimer({ amount }: { amount: number }) {
  const [total, setTotal] = useState(0);
  const onTick = useEffectEvent(() => setTotal((t) => t + amount));
  useEffect(() => {
    intervalsCreated++;
    const id = setInterval(onTick, 20);
    return () => clearInterval(id);
  }, []);
  return <p>{total}</p>;
}

// الحل 4: قبل React 19.2 كان الـ ref هو الطريقة: آخر قيمة بتتكتب في effect
function RefTimer({ amount }: { amount: number }) {
  const [total, setTotal] = useState(0);
  const latestAmount = useRef(amount);
  useEffect(() => {
    latestAmount.current = amount;
  }, [amount]);
  useEffect(() => {
    intervalsCreated++;
    const id = setInterval(() => setTotal((t) => t + latestAmount.current), 20);
    return () => clearInterval(id);
  }, []);
  return <p>{total}</p>;
}

  console.log(`${name.padEnd(16)} shows ${shown.padStart(3)} after 300 ms, setInterval called ${intervalsCreated}x`);

  await sleep(30);
}

// قبل: state و effect لكل قيمة محسوبة
function Before({ lines }: { lines: Line[] }) {

  const [total, setTotal] = useState(0);

  const total = lines.reduce((sum, l) => sum + l.price * l.qty, 0);

}

2. Fix the search 🟡 medium An InvoiceSearch builds const filters = { status, query } during render and calls searchInvoices(filters).then(setResult) in an effect on [filters]. It has two bugs from Part 2. Fix both, and make a slow old request unable to overwrite a newer result, using AbortController this time.
InvoiceSearch بيعمل const filters = { status, query } في الـ render وبينادي searchInvoices(filters).then(setResult) في effect على [filters]. فيه 2 bugs من الجزء 2. صلّح الاتنين، وخلّي الـ request القديم البطيء ميقدرش يكتب فوق نتيجة أحدث، والمرة دي بـ AbortController.
Hint · تلميح Build the object inside the effect and depend on [status, query]. An abort rejects the promise, so it isn't an error to show.
اعمل الـ object جوه الـ effect واعتمد على [status, query]. والـ abort بيعمل reject للـ promise، بس ده مش error يتعرض للمستخدم.
Solution · الحل Two calls (one per query), and the final result belongs to the newest query even though the older one was slower.
نداءين، واحد لكل query، والنتيجة النهائية بتاعة أحدث query رغم إن القديمة كانت أبطأ.
import { useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

type Filters = { status: string; query: string };
let calls = 0;
const LATENCY: Record<string, number> = { in: 200, inv: 20 };

async function searchInvoices(filters: Filters, signal: AbortSignal): Promise<string> {
  calls++;
  await sleep(LATENCY[filters.query] ?? 5);
  signal.throwIfAborted();
  return `${filters.status}:${filters.query}`;
}

function InvoiceSearch({ status, query }: Filters) {
  const [result, setResult] = useState("");
  useEffect(() => {
    const controller = new AbortController();
    searchInvoices({ status, query }, controller.signal)
      .then(setResult)
      .catch((error: unknown) => {
        // الـ abort مش خطأ حقيقي: الـ request اتلغى عشان فيه أحدث منه
        if (!controller.signal.aborted) throw error;
      });
    return () => controller.abort();
  }, [status, query]);
  return <p id="result">{result}</p>;
}

const root = createRoot(document.getElementById("root")!);
root.render(<InvoiceSearch status="paid" query="in" />);
await sleep(10);
root.render(<InvoiceSearch status="paid" query="inv" />);
await sleep(400);
console.log(`calls=${calls} final=${document.getElementById("result")!.textContent}`);
root.unmount();
console.log("--- done");
calls=2 final=paid:inv
نداءين بس، والنتيجة النهائية paid:inv، يعني أحدث query.
3. A polling hook that doesn't restart 🔴 hard Write useOrdersPolling({ tenantId, intervalMs, fetchOrders, onOrders }). It must keep one interval when the caller passes new inline callbacks, always call the latest callback, restart when tenantId or intervalMs changes, and leave no timer after unmount. Prove it with Vitest fake timers.
اكتب useOrdersPolling({ tenantId, intervalMs, fetchOrders, onOrders }). لازم يفضل interval واحد لما اللي بينادي يبعت callbacks جديدة inline، وينادي دايمًا آخر callback، ويبدأ من جديد لما tenantId أو intervalMs يتغير، وميسيبش أي timer بعد الـ unmount. وأثبتها بـ fake timers في Vitest.
Hint · تلميح tenantId and intervalMs are reactive. The callbacks aren't: that's useEffectEvent. vi.getTimerCount() shows the live timers.
tenantId و intervalMs قيم reactive. الـ callbacks لأ: يبقى useEffectEvent. وvi.getTimerCount() بيوريك الـ timers العايشة.
Solution · الحل The hook is five lines. The test passes on Vitest 5 with jsdom.
الـ hook خمس سطور، والـ test بينجح على Vitest 5 مع jsdom.
import { useEffect, useEffectEvent } from "react";
import { act, renderHook } from "@testing-library/react";
import { afterEach, beforeEach, expect, it, vi } from "vitest";

type Options = {
  tenantId: string;
  intervalMs: number;
  fetchOrders: (tenantId: string) => number;
  onOrders: (count: number) => void;
};

function useOrdersPolling({ tenantId, intervalMs, fetchOrders, onOrders }: Options) {
  // الـ callbacks بتتغير كل render عند اللي بينادي: مش سبب نعيد الـ interval
  const onTick = useEffectEvent(() => onOrders(fetchOrders(tenantId)));
  useEffect(() => {
    const id = setInterval(onTick, intervalMs);
    return () => clearInterval(id);
  }, [tenantId, intervalMs]);
}

beforeEach(() => vi.useFakeTimers());
afterEach(() => vi.useRealTimers());

it("keeps one interval when callbacks change, restarts on tenant, stops on unmount", () => {
  const fetchOrders = vi.fn((tenantId: string) => tenantId.length);
  const seen: string[] = [];
  const { rerender, unmount } = renderHook((props: { tenantId: string; label: string }) =>
    useOrdersPolling({
      tenantId: props.tenantId,
      intervalMs: 1000,
      fetchOrders,
      onOrders: (count) => seen.push(`${props.label}:${count}`),
    }),
    { initialProps: { tenantId: "acme", label: "a" } },
  );

  // عملية re-render بـ callback جديد في نص الـ interval: العداد مش بيبدأ من الأول
  act(() => vi.advanceTimersByTime(500));
  rerender({ tenantId: "acme", label: "b" });
  expect(vi.getTimerCount()).toBe(1);
  act(() => vi.advanceTimersByTime(500));
  // الـ tick بيستخدم آخر callback
  expect(seen).toEqual(["b:4"]);

  // تغيير الـ tenant بيعيد الـ interval
  rerender({ tenantId: "globex", label: "b" });
  expect(vi.getTimerCount()).toBe(1);
  act(() => vi.advanceTimersByTime(1000));
  expect(fetchOrders).toHaveBeenLastCalledWith("globex");
  expect(seen).toEqual(["b:4", "b:6"]);

  unmount();
  expect(vi.getTimerCount()).toBe(0);
});

Cheat sheet · الخلاصة

  • An effect syncs with an external system: setup plus cleanup. Ask what it syncs with, not when it runs.
  • Deps: none means every commit; [] means mount; [a] means when a changes by Object.is. New object or function means it runs each time.
  • Order on change: render, commit, old cleanup (sees old values), new setup. Unmount: cleanup only.
  • useEffect runs after commit and may land on either side of paint. From a click it runs before paint, so slow work there hurts INP.
  • Three classic bugs: fetch with no cleanup (race), props copied to state (wrong commit), object dep (loop). The async loop is completely silent.
  • Not for effects: derived values (render), reset (key), user events (handler), chains, notifying a parent. A flag plus an effect for a POST double-fires.
  • useEffectEvent (19.2): read the latest value without restarting. Not in deps, only from effects, and hiding a real dep in it is silent.
  • useLayoutEffect: measure then adjust, before paint; it blocks paint. useInsertionEffect: CSS-in-JS libraries only, no refs, no setState. Neither runs on the server.
  • Children's effects run before the parent's. Per-row read and write means per-row layout (201 vs 2): batch in the parent, use ResizeObserver, or use CSS.
  • Leaks are silent since React 18. Clean up each subscription, listener and timer; AbortController closes a group. Watch listeners and nodes in the Performance monitor.
  • Stale closure fixes: updater first, then deps, then useEffectEvent, then a ref written in an effect. Never eslint-disable.
بالعامية
  • الـ effect بيعمل sync مع نظام خارجي: setup و cleanup. اسأل بيعمل sync مع إيه، مش بيشتغل إمتى.
  • الـ deps: من غير array يعني كل commit، و[] يعني الـ mount، و[a] يعني لما a تتغير بـ Object.is. وأي object أو function جديد يعني بيشتغل كل مرة.
  • الترتيب وقت التغيير: render، بعدين commit، بعدين الـ cleanup القديم (بيشوف القيم القديمة)، بعدين الـ setup الجديد. والـ unmount: cleanup بس.
  • useEffect بيشتغل بعد الـ commit، وممكن ييجي قبل الـ paint أو بعده. ولو من click بيشتغل قبل الـ paint، فالشغل البطيء فيه بيضر الـ INP.
  • الـ 3 bugs الكلاسيكية: fetch من غير cleanup (race)، و props منسوخة في state (commit غلط)، و object في الـ deps (loop). والـ loop الـ async ساكت تمامًا.
  • مش مكانها effect: القيم المحسوبة (الـ render)، والتصفير (key)، وأحداث المستخدم (الـ handler)، والـ chains، وتبليغ الأب. وflag مع effect لـ POST بيبعت مرتين.
  • useEffectEvent (19.2): تقرا آخر قيمة من غير ما تعيد الـ sync. ميتحطش في الـ deps، بيتنادى من effects بس، وإخفاء dep حقيقية فيه بيعدّي ساكت.
  • useLayoutEffect: قيس وبعدين عدّل قبل الـ paint، وبيوقف الـ paint. useInsertionEffect: مكتبات CSS-in-JS بس، من غير refs ومن غير setState. والاتنين مش بيشتغلوا على الـ server.
  • effects الأبناء قبل بتاعة الأب. قراية وكتابة لكل row يعني layout لكل row (201 مقابل 2): جمّع في الأب، أو ResizeObserver، أو CSS.
  • الـ leaks ساكتة من أيام React 18. اقفل كل subscription و listener و timer، وAbortController بيقفل مجموعة. وراقب الـ listeners والـ nodes في Performance monitor.
  • حلول الـ stale closure: الـ updater الأول، بعدين الـ deps، بعدين useEffectEvent، بعدين ref بيتكتب في effect. وعمرك ما تستخدم eslint-disable.
