Why this matters · ليه ده مهم

English

Most React bugs in a full-stack developer's code aren't exotic. A handler runs during render and charges a card. A form reloads the page on Enter and cancels the POST that was in flight. An effect opens a second WebSocket. A poll keeps sending the previous tenant's id because someone silenced a lint rule. All of these come from not having an exact picture of what React does between a user action and the pixels on screen.

This lesson builds that picture by running each step in real Chrome on React 19.3: how an event reaches your handler, who owns an input's value, when a component really renders, what commit means, and why StrictMode runs things twice. The last part covers the toolchain you actually get from npm create vite in November 2026, which has changed more than most tutorials admit. "When does a component re-render?" and "render vs commit" are also the first exit questions in this section's README.

بالعامية

معظم الـ bugs بتاعة React في كود الـ full-stack developer مش حاجات غريبة. handler بيشتغل أثناء الـ render ويخصم من الكارت. form بيعمل reload للصفحة لما تدوس Enter ويلغي الـ POST اللي كان ماشي. effect بيفتح WebSocket تاني. polling فاضل بيبعت id الـ tenant القديم عشان حد سكّت lint rule. كل دول جايين من إنك معندكش صورة دقيقة للي React بيعمله بين ضغطة اليوزر والـ pixels اللي على الشاشة.

الدرس ده بيبني الصورة دي بإنه يشغّل كل خطوة في Chrome بجد على React 19.3: الـ event بيوصل للـ handler بتاعك إزاي، مين صاحب قيمة الـ input، الـ component بيعمل render إمتى بالظبط، يعني إيه commit، وليه StrictMode بيشغّل الحاجات مرتين. والجزء الأخير عن الـ toolchain اللي بتاخده فعلًا من npm create vite في نوفمبر 2026، وده اتغيّر أكتر مما معظم الـ tutorials بتقول. وسؤال "الـ component بيعمل re-render إمتى؟" و"render ضد commit" هما كمان أول أسئلة اختبار الخروج في الـ README بتاع القسم.

Part 1 — Synthetic events 🟢 Basicالجزء 1 — الـ synthetic events

English

An onClick in JSX is not addEventListener on that element. React attaches its listeners to the root container, the #root you passed to createRoot. When a native event reaches the root, React works out which components it passed through and calls their handlers in order: capture handlers first, then bubble handlers. Event delegation itself is already taught in JavaScript lesson 14, Part 3. What's new here is what React hands your handler.

That object is a SyntheticEvent: a thin wrapper with the same API as the native event (target, currentTarget, preventDefault(), stopPropagation()), plus nativeEvent, the real browser event inside it. In the run below, e.currentTarget is the <li> you attached the handler to, but e.nativeEvent.currentTarget is root. That's the proof of where the real listener lives. Three behaviours follow from it, and you can read each one in the output:

  • A native listener on the row runs before the React row handler, because the native event passes the <li> on its way up and reaches React only at the root.
  • stopPropagation() ends React's walk, so the row's onClick doesn't fire. It also stops the native event at the root, so the document listener never runs. It can't undo the native row listener, which already ran.
  • preventDefault() cancels the browser's default action (here the navigation to the PDF, so the path stays /page) and has nothing to do with propagation: the row's onClick still fires.

onClickCapture runs first on the way down, even when a child later stops propagation. If you read an old tutorial that talks about event pooling and e.persist(): pooling was removed in React 17. On 19.3 the method still exists and does nothing, and e.isPersistent() returned true when I ran it.

import { flushSync } from "react-dom";
import { createRoot } from "react-dom/client";

  function openDetails(e: MouseEvent<HTMLLIElement>) {
    // الـ target هو اللي اتداس عليه، والـ currentTarget هو اللي الـ handler راكب عليه
    console.log("React row onClick", {
      target: (e.target as HTMLElement).tagName,
      currentTarget: e.currentTarget.tagName,
      // الـ native event لسه موجود، وجواه الـ listener الحقيقي على الـ root
      nativeType: e.nativeEvent.constructor.name,
      nativeCurrentTarget: (e.nativeEvent.currentTarget as HTMLElement).id,
    });
  }

  function refund(e: MouseEvent<HTMLButtonElement>) {
    // لولا السطر ده الضغطة هتطلع للصف وتفتح الـ details كمان
    e.stopPropagation();
    console.log(`React refund ${orderId}`);
  }

  function downloadInvoice(e: MouseEvent<HTMLAnchorElement>) {
    // الـ preventDefault بيوقف الـ navigation بس، مش الـ bubbling
    e.preventDefault();
    console.log("React invoice link, defaultPrevented =", e.defaultPrevented);
  }

  return (
    <li id="row" onClick={openDetails} onClickCapture={() => console.log("React row onClickCapture")}>
      <span id="label">{orderId}</span>
      <button id="refund" onClick={refund}>Refund</button>
      <a id="invoice" href="/invoices/1001.pdf" onClick={downloadInvoice}>Invoice</a>
    </li>
  );
}

بالعامية

onClick في الـ JSX مش addEventListener على العنصر ده. React بيركّب الـ listeners بتاعته على الـ root container، يعني الـ #root اللي ادّيته لـ createRoot. لما الـ native event يوصل للـ root، React بيحسب هو عدّى على أنهي components وينادي الـ handlers بتاعتهم بالترتيب: الـ capture الأول وبعدين الـ bubble. فكرة الـ delegation نفسها اتشرحت في درس 14 في JavaScript، الجزء 3. الجديد هنا هو اللي React بيديهولك في الـ handler.

الحاجة دي اسمها SyntheticEvent: wrapper خفيف ليه نفس API الـ native event (target، currentTarget، preventDefault()، stopPropagation())، وزيادة عليهم nativeEvent وده الـ event الحقيقي بتاع الـ browser. في التشغيل فوق e.currentTarget هو الـ <li> اللي ركّبت عليه الـ handler، بس e.nativeEvent.currentTarget هو root. ده الدليل على مكان الـ listener الحقيقي. وطالع من كده 3 حاجات تقدر تقراهم في الـ output:

  • الـ native listener على الصف بيشتغل قبل الـ React handler بتاع الصف، لأن الـ native event بيعدّي على الـ <li> وهو طالع، ومابيوصلش لـ React غير عند الـ root.
  • stopPropagation() بينهي مشي React في الشجرة، فـ onClick بتاع الصف مش بيشتغل. وكمان بيوقف الـ native event عند الـ root، فالـ listener اللي على document عمره ما بيشتغل. بس مش بيقدر يرجّع الـ native row listener، لأنه خلاص اشتغل.
  • preventDefault() بيلغي الفعل الافتراضي بتاع الـ browser (هنا الانتقال للـ PDF، فالـ path بيفضل /page) وملوش علاقة بالـ propagation: onClick بتاع الصف بيشتغل برضه.

وonClickCapture بيشتغل الأول وهو نازل، حتى لو ابن وقّف الـ propagation بعد كده. ولو قريت tutorial قديم بيتكلم عن event pooling وe.persist(): الـ pooling اتشال في React 17. في 19.3 الـ method لسه موجودة ومش بتعمل حاجة، وe.isPersistent() رجّعت true لما شغّلتها.

فين هستخدمه في شغلي؟ جدول orders في الـ admin: الصف كله بيفتح صفحة الـ order، وجواه زرار Refund. من غير stopPropagation الضغطة على Refund هتعمل refund وتفتح الصفحة كمان. بس خد بالك: لو عندك analytics أو "click outside" سامع على document، الضغطة دي مش هتوصله خالص. فلو جالك ticket "الـ analytics مش بيسجّل ضغطات Refund"، ده أول مكان تبص فيه. الأنضف ساعات تسيب الـ event يطلع وتشيّك في handler الصف بـ e.target.closest("button").
Interview question "e.stopPropagation() in a React handler doesn't stop a native listener on the same element. Why?" → The native listener already ran. React's listener sits on the root, so the native event has bubbled through the element before React dispatches anything. The call does stop the event from going past the root, which is why document listeners don't see it.
"e.stopPropagation() في React handler مش بيوقف native listener على نفس العنصر. ليه؟" ← لأن الـ native listener خلاص اشتغل. الـ listener بتاع React على الـ root، فالـ native event بيكون عدّى على العنصر قبل ما React يعمل أي dispatch. بس الـ call ده بيمنع الـ event يعدّي الـ root، وعشان كده listeners الـ document مش بتشوفه.

The classic bug: onClick={pay()}الـ bug الكلاسيكي: onClick={pay()}

English

onClick wants a function. onClick={pay()} calls pay during render and passes its return value, undefined, as the handler. So the render now has a side effect, and the button does nothing. In the run below: 1 charge at mount, 3 more from typing 3 letters in an unrelated input, and 4 charges in total with zero clicks. The one real click adds nothing. TypeScript catches this one because pay returns void; plain JavaScript ships it silently. The fix is a reference, onClick={pay}, or an arrow when you need arguments, onClick={() => pay(order.id)}.

import { useState } from "react";
import { createRoot } from "react-dom/client";

let charges = 0;
function pay() {
  charges++;
  console.log(`POST /charges -> charge #${charges}`);
}

function Checkout() {
  const [coupon, setCoupon] = useState("");
  // ❌ الأقواس بتنادي pay دلوقتي أثناء الـ render، مش لما اليوزر يدوس
  // ✗ TS2322: Type 'void' is not assignable to type 'MouseEventHandler<HTMLButtonElement> | undefined'.
  return (
    <>
      <input id="coupon" value={coupon} onChange={(e) => setCoupon(e.target.value)} />
      <button id="pay" onClick={pay()}>Pay</button>
    </>
  );
}

createRoot(document.getElementById("root")!).render(<Checkout />);

بالعامية

onClick عايز function. onClick={pay()} بينادي pay أثناء الـ render ويدّي الناتج بتاعها، يعني undefined، كـ handler. فبقى الـ render عنده side effect والزرار مش بيعمل حاجة. في التشغيل فوق: خصم عند الـ mount، و3 كمان من كتابة 3 حروف في input ملوش علاقة، يعني 4 خصومات من غير ولا ضغطة، والضغطة الحقيقية مش بتزوّد حاجة. TypeScript بيمسكها هنا لأن pay بترجّع void، بس JavaScript العادي بيعدّيها في صمت. الحل: reference زي onClick={pay}، أو arrow لو محتاج arguments زي onClick={() => pay(order.id)}.

فين هستخدمه في شغلي؟ في code review دوّر على onClick={name( بالظبط. وصورتها في production: الـ logs بتاعة POST /analytics أو POST /charges فيها آلاف الـ requests من صفحة ماحدش داس فيها على حاجة، والعدد ماشي مع الكتابة في الـ inputs مش مع الضغطات.

Part 2 — Controlled vs uncontrolled inputs 🟢 Basicالجزء 2 — الـ controlled ضد الـ uncontrolled

English

The question is who owns the value. In a controlled input, React state does: every keystroke goes onChange → setState → render → React writes the value back to the DOM. That round trip is what lets you format as the user types, enable a button from the value, or reset the field with one setState. In an uncontrolled input, the DOM does: defaultValue sets the starting value only, and you read the current one with a ref or FormData when you need it. There's no render per keystroke.

<input type="file"> is always uncontrolled, because only the user may choose a file. JavaScript may set its value to the empty string and nothing else. I ran value="receipt.pdf" on one: the browser throws InvalidStateError and, with no error boundary, React unmounts the whole tree.

import { useRef, useState, type ChangeEvent } from "react";
import { createRoot } from "react-dom/client";

function formatCoupon(raw: string): string {
  return raw.toUpperCase().replace(/[^A-Z0-9]/g, "").slice(0, 8);
}

// (1) الـ controlled: الـ state هي مصدر الحقيقة، والـ DOM بيعرض اللي هي بتقوله
function CouponField() {
  const [coupon, setCoupon] = useState("");
  return (
    <input
      id="coupon"
      value={coupon}
      onChange={(e: ChangeEvent<HTMLInputElement>) => setCoupon(formatCoupon(e.target.value))}
    />
  );
}

// (2) الـ uncontrolled: الـ DOM هو مصدر الحقيقة، وبنقرا القيمة لما نحتاجها بس
function DeliveryNote() {
  const noteRef = useRef<HTMLTextAreaElement>(null);
  return (
    <>
      <textarea id="note" ref={noteRef} defaultValue="Leave at the door" />
      <button id="read-note" onClick={() => console.log("note =", noteRef.current?.value)}>Read note</button>
    </>
  );
}

// (3) الـ file input دايمًا uncontrolled: الـ browser بس هو اللي يقدر يملاه
function ReceiptUpload() {
  const fileRef = useRef<HTMLInputElement>(null);
  return (
    <>
      <input
        id="receipt"
        type="file"
        ref={fileRef}
        onChange={(e) => console.log("picked:", e.target.files?.[0]?.name ?? "(none)")}
      />
      <button
        id="clear-receipt"
        onClick={() => {
          // المسموح بس هو تفضيته بـ string فاضية
          fileRef.current!.value = "";
          console.log("files after clear:", fileRef.current!.files?.length);
        }}
      >
        Clear
      </button>
    </>
  );
}

createRoot(document.getElementById("root")!).render(
  <>
    <CouponField />
    <DeliveryNote />
    <ReceiptUpload />
  </>,
);

بالعامية

السؤال هو مين صاحب القيمة. في الـ controlled الـ state بتاعة React هي الصاحب: كل حرف بيمشي onChange ← setState ← render ← React يكتب القيمة تاني في الـ DOM. اللفة دي هي اللي بتخليك تعمل formatting وانت بتكتب، أو تفتح زرار حسب القيمة، أو تصفّر الـ field بـ setState واحدة. في الـ uncontrolled الـ DOM هو الصاحب: defaultValue بتحدد قيمة البداية بس، وبتقرا القيمة الحالية بـ ref أو FormData لما تحتاجها. ومفيش render مع كل حرف.

<input type="file"> دايمًا uncontrolled، لأن اليوزر بس هو اللي من حقه يختار ملف. الـ JavaScript مسموحله يخلي القيمة string فاضية وبس. جرّبت value="receipt.pdf": الـ browser بيرمي InvalidStateError، ومن غير error boundary، React بيشيل الـ tree كلها من الصفحة.

فين هستخدمه في شغلي؟ خانة كوبون أو رقم كارت لازم تتظبط وانت بتكتب: controlled. فورم feedback أو note طويلة بتتقرا عند الـ submit بس: uncontrolled مع FormData بيوفّر كود وrenders. رفع صورة الإيصال: file input بـ ref، وبعد نجاح الـ upload تعمل ref.current.value = "" عشان اليوزر يقدر يختار نفس الملف تاني ويشتغل onChange.

The warnings React really printsالتحذيرات اللي React بيطبعها فعلًا

English

Three mistakes produce three different dev-only messages. These were copied from Chrome on React 19.3.1. Note that the first isn't only a warning: typing into that field really does nothing. The second appears on the first keystroke, not at mount, because the input only becomes controlled at that moment. The fix for all of them is the same idea: a controlled input always gets a string, so start from useState("") and convert with value={customer.phone ?? ""}.

import { useState } from "react";
import { createRoot } from "react-dom/client";

// (1) فيه value ومفيش onChange: الـ field بقى read-only من غير ما تقصد
function ReadOnlyByAccident() {
  return <input id="locked" value="SAVE10" />;
}

// (2) الـ state بدأت undefined فالـ input بدأ uncontrolled، وبعدين بقت string
function LoadedLater() {
  const [email, setEmail] = useState<string>();
  return <input id="email" value={email} onChange={(e) => setEmail(e.target.value)} />;
}

// (3) الـ API رجّع null لعمود فاضي في الـ DB وحطيناه زي ما هو
function NullFromApi({ phone }: { phone: string | null }) {
  // @ts-expect-error ⁧الـ value مش بتقبل null في الـ types⁩
  return <input id="phone" value={phone} onChange={() => {}} />;
}

createRoot(document.getElementById("root")!).render(
  <>
    <ReadOnlyByAccident />
    <LoadedLater />
    <NullFromApi phone={null} />
  </>,
);

What breaks: the caret jumpإيه اللي بيكسر: قفزة الـ caret

English

Formatting has a cost that tutorials skip. When the value React writes back differs from what the user typed, the browser moves the caret to the end. I put the caret in the middle of SAVE10 and typed two letters with a real keyboard in three versions: uppercase formatting, no formatting, and a setState delayed by setTimeout. Both the formatted one and the delayed one jump, which is also why a controlled input must update its state synchronously in onChange. A pragmatic fix is to write the formatted value yourself and restore the caret; then React finds nothing to change. For display-only uppercase, CSS text-transform: uppercase plus normalizing on submit avoids the problem entirely.

import { useState, type ChangeEvent } from "react";
import { createRoot } from "react-dom/client";

function formatCoupon(raw: string): string {
  return raw.toUpperCase().replace(/[^A-Z0-9]/g, "").slice(0, 8);
}

function CouponField() {
  const [coupon, setCoupon] = useState("SAVE10");

  function handleChange(e: ChangeEvent<HTMLInputElement>) {
    const input = e.target;
    const next = formatCoupon(input.value);
    // مكان الـ caret الجديد = طول اللي قبله بعد الـ formatting
    const caret = formatCoupon(input.value.slice(0, input.selectionStart ?? 0)).length;
    // بنكتب القيمة في الـ DOM بإيدنا، فـ React ميلاقيش فرق ومايحرّكش الـ caret
    input.value = next;
    input.setSelectionRange(caret, caret);
    setCoupon(next);
  }

  return <input id="coupon" value={coupon} onChange={handleChange} />;
}

Part 3 — Form submission 🟢 Basicالجزء 3 — الـ form submission

English

Put submit logic in <form onSubmit>, not in a button's onClick. A real form gives you Enter to submit, native validation (required, pattern), and what password managers and assistive tech expect. I pressed Enter with Playwright in five variants, and the result is less simple than "Enter doesn't work without a form":

  • A, the correct one: Enter calls the handler once and nothing reloads.
  • B (no form) and C (form, two inputs, type="button"): Enter does nothing at all, so keyboard users can't submit.
  • D (form, one input, type="button"): Enter submits the form natively. The HTML spec's implicit submission still applies when a form has a single text field and no submit button. Your handler never runs and the page reloads.
  • E (a <button> with no type inside a form, so it's type="submit", and no preventDefault): the browser synthesizes a click, so pay() runs, and then the page reloads, which throws away React state and cancels anything in flight.

Look at the URL in D and E: ?coupon=SAVE10. A native GET submit puts your fields in the query string, and from there in server access logs and browser history.

Reading the form: FormData and e.submitterقراءة الفورم: FormData وe.submitter

English

new FormData(e.currentTarget, e.submitter) reads every named field, and the second argument adds the name and value of the button that was used, so "Pay" and "Save draft" can share one handler. Three details from the run below. All values are strings ("25000"), so parse them, with Zod's coercion for example (lesson 12, Part 5). Pressing Enter gives submitter: pay, not null, because Enter activates the first submit button in the form, so a "Delete" button placed first would be what Enter triggers. And e.currentTarget is null after an await, because React resets it when the synchronous part of the handler ends; e.target survives. Save what you need before the first await.

onSubmit's event type in @types/react 19.3 is SubmitEvent; FormEvent is deprecated (TypeScript lesson 9, Part 3). React 19 also lets you write <form action={fn}>, which is covered in lesson 19, Part 4.

import { useState, type SubmitEvent } from "react";
import { createRoot } from "react-dom/client";

async function postCharge(body: unknown, idempotencyKey: string) {
  const res = await fetch("/api/charges", {
    method: "POST",
    headers: { "content-type": "application/json", "idempotency-key": idempotencyKey },
    body: JSON.stringify(body),
  });
  return (await res.json()) as { chargeId: string; replayed: boolean };
}

function CheckoutForm() {
  const [pending, setPending] = useState(false);
  // المفتاح بيتولد مرة لكل محاولة دفع، مش مرة لكل ضغطة
  const [attemptKey] = useState(() => crypto.randomUUID());

  async function handleSubmit(e: SubmitEvent<HTMLFormElement>) {
    e.preventDefault();
    // (1) اقرا الفورم قبل أي await: الـ currentTarget بيبقى null بعدها
    const form = e.currentTarget;
    // (2) الزرار اللي داس عليه اليوزر بيتبعت مع الـ data لو ادّيته لـ FormData
    const data = new FormData(form, e.submitter);

    try {
      const charge = await postCharge(payload, attemptKey);
      console.log("charge", charge.chargeId, "replayed:", charge.replayed);
      console.log("currentTarget after await:", e.currentTarget);
    } finally {
      setPending(false);
    }
  }

  // الزرارين submit، والفرق بينهم في الـ name والـ value
  return (
    <form id="checkout" onSubmit={handleSubmit}>
      <input id="coupon" name="coupon" defaultValue="SAVE10" />

The double charge: UI guard vs server guaranteeالخصم المزدوج: حماية الـ UI ضد ضمان السيرفر

English

A real double click on an unguarded form sends 2 POSTs and the server charges twice (first line of the output). Disabling the button while pending stops it: 1 POST, and pressing Enter during that window doesn't submit either, because the default button is disabled. setPending(true) has to come before the first await. When I put a 50 ms await validateCoupon() before it, the double click sent 2 POSTs again.

But disabling is UX, not protection. It can't stop a client retry after a timeout, a second tab, a page refresh, or a script calling your API. The real protection lives on the server: an idempotency key, generated once per payment attempt and sent with every try. Two POSTs with one key give one charge and the same chargeId, with the second marked replayed: true. A fresh key per click gives two charges, because the server can't tell they're the same attempt. Note that crypto.randomUUID() exists only in secure contexts: HTTPS and localhost, not plain HTTP on a LAN IP. The Map below is a stand-in; the production version (a unique constraint in Postgres, an in-progress state, replay, expiry) is in Node lesson 14, Part 6.

import type { IncomingMessage, ServerResponse } from "node:http";

type Charge = { chargeId: string; amountCents: number };

// في production ده جدول فيه UNIQUE على الـ key، مش Map في الـ memory
const byKey = new Map<string, Charge>();
let realCharges = 0;

export function handleCharge(req: IncomingMessage, res: ServerResponse) {
  const key = req.headers["idempotency-key"];
  const replay = typeof key === "string" ? byKey.get(key) : undefined;

  // نفس المفتاح اتشاف قبل كده: رجّع نفس النتيجة من غير ما تخصم تاني
  if (replay) {
    res.setHeader("content-type", "application/json");
    res.end(JSON.stringify({ ...replay, replayed: true }));
    return;
  }

  realCharges++;
  const charge: Charge = { chargeId: `ch_${realCharges}`, amountCents: 25000 };
  if (typeof key === "string") byKey.set(key, charge);

  res.setHeader("content-type", "application/json");
  res.end(JSON.stringify({ ...charge, replayed: false }));
}

export const countRealCharges = () => realCharges;
export function resetCharges() {
  realCharges = 0;
  byKey.clear();
}

Part 4 — What triggers a render 🟢 Basicالجزء 4 — إيه اللي بيعمل render

English

A component renders for one of four reasons: the initial render from root.render, a state change in that component, its parent re-rendered, or a context it reads changed. "Its props changed" is not on the list. Props get new values only as a result of a parent rendering, so a changed prop with no parent render does nothing. The counters below were read from a real run with no StrictMode, so each render counts once.

  • Parent re-render (step 2): CartHeader takes no props at all and still re-renders. Children re-render by default whether or not their props changed, unless they're wrapped in memo, as CartFooter is. Lesson 8, Part 2 covers when that's worth doing.
  • Same value (steps 3 to 6): React compares with Object.is and bails out, but read the counter closely. The first setQty(5) after a real change still renders CartPage once more (step 4), without going to its children. After that the count stays flat (steps 5, 6). The docs warn about this, so an extra render on the parent alone isn't a bug. Object.is is also why a new object or array always renders (lesson 2, Part 5).
  • A changed prop alone (step 7): mutating the object behind priceRef changes the value PriceTag received, and nothing renders. The DOM still says 100. It says 999 only when an unrelated state change forces a render (step 8), which is exactly why this looks like a random, timing-related bug in real apps.
  • Context (step 9): only the provider and the consumer render. CartTotal renders even inside a memoized parent, while CartPage doesn't, because the provider's children prop is the same element it received last time.

"الـ props اتغيرت" مش في القايمة. الـ props بتاخد قيم جديدة بس كنتيجة لـ render الأب، فـ prop اتغير من غير render للأب مش بيعمل حاجة. العدادات فوق متقرية من تشغيل حقيقي من غير StrictMode، فكل render بيتعد مرة.

Part 5 — Render vs commit 🟡 Intermediateالجزء 5 — الـ render ضد الـ commit

English

Rendering doesn't mean touching the DOM. After a trigger there are two phases. In the render phase React calls your components and works out what changed; this is a pure calculation that writes nothing to the screen, and it may be called more than once or thrown away. In the commit phase React detaches old refs, applies the minimal DOM changes, attaches new refs and runs layout effects, all synchronously. What the browser then does with those changes is taught in JavaScript lesson 15, Part 1, so I won't repeat it.

I instrumented the real order in Chrome. During render the DOM still shows the old value (100), and it shows 150 from the moment the new ref attaches. So reading the DOM in render reads the past, which is why measurements belong in a layout effect.

The order of useEffect against the frame is not fixed, and this was the surprise in the run. I ran the page in two batches of 12 with a requestAnimationFrame scheduled in the layout effect. rAF runs just before a paint, so an effect that runs before it ran before that paint. After a click, the effect came before rAF in all 24 runs: for a discrete event React flushes effects right away. On the initial mount both orders appeared: 6 and 6 in one batch, 11 and 1 in the other, so it depends on timing. "useEffect runs after paint" is a rule of thumb, not a guarantee. If you must run before paint, that's what useLayoutEffect is for (lesson 7, Part 5).

بالعامية

English

A re-render isn't a DOM update. Below, InvoiceHeader re-renders 3 times from a state change it doesn't use, and a MutationObserver on the whole tree records 0 mutations. When the customer's name really changes, it records exactly one: a characterData change on the text node. React didn't replace the <h1>, it edited the one piece of text. So "too many re-renders" costs JavaScript time and is not automatically a slow page. Measure before you optimize.

import { createRoot } from "react-dom/client";

}

English

<StrictMode> runs extra checks in development and does nothing in a production build. It calls component bodies twice, along with useState initializers and useMemo callbacks, because a pure function called twice gives the same result, so any difference exposes impure code. After the first mount it also runs each effect's mount → cleanup → mount, and does the same with refs (attach → detach → attach), which simulates a component leaving and coming back.

The run below counts this on a dev build and a production build (esbuild, with process.env.NODE_ENV set to each). The impure render is visible on screen: 2 rows in dev where production has 1, then 4 versus 2 after one state change. That's the whole point of the double render. And my lint run in Part 7 reported nothing on this file, so StrictMode caught what the linter missed.

The WebSocket with no cleanupالـ WebSocket من غير cleanup

English

Here's why the double effect exists. I ran a live orders feed against a real ws server and counted open connections on the server. With no cleanup, dev shows 2 live connections right after mount. "That's only dev", except that production has the same bug at a slower pace: leaving the page and coming back twice leaves 3 live connections in the production build, each with its handler still calling setState. With return () => ws.close() it's 1 in every case. StrictMode didn't create the leak; it showed it to you on the first page load.

import { StrictMode, useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

const wsUrl = `ws://${location.host}/ws`;

// ❌ بيفتح connection ومش بيقفله
function LiveOrdersLeaky() {
  const [last, setLast] = useState("-");
  useEffect(() => {
    const ws = new WebSocket(wsUrl);
    ws.onmessage = (e) => setLast(String(e.data));
  }, []);
  return <p>Last order: {last}</p>;
}

// ✅ الـ cleanup بيعكس اللي الـ effect عمله بالظبط
function LiveOrdersFixed() {
  const [last, setLast] = useState("-");
  useEffect(() => {
    const ws = new WebSocket(wsUrl);
    ws.onmessage = (e) => setLast(String(e.data));
    return () => ws.close();
  }, []);
  return <p>Last order: {last}</p>;
}

function App() {
  const [open, setOpen] = useState(true);
  const fixed = new URLSearchParams(location.search).get("v") === "fixed";
  const LiveOrders = fixed ? LiveOrdersFixed : LiveOrdersLeaky;
  return (
    <>
      <button id="toggle" onClick={() => setOpen(!open)}>Toggle page</button>
      {open && <LiveOrders />}
    </>
  );
}

"My fetch fires twice""الـ fetch بتاعي بيتبعت مرتين"

English

Two requests in the Network tab in dev isn't a production bug: the production build sent one. It does point at missing cleanup. With an AbortController in the cleanup, the first request gets aborted in the browser, though the server had already received both, and that's the reason a POST that creates something doesn't belong in a mount effect at all. Put it in the event handler that caused it. The full treatment of fetching is in lesson 9.

New in React 19.3: effects also double-invoke during hydration, matching client roots. I ran the same page on 19.2.9 and 19.3.1, below. So an SSR page with a missing cleanup that looked fine in dev on 19.2 can start double-running after the upgrade. That's the same old bug surfacing, not a regression.

Never turn StrictMode off to hide a double fetch or a double connection. Removing it from main.tsx, or setting reactStrictMode: false in a Next config, removes the alarm and leaves the fire.

import { StrictMode, useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

function Orders() {
  const [count, setCount] = useState<number | null>(null);

  useEffect(() => {
    // الـ cleanup بيلغي الـ request القديم، فأول واحد في dev بيتلغي لوحده
    const controller = new AbortController();
    fetch("/api/orders", { signal: controller.signal })
      .then((res) => res.json())
      .then((orders: unknown[]) => setCount(orders.length))
      .catch((err) => {
        if (err.name !== "AbortError") throw err;
      });
    return () => controller.abort();
  }, []);

  return <p id="count">{count ?? "loading"}</p>;
}

Why you don't silence exhaustive-depsليه متسكّتش exhaustive-deps

English

The most common line in an old React codebase is // eslint-disable-next-line react-hooks/exhaustive-deps. Here's what it hides. The effect closes over the tenantId from its first render, and with empty deps it never re-subscribes. After switching tenants, the screen says t_globex and the poll keeps asking for t_acme. In a multi-tenant product that's one customer's data on another customer's dashboard. The fix is one word in the array: the interval restarts with the new value. If the real objection is "the effect re-runs too often", the answer is useEffectEvent or a restructure, not silence (lesson 7, Part 4).

import { useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

function OrdersPoller({ tenantId }: { tenantId: string }) {
  useEffect(() => {
    const id = setInterval(() => console.log(`GET /orders?tenant=${tenantId}`), 100);
    return () => clearInterval(id);
    // ❌ حد سكّت الـ rule عشان "الـ warning مزعج"
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, []);

  return <h1 id="tenant">Dashboard for {tenantId}</h1>;
}

function App() {
  const [tenantId, setTenantId] = useState("t_acme");
  return (
    <>
      <OrdersPoller tenantId={tenantId} />
      <button id="switch" onClick={() => setTenantId("t_globex")}>Switch tenant</button>
    </>
  );
}

createRoot(document.getElementById("root")!).render(<App />);

أكتر سطر متكرر في كود React القديم هو // eslint-disable-next-line react-hooks/exhaustive-deps. وده اللي بيخبّيه. الـ effect ماسك tenantId بتاع أول render في closure، ومع deps فاضية عمره ما بيعمل subscribe تاني. بعد تغيير الـ tenant، الشاشة بتقول t_globex والـ polling لسه بيطلب t_acme. في منتج multi-tenant ده معناه بيانات عميل على dashboard عميل تاني. الحل كلمة واحدة في الـ array: الـ interval بيبدأ من جديد بالقيمة الجديدة. ولو اعتراضك الحقيقي إن "الـ effect بيتعاد كتير"، فالإجابة useEffectEvent أو إعادة ترتيب الكود، مش إنك تسكّت الـ rule (درس 7، الجزء 4).

فين هستخدمه في شغلي؟ في code review اعتبر أي eslint-disable على exhaustive-deps سؤال لازم له إجابة: "ليه القيمة دي مش محتاجة تبقى في الـ deps؟". واعمل search بيها في المشروع القديم: كل نتيجة ممكن تبقى stale closure حقيقي مستني يبان عند عميل.

ESLint plus the plugin gives the official rules, richer messages with code frames and the Compiler-specific rules, at the price of more dependencies and a TS 6 alias until typescript-eslint supports TS 7.

Solution · الحل 
import { useState, type SubmitEvent } from "react";
import { createRoot } from "react-dom/client";

const format = (raw: string) => raw.toUpperCase().replace(/[^A-Z0-9]/g, "").slice(0, 8);

function PromoForm() {
  const [code, setCode] = useState("");

  function handleSubmit(e: SubmitEvent<HTMLFormElement>) {
    e.preventDefault();
    const data = Object.fromEntries(new FormData(e.currentTarget, e.submitter));
    console.log("submit", data);
  }

  // زرار Clear لازم ⁦type="button"⁩، وإلا هيبقى submit ويبعت الفورم
  return (
    <form onSubmit={handleSubmit}>
      <input id="code" name="code" value={code} onChange={(e) => setCode(format(e.target.value))} />
      <button id="apply" name="intent" value="apply" disabled={code.length < 4}>Apply</button>
      <button id="check" name="intent" value="check" disabled={code.length < 4}>Check only</button>
      <button id="clear" type="button" onClick={() => setCode("")}>Clear</button>
    </form>
  );
}

createRoot(document.getElementById("root")!).render(<PromoForm />);

3. A hook that survives StrictMode 🔴 hard Write useOrderFeed(url) around a WebSocket, returning the last message. Use it inside <StrictMode> and switch tenants at runtime. On the server, the live connection count must be exactly 1 after mount and after switching. Count it with a small ws server.
اكتب useOrderFeed(url) حوالين WebSocket، ويرجّع آخر رسالة. استخدمه جوه <StrictMode> وغيّر الـ tenant وهو شغال. على السيرفر عدد الـ connections الشغالة لازم يبقى 1 بالظبط بعد الـ mount وبعد التغيير. عدّهم بـ ws server صغير.
Solution · الحل 
import { StrictMode, useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

// الـ hook: connection واحد لكل url، والـ cleanup بيقفله
function useOrderFeed(url: string) {
  const [last, setLast] = useState<string | null>(null);

  useEffect(() => {
    const ws = new WebSocket(url);
    ws.onmessage = (e) => setLast(String(e.data));
    return () => ws.close();
  }, [url]);

  return last;
}

function Feed({ tenant }: { tenant: string }) {
  const last = useOrderFeed(`ws://${location.host}/ws?tenant=${tenant}`);
  return <p id="last">{last ?? "waiting"}</p>;
}

function App() {
  const [tenant, setTenant] = useState("t_acme");
  return (
    <>
      <Feed tenant={tenant} />
      <button id="switch" onClick={() => setTenant("t_globex")}>Switch tenant</button>
    </>
  );
}

createRoot(document.getElementById("root")!).render(
  <StrictMode>
    <App />
  </StrictMode>,
);

after switching tenant: live = 1, screen = order from t_globex
opened: /ws?tenant=t_acme /ws?tenant=t_acme /ws?tenant=t_globex

Cheat sheet · الخلاصة

  • React's listeners sit on the root. Native listeners on inner elements run first; e.nativeEvent.currentTarget is the root.
  • stopPropagation ends React's walk and the native bubble past the root. preventDefault cancels the browser action and doesn't stop bubbling.
  • onClick={pay}, never onClick={pay()}. Reading e.currentTarget after await gives null.
  • Controlled: state owns the value, always a string. Uncontrolled: DOM owns it, with defaultValue plus a ref or FormData. File inputs are always uncontrolled.
  • Use <form onSubmit> with preventDefault first. Enter activates the first submit button. Buttons that shouldn't submit need type="button".
  • Disabling a button is UX. The real double-charge protection is a per-attempt idempotency key enforced on the server.
  • Render triggers: initial, own state, parent render, context. A changed prop alone isn't one. Same value bails out through Object.is, possibly after one extra render of that component.
  • Render is pure and writes nothing. Commit detaches old refs, writes the DOM, attaches new refs, then runs layout effects. A re-render with the same output gives 0 DOM mutations.
  • useEffect vs paint isn't fixed: before rAF in all 24 runs after a click, either order on mount. Use useLayoutEffect when you must run before paint.
  • StrictMode is dev only: double render, effect mount → cleanup → mount, and since 19.3 during hydration too. It exposes impure renders and missing cleanups, so never turn it off.
  • Vite template: oxlint, not ESLint. exhaustive-deps runs as a warning with exit code 0, so promote it to error. ESLint needs a TS 6 alias next to TS 7.
  • Silencing exhaustive-deps hides stale closures: the screen says one tenant while the poll asks for another.
بالعامية
  • الـ listeners بتاعة React على الـ root. الـ native listeners على العناصر اللي جوه بتشتغل الأول، وe.nativeEvent.currentTarget هو الـ root.
  • stopPropagation بينهي مشي React والـ native bubble بعد الـ root. وpreventDefault بيلغي فعل الـ browser ومش بيوقف الـ bubbling.
  • onClick={pay}، عمرك ما تكتب onClick={pay()}. وقراءة e.currentTarget بعد await بتدّي null.
  • الـ controlled: الـ state صاحبة القيمة ودايمًا string. الـ uncontrolled: الـ DOM صاحبها، بـ defaultValue مع ref أو FormData. والـ file inputs دايمًا uncontrolled.
  • استخدم <form onSubmit> وpreventDefault في الأول. Enter بيشغّل أول زرار submit. والزراير اللي مش المفروض تبعت لازم type="button".
  • قفل الزرار ده UX. الحماية الحقيقية من الخصم المزدوج هي idempotency key لكل محاولة ومتطبّق على السيرفر.
  • أسباب الـ render: الـ initial، والـ state بتاعته، وrender الأب، والـ context. والـ prop المتغير لوحده مش سبب. ونفس القيمة بتقف بـ Object.is، وممكن بعد render زيادة للـ component ده.
  • الـ render بيبقى pure ومش بيكتب حاجة. الـ commit بيفك الـ refs القديمة، ويكتب في الـ DOM، ويركّب الجديدة، وبعدين الـ layout effects. وre-render بنفس الناتج بيدّي 0 DOM mutations.
  • ترتيب useEffect مع الـ paint مش ثابت: قبل الـ rAF في الـ 24 مرة كلهم بعد ضغطة، وأي ترتيب عند الـ mount. استخدم useLayoutEffect لو لازم تشتغل قبل الـ paint.
  • StrictMode في dev بس: double render، والـ effect بيعمل mount ← cleanup ← mount، ومن 19.3 أثناء الـ hydration كمان. بيكشف الـ render الـ impure والـ cleanup الناقص، فمتقفلوش أبدًا.
  • template بتاع Vite فيه oxlint مش ESLint. exhaustive-deps شغالة كـ warning وexit code 0، فارفعها لـ error. وESLint محتاج alias لـ TS 6 جنب TS 7.
  • تسكيت exhaustive-deps بيخبّي stale closures: الشاشة بتقول tenant والـ polling بيطلب tenant تاني.
