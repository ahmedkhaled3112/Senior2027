Why this matters · ليه ده مهم

English

Accessibility decides whether people can use what you built: blind users on a screen reader, people who can't use a mouse, and also the support agent who processes 200 refunds a day from the keyboard. In many markets it's a legal requirement too. It keeps coming up in senior interviews because it tests whether you understand what the browser does for you and what you throw away when you replace it with a div.

This lesson is run, not recited: Tab presses, focus traces and the accessibility tree come from Playwright driving real Chrome 156. One thing can't run here: an actual screen reader. Part 5 is labelled "not run" and gives you a script to do it yourself once, by hand.

بالعامية

الـ accessibility بتحدد الناس تقدر تستخدم اللي بنيته ولا لأ: المكفوفين اللي بيستخدموا screen reader، واللي مش بيقدروا يستخدموا mouse، وكمان موظف الـ support اللي بيعمل 200 refund في اليوم من الـ keyboard. وفي أسواق كتير هي شرط قانوني كمان. وبتتسأل كتير في interviews السنيور، لأنها بتكشف إنت فاهم الـ browser بيعمل لك إيه، وبترمي إيه لما تبدله بـ div.

الدرس ده متشغّل مش محفوظ: ضغطات الـ Tab وتتبّع الـ focus وشجرة الـ accessibility كلها من Playwright بيسوق Chrome 156 الحقيقي. فيه حاجة واحدة مينفعش تتشغّل هنا: screen reader حقيقي. الجزء 5 مكتوب عليه "not run"، وفيه سكريبت تعمله بإيدك مرة واحدة.

Part 1 — Semantic HTML first 🟡 Intermediateالجزء 1 — الـ semantic HTML الأول

English

The browser turns the DOM into an accessibility tree: roles, names and states, which assistive technology reads. A native element arrives with all of it, plus focus and keyboard. A div arrives with none. So the cheapest accessibility work you'll ever do is choosing the right tag.

Below is the same order table twice. With the div version, Tab never reaches the Refund action, Enter does nothing, and the whole table is one line of text in the tree. With table and button, Tab lands on each action, Enter and Space both work, and each cell has a role and each button a name. All of that comes from changing tags, with no ARIA and no key handlers. The probes use the harness from lesson 15.

                    state: focusable, expanded?, invalid?

<div onClick>       role: none        name: none        focusable: no
<button>            role: button      name: from text   focusable: yes, Enter + Space

Landmarks, headings, labels, lists الـ landmarks والـ headings والـ labels والـ lists

English

Screen reader users skim by structure, the way you skim by looking. Landmarks are jump targets: header becomes banner, nav becomes navigation, main stays main, footer becomes contentinfo. A section or form becomes a landmark only once it has a name, as the snapshot shows with aria-labelledby. Two navs need different aria-labels.

Headings are the table of contents: one h1, no skipped levels, chosen by structure rather than font size. Every input needs a label tied with htmlFor; a placeholder disappears as soon as you type. Lists use ul or ol, so "2 items" can be announced. In tables, th scope ties each cell to its headers, which is what makes "Total, 250 EGP" possible while moving through cells.

import { createRoot } from "react-dom/client";

Link or button? link ولا button؟

English

A link goes somewhere and a button does something. If it changes the URL, use a href: middle click and "open in new tab" work. If it acts on the page, use button. They're activated differently, too: in the run below, Space does nothing on a link and Enter follows it, while a button responds to both. An a with no href is neither: the tree shows plain text and Tab skips it.

import { useState } from "react";
import { createRoot } from "react-dom/client";

function Actions() {
  const [log, setLog] = useState<string[]>([]);
  const hit = (name: string) => setLog((l) => [...l, name]);
  // ✅ الـ link بيودّي لمكان: الـ URL حقيقي، فـ middle click و open in new tab شغالين
  // ❌ الـ a من غير href مش focusable ومش link أصلًا
  // ✅ الـ button بيعمل حاجة في نفس الصفحة
  return (
    <>
      <a href="#invoice-7" onClick={() => hit("real link")}>Open invoice</a>
      <a onClick={() => hit("a without href")}>Fake link</a>
      <button type="button" onClick={() => hit("button")}>Download PDF</button>
      <output data-log>{log.join(", ")}</output>
    </>
  );
}

Part 2 — ARIA basics 🟡 Intermediateالجزء 2 — أساسيات الـ ARIA

English

ARIA changes what the accessibility tree says and nothing else: no focus, no keyboard, no behaviour. That's why the first rule of ARIA use is not to use it when native HTML already does the job, and why the WAI authoring guide has a section titled "No ARIA is better than Bad ARIA". The third rule says all interactive ARIA controls must be usable with the keyboard. The LyingButton below breaks it: getByRole("button") finds it, but Tab never stops on it. It announces a promise the page doesn't keep.

The attributes you'll actually use:

  • aria-label: a name when there's no visible text, as on an icon button. Hide the icon with aria-hidden.
  • aria-describedby: extra text read after the name, such as a hint or an error. Build the ids with useId (lesson 06). Chrome's tree below shows both texts as the input's description.
  • aria-expanded: open or closed on a disclosure. Keep it on the button, and let the button supply the keyboard.
  • aria-invalid: this field failed validation.
import { useId, useState } from "react";
import { createRoot } from "react-dom/client";

// (1) الاسم والوصف: الـ label هو الاسم، والـ hint والـ error بيتقروا كـ description
function Field({ label, hint, error }: { label: string; hint: string; error?: string }) {
  const id = useId();
  const hintId = `${id}-hint`;
  const errorId = `${id}-error`;
  return (
    <div>
      <label htmlFor={id}>{label}</label>
      <input
        id={id}
        aria-invalid={error ? true : undefined}
        aria-describedby={error ? `${hintId} ${errorId}` : hintId}
      />
      <p id={hintId}>{hint}</p>
      {error && <p id={errorId}>{error}</p>}
    </div>
  );
}

// (2) الـ disclosure: الـ aria-expanded بيقول الحالة، والـ button بيدّي الـ keyboard مجانًا
function OrderDetails() {
  const [open, setOpen] = useState(false);
  const panelId = useId();
  return (
    <>
      <button type="button" aria-expanded={open} aria-controls={panelId} onClick={() => setOpen(!open)}>
        Order details
      </button>
      <div id={panelId} hidden={!open}>Keyboard x1, Mouse x2</div>
    </>
  );
}

// شجرة الـ accessibility الحقيقية من Chrome، زي اللي الـ screen reader بيقراها
const axNodes = async (page) => {
  const cdp = await page.context().newCDPSession(page);
  const { nodes } = await cdp.send("Accessibility.getFullAXTree");
  return nodes.filter((n) => !n.ignored).map((n) => {
    const props = Object.fromEntries((n.properties ?? []).map((p) => [p.name, p.value?.value]));
    return { role: n.role?.value, name: n.name?.value ?? "", description: n.description?.value ?? "", ...props };
  });
};

Live regions: announcing without moving focus الـ live regions: إعلان من غير نقل الـ focus

English

A toast appears where the user isn't looking. A live region tells assistive tech to announce changes inside it. role="status" means polite: wait for the current speech to finish. role="alert" means assertive: interrupt. Chrome's tree below confirms those values. Use polite for "Payment succeeded" and assertive only for what needs action now, like a declined card.

The trap in React is conditional rendering. if (!message) return null mounts the region together with its text, so the region and the change arrive at once, and that change may not be announced. MDN's guidance is to establish the region first, empty, and that including it in the initial markup is the most reliable way to get it registered. It also notes that behaviour varies across browser and assistive tech combinations, and that role="alert" usually gets announced even when injected. So keep the region mounted and change only its text.

What I could verify here is the DOM difference, shown below: the bad version adds a new region node holding the text; the good one adds text to a node that was already there. I didn't hear any of this: no screen reader ran here. Part 5 is where you confirm it with your own ears.

Part 3 — Focus management 🟡 Intermediateالجزء 3 — إدارة الـ focus

English

A modal has three focus duties. On open, move focus inside. While open, the background must be unreachable by Tab, by mouse and by screen reader, not merely covered by an overlay. On close, return focus to whatever opened it. inert handles the middle duty in one attribute, and React 19 accepts it as a boolean.

Below is a refund modal built three ways and driven by the same probe. The traces aren't identical, and the differences matter:

  • The hand-written trap and Radix loop: Tab from Cancel returns to Amount.
  • Native showModal() doesn't loop inside the page: Tab from Cancel gives BODY, then Amount. In a normal window that step usually means focus went to the browser's own UI, though I could only observe headless Chrome. This isn't a bug, and the background stays inert throughout.
  • Only Radix blocked page scrolling (0 px moved, against 600 px for the other two), and only Radix closed on an outside click. Native gets that with closedby="any" (ran in Chrome 156; check support for your browsers).
  • Native Escape closes the dialog without telling React, so keep state in sync through onClose.
  • The hand-written trap is here to show the mechanism, not to ship: its selector ignores hidden elements, iframes, shadow DOM and radio groups. And its close function must stay stable, or the effect re-runs and its cleanup sends focus out of the modal.

const FOCUSABLE = 'a[href], button:not([disabled]), input:not([disabled]), select:not([disabled]), textarea:not([disabled]), [tabindex]:not([tabindex="-1"])';

function useFocusTrap(ref: RefObject<HTMLElement | null>, onEscape: () => void) {
  useEffect(() => {
    const dialog = ref.current!;
    // (1) سجّل مين كان عليه الـ focus، عشان ترجعله وقت القفل
    const opener = document.activeElement as HTMLElement | null;
    const items = () => [...dialog.querySelectorAll<HTMLElement>(FOCUSABLE)];
    // (2) دخّل الـ focus جوه الـ modal
    items()[0]?.focus();

    const onKeyDown = (e: KeyboardEvent) => {
      if (e.key === "Escape") onEscape();
      if (e.key !== "Tab") return;
      const list = items();
      const first = list[0];
      const last = list.at(-1);
      // (3) الـ loop: من الآخر للأول، ومن الأول للآخر مع Shift
      if (e.shiftKey && document.activeElement === first) {
        e.preventDefault();
        last?.focus();
      } else if (!e.shiftKey && document.activeElement === last) {
        e.preventDefault();
        first?.focus();
      }
    };
    document.addEventListener("keydown", onKeyDown);
    return () => {
      document.removeEventListener("keydown", onKeyDown);
      // (4) رجّع الـ focus للزرار اللي فتح الـ modal
      opener?.focus();
    };
  }, [ref, onEscape]);
}

function Modal({ title, onClose, children }: { title: string; onClose: () => void; children: ReactNode }) {
  const ref = useRef<HTMLDivElement>(null);
  useFocusTrap(ref, onClose);
  return createPortal(
    <div className="overlay">
      <div ref={ref} role="dialog" aria-modal="true" aria-label={title} className="modal">
        {children}
      </div>
    </div>,
    document.body,
  );
}

Skip links, route changes, deleted rows, focus rings الـ skip links وتغيير الـ route والصفوف المحذوفة وحلقات الـ focus

English

Skip link: the first focusable element, hidden until focused, pointing at #main. Without it a keyboard user tabs through the whole nav on every page. tabIndex={-1} on main lets it receive focus without joining the Tab order. The trace confirms the next Tab lands on the first control inside.

Route change: an SPA has no page load, so nothing announces the new page or resets focus. Move focus to the new h1, skipping the first load. Next.js documents a built-in route announcer for client-side transitions, which reads document.title, so give every page a unique title. In a plain SPA this is your job.

Deleting a row: the focused button disappears and activeElement falls to BODY. An honest note from this run: Chrome kept its place, and the next Tab went to the following row. That's better than I expected, but focus is still nowhere: nothing is announced, and Enter does nothing. Decide the target yourself: the next row, else the previous, else the heading.

:focus-visible: shows the ring when the browser judges it useful. In the run, a mouse click on a button doesn't match it, Tab does, and a click on a text input does. So replace outline: none with styling on :focus-visible, and designers get no ring on click while keyboard users keep theirs.

// (1) الـ skip link: أول حاجة في الصفحة، والـ CSS بيخفيها لحد ما تاخد focus
function SkipLink() {
  return <a className="skip" href="#main">Skip to content</a>;
}

// (2) تغيير الـ route: الـ SPA مبتعملش page load، فلازم تنقل الـ focus بنفسك
function RoutePage({ path }: { path: string }) {
  const ref = useRef<HTMLHeadingElement>(null);
  const first = useRef(true);
  useEffect(() => {
    // أول تحميل للصفحة سيبه: الـ browser هو اللي بيبدأ من فوق
    if (first.current) {
      first.current = false;
      return;
    }
    ref.current?.focus();
  }, [path]);
  // الـ ⁦tabIndex={-1}⁩ بيخلّي الـ h1 يقبل focus من الكود من غير ما يدخل ترتيب الـ Tab
  return <h1 ref={ref} tabIndex={-1}>{path === "/orders" ? "Orders" : "Invoices"}</h1>;
}

// (3) حذف صف: العنصر اللي عليه الـ focus بيختفي، فلازم تحدد الـ focus يروح فين
function InvoiceRows({ fix }: { fix: boolean }) {
  const [rows, setRows] = useState(["inv_1", "inv_2", "inv_3"]);
  const buttons = useRef(new Map<string, HTMLButtonElement>());
  const nextFocus = useRef<string | null>(null);
  const heading = useRef<HTMLHeadingElement>(null);

  useEffect(() => {
    if (!fix || nextFocus.current === null) return;
    const target = buttons.current.get(nextFocus.current) ?? heading.current;
    target?.focus();
    nextFocus.current = null;
  }, [rows, fix]);

  const remove = (id: string) => {
    const at = rows.indexOf(id);
    const next = rows.filter((r) => r !== id);
    // الأولوية: الصف اللي جاي مكانه، وبعدين اللي قبله، ولو الجدول فضي نروح للعنوان
    nextFocus.current = next[at] ?? next[at - 1] ?? "__heading";
    setRows(next);
  };

  return (
    <section data-fix={fix}>
      <h2 ref={heading} tabIndex={-1}>{fix ? "Invoices (fixed)" : "Invoices (naive)"}</h2>
      <ul>
        {rows.map((id) => (
          <li key={id}>
            {id}
            <button
              ref={(el) => {
                if (el) buttons.current.set(id, el);
                else buttons.current.delete(id);
              }}
              aria-label={`Delete ${id}${fix ? " fixed" : ""}`}
              onClick={() => remove(id)}
            >
              Delete
            </button>
          </li>
        ))}
      </ul>
    </section>
  );
}

Tab order follows the DOM. Never use a positive tabIndex: it jumps ahead of everything else on the page, as the CVV field does below, landing before the Help link and before the name on the card. Only two values are normal: 0 (in the order, for custom widgets) and -1 (focusable from code only). If the visual order differs from the tab order, fix the DOM or the CSS.

Tab moves between widgets; arrow keys move inside one. A 10-tab strip shouldn't take 10 Tab presses to cross. Roving tabindex does this: only the active tab has tabIndex={0}, the others -1, and arrow keys move both focus and the zero. Shift+Tab then returns to the active tab rather than the first. Exact behaviour per widget is in the ARIA APG patterns; the Tabs pattern recommends activating on focus when panels show without noticeable delay. If a panel triggers a slow fetch, use manual activation (Enter or Space) instead.

import { useId, useRef, useState, type KeyboardEvent } from "react";
import { createRoot } from "react-dom/client";

interface TabItem {
  id: string;
  label: string;
}

export function RovingTabs({ tabs, label }: { tabs: TabItem[]; label: string }) {
  const [active, setActive] = useState(tabs[0]!.id);
  const buttons = useRef(new Map<string, HTMLButtonElement>());
  const baseId = useId();

  const onKeyDown = (e: KeyboardEvent<HTMLButtonElement>, index: number) => {
    // في الـ RTL الأسهم بتتعكس: السهم الشمال معناه "اللي بعده"
    const rtl = getComputedStyle(e.currentTarget).direction === "rtl";
    const nextKey = rtl ? "ArrowLeft" : "ArrowRight";
    const prevKey = rtl ? "ArrowRight" : "ArrowLeft";

    let target: number | null = null;
    if (e.key === nextKey) target = (index + 1) % tabs.length;
    else if (e.key === prevKey) target = (index - 1 + tabs.length) % tabs.length;
    else if (e.key === "Home") target = 0;
    else if (e.key === "End") target = tabs.length - 1;
    if (target === null) return;

    // الـ preventDefault عشان Home و End ميعملوش scroll للصفحة
    e.preventDefault();
    const id = tabs[target]!.id;
    setActive(id);
    buttons.current.get(id)?.focus();
  };

  return (
    <div>
      <div role="tablist" aria-label={label}>
        {tabs.map((tab, index) => (
          <button
            key={tab.id}
            ref={(el) => {
              if (el) buttons.current.set(tab.id, el);
              else buttons.current.delete(tab.id);
            }}
            type="button"
            role="tab"
            id={`${baseId}-tab-${tab.id}`}
            aria-selected={tab.id === active}
            aria-controls={`${baseId}-panel-${tab.id}`}
            // ده قلب الـ roving tabindex: tab واحد بس جوه ترتيب الـ Tab
            tabIndex={tab.id === active ? 0 : -1}
            onClick={() => setActive(tab.id)}
            onKeyDown={(e) => onKeyDown(e, index)}
          >
            {tab.label}
          </button>
        ))}
      </div>
      {tabs.map((tab) => (
        <div
          key={tab.id}
          role="tabpanel"
          id={`${baseId}-panel-${tab.id}`}
          aria-labelledby={`${baseId}-tab-${tab.id}`}
          hidden={tab.id !== active}
          tabIndex={0}
        >
          {tab.label} content
        </div>
      ))}
    </div>
  );
}

A native button fires its click on Enter keydown and on Space keyup, as the counter below shows. // لو اتحكم عليك بـ div: ده أقل حاجة تخلّيه يتصرف زي button، وده كله ببلاش في button
function FakeButton({ onPress, children }: { onPress: () => void; children: string }) {
  const onKeyDown = (e: KeyboardEvent<HTMLDivElement>) => {
    if (e.key === "Enter") onPress();
    // الـ Space لازم preventDefault، وإلا الصفحة هتعمل scroll
    if (e.key === " ") e.preventDefault();
  };
  const onKeyUp = (e: KeyboardEvent<HTMLDivElement>) => {
    // زي الـ button الحقيقي: الـ Space بيشتغل وقت ما المفتاح يطلع
    if (e.key === " ") onPress();
  };
  return (
    <div role="button" tabIndex={0} onClick={onPress} onKeyDown={onKeyDown} onKeyUp={onKeyUp}>
      {children}
    </div>
  );
}

WCAG 2.2 sets the numbers. Normal text needs at least 4.5:1 (SC 1.4.3). Large text, 18 point or 14 point bold (about 24 px or 18.66 px), needs 3:1. UI components and meaningful graphics, like an input border, need 3:1 against adjacent colors (SC 1.4.11).

// الـ channel: تحويل من sRGB للـ linear بنفس معادلة WCAG 2.2
const channel = (value8bit: number): number => {
  const srgb = value8bit / 255;
  return srgb <= 0.04045 ? srgb / 12.92 : ((srgb + 0.055) / 1.055) ** 2.4;
};

export function luminance(hex: string): number {
  const n = Number.parseInt(hex.slice(1), 16);
  const [r, g, b] = [(n >> 16) & 255, (n >> 8) & 255, n & 255] as const;
  return 0.2126 * channel(r) + 0.7152 * channel(g) + 0.0722 * channel(b);
}

export function contrast(a: string, b: string): number {
  const [lighter, darker] = [luminance(a), luminance(b)].sort((x, y) => y - x) as [number, number];
  return (lighter + 0.05) / (darker + 0.05);
}

prefers-reduced-motion in JavaScript الـ prefers-reduced-motion في الـ JavaScript

English

Some people get dizzy or nauseous from motion. The CSS side is in lesson 05; JavaScript animations need the same signal: smooth scrolling, count-ups, confetti. Read it through matchMedia and subscribe to changes. useSyncExternalStore is the right tool, because this is an external value that can change while the page is open, and it has a server snapshot for SSR. Removing motion doesn't mean removing feedback: the page still jumps to the invoice, just without the animation.

In the run, emulateMedia switches the preference with no reload and the hook updates by itself. Two frames after the click, the smooth version has barely moved and the reduced version is already at the target.

import { useSyncExternalStore } from "react";
import { createRoot } from "react-dom/client";

const query = "(prefers-reduced-motion: reduce)";

function subscribe(notify: () => void) {
  const mql = window.matchMedia(query);
  mql.addEventListener("change", notify);
  return () => mql.removeEventListener("change", notify);
}

// التالت هو الـ server snapshot: في الـ SSR مفيش matchMedia، فبنبدأ بـ false
export function usePrefersReducedMotion(): boolean {
  return useSyncExternalStore(subscribe, () => window.matchMedia(query).matches, () => false);
}

      Jump to invoice

}

Linting: jsx-a11y and oxlint الـ lint: jsx-a11y و oxlint

English

Lint catches mistakes visible in source, before anything renders. eslint-plugin-jsx-a11y 6.10.2 declares a peer range up to ESLint 9, so a plain install beside ESLint 10 fails with ERESOLVE. With --legacy-peer-deps it installed and ran fine here, but that flag accepts a range the plugin doesn't claim to support, so watch for a release that adds ESLint 10. How much do tools catch? الأدوات بتمسك قد إيه؟

English

Only part of the problems, and the numbers depend on how you count. Two sourced figures, neither a universal truth:

  • Deque's coverage report: automated tests found 57.38% of issues by volume, over 13,000+ pages and nearly 300,000 issues from first-time audits. Deque makes axe, so it has an interest in this result, and frequent issue types count many times.
  • UK government (GDS), 2017: a page with 143 deliberate barriers against 10 tools. Together they found 71%, the best single tool 41% (37% counting only errors and warnings), and 29% were missed by every tool. It's old, and tools have improved since.

The takeaway is the same either way: tools are a floor. Nothing in this lesson's axe report would have caught the color-only dots, a meaningless name, or a live region that stays silent.

import { createContext, use, useCallback, useRef, useState, type ReactNode } from "react";
import { createRoot } from "react-dom/client";

const AnnouncerContext = createContext<(message: string) => void>(() => {});

export const useAnnounce = () => use(AnnouncerContext);

// الـ provider في الـ layout: region واحد متركب طول عمر الصفحة
export function AnnouncerProvider({ children }: { children: ReactNode }) {
  const [text, setText] = useState("");
  const timer = useRef<number | undefined>(undefined);

  const announce = useCallback((message: string) => {
    // فضّي الأول، وبعدين حط النص في task تاني: كده نفس الرسالة تتحسب تغيير جديد
    setText("");
    window.clearTimeout(timer.current);
    timer.current = window.setTimeout(() => setText(message), 100);
  }, []);

  return (
    <AnnouncerContext value={announce}>
      {children}
      <div role="status" data-announcer>{text}</div>
    </AnnouncerContext>
  );
}

function SaveButton() {
  const announce = useAnnounce();
  return <button onClick={() => announce("Invoice saved")}>Save</button>;
}

import { useEffect, useRef, useState, type RefObject } from "react";
import { createRoot } from "react-dom/client";

// الحل: لو الـ opener اتشال من الـ DOM، روح لعنصر بديل بدل ما الـ focus يقع على body
function useReturnFocus(fallback: RefObject<HTMLElement | null>, useFallback: boolean) {
  useEffect(() => {
    const opener = document.activeElement as HTMLElement | null;
    return () => {
      if (opener?.isConnected || !useFallback) opener?.focus();
      else fallback.current?.focus();
    };
  }, [fallback, useFallback]);
}

function ConfirmDelete(props: { id: string; onConfirm: () => void; fallback: RefObject<HTMLElement | null>; fix: boolean }) {
  const confirm = useRef<HTMLButtonElement>(null);
  useReturnFocus(props.fallback, props.fix);
  useEffect(() => confirm.current?.focus(), []);
  return (
    <div role="dialog" aria-modal="true" aria-label={`Delete ${props.id}`}>
      <button ref={confirm} onClick={props.onConfirm}>Confirm delete {props.fix ? "fixed" : "naive"}</button>
    </div>
  );
}

function Invoices({ fix }: { fix: boolean }) {
  const [rows, setRows] = useState(["inv_1"]);
  const [deleting, setDeleting] = useState<string | null>(null);
  const heading = useRef<HTMLHeadingElement>(null);
  return (
    <section>
      <h2 ref={heading} tabIndex={-1}>Invoices {fix ? "fixed" : "naive"}</h2>
      {rows.map((id) => (
        <button key={id} onClick={() => setDeleting(id)}>Delete {id} {fix ? "fixed" : "naive"}</button>
      ))}
      {deleting && (
        <ConfirmDelete
          id={deleting}
          fix={fix}
          fallback={heading}
          onConfirm={() => {
            setRows((r) => r.filter((x) => x !== deleting));
            setDeleting(null);
          }}
        />
      )}
    </section>
  );
}

Cheat sheet · الخلاصة

  • Right tag first: button, a href, table, label, landmarks. A div onClick gets no Tab stop, no Enter, no role.
  • Link goes somewhere, button does something. Space doesn't activate a link; a without href isn't focusable.
  • ARIA changes the tree only, never behaviour. No ARIA is better than bad ARIA. Every interactive role needs a keyboard.
  • aria-label names, aria-describedby adds a hint or error, aria-expanded gives state.
  • Live region: always mounted, change the text. status is polite, alert is assertive and interrupts.
  • Modal: focus in, background inert, Escape closes, focus returns. Radix loops and locks scroll; native dialog leaves the page on Tab and costs 0 KB.
  • Skip link first; move focus to h1 on route change; pick a target when deleting a row; style :focus-visible, never bare outline: none.
  • Tab between widgets, arrows inside them with roving tabindex. Only 0 and -1. Arrows flip in RTL. Escape closes the top layer only.
  • Button: Enter on keydown, Space on keyup.
  • Contrast: 4.5:1 for text, 3:1 for large text and UI. #767676 on white passes, #777777 doesn't. Check dark tokens too. Never color alone.
  • Reduced motion in JS: matchMedia with useSyncExternalStore, tested with emulateMedia.
  • Layers: lint, axe in CI, keyboard flows, a human screen reader pass. ariaSnapshot misses description, live and required. Tools are a floor: see the Deque and GDS figures.
بالعامية
  • الـ tag الصح الأول: button وa href وtable وlabel والـ landmarks. والـ div onClick مفيش عليه Tab ولا Enter ولا role.
  • الـ link بيودّي لمكان، والـ button بيعمل حاجة. الـ Space مش بتشغّل link، والـ a من غير href مش focusable.
  • الـ ARIA بتغيّر الشجرة بس، مش السلوك. ومفيش ARIA أحسن من ARIA غلط. وكل role تفاعلي لازم له keyboard.
  • الـ aria-label اسم، والـ aria-describedby hint أو error، والـ aria-expanded حالة.
  • الـ live region: متركب طول الوقت وغيّر النص. الـ status polite، والـ alert assertive وبيقطع الكلام.
  • الـ modal: focus جوه، وخلفية inert، وEscape يقفل، والـ focus يرجع. وRadix بيلف وبيقفل الـ scroll، والـ dialog الـ native بيخرج من الصفحة مع الـ Tab وتكلفته 0 KB.
  • الـ skip link أول حاجة، وانقل الـ focus لـ h1 مع تغيير الـ route، وحدد وجهة لما تحذف صف، واعمل styling لـ :focus-visible ومتستخدمش outline: none لوحدها.
  • الـ Tab بين الـ widgets، والأسهم جوه الـ widget بـ roving tabindex. بس 0 و-1. والأسهم بتتعكس في الـ RTL. والـ Escape بيقفل الطبقة اللي فوق بس.
  • الـ button: الـ Enter مع نزول المفتاح، والـ Space مع طلوعه.
  • الـ contrast: 4.5:1 للنص، و3:1 للنص الكبير والـ UI. #767676 على الأبيض بينجح و#777777 لأ. وافحص الـ dark tokens كمان. ومتعتمدش على اللون لوحده.
  • الـ reduced motion في الـ JS: matchMedia مع useSyncExternalStore، والـ test بـ emulateMedia.
  • الطبقات: lint، وaxe في الـ CI، وkeyboard flows، وجولة screen reader بإيد بني آدم. والـ ariaSnapshot مش بيعرض description ولا live ولا required. والأدوات هي الحد الأدنى: شوف أرقام Deque وGDS.
