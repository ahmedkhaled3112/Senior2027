Why this matters · ليه ده مهم

English

The first wrong move on a slow React page is guessing. A Senior says "this commit takes 18 ms because 2,000 rows re-render after a new onSelect prop", changes one thing, and shows the number again. This lesson gives you three instruments for that: a why-did-it-render hook, the Profiler API inside a production build, and React Performance Tracks in a real Chrome trace. It then covers the one big automatic optimization, the React Compiler, including the two ways it can change your app's behaviour with no error from the compiler or from the linter.

Interviewers ask this as "how would you debug a slow React page?" and "does the compiler make useMemo obsolete?". How measurements were taken: Chrome 156 on Windows, on a machine that other jobs were loading. Counts (renders, calls, rows) are exact and repeat on every run. Timings vary between runs, so read them as approximate (≈) and trust the ratios. The React DevTools UI can't be driven from this setup, so its steps come from the docs and are labelled "not run here".

Part 1 — Re-render causes and diagnosis 🟡 Intermediateالجزء 1 — أسباب الـ re-render وتشخيصها

English

A component renders for one of four reasons: initial mount, its own state changed, its parent rendered, or a context it reads changed (the full list with counters is in lesson 03). "Its props changed" isn't on that list. A parent render re-renders the child whether or not the props changed, and props only matter once the child is wrapped in memo, which compares each one with Object.is (lesson 08). So the useful question is: was this render wasted, and which prop broke the memo?

The DevTools way (from the docs, not run here; do it yourself in exercise 2). Open the Profiler tab, click the gear, open the Profiler settings and tick "Record why each component rendered while profiling". Record, interact, stop, pick a commit and click a component. The side panel then says something like "Props changed: onSelect", "Hook 2 changed" or "The parent component rendered".

An equivalent that runs anywhere. useWhyDidYouRender keeps the previous props in a ref and compares them after each commit, using the same Object.is check memo uses. On a 1,000-row page where only a note input changes, it prints onSelect changed 1,000 times. That one line tells you the fix: make onSelect stable. After useCallback, the rows run zero times per keystroke.

A whole-app view. DevTools learns about commits through __REACT_DEVTOOLS_GLOBAL_HOOK__, and you can install your own version before react-dom loads. React calls onCommitFiberRoot on every commit, and you walk the fibers (lesson 18). Two details matter. The PerformedWork flag means "this function ran in this commit". And you must skip a subtree whose child pointer equals its alternate's: it bailed out, so the flags inside are left over from an older commit. In production the names are minified. This is a private API, so use it for diagnosis only and expect it to change.

import { useEffect, useRef } from "react";

// بيقارن الـ props بتاعة الـ render ده باللي قبله بـ Object.is، نفس المقارنة بتاعة memo
export function useWhyDidYouRender(
  name: string,
  props: Record<string, unknown>,
  report: (line: string) => void = console.log,
): void {
  const previous = useRef<Record<string, unknown> | null>(null);
  // من غير deps: لازم يشتغل بعد كل commit للـ component ده
  useEffect(() => {
    const before = previous.current;
    previous.current = props;
    // أول render مفيش حاجة نقارن بيها
    if (before === null) return;
    const keys = new Set([...Object.keys(before), ...Object.keys(props)]);
    const changed = [...keys].filter((key) => !Object.is(before[key], props[key]));
    report(changed.length > 0
      ? `${name}: ${changed.join(", ")} changed`
      : `${name}: no prop changed (parent or own state)`);
  });
}

// لازم الملف ده يتنفّذ قبل react-dom: الـ renderer بيدوّر على الـ hook وقت ما بيتحمّل
// تحذير: ده private API بتاع الـ DevTools، استخدمه في التشخيص بس مش في الـ production

interface Fiber {
  type: unknown;
  flags: number;
  child: Fiber | null;
  sibling: Fiber | null;
  alternate: Fiber | null;
}

// الـ flag ده معناه إن الـ component اتنفّذ فعلًا في الـ commit ده
const PerformedWork = 1;
export const renders = new Map<string, number>();
export let commits = 0;

const nameOf = (type: unknown): string | null => {
  if (typeof type === "function") return type.name || "Anonymous";
  // الـ memo بيلف الـ component جوه object فيه type
  const inner = (type as { type?: unknown } | null)?.type;
  return typeof inner === "function" ? inner.name || "Anonymous" : null;
};

function walk(fiber: Fiber | null): void {
  for (let node = fiber; node !== null; node = node.sibling) {
    const name = nameOf(node.type);
    if (name !== null && (node.flags & PerformedWork) !== 0) {
      renders.set(name, (renders.get(name) ?? 0) + 1);
    }
    // لو الـ child زي اللي في الـ alternate يبقى الـ subtree كلها عملت bail out
    // والـ flags اللي جواها قديمة من commit فات، فمندخلش جواها
    const bailedOut = node.alternate !== null && node.alternate.child === node.child;
    if (!bailedOut) walk(node.child);
  }
}

بالعامية

الـ component بيعمل render لواحد من 4 أسباب: أول mount، أو الـ state بتاعته اتغيرت، أو الـ parent عمل render، أو context بيقراه اتغير (القايمة كاملة بالعدّادات في درس 03). "الـ props اتغيرت" مش من الأسباب دي. لما الـ parent يعمل render الـ child بيعمل render سواء الـ props اتغيرت أو لأ، والـ props بتفرق بس لما الـ child يبقى ملفوف في memo، اللي بيقارن كل prop بـ Object.is (درس 08). فالسؤال المفيد هو: الـ render ده كان على الفاضي؟ وأنهي prop كسر الـ memo؟

طريقة DevTools (من الـ docs، not run here، هتعملها بإيدك في تمرين 2). افتح تاب Profiler، دوس على الترس، افتح إعدادات Profiler وعلّم على "Record why each component rendered while profiling". سجّل، اعمل الـ interaction، وقّف، اختار commit ودوس على component. الـ panel الجانبي هيقولك حاجة زي "Props changed: onSelect" أو "Hook 2 changed" أو "The parent component rendered".

بديل بيشتغل في أي مكان. useWhyDidYouRender بيحتفظ بالـ props القديمة في ref وبيقارنها بعد كل commit بنفس مقارنة Object.is اللي memo بيستخدمها. في صفحة فيها 1,000 row واللي بيتغير input بتاع note بس، بيطبع onSelect changed 1,000 مرة. السطر ده لوحده بيقولك الحل: خلي onSelect ثابت. وبعد useCallback الـ rows مبتتنفذش خالص مع كل حرف.

نظرة على التطبيق كله. الـ DevTools بيعرف بالـ commits عن طريق __REACT_DEVTOOLS_GLOBAL_HOOK__، وتقدر تركّب نسختك قبل ما react-dom يتحمّل. الـ React بينادي onCommitFiberRoot مع كل commit، وإنت تلف على الـ fibers (درس 18). فيه تفصيلتين مهمين: الـ flag اللي اسمه PerformedWork معناه "الـ function دي اتنفذت في الـ commit ده"، ولازم تتخطى أي subtree الـ child بتاعها هو نفسه بتاع الـ alternate، لأنها عملت bail out والـ flags اللي جواها فاضلة من commit أقدم. وفي الـ production الأسماء بتبقى minified. وده private API، فاستخدمه في التشخيص بس واتوقع إنه يتغير.

فين هستخدمه في شغلي؟ الـ support بيقولوا إن صفحة الـ invoices بتقطّع وهما بيكتبوا note. تحط useWhyDidYouRender مؤقتًا في InvoiceRow على الـ branch بتاعك، تكتب حرف واحد، وتشوف السطر. لو طلع onMarkPaid changed يبقى العلاج في الـ parent، مش في الـ row. وفي الـ PR تحط السطرين، قبل وبعد، بدل جملة "حسّنت الـ performance". أما الـ commit tracker فبتحطه مؤقتًا لما مش عارف تبدأ منين في صفحة فيها 200 component، عشان تطلّع أكتر 5 أسماء بيتنفذوا.
Trade-off: a wasted render isn't always a problem The same 1,000 wasted row renders cost about 12 ms per commit in a dev build but only about 2.4 ms in a production-profiling build (Part 6). If the rows are this cheap, the fix buys almost nothing, so measure the commit before spending review time on memo. Fix wasted renders when the commit is what's slow, not because the counter is high.
نفس الـ 1,000 render اللي على الفاضي بتكلّف حوالي 12 ms للـ commit في dev build، لكن حوالي 2.4 ms بس في production-profiling build (الجزء 6). لو الـ rows رخيصة كده، الـ fix مش هيجيب حاجة تقريبًا، فقيس الـ commit الأول قبل ما تضيّع وقت review على memo. صلّح الـ renders الزيادة لما يكون الـ commit هو البطيء فعلًا، مش عشان العدّاد رقمه كبير.

Part 2 — The Profiler API in production 🔴 Advancedالجزء 2 — الـ Profiler API في الـ production

English

<Profiler id onRender> calls your callback after each commit in its subtree with six values: id; phase ("mount", "update" or "nested-update"); actualDuration, the time spent rendering this subtree in this commit; baseDuration, the estimated cost of re-rendering the whole subtree with no memoization, summed from each component's most recent render; startTime; and commitTime, which is shared by every Profiler in the same commit so you can group them.

The pair to read is actual against base. With plain rows, actual stays close to base because everything re-renders. With memo rows, actual falls far below base. If you added memoization and actual is still close to base, it isn't working.

The trap: a normal production build calls onRender zero times, silently. React ships a separate build for this: alias react-dom/client to react-dom/profiling. That alias took the same page from 0 calls to 4 (mount plus three keystrokes) and cost 17 KB raw, about 5 KB gzip. Dev numbers aren't a substitute: the same commit is about twice as slow in dev.

Sending samples. Buffer in memory, cap the buffer, drop tiny commits, and flush with sendBeacon when the page is hidden, the last event you can rely on, especially on mobile. Sample whole sessions so one user's data stays comparable. The overhead caveat: the alias is decided at build time, so everyone on that build pays for it, and a sampling constant only reduces what you report. In my runs a 2,000-row commit went from about 2–2.7 ms to about 5.4 ms with a <Profiler> in the profiling build. So ship it to a canary or a performance environment, and keep the Profiler around the few subtrees you care about. Next has its own switch, a reactProductionProfiling config key (seen in the Next 16.4 config schema, not run here).

English

Reading DevTools Profiler (from the docs, not run here). Profiles are grouped by commit, shown as a bar chart at the top: each bar is one commit, and its height and colour show how long it took. The flame chart shows the tree for the selected commit: a bar's width is how long that component took when it last rendered, and its colour is the time in this commit (yellow is slow, blue is fast, gray didn't render). Part 4 — What the Compiler does 🔴 Advancedالجزء 4 — الـ Compiler بيعمل إيه

English

The React Compiler is a build-time Babel plugin (babel-plugin-react-compiler, version 1.0, stable since October 2025). It isn't on by default in React or in the Vite template: you install it. It rewrites each component and hook so that values and JSX are cached in a per-fiber array, which _c(n) from react/compiler-runtime gives you, guarded by checks like if ($[0] !== label).

That's finer than manual memoization in three ways. It caches individual values and JSX pieces, so one changed prop rebuilds only what depends on it. It works after an early return, where useMemo can't go because of the Rules of Hooks. And it gives children a stable element, so a child with unchanged input skips rendering without being wrapped in memo. Run on the same source, a page with no memoization code renders Row 8 times plain and 2 times compiled.

What it doesn't fix. It's caching, so it can't help when the inputs really change. An expensive function whose input changes runs every time: expensiveFilter still ran 3 times for 3 keystrokes in the search box, though an unrelated note input went from 3 calls to 0. A context value that changes must re-render every consumer: 100 PriceTags rendered in both builds, while the 100 non-consumers went from 100 to 0. Per the docs it only memoizes components and hooks, its cache isn't shared between components, and it targets updates, not the first mount. A slow computation used in five components runs five times, and that one still needs its own cache outside React.

The Rules of React are the contract: components are pure during render, props and state aren't mutated, and hooks are called unconditionally at the top level. A function the compiler can see breaking a rule is skipped: it stays as you wrote it and the rest of the file still compiles, so the build doesn't fail. That's panicThreshold: "none", the default.

Controlling scope. compilationMode is "infer" by default, which compiles functions named like components or hooks that create JSX or call hooks. "annotation" compiles only functions with a "use memo" directive. "all" compiles every top-level function and isn't recommended. "use no memo" opts one function out, and that's your first debugging tool. Below React 19, set target: "18" or "17" and install react-compiler-runtime: I confirmed the import changes. There's also an experimental Rust port, enabled with react({ compiler: true }) and the oxc-transform-react package. I'm mentioning it only so you recognise it; I didn't run it, and its README marks it experimental.

In a bundled production build react/compiler-runtime appeared 0 times, compiled or not, because the bundler inlines it. memo_cache_sentinel appeared once in the plain build, since React itself contains the string, and 4 times when compiled. // بيفرّق بين قيمة اتغيرت فعلًا و object جديد بنفس المحتوى
export function describeChange(key: string, before: unknown, after: unknown): string {
  if (typeof before === "function" && typeof after === "function") {
    return `${key}: new function (inline callback?)`;
  }
  if (typeof before === "object" && typeof after === "object" && before !== null && after !== null) {
    const same = JSON.stringify(before) === JSON.stringify(after);
    return same ? `${key}: new reference, same content` : `${key}: content changed`;
  }
  return `${key}: ${String(before)} -> ${String(after)}`;
}

Cheat sheet · الخلاصة

  • Render triggers: mount, own state, parent render, context. Props only matter behind memo, compared with Object.is.
  • Loop: reproduce, find the cause, change one thing, measure the same path.
  • "Why did this render": the DevTools setting, or a hook comparing previous props. onCommitFiberRoot gives an app-wide view, but it's a private API and you must skip bailed-out subtrees.
  • onRender: actual close to base means nothing skipped; actual far below base means memoization works.
  • Normal production build: onRender runs 0 times, no warning. Alias react-dom/client to react-dom/profiling. It costs about 5 KB gzip plus per-commit overhead, for everyone on that build.
  • Dev numbers are about twice as slow: use dev for counts and causes, profiling for timing.
  • Performance Tracks: dev has everything; profiling has Scheduler, plus Components inside <Profiler> with minified names; production has none. Throttle with Emulation.setCPUThrottlingRate.
  • Compiler: opt-in, caches values and JSX per fiber (_c(n), $[0] !== label). Row went from 8 renders to 2 with no memo code.
  • It doesn't fix inputs that really change, context values that change, sharing between components, or first mount.
  • Setup: babel({ presets: [reactCompilerPreset()] }). The old react({ babel }) is silently ignored on plugin-react 6.
  • Verify with the logger, or compare memo_cache_sentinel against a plain baseline (1 vs 4). react/compiler-runtime is 0 in any bundle.
  • A clean compile proves nothing: prop and state mutation passed both compiler and lint and showed 1 row instead of 3. Roll out by folder with E2E tests and numbers.

  • أسباب الـ render: mount، أو state بتاعته، أو render الـ parent، أو context. الـ props بتفرق بس ورا memo، وبتتقارن بـ Object.is.

  • onRender: لو actual قريب من base يبقى مفيش حاجة اتخطّت؛ ولو actual أقل بكتير يبقى الـ memoization شغالة.
  • الـ production العادي: onRender بيتنادى صفر مرة ومن غير warning. اعمل alias لـ react-dom/client على react-dom/profiling. تمنه حوالي 5 KB gzip وoverhead مع كل commit، لكل اللي على الـ build ده.
