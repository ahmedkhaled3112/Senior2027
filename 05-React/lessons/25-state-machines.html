Why this matters · ليه ده مهم

English

Every team has shipped this bug: a spinner sitting on top of an error, a customer charged twice after a double-click, a Back button that lands on a step with no data. They look unrelated, but they share a cause. The screen's real state was spread across several booleans, so it could reach combinations nobody designed, and nothing stopped it.

This lesson fixes that in three steps: a discriminated union, a transition table in a reducer (neither needs a dependency), and XState 5 when the flow earns it. Interviewers ask about it because this is where frontend and backend meet: an order's lifecycle on the server has the same shape. Every count and size below comes from a real run in Chrome 156 or Node 22.19.

بالعامية

كل فريق طلّع الـ bug ده قبل كده: spinner فوق رسالة error، عميل اتخصم منه مرتين عشان داس double-click، زرار Back بيوديك على خطوة مفيهاش data. شكلهم مش مرتبطين ببعض، بس السبب واحد: الـ state الحقيقية بتاعة الشاشة متفرقة على كذا boolean، فالشاشة ممكن توصل لتركيبات محدش صممها، ومفيش حاجة بتمنعها.

الدرس ده بيحل المشكلة على 3 خطوات: discriminated union، وبعده transition table جوه reducer (الاتنين من غير أي dependency)، وبعدين XState 5 لما الـ flow يستاهل. ده بيتسأل في الـ interviews لأنه النقطة اللي الـ frontend والـ backend بيتقابلوا فيها: دورة حياة الـ order على السيرفر ليها نفس الشكل. كل رقم وكل حجم تحت طالع من تشغيل حقيقي على Chrome 156 أو Node 22.19.

Part 1 — Boolean soup to a discriminated union 🔴 Advancedالجزء 1 — من الـ boolean soup للـ discriminated union

English

Take the usual hook: isLoading, isError, isSuccess, data. Four independent values, each on or off, give 24 = 16 combinations. Only 4 mean anything: idle, loading, success with data, error. The other 12 are states your types allow and your UI never designed for. Each setter runs on its own, so a code path that forgets one lands in one of those 12. Nothing throws. The screen just shows something impossible.

The run below forgets one line, setIsError(false), in a retry. During the retry the customer sees a spinner and an error together. After it succeeds they see "Could not load the order" right next to the order. There's no exception and no type error, and a test catches it only if someone thought to assert that the error is gone.

The fix is to make illegal states unrepresentable: one status field with a variant per state, and data attached only to the variant that has it. Now one setState replaces the whole state, so entering loading clears the error by construction, and order doesn't exist to read during loading. The same flow goes spinner, error, spinner, order.

The compiler does the rest. A switch ending in assertNever (TS lesson 04, part 4) turns "someone added a status" into a compile error at every switch that didn't handle it. Not every boolean is a smell, though: isSidebarOpen and isDarkMode are independent, so all 4 of their combinations are valid. The test is whether both can be true at once and still mean something. If not, they're one field. TanStack Query draws the same line: status and fetchStatus are separate because "do we have data" and "is it fetching" really are independent (lesson 10).

// بنعدّ كل الـ combinations اللي الـ 4 flags دول يسمحوا بيها
const flags = [false, true];
let total = 0;
const valid: string[] = [];

for (const isLoading of flags) {
  for (const isError of flags) {
    for (const isSuccess of flags) {
      for (const hasData of flags) {
        total++;
        const on = Number(isLoading) + Number(isError) + Number(isSuccess);
        // الـ data موجودة مع success بس، ومفيش غير flag واحد شغال في نفس الوقت
        if (on <= 1 && hasData === isSuccess) {
          valid.push(isLoading ? "loading" : isError ? "error" : isSuccess ? "success" : "idle");
        }
      }
    }
  }
}

type OrderLoad =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; order: Order }
  | { status: "error"; message: string };

function assertNever(value: never): never {
  throw new Error(`Unhandled state: ${JSON.stringify(value)}`);
}

let calls = 0;
async function fetchOrder(id: string): Promise<Order> {
  calls++;
  await wait(20);
  if (calls === 1) throw new Error("502 from orders-api");
  return { id, totalCents: 4200 };
}

// كل branch بيرجع شاشة واحدة، فمستحيل spinner و error مع بعض
function renderOrder(state: OrderLoad) {
  switch (state.status) {
    case "idle":
      return <p>Press Load</p>;
    case "loading":
      return <p>spinner</p>;
    case "success":
      return <p>Order {state.order.id}</p>;
    case "error":
      return <p>Could not load the order: {state.message}</p>;
    default:
      return assertNever(state);
  }
}

بالعامية

خد الـ hook المعتاد: isLoading وisError وisSuccess وdata. 4 قيم مستقلة، كل واحدة شغالة أو لأ، يبقى 24 = 16 تركيبة. منهم 4 بس ليهم معنى: idle، loading، success ومعاه data، وerror. الـ 12 التانيين الـ type سامح بيهم والـ UI عمره ما اتصمم ليهم. كل setter بيشتغل لوحده، فأي code path ينسى واحد بيقع في واحدة من الـ 12 دول. مفيش حاجة بتضرب error، الشاشة بس بتعرض حاجة مستحيلة.

المثال فوق نسي سطر واحد: setIsError(false) في الـ retry. أثناء الـ retry العميل شايف spinner و error مع بعض، وبعد ما ينجح شايف "Could not load the order" جنب الـ order. مفيش exception ولا type error، والـ test مش هيمسكها غير لو حد فكّر يتأكد إن الـ error اختفى.

الحل إنك تخلي الحالات الغلط مش ممكن تتكتب أصلًا: field واحد اسمه status، وكل حالة ليها variant، والـ data متعلقة بالـ variant اللي عنده data بس. كده setState واحدة بتبدل الحالة كلها، فدخول loading بيمسح الـ error لوحده، وorder مش موجود أصلًا عشان تقراه وإنت في loading. ونفس الـ flow بقى: spinner، error، spinner، order.

والباقي على الـ compiler. الـ switch اللي بينتهي بـ assertNever (الجزء 4 من درس TS رقم 04) بيحوّل "حد ضاف status" لـ compile error في كل switch ماغطّاهاش. بس مش كل boolean غلط: isSidebarOpen وisDarkMode مستقلين، والـ 4 تركيبات بتوعهم سليمين. الاختبار: ينفع الاتنين يبقوا true مع بعض ويبقى ليهم معنى؟ لو لأ، يبقوا field واحد. وTanStack Query بيرسم نفس الخط: status وfetchStatus منفصلين لأن "عندنا data؟" و"بنعمل fetch؟" فعلًا مستقلين (درس 10).

Part 2 — A machine by hand 🔴 Advancedالجزء 2 — machine بإيدك

English

A finite state machine is three things: a finite set of states, a set of events, and a transition function (state, event) → state. Its power is in what's missing. If the table has no entry for this event in this state, nothing happens. You don't write "ignore Pay while processing"; that's the default.

The checkout below has six states and seven events, and the whole machine fits in under 50 lines of TypeScript, types included, in a plain reducer. Compare six flags (isCart, isShipping, isPayment, isProcessing, isConfirmed, isFailed): that's 26 = 64 combinations for 6 valid states, with guards scattered across handlers. The table puts every rule in one object you can read top to bottom, review in a PR, and test with no React at all.

The payoff shows at the edges. The double-pay test clicks twice, 10 ms apart, as a real double-click does. The boolean version has a guard, but there's an await between checking isProcessing and setting it, so both clicks read false and the card is charged twice. In the machine version a click only dispatches PAY. React queues actions and runs the reducer against the latest state, so the first moves to processing and the second finds no entry and returns the same object (lesson 06, part 2). The charge lives in an effect keyed on status, so the reducer stays pure.

Two limits to say out loud. The UI machine protects one tab of one browser: a second tab or a retried request still reaches your API, so the server needs an idempotency key too (Node lesson 14, part 6). And this version has no guards, no timers, no nesting, and cancellation is only a flag. When you start adding those, you're rewriting XState, which is the next part.

كل سهم هو سطر في الجدول، وكل حاجة مالهاش سهم مبتحصلش. من cart لـ shipping بـ CHECKOUT، ومن shipping لـ payment بـ SHIPPING_SUBMITTED، ومن payment لـ processing بـ PAY، وBACK بيرجع خطوة في الخطوتين الأولانيين. من processing يا إما confirmed يا إما failed، ومن failed الـ RETRY بيرجعك لـ payment. في processing مفيش سهم لـ PAY ولا BACK فمبيعملوش حاجة، وconfirmed مفيش منها أي سهم خارج، فـ PAYMENT_FAILED لو وصل متأخر مش هيلغي الدفع.
export interface CartItem { sku: string; priceCents: number }

export type Status = "cart" | "shipping" | "payment" | "processing" | "confirmed" | "failed";

export type CheckoutEvent =
  | { type: "CHECKOUT" }
  | { type: "SHIPPING_SUBMITTED"; address: string }
  | { type: "PAY"; cardToken: string }
  | { type: "BACK" }
  | { type: "PAYMENT_OK"; paymentId: string }
  | { type: "PAYMENT_FAILED"; reason: string }
  | { type: "RETRY" };

export interface Checkout {
  status: Status;
  items: CartItem[];
  address?: string;
  cardToken?: string;
  paymentId?: string;
  failure?: string;
}

// الجدول هو الـ spec كله: لكل حالة، إيه الـ events المسموحة وبتودّي على فين
const table = {
  cart: { CHECKOUT: "shipping" },
  shipping: { SHIPPING_SUBMITTED: "payment", BACK: "cart" },
  payment: { PAY: "processing", BACK: "shipping" },
  processing: { PAYMENT_OK: "confirmed", PAYMENT_FAILED: "failed" },
  confirmed: {},
  failed: { RETRY: "payment" },
} as const satisfies Record<Status, Partial<Record<CheckoutEvent["type"], Status>>>;

export function checkoutReducer(state: Checkout, event: CheckoutEvent): Checkout {
  const row: Partial<Record<CheckoutEvent["type"], Status>> = table[state.status];
  const target = row[event.type];
  // لو الـ event مش في الجدول: نفس الـ reference، و React مش هيعمل re-render
  if (!target) return state;

  const next: Checkout = { ...state, status: target };
  if (event.type === "SHIPPING_SUBMITTED") next.address = event.address;
  if (event.type === "PAY") next.cardToken = event.cardToken;
  if (event.type === "PAYMENT_OK") next.paymentId = event.paymentId;
  if (event.type === "PAYMENT_FAILED") next.failure = event.reason;
  if (event.type === "RETRY") delete next.failure;
  return next;
}

Part 3 — XState 5 🔴 Advancedالجزء 3 — XState 5

English

XState 5 separates the diagram from the code. setup({ types, actors, actions, guards }) declares TypeScript types and named implementations. .createMachine({...}) is the chart itself, as data: states and transitions that refer to those implementations by name. Because they're named, machine.provide({ actors: {...} }) swaps the real payment API for a fake in a test.

Five pieces do the work:

  • context: data that isn't a state, such as attempts and paymentId.
  • assign: updates context, and runs as an action during a transition. Context is never mutated directly.
  • Guards: a predicate decides whether a transition is taken. canRetry blocks the fourth attempt. When a transition is an array, the first passing guard wins, which is how onDone below picks threeDS or confirmed.
  • Actions: fire-and-forget side effects such as analytics.
  • invoke with fromPromise: the state owns the async work. It starts on entry, reports through onDone or onError, and gets an AbortSignal that fires when the state exits or the actor stops.

Testing needs no React: createActor(machine, { input }).start(), then send, waitFor and assert. In React, useMachine from @xstate/react 6 returns [snapshot, send, actorRef], and the component only asks questions: snapshot.matches("threeDS") and snapshot.can({ type: "PAY", ... }). can evaluates guards without sending, so a button's disabled can't drift away from the rules.

Now the costs, measured. XState plus @xstate/react add 14.3 KB gzip over React alone in an esbuild production build, against 0.4 KB for the hand-written table. useMachine re-renders on every new snapshot: 101 renders for 100 events that changed only context, against 1 with useActorRef and useSelector. And under StrictMode in development, the hook starts the actor, stops it and starts it again, so an invoke in the initial state runs twice. One reached through an event runs once, and a production build runs either once. Anything invoked on mount has to be safe to repeat.

export type ChargeResult =
  | { outcome: "paid"; paymentId: string }
  | { outcome: "requires_3ds"; paymentId: string; challengeUrl: string };

interface Context {
  totalCents: number;
  idempotencyKey: string;
  attempts: number;
  address?: string;
  cardToken?: string;
  paymentId?: string;
  challengeUrl?: string;
  failure?: string;
}

  | { type: "CHECKOUT" }
  | { type: "SUBMIT_SHIPPING"; address: string }
  | { type: "PAY"; cardToken: string }
  | { type: "CHALLENGE_PASSED" }
  | { type: "CHALLENGE_FAILED" }
  | { type: "BACK" }
  | { type: "RETRY" };

export const MAX_ATTEMPTS = 3;

export const checkoutMachine = setup({
  types: {
    context: {} as Context,
    events: {} as Event,
    input: {} as { totalCents: number; idempotencyKey: string },
  },
  // الـ implementations هنا default، والـ test أو الـ app بيبدّلها بـ provide
  actors: {
    chargeCard: fromPromise<ChargeResult, ChargeInput>(async () => {
      throw new Error("chargeCard not provided");
    }),
  },
  actions: {
    trackFailure: (_, params: { reason: string }) => {
      console.log(`[analytics] payment_failed: ${params.reason}`);
    },
  },
  guards: {
    needs3ds: (_, params: { result: ChargeResult }) => params.result.outcome === "requires_3ds",
    canRetry: ({ context }) => context.attempts < MAX_ATTEMPTS,
    hasAddress: (_, params: { address: string }) => params.address.trim().length > 0,
  },
}).createMachine({
  id: "checkout",
  initial: "cart",
  context: ({ input }) => ({ ...input, attempts: 0 }),
  states: {
    cart: { on: { CHECKOUT: "shipping" } },
    shipping: {
      on: {
        BACK: "cart",
        SUBMIT_SHIPPING: {
          // الـ guard بيرفض العنوان الفاضي، والـ state مبيتغيرش
          guard: { type: "hasAddress", params: ({ event }) => ({ address: event.address }) },
          target: "payment",
          actions: assign({ address: ({ event }) => event.address }),
        },
      },
    },
    payment: {
      on: {
        BACK: "shipping",
        PAY: {
          target: "processing",
          actions: assign({
            cardToken: ({ event }) => event.cardToken,
            attempts: ({ context }) => context.attempts + 1,
          }),
        },
      },
    },
    processing: {
      // الـ invoke بيبدأ مع الدخول، وبيتلغي لوحده مع الخروج من الحالة
      invoke: {
        src: "chargeCard",
        input: ({ context }) => ({
          cardToken: context.cardToken!,
          totalCents: context.totalCents,
          idempotencyKey: context.idempotencyKey,
        }),
        onDone: [
          {
            guard: { type: "needs3ds", params: ({ event }) => ({ result: event.output }) },
            target: "threeDS",
            actions: assign({
              paymentId: ({ event }) => event.output.paymentId,
              challengeUrl: ({ event }) =>
                event.output.outcome === "requires_3ds" ? event.output.challengeUrl : undefined,
            }),
          },
          {
            target: "confirmed",
            actions: assign({ paymentId: ({ event }) => event.output.paymentId }),
          },
        ],
        onError: {
          target: "failed",
          actions: [
            assign({ failure: ({ event }) => (event.error as Error).message }),
            { type: "trackFailure", params: ({ event }) => ({ reason: (event.error as Error).message }) },
          ],
        },
      },
    },
    threeDS: {
      on: {
        CHALLENGE_PASSED: "confirmed",
        CHALLENGE_FAILED: {
          target: "failed",
          actions: assign({ failure: "3DS challenge failed" }),
        },
      },
    },
    failed: {
      on: {
        RETRY: { guard: "canRetry", target: "payment" },
      },
    },
    confirmed: { type: "final" },
  },
});

بالعامية

XState 5 بيفصل الرسمة عن الكود. setup({ types, actors, actions, guards }) بتعرّف فيها الـ types والـ implementations بأسماء. و.createMachine({...}) هي الـ chart نفسها كـ data: حالات وانتقالات بتنادي الـ implementations دي بالاسم. ولأنها بأسماء، machine.provide({ actors: {...} }) بتبدّل API الدفع الحقيقي بـ fake في الـ test.

5 حاجات بيعملوا الشغل:

  • context: الـ data اللي مش حالة، زي attempts وpaymentId.
  • assign: بتعدّل الـ context، وبتشتغل كـ action أثناء الانتقال. الـ context عمره ما بيتعدل مباشرة.
  • الـ guards: شرط بيقرر الانتقال يحصل ولا لأ. canRetry بيمنع المحاولة الرابعة. ولو الانتقال array، أول guard ينجح هو اللي بيكسب، وده اللي بيخلي onDone يختار threeDS أو confirmed.
  • الـ actions: side effects تعملها وتمشي زي الـ analytics.
  • invoke مع fromPromise: الحالة نفسها مسؤولة عن الشغل الـ async. بيبدأ مع الدخول، وبيبلّغ بـ onDone أو onError، وبياخد AbortSignal بيتفعّل لما الحالة تخلص أو الـ actor يقف.

الـ testing مش محتاج React: createActor(machine, { input }).start()، وبعدها send وwaitFor وassert. وفي React، useMachine من @xstate/react 6 بيرجع [snapshot, send, actorRef]، والـ component بيسأل بس: snapshot.matches("threeDS") وsnapshot.can({ type: "PAY", ... }). الـ can بتحسب الـ guards من غير ما تبعت حاجة، فالـ disabled بتاع الزرار مستحيل يبعد عن القواعد.

ودي التكلفة بالأرقام. XState ومعاه @xstate/react بيزوّدوا 14.3 KB gzip فوق React في production build بـ esbuild، مقابل 0.4 KB للجدول بإيدك. useMachine بيعمل re-render مع كل snapshot جديد: 101 render لـ 100 event غيّروا الـ context بس، مقابل 1 مع useActorRef وuseSelector. وتحت StrictMode في development، الـ hook بيعمل start للـ actor وstop وstart تاني، فالـ invoke اللي في الحالة الأولى بيتنفذ مرتين، واللي بتوصله بـ event مرة واحدة، وفي production الاتنين مرة واحدة. يعني أي حاجة بتتنادى مع الـ mount لازم تستحمل التكرار.

Part 4 — Statecharts 🔴 Advancedالجزء 4 — الـ statecharts

English

Flat machines break down as flows grow. Adding Back to 12 states means 12 arrows, and independent concerns multiply: a 4-state upload next to a 2-state form needs 4 × 2 = 8 flat states, and one more 3-state region makes it 24. David Harel's statecharts (1987) add what stops that explosion, and XState implements them:

  • Hierarchical states. payment contains card, wallet and threeDS. BACK on the parent is inherited by every child, and a child can override it (BACK: {} blocks it during the 3DS challenge). matches("payment") and matches({ payment: "threeDS" }) are both true, so a layout can ask about the region without knowing the step.
  • Guards work as in Part 3, and stateIn lets a guard ask about another region.
  • Entry and exit actions run however you got there. Wiping the one-time 3DS session on exit can't be forgotten on some route out.
  • History. A type: "history" node remembers the last child. Back from review returns to wallet, not to the initial card. shallow remembers one level and deep the whole path.
  • Parallel states. With type: "parallel" all regions are active at once. value becomes an object with one key per region, and the 8 flat states become 4 + 2 = 6 nodes.

A multi-step wizard needs one more thing: surviving a reload. actor.getPersistedSnapshot() returns a JSON-safe snapshot with the state, context and history, and createActor(machine, { snapshot }) resumes from it. The page below does a real location.reload() in Chrome and comes back on payment.wallet.

Three traps, each measured below. First, context is saved verbatim, so a cardToken lands in localStorage as plain text; keep secrets out of context or save a filtered copy. Second, a snapshot saved mid-invoke restarts the promise on restore: that's a second charge. Save only settled states, and keep the API idempotent. Third, after a release renames a state, createActor doesn't throw. The snapshot's status is "error", and if you call start() the error surfaces later as an uncaught exception, so try/catch doesn't help (in Node it killed the process). Check the status before starting and put a version in the storage key.

Part 5 — Choosing 🔴 Advancedالجزء 5 — تختار إزاي

English

Climb only when the rung below hurts. Start with useState. Use a union as soon as one request has more than one outcome. Reach for a table in useReducer when there are ordering rules and several entry points. Move to XState when you need what a table can't do cheaply: nesting, parallel regions, invoked work with cancellation, timers, history or resume.

Signs you've gone too far: a machine with only open and closed; a table where every state reaches every other, so it enforces nothing; server data copied into context, when TanStack Query already owns caching, retries and dedup, and the machine should hold the flow, not the data; one giant machine for the whole app; a machine only its author can read. The team cost is real: actors, snapshots and setup typing take time to learn, and the deep generics give long errors. An inline and([stateIn(...), stateIn(...)]) failed on TS 7 with a four-line TS2322 here, ending in Type 'any' is not assignable to type 'never', and named guards fixed it. That cost is worth paying when a bug costs money or a flow has outgrown a code review, and not otherwise.

The backend has the same shape. An order on the server moves through pending, paid, shipped, and an illegal move becomes a 409. There's one addition a table can't give you alone: two requests can both read pending. UPDATE ... WHERE id = $2 AND status = $3 is the guard at the database level, so only one wins. The run below uses PGlite, which is Postgres compiled to WASM with one connection in-process: the statements interleave as they would on a server, but it isn't a load test.

Don't share one table between them. shipping, processing and BACK are UI steps, while paid and refunded are domain facts, and the server is the source of truth. The UI machine shows where the customer is in the flow. Section 08 (Design Patterns, the State pattern) and section 09 (Software Architecture, lifecycles as an architectural tool) take the server side further.

// نفس شكل جدول الـ checkout، بس على order في الـ backend
type OrderStatus = "pending" | "paid" | "shipped" | "cancelled" | "refunded";
type OrderEvent = "PAY" | "SHIP" | "CANCEL" | "REFUND";

const orderTable: Record<OrderStatus, Partial<Record<OrderEvent, OrderStatus>>> = {
  pending: { PAY: "paid", CANCEL: "cancelled" },
  paid: { SHIP: "shipped", REFUND: "refunded" },
  shipped: { REFUND: "refunded" },
  cancelled: {},
  refunded: {},
};

class IllegalTransition extends Error {
  readonly httpStatus = 409;
  constructor(from: OrderStatus, event: OrderEvent) {
    super(`order is ${from}: ${event} not allowed`);
  }
}

const db = new PGlite();
await db.exec(`
  CREATE TABLE orders (id text PRIMARY KEY, status text NOT NULL);
  INSERT INTO orders VALUES ('ord_1', 'pending');
`);

// الـ WHERE status هو نفس الـ guard: لو حد سبقك، الصف مش هيتعدّل
async function applyEvent(id: string, event: OrderEvent): Promise<OrderStatus> {
  const { rows } = await db.query<{ status: OrderStatus }>("SELECT status FROM orders WHERE id = $1", [id]);
  const from = rows[0]!.status;
  const to = orderTable[from][event];
  if (!to) throw new IllegalTransition(from, event);
  const res = await db.query("UPDATE orders SET status = $1 WHERE id = $2 AND status = $3", [to, id, from]);
  if (res.affectedRows === 0) throw new IllegalTransition(from, event);
  return to;
}

    </>
  );
}

Solution · الحل 
interface Invoice { id: string; totalCents: number }

// كل حالة شايلة الـ data بتاعتها بس
type InvoiceLoad =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; invoice: Invoice }
  | { status: "error"; message: string };

type InvoiceEvent =
  | { type: "LOAD" }
  | { type: "LOADED"; invoice: Invoice }
  | { type: "FAILED"; message: string };

export function invoiceReducer(state: InvoiceLoad, event: InvoiceEvent): InvoiceLoad {
  switch (event.type) {
    case "LOAD":
      return { status: "loading" };
    case "LOADED":
      // رد متأخر بعد ما خرجنا من loading بيتجاهل
      return state.status === "loading" ? { status: "success", invoice: event.invoice } : state;
    case "FAILED":
      return state.status === "loading" ? { status: "error", message: event.message } : state;
    default: {
      const unreachable: never = event;
      return unreachable;
    }
  }
}

const s1 = invoiceReducer({ status: "idle" }, { type: "LOAD" });
const s2 = invoiceReducer(s1, { type: "FAILED", message: "502" });
const s3 = invoiceReducer(s2, { type: "LOAD" });
const s4 = invoiceReducer(s3, { type: "LOADED", invoice: { id: "inv_1", totalCents: 900 } });
console.log(s2, s3, s4);
console.log(invoiceReducer(s4, { type: "FAILED", message: "late" }) === s4);

import assert from "node:assert/strict";

type Status = "payment" | "applyingCoupon" | "processing";
type EventType = "APPLY_COUPON" | "COUPON_OK" | "COUPON_FAILED" | "PAY";

// حالة جديدة = سطر جديد في الجدول، ومفيش if في أي component
const table = {
  payment: { APPLY_COUPON: "applyingCoupon", PAY: "processing" },
  applyingCoupon: { COUPON_OK: "payment", COUPON_FAILED: "payment" },
  processing: {},
} as const satisfies Record<Status, Partial<Record<EventType, Status>>>;

function next(status: Status, event: EventType): Status {
  const row: Partial<Record<EventType, Status>> = table[status];
  return row[event] ?? status;
}

assert.equal(next("processing", "APPLY_COUPON"), "processing");

import { assign, createActor, fromPromise, setup, SimulatedClock } from "xstate";

let aborted = false;

const machine = setup({
  types: { context: {} as { failure?: string } },
  actors: {
    // الـ API معلّق ومبيردش، زي بوابة دفع واقعة
    chargeCard: fromPromise(({ signal }) => {
      signal.addEventListener("abort", () => { aborted = true; });
      return new Promise<{ paymentId: string }>(() => {});
    }),
  },
  delays: { PAYMENT_TIMEOUT: 30_000 },
}).createMachine({
  initial: "processing",
  context: {},
  states: {
    processing: {
      invoke: { src: "chargeCard", onDone: "confirmed" },
      // الـ after بيتلغي لوحده لو خرجنا من الحالة قبل المدة
      after: {
        PAYMENT_TIMEOUT: {
          target: "failed",
          actions: assign({ failure: "Payment gateway timed out" }),
        },
      },
    },
    confirmed: { type: "final" },
    failed: {},
  },
});

// الساعة الوهمية بتخلي الـ test يخلص فورًا من غير ما يستنى 30 ثانية
const clock = new SimulatedClock();
const actor = createActor(machine, { clock }).start();

clock.increment(1);
console.log("at 30.000s:", actor.getSnapshot().value, "|", actor.getSnapshot().context.failure);
console.log("charge aborted:", aborted);

Cheat sheet · الخلاصة

  • N booleans allow 2N combinations. 4 flags: 16 combinations, 4 valid. If two can't both be true, they're one field.
  • Union on status, data on its variant only, assertNever in the switch: a new status fails the build.
  • Machine = states + events + (state, event) → state. No entry means nothing happens, and that's the feature.
  • Reducers stay pure. Start side effects on entering a state: an effect keyed on status, or invoke.
  • XState 5: setup({...}).createMachine({...}), provide for fakes, createActor and waitFor for tests with no React. ≈ 14.3 KB gzip.
  • invoke with fromPromise gets a signal that aborts on exit. Under dev StrictMode, an invoke in the initial state runs twice.
  • can() drives disabled. useActorRef with useSelector cut 101 renders to 1. createActorContext shares one actor.
  • Statecharts: hierarchy, parallel regions, entry and exit actions, history. They stop the state explosion: 4 × 2 flat becomes 4 + 2.
  • Persist: getPersistedSnapshot, settled states only, no secrets in context, a version in the key, check status before start.
  • Choose: useState, then a union, then a table, then XState. Server data stays in TanStack Query.
  • The UI machine guards one tab. The server enforces transitions with WHERE status = $from, 409 and idempotency keys.
بالعامية
  • عدد N من الـ booleans بيسمح بـ 2N تركيبة. 4 flags يعني 16 تركيبة منهم 4 سليمين. لو اتنين مينفعش يبقوا true مع بعض، يبقوا field واحد.
  • union على status، والـ data على الـ variant بتاعها بس، وassertNever في الـ switch: أي status جديد يكسر الـ build.
  • الـ machine هي حالات وevents و(state, event) → state. مفيش سطر يعني مفيش حاجة بتحصل، ودي الميزة نفسها.
  • الـ reducers تفضل pure. ابدأ الـ side effects مع دخول الحالة: effect مربوط بـ status أو invoke.
  • XState 5: setup({...}).createMachine({...})، وprovide للـ fakes، وcreateActor وwaitFor للـ tests من غير React. حوالي 14.3 KB gzip.
  • invoke مع fromPromise بياخد signal بيعمل abort عند الخروج. وتحت StrictMode في dev، الـ invoke اللي في الحالة الأولى بيتنفذ مرتين.
  • can() هي اللي تحدد الـ disabled. useActorRef مع useSelector نزّلوا 101 render لـ 1. وcreateActorContext بيشارك actor واحد.
  • الـ statecharts: hierarchy، وparallel regions، وentry وexit actions، وhistory. بيوقفوا انفجار الحالات: 4 × 2 مسطحة بتبقى 4 + 2.
  • الـ persist: getPersistedSnapshot، والحالات المستقرة بس، ومفيش أسرار في الـ context، وversion في المفتاح، وافحص status قبل start.
  • الاختيار: useState، بعدين union، بعدين جدول، بعدين XState. و data السيرفر تفضل في TanStack Query.
