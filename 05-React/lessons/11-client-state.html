Why this matters · ليه ده مهم

English

Most React performance problems and many of its strangest bugs come down to one decision: where a piece of state lives. Put it too high and typing one letter re-renders 2,000 table rows. Put it in a module-level store on a server and one user's data can end up in another user's HTML. Put it in localStorage without a version and your next release breaks every returning customer's cart.

Choosing a library is the smaller half of this. Once server state has moved to TanStack Query (lesson 10), what's left is usually small, and the choice between Zustand, Jotai and Redux Toolkit becomes a real engineering trade-off you can defend with numbers. Interviewers ask about exactly that. Every count and bundle size in this lesson comes from a real run in Chrome 156; the timings are from a loaded Windows machine, so they're marked ≈ and the counts are what you should trust.

بالعامية

أغلب مشاكل الـ performance في React، وكتير من أغرب الـ bugs، راجعين لقرار واحد: الـ state ده عايش فين. لو حطيته عالي زيادة، كتابة حرف واحد بتعمل re-render لـ 2,000 row في جدول. لو حطيته في store على مستوى الـ module على السيرفر، بيانات user ممكن تظهر في HTML بتاع user تاني. ولو حطيته في localStorage من غير version، الـ release الجاي هيكسر الـ cart بتاع كل عميل راجع.

اختيار الـ library هو النص الأصغر من الموضوع. أول ما الـ server state ينتقل لـ TanStack Query (درس 10)، اللي بيفضل غالبًا حاجة صغيرة، والاختيار بين Zustand وJotai وRedux Toolkit بيبقى trade-off هندسي حقيقي تقدر تدافع عنه بأرقام. وده بالظبط اللي بيتسأل في الـ interviews. كل رقم عدّ وكل حجم bundle في الدرس ده طالع من تشغيل حقيقي على Chrome 156، أما الأزمنة فمن جهاز Windows عليه ضغط، فمعلّم عليها بـ ≈، والـ counts هي اللي تعتمد عليها.

Part 1 — Where state lives 🟡 Intermediateالجزء 1 — الـ state مكانه فين

English

Treat placement as a ladder and climb only when the current rung stops working. Start with local state in the component that uses it. If two siblings need it, lift it to their closest common ancestor, and no higher. If a prop only passes through layers that don't read it, try composition (pass elements as children) before anything global. If many distant components read something that rarely changes, use context. If many distant components read and write something that changes often, use a store.

The cost of lifting too high is concrete. When a component's state changes, React re-renders it and everything it renders, unless the child element is the same reference or is memoized and its props and context are unchanged. The example below keeps a sidebar note above a 2,000-row table that never reads it. The table runs 2,000 row renders per keystroke. There are two fixes, and neither needs memo: push the state down into the sidebar, or keep it in a layout and pass the table as children. In the second fix the table's element was created by the layout's parent, so when the layout re-renders it gets the same element back and React skips that subtree. (The counters in these examples are measuring tools. Incrementing a module variable during render is impure, so don't ship them.)

Second rule: derive, don't duplicate. If a value can be computed from other state during render, it's not state. Keeping it in a second useState synced by an effect costs an extra render and creates a commit where the two values disagree. React may even let that wrong commit reach the screen.

This lesson covers client state only. Three other kinds have their own lessons: server state (lesson 10), form state (lesson 12) and URL state (lesson 13).

import { useEffect, useState } from "react";

interface Line { sku: string; cents: number }
const first: Line = { sku: "KB-1", cents: 150_000 };
const second: Line = { sku: "MS-2", cents: 50_000 };
const sum = (lines: Line[]) => lines.reduce((acc, l) => acc + l.cents, 0);
const log: string[] = [];

// ❌ الـ total متخزّن تاني في state وبيتزامن بـ effect
function CartDuplicated() {
  const [lines, setLines] = useState([first]);
  const [total, setTotal] = useState(sum([first]));
  useEffect(() => setTotal(sum(lines)), [lines]);
  log.push(`duplicated render: lines=${lines.length} total=${total}`);
  return <button id="dup" onClick={() => setLines([first, second])}>{total}</button>;
}

  log.push(`derived render: lines=${lines.length} total=${total}`);

}

بالعامية

فكّر في مكان الـ state كأنه سلّم، ومتطلعش درجة غير لما الدرجة الحالية تفشل. ابدأ بـ local state في الـ component اللي بيستخدمه. لو اتنين siblings محتاجينه، ارفعه لأقرب ancestor مشترك ومش أعلى من كده. لو الـ prop بيعدّي من layers مش بتقراه، جرّب composition (تعدّي elements كـ children) قبل أي حاجة global. لو components كتير وبعيد عن بعض بتقرا حاجة نادرًا ما بتتغير، استخدم context. ولو بتقرا وتكتب في حاجة بتتغير كتير، استخدم store.

تكلفة الرفع الزيادة حاجة ملموسة. لما الـ state بتاع component يتغير، React بيعمل re-render ليه ولكل اللي بيرسمه، إلا لو الـ child element هو نفس الـ reference، أو معمول له memo والـ props والـ context بتوعه متغيروش. المثال فوق حاطط note بتاعة sidebar فوق جدول 2,000 row مش بيقراها أصلًا، فالجدول بيعمل 2,000 render مع كل حرف. فيه حلّين، ومحدش فيهم محتاج memo: تنزّل الـ state جوه الـ sidebar، أو تسيبه في layout وتعدّي الجدول كـ children. في الحل التاني الـ element بتاع الجدول اتعمل في الـ parent بتاع الـ layout، فلما الـ layout يعمل re-render بياخد نفس الـ element، وReact بيتخطى الـ subtree ده. (العدّادات اللي في الأمثلة دي أدوات قياس بس. زيادة متغير على مستوى الـ module وقت الـ render حاجة مش pure، فمتنزّلهاش production.)

القاعدة التانية: اشتق، متكررش. لو القيمة تتحسب من state تاني وقت الـ render، يبقى هي مش state. لو خزنتها في useState تاني وزامنتها بـ effect، بتدفع render زيادة وبيبقى عندك commit القيمتين فيه مش متفقين، وReact ممكن كمان يسيب الـ commit الغلط ده يوصل للشاشة.

الدرس ده عن الـ client state بس. فيه 3 أنواع تانية ليها دروسها: الـ server state (درس 10)، والـ form state (درس 12)، والـ URL state (درس 13).

فين هستخدمه في شغلي؟ صفحة admin فيها جدول orders وbox بحث في الـ sidebar، والـ PM بيشتكي إن الكتابة تقيلة على لابتوب الفريق. قبل ما تفكر في memo أو virtualization، افتح الكود وبص الـ useState بتاع البحث فين. لو الجدول مش بيقرا القيمة لحد ما المستخدم يدوس Enter، نزّل الـ state جوه الـ box وابعت القيمة النهائية بس فوق. ده تعديل 5 سطور بيوفر 2,000 render في الـ keystroke.
Interview question "Typing in a search box is slow because the page re-renders a huge table. What do you try, in what order?" → First ask who reads the value. If the table doesn't read it while typing, move the state down, or pass the table as children so its element stays the same. If the table does read it, use a deferred render for the table (useDeferredValue, lesson 19) and memoize the rows. Virtualize if the row count is the real problem. memo alone is rarely the first answer, because it treats the symptom.
"الكتابة في box بحث بطيئة لأن الصفحة بتعمل re-render لجدول ضخم. هتجرّب إيه وبأي ترتيب؟" ← الأول اسأل مين بيقرا القيمة. لو الجدول مش بيقراها وقت الكتابة، نزّل الـ state لتحت، أو عدّي الجدول كـ children عشان الـ element بتاعه يفضل هو هو. لو الجدول بيقراها فعلًا، خلّي الـ render بتاعه deferred بـ useDeferredValue (درس 19) واعمل memo للـ rows. واعمل virtualization لو عدد الـ rows هو المشكلة الحقيقية. memo لوحده نادرًا ما يكون أول إجابة، لأنه بيعالج العَرَض مش السبب.

Part 2 — Context for dependency injection 🟡 Intermediateالجزء 2 — الـ context للـ dependency injection

English

Context is a way to hand a value to a subtree without passing props. It isn't a state manager and has no selectors: every consumer re-renders whenever the provider's value changes by Object.is, and memo can't stop that (the mechanics are in lesson 08). So it fits values that change rarely and are read widely: theme, the signed-in user, locale, the current tenant, feature flags. When the theme does change, re-rendering everything is usually correct anyway.

The typed pattern is createContext<T | null>(null) plus a small hook that throws when the provider is missing. A fake default value hides a missing provider until a user finds it in production. The hook also narrows the type, so call sites never deal with null. React 19 lets you render <TenantContext value={...}> directly, and use(Context) reads the value (<Ctx.Provider> and useContext still work).

The wrong use is high-frequency state. In the example below a 500-product grid shares one context with a cart note. Every card reads only addLine, yet each keystroke in the note re-renders all 500, and neither memo nor useMemo helps, because the value really did change. The fix is to keep the note local and put only a stable action in context.

The best use of context is the one its name suggests: dependency injection. If a component gets its analytics client, payment gateway or clock from context, tests can inject a plain object instead of mocking a module. That test double needs no vi.mock, no network and no knowledge of the vendor's SDK.

import { createContext, use } from "react";
import { renderToStaticMarkup } from "react-dom/server";

interface Tenant { id: string; name: string; currency: "EGP" | "USD"; plan: "free" | "pro" }

// الـ default هنا null عشان نسيان الـ provider يبقى error واضح مش tenant وهمي
const TenantContext = createContext<Tenant | null>(null);

export function useTenant(): Tenant {
  const tenant = use(TenantContext);
  if (tenant === null) {
    throw new Error("useTenant must be used inside <TenantContext value={...}>");
  }
  return tenant;
}

  const { currency } = useTenant();
  return <b>{`${(cents / 100).toFixed(2)} ${currency}`}</b>;
}

import { Profiler, createContext, memo, use, useCallback, useMemo, useState } from "react";
import { createRoot } from "react-dom/client";

const stats = { cardRenders: 0, commitMs: 0 };

// ⁦==== ❌⁩ النسخة الغلط: draft الـ cart كله في context واحد ⁦====⁩
interface CartDraft {
  note: string;
  setNote: (note: string) => void;
  lines: string[];
  addLine: (sku: string) => void;
}
const CartDraftContext = createContext<CartDraft | null>(null);

function useCartDraft() {
  const value = use(CartDraftContext);
  if (!value) throw new Error("missing provider");
  return value;
}

function CartDraftProvider({ children }: { children: React.ReactNode }) {
  const [note, setNote] = useState("");
  const [lines, setLines] = useState<string[]>([]);
  // الـ useMemo مش هينقذك هنا: الـ note اتغير فالـ value لازم يتغير
  const value = useMemo(
    () => ({ note, setNote, lines, addLine: (sku: string) => setLines((l) => [...l, sku]) }),
    [note, lines],
  );
  return <CartDraftContext value={value}>{children}</CartDraftContext>;
}

// الكارت بياخد addLine بس، ومع كده بيعمل re-render مع كل حرف في الـ note
const ProductCard = memo(function ProductCard({ sku }: { sku: string }) {
  stats.cardRenders++;
  const { addLine } = useCartDraft();
  return <button onClick={() => addLine(sku)}>{sku}</button>;
});

function NoteInput() {
  const { note, setNote } = useCartDraft();
  return <input aria-label="note" value={note} onChange={(e) => setNote(e.target.value)} />;
}

const skus = Array.from({ length: 500 }, (_, i) => `SKU-${i}`);

const AddLineContext = createContext<((sku: string) => void) | null>(null);

function CartActionsProvider({ children }: { children: React.ReactNode }) {
  const [, setLines] = useState<string[]>([]);
  // الـ function دي ثابتة طول عمر الـ provider، فالـ value عمره ما بيتغير
  const addLine = useCallback((sku: string) => setLines((l) => [...l, sku]), []);
  return <AddLineContext value={addLine}>{children}</AddLineContext>;
}

  stats.cardRenders++;
  const addLine = use(AddLineContext)!;

Trade-off: splitting contexts vs moving to a store You can split one context into state and dispatch so that action-only consumers stop re-rendering. That works and needs no dependency. But if readers still need different slices of a changing object, you'd end up with one context per slice. At that point a store with selectors is simpler.

Part 3 — Zustand 5 🟡 Intermediateالجزء 3 — Zustand 5

English

Zustand gives you a store outside React with state and actions together, and a hook that subscribes through a selector. There's no provider. The component re-renders only when the selector's result changes by Object.is, so useCart((s) => s.qty[sku]) makes a card care about its own quantity alone. Calling useCart() with no selector subscribes to the entire state object: any change re-renders the component. On a 200-product grid that's the difference between 1 and 200 renders per click.

Version 5 has a trap older tutorials don't warn about. Its hook calls React's useSyncExternalStore directly, and React requires the snapshot to stay the same between calls if the store hasn't changed. A selector that builds a new object, such as (s) => ({ count: s.count }), returns a different reference every time, so React believes the store keeps changing. It logs The result of getSnapshot should be cached and then throws Maximum update depth exceeded. Wrap the selector in useShallow, or simply select each primitive separately.

The store also lives outside the component tree: getState() reads the current value without subscribing, subscribe() listens from anywhere, and actions can be called from a 401 handler or a socket callback. Because the React binding is about ten lines on top of useSyncExternalStore (lesson 19 explains that hook and tearing), you can read it in full.

The server is where a module-level store hurts. That store is one object per process, so concurrent requests share it. The run below shows what really happens on Zustand 5.0. The hook's server snapshot is getInitialState(), so a value set with setState on the server doesn't appear in the HTML at all: the page renders empty. getState() reads the shared current value, so Alice's page shows Bob's email. Both are wrong. The fix is a store per request, created with the data in its initial state and passed down through context (more in lesson 21).

function useStore(api, selector = identity) {
  const slice = React.useSyncExternalStore(
    api.subscribe,
    // ده الـ snapshot: لو رجع reference جديد كل مرة، React يفضل يعيد الـ render
    React.useCallback(() => selector(api.getState()), [api, selector]),
    // ده الـ snapshot بتاع السيرفر والـ hydration: دايمًا الـ initial state
    () => selector(api.getInitialState())
  );
  React.useDebugValue(slice);
  return slice;
}

Zustand بيديك store بره React، فيه الـ state والـ actions مع بعض، وhook بيشترك عن طريق selector. مفيش provider. الـ component بيعمل re-render بس لما نتيجة الـ selector تتغير بـ Object.is، فـ useCart((s) => s.qty[sku]) بتخلي الكارت مهتم بالكمية بتاعته هو بس. أما useCart() من غير selector فبتشترك في الـ state object كله: أي تغيير يعمل re-render. وفي grid فيه 200 منتج، ده الفرق بين 1 و200 render في الدوسة.

النسخة 5 فيها trap الـ tutorials القديمة مش بتحذر منه. الـ hook بينادي useSyncExternalStore بتاع React مباشرة، وReact بيشترط إن الـ snapshot يفضل هو هو بين النداءات لو الـ store متغيرش. الـ selector اللي بيبني object جديد زي (s) => ({ count: s.count }) بيرجّع reference مختلف كل مرة، فReact فاكر إن الـ store بيتغير على طول. فبيطبع The result of getSnapshot should be cached وبعدين يرمي Maximum update depth exceeded. لفّ الـ selector بـ useShallow، أو ببساطة اختار كل قيمة primitive لوحدها.

وكمان الـ store عايش بره شجرة الـ components: getState() بتقرا القيمة الحالية من غير اشتراك، وsubscribe() بتسمع من أي حتة، والـ actions تتنادى من handler بتاع 401 أو callback بتاع socket. ولأن الربط بـ React حوالي 10 سطور فوق useSyncExternalStore (درس 19 بيشرح الـ hook ده والـ tearing)، تقدر تقراه كله.

السيرفر هو المكان اللي الـ store اللي على مستوى الـ module بيوجع فيه. الـ store ده object واحد لكل process، فالـ requests اللي شغالة في نفس الوقت بتشاركه. التشغيل فوق بيوضح اللي بيحصل فعلًا على Zustand 5.0. الـ snapshot بتاع السيرفر في الـ hook هو getInitialState()، فالقيمة اللي اتحطت بـ setState على السيرفر مش بتظهر في الـ HTML خالص، والصفحة بتطلع فاضية. أما getState() فبتقرا القيمة الحالية المشتركة، فصفحة Alice بتعرض إيميل Bob. الاتنين غلط. الحل: store لكل request، بيتعمل والبيانات في الـ initial state بتاعه، وبيتوصل عن طريق context (تفاصيل أكتر في درس 21).

فين هستخدمه في شغلي؟ الـ cart في مشروع Next.js: useCart((s) => s.count) في الـ header، وuseCart((s) => s.qty[sku]) في كل كارت، وuseCart.getState().clear() في الـ handler اللي بيمسك 401 من الـ API عشان يمسح البيانات بعد انتهاء الـ session. وفي الـ code review، أي useCart.getState() جوه component بيتعمل له render على السيرفر أو جوه Server Component علّم عليه فورًا: ده طريق تسريب بيانات بين الـ users. وأي useCart() من غير selector في list كبيرة علّم عليه هو كمان.

Part 4 — Zustand middleware 🟡 Intermediateالجزء 4 — الـ middleware في Zustand

English

persist writes state to storage (localStorage by default) and restores it on load. Three options keep it safe in production. partialize is an allow-list of what gets written, so UI flags and functions stay out. version stamps the stored shape. migrate upgrades older shapes when the stored version differs. If you bump the version without a migrate, the stored value is ignored and a console.error is logged. The default merge is shallow, so a nested object you later extend loses its new defaults: { settings: { currency } } replaces all of settings. Write a custom merge for nested shapes.

Three things break. Secrets: storage is readable by any script on your origin, so one XSS exposes it. Never persist tokens or personal data (see JS lesson 14). Two tabs: each tab holds its own copy in memory and the last writer wins. Tab A adds 3 items, tab B still shows 0, adds 1 and overwrites storage with a count of 1. Listen for the storage event and call persist.rehydrate(). SSR: the server has no localStorage, so its HTML shows the empty cart.

On that last one, the usual warning needs updating. On Zustand 5.0, reading through the hook does not cause a hydration mismatch, because the hook's server snapshot is the pre-storage initial state: hydration sees 0 like the server did, and then React re-renders with 3. What remains is a visible flash from 0 to 3. A mismatch still occurs if a component reads getState() during render. skipHydration: true plus a manual persist.rehydrate() in an effect gives you control over when storage is read, so you can show a skeleton instead of a wrong number.

devtools connects to the Redux DevTools extension and logs each set under the name in its third argument. Turn it off in production. immer lets you write mutations on a draft and needs the immer package installed. The docs recommend applying devtools last, which makes it the outermost: devtools(persist(immer(...))). I ran all six orders on Zustand 5.0.16, and action names, draft updates, storage writes and outside setState calls behaved the same in every order. The only visible difference: with devtools outside persist, the hydration write shows up in the log. Keep the documented order, but know it isn't a bug if you find another one in old code.

Part 5 — Jotai 3 🟡 Intermediateالجزء 5 — Jotai 3

English

Zustand starts from one store and slices it top-down. Jotai goes the other way: you declare small atoms and compose them bottom-up. An atom is a config object, with the value held in a store. A derived atom is a function that calls get(otherAtom), and each get registers a dependency automatically. There's no dependency array to maintain, and when a dependency changes only the atoms and components that depend on it update.

The invoice editor below has 1,000 lines. With context, the whole array is one value, so editing a cell re-renders all 1,000 rows, and memo can't help. With one atom per line, the same edit re-renders 1 row and the total, and the derived total recomputes once. Typing in an unrelated note atom recomputes nothing. The Zustand version gets the same 1 row re-render through selectors, but each update has to run all 1,000 selectors to discover that (1,002 selector runs in the run below). Selectors are cheap, so that's rarely a problem by itself. What atoms really offer is a dependency graph you don't manage by hand.

Jotai 3.0 (September 2026) changed things you'll see in older articles. It's ESM only. atomFamily moved from jotai/utils to the jotai-family package. loadable was removed in favor of unwrap. The setSelf option of an atom's read function is gone, and so is the delay option of useAtom. A family keeps every atom it has created, so call remove(id) when a line is deleted or it becomes a memory leak.

Without a Provider, hooks use a default store that's one per process, so the server leak from Part 3 applies here too, and it's worse: Jotai's hook reads the current value on the server. Use createStore() and a Provider per request.

بالعامية

Zustand بيبدأ من store واحد ويقطّعه من فوق لتحت. Jotai بيمشي بالعكس: بتعرّف atoms صغيرة وتركّبها من تحت لفوق. الـ atom هو config object، والقيمة نفسها متخزنة في store. والـ atom المشتق هو function بتنادي get(otherAtom)، وكل get بتسجّل dependency لوحدها. مفيش dependency array تحافظ عليها، ولما dependency تتغير، الـ atoms والـ components اللي معتمدين عليها بس هم اللي بيتحدثوا.

محرر الفواتير فوق فيه 1,000 سطر. مع context، الـ array كلها value واحد، فتعديل خلية بيعمل re-render لكل الـ 1,000 row، وmemo مش هينفع. مع atom لكل سطر، نفس التعديل بيعمل re-render لـ row واحدة والـ total، والـ total المشتق بيتحسب مرة واحدة. والكتابة في note atom ملوش علاقة مش بتحسب حاجة خالص. نسخة Zustand بتوصل لنفس الـ row الواحدة عن طريق selectors، بس كل update لازم يشغّل الـ 1,000 selector عشان يكتشف ده (1,002 نداء selector في التشغيل فوق). الـ selectors رخيصة، فده نادرًا ما يبقى مشكلة لوحده. الميزة الحقيقية في الـ atoms هي dependency graph مش بتديره بإيدك.

Jotai 3.0 (سبتمبر 2026) غيّر حاجات هتشوفها في المقالات القديمة. بقى ESM بس. atomFamily اتنقل من jotai/utils لـ package اسمه jotai-family. loadable اتشال وبدله unwrap. الـ option اللي اسمه setSelf في الـ read function بتاعة الـ atom اتشال، وكمان الـ option اللي اسمه delay في useAtom. والـ family بتحتفظ بكل atom عملته، فنادي remove(id) لما سطر يتمسح وإلا هتبقى memory leak.

من غير Provider، الـ hooks بتستخدم default store واحد لكل process، فتسريب السيرفر من الجزء 3 موجود هنا كمان، وهنا أوحش: الـ hook بتاع Jotai بيقرا القيمة الحالية على السيرفر. استخدم createStore() وProvider لكل request.

فين هستخدمه في شغلي؟ شاشة زي spreadsheet: محرر فاتورة، pricing rules، dashboard builder، بحيث كل خلية مستقلة وفيه قيم مشتقة بتعتمد على خلايا تانية. Jotai بيديك graph الاعتماديات ده من غير ما تكتب selectors. لكن cart عادي فيه 5 حقول، Zustand أبسط ومفيش سبب للـ atoms. ولو بتطلّع مقال قديم فيه import { atomFamily } from "jotai/utils"، هتعرف إنه قبل v3 وتظبط الـ import.

Part 6 — Redux Toolkit and the final decision 🟡 Intermediateالجزء 6 — Redux Toolkit والقرار النهائي

English

Classic Redux was hated mostly for its boilerplate: action type constants, action creators, hand-written spreading in switch statements. Redux Toolkit is the official answer. createSlice generates the reducer and actions together. Immer lets reducers look like mutations. configureStore sets up thunk and DevTools and adds dev-only checks, for example a warning when a non-serializable value goes through an action. RTK Query adds a server-state cache with deduplication, like TanStack Query: three simultaneous requests in the run below produce one HTTP call.

What makes Redux different from the others is the event log. State only changes through plain, serializable action objects going through pure reducers, so you can log every action, attach the log to a bug report, and replay it to any point in time. That's what "time travel" in DevTools means, and it's a real feature when your product needs undo, audit trails or reproducible bug reports. You pay for it in ceremony and bytes. For the same cart below, Redux Toolkit adds about 23 KB to the production bundle against under 1 KB for Zustand and about 7 KB for Jotai.

Why it's now an uncommon default for new projects: years ago the Redux store was mostly a hand-written cache of API responses. TanStack Query took that job (lesson 10), and what stayed behind is often a few UI flags that don't justify the setup. It's still the right call in an existing Redux app, when several teams benefit from one strict pattern, and when the event log itself is the feature. You'll also read plenty of it in legacy code, so learn the older vocabulary: connect still works on React 19.3 and react-redux 9. The one classic performance bug in that code is a selector that builds a new array, which re-renders on every action in the whole app. createSelector fixes it.

الصف الأول: connect غلاف بيحقن الـ state والـ actions كـ props، والنهارده useSelector وuseDispatch. التاني: switch وثوابت زي ADD_ITEM يعني reducers مكتوبة بالإيد، والنهارده createSlice. التالت: createStore وcombineReducers إعداد يدوي (وcreateStore متعلّم عليه deprecated)، والنهارده configureStore. الرابع: thunks أو sagas بتجيب بيانات API وتخزنها، ده cache مكتوب بالإيد، والنهارده TanStack Query أو RTK Query. الخامس: createSelector لسه صح، سيبه زي ما هو.
بالعامية

الناس كانت بتكره Redux القديم أساسًا عشان الـ boilerplate: ثوابت للـ action types، وaction creators، وspread بالإيد جوه switch. Redux Toolkit هو الرد الرسمي. createSlice بيطلّع الـ reducer والـ actions مع بعض. Immer بيخلي الـ reducers شكلها mutations. configureStore بيظبط thunk وDevTools ويضيف checks في dev بس، زي التحذير لما قيمة مش serializable تعدّي في action. وRTK Query بيضيف cache للـ server state فيه dedup زي TanStack Query: 3 requests في نفس اللحظة في التشغيل فوق طلّعوا HTTP call واحد.

اللي بيميّز Redux عن الباقي هو الـ event log. الـ state مش بيتغير غير عن طريق action objects عادية وserializable بتعدّي على reducers pure، فتقدر تسجّل كل action، وتلزق الـ log في bug report، وتعيد تشغيله لأي لحظة. ده معنى "time travel" في DevTools، وهي ميزة حقيقية لما المنتج محتاج undo أو audit trail أو bug reports تتعاد بالظبط. وبتدفع تمنها كلام كتير وbytes. لنفس الـ cart فوق، Redux Toolkit بيزوّد حوالي 23 KB على الـ production bundle، مقابل أقل من 1 KB لـ Zustand وحوالي 7 KB لـ Jotai.

ليه بقى default مش شائع في المشاريع الجديدة: زمان الـ Redux store كان في الأغلب cache مكتوب بالإيد لردود الـ API. TanStack Query أخد الشغلانة دي (درس 10)، واللي فضل غالبًا شوية UI flags ميستاهلوش الإعداد ده. بس لسه هو القرار الصح في app شغال بـ Redux أصلًا، ولما كذا فريق يستفيدوا من pattern واحد صارم، ولما الـ event log نفسه هو الميزة. وهتقرا منه كتير في الكود القديم، فاتعلم مفرداته: connect لسه شغال على React 19.3 وreact-redux 9. والـ performance bug الكلاسيكي في الكود ده هو selector بيبني array جديدة، فبيعمل re-render مع كل action في الـ app كله، وcreateSelector بيصلّحه.

فين هستخدمه في شغلي؟ اتعينت في شركة عندها app بـ Redux عمره 6 سنين، أول خطوة مش rewrite. افتح DevTools وشوف نسبة الـ store اللي هي ردود API، وانقلها واحدة واحدة لـ TanStack Query. وبعدها الـ store هيبقى صغير، وساعتها تقرر. أما في editor فيه undo/redo وcollaboration، الـ event log هيوفر عليك كتير، وRTK هنا قرار معقول حتى في مشروع جديد.
Interview question "Would you pick Redux Toolkit, Zustand or Jotai for a new dashboard?" → Start by removing what isn't client state: API data goes to TanStack Query, filters to the URL, drafts to the form. If what's left is a small object read across the app, I'd pick Zustand: under 1 KB, no provider, selectors. If it's many independent cells with derived values, Jotai. I'd pick Redux Toolkit if we need the event log for undo or audit, or we already run on Redux and several teams share its conventions.
"هتختار Redux Toolkit ولا Zustand ولا Jotai لـ dashboard جديد؟" ← ابدأ بإنك تشيل اللي مش client state: بيانات الـ API لـ TanStack Query، والـ filters للـ URL، والـ drafts للـ form. لو اللي فاضل object صغير بيتقرا في الـ app كله، هختار Zustand: أقل من 1 KB ومن غير provider وبـ selectors. لو خلايا كتير مستقلة وفيها قيم مشتقة، Jotai. وهختار Redux Toolkit لو محتاجين الـ event log عشان undo أو audit، أو لو شغالين على Redux أصلًا وكذا فريق ماشيين على نفس الـ conventions.

الجدول النهائي، صف صف:

  • component واحد أو subtree صغيرة: useState أو useReducer، أرخص حاجة وبيموت مع الـ component.
  • اتنين siblings بيشاركوا قيمة: ارفعها لأقرب ancestor مشترك، مالك واحد ومن غير library.
  • prop بيعدّي من layers بس: composition بالـ children، بيشيل الـ drilling والـ re-renders كمان.
  • نادرًا ما بيتغير وبيتقرا في كل حتة (theme، auth، locale، tenant، flags): context، dependency injection وtest doubles سهلة.
  • صغير وبيتغير كتير وبيتقرا في الـ app كله (cart، drawer، wizard): Zustand، selectors ومن غير provider وأقل من 1 KB.
  • خلايا كتير مستقلة وفيها قيم مشتقة: Jotai، graph اعتماديات أوتوماتيك.
  • محتاج event log أو الكود أصلًا Redux: Redux Toolkit، replay وaudit وpattern واحد صارم.
  • بيانات من الـ API: TanStack Query، ده cache مش state.
  • filters وpagination وviews بتتشارك: الـ URL، زرار back والروابط بتشتغل.
  • draft قبل الـ submit: React Hook Form، local وعمره قصير.

Common mistakes · غلطات شائعة

❌ Subscribing to the whole store 
function ProductCard({ sku }: { sku: string }) {
  // ده اشتراك في كل حاجة: 200 re-render في الدوسة
  const cart = useCart();
  return <button onClick={() => cart.add(sku)}>{cart.qty[sku] ?? 0}</button>;
}
✅ Select only what you read 
function ProductCard({ sku }: { sku: string }) {
  // كل كارت مهتم برقمه هو: re-render واحد في الدوسة
  const qty = useCart((s) => s.qty[sku] ?? 0);
  const add = useCart((s) => s.add);
  return <button onClick={() => add(sku)}>{qty}</button>;
}
بالعامية

❌ useCart() من غير selector بيشترك في الـ state كله، فأي تغيير في أي منتج بيعيد رسم كل الكروت: 200 render في التشغيل بتاعنا. ✅ selector للقيمة اللي بتقراها بس وselector للـ action، فالكارت اللي اتغير هو بس اللي بيتحرك: render واحد.

❌ A selector that builds an object in v5 
// ✗ Maximum update depth exceeded
const { count, totalCents } = useCart((s) => ({
  count: s.count,
  totalCents: s.totalCents,
}));
✅ useShallow, or two selectors 
const { count, totalCents } = useCart(
  useShallow((s) => ({ count: s.count, totalCents: s.totalCents })),
);
// أو الأبسط: selector لكل قيمة primitive
const count2 = useCart((s) => s.count);
بالعامية

❌ الـ object جديد مع كل نداء، فالـ snapshot عمره ما بيثبت والـ component بيقع بالـ error ده. الكود ده كان شغال في v4 عشان كده بيظهر بعد الـ upgrade. ✅ useShallow بيقارن الـ keys ويرجّع نفس الـ object لو متغيرتش، أو selector منفصل لكل قيمة، وده غالبًا الأبسط.

❌ High-frequency state in context 
// ده بيعمل re-render لكل consumer مع كل حرف
const value = useMemo(
  () => ({ note, setNote, lines, addLine }),
  [note, lines],
);
return <CartContext value={value}>{children}</CartContext>;
✅ Local state, and only stable things in context 
// الـ note بقى local جوه الـ input بتاعه
function NoteInput() {
  const [note, setNote] = useState("");
  return <input value={note} onChange={(e) => setNote(e.target.value)} />;
}
// والـ context فيه action ثابت بس
return <AddLineContext value={addLine}>{children}</AddLineContext>;
بالعامية

❌ useMemo بيدّيك إحساس بالأمان، بس الـ note في الـ deps، فالـ value بيتغير مع كل حرف و500 كارت بيتعاد رسمهم. ✅ الـ state المتغير بسرعة يفضل local، والـ context ميشيلش غير حاجة ثابتة: 0 كروت لكل حرف.

❌ Copying server data into a store 
const useOrders = create<OrdersState>()((set) => ({
  orders: [],
  loading: false,
  error: null,
  // انت كده بتعيد كتابة cache بإيدك
  fetchOrders: async () => {
    set({ loading: true });
    const res = await fetch("/api/orders");
    set({ orders: await res.json(), loading: false });
  },
}));
✅ Server state in a query library 
// الـ cache والـ dedup والـ retry جاهزين
const { data } = useQuery({
  queryKey: ["orders"],
  queryFn: async () =>
    (await (await fetch("/api/orders")).json()) as Order[],
});
بالعامية

❌ الـ store هنا شايل نسخة من بيانات السيرفر، فهتكتب بإيدك الـ loading والـ error والـ dedup والـ refetch والـ invalidation، ولسه البيانات هتبقى قديمة. ✅ useQuery بيعمل كل ده (درس 10)، والـ store يفضل للحاجات اللي ملهاش مصدر غير المتصفح.

❌ One store shared by all requests 
// واحد للـ process كله
export const useSession = create<SessionState>()(sessionSlice);

// جوه الـ request handler
useSession.getState().setEmail(user.email);
await loadPageData();

render(useSession.getState().email);
✅ A store per request

  createStore<SessionState>()((set) => ({
    email,
    setEmail: (next) => set({ email: next }),

// وبيتوصل عن طريق context
<SessionContext value={store}>{children}</SessionContext>

❌ الـ process واحد بيخدم كل الـ users، فأي await في النص بيدّي فرصة لـ request تاني يكتب في نفس الـ store، وAlice تشوف إيميل Bob: تسريب بيانات حقيقي اتشغل فوق في الجزء 3. ✅ store جديد لكل request، والبيانات في الـ initial state عشان الـ hook يشوفها على السيرفر، وبيتوصل بـ context.

Solution · الحل 
import { createStore } from "zustand/vanilla";
import { createJSONStorage, persist, type StateStorage } from "zustand/middleware";

interface WishlistState {
  skus: string[];
  panelOpen: boolean;
  toggle: (sku: string) => void;
}

const saved = new Map<string, string>();
const memory: StateStorage = {
  getItem: (k) => saved.get(k) ?? null,
  setItem: (k, v) => void saved.set(k, v),
  removeItem: (k) => void saved.delete(k),
};

// الـ user القديم عنده version 0 وشكلها ⁦{ ids: [...] }⁩
saved.set("wishlist", JSON.stringify({ state: { ids: ["KB-1", "MS-2"] }, version: 0 }));

const wishlist = createStore<WishlistState>()(
  persist(
    (set) => ({
      skus: [],
      panelOpen: false,
      toggle: (sku) =>
        set((s) => ({
          skus: s.skus.includes(sku) ? s.skus.filter((x) => x !== sku) : [...s.skus, sku],
        })),
    }),
    {
      name: "wishlist",
      version: 1,
      storage: createJSONStorage(() => memory),
      // قايمة allow-list: اللي مش مكتوب هنا مش بيتخزن
      partialize: (s) => ({ skus: s.skus }),
      migrate: (stored, from) =>
        from === 0 ? { skus: (stored as { ids: string[] }).ids } : (stored as { skus: string[] }),
    },
  ),
);

console.log(wishlist.getState().skus);
wishlist.getState().toggle("KB-1");
console.log(saved.get("wishlist"));

import { memo } from "react";
import { createRoot } from "react-dom/client";
import { create } from "zustand";

interface Line { id: string; qty: number; unitCents: number }
interface InvoiceState {
  lines: Record<string, Line>;
  setQty: (id: string, qty: number) => void;
}

const stats = { rows: 0, totals: 0, selectorRuns: 0 };
const ids = Array.from({ length: 1000 }, (_, i) => `line_${i}`);

const useInvoice = create<InvoiceState>()((set) => ({
  lines: Object.fromEntries(ids.map((id, i) => [id, { id, qty: 1, unitCents: 1000 + i }])),
  setQty: (id, qty) =>
    set((s) => ({ lines: { ...s.lines, [id]: { ...s.lines[id], qty } } })),
}));

const LineRow = memo(function LineRow({ id }: { id: string }) {
  stats.rows++;
  // كل row عندها selector: كل تعديل بيشغّل الـ 1000 selector عشان يقارنوا
  const qty = useInvoice((s) => {
    stats.selectorRuns++;
    return s.lines[id].qty;
  });
  const setQty = useInvoice((s) => s.setQty);
  return <input aria-label={id} value={qty} onChange={(e) => setQty(id, Number(e.target.value))} />;
});

function Total() {
  stats.totals++;
  const total = useInvoice((s) =>
    Object.values(s.lines).reduce((sum, l) => sum + l.qty * l.unitCents, 0),
  );
  return <output>{total}</output>;
}

createRoot(document.getElementById("root")!).render(
  <>
    <Total />
    {ids.map((id) => <LineRow key={id} id={id} />)}
  </>,
);
// عشان Playwright يقرا العدّادات من الصفحة
Object.assign(window, { stats });

Cheat sheet · الخلاصة

  • Ladder: local → lift to closest common ancestor → composition → context → store. Climb only when the rung fails.
  • Lifted too high: 2,000 row renders per key. Push down or pass as children: 0.
  • Derive, don't duplicate. A useEffect that syncs state costs an extra render and a wrong commit.
  • Context: rarely changes, read widely. createContext<T | null>(null) plus a hook that throws. Best use is dependency injection and test doubles.
  • memo doesn't stop context. A changing value re-renders every consumer.
  • Zustand: useCart((s) => s.count) re-renders 1 card; useCart() re-renders all 200.
  • v5 trap: a selector returning a new object throws Maximum update depth exceeded. Use useShallow or primitive selectors.
  • Server: the Zustand hook reads getInitialState(), getState() leaks between users, and Jotai without a Provider leaks through the hook too. Use one store per request.
  • persist: partialize as an allow-list, version and migrate from day one, custom merge for nested shapes, sync tabs with the storage event, no secrets.
  • SSR plus persist on 5.0: the hook gives a flash, not a mismatch; getState() in render gives a mismatch; skipHydration gives you control.
  • Jotai 3: atoms with auto-tracked deps. ESM only, atomFamily in jotai-family, unwrap instead of loadable, no setSelf, no delay.
  • Added bundle size for the same cart: Zustand 0.7 KB, Jotai 7.2 KB, RTK 23.4 KB. Choose RTK for the event log or an existing Redux app.
بالعامية
  • السلّم: local ← ارفع لأقرب ancestor مشترك ← composition ← context ← store. متطلعش درجة غير لما اللي قبلها تفشل.
  • رفع زيادة: 2,000 render للـ rows مع كل حرف. نزّله أو عدّيه كـ children: صفر.
  • اشتق متكررش. الـ useEffect اللي بيزامن state بيكلفك render زيادة وcommit غلط.
  • الـ context: بيتغير نادرًا وبيتقرا في كل حتة. createContext<T | null>(null) مع hook بيرمي error. وأحسن استخدام ليه dependency injection والـ test doubles.
  • memo مش بيوقف الـ context. أي تغيير في الـ value بيعمل re-render لكل consumer.
  • Zustand: useCart((s) => s.count) بيحرّك كارت واحد، وuseCart() بيحرّك الـ 200.
  • trap بتاع v5: selector بيرجّع object جديد بيرمي Maximum update depth exceeded. استخدم useShallow أو selectors لقيم primitive.
  • السيرفر: الـ hook بتاع Zustand بيقرا getInitialState()، وgetState() بتسرّب بين الـ users، وJotai من غير Provider بيسرّب عن طريق الـ hook كمان. استخدم store لكل request.
