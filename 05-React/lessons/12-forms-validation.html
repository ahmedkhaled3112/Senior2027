Why this matters · ليه ده مهم

English

Forms are where your frontend and your API actually meet. As a full-stack developer you own both ends, and most form bugs come from the seam between them: a validation rule that exists on one side only, a 422 that turns into a useless toast, a draft that leaks from one invoice into another, a price that's a string in the form and an integer in the database.

The goal of this lesson is one schema that drives both the form and the route, plus a form that stays out of React's way while people type and shows server errors on the exact field they belong to. Every render count, compiler message and error text below was copied from a real run in Chrome 156, Vitest 5 or TypeScript 7. Timings come from a loaded Windows machine, so they're marked ≈.

بالعامية

الـ forms هي المكان اللي الـ frontend والـ API بتاعك بيتقابلوا فيه فعلًا. وإنت كـ full-stack ماسك الناحيتين، وأغلب bugs الـ forms طالعة من الوصلة اللي بينهم: قاعدة validation موجودة في ناحية واحدة بس، أو 422 بتتحول لـ toast ملوش لازمة، أو draft بيتسرّب من فاتورة لفاتورة تانية، أو سعر هو string في الفورم وinteger في الـ database.

هدف الدرس: schema واحد بيشغّل الفورم والـ route مع بعض، وفورم مش بيضايق React وقت الكتابة، وبيعرض أخطاء السيرفر على الـ field الصح بالظبط. كل رقم render ورسالة compiler ونص error تحت متنسخ من تشغيل حقيقي على Chrome 156 أو Vitest 5 أو TypeScript 7. والأزمنة من جهاز Windows عليه ضغط، فمعلّم عليها بـ ≈.

Part 1 — Form state is its own kind of state 🟡 Intermediateالجزء 1 — الـ form state نوع لوحده من الـ state

English

A form holds more than values. It also tracks which fields are dirty (changed from their defaults), which are touched (blurred at least once), the current errors, and whether a submit is in flight. All of that is short-lived and local. It exists from the moment the form opens until it's submitted or abandoned, and nothing outside the form should depend on half-typed text.

That's why it doesn't belong in the other two places people try. In a global store, nothing ties a draft to the invoice it was typed for, so it follows the user to the next invoice. The run below shows exactly that. In the query cache, the draft is mixed with server data: every other reader of that key sees unsaved text, and a background refetch can overwrite what the user is typing.

The form's lifetime should match the thing being edited. A React Hook Form instance inside the editor dies with it, but there's a second trap: defaultValues are read once. Without a key, switching invoices reuses the same instance and keeps the old text, which is the same bug as the store. Give the editor key={invoice.id}, which means "a different invoice is a different form". Or use the values option, which resets the form when the prop changes. With values and TanStack Query, a background refetch would overwrite what the user is typing, so add resetOptions: { keepDirtyValues: true }.

  What is this value?                               Where it lives
  ------------------------------------------------------------------------
  Came from the API, others can change it      ->   SERVER state  (TanStack Query)
  A pasted link should restore it              ->   URL state     (router, search params)
  Half-typed, not saved yet                    ->   FORM state    (React Hook Form)
  Only this browser cares (cart, open drawer)  ->   CLIENT state  (useState, Zustand)

  Editing an invoice:   SERVER --defaults--> FORM --submit--> SERVER --invalidate--> refetch
الخريطة بتسأل سؤال عن كل قيمة. جاية من الـ API وناس تانية تقدر تغيّرها: server state في TanStack Query. اللينك لما يتبعت لازم يرجّعها: URL state في الـ router. مكتوبة نص كتابة ولسه متحفظتش: form state في React Hook Form. والمتصفح ده بس اللي يهمه (cart، drawer مفتوح): client state في useState أو Zustand. وآخر سطر رحلة تعديل الفاتورة: من السيرفر للفورم كـ defaults، ومن الفورم للسيرفر بالـ submit، وبعدها invalidate وrefetch.
import { useState } from "react";
import { createRoot } from "react-dom/client";
import { useForm } from "react-hook-form";
import { create } from "zustand";

interface Invoice { id: string; note: string }
const invoices: Invoice[] = [
  { id: "INV-1", note: "Net 30" },
  { id: "INV-2", note: "Paid upfront" },
];

// ❌ الـ draft في store عام: مفيش حاجة بتربطه بالـ invoice اللي مفتوحة
const useDraft = create<{ note: string | null; setNote: (note: string) => void }>()((set) => ({
  note: null,
  setNote: (note) => set({ note }),
}));

function GlobalDraftEditor({ invoice }: { invoice: Invoice }) {
  const note = useDraft((s) => s.note);
  const setNote = useDraft((s) => s.setNote);
  return <input aria-label="note" value={note ?? invoice.note} onChange={(e) => setNote(e.target.value)} />;
}

// ✅ الـ form state عايش جوه الـ editor، وبيموت معاه
function LocalFormEditor({ invoice }: { invoice: Invoice }) {
  const { register } = useForm({ defaultValues: { note: invoice.note } });
  return <input aria-label="note" {...register("note")} />;
}

// الـ values بيتابع الـ prop: أي تغيير في الـ invoice بيعمل reset للفورم
function ValuesEditor({ invoice }: { invoice: Invoice }) {
  const { register } = useForm({ values: { note: invoice.note } });
  return <input aria-label="note" {...register("note")} />;
}

const variant = new URLSearchParams(location.search).get("v") ?? "global";

function App() {
  const [current, setCurrent] = useState(invoices[0]);
  return (
    <>
      {invoices.map((inv) => (
        <button key={inv.id} id={inv.id} onClick={() => setCurrent(inv)}>{inv.id}</button>
      ))}
      {variant === "global" && <GlobalDraftEditor invoice={current} />}
      {variant === "nokey" && <LocalFormEditor invoice={current} />}
      {variant === "key" && <LocalFormEditor key={current.id} invoice={current} />}
      {variant === "values" && <ValuesEditor invoice={current} />}
    </>
  );
}

createRoot(document.getElementById("root")!).render(<App />);

بالعامية

الفورم شايل أكتر من القيم. شايل كمان الـ fields اللي بقت dirty (اتغيرت عن الـ defaults)، واللي بقت touched (حصل لها blur مرة على الأقل)، والأخطاء الحالية، وهل فيه submit شغال دلوقتي. كل ده عمره قصير وlocal. موجود من لحظة ما الفورم يتفتح لحد ما يتبعت أو يتساب، ومفيش حاجة بره الفورم المفروض تعتمد على كلام نص مكتوب.

وعشان كده مكانه مش في المكانين اللي الناس بتجربهم. في store عام، مفيش حاجة بتربط الـ draft بالفاتورة اللي اتكتب عشانها، فبيمشي ورا المستخدم للفاتورة اللي بعدها، والتشغيل فوق بيوضح ده بالظبط. وفي الـ query cache، الـ draft بيتخلط ببيانات السيرفر: أي حد تاني بيقرا نفس الـ key هيشوف كلام متحفظش، وأي background refetch ممكن يمسح اللي المستخدم بيكتبه.

عمر الفورم لازم يطابق الحاجة اللي بتتعدل. الـ instance بتاع React Hook Form جوه الـ editor بيموت معاه، بس فيه trap تاني: الـ defaultValues بتتقرا مرة واحدة. من غير key، التنقل بين الفواتير بيستخدم نفس الـ instance ويفضل الكلام القديم، وده نفس bug الـ store. ادّي الـ editor key={invoice.id}، ومعناها "فاتورة مختلفة يعني فورم مختلف". أو استخدم option اسمه values، بيعمل reset للفورم لما الـ prop يتغير. ومع values وTanStack Query، الـ background refetch هيمسح اللي المستخدم بيكتبه، فزوّد resetOptions: { keepDirtyValues: true }.

فين هستخدمه في شغلي؟ صفحة /invoices/:id/edit في Next.js: useQuery بيجيب الفاتورة، وبعدين <InvoiceEditor key={invoice.id} invoice={invoice} />. وفي الـ code review، أي store فيه draft من غير ما يكون متخزن بـ id علّم عليه. ده نفس الـ bug اللي ممكن يخلي خصم عميل يتحفظ على فاتورة عميل تاني، وده incident حقيقي مش مشكلة شكل.
Trade-off: when a draft must survive navigation key drops the draft when the user leaves, as the run shows. If your product wants drafts to survive, make that an explicit feature: keep them in sessionStorage or a store keyed by invoice id, restore them on mount, and delete them on successful submit. Then decide what happens when the server copy changed in the meantime.
key بيرمي الـ draft لما المستخدم يمشي، زي ما التشغيل بيوضح. لو المنتج عايز الـ drafts تفضل، خليها ميزة صريحة: خزّنها في sessionStorage أو store متخزن بـ id الفاتورة، ورجّعها وقت الـ mount، وامسحها بعد submit ناجح. وساعتها لازم تقرر هيحصل إيه لو نسخة السيرفر اتغيرت في الوقت ده.

Part 2 — Controlled forms under load 🟡 Intermediateالجزء 2 — الـ controlled forms تحت الضغط

English

In a controlled form, React state is the source of truth, so every keystroke goes through setState and re-renders whatever owns that state. If one useState at the top holds all 50 fields of an invoice, each key re-renders the form and all 50 fields. I typed 24 characters with Playwright into four versions of the same form and recorded render counts and Profiler time. (The counters are measuring tools. Don't ship a module variable that changes during render.)

Be careful what you conclude. With bare inputs in a production build on a fast machine, 50 fields cost only about 0.7 ms per key. That won't hurt anyone, and "controlled forms are slow" isn't true on its own. Three things multiply that cost: slow devices (about 8.5 ms with a 6× CPU throttle), expensive fields (formatters and design-system wrappers), and validating the whole form on every key. Adding an Intl.NumberFormat per field and a schema parse per key took it to about 28–96 ms per key at 6× across two runs, with some events taking 112–480 ms from input to next paint. Interaction to Next Paint (INP) counts as good up to 200 ms, and lesson 24 covers it properly.

The partial fixes form a ladder. memo with a stable onChange cuts field renders to 1 per key, but the parent still runs and you must keep every prop stable. Field-level state stops the form re-rendering at all, but now you have to collect the values yourself. Uncontrolled inputs bring it to zero: the DOM holds the value, and you read it once at submit. That last step is what React Hook Form is built on.

import { Profiler, memo, useCallback, useState, type ChangeEvent, type FormEvent } from "react";
import { createRoot } from "react-dom/client";

const stats = { form: 0, fields: 0, commitMs: 0, commits: 0, submitted: 0 };

// فورم فاتورة فيه 50 field: 5 بيانات عامة و 15 سطر ⁦× 3⁩ أعمدة
const fieldNames = [
  "customerName", "customerEmail", "issueDate", "dueDate", "notes",
  ...Array.from({ length: 15 }, (_, i) => [`line${i}.desc`, `line${i}.qty`, `line${i}.price`]).flat(),
];
const initial = Object.fromEntries(fieldNames.map((n) => [n, ""]));

interface FieldProps {
  name: string;
  value: string;
  onChange: (name: string, value: string) => void;
}

// الـ field العادي: label و input و hint، زي أي design system
function Field({ name, value, onChange }: FieldProps) {
  stats.fields++;
  return (
    <div className="field">
      <label htmlFor={name}>{name}</label>
      <input id={name} value={value} onChange={(e) => onChange(name, e.target.value)} />
      <small>{value.length}/120</small>
    </div>
  );
}

// ⁦(1) ❌⁩ النسخة controlled: كل الـ state فوق، وكل حرف بيعيد الـ 50 field
function ControlledForm() {
  stats.form++;
  const [values, setValues] = useState(initial);
  return (
    <form>
      {fieldNames.map((name) => (
        <Field
          key={name}
          name={name}
          value={values[name]}
          onChange={(n, v) => setValues((prev) => ({ ...prev, [n]: v }))}
        />
      ))}
    </form>
  );
}

// (2) 🟡 نفس الكلام بـ memo و onChange ثابت: الـ fields بتقف، بس الـ parent لسه بيتنفذ
const MemoField = memo(Field);
function MemoForm() {
  stats.form++;
  const [values, setValues] = useState(initial);
  const onChange = useCallback(
    (n: string, v: string) => setValues((prev) => ({ ...prev, [n]: v })),
    [],
  );
  return (
    <form>
      {fieldNames.map((name) => (
        <MemoField key={name} name={name} value={values[name]} onChange={onChange} />
      ))}
    </form>
  );
}

// (3) 🟡 الـ state على مستوى الـ field: الـ form نفسه مبيتحركش، بس لازم تجمّع القيم بنفسك
function OwnStateField({ name }: { name: string }) {
  stats.fields++;
  const [value, setValue] = useState("");
  return (
    <div className="field">
      <label htmlFor={name}>{name}</label>
      <input id={name} name={name} value={value} onChange={(e: ChangeEvent<HTMLInputElement>) => setValue(e.target.value)} />
      <small>{value.length}/120</small>
    </div>
  );
}
function FieldStateForm() {
  stats.form++;
  return <form>{fieldNames.map((name) => <OwnStateField key={name} name={name} />)}</form>;
}

// ⁦(4) ✅⁩ النسخة uncontrolled: الـ DOM شايل القيمة، وبنقراها مرة واحدة عند الـ submit
function PlainField({ name }: { name: string }) {
  stats.fields++;
  return (
    <div className="field">
      <label htmlFor={name}>{name}</label>
      <input id={name} name={name} defaultValue="" />
    </div>
  );
}
function UncontrolledForm() {
  stats.form++;
  const onSubmit = (e: FormEvent<HTMLFormElement>) => {
    e.preventDefault();
    stats.submitted = Object.keys(Object.fromEntries(new FormData(e.currentTarget))).length;
  };
  return (
    <form onSubmit={onSubmit}>
      {fieldNames.map((name) => <PlainField key={name} name={name} />)}
    </form>
  );
}

const FormSchema = z.object(Object.fromEntries(fieldNames.map((n) => [n, z.string().max(120)])));

function Field({ name, value, onChange }: { name: string; value: string; onChange: (n: string, v: string) => void }) {
  stats.fields++;
  // تنسيق بالعملة جوه الـ render: الـ constructor بتاع Intl غالي
  const formatted = new Intl.NumberFormat("en-EG", { style: "currency", currency: "EGP" }).format(value.length);
  return (
    <div className="field">
      <label htmlFor={name}>{name}</label>
      <input id={name} value={value} onChange={(e) => onChange(name, e.target.value)} />
      <small>{formatted}</small>
    </div>
  );
}

function HeavyForm() {
  stats.form++;
  const [values, setValues] = useState(initial);
  const issues = FormSchema.safeParse(values);
  return (
    <form data-valid={issues.success}>
      {fieldNames.map((name) => (
        <Field key={name} name={name} value={values[name]} onChange={(n, v) => setValues((p) => ({ ...p, [n]: v }))} />
      ))}
    </form>
  );
}

بالعامية

في الـ controlled form، الـ React state هو مصدر الحقيقة، فكل حرف بيعدّي على setState وبيعمل re-render للي ماسك الـ state ده. لو useState واحد فوق شايل الـ 50 field بتوع الفاتورة، كل حرف بيعيد الفورم والـ 50 field. كتبت 24 حرف بـ Playwright في 4 نسخ من نفس الفورم وسجّلت عدد الـ renders ووقت الـ Profiler. (العدّادات أدوات قياس بس، فمتنزّلش متغير module بيتغير وقت الـ render.)

خد بالك من الاستنتاج. بـ inputs عادية في production build على جهاز سريع، الـ 50 field بياخدوا حوالي 0.7ms في الحرف بس. ده مش هيضايق حد، وجملة "الـ controlled forms بطيئة" لوحدها مش صح. فيه 3 حاجات بتضرب التكلفة دي: الأجهزة البطيئة (حوالي 8.5ms مع إبطاء 6 مرات)، والـ fields الغالية (formatters وأغلفة الـ design system)، وvalidation للفورم كله مع كل حرف. لما زوّدنا Intl.NumberFormat لكل field وparse للـ schema مع كل حرف، وصلنا لحوالي 28–96ms في الحرف مع الإبطاء في تشغيلين، وبعض الأحداث خدت 112–480ms من الـ input لحد الـ paint اللي بعده. الـ Interaction to Next Paint (INP) بيعتبر كويس لحد 200ms، ودرس 24 بيشرحه كويس.

الحلول الجزئية زي السلّم. memo مع onChange ثابت بينزّل الـ fields لواحد في الحرف، بس الـ parent لسه بيشتغل ولازم تحافظ على كل prop ثابت. الـ state على مستوى الـ field بيوقف re-render الفورم خالص، بس بقيت مسؤول تجمّع القيم بنفسك. والـ uncontrolled inputs بتوصّلها لصفر: الـ DOM شايل القيمة، وبتقراها مرة واحدة عند الـ submit. والخطوة الأخيرة دي هي اللي React Hook Form مبني عليها.

فين هستخدمه في شغلي؟ الـ support بيقول إن فورم إنشاء الفاتورة "بيهنّج" عند المحاسبين على لابتوبات قديمة. متبدأش بإعادة كتابة: افتح الـ Performance panel واعمل CPU throttle 6× واكتب في field. لو الـ long tasks طويلة، بص الأول على اللي بيتنفذ مع كل حرف: safeParse للفورم كله في الـ render، وnew Intl.NumberFormat جوه كل field. ساعات شيل دول بس بيحل المشكلة، وبعدها تقرر تنتقل لـ React Hook Form.
Trade-off: a small controlled form is fine A login form with 3 fields, or an input whose value drives the UI on every key such as a live search or a character counter, is simpler as controlled state. Don't add a form library to save 0.1 ms. Reach for one when you have many fields, field arrays, dirty tracking or server errors to map.

Part 3 — React Hook Form 🟡 Intermediateالجزء 3 — React Hook Form

English

React Hook Form (7.91 is the current release; 8 is still in beta) keeps inputs uncontrolled and holds form state in refs outside React. register("customerEmail") returns a plain object with four things: name, ref, onChange and onBlur. You spread it on the input. The ref gives the library the DOM node so it can read values and move focus; the two handlers update its internal state without calling setState for each key. handleSubmit(onValid, onInvalid) validates first, then calls one of your callbacks, and focuses the first invalid field by default.

The clever part is formState, whose properties are getters. Reading formState.isDirty during render subscribes that form to changes in isDirty, and to nothing else. In the run below, a form that reads nothing has 0 renders across 24 keystrokes. Reading isDirty costs 1 render, when it flips to true. Reading errors with mode: "onChange" costs 2: when the error appears and when it clears. Because those are getters, read them before you return, and don't spread formState: the properties aren't enumerable, so { ...formState }.isDirty is undefined.

For a live value, watch and useWatch look alike but differ a lot. watch("customerName") re-renders the whole form on every key: 24 form renders and 1,200 field renders in my run. useWatch in a small child re-renders only that child. watch also hurts you with the compiler: the react-hooks/incompatible-library lint warns about it, and React Compiler skips the whole component, as the logs below show (the compiler itself is covered in lesson 23).

mode sets when validation first runs. The default, onSubmit, is usually the kindest. After a submit, reValidateMode (default onChange) takes over, so an error clears as soon as the user fixes it. With a resolver, mode: "onChange" runs your entire schema on every key: 24 parses of a 50-field schema in my run, even though the form didn't re-render.

بالعامية

React Hook Form (الإصدار الحالي 7.91، و8 لسه beta) بيسيب الـ inputs uncontrolled وبيحتفظ بالـ form state في refs بره React. register("customerEmail") بيرجّع object عادي فيه 4 حاجات: name وref وonChange وonBlur، وبتعمله spread على الـ input. الـ ref بيدّي المكتبة الـ DOM node عشان تقرا القيم وتحرّك الـ focus، والـ handlers بيحدّثوا الـ state الداخلي من غير setState مع كل حرف. وhandleSubmit(onValid, onInvalid) بيعمل validate الأول، وبعدين ينادي واحد من الـ callbacks، وبيعمل focus لأول field غلط افتراضيًا.

الحتة الذكية هي formState، خصايصه كلها getters. لما تقرا formState.isDirty وقت الـ render، الفورم بيشترك في تغييرات isDirty بس ومش في أي حاجة تانية. في التشغيل فوق، الفورم اللي مبيقراش حاجة عمل 0 renders في 24 حرف. قراءة isDirty بتكلف render واحد لما تقلب true. وقراءة errors مع mode: "onChange" بتكلف اتنين: لما الغلطة تظهر ولما تختفي. ولأنها getters، اقراها قبل الـ return، ومتعملش spread لـ formState: الخصايص مش enumerable، فـ { ...formState }.isDirty بيطلع undefined.

عشان تقرا قيمة live، watch وuseWatch شكلهم زي بعض بس الفرق كبير. watch("customerName") بيعيد الفورم كله مع كل حرف: 24 render للفورم و1,200 render للـ fields في التشغيل بتاعي. وuseWatch في child صغير بيعيد الـ child ده بس. وكمان watch بيضرك مع الـ compiler: قاعدة react-hooks/incompatible-library بتحذر منه، وReact Compiler بيسيب الـ component كله من غير compile، زي ما الـ logs فوق بتوضح (الـ compiler نفسه في درس 23).

mode بيحدد الـ validation يشتغل إمتى أول مرة. الـ default هو onSubmit، وغالبًا هو الألطف على المستخدم. بعد الـ submit، reValidateMode (الـ default بتاعه onChange) بيمسك الموضوع، فالغلطة بتختفي أول ما المستخدم يصلحها. ومع resolver، mode: "onChange" بينفذ الـ schema كله مع كل حرف: 24 parse لـ schema فيه 50 field في التشغيل بتاعي، حتى لو الفورم معملش re-render.

Interview question "Why doesn't React Hook Form re-render on every keystroke, and what can bring those re-renders back?" → Inputs are uncontrolled: the DOM holds the value and the library reads it through a ref, so typing never calls setState. formState properties are getters that subscribe the form only to what it read. Re-renders come back if you call watch() in the form body, read something from formState that changes on each key, or drive the inputs from your own useState.
"ليه React Hook Form مش بيعمل re-render مع كل حرف، وإيه اللي ممكن يرجّع الـ re-renders؟" ← الـ inputs uncontrolled: الـ DOM شايل القيمة والمكتبة بتقراها عن طريق ref، فالكتابة عمرها ما بتنادي setState. وخصايص formState عبارة عن getters بتشترك الفورم في اللي قراه بس. والـ re-renders بترجع لو ناديت watch() في جسم الفورم، أو قريت حاجة من formState بتتغير مع كل حرف، أو مشّيت الـ inputs من useState بتاعك.

Part 4 — Controller and field arrays 🟡 Intermediateالجزء 4 — الـ Controller والـ field arrays

English

register needs a real input that takes a ref and fires native change events. A Radix Select, a date picker or a rich text editor doesn't. Controller bridges them: its render prop hands you field (value, onChange, onBlur, ref) and fieldState. You map those onto the widget's own props, such as onValueChange. Pass field.ref to something focusable, or focus on error can't reach it.

useFieldArray manages repeating groups like invoice lines, with append, remove, move and more. Its fields items carry a generated id, and that id must be the React key. The result differs from what you might expect, so I ran both. On 7.91, the registered input values come out right even with an index key, because the library writes them back after a change. What shifts is everything else tied to a row's identity: local useState, focus and DOM state. In the run below, removing the first line with an index key moved its open discount panel onto the Mouse line (the React rule behind this is in lesson 01).

A live total goes in its own component with useWatch. At 200 lines (600 inputs) typing cost didn't grow at all: 0 form renders and only the total re-rendered. Adding or removing a line does re-render the form and every row, at about 14 ms and 12 ms in production, and about 98 ms and 217 ms with a 6× CPU throttle. If that becomes a problem, memoize rows with stable props, then consider windowing (lesson 24). Windowing unmounts rows, so test what that does to registered values.

Part 5 — Zod and one shared schema 🟡 Intermediateالجزء 5 — Zod وschema واحد مشترك

English

Put the schema in its own package that imports only Zod, with no React and no Fastify. The form passes it to zodResolver from @hookform/resolvers 7, and the route calls safeParse on the request body (the basics of runtime validation are in TS lesson 08). There's now one definition of "a valid invoice", and error messages stay in sync without any effort.

The part people get wrong is that a schema has two types. z.input is what goes in, and z.output is what comes out after coercions and transforms. A form holds strings while the API wants numbers. In Zod 4, z.coerce.number() has an input type of unknown, and my price transform goes from string to integer cents. So use all three generics on useForm: useForm<z.input<S>, unknown, z.output<S>>. Inputs are then typed by the input type, and handleSubmit receives the output. Writing useForm<z.infer<S>> fails with a real compile error, shown in the mistakes section, because z.infer is the output type.

Rules across fields use refine, with a path so the message lands under the right field. Note when it runs. A refine still runs if the earlier issues are only check failures, such as an empty string or a bad format, but a wrong type stops it, as the output shows. That's why an empty form gets two messages on dueDate. React Hook Form shows only the first, so the user sees Invalid ISO date.

Sharing has limits, and the server always validates again, because anyone can call your API without your form. The schema can't check rules that need the database (is this invoice number taken?), that need the session (may this user do this?), or that depend on the current state of the world (is it in stock?). Those stay in the route. Also watch the bundle cost: React Hook Form added 12.1 KB gzipped and the Zod resolver plus classic Zod added 22.6 KB more in my measurements. Use import * as z from "zod". TS lesson 08 measured import { z } at about 91 KB gzipped with esbuild. On Vite 8 (Rolldown) I got the same 19.2 KB gzipped from both styles, so that penalty depends on your bundler, and the namespace import is safe on both.

الحتة اللي الناس بتغلط فيها إن الـ schema ليه نوعين. z.input هو اللي بيدخل، وz.output هو اللي بيطلع بعد الـ coercions والـ transforms. الفورم ماسك strings والـ API عايز أرقام. في Zod 4، الـ input type بتاع z.coerce.number() هو unknown، والـ transform بتاع السعر بيحوّل من string لقروش integer. فاستخدم الـ 3 generics على useForm: useForm<z.input<S>, unknown, z.output<S>>. كده الـ inputs ليها نوع الـ input، وhandleSubmit بياخد الـ output. ولو كتبت useForm<z.infer<S>> هتاخد compile error حقيقي، موجود في قسم الغلطات، لأن z.infer هو نوع الـ output.

القواعد اللي بين حقلين بتستخدم refine مع path عشان الرسالة تنزل تحت الـ field الصح. وخد بالك هو بيشتغل إمتى. الـ refine بيشتغل حتى لو المشاكل اللي قبله كلها check failures زي string فاضي أو format غلط، بس النوع الغلط بيوقفه، زي ما الـ output بيوضح. وعشان كده الفورم الفاضي بياخد رسالتين على dueDate. وReact Hook Form بيعرض الأولى بس، فالمستخدم بيشوف Invalid ISO date.

المشاركة ليها حدود، والسيرفر دايمًا بيعمل validate تاني، لأن أي حد يقدر ينادي الـ API من غير الفورم بتاعك. الـ schema مش هيقدر يفحص قواعد محتاجة الـ database (رقم الفاتورة ده محجوز؟)، أو محتاجة الـ session (الـ user ده مسموح له؟)، أو معتمدة على حالة الدنيا دلوقتي (لسه في المخزن؟). دول يفضلوا في الـ route. وخد بالك كمان من حجم الـ bundle: React Hook Form زوّد 12.1 KB gzip، والـ resolver مع Zod العادية زوّدوا 22.6 KB كمان في القياس بتاعي. استخدم import * as z from "zod". درس TS 08 قاس import { z } بحوالي 91 KB gzip مع esbuild. وعلى Vite 8 (Rolldown) طلع عندي نفس الـ 19.2 KB gzip للطريقتين، يعني العقوبة دي معتمدة على الـ bundler، والـ namespace import آمن في الاتنين.

فين هستخدمه في شغلي؟ في monorepo بـ npm workspaces أو pnpm: packages/schemas بيستوردوه apps/web وapps/api. لما الـ PM يطلب "الكمية لازم تكون أقل من 10,000"، بتعدل سطر واحد والناحيتين بيتحدثوا مع بعض في نفس الـ PR. وفي الـ code review، لو لقيت tenantId أو userId في الـ schema بتاع الـ body، ده مدخل لـ IDOR: اللي زي ده ييجي من الـ session.
Interview question "You share a Zod schema between the form and the API. Is client validation enough? What can't be shared?" → No. Client validation is only UX, since anyone can call the API directly, so the route must parse the body again. The schema can't express rules needing the database, the session or current stock, like uniqueness, permissions and availability. Those live in the route and come back as field errors. And anything identifying the actor, like tenantId, comes from the session and not from the schema.
"بتشارك Zod schema بين الفورم والـ API. الـ validation بتاع الـ client كفاية؟ وإيه اللي مش بيتشارك؟" ← لأ. الـ validation بتاع الـ client تجربة استخدام بس، لأن أي حد يقدر ينادي الـ API مباشرة، فالـ route لازم يعمل parse تاني. والـ schema مش هيعبّر عن قواعد محتاجة الـ database أو الـ session أو المخزن الحالي، زي الأرقام المكررة والصلاحيات والتوفر. دول مكانهم الـ route، وبيرجعوا كأخطاء على الـ fields. وأي حاجة بتحدد مين اللي بيعمل الطلب، زي tenantId، بتيجي من الـ session مش من الـ schema.

Part 6 — Server errors onto fields 🟡 Intermediateالجزء 6 — أخطاء السيرفر على الـ fields

English

Give the API one error contract. RFC 9457 (Problem Details, which replaced RFC 7807) defines the application/problem+json media type with type, title, status, detail and instance, and it allows extension members. My errors: [{ path, message }] is such an extension. The RFC's own example uses detail and a JSON pointer, so pick one shape and document it.

On the client, turn that body into form state. Call setError(path, { type: "server", message }, { shouldFocus }) for each field, including nested paths like lines.0.qty. Anything without a field goes to root.serverError. There are two cases people forget. A path the form doesn't know, such as tenantId, would set an error nobody can see, so check it first and send it to root. And not every failure is problem+json: a proxy can answer 502 with HTML, so read the content type before trusting the body, and fall back to a generic message.

Accessibility costs almost nothing here. Set aria-invalid on the input, link the message with aria-describedby, render the message with role="alert" so screen readers announce it, and move focus to the first invalid field. Lesson 16 goes further.

The wiring uses mutateAsync from useMutation inside onValid, so isSubmitting stays true for the whole request. Test it with MSW so the real fetch code runs. In MSW 3 the strict option is onUnhandledFrame: "error". I tested the old name, onUnhandledRequest: "error", against a real local server on 3.0.3: it's ignored, and the request reaches the real server with only a warning, so your tests could call a real API without failing. If you're using React 19 Actions without a form library, useActionState is the alternative, covered in lesson 19.

import { zodResolver } from "@hookform/resolvers/zod";
import { useMutation } from "@tanstack/react-query";
import { useFieldArray, useForm, type FieldPath } from "react-hook-form";
import {
  CreateInvoice,
  type CreateInvoiceInput,
  type CreateInvoiceOutput,
} from "@acme/schemas";

interface FieldProblem { path: string; message: string }
interface ProblemDetails { title: string; status: number; detail?: string; errors?: FieldProblem[] }

// الـ error بيحمل الـ body كله عشان الـ form يقدر يوزّعه على الـ fields
export class ApiProblem extends Error {
  constructor(readonly problem: ProblemDetails) {
    super(problem.title);
  }
}

export async function createInvoice(input: CreateInvoiceOutput): Promise<{ id: string }> {
  const res = await fetch("/api/invoices", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify(input),
  });
  const body: unknown = await res.json().catch(() => null);
  if (!res.ok) {
    // مش كل error هيبقى problem+json: الـ proxy ممكن يرجّع 502 HTML
    const isProblem = res.headers.get("content-type")?.includes("problem+json");
    throw new ApiProblem(
      isProblem ? (body as ProblemDetails) : { title: "Something went wrong, try again", status: res.status },
    );
  }
  return body as { id: string };
}

const emptyLine = { description: "", qty: "1", unitPrice: "" };

export function InvoiceForm({ onCreated }: { onCreated: (id: string) => void }) {
  // تلات generics: اللي بيتكتب، الـ context، واللي بيطلع بعد الـ resolver
  const form = useForm<CreateInvoiceInput, unknown, CreateInvoiceOutput>({
    resolver: zodResolver(CreateInvoice),
    defaultValues: { number: "", customerEmail: "", issueDate: "", dueDate: "", lines: [emptyLine] },
  });
  const { register, handleSubmit, setError, control, getValues, formState: { errors, isSubmitting } } = form;
  const { fields, append } = useFieldArray({ control, name: "lines" });
  const mutation = useMutation({ mutationFn: createInvoice });

  // السيرفر ممكن يرجّع path مش موجود في الفورم، زي tenantId
  const isFormField = (path: string): path is FieldPath<CreateInvoiceInput> =>
    getValues(path as FieldPath<CreateInvoiceInput>) !== undefined;

  const applyProblem = (problem: ProblemDetails) => {
    const leftovers: string[] = [];
    let focused = false;
    for (const { path, message } of problem.errors ?? []) {
      if (!isFormField(path)) {
        leftovers.push(message);
        continue;
      }
      // أول field غلط بس هو اللي ياخد الـ focus
      setError(path, { type: "server", message }, { shouldFocus: !focused });
      focused = true;
    }
    // أي حاجة ملهاش field تروح لـ root عشان متختفيش
    if (leftovers.length > 0 || !problem.errors?.length) {
      setError("root.serverError", {
        type: String(problem.status),
        message: leftovers.join(" ") || problem.detail || problem.title,
      });
    }
  };

  const onValid = async (values: CreateInvoiceOutput) => {
    try {
      const created = await mutation.mutateAsync(values);
      onCreated(created.id);
    } catch (err) {
      if (err instanceof ApiProblem) applyProblem(err.problem);
      else setError("root.serverError", { type: "network", message: "Network error, check your connection" });
    }
  };

  return (
    <form onSubmit={handleSubmit(onValid)} noValidate>
      {errors.root?.serverError && <p role="alert">{errors.root.serverError.message}</p>}

      <label htmlFor="number">Invoice number</label>
      <input
        id="number"
        aria-invalid={errors.number ? "true" : "false"}
        aria-describedby={errors.number ? "number-error" : undefined}
        {...register("number")}
      />
      {errors.number && <p id="number-error" role="alert">{errors.number.message}</p>}

      <label htmlFor="customerEmail">Customer email</label>
      <input
        id="customerEmail"
        aria-invalid={errors.customerEmail ? "true" : "false"}
        aria-describedby={errors.customerEmail ? "email-error" : undefined}
        {...register("customerEmail")}
      />
      {errors.customerEmail && <p id="email-error" role="alert">{errors.customerEmail.message}</p>}

      <label htmlFor="issueDate">Issue date</label>
      <input id="issueDate" type="date" {...register("issueDate")} />

      <label htmlFor="dueDate">Due date</label>
      <input id="dueDate" type="date" aria-invalid={errors.dueDate ? "true" : "false"} {...register("dueDate")} />
      {errors.dueDate && <p role="alert">{errors.dueDate.message}</p>}

      {fields.map((field, i) => (
        <fieldset key={field.id}>
          <legend>{`Line ${i + 1}`}</legend>
          <label htmlFor={`d${i}`}>Description</label>
          <input id={`d${i}`} {...register(`lines.${i}.description`)} />
          {errors.lines?.[i]?.description && <p role="alert">{errors.lines[i].description.message}</p>}
          <label htmlFor={`q${i}`}>Quantity</label>
          <input id={`q${i}`} inputMode="numeric" {...register(`lines.${i}.qty`)} />
          {errors.lines?.[i]?.qty && <p role="alert">{errors.lines[i].qty.message}</p>}
          <label htmlFor={`p${i}`}>Unit price</label>
          <input id={`p${i}`} inputMode="decimal" {...register(`lines.${i}.unitPrice`)} />
          {errors.lines?.[i]?.unitPrice && <p role="alert">{errors.lines[i].unitPrice.message}</p>}
        </fieldset>
      ))}
      <button type="button" onClick={() => append(emptyLine)}>Add line</button>

      <button disabled={isSubmitting}>{isSubmitting ? "Saving…" : "Save invoice"}</button>
    </form>
  );
}

بالعامية

ادّي الـ API عقد واحد للأخطاء. RFC 9457 (Problem Details، وبيحل محل RFC 7807) بيعرّف media type اسمه application/problem+json فيه type وtitle وstatus وdetail وinstance، وبيسمح بحقول زيادة. وerrors: [{ path, message }] بتاعتي حقل زيادة من دول. المثال بتاع الـ RFC نفسه بيستخدم detail وpointer من نوع JSON pointer، فاختار شكل واحد ووثّقه.

على الـ client، حوّل الـ body ده لـ form state. نادي setError(path, { type: "server", message }, { shouldFocus }) لكل field، ومنهم الـ paths الـ nested زي lines.0.qty. وأي حاجة ملهاش field تروح لـ root.serverError. فيه حالتين الناس بتنساهم. path الفورم مش عارفه، زي tenantId، هيعمل error محدش يشوفه، فافحصه الأول وابعته لـ root. ومش كل فشل بيبقى problem+json: الـ proxy ممكن يرد 502 بـ HTML، فاقرا الـ content type قبل ما تثق في الـ body، وارجع لرسالة عامة.

الـ accessibility هنا تكاد تكون ببلاش. حط aria-invalid على الـ input، واربط الرسالة بـ aria-describedby، واعرض الرسالة بـ role="alert" عشان الـ screen readers تقراها، وانقل الـ focus لأول field غلط. درس 16 بيدخل أعمق.

التوصيل بيستخدم mutateAsync من useMutation جوه onValid، فـ isSubmitting يفضل true طول الـ request. واختبره بـ MSW عشان كود الـ fetch الحقيقي يتنفذ. في MSW 3 الـ option الصارم هو onUnhandledFrame: "error". جرّبت الاسم القديم onUnhandledRequest: "error" قدام سيرفر محلي حقيقي على 3.0.3: بيتجاهل، والـ request بيوصل للسيرفر الحقيقي بتحذير بس، يعني الـ tests بتاعتك ممكن تنادي API حقيقي من غير ما تفشل. ولو بتستخدم React 19 Actions من غير form library، البديل هو useActionState، وموجود في درس 19.

فين هستخدمه في شغلي؟ الـ backend عندك NestJS أو Fastify: اعمل error handler واحد بيطلّع problem+json لكل ZodError ولأخطاء الـ DB زي unique constraint، فأي فورم في الـ app ياخد نفس الشكل. وفي الـ frontend، applyProblem تبقى helper واحدة مشتركة. وفي الـ Sentry، أي toast بيقول "Something went wrong" على 422 يبقى bug في التوصيل، مش في المستخدم: البيانات اللي يصلح بيها الغلطة كانت موجودة في الـ response.

Send anything else, or an error with no field list, to a root-level alert so nothing disappears. Each input gets aria-invalid and aria-describedby, and each message has role="alert". I'd test it with MSW and Testing Library, asserting the message, the attributes and the focus.
"الـ API رجّع 422 فيها قايمة أخطاء fields. احكيلي الـ client بيعمل إيه." ← بيفحص الـ content type قبل ما يثق في الـ body. لكل غلطة، لو الـ path موجود في الفورم ينادي setError بيه، وأول واحدة تاخد الـ focus. وأي حاجة تانية، أو غلطة من غير قايمة fields، تروح لـ alert على مستوى الـ root عشان محدش يختفي. كل input بياخد aria-invalid وaria-describedby، وكل رسالة فيها role="alert". وباختبره بـ MSW وTesting Library وأتأكد من الرسالة والـ attributes والـ focus.

❌ watch() in the form body

  const { register, watch } = useForm<Values>();

      <output>{name}</output>

    </form>

}

❌ watch في جسم الفورم بيرجّعك لتكلفة الـ controlled: 24 render للفورم و1,200 للـ fields في 24 حرف، وReact Compiler بيسيب الـ component من غير compile. ✅ useWatch في child صغير: الفورم صفر، والـ child بس بيتحرك.

❌ Spreading formState 
const { formState } = useForm();

// → {"spreadIsDirty":"undefined","keys":[]}

✅ Read the getter you need

// القراءة هنا هي اللي بتعمل الاشتراك

بالعامية

❌ الـ spread بيرجّع object فاضي: مفيش مفاتيح وisDirty بـ undefined، فالزرار هيفضل disabled حتى بعد الكتابة، ومفيش اشتراك خالص. ✅ اقرا الخاصية نفسها وقت الـ render، والقراءة دي هي اللي بتعمل الاشتراك.

❌ z.infer with coerce or transform 
// الـ z.infer هو نفسه z.output: أرقام

  resolver: zodResolver(Line),

✅ Three generics, or none 
const form = useForm<
  z.input<typeof Line>,
  unknown,
  z.output<typeof Line>
>({
  resolver: zodResolver(Line),
  defaultValues: { qty: "1", unitPrice: "" },

// لو سبت الـ generics خالص، TypeScript بيستنتج نفس النتيجة

❌ z.infer هو نوع الـ output، أرقام، بس الفورم بيمسك strings. فـ TypeScript 7 بيرفضه بالرسالة دي، والناس بتحلها غلط بـ as any، وبعدين unitPrice يوصل string في الـ runtime. ✅ الـ 3 generics بيوصفوا الحقيقة: strings جوه الفورم وأرقام في handleSubmit. ولو سبت الـ generics خالص، الاستنتاج بيشتغل برضه واتكمبل عندي.

Solution · الحل 
import * as z from "zod";

const DAY_MS = 86_400_000;

// قاعدتين بين الحقلين، وكل واحدة بتحط الغلطة على dueDate
export const InvoiceDates = z
  .object({ issueDate: z.iso.date(), dueDate: z.iso.date() })
  .refine((d) => d.dueDate > d.issueDate, {
    error: "Due date must be after the issue date",
    path: ["dueDate"],
  })
  .refine((d) => Date.parse(d.dueDate) - Date.parse(d.issueDate) <= 90 * DAY_MS, {
    error: "Due date must be within 90 days",
    path: ["dueDate"],
  });

const check = (issueDate: string, dueDate: string) => {
  const r = InvoiceDates.safeParse({ issueDate, dueDate });
  console.log(issueDate, dueDate, r.success ? "ok" : r.error.issues.map((i) => i.message).join(" | "));
};

check("2026-11-01", "2026-12-01");
check("2026-11-10", "2026-11-01");
check("2026-11-01", "2027-03-01");

2026-11-01 2027-03-01 Due date must be within 90 days

Cheat sheet · الخلاصة

  • Form state (values, dirty, touched, errors, submitting) is short-lived and local: not in a global store, not in the query cache.
  • defaultValues are read once. Use key={invoice.id} or values with resetOptions: { keepDirtyValues: true }.
  • 50 controlled fields: 50 renders per key. About 0.7 ms on a fast machine, far more on slow devices with expensive fields and per-key validation.
  • Ladder: memo → field-level state → uncontrolled. React Hook Form is built on the last one.
  • register returns name, ref, onChange, onBlur. handleSubmit validates, calls your callback and focuses the first invalid field.
  • formState is getters: only what you read subscribes. Don't spread it.
  • useWatch in a child, not watch() in the form: watch gave 1,200 field renders and makes React Compiler skip the component.
  • Default mode: "onSubmit" or onTouched. With a resolver, onChange runs the whole schema per key.
  • Controller for widgets with no native input, and pass field.ref. useFieldArray with field.id as the key: an index key moves row state to the wrong row.
  • One schema package, two types: useForm<z.input<S>, unknown, z.output<S>>. Use import * as z from "zod".
  • The server always validates again, and adds what the schema can't know: uniqueness, permissions, stock. tenantId comes from the session.
  • 422 as application/problem+json → setError(path) with focus on the first, unknown paths to root.serverError, aria-invalid, role="alert". Test with MSW and onUnhandledFrame: "error".
بالعامية
  • الـ form state (القيم وdirty وtouched والأخطاء والـ submitting) عمره قصير وlocal: مش في store عام ومش في الـ query cache.
  • defaultValues بتتقرا مرة واحدة. استخدم key={invoice.id} أو values مع resetOptions: { keepDirtyValues: true }.
  • 50 field controlled يعني 50 render مع كل حرف. حوالي 0.7ms على جهاز سريع، وأكتر بكتير على الأجهزة البطيئة مع fields غالية وvalidation في كل حرف.
  • السلّم: memo ← state على مستوى الـ field ← uncontrolled. وReact Hook Form مبني على الأخيرة.
  • register بيرجّع name وref وonChange وonBlur. وhandleSubmit بيعمل validate، وبينادي الـ callback بتاعك، وبيعمل focus لأول field غلط.
  • formState عبارة عن getters: اللي بتقراه بس هو اللي بيشترك. ومتعملوش spread.
  • useWatch في child مش watch() في الفورم: watch عمل 1,200 render للـ fields وبيخلي React Compiler يسيب الـ component.
  • خلي mode على onSubmit الافتراضي أو onTouched. ومع resolver، onChange بينفذ الـ schema كله مع كل حرف.
  • Controller للـ widgets اللي مفيهاش native input، ووصّل field.ref. وuseFieldArray بـ field.id كـ key: الـ index key بينقل state الـ row لـ row غلط.
