Why this matters · ليه ده مهم

English

Almost every React codebase has useMemo sprinkled around "for performance", memo that never skips anything, and a context that re-renders half the page. The cost is real: noise in each component, deps to maintain, bugs from stale comparisons, and still a slow screen. A Senior measures first, knows why a prop changed identity, and reaches for the cheapest fix. In interviews, "when does useMemo actually help?" separates people who memorized the API from people who've profiled something. Custom hooks are the other half: they're how you keep that logic out of your components and test it on its own.

بالعامية

تقريبًا كل codebase فيها React هتلاقي فيه useMemo مرشوش في كل حتة "عشان الـ performance"، و memo عمره ما منع render، و context بيعمل re-render لنص الصفحة. والتكلفة حقيقية: كود زيادة في كل component، و deps لازم تتظبط، و bugs من مقارنات قديمة، والشاشة برضو بطيئة. السنيور بيقيس الأول، وعارف ليه الـ prop غيّر الـ identity بتاعه، وبيبدأ بأرخص حل. وفي الـ interviews، سؤال "useMemo بيفيد فعلًا إمتى؟" بيفرّق بين اللي حافظ الـ API واللي عمل profiling لحاجة قبل كده. والـ custom hooks هي النص التاني: بيها بتطلّع المنطق ده برّه الـ components وتعمله test لوحده.

Part 1 — What's actually expensive 🟡 Intermediateالجزء 1 — إيه اللي غالي فعلًا

English

useMemo caches a calculation between renders and skips it when its deps are unchanged. So it only pays off when the calculation is slow and the component re-renders for other reasons. The react.dev reference gives you a concrete guide: "In general, unless you're creating or looping over thousands of objects, it's probably not expensive." And for the measurement: "If the overall logged time adds up to a significant amount (say, 1ms or more), it might make sense to memoize that calculation." It also points out that useMemo won't make the first render faster, since the calculation has to run once anyway.

Below, a page filters and sorts 50,000 orders, and a theme change that has nothing to do with the orders re-renders it. I measure with <Profiler>, whose actualDuration is the time spent rendering the subtree in that commit, in dev and in a production build. Production needs the react-dom/profiling alias, or onRender is never called; that's covered in lesson 23.

import { Profiler, useMemo, useState } from "react";
import { flushSync } from "react-dom";
import { createRoot } from "react-dom/client";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

type Order = { id: number; status: "paid" | "refunded"; total: number; customer: string };

// 50 ألف order بأرقام ثابتة (مش random) عشان القياس يتكرر
const orders: Order[] = Array.from({ length: 50_000 }, (_, i) => ({
  id: i,
  status: i % 3 === 0 ? "refunded" : "paid",
  total: (i * 7919) % 10_000,
  customer: `customer-${i % 500}`,
}));

function selectVisible(all: Order[], status: Order["status"]) {
  return all
    .filter((o) => o.status === status)
    .toSorted((a, b) => b.total - a.total || a.id - b.id)
    .slice(0, 50);
}

type PageProps = { status: Order["status"]; theme: string };

function PlainPage({ status, theme }: PageProps) {
  const visible = selectVisible(orders, status);
  return <p className={theme}>{visible.length} rows, top total {visible[0].total}</p>;
}

function MemoPage({ status, theme }: PageProps) {
  const visible = useMemo(() => selectVisible(orders, status), [status]);
  return <p className={theme}>{visible.length} rows, top total {visible[0].total}</p>;
}

// قيمة رخيصة خالص: useMemo هنا تكلفة من غير فايدة
function CheapPlain({ price, qty }: { price: number; qty: number }) {
  const lineTotal = price * qty;
  return <span>{lineTotal}</span>;
}
function CheapMemo({ price, qty }: { price: number; qty: number }) {
  const lineTotal = useMemo(() => price * qty, [price, qty]);
  return <span>{lineTotal}</span>;
}

const median = (xs: number[]) => xs.toSorted((a, b) => a - b)[Math.floor(xs.length / 2)];

async function measurePage(name: string, Page: typeof PlainPage) {
  const durations: number[] = [];
  const root = createRoot(document.getElementById("root")!);
  const element = (theme: string) => (
    <Profiler id={name} onRender={(_id, _phase, actualDuration) => durations.push(actualDuration)}>
      <Page status="paid" theme={theme} />
    </Profiler>
  );
  flushSync(() => root.render(element("light")));
  durations.length = 0;
  // 21 مرة: تغيير theme ملوش علاقة بالـ orders
  for (let i = 0; i < 21; i++) {
    flushSync(() => root.render(element(i % 2 ? "light" : "dark")));
    await sleep(5);
  }
  console.log(`${name}: unrelated re-render ≈ ${median(durations).toFixed(2)} ms`);
  root.unmount();
}

async function measureCheap(name: string, Cell: typeof CheapPlain) {
  const durations: number[] = [];
  const root = createRoot(document.getElementById("root")!);
  const element = (tick: number) => (
    <Profiler id={name} onRender={(_id, _phase, actualDuration) => durations.push(actualDuration)}>
      <div data-tick={tick}>
        {Array.from({ length: 2000 }, (_, i) => <Cell key={i} price={i} qty={2} />)}
      </div>
    </Profiler>
  );
  flushSync(() => root.render(element(0)));
  durations.length = 0;
  for (let i = 1; i <= 41; i++) {
    flushSync(() => root.render(element(i)));
    await sleep(5);
  }
  console.log(`${name}: 2000 cells re-render ≈ ${median(durations).toFixed(2)} ms`);
  root.unmount();
}

English

Three things to take from those numbers:

  • The expensive case is a clear win. ≈4 to 6 ms per re-render is about a third of a 16.7 ms frame at 60 Hz, spent on each keystroke or theme toggle; with useMemo it's effectively zero. An earlier run of the same code, while this machine was under much heavier load, measured ≈22 ms: more than a whole frame. A slow device moves you toward that second number.
  • The cheap case gains nothing. Memoizing a multiplication was slightly slower in each production round (≈1.4 ms vs ≈1.8 ms for 2000 cells), and lost in the noise in dev. You also pay in reading time, in deps to keep correct and in memory for the cached value.
  • Measure in a production build. Dev mode inflates React's own work (≈4 ms vs ≈1.4 ms for the same cells, and ≈78 ms vs ≈3 ms in the loaded run) while your own calculation stays in the same range. So dev timings exaggerate the render cost and hide what your code contributes.

The reference limits useMemo to a few cases: the calculation is noticeably slow and its deps rarely change, the value goes to a component wrapped in memo, or the value is a dependency of another hook. The last two are about identity, not speed, which is the next part.

بالعامية

useMemo بيخزّن نتيجة حساب بين الـ renders وبيعدّيه لو الـ deps زي ما هي. يعني بيفيد بس لما الحساب يبقى بطيء والـ component بيعمل re-render لأسباب تانية. وreference بتاع react.dev بيديك مقياس واضح: في العموم، لو مش بتعمل أو بتلف على آلاف الـ objects، غالبًا مش غالي. وللقياس: لو الوقت المتسجل مجموعه كبير (يعني 1ms أو أكتر)، ممكن يبقى منطقي تعمل memoize. وبينبهك كمان إن useMemo مش هيخلّي أول render أسرع، لأن الحساب لازم يشتغل مرة في كل الأحوال.

في المثال، صفحة بتعمل filter و sort لـ 50 ألف order، وتغيير theme ملوش علاقة بالـ orders بيعمل re-render. بقيس بـ <Profiler>، وactualDuration بتاعه هو الوقت اللي اتصرف في رسم الـ subtree في الـ commit ده، في dev وفي production build. والـ production محتاج alias لـ react-dom/profiling، وإلا onRender مش هيتنادى خالص، والتفاصيل في الدرس 23.

3 حاجات تاخدها من الأرقام:

  • الحالة الغالية مكسب واضح. حوالي 4 لـ 6ms لكل re-render ده حوالي تلت frame (16.7ms على 60Hz)، بيتصرفوا مع كل حرف أو تغيير theme، ومع useMemo تقريبًا صفر. وتشغيل قبل كده لنفس الكود، والجهاز عليه ضغط أكبر بكتير، طلّع حوالي 22ms، يعني أكتر من frame كامل. والجهاز البطيء بيقرّبك من الرقم التاني ده.
  • الحالة الرخيصة مفيهاش مكسب. الـ memoize لعملية ضرب كان أبطأ شوية في كل جولة production (حوالي 1.4ms مقابل 1.8ms لـ 2000 خلية)، وفي dev ضايع في الـ noise. وكمان بتدفع في وقت القراية، وفي deps لازم تفضل مظبوطة، وفي memory للقيمة المتخزنة.
  • قيس في production build. الـ dev بينفخ شغل React نفسه (حوالي 4ms مقابل 1.4ms لنفس الخلايا، وحوالي 78ms مقابل 3ms في التشغيل اللي عليه ضغط)، والحساب بتاعك فاضل في نفس الحدود. فأرقام الـ dev بتكبّر تكلفة الـ render وبتخبي نصيب الكود بتاعك.

والـ reference بيحصر useMemo في حالات قليلة: الحساب بطيء بشكل ملحوظ والـ deps نادرًا ما بتتغير، أو القيمة رايحة لـ component ملفوف بـ memo، أو القيمة dependency في hook تاني. وآخر حالتين موضوعهم الـ identity مش السرعة، وده الجزء الجاي.

فين هستخدمه في شغلي؟ صفحة orders في admin dashboard بتجيب 50 ألف صف وتعمل filter و sort على الـ client، والمستخدم بيشتكي إن الكتابة في الـ search بتهنّج. أول خطوة console.time أو Profiler حوالين الحساب، مش useMemo على كل حاجة. ولو الرقم طلع كبير، useMemo يحل جزء، بس السؤال الأكبر كـ Full-Stack: ليه الـ 50 ألف صف بييجوا للـ browser أصلًا؟ الـ filter والـ pagination في الـ API و Postgres أرخص من أي memoization. الغلطة الشائعة إنك تلف total = price * qty في useMemo وتعتبر ده optimization.

Part 2 — Referential equality 🟡 Intermediateالجزء 2 — الـ referential equality

English

memo(Component) skips a re-render when every prop is unchanged by Object.is. Primitives compare by value, but objects and functions compare by identity, and an inline onSelect={(id) => ...} is a new function on each render. So one inline prop is enough to defeat memo completely. useCallback exists to keep that identity stable. Neither one helps alone, and the matrix below shows it with 1000 rows:

import { memo, useCallback, useState, type ComponentType } from "react";
import { createRoot } from "react-dom/client";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

type Order = { id: string; total: number };
const orders: Order[] = Array.from({ length: 1000 }, (_, i) => ({ id: `o-${i}`, total: i * 10 }));

let rowRenders = 0;
type RowProps = { order: Order; isSelected: boolean; onSelect: (id: string) => void };

function PlainRow({ order, isSelected, onSelect }: RowProps) {
  rowRenders++;
  return (
    <li id={order.id} aria-selected={isSelected} onClick={() => onSelect(order.id)}>
      {order.total}
    </li>
  );
}
const MemoRow = memo(PlainRow);

type ListProps = { Row: ComponentType<RowProps>; stable: boolean };

function OrdersList({ Row, stable }: ListProps) {
  const [selectedId, setSelectedId] = useState<string | null>(null);
  const stableSelect = useCallback((id: string) => setSelectedId(id), []);
  const inlineSelect = (id: string) => setSelectedId(id);
  const onSelect = stable ? stableSelect : inlineSelect;
  return (
    <ul>
      {orders.map((order) => (
        <Row key={order.id} order={order} isSelected={order.id === selectedId} onSelect={onSelect} />
      ))}
    </ul>
  );
}

بالعامية

memo(Component) بيعدّي الـ re-render لو كل الـ props زي ما هي حسب Object.is. الـ primitives بتتقارن بالقيمة، بس الـ objects والـ functions بتتقارن بالـ identity، وonSelect={(id) => ...} الـ inline ده function جديدة في كل render. فـ prop واحد inline كفاية يلغي الـ memo خالص. وuseCallback موجود عشان يثبّت الـ identity دي. ولا واحد فيهم بيفيد لوحده، وده اللي الجدول بيوريه على 1000 row.

English

The same identity rule produces a set of traps:

  • Default object props. { options = {} } creates a new object on each render, which breaks any memo child or effect deps downstream. Use a constant outside the component.
  • children always differs. JSX creates a new element object on each render, so memo on a component with element children does nothing unless the element itself is stable.
  • A custom compare can lie. The second argument of memo lets you skip re-renders by your own rule. Below, comparing only the id means a refund to 40 never reaches the DOM. The reference says you must compare every prop, including functions, because a skipped function prop keeps the props and state of an old render. It also warns that deep equality can freeze the app when the data grows.
  • useCallback is useMemo for functions. useCallback(fn, deps) caches the function; useMemo(() => fn, deps) caches the result of calling your factory, which here is the same function.
  • Deps travel. A useCallback that depends on [cart] changes whenever the cart changes, so each memoized child re-renders anyway: 30 renders in 3 adds. The updater form removes the dep: 0 renders. That's the hidden cost of manual memoization: each stable value needs its own inputs to be stable, all the way up.
import { memo, useCallback, useMemo, useState, type ReactNode } from "react";
import { createRoot } from "react-dom/client";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

let renders = 0;
let rerenderParent = () => {};

function useRerender() {
  const [, setTick] = useState(0);
  rerenderParent = () => setTick((t) => t + 1);
}

async function countRenders(name: string, element: React.JSX.Element) {
  const root = createRoot(document.getElementById("root")!);
  root.render(element);
  await sleep(30);
  renders = 0;
  for (let i = 0; i < 5; i++) {
    rerenderParent();
    await sleep(10);
  }
  console.log(`${name}: ${renders} renders in 5 parent updates`);
  root.unmount();
  await sleep(10);
}

Part 3 — Composition before memo 🟡 Intermediateالجزء 3 — الـ composition قبل الـ memo

English

Before any memoization, change the component structure. When React re-renders a component, it re-renders the children it created in that render. If an element comes from outside as children, it was created by the parent, whose render didn't run. The element object is the same as last time, and React skips that subtree when it sees an identical element. This is lifting expensive children: the state lives in a wrapper, and the expensive part is passed through it.

The sibling technique is moving state down: if only one small leaf needs a fast-changing value, like a cursor position, keep the state in that leaf. Both need no memo, no deps and no new concepts. Both cut the table's renders from 100 to 0 here:

Part 5 — useContext 🟡 Intermediateالجزء 5 — useContext

English

Context passes a value down the tree without threading props. createContext makes the context, a provider supplies a value, and useContext reads the nearest provider above the calling component. In React 19, you render <SessionContext value={...}> directly. The older <SessionContext.Provider> still works, with no warning on 19.3.1 (the third line below), so you'll see both in real code.

The rule that matters: when the provider's value changes identity by Object.is, every consumer below re-renders, and memo on a parent doesn't stop it. So value={{ user, setUser }} is the classic bug: a new object on each render of the provider, even for a state change unrelated to the session. All 200 consumers re-render through a memo parent that itself didn't render. The fix is useMemo on the value. A real change of user still re-renders all 200, as it should.

Reading context conditionally with use(Context) is in lesson 19.

Part 6 — Context splitting and selectors 🟡 Intermediateالجزء 6 — تقسيم الـ context والـ selectors

English

useMemo on the value only stops unrelated updates. If one context holds both the cart state and the dispatch, a component that only dispatches still re-renders on each cart change, because the object changed. A grid of 200 AddToCartButtons re-renders on each click, even though none of them displays anything from the cart.

The fix is splitting by how things change: dispatch from useReducer is stable forever, so it gets its own context, and consumers of it never re-render. Those 200 re-renders become 0, while CartCount, which really reads the state, still updates. Split by concern too: session, theme and locale shouldn't share one provider, since they change for different reasons.

There's no built-in selector. You can't subscribe to one field of a context. A useCartSelector built on useContext looks right, and still re-renders on each change, which the output below proves. The manual workaround is an outer component that reads and a memo inner one that renders: the outer still runs, but the expensive part doesn't. Real selectors need a store outside React: Zustand in lesson 11, built on useSyncExternalStore in lesson 19.

That gives the rule: context is fine for low-frequency values such as auth, theme, locale, tenant and feature flags. For values that change on each keystroke or mouse move with many readers, use local state or a store.

Part 7 — Custom hooks 🟡 Intermediateالجزء 7 — الـ custom hooks

English

A custom hook is a function whose name starts with use and which calls other hooks. It extracts logic from a component so that it gets a name, can be reused and can be tested alone. Three examples at different levels:

  • useDebouncedValue wraps an effect with a timer and its cleanup.
  • useOrderFilters wraps a domain's state transitions: changing the status resets the page, and that rule now lives in one place.
  • useOnlineStatus wraps an external source with useSyncExternalStore, explained in lesson 19.

The use prefix isn't decoration: the lint rules depend on it. That's how react-hooks/rules-of-hooks knows a function may call hooks, and how it checks its callers. The reverse also holds, in the docs' words: "If your function doesn't call any Hooks, avoid the use prefix."

import { useCallback, useEffect, useMemo, useState, useSyncExternalStore } from "react";

// قيمة بتتأخر: بترجع القيمة الجديدة بعد ما المستخدم يبطّل كتابة delayMs
export function useDebouncedValue<T>(value: T, delayMs = 300): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delayMs);
    // الـ cleanup بيلغي الـ timer القديم مع كل حرف جديد
    return () => clearTimeout(id);
  }, [value, delayMs]);
  return debounced;
}

export function useOrderFilters({ initialStatus = "all", pageSize = 20 }: UseOrderFiltersOptions = {}) {
  const [filters, setFilters] = useState<OrderFilters>({ status: initialStatus, query: "", page: 1 });

  // كل الـ callbacks بـ updater function، فالـ identity ثابتة وتتحط في deps بأمان
  const setStatus = useCallback((status: OrderStatus) => setFilters((f) => ({ ...f, status, page: 1 })), []);
  const setQuery = useCallback((query: string) => setFilters((f) => ({ ...f, query, page: 1 })), []);

    () => setFilters({ status: initialStatus, query: "", page: 1 }),
    [initialStatus],
  );

      limit: pageSize,
      offset: (filters.page - 1) * pageSize,
    }),
    [filters, pageSize],
  );

  return { filters, apiParams, setStatus, setQuery, nextPage, reset };
}

English

API design is what separates a helpful hook from one that spreads bugs:

  • Options object over positional arguments. useOrderFilters({ pageSize: 50 }) reads clearly and can grow; useOrderFilters("all", 50, true) can't.
  • Object or tuple return. Return a tuple for one or two values that callers will rename, like useState. Return an object with more than two, where order would be a trap. The typing, including as const, is in lesson 14.
  • Stable callbacks. If callers may put your function in deps, keep its identity stable with useCallback and updaters, as useOrderFilters does. Memoize derived objects like apiParams for the same reason. A shared hook should do this even if your app uses the Compiler, since its callers may not.
  • Don't wrap lifecycle. useMount(fn) looks tidy and hides the deps from the linter. The docs: "Custom 'lifecycle' Hooks like useMount don't fit well into the React paradigm", because the linter only checks direct useEffect calls. The output above shows the result: globex never loads. Name hooks after what they do: useOrderFilters, useSocket(url).

Common mistakes · غلطات شائعة

❌ Memoizing a cheap value 
const lineTotal = useMemo(() => price * qty, [price, qty]);
// production: 2000 cells ≈ 1.8 ms, slower and harder to read
✅ Just compute it 
const lineTotal = price * qty;
// production: 2000 cells ≈ 1.4 ms
بالعامية

❌ useMemo لعملية ضرب بيكلّف أكتر من الضرب، وبيضيف deps لازم تتراجع، ومفيش أي مكسب. ✅ احسبها وخلاص. قيس الأول، وuseMemo يبقى لما الوقت يوصل لـ 1ms أو أكتر، أو لما تكون محتاج identity ثابتة. والأرقام تقريبية، والفرق صغير، بس المهم إن مفيش مكسب.

❌ A compare function that skips props 
const LineRow = memo(LineRowImpl, (prev, next) =>
  prev.line.id === next.line.id,
);
// after a refund to 40, the DOM says: "o-1: 100"
✅ Default compare and stable props 
// الأب بيبعت object جديد لما البيانات تتغير بس
const LineRow = memo(LineRowImpl);
بالعامية

❌ المقارنة على الـ id بس معناها إن أي تغيير تاني مش هيوصل الشاشة، فالمستخدم شايف 100 والحقيقة 40، ومفيش أي error. ✅ سيب المقارنة الـ default، وخلّي الأب يحافظ على الـ reference طول ما البيانات متغيرتش. ولو لازم compare مخصص، لازم يقارن كل prop.

❌ High-frequency state in context 
function CursorProvider({ children }: { children: ReactNode }) {
  const [cursor, setCursor] = useState({ x: 0, y: 0 });
  // كل حركة ماوس بترسم كل اللي بيقرا الـ context
  return <CursorContext value={cursor}>{children}</CursorContext>;
}
✅ State in the leaf that needs it 
function CursorBadge() {
  const [cursor, setCursor] = useState({ x: 0, y: 0 });
  // هنا بس اللي بيترسم، ولو قرّاء كتير استخدم store
  return <output>{cursor.x},{cursor.y}</output>;
}
بالعامية

❌ الـ context مفيهوش selector، فأي قيمة بتتغير عشرات المرات في الثانية بتعمل re-render لكل قارئ كل مرة. ✅ خلّي الـ state في الـ leaf اللي محتاجاها زي الجزء 3، ولو ليها قرّاء كتير استخدم store بـ selectors زي Zustand. الـ context للقيم اللي بتتغير قليل.

❌ The hook's whole return value in deps 
const filters = useOrderFilters();
useEffect(() => {
  loads++;
}, [filters]);
// [filters]  : 4 loads in 4 renders
✅ The stable piece you actually use 
const { apiParams } = useOrderFilters();
useEffect(() => {
  loads++;
}, [apiParams]);
// [apiParams]: 1 loads in 4 renders
بالعامية

❌ الـ hook بيرجّع object جديد في كل render، فلو حطيته كله في الـ deps الـ effect هيشتغل كل render: 4 loads في 4 renders، ولو الـ effect فيه setState يبقى loop الدرس 07. ✅ اعمل destructure للقيمة الثابتة اللي بتستخدمها فعلًا: load واحد. وعشان كده لازم الـ hook يثبّت apiParams بـ useMemo.

3. useDebouncedCallback, tested 🔴 hard Write useDebouncedCallback(fn, delayMs). import { useCallback, useEffect, useRef } from "react";
import { act, renderHook } from "@testing-library/react";
import { afterEach, beforeEach, expect, it, vi } from "vitest";

// دالة ثابتة الـ identity بتنادي آخر fn بعد ما النداءات تقف delayMs
function useDebouncedCallback<A extends unknown[]>(fn: (...args: A) => void, delayMs: number) {
  const timer = useRef<ReturnType<typeof setTimeout> | undefined>(undefined);
  const latest = useRef(fn);
  // الـ ref بيتحدث في effect، مش في الـ render
  useEffect(() => {
    latest.current = fn;
  });
  useEffect(() => () => clearTimeout(timer.current), []);
  return useCallback(
    (...args: A) => {
      clearTimeout(timer.current);
      timer.current = setTimeout(() => latest.current(...args), delayMs);
    },
    [delayMs],
  );
}

beforeEach(() => vi.useFakeTimers());
afterEach(() => vi.useRealTimers());

it("is stable, calls the latest fn once, and stops on unmount", () => {
  const calls: string[] = [];
  const { result, rerender, unmount } = renderHook(
    ({ label }: { label: string }) =>
      useDebouncedCallback((query: string) => calls.push(`${label}:${query}`), 300),
    { initialProps: { label: "first" } },
  );
  const stable = result.current;

  act(() => {
    result.current("r");
    result.current("re");
  });
  rerender({ label: "second" });
  expect(result.current).toBe(stable);

  act(() => vi.advanceTimersByTime(300));
  // نداء واحد بس، بآخر قيمة، وبآخر callback
  expect(calls).toEqual(["second:re"]);

  act(() => result.current("ref"));
  unmount();
  expect(vi.getTimerCount()).toBe(0);
});

Cheat sheet · الخلاصة

  • Measure first, in a production build. react.dev's guide: thousands of objects, or 1 ms or more, before useMemo makes sense.
  • useMemo helps for a slow calculation with stable deps, or for identity. It doesn't speed up the first render. 50k filter and sort: ≈5 ms (≈22 ms under heavy load) vs ≈0. A multiplication: no gain.
  • memo compares props with Object.is. memo alone or useCallback alone: 1000 renders. Together: 1.
  • Identity traps: inline functions, default {}, element children, callbacks depending on [cart] (use an updater).
  • A custom compare must check every prop, or the UI shows stale data (a total of 100 after a refund to 40).
  • Cheapest first: move state down, lift children (table renders 100 → 0), then memo.
  • The Compiler is opt-in: 8 → 2 renders with no manual memo. With it on, don't memoize by default. It silently skips functions that break the rules.
  • Context: a changed value re-renders all consumers, through memo parents. An inline value re-renders 200 on any provider render; fix with useMemo. <Ctx value> in React 19; .Provider still works.
  • Split state and dispatch: 200 → 0 renders. There's no built-in selector, so use a store for frequent values. Context suits low-frequency values.
  • Custom hooks share logic, not state. The use prefix is what the lint rules depend on, and it's only for functions that call hooks.
  • Hook API: options object, tuple up to 2 values or object beyond, stable callbacks, no useMount. Test with renderHook, act and fake timers.
بالعامية
  • قيس الأول، في production build. مقياس react.dev: آلاف الـ objects، أو 1ms أو أكتر، قبل ما useMemo يبقى منطقي.
  • useMemo بيفيد لحساب بطيء و deps ثابتة، أو للـ identity. ومش بيسرّع أول render. الـ filter والـ sort لـ 50 ألف: حوالي 5ms (و 22ms تحت ضغط كبير) مقابل حوالي صفر. وعملية الضرب: مفيش مكسب.
  • memo بيقارن الـ props بـ Object.is. memo لوحده أو useCallback لوحده: 1000 render. مع بعض: 1.
  • فخاخ الـ identity: functions inline، و default {}، و children elements، و callbacks معتمدة على [cart] (استخدم updater).
  • الـ compare المخصص لازم يراجع كل prop، وإلا الـ UI هيعرض بيانات قديمة (total بـ 100 بعد refund لـ 40).
  • الأرخص الأول: نزّل الـ state لتحت، ارفع الـ children (renders الـ table من 100 لصفر)، وبعدين memo.
  • الـ Compiler اختياري: من 8 لـ 2 renders من غير memo يدوي. ولو شغال، متعملش memoize كـ default. وهو بيعدّي من غير ما يقولك الـ functions اللي بتكسر القواعد.
  • الـ context: value اتغيرت يعني re-render لكل الـ consumers، حتى من خلال أب عليه memo. والـ value الـ inline بتعمل re-render لـ 200 مع أي render للـ provider، والحل useMemo. و<Ctx value> في React 19، و .Provider لسه شغالة.
  • قسّم الـ state والـ dispatch: من 200 لصفر render. ومفيش selector جاهز، فاستخدم store للقيم اللي بتتغير كتير. والـ context مناسب للقيم اللي بتتغير قليل.
  • الـ custom hooks بتشارك المنطق مش الـ state. والـ use في الأول هي اللي الـ lint rules معتمدة عليها، وهي للـ functions اللي بتنادي hooks بس.
  • API الـ hook: options object، و tuple لحد قيمتين أو object لو أكتر، و callbacks ثابتة، ومن غير useMount. واختبره بـ renderHook و act و fake timers.
