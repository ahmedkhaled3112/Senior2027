Why this matters · ليه ده مهم

English

A CV makes claims. An article, a merged PR or a recording is something a stranger can open and test. This lesson treats each of them as evidence that has to survive a technical interviewer for ten minutes, because that is what a good interviewer does with anything you link.

How to write the article or give the talk belongs to section 13 · 3.5. Here you check what you have published against the questions it invites, and you add runnable checks, because section 13 has no code. The curriculum says published work gets examined more than any certificate. That is its opinion and nothing here measures it. Either way, this is the difference between saying you understand production and letting someone check.

⏱ Timed prompt · 15 minutes Pick three topics you have really worked on. For each one, write one line about the problem and the single hardest question an interviewer could ask you about it. If you can't write the question, you don't have an article yet. Stop reading and do it.

English

Model solution. How to write a post, how to open it and what you may publish from work are in section 13 · 3.5, so this part doesn't repeat them. Here you read topics the way an interviewer does: each one is a claim about you, and it is worth what it survives.

The README suggests five topics. Mariam picks three, the ones where something actually happened to her (starred below), and writes the question each one invites. A topic you can't write a hard question for isn't ready. A question you can't answer means the work isn't done yet, and it is better to learn that now than in the interview.

The README's target of 6–10 articles is the curriculum's opinion. A more useful rule for your time: three real ones beat ten thin ones. The test for each is whether a stranger could dig into it for 10 minutes and still find something to ask, and whether you would still have an answer.

The README's chain is real problem → experiment → numbers → lesson. article-lint.ts checks whether a draft has that shape and flags tutorial phrasing. It is a rough heuristic made of regular expressions: it looks at the shape of the text and does not judge whether the story is true.

import { readFileSync } from "node:fs";

// تحذير: ده فحص شكل بس (rough heuristic): مبيعرفش القصة حقيقية ولا مفبركة
const CHAIN = [
  {
    link: "real problem",
    re: /\b(production|incident|outage|paged|timeouts?|timed out|complain\w*|tickets?|customers?|tenants?|p9[59])\b/i,
    missing: "who was hurt, and how did you know?",
  },
  {
    link: "experiment",
    re: /\b(EXPLAIN|reproduc\w+|measured|benchmark\w*|load[- ]test\w*|compared)\b/i,
    missing: "what did you actually run?",
  },
  {
    link: "lesson",
    re: /\b(lesson|learned|next time|would (?:do|change)|trade-?offs?|mistake)\b/i,
    missing: "what would you do differently?",
  },
];

// الرقم لازم جنبه وحدة: رقم لوحده ملوش معنى في مقال
const NUMBER_WITH_UNIT =
  /\b\d[\d,.]*\s?(?:ms|s|sec|seconds?|minutes?|kB|MB|GB|%|rows?|buffers?|pages?|rps|requests?|users?|tenants?|bytes)(?!\w)/gi;
const MIN_NUMBERS = 3;

// لو مفيش إصدار وحجم بيانات، محدش يقدر يعيد التجربة أو يحفر فيها
const SETUP = /\b(?:postgres(?:ql)?\s?\d+|node(?:\.js)?\s?\d+|\d[\d,]*\s?rows|vCPU|laptop)\b/i;

const TUTORIAL = [
  /in this (?:tutorial|talk i will explain)/i,
  /let'?s (?:dive|get started|learn|explore)/i,
  /step[- ]by[- ]step/i,
  /beginner'?s guide/i,
  /\bwhat is an?\b/i,
];

function lint(path: string): void {
  const text = readFileSync(path, "utf8");
  const words = text.split(/\s+/).filter(Boolean).length;
  const lines: string[] = [];
  let passed = 0;
  let last = -1;

  for (const { link, re, missing } of CHAIN) {
    const at = text.search(re);
    if (at < 0) {
      lines.push(`  x ${link}: ${missing}`);
      continue;
    }
    passed++;
    // الترتيب مهم: المشكلة قبل التجربة، والتجربة قبل الدرس
    lines.push(at < last ? `  ~ ${link}: shows up before the step it should follow` : `  ok ${link}`);
    last = at;
  }

  const numbers = text.match(NUMBER_WITH_UNIT) ?? [];
  if (numbers.length >= MIN_NUMBERS) {
    passed++;
    lines.push(`  ok numbers: ${numbers.length} with units (${numbers.slice(0, 3).join(", ")}...)`);
  } else {
    lines.push(`  x numbers: found ${numbers.length} with units, want at least ${MIN_NUMBERS}`);
  }

  if (!SETUP.test(text)) lines.push("  ~ setup: no version or data size, so nobody can repeat it");
  const phrases = TUTORIAL.flatMap((re) => text.match(re)?.[0] ?? []);
  if (phrases.length > 0) lines.push(`  ~ tutorial phrasing: ${phrases.map((p) => `"${p}"`).join(", ")}`);

  console.log(`\n${path} (${words} words) chain ${passed}/4`);
  for (const line of lines) console.log(line);
}

for (const path of process.argv.slice(2)) lint(path);

Part 2 — An article an interviewer can dig into 🔴 Advancedالجزء 2 — مقال الـ interviewer يقدر يحفر فيه

⏱ Timed prompt · 10 minutes Take your strongest published claim, or Mariam's below if you don't have one yet. Record yourself answering these aloud: What hardware was this on? How much data? What else changed between the runs? What did the fix cost on writes?
تمرين بتوقيت · 10 دقايق. خد أقوى ادعاء منشور عندك، أو بتاع مريم تحت لو لسه معندكش. سجّل نفسك وإنت بتجاوب بصوت عالي: كان على أنهي hardware؟ حجم الـ data كام؟ إيه اللي اتغير بين التشغيلتين؟ والـ fix كلّف كام على الكتابة؟
English

Model solution. Mariam's claim is about a slow per-tenant invoice query. She doesn't stop at a faster number. She runs three variants (no index, an index on the tenant alone, a composite index) at two data sizes and on two builds of Postgres 18 (a native server and PGlite, the WebAssembly one), and she measures what the index costs on writes. For how to read a plan, see 07 · EXPLAIN, scans and nodes.

Buffers are pages touched, so they don't depend on the machine's speed. That is why a post that quotes them survives "what hardware?". In Postgres 18 EXPLAIN ANALYZE includes buffer counts automatically; writing BUFFERS keeps the command working on older versions.

The four follow-ups, answered from the run below:

  • What hardware? A Windows development machine under load, PostgreSQL 18.4 and PGlite 0.5.15 (which reports Postgres 18.6), not production. So she compares buffers and treats milliseconds as indicative: both builds read the same 10 buffers at 20,000 rows.
  • How much data? 20,000 and 200,000 rows. Going ten times bigger took the no-index plan from 148 to about 1,500 buffers, while the composite index stayed at 10 to 11. That is the real claim: one grows with the table and the other doesn't.
  • What else changed? Nothing else. Same session, same data, ANALYZE first, median of five runs. She also tried the simpler index: on the tenant alone it still read 1,476 buffers, because every page holds rows from every tenant in this generated data.
  • What did the write cost? A 5,000-row insert wrote 1,156,189 bytes of WAL instead of 779,928, which is 48% more, and the index is about 6 MB next to a 12 MB table. Worth it for a read-heavy table, and she says she'd check the real write rate first.

If a number doesn't exist for you, you have three honest options: measure it, give an estimate and say how you made it, or say it wasn't measured.

Publishing. Put it on your own blog first, then cross-post to dev.to or Medium pointing back at it, so search engines treat your blog as the original. dev.to's front matter has a canonical_url field, and Google documents rel="canonical" as a strong signal of your preference. Medium's help page refused an automated check on 2026-11-09, so look up its current canonical setting yourself. dev.to's editor guide also lists an ai_disclosure_level field, which is worth filling in honestly. import { PGlite } from "@electric-sql/pglite";

// نوع صغير لنتيجة EXPLAIN بصيغة JSON: محتاجين منه الـ plan والوقت بس
type PlanNode = {
  "Node Type": string;
  "Index Name"?: string;
  "Shared Hit Blocks"?: number;
  "Shared Read Blocks"?: number;
  Plans?: PlanNode[];
};
type Explain = { Plan: PlanNode; "Execution Time": number };

const ROWS = Number(process.argv[2] ?? 20_000);
const QUERY = `select id, total_cents, created_at from invoices
               where tenant_id = 7 order by created_at desc limit 20`;

const db = new PGlite();

// بيانات خيالية: كل tenant عنده نفس عدد الفواتير تقريبًا
await db.exec(`
  create table invoices (
    id bigserial primary key,
    tenant_id int not null,
    status text not null,
    total_cents int not null,
    created_at timestamptz not null
  );
  insert into invoices (tenant_id, status, total_cents, created_at)
  select i % 50, case when i % 7 = 0 then 'overdue' else 'paid' end,
         (i * 37) % 90000, now() - (i || ' minutes')::interval
  from generate_series(1, ${ROWS}) i;
  analyze invoices;
`);

async function explain(): Promise<Explain> {
  const r = await db.query<{ "QUERY PLAN": Explain[] }>(
    `explain (analyze, buffers, format json) ${QUERY}`,
  );
  return r.rows[0]["QUERY PLAN"][0];
}

function nodes(n: PlanNode): string {

async function measure(label: string): Promise<void> {
  const runs: Explain[] = [];
  for (let i = 0; i < 5; i++) runs.push(await explain());
  const times = runs.map((r) => r["Execution Time"]).sort((a, b) => a - b);
  const last = runs[4].Plan;
  // الرقم بتاع الـ root بيشمل كل اللي تحته، فمش محتاجين نجمع يدوي
  const buffers = (last["Shared Hit Blocks"] ?? 0) + (last["Shared Read Blocks"] ?? 0);
  console.log(`${label.padEnd(16)} buffers=${String(buffers).padEnd(5)} median=${times[2].toFixed(2)} ms`);
  console.log(`  ${nodes(last)}`);
}

English

Model solution. The workflow for a first merged PR is in section 13 · 3.5. This part is about how 2–3 merged PRs read to a hiring engineer. The target and the ranking below are this curriculum's advice, not data.

  • A real bug fix beats a feature as a story: you read someone else's code, found a cause and convinced a maintainer.
  • A failing test is the proof that the bug was real and is now fixed.
  • A library you use lets you say why it mattered.
  • Merged beats open: a merged PR passed somebody else's review, and that is what your own repositories can't show.

pr-evidence.ts turns a PR record into a CV bullet and a 60-second story, and warns about weak evidence. It is a rough heuristic: it checks the fields you give it, so a lie goes straight through.

Market reality, as of 2026-01. On 2026-01-26 Daniel Stenberg announced that curl's bug bounty would stop on 2026-01-31, citing an explosion of AI slop reports. He wrote that the confirmed rate fell from above 15% to below 5% in 2025. Be careful with what this shows: it was about security reports, and he says curl had not yet seen the problem in pull requests, though other projects report it. The conclusion for you is advice: maintainers are tired of generated noise, so an AI-written PR you can't defend counts against you.

type PrRecord = {
  project: string;
  kind: "bug fix" | "feature" | "docs";
  symptom: string;
  rootCause: string;
  fix: string;
  whyItMattered: string;
  reviewLesson: string;
  issue: string | null;
  failingTest: string | null;
  linesChanged: number;
  merged: boolean;
  url: string;
  role: string;
  usedInMyWork: boolean;
  canExplainEveryLine: boolean;
};

function warnings(pr: PrRecord): string[] {
  const out: string[] = [];
  if (!pr.canExplainEveryLine) out.push("STOP: you can't explain every line, so don't list this PR");
  if (!pr.merged) out.push("not merged: it shows an attempt, so call it an open PR");
  if (pr.issue === null) out.push("no linked issue: nothing shows the problem was real");
  if (pr.failingTest === null) out.push("no failing test: how do you know it was broken and is fixed?");
  if (pr.kind !== "bug fix") out.push(`kind is "${pr.kind}": fine, but a real bug fix is a stronger story`);
  if (!pr.usedInMyWork) out.push("a library you don't use: expect 'why this project?'");
  if (pr.linesChanged > 400) out.push(`${pr.linesChanged} changed lines: hard to defend line by line`);
  return out;
}

function cvBullet(pr: PrRecord): string {
  if (!pr.merged || !pr.canExplainEveryLine) return "(no CV bullet yet)";
  const test = pr.failingTest ? " and added a regression test" : "";
  return `Fixed ${pr.symptom} in ${pr.project}${test} (merged PR: ${pr.url}).`;
}

function story(pr: PrRecord): string {
  return [
    pr.usedInMyWork ? `I use ${pr.project}, and I hit this: ${pr.symptom}.` : `I found this in ${pr.project}: ${pr.symptom}.`,
    pr.failingTest ? `I first wrote a failing test: ${pr.failingTest}.` : "I had no failing test.",
    `The cause was ${pr.rootCause}.`,
    `The fix: ${pr.fix}, ${pr.linesChanged} ${pr.linesChanged === 1 ? "line" : "lines"} changed.`,
    `It mattered because ${pr.whyItMattered}.`,
    `In review I learned ${pr.reviewLesson}.`,
    `My role: ${pr.role}. Status: ${pr.merged ? "merged" : "still open"}.`,
  ].join(" ");
}

Common mistakes · غلطات شائعة

❌ A ratio over a tiny number 
"The query is 930x faster"
18.60 ms / 0.02 ms = 930
(0.02 is rounded: 0.015 to
0.025 gives 744x to 1240x)
✅ Counts, with the setup 
"From 1,509 to 11 buffers on
200,000 rows, Postgres 18.4;
timings are rough on this box"
بالعامية

❌ "الـ query بقت أسرع 930 مرة": الرقم ده صح حسابيًا (18.60 على 0.02)، بس 0.02 دي متقرّبة لرقمين عشريين، يعني ممكن تكون أي حاجة من 0.015 لـ 0.025، والنسبة بالتالي ممكن تبقى 744 أو 1240. والمقام الصغير ده أي تذبذب بسيط بيغيّره بشكل كبير.

✅ "من 1,509 لـ 11 buffer على 200,000 صف، Postgres 18.4، والأوقات تقريبية": الـ buffers عدّ ثابت، والـ setup مكتوب، وإنت بتقول صراحةً إن الوقت تقريبي.

❌ الكود الأول بيعدّ كل حساب ظهر في الـ log، يعني إنت وحساب الـ test والـ uptime bot، فبيطلع 14. وأول حد هيسألك عدّيت إزاي هيكتشف ده.

import { PGlite } from "@electric-sql/pglite";

// التمرين 2: index بيغطي الأعمدة كلها، فالـ heap مش محتاج يتقري
const QUERY = `select id, total_cents, created_at from invoices
               where tenant_id = 7 order by created_at desc limit 20`;

type Node = { "Node Type": string; "Shared Hit Blocks"?: number; "Shared Read Blocks"?: number; "Heap Fetches"?: number; Plans?: Node[] };

const db = new PGlite();
await db.exec(`
  create table invoices (id bigserial primary key, tenant_id int not null, status text not null,
    total_cents int not null, created_at timestamptz not null);
  insert into invoices (tenant_id, status, total_cents, created_at)
  select i % 50, 'paid', (i * 37) % 90000, now() - (i || ' minutes')::interval
  from generate_series(1, 200000) i;
  create index invoices_cover on invoices (tenant_id, created_at desc) include (id, total_cents);
`);

async function show(label: string): Promise<void> {
  const r = await db.query<{ "QUERY PLAN": { Plan: Node }[] }>(`explain (analyze, buffers, format json) ${QUERY}`);
  const root = r.rows[0]["QUERY PLAN"][0].Plan;
  const scan = root.Plans?.[0] ?? root;
  const buffers = (root["Shared Hit Blocks"] ?? 0) + (root["Shared Read Blocks"] ?? 0);
  console.log(`${label.padEnd(14)} ${scan["Node Type"]}  buffers=${buffers}  heap fetches=${scan["Heap Fetches"] ?? "-"}`);
}

// الـ Index Only Scan محتاج visibility map، والـ vacuum هو اللي بيبنيها
await db.exec("vacuum invoices");
await show("after vacuum");
await db.close();

Cheat sheet · الخلاصة

  • Each public item is evidence: can a stranger dig into it for 10 minutes, and can you still answer?
  • Three real articles beat ten thin ones; 6–10 is the curriculum's opinion.
  • The chain: real problem → experiment → numbers → lesson. article-lint.ts checks shape, not truth.
  • Quote buffers and data size; treat milliseconds as rough and say so.
  • Always show the cost: WAL, index size, what you'd check next.
  • Own blog first, then cross-post with a canonical URL (dev.to canonical_url).
  • Bug fix with a failing test > feature; merged > open; can't defend a line = don't list it.
  • One talk from one article: recording, a CV line, and a 5-minute version.
  • "Used" needs a definition: exclude yourself and bots, count real actions, say the real number.
  • Same title and dates everywhere; every claim opens on something; one thread.
بالعامية
  • كل حاجة منشورة دليل: غريب يقدر يحفر فيها 10 دقايق، وإنت لسه عندك إجابة؟
  • 3 مقالات حقيقية أحسن من 10 خفاف، و6–10 ده رأي المنهج.
  • السلسلة: مشكلة حقيقية ← تجربة ← أرقام ← درس. وarticle-lint.ts بيفحص الشكل مش الحقيقة.
  • قول الـ buffers وحجم الـ data، والـ ms قولها تقريبًا وقول إنها كده.
  • وري التكلفة دايمًا: الـ WAL، حجم الـ index، وهتراجع إيه بعد كده.
  • الـ blog بتاعك الأول، وبعدين انشر نسخة بـ canonical URL (canonical_url على dev.to).
  • bug fix بـ test فاشل أحسن من feature، والمقبول أحسن من المفتوح، وسطر مش قادر تدافع عنه متحطوش.
  • talk واحد من مقال واحد: تسجيل، وسطر CV، ونسخة 5 دقايق.
  • "مستخدم" محتاجة تعريف: شيل نفسك والـ bots، وعدّ الـ actions الحقيقية، وقول الرقم الحقيقي.
  • نفس العنوان والتواريخ في كل مكان، وكل ادعاء بيفتح على حاجة، وخيط واحد.
