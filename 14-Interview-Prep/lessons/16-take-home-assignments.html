Why this matters · ليه ده مهم

English

A take-home is the interview format closest to the real job, and it's the one where a Mid-level engineer can look Senior or look careless with the same amount of code. The reviewer reads your scope decisions, your error handling and your README before they read your cleverness. Then, in the follow-up, they ask why you did each thing.

This lesson builds one small service for real, in the time a brief suggests, then writes it up and defends it with numbers. The same service doubles as README artifact 7, a take-home sample you can reuse.

Part 1 — Read the brief, cut the scope 🟡 Intermediateالجزء 1 — اقرا الـ brief وقص الـ scope

English

⏱ Timed prompt, 20 minutes. Read the fictional brief below. On paper, write your assumptions, the questions you'd send, and three lists: must, one extra, not doing. Give each item a time estimate. Stop at 20 minutes.

Model solution. Assumptions in writing come first, because the reviewer can only judge what they can see. Questions go to the recruiter early, and you keep working while you wait. The three lists are the real work: must covers the brief done properly, one extra shows your level, and not doing proves you made a decision instead of forgetting.

The AI policy. Check it before you write code and follow it. If the brief doesn't say, ask. As one public example, Datadog's AI guidelines (last updated May 13, 2026, read 2026-11-09) say that a take-home "should reflect your original conclusions and perspectives", that you "should expect to answer questions live based on your work", and that you shouldn't include ideas you wouldn't be comfortable explaining. Other companies set other rules, so read yours.

A common pairing today is a take-home followed by a live walkthrough, so build as if someone will open any file and ask about it. That's advice from how these rounds usually run, and you should ask each company what its process is.

The brute force is "do everything I can think of". The check below shows what that costs: 660 minutes planned for a 240-minute brief. The check itself is a linear pass over the items.

import { readFileSync } from "node:fs";
import { basename, resolve } from "node:path";

export interface Item {
  name: string;
  minutes: number;
}

export interface Scope {
  suggestedMinutes: number;
  assumptions: string[];
  questions: string[];
  aiPolicy: string;
  must: Item[];
  extra: Item[];
  notDoing: string[];
}

const sum = (items: Item[]) => items.reduce((a, i) => a + i.minutes, 0);

export function checkScope(s: Scope): string[] {
  const problems: string[] = [];
  if (s.must.length === 0) problems.push("must list is empty");
  if (s.extra.length !== 1) problems.push(`one extra allowed, found ${s.extra.length}`);
  if (s.assumptions.length === 0) problems.push("no written assumptions");
  if (s.questions.length === 0) problems.push("no questions to send");
  if (s.notDoing.length === 0) problems.push("not-doing list is empty: nothing was cut");
  if (s.aiPolicy.trim() === "") problems.push("AI policy not checked");
  const planned = sum(s.must) + sum(s.extra);
  if (planned > s.suggestedMinutes) problems.push(`planned ${planned} min against ${s.suggestedMinutes} suggested (${Math.round((planned / s.suggestedMinutes) * 100)}%)`);
  for (const i of [...s.must, ...s.extra]) {
    if (!Number.isInteger(i.minutes) || i.minutes <= 0) problems.push(`${i.name}: minutes must be a positive integer`);
  }
  return problems;
}

if (process.argv[1] && import.meta.filename === resolve(process.argv[1])) {
  for (const f of process.argv.slice(2)) {

    const problems = checkScope(s);
    console.log(`${basename(f)}: must ${sum(s.must)} min + extra ${sum(s.extra)} min of ${s.suggestedMinutes} suggested, ${problems.length} problem(s)`);
    for (const p of problems) console.log(`  - ${p}`);
  }
}

Part 2 — Production-shaped and small 🟡 Intermediateالجزء 2 — شكل production وحجم صغير

English

⏱ Timed prompt, inside the full build. Implement the core: POST /exports, GET /exports/:id and a download, in 65 + 45 + 20 minutes. Attempt it before reading.

Model solution. Fastify 5.12 and Zod 4, Postgres through PGlite so the reviewer needs no database, CSV streamed with backpressure, validation, one error format, tenant isolation and an idempotent create. See Fastify in depth, testing Node services and errors and shutdown for the framework details. Here is what makes it read as production work:

  • The create is idempotent. A unique index on (tenant_id, idempotency_key) with ON CONFLICT DO NOTHING, so the database decides races. A replay returns the same id; the same key with a different body is a 409.
  • Tenant isolation lives in the query. Every read filters on tenant_id inside the SQL. Another tenant gets a 404, not a 403, so the API doesn't confirm that an id exists.
  • One error format. Validation, business errors, unknown routes and crashes all return { error: { code, message, requestId } }. A crash logs the real error and shows the caller a generic message.
  • The export is a job. POST records it, a worker claims it, and the status endpoint reports it. Tests call worker.idle() instead of sleeping.

Complexity first. The brute force loads every row, then writes: O(n) time and O(n) memory. Paging with OFFSET fixes the memory but reads every skipped row again, which is O(n²/page). Keyset paging is O(n) time and O(page) memory. The measurements below count the rows the database actually read, using EXPLAIN ANALYZE.

export function textField(value: string): string {
  const safe = FORMULA_START.test(value) ? `'${value}` : value;
  return NEEDS_QUOTES.test(safe) ? `"${safe.replaceAll('"', '""')}"` : safe;
}

export function toCsvLine(row: InvoiceRow): string {
  return `${textField(row.number)},${textField(row.customer)},${row.total_cents},${textField(row.issued_at)}\n`;
}

// الـ INSERT بـ ON CONFLICT DO NOTHING: الاتنين طلبات المتزامنين مفيش غير واحد فيهم يكسب
export async function createExport(db: PGlite, req: CreateRequest): Promise<{ record: ExportRecord; replayed: boolean }> {
  const hash = createHash("sha256").update(`${req.from}|${req.to}`).digest("hex");
  const inserted = await db.query<ExportRecord>(
    `INSERT INTO exports (id, tenant_id, idempotency_key, request_hash, range_from, range_to)
     VALUES ($1, $2, $3, $4, $5, $6)
     ON CONFLICT (tenant_id, idempotency_key) DO NOTHING
     RETURNING ${COLUMNS}`,
    [randomUUID(), req.tenantId, req.idempotencyKey, hash, req.from, req.to],
  );
  if (inserted.rows[0]) return { record: inserted.rows[0], replayed: false };

  const existing = await db.query<ExportRecord>(
    `SELECT ${COLUMNS} FROM exports WHERE tenant_id = $1 AND idempotency_key = $2`,
    [req.tenantId, req.idempotencyKey],
  );
  const record = existing.rows[0];
  if (record.request_hash !== hash) {
    throw new ApiError(409, "idempotency_key_reused", "This Idempotency-Key was already used with a different request");
  }
  return { record, replayed: true };
}

// شرط الـ tenant جوه الـ query نفسها: تصير 404 مش 403 عشان متكشفش إن الـ id موجود
export async function getExport(db: PGlite, tenantId: string, id: string): Promise<ExportRecord> {
  const { rows } = await db.query<ExportRecord>(`SELECT ${COLUMNS} FROM exports WHERE id = $1 AND tenant_id = $2`, [id, tenantId]);
  if (!rows[0]) throw new ApiError(404, "export_not_found", "No such export");
  return rows[0];
}

// تحذير: الـ ORDER BY لازم يبقى باسم الجدول، وإلا بيرتّب على الـ alias النصي
export async function* invoiceRows(db: PGlite, tenantId: string, from: string, to: string, pageSize = 500): AsyncGenerator<InvoiceRow> {
  let cursor: { issuedAt: string; id: string } | null = null;
  for (;;) {
    const after: string = cursor ? "AND (issued_at, id) > ($4::timestamptz, $5::bigint)" : "";
    const params: unknown[] = cursor ? [tenantId, from, to, cursor.issuedAt, cursor.id, pageSize] : [tenantId, from, to, pageSize];
    const limit: string = cursor ? "$6" : "$4";
    const page: { rows: InvoiceRow[] } = await db.query<InvoiceRow>(
      `SELECT id::text AS id, number, customer, total_cents::text AS total_cents, issued_at::text AS issued_at
       FROM invoices
       WHERE tenant_id = $1 AND issued_at >= $2::date AND issued_at < $3::date ${after}
       ORDER BY invoices.issued_at, invoices.id
       LIMIT ${limit}`,
      params,
    );
    yield* page.rows;
    if (page.rows.length < pageSize) return;
    const last: InvoiceRow = page.rows[page.rows.length - 1];
    cursor = { issuedAt: last.issued_at, id: last.id };
  }
}

  #running: Promise<void> | null = null;
  #stopping = false;

  constructor(db: PGlite, dir: string, onFinish: (status: "done" | "failed") => void = () => {}) {
    this.#db = db;
    this.#dir = dir;
    this.#onFinish = onFinish;
  }

  // بعد crash: أي job كان running بيرجع queued، ده آمن لأن عندنا instance واحد
  async requeueInterrupted(): Promise<number> {
    const r = await this.#db.query("UPDATE exports SET status = 'queued' WHERE status = 'running' RETURNING id");
    return r.rows.length;
  }

  kick(): void {
    if (this.#stopping) return;
    this.#running ??= this.#drain().finally(() => {
      this.#running = null;
    });
  }

  async idle(): Promise<void> {
    while (this.#running) await this.#running;
  }

  async stop(): Promise<void> {
    this.#stopping = true;
    await this.idle();
  }

  async #claim(): Promise<ClaimedJob | undefined> {
    // الـ SKIP LOCKED مش فارق مع worker واحد، بس بيخلّي نفس الـ SQL يشتغل مع كذا worker
    const { rows } = await this.#db.query<ClaimedJob>(
      `UPDATE exports SET status = 'running'
       WHERE id = (SELECT id FROM exports WHERE status = 'queued' ORDER BY created_at, id LIMIT 1 FOR UPDATE SKIP LOCKED)
       RETURNING id, tenant_id, range_from::text AS range_from, range_to::text AS range_to`,
    );
    return rows[0];
  }

  async #drain(): Promise<void> {
    for (;;) {
      if (this.#stopping) return;
      const job = await this.#claim();
      if (!job) return;
      await this.#run(job);
    }
  }

  async #run(job: ClaimedJob): Promise<void> {
    const fileName = `${job.id}.csv`;
    const tmp = join(this.#dir, `${fileName}.tmp`);
    let rowCount = 0;
    async function* counted(rows: AsyncIterable<InvoiceRow>): AsyncGenerator<InvoiceRow> {
      for await (const row of rows) {
        rowCount++;
        yield row;
      }
    }
    try {
      // الـ pipeline بيستنى drain لوحده، فالـ memory ثابتة مهما كان عدد الصفوف
      await pipeline(csvLines(counted(invoiceRows(this.#db, job.tenant_id, job.range_from, job.range_to))), createWriteStream(tmp));
      await rename(tmp, join(this.#dir, fileName));
      await this.#db.query("UPDATE exports SET status = 'done', row_count = $2, file_name = $3 WHERE id = $1", [job.id, rowCount, fileName]);
      this.#onFinish("done");
    } catch (err) {
      await rm(tmp, { force: true });
      const code = err instanceof Error && "code" in err ? String(err.code) : "export_failed";
      await this.#db.query("UPDATE exports SET status = 'failed', error_code = $2 WHERE id = $1", [job.id, code]);
      this.#onFinish("failed");
    }
  }
}

  const r = schema.safeParse(value);

    return leaves(r.rows[0]["QUERY PLAN"][0].Plan);

# ADR-0001: Generate the CSV in a background worker, to local disk

- **Date:** 2026-11-09
- **Status:** Accepted
- **Deciders:** the author of this take-home

## Context

Exports can reach a few hundred thousand rows. A request held open for that long ties up a connection and dies with any deploy. The brief suggests 4 hours and one instance is enough for the exercise.

## Options considered

### Option 1: stream the CSV directly from the request

- Pros: no job table, no worker.
- Cons: a client disconnect loses the work, and there is no status to poll, which the brief asks for.

### Option 2: background worker writing to local disk

- Pros: survives a client disconnect, fits the status endpoint, small to build.
- Cons: tied to one instance, because the file is on that machine's disk.

### Option 3: broker queue and object storage

- Pros: the right shape for several instances.
- Cons: two more systems to run and to review, for no gain inside this brief.

## Decision

Option 2. The status endpoint is a requirement, and it fits in the time. Pages are read by keyset, because OFFSET read x4 more rows per doubling when measured.

## Consequences

- **Good:** memory stays flat, and the API answers while an export runs.
- **Accepted:** one instance only, and an interrupted job restarts from the beginning.
- **We revisit this if:** a second instance is needed, or exports pass a few million rows.

import { Counter, Histogram, Registry } from "@prometheus-io/client";

export interface Metrics {
  registry: Registry;
  observe(method: string, route: string, status: number, seconds: number): void;
  exportFinished(status: "done" | "failed"): void;
}

export function createMetrics(): Metrics {
  const registry = new Registry();
  const requests = new Counter({
    name: "http_requests_total",
    help: "HTTP requests by method, route template and status",
    labelNames: ["method", "route", "status"] as const,
    registers: [registry],
  });
  const duration = new Histogram({
    name: "http_request_duration_seconds",
    help: "HTTP request duration by route template",
    labelNames: ["method", "route"] as const,
    buckets: [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5],
    registers: [registry],
  });
  const exports = new Counter({
    name: "exports_finished_total",
    help: "Finished exports by outcome",
    labelNames: ["status"] as const,
    registers: [registry],
  });
  return {
    registry,
    observe(method, route, status, seconds) {
      requests.inc({ method, route, status: String(status) });
      duration.observe({ method, route }, seconds);
    },
    exportFinished(status) {
      exports.inc({ status });
    },
  };
}

import { Counter, Registry } from "@prometheus-io/client";

async function seriesCount(labelOf: (id: number) => string, requests: number): Promise<number> {
  const registry = new Registry();
  const counter = new Counter({ name: "http_requests_total", help: "requests", labelNames: ["route"] as const, registers: [registry] });

  const text = await registry.metrics();
  return text.split("\n").filter((l) => l.startsWith("http_requests_total{")).length;
}

Part 5 — Stop on time 🟡 Intermediateالجزء 5 — وقّف في وقتك

English

⏱ Timed by nature. Write the plan per phase before you start, log the actual minutes at the end of each phase, and stop when the time is up.

Model solution. The brute force is watching only the total. The fictional log below ends at 245 of 240 minutes, 102%, and looks fine. Per phase, it shows the core taking 154% of its plan, and that's what ate the tests. A check per phase flags anything past 110%, using integers (actual * 100 > plan * 110) so that exactly 110% isn't flagged by rounding.

Write the "with more time" section as you go, because every feature you cut is a line in it. When you run out of time, stop and write what's unfinished. Going four hours over and saying nothing misleads the reviewer about how long the work takes.

It's fair to ask how long a take-home is meant to take, and to ask for a smaller version or to decline one that's oversized. That is advice, and whether you can afford to say no depends on your situation.

import { resolve } from "node:path";

export interface Phase {
  name: string;
  plan: number;
  actual: number;
}

export interface PhaseResult extends Phase {
  percent: number;
  over: boolean;
}

export function analyse(phases: Phase[]): { rows: PhaseResult[]; plan: number; actual: number } {
  const rows = phases.map((p) => {
    if (p.plan <= 0) throw new RangeError(`${p.name}: plan must be above 0, got ${p.plan}`);
    // مقارنة أعداد صحيحة: actual * 100 ضد plan * 110 عشان مفيش float
    return { ...p, percent: Math.round((p.actual / p.plan) * 100), over: p.actual * 100 > p.plan * 110 };
  });
  return { rows, plan: phases.reduce((a, p) => a + p.plan, 0), actual: phases.reduce((a, p) => a + p.actual, 0) };
}

Part 6 — Defend it 🟡 Intermediateالجزء 6 — دافع عنه

English

⏱ Timed prompt, 10 minutes (the drill for this session). Without notes, out loud and recorded: for three decisions in this service, answer "why this?". Then answer "how would you scale it?" and name what breaks first. Then read on.

Model solution. A defence has four parts: the choice, the alternative you rejected, a number or a constraint, and what would change your mind. Numbers beat opinions, so measure. The load test below uses autocannon 9.0.0 against the service on port 0, with a seeded table of 200,000 rows, 20 connections and 3 seconds per scenario. These numbers come from PGlite on a loaded Windows machine: treat them as relative, not as capacity.

What breaks first, in order.

  1. The database. A route with one query drops from ≈25,000 req/s to ≈3,500 req/s, so the database is the limit, not Fastify. PGlite is a single connection in the same thread. On real Postgres the limit is the pool: pg defaults to 10 connections, so a 2 ms query caps near 10 / 0.002 = 5,000 queries a second by Little's law. That's arithmetic, not a measurement on Postgres.
  2. One process. The ≈25,000 req/s on /healthz is one event loop's ceiling, and it's a ceiling for all routes combined. Past that you add processes behind a load balancer.
  3. A slow export. While a 200,000-row export ran, the status route fell from ≈3,500 to ≈2,500 req/s, because the worker and the requests share one thread and one connection. The worker also runs one export at a time, so a second tenant's export waits behind the first. That's the first thing to move out: a separate worker process with its own connection.

Scaling path: run the worker as its own process, move files to object storage so any instance can serve them, then add API processes behind a load balancer with a real connection pool. Each step has a trigger, and you don't take a step before its trigger.

 now:   [ Fastify + worker + PGlite ]  one process, one thread
                 |
 step 1 [ Fastify ]   [ worker ]        separate processes, real Postgres
                 |        |
 step 2 [ Fastify ] x N   [ worker ] x M   files on object storage
                 |
 step 3 add queue broker + lease, per-tenant limits

"إزاي تعملها scale لعشر tenants بيعملوا export في نفس الوقت؟". إجابة نموذجية: "الأول أقيس واحد، وقست فعلًا: 200 ألف صف في حوالي 3.8 ثانية على PGlite هنا. الـ export بيشتغل واحد واحد، فالـ queue اللي وراه هو اللي بيوجع. هنقل الـ worker لـ process لوحده بـ connection لوحدها، وأحط حد للـ exports الشغالة لكل tenant عشان tenant واحد ميحجزش كل الـ slots، وبعدها بس أفكر في object storage. وهتابع الـ queue depth ومدة الـ export عشان أقرر".

Common mistakes · غلطات شائعة

❌ WHERE id = $1 
// ❌ أي tenant يعرف الـ id يقدر يقرا الـ export
const { rows } = await db.query(
  "SELECT * FROM exports WHERE id = $1",
  [id],
);
✅ Tenant inside the query 
// ✅ الـ tenant جوه الشرط، وفرق الصلاحية يبان 404
const { rows } = await db.query(
  "SELECT * FROM exports WHERE id = $1 AND tenant_id = $2",
  [id, tenantId],
);
بالعامية

الـ ❌ مفيهاش tenant، فأي tenant معاه id يقرا export غيره (IDOR). الـ ✅ الـ tenant جوه الـ query، والنتيجة الفاضية بتطلع 404 فمبتأكدش إن الـ id موجود.

❌ Load everything, then write 
// ❌ كل الصفوف في الـ memory والـ string كله في الآخر
const { rows } = await db.query(`SELECT * FROM invoices WHERE tenant_id = $1`, [t]);
await writeFile(path, rows.map(toCsvLine).join(""));
✅ Keyset pages through pipeline 
// ⁦✅ 500⁩ صف في الـ memory، و pipeline بيستنى الـ drain
await pipeline(csvLines(invoiceRows(db, t, from, to)), createWriteStream(tmp));
بالعامية

الـ ❌ ماسك n صف في الـ memory والملف الكامل كنص، و export كبير يوقّع الـ process. الـ ✅ 500 صف بس في كل لحظة، والـ pipeline بيوقف المصدر لما الديسك يبطأ.

❌ Label by raw URL 
// ❌ كل id بيعمل time series جديدة
requests.inc({ route: req.url, status });
✅ Label by route template 
// ✅ الـ template ثابت مهما كان عدد الـ ids
requests.inc({ route: req.routeOptions.url ?? "unmatched", status });
بالعامية

الـ ❌ مع 4000 id طلعت 4000 series (قسناها). الـ ✅ series واحدة، و"unmatched" للـ 404 عشان متبقاش undefined.

❌ Trust the incoming request id 
// ❌ أي string من برّه بيدخل الـ logs، وفيه log injection
genReqId: (raw) => String(raw.headers["x-request-id"]);
✅ Validate, or generate 
// ✅ نقبل الشكل السليم بس، وغيره نولّد UUID جديد
const ok = typeof id === "string" && /^[A-Za-z0-9-]{8,64}$/.test(id);
return ok ? id : randomUUID();
بالعامية

الـ ❌ لو الـ header فيه سطر جديد، الـ logs بتتزوّر. الـ ✅ بنقبل الشكل السليم بس، وغيره بناخد UUID جديد. والـ test بيتأكد إن evil\ninjected اتبدّل.

Solution · الحل 
// حل التمرين: حد أقصى للـ exports الشغالة لكل tenant
import type { PGlite } from "./app/src/db.ts";
import { ApiError } from "./app/src/errors.ts";

export async function assertUnderLimit(db: PGlite, tenantId: string, max = 3): Promise<void> {
  const { rows } = await db.query<{ active: number }>(
    "SELECT count(*)::int AS active FROM exports WHERE tenant_id = $1 AND status IN ('queued', 'running')",
    [tenantId],
  );
  if (rows[0].active >= max) {
    throw new ApiError(429, "too_many_exports", `At most ${max} active exports per tenant`);
  }
}
test("happy path: under the limit passes", async () => {
  await addExport("a", "k1", "queued");
  await assertUnderLimit(db, "a");
});

✔ edge: at the limit is 429 with the error code (2.0584ms)
✔ edge: done and failed exports do not count, other tenants do not count (1.4136ms)
ℹ tests 3
ℹ pass 3
ℹ fail 0
ℹ duration_ms 1096.1048

Cheat sheet · الخلاصة

  • Spend the first 20 minutes on assumptions, questions and three lists: must, one extra, not doing.
  • Read the AI policy first. Whatever it allows, you must be able to explain every line.
  • Production-shaped and small: validation, one error format, tenant in every query, idempotent create, streamed data, tests.
  • Keyset paging is O(n) reads and O(page) memory. OFFSET is O(n²/page) reads. Loading everything is O(n) memory.
  • Sort by real columns, not by a text alias with the same name. Measure, it catches this.
  • README: what and why, 3 commands, what's built, decisions, tests, with more time.
  • One real ADR is enough. Say what you rejected.
  • Docker unverified on your own machine isn't done: run it, or say that you didn't.
  • One finished extra beats ten half-done. Label metrics by route, never by raw URL.
  • Log plan against actual per phase. Flag anything past 110%.
  • Defend with a choice, a rejected option, a number, and what would change your mind.
بالعامية
  • أول 20 دقيقة: افتراضات وأسئلة و3 قوايم: must، حاجة واحدة زيادة، not doing.
  • اقرا سياسة الـ AI الأول، وأيًا كان المسموح لازم تقدر تشرح كل سطر.
  • شكل production وحجم صغير: validation، error format واحد، tenant في كل query، create متكرر بأمان، data متدفقة، tests.
  • الـ keyset قراية O(n) و memory O(page). الـ OFFSET قراية O(n²/page). تحميل كله O(n) memory.
  • رتّب بالأعمدة الحقيقية مش بـ alias نصي بنفس الاسم. والقياس هو اللي يمسك ده.
  • الـ README: إيه وليه، 3 أوامر، إيه المعمول، القرارات، الـ tests، ولو فيه وقت أكتر.
  • ADR واحد حقيقي كفاية، وقول إيه اللي رفضته.
  • الـ Docker اللي متجربش على جهازك مش خلصان: شغّله أو قول إنك مشغلتوش.
  • حاجة واحدة زيادة خلصانة أحسن من 10 نص-نص. والـ metrics labels بالـ route مش بالـ URL الخام.
  • سجّل المخطط ضد الفعلي لكل مرحلة، وعلّم أي حاجة عدّت 110%.
  • دافع باختيار وبديل مرفوض ورقم وإيه اللي يغيّر رأيك.
