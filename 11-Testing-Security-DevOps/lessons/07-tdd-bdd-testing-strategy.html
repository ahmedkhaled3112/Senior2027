Why this matters · ليه ده مهم

English

Writing tests is a skill you already have. Deciding which tests a team writes, in what order, and how much they cost is the part that makes someone senior. TDD changes the design of the code you are writing, BDD is a tool that is usually misapplied, and fakes on ports decide whether your suite runs in 40 ms or in minutes. A testing strategy that lives in a document and is enforced by a script is what stops a team from drifting into 400 slow E2E tests nobody trusts. Every technique below ran on this machine against real code, so the numbers are from runs and not from opinion.

بالعامية

إنك تكتب test دي حاجة إنت عارفها خلاص. اللي بيفرّق السنيور هو إنه يقرر الفريق يكتب tests إيه، وبأي ترتيب، وبتكلّف كام. الـ TDD بيغيّر الـ design بتاع الكود اللي بتكتبه، والـ BDD أداة أغلب الناس بتستخدمها في المكان الغلط، والـ fakes على الـ ports هي اللي بتحدد الـ suite بتاعتك هتخلص في 40 ms ولا في دقايق. والـ testing strategy المكتوبة في document ومتراقبة بـ script هي اللي بتمنع الفريق إنه يلاقي نفسه عنده 400 E2E بطيئين ومحدش مصدّقهم. كل حاجة تحت اتشغّلت فعلًا على الجهاز ده على كود حقيقي، فالأرقام جاية من runs مش من رأي.

Part 1 — Red, green, refactor 🟡 Intermediateالجزء 1 — red و green و refactor

English

TDD is a short loop with three steps. Red: write one small test for behaviour that does not exist and watch it fail for the right reason. Green: write the least code that passes, even if it looks embarrassing. Refactor: with the tests green, improve names and structure without changing behaviour. Seeing red matters because a test that has never failed has not proved it can fail.

We will build a RefundPolicy in four cycles: a basic window, the boundary at day 14, partial refunds, and order status. The third cycle is the point of the exercise. The product asks "tell the customer why it was refused and how much is left", and a boolean cannot carry that. The test is the first caller of the function, so the test is what forces the signature to change. That design pressure is the main benefit of TDD; the safety net is the side effect.

        +---------------------------------------------+
        |                                             |
        v                                             |
   +---------+  fails for   +---------+  least code  +----------+
   |   RED   |  the right   |  GREEN  |  that passes | REFACTOR |
   |one test |  reason ---->|  code   |------------->| no new   |
   +---------+              +---------+              | behaviour|
                                                     +----------+
   Cycle 1: canRefund -> true           (constant is fine)
   Cycle 2: boundary day 14 / day 15    (forces the real rule)
   Cycle 3: partial + reason            (forces a NEW SIGNATURE)
   Cycle 4: status: paid/shipped        (then refactor, tests untouched)
الدايرة: test واحد بيفشل للسبب الصح (RED)، بعدين أقل كود يعدّيه (GREEN)، بعدين تحسين من غير سلوك جديد (REFACTOR)، وترجع تاني. والدورات الأربعة: الأولى true ثابتة ومقبولة، التانية الحد عند يوم 14 ويوم 15 بيجبرك تكتب القاعدة الحقيقية، التالتة الـ partial والسبب بيجبروك على signature جديدة، والرابعة الـ status وبعدها refactor من غير ما تلمس الـ tests.

الدورة 3: الـ test اللي غيّر الـ signature. الـ product عايز partial refund، وعايز يقول للعميل ليه اترفض وفاضل كام. مفيش boolean هيقدر يقول ده، فاكتب الـ test بالشكل اللي إنت نفسك تنادي بيه الـ function.

import { expect, it } from "vitest";
import { decideRefund, type RefundableOrder } from "./refund-policy.ts";

const DAY = 86_400_000;
const deliveredAt = new Date("2026-11-01T10:00:00Z");
const after = (days: number) => new Date(deliveredAt.getTime() + days * DAY);
const order = (over: Partial<RefundableOrder> = {}): RefundableOrder => ({
  totalMinor: 10_000, refundedMinor: 0, deliveredAt, ...over,
});

it("approves a partial refund inside the window", () => {
  expect(decideRefund(order(), { amountMinor: 3_000 }, after(3)))
    .toEqual({ kind: "approved", amountMinor: 3_000 });
});

it("rejects after the window and says why", () => {
  expect(decideRefund(order(), { amountMinor: 1_000 }, after(15)))
    .toEqual({ kind: "rejected", reason: "WINDOW_EXPIRED" });
});

// السطر ده هو اللي كسر الـ boolean: محتاج أقول فاضل كام
it("rejects more than what is left and reports the remainder", () => {
  expect(decideRefund(order({ refundedMinor: 8_000 }), { amountMinor: 3_000 }, after(3)))
    .toEqual({ kind: "rejected", reason: "EXCEEDS_REMAINING", remainingMinor: 2_000 });
});
const WINDOW_MS = 14 * 86_400_000;

export type RefundableOrder = { totalMinor: number; refundedMinor: number; deliveredAt: Date };

// الـ test طلب "ليه رفضت؟" و"فاضل كام؟"، فالـ boolean بقى union
export type RefundDecision =
  | { kind: "approved"; amountMinor: number }
  | { kind: "rejected"; reason: "WINDOW_EXPIRED" }
  | { kind: "rejected"; reason: "EXCEEDS_REMAINING"; remainingMinor: number };

export function decideRefund(
  order: RefundableOrder,
  request: { amountMinor: number },
  now: Date,
): RefundDecision {
  if (now.getTime() - order.deliveredAt.getTime() > WINDOW_MS) {
    return { kind: "rejected", reason: "WINDOW_EXPIRED" };
  }
  const remainingMinor = order.totalMinor - order.refundedMinor;
  if (request.amountMinor > remainingMinor) {
    return { kind: "rejected", reason: "EXCEEDS_REMAINING", remainingMinor };
  }
  return { kind: "approved", amountMinor: request.amountMinor };
}

import { describe, expect, it } from "vitest";
import { decideRefund, type RefundableOrder } from "./refund-policy.ts";

const DAY = 86_400_000;
const deliveredAt = new Date("2026-11-01T10:00:00Z");
const after = (days: number) => new Date(deliveredAt.getTime() + days * DAY);

      .toEqual({ kind: "rejected", reason: "WINDOW_EXPIRED" });
  });
  it("rejects more than what is left and reports the remainder", () => {
    expect(decideRefund(delivered({ refundedMinor: 8_000 }), { amountMinor: 3_000 }, after(3)))
      .toEqual({ kind: "rejected", reason: "EXCEEDS_REMAINING", remainingMinor: 2_000 });
  });
});

// الجديد في الدورة دي: الـ status بقى جزء من القرار
describe("orders not delivered yet", () => {
  it("rejects while the parcel is in transit", () => {
    const order: RefundableOrder = { status: "shipped", totalMinor: 10_000, refundedMinor: 0 };
    expect(decideRefund(order, { amountMinor: 1_000 }, after(1)))
      .toEqual({ kind: "rejected", reason: "IN_TRANSIT" });
  });
  it("approves a paid order that never shipped, with no time limit", () => {
    const order: RefundableOrder = { status: "paid", totalMinor: 10_000, refundedMinor: 0 };
    expect(decideRefund(order, { amountMinor: 10_000 }, after(90)))
      .toEqual({ kind: "approved", amountMinor: 10_000 });
  });
});
const WINDOW_MS = 14 * 86_400_000;

type Money = { totalMinor: number; refundedMinor: number };
export type RefundableOrder =
  | (Money & { status: "paid" | "shipped" })
  | (Money & { status: "delivered"; deliveredAt: Date });

export type RefundDecision =
  | { kind: "approved"; amountMinor: number }
  | { kind: "rejected"; reason: "WINDOW_EXPIRED" | "IN_TRANSIT" }
  | { kind: "rejected"; reason: "EXCEEDS_REMAINING"; remainingMinor: number };

type Rejection = Extract<RefundDecision, { kind: "rejected" }>;

// الـ refactor: كل قاعدة بقت function صغيرة بترجع رفض أو null
function statusRule(order: RefundableOrder, now: Date): Rejection | null {
  if (order.status === "shipped") return { kind: "rejected", reason: "IN_TRANSIT" };
  if (order.status !== "delivered") return null;
  const expired = now.getTime() - order.deliveredAt.getTime() > WINDOW_MS;
  return expired ? { kind: "rejected", reason: "WINDOW_EXPIRED" } : null;
}

function amountRule(order: Money, amountMinor: number): Rejection | null {
  const remainingMinor = order.totalMinor - order.refundedMinor;
  return amountMinor > remainingMinor
    ? { kind: "rejected", reason: "EXCEEDS_REMAINING", remainingMinor }
    : null;
}

export function decideRefund(
  order: RefundableOrder,
  { amountMinor }: { amountMinor: number },
  now: Date,
): RefundDecision {
  return statusRule(order, now) ?? amountRule(order, amountMinor) ?? { kind: "approved", amountMinor };
}

الـ TDD دورة قصيرة من 3 خطوات. Red: تكتب test صغير واحد لسلوك مش موجود، وتشوفه بيقع للسبب الصح. Green: تكتب أقل كود يعدّيه حتى لو شكله وحش. Refactor: والـ tests خضرا، تحسّن الأسماء والبنية من غير ما تغيّر السلوك. لازم تشوف الأحمر، لأن test عمره ما وقع لسه ماثبتش إنه يقدر يقع.

بنينا RefundPolicy في 4 دورات: window أساسي، الحد عند يوم 14، partial refund، والـ status. الدورة التالتة هي المقصد كله: الـ product قال "قول للعميل ليه اترفض وفاضل كام"، والـ boolean مايقدرش يشيل ده. الـ test هو أول caller للـ function، فهو اللي أجبر الـ signature تتغيّر من canRefund(): boolean لـ decideRefund(): RefundDecision. الضغط ده على الـ design هو الفايدة الأساسية من الـ TDD، وشبكة الأمان ييجي معاها كـ bonus.

والغلطة الشائعة: تكتب الـ implementation الأول وبعدين الـ test وتسميه TDD. ساعتها مش هتشوف أحمر، ومش هتعرف إن الـ test بيمسك فعلًا، ومش هيأثر في الـ design لأن الـ signature اتحددت خلاص.

فين هستخدمه في شغلي؟ لما تيجيلك task "نضيف partial refund في POST /orders/:id/refund": قبل ما تفتح الـ controller، اكتب في refund-policy.test.ts كل قاعدة في test واحد (الـ window، الحد، المبلغ المتبقي، الـ status). هتكتشف من الأول إن الـ endpoint لازم يرجّع reason بدل 400 فاضية، وده اللي هيتكتب في الـ OpenAPI ويتبعت لفريق الـ frontend. الكود بعد كده function خالصة، والـ controller سطرين.
Trade-off: how small is a cycle? A cycle of a few minutes keeps you honest; a cycle of an hour means the test was too big and you are writing the design in your head again. The cost: TDD rewrites tests while the API is still moving (we rewrote two tests in cycle 3). That is cheap early and expensive if you wrote fifty tests before asking the signature question.
الدورة اللي بتاخد كام دقيقة بتفضّلك أمين؛ لو أخدت ساعة يبقى الـ test كان كبير وإنت رجعت تعمل الـ design في دماغك. التكلفة: الـ TDD بيخليك تعيد كتابة tests طول ما الـ API بيتغيّر (إحنا أعدنا كتابة 2 tests في الدورة التالتة). ده رخيص في الأول، وغالي لو كتبت 50 test قبل ما تسأل سؤال الـ signature.

Part 2 — When TDD pays and when it doesn't 🟡 Intermediateالجزء 2 — إمتى الـ TDD يستاهل وإمتى لأ

English

TDD pays where the expected result is knowable before you write the code: business rules, a new public API, and bug fixes. It does not pay where the answer is unknown, or where correctness is judged by a human eye. In those cases you spike first, learn what the result should be, throw the spike away, and then write tests.

Legacy code is a third case. You cannot test-first code that already exists, and you don't yet know which of its behaviours are bugs. A characterization test records what the code does today so a later change can be proven safe. Mechanics of the Strangler approach and legacy work are in 09 · lesson 09; here we run both worked cases for real.

SituationApproachWhy
Many business rules (refunds, pricing, tax)TDDEach rule is an example you can state as a test
New public API or function shapeTDDThe test is the first caller and exposes awkward signatures
Bug fixTDDReproduce it red first, so the fix is proven and can't regress
Exploring a library or an unknown outputSpike, throw away, then testYou can't assert what you don't know yet
UI layout, stylingBuild, review by eyeA test on pixels costs more than the bugs it catches
Legacy code with no testsCharacterization test firstPin today's behaviour, then change it safely
صف بصف: (1) قواعد business كتير زي الـ refunds والتسعير والضريبة → TDD لأن كل قاعدة مثال تقدر تكتبه test. (2) API أو function جديدة → TDD لأن الـ test أول caller وبيكشف الـ signature الوحشة. (3) bug fix → TDD: اعمله reproduce بـ test أحمر الأول، فالـ fix يتثبت ومايرجعش. (4) استكشاف library أو output مش معروف → spike وترميه وبعدين tests، لأنك مش هتقدر تعمل assert على حاجة لسه مش عارفها. (5) الـ UI layout والـ styling → ابنيه وراجعه بعينك، لأن test على pixels بيكلف أكتر من الـ bugs اللي بيمسكها. (6) legacy من غير tests → characterization test الأول: ثبّت السلوك الحالي وبعدين غيّره بأمان.

حالة 1: characterization test لـ calcShipping القديمة. شبكة من 90 مدخل بتصوّر السلوك الحالي، حتى الحاجات اللي شكلها غلط.

// كود قديم من 2021: محدش فاكر ليه كده، والـ checkout كله معتمد عليه
export function calcShipping(weightKg: number, region: string, isVip?: boolean): number {
  let cost = 30;
  if (region == "EG-CAI") cost = 25;
  else if (region == "EG-ALX") cost = 35;
  else if (region.startsWith("EG")) cost = 45;
  else cost = 120;
  if (weightKg > 5) cost += Math.floor(weightKg - 5) * 8;
  if (weightKg > 30) cost = cost * 1.5;
  if (isVip && cost > 100) cost -= 20;
  if (weightKg == 0) return 0;
  return Math.round(cost);
}

Part 3 — BDD and Gherkin 🟡 Intermediateالجزء 3 — الـ BDD والـ Gherkin

English

BDD is a way of agreeing on behaviour in business language before building it. Gherkin is the file format (Feature / Given / When / Then), and Cucumber is the tool that binds each sentence to a step function. Below is the real refund policy from Part 1, written as a .feature file, calling exactly the same decideRefund.

The real cost is the extra layer. For the same three scenarios, Gherkin plus step definitions is 19 + 39 = 58 lines against 23 lines of Vitest, about 2.5 times, and there is now a string binding between English sentences and code: rewording one sentence breaks the link at run time. That cost is justified only when business people actually read or write the scenarios. In most teams they never do, and plain describe/it with Given/When/Then wording gets most of the value.

Feature: Refund policy
  Customers can get their money back within 14 days of delivery.

  Background:
    Given an order of 100.00 EGP delivered on "2026-11-01"

  Scenario: Partial refund inside the window
    When the customer asks for 30.00 EGP on day 3
    Then the refund is approved for 30.00 EGP

  Scenario: Too late
    When the customer asks for 10.00 EGP on day 15
    Then the refund is rejected with reason "WINDOW_EXPIRED"

  Scenario: More than what is left
    Given 80.00 EGP was already refunded
    When the customer asks for 30.00 EGP on day 3
    Then the refund is rejected with reason "EXCEEDS_REMAINING"

}
setWorldConstructor(RefundWorld);

Given("an order of {float} EGP delivered on {string}", function (this: RefundWorld, egp: number, date: string) {

});

Given("{float} EGP was already refunded", function (this: RefundWorld, egp: number) {
  this.order.refundedMinor = minor(egp);
});

When("the customer asks for {float} EGP on day {int}", function (this: RefundWorld, egp: number, day: number) {

  this.decision = decideRefund(this.order, { amountMinor: minor(egp) }, now);
});

  assert.deepEqual(this.decision, { kind: "approved", amountMinor: minor(egp) });
});

Then("the refund is rejected with reason {string}", function (this: RefundWorld, reason: string) {
  assert.equal(this.decision.kind === "rejected" && this.decision.reason, reason);
});

Then("{float} EGP remains refundable", function (this: RefundWorld, egp: number) {
  assert.ok(this.decision.kind === "rejected" && this.decision.reason === "EXCEEDS_REMAINING");
  assert.equal(this.decision.remainingMinor, minor(egp));
});

Part 4 — The core tested with fakes 🟡 Intermediateالجزء 4 — اختبار الـ core بـ fakes

English

In a hexagonal design the domain core depends on ports (interfaces), not on Postgres. That gives you the fastest possible test: real logic through in-memory fakes that implement those ports. Here placeOrder runs through 500 generated cases, first against fakes and then, unchanged, against real Postgres. Doubles in general are covered in lesson 02; what matters here is which fakes you can trust.

A fake is only useful if it behaves like the real adapter, so a contract test runs the same suite against both (see lesson 02, part 3). Below, a naive fake without uniqueness fails one contract test, the honest one passes all six, and a broken migration without the UNIQUE constraint fails the Postgres side while all 500 fake tests stay green. That last result is why fakes never replace integration tests.

export type Line = { sku: string; qty: number; unitPriceMinor: number };
export type Order = {
  id: string; idempotencyKey: string; customerId: string; lines: Line[]; totalMinor: number;
};
export type PlaceOrderCmd = { idempotencyKey: string; customerId: string; lines: Line[] };
export type PlaceOrderResult =
  | { kind: "placed" | "duplicate"; order: Order }
  | { kind: "rejected"; reason: "EMPTY_CART" | "INVALID_QTY" | "OUT_OF_STOCK" };

// الـ error ده جزء من الـ port: أي adapter لازم يرميه عند تكرار الـ key
export class DuplicateKeyError extends Error {}

// الـ ports: الـ core يعرف الـ interfaces دي بس، مش Postgres
export interface OrderRepo {
  findByKey(key: string): Promise<Order | null>;
  insert(order: Order): Promise<void>;
}
export interface StockPort {
  reserve(lines: Line[]): Promise<boolean>;
}
export type Deps = { orders: OrderRepo; stock: StockPort; nextId: () => string };

export async function placeOrder(deps: Deps, cmd: PlaceOrderCmd): Promise<PlaceOrderResult> {
  if (cmd.lines.length === 0) return { kind: "rejected", reason: "EMPTY_CART" };
  if (cmd.lines.some((l) => !Number.isInteger(l.qty) || l.qty <= 0)) {
    return { kind: "rejected", reason: "INVALID_QTY" };
  }
  const existing = await deps.orders.findByKey(cmd.idempotencyKey);
  if (existing) return { kind: "duplicate", order: existing };
  if (!(await deps.stock.reserve(cmd.lines))) return { kind: "rejected", reason: "OUT_OF_STOCK" };

  const totalMinor = cmd.lines.reduce((sum, l) => sum + l.qty * l.unitPriceMinor, 0);
  const order: Order = { id: deps.nextId(), ...cmd, totalMinor };
  try {
    await deps.orders.insert(order);
  } catch (err) {
    // طلبين في نفس اللحظة: الـ constraint مسك التاني، فنرجّع اللي كسب
    if (err instanceof DuplicateKeyError) {
      const winner = await deps.orders.findByKey(cmd.idempotencyKey);
      if (winner) return { kind: "duplicate", order: winner };
    }
    throw err;
  }
  return { kind: "placed", order };
}

export class FakeOrderRepo implements OrderRepo {

  async findByKey(key: string): Promise<Order | null> {

    if (this.byKey.has(order.idempotencyKey)) throw new DuplicateKeyError(order.idempotencyKey);

  constructor(initial: Record<string, number>) {
    this.qty = new Map(Object.entries(initial));

فين هستخدمه في شغلي؟ في POST /orders بتاعك: كل قواعد الـ cart والخصم والـ idempotency تتختبر بالـ fakes في ثواني، وعلى كل حفظ. بعدها 20 أو 30 integration test على Postgres للـ repo نفسه: الـ unique، الـ rollback لو الـ stock فشل، وترتيب النتائج. مش محتاج تشغّل الـ 500 حالة كلها على الـ DB، بس contract test واحد لكل method في الـ port.

Part 5 — The strategy document 🟡 Intermediateالجزء 5 — الـ strategy document

English

A testing strategy answers specific questions on one page: what counts as unit, integration and E2E here, the coverage target per layer, the CI time budget, who owns a flaky test, and what is deliberately not tested. If it isn't written, every engineer answers those differently and the suite drifts.

Writing it is not enough, because documents go stale. Below is the page for the orders SaaS, with its numeric targets in a marked table. A script asks Vitest itself how many tests exist in each folder and under each tag, compares that with the table, and fails the build on any mismatch. The second run adds nine validation-message tests in e2e/ and a stray test in src/lib/, and the script catches both.

# Orders SaaS: testing strategy (owner: backend guild, reviewed every quarter)

## What each layer proves
- **Unit** (`src/domain`, `src/core`): pricing, refund and order state rules, through fakes on ports. No I/O.
- **Integration** (`src/api`, `src/adapters`): SQL, constraints, transactions, HTTP contract, against real Postgres.
- **E2E** (`e2e`): signup, checkout, refund, against the deployed preview. Nothing else earns an E2E.

## Rules
- CI budget per PR: 10 minutes total. A slower PR pipeline is a bug with an owner.
- A flaky test is owned by whoever owns the code under test; quarantine expires in 14 days.
- Mutation score on `src/domain` is checked nightly, target 70%.

## Not tested, on purpose
- Third-party dashboards (Stripe, SES): covered by contract tests on our side of the API.
- Pixel-perfect layout: visual review on the preview URL.
- Admin one-off scripts: reviewed by a second engineer and run with `--dry-run` first.

export type Coupon = { percent: number; capMinor: number; expiresAt: Date };

export function couponDiscount(totalMinor: number, coupon: Coupon, now: Date): number {
  if (now > coupon.expiresAt) return 0;
  const raw = Math.floor((totalMinor * coupon.percent) / 100);
  return Math.min(raw, coupon.capMinor);
}

import { randomUUID } from "node:crypto";
import { afterAll, beforeAll, describe, expect, it } from "vitest";
import pg from "pg";

type Row = { id: string; customerId: string; createdAt: Date };
interface OrderLister {
  insert(o: Row): Promise<void>;
  listByCustomer(customerId: string): Promise<Row[]>;
}

class FakeLister implements OrderLister {
  private rows: Row[] = [];
  async insert(o: Row) { this.rows.push(o); }
  // السطر ده هو اللي الـ contract بيجبرك عليه: الـ fake لازم يرتّب زي الـ SQL
  async listByCustomer(customerId: string) {
    return this.rows
      .filter((r) => r.customerId === customerId)
      .sort((a, b) => b.createdAt.getTime() - a.createdAt.getTime());
  }
}

const pool = new pg.Pool({ connectionString: process.env.PG_URL, max: 2 });
class PgLister implements OrderLister {
  async insert(o: Row) {
    await pool.query("INSERT INTO ex_orders (id, customer_id, created_at) VALUES ($1, $2, $3)", [o.id, o.customerId, o.createdAt]);
  }
  async listByCustomer(customerId: string) {
    const { rows } = await pool.query("SELECT id, customer_id, created_at FROM ex_orders WHERE customer_id = $1 ORDER BY created_at DESC", [customerId]);
    return rows.map((r) => ({ id: r.id, customerId: r.customer_id, createdAt: r.created_at }));
  }
}

beforeAll(async () => {
  await pool.query("DROP TABLE IF EXISTS ex_orders");
  await pool.query("CREATE TABLE ex_orders (id text PRIMARY KEY, customer_id text NOT NULL, created_at timestamptz NOT NULL)");
});
afterAll(() => pool.end());

function listerContract(name: string, make: () => Promise<OrderLister>) {
  describe(`OrderLister contract: ${name}`, () => {
    it("returns only this customer's orders, newest first", async () => {
      const repo = await make();
      const old = { id: randomUUID(), customerId: "c1", createdAt: new Date("2026-01-01T00:00:00Z") };
      const recent = { id: randomUUID(), customerId: "c1", createdAt: new Date("2026-06-01T00:00:00Z") };
      const other = { id: randomUUID(), customerId: "c2", createdAt: new Date("2026-03-01T00:00:00Z") };
      for (const o of [old, other, recent]) await repo.insert(o);
      expect((await repo.listByCustomer("c1")).map((r) => r.id)).toEqual([recent.id, old.id]);
    });
  });
}

listerContract("fake", async () => new FakeLister());
listerContract("Postgres", async () => {
  await pool.query("TRUNCATE ex_orders");
  return new PgLister();
});

Cheat sheet · الخلاصة

  • TDD: one small red, the least code to go green, refactor with tests unchanged. Red proves the test can fail.
  • The test is the first caller, so it shapes the signature: boolean became a discriminated union in cycle 3.
  • TDD fits: business rules, new APIs, bug fixes. Spike and throw away for exploration. Eyeball UI layout.
  • Legacy code: characterization tests first (90 cases here; 20 caught a "harmless" cleanup).
  • Gherkin costs ~2.5× the lines (58 vs 23) and binds by string. Worth it only if the business really reads it.
  • Fakes on ports: 500 cases ≈ 36 ms vs ≈ 5.8 s on Postgres (≈ 160× inside tests).
  • A contract test keeps the fake honest; a missing UNIQUE still passes 500 fake tests, so adapters need a real DB.
  • Strategy doc: layers, coverage per layer, CI budget, flake owner, what isn't tested. Enforce it with a script.
  • Tally incidents by cheapest catching test; invest in the biggest gap, and don't delete tests from this alone.
بالعامية
  • الـ TDD: red صغير، أقل كود يبقى green، refactor والـ tests زي ما هي. الـ red بيثبت إن الـ test يقدر يقع.
  • الـ test أول caller فهو اللي بيشكّل الـ signature: الـ boolean بقى discriminated union في الدورة التالتة.
  • الـ TDD ينفع في: قواعد business، APIs جديدة، bug fixes. الاستكشاف spike وترميه، والـ UI layout بالعين.
  • الـ legacy: characterization tests الأول (90 حالة هنا، 20 منهم مسكوا "تنضيف" شكله بريء).
  • الـ Gherkin بياخد حوالي 2.5 مرة السطور (58 مقابل 23) وبيربط بالنص. يستاهل بس لو الـ business بيقراه فعلًا.
  • الـ fakes على الـ ports: 500 حالة ≈ 36 ms مقابل ≈ 5.8 ثانية على Postgres (≈ 160 مرة جوه الـ tests).
  • الـ contract test بيخلي الـ fake أمين، و UNIQUE ناقصة لسه بتعدّي 500 test بالـ fakes، فالـ adapters محتاجين DB حقيقية.
  • الـ strategy doc: الـ layers، الـ coverage لكل layer، الـ CI budget، مين مسؤول عن الـ flakes، وإيه اللي مش بنختبره. وافرضها بـ script.
  • عدّ الـ incidents حسب أرخص test، واستثمر في أكبر فجوة، ومتمسحش tests بناءً على الجدول ده لوحده.
