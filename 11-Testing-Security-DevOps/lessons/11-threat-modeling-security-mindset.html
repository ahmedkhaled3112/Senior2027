Why this matters · ليه ده مهم

English

Most breaches aren't clever. A route that forgot its auth middleware, a queue message trusted because it was "internal", a service running as a database superuser. A security mindset means you stop asking "does this work?" and start asking "what happens if the input lies, and how far does the damage reach?". This lesson turns that question into things you can run: an inventory of every input, a measured table showing which layer stops an attack, a router that denies by default, and a threat model stored in the repo that fails CI when it goes stale. It's also what a senior gets asked in interviews: "threat model this feature in five minutes".

بالعامية

أغلب الاختراقات مش عبقرية. route نسيت الـ auth middleware، أو queue message اتصدقت عشان "داخلية"، أو service شغالة بـ database superuser. الـ security mindset معناه إنك تبطل تسأل "ده شغال؟" وتبدأ تسأل "لو الـ input بيكدب، إيه اللي هيحصل، والضرر هيوصل لحد فين؟". الدرس ده بيحوّل السؤال ده لحاجات بتتشغّل: inventory لكل input، جدول متقاس بيوريك أنهي طبقة وقفت الهجوم، router بيرفض by default، و threat model متخزن في الـ repo والـ CI بيقع لو بقى قديم. وده بالظبط اللي بيتسأل فيه السنيور في الـ interview: "اعمل threat model للـ feature دي في 5 دقايق".

Part 1 — Attack surface as an inventory 🟢 Basicالجزء 1 — الـ attack surface كـ inventory بيتولد من الكود

English

The attack surface is every place data enters your system from something you don't fully control. HTTP routes are the obvious part, but headers, cookies, uploaded files, environment variables, queue messages and webhooks are all input too. The useful way to think about it isn't a diagram from memory. It's a list generated from the code, because the code is what actually runs.

The script below walks Express's router and prints every route with the middleware in front of it, then scans the source for env reads and queue consumers. Express 5 removed app._router (it's app.router now) and no longer keeps a mount path on the layer, so the prefix is recorded by a small mount() helper. A route with no requireAuth that isn't in an explicit public list gets flagged and the script exits 1, which makes it usable in CI. It's a heuristic: a regex over source misses a dynamic process.env[name], so treat the output as a starting list and not as proof of completeness.

Internal doesn't mean trusted. The second script is the mistake that hurts most in multi-tenant systems. An API forwards req.body into a Redis queue, the worker trusts the tenantId inside, and a member of tenant acme refunds an order of tenant globex. The same forged message can also be pushed straight into Redis by anything that can reach it. The fix has three independent parts: the producer takes the tenant from the authenticated principal and ignores the body; the envelope is signed with an HMAC, so a message that didn't come from a trusted producer is rejected; and the worker re-checks the tenant against the row it's about to change. Replay still needs an idempotency key, which you'll add in the exercises.

type Row = { method: string; path: string; chain: string[] };
type Layer = {
  name: string;
  route?: { path: string; methods: Record<string, boolean>; stack: { name: string; handle: { name: string } }[] };
  handle: { name: string; stack?: Layer[]; mountPath?: string };

// الـ middleware بيتطبق على الـ routes اللي اتسجلت بعده بس، فبنجمعه بالترتيب
function walk(stack: Layer[], prefix = "", inherited: string[] = []): Row[] {
  const rows: Row[] = [];
  const chain = [...inherited];
  for (const layer of stack) {
    if (layer.route) {
      for (const method of Object.keys(layer.route.methods)) {
        const names = layer.route.stack.map((s) => s.handle.name || "(anonymous)");
        rows.push({ method: method.toUpperCase(), path: prefix + layer.route.path, chain: [...chain, ...names] });
      }
    } else if (layer.handle.stack) {
      rows.push(...walk(layer.handle.stack, prefix + (layer.handle.mountPath ?? "?"), chain));
    } else {
      chain.push(layer.handle.name || layer.name);
    }
  }
  return rows;
}

// ✅ الـ tenant جاي من الـ principal، ومن الـ body بناخد الـ orderId بس
async function goodEnqueue(who: Principal, body: { orderId: number }) {
  const payload = JSON.stringify({ orderId: body.orderId, tenantId: who.tenantId, requestedBy: who.userId });
  await redis.rpush("refunds", JSON.stringify({ payload, sig: sign(payload) }));
}
// ✅ الـ worker بيتحقق من التوقيع والشكل، وبعدين يقارن الـ tenant بصف الـ DB نفسه
async function goodWorker(orders: ReturnType<typeof seed>, raw: string) {
  const env = JSON.parse(raw) as { payload?: unknown; sig?: unknown };
  const given = Buffer.from(String(env.sig));
  const want = Buffer.from(sign(String(env.payload)));
  if (given.length !== want.length || !timingSafeEqual(given, want)) return "rejected: bad-signature";
  const msg = Msg.parse(JSON.parse(String(env.payload)));
  const order = orders.get(msg.orderId);
  if (!order || order.tenantId !== msg.tenantId) return "rejected: tenant-mismatch";
  order.refunded = true;
  return `refunded ${msg.orderId} for tenant ${msg.tenantId}`;
}

  const results: string[] = [];
  for (let raw = await redis.lpop("refunds"); raw; raw = await redis.lpop("refunds")) results.push(await worker(raw));
  return results;
}

بالعامية

الـ attack surface هو كل مكان الـ data بتدخل منه السيستم من حاجة إنت مش متحكم فيها بالكامل. الـ HTTP routes هي الجزء الواضح، بس الـ headers والـ cookies والـ files المرفوعة والـ env vars والـ queue messages والـ webhooks كلهم input برضه. والطريقة المفيدة إنك متعتمدش على diagram من دماغك، تعمل قايمة بتتولد من الكود، عشان الكود هو اللي بيتشغّل فعلًا.

السكريبت بيمشي على الـ router بتاع Express ويطبع كل route والـ middleware اللي قدامها، وبعدين يمسح الكود عشان الـ env والـ queue consumers. في Express 5 الـ app._router اتشال وبقى app.router، والـ mount path مش محفوظ على الـ layer، فبنسجله بـ helper صغير اسمه mount(). أي route من غير requireAuth ومش في قايمة public مكتوبة بتتعلّم، والسكريبت بيخرج بـ exit 1 فينفع في الـ CI. وده heuristic: الـ regex مش هيمسك process.env[name] الديناميكي، فاعتبر الناتج نقطة بداية مش دليل إن القايمة كاملة.

"داخلي" مش معناها "موثوق". السكريبت التاني هو أكتر غلطة بتوجع في الـ multi-tenant. الـ API بتحط req.body في Redis queue، والـ worker بيصدق الـ tenantId اللي جواها، فـ member في tenant acme يعمل refund لـ order بتاع tenant globex. ونفس الرسالة المزورة ممكن أي حاجة واصلة لـ Redis تحطها مباشرة. التصليح 3 حاجات مستقلة: الـ producer بياخد الـ tenant من الـ principal المتحقق منه ويتجاهل الـ body؛ والـ envelope متوقّع بـ HMAC فأي رسالة مش من producer موثوق بتترفض؛ والـ worker بيرجع يقارن الـ tenant بالصف اللي هيغيّره. لسه فيه الـ replay ودي محتاجة idempotency key، وهتعملها في التمارين.

فين هستخدمه في شغلي؟ لما تمسك codebase جديد: شغّل inventory زي ده على أول يوم، هتطلعلك routes منسية و webhooks محدش عارفها. وأي worker بيقرا من BullMQ أو SQS: ارجع للـ handler وشوف لو job.data.tenantId بيوصل لـ query من غير ما يتقارن بالـ row. نفس الكلام لأي Next.js Server Action بياخد tenantId من الـ form بدل الـ session.

Part 2 — Defense in depth, measured 🟢 Basicالجزء 2 — الـ defense in depth متقاس طبقة طبقة

English

Defense in depth means assuming each layer will eventually fail, so the next one has to hold on its own. You can't claim that by counting controls, only by measuring them. Here one endpoint has four independent layers on real Postgres 18: Zod validation (the input must look like ORD-0001), a parameterized query (the input stays data), a limited role (shop_app has no grant on payment_keys), and RLS (rows filtered by app.tenant_id).

Two payloads run against each configuration: x' OR 1=1 -- tries to read other tenants' orders, and a UNION tries to read the payment keys table. Switching off one layer at a time shows what each one actually contributes. Each layer stops something the others don't: Zod and parameters stop the query from being attacker-shaped at all, the role stops access to a table (real error 42501 permission denied for table payment_keys), and RLS narrows rows but does nothing for a table it isn't on. That last point is why the table shows RLS alone doesn't save payment_keys, and the role alone doesn't save other tenants' orders. Only with all four off do both payloads leak.

     v

// نفس الـ endpoint، والـ 4 طبقات متحكم فيهم بـ flags عشان نقدر نطفي طبقة طبقة
async function findOrder(ref: string, on: Layers): Promise<string> {
  if (on.zod && !OrderRef.safeParse(ref).success) return "stopped: zod 400";
  const client = await (on.role ? limited : wide).connect();
  try {
    await client.query("BEGIN");
    await client.query("SELECT set_config('app.tenant_id', $1, true)", [String(CALLER_TENANT)]);
    const { rows } = on.param
      ? await client.query("SELECT id, tenant_id, ref FROM orders WHERE ref = $1 AND tenant_id = $2", [ref, CALLER_TENANT])
      : await client.query(`SELECT id, tenant_id, ref FROM orders WHERE ref = '${ref}' AND tenant_id = ${CALLER_TENANT}`);
    await client.query("COMMIT");
    const foreign = rows.filter((r) => r.tenant_id !== CALLER_TENANT).length;
    const secrets = rows.filter((r) => String(r.ref).startsWith("fake-psp")).length;
    if (foreign || secrets) return `LEAK: ${rows.length} rows (${foreign} foreign, ${secrets} secrets)`;
    return `${rows.length} rows, own tenant only`;
  } catch (e) {
    await client.query("ROLLBACK");
    const err = e as { code?: string; message: string };
    return `stopped: ${err.code} ${err.message}`;
  } finally {
    client.release();
  }
}

Part 3 — Least privilege 🟢 Basicالجزء 3 — الـ least privilege: نفس الهجوم بصلاحيات مختلفة

English

Least privilege decides the blast radius: when the bug happens, what can the attacker do with it? The script runs the exact same vulnerable query with the exact same payloads against two users. The superuser reads the payment keys, reads pg_authid (19 rows here), drops a table, and writes a file on the DB host's disk with COPY ... TO. The limited role gets four 42501 errors and nothing else. The payloads use stacked statements (x'; DROP TABLE invoices; --): pg sends a query with no parameters through the simple protocol, which allows several statements in one string, while a query with $1 uses the extended protocol, which doesn't. So parameters close this door for a second reason.

The same rule repeats at three levels. The DB user gets only the grants it needs, and no ownership of tables, because an owner can drop them and skips RLS unless the table has FORCE ROW LEVEL SECURITY (details in section 07 · 3.1, part 4). The container user is non-root (lesson 26), and the IAM role lists exact actions on exact resources (lesson 37). Migrations run as a separate owner role in a separate step, so the running app can't change the schema.

Part 4 — Secure defaults 🟢 Basicالجزء 4 — الـ secure defaults: الرفض هو الوضع الافتراضي

English

A secure default means forgetting something leaves you safe instead of exposed. app.get(path, requireAuth, handler) is the opposite: auth is opt-in, every route has to remember it, and one route that forgets it answers 200 to anyone. That route also passes review easily, because a diff shows what was added, not what was missing.

The fix moves the decision into the shape of the API. Routes register through secureRoutes(), where the policy is a required argument. Omitting it is a compile error (real TS 7 output: TS2554: Expected 3 arguments, but got 2), and public must carry a written reason. At runtime the guard rejects anything it doesn't recognise, so a bad cast or a typo in a config file denies instead of allowing. The type check only covers code that uses the helper, though. Someone can still write app.get(...) directly, so a test enumerates every registered route and fails on one with no policy attached. Type check, runtime deny and a test: three independent nets for the same mistake.

The test walks only top-level routes for brevity. If you mount nested routers, walk them too, as the inventory in Part 1 does. It also asserts a minimum route count, because a walker broken by an Express upgrade would otherwise pass with zero routes checked.

import type { Express, RequestHandler } from "express";

export type Role = "member" | "admin";
export type Principal = { userId: number; role: Role };
// مفيش default هنا: الـ route لازم تعلن قرارها، وحتى الـ public لازم يبقى معاه سبب مكتوب
export type Policy =
  | { kind: "public"; reason: string }
  | { kind: "authenticated" }
  | { kind: "role"; role: Role };

const tokens: Record<string, Principal> = {
  "tok-sara": { userId: 1, role: "member" },
  "tok-admin": { userId: 2, role: "admin" },
};

export function enforce(policy: Policy): RequestHandler {
  const guard: RequestHandler = (req, res, next) => {
    const who = tokens[req.get("authorization")?.replace("Bearer ", "") ?? ""];
    if (policy.kind === "public") return next();
    if (policy.kind === "authenticated" || policy.kind === "role") {
      if (!who) return void res.status(401).json({ error: "unauthenticated" });
      if (policy.kind === "role" && who.role !== policy.role) return void res.status(403).json({ error: "forbidden" });
      res.locals.principal = who;
      return next();
    }
    // أي kind مش معروف يوصل هنا (JSON غلط أو cast): الرد الوحيد المسموح هو الرفض
    res.status(403).json({ error: "no-policy" });
  };
  return Object.assign(guard, { policy });
}

type Method = "get" | "post" | "delete";
export function secureRoutes(app: Express) {
  const add = (method: Method) => (path: string, policy: Policy, handler: RequestHandler) => {
    app[method](path, enforce(policy), handler);
  };
  return { get: add("get"), post: add("post"), delete: add("delete") };
}

type RouteLayer = { route?: { path: string; methods: Record<string, boolean>; stack: { handle: object }[] } };

// الـ test بيستخدم الدالة دي عشان يلف على كل الـ routes اللي اتسجلت فعلًا
export function listRoutes(app: Express) {
  const stack = (app as unknown as { router: { stack: RouteLayer[] } }).router.stack;
  return stack.flatMap(({ route }) => {
    if (!route) return [];
    const first = route.stack[0]?.handle as { policy?: Policy } | undefined;
    return Object.keys(route.methods).map((m) => ({ method: m.toUpperCase(), path: route.path, policy: first?.policy }));
  });
}

Part 6 — A full threat model 🔴 Advancedالجزء 6 — threat model كامل: DFD و trust boundaries و mitigations

English

This is README artifact 4. A full model starts from a data flow diagram: external entities (browser, Stripe), processes (API, worker), data stores (Postgres, the jobs queue, the avatar bucket), and the flows between them. A trust boundary is any line where the level of trust changes: internet to edge, edge to data, your code to a third party. Flows crossing a boundary are where attacks happen, so they get the attention.

Keep the diagram as data in the repo, not in a drawing tool. Then a script can generate the picture, and it can enforce rules. Microsoft's STRIDE-per-element gives the starting candidates: external entities get S and R, processes get all six, data stores get T, I, D (plus R when the store holds audit logs, which this script skips), and flows get T, I, D. Here that's 52 candidates to walk through, and most will be "not applicable". The script produces the checklist; a person writes the threats, mitigations and residual risk. Automating that judgment would produce noise that nobody reads.

Residual risk is what's left after the mitigation. A medium risk that nobody signed for is an unknown, so the check fails until a named person accepts it. The check also fails when a boundary-crossing flow has no threat with both a mitigation and an owner, because a mitigation with no owner doesn't get built.

Part 7 — Keeping it alive 🔴 Advancedالجزء 7 — إزاي الـ threat model يفضل عايش

English

A threat model written once and filed away is wrong within a quarter. Rules that keep it true: redo the affected part when there's a new data flow, a new external dependency or a new kind of data (PII, payment), and skip it for a change that adds neither. Review it in the same PR as the design change, so the reviewer sees both. Link each threat to an issue so that a mitigation is something tracked and closable. And a specific named person accepts each residual risk that isn't low (a team lead or the CTO, not "the team"), because accepting risk is a decision somebody has to be able to answer for.

A mechanical check catches the most common failure: the code changed and the model didn't. List the source files that define each data flow, then fail if any changed after the model did. The script does that with file times. File times break in CI, since a fresh clone sets every mtime to checkout time, so the same script has a git mode that compares the last commit touching each file. The check only forces the question ("did this change affect the model?"), and the answer can be "no". So add a one-line review note to the model when it doesn't.

For bigger teams, OWASP Threat Dragon (a diagram-based tool) and pytm (a Python model that generates diagrams and threats) are the established options. Not run here: Threat Dragon needs its own install and pytm needs Python, and neither is required for the model above.

function changedAt(file: string): number {

  const out = execFileSync("git", ["-C", root, "log", "-1", "--format=%ct", "--", file], { encoding: "utf8" });
  return Number(out.trim()) * 1000;
}

فين هستخدمه في شغلي؟ ضيف node src/tm-fresh.ts git . كـ step في الـ CI. لما حد يغيّر src/webhooks/stripe.ts الـ PR يقع ويقوله "راجع الـ threat model"، فيعدل الموديل أو يكتب سطر "مراجعتش عشان ده تغيير داخلي بس".
Interview question "Your threat model is six months old. How do you make sure it doesn't rot?" → It lives in the repo as data, it's reviewed in the PR that changes a data flow, every threat links to an issue, a named person signs each non-low residual risk, and CI fails when a listed flow's source changed after the model. Then say what it can't do: it forces the review but doesn't guarantee the review was good.
"الـ threat model بتاعك عمره 6 شهور. إزاي تضمن إنه ميبوظش؟" ← يبقى data في الـ repo، ويتراجع في الـ PR اللي بيغيّر data flow، وكل threat مربوطة بـ issue، وشخص باسمه يمضي على أي residual risk مش low، والـ CI يقع لو ملف flow اتغير بعد الموديل. وبعدين قول اللي مش هيقدر يعمله: هو بيجبر المراجعة بس، مبيضمنش إن المراجعة كانت كويسة.

Common mistakes · غلطات شائعة

❌ Trusting a field because it came from "inside" 
// ❌ الـ tenantId طالع من الرسالة نفسها
const msg = JSON.parse(raw);
await refund(msg.orderId, msg.tenantId);
✅ Verify at the point of use 
// ✅ بنتأكد إن الـ order فعلًا بتاع الـ tenant
const order = await orders.byId(msg.orderId);
if (order?.tenantId !== msg.tenantId) return reject();
بالعامية

❌ الـ worker بياخد الـ tenantId من الرسالة زي ما هو، فأي حد قدر يحط رسالة في الـ queue بقى tenant تاني. ✅ الـ worker بيرجع يقرا الـ row من الـ DB ويقارن الـ tenant. أي حاجة بتعدّي boundary لازم تتفحص عند الاستخدام، حتى لو جاية من service عندك.

❌ Auth you have to remember 
// ❌ النسيان هنا بيرد 200
app.get("/invoices/:id", getInvoice);
✅ A decision the compiler demands 
// ✅ من غير policy مش هيعمل compile
routes.get("/invoices/:id", { kind: "authenticated" }, getInvoice);
بالعامية

❌ الـ auth اختياري وكل route لازم تفتكر، والـ diff مبيوريش الناقص. ✅ الـ policy argument إجباري، والـ compiler والـ test الاتنين بيقعوا لو route معلنتش قرارها.

❌ One DB user that owns everything 
-- ❌ نفس الـ user للـ app وللـ migrations
-- DATABASE_URL=postgres://owner@db/shop
GRANT ALL ON ALL TABLES IN SCHEMA public TO app;
✅ Separate roles with exact grants 
-- ✅ الـ app بتاخد اللي محتاجاه بس، والـ owner للـ migrations
CREATE ROLE shop_app LOGIN;
GRANT SELECT, INSERT, UPDATE ON orders TO shop_app;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;
بالعامية

❌ user واحد للـ app والـ migrations ومعاه كل حاجة: أي injection يبقى DROP TABLE، والـ RLS عليه مبتشتغلش عشان owner. ✅ role للـ app بـ grants محددة و role تاني للـ migrations، وFORCE ROW LEVEL SECURITY عشان حتى الـ owner يخضع للـ policy.

❌ A mitigation that means nothing 
{ "letter": "T", "threat": "bad file uploaded",
  "mitigation": "validate input", "owner": "" }
✅ A control you can verify, with an owner 
{ "letter": "T", "threat": "SVG disguised as PNG runs on our origin",
  "mitigation": "re-encode to WebP, separate domain",
  "owner": "backend", "issue": "#107" }
بالعامية

❌ "validate input" و owner فاضي دي مش mitigation، دي جملة تريحك. ✅ control محدد تقدر تختبره (re-encode، domain منفصل) ومعاه owner و issue، فحد مسؤول إنه يتعمل ويتقفل.

1. Extend the inventory 🟢 easy Add a rule to inventory.ts: every POST route must have a middleware named rateLimit, or it's flagged. Run it and read which routes fail.
ضيف قاعدة في inventory.ts: أي POST route لازم يكون عليها middleware اسمه rateLimit وإلا تتعلّم. شغّله واقرا أنهي routes وقعت.
Solution · الحل 
// ضيف ده بعد الـ loop الأصلي في inventory.ts
const noLimit = routes.filter((r) => r.method === "POST" && !r.chain.includes("rateLimit"));
for (const r of noLimit) console.log(`  POST without rateLimit: ${r.path}`);
flagged += noLimit.length;
// ملحوظة: مع التطبيق بتاع الدرس بيطلع 4 routes (login و webhook و refund و avatar)
الحل بيستخدم نفس routes اللي الـ walker طلعها. الـ login والـ refund لازم يبقى عليهم limit فعلًا، والـ webhook ينفع يبقى استثناء صريح لو عليه HMAC.
2. Close the replay hole 🟡 medium The signed message from Part 1 can still be pushed twice. Add a job id to the signed payload and make the worker reject a repeated id using Redis SET id 1 NX EX 86400.
الرسالة المتوقّعة بتاعة الجزء 1 لسه ممكن تتحط مرتين (replay). ضيف job id جوه الـ payload المتوقّع، وخلي الـ worker يرفض أي id اتكرر باستخدام Redis SET id 1 NX EX 86400.
Hint · تلميح SET ... NX returns "OK" only for the first writer, and null after that. The signature proves who sent the message; the id proves it's the first time.
SET ... NX بترجع "OK" لأول واحد بس وnull بعد كده. التوقيع بيثبت مين اللي بعت، والـ id بيثبت إنها أول مرة.
3. Five minutes, new feature 🟡 medium Set a timer for 5 minutes and write the STRIDE table for "password reset by email link". Put it in the same format as stride-avatar.ts and make the checker pass.
شغّل تايمر 5 دقايق واكتب جدول الـ STRIDE لـ "password reset بلينك في الإيميل". حطه بنفس شكل stride-avatar.ts وخلي الـ checker يعدّي.
Hint · تلميح Think of: a guessable or reusable token (S), the token in logs or Referer (I), mass reset emails (D), the audit trail for "I never asked for this" (R).
فكّر في: توكن يتخمن أو يتستخدم مرتين (S)، والتوكن في الـ logs أو الـ Referer (I)، وإغراق اليوزرز بإيميلات reset (D)، والـ audit trail لـ "أنا مطلبتش ده" (R).
4. In your project 🔴 project Write the real threat-model.json for your side project with at least 6 elements and 6 flows, one threat per boundary-crossing flow, an owner and a linked issue for each, and add tm.ts and the git mode of tm-fresh.ts as CI steps.
اكتب threat-model.json الحقيقي بتاع مشروعك الجانبي: 6 elements و6 flows على الأقل، threat لكل flow بيعدّي boundary، ولكل واحدة owner و issue مربوط، وضيف tm.ts ووضع git من tm-fresh.ts كـ steps في الـ CI.
Hint · تلميح Start with a flow where your app calls a third party, and one where money or PII moves. Those two usually give you the threats that matter most.
ابدأ بـ flow بتنادي فيه طرف خارجي، و flow بتتحرك فيه فلوس أو PII. الاتنين دول غالبًا هيطلعولك أهم الـ threats.

Cheat sheet · الخلاصة

  • Attack surface = every input, including env, queues, webhooks, files. Generate the list from the code, and fail CI on a route with no decision.
  • "Internal" isn't "trusted": take the tenant from the principal, sign the envelope, re-check against the row at the point of use.
  • Defense in depth is measured, not counted: switch layers off one at a time. Each one stops something the others don't (Zod, parameters, role, RLS).
  • Least privilege sets the blast radius: the same injection read 2 keys, dropped a table and wrote a file as superuser, and got four 42501 errors as a limited role.
  • Superusers and BYPASSRLS roles skip RLS; owners skip it unless FORCE ROW LEVEL SECURITY.
  • Secure defaults: required policy argument, runtime deny on unknown, and a test that enumerates every route.
  • STRIDE: one concrete threat and one concrete control per letter, with an owner. "Be careful" isn't a mitigation.
  • Threat model as data: elements, flows and zones in the repo, STRIDE candidates generated, judgment written by hand.
  • CI fails when a boundary-crossing flow lacks a mitigation or owner, or when a non-low residual risk has no named person.
  • Revisit on a new flow, dependency or data type; check freshness with git time in CI, since a clone resets mtimes.
بالعامية
  • الـ attack surface هو كل input، ومنهم الـ env والـ queues والـ webhooks والـ files. ولّد القايمة من الكود، وخلي الـ CI يقع على أي route من غير قرار.
  • "داخلي" مش معناها "موثوق": خد الـ tenant من الـ principal، ووقّع الـ envelope، وقارن بالـ row عند الاستخدام.
  • الـ defense in depth بيتقاس مش بيتعد: اطفي طبقة طبقة. كل طبقة بتمنع حاجة التانية مبتمنعهاش (Zod والـ parameters والـ role والـ RLS).
  • الـ least privilege بيحدد الـ blast radius: نفس الـ injection قرا مفتاحين ومسح جدول وكتب ملف بالـ superuser، وخد 4 errors 42501 بالـ limited role.
  • الـ superusers والـ roles اللي عليها BYPASSRLS بيتخطوا الـ RLS، والـ owners بيتخطوها إلا لو فيه FORCE ROW LEVEL SECURITY.
  • الـ secure defaults: argument إجباري للـ policy، ورفض في الـ runtime لأي حاجة مش معروفة، و test بيلف على كل الـ routes.
  • الـ STRIDE: threat محددة و control محدد لكل حرف، ومعاه owner. "خلي بالك" مش mitigation.
  • الـ threat model كـ data: الـ elements والـ flows والـ zones في الـ repo، والـ STRIDE candidates بتتولد، والحكم بيتكتب بإيد.
  • الـ CI يقع لو flow بيعدّي boundary من غير mitigation أو owner، أو residual risk مش low من غير شخص باسمه.
  • راجع الموديل مع أي flow أو dependency أو نوع data جديد، وافحص الحداثة بوقت git في الـ CI عشان الـ clone بيغيّر الـ mtimes.
