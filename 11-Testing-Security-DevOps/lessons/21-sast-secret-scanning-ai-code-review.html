Why this matters · ليه ده مهم

English

Most security bugs reach production through a normal, green pull request. A pipeline can stop whole classes of them cheaply, but every scanner has blind spots, and a noisy one gets switched off within a month. This lesson builds the gates for real: static rules for your patterns, a dependency gate where exceptions expire, secret scanning that also reads history, and one merge decision. Then it measures how far those gates get on an AI-written endpoint with five planted flaws. They caught three. The two they missed are the ones that hurt the most.

بالعامية

معظم الثغرات بتوصل production عن طريق pull request عادي وأخضر. الـ pipeline يقدر يوقف أنواع كاملة منها بتكلفة قليلة، بس كل scanner عنده حاجات مش شايفها، والـ scanner الدوشة بيتقفل في خلال شهر. في الدرس ده هنبني الـ gates فعلًا: static rules للـ patterns بتاعتك، بوابة dependencies الاستثناءات فيها ليها تاريخ انتهاء، secret scanning بيقرا الـ history كمان، وقرار merge واحد. وبعدين هنقيس الـ gates دي وصلت لفين على endpoint مكتوب بالـ AI فيه 5 ثغرات متزرعة. مسكوا 3. والاتنين اللي فلتوا هما اللي بيوجعوا أكتر.

Part 1 — SAST: what a rule can and can't see 🟡 Intermediateالجزء 1 — الـ SAST: الـ rule تقدر تشوف إيه ومتقدرش تشوف إيه

English

The SAST/DAST/SCA comparison table is in 04 · lesson 28, part 6: read it first, this part doesn't repeat it. The new idea here is that static analysis comes in three strengths, and each one misses what the next one catches.

  • Text patterns (grep, simple regex) see characters. Fast, and blind to structure.
  • AST rules (ESLint, plain Semgrep patterns) see syntax: "a call to .query() whose first argument is a template with an expression". Precise about shape, blind to where a value came from.
  • Taint analysis (Semgrep mode: taint, CodeQL) follows data from a source like req.query to a sink like the SQL argument, across variables and helper calls, and stops if a sanitizer is in the way.

Semgrep's status changed recently, so don't rely on an old blog post. The engine stays LGPL 2.1, while the official rules have been under the Semgrep Rules License v1.0 since December 2024, which limits redistributing those rules, for example inside a competing product, so read it before you ship them. Opengrep forked the engine in January 2025 under LGPL 2.1. For an internal CI job the practical choice is the same either way: run the engine, and write the rules that matter to you yourself. CodeQL is the heavy option: it builds a database of your code and queries it, so it's slower and much better at deep flows. It's free on public GitHub repositories, and private ones need a paid GitHub code-security plan.

English

What actually ran: a 20-line ESLint rule that rejects interpolated SQL in .query(), alongside eslint-plugin-security 4.2. Then a sample file where each line carries a label a human wrote after reading it, so the tool's precision can be counted instead of argued about.

// قاعدة ESLint: أي نداء ⁦.query()⁩ أول argument فيه interpolation يبقى خطر
export default {
  meta: {
    type: "problem",
    docs: { description: "Disallow interpolated SQL passed to .query()" },
    schema: [],
    messages: {
      interpolated: "Interpolated SQL in .query(): pass values as parameters ($1, $2).",
    },
  },
  create(context) {
    return {
      // الـ selector ده بيمسك ⁦x.query(...)⁩ و ⁦a.b.query(...)⁩ بأي اسم object
      'CallExpression[callee.type="MemberExpression"][callee.property.name="query"]'(node) {
        const sql = node.arguments[0];
        if (!sql) return;
        const interpolated =
          (sql.type === "TemplateLiteral" && sql.expressions.length > 0) ||
          (sql.type === "BinaryExpression" && sql.operator === "+");
        if (interpolated) context.report({ node: sql, messageId: "interpolated" });
      },
    };
  },
};

جدول مقارنة SAST و DAST و SCA موجود في درس 28 من قسم 04، جزء 6: اقراه الأول لأن هنا مش هنكرره. الجديد هنا إن الـ static analysis ليه 3 درجات قوة، وكل درجة بتفوّت اللي الدرجة اللي بعدها بتمسكه:

  • Text patterns زي grep: بيشوف حروف. سريع وأعمى عن الـ structure.
  • AST rules زي ESLint و Semgrep patterns العادية: بيشوف الـ syntax، يعني "نداء لـ .query() وأول argument فيه template فيه expression". دقيق في الشكل، بس مش عارف الـ value جاية منين.
  • Taint analysis زي mode: taint في Semgrep و CodeQL: بيتتبع الـ data من source زي req.query لـ sink زي الـ SQL argument، عبر الـ variables والـ helpers، وبيقف لو فيه sanitizer في السكة.

وضع Semgrep اتغير من قريب، فمتعتمدش على مقال قديم: الـ engine لسه LGPL 2.1، والـ rules الرسمية من ديسمبر 2024 تحت Semgrep Rules License v1.0 اللي بتحدد إعادة توزيعها، زي جوه منتج منافس، فاقراها قبل ما تشحن الـ rules دي مع منتج. و Opengrep عمل fork للـ engine في يناير 2025 برضه LGPL 2.1. في CI داخلي القرار العملي واحد في الحالتين: شغّل الـ engine، واكتب بنفسك الـ rules اللي تهمك. CodeQL هو الاختيار التقيل: بيبني database للكود ويعمل عليها queries، فهو أبطأ بس أقوى بكتير في الـ flows العميقة، ومجاني على الـ public repos والـ private محتاجة plan مدفوعة من GitHub.

اللي اشتغل فعلًا: rule في ESLint حوالي 20 سطر بترفض الـ SQL الـ interpolated في .query()، ومعاها eslint-plugin-security 4.2. وملف عينة كل سطر عليه label كتبه بني آدم بعد ما قراه، عشان نعدّ دقة الأداة بدل ما نتجادل.

Interview: "What can a taint-tracking SAST find that a lint rule can't?" A lint rule judges one syntactic shape, so it misses input that travels through a variable or helper before it reaches the sink, and it flags safe constants that merely look like interpolation. Taint analysis models source, sink and sanitizer, so it follows the flow. It costs more to run, and it needs models of your framework to stay accurate.
السؤال: "الـ taint SAST بيلاقي إيه الـ lint rule مش بتلاقيه؟" الإجابة: الـ lint rule بتحكم على شكل syntax واحد، فبتفوّت الـ input اللي بيعدي على variable أو helper قبل ما يوصل للـ sink، وبتعلّم على constants آمنة شكلها interpolation. الـ taint بيعمل model للـ source والـ sink والـ sanitizer فبيتتبع الـ flow. بس تكلفته أعلى في التشغيل ومحتاج models للـ framework بتاعك عشان يفضل دقيق.

Part 2 — Custom rules for your own patterns 🟡 Intermediateالجزء 2 — Custom rules للـ patterns بتاعتك

English

Off-the-shelf rules don't know your domain. A rule that says "every repository call must carry tenantId" is worth more than ten generic ones in a multi-tenant app, because cross-tenant reads are your most expensive bug class (see lesson 17). The rule below takes a conservative stance: if it can't prove a tenant is there, for instance when where comes from a variable, it reports. Forcing that shape is the point: the correct code is then also the code that's easy to review.

A rule without tests rots, so RuleTester pins the behaviour with valid and invalid cases, and it runs under plain node as well as under a test runner. ESLint's exit codes are what the pipeline reads: 0 clean, 1 lint errors, 2 a crash or bad configuration.

// قاعدة ESLint: أي نداء repository لازم يعدّي tenantId جوه الـ where
const METHODS = new Set(["findMany", "findFirst", "findById", "count", "updateMany", "deleteMany"]);
const keyName = (p) => (p.key.type === "Identifier" ? p.key.name : p.key.value);

export default {
  meta: {
    type: "problem",
    docs: { description: "Repository calls must be scoped by tenant" },
    schema: [
      {
        type: "object",
        properties: { repoSuffix: { type: "string" }, tenantKey: { type: "string" } },
        additionalProperties: false,
      },
    ],
    messages: {
      missing: "{{repo}}.{{method}}() has no {{key}} in `where`: possible cross-tenant access.",
    },
  },
  create(context) {
    const { repoSuffix = "Repo", tenantKey = "tenantId" } = context.options[0] ?? {};
    const source = context.sourceCode;
    return {
      CallExpression(node) {
        const callee = node.callee;
        if (callee.type !== "MemberExpression" || callee.computed) return;
        const obj = callee.object;
        const repo =
          obj.type === "Identifier" ? obj.name
          : obj.type === "MemberExpression" && !obj.computed ? obj.property.name
          : null;
        if (!repo || !repo.endsWith(repoSuffix) || !METHODS.has(callee.property.name)) return;

        const arg = node.arguments[0];
        const whereProp =
          arg?.type === "ObjectExpression"
            ? arg.properties.find((p) => p.type === "Property" && keyName(p) === "where")
            : undefined;
        // لو الـ where مش object literal مش هنقدر نثبت حاجة: نبلّغ أحسن ما نسكت
        const props = whereProp?.value.type === "ObjectExpression" ? whereProp.value.properties : [];
        const scoped =
          props.some((p) => p.type === "Property" && keyName(p) === tenantKey) ||
          props.some((p) => p.type === "SpreadElement" && /tenant|scope/i.test(source.getText(p.argument)));
        if (!scoped) {
          context.report({
            node: callee.property,
            messageId: "missing",
            data: { repo, method: callee.property.name, key: tenantKey },
          });
        }
      },
    };
  },
};

English

You can't turn on a new rule in an old codebase and fail every build, and you can't wait until the 300 old findings are fixed either. The answer is a baseline, so only new findings fail. ESLint has this built in as bulk suppressions: a JSON file of counts per file and per rule. Two behaviours are worth knowing, and both were observed here on ESLint 10. First, the baseline counts per file, so one new finding in an already-baselined file surfaces all of that rule's findings in that file, old and new. Second, when you fix an old finding, the run exits 2 until you prune the file, which keeps the baseline from silently going stale.

بالعامية

الـ rules الجاهزة مش عارفة الـ domain بتاعك. قاعدة بتقول "أي نداء repository لازم يبقى فيه tenantId" بتساوي أكتر من 10 قواعد عامة في app multi-tenant، لأن الـ cross-tenant read هو أغلى نوع bug عندك (شوف درس 17). القاعدة دي متحفظة: لو مش قادرة تثبت إن فيه tenant، زي لما الـ where جاي من variable، بتبلّغ. ودي الفكرة: الكود الصح يبقى هو كمان الكود السهل تعمله review.

أي rule من غير tests بتبوظ مع الوقت، فـ RuleTester بيثبّت السلوك بحالات valid و invalid، وبيشتغل بـ node عادي أو جوه test runner. وخد بالك من الـ exit codes لأن الـ pipeline بيقراها: 0 نضيف، 1 فيه lint errors، 2 crash أو config غلط.

مش هتقدر تشغّل قاعدة جديدة على كود قديم وتوقّع كل الـ builds، ولا هتستنى 300 finding قديم يتصلحوا. الحل baseline عشان الجديد بس هو اللي يوقّع. ESLint بيعمل ده جاهز باسم bulk suppressions: ملف JSON فيه عدد الـ findings لكل ملف ولكل rule. سلوكين مهمين شفناهم فعلًا على ESLint 10: الأول، الـ baseline بيعدّ لكل ملف، فـ finding واحد جديد في ملف فيه قديم بيطلّع كل findings القاعدة دي في الملف، القديم والجديد. التاني، لما تصلّح finding قديم الـ run بيرجّع 2 لحد ما تعمل prune للملف، وده بيمنع الـ baseline إنه يقدم من غير ما تاخد بالك.

فين هستخدمه في شغلي؟ SaaS عندك فيه tenantId في كل جدول: انزل بالقاعدة دي على ordersRepo و invoicesRepo الأول، اعمل baseline، وخلّي أي PR جديد ممنوع يضيف نداء من غير tenant. كده الدين القديم بيقل تدريجيًا والجديد واقف عند الصفر. الغلطة الشائعة: تعمل suppress بـ eslint-disable في كل سطر من غير سبب، فبيضيع الأثر كله.
Trade-off: a strict rule vs a noisy one Reporting whenever the rule can't prove a tenant is there produces some extra findings on legitimate code. The price buys a uniform calling convention, which is what actually makes review fast. If the noise grows, fix the rule by adding a blessed helper such as ...tenantScope(user) instead of weakening the check.

// بوابة الـ dependencies: npm audit + allowlist كل entry فيها owner وسبب وتاريخ انتهاء
// الاستخدام: ⁦node audit-gate.mjs <project-dir> <allowlist.json> [YYYY-MM-DD]⁩
import { spawnSync } from "node:child_process";
import { readFileSync } from "node:fs";

const RANK = { info: 0, low: 1, moderate: 2, high: 3, critical: 4 };

export function advisoriesFrom(report, level = "high") {
  const out = [];
  for (const [pkg, vuln] of Object.entries(report.vulnerabilities ?? {})) {
    for (const via of vuln.via) {
      // الـ via لو string يبقى عابر من package تانية: الـ advisory الأصلي هيتعدّ هناك
      if (typeof via === "string" || RANK[via.severity] < RANK[level]) continue;
      out.push({ ghsa: via.url.split("/").pop(), pkg, severity: via.severity, title: via.title });
    }
  }
  return out;
}

export function decide(advisories, allowlist, today) {
  const invalid = allowlist.filter((e) => !e.ghsa || !e.owner || !e.reason || !e.expires);
  const blocking = [];
  const waived = [];
  for (const adv of advisories) {
    const entry = allowlist.find((e) => e.ghsa === adv.ghsa);
    // مقارنة التواريخ كـ string تمام لأن الصيغة ثابتة YYYY-MM-DD
    if (entry && entry.expires >= today) waived.push({ ...adv, expires: entry.expires, owner: entry.owner });
    else blocking.push({ ...adv, why: entry ? `waiver expired ${entry.expires}` : "not on allowlist" });
  }
  // الـ entries القديمة اللي مبقتش بتطابق حاجة لازم تتشال، عشان متغطيش ثغرة جاية
  const stale = allowlist.filter((e) => !advisories.some((a) => a.ghsa === e.ghsa)).map((e) => e.ghsa);
  return { ok: blocking.length === 0 && invalid.length === 0, blocking, waived, invalid, stale };
}

import { readFileSync, readdirSync, statSync } from "node:fs";
import { join, relative } from "node:path";

export function shannon(s) {
  const freq = new Map();
  for (const ch of s) freq.set(ch, (freq.get(ch) ?? 0) + 1);
  let bits = 0;
  for (const n of freq.values()) bits -= (n / s.length) * Math.log2(n / s.length);
  return bits;
}

export function scan(root, threshold = 4.5) {
  const hits = [];
  const walk = (dir) => {
    for (const name of readdirSync(dir)) {
      const p = join(dir, name);
      if (statSync(p).isDirectory()) walk(p);
      else
        readFileSync(p, "utf8").split("\n").forEach((line) => {
          for (const m of line.matchAll(/[A-Za-z0-9+/_=-]{20,}/g)) {
            if (shannon(m[0]) >= threshold) hits.push(relative(root, p).replaceAll("\\", "/"));
          }
        });
    }
  };
  walk(root);
  return hits;
}

Part 5 — Security tests as a test category 🟡 Intermediateالجزء 5 — الـ security tests كفئة اختبارات

English

Treat security checks like any other test category. Each one has a place in the pipeline, a time budget, and a clear decision: it blocks, it warns, or it doesn't exist. A check that nobody reads is theatre, and the fastest way to get there is one that takes 25 minutes on every push. Put the cheap gates on every PR and move the slow ones such as full CodeQL and DAST to main or nightly.

The orchestrator below runs each gate as its own process with a budget, treats a timeout as a block, and prints one merge decision. Semgrep and Trivy aren't installed here, so they appear as NOT-RUN, and that's exactly the status a real pipeline must never treat as a pass. The --strict flag proves it: a required gate that didn't run blocks the merge.

  on every commit     on every PR (blocking, under ~5 min)        main / nightly
  ---------------     ----------------------------------------   ------------------
  pre-commit:         secrets -> SAST rules -> deps audit         full CodeQL
  secretlint          -> security tests -> image scan              DAST on staging
  (seconds, local)    one merge decision                           (lesson 22)

Part 6 — Reviewing AI-written code 🟡 Intermediateالجزء 6 — مراجعة الكود اللي الـ AI كتبه

English

General code review of AI output is covered in section 12 · 2.8, and security questions for the LLM feature itself are in section 12 · 2.7. Here the job is narrower: the security checklist for an AI-written endpoint. AI tools produce code that compiles, reads cleanly and handles the happy path, so the review has to go against the grain and hunt for what's missing: the ownership check, the error boundary, the input bound. Five questions cover most of it: injection, authorization on every endpoint, secrets, error handling and new dependencies.

The sample below was hand-written in that style for this lesson, and it's labelled as such. It has five planted flaws, one per checklist item. All gates ran against it. Then a person wrote two extra tests after reading the code, which is the point.

Interview (exit test Q8): "The AI wrote an endpoint. What are the 5 things you review for security?" (1) Injection: is user input concatenated into SQL, a shell, HTML or a path? (2) AuthZ on every endpoint: does the handler check that this user owns this object, not only that they're logged in? (3) Secrets: anything hardcoded, logged or defaulted to a fallback value? (4) Error handling: does it fail closed and keep stack traces and internal messages out of the response? (5) Dependencies: is each new package real, needed, unpatched and not hallucinated? Then remember that a green SAST run doesn't answer (2).

const INVOICE_FIELDS = ["id", "total_cents", "customer_email"];

export function createApp(db, requireAuth) {
  const app = express();

  app.get("/invoices/:id", requireAuth, async (req, res, next) => {

  });
  return app;

Trade-off: more tools vs more review A sixth scanner adds noise and CI time, and it still can't see intent. Past a good SAST baseline, one rule that encodes your authorization convention, plus a reviewer who owns "who may see this", catches more than extra tools. Run SAST on every PR because it's mandatory, and don't let it replace the review.
Scanner سادس بيزود دوشة ووقت CI ولسه مش شايف الـ intent. بعد baseline كويس، قاعدة واحدة تثبّت طريقة الـ authorization عندك، وreviewer شايل مسؤولية "مين يقدر يشوف ده"، بيمسكوا أكتر من أدوات زيادة. شغّل SAST على كل PR لأنه إلزامي، بس متخليهوش بديل للـ review.

// الحل: نسمح بالـ expressions لو كلها constants معروفة (اسم بحروف كبيرة أو literal)
const isConstant = (e) => (e.type === "Identifier" && /^[A-Z][A-Z0-9_]*$/.test(e.name)) || e.type === "Literal";

export default {
  meta: { type: "problem", schema: [], messages: { interpolated: "Interpolated SQL in .query(): pass values as parameters." } },
  create(context) {
    return {
      'CallExpression[callee.type="MemberExpression"][callee.property.name="query"]'(node) {
        const sql = node.arguments[0];
        if (!sql) return;
        const dynamicTemplate = sql.type === "TemplateLiteral" && sql.expressions.some((e) => !isConstant(e));
        const concat = sql.type === "BinaryExpression" && sql.operator === "+";
        if (dynamicTemplate || concat) context.report({ node: sql, messageId: "interpolated" });
      },
    };
  },
};

Solution · الحل 
// الحل: أي res.json أو res.send فيه err.stack أو err.message يبقى تسريب تفاصيل للـ client
const LEAKY = new Set(["stack", "message"]);

export default {
  meta: { type: "problem", schema: [], messages: { leak: "Do not send error details to the client: log them instead." } },
  create(context) {
    return {
      'CallExpression[callee.type="MemberExpression"][callee.property.name=/^(json|send)$/]'(node) {
        for (const arg of node.arguments) {
          // بنمشي على كل الـ nodes جوه الـ argument وندوّر على err.stack أو err.message
          const stack = [arg];
          while (stack.length) {
            const n = stack.pop();
            if (n.type === "MemberExpression" && !n.computed && LEAKY.has(n.property.name) && /^(err|error|e)$/i.test(n.object.name ?? "")) {
              context.report({ node: n, messageId: "leak" });
            }
            for (const key of context.sourceCode.visitorKeys[n.type] ?? []) {
              const child = n[key];
              if (Array.isArray(child)) stack.push(...child.filter(Boolean));
              else if (child?.type) stack.push(child);
            }
          }
        }
      },
    };
  },
};

Cheat sheet · الخلاصة

  • Three strengths: text patterns, AST rules, taint analysis. Each misses what the next finds.
  • Measured here: AST rule 3 TP / 3 FP / 3 FN on 11 labelled lines. Count before you trust a tool.
  • Semgrep: LGPL engine, rules under the Rules License since Dec 2024; Opengrep is the LGPL fork.
  • Write rules for your own conventions (require-tenant-scope) and test them with RuleTester.
  • ESLint baseline: count per file, a new finding surfaces all of them, exit 2 until pruned.
  • npm audit --audit-level=high blocks; every exception needs owner, reason and expiry, and the gate fails closed.
  • Format rules and entropy miss different secrets. Entropy: 41 false positives here. Weak human secrets: both miss.
  • Deleting a secret doesn't remove it from history: rotate first.
  • Every gate gets a budget. A timeout or a missing tool blocks the merge.
  • Pin third-party actions by SHA.
  • AI review checklist: injection, authZ on every endpoint, secrets, error handling, new dependencies.
  • Tools found 3 of 5 planted flaws; missing ownership needed a person. SAST is mandatory and not sufficient.
