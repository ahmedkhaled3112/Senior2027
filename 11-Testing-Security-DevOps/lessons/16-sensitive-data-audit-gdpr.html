Why this matters · ليه ده مهم

English

Most breaches don't start with a clever exploit. They start with a log line, a dump, a backup or a key in a repo. This lesson is about knowing where personal data lives, proving who touched it, and being able to remove it when a user or a regulator asks. Senior interviews reach for exactly this: "where does PII sit in your system, and how would you delete one user?"

بالعامية

معظم الـ breaches مش بتبدأ بـ exploit ذكي. بتبدأ بسطر log، أو dump، أو backup، أو key في repo. الدرس ده عن إنك تعرف الـ personal data قاعدة فين، وتثبت مين لمسها، وتقدر تمسحها لما user أو جهة رقابية تطلب. وأسئلة الـ senior interviews بتروح لده بالظبط: "الـ PII عندك قاعدة فين، وإزاي هتمسح user واحد؟"

Part 1 — Find the leak 🟢 Basicالجزء 1 — دوّر على التسريب

English

OWASP's Top 10:2025 files this under A04:2025 Cryptographic Failures; the README's "sensitive data exposure" is the older name. The idea hasn't changed: data that should be protected is readable by someone who shouldn't be able to read it. The sample app below leaks on purpose in four classic ways: PII in logs, an unsalted fast hash, an internal call over plain HTTP, and a key committed to git.

The hash result is the one to remember. SHA-1 is fast, and no salt means identical passwords give identical hashes, so sara and mona are visibly the same before anything is cracked, and a tiny wordlist finds 5 of 6 in well under a millisecond. Password storage belongs to a slow, salted KDF such as argon2id (lesson 13). Keys and encryption at rest are in System Design lesson 38.

بالعامية

الـ OWASP Top 10:2025 بيحط ده تحت A04:2025 Cryptographic Failures، و"sensitive data exposure" اللي في الـ README هو الاسم القديم. الفكرة زي ما هي: data المفروض تبقى محمية بيقراها حد مش المفروض يقراها. التطبيق هنا بيسرّب عن قصد بـ 4 طرق كلاسيك: PII في الـ logs، hash سريع من غير salt، مكالمة داخلية على HTTP، و key اتعمل له commit في git.

أهم نتيجة هي الـ hash. الـ SHA-1 سريع، وغياب الـ salt معناه إن نفس الـ password بيدّي نفس الـ hash، فـ sara وmona باينين إنهم نفس الحاجة قبل ما تكسر أي حاجة، وقايمة صغيرة بتكسر 5 من 6 في أقل من ملي ثانية. تخزين الـ passwords مكانه KDF بطيء وبـ salt زي argon2id (درس 13). والمفاتيح والتشفير at rest في درس System Design رقم 38.

فين هستخدمه في شغلي؟ اعمل جولة ساعة واحدة في الـ codebase بتاعك: شوف logger بيطبع إيه، دور في جدول الـ users على عمود الـ password وشوف شكله، شوف الـ services الداخلية بتكلم بعض بإيه، وشغّل secret scanner على الـ history. أغلب الوقت هتلاقي واحدة على الأقل من الأربعة.

Part 2 — Audit trails 🟡 Intermediateالجزء 2 — الـ audit trails

English

An audit trail answers "who did what, to what, when, and from where", and it has to survive the person being investigated. Log three families of events: authentication (login success and failure, password change, MFA), permission changes (role granted, API key created), and sensitive reads (an agent opening a customer record, an export). The design options are compared in Databases lesson 21 and System Design lesson 38, part 6; here we build the tamper-evident version.

Two independent controls. Privileges and a blocking trigger make it append-only: the app role has only INSERT and SELECT, and even the owner hits the trigger. A hash chain makes tampering detectable by anyone who bypasses those, since each row's hash covers the previous hash.

Building this surfaced a trap. With a bigserial column the sequence value is drawn when the row is created, before the BEFORE INSERT trigger takes the advisory lock, so ids and chain order diverge under concurrency: the first version reported chain breaks even with the lock. The id must be assigned inside the trigger, after the lock.

Retention has to be designed in: keep the period your regulator or auditor requires, and delete deliberately. Here only the owner can delete old rows, and a checkpoint holds the last deleted hash so the remaining chain stays verifiable. In production, drop monthly partitions instead of deleting rows.

  row 1              row 2               row 3
  prev: genesis      prev: hash(1)       prev: hash(2)
  login ok           role granted        customer export
  hash(1) ─────────▶ hash(2) ──────────▶ hash(3)

  edit row 2 ==> its hash no longer matches ==> verifyChain: [ 2 ]
كل صف فيه الـ hash بتاع اللي قبله، وأول صف بيبدأ من genesis. لو حد عدّل صف 2، الـ hash المحسوب مش هيطابق المتخزن، فالفحص بيقول [ 2 ]. يعني مش بس عارفين إن فيه تلاعب، عارفين فين.
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";
import pg from "pg";

if (!process.env.DATABASE_URL) throw new Error("set DATABASE_URL");
const admin = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 20 });

// الـ id بيتاخد جوه الـ trigger بعد الـ lock: لو اتاخد قبله، ترتيب الـ ids هيختلف عن ترتيب الـ chain
const ddl = (table: string, withLock: boolean) => `
  CREATE SEQUENCE ${table}_id_seq;
  CREATE TABLE ${table} (
    id        bigint PRIMARY KEY,
    at        timestamptz NOT NULL DEFAULT now(),
    actor     text NOT NULL,
    action    text NOT NULL,
    target    text NOT NULL,
    meta      jsonb NOT NULL DEFAULT '{}',
    prev_hash text NOT NULL,
    hash      text NOT NULL
  );
  CREATE FUNCTION ${table}_chain() RETURNS trigger LANGUAGE plpgsql AS $f$
  BEGIN
    ${withLock ? `PERFORM pg_advisory_xact_lock(hashtext('${table}'));` : ""}
    NEW.id := nextval('${table}_id_seq');
    SELECT coalesce((SELECT hash FROM ${table} ORDER BY id DESC LIMIT 1), 'genesis') INTO NEW.prev_hash;
    NEW.hash := row_hash(NEW.prev_hash, NEW.at, NEW.actor, NEW.action, NEW.target, NEW.meta);
    RETURN NEW;
  END $f$;
  CREATE TRIGGER ${table}_chain_t BEFORE INSERT ON ${table} FOR EACH ROW EXECUTE FUNCTION ${table}_chain();
  CREATE TRIGGER ${table}_no_mutate BEFORE UPDATE OR DELETE ON ${table} FOR EACH ROW EXECUTE FUNCTION forbid_mutation();
  CREATE TRIGGER ${table}_no_truncate BEFORE TRUNCATE ON ${table} FOR EACH STATEMENT EXECUTE FUNCTION forbid_mutation();
`;

await admin.query(`
  CREATE FUNCTION row_hash(p text, at timestamptz, actor text, action text, target text, meta jsonb) RETURNS text
  LANGUAGE sql IMMUTABLE AS $f$
    SELECT encode(sha256(convert_to(p || '|' || extract(epoch from at)::text || '|' || actor || '|' || action || '|' || target || '|' || meta::text, 'UTF8')), 'hex')
  $f$;
  CREATE FUNCTION forbid_mutation() RETURNS trigger LANGUAGE plpgsql AS $f$
  BEGIN RAISE EXCEPTION 'audit log is append-only'; END $f$;
  ${ddl("audit_log", true)}
  ${ddl("audit_nolock", false)}
  CREATE TABLE user_roles (user_id text PRIMARY KEY, role text NOT NULL);
  CREATE TABLE audit_checkpoint (last_id bigint PRIMARY KEY, last_hash text NOT NULL, created_at timestamptz DEFAULT now());
  CREATE ROLE app_user LOGIN;
  GRANT SELECT, INSERT ON audit_log, audit_nolock, audit_checkpoint TO app_user;
  GRANT USAGE ON SEQUENCE audit_log_id_seq, audit_nolock_id_seq TO app_user;
`);

const asApp = async <T>(fn: (c: pg.PoolClient) => Promise<T>) => {
  const c = await admin.connect();
  try {
    await c.query("SET ROLE app_user");
    return await fn(c);
  } finally {
    await c.query("RESET ROLE");
    c.release();
  }
};

const record = (actor: string, action: string, target: string, meta = {}) =>
  admin.query("INSERT INTO audit_log (actor, action, target, meta, prev_hash, hash) VALUES ($1, $2, $3, $4, '', '')", [actor, action, target, meta]);

// الفحص بيبدأ من آخر checkpoint: أي صف اتغير أو اتمسح من النص بيبان هنا
async function verifyChain(table: string) {
  const { rows } = await admin.query(`
    SELECT id FROM (
      SELECT *, lag(hash) OVER (ORDER BY id) AS real_prev,
             row_hash(prev_hash, at, actor, action, target, meta) AS computed
      FROM ${table}
    ) s
    WHERE hash <> computed
       OR prev_hash <> coalesce(real_prev, (SELECT last_hash FROM audit_checkpoint ORDER BY last_id DESC LIMIT 1), 'genesis')
    ORDER BY id`);
  return rows.map((r) => Number(r.id));
}

بالعامية

الـ audit trail بيجاوب "مين عمل إيه، لأنهي حاجة، إمتى، ومنين"، ولازم يفضل موجود حتى لو الشخص ده هو اللي بيتحقق معاه. سجّل 3 عائلات من الـ events: الـ authentication (login ناجح وفاشل، تغيير password، MFA)، وتغيير الصلاحيات (role اتدى، API key اتعمل)، والقراءات الـ sensitive (موظف فتح بيانات عميل، export). المقارنة بين طرق التصميم في درس Databases رقم 21 ودرس System Design رقم 38، الجزء 6، وهنا بنبني النسخة اللي بتكشف التلاعب.

فيه حاجتين مستقلين. الصلاحيات مع trigger بيوقّف التعديل بيخلوها append-only: الـ app role معاه INSERT وSELECT بس، وحتى الـ owner بيخبط في الـ trigger. والـ hash chain بتخلي التلاعب مكشوف لأي حد عدّى الاتنين دول، لأن كل صف الـ hash بتاعه بيغطي الـ hash اللي قبله.

وأنا ببني ده طلعلي فخ. لو العمود bigserial الـ sequence بيتسحب وقت إنشاء الصف، قبل ما الـ BEFORE INSERT trigger ياخد الـ advisory lock، فترتيب الـ ids وترتيب الـ chain بيختلفوا تحت الـ concurrency: أول نسخة طلّعت chain breaks حتى مع الـ lock. الـ id لازم يتاخد جوه الـ trigger بعد الـ lock.

Trade-off: what the hash chain does not prove A hash chain detects edits, but someone with full DB access can recompute every hash after their edit. To stop that, regularly copy the latest hash somewhere that person can't write: another account, or object storage with a retention lock (not run here). Serializing writers with one advisory lock also caps throughput on this table, which is why the audit table holds security events and not every request. High-volume access logs go to a log pipeline.
الـ hash chain بيكشف التعديل، بس حد معاه full DB access يقدر يعيد حساب كل الـ hashes بعد ما يعدّل. عشان تمنع ده، انسخ آخر hash بانتظام لمكان الشخص ده ميقدرش يكتب فيه: account تاني، أو object storage بـ retention lock (مش متشغّل هنا). وكمان الـ advisory lock الواحد بيحط سقف للـ throughput على الجدول ده، وعشان كده الجدول فيه الـ security events بس، مش كل request. الـ access logs الكبيرة تروح لـ log pipeline.
Interview question "How do you make an audit log immutable?" → Privilege separation first: the application role can only insert and read. Then a trigger blocking updates and deletes. Then a hash chain so that tampering by someone with higher privileges is detectable, plus the latest hash copied outside the database so a full rewrite is detectable too. And an alert when the verification fails, because a log nobody checks doesn't protect you.
"إزاي تخلي الـ audit log immutable؟" ← الأول فصل الصلاحيات: الـ application role يعمل insert و read بس. بعدها trigger يمنع الـ update والـ delete. بعدها hash chain عشان التلاعب من حد بصلاحيات أعلى يبان، وآخر hash يتنسخ بره الـ database عشان إعادة الكتابة الكاملة تبان برضه. ومعاه alert لما الفحص يفشل، لأن log محدش بيفحصه مش بيحميك.

Redaction works on paths, and that leaves three holes: the same field under another key or at another depth (customers[0].email isn't covered by user.email, and items[*].email only matches that exact shape), values inside a message string, and values inside err.message, which is where a Postgres duplicate-key error puts the email.

Part 4 — Classification & field encryption 🟡 Intermediateالجزء 4 — التصنيف وتشفير الـ fields

English

You can't protect data you haven't located, as System Design lesson 38, part 5 explains. Keep a classification map per column in the repo, and make it enforceable: a test reads information_schema and fails on any unclassified column, so the conversation about date_of_birth happens in the PR that adds it. The cheapest protection is often to not have the data: this feature only needed to know the user is an adult, so a boolean replaced the birth date.

For fields you must keep, application-level encryption differs from disk encryption in one way that matters: where the key lives. Disk encryption (AWS EBS, LUKS; not run here) protects against someone walking off with the disk. The database still decrypts for anyone who can connect, so a SQL injection, a stolen app credential or a pg_dump all see plaintext. With AES-256-GCM in the application, the database and its dumps hold only ciphertext.

Encrypted columns can't be queried, so add a blind index: an HMAC of the normalized value under a separate key, which supports equality lookups and nothing else. Two details: use the authenticated data (AAD) to bind ciphertext to its row and column, so a row's value can't be swapped into another row; and never blind-index low-cardinality fields like gender or country, because equal values give equal indexes and that reveals the distribution.

const DATA_KEY = randomBytes(32);
const INDEX_KEY = randomBytes(32);

function encrypt(plain: string, aad: string): string {
  const iv = randomBytes(12);
  const c = createCipheriv("aes-256-gcm", DATA_KEY, iv);
  c.setAAD(Buffer.from(aad));
  const ct = Buffer.concat([c.update(plain, "utf8"), c.final()]);
  return Buffer.concat([iv, c.getAuthTag(), ct]).toString("base64");
}
function decrypt(blob: string, aad: string): string {
  const b = Buffer.from(blob, "base64");
  const d = createDecipheriv("aes-256-gcm", DATA_KEY, b.subarray(0, 12));
  d.setAAD(Buffer.from(aad));
  d.setAuthTag(b.subarray(12, 28));
  return Buffer.concat([d.update(b.subarray(28)), d.final()]).toString("utf8");
}

English

The GDPR needs a lawful basis (Article 6) for each processing purpose: consent, contract, legal obligation, vital interests, public task, or legitimate interests. For a developer, the practical effect is that the same data can have different bases. An order address is needed under contract, marketing emails need consent, and an invoice is kept under a legal obligation. That's why "delete my account" doesn't mean deleting everything.

Rights that turn into code: access (Article 15) and portability (Article 20) are an export function, and erasure (Article 17) is a delete function with exceptions such as legal obligations. Personal data spreads across your tables, Redis, object storage, search, analytics and logs, so the hard engineering is fan-out and proof. deleteUser below records an erasure job in the same transaction as the database change, so a crash between the database and Redis leaves work that can be finished, and a verification query looks for what's left instead of assuming success.

Backups need a policy too: you usually can't edit them, so they expire, and crypto-shredding (System Design lesson 38, part 6) handles the rest.

// الـ store الخارجي في transaction منفصلة: بنسجل job الأول عشان لو حصل crash نقدر نكمل
export async function deleteUser(userId: number, crashAfterCommit = false) {
  const c = await db.connect();
  try {
    await c.query("BEGIN");
    const u = await c.query("SELECT email FROM users WHERE id = $1 FOR UPDATE", [userId]);
    if (u.rowCount === 0) throw new Error("no such user");
    await c.query("INSERT INTO erasure_jobs (user_id, email) VALUES ($1, $2) ON CONFLICT DO NOTHING", [userId, u.rows[0].email]);
    // الفاتورة نفسها لازم تفضل (legal obligation)، بس الاسم بيتشال منها
    await c.query("UPDATE invoices SET customer_name = '[erased]' WHERE order_id IN (SELECT id FROM orders WHERE user_id = $1)", [userId]);
    await c.query("UPDATE orders SET shipping_address = NULL WHERE user_id = $1", [userId]);
    await c.query("DELETE FROM users WHERE id = $1", [userId]);
    await c.query("COMMIT");
  } catch (e) {
    await c.query("ROLLBACK");
    throw e;
  } finally {
    c.release();
  }
  if (crashAfterCommit) throw new Error("simulated crash between the DB and Redis");
  await finishErasure();
}

async function finishErasure() {
  const { rows } = await db.query("SELECT user_id FROM erasure_jobs WHERE status = 'pending'");
  for (const { user_id: id } of rows) {
    await redis.del(`session:${id}`, `cart:${id}`);
    rmSync(join(BUCKET, "avatars", `${id}.png`), { force: true });
    await db.query("UPDATE erasure_jobs SET status = 'done' WHERE user_id = $1", [id]);
  }
  return rows.length;
}

async function verifyErased(userId: number, email: string) {
  const left: string[] = [];
  const scan = async (label: string, sql: string, params: unknown[]) => {
    const r = await db.query(sql, params);
    if (r.rowCount) left.push(`${label}: ${r.rowCount}`);
  };
  await scan("users", "SELECT 1 FROM users WHERE id = $1 OR email = $2", [userId, email]);
  await scan("orders.user_id", "SELECT 1 FROM orders WHERE user_id = $1", [userId]);
  await scan("orders.address", "SELECT 1 FROM orders o WHERE o.id = 10 AND o.shipping_address IS NOT NULL", []);
  await scan("invoices.name", "SELECT 1 FROM invoices WHERE customer_name = 'Sara Ali'", []);
  await scan("support_notes", "SELECT 1 FROM support_notes WHERE user_id = $1 OR note ILIKE '%' || $2 || '%'", [userId, email]);
  for await (const keys of redis.scanStream({ match: `*:${userId}` })) {
    if ((keys as string[]).length) left.push(`redis: ${(keys as string[]).join(",")}`);
  }
  if (readdirSync(join(BUCKET, "avatars")).some((f) => f.startsWith(`${userId}.`))) left.push("bucket: avatar");
  return left;
}

Part 6 — Anonymization vs pseudonymization 🟡 Intermediateالجزء 6 — الـ anonymization والـ pseudonymization

English

Pseudonymization (Article 4(5)) replaces identifiers with a token that can be linked back using separate information, such as a key. Anonymization means no one can reasonably identify the person any more. The legal difference is large: pseudonymized data is still personal data, so GDPR still applies, while truly anonymous data falls outside it (Recital 26). The run shows why: an HMAC export has no names, yet anyone with the key can recompute every token from a list of emails, so the export can be reversed.

Removing names also isn't anonymization, because the remaining columns can identify a person. k-anonymity measures this: group rows by their quasi-identifiers (zip, birth year, gender), and k is the size of the smallest group. A group of 1 means that row is unique. The join below links the export to a public-style list and re-identifies people, including what they bought, using no secrets. Generalizing the columns raises k and the join stops working. k-anonymity has known limits: if everyone in a group has the same sensitive value, that value is still revealed, which is why l-diversity exists.

const exported = orders.map((o) => ({ uid: pseudo(o.email), zip: o.zip, birthYear: o.birthYear, gender: o.gender, item: o.item }));
console.log("pseudonymized row:", JSON.stringify(exported[2]));

// أي حد معاه الـ key وقايمة الـ emails يرجّع كل صف لصاحبه
const reverse = new Map(orders.map((o) => [pseudo(o.email), o.email]));
console.log("with the key     :", exported[2].uid, "->", reverse.get(exported[2].uid));

// (2) الـ k-anonymity: كل مجموعة quasi-identifiers لازم تحتوي k صفوف على الأقل
type QI = (r: typeof exported[number]) => string;
const kAnonymity = (qi: QI) => {
  const groups = new Map<string, number>();
  for (const r of exported) groups.set(qi(r), (groups.get(qi(r)) ?? 0) + 1);
  return { k: Math.min(...groups.values()), singletons: [...groups.values()].filter((n) => n === 1).length, groups: groups.size };
};
const raw: QI = (r) => `${r.zip}|${r.birthYear}|${r.gender}`;
const generalized: QI = (r) => `${r.zip.slice(0, 2)}xxx|${Math.floor(r.birthYear / 10) * 10}s`;
console.log("raw quasi-ids    :", kAnonymity(raw));
console.log("generalized      :", kAnonymity(generalized));

const publicList = [
  { name: "Mona Hassan", zip: "12611", birthYear: 1985, gender: "F" },

  }
  console.log(`${label}: ${hits.length}/${publicList.length} unique matches`, hits);
};

بالعامية

الـ pseudonymization (المادة 4(5)) بيبدّل الـ identifiers بـ token ينفع يرجع للشخص بمعلومة منفصلة زي key. الـ anonymization معناها مفيش حد يقدر بشكل معقول يعرف الشخص تاني. الفرق القانوني كبير: الـ pseudonymized data لسه personal data والـ GDPR لسه بيطبق، أما الـ anonymous data بجد بره نطاقه (Recital 26). الـ run بيوريك ليه: الـ HMAC export مفيهوش أسماء، بس أي حد معاه الـ key يقدر يعيد حساب كل الـ tokens من قايمة emails، فالـ export يتعكس.

وكمان شيل الأسماء مش anonymization، لأن الأعمدة الباقية ممكن تحدد الشخص. الـ k-anonymity بيقيس ده: جمّع الصفوف بالـ quasi-identifiers (zip، سنة الميلاد، النوع)، و k هو حجم أصغر مجموعة. مجموعة من 1 معناها الصف ده فريد. الـ join هنا بيربط الـ export بقايمة شكلها عام ويعرف الناس وإيه اللي اشتروه، من غير أي secrets. لما تعمل generalization للأعمدة k بيعلى والـ join بيبطل يشتغل. والـ k-anonymity ليه حدود: لو كل المجموعة ليها نفس القيمة الحساسة، القيمة دي بتنكشف برضه، وعشان كده فيه l-diversity.

فين هستخدمه في شغلي؟ لما الـ data team تطلب dump للـ analytics أو staging فيه بيانات حقيقية: لو عملت HMAC بس يبقى لسه personal data وعليها كل الالتزامات. وللـ staging استخدم data متولدة (Faker). ولو هتبعت export لفريق تاني، احسب k قبل ما تبعت.

الـ pseudonymized ينفع يترجع بمعلومة زيادة زي key أو جدول، ولسه personal data، وكويس للـ analytics الداخلية وتقليل التعرض وربط الـ datasets، وخطره إن الـ key يتسرب أو تعامله كأنه anonymous. الـ anonymized مينفعش يترجع بأي طريقة معقولة، ومش personal data، وكويس للنشر والمشاركة والاحتفاظ بعد الـ retention، وخطره الـ re-identification عن طريق الـ joins.
Interview question "We hashed the emails, so the export is anonymous, right?" → No. A plain hash of an email can be reversed with a list of emails. A keyed HMAC can be reversed by whoever has the key, so it's pseudonymization and still personal data. And the other columns may identify people on their own: check k-anonymity on the quasi-identifiers. Whether a specific recipient without the key is processing personal data is a legal question, so ask your DPO.
"إحنا عملنا hash للإيميلات، يبقى الـ export anonymous صح؟" ← لأ. الـ hash العادي للإيميل بيتعكس بقايمة إيميلات. والـ HMAC بمفتاح بيتعكس لأي حد معاه المفتاح، فده pseudonymization ولسه personal data. والأعمدة التانية ممكن تحدد الناس لوحدها: احسب الـ k-anonymity على الـ quasi-identifiers. أما هل مستلم معين من غير المفتاح بيعالج personal data ولا لأ، فده سؤال قانوني، فاسأل الـ DPO.

❌ Log the whole request

❌ "We're encrypted at rest" 
-- القرص متشفر، بس الـ dump بيطلع plaintext

الـ disk encryption مبيحميش من حد عنده connection أو dump، لأن الـ database بتفك التشفير لأي حد يتوصل. الصح تشفر الـ fields الحساسة في الـ application وتستخدم blind index للبحث.

❌ Hash chain with a serial id

الـ bigserial بيجيب الرقم قبل الـ trigger، فتحت الـ concurrency الـ chain بتبان مكسورة. الصح تاخد الـ lock وبعدين تاخد الـ id جوه الـ trigger.

Solution · الحل 
import { createHmac, randomBytes } from "node:crypto";

const INDEX_KEY = randomBytes(32);

// التطبيع لازم يبقى قبل الـ HMAC: أي اختلاف في الشكل بيطلّع index مختلف تمامًا
function normalizeEgyptianPhone(input: string): string {
  const digits = input.replace(/[^\d]/g, "");
  if (digits.startsWith("0020")) return "+20" + digits.slice(4);
  if (digits.startsWith("20")) return "+20" + digits.slice(2);
  if (digits.startsWith("0")) return "+20" + digits.slice(1);
  return "+20" + digits;
}

const bidx = (v: string) => createHmac("sha256", INDEX_KEY).update(v).digest("hex").slice(0, 16);

const forms = ["+20 100 000 0001", "0020-100-000-0001", "01000000001", "20 1000000001"];
const normalized = forms.map(normalizeEgyptianPhone);
console.log(normalized);
console.log("one index for all forms:", new Set(normalized.map(bidx)).size === 1);
console.log("without normalization  :", new Set(forms.map(bidx)).size, "different indexes");

Cheat sheet · الخلاصة

  • A04:2025 Cryptographic Failures is the current name for sensitive data exposure. Look in logs, git history, internal HTTP and password columns.
  • Unsalted fast hashes give equal hashes for equal passwords. Use argon2id. A key in git history means rotate.
  • Audit trail: who, what, target, when, from where. Auth events, permission changes, sensitive reads, in the same transaction as the change.
  • Append-only: least privilege, a blocking trigger, a hash chain, and the latest hash copied outside the database.
  • Assign chain ids inside the trigger after the lock, or concurrency makes the chain look broken.
  • A09:2025 includes alerting: a log nobody is alerted on doesn't protect you.
  • redact works on paths only. Text and err.message pass through. Add a lint rule and a PII canary test.
  • Classify every column, fail CI on unclassified ones, and drop what you don't need.
  • Disk encryption doesn't protect against the app or a dump. AES-GCM with AAD and a blind index does, for equality lookups only.
  • GDPR: a lawful basis per purpose, export and erasure functions, fan-out with a job and verification, DPAs, residency, 72 hours.
  • Pseudonymized data is still personal data. Anonymized data isn't, and removing names doesn't get you there: measure k and test joins.
بالعامية
  • الـ A04:2025 Cryptographic Failures هو الاسم الحالي لـ sensitive data exposure. دوّر في الـ logs والـ git history والـ HTTP الداخلي وأعمدة الـ passwords.
  • الـ hash السريع من غير salt بيدّي نفس الـ hash لنفس الـ password. استخدم argon2id. والـ key في الـ git history معناه rotate.
  • الـ audit trail: مين، إيه، على إيه، إمتى، منين. الـ auth events وتغيير الصلاحيات والقراءات الـ sensitive، في نفس الـ transaction مع التغيير.
  • الـ append-only: أقل صلاحيات، و trigger بيوقّف التعديل، و hash chain، وآخر hash يتنسخ بره الـ database.
  • الـ ids بتاعة الـ chain تتاخد جوه الـ trigger بعد الـ lock، وإلا الـ concurrency تخلي الـ chain تبان مكسورة.
  • الـ A09:2025 فيها alerting: log محدش بيتنبّه عليه مش بيحميك.
  • الـ redact شغال على الـ paths بس، والنص وerr.message بيعدّوا. ضيف lint rule و PII canary test.
  • صنّف كل عمود، وخلّي الـ CI يقع على غير المصنّف، وشيل اللي مش محتاجه.
  • الـ disk encryption مبيحميش من الـ app أو الـ dump. الـ AES-GCM مع AAD و blind index بيحموا، والبحث equality بس.
  • الـ GDPR: lawful basis لكل غرض، و export و erasure functions، و fan-out بـ job وفحص، و DPAs، و residency، و 72 ساعة.
  • الـ pseudonymized data لسه personal data. الـ anonymized لأ، وشيل الأسماء مبيوصلكش لده: احسب k وجرّب الـ joins.
