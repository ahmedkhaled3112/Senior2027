Why this matters · ليه ده مهم

English

Every team that runs software eventually spends part of its week on work that keeps the lights on and leaves nothing behind. Left alone, that work grows with your customers while your headcount doesn't. A senior engineer is expected to put a number on it, remove the expensive part, and then stop other teams from re-solving the same problem, which is what platform engineering is. The hard half of the job is knowing when not to build one: an internal platform nobody needs is an expensive mistake. Interviewers use this topic to separate people who have run systems from people who have only built them.

بالعامية

أي فريق بيشغّل software بييجي عليه وقت يلاقي جزء من أسبوعه رايح في شغل بيخلّي الدنيا ماشية ومش بيسيب وراه أي حاجة. لو سبته، الشغل ده بيكبر مع عدد العملاء، وعدد الفريق مبيكبرش بنفس السرعة. المتوقع من الـ senior إنه يحط رقم على ده، يشيل الجزء الغالي، وبعدين يمنع باقي الفرق إنها تحل نفس المشكلة كل واحد لوحده، وده اللي اسمه platform engineering. والنص الصعب في الشغلانة إنك تعرف إمتى متبنيش: platform داخلية محدش محتاجها غلطة غالية. والـ interviewers بيستخدموا الموضوع ده عشان يفرّقوا بين اللي شغّل systems بجد واللي بناها وبس.

Part 1 — Measuring toil 🔴 Advancedالجزء 1 — قياس الـ toil

English

The SRE book defines toil as work tied to running a production service that tends to be manual, repetitive, automatable, tactical, devoid of enduring value, and that scales linearly as the service grows. Each word is a test. The first time you debug a new failure isn't toil, because it isn't repetitive and you learn from it. A postmortem isn't toil, because it has lasting value. A team meeting isn't toil either: the book calls that overhead, work not directly tied to running the service. Google's SRE organization has an advertised goal of keeping toil below 50% of each SRE's time.

You can't reduce what you haven't counted, and people are poor judges of where their own time goes: they remember what was annoying, not what was expensive. So the first step is boring on purpose. Take whatever log you have (tickets, on-call notes, a shared sheet), classify each row, and rank by hours, not by count. The script below does that on a sample log: 649 rows for 3 engineers over 13 weeks. The data is generated for this lesson, not taken from a real team. Unmatched rows land in an explicit unclassified bucket, so a gap in the rules is visible instead of silently disappearing.

Two details matter when you read the result. Pick one denominator and keep it, because toil as a share of capacity (1,560 h) and as a share of logged time (about 1,054 h) are different numbers. And look at the trend: 12.8% of logged time in August and 22.8% in October is the O(n) growth the definition warns about, even though the quarterly total of 11.5% of capacity looks comfortable.

English

Now automate the top item, and treat the automation as a production change, because a script that replays webhooks can double-charge a customer as fast as it can fix one. Four guardrails carry most of the safety: dry-run by default, a cap on how much one run can touch, a stable idempotency key so a second run is harmless, and a stop condition when the other side is clearly down. Every action goes to an audit file. In this run the receiver is a labelled stand-in on loopback, not a real customer endpoint, so it doesn't capture real latency, rate limits or a customer's own retry behaviour.

// أتمتة أعلى بند toil: إعادة إرسال الـ webhooks الفاشلة
// الـ receiver هنا stand-in محلي على loopback بدل الـ endpoints الحقيقية بتاعة العملاء
import { appendFileSync, rmSync } from "node:fs";
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";

type Failed = { id: string; tenant: string; event: string };
type Options = { apply: boolean; maxRuns: number; stopAfterFailures: number };

const AUDIT = "replay-audit.jsonl";
const audit = (e: object) => appendFileSync(AUDIT, JSON.stringify({ ...e }) + "\n");

export async function replay(items: Failed[], baseUrl: string, o: Options) {
  // السقف ده بيحدد أكبر ضرر ممكن لو الـ script نفسه غلط
  const batch = items.slice(0, o.maxRuns);
  const skipped = items.length - batch.length;
  if (!o.apply) {
    console.log(`DRY RUN: would replay ${batch.length}, held back by cap ${skipped}. Add --apply to send.`);
    return { sent: 0, failed: 0, skipped, aborted: false };
  }
  let sent = 0, failed = 0, streak = 0;
  for (const item of batch) {
    // الـ key ثابت لكل event: لو الـ script اتشغل مرتين العميل ميتحاسبش مرتين
    const res = await fetch(`${baseUrl}/${item.tenant}`, {
      method: "POST",
      headers: { "content-type": "application/json", "idempotency-key": item.id },
      body: JSON.stringify({ event: item.event }),
    });
    audit({ id: item.id, tenant: item.tenant, status: res.status });
    if (res.ok) { sent++; streak = 0; continue; }
    failed++; streak++;
    // لو الـ endpoint واقع، الضغط عليه بأكتر من كده مش هيفيد
    if (streak >= o.stopAfterFailures) {
      console.log(`ABORT: ${streak} failures in a row at ${item.id}, leaving the rest queued`);
      return { sent, failed, skipped: items.length - sent - failed, aborted: true };
    }
  }
  return { sent, failed, skipped, aborted: false };
}

English

The last step is the one most teams skip: did it pay for itself? The inputs are the 195 occurrences and 21.5 minutes from the report, plus assumptions written in the code: 24 hours to build, 2 hours a month to maintain, 3 minutes of residual human review per occurrence, and 8% monthly growth in volume. "Never" in the output means not within those 13 weeks.

// الأرقام جاية من الـ report، والافتراضات مكتوبة صراحةً تحت
type Input = {
  occurrences: number; minutesEach: number; residualMinutes: number;
  buildHours: number; maintenanceHoursPerMonth: number; growthPerMonth: number;
};

function payback(i: Input, weeks: number) {
  const perWeek = i.occurrences / 13;
  let saved = 0;
  let cost = i.buildHours;
  let breakEvenWeek: number | null = null;
  for (let w = 1; w <= weeks; w++) {
    // عدد المرات بيكبر كل شهر (4.33 أسبوع) مع زيادة الـ tenants
    const volume = perWeek * Math.pow(1 + i.growthPerMonth, w / 4.33);
    saved += (volume * (i.minutesEach - i.residualMinutes)) / 60;
    cost += i.maintenanceHoursPerMonth / 4.33;
    if (breakEvenWeek === null && saved >= cost) breakEvenWeek = w;
  }
  return { savedHours: saved, costHours: cost, netHours: saved - cost, breakEvenWeek };
}

// الافتراضات: بناء 24 ساعة، صيانة ساعتين في الشهر، 3 دقايق مراجعة، نمو 8% في الشهر

بالعامية

الـ SRE book بيعرّف الـ toil إنه شغل مرتبط بتشغيل service في production وبيبقى manual، repetitive، automatable، tactical، ومالوش قيمة بتفضل، وبيكبر خطيًا مع كبر الـ service. وكل كلمة منهم اختبار. أول مرة تـ debug مشكلة جديدة مش toil لأنها مش متكررة وإنت بتتعلم. الـ postmortem مش toil لأن قيمته بتفضل. والاجتماع برضه مش toil، الكتاب بيسميه overhead، يعني شغل مش مرتبط مباشرة بتشغيل الـ service. ومنظمة الـ SRE في Google عندها هدف معلن: الـ toil يفضل أقل من 50% من وقت كل SRE.

مش هتعرف تقلل حاجة معدّتهاش، والناس مش بتعرف وقتها راح فين: بيفتكروا اللي ضايقهم مش اللي كلّفهم. عشان كده أول خطوة مملة بالقصد: هات أي log عندك (tickets، on-call notes، شيت مشترك)، صنّف كل صف، ورتّب بالـ ساعات مش بعدد المرات. الـ script فوق بيعمل كده على log تجريبي: 649 صف لـ 3 مهندسين في 13 أسبوع. الداتا دي متولّدة للدرس، مش من فريق حقيقي. والصفوف اللي مطابقتش أي rule بتروح في unclassified صريحة، فالنقص في الـ rules بيبان بدل ما يختفي.

فيه حاجتين مهمين وإنت بتقرا النتيجة. اختار مقام واحد وخليك عليه، لأن الـ toil كنسبة من الـ capacity (1,560 ساعة) غير نسبته من الوقت المتسجل (حوالي 1,054 ساعة). وبص على الاتجاه: 12.8% من الوقت المتسجل في أغسطس و22.8% في أكتوبر، ده النمو الـ O(n) اللي التعريف بيحذر منه، حتى لو الرقم الإجمالي 11.5% من الـ capacity شكله مريح.

بعد كده أتمت أكبر بند، وعامل الأتمتة كأنها تغيير في production، لأن script بيعيد إرسال webhooks ممكن يحاسب العميل مرتين بنفس سرعة ما بيصلّح. 4 حواجز بيشيلوا معظم الأمان: dry run افتراضي، سقف على اللي التشغيلة الواحدة تقدر تلمسه، idempotency key ثابت عشان التشغيلة التانية متعملش ضرر، وشرط وقوف لما الطرف التاني واقع بوضوح. وكل عملية بتتسجل في audit file. الـ receiver في التشغيلة دي stand-in محلي على loopback وعليه label، مش endpoint عميل حقيقي، فمش بيغطي الـ latency الحقيقية ولا الـ rate limits ولا الـ retries اللي العميل نفسه بيعملها.

آخر خطوة وأكتر خطوة الفرق بتنساها: هل رجّعت اللي اتصرف؟ المدخلات هي الـ 195 مرة والـ 21.5 دقيقة من الـ report، ومعاهم افتراضات مكتوبة في الكود: 24 ساعة بناء، ساعتين صيانة في الشهر، 3 دقايق مراجعة بشرية لكل مرة، و8% نمو شهري في الحجم. وكلمة never في الـ output معناها مش جوه الـ 13 أسبوع دول.

فين هستخدمه في شغلي؟ لو إنت في SaaS وبتتعب من "ابعتلي الـ webhook تاني للعميل ده": ابدأ بشيت بسيط أسبوعين، صنّف، ورتّب بالساعات. اكتب script زي replay-webhooks.ts بـ dry run و cap و idempotency key، وشغّله من cron أو من BullMQ job لما الـ failure يتكرر. وخد الرقم للـ manager: "وفّرنا 38 ساعة في الربع"، مش "عملت script حلو". والغلطة الشائعة إنك تأتمت اللي ضايقك امبارح، زي disk-cleanup، وتخسر 22.6 ساعة وإنت فاكر إنك بتوفّر.
Interview question "What's the difference between toil and other work you don't enjoy, and how would you reduce it?" → Toil is manual, repetitive, automatable, tactical, has no enduring value and grows with the service. Trade-off: how much to generate Generate too little and every team reinvents the hard parts. Generate too much and you've copied a framework into every repo, where each copy now drifts on its own. A good rule is to generate the things that differ per service (name, owner, routes) and pull the things that should stay identical (the CI logic, the base image) from one shared place, such as a reusable workflow. The cost of that second choice is a shared dependency that can break every service at once, so it needs versioning.

Part 3 — Self-service environments 🔴 Advancedالجزء 3 — بيئات self-service

English

Lesson 30 built preview environments driven by CI: a database cloned with CREATE DATABASE ... TEMPLATE, an app process on its own port, and a leak detector. A platform takes that mechanism and hands it to developers directly, which adds a new set of problems. Once anyone can create an environment, you need quotas so one team can't eat the cluster, expiry so "temporary" stays temporary, and an owner on everything so there's a person to ask.

The interesting bug is in the quota. "Count, then insert" is two steps, and under concurrency several requests read the same count before any of them commits. The run below fires 8 concurrent creates at a quota of 2: without a lock it accepted 2, 4 and 4 in three runs, which is exactly the kind of bug that passes every sequential test. With a transaction-scoped advisory lock it accepted 2 every time. The lock here is global on purpose, because the platform-wide limit has to be checked atomically too. Per-team locks would be finer-grained but would race on that global limit.

Provisioning has a second trap: CREATE DATABASE can't run inside a transaction block. So the flow is a reservation first (a row with status provisioning, committed), then the slow work outside the transaction, then the status update. If provisioning fails, the code removes the reservation, otherwise a failed create would consume quota forever. The reaper handles the rest: it destroys anything past expires_at and reports databases with no registry row, which is what a crash mid-provision leaves behind. The listings show the reservation, the create command and the reaper. The list, extend and destroy commands are plumbing.

Stand-in: no Kubernetes, DNS, TLS or real cost This is a labelled stand-in. What's real: Postgres, the TEMPLATE clones, the app processes, the concurrency behaviour of the quota. What it doesn't capture: namespaces and network isolation, ingress and certificates, per-environment cost, and identity. Anyone can destroy any environment here, while a real platform would take the caller's identity from SSO. Each command is the same main(argv) a shell would call, run in one process so the app processes stay alive between commands, and the clock is injected so that expiry can be shown without waiting 5 hours.

English

All of that is the mechanism. Whether developers actually use it is a separate question, and it decides whether the platform lives or dies. A platform is bypassed when the workaround is cheaper, so compete on cost to the developer:

  • Be faster than the workaround. A clone and boot of ≈400 ms beats a ticket and beats a shared staging database.
  • Errors say what to do next. The quota message above lists what's running and how to free a slot, so the developer doesn't need to open a ticket.
  • Guardrails, not gates. Quotas and TTLs are visible and self-explanatory, with a named way to ask for more.
  • Leave an escape hatch. The golden path is optional. Forcing it means people route around you quietly, and you lose the signal that the path doesn't fit.
  • Treat developers as customers. Measure adoption: the share of new services created by the template, environments created per week, tickets to the platform team. A mandate hides those numbers.

Part 4 — Service catalog 🔴 Advancedالجزء 4 — الـ service catalog

English

A service catalog answers a question that gets expensive at 3 a.m.: what is this thing, who owns it, and who breaks if it's down? Backstage is the best-known tool, and its unit is a catalog-info.yaml file living in the repo. For a Component, the required fields are apiVersion, kind, metadata.name, spec.type, spec.lifecycle and spec.owner. Backstage's docs describe the owner as the entity with ultimate responsibility, the contact point when something goes wrong, and warn that it isn't meant to drive automated authorization.

The catalog's main enemy is staleness. A wiki page of services goes out of date because updating it is nobody's job, which is why the source of truth belongs in the repo, next to the code, and the catalog is generated. You also don't need Backstage to start: the scanner below reads repos/*/catalog-info.yaml, handles multi-document YAML, and writes catalog.json. It reports what a portal would hide: repos with no file, broken YAML, no owner, an owner that's no longer a team, dependencies on things that don't exist, and services on old golden-path templates. Then it exits non-zero when a repo has no reachable owner, which makes it a CI gate.

The sample run scans 7 repos. Three have no reachable owner. Two of the seven never reach the JSON (cart-api has broken YAML and legacy-reports has no file), so it holds 5 services. Backstage's own validator, installed from npm with no server, agrees about the missing owner.

Not run here: there is no Backstage server on this machine catalog-info.yaml was checked with Backstage's own @backstage/catalog-model package (1.10.2), which validates the entity without a portal. The scanner is a real script over sample repos created on disk. It doesn't do what Backstage adds on top: the UI, TechDocs, or plugins.

const rank = (v: string) => v.split(".").reduce((n, x) => n * 1000 + Number(x), 0);

type Service = {
  name: string; repo: string; type: string; lifecycle: string; owner: string | null;
  dependsOn: string[]; runbook: string | null; template: string | null;
};

  const path = join(ROOT, repo, "catalog-info.yaml");
  if (!existsSync(path)) { report(repo, "no-catalog-file", "nobody knows this repo exists"); continue; }

  // الملف ممكن يبقى فيه أكتر من entity مفصولين بـ ⁦---⁩
  const docs = parseAllDocuments(readFileSync(path, "utf8"));
  const broken = docs.find((d) => d.errors.length > 0);
  if (broken) { report(repo, "invalid-yaml", broken.errors[0]!.code); continue; }

  for (const doc of docs) {
    const e = doc.toJS() as { kind?: string; metadata?: { name?: string; annotations?: Record<string, string> }; spec?: Record<string, unknown> };
    if (e.kind !== "Component") continue;
    const owner = typeof e.spec?.owner === "string" ? e.spec.owner : null;
    const goldenPath = join(ROOT, repo, ".golden-path.json");
    const service: Service = {
      name: e.metadata?.name ?? repo, repo,
      type: String(e.spec?.type), lifecycle: String(e.spec?.lifecycle), owner,

      runbook: e.metadata?.annotations?.["acme.dev/runbook"] ?? null,
      template: existsSync(goldenPath) ? (JSON.parse(readFileSync(goldenPath, "utf8")) as { version: string }).version : null,
    };
    services.push(service);
    if (!owner) report(repo, "no-owner", "spec.owner is missing");
    else if (!TEAMS.has(owner)) report(repo, "unknown-owner", `${owner} is not a current team`);
    if (!service.runbook) report(repo, "no-runbook", "annotation acme.dev/runbook is missing");
    if (service.template && rank(service.template) < rank(LATEST_TEMPLATE)) report(repo, "old-template", `${service.template}, latest is ${LATEST_TEMPLATE}`);
  }
}

Part 5 — Developer experience metrics 🔴 Advancedالجزء 5 — مقاييس الـ developer experience

English

Three numbers are cheap to get and hard to argue with: time to first deploy for a new hire, CI time, and local setup time. Report a percentile rather than an average, because the tail is where the pain lives. In the sample logs below (generated for this lesson), time to first deploy has a p50 of 21 working hours and a p90 of 103. The median says onboarding is fine, and the p90 points at the two hires who were blocked for days. Local setup has the same shape, p50 17 and p90 59 minutes, with the failures concentrated in one step. That's a concrete fix, which an average would have buried.

For delivery, DORA is the standard reference, and it's worth checking rather than quoting from memory. People still say "the four keys", but on 2026-11-09 dora.dev lists five metrics in two groups. Throughput: change lead time, deployment frequency and failed deployment recovery time. Instability: change fail rate and deployment rework rate, the ratio of deployments that are unplanned and caused by a production incident.

The same page warns against making these goals, against comparing unlike teams, and against relying on a single metric. Goodhart's law is easy to demonstrate. In the second script the team does exactly the same work and adds 3 empty deploys after each real one. Deploys per week go from 5 to 19.9, median lead time from 20.6 hours to 0.3, and change fail rate from 12.5% to 3.1%. Real changes stay at 64 and failures stay at 8. Nothing improved except the dashboard.

// بيحسب مقاييس الـ developer experience والـ DORA الخمسة من logs
import { readFileSync } from "node:fs";

type Hire = { dev: string; workingHours: number };
type Setup = { minutes: number; ok: boolean; step: string | null };
type Ci = { kind: string; minutes: number; ok: boolean };
export type Deploy = { id: number; committedAt: string; deployedAt: string; failed: boolean; recoveredAt: string | null; rework: boolean; noop?: boolean };

const read = <T,>(f: string): T[] => readFileSync(f, "utf8").trim().split("\n").map((l) => JSON.parse(l) as T);

// الـ nearest-rank: رقم موجود فعلًا في البيانات، مش متوسط بين رقمين
export function percentile(xs: number[], p: number): number {
  const sorted = [...xs].sort((a, b) => a - b);
  const rank = Math.ceil((p / 100) * sorted.length);
  return sorted[Math.min(sorted.length - 1, Math.max(0, rank - 1))]!;
}
const p = (xs: number[]) => `p50 ${percentile(xs, 50)} / p90 ${percentile(xs, 90)}`;
const HOUR = 3_600_000;

export function dora(deploys: Deploy[], days: number) {
  const lead = deploys.map((d) => (Date.parse(d.deployedAt) - Date.parse(d.committedAt)) / HOUR);
  const failures = deploys.filter((d) => d.failed);
  const recovery = failures.map((d) => (Date.parse(d.recoveredAt!) - Date.parse(d.deployedAt)) / HOUR);

Part 6 — When not to build a platform 🔴 Advancedالجزء 6 — إمتى متبنيش platform

English

A platform is a product with a small captive market and a long maintenance tail. Don't build one because the industry is talking about it. Build it when the same measured pain shows up in several teams, and when someone will fund the running cost for years, not only the launch. A portal doesn't fix slow CI, and Backstage on top of a broken deploy process is a nicer way to look at the broken deploy process.

The script below compares three options in engineer-months over 36 months. Every input is an assumption stated in the code, and adoption ramps up over a year and stops at 70%, because no platform gets everyone on day one. Read the shape, not the digits. At 8 engineers nothing pays back, including scripts. At 20, only scripts and templates do. Around 50, buying or scripting pays and building in-house still loses 44 engineer-months over three years. An in-house platform pays back at 120 engineers, but only in month 26, later than buying. At 300 it finally wins. The $40 per engineer per month for a portal is a placeholder for the calculation, not a price from any vendor.

Those results support some rules of thumb, which are judgment and not data: under about 20 engineers, write a good README, a template repo and some shared scripts; from about 20 to 50, a scaffolder and reusable workflows, owned part-time; from about 50 to 150, a small dedicated team of 2 to 4 people, buying before building where you can; beyond about 150, a platform as a product with its own roadmap and users. Change the inputs and the thresholds move, so run it with your own numbers.

// متى المنصة ترجّع اللي اتصرف عليها؟ الحساب كله بالـ engineer-months
// كل الأرقام دي افتراضات مكتوبة، غيّرها بأرقام فريقك
type Option = {
  label: string;
  buildEngMonths: number;
  runEngPerMonth: number;
  // نسبة الوقت الموفّر مقارنة بمنصة كاملة (الـ scripts بتوفر أقل)
  savingsFactor: number;
  vendorPerEngPerMonth: number;
};

const HOURS_SAVED_PER_ENG_MONTH = 6;
const ENG_MONTH_HOURS = 160;
const LOADED_ENG_MONTH_USD = 12_000;
const MAX_ADOPTION = 0.7;
const RAMP_MONTHS = 12;
const HORIZON = 36;

const options: Option[] = [
  { label: "scripts+templates", buildEngMonths: 1, runEngPerMonth: 0.1, savingsFactor: 0.4, vendorPerEngPerMonth: 0 },
  { label: "buy a portal", buildEngMonths: 2, runEngPerMonth: 0.3, savingsFactor: 0.7, vendorPerEngPerMonth: 40 },
  { label: "build in-house", buildEngMonths: 12, runEngPerMonth: 2, savingsFactor: 1, vendorPerEngPerMonth: 0 },
];

function simulate(engineers: number, o: Option) {
  let spent = o.buildEngMonths;
  let saved = 0;
  let breakEven: number | null = null;
  for (let m = 1; m <= HORIZON; m++) {
    // الـ adoption بيطلع تدريجي: مفيش منصة الناس بتستخدمها من أول يوم
    const adoption = Math.min(MAX_ADOPTION, (MAX_ADOPTION * m) / RAMP_MONTHS);
    saved += (engineers * adoption * HOURS_SAVED_PER_ENG_MONTH * o.savingsFactor) / ENG_MONTH_HOURS;
    spent += o.runEngPerMonth + (engineers * o.vendorPerEngPerMonth) / LOADED_ENG_MONTH_USD;
    if (breakEven === null && saved >= spent) breakEven = m;
  }
  return { net: saved - spent, breakEven };
}

1. Who carries the toil? 🟢 easy Extend the report to show toil hours per engineer on the same ops-log.csv. If one person carries most of it, that's a bus-factor problem as well as a toil problem.
زوّد في الـ report ساعات الـ toil لكل مهندس على نفس ops-log.csv. لو واحد شايل معظمها، دي مشكلة bus factor كمان مش بس toil.
Solution · الحل 
// الحل: الـ toil بيتحسب لكل مهندس عشان تشوف مين شايل الحمل
import { readFileSync } from "node:fs";

const TOIL = /replay failed|onboard new|restart stuck|export customer|reset 2fa|clean disk/i;
const hours = new Map<string, number>();
for (const line of readFileSync(process.argv[2]!, "utf8").trim().split("\n").slice(1)) {
  const [, engineer, minutes, summary] = /^[^,]+,(\w+),(\d+),"(.*)"$/.exec(line)!;
  if (TOIL.test(summary!)) hours.set(engineer!, (hours.get(engineer!) ?? 0) + Number(minutes) / 60);
}
const total = [...hours.values()].reduce((a, b) => a + b, 0);
for (const [e, h] of [...hours].sort((a, b) => b[1] - a[1])) {
  console.log(e.padEnd(6), h.toFixed(1).padStart(6), "h", `${((h / total) * 100).toFixed(0)}%`);
}

omar     59.4 h 33%
sara     57.2 h 32%
الناتج ده من تشغيل حقيقي على الـ log التجريبي: الحمل متوزع تقريبًا بالتساوي بين الـ 3، 35% و33% و32%، فمفيش bus factor هنا. لو واحد طلع 70% يبقى عندك مشكلة تانية غير الـ toil.
2. Deprecated dependencies 🟡 medium Before you remove a service, you need to know who still depends on it. Using catalog.json, report every service that depends on a deprecated component.
قبل ما تشيل service لازم تعرف مين لسه معتمد عليها. استخدم catalog.json وطلّع كل service معتمدة على component حالته deprecated.
Solution · الحل 
// الحل: أي service معتمدة على حاجة deprecated لازم تظهر قبل ما الحاجة دي تتشال
import { readFileSync } from "node:fs";

type Service = { name: string; owner: string | null; lifecycle: string; dependsOn: string[] };

const services = JSON.parse(readFileSync(process.argv[2]!, "utf8")) as Service[];
// مثال بس: نعلّم invoice-api إنها deprecated
services.find((s) => s.name === "invoice-api")!.lifecycle = "deprecated";

const deprecated = new Set(services.filter((s) => s.lifecycle === "deprecated").map((s) => s.name));
for (const s of services) {
  for (const dep of s.dependsOn) {
    const target = dep.replace(/^component:/, "");
    if (deprecated.has(target)) console.log(`${s.name} (${s.owner}) depends on deprecated ${target}`);
  }
}

payment-gateway (team-billing) depends on deprecated invoice-api
لما علّمنا invoice-api إنها deprecated، الـ script طلّع الـ 2 services اللي معتمدين عليها وأصحابهم، وده بالظبط اللي تحتاجه قبل ما تقفلها.
3. Template drift 🔴 hard A repo can claim template 1.4.0 and still have a hand-edited CI file. Detect that: regenerate a clean copy from the template and compare the files that matter by hash. Test it by changing timeout-minutes in a copy of the generated service.
الـ repo ممكن يقول إنه على template 1.4.0 وملف الـ CI بتاعه متعدّل بالإيد. اكتشف ده: ولّد نسخة نضيفة من الـ template وقارن الملفات المهمة بالـ hash. وجرّبها بتغيير timeout-minutes في نسخة من الـ service اللي اتولدت.
Solution · الحل 
// الحل: بنولّد نسخة نضيفة من نفس الـ template ونقارن الملفات المهمة بالـ hash
import { createHash } from "node:crypto";
import { mkdtempSync, readFileSync, rmSync } from "node:fs";
import { join } from "node:path";
import { createService } from "../p2/create-service.ts";

const repo = process.argv[2]!;
const name = (JSON.parse(readFileSync(join(repo, "package.json"), "utf8")) as { name: string }).name;
const owner = /owner:\s*(\S+)/.exec(readFileSync(join(repo, "catalog-info.yaml"), "utf8"))![1]!;

const sha = (p: string) => createHash("sha256").update(readFileSync(p)).digest("hex").slice(0, 12);
const tmp = mkdtempSync(join(process.cwd(), "drift-"));
try {
  const clean = createService(name, owner, tmp);
  for (const f of [".github/workflows/ci.yml", "Dockerfile"]) {
    const [a, b] = [sha(join(clean, f)), sha(join(repo, f))];
    console.log(a === b ? "same   " : "DRIFTED", f, a === b ? "" : `template ${a} repo ${b}`);
  }
} finally {
  rmSync(tmp, { recursive: true, force: true, maxRetries: 5, retryDelay: 200 });
}

same    Dockerfile
الناتج ده من تشغيل حقيقي على نسخة اتغير فيها timeout-minutes من 10 لـ 60: الـ CI طلع DRIFTED والـ Dockerfile زي الـ template. وعلى النسخة الأصلية من غير تعديل الملفين طلعوا same.

Cheat sheet · الخلاصة

  • Toil is manual, repetitive, automatable, tactical, with no enduring value, and grows with the service. Meetings are overhead. A first-time debug isn't toil.
  • Rank toil by hours from a real log, keep an unclassified bucket, and watch the trend. Google SRE's goal: below 50%.
  • Automation guardrails: dry-run default, a blast-radius cap, idempotency key, stop on repeated failure, audit file.
  • Report the payback including maintenance. Automating the rare item can lose money.
  • A golden path is "opinionated and supported" and stays optional. It has to be the cheapest way to do the right thing.
  • Templates need tests and a recorded version, or they rot quietly.
  • Self-service needs quotas, expiry and owners. "Count then insert" races: use a transaction with an advisory lock. CREATE DATABASE can't run in a transaction, so reserve first and clean up on failure.
  • A platform is bypassed when the workaround is cheaper. Measure adoption rather than mandating.
  • The catalog lives in the repo and gets generated. Its job is ownership and "who breaks if this is down". Backstage is optional until people ask for a portal.
  • Use percentiles for time to first deploy, CI and setup. DORA now lists five metrics, including deployment rework rate.
  • Metrics as targets get gamed: empty deploys took deploys per week from 5 to 19.9 with no real change. Pair metrics and compare a team with itself.
  • Don't build a platform for hype. Compute the break-even in engineer-months, including running cost: scripts first, buy next, build last.
