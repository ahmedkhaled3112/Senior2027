Why this matters · ليه ده مهم

English

Everything breaks eventually, and at 3 a.m. the quality of your system is the quality of what the tired person holding the pager can do. This lesson makes that concrete: a rotation and an escalation path that are data, runbooks that run, a timeline built from logs, a real drill where a bad deploy and a Redis failure land together, and a postmortem whose action items get finished. A senior engineer owns production, and these are the tools for it.

Part 1 — On-call as a system 🔴 Advancedالجزء 1 — الـ on-call كـ system

English

On-call is a system, and it can be designed and measured. The sustainability numbers from the Google SRE book (at most 25% of time on-call, at most two incidents per 12-hour shift) and the monthly pager review are in section 10, part 7. This part turns the remaining pieces into data.

Rotation as data. A file holds the schedule, the handoff time, and overrides for leave or swaps, so "who has the pager at 03:30?" has one answer. Keep a primary and a secondary, and rotate at a fixed time in working hours so a handoff conversation can actually happen. Escalation as data means every step has a time: primary now, secondary after 5 minutes without an ack, manager after 15. A person who can't answer shouldn't be the end of the road.

Every alert needs a runbook. The README's rule is blunt: an alert without a runbook is noise, because whoever gets woken up has nothing to do. So a linter runs in CI and rejects a page or ticket alert that has no runbook, whose runbook file doesn't exist, whose runbook lacks the required sections, or that doesn't point at a runnable check. info alerts wake nobody and are skipped. In the run below it rejects two of six alerts.

On-call health is measured in pages per week, the share of pages at night, and the share that needed a human. The numbers below are sample data and the limits are ones your team picks. karim shows why you measure per person rather than per team: 19 pages in a week, 47% at night, only 32% actionable, while the other three had 3 to 5 pages. The team average of 7.75 hides who is carrying it.

import { readFileSync } from "node:fs";
import { parse } from "yaml";

type Override = { from: string; to: string; member: string; reason: string };
type Config = {
  schedule: { name: string; firstHandoff: string; shiftDays: number; members: string[] };
  overrides: Override[];
  escalation: { level: string; afterMinutes: number }[];
};
const cfg = parse(readFileSync("oncall.yaml", "utf8")) as Config;
const DAY = 86_400_000;

function primaryAt(at: Date): string {
  // الـ override بيغلب الجدول: إجازة أو تبديل بين اتنين
  const o = cfg.overrides.find((x) => at >= new Date(x.from) && at < new Date(x.to));
  if (o) return o.member;
  const shifts = Math.floor((at.getTime() - new Date(cfg.schedule.firstHandoff).getTime()) / (cfg.schedule.shiftDays * DAY));
  return cfg.schedule.members[shifts % cfg.schedule.members.length]!;
}

const secondaryAt = (at: Date) => {
  const shifts = Math.floor((at.getTime() - new Date(cfg.schedule.firstHandoff).getTime()) / (cfg.schedule.shiftDays * DAY));
  return cfg.schedule.members[(shifts + 1) % cfg.schedule.members.length]!;
};

# كل alert لازم تقول مين بيرد عليها وإزاي: runbook ليها check متنفذ
alerts:
  - { alert: DbPoolExhausted, severity: page, runbook: runbooks/db-pool-exhausted.md }
  - { alert: QueueBacklog, severity: page, runbook: runbooks/queue-backlog.md }
  - { alert: ErrorSpike, severity: page, runbook: runbooks/error-spike.md }
  - { alert: HighCPU, severity: page }
  - { alert: DiskFilling, severity: page, runbook: runbooks/disk-filling.md }
  - { alert: CacheSlow, severity: info }
import { existsSync, readFileSync } from "node:fs";
import { parse } from "yaml";

type Alert = { alert: string; severity: string; runbook?: string };
const { alerts } = parse(readFileSync("alerts.yaml", "utf8")) as { alerts: Alert[] };

const SECTIONS = ["## Symptoms", "## Check", "## Mitigate", "## Escalate"];
const problems: string[] = [];

for (const a of alerts) {
  // الـ info مش بتصحّي حد، فمش لازم runbook، بس كل حاجة بتعمل page لازم
  if (a.severity !== "page" && a.severity !== "ticket") continue;
  if (!a.runbook) { problems.push(`${a.alert}: no runbook`); continue; }
  if (!existsSync(a.runbook)) { problems.push(`${a.alert}: ${a.runbook} does not exist`); continue; }
  const text = readFileSync(a.runbook, "utf8");
  for (const s of SECTIONS) if (!text.includes(s)) problems.push(`${a.alert}: runbook is missing "${s}"`);
  const check = /node (checks\/[\w-]+\.ts)/.exec(text);
  if (!check || !existsSync(check[1]!)) problems.push(`${a.alert}: runbook has no runnable check script`);
}

console.log(`${alerts.length} alerts checked, ${problems.length} problems`);
for (const p of problems) console.log(`  REJECT ${p}`);
process.exit(problems.length ? 1 : 0);

بالعامية

الـ on-call system بتقدر تصممه وتقيسه. أرقام الاستدامة من كتاب Google SRE (مش أكتر من 25% من الوقت on-call، ومش أكتر من incidentين في الـ shift اللي 12 ساعة) ومراجعة الـ pager الشهرية موجودين في قسم 10، الجزء 7. الجزء ده بيحوّل الباقي لـ data.

الـ rotation كـ data. ملف فيه الجدول ووقت الـ handoff والـ overrides للإجازات والتبديلات، فالسؤال "مين ماسك الـ pager الساعة 3:30؟" ليه إجابة واحدة. خلّي primary وsecondary، وبدّل في وقت ثابت في ساعات الشغل عشان الـ handoff يبقى كلام فعلًا. الـ escalation كـ data معناها إن كل خطوة ليها وقت: الـ primary دلوقتي، والـ secondary بعد 5 دقايق من غير ack، والمدير بعد 15. الشخص اللي مش عارف يرد ماينفعش يبقى آخر السكة.

كل alert محتاجة runbook. قاعدة الـ README واضحة: الـ alert من غير runbook = noise، لأن اللي صحي مش عارف يعمل إيه. فيه linter بيشتغل في الـ CI بيرفض أي alert من نوع page أو ticket مفيهاش runbook، أو ملف الـ runbook مش موجود، أو ناقصها sections مطلوبة، أو مش بتشاور على check ينفع يتشغل. الـ info مش بتصحّي حد فبتعدي. والـ run بيرفض اتنين من 6.

صحة الـ on-call بتتقاس بـ pages في الأسبوع، ونسبة اللي بالليل، ونسبة اللي محتاجة إنسان فعلًا. الأرقام sample والحدود إنتوا اللي بتحددوها. karim بيوريك ليه بتقيس لكل شخص مش للفريق: 19 page في أسبوع، 47% بالليل، و32% بس actionable، والتلاتة التانيين من 3 لـ 5 pages، فالمتوسط (7.75) مخبّي مين شايل الحمل.

فين هستخدمه في شغلي؟ لما فريقك يكبر ويبقى الـ on-call "اللي فاضي يرد": حط oncall.yaml في الـ repo وخلّي الـ tool بتاعة الـ paging تتبنى منه أو تتراجع قصاده. وفي الـ PR اللي بيضيف alert جديدة، الـ linter يقع لو مفيش runbook، فمفيش alert توصل production من غير ما حد يعرف يتعامل معاها. الغلطة الشائعة: تقيس الـ pages على مستوى الفريق، فشخص واحد بيتحرق والمتوسط مش بيبيّن مين شايل الحمل.

Part 2 — Runbooks that execute 🔴 Advancedالجزء 2 — runbooks بتتنفذ

English

A runbook that's prose in a wiki rots and gets skipped. A useful one has four sections, Symptoms, Check, Mitigate and Escalate, and its Check is a script. Three exit codes matter: 0 healthy, 2 act now, 3 the check itself couldn't run. Code 3 exists so that a check that crashed never looks like a healthy system. Any step that changes production needs an explicit --apply, so running the check is always safe.

These are the three runbooks README artifact 13 asks for, each run against a real local stack: a real Express API, real Postgres 18 (max_connections 20) and real Redis 8. Each scenario goes healthy, then fault, then mitigate, then healthy again. Runbook 1 uses pg_blocking_pids to find the session pinning the pool: an idle in transaction session holding one row lock stalled every API connection.

The first version of this check had a real bug, which is worth seeing. pg_blocking_pids returns queued waiters too, so five "blockers" came back, four of them innocent API sessions waiting in line. --apply terminated all five and then the whole API crashed, because the pg client it had checked out emitted an 'error' event with no listener. The API did have a pool.on('error') handler, and the docs describe that event for idle clients: this run shows it doesn't protect a checked-out one. The fix is to terminate root blockers only and to add a listener on every checked-out client. A runbook that can make things worse is a bug too, so test it before you need it.

# Runbook: DbPoolExhausted

## Symptoms
`POST /orders` returns 503 with `pool_timeout`, latency climbs, `pool.waiting` above 0.

## Check
Run `node checks/db-pool.ts`. Exit 0 means healthy, exit 2 means act, exit 3 means the check itself failed.
It lists root blockers: sessions that hold a lock and aren't waiting on anyone.

## Mitigate
1. If one session is the root blocker, run `node checks/db-pool.ts --apply` to terminate it.
2. If it's a leaked pool or a traffic spike, roll back or scale the API. Do not raise `max_connections` first.

## Escalate
After 15 minutes without recovery, page the DB owner and declare SEV2.
كل runbook فيها 4 أجزاء: Symptoms (شكل المشكلة)، وCheck (أمر بيتشغل، وexit 0 سليم، و2 اتحرك، و3 الفحص نفسه فشل)، وMitigate (لو session واحدة هي الـ root blocker اعمل --apply، ولو leak أو ضغط اعمل rollback أو scale، ومتزودش max_connections كأول حل)، وEscalate (بعد 15 دقيقة من غير تعافي نادي صاحب الـ DB وأعلن SEV2).
# Runbook: QueueBacklog

## Symptoms
Notifications arrive late. Queue depth above 100 or oldest job older than 30 s.

## Check
Run `node checks/queue.ts`. It prints depth, oldest age and the worker heartbeat.

## Mitigate
1. No heartbeat: restart the worker and watch the depth fall.
2. Heartbeat present but depth rising: add consumers and pause low-priority producers.

## Escalate
If the oldest job passes 15 minutes, page the service owner and post a status update.
runbook الـ queue: العرض إن الـ notifications بتتأخر والـ depth فوق 100 أو أقدم job عدّى 30 ثانية. الفحص بيطبع الـ depth وأقدم عمر والـ heartbeat. لو مفيش heartbeat اعمل restart للـ worker، ولو فيه heartbeat والـ depth بيزيد ضيف consumers ووقّف الـ producers قليلة الأهمية. ولو أقدم job عدّى 15 دقيقة نادي صاحب الـ service وابعت status update.
# Runbook: ErrorSpike

## Symptoms
Availability burn alert fired, 5xx ratio above 2%.

## Check
Run `node checks/errors.ts`. It groups recent errors by version, route and cause.

## Mitigate
1. Errors from one new version: roll back first, diagnose after.
2. Errors across versions: a dependency is the likely cause. Flip its fallback flag.

## Escalate
Declare an incident (SEV2 or higher) and assign an incident commander if not recovered in 10 minutes.
runbook الـ error spike: العرض إن alert الـ burn ضرب والـ 5xx فوق 2%. الفحص بيجمّع الأخطاء بالـ version والـ route والسبب. لو الأخطاء من version جديد واحد اعمل rollback الأول وشخّص بعدين، ولو عابرة أكتر من version يبقى غالبًا dependency فاقلب الـ fallback flag. ولو ماتعافتش في 10 دقايق أعلن incident وعيّن incident commander.

export function safePort(raw: string | undefined): number {
  const n = Number(raw);
  if (!/^\d+$/.test(String(raw)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port ${raw}`);
  }
  return n;
}

}

    await client.query("ROLLBACK").catch(() => {});
    res.locals.err = (err as Error).message;
    res.status(500).json({ error: "internal" });

    client.off("error", onError);
    // لو الـ connection اتقطع، ⁦release(true)⁩ بترميه بدل ما يرجع للـ pool
    client.release(broken);
  }
});

English

This part is the mechanics. How people behave under pressure, and how an incident commander leads a room, is section 13 · 2.7. The mechanics are roles, a severity scale agreed in advance, a status-update format, and a timeline that comes from logs rather than memory.

The most important rule is that the incident commander doesn't touch the keyboard. Someone has to keep the whole picture, set priorities and decide, and that person can't be inside a psql session. In a small team one person can hold two roles, but IC and Ops should still be different people whenever possible. Severity decides who gets pulled in and how often you communicate, so it's set from user impact, never from how scared the on-call feels, and it can change during the incident.

A status update says the impact, what you're doing, and when the next update will be. Never state a cause you haven't confirmed. The next-update time is a promise, and silence is what makes customers angry. The timeline below is built by a script that merges the event log and the API's access log and collapses thousands of identical errors into one line per cause. A human writing from memory, two days later, gets the order wrong. A script doesn't, and it costs nothing during the incident.

Part 4 — Mitigation first 🔴 Advancedالجزء 4 — الـ mitigation الأول

English

The instinct of a good engineer is to understand the problem. During an incident that instinct costs money, because users are failing while you read stack traces. So the order is mitigate first, root cause later. Rollback, flip a flag, drain a region, restart a stuck worker: these are cheap, usually reversible, and don't need you to know why. A rollback that turns out to be unnecessary costs a few minutes. A correct diagnosis that takes 30 minutes costs 30 minutes of errors. Game-day structure is in section 10, deployment safety, part 6.

Two numbers track this: time to detect (TTD), from the first fault to the alert, and time to mitigate (TTM), from the first fault to users being fine again. Note that it's "mitigate", not "fix": the bug can still be in the code.

The drill runs on real processes: a bad version 2.0.0 that throws on guest orders, and then real Redis is shut down about 300 ms later. In mitigate-first mode the on-call rolls back within about half a second of the alert, without knowing why. Errors remain, the rollback didn't fix everything, and that's useful information: the runbook check now sees that the errors aren't from the last deploy, points at a dependency, and the cache-bypass flag restores carts from Postgres. Diagnose-first mode runs the same fixes after 8 seconds of investigation.

Results (≈, Windows on a loaded machine): mitigate-first reached TTM ≈4.1 s with 91 failed requests. Diagnose-first reached TTM ≈9.9 s with 348 failed requests, 3.8× more failures. TTD was the same ≈0.4 s in both, because detection doesn't depend on the response. Everything here is compressed: the alert windows are seconds rather than minutes, and the 0.5 s ack and 8 s investigation are labelled stand-ins for what's minutes in real life. Use the ratio. The load balancer is one variable in the script, so a rollback here is instant, unlike a real one that takes minutes.

The reasoning behind blameless postmortems and the "contributing factors, not one root cause" rule are in section 10, part 6. Here we fill one in from the drill. Four contributing factors came out of a two-fault drill: no guest-order test, no canary, a hard dependency on Redis, and a fallback that needed a human. Notice that none of them is a person. Blameless wording isn't politeness. If someone gets blamed, the next person hides what they did, and you lose your only data. Blameless doesn't mean nobody is accountable: it means asking why the system made the error easy. The same event, written in two ways:

  • Weak: "Karim deployed without testing guest checkout."
  • Strong: "The deploy passed every existing check because the suite had no guest-order case, and the pipeline moved 100% of traffic in one step with no canary."

Part 6 — Closing the loop 🔴 Advancedالجزء 6 — قفل الدايرة

English

A postmortem that never finishes its action items was an expensive writing exercise. Three things close the loop. Track actions in the same system as feature work, so they compete on a real backlog instead of living in a doc. Measure the repeat rate: the share of incidents with the same cause as one in the previous 90 days. Hold a monthly review that looks at open and overdue actions, repeats by cause, and the on-call health numbers from Part 1.

The script below uses invented sample data to show what the review surfaces. 50% of action items are overdue, and 4 of 8 incidents are repeats. The most useful line is the join between the two: in 3 of the 4 repeats, the earlier incident's action item was still open when the same failure came back. That turns "we keep having Redis problems" into a concrete sentence for the planning meeting: we had the fix identified and hadn't shipped it.

The README also lists a review step for the postmortem: someone outside the incident reviews it before it's closed, usually in a short weekly meeting, and a sample is shared wider so other teams learn. Keep the review about the system. Section 13 covers running that meeting.

Common mistakes · غلطات شائعة

❌ A check that crashes looks healthy 
// الفحص وقع؟ الـ process بيطلع بـ exit 0 والـ on-call فاكر كله تمام
try {
  await inspect();
} catch {
  console.log("could not inspect");
}
✅ A separate exit code for "couldn't check" 
// الخروج بـ 3 يفرق بين "سليم" و"ماقدرتش أعرف"
try {
  await inspect();
} catch (err) {
  console.log(`CHECK FAILED: ${(err as Error).message}`);
  process.exit(3);
}
بالعامية

❌ لو الفحص وقع ورجع exit 0، الـ on-call هيفتكر الـ system سليم وهو أصلًا مش قادر يشوف حاجة. ✅ خلي exit 3 معناه "الفحص نفسه فشل"، فيتعامل معاه كمشكلة لوحده.

❌ Terminating every session in the queue 
// الضحايا الواقفين في الطابور اتحسبوا blockers واتقتلوا معاه
const blockers = rows.filter((r) => blockerPids.includes(r.pid));
✅ Root blockers only 
// الـ root blocker بس: ماسك الـ lock ومش مستني حد
const blockers = rows.filter(
  (r) => blockerPids.includes(r.pid) && r.blocked_by.length === 0,
);
بالعامية

❌ pg_blocking_pids بترجّع الواقفين في الطابور كمان، فقتل الكل بيقتل sessions سليمة وعمل outage أكبر، زي ما حصل في أول run هنا. ✅ قصّرها على الـ root blockers: اللي ماسكين lock ومش مستنيين حد.

❌ No listener on a checked-out client 
// الـ pool.on بيغطي الـ idle بس، فالـ client ده ممكن يوقع الـ process
const client = await pool.connect();
await client.query("UPDATE inventory ...");
client.release();
✅ A listener, and destroy broken connections 
// لو الـ connection اتقطعت، الـ client بيترمي ومايرجعش للـ pool
const client = await pool.connect();
let broken = false;
const onError = () => { broken = true; };
client.on("error", onError);
try {
  await client.query("UPDATE inventory ...");
} finally {
  client.off("error", onError);
  client.release(broken);
}
بالعامية

❌ لما الـ backend يقفل الـ connection، الـ client بيطلّع 'error'، ومن غير listener الـ process كله بيقع. ✅ حط listener وقت الـ checkout وشيله في finally، وrelease(true) بترمي الـ connection البايظ بدل ما يرجع للـ pool.

❌ An action nobody can verify 
| AI-1 | Be more careful with deploys | | soon | prevent |
✅ Owner, date, verifiable 
| AI-2 | Deploy through a 5% canary that blocks on the error ratio | platform | 2026-12-05 | mitigate |

❌ "Be more careful" مفيهاش owner ولا تاريخ ومفيش حد يقدر يتأكد إنها خلصت، فمش هتتعمل. ✅ action فيها حاجة تتفحص (canary بـ 5% بيقف على الـ error ratio)، وowner اسمه platform، وتاريخ، وتصنيف.

Cheat sheet · الخلاصة

  • Rotation and escalation live in a reviewed file. Primary, secondary, overrides, timed escalation.
  • Every paging alert has a runbook, enforced by a CI linter.
  • Runbook sections: Symptoms, Check, Mitigate, Escalate. Exit 0 healthy, 2 act, 3 check failed.
  • Changing production needs an explicit --apply. Test the runbook, it can make things worse.
  • On-call health per person: pages/week, night share, actionable share.
  • IC decides and doesn't touch the keyboard. Severity comes from user impact.
  • Status update: impact, action, next update time. No unconfirmed causes.
  • Build the timeline from logs, not memory.
  • Mitigate first (rollback, flag, restart), then diagnose. TTM counts until users are fine.
  • Contributing factors, owners, dates, verifiable actions, and a checker on the PR.
  • Blameless wording asks why the system made the error easy.
  • Track actions with feature work, measure repeat rate, review monthly.
بالعامية
  • الـ rotation والـ escalation في ملف بيتراجع: primary وsecondary وoverrides وescalation بأوقات.
  • كل alert بتعمل page ليها runbook، والـ linter في الـ CI بيفرض ده.
  • أجزاء الـ runbook: Symptoms وCheck وMitigate وEscalate. والـ exit: 0 سليم، و2 اتحرك، و3 الفحص فشل.
  • أي تغيير في الـ production محتاج --apply صريح. وجرّب الـ runbook، لأنه ممكن يبوّظ الدنيا.
  • صحة الـ on-call لكل شخص: pages في الأسبوع، ونسبة الليل، ونسبة الـ actionable.
  • الـ IC بيقرر ومش بيلمس الكيبورد. والـ severity من أثر المستخدم.
