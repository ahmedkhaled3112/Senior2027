Why this matters · ليه ده مهم

English

The most expensive tests are the ones that are green while production is on fire. They mostly come from two things: doubles placed in the wrong spot, so the real SQL or the real HTTP call never ran, and tests whose result depends on the clock, on randomness or on a promise nobody awaited. This lesson is about putting doubles at the boundary and making every test give the same answer on any machine, at any hour.

بالعامية

أغلى tests هي اللي خضرا والـ production بيولّع. وده غالبًا جاي من حاجتين: doubles متحطوطة في المكان الغلط، فالـ SQL الحقيقي أو الـ HTTP call الحقيقي عمره ما اشتغل، أو tests نتيجتها متوقفة على الساعة أو الـ random أو promise محدش مستنيها. الدرس ده عن إنك تحط الـ doubles عند الحدود بتاعة النظام، وإن كل test يدي نفس الإجابة على أي جهاز وفي أي وقت.

Part 1 — The five doubles 🟢 Basicالجزء 1 — الخمس أنواع بتوع الـ test doubles

English

A test double is anything that stands in for a real collaborator. Gerard Meszaros named five kinds, and they differ in what the test can verify through them:

  • Dummy: passed only to satisfy a signature; it should never be used. Ours throws if it is.
  • Stub: returns a canned answer. The test checks your code's result, nothing about the call.
  • Spy: records calls and usually delegates to a real or stub implementation. The test inspects the record afterwards.
  • Mock: pre-programmed with expectations, and the double itself decides whether the interaction was right.
  • Fake: a real, working but simplified implementation, like an in-memory repository with the same unique-email rule as the database.

Below is one checkout use case with a PaymentGateway port, tested with each. The dummy fits only a path where the gateway isn't touched (a zero amount), so that path is the one it gets. Everyone says "mock" for all five, including Vitest's vi.fn(), which is really a stub and a spy in one. In a review the difference is worth stating: a stub and a mock make very different promises.

export type Charge = { id: string; amountCents: number };

export interface PaymentGateway {
  charge(customerId: string, amountCents: number): Promise<Charge>;
}

export type Customer = { id: string; email: string };

export interface CustomerRepository {
  insert(email: string): Promise<Customer>;
  findByEmail(email: string): Promise<Customer | undefined>;
}

export type CheckoutResult =
  | { status: "paid"; chargeId: string; customerId: string }
  | { status: "rejected"; reason: "invalid_amount" };

export type CheckoutDeps = { gateway: PaymentGateway; customers: CustomerRepository };

export async function checkout(
  deps: CheckoutDeps,
  input: { email: string; amountCents: number },
): Promise<CheckoutResult> {
  if (input.amountCents <= 0) return { status: "rejected", reason: "invalid_amount" };
  const existing = await deps.customers.findByEmail(input.email);
  const customer = existing ?? (await deps.customers.insert(input.email));
  const charge = await deps.gateway.charge(customer.id, input.amountCents);
  return { status: "paid", chargeId: charge.id, customerId: customer.id };
}
import type { Charge, Customer, CustomerRepository, PaymentGateway } from "./checkout.ts";

// الـ Dummy: موجود عشان الـ signature تكمّل بس. لو حد استخدمه، ده bug
export const dummyGateway: PaymentGateway = {
  charge: () => {
    throw new Error("dummy gateway must never be called");
  },
};

// الـ Stub: بيرجّع إجابة ثابتة ومش بيسأل عن حاجة
export const stubGateway: PaymentGateway = {
  charge: async (_customerId, amountCents) => ({ id: "ch_stub", amountCents }),
};

// الـ Spy: بيلف حوالين gateway تاني وبيسجّل الـ calls، والتحقق بييجي بعدين في الـ test
export class SpyGateway implements PaymentGateway {
  readonly calls: Array<{ customerId: string; amountCents: number }> = [];
  constructor(private readonly inner: PaymentGateway) {}
  charge(customerId: string, amountCents: number): Promise<Charge> {
    this.calls.push({ customerId, amountCents });
    return this.inner.charge(customerId, amountCents);
  }
}

// الـ Mock: التوقعات متسجلة فيه مقدمًا، وهو نفسه اللي بيحكم في verify
export class MockGateway implements PaymentGateway {
  private expected?: { customerId: string; amountCents: number };
  private calledCorrectly = false;
  expectCharge(customerId: string, amountCents: number): void {
    this.expected = { customerId, amountCents };
  }
  async charge(customerId: string, amountCents: number): Promise<Charge> {
    if (customerId !== this.expected?.customerId || amountCents !== this.expected?.amountCents) {
      throw new Error(`unexpected charge(${customerId}, ${amountCents})`);
    }
    this.calledCorrectly = true;
    return { id: "ch_mock", amountCents };
  }
  verify(): void {
    if (!this.calledCorrectly) throw new Error("expected charge was never made");
  }
}

// الـ Fake: implementation حقيقية بس بسيطة، وفيها نفس قاعدة الـ unique email
export class DuplicateEmailError extends Error {}

export class InMemoryCustomers implements CustomerRepository {
  private readonly byEmail = new Map<string, Customer>();
  private nextId = 1;
  async insert(email: string): Promise<Customer> {
    if (this.byEmail.has(email)) throw new DuplicateEmailError(email);
    const customer = { id: `cus_${this.nextId++}`, email };
    this.byEmail.set(email, customer);
    return customer;
  }
  async findByEmail(email: string): Promise<Customer | undefined> {
    return this.byEmail.get(email);
  }
}
import { describe, expect, it } from "vitest";
import { checkout } from "../p1/src/checkout.ts";
import {
  DuplicateEmailError, InMemoryCustomers, MockGateway, SpyGateway, dummyGateway, stubGateway,
} from "../p1/src/doubles.ts";

const input = { email: "mona@example.com", amountCents: 5_000 };

describe("checkout, with each kind of double", () => {
  it("Dummy: rejects a zero amount and never needs the gateway", async () => {
    const result = await checkout(
      { gateway: dummyGateway, customers: new InMemoryCustomers() },
      { ...input, amountCents: 0 },
    );

    expect(result).toEqual({ status: "rejected", reason: "invalid_amount" });
  });

  it("Stub: returns paid with the charge id the gateway gave", async () => {
    const result = await checkout({ gateway: stubGateway, customers: new InMemoryCustomers() }, input);

    expect(result).toEqual({ status: "paid", chargeId: "ch_stub", customerId: "cus_1" });
  });

  it("Spy: charges the right customer the right amount, once", async () => {
    const gateway = new SpyGateway(stubGateway);

    await checkout({ gateway, customers: new InMemoryCustomers() }, input);

    expect(gateway.calls).toEqual([{ customerId: "cus_1", amountCents: 5_000 }]);
  });

  it("Mock: the double itself decides whether the interaction was right", async () => {
    const gateway = new MockGateway();
    gateway.expectCharge("cus_1", 5_000);

    await checkout({ gateway, customers: new InMemoryCustomers() }, input);

    gateway.verify();
  });

  it("Fake: a second checkout with the same email reuses the customer", async () => {
    const customers = new InMemoryCustomers();
    const deps = { gateway: stubGateway, customers };

    const first = await checkout(deps, input);
    const second = await checkout(deps, input);

    expect(first).toMatchObject({ customerId: "cus_1" });
    expect(second).toMatchObject({ customerId: "cus_1" });
    await expect(customers.insert(input.email)).rejects.toBeInstanceOf(DuplicateEmailError);
  });
});

بالعامية

الـ test double هو أي حاجة بتحل محل collaborator حقيقي. Gerard Meszaros سمّى 5 أنواع، والفرق بينهم هو الـ test يقدر يتحقق من إيه من خلالهم:

  • Dummy: بيتبعت عشان الـ signature تكمل بس، ومفروض ميتستخدمش. بتاعنا بيرمي error لو حد لمسه.
  • Stub: بيرجع إجابة ثابتة. الـ test بيتأكد من نتيجة الكود بتاعك، مش من الـ call.
  • Spy: بيسجل الـ calls وغالبًا بيكمّل على implementation حقيقية أو stub. الـ test بيبص على السجل بعدين.
  • Mock: متبرمج مقدمًا بالتوقعات، وهو نفسه اللي بيحكم التفاعل صح ولا غلط.
  • Fake: implementation حقيقية شغالة بس مبسطة، زي repository في الـ memory فيه نفس قاعدة الـ unique email بتاعة الـ DB.

فوق عندك use case واحد checkout بـ port اسمه PaymentGateway، ومتختبر بكل نوع. الـ dummy بينفع بس في path الـ gateway مبيتلمسش فيه (مبلغ صفر)، فده اللي اخد. الكل بيقول "mock" على الخمسة، حتى vi.fn() بتاع Vitest هو في الحقيقة stub و spy مع بعض. في الـ review فرّق بينهم: الـ stub والـ mock بيوعدوك بحاجات مختلفة خالص.

فين هستخدمه في شغلي؟ لما تكتب unit test لـ checkout: الـ PaymentGateway stub عشان تجرب "الدفع نجح"، وspy لو عايز تتأكد إن الـ charge اتبعت مرة واحدة بالمبلغ الصح، وFake للـ customers عشان الـ unique email تفضل قاعدة حقيقية. وفي الـ PR لو حد كتب "mocked the gateway" اسأله: mock فعلًا ولا stub؟ الاختلاف ده هو اللي بيحدد الـ test هيتكسر لو غيّرت طريقة الـ call.
Interview question "What's the difference between a stub, a mock and a fake?" → A stub returns canned data and the test checks my code's output. A mock carries expectations about the interaction and fails if the call isn't right, so it verifies behaviour through calls and couples the test to them. A fake is a working simplified implementation, such as an in-memory repository, so tests stay fast and exercise real rules, but it needs its own contract test against the real thing or it drifts.
"إيه الفرق بين الـ stub والـ mock والـ fake؟" ← الـ stub بيرجع data ثابتة والـ test بيتأكد من نتيجة كودي. الـ mock معاه توقعات عن التفاعل وبيفشل لو الـ call مش صح، فبيتحقق من السلوك عن طريق الـ calls وبيربط الـ test بيها. الـ fake implementation مبسطة شغالة زي in-memory repository، فالـ tests بتفضل سريعة وبتجرب قواعد حقيقية، بس لازم contract test قصاد الحاجة الحقيقية وإلا هيبعد عنها مع الوقت.

Part 2 — vi.fn, vi.spyOn, vi.mock 🟢 Basicالجزء 2 — الـ vi.fn والـ vi.spyOn والـ vi.mock

English

Three tools, three different jobs, all shown on notifyCustomer. vi.fn() makes a new function that you inject. vi.spyOn(obj, "method") watches a real method on an existing object, and the real code still runs unless you add a mockImplementation. vi.mock("./module") replaces a whole module for everyone who imports it, and it's hoisted above the imports (the mechanics are in 04 Node, lesson 29, part 2).

Two things to get right. First, cleanup. In Vitest 5 clearMocks defaults to true (ran: a plain vi.fn() shows 0 calls in the next test), but restoreMocks defaults to false, so a vi.spyOn stays installed. That's the source of the classic bug below: a spy set up in one test keeps replacing the real method for the next test, and the next test fails with an error from a test that already passed. Jest 30 keeps clearMocks: false (ran: calls carried over), so copying Jest habits into Vitest or back changes behaviour. Use afterEach(() => vi.restoreAllMocks()), or better, set restoreMocks: true once in the config. In Vitest 5 vi.restoreAllMocks restores spies; plain vi.fn() implementations stay configured, as the output shows.

Second, typing. vi.mock doesn't change the static type of the import, so notifyCustomer.mock is a compile error. vi.mocked(notifyCustomer) casts it to the mocked type. The checks below ran on TypeScript 7.

  vi.spyOn(a, m)  wraps a.m on the real object            real code still runs
                                                          unless you replace it
  vi.mock(path)   swaps the whole module, for everyone    real module not loaded
                  who imports it, hoisted above imports
vi.fn function جديدة إنت اللي بتمررها، ومفيش كود حقيقي. vi.spyOn بيلف حوالين method موجودة على object حقيقي، والكود الحقيقي بيشتغل إلا لو استبدلته. vi.mock بيبدّل الـ module كله لكل حد بيعمله import، وبيترفع فوق الـ imports، فالـ module الحقيقي مبيتحملش.

بالعامية

تلات أدوات لتلات شغلات مختلفة، وكله متجرب على notifyCustomer. vi.fn() بتعمل function جديدة إنت بتمررها. vi.spyOn(obj, "method") بتـراقب method حقيقية على object موجود، والكود الحقيقي لسه بيشتغل إلا لو حطيت mockImplementation. وvi.mock("./module") بتـبدّل module كامل لكل حد بيعمله import، وبتترفع فوق الـ imports (التفاصيل في الدرس 29 في قسم Node، الجزء 2).

حاجتين لازم يتعملوا صح. الأولى التنضيف. في Vitest 5 الـ clearMocks افتراضيًا true (اتشغل: الـ vi.fn() العادية بتبدأ بـ 0 calls في الـ test اللي بعده)، بس restoreMocks افتراضيًا false، يعني الـ vi.spyOn بيفضل متركب. ومن هنا الـ bug المشهور اللي تحت: spy اتعمل في test وفضل مبدّل الـ method الحقيقية للـ test اللي بعده، فالـ test اللي بعده يفشل بـ error من test عدّى فعلًا. أما Jest 30 الـ clearMocks فيه false (اتشغل: الـ calls كملت)، فنقل عادات Jest لـ Vitest أو العكس بيغيّر السلوك. استخدم afterEach(() => vi.restoreAllMocks())، أو أحسن: حط restoreMocks: true مرة واحدة في الـ config. في Vitest 5 vi.restoreAllMocks بترجّع الـ spies، والـ vi.fn() العادية بتفضل زي ما هي زي ما الـ output وريتك.

التانية الـ typing. vi.mock مش بيغير الـ static type بتاع الـ import، فـ notifyCustomer.mock compile error. وvi.mocked(notifyCustomer) بتعمله cast للنوع الـ mocked. والكود ده اتعمله check على TypeScript 7.

فين هستخدمه في شغلي؟ vi.fn() لما الكود بياخد الـ dependency من الـ constructor (زي notify في الـ OrderService). vi.spyOn على mailer.send لما تحب تتفرج على object موجود من غير ما تكسره. vi.mock لما مش قادر تحقن الـ dependency، زي module بيتعمله import مباشرة. والغلطة الشائعة: حد يكتب vi.spyOn من غير restore في test فيها error، وتبات تـ debug في test تاني خالص. حط restoreMocks: true في vitest.config.ts بتاع المشروع من أول يوم.

Part 3 — Mock the boundary, not your code 🟢 Basicالجزء 3 — اعمل mock للحدود، مش للكود بتاعك

English

Over-mocking is a test that replaces so much that nothing real runs. The OrderService test below mocks the repository, the tax calculator and even its own helper totals.addVat. It passes. Then a migration renames total_cents to amount_cents, and in production every order fails with Postgres error 42703, while this test stays green: it never ran any SQL.

The rule: mock what you don't own and can't run (a payment API, an email provider, the clock). The database is yours, so run it for real. Your own helpers and calculators stay real too, because they're your logic under test. A fake is fine for fast unit tests, but fakes drift from the real adapter, so one shared contract suite runs against both the fake and the real Postgres adapter. When the fake's unique-email rule was deleted on purpose, the suite caught it, and only on the fake.

Setup and the reasons to prefer msw over vi.mock of your client are in 04 Node, lesson 29, part 4 and 05 React, lesson 17, part 4. Note that msw 3 ships ESM only, and the option is onUnhandledFrame. Checked on 3.0.4: the old onUnhandledRequest: "error" is ignored at runtime, the default "warn" applies, and the request really went out (a .invalid host, so it ended in ENOTFOUND). This part adds three things those lessons don't cover.

1. A provider failure matrix in one table. A retrying client has at least four bad days: a 500, a response slower than your timeout, a malformed body with status 200, and a 429 with Retry-After. Put them in one it.each and assert the number of attempts, not just the error. The client takes an injected sleep, so backoff is recorded rather than waited out, and the matrix runs in about 300 ms. Note that every attempt must reuse the same idempotency key: a retry that charges twice is the worst possible bug here, so the test checks it. (Real Retry-After values can also be an HTTP date: handle both in production code.)

2. A fetch mock can't see a wrong URL. I changed the path to /v1/charge, singular. The vi.stubGlobal("fetch", ...) test still passed, because it answers everything. The msw test failed, because no handler matched.

3. Handlers drift too. A hand-written handler is a claim about the provider, and claims go stale. Running every mock body through the same Zod schema the client uses makes a stale handler fail at the source, with a message naming the missing field, rather than letting your code quietly handle a shape that doesn't exist.

  your code ──▶ fetch() ──▶ [ msw interceptor ] ──handler──▶ fake response
                                    │
                                    └─ no handler + onUnhandledFrame: "error"
                                       ──▶ the request is rejected, nothing leaves

  vi.stubGlobal("fetch", ...)  replaces fetch itself: URL, method and headers are
                               never checked, unless you assert them yourself

  constructor(readonly kind: ProviderErrorKind, message: string) {
    super(message);
  }

export type ClientDeps = {
  baseUrl: string;
  timeoutMs: number;
  maxAttempts: number;
  sleep: (ms: number) => Promise<void>;
};

const CHARGES_PATH = "/v1/charges";

export async function createCharge(deps: ClientDeps, idempotencyKey: string, amountCents: number): Promise<ChargeResponse> {
  let last: ProviderError | undefined;
  for (let attempt = 1; attempt <= deps.maxAttempts; attempt++) {
    let res: Response;
    try {
      res = await fetch(deps.baseUrl + CHARGES_PATH, {
        method: "POST",
        // نفس الـ key في كل محاولة، عشان الـ retry ميدفعش مرتين
        headers: { "content-type": "application/json", "idempotency-key": idempotencyKey },
        body: JSON.stringify({ amountCents }),
        signal: AbortSignal.timeout(deps.timeoutMs),
      });
    } catch (err) {
      if ((err as Error).name !== "TimeoutError") throw err;
      last = new ProviderError("timeout", `no response in ${deps.timeoutMs} ms`);
      continue;
    }

    if (res.status === 429) {
      last = new ProviderError("rate_limited", "provider said slow down");
      // الـ Retry-After بالثواني، والـ server هو اللي بيحدد إمتى نرجع
      if (attempt < deps.maxAttempts) await deps.sleep(Number(res.headers.get("retry-after") ?? "1") * 1000);
      continue;
    }
    if (res.status >= 500) {
      last = new ProviderError("unavailable", `status ${res.status}`);
      if (attempt < deps.maxAttempts) await deps.sleep(100 * 2 ** (attempt - 1));
      continue;
    }

    return parseCharge(await res.text());
  }
  throw last ?? new ProviderError("unavailable", "no attempts made");
}

function parseCharge(text: string): ChargeResponse {
  let json: unknown;
  try {
    json = JSON.parse(text);
  } catch {
    throw new ProviderError("bad_response", "body is not JSON");
  }
  const parsed = ChargeResponse.safeParse(json);
  if (!parsed.success) throw new ProviderError("bad_response", "unexpected response shape");
  return parsed.data;
}

Part 5 — Time and randomness 🟡 Intermediateالجزء 5 — الوقت والـ random

English

Clocks, randomness, ids and timezones are hidden inputs. There are two ways to control time, and they fit different jobs. An injected Clock port is plain code: pass a fixed clock and the logic runs with no test framework magic, so it's the better default for domain logic like billing. vi.useFakeTimers (with setSystemTime and advanceTimersByTimeAsync) is for code you can't inject into, or that really schedules work with setTimeout. The basics, the month-end bug and clamping are in 04 Node, lesson 29, part 6; here the bug is reproduced briefly and the words go to what that lesson doesn't cover.

The hang. vi.advanceTimersByTime moves the clock synchronously. If the code reaches its setTimeout only after an await, the timer isn't registered yet when you advance, the clock moves past it, and your await on the promise waits forever until the test times out (real: below, with the timeout lowered to 800 ms). advanceTimersByTimeAsync lets microtasks settle between steps, so the timer gets registered and fires.

Seed policy. Random data should be repeatable or it's a flake generator. Use a seeded generator such as mulberry32 for your own randomness, faker.seed(42) for fake data (printed below: identical twice), and an injected id generator instead of crypto.randomUUID in the code under test, so ids are predictable. Fix the timezone in the test environment with env: { TZ: "UTC" }: on this machine (Africa/Cairo) getHours() for 22:00Z returns 0 without it and 22 with it. Finally, make a call nobody mocked fail loudly. With onUnhandledFrame: "error" it never leaves the process. Raw TCP traffic, like a database driver, isn't intercepted by msw, so that's what real-database tests are for.

export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

Part 6 — Honest async tests 🟡 Intermediateالجزء 6 — async tests صادقة

English

An async test is only honest if the test function waits for everything it started. Each failure mode below ran for real:

  • Floating promise. A .then with no return or await: the test finishes first and passes while the wrong assertion runs later or never (our file: green, exit 0).
  • Use await expect(p).resolves / .rejects. For a try/catch you can't avoid, start with expect.hasAssertions(), which fails the test if no assertion ran.
  • No done callback. Vitest doesn't implement Jest's done. The first argument of a test is the test context, not a callback: the test doesn't wait for it, and calling it throws done() callback is deprecated, use promise instead. A failing assertion in a setTimeout then surfaces later as an uncaught exception that fails the run, attributed to whatever was running.
  • Eventual state. Don't sleep(500) and hope. vi.waitFor polls the assertion until it passes or times out. Over 50 tests where the work takes about 15 ms, sleep(500) took ≈25.6 s and vi.waitFor took ≈1.8 s, and it's also more reliable under load because it adapts to how long the work takes.
  • Unhandled rejections fail the run. A background promise that rejects while the suite is running fails it (Errors 1 error, exit 1) even if every test is green. Note the honest limit: if the rejection arrives after the file's tests have finished and the worker has moved on, nothing notices. That's exactly what happened in the first run of this experiment, and why a suite with only fast tests can hide it.

الـ async test صادق بس لو الـ test function مستنية كل حاجة بدأتها. كل حالة تحت اتشغلت فعلًا:

  • الـ floating promise. .then من غير return أو await: الـ test بيخلص الأول وينجح والـ assertion الغلط بتتنفذ بعدين أو مبتتنفذش (عندنا: أخضر و exit 0).
  • استخدم await expect(p).resolves و.rejects. ولو عندك try/catch مش هتقدر تتخلص منه، ابدأ بـ expect.hasAssertions()، وده بيفشّل الـ test لو مفيش assertion اتنفذت.
  • مفيش done callback. Vitest مش بيعمل done بتاعة Jest. أول argument في الـ test هو الـ test context مش callback: الـ test مش بيستناها، وندائها بيرمي done() callback is deprecated, use promise instead. والـ assertion الغلط في setTimeout بتطلع بعدين كـ uncaught exception تفشّل الـ run، وبتتنسب لأي حاجة كانت شغالة ساعتها.
  • الـ eventual state. متعملش sleep(500) وتتمنى. vi.waitFor بيعيد الـ assertion لحد ما تنجح أو الـ timeout يخلص. على 50 test الشغل فيهم بياخد حوالي 15 ms، الـ sleep(500) خد حوالي 25.6 ثانية وvi.waitFor خد حوالي 1.8 ثانية، وكمان أوثق تحت الضغط لأنه بيتأقلم مع الوقت الحقيقي.
  • الـ unhandled rejections بتفشّل الـ run. promise في الخلفية بترفض والـ suite شغالة بتفشّلها (Errors 1 error، exit 1) حتى لو كل الـ tests خضرا. بس فيه حد صادق لازم تعرفه: لو الـ rejection وصلت بعد ما الـ tests بتاعة الملف خلصت والـ worker مشي، محدش هيلاحظ. وده اللي حصل في أول تشغيل للتجربة دي، وعشان كده suite كلها tests سريعة ممكن تخبيها.
فين هستخدمه في شغلي؟ أي test على queue أو worker أو event: await الـ promise لو هي راجعة، وvi.waitFor لو النتيجة بتظهر في DB أو cache بعد شوية. وأي sleep في test اعتبره bug واستبدله. ولو الـ CI فجأة بقى Errors 1 error والـ tests كلها خضرا، دور على promise مش متعمل لها await في كود الـ test أو في الكود نفسه، وده غالبًا bug حقيقي في الـ production كمان.
vi.waitFor is not a free pass It hides how long the work takes. If a job that should take 15 ms starts taking 900 ms, a waitFor with a 1 s timeout still passes. For anything latency-sensitive, assert the duration separately or use the injected clock.
الـ vi.waitFor مش ببلاش: بيخبي الشغل بياخد قد إيه. لو job المفروض ياخد 15 ms بقى ياخد 900 ms، الـ waitFor بـ timeout ثانية هيعدّي. لو الـ latency مهمة، اعمل assert على الوقت لوحده أو استخدم الـ clock المحقون.

Common mistakes · غلطات شائعة

❌ Spy with no restore 
it("handles an outage", async () => {
  vi.spyOn(mailer, "send").mockRejectedValue(new Error("smtp down"));
  // الـ spy هيفضل متركب للـ test اللي بعده
  await expect(notifyCustomer("a@b.c", "x")).rejects.toThrow();
});
✅ Restore automatically 
// في ⁦vitest.config.ts: test: { restoreMocks: true }⁩
it("handles an outage", async () => {
  vi.spyOn(mailer, "send").mockRejectedValue(new Error("smtp down"));
  await expect(notifyCustomer("a@b.c", "x")).rejects.toThrow();
});
بالعامية

❌ من غير restore الـ spy بيفضل مبدّل الـ method، والـ test اللي بعده بيفشل بـ smtp down من حتة مالوش علاقة بيها، وتقعد تدور في المكان الغلط. ✅ حط restoreMocks: true مرة واحدة في الـ config، فكل test يبدأ والـ spies راجعة لوضعها.

❌ Stubbing fetch 
vi.stubGlobal("fetch", vi.fn().mockResolvedValue(new Response("{}")));
// أي URL وأي method هيعدّوا، حتى لو الـ path غلط
await createCharge(deps, "idem-1", 500);
✅ msw that rejects unknowns 
server.listen({ onUnhandledFrame: "error" });
server.use(http.post(`${BASE}/v1/charges`, () => HttpResponse.json(good)));
// أي URL تاني بيترفض باسم الـ URL نفسه
await createCharge(deps, "idem-1", 500);
بالعامية

❌ الـ stub لـ fetch بيرد على أي request، فالـ URL الغلط والـ header الناقص بيعدّوا، وده اللي شفناه فعلًا في الجزء 4. ✅ msw بـ onUnhandledFrame: "error" بيتحقق من الـ URL والـ method وبيفشل بالـ URL الغلط في الرسالة.

❌ Sync advance with a promise 
const job = scheduleReminder(load, send);
vi.advanceTimersByTime(86_400_000);
// الـ timeout هيعدّي والـ test هيعلّق
await job;
✅ Async advance 
const job = scheduleReminder(load, send);
await vi.advanceTimersByTimeAsync(86_400_000);
await job;
بالعامية

❌ لو فيه await قبل الـ setTimeout، الـ sync advance بيتنفذ والـ timer لسه ماتسجلش، فالـ test بيعلّق لحد الـ timeout. ✅ الـ async variant بتفضّي الـ microtasks بين الخطوات، فالـ timer بيتسجل ويشتغل.

❌ Mocking your own logic 
const tax = { vatCents: vi.fn().mockReturnValue(1_400) };
vi.spyOn(totals, "addVat").mockReturnValue(11_400);
// كده محدش بيختبر حساب الـ VAT خالص
✅ Real logic, mocked boundary 
const tax = { vatCents: (net: number) => Math.round(net * 0.14) };
const saved = await new OrderService(pgRepo, tax).place(input);
// الحساب حقيقي، والـ SQL اتنفذ على DB حقيقية
بالعامية

❌ الـ helper والـ tax calculator بتوعك مش boundary، لو عملت لهم mock يبقى الـ test بيختبر الـ mocks. ✅ سيب حساب الضريبة حقيقي، ووصّل الـ repository بـ Postgres حقيقية، و mock بس للي مش بتاعك زي الـ payment provider.

Solution · الحل 
import { http, HttpResponse } from "msw";
import { setupServer } from "msw/node";
import { afterAll, afterEach, beforeAll, expect, it } from "vitest";
import { createCharge, type ClientDeps } from "../p4/src/payments-client.ts";

const BASE = "https://api.payments.test";
const server = setupServer();
beforeAll(() => server.listen({ onUnhandledFrame: "error" }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

it("a 200 with the wrong shape is bad_response and is not retried", async () => {
  let calls = 0;
  server.use(http.post(`${BASE}/v1/charges`, () => {
    calls++;
    return HttpResponse.json({ id: "not-a-charge-id", status: "succeeded", amountCents: 500 });
  }));
  const deps: ClientDeps = { baseUrl: BASE, timeoutMs: 60, maxAttempts: 3, sleep: async () => {} };

  await expect(createCharge(deps, "idem-1", 500)).rejects.toMatchObject({ kind: "bad_response" });
  expect(calls).toBe(1);
});
اتشغل وعدّى: مرة واحدة بس (calls بقت 1) وkind بقى bad_response، لأن الـ Zod schema رفض id اللي مش بيبدأ بـ ch_.
4. In your project: a contract for one fake 🔴 project Pick one port in your side project that has an in-memory implementation (a repository, a mailer log). Write a contract suite for it and run it against the real adapter too. Then point msw at one provider call with onUnhandledFrame: "error" and a Zod schema on the response.

انسخ شكل orderRepositoryContract: function بتاخد اسم و factory. وبعدين اكسر rule في الـ fake عمدًا وشوف الـ suite تحمر على الـ fake بس.

Cheat sheet · الخلاصة

  • Dummy: never used. Stub: canned answer. Spy: records the calls. Mock: owns the expectations. Fake: working simplified implementation.
  • vi.fn = new function, vi.spyOn = watch a real method, vi.mock = replace a module (hoisted); vi.mocked for typing.
  • Vitest 5: clearMocks on by default, restoreMocks off. Set restoreMocks: true. Jest 30 keeps call history.
  • Mock what you don't own and can't run. Run your database for real. Keep your own helpers real.
  • Fakes drift: one contract suite against the fake and the real adapter.
  • msw 3: onUnhandledFrame: "error" (onUnhandledRequest is ignored). A fetch stub can't see a wrong URL.
  • Failure matrix in one it.each: 500, timeout, malformed body, 429 + Retry-After. Assert attempts and the same idempotency key.
  • Parse mock bodies through the production Zod schema so handlers can't go stale.
  • Prefer an injected Clock; advanceTimersByTimeAsync whenever a promise is involved. Sync advance hangs.
  • Seed everything: faker.seed, mulberry32, injected ids, TZ=UTC.
  • Async: await expect(p).resolves/rejects, expect.hasAssertions() around try/catch, never done, vi.waitFor instead of sleep.
  • An unhandled rejection fails the run (exit 1), but only if it arrives while the suite is still running.
بالعامية
  • الـ Dummy: مش بيتستخدم. الـ Stub: إجابة ثابتة. الـ Spy: بيسجل الـ calls. الـ Mock: معاه التوقعات. الـ Fake: implementation مبسطة شغالة.
  • vi.fn = function جديدة، vi.spyOn = مراقبة method حقيقية، vi.mock = تبديل module (بيترفع فوق)، وvi.mocked للـ typing.
  • في Vitest 5: clearMocks شغالة افتراضيًا وrestoreMocks لأ، فحط restoreMocks: true. في Jest 30 الـ call history بيفضل.
  • اعمل mock للي مش بتاعك ومش بتقدر تشغّله، وشغّل الـ DB بجد، وسيب الـ helpers بتاعتك حقيقية.
  • الـ fakes بتبعد عن الواقع: contract suite واحدة على الـ fake وعلى الـ adapter الحقيقي.
  • الـ msw 3: onUnhandledFrame: "error" (وonUnhandledRequest بتتجاهل)، وfetch stub مش بيشوف URL غلط.
  • جدول الفشل في it.each واحد: 500، timeout، body بايظ، 429 مع Retry-After. واتأكد من عدد المحاولات ونفس الـ idempotency key.
  • عدّي الـ mock bodies على Zod schema بتاع الـ production عشان الـ handlers متقدمش.
  • الأفضل Clock محقون، وadvanceTimersByTimeAsync كل ما فيه promise. الـ sync advance بيعلّق.
  • ثبّت كل حاجة بـ seed: faker.seed، mulberry32، ids محقونة، TZ=UTC.
  • الـ async: await expect(p).resolves/rejects، وexpect.hasAssertions() مع try/catch، ومفيش done، وvi.waitFor بدل sleep.
  • الـ unhandled rejection بتفشّل الـ run (exit 1)، بس لو وصلت والـ suite لسه شغالة.
