Why this matters · ليه ده مهم

English

Almost every Node service you ship runs in a container, and the first production surprises come from not knowing what the image really is: a slow CI because the cache is busted, a .env baked into a layer, an app that can't find localhost:5432. Compose is also how a team gets the same Postgres, Redis and Kafka on every laptop with one command. Interviewers ask this because it separates people who copy Dockerfiles from people who can debug them.

بالعامية

تقريبًا كل Node service هتشحنها بتشتغل في container، وأول مفاجآت الـ production بتيجي من إنك مش عارف الـ image دي إيه أصلًا: CI بطيء عشان الـ cache بيتكسر، .env اتحرق جوه layer، أو app مش لاقي localhost:5432. والـ Compose هو الطريقة اللي الفريق كله بياخد بيها نفس الـ Postgres والـ Redis والـ Kafka على كل لابتوب بأمر واحد. والـ interviewers بيسألوا في ده عشان بيفرّق بين اللي بينسخ Dockerfile واللي بيعرف يـ debug واحد.

Part 1 — Images, containers, layers 🟢 Basicالجزء 1 — الـ images والـ containers والـ layers

English

An image is an immutable, ordered stack of read-only filesystem layers plus a config (default command, env, user). A container is a process (or process tree) started from that image, isolated with Linux namespaces and cgroups, with one thin writable layer on top. Deleting a container removes only that thin layer; the image is untouched. So the image is the class and the container is the running instance, and one image can back many containers.

Layers are content-addressed: a layer's name is the sha256 of its bytes. Change one byte and you get a different digest, so a different layer. An image's manifest lists its layers by digest. A registry is content-addressed storage plus names: tag → manifest → blobs. Tags like orders-api:1.0 are mutable pointers, digests are immutable. Because a layer is identified by its content, two images built on the same node:26-slim share those layers on disk and in the registry, and a push only uploads blobs the registry doesn't already have. There are two digests per layer: the diff_id of the uncompressed tar (in the image config) and the digest of the compressed blob (in the manifest).

The stand-in below builds real tar layers, gzips them, hashes them, and writes an OCI-shaped manifest into a store folder. It does not do overlayfs, whiteouts or a full image config: those are Docker's job.

// بديل تعليمي (stand-in) لتخزين الـ image: بيعمل tar حقيقي و sha256 حقيقي و manifest
// مبيعملش overlayfs ولا whiteouts ولا image config كامل، دي شغلة Docker الحقيقي
import { createHash } from "node:crypto";
import { gzipSync } from "node:zlib";
import { existsSync, mkdirSync, readdirSync, writeFileSync } from "node:fs";
import { join } from "node:path";

export type Files = Record<string, string | Buffer>;
export type LayerRef = { digest: string; diffId: string; size: number; reused: boolean };

const sha256 = (b: Buffer): string => "sha256:" + createHash("sha256").update(b).digest("hex");

function tarEntry(name: string, data: Buffer): Buffer {
  const h = Buffer.alloc(512);
  h.write(name.slice(0, 100), 0);
  h.write("0000644\0", 100);
  h.write("0000000\0", 108);
  h.write("0000000\0", 116);
  h.write(data.length.toString(8).padStart(11, "0") + "\0", 124);
  // الـ mtime صفر عشان نفس المحتوى يدّي نفس الـ bytes ونفس الـ digest
  h.write("00000000000\0", 136);
  h.write("        ", 148);
  h[156] = 48;
  h.write("ustar\x0000", 257);
  const sum = h.reduce((a, b) => a + b, 0);
  h.write(sum.toString(8).padStart(6, "0") + "\0 ", 148);
  return Buffer.concat([h, data, Buffer.alloc((512 - (data.length % 512)) % 512)]);
}

export function tar(files: Files): Buffer {
  // الترتيب ثابت: نفس الملفات لازم تطلّع نفس الـ layer
  const names = Object.keys(files).sort();
  const parts = names.map((n) => tarEntry(n, Buffer.from(files[n]!)));
  return Buffer.concat([...parts, Buffer.alloc(1024)]);
}

export function listTar(archive: Buffer): string[] {
  const names: string[] = [];
  for (let off = 0; off + 512 <= archive.length && archive[off] !== 0; ) {
    names.push(archive.toString("utf8", off, off + 100).replace(/\0.*$/s, ""));
    const size = parseInt(archive.toString("ascii", off + 124, off + 135), 8);
    off += 512 + Math.ceil(size / 512) * 512;
  }
  return names;
}

export class BlobStore {
  private dir: string;
  constructor(dir: string) {
    this.dir = dir;
    mkdirSync(dir, { recursive: true });
  }
  // زي الـ registry: لو الـ digest موجود مفيش upload تاني خالص
  put(blob: Buffer): { digest: string; reused: boolean } {
    const digest = sha256(blob);
    const file = join(this.dir, digest.replace(":", "_"));
    const reused = existsSync(file);
    if (!reused) writeFileSync(file, blob);
    return { digest, reused };
  }
  count(): number {
    return readdirSync(this.dir).length;
  }
  pushLayer(files: Files): LayerRef {
    const t = tar(files);
    // الـ diffId للـ tar الخام، والـ digest للنسخة المضغوطة اللي بتتخزن وتتنقل
    const gz = gzipSync(t);
    const { digest, reused } = this.put(gz);
    return { digest, diffId: sha256(t), size: gz.length, reused };
  }
  pushImage(layers: Files[]): { manifest: string; layers: LayerRef[] } {
    const refs = layers.map((l) => this.pushLayer(l));
    const doc = {
      schemaVersion: 2,
      mediaType: "application/vnd.oci.image.manifest.v1+json",
      layers: refs.map((r) => ({ digest: r.digest, size: r.size })),
    };
    return { manifest: this.put(Buffer.from(JSON.stringify(doc))).digest, layers: refs };
  }
}

بالعامية

الـ image عبارة عن stack ثابت من layers read-only فوق بعض، ومعاها config (الأمر الافتراضي، الـ env، الـ user). الـ container هو process (أو شجرة processes) اتشغّلت من الـ image دي، معزولة بـ namespaces و cgroups بتوع Linux، وفوقها layer رفيعة قابلة للكتابة. لما تمسح الـ container، الـ layer الرفيعة بس هي اللي بتتمسح والـ image سليمة. يعني الـ image هي الـ class والـ container هو الـ instance الشغال، وimage واحدة ممكن تشغّل containers كتير.

الـ layers متخزنة بالـ content-address: اسم الـ layer هو sha256 بتاع الـ bytes بتاعتها، فتغيير byte واحد يعني digest جديد يعني layer جديدة. الـ manifest بيليست الـ layers بالـ digest. والـ registry هو تخزين بالمحتوى + أسماء: tag ← manifest ← blobs. الـ tag زي orders-api:1.0 مؤشر ممكن يتغيّر، لكن الـ digest ثابت. وعشان الـ layer متعرفة بمحتواها، اتنين images مبنيين على نفس node:26-slim بيتشاركوا نفس الـ layers على الـ disk وفي الـ registry، والـ push بيرفع بس الـ blobs اللي مش موجودة. ولكل layer اتنين digests: diff_id للـ tar قبل الضغط (في الـ image config) و digest للـ blob المضغوط (في الـ manifest).

الـ stand-in اللي فوق بيعمل tar حقيقي ويضغطه بـ gzip ويحسب الـ hash ويكتب manifest بشكل OCI في folder. اللي مبيعملوش: overlayfs والـ whiteouts والـ image config الكامل، دي شغلة Docker الحقيقي.

فين هستخدمه في شغلي؟ لما الـ orders API والـ billing worker يبقوا من نفس الـ base image ونفس الـ deps، الـ push في الـ CI بيرفع layer الكود بس (كام KB) بدل مئات الـ MB، والـ server بيعمل pull للجديد بس. ولما حد يقولك "الـ tag 1.0 اتغيّر تحتنا"، ده ممكن فعلًا لأن الـ tag مؤشر، فتثبّت الـ digest في الـ production وتعرف بالظبط إيه اللي شغال.
Interview question: image vs container, and why are layers shared? An image is immutable layers plus config; a container is a running process with a writable layer on top. Layers are content-addressed by digest, so identical content is stored and transferred once. That's why rebuilding only the top layers makes pushes and pulls fast.
سؤال interview: الفرق بين image و container؟ وليه الـ layers بتتشارك؟ الـ image هي layers ثابتة + config، والـ container process شغالة وفوقها writable layer. والـ layers متعرفة بالـ digest بتاع محتواها، فالمحتوى المتطابق بيتخزن ويتنقل مرة واحدة. وعشان كده إعادة بناء الـ layers اللي فوق بس بتخلي الـ push والـ pull سريعين.

Part 2 — The basic Dockerfile 🟢 Basicالجزء 2 — الـ Dockerfile الأساسي

English

A Dockerfile is an ordered list of instructions; each filesystem change becomes a layer. For the orders API: FROM picks the base image and starts a stage. WORKDIR sets the directory for everything after it, creating it if needed. COPY brings files from the build context into the image. RUN executes a command at build time and saves the resulting filesystem as a layer. CMD is the default command at run time: it does nothing during the build. EXPOSE only documents which port the app listens on: it doesn't publish anything, and only -p does.

This is the basic version, on purpose. It runs dependencies and source in one stage, as root, with no health check. The production version is the next lesson and 04 Node lesson 32, part 3. The file below was parsed with dockerfile-ast, the parser the VS Code Docker extension uses, so it's real syntax even though it was never built here.

# الأساس: Node 26 LTS على Debian، والنسخة بتاعتها مكتوبة صراحةً
FROM node:26-slim

# كل الأوامر الجاية بتشتغل جوه الـ folder ده، ولو مش موجود بيتعمل
WORKDIR /app

# ملفات الـ dependencies الأول، عشان الـ cache يفضل صالح لو الكود بس اللي اتغيّر
COPY package*.json ./
RUN npm ci --omit=dev

# الكود آخر حاجة، لأنه أكتر حاجة بتتغيّر
COPY . .

# ده توثيق بس: مبيفتحش أي port، اللي بيفتحه هو ⁦-p⁩ وقت الـ run
EXPOSE 3000

# الأمر اللي بيبدأ الـ container، بالـ exec form من غير shell
CMD ["node", "src/server.js"]

بالعامية

الـ Dockerfile ليستة أوامر مرتبة، وكل تغيير في الـ filesystem بيبقى layer. لو على الـ orders API: FROM بيختار الـ base image وبيبدأ stage. WORKDIR بيحدد الـ folder لكل اللي بعده، ولو مش موجود بيعمله. COPY بيجيب الملفات من الـ build context جوه الـ image. RUN بينفذ أمر وقت الـ build ويحفظ النتيجة كـ layer. CMD هو الأمر الافتراضي وقت الـ run ومبيعملش حاجة أثناء الـ build. وEXPOSE توثيق بس بيقول الـ app بيسمع على port كام، مبيفتحش حاجة، واللي بيفتح هو -p.

دي النسخة الأساسية عن قصد: dependencies وكود في stage واحدة، بـ root، ومن غير health check. النسخة بتاعة الـ production في الدرس الجاي وفي درس 32 في قسم Node، الجزء 3. الملف اتقرا بـ dockerfile-ast، نفس الـ parser بتاع VS Code Docker extension، فالصيغة حقيقية حتى لو الـ build ماتعملش هنا.

فين هستخدمه في شغلي؟ أول PR تعمله لـ service لسه من غير Docker: الملف ده بالظبط، بـ npm ci مش npm install عشان يلتزم بالـ lockfile. ولو حد راجعلك PR وحط EXPOSE 3000 ومستني الـ port يتفتح، قوله إن EXPOSE توثيق وإن الـ -p أو الـ ports: في Compose هو اللي بيفتح فعلًا.
Interview question: RUN vs CMD vs ENTRYPOINT? RUN runs during the build and bakes a layer. CMD and ENTRYPOINT run when a container starts; ENTRYPOINT is the executable, CMD is its default arguments, and anything after the image name in docker run replaces CMD.
سؤال interview: الفرق بين RUN و CMD و ENTRYPOINT؟ RUN بيشتغل وقت الـ build ويعمل layer. CMD وENTRYPOINT بيشتغلوا لما الـ container يبدأ: ENTRYPOINT هو البرنامج، وCMD هو الـ arguments الافتراضية بتاعته، وأي حاجة تكتبها بعد اسم الـ image في docker run بتحل محل الـ CMD.

Part 3 — Layer caching, measured 🟢 Basicالجزء 3 — الـ layer caching بالأرقام

English

The builder reuses a layer when the instruction and its inputs are unchanged, and the cache is a chain: the first miss invalidates everything after it. For COPY, the key includes the checksums of the copied files (not their modification times). For RUN, the key is the command text plus the parent layer. That second rule is sharp: a RUN is cached even if the outside world changed, and RUN npm ci reruns only because something before it changed.

So order matters. COPY . . before npm ci means any source edit reinstalls all dependencies. COPY package*.json ./ then npm ci then COPY . . means a source edit reuses the install, and only a lockfile change reruns it. The stand-in layer-cache.ts below hashes each instruction plus its copied files and keeps results in a folder, printing CACHED or BUILT. The npm ci is real, in a temporary copy. It doesn't model BuildKit's parallel stages or a real image filesystem, and the seconds count only each step's own work (saving a snapshot isn't counted). Warm npm cache, small tree, Windows on a loaded machine: read the ratio, not the absolute numbers.

 BAD order                                     GOOD order
 COPY . .      src changed -> digest changes   COPY package*.json ./   CACHED (lockfile same)
    | chain                                       |
 RUN npm ci    MISS -> reinstall everything    RUN npm ci              CACHED (parent same)
                                                  |
                                               COPY . .                MISS -> re-copies code only
الـ cache سلسلة: كل layer مبنية على اللي قبلها. في الترتيب الغلط تغيير ملف كود بيغيّر أول layer فالـ npm ci اللي وراها لازم يتعاد. في الترتيب الصح ملفات الـ dependencies هي اللي في الأول ومتغيرتش، فالتنين الأولانيين CACHED والكود بس هو اللي بيتنسخ.
// بديل تعليمي لـ layer cache: key كل خطوة ⁦= hash(⁩الـ key اللي قبله + نص الأمر + محتوى الملفات)
// الـ npm ci حقيقي والثواني حقيقية، بس مفيش image filesystem حقيقي ولا BuildKit
import { createHash } from "node:crypto";
import { execSync } from "node:child_process";
import { cpSync, existsSync, mkdirSync, readFileSync, readdirSync, rmSync, statSync } from "node:fs";
import { dirname, join, relative } from "node:path";

const here = dirname(new URL(import.meta.url).pathname.replace(/^\/([A-Z]:)/, "$1"));
const APP = join(here, "../orders-app");
const LAB = join(here, "../.lab/cache");

const sha = (s: string | Buffer): string => createHash("sha256").update(s).digest("hex");

function walk(dir: string): string[] {
  return readdirSync(dir).flatMap((n) => {
    const p = join(dir, n);
    if (n === "node_modules") return [];
    return statSync(p).isDirectory() ? walk(p) : [p];
  });
}

function matched(pattern: string): string[] {
  const all = walk(APP);
  if (pattern === ".") return all;
  const re = new RegExp("^" + pattern.replaceAll(".", "[.]").replaceAll("*", "[^/]*") + "$");
  return all.filter((f) => re.test(relative(APP, f).replaceAll("\\", "/")));
}

export function build(name: string, steps: string[]): number {
  const cacheDir = join(LAB, name);
  const work = join(LAB, name + "-work");
  rmSync(work, { recursive: true, force: true });
  mkdirSync(work, { recursive: true });
  mkdirSync(cacheDir, { recursive: true });
  let key = sha("FROM node:26-slim");
  let miss = false;
  let total = 0;
  let previous = "";
  for (const [i, step] of steps.entries()) {
    const [verb, ...rest] = step.split(" ");
    const files = verb === "COPY" ? matched(rest[0]!) : [];
    // الـ COPY بيدخل فيه محتوى الملفات، لكن الـ RUN بيدخل فيه نص الأمر بس
    key = sha(key + step + files.map((f) => relative(APP, f) + sha(readFileSync(f))).join());
    const snapshot = join(cacheDir, key);
    if (!miss && existsSync(snapshot)) {
      console.log(`  [${i + 1}/${steps.length}] CACHED  ${step}`);
      previous = snapshot;
      continue;
    }
    if (!miss && previous) cpSync(previous, work, { recursive: true });
    // أول miss بيكسر كل اللي بعده، لأن كل key بيعتمد على اللي قبله
    miss = true;
    const started = performance.now();
    if (verb === "COPY") for (const f of files) cpSync(f, join(work, relative(APP, f)));
    else execSync(rest.join(" "), { cwd: work, stdio: "ignore" });
    const secs = (performance.now() - started) / 1000;
    total += secs;
    console.log(`  [${i + 1}/${steps.length}] BUILT   ${step}  (${secs.toFixed(2)} s)`);
    cpSync(work, snapshot, { recursive: true });
  }
  return total;
}

Part 4 — .dockerignore 🟢 Basicالجزء 4 — ملف .dockerignore

English

The build context is the folder you send to the builder, and COPY can only see what's in it. .dockerignore removes files from the context, for three reasons: size (fewer files to transfer and to copy), cache stability (COPY . . stops being invalidated by .git changes, logs and coverage), and security (a .env that COPY . . pulls in is now in a layer forever; even RUN rm .env in a later step leaves it readable in the earlier layer, since layers are additive).

The numbers below are computed for real, by tarring the actual project with a stand-in matcher for .dockerignore rules. The stand-in covers *, **/ and !, not every Go-glob feature. Two traps show up: unlike .gitignore, patterns are relative to the context root, so node_modules misses packages/web/node_modules and you need **/node_modules; and ! exceptions must come after the rule they override, because the last matching rule wins.

Why not copy your Windows node_modules? Compiled packages are built for one OS and CPU. esbuild's binary here starts with MZ, the Windows PE header, and its package declares os: win32. Running npm ci inside the Linux image picks the right linux-x64 package from optionalDependencies. Copying from your laptop ships a binary Linux can't load.

import { readFileSync, readdirSync, statSync } from "node:fs";
import { dirname, join, relative } from "node:path";
import { listTar, tar, type Files } from "./oci-lite.ts";

const here = dirname(new URL(import.meta.url).pathname.replace(/^\/([A-Z]:)/, "$1"));
const ROOT = join(here, "../orders-app");

function walk(dir: string): string[] {
  return readdirSync(dir).flatMap((n) => {
    const p = join(dir, n);
    return statSync(p).isDirectory() ? walk(p) : [relative(ROOT, p).replaceAll("\\", "/")];
  });
}

// بديل تعليمي لقواعد ⁦.dockerignore⁩: الـ pattern بيتحسب من root الـ context، و ⁦**⁩ بس اللي بيعدّي folders
function toRegex(pattern: string): RegExp {
  const body = pattern
    .replaceAll(".", "[.]")
    .replace(/\*\*\//g, "§")
    .replace(/\*/g, "[^/]*")
    .replace(/§/g, "(?:.*/)?");
  return new RegExp(`^${body}(?:/.*)?$`);
}

export function isIgnored(path: string, patterns: string[]): boolean {
  let ignored = false;
  // آخر قاعدة بتطابق هي اللي بتكسب، عشان كده الـ ! لازم ييجي بعد
  for (const raw of patterns) {
    const negate = raw.startsWith("!");
    if (toRegex(negate ? raw.slice(1) : raw).test(path)) ignored = !negate;
  }
  return ignored;
}

const patterns = readFileSync(join(ROOT, ".dockerignore"), "utf8")
  .split(/\r?\n/)
  .map((l) => l.trim())
  .filter((l) => l && !l.startsWith("#"));

function context(keep: (path: string) => boolean): Buffer {
  const files: Files = {};
  for (const f of walk(ROOT)) if (keep(f)) files[f] = readFileSync(join(ROOT, f));
  return tar(files);
}

الـ build context هو الـ folder اللي بتبعته للـ builder، وCOPY مش شايف غير اللي جواه. الـ .dockerignore بيشيل ملفات من الـ context لتلات أسباب: الحجم (ملفات أقل تتنقل وتتنسخ)، وثبات الـ cache (الـ COPY . . مبقاش بيتكسر بسبب تغييرات .git والـ logs والـ coverage)، والأمان (الـ .env اللي COPY . . يجيبه بيقعد في layer للأبد، وحتى RUN rm .env في خطوة بعدها مبيشيلوش من الـ layer الأقدم، لأن الـ layers بتتراكم فوق بعض).

الأرقام فوق محسوبة بجد، بـ tar للمشروع الحقيقي و stand-in matcher لقواعد .dockerignore (بيغطي * و**/ و!، مش كل Go-glob). وفيه فخّين: عكس .gitignore، الـ patterns نسبة لـ root الـ context، فـ node_modules مش بيمسك packages/web/node_modules ولازم **/node_modules. والاستثناء بـ ! لازم ييجي بعد القاعدة اللي بيلغيها، لأن آخر قاعدة بتطابق هي اللي بتكسب.

ليه متنسخش الـ node_modules بتاعة Windows؟ الـ packages المتكمبلة معمولة لنظام و CPU محددين. الـ binary بتاع esbuild هنا بيبدأ بـ MZ، الـ header بتاع Windows PE، والـ package معلن os: win32. لما تعمل npm ci جوه الـ Linux image بيختار package الـ linux-x64 الصح من الـ optionalDependencies. النسخ من اللابتوب بيشحن binary Linux مش هيعرف يشغّله.

Part 5 — The Docker CLI 🟢 Basicالجزء 5 — أوامر Docker

English

Most Docker commands are about one process. A container's main process is PID 1 in its own namespaces, so docker logs shows that process's stdout and stderr, and docker stop sends it a signal. Separate two things that look alike: build-time values (ARG and --build-arg, baked in and visible in image history) and run-time env (-e, set per container, no rebuild). -p 8080:3000 maps a host port to a container port. Each container has its own network namespace, so two containers can both listen on 3000; a single host cannot, which the real run below shows as EADDRINUSE.

--rm deletes the container's writable layer when it exits, so docker ps -a doesn't fill with dead containers. --init runs a tiny init process as PID 1 that forwards signals and reaps zombies; the next lesson, part 4 explains why that matters.

import { spawn, type ChildProcess } from "node:child_process";

import { once } from "node:events";

const SERVER = new URL("./whoami-server.ts", import.meta.url).pathname.replace(/^\/([A-Z]:)/, "$1");

async function freePort(): Promise<number> {
  const probe = createServer().listen(0, "127.0.0.1");
  await once(probe, "listening");
  const { port } = probe.address() as { port: number };
  probe.close();
  await once(probe, "close");
  return port;
}

function run(env: Record<string, string>): ChildProcess {

  return spawn(process.execPath, [SERVER], { env: { PATH, SystemRoot, ...env }, stdio: ["ignore", "inherit", "inherit"] });
}

--rm بيمسح الـ writable layer بتاعة الـ container لما يخلص، عشان docker ps -a ميتملاش containers ميتة. --init بيشغّل init صغير كـ PID 1 بيوصّل الـ signals ويعمل reap للـ zombies، والدرس الجاي، الجزء 4 بيشرح ليه ده مهم.

فين هستخدمه في شغلي؟ نفس الـ image تتشحن للـ staging والـ production من غير rebuild، والفرق كله -e: DATABASE_URL و LOG_LEVEL. وأي حاجة حساسة مش مكانها ARG. وزي ما اتشرح في Part 4، أي حاجة وقت الـ build بتفضل في الـ layers. ولما service تقع في الـ production، أول ثلاث أوامر: docker ps (شغالة؟)، docker logs (بتقول إيه؟)، docker exec (لو فيه shell).

function startOrder(all: Record<string, Service>): string[] {
  const seen = new Set<string>();
  const order: string[] = [];
  const visit = (name: string): void => {
    if (seen.has(name)) return;
    seen.add(name);
    // كل dependency لازم يبدأ الأول: ده topological sort بسيط
    for (const dep of Object.keys(all[name]?.depends_on ?? {})) visit(dep);
    order.push(name);
  };
  Object.keys(all).forEach(visit);
  return order;
}

async function waitHealthy(name: string, check: () => Promise<string | true>): Promise<void> {
  let last = "";
  for (let attempt = 1; attempt <= 150; attempt++) {
    const state = await check();
    if (state === true) return console.log(`${name}: healthy after ${attempt} checks`);
    if (state !== last) console.log(`${name}: not ready (${state})`);
    last = state;
    await sleep(100);
  }
  throw new Error(`${name} never became healthy`);
}

Part 7 — Volumes and networking 🟢 Basicالجزء 7 — الـ volumes والـ networking

English

A container's writable layer dies with the container, so data needs to live somewhere else. A named volume is storage managed by Docker: use it for database data, because it survives docker compose down and doesn't depend on your laptop's paths or filesystem. A bind mount maps a host folder into the container: use it for source code in development, so edits show up instantly. Don't use bind mounts for Postgres data on Windows or macOS, where the file-sharing layer is slow and permissions get in the way. Decide by asking who owns the files. Docker owns the data, you own the code.

The run below is a stand-in for a named volume, with a real Postgres 18 server: a data directory that outlives the server. Same directory, rows are there. New directory, the table doesn't exist. That's exactly what docker compose down vs down -v decides. There is one version trap: postgres:18 moved its data path, so the mount is /var/lib/postgresql, not the old /var/lib/postgresql/data; see 07 lesson 01, part 3 for the full story.

Networking. Compose puts every service on a private network with a built-in DNS, so a service's name is its hostname: the API connects to db:5432. localhost inside a container means that same container. So DATABASE_URL=postgres://...@localhost:5432/... copied from your laptop's .env connects to nothing and fails with ECONNREFUSED. From your laptop you use the published port, localhost:5433. The lint below checks the real file for this bug through env config, without any Docker.

    } catch (err) {
      if (i > 200) throw err;
      await new Promise((r) => setTimeout(r, 100));
    }
  }
  try {
    return await work(client);
  } finally {
    await client.end();
    await stopPostgres(data, child);
  }
}

// فحص صغير للغلطة الكلاسيكية: أي hostname في env الـ service لازم يبقى اسم service تاني
import { readFileSync } from "node:fs";
import { parse } from "yaml";

type Compose = { services: Record<string, { environment?: Record<string, string> }> };

function lint(label: string, text: string): void {
  const { services } = parse(text) as Compose;
  const names = new Set(Object.keys(services));
  const problems: string[] = [];
  for (const [service, def] of Object.entries(services)) {
    for (const [key, value] of Object.entries(def.environment ?? {})) {
      if (!/(_URL|_BROKERS)$/.test(key)) continue;
      const host = /^[a-z]+:\/\//.test(value) ? new URL(value).hostname : value.split(":")[0]!;
      if (host === "localhost" || host === "127.0.0.1") problems.push(`${service}.${key}: "${host}" means the container itself`);
      else if (!names.has(host)) problems.push(`${service}.${key}: no service named "${host}"`);
    }
  }
  console.log(`${label}: ${problems.length ? problems.join("; ") : "ok"}`);
}

بالعامية

الـ writable layer بتاعة الـ container بتموت معاه، فالـ data لازم تعيش في مكان تاني. الـ named volume تخزين Docker بيديره: استخدمه لداتا الـ database، عشان بيعيش بعد docker compose down ومش معتمد على paths أو filesystem اللابتوب. الـ bind mount بيربط folder من الـ host جوه الـ container: استخدمه للكود في الـ development عشان التعديلات تبان فورًا. ومتستخدمش bind mount لداتا Postgres على Windows أو macOS، طبقة الـ file sharing بطيئة والـ permissions بتعمل مشاكل. اسأل نفسك: مين صاحب الملفات؟ Docker صاحب الداتا، وإنت صاحب الكود.

الـ run فوق stand-in للـ named volume بـ Postgres 18 حقيقي: data directory بيعيش بعد الـ server. نفس الـ directory والصفوف موجودة، directory جديد والـ table مش موجود. ده بالظبط اللي بيتحدد بـ docker compose down مقابل down -v. وفي فخ في النسخة: postgres:18 غيّر مسار الداتا، فالـ mount على /var/lib/postgresql مش /var/lib/postgresql/data القديم، والتفاصيل في 07 الدرس 01، الجزء 3.

الـ Networking. الـ Compose بيحط كل الـ services على network خاصة فيها DNS، فـ اسم الـ service هو الـ hostname بتاعها: الـ API بيتصل بـ db:5432. وlocalhost جوه الـ container معناها نفس الـ container. فـ DATABASE_URL=postgres://...@localhost:5432/... المنسوخ من الـ .env بتاع اللابتوب بيوصل لمفيش حاجة وبيطلع ECONNREFUSED. ومن اللابتوب بتستخدم الـ published port، localhost:5433. والـ lint فوق بيفحص الملف الحقيقي عن الغلطة دي عن طريق الـ env config من غير Docker.

فين هستخدمه في شغلي؟ الـ API في الـ container بيقول ECONNREFUSED 127.0.0.1:5432 بس الـ DB شغالة: ده الـ localhost الغلط 90% من المرات، واستخدم اسم الـ service. ولما حد يعمل docker compose down -v ويصرخ "الداتا راحت"، ده طبيعي: الـ -v بيمسح الـ volumes. ولو الـ app محتاج يوصل لخدمة شغالة على اللابتوب نفسه، استخدم host.docker.internal، وعلى Linux لازم تضيف extra_hosts: ["host.docker.internal:host-gateway"].

Common mistakes · غلطات شائعة

❌ COPY . . first 
# غلط: أي تعديل في ملف كود بيعيد الـ npm ci
FROM node:26-slim
WORKDIR /app
COPY . .
RUN npm ci
CMD ["node", "src/server.js"]
✅ Dependencies first 
# صح: الـ npm ci بيتعاد لما الـ lockfile يتغيّر بس
FROM node:26-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
CMD ["node", "src/server.js"]
بالعامية

❌ COPY . . الأول بيخلي أي تعديل في الكود يكسر الـ cache ويعيد تسطيب كل الـ dependencies في كل build. ✅ انسخ package*.json الأول وnpm ci وبعدين الكود، فتغيير الكود مبيعيدش الـ install، وتغيير الـ lockfile بس هو اللي بيعيده.

❌ Secret removed in a later layer 
# غلط: الملف لسه جوه layer الـ COPY وأي حد يقدر يقراه
COPY .env .
RUN node scripts/migrate.js
RUN rm .env
✅ Ignored, passed at run time 
# صح: الملف مش في الـ context أصلًا، والقيم بتيجي وقت الـ run
echo ".env" >> .dockerignore
docker run --env-file .env orders-api:1.0
بالعامية

❌ RUN rm .env بيعمل layer جديدة بس، والملف لسه موجود في layer الـ COPY وأي حد عنده الـ image يقراه. ✅ حط .env في .dockerignore عشان ميدخلش الـ context أصلًا، والقيم تيجي وقت الـ run بـ --env-file أو من الـ secret manager. ولو اتسرّب قبل كده، غيّر الـ secret.

❌ localhost inside a container 
services:
  api:
    environment:
      # غلط: localhost هنا معناها الـ api نفسه
      DATABASE_URL: postgres://orders:dev@localhost:5432/orders
✅ The service name 
services:
  api:
    environment:
      # صح: اسم الـ service هو الـ hostname
      DATABASE_URL: postgres://orders:dev@db:5432/orders
بالعامية

❌ localhost جوه الـ container هو الـ container نفسه، ومفيش Postgres سامع هناك، فتاخد ECONNREFUSED. ✅ استخدم اسم الـ service (db)، والـ Compose DNS بيحوله للـ container الصح. ومن اللابتوب بس بتستخدم localhost مع الـ published port.

❌ depends_on with no condition 
services:
  api:
    # غلط: بيستنى الـ container يبدأ بس، مش يبقى جاهز
    depends_on:
      - db
✅ Wait for healthy 
services:
  api:
    # صح: بيستنى الـ healthcheck يعدّي
    depends_on:
      db:
        condition: service_healthy
بالعامية

❌ depends_on لوحده بيستنى الـ container يبدأ، و Postgres ساعتها لسه بيبدأ (وده الـ 57P03 اللي شفناه)، فالـ app بيقع على الأجهزة البطيئة بس. ✅ condition: service_healthy مع healthcheck على الـ db بيستنى الجاهزية الفعلية. وبرضو الـ app لازم يعمل retry، لأن الـ DB ممكن تعمل restart بعدين.

Cheat sheet · الخلاصة

  • Image = immutable layers + config. Container = running process + thin writable layer.
  • Layers are content-addressed by sha256; identical content is stored and pushed once. Tag = mutable pointer, digest = immutable.
  • EXPOSE only documents. -p publishes. RUN runs at build, CMD at run.
  • Cache is a chain: first miss breaks everything after it. COPY package*.json → npm ci → COPY . .
  • RUN is cached by its text, not by what the outside world did.
  • .dockerignore: size, cache stability, secrets. Root-relative: use **/node_modules. ! goes after the rule.
  • A file deleted in a later layer is still in the earlier layer. Rotate leaked secrets.
  • -e = per run, no rebuild. ARG = baked in. Same image, different env.
  • Compose: no top-level version:. depends_on + condition: service_healthy, plus retries in the app.
  • Named volume for data, bind mount for code. postgres:18 mounts /var/lib/postgresql.
  • Inside a container, localhost is the container. Use the service name.
بالعامية
  • الـ image = layers ثابتة + config. والـ container = process شغالة + writable layer رفيعة.
  • الـ layers متعرفة بـ sha256، والمحتوى المتطابق بيتخزن ويترفع مرة واحدة. الـ tag مؤشر بيتغيّر والـ digest ثابت.
  • EXPOSE توثيق بس و-p هو اللي بيفتح. RUN وقت الـ build وCMD وقت الـ run.
  • الـ cache سلسلة: أول miss بيكسر كل اللي بعده. COPY package*.json ← npm ci ← COPY . .
  • الـ RUN بيتعمله cache بنص الأمر، مش باللي حصل بره.
  • الـ .dockerignore للحجم وثبات الـ cache والـ secrets. نسبة للـ root، فاستخدم **/node_modules، و! ييجي بعد القاعدة.
  • الملف اللي اتمسح في layer بعدين لسه موجود في الأقدم، والـ secret اللي اتسرّب لازم يتغيّر.
  • -e لكل run من غير rebuild، وARG بيتحرق جوه. نفس الـ image و env مختلف.
  • الـ Compose: مفيش version: فوق. depends_on + condition: service_healthy و retries في الـ app.
  • الـ named volume للداتا والـ bind mount للكود، وpostgres:18 بيتعمله mount على /var/lib/postgresql.
  • جوه الـ container، localhost هي الـ container نفسها. استخدم اسم الـ service.
