Why this matters · ليه ده مهم

English

A deploy that drops a handful of requests at every release, a node upgrade that takes your whole service down, a pod stuck in CrashLoopBackOff while everyone reads the wrong logs: these are the everyday Kubernetes problems a senior engineer is expected to solve, usually under pressure. This lesson measures the settings that decide them, and turns debugging into a fixed order of commands instead of guessing.

This machine has no cluster, so the behaviour is measured on the labelled stand-in from lesson 33 (real Node processes, real HTTP errors), and kubectl is shown as documentation samples, marked as such.

الجهاز ده مفيهوش cluster، فالسلوك بيتقاس على الـ stand-in المعلَّم عليه من الدرس 33 (Node processes حقيقية و HTTP errors حقيقية)، و kubectl معروض كـ samples من الـ docs ومكتوب عليها كده.

Part 1 — Rolling update settings 🟡 Intermediateالجزء 1 — إعدادات الـ rolling update

English

A RollingUpdate replaces pods gradually, and two numbers set the bounds. maxSurge is how many pods may exist above replicas. maxUnavailable is how many may be unavailable below it. Both default to 25%; surge rounds up and unavailable rounds down, and they can't both be 0. So 3 replicas with the defaults gives 1 and 0, while 10 replicas gives 3 and 2.

These trade speed against cost and capacity. The stand-in rolled 3 replicas from v1 to v2 while 8 clients sent traffic, with graceful pods and a drain window so strategy is the only variable:

  • 1/0 (default for small deployments): one extra pod, capacity never drops, slowest at about 1807 ms.
  • 0/1: no extra pods, so no extra cost, but ready pods drop to 2 of 3 during the rollout. Use it only when you have no spare room (a fixed-size node pool, a license limit).
  • 1/1: faster, about 1059 ms. Ready dropped to 2 and peak was 4.
  • 3/0: full surge, about 835 ms, capacity never drops, but doubles your pods briefly (6 at peak): the cost is real at 50 replicas.

All four runs had 0 failed requests, because every pod shut down gracefully and the drain was long enough. Part 2 shows what happens when it isn't. In a real cluster, also set minReadySeconds so a pod must stay Ready for a while before it counts, and progressDeadlineSeconds so a stuck rollout is reported (default 600 s) instead of hanging silently.

// الـ K8s: الـ maxSurge بيتقرّب لفوق والـ maxUnavailable لتحت
export function resolveRolling(replicas, maxSurge, maxUnavailable) {
  const abs = (v, round) => (typeof v === 'string' ? round((parseFloat(v) / 100) * replicas) : v);
  const s = abs(maxSurge, Math.ceil), u = abs(maxUnavailable, Math.floor);
  if (s === 0 && u === 0) throw new Error('maxSurge and maxUnavailable cannot both be 0');
  return { maxSurge: s, maxUnavailable: u };
}

console.log('defaults on 10 replicas:', JSON.stringify(resolveRolling(10, '25%', '25%')));

const REPLICAS = 3;
async function run(maxSurge, maxUnavailable) {
  const c = createCluster({
    script,
    env: { PRESTOP_MS: '150', WORK_MS: '30', BOOT_MS: '300' },
    probe: { endpointDelayMs: 40, periodMs: 100, timeoutMs: 800 },
  });
  const port = await c.start(REPLICAS);
  await c.waitReady(REPLICAS);
  const load = closedLoop(port, 8, { gapMs: 2 });
  await sleep(300);
  const before = load.latencies.length;
  const t0 = Date.now();
  await c.rollout('v2', { maxSurge, maxUnavailable });
  const durationMs = Date.now() - t0;
  const during = load.latencies.slice(before);
  await sleep(200);
  const codes = await load.end();
  const total = Object.values(codes).reduce((a, b) => a + b, 0);
  c.kill();
  await sleep(150);

    durationMs,
    peakPods: c.stats.peakAlive,
    minReady: c.stats.minReady,
    p99Ms: Math.round(pct(during, 99)),
    failed: total - (codes[200] ?? 0),
    requests: total,
  };
}

بالعامية

الـ RollingUpdate بيبدّل الـ pods بالتدريج، وفيه رقمين بيحددوا الحدود. الـ maxSurge كام pod مسموح يبقوا فوق الـ replicas. والـ maxUnavailable كام واحدة مسموح تبقى مش متاحة تحته. الاتنين default 25%، والـ surge بيتقرب لفوق والـ unavailable لتحت، ومينفعش الاتنين يبقوا صفر. يعني 3 replicas بالـ defaults بيدّوا 1 و 0، و10 replicas بيدّوا 3 و 2.

الرقمين دول بيبدّلوا السرعة قصاد التكلفة والـ capacity. الـ stand-in عمل rollout لـ 3 replicas من v1 لـ v2 و8 clients بيبعتوا traffic، والـ pods graceful وفيه drain window، عشان الـ strategy تبقى هي الحاجة الوحيدة اللي بتتغير:

  • 1/0 (الـ default للـ deployments الصغيرة): pod زيادة واحدة، الـ capacity عمرها ما بتنزل، وأبطأ حاجة حوالي 1807ms.
  • 0/1: مفيش pods زيادة فمفيش تكلفة زيادة، بس الـ ready بينزل لـ 2 من 3 أثناء الـ rollout. استخدمه لو مفيش مكان زيادة (node pool حجمها ثابت، أو license محدودة).
  • 1/1: أسرع، حوالي 1059ms. الـ ready نزل لـ 2 والـ peak كان 4.
  • 3/0: surge كامل، حوالي 835ms، الـ capacity عمرها ما نزلت، بس عدد الـ pods بيتضاعف لفترة (6 في الـ peak)، ودي تكلفة حقيقية عند 50 replica.

الأربع runs كان فيهم صفر requests فاشلة، لأن كل pod بتقفل graceful والـ drain طويل كفاية. الجزء 2 هيوريك لو الـ drain مش كفاية. وفي cluster حقيقي حط كمان minReadySeconds عشان الـ pod لازم تفضل Ready شوية قبل ما تتحسب، و progressDeadlineSeconds (default 600 ثانية) عشان rollout واقف يتبلّغ بدل ما يفضل معلّق من غير صوت.

فين هستخدمه في شغلي؟ orders-api عندك 6 replicas في peak traffic: maxSurge: 2, maxUnavailable: 0 عشان تفضل 6 pods شغالة طول الـ deploy. لو الـ cluster مفيهوش مكان لـ 2 زيادة، الـ surge pods هتبقى Pending والـ rollout يقف، وهتشوف رسالة ProgressDeadlineExceeded بعد 600 ثانية. وقتها الحل يا capacity زيادة يا maxUnavailable: 1.

Part 2 — The termination race 🟡 Intermediateالجزء 2 — سباق الـ termination

English

The shutdown code itself was built in 04 · lesson 24, part 5. This part is about what happens around it. When a Pod is deleted, two things start at the same time: the kubelet begins shutdown (preStop hook, then SIGTERM to PID 1) and the control plane updates EndpointSlices, which every kube-proxy and load balancer then has to act on. They aren't ordered. So for a moment your process is shutting down while traffic still arrives.

Here it is measured on the stand-in, 3 replicas, 8 clients, rollout v1 to v2:

  • Endpoint removed at the same instant as shutdown (best case): 0 of 232 requests failed.
  • Endpoint removed 300 ms late, graceful shutdown: 16 of 288 failed with 502, because server.close stops accepting new connections while they still arrive. Graceful shutdown alone doesn't solve this.
  • Endpoint removed 300 ms late, no graceful shutdown: 14 of 248 failed, about the same: this particular race isn't fixed by graceful code.
  • Endpoint 300 ms late with a 500 ms preStop-style delay before shutdown: 0 of 328 failed.

Read these counts as a lower bound. This stand-in forgets a Pod the moment its process exits, even if the 300 ms hasn't passed, so the failure window is cut short. Lesson 45, part 3 keeps the Pod in the endpoints for the full delay and measures 79 to 88 failed requests at 300 req/s, and 0 with a preStop-style delay. The conclusion is the same.

The fix is to wait for the world to stop sending traffic before you stop serving: a preStop sleep of a few seconds, or the in-app drain delay from lesson 24. Pick one. The sleep handler is run by the kubelet, so it works on distroless images with no shell.

terminationGracePeriodSeconds (default 30) is the cap on everything. The countdown starts before the preStop hook, so your budget is preStop plus drain plus in-flight requests. If the hook is still running when it expires, the kubelet grants a one-off 2 s extension, and then SIGKILL. In the run below, requests of 800 ms with a 500 ms preStop need at least 1300 ms: a 700 ms grace SIGKILLed 2 pods and lost 4 of 30 requests, while 2500 ms lost none. Rule: grace ≥ preStop + longest request + margin. For workers that run long jobs, increase it a lot or make the jobs resumable.

  kubectl delete pod / rollout replaces a pod (t = 0)
       │
       ├── control plane ──▶ EndpointSlice update ──▶ each node / LB, on its own clock
       │
       └── kubelet ──▶ preStop hook ──▶ SIGTERM ──▶ app drains ──▶ exit
                       |<-------- terminationGracePeriodSeconds -------->| SIGKILL

  If SIGTERM lands before the endpoint update reaches every node: 502s.

بالعامية

كود الـ shutdown نفسه اتبنى في 04 · درس 24، الجزء 5. الجزء ده عن اللي بيحصل حواليه. لما Pod تتمسح، حاجتين بيبدأوا مع بعض: الـ kubelet بيبدأ الـ shutdown (الـ preStop وبعدين SIGTERM لـ PID 1) والـ control plane بيحدث الـ EndpointSlices، وكل kube-proxy و load balancer لازم يتحرك على التحديث ده. مفيش ترتيب بينهم. فلفترة صغيرة الـ process بيقفل والـ traffic لسه جاي.

مقاس على الـ stand-in، 3 replicas و 8 clients و rollout من v1 لـ v2:

  • الـ endpoint اتشال في نفس لحظة الـ shutdown (أحسن حالة): 0 من 232 طلب فشلوا.
  • الـ endpoint اتشال متأخر 300ms مع graceful shutdown: 16 من 288 فشلوا بـ 502، لأن server.close بيوقف استقبال connections جديدة وهي لسه جاية. يعني الـ graceful لوحده مش بيحل الموضوع.
  • الـ endpoint متأخر 300ms ومن غير graceful خالص: 14 من 248 فشلوا، تقريبًا نفس الرقم: السباق ده بالذات مش بيتحل بكود graceful.
  • الـ endpoint متأخر 300ms مع delay 500ms على شكل preStop قبل الـ shutdown: 0 من 328 فشلوا.

اعتبر الأرقام دي حد أدنى. الـ stand-in ده بينسى الـ Pod أول ما الـ process بتاعها يخرج، حتى لو الـ 300ms لسه مخلصتش، فنافذة الفشل بتتقصّر. الدرس 45، الجزء 3 بيسيب الـ Pod في الـ endpoints طول مدة التأخير، وبيقيس من 79 لـ 88 طلب فاشل عند 300 req/s، وصفر مع delay على شكل preStop. النتيجة نفسها.

الحل إنك تستنى لحد ما الدنيا تبطل تبعت traffic قبل ما تبطل تخدم: sleep في الـ preStop كام ثانية، أو الـ drain delay جوه الـ app من الدرس 24. اختار واحدة. الـ sleep handler بيشغله الـ kubelet نفسه، فبيشتغل على distroless من غير shell.

الـ terminationGracePeriodSeconds (default 30) هو السقف لكل حاجة. العد التنازلي بيبدأ قبل الـ preStop، فالميزانية بتاعتك = preStop + drain + requests جوه الطيران. لو الـ hook لسه شغال لما الوقت يخلص، الـ kubelet بيدّي تمديد مرة واحدة 2 ثانية، وبعدها SIGKILL. في التجربة فوق، طلبات 800ms مع preStop 500ms محتاجين 1300ms على الأقل: grace 700ms قتلت 2 pods وضيّعت 4 من 30 طلب، و2500ms ما ضيّعتش حاجة. القاعدة: grace ≥ preStop + أطول request + هامش. والـ workers اللي بتشغل jobs طويلة، زودها كتير أو خلّي الـ jobs قابلة تكمّل بعد restart.

فين هستخدمه في شغلي؟ لو عندك 3–5 errors 502 مع كل deploy في orders-api، ده السباق ده بالظبط. ضيف preStop: { sleep: { seconds: 5 } } و terminationGracePeriodSeconds: 40، وشغّل load test أثناء الـ deploy (الـ artifact رقم 10 و12 في الـ README): لازم يطلع صفر errors. ولو الـ endpoint بياخد PDF export بياخد دقيقة، الـ grace 40 مش هتكفي، إما تزودها أو تخلّي الـ export يروح queue.
Interview question "Every deploy causes a handful of 502s even though the app handles SIGTERM gracefully. Why, and what do you change?" → SIGTERM and the endpoint removal happen concurrently, so traffic keeps arriving after server.close stops accepting. Add a wait before shutdown, usually a preStop sleep of a few seconds or a drain delay in the app, so kube-proxy and the load balancer catch up. Then check that terminationGracePeriodSeconds covers preStop plus the longest request, or requests get SIGKILLed.
"كل deploy بيطلّع شوية 502 مع إن الـ app بيعمل SIGTERM graceful. ليه وهتغيّر إيه؟" ← الـ SIGTERM وشيل الـ endpoint بيحصلوا في نفس الوقت، فالـ traffic بيفضل يوصل بعد ما server.close يبطل يستقبل. ضيف انتظار قبل الـ shutdown، غالبًا preStop sleep كام ثانية أو drain delay جوه الـ app، عشان الـ kube-proxy والـ load balancer يلحقوا. وبعدين اتأكد إن terminationGracePeriodSeconds كفاية للـ preStop وأطول request، وإلا الطلبات هتاخد SIGKILL.

Part 3 — Disruptions 🟡 Intermediateالجزء 3 — الـ disruptions

English

Pods also disappear for reasons that have nothing to do with your deploy. Voluntary disruptions are planned: a node drain for an upgrade, a cluster autoscaler compacting nodes. Involuntary ones aren't: a node crashes or a zone goes away.

A PodDisruptionBudget protects you from the voluntary kind. kubectl drain uses the Eviction API, which refuses an eviction with 429 Too Many Requests if it would break the budget, so the drain waits and retries. minAvailable: 2 on 3 replicas means pods leave one at a time, each waiting for a replacement to be Ready. A PDB doesn't help with a crash, and it doesn't limit a normal rolling update (that's maxUnavailable).

For involuntary failures you need replicas on different nodes. podAntiAffinity keeps pods apart, and topologySpreadConstraints (maxSkew, topologyKey, whenUnsatisfiable) spreads them evenly over nodes and zones. Prefer ScheduleAnyway/preferred rules unless you can tolerate a Pending pod when capacity runs out.

The stand-in below has real processes and real traffic, with a simplified scheduler and drain. Three pods on one node with no PDB, drained: 328 of 457 requests failed with 503, because all three left together. Same with minAvailable: 2: 0 of 472 failed, and 33 evictions were refused (429) while replacements came up. Now a sudden node death, no drain at all: three pods on the dead node gave 448 of 568 failures; spread across three nodes it was 0 of 225, 0 of 224 and 3 of 221 over three runs, and only in-flight requests on the dead pod can fail.

Interview question "Why do you need both a PodDisruptionBudget and anti-affinity?" → They cover different failures. A PDB limits how many pods a voluntary eviction, like a node drain, can remove at once, but does nothing when a node crashes. Anti-affinity or topology spread keeps replicas on different nodes, so a crash takes only some of them, but it doesn't stop a drain from evicting them all. You want both, and a PDB must leave room to evict: minAvailable equal to replicas blocks drains forever.
"ليه محتاج PDB و anti-affinity مع بعض؟" ← كل واحد بيغطي فشل مختلف. الـ PDB بيحدد كام pod ممكن eviction اختيارية زي الـ node drain تشيلها مرة واحدة، بس مش بيعمل حاجة لو node وقعت. والـ anti-affinity أو الـ topology spread بيحطوا الـ replicas على nodes مختلفة فالوقوع ياخد جزء بس، لكن مش بيمنع drain يطرد الكل. عايز الاتنين، والـ PDB لازم يسيب مساحة للـ eviction: minAvailable مساوي للـ replicas بيقفل الـ drains للأبد.

Part 4 — The kubectl toolkit 🟡 Intermediateالجزء 4 — أدوات kubectl

English

You don't need to memorise flags, you need an order. Each command answers one question:

  1. kubectl get pods: status, restarts, age. Restart counts and age say whether it's a crash loop or a new deploy.
  2. kubectl describe pod X: Events at the bottom, Last State with exit code and reason. This is where most answers are.
  3. kubectl logs X --previous: the logs of the crashed container. Plain logs shows the new one, which is usually still booting or empty.
  4. kubectl get events --sort-by=.lastTimestamp: everything in the namespace, in order.
  5. kubectl top pod: CPU and memory right now (needs metrics-server).
  6. kubectl exec -it X -- sh: look inside, if the image has a shell.
  7. kubectl port-forward pod/X 3000: hit the app directly and bypass the Service, to see whether the problem is the pod or the path to it.
  8. kubectl debug -it X --image=busybox --target=api: an ephemeral debug container for distroless images, which have no shell. It needs RBAC on pods/ephemeralcontainers.

Read events like an investigator: warnings first, then oldest to newest, because the cause comes before its symptoms. Five statuses cover almost everything you'll see. CrashLoopBackOff isn't a failure itself, it means the container keeps exiting and the kubelet is waiting before the next restart (10 s, 20 s, 40 s, doubling up to a 5 minute cap, reset after 10 minutes of healthy running).

The table gives cause and first check, and the triage script encodes the same logic: it reads the JSON from kubectl get pod -o json, and tells you which of these you have. One trap is worth stating: exit 137 doesn't always mean OOM. It means SIGKILL. The reason field decides: OOMKilled is the memory limit, while Error with a failing liveness probe means the kubelet killed it.

export function classify(pod) {
  const st = pod.status ?? {};
  const events = (pod.events ?? []).join('\n');
  const init = (st.initContainerStatuses ?? []).map((c) => ({ ...c, init: true }));
  const all = [...init, ...(st.containerStatuses ?? [])];

  for (const c of all) {
    const waiting = c.state?.waiting;
    const last = c.lastState?.terminated;
    const where = c.init ? `init container ${c.name}` : c.name;

    if (waiting?.reason === 'CrashLoopBackOff' || c.state?.terminated) {
      if (last?.reason === 'OOMKilled' || c.state?.terminated?.reason === 'OOMKilled') {
        return ['OOMKilled', `${where} exceeded its memory limit (exit 137)`, 'compare limit, heap flag and RSS; kubectl top; logs --previous'];
      }
      if (/Liveness probe failed/.test(events)) {
        return ['CrashLoop (liveness)', `${where} killed by its liveness probe (exit ${last?.exitCode})`, 'describe events; add a startupProbe or fix the probe'];
      }
      return [`CrashLoop${c.init ? ' (init)' : ''}`, `${where} exits by itself (code ${last?.exitCode})`, 'kubectl logs --previous -c ' + c.name];
    }
    if (waiting?.reason === 'ImagePullBackOff' || waiting?.reason === 'ErrImagePull') {
      const msg = waiting.message ?? '';
      if (/unauthorized|denied|401|403/i.test(msg)) return ['ImagePull (auth)', 'registry refused the credentials', 'imagePullSecrets in this namespace'];
      if (/manifest unknown|not found/i.test(msg)) return ['ImagePull (tag)', 'tag or image name does not exist', 'compare image:tag with the registry'];
      return ['ImagePull', msg, 'describe pod; registry reachability'];
    }
    if (waiting?.reason === 'CreateContainerConfigError') {
      return ['ConfigError', waiting.message, 'kubectl get secret/configmap and the referenced keys'];
    }
  }

  const unschedulable = (st.conditions ?? []).find((c) => c.type === 'PodScheduled' && c.status === 'False');
  if (unschedulable) {
    const m = unschedulable.message;
    if (/Insufficient/.test(m)) return ['Pending (capacity)', m, 'requests vs node allocatable; describe node'];
    if (/affinity|selector/i.test(m)) return ['Pending (selector)', m, 'nodeSelector/affinity vs kubectl get nodes --show-labels'];
    if (/taint/i.test(m)) return ['Pending (taint)', m, 'tolerations vs node taints'];
    if (/PersistentVolumeClaim/.test(m)) return ['Pending (volume)', m, 'kubectl get pvc'];
    return ['Pending', m, 'kubectl describe pod'];
  }

  if (st.phase === 'Running' && all.some((c) => !c.ready)) {
    return ['Not Ready', /Readiness probe failed/.test(events) ? 'readiness probe failing, pod receives no traffic' : 'container not ready', 'describe events; probe path and port'];
  }
  return ['Healthy', '-', '-'];
}

// تمرين 1: حدود الـ rollout من الـ percentages
function rollingBounds(replicas, maxSurge = '25%', maxUnavailable = '25%') {
  const abs = (v, round) => (typeof v === 'string' ? round((parseFloat(v) / 100) * replicas) : v);
  const surge = abs(maxSurge, Math.ceil);
  const unavailable = abs(maxUnavailable, Math.floor);
  return { maxPods: replicas + surge, minAvailable: replicas - unavailable };
}

Cheat sheet · الخلاصة

  • maxSurge rounds up, maxUnavailable rounds down, both default to 25%, and they can't both be 0.
  • Surge costs pods, unavailable costs capacity. 1/0 is slow but safe; a large surge is fast but briefly doubles pods.
  • SIGTERM and endpoint removal start together. Graceful shutdown alone leaves 502s: wait first with a preStop sleep or an in-app drain delay.
  • terminationGracePeriodSeconds (default 30) starts before preStop. Grace ≥ preStop + longest request + margin. One-off 2 s extension, then SIGKILL.
  • PDB: protects from voluntary evictions (429 from the Eviction API), not from crashes. minAvailable must be below replicas.
  • Anti-affinity and topologySpreadConstraints: replicas on different nodes and zones, so one node failure isn't an outage.
  • Order: get → describe → logs --previous → events → top → exec or debug. port-forward to skip the Service.
  • Events: warnings first, then oldest to newest: causes come before symptoms.
  • CrashLoopBackOff: restart delay 10 s, doubling, capped at 5 min, reset after 10 min healthy.
  • Exit 137 is SIGKILL. Check reason: OOMKilled means memory; Error with a failing liveness probe means the kubelet killed it.
  • Pending → FailedScheduling message. ImagePullBackOff → message says tag or auth. CreateContainerConfigError → missing Secret or key.
بالعامية
  • الـ maxSurge بيتقرب لفوق والـ maxUnavailable لتحت، والاتنين default 25%، ومينفعش الاتنين صفر.
  • الـ surge بيكلف pods زيادة والـ unavailable بيكلف capacity. 1/0 بطيء وآمن، والـ surge الكبير سريع بس بيضاعف الـ pods لفترة.
  • الـ SIGTERM وشيل الـ endpoint بيبدأوا مع بعض. الـ graceful لوحده بيسيب 502: استنى الأول بـ preStop sleep أو drain delay جوه الـ app.
  • الـ terminationGracePeriodSeconds (default 30) بيبدأ قبل الـ preStop. الـ grace لازم يكون ≥ preStop + أطول request + هامش. تمديد 2 ثانية مرة واحدة، وبعدها SIGKILL.
  • الـ PDB بيحمي من الـ evictions الاختيارية (429 من الـ Eviction API) مش من الـ crashes. والـ minAvailable لازم يبقى أقل من الـ replicas.
  • الـ anti-affinity والـ topologySpreadConstraints: replicas على nodes و zones مختلفة، عشان وقوع node ما يبقاش outage.
  • الترتيب: get ← describe ← logs --previous ← events ← top ← exec أو debug. وport-forward عشان تعدّي الـ Service.
  • الـ events: الـ warnings الأول، وبعدين من الأقدم للأحدث، لأن الأسباب بتيجي قبل الأعراض.
  • الـ CrashLoopBackOff: تأخير الـ restart 10 ثواني بيتضاعف لحد 5 دقايق، وبيتصفر بعد 10 دقايق سليمة.
  • الـ exit 137 معناها SIGKILL. بص على الـ reason: OOMKilled يبقى memory، وError مع فشل liveness يبقى الـ kubelet قتلها.
  • الـ Pending ← رسالة الـ FailedScheduling. الـ ImagePullBackOff ← الرسالة بتقول tag ولا auth. الـ CreateContainerConfigError ← Secret أو مفتاح ناقص.
