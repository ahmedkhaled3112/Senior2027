Why this matters · ليه ده مهم

English

The browser enforces more of your security than most backend developers realise, and it enforces exactly what your headers and cookies tell it to. A wrong CORS header, one innerHTML, or a cookie without the right flag undoes a lot of careful server work. These topics also turn up in almost every senior interview, usually with a follow-up that a memorised answer can't handle.

Everything below ran in real Chrome (the installed one, headless, through Playwright) against this lesson's own servers on loopback. The payloads only write a marker into the page, so each result is something the browser actually did.

بالعامية

المتصفح بيطبّق جزء من الأمان بتاعك أكبر مما أغلب الـ backend developers متخيلين، وبيطبّق بالظبط اللي الـ headers والـ cookies بتقوله. CORS header غلط، أو innerHTML واحدة، أو cookie من غير الـ flag الصح، بيضيّعوا شغل كتير على السيرفر. والمواضيع دي بتيجي في أغلب interviews الـ senior، وغالبًا بسؤال متابعة الحفظ مش بينفع فيه.

كل اللي تحت اتشغّل في Chrome حقيقي (المتثبت على الجهاز، headless، من خلال Playwright) ضد servers الدرس ده بس على الـ loopback. والـ payloads بتكتب علامة في الصفحة وبس، فكل نتيجة هي حاجة المتصفح عملها فعلًا.

Part 1 — Same-origin and CORS 🟡 Intermediateالجزء 1 — الـ same-origin والـ CORS

English

An origin is scheme, host and port together. The same-origin policy (SOP) stops a page from reading responses from another origin. It doesn't stop the page from sending requests. Forms and images have crossed origins since the 1990s, and the web relies on it.

CORS is the server's way of relaxing the reading rule for chosen origins. For a "simple" request (GET, or a POST with a form or text/plain type) the browser sends it and then decides whether your JavaScript may see the response. Anything else, like Content-Type: application/json or a custom header, triggers an OPTIONS preflight first, and the real request goes only if the preflight allows it.

The most important line in the output is the last one in the first block. A POST with no CORS headers at all changed server state, and only the JavaScript's view of the response was blocked. CORS protects the reader. It isn't an access control on your server.

  | POST ---->| runs handler            | OPTIONS ->| no state change

import type { Express } from "express";
import { once } from "node:events";
import type { AddressInfo } from "node:net";
import { setTimeout as sleep } from "node:timers/promises";

// الـ Chrome المتثبت على الجهاز في headless: مفيش browser بيتنزل ولا نافذة بتفتح
export const launch = (): Promise<Browser> => chromium.launch({ channel: "chrome", headless: true });

// كل server على 127.0.0.1 وبورت عشوائي: الهجوم على الـ app بتاع الدرس بس
export async function serve(app: Express) {
  const server = app.listen(0, "127.0.0.1");
  await once(server, "listening");
  return (server.address() as AddressInfo).port;
}

// الـ browser.close ممكن يعلّق تحت الحمل، فبنحط له سقف 6 ثواني
export async function finish(browser: Browser): Promise<never> {
  await Promise.race([browser.close(), sleep(6000)]);
  process.exit(0);
}

// تجميع رسايل الـ console عشان نطبع نص Chrome الحقيقي
export function collectConsole(page: Page): string[] {
  const lines: string[] = [];
  page.on("console", (m) => { if (m.type() === "error") lines.push(m.text()); });
  page.on("pageerror", (e) => lines.push("pageerror: " + e.message));
  return lines;
}

بالعامية

الـ origin هو الـ scheme والـ host والـ port مع بعض. الـ same-origin policy (SOP) بتمنع الصفحة إنها تقرا ردود origin تاني، بس مش بتمنعها إنها تبعت طلبات. الـ forms والصور بتعدي بين الـ origins من التسعينات والويب كله قايم على كده.

الـ CORS هو طريقة السيرفر إنه يخفف قاعدة القراية لـ origins معينة. في الطلب "البسيط" (GET، أو POST بنوع form أو text/plain) المتصفح بيبعته، وبعدين يقرر هل الـ JavaScript يشوف الرد ولا لأ. أي حاجة تانية زي Content-Type: application/json أو header مخصوص بتشغّل OPTIONS preflight الأول، والطلب الحقيقي مش بيتبعت غير لو الـ preflight سمح.

أهم سطر في الناتج: POST من غير أي CORS headers غيّر الرصيد على السيرفر، واللي اتمنع بس هو إن الـ JavaScript يشوف الرد. الـ CORS بيحمي القارئ، ومش access control على السيرفر.

فين هستخدمه في شغلي؟ Next.js على app.shop.com بيكلم API على api.shop.com: حط allowlist بالـ origins بالاسم، وcredentials: true بس لو فعلًا بتستخدم cookies. ولو حد قالك "ضيفنا CORS يبقى الـ API محمي"، قوله إن curl وأي script مش بيسأل عن CORS أصلًا، والحماية هي الـ authentication والـ authorization على السيرفر. والغلطة الشائعة: تعكس أي Origin جاي مع credentials.
Interview question "Does CORS protect your API?" → No. It controls which origins may read a response in a browser. The request still reaches the server, and non-browser clients ignore CORS entirely. Authentication, authorization and CSRF defences protect the server.
"الـ CORS بيحمي الـ API بتاعك؟" ← لأ. هو بيتحكم في مين يقدر يقرا الرد جوه المتصفح. الطلب بيوصل السيرفر برضه، والعملاء اللي مش متصفحات أصلًا مش بيهتموا بالـ CORS. اللي بيحمي السيرفر هو الـ authentication والـ authorization ودفاعات الـ CSRF.

Part 2 — XSS three ways 🟡 Intermediateالجزء 2 — الـ XSS بأنواعه التلاتة

English

The server-rendered basics are in 04 · OWASP in Node, part 2. Here all three variants run in Chrome. Stored: a product review comes from the database. Reflected: a search term comes back in the same response. DOM-based: the page's own script moves location.hash into innerHTML, and the server never sees the fragment, so server-side filtering can't help.

The defence is encoding for the exact context, and the context decides the encoding. HTML escaping is wrong inside a <script>: JSON.stringify alone isn't enough either, because the HTML parser closes the script at the first </script>, before JavaScript runs at all. An href needs its scheme checked, since an escaped javascript: URL is still a valid javascript: URL.

import express from "express";
import { launch, serve, finish } from "./lab.ts";

// مكان واحد للـ escaping بتاع HTML: كل مكان بيطبع بيانات مستخدم يعدّي من هنا
const escapeHtml = (s: string) =>
  s.replace(/[&<>"']/g, (c) => ({ "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;" })[c] as string);

const page = (body: string) => `<!doctype html><meta charset="utf-8"><title>shop</title><body>${body}</body>`;

// الـ payload بيكتب علامة في الصفحة بس: مفيش سرقة ولا اتصال بره
const marker = (kind: string) => `<img src=x onerror="document.body.dataset.xss='${kind}'">`;

const reviews: string[] = [`Great phone ${marker("stored")}`];
const app = express();

// ❌ النوع الأول stored: التعليق من الـ DB بيتحط في الـ HTML زي ما هو
app.get("/bad/product", (_req, res) => { res.send(page(reviews.map((r) => `<p>${r}</p>`).join(""))); });
// ✅ نفس البيانات بعد الـ escape
app.get("/good/product", (_req, res) => { res.send(page(reviews.map((r) => `<p>${escapeHtml(r)}</p>`).join(""))); });

// ❌ النوع التاني reflected: قيمة من الـ URL بترجع في نفس الرد
app.get("/bad/search", (req, res) => { res.send(page(`<h1>Results for ${req.query.q}</h1>`)); });
app.get("/good/search", (req, res) => { res.send(page(`<h1>Results for ${escapeHtml(String(req.query.q))}</h1>`)); });

// ❌ النوع التالت DOM-based: الـ server مش شايف الـ hash خالص
app.get("/bad/dom", (_req, res) => { res.send(page(`<div id="out"></div><script>out.innerHTML = decodeURIComponent(location.hash.slice(1));</script>`)); });
app.get("/good/dom", (_req, res) => { res.send(page(`<div id="out"></div><script>out.textContent = decodeURIComponent(location.hash.slice(1));</script>`)); });

// ❌ سياق جوه script: الـ JSON.stringify لوحده مش كفاية مع وجود كلمة الـ close tag
app.get("/bad/inline", (req, res) => { res.send(page(`<script>const term = ${JSON.stringify(String(req.query.q))};</script><p>ok</p>`)); });
// ✅ تحويل كل قوس لـ unicode escape، فالـ parser مش هيشوف نهاية للـ script
app.get("/good/inline", (req, res) => {
  const safe = JSON.stringify(String(req.query.q)).replace(/</g, "\\u003c");
  res.send(page(`<script>const term = ${safe};</script><p>ok</p>`));
});

const safeHref = (raw: string) => {
  const u = new URL(raw, "http://shop.invalid");
  return ["http:", "https:"].includes(u.protocol) ? raw : "#";
};
app.get("/bad/link", (req, res) => { res.send(page(`<a id="l" href="${escapeHtml(String(req.query.u))}">site</a>`)); });
app.get("/good/link", (req, res) => { res.send(page(`<a id="l" href="${escapeHtml(safeHref(String(req.query.u)))}">site</a>`)); });

English

React escapes text children by default, so {review} renders as text. dangerouslySetInnerHTML turns that off; if you really need user HTML, sanitize it first (DOMPurify removed the onerror below).

The outline for this lesson expected a javascript: href to fire in React. On the installed React 19.3 it doesn't: React replaces the URL with one that throws, and the click only logs an error. The same component on React 18.3.1, run alongside it, kept the URL and the payload executed. So this protection depends on your React version, and a scheme allowlist is still worth having, because other libraries and plain DOM code don't do this for you.

Part 3 — CSP rollout and SRI 🟡 Intermediateالجزء 3 — نشر الـ CSP والـ SRI

English

Directives and nonces are covered in 04 · Hardening, part 1. What people get wrong is the rollout: a strict policy turned on cold breaks production. The safe sequence is Content-Security-Policy-Report-Only with a collector, read what would have broken, fix it, then enforce.

In phase 1 the page runs normally while Chrome posts three real reports to /csp-report. Phase 3 gives the page a per-response nonce and allows the widget's origin by name. The page keeps working, and the injected onerror doesn't run. The one violation left after the fix is the attack itself, which is exactly the signal you want in your logs.

'unsafe-inline' in script-src defeats the point: the same injection ran. Subresource Integrity is the matching control for third-party files: the browser hashes the download and refuses a mismatch, even from an allowed origin. A cross-origin SRI script also needs crossorigin and CORS headers. The lab uses report-uri, which MDN now marks deprecated in favour of report-to with Reporting-Endpoints; report-to delivery is not run here, so send both during a migration.

Part 4 — Cookie flags, observed 🟡 Intermediateالجزء 4 — الـ cookie flags عمليًا

English

Each flag answers one question. HttpOnly hides the cookie from JavaScript, so an XSS can't read the value (it can still act as the user). Secure restricts it to secure transport. SameSite decides whether it goes on cross-site requests. The __Host- prefix forces Secure, Path=/ and no Domain, so a sibling subdomain can't overwrite it.

Two things surprise people here. Chrome accepted Secure and __Host- cookies on both http://localhost and http://127.0.0.1, because loopback is treated as trustworthy; don't conclude that plain HTTP works on a real domain. And cookies aren't isolated by port, while "site" ignores the port too, so two ports on one host are cross-origin but same-site, and even a Strict cookie goes along (more in 04 · OWASP in Node, part 3). localhost and 127.0.0.1 are different sites, which makes them a handy cross-site test bed on one machine.

Part 5 — CSRF in depth 🟡 Intermediateالجزء 5 — الـ CSRF بالتفصيل

English

CSRF exists because the browser attaches cookies automatically. A form on the attacker's site posts to your API, and the victim's session rides along. It needs cookie-based (or other ambient) authentication, and it's blind: the attacker changes state but can't read the result. The lab posts a real auto-submitting form across sites, and later from a sibling subdomain.

Each line of the output changes one thing. Read especially: SameSite=Lax blocks the form POST but not the state-changing GET. A cookie with no SameSite still went on the POST: Chrome's documented Lax+POST exception sends cookies at most 2 minutes old on top-level cross-site POSTs, so the default isn't Lax in that window. And Strict didn't help against an attacker on a sibling subdomain, since that's same-site.

The defences that hold are a signed double-submit token (csrf-csrf 4; csurf is deprecated), Sec-Fetch-Site, which JavaScript can't forge and which is only sent to trustworthy URLs, so plan a fallback when it's absent, and bearer tokens in a header, where nothing is attached automatically.

A JSON content type isn't a defence on its own. application/json forces a preflight, but a text/plain body sails through if your parser accepts any type, and a reflected CORS origin answers the preflight for the attacker. A strict parser plus body validation is what actually blocked the first of those.

import cookieParser from "cookie-parser";

type CookieMode = "none" | "lax" | "strict" | "default";

// الـ app الهدف: Express بكوكي login، وكل سيناريو بيضيف defense واحدة
function buildBank(mode: CookieMode, opts: { sibling?: string; csrfLib?: boolean; secFetch?: boolean; bearer?: boolean; looseJson?: boolean; reflectCors?: boolean } = {}) {
  const state = { moved: 0 };
  const app = express();
  app.use(cookieParser());
  if (opts.looseJson) app.use(express.json({ type: "*/*" }));
  else { app.use(express.json()); app.use(express.urlencoded({ extended: false })); }

  const attrs = (cookie: string) => {
    const base = `${cookie}; Path=/; HttpOnly`;
    return mode === "none" ? `${base}; SameSite=None; Secure` : mode === "lax" ? `${base}; SameSite=Lax` : mode === "strict" ? `${base}; SameSite=Strict` : base;
  };
  app.get("/login", (_req, res) => { res.set("Set-Cookie", attrs("sid=victim-session")).type("html").send("<!doctype html>logged in"); });

  if (opts.reflectCors) {
    // ❌ عكس أي origin مع credentials: ده بيلغي الحماية بتاعة الـ preflight
    app.use((req, res, next) => {
      if (req.headers.origin) res.set({ "Access-Control-Allow-Origin": req.headers.origin, "Access-Control-Allow-Credentials": "true", "Access-Control-Allow-Headers": "content-type" });
      if (req.method === "OPTIONS") return res.status(204).end();
      next();
    });
  }

  const { doubleCsrfProtection, generateCsrfToken } = doubleCsrf({
    // قيمة وهمية للمعمل بس: السر الحقيقي بييجي من secret manager
    getSecret: () => "lab-only-fake-csrf-secret",
    getSessionIdentifier: (req) => req.cookies.sid ?? "",
    cookieName: "csrf",
    cookieOptions: { sameSite: "lax", secure: false, path: "/" },
    getCsrfTokenFromRequest: (req) => req.headers["x-csrf-token"] as string,
  });

  const auth = (req: Request, res: Response, next: NextFunction) => {
    if (opts.bearer) {
      if (req.headers.authorization !== "Bearer lab-only-fake-token") return res.status(401).json({ error: "no_token" });
    } else if (req.cookies.sid !== "victim-session") {
      return res.status(401).json({ error: "no_session" });
    }
    return next();
  };

  // ✅ الـ Sec-Fetch-Site: المتصفح بيقولك الطلب جاي منين، والـ JavaScript مش يقدر يزوّره
  const fetchMetadata = (req: Request, res: Response, next: NextFunction) => {
    const site = req.headers["sec-fetch-site"];
    if (site && !["same-origin", "none"].includes(site as string)) return res.status(403).json({ error: "cross_site_blocked" });
    return next();
  };

  const guards = [auth, ...(opts.secFetch ? [fetchMetadata] : []), ...(opts.csrfLib ? [doubleCsrfProtection] : [])];
  // الـ handler الحقيقي بيقرا الـ body، فلو الـ parser ما فهموش مفيش تحويل
  const transfer = (req: Request, res: Response) => {
    if (!req.body?.to) return res.status(400).json({ error: "invalid_body" });
    state.moved++;
    return res.json({ ok: true, moved: state.moved });
  };
  app.post("/transfer", ...guards, transfer);
  // ❌ تغيير حالة على GET: أي لينك بيعمله
  app.get("/transfer-get", auth, (_req, res) => { state.moved++; res.json({ ok: true }); });
  app.get("/csrf-token", auth, (req, res) => { res.json({ token: generateCsrfToken(req, res) }); });
  app.get("/page", (_req, res) => { res.type("html").send("<!doctype html>bank page"); });
  // أخطاء الـ csrf بترجع 403 من غير stack في الـ console
  app.use((err: Error & { status?: number; code?: string }, _req: Request, res: Response, _next: NextFunction) => {
    res.status(err.status ?? 500).json({ error: err.code ?? "error" });
  });
  return { app, state };
}

الـ CSRF موجود لأن المتصفح بيبعت الـ cookies لوحده. form على موقع المهاجم بيعمل POST على الـ API بتاعك، والـ session بتاعة الضحية بتركب مع الطلب. لازم يكون فيه authentication بالـ cookie (أو حاجة بتتبعت لوحدها)، والهجمة عمياء: المهاجم بيغيّر الحالة بس مش بيقرا النتيجة. المعمل بيبعت form حقيقي cross-site، وبعدها من subdomain شقيق.

English

The full helmet 8 list is in 04 · API security, part 1. New here is measuring what your responses actually send, because headers get dropped by proxies and routes that skip the middleware. The audit below grades one of your own URLs on HSTS, CSP, X-Content-Type-Options, Referrer-Policy and Permissions-Policy.

Plain Express scores 0/5 and helmet() scores 4/5, because helmet 8 doesn't send Permissions-Policy: add it yourself. HSTS only counts over HTTPS; a browser ignores it on a plain HTTP response, and this lab runs on loopback HTTP, so that row is a header check, not a test of enforcement.

The last four lines are the headers doing their job in Chrome. Permissions-Policy: geolocation=() blocks the API even though the context had the permission granted, and nosniff stops a script served as text/plain that otherwise ran.

// السكريبت بيقيّم الردود بتاعتك إنت بس، ومبيعملش scan لأي حاجة بره
type Check = { name: string; ok: boolean; note: string };

function grade(h: Headers): Check[] {
  const hsts = h.get("strict-transport-security") ?? "";
  const maxAge = Number(/max-age=(\d+)/.exec(hsts)?.[1] ?? 0);
  const csp = h.get("content-security-policy") ?? "";
  const scriptSrc = /script-src[^;]*/.exec(csp)?.[0] ?? "";
  const referrer = h.get("referrer-policy") ?? "";
  const permissions = h.get("permissions-policy") ?? "";
  return [
    { name: "HSTS", ok: maxAge >= 15_552_000, note: hsts ? `max-age=${maxAge}` : "missing" },
    { name: "CSP", ok: csp !== "" && !scriptSrc.includes("'unsafe-inline'"), note: csp ? (scriptSrc || "default-src only") : "missing" },
    { name: "X-Content-Type-Options", ok: h.get("x-content-type-options") === "nosniff", note: h.get("x-content-type-options") ?? "missing" },
    { name: "Referrer-Policy", ok: ["no-referrer", "strict-origin-when-cross-origin", "same-origin"].includes(referrer), note: referrer || "missing" },
    { name: "Permissions-Policy", ok: permissions !== "", note: permissions || "missing" },
  ];
}

out.innerHTML = decodeURIComponent(
  location.hash.slice(1),
);
✅ textContent 
out.textContent = decodeURIComponent(
  location.hash.slice(1),
);
بالعامية

❌ innerHTML بيشغّل أي HTML جاي من الـ hash، والسيرفر ماشافش حاجة أصلًا. ✅ textContent بيعرضه كنص، والعلامة في المعمل بقت none.

❌ JSON.stringify inside a script tag 
`<script>const q = ${JSON.stringify(term)};</script>`
✅ Escape the angle bracket too 
const safe = JSON.stringify(term).replace(/</g, "\\u003c");
`<script>const q = ${safe};</script>`
بالعامية

❌ الـ HTML parser بيقفل الـ script عند أول </script> حتى لو جوه string، فأي حاجة بعدها بتبقى HTML حقيقي، وفي المعمل العلامة ظهرت. ✅ تحويل القوس لـ Unicode escape بيخلي JavaScript يقرا نفس القيمة والـ parser ميشوفش نهاية للـ script.

❌ Keeping 'unsafe-inline' 
script-src 'self' 'unsafe-inline'
✅ A nonce per response 
script-src 'self' 'nonce-RANDOM'
بالعامية

❌ 'unsafe-inline' بيسمح لأي inline، ومعاه الـ payload نفسه اتنفذ. ✅ الـ nonce بيتولد لكل response، فالسكريبت اللي الـ server كتبه بس هو اللي بيشتغل، والحقن بيتمنع ويتبلغ.

❌ "We're a JSON API, so no CSRF" 
app.use(express.json({ type: "*/*" }));
app.post("/transfer", requireSession, transfer);
✅ Strict parser plus a real defence 
app.use(express.json());
app.post("/transfer", requireSession, csrfGuard, transfer);
بالعامية

❌ الـ parser اللي بيقبل أي نوع بيخلّي text/plain يعدي من غير preflight، والتحويل اتنفذ في المعمل. ✅ parser بيقبل JSON بس، ومعاه دفاع حقيقي زي token أو Sec-Fetch-Site، وكمان validation للـ body.

1. An allowlist that holds 🟢 easy Write a CORS middleware that allows exactly two origins with credentials and sets Vary: Origin. Test it with a real allowed origin, a look-alike, and a suffix attack such as app.shop.example.evil.example.
اكتب CORS middleware بيسمح بـ 2 origins بالظبط مع credentials ويحط Vary: Origin. جرّبه بـ origin مسموح، وواحد شبهه، وواحد زي app.shop.example.evil.example.
Solution · الحل 
import express, { type NextFunction, type Request, type Response } from "express";
import { serve } from "./lab.ts";

const ALLOWED = new Set(["https://app.shop.example", "https://admin.shop.example"]);

// ✅ قايمة مسموحة بالقيمة الكاملة، مش endsWith ولا regex سايب
function cors(req: Request, res: Response, next: NextFunction) {
  const origin = req.headers.origin;
  if (origin && ALLOWED.has(origin)) {
    res.set({ "Access-Control-Allow-Origin": origin, "Access-Control-Allow-Credentials": "true" });
  }
  // الـ Vary بيمنع الـ CDN إنه يخزّن رد موقع ويدّيه لموقع تاني
  res.vary("Origin");
  if (req.method === "OPTIONS") return res.sendStatus(204);
  return next();
}

const app = express();
app.use(cors);
app.get("/me", (_req, res) => { res.json({ user: "sara" }); });
const port = await serve(app);

for (const origin of ["https://app.shop.example", "https://evil-shop.example", "https://app.shop.example.evil.example"]) {
  const r = await fetch(`http://127.0.0.1:${port}/me`, { headers: { origin } });
  console.log(origin.padEnd(40), "ACAO:", r.headers.get("access-control-allow-origin"), "| Vary:", r.headers.get("vary"));
}
process.exit(0);

2. Reports you can read 🟡 medium A busy site sends thousands of CSP reports. Build a collector that groups them by path, directive and blocked URI, keeps a count for each, and refuses new keys after a cap so a spammer can't fill memory.
موقع عليه ضغط بيبعت آلاف تقارير CSP. اعمل collector بيجمّعهم بالـ path والـ directive والـ blocked URI، وبيعدّ كل مجموعة، وبيرفض مفاتيح جديدة بعد سقف معين عشان مفيش حد يملا الـ memory.
Solution · الحل 
type Report = { "document-uri": string; "violated-directive": string; "blocked-uri": string };

// كل مجموعة بتتعد مرة واحدة، والعدد بيتحسب لكل origin + directive + blocked
const counts = new Map<string, number>();
const MAX_KEYS = 1000;

export function record(r: Report): boolean {
  const key = `${new URL(r["document-uri"]).pathname} | ${r["violated-directive"]} | ${r["blocked-uri"]}`;
  // السقف بيحمي الـ memory: أي حد يقدر يبعت POST للـ collector
  if (!counts.has(key) && counts.size >= MAX_KEYS) return false;
  counts.set(key, (counts.get(key) ?? 0) + 1);
  return true;
}

for (let i = 0; i < 400; i++) record({ "document-uri": "https://shop.example/checkout?o=" + i, "violated-directive": "script-src-elem", "blocked-uri": "https://widget.example/x.js" });
record({ "document-uri": "https://shop.example/", "violated-directive": "img-src", "blocked-uri": "data" });

const top = [...counts.entries()].sort((a, b) => b[1] - a[1]);
for (const [key, n] of top) console.log(String(n).padStart(4), key);

3. Fetch-metadata with a fallback 🔴 hard Write a guard: allow safe methods, allow same-origin, reject cross-site and same-site, and when the header is absent fall back to a token check. Test every branch.
اكتب guard: اسمح بالـ safe methods وsame-origin، وارفض cross-site وsame-site، ولو الهيدر مش موجود ارجع لفحص token. جرّب كل الفروع.
Solution · الحل 
import express, { type NextFunction, type Request, type Response } from "express";
import { serve } from "./lab.ts";

const SAFE = new Set(["GET", "HEAD", "OPTIONS"]);

// ✅ الـ Sec-Fetch-Site أولًا، والـ token احتياطي للعميل اللي مبيبعتش الهيدر
function csrfGuard(req: Request, res: Response, next: NextFunction) {
  if (SAFE.has(req.method)) return next();
  const site = req.headers["sec-fetch-site"];
  if (site === "same-origin") return next();
  if (site === undefined && req.headers["x-csrf-token"] === "lab-only-fake-valid-token") return next();
  return res.status(403).json({ error: "csrf_rejected", site: site ?? "absent" });
}

const app = express();
app.use(csrfGuard);
app.post("/transfer", (_req, res) => { res.json({ ok: true }); });
const port = await serve(app);

// القيم دي المتصفح هو اللي بيكتبها، وهنا بنحطها بإيدنا عشان نختبر كل فرع

  ["sibling subdomain", { "sec-fetch-site": "same-site" }],
  ["old client, token", { "x-csrf-token": "lab-only-fake-valid-token" }],
  ["old client, no token", {}],
];
for (const [name, headers] of cases) {
  const r = await fetch(`http://127.0.0.1:${port}/transfer`, { method: "POST", headers });
  console.log(name.padEnd(24), r.status, await r.text());
}
process.exit(0);

Cheat sheet · الخلاصة

  • SOP blocks reading, not sending; CORS relaxes reading; neither protects the server.
  • JSON or custom headers trigger an OPTIONS preflight; * with credentials is refused by the browser.
  • XSS: stored, reflected, DOM. Encode for the exact context; check href schemes.
  • React escapes text. dangerouslySetInnerHTML needs DOMPurify. React 19.3 blocks javascript: URLs and React 18.3 doesn't.
  • CSP rollout: Report-Only with a collector, fix, enforce. Nonce per response, never 'unsafe-inline'.
  • SRI blocks a tampered third-party file, even from an allowed origin; needs crossorigin.
  • HttpOnly stops reading only. Use __Host- for session cookies.
  • Two ports on one host are same-site. localhost and 127.0.0.1 are different sites. Chrome treats loopback as secure.
  • CSRF: Lax blocks cross-site POST, not state-changing GET and not sibling subdomains. Unset SameSite allows POST for 2 minutes in Chrome.
  • Defences that hold: signed token (csrf-csrf), Sec-Fetch-Site, bearer in a header. JSON alone isn't one.
  • Audit real responses; helmet 8 doesn't send Permissions-Policy; HSTS only counts over HTTPS.
بالعامية
  • الـ SOP بتمنع القراية مش الإرسال، والـ CORS بيخفف القراية، والاتنين مش بيحموا السيرفر.
  • الـ JSON أو الـ custom headers بيشغّلوا OPTIONS preflight، و* مع credentials المتصفح بيرفضها.
  • الـ XSS: stored وreflected وDOM. اعمل encoding مناسب للسياق بالظبط، وافحص scheme بتاع href.
  • React بيعمل escape للنص. dangerouslySetInnerHTML محتاج DOMPurify. وReact 19.3 بيمنع javascript: وReact 18.3 لأ.
  • نشر الـ CSP: Report-Only مع collector، صلّح، enforce. nonce لكل response، وعمرك ما تستخدم 'unsafe-inline'.
  • الـ SRI بيمنع ملف third-party اتغير حتى لو من origin مسموح، ومحتاج crossorigin.
  • HttpOnly بيمنع القراية بس. استخدم __Host- لـ session cookies.
  • بورتين على نفس الـ host يعتبروا same-site. وlocalhost و127.0.0.1 موقعين مختلفين. وChrome بيعتبر الـ loopback secure.
  • الـ CSRF: Lax بيمنع POST cross-site، بس مش GET بيغيّر حالة ومش subdomains شقيقة. والـ SameSite الفاضي بيسمح بالـ POST لدقيقتين في Chrome.
  • الدفاعات اللي بتصمد: signed token (csrf-csrf)، وSec-Fetch-Site، وbearer في header. الـ JSON لوحده مش دفاع.
  • راجع الردود الحقيقية. helmet 8 مبيبعتش Permissions-Policy. والـ HSTS بيتحسب على HTTPS بس.
