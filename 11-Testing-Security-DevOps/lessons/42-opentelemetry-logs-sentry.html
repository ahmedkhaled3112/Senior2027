Why this matters · ليه ده مهم

English

Instrumenting code is the easy half of observability. The hard half is the road between your process and the place you read the data: a collector pipeline that batches and samples, a shipper that must not lose log lines when it crashes, backends that each store something different, and a release marker on every error so you can see which deploy broke it. On-call, the payoff is a single question answered fast: this p99 spike, which request, what did it log, and which deploy shipped it. Interviews test the same chain, usually as "where would you do tail sampling, and what does it cost?" and "how do you make a log pipeline not lose data?"

بالعامية

الـ instrumentation في الكود هو النص السهل من الـ observability. النص الصعب هو الطريق بين الـ process بتاعك والمكان اللي بتقرا فيه: collector بيعمل batching و sampling، shipper لازم ميضيعش log lines لو وقع، backends كل واحدة بتخزن حاجة مختلفة، و release على كل error عشان تعرف أنهي deploy بوّظها. وقت الـ on-call كل ده بيجاوب سؤال واحد بسرعة: الـ p99 spike ده، أنهي request، كتب إيه في الـ logs، وأنهي deploy نزّله. والـ interviews بتختبر نفس السلسلة، غالبًا بسؤال "هتعمل tail sampling فين وبيكلّف إيه؟" و"إزاي الـ log pipeline ميضيعش data؟"

Part 1 — The collector pipeline 🟡 Intermediateالجزء 1 — الـ collector pipeline

English

Why a collector exists. Apps could export straight to the backend, but then every service carries the retry logic, batching, credentials and sampling policy, and switching vendors means a redeploy of everything. The OpenTelemetry Collector takes that out of the app: receivers accept data (OTLP on 4317 gRPC / 4318 HTTP, among others), processors transform it in order, exporters send it onward. A pipeline wires those together per signal: traces, metrics and logs each get one.

Processors in order. memory_limiter goes first, the docs call that best practice, so back-pressure kicks in before anything else allocates. batch (defaults: 8,192 items or a 200 ms timeout, whichever comes first) trades latency for fewer, bigger outbound requests. Between them sit transforms: attributes for scrubbing PII, sampling (Part 2). If you stop reading after this part, remember that the order in the pipeline is the order of execution.

Current naming. In the current Collector docs the HTTP exporter is otlp_http; otlphttp is a deprecated alias that still works and will be removed. Other vendor docs (Grafana's Loki page, at time of writing) still show otlphttp, so you will see both.

The SDK side. Setup from scratch is in 04 · 31, Part 1. New here: @opentelemetry/sdk-trace-base is deprecated on npm in favour of @opentelemetry/sdk-trace 3.x, and BatchSpanProcessor and BatchLogRecordProcessor now take one options object ({ exporter, scheduledDelayMillis }). The old positional form new BatchSpanProcessor(exporter, config) doesn't throw at construction. It silently exports nothing, and this page's first run sent 0 OTLP requests until that was fixed.

The run. The real SDK, auto-instrumenting Express and pino, sent 600 requests' worth of data to the stand-in over OTLP/HTTP. 37 OTLP requests carried 4,200 spans (7 per request, mostly Express middleware layers) and 305 log records. The stand-in's batch processor re-chunked those into 54 store writes for spans and 18 for logs, in sizes like 75, 111 and 72 because the SDK sends its own batches and the batch processor re-buffers them.

// ⚠️ بديل تعليمي للـ OpenTelemetry Collector: receiver لـ OTLP/HTTP بصيغة JSON، و batch processor،
// و routing لـ store لكل signal. مفيهوش gRPC ولا protobuf ولا memory_limiter ولا retries.
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";

export type Span = {
  traceId: string; spanId: string; parentSpanId?: string; name: string;
  startNs: bigint; endNs: bigint; error: boolean; service: string; attributes: Record<string, unknown>;
};
export type LogRecord = { traceId?: string; spanId?: string; severity: string; body: string; timeNs: bigint };

type KV = { key: string; value: Record<string, unknown> };
const attrs = (list: KV[] = []) => Object.fromEntries(list.map((kv) => [kv.key, Object.values(kv.value)[0]]));

type BatchOptions = { batchSize: number; timeoutMs: number };

class BatchProcessor<T> {
  private buffer: T[] = [];
  private timer: NodeJS.Timeout | undefined;
  private readonly opts: BatchOptions;
  private readonly sink: (items: T[]) => void;
  readonly flushes: number[] = [];

  constructor(opts: BatchOptions, sink: (items: T[]) => void) {
    this.opts = opts;
    this.sink = sink;
  }

  add(items: T[]) {
    this.buffer.push(...items);
    if (this.buffer.length >= this.opts.batchSize) this.flush();
    else this.timer ??= setTimeout(() => this.flush(), this.opts.timeoutMs);
  }

  flush() {
    clearTimeout(this.timer);
    this.timer = undefined;
    if (!this.buffer.length) return;
    this.flushes.push(this.buffer.length);
    this.sink(this.buffer);
    this.buffer = [];
  }
}

export async function startCollector(opts: BatchOptions) {
  // الـ stores: Tempo مكان الـ spans و Loki مكان الـ logs، array عادية هنا
  const spans: Span[] = [];
  const logs: LogRecord[] = [];
  const stats = { otlpRequests: 0, droppedHealthSpans: 0 };
  const spanBatches = new BatchProcessor<Span>(opts, (items) => spans.push(...items));
  const logBatches = new BatchProcessor<LogRecord>(opts, (items) => logs.push(...items));

  const server = createServer((req, res) => {
    const chunks: Buffer[] = [];
    req.on("data", (c: Buffer) => chunks.push(c));
    req.on("end", () => {
      stats.otlpRequests++;
      const body = JSON.parse(Buffer.concat(chunks).toString());
      for (const rs of body.resourceSpans ?? []) {
        const service = String(attrs(rs.resource?.attributes)["service.name"]);
        for (const ss of rs.scopeSpans ?? []) {
          const items: Span[] = [];
          for (const s of ss.spans ?? []) {
            const attributes = attrs(s.attributes);
            // الـ processor ده بيرمي spans الـ health check قبل ما تتصدر
            if (attributes["http.route"] === "/healthz") { stats.droppedHealthSpans++; continue; }
            items.push({
              traceId: s.traceId, spanId: s.spanId, parentSpanId: s.parentSpanId, name: s.name,
              startNs: BigInt(s.startTimeUnixNano), endNs: BigInt(s.endTimeUnixNano),
              error: s.status?.code === 2, service, attributes,
            });
          }
          spanBatches.add(items);
        }
      }
      for (const rl of body.resourceLogs ?? []) {
        for (const sl of rl.scopeLogs ?? []) {
          logBatches.add(
            (sl.logRecords ?? []).map((r: { traceId?: string; spanId?: string; severityText?: string; body?: { stringValue?: string }; timeUnixNano?: string }) => ({
              traceId: r.traceId || undefined, spanId: r.spanId || undefined,
              severity: r.severityText ?? "", body: r.body?.stringValue ?? "", timeNs: BigInt(r.timeUnixNano ?? "0"),
            })),
          );
        }
      }
      res.writeHead(200, { "content-type": "application/json" }).end("{}");
    });
  });
  await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));

  return {
    port: (server.address() as AddressInfo).port,
    stats, spanBatches, logBatches, spans, logs,
    spansFor: (traceId: string) => spans.filter((s) => s.traceId === traceId).sort((a, b) => Number(a.startNs - b.startNs)),
    logsFor: (traceId: string) => logs.filter((l) => l.traceId === traceId),
    flush() { spanBatches.flush(); logBatches.flush(); },
    stop: () => server.close(),
  };
}

بالعامية

ليه الـ collector أصلًا. الـ apps ممكن تبعت للـ backend مباشرة، بس ساعتها كل service لازم تشيل الـ retry والـ batching والـ credentials وسياسة الـ sampling، ولو غيرت الـ vendor هتعمل redeploy لكله. الـ collector بياخد ده بره الـ app: receivers بتستقبل الـ data (OTLP على 4317 gRPC و4318 HTTP ضمن غيرهم)، وprocessors بتعدّل عليها بالترتيب، وexporters بتبعتها. والـ pipeline بتوصل دول مع بعض لكل signal: traces و metrics و logs كل واحدة لوحدها.

ترتيب الـ processors. memory_limiter بيتحط الأول، والـ docs بتقول إن ده الـ best practice، عشان الـ back-pressure يشتغل قبل أي حاجة تاني. batch (الـ default: 8192 عنصر أو 200 ms، أيهما أول) بيضحي بشوية latency مقابل requests أقل وأكبر. وبينهم الـ transforms: attributes لمسح الـ PII، والـ sampling (الجزء 2). ولو هتفتكر حاجة واحدة: ترتيب الـ pipeline هو ترتيب التنفيذ.

الأسماء الحالية. في الـ docs الحالية للـ Collector، الـ HTTP exporter اسمه otlp_http، وotlphttp بقى alias متشال مستقبلًا (deprecated). docs تانية (صفحة Loki مثلًا وقت كتابة ده) لسه مكتوب فيها otlphttp، فهتشوف الاتنين.

ناحية الـ SDK. الإعداد من الصفر في الدرس 31 في قسم 04، الجزء 1. الجديد هنا: @opentelemetry/sdk-trace-base بقت deprecated على npm لحساب @opentelemetry/sdk-trace 3.x، وBatchSpanProcessor وBatchLogRecordProcessor بقوا بياخدوا object واحد ({ exporter, scheduledDelayMillis }). الشكل القديم new BatchSpanProcessor(exporter, config) مبيرميش error وقت الـ construction، بس بيسكت ومبيصدّرش حاجة، وأول run في الصفحة دي بعت 0 OTLP requests لحد ما اتصلحت.

الـ run. الـ SDK الحقيقي، بـ auto-instrumentation لـ Express و pino، بعت 600 request data للـ stand-in على OTLP/HTTP: 37 OTLP request شالوا 4200 span (7 لكل request، معظمهم Express middleware) و305 log. الـ batch processor بتاع الـ stand-in قسّمهم 54 store write للـ spans و18 للـ logs، والأحجام مختلفة (75 و111 و72 مثلًا) لأن الـ SDK بيبعت batches بتاعته والـ processor بيعيد تجميعها.

فين هستخدمه في شغلي؟ في Kubernetes حط Collector كـ DaemonSet أو sidecar جنب الـ pods يعمل batching ويخفف عن الـ app، وكل الـ services تبعت لـ localhost:4318 من غير ما تعرف الـ backend مين. ولما تغيّر من Jaeger لـ Tempo تعدل config الـ Collector بس، من غير redeploy لأي service. ولو الـ Collector نفسه OOM تحت الضغط، أول حاجة تراجعها إن memory_limiter أول processor.
Trade-off: another hop The collector is one more process that can fall behind or die. Without persistent queues in its exporters, a crash drops what was buffered in memory. For most teams that's a good trade against per-app retry logic, but it means the collector is a production service you monitor and scale, with its own /metrics.
الـ trade-off: hop زيادة. الـ collector process زيادة ممكن يتأخر أو يقع. ومن غير persistent queues في الـ exporters، لو وقع بيضيع اللي كان في الـ memory. ده غالبًا trade كويس مقابل الـ retry في كل app، بس معناه إن الـ collector production service بتراقبها وتعمل لها scale، وليها /metrics بتاعتها.

Part 2 — Sampling 🟡 Intermediateالجزء 2 — الـ sampling

English

Head versus tail, and the numbers behind tail sampling, are in 10 · 39, Part 3. New here is where sampling sits in a pipeline and what it costs in memory.

  1. In the SDK: TraceIdRatioBasedSampler decides at the first span. Cheapest, and it never sees errors in advance.
  2. In a Collector tier that's close to the app: the probabilistic_sampler processor. It hashes the trace ID (mode hash_seed by default), so every replica keeps or drops the same traces, as long as they share a hash_seed.
  3. In a gateway Collector tier: tail_sampling waits for the whole trace, then decides: all spans of a trace must reach the same Collector instance, or the decision sees half the trace. So you deploy two layers, with the loadbalancing exporter in front, routing by trace ID. Defaults: decision_wait 30s and num_traces 50,000.

Memory is decision_wait × spans/second × bytes per span. Spans wait in memory for the whole decision window, so it's a straight multiplication. Measured on a JS stand-in (a Map of real span shapes): 355 bytes per buffered span. At 500 spans/s that's about 5 MB for a 30-second window, at 20,000 spans/s about 203 MB. The Collector is Go with its own data model, so measure yours; the shape is what carries over: double decision_wait, double the memory. Set decision_wait a bit above your slowest healthy trace, not to "a long time".

The policy on real traces. Keeping all errors, everything slow, and 10% of the rest on the same 600 real traces kept 67: 4 with errors, 5 slow, 58 baseline. That is the point of tail sampling: every error and slow trace survives, at about 11% of volume. A 10% head sample would keep about 60 traces too, and on average only one tenth of the errors and slow traces would be among them.

  SDK (head sampler)  ->  agent collector (probabilistic_sampler: hash trace_id)
                              |
                              v  loadbalancing exporter: route by trace_id
              gateway collector replicas (tail_sampling) [same trace, same replica]
                              |
                              v
                         Tempo / Jaeger
مكان القرار: الـ SDK ممكن يعمل head sampling بدري، وبعدين agent collector قريب من الـ app يعمل probabilistic_sampler بالـ hash بتاع الـ trace ID. لو عايز tail sampling، لازم layer تانية من gateway collectors والـ loadbalancing exporter قدامها بيوزع بالـ trace ID، عشان كل spans الـ trace الواحد توصل لنفس الـ replica، وبعدين Tempo أو Jaeger.

بالعامية

الـ head والـ tail وأرقام الـ tail sampling موجودين في الدرس 39 في قسم 10، الجزء 3. الجديد هنا: الـ sampling بيتحط فين في الـ pipeline وبياكل memory قد إيه.

  1. في الـ SDK: TraceIdRatioBasedSampler بيقرر عند أول span. أرخص حاجة، وعمره ما بيشوف الـ errors اللي لسه هتحصل.
  2. في طبقة Collector قريبة من الـ app: الـ probabilistic_sampler. بيعمل hash للـ trace ID (الـ default mode هو hash_seed)، فكل الـ replicas بتاخد نفس القرار بشرط يبقى عندهم نفس الـ hash_seed.
  3. في طبقة Collector gateway: الـ tail_sampling بيستنى الـ trace كله وبعدين يقرر، وكل spans الـ trace لازم توصل لنفس الـ instance، وإلا القرار هيشوف نص الـ trace. عشان كده بتعمل طبقتين، والـ loadbalancing exporter قدام بيوزع بالـ trace ID. الـ defaults: decision_wait 30 ثانية وnum_traces 50,000.

الـ memory = decision_wait × spans/ثانية × حجم الـ span. الـ spans بتفضل مستنية في الـ memory طول فترة القرار، فهي عملية ضرب مباشرة. قسناها على stand-in في JS: 355 byte لكل span متخزن. يعني 500 span/s بيبقى حوالي 5 MB لـ window بتاعة 30 ثانية، و20,000 span/s حوالي 203 MB. الـ Collector مكتوب بـ Go وليه data model تاني، فاقيس بتاعك، بس الشكل هو اللي بيفضل صحيح: ضاعف decision_wait تضاعف الـ memory. حط decision_wait فوق أبطأ trace سليم عندك بشوية، مش "وقت طويل وخلاص".

السياسة على traces حقيقية. كل الأخطاء، وكل البطيء، و10% من الباقي، على نفس الـ 600 trace الحقيقيين، احتفظت بـ 67: 4 أخطاء و5 بطيئين و58 baseline. ده بالظبط فايدة الـ tail sampling: كل error وكل trace بطيء بيفضلوا، على حوالي 11% من الحجم. و head sampling 10% كان هيحتفظ بحوالي 60 trace برضو، بس في المتوسط عُشر الأخطاء والبطيء بس.

فين هستخدمه في شغلي؟ لو الـ traces بتكلفك كتير: ابدأ بـ head sampling 10% في الـ SDK لو مش محتاج تحليل أخطاء دقيق، ولما تعوز "كل error و latency spike يتشافوا"، ضيف tail sampling في gateway collector. وقبل ما تكبر decision_wait، احسب memory الـ gateway بنفس الضرب ده بأرقام الـ spans بتاعتك.
What breaks: tail sampling without trace affinity With two Collector replicas behind a plain load balancer, a trace's spans land on both. Each replica sees half a trace: an error span on one replica means nothing to the other, which drops the rest of the trace, and you end up with partial traces in Tempo. The README states it flatly: "All spans for a given trace MUST be received by the same collector instance."
إيه اللي بيكسر: tail sampling من غير affinity. لو عندك 2 Collector replicas ورا load balancer عادي، spans الـ trace الواحد بتوصل للاتنين، وكل واحد شايف نص trace: span فيها error في replica والتانية مش عارفة وترمي الباقي، فتلاقي traces ناقصة في Tempo. الـ README بتقولها صراحة: كل spans الـ trace الواحد لازم توصل لنفس الـ collector instance.
Interview question "We want every errored trace kept, but only 10% of normal traffic. Where does that decision live and what's the cost?" → It has to be tail sampling, because the head doesn't know yet if a trace will fail. Run it in a gateway Collector tier, behind a load-balancing exporter keyed on trace ID so one replica sees the whole trace, and budget memory as decision_wait × spans/s × bytes per span.

Part 3 — Traces and logs backends 🟡 Intermediateالجزء 3 — الـ backends بتاعة الـ traces والـ logs

English

Each store is built around one question. Prometheus answers "what's the rate and p99 now?" with sampled numbers in a time-series database; it also accepts OTLP directly with --web.enable-otlp-receiver at /api/v1/otlp/v1/metrics. Tempo answers "show me this trace": it stores full traces in object storage and retrieves them by trace ID, with TraceQL on top. Jaeger answers the same question and is now built on the OpenTelemetry Collector framework; storage plugs into Cassandra, Elasticsearch/OpenSearch, ClickHouse, Badger or memory. Loki answers "which log lines match?" by indexing only labels, not the text, so it's cheap to run but a full-text search scans chunks. It takes OTLP at /otlp, and everything in the LogRecord except body and timestamps is stored as structured metadata. Elasticsearch/OpenSearch (the ELK-style stacks) index the full text, which makes searches fast and storage and memory much more expensive.

Tempo 3 changed the write path. Tempo 3.0 removed the ingester module: the design previously called Project Rhythm is now the only ingest path. In microservices mode writes go to a Kafka-compatible log (acknowledged after Kafka confirms), block-builders cut blocks for object storage, and live-stores serve recent queries, with replication factor 1 instead of the old 3. If you carry a Tempo 2.x config you must migrate it: tempo-cli migrate config.

Routing is one line per pipeline in the config from Part 1. The stand-in routes spans and logs to two separate stores and answers the backend's core query: all spans for a trace. A linear scan of 4,200 spans took about 0.2 ms here; real backends use an index because they hold billions.

Part 4 — The log pipeline 🟡 Intermediateالجزء 4 — الـ log pipeline

English

The shape. The app writes structured JSON to stdout or a file (the pino setup is in 04 · 30). A shipper (Fluent Bit or Vector) tails that output, parses it, batches it and sends it to a store. Its job is to survive restarts: it keeps an offset file (Fluent Bit's db, Vector's data_dir checkpoint) so it resumes where it stopped.

At-least-once, not exactly-once. Fluent Bit's docs say it plainly: on restart it resumes from the last committed checkpoint, so a small number of records can be re-ingested. Vector checkpoints after each read. The stand-in demonstrates the mechanism. It tails a real file written by real pino, batches up to 100 lines, retries on failure with exponential backoff, and saves the offset only after a batch is accepted. It crashed deliberately at the worst moment, right after the store accepted batch 8 and before the offset was saved. On restart it re-sent that batch, 26 lines.

Result of the run. 3,000 lines written, 3,000 unique lines stored, 0 lost. The store received 3,226 lines: 26 from the crash and 200 from two batches retried after their reply was lost. If you need exactly-once downstream, dedupe with an idempotency key on ingest; the log line's own i field did that job in this demo. Save the offset after the ack, or you trade duplicates for silent data loss.

Retention and cost. Retention is a backend setting (in Loki, the compactor applies it), and volume, not vendor, drives the bill. At 300 req/s, 4 lines per request, 450 bytes per line, that's 1,400 GB and 3.1 billion events a month. At the list prices from the previous lesson, Grafana Cloud's logs line is about $742/month and Datadog's (ingest plus indexing) about $5,428. Dropping debug and health-check noise leaves 770 GB. Sampling info to 10% while keeping every warn and error leaves 147 GB: about $53 and $570. Field-level redaction, levels and per-tenant sampling are in 04 · 30, Part 6.

Not run here: Fluent Bit Fluent Bit isn't installed on this machine. This real config was checked by a YAML parser only. The same job in Vector would be a file source with data_dir and a Loki sink.

// ⚠️ بديل تعليمي لـ Fluent Bit أو Vector: بيتابع ملف حقيقي بـ offset محفوظ، و batches، و retries.
// مفيهوش log rotation ولا compression ولا backpressure ولا buffering على القرص.
import { closeSync, existsSync, openSync, readFileSync, readSync, statSync, writeFileSync } from "node:fs";

const [, , file, sinkUrl, checkpoint, crashAfterArg] = process.argv as unknown as [string, string, string, string, string, string?];
const crashAfter = Number(crashAfterArg ?? 0);
const BATCH_SIZE = 100;

let offset = existsSync(checkpoint) ? Number(readFileSync(checkpoint, "utf8")) : 0;
console.log(`shipper start: resuming at byte ${offset}`);

let batches = 0;
let retries = 0;
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

async function sendWithRetry(lines: string[]) {
  for (let attempt = 0; ; attempt++) {
    try {
      const res = await fetch(sinkUrl!, { method: "POST", body: lines.join("\n"), signal: AbortSignal.timeout(3000) });
      if (res.ok) return;
    } catch {
      // الـ timeout والـ network error معاملتهم زي الـ 500: نعيد
    }
    retries++;
    await sleep(Math.min(1000, 40 * 2 ** attempt));
  }
}

for (;;) {
  const { size } = statSync(file!);
  if (size > offset) {
    const fd = openSync(file!, "r");
    const buffer = Buffer.alloc(size - offset);
    readSync(fd, buffer, 0, buffer.length, offset);
    closeSync(fd);

    // بنقف عند آخر سطر كامل، والسطر الناقص يستنى الدورة الجاية
    const lastNewline = buffer.lastIndexOf(10);
    if (lastNewline >= 0) {
      const complete = buffer.subarray(0, lastNewline + 1);
      const lines = complete.toString("utf8").split("\n").filter(Boolean);
      let consumed = 0;
      for (let i = 0; i < lines.length; i += BATCH_SIZE) {
        const chunk = lines.slice(i, i + BATCH_SIZE);
        await sendWithRetry(chunk);
        batches++;

        // ده أسوأ وقت للوقوع: الـ batch وصل والـ offset لسه متحفظش
        if (crashAfter && batches === crashAfter) {
          console.log(`shipper crash: batch ${batches} delivered (${chunk.length} lines), offset not yet saved`);
          process.exit(137);
        }

        consumed += chunk.reduce((n, l) => n + Buffer.byteLength(l) + 1, 0);
        writeFileSync(checkpoint, String(offset + consumed));
      }
      offset += consumed;
    }
  } else if (existsSync(`${file}.done`)) {
    console.log(`shipper done: batches=${batches} retries=${retries} offset=${offset}`);
    process.exit(0);
  } else {
    await sleep(40);
  }
}

Releases. Basic Sentry setup is in 04 · 31, Part 5. The new piece is that every event carries a release and an environment, so a spike can be pinned to the deploy that introduced it and regressions can be flagged. An envelope is newline-delimited JSON: one header line, then pairs of item header and payload.

Source maps and debug IDs. Minified production code gives useless frames; the run captured {"file":"checkout.min.cjs","line":1,"col":507,"fn":"c"}. Sentry symbolicates using source maps you upload. Debug IDs tie a bundle to its map without relying on file names: sentry-cli sourcemaps inject adds a //# debugId=… comment to the JS and a "debug_id" field to the map (esbuild's output here had neither). The release given to sentry-cli sourcemaps upload --release=… must match release in Sentry.init.

Budget for events. Sentry bills by events, so an error budget for volume matters. At 1,000 req/s and 0.5% errors you'd send 5 events/s, 13M a month. Controls, in order of leverage: don't send expected errors (validation failures as handled responses, or ignoreErrors), beforeSend to drop or scrub, sampleRate below 1 for the rest. When the ingest answers 429 with X-Sentry-Rate-Limits, the SDK stops sending that category for the stated time. In the run, 51 captures produced only 4 error events on the wire before the limit stopped the rest; the other envelopes were sessions and a client report, which tells the server what was dropped client-side.

import { createServer } from "node:http";
import type { AddressInfo } from "node:net";
import { gunzipSync } from "node:zlib";

export async function startIngest(rateLimitAfter: number) {
  const events: Record<string, any>[] = [];
  let posts = 0;
  let limited = 0;
  const itemTypes: Record<string, number> = {};

  const server = createServer((req, res) => {
    const chunks: Buffer[] = [];
    req.on("data", (c: Buffer) => chunks.push(c));
    req.on("end", () => {
      posts++;
      const raw = Buffer.concat(chunks);
      const text = (req.headers["content-encoding"] === "gzip" ? gunzipSync(raw) : raw).toString();
      const lines = text.split("\n").filter(Boolean);

      // الـ envelope سطور JSON: header للـ envelope، وبعدين زوج (item header ثم payload)
      for (let i = 1; i < lines.length - 1; i += 2) {
        const header = JSON.parse(lines[i]!);
        itemTypes[header.type] = (itemTypes[header.type] ?? 0) + 1;
        if (header.type === "event") events.push(JSON.parse(lines[i + 1]!));
      }

      if (posts > rateLimitAfter) {
        limited++;
        // ده نفس header الـ rate limit الحقيقي بتاع Sentry: ممنوع errors لمدة 60 ثانية
        res.writeHead(429, { "Retry-After": "60", "X-Sentry-Rate-Limits": "60:error:key" }).end();
        return;
      }
      res.writeHead(200, { "content-type": "application/json" }).end(JSON.stringify({ id: "stand-in" }));
    });
  });
  await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));
  return {

    get limited() { return limited; },
    stop: () => server.close(),
  };
}

Common mistakes · غلطات شائعة

❌ Old positional constructor (sdk-trace 3.x) 
new BatchSpanProcessor(exporter, { scheduledDelayMillis: 200 })
// مفيش error عند التشغيل، والـ run الحقيقي: 0 OTLP requests
✅ One options object 
new BatchSpanProcessor({ exporter, scheduledDelayMillis: 200 })
// الـ run الحقيقي: 37 OTLP request و 4200 span
بالعامية

❌ لما ترقّي من sdk-trace-base لـ sdk-trace 3، الشكل القديم مبيعملش error، بيسكت بس ومبيبعتش spans خالص، وهتفضل تدور في الـ network والـ endpoint. ✅ الشكل الجديد object فيه exporter وscheduledDelayMillis. وأول علامة على المشكلة دي: زيرو requests بتوصل للـ collector، فراجع ده أول حاجة بعد أي upgrade.

❌ Save the offset before the store accepts 
writeFileSync(checkpoint, String(newOffset));
await sendWithRetry(batch);
// لو وقع هنا الـ batch بيضيع للأبد
✅ Save after the ack 
await sendWithRetry(batch);
writeFileSync(checkpoint, String(newOffset));
// لو وقع هنا بيعيد الإرسال: تكرار من غير فقد
بالعامية

❌ لو حفظت الـ offset قبل ما الـ store يقبل، ووقعت بعد الحفظ وقبل الـ send، الـ batch ضاع من غير ما حد يعرف. ✅ لما تحفظ بعد الـ ack، الوقوع في أسوأ لحظة بيعمل تكرار بس: في الـ run طلعوا 226 سطر مكرر و0 ضايع. التكرار بيتعالج بـ idempotency key، أما الفقد ملوش حل.

❌ Tail sampling across replicas with no affinity 
service/otelcol-gateway: replicas: 3
load balancer: round robin
tail_sampling: on every replica
# each replica sees half of each trace
✅ Route by trace ID first 
agent tier: loadbalancing exporter
  routing_key: traceID
gateway tier: tail_sampling
# one replica sees the whole trace
بالعامية

❌ load balancer عادي بيوزع spans الـ trace الواحد على replicas مختلفة، فكل واحدة بتاخد قرار على نص trace، والنتيجة traces ناقصة في Tempo. ✅ حط loadbalancing exporter بـ routing_key: traceID في طبقة قبل الـ gateway، فـ replica واحدة تشوف الـ trace كله. الـ README بتاع الـ tail sampling بيقول ده صراحة.

❌ Sentry with no release or source maps 
Sentry.init({ dsn });
// الـ top frame: الملف checkout.min.cjs:1:507 والـ function c
// أنهي deploy؟ أنهي سطر؟ مش معروف
✅ Release plus uploaded source maps 
Sentry.init({ dsn, release: "orders-api@1.4.2", environment: "production" });
// sentry-cli sourcemaps inject ./dist
// sentry-cli sourcemaps upload --release=orders-api@1.4.2 ./dist
بالعامية

❌ من غير release مش هتعرف أنهي deploy بوّظها، ومن غير source maps الـ frame بيقول checkout.min.cjs:1:507 ومفيش حاجة تانية. ✅ حدد release وenvironment في Sentry.init، وارفع الـ source maps بنفس الـ release، ولازم الاسم يطابق بالظبط.

1. A filter processor 🟢 easy Add a filter to the stand-in collector that drops spans whose http.route is /metrics, so they don't get batched or stored. Verify the count goes down.

// الحل: filter processor بيشيل spans الـ metrics قبل ما تتجمع في batch
type Span = { name: string; attributes: Record<string, unknown> };

  return span.attributes["http.route"] !== "/metrics";

2. An atomic checkpoint 🟡 medium If the shipper crashes in the middle of writeFileSync, the checkpoint can be half-written. Make the write atomic.
لو الـ shipper وقع في نص writeFileSync، الـ checkpoint ممكن يتكتب نصه بس. خلّي الكتابة atomic.
Hint · تلميح Write a temp file on the same disk, then rename it over the target.

Solution · الحل 
// الحل: اكتب في ملف مؤقت وبعدين rename، عشان مفيش حد يقرا نص checkpoint
import { readFileSync, renameSync, writeFileSync, rmSync, existsSync } from "node:fs";

import path from "node:path";

const file = path.join(tmpdir(), `checkpoint-${process.pid}.offset`);

export function saveOffset(offset: number) {
  const temp = `${file}.tmp`;
  writeFileSync(temp, String(offset));
  // الـ rename على نفس الـ disk atomic: يا القديم يا الجديد، مفيش نص
  renameSync(temp, file);
}

3. Consistent sampling 🔴 hard Write keepTrace(traceId, percent) so that any replica makes the same decision for the same trace, and the kept rate matches percent. Watch for bias.
اكتب keepTrace(traceId, percent) بحيث أي replica تاخد نفس القرار لنفس الـ trace، ونسبة الاحتفاظ تطلع قد percent. خد بالك من الـ bias.
Solution · الحل 
// الحل: القرار من الـ trace ID نفسه، فأي replica بتاخد نفس القرار على نفس الـ trace
import { createHash, randomBytes } from "node:crypto";

export function keepTrace(traceId: string, percent: number, seed = "orders"): boolean {
  const hash = createHash("sha256").update(seed + traceId).digest();
  // نقسم على أكبر قيمة 32-bit: توزيع متساوي، و ⁦% 10000⁩ كان هيبقى فيه bias
  return hash.readUInt32BE(0) / 2 ** 32 < percent / 100;
}

const traces = Array.from({ length: 10_000 }, () => randomBytes(16).toString("hex"));
const replicaA = traces.map((t) => keepTrace(t, 25));
const replicaB = traces.map((t) => keepTrace(t, 25));
const kept = replicaA.filter(Boolean).length;
const agree = replicaA.every((v, i) => v === replicaB[i]);
console.log(`kept ${kept} of ${traces.length} (${(kept / 100).toFixed(1)}%) | replicas agree on every trace: ${agree}`);
kept 2545 of 10000 (25.4%) | replicas agree on every trace: true
نفس الـ hash لنفس الـ trace على أي replica، فالقرار واحد. ولو عملت % 10000 على 16-bit كان هيبقى فيه bias (طلع 26.6% في تجربة أولى بدل 25%)، فالقسمة على 2 أس 32 هي اللي بتدي توزيع متساوي، والناتج هنا 25.4%.

Cheat sheet · الخلاصة

  • Collector: receivers → processors (memory_limiter first, batch last) → exporters; one pipeline per signal; the HTTP exporter is otlp_http.
  • @opentelemetry/sdk-trace 3.x processors take one options object; the old positional form silently exports nothing.
  • Sampling location: SDK head (cheap), collector probabilistic_sampler (hash, consistent), gateway tail_sampling (needs one replica per trace).
  • Tail memory ≈ decision_wait × spans/s × bytes per span; measure yours.
  • Backends answer different questions: Prometheus numbers, Tempo/Jaeger traces, Loki labels then scan, Elasticsearch full text. Tempo 3 removed the ingester path.
  • Shippers are at-least-once: save the offset after the ack, dedupe downstream if needed.
  • Log cost is volume × price: drop noise and sample info before picking a vendor.
  • Correlation: exemplar on the bucket, trace by ID, logs by the same ID; exemplars need OpenMetrics and exemplar-storage.
  • Sentry: set release and environment, upload source maps with debug IDs, and control volume with beforeSend, ignoreErrors and sampleRate.
بالعامية
  • الـ Collector: receivers ← processors (memory_limiter الأول وbatch الآخر) ← exporters، و pipeline لكل signal، والـ HTTP exporter اسمه otlp_http.
  • الـ processors في @opentelemetry/sdk-trace 3 بتاخد options object واحد، والشكل القديم بيسكت ومبيصدرش حاجة.
  • مكان الـ sampling: head في الـ SDK (رخيص)، وprobabilistic_sampler في الـ collector (hash ومتسق)، وtail_sampling في gateway (لازم replica واحدة للـ trace).
  • memory الـ tail ≈ decision_wait × spans/s × حجم الـ span، واقيس بتاعك.
  • الـ backends بتجاوب أسئلة مختلفة: Prometheus أرقام، Tempo/Jaeger traces، Loki labels ثم scan، Elasticsearch نص كامل. و Tempo 3 شال مسار الـ ingester.
  • الـ shippers at-least-once: احفظ الـ offset بعد الـ ack، واعمل dedupe تحت لو محتاج.
  • تكلفة الـ logs = حجم × سعر: شيل الدوشة واعمل sampling للـ info قبل ما تختار vendor.
  • الـ correlation: exemplar على الـ bucket، trace بالـ ID، logs بنفس الـ ID، والـ exemplars محتاجة OpenMetrics وexemplar-storage.
  • Sentry: حط release وenvironment، وارفع source maps بـ debug IDs، وتحكم في الحجم بـ beforeSend وignoreErrors وsampleRate.
