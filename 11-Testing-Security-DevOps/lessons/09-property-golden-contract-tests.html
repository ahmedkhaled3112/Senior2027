Why this matters · ليه ده مهم

English

Example tests only check the cases you thought of, and the bugs that reach production live in the cases you didn't. Three techniques attack that gap from different sides: property tests generate the inputs, golden tests freeze a whole output so nothing changes unnoticed, and contract tests prove two services still agree without starting both. A senior engineer knows which of these catches which bug, because every one of them costs maintenance. This lesson plants real bugs and measures which technique finds each one.

بالعامية

الـ example tests بتتأكد من الحالات اللي إنت فكرت فيها بس، والـ bugs اللي بتوصل production عايشة في الحالات اللي مفكرتش فيها. فيه 3 techniques بيهاجموا الفجوة دي من 3 نواحي: الـ property tests بتولّد الـ inputs لوحدها، والـ golden tests بتجمّد الناتج كله عشان مفيش حاجة تتغير من غير ما تاخد بالك، والـ contract tests بتثبت إن اتنين services لسه متفقين من غير ما تشغّلهم مع بعض. السنيور عارف أنهي technique بيمسك أنهي bug، لأن كل واحد فيهم ليه تكلفة صيانة. في الدرس ده هنزرع bugs حقيقية ونقيس كل technique بيلاقي إيه.

Part 1 — Property-based testing 🔴 Advancedالجزء 1 — الـ property-based testing

English

A property is a statement that must hold for every valid input: "the installments always add up to the total". fast-check generates inputs from arbitraries such as fc.integer({ min, max }), runs your predicate 100 times by default, and fails as soon as one input breaks it. fc.assert(fc.property(...)) throws, which is what you use in a test. fc.check(...) returns the report instead, which is how the script below reads the seed.

The planted bug rounds each installment on its own, so the rounding error is multiplied by n. Three example tests with round numbers pass. The property fails on the very first generated input, because most totals don't divide evenly.

After a failure fast-check shrinks: it retries smaller versions of the failing input until none of them fail, then reports the smallest one it reached. Here that's [1, 2]: one piastre split in two gives Math.round(0.5) = 1 twice, so the parts sum to 2. Every failure prints a seed and a path. Passing both, with endOnFailure: true, replays exactly that case in one run, which turns a random failure into a normal debuggable one.

// ❌ النسخة الغلط: كل قسط بيتقرّب لوحده، فالتقريب بيتجمع على المجموع
export function splitInstallmentsBad(totalMinor: number, n: number): number[] {
  const each = Math.round(totalMinor / n);
  return Array.from({ length: n }, () => each);
}

// ✅ الصح: الباقي بيتوزع قرش قرش على أول الأقساط، فالمجموع مبيتغيرش أبدًا
export function splitInstallments(totalMinor: number, n: number): number[] {
  const base = Math.floor(totalMinor / n);
  const remainder = totalMinor - base * n;
  return Array.from({ length: n }, (_, i) => base + (i < remainder ? 1 : 0));
}

بالعامية

الـ property جملة لازم تبقى صح لأي input سليم: "مجموع الأقساط دايمًا بيساوي المبلغ". الـ fast-check بيولّد الـ inputs من حاجات اسمها arbitraries زي fc.integer({ min, max })، وبيشغّل الشرط بتاعك 100 مرة by default، وأول input يكسره بيوقف. fc.assert(fc.property(...)) بترمي exception، ودي اللي بتستخدمها جوه الـ test. وfc.check(...) بترجّع تقرير بدل الـ exception، وبيها السكريبت بيقرا الـ seed.

الـ bug المزروع بيقرّب كل قسط لوحده، فغلطة التقريب بتتضرب في n. 3 أمثلة بأرقام مدوّرة عدّوا عادي. أما الـ property فوقعت من أول input، لأن معظم المبالغ مش بتتقسم بالظبط.

بعد الفشل، الـ fast-check بيعمل shrinking: بيجرّب نسخ أصغر من الـ input الغلط لحد ما مفيش نسخة أصغر تفشل، ويقولك على أصغر واحد وصله. هنا طلع [1, 2]: قرش واحد على قسطين، وMath.round(0.5) = 1 مرتين، فالمجموع بقى 2. وكل فشل بيطبع seed وpath. لو بعتهم الاتنين مع endOnFailure: true، الحالة دي بالظبط بتتعاد في تشغيلة واحدة، وكده الفشل العشوائي بيبقى فشل عادي تقدر تعمله debug.

فين هستخدمه في شغلي؟ أي feature فيها تقسيط أو تقسيم فاتورة على شركاء أو خصم موزّع على سطور. الـ reconciliation مع payment gateway بيقع على قرش واحد، والمحاسب هيفتح ticket. property واحدة بتقول "المجموع ثابت" بتحميك من كل صور الـ rounding. ولو الـ test وقع في الـ CI، خد الـ seed والـ path من الـ log وأعد الحالة عندك على الجهاز.
Interview question "What does shrinking give you, and what does it not guarantee?" → A small input that's far easier to debug. It's a local minimum found by simplifying the failing case, so it isn't guaranteed to be the smallest failing input that exists.
"الـ shrinking بيديك إيه ومش بيضمن إيه؟" ← بيديك input صغير أسهل بكتير في الـ debug. بس هو أصغر حاجة وصلها وهو بيبسّط المثال اللي فشل، فمش مضمون إنه أصغر input فاشل موجود في الدنيا.

Part 2 — Choosing properties 🔴 Advancedالجزء 2 — إزاي تختار الـ properties

English

The hard part is deciding what to assert, since you can't recompute the answer without copying the code. Five patterns cover most business logic:

  • Round trip: decode(encode(x)) equals x. For serializers, money strings, CSV.
  • Idempotent: f(f(x)) equals f(x). For normalizers and anything a retry may run twice.
  • Invariant: something always true of the output, such as a cart total that's never negative and never above the sum of its lines.
  • Oracle: compare with a slow, obviously correct implementation. Good for replacing a linear scan with a binary search.
  • Metamorphic: you don't know the answer, but you know how two answers relate. A heavier parcel never costs less to ship.

The output below shows each one catching a planted bug. Two details are worth reading closely. The money bug is reported at 14243327 although 115 fails too, so shrinking stopped at a local minimum. And the CSV round trip reports one bug at a time: first an empty row lost to filter(Boolean), then a quote, and only when the generator is limited to letters, spaces and commas does it report the bug you came for, the comma inside quotes. Fix, re-run, and the next bug appears.

// ❌ بيعدّي من float: الـ 1.15 لما تضربها في 100 بتطلع 114.99999999999999
export function parseMoneyBad(text: string): number {
  return Math.trunc(Number.parseFloat(text) * 100);
}

// ✅ بيتعامل مع النص نفسه من غير ما يلمس float خالص
export function parseMoney(text: string): number {
  const match = /^(\d+)\.(\d{2})$/.exec(text);
  if (!match) throw new Error(`bad money: ${text}`);
  return Number(match[1]) * 100 + Number(match[2]);
}

export function formatMoney(minor: number): string {
  const pounds = Math.floor(minor / 100);
  const cents = String(minor % 100).padStart(2, "0");
  return `${pounds}.${cents}`;
}
// ❌ بيضيف كود الدولة من غير ما يتأكد إنه اتضاف قبل كده
export function normalizePhoneBad(raw: string): string {
  const digits = raw.replace(/[\s-]/g, "");
  return `+20${digits.replace(/^0/, "")}`;
}

// ✅ بيشيل أي شكل قديم لكود الدولة الأول، فالتطبيق التاني ميغيرش حاجة

export interface Tier { fromMinor: number; percent: number }

export const TIERS: readonly Tier[] = [
  { fromMinor: 0, percent: 0 },
  { fromMinor: 100_000, percent: 5 },
  { fromMinor: 500_000, percent: 10 },
  { fromMinor: 2_000_000, percent: 15 },
];

// ❌ الـ binary search ده بيقف قبل الـ tier الصح لما القيمة على الحد بالظبط
export function tierPercentFastBad(amount: number, tiers: readonly Tier[] = TIERS): number {
  let lo = 0;
  let hi = tiers.length - 1;
  while (lo < hi) {
    const mid = Math.ceil((lo + hi) / 2);
    if (tiers[mid]!.fromMinor < amount) lo = mid;
    else hi = mid - 1;
  }
  return tiers[lo]!.percent;
}

// ✅ نفس الـ binary search بالشرط الصح
export function tierPercentFast(amount: number, tiers: readonly Tier[] = TIERS): number {
  let lo = 0;
  let hi = tiers.length - 1;
  while (lo < hi) {
    const mid = Math.ceil((lo + hi) / 2);
    if (tiers[mid]!.fromMinor <= amount) lo = mid;
    else hi = mid - 1;
  }
  return tiers[lo]!.percent;
}

// الـ oracle: نسخة غبية بس واضحة، بتمشي على كل الـ tiers
export function tierPercentNaive(amount: number, tiers: readonly Tier[] = TIERS): number {
  return tiers.filter((t) => t.fromMinor <= amount).at(-1)!.percent;
}
export interface Line { sku: string; qty: number; unitMinor: number }

export const lineTotal = (l: Line) => l.qty * l.unitMinor;

// ❌ الـ coupon بيتخصم من غير سقف، فالإجمالي ممكن يبقى بالسالب
export function cartTotalBad(lines: Line[], couponMinor: number): number {
  return lines.reduce((sum, l) => sum + lineTotal(l), 0) - couponMinor;
}

// ✅ الخصم مش ممكن يعدّي قيمة الـ cart
export function cartTotal(lines: Line[], couponMinor: number): number {
  const subtotal = lines.reduce((sum, l) => sum + lineTotal(l), 0);
  return subtotal - Math.min(subtotal, couponMinor);
}

// ❌ فيه خصم بيدخل عند الـ 5 كيلو، فالطرد الأتقل ممكن يطلع أرخص

}

// ✅ كل كيلو زيادة بيزوّد السعر أو بيثبّته، عمره ما بيقلّله
export function shippingForWeight(grams: number): number {
  return 5_000 + Math.ceil(grams / 1_000) * 500;

export type Row = string[];

// ❌ الـ split بيقطع جوه الفواصل اللي جوه الـ quotes
export function parseCsvBad(text: string): Row[] {
  return text.split("\n").filter(Boolean).map((line) => line.split(","));
}

// ❌ نفس الغلطة من غير الـ filter، عشان نشوف الـ bug اللي بعده
export function parseCsvNoFilterBad(text: string): Row[] {
  return text.split("\n").map((line) => line.split(","));
}

// الـ serializer: بيحط quotes لو الخانة فيها فاصلة أو quote أو سطر جديد
export function toCsv(rows: Row[]): string {
  const cell = (c: string) => (/[",\r\n]/.test(c) ? `"${c.replaceAll('"', '""')}"` : c);
  return rows.map((r) => r.map(cell).join(",")).join("\n");
}

// ✅ الـ state machine بيمشي حرف حرف، فالـ quotes والفواصل بيتفهموا صح
export function parseCsv(text: string): Row[] {
  const rows: Row[] = [];
  let row: Row = [];
  let cell = "";
  let quoted = false;
  for (let i = 0; i < text.length; i++) {
    const ch = text[i]!;
    if (quoted) {
      if (ch !== '"') cell += ch;
      else if (text[i + 1] === '"') { cell += '"'; i++; }
      else quoted = false;
    } else if (ch === '"') {
      quoted = true;
    } else if (ch === ",") {
      row.push(cell);
      cell = "";
    } else if (ch === "\n") {
      row.push(cell);
      rows.push(row);
      row = [];
      cell = "";
    } else {
      cell += ch;
    }
  }
  row.push(cell);
  rows.push(row);
  return rows;
}

// مساعد: بيشغّل الـ property على النسختين ويطبع أصغر مثال بيكسر الغلط
function compare(name: string, bad: fc.IProperty<any>, good: fc.IProperty<any>) {
  const b = fc.check(bad, { numRuns: 2_000 });
  const g = fc.check(good, { numRuns: 2_000 });
  const badText = b.failed ? `FAILED after ${b.numRuns} runs, smallest ${JSON.stringify(b.counterexample)}` : "passed";
  const goodText = g.failed ? `FAILED ${JSON.stringify(g.counterexample)}` : `passed ${g.numRuns} runs`;
  console.log(`${name}\n  bad : ${badText}\n  good: ${goodText}`);
}

  • Round trip (ذهاب وعودة): decode(encode(x)) لازم يساوي x. للـ serializers وأرقام الفلوس والـ CSV.
  • Idempotent: f(f(x)) لازم يساوي f(x). للـ normalizers وأي حاجة ممكن retry يشغّلها مرتين.
  • Invariant: حاجة دايمًا صح في الناتج، زي إجمالي cart عمره ما يبقى سالب وعمره ما يعدّي مجموع سطوره.
  • Oracle: قارن بنسخة بطيئة بس واضح إنها صح. ممتاز لما تبدّل linear scan بـ binary search.
  • Metamorphic: مش عارف الإجابة، بس عارف العلاقة بين إجابتين. الطرد الأتقل عمره ما يتشحن بسعر أقل.

الناتج فوق بيوريك كل نمط ماسك bug مزروع. فيه تفصيلتين مهمين. bug الفلوس اتبلّغ عنده عند 14243327 مع إن 115 بتفشل برضه، يعني الـ shrinking وقف عند أصغر حاجة وصلها مش أصغر حاجة موجودة. وround trip الـ CSV بيقولك على bug واحد كل مرة: الأول صف فاضي ضاع بسبب filter(Boolean)، بعدين quote، ولما قصرنا الـ generator على حروف ومسافات وفواصل بس، ظهر الـ bug اللي جينا عشانه: الفاصلة اللي جوه الـ quotes. تصلّح، تشغّل تاني، يظهر اللي بعده.

Part 3 — Stateful model tests 🔴 Advancedالجزء 3 — الـ stateful model tests

English

Some bugs need a sequence of operations, and no single input reveals them. fc.commands generates sequences of command objects. Each command runs against the real object and a deliberately simple model, then compares the two. check says whether a command is allowed in the current state, and fc.modelRun drives the sequence.

The planted bug keeps an index of array positions and doesn't update it when splice shifts the lines. fast-check found it within 3 runs and shrank it to 4 steps: add(MUG,1), add(TSHIRT,1), remove(MUG), remove(TSHIRT). The last remove uses a stale index and silently does nothing. Example tests rarely contain that order.

Run count is a budget. In the measurement below, 10 runs caught the bug with 12 of 20 seeds, and 100 runs caught it with all 20, so 10 is too few even for a bug this easy to reach. A practical split: on every PR use a fixed seed, so a red build is reproducible and caused by the code change. At night use a random seed and more runs to explore new inputs, and log the seed. @fast-check/vitest gives you test.prop so properties read like normal Vitest tests.

Part 4 — Golden tests 🔴 Advancedالجزء 4 — الـ golden tests

English

A golden (approval) test saves a whole approved output in the repo and fails on any difference. It suits outputs too big to assert field by field: reports, invoices, emails, generated code. Three rules make it useful. Fields that change between runs must be injected or normalized, or the test always fails. Updating the file must be a deliberate act: vitest -u or UPDATE_GOLDEN=1, never in CI. And a human must read the diff, because after an update the test passes by definition.

For text, Vitest's toMatchFileSnapshot does this. With CI=1 a missing file is a failure rather than something written quietly, as the output below shows. Change toFixed(2) to String and the diff shows exactly which amounts lost their zeros.

PDFs add a problem. The same invoice rendered twice differed in 59 to 65 of 1395 bytes across runs, because pdfkit stamps the creation date and derives the file ID from it. With info.CreationDate fixed, the bytes are identical. That still leaves the question of what to compare. Bytes catch everything, including harmless layout moves. Extracted text ignores layout, but it passes when the total is drawn in white. So keep both, and commit the extracted text beside the PDF: git diff --stat showed Bin 1395 -> 1395 bytes for a changed total, same size and nothing a reviewer can judge, while the .txt shows the changed line.

  const task = getDocument({ data: new Uint8Array(bytes), verbosity: 0 });

  const lines: string[] = [];
  for (let p = 1; p <= doc.numPages; p++) {

    const content = await page.getTextContent();
    for (const item of content.items) if ("str" in item && item.str.trim()) lines.push(item.str);
  }
  await task.destroy();
  return lines.join("\n") + "\n";
}

English

Writing and verifying a Pact is covered in section 09, lesson 32, parts 5 and 6, which run it for real. This part covers the pipeline around it, which is where teams usually go wrong.

  • Who publishes: the consumer's CI, on every commit, tagged with the git SHA and branch.
  • Who verifies: the provider's CI, in two situations: on its own commits, against the pacts of the consumers in each environment, and when a webhook announces a contract that needs verifying (contract_requiring_verification_published, an event name read from the Pact Broker source).

  • After deploying: record-deployment tells the Broker what's in the environment. Skip it and every later answer is based on a stale picture.

// ده مجرد stand-in للـ Pact Broker: بيحسب الـ matrix بس، من غير HTTP ولا webhooks ولا pending pacts
export type Verdict = "yes" | "no" | "unknown";

interface Pact { consumer: string; consumerVersion: string; provider: string; content: string }
interface Result { provider: string; providerVersion: string; content: string; success: boolean }

export class MatrixStandIn {
  #pacts: Pact[] = [];
  #results: Result[] = [];
  #deployed = new Map<string, string>();

  publish(consumer: string, consumerVersion: string, provider: string, content: string) {
    this.#pacts.push({ consumer, consumerVersion, provider, content });
  }

  recordVerification(provider: string, providerVersion: string, content: string, success: boolean) {
    this.#results.push({ provider, providerVersion, content, success });
  }

  recordDeployment(app: string, version: string, env: string) {
    this.#deployed.set(`${env}/${app}`, version);
  }

  #check(content: string, provider: string, providerVersion: string): Verdict {
    const result = this.#results.findLast((r) => r.provider === provider && r.providerVersion === providerVersion && r.content === content);
    if (!result) return "unknown";
    return result.success ? "yes" : "no";
  }

  // السؤال: لو نشرت الـ version ده على الـ env ده، هيشتغل مع اللي موجود هناك؟
  canIDeploy(app: string, version: string, env: string): { verdict: Verdict; reason: string } {
    const reasons: { verdict: Verdict; reason: string }[] = [];
    for (const p of this.#pacts) {
      if (p.consumer === app && p.consumerVersion === version) {
        const live = this.#deployed.get(`${env}/${p.provider}`);
        if (live) reasons.push({ verdict: this.#check(p.content, p.provider, live), reason: `${app} ${version} -> ${p.provider} ${live}` });
      }
      if (p.provider === app && this.#deployed.get(`${env}/${p.consumer}`) === p.consumerVersion) {
        reasons.push({ verdict: this.#check(p.content, app, version), reason: `${p.consumer} ${p.consumerVersion} -> ${app} ${version}` });
      }
    }
    return (
      reasons.find((r) => r.verdict === "no") ??
      reasons.find((r) => r.verdict === "unknown") ?? { verdict: "yes", reason: `${reasons.length} integration(s) verified` }
    );
  }
}

  • Example: الأفضل لتوثيق الحالات المعروفة والقواعد بقيم مظبوطة. أعمى عن أي حاجة مفكرتش فيها. التكلفة قليلة.
  • Property: الأفضل للـ rounding والـ parsers والتسلسلات والـ invariants. أعمى عن القيم التجارية المظبوطة اللي مش متعبّر عنها كقاعدة. التكلفة متوسطة: الصعب هو إيجاد الـ property.
  • Golden: الأفضل للتغييرات اللي بتعدّي من غير ملاحظة في النواتج الكبيرة. أعمى عن الـ inputs اللي بره العينة، وعن السلوك الغلط اللي اتعمد قبل كده. سهل في الكتابة، بس لازم مراجعة diff.
  • Contract: الأفضل لما اتنين services يبعدوا عن بعض. أعمى عن المنطق الداخلي ونتيجة الـ business عبر الـ services. التكلفة متوسطة: الـ pipeline والـ Broker.
  • Mutation: الأفضل إنه يوريك الـ tests مش بتبص فين. أعمى عن bugs في كود مش موجود عندك. التكلفة عالية في الـ CPU، فشغّله بالليل على الموديولات المهمة.
بالعامية

هنا كل bug مزروع اتشغّل قدام كل technique. كل bug هو الموديول الصح بدالة واحدة متبدلة. example هي الـ suite اللي المطور بيكتبها الأول. property فيها قواعد عامة بس. golden بيقارن عينة واقعية واحدة. contract بيتأكد من الـ fields اللي الـ consumer محتاجها من الـ API response (فحص محلي بدل الـ Pact verification). عمود الـ mutation معناه مختلف: Stryker 10 الحقيقي اتشغل على الكود الصح بالـ example suite، و"gap (n)" بيعد الـ mutants اللي عاشوا جوه الدالة اللي فيها الـ bug. الـ mutation testing بيقيّم الـ tests بتاعتك، ومبيشوفش الـ bug أصلًا.

الـ matrix بتقول: مفيش technique بيمسك كل حاجة. الـ golden مسك bug الـ rounding بس لأن العينة بتاعته بالصدفة فيها 100000 على 3. والـ mutation لوحده هو اللي شاور على حد الشحن المجاني (>= لما اتغيرت لـ > عاشت)، لأن الـ property بتقول بس إن الطلب الأكبر عمره ما يدفع أكتر، وده بيفضل صح عند الحد. والـ cart طلع "no gap": الـ Stryker بيغيّر في الكود اللي عندك، ونسخة الـ Map الصح مفيهاش index يغلط، فمش هيعرف يتوقع bug تبع تصميم تاني.

فين هستخدمه في شغلي؟ لما تعمل review لخطة testing لـ feature جديدة: حسابات الفلوس والـ parsing بـ properties، والفاتورة الـ PDF بـ golden، والتكامل مع service تاني بـ contract، والقواعد ذات الأرقام المحددة (الشحن المجاني من 500 جنيه) بـ example على الحد بالظبط. وشغّل mutation بالليل على موديول الفلوس عشان يوريك الحدود اللي مش متغطية. الغلطة الشائعة إن الفريق يختار أداة واحدة ويطبقها على كل حاجة.

How?" → The property described a general trend, which still holds when the boundary is off by one. Exact business numbers need example tests on the boundary, and mutation testing exposes the missing ones by showing that a >= to > mutant survives.

Common mistakes · غلطات شائعة

❌ The property repeats the code 
fc.property(total, count, (t, n) => {
  // نفس المعادلة اللي في الكود، فلو غلطانة الاتنين هيغلطوا مع بعض
  expect(split(t, n)[0]).toBe(Math.round(t / n));
});
✅ The property states an outcome 
fc.property(total, count, (t, n) => {
  // الناتج المطلوب من غير ما نعرف إزاي اتحسب
  expect(sum(split(t, n))).toBe(t);
});
بالعامية

❌ لو الـ property بتعيد نفس معادلة الكود، الاتنين هيقعوا في نفس الـ bug والـ test هيفضل أخضر. ✅ قول النتيجة المطلوبة: المجموع يساوي المبلغ، من غير ما تقول اتحسب إزاي.

❌ Updating goldens in CI 
# الـ CI بيعتمد أي تغيير لوحده، فالـ test مبيفشلش أبدًا
vitest run -u
✅ Update locally, review the diff 
# في الـ CI: مقارنة بس، والملف الناقص بيفشل
CI=1 vitest run
# على جهازك: تحديث مقصود وبعده قراءة الـ diff
vitest run -u && git diff test/__golden__
بالعامية

❌ الـ -u في الـ CI معناها إن أي تغيير بيتعمد أوتوماتيك، يبقى الـ test ملوش لازمة. ✅ في الـ CI مقارنة بس، والتحديث على جهازك وبعده تقرا الـ diff وتشرحه في الـ PR.

❌ Volatile fields in the golden 
// الوقت بيتغير كل تشغيلة، فالـ test بيقع دايمًا
const html = renderHtml(report);
await expect(html).toMatchFileSnapshot(file);
✅ Normalize, or inject the clock 
// بنبدّل المتغير بعلامة ثابتة قبل المقارنة
const html = normalizeVolatile(renderHtml(report));
await expect(html).toMatchFileSnapshot(file);
بالعامية

❌ لو الـ timestamp أو الـ UUID داخلين في الملف، الـ test هيقع كل مرة، والفريق هيتعود يعمل -u من غير ما يبص. ✅ اعمل normalize لكل حقل متغير، أو الأحسن احقن الـ clock في الكود نفسه.

❌ A model built like the real code 
// الـ model بنفس الـ array والـ index، فالـ bug هيتكرر فيه
type Model = { lines: Line[]; index: Map<string, number> };
✅ The simplest thing that can be true 
// الـ Map البسيط ده هو تعريف الحقيقة
type Model = Map<string, number>;
بالعامية

❌ الـ model لو اتكتب بنفس تصميم الكود، هيغلط نفس الغلطة والمقارنة هتعدّي. ✅ خلّيه أبسط شكل ممكن، حتى لو بطيء، عشان يبقى مرجع مش نسخة تانية.

Solution · الحل 
import fc from "fast-check";
import assert from "node:assert/strict";
import { MapCart, type Cart } from "../src/cart.ts";

type Model = Map<string, number>;

const same = (m: Model, c: Cart) =>
  assert.deepEqual(
    c.lines().toSorted((a, b) => a.sku.localeCompare(b.sku)),
    [...m].map(([sku, qty]) => ({ sku, qty })).toSorted((a, b) => a.sku.localeCompare(b.sku)),
  );

class Add implements fc.Command<Model, Cart> {
  sku: string;
  constructor(sku: string) { this.sku = sku; }
  check = () => true;
  run(m: Model, c: Cart) { c.add(this.sku, 1); m.set(this.sku, (m.get(this.sku) ?? 0) + 1); same(m, c); }
  toString = () => `add(${this.sku})`;
}

// الأمر الجديد: بيفضّي الـ cart والـ model مع بعض
class Clear implements fc.Command<Model, Cart & { clear(): void }> {
  check = (m: Readonly<Model>) => m.size > 0;
  run(m: Model, c: Cart & { clear(): void }) { c.clear(); m.clear(); same(m, c); }
  toString = () => "clear";
}

class ClearableCart extends MapCart {
  clear() { for (const line of this.lines()) this.remove(line.sku); }
}

const sku = fc.constantFrom("MUG", "CAP");
fc.assert(
  fc.property(fc.commands([sku.map((s) => new Add(s)), fc.constant(new Clear())], { maxCommands: 30 }), (cmds) => {
    fc.modelRun(() => ({ model: new Map(), real: new ClearableCart() }), cmds);
  }),
  { numRuns: 2_000 },
);
console.log("clear command: 2000 sequences passed");
الـ check بتمنع الأمر لما الـ model يكون فاضي، وrun بتفضّي الاتنين وتقارنهم. لما شغّلناه طبع clear command: 2000 sequences passed.

Cheat sheet · الخلاصة

  • Property = a rule for all valid inputs. fc.assert in tests, fc.check to read the report.
  • A failure prints seed and path; replay with both plus endOnFailure: true.
  • Shrinking gives a small case, not the guaranteed smallest one.
  • Five patterns: round trip, idempotent, invariant, oracle, metamorphic.
  • fc.commands plus a simple model finds bugs that need a sequence.
  • PRs: fixed seed. Nightly: random seed, more runs, logged seed.
  • Golden: normalize or inject volatile fields, update on purpose, read the diff.
  • PDF: fix CreationDate; keep bytes and extracted text; commit the text for reviewers.
  • Contracts: consumer publishes, provider verifies, can-i-deploy blocks on no or unknown, then record-deployment.
  • Keep a few E2E tests for the money paths: contracts don't prove the business outcome.
  • Mutation grades tests and can't see bugs from a different design. Exact thresholds need example tests on the boundary.
بالعامية
  • الـ property قاعدة لكل الـ inputs السليمة. fc.assert جوه الـ tests، وfc.check لو عايز تقرا التقرير.
  • الفشل بيطبع seed وpath، وتعيد الحالة بيهم مع endOnFailure: true.
  • الـ shrinking بيديك حالة صغيرة، مش أصغر حالة مضمونة.
  • 5 أنماط: round trip و idempotent و invariant و oracle و metamorphic.
  • fc.commands مع model بسيط بيلاقي الـ bugs اللي محتاجة تسلسل.
  • في الـ PR: seed ثابت. بالليل: seed عشوائي وتشغيلات أكتر، واطبع الـ seed.
  • الـ golden: اعمل normalize أو inject للحقول المتغيرة، وحدّث بقرار، واقرا الـ diff.
  • الـ PDF: ثبّت CreationDate، واحتفظ بالـ bytes والنص المستخرج، واعمل commit للنص عشان الـ reviewer.
  • الـ contracts: الـ consumer بينشر، والـ provider بيتحقق، وcan-i-deploy بيوقف عند no أو unknown، وبعدين record-deployment.
  • سيب شوية E2E لمسارات الفلوس: الـ contracts مبتثبتش نتيجة الـ business.
  • الـ mutation بيقيّم الـ tests، ومبيشوفش bugs من تصميم تاني. والأرقام المظبوطة محتاجة example tests على الحد.
