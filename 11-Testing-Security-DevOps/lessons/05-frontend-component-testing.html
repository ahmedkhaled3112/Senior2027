Why this matters · ليه ده مهم

English

A frontend test suite earns trust only if a refactor leaves it green and a real bug turns it red. Most suites fail on one side: tests tied to CSS classes break on every redesign, and a 365-line snapshot gets approved with -u without anyone reading it. This lesson is about the choices that decide which side you land on: how you find elements, how you wire providers, what you snapshot, what pixels you compare, and what axe can and cannot tell you.

React lesson 17 already teaches the philosophy, user-event, renderHook basics and MSW. Here we spend the time on what a senior reviews: failures you can read, helpers that stop whole classes of mistakes, and the honest cost of each tool. Every number below comes from a real run on this Windows machine, so read timings as approximate (≈) and trust the counts and ratios.

الـ frontend test suite بتكسب الثقة بشرط واحد: الـ refactor يعدّي وهي خضرا، والـ bug الحقيقي يقلبها حمرا. أغلب الـ suites بتفشل في ناحية من الاتنين: tests مربوطة بـ CSS classes بتتكسر مع كل redesign، و snapshot طوله 365 سطر بيتعمله -u من غير ما حد يقراه. الدرس ده عن القرارات اللي بتحدد إنت في أنهي ناحية: إزاي بتلاقي الـ elements، إزاي بتوصّل الـ providers، بتعمل snapshot لإيه، بتقارن pixels إيه، و axe يقدر يقولك إيه وميقدرش يقولك إيه.

Part 1 — Queries that survive refactors 🟡 Intermediateالجزء 1 — queries بتعيش بعد الـ refactor

English

A real admin screen has a table with a Refund button in every row, so "the Refund button" is ambiguous. within(element) returns the same queries scoped to one subtree: first find the row of order 1042, then find the button inside it. The row is found through its accessible name too, which in a table comes from its cell content, so this test also fails if the row stops showing the order number.

The accessible name is what a screen reader announces, computed by the W3C accname algorithm. Priority, highest first: aria-labelledby, aria-label, native labelling (<label>, alt), the element's content for roles that allow it (buttons, links), then title as a last resort. Content under aria-hidden="true" doesn't count. getByRole("button", { name }) matches against that computed name: a string must match the whole name, a regex can match part of it. So a passing role query is also a small accessibility check that a test ID can never give you.

getBy* throws immediately, queryBy* returns null (use it only to assert absence), and findBy* returns a promise that retries for up to 1000 ms by default (polling every 50 ms and on DOM mutations). findBy is just getBy inside waitFor. Use findBy for "an element will appear" and waitFor for assertions that aren't queries, like a mock's call count or a hook's state. Never put an action inside waitFor: its callback is retried, so a click in there happens again on every retry.

بالعامية

في شاشة admin حقيقية عندك جدول وكل صف فيه زرار Refund، فكلمة "زرار الـ Refund" ملخبطة. within(element) بترجّعلك نفس الـ queries بس محصورة جوه عنصر واحد: الأول هات صف الأوردر 1042، وبعدين دوّر على الزرار جواه. الصف نفسه بنلاقيه بالـ accessible name، واللي في الجدول بييجي من محتوى الخلايا، فالـ test ده كمان هيفشل لو الصف بطّل يعرض رقم الأوردر.

الـ accessible name هو اللي الـ screen reader بيقوله، وبيتحسب بـ algorithm من W3C اسمه accname. الأولوية من الأعلى: aria-labelledby، بعده aria-label، بعده الـ labelling الـ native (<label> و alt)، بعده محتوى العنصر للـ roles اللي بتسمح بكده (الزراير واللينكات)، وآخر حاجة title. أي محتوى تحت aria-hidden="true" مبيتحسبش. getByRole("button", { name }) بيطابق على الاسم المحسوب ده: الـ string لازم يطابق الاسم كله، والـ regex ممكن يطابق جزء منه. يعني query بالـ role لو عدّت فهي كمان فحص accessibility صغير، وده اللي الـ test ID عمره ما هيديهولك.

getBy* بيرمي error على طول، queryBy* بيرجّع null (استخدمه بس عشان تتأكد إن حاجة مش موجودة)، و findBy* بيرجّع promise بتحاول لحد 1000ms افتراضيًا (بتجرب كل 50ms ومع أي تغيير في الـ DOM). findBy هو ببساطة getBy جوه waitFor. استخدم findBy لـ "عنصر هيظهر"، و waitFor للـ assertions اللي مش queries زي عدد مرات نداء mock أو state بتاع hook. وأوعى تحط action جوه waitFor: الـ callback بيتعاد، فالـ click بيتكرر مع كل retry، وده اللي طلّع الـ 4 refunds فوق.

فين هستخدمه في شغلي؟ شاشة الـ orders في الـ admin panel عندك: "زرار الـ Refund في صف الأوردر اللي العميل بيشتكي منه". الـ reviewer يشوف within(row) ويفهم الـ test بيتكلم عن إيه، وأي sort أو pagination ميكسروش. ولما الـ designer يغيّر الزرار لـ icon والـ test يقع برسالة Name ""، إنت عرفت فورًا إن الـ redesign كسر الـ accessibility، وهتصلح الـ component قبل ما يوصل للـ production.
Interview question "Why prefer getByRole over data-testid?" → A role query fails when the element stops being reachable the way users reach it: wrong role, no accessible name. A test ID survives those bugs and only breaks when someone deletes the attribute. Keep test IDs for things with no semantic role, like a chart canvas.
"ليه تفضّل getByRole على data-testid؟" ← الـ role query بيفشل لما العنصر يبطّل يتوصل زي ما المستخدم بيوصله: role غلط أو من غير accessible name. الـ test ID بيعدّي مع الـ bugs دي وبيتكسر بس لما حد يمسح الـ attribute. سيب الـ test IDs للحاجات اللي ملهاش role زي canvas بتاع chart.

Part 2 — Hooks and provider wrappers 🟡 Intermediateالجزء 2 — الـ hooks والـ provider wrappers

English

React lesson 17, part 3 covers renderHook itself. In a real app almost no hook runs alone: useCartTotals needs a QueryClientProvider, a page needs auth and theme too. If each test wires that by hand you get about 15 lines of ceremony per test, and the failure mode is worse than the boilerplate: the one test that forgets retry: false silently takes the production retry path.

TanStack Query retries a failed query 3 times by default with exponential backoff of 1 s, 2 s and 4 s. The test that forgot took ≈7,067 ms and made 4 fetch calls; with the shared helper the same error path took ≈75 ms, about 94 times faster. Worse, with RTL's default 1000 ms waitFor timeout, the forgetful test simply fails with expected false to be true, a message that says nothing about retries.

The fix is one test-utils.tsx that exports renderWithProviders and renderHookWithProviders. It builds a new QueryClient per test, because the cache is state: with one client per file, the second test read the first test's cache and got expected 12000 to be 500. The helper also returns user from userEvent.setup(), so nobody forgets that either. Options let a test change only what it cares about, like { authUser: { role: "admin" } }.

import { useQuery } from "@tanstack/react-query";

export type CartLine = { sku: string; qty: number; unitCents: number };
export type Cart = { id: string; lines: CartLine[]; discountCents: number };

async function fetchCart(cartId: string): Promise<Cart> {
  const res = await fetch(`/api/carts/${cartId}`);
  if (!res.ok) throw new Error(`cart ${cartId}: HTTP ${res.status}`);
  return (await res.json()) as Cart;
}

export function useCartTotals(cartId: string) {
  const query = useQuery({ queryKey: ["cart", cartId], queryFn: () => fetchCart(cartId) });
  const lines = query.data?.lines ?? [];
  const subtotalCents = lines.reduce((sum, l) => sum + l.qty * l.unitCents, 0);
  const totalCents = Math.max(0, subtotalCents - (query.data?.discountCents ?? 0));
  return { isLoading: query.isLoading, isError: query.isError, subtotalCents, totalCents };
}
import { createContext, useContext, type PropsWithChildren, type ReactElement } from "react";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { render, renderHook, type RenderOptions } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

export type AuthUser = { id: string; role: "customer" | "admin" };
export const AuthContext = createContext<AuthUser | null>(null);
export const ThemeContext = createContext<"light" | "dark">("light");
export const useAuth = () => useContext(AuthContext);

type ProviderOptions = {
  authUser?: AuthUser | null;
  theme?: "light" | "dark";
  queryClient?: QueryClient;
};

// مهم: QueryClient جديد لكل test، و retry مقفول عشان الـ error path يخلص فورًا
export function createTestQueryClient(): QueryClient {
  return new QueryClient({
    defaultOptions: { queries: { retry: false }, mutations: { retry: false } },
  });
}

function makeWrapper({ authUser = null, theme = "light", queryClient }: ProviderOptions & { queryClient: QueryClient }) {
  return function Wrapper({ children }: PropsWithChildren) {
    return (
      <QueryClientProvider client={queryClient}>
        <AuthContext value={authUser}>
          <ThemeContext value={theme}>{children}</ThemeContext>
        </AuthContext>
      </QueryClientProvider>
    );
  };
}

export function renderWithProviders(
  ui: ReactElement,
  { authUser, theme, queryClient = createTestQueryClient(), ...options }: ProviderOptions & Omit<RenderOptions, "wrapper"> = {},
) {
  const wrapper = makeWrapper({ authUser, theme, queryClient });
  return { ...render(ui, { wrapper, ...options }), queryClient, user: userEvent.setup() };
}

export function renderHookWithProviders<Result>(
  callback: () => Result,
  { authUser, theme, queryClient = createTestQueryClient() }: ProviderOptions = {},
) {
  const wrapper = makeWrapper({ authUser, theme, queryClient });
  return { ...renderHook(callback, { wrapper }), queryClient };
}

English

A story renders one state of a component in a real browser. A play function is a script attached to a story that runs after render: it types, clicks and asserts, using the same within and userEvent API as RTL, imported from storybook/test (Storybook 10 is ESM only and that one package replaced the older @storybook/test). React lesson 17, part 5 introduced Storybook; here we run the play functions and read what a failure looks like.

The official runners are @storybook/addon-vitest (browser mode) and @storybook/test-runner. Not run here: Vitest's browser mode did not start on this machine (iframe not ready within 60,000 ms; the apostrophe in the folder path is the suspect). As a labelled stand-in, run-stories.mjs builds the static Storybook and opens each story in installed Chrome through Playwright, then listens on Storybook's event channel for storyRendered or playFunctionThrewException. It shows the mechanism, but it doesn't give you the coverage or reporting of the official runners.

When does a story beat an RTL test? When the component's value is visual or needs a real browser: focus handling, layout, CSS behaviour, a design-system component with many states. It also doubles as documentation and as a visual-regression baseline. RTL wins for logic and speed, because it needs no browser. Part 4 — Visual regression 🟡 Intermediateالجزء 4 — الـ visual regression

English

Visual regression compares a screenshot against an approved baseline, pixel by pixel. Chromatic and Percy are the hosted options; they render in their own browsers, show diffs in a UI and handle approvals. Not run here: both need an account. Locally, Playwright's toHaveScreenshot does the same job and everything below is a real run on installed Chrome.

The first run has no baseline, so it writes one and fails on purpose (A snapshot doesn't exist at ..., writing actual): a baseline nobody looked at must not pass. The file name includes the platform (invoice-win32.png), because the same page renders differently on Windows and Linux. So baselines committed from a Windows laptop can't pass on a Linux CI runner: generate them in CI, in the same image as the tests (for example mcr.microsoft.com/playwright:v1.65.0). Not run here: Docker and Linux.

Two numbers control sensitivity, and people confuse them. threshold (default 0.2, YIQ) decides whether a single pixel counts as different, so a slight colour tweak from #15803d to #16a34a passed with zero tolerance. maxDiffPixelRatio decides how many different pixels are acceptable: a total line turned red changed 309 pixels (ratio 0.01), failing at 0 and passing at 0.02. Dynamic content must be masked (mask: [locator]), and animations are disabled by default in toHaveScreenshot, which is why turning them on times out with element is not stable.

The price is flake. Pixels depend on fonts, antialiasing and GPU, so a change in the environment shows up as a failure. As a stand-in for an OS difference, rendering the invoice twice with only --disable-lcd-text changed 2.76% of its pixels, well above any sensible tolerance. Keep the suite small: a few pages, a stable environment, and a human approving every baseline change.

Part 5 — Snapshots with care 🟡 Intermediateالجزء 5 — الـ snapshots بحذر

English

A snapshot test records output and fails when it changes. It never says the output is right, only that it's different, and the person who decides is whoever runs -u. On a whole component, that person is outnumbered: the snapshot of OrderDetails with 11 line items is 365 lines. Renaming one CSS class, a one-word change, produced 120 changed lines of diff.

The dangerous part comes next. We changed the class and, in the same commit, introduced a real bug that adds $10 to the total. vitest run -u reported Snapshots 1 updated, tests passed, and the snapshot file now states $670.00 where the correct total is $660.00. The bug is enshrined and the test will now defend it.

Snapshots are fine for small, stable, serialized output that a person can read in one glance: a formatted invoice line, an error payload. toMatchInlineSnapshot writes the value into the test file itself, so the reviewer sees it inside the diff, right next to the code that produced it. For values that change every run, property matchers fix the type and snapshot everything else: { occurredAt: expect.any(Date), requestId: expect.any(String) }.

Part 6 — Accessibility tests 🟡 Intermediateالجزء 6 — اختبارات الـ accessibility

English

jest-axe runs the axe-core engine against rendered HTML and fails with one line per rule. Version 11 works under Vitest 5 (vitest-axe is stale at 0.1.0, so don't reach for it). It ships without Vitest types, so you declare toHaveNoViolations yourself in a small .d.ts. A nameless button and an image with no alt are real, critical violations, and each message says exactly what to add.

jsdom has no layout and no rendering, so anything visual is outside its reach. The clearest example is colour contrast: jest-axe's README says these checks don't work in jsdom and turns them off. We forced the rule on and it came back incomplete, never a violation. The same markup in real Chrome through @axe-core/playwright is a clear violation with a measured ratio of 1.91 where 4.5 is required. So: run axe in unit tests for markup rules, and in a browser test for contrast.

And automation only covers part of the problem: axe-core's own README claims on average 57% of WCAG issues are found automatically. The other part, keyboard order, focus management, whether a screen reader's output makes sense, needs a person or a specific test. A keyboard-only test is cheap, and React lesson 16 covers the manual checklist.

1. Scope a query 🟢 easy Using OrdersTable and renderWithProviders, write a test that refunds order 1043 and proves order 1042 wasn't touched.
باستخدام OrdersTable و renderWithProviders، اكتب test بيعمل refund للأوردر 1043 ويثبت إن الأوردر 1042 متلمسش.
Hint · تلميح Find the row by name with a regex, then use within(row). toHaveBeenCalledExactlyOnceWith covers both the count and the argument.
هات الصف بالاسم بـ regex، وبعدين within(row). و toHaveBeenCalledExactlyOnceWith بيغطي العدد والـ argument مع بعض.
Solution · الحل 
it("refunds only the row that was clicked", async () => {
  const onRefund = vi.fn();
  const { user } = renderWithProviders(<OrdersTable orders={orders} onRefund={onRefund} />);

  const row = screen.getByRole("row", { name: /#1043/ });
  await user.click(within(row).getByRole("button", { name: /refund/i }));

  expect(onRefund).toHaveBeenCalledExactlyOnceWith(1043);
  expect(onRefund).not.toHaveBeenCalledWith(1042);
});
الـ test ده اتشغّل وعدّى. لو شيلت within هيفشل بـ Found multiple elements.
2. A role-gated button 🟡 medium Write RefundAction that reads the current user from AuthContext and shows a Refund order N button to admins only. Test both roles through the authUser option of renderWithProviders.
اكتب RefundAction بيقرا الـ user من AuthContext ويعرض زرار Refund order N للـ admin بس. اختبر الـ role الاتنين عن طريق option authUser في renderWithProviders.
Hint · تلميح Use queryByRole for the absence check. getByRole would throw before your assertion runs.
استخدم queryByRole للتأكد إن الزرار مش موجود، لأن getByRole هيرمي error قبل الـ assertion.
Solution · الحل 
function RefundAction({ orderId }: { orderId: number }) {
  const user = useContext(AuthContext);
  if (user?.role !== "admin") return null;
  return <button type="button">Refund order {orderId}</button>;
}

it("shows the refund button to admins", () => {
  renderWithProviders(<RefundAction orderId={1042} />, { authUser: { id: "u1", role: "admin" } });
  expect(screen.getByRole("button", { name: "Refund order 1042" })).toBeInTheDocument();
});

it("hides the refund button from customers", () => {
  renderWithProviders(<RefundAction orderId={1042} />, { authUser: { id: "u2", role: "customer" } });
  expect(screen.queryByRole("button", { name: /refund/i })).not.toBeInTheDocument();
});
الاتنين اتشغّلوا وعدّوا. الجزء المهم إن الـ test بيغيّر الـ auth بـ option واحد، من غير ما يكتب أي wrapper.

Cheat sheet · الخلاصة

  • Scope ambiguous queries: within(row).getByRole("button", { name }). String name = exact, regex = partial.
  • Accessible name order: aria-labelledby > aria-label > label/alt > content > title. An empty name is a bug in the component, not the test.
  • findBy = getBy + waitFor (1000 ms). Never put an action inside waitFor.
  • One test-utils.tsx: fresh QueryClient per test, retry: false. Forgetting it cost ≈7 s and a misleading failure.
  • Storybook 10: import from storybook/test; composeStories avoids writing a scenario twice.
  • toHaveScreenshot: first run writes the baseline and fails; baselines are per platform, so generate them in CI.
  • threshold = is this pixel different; maxDiffPixelRatio = how many may differ. Mask dynamic content.
  • Snapshots: small serialized output only. Prefer toMatchInlineSnapshot; property matchers for dates and IDs.
  • jest-axe finds markup issues; jsdom can't do contrast, so use @axe-core/playwright. Green axe ≠ accessible.
