Why this matters · ليه ده مهم

English

The Dockerfile from the last lesson works, and it would also ship your compiler and test framework, run as root, drop requests on every deploy, and get OOM-killed with no stack trace. A production image is a set of small, deliberate decisions: what goes in, which base, which user, who receives SIGTERM, and how much memory V8 thinks it has. "Write a production Dockerfile from memory and explain each line" is a real exit question for this section and a common interview task.

بالعامية

الـ Dockerfile بتاع الدرس اللي فات شغال، بس برضو هيشحن الـ compiler والـ test framework، ويشتغل بـ root، ويقطع requests مع كل deploy، ويتقتل بـ OOM من غير stack trace. الـ production image عبارة عن شوية قرارات صغيرة ومقصودة: إيه اللي يدخل، base إيه، user مين، مين اللي بيستلم الـ SIGTERM، و V8 فاكر معاه memory قد إيه. وسؤال "اكتب Dockerfile production من الذاكرة واشرح كل سطر" هو سؤال حقيقي في الـ exit test بتاع القسم ده، وكمان مهمة interview شائعة.

Part 1 — Multi-stage builds 🟡 Intermediateالجزء 1 — الـ multi-stage builds

English

A multi-stage Dockerfile has several FROMs, and only the last stage becomes the image. Stages let you install compilers in one place and leave them behind. For a TypeScript API, the standard shape is three stages from a shared base: deps (production packages only, npm ci --omit=dev), build (all packages plus tsc, producing dist), and runtime (COPY --from just node_modules from deps and dist from build). The layer-caching rules from lesson 25, part 3 still apply inside each stage. The mechanics were introduced in 04 Node lesson 32, part 3, and 06 Next.js lesson 20, part 3 does the same for output: standalone. This part adds real numbers.

Measured on the orders API here (Express, pg, ioredis, Zod; dev tools TypeScript, Vitest, ESLint, on this Windows machine): the full install is 63.64 MB, 5,137 files, and with --omit=dev it is 9.94 MB, 1,692 files: 84% smaller. Compiled dist and src are about the same size (it's one small file); the win is not shipping src and the compiler. Fewer files also means less to scan and a smaller attack surface.

Bundling goes further: esbuild --bundle --platform=node folds everything into one 2.41 MB file that starts about 2.7× faster here (a median ≈215 ms against ≈574 ms until listening, 15 alternating runs on a loaded Windows machine, so read the ratio). It's not free: native addons (--external:pg-native here, and bcrypt or sharp in other apps) must stay external, stack traces need source maps, and npm audit can't see what's inside a bundle.

# الأساس المشترك: كل الـ stages بتبدأ من هنا
FROM node:26-slim AS base
WORKDIR /app

# الـ production dependencies بس، ده اللي هيتشحن
FROM base AS deps
COPY package*.json ./
RUN npm ci --omit=dev

# الـ build: هنا بس TypeScript وباقي الـ devDependencies
FROM base AS build
COPY package*.json ./
RUN npm ci
COPY tsconfig.json ./
COPY src ./src
RUN npm run build

# الـ runtime: آخر stage هي الـ image، والباقي بيتساب ورا
FROM base AS runtime
COPY --from=deps /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY package.json ./
CMD ["node", "dist/server.js"]

import { spawn } from "node:child_process";

const APP = new URL("../orders-api/", import.meta.url).pathname.replace(/^\/([A-Z]:)/, "$1");
const env = { ...process.env, PORT: "0", DATABASE_URL: "postgres://x@127.0.0.1:1/x", REDIS_URL: "redis://127.0.0.1:1" };

function once(entry) {
  return new Promise((resolve, reject) => {
    const started = performance.now();
    const child = spawn(process.execPath, [entry], { cwd: APP, env, stdio: ["ignore", "pipe", "inherit"] });
    child.stdout.on("data", () => {
      const ms = performance.now() - started;
      child.kill();
      resolve(ms);
    });
    child.on("error", reject);
  });
}

بالعامية

الـ multi-stage Dockerfile فيه كذا FROM، وآخر stage بس هي اللي بتبقى الـ image. الـ stages بتخليك تسطّب الـ compiler في مكان وتسيبه ورا. لـ TypeScript API الشكل المعتاد 3 stages من base مشترك: deps (الـ production packages بس بـ npm ci --omit=dev)، build (كل الـ packages + tsc ويطلّع dist)، و runtime (بـ COPY --from بتاخد node_modules من deps وdist من build بس). قواعد الـ layer caching من درس 25، الجزء 3 لسه شغالة جوه كل stage. الميكانيزم اتشرح في درس 32 في قسم Node، الجزء 3، ودرس 20 في قسم Next.js، الجزء 3 بيعمل نفس الحاجة مع output: standalone. الجزء ده بيضيف أرقام حقيقية.

اتقاس على الـ orders API هنا (Express و pg و ioredis و Zod، وأدوات التطوير TypeScript و Vitest و ESLint، على Windows): الـ install الكامل 63.64 MB و 5,137 ملف، وبـ --omit=dev 9.94 MB و 1,692 ملف، أقل بـ 84%. الـ dist والـ src نفس الحجم تقريبًا (ملف صغير واحد)، والمكسب الحقيقي إن src والـ compiler مش بيتشحنوا. ملفات أقل كمان يعني scan أقل و attack surface أصغر.

الـ bundling بيروح لأبعد: esbuild --bundle --platform=node بيجمّع كل حاجة في ملف واحد 2.41 MB، وبيبدأ أسرع حوالي 2.7 مرة هنا (median ≈215 ms مقابل ≈574 ms لحد listening، 15 run بالتبادل على Windows محمّل، فخد النسبة). بس له تمن: الـ native addons (--external:pg-native هنا، وbcrypt أو sharp في apps تانية) لازم تفضل external، والـ stack traces محتاجة source maps، وnpm audit مش شايف اللي جوه الـ bundle.

فين هستخدمه في شغلي؟ لما تلاقي الـ image بتاعة الـ orders API حجمها 1.2 GB، أول حاجة تبص عليها: هل فيها devDependencies وsrc و Vitest؟ بعد الـ multi-stage الـ pull بيبقى أسرع والـ scan أقل. ولو الـ service بتتعمل scale-out كتير (جزء من autoscaling أو Lambda)، الـ startup الأسرع بتاع الـ bundle بيفرق، بس اقعد مع الـ team على موضوع الـ source maps والـ native addons الأول.
Trade-off: node_modules or a bundle? A bundle is smaller and starts faster, but it breaks with native addons and dynamic require, and hides what's shipped from npm audit. For most APIs, a multi-stage image with --omit=dev is the safe default. Bundle when startup time or image size is a measured problem.
الموازنة: node_modules ولا bundle؟ الـ bundle أصغر وأسرع في البدء، بس بيتكسر مع native addons وrequire الـ dynamic، وبيخبّي اللي اتشحن عن npm audit. لمعظم الـ APIs، multi-stage مع --omit=dev هو الاختيار الآمن. اعمل bundle لما وقت البدء أو حجم الـ image يبقى مشكلة متقاسة.

Part 2 — Base images 🟡 Intermediateالجزء 2 — الـ base images

English

What changed. The README says node:22-slim. Node 22 is now a Maintenance LTS line and Node 26 is LTS (nodejs.org releases page, checked 2026-11-09), so new images use node:26-slim. The sizes below are compressed amd64 sizes, read from registry manifests as plain JSON, with no layers pulled.

slim is Debian with glibc and a shell. It's the safe default: prebuilt native addons target glibc first. alpine is smaller but uses musl, not glibc, and native addons need a separate musl build: sharp publishes @img/sharp-linuxmusl-x64 with libc: musl next to its glibc package. A package with no musl prebuild usually falls back to compiling from source with node-gyp, which needs python3, make and g++ in the image. In Node's own support table, x64 musl is Tier 2 (Alpine). distroless (gcr.io/distroless/nodejs26-debian13) has no shell, no package manager, only Node and its runtime dependencies, which is a much smaller attack surface; its entrypoint is already node, so CMD is just the script. Docker Hardened Images became free under Apache 2.0 in December 2025 (for example dhi.io/node:24). Pulling them needs a Docker account login, so they weren't queried here.

The debugging story is the real cost of going smaller. With slim you can docker exec in and apt-get install a tool. Distroless has no shell, so docker exec ... sh fails; you need its :debug tag (BusyBox, 61.0 MB) or an ephemeral debug container alongside it (kubectl debug, see lesson 33). Alpine has apk. Choose by what you must be able to do at 3 a.m.

async function hubTag(repo, tag) {
  const res = await fetch(`https://hub.docker.com/v2/repositories/${repo}/tags/${tag}`);
  if (!res.ok) return console.log(`${repo}:${tag}`.padEnd(40), `HTTP ${res.status}`);
  const body = await res.json();
  const amd = body.images.find((i) => i.architecture === "amd64" && i.os === "linux");
  console.log(`docker.io/${repo}:${tag}`.padEnd(44), MB(amd.size), " updated", body.last_updated.slice(0, 10));
  return { digest: amd.digest, size: amd.size };
}

const OCI = "application/vnd.oci.image.index.v1+json, application/vnd.docker.distribution.manifest.list.v2+json, application/vnd.oci.image.manifest.v1+json, application/vnd.docker.distribution.manifest.v2+json";

async function gcrSize(repo, tag) {
  const get = (ref) => fetch(`https://gcr.io/v2/${repo}/manifests/${ref}`, { headers: { Accept: OCI } });
  const res = await get(tag);
  if (!res.ok) return console.log(`gcr.io/${repo}:${tag}`.padEnd(44), `HTTP ${res.status}`);
  let doc = await res.json();
  if (doc.manifests) {
    const entry = doc.manifests.find((m) => m.platform?.architecture === "amd64" && m.platform?.os === "linux");
    doc = await (await get(entry.digest)).json();
  }
  const size = doc.layers.reduce((a, l) => a + l.size, 0);
  console.log(`gcr.io/${repo}:${tag}`.padEnd(44), MB(size), ` ${doc.layers.length} layers`);
}

Part 3 — Non-root, read-only, capabilities 🟡 Intermediateالجزء 3 — non-root و read-only و capabilities

English

By default a container runs as root. A remote-code-execution bug then has root inside the container, and any kernel or runtime escape starts from there. Layer the defences: USER node (the official image ships a node user, uid 1000) drops root; --read-only makes the root filesystem unwritable, with a --tmpfs /tmp for the places that must be written; --cap-drop=ALL removes Linux capabilities the app doesn't need; and --security-opt=no-new-privileges stops setuid binaries regaining privileges. These are defence-in-depth, covered in 04 Node lesson 28, part 3. Inside a container the OS enforces them for every process and native library.

Two practical consequences. Files must be owned by the runtime user, so COPY --chown=node:node, or the app can't write logs or temp files. And the app should listen on a high port (3000, not 80). Binding below 1024 normally needs the NET_BIND_SERVICE capability you just dropped; recent Docker versions relax that with a default sysctl, but not every platform does, so don't depend on it and let the platform map 443 to your port.

You can see the same failure without Docker. Node's permission model (lesson 28, part 4) is a labelled stand-in: a process started with --permission can't write outside the paths you allowed, and an app that writes a report to ./invoices fails exactly where a read-only root filesystem would make it fail. The stand-in doesn't capture the kernel side: real read-only rootfs returns EROFS from the kernel and covers native code and child processes, while Node's permission check is per-process inside Node.

English

This part assumes the shutdown sequence in 04 Node lesson 24, part 5 and the PID 1 details in lesson 32, part 4: PID 1 ignores signals with the default action unless it installs a handler, and docker stop sends SIGTERM, waits 10 s, then sends SIGKILL (exit 137). The exec form CMD ["node", "dist/server.js"] makes Node PID 1 directly. The shell form CMD node dist/server.js runs under /bin/sh -c, so a shell may sit in front of Node and signals aren't guaranteed to reach it. npm start adds another layer. docker run --init (or tini in the image) runs a tiny init as PID 1 that forwards signals and reaps zombies.

The stand-in below shows the cost. Windows can't deliver SIGTERM to a Node handler (child.kill('SIGTERM') just ends the process), so the "signal" is an IPC message: the same logic Linux would run in process.on('SIGTERM'). Three setups under autocannon, 20 connections: direct exec, a wrapper that doesn't forward the signal (a stand-in for a shell in front), and a wrapper that forwards it (an init). It doesn't capture PID namespaces, zombie reaping or real signal semantics; those are stated from the docs.

One real finding while building this: with keep-alive clients, server.close() alone never finished, and the run hit the grace timeout. Node's close() stops accepting new connections and closes only idle ones, and a keep-alive client that keeps sending stays "active" forever. The fix is to set Connection: close on responses once shutdown has started.

// الـ orders API: كل request بياخد 150ms، والـ shutdown بيستنى الشغال يخلص

    res.end("order accepted\n");
  }, 150);
});

  server.close(() => {
    process.send({ drained: true });
    process.exit(0);

    child.on("message", (m) => {
      if (m.listening) (apiPid = m.pid), resolve(m.listening);

Part 5 — HEALTHCHECK and limits 🟡 Intermediateالجزء 5 — الـ HEALTHCHECK وحدود الموارد

English

HEALTHCHECK gives Docker a command whose exit code decides healthy (0) or unhealthy (1). Distroless and many slim images have no curl, and a shell-based check can't work with no shell, so the portable choice is a small Node script in exec form, tested below against a real server. Docker and Compose honour HEALTHCHECK; Kubernetes ignores it and uses its own probes (lesson 33).

--memory and --cpus set cgroup limits. Exceed --memory and the kernel OOM-kills the process (SIGKILL, exit 137, no JavaScript stack trace). --cpus throttles the process, which shows up as latency spikes, not crashes. V8 doesn't reliably size itself to your limit: set --max-old-space-size below the container limit. Real numbers on this machine: --max-old-space-size=128 gives a heap_size_limit of 176 MB, because the flag covers old space only and V8 adds the young generation (3 × 16 MB semi-spaces = 48 MB, and --max-semi-space-size=8 gives 152). With no flag the default was 4144 MB. With --max-old-space-size=64 and a growing array the process dies with exit code 134 and FATAL ERROR: Reached heap limit. Current Node docs also document --max-old-space-size-percentage, but Node 22.19 here rejects it (bad option), so check your version.

Why RSS is bigger than the heap. RSS counts everything in memory, including Buffers, which live outside the V8 heap. Below, with the heap capped at 128 MB, allocating a 200 MB Buffer takes RSS to 246 MB while heapUsed stays at 4 MB: the heap flag can't stop that, so the container limit has to cover heap plus Buffers, code, stacks and native memory. A common starting point is the heap at roughly 75% of the container limit, then adjust using measured RSS.

This is the file from question 10 of this section's exit test: "write a production-ready Node Dockerfile from memory and explain each line". Read it once with the annotations, then close the page and write it from memory. Everything here was introduced earlier in this lesson or the last one, and each line exists for a reason you can defend in a code review.

A review shouldn't depend on memory alone, so the rules can be automated. The script below uses dockerfile-ast to flag five things: a latest or missing tag, a final stage running as root, ADD, a shell-form CMD or ENTRYPOINT, and a missing HEALTHCHECK. It's not a replacement for hadolint, which has many more rules: hadolint is not run here (it needs a binary we don't have). The script is what CI would run on every Dockerfile in a repository.

# syntax=docker/dockerfile:1

# (1) الأساس المشترك: نسخة محددة، ومحدش بيعتمد على latest
FROM node:26-slim AS base
WORKDIR /app

# (2) الـ production dependencies بس: هي اللي هتتشحن
FROM base AS deps
COPY package*.json ./
RUN npm ci --omit=dev

# (3) الـ build: هنا بس TypeScript وأدوات التطوير، وكل ده بيتساب ورا
FROM base AS build
COPY package*.json ./
RUN npm ci
COPY tsconfig.json ./
COPY src ./src
RUN npm run build

# (4) الـ runtime: الـ stage الوحيدة اللي بتتشحن، من غير source ولا devDependencies
FROM base AS runtime
ENV NODE_ENV=production
COPY --from=deps --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
COPY --chown=node:node package.json healthcheck.mjs ./
# (5) مستخدم عادي بـ uid 1000 موجود جاهز في الـ image الرسمية
USER node
EXPOSE 3000
# (6) فحص الصحة بـ Node نفسه، لأن curl مش مضمون يبقى موجود
HEALTHCHECK --interval=10s --timeout=3s --start-period=20s --retries=3 CMD ["node", "healthcheck.mjs"]
# (7) الـ exec form: node بيستقبل الـ SIGTERM مباشرة
CMD ["node", "dist/server.js"]

// قواعد review بسيطة بـ parser حقيقي: مش بديل لـ hadolint، بس بتمسك أشهر 5 غلطات
import { readFileSync } from "node:fs";
import { DockerfileParser, type Instruction } from "dockerfile-ast";

type Finding = { line: number; rule: string; message: string };

export function lint(source: string): Finding[] {
  const dockerfile = DockerfileParser.parse(source);
  const all: Instruction[] = dockerfile.getInstructions();
  const findings: Finding[] = [];
  const at = (i: Instruction): number => i.getRange().start.line + 1;
  const froms = all.filter((i) => i.getKeyword() === "FROM");

  // الآخر هو الـ runtime stage: هو اللي بيتشحن، وقواعد الـ runtime بتنطبق عليه بس
  const lastFrom = froms[froms.length - 1];
  const final = lastFrom ? all.slice(all.indexOf(lastFrom)) : all;

  const stageNames = new Set(froms.map((f) => f.getArgumentsContent()?.split(/\s+as\s+/i)[1]?.trim()));
  for (const from of froms) {
    const image = from.getArguments()[0]?.getValue() ?? "";
    if (stageNames.has(image) || image.includes("@sha256:")) continue;
    if (image.endsWith(":latest") || !image.includes(":")) findings.push({ line: at(from), rule: "pin-tag", message: `${image}: use an explicit version` });
  }
  for (const add of all.filter((i) => i.getKeyword() === "ADD")) {
    findings.push({ line: at(add), rule: "no-add", message: "use COPY unless you need ADD's URL or archive behaviour" });
  }
  const users = final.filter((i) => i.getKeyword() === "USER");
  const lastUser = users[users.length - 1];
  const value = lastUser?.getArguments()[0]?.getValue();
  if (!lastUser || value === "root" || value === "0") {
    findings.push({ line: lastUser ? at(lastUser) : at(lastFrom!), rule: "non-root", message: "final stage runs as root" });
  }
  for (const entry of final.filter((i) => ["CMD", "ENTRYPOINT"].includes(i.getKeyword()))) {
    if (!(entry.getArgumentsContent() ?? "").trim().startsWith("[")) {
      findings.push({ line: at(entry), rule: "exec-form", message: `${entry.getKeyword()} in shell form: /bin/sh is PID 1, signals may not reach node` });
    }
  }
  if (!final.some((i) => i.getKeyword() === "HEALTHCHECK")) {
    findings.push({ line: at(lastFrom!), rule: "healthcheck", message: "final stage has no HEALTHCHECK" });
  }
  return findings.sort((a, b) => a.line - b.line);
}

for (const file of process.argv.slice(2)) {
  const findings = lint(readFileSync(file, "utf8"));
  console.log(`${file}: ${findings.length} finding(s)`);
  for (const f of findings) console.log(`  line ${String(f.line).padStart(2)}  ${f.rule.padEnd(12)} ${f.message}`);
}

بالعامية

ده الملف بتاع السؤال 10 في الـ exit test بتاع القسم: "اكتب Dockerfile لـ Node production-ready من الذاكرة واشرح كل سطر". اقراه مرة بالتعليقات، وبعدين اقفل الصفحة واكتبه من دماغك. كل حاجة فيه اتشرحت في الدرس ده أو اللي قبله، وكل سطر ليه سبب تقدر تدافع عنه في code review.

الـ review مش لازم يعتمد على الذاكرة بس، فالقواعد ممكن تتعمل أوتوماتيك. الـ script فوق بيستخدم dockerfile-ast ويمسك 5 حاجات: tag latest أو مفيش tag، آخر stage بـ root، ADD، CMD أو ENTRYPOINT بالـ shell form، ومفيش HEALTHCHECK. ده مش بديل لـ hadolint اللي فيه rules أكتر بكتير، و hadolint متشغّلش هنا (محتاج binary مش عندنا). الـ script هو اللي الـ CI يشغّله على كل Dockerfile في الـ repo.

فين هستخدمه في شغلي؟ حط script زي ده في الـ CI عشان أي PR فيه FROM node:latest أو CMD npm start يترفض لوحده، وأنت في الـ code review تركز على الحاجات اللي الأدوات متعرفش تشوفها: الـ memory limit، وNODE_ENV، ومكان الملفات المكتوبة.

Common mistakes · غلطات شائعة

❌ One stage, everything inside 
# غلط: الـ devDependencies والـ source والـ compiler في الـ image
FROM node:26-slim
WORKDIR /app
COPY . .
RUN npm install && npm run build
CMD ["node", "dist/server.js"]
✅ Multi-stage, prod only 
# صح: الـ runtime بياخد الـ dist والـ prod deps بس
FROM node:26-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY src ./src
COPY tsconfig.json ./
RUN npm run build

FROM node:26-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
CMD ["node", "dist/server.js"]
بالعامية

❌ كل حاجة في stage واحدة: الـ devDependencies (63.64 MB في المثال) والـ source والـ compiler كلهم بيتشحنوا، وnpm install مش بيلتزم بالـ lockfile. ✅ multi-stage وnpm ci --omit=dev، والـ runtime بياخد اللي محتاجه بس (9.94 MB)، وUSER node قبل الـ CMD.

❌ Shell form and npm start 
# غلط: ⁦/bin/sh⁩ ممكن يبقى PID 1 والـ SIGTERM ميوصلش
CMD npm start
✅ Exec form, node directly 
# صح: node هو PID 1 والـ handler بيشتغل
CMD ["node", "dist/server.js"]
بالعامية

❌ CMD npm start shell form: الـ /bin/sh هو PID 1 و npm طبقة زيادة، فالإشارة ممكن ماتوصلش و docker stop يستنى الـ 10 ثواني ويقتله، وتتقطع الـ requests. ✅ الـ exec form وnode مباشرة، والـ handler بيشتغل والـ requests بتخلص.

❌ Heap at the container limit 
services:
  api:
    # غلط: الـ heap لوحده بيساوي الـ limit، ومفيش مكان للـ Buffers
    mem_limit: 512m
    environment:
      NODE_OPTIONS: --max-old-space-size=512
✅ Heap below the limit 
services:
  api:
    # صح: الـ ⁦heap 75%⁩ تقريبًا، والباقي للـ Buffers والكود
    mem_limit: 512m
    environment:
      NODE_OPTIONS: --max-old-space-size=384
بالعامية

❌ --max-old-space-size=512 مع limit 512 MB: الـ heap_size_limit الفعلي أكبر من الرقم (زي ما 128 طلع 176)، والـ Buffers والكود بره الـ heap، فالـ kernel هيعمل OOM kill بـ exit 137 من غير trace. ✅ خلي الـ heap حوالي 75% من الـ limit (384 من 512)، وتابع الـ RSS الفعلي.

❌ node:latest 
# غلط: كل build ممكن يجيب نسخة Node مختلفة
FROM node:latest
✅ Explicit, pinned version 
# صح: نسخة معروفة، وفي الـ production ثبّت الـ digest
FROM node:26-slim
بالعامية

❌ node:latest مؤشر بيتحرك: build النهارده غير بكره، وممكن تدخل major جديدة (26 ← 27) من غير ما تحس. ✅ حدد النسخة node:26-slim، وفي الـ production ثبّت الـ digest كمان عشان نفس الـ build يطلع نفس الـ image، وحدّثه بأداة زي Renovate.

2. Reproduce the keep-alive drain bug 🟡 medium Remove the Connection: close line from api.mjs, run pid1-standin.mjs, and confirm the direct scenario now reaches the grace timeout. Put the line back and confirm it drains.
امسح سطر Connection: close من api.mjs، وشغّل pid1-standin.mjs، واتأكد إن حالة الـ direct بقت بتوصل للـ grace timeout. رجّع السطر واتأكد إنها بتخلص (drain).
Solution · الحل Without the header the direct line reads killed at grace timeout, drained=false, dropped=20: the same 20 in-flight requests as the no-forwarding case, because server.close() waits for keep-alive connections that never go idle.
من غير الـ header سطر الـ direct بيبقى killed at grace timeout وdrained=false وdropped=20، نفس الـ 20 in-flight بتوع حالة الـ wrapper، لأن server.close() مستني keep-alive connections عمرها ما بتبقى idle.
3. Extend the linter 🟡 medium Add one rule to lint-dockerfile.ts: flag a final stage that COPYs node_modules without --chown, because a non-root user can't write there, and flag a RUN npm install anywhere.
زوّد قاعدة في lint-dockerfile.ts: يعلّم على آخر stage بتعمل COPY لـ node_modules من غير --chown، وعلى أي RUN npm install.

Cheat sheet · الخلاصة

  • Multi-stage: deps (--omit=dev) + build (TypeScript) → runtime gets node_modules and dist only. Here: 63.64 MB → 9.94 MB.
  • Bundling with esbuild: one 2.41 MB file, ≈2.7× faster start, but native addons, source maps and npm audit become your problem.
  • New images: node:26-slim. 22 is Maintenance LTS.
  • slim (glibc, shell, safe default); alpine (musl, native addons need musl builds); distroless (no shell, debug via :debug or a debug container).
  • Non-root + --read-only + --tmpfs + --cap-drop=ALL + no-new-privileges. COPY --chown=node:node. Listen above 1024.
  • Exec form CMD ["node", "..."]. Use --init or tini if you spawn children. docker stop: SIGTERM, 10 s, SIGKILL (137).
  • Under keep-alive, set Connection: close during shutdown or server.close() never finishes.
  • HEALTHCHECK as a small Node script in exec form. Kubernetes ignores it.
  • --max-old-space-size covers old space only: 128 → heap_size_limit 176 MB. Heap ≈ 75% of the container limit.
  • Exit 134 = V8 out of heap, with a stack trace. Exit 137 = killed, no trace. RSS includes Buffers.
  • Lint every Dockerfile in CI: latest, root, ADD, shell-form CMD, missing HEALTHCHECK.
