Why this matters · ليه ده مهم

English

E2E tests are the only tests that prove the real product works: browser, API, database, cookies, all wired together. They're also the slowest and flakiest tests you own, so a team either gets a few that it trusts or a big suite it reruns until it's green. This lesson is about getting the first kind: a small set on the flows that lose money when broken, with waiting done right, data that can't collide, a trace you can read when something fails, and a CI setup that reports flakiness instead of hiding it.

Every number below comes from a real run: Playwright 1.65 on the installed Chrome (channel: "chrome", nothing downloaded), against a small Express and Postgres 18 shop built for this lesson, on a loaded Windows machine. Treat timings as approximate (≈) and trust counts and ratios.

بالعامية

الـ E2E هي الـ tests الوحيدة اللي بتثبت إن المنتج الحقيقي شغال: browser و API و database و cookies كلهم متوصلين. وفي نفس الوقت هي أبطأ وأكتر tests بتعمل flake، فالفريق يا إما عنده شوية tests واثق فيهم، يا إما suite كبيرة بيعيدها لحد ما تخضر. الدرس ده عشان توصل للنوع الأول: عدد قليل على الـ flows اللي بتخسّر فلوس لو وقعت، انتظار مظبوط، data متتصادمش، trace تعرف تقراه لما حاجة تقع، و CI بيبلّغ عن الـ flakiness بدل ما يخبيها.

كل رقم تحت جاي من تشغيل حقيقي: Playwright 1.65 على Chrome المتسطّب (channel: "chrome"، مفيش download)، ضد متجر صغير Express و Postgres 18 معمول مخصوص للدرس، على جهاز Windows عليه ضغط. فالـ timings تقريبية (≈) واعتمد على الأعداد والنسب.

Part 1 — Locators and auto-waiting 🟡 Intermediateالجزء 1 — الـ locators والـ auto-waiting

English

React lesson 17, part 6 covers the Playwright basics. Two things decide whether your suite is stable, and both are about waiting. Use role-based locators by default (getByRole, getByLabel), for the same reason as in RTL. A locator is a recipe, not an element: it's re-resolved each time you act on it, so it survives re-renders. And it's strict: if two elements match, the action throws instead of clicking the wrong one.

Before a click, Playwright runs actionability checks and retries until they all pass or the timeout expires: the element is visible, stable (not animating), receives events (nothing covers it at the click point), and enabled. fill checks visible, enabled and editable. So a button that's covered by a loading overlay or disabled during a request is waited for automatically, and when it never becomes clickable the error names the reason.

The other half is web-first assertions: await expect(locator).toHaveText("$30.00") keeps re-reading until it matches or the assertion timeout (5 s by default) runs out. expect(await locator.textContent()).toBe(...) reads once, right now. The test below pays for that difference in time and in failures: a shop whose API answers in 50 to 800 ms, 20 runs of each variant. A fixed 2 s sleep never fails but is the slowest; a sleep tuned to "usually enough" (300 ms) passed 1 run out of 20; the web-first version passed all 20 and took about 40% of the sleep's time.

بالعامية

الجزء 6 من درس React 17 شرح أساسيات Playwright. حاجتين بيحددوا الـ suite بتاعك ثابتة ولا لأ، والاتنين عن الانتظار. استخدم الـ locators بالـ role كـ default (getByRole، getByLabel) لنفس السبب بتاع RTL. الـ locator وصفة مش element: بيتحدد من أول وجديد كل مرة تعمل عليه action، فبيستحمل الـ re-renders. وكمان strict: لو عنصرين طابقوه، الـ action بيرمي error بدل ما يضغط على الغلط.

قبل الـ click، Playwright بيعمل actionability checks وبيعيد لحد ما كلهم يعدّوا أو الـ timeout يخلص: العنصر visible (ظاهر)، stable (مش بيتحرك)، receives events (مفيش حاجة مغطياه عند نقطة الضغط)، و enabled. و fill بيفحص visible و enabled و editable. يعني زرار متغطي بـ overlay تحميل أو disabled أثناء request بيتستنى أوتوماتيك، ولو عمره ما بقى قابل للضغط الـ error بيقولك السبب.

النص التاني هو الـ web-first assertions: await expect(locator).toHaveText("$30.00") بتفضل تقرا لحد ما يطابق أو الـ timeout (5 ثواني افتراضيًا) يخلص. أما expect(await locator.textContent()).toBe(...) بتقرا مرة واحدة دلوقتي. التجربة فوق: متجر الـ API بتاعه بيرد في 50 لـ 800ms، و 20 run لكل نسخة. الـ sleep الثابت ثانيتين عمره ما فشل بس أبطأ حاجة، الـ sleep "المتظبط" 300ms عدّى مرة واحدة من 20، و الـ web-first عدّى الـ 20 وأخد حوالي 40% من وقت الـ sleep.

فين هستخدمه في شغلي؟ لو في الـ codebase بتاعك waitForTimeout أو sleep في أي E2E، اعتبرها bug واستبدلها بـ assertion على النتيجة اللي بتستناها (الـ total اتغيّر، الـ toast ظهر، الزرار بقى enabled). الـ retries في CI وقتها بتبقى لمشاكل نادرة بجد، مش لعلاج sleep ناقص.
Interview question "Why is page.waitForTimeout banned in most E2E suites?" → It waits for the wrong thing. The real condition is 'the total updated', and time is a guess at it, so you pick between slow and flaky. A web-first assertion waits for exactly that condition and stops the moment it's true.
"ليه page.waitForTimeout ممنوع في أغلب الـ E2E suites؟" ← عشان بيستنى الحاجة الغلط. الشرط الحقيقي هو "الـ total اتغيّر"، والوقت مجرد تخمين ليه، فبتختار يا بطيء يا flaky. الـ web-first assertion بتستنى الشرط بالظبط وبتقف أول ما يتحقق.

Part 2 — Fixtures and auth state 🟡 Intermediateالجزء 2 — الـ fixtures والـ auth state

English

A fixture is a value the test asks for by name, plus its setup and teardown. test.extend defines them. A worker-scoped fixture ({ scope: "worker" }) is built once per worker process and shared by every test that worker runs: here, one database and one app server. A test-scoped fixture is built fresh for each test. Code after await use(...) is the teardown, and it runs even when the test fails, which is the reason to prefer fixtures over beforeEach and afterEach pairs.

seededOrder creates its data through the API and removes it through the API, so the test knows nothing about SQL and the seed goes through the same validation as real traffic. testUser creates a unique user and session for each test, so its cart can't collide with anyone's. Both are requested in the test's parameters, and Playwright builds exactly what's asked for, in dependency order.

For login, a setup project signs in through the UI once per role and writes the browser state to a file with storageState; projects that depend on it load that file (Next lesson 17, part 5 covers per-role state in the App Router). We measured 20 tests against a password hash tuned to ≈355 ms, like a production-sized work factor: per-test login averaged ≈727 ms per test (≈10.1 s wall), reused state ≈236 ms per test (≈6.3 s wall, including the 2 setup tests). The gap grows with real login paths like SSO and MFA. The login flow keeps its own test: reusing state skips login everywhere else, so something must still prove login works.

export const test = base.extend<TestFixtures, WorkerFixtures>({
  // نطاق worker: database وسيرفر لكل worker، بيتعملوا مرة واحدة
  shop: [
    async ({}, use, workerInfo) => {
      const adminUrl = safePort(process.env.E2E_DATABASE_URL);
      const dbName = process.env.E2E_SHARED_DB ? "shop_shared" : `shop_w${workerInfo.parallelIndex}`;

      const admin = new Client({ connectionString: adminUrl });
      await admin.connect();
      if (process.env.E2E_SHARED_DB) {
        const exists = await admin.query("SELECT 1 FROM pg_database WHERE datname = $1", [dbName]);
        if (exists.rowCount === 0) await admin.query(`CREATE DATABASE ${dbName} TEMPLATE shop_template`).catch(() => {});
      } else {
        await admin.query(`DROP DATABASE IF EXISTS ${dbName} WITH (FORCE)`);
        await admin.query(`CREATE DATABASE ${dbName} TEMPLATE shop_template`);
      }
      await admin.end();

      const pool = makePool(adminUrl.replace(/\/postgres$/, `/${dbName}`));
      const server: Server = createShop({ pool, ...shopOptions() }).listen(0, "127.0.0.1");
      await new Promise((resolve) => server.once("listening", resolve));
      const { port } = server.address() as AddressInfo;

      await use({ baseURL: `http://127.0.0.1:${port}`, pool });

      server.closeAllConnections();
      await new Promise((resolve) => server.close(resolve));
      await pool.end();
    },
    { scope: "worker" },
  ],

  baseURL: async ({ shop }, use) => {
    await use(shop.baseURL);
  },

    expect(removed.status()).toBe(204);

بالعامية

الـ fixture حاجة الـ test بيطلبها باسمها، ومعاها الـ setup والـ teardown بتوعها. test.extend هو اللي بيعرّفهم. الـ fixture بـ نطاق worker ({ scope: "worker" }) بيتعمل مرة واحدة لكل worker process وكل الـ tests في الـ worker ده بيشاركوه: هنا database واحدة وسيرفر واحد. الـ fixture بـ نطاق test بيتعمل جديد لكل test. والكود اللي بعد await use(...) هو الـ teardown وبيشتغل حتى لو الـ test وقع، ودي الميزة على زوج beforeEach و afterEach.

seededOrder بيعمل البيانات عن طريق الـ API وبيمسحها عن طريق الـ API، فالـ test ميعرفش حاجة عن SQL، والـ seed بيعدي على نفس الـ validation بتاع الـ traffic الحقيقي. testUser بيعمل user و session جداد لكل test، فالكارت بتاعه مستحيل يتصادم مع حد. والاتنين بيتطلبوا في parameters الـ test، و Playwright بيبني المطلوب بس بترتيب الاعتماديات.

للـ login، setup project بيعمل login من الـ UI مرة واحدة لكل role وبيحفظ حالة الـ browser في ملف بـ storageState، والـ projects اللي معتمدة عليه بتحمّل الملف ده (الجزء 5 من درس Next 17 شرح الـ state لكل role). قسنا 20 test مع password hash متظبط على ≈355ms زي work factor الـ production: الـ login مع كل test متوسطه ≈727ms للـ test (≈10.1 ثانية إجمالي)، والـ state المعاد استخدامه ≈236ms للـ test (≈6.3 ثانية، شامل الـ 2 setup tests). والفرق بيكبر مع SSO و MFA. والـ login flow له test خاص بيه: لما كل الباقي بيعدّي الـ login، لازم حاجة تثبت إن الـ login شغال.

فين هستخدمه في شغلي؟ أي app فيها admin و customer: setup project بيعمل login للاتنين مرة واحدة، و test.use({ storageState: "..." }) لكل مجموعة tests. أي بيانات زي order أو tenant بتتعمل بـ fixture عن طريق الـ API، وبتتمسح في الـ teardown حتى لو الـ test وقع، فالـ staging مش هيتملى زبالة مع الوقت.

Part 3 — Parallelism 🟡 Intermediateالجزء 3 — الـ parallelism

English

fullyParallel: true runs tests in parallel inside a file as well as across files; workers caps the processes on one machine; --shard=1/3 splits the suite across CI machines (our 24 tests became 8 per shard). Parallelism makes every piece of shared state a bug. The failure below is real: 8 tests against one buyer with 4 workers. 6 of 8 failed, and the received totals ($60.00, $120.00, $180.00) are other tests' keyboards in the same cart.

Two layers of fix. Database per worker: workerInfo.parallelIndex (the same number as testInfo.parallelIndex inside a test) is a stable slot number from 0 to workers−1, so a worker that restarts after a failure comes back to the same shop_w0 database (workerIndex would be a new number). Cloning a template database with CREATE DATABASE ... TEMPLATE is what makes that cheap. Data unique per test: testUser creates a new user, so two tests in the same worker can't collide either. With both, the same 8 tests passed 8 of 8.

More workers stop helping fast. With 96 tests: 1 worker took ≈28.4 s, 2 took ≈19.5 s, 4 took ≈18.0 s, and 8 took ≈25.3 s, slower than 2. The sum of test durations was about 16.8 s, so roughly 11.6 s is serial and fixed: starting Playwright, global setup, Chrome, cloning databases. Amdahl's law says the serial part caps the speedup at about 28.4 / 11.6 ≈ 2.4 times however many workers you add. Past that, 8 workers meant 8 Chromes and 8 servers on a machine already under load, and the contention made it slower. Measure your own curve and pick the knee.

Part 4 — Reading a trace 🟡 Intermediateالجزء 4 — قراية الـ trace

English

When an E2E fails, guessing is expensive. trace: "retain-on-failure" writes a trace.zip holding the action log, DOM snapshots, network and console. npx playwright show-trace opens it in a viewer; here that would open a window, so a small script unzips it and prints the same events. In CI you'd download the artifact and open it locally.

The scenario: a customer applies a coupon and hits Pay straight away. The test expects $27.00 and gets $30.00. Read the output below from the bottom up. /api/checkout started 21 ms after /api/cart/coupon, the coupon request has status -1 (no response recorded, it was still in flight when the page navigated away), and checkout sent {"cartVersion":1}, the version from before the coupon. So the server had nothing to discount yet. That's a real bug: anyone who clicks fast pays full price.

The tempting fix is waitForTimeout(1500) before Pay. We tried it: the test goes green and the bug stays for every real user. The right fix is in the app: disable Pay while the coupon request is pending. Because click waits for enabled (Part 1), the unchanged test passes 5 of 5, with no sleep anywhere.

Part 5 — What deserves an E2E 🟡 Intermediateالجزء 5 — إيه اللي يستاهل E2E

English

An E2E test proves that the wiring works end to end, so spend it on the flows where broken wiring costs money or trust: signup and login, checkout, and your product's core action. Everything below that bar belongs in a faster layer. A budget makes the rule enforceable. A reasonable one to start with: a handful of flows per product area, the whole suite under 10 minutes in CI, and a flake rate under 1%. These numbers are a starting judgement, not a standard; pick yours and write them down.

The classic waste is an E2E asserting a validation message. We wrote both versions of the same rule: coupon-field.test.tsx (RTL, jsdom) and coupon-validation.spec.ts (browser, server, database). The component test took ≈240 ms on average, including typing eight characters, and ≈2.3 s for the whole Vitest run. The E2E took ≈320 ms per test on a warm worker, and ≈2.9 s for a one-test run with Postgres already up. Those two numbers look close only because this shop is tiny, with no bundle and no SSR. Real pages add seconds per navigation, and each extra validation branch adds another full browser round trip. Worse, the E2E fails for reasons unrelated to the rule.

A rule for deleting E2E tests: remove one when it duplicates a lower-level test, when it isn't on a critical flow, or when it has flaked twice in a month and nobody fixed the cause. A test that's always rerun until green is worse than no test.

قاعدة لمسح الـ E2E: امسحه لما يكرر test في layer أقل، أو لما مش على flow مهم، أو لما عمل flake مرتين في الشهر ومحدش صلّح السبب. Test بيتعاد لحد ما يخضر أوحش من مفيش test.

فين هستخدمه في شغلي؟ في الـ code review: حد ضاف E2E بيتأكد من "Email is required". رد عليه: ده component test بياخد أجزاء من الثانية ومش بيتكسر لو الـ DB وقعت. والـ E2E يفضل على "العميل يقدر يخلص الشراء" من أول الكارت لحد صفحة التأكيد، لأن ده اللي لو وقع الشركة بتخسر فيه فلوس.

Part 6 — Page Object Model 🟡 Intermediateالجزء 6 — الـ Page Object Model

English

A page object wraps a page's locators and actions behind methods named for what the user does: checkout.placeOrder(), not click("#pay"). The payoff is concentrated change. We wrote the same 12 tests twice and renamed the button from "Pay now" to "Place order". Without a page object, 12 lines had to change across the test file; with one, 1 line in CheckoutPage.ts. Until the fix, both suites failed 12 of 12, and each failure waited out the 30 s test timeout on the click (≈98 s wall on 4 workers instead of ≈4 s).

Where should assertions live? This is a real debate. A page object that asserts hides what the test is checking, so keep the assertions of the behaviour under test in the test. A readiness assertion inside a method is fine when it keeps every caller honest, like addKeyboards waiting for the total to update, or expectTotal as a named check. Playwright's own POM guide does the same: its page object has an expect inside a navigation method as a readiness check, while the test's own checks stay in the spec.

The page object becomes a god object when one class holds every page and dozens of methods: split it by screen and by user task instead. Screenplay is a further step, as a concept: instead of pages you model actors who perform tasks and ask questions (actor.attemptsTo(PlaceOrder.withCoupon("SAVE10"))). It reads like the business process and composes well on big suites, at the cost of many small classes. Reach for it only when page objects have stopped scaling.

import { expect, type Locator, type Page } from "@playwright/test";

// صفحة الـ checkout: كل locator في مكان واحد، والـ methods باسم نية المستخدم
export class CheckoutPage {
  private readonly total: Locator;
  private readonly coupon: Locator;
  private readonly applyCoupon: Locator;
  private readonly addKeyboard: Locator;
  private readonly pay: Locator;

  constructor(private readonly page: Page) {
    this.total = page.getByTestId("total");
    this.coupon = page.getByLabel("Coupon");
    this.applyCoupon = page.getByRole("button", { name: "Apply coupon" });
    this.addKeyboard = page.getByRole("button", { name: "Add keyboard" });
    this.pay = page.getByRole("button", { name: "Pay now" });
  }

  async open() {
    await this.page.goto("/cart");
  }

  async addKeyboards(count: number) {
    for (let i = 1; i <= count; i++) {
      await this.addKeyboard.click();
      await expect(this.total).toHaveText(`$${(30 * i).toFixed(2)}`);
    }
  }

  async applyCouponCode(code: string) {
    await this.coupon.fill(code);
    await this.applyCoupon.click();
  }

  async placeOrder() {
    await this.pay.click();
  }

  async expectTotal(text: string) {
    await expect(this.total).toHaveText(text);
  }
}

الـ page object بيلف الـ locators والـ actions بتوع الصفحة ورا methods باسم اللي المستخدم بيعمله: checkout.placeOrder() مش click("#pay"). الفايدة إن التغيير بيتركز في مكان واحد. كتبنا نفس الـ 12 test مرتين وغيّرنا اسم الزرار من "Pay now" لـ "Place order". من غير page object لازم 12 سطر يتغيروا في ملف الـ tests، ومعاه سطر واحد في CheckoutPage.ts. وقبل الإصلاح النسختين فشلوا 12 من 12، وكل failure استنى الـ 30 ثانية timeout على الـ click (≈98 ثانية بدل ≈4).

الـ assertions مكانها فين؟ دي مناقشة حقيقية. الـ page object اللي بيعمل assert بيخبّي الـ test بيتأكد من إيه، فخلّي الـ assertions بتاعة السلوك اللي بتختبره جوه الـ test. assertion جاهزية جوه method تمام لما بتخلي كل اللي بيناديها صادق، زي addKeyboards اللي بتستنى الـ total يتغيّر، أو expectTotal كفحص باسم واضح. والدليل الرسمي بتاع Playwright بيعمل نفس الحكاية: الـ page object فيه expect جوه method تنقّل كفحص جاهزية، وفحوصات الـ test نفسها في ملف الـ spec.

الـ page object بيتحول لـ god object لما class واحد يشيل كل الصفحات وعشرات الـ methods: قسّمه بالشاشة وبالـ user task. والـ Screenplay خطوة أبعد كمفهوم: بدل الصفحات بتعمل actors بيعملوا tasks ويسألوا questions (actor.attemptsTo(PlaceOrder.withCoupon("SAVE10"))). بيتقري زي الـ business process وبيتركب كويس في الـ suites الكبيرة، على حساب classes صغيرة كتير. استخدمه بس لما الـ page objects توقف إنها تكفي.

فين هستخدمه في شغلي؟ الفريق بيغيّر الـ checkout كل sprint، و"Pay now" هتبقى "Place order" و"Confirm and pay" قبل نهاية السنة. لو عندك 40 E2E فيهم نفس الـ selector، كل redesign بقى يوم شغل. CheckoutPage واحد بيخلي التغيير سطر، والـ reviewer يقرا test كأنه خطوات المستخدم.
Trade-off: page objects on a tiny suite Five tests don't need a page object. Inline the locators until you've seen the same one change in three places, then extract it. A page object added too early is indirection with no payoff, and it hides what the test does.
خمس tests مش محتاجين page object. سيب الـ locators inline لحد ما تشوف نفس الـ selector اتغيّر في 3 أماكن، وبعدين اطلعه. الـ page object المبكر مجرد indirection من غير فايدة وبيخبّي الـ test بيعمل إيه.

Cheat sheet · الخلاصة

  • Locators are lazy and strict; default to getByRole. Auto-wait checks visible, stable, receives events, enabled.
  • Never waitForTimeout; use web-first assertions: they wait for the condition, not a guess.
  • test.extend: scope: "worker" for DB and server, test scope for data. Code after await use() runs even on failure.
  • Auth: one setup project per role + storageState; the login flow keeps its own test.
  • Parallel: parallelIndex for a DB per worker, unique data per test. Amdahl caps the speedup; measure the curve.
  • Trace: retain-on-failure or on-first-retry; read actions, API calls, console. Fix the app, not the wait.
  • E2E budget: critical flows only, under 10 minutes, under 1% flake. A validation message is a component test.
  • Page objects: intent-named methods, assertions mostly in the test, split before a god object. Screenplay is a concept for later.
  • CI: retries: process.env.CI ? 2 : 0, report flaky as flaky; video needs Playwright's ffmpeg; validate the YAML.
  • Next: async Server Components can't render; Server Actions are plain functions; request-cycle behaviour is E2E.
بالعامية
  • الـ locators lazy و strict، و getByRole هو الافتراضي. الـ auto-wait بيفحص visible و stable و receives events و enabled.
  • مفيش waitForTimeout، استخدم web-first assertions: بتستنى الشرط مش تخمين.
  • test.extend: scope: "worker" للـ DB والسيرفر، ونطاق test للبيانات. اللي بعد await use() بيشتغل حتى لو الـ test فشل.
  • الـ auth: setup project لكل role و storageState، و الـ login flow له test خاص بيه.
  • الـ parallel: parallelIndex لـ DB لكل worker، و data فريدة لكل test. Amdahl بيحدد سقف التسريع، فقيس المنحنى.
  • الـ trace: retain-on-failure أو on-first-retry، اقرا الأكشنز والـ API calls والـ console. صلّح الـ app، مش الـ wait.
  • E2E budget: الـ flows المهمة بس، تحت 10 دقايق، و flake أقل من 1%. رسالة الـ validation مكانها component test.
  • الـ page objects: methods بأسماء النية، والـ assertions غالبًا في الـ test، وقسّمه قبل ما يبقى god object. و Screenplay مفهوم لبعدين.
  • الـ CI: retries: process.env.CI ? 2 : 0 وبلّغ عن الـ flaky كـ flaky، والـ video محتاج ffmpeg بتاع Playwright، وافحص الـ YAML.
