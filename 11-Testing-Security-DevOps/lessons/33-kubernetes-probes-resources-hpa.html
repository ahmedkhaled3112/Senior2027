Why this matters · ليه ده مهم

English

A Deployment only says what should run. Probes, resource settings and the autoscaler decide how the platform treats your Node process once it's under stress: whether a database blip becomes a restart storm, whether p99 jumps because of a CPU limit, whether a pod dies with no log line. Most Kubernetes incidents a backend engineer gets paged for come from these three settings, and "liveness vs readiness" and "why was my Node pod OOMKilled" are standard senior interview questions.

Nothing here needs a cluster to understand. There's no Docker or kubectl on this machine, so every experiment runs on a labelled stand-in made of real Node processes, and the real manifests are checked against the Kubernetes schema.

Part 1 — Liveness, readiness, startup 🟡 Intermediateالجزء 1 — الـ liveness والـ readiness والـ startup

English

The endpoints themselves were built in 04 · lesson 24, part 6 (/health/live checks only the process, /health/ready checks dependencies), and 04 · lesson 33, part 4 introduced the three probes. Here we measure what the platform does with them.

Each probe has one consequence, and that consequence is the whole lesson:

  • livenessProbe fails → the kubelet kills and restarts the container. It runs for the Pod's whole life. The only correct question is "is this process stuck in a way only a restart fixes?"
  • readinessProbe fails → the Pod is removed from Service endpoints, with no restart. Dependencies belong here, because leaving the load balancer is the right response to "Postgres is down".
  • startupProbe holds off the other two until it passes, so a slow boot isn't mistaken for a hung process. If it never passes, the container is killed.

Put a database check in liveness and the failure mode changes completely. A restart can't fix Postgres, so when the database has a blip, every replica fails the probe at about the same moment and every replica restarts. The experiment below does this for real: three pods, a real Postgres 18 that we stop for 1.5 s and start again, and a stand-in kubelet running the probes every 100 ms. With the check in liveness, all 3 pods restarted and the first successful request after the database returned took about 212 ms. With the check only in readiness, there were 0 restarts, the pods simply left the Service and came back, and the first success took about 65 ms. Each pod here boots in 500 ms; a real one that warms caches and reconnects takes seconds to minutes, and all replicas do it together, so the gap in production is far bigger.

One honest detail: with the default periodSeconds: 10 and failureThreshold: 3, a real cluster would absorb any blip shorter than about 30 s. The stand-in compresses time (100 ms period), so a 1.5 s blip is enough to trigger it. The defect is the same: the outage just has to outlast your probe settings.

// مش بيغطي: الـ scheduler الحقيقي، cgroups، CNI، iptables، ولا signals حقيقية.

import { fork } from 'node:child_process';
import http from 'node:http';

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// الـ probe بينجح بـ 200 بس، وأي timeout أو رفض اتصال يبقى فشل زي الـ kubelet
function probeOk(port, path, timeoutMs) {
  return new Promise((done) => {
    const req = http.get({ host: '127.0.0.1', port, path, timeout: timeoutMs, agent: false }, (res) => {
      res.resume();
      done(res.statusCode === 200);
    });
    req.on('timeout', () => { req.destroy(); done(false); });
    req.on('error', () => done(false));
  });
}

export function createCluster({ script, env = {}, probe = {}, nodes = ['node-a'], placement = 'spread', log = () => {} }) {
  const p = {
    periodMs: 100, timeoutMs: 400, failureThreshold: 3,
    // صفر يعني مفيش startupProbe
    startupFailureThreshold: 50, startupPeriodMs: 100,
    livePath: '/health/live', readyPath: '/health/ready',
    liveness: true, graceMs: 5000, endpointDelayMs: 0,
    ...probe,
  };
  const pods = new Set();
  const cordoned = new Set();
  const stats = { restarts: 0, reasons: {}, evictionsRefused: 0, peakAlive: 0, minReady: Infinity, killedAfterGrace: 0 };
  let seq = 0, rr = 0, stopped = false;
  const t0 = Date.now();
  const note = (msg) => log(`+${String(Date.now() - t0).padStart(5)}ms ${msg}`);

  function pickNode() {
    const free = nodes.filter((n) => !cordoned.has(n));
    if (placement === 'pack') return free[0];
    const load = (n) => [...pods].filter((x) => x.node === n && !x.terminating).length;
    return free.sort((a, b) => load(a) - load(b))[0];
  }

  function launch(pod) {
    const gen = ++pod.gen;
    Object.assign(pod, { port: 0, ready: false, inEndpoints: false });
    pod.child = fork(script, [], {
      env: { ...process.env, ...env, ...pod.env, PORT: '0', VERSION: pod.version, POD_NAME: pod.name },
      stdio: ['ignore', 'ignore', 'ignore', 'ipc'],
    });
    pod.child.on('message', (m) => { if (m?.type === 'listening' && pod.gen === gen) pod.port = m.port; });
    pod.child.on('exit', (code) => {
      if (pod.gen !== gen) return;
      if (pod.terminating || stopped) { pods.delete(pod); note(`${pod.name} exited code=${code}`); return; }
      restart(pod, 'crash');
    });
    probeLoop(pod, gen);
  }

  function restart(pod, why) {
    stats.restarts++;
    stats.reasons[why] = (stats.reasons[why] ?? 0) + 1;
    pod.restarts++;
    note(`${pod.name} restart #${pod.restarts} (${why})`);
    const old = pod.child;
    pod.gen++;
    old.kill();
    if (!stopped) launch(pod);
  }

  // كل pod ليها لوب probes مستقلة بـ period ثابت زي الـ kubelet
  async function probeLoop(pod, gen) {
    const alive = () => pod.gen === gen && !pod.terminating && !stopped;
    let next = Date.now();
    const tick = async (ms) => { next += ms; await sleep(Math.max(0, next - Date.now())); };
    // الـ startupProbe بيقفل الـ liveness والـ readiness لحد ما ينجح
    if (p.startupFailureThreshold > 0) {
      let fails = 0;
      for (;;) {
        await tick(p.startupPeriodMs);
        if (!alive()) return;
        if (pod.port && (await probeOk(pod.port, p.livePath, p.timeoutMs))) break;
        if (!alive()) return;
        if (++fails >= p.startupFailureThreshold) return restart(pod, 'startup');
      }
    }
    let liveFails = 0, readyFails = 0;
    for (;;) {
      await tick(p.periodMs);
      if (!alive()) return;
      const [live, ready] = pod.port
        ? await Promise.all([probeOk(pod.port, p.livePath, p.timeoutMs), probeOk(pod.port, p.readyPath, p.timeoutMs)])
        : [false, false];
      if (!alive()) return;
      readyFails = ready ? 0 : readyFails + 1;
      const nowReady = ready || (pod.ready && readyFails < p.failureThreshold);
      if (nowReady !== pod.ready) note(`${pod.name} ready=${nowReady}`);
      pod.ready = nowReady;
      pod.inEndpoints = nowReady;
      if (p.liveness) {
        liveFails = live ? 0 : liveFails + 1;
        if (liveFails >= p.failureThreshold) return restart(pod, 'liveness');
      }
    }
  }

  function startPod(version, podEnv = {}) {
    const pod = { name: `${version}-${++seq}`, version, env: podEnv, node: pickNode(), gen: 0, restarts: 0, port: 0, ready: false, inEndpoints: false, terminating: false };
    pods.add(pod);
    launch(pod);
    return pod;
  }

  // السباق الحقيقي: شيل الـ endpoint والـ SIGTERM بيحصلوا مع بعض مش بالترتيب
  async function terminate(pod, { hard = false } = {}) {
    pod.terminating = true;
    note(`${pod.name} terminating`);
    if (hard) { pod.inEndpoints = false; pod.child.kill(); return; }
    setTimeout(() => { pod.inEndpoints = false; }, p.endpointDelayMs);
    pod.child.send?.({ type: 'SIGTERM' });
    const deadline = Date.now() + p.graceMs;
    while (pods.has(pod) && Date.now() < deadline) await sleep(10);
    if (pods.has(pod)) { note(`${pod.name} SIGKILL after grace`); stats.killedAfterGrace++; pod.child.kill(); }
  }

  const service = http.createServer((req, res) => {
    const ends = [...pods].filter((x) => x.inEndpoints && x.port);
    if (!ends.length) { res.writeHead(503).end('no endpoints'); return; }
    const pod = ends[rr++ % ends.length];
    const up = http.request({ host: '127.0.0.1', port: pod.port, path: req.url, method: req.method, headers: req.headers, agent: false }, (m) => {
      res.writeHead(m.statusCode, m.headers);
      m.pipe(res);
    });
    up.on('error', () => { if (!res.headersSent) res.writeHead(502).end('upstream error'); else res.destroy(); });
    req.pipe(up);
  });

  const live = () => [...pods].filter((x) => !x.terminating);
  const readyCount = (version) => live().filter((x) => x.ready && (!version || x.version === version)).length;
  async function waitReady(n, version, ms = 20000) {
    const end = Date.now() + ms;
    while (readyCount(version) < n) { if (Date.now() > end) throw new Error('timeout waiting ready'); await sleep(10); }
  }
  function sample() {
    stats.peakAlive = Math.max(stats.peakAlive, live().length);
    stats.minReady = Math.min(stats.minReady, readyCount());
  }

  return {
    pods, stats, startPod, terminate, waitReady, readyCount, live, cordoned, restart,
    async start(replicas, version = 'v1', podEnv = {}) {
      await new Promise((r) => service.listen(0, '127.0.0.1', r));
      for (let i = 0; i < replicas; i++) startPod(version, podEnv);
      return service.address().port;
    },
    // الـ rolling update: على الأكتر replicas+maxSurge شغالين وعلى الأقل replicas-maxUnavailable جاهزين
    async rollout(version, { maxSurge = 1, maxUnavailable = 0 } = {}, podEnv = {}) {
      const replicas = live().length;
      stats.peakAlive = 0; stats.minReady = Infinity;
      const timer = setInterval(sample, 5);
      let made = 0;
      const dying = [];
      for (;;) {
        const old = live().filter((x) => x.version !== version);
        const cur = live().filter((x) => x.version === version);
        if (!old.length && cur.length === replicas && readyCount(version) === replicas) break;
        if (made < replicas && live().length < replicas + maxSurge) { startPod(version, podEnv); made++; continue; }
        if (old.length && readyCount() - 1 >= replicas - maxUnavailable) { dying.push(terminate(old[0])); continue; }
        await sleep(10);
      }
      await Promise.all(dying);
      clearInterval(timer);
    },
    // الـ kubectl drain: بيحاول يـ evict كل pod، والـ PDB بيرد 429 لو هيكسر الـ minAvailable
    async drain(node, { minAvailable = 0 } = {}) {
      cordoned.add(node);
      const victims = live().filter((x) => x.node === node);
      const all = victims.map(async (pod) => {
        while (readyCount() - 1 < minAvailable) { stats.evictionsRefused++; await sleep(50); }
        pod.terminating = true;
        startPod(pod.version, pod.env);
        await terminate(pod);
      });
      await Promise.all(all);
    },
    // عطل مفاجئ في node: مفيش eviction ومفيش grace والـ PDB ملوش دور هنا
    failNode(node) {
      cordoned.add(node);
      for (const pod of live().filter((x) => x.node === node)) { startPod(pod.version, pod.env); terminate(pod, { hard: true }); }
    },
    kill() {
      stopped = true;
      for (const x of pods) { x.terminating = true; x.child.kill(); }
      service.closeAllConnections?.();
      service.close();
    },
  };
}
بالعامية

الـ endpoints نفسها عملناها في 04 · درس 24، الجزء 6 (الـ /health/live بيبص على الـ process بس، والـ /health/ready بيبص على الـ dependencies)، و04 · درس 33، الجزء 4 عرّفنا فيه التلات probes. هنا هنقيس الـ platform بتعمل بيها إيه.

كل probe ليها نتيجة واحدة، والنتيجة دي هي الدرس كله:

  • livenessProbe يفشل ← الـ kubelet بيقتل الـ container ويعمله restart. وده شغال طول عمر الـ Pod. السؤال الصح الوحيد: "الـ process ده واقف بطريقة الـ restart بس هو اللي يصلّحها؟"
  • readinessProbe يفشل ← الـ Pod بتتشال من الـ Service endpoints من غير restart. الـ dependencies مكانها هنا، لأن الخروج من الـ load balancer هو الرد الصح على "Postgres واقع".
  • startupProbe بيأجّل الاتنين التانيين لحد ما ينجح، عشان البوت البطيء ميتفهمش إن الـ process واقف. لو عمره ما نجح، الـ container بيتقتل.

Interview question (exit test Q11) "Liveness vs readiness: what happens if you mix them up?" → Liveness failure restarts the container; readiness failure removes the Pod from Service endpoints with no restart. Put a dependency check in liveness and a database blip restarts every replica at once, so a small outage becomes a restart storm with a reconnect herd. Put nothing in readiness and a Pod that can't reach its database keeps receiving traffic and returns errors. Dependencies go in readiness, only process health goes in liveness, and slow boots go in a startupProbe.
"Liveness vs readiness: إيه اللي بيحصل لو لخبطتهم؟" ← فشل الـ liveness بيعمل restart للـ container، وفشل الـ readiness بيشيل الـ Pod من الـ Service endpoints من غير restart. لو حطيت check لـ dependency في الـ liveness، وقفة صغيرة في الـ DB هتعمل restart لكل الـ replicas مرة واحدة، فـ outage صغير يتحول لعاصفة restarts مع زحمة reconnects. ولو مفيش dependency check في الـ readiness، Pod مش عارفة توصل للـ DB هتفضل تاخد traffic وترجّع errors. يبقى الـ dependencies في الـ readiness، وصحة الـ process بس في الـ liveness، والبوت البطيء في الـ startupProbe.

Part 2 — Probe timing 🟡 Intermediateالجزء 2 — توقيت الـ probes

English

A probe has four numbers, with these defaults: periodSeconds: 10, timeoutSeconds: 1, failureThreshold: 3, initialDelaySeconds: 0. Together they decide two things you should always compute.

Worst-case detection is the time from "the process hung right after a successful probe" to "the kubelet acts": failureThreshold × periodSeconds + timeoutSeconds. With the defaults that's 3 × 10 + 1 = 31 s. In the stand-in, 150 ms timeout × 3 at a 200 ms period gives a formula value of 750 ms, and six real hangs measured 644 to 751 ms.

Startup budget is failureThreshold × periodSeconds. A startupProbe of 24 × 5 s allows 120 s to boot. Set it from your slowest real boot (cold image pull, cache warmup, migrations you run before listening). Don't use a large initialDelaySeconds on liveness for this: it delays every boot by the full amount, while a startupProbe releases as soon as the app is up.

Too tight kills you under load. A probe goes through the same event loop as your requests. In the run below each request burns 40 ms of CPU with 30 clients on 3 pods, so a request queue around 400 ms is normal. A 100 ms timeout looks hung: the pods got 12 restarts, and 863 of 986 requests failed, because each restart moved the load to the survivors and made their probes fail too. That's the feedback loop. With a 1500 ms timeout on the same load: 0 restarts, 0 failures. The fix for overload is more capacity or shedding, never a stricter probe.

What breaks at scale: the probe path Keep liveness trivial and fast, because it runs on every replica forever, and at 200 pods and a 10 s period that's 20 requests per second of pure overhead. And never let a shared dependency or a slow middleware sit in front of it: auth, logging sinks and rate limiters have turned probes into outages.

Part 3 — CPU requests and limits 🟡 Intermediateالجزء 3 — الـ CPU requests والـ limits

English

A request does two jobs. The scheduler uses it to place the Pod on a node with enough unreserved capacity, and on a busy node it's a weighting: when containers compete, larger requests get proportionally more CPU. You can use more than your request whenever the node has spare CPU.

A limit is a hard ceiling, enforced by the Linux CFS bandwidth controller with quotas per period, 100 ms by default (kernel docs). A cpu: 500m limit means 50 ms of CPU time per 100 ms period, summed over all threads in the container. Once the quota is gone, every thread freezes until the next period. There's no error and no log line: requests just take longer, which is why CPU throttling is so often misdiagnosed as a slow database.

Node is more than one thread. The JS event loop is one, but V8's garbage collector and compiler and the libuv pool run alongside it. In the run below, an allocation-heavy loop used about 2124m on a 2 s wall clock, more than two cores' worth. So a 500m limit can be exhausted by a GC burst that your "single-threaded" mental model doesn't predict.

Averages hide this. The stand-in below (a process that freezes itself when its quota runs out, labelled) has an average demand of 320m. Under a 500m limit p99 went from 23 ms to 38 ms, with 4 of 40 periods throttled. Under a 350m limit, still above the average, p99 hit 152 ms, 6.6 times the unlimited value, with 24 of 41 periods throttled and about 1057 ms spent frozen. Event-loop delay p99 went from 23 ms to 106 ms. A dashboard showing "CPU at 90% of limit" looks fine while users wait.

You can change these values without restarting: in-place Pod resize is GA since Kubernetes 1.35, using the Pod's resize subresource. CPU resizes are the safe direction. Memory has the rules you'd expect (lowering memory below current usage is refused on a best-effort basis).

import { monitorEventLoopDelay } from 'node:perf_hooks';

const PERIOD_MS = 100;
const limitM = Number(process.env.CPU_LIMIT_M ?? 0);
const burnMs = Number(process.env.BURN_MS ?? 8);
// الـ 500m معناها 50ms شغل في كل 100ms
const quotaMs = (limitM / 1000) * PERIOD_MS;

let win = -1, used = 0, active = 0, throttled = 0, frozenMs = 0;
const gate = new Int32Array(new SharedArrayBuffer(4));

function enterWindow() {
  const w = Math.floor(performance.now() / PERIOD_MS);
  if (w !== win) { win = w; used = 0; active++; }
}

function burn(ms) {
  let left = ms;
  while (left > 0) {
    enterWindow();
    const slice = Math.min(left, 0.25);
    const end = performance.now() + slice;
    while (performance.now() < end);
    left -= slice;
    used += slice;
    if (limitM && used >= quotaMs) {
      // الـ quota خلص: كل حاجة بتتجمد لحد أول الـ period الجاي
      const wait = (win + 1) * PERIOD_MS - performance.now();
      if (wait > 0) { throttled++; frozenMs += wait; Atomics.wait(gate, 0, 0, wait); }
    }
  }
}

  return () => { a |= 0; a = (a + 0x6d2b79f5) | 0; let t = Math.imul(a ^ (a >>> 15), 1 | a); t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t; return ((t ^ (t >>> 14)) >>> 0) / 4294967296; };
}

Trade-off: CPU limit or no CPU limit? No limit means no surprise throttling and better p99, because idle CPU on the node gets used; the risk is a noisy neighbour, and that a pod which never saw a limit in staging behaves differently in production. A limit gives predictable, isolated performance at the cost of throttling. Common practice for Node APIs: set a CPU request from measurements and either no CPU limit or a limit well above it (for example 2 to 4 times the request). A memory limit is different: always set one, because memory isn't compressible. If your platform demands Guaranteed QoS, set requests equal to limits for both CPU and memory, and size CPU for the peak.

Part 4 — Memory and OOMKilled 🟡 Intermediateالجزء 4 — الـ memory والـ OOMKilled

English

A memory limit counts the whole container's memory (close to RSS), not the V8 heap. Exceed it and the kernel kills the container with SIGKILL: exit code 137, reason OOMKilled in lastState, and no JavaScript stack trace at all. 04 · lesson 33, part 4 covered why the heap isn't your memory; here we reproduce the failures.

First, a flag isn't the number you think. --max-old-space-size=128 gives a heap_size_limit of 176 MB, because V8 adds its young generation on top (about 48 MB in every run below).

Then the three outcomes that matter, from one stand-in kubelet that reads the child's RSS and SIGKILLs it past 256 MiB (the kill and the 137 are the stand-in's; the heap, RSS, and exit 134 are real):

  • Heap flag above the limit (--max-old-space-size=512, limit 256): a leak reaches the limit at 180 MB of heap, RSS 256 MB, and it's a silent kill. V8 never hits its own limit, so you get no error at all. This is the README's "why Node gets killed".
  • Heap flag below the limit (--max-old-space-size=128, same leak): V8 stops first at 124 MB of heap, with a real FATAL ERROR: Reached heap limit and exit 134. You lose the pod either way, but now the log says exactly what happened.
  • Off-heap Buffers (heap 128, limit 256): heapUsed stays at 4 MB while RSS reaches 258 MB through 208 MB of arrayBuffers. A perfect heap flag can't help: Buffers, streams with large highWaterMarks, native addons and thread stacks all count.

The usual causes, in the order to check them: (1) heap flag at or above the limit, or no flag so V8 picks a default from the memory it detects (see the Node lesson), (2) off-heap buffers: uploads, compression, large response bodies, (3) a genuine leak, where heap grows without flattening between GCs, (4) native addons or too many worker threads. Set the heap from measurement: the rest of the container (Buffers, stacks, code, native) needs real room, so a common starting point is about 75% of the limit, then lower it if your overhead outside the heap is bigger, as Part 6 does.

Part 5 — The Horizontal Pod Autoscaler 🟡 Intermediateالجزء 5 — الـ Horizontal Pod Autoscaler

English

The HPA control loop (every 15 s by default) reads a metric and applies desiredReplicas = ceil(currentReplicas × currentMetricValue / desiredMetricValue). A ratio within the tolerance (10% by default, and per-HPA configurable: the tolerance field reached stable in Kubernetes 1.37) causes no action. Capacity reasoning for choosing these numbers is in 10 · lesson 41.

Three rules from the docs matter in practice. CPU utilization is measured against the request, so if a container in the Pod has no request, CPU utilization is undefined and the autoscaler doesn't act on that metric. Pods with missing metrics count as 0% on a scale up and 100% on a scale down, and not-yet-ready pods count as 0% on a scale up, which avoids flapping on startup CPU spikes. And scale-down has a default stabilizationWindowSeconds: 300: the HPA picks the highest recommendation from the last 5 minutes before removing pods, while scale-up has no window but is rate-limited (default: add up to 100% or 4 pods per 15 s, whichever is more).

The stand-in implements the formula on real processes, real CPU from process.cpuUsage() and real open-loop traffic, on a compressed clock (sync every 400 ms). Going from 20 to 100 requests per second took it from 1 to 8 pods (capped by maxReplicas) within 1.6 s, and back down over the next seconds. The jump to 8 overshot, because new pods were still warming up and the per-pod CPU read high, so it corrected to 6 at 4.5 s even before the load dropped at 6 s; the real HPA sets aside not-yet-ready pods for this reason. Without stabilization, a square-wave load caused 18 scale events and 26 pods launched in 10 s: pods start, take their share, get removed, restart. With a 2.5 s window: 6 events and 8 pods launched.

Memory-based HPA is usually wrong for Node. V8 doesn't return heap to the OS eagerly, so memory stays high after the load ends and the HPA won't scale down. Use CPU, or a per-Pod workload metric. For workers, the number that matters is queue depth: type: Pods or External metrics reach the HPA through an adapter (Prometheus Adapter, etc). KEDA packages that for common sources like Redis lists, and can scale to zero. Native HPA minReplicas: 0 also exists (HPAScaleToZero, beta in 1.37) but only with object or external metrics, since CPU can't be measured on zero pods.

// خوارزمية الـ HPA من الـ ⁦docs: ceil(currentReplicas × currentMetric / targetMetric)⁩ مع tolerance
export function desiredReplicas({ current, metric, target, tolerance = 0.1 }) {
  const ratio = metric / target;
  // جوه الـ tolerance مفيش أي scaling خالص
  if (Math.abs(ratio - 1) <= tolerance) return current;
  return Math.ceil(current * ratio);
}

// الـ stabilization: في الـ scale down بناخد أعلى recommendation في آخر windowMs
export function createStabilizer(windowMs) {
  const recs = [];
  return (desired, current, now) => {
    recs.push({ at: now, desired });
    while (recs.length && recs[0].at < now - windowMs) recs.shift();
    if (desired >= current) return desired;
    return Math.min(current, Math.max(...recs.map((r) => r.desired)));
  };
}

  http.get({ host: '127.0.0.1', port: pod.port, path: '/cpu', agent: false, timeout: 300 }, (res) => {
    let b = ''; res.on('data', (d) => (b += d));
    res.on('end', () => { const c = JSON.parse(b); done((c.user + c.system) / 1000); });
  }).on('error', () => done(null)).on('timeout', function () { this.destroy(); done(null); });
});

async function run(label, { rateAt, durationMs, stabilizeMs }) {
  const c = createCluster({ script, env: { BURN_MS: '5' }, probe: { timeoutMs: 1500 } });
  const port = await c.start(1);
  await c.waitReady(1);
  const stabilize = createStabilizer(stabilizeMs);
  const last = new Map();
  const t0 = Date.now();
  const timeline = [];
  let events = 0, launched = 0, sent = 0, failed = 0, stop = false;

  // ضغط حقيقي (open loop) على الـ Service بمعدل بيتغير مع الوقت
  const driver = (async () => {
    let debt = 0;
    while (!stop) {
      const rate = rateAt(Date.now() - t0);
      debt += rate * 0.02;
      while (debt >= 1) {
        debt--; sent++;
        http.get({ host: '127.0.0.1', port, path: '/work', agent: false, timeout: 2000 }, (res) => {
          res.resume(); if (res.statusCode !== 200) failed++;
        }).on('error', () => failed++).on('timeout', function () { this.destroy(); });
      }
      await sleep(20);
    }
  })();

  let sum = 0, syncs = 0;
  while (Date.now() - t0 < durationMs) {
    await sleep(SYNC_MS);
    const pods = c.live().filter((x) => x.ready);
    if (!pods.length) continue;
    const millis = [];
    for (const pod of pods) {
      const v = await cpuOf(pod);
      const now = Date.now();
      const prev = last.get(pod.name);
      last.set(pod.name, { v, now });
      if (prev && v !== null) millis.push(((v - prev.v) / (now - prev.now)) * 1000);
    }
    if (!millis.length) continue;
    const metric = millis.reduce((a, b) => a + b, 0) / millis.length;
    const current = c.live().length;
    const raw = desiredReplicas({ current, metric, target: TARGET_M });
    const bounded = Math.min(MAX, Math.max(MIN, stabilizeMs ? stabilize(raw, current, Date.now()) : raw));
    sum += current; syncs++;
    if (bounded !== current) {
      events++;
      timeline.push(`t=${((Date.now() - t0) / 1000).toFixed(1)}s ${current}->${bounded} (avg ${Math.round(metric)}m)`);
      if (bounded > current) { for (let i = current; i < bounded; i++) { c.startPod('v1'); launched++; } }
      else for (const pod of c.live().slice(0, current - bounded)) c.terminate(pod);
    }
  }
  stop = true;
  await driver;
  await sleep(300);
  console.log(`\n${label}`);
  console.log(timeline.join('\n'));
  console.log(`scale events: ${events}, pods launched: ${launched}, avg replicas ≈${(sum / syncs).toFixed(1)}, requests: ${sent}, failed: ${failed}`);
  c.kill();
  await sleep(300);
}

تلات قواعد من الـ docs مهمين عمليًا. الـ CPU utilization بيتقاس بالنسبة للـ request، فلو container في الـ Pod مفيهوش request، الـ utilization مش متعرف والـ autoscaler مش بيتحرك على الـ metric ده. الـ pods اللي الـ metrics بتاعتها ناقصة بتتحسب 0% في الـ scale up و100% في الـ scale down، والـ pods اللي لسه مش ready بتتحسب 0% في الـ scale up، وده بيمنع التقلب بسبب CPU الـ startup. والـ scale down له stabilizationWindowSeconds: 300 بالـ default: الـ HPA بياخد أعلى recommendation في آخر 5 دقايق قبل ما يشيل pods، بينما الـ scale up مفيش له window بس عليه حد معدل (الـ default: زيادة لحد 100% أو 4 pods كل 15 ثانية، أيهم أكبر).

What breaks at scale: scaling chases the bottleneck More pods mean more connections, and past a point the bottleneck is Postgres, not your API. If you scale from 3 to 30 pods with a pool of 10 each, you ask for 300 connections on a database that might allow 100. Before raising maxReplicas, multiply it by the pool size (or use a pooler like PgBouncer, section 07). Remember also that HPA reacts over minutes: for a sudden spike you need headroom or a queue in front.

Part 6 — Setting real values 🟡 Intermediateالجزء 6 — تحديد القيم الحقيقية

English

Stop guessing numbers: the method is load test → observe → set requests → set limits → repeat.

  1. Load test one pod at your target traffic (autocannon here; k6 is in lesson 10). Skip the first second, when the JIT warms up.
  2. Observe p95 CPU, peak RSS and peak heap. Under load, RSS and heap tell you how much lives outside the heap.
  3. Set requests: CPU request from measured p95 with a margin. Memory request equal to the memory limit, so a node under pressure doesn't evict you first.
  4. Set limits: memory limit from peak RSS × 1.5 (never below a floor like 256Mi). Heap below the limit, using what you measured. CPU limit as discussed in Part 3.

The script below does exactly that on a real process: 100 req/s measured at p95 ≈ 502m and peak RSS 66 Mi, which gives a 650m CPU request, a 256 Mi limit and a 168 Mi heap (overhead outside the heap measured 56 Mi). It generates the manifest from those numbers, validates it against the Kubernetes schema and writes it out. Numbers are from this Windows machine; on Linux containers measure again.

VPA. A VerticalPodAutoscaler (docs) recommends or applies requests from observed use, and with in-place resize its InPlaceOrRecreate mode can do so without evicting the Pod where possible. It's a good way to get a recommendation (mode Off), but avoid running it in an applying mode against the same CPU metric the HPA uses, because they'll fight. It's an add-on you must install, and it needs metrics-server.

  1. Load test لـ pod واحدة على الـ traffic المستهدف (هنا autocannon، و k6 في الدرس 10). وسيب أول ثانية عشان الـ JIT بيسخن.
  2. Observe: الـ CPU p95 وأعلى RSS وأعلى heap. تحت الضغط الـ RSS والـ heap بيقولولك قد إيه عايش بره الـ heap.
  3. حدد الـ requests: الـ CPU request من الـ p95 المقاس بهامش. والـ memory request زي الـ memory limit عشان الـ node لما تضغط ما تطردكش الأول.
  4. حدد الـ limits: الـ memory limit من أعلى RSS × 1.5 (ومش أقل من 256Mi مثلًا). الـ heap تحت الـ limit بالقياس. والـ CPU limit زي ما اتكلمنا في الجزء 3.

السكريبت فوق بيعمل كده بالظبط على process حقيقي: عند 100 req/s طلع p95 حوالي 502m و RSS 66Mi، فجابلنا CPU request بـ 650m، و limit 256Mi، و heap 168Mi (والـ overhead بره الـ heap 56Mi). وبيولّد الـ manifest من الأرقام دي، ويتحقق منه على schema بتاع Kubernetes ويكتبه. الأرقام من الجهاز ده (Windows)، ولازم تقيس تاني جوه Linux container.

الـ VPA. الـ VerticalPodAutoscaler (docs) بيقترح أو يطبق requests من الاستهلاك الفعلي، ومع الـ in-place resize الـ mode بتاعه InPlaceOrRecreate بيعملها من غير eviction لو ينفع. استخدمه كويس لجلب توصية (mode Off)، بس متشغلهوش في mode بيطبق على نفس الـ CPU metric اللي الـ HPA شغال عليه، عشان هيتخانقوا. وده add-on لازم تسطّبه ومحتاج metrics-server.

فين هستخدمه في شغلي؟ قبل ما تدخل orders-api الـ production أول مرة: شغّل load test بالـ traffic المتوقع (مثلًا 100 req/s لكل pod)، قِس الـ CPU p95 والـ RSS، وولّد القيم. واكتب الأرقام دي في الـ ADR بتاع الـ deploy. لما حد بعد 6 شهور يسأل "ليه 650m؟" يلاقي قياس مش تخمين، ومعاك إجراء لو الـ traffic اتغير.
Interview question "How do you choose CPU and memory requests for a new service?" → Don't guess. Load test one replica at the target traffic, measure p95 CPU and peak RSS, set the CPU request from that with a margin and the memory limit from peak RSS with headroom, and keep the heap below the limit so a leak gives you a V8 error. Revisit after real traffic, because staging traffic is never the real shape.
"بتختار الـ CPU والـ memory requests إزاي لـ service جديدة؟" ← متخمّنش. اعمل load test لـ replica واحدة على الـ traffic المستهدف، قِس الـ CPU p95 وأعلى RSS، حدد الـ CPU request منهم بهامش، والـ memory limit من أعلى RSS بـ headroom، وخلّي الـ heap تحت الـ limit عشان الـ leak يدّيك V8 error. وراجع بعد الـ traffic الحقيقي، لأن الـ traffic في staging عمره ما بيبقى زي الحقيقي.

Common mistakes · غلطات شائعة

❌ Database check in liveness 
livenessProbe:
  httpGet: { path: /health/ready, port: http }
  # الـ endpoint ده بيعمل SELECT 1 ولما الـ DB تقع كله يعمل restart
✅ Dependencies only in readiness 
livenessProbe:
  httpGet: { path: /health/live, port: http }
readinessProbe:
  httpGet: { path: /health/ready, port: http }
  # لو الـ DB وقعت الـ pod بتخرج من الـ Service من غير restart
بالعامية

❌ الـ liveness بيضرب على endpoint بيسأل عن الـ DB، فوقفة في Postgres بتعمل restart لكل الـ replicas مرة واحدة زي ما قسنا. ✅ الـ liveness بيسأل عن الـ process بس، والـ readiness هو اللي بيسأل عن الـ DB، فالـ pod بتخرج من الـ Service ومفيش restart.

❌ initialDelaySeconds for slow boots 
livenessProbe:
  initialDelaySeconds: 120
  # كل boot بيستنى دقيقتين، وأي hang في البوت مش هيتكشف
✅ A startupProbe with a budget 
startupProbe:
  httpGet: { path: /health/live, port: http }
  periodSeconds: 5
  failureThreshold: 24
  # ميزانية 120 ثانية وبيعدّي أول ما الـ app يقوم
بالعامية

❌ initialDelaySeconds: 120 بيأخر كل boot دقيقتين كاملين، حتى لو الـ app قام في 10 ثواني، وأي hang جوه الـ window دي مش هيتشاف. ✅ الـ startupProbe بـ 24 × 5 ثواني بيدّي نفس الميزانية بس بيعدّي أول ما الـ app يبقى جاهز.

❌ Heap flag above the limit 
env:
  - { name: NODE_OPTIONS, value: --max-old-space-size=1024 }
resources:
  limits: { memory: 512Mi }
  # الـ V8 فاكر إن عنده 1GB والـ kernel هيقتله عند 512
✅ Heap below the limit, with a margin 
env:
  - { name: NODE_OPTIONS, value: --max-old-space-size=384 }
resources:
  limits: { memory: 512Mi }
  # الـ V8 بيقف الأول ويدي FATAL ERROR واضح في الـ logs
بالعامية

❌ الـ flag (1024) أكبر من الـ limit (512Mi): الـ leak توصل الـ limit والـ kernel يقتلها بـ 137 من غير ولا سطر، زي الصف الأول في تجربة الجزء 4. ✅ الـ 384 (75%) تحت الـ limit، فالـ V8 يقف بـ FATAL ERROR واضح، ومساحة للـ Buffers. لو الـ overhead بره الـ heap عندك أكبر، قلّل كمان.

❌ HPA with no CPU request 
resources: {}
---
metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 60 }
# من غير request الـ utilization مش متعرف والـ HPA مش بيتحرك
✅ A measured request first 
resources:
  requests: { cpu: 650m, memory: 256Mi }
  limits: { memory: 256Mi }
---
metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 60 }
بالعامية

❌ الـ utilization نسبة من الـ request، فلو مفيش request الـ CPU utilization مش متعرف، والـ HPA مش بيعمل حاجة على الـ metric ده، وكل واحد فاكر إن الـ autoscaling شغال. ✅ حط request من القياسات، وبعدها الـ HPA عنده أساس يحسب عليه.

Try it yourself · جرّب بنفسك

1. Calculate the budgets 🟢 easy Write detectSeconds(probe) and startupBudget(probe), then compute worst-case detection for a liveness probe with period 5 s, threshold 6, timeout 2 s, and the startup budget for 24 × 5 s.
اكتب detectSeconds(probe) و startupBudget(probe)، واحسب أسوأ وقت اكتشاف لـ liveness بـ period 5 ثواني و threshold 6 و timeout 2 ثانية، وميزانية الـ startup لـ 24 × 5 ثواني.
Solution · الحل
الحل تحت مع التمرين التاني والتالت في نفس الملف، وطلع من تشغيل حقيقي. وقت الاكتشاف = failureThreshold × period + timeout، يعني 32 ثانية، وميزانية الـ startup 120 ثانية.
// حلول تمارين الدرس 33، والنتايج اللي تحت طالعة من تشغيل حقيقي
import assert from 'node:assert/strict';

// تمرين 1: وقت الاكتشاف وميزانية الـ startup
const detectSeconds = ({ periodSeconds, failureThreshold, timeoutSeconds }) => failureThreshold * periodSeconds + timeoutSeconds;
const startupBudget = ({ periodSeconds, failureThreshold }) => periodSeconds * failureThreshold;
console.log('defaults detection:', detectSeconds({ periodSeconds: 10, failureThreshold: 3, timeoutSeconds: 1 }), 's');
console.log('custom detection:', detectSeconds({ periodSeconds: 5, failureThreshold: 6, timeoutSeconds: 2 }), 's');
console.log('startup budget:', startupBudget({ periodSeconds: 5, failureThreshold: 24 }), 's');

// تمرين 2: الـ heap من القياسات
function recommendHeap(limitMi, overheadMi, marginMi = 32) {
  const heap = Math.floor(Math.min(limitMi * 0.75, limitMi - overheadMi - marginMi));
  if (heap < 64) throw new Error('memory limit too small for this overhead');
  return heap;
}
assert.equal(recommendHeap(256, 56), 168);
assert.equal(recommendHeap(512, 56), 384);
assert.equal(recommendHeap(512, 300), 180);
assert.throws(() => recommendHeap(128, 100));
console.log('recommendHeap: 4 assertions passed');

// تمرين 3: policy بتسمح بالضعف بس في كل مرة، زي الـ Percent 100
function limitScaleUp(current, desired, maxPercent = 100, minPods = 4) {
  const limit = current + Math.max(Math.ceil((current * maxPercent) / 100), minPods);
  return Math.min(desired, limit);
}
assert.equal(limitScaleUp(2, 30), 6);
assert.equal(limitScaleUp(10, 30), 20);
assert.equal(limitScaleUp(10, 12), 12);
console.log('limitScaleUp: 3 assertions passed');
defaults detection: 31 s
custom detection: 32 s
startup budget: 120 s
recommendHeap: 4 assertions passed
limitScaleUp: 3 assertions passed
النتايج: 31 ثانية للـ defaults، 32 ثانية للـ config ده، و 120 ثانية للـ startup. والـ assertions بتاعة التمرينين التانيين عدّت.
2. A heap calculator 🟡 medium Write recommendHeap(limitMi, overheadMi, marginMi = 32) that returns the smaller of 75% of the limit and the limit minus overhead and margin. It throws if the result is below 64 Mi. Test with limits of 256 and 512.
اكتب recommendHeap(limitMi, overheadMi, marginMi = 32) اللي بترجع الأقل بين 75% من الـ limit والـ limit ناقص الـ overhead والـ margin، وترمي error لو النتيجة أقل من 64Mi. اختبرها على limits بـ 256 و 512.
Hint · تلميح
استخدم Math.min و Math.floor، وارمي error صريح بدل ما ترجع رقم مش منطقي. الحل موجود في التمرين الأول في نفس الملف.
3. Scale-up rate limit 🔴 hard The stand-in HPA jumped from 3 to 8 pods in one step. Implement limitScaleUp(current, desired) that applies the default rule: add at most max(100% of current, 4 pods) per period. Then add it to the HPA loop in t-hpa.mjs and compare the scale-up steps.
الـ HPA الـ stand-in نط من 3 لـ 8 pods في خطوة واحدة. نفّذ limitScaleUp(current, desired) اللي بتطبق القاعدة الـ default: زيادة بأقصى max(100% من الحالي, 4 pods) في كل period. ضيفها على لوب الـ HPA في t-hpa.mjs وقارن خطوات الـ scale up.
Solution · الحل
الدالة في الملف فوق (التمرين الأول). عند current = 2 و desired = 30 بتطلع 6، يعني 2 + max(2, 4). جرّب تحطها بين raw و bounded في الـ t-hpa.mjs وهتشوف الخطوات أهدى.
4. In your project / at work 🔴 project In your side project's Helm chart (README artifact 10): add the three probes, measured resources and an HPA. Load test one pod with autocannon, write the numbers in the chart's values-prod.yaml, deploy it on a local kind or k3d cluster when you have one, and write down how many restarts a kubectl delete pod of Postgres causes.
في الـ Helm chart بتاع مشروعك الجانبي (الـ artifact رقم 10 في الـ README): ضيف التلات probes و resources مقاسة و HPA. اعمل load test لـ pod واحدة بـ autocannon، واكتب الأرقام في values-prod.yaml، وانشره على cluster محلي بـ kind أو k3d لما يبقى عندك، واكتب كام restart هيحصل لو عملت kubectl delete pod لـ Postgres.
Hint · تلميح
لو الـ restarts زادت لما Postgres وقع، يبقى الـ liveness بتاعك لسه بيعدّي على الـ DB. ارجع لـ /health/live بتاع الدرس 24 في قسم Node، واتأكد إنه مش بيعمل أي query.

Cheat sheet · الخلاصة

  • Liveness fails → restart. Readiness fails → out of the Service, no restart. Startup gates the other two. Dependencies go only in readiness.
  • Worst-case detection = failureThreshold × period + timeout. Startup budget = failureThreshold × period.
  • A probe shares the event loop with requests: too tight a timeout under load is a restart loop.
  • CPU request: scheduling and weight. CPU limit: CFS quota per 100 ms, summed over all threads. Throttling shows in p99, not in averages or logs.
  • In-place Pod resize is GA since Kubernetes 1.35.
  • OOMKilled = exit 137 from the kernel, no JS stack. FATAL ERROR: Reached heap limit = exit 134 from V8, stack in logs.
  • RSS counts Buffers; --max-old-space-size doesn't limit them. heap_size_limit ≈ flag + 48 MB (measured here).
  • HPA: ceil(current × metric / target), 10% tolerance, 300 s scale-down stabilization, CPU % is relative to the request.
  • Memory-based HPA rarely scales a Node service down. Workers scale on queue depth (custom metrics or KEDA).
  • Method: load test → observe p95 CPU and peak RSS → requests → limits. Keep the numbers in the ADR.
بالعامية
  • الـ liveness يفشل ← restart. الـ readiness يفشل ← برا الـ Service من غير restart. الـ startup بيقفل الاتنين التانيين. والـ dependencies مكانها الـ readiness بس.
  • أسوأ وقت اكتشاف = failureThreshold × period + timeout. وميزانية الـ startup = failureThreshold × period.
  • الـ probe بتشارك الـ event loop مع الـ requests: timeout ضيق تحت الضغط يبقى restart loop.
  • الـ CPU request: للـ scheduling وللـ weight. والـ CPU limit: CFS quota كل 100ms محسوب على كل الـ threads. والـ throttling بيبان في الـ p99 مش في الـ averages ولا الـ logs.
  • الـ in-place Pod resize بقى GA من Kubernetes 1.35.
  • الـ OOMKilled هو exit 137 من الـ kernel من غير JS stack. والـ FATAL ERROR: Reached heap limit هو exit 134 من V8 ومعاه stack في الـ logs.
  • الـ RSS بيحسب الـ Buffers، و --max-old-space-size مبيحددهاش. والـ heap_size_limit حوالي الـ flag + 48MB (مقاس هنا).
  • الـ HPA: ceil(current × metric / target)، و tolerance 10%، و stabilization 300 ثانية للـ scale down، والـ CPU % نسبة من الـ request.
  • الـ HPA على الـ memory نادرًا ما بينزّل service بتاعة Node. والـ workers بيعملوا scale على عمق الـ queue (custom metrics أو KEDA).
  • الطريقة: load test ← observe لـ CPU p95 وأعلى RSS ← requests ← limits، واكتب الأرقام في الـ ADR.
