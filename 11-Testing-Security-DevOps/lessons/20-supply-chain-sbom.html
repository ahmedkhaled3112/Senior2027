Why this matters · ليه ده مهم

English

Most of the code you ship was written by people you've never met, and it runs with the same privileges as yours. Software Supply Chain Failures is A03 in the OWASP Top 10:2025. In a Node shop this is daily work: every npm install, every bot PR, every release pipeline is a decision about whom you trust.

The ground also moved recently. npm 12 stopped running dependency install scripts by default, a cooldown setting now exists, and classic tokens are gone. So the advice you may remember is partly out of date, and interviewers increasingly ask what you'd do after the next worm.

بالعامية

معظم الكود اللي بتشحنه كتبه ناس عمرك ما قابلتهم، وبيشتغل بنفس صلاحيات كودك. الـ Software Supply Chain Failures هي A03 في OWASP Top 10:2025. وفي شغل Node ده بيحصل كل يوم: كل npm install، وكل PR من bot، وكل release pipeline هو قرار بتاخده: بتثق في مين؟

وكمان الدنيا اتغيرت قريب: npm 12 بطّل يشغّل install scripts بتاعة الـ dependencies افتراضيًا، وبقى فيه cooldown setting، والـ classic tokens راحت. فالنصايح اللي فاكرها ممكن تكون قديمة جزئيًا، والـ interviewers بقوا يسألوا هتعمل إيه بعد الـ worm الجاي.

Part 1 — Why npm is the biggest risk 🟡 Intermediateالجزء 1 — ليه npm أكبر مصدر خطر

English

Four attack shapes account for most of it. Typosquatting publishes a name close to a popular one and waits for a slip. Dependency confusion publishes your internal package name on a public registry with a higher version. Malicious install scripts run during npm install, before any of your code. Maintainer account takeover publishes a bad version of a package you already trust, which is the hardest of the four, because nothing about the name looks wrong.

Two recent incidents show the scale. In September 2025, CISA described a self-replicating worm known as Shai-Hulud that compromised over 500 npm packages: it harvested credentials and used stolen npm tokens to publish itself into more packages. In March 2026, an attacker force-pushed malicious code onto most version tags of aquasecurity/trivy-action (CVE-2026-33634, GHSA-69fq-xp46-6x23; Aqua's count is 76 of 77 tags, Snyk and Wiz report 75 of 76). The credential stealer ran before the real scan, so the logs looked normal. A security tool was the entry point, and a mutable tag was the mechanism.

Your exposure is the size of the tree, not the size of package.json. In this lesson's sample, 5 direct dependencies pulled in 79 packages, each with its own maintainers. The lab below reproduces dependency confusion with the real npm client and local stand-in registries. The classic mistake is an unscoped internal name behind a registry that merges internal and public sources: npm asks for the highest version that satisfies the range, and the attacker's 1.99.0 beats your 1.2.0. A scope pinned to your internal registry means the public side is never asked.

Stand-in, loopback only The npm client is real (11.6.4). The two registries are small Node servers on 127.0.0.1, and mergeReleases imitates a virtual repository that merges sources. They have no auth, publish flow, audit endpoint or signatures. The "malicious" script only writes a marker file next to the project.
Stand-in وعلى loopback بس: الـ npm client حقيقي (11.6.4). الـ registries الاتنين servers صغيرة بـ Node على 127.0.0.1، وmergeReleases بيقلّد virtual repository بيدمج المصادر. مفيهومش auth ولا publish ولا audit endpoint ولا signatures. والـ script "الخبيث" بيكتب ملف marker جنب المشروع وبس.
// ده stand-in: registry صغير على 127.0.0.1 للمعمل بس، بيقدم packuments و tarballs
// مفيهوش auth ولا publish ولا search ولا audit endpoint ولا signatures
import { createHash } from 'node:crypto';
import { readFileSync } from 'node:fs';
import { createServer } from 'node:http';

export async function startRegistry(label, releases) {
  const hits = [];
  const byName = new Map();
  for (const r of releases) {
    if (!byName.has(r.name)) byName.set(r.name, []);
    byName.get(r.name).push(r);
  }
  const base = () => `http://127.0.0.1:${server.address().port}`;
  const tarballName = (r) => `${r.name.replace('/', '__')}-${r.version}.tgz`;

  const packument = (name) => {
    const list = byName.get(name);
    const versions = {};
    const time = { created: '2020-01-01T00:00:00.000Z', modified: new Date().toISOString() };
    for (const r of list) {
      const bytes = readFileSync(r.tarball);
      versions[r.version] = {
        name,
        version: r.version,
        ...(r.hasInstallScript ? { hasInstallScript: true, scripts: { postinstall: 'node postinstall.cjs' } } : {}),
        dist: {
          tarball: `${base()}/-/tarballs/${tarballName(r)}`,
          integrity: `sha512-${createHash('sha512').update(bytes).digest('base64')}`,
          shasum: createHash('sha1').update(bytes).digest('hex'),
        },
      };
      time[r.version] = r.publishedAt ?? '2024-01-01T00:00:00.000Z';
    }
    const latest = list.map((r) => r.version).sort((a, b) => a.localeCompare(b, undefined, { numeric: true })).at(-1);
    return { name, 'dist-tags': { latest }, versions, time };
  };

  const server = createServer((req, res) => {
    const path = decodeURIComponent(req.url.split('?')[0]).replace(/^\//, '');
    if (path.startsWith('-/tarballs/')) {
      const file = path.slice('-/tarballs/'.length);
      const rel = releases.find((r) => tarballName(r) === file);
      if (!rel) return void res.writeHead(404).end();
      hits.push(`tarball ${rel.name}@${rel.version}`);
      return void res.writeHead(200, { 'content-type': 'application/octet-stream' }).end(readFileSync(rel.tarball));
    }
    if (byName.has(path)) {
      hits.push(`packument ${path}`);
      return void res.writeHead(200, { 'content-type': 'application/json' }).end(JSON.stringify(packument(path)));
    }
    hits.push(`404 ${path}`);
    res.writeHead(404, { 'content-type': 'application/json' }).end('{"error":"not found"}');
  });
  await new Promise((r) => server.listen(0, '127.0.0.1', r));
  return { label, url: `${base()}/`, hits, stop: () => new Promise((r) => server.close(r)) };
}

// ده stand-in لـ virtual repository زي Artifactory أو Nexus: بيدمج الداخلي مع العام
export function mergeReleases(...lists) {
  const seen = new Set();
  const out = [];
  for (const list of lists) {
    for (const r of list) {
      const key = `${r.name}@${r.version}`;
      if (!seen.has(key)) {
        seen.add(key);
        out.push(r);
      }
    }
  }
  return out;
}

بالعامية

فيه 4 أشكال هجوم بتغطي معظم الموضوع:

  • Typosquatting: اسم قريب من package مشهور، ومستني غلطة كتابة.
  • Dependency confusion: نفس اسم الـ package الداخلي بتاعك على registry عام بإصدار أعلى.
  • Malicious install scripts: بتشتغل وقت npm install، قبل أي كود بتاعك.
  • Maintainer account takeover: إصدار سيئ من package إنت أصلًا واثق فيه، ودي أصعب واحدة لأن الاسم نفسه سليم.

وحادثتين قريبين بيوضحوا الحجم. في سبتمبر 2025 وصفت CISA worm بيتكاثر لوحده اسمه Shai-Hulud، خرّب أكتر من 500 npm package: جمع credentials واستخدم npm tokens المسروقة ينشر نفسه في packages تانية. وفي مارس 2026 مهاجم عمل force-push لكود خبيث على معظم الـ version tags بتاعة aquasecurity/trivy-action (CVE-2026-33634، GHSA-69fq-xp46-6x23؛ عدّ Aqua هو 76 من 77 tag، و Snyk و Wiz بيقولوا 75 من 76). الـ credential stealer اشتغل قبل الـ scan الحقيقي، فالـ logs كانت شكلها طبيعي. يعني أداة أمان هي اللي دخل منها، والـ tag اللي بيتغير هو الوسيلة.

حجم تعرضك هو حجم الشجرة، مش حجم package.json. في عينة الدرس ده، 5 dependencies مباشرة جابوا 79 package، وكل واحد ليه maintainers. والمعمل بيعيد dependency confusion بـ npm الحقيقي و registries بديلة محلية. الغلطة الكلاسيك اسم داخلي من غير scope ورا registry بيدمج الداخلي والعام: npm بيطلب أعلى إصدار يطابق الـ range، فـ 1.99.0 بتاعة المهاجم بتكسب 1.2.0 بتاعتك. أما scope متثبت على الـ registry الداخلي فمعناه إن الجانب العام مابيتسألش أصلًا.

فين هستخدمه في شغلي؟ لو عندك packages داخلية زي orders-shared-utils من غير scope، دي أول حاجة تتغير: اعمل scope زي @acme/، واحجز نفس الـ scope على npm العام حتى لو مش هتنشر عليه، وحط في .npmrc بتاع الـ repo @acme:registry=https://npm.internal.acme.example/. ولو بتستخدم Artifactory أو Nexus، راجع إعدادات الـ virtual repository عشان أسماء الـ scope الداخلي ماتتجابش من العام.

الغلطة الشائعة: تفتكر إن الاسم الداخلي "سري". الأسماء بتظهر في package.json و source maps و error stacks، وأسهل حاجة تتجمع.

Pinning actions, not just packages The Trivy incident hit people who trusted a tag. uses: some/action@v1 follows whatever the tag points at today; uses: some/action@<40-char-sha> doesn't move. Pin third-party actions by commit SHA and let a bot propose the updates. It costs readability and adds PR noise, which grouping in Part 4 reduces.
ثبّت الـ actions كمان، مش الـ packages بس: حادثة Trivy ضربت اللي وثقوا في tag. uses: some/action@v1 بيتبع أي حاجة الـ tag بيشاور عليها النهاردة، وuses: some/action@<40-char-sha> مابيتحركش. ثبّت الـ third-party actions بالـ commit SHA وخلي bot يقترح التحديثات. التكلفة إن القراية بتبقى أصعب والـ PRs بتزيد، والـ grouping في الجزء 4 بيقلل ده.

Part 2 — Install scripts 🟡 Intermediateالجزء 2 — الـ install scripts

English

What an install script can reach is shown in Node lesson 28, part 2: your environment, your files, your network. The new part is the default behavior. npm 11 runs a dependency's postinstall; npm 12 doesn't. Against the same local package, 11.6.4 wrote the marker and 12.2.2 skipped the script and printed a warning.

So the README's --ignore-scripts advice has changed: on npm 12 blocking dependency scripts is the default. It still matters on npm 11, where it's the only protection. On 12 the decision moves to an allowlist in package.json, which you manage with npm install-scripts ls and npm install-scripts approve <pkg> (there's also npm install-scripts deny, and npm approve-scripts writes the same list). That makes approvals reviewable in a PR, which is better than a global flag. npm's docs say entries are pinned as pkg@version by default (allow-scripts-pin); in this lab npm wrote a name-only entry and warned about it, as the output shows.

Note the runtime requirement: npm 12.2.2 declares support for Node ^22.22.2, ^24.15.0 or >=26. On this machine's 22.19 it only printed a warning and kept working, but on a pipeline you'd want a supported version.

بالعامية

اللي الـ install script يقدر يوصله موجود في الدرس 28 في Node، الجزء 2: الـ environment والملفات والشبكة. الجديد هو الـ default. npm 11 بيشغّل postinstall بتاع الـ dependency، و npm 12 لأ. على نفس الـ package المحلي، 11.6.4 كتب الـ marker، و 12.2.2 تخطى الـ script وطبع تحذير.

فنصيحة --ignore-scripts اللي في الـ README اتغيرت: على npm 12 حجب scripts الـ dependencies هو الافتراضي. وبتفضل مهمة على npm 11، لأنها الحماية الوحيدة هناك. وعلى 12 القرار بينقل لـ allowlist في package.json، وبتديرها بـ npm install-scripts ls وnpm install-scripts approve <pkg> (وفيه كمان npm install-scripts deny، وnpm approve-scripts بيكتب نفس القايمة). وده بيخلي الموافقة تتراجع في PR، وده أحسن من flag عام. docs بتاعة npm بتقول إن الإدخالات بتتثبت كـ pkg@version افتراضيًا (allow-scripts-pin)، وفي المعمل ده npm كتب اسم بس وحذر من ده زي ما الـ output بيبين.

وخد بالك من متطلبات الـ runtime: npm 12.2.2 بيعلن دعمه لـ Node ^22.22.2 أو ^24.15.0 أو >=26. على 22.19 اللي على الجهاز ده طبع تحذير بس وكمل، بس في الـ pipeline عايز نسخة مدعومة.

فين هستخدمه في شغلي؟ لما تحدّث الفريق لـ npm 12، أول npm ci هيبين إن bcrypt أو sharp ماتبنوش. متحطش approve لكل حاجة عشان تخلص: شغّل npm install-scripts ls، وافق بس على اللي محتاج build فعلًا، والـ allowScripts يدخل الـ repo في PR ويتراجع زي أي كود. ولسه على npm 11؟ حط --ignore-scripts في الـ CI وnpm rebuild للي محتاج.

الغلطة الشائعة: تعتبر إن --ignore-scripts بتوقف كل حاجة. الكود الخبيث ممكن يكون في الـ package نفسه ويشتغل أول ما تعمله import. الـ allowlist بتقفل طريق واحد بس.

Interview question "What does --ignore-scripts actually protect you from, and what doesn't it?" → It stops code from running at install time, on your laptop or CI runner, which is where tokens live. It doesn't stop malicious code that runs when the package is imported. On npm 12 blocking is the default and approvals live in allowScripts, so you review them like code.
"الـ --ignore-scripts بيحميك من إيه بالظبط، ومن إيه لأ؟" ← بيمنع تشغيل كود وقت التثبيت على جهازك أو الـ CI runner، ودي الأماكن اللي فيها الـ tokens. لكنه مش بيمنع كود خبيث بيشتغل لما الـ package يتعمله import. وعلى npm 12 الحجب هو الافتراضي والموافقات في allowScripts، فبتتراجع زي الكود.

Part 3 — Lockfiles and release age 🟡 Intermediateالجزء 3 — الـ lockfiles وعمر الإصدار

English

npm ci versus npm install and EINTEGRITY are covered in Node lesson 28, part 2. In short: the lockfile fixes both the versions and their hashes, and npm ci fails instead of drifting. What's new is the release-age gate. Most malicious versions are detected and pulled within days, so refusing anything newer than N days closes that window for very little effort.

min-release-age arrived in npm 11.10 (per secondary sources; npm 12.2.2's own docs describe it). The lab below used 12.2.2 against a stand-in with 1.9.0 published 40 days ago and 2.0.0 published about an hour ago. An open install picked 1.9.0. A range that only 2.0.0 satisfies failed with ETARGET, and when no version at all was old enough the error was ENOVERSIONS.

The trade-off is real: a cooldown also delays a security fix. npm's docs say that when the window blocks a patch that npm audit fix wants, npm keeps the vulnerable version, warns, and exits non-zero. So set up the override before you need it: min-release-age-exclude exempts named packages or globs, which the last run used to install the new version. The runs passed these as CLI flags, and the same two options can live in the repo's .npmrc, as shown below. As for pinning: pin exact versions for critical dependencies, where a surprise is expensive (auth, payments, your ORM), and leave ranges for the rest, because the lockfile already freezes what's installed and ranges let bots propose updates.

السطر الأول: الإصدار الخبيث بيتنشر وبيتكشف ويتشال غالبًا في أيام، والـ cooldown بيرفض التثبيت في الفترة دي. السطر التاني: إصلاح CVE خطير كمان بيتأخر بنفس الـ cooldown، فاستخدم min-release-age-exclude للحالات دي.
بالعامية

npm ci مقابل npm install وEINTEGRITY موجودين في الدرس 28 في Node، الجزء 2. باختصار: الـ lockfile بيثبت الإصدارات والـ hashes، وnpm ci بيفشل بدل ما يغيّر حاجة. الجديد هو بوابة عمر الإصدار: معظم الإصدارات الخبيثة بتتكشف وتتشال في أيام، فرفض أي حاجة أحدث من N يوم بيقفل النافذة دي بمجهود قليل جدًا.

min-release-age وصل في npm 11.10 (حسب مصادر ثانوية، و docs بتاعة 12.2.2 بتوصفه). المعمل استخدم 12.2.2 مع stand-in عليه 1.9.0 منشورة من 40 يوم و2.0.0 منشورة من حوالي ساعة. التثبيت من غير range اختار 1.9.0. والـ range اللي 2.0.0 بس بتطابقه فشل بـ ETARGET، ولما مفيش ولا إصدار قديم كفاية الخطأ كان ENOVERSIONS.

والـ trade-off حقيقي: الـ cooldown بيأخر الـ security fix كمان. docs بتاعة npm بتقول إن لما النافذة تمنع patch عايزه npm audit fix، npm بيفضل على الإصدار الضعيف ويحذر ويرجع non-zero. فجهّز الاستثناء قبل ما تحتاجه: min-release-age-exclude بيستثني أسماء أو globs، وآخر run استخدمه ونزّل الإصدار الجديد. والتجارب مررت الخيارين كـ CLI flags، ونفس الخيارين ممكن يتحطوا في .npmrc بتاع الـ repo زي ما هو موضح تحت.

وعن الـ pinning: ثبّت versions بالظبط للـ dependencies الحساسة اللي المفاجأة فيها غالية (الـ auth والـ payments والـ ORM)، وسيب ranges للباقي، لأن الـ lockfile أصلًا بيثبت اللي متثبت، والـ ranges بتخلي الـ bots تقترح تحديثات.

فين هستخدمه في شغلي؟ حط min-release-age=7 في .npmrc بتاع الـ repo، وmin-release-age-exclude=@acme/* عشان الـ packages الداخلية متتأخرش. وخلي الـ runbook فيه خطوة صريحة: "CVE حرج طلع وإصلاحه جديد؟ ضيف الـ package في min-release-age-exclude في PR، وبعد ما الـ window يعدي شيله". وبكده مفيش حد يعطل الحماية كلها وقت الحادثة.

الغلطة الشائعة: تفعّل الـ cooldown من غير مسار استثناء، فيوم الـ CVE الحرج أول حاجة الناس تعملها هي إنهم يقفلوه خالص وينسوا يرجعوه.

English

npm audit compares your lockfile with an advisory database. On its own it's noisy, so wrap it in a gate. The script below reads npm audit --json, blocks on high and critical, and supports a written exception with a reason and an expiry date. An exception that can expire is a decision; one that can't is a way of forgetting. Run it with --omit=dev for deploy gates: dev tooling never reaches production, and in the fixture that removed the only critical finding.

Reachability is the other filter. An advisory about a function you never call is a smaller risk than one on your request path, and npm audit can't tell the two apart. Tools with call-graph analysis try to; without one, a human records the reasoning, as in the lodash exception below. A transitive fix uses overrides when the parent is stuck: express@4.17.1 pins qs to 6.7.0, and the override moved it to 6.17.1. Read the advisory's range before choosing a version: the first attempt at 6.14.0 was still flagged. It also grew the production tree from 52 to 70 packages, and the parent was never tested against that version, so run your tests. The durable fix is upgrading express, which is why the gate still fails on it afterwards.

Part 5 — SBOM and provenance 🟡 Intermediateالجزء 5 — الـ SBOM والـ provenance

English

An SBOM is a machine-readable list of what's inside a build: names, versions, licenses, hashes and package URLs. Its value shows up on the day a new CVE lands and someone asks "are we affected?": you query stored SBOMs instead of checking out every old release. npm sbom --sbom-format cyclonedx produces one with no extra tool, and @cyclonedx/cyclonedx-npm produced a newer spec version here (1.6, against npm's 1.5). Diffing two SBOMs is cheap and useful in a PR: it shows exactly what a change adds to production.

Provenance answers a different question: not what's in the package, but where it was built. npm audit signatures checks registry signatures and attestations for your installed tree. npm provenance links a published version to the source commit and CI workflow that built it, signed through Sigstore, which issues short-lived certificates tied to an OIDC identity instead of asking maintainers to manage long-lived keys. The registry exposes it under dist.attestations. Keep the limit in mind: an attestation proves the origin, not that the code is safe. A compromised CI pipeline produces perfectly valid provenance.

Publishing changed too. GitHub's changelog of 2025-12-09 announced that npm classic tokens were revoked. Trusted publishing goes further: CI publishes through OIDC with no stored npm token at all, so there's nothing for a Shai-Hulud-style worm to harvest from that pipeline.

Part 6 — Fewer dependencies 🟡 Intermediateالجزء 6 — dependencies أقل

English

Every dependency is a standing grant: its maintainers, their accounts, their CI and all of its transitive dependencies get to run in your process. The cheapest supply-chain control is one you don't have to install. So rank what you have, using signals you can read from the registry: tree size, maintainer count, time since last publish, and install scripts. None of these is a verdict. A single active maintainer can be fine and a large tree can be justified; the ranking tells you where to look first. The score weights in the script are a judgment call you should adjust.

Node now covers several things that used to need a package. util.parseArgs replaces simple argument parsers, with the bonus that an unknown flag is an error. fetch covers plain HTTP calls. structuredClone handles Date and Map, and throws DataCloneError on functions instead of quietly dropping them. Removing three packages shrank the sample tree from 79 to 66, a real but modest win, which is the honest picture: most of the tree came from express, so the big decisions are about your framework-level dependencies.

The durable part is the policy: adding a dependency becomes a small written decision, so the question gets asked before the import does.

async function transitiveCount(name, version) {
  mkdirSync(path.join(here, "rank-tmp"), { recursive: true });
  const dir = mkdtempSync(path.join(here, "rank-tmp", "x-"));
  writeFileSync(path.join(dir, "package.json"), JSON.stringify({ name: "x", private: true, version: "1.0.0", dependencies: { [name]: version } }));
  await npm(dir, "install", "--package-lock-only", "--ignore-scripts", "--no-audit", "--no-fund", "--loglevel=error");
  const lock = JSON.parse(readFileSync(path.join(dir, "package-lock.json"), "utf8"));
  const pkgs = Object.entries(lock.packages).filter(([k]) => k !== "");
  rmSync(dir, { recursive: true, force: true });
  return { total: pkgs.length, installScripts: pkgs.filter(([, v]) => v.hasInstallScript).length };
}

async function inspect(name, range) {
  const res = await fetch(`https://registry.npmjs.org/${name}`);
  if (!res.ok) throw new Error(`${name}: ${res.status}`);
  const doc = await res.json();
  const latest = doc["dist-tags"].latest;
  const published = doc.time[latest];
  const ageDays = Math.round((Date.now() - Date.parse(published)) / 86_400_000);
  const tree = await transitiveCount(name, range);
  return { name, range, latest, maintainers: doc.maintainers?.length ?? 0, ageDays, tree: tree.total, installScripts: tree.installScripts };
}

بالعامية

كل dependency هو تصريح دايم: الـ maintainers بتوعه وحساباتهم والـ CI بتاعهم وكل الـ transitive dependencies بيشتغلوا جوه الـ process بتاعك. وأرخص control في الـ supply chain هو اللي مش محتاج تثبته. فرتّب اللي عندك بإشارات تقدر تقراها من الـ registry: حجم الشجرة، وعدد الـ maintainers، والوقت من آخر نشر، والـ install scripts. ولا واحدة منهم حكم نهائي: maintainer واحد نشيط ممكن يكون تمام، وشجرة كبيرة ممكن تبقى مبررة. الترتيب بيقولك تبص فين الأول، والأوزان في الـ script تقدير شخصي لازم تعدله.

Node بقى بيغطي حاجات كانت محتاجة package:

  • util.parseArgs بدل parsers البسيطة، وزيادة على كده الـ flag المجهول بيبقى error.
  • fetch بيغطي الـ HTTP calls العادية.
  • structuredClone بيتعامل مع Date وMap، وبيرمي DataCloneError على الـ functions بدل ما يسقطها بصمت.

شيل 3 packages نزّل الشجرة من 79 لـ 66، مكسب حقيقي بس متوسط، وده الكلام الصادق: معظم الشجرة جاية من express، فالقرارات الكبيرة هي الـ dependencies على مستوى الـ framework.

الجزء اللي بيدوم هو الـ policy: إضافة dependency تبقى قرار صغير مكتوب، فالسؤال يتسأل قبل الـ import.

فين هستخدمه في شغلي؟ في الـ code review: PR ضاف moment عشان تنسيق تاريخ واحد؟ اطلب الـ ADR القصير، والإجابة غالبًا هتبقى Intl.DateTimeFormat. وكل ربع سنة شغّل rank-deps.mjs على الـ repo وخد أعلى 3، وقرر: ترقية ولا استبدال ولا قبول مكتوب.

الغلطة الشائعة: تستبدل package ناضج بكود كتبته بسرعة في حاجات صعبة زي crypto أو parsing الـ dates المعقد. الـ policy معناها "فكّر الأول"، مش "ممنوع".

Common mistakes · غلطات شائعة

❌ An internal name with no scope 
{ "dependencies": { "orders-shared-utils": "^1.2.0" } }
✅ A scope pinned to your registry 
# الـ scope ده مش بيتسأل عليه أي registry غير الداخلي
@orders-internal:registry=https://npm.internal.orders.example/
بالعامية

❌ اسم من غير scope ورا registry بيدمج المصادر معناه إن المهاجم يقدر ينشر نفس الاسم بإصدار أعلى، وده اللي حصل في المعمل. ✅ الـ scope المتثبت بيخلي الطلب يروح للـ registry الداخلي بس، واحجز الـ scope على npm العام كمان.

❌ npm install in CI 
npm install
# الـ lockfile ممكن يتغير والـ scripts بتشتغل على npm 11
✅ npm ci, scripts off 
npm ci --ignore-scripts
# الـ versions والـ hashes من الـ lockfile بالظبط، ومن غير scripts
بالعامية

❌ npm install ممكن يعدل الـ lockfile، وعلى npm 11 بيشغّل install scripts. ✅ npm ci بيفشل لو الـ lockfile مش مطابق، و--ignore-scripts بيقفل الـ scripts على npm 11، وعلى npm 12 ده الافتراضي أصلًا للـ dependencies.

❌ npm audit fix --force 
npm audit fix --force
# ممكن يرقّي major versions من غير ما تعرف
✅ Read, then decide 
npm audit --omit=dev --json > audit.json
node audit-gate.mjs audit.json audit-exceptions.json
# إصلاح محدد أو override بعد قراية الـ advisory، وبعدين الـ tests
بالعامية

❌ --force بيعمل upgrades ممكن تكون breaking وإنت مش عارف إيه اتغير. ✅ اقرا الـ JSON، وقرر بالـ gate، واستخدم إصلاح محدد أو overrides بعد قراية range الـ advisory، وشغّل الـ tests.

❌ A cooldown with no fast lane

# يوم الـ CVE الحرج الناس هتقفله خالص
✅ A cooldown with an exit 
min-release-age=7
# استثناء مؤقت للـ package اللي إصلاحه لسه جديد
min-release-age-exclude=qs
بالعامية

❌ cooldown من غير مسار استثناء بيتقفل كله أول ما يعطل إصلاح مهم، وبيفضل مقفول. ✅ استثناء للـ package ده بس في PR، ويتشال بعد ما الـ window يعدي.

Cheat sheet · الخلاصة

  • Four attacks: typosquatting, dependency confusion, install scripts, account takeover. Your exposure is the tree (79 packages from 5 here), not the package.json.
  • Dependency confusion: use a scope pinned to your internal registry, and reserve the scope publicly.
  • Pin third-party GitHub Actions by commit SHA. Tags can be moved, as in the March 2026 trivy-action compromise.
  • npm 12 blocks dependency install scripts by default; approvals go in allowScripts. On npm 11 use --ignore-scripts in CI.
  • npm ci in CI. min-release-age keeps very new versions out; min-release-age-exclude is the security fast lane.
  • Audit gate: high and critical, --omit=dev for deploys, written exceptions with an expiry. Don't use || true.
  • overrides fixes a transitive dep: read the advisory range, run the tests, and plan the real upgrade.
  • Bots open PRs and humans approve them. Add a cooldown and grouping.
  • SBOM = what's inside. Provenance = where it was built. Neither one means safe.
  • Trusted publishing through OIDC beats a stored token. npm classic tokens were revoked on 2025-12-09.
  • Every dependency is a standing grant. Rank them, prefer the platform, and write a short ADR before adding one.
