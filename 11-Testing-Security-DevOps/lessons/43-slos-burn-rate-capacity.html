Why this matters · ليه ده مهم

English

An SLO that lives in a slide changes nothing. It starts to matter when a file generates the alert rules, a CI step reads the remaining budget and refuses a feature deploy, and a forecast tells you the month you run out of capacity. That is the gap between "we have dashboards" and "we run this service". This lesson builds all three and ends with a capacity report you can defend. Interviewers ask about it directly: "what is an error budget and how does it change the team's decisions?" is exit question 15 of this section.

بالعامية

الـ SLO اللي قاعد في slide مش بيغيّر حاجة. قيمته بتبدأ لما ملف واحد يولّد الـ alert rules، وخطوة في الـ CI تقرا الـ budget الفاضل وترفض deploy لـ feature، وتوقع يقولك هتخلص من الـ capacity في أنهي شهر. ده الفرق بين "عندنا dashboards" و"إحنا شايلين الـ service دي". الدرس ده بيبني التلاتة وبيخلص بـ capacity report تقدر تدافع عنه. والـ interview بيسأل فيها صريح: "إيه هو الـ error budget وإزاي بيغيّر قرارات الفريق؟" وده سؤال رقم 15 في اختبار القسم.

Part 1 — SLOs as code 🔴 Advancedالجزء 1 — الـ SLOs ككود

English

SLI, SLO, SLA and the budget arithmetic are in section 10, SLOs and alerting, parts 1 and 2, so they aren't repeated here. The new step is making the SLO a versioned file that generates everything else. Hand-written rules drift: someone raises the target in a document, nobody edits the alert, and the alert keeps guarding last year's number. Sloth and Pyrra solve this by generating rules from a small spec. A real Sloth spec has version: "prometheus/v1" and a list of slos, each with sli.events.error_query and total_query. Sloth also emits a 2h and 1d ticket pair that our three-rule version leaves out. The generator below is small and in that style, so the mechanism is visible.

Choosing SLIs. Checkout gets two: availability (valid requests that didn't fail on our side) and latency. The README says "latency p99", but the budgetable form is a threshold ratio, "the share of valid requests answered within 300 ms", because a ratio adds up over a window and a percentile doesn't. A realistic target starts from what you measured and what your dependencies allow. Over 30 days, 99.9% is 43.2 minutes, 99.99% is 4.32 minutes and 99.999% is 26 seconds. With two hard dependencies in series at 99.95% each, the best you can honestly promise is about 99.90%.

What the spec buys you. The burn factor is derived, spend × windowHours / longWindowHours, so 14.4 is really 0.02 × 720 / 1, and changing to a 28-day window recomputes every rule. The loader rejects three mistakes before anything ships: a 100% target (no budget at all), a latency threshold with no matching histogram bucket (the query returns nothing, so the alert silently never fires), and a target so loose that the page condition would need an error ratio above 100%.

The rules go to Prometheus, which doesn't run on this machine. The SLI is computed for real: 4,000 HTTP requests against a real Express server, read back from its access log using the same route, exclusions and threshold as the spec. 3,232 of those requests were valid, 17 failed on our side, so availability was 99.474%, a 5.26× burn: this sample would spend a month of budget in under 6 days.

import { parse } from "yaml";

export type Objective = {
  name: string;
  kind: "availability" | "latency";
  target: number;
  thresholdSeconds?: number;
  description: string;
};
export type Spec = {
  version: number;
  service: string;
  owner: string;
  runbookBase: string;
  windowDays: number;
  route: string;
  excludePaths: string[];
  histogramBuckets: number[];
  objectives: Objective[];
};
export type AlertPlan = {
  alert: string;
  objective: Objective;
  severity: "page" | "ticket";
  factor: number;
  long: string;
  short: string;
  threshold: number;
};

const round = (n: number, d = 8) => Number(n.toFixed(d));
const cap = (s: string) => s[0]!.toUpperCase() + s.slice(1);

// الـ spend ده نسبة الـ budget اللي القاعدة بتستحملها، والأرقام من الـ SRE Workbook
const WINDOWS = [
  { label: "Fast", severity: "page", spend: 0.02, long: "1h", short: "5m" },
  { label: "Medium", severity: "page", spend: 0.05, long: "6h", short: "30m" },
  { label: "Slow", severity: "ticket", spend: 0.1, long: "3d", short: "6h" },
] as const;

export const HOURS: Record<string, number> = { "5m": 1 / 12, "30m": 0.5, "1h": 1, "6h": 6, "3d": 72 };

export const budgetOf = (o: Objective) => round((100 - o.target) / 100);

export function loadSpec(path: string): Spec {
  const spec = parse(readFileSync(path, "utf8")) as Spec;
  for (const o of spec.objectives) {
    // هدف 100% معناه budget صفر: يعني أي deploy ممنوع للأبد
    if (o.target >= 100) throw new Error(`${o.name}: target ${o.target} leaves no error budget`);
    if (o.target > 99.99) throw new Error(`${o.name}: target ${o.target} is tighter than your dependencies`);
    if (o.kind === "latency" && !o.thresholdSeconds) throw new Error(`${o.name}: latency needs thresholdSeconds`);
    // لو الـ bucket مش موجود الـ query بترجع فاضية، والـ alert عمره ما هيضرب من غير أي error
    if (o.kind === "latency" && !spec.histogramBuckets.includes(o.thresholdSeconds!)) {
      throw new Error(`${o.name}: no histogram bucket at ${o.thresholdSeconds}s, the rule would return nothing`);
    }
  }
  return spec;
}

export function alertPlan(spec: Spec): AlertPlan[] {
  return spec.objectives.flatMap((objective) =>
    WINDOWS.map((w) => {
      // الـ factor بيتحسب من طول الـ window: لو غيّرته لـ 28 يوم، كله بيتغير لوحده
      const factor = round((w.spend * spec.windowDays * 24) / HOURS[w.long]!, 4);
      const threshold = round(factor * budgetOf(objective));
      // لو الحد فوق 100% الـ alert عمره ما هيضرب، فارفض بدل ما تكتشفها في الـ incident
      if (threshold >= 1) throw new Error(`${objective.name}/${w.label}: needs error ratio ${threshold}, can never fire`);
      return {
        alert: `${cap(spec.service)}${cap(objective.name)}Burn${w.label}`,
        objective,
        severity: w.severity,
        factor,
        long: w.long,
        short: w.short,
        threshold,
      };
    }),
  );
}

// (1) نسبة الأخطاء لكل window: نفس التعريف بالظبط اللي في حساب الـ log
function errorRatio(o: Objective, w: string): string {
  if (o.kind === "availability") {
    const bad = `http_requests_total{${base},code=~"5.."}`;
    const valid = `http_requests_total{${base},code!~"4.."}`;
    return `sum(rate(${bad}[${w}])) / sum(rate(${valid}[${w}]))`;
  }
  const fast = `http_request_duration_seconds_bucket{${base},code!~"4..",le="${o.thresholdSeconds}"}`;
  const all = `http_request_duration_seconds_count{${base},code!~"4.."}`;
  return `1 - (sum(rate(${fast}[${w}])) / sum(rate(${all}[${w}])))`;
}

const metric = (o: Objective, w: string) => `slo:${spec.service}_${o.name}:error_ratio_${w}`;

const recording = spec.objectives.flatMap((o) => [
  ...ALL_WINDOWS.map((w) => ({ record: metric(o, w), expr: errorRatio(o, w) })),
  {
    record: `slo:${spec.service}_${o.name}:budget_remaining`,
    expr: `1 - (avg_over_time(${metric(o, "5m")}[${spec.windowDays}d]) / ${budgetOf(o)})`,
  },
]);

// (2) كل alert ليها long window وshort window ولازم الاتنين يعدّوا الحد

import { parser } from "@prometheus-io/lezer-promql";
import { parse } from "yaml";

type Rule = { record?: string; alert?: string; expr: string; annotations?: Record<string, string> };
const doc = parse(readFileSync(process.argv[2]!, "utf8")) as { groups: { rules: Rule[] }[] };

// الـ parser ده الـ grammar الرسمي بتاع PromQL، فبيمسك أخطاء الكتابة من غير binary
function errorsIn(expr: string): number {
  let errors = 0;
  parser.parse(expr).iterate({ enter: (n) => { if (n.type.isError) errors++; } });
  return errors;
}

let rules = 0;
let problems = 0;
for (const r of doc.groups.flatMap((g) => g.rules)) {
  rules++;
  const name = r.record ?? r.alert;
  if (errorsIn(r.expr)) { problems++; console.log(`PARSE ERROR in ${name}: ${r.expr}`); }
  if (r.alert && !r.annotations?.runbook_url) { problems++; console.log(`NO RUNBOOK on ${name}`); }
}
console.log(`${rules} rules parsed by the PromQL grammar, ${problems} problems`);
// اختبار للفاحص نفسه: لو قبل expression مكسور يبقى الـ check كله مالوش لازمة
console.log("control:", errorsIn("sum(rate(http_requests_total[5m]) /") > 0 ? "broken expression is rejected" : "PARSER ACCEPTS ANYTHING");
process.exit(problems ? 1 : 0);

التعريفات بتاعة SLI وSLO وSLA وحساب الـ budget موجودة في درس SLOs في قسم 10، الجزء 1 و2، فمش هنعيدها. الجديد هنا إن الـ SLO يبقى ملف عليه version وكل حاجة تانية تطلع منه. الـ rules اللي بتتكتب بالإيد بتتوه: حد يعلّي الهدف في document، ومحدش يعدّل الـ alert، فالـ alert يفضل حارس رقم السنة اللي فاتت. Part 2 — An error-budget policy that bites 🔴 Advancedالجزء 2 — سياسة error budget ليها أسنان

English

A budget with no policy is a number on a dashboard. The policy is a short document, agreed with product before anything goes wrong, that answers four things: what changes at each budget level, who decides, what counts as an exception, and when it ends. Writing it in advance is the point, because nobody argues rationally about a freeze during a bad week. The Google SRE Workbook's sample halts changes other than P0 issues and security fixes until the service is back within SLO, and asks for a postmortem when a single incident uses more than 20% of the budget.

A policy only bites when something enforces it, so the deploy gate reads the budget and exits non-zero. Four design decisions are in the code. A rollback or a fix is always exempt, because a gate must never block the thing that repairs the outage. Exceptions are data, with a PR, a reason, an approver and an expiry date, because a verbal "just ship it" can't be audited and never ends. Missing or stale budget data blocks features, because you can't prove the budget is healthy, but it never blocks a rollback. Yellow doesn't freeze anything: it switches features to canary-only, so the team feels the budget before it runs out.

The gate runs as a real process in all nine cases below, and the exit code is what a CI job would read. Here it reads a sample budget file. In a real pipeline the file comes from a Prometheus API query of the budget_remaining rule from Part 1.

# Error budget policy: checkout
Owner: team-payments. Reviewed quarterly. Exceptions approved by the VP of Engineering.

## Objectives
Availability 99.9% and latency 99% under 300 ms, rolling 30 days.

## States
| Budget left | State  | What changes                                               |
| ----------- | ------ | ---------------------------------------------------------- |
| over 25%    | Green  | Normal releases.                                           |
| 0% to 25%   | Yellow | Features ship as canary only, on-call is told first.       |
| 0% or less  | Red    | Feature freeze: only fixes, reliability, security, rollback |

## While red
- One engineer per squad moves to reliability work until the budget is positive.
- A single incident that used over 20% of the budget gets a postmortem with a P0 action.

## Exceptions, each one written down
- Legal or contractual deadline only, approved in writing, with an expiry date.
- Recorded in exceptions.yaml: id, PR, reason, approver, expiry. No verbal approvals.

## When the data is missing or stale
- Rollbacks and fixes are never blocked. Features wait.

## When it ends
- Automatically, when the rolling window brings the budget back above 0%.

The multi-window maths and a 30-day evaluator comparing them with threshold alerts are in section 10, part 3. In short: burn rate is how many times faster than allowed you're spending the budget, the long window proves the problem is big enough to matter, and the short window proves it's still happening so the alert stops soon after a fix. The factors and windows come from the SRE Workbook: 14.4× over 1h and 5m, 6× over 6h and 30m, 1× over 3d and 6h.

What's new is that the same generator now writes a promtool unit-test file, so an alert is tested like code. The file gives Prometheus exact input series in the a+bxn notation (a, a+b, ... a+n·b), an eval_time, and the alerts expected at that moment with their exact labels and annotations. Real command: promtool test rules checkout.rules.test.yaml. It can't run here, so a clearly labelled stand-in reads the same generated file and checks the same assertions.

All nine assertions pass: the 10% outage pages within 12 minutes, the 0.2% slow burn opens a ticket within two days and never pages, and the 3-minute 3% blip fires nothing. Look at the fast-burn line 10 minutes after the outage ended: the 1-hour ratio is still 3.339%, well over the limit, and only the 0% short window keeps the page from continuing.

What breaks at low traffic. The ratio has no idea how many requests sit behind it. At 1,000 requests a minute it takes 865 failures in an hour to page; at 1 request a minute it takes one. A quiet internal API or a small tenant will page you for a single bad request. Add a minimum-events condition, send synthetic traffic, or group small services into one SLO.

Part 4 — Forecasting 🔴 Advancedالجزء 4 — التوقع

English

Capacity planning needs two numbers: how much one instance can really serve (Part 5, and the capacity model in section 10, part 1), and how fast demand grows. The second one comes from a fit on monthly peaks. Peak, not average, because capacity is exhausted at the worst minute of the day. The script fits both a straight line and a compound (log-linear) model over 12 months of invented sample numbers, then asks when the usable capacity is exceeded: instances × capacity per instance × headroom.

The honest test is a back-test: fit on the first 9 months and predict the last 3, which the model never saw. On this data the line is 3.9% to 7.6% low and the compound model is 2.0% to 3.5% low, and the gap gets wider with distance. That difference is what matters for a date: the line says capacity runs out in 10 months and the compound model says 6.

Where a straight line stops being honest:

  • Compounding growth. A percentage growth rate curves upward, so a line is always late, and it gets later the further out you look.
  • Step changes. A large customer or a new market isn't a trend. In the run below one step makes the fit error jump from ±13.7 to ±104.2 RPS, and the line is wrong on both sides of the jump. Model the step separately.
  • Seasonality. Sales and paydays repeat. Compare to the same month last year, and plan events separately (Part 5).
  • Saturation. Growth flattens when a market fills up, and no line tells you when.
  • Few points. Twelve points can't say much about 24 months out. Forecast near, and refit monthly.
  • The system isn't linear. A forecast in RPS assumes each instance keeps its capacity, but a shared database or a connection limit may hit its own knee first.

type Fit = { predict: (t: number) => number; slope: number };

// (1) أقل مربعات: أبسط خط بيعدّي في وسط النقط
function linear(ys: number[]): Fit {
  const n = ys.length;
  const mx = (n - 1) / 2;
  const my = ys.reduce((a, b) => a + b, 0) / n;
  let num = 0;
  let den = 0;
  ys.forEach((y, x) => { num += (x - mx) * (y - my); den += (x - mx) ** 2; });
  const b = num / den;
  const a = my - b * mx;
  return { slope: b, predict: (t) => a + b * t };
}

// (2) نمو مركّب: نفس الخط بس على log الأرقام
function exponential(ys: number[]): Fit {
  const f = linear(ys.map(Math.log));
  return { slope: Math.exp(f.slope) - 1, predict: (t) => Math.exp(f.predict(t)) };
}

const rmse = (ys: number[], f: Fit) => Math.sqrt(ys.reduce((s, y, x) => s + (y - f.predict(x)) ** 2, 0) / ys.length);

English

A forecast tells you the demand. A load test tells you what you can serve. The ramp below uses autocannon 9 against a real Express process, doubling connections from 1 to 128 for 4 seconds each. The handler does real CPU work and a 20 ms wait that stands in for a database call. First it measures the generator's own ceiling on an empty route, about 11,200 RPS, so we know the limit we find isn't autocannon's. How to load-test properly, including coordinated omission, is in Node lesson 35.

The knee is clear: 1, 2 and 4 connections roughly double the throughput each time, 8 connections adds +34%, then at 16 connections the gain is only +1% and latency doubles. Past the knee you add waiting, not work, which is Little's Law (L = λW): with throughput fixed, more connections can only mean more latency. Latency keeps climbing to a p99 of 1,768 ms at 128 connections, with zero errors. A load test that only checks for errors would have reported success.

So one instance sustains ≈170 RPS (Windows on a loaded machine, so trust the shape and the ratios). Sized for a 3× event at 2,226 RPS with 70% headroom, that's 20 instances. import { once } from "node:events";
import { writeFileSync } from "node:fs";
import autocannon from "autocannon";

const server = fork("server.ts", { env: { ...process.env, CPU_ITER: "20000", IO_MS: "20" } });
const [msg] = (await once(server, "message")) as [{ port: number }];
const url = `http://127.0.0.1:${msg.port}`;

// (1) السقف بتاع الـ load generator نفسه، عشان ماتقيسش autocannon بدل الـ API
const empty = await autocannon({ url: `${url}/empty`, connections: 32, duration: 3 });
const ceiling = Math.round(empty.requests.average);
console.log(`generator ceiling on an empty route: ≈${ceiling} RPS\n`);

type Step = { connections: number; rps: number; p50: number; p99: number; non2xx: number; errors: number };
const SLO_P99_MS = 300;
const steps: Step[] = [];

// (2) الـ ramp: كل خطوة بتضاعف الـ connections
console.log("conns   RPS  gain     p50 ms   p99 ms   non-2xx  errors");
for (const connections of [1, 2, 4, 8, 16, 32, 64, 128]) {
  const r = await autocannon({
    url: `${url}/orders`,
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ sku: "SKU-1", qty: 2 }),
    connections,
    duration: 4,
  });
  const step = { connections, rps: Math.round(r.requests.average), p50: r.latency.p50, p99: r.latency.p99, non2xx: r.non2xx, errors: r.errors };
  const prev = steps.at(-1);
  const pct = prev ? Math.round((step.rps / prev.rps - 1) * 100) : 0;
  const gain = prev ? `${pct >= 0 ? "+" : ""}${pct}%` : "-";
  steps.push(step);
  console.log(`${String(connections).padStart(5)} ${String(step.rps).padStart(5)} ${gain.padStart(5)} ${String(step.p50).padStart(10)} ${String(step.p99).padStart(8)} ${String(step.non2xx).padStart(9)} ${String(step.errors).padStart(7)}`);
}

// (3) الـ knee: أول خطوة ضاعفت فيها الـ connections والـ RPS زاد أقل من 10% أو الـ p99 كسر الـ SLO
const kneeAt = steps.findIndex((s, i) => i > 0 && (s.rps < steps[i - 1]!.rps * 1.1 || s.p99 > SLO_P99_MS));
const knee = steps[kneeAt]!;
const safe = steps[kneeAt - 1]!;
console.log(`\nknee at ${knee.connections} connections (${knee.rps} RPS, p99 ${knee.p99} ms)`);
console.log(`last healthy step: ${safe.connections} connections, ${safe.rps} RPS, p99 ${safe.p99} ms`);

writeFileSync("out/ramp.json", JSON.stringify({ steps, knee, safe, ceiling, sloP99: SLO_P99_MS }, null, 2));
server.send("stop");
await once(server, "exit");

التوقع بيقولك الطلب. والـ load test بيقولك تقدر تخدّم قد إيه. الـ ramp اللي فوق بيستخدم autocannon 9 على Express process حقيقي، وبيضاعف الـ connections من 1 لـ 128، كل خطوة 4 ثواني. الـ handler بيعمل شغل CPU حقيقي وانتظار 20ms بيمثّل DB call. الأول بيقيس سقف الـ generator نفسه على route فاضي، حوالي 11,200 RPS، عشان نعرف إن الحد اللي هنلاقيه مش بتاع autocannon. إزاي تعمل load test صح، بما فيها الـ coordinated omission، موجود في درس Node رقم 35.

الـ knee واضح: 1 و2 و4 connections بيضاعفوا الـ throughput تقريبًا كل مرة، و8 بيزوّد +34%، وبعدين عند 16 الزيادة +1% بس والـ latency اتضاعف. بعد الـ knee إنت بتزود انتظار مش شغل، وده Little's Law (L = λW): لما الـ throughput ثابت، زيادة الـ connections معناها زيادة الـ latency بس. الـ p99 فضل يطلع لـ 1,768ms عند 128 connection وعدد الـ errors صفر. load test بيبص على الـ errors بس كان هيقول نجح.

Common mistakes · غلطات شائعة

❌ A target picked from ambition 
# الهدف ده مش مبني على قياس ولا dependencies
- name: availability
  target: 99.99
✅ From measurement, capped by dependencies 
# آخر 8 أسابيع: 99.93%، والـ payment provider بيضمن 99.95%
- name: availability
  target: 99.9
بالعامية

❌ 99.99% يعني 4.32 دقيقة في الشهر، ولو الـ payment provider نفسه بيضمن 99.95% يبقى الهدف ده مستحيل تحققه، والـ alerts هتضرب طول الوقت لحد ما حد يكتمها. ✅ ابدأ من اللي قستَه فعلًا والـ dependencies بتسمح بإيه، وسيب مكان للـ deploys، وراجعه كل ربع سنة.

❌ Factors copied by hand 
# الـ window اتغير لـ 28 يوم، بس الـ 14.4 فضلت زي ما هي
windowDays: 28
expr: error_ratio_1h > (14.4 * 0.001)
✅ Derived from the window 
// الـ factor بيتحسب كل مرة من نفس الـ spec
const factor = (w.spend * spec.windowDays * 24) / HOURS[w.long]!;
// → 0.02 * 28 * 24 / 1 = 13.44
بالعامية

❌ الـ 14.4 جاية من 30 يوم بالظبط. لو الـ window بقى 28 يوم، الرقم الصح 13.44، والـ alert المنسوخ بيحسب غلط من غير ما حد ياخد باله. ✅ احسب الـ factor من الـ spec فأي تغيير في الـ window يوصل لكل الـ rules.

❌ The gate blocks the fix 
// الـ gate بيمنع كل حاجة لما الـ budget يخلص
if (budget.remaining <= 0) process.exit(1);
✅ Rollbacks and fixes are exempt 
// الـ rollback والـ fix لازم يعدّوا الأول قبل ما تبص على الـ budget
const EXEMPT = new Set(["rollback", "fix", "reliability", "security"]);
if (EXEMPT.has(kind)) process.exit(0);
if (budget.remaining <= 0) process.exit(1);
بالعامية

❌ لما الـ budget يخلص عادة بيبقى في incident شغال، والـ gate اللي بيمنع كل حاجة هيمنع الـ rollback اللي بيصلّحه، فالناس هتعمل disable للـ gate كله. ✅ اعفي الـ rollback والـ fix والـ reliability والـ security قبل أي check.

❌ Capacity read from the highest RPS seen 
conns   RPS   p99 ms
   64   196      583
"we can do 196 RPS"
✅ Capacity is the last step inside the SLO 
conns   RPS   p99 ms
    8   170       77
"170 RPS under a 300 ms p99"
بالعامية

❌ أعلى RPS في الجدول كان 196، بس الـ p99 هناك 583ms فالـ SLO بتاعنا (300ms) مكسور، ومفيش errors عشان تنبّهك. ✅ الـ capacity هو آخر خطوة جوه الـ SLO قبل الـ knee: 170 RPS عند p99 قدره 77ms، وعليها تحسب الـ headroom.

Cheat sheet · الخلاصة

  • One versioned SLO spec generates rules, tests and the log-based SLI, so nothing drifts.
  • Latency SLI as a threshold ratio, not a percentile: ratios can be budgeted.
  • Over 30 days: 99.9% = 43.2 min, 99.99% = 4.32 min, 99.999% = 26 s. Dependencies cap the target.
  • Derive factors: spend × windowHours / longHours. 14.4× = 2% in 1h of a 30-day window.
  • Guard in the generator: 100% target, missing bucket, threshold ≥ 1.
  • Policy: states, who decides, written exceptions with expiry, when it ends. The gate exits non-zero.
  • Rollbacks and fixes are always exempt. Missing data blocks features only.
  • Long window = big enough. Short window = still happening. Test both firing and staying quiet.
  • Low traffic: one bad request can page. Add minimum events or group services.
  • Forecast peaks, back-test it, report a range. A line under-forecasts compound growth and misses steps.
  • Knee = throughput stops growing. Capacity = last step inside the SLO, not the highest RPS.
  • Every capacity report states what wasn't tested.
بالعامية
  • spec واحدة عليها version بتطلّع الـ rules والـ tests والـ SLI من الـ log، فمفيش حاجة بتتوه.
  • الـ latency SLI يبقى نسبة على threshold مش percentile، لأن النسب هي اللي بيتعملها budget.
  • في 30 يوم: 99.9% = 43.2 دقيقة، و99.99% = 4.32 دقيقة، و99.999% = 26 ثانية. والـ dependencies بتحط سقف للهدف.
  • الـ factor يتحسب: spend × windowHours / longHours. والـ 14.4× يعني 2% في ساعة من window 30 يوم.
  • الـ generator يرفض: هدف 100%، أو bucket مش موجود، أو threshold يوصل 1 أو أكتر.
  • السياسة: درجات، ومين بيقرر، واستثناءات مكتوبة بتاريخ انتهاء، وبتنتهي إمتى. والـ gate بيخرج بـ exit غير صفر.
  • الـ rollback والـ fix معفيين دايمًا. والـ data الناقصة بتمنع الـ features بس.
  • الـ long window = كبيرة كفاية. والـ short window = لسه شغالة. اختبر إن الـ alert بيضرب وإنه بيسكت.
  • مع الـ traffic القليل، request واحد ممكن يضرب page. ضيف minimum events أو جمّع الـ services.
  • اتوقع على الـ peaks، واعمل back-test، وقول رينج. الخط بيقلل النمو المركّب وبيضيّع القفزات.
  • الـ knee = الـ throughput بطّل يزيد. والـ capacity = آخر خطوة جوه الـ SLO، مش أعلى RPS.
  • أي capacity report لازم يقول إيه اللي ماتجربش.
