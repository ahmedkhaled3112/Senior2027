Why this matters · ليه ده مهم

English

In a backend the expensive bugs live where your code meets the database: a unique index, a jsonb comparison, a transaction boundary, a migration that doesn't match the code. Integration tests catch those, and they only catch them when the database is the real engine and the schema comes from your real migrations. This lesson builds that setup: an app you can test without opening a port, a throwaway Postgres per run, four isolation strategies with real timings, migrations in setup, factories, and a suite that runs on several workers.

بالعامية

في الـ backend البقز الغالية عايشة في المكان اللي الكود بتاعك بيقابل فيه الـ database: unique index، مقارنة jsonb، حدود transaction، migration مش ماشية مع الكود. الـ integration tests بتمسك ده، بس بتمسكه لما الـ database تبقى الـ engine الحقيقي والـ schema جاية من الـ migrations الحقيقية بتاعتك. الدرس ده بيبني الـ setup ده: app تقدر تختبره من غير ما تفتح port، و Postgres مؤقت لكل run، و4 استراتيجيات للـ isolation بأرقام حقيقية، والـ migrations في الـ setup، والـ factories، و suite بتشتغل على كذا worker.

Part 1 — Supertest on the app object 🟡 Intermediateالجزء 1 — الـ Supertest على الـ app نفسه

English

The basics of Supertest are in Node lesson 29, part 3. What this part adds: the app is a factory that takes its dependencies, so a test can hand it a fake or a real repository and never touches a global. Then the assertions go past the status code into the contract: Location on a 201, the problem+json media type on errors, no X-Powered-By, and the flags on Set-Cookie.

request.agent(app) keeps cookies between calls, so a sign-in followed by an authenticated request reads like a real session. One real gotcha: the agent is honest about the Secure flag. With a Secure cookie over plain HTTP it does not send the cookie back, and the next request gets 401 (measured below). So the factory takes secureCookies, the HTTP-level tests pass false, and one test asserts that the production value of the flag is set.

Why pass the app object instead of a URL: Supertest binds it to an ephemeral port for each request, so parallel test files can never collide. A fixed listen(3000) in a test does, and Vitest runs files in parallel by default.

import { randomUUID } from 'node:crypto';
import express, { type Express, type NextFunction, type Request, type Response } from 'express';

export interface Order {
  id: string;
  tenantId: string;
  status: 'pending' | 'paid';
  totalMinor: number;
}

export interface OrderRepo {
  findByKey(tenantId: string, key: string): Promise<Order | undefined>;
  create(input: { tenantId: string; totalMinor: number; idempotencyKey: string }): Promise<Order>;
  findById(id: string): Promise<Order | undefined>;
  markPaid(id: string): Promise<Order | undefined>;
}

export interface Session {
  userId: string;
  tenantId: string;
}

export interface AppDeps {
  orders: OrderRepo;
  sessions?: Map<string, Session>;
  // في الـ production تبقى true، وفي tests الـ http تبقى false
  secureCookies?: boolean;
}

function problem(res: Response, status: number, title: string): void {
  res.status(status).type('application/problem+json').json({ type: 'about:blank', title, status });
}

// الـ factory ده اللي بيخلّي الـ tests تدّي dependencies من غير ما تفتح port
export function createApp({ orders, sessions = new Map(), secureCookies = true }: AppDeps): Express {
  const app = express();
  app.disable('x-powered-by');
  app.use(express.json());

  const requireSession = (req: Request, res: Response, next: NextFunction) => {
    const sid = /(?:^|;\s*)sid=([^;]+)/.exec(req.headers.cookie ?? '')?.[1];
    const session = sid ? sessions.get(sid) : undefined;
    if (!session) return problem(res, 401, 'Sign in required');
    res.locals.session = session;
    next();
  };

  app.post('/sessions', (req, res) => {
    const { userId, tenantId } = req.body as Partial<Session>;
    if (!userId || !tenantId) return problem(res, 422, 'userId and tenantId are required');
    const sid = randomUUID();
    sessions.set(sid, { userId, tenantId });
    res.cookie('sid', sid, { httpOnly: true, secure: secureCookies, sameSite: 'lax', path: '/' });
    res.status(204).end();
  });

  app.get('/me', requireSession, (_req, res) => {
    res.json(res.locals.session);
  });

  app.post('/orders', requireSession, async (req, res) => {
    const session = res.locals.session as Session;
    const key = req.header('Idempotency-Key');
    const totalMinor = req.body?.totalMinor;
    if (!key) return problem(res, 400, 'Idempotency-Key header is required');
    if (!Number.isInteger(totalMinor) || totalMinor <= 0) return problem(res, 422, 'totalMinor must be a positive integer');

    const existing = await orders.findByKey(session.tenantId, key);
    if (existing) {
      res.set('Idempotent-Replayed', 'true').status(200).json(existing);
      return;
    }
    const order = await orders.create({ tenantId: session.tenantId, totalMinor, idempotencyKey: key });
    res.status(201).location(`/orders/${order.id}`).json(order);
  });

  app.get('/orders/:id', requireSession, async (req, res) => {
    const session = res.locals.session as Session;
    const order = await orders.findById(req.params.id);
    if (!order) return problem(res, 404, 'Order not found');
    if (order.tenantId !== session.tenantId) return problem(res, 403, 'Not your order');
    res.json(order);
  });

  app.post('/orders/:id/pay', requireSession, async (req, res) => {
    const session = res.locals.session as Session;
    const order = await orders.findById(req.params.id);
    if (!order) return problem(res, 404, 'Order not found');
    if (order.tenantId !== session.tenantId) return problem(res, 403, 'Not your order');
    if (order.status === 'paid') return problem(res, 409, 'Order is already paid');
    const paid = await orders.markPaid(order.id);
    res.json(paid);
  });

  return app;
}

// المخزن ده في الـ memory عشان الجزء ده عن الـ HTTP بس، والـ DB الحقيقية في الجزء 2
function memoryOrders(): OrderRepo {
  const byId = new Map<string, Order>();
  const byKey = new Map<string, Order>();
  let n = 0;
  return {
    findByKey: async (tenantId, key) => byKey.get(`${tenantId}:${key}`),
    create: async ({ tenantId, totalMinor, idempotencyKey }) => {
      const order: Order = { id: `ord_${++n}`, tenantId, status: 'pending', totalMinor };
      byId.set(order.id, order);
      byKey.set(`${tenantId}:${idempotencyKey}`, order);
      return order;
    },
    findById: async (id) => byId.get(id),
    markPaid: async (id) => {
      const order = byId.get(id);
      if (order) order.status = 'paid';
      return order;
    },
  };
}

أساسيات الـ Supertest في درس Node رقم 29، الجزء 3. الجديد هنا: الـ app بقى factory بياخد الـ dependencies بتاعته، فالـ test يقدر يدّيله repository حقيقي أو fake من غير global. وبعدين الـ assertions تعدّي الـ status code وتوصل للـ contract: Location على الـ 201، الـ media type بتاع problem+json في الـ errors، مفيش X-Powered-By، والـ flags بتاعة Set-Cookie.

الـ request.agent(app) بيحفظ الـ cookies بين الطلبات، فـ sign-in وبعده طلب authenticated بيتقري زي session حقيقية. والفخ الحقيقي: الـ agent بيحترم الـ Secure. لو الـ cookie عليها Secure والطلب http، مش هيبعتها والطلب اللي بعده هيرجع 401 (اتقاس فوق). عشان كده الـ factory بياخد secureCookies، والـ tests بتاعة الـ HTTP بتدّي false، وtest واحد بيتأكد إن قيمة الـ production فيها الـ flag.

ليه الـ app object مش URL: الـ Supertest بيربطه بـ ephemeral port لكل طلب، فالملفات اللي شغالة in parallel مش ممكن تتخبط. لكن listen(3000) ثابت بيتخبط، و Vitest بيشغّل الملفات in parallel افتراضيًا.

فين هستخدمه في شغلي؟ أي API على Express أو Fastify: افصل createApp(deps) عن app.listen. ملف الـ server يبقى createApp({ orders: pgOrders(pool) }).listen(PORT) بس، والـ tests تستدعي createApp مباشرة. وفي الـ review، لو لقيت test فيه app.listen(3000) أو BASE_URL بيشاور على localhost، ده سبب flaky جاهز. والـ Location والـ problem+json جزء من الـ contract اللي الـ frontend بيعتمد عليه، فلازم يتختبروا زي الـ body بالظبط.

Part 2 — Why a real database 🟡 Intermediateالجزء 2 — ليه database حقيقية

English

SQLite and Postgres disagree in exactly the places integration tests exist for. Same SQL, same data, run for real below: a booking for the same instant written with a different UTC offset is two rows on SQLite (it stores text) and a 23505 on Postgres (it stores an instant). A jsonb document with its keys in another order: two rows on SQLite, 23505 on Postgres, because jsonb normalizes key order. @> does not even parse on SQLite. Where they agree, as with a partial index and ON CONFLICT that omits the predicate, both reject it. So an SQLite-backed suite passes while production returns 23505.

Testcontainers is the standard answer: a real Postgres, Redis or Kafka in Docker, started from the test run, thrown away at the end. Version 12 of the Node library has PostgreSqlContainer('postgres:18'), RedisContainer('redis:8'), and KafkaContainer(...).withKraft() for a broker with no ZooKeeper. There is no Docker on this machine, so the code is checked by the TypeScript 7 compiler and labelled below, with the real error it produces here.

Instead, this lesson runs a throwaway Postgres 18 from the binaries already installed, wrapped in the same shape (getConnectionUri(), stop()), so the swap to Testcontainers is one line. Same engine, same behaviour, no container.

PGlite (Postgres compiled to WASM) is a third option: measured here at ≈1.2 s to start against ≈5.5 s for initdb plus server start on this Windows machine. It speaks real Postgres SQL, so jsonb and partial indexes behave correctly. Its limit is concurrency: it has one connection, so transactions run one after another. The classic read-then-write race, real in Postgres, simply cannot happen. Fine for repository logic, misleading for anything about concurrency.

  let a, b;
  try {
    const r = sqlite.prepare(sqliteSql).run(...params);
    a = `ok, changes=${r.changes}`;
  } catch (e) {
    a = `ERROR ${e.message}`;

Note that the last two strategies isolate files: inside one file, tests share the database and need their own reset. TRUNCATE is roughly 20× the rollback cost per test here, and the per-file database clone dominates at this size: ≈ 400 ms per file. Schema-per-file is cheap here only because the DDL is two tables; its cost grows with your migration count.

Rollback is fastest and it silently breaks in three cases, all real below: (1) code under test runs its own BEGIN/COMMIT: the inner COMMIT ends the test's transaction and the row is left behind. (2) Code that wants SERIALIZABLE and retries: inside an open transaction Postgres rejects the isolation change with 25001, so the retry path can't be tested. (3) A second connection (a worker, a pool that picks another client) can't see uncommitted rows. When the code under test needs nesting, make it savepoint-aware.

Part 4 — Migrations in the setup 🟡 Intermediateالجزء 4 — الـ migrations في الـ setup

English

The test schema must come from the project's real migrations, run once in globalSetup. Tests never hand-write CREATE TABLE, because the moment they do, a bad migration can reach production with a green suite. Writing safe migrations is covered in section 07 · 2.5; the point here is that the tests exercise the same files that production runs.

The flow: globalSetup runs the migrations once into a template database, then clones it for each worker. In a real test, a planted typo in a migration failed the run with column "tennant_id" does not exist, before a single test ran.

An honest measurement: cloning does not automatically beat re-running migrations. With 150 small migrations here, migrating from scratch took ≈1.1 s and one clone took ≈1.3 s (the default WAL_LOG strategy), ≈1.7 s with FILE_COPY. A template pays off when migrations are slow (backfills, seed data) and it guarantees a single point of failure and identical databases per worker.

The drift check catches a broken down: run the newest migration up, down, up, and compare pg_dump --schema-only before and after. Clean migrations match. A planted down that renames the column instead of dropping it is caught on the second up.

import { readdirSync, readFileSync } from 'node:fs';
import path from 'node:path';
import type { Client } from 'pg';

const dir = path.resolve(import.meta.dirname, '../migrations');

// كل migration في transaction بتاعتها، فلو واحدة وقعت قاعدة البيانات مبتفضلش نص متعدّلة
export async function migrateUp(client: Client, folder = dir): Promise<string[]> {
  await client.query('CREATE TABLE IF NOT EXISTS schema_migrations (name text PRIMARY KEY)');
  const done = new Set((await client.query('SELECT name FROM schema_migrations')).rows.map((r) => r.name));
  const ups = readdirSync(folder).filter((f) => f.endsWith('.up.sql')).sort();
  const applied: string[] = [];
  for (const file of ups) {
    const name = file.replace('.up.sql', '');
    if (done.has(name)) continue;
    await client.query('BEGIN');
    try {
      await client.query(readFileSync(path.join(folder, file), 'utf8'));
      await client.query('INSERT INTO schema_migrations (name) VALUES ($1)', [name]);
      await client.query('COMMIT');
      applied.push(name);
    } catch (e) {
      await client.query('ROLLBACK');
      throw new Error(`migration ${file} failed: ${(e as Error).message}`);
    }
  }
  return applied;
}

export async function migrateDownLast(client: Client, folder = dir): Promise<void> {
  const { rows } = await client.query('SELECT name FROM schema_migrations ORDER BY name DESC LIMIT 1');
  const name = rows[0].name;
  await client.query('BEGIN');
  await client.query(readFileSync(path.join(folder, `${name}.down.sql`), 'utf8'));
  await client.query('DELETE FROM schema_migrations WHERE name = $1', [name]);
  await client.query('COMMIT');
}

export async function migrateDownAll(client: Client, folder = dir): Promise<void> {
  const { rows } = await client.query('SELECT name FROM schema_migrations ORDER BY name DESC');
  for (const { name } of rows) {
    await client.query('BEGIN');
    await client.query(readFileSync(path.join(folder, `${name}.down.sql`), 'utf8'));
    await client.query('DELETE FROM schema_migrations WHERE name = $1', [name]);
    await client.query('COMMIT');
  }
}

async function withDb<T>(db: string, fn: (c: Client) => Promise<T>): Promise<T> {
  const c = new Client({ connectionString: url(db) });
  await c.connect();
  try {
    return await fn(c);
  } finally {
    await c.end();
  }
}

English

A shared fixture couples tests that have nothing to do with each other. Below, two test files read the same JSON. Someone edits it for a refund test, changing the total from 15000 to 9000, and the invoice test, which nobody touched, fails.

A factory creates what the test needs and the test states only what it cares about: createUser(pool, { role: 'admin' }) says "an admin", and the tenant, the email and the password hash come from defaults. A builder reads like a sentence: anOrder().paid().withItems(3). A persisting factory also builds the foreign-key chain itself: tenant, then user, then order, then items, with a sequence so unique columns never collide.

Random data has one trap: a failure you cannot reproduce. Seed faker and print the seed when a test fails, so the run can be replayed with FAKER_SEED=12345. With the same seed the generated total was 80663 on both runs here; with another seed it was 46235.

export interface OrderSpec {
  tenantId?: string;
  status: 'pending' | 'paid';
  totalMinor: number;
  itemCount: number;

export function anOrder() {
  const spec: OrderSpec = { status: 'pending', totalMinor: faker.number.int({ min: 1_000, max: 90_000 }), itemCount: 1 };
  return {
    forTenant(tenantId: string) {
      spec.tenantId = tenantId;
      return this;
    },
    paid() {
      spec.status = 'paid';
      return this;
    },
    withTotal(totalMinor: number) {
      spec.totalMinor = totalMinor;
      return this;
    },
    withItems(itemCount: number) {
      spec.itemCount = itemCount;
      return this;
    },
    build(): OrderSpec {
      return { ...spec };
    },
    async create(pool: Pool) {
      // بيبني الـ chain بتاع الـ foreign keys لوحده: tenant ثم user ثم order ثم items
      const user = await createUser(pool, { tenantId: spec.tenantId });
      const { rows } = await pool.query(
        'INSERT INTO orders (tenant_id, user_id, status, total_minor, idempotency_key) VALUES ($1, $2, $3, $4, $5) RETURNING *',
        [user.tenant_id, user.id, spec.status, spec.totalMinor, `seed-key-${next()}`],
      );
      const order = rows[0] as { id: string; tenant_id: string; status: string; total_minor: number };
      for (let i = 0; i < spec.itemCount; i++) {
        await pool.query('INSERT INTO order_items (order_id, sku, qty) VALUES ($1, $2, $3)', [order.id, `SKU-${next()}`, faker.number.int({ min: 1, max: 5 })]);
      }
      return order;
    },
  };
}

Part 6 — A worked suite 🟡 Intermediateالجزء 6 — suite كاملة

English

Everything together: the real app, the real repository, real Postgres, real migrations, factories. Three behaviours that matter for orders: replaying the same Idempotency-Key returns the first response and creates one row; a user from another tenant gets 403 and the order stays pending; and paying moves pending to paid once, with a second attempt getting 409.

A note on 403: returning 404 for another tenant's order hides that it exists, and that is what lesson 03's refundOrder did. Which one is right depends on your API contract. This suite pins 403, and the assertion is one line if you choose 404.

Parallelism: VITEST_POOL_ID is the worker number, from 1 to maxWorkers, and it selects the database, so files on different workers cannot see each other's rows. To have enough work to measure, the orders suite was copied into 8 files (10 files and 39 tests in total). Scaling isn't linear, because part of every run is fixed: starting Postgres (≈5.5 s for initdb and start here) and cloning eight databases (≈2 s). What parallelism breaks, and what to do about it, is in lesson 08.

Cheat sheet · الخلاصة

  • createApp(deps) + request(app): no port, no collisions. Assert status, body, headers (Location, problem+json, no X-Powered-By, cookie flags).
  • request.agent keeps cookies, and won't send a Secure cookie over http (got 401): make the flag a dependency.
  • SQLite isn't Postgres: same instant at another offset and jsonb key order gave 2 rows on SQLite and 23505 on Postgres. @> doesn't parse.
  • Testcontainers: new PostgreSqlContainer('postgres:18').start(), getConnectionUri(), stop(). Needs Docker. Same shape for a throwaway Postgres.
  • PGlite starts faster (≈1.2 s vs ≈5.5 s here) but has one connection: a real lost update on Postgres was invisible on PGlite (90 vs 80).
  • Rollback ≈1.4 ms per test, TRUNCATE ≈27 ms, clone per file ≈400 ms. Rollback breaks with inner COMMIT, SERIALIZABLE retries (25001) and a second connection; savepoints handle nesting.
  • Real migrations in globalSetup, once, into a template; a bad one stops the run.
  • Up-down-up plus pg_dump --schema-only catches a bad down. Filter \restrict in pg_dump 18, and down only the newest migration.
  • Factories state only what the test cares about. Builders read like a sentence. Seed faker and print the seed on failure.
  • VITEST_POOL_ID picks the worker's database. Fixed setup cost limits scaling: 1, 2, 4 workers gave ≈17.6, ≈11.1, ≈10.4 s.
بالعامية
  • createApp(deps) مع request(app): من غير port ومن غير تخبيط. اتأكد من الـ status والـ body والـ headers (Location، problem+json، مفيش X-Powered-By، وflags الـ cookie).
  • الـ request.agent بيحفظ الـ cookies، ومش بيبعت cookie عليها Secure على http (طلعت 401): خلي الـ flag dependency.
  • SQLite مش Postgres: نفس اللحظة بـ offset تاني وترتيب keys الـ jsonb اديوا صفين على SQLite و 23505 على Postgres، والـ @> مش بتتفهم.
  • الـ Testcontainers: new PostgreSqlContainer('postgres:18').start() وgetConnectionUri() وstop(). محتاج Docker، ونفس الشكل لـ Postgres مؤقت.
  • الـ PGlite بيبدأ أسرع (≈1.2 ثانية مقابل ≈5.5) بس عنده connection واحدة: lost update حقيقي على Postgres ماظهرش على PGlite (90 مقابل 80).
  • الـ rollback ≈1.4 ms للـ test، والـ TRUNCATE ≈27 ms، والـ clone لكل ملف ≈400 ms. الـ rollback بيكسر مع COMMIT داخلي، و retries على SERIALIZABLE (25001)، و connection تانية؛ والـ savepoints بتحل الـ nesting.
