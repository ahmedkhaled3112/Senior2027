Why this matters · ليه ده مهم

English

Cost is a production metric that nobody pages you for until it is expensive. A single forgotten debug log or a job pulling data through a NAT Gateway can add thousands a month, and it usually hides behind a line item called EC2 - Other. Knowing how to read the bill, price a design before it exists and say what a feature costs is one of the clearest differences between a Senior and someone who only writes the code.

It also comes up directly in interviews: "the AWS bill went up 40% this month, how do you investigate?" is exit question 16 of this section, and we answer it with a real script.

بالعامية

التكلفة metric في الـ production محدش بيعمل لك عليها page غير لما تبقى غالية. log واحد للـ debug اتنسي، أو job بيسحب data من خلال NAT Gateway، ممكن يزوّدوا آلاف الدولارات في الشهر، وغالبًا مستخبيين ورا بند اسمه EC2 - Other. إنك تعرف تقرا الـ bill، وتسعّر design قبل ما يتبني، وتقول الـ feature دي بتكلّف كام، ده من أوضح الفروق بين السنيور واللي بيكتب الكود بس.

وكمان بييجي في الـ interviews على طول: "فاتورة AWS زادت 40% الشهر ده، هتحقق إزاي؟" ده سؤال 16 من اختبار الخروج بتاع القسم، وهنجاوبه بـ script حقيقي.

Part 1 — Investigating the bill 🟡 Intermediateالجزء 1 — التحقيق في الـ bill

English

When the bill jumps, don't start by guessing. Work top-down the way Cost Explorer lets you: group by service, then region, then usage type. Usage type is the level that names the actual meter. EC2 - Other tells you nothing, while NatGateway-Bytes tells you exactly what to look for. Then narrow by time with daily granularity: a step change on a particular day almost always lines up with a deploy, and a slow ramp means growth. Finally, compare against a usage driver, because a bill that grew 40% while requests grew 40% is not a bug.

Tagging decides whether you can answer "whose is it". Tags only help for allocation once the key is activated as a cost allocation tag: after you apply a tag it can take up to 24 hours for the key to appear in the billing console, and up to another 24 hours to activate. Whatever isn't tagged is unallocated spend, and it tends to be exactly where the surprise is, so tagging belongs in your IaC defaults rather than in a reminder.

بالعامية

لما الفاتورة تقفز، متبدأش بالتخمين. انزل من فوق لتحت زي ما Cost Explorer بيخليك: بالـ service، وبعدين الـ region، وبعدين الـ usage type. الـ usage type هو المستوى اللي بيسمّي العداد الحقيقي: EC2 - Other مش بيقولك حاجة، وNatGateway-Bytes بيقولك بالظبط تدوّر على إيه. بعدها ضيّق بالوقت بـ daily granularity: قفزة في يوم معين غالبًا بتيجي مع deploy، وزيادة بطيئة معناها نمو. وأخيرًا قارن بالـ usage driver، لأن فاتورة زادت 40% والـ requests زادت 40% مش bug.

الـ tagging هو اللي بيحدد تقدر تجاوب "بتاع مين" ولا لأ. الـ tags بتفيد في الـ allocation بس بعد ما الـ key يتفعل كـ cost allocation tag: بعد ما تحط التاج ممكن ياخد لحد 24 ساعة عشان الـ key يظهر في الـ billing console، ولحد 24 ساعة كمان عشان يتفعّل. وأي حاجة من غير تاج بتبقى unallocated spend، وغالبًا هو ده المكان اللي فيه المفاجأة، فالـ tagging مكانه الـ IaC defaults مش reminder.

فين هستخدمه في شغلي؟ الـ CTO بعت لك على Slack "الفاتورة دي ليه كده؟". بدل ما تقعد تبص في الـ console ساعتين: export من Cost Explorer للشهرين، و bill-diff.ts، وفي 10 دقايق بترد "54% من الزيادة NAT data، بدأت يوم 12، و الـ reports job اتغير اليوم ده". والغلطة الشائعة: تبص على الـ service بس وتقول "EC2 زاد" فتروح تقلل instances وهي مش السبب.
Interview question (exit test Q16): "The AWS bill went up 40% this month. How do you investigate?" Confirm it's real first: compare full periods and the same number of days, and check for one-off charges such as an annual payment. Group by service, then usage type, in Cost Explorer. Switch to daily to find whether it's a step or a slope. Compare against a usage driver like requests. Correlate the step date with deploys. Fix the cause, then add a guardrail: an AWS Budget alert, anomaly detection, and tagging so the next one has an owner. Lastly, say how much you expect to recover.

Part 2 — The FinOps mindset 🔴 Advancedالجزء 2 — طريقة تفكير الـ FinOps

English

The FinOps Foundation defines FinOps as an operational framework and cultural practice that maximizes the business value of technology and creates financial accountability through collaboration between engineering, finance and business. The engineering translation is short: cost is a metric of the service, and it belongs on the same dashboard as latency and errors. A monthly invoice arrives too late to connect to a change. Cost per 1,000 requests does connect to a change, and it stays comparable while traffic grows.

Who owns the number? The team that owns the service owns its cost per request. The platform team owns shared costs and how they are divided up. If nobody's name is on it, nobody will act on it. Capacity reasoning (requests per task, utilization target) is in System Design lesson 41, part 3, so here we only turn its output into money.

// الـ server ده بنقيس بيه: نفس الـ endpoint بنسختين بتكلفة CPU مختلفة
import http from "node:http";
import { createHash } from "node:crypto";

const mode = process.argv[2] ?? "v1";

// نسخة v1 بتعمل الشغل كله، و v2 الـ query اتظبطت فبقت خُمس الشغل
const ROUNDS = mode === "v2" ? 1600 : 8000;

function buildReport() {
  // شغل CPU حقيقي بيمثل تجميع report لكل request
  let h = "seed";
  for (let i = 0; i < ROUNDS; i++) h = createHash("sha256").update(h).digest("hex");
  return JSON.stringify({ status: "ok", digest: h });
}

const server = http.createServer((_req, res) => {
  const body = buildReport();
  res.setHeader("content-type", "application/json");
  res.end(body);
});

server.listen(0, "127.0.0.1", () => process.send({ port: server.address().port }));
process.on("message", () => server.close(() => process.exit(0)));

const VCPU_H = 0.04048, GB_H = 0.004445, HOURS = 730;
const TASK_HOUR = 1 * VCPU_H + 2 * GB_H;
// مش بنشغل الـ task على 100%: الـ target الواقعي 60%
const TARGET_UTIL = 0.6;
const MONTHLY_REQUESTS = 2_000_000_000;

async function measure(version) {
  const child = fork(new URL("./server.mjs", import.meta.url), [version], { stdio: ["ignore", "ignore", "inherit", "ipc"] });
  const [{ port }] = await once(child, "message");
  const r = await autocannon({ url: `http://127.0.0.1:${port}/report`, connections: 20, duration: 4 });
  child.send("stop");
  await once(child, "exit");
  return { version, rps: r.requests.average, p99: r.latency.p99, errors: r.errors + r.non2xx };

بالعامية

الـ FinOps Foundation بتعرّف الـ FinOps إنه إطار تشغيلي وثقافة بتزوّد القيمة من التكنولوجيا وبتعمل financial accountability بالتعاون بين الهندسة والمالية والـ business. الترجمة الهندسية بسيطة: الـ cost هو metric للـ service، ومكانه نفس الـ dashboard بتاع الـ latency والـ errors. الفاتورة الشهرية بتيجي متأخر جدًا عشان تربطها بتغيير. لكن الـ cost لكل 1000 request بيتربط بالتغيير، وبيفضل قابل للمقارنة حتى لو الـ traffic كبر.

مين صاحب الرقم؟ الفريق صاحب الـ service هو صاحب الـ cost per request بتاعه، وفريق الـ platform صاحب الـ shared costs وطريقة توزيعها. لو مفيش اسم حد على الرقم، محدش هيتحرك. وحساب الـ capacity (requests لكل task والـ utilization target) موجود في درس 41 في System Design، الجزء 3، فهنا بنحوّل النتيجة لفلوس بس.

فين هستخدمه في شغلي؟ في الـ PR description بتاع أي optimization: اكتب "p99 نزل من X لـ Y، و cost/1k request نزل من A لـ B". ولما حد يقترح feature بتزوّد الشغل على كل request، اسأل الرقم ده هيبقى كام. والغلطة الشائعة: تتكلم عن الـ p99 لوحده وتنسى إن نفس التغيير ممكن يقلل عدد الـ tasks 4 مرات.

Part 3 — Right-sizing and autoscaling 🔴 Advancedالجزء 3 — الـ right-sizing والـ autoscaling

English

Right-size from measurements, with different rules for each resource. CPU uses a high percentile with a target utilization, because running short only slows the service down. Memory uses the maximum with a margin, because crossing the limit gets the task killed. Node adds its own wrinkle: one event loop uses about one core, so a task above 1 vCPU rarely helps unless you run worker threads or several processes.

Right-sizing is not the same as downsizing. In the sample below two services are too big, one is memory-bound and gets slightly more expensive, and one is starving and needs to grow. Autoscaling then has to work in both directions. Scale-in is the half teams forget, either because they disable it after one bad night or because the threshold is too tight, and the result is capacity that only ever goes up. New tasks also take minutes to arrive, while removal is instant, so you need a gap between the out and in thresholds plus a cooldown.

// الـ policies بنقارنها على يوم 1440 دقيقة بنفس الـ traffic بالظبط
const TASK_RPS = 100;
const MIN_TASKS = 2;

function rpsAt(min: number): number {
  const h = min / 60;
  // منحنى يومي: ذروة حوالين الساعة 8 مساءً، وسبايك نص ساعة الساعة 12
  const base = 200 + 500 * Math.pow(Math.max(0, Math.sin(((h - 6) / 24) * 2 * Math.PI)), 2);
  return base + (h >= 12 && h < 12.5 ? 400 : 0);
}

interface Policy { name: string; outTarget: number; inTarget: number | null; inCooldownMin: number; }
const POLICIES: Policy[] = [
  { name: "scale-out only (no scale-in)", outTarget: 0.6, inTarget: null, inCooldownMin: 0 },
  { name: "scale-in, 5 min cooldown", outTarget: 0.6, inTarget: 0.45, inCooldownMin: 5 },
  { name: "scale-in, no cooldown, tight band", outTarget: 0.6, inTarget: 0.58, inCooldownMin: 0 },
];

// الـ task الجديد مش بيشتغل فورًا: alarm ثم pull للـ image ثم health check
const START_DELAY_MIN = 3;

function simulate(p: Policy) {
  let running = MIN_TASKS, lastIn = -Infinity, outEvents = 0, inEvents = 0, taskMinutes = 0, overloaded = 0;
  const pending: number[] = [];
  for (let m = 0; m < 1440; m++) {
    while (pending.length && pending[0]! <= m) { pending.shift(); running++; }
    const rps = rpsAt(m);
    const desiredCapacity = running + pending.length;
    const util = rps / (desiredCapacity * TASK_RPS);
    if (util > p.outTarget) {
      // الـ scale-out بيطلب العدد الناقص مرة واحدة، زي الـ target tracking
      const need = Math.ceil(rps / (TASK_RPS * p.outTarget)) - desiredCapacity;
      for (let i = 0; i < need; i++) pending.push(m + START_DELAY_MIN);
      outEvents++;
    } else if (p.inTarget !== null && util < p.inTarget && m - lastIn >= p.inCooldownMin && running > MIN_TASKS) {
      running--;
      inEvents++;
      lastIn = m;
    }
    taskMinutes += running;
    // تحميل فوق 90% معناه الـ requests بتستنى في الطابور
    if (rps / (running * TASK_RPS) > 0.9) overloaded++;
  }
  return { avgTasks: taskMinutes / 1440, outEvents, inEvents, overloaded };
}

بالعامية

اعمل right-size من القياسات، وبقواعد مختلفة لكل resource. الـ CPU بناخد له percentile عالي مع target utilization، لأن النقص بيبطّأ الـ service بس. الـ memory بناخد لها الـ max مع هامش، لأن تجاوز الحد بيقتل الـ task. و Node ليها نقطة خاصة: event loop واحد بيستخدم حوالي core واحد، فـ task أكبر من 1 vCPU نادرًا ما بيفيد إلا لو مشغّل worker threads أو كذا process.

الـ right-sizing مش هو الـ downsizing. في العيّنة فوق، اتنين كبار زيادة، وواحد الـ memory بتحكمه فبيغلى شوية، وواحد بيعاني ومحتاج يكبر. وبعدها الـ autoscaling لازم يشتغل في الاتجاهين. الـ scale-in هو النص اللي الفرق بتنساه، إما عشان عطّلوه بعد ليلة وحشة أو عشان الـ threshold ضيق أوي، والنتيجة capacity بتطلع وبس. وكمان الـ tasks الجديدة بتاخد دقايق عشان توصل، بينما الشيل فوري، فمحتاج مسافة بين threshold الـ out والـ in، و cooldown.

فين هستخدمه في شغلي؟ كل ربع: اسحب p95 CPU و max memory من CloudWatch لآخر 14 يوم وشغّل rightsize.ts. وقبل ما تنزّل الحجم، اعمل load test على الحجم الجديد. والغلطة الشائعة: تعطّل الـ scale-in بعد حادثة فالفاتورة تفضل عالية للأبد، والحل cooldown أطول ومسافة بين الـ thresholds مش تعطيله.
Trade-off: how much headroom? A lower target utilization (say 50%) absorbs spikes and task startup time, and you pay for idle capacity all day. A higher one (70%+) is cheaper and gives you less warning. Pick it from your startup time and how spiky the traffic is, then use scheduled scaling for spikes you can predict, like a nightly job or a Friday campaign.
الـ target utilization الأقل (مثلًا 50%) بيستحمل الـ spikes ووقت بدء الـ task، بس بتدفع على capacity فاضية طول اليوم. والأعلى (70% وأكتر) أرخص وبيديك إنذار أقل. اختاره على أساس وقت البدء وقد إيه الـ traffic متذبذب، واستخدم scheduled scaling للـ spikes اللي تقدر تتوقعها، زي job بالليل أو campaign يوم الجمعة.

Part 5 — Spot and commitments 🔴 Advancedالجزء 5 — الـ Spot والـ commitments

English

Spot is spare capacity at a discount that AWS can take back. EC2 gives a two-minute interruption notice, and for Fargate Spot the warning arrives as a task state change event and a SIGTERM to the task, with SIGKILL following after stopTimeout (default 30 seconds, maximum 120). That makes it a good fit for work that can be retried: queue workers and CI. It is a poor fit for a single-replica API or anything holding state.

A queue worker is safe on Spot if two things hold. On notice, it stops taking jobs and finishes the ones in hand. And if it dies anyway, the job is not lost: BullMQ holds a lock per job, and when the lock expires another worker's stalled-job check moves the job back to the queue. That means the same job can run twice, so the effect has to be idempotent. The worker below uses SET NX for that.

Commitments are the opposite trade: you promise a fixed hourly spend for one or three years in exchange for a discount. Compute Savings Plans apply across EC2, Fargate and Lambda regardless of instance family, size or region, Reserved Instances are less flexible, and there are also Database Savings Plans for databases. Break-even is the share of hours the thing must actually run for the discount to win. The rule that follows: commit only to the baseline that runs all the time, and leave everything above it on-demand or Spot.

  spot-a takes job 17
     |
     +-- notice arrives --> worker.close()
     |                      stops taking jobs, finishes 17, exits 0
     |                      -> job 17 delivered once
     |
     +-- killed first ----> lock on job 17 expires (1.5 s)
                            stalled check on ondemand-b moves it to waiting
                            ondemand-b runs job 17 again
                            SET NX done:17 -> effect happens once
الرسمة بتوضح السيناريوهين. لو الإشعار وصل، الـ worker بيعمل close(): بيبطّل يسحب jobs، ويخلص اللي معاه، ويخرج بـ 0، فالـ job اتسلم مرة واحدة. لو اتقتل قبل كده، الـ lock بيخلص بعد 1.5 ثانية، والـ stalled check عند الـ worker التاني بيرجّع الـ job للطابور ويتشغل تاني، والـ SET NX بيضمن إن التأثير يحصل مرة واحدة بس.
Stand-in for the interruption notice BullMQ and Redis 8 below are real. The notice is not: an IPC message replaces the real SIGTERM, because on Windows child.kill('SIGTERM') ends the process without running a handler. spot.kill() stands in for the SIGKILL after stopTimeout. On Linux you would handle process.on("SIGTERM", ...) with the same body. It doesn't capture real capacity behaviour or AWS's timing.

  await once(onDemand, "exit");
  await queue.close();

بالعامية

الـ Spot هي capacity فاضية بخصم، و AWS يقدر يسحبها. الـ EC2 بيدي إشعار قبلها بدقيقتين، والـ Fargate Spot الإنذار بييجي كـ task state change event و SIGTERM للـ task، وبعدها SIGKILL بعد الـ stopTimeout (الـ default 30 ثانية والأقصى 120). فمناسبة للشغل اللي ينفع يتعاد: الـ queue workers والـ CI. ومش مناسبة لـ API بـ replica واحدة أو أي حاجة ماسكة state.

الـ queue worker بيبقى آمن على Spot بشرطين. لما الإشعار ييجي، يبطّل يسحب jobs ويخلص اللي في إيده. ولو مات برضه، الـ job ميضيعش: الـ BullMQ بيمسك lock لكل job، ولما الـ lock يخلص، الـ stalled check عند worker تاني بيرجّع الـ job للطابور. معنى كده إن نفس الـ job ممكن يتشغل مرتين، فلازم التأثير يبقى idempotent، والـ worker اللي فوق بيستخدم SET NX عشان كده.

Interview question: "Would you run your Node workers on Spot? What has to be true?" Yes for retryable work, with three conditions. Jobs must survive a dead worker (locks and stalled-job recovery, or a visibility timeout). Handlers must be idempotent, because a job can run twice; in my test 2 of 40 were re-delivered and the effects were still 40. Part 6 — Unit economics 🔴 Advancedالجزء 6 — الـ unit economics

English

A total bill can't tell you who or what is profitable. For that you need cost per tenant and per feature: meter the usage with a tenant_id and a feature label, turn last month's infrastructure into unit costs, and add the fixed cost through an allocation key. That key is a policy decision. Here fixed cost follows request share, and a different key would change who looks expensive, so write it down and keep it stable.

The output is a business conversation, in numbers. In the sample a starter tenant loses money on a $49 plan, and PDF export costs roughly nine times what it earns, with one tenant behind 92% of it. The options are a usage limit, a higher price or a cheaper implementation, and engineering is the only team that can produce the number. AI features are the sharpest case because each request has a real marginal cost; per-request LLM cost is covered in section 12 · 2.6.

Solution · الحل 
// نفس firstStep من bill-diff.ts، على سلسلة تانية: الـ CloudWatch logs كل يوم
function firstStep(series: number[], factor = 3): number {
  for (let i = 3; i < series.length; i++) {
    const before = [...series.slice(0, i)].sort((a, b) => a - b);
    const median = before[Math.floor(before.length / 2)]!;
    if (series[i]! > median * factor) return i;
  }
  return -1;
}

const logs = Array.from({ length: 31 }, (_, i) => (i < 19 ? 28 : 96));

// → -1

Cheat sheet · الخلاصة

  • Investigate top-down: service, usage type, day, then the deploy that matches the step.
  • Usage type names the meter. EC2 - Other is where NAT and EBS hide.
  • Cost allocation tags need activation: up to 24 h to appear plus up to 24 h to activate. Untagged spend is where surprises hide.
  • Put cost per 1,000 requests next to p99, owned by the service's team.
  • Right-size CPU from p95 at a target utilization and memory from the max with a margin. Node rarely uses more than one vCPU.
  • Scale in too, with a gap between thresholds and a cooldown. A tight band flaps.
  • Traps: NAT $0.045/GB, cross-AZ $0.01/GB each way, cross-region $0.02/GB, egress $0.09/GB, logs $0.50/GB ingest, gp3 $0.08/GB-month (us-east-1, 2026-11-09).
  • S3 gateway endpoints have no additional charge and remove S3 traffic from the NAT.
  • Spot for retryable work: drain on notice, keep idempotent handlers, keep some on-demand base.
  • Commit to the baseline only. Break-even is the committed rate over the on-demand rate.
  • Unit economics: per-tenant and per-feature cost from labelled usage; the allocation key is a written decision.
  • Estimate before building: written assumptions, fixed vs traffic-driven, a range, and what's excluded.

  • حقق من فوق لتحت: الـ service، وبعدين الـ usage type، وبعدين اليوم، وبعدين الـ deploy اللي بييجي مع القفزة.
  • الـ usage type بيسمّي العداد الحقيقي، وEC2 - Other هو المكان اللي الـ NAT والـ EBS بيستخبوا فيه.
