Why this matters · ليه ده مهم

English

Most tests run on a healthy machine with one request at a time and a database that always answers. Production has none of that: an N+1 query slips in, the database stalls, a relay dies mid-batch, and a message arrives twice or out of order. This lesson turns each of those into a repeatable test against real Node, Postgres and Redis, with the failure counted rather than assumed. In interviews, "what happens when the database hangs?" is the question that separates people who have run production from people who haven't.

بالعامية

معظم الـ tests بتشتغل على جهاز سليم، بـ request واحد في المرة، و database دايمًا بترد. الـ production مفيهوش حاجة من دي: N+1 query بيتسلل، الـ database بتقف، الـ relay بيموت في نص الـ batch، ورسالة بتوصل مرتين أو بترتيب غلط. في الدرس ده هنحوّل كل حالة من دول لـ test بيتكرر على Node و Postgres و Redis حقيقيين، والفشل بيتعد مش بيتفرض. وفي الـ interviews، سؤال "لو الـ database علّقت إيه اللي هيحصل؟" هو اللي بيفرّق بين اللي شغّل production واللي مشغّلش.

Part 1 — Load tests as tests 🔴 Advancedالجزء 1 — الـ load tests كـ tests

English

A load test becomes part of the test suite when it has assertions and an exit code. How to design and read one is in section 04, lesson 35. Here the new step is calling autocannon programmatically inside a Vitest file, against the real app and a real Postgres, and asserting on the result object: errors, timeouts, non2xx and latency.p99.

The assertion is an error budget plus a latency budget. Errors must be zero in this test, because any error during a short run on loopback is a bug. The p99 limit of 500 ms is deliberately loose: a fixed number in milliseconds only catches disasters, and it would flap if it were tight, since CI machines differ. Part 2 deals with that properly.

For load from outside the Node process, or at higher rates, k6 is the common choice. Its thresholds play the same role as assertions and set a non-zero exit code when they fail.

import express, { type NextFunction, type Request, type Response } from "express";
import type { Pool } from "pg";

export interface AppOptions {
  nPlusOne?: boolean;
}

export function createApp(pool: Pool, opts: AppOptions = {}) {
  const app = express();
  let queries = 0;
  // العدّاد: كل query بيعدّي من هنا، فعدد الـ queries لكل request رقم مظبوط
  const query = (text: string, values?: unknown[]) => {
    queries++;
    return pool.query(text, values);
  };

  app.get("/healthz", async (_req, res) => {
    await query("SELECT 1");
    res.json({ ok: true });
  });

  app.get("/orders", async (_req, res) => {
    if (!opts.nPlusOne) {
      const { rows } = await query(
        `SELECT o.id, o.status, o.total_minor, c.name AS customer
         FROM orders o JOIN customers c ON c.id = o.customer_id
         ORDER BY o.id LIMIT 20`,
      );
      res.json(rows);
      return;
    }
    // ❌ الـ regression المزروع: query لكل order عشان يجيب اسم العميل
    const { rows } = await query("SELECT id, status, total_minor, customer_id FROM orders ORDER BY id LIMIT 20");
    for (const row of rows) {
      const customer = await query("SELECT name FROM customers WHERE id = $1", [row.customer_id]);
      row.customer = customer.rows[0].name;
    }
    res.json(rows);
  });

  app.use((err: Error, _req: Request, res: Response, _next: NextFunction) => {
    res.status(503).json({ error: "unavailable", detail: err.message });
  });

  return { app, queryCount: () => queries, resetQueries: () => { queries = 0; } };
}

export const makePool = (url: string, extra: PoolConfig = {}) =>
  new Pool({ connectionString: url, max: 10, ...extra });

export async function seed(url: string) {
  const pool = makePool(url, { max: 1 });
  await pool.query(`
    DROP TABLE IF EXISTS orders, customers;
    CREATE TABLE customers (id int PRIMARY KEY, name text NOT NULL);
    CREATE TABLE orders (
      id int PRIMARY KEY, customer_id int NOT NULL REFERENCES customers(id),
      status text NOT NULL, total_minor int NOT NULL
    );
    INSERT INTO customers SELECT g, 'customer-' || g FROM generate_series(1, 500) g;
    INSERT INTO orders SELECT g, 1 + g % 500, 'paid', 1000 + g FROM generate_series(1, 5000) g;
    ANALYZE;
  `);
  await pool.end();
}
// الحارس: أي port فاضي أو default يتمنع قبل ما أي client يتوصل
export function safePort(port: string | number): number {
  const n = Number(port);
  if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port ${port}`);
  }
  return n;
}
import autocannon from "autocannon";
import type { AddressInfo } from "node:net";
import type { Server } from "node:http";

export interface LoadResult { p50: number; p99: number; rps: number; non2xx: number; errors: number; timeouts: number }

export const portOf = (server: Server) => (server.address() as AddressInfo).port;

export async function load(url: string, durationSec = 2, connections = 10): Promise<LoadResult> {
  const r = await autocannon({ url, connections, duration: durationSec });
  return {
    p50: r.latency.p50,
    p99: r.latency.p99,
    rps: r.requests.average,
    non2xx: r.non2xx,
    errors: r.errors,
    timeouts: r.timeouts,
  };
}

export const median = (xs: number[]) => {
  const s = xs.toSorted((a, b) => a - b);
  return s[Math.floor(s.length / 2)]!;
};

export interface Sample { ratio: number; calibrationP99: number; ordersP99: number; rps: number }

// القياس: الـ endpoint المرجعي والـ endpoint اللي بنراقبه في نفس اللحظة تقريبًا
export async function sample(base: string, seconds = 2): Promise<Sample> {
  const calibration = await load(`${base}/healthz`, seconds);
  const orders = await load(`${base}/orders`, seconds);
  return {
    ratio: orders.p99 / Math.max(calibration.p99, 1),
    calibrationP99: calibration.p99,
    ordersP99: orders.p99,
    rps: orders.rps,
  };
}

Part 2 — Catching a regression 🔴 Advancedالجزء 2 — إزاي تمسك الـ regression

English

To catch a slowdown you compare against a baseline stored in the repo. Comparing milliseconds across machines doesn't work, so the script measures a cheap calibration endpoint (/healthz) and the watched endpoint back to back, and compares the ratio of their p99s. A slow CI runner moves both numbers, so the ratio holds better.

Noise is real and the output shows it. Five baseline runs of the same code gave ratios of 1, 1, 1, 1.5 and 2.5. A single run could have reported 2.5 against a limit of 1.5, a false alarm. The median of five reported 1. Latency here is also reported in whole milliseconds, so on an endpoint this fast one extra millisecond moves the ratio a lot.

The strongest signal isn't timing at all. The app counts queries, and queries per request is an exact number with no noise. The planted N+1 took it from 1 to 21, and the median ratio from 1 to 4.5, so the gate failed with exit code 1 and printed the comparison. Check the query count on every PR, because it's cheap and deterministic. Run the timing comparison nightly on a quiet runner: it took about 20 seconds of load here, and it's meaningless on a busy machine.

Part 3 — Fault injection 🔴 Advancedالجزء 3 — الـ fault injection

English

A fault-injection test forces a dependency to misbehave and asserts what your service does. The concepts are in section 10, lesson 23 and the resilience code in section 08, lesson 22. What's new is the test harness: a small TCP proxy between the app and real Postgres that can add latency, swallow all traffic (a blackhole, where the connection stays open and nothing comes back), or cut every connection.

The contract under test: while the database is sick, every request gets a 503 inside its budget, none hangs, and the service recovers by itself afterwards. With node-postgres defaults there are no timeouts, so the blackhole left all 40 requests hanging until the client gave up at 3 seconds. Worse, 65 requests were still queued for a connection when the burst ended, including requests whose callers had already left. That queue is how a slow database becomes an out-of-memory crash.

With connectionTimeoutMillis: 300 and query_timeout: 500, all 40 got a 503, in about 320 ms under the blackhole and about 516 ms under latency, and nothing stayed queued. A separate trap: a pool emits 'error' when an idle connection dies, and with no listener Node treats that as an uncaught exception. The child process without one exited with code 1 at the moment the connections were cut.

import net from "node:net";

export type Fault = { kind: "none" } | { kind: "latency"; ms: number } | { kind: "blackhole" };

// الـ stand-in ده فكرة Toxiproxy بس: مفيش API ولا bandwidth ولا partial writes
export class ChaosProxy {
  #fault: Fault = { kind: "none" };
  #server: net.Server;
  #sockets = new Set<net.Socket>();

  constructor(targetPort: number) {
    this.#server = net.createServer((client) => {
      if (this.#fault.kind === "blackhole") {
        // الـ blackhole: الاتصال بيتقبل وبعدها مفيش ولا byte بيرجع
        this.#track(client);
        client.on("error", () => {});
        return;
      }
      const upstream = net.connect(targetPort, "127.0.0.1");
      this.#track(client);
      this.#track(upstream);
      const forward = (from: net.Socket, to: net.Socket) => {
        from.on("data", (chunk) => {
          if (this.#fault.kind === "blackhole") return;
          const delay = this.#fault.kind === "latency" ? this.#fault.ms : 0;
          if (delay) setTimeout(() => to.destroyed || to.write(chunk), delay);
          else if (!to.destroyed) to.write(chunk);
        });
        from.on("close", () => to.destroy());
        from.on("error", () => to.destroy());
      };
      forward(client, upstream);
      forward(upstream, client);
    });
  }

  #track(socket: net.Socket) {
    this.#sockets.add(socket);
    socket.on("close", () => this.#sockets.delete(socket));
  }

  listen(): Promise<number> {
    return new Promise((resolve) =>
      this.#server.listen(0, "127.0.0.1", () => resolve((this.#server.address() as net.AddressInfo).port)),
    );
  }

  set(fault: Fault) { this.#fault = fault; }

async function burst(base: string, count = 40, capMs = 3_000) {
  const started = performance.now();
  const results = await Promise.all(
    Array.from({ length: count }, async () => {
      const t0 = performance.now();
      try {
        const res = await fetch(`${base}/orders`, { signal: AbortSignal.timeout(capMs) });
        await res.arrayBuffer();
        return { status: res.status, ms: performance.now() - t0 };
      } catch {
        return { status: 0, ms: performance.now() - t0 };
      }
    }),
  );
  const answered = results.filter((r) => r.status !== 0);
  return {
    ok200: results.filter((r) => r.status === 200).length,
    unavailable503: results.filter((r) => r.status === 503).length,
    hung: results.filter((r) => r.status === 0).length,
    slowestAnsweredMs: Math.round(Math.max(0, ...answered.map((r) => r.ms))),
    totalMs: Math.round(performance.now() - started),
  };
}

Part 5 — Consumer idempotency and ordering 🔴 Advancedالجزء 5 — الـ idempotency والترتيب عند الـ consumer

English

Since the relay delivers at least once, the consumer must handle repeats. The pattern is in section 08, lesson 24. Real results with BullMQ on Redis:

  • No dedupe, delivered twice: 2 side effects. That's the bug.
  • A jobId, with the job kept: 1 side effect, which looks like the fix.
  • The same jobId with removeOnComplete: true: 2 side effects. BullMQ only ignores a duplicate ID while the job still exists, so it isn't an idempotency mechanism.
  • A processed_events table with ON CONFLICT DO NOTHING, in the same transaction as the side effect: 3 deliveries, 1 side effect.

Ordering is a separate problem. Delivering OrderShipped before OrderPaid left the last-write-wins consumer at status=paid, permanently wrong. Each event carries a per-aggregate version, so the consumer ignores anything old, applies the next version, and parks anything early until the gap fills.

Checking a few orderings by hand isn't enough, so fast-check generates them (technique from lesson 09): every permutation of three events plus up to five duplicates must end in the same state. Last-write-wins and drop-on-gap both failed on the first run. The version-checked reducer passed 5000 orderings. This lab runs one worker at concurrency: 1; with several workers you also need a per-aggregate lock, such as SELECT ... FOR UPDATE on the order row, or two events can read the same version.

export type EventType = "OrderPlaced" | "OrderPaid" | "OrderShipped";
export interface OrderEvent { eventId: string; orderId: string; version: number; type: EventType }

export interface OrderView { version: number; status: string; parked: OrderEvent[] }

export const emptyView = (): OrderView => ({ version: 0, status: "none", parked: [] });

const statusOf: Record<EventType, string> = { OrderPlaced: "placed", OrderPaid: "paid", OrderShipped: "shipped" };

// ❌ آخر event وصل هو اللي بيكسب، حتى لو أقدم من اللي قبله
export function applyLastWriteWins(view: OrderView, event: OrderEvent): OrderView {
  return { ...view, version: event.version, status: statusOf[event.type] };
}

// ❌ بيرمي أي event جه بدري، فالأوردر بيقف ومبيكملش
export function applyDropOnGap(view: OrderView, event: OrderEvent): OrderView {
  if (event.version !== view.version + 1) return view;
  return { ...view, version: event.version, status: statusOf[event.type] };

// ✅ القديم بيتجاهل، والجاي بدري بيستنى لحد ما اللي قبله يوصل
export function applyInVersionOrder(view: OrderView, event: OrderEvent): OrderView {
  if (event.version <= view.version) return view;
  if (event.version > view.version + 1) {
    if (view.parked.some((p) => p.version === event.version)) return view;
    return { ...view, parked: [...view.parked, event].toSorted((a, b) => a.version - b.version) };
  }
  let next: OrderView = { version: event.version, status: statusOf[event.type], parked: view.parked };
  const ready = next.parked.find((p) => p.version === next.version + 1);
  if (ready) {
    next = { ...next, parked: next.parked.filter((p) => p !== ready) };
    return applyInVersionOrder(next, ready);
  }
  return next;
}

Part 6 — Eventually consistent assertions 🔴 Advancedالجزء 6 — الـ assertions على الـ eventual consistency

English

When the result appears later, a fixed sleep is wrong in both directions: too short and the test fails, too long and the suite crawls. In the run below a 30 ms sleep gave the wrong answer in 28 of 40 rounds. vi.waitFor retries the assertion until it passes or a deadline expires, and it failed 0 of 40 times.

Wait on something that identifies this operation, a correlation ID, and not on a global count that another test can change. The same loop gives you a useful number for free: time to consistency, here about 46 ms at p50 and 79 ms at p95 for a worker with a 5 to 60 ms simulated delay. You can assert on it like any latency budget.

"Exactly one row" is a harder kind of assertion, because waiting for something to appear can't prove that nothing else will. For that, wait for quiescence: the queue has no waiting, active or delayed jobs.

Teardown matters more here than anywhere else, because a queue outlives the test. Test A scheduled a delayed job and returned. Test B then saw 2 rows where it expected 1, and the failure pointed at B, which was innocent. The fix is a unique queue name per test, then closing the worker first and calling obliterate, plus an assertion that no bull:<name>:* keys remain.

الـ teardown هنا أهم من أي مكان تاني، لأن الـ queue بتعيش بعد الـ test. الـ test A حط جوب مؤجل ورجع. الـ test B لقى صفين وهو متوقع واحد، والفشل شاور على B وهو بريء. الحل: اسم queue فريد لكل test، وقفل الـ worker الأول، وبعدين obliterate، و assertion إن مفيش bull:<name>:* keys فاضلة.

فين هستخدمه في شغلي؟ أي integration test بعد action بيعدّي على queue: "العميل دفع، فالفاتورة لازم تظهر في الـ read model". استخدم vi.waitFor بالـ orderId نفسه، وحط deadline واضح. ولو الـ CI بيقع بشكل عشوائي في tests مالهاش علاقة ببعض، أول حاجة تشك فيها: jobs فاضلة من test قبله. شوف الدرس 08 لتشخيص الـ flakiness.

Common mistakes · غلطات شائعة

❌ Asserting absolute milliseconds in CI 
// الرقم ده من جهازك، والـ CI runner أبطأ أو أسرع
expect(result.p99).toBeLessThan(20);
✅ Exact counts, plus ratios over several runs 
// العدد مظبوط، والنسبة median على 5 تشغيلات
expect(queriesPerRequest).toBe(baseline.queriesPerRequest);
expect(medianRatio).toBeLessThanOrEqual(limit);
بالعامية

❌ رقم ms ثابت هيبقى flaky على أجهزة مختلفة، وهيتعلّق أو هيتحذف بعد شهر. ✅ قارن حاجة مظبوطة زي عدد الـ queries، ونسبة median على 5 تشغيلات. في التجربة بتاعتنا تشغيلة واحدة طلعت 2.5 والـ median كان 1.

❌ A pool with defaults 
// مفيش timeouts ومفيش listener للـ error
const pool = new Pool({ connectionString });
✅ Budgets and an error listener 
const pool = new Pool({
  connectionString,
  connectionTimeoutMillis: 300,
  query_timeout: 500,
});
// الـ listener بيمنع إن اتصال idle يوقّع الـ process
pool.on("error", (err) => logger.warn({ err }, "idle client error"));
بالعامية

❌ بالـ defaults، الـ blackhole علّق 40 من 40 request، واتصال idle مات وقّع الـ process بـ exit code 1. ✅ حط سقف لكل مرحلة وlistener للـ error: كله رجع 503 في أقل من ثانية والـ process فضل شغال.

❌ jobId as idempotency 
// بيحمي بس طول ما الجوب لسه موجود في Redis
await queue.add("evt", event, { jobId: event.eventId, removeOnComplete: true });
✅ Dedupe in the side effect's transaction 
-- الاتنين في نفس الـ transaction: يا الاتنين يتكتبوا يا ولا واحد
INSERT INTO processed_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING;
INSERT INTO notifications (order_id) VALUES ($2);
بالعامية

❌ الـ jobId مع removeOnComplete عمل 2 side effects في التجربة. ✅ جدول الـ dedupe في نفس الـ transaction، ونفّذ الـ side effect بس لو الـ insert دخل صف فعلًا (rowCount === 1): 3 مرات توصيل وطلع side effect واحد.

❌ Trusting arrival order 
// آخر رسالة وصلت هي اللي بتكتب، حتى لو أقدم
view.status = statusOf[event.type];
✅ Per-aggregate version check 
// القديم بيتجاهل، والجاي بدري بيتركن
if (event.version <= view.version) return view;
if (event.version > view.version + 1) return park(view, event);
return applyAndDrain(view, event);
بالعامية

❌ الترتيب في الـ queue مش ضمان، وOrderShipped ممكن يوصل قبل OrderPaid فالحالة تبقى غلط للأبد. ✅ version لكل aggregate، والقديم يتجاهل والبدري يستنى دوره.

2. Cut after N bytes 🟡 medium Write a proxy that forwards only the first N bytes from the server, then destroys both sockets. Prove that a client receives exactly N bytes. This fault looks like a connection dying halfway through a response.
اكتب proxy بيعدّي أول N bytes بس من الـ server، وبعدين يقفل الاتنين sockets. وأثبت إن الـ client استلم N بالظبط. العطل ده شبه اتصال بيموت في نص الـ response.
Solution · الحل 
import net from "node:net";

// الـ proxy البسيط ده بيقطع الاتصال بعد عدد bytes محدد من الـ server
function cutAfterBytes(targetPort: number, limit: number) {
  return net.createServer((client) => {
    const upstream = net.connect(targetPort, "127.0.0.1");
    let sent = 0;
    upstream.on("data", (chunk) => {
      const allowed = chunk.subarray(0, limit - sent);
      sent += allowed.length;
      client.write(allowed, () => {
        if (sent >= limit) { client.destroy(); upstream.destroy(); }
      });
    });
    client.on("data", (chunk) => upstream.write(chunk));
    client.on("error", () => upstream.destroy());
    upstream.on("error", () => client.destroy());
  });
}

// الـ target المحلي: بيبعت 100 byte، فالـ client لازم يشوف الاتصال بيتقطع
const target = net.createServer((s) => s.write(Buffer.alloc(100, 1)));
await new Promise<void>((r) => target.listen(0, "127.0.0.1", r));
const proxy = cutAfterBytes((target.address() as net.AddressInfo).port, 10);
await new Promise<void>((r) => proxy.listen(0, "127.0.0.1", r));

const received = await new Promise<number>((resolve) => {
  let n = 0;
  const c = net.connect((proxy.address() as net.AddressInfo).port, "127.0.0.1");
  c.on("data", (d) => (n += d.length));
  c.on("close", () => resolve(n));
  c.on("error", () => {});
});
console.log("bytes received before the cut:", received);
proxy.close();
target.close();
process.exit(0);
الـ subarray بيقص الـ chunk عند الحد بالظبط، والقفل بيحصل في الـ callback بتاع write عشان الـ bytes تتبعت الأول. لما شغّلناه طبع bytes received before the cut: 10.
3. A fourth event 🔴 hard Add OrderCancelled as version 4 and prove with fast-check that every delivery order, with duplicates, ends in cancelled with nothing parked.
زوّد OrderCancelled كـ version 4، وأثبت بـ fast-check إن أي ترتيب توصيل، ومعاه رسايل مكررة، بينتهي بـ cancelled ومفيش حاجة مركونة.
Solution · الحل 
import fc from "fast-check";
import assert from "node:assert/strict";

type EventType = "OrderPlaced" | "OrderPaid" | "OrderShipped" | "OrderCancelled";
interface OrderEvent { eventId: string; version: number; type: EventType }
interface OrderView { version: number; status: string; parked: OrderEvent[] }

const statusOf: Record<EventType, string> = {
  OrderPlaced: "placed", OrderPaid: "paid", OrderShipped: "shipped", OrderCancelled: "cancelled",
};

function apply(view: OrderView, event: OrderEvent): OrderView {
  if (event.version <= view.version) return view;
  if (event.version > view.version + 1) {
    if (view.parked.some((p) => p.version === event.version)) return view;
    return { ...view, parked: [...view.parked, event].toSorted((a, b) => a.version - b.version) };
  }
  const next: OrderView = { version: event.version, status: statusOf[event.type], parked: view.parked };
  const ready = next.parked.find((p) => p.version === next.version + 1);
  return ready ? apply({ ...next, parked: next.parked.filter((p) => p !== ready) }, ready) : next;
}

// الحالة النهائية لازم تبقى cancelled مهما كان ترتيب الوصول
const events: OrderEvent[] = [
  { eventId: "e1", version: 1, type: "OrderPlaced" },
  { eventId: "e2", version: 2, type: "OrderPaid" },
  { eventId: "e3", version: 3, type: "OrderShipped" },
  { eventId: "e4", version: 4, type: "OrderCancelled" },
];
const deliveries = fc.array(fc.constantFrom(...events), { maxLength: 4 }).chain((dupes) => {
  const all = [...events, ...dupes];
  return fc.shuffledSubarray(all, { minLength: all.length, maxLength: all.length });
});
fc.assert(fc.property(deliveries, (list) => {
  const view = list.reduce(apply, { version: 0, status: "none", parked: [] } as OrderView);
  assert.equal(view.status, "cancelled");
  assert.equal(view.parked.length, 0);
}), { numRuns: 3_000 });
console.log("OrderCancelled: 3000 orderings converged");
الـ reducer نفسه متغيرش، زوّدنا النوع الجديد في الـ map بس. لما شغّلناه طبع OrderCancelled: 3000 orderings converged.

Cheat sheet · الخلاصة

  • A load test is a test when it has assertions: errors, timeouts, non2xx, p99.
  • Compare ratios to a calibration endpoint, take the median of 5 runs, and use a tolerance band.
  • Queries per request is exact: check it on every PR, and run timing nightly.
  • Fault tests: add latency, blackhole, cut. Assert 503 inside the budget, nothing hangs, self-recovery.
  • node-postgres has no timeouts by default. Set connectionTimeoutMillis and query_timeout.
  • Always add pool.on('error'): an idle connection dying can kill the process.
  • Outbox: commit and roll back together; kill the relay for real; assert distinct IDs; bound the duplicates.
  • BullMQ jobId dedupes only while the job exists. Use a dedupe table in the side effect's transaction.
  • Per-aggregate version: ignore old, apply next, park early, alert on anything parked too long.
  • Generate delivery orders with fast-check: every permutation must reach the same state.
  • vi.waitFor on a correlation ID, never a fixed sleep. "Exactly one" needs a quiescence check.
  • A unique queue per test; close the worker, then obliterate; assert no keys remain.
بالعامية
  • الـ load test بيبقى test لما يكون ليه assertions: errors وtimeouts وnon2xx والـ p99.
  • قارن نسب لـ endpoint معايرة، وخد median بتاع 5 تشغيلات، واستخدم tolerance band.
  • عدد الـ queries لكل request رقم مظبوط: افحصه في كل PR، والتوقيت بالليل.
  • الـ fault tests: زوّد latency، blackhole، cut. واتأكد من 503 جوه الـ budget، ومفيش تعليق، والرجوع لوحده.
  • الـ node-postgres مفيهوش timeouts by default. حط connectionTimeoutMillis وquery_timeout.
  • دايمًا زوّد pool.on('error'): موت اتصال idle ممكن يقتل الـ process.
  • الـ outbox: commit و rollback مع بعض، واقتل الـ relay بجد، واتأكد من الـ IDs المختلفة، وحط سقف للـ duplicates.
  • الـ jobId في BullMQ بيمنع التكرار طول ما الجوب موجود بس. استخدم جدول dedupe في transaction الـ side effect.
  • version لكل aggregate: اتجاهل القديم، وطبّق اللي عليه الدور، واركن البدري، و alert على أي حاجة اتركنت كتير.
  • ولّد ترتيبات التوصيل بـ fast-check: كل ترتيب لازم يوصل لنفس الحالة.
  • vi.waitFor على correlation ID، وعمرك ما تستخدم sleep ثابت. و"واحد بالظبط" محتاجة فحص هدوء الـ queue.
  • queue فريدة لكل test، واقفل الـ worker وبعدين obliterate، واتأكد إن مفيش keys فاضلة.
