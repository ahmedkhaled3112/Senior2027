Why this matters · ليه ده مهم

English

A flaky test costs more than a missing one. Once a red build might be "just a flake", people stop reading red builds, and the real regression ships behind a re-run button. Speed has the same effect: a 40-minute pipeline gets merged around. This lesson plants every classic cause on purpose, measures it over 100 runs, fixes it, and shows why retry is the wrong fix. Then it covers per-worker databases, sharding and how to organise test code in a monorepo. "How do you deal with a flaky test?" comes up in almost every senior interview.

بالعامية

الـ flaky test بيكلّف أكتر من test مش موجود. أول ما الـ build الأحمر يبقى "يمكن flake وخلاص"، الناس بتبطل تقرا الأحمر، والـ regression الحقيقي بيعدّي ورا زرار re-run. والسرعة نفس الحكاية: pipeline بياخد 40 دقيقة الناس بتلف حواليه. في الدرس ده هنزرع كل سبب من الأسباب المشهورة بقصد، نقيسه على 100 run، نصلّحه، ونوضّح ليه الـ retry هو الحل الغلط. وبعدها DB لكل worker، الـ sharding، وإزاي تنظّم كود الـ tests في monorepo. وسؤال "بتتعامل إزاي مع flaky test؟" بييجي في أغلب interviews السنيور.

Part 1 — Five causes, reproduced 🟡 Intermediateالجزء 1 — الأسباب الخمسة، متكررة قدامك

English

Nearly every flaky test comes from one of five causes: shared mutable state (module variables, a shared database), timing (a setTimeout racing real work), order dependency (a test that needs another to run first), real network (a test that depends on a service you don't control), and leaked resources (a handle that outlives its test and interferes with the next one).

Each file below plants one cause. The jitter is deliberate and stands in for the load a busy CI machine creates, so the failure shows up at a measurable rate. The "real network" case uses a local server on the loopback interface that returns 503 about 20% of the time; no external service is called.

بالعامية

أغلب الـ flaky tests جاية من واحد من 5 أسباب: shared mutable state (متغيرات على مستوى الـ module أو DB مشتركة)، timing (setTimeout بيسابق شغل حقيقي)، order dependency (test محتاج test تاني يشتغل قبله)، real network (test معتمد على service مش بتاعك)، وleaked resources (handle بيفضل عايش بعد ما الـ test خلص وبيضرب اللي بعده).

كل ملف فوق بيزرع سبب واحد. الـ jitter مقصود وبيمثّل الحمل اللي بيعمله CI مشغول، عشان الفشل يظهر بنسبة نقدر نقيسها. وحالة الـ "real network" بتستخدم server محلي على الـ loopback بيرد 503 حوالي 20% من الوقت، ومفيش أي service خارجي اتنادى عليه.

أهم ملحوظة: الـ order-dependent معدّاش حتى run واحد فاشل بالترتيب العادي. يعني الـ suite ممكن يبقى شكله سليم سنة، ويقع أول ما حد يزوّد test أو يشغّل shuffle. والـ leaked handle وقّع test تاني غير اللي عمل الـ leak، وده اللي بيخليه صعب تشخيصه: الـ test اللي بيقع بريء.

فين هستخدمه في شغلي؟ لما الـ CI يقع على checkout.test.ts ويعدّي في الـ re-run: اسأل الـ 5 أسئلة دول بالترتيب. فيه let على مستوى الملف؟ فيه sleep؟ بيعدّي لوحده بـ .only؟ بيكلّم Stripe sandbox؟ فيه connection أو setInterval مفتوح من test قبله؟ الترتيب ده بيوفّر عليك ساعات تخمين.

Part 2 — Diagnosis 🟡 Intermediateالجزء 2 — التشخيص

English

Diagnosis starts with a number. The README mentions --repeat, but in Vitest 5 that flag does not exist: the real flag is --repeats (and there is a per-test repeats option). repeats reruns a test regardless of its result, but inside the same process and with the same module state, so it won't expose a problem that needs a new process. The most reliable measure is a script that launches a fresh Vitest process N times and records the failure rate per test.

For order problems, --sequence.shuffle --sequence.seed=N makes an order reproducible, and a bisect narrows which test pollutes which. For leaks, process.getActiveResourcesInfo() lists what is still keeping the event loop alive.

// بيشغّل Vitest مرة واحدة في process جديد ويرجّع نتيجة كل test
import { spawn } from "node:child_process";
import { mkdtempSync, readFileSync, rmSync } from "node:fs";
import path from "node:path";

const vitest = path.join(import.meta.dirname, "../../node_modules/vitest/vitest.mjs");

export function runOnce(root, file, extra = []) {
  const dir = mkdtempSync(path.join(root, ".tmp-"));
  const out = path.join(dir, "r.json");
  const args = [vitest, "run", file, "--root", root, "--reporter=json", `--outputFile=${out}`, ...extra];
  return new Promise((resolve) => {
    const child = spawn(process.execPath, args, { cwd: root, stdio: "ignore", env: { ...process.env, NO_COLOR: "1" } });
    child.on("close", (code) => {
      const json = JSON.parse(readFileSync(out, "utf8"));
      rmSync(dir, { recursive: true, force: true });
      const tests = json.testResults.flatMap((f) => f.assertionResults.map((t) => ({
        name: t.fullName, title: t.title, status: t.status, duration: t.duration ?? 0,
      })));
      resolve({ code, tests });
    });
  });
}

بالعامية

التشخيص بيبدأ برقم. الـ README بيقول --repeat، بس في Vitest 5 الـ flag ده مش موجود، والصح --repeats (وفيه كمان خيار repeats لكل test). الـ repeats بيعيد الـ test بغض النظر عن النتيجة، لكن جوه نفس الـ process وبنفس الـ module state، فمش هيكشف مشكلة محتاجة process جديد. أوثق قياس هو script بيشغّل Vitest في process جديد N مرة ويسجّل نسبة الفشل لكل test.

لمشاكل الترتيب، --sequence.shuffle --sequence.seed=N بيخلّي الترتيب قابل للتكرار، والـ bisect بيضيّق مين بيلوّث مين: السكريبت هنا لقى الـ test الملوّث من 7 مرشحين في 3 خطوات. وللـ leaks، process.getActiveResourcesInfo() بيقولك إيه اللي لسه ماسك الـ event loop.

الغلطة الشائعة: تشغّل الـ test 3 مرات وتقول "أهو عدّى". بنسبة فشل 28%، احتمال 3 runs ناجحين ورا بعض حوالي 37%. لازم عدد كبير عشان الرقم يبقى ليه معنى.

فين هستخدمه في شغلي؟ فيه test في الـ CI بيقع مرة كل كام يوم. حط flaky-rate.mjs في tools/، شغّله عليه 100 مرة على فرعك، وسجّل الرقم في الـ ticket. بعد الـ fix شغّله تاني. لو الرقم 0 من 100 تقدر تقفل الـ ticket وأنت مطمّن، بدل "مابقاش بيقع عندي".
Trade-off: repeats vs a fresh process per run --repeats is fast and good for timing and randomness inside one test. A new process per run is slower but also catches module-state and start-up problems. Use repeats while narrowing down, and the per-process script as the final measure.

Part 3 — Fix, don't retry 🟡 Intermediateالجزء 3 — صلّحها، متعملش retry

English

Each cause has a specific fix, and the only proof a fix worked is the same 100 runs afterwards. Below, every cause was fixed and re-run 100 times: all five reached 0 failed runs. The fixes share one idea: remove the thing the test doesn't control. Shared state becomes a parameter, wall-clock time becomes fake timers, ordering becomes per-test setup, the network becomes an injected port, and leaks get a registered cleanup.

A retry changes none of that. With retry: 2, a test that fails 30% of the time reports failure in about 0.3³ = 2.7% of runs. We calculated it and observed it over 1000 tests: about 25 failed, but about 260 passed only after a retry. The suite turned green; those bugs are still there. If a test can't be fixed today, quarantine it with an owner, a ticket and an expiry date, and fail the build when the date passes.

Part 4 — Parallelism 🟡 Intermediateالجزء 4 — الـ Parallelism

English

Vitest runs test files in parallel workers. The default pool is forks (child processes, which work with everything); threads are faster to start but don't suit every native module or process.chdir. Parallel workers make isolation mandatory: two workers running TRUNCATE orders against one database will wreck each other.

The standard fix is one database per worker, using VITEST_POOL_ID, a stable number from 1 up to maxWorkers. Files inside one worker still run one at a time, so per-test cleanup remains safe. isolate: false skips re-creating the module environment for every file. It is much faster and it is a real trade: any module-level state now survives between files.

  maxWorkers: 4, globalSetup creates 4 databases

  worker 2 (POOL_ID=2) ---> orders_test_2
  worker 3 (POOL_ID=3) ---> orders_test_3
  worker 4 (POOL_ID=4) ---> orders_test_4

  Files in one worker run one after another,
  so TRUNCATE inside that worker is safe.

Part 5 — Speed budget 🟡 Intermediateالجزء 5 — الـ Speed budget

English

Treat test time as a budget: unit tests in seconds, integration in minutes. Start by measuring. The JSON reporter already has per-test durations, so a small script gives you the slowest list. On a generated 300-test suite, three tests took about 400 ms each while everything else was around 25 ms: fixing three tests saves more than tuning the rest.

Locally, run less: vitest --changed runs only tests affected by your uncommitted changes (here 1 of 30 files), and --sinceLastRun reruns only tests whose recorded dependencies changed since the last run. In CI, split the work: --shard=1/3 runs a third of the files, and --reporter=blob saves each shard's result under .vitest/blob. --merge-reports then combines them into one report.

English

In a monorepo, shared test code belongs in its own package: packages/test-utils with factories, custom matchers and a database helper, so every service builds orders the same way. It must be fenced: production code must never import it, enforced by a lint rule (the general technique is in section 09 · lesson 16). Below, ESLint 10 rejects the import in src/checkout.ts and allows it in checkout.test.ts.

Categories make selection possible. Vitest 5 has built-in tags: declare them in tags in the config, attach them with { tags: ['slow'] }, and filter with --tagsFilter, which understands boolean expressions. strictTags is on by default, so a typo like slwo is an error. Try it yourself · جرّب بنفسك

1. Tame a debounce 🟢 easy Write a test for a 300 ms debounce that saves a draft, using fake timers. It must check that nothing is called at 299 ms and that it fires exactly once with the last value at 300 ms.
اكتب test لـ debounce مدته 300 ms بيحفظ draft، بالـ fake timers. لازم يتأكد إن مفيش حاجة اتنادت عند 299 ms وإنها اشتغلت مرة واحدة بآخر قيمة عند 300 ms.
Solution · الحل 
import { afterEach, beforeEach, expect, it, vi } from "vitest";
import { debounce } from "./debounce.ts";

beforeEach(() => vi.useFakeTimers());
afterEach(() => vi.useRealTimers());

it("saves the last draft once, after the quiet period", () => {
  const save = vi.fn();
  const saveDraft = debounce(save, 300);
  saveDraft("first");
  vi.advanceTimersByTime(200);
  saveDraft("second");
  vi.advanceTimersByTime(299);
  expect(save).not.toHaveBeenCalled();
  vi.advanceTimersByTime(1);
  expect(save).toHaveBeenCalledExactlyOnceWith("second");
});
الـ advanceTimersByTime بيحرّك الوقت بدقة من غير أي انتظار حقيقي، فالـ test ده مش ممكن يكون flaky بسبب الجهاز. اتشغّل: 1 passed.
2. A budget that fails the build 🟡 medium Extend slowest.mjs into budget.mjs: read the JSON report and exit 1 if any test goes over a limit given as an argument.
كبّر slowest.mjs لـ budget.mjs: يقرا الـ JSON report ويخرج بـ exit 1 لو أي test عدّى حد تديهوله كـ argument.
Solution · الحل 
// الاستخدام: node budget.mjs report.json 100
import { readFileSync } from "node:fs";

const [report, limitArg = "100"] = process.argv.slice(2);
const limit = Number(limitArg);
const tests = JSON.parse(readFileSync(report, "utf8")).testResults.flatMap((file) =>
  file.assertionResults.map((t) => ({ name: `${file.name.split("/").pop()} ${t.fullName}`, ms: t.duration ?? 0 })),
);
const overBudget = tests.filter((t) => t.ms > limit).sort((a, b) => b.ms - a.ms);
for (const t of overBudget) console.log(`FAIL ${t.ms.toFixed(0)} ms  ${t.name}`);
console.log(`${overBudget.length} of ${tests.length} tests over the ${limit} ms budget`);
process.exit(overBudget.length ? 1 : 0);
شغّلناه على الـ report الحقيقي: 3 من 300 test عدّوا الـ 100 ms، وexit 1. حطه في الـ CI بعد الـ test job مباشرة.

Cheat sheet · الخلاصة

  • Five causes: shared state, timing, order, real network, leaked resources. Measure first: 100 runs in fresh processes.
  • Vitest 5: the flag is --repeats, not --repeat. --sequence.shuffle --sequence.seed=N makes an order reproducible.
  • Bisect finds the polluter; process.getActiveResourcesInfo() shows leaked handles.
  • Fix by removing what the test doesn't control: parameter, fake timers, per-test setup, injected port, registered cleanup.
  • retry: 2 turns 30% into ~2.7% reported and hides ~260 of 1000 failures. Retries are not a fix.
  • Quarantine needs an owner, a ticket and an expiry date, with a script that fails on expiry.
  • VITEST_POOL_ID gives one database per worker. 4 workers on one DB: 21–22 of 80 failed.
  • isolate: false was ~5× faster here and broke the module-state suite. Use it only on clean code.
  • Slowest-test list first, then --changed locally and --shard + blob + --merge-reports in CI.
  • Vitest 5 tags with --tagsFilter; strict by default. Fence test-utils from production with a lint rule.
  • CI stages: commit under 5 min, merge under 15 min, nightly under 60 min.
