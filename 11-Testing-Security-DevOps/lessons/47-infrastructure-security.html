Why this matters · ليه ده مهم

English

The application-level attacks from the earlier lessons assume the attacker starts outside. Infrastructure security answers the next question: what can they reach once a single container is compromised? A hardened Pod, a default-deny network and a scoped IAM role turn "they got RCE on notifications" into "they got RCE on notifications and could do nothing with it".

It also decides whether the company can sell to enterprise customers. A SOC 2 report is usually the first thing a large buyer's security team asks for, and most of what it needs comes from engineers. The Senior who already has the evidence in a query is the one who saves the quarter.

بالعامية

الهجمات اللي شفناها في الدروس اللي فاتت بتفترض إن المهاجم لسه برّه. الـ infrastructure security بتجاوب على السؤال اللي بعده: لو container واحد اتخترق، يقدر يوصل لإيه؟ الـ Pod المتأمّن، والـ network اللي الـ default بتاعها deny، والـ IAM role المحدود، هم اللي بيحوّلوا "حد عمل RCE على notifications" لـ "حد عمل RCE على notifications ومعرفش يعمل بيها أي حاجة".

وكمان ده اللي بيحدد الشركة تقدر تبيع لعملاء enterprise ولا لأ. الـ SOC 2 report غالبًا أول حاجة فريق الأمن عند أي عميل كبير بيطلبها، ومعظم اللي محتاجينه بييجي من المهندسين. والسنيور اللي عنده الـ evidence جاهزة في query واحدة هو اللي بينقذ الربع.

Part 1 — Container security 🔴 Advancedالجزء 1 — تأمين الـ containers

English

Image choices are covered in lesson 26 (distroless, multi-stage, non-root USER) and scanning in lesson 27: the CI job fails the build on any critical CVE. Here we take the next layer, what the running container is allowed to do. The list fits in one securityContext, and each field removes one concrete attack.

Pod Security Standards define a restricted profile that is the floor for this list. Note what it does not include: readOnlyRootFilesystem is not required by any profile, and neither is a memory limit. So "passes restricted" is necessary and not sufficient. Our linter separates the two levels, and it runs after a schema check because a manifest can be perfectly valid and completely unsafe.

// الـ checks دي بتتطبق على الـ Pod spec نفسه، سواء جوه Deployment أو CronJob
export type Severity = "restricted" | "extra";
export interface Finding { container: string; rule: string; level: Severity; }

type Obj = Record<string, any>;

const CAPS_ALLOWED = new Set(["NET_BIND_SERVICE"]);

export function lintPodSpec(pod: Obj): Finding[] {
  const out: Finding[] = [];
  const add = (container: string, rule: string, level: Severity = "restricted") => out.push({ container, rule, level });
  const psc: Obj = pod.securityContext ?? {};

  if (pod.hostNetwork) add("<pod>", "hostNetwork must be false");
  if (pod.hostPID) add("<pod>", "hostPID must be false");
  if (pod.hostIPC) add("<pod>", "hostIPC must be false");
  for (const v of pod.volumes ?? []) {
    if (v.hostPath) add("<pod>", `volume ${v.name}: hostPath is forbidden`);
  }
  if (pod.automountServiceAccountToken !== false) add("<pod>", "automountServiceAccountToken should be false", "extra");

  const containers: Obj[] = [...(pod.initContainers ?? []), ...(pod.containers ?? [])];
  for (const c of containers) {
    const sc: Obj = c.securityContext ?? {};
    // قيمة الـ container بتغلب قيمة الـ Pod لو الاتنين موجودين
    const nonRoot = sc.runAsNonRoot ?? psc.runAsNonRoot;
    const uid = sc.runAsUser ?? psc.runAsUser;
    const seccomp = (sc.seccompProfile ?? psc.seccompProfile)?.type;

    if (sc.privileged) add(c.name, "privileged must be false");
    if (nonRoot !== true) add(c.name, "runAsNonRoot must be true");
    if (uid === 0) add(c.name, "runAsUser must not be 0");
    if (sc.allowPrivilegeEscalation !== false) add(c.name, "allowPrivilegeEscalation must be false");
    if (!(sc.capabilities?.drop ?? []).includes("ALL")) add(c.name, 'capabilities.drop must include "ALL"');
    for (const cap of sc.capabilities?.add ?? []) {
      if (!CAPS_ALLOWED.has(cap)) add(c.name, `capability ${cap} must not be added`);
    }
    if (seccomp !== "RuntimeDefault" && seccomp !== "Localhost") add(c.name, "seccompProfile must be RuntimeDefault or Localhost");
    // ده مش جزء من الـ restricted profile، بس إحنا عايزينه
    if (sc.readOnlyRootFilesystem !== true) add(c.name, "readOnlyRootFilesystem should be true", "extra");
    if (!c.resources?.limits?.memory) add(c.name, "resources.limits.memory should be set", "extra");
  }
  return out;
}

export function podSpecOf(doc: Obj): Obj | undefined {
  if (doc.kind === "Pod") return doc.spec;
  if (doc.kind === "CronJob") return doc.spec?.jobTemplate?.spec?.template?.spec;
  return doc.spec?.template?.spec;
}

Trade-off: a read-only root has a cost Anything that writes to disk needs an explicit emptyDir: temp uploads, heap snapshots, some native modules' caches. With medium: Memory those writes count against the container's memory limit, so a large upload can OOMKill the Pod. Keep the default disk-backed emptyDir with a sizeLimit unless you need the speed. And runAsNonRoot needs a numeric UID: the kubelet can't verify a name like USER node, so the container is refused unless you set a numeric runAsUser.
أي حاجة بتكتب على الـ disk محتاجة emptyDir صريح: الـ uploads المؤقتة، الـ heap snapshots، والـ cache بتاع بعض الـ native modules. ولو استخدمت medium: Memory، الكتابة دي بتتحسب على الـ memory limit بتاع الـ container، فـ upload كبير ممكن يعمل OOMKill للـ Pod. سيب الـ emptyDir العادي على الـ disk بـ sizeLimit إلا لو محتاج السرعة فعلًا. وكمان runAsNonRoot محتاج UID رقمي: الـ kubelet مش هيعرف يتأكد من اسم زي USER node، فالـ container هيترفض إلا لو حطيت runAsUser برقم.

Part 2 — Kubernetes security 🔴 Advancedالجزء 2 — تأمين Kubernetes

English

RBAC and service accounts. Give each app its own ServiceAccount and a Role that names exact resources and verbs. Set automountServiceAccountToken: false if the app never calls the API server, since a mounted token is the first thing an attacker steals. Watch two verbs: list on Secrets returns their full contents, and create on Pods lets someone run a Pod as any ServiceAccount in the namespace, which is privilege escalation in disguise.

NetworkPolicy. By default every Pod can reach every other Pod. A policy that selects a Pod makes that direction default-deny for it, and policies add up as a union. A connection needs permission on both sides: egress at the sender and ingress at the receiver. Two traps: policies only work if the CNI enforces them (Calico or Cilium do, and on a CNI that doesn't, they are silently ignored), and a default-deny on egress also blocks DNS.

Pod Security Standards are enforced by a built-in admission controller through namespace labels: enforce rejects, warn and audit only report, so you can roll out with warn first. Secrets at rest: by default the API server stores resources in etcd as plain text with no at-rest encryption, and the identity provider offers no confidentiality. A Secret's value is only base64. Enable an EncryptionConfiguration, preferably with a KMS provider, and see System Design lesson 38 for envelope encryption. On a managed cluster check what your provider already does.

  const nsOk = peer.namespaceSelector ? matches(peer.namespaceSelector, nsLabels(other.ns)) : other.ns === policyNs;
  const podOk = peer.podSelector ? matches(peer.podSelector, other.labels) : true;
  return nsOk && podOk;
}

function sideAllows(np: Obj[], pod: Pod, other: Pod, port: number, dir: "ingress" | "egress"): boolean {
  const type = dir === "ingress" ? "Ingress" : "Egress";
  const applying = np.filter(
    (p) => p.metadata.namespace === pod.ns && matches(p.spec.podSelector, pod.labels) && (p.spec.policyTypes ?? ["Ingress"]).includes(type),
  );
  // لو مفيش ولا policy بتختار الـ Pod، يبقى مفتوح بالكامل: ده الـ default في Kubernetes
  if (applying.length === 0) return true;
  // الـ policies بتتجمع بـ OR: أي rule بتسمح تكفي
  return applying.some((p) =>
    (p.spec[dir] ?? []).some((rule: Obj) => {
      const peers: Obj[] = rule[dir === "ingress" ? "from" : "to"] ?? [];
      const peerOk = peers.length === 0 || peers.some((x) => peerMatches(x, other, p.metadata.namespace));
      const portOk = !rule.ports || rule.ports.some((r: Obj) => r.port === port);
      return peerOk && portOk;
    }),
  );
}

export const canConnect = (np: Obj[], from: Pod, to: Pod, port: number) =>
  sideAllows(np, from, to, port, "egress") && sideAllows(np, to, from, port, "ingress");

  const seen = new Set([start]);

  while (queue.length) {

      if (t.name !== "coredns") queue.push(t.name);
    }
  }
  seen.delete(start);
  return [...seen].sort();

English

Lesson 37 covers writing a least-privilege policy and putting the database in a private subnet. An audit is the opposite direction: read what exists and find what drifted. A grep for "*" is not enough. A Deny with a wildcard is a guardrail, some read actions only accept Resource: "*", and iam:PassRole on * looks harmless next to s3:* but is a privilege-escalation path. CloudTrail records who called which API, and event history covers only the last 90 days of management events, so a trail delivering to S3 is what gives you long-term evidence. It should be multi-region, since an attacker will gladly use a region you never look at, with log file validation on. GuardDuty is a managed detector that reads CloudTrail, VPC Flow Logs and DNS logs for anomalies such as credentials used from an unusual location. It finds things you didn't think to write a rule for, and it needs someone reading its findings.

export function auditIam(policies: Obj[]): Finding[] {
  const out: Finding[] = [];
  for (const p of policies) {
    for (const s of p.statements as Obj[]) {
      // الـ Deny بنجمة حماية مش مشكلة، وده الفرق بين grep غبي و audit
      if (s.Effect !== "Allow") continue;
      const actions = asArray<string>(s.Action);
      const anyResource = asArray<string>(s.Resource).includes("*");
      if (actions.includes("*")) { out.push({ sev: "CRITICAL", resource: `iam/${p.name}`, issue: "Allow * on *: full admin" }); continue; }
      for (const a of actions) {
        if (a.endsWith(":*")) out.push({ sev: anyResource ? "HIGH" : "MEDIUM", resource: `iam/${p.name}`, issue: `wildcard action ${a}${anyResource ? " on Resource *" : ""}` });

        else if (anyResource && !READ_ONLY.test(a)) out.push({ sev: "MEDIUM", resource: `iam/${p.name}`, issue: `${a} on Resource *: scope it to an ARN` });
      }
    }
  }
  return out;
}

English

Lesson 20 covers npm dependencies and SBOMs. The same risk exists one layer down, in the things your pipeline runs. On 2026-03-19 an attacker force-pushed malicious code to most version tags of aquasecurity/trivy-action and all of setup-trivy (CVE-2026-33634). The stealer ran before the real scan, so logs looked normal. Pipelines that used @v0.x tags pulled it; pipelines pinned to a commit SHA did not.

A tag or branch is a movable pointer. A full 40-character commit SHA is content-addressed. GitHub's docs say the same, and add two details: verify that the SHA comes from the action's own repository and not a fork, and that Dependabot will not create alerts for actions pinned to SHA values. They also list workflow dependency lockfiles as the strongest protection for repositories that can adopt them. Container images get the same treatment: a @sha256: digest instead of a tag, because :latest or :1.4.0 can change under you.

Pinning says "this exact artifact". Signing says "and we built it". The registry stores a signature over the digest, an admission controller verifies it before the Pod starts, and an SBOM attached as a signed attestation records what is inside. Policy as code (Kyverno, OPA) is where these rules live, in version control and enforced at the cluster door instead of remembered by reviewers.

import { generateKeyPairSync, sign, verify, type KeyObject } from "node:crypto";

interface Decision { image: string; allowed: boolean; reason: string; }

const { privateKey, publicKey } = generateKeyPairSync("ed25519");

// الـ signatures store هنا بديل عن الـ ⁦.sig⁩ اللي بتتخزن جنب الـ image في الـ registry
const signatures = new Map<string, Buffer>();

function signImage(digest: string, key: KeyObject): void {
  signatures.set(digest, sign(null, Buffer.from(digest), key));
}

const DIGEST = /@(sha256:[0-9a-f]{64})$/;

export function admit(image: string, trustedKey: KeyObject): Decision {
  const m = image.match(DIGEST);
  if (!m) return { image, allowed: false, reason: "image is not pinned by digest" };
  const digest = m[1]!;
  const sig = signatures.get(digest);
  if (!sig) return { image, allowed: false, reason: "no signature for this digest" };
  // المهم: بنوقّع على الـ digest مش على الـ tag، عشان الـ tag بيتحرك
  if (!verify(null, Buffer.from(digest), trustedKey, sig)) return { image, allowed: false, reason: "signature does not match the trusted key" };
  return { image, allowed: true, reason: "signed by the trusted key" };
}

const unsigned = `sha256:${"9b7d3a6f".repeat(8)}`;
const forged = `sha256:${"5e0c8b1d".repeat(8)}`;

signImage(good, privateKey);
// المهاجم معاه مفتاح بتاعه، فالتوقيع سليم رياضيًا بس مش من المفتاح اللي بنثق فيه

Part 5 — Compliance as engineering work 🔴 Advancedالجزء 5 — الـ compliance كشغل هندسي

English

This is not legal or audit advice. It is what the work looks like from the engineering side. SOC 2 is an attestation report from a CPA firm against the AICPA Trust Services Criteria, which have five categories: Security, Availability, Processing Integrity, Confidentiality and Privacy. Security is the one every report includes. A Type I report looks at whether controls are designed properly at a point in time. A Type II report tests whether they actually operated over a period, commonly 3 to 12 months, and that is what buyers usually want. ISO/IEC 27001 is a certifiable standard for an information security management system (ISMS); the 2022 edition's Annex A lists 93 controls. Certificates are generally issued for three years with yearly surveillance audits. (The Type I and II detail and these ISO figures are from general knowledge: the AICPA page read here doesn't spell them out, and iso.org refused the automated fetch. Confirm them with your auditor.)

Neither one prescribes a technology. They ask you to define controls and then prove you followed them, so the engineering job is evidence. An auditor samples, say, 25 changes from the period and asks to see that each one was reviewed by someone else and approved before it reached production. If that evidence is a query, the audit costs days. If it is screenshots, it costs months.

import { parseAllDocuments } from "yaml";
import { auditAll } from "./cloud-audit.ts";
import { lintPodSpec, podSpecOf } from "./pod-checks.ts";
import { scanTree } from "./scan-pins.ts";

type Obj = Record<string, any>;
interface Check { id: string; title: string; lesson: string; run(dir: string): string | null; }

const yamlDocs = (f: string): Obj[] => parseAllDocuments(readFileSync(f, "utf8")).map((d) => d.toJS() as Obj).filter(Boolean);
const deployDocs = (dir: string): Obj[] => readdirSync(join(dir, "deploy")).flatMap((f) => yamlDocs(join(dir, "deploy", f)));

// كل check بيرجّع null لو عدّى، أو سبب الفشل كنص واضح
const CHECKS: Check[] = [
  {
    id: "IMG-1", title: "Image: pinned base, non-root USER", lesson: "26",
    run(dir) {
      const lines = readFileSync(join(dir, "Dockerfile"), "utf8").split("\n");
      const from = lines.find((l) => l.startsWith("FROM ")) ?? "";
      const user = lines.filter((l) => l.startsWith("USER ")).pop();
      if (!from.includes("@sha256:")) return `base image not pinned: ${from}`;
      if (!user || /\b(root|0)\b/.test(user)) return "no non-root USER";
      return null;
    },
  },
  {
    id: "POD-1", title: "Pod spec meets restricted", lesson: "47 p1",
    run(dir) {
      const bad = deployDocs(dir).filter((d) => d.kind === "Deployment").flatMap((d) => lintPodSpec(podSpecOf(d)!)).filter((f) => f.level === "restricted");
      return bad.length ? `${bad.length} restricted violations` : null;
    },
  },
  {
    id: "NET-1", title: "Default-deny NetworkPolicy exists", lesson: "47 p2",
    run(dir) {
      const ok = deployDocs(dir).some((d) => d.kind === "NetworkPolicy" && Object.keys(d.spec.podSelector ?? {}).length === 0 && d.spec.policyTypes?.includes("Egress") && !d.spec.egress);
      return ok ? null : "no default-deny policy in deploy/";
    },
  },
  {
    id: "SUP-1", title: "Actions and images pinned", lesson: "47 p4",
    run(dir) {
      const fails = scanTree(dir).filter((p) => p.level === "FAIL");
      return fails.length ? `${fails.length} mutable refs` : null;
    },
  },
  {
    id: "CLD-1", title: "No critical cloud findings", lesson: "47 p3",
    run(dir) {
      const crit = auditAll(JSON.parse(readFileSync(join(dir, "cloud-inventory.json"), "utf8"))).filter((f) => f.sev === "CRITICAL");
      return crit.length ? `${crit.length} critical findings` : null;
    },
  },
  {
    id: "SEC-1", title: "No .env committed", lesson: "19",
    run(dir) { return existsSync(join(dir, ".env")) ? ".env present in the repo" : null; },
  },
  {
    id: "CMP-1", title: "Change evidence has no exceptions", lesson: "47 p5",
    run(dir) {
      const e = JSON.parse(readFileSync(join(dir, "evidence.json"), "utf8")) as { exceptions: number };
      return e.exceptions ? `${e.exceptions} open exceptions` : null;
    },
  },
];

for (const dir of process.argv.slice(2)) {
  console.log(`\n=== ${dir}`);
  let failed = 0;
  for (const c of CHECKS) {
    const why = c.run(dir);
    if (why) failed++;
    console.log(`${why ? "FAIL" : "PASS"}  ${c.id.padEnd(6)} ${c.title.padEnd(36)} lesson ${c.lesson.padEnd(6)} ${why ?? ""}`.trimEnd());
  }
  console.log(`${CHECKS.length - failed}/${CHECKS.length} passed`);
  if (failed) process.exitCode = 1;
}

بالعامية

أي checklist محدش بيشغّلها بتموت من أول أسبوع. الـ baseline المفيدة صفحة واحدة، وكل سطر فيها ليه check بيفرضه، فسؤال "إحنا ماشيين على الـ standard بتاعنا؟" يبقى أمر واحد بس. ابدأ صغير: 7 checks بيوقّعوا الـ build أحسن من 50 بند في wiki. وكل بند في الجدول فوق بيربطك بالدرس اللي بيشرحه وبالـ check اللي بيفرضه.

وخليك واضح في اللي الـ baseline مش شايفاه. هي مش بتقول حاجة عن منطق الـ application، زي الـ broken object-level authorization أو إساءة استخدام business flow، ودي شغل الـ threat modeling والـ penetration tests. وكل استثناء لازم يبقى ليه owner وتاريخ انتهاء، وإلا الصفحة كلها هتفقد معناها من غير ما حد يحس.

فين هستخدمه في شغلي؟ لما تعمل service جديدة، أول PR فيها يبقى الـ baseline نفسها: baseline.ts في الـ CI و required check على main. ومن هنا أي service في الشركة تعرف مكانها بنسبة واحدة زي 7/7. والغلطة الشائعة: تعمل الـ baseline من غير استثناءات موثقة، فالفرق تعطّلها أول ما تقف في وشهم؛ اعمل ملف exceptions فيه تاريخ انتهاء و owner.

Common mistakes · غلطات شائعة

❌ Default-deny that kills DNS 
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
# وخلاص: مفيش rule تسمح بـ DNS
✅ Deny, then allow DNS by name 
egress:
  - to:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: kube-system
    ports:
      - { protocol: UDP, port: 53 }
      - { protocol: TCP, port: 53 }
بالعامية

❌ الـ default-deny على الـ egress من غير rule للـ DNS بيخلي كل الـ apps تقع بـ ENOTFOUND، وشكلها مشكلة شبكة غامضة. ✅ بعد الـ deny، افتح UDP و TCP 53 لـ kube-system بالاسم. TCP مهمة كمان لأن الـ responses الكبيرة بتروح عليها.

❌ Pinned to a tag 
- uses: aquasecurity/trivy-action@0.30.0
# الـ tag بيتحرك، وده اللي حصل في مارس 2026
✅ Pinned to a commit SHA 
- uses: actions/checkout@1111111111111111111111111111111111111111 # النسخة v7.0.1
# عيّنة: هات الـ SHA الحقيقي من صفحة الـ release
بالعامية

❌ الـ tag ممكن يتنقل على commit تاني، فنفس السطر يجيب كود مختلف من غير ما تعمل أي تغيير. ✅ الـ SHA الكامل مبيتغيرش، وسيب الـ version في comment عشان القراءة والتحديث. واتأكد إن الـ SHA من الـ repo الأصلي مش من fork.

❌ iam:PassRole on everything 
{ "Effect": "Allow",
  "Action": ["ecs:UpdateService", "iam:PassRole"],
  "Resource": "*" }
✅ Scoped to the exact role and service 
{ "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::000000000000:role/orders-task-role",
  "Condition": { "StringEquals":
    { "iam:PassedToService": "ecs-tasks.amazonaws.com" } } }
بالعامية

❌ iam:PassRole على * معناه الـ CI يقدر يدّي أي task أي role، حتى admin، وده privilege escalation كامل. ✅ حدّد الـ role بالـ ARN وحدّد الـ service بـ iam:PassedToService.

❌ runAsNonRoot with a named user 
USER node
# الـ kubelet مش هيعرف يتأكد إن الاسم ده مش root
✅ A numeric UID 
USER 65532
# رقم واضح يقدر الـ kubelet يتأكد منه
بالعامية

❌ لما الـ image فيها USER node والـ Pod فيه runAsNonRoot: true، الـ kubelet مش عارف الاسم ده UID كام، فالـ container بيترفض. ✅ حط رقم في الـ Dockerfile أو runAsUser في الـ Pod.

❌ Audit table the app can rewrite 
GRANT ALL ON deploy_audit TO app;
-- كده أي bug أو مهاجم يقدر يعدّل التاريخ
✅ Insert-only role 
GRANT SELECT, INSERT ON deploy_audit TO audit_writer;
-- أي UPDATE هيترفض بـ permission denied
بالعامية

❌ لو الـ app role يقدر يعمل UPDATE أو DELETE على جدول الـ audit، الـ evidence كلها ملهاش قيمة. ✅ role بـ INSERT وSELECT بس، وجرّبناه فوق والـ Postgres رفض بـ permission denied for table deploy_audit.

1. Predict the verdict 🟢 easy Before running anything, decide whether gateway can reach billing:8080 with the policies in Part 2. Then add one q(...) line to policy-sim.ts and check.

2. Catch hostPort 🟡 medium The Baseline profile disallows hostPort. Add a check to lintPodSpec and prove it with a container that sets hostPort: 8080.
الـ Baseline profile بيمنع hostPort. ضيف check في lintPodSpec واثبته بـ container فيه hostPort: 8080.
Solution · الحل 
import { lintPodSpec } from "../pod-checks.ts";

type Obj = Record<string, any>;

// الـ check الجديد: بيتحط جوه lintPodSpec مع باقي الـ checks بتاعة الـ container
function hostPortFindings(pod: Obj): string[] {
  const out: string[] = [];
  for (const c of pod.containers ?? []) {
    for (const p of c.ports ?? []) {
      if (p.hostPort) out.push(`${c.name}: hostPort ${p.hostPort} must not be used`);
    }
  }
  return out;
}

const pod: Obj = {
  containers: [{ name: "orders", image: "x", ports: [{ containerPort: 3000, hostPort: 8080 }] }],
};
console.log(hostPortFindings(pod));
// → [ 'orders: hostPort 8080 must not be used' ]

// الـ linter الأصلي مكانش بيشوفها: 0 يعني مفيش finding عن الـ port
console.log(lintPodSpec(pod).filter((f) => f.rule.includes("hostPort")).length);
// → 0
الـ loop بيمشي على ports بتاعة كل container ويضيف finding لو فيه hostPort، والـ output جاي من تشغيل حقيقي.
3. Find the sneaky NotAction 🔴 hard "Effect": "Allow", "NotAction": ["iam:*"] grants everything except IAM, and auditIam misses it completely because there is no Action field. Add a rule and prove it.
"Effect": "Allow", "NotAction": ["iam:*"] بيدّي كل حاجة ما عدا IAM، وauditIam مش بيشوفه خالص لأن مفيش field اسمه Action. ضيف rule واثبته.
Hint · تلميح Check for s.NotAction before reading s.Action. Treat NotResource the same way.
اتشيك على s.NotAction قبل ما تقرا s.Action، وعامل NotResource بنفس الطريقة.
Solution · الحل 
type Obj = Record<string, any>;
interface Finding { sev: string; resource: string; issue: string; }

// الـ rule ده أول حاجة جوه الـ loop في auditIam، قبل ما نقرا s.Action
function notActionFindings(policyName: string, s: Obj): Finding[] {
  if (s.Effect !== "Allow") return [];
  const out: Finding[] = [];
  if (s.NotAction) out.push({ sev: "HIGH", resource: `iam/${policyName}`, issue: "Allow with NotAction grants everything except the list" });
  if (s.NotResource) out.push({ sev: "HIGH", resource: `iam/${policyName}`, issue: "Allow with NotResource grants every other resource" });
  return out;
}

console.log(notActionFindings("support-role", { Effect: "Allow", NotAction: ["iam:*"], Resource: "*" }));
// → [
// →   {
// →     sev: 'HIGH',
// →     resource: 'iam/support-role',
// →     issue: 'Allow with NotAction grants everything except the list'
// →   }
// → ]

// الـ Deny بـ NotAction شكل مشهور للـ guardrails، فمش finding
console.log(notActionFindings("guardrail", { Effect: "Deny", NotAction: ["iam:*"], Resource: "*" }).length);
// → 0
الـ rule بيتحط أول حاجة جوه الـ loop، والـ output اللي تحت جاي من تشغيل حقيقي.

Cheat sheet · الخلاصة

  • Container: non-root numeric UID, no privilege escalation, drop ALL, seccomp RuntimeDefault, read-only root, memory limit, no hostPath/hostNetwork.
  • restricted doesn't require a read-only root or memory limits: add them yourself.
  • A schema check proves a manifest is valid, not safe. Lint it after.
  • Per-app ServiceAccount, minimal Role, no auto-mounted token. list Secrets and create Pods are the dangerous verbs.
  • NetworkPolicy is deny only once selected. Needs an enforcing CNI, both sides, and a DNS exception.
  • Secrets are base64 in etcd by default. Enable EncryptionConfiguration, KMS first, identity last.
  • Cloud audit: Deny * is fine, iam:PassRole * is critical, 443 on the ALB is fine, 5432 on the internet is critical.
  • CloudTrail multi-region with validation for who-did-what. GuardDuty for what you never wrote a rule for.
  • Pin actions by full SHA and images by digest. Tags move: the 2026 trivy-action compromise.
  • Sign the digest, verify at admission, attach the SBOM as an attestation. Policy lives in Kyverno or OPA.
  • SOC 2 Type II and ISO 27001 ask you to prove controls operated. Engineering's job is evidence from queries.
  • A baseline is one page where every line has a check that fails the build.
بالعامية
  • الـ container: UID رقمي مش root، مفيش privilege escalation، drop ALL، و seccomp RuntimeDefault، و read-only root، و memory limit، ومفيش hostPath ولا hostNetwork.
  • restricted مش بيطلب read-only root ولا memory limit: ضيفهم بنفسك.
  • الـ schema check بيثبت إن الـ manifest صح، مش إنه آمن. اعمل lint بعده.
  • ServiceAccount لكل app، و Role محدود، ومفيش token متركّب أوتوماتيك. list على الـ Secrets وcreate على الـ Pods هما الـ verbs الخطر.
  • الـ NetworkPolicy بتبقى deny بس لما تختار الـ Pod. ومحتاجة CNI بيطبقها، وإذن من الناحيتين، واستثناء للـ DNS.
  • الـ Secrets في etcd base64 بس by default. فعّل EncryptionConfiguration، الـ KMS الأول وidentity آخر حاجة.
  • الـ cloud audit: Deny * عادي، وiam:PassRole * critical، و 443 على الـ ALB عادي، و 5432 على الإنترنت critical.
  • CloudTrail multi-region و validation عشان تعرف مين عمل إيه، و GuardDuty للحاجات اللي عمرك ما كتبت لها rule.
  • ثبّت الـ actions بـ SHA كامل والـ images بـ digest. الـ tags بتتحرك، وده اللي حصل في حادثة trivy-action في 2026.
  • وقّع على الـ digest، واتحقق عند الـ admission، وحط الـ SBOM كـ attestation. والـ policy تعيش في Kyverno أو OPA.
  • الـ SOC 2 Type II و ISO 27001 بيطلبوا إنك تثبت إن الـ controls اتنفذت، وشغل الهندسة هو evidence بتطلع من queries.
  • الـ baseline صفحة واحدة، وكل سطر فيها ليه check بيوقّع الـ build.
