Why this matters · ليه ده مهم

English

A test suite is the thing that lets a team change code on a Tuesday afternoon without a meeting. It only earns that trust if each test can actually fail, if a failure names the behaviour that broke, and if the bugs that really reach production are the ones it catches. Most suites fail at one of those three. In interviews, "what would you test and at which level?" separates people who wrote tests from people who decided what the tests were for.

بالعامية

الـ test suite هي اللي بتخلّي الفريق يغيّر الكود يوم التلات بعد الضهر من غير اجتماع ومن غير خوف. بس الثقة دي مش ببلاش: لازم كل test يكون قادر يفشل فعلًا، ولما يفشل يقولك إيه السلوك اللي اتكسر، ويكون بيمسك الـ bugs اللي بتوصل production بجد. أغلب الـ suites بتقع في واحدة من التلاتة دول. وفي الـ interviews، سؤال "هتختبر إيه وعلى أنهي level؟" بيفرّق بين حد كتب tests وحد قرر الـ tests دي موجودة ليه.

Part 1 — Four kinds of test on one feature 🟢 Basicالجزء 1 — أربع أنواع tests على feature واحدة

English

The names come down to one question: how much of the real system is running? A unit test runs one function with nothing around it. An integration test runs several real parts together, here the Express app and a real Postgres. An E2E test drives the product the way a user does, through a real browser. A smoke test asks one thing after a deploy: is the system up at all?

Below is a real POST /orders on Express 5 with Postgres 18, tested at all four levels. Each file was run. After that come four planted bugs, one per level, because the interesting result isn't that the tests pass. It's which test notices which bug.

Two details in the handler matter for this part. The pre-check select makes the handler look idempotent, but only the unique index makes it so when two requests race. And /health runs a real query, because a health check that returns ok without touching the database can't tell you the database URL is wrong.

export type LineItem = { sku: string; unitPriceCents: number; quantity: number };
export type PricedOrder = { subtotalCents: number; vatCents: number; totalCents: number };

// الـ function دي pure: مفيش DB ولا وقت ولا network
export function priceOrder(items: LineItem[], vatRate: number): PricedOrder {
  const subtotalCents = items.reduce((sum, i) => sum + i.unitPriceCents * i.quantity, 0);
  const vatCents = Math.round(subtotalCents * vatRate);
  return { subtotalCents, vatCents, totalCents: subtotalCents + vatCents };
}

    const { rows } = await pool.query(

    res.json({ orders: rows });
  });

  app.post("/orders", async (req, res) => {
    const key = req.header("idempotency-key");
    if (!key) return void res.status(400).json({ error: "missing_idempotency_key" });

    const parsed = CreateOrder.safeParse(req.body);
    if (!parsed.success) return void res.status(422).json({ error: "invalid_order" });

    const previous = await pool.query(
      "select id, total_cents from orders where idempotency_key = $1", [key]);
    if (previous.rows[0]) return void res.status(200).json(previous.rows[0]);

    const { subtotalCents, vatCents, totalCents } = priceOrder(parsed.data.items, EGYPT_VAT);
    try {
      const { rows } = await pool.query(
        `insert into orders (idempotency_key, customer_email, subtotal_cents, vat_cents, total_cents)
         values ($1, $2, $3, $4, $5) returning id, total_cents`,
        [key, parsed.data.customerEmail, subtotalCents, vatCents, totalCents]);
      res.status(201).json(rows[0]);
    } catch (err) {
      // لو request تاني سبقنا، الـ unique index بيرمي 23505 ونرجّع الـ order بتاعه
      if ((err as { code?: string }).code !== "23505") throw err;
      const winner = await pool.query(
        "select id, total_cents from orders where idempotency_key = $1", [key]);
      res.status(200).json(winner.rows[0]);
    }
  });

  return app;
}

export function testDatabaseUrl(): string {
  const raw = process.env.DATABASE_URL ?? "";
  const url = new URL(raw);
  const port = Number(url.port);
  if (!/^\d+$/.test(url.port) || port < 1024 || [5432, 27017, 6379].includes(port)) {
    throw new Error(`refusing to run tests against port "${url.port}"`);
  }
  return raw;
}

الأسماء كلها بترجع لسؤال واحد: قد إيه من النظام الحقيقي شغال في الـ test؟ الـ unit بيشغّل function واحدة ومفيش حواليها حاجة. الـ integration بيشغّل كذا جزء حقيقي مع بعض، وهنا Express مع Postgres حقيقية. الـ E2E بيمشي في المنتج زي المستخدم بالظبط، من browser حقيقي. والـ smoke بيسأل سؤال واحد بعد الـ deploy: هو النظام شغال أصلًا؟

فوق عندك POST /orders حقيقي على Express 5 و Postgres 18، متختبر على الأربع levels، وكل ملف اتشغّل فعلًا. وبعدها 4 bugs مزروعة، واحدة لكل level، لأن المهم مش إن الـ tests تعدّي، المهم مين بيلاحظ أنهي bug.

فيه حاجتين في الـ handler مهمين للجزء ده. الـ select اللي قبل الـ insert بيخلّي الـ handler شكله idempotent، بس الضمان الحقيقي لما اتنين requests يتسابقوا هو الـ unique index. والـ /health بيعمل query حقيقية، لأن health check بترد ok من غير ما تلمس الـ DB عمرها ما هتقولك إن الـ database URL غلط.

فين هستخدمه في شغلي؟ في أي API جديد عندك، قبل ما تبدأ tests اسأل: أنهي bug لو عدّى هيوجع أكتر، وأنهي level هو الوحيد اللي هيمسكه؟ حساب الضريبة في priceOrder ده unit. الـ unique index بتاع الـ idempotency ده integration بس. زرار الدفع اللي مش متوصل ده E2E. والـ DATABASE_URL الغلط في الـ environment الجديدة ده smoke بعد الـ deploy. لو حد في الـ code review قالك "اكتب E2E لكل حاجة"، الجدول اللي تحت هو ردك.

Part 2 — Pyramid vs trophy 🟢 Basicالجزء 2 — الـ pyramid ضد الـ trophy

English

The test pyramid (Mike Cohn, 2009) says: many unit tests, some integration, few E2E, because unit tests are cheap and E2E is slow and brittle. The testing trophy (Kent C. Dodds) keeps static analysis as the base, then puts most of the weight on integration, with some unit tests and a few E2E. Its argument: "the more your tests resemble the way your software is used, the more confidence they can give you".

For a Node API or a Next app, most real bugs live at the seams: the SQL that doesn't match the schema, the validation that lets a bad body through, the auth middleware that isn't mounted on one route. A unit test with everything around it mocked can't see any of those. An integration test through the HTTP layer with a real database sees all of them, and it's cheap now: a real Postgres test costs tens of milliseconds (≈31 ms here).

The pyramid still wins where the logic is pure and the input space is large: pricing rules, parsers, date arithmetic, state machines. There, one integration test per edge case would be slow and would obscure which rule broke. Static analysis (TypeScript strict, ESLint) is the base of the trophy: a whole class of mistakes costs zero test code.

Using the per-test costs measured for Part 1, the suite time of a 200-test service in each shape is below. The trophy costs more, but both shapes are minutes, not hours, and E2E dominates either way. The right question is what the extra 3 to 10 seconds buys.

// بنحسب وقت suite فيها 200 test بالأرقام اللي اتقاست في الجزء الأول
type LevelCost = { name: string; perTestMs: number; overheadMs: number };

const unit: LevelCost = { name: "unit", perTestMs: 0.9, overheadMs: 576 };
const integration: LevelCost = { name: "integration", perTestMs: 102, overheadMs: 798 };
const plainIntegration: LevelCost = { name: "plain integration", perTestMs: 31, overheadMs: 798 };
const e2e: LevelCost = { name: "e2e", perTestMs: 314, overheadMs: 1569 };

type Shape = { name: string; unit: number; integration: number; e2e: number };

function suiteSeconds(shape: Shape, integrationCost: LevelCost): number {
  const testsMs =
    shape.unit * unit.perTestMs +
    shape.integration * integrationCost.perTestMs +
    shape.e2e * e2e.perTestMs;
  const overheadMs = unit.overheadMs + integrationCost.overheadMs + e2e.overheadMs;
  return (testsMs + overheadMs) / 1000;
}

بالعامية

الـ test pyramid (Mike Cohn، سنة 2009) بتقول: unit كتير، integration أقل، E2E قليل، عشان الـ unit رخيص والـ E2E بطيء وبيتكسر بسهولة. الـ testing trophy (Kent C. Dodds) بيخلّي الـ static analysis هو القاعدة، وبعدين يحط أغلب الوزن على الـ integration، وشوية unit، وE2E قليل. وحجته: "كل ما الـ tests بتاعتك تشبه الطريقة اللي الـ software بيتستخدم بيها، كل ما تديك ثقة أكتر".

في Node API أو Next app، أغلب الـ bugs الحقيقية قاعدة عند الـ seams (نقط التوصيل): الـ SQL اللي مش ماشي مع الـ schema، الـ validation اللي سايب body غلط يعدّي، الـ auth middleware اللي مش متركب على route معين. الـ unit test اللي كل حاجة حواليه mock مش هيشوف ولا واحدة من دول. والـ integration من الـ HTTP layer بـ DB حقيقية بيشوفهم كلهم، وبقى رخيص كمان: test على Postgres حقيقية بياخد عشرات الـ milliseconds (حوالي 31 ms هنا).

الـ pyramid لسه كسبانة لما الـ logic يكون pure والـ inputs كتير: قواعد التسعير، الـ parsers، حسابات التواريخ، الـ state machines. هناك لو عملت integration لكل edge case هيبقى بطيء ومش هتعرف أنهي rule اللي اتكسرت. والـ static analysis (TypeScript strict و ESLint) هو قاعدة الـ trophy: نوع كامل من الغلطات بتخلص منه من غير ما تكتب سطر test.

بالأرقام اللي قسناها في الجزء الأول، وقت suite فيها 200 test في كل شكل موجود فوق. الـ trophy أغلى شوية، بس الاتنين بالدقايق مش بالساعات، والـ E2E هو اللي بياكل الوقت في الحالتين. السؤال الصح: الـ 3 لـ 10 ثواني الزيادة دول بيشتروا إيه؟

فين هستخدمه في شغلي؟ في service زي orders API: حط priceOrder والـ state machine بتاعة الـ order في unit tests كتير، وكل route بـ Supertest على Postgres حقيقية (ده الجسم الأساسي)، وE2E للـ checkout والـ signup بس. ولما حد يقترح "نغطي كل الـ services بـ E2E" احسبها بالجدول ده: كل E2E بياخد مئات الـ ms وبيبقى flaky، فخليها للـ critical flows.
Interview question (exit test Q1) "Why is an integration test worth more than a unit test in a backend, and when is a unit test better?" → Most backend bugs are at seams: SQL, validation, auth middleware, serialization. An integration test through HTTP with a real database exercises those seams, and a unit test with mocks can't. Unit is better for pure logic with many cases (pricing, parsers, dates): it's dozens of times faster (≈0.9 ms vs ≈31 ms here) and tells you exactly which rule broke.

Part 4 — AAA and one behaviour per test 🟢 Basicالجزء 4 — الـ AAA و سلوك واحد في كل test

English

Arrange, Act, Assert: set up the world, do the one thing you're testing, check the outcome. Three blocks, and the Act is usually one line. When a test has several Acts in a row, it's several tests pretending to be one.

The test below creates an order, pays it, refunds it and asserts nine things in one body. It has two independent problems. First, an assertion that fails throws, so everything after it never runs: two bugs need two CI cycles to be seen. Second, the name says nothing, so the report tells you "test order flow failed" and you read the code to find out what the flow was.

"One behaviour" isn't "one expect". Several asserts on one outcome are fine: status and amount of the same receipt are one behaviour. When you do want every mismatch from a single outcome reported in one run, expect.soft records the failure and carries on.

export type OrderStatus = "pending" | "paid" | "partially_refunded" | "refunded";

export type Order = {
  id: string;
  status: OrderStatus;
  totalCents: number;
  paidCents: number;
  refundedCents: number;
  history: string[];
};

export function createOrder(id: string, totalCents: number): Order {
  return { id, status: "pending", totalCents, paidCents: 0, refundedCents: 0, history: ["created"] };
}

export function payOrder(order: Order, amountCents: number): Order {
  if (amountCents !== order.totalCents) throw new Error("amount_mismatch");
  return { ...order, status: "paid", paidCents: amountCents, history: [...order.history, "paid"] };
}

export function refundOrder(order: Order, amountCents: number): Order {
  if (order.status === "pending") throw new Error("not_paid");
  const refundedCents = order.refundedCents + amountCents;
  if (refundedCents > order.paidCents) throw new Error("refund_exceeds_paid");
  const status = refundedCents === order.paidCents ? "refunded" : "partially_refunded";
  return { ...order, status, refundedCents, history: [...order.history, "refunded"] };
}

Part 5 — Given/When/Then and names that read as a spec 🟢 Basicالجزء 5 — Given/When/Then وأسماء بتتقرا كـ spec

English

Given/When/Then is a way of thinking about a test before you write it: given this situation, when this happens, then that should be true. It maps directly onto AAA, and in Vitest it fits nested describe blocks: one describe per Given, one it per Then.

A good name states a requirement a product person would recognise: returns 404 when the order belongs to another tenant. A bad name says nothing (test1, it works) or describes the implementation (calls repository.findById). The implementation name is the most dangerous one, because it survives while becoming false: rename findById and the test name is now a lie, or a bug appears and the name still reads as "correct".

The practical test: run --reporter=verbose and read the output aloud. If it reads like the requirements, the names are right.

export type Order = { id: string; tenantId: string; totalCents: number };

export interface OrderRepository {
  findById(id: string): Promise<Order | undefined>;
}

export type GetOrderResult = { status: 200; order: Order } | { status: 404 };

export async function getOrder(repo: OrderRepository, tenantId: string, orderId: string): Promise<GetOrderResult> {
  const order = await repo.findById(orderId);
  // نفس الـ 404 للي مش موجود وللي بتاع tenant تاني، عشان منكشفش إن الـ id موجود
  if (!order || order.tenantId !== tenantId) return { status: 404 };
  return { status: 200, order };
}

Part 6 — See it fail first 🟢 Basicالجزء 6 — لازم تشوفه يفشل الأول

English

A test that has never failed has told you nothing: a green that can't turn red is decoration. All the examples below ran against a chargeCard that has a real bug: an expired card gets charged anyway.

What changed with Vitest 5. The classic advice says a missing await on .rejects lets the test pass forever. That's no longer true here: Vitest 5.1 fails the test with an explicit "was not awaited" message (real output below), and Jest 30.5 fails too, though less helpfully: the assertion surfaces as an uncaught error that crashes the run with exit 1. So that specific mistake now gets caught. Three others still pass forever:

  • a .catch-only test: if nothing rejects, the callback (and every assertion in it) never runs;
  • a try/catch test with the expect inside the catch: same thing;
  • an assertion against a value you just mocked: it compares the mock with itself and never runs a line of production code.

The procedure. For a new test: write it, watch it go red for the right reason, then make it green. For a test on code that already exists: break the production line on purpose, see the test fail, and restore the line. My first version of the race test in Part 1 taught me this: with a cold connection pool the first request apparently finished before the others got a connection, so the index could be deleted and the test stayed green (0 of 5 runs caught it). Warming the pool so the requests actually race made it catch the bug in 5 of 5 runs. I'd never have known without breaking it on purpose. Lesson 03 automates this procedure with mutation testing.

Part 7 — The Vitest toolkit 🟢 Basicالجزء 7 — أدوات Vitest

English

Vitest 5 is a sensible default for new TypeScript and ESM code, and Jest 30 is what you'll meet in many existing codebases. The API is almost the same. The real differences, each checked here on Vitest 5.1 and Jest 30.5:

  • Globals: Jest injects describe, it, expect; Vitest imports them from "vitest" unless you set globals: true.
  • Mock API: jest.fn() and jest.spyOn() versus vi.fn() and vi.spyOn().
  • TypeScript and ESM: Vitest transforms them out of the box; Jest needs a transform (ts-jest or Babel) and ESM support is still experimental.
  • Aliases: Jest 30 removed toBeCalled and friends, so use toHaveBeenCalled. Vitest 5 still has both. Use the long form in both and you never think about it.
  • expect.soft: exists in Vitest; undefined in Jest 30.

Hoisting of vi.mock and fake timers are in 04 Node, lesson 29, part 2. New here are the matchers people misuse. toEqual ignores properties whose value is undefined and ignores the class of an object, so a serialization bug can pass it. toStrictEqual doesn't. toMatchObject checks a subset of the object's properties, but arrays must match in length. expect.any and asymmetric matchers (expect.stringMatching, expect.arrayContaining, expect.objectContaining) describe what you can't predict, like generated ids and timestamps. And toThrow needs a function, not the result of calling one.

Hooks run outside-in before a test and inside-out after it (order printed below). it.each turns a table into named cases. it.only and it.skip focus and skip tests. A stray .only silently removes every other test in that file from the run, so CI must refuse it: Vitest does so when CI is set (it defaults allowOnly to off there), and --allowOnly=false makes the same check explicit.

  • expect.soft: موجود في Vitest؛ undefined في Jest 30.

الـ hoisting بتاع vi.mock والـ fake timers موجودين في الدرس 29 في قسم Node، الجزء 2. الجديد هنا هو الـ matchers اللي الناس بتستخدمها غلط. toEqual بيتجاهل أي property قيمتها undefined وبيتجاهل نوع الـ class، فـ bug في الـ serialization ممكن يعدّي. toStrictEqual لأ. toMatchObject بيتأكد من subset من الـ properties، بس الـ arrays لازم نفس الطول. expect.any والـ asymmetric matchers (expect.stringMatching وexpect.arrayContaining وexpect.objectContaining) بيوصفوا اللي مش هتقدر تتوقعه زي الـ generated ids والـ timestamps. وtoThrow محتاجة function مش نتيجة نداء function.

الـ hooks بتشتغل من بره لجوه قبل الـ test، ومن جوه لبره بعده (الترتيب مطبوع فوق). it.each بيحوّل جدول لـ tests بأسماء. it.only وit.skip بيركزوا أو يتخطوا tests. والـ .only المنسية بتشيل باقي الملف من الـ run في صمت، فالـ CI لازم يرفضها: Vitest بيعمل ده لوحده لما CI تكون متظبطة (allowOnly بيبقى off افتراضيًا هناك)، و--allowOnly=false بيخلي نفس الفحص صريح.

فين هستخدمه في شغلي؟ it.each هو اللي هتستخدمه لجدول الضرايب بالدول بدل 4 tests متكررين. وtoMatchObject مع expect.any(String) هو اللي هيريّحك في response فيها id وcreatedAt. والغلطة الشائعة: حد يسيب .only في PR والـ CI يعدّيها، فلازم تتأكد إن الـ pipeline شغال بـ CI=true أو --allowOnly=false، وكمان lint rule زي jest/no-focused-tests لو بتستخدم Jest.
What Vitest's check doesn't cover --allowOnly=false turns a stray .only into a failure. It doesn't turn a stray .skip into one: a skipped test still shows up as skipped and the run stays green. Grep for .skip in review, or fail CI on it with a lint rule, and put a ticket number next to any you keep.
الفحص ده ميمسكش .skip. الـ --allowOnly=false بيفشّل الـ .only المنسية بس، لكن الـ .skip بتفضل skipped والـ run أخضر. دوّر على .skip في الـ review أو فشّل الـ CI عليها بـ lint rule، ولو سيبت واحدة حط جنبها رقم ticket.

Common mistakes · غلطات شائعة

❌ toThrow on a value 
expect(parseAmount("abc")).toThrow();
// الـ function اتنادت قبل expect، فالـ test وقع بالـ RangeError نفسه
✅ toThrow on a function 
expect(() => parseAmount("abc")).toThrow(RangeError);
// الـ expect هو اللي بينادي الـ function ويمسك الـ error
بالعامية

❌ expect(parseAmount("abc")) بينادي الـ function قبل ما expect يبدأ، فالـ error بيوقع الـ test برسالة مش متوقعة، وtoThrow نفسها عمرها ما بتشتغل. ✅ لفّها في arrow function، وexpect هو اللي ينادي ويقدر يمسك الـ error ويتأكد من نوعه أو رسالته.

❌ Asserting on the mock 
const repo = { findById: vi.fn().mockResolvedValue(order) };
const found = await repo.findById("o-1");
// ده بيقارن الـ mock بنفسه، ومفيش سطر production اتنفذ
expect(found).toEqual(order);
✅ Assert on your code's result 
const repo = { findById: vi.fn().mockResolvedValue(order) };
const result = await getOrder(repo, "acme", "o-1");
// الـ production code اتنفذ، والـ assertion على نتيجته هو
expect(result).toEqual({ status: 200, order });
بالعامية

❌ لو الـ test بينادي الـ mock مباشرة ويقارن نتيجته، يبقى بيختبر Vitest مش الكود بتاعك، وهيفضل أخضر حتى لو مسحت الـ production code كله. ✅ نادي الـ function الحقيقية (getOrder) واعمل assert على اللي هي رجّعته، والـ mock يبقى مجرد input ليها.

❌ Assertions inside catch 
try {
  await chargeCard(expired, 500);
} catch (err) {
  // لو مفيش throw، ولا expect بيتنفذ والـ test بينجح
  expect((err as CardError).code).toBe("expired_card");
}
✅ rejects with await 
await expect(chargeCard(expired, 500))
  .rejects.toMatchObject({ code: "expired_card" });
// لو الـ promise نجحت، الـ test بيفشل وبيقول ليه
بالعامية

❌ الـ expect جوه catch مبيتنفذش لو الـ function مش بترمي، فالـ test بيعدّي على bug واضح. وده اللي شفناه في الجزء 6 بتشغيل حقيقي. ✅ await expect(promise).rejects… بيفشل لو الـ promise نجحت، ومعاه رسالة بتقول ليه.

❌ A name about the implementation 
it("calls repository.findById", async () => {
  await getOrder(repo, "acme", "missing");
  expect(repo.findById).toHaveBeenCalledWith("missing");
});
✅ A name about behaviour 
it("returns 404 for an id that does not exist", async () => {
  const result = await getOrder(repoWith(), "acme", "missing");
  expect(result).toEqual({ status: 404 });
});
بالعامية

❌ الاسم الأول بيوصف call داخلية، فأي refactor يكسره ولو السلوك زي ما هو، ومش بيضمن إن المستخدم بياخد 404. ✅ التاني بيقول requirement، وبيفضل صح مهما غيّرت في الـ repository، ولو السلوك نفسه اتكسر بيفشل بجد.

Cheat sheet · الخلاصة

  • Unit: one function, no I/O. Integration: real parts together (Express + real Postgres). E2E: real browser. Smoke: is the deployed system up.
  • A level earns its place by catching a bug the others can't see; the matrix proves it.
  • Pyramid: many unit tests. Trophy: static base, most weight on integration. Backend and Next bugs live at the seams, so trophy fits; pure logic stays unit.
  • Choose by speed, confidence, maintenance. A mock-heavy test can fail on a rename and pass a real bug.
  • AAA, one behaviour per test. Several asserts on one outcome are fine; expect.soft reports all of them.
  • Name the behaviour, not the call: Given in describe, Then in it; verbose output should read as requirements.
  • A test that never failed proves nothing: red first, or break the line and restore it. Vitest 5 fails a missing await on .rejects; .catch, try/catch and mocked-value tests still pass forever.
  • toEqual ignores undefined and class; toStrictEqual doesn't; toThrow needs a function.
  • Hooks: before outside-in, after inside-out. it.each for tables. CI must reject .only: CI=true or --allowOnly=false.
بالعامية
  • الـ unit: function واحدة ومفيش I/O. الـ integration: أجزاء حقيقية مع بعض (Express و Postgres حقيقية). الـ E2E: browser حقيقي. الـ smoke: هل الـ system اللي اتعمله deploy شغال.
  • الـ level بيستحق مكانه لما يمسك bug التانيين مش شايفينه، وجدول الـ bugs المزروعة بيثبت ده.
  • الـ pyramid: unit كتير. الـ trophy: قاعدة static وأغلب الوزن على الـ integration. الـ bugs في Backend و Next عند الـ seams، فالـ trophy أنسب، والـ logic الـ pure يفضل unit.
  • اختار بالسرعة والثقة والصيانة. الـ test اللي كله mocks ممكن يفشل على rename ويعدّي على bug حقيقي.
  • الـ AAA وسلوك واحد في كل test. كذا assert على نتيجة واحدة مفيش مشكلة، وexpect.soft بيطلّعهم كلهم.
  • سمّي السلوك مش الـ call: الـ Given في describe والـ Then في it، والـ verbose output المفروض يتقرا زي الـ requirements.
  • الـ test اللي عمره ما فشل ما أثبتش حاجة: أحمر الأول، أو اكسر السطر ورجّعه. Vitest 5 بيفشّل نسيان الـ await على .rejects، بس .catch وtry/catch والـ mocked value لسه بيعدّوا على طول.
  • toEqual بيتجاهل undefined والـ class، وtoStrictEqual لأ، وtoThrow محتاجة function.
  • الـ hooks: الـ before من بره لجوه، والـ after من جوه لبره. it.each للجداول. والـ CI لازم يرفض .only: يا CI=true يا --allowOnly=false.
