Why this matters · ليه ده مهم

English

A secret has a lifecycle: it gets created, stored, delivered to a process, used, sometimes leaked, and eventually replaced. Most teams only design the "stored" step. The expensive incidents come from the others: a key that was deleted in a later commit but still sits in history, a database URL printed by a crash handler, a password nobody dares change because the last rotation took the API down.

This lesson walks the whole lifecycle with things you can run. Interviewers ask "a key leaked, what do you do in the first hour?" and "how do you rotate a database password with no downtime?" because the answers separate people who have operated a system from people who have only built one.

بالعامية

الـ secret ليه دورة حياة: بيتعمل، بيتخزن، بيوصل للـ process، بيتستخدم، وساعات بيتسرب، وفي الآخر بيتغير. معظم الفرق بتصمم خطوة التخزين بس. الحوادث الغالية بتيجي من الباقي: key اتمسح في commit بعدها بس لسه قاعد في الـ history، أو database URL طبعه الـ crash handler، أو password محدش بيجرؤ يغيره عشان آخر rotation وقّعت الـ API.

الدرس ده بيمشي على الدورة كلها بحاجات تقدر تشغلها. وفي الـ interviews هيسألوك "key اتسرب، هتعمل إيه في أول ساعة؟" و"إزاي تغيّر password الـ database من غير downtime؟"، لأن الإجابات دي بتفرّق بين اللي شغّل system بجد واللي بناه بس.

Part 1 — Not in code, not in history 🟢 Basicالجزء 1 — مش في الكود ومش في الـ history

English

Deleting a secret in a new commit removes it from the working tree and leaves it in every earlier commit. Node lesson 26, part 5 walks through that accident, so here is only the proof from this lesson's sandbox repo: the current file is clean, and git log -p -S finds the key in two commits.

The defense has to run before the commit exists. secretlint 13 is a Node tool, so it fits a Node repo with no extra binary, and below it runs as a real pre-commit hook on staged files only. Two limits matter. A scanner only finds shapes it knows, so your internal key format needs its own pattern: in this run the preset flagged a postgres:// URL with a password, but not the internal key and not an https://user:password@ URL. And a local hook is optional by nature: git commit --no-verify skipped it here and the commit went through. So the hook gives fast feedback, and the enforcing check belongs on the server: CI plus the host's push protection.

Part 2 — .env vs a secrets manager 🟢 Basicالجزء 2 — الـ .env مقابل الـ secrets manager

English

.env is fine for local development: one developer, fake or sandbox values, ignored by git. Loading and validating config with Zod at startup is covered in Node lesson 32, part 2. It stops being fine in production because a file on a host has no access log, no versioning, no rotation and no per-service permission.

A secrets manager answers those four. The app authenticates with its platform identity, such as an IAM role, so no long-lived credential ships with it, and that also solves the "secret zero" question of what protects the secret that fetches the secrets. Calling the manager on every request is the classic mistake: it adds a network hop, it costs money per call, and a manager outage becomes your outage. So cache with a TTL, collapse concurrent misses into one call, and keep serving the stale value if a refresh fails. A cold start during an outage still has to fail, because there's nothing to serve.

The TTL is also your rotation propagation delay: with a 5-minute TTL, a rotated value can take up to 5 minutes to reach every instance, which is why Part 7 keeps both credentials valid for longer than that.

import { GetSecretValueCommand, type SecretsManagerClient } from "@aws-sdk/client-secrets-manager";

type Entry = { value: string; fetchedAt: number };

export class SecretCache {
  private entries = new Map<string, Entry>();
  private inflight = new Map<string, Promise<string>>();

  private readonly client: SecretsManagerClient;
  private readonly ttlMs: number;
  private readonly now: () => number;

  constructor(client: SecretsManagerClient, ttlMs: number, now: () => number = Date.now) {
    this.client = client;
    this.ttlMs = ttlMs;
    this.now = now;
  }

  async get(secretId: string): Promise<string> {
    const hit = this.entries.get(secretId);
    if (hit && this.now() - hit.fetchedAt < this.ttlMs) return hit.value;

    // طلب واحد بس للـ secret ده، حتى لو 1000 request طلبوه في نفس اللحظة
    const running = this.inflight.get(secretId);
    if (running) return running;
    const p = this.fetchFresh(secretId, hit).finally(() => this.inflight.delete(secretId));
    this.inflight.set(secretId, p);
    return p;
  }

  private async fetchFresh(secretId: string, stale: Entry | undefined): Promise<string> {
    try {
      const res = await this.client.send(new GetSecretValueCommand({ SecretId: secretId }));
      if (res.SecretString === undefined) throw new Error(`secret ${secretId} has no string value`);
      this.entries.set(secretId, { value: res.SecretString, fetchedAt: this.now() });
      return res.SecretString;
    } catch (err) {
      // لو الـ manager وقع والقيمة القديمة موجودة كمّل بيها، بدل ما الـ API كله يقع
      if (stale) return stale.value;
      throw err;
    }
  }
}

بالعامية

.env تمام للـ local: developer واحد، قيم وهمية أو sandbox، ومتجاهل في git. تحميل الـ config والتحقق منه بـ Zod وقت الـ startup موجود في الدرس 32 في Node، الجزء 2. لكنه مش مناسب لـ production، لأن ملف على host مفيهوش access log ولا versioning ولا rotation ولا صلاحيات لكل service.

الـ secrets manager بيحل الأربعة دول. الـ app بيعمل authenticate بالـ identity بتاعته من الـ platform (زي IAM role)، فمفيش credential طويل العمر بيتشحن معاه، وده كمان بيحل مشكلة "secret zero": مين بيحمي الـ secret اللي بيجيب الـ secrets.

الغلطة الكلاسيك إنك تنادي الـ manager مع كل request: ده network hop زيادة، وفلوس على كل call، ولو الـ manager وقع إنت كمان وقعت. فالصح: cache بـ TTL، ودمج الطلبات المتزامنة في call واحد، وتكمل بالقيمة القديمة لو الـ refresh فشل. أما process لسه بادئ وقت الـ outage فلازم يفشل، لأن مفيش حاجة يقدمها.

والـ TTL كمان هو وقت انتشار الـ rotation: لو الـ TTL خمس دقايق، القيمة الجديدة ممكن تاخد لحد خمس دقايق توصل لكل instance. وعشان كده الجزء 7 بيخلي الـ credentials الاتنين شغالين مدة أطول من كده.

عن التكلفة: مثال AWS نفسها على صفحة الأسعار (اتقرت 2026-11-09) بيستخدم $0.40 للـ secret في الشهر، والـ API calls بتتحسب لكل 10,000 call، وراجع الجدول الحي لرقمها.

فين هستخدمه في شغلي؟ API على ECS أو Kubernetes: الـ pod بياخد IAM role، وعند الـ boot بيعمل cache.get("prod/orders/db")، والـ JSON بيعدي على parseDbSecret قبل ما يتبني الـ pool. ولو الـ Secrets Manager عمل throttling وقت deploy كبير، الـ pods الشغالة بتكمل بالـ cache، والجديدة بس هي اللي بتفشل وتعيد المحاولة.

Part 3 — Layers, logs and errors 🟢 Basicالجزء 3 — الـ layers والـ logs والـ errors

English

Docker image layers are covered in Node lesson 28, part 5. This part is about the sinks that don't look like storage: the message of a thrown error, a crash dump, and the logs. Each one gets copied to places with far weaker access control than your secrets manager, and they're retained for months.

The sharpest trap is one nobody writes on purpose. new URL(badUrl) throws a TypeError whose input property holds the full URL, password included. The pg driver knows about this and replaces it with *****REDACTED*****, but your own new URL(process.env.DATABASE_URL) gets no such protection. If you wrap that error with { cause: err } you carry the secret along with it.

You can't review your way out of this, so test it. A canary test starts the real program with a random value in the secret and collects every sink it writes to. If the canary appears anywhere, raw, URL-encoded or base64, the test fails. The child gets an explicitly built environment, so the CI's own secrets don't reach it.

Part 4 — Rotation basics 🟢 Basicالجزء 4 — أساسيات الـ rotation

English

Rotate on three triggers: on a schedule (which limits how long a stolen secret stays useful and keeps the procedure rehearsed), when someone with access leaves, and on suspicion (you don't need proof of a leak to rotate). A secret you've never rotated is one you can't rotate safely, and you'll find that out during the incident.

The general method is the same everywhere: two valid at once. The verifier learns the new key first, then the signer moves, then the old key is retired once nothing signed with it can still arrive. Node lesson 28, part 5 runs this for JWKS with asymmetric keys, including the wrong order. It applies to anything with two ends: JWT signing keys through kid, webhook secrets where the receiver tries each active secret, and database users, which is Part 7.

The retirement date isn't arbitrary. It's now + the longest time an old credential can still legitimately arrive: token lifetime, webhook retry window, or cache TTL plus deployment time.

             before      window opens          window closes
verifier:    [A]         [B, A(retires T)]     [B]
signer:      A           B                     B
                         ^ verifier first      ^ T = now + longest token / retry / TTL
tokens signed with A:    still accepted        rejected
قبل التبديل الـ verifier عارف A بس والـ signer بيوقع بيه. عند فتح الـ window الـ verifier بيعرف B الأول ومعاه A بتاريخ انتهاء T، والـ signer بينقل لـ B. عند قفل الـ window الـ verifier بيعرف B بس. والتوكنات الموقعة بـ A مقبولة جوه الـ window ومرفوضة بعدها. و T بيتحسب من أطول توكن أو retry أو TTL.
import { createHmac, timingSafeEqual } from "node:crypto";
import { SignJWT, jwtVerify } from "jose";

type SigningKey = { id: string; secret: string; retiresAt?: number };

// الـ ring فيها مفتاحين في فترة التبديل، والمفتاح القديم له تاريخ انتهاء
class KeyRing {
  #keys: SigningKey[];
  #now: () => number;
  constructor(keys: SigningKey[], now: () => number) {
    this.#keys = keys;
    this.#now = now;
  }
  active(): SigningKey[] {
    return this.#keys.filter((k) => k.retiresAt === undefined || this.#now() < k.retiresAt);
  }
  byId(id: string | undefined): SigningKey | undefined {
    return this.active().find((k) => k.id === id);
  }
}

const hmac = (secret: string, body: string) => createHmac("sha256", secret).update(body).digest();

// الـ webhook مفيهوش kid، فبنجرب كل مفتاح active بمقارنة ثابتة الوقت
function verifyWebhook(ring: KeyRing, body: string, signature: Buffer): string | null {
  for (const key of ring.active()) {
    const expected = hmac(key.secret, body);
    if (signature.length === expected.length && timingSafeEqual(signature, expected)) return key.id;
  }
  return null;
}

// الـ JWT فيه kid في الـ header، فالـ verifier بيختار المفتاح الصح مرة واحدة
function verifyJwt(ring: KeyRing, token: string) {
  return jwtVerify(
    token,
    (header) => {
      const key = ring.byId(header.kid);
      if (!key) throw new Error(`unknown or retired kid: ${header.kid}`);
      return new TextEncoder().encode(key.secret);
    },
    { algorithms: ["HS256"], issuer: "orders-api" },
  ).then(
    (r) => `valid (kid=${r.protectedHeader.kid})`,
    (e: Error) => `rejected (${e.message})`,
  );
}

const signJwt = (key: SigningKey, orderId: string) =>
  new SignJWT({ orderId })
    .setProtectedHeader({ alg: "HS256", kid: key.id })
    .setIssuer("orders-api")
    .setExpirationTime("2h")
    .sign(new TextEncoder().encode(key.secret));

Part 5 — The leaked-secret drill 🟡 Intermediateالجزء 5 — تدريب الـ secret المسرّب

English

When a secret reaches a remote repository, assume it's stolen. Automated scanners watch public pushes, so the useful question is how fast you can make the key worthless. Rotate first, always. History cleanup comes later and is optional hygiene, because it can't reach forks, other people's clones, CI caches, or anything already scraped.

The script below proves it in a sandbox. It commits a fake key, clones the repo as a teammate would, rewrites history with git filter-branch, and then looks for the key in each place. Three results matter: the rewrite changes every commit hash, so everyone has to re-clone; the old objects remain reachable through refs/original and the reflog until you delete those and run gc; and the teammate's clone still has the key, even after a fetch.

After revoking, check for abuse in the provider's usage logs from the moment of the leak, not from when you noticed it. Handling the wider incident is lesson 22.

Not run here: git filter-repo is a separate tool and isn't installed It's the tool Git's own docs recommend over filter-branch, and for this job you'd give it a replacements file: git filter-repo --replace-text secrets.txt. The sandbox below uses git filter-branch because it ships with Git, and only on a repo created for this lab.

Part 6 — KMS and envelope encryption 🔴 Advancedالجزء 6 — الـ KMS والـ envelope encryption

English

System Design lesson 38, parts 3 and 4 build the DEK and KEK with a FakeKms, so the mechanism isn't repeated. This part adds three things that lesson doesn't cover: how rotation avoids re-encrypting your data, what your call pattern costs, and what the real SDK calls look like.

Key versions. AWS's docs say rotation changes only the key's current material, and that it has no effect on the data the key protects: it doesn't rotate your data keys and doesn't re-encrypt anything. The ciphertext records which material wrapped it, so Decrypt takes no version argument and old rows keep working. New data keys get wrapped with the new material. If policy requires moving old data keys onto the new material, ReEncrypt does it per wrapped DEK, inside KMS, and the plaintext DEK never reaches your app. Your data bytes don't change either way.

Encryption context is bound to the ciphertext, so passing a tenant ID means tenant A's wrapped key can't be unwrapped as tenant B. The bill depends mostly on three numbers you control: distinct DEKs, cache TTL and pod count, because each pod refreshes each DEK independently. Per AWS's pricing page (read 2026-11-09): $1 per key per month, plus $1 per month for each of the first two rotations with no further increase after that, a free tier of 20,000 requests a month, and $0.03 per 10,000 requests in AWS's own examples. Check the table for your region and key type. KMS also has per-second request quotas that vary by region, so a per-row pattern can throttle before it gets expensive.

import { DecryptCommand, GenerateDataKeyCommand, ReEncryptCommand, type KMSClient } from "@aws-sdk/client-kms";

export type SealedInvoice = {
  wrappedDek: Uint8Array;
  iv: Buffer;
  tag: Buffer;
  ciphertext: Buffer;
};

const contextFor = (tenantId: string) => ({ tenant: tenantId });

export async function sealInvoice(kms: KMSClient, keyId: string, tenantId: string, plaintext: string): Promise<SealedInvoice> {
  const res = await kms.send(
    new GenerateDataKeyCommand({ KeyId: keyId, KeySpec: "AES_256", EncryptionContext: contextFor(tenantId) }),
  );
  // الـ DEK بيستخدم مرة وبيتمسح، والـ wrapped بس هو اللي بيتخزن
  const dek = Buffer.from(res.Plaintext!);
  const iv = randomBytes(12);
  const cipher = createCipheriv("aes-256-gcm", dek, iv);
  cipher.setAAD(Buffer.from(tenantId));
  const ciphertext = Buffer.concat([cipher.update(plaintext, "utf8"), cipher.final()]);
  dek.fill(0);
  return { wrappedDek: res.CiphertextBlob!, iv, tag: cipher.getAuthTag(), ciphertext };
}

export async function openInvoice(kms: KMSClient, tenantId: string, s: SealedInvoice): Promise<string> {
  // الـ Decrypt مفيهوش key version: الـ ciphertext نفسه بيقول اتشفر بأنهي version
  const res = await kms.send(new DecryptCommand({ CiphertextBlob: s.wrappedDek, EncryptionContext: contextFor(tenantId) }));
  const dek = Buffer.from(res.Plaintext!);
  const decipher = createDecipheriv("aes-256-gcm", dek, s.iv);
  decipher.setAAD(Buffer.from(tenantId));
  decipher.setAuthTag(s.tag);
  const out = Buffer.concat([decipher.update(s.ciphertext), decipher.final()]).toString("utf8");
  dek.fill(0);
  return out;
}

// اللف من جديد بيغيّر الـ wrappedDek بس، والـ ciphertext بتاع الداتا ما بيتلمسش
export async function rewrapInvoice(kms: KMSClient, keyId: string, tenantId: string, s: SealedInvoice): Promise<SealedInvoice> {
  const res = await kms.send(
    new ReEncryptCommand({
      CiphertextBlob: s.wrappedDek,
      SourceEncryptionContext: contextFor(tenantId),
      DestinationKeyId: keyId,
      DestinationEncryptionContext: contextFor(tenantId),
    }),
  );
  return { ...s, wrappedDek: res.CiphertextBlob! };
}

الـ key versions. docs بتاعة AWS بتقول إن الـ rotation بتغيّر الـ current material بس، وملهاش تأثير على الداتا اللي المفتاح بيحميها: مش بتغيّر الـ data keys بتاعتك ومش بتعيد تشفير حاجة. الـ ciphertext نفسه بيسجل أنهي material لفّه، فـ Decrypt مفيهوش version argument والصفوف القديمة بتفضل شغالة. والـ data keys الجديدة بتتلف بالـ material الجديد. ولو الـ policy طالبة تنقل الـ DEKs القديمة، ReEncrypt بيعمل ده لكل wrapped DEK جوه الـ KMS، والـ DEK نفسه مابيوصلش للـ app كـ plaintext. وفي الحالتين الـ bytes بتاعة الداتا مابتتغيرش.

الـ encryption context مربوط بالـ ciphertext، فلو بعت الـ tenant ID، الـ wrapped key بتاع tenant A مايتفكش كـ tenant B.

الفاتورة بتعتمد أساسًا على 3 أرقام إنت متحكم فيها: عدد الـ DEKs المختلفة، والـ cache TTL، وعدد الـ pods، لأن كل pod بيجدد كل DEK لوحده. صفحة أسعار AWS (اتقرت 2026-11-09) بتقول: $1 للمفتاح في الشهر، و$1 في الشهر زيادة لكل واحدة من أول rotationين ومفيش زيادة بعد كده، و free tier بـ 20,000 request في الشهر، و$0.03 لكل 10,000 request في أمثلة AWS نفسها. راجع الجدول لمنطقتك ونوع المفتاح. وكمان الـ KMS عنده حدود requests في الثانية بتختلف حسب الـ region، فالنمط اللي بيعمل call لكل صف ممكن يتعمله throttle قبل ما يبقى غالي.

Trade-off: a longer DEK cache is cheaper and riskier A DEK in memory can be read from a heap dump or by a compromised dependency. Longer TTL means fewer KMS calls and a longer exposure if the process is compromised, so cap both the time and the number of uses, and keep the cache in one module that never logs its contents.

Part 7 — Rotation with no downtime 🔴 Advancedالجزء 7 — الـ rotation من غير downtime

English

Changing a database password in place has a hidden shape: existing connections stay authenticated, so nothing fails until something opens a new connection. That's the danger. The pool recycles, a pod restarts, autoscaling adds an instance, and 28P01 (invalid password) appears at a random later moment, disconnected from the change that caused it.

The fix is the same two-valid-at-once method, applied with two database users who hold the same privileges. Rotate the one the app is not using, then move the app to it. AWS calls this the alternating users strategy. The app side has its own trap: pg's pool.end() stops serving its waiting queue, so requests already queued for a connection are stranded until they time out. Reading pg-pool 3.14's source confirms it: while ending, _pulseQueue returns before it reaches the pending queue. The fix is to wait for waitingCount to reach zero before calling end().

The lab runs real Postgres 18 with scram-sha-256 and real roles, under autocannon load (30 connections, 5 seconds, a pool of 5). maxLifetimeSeconds: 1 forces constant reconnects so the failure window is visible inside a 5-second run, standing in for what a pool recycle, restart or scale-up would do later. Budget max_connections for both pools, since they coexist during the swap.

import pg from "pg";

export type DbCredentials = { user: string; password: string };
export type SwapMode = "naive-end" | "drain-then-end";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

export class RotatingPool {
  #current: pg.Pool;
  #connect: (c: DbCredentials) => pg.Pool;

  constructor(connect: (c: DbCredentials) => pg.Pool, first: DbCredentials) {
    this.#connect = connect;
    this.#current = connect(first);
  }

  query(text: string) {
    return this.#current.query(text);
  }

  async swap(next: DbCredentials, mode: SwapMode): Promise<void> {
    const fresh = this.#connect(next);
    // تأكد إن الـ credentials الجديدة شغالة قبل ما تحوّل أي traffic عليها
    await fresh.query("select 1");

    const old = this.#current;
    this.#current = fresh;

    // المهم: end لوحده بيسيب اللي واقفين في الـ queue من غير client خالص
    if (mode === "drain-then-end") {
      while (old.waitingCount > 0) await sleep(5);
    }
    await old.end();
  }

  end() {
    return this.#current.end();
  }
}

    } catch (err) {

      res.statusCode = 500;
      res.end("fail");
    }
  });

import {
  DescribeSecretCommand,
  GetRandomPasswordCommand,
  GetSecretValueCommand,
  PutSecretValueCommand,
  UpdateSecretVersionStageCommand,
  type SecretsManagerClient,
} from "@aws-sdk/client-secrets-manager";

export type RotationEvent = {
  SecretId: string;
  ClientRequestToken: string;
  Step: "createSecret" | "setSecret" | "testSecret" | "finishSecret";
};
type DbSecret = { username: string; password: string };
export type Db = {
  setPassword(admin: DbSecret, target: DbSecret): Promise<void>;
  canLogin(target: DbSecret): Promise<boolean>;
};

const USERS = ["orders_app_a", "orders_app_b"] as const;
const otherUser = (u: string) => (u === USERS[0] ? USERS[1] : USERS[0]);

export function makeHandler(sm: SecretsManagerClient, db: Db, admin: DbSecret) {
  const read = async (SecretId: string, stage: string): Promise<DbSecret> => {
    const r = await sm.send(new GetSecretValueCommand({ SecretId, VersionStage: stage }));
    return JSON.parse(r.SecretString!) as DbSecret;
  };

  return async function handler({ SecretId, ClientRequestToken, Step }: RotationEvent): Promise<void> {
    if (Step === "createSecret") {
      // الخطوة 1: نكتب النسخة الجديدة بالـ user التاني، والـ app لسه على القديم
      const current = await read(SecretId, "AWSCURRENT");
      const pw = await sm.send(new GetRandomPasswordCommand({ PasswordLength: 32, ExcludePunctuation: true }));
      await sm.send(
        new PutSecretValueCommand({
          SecretId,
          ClientRequestToken,
          SecretString: JSON.stringify({ username: otherUser(current.username), password: pw.RandomPassword }),
          VersionStages: ["AWSPENDING"],
        }),
      );
    } else if (Step === "setSecret") {
      // الخطوة 2: الـ DB نفسها بتاخد الـ password الجديد على الـ user اللي مش شغال
      await db.setPassword(admin, await read(SecretId, "AWSPENDING"));
    } else if (Step === "testSecret") {
      // الخطوة 3: لو الـ login فشل هنا الـ rotation بتقف والـ app مابيتأثرش
      if (!(await db.canLogin(await read(SecretId, "AWSPENDING")))) throw new Error("pending secret cannot log in");
    } else {
      // الخطوة 4: نقل الـ label، وده اللحظة الوحيدة اللي الـ app بيشوف فيها الجديد
      const meta = await sm.send(new DescribeSecretCommand({ SecretId }));
      const currentVersion = Object.entries(meta.VersionIdsToStages ?? {}).find(([, s]) => s.includes("AWSCURRENT"))?.[0];
      await sm.send(
        new UpdateSecretVersionStageCommand({
          SecretId,
          VersionStage: "AWSCURRENT",
          MoveToVersionId: ClientRequestToken,
          RemoveFromVersionId: currentVersion,
        }),
      );
    }
  };
}

Interview question "How do you rotate a database password with zero failed requests?" → Two users with identical grants. Rotate the idle user, verify it can log in, publish the secret, then have each instance open a new pool, health-check it, switch traffic, and drain the old pool before closing it. Keep the old password valid for longer than the secret cache TTL. Rotating a single user in place only looks safe until the next reconnect.

Cheat sheet · الخلاصة

  • A secret deleted in a later commit is still in history: stop it before the commit with a hook, and enforce it on the server.
  • Scanners find known shapes only, so add a pattern for your internal key format. --no-verify skips a local hook.
  • .env for local only. In production: a secrets manager, a platform identity, a TTL cache, one call per miss, stale on failure.
  • Secrets leak through error messages, crash dumps and logs. new URL() errors carry the full URL in err.input. Prove it with a canary test.
  • Rotate on a schedule, on departure, on suspicion. Two valid at once: verifier first, signer next, retire after the longest lifetime.
  • Leak: rotate and revoke first, audit from the push time, clean history last. It can't reach forks and clones.
  • KMS rotation changes the current material only. Ciphertext names its version, so data isn't re-encrypted; ReEncrypt moves DEKs when policy requires it.
  • KMS bill ≈ distinct DEKs × pods × refreshes per month. Check the live prices and per-second quotas.
  • DB rotation: two users, change the idle one, health-check, swap, then wait for waitingCount to hit 0 before end().
بالعامية
  • الـ secret اللي اتمسح في commit بعدين لسه في الـ history: امنعه قبل الـ commit بـ hook، وخلّي الإجبار على السيرفر.
  • الـ scanners بتلاقي الأشكال المعروفة بس، فضيف pattern للـ format الداخلي بتاعك. و--no-verify بيعدّي الـ hook المحلي.
  • .env للـ local بس. في production: secrets manager و platform identity و cache بـ TTL و call واحد لكل miss، وتكمل بالقيمة القديمة لو الـ refresh فشل.
  • الـ secrets بتتسرب من رسايل الـ errors والـ crash dumps والـ logs. errors بتاعة new URL() شايلة الـ URL كامل في err.input. وأثبت ده بـ canary test.
  • الـ rotation: على جدول، أو لما حد يمشي، أو عند الشك. اتنين شغالين: الـ verifier الأول، بعدين الـ signer، والتقاعد بعد أطول عمر.
  • التسريب: rotate و revoke الأول، وراجع الاستخدام من وقت الـ push، وتنضيف الـ history في الآخر، ومش بيوصل للـ forks والـ clones.
  • rotation الـ KMS بتغيّر الـ current material بس. الـ ciphertext بيحدد الـ version بتاعه، فالداتا مابتتشفرش تاني، وReEncrypt بينقل الـ DEKs لو الـ policy طالبة كده.
  • فاتورة الـ KMS تقريبًا = عدد الـ DEKs × عدد الـ pods × مرات التجديد في الشهر. وراجع الأسعار الحالية وحدود الـ requests في الثانية.
  • rotation الـ DB: 2 users، غيّر العاطل، health check، تبديل، وبعدين استنى waitingCount يوصل 0 قبل end().
