Why this matters · ليه ده مهم

English

Most outages start with a change someone shipped. How you ship decides how many users that change can hurt before anyone notices, and how long it takes to undo. A Senior is the person who can say, before the deploy, "if this goes wrong, we lose about this many requests and we are back in under a minute", and has tested that the way back works once the database has moved on. These are also standard interview questions: rolling vs canary, deploy vs release, and "how do you roll back a migration?"

بالعامية

معظم الـ outages بتبدأ بتغيير حد نزّله. وطريقة النزول هي اللي بتحدد التغيير ده هيأذي كام user قبل ما حد ياخد باله، وهياخد قد إيه عشان يترجع. السنيور هو اللي يقدر يقول قبل الـ deploy: "لو ده باظ، هنخسر تقريبًا كذا request وهنرجع في أقل من دقيقة"، ويكون جرّب إن طريق الرجوع شغال حتى بعد ما الـ database اتغيرت. والمواضيع دي أسئلة interview ثابتة: rolling ولا canary، الفرق بين deploy و release، و"إزاي تعمل rollback لـ migration؟"

Part 1 — Three strategies under load 🟡 Intermediateالجزء 1 — تلات استراتيجيات تحت الـ load

English

All three strategies replace v1 with v2 without downtime. They differ in two numbers: how much traffic the new version can hurt before you notice, and how fast you get back. The mechanics (hash-based slices, automated rollback rules, the blue/green pointer) are taught in 10 · Deployment safety. Here we put them under the same load with the same bad version and count the damage.

  • Rolling: replace pods a few at a time. It is the Kubernetes default and costs almost nothing extra, but old and new run side by side, so they must be compatible.
  • Blue/green: run a complete second environment, then move one pointer. Rollback is moving the pointer back. You pay for double capacity while both exist, and 100% of traffic hits the new version at once.
  • Canary: send a small slice to the new version, watch it, then grow (1% → 10% → 100%). It limits exposure, but needs traffic splitting and metrics good enough to judge a small slice.

The experiment: 3 replicas behind a proxy at a steady 300 requests per second for 9 seconds. v2 returns 500 on every order, while its readiness probe stays green. That is the worst case, because the platform sees a healthy pod. Every strategy gets the same alert: at least 5% errors over the last second, then 1 second of delay standing in for the alerting pipeline. Then we roll back.

Stand-in, not Kubernetes: real Node processes play the pods and a small proxy plays the load balancer. It does not capture image pulls, scheduling, real signals or a real metrics pipeline. Windows, loaded machine: timings are ≈.

import { fileURLToPath } from 'node:url';
import autocannon from 'autocannon';

const script = fileURLToPath(new URL('./pod.mjs', import.meta.url));
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const REPLICAS = 3;
// تأخير الـ alert مضغوط لثانية، في الحقيقة دقايق: scrape وevaluation وnotification
const DETECT_MS = 1000;
const RATE = 300;

// الـ router بيلعب دور الـ load balancer: نسبة weight للنسخة الجديدة والباقي للقديمة
function createRouter(bluePort, greenPort) {
  const st = { weight: 0, ok: 0, err: 0, lastBad: 0, samples: [] };
  let n = 0;
  const server = http.createServer((req, res) => {
    const green = st.weight > 0 && n++ % 100 < st.weight;
    const up = http.request({ host: '127.0.0.1', port: green ? greenPort() : bluePort(), path: req.url, method: req.method, headers: req.headers, agent: false }, (m) => {
      const bad = m.statusCode >= 500;
      if (bad) { st.err++; st.lastBad = Date.now(); } else st.ok++;
      st.samples.push({ t: Date.now(), green, bad });
      const { connection, ...headers } = m.headers;
      res.writeHead(m.statusCode, headers);
      m.pipe(res);
    });
    up.on('error', () => { st.err++; st.lastBad = Date.now(); res.writeHead(502).end(); });
    req.pipe(up);
  });
  return { st, server };
}

// نفس الـ alert لكل الاستراتيجيات: 5% أخطاء في آخر ثانية، وبعدها تأخير DETECT_MS
function alertOn(st, onlyGreen, min = 10) {
  let seen = 0;
  return () => {
    if (!seen) {
      const now = Date.now();
      const w = st.samples.filter((s) => s.t > now - 1000 && (!onlyGreen || s.green));
      if (w.length >= min && w.filter((s) => s.bad).length / w.length >= 0.05) seen = now;
    }
    return seen > 0 && Date.now() >= seen + DETECT_MS;
  };
}
const waitFor = async (fn) => { const end = Date.now() + 20_000; while (!fn()) { if (Date.now() > end) throw new Error('timeout'); await sleep(10); } };

// الـ rolling update: pod جديد، يستنى يبقى ready، يشيل قديم، ووقفة اختيارية بعد كل pod
async function rollingUpdate(c, version, env, { pauseMs = 0, abort = () => false } = {}) {
  let nextAt = 0;
  while (true) {
    if (abort()) return false;
    if (Date.now() < nextAt) { await sleep(10); continue; }
    const fresh = [...c.pods].filter((p) => p.version === version && !p.terminating);
    const old = [...c.pods].filter((p) => p.version !== version && !p.terminating);
    if (!old.length && fresh.filter((p) => p.ready).length === REPLICAS) return true;
    if (fresh.length < REPLICAS && fresh.length + old.length < REPLICAS + 1) { c.startPod(version, env); nextAt = Date.now() + pauseMs; continue; }
    if (old.length && [...c.pods].filter((p) => p.ready && !p.terminating).length - 1 >= REPLICAS) { await c.terminate(old[0]); continue; }
    await sleep(10);
  }
}

async function scenario(name, run) {
  const blue = createCluster({ script, probe: { periodMs: 40 } });
  const green = createCluster({ script, env: { BAD: '1' }, probe: { periodMs: 40 } });
  const bluePort = await blue.start(REPLICAS, 'v1');
  let greenPort = 0;
  const { st, server } = createRouter(() => bluePort, () => greenPort);
  await new Promise((r) => server.listen(0, '127.0.0.1', r));
  const load = autocannon({ url: `http://127.0.0.1:${server.address().port}/orders`, connections: 10, overallRate: RATE, duration: 9, timeout: 3 });
  await sleep(500);
  const fired = await run({ blue, st, startGreen: async (n) => { greenPort = await green.start(n, 'v2'); } });
  const res = await load;
  const total = st.ok + st.err;
  console.log(`${name.padEnd(30)} total=${total} failed=${String(st.err).padEnd(4)} (${(st.err / total * 100).toFixed(1)}%) last bad response ${Math.max(0, st.lastBad - fired)} ms after the rollback decision, socket errors=${res.errors}`);
  await blue.stop();
  await green.stop();
  server.closeAllConnections();
  server.close();
}

const scenarios = {
  'rolling, no pause': async ({ blue, st }) => {
    const alert = alertOn(st, false);
    await rollingUpdate(blue, 'v2', BAD, { abort: alert });
    await waitFor(alert);
    const fired = Date.now();
    await rollingUpdate(blue, 'v1', {});
    return fired;
  },
  'rolling, 1.5 s pause per pod': async ({ blue, st }) => {
    const alert = alertOn(st, false);
    await rollingUpdate(blue, 'v2', BAD, { pauseMs: 1500, abort: alert });
    await waitFor(alert);
    const fired = Date.now();
    await rollingUpdate(blue, 'v1', {});

    await startGreen(REPLICAS);

    await waitFor(alertOn(st, true));

بالعامية

التلات طرق بيبدّلوا v1 بـ v2 من غير downtime. الفرق في رقمين: النسخة الجديدة تقدر تأذي قد إيه قبل ما تاخد بالك، وترجع بسرعة قد إيه. الشرح التفصيلي للآلية (شرايح الـ hash، قواعد الـ rollback الأوتوماتيك، pointer الـ blue/green) موجود في 10 · Deployment safety. هنا بنحطهم تحت نفس الـ load ونفس النسخة البايظة ونعدّ الخسارة.

  • Rolling: بيبدّل pods قليلة قليلة. ده الـ default في Kubernetes وتكلفته تقريبًا صفر، بس القديم والجديد شغالين جنب بعض، فلازم يكونوا compatible.
  • Blue/green: environment كامل تاني، وبعدين تحرّك pointer واحد، والرجوع إنك ترجّع الـ pointer. بتدفع capacity الضعف طول ما الاتنين موجودين، و100% من الـ traffic بيخبط في الجديد مرة واحدة.
  • Canary: شريحة صغيرة تروح للجديد، تراقبها، وبعدين تكبّر (1% ثم 10% ثم 100%). بيقلل التعرّض، بس محتاج traffic splitting و metrics كويسة كفاية تحكم على شريحة صغيرة.

التجربة: 3 replicas ورا proxy بـ 300 request في الثانية لمدة 9 ثواني. الـ v2 بترجّع 500 على كل order، والـ readiness probe بتاعتها سليمة. ده أسوأ سيناريو لأن الـ platform شايفة pod سليم. كل استراتيجية ليها نفس الـ alert: 5% errors على الأقل في آخر ثانية، وبعدها ثانية تأخير بتمثل الـ alerting pipeline، وبعدين نرجع.

الرقم اللي يهمك من الجدول: الفشل تقريبًا = الـ rate × نسبة التعرّض × وقت الاكتشاف. الـ blue/green هنا: 300 × 100% × حوالي 1.1 ثانية = حوالي 330، والـ canary: 300 × 5% × حوالي 1.3 ثانية = حوالي 20.

فين هستخدمه في شغلي؟ إنت بتنزّل تعديل على POST /payments بـ 300 request في الثانية، والـ alert بتاعك بياخد 3 دقايق. بالحساب: blue/green يعرّض 100%، يعني 300 × 180 = 54,000 request فاشل، والـ canary 5% يعني 2,700. يبقى لو الـ endpoint حساس زي الفلوس، خد canary بـ router حقيقي؛ ولو خدمة داخلية بسيطة، rolling بـ minReadySeconds كفاية. والغلطة الشائعة: تفتكر إن الـ readiness probe هتمسك الـ bug، وهي بتسأل "الـ pod شغال؟" مش "الـ orders بتتعمل صح؟"

"إمتى تختار blue/green بدل canary؟" ← لما التغيير مش ينفع يشتغل جنب القديم مدة طويلة، ولما عايز رجوع لحظي لـ environment كامل، ولما تقدر تدفع capacity الضعف وقت الـ deploy. الـ canary أحسن لما عايز تحدد عدد الـ users اللي نسخة بايظة توصلهم، وعندك metrics لكل نسخة تحكم بيها.

Part 2 — Deploy isn't release 🟡 Intermediateالجزء 2 — الـ deploy مش هو الـ release

English

A deploy puts code on servers. A release exposes behaviour to users. A feature flag separates the two: bad code can be merged and running everywhere, and no user reaches it. Flag design and flag debt are covered in 09 · Flags as architecture and Rollout, kill switch, flag debt. Here we measure two things: the real size of a "5%" and how long a kill switch takes.

The flag buckets users with a hash, so the same user always lands in the same group. Three real processes poll a small flag service every 250 ms. With the flag off, the bug is in production and 0 of 10,000 users are affected. At 5%, 465 users failed: 4.65%, because hashing gives you close to 5%, not exactly 5%. The second pass hit the same 465 users, so the group is sticky. Turning the flag off stopped the errors within 141–238 ms, which is bounded by the poll interval. A redeploy cannot match that, because it has to replace pods.

Limits: a flag only guards the code path it wraps. It can't undo a schema change, a dependency upgrade or a bug in code that runs before the check.

// الكود الجديد متنشر على كل الـ replicas، بس مقفول ورا flag
import { createHash } from 'node:crypto';
import http from 'node:http';

type Flag = { rolloutBps: number }; // 500 يعني 5%
let flag: Flag = { rolloutBps: 0 };
const FLAG_URL = process.env.FLAG_URL!;
const POLL_MS = Number(process.env.POLL_MS ?? 250);

async function poll(): Promise<void> {
  try {
    flag = (await (await fetch(FLAG_URL)).json()) as Flag;
  } catch {
    // لو خدمة الـ flags وقعت، بنفضل على آخر قيمة عرفناها
  }
  setTimeout(poll, POLL_MS);
}

// نفس الـ user دايمًا في نفس الـ bucket: الـ 5% ثابتين مش عشوائيين
function bucket(userId: string): number {
  return createHash('sha256').update('new-checkout:' + userId).digest().readUInt32BE(0) % 10_000;
}

const server = http.createServer((req, res) => {
  const userId = new URL(req.url!, 'http://x').searchParams.get('user') ?? 'anon';
  const onNewFlow = bucket(userId) < flag.rolloutBps;
  // الـ bug موجود في الـ flow الجديد بس: أي حد داخل عليه بياخد 500
  res.writeHead(onNewFlow ? 500 : 200, { 'x-flow': onNewFlow ? 'new' : 'old' }).end();
});
await poll();
server.listen(0, '127.0.0.1', () => {
  const addr = server.address();
  if (addr && typeof addr === 'object') process.send?.({ port: addr.port });
});

بالعامية

Part 3 — The rollback plan 🟡 Intermediateالجزء 3 — خطة الرجوع

English

A rollback has two halves. The code half is easy if the previous image still exists: keep images tagged by git SHA (see 27 · Registry), never overwrite a tag, and the old version comes back as fast as a process can start. On this machine that was ≈128 ms for one Node process. On a cluster, add the image pull and readiness time.

The data half is where rollbacks die. Code rolls back in seconds, but a schema does not. The rule from 07 · Expand/contract is that the old version must keep working on the new schema. The run below uses real Postgres and separate v1, v2 and v3 processes:

  • After expand (add a nullable column, drop NOT NULL on the old one), v1 keeps working and rolling back is safe.
  • While v1 runs again it writes rows with NULL in the new column. That is why v2 reads with COALESCE, and why you backfill again before moving on.
  • After contract (DROP COLUMN total), v1 fails on every write with 42703. The old image is intact, and it is useless.

So the contract step is the point of no return. Do it in a later deploy, after the new version has been stable long enough that you will not want to go back.

My first run of this script failed at step 6: v3 stopped writing total, but the column was still NOT NULL, so every insert failed with 23502. Relaxing the old column belongs in the expand phase.

Part 4 — Migrations as their own step 🟡 Intermediateالجزء 4 — الـ migrations كخطوة منفصلة

English

Running migrations when the app boots looks convenient. With 3 replicas it means 3 processes running the same migration at the same moment, and every restart re-enters that code. The right shape is one runner, one step, before the deploy: a CI step or a Kubernetes Job (see 32 · Jobs). If it fails, the deploy doesn't start.

The race is real. Three processes started together on Postgres 18, with the usual check-then-run code. Across 3 runs the outcome wasn't stable: two runs left loyalty_points at 20 instead of 10, because two processes both decided the migration hadn't run. One run happened to get 10. And replicas crashed with duplicate key value violates unique constraint "pg_type_typname_nsp_index": CREATE TABLE IF NOT EXISTS is not safe when run concurrently. In production that crash is a restart loop.

The fix is a Postgres advisory lock taken before anything else, inside a transaction, with the check for "already applied" after it. My first version took the lock after CREATE TABLE IF NOT EXISTS and still crashed, so the order matters. pg_advisory_xact_lock is released automatically at commit or rollback, and it also works behind PgBouncer in transaction mode, where a session-level lock would not. With it, all 3 runs applied the migration exactly once.

// الـ migration runner: خطوة واحدة بتشتغل قبل الـ deploy
import pg from 'pg';

const MIGRATION_ID = '0042_loyalty_points';
const LOCK_KEY = 727_001;

// وضعين: unsafe زي ما بيتعمل غلط وقت الـ boot، وsafe بـ advisory lock
export async function migrate(url: string, mode: 'unsafe' | 'safe'): Promise<string> {
  const client = new pg.Client({ connectionString: url });
  await client.connect();
  try {
    if (mode === 'safe') {
      await client.query('BEGIN');
      // القفل لازم ييجي قبل أي DDL، وبيفضل ماسك لحد نهاية الـ transaction
      await client.query('SELECT pg_advisory_xact_lock($1)', [LOCK_KEY]);
    }
    await client.query('CREATE TABLE IF NOT EXISTS schema_migrations (id text PRIMARY KEY, applied_at timestamptz DEFAULT now())');
    const done = await client.query('SELECT 1 FROM schema_migrations WHERE id = $1', [MIGRATION_ID]);
    if (done.rowCount) {
      if (mode === 'safe') await client.query('COMMIT');
      return 'skipped';
    }
    // الـ migration نفسها: عمود جديد وتعديل ⁦data (⁩الجزء الخطر لو اتكرر)
    await client.query('ALTER TABLE orders ADD COLUMN IF NOT EXISTS loyalty_points int NOT NULL DEFAULT 0');
    await client.query('UPDATE orders SET loyalty_points = loyalty_points + 10');
    await client.query('INSERT INTO schema_migrations (id) VALUES ($1) ON CONFLICT DO NOTHING', [MIGRATION_ID]);
    if (mode === 'safe') await client.query('COMMIT');
    return 'applied';
  } catch (err) {
    if (mode === 'safe') await client.query('ROLLBACK').catch(() => {});
    throw err;
  } finally {
    await client.end();
  }
}

الحل: Postgres advisory lock يتاخد قبل أي حاجة تانية، جوه transaction، والـ check بتاع "اتعملت قبل كده" ييجي بعده. أول نسخة عندي خدت الـ lock بعد CREATE TABLE IF NOT EXISTS ولسه وقعت، فالترتيب مهم. الـ pg_advisory_xact_lock بيتساب لوحده مع الـ commit أو الـ rollback، وبيشتغل كمان ورا PgBouncer في transaction mode، اللي الـ session lock مش بينفع فيه. بيه، الـ 3 جولات نفذوا الـ migration مرة واحدة بالظبط.

فين هستخدمه في شغلي؟ في الـ pipeline بتاعك: خطوة npm run migrate بعد الـ build وقبل الـ helm upgrade، بـ credentials ليها صلاحية DDL، والتطبيق نفسه بصلاحية DML بس. كده لو الـ app اتخترق، مش هيقدر يمسح جدول. والغلطة الشائعة: تستخدم أداة بتاخد lock على مستوى الـ session من ورا PgBouncer في transaction mode، فالـ lock يتساب في connection تاني والحماية تختفي.

Part 5 — Trunk-based vs GitFlow 🟡 Intermediateالجزء 5 — الـ Trunk-based ولا GitFlow

English

The branching models themselves are in 01 · Branching strategies. This part measures why long-lived branches cost more. A sandbox git repo runs the same edit schedule twice: 3 developers, 10 days, 2 edits a day each, on a shared file of 30 pricing rules. In one run each developer works on a 10-day branch and merges at the end. In the other, everyone merges daily.

Across 3 seeds, long-lived branches produced 16–19 conflict hunks, with up to 12 in a single merge. Daily merges produced 0–6, and never more than 2 in one merge. The absolute numbers come from a model with uniformly random edits, so trust the ratio and the shape. The total matters less than the batch: a 12-conflict merge of 10-day-old work is a bad afternoon, while one conflict in code you wrote this morning is a minute.

DORA's trunk-based development capability lists what its research found: "Have three or fewer active branches", branches that "typically last no more than a few hours", and "Don't have code freezes and don't have integration phases". It reports that DORA data from 2016 and 2017 shows teams doing this achieve higher delivery speed, stability and availability. That page does not discuss feature flags. Flags are the standard way to merge unfinished work without releasing it, and that is the reason flags belong in this same conversation.

Trunk-based needs fast CI, tests you trust and flags. GitFlow still fits software you ship in versions: mobile apps waiting on store review, on-premise products, or several supported releases at once.

import { execFileSync } from 'node:child_process';
import { existsSync, mkdirSync, readFileSync, rmSync, writeFileSync } from 'node:fs';
import path from 'node:path';
import { fileURLToPath } from 'node:url';

const here = path.dirname(fileURLToPath(import.meta.url));
const norm = (p) => path.resolve(p).replaceAll('\\', '/').toLowerCase();

function git(repo, ...args) {
  return execFileSync('git', ['-C', repo, '-c', 'user.name=lesson', '-c', 'user.email=lesson@example.invalid', '-c', 'core.autocrlf=false', ...args], {
    encoding: 'utf8',
    stdio: ['ignore', 'pipe', 'pipe'],
  });
}

function newRepo(name) {
  const repo = path.join(here, name);
  if (existsSync(repo)) rmSync(repo, { recursive: true, force: true });
  mkdirSync(repo);
  git(repo, 'init', '-b', 'main');
  // نتأكد إن الأوامر بتشتغل في الـ sandbox ده بس
  if (norm(git(repo, 'rev-parse', '--show-toplevel').trim()) !== norm(repo)) throw new Error('not the sandbox repo');
  return repo;
}

// ملف pricing فيه 30 rule، وكل rule بلوك منفصل
const RULES = 30;
const FILE = 'pricing.ts';
const initial = Array.from({ length: RULES }, (_, i) => `export const rule${i} = {\n  rate: 0,\n  flag: 'pricing-v2',\n};\n`).join('\n');

function applyEdit(repo, rule, value) {
  const f = path.join(repo, FILE);
  const re = new RegExp(`(export const rule${rule} = \\{\\n  rate: )[^,]+,`);
  writeFileSync(f, readFileSync(f, 'utf8').replaceAll('\r\n', '\n').replace(re, `$1${value},`));
}

function commitAll(repo, msg) {
  git(repo, 'add', FILE);
  git(repo, 'commit', '-q', '-m', msg);
}

// مولّد أرقام بـ seed: الجدول نفسه في الطريقتين
function schedule(seed, days, devs, perDay) {
  let s = seed;
  const rnd = () => ((s = (s * 1664525 + 1013904223) >>> 0) / 2 ** 32);
  return Array.from({ length: days }, () =>
    Array.from({ length: devs }, () => {
      const picked = new Set();
      while (picked.size < perDay) picked.add(Math.floor(rnd() * RULES));
      return [...picked];
    }),
  );
}

// الـ merge: لو فيه conflict بنعدّ الـ hunks وبنحلّها بأخد الجانب الجاي
function merge(repo, branch) {
  try {
    git(repo, 'merge', '--no-ff', '-q', '-m', `merge ${branch}`, branch);
    return 0;
  } catch {
    const f = path.join(repo, FILE);
    const text = readFileSync(f, 'utf8');
    const hunks = (text.match(/^<<<<<<< /gm) ?? []).length;
    writeFileSync(f, text.replace(/^<<<<<<< .*\n[\s\S]*?^=======\n([\s\S]*?)^>>>>>>> .*\n/gm, '$1'));
    git(repo, 'add', FILE);
    git(repo, 'commit', '-q', '-m', `merge ${branch} (resolved)`);
    return hunks;
  }
}

function report(mode, conflictsPerMerge, oldestDays) {
  const total = conflictsPerMerge.reduce((a, b) => a + b, 0);
  console.log(`${mode.padEnd(26)} merges=${String(conflictsPerMerge.length).padEnd(3)} conflict hunks=${String(total).padEnd(3)} worst single merge=${String(Math.max(...conflictsPerMerge)).padEnd(3)} code unmerged for up to ${oldestDays} days`);
}

const DAYS = 10;
const DEVS = 3;

function longLived(seed) {
  const repo = newRepo('sandbox-long');
  writeFileSync(path.join(repo, FILE), initial);
  commitAll(repo, 'initial');
  const plan = schedule(seed, DAYS, DEVS, 2);
  for (let dev = 0; dev < DEVS; dev++) {
    git(repo, 'switch', '-q', '-c', `feature/dev${dev}`, 'main');
    for (let day = 0; day < DAYS; day++) {
      plan[day][dev].forEach((rule, i) => applyEdit(repo, rule, 100 * day + 10 * dev + i));
      commitAll(repo, `dev${dev} day${day}`);
    }
  }
  git(repo, 'switch', '-q', 'main');
  // كل الشغل بيتدمج مرة واحدة في آخر الـ 10 أيام
  report('long-lived branches', Array.from({ length: DEVS }, (_, dev) => merge(repo, `feature/dev${dev}`)), DAYS);
}

function trunk(seed, branchDays) {
  const repo = newRepo('sandbox-trunk');
  writeFileSync(path.join(repo, FILE), initial);
  commitAll(repo, 'initial');
  const plan = schedule(seed, DAYS, DEVS, 2);
  const conflicts = [];
  for (let day = 0; day < DAYS; day += branchDays) {
    // كل واحد بيفتح branch من نفس الـ main، ويدمجه بعد branchDays يوم
    const base = git(repo, 'rev-parse', 'HEAD').trim();
    for (let dev = 0; dev < DEVS; dev++) {
      git(repo, 'switch', '-q', '-c', `b${day}/dev${dev}`, base);
      for (let d = day; d < Math.min(day + branchDays, DAYS); d++) {
        plan[d][dev].forEach((rule, i) => applyEdit(repo, rule, 100 * d + 10 * dev + i));
        commitAll(repo, `dev${dev} day${d}`);
      }
    }
    git(repo, 'switch', '-q', 'main');
    for (let dev = 0; dev < DEVS; dev++) conflicts.push(merge(repo, `b${day}/dev${dev}`));
  }
  report(`merge every ${branchDays} day(s)`, conflicts, branchDays);
}

Part 6 — GitOps 🟡 Intermediateالجزء 6 — الـ GitOps

English

GitOps means the desired state of your deployment lives in git, and an agent inside the cluster continuously makes reality match it. The usual push model has CI run kubectl apply, so CI holds cluster credentials and nothing notices later drift. In the pull model, the agent (Argo CD or Flux) reads the repo and applies changes, so the cluster's credentials never leave the cluster. IaC basics are in 10 · Infrastructure as code.

The stand-in below is a reconcile loop. Desired state is a JSON file in a sandbox git repo, live state is running processes. It does three things a real controller does: applies a commit, corrects a manual change, and treats git revert as the rollback. Every step left history in git.

From the official docs: Argo CD's automated sync doesn't delete resources or undo live changes unless you set prune: true and selfHeal: true. Its default polling is 120 s plus up to 60 s of jitter, and "Rollback cannot be performed against an application with automated sync enabled", so under auto-sync git revert really is how you roll back. Flux's Kustomization requires interval (minimum 60 s), sourceRef and prune.

What it costs you: secrets can't sit in git in plain text, so you need External Secrets or sealed secrets. CI now has to commit new image tags to the config repo. And anything that legitimately changes live state fights the agent: if an HPA scales your Deployment and the manifest pins replicas, self-heal keeps undoing it. The stand-in deleted an extra pod in exactly that way, so don't set replicas on anything an HPA manages.

Stand-in, not Argo CD or Flux: a Node loop reads a sandbox git repo and manages real processes. It does not capture Kubernetes objects, health assessment, sync waves or multi-cluster.

let lastRevision = '';
async function reconcileOnce() {
  const revision = git('rev-parse', '--short', 'HEAD').trim();
  const want = JSON.parse(git('show', `HEAD:${FILE}`));
  if (revision !== lastRevision) {
    log(`git HEAD ${revision} wants ${want.version} x${want.replicas}; live: ${summary()}`);
    lastRevision = revision;
  }
  const pods = live();
  const wrong = pods.filter((p) => p.version !== want.version);
  const right = pods.filter((p) => p.version === want.version);
  if (right.length < want.replicas) {
    if (wrong.length || right.length) log(`create ${want.version} (have ${right.length}/${want.replicas})`);
    cluster.startPod(want.version);
    await cluster.waitReady(right.length + 1, want.version);
    return true;
  }
  if (wrong.length) {
    log(`delete drifted pod ${wrong[0].name} (${wrong[0].version})`);
    await cluster.terminate(wrong[0]);
    return true;
  }
  if (right.length > want.replicas) {
    log(`delete extra pod ${right.at(-1).name}`);
    await cluster.terminate(right.at(-1));
    return true;
  }
  return false;
}

بالعامية

الـ GitOps معناه إن الـ desired state بتاع الـ deployment متسجل في git، و agent جوه الـ cluster بيخلي الواقع يطابقه باستمرار. في الـ push model العادي، الـ CI بيشغّل kubectl apply، فالـ CI ماسك credentials الـ cluster، ومفيش حد بياخد باله من الـ drift بعدها. في الـ pull model، الـ agent (Argo CD أو Flux) بيقرا الـ repo ويطبّق، فالـ credentials مبتخرجش من الـ cluster. أساسيات الـ IaC في 10 · Infrastructure as code.

الـ stand-in فوق عبارة عن reconcile loop: الـ desired state ملف JSON في repo git sandbox، والـ live state processes شغالة. بيعمل 3 حاجات الـ controller الحقيقي بيعملها: يطبّق commit، يصلّح تغيير يدوي، ويعتبر git revert هو الـ rollback. وكل خطوة سابت history في git.

من الـ docs الرسمية: الـ automated sync في Argo CD مش بيمسح resources ومش بيرجّع تغييرات الـ live إلا لو حطيت prune: true وselfHeal: true. الـ polling الافتراضي 120 ثانية وعليها لحد 60 ثانية jitter، ومكتوب نصًا إن "Rollback cannot be performed against an application with automated sync enabled"، يعني مع الـ auto-sync الـ git revert هو فعلًا طريق الرجوع. والـ Kustomization في Flux لازم فيها interval (أقل حاجة 60 ثانية) وsourceRef وprune.

التكلفة: الـ secrets متنفعش تبقى في git كـ plain text، فمحتاج External Secrets أو sealed secrets. والـ CI بقى لازم يعمل commit للـ image tags الجديدة في الـ config repo. وأي حاجة بتغيّر الـ live بشكل مشروع هتتخانق مع الـ agent: لو HPA بيعمل scale لـ Deployment والـ manifest مثبّت replicas، الـ self-heal هيفضل يلغي شغله. الـ stand-in مسح pod زيادة بنفس الطريقة بالظبط، فمتحطش replicas على أي حاجة الـ HPA بيديرها.

فين هستخدمه في شغلي؟ فريق عنده 12 service و3 environments، ومحدش عارف إيه اللي شغال فين: كل واحد بيعمل kubectl edit. مع GitOps، repo واحد فيه الـ prod state، و"مين غيّر الـ replicas ليه" بقت git log، والـ rollback بقى git revert يتراجع في PR. والغلطة الشائعة: تفعّل selfHeal وتسيب واحد يعمل hotfix بـ kubectl وقت حادثة، فالـ agent يمسح الـ hotfix بعد دقيقتين وهو فاكر إنه صلّح. الـ hotfix لازم يبقى commit.
Interview question "What problem does GitOps solve that a CD pipeline doesn't?" → A pipeline runs once and stops, so nobody corrects what changes afterwards. GitOps keeps reconciling, so drift gets fixed or at least reported, git becomes the audit log, and the cluster credentials stay inside the cluster.
"الـ GitOps بيحل إيه الـ CD pipeline مش بيحله؟" ← الـ pipeline بتشتغل مرة وتقف، فمحدش بيصلّح اللي بيتغير بعدها. الـ GitOps بيفضل يعمل reconcile، فالـ drift بيتصلّح أو على الأقل بيتبلغ عنه، والـ git بيبقى الـ audit log، والـ credentials بتاعت الـ cluster بتفضل جواه.

Common mistakes · غلطات شائعة

❌ Migrate when the app boots 
// كل replica بتشغّل الـ migration
await runMigrations();
app.listen(3000);
✅ One runner, before the deploy 
# خطوة منفصلة، ولو فشلت الـ deploy ميبدأش
node dist/migrate.js
helm upgrade --install shop ./chart
بالعامية

❌ كل replica بيشغّل الـ migration وقت الـ boot، فاتنين منهم ممكن ينفذوها مع بعض والـ data تتكرر (زي الـ 20 بدل 10 في الجزء 4)، والفشل بيبقى crash loop. ✅ خطوة واحدة قبل الـ deploy بـ runner واحد وبـ advisory lock، ولو فشلت الـ deploy ميبدأش أصلًا.

❌ Deploying :latest 
# الـ rollback لـ إيه؟ الـ tag اتكتب عليه خلاص
image: ghcr.io/acme/orders-api:latest
✅ An immutable tag per commit 
# كل نسخة ليها tag، والرجوع يعني الـ SHA اللي قبله
image: ghcr.io/acme/orders-api:sha-4f2a9c1
بالعامية

❌ :latest tag بيتكتب فوقه كل مرة، فـ"النسخة اللي قبلها" مبقتش موجودة بالاسم، ومتعرفش كل pod شغال إيه. ✅ tag بـ git SHA ثابت: الرجوع يعني ترجّع الـ SHA اللي قبله، والـ image لسه موجودة، ولو خليت retention policy تحتفظ بآخر النسخ.

❌ Cutover and contract in one release 
-- نفس الـ deploy: الكود الجديد ومسح القديم
ALTER TABLE orders DROP COLUMN total;
✅ Contract in a later deploy 
-- الأول: عمود جديد nullable، والقديم يفضل
ALTER TABLE orders ADD COLUMN total_cents bigint;
-- وبعد ما النسخة الجديدة تثبت أيام، في deploy تاني:
-- ALTER TABLE orders DROP COLUMN total;
بالعامية

❌ لو مسحت العمود القديم في نفس الـ release، أي مشكلة في الكود الجديد ملهاش رجوع، وv1 هتفشل بـ 42703 زي ما شفنا. ✅ الـ expand الأول، والـ DROP في deploy منفصل بعد ما النسخة الجديدة تثبت.

❌ A "canary" made of replica counts 
# نسخة Deployment تانية بـ pod واحد جنب 3 قديمة
# النتيجة 25% من الـ traffic مش 5%
replicas: 1
✅ Weights set in a router 
# الـ HTTPRoute بيحدد النسبة بصرف النظر عن عدد الـ pods
backendRefs:
  - name: orders-api-v1
    port: 80
    weight: 95
  - name: orders-api-v2
    port: 80
    weight: 5
بالعامية

❌ لو بتعمل canary بعدد الـ pods، pod جديد جنب 3 قدام معناه 25% من الـ traffic، مش 5%، فبتعرّض ناس أكتر من اللي فاكره. ✅ النسبة تتحدد في الـ router (Gateway أو mesh) بالـ weight، فـ 5% تبقى 5% مهما كان عدد الـ pods.

❌ Hotfix with kubectl under selfHeal 
# شغالة دقيقتين، وبعدين الـ agent بيمسحها
kubectl set image deploy/orders-api api=ghcr.io/acme/orders-api:hotfix
✅ Hotfix is a commit 
# الـ git هو الحقيقة، حتى وقت الحادثة
git revert HEAD
git push origin main
بالعامية

❌ لو غيّرت حاجة بـ kubectl والـ selfHeal شغال، الـ agent هيرجّعها زي ما مسح الـ v2-hotfix في التجربة، وإنت فاكر إن المشكلة اتحلت. ✅ حتى الـ hotfix يبقى commit أو git revert، ويتطبق من الـ repo.

Solution · الحل 
// تمرين: migration بتستنى lock على جدول مشغول، ومعاها lock_timeout
import pg from 'pg';
import { startPg } from './pg-throwaway.mjs';
import { assertPort } from './port-guard.mjs';

const db = await startPg();
assertPort(db.port);
const longTx = new pg.Client({ connectionString: db.url });
const migrator = new pg.Client({ connectionString: db.url });
await longTx.connect();
await migrator.connect();
await longTx.query('CREATE TABLE orders (id serial PRIMARY KEY, total numeric(10,2))');

// فيه transaction طويلة ماسكة الجدول، زي report شغال أو request عالق
await longTx.query('BEGIN');
await longTx.query('SELECT * FROM orders');

const t0 = performance.now();
try {
  await migrator.query('BEGIN');
  await migrator.query("SET LOCAL lock_timeout = '500ms'");
  await migrator.query('ALTER TABLE orders ADD COLUMN status text');
  await migrator.query('COMMIT');
  console.log('applied');
} catch (e) {
  await migrator.query('ROLLBACK');
  console.log(`${e.code} ${e.message} after ≈${Math.round(performance.now() - t0)} ms`);
}
await longTx.query('COMMIT');
await longTx.end();
await migrator.end();
await db.stop();
process.exit(0);

Cheat sheet · الخلاصة

  • Failed requests ≈ rate × exposure × detection time. Measured here at 300 req/s: rolling ≈15%, paused rolling ≈3.3%, blue/green ≈12%, canary 5% ≈0.7%.
  • Readiness probes don't catch logic bugs: alert on error rate per version.
  • Blue/green costs double capacity and switches back instantly. Canary needs a router, because replica counts only approximate a weight.
  • Deploy puts code on servers; release exposes it. A flag reverses in under one poll (≈141–238 ms at a 250 ms poll), and only guards the path it wraps.
  • A 5% hash bucket is about 5%, and sticky: here 465 of 10,000 users.
  • Tag images by SHA and keep the previous ones. Rollback time is process start plus pull plus readiness.
  • Expand keeps rollback possible, and DROP COLUMN ends it (42703). Run contract in a later deploy.
  • Migrate in one step before deploying: BEGIN, pg_advisory_xact_lock first, then the check, then DDL. Add lock_timeout.
  • Shorter branches mean smaller conflicts: 16–19 hunks over 3 merges vs 0–6 over 30. DORA: ≤3 active branches, lifetime of hours, no code freezes.
  • GitOps: git is the desired state, an in-cluster agent reconciles, git revert is the rollback. Don't pin replicas under an HPA.
بالعامية
  • الـ failed requests تقريبًا = الـ rate × التعرّض × وقت الاكتشاف. متقاس هنا على 300 request في الثانية: rolling حوالي 15%، rolling بوقفة حوالي 3.3%، blue/green حوالي 12%، canary 5% حوالي 0.7%.
  • الـ readiness probes مش بتمسك الـ logic bugs: اعمل alert على الـ error rate لكل نسخة.
  • الـ blue/green تكلفته الضعف والرجوع لحظي. الـ canary محتاج router، لأن عدد الـ replicas تقريب للـ weight بس.
  • الـ deploy بيوصّل الكود، والـ release بيوريه للـ users. الـ flag بيرجع في أقل من دورة poll (حوالي 141–238 ms عند poll كل 250 ms)، وبيحمي الـ path اللي حواليه بس.
  • شريحة hash بـ 5% هي تقريبًا 5% وثابتة: هنا 465 من 10,000 user.
  • سمّي الـ images بالـ SHA واحتفظ باللي قبلها. وقت الرجوع = قومة الـ process + الـ pull + الـ readiness.
  • الـ expand بيخلّي الرجوع ممكن، وDROP COLUMN بينهيه (42703). اعمل الـ contract في deploy لاحق.
  • الـ migrate في خطوة واحدة قبل الـ deploy: BEGIN، وpg_advisory_xact_lock الأول، بعدين الـ check، بعدين الـ DDL. وضيف lock_timeout.
