Why this matters · ليه ده مهم

English

A slow pipeline taxes every commit by every engineer, and it changes behaviour: people batch changes, skip tests locally and merge on Friday to avoid waiting. Speed work also goes wrong in expensive ways. A cache can serve a stale build, an affected-only run can skip the one test that mattered, and a path filter can block every merge. Senior engineers measure first, spend effort on the critical path, and know what each optimisation can break.

بالعامية

الـ pipeline البطيء ضريبة على كل commit من كل مهندس، وكمان بيغيّر السلوك: الناس بتجمّع تغييرات كتير، وبتسيب الـ tests المحلية، وبتعمل merge يوم الخميس عشان متستناش. وشغل السرعة كمان بيغلط بطرق غالية: الـ cache ممكن يرجّع build قديم، والـ affected-only ممكن يسيب الـ test اللي كان مهم، والـ path filter ممكن يقفل كل الـ merges. السنيور بيقيس الأول، وبيحط مجهوده على الـ critical path، وعارف كل optimization ممكن تكسر إيه.

Part 1 — Where the time goes 🟡 Intermediateالجزء 1 — الوقت بيروح فين

English

Start from data. Lesson 29's runner wrote a real timeline.json. Two numbers come from it: the critical path, which is what a developer waits for, and the sum of job durations, which is what you pay for. They differ, and each optimisation moves one or the other. The script below prints the top jobs and then asks a what-if question: if I halve this job, how much does the pipeline actually shrink?

The result is the point of this part. Halving typecheck or scan saves nothing, because neither is on the critical path. Halving integration saves ≈5.4 s. A commonly used target is a 10-minute budget for PR feedback: long enough for real checks, short enough that people wait instead of switching tasks. The money calculation states its assumptions so you can replace them with your team's numbers.

// بيقرا الـ timeline الحقيقي من runner الدرس 29، وبيجيب أكبر 3 jobs والـ critical path
import { readFileSync } from "node:fs";
import { criticalPath } from "../l29/critical-path.mjs";

const NEEDS = {
  lint: [], typecheck: [], unit: [],
  build: ["lint", "typecheck", "unit"],
  integration: ["build"], scan: ["build"],
  e2e: ["integration", "scan"],
  staging: ["e2e"], smoke: ["staging"], production: ["smoke"],
};

const { jobs: timeline } = JSON.parse(readFileSync(process.argv[2], "utf8"));
const graph = (patch = {}) => Object.fromEntries(Object.entries(NEEDS).map(([n, needs]) => [n, { needs, ms: patch[n] ?? timeline[n].ms }]));

const sorted = Object.entries(timeline).sort((a, b) => b[1].ms - a[1].ms);
console.log("top 3 jobs by duration:");
sorted.slice(0, 3).forEach(([n, j]) => console.log(`  ${n.padEnd(12)} ${(j.ms / 1000).toFixed(1)}s`));

const base = criticalPath(graph());
console.log(`\ncritical path now: ${base.path.join(" -> ")} = ${(base.ms / 1000).toFixed(1)}s`);

// تجربة: لو نصّينا وقت job واحد، الـ pipeline هيوفّر قد إيه فعلًا؟
const whatIf = (job) => {
  const r = criticalPath(graph({ [job]: timeline[job].ms / 2 }));
  return `  halve ${job.padEnd(12)} -> ${(r.ms / 1000).toFixed(1)}s (saves ${((base.ms - r.ms) / 1000).toFixed(1)}s) via ${r.path.join(" -> ")}`;
};
console.log("\nwhat if we halve one job:");
for (const j of ["typecheck", "scan", "integration", "e2e"]) console.log(whatIf(j));

// حساب تكلفة الـ CI: كل الأرقام افتراضات مكتوبة صراحة، غيّرها بأرقام فريقك
const assume = {
  devs: 6,
  pushesPerDevPerDay: 8,
  workDays: 21,
  // مدد jobs واقعية لمشروع orders حقيقي بالدقايق، مش مدد الـ sandbox
  jobMinutes: { lint: 1.2, typecheck: 1.5, unit: 2.2, build: 2.5, integration: 4.1, scan: 3.2, e2e: 6.3 },
  criticalPathMin: 13.4,
  linuxPerMin: 0.006,
  loadedDevPerHour: 40,
  // نسبة وقت الانتظار اللي بتضيع فعلًا، الباقي بيروح في شغل تاني
  lostShare: 0.3,
};

const runs = assume.devs * assume.pushesPerDevPerDay * assume.workDays;
// التقريب لفوق: كل job بيتحسب بدقايق كاملة، فالـ jobs الصغيرة الكتير بتتحسب أغلى
const billedPerRun = Object.values(assume.jobMinutes).reduce((a, m) => a + Math.ceil(m), 0);
const exactPerRun = Object.values(assume.jobMinutes).reduce((a, m) => a + m, 0);
const minutes = billedPerRun * runs;
const ciBill = minutes * assume.linuxPerMin;
const lostHours = (runs * assume.criticalPathMin * assume.lostShare) / 60;
const waitCost = lostHours * assume.loadedDevPerHour;

console.log(`runs/month                 : ${runs}`);
console.log(`job minutes per run        : ${exactPerRun.toFixed(1)} exact, ${billedPerRun} billed after rounding up`);
console.log(`billed minutes/month       : ${minutes}`);
console.log(`CI bill/month (Linux 2c)   : $${ciBill.toFixed(0)}`);
console.log(`lost developer hours/month : ${lostHours.toFixed(0)}`);
console.log(`waiting cost/month         : $${waitCost.toFixed(0)}`);
console.log(`waiting / CI bill ratio    : ${(waitCost / ciBill).toFixed(0)}x`);

// لو نزّلنا الـ critical path لـ 9 دقايق بـ 3 shards للـ ⁦E2E (⁩دقايق أكتر شوية بس أسرع)
const afterMinutes = billedPerRun + 3;
const afterBill = afterMinutes * runs * assume.linuxPerMin;
const afterCost = ((runs * 9 * assume.lostShare) / 60) * assume.loadedDevPerHour;
console.log(`\nwith 3 E2E shards          : +${afterMinutes - billedPerRun} billed min/run, critical path 9 min`);
console.log(`CI bill then               : $${afterBill.toFixed(0)} (+$${(afterBill - ciBill).toFixed(0)})`);
console.log(`waiting cost then          : $${afterCost.toFixed(0)} (-$${(waitCost - afterCost).toFixed(0)})`);

بالعامية

ابدأ من الداتا. الـ runner بتاع الدرس 29 كتب timeline.json حقيقي، وبيطلع منه رقمين: الـ critical path وده اللي المطور بيستناه، ومجموع وقت الـ jobs وده اللي بتدفعه. الرقمين مختلفين، وكل optimization بتحرّك واحد منهم. السكريبت اللي فوق بيطبع أكبر الـ jobs، وبعدين بيسأل: لو نصّيت وقت الـ job ده، الـ pipeline هيقصر قد إيه فعلًا؟

النتيجة هي الفكرة كلها: نص وقت typecheck أو scan مبيوفّرش حاجة لأنهم مش على الـ critical path، ونص وقت integration بيوفّر ≈5.4 ثانية. الهدف الشائع هو ميزانية 10 دقايق لنتيجة الـ PR: وقت كفاية لفحوصات حقيقية، وقصير كفاية إن الناس تستنى بدل ما تفتح حاجة تانية. وحساب الفلوس كاتب افتراضاته عشان تبدّلها بأرقام فريقك.

فين هستخدمه في شغلي؟ لو المدير سأل "نستثمر في تسريع الـ CI؟"، خد مدد آخر 50 run من API بتاع GitHub واحسب الـ critical path وتكلفة الانتظار، وادّيله رقم بالدولار بدل "الـ CI بطيء". الغلطة الشائعة: تسرّع أكبر job من غير ما تتأكد إنه على الـ critical path، فتتعب ومفيش توفير.
Interview question "Your CI takes 25 minutes. Where do you start?" → Pull timings for recent runs, compute the critical path, and look at queue time separately. Optimise only jobs on that path, then re-measure because the path can shift to another job after each fix.
"الـ CI بتاعك بياخد 25 دقيقة. هتبدأ منين؟" ← هات timings الـ runs الأخيرة، احسب الـ critical path، وبص على وقت الطابور لوحده. سرّع الـ jobs اللي على الـ path ده بس، وبعدين قيس تاني لأن الـ path ممكن يتنقل لـ job تاني بعد كل تصليح.

Part 2 — Caching strategies 🟡 Intermediateالجزء 2 — استراتيجيات الـ caching

English

Four layers, each with its own key. Dependencies: setup-node with cache: npm stores ~/.npm keyed on the lockfile, and npm ci still rebuilds node_modules (lesson 28). Build output: .tsbuildinfo and .next/cache go in actions/cache with restore-keys, so a partial match still helps. Docker layers: cache-from and cache-to: type=gha,mode=max store BuildKit layers in the Actions cache (lesson 27 covers layers). Task cache: Turborepo hashes each task's inputs and restores the outputs.

Measure every layer. On 300 small generated files, TypeScript 7's cold compile (≈0.4 s) beat TypeScript 6's warm incremental build (≈0.7 s), and one-file changes were noisy on both. At that size tsbuildinfo isn't worth the moving parts; on a large project on the JS compiler it can be.

A task cache is only safe if its hash covers everything that affects the output. Turborepo's default strict env mode filters the environment, so a variable not listed in env doesn't reach the task at all: our build silently produced UNSET. With --env-mode=loose the variable reaches the task but stays out of the hash, so a production build restored the staging URL from cache and reported FULL TURBO. Declaring "env": ["API_URL"] fixes both. Use passThroughEnv for values that shouldn't change the hash, such as tokens. Turbo's daemon key is deprecated in 2.11 and prints a warning, so remove it from older configs.

A remote cache shares task output between runners and developers (TURBO_TOKEN, TURBO_TEAM). It's also a trust boundary: anyone who can write to it can place an artifact that later builds restore, so don't give write access to fork PRs, and consider signing with TURBO_REMOTE_CACHE_SIGNATURE_KEY.

Not run here: actions/cache, Docker Buildx and the Turborepo remote cache need GitHub or Docker. The workflow is checked by @action-validator/core with zero errors. The Turborepo and tsc results below are real runs.

بالعامية

عندك 4 طبقات وكل واحدة ليها مفتاح. الـ dependencies: setup-node مع cache: npm بيخزّن ~/.npm بمفتاح من الـ lockfile، و npm ci لسه بيبني node_modules (الدرس 28). ناتج الـ build: .tsbuildinfo و .next/cache في actions/cache مع restore-keys، فحتى التطابق الجزئي بيفيد. طبقات الـ Docker: cache-from و cache-to: type=gha,mode=max بيخزّنوا الـ BuildKit layers في cache بتاع Actions (الدرس 27 بيغطي الـ layers). Task cache: الـ Turborepo بيعمل hash لمدخلات كل task ويرجّع المخرجات.

قيس كل طبقة. على 300 ملف صغير متولّدين، الـ cold compile على TypeScript 7 (≈0.4 ثانية) كان أسرع من الـ warm incremental على TypeScript 6 (≈0.7 ثانية)، وتعديل ملف واحد طلع noisy في الاتنين. في الحجم ده tsbuildinfo ميستاهلش التعقيد، وفي مشروع كبير على الـ JS compiler ممكن يستاهل.

الـ task cache آمن بس لو الـ hash بيغطي كل حاجة بتأثر على الـ output. الـ strict الافتراضي في Turborepo بيفلتر الـ environment، فالمتغير اللي مش في env مبيوصلش للـ task خالص: الـ build بتاعنا طلّع UNSET من غير أي error. ومع --env-mode=loose المتغير بيوصل بس مش داخل في الـ hash، فبناء الـ production رجّع رابط staging من الـ cache وكتب FULL TURBO. لما تعلن "env": ["API_URL"] بتحل الاتنين. واستخدم passThroughEnv للقيم اللي المفروض متغيرش الـ hash زي الـ tokens. ومفتاح daemon بقى deprecated في 2.11 وبيطبع warning، فشيله من الـ configs القديمة.

الـ remote cache بيشارك مخرجات الـ tasks بين الـ runners والمطورين (TURBO_TOKEN و TURBO_TEAM). وده كمان حد ثقة: أي حد يقدر يكتب فيه يقدر يحط artifact الـ builds الجاية هترجّعه، فمتديش صلاحية كتابة لـ fork PRs، وفكّر في التوقيع بـ TURBO_REMOTE_CACHE_SIGNATURE_KEY.

فين هستخدمه في شغلي؟ لو الـ web app بتاع Next بياخد NEXT_PUBLIC_API_URL وقت الـ build وعندك staging و production، لازم المتغير يبقى في env بتاع task الـ build، وإلا هتنشر رابط غلط. الغلطة الشائعة: تشوف FULL TURBO وتفرح من غير ما تتأكد إن قيم الـ env كلها داخلة في الـ hash.
What breaks: poisoned or stale caches A cache key missing an input serves wrong output with no error, as the run above shows. Fix the key, and if a poisoned entry may exist, change the key prefix to invalidate everything.
مفتاح cache ناقص منه input بيرجّع output غلط من غير أي error، زي التشغيل اللي فوق. صلّح المفتاح، ولو ممكن يكون فيه entry متلوّث غيّر prefix المفتاح عشان تلغي كل القديم.

Part 3 — Affected-only builds 🟡 Intermediateالجزء 3 — تشغيل المتأثر بس

English

Monorepo basics are in 06 · lesson 19 and 04 · lesson 39. CI adds one question: which packages can this change affect? turbo run test --filter=...[origin/main] selects packages changed since origin/main and, through the ... prefix, everything that depends on them. A change to apps/web runs only web. A change to packages/pricing runs pricing, api and web. A change to a file in globalDependencies runs everything, and a file outside any package and outside that list runs nothing, which can be a gap.

The real trap is the checkout. On a pull request, actions/checkout fetches one merge commit and no origin/main. In that shape --filter=...[origin/main] failed outright, and --affected printed a warning and ran everything. Set fetch-depth: 0, or fetch the base branch, and pass TURBO_SCM_BASE explicitly. Nx has the same idea with nx affected -t test --base=origin/main --head=HEAD.

GitHub path filters have a sharper edge. If on.pull_request.paths skips a whole workflow, its required check stays Pending and blocks merging. A job skipped through if: reports Success instead. So filter at job level, and make one always-running ci-ok job the only required check.

Part 4 — Parallelism and sharding 🟡 Intermediateالجزء 4 — التوازي والـ sharding

English

Parallel jobs only help when they are on the critical path or you have idle runners. Sharding splits one test suite across machines: vitest run --shard=1/3 or playwright test --shard=1/3. Wall clock becomes the slowest shard, and the bill becomes the sum of all shards plus each one's setup. That setup is why a real speed-up lands below the ideal: 3 Vitest shards gave ≈2.3×, not 3×.

Vitest shards by file, so one heavy file sets the worst shard: our 12 files split unevenly at ≈2.2 s, 4.7 s and 4.6 s. Playwright with fullyParallel distributes individual tests, so its shards came out even. Both need a merge step, because a single report matters: each shard writes a blob report, and a final step combines them. Vitest 5's --merge-reports defaults to .vitest/blob and failed with ENOENT when we'd written to .vitest-reports, so pass the directory as --merge-reports=.vitest-reports. In Playwright, set PLAYWRIGHT_BLOB_OUTPUT_DIR per shard when they share a machine, then run playwright merge-reports.

Fail fast is a matrix default that cancels siblings on the first failure. It gives quick signal and saves minutes, but with shards you lose the rest of the report, so fail-fast: false is the usual choice there. Cancelling superseded runs is the same idea across pushes (lesson 29).

Part 5 — Preview environments 🟡 Intermediateالجزء 5 — بيئة preview لكل PR

English

A preview environment gives each pull request its own URL, so reviewers and E2E tests see the real change. On Vercel every push to a branch gets a preview deployment (06 · lesson 20); the part you must solve is the data, because previews sharing one database interfere with each other. On Kubernetes, the equivalent is an ephemeral namespace per PR. Either way the lifecycle has three steps: create on open or push, update on push, and destroy on close.

The stand-in below does the real data and process work: CREATE DATABASE pr_123 TEMPLATE orders_template clones a migrated, seeded database in ≈0.2 s, and each PR gets its own app process on its own port. TEMPLATE needs no open connections on the source, or it fails with 55006, which the run shows. Isolation is checked: an order on PR 101 doesn't appear on PR 102. Teardown uses DROP DATABASE ... WITH (FORCE).

The failure that costs money is the forgotten environment: a webhook gets lost, a close event fails, and a database keeps running. Treat teardown as unreliable and add a leak detector that compares what exists with what should exist, on a schedule, with a TTL as a backstop. Previews also need access control and fake data: a public URL with production data is a breach. PRs from forks get no secrets, so they can't deploy previews.

Stand-in: previews Real Postgres 18 and real app processes on local ports. No Vercel, Kubernetes, DNS or TLS. Clone timing is from a Postgres with fsync off on a loaded Windows machine, so read it as a rough size only.

  const env = registry.get(pr);
  env.app.kill();
  await once(env.app, "exit");
  // الـ FORCE بيقفل أي اتصال فاضل بدل ما الـ DROP يفشل
  await admin.query(`DROP DATABASE IF EXISTS ${env.db} WITH (FORCE)`);
  registry.delete(pr);
  console.log(`PR #${pr}: torn down, ${env.db} dropped`);
}

// كاشف التسريب: اللي موجود فعلًا مقارنة باللي المفروض يكون موجود
async function findLeaks(openPrs, ttlMs) {
  const { rows } = await admin.query("SELECT datname FROM pg_database WHERE datname LIKE 'pr\\_%'");
  const leaks = [];
  for (const { datname } of rows) {
    const pr = Number(datname.slice(3));
    const env = registry.get(pr);
    if (!openPrs.includes(pr)) leaks.push({ pr, datname, reason: "PR is closed but the environment still exists" });
    else if (env && Date.now() - env.openedAt > ttlMs) leaks.push({ pr, datname, reason: "older than the TTL" });
  }
  return leaks;
}

GitHub cut hosted-runner prices by up to 39% from 1 January 2026. On the official page as of 2026-11-09: Linux 2-core x64 is $0.006 per minute, arm64 $0.005, Windows $0.010, macOS $0.062, Linux 4-core $0.012 and 8-core $0.022. Included usage is now expressed as money, not minutes: $12 a month on Free, $18 on Pro and Team, $300 on Enterprise Cloud. Standard runners in public repositories are free.

A $0.002-per-minute charge on self-hosted runners was announced in December 2025 for March 2026 and then postponed within days. As of 2026-11-09 GitHub's billing page lists self-hosted runners as free and describes no charge. Postponed isn't cancelled, so check that page before you plan around it. Self-hosting still costs you the machines and the upkeep.

GitHub rounds each job up to a whole minute, so many tiny jobs cost more: ten 12-second jobs are 2 minutes of work and 10 billed. arm64 is the cheapest easy win. A bigger runner only pays off if the work actually parallelises, and on our assumptions the 4-core costs more than the 2-core while finishing faster. Spot and self-hosted runners come in lesson 48.

// بيوزّع الملفات على الـ shards: الأبطأ الأول على أخف shard، وده أقرب لأحسن توزيع
export function balance(files, shards) {
  const bins = Array.from({ length: shards }, () => ({ ms: 0, files: [] }));
  for (const f of [...files].sort((a, b) => b.ms - a.ms)) {
    const lightest = bins.reduce((a, b) => (b.ms < a.ms ? b : a));
    lightest.ms += f.ms;
    lightest.files.push(f.name);
  }
  return bins;
}

// بيدوّر على process.env.X في الكود، ويقول إيه اللي مش معلن في turbo.json
export function undeclaredEnv(source, declared) {
  const used = new Set([...source.matchAll(/process\.env\.([A-Z][A-Z0-9_]*)/g)].map((m) => m[1]));
  return [...used].filter((name) => !declared.includes(name)).sort();
}

  • --filter=...[origin/main] needs that ref; --affected without history runs everything.
  • Use fetch-depth: 0 and TURBO_SCM_BASE for affected-only runs on PRs, and keep a full run on main.
  • A skipped workflow leaves a required check Pending; a job skipped through if: reports Success. Use one ci-ok gate.
