Why this matters · ليه ده مهم

English

Most Node teams that run on Kubernetes don't operate the cluster, but they do own the YAML that describes their service. When a deploy fails at 2 a.m., the answer is usually in a selector, a quoted number, a missing secret or a CronJob that ran twice. This lesson gives you the objects behind one real API, then the two tools teams use to keep that YAML sane across environments.

بالعامية

معظم فرق Node اللي شغالة على Kubernetes مش بتدير الـ cluster، بس هي المسؤولة عن الـ YAML اللي بيوصف الـ service بتاعها. ولما deploy يقع الساعة 2 بالليل، الإجابة غالبًا في selector، أو رقم بين علامات تنصيص، أو secret ناقص، أو CronJob اشتغل مرتين. الدرس ده بيوريك الـ objects اللي ورا API حقيقي واحد، وبعدها الأداتين اللي الفرق بتستخدمهم عشان الـ YAML يفضل منظم عبر الـ environments.

Part 1 — The objects on one page 🟡 Intermediateالجزء 1 — الـ objects في صفحة واحدة

English

Kubernetes 1.37 is the current release, and 1.35–1.37 are the maintained versions. Every object is a desired-state record: you describe what should exist, and controllers work to make it true. For one API you need six kinds:

  • Pod: one or more containers scheduled together. The smallest unit, and disposable. You almost never create one directly.
  • Deployment: keeps N identical Pods running and replaces them gradually when the template changes.
  • Service: a stable name and virtual IP in front of whichever Pods match a label selector.
  • ConfigMap and Secret: configuration injected into Pods as environment variables or files.
  • Namespace: a scope for names, quotas and access rules.

A Secret is not encrypted by being a Secret. Its values are base64, which anyone can decode, and the Kubernetes docs warn that Secrets are "by default, stored unencrypted in the API server's underlying data store (etcd)", and that anyone who can create a Pod in a namespace can read the Secrets there. The docs' list of steps is: enable encryption at rest, restrict access with least-privilege RBAC, limit which containers get the Secret, and consider an external secret store.

You can check manifests without a cluster. kubernetes-models validates a manifest against the Kubernetes schemas. The run below shows what that catches, and what it can't: a misspelled field and a selector that doesn't match its template both pass. A schema knows field types. It doesn't know your intent, and it doesn't apply the API server's own cross-field rules.

Not run here: no cluster or kubectl on this machine. The manifest was validated with kubernetes-models 5.1 (real output below).

// بترجع سطر لكل object: اسمه ونوعه ومظبوط ولا لأ
export function validateYaml(text) {
  const results = [];
  for (const doc of parseAllDocuments(text)) {
    if (doc.errors.length) {
      results.push({ kind: '?', name: '?', status: 'YAML error', detail: doc.errors[0].message.split('\n')[0] });
      continue;
    }
    const obj = doc.toJS();
    if (!obj) continue;
    const Model = models[obj.kind];
    const row = { kind: obj.kind, name: obj.metadata?.name ?? '?' };
    if (!Model) { results.push({ ...row, status: 'not checked' }); continue; }
    try {
      new Model(obj).validate();
      results.push({ ...row, status: 'ok' });
    } catch (e) {
      results.push({ ...row, status: 'INVALID', detail: e.message.split('\n')[0] });
    }
  }
  return results;
}

بالعامية

الإصدار الحالي Kubernetes 1.37، والمدعوم 1.35 لـ 1.37. كل object عبارة عن وصف للحالة المطلوبة: إنت بتوصف المفروض يبقى إيه، والـ controllers بتشتغل عشان تخلي ده حقيقي. لـ API واحد محتاج 6 أنواع:

  • Pod: container أو أكتر بيتشغلوا مع بعض. أصغر وحدة، وبتترمي عادي. تقريبًا عمرك ما بتعمله بإيدك.
  • Deployment: بيخلي N Pods متطابقين شغالين، وبيبدّلهم بالتدريج لما الـ template يتغير.
  • Service: اسم ثابت و virtual IP قدام أي Pods بتطابق label selector.
  • ConfigMap و Secret: إعدادات بتدخل الـ Pods كـ environment variables أو ملفات.
  • Namespace: نطاق للأسماء والـ quotas وصلاحيات الوصول.

الـ Secret مش متشفر لمجرد إنه Secret. القيم base64، وأي حد يقدر يفكها، والـ docs بتحذر إن الـ Secrets "by default, stored unencrypted in the API server's underlying data store (etcd)"، وإن أي حد يقدر يعمل Pod في namespace يقدر يقرا الـ Secrets بتاعته. والخطوات اللي الـ docs بتقولها: فعّل encryption at rest، وقيّد الوصول بـ RBAC بأقل صلاحيات، وحدد أنهي containers تاخد الـ Secret، وفكر في external secret store.

تقدر تفحص الـ manifests من غير cluster. kubernetes-models بتتأكد من الـ manifest ضد schemas بتاعة Kubernetes. والتجربة فوق بتوريك بتمسك إيه ومش بتمسك إيه: غلطة إملائية في اسم field و selector مش مطابق الـ template عدّوا الاتنين. الـ schema بتعرف أنواع الـ fields، مش بتعرف قصدك، ومش بتطبّق القواعد اللي بتربط fields ببعض في الـ API server.

فين هستخدمه في شغلي؟ ضيف الـ validator ده في CI على كل PR بيعدّل k8s/: يمسك replicas: "3" وcontainerPort كـ string في ثواني، قبل ما حد يلمس cluster. والخطوة اللي بعدها في بيئة حقيقية: kubectl apply --dry-run=server عشان الـ API server يمسك الباقي، زي الـ selector. والغلطة الشائعة: تفتكر إن وجود الـ Secret في Kubernetes معناه إنه آمن، فتحطه في git بـ base64 وتفتكر إن الموضوع خلص.
A schema check passes things that will still fail, or silently misbehave replica: 3 isn't a known field, so this validator ignores it and the object is treated as having no replicas. A real API server reports unknown fields according to its validation setting, and kubectl apply uses strict validation by default. The selector mismatch is rejected only by the API server's own rules. Neither was run here, so use kubectl apply --dry-run=server in a real pipeline.
replica: 3 field مش معروف، فالـ validator ده بيتجاهله، والـ object بيتعامل كأنه من غير replicas. الـ API server الحقيقي بيبلّغ عن الـ fields المجهولة حسب إعداد الـ validation، وkubectl apply بيستخدم strict validation افتراضيًا. والـ selector المش مطابق بيترفض بقواعد الـ API server نفسه بس. الاتنين دول متشغلوش هنا، فاستخدم kubectl apply --dry-run=server في أي pipeline حقيقية.
Interview question "Is a Kubernetes Secret secure?" → Not by itself. It's base64 in the manifest, and by default unencrypted in etcd. It's a handle that lets you keep the value out of the image and control access. Real safety needs encryption at rest, tight RBAC, and usually an external secrets manager.
"الـ Kubernetes Secret آمن؟" ← مش لوحده. هو base64 في الـ manifest، ومش متشفر في etcd افتراضيًا. هو مجرد طريقة تخلّي القيمة بره الـ image وتتحكم في الوصول ليها. الأمان الحقيقي محتاج encryption at rest، و RBAC مضبوط، وغالبًا external secrets manager.

Part 2 — Services and routing 🟡 Intermediateالجزء 2 — الـ Services والـ routing

English

Pods come and go, and each one gets a new address. A Service gives clients one stable name, and Kubernetes keeps the list of matching Pod addresses up to date in EndpointSlices. The run below shows it: a client keeps talking to the same port through a full rollout while the pods behind it are replaced.

  • ClusterIP (the default): reachable only inside the cluster. Use it for service-to-service traffic.
  • NodePort: opens the same port on every node (30000–32767 by default). Rarely the right answer in production.
  • LoadBalancer: asks the cloud for an external load balancer. Simple, but one per Service gets expensive.

HTTP routing is where the README is out of date. It lists Ingress, and the Ingress API still exists, but the community ingress-nginx controller was retired: maintenance stopped in March 2026, with, per the Kubernetes announcement, "no further releases, no bugfixes, and no updates to resolve any security vulnerabilities". The same announcement says "Existing deployments of Ingress NGINX will not be broken", and recommends migrating to Gateway API or another controller.

Gateway API (v1.7 is current) splits the job in two. A Gateway is owned by the platform team and defines listeners and certificates. An HTTPRoute is owned by your team and lives in your namespace. That split is the practical improvement: you can change your routes without touching shared infrastructure. Ingress is shown too, because you will meet it in existing clusters.

Stand-in, not Kubernetes: real Node processes are the pods and a small proxy is the Service. It does not capture kube-proxy, cluster DNS or EndpointSlice propagation delay. The Gateway and Ingress files were validated by schema only and were not applied.

ده بديل تجريبي مش Kubernetes: عمليات Node حقيقية هي الـ pods و proxy صغير هو الـ Service. مش بيغطي kube-proxy ولا الـ cluster DNS ولا تأخير تحديث الـ EndpointSlices. وملفات الـ Gateway والـ Ingress اتفحصت بالـ schema بس ومتطبقتش.

const script = fileURLToPath(new URL('./pod.mjs', import.meta.url));

const get = (port) => new Promise((res) => {
  http.get({ host: '127.0.0.1', port, path: '/orders', agent: false }, (m) => {
    let b = '';
    m.on('data', (d) => (b += d));
    m.on('end', () => res({ status: m.statusCode, body: b }));
  }).on('error', () => res({ status: 0, body: '' }));
});

const cluster = createCluster({ script, probe: { periodMs: 40 } });

const podPorts = () => [...cluster.pods].filter((p) => p.inEndpoints).map((p) => p.port).sort();

  const seen = new Set();
  let failed = 0;
  for (let i = 0; i < 40; i++) {
    const r = await get(servicePort);
    if (r.status === 200) seen.add(r.body); else failed++;
  }
  console.log(`${label}\n  Service port ${servicePort}, pod ports [${podPorts().join(', ')}], served by [${[...seen].sort().join(', ')}], failed ${failed}/40`);

بالعامية

الـ Pods بتيجي وتمشي، وكل واحد بياخد عنوان جديد. الـ Service بتدي العملاء اسم ثابت واحد، و Kubernetes بيحدّث قايمة عناوين الـ Pods المطابقة في الـ EndpointSlices. والتجربة فوق بتوري ده: العميل فاضل بيكلم نفس الـ port طول الـ rollout والـ pods اللي وراه بتتبدل.

  • ClusterIP (الـ default): جوه الـ cluster بس. للـ traffic بين الـ services.
  • NodePort: بيفتح نفس الـ port على كل node (من 30000 لـ 32767 افتراضيًا). نادرًا ما بيبقى الاختيار الصح في production.
  • LoadBalancer: بيطلب load balancer خارجي من الـ cloud. سهل، بس واحد لكل Service بيبقى غالي.

الـ HTTP routing هو المكان اللي الـ README فيه قديم. هو مكتوب فيه Ingress، والـ Ingress API لسه موجود، بس الـ controller المجتمعي ingress-nginx اتقاعد: الصيانة وقفت في مارس 2026، وحسب إعلان Kubernetes "no further releases, no bugfixes, and no updates to resolve any security vulnerabilities". ونفس الإعلان بيقول "Existing deployments of Ingress NGINX will not be broken"، وبينصح تنقل لـ Gateway API أو controller تاني.

Part 3 — A Helm chart 🟡 Intermediateالجزء 3 — Helm chart

English

Plain manifests repeat themselves across dev, staging and prod. A Helm chart is a set of templates plus values, and rendering combines them. Values merge in order: values.yaml, then each -f file, then --set. Objects merge deeply and arrays are replaced whole.

Helm 4.3 is current. Helm 3 is at the end of its support, with security patches stopping on 2026-11-11. Helm 4 brings server-side apply by default for new releases and WebAssembly plugins, and v2 charts keep working unchanged. Per the Helm 4 overview, --atomic was renamed to --rollback-on-failure. Check helm upgrade --help on your own version, because older scripts may still use the old name.

Three template functions cause most of the pain, and the run below shows each one breaking for real:

  • Quoting: replicas: "{{ .Values.replicaCount }}" renders a string where Kubernetes needs an integer. Going the other way, an environment variable value must be a string, so value: {{ .Values.port }} needs | quote.
  • nindent: toYaml returns several lines, and only the first picks up the indentation in your template. nindent N starts a new line and indents every line. Without it, the structure breaks.
  • Secrets in values: anything in a values file ends up in git and in the rendered output. Reference an existing Secret by name instead, and let something else create it.

export function deepMerge(base, over) {
  const out = { ...base };
  for (const [k, v] of Object.entries(over ?? {})) {
    const isObj = (x) => x && typeof x === 'object' && !Array.isArray(x);
    out[k] = isObj(v) && isObj(out[k]) ? deepMerge(out[k], v) : v;

  return out;

Part 4 — Kustomize 🟡 Intermediateالجزء 4 — الـ Kustomize

English

Kustomize (5.8 is current) takes the opposite approach: no template language. You keep plain, valid YAML in a base, and each environment is an overlay that describes only its differences. It is also built into kubectl apply -k, though the embedded version can lag behind the standalone release.

The core of it is the strategic merge: your patch states the path to what you want to change, and lists of named items are merged by name rather than replaced. In the run below, the prod patch changed the LOG_LEVEL entry and the resources, and the ports list it never mentioned survived untouched. Compare that with Helm values, where an array replaces the whole array.

Dedicated transformers cover the common cases, so images sets a tag and replicas sets a count without a patch. The configMapGenerator feature, which the stand-in doesn't implement, appends a content hash to the ConfigMap's name, so changing the config rolls the Pods automatically.

Not run here: Kustomize and kubectl are not installed (the real command would be kustomize build overlays/prod). Stand-in: a small builder that handles resources, namespace, images, replicas and strategic-merge patches. It does not capture generators, hash suffixes, components or other transformers.

import { readFileSync } from 'node:fs';
import path from 'node:path';
import YAML from 'yaml';

const isObj = (x) => x && typeof x === 'object' && !Array.isArray(x);

// الـ strategic merge: الـ objects بتتدمج، والـ lists اللي فيها name بتتدمج بالاسم
export function strategicMerge(base, patch) {
  if (Array.isArray(base) && Array.isArray(patch) && patch.every((p) => isObj(p) && p.name)) {
    const out = base.map((b) => {
      const p = patch.find((x) => x.name === b.name);
      return p ? strategicMerge(b, p) : b;
    });
    for (const p of patch) if (!base.some((b) => b.name === p.name)) out.push(p);
    return out;
  }
  if (isObj(base) && isObj(patch)) {
    const out = { ...base };
    for (const [k, v] of Object.entries(patch)) out[k] = k in base ? strategicMerge(base[k], v) : v;
    return out;
  }
  return patch;
}

export function build(dir) {
  const k = YAML.parse(readFileSync(path.join(dir, 'kustomization.yaml'), 'utf8'));
  let objects = [];
  for (const res of k.resources ?? []) {
    const full = path.join(dir, res);
    // لو المسار فولدر يبقى base تانية، ولو ملف نقراه
    if (res.endsWith('.yaml')) objects.push(...YAML.parseAllDocuments(readFileSync(full, 'utf8')).map((d) => d.toJS()).filter(Boolean));
    else objects.push(...build(full));
  }
  for (const { path: file } of k.patches ?? []) {
    const patch = YAML.parse(readFileSync(path.join(dir, file), 'utf8'));
    objects = objects.map((o) => (o.kind === patch.kind && o.metadata.name === patch.metadata.name ? strategicMerge(o, patch) : o));
  }
  for (const r of k.replicas ?? []) for (const o of objects) if (o.metadata.name === r.name && o.spec?.replicas !== undefined) o.spec.replicas = r.count;
  for (const img of k.images ?? []) {
    for (const o of objects) {
      for (const c of o.spec?.template?.spec?.containers ?? []) {
        if (c.image.split(':')[0] === img.name) c.image = `${img.newName ?? img.name}:${img.newTag}`;
      }
    }
  }
  if (k.namespace) for (const o of objects) o.metadata.namespace = k.namespace;
  return objects;
}

Part 5 — Jobs and CronJobs 🟡 Intermediateالجزء 5 — الـ Jobs والـ CronJobs

English

A Job runs a Pod to completion. It suits a database migration (see 31 · Migrations as their own step) or a backfill. A CronJob creates a Job on a schedule, such as nightly invoicing.

The fields that matter, from the Kubernetes docs:

  • backoffLimit is the number of retries before the Job fails, and defaults to 6. Retries wait with exponential back-off: 10 s, 20 s, 40 s and so on, capped at ten minutes.
  • activeDeadlineSeconds limits the whole Job and "takes precedence over its .spec.backoffLimit".
  • restartPolicy must be Never or OnFailure. ttlSecondsAfterFinished cleans up finished Jobs.
  • concurrencyPolicy: Allow is the default and lets runs overlap. Forbid skips a run if the previous one hasn't finished. Replace cancels the running one.
  • timeZone: without it, the schedule uses the controller's local time zone. Set an IANA name such as Africa/Cairo.

Even a perfect policy doesn't remove the duty to be idempotent. The docs say it directly: "there are certain circumstances where two Jobs might be created, or no Job might be created", and "the Jobs that you define should be idempotent".

In the run below, a job takes 500 ms and is scheduled every 300 ms, with 10 orders arriving per tick. Under Allow, up to 3 runs overlapped, and 50 of 110 invoices were duplicates: two runs read the same pending orders before either finished. Forbid skipped 3 runs and produced no duplicates. Making the job idempotent, using the invoice's order id as a unique key, removed duplicates even under Allow.

Stand-in, not the CronJob controller: real processes run on a compressed schedule. It does not capture missed schedules, startingDeadlineSeconds, Pods or retries. The YAML was validated by schema only.

// بديل تجريبي مش CronJob controller: كل tick بيشغّل job كـ process حقيقي
import { fork } from 'node:child_process';
import { mkdirSync, mkdtempSync, readdirSync, rmSync, writeFileSync } from 'node:fs';
import path from 'node:path';
import { fileURLToPath } from 'node:url';

const here = path.dirname(fileURLToPath(import.meta.url));
const script = path.join(here, 'invoice-job.mjs');
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const TICK_MS = 300;
const WORK_MS = 500;
const TICKS = 6;

async function schedule(policy, idempotent) {
  const dir = mkdtempSync(path.join(here, 'cron-'));
  mkdirSync(path.join(dir, 'invoices'));
  const orders = [];
  const running = new Set();
  let started = 0, skipped = 0, replaced = 0, peak = 0;

  const start = () => {
    const child = fork(script, [], { env: { ...process.env, STATE_DIR: dir, WORK_MS: String(WORK_MS), IDEMPOTENT: idempotent ? '1' : '0' } });
    running.add(child);
    started++;
    peak = Math.max(peak, running.size);
    child.once('exit', () => running.delete(child));
  };

  for (let tick = 0; tick < TICKS; tick++) {
    // كل tick بييجي 10 orders جديدة لازم يتعمل لها فواتير
    for (let i = 0; i < 10; i++) orders.push(`order-${tick}-${i}`);
    writeFileSync(path.join(dir, 'orders.json'), JSON.stringify(orders));
    if (running.size && policy === 'Forbid') skipped++;
    else {
      if (running.size && policy === 'Replace') {
        for (const c of running) c.kill();
        replaced++;
        await sleep(20);
      }
      start();
    }
    await sleep(TICK_MS);
  }
  while (running.size) await sleep(20);

  const files = readdirSync(path.join(dir, 'invoices'));
  const distinct = new Set(files.map((f) => f.split('--')[0])).size;
  console.log(`${(policy + (idempotent ? ' + idempotent' : '')).padEnd(20)} started=${started} skipped=${skipped} replaced=${replaced} peak concurrent=${peak} orders=${orders.length} invoices=${files.length} duplicates=${files.length - distinct} unbilled=${orders.length - distinct}`);
  rmSync(dir, { recursive: true, force: true });
}

await schedule('Allow', false);
await schedule('Forbid', false);
await schedule('Replace', false);
await schedule('Allow', true);
process.exit(0);

بالعامية

الـ Job بيشغّل Pod لحد ما يخلص، ومناسب لـ database migration (شوف 31 · Migrations كخطوة منفصلة) أو backfill. والـ CronJob بيعمل Job بجدول زمني، زي الفواتير كل ليلة.

الـ fields المهمة من الـ docs بتاعة Kubernetes:

  • backoffLimit: عدد المحاولات قبل ما الـ Job يفشل، والافتراضي 6. والمحاولات بتستنى بـ exponential back-off: 10 ثواني، 20، 40 وهكذا، لحد أقصى عشر دقايق.
  • activeDeadlineSeconds: حد زمني للـ Job كله، و"takes precedence over its .spec.backoffLimit".
  • restartPolicy لازم يكون Never أو OnFailure. وttlSecondsAfterFinished بيمسح الـ Jobs اللي خلصت.
  • concurrencyPolicy: Allow هو الافتراضي وبيخلي الـ runs تتداخل. Forbid بيتخطى الـ run لو اللي قبله لسه مخلصش. Replace بيلغي اللي شغال.
  • timeZone: من غيره الجدول بيتحسب بتوقيت الـ controller المحلي. حط اسم IANA زي Africa/Cairo.

وحتى أحسن policy مش بتشيل عنك إن الـ job يبقى idempotent. الـ docs بتقولها صراحةً: "there are certain circumstances where two Jobs might be created, or no Job might be created"، و"the Jobs that you define should be idempotent".

في التجربة فوق، الـ job بياخد 500 ms والجدول كل 300 ms، وكل tick بييجي 10 orders. مع Allow، وصلنا لـ 3 runs في نفس الوقت، و50 من 110 فاتورة طلعوا مكررين: اتنين runs قروا نفس الـ orders المعلقة قبل ما أي واحد يخلص. Forbid اتخطى 3 runs ومفيش تكرار. ولما خلينا الـ job idempotent باستخدام الـ order id كـ unique key، التكرار اختفى حتى مع Allow.

ON CONFLICT DO NOTHING. الاتنين مع بعض، لأن الـ Forbid لوحده مبيمنعش الـ job يتكرر بعد retry. والغلطة الشائعة: تعتمد على الـ Forbid وتنسى إن الـ retry بعد فشل الـ Pod بيعيد نفس الشغل.

You are not expected to run a cluster. Managed offerings such as EKS and GKE take care of the control plane, and in most companies a platform team runs the rest. حد عملي: نطاق الـ object. الـ namespaced objects بتوعك. والأنواع الـ cluster-scoped زي ClusterRole وCustomResourceDefinition وNode بتأثر على كل الناس، فمحتاجة مراجعة من الـ platform. الـ script فوق بيقرا الـ chart المتولد من الجزء 3 وبيعلّم عليهم، ولقى الـ ClusterRole وClusterRoleBinding بتوع الـ chart نفسه، و CRD اتضاف زي ما subchart هيضيفه. والـ exit code غير الصفر بيخليه ينفع CI gate.

للتمرين، kind أو k3d بيشغلوا cluster حقيقي محلي في Docker. الاتنين مش موجودين على الجهاز ده، فالأوامر معروضة بس متشغلتش. الـ probes والـ limits والـ autoscaling بيكملوا في 33، والـ rollouts و debugging بـ kubectl في 34.

فين هستخدمه في شغلي؟ PR بيضيف subchart للـ monitoring، والـ pipeline تقف عند الـ check ده: "فيه CRD و ClusterRole". تبعت للـ platform team رسالة محددة بالاسم بدل ما الـ deploy يفشل بـ forbidden الساعة 6 المغرب. والغلطة الشائعة: تطلب cluster-admin عشان تخلّص الشغل، بدل ما تحدد بالظبط إيه اللي محتاجه.

I don't need to run etcd. I do need to know why my Pod is Pending.
"محتاج تعرف Kubernetes كـ backend developer؟" ← على قد ما أنشر وأشخّص: أكتب وأراجع الـ manifests أو الـ chart بتاع الـ service بتاعي، أقرا الـ events والـ logs، أفهم الـ probes والـ limits، وأعرف إيه اللي أرفعه للـ platform. مش محتاج أدير etcd، بس لازم أعرف الـ Pod بتاعي واقف Pending ليه.

Common mistakes · غلطات شائعة

❌ Quoted number 
# ✗ data/spec/replicas must be integer
replicas: "{{ .Values.replicaCount }}"
✅ No quotes on numbers, quotes on env values 
replicas: {{ .Values.replicaCount }}
env:
  - name: PORT
    value: {{ .Values.port | quote }}
بالعامية

❌ علامات التنصيص حولت الرقم لـ string، و Kubernetes طالب integer، والخطأ ده طلع فعلًا في التجربة. ✅ الأرقام من غير تنصيص، وقيم الـ env بـ | quote لأنها لازم تكون strings، وعكس ده اترفض برضه.

❌ toYaml without nindent 
# في التجربة: الـ resources اختفت من غير أي error
resources:
  {{ toYaml .Values.resources }}
✅ nindent with the right column 
resources:
  {{- toYaml .Values.resources | nindent 12 }}
بالعامية

❌ أول سطر بس بياخد المسافات، والباقي بيروح لبداية السطر، فالـ resources ضاعت من غير أي error. ✅ nindent 12 بيبدأ سطر جديد وبيزحزح كل السطور، والرقم لازم يطابق العمود الصح.

❌ Password in the values file 
# فضل في git وفي الناتج المتولد
config:
  DATABASE_PASSWORD: fake-db-password-in-values
✅ Reference a Secret by name 
# الاسم بس في الـ chart، والقيمة بره
existingSecret: orders-api-secrets
بالعامية

❌ أي قيمة في ملف values بتتحفظ في git، وظهرت في الناتج كنص عادي في التجربة، ولو اتعملت rotate لازم تعدّل الـ repo. ✅ الـ chart بيشاور على Secret بالاسم، والقيمة نفسها بتيجي من secrets manager.

❌ Default policy, non-idempotent job 
# الافتراضي Allow: 50 فاتورة مكررة من 110 في التجربة
schedule: "*/5 * * * *"
✅ Forbid, plus an idempotency key 
-- الـ schedule بقى concurrencyPolicy: Forbid
-- والتكرار ممنوع في الـ DB كمان
INSERT INTO invoices (order_id, period)
VALUES ($1, $2) ON CONFLICT DO NOTHING;
بالعامية

❌ الـ Allow هو الافتراضي، فلو الـ job أطول من الجدول، الـ runs بتتداخل وتطلع فواتير مكررة. ✅ Forbid بيمنع التداخل، و unique key في الـ DB بيحمي من تكرار الـ retry، لأن الـ policy لوحدها مش كفاية.

❌ Installing ingress-nginx on a new cluster 
# المشروع ده متقاعد ومفيش security updates
helm install ingress ingress-nginx/ingress-nginx
✅ Gateway API with a maintained controller 
# بعد ما تتأكد من الـ GatewayClass عند فريقك
kind: HTTPRoute
spec:
  parentRefs:
    - name: public
بالعامية

❌ الـ community ingress-nginx اتقاعد، يعني مفيش patches لأي ثغرة جديدة، ولو ركبته في cluster جديد بتبدأ بدَين. ✅ استخدم Gateway API مع controller مدعوم، أو Ingress controller تاني لو لازم تفضل على Ingress.

3. When the job gets killed halfway 🟡 medium Change the job so it writes invoices one at a time, then compare Replace and Forbid with 20 orders per tick. Predict first: which one leaves work undone?
عدّل الـ job يكتب الفواتير واحدة واحدة، وقارن Replace وForbid بـ 20 order في كل tick. توقّع الأول: أنهي واحدة هتسيب شغل مخلصش؟
Solution · الحل 
// نسخة بتكتب فاتورة فاتورة: زي الشغل الحقيقي لما يتقتل في النص
import { readdirSync, readFileSync, writeFileSync } from 'node:fs';
import { randomUUID } from 'node:crypto';
import path from 'node:path';

const dir = process.env.STATE_DIR;
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const orders = JSON.parse(readFileSync(path.join(dir, 'orders.json'), 'utf8'));
const billed = new Set(readdirSync(path.join(dir, 'invoices')).map((f) => f.split('--')[0]));

for (const orderId of orders.filter((id) => !billed.has(id))) {
  // كل فاتورة بتاخد وقت: لو الـ process اتقتل، الباقي مبيتكتبش
  await sleep(25);
  writeFileSync(path.join(dir, 'invoices', `${orderId}--${randomUUID()}.json`), '{}');
}
process.exit(0);
Replace  killed=5 skipped=0 orders=120 invoices=120 duplicates=0 unbilled=0
Forbid   killed=0 skipped=4 orders=120 invoices=80 duplicates=0 unbilled=40
النتيجة مش زي ما تتوقع. Replace قتل 5 runs وبرضه كله اتفوتر، لأن كل run بيقرا اللي اتعمل قبل كده وبيكمّل (resumable). Forbid اتخطى 4 runs، و40 order فضلوا من غير فاتورة وقت ما التجربة خلصت، لأن آخر run قرا القايمة قبل ما الـ orders دي توصل. دول هيتفوتروا في أول run بعدها، مش ضايعين. الدرس: الـ policy مش اللي بتحمي الشغل، الـ job لازم يكون resumable و idempotent.

Cheat sheet · الخلاصة

  • For one API: Deployment, Service, ConfigMap, Secret, Namespace, plus an HTTPRoute. Pods are created for you.
  • A Secret is base64, unencrypted in etcd by default. Enable encryption at rest, tight RBAC, and an external secret store.
  • Schema validation catches types (replicas must be integer), but not typos in field names or a selector mismatch. Use --dry-run=server as well.
  • ClusterIP inside, LoadBalancer outside but one each, NodePort rarely. A Service is a stable name over changing Pods.
  • Community ingress-nginx was retired in March 2026. Gateway API (v1.7): platform owns the Gateway, you own the HTTPRoute.
  • Helm values merge deeply and arrays replace. Helm 3 security patches end 2026-11-11, and Helm 4.3 is current.
  • Don't quote numbers, do quote env values, always | nindent after toYaml, and no secrets in values.
  • Kustomize: plain base, overlays of differences, strategic merge by name. Helm for packaged software, Kustomize for thin differences.
  • backoffLimit defaults to 6, back-off caps at 10 minutes, and activeDeadlineSeconds wins over backoffLimit.
  • Allow is the default and overlaps (50 of 110 invoices were duplicates here). Use Forbid plus timeZone, and make every Job idempotent.
  • You own namespaced objects. Flag cluster-scoped kinds for the platform team.
بالعامية
  • لـ API واحد: Deployment و Service و ConfigMap و Secret و Namespace، وHTTPRoute. والـ Pods بتتعمل لوحدها.
  • الـ Secret ده base64 ومش متشفر في etcd افتراضيًا. فعّل encryption at rest و RBAC مضبوط و external secret store.
  • الـ schema validation بيمسك الأنواع (replicas must be integer)، بس مش بيمسك غلطة في اسم field ولا selector مش مطابق. استخدم --dry-run=server كمان.
  • الـ ClusterIP جوه، و LoadBalancer بره بس واحد لكل service، والـ NodePort نادرًا. الـ Service اسم ثابت فوق Pods بتتغير.
  • الـ ingress-nginx المجتمعي اتقاعد في مارس 2026. الـ Gateway API (v1.7): الـ Gateway بتاع الـ platform والـ HTTPRoute بتاعك.
  • الـ Helm values بتتدمج بالعمق والـ arrays بتتبدل. الـ security patches بتاعة Helm 3 بتخلص 2026-11-11، و Helm 4.3 هو الحالي.
  • متحطش تنصيص على الأرقام، وحط تنصيص على قيم الـ env، ودايمًا | nindent بعد toYaml، ومفيش secrets في الـ values.
  • الـ Kustomize: base عادي، و overlays بالفروقات، و strategic merge بالاسم. Helm للـ software الجاهز، و Kustomize للفروقات البسيطة.
  • الـ backoffLimit افتراضيه 6، والـ back-off أقصاه 10 دقايق، وactiveDeadlineSeconds أهم من backoffLimit.
  • الـ Allow هو الافتراضي وبيداخل (50 فاتورة مكررة من 110 هنا). استخدم Forbid وtimeZone، وخلي كل Job يبقى idempotent.
  • الـ namespaced objects بتاعتك. والـ cluster-scoped علّم عليها لفريق الـ platform.
