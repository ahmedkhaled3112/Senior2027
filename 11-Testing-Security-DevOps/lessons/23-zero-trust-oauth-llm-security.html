Why this matters · ليه ده مهم

English

Every serious breach walks through a boundary someone assumed was safe: "it's internal", "the gateway checked it", "OAuth handles that", "the model only summarizes". A trust boundary is any place where data or a request crosses from something you don't control into something you do. This lesson runs real attacks against this lesson's own loopback apps at four of those boundaries (service to service, browser to OAuth, browser to tokens, user text to an LLM tool), then fixes each one and re-runs it. In interviews, "how do your services trust each other?" and "where do you keep tokens in a SPA?" are the questions that separate people who used OAuth from people who can defend it.

Part 1 — Zero trust between services 🔴 Advancedالجزء 1 — الـ zero trust بين الـ services

English

Zero trust means no network location grants access: there is no "inside" that is trusted, so every call proves who is calling and is authorized on its own (NIST SP 800-207). Section 10, lesson 37, part 4 builds mTLS with an internal CA and shows the SSRF that breaks "internal means safe", so that isn't repeated here. This part adds the other half of the README item: a service identity token, a short-lived JWT that the caller attaches and the callee verifies in its own application code.

Why a token when you have mTLS? mTLS authenticates a connection, often at a sidecar, so by the time your handler runs the identity is a header somebody else set. A token is verified by the service that owns the data, and it says which service it was minted for. That is the part that stops the replay below: a token minted for billing, taken by a compromised billing and replayed at orders, fails with unexpected "aud" claim value. The same token against a verifier that skips the audience check is accepted.

What each claim is doing: iss pins the issuer; sub is the caller's SPIFFE-style ID; aud is exactly one callee; exp is 60 seconds; jti identifies the token for logs; typ: svc+jwt means a user's JWT can't be presented as a service token. On the verifying side, algorithms blocks algorithm confusion, clockTolerance: 5 absorbs host clock drift, and maxTokenAge rejects a long-lived token even if a buggy issuer signed one. Only the issuer holds the private key, so a compromised service can obtain tokens for itself but can't forge one for another service.

SPIFFE is the standard shape for this: an identity like spiffe://shop.internal/billing, delivered as a certificate or JWT (an SVID) through a local Workload API, with SPIRE as a common implementation that attests the workload instead of handing it a static secret. Cost is small: on this loaded Windows machine ≈180 µs to mint and ≈130 µs to verify a 409-byte ES256 token. Verification per request is fine; minting per request is wasteful, so cache per caller and callee and renew at about half the lifetime.

import { randomUUID } from "node:crypto";
import { createLocalJWKSet, exportJWK, generateKeyPair, jwtVerify, SignJWT } from "jose";

export type Service = "gateway" | "orders" | "billing";

// ده بيلعب دور الـ workload identity issuer زي SPIRE: stand-in محلي، مفيش attestation حقيقي
const ISSUER = "https://identity.shop.internal";
const TRUST_DOMAIN = "spiffe://shop.internal";
export const idOf = (s: Service) => `${TRUST_DOMAIN}/${s}`;

export async function createIdentityIssuer() {
  // المفتاح الخاص عند الـ issuer بس: لو billing اتخترقت، متقدرش تمضي بدل orders
  const { publicKey, privateKey } = await generateKeyPair("ES256");
  const jwk = { ...(await exportJWK(publicKey)), kid: "id-1", alg: "ES256", use: "sig" };
  const jwks = createLocalJWKSet({ keys: [jwk] });

  async function mint(caller: Service, callee: Service, now = Math.floor(Date.now() / 1000), ttlSec = 60) {
    return new SignJWT({})
      .setProtectedHeader({ alg: "ES256", kid: "id-1", typ: "svc+jwt" })
      .setIssuer(ISSUER)
      .setSubject(idOf(caller))
      // الـ audience هو الخدمة اللي هتستقبل، مش قايمة خدمات
      .setAudience(idOf(callee))
      .setIssuedAt(now)
      .setExpirationTime(now + ttlSec)
      .setJti(randomUUID())
      .sign(privateKey);
  }

  async function verify(token: string, me: Service, currentDate?: Date) {
    const { payload } = await jwtVerify(token, jwks, {
      issuer: ISSUER,
      audience: idOf(me),
      algorithms: ["ES256"],
      typ: "svc+jwt",
      clockTolerance: 5,
      // حتى لو حد مضى token عمره ساعة بالغلط، الـ verifier هيرفضه
      maxTokenAge: 65,
      requiredClaims: ["sub", "exp", "iat", "jti"],
      currentDate,
    });
    return payload.sub!.replace(`${TRUST_DOMAIN}/`, "") as Service;
  }

  // ده الـ verify الغلط: نفس الكود بس من غير audience، عشان نشوف الـ replay بينجح
  async function verifyWithoutAudience(token: string) {
    const { payload } = await jwtVerify(token, jwks, { issuer: ISSUER, algorithms: ["ES256"] });
    return payload.sub!.replace(`${TRUST_DOMAIN}/`, "");
  }

  return { mint, verify, verifyWithoutAudience };
}

بالعامية

الـ zero trust معناه إن مكانك في الشبكة مش بيدّيك أي صلاحية: مفيش "جوه" موثوق فيه، وكل call لازم يثبت مين اللي بينادي وياخد authorization لوحده (NIST SP 800-207). درس 37 في السيستم ديزاين، الجزء 4 بيبني mTLS بـ CA داخلية وبيوريك الـ SSRF اللي بيكسر فكرة "internal يبقى آمن"، فمش هنعيده هنا. الجديد هنا هو النص التاني من بند الـ README: service identity token، يعني JWT قصير العمر الـ caller بيحطه والـ callee بيتأكد منه في كوده هو.

طب ليه token وعندنا mTLS؟ الـ mTLS بيثبت هوية الـ connection، وغالبًا عند sidecar، فلما الـ handler بتاعك يشتغل تبقى الهوية header حد تاني حاطه. الـ token بيتحقق منه الـ service صاحب الـ data، وكمان بيقول هو معمول لمين. ده اللي بيوقف الـ replay: token معمول لـ billing، الـ billing اتخترقت وخدته وعادت استخدامه عند orders، بيترفض بـ unexpected "aud" claim value. نفس الـ token على verifier مش بيتأكد من الـ audience بيتقبل عادي.

كل claim بيعمل إيه: iss بيثبّت مين اللي مضى؛ sub هو هوية الـ caller بشكل SPIFFE؛ aud هو callee واحد بس؛ exp بعد 60 ثانية؛ jti بيعرّف الـ token في الـ logs؛ وtyp: svc+jwt معناه إن JWT بتاع user ميتقدمش كـ service token. وعند الـ verifier: algorithms بيمنع algorithm confusion، clockTolerance: 5 بيستوعب اختلاف الساعات بين الأجهزة، وmaxTokenAge بيرفض token طويل العمر حتى لو issuer فيه bug مضاه. والمفتاح الخاص عند الـ issuer بس، فالـ service اللي اتخترقت تقدر تطلب tokens لنفسها بس، ومتقدرش تزوّر token لـ service تانية.

SPIFFE هو الشكل المعياري للموضوع ده: هوية زي spiffe://shop.internal/billing بتوصل كـ certificate أو JWT (اسمها SVID) عن طريق Workload API محلي، و SPIRE implementation مشهور بيعمل attestation للـ workload بدل ما يديله secret ثابت. والتكلفة بسيطة: على الجهاز ده وعليه ضغط ≈180 مايكروثانية للـ mint و≈130 للـ verify لـ ES256 token حجمه 409 byte. الـ verify لكل request مفيش فيه مشكلة، إنما الـ mint لكل request هدر، فاعمل cache لكل caller و callee وجدّد عند حوالي نص العمر.

فين هستخدمه في شغلي؟ عندك payments بتنادي orders عشان تعمل refund. لو الـ token بدون aud واتسرّب في log أو خدته service اتخترقت، ينفع يفتح كل حاجة تانية في الـ system. مع aud لـ orders بس و60 ثانية: أقصى ضرر إن حد يعمل اللي orders تسمح بيه، ولدقيقة واحدة. الغلطة الشائعة: تستخدم JWT واحد طويل العمر مشترك بين كل الـ services ("internal token") وتحطه في env: ده باسورد مشترك للنظام كله، وأول service تتخترق بتفتح الكل.
Trade-off: mTLS vs service tokens mTLS protects the channel and removes secrets from your code, but it stops at the proxy and says nothing about which route is allowed. Service JWTs carry audience and can be checked in the handler, but they are bearer tokens: stolen means usable until expiry, so keep them short. Use mTLS (or a mesh) for the transport and tokens for the application decision; if you can only have one, tokens with audience are cheaper to adopt.
الـ mTLS بيحمي الـ channel وبيشيل الـ secrets من الكود، بس بيقف عند الـ proxy ومش بيقول مسموح لمين ينادي أنهي route. الـ service JWT فيه audience وبيتتشك في الـ handler، بس هو bearer token: اللي يسرقه يستخدمه لحد ما يخلص، فخليه قصير. استخدم mTLS (أو mesh) للـ transport والـ tokens لقرار الـ application. ولو لازم واحد بس، الـ tokens بالـ audience أرخص في التطبيق.

Interview question "You already have mTLS in the mesh. Why would you add JWTs between services?" → mTLS proves which workload is on the other end of the connection, usually at the proxy. It doesn't express which callee a credential is valid for or which route is allowed, and the app never verifies it itself. A short-lived token with one audience lets the service that owns the data decide, and a compromised service can't replay what it received at another service.
"عندك mTLS في الـ mesh بالفعل، ليه تضيف JWT بين الـ services؟" ← الـ mTLS بيثبت مين الـ workload اللي على الطرف التاني من الـ connection، وغالبًا عند الـ proxy. مش بيعبّر عن الـ credential صالح لمين ولا أنهي route مسموح، والـ app نفسه مش بيتحقق منه. token قصير العمر و audience واحد بيخلّي الـ service صاحبة الـ data هي اللي تقرر، والـ service المخترقة مش هتقدر تعيد استخدام اللي جالها عند service تانية.

Part 2 — Authorization at every hop 🔴 Advancedالجزء 2 — الـ authorization في كل hop

English

A token answers "who is calling". Whether that caller may do this particular thing is a separate decision, and it belongs in code that gets reviewed. Below, the whole service-to-service policy is one table: route to allowed callers, deny by default. guard() keeps the two steps apart on purpose: a bad or missing token is 401 (identity failed), a valid token from the wrong caller is 403 (policy failed). That difference tells you what went wrong during an incident.

The run shows the case the gateway-only design misses. A logged-in user goes through the gateway, the gateway is happy, and the request is still refused at orders because the policy says only billing may refund. Next, a request from inside the network with no token gets 401: here "inside" is literally the same machine, and it buys nothing. A flat VPC, an SSRF in any service or one compromised pod all put an attacker "inside", so the network location was never a control.

Typing the table means a route name that doesn't exist fails at compile time. The table only covers services; it says nothing about which user's order this is. Carry the user as a separate signed claim and have the owner check it (object-level authorization, in lesson 17), otherwise you've built a confused deputy: the gateway has broad rights and any user can drive it.

import type { RequestHandler } from "express";
import type { createIdentityIssuer, Service } from "./service-token.ts";

// الجدول ده هو الـ policy كلها: PR واحد يتراجع، ومفيش route مش مكتوب فيه يعدّي
export const POLICY = {
  orders: {
    "GET /orders/:id": ["gateway", "billing"],
    "POST /orders/:id/refund": ["billing"],
  },
  billing: {
    "POST /invoices": ["orders"],
  },
} as const satisfies Partial<Record<Service, Record<string, readonly Service[]>>>;

type Identity = Awaited<ReturnType<typeof createIdentityIssuer>>;

export function guard<S extends keyof typeof POLICY>(
  id: Identity,
  me: S,
  route: keyof (typeof POLICY)[S] & string,
): RequestHandler {
  const allowed = POLICY[me][route] as readonly Service[];
  return async (req, res, next) => {
    const raw = req.headers.authorization?.replace(/^Bearer /, "");
    if (!raw) return void res.status(401).json({ error: "no_service_token" });
    let caller: Service;
    try {
      caller = await id.verify(raw, me);
    } catch {
      return void res.status(401).json({ error: "bad_service_token" });
    }
    // خطوتين منفصلين: الـ token بيقول مين، والجدول بيقول مسموح له ولا لأ
    if (!allowed.includes(caller)) {
      return void res.status(403).json({ error: "caller_not_allowed", caller, route });
    }
    next();
  };
}

const listen = async (app: express.Express) => {
  // كل الخدمات على 127.0.0.1 و port 0: كل حاجة جوه الجهاز ده
  const server = app.listen(0, "127.0.0.1");

export async function startMesh() {
  const id = await createIdentityIssuer();

  const ordersApp = express();
  ordersApp.get("/orders/:id", guard(id, "orders", "GET /orders/:id"), (req, res) => {
    res.json({ id: req.params.id, status: "paid" });
  });
  ordersApp.post("/orders/:id/refund", guard(id, "orders", "POST /orders/:id/refund"), (req, res) => {
    res.json({ id: req.params.id, refunded: true });
  });
  const orders = await listen(ordersApp);

  const call = async (from: Service, path: string, method = "GET") => {
    const token = await id.mint(from, "orders");
    const r = await fetch(orders.url + path, { method, headers: { authorization: `Bearer ${token}` } });
    return { status: r.status, body: await r.json() };
  };

  const gatewayApp = express();
  // الـ gateway بتعدّي أي user عنده header صح: دي البوابة، مش كل الأمان
  gatewayApp.use((req, res, next) => (req.headers["x-user"] ? next() : void res.status(401).end()));
  gatewayApp.get("/api/orders/:id", async (req, res) => {
    const r = await call("gateway", `/orders/${req.params.id}`);
    res.status(r.status).json(r.body);
  });
  gatewayApp.post("/api/orders/:id/refund", async (req, res) => {
    const r = await call("gateway", `/orders/${req.params.id}/refund`, "POST");
    res.status(r.status).json(r.body);
  });
  const gateway = await listen(gatewayApp);

  return { id, orders, gateway, call, close: () => { orders.close(); gateway.close(); } };
}

The authorization server here is the teaching server from section 04, lesson 17, part 2, copied and given three lab-only flags, each of which opens one hole. The default is the safe behaviour. A small client plays your web backend. Every run stays on 127.0.0.1, and a "redirect" to the attacker's domain is only read from the Location header, never followed. The current wording of the rules is RFC 9700 (BCP 240, January 2025).

No state (login CSRF). The attacker logs in with their own account, stops before exchanging the code, and makes the victim's browser hit your callback with that code. The victim's session is now logged in as the attacker, and whatever card or data they add lands in the attacker's account. RFC 9700 requires a defence: PKCE if you have ensured the server supports it, the OIDC nonce, or a one-time state bound to the browser session. The run shows both fixes working: state gets a 403, and PKCE gets a 400 because the victim's session never had the verifier that matches.

Redirect URI matched by prefix. Registering https://shop.test and checking startsWith means https://shop.test.evil.test/steal passes. RFC 9700 says authorization servers MUST use exact string matching (localhost ports for native apps are the one exception). Note what the run proves: PKCE does not help here. The attacker builds the whole authorization link, so the attacker chooses the challenge and holds the verifier.

No PKCE. Codes leak through Referer headers, proxy logs, browser history and malicious apps. Without PKCE, a thief holding only a code gets tokens. With it, the same code needs a verifier the thief never saw. Also enforced: a code_verifier with no earlier challenge is rejected, which is RFC 9700's PKCE downgrade defence. Replayed code. A code is single use; if it arrives twice, someone stole it, so reject it and revoke what it produced. RFC 9700 also says clients should not use the implicit grant, and clients that talk to more than one authorization server need a mix-up defence such as the iss parameter (RFC 9207).

export async function startClient(opts: { issuer: string; clientId: string; checkState: boolean; usePkce: boolean }) {
  const sessions = new Map<string, Session>();
  const app = express();
  const server = app.listen(0, "127.0.0.1");
  await once(server, "listening");
  const url = `http://127.0.0.1:${(server.address() as AddressInfo).port}`;
  const redirectUri = `${url}/callback`;

  const sessionOf = (req: express.Request, res: express.Response) => {
    let sid = /sid=([\w-]+)/.exec(req.headers.cookie ?? "")?.[1];
    if (!sid || !sessions.has(sid)) {
      sid = rnd();
      sessions.set(sid, {});
      res.setHeader("set-cookie", `sid=${sid}; HttpOnly; SameSite=Lax; Path=/`);
    }
    return sessions.get(sid)!;
  };

  app.get("/login", (req, res) => {
    const s = sessionOf(req, res);
    const u = new URL(`${opts.issuer}/authorize`);
    u.searchParams.set("response_type", "code");
    u.searchParams.set("client_id", opts.clientId);
    u.searchParams.set("redirect_uri", redirectUri);
    u.searchParams.set("scope", "openid email");
    if (opts.checkState) u.searchParams.set("state", (s.state = rnd()));
    if (opts.usePkce) {
      s.verifier = rnd();
      u.searchParams.set("code_challenge", s256(s.verifier));
      u.searchParams.set("code_challenge_method", "S256");
    }
    res.redirect(302, u.href);
  });

  app.get("/callback", async (req, res) => {
    const s = sessionOf(req, res);
    const q = req.query as Record<string, string>;
    // الـ state لازم يكون نفس اللي اتحط في الـ session بتاعة المتصفح ده بالظبط
    if (opts.checkState && (!q.state || q.state !== s.state)) {
      return void res.status(403).json({ error: "state_mismatch" });
    }
    delete s.state;
    const r = await fetch(`${opts.issuer}/token`, {
      method: "POST",
      body: new URLSearchParams({
        grant_type: "authorization_code",
        client_id: opts.clientId,
        redirect_uri: redirectUri,
        code: q.code ?? "",
        code_verifier: s.verifier ?? "",
      }),
    });
    const body = (await r.json()) as { id_token?: string; error_description?: string };
    if (!r.ok) return void res.status(400).json({ error: body.error_description });
    delete s.verifier;
    s.user = decodeJwt(body.id_token!).sub!;
    res.json({ loggedInAs: s.user });
  });

  app.get("/whoami", (req, res) => void res.json({ user: sessionOf(req, res).user ?? null }));

  return { url, redirectUri, close: () => { server.closeAllConnections(); server.close(); } };
}

Interview question "Does PKCE replace state?" → For CSRF on the redirect, RFC 9700 allows relying on PKCE only if you've ensured the authorization server supports it, and OIDC's nonce also protects it; otherwise a one-time state bound to the browser is required. PKCE protects the code-for-token exchange against someone who has the code. It doesn't protect against a loose redirect URI: there the attacker built the request and owns the challenge.

Part 4 — Token storage and refresh rotation 🔴 Advancedالجزء 4 — تخزين الـ tokens والـ refresh rotation

English

Where should a SPA keep tokens? The answer below comes from a real injected script in real Chrome (channel: 'chrome', headless), reading what it can. The payload only writes a marker into the DOM. document.cookie shows the plain cookie but not the httpOnly one. localStorage gives up the token immediately. A variable inside a closure can't be read directly, but the attacker doesn't have to read it: wrapping fetch caught the Authorization header on the app's next call. And the httpOnly cookie, invisible to JavaScript, is still sent: fetch('/api/me') came back 200 as the victim.

So httpOnly stops the token from leaving, not the session from being used while the page is open. That's a real gain: an attacker can't take a long-lived credential away with them, and the abuse ends when the tab closes or the session is revoked. It isn't a substitute for stopping XSS. With a nonce-based CSP the injected script didn't run at all. CSP and output encoding are lesson 14's subject.

Rotation with reuse detection is built in section 04, lesson 16, part 4. What's new here is the BFF: a small server-side component holds the OAuth tokens in a Redis session, and the browser only gets a __Host- prefixed, HttpOnly, Secure, SameSite cookie. JavaScript never touches a token, and the IETF's draft on browser-based apps describes this pattern. It also moves the refresh to one place, which is exactly where the two-tab race shows up.

The race is real: two requests arrive with an expired access token, both refresh with the same refresh token, the first rotates, the second looks like a stolen-token replay, the family is revoked and the user is logged out for opening a second tab. The run shows it: statuses [200, 401] and the session is dead afterwards. A grace window (here 2 seconds) treats a repeat within the window as the same refresh; a replay after the window still revokes the whole family. The better first fix is single-flight in the BFF: a Redis lock so only one instance refreshes, and the others wait for the new token. With two BFF instances and 10 concurrent requests, the authorization server saw exactly 1 refresh call.

const ROTATE = `
if redis.call('HEXISTS', KEYS[1], 'revoked') == 1 then return 'revoked' end
local at = redis.call('HGET', KEYS[1], ARGV[1])
if not at then return 'unknown' end
at = tonumber(at)
local now = tonumber(ARGV[3])
if at == 0 then
  redis.call('HSET', KEYS[1], ARGV[1], now, ARGV[2], 0)
  redis.call('EXPIRE', KEYS[1], ARGV[5])
  return 'rotated'
end
if now - at <= tonumber(ARGV[4]) then
  redis.call('HSET', KEYS[1], ARGV[2], 0)
  return 'grace'
end
redis.call('HSET', KEYS[1], 'revoked', now)
return 'reuse'`;

const hash = (t: string) => createHash("sha256").update(t).digest("base64url");
const mint = (family: string) => `${family}.${randomBytes(32).toString("base64url")}`;

export function refreshStore(redis: Redis, graceMs: number) {
  return {
    async issue() {
      const family = randomUUID();
      const token = mint(family);
      // بنخزن الـ hash بس: لو الـ Redis اتسرّب، الـ tokens مش هتتسرّب معاه
      await redis.hset(`family:${family}`, hash(token), 0);
      return token;
    },
    async rotate(token: string, now = Date.now()) {
      const family = token.split(".")[0]!;
      const next = mint(family);
      const status = (await redis.eval(ROTATE, 1, `family:${family}`, hash(token), hash(next), now, graceMs, 2_592_000)) as string;
      return status === "rotated" || status === "grace" ? { status, token: next } : { status };
    },
  };
}

export async function startRefreshAs(redis: Redis, graceMs: number) {
  const store = refreshStore(redis, graceMs);
  const stats = { calls: 0 };
  const app = express();
  app.post("/token", express.json(), async (req, res) => {
    stats.calls++;
    const r = await store.rotate(req.body.refresh_token);
    if (!r.token) return void res.status(400).json({ error: "invalid_grant", reason: r.status });
    res.json({ access_token: `at_${randomUUID()}`, expires_in: 300, refresh_token: r.token });
  });
  const http = await listen(app);
  return { ...http, stats, store };
}

// الـ BFF: الـ tokens عنده هو، والمتصفح معاه cookie بس
export async function startBff(opts: { redis: Redis; asUrl: string; singleFlight: boolean }) {
  const { redis, asUrl, singleFlight } = opts;
  const load = async (sid: string) => {
    const raw = await redis.get(`sess:${sid}`);
    return raw ? (JSON.parse(raw) as Session) : null;
  };

  async function refresh(sid: string, s: Session): Promise<string | null> {
    const r = await fetch(`${asUrl}/token`, {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ refresh_token: s.refreshToken }),
    });
    if (!r.ok) {
      // الـ family اتحرقت: السيشن كلها بتتمسح والـ user لازم يعمل login تاني
      await redis.del(`sess:${sid}`);
      return null;
    }
    const t = (await r.json()) as { access_token: string; expires_in: number; refresh_token: string };
    const next = { accessToken: t.access_token, expiresAt: Date.now() + t.expires_in * 1000, refreshToken: t.refresh_token };
    await redis.set(`sess:${sid}`, JSON.stringify(next));
    return next.accessToken;
  }

  async function tokenFor(sid: string): Promise<string | null> {
    const s = await load(sid);
    if (!s) return null;
    if (s.expiresAt > Date.now()) return s.accessToken;
    if (!singleFlight) return refresh(sid, s);

    // الـ lock في Redis عشان يشتغل مع كذا instance من الـ BFF، مش بس جوه process واحد
    const got = await redis.set(`lock:refresh:${sid}`, "1", "PX", 5000, "NX");
    if (got) {
      try {
        return await refresh(sid, s);
      } finally {
        await redis.del(`lock:refresh:${sid}`);
      }
    }
    // اللي خسر الـ lock بيستنى الكسبان يكتب الـ token الجديد، ومبيعملش refresh تاني
    for (let i = 0; i < 100; i++) {
      await new Promise((r) => setTimeout(r, 20));
      const fresh = await load(sid);
      if (!fresh) return null;
      if (fresh.expiresAt > Date.now()) return fresh.accessToken;
    }
    return null;
  }

  const app = express();
  app.get("/bff/orders", async (req, res) => {
    const sid = /__Host-sid=([\w-]+)/.exec(req.headers.cookie ?? "")?.[1];
    const token = sid ? await tokenFor(sid) : null;
    if (!token) return void res.status(401).json({ error: "login_required" });
    res.json({ orders: [], usedToken: token.slice(0, 6) });
  });
  return listen(app);
}

}

export async function replayAfterGrace(redis: Redis, graceMs: number) {
  const as = await startRefreshAs(redis, graceMs);

  const child = await as.store.rotate(stolen);

  const thief = await as.store.rotate(stolen);
  const victim = await as.store.rotate(child.token!);

بالعامية

فين تحفظ الـ tokens في SPA؟ الإجابة تحت جاية من script حقيقي اتحقن في Chrome حقيقي (channel: 'chrome'، headless) وقرا اللي يقدر عليه. الـ payload بس بيكتب marker في الـ DOM. الـ document.cookie بيوريك الـ cookie العادي ومش بيوريك الـ httpOnly. الـ localStorage بيدّيك الـ token على طول. متغير جوه closure مش بيتقرا مباشرة، بس الـ attacker مش محتاج يقراه: لف fetch صاد الـ Authorization header في أول call للـ app. والـ httpOnly cookie، اللي الـ JavaScript مش شايفها، بتتبعت برضو: fetch('/api/me') رجع 200 كأنه الضحية.

يعني الـ httpOnly بيمنع الـ token إنه يخرج، مش إن الـ session تتستخدم والصفحة مفتوحة. ده مكسب حقيقي: الـ attacker مش هيقدر ياخد credential طويل العمر معاه، والضرر بيقف لما الـ tab تتقفل أو الـ session تتلغي. بس ده مش بديل عن منع الـ XSS. مع CSP بـ nonce، الـ script المحقون متنفذش خالص. الـ CSP و output encoding موضوع درس 14.

الـ rotation مع reuse detection اتبنى في درس 16 في Node، الجزء 4. الجديد هنا هو الـ BFF: component صغير على الـ server ماسك الـ OAuth tokens في Redis session، والـ browser بياخد cookie بـ __Host- وHttpOnly وSecure وSameSite بس. الـ JavaScript عمره ما بيلمس token، والـ draft بتاع IETF عن الـ browser-based apps بيوصف الـ pattern ده. وكمان بينقل الـ refresh لمكان واحد، وده بالظبط اللي بيظهر فيه race الـ tabs.

الـ race ده حقيقي: request اتنين وصلوا بـ access token منتهي، الاتنين بيعملوا refresh بنفس الـ refresh token، الأول بيدوّر، والتاني بيبان كأنه replay لـ token مسروق، والـ family بتتحرق والـ user بيخرج لأنه فتح tab تانية. الـ run بيوريك ده: statuses [200, 401] والـ session ماتت بعدها. الـ grace window (هنا 2 ثانية) بيعتبر التكرار جوه الفترة نفس الـ refresh، إنما replay بعد الفترة بيحرق الـ family كلها. والإصلاح الأحسن كأول خطوة single-flight في الـ BFF: lock في Redis عشان instance واحد بس هو اللي يعمل refresh، والباقي يستنى الـ token الجديد. ومع BFF اتنين و10 requests في نفس الوقت، الـ auth server شاف refresh call واحد بالظبط.

فين هستخدمه في شغلي؟ SPA في Next بيتعامل مع payments: بدل ما تحط access token في localStorage، خلّي الـ route handlers في Next هي الـ BFF، والـ session في Redis. وأول ما حد يشتكي "بيطلعني بره لوحده" ودوّرت على الـ logs تلاقي reuse detected من نفس الـ user في نفس الثانية: دي مش هجمة، ده two-tab race، صلّحه بـ single-flight و grace قصير مش بإلغاء الـ reuse detection.
Trade-off: how long is the grace window? Longer means fewer false logouts and a wider window for a thief who raced the real client. Keep it to seconds, not minutes, and prefer single-flight so the window rarely matters. Bind the refresh token to the client where you can (sender constraining), and always alert on a real reuse: it is a compromise signal, not noise.
كل ما طوّلت الـ grace، الـ logouts الغلط بتقل، بس فرصة لص سابق الـ client الحقيقي بتزيد. خليه بالثواني مش دقايق، وفضّل الـ single-flight عشان الـ window متفرقش كتير. واربط الـ refresh token بالـ client لو تقدر (sender constraining)، ودايمًا اعمل alert على أي reuse حقيقي: ده إشارة اختراق مش noise.

Part 5 — An LLM feature as a trust boundary 🔴 Advancedالجزء 5 — الـ LLM feature كـ trust boundary

English

Depth on prompt injection lives in section 12 · 2.7. The angle here is architectural: treat the model as an untrusted input source and an untrusted output source. Anything it reads may contain instructions, and anything it produces is attacker-influenced. The model below is a labelled local stand-in with worst-case behaviour: it obeys any instruction it finds, from the user or from a retrieved document. No provider is called.

Direct injection is the user typing "ignore previous instructions". Indirect injection is the dangerous one: the attacker writes a support ticket with a hidden comment, an agent later clicks "Summarize", and the model reads the instruction as if it were part of the task. In the run, the vulnerable version issues a refund of 99,900 cents to another tenant's order. Data leakage through the prompt happens the moment an email and phone number go to a third-party provider, even if the reply never repeats them; the same call also shows the model echoing PII to whoever asked. Tools beyond the user's rights: a customer asked for a refund and the vulnerable code executed it, because the tool ran with the service account.

The defences that hold don't depend on the model behaving. AuthZ on tools as the user: a tool call is a request from that user, so a customer can't refund and an agent can't touch another tenant, regardless of what the model said. Zod on output: malformed JSON and an unexpected admin: true field both fall back to a fixed safe reply and execute nothing. PII redaction before the call: the captured prompt shows [EMAIL] and [PHONE]. A per-tenant budget in Redis, reserved atomically before the call: 50 concurrent calls with room for 20 allowed exactly 20, and another tenant was unaffected. Notice the direct injection still "worked" in the defended run: the model printed its system prompt. That is fine, because nothing secret was in it. Assume the prompt can leak and design for it.

Stand-in label: this is not an LLM standInModel is a small rule-based function that plays a gullible model. It captures the worst case (it always obeys) so the defences can be tested deterministically. It does not capture that real models are probabilistic, that the same injection succeeds some of the time, or how much "prompt hardening" helps. No LLM provider was called in this lesson.

// بيمثّل أسوأ حالة: بينفّذ أي أمر يلاقيه في الـ input، سواء من الـ user أو من الـ data
// مش بيمثّل: إن المودل الحقيقي احتمالي، وإن نفس الهجمة ممكن تنجح مرة وتفشل مرة
export type Prompt = { system: string; user: string; context: string };

export function standInModel(p: Prompt): string {
  const input = `${p.user}\n${p.context}`;
  if (input.includes("__MALFORMED__")) return 'Sure! here is your JSON: {"reply": oops';
  if (input.includes("__EXTRA_FIELD__")) return JSON.stringify({ reply: "ok", toolCalls: [], admin: true });

  const obey = /ignore (all |your |previous )+instructions/i.test(input);
  const call = /CALL refund_order\(orderId=(\w+), amountCents=(\d+)\)/.exec(input);
  if (obey && call) {
    return JSON.stringify({ reply: "Done.", toolCalls: [{ name: "refund_order", args: { orderId: call[1], amountCents: Number(call[2]) } }] });
  }
  if (obey && /system prompt/i.test(input)) return JSON.stringify({ reply: p.system, toolCalls: [] });
  if (obey && /emails?/i.test(input)) {
    return JSON.stringify({ reply: (input.match(/[\w.+-]+@[\w.-]+/g) ?? []).join(", "), toolCalls: [] });
  }
  const direct = /refund order (\w+)/i.exec(p.user);
  if (direct) {
    return JSON.stringify({ reply: "Refunding.", toolCalls: [{ name: "refund_order", args: { orderId: direct[1], amountCents: 5000 } }] });
  }
  return JSON.stringify({ reply: "The customer is asking about a late delivery.", toolCalls: [] });
}

  return { reply: redact(parsed.data.reply), denied, executed };
}

بالعامية

العمق في الـ prompt injection موجود في section 12 · 2.7. الزاوية هنا معمارية: اعتبر الموديل مصدر input مش موثوق ومصدر output مش موثوق. أي حاجة بيقراها ممكن يبقى فيها أوامر، وأي حاجة بيطلعها الـ attacker أثّر فيها. الموديل تحت stand-in محلي بسلوك أسوأ حالة: بيطيع أي أمر يلاقيه، سواء من الـ user أو من document جابه. ومفيش provider بيتنادى.

الـ direct injection هو إن الـ user يكتب "ignore previous instructions". الـ indirect injection هو الخطير: الـ attacker يكتب support ticket فيه comment مخفي، والـ agent بعدين يدوس "Summarize"، والموديل يقرا الأمر كأنه جزء من الشغل. في الـ run الـ vulnerable عمل refund بـ 99,900 cents لـ order بتاع tenant تاني. الـ data leakage عبر الـ prompt بيحصل أول ما email ورقم تليفون يروحوا لـ provider خارجي، حتى لو الرد مكررهمش؛ ونفس الـ call بيوريك الموديل بيرجّع PII لأي حد يطلب. وtools فوق صلاحية الـ user: customer طلب refund والكود الضعيف نفّذه، لأن الـ tool شغالة بالـ service account.

الدفاعات اللي بتصمد مش معتمدة على إن الموديل يبقى كويس. الـ authZ على الـ tools بصلاحية الـ user: الـ tool call هو request من الـ user ده، فالـ customer ميقدرش يعمل refund والـ agent ميلمسش tenant تاني، مهما الموديل قال. Zod على الـ output: JSON بايظ أو field زيادة زي admin: true بيرجعوا رد ثابت آمن ومفيش حاجة بتتنفذ. PII redaction قبل الـ call: الـ prompt المتسجّل فيه [EMAIL] و[PHONE]. وميزانية لكل tenant في Redis، بتتحجز atomic قبل الـ call: 50 call في نفس الوقت ومساحة لـ 20 طلعوا 20 بالظبط، والـ tenant التاني مش متأثر. وخد بالك إن الـ direct injection "نجح" برضو في الـ defended: الموديل طلّع الـ system prompt بتاعه، وده مش مشكلة لأن مفيهوش حاجة سرية. افترض إن الـ prompt ممكن يتسرّب وصمّم على كده.

فين هستخدمه في شغلي؟ بتضيف "AI summary" لـ dashboard الـ support؟ قبل ما يبقى ليه tools: خلّي الـ refund function تاخد user الحقيقي وتعمل نفس الـ authorization اللي الـ API بيعمله، حط Zod على الرد، شيل الـ PII قبل الـ call، وحط ميزانية لكل tenant في Redis عشان tenant واحد ميحرقش فلوسك في ساعة. الغلطة الشائعة: تحط الـ rules في الـ system prompt ("never refund more than…") وتعتبرها authorization. الـ prompt طلب، مش control.
What breaks at scale Redaction by regex misses names and addresses, and it can corrupt text the model needs. Treat it as one layer. Reserve budget before the call and give back the unused tokens afterwards, or a burst of expensive calls will exceed the limit. Log every denied tool call with the user and tenant: a spike is your injection alarm.
الـ redaction بالـ regex مش بيمسك الأسماء والعناوين، وممكن يبوظ نص الموديل محتاجه. اعتبره طبقة واحدة بس. واحجز الميزانية قبل الـ call ورجّع الـ tokens اللي متستهلكتش بعدها، وإلا مجموعة calls غالية هتعدّي الحد. وسجّل كل tool call اترفض ومعاه الـ user والـ tenant: أي spike ده إنذار injection.

Common mistakes · غلطات شائعة

❌ Verify without audience 
// ده بيقبل أي token موقّع من الـ issuer، حتى لو معمول لـ service تانية
await jwtVerify(token, jwks, { issuer: ISSUER });
✅ Pin audience, algorithm, typ 
// الـ token لازم يكون معمول للخدمة دي بالاسم
await jwtVerify(token, jwks, {
  issuer: ISSUER,
  audience: idOf(me),
  algorithms: ["ES256"],
  typ: "svc+jwt",
});
بالعامية

❌ من غير audience الـ verify بينجح لأي token الـ issuer مضاه، فأي service اتخترقت تعيد استخدام اللي جالها عند الباقي (جرّبناها في الجزء 1 واتقبل). ✅ لما تثبّت الـ audience والـ algorithms والـ typ، الـ token ينفع للخدمة دي بس، وميبقاش ينفع تقدّم user JWT مكان service token.

❌ Trust the gateway 
// ده route داخلي، والـ ⁦gateway "⁩أكيد" اتأكدت من كل حاجة
app.post("/orders/:id/refund", refundHandler);
✅ Every service decides 
// الـ token بيقول مين، والجدول بيقول مسموح ولا لأ
app.post(
  "/orders/:id/refund",
  guard(id, "orders", "POST /orders/:id/refund"),
  refundHandler,
);
بالعامية

❌ اللي بيوصل للـ route ده أي حد جوه الشبكة: SSRF، pod مخترق، أو حتى service تانية عندها bug. ✅ guard بيتأكد من الـ token وبعدين من الجدول، والـ gateway بقت مجرد باب مش الحماية كلها، وده اللي شفناه في الجزء 2 لما رفض الـ refund بـ 403.

❌ Prefix-matching redirect URIs 
// الدومين shop.test.evil.test بيبدأ بـ shop.test برضو
if (redirectUris.some((u) => sent.startsWith(u))) return allow();
✅ Exact string match 
// الـ allowlist بالحرف، زي ما RFC 9700 بيطلب
if (redirectUris.includes(sent)) return allow();
بالعامية

❌ أي دومين بيبدأ بنفس الحروف بيعدّي، والـ code بيروح للـ attacker، وحتى الـ PKCE مش بينفع لأن هو اللي عمل الـ challenge. ✅ exact match: لو الـ URL مش مسجّل حرف بحرف يبقى 400. ولو محتاج staging URLs سجّلهم صراحةً، متستخدمش wildcard.

❌ Tool runs as the service 
// المودل طلب refund، فالـ service بينفّذ من غير ما يسأل مين الـ user
for (const call of toolCalls) {
  await refundOrder(call.args);
}
✅ AuthZ on the tool, as the user 
// الـ tool call ده request من الـ user، ونفس الصلاحيات بتتطبق
for (const call of toolCalls) {
  const denied = authorizeTool(user, call.args);
  if (denied) { log(user, denied); continue; }
  await refundOrder(call.args);
}
بالعامية

❌ أي نص قدر يأثر على الموديل، حتى ticket كاتبه attacker، بقى يقدر ينفّذ أي tool بصلاحية الـ service كلها. ✅ الـ authorization بيتحسب من الـ user اللي عامل الـ request، فمهما الموديل اتخدع النتيجة order_not_in_tenant ومفيش فلوس بتتحرك. والـ denied calls بتتسجّل، وده اللي بيخليك تشوف الهجمة.

❌ Refresh per tab, no coordination 
// كل tab بتعمل refresh بنفس الـ token: reuse detection هيحرق الـ family
if (expired) return refresh(session);
✅ Single-flight, then short grace 
// الـ lock في Redis عشان refresh واحد، والباقي يستنى الـ token الجديد
const got = await redis.set(`lock:refresh:${sid}`, "1", "PX", 5000, "NX");
if (got) return refresh(session);
return waitForFreshToken(sid);
بالعامية

❌ tabين في نفس اللحظة بيبعتوا نفس الـ refresh token، والتاني بيتفهم إنه هجوم، والـ user يخرج (شفناها [200, 401]). ✅ lock في Redis، واللي مكسبش الـ lock بيستنى الـ token الجديد، والـ auth server شاف refresh واحد. وسيب grace قصير كشبكة أمان، وأي reuse بعد كده هو الهجوم الحقيقي.

Cheat sheet · الخلاصة

  • No network location grants access; every call proves identity and is authorized on its own.
  • Service JWT: aud = one callee, ~60 s, pin iss, algorithms, typ; only the issuer holds the key.
  • 401 means identity failed, 403 means policy failed; keep them apart and deny by default.
  • Redirect URIs: exact string match (RFC 9700). PKCE doesn't save a loose redirect because the attacker owns the challenge.
  • state bound to the session stops login CSRF; PKCE stops a stolen code; single-use codes plus revoke-on-replay stop replay.
  • httpOnly keeps a token from leaving the page, but XSS can still use the session. A fetch hook catches tokens "safely" in memory.
  • BFF: tokens stay on the server, the browser gets a __Host- cookie only.
  • Two tabs refreshing race reuse detection: single-flight first, a grace of seconds as the safety net.
  • Treat an LLM as untrusted in both directions: authZ tools as the user, Zod its output, redact PII first, atomic per-tenant budget.
  • A prompt is a request, not a control: assume the system prompt can leak.
  • Every boundary gets a test and a script that fails the build when a test is missing.
بالعامية
  • مكانك في الشبكة مش بيدّيك صلاحية؛ كل call لازم يثبت هويته وياخد authorization لوحده.
  • الـ service JWT: aud واحد للـ callee، حوالي 60 ثانية، وثبّت iss وalgorithms وtyp، والمفتاح عند الـ issuer بس.
  • الـ 401 يعني الهوية فشلت، والـ 403 يعني الـ policy فشلت؛ افصلهم، و deny by default.
  • الـ redirect URIs بـ exact match (RFC 9700)، والـ PKCE مش بينقذ redirect مفتوح لأن الـ attacker هو اللي بيعمل الـ challenge.
  • الـ state المربوط بالـ session بيوقف login CSRF؛ والـ PKCE بيوقف الـ code المسروق؛ والـ single use مع revoke عند الـ replay بيوقف إعادة الاستخدام.
  • الـ httpOnly بيمنع الـ token يخرج من الصفحة، بس الـ XSS يقدر يستخدم الـ session. والـ fetch hook بيصطاد tokens الـ memory.
  • الـ BFF: الـ tokens عند الـ server، والـ browser معاه cookie __Host- بس.
  • الـ tabين اللي بيعملوا refresh مع بعض بيضربوا الـ reuse detection: الـ single-flight الأول، و grace بالثواني كشبكة أمان.
  • تعامل مع الـ LLM كمصدر مش موثوق في الاتجاهين: authZ على الـ tools بصلاحية الـ user، Zod على الـ output، redaction للـ PII قبل الـ call، وميزانية atomic لكل tenant.
  • الـ prompt طلب مش control: افترض إن الـ system prompt ممكن يتسرّب.
  • كل حدود ليها test، وسكريبت يوقّع الـ build لو الـ test ناقص.
