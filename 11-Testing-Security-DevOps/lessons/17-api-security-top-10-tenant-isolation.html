Why this matters · ليه ده مهم

English

An API usually fails on logic, not on parsing. The request is valid JSON from a logged-in user, and the server simply answers something that user shouldn't get. No scanner reads your business rules, so these gaps reach production and stay there. In a multi-tenant product the same gap crosses a customer boundary, and one cross-tenant response is an incident you report to every affected client. Interviewers ask about BOLA and tenant isolation because the answer shows whether you think in controls or in patches.

This lesson is built from the defender's side: each risk gets a control, the fixed code and a test that proves the control is there. Everything below ran against a real Express service and a real Postgres 18 with separate database roles: 222 tests.

الـ API غالبًا بتقع في الـ logic مش في الـ parsing. الـ request JSON سليم من user عامل login، والسيرفر ببساطة بيرد بحاجة اليوزر ده مش من حقه يشوفها. ومفيش scanner بيقرا قواعد البيزنس بتاعتك، فالثغرات دي بتوصل production وتقعد فيها. وفي product فيه كذا tenant نفس الثغرة بتعدّي حدود عميل لعميل، و response واحد عدّى من tenant لتاني يعني incident لازم تبلّغ بيه كل عميل اتأثر. وفي الـ interviews بيسألوا عن BOLA و tenant isolation عشان الإجابة بتبيّن إنت بتفكر بالـ controls ولا بترقّع.

Part 1 — The 2023 list and the map 🟡 Intermediateالجزء 1 — قايمة 2023 والخريطة بتاعة الدرس

English

The README item lists the 2019 names. The current edition of the OWASP API Security Top 10 is still API:2023, and it isn't a rename: two risks merged, three new ones arrived, and two left. Learn the 2023 names, because that's what a security review or an interviewer will use today.

The biggest change for a backend developer is API3 BOPLA (Broken Object Property Level Authorization). The 2019 list had "excessive data exposure" (you return too many fields) and "mass assignment" (you accept too many fields) as separate items. They are the same bug in two directions: nobody decided which properties this caller may read or write. So 2023 has one risk for both, and Part 3 has one design for both.

Injection and insufficient logging left this list. That doesn't make them less real: both stay in the general Top 10:2025 (A05 and A09), lesson 12 covers injection and lesson 16 covers logging and audit.

Part 2 — Object and function level authorization 🟡 Intermediateالجزء 2 — الـ authorization على مستوى الـ object والـ function

English

Lesson 12, part 5 introduced a scoped repository and a route × role matrix. Here they become the design of a whole service, for three risks at once:

  • API1, objects. Every handler loads through a query scoped to the actor. findOrder(db, actor, id) takes the actor as a required argument, so there's no findOrderById(id) to call by mistake. A customer is limited to their own rows; staff are limited to their tenant.
  • API5, functions. policy.ts is the single source of policy: one line per route, saying who may call it. The route key is a type derived from that table, so a route that isn't in the table doesn't compile, and route() is the only function that mounts a protected handler.
  • API2, authentication. The token is random and opaque, the database stores only its SHA-256, and expiry is part of the lookup. An expired session and an unknown token take the same path and get the same answer. Lesson 13 goes deeper on sessions and login.

The status codes carry meaning. 401 means we don't know who you are, and it comes with WWW-Authenticate. 403 means we know you, and your role can't use this function; the route's existence isn't a secret, since it's in the OpenAPI document. 404 means this object isn't yours, and the body is byte-for-byte the same as for an order that doesn't exist, so the response can't confirm the object is there.

The order inside route() is fixed: authenticate, authorize, parse the body, validate, run the handler, validate the response. A caller who isn't allowed in never reaches the JSON parser or the validators, so they learn nothing about the schema.

  request
     |

    const header = req.get("authorization") ?? "";
    const token = header.startsWith("Bearer ") ? header.slice(7) : "";
    if (!token) throw new HttpError(401, "unauthenticated", { "WWW-Authenticate": "Bearer" });
    const hash = createHash("sha256").update(token).digest();

      "SELECT user_id, tenant_id, role FROM resolve_session($1)",
      [hash],
    );
    const row = rows[0];
    if (!row) throw new HttpError(401, "unauthenticated", { "WWW-Authenticate": "Bearer" });
    res.locals.actor = { userId: row.user_id, tenantId: row.tenant_id, role: row.role } satisfies Actor;
    next();
  };

    if (!roles.includes(actorOf(res).role)) throw new HttpError(403, "forbidden");

Part 3 — Response and request allowlists 🟡 Intermediateالجزء 3 — الـ allowlists للـ response والـ request

English

BOPLA is a missing decision about properties. The fix is the same in both directions: name what's allowed, and let everything else fall away. A denylist (delete user.passwordHash) fails open the day someone adds a column; an allowlist fails closed, because a new column stays invisible until a person adds it on purpose.

Three layers protect the password hash here, and each one would be enough on a good day:

  • The database. The app role has column-level GRANT SELECT on users without password_hash. Even SELECT password_hash fails with 42501.
  • The SQL. Repositories list their columns; there's no SELECT *.
  • The response schema. Every route declares one, and it's the last step before res.json. z.object drops keys it doesn't name, so a handler that returns too much still can't serialize it. If a required field is missing or has the wrong type, parse throws and the caller gets the generic 500, not a half-filled object.

Requests go the other way: z.strictObject rejects any key it doesn't name, with a 400 that lists field names and never echoes values. Rejecting is better than silently dropping: a client that sends role has a bug or an intent worth noticing, and a silent drop looks like success. Node lesson 27, part 7 shows how mass assignment works underneath; this part is the design that makes it impossible.

Field-level rules per role. Some fields are fine for one role and wrong for another. internalNote is readable only by staff, and a customer may write only shippingNote. Those are two schemas chosen by role, not an if inside the handler, and route() accepts either a schema or a function of the actor.

Part 4 — Limits and business flows 🟡 Intermediateالجزء 4 — الحدود والـ business flows

English

API4 is about the fact that every request spends something: rows, bytes, CPU, connections, seconds, and sometimes money, when the handler calls a paid SMS or email provider. A control here is simply a number next to each of those. This service has four:

  • Rows. limit is clamped to 100 by the schema, so a large value returns a full page and no error. A value that isn't a number gets 400. Paging uses a keyset before cursor rather than an offset (REST design, part 2).
  • Bytes. express.json({ limit: "16kb" }) answers 413 for anything bigger, and because parsing comes after authentication, an anonymous caller is turned away before the body is read.
  • Time at the HTTP layer. Node's defaults here are requestTimeout 300 s and headersTimeout 60 s, which are far too generous for an API that takes small JSON requests. The service sets 15 s and 8 s.
  • Time in the database. Each request's transaction sets statement_timeout with set_config(..., true), so it applies only to that transaction. Postgres cancels the query with code 57014, the handler answers 503 with Retry-After, and the connection goes back to the pool.

Then the measurement, because "limit the page size" is a claim until you see the number. Same service, 200,000 orders on one account, peak memory of the server process from process.resourceUsage().maxRSS:

API6 is different in kind. No endpoint is broken: each purchase is valid, and the harm comes from the rate and volume of a legitimate flow, like one account buying all of a limited launch. The control is a business rule, so it belongs in the transaction that changes the stock: SELECT ... FOR UPDATE on the product row serializes concurrent buyers, then the count of this account's recent units is read and checked before stock moves.

Doing the check inside that transaction is what makes the concurrency test pass: 8 parallel purchases from one account give exactly 2 successes and 6 of 429. A check before the transaction can let all 8 read "0 bought so far". General request rate limiting is a separate, wider tool (section 10, rate limiting and Node 26, part 2). A per-account rule doesn't stop one person with many accounts, so high-value launches add verified phone numbers, payment instrument checks or a queue, and that part is a product decision.

// قراءة اللي Express شايله فعلًا، مش اللي إحنا فاكرين إننا ركّبناه
export function mountedRoutes(app: Express): Mounted {
  const stack = (app as unknown as { router: { stack: Layer[] } }).router.stack;
  const routes: string[] = [];
  let unresolvedRouters = 0;
  for (const layer of stack) {
    if (layer.route) {
      const paths = Array.isArray(layer.route.path) ? layer.route.path : [layer.route.path];
      for (const path of paths) {
        for (const [method, on] of Object.entries(layer.route.methods)) {
          if (on && method !== "_all") routes.push(`${method.toUpperCase()} ${path}`);
        }
      }
    } else if (layer.handle?.stack) {
      // ملحوظة: Express 5 مبيحفظش الـ mount path، فأي sub-router بنعلّم عليه كمشكلة
      unresolvedRouters++;
    }
  }
  return { routes: routes.sort(), unresolvedRouters };
}

API10, unsafe consumption. Developers validate user input and then trust a partner's JSON completely. A partner is another network input: it can be down, slow, compromised or simply changed by a release you weren't told about. Treat its response with the same four controls as a request: schema, timeout, size cap and no surprises (redirect: "error", so it can't send you somewhere else).

AbortSignal.timeout covers the headers and the body together, so a partner that sends headers quickly and then stalls is still bounded (checked here: a stall mid-body ended as a timeout at ≈308 ms with a 300 ms limit). The byte cap cancels the stream as soon as it passes the limit, instead of buffering first and checking afterwards. And the failure the caller sees is ours: 502 or 504 with a fixed code, never the partner's text, which may contain internal detail.

Look at the route as well as the client. The order is loaded in its own short transaction, and that transaction is committed before the partner call, so a slow partner can't pin a database connection. The slow-partner test checks the pool while the call is in flight. For retries and circuit breakers on top of this, see Node 25.

English

Two tenants' data in one database is the most expensive bug class in SaaS. The goal here is a test that scales with the API: nobody writes a cross-tenant test by hand for each new route, so the matrix generates them from the route table. Every protected route, with every role, in both directions, sends the request aimed at the other tenant's object.

Each case makes two assertions. The status follows the policy: 403 if the role can't use the route, 404 for an object in the other tenant, 200 for a route that only returns the caller's own data. The body must contain none of the other tenant's canaries, the ids, emails and names recorded at seed time. Searching the raw text matters, because it catches a leak in a field the test author didn't think about, error bodies included. Then a fingerprint of all the other tenant's rows must be unchanged, which is what catches a write that crossed the boundary and returned 404 anyway.

Row-level security is the safety net (section 07 · 3.1 teaches it fully, and Architecture 22, part 6 compares isolation levels). A policy on each table means a query that forgets its tenant predicate still sees one tenant. The net only works if it's armed, so three facts get tests of their own: the app's role isn't a superuser and doesn't have BYPASSRLS; every table with a tenant_id has RLS enabled and forced; and a connection that served a tenant earlier returns zero rows, instead of the previous tenant or an error.

A composite foreign key adds one more guarantee cheaply: FOREIGN KEY (tenant_id, owner_id) REFERENCES users (tenant_id, id) means the database refuses an order that points at another tenant's user, even from a role that bypasses RLS.

Per-tenant encryption keys, as a concept. RLS separates rows at query time; it doesn't help with a stolen backup. Per-tenant keys do: each tenant's sensitive fields are encrypted under that tenant's own data key, and those keys are wrapped by a master key in a KMS. The envelope mechanics are in section 10, lesson 38, part 3. What you get is a smaller blast radius per key, a way to offboard a tenant by destroying its key, and a clean answer to "can you prove our data is separate?". You pay for key lookups on the hot path, more operational work, and searches that can't look inside encrypted columns. Not run here: no KMS in this lab.

Part 7 — A CI gate 🟡 Intermediateالجزء 7 — بوابة الأمان في الـ CI

English

Every control so far can still be skipped by the next route someone adds. The compiler only protects routes that go through route(); a plain app.get never meets it. The gate closes that gap by looking at what's really mounted and refusing anything undeclared.

The gate is a pure function over four facts: the routes Express has mounted, the policy table, the isolation case table and the OpenAPI document. It returns a list of problems, which makes the gate itself easy to test. The rules:

  • no-declared-policy: a mounted route with no line in the policy.
  • no-isolation-test: a mounted route with no entry in the case table, so the matrix can't generate tests for it.
  • not-in-openapi and documented-but-not-mounted: the inventory diff from Part 5, in both directions.
  • policy-for-missing-route: a policy line whose route is gone.
  • openapi-auth-disagrees-with-policy: the document says public and the policy says protected, or the reverse.
  • router-not-inspectable: a sub-router the gate can't read, reported instead of skipped.
  • risk-has-no-passing-test: a risk in the map from Part 1 with no passing test titled with its id. API7 declares coveredBy and points to lesson 15.

The gate needs no database. appForAudit builds the real app with a pool that throws on any use, so the route table is real and the check takes ≈0.4 s here. To show it working, we plant a route with neither a policy nor an isolation test:

import type { OpenApiDoc } from "./inventory.ts";
import type { Policy } from "./policy.ts";

export type Problem = { route: string; rule: string };

export type AuditInput = {
  app: Express;
  policy: Record<string, Policy>;
  isolationCases: Record<string, unknown>;
  openapi: OpenApiDoc;
};

// الـ gate دالة نقية: تدخل الحقيقة والـ policy، تطلع قايمة مشاكل
export function auditApi({ app, policy, isolationCases, openapi }: AuditInput): Problem[] {
  const { routes, unresolvedRouters } = mountedRoutes(app);
  const documented = documentedRoutes(openapi);
  const { undocumented, notMounted } = diffInventory(routes, documented);
  const problems: Problem[] = [];

  for (const route of routes) {
    if (!(route in policy)) problems.push({ route, rule: "no-declared-policy" });
    if (!(route in isolationCases)) problems.push({ route, rule: "no-isolation-test" });
  }
  for (const route of undocumented) problems.push({ route, rule: "not-in-openapi" });
  for (const route of notMounted) problems.push({ route, rule: "documented-but-not-mounted" });
  for (const route of Object.keys(policy)) {
    if (!routes.includes(route)) problems.push({ route, rule: "policy-for-missing-route" });
  }
  for (const doc of documented) {
    const rule = policy[doc.key];
    if (rule && (rule.access === "public") === doc.secured) {
      problems.push({ route: doc.key, rule: "openapi-auth-disagrees-with-policy" });
    }
  }
  if (unresolvedRouters > 0) {
    problems.push({ route: `(${unresolvedRouters} sub-router)`, rule: "router-not-inspectable" });
  }
  return problems;
}
// كل risk لازم يبقى له test ناجح، أو درس تاني بيغطيه بالاسم
function riskProblems(resultsFile: string): Problem[] {
  const results = JSON.parse(readFileSync(resultsFile, "utf8")) as VitestJson;
  const passed = results.testResults.flatMap((f) => f.assertionResults).filter((t) => t.status === "passed");
  return riskMap
    .filter((r) => r.proof === "tests" && !passed.some((t) => t.title.startsWith(`${r.id}:`)))
    .map((r) => ({ route: r.id, rule: "risk-has-no-passing-test" }));
}

export function runGate(app: ReturnType<typeof appForAudit>, resultsFile: string): number {
  const problems = [
    ...auditApi({ app, policy, isolationCases: routeCases, openapi: openapi as OpenApiDoc }),
    ...riskProblems(resultsFile),
  ];
  console.log(`security gate: ${routeKeys.length} declared routes, ${riskMap.length} risks`);
  for (const p of problems) console.log(`FAIL  ${p.rule.padEnd(28)} ${p.route}`);
  console.log(problems.length === 0 ? "gate passed" : `gate failed: ${problems.length} problem(s)`);
  return problems.length === 0 ? 0 : 1;
}

بالعامية

كل الـ controls اللي فاتت ممكن الـ route الجاي يتخطاها. الـ compiler بيحمي الـ routes اللي بتعدّي من route() بس، أما app.get العادية عمرها ما بتقابله. الـ gate بيقفل الثغرة دي: بيبص على اللي مركّب فعلًا ويرفض أي حاجة مش معلنة.

الـ gate دالة نقية على 4 حقايق: الـ routes اللي Express راكبها، وجدول الـ policy، وجدول الـ isolation cases، والـ OpenAPI. بترجّع قايمة مشاكل، وده اللي بيخلي اختبار الـ gate نفسه سهل. القواعد:

  • no-declared-policy: route مركّب ومالوش سطر في الـ policy.
  • no-isolation-test: route مركّب ومالوش case في الجدول، فالـ matrix مش هتقدر تولّدله tests.
  • not-in-openapi وdocumented-but-not-mounted: الـ inventory diff من الجزء 5 في الاتجاهين.
  • policy-for-missing-route: سطر policy والـ route بتاعه اختفى.
  • openapi-auth-disagrees-with-policy: الـ document بيقول public والـ policy بتقول protected، أو العكس.
  • router-not-inspectable: sub-router الـ gate مش قادر يقراه، بيتبلغ عنه بدل ما يتعدّى.
  • risk-has-no-passing-test: risk في خريطة الجزء 1 مالوش test ناجح عنوانه بالـ id بتاعه. الـ API7 معلن coveredBy وبيشاور على الدرس 15.

الـ gate مش محتاج DB. appForAudit بيبني الـ app الحقيقي بـ pool بيرمي error عند أي استخدام، فجدول الـ routes حقيقي والفحص بياخد ≈0.4 ثانية هنا. وعشان نوريه شغال، زرعنا route من غير policy ومن غير isolation test، والـ output فوق بيوضح الـ 3 مشاكل والـ exit code 1.

والـ workflow فوق اتفحص بـ @action-validator/core على schema الـ GitHub Actions وطلع 0 errors. متشغّلش هنا: runner بتاع GitHub، يعني الـ job نفسه متنفذش. وعلى runner حقيقي، الـ harness هيشاور على Postgres service container بدل الـ binaries المحلية (الدرس 28 والدرس 4).

فين هستخدمه في شغلي؟ لما junior يضيف app.get("/admin/export", ...) في PR يوم الخميس: الـ CI يقع فورًا برسالة واضحة، بدل ما تكتشفها أنت في review زحمة. وبدل ما تقول "فيه route من غير auth"، الـ gate بيحدد القاعدة اللي اتكسرت. ولما تضيف ده على repo قديم، هتلاقي routes قديمة كتير فاشلة: اعمل allowlist مؤقتة بتاريخ انتهاء وصفّرها route route بدل ما تستنى كله يبقى نضيف.
Trade-off: friction is the point, within reason Every new route now needs three declarations: a policy line, an isolation case and an OpenAPI entry. That's intended, because the question "who may call this?" gets answered before merge. Generate the OpenAPI document from the route table if the third one becomes noise. Keep the one escape hatch visible: access: "public" with a written reason, reviewed in the PR, and no bypass flag.
الموازنة: الاحتكاك مقصود، بس بحدود: كل route جديد بقى محتاج 3 إعلانات: سطر policy، و isolation case، وسطر OpenAPI. ده مقصود، لأن سؤال "مين يقدر ينادي ده؟" بيتجاوب قبل الـ merge. ولّد الـ OpenAPI من جدول الـ routes لو التالتة بقت مزعجة. وخلّي مخرج الطوارئ الوحيد ظاهر: access: "public" ومعاه reason مكتوب بيتراجع في الـ PR، ومن غير flag للتخطي.
What the gate doesn't prove It proves that every route was declared and that the declared controls are tested. It can't tell whether a declaration is right: a route marked public by mistake passes. SAST (lesson 21), DAST and pentests (lesson 22) and a human reading the policy diff still do their own jobs.
اللي الـ gate مش بيثبته: هو بيثبت إن كل route معلن وإن الـ controls المعلنة ليها tests. لكن مش بيعرف الإعلان نفسه صح ولا لأ: route متعلم public بالغلط هيعدّي. الـ SAST (الدرس 21) والـ DAST والـ pentests (الدرس 22) وبني آدم بيقرا الـ diff بتاع الـ policy، كلهم لسه ليهم شغلهم.

Cheat sheet · الخلاصة

  • Use the API:2023 names: API3 BOPLA merges excessive data exposure and mass assignment; API6 business flows, API7 SSRF and API10 unsafe consumption are new; injection and logging left this list but stay in the general Top 10.
  • Every risk gets a control and a test that proves it, in a map that CI can read.
  • Objects: repositories take the actor as a required argument, so an unscoped load can't be written by accident.
  • Functions: one policy table, one route() that mounts handlers, and a generated route × role matrix.
  • 401 unknown caller, 403 forbidden function, 404 someone else's object, with a body identical to a missing one.
  • Properties: z.object for responses (drops extras), z.strictObject for requests (rejects extras), and column-level grants below them.
  • Resources: clamp page size in the schema, limit the body, set HTTP timeouts and statement_timeout. Measured here: a 200,000-row page added 293 MB, against 2 MB for 100 rows.
  • Business flows: the rule goes in the transaction that changes the stock, with the row locked, and a parallel test proves it.
  • Inventory: diff the mounted routes against OpenAPI in both directions.
  • Partners: schema, timeout, byte cap, no redirects, no connection held, your own 502 or 504.
  • Tenants: a generated matrix with canaries and a row fingerprint, run with RLS on and with a bypass role, plus direct RLS tests. RLS only works for a non-superuser with FORCE.
  • CI gate: fail on any route without a policy, an isolation test or an OpenAPI entry, and check that the gate can fail.
