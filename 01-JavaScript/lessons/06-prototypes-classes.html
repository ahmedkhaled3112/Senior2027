Why this matters · ليه ده مهم

English

Every class you write, every instanceof in your error middleware, every Object.freeze(config) and every JSON.stringify that mysteriously dropped a field goes through the machinery in this lesson. When you don't know it, these show up as production mysteries: logs printing {} for an Error, err instanceof PaymentError being false because two copies of a package got installed, a "frozen" config that someone still changed, a TS private field appearing in an API response, a client crashing your endpoint with {"hasOwnProperty": 1}.

It's also interview gold: "what does new do?", "prototype vs __proto__?", "are classes just sugar?". This lesson builds new and instanceof by hand so you can answer those from understanding, and measures the memory cost that explains why methods live on the prototype.

Running the examples: node file.ts in a folder with "type": "module", on Node 22.19. The constructor-function examples are plain .mjs, because TypeScript refuses new on a function (TS7009). You'll read that style in older code and rarely write it.

بالعامية

أي class بتكتبه، وأي instanceof في الـ error middleware، وأي Object.freeze(config)، وأي JSON.stringify شال field من غير ما تعرف ليه، كلهم بيعدّوا على اللي في الدرس ده. ولما متبقاش عارفه، بيظهروا كمصايب غريبة في production: لوجز بتطبع {} بدل الـ Error، وerr instanceof PaymentError بترجع false عشان نسختين من نفس الـ package اتسطبوا، و config "متجمّد" حد لسه قادر يغيّره، و field مكتوب عليه TS private طالع في API response، و client بيوقّع الـ endpoint بتاعك بـ {"hasOwnProperty": 1}.

وكمان ده دهب في الـ interviews: "new بيعمل إيه؟"، "الفرق بين prototype و __proto__؟"، "الـ classes مجرد sugar؟". الدرس ده بيخليك تبني new و instanceof بإيدك عشان تجاوب عن فهم، وبيقيس تكلفة الـ memory اللي بتشرح ليه الـ methods مكانها على الـ prototype.

إزاي تشغّل الأمثلة: node file.ts في فولدر فيه "type": "module"، على Node 22.19. وأمثلة الـ constructor functions كاتبينها .mjs عادي، لأن TypeScript بيرفض new على function (TS7009). الأسلوب ده هتقراه في كود قديم ونادرًا ما هتكتبه.

Part 1 — Property descriptors, getters & setters 🟡 Intermediateالجزء 1 — الـ property descriptors والـ getters والـ setters

English

A property is more than a name and a value. Each one has a descriptor. A data property has value and writable; an accessor property has get and set instead. Both have enumerable and configurable. Read them with Object.getOwnPropertyDescriptor and set them with Object.defineProperty.

The trap is the defaults: a normal assignment gives you all true, while defineProperty gives you all false. configurable: false is one-way: you can't delete the property or change its flags, except that writable may still go from true to false.

Non-enumerable fields are hidden from JSON.stringify, Object.keys and spread, but they are still readable, so this is hiding, not security. It explains a bug everyone hits once: message and stack on an Error are own but non-enumerable, so JSON.stringify(err) prints {}.

Getters and setters run a function behind property syntax. A getter in an object literal is own and enumerable, so it shows up in JSON. A getter in a class lives on the prototype, so JSON.stringify doesn't see it, and you need toJSON(). Spread reads the getter once and stores the value, so the copy is no longer live. A setter is a single place for validation and normalization.

The expensive getter. cart.total looks like a cheap field, so people use it in comparators and templates. Sorting 10,000 carts of 200 items called the getter 237,174 times and walked 47 million items (≈ 100 ms); computing each total once first took 2 million items (≈ 12 ms). If a getter does real work, make it a method named calculateTotal() so the cost is visible at the call site, or cache it with a self-replacing lazy getter.

بالعامية

الـ property أكتر من اسم وقيمة. كل واحدة ليها descriptor. الـ data property فيها value و writable، والـ accessor property فيها get و set بدلهم. والاتنين فيهم enumerable و configurable. بتقراهم بـ Object.getOwnPropertyDescriptor وبتحطهم بـ Object.defineProperty.

الفخ في الـ defaults: الـ assignment العادي بيديك الكل true، وdefineProperty بيديك الكل false. وconfigurable: false طريق واحد: مش هتقدر تمسح الـ property ولا تغيّر الـ flags بتاعتها، إلا إن writable لسه ينفع يروح من true لـ false.

الـ fields الـ non-enumerable بتستخبى من JSON.stringify و Object.keys والـ spread، بس لسه مقرية، فده إخفاء مش أمان. وده بيشرح bug كلنا بنقع فيه مرة: message و stack في الـ Error own بس non-enumerable، فـ JSON.stringify(err) بيطبع {}.

الـ getters والـ setters بيشغّلوا function ورا شكل الـ property العادي. الـ getter في object literal بيبقى own و enumerable، فبيظهر في الـ JSON. والـ getter في class بيبقى على الـ prototype، فـ JSON.stringify مش بيشوفه، وهتحتاج toJSON(). والـ spread بيقرا الـ getter مرة ويخزن القيمة، فالنسخة مبتبقاش live. والـ setter مكان واحد للـ validation والـ normalization.

الـ getter الغالي. cart.total شكلها field رخيص، فالناس بتحطها في comparators و templates. ترتيب 10 آلاف cart كل واحدة فيها 200 item نادى الـ getter حوالي 237,174 مرة ولف على 47 مليون item (≈ 100 ms)، ولما حسبنا كل total مرة واحدة الأول بقوا 2 مليون item (≈ 12 ms). لو الـ getter بيعمل شغل حقيقي، خليه method اسمها calculateTotal() عشان التكلفة تبان في مكان النداء، أو اعمل له cache بـ lazy getter بيستبدل نفسه.

فين هستخدمه في شغلي؟ لوجز الـ errors: متعملش JSON.stringify(err)، اطبع message و stack و code بنفسك، أو سيب الـ logger يعمل ده (pino عنده serializer للـ errors). الـ response: الـ get total() في class مش هيطلع في الـ JSON لوحده، فحط toJSON(). وفي code review: الـ getter اللي بيعمل loop أو بيوصل لـ DB علامة خطر. الـ ORMs اللي فيها lazy loading (order.customer بيعمل query من ورا ضهرك) هي نفس الفكرة، ولما تحطها في loop بتبقى N+1. والغلطة الشائعة: defineProperty(obj, "x", { value: 1 }) ونسيان إن الـ property بقت read-only ومخفية.

Part 2 — freeze vs seal vs preventExtensions 🟡 Intermediateالجزء 2 — الـ freeze ضد الـ seal ضد الـ preventExtensions

English

These are three levels of lock on one object. preventExtensions stops new properties (and changing the prototype). seal adds configurable: false on everything, so no deleting either. freeze adds writable: false, so no value changes. They can't be undone.

Silent failure. Outside strict mode a blocked write does nothing and reports nothing. In strict mode it throws a TypeError. ES modules and class bodies are always strict, and TypeScript emits "use strict" when it compiles to CommonJS, so you get the error in modern code. A legacy .cjs file without "use strict" is where the silent bug still lives.

Freeze is shallow. Object.freeze({ db: { host } }) locks db's reference, but config.db.host = "x" still works. TypeScript's Readonly return type is shallow in the same way. deepFreeze below walks with Reflect.ownKeys (so it covers symbols and non-enumerable keys), reads through descriptors so it doesn't trigger getters, and uses a WeakSet so cycles don't recurse forever.

What deep freeze still can't do. Map, Set and Date keep their data in internal slots, not properties, so flags.set(…) and setFullYear(…) keep working on a frozen object. Typed arrays and Buffer with elements can't be frozen at all: they throw, which is why the function skips them. For config, use plain objects and arrays, and convert dates to strings or epoch numbers.

type DeepReadonly<T> = T extends (...args: never[]) => unknown
  ? T
  : T extends object
    ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
    : T;

function deepFreeze<T>(root: T, seen = new WeakSet<object>()): DeepReadonly<T> {
  const isObjectLike = typeof root === "object" || typeof root === "function";
  if (root === null || !isObjectLike) return root as DeepReadonly<T>;

  const target = root as object;
  // الـ seen بتحمينا من الـ cycles، والـ typed arrays والـ Buffer مش بيتجمدوا أصلًا
  if (seen.has(target) || ArrayBuffer.isView(target)) return root as DeepReadonly<T>;
  seen.add(target);

  // الـ Reflect.ownKeys بتجيب الـ symbols والـ non-enumerable كمان
  for (const key of Reflect.ownKeys(target)) {
    const descriptor = Object.getOwnPropertyDescriptor(target, key);
    // بنقرا من الـ descriptor عشان منشغلش أي getter
    if (descriptor && "value" in descriptor) deepFreeze(descriptor.value, seen);
  }
  return Object.freeze(root) as DeepReadonly<T>;
}

دول 3 مستويات قفل على object واحد. preventExtensions بيمنع properties جديدة (وتغيير الـ prototype). وseal بيزوّد configurable: false على كل حاجة، فمفيش مسح كمان. وfreeze بيزوّد writable: false، فمفيش تغيير قيم. ومفيش رجوع من أي واحد فيهم.

Part 3 — The prototype chain 🟡 Intermediateالجزء 3 — الـ prototype chain

English

Every object has an internal link, [[Prototype]], to another object or to null. Property lookup walks that chain: check the object's own properties, then its prototype, then that prototype's prototype, until there's a hit or the chain ends at null, which gives undefined. This is why every object has toString, and it is the entire inheritance mechanism in JavaScript. Classes are built on it.

prototype vs __proto__ are two different things. prototype is an ordinary property that exists on functions, not on instances: the object new will use as the new instance's [[Prototype]]. __proto__ is a legacy accessor inherited from Object.prototype that reads or writes an object's [[Prototype]]. In your code use Object.getPrototypeOf and Object.create. Because __proto__ lives on Object.prototype, objects from Object.create(null) don't have it, which is what makes them safe dictionaries (CS lesson 04).

Shadowing. Reads walk the chain; writes don't. tenant.taxRate = 0.1 creates an own property that hides the inherited one, and deleting it brings the inherited value back. There are two exceptions: if the inherited property is non-writable the write fails, and if it's an inherited setter the setter runs instead. Changing something nested (tenantB.limits.maxOrders = 5) isn't shadowing at all: it reads limits through the chain and then mutates the object every tenant shares. for...in also walks the chain, while Object.keys doesn't.

Why methods live on the prototype. One function object is shared by every instance. Measured with --expose-gc on 1,000,000 orders with 3 methods: 48 bytes per order with methods on the prototype, 240 with methods in a literal, and 280 with arrow class fields. That's ≈ 46 MB vs ≈ 229 MB vs ≈ 267 MB, 5 to 6 times the memory, and creating them was slower too. The lookup itself is cheap because of inline caches, which lesson 18 covers.

function chainOf(value) {
  const names = [];
  for (let proto = Object.getPrototypeOf(value); proto !== null; proto = Object.getPrototypeOf(proto)) {
    names.push(proto === Object.prototype ? "Object.prototype" : (proto.constructor?.name ?? "?") + ".prototype");
  }
  return names.concat("null").join(" → ");
}

بالعامية

كل object ليه link داخلي، [[Prototype]]، لـ object تاني أو لـ null. والـ property lookup بيمشي على الـ chain دي: يدور في الـ own properties، وبعدين في الـ prototype، وبعدين في الـ prototype بتاع الـ prototype، لحد ما يلاقي أو الـ chain تخلص عند null، فيرجّع undefined. وعشان كده كل object عنده toString، وده كل نظام الوراثة في JavaScript، والـ classes مبنية فوقه.

الـ prototype ضد الـ __proto__ حاجتين مختلفين. prototype property عادية موجودة على الـ functions، مش على الـ instances: هي الـ object اللي new هيحطه كـ [[Prototype]] للـ instance الجديد. أما __proto__ فـ accessor قديم موروث من Object.prototype بيقرا أو يكتب الـ [[Prototype]] بتاع الـ object. وفي الكود بتاعك استخدم Object.getPrototypeOf و Object.create. ولأن __proto__ عايش على Object.prototype، الـ objects اللي من Object.create(null) معندهاش، وده اللي بيخليها dictionaries آمنة (درس CS رقم 04).

الـ shadowing. القراية بتمشي على الـ chain، والكتابة لأ. tenant.taxRate = 0.1 بتعمل own property بتغطي الموروثة، ولو مسحتها الموروثة بترجع تبان. وفيه استثناءين: لو الموروثة non-writable الكتابة بتفشل، ولو الموروثة setter الـ setter هو اللي بيشتغل. أما تغيير حاجة nested (tenantB.limits.maxOrders = 5) فده مش shadowing خالص: ده بيقرا limits من الـ chain وبعدين بيعدّل الـ object اللي كل الـ tenants شايلينه. وfor...in بيمشي على الـ chain كمان، وObject.keys لأ.

ليه الـ methods مكانها على الـ prototype. عشان function object واحد يتشارك بين كل الـ instances. قسنا بـ --expose-gc على مليون order فيهم 3 methods: 48 byte لكل order لما الـ methods على الـ prototype، و240 لما تكون جوه literal، و280 مع arrow class fields. يعني ≈ 46 MB ضد ≈ 229 MB ضد ≈ 267 MB، من 5 لـ 6 أضعاف الـ memory، وإنشاءهم كان أبطأ كمان. والـ lookup نفسه رخيص بسبب الـ inline caches، ودرس 18 بيغطيها.

فين هستخدمه في شغلي؟ لما تشوف x.foo is not a function أو property طالعة من مكان مش متوقع، بتمشي على الـ chain في الـ debugger ([[Prototype]] في الـ DevTools) بدل ما تخمن. ولما تعمل حاجة بكميات: 500 ألف row بتتحول لـ objects في job واحد، الـ methods في class على الـ prototype مش arrow fields ولا factory بترجّع closures. وفي الـ code review: for...in على object جاي من بره بيجيب الموروث كمان، فاستخدم Object.keys. والغلطة الشائعة: Object.create(defaults) وتعديل tenant.limits.x وإنت فاكر إنك بتعدّل الـ tenant ده بس.
Trade-off: when memory per instance doesn't matter The extra 192 bytes matter when you have a million objects. For 1,000 objects it's about 192 KB, and for a singleton service it's nothing. A factory returning a literal with closures gives you real privacy and no this problems, so it's a fine choice for services. Choose by instance count, not by dogma.
الـ trade-off: إمتى الـ memory لكل instance مش مهمة. الـ 192 byte الزيادة بتفرق لما يبقى عندك مليون object. أما لـ 1000 object فهما حوالي 192 KB، ولـ service واحدة (singleton) مفيش فرق يتحس. والـ factory اللي بترجّع literal فيه closures بتديك privacy حقيقية ومفيش مشاكل this، فاختيار كويس للـ services. اختار حسب عدد الـ instances، مش حسب العقيدة.
Interview question "What's the difference between prototype and __proto__?" → prototype is a property on a function: it's the object that becomes the [[Prototype]] of instances created with new. __proto__ is an accessor on every ordinary object that exposes that object's own [[Prototype]]. So new Order().__proto__ === Order.prototype. In real code use Object.getPrototypeOf.

Part 4 — Constructor functions, new & instanceof 🟡 Intermediateالجزء 4 — الـ constructor functions والـ new والـ instanceof

English

new Ctor(args) does four things: (1) creates a new empty object, (2) sets its [[Prototype]] to Ctor.prototype, (3) runs Ctor with this bound to the new object, and (4) returns what the constructor returned if that's an object, otherwise the new object. myNew below is exactly those steps and behaves like real new for constructor functions. It can't work with class, because class constructors refuse to run without new; Reflect.construct is the official dynamic form. Forgetting new on a plain function throws in strict mode and, in sloppy mode, writes to the global object, which is one reason classes refuse the call.

x instanceof C doesn't compare names or types. It walks x's chain looking for the exact object C.prototype. (It checks C[Symbol.hasInstance] first, which a class can override.) Primitives give false. Because it depends on object identity, it breaks in two real situations:

  • Realms: every vm context and iframe has its own Array and Error. Use Array.isArray. Jest runs test files in vm contexts, so this surfaces there too (jest#2549). Error.isError() is a newer realm-safe check, but it's undefined on the Node 22.19 used here, so check your runtime.
  • Duplicate packages: two versions of a package in node_modules are two different classes. Retry logic with err instanceof PaymentError silently never matches. Find it with npm ls <pkg> and fix it with npm dedupe or by making the library a peerDependency. Then make your code robust with a stable code field, which also survives serialization across a queue.

hasOwnProperty vs in. in walks the chain, so "toString" in order is true. hasOwnProperty checks only the object itself, but it's a method looked up on the object: a request body with a hasOwnProperty key, or an Object.create(null) dictionary, makes it throw. Object.hasOwn(obj, key) has neither problem and is the default today. A real use is PATCH: {"discount": null} means "clear it" and {} means "leave it", and only a presence check can tell them apart.

function myInstanceof(value: unknown, Ctor: { prototype: object | null }): boolean {
  if (value === null || (typeof value !== "object" && typeof value !== "function")) return false;
  // بنطلع في الـ chain خطوة خطوة وندور على Ctor.prototype
  for (let proto = Object.getPrototypeOf(value); proto !== null; proto = Object.getPrototypeOf(proto)) {
    if (proto === Ctor.prototype) return true;
  }
  return false;
}

Part 5 — Classes 🟡 Intermediateالجزء 5 — الـ classes

English

Sugar, mostly. class Order creates a function, methods go on Order.prototype, and instances link to it, exactly as in Part 3. The real differences: methods are non-enumerable, the class can't be called without new, the body is always strict, and you get fields, #private and super. In a derived class the object is allocated by the base constructor, which is why extends Error and extends Array work properly.

Fields are created per instance in a fixed order: base fields → base constructor body → derived fields → derived constructor body. That order creates two traps. A base constructor calling an overridden method sees the derived fields as undefined, which gives db_undefined below. And re-declaring a field in a subclass (owner: string;) creates a new field holding undefined right after super() returns, wiping the base's value. TS2612 flags it, and declare owner: … is the type-only form.

#private vs TS private. TS private is erased at compile time, so the value is visible at runtime and in JSON. #private is enforced by the language, and nothing outside the class body can reach it. It's class-level, not instance-level: other.#pin works inside the class, and #pin in value is a brand check that a faked prototype can't fool, unlike instanceof. (It still fails across duplicate package copies, because each copy is a different class.) The table lists what you trade for it.

static members live on the class itself: factories like Money.fromMajor and guards like Money.isMoney. They inherit through a second chain (Object.getPrototypeOf(EmailJob) === BaseJob), and this in a static method is the class it was called on, so EmailJob.create() builds an EmailJob. Overriding is shadowing on the chain, and super.describe() calls the parent's version. TS's override keyword with noImplicitOverride catches it when a parent method gets renamed (TS4114).

What changed from older tutorials. (1) Object.setPrototypeOf(this, new.target.prototype) in error classes was a workaround for ES5 output. TS 7 removed target: es5 (TS5108) and TS 6 deprecates it (TS5107), so delete it. (2) Error.captureStackTrace(this, new.target) is no longer needed to hide constructor frames: V8 already drops them, and the top frame below is at findOrder without it. It's still useful for hiding a helper such as assertFound. (3) Node's strip-only mode rejects parameter properties: constructor(public id: string) fails with ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX, and TS erasableSyntaxOnly flags it at compile time (TS1294). That's why these classes declare their fields by hand.

Two classes worth keeping: Money (integer minor units, immutable, static factories, and a toJSON because JSON can't see #minor) and AppError (a code and status, new.target.name for the right name, and cause passed to super). Lesson 11 goes further into error design.

export class Money {
  readonly #minor: number;
  readonly currency: string;

  constructor(minor: number, currency: string) {
    if (!Number.isSafeInteger(minor)) {
      throw new RangeError(`minor units must be a safe integer, got ${minor}`);
    }
    this.#minor = minor;
    this.currency = currency;
  }

  // الـ static factories: أسماء واضحة بدل constructor واحد بيعمل كل حاجة
  static zero(currency: string): Money {
    return new Money(0, currency);
  }
  static fromMajor(major: number, currency: string): Money {
    return new Money(Math.round(major * 100), currency);
  }
  static isMoney(value: unknown): value is Money {
    return typeof value === "object" && value !== null && #minor in value;
  }

  get minor(): number {
    return this.#minor;
  }
  get major(): number {
    return this.#minor / 100;
  }

  // كل عملية بترجّع Money جديد: الـ class ده immutable
  add(other: Money): Money {
    this.#assertSameCurrency(other);
    return new Money(this.#minor + other.#minor, this.currency);
  }
  #assertSameCurrency(other: Money): void {
    if (other.currency !== this.currency) {
      throw new TypeError(`currency mismatch: ${this.currency} vs ${other.currency}`);
    }
  }

  toString(): string {
    return `${this.major.toFixed(2)} ${this.currency}`;
  }
  // الـ JSON مش بيشوف ⁦#minor⁩، فلازم نقوله يطبع إيه
  toJSON() {
    return { amount: this.#minor, currency: this.currency };
  }
}

Part 6 — Mixins vs inheritance 🟡 Intermediateالجزء 6 — الـ mixins ضد الـ inheritance

English

A class has one parent, and cross-cutting behaviour doesn't fit in a single line: some entities need timestamps, some need soft delete, some need both. A class-factory mixin is a function that takes a base class and returns a subclass: Timestamped(Base). Stacking them just builds an ordinary prototype chain, as the printed chain shows.

The rules and gotchas:

  • TypeScript requires the constructor type to be new (...args: any[]) => T, or you get TS2545. This is one of the few places any[] is mandatory.
  • A mixin can demand things from its base, like Constructor<{ id: string; touch(): void }>.
  • Order matters, and the last one applied wins any name collision silently (exportable below).
  • instanceof doesn't work with the factory, because each call creates a new class. Check the capability instead.
  • With declaration: true, an exported mixin can't have private or #private members (TS4094). That's a real limit for libraries.

Composition is usually the better default. The class holds its collaborators instead of inheriting them: OrderService takes a repo, an audit log and a clock, and a test passes fakes with no subclassing and no module mocking.

When deep hierarchies hurt. With BaseRepository → AuditedRepository → TenantRepository → OrderRepository, needing audit without tenancy is impossible, a change in the base hits every subclass (the fragile base class problem), and reading one method means jumping through four files. The decision is in the table below: keep inheritance to one or two levels and use it for a true is-a with a shared contract.

  };
}

القواعد والحاجات اللي تاخد بالك منها:

  • الـ TypeScript بيطلب إن نوع الـ constructor يبقى new (...args: any[]) => T، وإلا هتاخد TS2545. ودي من الأماكن القليلة اللي any[] فيها إجباري.

Part 7 — Symbols 🟡 Intermediateالجزء 7 — الـ symbols

English

Symbol() creates a unique primitive, and the description is only a label. As a property key it can't collide with any string key or any other symbol, so a library can attach data to your object with no risk of a clash. It is not private: Object.getOwnPropertySymbols and Reflect.ownKeys find it. There's no implicit conversion to string either, so `${sym}` throws; use String(sym) or sym.description.

Symbol.for(key) reads a registry shared by every module and vm context on the thread. That's how two copies of a library can recognise each other's objects, which plain Symbol() and instanceof can't do (Part 4). Node's own util.inspect.custom is Symbol.for("nodejs.util.inspect.custom"), and EventEmitter keeps internal state under symbol keys.

Well-known symbols are hooks the language looks up on your objects:

  • Symbol.iterator powers for...of, spread and array destructuring.
  • Symbol.toPrimitive controls conversion, with a hint of "number" (+x, x > y), "string" (template literals) or "default" (x + y).
  • Symbol.asyncIterator powers for await. In the demo, breaking after two orders made 1 request instead of 3.
  • Others: Symbol.hasInstance (custom instanceof) and Symbol.toStringTag. Symbol.dispose exists on Node 22.19, but the using syntax is still a SyntaxError there.

The depth lives elsewhere: iterators and generators in lesson 07, async iterators in lesson 10, and toPrimitive in lesson 17.

A metadata key that can't clash. A queue library needs an attempts counter on a job, but the user's payload may have its own attempts. A symbol key solves that, and it also stays out of the JSON sent to the queue. It has limits: spread copies it, structuredClone drops it, and it can't be added to a frozen object. When any of those matter, use a WeakMap, which doesn't touch the object at all.

Symbol() بيعمل primitive فريد، والوصف مجرد label. ولما تستخدمه كـ property key مش ممكن يتصادم مع أي string key ولا أي symbol تاني، فالمكتبة تقدر تعلّق data على الـ object بتاعك من غير خوف من تصادم. بس هو مش private: Object.getOwnPropertySymbols و Reflect.ownKeys بيلاقوه. وكمان مفيش تحويل ضمني لـ string، فـ `${sym}` بترمي error، فاستخدم String(sym) أو sym.description.

Symbol.for(key) بيقرا من registry مشتركة بين كل الـ modules والـ vm contexts على نفس الـ thread. وكده نسختين من مكتبة يقدروا يعرفوا الـ objects بتاعة بعض، وده اللي Symbol() العادي و instanceof مش بيعرفوا يعملوه (الجزء 4). والـ util.inspect.custom بتاع Node نفسه هو Symbol.for("nodejs.util.inspect.custom")، والـ EventEmitter بيشيل internal state تحت symbol keys.

الـ well-known symbols عبارة عن hooks اللغة بتدور عليها في الـ objects بتاعتك:

  • Symbol.iterator هو اللي بيشغّل for...of والـ spread والـ array destructuring.
  • Symbol.toPrimitive بيتحكم في التحويل، ومعاه hint: "number" (+x و x > y)، أو "string" (الـ template literals)، أو "default" (x + y).
  • Symbol.asyncIterator هو اللي بيشغّل for await. وفي الـ demo، الـ break بعد 2 orders عمل request واحد بدل 3.
  • وغيرهم: Symbol.hasInstance (لـ instanceof custom) و Symbol.toStringTag. وSymbol.dispose موجود على Node 22.19، بس الـ syntax بتاع using لسه SyntaxError هناك.

والعمق في دروس تانية: الـ iterators والـ generators في درس 07، والـ async iterators في درس 10، وtoPrimitive في درس 17.

metadata key مبيتصادمش. مكتبة queue محتاجة عدّاد attempts على الـ job، بس الـ payload بتاع اليوزر ممكن يكون فيه attempts بتاعته. الـ symbol key بيحل ده، وكمان مش بيدخل في الـ JSON اللي بيروح للـ queue. وليه حدود: الـ spread بينسخه، وstructuredClone بيشيله، ومينفعش يتضاف على frozen object. ولما أي حاجة من دول تفرق، استخدم WeakMap، لأنه مش بيلمس الـ object خالص.

Symbol.iterator: class Cart شايل items في #items ومع ذلك for...of و spread شغالين عليه. type PropertyKind = "own data" | "own accessor" | "inherited" | "missing";

function describeProperty(obj: object, key: PropertyKey): PropertyKind {
  const own = Object.getOwnPropertyDescriptor(obj, key);
  if (own) return "value" in own ? "own data" : "own accessor";
  return key in obj ? "inherited" : "missing";
}

Solution · الحل 
function defineLazy<T extends object, K extends string, V>(
  obj: T,
  key: K,
  compute: () => V,
): T & Readonly<Record<K, V>> {
  Object.defineProperty(obj, key, {
    configurable: true,
    enumerable: true,
    get() {
      const value = compute();
      // أول قراية: بنبدّل الـ getter بقيمة ثابتة
      Object.defineProperty(obj, key, { value, enumerable: true, writable: false });
      return value;
    },
  });
  return obj as T & Readonly<Record<K, V>>;
}

  runs++;
  return { orders: 120, revenue: 45000 };

type Line = { sku: string; qty: number; unitMinor: number };

class Invoice {
  #lines: Line[] = [];
  readonly id: string;

  constructor(id: string) {
    this.id = id;
  }

  addLine(line: Line): this {
    if (!Number.isInteger(line.qty) || line.qty <= 0) {
      throw new RangeError(`invalid qty for ${line.sku}: ${line.qty}`);
    }
    this.#lines.push({ ...line });
    return this;
  }

  get total(): number {
    return this.#lines.reduce((sum, line) => sum + line.qty * line.unitMinor, 0);
  }

  [Symbol.iterator](): IterableIterator<Readonly<Line>> {
    return this.#lines.values();
  }

  [Symbol.toPrimitive](hint: "number" | "string" | "default"): number | string {
    return hint === "number" ? this.total : `${this.id}: ${(this.total / 100).toFixed(2)} EGP`;
  }

  toJSON() {
    return { id: this.id, total: this.total, lines: this.#lines };
  }
}

// (2) الـ errors: class أساسي واحد وأكواد ثابتة
class AppError extends Error {
  readonly code: string;
  readonly status: number;
  constructor(message: string, code: string, status: number, cause?: unknown) {
    super(message, { cause });
    this.name = new.target.name;
    this.code = code;
    this.status = status;
  }
}
class NotFoundError extends AppError {
  constructor(resource: string, id: string) {
    super(`${resource} ${id} not found`, "NOT_FOUND", 404);
  }
}

// الـ error middleware بيفرّق بالـ code مش بالـ instanceof بس
const isAppError = (err: unknown): err is AppError =>
  err instanceof Error && typeof (err as AppError).code === "string";

function toResponse(err: unknown) {
  return isAppError(err)
    ? { status: err.status, body: { code: err.code, message: err.message } }
    : { status: 500, body: { code: "INTERNAL", message: "Something went wrong" } };
}

// → { status: 404, body: { code: 'NOT_FOUND', message: 'order ord_9 not found' } }

// → { status: 500, body: { code: 'INTERNAL', message: 'Something went wrong' } }

Cheat sheet · الخلاصة

  • Descriptors: writable, enumerable, configurable. Assignment makes them true; defineProperty makes them false. Non-enumerable means hidden, not secure.
  • JSON.stringify(err) is {} because message and stack are non-enumerable. A class getter is on the prototype, so it needs toJSON.
  • A getter runs on every read. Real work goes in a named method or a self-replacing lazy getter.
  • preventExtensions < seal < freeze. All shallow. Silent in sloppy mode, TypeError in ESM. Map and Date stay mutable.
  • Lookup: own → prototype → … → null. Reads walk the chain, writes shadow, nested mutation hits the shared object.
  • prototype is on functions; __proto__ exposes an object's link. Use Object.getPrototypeOf and Object.create.
  • Methods on the prototype: 48 bytes per order vs 240–280 per instance copies. It matters at a million objects, not at a thousand.
  • new: create, link, run, return. instanceof walks the chain by identity, so it breaks across realms and duplicate packages. Prefer a stable code.
  • Object.hasOwn over hasOwnProperty. in includes inherited keys.
  • Class order: base fields, base constructor, derived fields, derived constructor. Don't call overridable methods from a constructor. #private is real; TS private is erased.
  • Inheritance for a true is-a, 1–2 levels. Mixins for small independent behaviour. Composition for anything external. Functions when there's no state.
  • Symbols give non-collision, not privacy. iterator → for...of, toPrimitive → conversions, asyncIterator → for await. Symbol.for is shared across modules and realms.
بالعامية
  • الـ descriptors: writable و enumerable و configurable. الـ assignment بيخليهم true، وdefineProperty بيخليهم false. والـ non-enumerable معناها مخفية مش آمنة.
  • JSON.stringify(err) بيطلع {} لأن message و stack non-enumerable. والـ getter في class على الـ prototype، فمحتاج toJSON.
  • الـ getter بيشتغل مع كل قراية. الشغل الحقيقي مكانه method ليها اسم أو lazy getter بيستبدل نفسه.
  • preventExtensions أقل من seal أقل من freeze. والتلاتة سطحيين. وصامتين في الـ sloppy mode، وTypeError في الـ ESM. والـ Map والـ Date بيفضلوا بيتعدّلوا.
  • الـ lookup: own ثم prototype ثم … لحد null. القراية بتمشي على الـ chain، والكتابة بتعمل shadow، والتعديل الـ nested بيخبط في الـ object المشترك.
  • prototype على الـ functions، و__proto__ بيوريك الـ link بتاع الـ object. استخدم Object.getPrototypeOf و Object.create.
  • الـ methods على الـ prototype: 48 byte لكل order ضد 240–280 لو كل instance معاه نسخته. ده بيفرق عند مليون object، مش عند 1000.
  • new: اعمل، اربط، شغّل، رجّع. وinstanceof بيمشي على الـ chain بالهوية، فبيكسر بين الـ realms والـ packages المتكررة. استخدم code ثابت.
  • Object.hasOwn بدل hasOwnProperty. وin بيشمل الـ keys الموروثة.
  • ترتيب الـ class: fields الأب، constructor الأب، fields الابن، constructor الابن. متناديش methods ممكن يتعملها override من constructor. و#private حقيقي، و TS private بيتشال.
  • الـ inheritance لـ is-a حقيقية في level أو اتنين. والـ mixins لسلوك صغير مستقل. والـ composition لأي حاجة خارجية. والـ functions لما مفيش state.
  • الـ symbols بتديك عدم تصادم مش خصوصية. iterator لـ for...of، وtoPrimitive للتحويلات، وasyncIterator لـ for await. وSymbol.for مشترك بين الـ modules والـ realms.
