Why this matters · ليه ده مهم

English

This is the async code you write every day, on top of the event loop from lesson 08. A handler that calls ten services one at a time takes ten times longer than it needs to. One Promise.all over an optional service turns a dead recommendations widget into a 500 on the whole order page. One forgotten await crashes the process, and every request running on it dies too. These bugs pass code review because the code reads fine. They are also standard interview material: "write Promise.all by hand", "what's wrong with forEach(async …)", "debounce or throttle?".

بالعامية

ده الـ async code اللي بتكتبه كل يوم، فوق الـ event loop اللي في درس 08. handler بينادي 10 services واحد ورا التاني بياخد 10 أضعاف الوقت اللي محتاجه. Promise.all واحدة على service اختياري بتحوّل widget الـ recommendations الواقع لـ 500 على صفحة الأوردر كلها. وawait واحدة ناسيها بتوقّع الـ process، وكل الـ requests اللي شغالة عليه بتموت معاه. الـ bugs دي بتعدّي من الـ code review لأن الكود شكله سليم. وهي كمان أسئلة interview ثابتة: "اكتب Promise.all بإيدك"، "إيه الغلط في forEach(async …)"، "debounce ولا throttle؟".

Part 1 — Promise combinators, by hand 🟡 Intermediateالجزء 1 — الـ Promise combinators، بإيدك

English

All four take an iterable of promises (or plain values) and return one promise. None of them starts anything and none of them cancels anything. Calling an async function is what starts the work, so by the time a combinator receives the promises, the work is already running. A combinator only decides when you stop waiting and what you get back. The real difference between them is how they treat failure, which the table below lays out.

An order page usually needs more than one of them. The order and the customer are required: without them there is no page. Tracking is optional: without it the page still works. Putting all three in one Promise.all gives you a 500 whenever tracking is down, so split them by how much you need each one.

Writing them by hand comes down to five details. Store each result by index, because push gives you completion order instead of input order. Count completions, because results.length lies: assigning results[2] first makes the length 3 while two slots are still empty. Wrap each input in Promise.resolve so plain values and thenables work. Handle the empty input explicitly, since no callback will ever run. And iterate inside the executor, so an iterator that throws becomes a rejection instead of a synchronous throw.

The tests run every scenario on the native combinator and on ours, then compare the results. That differential style found a real bug in my first draft: myAllSettled called Array.from(values) outside any executor, so a throwing iterator threw synchronously while the native one rejected. Wrapping the iteration in a generator fixed it, which is why that generator is there.

async function loadPageAllOrNothing(id: string) {
  const [order, customer, tracking] = await Promise.all([
    fetchOrder(id),
    fetchCustomer(id),
    fetchTracking(id),

  return { order, customer, tracking };

async function loadPage(id: string) {
  const [[order, customer], [tracking]] = await Promise.all([
    Promise.all([fetchOrder(id), fetchCustomer(id)]),
    Promise.allSettled([fetchTracking(id)]),
  ]);
  return {
    order,
    customer,
    // الصفحة بترجع degraded بدل ما تقع، والـ frontend بيعرض "التتبع مش متاح"
    tracking: tracking.status === "fulfilled" ? tracking.value : null,

// مع race: الاستخدام الكلاسيكي timeout، وأول واحد يخلص (حتى لو فشل) بيكسب
function withTimeout<T>(work: Promise<T>, ms: number): Promise<T> {
  let timer!: NodeJS.Timeout;
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error(`timed out after ${ms}ms`)), ms);
  });
  // لازم clearTimeout: وإلا الـ timer بيفضل حاجز الـ process لحد ما يخلص
  return Promise.race([work, timeout]).finally(() => clearTimeout(timer));
}

  console.log("race         ->", err.message);
});

// الأربعة combinators بإيدك: نفس الـ semantics بتاعة الـ native، والـ tests بتقارنهم بيها
type Input<T> = Iterable<T | PromiseLike<T>>;

export function myAll<T>(values: Input<T>): Promise<Awaited<T>[]> {
  return new Promise((resolve, reject) => {
    const results: Awaited<T>[] = [];
    let total = 0;
    let fulfilled = 0;
    for (const value of values) {
      const index = total++;
      // الـ Promise.resolve عشان القيم العادية والـ thenables يتعاملوا زي الـ promises
      Promise.resolve(value).then((v) => {
        // (1) بنكتب في الـ index مش push: الترتيب بتاع الـ input مش بتاع مين خلص الأول
        results[index] = v;
        // (2) بنعدّ اللي خلص، لأن results.length كدابة لو آخر عنصر خلص الأول
        if (++fulfilled === total) resolve(results);
        // (3) أول rejection بيقفل الـ promise، وأي resolve أو reject بعده بيتجاهل
      }, reject);
    }
    // (4) الـ input الفاضي: مفيش then هتجري خالص، فلازم نقفلها هنا
    if (total === 0) resolve(results);
  });
}

export function myAllSettled<T>(values: Input<T>): Promise<PromiseSettledResult<Awaited<T>>[]> {
  // الفكرة: كل عنصر بيتحوّل لـ promise مبترفضش أبدًا، وبعدين myAll عادي
  // والـ generator هنا مقصود: الـ iteration تحصل جوه executor بتاع myAll، فلو الـ iterator رمى تبقى rejection
  function* wrapped() {
    for (const value of values) {
      yield Promise.resolve(value).then(
        (v): PromiseSettledResult<Awaited<T>> => ({ status: "fulfilled", value: v }),
        (reason: unknown): PromiseSettledResult<Awaited<T>> => ({ status: "rejected", reason }),
      );
    }
  }
  return myAll(wrapped());
}

export function myRace<T>(values: Input<T>): Promise<Awaited<T>> {
  return new Promise((resolve, reject) => {
    // أول واحد يخلص (نجاح أو فشل) بيقفلها. والـ input الفاضي بيفضل pending للأبد
    for (const value of values) Promise.resolve(value).then(resolve, reject);
  });
}

export function myAny<T>(values: Input<T>): Promise<Awaited<T>> {
  return new Promise((resolve, reject) => {
    const errors: unknown[] = [];
    let total = 0;
    let rejected = 0;
    const failAll = () => reject(new AggregateError(errors, "All promises were rejected"));
    for (const value of values) {
      const index = total++;
      Promise.resolve(value).then(resolve, (reason: unknown) => {
        // الأخطاء بترتيب الـ input برضه، مش بترتيب الوقوع
        errors[index] = reason;
        if (++rejected === total) failAll();
      });
    }
    // الـ input الفاضي بيترفض فورًا بـ AggregateError: مفيش حد ينجح
    if (total === 0) failAll();
  });
}

// شغّله كده node --test test/combinators.test.ts
import { describe, it } from "node:test";
import assert from "node:assert/strict";
import { myAll, myAllSettled, myAny, myRace } from "../src/combinators.ts";

// بنتحكم في ترتيب الـ settle بإيدنا بدل setTimeout: مفيش flakiness تحت الضغط
function deferred<T>() {
  let resolve!: (value: T) => void;
  let reject!: (reason: unknown) => void;
  const promise = new Promise<T>((res, rej) => { resolve = res; reject = rej; });
  return { promise, resolve, reject };
}

// كل scenario بيتشغّل على الـ native وعلى النسخة بتاعتنا، ولازم النتيجة تطابق
const outcome = async (p: Promise<unknown>) => {
  try {
    return { ok: await p };
  } catch (err) {
    const e = err as Error & { errors?: unknown[] };
    return { failed: e.constructor.name, message: e.message, errors: e.errors };
  }
};
const PENDING = Symbol("pending");
const stillPending = (p: Promise<unknown>) =>
  Promise.race([p, new Promise((r) => setTimeout(r, 20, PENDING))]);

const pairs: Record<string, [Combinator, Combinator]> = {
  all: [(v) => Promise.all(v), myAll],
  allSettled: [(v) => Promise.allSettled(v), myAllSettled],
  race: [(v) => Promise.race(v), myRace],
  any: [(v) => Promise.any(v), myAny],

for (const [name, [native, mine]] of Object.entries(pairs)) {
  describe(`${name}: same behaviour as native`, () => {
    const same = async (scenario: (combinator: Combinator) => Promise<unknown>) => {
      const [a, b] = [await scenario(native), await scenario(mine)];
      assert.deepEqual(b, a);
    };

        first.resolve("first");

بالعامية

الأربعة بياخدوا iterable من promises (أو قيم عادية) وبيرجعوا promise واحدة. ولا واحدة فيهم بتبدأ حاجة، ولا واحدة بتلغي حاجة. اللي بيبدأ الشغل هو نداء الـ async function نفسها، فلما الـ combinator يستلم الـ promises بيكون الشغل ماشي خلاص. الـ combinator بس بيقرر هتبطل تستنى إمتى وهيرجعلك إيه. والفرق الحقيقي بينهم هو بيتعاملوا مع الفشل إزاي، وده اللي في الجدول فوق.

صفحة الأوردر عادةً محتاجة أكتر من واحد فيهم. الـ order والـ customer required: من غيرهم مفيش صفحة. الـ tracking اختياري: من غيره الصفحة شغالة. لو حطيت التلاتة في Promise.all واحدة هتاخد 500 كل ما الـ tracking يقع، فقسّمهم حسب احتياجك لكل واحد.

لما تكتبهم بإيدك فيه 5 تفاصيل بس: خزّن كل نتيجة بالـ index، لأن push بيديك ترتيب الانتهاء مش ترتيب الـ input. عدّ اللي خلص، لأن results.length كدابة: لو كتبت results[2] الأول الطول بيبقى 3 واتنين من الخانات لسه فاضيين. لف كل input في Promise.resolve عشان القيم العادية والـ thenables يشتغلوا. اتعامل مع الـ input الفاضي صراحةً، لأن مفيش callback هيجري أصلًا. ولف على الـ iterable جوه الـ executor، عشان iterator بيرمي يبقى rejection مش throw sync.

الـ tests بتشغّل كل scenario على الـ native وعلى نسختنا وبتقارن. الأسلوب ده (differential testing) مسك bug حقيقي في أول نسخة كتبتها: myAllSettled كانت بتنده Array.from(values) بره أي executor، فالـ iterator اللي بيرمي كان بيطلع throw sync، والـ native بترفض. الحل كان إن الـ iteration تتلف في generator، وعشان كده الـ generator ده موجود في الكود.

فين هستخدمه في شغلي؟ route في Next.js أو BFF بيجمّع صفحة الأوردر: الـ order والـ customer بـ all ولو فشلوا ترد 500 أو 404، والـ tracking والـ recommendations بـ allSettled ولو فشلوا الـ frontend يعرض placeholder. وany لقراءة سعر من أكتر من replica، وrace لـ timeout بسيط. وفي job بيبعت 500 إيميل: allSettled عشان تعرف بالظبط مين فشل وتعمله retry.

Part 2 — async/await from the inside 🟡 Intermediateالجزء 2 — الـ async/await من جوه

English

Three rules cover what an async function does. It always returns a promise: a returned value gets wrapped, a returned promise gets adopted. It runs synchronously up to the first await, so the caller hasn't continued yet when that first part runs. And a throw never escapes synchronously: it becomes a rejection, so a try/catch around a call without await catches nothing.

An async function is a generator plus a small driver. await x means "pause here and resume with the result of x". The driver below is about 20 lines, and it's essentially what TypeScript emitted for async functions before ES2017. Knowing it answers most of the questions: resuming happens from a promise callback, so the code after an await is a microtask; a rejection is thrown at the await through gen.throw(), which is why plain try/catch works; and the local variables survive because a suspended generator keeps its frame.

That gives you the classic bug: return promise inside try. Without await, the function leaves the try block before the promise settles, so the rejection happens outside it and the catch never runs. return await promise keeps the function inside the try until the promise settles.

Outside a try, return and return await give the same result, but they still differ in two ways, measured below. Only return await keeps the caller in the async stack trace. It's also one microtask faster on V8 (2 ticks vs 3), because returning a native promise goes through the slower adoption path. So the old advice that return await wastes a tick is out of date. Neither number should drive your choice: pick it for correctness and for stack traces.

// الـ async function هي generator + driver بيمشيه: ده اللي الـ transpilers كانوا بيطلعوه قبل ES2017
export function run<T>(body: () => Generator<unknown, T, any>): Promise<T> {
  return new Promise((resolve, reject) => {
    const gen = body();
    const step = (method: "next" | "throw", arg?: unknown): void => {
      let result: IteratorResult<unknown, T>;
      try {
        // (1) بنشغّل الـ body لحد الـ yield الجاي، وده اللي بيقابل await
        result = gen[method](arg);
      } catch (err) {
        // (2) حصل throw من غير catch جوه الـ body، فالـ promise بتترفض
        reject(err);
        return;
      }
      // (3) وصلنا لـ return: قيمته هي قيمة الـ promise
      if (result.done) {
        resolve(result.value);
        return;
      }
      // (4) نستنى القيمة، وبعدين نرجع جوه الـ body بالنتيجة أو نرمي الخطأ عند الـ yield
      Promise.resolve(result.value).then(
        (value) => step("next", value),
        (err) => step("throw", err),
      );
    };
    step("next");
  });
}

الـ async function هي generator ومعاه driver صغير. await x معناها "وقّف هنا وارجع بنتيجة x". الـ driver اللي فوق حوالي 20 سطر، وهو تقريبًا اللي TypeScript كان بيطلّعه للـ async functions قبل ES2017. لما تعرفه هتجاوب على أغلب الأسئلة: الرجوع بيحصل من promise callback، فالكود اللي بعد await بيبقى microtask؛ الـ rejection بيترمي عند الـ await عن طريق gen.throw()، وعشان كده try/catch العادي شغال؛ والمتغيرات المحلية بتفضل عايشة لأن الـ generator الواقف محتفظ بالـ frame بتاعه.

ومن هنا الـ bug الكلاسيكي: return promise جوه try. من غير await الـ function بتخرج من الـ try قبل ما الـ promise تخلص، فالـ rejection بيحصل بره وcatch مبيجريش. return await promise بتخلي الـ function جوه الـ try لحد ما الـ promise تخلص.

بره الـ try، return وreturn await بيدّوا نفس النتيجة، بس فيه فرقين اتقاسوا فوق. return await بس هي اللي بتحافظ على الـ caller في الـ async stack trace. وهي كمان أسرع بـ microtask واحدة على V8 (تكّتين مقابل 3)، لأن رجوع native promise بيمشي في مسار الـ adoption الأبطأ. يعني النصيحة القديمة إن return await بتضيّع tick بقت قديمة. ومع كده الأرقام دي مش هي اللي تقرر: اختار على أساس الصحة والـ stack traces.

Part 3 — Sequential vs parallel 🟡 Intermediateالجزء 3 — واحد ورا التاني ولا مع بعض

English

await inside a for loop makes each call wait for the previous one. Ten calls of 100ms take about a second, while Promise.all(ids.map(fn)) takes about 100ms, a tenfold difference with no extra work on your side. The rule: if the calls don't depend on each other, start them all and then wait.

Sequential is still the right choice in three cases. Rate limits: a provider that allows a few requests per second will answer 429 to a burst (or use a concurrency limit, the middle ground in lesson 10). Ordering: each step needs the previous result or must happen after it: reserve stock, then charge, then ship. One transaction: a Postgres transaction lives on one connection, and one connection runs one query at a time, so Promise.all gains nothing. pg 8.23 also warns against it in its source: "Calling client.query() when the client is already executing a query is deprecated and will be removed in pg@9.0."

Parallel has two costs you must plan for. Fail-fast doesn't stop the others: Promise.all rejects at the first failure and your handler responds, but the other calls continue. In the demo below the client hears "request failed" while the card gets charged anyway. So never run steps in parallel if one failing must prevent another. Unbounded parallelism overloads things: Promise.all over 10,000 orders opens 10,000 requests at once and exhausts the DB pool.

There is also a trap that looks like the clean way to do parallel: start two promises and await them one after the other. If the second rejects while you're still waiting on the first, it has no handler yet, Node treats that as an unhandled rejection, and the process dies before your try/catch gets a chance. Use Promise.all, which attaches handlers to all of them immediately.

English

Floating promises. A promise with no await, no .catch and no return. If it rejects, nobody hears about it, Node emits unhandledRejection, and since Node 15 the default is to crash the process with exit code 1. The caller had already returned success, so the client got a 200 and every other request on that process dies. Handlers and exit policy belong to lesson 11. If fire-and-forget is really what you want, say so: void sendReceipt(id).catch(log).

forEach with async. forEach ignores what its callback returns, so the promises float: the loop finishes before any of the work does, and each rejection is unhandled. Use for...of for one at a time, or Promise.all(map) for all together.

Mixing callbacks and promises. Three versions show up in real code. .then(ok).catch(fail) around a callback calls it twice when the callback itself throws, since the catch also covers ok; use .then(ok, fail) or util.callbackify. An async function passed where a plain callback is expected, like an EventEmitter listener, has its promise ignored, so its rejection is unhandled; captureRejections: true routes it to the 'error' event. And new Promise(async ...): the executor's returned promise is ignored, so a throw never reaches reject and the outer promise hangs forever.

Forgetting await inside try. The same family as Part 2's bug: the call starts, the try ends, and you return 201 while the insert is about to fail. The catch never runs.

None of this needs discipline, because a linter finds all of it. @typescript-eslint/no-floating-promises, no-misused-promises, await-thenable and return-await use type information to see which expressions are promises. One tooling caveat for today: typescript-eslint 8.72 declares a peer range of typescript <6.1, so these rules run on TS 6.0.3 even if you compile with TS 7. That's how the run below was done.

English

await outside any function works in ES modules only: .mjs, "type": "module", or <script type="module">. In a .cjs file it's a SyntaxError. Node 22 also has syntax detection: a .js file in a package with no "type" field gets re-parsed as ESM when it sees top-level await, with a warning about the performance cost. TypeScript needs a suitable module setting and rejects commonjs with TS1378, shown below.

The good use: load config before anything starts. config.mjs awaits its secrets and exports the result, so no importer can ever see it half-loaded, and you don't need init() calls or null checks. A failure at that point crashes on startup, which is what you want for a server with no database URL.

How it blocks: a module with top-level await makes everything that depends on it wait, all the way up the import graph. Siblings that don't depend on it are not blocked: they run while it's waiting. The demo prints that order: sibling runs between slow: start and slow: end, dependent waits, and main runs last.

The risks. Slow start: a 5-second secrets call in a module that everything imports delays every process start by 5 seconds, including every test file, and it fails your readiness probe if it hangs, so give it a timeout. Deadlock: if a module awaits a dynamic import of something that imports it back, neither can finish. Node detects that nothing is left to run, warns "Detected unsettled top-level await" and exits with code 13. Compatibility: require() of ESM works on Node 22, but not for a module graph with top-level await, which throws ERR_REQUIRE_ASYNC_MODULE, because require has to return synchronously. esbuild can't emit it for --format=cjs either. The practical rule: use it in your app's entry and config, never in a library or a widely shared module; there, export an async function and let the app decide when to call it.

بالعامية

await بره أي function شغالة في الـ ES modules بس: .mjs، أو "type": "module"، أو <script type="module">. في ملف .cjs هي SyntaxError. و Node 22 عنده كمان syntax detection: ملف .js في package مفيهاش "type" بيتعمله parse تاني كـ ESM لما يلاقي top-level await، ومعاه warning عن تكلفة الأداء. و TypeScript محتاج module مناسب، ومع commonjs بيرفض بـ TS1378 اللي فوق.

الاستخدام الصح: تحميل الـ config قبل ما أي حاجة تبدأ. config.mjs بيعمل await للـ secrets ويعمل export للنتيجة، فمفيش حد يقدر يشوفها نص محمّلة، ومش محتاج init() ولا null checks. ولو فشل، بيقع عند الـ startup، وده اللي عايزه لـ server معندوش database URL.

بيوقّف إزاي: الـ module اللي فيه top-level await بيخلي كل اللي معتمد عليه يستنى، طالع لفوق في الـ import graph كله. الـ siblings اللي مش معتمدين عليه مش بيقفوا: بيشتغلوا وهو مستني. والـ demo بيطبع الترتيب ده: sibling بين slow: start وslow: end، وdependent بيستنى، وmain في الآخر.

المخاطر. الـ start البطيء: نداء secrets بياخد 5 ثواني في module الكل بيعمله import بيأخر كل start للـ process بـ 5 ثواني، وده يشمل كل ملف test، ولو علّق بيوقّع الـ readiness probe، فلازم تحطله timeout. الـ deadlock: لو module بيعمل await لـ dynamic import لحاجة بتعمل import ليه تاني، ولا واحد فيهم هيخلص. Node بيكتشف إن مفيش حاجة تشتغل، بيحذر بـ "Detected unsettled top-level await"، وبيخرج بـ code 13. التوافق: require() لـ ESM شغال على Node 22، بس مش مع module graph فيه top-level await: بيرمي ERR_REQUIRE_ASYNC_MODULE، لأن require لازم يرجع sync. و esbuild كمان مبيطلعهاش مع --format=cjs. القاعدة العملية: استخدمها في الـ entry والـ config بتوع الأبلكيشن، وعمرك ما تحطها في library أو module مشترك كتير؛ هناك اعمل export لـ async function وسيب الأبلكيشن يقرر هينادي إمتى.

فين هستخدمه في شغلي؟ API على Kubernetes بيجيب الـ secrets من Vault عند الـ start: export const config = await loadSecrets() في config.ts بدل let config وinitConfig() اللي حد هينسى يناديها. ولو Vault علّق من غير timeout، الـ pod هيفضل في CrashLoop أو الـ probe هيفشل من غير أي log واضح، فحط AbortSignal.timeout(5000). وفي ملف الـ db.ts المشترك بين الـ API والـ scripts والـ tests، بلاش: كل test هيفتح connection لمجرد إنه عمل import.

Part 6 — debounce & throttle by hand 🟡 Intermediateالجزء 6 — الـ debounce والـ throttle بإيدك

English

Both limit how often a function runs, and both are closures around a timer (lesson 03). Debounce waits for quiet: every call restarts the timer, so the function runs once, after the calls stop. Throttle keeps a steady rate: at most one run per window, however many calls arrive. Choose by asking: do I care about the final state (debounce: a search box, autosave, validating a form) or do I need updates along the way (throttle: scroll position, progress bars, resize, a metrics flush)?

The difference shows under non-stop input. Debounce can starve: with 100 calls, one every 100ms and a 200ms wait, it fired once, after 10 seconds. Throttle fired 51 times at a steady rate. A user who never pauses typing would never see search results with a plain debounce, and maxWait (exercise 3) is the fix.

Options. Trailing runs at the end of a burst with the latest arguments. Leading runs immediately on the first call, which suits a button you want to respond instantly while ignoring double-clicks. With both on, a lone call must run once, not twice, which is why both versions clear lastArgs when they invoke. cancel() drops the pending call and the timer. Call it on unmount or shutdown, or the timer fires against something already gone. flush() runs the pending call now, for saving a draft before the page closes.

Testing without sleeping. Real sleeps make tests slow and flaky on a loaded machine. Patching global timers (mock.timers in node:test, which is still marked experimental on Node 22, or vi.useFakeTimers() in Vitest) works, but it changes the world for everything in that test. Instead, make the timer an injected dependency: production gets the real setTimeout, and tests get a small manual clock they move by hand. Every test below runs in zero real time and is fully deterministic, plus one real-timer smoke test per utility to prove the default wiring works.

Two limits worth knowing: both versions return nothing, so an async fn that rejects is a floating promise (the demo shows it), and neither forwards this, so pass an arrow function or a bound method. lodash's versions do forward it.

export interface DebounceOptions {
  leading?: boolean;
  trailing?: boolean;
  timers?: Timers;
}

export interface Debounced<A extends unknown[]> {
  (...args: A): void;
  cancel(): void;
  flush(): void;
}

export function debounce<A extends unknown[]>(
  fn: (...args: A) => void,
  waitMs: number,
  { leading = false, trailing = true, timers = realTimers }: DebounceOptions = {},
): Debounced<A> {
  let timer: unknown;
  let lastArgs: A | undefined;

  const invoke = () => {
    // بنفضّي lastArgs قبل النداء: كده مفيش trailing زيادة بعد الـ leading، ولو fn رمت الحالة تفضل سليمة
    const args = lastArgs!;
    lastArgs = undefined;
    fn(...args);
  };

  const onQuiet = () => {
    timer = undefined;
    if (trailing && lastArgs) invoke();
    lastArgs = undefined;
  };

  const debounced = (...args: A) => {
    const firstOfBurst = timer === undefined;
    lastArgs = args;
    // كل نداء جديد بيلغي الـ timer ويبدأ العد من الأول: دي الفكرة كلها
    if (timer !== undefined) timers.clearTimeout(timer);
    timer = timers.setTimeout(onQuiet, waitMs);
    if (leading && firstOfBurst) invoke();
  };

  // الـ cancel: لازم تتنده في unmount أو shutdown، وإلا الـ timer هيشتغل على حاجة خلاص اتقفلت
  debounced.cancel = () => {
    if (timer !== undefined) timers.clearTimeout(timer);
    timer = undefined;
    lastArgs = undefined;
  };

  // الـ flush: نفّذ اللي مستني دلوقتي، زي حفظ الـ draft قبل ما اليوزر يقفل الصفحة
  debounced.flush = () => {
    if (timer === undefined) return;
    timers.clearTimeout(timer);
    onQuiet();
  };

  return debounced;
}

import { realTimers, type Timers } from "./timers-port.ts";

export interface ThrottleOptions {
  leading?: boolean;
  trailing?: boolean;
  timers?: Timers;
}

export interface Throttled<A extends unknown[]> {
  (...args: A): void;
  cancel(): void;
}

export function throttle<A extends unknown[]>(
  fn: (...args: A) => void,
  waitMs: number,
  { leading = true, trailing = true, timers = realTimers }: ThrottleOptions = {},
): Throttled<A> {
  // الاتنين false معناها fn عمرها ما هتتنده: أحسن نقع بدري من bug صامت
  if (!leading && !trailing) throw new TypeError("throttle: leading and trailing cannot both be false");

  let window: unknown;
  let lastArgs: A | undefined;

  const invoke = () => {
    const args = lastArgs!;
    lastArgs = undefined;
    fn(...args);
  };

  const openWindow = () => {
    window = timers.setTimeout(onWindowEnd, waitMs);
  };

  const onWindowEnd = () => {
    window = undefined;
    if (trailing && lastArgs) {
      // الـ trailing بيفتح window جديد: كده نداء جه بعده مباشرة مايعدّيش المعدل
      openWindow();
      invoke();
    }
    lastArgs = undefined;
  };

  const throttled = (...args: A) => {
    // جوه الـ window: بنفتكر آخر arguments بس، ومش بنأخر الـ timer زي الـ debounce
    lastArgs = args;
    if (window !== undefined) return;
    openWindow();
    if (leading) invoke();
  };

  throttled.cancel = () => {
    if (window !== undefined) timers.clearTimeout(window);
    window = undefined;
    lastArgs = undefined;
  };

  return throttled;
}

import type { Timers } from "./timers-port.ts";

export class ManualTimers implements Timers {
  now = 0;
  #nextId = 1;
  #scheduled = new Map<number, { at: number; fn: () => void }>();

  setTimeout(fn: () => void, ms: number): number {
    const id = this.#nextId++;
    this.#scheduled.set(id, { at: this.now + ms, fn });
    return id;
  }

  clearTimeout(handle: unknown): void {
    this.#scheduled.delete(handle as number);
  }

  // حرّك الساعة لقدام، وشغّل كل timer وقته جه بالترتيب
  advanceTo(time: number): void {
    for (;;) {
      const due = [...this.#scheduled.entries()]
        .filter(([, t]) => t.at <= time)
        .sort(([idA, a], [idB, b]) => a.at - b.at || idA - idB)[0];
      if (!due) break;
      const [id, t] = due;
      this.#scheduled.delete(id);
      this.now = t.at;
      t.fn();
    }
    this.now = time;
  }

  get pending(): number {
    return this.#scheduled.size;
  }
}

// بتشغّل سيناريو كامل: نداءات عند أوقات محددة، وبترجع fn اتندهت إمتى وبإيه
export function simulate(
  callTimes: number[],
  build: (fn: (at: number) => void, timers: ManualTimers) => (at: number) => void,
  endAt = Math.max(...callTimes) + 1000,
): Array<{ firedAt: number; calledAt: number }> {
  const timers = new ManualTimers();
  const fired: Array<{ firedAt: number; calledAt: number }> = [];
  const wrapped = build((calledAt) => fired.push({ firedAt: timers.now, calledAt }), timers);
  for (const t of callTimes) {
    timers.advanceTo(t);
    wrapped(t);
  }
  timers.advanceTo(endAt);
  return fired;
}

const BURSTS = [0, 50, 100, 150, 500, 550];
const firedAs = (r: Array<{ firedAt: number; calledAt: number }>) => r.map((f) => [f.firedAt, f.calledAt]);

describe("debounce", () => {
  it("trailing (default): fires once after the burst, with the latest args", () => {
    const fired = simulate(BURSTS, (fn, timers) => debounce(fn, WAIT, { timers }));
    assert.deepEqual(firedAs(fired), [[350, 150], [750, 550]]);
  });

  it("leading: fires on the first call of each burst, ignores the rest", () => {
    const fired = simulate(BURSTS, (fn, timers) => debounce(fn, WAIT, { timers, leading: true, trailing: false }));
    assert.deepEqual(firedAs(fired), [[0, 0], [500, 500]]);
  });

  it("leading + trailing: both edges, but a lone call fires only once", () => {
    const fired = simulate([...BURSTS, 2000], (fn, timers) => debounce(fn, WAIT, { timers, leading: true }));
    assert.deepEqual(firedAs(fired), [[0, 0], [350, 150], [500, 500], [750, 550], [2000, 2000]]);
  });

  it("a slow typist never gets debounced together", () => {
    const fired = simulate([0, 300, 600], (fn, timers) => debounce(fn, WAIT, { timers }));
    assert.deepEqual(firedAs(fired), [[200, 0], [500, 300], [800, 600]]);
  });

  it("non-stop calls starve it: nothing fires until the calls stop", () => {
    const calls = Array.from({ length: 100 }, (_, i) => i * 100);
    const fired = simulate(calls, (fn, timers) => debounce(fn, WAIT, { timers }));
    assert.deepEqual(firedAs(fired), [[10100, 9900]]);
  });

  it("cancel() drops the pending call and leaves no timer behind", () => {
    const timers = new ManualTimers();
    const calls: string[] = [];
    const save = debounce((draft: string) => calls.push(draft), WAIT, { timers });
    save("draft-1");
    save.cancel();
    assert.equal(timers.pending, 0);
    timers.advanceTo(1000);
    assert.deepEqual(calls, []);
  });

  it("flush() runs the pending call now and only once", () => {
    const timers = new ManualTimers();
    const calls: string[] = [];
    const save = debounce((draft: string) => calls.push(draft), WAIT, { timers });
    save("draft-1");
    save.flush();
    save.flush();
    timers.advanceTo(1000);
    assert.deepEqual(calls, ["draft-1"]);
  });

  it("flush() with nothing pending does nothing", () => {
    const calls: string[] = [];
    const save = debounce((draft: string) => calls.push(draft), WAIT, { timers: new ManualTimers() });
    save.flush();
    assert.deepEqual(calls, []);
  });

    const fired = simulate([0], (fn, timers) => {
      const d = debounce(fn, WAIT, { timers });
      return (at) => {
        d(at);
        d.cancel();
        d(at + 1);

// زي Promise.all بس على object: النتيجة بأسماء مش بأرقام، والأنواع بتفضل صح
export async function allProps<T extends Record<string, unknown>>(
  tasks: T,
): Promise<{ [K in keyof T]: Awaited<T[K]> }> {
  const keys = Object.keys(tasks);
  const values = await Promise.all(keys.map((key) => tasks[key]));
  return Object.fromEntries(keys.map((key, i) => [key, values[i]])) as { [K in keyof T]: Awaited<T[K]> };
}

Solution · الحل
الـ fire بتلغي الـ timer التاني، فمفيش تنفيذ مرتين. والـ 500 و1000 و1500 جايين من الـ maxTimer، وآخر واحدة عند 2000 جاية منه برضه لأن آخر نداء عند 1900.
// نسخة debounce بـ maxWait: لو النداءات مبتقفش، fn برضه بتتنده كل maxWaitMs على الأكتر
import { realTimers, type Timers } from "./timers-port.ts";

export function debounceMaxWait<A extends unknown[]>(
  fn: (...args: A) => void,
  waitMs: number,
  maxWaitMs: number,
  timers: Timers = realTimers,
) {
  let waitTimer: unknown;
  let maxTimer: unknown;
  let lastArgs: A | undefined;

  const fire = () => {
    timers.clearTimeout(waitTimer);
    timers.clearTimeout(maxTimer);
    waitTimer = undefined;
    maxTimer = undefined;
    const args = lastArgs!;
    lastArgs = undefined;
    fn(...args);
  };

  return (...args: A) => {
    lastArgs = args;
    // الـ timer ده بيتأخر مع كل نداء، زي الـ debounce العادي
    if (waitTimer !== undefined) timers.clearTimeout(waitTimer);
    waitTimer = timers.setTimeout(fire, waitMs);
    // وده بيبدأ مرة واحدة مع أول نداء، ومبيتأخرش
    if (maxTimer === undefined) maxTimer = timers.setTimeout(fire, maxWaitMs);
  };
}

Cheat sheet · الخلاصة

  • all = need them all, allSettled = report on each, race = first to finish, any = first success. None of them starts or cancels anything.
  • Empty input: all/allSettled give [], race hangs forever, any rejects with AggregateError.
  • By hand: store by index, count completions, Promise.resolve each input, handle empty, iterate inside the executor.
  • An async function always returns a promise, runs sync until the first await, and turns throw into a rejection.
  • Inside try, always return await. It also keeps async stack traces and isn't slower (2 ticks vs 3).
  • Independent calls: Promise.all. Rate limits, ordering, one transaction: sequential. Data-sized input: a limit.
  • Promise.all fail-fast doesn't stop the others. Their side effects still happen.
  • const a = f(); const b = g(); await a; await b; can crash the process. Use Promise.all.
  • Floating promises, forEach(async), async executors: all caught by no-floating-promises and no-misused-promises.
  • Top-level await: ESM only, blocks everything that depends on it, not its siblings. Unsettled means exit code 13. App entry and config yes, libraries no.
  • Debounce = final state, after quiet, can starve. Throttle = steady rate. Always cancel() on unmount or shutdown, and create one shared instance.
  • Test timer code by injecting the timer, not by sleeping.
بالعامية
  • all = محتاجهم كلهم، allSettled = تقرير عن كل واحد، race = أول واحد يخلص، any = أول نجاح. ولا واحدة فيهم بتبدأ أو بتلغي حاجة.
  • الـ input الفاضي: all وallSettled بيرجعوا []، race بتعلّق للأبد، any بترفض بـ AggregateError.
  • بإيدك: خزّن بالـ index، عدّ اللي خلص، Promise.resolve لكل input، اتعامل مع الفاضي، ولف جوه الـ executor.
  • الـ async function دايمًا بترجع promise، بتجري sync لحد أول await، وبتحوّل throw لـ rejection.
  • جوه try دايمًا return await. وكمان بتحافظ على الـ async stack traces ومش أبطأ (تكّتين مقابل 3).
  • نداءات مستقلة: Promise.all. rate limits أو ترتيب أو transaction واحدة: sequential. input حجمه من الداتا: حد أقصى.
  • الـ fail-fast بتاع Promise.all مش بيوقف الباقي، والـ side effects بتاعتهم بتحصل برضه.
  • const a = f(); const b = g(); await a; await b; ممكن توقّع الـ process. استخدم Promise.all.
  • الـ floating promises وforEach(async) والـ async executors: كلهم بيتمسكوا بـ no-floating-promises وno-misused-promises.
