Why this matters · ليه ده مهم

English

Module problems look like random crashes. Cannot access 'X' before initialization appears after someone adds an unrelated import. instanceof returns false for the right class. A 90 KB bundle becomes 300 KB because of one line. A service takes half a second longer to boot because of a PDF library nobody called. All of these follow from a few rules: how a module graph is loaded, what an import actually binds to, and how a package chooses a file. Node 22 also changed the old advice: require() of an ES module now works, so much of what you read about ERR_REQUIRE_ESM is out of date. Every behaviour in this lesson comes from small packages run on Node 22.19.

بالعامية

مشاكل الـ modules شكلها crashes عشوائية. Cannot access 'X' before initialization بتظهر بعد ما حد يضيف import ملوش علاقة. الـ instanceof بيرجّع false للـ class الصح. Bundle حجمه 90 KB بيبقى 300 KB بسبب سطر واحد. Service بياخد نص ثانية زيادة في الـ boot بسبب مكتبة PDF محدش ناداها. كل دول نتيجة قواعد قليلة: الـ module graph بيتحمّل إزاي، الـ import مربوط بإيه بالظبط، والـ package بيختار الملف إزاي. وكمان Node 22 غيّر النصيحة القديمة: require() لـ ES module بقى شغال، فكتير من اللي هتقراه عن ERR_REQUIRE_ESM بقى قديم. وكل سلوك في الدرس ده جاي من packages صغيرة اتشغّلت فعلًا على Node 22.19.

Part 1 — ESM & CommonJS basics 🟢 Basicالجزء 1 — أساسيات الـ ESM والـ CommonJS

English

ES Modules are the language standard. import and export are declarations the engine reads before running anything. A module has any number of named exports and at most one default. import * as money gives a namespace object: a read-only view of every export, where default is just another key. Imports are hoisted, so the imported module is evaluated before the first line of your file (the first line printed below proves it), and they must sit at the top level: import inside an if is a SyntaxError.

Why many teams prefer named exports: the name is a contract. A typo fails at link time, before any of your code runs. A default has no fixed name, so addVat and whateverIWant below are the same function, and search and rename across a codebase stop being reliable. Use a default when a framework asks for one, such as a Next.js page.tsx or a component passed to React.lazy.

CommonJS is Node's original system. Each file is wrapped in a function (the real wrapper is printed below), so exports, require, module, __filename and __dirname are simply parameters. require is an ordinary synchronous function that returns module.exports, so it can sit inside an if and take a computed path. exports is a local variable that starts out pointing at the same object. That explains the trap: exports = {…} only reassigns the local variable, and require still returns the original empty object. Likewise exports.x = 1 followed by module.exports = {…} loses x.

بالعامية

الـ ES Modules هي معيار اللغة. الـ import والـ export declarations الـ engine بيقراها قبل ما يشغّل أي حاجة. الـ module فيه أي عدد من الـ named exports، و default واحد بالكتير. الـ import * as money بيدّيك namespace object: عرض read-only لكل الـ exports، والـ default فيه مجرد key زي الباقي. الـ imports بتتعمل hoist، فالـ module المستورد بيتنفذ قبل أول سطر في ملفك (أول سطر مطبوع فوق بيثبت ده)، ولازم تبقى في أعلى مستوى في الملف: import جوه if بيبقى SyntaxError.

ليه فرق كتير بتفضّل الـ named exports: الاسم بيبقى contract. أي typo بيفشل وقت الـ link قبل ما كودك يشتغل. أما الـ default فملوش اسم ثابت، فـ addVat و whateverIWant فوق هما نفس الـ function، والبحث والـ rename في الكود كله بيبطلوا يبقوا مضمونين. استخدم default لما framework يطلبه، زي page.tsx في Next.js أو component بتبعته لـ React.lazy.

الـ CommonJS هو نظام Node الأصلي. كل ملف بيتلف في function (الـ wrapper الحقيقي مطبوع فوق)، فـ exports و require و module و __filename و __dirname مجرد parameters. الـ require function عادية synchronous بترجّع module.exports، فينفع تحطها جوه if وتديها path متحسب. والـ exports متغير محلي بيبدأ بيشاور على نفس الـ object. ده بيشرح الفخ: exports = {…} بيغيّر المتغير المحلي بس، و require لسه بيرجّع الـ object الفاضي الأصلي. وبنفس المنطق exports.x = 1 وبعدها module.exports = {…} بيضيّع x.

فين هستخدمه في شغلي؟ في أي service جديد: "type": "module" و named exports في الـ services والـ repositories، عشان import { createOrder } غلط يقع في الـ CI مش عند العميل. والـ default خليه لملفات Next زي page.tsx و layout.tsx بس. ولما تدخل كود قديم وتلاقي module رجّع {}، أول حاجة تدوّر عليها: exports = من غير module.. دي الغلطة الشائعة في الجزء ده، ولحد دلوقتي بتظهر في PRs.

Part 2 — Live bindings & module caching 🟡 Intermediateالجزء 2 — الـ live bindings والـ module caching

English

An ESM import isn't a variable holding a value. It's a live binding: a read-only view of the exporter's variable. When invoice-counter.js changes issued, every importer sees the new value under the same name. The importer can't write to it: assignment throws TypeError: Assignment to constant variable.

"CJS gets a copy" needs precision. require doesn't copy the module; everyone receives the same module.exports object. What was copied is the primitive, at the moment module.exports = { issued } ran. The property holds 0 forever, so both const { issued } = require() and counter.issued stay at 0. A getter on module.exports gives you live behaviour, but destructuring still takes a snapshot, as the last line of the run shows.

Caching: a module is evaluated once per resolved URL (ESM) or filename (CJS), so it's a natural singleton. That's why a db.js exporting one pool works without any singleton class. But "once per URL" has edges, and each one below was run: a query string makes a new URL and a new instance; different letter case on Windows opens the same file under a different key, so you get a second instance (Linux fails with "not found" instead); every worker thread has its own module graph; and two installed copies of a package are two instances (Part 7). CJS lets you delete require.cache[…]. ESM has no public way to evict a module, so a "hot reload" built on ?v=N never frees the old instances.

جملة "الـ CJS بياخد نسخة" محتاجة دقة. الـ require مش بينسخ الـ module، كله بياخد نفس الـ object بتاع module.exports. اللي اتنسخ هو الـ primitive في اللحظة اللي module.exports = { issued } اتنفذت فيها. الـ property بتفضل 0 على طول، فـ const { issued } = require() و counter.issued الاتنين بيفضلوا 0. الـ getter على module.exports بيدّيك سلوك حي، بس الـ destructuring برضه بياخد لقطة، زي آخر سطر في الـ run.

الـ caching: الـ module بيتنفذ مرة واحدة لكل URL (في الـ ESM) أو filename (في الـ CJS)، فهو singleton طبيعي. وعشان كده db.js بيصدّر pool واحد شغال من غير أي singleton class. بس "مرة لكل URL" ليها حدود، وكل واحدة منهم اتجربت فوق: الـ query string بيعمل URL جديد و instance جديد. اختلاف حالة الحروف على Windows بيفتح نفس الملف بـ key مختلف، فتاخد instance تاني (على Linux بيقولك مش موجود). كل worker thread ليه module graph خاص بيه. ونسختين متسطبين من package يعني instanceين (الجزء 7). الـ CJS بيسمحلك تعمل delete require.cache[…]، أما الـ ESM فمفيهوش طريقة رسمية تشيل module، فأي "hot reload" معمول بـ ?v=N عمره ما بيحرر الـ instances القديمة.

فين هستخدمه في شغلي؟ db.js بيصدّر pool واحد وكل الـ repositories تعمل منه import، من غير أي getInstance(). والـ live binding بيفيد في حاجة زي export let featureFlags بتتحدث من polling. وخلي بالك من الفخ ده: لو عندك 8 worker threads وكل واحد عمل import لـ db.js بـ max: 10، يبقى عندك 80 Postgres connection مش 10، وده ممكن يخلّص max_connections وأنت فاكر عندك pool واحد. وفي الـ code review، import("./x.js?tenant=" + id) معناه memory leak لكل tenant.
Interview question "What's the difference between an ESM import and const x = require() when the exporter changes the value later?" → ESM imports are live bindings, so the importer sees the new value and can't assign to it. In CJS the primitive was copied into a property when module.exports was set, so it never changes unless you use a getter, and destructuring takes a snapshot anyway.
"إيه الفرق بين import في الـ ESM و const x = require() لو الـ exporter غيّر القيمة بعدين؟" ← الـ ESM import هو live binding، فالـ importer بيشوف القيمة الجديدة ومايقدرش يكتب عليها. في الـ CJS الـ primitive اتنسخ في property وقت ما module.exports اتظبط، فمش بيتغير إلا لو استخدمت getter، والـ destructuring بياخد لقطة في كل الأحوال.

Part 3 — Dynamic import() 🟡 Intermediateالجزء 3 — الـ dynamic import()

English

import(specifier) is an expression that returns a promise for the namespace object. It works anywhere, including inside functions, if blocks and CommonJS files, and the specifier can be computed. Use it for code that's expensive and rarely needed. Below, the server imports the real pdfkit package: a static import makes every boot pay for it (≈ 261 ms vs ≈ 36 ms to ready, ≈ 72 MB vs ≈ 57 MB RSS, medians of 15 runs), even on pods that never render an invoice. With a dynamic import, the first invoice pays once (≈ 286 ms) and later calls pay nothing (≈ 4 ms). Exact numbers depend on this busy Windows machine; rely on the ratio.

Two details matter in production. Store the promise, not the result: if you store the loaded module only after the await, concurrent requests can each start their own load. import() is cached by Node anyway, but your own initialization (fonts, templates) isn't. And a failed evaluation is cached in ESM: the run below evaluates the failing ESM file once, and the second import() rejects with the same error without running it again, so retrying can't fix it. The CJS version does run again, because a module that throws is removed from require.cache.

Route-based splitting: in a bundler every import() is a split point. Each route becomes its own chunk, shared code moves to a common chunk, and the entry stays tiny. In the run below app.js is 0.2 KB while the invoices chunk is 892 KB, and a user who never opens invoices never downloads it. next/dynamic and React.lazy are this same mechanism. A template string like import(`./locales/${lang}.js`) also works: esbuild treated it as a glob and produced separate ar and en chunks. Never build the specifier from user input, because that lets a request choose which code you load.

Part 4 — Circular dependencies 🟡 Intermediateالجزء 4 — الـ circular dependencies

English

A cycle is orders.js importing users.js while users.js imports orders.js, often through several files. To understand the failure, you need ESM's three phases. Construction parses every file and finds its imports. Linking connects all the bindings, with the variables still uninitialized. Evaluation runs bodies depth-first, dependencies before dependents, skipping a module already in progress.

So starting at orders.js: it depends on users.js, whose dependency orders.js is already in progress and is skipped, so users.js runs first. Its top level reads ORDER_STATUSES, which is still in the TDZ, and you get ReferenceError: Cannot access 'ORDER_STATUSES' before initialization. The nasty part: import users.js first and the order flips and everything works. So an unrelated new import elsewhere can crash startup. A cycle is harmless in ESM while the use stays inside functions called after loading finishes (esm-safe below).

CommonJS fails differently. require of a file still in progress returns its partially filled module.exports, which here prints {}. Destructuring gives undefined, and the crash comes later and elsewhere: TypeError: ordersOf is not a function. With inheritance it's Class extends value undefined is not a constructor or null. Node can warn with Accessing non-existent property … inside circular dependency, but only if the process survives long enough to print it: the crashing run below shows no warning.

Detect cycles in CI: madge --circular exits 1 when it finds one. On TypeScript, madge counts import type as an edge and reports a false cycle unless you set skipTypeImports; I ran it both ways. Break them, in this order of preference: (1) move what's shared into a leaf module with no imports; (2) invert the dependency: pass the function in as a parameter and wire things up in one composition root; (3) use import type when only types are shared, since it disappears at runtime; (4) as a last resort, move the use inside a function or use import(), which hides the cycle rather than removing it.

Part 5 — Module resolution & tree shaking 🟡 Intermediateالجزء 5 — الـ module resolution والـ tree shaking

English

Resolution turns a specifier into a file. There are four kinds. Relative (./db.js) is resolved from the importing file, and in ESM it must be exact, with the extension and no directory (ERR_MODULE_NOT_FOUND, ERR_UNSUPPORTED_DIR_IMPORT); CJS guesses extensions and index.js. Bare (zod, @scope/x) walks up from the importing file, checking node_modules in each parent directory up to the root, and the nearest wins. That's why services/billing below gets v1.0.0 while the root has v2.1.0. node: goes straight to a built-in. #name looks in the imports field of your own package.json, which gives you internal aliases without a bundler or tsconfig paths.

Once a package is found, its package.json decides the file: exports if present, otherwise main. exports also encapsulates: any path it doesn't list fails with ERR_PACKAGE_PATH_NOT_EXPORTED. NODE_PATH affects require only; the same name through import fails. The walk also explains phantom dependencies: you can import a package you never declared, because something else put it in a parent node_modules (lesson 13 shows that breaking under pnpm).

Tree shaking removes unused code from a bundle. It needs ESM because imports and exports are static: the bundler can see exactly which names are used without running anything. require is a runtime call and module.exports can be computed, so a bundler has to keep the whole CJS module. That's the 278 KB vs 0.1 KB in the run below, and lodash at 72 KB vs lodash-es at 2.8 KB for one debounce. Dynamic access defeats it too: lib[name] keeps everything.

Removing an unused export is the easy part. A file's top-level code may have side effects, so the bundler keeps what it can't prove is safe: in the plain barrel, Object.freeze(…) is a call and stays (64 KB), while a plain object literal was dropped. "sideEffects": false in package.json is your promise that unused files can be dropped entirely (0.1 KB). If the promise is false, you get a bug that exists only in production: import "order-events/register" works in Node and silently vanishes from the bundle, though esbuild does warn. List the real ones instead: "sideEffects": ["./register.js"].

Barrel files (index.js with export *) have another cost that tree shaking doesn't touch: without a bundler (Node, tests, dev servers) importing one name still loads the whole barrel. With 400 small modules: ≈ 45 ms direct vs ≈ 442 ms through the barrel. That's about 10×, and I saw about 35× in an earlier run under heavier machine load.

الـ resolution بيحوّل الـ specifier لملف، وفيه 4 أنواع. الـ relative (./db.js) بيتحل من الملف اللي عامل import، وفي الـ ESM لازم يبقى بالظبط، بالامتداد ومن غير فولدر (ERR_MODULE_NOT_FOUND و ERR_UNSUPPORTED_DIR_IMPORT)، والـ CJS بيخمّن الامتدادات و index.js. الـ bare (zod و @scope/x) بيطلع لفوق من الملف، ويبص في node_modules في كل فولدر أب لحد الجذر، والأقرب بيكسب. وعشان كده services/billing فوق خد v1.0.0 رغم إن الـ root فيه v2.1.0. الـ node: بيروح لـ built-in على طول. الـ #name بيبص في imports في الـ package.json بتاعك، وده بيدّيك aliases داخلية من غير bundler ولا tsconfig paths.

لما الـ package يتلاقي، الـ package.json بتاعه بيحدد الملف: exports لو موجود، وإلا main. والـ exports كمان بيعمل encapsulation: أي path مش مكتوب فيه بيفشل بـ ERR_PACKAGE_PATH_NOT_EXPORTED. الـ NODE_PATH بيأثر على require بس، ونفس الاسم بـ import بيفشل. والـ walk ده بيشرح الـ phantom dependencies كمان: تقدر تعمل import لـ package عمرك ما كتبته، لأن حاجة تانية حطته في node_modules أب (درس 13 بيوري ده بيتكسر إزاي مع pnpm).

الـ tree shaking بيشيل الكود اللي مش مستخدم من الـ bundle. وهو محتاج ESM لأن الـ imports والـ exports static: الـ bundler يقدر يشوف الأسماء المستخدمة بالظبط من غير ما يشغّل حاجة. الـ require call وقت التشغيل و module.exports ممكن يتحسب، فالـ bundler لازم يحتفظ بالـ CJS module كله. ده الفرق بين 278 KB و 0.1 KB فوق، وبين lodash بـ 72 KB و lodash-es بـ 2.8 KB عشان debounce واحدة. والـ access الديناميكي بيبوظه برضه: lib[name] بيخلي كل حاجة تفضل.

شيل export مش مستخدم ده الجزء السهل. الـ top-level code في أي ملف ممكن يكون ليه side effects، فالـ bundler بيسيب اللي مش قادر يثبت إنه آمن: في الـ barrel العادي Object.freeze(…) ده call فاتساب (64 KB)، بينما object literal عادي اتشال. الـ "sideEffects": false في package.json هو وعد منك إن الملفات اللي مش مستخدمة تتشال بالكامل (0.1 KB). ولو الوعد ده مش صح، هيطلعلك bug في production بس: import "order-events/register" شغال في Node وبيختفي من الـ bundle من غير صوت، وإن كان esbuild بيحذّر. اكتب الملفات اللي ليها side effects فعلًا: "sideEffects": ["./register.js"].

الـ barrel files (index.js فيه export *) ليها تكلفة تانية الـ tree shaking مش بيلمسها: من غير bundler (Node، الـ tests، الـ dev servers) import لاسم واحد بيحمّل الـ barrel كله. مع 400 module صغير: ≈ 45 ms مباشرة ضد ≈ 442 ms عن طريق الـ barrel. يعني حوالي 10 مرات، وشفت حوالي 35 مرة في تشغيلة قبلها والجهاز عليه ضغط أكتر.

Interview question "Why does tree shaking work with ESM and not CommonJS?" → ESM's structure is static: imports and exports are top-level declarations, so usage is known at build time. require is a function call and module.exports can be built at runtime, so the bundler must keep all of it. Then mention sideEffects: unused exports are easy, top-level code is the hard part.
"ليه الـ tree shaking شغال مع الـ ESM ومش مع الـ CommonJS؟" ← هيكل الـ ESM static: الـ imports والـ exports declarations في أعلى الملف، فالاستخدام معروف وقت الـ build. الـ require function call و module.exports ممكن يتبني وقت التشغيل، فالـ bundler لازم يسيبه كله. وبعدها اذكر sideEffects: الـ exports اللي مش مستخدمة سهلة، والـ top-level code هو الصعب.

English

Which format is a file? .mjs is ESM and .cjs is CJS. A .js file follows "type" in the nearest package.json. With no type, Node 22 parses it as CommonJS and, if that fails because of ESM syntax, reparses it as ESM and prints a warning about the overhead. So set "type" explicitly.

require() of ESM works on this Node. The old rule "require can't load ESM, you get ERR_REQUIRE_ESM" is outdated. According to the Node 22 docs it was added in 22.0 behind a flag, enabled by default in 22.12, and stopped printing a warning in 22.13; the docs still mark it Stability 1.2, release candidate. On 22.19 I ran it from a local file and from node_modules with no flag and no warning. It returns the namespace object, with __esModule: true added when there's a default export. A package can choose what require returns by exporting a name literally called "module.exports". The hard limit: the ESM graph must be synchronous. Any top-level await (lesson 09) gives ERR_REQUIRE_ASYNC_MODULE, and import() is the only way in. Check process.features.require_module if your code may run on older versions.

import of CJS: the default is always the whole module.exports. Named imports are a best-effort extra: Node scans the CJS source with a static lexer (cjs-module-lexer) without running it. exports.charge = … and module.exports = { charge } are detected; names computed in a loop or returned from a factory aren't, and asking for one gives Named export 'refund' not found. The fallback always works: import gw from "…"; gw.refund().

The __esModule trap: CJS compiled from TypeScript or Babel sets exports.default and __esModule. Node ignores that marker, so your import sendInvoice from gets an object, and you need sendInvoice.default(). Bundlers may honour it: esbuild gave a function for a .js entry in a package without "type": "module", and an object for a .mjs entry, matching Node. So the same line can behave differently in your bundle and in Node.

Paths: ESM has no __dirname, __filename, require or module. Use import.meta.dirname and import.meta.filename (Node 20.11+), or import.meta.url, which is a file: URL. fs accepts new URL("./x.json", import.meta.url) directly. Never use new URL(…).pathname as a path: on Windows it gives /D:/… and it keeps %20 for spaces; fileURLToPath handles both. createRequire(import.meta.url) gives a real require inside ESM for the occasional case, such as require.resolve.

Part 7 — Dual packages & import maps 🔴 Advancedالجزء 7 — الـ dual packages والـ import maps

English

The exports field maps paths to files, and conditions pick a file for each environment. Conditions are checked in the order written and the first match wins, so default goes last and types first. The wrong-order entry below puts default first and gets the browser build on Node. import and require depend on how the package was loaded; node matches on Node; custom names turn on with node -C development. module-sync matches for both import and require and is meant for ESM with no top-level await, so one file serves both. If you add exports, list everything public, including ./package.json if tools read it (installing pdfkit for this lesson, my require("pdfkit/package.json") failed for exactly this reason).

The dual package hazard: a package that ships separate ESM and CJS files can load twice in one process. Your ESM app imports the ESM copy, and a CJS dependency requires the CJS copy. Two PaymentError classes now exist, so err instanceof PaymentError is false for a genuine PaymentError, and your error mapper turns a card decline into a 500. Any state inside the package (a cache, a registry, a pool) is duplicated too. It's reproduced below: both copies load and the check fails, even though the name and code look identical.

Fixes, in today's order of preference (all run below): (1) ship ESM only and set engines to Node 22.12+, because require(esm) now covers CJS consumers; (2) a thin ESM wrapper that re-exports the CJS file, so there's one real copy, at the cost of tree shaking; (3) a module-sync condition, so both paths resolve to one ESM file on Node versions that support it. In your own code, compare err.code across package boundaries instead of relying on instanceof. And check packages you publish with attw --pack, which caught a real mistake in my first package.json: types placed after import and require, and one declaration file for both formats. Section 06 goes deeper on publishing.

Import maps bring bare specifiers to the browser with no bundler. A <script type="importmap"> maps "money" to a URL; a key ending in / maps a whole folder, and scopes let one folder use a different version. Define the map before the modules that need it. In Chrome 156 an unmapped name fails with Failed to resolve module specifier. They suit internal tools and small apps without a build step. For a large public app, a bundler is still the better fit, since it also handles splitting, minifying and hashing.

Import attributes tell the runtime what a file must be: import rates from "./vat-rates.json" with { type: "json" }. It's a security feature: a server can't hand you JavaScript in place of a JSON file, because the type is checked and JSON is never executed. On Node 22.19 omitting it throws ERR_IMPORT_ATTRIBUTE_MISSING, the old assert { type: "json" } syntax is a SyntaxError now, and only the default export exists, so a named import fails. TypeScript with module: nodenext requires the attribute too (TS1543, on both 7.0.2 and 6.0.3).

// شغّله كده: node exercises/ex3-lazy.js
import assert from "node:assert/strict";

export function lazy(loader) {
  let pending;
  return () => {
    // الـ promise بيتخزن مش النتيجة، عشان الـ calls المتزامنة تشترك فيه
    pending ??= loader().catch((err) => {
      // لو فشل امسح الـ cache عشان الـ call الجاية تحاول تاني
      pending = undefined;
      throw err;
    });
    return pending;
  };
}

  return { render: () => "pdf" };
});

// أول محاولة: 3 calls مع بعض بيعملوا تحميل واحد وكلهم بيفشلوا
const first = await Promise.allSettled([loadPdf(), loadPdf(), loadPdf()]);
assert.equal(calls, 1);
assert.ok(first.every((r) => r.status === "rejected"));

// المحاولة التانية بتحمّل من جديد
shouldFail = false;
const [a, b] = await Promise.all([loadPdf(), loadPdf()]);
assert.equal(calls, 2);
assert.equal(a, b);

// بعد النجاح مفيش تحميل تاني خالص
await loadPdf();
assert.equal(calls, 2);
console.log("all assertions passed, loader calls:", calls);

all assertions passed, loader calls: 2
The stored promise is what makes concurrent callers share one load. Clearing it on failure allows a retry. It can't help with a failed ESM evaluation because Node caches that failure, as the Part 3 run showed: the retry just gets the same error back.

Cheat sheet · الخلاصة

  • Prefer named exports: a typo fails at link time. exports = {…} does nothing; use exports.x or module.exports.
  • ESM imports are live, read-only bindings. CJS copied the primitive into a property; getters help, destructuring still snapshots.
  • A module runs once per URL or filename: a natural singleton, except with query strings, letter case on Windows, workers, and duplicate packages.
  • import() moves heavy code's cost to first use (≈ 261 ms → ≈ 36 ms boot with pdfkit). A failed ESM evaluation is cached; CJS re-runs.
  • Cycles: ESM gives a TDZ crash that depends on import order; CJS gives half-filled exports. madge --circular in CI. Fix with a leaf module or by inverting the dependency.
  • ESM needs exact relative paths. Bare names walk up node_modules and the nearest wins. exports blocks unlisted paths. #name gives internal aliases.
  • Tree shaking needs static ESM. CJS and lib[name] keep everything. sideEffects is a promise; list the files that really have effects.
  • Barrels cost startup without a bundler, about 10× with 400 modules here.
  • On Node 22.12+, require(esm) works, and on 22.19 with no warning. Top-level await gives ERR_REQUIRE_ASYNC_MODULE.
  • import of CJS: default is module.exports, named only if the lexer sees them. Node ignores __esModule; bundlers may not.
  • Use import.meta.dirname or fileURLToPath, never .pathname. In exports, order matters: types first, default last.
  • Separate ESM and CJS builds can load twice and break instanceof. Ship ESM only or a wrapper, and check with attw. JSON needs with { type: "json" }; assert is gone.
بالعامية
  • فضّل الـ named exports: الـ typo بيفشل وقت الـ link. و exports = {…} مش بيعمل حاجة، استخدم exports.x أو module.exports.
  • الـ ESM imports هي live bindings و read-only. الـ CJS نسخ الـ primitive في property، والـ getter بيساعد، بس الـ destructuring برضه بياخد لقطة.
  • الـ module بيتنفذ مرة لكل URL أو filename: singleton طبيعي، ما عدا مع الـ query strings، وحالة الحروف على Windows، والـ workers، والـ packages المكررة.
  • الـ import() بينقل تكلفة الكود التقيل لأول استخدام (≈ 261 ms ← ≈ 36 ms في الـ boot مع pdfkit). والفشل في تنفيذ ESM بيتخزن، والـ CJS بيتنفذ تاني.
  • الـ cycles: الـ ESM بيدّي crash في الـ TDZ بيعتمد على ترتيب الـ imports، والـ CJS بيدّي exports ناقصة. حط madge --circular في الـ CI، وصلّح بـ leaf module أو بعكس الاعتماد.
  • الـ ESM محتاج relative paths بالظبط. الأسماء الـ bare بتطلع لفوق في node_modules والأقرب بيكسب. الـ exports بيقفل أي path مش مكتوب. والـ #name بيدّيك aliases داخلية.
  • الـ tree shaking محتاج ESM static. الـ CJS و lib[name] بيخلوا كل حاجة تفضل. والـ sideEffects وعد، فاكتب الملفات اللي ليها effects فعلًا.
  • الـ barrels بتكلف في الـ startup من غير bundler، حوالي 10 مرات مع 400 module هنا.
  • من Node 22.12 الـ require(esm) شغال، وعلى 22.19 من غير warning. والـ top-level await بيدّي ERR_REQUIRE_ASYNC_MODULE.
  • الـ import لـ CJS: الـ default هو module.exports، والـ named لو الـ lexer شافها بس. الـ Node بيتجاهل __esModule، والـ bundlers ممكن لأ.
  • استخدم import.meta.dirname أو fileURLToPath، وعمرك ما تستخدم .pathname. وفي exports الترتيب مهم: types الأول و default الآخر.
  • الـ builds المنفصلة ESM و CJS ممكن تتحمّل مرتين وتكسر instanceof. انشر ESM بس أو wrapper، وافحص بـ attw. والـ JSON محتاج with { type: "json" }، والـ assert خلاص راحت.
