Why this matters · ليه ده مهم

English

Error handling decides what an incident looks like. Done well, the client gets 409 ORDER_DUPLICATE and your log has the full chain down to the Postgres error. Done badly, the client reads your constraint names in a 500, the log line says {}, and the process either dies because of one missing await or keeps running with a leaked DB connection. This lesson covers the language mechanics, then what a senior looks for in code review: a typed error hierarchy, wrapping with cause, the async traps, and the last-resort global handlers. Interviewers like this area because one question ("why doesn't this catch run?") separates people who use try/catch from people who understand the call stack.

بالعامية

الـ error handling هو اللي بيحدد شكل الـ incident عامل إزاي. لو معمول صح، العميل بياخد 409 ORDER_DUPLICATE والـ log عندك فيه السلسلة كلها لحد الـ error بتاع Postgres. لو معمول غلط، العميل بيقرا أسامي الـ constraints بتاعتك في response 500، وسطر الـ log مكتوب فيه {}، والـ process يا إما بيموت بسبب await واحدة ناقصة، يا إما بيفضل شغال و DB connection ضايعة منه. الدرس ده بيغطي ميكانيكا اللغة، وبعدها اللي السنيور بيدوّر عليه في الـ code review: error hierarchy واضح، الـ wrapping بـ cause، فخاخ الـ async، والـ global handlers كخط دفاع أخير. والـ interviewers بيحبوا الموضوع ده عشان سؤال واحد ("ليه الـ catch ده مش بيشتغل؟") بيفرّق بين اللي بيستخدم try/catch واللي فاهم الـ call stack.

Part 1 — try/catch/finally & built-in errors 🟢 Basicالجزء 1 — الـ try/catch/finally والـ errors الجاهزة في اللغة

English

throw abandons the current function and unwinds the call stack until it reaches the nearest enclosing try; its catch receives the thrown value. finally runs on every way out of the block: normal completion, return, break/continue, or an exception.

An Error carries three things you use daily. name is the kind of error and is inherited from the prototype. message says what went wrong. stack says where: in V8 it is a string whose first line is name: message, followed by the frames (at most Error.stackTraceLimit, 10 by default). message and stack are own but non-enumerable, so Object.keys(err) is empty and JSON.stringify(err) gives {}. In TypeScript strict mode the catch variable is unknown, because JavaScript lets you throw anything, so you narrow it first.

The engine throws four error types you will meet constantly (table below). The useful habit is to sort them by what they mean: TypeError and ReferenceError are almost always bugs, so don't catch them and carry on. RangeError is a bug or unvalidated input. At runtime a SyntaxError comes from parsing external text (JSON.parse, new Function), and that one you do handle. A syntax error in your own file is different: the file never starts, so no try inside it can help.

الجدول بيرتب الـ 4 أنواع حسب معناها:
  • TypeError: القيمة نوعها غلط للعملية دي. سببها في الـ backend: rows[0].total على نتيجة فاضية، أو method مش موجودة. اتعامل معاها كـ bug.
  • RangeError: القيمة بره المدى المسموح. سببها: toFixed(200) أو new Array(-15) أو recursion ملهاش آخر. يا bug يا validation ناقص.
  • SyntaxError: نص ماتعرفش يتعمله parse. سببها: JSON.parse على صفحة HTML 502 جاية من الـ load balancer. دي data غلط من بره، لازم تتعامل معاها.
  • ReferenceError: اسم مش بيوصل لحاجة. سببها: typo، أو قراءة const قبل سطره (الـ TDZ). ده bug، و tsc بيمسك أغلبها.

Three finally rules surprise people, all shown below: a return in finally overrides the try's return and swallows a pending exception; a throw in finally replaces the original error; and the value being returned was already computed, so changing the variable in finally doesn't change the result. So keep finally for cleanup only, with no control flow in it (ESLint's no-unsafe-finally flags this).

Finally, you can throw "card declined", but a string has no stack and no message, so every handler that does err.message prints undefined and your error tracker has nothing to group by. Always throw Error objects (typescript-eslint's only-throw-error enforces it) and normalize anything from third-party code in one place.

function swallowsError(): string {
  try {
    throw new Error("payment failed");
  } finally {
    // أخطر حالة: الـ return ده بلع الـ exception خالص
    return "looks fine";
  }
}

function capturedValue(): string {
  let status = "pending";
  try {
    // القيمة اتحسبت هنا قبل ما الـ finally يشتغل
    return status;
  } finally {
    status = "done";
  }
}

  try {
    throw new Error("INSERT failed: root cause");

    // لو الـ cleanup نفسه رمى، الـ error الأصلي بيضيع

}

بالعامية

الـ throw بيسيب الـ function اللي هو فيها وبيفك الـ call stack لحد ما يوصل لأقرب try محيط بيه، والـ catch بتاعه بياخد القيمة اللي اترمت. الـ finally بيشتغل مع أي طريقة خروج من البلوك: خلص عادي، return، break أو continue، أو exception.

الـ Error فيه 3 حاجات هتستخدمهم كل يوم. الـ name نوع الـ error وبيتورث من الـ prototype. الـ message بتقول إيه اللي حصل. الـ stack بيقول حصل فين: في V8 هو string أول سطر فيه name: message وبعده الـ frames (بحد أقصى Error.stackTraceLimit، والـ default بتاعه 10). الـ message والـ stack خصايص own بس non-enumerable، فـ Object.keys(err) بيطلع فاضي و JSON.stringify(err) بيطلع {}. وفي TypeScript strict الـ catch variable نوعه unknown، لأن JavaScript بتسمح ترمي أي حاجة، فلازم تعمل narrow الأول.

الـ engine بيرمي 4 أنواع هتقابلهم على طول، والجدول فوق فيه أسبابهم. العادة المفيدة إنك ترتبهم بمعناهم: TypeError و ReferenceError في الغالب bugs، فمتمسكهمش وتكمّل عادي. الـ RangeError يا bug يا input من غير validation. والـ SyntaxError وقت التشغيل جاي من parsing لـ نص من بره (JSON.parse، new Function)، وده اللي لازم تتعامل معاه. أما syntax error في ملفك إنت فحاجة تانية: الملف مش بيبدأ أصلًا، فمفيش try جواه يقدر يعمل حاجة.

فيه 3 قواعد في finally بتفاجئ الناس، وكلهم في الكود فوق: return جوه finally بيلغي الـ return بتاع try وبيبلع أي exception كان طالع. الـ throw جوه finally بيحل محل الـ error الأصلي. والقيمة اللي راجعة بتتحسب قبل الـ finally، فلو غيرت المتغير جواه النتيجة مش بتتغير. عشان كده finally للـ cleanup بس ومن غير أي control flow جواه، وقاعدة ESLint اسمها no-unsafe-finally بتمسك ده.

وآخر حاجة: تقدر تكتب throw "card declined"، بس الـ string ملوش stack ولا message، فأي handler بيعمل err.message هيطبع undefined، والـ error tracker مش هيلاقي حاجة يجمّع عليها. ارمي Error objects دايمًا (قاعدة only-throw-error في typescript-eslint بتفرض ده)، وأي حاجة جاية من كود خارجي حوّلها في مكان واحد زي toError فوق.

فين هستخدمه في شغلي؟ أي endpoint بياخد DB client من الـ pool: const client = await pool.connect(); try { … } finally { client.release(); }. لو نسيت الـ finally، كل error بيضيّع connection، وبعد عدد requests قد الـ pool الـ API كله بيعلّق. وخلي بالك لو release() نفسها ممكن ترمي: هتخبي الـ error الحقيقي زي ما شفت في cleanupHidesRootCause. ولو بتعمل call لـ upstream، حط JSON.parse في try لوحده وارمي منه BadGateway بدل ما الـ SyntaxError يطلع للعميل 500.
Interview question "What does try { throw new Error('x') } finally { return 1 } do?" → It returns 1 and the exception disappears. A return in finally replaces whatever completion was pending, including a throw. That's why linters forbid control flow in finally.
"الكود try { throw new Error('x') } finally { return 1 } بيعمل إيه؟" ← بيرجّع 1 والـ exception بيختفي. الـ return جوه finally بيحل محل أي نتيجة كانت مستنية، حتى لو كانت throw. وعشان كده الـ linters بتمنع أي control flow جوه finally.

Part 2 — Custom error classes 🟡 Intermediateالجزء 2 — الـ custom error classes

English

A catch receives everything, so you need a way to tell "order not found" (expected, return 404) from "cannot read properties of undefined" (a bug, return 500 and alert). A small hierarchy does that. Subclass Error (see lesson 06 for how extends works) and give each class what the rest of the system needs: a stable code for machines (clients switch on it, dashboards group by it, and it survives rewording the message), an HTTP status, and a name for humans reading logs.

name isn't set for you: a bare class E extends Error {} still reports Error. Set it as a string literal. new.target.name looks neater, but a minifier renames classes, so it can turn into e in production, as the run below shows. (--keep-names in esbuild is the other fix.)

instanceof walks the prototype chain, so a NotFoundError is also an AppError and an Error. Old tutorials add Object.setPrototypeOf(this, new.target.prototype); that was only needed when compiling classes down to ES5. I compiled class A extends Error to ES5 with TS 6 and new A() instanceof A really was false. TS 7 removes the target altogether (TS5108: Option 'target=ES5' has been removed), so that line can go.

Error.captureStackTrace(target, fn) (V8 and Node) writes a stack onto target, omitting fn and everything above it. Many tutorials call it in every constructor, but on Node 22 that does nothing useful: V8 already leaves the constructor frames out, as the direct new line below shows. Its real job is hiding helper functions so the top frame is the code that actually has the problem, and adding a stack to a non-Error object. Use ?. if the code also runs in browsers. Also, V8 formats stack the first time you read it: edit message before that and the header follows; edit it after and the header stays stale. Don't mutate errors. Wrap them (Part 3).

Finally, convert errors to responses in one place. Handlers just throw; one function decides status and body. Express 5 forwards rejected async handlers to the error middleware by itself; I ran the same route on Express 4 and the rejection crashed the process (exit code 1), which is why Express 4 code needs a wrapper. Watch the {bad json case: express.json() throws a SyntaxError with status: 400, so a mapper that only knows AppError turns every malformed body into a 500 and pages someone over a client's mistake.

// الملف ده الـ error hierarchy بتاع الـ API كله
export class AppError extends Error {
  // الاسم literal مش new.target.name عشان الـ minifier بيغيّر أسماء الـ classes
  override name = "AppError";
  readonly code: string;
  readonly status: number;

  constructor(message: string, code: string, status: number, options?: ErrorOptions) {
    super(message, options);
    this.code = code;
    this.status = status;
  }
}

export class NotFoundError extends AppError {
  override name = "NotFoundError";
  constructor(entity: string, id: string, options?: ErrorOptions) {
    super(`${entity} ${id} not found`, `${entity.toUpperCase()}_NOT_FOUND`, 404, options);
  }
}

export class ValidationError extends AppError {
  override name = "ValidationError";
  readonly fields: Record<string, string>;
  constructor(fields: Record<string, string>) {
    super("Request validation failed", "VALIDATION_FAILED", 422);
    this.fields = fields;
  }
}

export class ConflictError extends AppError {
  override name = "ConflictError";
  constructor(message: string, code: string, options?: ErrorOptions) {
    super(message, code, 409, options);
  }
}

Part 3 — Error cause 🟡 Intermediateالجزء 3 — الـ error cause

English

A low-level error is often meaningless to the caller. duplicate key value violates unique constraint should become "this order already exists" by the time it leaves the repository. The old way, throw new Error("createOrder failed: " + err.message), keeps the text and throws away the original stack, the SQLSTATE code and the constraint. ES2022's new Error(message, { cause }) stores the original as an own, non-enumerable cause property: the caller gets the new meaning and the root cause survives.

Know who actually displays it, because the answers differ, and the run below proves each one: the err.stack string has no cause in it, so logger.error(err.stack) loses it; JSON.stringify has no cause either; console.log/util.inspect print it as [cause]; pino 10's err serializer appends it to the stack as caused by:. If your logger doesn't, walk the chain yourself with a guard against cycles.

Wrap where the meaning changes (driver → repository, third-party API → gateway client), not at every function, or your logs fill with five wrappers saying nothing. And never send the cause to the client: Postgres's detail contains the actual values (Key (email)=(sara@shop.test) already exists.), which tells an attacker that account exists and leaks personal data. The rule: the chain goes to logs, and code plus a safe message go to the client. For several failures at once, the built-in AggregateError (with its errors array, what Promise.any rejects with) plays the same role.

export async function createOrder(key: string): Promise<void> {
  try {
    await query("INSERT INTO orders (idempotency_key) VALUES ($1)", [key]);
  } catch (err) {
    if (hasSqlState(err) && err.code === "23505") {
      throw new ConflictError("Order already exists", "ORDER_DUPLICATE", { cause: err });

    throw new AppError("Could not create order", "ORDER_WRITE_FAILED", 500, { cause: err });

// بيمشي على سلسلة cause كلها، والـ Set عشان cycle ميعلّقش الـ logger
export function describeChain(err: unknown): string[] {
  const lines: string[] = [];
  const seen = new Set<unknown>();
  let current: unknown = err;

  while (current !== undefined && !seen.has(current)) {
    seen.add(current);
    if (!(current instanceof Error)) {
      lines.push(`non-error: ${String(current)}`);
      break;
    }
    const code = (current as { code?: unknown }).code;
    lines.push(`${current.name}${code ? ` [${String(code)}]` : ""}: ${current.message}`);
    current = current.cause;
  }
  return lines;
}

Part 4 — Errors in async code 🟡 Intermediateالجزء 4 — الـ errors في الكود الـ async

English

One sentence explains all of this: a try only protects code that fails while its frame is on the call stack. await works with that rule, because the async function suspends with its try region remembered, and when the promise rejects the function resumes and the rejection is thrown at the await line, so catch runs.

Remove the await and the try finishes before the promise fails. The catch never runs, your function returns success, and the rejection has no handler, so a moment later Node kills the process (first run below). Lesson 09 covers the sibling bug return vs return await and the lint rule no-floating-promises; here the point is the mechanism.

Callbacks are the same story. A throw inside a setTimeout callback or an event listener runs later, on a new stack that has nothing to do with the try around the registration, so it escapes to uncaughtException. The second run shows four variants. emit() is synchronous, so a throwing listener does reach a try around the emit (never one around the on). A timer inside a promise executor doesn't reject the promise; it stays pending forever and the error escapes. An async listener returns a promise nobody looks at, so it becomes an unhandled rejection. The fixes: put the try inside the callback, call reject rather than throw, or use new EventEmitter({ captureRejections: true }).

A subtler trap is the late await: const p = fetchProfile(); const orders = await fetchOrders(); await p;. If p rejects during the second await it has no handler yet, Node declares it unhandled, and the process dies, even though the whole thing sits in a try and await p is coming. Promise.all attaches handlers to both immediately.

.catch and try/await are the same mechanism with different reach. .catch is nice for a one-line fallback on one call. But it only sees rejections: a non-async function that throws synchronously before returning its promise skips it completely, while try/await catches both. And .then(ok, fail) doesn't catch errors thrown by ok; a following .catch does.

جملة واحدة بتشرح كل ده: الـ try بيحمي بس الكود اللي بيفشل والـ frame بتاعه لسه على الـ call stack. الـ await ماشية مع القاعدة دي، لأن الـ async function بتتعلق وهي فاكرة إنها جوه try، ولما الـ promise يعمل reject الـ function بترجع تشتغل، والـ rejection بيترمي عند سطر الـ await، فالـ catch بيشتغل.

شيل الـ await والـ try هيخلص قبل ما الـ promise يفشل. الـ catch مش هيشتغل، والـ function هترجّع نجاح، والـ rejection ملوش handler، فبعدها بلحظة Node بيقتل الـ process (أول run فوق). درس 09 بيغطي الـ bug القريب منه return ضد return await، وقاعدة الـ lint no-floating-promises، وإحنا هنا بنركز على الميكانيزم.

الـ callbacks نفس الحكاية. الـ throw جوه callback بتاع setTimeout أو event listener بيشتغل بعدين، على stack جديد ملوش علاقة بالـ try اللي حوالين التسجيل، فبيهرب لـ uncaughtException. الـ run التاني فيه 4 حالات. الـ emit() متزامن، فالـ listener اللي بيرمي بيوصل لـ try حوالين الـ emit (عمره ما يوصل لـ try حوالين الـ on). الـ timer جوه promise executor مش بيعمل reject: الـ promise بيفضل pending على طول والـ error بيهرب. والـ listener الـ async بيرجّع promise محدش بيبص عليه، فبيبقى unhandled rejection. الحلول: حط الـ try جوه الـ callback، أو استخدم reject بدل throw، أو new EventEmitter({ captureRejections: true }).

فيه فخ أدق اسمه الـ late await: const p = fetchProfile(); const orders = await fetchOrders(); await p;. لو p عمل reject أثناء الـ await التانية، مفيش عليه handler لسه، فـ Node بيعتبره unhandled والـ process بيموت، حتى لو الكود كله جوه try و await p جاية في السكة. الـ Promise.all بيحط handlers على الاتنين فورًا.

الـ .catch والـ try/await نفس الميكانيزم بس مدى كل واحد مختلف. الـ .catch حلو لـ fallback في سطر واحد على call واحدة، بس بيشوف الـ rejections بس: function مش async بترمي synchronously قبل ما ترجّع الـ promise بتعدّي عليه خالص، إنما try/await بيمسك الاتنين. وكمان .then(ok, fail) مش بيمسك اللي بيترمي من ok، والـ .catch اللي بعده هو اللي بيمسكه. والجدول فوق بيلخص تستخدم إيه إمتى.

فين هستخدمه في شغلي؟ endpoint بتاع dashboard بيجيب الـ profile والـ orders: واحد في الفريق كتب const p = getProfile(); const o = await getOrders(); res.json({ p: await p, o }) عشان "يبقوا parallel". الكود بيعدي في كل الـ tests، ولما خدمة الـ profile ترجّع 503 لمدة دقيقة، كل request بيوقّع الـ pod بدل ما يرجّع error. في الـ code review، أي promise متخزن في متغير وقبل الـ await بتاعه فيه await تانية لازم ينوّر عندك. ونفس الكلام لأي emitter.on('order.paid', async () => …): لو الإيميل فشل، الـ process كله ممكن يقع.

Part 5 — Global handlers 🟡 Intermediateالجزء 5 — الـ global handlers

English

Global handlers are a smoke alarm, not a sprinkler: they tell you something escaped; they can't repair it. In the browser, window.onerror receives (message, source, lineno, colno, error) and returning true suppresses the console message. addEventListener("error", fn, true) gets the same errors as an ErrorEvent, plus resource failures like a broken <img> when you listen in the capture phase. unhandledrejection gives you event.reason and event.promise. A script from another origin reports only Script error. with line 0 and no error object, which makes your CDN bundle's errors useless. The fix is crossorigin="anonymous" on the tag plus an Access-Control-Allow-Origin header; both cases were run in Chrome below. The page keeps running afterwards, so the job here is to report (Sentry and friends hook these same events).

In Node, process.on("uncaughtException", (err, origin) => …) receives synchronous escapes, and process.on("unhandledRejection", (reason, promise) => …) receives rejected promises with no handler. Since Node 15 the default mode is --unhandled-rejections=throw: emit unhandledRejection, and if nobody is listening, raise it as an uncaught exception, which prints the error and exits with code 1. A throw inside your uncaughtException handler exits with code 7. uncaughtExceptionMonitor lets you observe without changing that behaviour, so the process still dies.

Registering a handler turns off the crash: the process continues and even exits with code 0, as the run below shows. So should you log and carry on? Node's docs and experience both say no. After an unexpected throw you don't know what was skipped: a lock not released, a transaction left open, a connection not returned. The simulation below is what "carry on" looks like: every bad payload leaks a pool connection, and after three of them the process is alive, the health check is green, and every request hangs. That's worse than a crash, because a crash gets restarted by Kubernetes or systemd within seconds. Log it, stop accepting work, let in-flight requests finish with a time limit, exit non-zero, and let the supervisor restart you. Section 06 covers the production details (graceful shutdown, draining connections); signals are in CS lesson 11.

في Node، process.on("uncaughtException", (err, origin) => …) بيوصله اللي هرب synchronously، و process.on("unhandledRejection", (reason, promise) => …) بيوصله الـ promises اللي عملت reject من غير handler. من Node 15 الـ default هو --unhandled-rejections=throw: بيبعت unhandledRejection، ولو محدش سامع بيحوّله لـ uncaught exception، وده بيطبع الـ error ويخرج بـ exit code 1. ولو عملت throw جوه handler الـ uncaughtException نفسه بيخرج بـ exit code 7. أما uncaughtExceptionMonitor فبيخليك تتفرج من غير ما يغيّر السلوك، يعني الـ process بيموت برضه. والجدول فوق فيه كل الـ modes.

تسجيل handler بيلغي الـ crash: الـ process بيكمّل وممكن كمان يخرج بـ exit code 0، زي الـ run فوق. طب تسجل وتكمّل؟ الـ docs بتاعة Node والخبرة بيقولوا لأ. بعد throw مش متوقع إنت مش عارف إيه اللي اتنط: lock ماتفكش، transaction مفتوحة، connection مارجعتش. الـ simulation فوق هي شكل "نكمّل": كل payload غلط بيضيّع connection، وبعد 3 منهم الـ process عايش والـ health check أخضر وكل request بيعلّق. ده أوحش من الـ crash، لأن الـ crash بيرجع في ثواني مع Kubernetes أو systemd. سجّل، بطّل تستقبل شغل جديد، سيب الـ requests الشغالة تخلص في وقت محدد، اخرج بـ non-zero، وسيب الـ supervisor يشغّلك من جديد. القسم 06 فيه تفاصيل production (الـ graceful shutdown وتصفية الـ connections)، والـ signals في درس 11 في CS.

فين هستخدمه في شغلي؟ في main.ts بتاع أي service: حط fatal handler زي اللي فوق مرة واحدة، وفي الـ frontend اربط unhandledrejection بـ Sentry أو endpoint بتاعك، وحط crossorigin على الـ scripts اللي على الـ CDN. ولما تدخل مشروع قديم، دوّر على process.on('uncaughtException', console.error) لوحدها: دي إشارة إن الـ service بيكمّل بـ state بايظ، وغالبًا هي سبب "الـ API بيعلّق كل كام يوم ولما نعمل restart بيرجع تمام". الغلطة الشائعة التانية إن الـ handler يبقى async وبيبعت لـ log server وبعدين process.exit(1) من غير حد أقصى للوقت، فالـ process يعلق للأبد لو الـ log server نفسه واقع.
Interview question "Should a Node service keep running after uncaughtException?" → No. State may be corrupt (held locks, leaked connections, half-done work). Log it, drain with a time limit, exit non-zero, and rely on the supervisor to restart. Use the handler for reporting, not recovery.
"المفروض service في Node يكمّل بعد uncaughtException؟" ← لأ. الـ state ممكن تكون بايظة (locks ممسوكة، connections ضايعة، شغل متعمل نصه). سجّل، صفّي في وقت محدد، اخرج بـ non-zero، واعتمد على الـ supervisor يشغّله تاني. الـ handler للتبليغ مش للإصلاح.

type SerializedError = {
  name: string;
  message: string;
  stack?: string;
  code?: string;
  cause?: SerializedError;
};

export function serializeError(input: unknown, seen = new Set<unknown>()): SerializedError {
  if (!(input instanceof Error)) {
    return { name: "NonError", message: String(input) };
  }
  // الـ cycle بيتوقف هنا بدل stack overflow
  if (seen.has(input)) return { name: "Circular", message: input.message };
  seen.add(input);

  const out: SerializedError = { name: input.name, message: input.message, stack: input.stack };
  const code = (input as { code?: unknown }).code;
  if (typeof code === "string") out.code = code;
  if (input.cause !== undefined) out.cause = serializeError(input.cause, seen);
  return out;
}

// شغّله كده: node exercises/ex3-safe-listener.ts
import assert from "node:assert/strict";
import { EventEmitter } from "node:events";

type Listener<A extends unknown[]> = (...args: A) => unknown;

export function safeListener<A extends unknown[]>(
  name: string,
  listener: Listener<A>,
  report: (name: string, err: unknown) => void,
): Listener<A> {
  return (...args: A) => {
    try {
      const result = listener(...args);
      // لو الـ listener async، امسك الـ rejection بتاعه كمان
      if (result instanceof Promise) result.catch((err: unknown) => report(name, err));
    } catch (err) {
      report(name, err);
    }
  };
}

// شغّله كده: node --test exercises/ex4-http-errors.test.ts
import assert from "node:assert/strict";
import { test } from "node:test";
import { ConflictError, NotFoundError, ValidationError } from "../src/errors.ts";
import { toHttpResponse } from "../src/http-errors.ts";

test("404 keeps the safe message", () => {
  const { status, body } = toHttpResponse(new NotFoundError("Order", "ord_1"));
  assert.equal(status, 404);
  assert.equal(body.error.code, "ORDER_NOT_FOUND");
});

test("422 returns the field errors", () => {
  const { status, body } = toHttpResponse(new ValidationError({ qty: "must be >= 1" }));
  assert.equal(status, 422);
  assert.deepEqual(body.error.fields, { qty: "must be >= 1" });
});

test("409 never leaks the pg detail in its cause", () => {
  const cause = Object.assign(new Error("duplicate key"), { detail: "Key (email)=(a@b.c) already exists." });
  const { status, body } = toHttpResponse(new ConflictError("Already exists", "USER_DUPLICATE", { cause }));
  assert.equal(status, 409);
  assert.ok(!JSON.stringify(body).includes("a@b.c"));
});

test("unknown errors become a generic 500", () => {
  const { status, body } = toHttpResponse(new TypeError("Cannot read properties of undefined"));
  assert.equal(status, 500);
  assert.equal(body.error.message, "Something went wrong");
});

Cheat sheet · الخلاصة

  • message/stack are non-enumerable: JSON.stringify(err) is {}. Log via a serializer.
  • TypeError/ReferenceError = bug, don't swallow. Runtime SyntaxError = bad external text, handle it.
  • finally is for cleanup: return/throw/continue inside it replaces or swallows what was pending.
  • Throw only Error objects. catch (err) is unknown; normalize third-party values.
  • Hierarchy: AppError with a stable code and status; name as a string literal, because minifiers rename classes.
  • captureStackTrace isn't needed for constructor frames on V8; use it to hide helpers.
  • instanceof inside one service; err.code across packages, realms, workers and queues.
  • One mapper from error to response. Express 5 forwards async rejections; Express 4 crashes without a wrapper.
  • { cause } when the meaning changes. err.stack doesn't include it; never send it to the client.
  • A try only covers failures while its frame is on the stack: missing await, timers and listeners all escape.
  • A promise stored and awaited after another await can crash the process: use Promise.all.
  • Global handlers are for reporting: log, drain with a time limit, exit non-zero. Default for an unhandled rejection is exit code 1.
بالعامية
  • الـ message والـ stack non-enumerable، فـ JSON.stringify(err) بيطلع {}. سجّل عن طريق serializer.
  • TypeError و ReferenceError معناهم bug، متبلعهمش. والـ SyntaxError وقت التشغيل معناه نص غلط من بره، اتعامل معاه.
  • الـ finally للـ cleanup: أي return أو throw أو continue جواه بيلغي أو يبلع اللي كان مستني.
  • ارمي Error objects بس. الـ catch (err) نوعه unknown، وأي قيمة من مكتبة خارجية حوّلها.
  • الـ hierarchy: AppError فيه code ثابت و status، والـ name يبقى string literal لأن الـ minifiers بتغيّر أسامي الـ classes.
  • الـ captureStackTrace مش لازم لـ frames الـ constructors على V8، استخدمه تخبي الـ helpers.
  • الـ instanceof جوه الـ service الواحد، و err.code بين الـ packages والـ realms والـ workers والـ queues.
  • mapper واحد من الـ error للـ response. Express 5 بيوصّل الـ async rejections لوحده، و Express 4 بيقع من غير wrapper.
  • { cause } لما المعنى يتغير. الـ err.stack مفيهوش الـ cause، وعمرك ما تبعته للعميل.
  • الـ try بيغطي الفشل والـ frame بتاعه على الـ stack بس: الـ await الناقصة والـ timers والـ listeners كلهم بيهربوا.
  • promise متخزن ومستني await بعد await تانية ممكن يوقّع الـ process: استخدم Promise.all.
  • الـ global handlers للتبليغ: سجّل، صفّي في وقت محدد، اخرج بـ non-zero. والـ default للـ unhandled rejection هو exit code 1.
