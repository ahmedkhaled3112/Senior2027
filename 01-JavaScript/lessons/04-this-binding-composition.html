Why this matters · ليه ده مهم

English

This lesson is about how functions connect. Cannot read properties of undefined (reading 'gateway') on a route that passed every unit test is a lost this, and it reaches production because the compiler doesn't catch it when the method is passed as a callback. A retried job that discounts an invoice twice is an impure function. A React screen that doesn't update after a successful click is a mutated state object. Partial application is how you inject dependencies without a framework, and pipe is how a pricing rule stays readable. "What is this here?", "implement bind" and "why must React state be immutable?" are standard interview questions, and each one has a precise answer you can run.

Part 1 — this: the 5 rules 🟡 Intermediateالجزء 1 — الـ this: القواعد الخمسة

English

Think of this as a hidden parameter filled in at call time. For a regular function, it doesn't matter where the function was written or which object it "belongs to". All that matters is how this particular call is written. Five rules cover every case:

  1. Method call, obj.method(): this is the object before the last dot. In a.b.c() it's a.b.
  2. Plain call, fn(): undefined in strict mode (all ES modules, all class bodies, "use strict"), globalThis in sloppy mode.
  3. Arrow function: no this of its own. It reads this from the scope where it was written, and nothing at call time can change it.
  4. new Fn(): this is a brand-new object (the full steps are in lesson 06).
  5. Explicit, call / apply / bind: you pass the value yourself.

Precedence when several apply: new beats bind; bind beats a method call and call; a method call beats a plain call. Arrows are outside the contest.

Event handlers and callbacks aren't a sixth rule. They are someone else's code using rule 5, so the caller decides. A DOM listener gets the element, an EventEmitter listener gets the emitter, Node's setTimeout callback gets a Timeout object, the browser's gets window, and in React 19.3 a method passed as onClick={form.onClick} ran with this === undefined. Each of those results comes from a real run.

بالعامية

فكّر في this على إنه parameter مخفي بيتملى وقت الـ call. في الـ regular function، مش مهم الـ function اتكتبت فين ولا "تبع" أنهي object. المهم بس الـ call دي بالذات مكتوبة إزاي. وفيه 5 قواعد بيغطوا كل الحالات:

  1. الـ method call، obj.method(): الـ this هو الـ object اللي قبل آخر نقطة. في a.b.c() هيبقى a.b.
  2. الـ plain call، fn(): undefined في الـ strict mode (كل ES modules، وكل class bodies، و"use strict")، وglobalThis في الـ sloppy mode.
  3. الـ arrow function: مالهاش this خاص بيها. بتقراه من الـ scope اللي اتكتبت فيه، ومفيش حاجة وقت الـ call تقدر تغيّره.
  4. new Fn(): الـ this هو object جديد خالص (الخطوات كلها في درس 06).
  5. الـ explicit، call / apply / bind: إنت بتبعت القيمة بنفسك.

الأولوية لو أكتر من قاعدة انطبقت: new أقوى من bind؛ وbind أقوى من الـ method call وcall؛ والـ method call أقوى من الـ plain call. والـ arrow برا المنافسة أصلًا.

الـ event handlers والـ callbacks مش قاعدة سادسة. دي كود حد تاني بيستخدم القاعدة 5، يعني اللي بينادي هو اللي بيقرر. الـ DOM listener بياخد العنصر، وEventEmitter listener بياخد الـ emitter، وsetTimeout في Node بيدّي Timeout object، وفي الـ browser بيدّي window، وفي React 19.3 الـ method اللي اتبعتت كـ onClick={form.onClick} اشتغلت وthis === undefined. وكل النتايج دي من تشغيل حقيقي.

فين هستخدمه في شغلي؟ لما تشوف في الـ logs Cannot read properties of undefined (reading 'x') والسطر فيه this.x، ماتدوّرش على الـ data: بص مين نادى الـ method دي وإزاي. وفي Node، this في callback بتاع setTimeout مش undefined، هو Timeout، فالـ error هيتكلم عن الـ property اللي بعدها وهيضللك. وفي الـ frontend، method اتبعتت لـ addEventListener مش هتقع، هتقرا من الزرار وترجّع undefined في صمت، فتلاقي الإجمالي NaN في الشاشة. ولو قريت compiled code ولقيت (0, charge_js_1.charge)(100)، ده TS 7 وهو بيعمل compile لـ CommonJS: الـ (0, …) عشان الـ this ميبقاش الـ exports object.
Interview question "How is this determined?" → By the call site, except for arrows. Check in order: arrow (lexical), new (new object), bind/call/apply (given value), obj.method() (obj), otherwise a plain call: undefined in strict mode, globalThis in sloppy. A library calling your callback can pick any value, so check its docs or log it.
"الـ this بيتحدد إزاي؟" ← من الـ call site، ماعدا الـ arrow. افحص بالترتيب: arrow (lexical)، new (object جديد)، bind/call/apply (القيمة اللي اتبعتت)، obj.method() (يبقى obj)، وغير كده plain call: undefined في strict وglobalThis في sloppy. والمكتبة اللي بتنادي الـ callback بتاعك تقدر تختار أي قيمة، فشوف الـ docs أو اطبعها.

Part 2 — The lost-this bug 🟡 Intermediateالجزء 2 — bug ضياع الـ this

English

The expression svc.charge alone evaluates to a plain function value. The link to svc exists only when the dot and the call are written together: svc.charge(…). So app.post("/pay", svc.charge) hands Express the bare function, and Express's router later runs fn(req, res, next), which is rule 2. Class bodies are strict, so this is undefined, and the first this.gateway crashes. Express 5 forwards the rejected promise to the error handler, so the client sees a 500.

The same thing happens anywhere a method is passed as a value: destructuring, array.map, promise.then, and timers. The symptom varies by caller, which makes it confusing. With setTimeout in Node, this is a Timeout, so this.gateway is undefined and the crash names the next property. With EventEmitter, this is the emitter, and a read may quietly return undefined with no crash at all.

  svc.charge(req, res)                 app.post("/pay", svc.charge)
  ─────────────────────                ─────────────────────────────
  1. find charge on svc                1. find charge on svc
  2. call it with base = svc           2. pass only the function VALUE
     this = svc          OK            3. later, inside the router:
                                             fn(req, res, next)
                                          this = undefined     CRASH
على الشمال: النقطة والـ call مكتوبين مع بعض، فالـ engine بيلاقي charge على svc وينادي عليها والـ this هو svc. على اليمين: svc.charge بتتقري كقيمة بس، فالـ router استلم function لوحدها، وبعدين نادى عليها fn(req, res, next) من غير أي object قبلها، فالـ this بقى undefined والكود وقع.
// شغّله: node src/lost-this.ts
import express from "express";
import type { ErrorRequestHandler, Request, Response } from "express";

class PaymentService {
  gateway = { charge: async (cents: number) => ({ id: "ch_1", cents }) };

  async charge(req: Request, res: Response) {
    const receipt = await this.gateway.charge(req.body.cents);
    res.json(receipt);
  }

  // الـ class-field arrow: الـ this اتمسك وقت إنشاء الـ instance
  chargeField = async (req: Request, res: Response) => {
    const receipt = await this.gateway.charge(req.body.cents);
    res.json(receipt);
  };

English

Which fix? The arrow wrapper is the default for wiring: it costs nothing per instance and looks the method up on every call, so a spy installed later still works. bind at the call site is equally cheap, but it captures the function at wiring time. Class-field arrows and bind in the constructor create one function per method per instance. That's irrelevant for a singleton service, and real money if you allocate many objects: 3 methods cost about 40 bytes per instance on the prototype, about 272 bytes as field arrows, and about 208 bytes bound in the constructor. On a million in-memory orders that's about 230 MB more. Field arrows also become own enumerable properties, aren't on the prototype so you can't spy on them there, and can't be reached through super.

Part 3 — call, apply, bind 🟡 Intermediateالجزء 3 — الـ call والـ apply والـ bind

English

All three set this explicitly. call and apply run the function immediately and differ only in how arguments are passed. bind runs nothing: it returns a new function with this fixed and, optionally, the first arguments preset. strictBindCallApply, part of strict, type-checks the arguments of all three.

Runs now?ArgumentsReturns
fn.call(ctx, a, b)YesOne by oneThe result
fn.apply(ctx, [a, b])YesAn arrayThe result
fn.bind(ctx, a)NoPreset first, rest laterA new function
الفرق: call بتنفذ دلوقتي والـ arguments واحدة واحدة وبترجّع النتيجة. apply بتنفذ دلوقتي والـ arguments في array وبترجّع النتيجة. bind مش بتنفذ، بتثبّت أول arguments والباقي ييجي بعدين، وبترجّع function جديدة.

Details worth knowing about bind: the first bind wins, so rebinding does nothing; the result is named bound x, and its length is reduced by the preset arguments; on an arrow it can't change this, but it can still preset arguments.

Where they still matter: borrowing a method, like Object.prototype.hasOwnProperty.call(payload, "amount") when a JSON payload could contain its own hasOwnProperty key (Object.hasOwn is the modern form); and forwarding in wrappers. Math.max.apply(null, prices) is the old way to spread an array; both it and Math.max(...prices) put every element on the stack, so a big enough array throws RangeError. Here 100,000 worked and 200,000 didn't, and the exact limit depends on stack size. Use a loop for data you don't control.

Writing bind by hand teaches the whole mechanism: a closure holds fn, thisArg and the preset arguments; new.target detects a new call, in which case thisArg is ignored. Preserving length isn't cosmetic: Express reads it to recognize error handlers, so a plain (...args) => handler(...args) wrapper with length 0 silently stops your error middleware from running (lesson 03, Part 2), while native bind keeps it at 4.

import assert from "node:assert/strict";

function myBind<T, P extends unknown[], L extends unknown[], R>(
  fn: (this: T, ...args: [...P, ...L]) => R,
  thisArg: T,
  ...preset: P
): (...later: L) => R {
  function bound(this: unknown, ...later: L) {
    const args = [...preset, ...later] as [...P, ...L];
    // لو اتنادت بـ new: الـ new بيكسب والـ thisArg بيتجاهل، زي الـ native
    if (new.target) {
      const newTarget = new.target === bound ? fn : new.target;
      return Reflect.construct(fn as unknown as Function, args, newTarget);
    }
    return fn.apply(thisArg, args);
  }
  // الـ Express بيعتمد على fn.length، فلازم نحافظ عليه
  Object.defineProperty(bound, "length", { value: Math.max(0, fn.length - preset.length) });
  Object.defineProperty(bound, "name", { value: `bound ${fn.name}` });
  return bound as unknown as (...later: L) => R;
}

التلاتة بيحددوا الـ this بإيدك. call وapply بينفذوا الـ function على طول، والفرق بينهم بس في طريقة بعت الـ arguments. bind مش بتنفذ حاجة: بترجّع function جديدة الـ this بتاعها ثابت، ولو عايز أول arguments متحددين كمان. وstrictBindCallApply، وهو جزء من strict، بيشيك على الـ arguments في التلاتة.

تفاصيل مهمة في bind: أول bind هو اللي بيكسب، فالـ rebind مش بيعمل حاجة؛ والناتج اسمه bound x، والـ length بتاعه بيقل بعدد الـ arguments المتحددة؛ ومع الـ arrow مش بتقدر تغيّر الـ this، بس تقدر تحدد arguments.

لسه بيفرقوا فين؟ في استعارة method زي Object.prototype.hasOwnProperty.call(payload, "amount") لما JSON payload ممكن يبقى فيه key اسمه hasOwnProperty (الشكل الحديث Object.hasOwn)؛ وفي الـ forwarding جوه الـ wrappers. وMath.max.apply(null, prices) الطريقة القديمة لفرد array؛ وهي وMath.max(...prices) الاتنين بيحطوا كل عنصر على الـ stack، فالـ array الكبيرة كفاية بترمي RangeError. هنا 100,000 اشتغلت و200,000 لأ، والحد بالظبط بيعتمد على حجم الـ stack. للـ data اللي مش في إيدك استخدم loop.

لما تكتب bind بإيدك بتفهم الآلية كلها: closure ماسكة fn وthisArg والـ arguments المتحددة؛ وnew.target بيكشف لو اتنادت بـ new، ووقتها الـ thisArg بيتجاهل. والحفاظ على length مش شكليات: Express بيقراه عشان يعرف الـ error handlers، فـ wrapper عادي زي (...args) => handler(...args) الـ length بتاعه 0 بيوقف الـ error middleware في صمت (درس 03، الجزء 2)، إنما bind بيسيبه 4، زي ما الـ output طلّع 0 4 4.

فين هستخدمه في شغلي؟ لو بتعمل wrapper عام لـ methods (logging، tracing، retry)، استخدم fn.apply(this, args) جواه عشان الـ this اللي الـ caller بعته يوصل. ولو بتلف Express error handler، استخدم bind أو احتفظ بالأربع parameters صريحين. وأي Math.max(...values) على نتيجة query أو CSV خليها reduce: الكود شغال في التست على 10 صفوف، ويرمي RangeError أول ما عميل كبير يرفع ملف فيه 300,000 صف.

English

Partial application fixes some arguments now and returns a function that takes the rest. Currying is more specific: it transforms f(a, b, c) into f(a)(b)(c), one argument at a time. Currying is one way to get partial application, but you rarely need the general form. In backend code, the pattern that pays off is a function with two levels and a meaning for each: createGetOrderHandler(deps)(req) takes dependencies once at boot and the request many times. That is dependency injection with nothing but closures, and the test just passes plain functions instead of a mocking library. withTenant(tenantId)(query) fixes the tenant so no query can forget it.

Part 5 — compose & pipe 🟡 Intermediateالجزء 5 — الـ compose والـ pipe

English

pipe(f, g, h)(x) means h(g(f(x))): data flows left to right, in reading order. compose(f, g, h)(x) means f(g(h(x))): right to left, like the math notation. Both are one line of reduce / reduceRight. Most codebases should prefer pipe. The steps must take one input and return one output, which is why curried steps fit so well: addVat(14) is configured now and receives the price later.

Order is business logic. A coupon before VAT and a coupon after VAT give 17100 and 17800 on the same 20000 cart. Rounding early changes the result too. A pipeline makes that order visible on one line, which is the real benefit. Types: TypeScript can't express a variadic chain where each type feeds the next without tricks, so libraries such as fp-ts and RxJS use overloads, and so does this code. A wrong order becomes a compile error.

  pipe(applyDiscount(10), addVat(14), roundToCents)(19999)

  19999 ─▶ applyDiscount(10) ─▶ 17999.1 ─▶ addVat(14) ─▶ 20518.974 ─▶ roundToCents ─▶ 20519

  compose(roundToCents, addVat(14), applyDiscount(10))(19999)
          ◀──────────── data flows right to left ──────────
فوق: الـ pipe بتمشي من الشمال لليمين زي القراءة: 19999 بعد خصم 10% بتبقى 17999.1، وبعد VAT 14% بتبقى 20518.974، وبعد التقريب 20519. تحت: الـ compose نفس الخطوات ونفس النتيجة، بس بتتكتب بالعكس والـ data بتمشي من اليمين للشمال.

function pipe<A, B>(f1: (a: A) => B): (a: A) => B;
function pipe<A, B, C>(f1: (a: A) => B, f2: (b: B) => C): (a: A) => C;
function pipe<A, B, C, D>(f1: (a: A) => B, f2: (b: B) => C, f3: (c: C) => D): (a: A) => D;
function pipe<A, B, C, D, E>(
  f1: (a: A) => B,
  f2: (b: B) => C,
  f3: (c: C) => D,
  f4: (d: D) => E,
): (a: A) => E;
function pipe(...fns: Array<(value: unknown) => unknown>) {
  return (input: unknown) => fns.reduce((value, fn) => fn(value), input);
}

// الـ compose نفس الفكرة بس من اليمين للشمال، زي ⁦f(g(h(x)))⁩

  return (input: number) => fns.reduceRight((value, fn) => fn(value), input);

الـ async pipe. اعمل await لكل خطوة في loop. الخطوات بتمشي واحدة ورا التانية بالظبط، والـ rejection بتنط على كل اللي بعدها. وفيه نقطتين لازم تعرفهم. الأولى: النط مش معناه رجوع: في المثال الـ stock فضل محجوز بعد ما الكارت اترفض، فالـ checkout الحقيقي محتاج خطوة compensation (فكرة الـ saga). التانية: استخدم for مع await بدل reduce مع then. السلوك واحد، بس V8 يقدر يتتبع await في الـ async stack traces. الـ output الحقيقي بيوري السلسلة كاملة مع await، و frame واحد بس مع then.

وباقي الكلام عن الـ composition والـ point-free style، و pipeline operator بتاع TC39 في درس 20.

Part 6 — Pure functions, side effects, immutability 🟡 Intermediateالجزء 6 — الـ pure functions والـ side effects والـ immutability

English

A pure function has two properties: the same inputs always give the same output, and it has no observable side effects. Side effects include writing to a database, sending an email, logging, mutating an argument, and changing a module variable. Hidden inputs break purity too: Date.now(), Math.random(), process.env.

calculateInvoiceImpure below has all of it, and it shows up as a real bug: job queues deliver at least once, so a retry applies the coupon a second time, and the same order is invoiced at 2052 and then 1847. The pure version receives everything through its parameters and returns a new object. Testing it needs no mocks, no fake timers and no database, and calling it twice is always safe. Object.freeze helps catch accidental mutation in tests, but it's shallow, as the output shows.

You can't make a whole backend pure, and you shouldn't try. Push the I/O to the edges: functional core, imperative shell. The full treatment is in lesson 20.

// شغّله: node src/pure.ts
import assert from "node:assert/strict";

type Item = { sku: string; cents: number; qty: number };
type Order = { id: string; items: Item[]; couponPercent: number };

const makeOrder = (): Order => ({
  id: "o1",
  items: [{ sku: "kb", cents: 1000, qty: 2 }],
  couponPercent: 10,

// ❌ بيقرا الساعة، وبيعدّل الـ order اللي جاله، وبيزوّد counter برا
let lastInvoiceNumber = 0;
function calculateInvoiceImpure(order: Order) {
  for (const item of order.items) item.cents -= (item.cents * order.couponPercent) / 100;
  const subtotal = order.items.reduce((sum, item) => sum + item.cents * item.qty, 0);
  return {
    number: ++lastInvoiceNumber,
    issuedAt: Date.now(),
    total: Math.round(subtotal * 1.14),
  };
}

// الـ queue بتعمل ⁦retry (at-least-once)⁩، فالخصم بيتطبق مرتين على نفس الـ order
const shared = makeOrder();
const firstTry = calculateInvoiceImpure(shared);
const retry = calculateInvoiceImpure(shared);
console.log(firstTry.total, retry.total, firstTry.number, retry.number);
// → 2052 1847 1 2

// ✅ كل المدخلات ظاهرة في الـ signature، والنتيجة object جديد
type InvoiceContext = { number: number; now: number; vatPercent: number };
function calculateInvoice(order: Order, { number, now, vatPercent }: InvoiceContext) {
  const subtotal = order.items.reduce((sum, item) => {
    const discounted = item.cents - (item.cents * order.couponPercent) / 100;
    return sum + discounted * item.qty;
  }, 0);
  return {
    number,
    issuedAt: now,
    total: Math.round(subtotal + (subtotal * vatPercent) / 100),
  };
}

English

Why React depends on immutability. React decides whether anything changed by comparing references with Object.is: in setState, in memo props, and in hook dependencies. It never looks inside objects, because deep comparison on every render would be too slow. So if you mutate and pass the same reference, React concludes nothing changed. The Chrome output below shows it: the mutating click does not re-render. The mutation isn't gone, though: the next immutable click shows 3 items, not 2. And because the immutable update keeps shipping as the same reference, the memo child doesn't re-render.

Updating nested data immutably. Copy every level on the path to the change and leave everything else shared (structural sharing). A top-level spread is shallow, so its nested objects are still the original ones. structuredClone gives a correct copy, but it breaks reference equality everywhere, so every memo re-renders. Immer lets you write mutations on a draft and returns the same structural sharing, frozen. ES2023 added non-mutating array methods: toSorted, toSpliced, with. And const only prevents reassignment; it doesn't make anything immutable.

// الـ component ده اتشغّل في Chrome حقيقي بـ React 19.3

  renders.shipping++;

  const [order, setOrder] = useState(initial);

  const addItemMutating = () => {

  };

  const addItemImmutable = () => {

    </>
  );
}

بالعامية

الـ pure function ليها صفتين: نفس المدخلات بتدّي نفس الناتج دايمًا، ومفيهاش side effects باينة. والـ side effects زي الكتابة في الـ DB، وبعت email، والـ logging، وتعديل argument، وتغيير variable في الـ module. وكمان المدخلات المخفية بتكسر الـ purity: Date.now() وMath.random() وprocess.env.

calculateInvoiceImpure فيها كل ده، وبيطلع bug حقيقي: الـ job queues بتوصّل الرسالة مرة على الأقل (at-least-once)، فالـ retry بيطبق الكوبون تاني، ونفس الـ order بيتفوتر بـ 2052 وبعدين 1847. الـ pure version بتاخد كل حاجة من الـ parameters وبترجّع object جديد. والتست بتاعها مش محتاج mocks ولا fake timers ولا DB، وتناديها مرتين في أمان. وObject.freeze بيساعد يمسك أي mutation بالغلط في الـ tests، بس هو shallow زي ما الـ output بيوري (qty بقى 99).

مش هتقدر تخلي backend كامل pure، ومش المطلوب. ادفع الـ I/O للأطراف: functional core, imperative shell. والشرح الكامل في درس 20.

ليه React معتمد على الـ immutability؟ الـ React بيعرف إن حاجة اتغيرت بمقارنة الـ references بـ Object.is: في setState، وفي props بتاعة memo، وفي الـ hook dependencies. عمره ما بيبص جوه الـ objects، لأن المقارنة العميقة مع كل render هتبقى بطيئة أوي. فلو عدّلت وبعت نفس الـ reference، الـ React هيقرر إن مفيش حاجة اتغيرت. والـ output بيوري ده: دوسة الـ mutate مفيهاش re-render. بس الـ mutation ماراحتش: دوسة الـ immutable اللي بعدها بتوري 3 عناصر مش 2. ولأن التحديث الـ immutable ساب shipping بنفس الـ reference، الـ memo child ماعملش re-render.

تعديل nested data بشكل immutable. انسخ كل مستوى على المسار للتغيير، وسيب الباقي مشترك (structural sharing). الـ spread في المستوى الأول shallow، فالـ nested objects لسه هي الأصلية. وstructuredClone بيدّيك نسخة صح، بس بيكسر الـ reference equality في كل حاجة، فكل memo هيعمل re-render. والـ Immer بيخليك تكتب mutations على draft وبيرجّع نفس الـ structural sharing ومعمول له freeze. وES2023 ضاف array methods مش بتعدّل الأصل: toSorted وtoSpliced وwith. والـ const بيمنع إعادة الربط بس، مش بيخلي حاجة immutable.

فين هستخدمه في شغلي؟ في الـ backend: طلّع حساب الفاتورة والخصومات والعمولات لـ pure functions، وخلي الـ controller يقرا من الـ DB، ينادي الـ function، ويكتب. كده الـ retry من BullMQ مش هيخصم مرتين، وعندك 200 test من غير DB بيخلصوا في ثانية. والـ now يتبعت كـ parameter، فتجرب حالة "آخر يوم في الشهر" من غير fake timers. وفي Next: لو الـ state اتغير والشاشة ماتحدثتش، أول حاجة تدوّر عليها push أو sort أو order.x = … على object جاي من useState. ولو الـ reducer فيه تعديل nested عميق، استخدم Immer بدل 5 مستويات spread.
Interview question "Why must React state be updated immutably?" → React detects changes by reference with Object.is, in setState, memo and hook dependencies. Mutating and setting the same reference looks like no change, so it skips the render. New references along the changed path signal the change, and sharing the untouched parts lets memo skip work. Then mention the trade-off: structuredClone is correct but defeats memo, and Immer gives the sharing for you.
"ليه لازم الـ state في React يتحدث بشكل immutable؟" ← الـ React بيكشف التغيير بالـ reference عن طريق Object.is، في setState وmemo والـ hook dependencies. لو عدّلت وبعت نفس الـ reference، هيبان مفيش تغيير فبيتخطى الـ render. والـ references الجديدة على المسار المتغير بتبلّغ بالتغيير، ومشاركة الأجزاء اللي ماتلمستش بتخلي memo يوفّر شغل. وبعدين اذكر الـ trade-off: structuredClone صح بس بيبوّظ فايدة memo، و Immer بيعمل الـ sharing بدالك.

Solution · الحل 
// شغّله: node src/my-call.ts
import assert from "node:assert/strict";

// الفكرة: القاعدة 1 نفسها. حط الـ function على الـ object مؤقتًا ونادي عليها بنقطة
function myCall<T extends object, A extends unknown[], R>(
  fn: (this: T, ...args: A) => R,
  thisArg: T,
  ...args: A
): R {
  // الـ Symbol عشان مندوسش على property موجودة بنفس الاسم
  const key = Symbol("fn");
  const target = thisArg as T & Record<symbol, unknown>;
  Object.defineProperty(target, key, { value: fn, configurable: true });
  try {
    return (target[key] as (...args: A) => R)(...args);
  } finally {
    delete target[key];
  }
}

function myApply<T extends object, A extends unknown[], R>(
  fn: (this: T, ...args: A) => R,
  thisArg: T,
  args: A,
): R {
  return myCall(fn, thisArg, ...args);
}

function describeCharge(this: { currency: string }, cents: number) {
  return `${cents} ${this.currency}`;
}
const egp = { currency: "EGP" };
assert.equal(myCall(describeCharge, egp, 100), "100 EGP");
assert.equal(myApply(describeCharge, egp, [200]), "200 EGP");
// الـ object رجع زي ما كان: مفيش property زيادة
assert.deepEqual(Reflect.ownKeys(egp), ["currency"]);
console.log("all passed");
// → all passed
3. A checkout pipe you can debug 🔴 hard Write pipeAsyncLabeled({ name, run }, …). It reports each step's name and duration through a callback, including the step that fails. A failure must be rethrown as step "charge" failed, with the original error kept in cause.

Solution · الحل 
// شغّله: node src/pipe-labels.ts
import assert from "node:assert/strict";

type Step<T> = { name: string; run: (value: T) => T | Promise<T> };
type Timing = { name: string; ms: number };

function pipeAsyncLabeled<T>(...steps: Array<Step<T>>) {
  return async (input: T, onStep: (timing: Timing) => void = () => {}): Promise<T> => {
    let value = input;
    for (const { name, run } of steps) {
      const start = performance.now();
      try {
        value = await run(value);
      } catch (cause) {
        // الـ cause بيحافظ على الـ error الأصلي، والـ message بتقول مين الخطوة
        throw new Error(`step "${name}" failed`, { cause });
      } finally {
        onStep({ name, ms: performance.now() - start });
      }
    }
    return value;
  };
}

const seen: string[] = [];
const checkout = pipeAsyncLabeled<number>(
  { name: "validate", run: (cents) => cents },
  { name: "charge", run: async (cents) => {
      if (cents > 100) throw new Error("card declined");
      return cents;
    } },
  { name: "receipt", run: (cents) => cents + 1 },
);

assert.equal(await checkout(50, (t) => seen.push(t.name)), 51);
assert.deepEqual(seen, ["validate", "charge", "receipt"]);

seen.length = 0;
await assert.rejects(checkout(500, (t) => seen.push(t.name)), (err: Error) => {
  assert.equal(err.message, 'step "charge" failed');
  assert.equal((err.cause as Error).message, "card declined");
  return true;
});
// الخطوة اللي فشلت متسجلة، واللي بعدها متنفذتش
assert.deepEqual(seen, ["validate", "charge"]);
console.log("all passed");
// → all passed

Cheat sheet · الخلاصة

  • this is set at call time. Order: arrow (lexical) → new → bind/call/apply → obj.method() → plain call.
  • Plain call: undefined in ESM, class bodies and strict mode; globalThis in sloppy CJS. A .ts file with no "type" and no import is sloppy.
  • Callers decide for callbacks: DOM gives the element, EventEmitter the emitter, Node's setTimeout a Timeout, the browser's window, React undefined.
  • svc.charge without a call is a bare function. Default fix: (req, res) => svc.charge(req, res).
  • Field arrows and constructor bind: a function per method per instance (≈ 40 vs ≈ 272 bytes here), no prototype spy, no super. Fine for singletons.
  • The compiler misses a method passed as a callback. @typescript-eslint/unbound-method catches it, and needs TS ≤ 6.0 for now.
  • call: args one by one, runs now. apply: array, runs now. bind: returns a function; the first bind wins; new beats it; it keeps a correct length.
  • Wrappers with ...args have length 0, which breaks Express error handlers. Math.max(...hugeArray) throws RangeError.
  • Partial application fixes arguments; currying is a chain of one-argument calls. Two-level factories are good DI. General curry() loses generics, optional params and overloads, and hides the configuration site from stack traces.
  • pipe: left to right. compose: right to left. Order is business logic. Async: for + await for better stacks; a rejection skips later steps but undoes nothing.
  • Pure: same input, same output, no side effects. Inject now. Functional core, imperative shell.
  • React compares references with Object.is. Copy the changed path, share the rest. structuredClone defeats memo; Immer and toSorted/with/toSpliced help.
بالعامية
  • الـ this بيتحدد وقت الـ call. الترتيب: arrow (lexical) ← new ← bind/call/apply ← obj.method() ← plain call.
  • الـ plain call: undefined في ESM والـ class bodies والـ strict mode؛ وglobalThis في sloppy CJS. وملف .ts من غير "type" ومن غير import بيبقى sloppy.
  • في الـ callbacks اللي بينادي هو اللي بيقرر: الـ DOM بيدّي العنصر، وEventEmitter بيدّي الـ emitter، وsetTimeout في Node بيدّي Timeout، وفي الـ browser بيدّي window، و React بيدّي undefined.
  • svc.charge من غير call عبارة عن function لوحدها. الحل الافتراضي: (req, res) => svc.charge(req, res).
  • الـ field arrows وbind في الـ constructor: function لكل method في كل instance (≈ 40 مقابل ≈ 272 byte هنا)، ومفيش spy على الـ prototype ولا super. عادي مع الـ singletons.
  • الـ compiler مش بيمسك method اتبعتت كـ callback. اللي بيمسكها @typescript-eslint/unbound-method، ومحتاجة TS ≤ 6.0 لحد دلوقتي.
  • call: الـ args واحدة واحدة وبتنفذ دلوقتي. apply: array وبتنفذ دلوقتي. bind: بترجّع function؛ أول bind بيكسب؛ new أقوى منها؛ والـ length بيفضل مظبوط.
