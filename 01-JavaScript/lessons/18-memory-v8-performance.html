Why this matters · ليه ده مهم

English

The memory graph that climbs for six hours and ends in an OOMKilled pod is one of the most common production incidents in Node, and most engineers can only answer it by restarting. This lesson gives you the tools to answer it properly: read a --trace-gc line, take two heap snapshots, and follow the retainer path to the exact Map holding the memory. It also gives you a working model of the JIT, so you can tell which performance advice is real and which is folklore. Every number below comes from running the code. Some of the results contradict common advice: try/catch costs nothing measurable here, and += beats join.

بالعامية

جراف الـ memory اللي بيطلع 6 ساعات وبيخلص بـ pod متعمله OOMKilled من أشهر الـ incidents في Node، وأغلب الناس إجابتهم الوحيدة عليه restart. الدرس ده بيديك الأدوات اللي تجاوب بيها صح: تقرا سطر --trace-gc، تاخد اتنين heap snapshots، وتمشي ورا الـ retainer path لحد الـ Map اللي ماسكة الـ memory بالظبط. وكمان بيديك صورة شغالة للـ JIT، عشان تعرف أنهي نصيحة performance حقيقية وأنهي كلام متوارث. وكل رقم تحت جاي من تشغيل الكود فعلًا، وفيه نتايج ضد الكلام المشهور: try/catch هنا تكلفته مش ظاهرة في القياس، و+= أسرع من join.

Part 1 — GC in V8 🔴 Advancedالجزء 1 — الـ GC في V8

English

The general theory (roots and reachability, mark-sweep vs mark-compact vs copying, the generational hypothesis, tail latency) is in 01-CS Lesson 12, Part 7. Here we watch V8 do it. In short, mark-and-sweep finds everything reachable from the roots and frees the rest, and generational collection splits the heap by age because most objects die young.

New objects go into the young generation, two semi-spaces collected by the Scavenger. It copies the survivors to the other semi-space and abandons the rest in one step, so its cost follows the number of survivors, not the amount of garbage. An object that survives twice is promoted to the old generation, which is collected by Mark-Compact. Marking there runs incrementally in small steps and concurrently on helper threads, so the stop-the-world pause is only the final part. That's why the Mark-Compact lines below show a pause of ≈ 2 ms with marking that took ≈ 27 ms of wall time.

The word allocation failure in a trace is not an error. It means the semi-space filled up, which is the normal trigger for a scavenge. mu is mutator utilization, the share of time your JavaScript got to run: ≈ 0.88 here means GC took about 12% in that window. Inside a running service, you don't need the flag: a PerformanceObserver on gc entries gives the same numbers as metrics.

// شغّله كده: node --trace-gc --max-old-space-size=256 gc-churn.ts

// شغّله كده: node gc-observer.ts 0   أو   node gc-observer.ts 50
// الرقم هو نسبة الـ objects اللي بتعيش (survival %)، والـ observer بيقيس الـ GC من جوه الـ process
import { PerformanceObserver, constants } from "node:perf_hooks";

const survivalPercent = Number(process.argv[2] ?? 0);
const KINDS: Record<number, string> = {
  [constants.NODE_PERFORMANCE_GC_MINOR]: "scavenge",
  [constants.NODE_PERFORMANCE_GC_MAJOR]: "mark-compact",
  [constants.NODE_PERFORMANCE_GC_INCREMENTAL]: "incremental",
  [constants.NODE_PERFORMANCE_GC_WEAKCB]: "weakcb",
};
const stats = new Map<string, { count: number; ms: number; max: number }>();
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    const kind = KINDS[(entry as unknown as { detail: { kind: number } }).detail.kind] ?? "other";
    const s = stats.get(kind) ?? { count: 0, ms: 0, max: 0 };
    s.count++;
    s.ms += entry.duration;
    s.max = Math.max(s.max, entry.duration);
    stats.set(kind, s);
  }
});
observer.observe({ entryTypes: ["gc"] });

// نفس عدد الـ allocations في كل مرة، والفرق بس في كام واحد فضل عايش شوية
const window: object[] = new Array(200_000).fill(null);
// الـ last بيضمن إن الـ object بيهرب من الـ loop، فالـ JIT ميشيلش الـ allocation
const holder: { last: object | null } = { last: null };
const started = performance.now();
for (let i = 0; i < 30_000_000; i++) {
  const order = { id: i, cents: i % 9000, status: "new" };
  holder.last = order;
  if (i % 100 < survivalPercent) window[i % window.length] = order;
}
const elapsed = performance.now() - started;

بالعامية

النظرية العامة (الـ roots والـ reachability، و mark-sweep قصاد mark-compact قصاد copying، والـ generational hypothesis، والـ tail latency) موجودة في 01-CS Lesson 12، الجزء 7، وهنا هنتفرج على V8 وهو بيعملها. باختصار: الـ mark-and-sweep بيلاقي كل حاجة الـ roots توصلها ويفضّي الباقي، والـ generational بيقسم الـ heap حسب السن، لأن أغلب الـ objects بتموت صغيرة.

الـ objects الجديدة بتدخل الـ young generation، وده عبارة عن 2 semi-spaces بيلمّهم الـ Scavenger. بينسخ الحيين للـ semi-space التانية ويسيب الباقي مرة واحدة، فتكلفته ماشية مع عدد الحيين مش كمية الزبالة. والـ object اللي يعيش مرتين بيتنقل للـ old generation، وده بيلمّه Mark-Compact. الـ marking هناك شغال incremental على خطوات صغيرة وconcurrent على helper threads، فالـ stop-the-world pause هو الحتة الأخيرة بس. وعشان كده سطور الـ Mark-Compact فوق بتوري pause ≈ 2 ms مع marking أخد ≈ 27 ms wall time.

كلمة allocation failure في الـ trace مش error. معناها إن الـ semi-space اتملت، وده السبب الطبيعي للـ scavenge. وmu هي mutator utilization، يعني نسبة الوقت اللي الـ JavaScript بتاعك اشتغل فيه: ≈ 0.88 هنا معناها إن الـ GC أخد حوالي 12% في الفترة دي. وجوه service شغال مش محتاج الـ flag: PerformanceObserver على gc بيديك نفس الأرقام كـ metrics.

الأرقام بتثبت الكلام: نفس الـ 30 مليون object، بس لما 0% بيعيشوا الـ scavenges أخدت ≈ 40–135 ms، ولما 50% بيعيشوا أخدت ≈ 530–920 ms، يعني ≈ 7–14 مرة أكتر، مع إن الـ allocations نفس العدد. ولاحظ إن الـ 703 scavenge في حالة 0% أرخص من 131 في حالة 50%: العدد مش هو المشكلة، النسخ هو المشكلة. وفي الـ semi-space: من 1MB لـ 16MB نزل العدد من 1486 لـ 116 والوقت قل ≈ 3–4 مرات، لكن من 16MB لـ 64MB مفيش فرق واضح في الوقت (≈ 60–180 ms في الاتنين). يعني الـ --max-semi-space-size مش زرار سحري، وكمان بيزوّد الـ memory، فقيسه على الـ workload بتاعك قبل ما تغيّره.

فين هستخدمه في شغلي؟ API عندك الـ p99 بتاعها بتعلّي من غير سبب والـ p50 ثابت. شغّل instance واحد بـ --trace-gc أو الأحسن تصدّر PerformanceObserver لـ Prometheus (التمرين 4)، وبص: pauses كبيرة ولا mu قليل؟ ولو الـ scavenges تقيلة، دور على data بتعيش شوية صغيرة زي response objects ماسكها batch أو queue في الـ memory، ده النوع اللي بيتنسخ مرتين وبعدين يموت في الـ old space. الحل غالبًا تقلل اللي بيعيش مش تكبّر الـ heap.
Interview question "Why are short-lived objects cheap in V8, and what's expensive?" → The Scavenger copies only survivors and discards the rest in one step, so dead objects cost almost nothing. Objects that live just long enough to be copied and promoted are the expensive case. In my test, the same 30 million allocations spent ≈ 7–14 times longer in scavenges with 50% survival than with 0%.
"ليه الـ objects اللي عمرها قصير رخيصة في V8، وإيه الغالي؟" ← الـ Scavenger بينسخ الحيين بس ويسيب الباقي مرة واحدة، فالميتين تقريبًا ببلاش. الغالي هو الـ objects اللي بتعيش وقت كفاية إنها تتنسخ وتتنقل للـ old space. وفي التجربة هنا، نفس الـ 30 مليون allocation أخدوا وقت في الـ scavenges ≈ 7–14 مرة أكتر مع survival 50% مقارنةً بـ 0%.

Part 2 — The memory leaks you will actually meet 🔴 Advancedالجزء 2 — الـ memory leaks اللي هتقابلها فعلًا

English

A leak in a garbage-collected language is memory that's still reachable but will never be used again. The collector is doing its job: something long-lived holds a reference you forgot about. Almost every real case is one of six patterns: a closure holding a big value, a listener that's never removed, a timer that's never cleared, a global cache with no limit, a Map keyed by objects where a WeakMap belongs, and in browsers, detached DOM nodes.

The harness below runs each pattern for 5,000 "requests" of ≈ 20 KB each, forces a full GC at each checkpoint, and reports what stayed. Measuring after a forced GC is the important part: without it, heapUsed also contains garbage that hasn't been collected yet. The signature of a leak is linear growth after GC. The fixed versions stay flat.

The sneakiest one is the shared context. In V8, all closures created in one scope share a single context object. audit.push(() => `o_${i}`) never mentions rawBody, yet it retains all of it, because a sibling closure (measure) uses rawBody, which puts it in the shared context. The table shows it: 96 MB, the same as the closure that uses it directly.

// شغّله كده: node --expose-gc --no-warnings leaks.ts
import { EventEmitter } from "node:events";

const gc = (globalThis as unknown as { gc: () => void }).gc;
const KB_20 = 2_500; // عدد العناصر اللي بتساوي حوالي 20KB في الـ heap
const CHECKPOINTS = [1000, 2000, 3000, 4000, 5000];

function usedMB(): number {
  gc();
  gc();
  return process.memoryUsage().heapUsed / 1048576;
}

// الـ harness: بينفّذ step لكل request وبيقيس الزيادة بعد GC كامل عند كل checkpoint
function run(name: string, setup: () => { step: (i: number) => void; cleanup?: () => void }) {
  const base = usedMB();
  const { step, cleanup } = setup();
  const samples: string[] = [];
  let i = 0;
  for (const target of CHECKPOINTS) {
    for (; i < target; i++) step(i);
    samples.push((usedMB() - base).toFixed(1).padStart(6));
  }
  cleanup?.();
  console.log(name.padEnd(30), samples.join(" "));
}

console.log("MB retained after N requests".padEnd(30), CHECKPOINTS.map((c) => String(c).padStart(6)).join(" "));

الـ leak في لغة فيها GC هو memory لسه reachable بس عمرها ما هتتستخدم تاني. الـ GC بيعمل شغله صح: فيه حاجة عايشة طول الوقت ماسكة reference إنت نسيته. وأغلب الحالات الحقيقية واحدة من 6: closure ماسك قيمة كبيرة، listener محدش شاله، timer محدش قفله، global cache من غير حد أقصى، Map مفاتيحها objects والمفروض WeakMap (الفرق ده مشروح في Lesson 07)، وفي المتصفح الـ detached DOM nodes.

Part 3 — Finding leaks with heap snapshots 🔴 Advancedالجزء 3 — تلاقي الـ leaks بالـ heap snapshots

English

A heap snapshot is the full object graph at one instant: every object, its size, and every reference. Take one in Chrome DevTools (Memory tab), or in Node with v8.writeHeapSnapshot() and load the .heapsnapshot file into that same tab. For a running server, start it with node --inspect and open chrome://inspect. The method that works is compare, don't stare: take a snapshot, apply load, take another, then open the Comparison view and sort by what grew.

Two numbers matter. Shallow (self) size is the object's own memory. Retained size is what would be freed if that object disappeared, including everything only it keeps alive. Sort by shallow size and you'll see strings and arrays, which tells you nothing. Sort by retained size and you'll see the culprit. In the snapshot below, one OrderContext has a self size of 48 bytes and a retained size of 8,120 bytes, while the Map holding them has a self size of 32 bytes and retains ≈ 86 MB. Then read the Retainers panel: the path from a GC root down to the object tells you who holds it, and that's the line of code to fix.

Other tools fit around this. The Allocation instrumentation on timeline records allocations over time and shows which ones are still alive at the end, which helps when you know the action but not the object. In Node, --heapsnapshot-near-heap-limit=1 writes a snapshot automatically just before an out-of-memory crash, which I ran successfully on this machine. Snapshots have a real cost, though: they block the main thread (≈ 210–380 ms here for a heap of only ≈ 13–90 MB, and it grows with object count), and the Node docs warn that generating one needs memory about twice the heap size. In production, take them on one instance that's out of rotation.

// شغّله كده: node analyze-snapshot.ts before.heapsnapshot after.heapsnapshot OrderContext
// بيعمل بالكود نفس اللي الـ DevTools بيعمله: summary و comparison و retained size و retainers
import { readFileSync } from "node:fs";

type Snapshot = {
  snapshot: { meta: {
    node_fields: string[]; node_types: [string[], ...unknown[]];
    edge_fields: string[]; edge_types: [string[], ...unknown[]];
  } };
  nodes: number[]; edges: number[]; strings: string[];
};

function load(file: string) {
  const s: Snapshot = JSON.parse(readFileSync(file, "utf8"));
  const { node_fields: nf, node_types: nt, edge_fields: ef, edge_types: et } = s.snapshot.meta;
  const NF = nf.length, EF = ef.length;
  const count = s.nodes.length / NF;
  const [T, N, SELF, EC] = ["type", "name", "self_size", "edge_count"].map((f) => nf.indexOf(f));
  const [ET, EN, TO] = ["type", "name_or_index", "to_node"].map((f) => ef.indexOf(f));
  const WEAK = et[0].indexOf("weak");
  const typeOf = (i: number) => nt[0][s.nodes[i * NF + T]];
  const nameOf = (i: number) => s.strings[s.nodes[i * NF + N]];
  const selfOf = (i: number) => s.nodes[i * NF + SELF];

  // الـ edges متخزنة ورا بعض، فبنحسب بداية edges كل node
  const firstEdge = new Uint32Array(count + 1);
  for (let i = 0; i < count; i++) firstEdge[i + 1] = firstEdge[i] + s.nodes[i * NF + EC];
  const targets = (i: number) => {
    const out: number[] = [];
    for (let e = firstEdge[i]; e < firstEdge[i + 1]; e++) {
      if (s.edges[e * EF + ET] !== WEAK) out.push(s.edges[e * EF + TO] / NF);
    }
    return out;
  };
  const edgeLabel = (e: number) => {
    const type = et[0][s.edges[e * EF + ET]];
    const raw = s.edges[e * EF + EN];
    return type === "element" || type === "hidden" ? `[${raw}]` : s.strings[raw];
  };
  return { s, count, typeOf, nameOf, selfOf, targets, firstEdge, EF, TO, ET, WEAK, NF, edgeLabel };
}

// الـ summary: كل constructor عنده كام instance وكام byte
function summarize(h: ReturnType<typeof load>) {
  const byName = new Map<string, { n: number; self: number }>();
  for (let i = 0; i < h.count; i++) {
    if (h.typeOf(i) !== "object") continue;
    const e = byName.get(h.nameOf(i)) ?? { n: 0, self: 0 };
    e.n++;
    e.self += h.selfOf(i);
    byName.set(h.nameOf(i), e);
  }
  return byName;
}

// الـ retained size: بنبني dominator tree بالـ algorithm بتاع Cooper-Harvey-Kennedy
function retainedSizes(h: ReturnType<typeof load>): Float64Array {
  const order: number[] = [];
  const seen = new Uint8Array(h.count);
  const stack: [number, number[], number][] = [[0, h.targets(0), 0]];
  seen[0] = 1;
  while (stack.length) {
    const top = stack[stack.length - 1];
    if (top[2] < top[1].length) {
      const t = top[1][top[2]++];
      if (!seen[t]) { seen[t] = 1; stack.push([t, h.targets(t), 0]); }
    } else { order.push(top[0]); stack.pop(); }
  }
  const rank = new Int32Array(h.count).fill(-1);
  order.forEach((n, r) => { rank[n] = r; });
  const preds: number[][] = Array.from({ length: h.count }, () => []);
  for (const n of order) for (const t of h.targets(n)) preds[t].push(n);
  const idom = new Int32Array(h.count).fill(-1);
  idom[0] = 0;
  const intersect = (a: number, b: number) => {
    while (a !== b) {
      while (rank[a] < rank[b]) a = idom[a];
      while (rank[b] < rank[a]) b = idom[b];
    }
    return a;
  };
  for (let changed = true; changed; ) {
    changed = false;
    for (let r = order.length - 2; r >= 0; r--) {
      const n = order[r];
      let best = -1;
      for (const p of preds[n]) if (idom[p] !== -1) best = best === -1 ? p : intersect(best, p);
      if (best !== -1 && idom[n] !== best) { idom[n] = best; changed = true; }
    }
  }
  const retained = new Float64Array(h.count);
  for (const n of order) {
    retained[n] += h.selfOf(n);
    if (n !== 0) retained[idom[n]] += retained[n];
  }
  return retained;
}

// الـ retainers path: أقصر طريق من الـ root للـ object، وده اللي بيقولك مين ماسكه
function retainerPath(h: ReturnType<typeof load>, target: number): string[] {
  const parent = new Int32Array(h.count).fill(-1);
  const via = new Int32Array(h.count).fill(-1);
  parent[0] = 0;
  const queue = [0];
  for (let q = 0; q < queue.length; q++) {
    const n = queue[q];
    if (n === target) break;
    for (let e = h.firstEdge[n]; e < h.firstEdge[n + 1]; e++) {
      if (h.s.edges[e * h.EF + h.ET] === h.WEAK) continue;
      const t = h.s.edges[e * h.EF + h.TO] / h.NF;
      if (parent[t] === -1) { parent[t] = n; via[t] = e; queue.push(t); }
    }
  }
  const path: string[] = [];
  for (let n = target; n !== 0; n = parent[n]) {
    path.unshift(`--${h.edgeLabel(via[n])}--> ${h.nameOf(n).slice(0, 40) || "(" + h.typeOf(n) + ")"}`);
  }
  return ["(root)", ...path];
}

Part 4 — Memory in Node 🔴 Advancedالجزء 4 — الـ memory في Node

English

process.memoryUsage() returns five fields, and they answer different questions. rss is the physical memory of the whole process, and it's what a container limit counts. heapTotal is what V8 has committed; heapUsed is what's occupied inside it. external is memory outside the JS heap owned by C++ objects tied to JS objects, and arrayBuffers is the part of it used by ArrayBuffer and Buffer. Two consequences show up in the output. A 200 MB Buffer moves rss and external but not heapUsed. And freeing objects drops heapUsed at once, while rss barely moves, because memory isn't handed back to the OS immediately. So rss alone doesn't prove a leak.

--max-old-space-size caps V8's old space in MB. On this 32 GB machine the default limit (heap_size_limit) is 4,144 MB. It does not cap Buffers: with a 32 MB limit, the test below still holds 400 MB of them. When the old space can't fit what's alive, V8 runs back-to-back full GCs that free almost nothing, then aborts with FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory. That's a native abort, so no JavaScript catch or 'uncaughtException' handler runs. Here it exited with code 134. A heap OOM inside a Worker with resourceLimits is the exception: only the worker dies, with ERR_WORKER_OUT_OF_MEMORY.

In a container there are two independent limits. If rss crosses the cgroup limit first, the kernel sends SIGKILL: exit 137, OOMKilled, no stack trace, no snapshot. So set the old space below the container limit, commonly ≈ 75%, leaving room for Buffers, stacks, code and the young generation. Then V8 works harder before giving up, and a true overflow fails with a debuggable 134. I had no Docker on this machine, so the container behaviour here comes from the docs and the earlier CS lesson, not from a run. process.constrainedMemory() returned 0 here, meaning no known limit. Node 22.19 rejects --max-old-space-size-percentage with bad option, so use a fixed number on this version.

Part 5 — The JIT 🔴 Advancedالجزء 5 — الـ JIT

English

V8 doesn't compile your code once. It starts cheap and spends more only on code that earns it. Ignition, the interpreter, runs bytecode and records type feedback: which shapes and number types each operation has actually seen. Sparkplug is a baseline compiler that turns bytecode into machine code quickly, with no real optimization. TurboFan is the optimizing compiler: it takes hot functions and uses the feedback to speculate ("cents is always a small integer, this object always has this shape"), then inlines and removes work based on those guesses, with cheap checks guarding each one. If a check fails, the function deoptimizes back to bytecode. That's Part 6.

Maglev is a mid-tier optimizer between Sparkplug and TurboFan, and the V8 blog describes it as shipped in Chrome. It's off in the Node I tested: --v8-options on 22.19 reports default: --no-maglev, so the path here is Ignition → Sparkplug → TurboFan. Even with --maglev switched on, the trace for this function showed only TurboFan. Check your own Node version rather than assuming.

--trace-opt shows the decision: reason: hot and stable means the function ran enough and its feedback stopped changing. ConcurrencyMode::kConcurrent means the compile happened on a background thread, so the event loop kept running the slower code meanwhile. Disabling tiers shows what each one is worth: without TurboFan the same loop is ≈ 10–17 times slower, and with interpretation alone ≈ 17–28 times.

Part 6 — Hidden classes, inline caches & deopts 🔴 Advancedالجزء 6 — الـ hidden classes والـ inline caches والـ deopts

English

A JS object looks like a dictionary, but V8 doesn't store it as one if it can avoid it. Each object points to a hidden class (V8 calls it a Map, and other engines call it a shape) that records which property lives at which offset. Objects built the same way share one Map, so reading order.cents can become "check the Map, then read at offset N". Adding a property moves the object along a transition to another Map, so property order matters: { id, cents } and { cents, id } have different Maps. delete usually pushes the object into slow dictionary mode, while assigning undefined keeps the shape. %HaveSameMap and %HasFastProperties below show all this directly.

An inline cache (IC) remembers, at each property access site, the Maps it has seen. One Map is monomorphic, and TurboFan can inline it to almost nothing. Two to four is polymorphic: a short chain of checks. Beyond that it's megamorphic: a slower generic lookup. Measured with the same loop in fresh processes, reads cost ≈ 1 ns for one shape, ≈ 2–3× for four shapes, ≈ 3–6× for eight, and ≈ 5–11× after delete.

A deopt happens when a speculation fails. --trace-deopt prints the reason. Some are normal and cheap, such as code reaching a path it never saw while warming up. The ones to fix repeat: a hot function that keeps receiving a new type. Some older advice no longer holds. try/catch blocked optimization in the old Crankshaft compiler, but that ended when Ignition and TurboFan launched in 2017, and I measured no difference. arguments and rest parameters cost about the same here, and the slowdown appears only when arguments escapes (≈ 1.6–1.8×).

الـ JS object شكله dictionary، بس V8 مش بيخزنه كده لو يقدر يتجنب. كل object بيشاور على hidden class (V8 بيسميها Map والـ engines التانية بتسميها shape) فيها كل property في أنهي offset. والـ objects اللي اتبنت بنفس الطريقة بتشارك Map واحدة، فقراية order.cents ممكن تبقى "اتأكد من الـ Map واقرا من offset N". وإضافة property بتنقل الـ object عبر transition لـ Map تانية، وعشان كده الترتيب مهم: { id, cents } و{ cents, id } ليهم Maps مختلفة. والـ delete عادةً بيرمي الـ object في dictionary mode البطيء، إنما undefined بيحافظ على الـ shape. وأول output بيوري ده كله مباشرةً.

الـ inline cache بيفتكر، عند كل مكان بتقرا فيه property، الـ Maps اللي شافها. Map واحدة يبقى monomorphic و TurboFan يقدر يعمل inlining لحد ما تبقى تقريبًا ولا حاجة. من 2 لـ 4 يبقى polymorphic: سلسلة checks قصيرة. وأكتر من كده megamorphic: lookup عام أبطأ. واتقاس بنفس الـ loop في processes منفصلة: ≈ 1 ns لـ shape واحد، ≈ 2–3 مرات لـ 4 shapes، ≈ 3–6 مرات لـ 8، و ≈ 5–11 مرة بعد delete. والفرق بين ترتيبين بس طلع صغير (≈ 1–1.4 مرة).

الـ deopt بيحصل لما تخمين يقع، و--trace-deopt بيطبع السبب. فيه أسباب طبيعية ورخيصة، زي كود وصل لسكة عمره ما شافها في الـ warmup. واللي لازم يتصلح هو اللي بيتكرر: hot function كل شوية بياخد نوع جديد. وفيه نصايح قديمة بقت غلط. try/catch كان بيمنع الـ optimization في Crankshaft القديم، وده خلص لما Ignition و TurboFan نزلوا في 2017، وأنا قست ومطلعش فرق: plain loop وtry/catch بيتبادلوا المركز الأول بين الـ runs (≈ 100–200 ns حسب ضغط الجهاز). وarguments والـ rest parameters تكلفتهم متقاربة هنا (≈ 20–40 ns)، والبطء بيظهر بس لما arguments يهرب بره الـ function (≈ 1.6–1.8 مرة). يعني اكتب try/catch في المكان اللي يخدم الـ error handling، من غير ما تفكر في الـ performance.

English

A performance.now() around a loop usually measures something other than what you meant, and the JIT is why. Dead code elimination: if the result is never used, TurboFan may remove the work. Below, creating an order line "costs" ≈ 1.2–2 ns when unused and ≈ 14–20 ns when it escapes, so the naive number is ≈ 10 times too good. This caught me while writing Part 1: my first 0%-survival GC test showed 3 scavenges instead of 703, because the allocations had been optimized away. Warmup: the first batch of calls is ≈ 8–10 times slower than the later ones. Order effects: the same function measured again on the same data took ≈ 2–3 times longer once the call site had seen other shapes, so whichever test runs first gets an unfair advantage.

A tool like tinybench handles warmup and repetition and reports a margin of error instead of one number. It can't save you from everything: you must still use the result, keep inputs realistic, and treat close results as ties. Rerun on a quiet machine, and don't quote differences smaller than the noise. Here the machine was loaded, so every figure is a range across runs.

On strings, += beat join in every run. V8 builds a rope and flattens it only when needed, which is also why you must force a flatten to measure honestly: skipping that makes += look twice as fast as it is. On arrays, writing by index into new Array(n) beat push ≈ 3 times, but it leaves a holey array for good, and a very large new Array goes straight to slow dictionary elements. Array.from({ length }) was the surprise: ≈ 30–40 times slower than map. Then comes the honest conclusion. These savings are microseconds per thousand items, a single localhost TCP round trip is ≈ 50–70 µs before any database work, and removing one 2 ms query is worth hundreds of these optimizations. Profile first, with node --cpu-prof.

بالعامية

performance.now() حوالين loop غالبًا بيقيس حاجة غير اللي إنت عايزها، والسبب الـ JIT. الـ dead code elimination: لو النتيجة مش مستخدمة، TurboFan ممكن يشيل الشغل كله. تحت، إنشاء order line "بيتكلف" ≈ 1.2–2 ns لو مش مستخدم، و ≈ 14–20 ns لو بيهرب، يعني الرقم الساذج ≈ 10 مرات أحسن من الحقيقة. وده حصلي وأنا بكتب الجزء 1: أول نسخة من تجربة الـ GC بـ 0% survival طلّعت 3 scavenges بدل 703، لأن الـ allocations اتشالت خالص. الـ warmup: أول batch من الـ calls ≈ 8–10 مرات أبطأ من اللي بعده. تأثير الترتيب: نفس الـ function لما اتقاست تاني على نفس الـ data أخدت ≈ 2–3 مرات أكتر، بعد ما الـ call site شاف shapes تانية، فأي test بيجري الأول بياخد ميزة مش من حقه.

أداة زي tinybench بتتعامل مع الـ warmup والتكرار، وبتديك margin of error بدل رقم واحد. بس مش هتنقذك من كل حاجة: لازم برضه تستخدم النتيجة، وتخلي الـ input واقعي، وتعتبر النتايج القريبة تعادل. وأعد التشغيل على جهاز هادي، ومتقولش فرق أصغر من الـ noise. والجهاز هنا كان عليه ضغط، فكل رقم في الدرس مدى من كذا run.

في الـ strings، += كسب join في كل run. V8 بيبني rope ومش بيعمله flatten غير لما يحتاج، وعشان كده لازم تجبره على الـ flatten عشان القياس يبقى أمين، ولو مجبرتوش += هيبان ضعف سرعته الحقيقية. وفي الـ arrays، الكتابة بالـ index في new Array(n) كسبت push ≈ 3 مرات، بس بتسيب array holey للأبد (السطر التاني في output الـ elements)، وnew Array كبيرة أوي بتروح dictionary elements البطيئة على طول. والمفاجأة كانت Array.from({ length }): ≈ 30–40 مرة أبطأ من map. وبعدين الخلاصة الأمينة: التوفير ده microseconds لكل ألف عنصر، و round trip واحد على TCP على نفس الجهاز ≈ 50–70 µs قبل أي شغل DB، وشيل query واحدة بـ 2 ms يساوي مئات من الـ optimizations دي (الـ 2 ms افتراض مش قياس). ابدأ دايمًا بـ profile: node --cpu-prof بيطلّع ملف .cpuprofile تفتحه في DevTools.

فين هستخدمه في شغلي؟ في code review حد طلب تغيّر += لـ join "عشان الـ performance"؟ دلوقتي معاك رقم. Endpoint بطيء؟ الترتيب: شوف الـ trace، اعرف عدد الـ queries (N+1 بـ 50 query × 2 ms = 100 ms، ولا micro-optimization هتقرب من ده)، بعدين الـ cache، بعدين --cpu-prof، وآخر حاجة خالص الـ micro-benchmarks، وبس على السطور اللي الـ profile قال إنها hot. ولو هتكتب benchmark لقرار حقيقي زي اختيار serializer، استخدم tinybench، وشغّل كل حالة في process لوحده زي shape-bench.ts فوق، وبيانات شبه production.
Trade-off Performance-shaped code has a real cost: new Array(n) stays holey, hand-written loops are longer than .map, and a clever trick gets copied everywhere long after the engine changed. Write the clear version first, then change it only for a line a profile has identified, and keep the benchmark next to the change so it can be re-run on the next Node version.

// الحل: GC و memory metrics صغيرة تتحط في أي service، وبتتجرب بـ node ex4-metrics.ts
import { PerformanceObserver, constants } from "node:perf_hooks";

export function startMemoryMetrics(log: (line: Record<string, number>) => void, everyMs = 30_000) {
  let minorMs = 0, majorMs = 0, maxPause = 0;
  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      const { kind } = (entry as unknown as { detail: { kind: number } }).detail;
      if (kind === constants.NODE_PERFORMANCE_GC_MINOR) minorMs += entry.duration;
      if (kind === constants.NODE_PERFORMANCE_GC_MAJOR) majorMs += entry.duration;
      maxPause = Math.max(maxPause, entry.duration);
    }
  });
  observer.observe({ entryTypes: ["gc"] });

  const timer = setInterval(() => {
    const m = process.memoryUsage();
    const mb = (b: number) => Math.round(b / 1048576);
    log({
      rssMb: mb(m.rss), heapUsedMb: mb(m.heapUsed), externalMb: mb(m.external),
      gcMinorMs: Math.round(minorMs), gcMajorMs: Math.round(majorMs), gcMaxPauseMs: Math.round(maxPause),
    });
    minorMs = majorMs = maxPause = 0;
  }, everyMs);
  // الـ unref عشان الـ metrics متمنعش الـ process إنه يقفل
  timer.unref();
  return () => { clearInterval(timer); observer.disconnect(); };
}

const lines: Record<string, number>[] = [];
const stop = startMemoryMetrics((l) => lines.push(l), 100);
const keep: object[] = [];
const started = Date.now();
while (Date.now() - started < 300) {
  for (let i = 0; i < 100_000; i++) keep[i % 50_000] = { id: i };
  await new Promise((r) => setTimeout(r, 1));
}
stop();
console.log(lines.at(-1));

// الـ output الحقيقي (Node 22.19 على Windows):
// → {
// →   rssMb: 101,
// →   heapUsedMb: 26,
// →   externalMb: 9,
// →   gcMinorMs: 7,
// →   gcMajorMs: 0,
// →   gcMaxPauseMs: 4
// → }
ده جزء (أ) بس، كود صغير تحطه في الـ startup. الـ unref بيضمن إن الـ timer مش هيمنع الـ graceful shutdown. الجزء (ب) و(ج) على الـ infrastructure والـ load بتوعك.

Cheat sheet · الخلاصة

  • Young: Scavenger copies survivors; cost follows survivors, not garbage. Old: Mark-Compact with incremental and concurrent marking, so the pause is only the final part. allocation failure in a trace is normal.
  • A leak is reachable but unused memory: linear growth after a forced GC. The six usual suspects: closures, listeners, timers, unbounded caches, Map instead of WeakMap, detached DOM.
  • Closures in one scope share a context: an unrelated closure can retain a big value used by its sibling.
  • Snapshots: compare two, sort by retained, read the retainers path. They block the main thread and need about twice the heap; treat the file as sensitive.
  • Fields: rss is what the container counts; heapUsed is JS objects; external includes Buffers, which --max-old-space-size does not cap.
  • Exit codes: 134 means V8 hit its heap limit; 137 means the kernel killed the process. Set the old space to ≈ 75% of the container limit and add --heapsnapshot-near-heap-limit=1.
  • JIT in Node 22.19: Ignition → Sparkplug → TurboFan (--no-maglev by default). Hot code is ≈ 10–28 times faster than without the optimizing tier.
  • Shapes: same properties, same order, no delete. Read cost: mono ≈ 1 ns, 8 shapes ≈ 3–6×, after delete ≈ 5–11×. Only hot code cares.
  • Deopts: read the reason in --trace-deopt; worry about the repeating ones. try/catch showed no cost; arguments costs only when it escapes.
  • Benchmarks lie through dead code elimination, warmup and order effects. Use the result, use tinybench, separate processes, ranges not single numbers.
  • Strings and arrays: += beats join; new Array(n) beats push ≈ 3× but stays holey; avoid Array.from({ length }) in hot paths. One avoided 2 ms query is worth hundreds of these. Profile first.
بالعامية
  • الـ young: الـ Scavenger بينسخ الحيين، وتكلفته ماشية مع الحيين مش الزبالة. الـ old: Mark-Compact بـ marking incremental و concurrent، فالـ pause هو الحتة الأخيرة بس. وallocation failure في الـ trace طبيعية.
  • الـ leak memory reachable بس مش مستخدمة: زيادة خطية بعد GC إجباري. والمتهمين الستة: closures و listeners و timers و caches من غير حد وMap بدل WeakMap و detached DOM.
  • الـ closures في نفس الـ scope بتشارك context: closure مالهاش علاقة ممكن تمسك قيمة كبيرة بتستخدمها closure جنبها.
  • الـ snapshots: قارن اتنين، رتّب بالـ retained، واقرا الـ retainers path. بتوقف الـ main thread ومحتاجة حوالي ضعف الـ heap، وعامل الملف كـ data حساسة.

  • الـ exit codes: 134 يعني V8 وصل حد الـ heap، و137 يعني الـ kernel قتل الـ process. خلّي الـ old space ≈ 75% من حد الـ container، وضيف --heapsnapshot-near-heap-limit=1.

  • الـ shapes: نفس الـ properties، نفس الترتيب، ومن غير delete. تكلفة القراية: mono ≈ 1 ns، و8 shapes ≈ 3–6 مرات، وبعد delete ≈ 5–11 مرة. والـ hot code بس هو اللي بيفرق معاه.
