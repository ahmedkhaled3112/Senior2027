Why this matters · ليه ده مهم

English

You have shipped JavaScript for years, so this lesson skips "what is a variable" and goes straight to the rules that cause real incidents: a free-shipping order charged the default fee because 0 is falsy, a page === 1 check that never passes because query values are strings, a price cache corrupted by one handler mutating a shared object, a passwordHash leaking through a spread. All of these look correct in code review unless you know the rule underneath. Interviewers probe the same rules, because being able to predict the output of a small snippet is a fast test of whether someone understands the language or only uses it.

بالعامية

إنت بتكتب JavaScript بقالك سنين، فالدرس ده مش هيقولك "يعني إيه variable". هندخل على طول في القواعد اللي بتعمل مشاكل حقيقية في الـ production: order شحنه مجاني اتحسبت عليه رسوم الشحن الافتراضية عشان 0 قيمته falsy، وشرط page === 1 عمره ما بيتحقق عشان قيم الـ query دايمًا strings، وكاش أسعار باظ عشان handler واحد عدّل object مشترك، وpasswordHash اتسرب للـ client من spread. كل دول شكلهم سليم في الـ code review لو مش عارف القاعدة اللي تحتهم. وفي الـ interviews بيسألوا على نفس القواعد، لأن إنك تتوقع ناتج كود صغير هو أسرع اختبار يبيّن إنت فاهم اللغة ولا بس بتستخدمها.

Part 1 — Statements vs expressions 🟢 Basicالجزء 1 — الفرق بين الـ statement والـ expression

English

An expression is code that evaluates to a value: qty * price, order.status === "paid", a function call, an arrow function, a ternary, even an assignment. A statement is code that performs an action and produces no value you can use: if, for, while, switch, return, throw, and declarations like const x = 1.

The grammar enforces the difference. Wherever a value is expected (the right side of =, a function argument, an array element, a template literal's ${}, an arrow's expression body, JSX {}), only an expression fits. Wherever a statement is expected, an expression may also appear (sendEmail(user); is an expression statement). It doesn't work the other way round, which is why const a = if (x) { 1 } is a SyntaxError.

Three everyday consequences. First, an arrow with an expression body returns implicitly; the same code with { } around it is a block and returns undefined unless you write return. Second, { right after => always means a block, so (o) => { id: o.id } is a block containing a label called id, and returning an object literal needs parentheses. Third, assignment is an expression, so if (order.status = "paid") compiles, overwrites the status, and always takes the branch.

const order = {
  id: "ord_1001",
  status: "paid",
  items: [
    { sku: "TSHIRT", priceMinor: 25000, qty: 2 },
    { sku: "CAP", priceMinor: 9000, qty: 1 },
  ],
};

// كل حتة هنا expression: بتتحسب وتطلّع قيمة، فتقدر تحطها في أي مكان محتاج قيمة
const lineTotal = (item) => item.priceMinor * item.qty;
const orderTotal = (o) => o.items.reduce((sum, item) => sum + lineTotal(item), 0);
console.log(orderTotal(order));
// → 59000

// الـ if هنا statement: بينفّذ حاجة ومبيطلّعش قيمة، فلازم متغير let بره
let label;
if (order.status === "paid") {
  label = "Paid";
} else {
  label = "Pending";
}

// نفس الفكرة بـ ternary: ده expression فبيدخل مباشرة في const
const sameLabel = order.status === "paid" ? "Paid" : "Pending";
console.log(label === sameLabel);
// → true

// غلطة: block body من غير return بيرجّع undefined
const brokenLineTotal = (item) => { item.priceMinor * item.qty; };
console.log(brokenLineTotal(order.items[0]));
// → undefined

// غلطة: القوس اللي بعد السهم بيتقرا block، والـ id بتتقرا label مش key
const brokenDto = (o) => { id: o.id };
const dto = (o) => ({ id: o.id });
console.log(brokenDto(order), dto(order));
// → undefined { id: 'ord_1001' }

// إثبات من الـ parser نفسه: statement مينفعش مكان قيمة
const parses = (src) => {
  try {
    new Function(src);
    return "OK";
  } catch (e) {
    return `${e.name}: ${e.message}`;
  }
};
console.log(parses("const a = if (true) { 1 };"));
// → SyntaxError: Unexpected token 'if'
console.log(parses("console.log(for (;;) {});"));
// → SyntaxError: Unexpected token 'for'
console.log(parses("const a = true ? 1 : 2;"));
// → OK

// خد بالك: الـ assignment نفسه expression، فده بيعدّي من غير error وبيغيّر الـ status
const pending = { status: "pending" };
if (pending.status = "paid") console.log("charged!", pending.status);
// → charged! paid
بالعامية

الـ expression هو أي كود بيتحسب ويطلّع قيمة: qty * price، وorder.status === "paid"، ونداء function، و arrow function، و ternary، وحتى الـ assignment نفسه. أما الـ statement فهو كود بينفّذ حاجة ومبيطلّعش قيمة تقدر تستخدمها: if وfor وwhile وswitch وreturn وthrow، والـ declarations زي const x = 1.

الـ grammar نفسها بتفرض الفرق ده. أي مكان محتاج قيمة (يمين الـ =، أو argument لـ function، أو عنصر في array، أو ${} في template literal، أو الـ expression body بتاع arrow، أو {} في JSX) مفيش غير expression يدخل فيه. وأي مكان محتاج statement ينفع تحط فيه expression عادي (sendEmail(user); اسمه expression statement). العكس مش شغال، وعشان كده const a = if (x) { 1 } بتضرب SyntaxError.

فيه 3 نتايج هتقابلك كل يوم. الأولى: الـ arrow بـ expression body بيرجّع القيمة لوحده، ونفس الكود لو حطيت حواليه { } بقى block وبيرجّع undefined لو مكتبتش return. التانية: القوس { بعد => على طول معناه block دايمًا، فـ (o) => { id: o.id } ده block جواه label اسمه id، ولو عايز ترجّع object literal لازم أقواس. التالتة: الـ assignment نفسه expression، فـ if (order.status = "paid") بتعدّي من الـ compiler، وبتكتب فوق الـ status، وبتدخل الـ branch دايمًا.

فين هستخدمه في شغلي؟ في الـ code review: لما تلاقي let status; if (paid) { status = 200 } else { status = 402 } في controller، اقترح const status = paid ? 200 : 402. متغير أقل بيتعدّل يعني حالات أقل تفكر فيها. وفي أي .map بيحوّل rows لـ DTOs: لو الـ API بدأت ترجّع arrays مليانة undefined، أول حاجة تدور عليها هي arrow بـ { } ناسية الـ return أو object literal من غير أقواس.

Why if can't go inside JSX ليه الـ if مينفعش جوه JSX

English

JSX isn't a template language. The compiler turns each tag into a function call, and whatever sits inside {} becomes a property value in that call's object argument. A property value has to be an expression, and that's the entire reason a ternary works there and if doesn't. When a branch gets too big for a ternary, move it out: compute a const above the return, using a normal if if you like, or extract a small component.

import { renderToStaticMarkup } from "react-dom/server";

type Props = { status: "paid" | "pending"; totalMinor: number };

// جوه القوسين في JSX لازم expression: الـ ternary والقسمة تمام
function OrderBadge({ status, totalMinor }: Props) {
  return (
    <span>
      {status === "paid" ? "Paid" : "Pending"} · {totalMinor / 100} EGP
    </span>
  );
}

console.log(renderToStaticMarkup(<OrderBadge status="paid" totalMinor={59000} />));
// → <span>Paid · 590 EGP</span>

بالعامية

الـ JSX مش template language. الـ compiler بيحوّل كل tag لنداء function، واللي جوه {} بيبقى قيمة property في الـ object اللي بيتبعت للنداء ده. والـ property value لازم تبقى expression، وده السبب كله إن الـ ternary شغال هناك والـ if لأ. ولو الـ branch كبر على الـ ternary، طلّعه بره: احسب const فوق الـ return (وهنا تستخدم if عادي)، أو اعمل component صغير.

فين هستخدمه في شغلي؟ صفحة order في Next.js: لو عندك 4 حالات (paid، pending، failed، refunded) متعملش ternaries متداخلة جوه الـ JSX. اعمل const badge = statusBadge(order.status) فوق الـ return وحط {badge} بس. الكود هيتقري أسرع، وكل حالة هتبقى ليها test لوحدها.

Part 2 — var, let, const, scope, hoisting & the TDZ 🟢 Basicالجزء 2 — var و let و const، والـ scope، والـ hoisting، والـ TDZ

English

JavaScript has three scopes you need here. Global: visible everywhere. Function: visible inside one function. Block: visible inside one { }, including if and loop bodies. var is function-scoped and ignores blocks. let and const are block-scoped.

Hoisting means a declaration takes effect when its scope is entered, not when execution reaches its line. The engine scans the scope first and creates all the bindings. What differs is their initial state: a var starts as undefined, so reading it early silently gives you undefined. A let or const binding exists but is uninitialized until its declaration line runs. The stretch between entering the scope and that line is the Temporal Dead Zone, and any access inside it throws a ReferenceError. So let is hoisted: if it weren't, reading the name early would find the outer variable with that name instead of throwing.

const only stops you from rebinding the name. It says nothing about the value: a const object can be mutated freely. Object.freeze protects the object, but only its first level (the details are in Lesson 06).

              scope entered                 declaration line         scope ends
                   │                              │                      │
 var    ───────────┼── readable, value undefined ─┼── assigned value ────┼──▶ (whole function)
 let    ───────────┼── TDZ: read → ReferenceError ┼── readable, writable ┼──▶ (this block)
 const  ───────────┼── TDZ: read → ReferenceError ┼── readable, no rebind┼──▶ (this block)
الخط الأفقي هو عمر الـ binding من أول دخول الـ scope لحد آخره. الـ var: من أول لحظة تقدر تقراها وقيمتها undefined، ولما توصل لسطر الـ declaration بتاخد قيمتها، وعايشة في الـ function كلها. الـ let: قبل سطرها هي في الـ TDZ وأي قراءة بتضرب ReferenceError، وبعد السطر تقراها وتكتب فيها عادي، وعايشة في الـ block بس. الـ const: نفس الـ TDZ ونفس الـ block، بس بعد السطر مينفعش تربطها بقيمة تانية.
var region = "EG";
let currency = "EGP";
const vatPercent = 14;

function printInvoice() {
  // (1) الـ var اللي تحت اترفعت لأول الـ function بقيمة undefined، وغطّت اللي بره
  console.log(region);
  // → undefined
  var region = "SA";

  // (2) الـ let اللي تحت موجودة من أول الـ block بس لسه في الـ TDZ
  try {
    console.log(currency);
  } catch (e) {
    console.log(`${e.name}: ${e.message}`);
  }
  // → ReferenceError: Cannot access 'currency' before initialization
  let currency = "SAR";

  if (region === "SA") {
    var discount = 10;
    let fee = 5;
    const note = "promo";
    console.log(discount + fee, note);
    // → 15 promo
  }

  // (3) الـ var بتخرج من الـ block عادي، لكن let و const مبيخرجوش منه
  console.log(discount);
  // → 10
  console.log(typeof fee, typeof note);
  // → undefined undefined

  // (4) مفيش حد غطّى vatPercent فبنوصل للي بره عن طريق الـ scope chain
  console.log(vatPercent, currency, region);
  // → 14 SAR SA
}

printInvoice();
// (5) القيم اللي بره متأثرتش خالص، لأن جوه الـ function فيه bindings تانية
console.log(region, currency);
// → EG EGP
const tryIt = (fn) => {
  try {
    return fn();
  } catch (e) {
    return `${e.name}: ${e.message}`;
  }
};

// (1) الـ const اللي جوه موجودة من أول الـ block، فبتغطي اللي بره وتمنع الوصول ليها
const tenantId = "outer";
console.log(tryIt(() => {
  const before = tenantId;
  const tenantId = "inner";
  return before;
}));
// → ReferenceError: Cannot access 'tenantId' before initialization

// (2) الـ typeof آمن مع اسم مش موجود أصلًا، لكنه بيضرب جوه الـ TDZ
console.log(tryIt(() => typeof neverDeclared));
// → undefined
console.log(tryIt(() => {
  const t = typeof planId;
  let planId = "pro";
  return t;
}));
// → ReferenceError: Cannot access 'planId' before initialization

// (3) الـ default parameters بتتقيّم بالترتيب، فده برضه TDZ
const paginate = (limit = offset * 2, offset = 10) => ({ limit, offset });
console.log(tryIt(() => paginate()));
// → ReferenceError: Cannot access 'offset' before initialization

// (4) الـ const بتمنع إعادة الربط بس، مش تعديل الـ object
const order = { id: 1, status: "pending", items: [] };
order.status = "paid";
order.items.push("TSHIRT");
console.log(order);
// → { id: 1, status: 'paid', items: [ 'TSHIRT' ] }
console.log(tryIt(() => {
  order = {};
}));
// → TypeError: Assignment to constant variable.

// (5) الـ freeze بيجمّد أول طبقة بس، والـ array اللي جوه لسه بتتعدّل
const frozen = Object.freeze({ status: "paid", items: [] });
console.log(tryIt(() => {
  frozen.status = "refunded";
}));
// → TypeError: Cannot assign to read only property 'status' of object '#<Object>'
frozen.items.push("CAP");
console.log(frozen.items);
// → [ 'CAP' ]
بالعامية

عندنا 3 scopes مهمين هنا. الـ global: باين في كل حتة. الـ function: باين جوه function واحدة. الـ block: باين جوه { } واحدة، ودي تشمل جسم الـ if والـ loops. الـ var نطاقها الـ function ومبتعترفش بالـ blocks. أما let وconst فنطاقهم الـ block.

الـ hoisting معناه إن الـ declaration بيشتغل لحظة دخول الـ scope، مش لما التنفيذ يوصل لسطره. الـ engine بيلف على الـ scope الأول ويعمل كل الـ bindings. الفرق في الحالة اللي بيبدأوا بيها: الـ var بتبدأ بـ undefined، فلو قريتها بدري هتاخد undefined في صمت. أما let وconst فالـ binding موجود بس مش متهيّأ لحد ما سطر الـ declaration يتنفذ. المسافة من أول الـ scope لحد السطر ده اسمها Temporal Dead Zone، وأي وصول جواها بيضرب ReferenceError. يعني let بتتعملها hoisting فعلًا: لو مكانتش كده، القراءة بدري كانت هتلاقي المتغير اللي بره بنفس الاسم بدل ما تضرب error.

الـ const بتمنعك من إعادة ربط الاسم بس، وملهاش دعوة بالقيمة: object معرّف بـ const تقدر تعدّل فيه براحتك. الـ Object.freeze هو اللي بيحمي الـ object، بس أول طبقة منه بس (التفاصيل في الدرس 06).

امشي على الـ quiz بالترتيب: region طلعت undefined عشان الـ var اللي جوه اترفعت وغطّت اللي بره. currency ضربت ReferenceError عشان الـ let اللي جوه في الـ TDZ لسه. discount خرجت من الـ if عادي عشان var، وfee وnote مخرجوش. وvatPercent وصلنا لها من الـ scope اللي بره. وفي الآخر القيم اللي بره متأثرتش، لأن اللي جوه كانوا bindings تانية بنفس الأسماء. وفي tdz.mjs: حتى typeof اللي بيبقى آمن مع اسم مش موجود بيضرب جوه الـ TDZ، والـ default parameters بتتقيّم بالترتيب فـ limit = offset * 2 بتقع لأن offset لسه متعملش.

فين هستخدمه في شغلي؟ قاعدة الفريق اللي تمشي عليها في أي مشروع: const دايمًا، وlet لو محتاج تعيد الربط فعلًا (عدّاد مثلًا)، وvar أبدًا. والـ ESLint بيفرضها بـ no-var وprefer-const (الـ config في الجزء 5). أما الـ TDZ فهتقابله في الشغل كده: ReferenceError: Cannot access 'db' before initialization في الـ production بعد refactor. غالبًا السبب circular import بين ملفين، والملف التاني بيقرا الـ const قبل ما الأول يخلص (الدرس 12). ولما تشوف الـ error ده، متحطش var عشان تسكّته، صلّح ترتيب الـ imports.

The global scope, and why strict mode matters الـ global scope، وليه الـ strict mode مهم

English

In a classic script (a plain <script> tag) a top-level var becomes a property of the global object, which can collide with anything else on the page, and a top-level let doesn't. Without strict mode, assigning to a name you never declared silently creates a global, so a typo becomes shared state. In an ES module neither happens: top-level declarations stay in the module, and the code is always strict, so the typo throws straight away. Files using CommonJS aren't strict unless they say "use strict", although TypeScript's strict option adds it to emitted output.

import vm from "node:vm";

// (1) في script عادي: الـ var بتبقى property على الـ global، والـ let لأ
const scriptResult = vm.runInNewContext(`
  var apiUrl = "https://api.example.com";
  let apiKey = "secret";
  [typeof globalThis.apiUrl, typeof globalThis.apiKey];
`);
console.log(scriptResult);
// → [ 'string', 'undefined' ]

// (2) في script من غير strict: غلطة كتابة بتعمل global من غير ما تحس
const sloppy = vm.runInNewContext(`
  function chargeOrder() { totl = 500; }
  chargeOrder();
  globalThis.totl;
`);
console.log(sloppy);
// → 500

// (3) في ESM الكود strict دايمًا، فنفس الغلطة بتضرب ReferenceError على طول
function chargeOrder() {
  try {
    totl = 500;
  } catch (e) {
    console.log(`${e.name}: ${e.message}`);
  }
}
chargeOrder();
// → ReferenceError: totl is not defined

// (4) في ESM الـ var اللي على مستوى الملف بتفضل جوه الـ module ومبتوصلش للـ global
var moduleScoped = 1;
console.log(typeof globalThis.moduleScoped);
// → undefined
بالعامية

في script عادي (<script> tag من غير module) الـ var اللي على المستوى الأعلى بتبقى property على الـ global object، وممكن تتخانق مع أي حاجة تانية في الصفحة، أما let فلأ. ومن غير strict mode، لو كتبت في اسم عمرك ما عرّفته، بيتعمل global في صمت، فغلطة كتابة بتتحول لـ state مشتركة. في الـ ES module مفيش الكلام ده: الـ declarations بتفضل جوه الـ module، والكود strict دايمًا، فالغلطة بتضرب على طول. أما ملفات CommonJS فمش strict إلا لو كتبت "use strict"، مع إن خيار strict في TypeScript بيضيفها في الـ output.

Interview question: "Is let hoisted? What is the TDZ?" Yes, let and const are hoisted: the binding is created when the scope is entered. Part 3 — Primitives & typeof 🟢 Basicالجزء 3 — الـ primitives و typeof

English

JavaScript has seven primitive types; everything else is an object (arrays and functions included). Primitives are immutable: "abc".toUpperCase() returns a new string and leaves the original alone, and you can't change a character in place. Writing to a string's index or adding a property to it throws a TypeError in strict mode and is silently ignored in sloppy mode. You can call methods on primitives because the engine behaves as if it wrapped them in a temporary object for that one access.

typeof null === "object" is a bug from the first version of the language that can never be fixed. Early engines stored values with a small type tag, and the tag for objects was 0. null was represented as the null pointer, all zeros, so its tag read as "object". A fix was proposed for ECMAScript and rejected, because too much existing code depends on the behaviour. In practice: check for null with === null, check for arrays with Array.isArray, and when you write typeof v === "object" also add && v !== null.

undefined and null are different signals. undefined means "nothing was provided": a missing property, a missing argument, a function with no return. null means "deliberately empty", which is also how SQL NULL reaches you from a database driver. The difference has semantic weight in APIs, because JSON.stringify drops undefined keys and keeps null ones. In PATCH /orders/:id a missing key means "don't touch this column" and null means "clear it".

Part 4 — Objects as references 🟢 Basicالجزء 4 — الـ objects كـ references

English

A variable holding an object doesn't hold the object, it holds a reference to it (the memory model is covered in CS Lesson 01, Part 3). This lesson is about the language rules that follow from that. Assignment copies the reference, so two names can point at one object and a change through either is visible through both. Comparison compares identity: === asks "same object?", never "same contents?", so { id: 1 } === { id: 1 } is false. Set and Map use nearly the same rule, which is why new Set([{ id: 1 }, { id: 1 }]) has 2 items.

JavaScript passes arguments by sharing: the parameter receives a copy of the reference. Mutating the object through the parameter is visible to the caller. Rebinding the parameter to something new isn't. So a function that "just adjusts" an order it was handed is really changing everyone's order. The fix is a function that returns a new object and leaves its input alone. Spread only makes a shallow copy, though: nested objects are still shared (deep copies and structuredClone are in Lesson 05).

React is built on this rule. memo, useEffect dependencies and state updates all compare with Object.is, which treats objects by identity. An object literal in JSX is a brand-new object on every render, so memo never sees "same props". Measured below: 4 renders with a new object, 1 with a stable reference. The same rule is why mutating state in place doesn't re-render: the reference hasn't changed.

What breaks in production: the shared cache إيه اللي بيقع في الـ production: الكاش المشترك

An in-process cache returns references, not copies. Every request in a Node process shares the same heap, so one handler mutating a cached object changes it for all later requests, for as long as that process lives. It doesn't reproduce in a unit test that hits the handler once, it only hits some customers, and a restart "fixes" it, which sends the investigation in the wrong direction. A value fetched from Redis doesn't have this problem, since each read deserializes a fresh object.

Part 5 — Coercion: == vs ===, truthy & falsy 🟢 Basicالجزء 5 — الـ coercion: الفرق بين == و ===، والـ truthy والـ falsy

English

Coercion is JavaScript converting a value to another type because an operator needs it. There are three conversions to know: to boolean (conditions), to number (arithmetic and ==), and to string (+ and templates).

Boolean. Exactly 8 values are falsy: false, 0, -0, 0n, "", null, undefined, NaN. Everything else is truthy, including "0", "false", [] and {}. (Browsers have one legacy exception, document.all, which you won't use on purpose.) That makes if (x) a question about truthiness, not presence, and 0 and "" are often perfectly valid data: a 0% discount, free shipping, an empty note.

The + operator. It's the only arithmetic operator that also does strings. Both sides are converted to primitives; if either is a string, it concatenates; otherwise it adds numbers. -, * and / always convert to numbers. So "5" + 1 is "51" and "5" - 1 is 4.

Equality. === never converts: different types means false. == converts first, and that's where "" == 0, "0" == false and [] == false all come out true. Use === everywhere. The one accepted exception is x == null, which matches null and undefined and nothing else, so it's a precise "is it missing?" check.

Values from outside your process often arrive as strings: req.query, req.params, process.env, form data, CSV cells, and Postgres numeric and bigint through pg. Convert them once at the boundary, validate the result, and work with real types from then on.

Part 6 — Operators that bite 🟢 Basicالجزء 6 — الـ operators اللي بتعض

English

Arithmetic and comparison. % is a remainder, not a modulo: the result takes the sign of the left operand, so -7 % 3 is -1. Dividing by zero doesn't throw, it gives Infinity or NaN. Comparing two strings goes character by character, so "10" < "9" is true; comparing a string with a number converts to numbers. null is its own trap: null >= 0 is true because relational operators convert it to 0, while null == 0 is false because == has a special case for it.

|| vs ??. a || b returns b whenever a is falsy. a ?? b returns b only when a is null or undefined. For defaults you almost always mean ??, because 0, "" and false are real values. The two can't be mixed without parentheses: that's a SyntaxError by design.

&& and || return operands, not booleans. a && b returns a if it's falsy, otherwise b. Both short-circuit, so the right side isn't evaluated when the left decides. This causes a classic React bug: {count && <List />} with count = 0 evaluates to 0, and React renders the number, since it skips false, null and undefined but not 0.

Logical assignment. a ||= b, a &&= b and a ??= b assign only when the condition holds, and they use the same truthiness rules.

Optional chaining: what it protects and what it doesn't الـ optional chaining: بيحمي إيه ومبيحميش إيه

English

a?.b evaluates to undefined if a is null or undefined, and it short-circuits the rest of the chain: guest.customer?.address.city.length doesn't throw when customer is null, because nothing after ?. runs, including arguments in a call. Parentheses end the chain, so (a?.b).c throws. And ?. only guards the value right before it: if customer exists but address doesn't, customer?.address.city still throws. It comes in three forms: a?.b, a?.[key], a?.().

Don't scatter it everywhere. If an order must have a customer by your data model, order.customer?.name turns a clear crash at the source into a blank name on an invoice three layers later. Use ?. where absence is legitimate.

const tryIt = (fn) => {
  try {
    return fn();
  } catch (e) {
    return `${e.name}: ${e.message}`;
  }
};

const guest = { id: 1, customer: null };

  id: 2,
  customer: {
    address: { city: "Cairo" },

      return "sent";
    },

console.log(guest.customer?.address.city, member.customer?.address.city);

console.log(tryIt(() => guest.customer?.address.city.length));
// → undefined

// الأقواس بتقفل الـ chain، فاللي بعدها بيتنفذ على undefined ويقع
console.log(tryIt(() => (guest.customer?.address).city));

الـ a?.b بتطلع undefined لو a بـ null أو undefined، وبتقطع باقي الـ chain: guest.customer?.address.city.length مبتضربش لما customer تبقى null، لأن مفيش حاجة بعد ?. بتتنفذ، حتى الـ arguments في نداء function. والأقواس بتقفل الـ chain، فـ (a?.b).c بتضرب. والـ ?. بتحمي القيمة اللي قبلها بس: لو customer موجود وaddress لأ، customer?.address.city لسه بتضرب. وليها 3 أشكال: a?.b وa?.[key] وa?.().

متفرّشهاش في كل حتة. لو الـ order لازم يكون ليه customer حسب الـ data model، فـ order.customer?.name بتحوّل crash واضح في مكانه لاسم فاضي على فاتورة بعد 3 طبقات. استخدم ?. في الأماكن اللي الغياب فيها طبيعي فعلًا.

Spread, rest & ternary الـ spread والـ rest والـ ternary

English

Spread { ...a, ...b } copies own enumerable properties left to right, and the last writer wins. So { ...defaults, ...input } means defaults first, overridden by input. Reverse the order deliberately when a field must not be overridable, like { ...body, tenantId: session.tenantId }, otherwise a client can send its own tenantId. An explicit undefined in input still overwrites the default, unlike a default parameter.

Rest const { passwordHash, ...safe } = user collects everything you didn't name, which is the usual way to strip a field. It's a deny-list, though: when someone adds resetToken to the table, it goes out with the response. For anything that crosses a trust boundary, an allow-list (({ id, email }) => ({ id, email })) is the safer default. Rest in parameters, (...amounts), collects arguments into a real array.

Ternary. One level is clear and works as an expression. Nested ternaries get hard to read and hard to extend, so replace them with a lookup. A plain object lookup has its own trap when the key comes from a user: obj["constructor"] finds an inherited function. Use a Map or Object.hasOwn for that case.

const defaults = { limit: 20, sort: "createdAt", includeDeleted: false };

// الـ spread: اللي بييجي آخر هو اللي بيكسب
const fromUser = { limit: 50 };
console.log({ ...defaults, ...fromUser });
// → { limit: 50, sort: 'createdAt', includeDeleted: false }

// ❌ لو عكست الترتيب، الـ defaults بتكسب وكلام المستخدم بيضيع
console.log({ ...fromUser, ...defaults }.limit);
// → 20

// ✅ الترتيب ده مفيد لما عايز تقفل حقل: tenantId لازم يبقى من الـ session
const body = { name: "Acme", tenantId: 999 };
const session = { tenantId: 7 };
console.log({ ...body, tenantId: session.tenantId });
// → { name: 'Acme', tenantId: 7 }

const fromForm = { limit: undefined };
console.log({ ...defaults, ...fromForm }.limit);
// → undefined

// الـ rest: شيل الحقول الحساسة قبل ما تبعت الـ user
const userRow = { id: 1, email: "a@x.io", passwordHash: "$argon2id$abc", mfaSecret: "JBSW" };
const { passwordHash, ...withoutHash } = userRow;
console.log(Object.keys(withoutHash));
// → [ 'id', 'email', 'mfaSecret' ]

// ✅ الـ allow-list أأمن: أي عمود جديد مش هيتسرب من غير ما تقصد
const toPublicUser = ({ id, email }) => ({ id, email });
console.log(toPublicUser(userRow));
// → { id: 1, email: 'a@x.io' }

// الـ rest في الـ parameters بتجمّع الباقي في array حقيقية
const sumMinor = (...amounts) => amounts.reduce((a, b) => a + b, 0);
console.log(sumMinor(100, 250, 50));
// → 400
// الـ ternary مستوى واحد واضح وبيدخل في const
const badge = (order) => (order.paid ? "Paid" : "Unpaid");
console.log(badge({ paid: true }));
// → Paid

// ❌ المتداخل بيتقري بالعافية، وأي حالة جديدة بتبوّظه
const statusLabelBad = (s) =>
  s === "paid" ? "Paid" : s === "pending" ? "Pending" : s === "failed" ? "Failed" : "Unknown";

// ✅ الـ lookup بيخلي كل حالة في سطر، والـ nullish coalescing بتمسك أي حالة مش معروفة
const STATUS_LABELS = { paid: "Paid", pending: "Pending", failed: "Failed" };

console.log(statusLabelBad("failed"), statusLabel("failed"), statusLabel("shipped"));
// → Failed Failed Unknown

// خد بالك: الـ object العادي بيورث من Object.prototype، فدي مش Unknown
console.log(typeof statusLabel("constructor"));
// → function

// ✅ الـ Map مفيهاش الوراثة دي، وده مهم لو الـ key جاي من المستخدم
const LABELS = new Map(Object.entries(STATUS_LABELS));
console.log(LABELS.get("constructor") ?? "Unknown");
// → Unknown
بالعامية

الـ spread { ...a, ...b } بينسخ الـ own enumerable properties من الشمال لليمين، واللي بييجي آخر هو اللي بيكسب. يعني { ...defaults, ...input } معناها الـ defaults الأول والـ input بيكتب فوقها. واعكس الترتيب بقصد لما يكون فيه حقل ممنوع يتغيّر، زي { ...body, tenantId: session.tenantId }، وإلا الـ client يقدر يبعت tenantId بتاعه. وقيمة undefined صريحة في الـ input بتكتب فوق الـ default برضه، عكس الـ default parameter.

الـ rest const { passwordHash, ...safe } = user بيجمّع كل اللي مسمّيتوش، ودي الطريقة المعتادة لشيل حقل. بس دي deny-list: لو حد ضاف resetToken للجدول، هيطلع مع الـ response. فأي حاجة بتعدّي حدود الثقة، الـ allow-list (({ id, email }) => ({ id, email })) هي الاختيار الأأمن. والـ rest في الـ parameters (...amounts) بيجمّع الـ arguments في array حقيقية.

الـ ternary: مستوى واحد واضح وبيشتغل كـ expression. أما المتداخل فصعب يتقري وصعب تزوّد عليه، فاستبدله بـ lookup. والـ lookup على object عادي ليه فخ لوحده لو الـ key جاي من المستخدم: obj["constructor"] بتلاقي function موروثة. في الحالة دي استخدم Map أو Object.hasOwn.

فين هستخدمه في شغلي؟ { ...body, tenantId: session.tenantId } هي السطر اللي بيمنع tenant يكتب في data tenant تاني في SaaS. وres.json(user) من غير DTO هي أشهر طريقة لتسريب passwordHash، فخلّي toPublicUser هي الطريق الوحيد اللي الـ user بيخرج منه. والـ STATUS_LABELS[s] ?? "Unknown" تمام طول ما s جاية من الكود بتاعك؛ لو جاية من req.query استخدم Map.
Interview question: "What's the difference between || and ??? Give a bug that || causes." || falls back on any falsy value, ?? only on null and undefined. Bug: const fee = order.shippingFeeMinor || 5000 charges 50 EGP on an order with free shipping, because 0 is falsy. ?? keeps the 0. || is still right when an empty string should also fall back, such as a display name.
السؤال: "إيه الفرق بين || و??؟ وهات bug بيعمله ||." الإجابة: الـ || بتاخد الـ fallback مع أي قيمة falsy، و?? مع null وundefined بس. الـ bug: const fee = order.shippingFeeMinor || 5000 بتحسب 50 جنيه على order شحنه مجاني، لأن 0 falsy. الـ ?? بتسيب الصفر زي ما هو. والـ || لسه صح لما الـ string الفاضية المفروض تاخد fallback برضه، زي اسم العرض.

Solution · الحل 
const MAX_LIMIT = 100;

const toInt = (raw) => {
  if (typeof raw !== "string" || raw.trim() === "") return NaN;
  const n = Number(raw);
  return Number.isInteger(n) ? n : NaN;
};

// الـ limit و الـ offset جايين strings من req.query، وأي حاجة غلط بترجّع error واضح
export function parsePagination(query) {
  const limit = query.limit === undefined ? 20 : toInt(query.limit);
  const offset = query.offset === undefined ? 0 : toInt(query.offset);
  if (Number.isNaN(limit) || limit < 1 || limit > MAX_LIMIT) return { error: "invalid limit" };
  if (Number.isNaN(offset) || offset < 0) return { error: "invalid offset" };
  return { limit, offset };
}

// → { limit: 50, offset: 0 }
console.log(parsePagination({ limit: "" }));
// → { error: 'invalid limit' }
console.log(parsePagination({ limit: ["1", "2"] }));
// → { error: 'invalid limit' }
console.log(parsePagination({ limit: "1000" }));
// → { error: 'invalid limit' }
console.log(parsePagination({ offset: "-1" }));
// → { error: 'invalid offset' }

  Object.fromEntries(Object.entries(obj).filter(([, v]) => v !== undefined));

const DEFAULTS = { currency: "EGP", locale: "ar-EG", marketingEmails: true };

export function mergeSettings(saved, patch, session) {
  return { ...DEFAULTS, ...compact(saved), ...compact(patch), tenantId: session.tenantId };
}

  { marketingEmails: false, tenantId: 999 },

);

Cheat sheet · الخلاصة

  • Expression = gives a value; statement = does something. {} in JSX, ${} and arguments take expressions only, because JSX compiles to a function call.
  • Arrow with { } needs return. Returning an object literal needs ({ }).
  • const by default, let when rebinding, var never. const doesn't freeze; Object.freeze does, one level deep.
  • var starts as undefined; let/const are hoisted into the TDZ, and access there throws. ESM is always strict.
  • 7 primitives, all immutable. typeof null === "object" is a permanent bug; check with === null.
  • undefined = not provided, null = deliberately empty. JSON drops the first and keeps the second, which is what makes PATCH work.
  • Assignment copies references, === compares identity, arguments are passed by sharing. Return a new object instead of mutating your input. Spread is shallow.
  • In-process caches hand out shared references: mutating one corrupts it for every later request.
  • 8 falsy values: false 0 -0 0n "" null undefined NaN. "0", "false", [], {} are truthy.
  • + concatenates if either side is a string; - * / always go numeric. req.query, process.env and pg numeric/bigint are strings: convert once at the boundary.
  • === everywhere; x == null is the only accepted ==. For defaults use ??, not ||. In JSX use count > 0 && …, not count && ….
  • ?. short-circuits the rest of the chain but guards only what's before it. Spread: last wins, so { ...defaults, ...input, tenantId }. Allow-list what leaves your API.
