Why this matters · ليه ده مهم

English

Backend code spends its life reshaping collections: grouping orders, indexing users, checking permissions, importing a million rows. The choice of collection and of how you walk it decides whether that endpoint takes 3 ms or 60 seconds, and whether the process holds 19 MB or 121 MB. Those two pairs of numbers are measured in this lesson on the same data. Interviews use the same material: the {...acc} trap, why a Map keyed by objects leaks, and how to make a class work with for...of.

بالعامية

كود الـ backend طول عمره بيشكّل في collections: يجمّع orders، يعمل index للـ users، يتشيك على permissions، يستورد مليون row. واختيارك للـ collection وللطريقة اللي بتلف بيها عليها هو اللي بيحدد الـ endpoint هياخد 3 ms ولا 60 ثانية، والـ process هيمسك 19 MB ولا 121 MB. الرقمين دول متقاسين في الدرس ده على نفس الـ data. والـ interviews بتسأل في نفس الحاجات: فخ الـ {...acc}، وليه Map الـ keys بتاعتها objects بتعمل leak، وإزاي تخلي class يشتغل مع for...of.

Part 1 — Modern array methods & reduce mastery 🟡 Intermediateالجزء 1 — الـ array methods الحديثة وإتقان reduce

English

flat(depth = 1) flattens nested arrays. flatMap(fn) is map followed by flat(1), and it can do something map can't: return [] to drop an element, or several elements to expand one. at(i) accepts negative indexes; arr[-1] is just a lookup of a property named "-1", so it returns undefined without complaint.

The ES2023 copying methods let you stop mutating shared arrays. They copy the array, not the objects inside it, so the copy is shallow:

العمود الشمال بيعدّل في الـ array الأصلية، واللي في النص بيرجّع array جديدة. sort قصادها toSorted بنفس قواعد الـ comparator: من غير fn الترتيب بيبقى كـ strings. reverse قصادها toReversed. splice قصادها toSpliced، وخد بالك إنها بترجّع الناتج مش العناصر اللي اتشالت. وarr[i] = v قصادها with(i, v): دي بتضرب RangeError لو الـ index بره الحدود، أما الـ assignment العادي بيعمل holes في صمت.

Array.from(source, mapFn) builds an array from any iterable or array-like and maps it in one pass. Array.of(3) gives [3], while Array(3) gives three holes that map skips. Object.groupBy (ES2024) replaces most hand-written group-bys; it returns a null-prototype object, and Map.groupBy does the same for non-string keys.

reduce folds a list into one value of any shape: a number, an object, a Map, or a function pipeline. Reach for it when the result accumulates across elements, such as totals per user. If a plain groupBy, map or Object.fromEntries says the same thing, use those: they read better. The basics of reduce are in lesson 05; here we go after the patterns and the trap.

const minimumCharge: Step<number> = (cents) => Math.max(cents, 1000);

const checkoutTotal = pipe(applyCoupon, addVat, minimumCharge);
console.log(checkoutTotal(12_000), checkoutTotal(800));
// → 13110 1000

English

The trap. (acc, o) => ({ ...acc, [o.id]: o }) looks clean and functional, but each step copies every key collected so far. That is 1 + 2 + … + n copies, or O(n²) (see CS lesson 02). Measured below on this machine, which was under load, so read the ratios: doubling n multiplies the time by roughly 4 to 6.

type Order = { id: string; total: number };
const makeOrders = (n: number): Order[] =>
  Array.from({ length: n }, (_, i) => ({ id: `ord_${i}`, total: i % 500 }));

// ❌ كل iteration بتنسخ الـ acc كله: ⁦1 + 2 + 3 + … + n = O(n²)⁩ نسخة key
const indexWithSpread = (orders: Order[]) =>
  orders.reduce<Record<string, Order>>((acc, o) => ({ ...acc, [o.id]: o }), {});

// ✅ عدّل الـ acc بتاعك: الـ reduce هو اللي عمله فمحدش تاني شايفه
const indexWithMutation = (orders: Order[]) =>
  orders.reduce<Record<string, Order>>((acc, o) => {
    acc[o.id] = o;
    return acc;
  }, {});

// ✅ أو من غير reduce خالص: الأوضح لما الـ key معروف
const indexWithFromEntries = (orders: Order[]) =>
  Object.fromEntries(orders.map((o) => [o.id, o]));

const time = (fn: () => unknown) => {
  const t0 = performance.now();
  fn();
  return performance.now() - t0;
};

console.log("     n     spread   mutation  fromEntries");
for (const n of [1_000, 2_000, 4_000, 8_000, 16_000]) {
  const orders = makeOrders(n);
  const a = time(() => indexWithSpread(orders));
  const b = time(() => indexWithMutation(orders));
  const c = time(() => indexWithFromEntries(orders));
  console.log(
    `${String(n).padStart(6)} ${a.toFixed(0).padStart(8)}ms ${b.toFixed(1).padStart(8)}ms ${c.toFixed(1).padStart(10)}ms`,
  );
}

بالعامية

flat(depth = 1) بيفرد الـ arrays المتداخلة. وflatMap(fn) يعني map وبعدها flat(1)، وبتعمل حاجة الـ map متعرفش تعملها: ترجّع [] فالعنصر يتشال، أو ترجّع كذا عنصر فالعنصر الواحد يتوسّع. وat(i) بتاخد index سالب؛ أما arr[-1] فهي مجرد lookup على property اسمها "-1"، فبترجع undefined من غير ما تشتكي.

الـ methods الجديدة بتاعة ES2023 بتخليك تبطّل تعدّل في arrays مشتركة: toSorted وtoReversed وtoSpliced وwith. بس النسخة shallow: الـ array جديدة، والـ objects اللي جواها هي هي. عشان كده byTotalDesc[0] === orders[2] طلعت true في الـ output، وأي تعديل على الـ object هيوصل للأصلية.

Array.from(source, mapFn) بتبني array من أي iterable أو array-like وتعمل map في pass واحد. Array.of(3) بتدّيك [3]، أما Array(3) بتدّيك 3 holes، والـ map بيتخطاهم. وObject.groupBy (ES2024) بتغنيك عن أغلب الـ group by اللي بتكتبه بإيدك، وبترجّع object من غير prototype (فمفيش hasOwnProperty عليه)؛ وMap.groupBy بتعمل نفس الحاجة لو الـ key مش string.

reduce بتحوّل list لقيمة واحدة بـ أي شكل: رقم، object، Map، أو pipeline من functions. استخدمها لما الناتج بيتراكم عبر العناصر، زي الـ totals لكل user. ولو groupBy أو map أو Object.fromEntries بيقولوا نفس الكلام، استخدمهم: أوضح في القراية. الأساسيات في درس 05؛ هنا بنركز على الـ patterns والفخ.

الفخ: (acc, o) => ({ ...acc, [o.id]: o }) شكلها نضيف و functional، بس كل خطوة بتنسخ كل الـ keys اللي اتجمعت لحد دلوقتي: 1 + 2 + … + n نسخة، يعني O(n²) (درس CS رقم 02). الـ "immutability" هنا ملهاش لازمة أصلًا: الـ acc إنت اللي عامله ومحدش تاني شايفه، فتعديله أمان تمامًا.

فين هستخدمه في شغلي؟ في GET /admin/orders عندك cache للـ orders مشترك بين الـ requests: toSorted بدل sort عشان request واحد ميغيّرش الترتيب على الباقيين. وفي React، toSorted وwith بيدّوك state update من غير mutation. وفي تقرير "الإيراد لكل tenant" استخدم reduce بـ acc بتعدّله أو Map. ولو شوفت في code review {...acc} جوه reduce على list ممكن تكبر، علّق عليها: ده endpoint شغال كويس على 1,000 order في staging، وبياخد دقيقة على 16 ألف في production.

Part 2 — Iteration protocols 🟡 Intermediateالجزء 2 — الـ iteration protocols

English

Two small contracts make for...of work. An iterable is any object with a [Symbol.iterator]() method that returns an iterator (lesson 06 introduced the symbol). An iterator is any object with a next() method that returns { value, done }. The split matters: the iterable is the collection and can be walked many times; the iterator is one cursor, it holds the position, and it is used up once.

An iterator may also have a return() method. It is called when the consumer stops early: break, a return or exception inside the loop, or array destructuring that takes fewer values than exist. It is not called when the iterator ran to done: true on its own. This is where you release a connection or close a file.

Everything below speaks the protocol, so your class gets all of it for free: for...of, spread, array destructuring, Array.from, new Map(...), new Set(...), Promise.all and friends, Object.fromEntries, and yield*. for...in and Object.keys don't use it. The protocol is synchronous: next() must return now. Pagination over a real network needs the async version, covered in lesson 10.

الـ for...of بينادي orders[Symbol.iterator]() ويستلم iterator، وده cursor واحد ماسك المكان. بعدين بينادي next() كل لفة: لو رجع { value, done: false } بيشغّل جسم الـ loop؛ ولو رجع { done: true } الـ loop بيخلص ومن غير ما ينادي return(). ولو عملت break في النص، بينادي iterator.return() الأول وبعدين الـ loop يخلص.
type Order = { id: string; total: number };

// تخيّل إن ده read من ملف cache: sync، صفحة كل مرة
const fetchPage = (page: number): Order[] => {
  console.log(`  [db] load page ${page}`);
  if (page >= 3) return [];
  return [0, 1].map((i) => ({ id: `ord_${page}${i}`, total: 100 * page + i }));
};

class PagedOrders implements Iterable<Order> {
  // (1) الـ iterable: أي object عنده ⁦[Symbol.iterator]()⁩ بيرجع iterator جديد
  [Symbol.iterator](): Iterator<Order> {
    let page = 0;
    let buffer: Order[] = [];
    let position = 0;
    let finished = false;

    return {
      // (2) الـ iterator: أي object عنده ⁦next()⁩ بيرجع ⁦{ value, done }⁩
      next(): IteratorResult<Order> {
        if (finished) return { value: undefined, done: true };
        if (position === buffer.length) {
          buffer = fetchPage(page++);
          position = 0;
          if (buffer.length === 0) {
            finished = true;
            return { value: undefined, done: true };
          }
        }
        return { value: buffer[position++], done: false };
      },
      // (3) اختياري: بيتنادى لما الـ consumer يوقف بدري (break، throw، destructuring)
      return(): IteratorResult<Order> {
        console.log("  [db] release connection");
        finished = true;
        return { value: undefined, done: true };
      },
    };
  }
}

عقدين صغيرين هما اللي بيشغّلوا for...of. الـ iterable: أي object عنده method اسمها [Symbol.iterator]() بترجّع iterator (الـ symbol شرحناه في درس 06). والـ iterator: أي object عنده next() بترجّع { value, done }. والفصل ده مهم: الـ iterable هو الـ collection وتقدر تلف عليه كذا مرة؛ أما الـ iterator فهو cursor واحد، ماسك المكان، وبيخلص مرة واحدة. عشان كده [...oneShot] التانية في الكود طلعت [].

الـ iterator ممكن يبقى عنده return() كمان. بتتنادى لما الـ consumer يوقف بدري: break، أو return أو exception جوه الـ loop، أو destructuring بياخد قيم أقل من الموجود. ومش بتتنادى لو الـ iterator وصل done: true لوحده. ده مكان إنك تسيب الـ connection أو تقفل الملف.

كل دول بيتكلموا بالـ protocol، فالـ class بتاعك بياخدهم ببلاش: for...of، والـ spread، والـ array destructuring، وArray.from، وnew Map(...)، وnew Set(...)، وPromise.all وأخواتها، وObject.fromEntries، وyield*. أما for...in وObject.keys ملهمش دعوة بيه. والـ protocol ده sync: next() لازم ترجع دلوقتي؛ فالـ pagination على network حقيقية محتاجة النسخة الـ async اللي في درس 10.

وخد بالك: الـ plain object مش iterable (TypeError: totalsByUser is not iterable)، فلف على Object.entries. والـ array-like (عنده length) مش iterable برضه بس Array.from بتفهمه. والـ string بتتلف بالـ code points، فالـ emoji بيفضل حرف واحد: label.length طلع 5 بس [...label].length طلع 4.

فين هستخدمه في شغلي؟ عندك في الـ data layer class زي OrderCollection أو CartLines جواه array أو pages: بدل ما تكشف الـ array الداخلية وتسيب كل اللي بيستخدمه يعدّل فيها، اعمله [Symbol.iterator]. الـ caller يكتب for (const line of cart) أو [...cart]، وإنت حر تغيّر التخزين من array لـ pages من غير ما تكسر حد. ولو الـ loop ممكن يوقف بدري وفيه resource مفتوح، return() هو اللي بيمنع connection leak في الـ pool.

Part 3 — Generators 🟡 Intermediateالجزء 3 — الـ generators

English

Writing an iterator by hand means keeping the position in variables, as PagedOrders did. A generator lets the language keep it for you: the function's local variables and its place in the code survive between calls. Calling a function* runs nothing; it returns a generator object. Each next() resumes the body until the next yield, which hands out a value and pauses. return x finishes with { value: x, done: true }, and for...of and spread ignore that final value. The generator object is both iterable and iterator (gen[Symbol.iterator]() === gen), so it is single-use.

yield* delegates to another iterable and evaluates to the delegate's return value, which makes recursive walks short. Because a value is computed only when someone asks, an endless loop is safe (invoice numbers below). It also means generators are pull-based: if the consumer awaits a slow insert between next() calls, no new rows are produced in the meantime. That is backpressure at no extra cost.

return() and throw() let the consumer act on a paused generator. gen.return(v) finishes it at the current yield, runs any finally, and gives back { value: v, done: true }. gen.throw(err) raises err at the paused yield; the generator can catch it and keep going. If the generator never started, there is no try to enter yet, so return() skips the body entirely and throw() sends the error straight back to the caller. Either way the generator is finished.

yield* بتسلّم الشغل لـ iterable تاني، وقيمتها هي الـ return بتاع اللي سلّمته، وده بيخلي الـ recursion قصير (الـ walk على شجرة الـ categories). ولأن القيمة مش بتتحسب غير لما حد يطلبها، الـ loop اللي ملوش نهاية أمان. وده معناه كمان إن الـ generators pull-based: لو الـ consumer مستني insert بطيء بين كل next() والتاني، مفيش rows جديدة بتتعمل. يعني backpressure من غير أي تكلفة زيادة.

return() وthrow() بيخلّوا الـ consumer يتدخل في generator واقف. gen.return(v) بتنهيه عند الـ yield الحالي، وتشغّل أي finally، وترجّع { value: v, done: true }. وgen.throw(err) بترمي err عند الـ yield الواقف، والـ generator يقدر يمسكه ويكمل. ولو الـ generator لسه مبدأش، فمفيش try دخلها أصلًا: return() بتتخطى الجسم كله، وthrow() بترجّع الـ error للي نادى على طول. وفي الحالتين الـ generator بيخلص.

الـ iterator helpers (ES2025) هي نسخ lazy من map وfilter وtake وdrop وflatMap وreduce وtoArray وforEach وsome وevery وfind، بس على iterators. موجودة في Node 22، واتأكدنا بالتشغيل. بتشتغل على الـ generators، وarray.values()، وmap.values()، وأي iterable عن طريق Iterator.from. وبعكس الـ array methods، مش بتعمل شغل غير لما حد يسحب، وبتقف أول ما تقدر.

التكلفة: كل yield بيعمل suspend و resume لـ function. في التشغيل ده الـ generator كلّف حوالي 11 مرة قد الـ loop العادي لكل عنصر، يعني 34 ns تقريبًا. ده بيفرق في loop رقمي ضيق، وملوش أي لازمة جنب round trip واحد للداتابيز. وبناء نفس الـ 20 مليون قيمة في array طلع أبطأ من الـ generator بسبب الـ allocation. والغلطة الشائعة هنا: تعدّ الـ generator بـ [...rows] وبعدين تلف عليه تاني فتلاقيه فاضي (موجودة في الـ common mistakes).

فين هستخدمه في شغلي؟ أي job بيستورد CSV أو ينقل data بين جدولين: for (const batch of chunk(rows, 1000)) await db.insert(batch). الـ memory ثابتة مهما كان الحجم، والـ await بيهدّي الـ producer لوحده لو الداتابيز بطّأت. وعدد الـ columns × حجم الـ batch لازم يفضل تحت حد الـ 65535 parameter بتاع Postgres؛ وده السبب الأصلي إن الـ batch بيتقسم. ولو الـ rows جاية من مصدر async (cursor أو API) هتستخدم نفس الفكرة بـ async function* في درس 10. وفي الـ pipeline الـ sync على data كبيرة، .filter().map().take() من iterator helpers بدل ما تبني 3 arrays وسيطة.

Part 4 — Map vs Object, Set operations 🟡 Intermediateالجزء 4 — الـ Map ضد الـ Object، وعمليات الـ Set

English

Use an object for a record (a fixed, known set of fields) and a Map for a dictionary (keys that come from data and get added and removed at runtime). The full comparison table, the hash-table internals, and the benchmark are in CS lesson 04; that run measured inserts about 4× faster and add/delete churn about 2.5× faster with Map. Not repeated here. This part covers the behaviour that causes bugs:

  • Non-string keys. An object turns every key into a string, so two different objects both become "[object Object]". A Map keeps the real key; objects compare by reference.
  • Inherited keys. On a plain object counts["constructor"] is already a function. User data can hit that. Map starts empty.
  • Order. A Map iterates in insertion order. An object puts integer-like keys first, ascending. Calling set on an existing key keeps its position; delete then set moves it to the end, which is the idea behind an LRU cache.
  • Size and iteration. map.size is O(1) and a Map is directly iterable. An object needs Object.keys(o).length or Object.entries, which build arrays first.
  • JSON. JSON.stringify(map) gives {}. Convert at the API boundary.

Set methods (ES2025, in Node 22, verified below): union, intersection, difference, symmetricDifference, isSubsetOf, isSupersetOf, isDisjointFrom. They replace [...a].filter(x => b.has(x)). The argument must be set-like (with size, has and keys), so a Map works and an array throws. A Set compares objects by reference, so de-duplicating by value needs a Map on a key.

Part 5 — WeakMap & WeakSet 🟡 Intermediateالجزء 5 — الـ WeakMap والـ WeakSet

English

A Map holds a strong reference to each key, so as long as the map lives, the key can't be collected. A WeakMap holds its keys weakly: the entry doesn't count as a reason to keep the key alive. When nothing else references the key, the garbage collector may reclaim it and the entry goes with it. The value is only kept alive through the key, so even a value that points back at its own key doesn't keep the pair alive. That structure is called an ephemeron.

That gives three uses: metadata on objects you don't own (a request, a socket, a DOM node), caching derived data per object, and private data stored outside the object (the pattern before #private, still seen in libraries). WeakSet is the same idea for membership, such as marking objects already visited.

Why no size, keys() or for...of? If you could list the entries, your program's output would depend on when GC happened to run, and that is non-deterministic. The API (get, set, has, delete) only lets you ask about a key you already hold. Keys must be objects or non-registered symbols; primitives throw, because a string like "u_1" can be recreated at any time, so it has no lifetime for the entry to follow.

 Map (strong)                         WeakMap (weak key)

 cache ====> key: order  -> value     cache - - -> key: order  -> value
                ^                                     ^
 request done:  |                     request done:   |
 no one else    | still reachable     no one else     | unreachable
 holds it ------+ through the map     holds it        | -> GC frees both

 ====>  strong reference              - - ->  weak reference
في الشمال: الـ Map ماسكة الـ key بـ strong reference، فلما الـ request يخلص ومحدش تاني ماسك الـ order، لسه reachable عن طريق الـ map وبيفضل في الـ memory. في اليمين: الـ WeakMap ماسكاه weak، فلما الـ request يخلص بيبقى unreachable، والـ GC بيلم الـ key والـ value مع بعض. الخط الـ ====> معناه strong reference، والـ - - -> معناه weak reference.

الـ Map ماسكة كل key بـ reference strong، فطول ما الـ map عايشة الـ key مستحيل يتلم. الـ WeakMap ماسكة الـ keys بشكل weak: الـ entry مش سبب إن الـ key يفضل عايش. لما محدش تاني يبقى ماسك الـ key، الـ GC ممكن يلمه والـ entry بتروح معاه. والـ value بيفضل عايش عن طريق الـ key بس، فحتى لو الـ value بيشاور على الـ key نفسه، ده مش بيمسكهم. الشكل ده اسمه ephemeron.

فده بيدّيك 3 استخدامات: metadata على objects مش بتاعتك (request، socket، DOM node)، وcache لحاجة محسوبة لكل object، وprivate data متخزنة بره الـ object (الـ pattern اللي كان قبل #private، ولسه موجود في libraries). والـ WeakSet نفس الفكرة بس للعضوية، زي إنك تعلّم على objects اتزارت قبل كده: في الكود الـ deepCountNodes عدّى من الـ reference الدائرية invoice.self من غير loop لا نهائي.

Interview question "When would you use a WeakMap instead of a Map, and why can't you iterate one?" → When the key's lifetime is owned by someone else and your data should die with it, such as metadata on a request. It can't be iterated because the set of live entries depends on GC timing, so listing them would make program behaviour non-deterministic. It only works with object keys, so it can't replace an id-keyed cache.

Part 6 — WeakRef & FinalizationRegistry 🟡 Intermediateالجزء 6 — الـ WeakRef والـ FinalizationRegistry

English

new WeakRef(obj) holds obj without keeping it alive; ref.deref() returns it, or undefined once it has been collected. new FinalizationRegistry(callback) lets you register an object and a "held value", and the callback may run with that held value some time after the object is collected. Together they can build a cache that gives memory back under pressure. The spec guarantees one thing that matters: an object you just created a WeakRef to, or just deref'd, stays alive until the end of the current job, so two deref() calls in a row can't disagree.

What's not guaranteed: when the callback runs, or whether it runs. It might never run, and it doesn't run at process exit. The GC runs based on memory pressure, not on your schedule. So finalizers are only acceptable for cleaning up bookkeeping that's harmless if it lingers, such as a stale Map entry. Don't use them for logic, and don't use them to close connections, release locks or flush data. Those need try/finally or an explicit close().

import { setTimeout as sleep } from "node:timers/promises";

// الـ cache بيدّي الـ report لو لسه عايش، ومبيمنعش الـ GC يلمّه لما الـ memory تحتاج
class WeakReportCache {
  #refs = new Map<string, WeakRef<Report>>();
  // بيشيل الـ key بعد ما الـ value يموت، عشان الـ Map نفسها متكبرش
  #registry = new FinalizationRegistry<string>((tenantId) => {
    // لازم تتأكد: ممكن يكون حد حط report جديد لنفس الـ key قبل ما الـ finalizer يشتغل
    if (this.#refs.get(tenantId)?.deref() === undefined) this.#refs.delete(tenantId);
    console.log(`  [finalizer] cleaned ${tenantId}`);
  });

  set(tenantId: string, report: Report) {
    this.#refs.set(tenantId, new WeakRef(report));
    this.#registry.register(report, tenantId);
  }
  get(tenantId: string) {
    return this.#refs.get(tenantId)?.deref();
  }
  get size() {
    return this.#refs.size;
  }
}

new WeakRef(obj) بتمسك obj من غير ما تخليه عايش، وref.deref() بترجّعه، أو undefined لو اتلم خلاص. وnew FinalizationRegistry(callback) بتخليك تسجّل object و"held value"، والـ callback ممكن يشتغل بالـ held value ده في وقت ما بعد ما الـ object يتلم. مع بعض ممكن يعملوا cache بيرجّع الـ memory وقت الضغط. والـ spec ضامنة حاجة واحدة مهمة: الـ object اللي لسه عامل له WeakRef، أو لسه عامل له deref، بيفضل عايش لحد آخر الـ job الحالي، فـ 2 deref() ورا بعض مستحيل يختلفوا.

والـ cache لازم يتأكد قبل المسح (deref() === undefined)، لأن ممكن حد يحط report جديد لنفس الـ key قبل ما الـ finalizer بتاع القديم يشتغل، ولو مسحت من غير check هتمسح الجديد.

إيه اللي مش مضمون: إمتى الـ callback يشتغل، وهل هيشتغل أصلًا. ممكن ميشتغلش أبدًا، ومش بيشتغل عند خروج الـ process. والـ GC بيشتغل على حسب ضغط الـ memory، مش على جدولك. فالـ finalizers مقبولة بس لتنضيف bookkeeping مش هيضر لو فضل شوية، زي entry قديمة في Map. متستخدمهاش في logic، ومتستخدمهاش تقفل connections أو تفك locks أو تعمل flush لـ data. دول محتاجين try/finally أو close() صريحة. وعلى Node 22.19 الـ using syntax مش مدعومة لسه (جرّبناها)، فـ try/finally هي الطريق الصح هنا.

فين هستخدمه في شغلي؟ بصراحة: نادرًا جدًا. في backend عادي، cache محتاجه هيبقى LRU أو Redis بحد واضح، لأن الـ WeakRef cache بيفضى لما الـ GC يقرر، فالـ hit rate مش ثابت ومتقدرش تتوقعه. هتقابله في libraries: مثلًا native binding بيفك resource كـ safety net، مع log لو حد نسي يقفل. والمهم إنك في code review لما تشوف FinalizationRegistry بيقفل connection، توقفها: ده pool هيخلص تحت الضغط. نفس الكلام لأي WeakRef شايل منطق business.
What breaks A test that passes locally with --expose-gc says nothing about production. Heap growth patterns, V8 version and memory limits all change when and whether collection happens. Treat a WeakRef as "might be gone at any await", and always handle undefined.
إيه اللي هيكسر: test ناجح عندك بـ --expose-gc مش بيقول حاجة عن الـ production. شكل نمو الـ heap، ونسخة V8، وحدود الـ memory، كلهم بيغيّروا إمتى وهل الـ GC هيلم. اعتبر الـ WeakRef "ممكن يختفي عند أي await"، ودايمًا اتعامل مع undefined.

Part 7 — Typed arrays, ArrayBuffer, DataView 🟡 Intermediateالجزء 7 — الـ typed arrays والـ ArrayBuffer والـ DataView

English

An ArrayBuffer is a fixed-size block of raw bytes. You can't read it directly; you put a view on it. A typed array (Uint8Array, Uint32Array, Float64Array…) reads those bytes as a sequence of one numeric type, using the machine's byte order. Many views can share one buffer, and writing through one is visible through the others. Typed arrays have a fixed length, are zero-initialized, and the type constrains values: Uint8Array wraps on overflow, Uint8ClampedArray saturates, and writing past the end is silently ignored. A multi-byte view must start at a multiple of its element size.

Endianness is the order of a number's bytes in memory. x86 and the ARM servers you'll meet are little-endian (least significant byte first). Network protocols are usually big-endian, and file formats vary (PNG is big-endian, ZIP is little-endian), so read the spec. And never read a wire format with a Uint32Array: its answer depends on the CPU. DataView reads any type at any offset, in the byte order you name. Its default is big-endian, so forgetting the true argument on little-endian data gives a wrong number with no error. Out-of-bounds reads throw RangeError, unlike typed arrays which give undefined.

Parsing a binary event header. Every length, type and magic number in a wire format comes from outside your process, so treat them as untrusted input: check the size before reading, check the magic, and cap any length before you allocate from it. Respect byteOffset too, because the bytes you received are often a window into a larger buffer. 64-bit integers come back as BigInt, since they may not fit in a number.

// الـ layout في الرسمة اللي فوق: 20 byte ثابتين، وكله ⁦big-endian (network order)⁩
const HEADER_SIZE = 20;
const MAGIC = 0x4f45;
const MAX_PAYLOAD = 1024 * 1024;

type EventHeader = { version: number; type: number; tenantId: number; timestamp: Date; payloadLength: number };

function encodeHeader(h: EventHeader): Uint8Array {
  const bytes = new Uint8Array(HEADER_SIZE);
  const view = new DataView(bytes.buffer);
  view.setUint16(0, MAGIC);
  view.setUint8(2, h.version);
  view.setUint8(3, h.type);
  view.setUint32(4, h.tenantId);
  // الـ uint64 أكبر من Number.MAX_SAFE_INTEGER ممكن، فالـ DataView بتطلبه BigInt
  view.setBigUint64(8, BigInt(h.timestamp.getTime()));
  view.setUint32(16, h.payloadLength);
  return bytes;
}

function parseHeader(bytes: Uint8Array): EventHeader {
  // (1) متفترضش حاجة عن الـ input: اللي جاي من الشبكة ممكن يبقى ناقص أو ملعوب فيه
  if (bytes.byteLength < HEADER_SIZE) throw new RangeError(`header too short: ${bytes.byteLength} bytes`);
  // (2) احترم byteOffset: الـ bytes ممكن تكون view في نص buffer أكبر
  const view = new DataView(bytes.buffer, bytes.byteOffset, bytes.byteLength);
  if (view.getUint16(0) !== MAGIC) throw new Error("bad magic: not one of our events");
  const payloadLength = view.getUint32(16);
  // (3) الطول جاي من اللي باعت: من غير حد، 4GB allocation واحدة توقّع الـ process
  if (payloadLength > MAX_PAYLOAD) throw new RangeError(`payload too large: ${payloadLength}`);
  return {
    version: view.getUint8(2),
    type: view.getUint8(3),
    tenantId: view.getUint32(4),
    timestamp: new Date(Number(view.getBigUint64(8))),
    payloadLength,
  };
}

1M prices: Float64Array vs number[]. The common claim is that typed arrays are always far smaller and faster. The measurement is more interesting. V8 already stores an all-doubles array as raw doubles, so a clean number[] is close in both size and read speed. The difference is that a number[] can degrade: one null switches it to tagged pointers, and every price becomes a separate heap object. A Float64Array can't degrade, has no growth slack, and lives off the JS heap, so GC never scans its contents. V8's internals are in lesson 18.

// مليون سعر بأشكال مختلفة: كل شكل في process لوحده عشان الـ heap يبدأ نضيف
import { execFileSync } from "node:child_process";

const N = 1_000_000;
const price = (i: number) => ((i * 7) % 90000) / 100 + 0.5;

const builders: Record<string, () => ArrayLike<unknown>> = {
  // (1) الـ array العادية كلها doubles، متعبية بـ push
  "number[] doubles": () => {
    const a: number[] = [];
    for (let i = 0; i < N; i++) a.push(price(i));
    return a;
  },
  // (2) نفس الأرقام، بس null واحد حوّل الـ array كلها لـ tagged pointers
  "(number|null)[]": () => {
    const a: (number | null)[] = [null];
    for (let i = 1; i < N; i++) a.push(price(i));
    return a;
  },
  // (3) الـ Float64Array: حجم ثابت و bytes خام بره الـ JS heap
  Float64Array: () => {
    const a = new Float64Array(N);
    for (let i = 0; i < N; i++) a[i] = price(i);
    return a;
  },
};

Node's Buffer is a Uint8Array subclass, so all of this applies to it. Its readUInt32BE-style methods are DataView with the endianness in the name. Two traps come straight from the shared-memory model: buf.slice() shares memory (it is deprecated in favour of subarray, which says so clearly), the opposite of Uint8Array.prototype.slice, which copies. And small buffers are carved out of a shared 8 KB pool, so buf.buffer is usually not just your bytes: any view you build on it must pass byteOffset and length. Streams and Buffers get their full treatment in the Node section.

الـ ArrayBuffer حتة ثابتة الحجم من bytes خام. مبتقراهاش مباشرة، بتحط فوقها view. الـ typed array (Uint8Array وUint32Array وFloat64Array…) بيقرا الـ bytes دي كسلسلة من نوع رقمي واحد، بترتيب الـ bytes بتاع الجهاز. وممكن كذا view يشتركوا في buffer واحد، والكتابة من واحد بتبان من الباقيين. والـ typed arrays طولها ثابت، وبتبدأ أصفار، والنوع بيحكم القيمة: Uint8Array بتلف عند الـ overflow (250 + 10 طلعت 4)، وUint8ClampedArray بتقف عند الحد (255)، والكتابة بعد الآخر بتتجاهل في صمت. والـ view متعدد الـ bytes لازم يبدأ من مضاعف لحجم العنصر. وsubarray بتشارك الـ memory وslice بتنسخ.

الـ endianness هو ترتيب bytes الرقم في الـ memory. الـ x86 والـ ARM servers اللي هتقابلها little-endian (أصغر byte الأول). والـ network protocols غالبًا big-endian، والـ file formats بتختلف (PNG big-endian و ZIP little-endian)، فاقرا الـ spec. ومتقراش wire format بـ Uint32Array أبدًا: الإجابة هتعتمد على الـ CPU. الـ DataView بيقرا أي نوع من أي offset بالترتيب اللي تحدده. والـ default بتاعه big-endian، فلو نسيت الـ true على data بـ little-endian هتاخد رقم غلط من غير أي error. والقراية بره الحدود بتضرب RangeError، عكس الـ typed arrays اللي بترجّع undefined.

الـ binary header: كل طول ونوع وmagic number في wire format جاي من بره الـ process، فاعتبرهم input مش موثوق: اتأكد من الحجم قبل ما تقرا، واتأكد من الـ magic، وحط حد لأي طول قبل ما تعمل allocation على أساسه. واحترم byteOffset كمان، لأن الـ bytes اللي استلمتها غالبًا شباك في buffer أكبر. والـ integers اللي 64-bit بترجع BigInt لأنها ممكن متدخلش في number.

مليون سعر: Float64Array ولا number[]؟ الكلام الشائع إن الـ typed arrays دايمًا أصغر وأسرع بكتير. القياس بيقول حاجة أحلى. V8 أصلًا بيخزن الـ array اللي كلها doubles كـ doubles خام، فالـ number[] النضيفة قريبة جدًا في الحجم وسرعة القراية. الفرق إن number[] ممكن تبوظ: null واحد بيحوّلها لـ tagged pointers، وكل سعر بيبقى object لوحده على الـ heap. أما Float64Array مستحيل تبوظ، ومفيهاش مساحة نمو زيادة، وعايشة بره الـ JS heap، فالـ GC مش بيلف على محتواها. تفاصيل V8 في درس 18.

الـ Buffer بتاع Node هو subclass من Uint8Array، فكل ده بينطبق عليه. والـ methods زي readUInt32BE هي DataView بس الـ endianness في الاسم. وفخّين جايين مباشرة من فكرة الـ memory المشتركة: buf.slice() بتشارك الـ memory (وهي deprecated لصالح subarray اللي اسمها واضح)، عكس Uint8Array.prototype.slice اللي بتنسخ. والـ buffers الصغيرة بتتقطع من pool مشترك 8 KB، فـ buf.buffer غالبًا مش الـ bytes بتاعتك بس: أي view تعمله عليه لازم تدّيله byteOffset وlength. تفاصيل الـ streams والـ Buffers في قسم Node.

فين هستخدمه في شغلي؟ لما تقرا magic bytes بتاعة ملف مرفوع عشان تتأكد إنه PDF فعلًا مش بس الـ extension، أو تتعامل مع binary protocol زي Kafka أو MQTT، أو WebSocket frames بـ custom format، أو crypto.randomBytes وcrypto.subtle. وفي الأرقام: عندك 5 مليون price point في الـ memory لـ pricing engine: Float64Array بتشيل الضغط من الـ GC وبتتنقل لـ worker thread بـ transfer من غير نسخ. لكن لـ 100 order في response عادي، number[] وArray عادية هي الصح. وفي الـ code review: new DataView(chunk.buffer) من غير offset على Node Buffer ده bug أكيد.
Trade-off: when typed arrays earn their place Use them for binary formats (always), and for large numeric data that lives long enough for GC pressure to matter or that moves between threads. Don't use them for ordinary lists: they can't hold null for a missing value, can't grow, and throw away array ergonomics such as push. For missing values you'd need a sentinel like NaN, which is one more thing to get wrong.
الـ trade-off: إمتى الـ typed arrays تستاهل. استخدمها للـ binary formats دايمًا، وللـ data الرقمية الكبيرة اللي بتعيش كفاية إن ضغط الـ GC يفرق، أو اللي بتتنقل بين threads. متستخدمهاش للـ lists العادية: مش بتشيل null لقيمة ناقصة، ومبتكبرش، وبتخسّرك حاجات زي push. وللقيم الناقصة هتحتاج قيمة مخصوصة زي NaN، ودي حاجة زيادة ممكن تغلط فيها.

Solution · الحل 
function memoizeByObject<K extends object, V>(compute: (key: K) => V) {
  const cache = new WeakMap<K, V>();
  const stats = { hits: 0, misses: 0 };
  const memoized = (key: K): V => {
    // الـ has مش الـ get، عشان undefined تبقى نتيجة صالحة تتخزن
    if (cache.has(key)) {
      stats.hits++;
      return cache.get(key)!;
    }
    stats.misses++;
    const value = compute(key);
    cache.set(key, value);
    return value;
  };
  return Object.assign(memoized, { stats });
}

  });
  return {
    text: `INSERT INTO orders (id, user_id, total) VALUES ${placeholders.join(", ")}`,
    values: batch.flatMap((row) => [row.id, row.userId, row.total]),
  };
}

function* readCsvRows(count: number): Generator<Row> {
  for (let i = 1; i <= count; i++) yield { id: i, userId: i % 10, total: i * 5 };
}

const sample = buildInsert([...readCsvRows(2)]);
console.log(sample.text);
// → INSERT INTO orders (id, user_id, total) VALUES ($1, $2, $3), ($4, $5, $6)
console.log(sample.values);
// → [ 1, 1, 5, 2, 2, 10 ]

let batches = 0;
let rows = 0;
let maxParams = 0;
for (const batch of chunk(readCsvRows(1_000_000), 1_000)) {
  const query = buildInsert(batch);
  // هنا: ⁦await pool.query(query)⁩؛ الـ await هو الـ backpressure، مفيش row جديد قبل ما الـ insert يخلص
  batches++;
  rows += batch.length;
  maxParams = Math.max(maxParams, query.values.length);
}
console.log({ batches, rows, maxParams, underLimit: maxParams <= MAX_PARAMS });
// → { batches: 1000, rows: 1000000, maxParams: 3000, underLimit: true }
الـ query builder ده اشتغل على مليون row من غير داتابيز: 1000 batch، وبحد أقصى 3000 parameter في الـ query. غيّر الـ comment بـ await pool.query(query)، وقتها لازم الـ loop يبقى جوه async function.

Cheat sheet · الخلاصة

  • toSorted, toReversed, toSpliced, with copy the array shallowly. Use them on anything shared.
  • flatMap filters and expands in one pass. at(-1) works; arr[-1] doesn't. Object.groupBy before a hand-written reduce.
  • Never {...acc} in a reduce that can grow: it's O(n²). Mutate the local accumulator, or use Object.fromEntries or a Map.
  • Iterable = [Symbol.iterator](), re-walkable. Iterator = next(), one cursor. return() runs on early exit only.
  • Generators are lazy, pull-based and single-use. finally runs on break and return(), but not if the generator never started.
  • chunk() over a generator keeps bulk jobs at constant memory, and the await gives you backpressure. Iterator helpers work on Node 22 (TS: es2025).
  • Object for records, Map for dictionaries. JSON.stringify(map) is {}. Object keys compare by reference.
  • Set methods need a set-like argument (a Map works, an array throws). isSubsetOf and difference are your permission checks.
  • WeakMap: keyed by objects, entry dies with the key, not iterable because GC timing would show. It's not a cache for ids.
  • WeakRef/FinalizationRegistry: finalizers may never run. Don't use them for logic or for closing anything; use try/finally.
  • Typed arrays are views on one ArrayBuffer. DataView for wire formats, and its default is big-endian. Validate lengths from the wire.
  • Buffer is a Uint8Array in a shared pool: always pass byteOffset and length. A clean number[] is fine until one null turns it into 2.5× the memory.
بالعامية
  • toSorted وtoReversed وtoSpliced وwith بينسخوا الـ array نسخة shallow. استخدمهم على أي حاجة مشتركة.
  • flatMap بتفلتر وتوسّع في pass واحد. at(-1) شغالة وarr[-1] لأ. جرّب Object.groupBy قبل ما تكتب reduce بإيدك.
  • أوعى {...acc} جوه reduce ممكن تكبر: ده O(n²). عدّل في الـ acc المحلي، أو استخدم Object.fromEntries أو Map.
  • الـ iterable = [Symbol.iterator]() وتلف عليه كذا مرة. الـ iterator = next() وهو cursor واحد. وreturn() بتشتغل عند الخروج البدري بس.
  • الـ generators كسولة، و pull-based، وبتنفع مرة واحدة. الـ finally بتشتغل مع break وreturn()، بس مش لو الـ generator مبدأش أصلًا.
  • chunk() فوق generator بتخلي الـ bulk jobs بـ memory ثابتة، والـ await بيدّيك الـ backpressure. والـ iterator helpers شغالة في Node 22 (في TS محتاج es2025).
  • الـ object للـ records، والـ Map للـ dictionaries. JSON.stringify(map) بتطلّع {}. والـ object keys بتتقارن بالـ reference.
  • الـ Set methods محتاجة argument set-like (الـ Map بتعدّي والـ array بتضرب). isSubsetOf وdifference هما الـ permission checks بتوعك.
  • الـ WeakMap: الـ keys objects، والـ entry بتموت مع الـ key، ومش iterable عشان توقيت الـ GC ميبانش. ومش cache للـ ids.
  • الـ WeakRef والـ FinalizationRegistry: الـ finalizers ممكن متشتغلش أبدًا. متستخدمهمش في logic ولا في قفل أي حاجة؛ استخدم try/finally.
