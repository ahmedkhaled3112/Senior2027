Why this matters · ليه ده مهم

English

Everything you build in JavaScript is functions holding on to state: an Express middleware factory, a React hook, a retry wrapper, a cache in front of a tax API. Most of the "impossible" bugs come from this lesson's mechanics: a React effect that keeps saving yesterday's cart, an error handler Express silently ignores because of one default parameter, a query with no limit because null skipped a default, a 5 MB request body kept alive by a one-line callback. "What does a closure capture?" and "why does this loop print 3, 3, 3?" are also two of the most common JavaScript interview questions, and the follow-ups go straight to memory and scope.

بالعامية

كل اللي بتبنيه في JavaScript في الآخر functions ماسكة state: middleware factory في Express، hook في React، retry wrapper، cache قدام tax API. وأغلب الـ bugs اللي شكلها "مستحيل" جاية من اللي في الدرس ده: effect في React فضل يحفظ cart قديم، error handler الـ Express بيتجاهله بسبب default parameter واحد، query من غير limit عشان null عدّى من الـ default، و request body حجمه 5 MB فضل عايش بسبب callback من سطر واحد. وكمان "الـ closure بتمسك إيه؟" و"ليه الـ loop دي بتطبع 3، 3، 3؟" من أشهر أسئلة الـ JavaScript في الـ interviews، والأسئلة اللي بعدهم بتدخل على طول في الـ memory والـ scope.

Part 1 — Declaration vs expression vs arrow 🟢 Basicالجزء 1 — الـ declaration والـ expression والـ arrow

English

JavaScript has three everyday ways to make a function, and they differ in two independent ways: when the name becomes usable and what the function brings with it.

When the name is usable. Before any statement in a scope runs, the engine registers the scope's declarations. A function declaration is bound and initialized with its body right then, so you can call it above the line where it is written. A const or let holding a function expression exists but stays uninitialized until its line runs (the TDZ from lesson 01), so an early call throws ReferenceError. A var is initialized to undefined, so an early call throws TypeError: … is not a function. In strict mode, a declaration inside a block is scoped to that block.

What it brings. A regular function has its own this, arguments, new.target and prototype, and it can be called with new. An arrow function has none of these: this and arguments are resolved from the enclosing scope, it has no [[Construct]] internal method, so new throws, and it cannot be a generator.

Names. A function assigned directly to a binding gets an inferred .name, and that name is what shows up in stack traces. An inline callback has no name, so its stack frame has only a file and a line. A named function expression (const retry = function attempt() {}) exposes its name only inside itself, which is handy for recursion.

English

In a real service file, the choice is mostly about readability. Use declarations for the file's named functions: hoisting lets you put the public API on top and the helpers below, and every frame in a stack trace has a name. Use arrows for short inline callbacks. The trap to remember: hoisting moves the function, not the const it reads, and the compiler can't see that across a function boundary.

بالعامية

عندك 3 طرق تعمل بيها function، والفرق بينهم في حاجتين منفصلين: الاسم بيبقى جاهز إمتى، والـ function جايبة معاها إيه.

الاسم جاهز إمتى؟ قبل ما أي سطر في الـ scope يتنفذ، الـ engine بيسجّل الـ declarations بتاعته. الـ function declaration بتتربط وتتجهز بالـ body بتاعها في اللحظة دي، فتقدر تناديها فوق السطر اللي مكتوبة فيه. الـ const أو let اللي شايل function expression موجود، بس فاضل مش جاهز لحد ما سطره يتنفذ (ده الـ TDZ من درس 01)، فلو ناديته بدري هيرمي ReferenceError. أما الـ var فبيبدأ بـ undefined، فالـ call بدري بيرمي TypeError: … is not a function. وفي الـ strict mode، الـ declaration اللي جوه block بتفضل جوه الـ block ده بس.

جايبة معاها إيه؟ الـ regular function ليها this وarguments وnew.target وprototype خاصين بيها، وتقدر تناديها بـ new. الـ arrow مفيهاش أي حاجة من دول: الـ this والـ arguments بتجيبهم من الـ scope اللي حواليها، ومالهاش [[Construct]] فالـ new بيرمي error، وماينفعش تبقى generator.

الأسماء. الـ function اللي بتتحط مباشرة في binding بتاخد .name من اسمه، وده اللي بيظهر في الـ stack trace. إنما الـ inline callback مالهاش اسم، فالـ frame بتاعها فيه ملف وسطر بس: بص في الـ output، at chargeCard (…) قدام at function-forms.ts:75:9. والـ named function expression زي const retry = function attempt() {} اسمها ظاهر جواها هي بس، وده مفيد في الـ recursion.

كل الأمثلة في الدرس ده ES modules ("type": "module" في package.json) بتتشغّل على طول بـ node file.ts على Node 22، يعني strict mode دايمًا. خد بالك من النقطة دي، لأن في درس 04 هتشوف نفس الكود بيتصرف بشكل مختلف في الـ sloppy mode.

في service file حقيقي الاختيار معظمه قراءة: استخدم declarations للـ functions اللي ليها اسم في الملف، عشان الـ hoisting يخليك تحط الـ public API فوق والـ helpers تحت، وكل frame في الـ stack trace يبقى ليه اسم. واستخدم arrow للـ callbacks القصيرة. والفخ اللي لازم تفتكره: الـ hoisting بيرفع الـ function، مش الـ const اللي هي بتقراه، والـ compiler مش شايف ده لما الاستخدام يبقى جوه function تانية. وده اللي حصل مع VAT_PERCENT في المثال.

فين هستخدمه في شغلي؟ افتح أي order.service.ts: placeOrder فوق، وsumItems وwithVat تحت كـ declarations، فاللي بيقرا الملف بيشوف الـ flow الأول والتفاصيل بعدين. ولما production يطلّع stack فيه at chargeCard بتعرف المشكلة فين في ثانية، إنما frames من غير اسم بتضيّع وقتك. وأشهر crash وقت الـ boot: const defaults = createDefaults() فوق const VAT_PERCENT = 14، الـ compile بيعدّي عادي والـ service بتقع وهي بتقوم بـ Cannot access 'VAT_PERCENT' before initialization. الحل: ثوابت الملف فوق خالص، والحاجات اللي بتتنفذ وقت الـ load تحتها.
Interview question "What's the difference between an arrow function and a regular function?" → Not just syntax. Arrows have no own this or arguments (both are lexical), no prototype, can't be called with new, and can't be generators. Use them for callbacks; don't use them as object methods that need the object as this.
"إيه الفرق بين الـ arrow والـ regular function؟" ← مش الشكل بس. الـ arrow مالهاش this ولا arguments خاصين بيها (الاتنين lexical)، ومالهاش prototype، وماينفعش تتنادى بـ new، وماينفعش تبقى generator. استخدمها في الـ callbacks، ومتستخدمهاش كـ method على object محتاج الـ this يبقى هو الـ object.

Part 2 — Parameters & return values 🟢 Basicالجزء 2 — الـ parameters والـ return values

English

Defaults. A default initializer is evaluated at call time, on every call that needs it, not once at definition like in Python. So lines = [] gives each call a fresh array, and number = nextInvoiceNumber() runs each time. A default may read parameters to its left; reading one to its right hits the TDZ. Most importantly, a default fires only for undefined. null, 0 and '' pass straight through, and JSON bodies and database rows are full of null. If the value comes from outside, use ?? in the body instead.

Rest and arity. ...parts collects the remaining arguments into a real array, and it must be the last parameter. JavaScript never checks argument counts at runtime: extras are ignored and missing ones are undefined. That's why ["10","10","10"].map(parseInt) gives [10, NaN, 2]: map passes (value, index, array), so the index becomes the radix, and TypeScript accepts it because the signature is compatible. fn.length counts parameters only up to the first default or rest. That sounds like trivia until you learn that Express decides whether a function is an error handler by checking fn.length === 4 (router/lib/layer.js).

Options objects. Past two or three parameters, positional arguments stop being readable and start being dangerous: (…, true, null, 30) says nothing, and two swapped values of the same type still compile. A destructured options object names every value at the call site, keeps defaults in one place, and adding an optional field doesn't touch existing callers. Destructuring undefined throws, so give the whole object a default (= {}) when all options are optional. That default doesn't cover null either.

Return values. A function without a return, or with a bare return;, returns undefined. Four classic forms: a block-bodied arrow in map without return; () => { id: 1 }, where the braces are a block and id: is a label, so you need () => ({ id: 1 }); a newline right after return, where automatic semicolon insertion ends the statement; and the costly one, a function that calls something async but doesn't return the promise, so the caller's await finishes immediately while the work is still running (more in lesson 09).

What breaks in production: LIMIT NULL In Postgres, LIMIT with a NULL argument is the same as no LIMIT at all. A client sends {"limit": null}, the default doesn't fire, the driver binds null, and an endpoint that normally returns 20 rows reads the whole orders table. Treat every external value with ?? and clamp it.

English

First-class functions. In JavaScript a function is an ordinary value: store it in a variable or an object, pass it as an argument, return it from another function. A callback is a function you hand to someone else to call for you, either right now (map, sort) or later (setTimeout, an event listener). A higher-order function (HOF) takes a function, returns a function, or both.

Two patterns pay off every week. A handlers map replaces a long switch on an event type with a lookup. A wrapper like withLogging(fn) adds behaviour around a function without touching it, and generics keep the original signature, so a wrong argument is still a compile error. The handlers map has a trap: a plain object inherits from Object.prototype, so a type string from a webhook such as "constructor" finds a real function. It passes your if (!handler) check and gets called. Use a Map or Object.hasOwn for keys you don't control.

Scope and the lexical environment. Scope answers "which variable does this name refer to?". JavaScript has global, module, function and block scope. At runtime, each function call and each block entry creates a lexical environment: a record of the names declared there, plus a reference to the outer environment. A lookup starts in the current environment and walks outward along those references until it finds the name; if it reaches the end, you get a ReferenceError. Lookups never go inward.

The chain is fixed by where the function is written, not by who calls it. That is what "lexical" means: formatPrice prints EGP even when called from a function with its own currency = "USD". A name declared in an inner scope shadows the outer one only inside that scope.

English

Every function object carries an internal slot, [[Environment]], set when the function is created and pointing at the lexical environment where it was defined. When you call the function, the new environment's outer is that slot. A closure is simply this pair: a function plus the environment it remembers. So when createCheckout returned in Part 3, its environment didn't die, because priceLine still references it.

Three consequences to burn in. (1) It captures the variable, not a copy of the value: change vatPercent later and the closure sees the new value. Private state. A closure gives you data no outside code can reach: createCart has no items property to touch, and JSON.stringify sees nothing. All writes go through add, which can validate. Return copies from readers; handing back the internal array would undo the privacy.

function memoize<A extends unknown[], R>(
  fn: (...args: A) => R,
  keyOf: (...args: A) => string = (...args) => JSON.stringify(args),
): (...args: A) => R {
  // الـ cache عايش في الـ closure، وكل memoized function ليها cache لوحدها
  const cache = new Map<string, R>();
  return (...args) => {
    const key = keyOf(...args);
    if (cache.has(key)) return cache.get(key)!;
    const result = fn(...args);
    cache.set(key, result);
    return result;
  };
}

function memoizeAsync<A extends unknown[], R>(
  fn: (...args: A) => Promise<R>,
  keyOf: (...args: A) => string = (...args) => JSON.stringify(args),
): (...args: A) => Promise<R> {
  const cache = new Map<string, Promise<R>>();
  return (...args) => {
    const key = keyOf(...args);
    const hit = cache.get(key);
    if (hit) return hit;
    const pending = fn(...args);
    pending.catch(() => cache.delete(key));
    cache.set(key, pending);
    return pending;
  };
}

function once<A extends unknown[], R>(fn: (...args: A) => R): (...args: A) => R {
  let target: ((...args: A) => R) | null = fn;
  let result: R;
  return (...args) => {
    if (target) {
      const run = target;
      // بنصفّر قبل الـ call: لو fn نادت نفسها مش هتتنفذ مرتين، والـ GC يقدر يلم fn
      target = null;
      result = run(...args);
    }
    return result;
  };
}

The memory a closure keeps alive. On paper, an environment holds all its variables. V8 is smarter: during parsing it finds which variables are used by inner functions and moves only those into a heap-allocated Context; the rest stay on the stack and die with the call. The catch is that all closures created in one scope share one Context. So a variable read by any of them lives as long as any of them lives. In variant C below, the returned function never touches rows, but its sibling countPaid does, and rows stays on the heap. The fix is to do big work in a separate function and let the closure capture only the small result. Hunting leaks like this with heap snapshots is lesson 18.

// شغّله: node --expose-gc src/closure-memory.ts
type Row = { id: number; total: number };

function loadRows(): Row[] {
  return Array.from({ length: 1_000_000 }, (_, id) => ({ id, total: id * 2 }));
}

function heapMB() {
  globalThis.gc!();
  return Math.round(process.memoryUsage().heapUsed / 1e6);
}

// النسخة A: الـ closure مش بتقرا rows: الـ V8 بيخلي rows على الـ stack والـ GC بيلمها
function summaryA() {
  const rows = loadRows();
  const count = rows.length;
  return () => count;
}

// النسخة B: الـ closure بتقرا rows: طبيعي تفضل عايشة طول ما الـ closure عايشة
function summaryB() {
  const rows = loadRows();
  return () => rows.length;
}

// النسخة C، وهي الفخ: الـ closure الراجعة مش بتقرا rows، بس أختها بتقراها، والاتنين بيشاركوا context واحد
function summaryC() {
  const rows = loadRows();
  const countPaid = () => rows.filter((row) => row.total % 2 === 0).length;
  const paid = countPaid();
  return () => paid;
}

  const after = heapMB();

Part 5 — The classic closure bug 🟡 Intermediateالجزء 5 — الـ closure bug الكلاسيكي

English

A for (var i …) loop creates one binding for the whole function. Every callback closes over that same variable, and the loop finishes synchronously before any timer can fire, so all of them read the final value: 3, and channels[3] is undefined. It's rule (1) from Part 4 in action: closures capture the variable, not the value.

for (let j …) is different because the spec creates a new binding for every iteration and copies the current value into it before the increment. Each closure gets its own j, which the bumps example proves: each closure increments only its own copy, and the output is 1 2 2. The behaviour comes from where the binding is declared, not from the word let: declare let k outside the loop and you are back to one shared variable. for...of and for...in also create a fresh binding each iteration. Before ES2015, people used an IIFE to create a new scope per iteration.

TypeScript doesn't catch this, because the code is valid. ESLint does: no-var and no-loop-func.

English

Each React render is a function call, so seconds in render 1 and seconds in render 2 are different bindings, like iterations of a let loop. An effect with [] runs once, so its callback closes over render 1's variables forever. The timer keeps running and keeps seeing the first value. seconds + 1 is always 1, and the autosave below keeps sending the first cart to the server even after the user changed it. The output is from real Chrome, with the cart changing from 1 item to 5 items at 350 ms.

Three fixes, in the order to try them: use the updater form (setSeconds((current) => current + 1)) when the new state depends only on the old state; add the value to the dependency array when restarting the effect is fine; use useEffectEvent (stable since React 19.2) when you need the latest props inside a long-lived effect without restarting it. The react-hooks/exhaustive-deps lint rule warns about the bug. Don't silence it without thinking.

// الـ components دي اتشغّلت في Chrome حقيقي بـ React 19.3
import { useEffect, useEffectEvent, useState } from "react";

// ❌ الـ effect اشتغل مرة واحدة، فالـ closure ماسكة seconds بتاع أول render: يعني 0 للأبد
export function StaleCounter() {
  const [seconds, setSeconds] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setSeconds(seconds + 1), 100);
    return () => clearInterval(id);
  }, []);
  return <output id="stale">{seconds}</output>;
}

// ✅ الـ updater form: الـ React بيدّيك القيمة الحالية، فمش محتاج تقرا من الـ closure
export function FreshCounter() {
  const [seconds, setSeconds] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setSeconds((current) => current + 1), 100);
    return () => clearInterval(id);
  }, []);
  return <output id="fresh">{seconds}</output>;
}

Part 6 — IIFE & the arguments object 🟡 Intermediateالجزء 6 — الـ IIFE والـ arguments object

English

IIFE (Immediately Invoked Function Expression): define a function and call it on the spot. The surrounding parentheses are required, because a line starting with function is parsed as a declaration, not an expression. Before modules, every <script> shared one global scope and var only had function scope, so an IIFE was the only way to get private variables. The module pattern returned a small public API from one, and whole libraries were written that way.

Native modules made that use obsolete: each file now has its own scope. You still meet IIFEs in three places. Bundler output: esbuild --format=iife wraps your whole app in one so nothing leaks to window. Async main in CommonJS: CJS has no top-level await, so (async () => { … })().catch(…) is the entry point in many older workers. In ESM, just use top-level await (lesson 09). Initializing a const that needs statements such as if or try; a named function usually reads better once it passes a few lines. In code without semicolons, a line starting with ( gets parsed as a call on the previous line, which is why you sometimes see ;(async () => ….

arguments is an array-like object (length and indexes, no array methods, Array.isArray is false) that exists inside every non-arrow function, holding all the passed values. Arrows don't have one: the name resolves lexically like this, to the enclosing function's arguments, or to a ReferenceError at the top of an ES module. (In a CommonJS file the top level is really a function, so you get the module wrapper's 5 arguments.)

Why not use it. The parameters are invisible in the signature, so TypeScript rejects the call; you must convert it before using array methods; and in sloppy mode, it is linked to the named parameters, so writing to one changes the other. Rest parameters are a real array, typed, and visible. You'll see arguments only in old libraries and code like fn.apply(this, arguments). ESLint's prefer-rest-params flags it, with one exception: a plain arguments.length is allowed.

الـ IIFE (Immediately Invoked Function Expression): تعرّف function وتناديها في نفس اللحظة. والقوسين اللي حواليها لازم، لأن السطر اللي بيبدأ بـ function بيتقري declaration مش expression. قبل الـ modules، كل <script> كانوا شايلين global scope واحد، والـ var ليه function scope بس، فالـ IIFE كانت الطريقة الوحيدة تعمل private variables. والـ module pattern كان بيرجّع API عام صغير منها، ومكتبات كاملة اتكتبت كده.

الـ modules خلّت الاستخدام ده قديم، لأن كل ملف بقى ليه scope لوحده. بس لسه هتقابلها في 3 أماكن. الـ bundler output: esbuild --format=iife بيلف الـ app كله في واحدة عشان محدش يتسرب لـ window. الـ async main في CommonJS: الـ CJS مفيهوش top-level await، فـ (async () => { … })().catch(…) هي نقطة البداية في workers قديمة كتير. في ESM استخدم top-level await على طول (درس 09). تجهيز const محتاج statements زي if أو try؛ بس لو عدّت كام سطر، function باسم بتتقري أحسن. وفي الكود اللي من غير semicolons، السطر اللي بيبدأ بـ ( بيتقري كأنه call على السطر اللي قبله، وعشان كده ساعات بتشوف ;(async () => ….

الـ arguments object شبه array (فيه length و indexes، ومفيهوش array methods، وArray.isArray بترجّع false)، موجود جوه كل function مش arrow وفيه كل القيم اللي اتبعتت. الـ arrow مفيهاش واحد خاص بيها: الاسم بيتحل lexically زي this، يعني بتقرا arguments بتاع الـ function اللي حواليها (في المثال طلع 1 مش 3)، أو ReferenceError في أعلى ES module. (في ملف CommonJS المستوى الأعلى function في الحقيقة، فهتلاقي الـ 5 arguments بتوع الـ module wrapper.)

ليه متستخدموش؟ الـ parameters مش باينة في الـ signature فالـ TypeScript بيرفض الـ call؛ ولازم تحوّله قبل ما تستخدم array methods؛ وفي الـ sloppy mode مربوط بالـ parameters اللي ليها اسم، فالكتابة في واحد بتغيّر التاني (في المثال sloppy رجّعت refunded وstrict رجّعت paid). الـ rest array حقيقية ومتايبة وباينة. هتشوف arguments بس في مكتبات قديمة وفي كود زي fn.apply(this, arguments)، وprefer-rest-params في ESLint بتمسكه، ماعدا استثناء واحد: arguments.length لوحدها مسموحة.

فين هستخدمه في شغلي؟ لما تفتح dist/bundle.js وتدوّر على error، أول سطر (() => { ده هو الـ IIFE بتاع الـ bundler، مش حاجة غريبة. وفي repo قديم فيه worker بـ CommonJS: (async () => { … })().catch(…) هي الـ main، ومن غير الـ catch أي error هيبقى unhandled rejection والـ worker هيقع. وفي الـ migration لـ ESM شيلها واكتب top-level await. ولو شفت arguments في PR جديد اطلب تتغير لـ rest، ولو كانت جوه wrapper قديم فاعرف إنها بتفضل تشتغل بس TypeScript مش شايفها.

// شغّله: node src/ex2.ts
import assert from "node:assert/strict";

type TtlOptions = { ttlMs: number; maxSize?: number; now?: () => number };

function memoizeWithTtl<A extends unknown[], R>(
  fn: (...args: A) => R,
  { ttlMs, maxSize = 1000, now = Date.now }: TtlOptions,
): (...args: A) => R {
  const cache = new Map<string, { value: R; expiresAt: number }>();
  return (...args) => {
    const key = JSON.stringify(args);
    const hit = cache.get(key);
    if (hit && hit.expiresAt > now()) return hit.value;
    cache.delete(key);
    const value = fn(...args);
    // الـ Map بتحفظ ترتيب الإدخال، فأول key هو الأقدم
    if (cache.size >= maxSize) cache.delete(cache.keys().next().value!);
    cache.set(key, { value, expiresAt: now() + ttlMs });
    return value;
  };
}

// شغّله: node src/ex3.ts
import assert from "node:assert/strict";

function onceUntilSuccess<A extends unknown[], R>(
  fn: (...args: A) => Promise<R>,
): (...args: A) => Promise<R> {
  let pending: Promise<R> | null = null;
  return (...args) => {
    if (pending) return pending;
    pending = fn(...args);
    // الفشل بس هو اللي بيفتح الباب تاني. النجاح بيفضل متخزن للأبد
    pending.catch(() => {
      pending = null;
    });
    return pending;
  };
}

  attempts++;
  if (attempts === 1) throw new Error("gateway timeout");
  return `paid:${orderId}`;

Cheat sheet · الخلاصة

  • Declarations are hoisted with their body; const expressions hit the TDZ; var expressions are undefined. Hoisting moves the function, not the const it reads.
  • Arrows: no own this / arguments / prototype, no new, no generators. Good for callbacks, bad as object methods.
  • Defaults run per call and only for undefined. External values: x ?? fallback, then clamp. LIMIT NULL in Postgres means no limit.
  • fn.length stops at the first default or rest. Express needs exactly 4 for an error handler.
  • Over 2–3 parameters or any boolean flag: destructured options object, with = {} if all are optional.
  • Implicit undefined: block body without return, () => ({}) needs parentheses, newline after return, forgotten promise. Enable noImplicitReturns.
  • Scope chain: environment record plus outer reference, fixed by where the code is written. Walks outward only.
  • A closure is a function plus its environment. It captures the variable, not the value. Each call gets a new environment; closures from one call share it.
  • In V8, closures from one scope share one Context, so a variable read by any of them lives as long as any of them does. Capture small values.
  • memoize: cache the promise, delete on rejection, bound the size, add a TTL. once: a UI or process guard, not idempotency.
  • var in a loop means one binding; let or for...of means one per iteration. A stale useEffect closure is the same mechanism: updater form, deps, or useEffectEvent.
  • IIFE: bundler output, CJS async main, computing a const. arguments: legacy; use rest.
بالعامية
  • الـ declarations بتتعملها hoist بالـ body؛ الـ const expressions بتخبط في الـ TDZ؛ الـ var expressions بـ undefined. والـ hoisting بيرفع الـ function، مش الـ const اللي بتقراه.
  • الـ arrow: مفيهاش this ولا arguments ولا prototype خاصين بيها، ولا new، ولا generators. حلوة للـ callbacks، ووحشة كـ object methods.
  • الـ defaults بتشتغل مع كل call ومع undefined بس. القيم اللي من بره: x ?? fallback وبعدين حط سقف. وLIMIT NULL في Postgres معناها مفيش limit.
  • الـ fn.length بيقف عند أول default أو rest. والـ Express محتاج 4 بالظبط عشان الـ error handler.
  • أكتر من 2–3 parameters أو أي boolean flag: destructured options object، ومعاه = {} لو كلها اختيارية.
  • الـ undefined الضمني: block body من غير return، و() => ({}) محتاجة قوسين، وسطر جديد بعد return، وpromise منسية. وشغّل noImplicitReturns.
  • الـ scope chain: environment record ومعاه reference للي برّاه، متحددين من مكان كتابة الكود، والدوّرة لبره بس.
  • الـ closure هي function ومعاها الـ environment بتاعها. بتمسك الـ variable مش القيمة. كل call ليها environment جديد، والـ closures اللي من نفس الـ call بتشاركه.
  • في V8، الـ closures اللي من نفس الـ scope بتشارك Context واحد، فأي variable قرته واحدة منهم بيفضل عايش طول ما أي واحدة عايشة. امسك قيم صغيرة.
  • memoize: خزّن الـ promise، امسحها لو فشلت، حط حد للحجم، وضيف TTL. وonce: حماية للـ UI أو الـ process، مش idempotency.
  • var في loop يعني binding واحد؛ let أو for...of يعني واحد لكل لفة. والـ stale closure في useEffect نفس الآلية: updater form أو deps أو useEffectEvent.
  • الـ IIFE: في الـ bundler output، والـ async main في CJS، وحساب const. وarguments: حاجة قديمة، استخدم rest.
