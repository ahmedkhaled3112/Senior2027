Why this matters · ليه ده مهم

English

Everything fails eventually, so the useful questions are how long you are down and how much data you lose. Those two numbers, RTO and RPO, drive every decision in this lesson, and each has a price. A senior engineer can say "payments need RPO 0 within a region, which costs a round trip per commit, and here is what we measured". This lesson builds that habit: real Postgres failovers, real restores, and a drill script that prints the numbers instead of assuming them.

بالعامية

كل حاجة بتقع في الآخر، فالسؤال المفيد هو هتفضل واقع قد إيه وهتخسر data قد إيه. الرقمين دول، الـ RTO والـ RPO، بيحركوا كل قرار في الدرس ده، وكل واحد ليه تمن. الـ senior يقدر يقول "الـ payments محتاجة RPO صفر جوه الـ region، وده بيكلّف round trip على كل commit، وده اللي قسناه". الدرس بيبني العادة دي: failovers حقيقية على Postgres، و restores حقيقية، و drill script بيطبع الأرقام بدل ما نفترضها.

Part 1 — Active-passive vs active-active 🟡 Intermediateالجزء 1 — الـ active-passive والـ active-active

English

Active-passive keeps a standby that takes no traffic until it is promoted. Active-active serves from every site at once. Failover time is never just the promotion: it is detection + promotion + client reconnect. On real Postgres 18, with three 500 ms probes, detection took about 1.5 s, pg_promote about 0.14 s and the first write on the new primary about 25 ms, so ≈1.7 s in total. Detection dominates, and that number is a setting you chose. Production values are usually far larger, because a low threshold causes false failovers (Part 3). Replication details are in lesson 12.

For stateless services, active-active is the easy choice. In the stand-in below, one of two sites dies mid-run. With a 1 s health check and no retry, 13.6% of requests failed during the gap before the router noticed. Retrying the other site brought failures to zero, which is safe only because those requests were idempotent.

Redundancy has a capacity bill. If you must survive losing one site, the survivors carry the entire peak, so per-site utilization in normal operation has a ceiling of (N − 1) / N times your safe target. At a 70% target, two sites run at 35% and cost 2.00×, three sites run at 47% and cost 1.50×. That is why teams move from two sites to three. The odd row is four sites at 1.60×, costlier than three: whole-server rounding makes it lumpy.

Databases mostly stay active-passive because of writes. Two sites accepting a write to the same row have to reconcile afterwards, and last-write-wins silently drops one: debits of 300 and 500 from 1000 left a balance of 500 instead of 200. Multi-writer systems need conflict-free data types, partitioned ownership of rows, or consensus, which is the subject of lesson 32.

const c = await createPrimary();
try {
  const s = await addStandby(c, { name: "s1" });
  const a = await connect(c.port);
  await a.query("create table orders(id bigserial primary key, total_cents int not null)");
  await a.query("insert into orders(total_cents) select g from generate_series(1, 20000) g");
  await sleep(600);
  await a.end();

  const PROBE_MS = 500, MISSES = 3;
  const t0 = performance.now();
  stopNode(c, "primary", "immediate");
  const tKilled = performance.now();

  // الكشف: 3 probes فاشلة ورا بعض قبل ما نقرر إنه مات
  let misses = 0;
  while (misses < MISSES) {
    await sleep(PROBE_MS);
    misses = (await tcpProbe(c.port, 300)) ? 0 : misses + 1;
  }
  const tDetected = performance.now();

  const st = await connect(s.port);
  const inRecovery = (await st.query("select pg_is_in_recovery() x")).rows[0].x;
  await st.query("select pg_promote(true, 60)");
  const tPromoted = performance.now();

  // الـ client بيفتح connection جديد ويعمل write على العنوان الجديد
  const w = await connect(s.port);
  await w.query("insert into orders(total_cents) values (1)");
  const tServing = performance.now();
  const rows = (await w.query("select count(*)::int n from orders")).rows[0].n;
  await w.end();
  await st.end();

  const f = (x: number) => `${x.toFixed(0).padStart(6)} ms`;
  console.log(`real Postgres 18, standby in recovery before promote: ${inRecovery}, rows after failover: ${rows}`);
  console.log(`stop primary (immediate)    ${f(tKilled - t0)}`);
  console.log(`detection (3 x 500 ms)      ${f(tDetected - tKilled)}`);
  console.log(`pg_promote                  ${f(tPromoted - tDetected)}`);
  console.log(`client reconnect + write    ${f(tServing - tPromoted)}`);
  console.log(`total failover              ${f(tServing - tKilled)}`);
} finally {
  await stopAll(c);
}

function site(name: string) {
  const srv = http.createServer((_req, res) => res.end(name));
  return new Promise<{ srv: http.Server; port: number }>((r) =>
    srv.listen(0, "127.0.0.1", () => r({ srv, port: (srv.address() as AddressInfo).port })),
  );
}

async function run(retryOtherSite: boolean, healthEveryMs: number) {
  const cairo = await site("cairo");
  const dublin = await site("dublin");
  const up = new Map([[cairo.port, true], [dublin.port, true]]);
  const ports = [cairo.port, dublin.port];
  const timer = setInterval(async () => {
    for (const p of ports) up.set(p, await tcpProbe(p, 200));
  }, healthEveryMs);

  let turn = 0;
  const router = http.createServer(async (_req, res) => {
    const live = ports.filter((p) => up.get(p));
    const order = (live.length ? live : ports).slice();
    order.push(order.shift()!);
    if (turn++ % 2) order.reverse();
    const tries = retryOtherSite ? order : order.slice(0, 1);
    for (const p of tries) {
      try {
        const r = await fetch(`http://127.0.0.1:${p}/`, { signal: AbortSignal.timeout(500) });
        res.end(await r.text());
        return;
      } catch {
        // جرّب الموقع التاني لو مسموح
      }
    }
    res.statusCode = 502;
    res.end();
  });
  await new Promise<void>((r) => router.listen(0, "127.0.0.1", r));
  const url = `http://127.0.0.1:${(router.address() as AddressInfo).port}/`;

  let ok = 0, failed = 0, killed = false;
  const start = performance.now();
  const worker = async () => {
    while (performance.now() - start < 3000) {
      if (!killed && performance.now() - start > 1200) {
        killed = true;
        cairo.srv.closeAllConnections();
        cairo.srv.close();
      }
      const r = await fetch(url);
      await r.text();
      if (r.ok) ok++; else failed++;
      await sleep(5);
    }
  };
  await Promise.all(Array.from({ length: 4 }, worker));
  clearInterval(timer);
  router.closeAllConnections();
  router.close();
  dublin.srv.closeAllConnections();
  dublin.srv.close();
  console.log(`retry other site=${String(retryOtherSite).padEnd(5)} health check ${healthEveryMs} ms: ok ${ok}, failed ${failed} (${((failed / (ok + failed)) * 100).toFixed(1)}%)`);
}

await run(true, 1000);

بالعامية

الـ active-passive فيه standby مبياخدش traffic لحد ما يتعمله promote. الـ active-active كل المواقع بتخدم مع بعض. وقت الـ failover عمره ما بيبقى الـ promote بس: ده كشف + promote + reconnect الـ client. على Postgres 18 حقيقي، بـ 3 probes كل 500 ms، الكشف أخد حوالي 1.5 ثانية، وpg_promote حوالي 0.14 ثانية، وأول write على الـ primary الجديد حوالي 25 ms، يعني ≈1.7 ثانية إجمالي. الكشف هو الأكبر، والرقم ده إعداد إنت اخترته. في production بيبقى أكبر بكتير عادةً، لأن الـ threshold الصغير بيعمل false failovers (الجزء 3). تفاصيل الـ replication في الدرس 12.

للـ services اللي مفيهاش state، الـ active-active هو الاختيار السهل. في الـ stand-in تحت، موقع من اتنين بيموت في النص. بـ health check كل ثانية ومن غير retry، 13.6% من الـ requests فشلت في الفجوة لحد ما الـ router أخد باله. والـ retry على الموقع التاني نزّل الفشل لصفر، وده آمن بس لأن الـ requests دي idempotent.

الـ redundancy ليها فاتورة capacity. لو لازم تستحمل وقوع موقع، الباقيين بيشيلوا الـ peak كله، فالـ utilization العادي لكل موقع سقفه (N − 1) / N من الهدف الآمن بتاعك. عند هدف 70%، موقعين شغالين 35% وبتكلفة 2.00×، و3 مواقع شغالين 47% وبتكلفة 1.50×. وده سبب إن الفرق بتنقل من موقعين لـ 3. والصف الغريب 4 مواقع بـ 1.60×، أغلى من 3: التقريب لعدد servers صحيح بيعمل قفزات.

الـ databases معظمها بتفضل active-passive بسبب الـ writes. موقعين بيقبلوا write على نفس الصف لازم يتفقوا بعدين، والـ last-write-wins بيرمي واحد من غير ما يقول: خصمين 300 و500 من 1000 سابوا رصيد 500 بدل 200. الأنظمة اللي فيها أكتر من writer محتاجة conflict-free data types، أو ملكية صفوف مقسمة، أو consensus، وده موضوع الدرس 32.

فين هستخدمه في شغلي؟ الـ API بتاعك stateless ورا load balancer: خليه active-active على 3 AZs، وكل AZ تشيل حوالي نص الـ peak. الـ Postgres يفضل active-passive بـ standby في AZ تاني. ولو حد قال "نخلي الاتنين يكتبوا عشان الـ availability"، اسأله الرصيد هيتحسب إزاي لو نفس الـ account اتعدّل في المكانين.
Interview question: why not make the database active-active too? Stateless tiers can be active-active because any node can serve any request. A database has to agree on the order of writes to the same row. Doing it across sites means consensus latency on each write, or conflict resolution that can lose updates. Most systems keep one writer per piece of data and spend the redundancy budget on fast failover.
السؤال: ليه منخليش الـ database active-active كمان؟ الإجابة: الطبقات اللي مفيهاش state ينفع لأن أي node يقدر يخدم أي request. الـ database لازم تتفق على ترتيب الـ writes على نفس الصف، وده بين المواقع يعني latency للـ consensus على كل write، أو conflict resolution ممكن يضيّع updates. معظم الأنظمة بتسيب writer واحد لكل قطعة data وبتصرف ميزانية الـ redundancy على failover سريع.

Part 2 — Multi-AZ vs multi-region 🟡 Intermediateالجزء 2 — الـ multi-AZ والـ multi-region

English

Redundancy only helps against failures it is outside of, so name the failure domain first. Microsoft's documentation states an inter-zone round-trip target of "less than approximately 2 milliseconds", with zones usually within 100 km. Its published region-to-region P50 figures range from 8–9 ms between nearby regions (East US and East US 2), through 67–85 ms for US West or Europe to East US, up to 224 ms for Southeast Asia to East US. Those are one provider's numbers; test your own pair.

The commit cost follows directly. With a synchronous standby, the primary cannot acknowledge until the standby confirms, so commit time is roughly one round trip. Using a stand-in delay proxy on real Postgres, a commit went from ≈0.45 ms without waiting to ≈31 ms at a measured 31 ms RTT and ≈125 ms at a 124 ms RTT. The proxy's delay was set to 5 ms and 50 ms one way; Windows timers rounded those up, which is why the RTT is printed next to the result. The conclusion that survives this is the ratio: commit time tracks RTT almost exactly.

So synchronous replication is affordable across zones and punishing across continents. Multi-AZ is the default for production. Multi-region is justified by a requirement: a regulator, users on another continent, or a business that cannot accept a whole-region outage. The calculator shows why the question deserves numbers: with these assumptions multi-AZ costs 1.35× and active-active across regions 2.71×. The replication transfer itself is small here and grows with write volume, not user count. Azure's docs state inter-zone transfer is free there, while third-party AWS guides commonly cite $0.01/GB each way, so check your provider.

import net from "node:net";
import { createPrimary, addStandby, connect, stopAll } from "../pg-cluster.mjs";
import { delayProxy, sleep } from "./common.ts";

console.log("STAND-IN for distance: a Node TCP proxy delays every chunk. Windows timers round small delays up.");
const c = await createPrimary();
const proxy = await delayProxy(c.port, 5);
try {
  const s = await addStandby(c, { name: "s1", conf: `primary_conninfo='host=127.0.0.1 port=${proxy.port} user=app application_name=s1'` });
  const a = await connect(c.port);
  await a.query("create table payments(id bigserial primary key, cents int not null)");
  await sleep(800);

  // القياس: متوسط وقت الـ commit لكل mode
  const lat = async (mode: string, n: number) => {
    await a.query(`set synchronous_commit='${mode}'`);
    const t0 = performance.now();
    for (let i = 0; i < n; i++) await a.query("insert into payments(cents) values (1)");
    return ((performance.now() - t0) / n).toFixed(2);
  };

  // الـ RTT الحقيقي للـ proxy: echo server بنفس الـ delay، لأن Windows بيقرّب الـ timers
  const echo = net.createServer((s2) => s2.pipe(s2));
  await new Promise<void>((r) => echo.listen(0, "127.0.0.1", r));
  const echoProxy = await delayProxy((echo.address() as net.AddressInfo).port, 5);
  const measureRtt = async (oneWay: number) => {
    echoProxy.setDelay(oneWay);
    const sock = net.connect(echoProxy.port, "127.0.0.1");
    sock.setNoDelay(true);
    await new Promise((r) => sock.once("connect", r));
    const rtts: number[] = [];
    for (let i = 0; i < 20; i++) {
      const t0 = performance.now();
      sock.write("x");
      await new Promise((r) => sock.once("data", r));
      rtts.push(performance.now() - t0);
    }
    sock.destroy();
    rtts.sort((x, y) => x - y);
    return rtts[10]!;
  };

  console.log(`baseline (no sync standby): synchronous_commit=local ${await lat("local", 60)} ms, on ${await lat("on", 60)} ms`);
  await a.query("alter system set synchronous_standby_names='FIRST 1 (s1)'");
  await a.query("select pg_reload_conf()");
  await sleep(1000);
  const syncState = (await a.query("select sync_state from pg_stat_replication")).rows[0]?.sync_state;
  console.log(`standby sync_state: ${syncState}, standby port ${s.port > 0 ? "up" : "?"}`);

  for (const oneWay of [5, 50]) {
    proxy.setDelay(oneWay);
    await sleep(500);
    const rtt = await measureRtt(oneWay);
    const n = oneWay > 10 ? 25 : 40;
    console.log(`one-way delay set ${oneWay} ms, measured proxy RTT ${rtt.toFixed(1)} ms: commit local ${await lat("local", n)} ms, on ${await lat("on", n)} ms, remote_apply ${await lat("remote_apply", n)} ms`);
  }
  await a.end();
  echoProxy.close();
  echo.close();
} finally {
  proxy.close();
  await stopAll(c);
}
process.exit(0);

تكلفة الـ commit بتطلع من هنا مباشرة. مع standby متزامن، الـ primary مش هيأكد قبل ما الـ standby يأكد، فوقت الـ commit تقريبًا round trip واحد. بـ stand-in delay proxy على Postgres حقيقي، الـ commit راح من ≈0.45 ms من غير انتظار لـ ≈31 ms عند RTT مقاس 31 ms، و≈125 ms عند RTT مقاس 124 ms. الـ delay كان 5 ms و50 ms في الاتجاه الواحد، و timers الـ Windows قرّبتهم لفوق، وده سبب طباعة الـ RTT جنب النتيجة. والخلاصة اللي بتفضل صحيحة هي النسبة: وقت الـ commit ماشي ورا الـ RTT تقريبًا بالظبط.

يعني الـ synchronous replication مقبولة بين zones وموجعة بين قارات. الـ Multi-AZ هو الـ default للـ production. والـ multi-region محتاج سبب: جهة رقابية، أو users في قارة تانية، أو بيزنس مش مستحمل وقوع region كامل. الحاسبة بتوريك ليه السؤال ده محتاج أرقام: بالافتراضات دي الـ multi-AZ بـ 1.35× والـ active-active بين regions بـ 2.71×. ونقل الـ replication نفسه صغير هنا وبيكبر مع حجم الكتابة مش عدد الـ users. Documentation بتاعة Azure بتقول إن النقل بين الـ zones مجاني عندهم، وأدلة third-party لـ AWS بتذكر عادةً $0.01/GB في كل اتجاه، فراجع الـ provider بتاعك.

الغلطة الشائعة: تعتبر الـ multi-region "حماية من كل حاجة". هو مبيحميش من الـ data domain في الجدول: DELETE غلط بيتنسخ للـ region التاني برضه.

فين هستخدمه في شغلي؟ المدير بيقول "عايزين multi-region عشان الـ availability". قبل ما تبدأ، اطلب الرقم: الـ SLO الحالي كام، وكام مرة في السنين اللي فاتت region كامل وقع، وهل عندنا users برة. غالبًا multi-AZ مع backups في region تاني بيغطي الاحتياج بجزء من التكلفة، وده بيوفر شهور شغل.
Trade-off: where do you pay for durability? Synchronous cross-region replication gives RPO 0 across regions and costs about one intercontinental RTT per commit. Asynchronous replication keeps commits fast and accepts losing the replication lag when a region dies. Choose per dataset, not per company: Postgres lets you set synchronous_commit per transaction.
بتدفع تمن الـ durability فين؟ الـ synchronous بين regions بيدّيك RPO صفر وبيكلف RTT بين قارات على كل commit. الـ asynchronous بيخلي الـ commits سريعة وبتقبل تخسر الـ replication lag لما region يقع. اختار لكل dataset مش للشركة كلها: Postgres بيسمح تحدد synchronous_commit لكل transaction.

Part 3 — What the app sees 🟡 Intermediateالجزء 3 — الـ app بيشوف إيه

English

A promoted standby does not help an application that still points at the dead address. We ran a real API with a pg pool under load, killed the primary at 2.5 s and promoted the standby about 0.8 s later. In the first scenario the pool held the old address: every read and write failed from then on, and the first good write never came. The database had recovered and the service had not.

The fix has three parts. First, a single write endpoint that moves on failover, so clients never hold a node's address. Here that is a labelled stand-in proxy; in production it is PgBouncer behind a virtual IP, a cloud endpoint, or a Patroni-managed route. Second, the pool must discard broken connections and open new ones, which pg.Pool does on its own as long as it has an 'error' listener. Third, retry reads only. A failed write is ambiguous: the commit may have landed and only the acknowledgement was lost, so a blind retry can double-charge. Writes need an idempotency key first, which is covered in lesson 30. With all three the first good write arrived about 1 s after the kill.

Failing over too eagerly is its own outage. Each false failover drops connections and, with asynchronous replication, can discard recent commits. The simulation counts false failovers on a healthy primary with short network blips: probing every second with 3 misses triggered 357 in 30 days, while every 5 s with 6 misses triggered none and detects a real failure in 30 s. A hold-down time blocks another failover soon after the last one, which is what stops flapping in the bad hour.

Do not write this control loop yourself in production. Patroni holds a leader lock in a consensus store (etcd and similar), and its defaults are ttl 30, loop_wait 10 and retry_timeout 10, deliberately far from our 1.5 s. Split-brain and fencing are covered in lesson 12.

      for (let attempt = 0; ; attempt++) {
        try {
          return await pool.query("select id, total_cents from orders where id = $1", [1 + Math.floor(Math.random() * 5000)]);

        res.end("ok");
      } catch {
        res.statusCode = 503;
        res.end();
      }
    });
    await new Promise<void>((r) => app.listen(0, "127.0.0.1", r));
    const url = `http://127.0.0.1:${(app.address() as AddressInfo).port}`;

    const KILL_AT = 2500, DURATION = 9000;
    const buckets = new Map<number, { rOk: number; rErr: number; wOk: number; wErr: number }>();
    const t0 = performance.now();
    const get = (sec: number) => {
      if (!buckets.has(sec)) buckets.set(sec, { rOk: 0, rErr: 0, wOk: 0, wErr: 0 });
      return buckets.get(sec)!;
    };

      fetch(url + path, { signal: AbortSignal.timeout(4000) })

        .catch(() => false)
        .then((ok) => {
          const b = get(Math.floor((performance.now() - t0) / 1000));
          if (path === "/read") { if (ok) b.rOk++; else b.rErr++; }
          else {
            if (ok) { b.wOk++; if (performance.now() - t0 > KILL_AT && firstWriteAfterKill < 0) firstWriteAfterKill = performance.now() - t0 - KILL_AT; }
            else b.wErr++;
          }
        });

    let nextProbe = 0;

      const now = performance.now() - t0;
      for (let i = 0; i < 4; i++) pending.push(fire("/read"));
      pending.push(fire("/write"));
      if (!killed && now >= KILL_AT) {
        killed = true;
        stopNode(c, "primary", "immediate");
      }
      if (killed && promotedAt < 0 && now >= nextProbe) {
        nextProbe = now + 250;
        misses = (await tcpProbe(c.port, 150)) ? 0 : misses + 1;
        if (misses >= 3) {
          detectedAt = now;
          const st = await connect(s.port);
          await st.query("select pg_promote(true, 60)");
          await st.end();
          promotedAt = performance.now() - t0;
          proxy.switchTo(s.port);
        }
      }
      await sleep(50);
    }
    await Promise.all(pending);

    console.log("sec   reads ok/err   writes ok/err");
    for (const [sec, b] of [...buckets.entries()].sort((a, b2) => a[0] - b2[0])) {
      if (sec >= DURATION / 1000) continue;

    app.close();
    await pool.end().catch(() => {});
  } finally {
    proxy.close();
    await stopAll(c);
  }
}

function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

Part 4 — RPO and RTO as inputs 🟡 Intermediateالجزء 4 — الـ RPO والـ RTO كمدخلات

English

RPO (Recovery Point Objective) is how much data you can afford to lose, measured in time. RTO (Recovery Time Objective) is how long you can be down. They are business inputs and they differ per dataset, so ask the business instead of picking one number for the company. Payments are usually RPO 0, a catalog can lose minutes because it can be re-imported, and analytics can often lose a day because it can be rebuilt.

AWS's disaster recovery whitepaper names four strategies. Backup and restore redeploys everything from backups. Pilot light keeps data replicated and core infrastructure ready, with application servers switched off. Warm standby keeps a scaled-down but fully functional copy that can take traffic immediately. Multi-site active/active serves from all regions, and the paper calls it "the most complex and costly approach". The distinction it stresses between the middle two: pilot light cannot process requests without first taking action, and warm standby can.

The calculator picks the cheapest strategy that satisfies each need, and two results are worth reading closely. Asynchronous strategies cannot reach RPO 0 across regions, so that row returns NONE, and the honest conversation is about synchronous cross-region commits at the cost from Part 2, or about accepting a small RPO. Second, the same service appears twice with different answers for losing a zone and losing a region. Replication does not cover corruption in any strategy: as the whitepaper says, data corruption "may need to rely on backups". Backup mechanics are in lesson 15.

Part 5 — Backup strategy 🟡 Intermediateالجزء 5 — استراتيجية الـ backup

English

A full backup copies everything. An incremental copies what changed since a parent backup. WAL archiving stores every change continuously and enables point-in-time recovery. Postgres 17 and later have native incrementals through pg_basebackup --incremental and pg_combinebackup; they need summarize_wal=on. How to run base backups and PITR is in section 07 · 3.1. The focus here is what they cost.

An incremental works in blocks, not rows, and that surprises people. Changing 1% of rows at the end of the table gave an incremental that was 6.2% of the full table files. Changing the same 1% scattered across the table gave 62.4%, because one changed row dirties a whole 8 KB page. The WAL for the scattered update was also 30 MB against 0.9 MB, because of full-page writes after a checkpoint. So the savings depend on your write pattern, and you only learn it by measuring. Scaled to an assumed 500 GB database, weekly fulls with daily incrementals cost less than 23 fulls for the clustered pattern ($202 against $266 a month) and more for the scattered one ($402).

Retention decides what to delete. The usual schedule is grandfather-father-son: 7 daily, 4 weekly, 12 monthly. The script below is tested, including the rule that matters most with incrementals: never delete a parent that a kept incremental still needs. The Postgres docs say so directly: there is "no built-in mechanism to figure out which backups are still needed".

Where the copies live matters as much as how many exist. A second region covers region loss. A separate account covers compromised credentials. Immutable storage covers ransomware and malicious deletion: with S3 Object Lock in compliance mode, a protected version "can't be overwritten or deleted by any user, including the root user" until its retention date. Object Lock was read from AWS's documentation and not run here.

const dayKey = (d: Date) => d.toISOString().slice(0, 10);
const monthKey = (d: Date) => d.toISOString().slice(0, 7);

// الأسبوع: الاثنين هو بداية الأسبوع بالـ UTC
function weekKey(d: Date) {
  const x = new Date(Date.UTC(d.getUTCFullYear(), d.getUTCMonth(), d.getUTCDate()));
  x.setUTCDate(x.getUTCDate() - ((x.getUTCDay() + 6) % 7));
  return dayKey(x);
}

// القرار: أحدث backup في كل يوم/أسبوع/شهر، والباقي يتمسح
export function keepSet(all: Backup[], policy: Policy): Set<string> {
  const sorted = [...all].sort((a, b) => b.at.getTime() - a.at.getTime());
  const keep = new Set<string>();
  const pass = (keyOf: (d: Date) => string, limit: number) => {
    const seen = new Set<string>();
    for (const b of sorted) {
      const k = keyOf(b.at);
      if (seen.has(k)) continue;
      if (seen.size === limit) break;
      seen.add(k);
      keep.add(b.id);
    }
  };
  pass(dayKey, policy.daily);
  pass(weekKey, policy.weekly);
  pass(monthKey, policy.monthly);

  // المهم: الـ incremental من غير الـ parent بتاعه ملوش فايدة، فبنحتفظ بالسلسلة كلها
  const byId = new Map(all.map((b) => [b.id, b]));
  for (const id of [...keep]) {
    let cur = byId.get(id);
    while (cur?.parent) {
      keep.add(cur.parent);
      cur = byId.get(cur.parent);
    }
  }
  return keep;
}

الـ full بينسخ كل حاجة. الـ incremental بينسخ اللي اتغير من backup قبله. والـ WAL archiving بيخزن كل تغيير باستمرار وبيسمح بالرجوع لأي لحظة. Postgres 17 وأحدث فيه incrementals أصلية بـ pg_basebackup --incremental وpg_combinebackup، ومحتاجين summarize_wal=on. إزاي تشغّل الـ base backups والـ PITR موجود في القسم 07 · 3.1، والتركيز هنا على التكلفة.

الـ incremental بيشتغل بالـ blocks مش بالصفوف، ودي بتفاجئ الناس. تعديل 1% من الصفوف في آخر الجدول طلّع incremental بحجم 6.2% من ملفات الجداول الكاملة. وتعديل نفس الـ 1% متفرقين على الجدول طلّع 62.4%، لأن صف واحد متغير بيوسّخ page كاملة 8 KB. والـ WAL للتعديل المتفرق كمان كان 30 MB مقابل 0.9 MB، بسبب الـ full-page writes بعد الـ checkpoint. فالتوفير بيعتمد على شكل الكتابة عندك، ومش هتعرفه غير بالقياس. وعلى 500 GB مفترضة، الـ weekly fulls مع daily incrementals أرخص من 23 full في النمط المتجمع (202 دولار مقابل 266 في الشهر) وأغلى في المتفرق (402 دولار).

الـ retention بيحدد إيه يتمسح. الجدول المعتاد grandfather-father-son: 7 يومي و4 أسبوعي و12 شهري. السكريبت تحت متختبر، ومعاه أهم قاعدة مع الـ incrementals: متمسحش parent لسه incremental محفوظ محتاجه. والـ docs بتاعة Postgres بتقولها صريحة: "no built-in mechanism to figure out which backups are still needed".

النسخ موجودة فين مهم زي عددها. الـ region التاني بيغطي وقوع region. والـ account المنفصل بيغطي الـ credentials المسروقة. والتخزين الـ immutable بيغطي الـ ransomware والمسح المقصود: مع S3 Object Lock في compliance mode، النسخة المحمية "can't be overwritten or deleted by any user, including the root user" لحد تاريخ الـ retention. الـ Object Lock قريناه من docs بتاعة AWS ومتشغلش هنا.

فين هستخدمه في شغلي؟ فاتورة الـ S3 بتاعة الـ backups كبرت. قبل ما تقلل الـ retention، بص على شكل الكتابة: لو عندك job بيعمل UPDATE على عمود في كل الجدول كل ليلة، الـ incremental هيبقى قريب من full والـ WAL هيتضخم. ساعتها إصلاح الـ job بيوفر أكتر من أي lifecycle rule.
What breaks: backups in the same blast radius Backups stored in the same account as production can be deleted by the same stolen credentials. Part 6 — DR drills 🟡 Intermediateالجزء 6 — الـ DR drills

English

A backup you have not restored is a hypothesis. In January 2017 GitLab lost production data when an engineer wiped the PostgreSQL data directory on the primary, believing it was the secondary. Their postmortem lists how every safety net failed: "the backup procedure was using pg_dump 9.2, while our database is running PostgreSQL 9.6", "The S3 bucket was empty", the failure emails were rejected because DMARC was not enabled, and disk snapshots "were not enabled for any of the database servers". They recovered from an LVM snapshot taken 6 hours earlier: "GitLab.com was down for about 18 hours", with an estimated loss of roughly 5,000 projects, 5,000 comments and 700 new user accounts.

A drill turns that into a script: lose the primary, restore from the base backup and WAL archive, verify the data, and print measured RTO and RPO. Verification is the point. "The server started" proves nothing, so the script compares row counts and checksums against what the client knows it committed. The real run passed with RTO ≈1.6 s and RPO ≈2.09 s on a tiny dataset, and lost 53 committed rows. That loss is what archive_timeout=2 means. RTO grows with data size, so the number from a 50,000-row table says nothing about your 500 GB database. Run the drill against a realistic copy.

The second run sabotages the archive to simulate a silently broken backup job, and the drill does exactly what GitLab's process could not: it fails loudly and exits non-zero. Make the drill a monthly scheduled job. Page the backup owner on failure, define a pass as "checksums match and measured RTO and RPO are within target", and record each result so you can see the trend as the data grows. The AWS paper puts it plainly: it is critical to "regularly assess and test your disaster recovery strategy".

import type { Backup } from "./retention.ts";

// الحل: نفس فكرة keepSet بس بمفتاح الساعة
function keepLastHours(all: Backup[], hours: number): Set<string> {
  const seen = new Set<string>();
  const keep = new Set<string>();
  for (const b of [...all].sort((x, y) => y.at.getTime() - x.at.getTime())) {
    const k = b.at.toISOString().slice(0, 13);
    if (seen.has(k)) continue;
    if (seen.size === hours) break;
    seen.add(k);
    keep.add(b.id);
  }
  return keep;
}

الـ primary key على idempotency_key وon conflict do nothing بيخلّوا التكرار من غير أثر، وrowCount بيقول هل ده أول مرة ولا تكرار. الناتج صف واحد و5000 cent رغم المحاولتين. التصميم الكامل في الدرس 30.

Cheat sheet · الخلاصة

  • Failover time = detection + promotion + client reconnect. Detection dominates, and you choose it.
  • Survive losing one of N sites: normal utilization ≤ target × (N − 1) / N. Two sites 2.00×, three 1.50×.
  • Databases stay active-passive because of writes: last-write-wins lost a debit in our run.
  • Name the failure domain. Multi-AZ is the default; multi-region needs a stated reason.
  • Synchronous commit costs about one RTT: ≈125 ms at a 124 ms RTT.
  • Pointing a pool at a node never recovers. Use a moving write endpoint, an 'error' listener, and read-only retries.
  • A write that fails during failover is ambiguous. Retry it only with an idempotency key.
  • False failovers: 1 s × 3 misses gave 357 per 30 days, 5 s × 6 gave 0 and still detects in 30 s. Add a hold-down.
  • RPO and RTO are per dataset and come from the business. RPO 0 across regions rules out asynchronous options.
  • Incrementals work in blocks: the same 1% of rows gave 6.2% clustered and 62.4% scattered.
  • Replication is not a backup. Keep a copy production credentials cannot delete.
  • An unrestored backup is a hypothesis. Run a scheduled drill with checksums and measured RTO and RPO.

  • الـ databases بتفضل active-passive بسبب الـ writes: الـ last-write-wins ضيّع خصم في الـ run بتاعنا.
  • سمّي الـ failure domain. الـ multi-AZ هو الـ default، والـ multi-region محتاج سبب مكتوب.
  • الـ synchronous commit بيكلّف حوالي RTT واحد: ≈125 ms عند RTT بـ 124 ms.
  • الـ pool المربوط بـ node عمره ما بيرجع. استخدم write endpoint بيتنقل، و 'error' listener، و retry للـ reads بس.
