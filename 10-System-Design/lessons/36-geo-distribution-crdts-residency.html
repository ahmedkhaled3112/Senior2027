Why this matters · ليه ده مهم

English

The speed of light sets a floor nobody can tune away, and a page with five sequential queries pays that floor five times. Going multi-region buys latency and survival, and charges you in lag, conflicts and legal scope. This lesson measures each of those: real Postgres behind a delay proxy, a simulation that counts the updates last-write-wins throws away, CRDTs tested against their merge laws, and a residency rule that fails CI.

Interviewers ask "how would you go global?" to hear whether you start from where the data must live and what may conflict, rather than from a product name. The honest default is one region until the numbers say otherwise.

بالعامية

سرعة الضوء حد أدنى محدش يقدر يعمله tuning، وصفحة فيها 5 queries ورا بعض بتدفع الحد ده 5 مرات. لما تروح multi-region بتكسب latency وقدرة على النجاة، وبتدفع lag و conflicts ونطاق قانوني أوسع. الدرس ده بيقيس كل حاجة من دول: Postgres حقيقي ورا delay proxy، ومحاكاة بتعدّ الـ updates اللي last-write-wins بيرميها، و CRDTs متجربة على قوانين الدمج، وقاعدة residency بتوقّع الـ CI.

لما الـ interviewer يسأل "هتعملها global إزاي؟"، عايز يعرف إنت بتبدأ من الـ data لازم تعيش فين وإيه اللي ممكن يتعارض، مش من اسم منتج. والـ default الصادق: region واحدة لحد ما الأرقام تقول غير كده.

Part 1 — Data locality 🔴 Advancedالجزء 1 — الـ data قريبة من مين

English

Latency depends on where each hop is. Take users in Cairo, Frankfurt and Virginia and a page that makes 5 sequential database queries. The calculator below uses ballpark round-trip times as inputs; they are assumptions, so measure your own paths. The result matters more than the exact numbers: an app next to the database costs one user-to-app round trip plus 5 tiny ones, while an app in Frankfurt with its database in Virginia pays the cross-region RTT on every query, 451 to 540 ms. Splitting the app from its data is the worst placement of the four.

The placement that serves everyone is to give each user a home region and keep that user's rows there. A real run below uses two Postgres clusters with a TCP delay proxy standing in for distance. Windows timers round delays up, so the proxy's real RTT is measured and printed next to the result (93.6 ms for a requested 90). Five sequential queries went from 3.5 ms locally to 492.7 ms across the delay, and packing the same data into one round trip brought it back to 91.7 ms. When the database has to stay far away, round trips are the thing to count.

Routing is then a lookup. A small directory maps a login to a home region, and every order is read and written in that region's database. Only that directory and the tenants table stay global, and neither holds order data. The directory stores a keyed hash of the email (an HMAC, with the key kept in a KMS) instead of the email. That reduces what leaves the region, but a keyed hash of an email is still pseudonymous personal data under GDPR, so it doesn't by itself make the table non-personal. Part 5 returns to that.

const SAME_REGION_MS = 1;

function rtt(a: string, b: string): number {
  if (a === b) return SAME_REGION_MS;
  return RTT_MS[`${a}-${b}`] ?? RTT_MS[`${b}-${a}`];
}

import net from "node:net";

// بروكسي TCP بيأخر كل chunk، وده بديل للمسافة مش مسافة حقيقية
// الخيار bytesPerSec بيحط سقف للسرعة في كل اتجاه عشان نشوف الـ lag وهو بيكبر
export function delayProxy(targetPort, oneWayMs) {
  const sockets = new Set();
  const state = { bytesPerSec: 0 };
  const server = net.createServer((client) => {
    const upstream = net.connect(targetPort, "127.0.0.1");
    sockets.add(client);
    sockets.add(upstream);
    client.setNoDelay(true);
    upstream.setNoDelay(true);
    const pipe = (from, to) => {
      let nextFree = 0;
      // طابور FIFO بتايمر واحد: لو كل chunk ليها تايمر، الـ bytes ممكن تتلخبط
      const queue = [];
      let timer = null;
      const drain = () => {
        timer = null;
        while (queue.length && queue[0].at <= performance.now()) {
          const { chunk } = queue.shift();
          if (!to.destroyed) to.write(chunk);
        }
        if (queue.length) timer = setTimeout(drain, Math.max(1, queue[0].at - performance.now()));
      };
      from.on("data", (chunk) => {
        const now = performance.now();
        const start = Math.max(now, nextFree);
        const serialize = state.bytesPerSec ? (chunk.length / state.bytesPerSec) * 1000 : 0;
        nextFree = start + serialize;
        queue.push({ at: nextFree + oneWayMs, chunk });
        if (timer === null) timer = setTimeout(drain, Math.max(1, queue[0].at - now));
      });
    };
    pipe(client, upstream);
    pipe(upstream, client);
    const kill = () => { client.destroy(); upstream.destroy(); };
    for (const s of [client, upstream]) { s.on("close", kill); s.on("error", kill); }
  });
  return new Promise((resolve) =>
    server.listen(0, "127.0.0.1", () =>
      resolve({
        port: server.address().port,
        setCap: (bytesPerSec) => { state.bytesPerSec = bytesPerSec; },
        close: () => { sockets.forEach((s) => s.destroy()); server.close(); },
      }),
    ),
  );
}

// الحارس: أي بورت فاضي أو افتراضي معناه خدمة حقيقية على الجهاز، فبنرفضه
export function guard(port) {
  const n = Number(port);
  if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error("refusing port " + port);
  }
  return n;
}

بالعامية

الـ latency بتتحدد بمكان كل hop. خد مستخدمين في القاهرة و Frankfurt و Virginia، وصفحة بتعمل 5 queries ورا بعض. الآلة الحاسبة بتستخدم RTT تقديرية كمدخلات، فدي فرضيات وقيس بتاعتك. النتيجة أهم من الأرقام بالظبط: app جنب الـ database بيكلف رحلة واحدة للمستخدم و5 رحلات صغيرة، أما app في Frankfurt والـ database بتاعه في Virginia بيدفع الـ RTT بين الـ regions في كل query، من 451 لـ 540 ms. إنك تفصل الـ app عن الـ data هو أسوأ مكان من الأربعة.

المكان اللي بيخدم الكل هو إنك تدي لكل مستخدم home region وتخلي صفوفه فيها. التجربة الحقيقية تحت بتستخدم 2 Postgres clusters، و TCP delay proxy كبديل للمسافة. الـ timers على Windows بتقرّب لفوق، فبنقيس الـ RTT الحقيقي للبروكسي ونطبعه جنب النتيجة (93.6 ms لما طلبنا 90). الـ 5 queries راحوا من 3.5 ms محليًا لـ 492.7 ms عبر الـ delay، ولما جمعناهم في رحلة واحدة رجعوا 91.7 ms. لو الـ database لازم يفضل بعيد، عدّ الـ round trips.

الـ routing بعدها lookup بسيط. directory صغير بيحوّل الـ login لـ home region، وكل order بيتقري ويتكتب في database الـ region دي. الحاجات اللي بتفضل global هي الـ directory ده وجدول tenants بس، ومفيش فيهم بيانات طلبات. الـ directory بيخزن keyed hash للإيميل (HMAC، والـ key في KMS) بدل الإيميل نفسه. ده بيقلل اللي بيخرج من الـ region، بس keyed hash للإيميل لسه pseudonymous personal data في GDPR، فلوحده مش بيخلي الجدول non-personal. هنرجع لده في الجزء 5.

فين هستخدمه في شغلي؟ لو عندك Next.js app على Vercel في Frankfurt والـ Postgres في us-east-1 وصفحة الـ order بتعمل 5 queries، الصفحة هتاخد نص ثانية من غير أي bug. قبل ما تعمل multi-region، اعمل الأرخص: حط الـ app في region الـ database، أو جمّع الـ queries في round trip واحد. ولما يبقى عندك فعلًا مستخدمين كتير في region تانية، ضيف home_region في users واعمل routing زي اللي فوق.
Latency versus operations A home region per user fixes latency for most traffic, and creates the cross-region case: a user who travels, or a query that needs users from two regions. Decide up front what happens then (usually: read through the home region, accept the latency).

Part 2 — Cross-region lag 🔴 Advancedالجزء 2 — الـ lag بين الـ regions

English

Asynchronous replication means the standby is behind by at least the one-way time plus apply time. With a real Postgres standby behind the delay proxy at 75 ms each way (measured RTT 157.2 ms) we can watch it in pg_stat_replication. During a three-second write burst the standby's replay_lag peaked at 204 ms with 13.3 MB unapplied. That's the delay plus whatever the burst queued up. When the same proxy also capped bandwidth at 1 MB/s (delay and bandwidth are separate costs, and links are shared), a modest burst left 4 MB behind, replay_lag rose to 1,794 ms and the standby took 3,989 ms to catch up after the writes stopped. Lag isn't a constant of the link; it grows when the write rate exceeds what the link and the replay process can carry.

Read-your-writes fails exactly as you'd predict: writing to the primary and immediately reading from the replica missed the row in 40 of 40 attempts. Two fixes, both worth having. Sticky reads: after a user writes, send that user's reads to the home region for a while. Token-based reads: after the write, capture the primary's WAL position and have the replica wait until it has replayed past that LSN. With the token, stale reads dropped from 40 to 0, at the cost of a median wait of 93 ms and 106 ms at worst. In production that wait needs a limit, and when the limit is hit the read goes to the home region instead. The vocabulary is in lesson 14.

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const c = await createPrimary();
const proxy = await delayProxy(guard(c.port), 75);
try {

  const primary = await connect(guard(c.port));
  const replica = await connect(guard(standby.port));
  const far = await connect(guard(proxy.port));
  await primary.query("create table orders(id bigint generated always as identity primary key, user_id int, status text, note text)");
  await sleep(1500);

  const samples = [];
  for (let i = 0; i < 15; i++) {
    const t = performance.now();
    await far.query("select 1");
    samples.push(performance.now() - t);
  }
  samples.sort((a, b) => a - b);
  console.log(`measured RTT through the proxy: median ${samples[7].toFixed(1)} ms (stand-in for distance, asked for 2 x 75 ms)`);

  // بنكتب burst لمدة 3 ثواني وبنقرا pg_stat_replication كل 150 ms
  async function burst(label, pauseMs = 0) {
    let running = true;
    let inserted = 0;
    const writer = (async () => {
      while (running) {
        await primary.query("insert into orders(user_id, status, note) select g, 'paid', repeat('x', 200) from generate_series(1, 200) g");
        inserted += 200;
        if (pauseMs) await sleep(pauseMs);
      }
    })();
    let maxBytes = 0;
    let maxReplayMs = 0;
    for (let i = 0; i < 20; i++) {
      await sleep(150);
      const { rows } = await primary.query(`select pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)::bigint as bytes,
        coalesce(extract(epoch from replay_lag) * 1000, 0)::int as replay_ms from pg_stat_replication`);
      if (rows[0]) {
        maxBytes = Math.max(maxBytes, Number(rows[0].bytes));
        maxReplayMs = Math.max(maxReplayMs, rows[0].replay_ms);
      }
    }
    running = false;
    await writer;
    console.log(`${label.padEnd(26)} inserted=${inserted}  max bytes behind=${maxBytes}  max replay_lag=${maxReplayMs} ms`);
  }
  await burst("burst, delay only");
  await sleep(2000);
  proxy.setCap(1_000_000);
  // بنبطّأ الكتابة هنا عشان اللي في الطريق يخلص في ثواني مش دقايق
  await burst("burst, delay + 1 MB/s cap", 25);
  const t0 = performance.now();
  let caughtUp = false;
  while (performance.now() - t0 < 45_000) {
    const { rows } = await primary.query("select pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)::bigint b from pg_stat_replication");
    if (rows[0] && Number(rows[0].b) === 0) { caughtUp = true; break; }
    await sleep(50);
  }
  console.log(`after the burst stopped: ${caughtUp ? "caught up" : "still behind"} in ${(performance.now() - t0).toFixed(0)} ms`);
  proxy.setCap(0);
  await sleep(300);

  // قراية بعد الكتابة على طول: بنكتب على الـ primary ونقرا فورًا من الـ replica
  const N = 40;
  let stale = 0;
  for (let i = 0; i < N; i++) {
    const { rows } = await primary.query("insert into orders(user_id, status) values ($1, 'pending') returning id", [100000 + i]);
    const seen = await replica.query("select 1 from orders where id = $1", [rows[0].id]);
    if (seen.rowCount === 0) stale++;
  }
  console.log(`read your writes from replica: ${stale}/${N} reads did not see the row`);
  await sleep(600);

  // الحل: token هو الـ LSN بعد الكتابة، والـ replica لازم توصل له قبل ما نقرا
  async function waitForToken(db, token, timeoutMs = 2000) {
    const start = performance.now();
    while (performance.now() - start < timeoutMs) {
      const { rows } = await db.query("select pg_last_wal_replay_lsn() >= $1::pg_lsn ok", [token]);
      if (rows[0].ok) return performance.now() - start;
      await sleep(5);
    }
    return -1;
  }
  let staleWithToken = 0;
  const waits = [];
  for (let i = 0; i < N; i++) {
    const { rows } = await primary.query("insert into orders(user_id, status) values ($1, 'pending') returning id", [200000 + i]);
    const token = (await primary.query("select pg_current_wal_insert_lsn() t")).rows[0].t;

Part 3 — Last-write-wins 🔴 Advancedالجزء 3 — آخر كتابة تكسب

English

If two regions both accept writes, the same key can be written in both before either has seen the other. Last-write-wins (LWW) picks the version with the higher timestamp and silently drops the other. The simulation below (seeded, virtual time, labelled as a simulation) replays 20,000 writes on 500 keys across two regions. It counts a lost update when a write disappears although the winning write never saw it.

Even with perfect clocks and only 100 ms of lag, 71 writes vanished. At 1 s of lag it was 645, so loss grows with lag, because more writes overlap. Then skew: with one region's clock 500 ms ahead the loss rises to 209, and with 5 s it reaches 1,593, of which 1,569 are cases where the later write in real time lost to an earlier one, because that clock ran fast. Skew and its measurement are in lesson 29. Note the last column: divergence is 0 in every row. LWW always converges. Converging and keeping your data are different things.

LWW is fine where the value is a replaceable snapshot and losing one is harmless: a last-seen timestamp, a cached preference, presence status. It is wrong for money, inventory, order state or anything a person typed and expects to keep. The next step is a custom merge that knows what the fields mean: merge field by field against the common ancestor, or walk a state machine so shipped beats paid regardless of clock. Below, LWW loses the phone change while a field merge keeps both changes and reports a real conflict only when the same field changed twice.

// دي محاكاة بوقت افتراضي وseed ثابت، مش قياس على شبكة حقيقية
// مش بتغطي: فقد الرسايل، تغيّر الـ lag مع الضغط، أو انقسام الشبكة
function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

interface Write { id: number; key: number; region: 0 | 1; trueTime: number; stamp: number; sawId: number | null }
type Versioned = { writeId: number; stamp: number; region: 0 | 1 };

function simulate(skewMs: number, lagMs: number) {
  const rng = mulberry32(2026);
  const WRITES = 20_000;
  const KEYS = 500;
  const DURATION_MS = 600_000;
  const writes = new Map<number, Write>();
  const state: Map<number, Versioned>[] = [new Map(), new Map()];
  const events: { at: number; kind: "write" | "replicate"; w?: Write; to?: 0 | 1 }[] = [];

  for (let i = 0; i < WRITES; i++) {
    const region = (rng() < 0.5 ? 0 : 1) as 0 | 1;
    const key = Math.floor(rng() * KEYS);
    const at = rng() * DURATION_MS;
    events.push({ at, kind: "write", w: { id: i, key, region, trueTime: at, stamp: 0, sawId: null } });
  }
  events.sort((a, b) => a.at - b.at);

  // الـ region التاني ساعته متقدمة بمقدار الـ skew
  const clock = (region: 0 | 1, t: number) => t + (region === 1 ? skewMs : 0);
  let lostUpdates = 0;
  let laterWriteLost = 0;
  const seenBy = new Map<number, Set<number>>();
  const chainOf = (w: Write): Set<number> => seenBy.get(w.id) ?? new Set();

  function apply(region: 0 | 1, incoming: Versioned, w: Write): void {
    const cur = state[region].get(w.key);
    const wins = !cur || incoming.stamp > cur.stamp || (incoming.stamp === cur.stamp && incoming.region > cur.region);
    if (!cur) { state[region].set(w.key, incoming); return; }
    const winnerId = wins ? incoming.writeId : cur.writeId;
    const loserId = wins ? cur.writeId : incoming.writeId;
    if (region === 0 && winnerId !== loserId) {
      const winner = writes.get(winnerId)!;
      const loser = writes.get(loserId)!;
      // خسارة صامتة: اللي كسب مكانش شاف اللي اتمسح أصلًا
      if (!chainOf(winner).has(loserId)) {
        lostUpdates++;
        if (loser.trueTime > winner.trueTime) laterWriteLost++;
      }
    }
    if (wins) state[region].set(w.key, incoming);
  }

  let idx = 0;
  const queue = [...events];
  queue.sort((a, b) => a.at - b.at);
  while (idx < queue.length) {
    const ev = queue[idx++];
    if (ev.kind === "write") {
      const w = ev.w!;
      const cur = state[w.region].get(w.key);
      w.sawId = cur ? cur.writeId : null;
      const chain = new Set<number>();
      if (w.sawId !== null) {
        chain.add(w.sawId);
        for (const id of seenBy.get(w.sawId) ?? []) chain.add(id);
      }
      seenBy.set(w.id, chain);
      w.stamp = clock(w.region, ev.at);
      writes.set(w.id, w);
      const v: Versioned = { writeId: w.id, stamp: w.stamp, region: w.region };
      apply(w.region, v, w);
      const other = (w.region === 0 ? 1 : 0) as 0 | 1;
      const arrive = ev.at + lagMs * (0.5 + rng());
      const pos = lowerBound(queue, arrive, idx);
      queue.splice(pos, 0, { at: arrive, kind: "replicate", w, to: other });
    } else {
      const w = ev.w!;
      apply(ev.to!, { writeId: w.id, stamp: w.stamp, region: w.region }, w);
    }
  }

  let divergent = 0;
  for (const [k, v] of state[0]) {
    if (state[1].get(k)?.writeId !== v.writeId) divergent++;
  }
  return { writes: WRITES, keys: KEYS, lostUpdates, laterWriteLost, divergent };
}

function lowerBound(q: { at: number }[], at: number, from: number): number {
  let lo = from;
  let hi = q.length;
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (q[mid].at < at) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}

export function mergeFields(base: Customer, a: Customer, b: Customer): { merged: Customer; conflicts: string[] } {
  const merged = { ...base };
  const conflicts: string[] = [];
  for (const field of Object.keys(base) as (keyof Customer)[]) {
    const changedA = a[field] !== base[field];
    const changedB = b[field] !== base[field];
    if (changedA && changedB && a[field] !== b[field]) {
      conflicts.push(field);
      merged[field] = a[field];
    } else {
      merged[field] = changedA ? a[field] : b[field];
    }
  }
  return { merged, conflicts };
}

Part 4 — CRDTs 🔴 Advancedالجزء 4 — الـ CRDTs

English

A CRDT avoids the conflict by design. Each replica keeps state such that merging two states is commutative (order doesn't matter), associative (grouping doesn't matter) and idempotent (merging the same thing twice changes nothing). If those three laws hold, replicas that exchange state in any order, with duplicates, end up equal. So you test the laws instead of hand-picking examples, and that's what the fast-check run below does: 300 random states per law, per type.

A G-Counter gives each region one slot that only it may increment; merge takes the max per slot. A PN-Counter is two G-Counters, for increments and decrements. An OR-Set gives each add a unique tag, and a remove deletes only the tags that replica has observed, so a concurrent add survives. That's the cart below: two regions edit during a partition, and after merging, each sees the same cart. The removal of the shirt wins because the shirt's tag had been observed, the phone and mug survive. For real shared documents, yjs does the same job for text and maps: concurrent edits on two docs merged with both fields kept and the same text on both sides.

The limit is the part interviewers want. CRDTs only guarantee convergence, so they can't enforce a global invariant. Two regions each debit 100 from a balance of 150, both locally correct, and after the merge the balance is -50. The same goes for "unique username": two regions can both accept it. An invariant needs coordination or a single owner. Metadata is the other bill: the OR-Set below stays at one visible element but its state reached 157,824 bytes after 10,000 add/remove cycles. Yjs garbage-collected its deleted items down to 27 bytes in the same kind of test, which is the best case for it, since adjacent deletes merge into one range.

// الـ G-Counter: كل region ليه خانة بيزوّدها هو بس، والدمج بياخد الأكبر
export type GCounter = Record<string, number>;

export const gInc = (c: GCounter, region: string, by = 1): GCounter => ({ ...c, [region]: (c[region] ?? 0) + by });
export const gValue = (c: GCounter): number => Object.values(c).reduce((s, n) => s + n, 0);
export function gMerge(a: GCounter, b: GCounter): GCounter {
  const out: GCounter = { ...a };
  for (const [region, n] of Object.entries(b)) out[region] = Math.max(out[region] ?? 0, n);
  return out;
}

// الـ PN-Counter: عدّادين G واحد للزيادة وواحد للنقصان

export const pnEmpty = (): PNCounter => ({ p: {}, n: {} });
export const pnInc = (c: PNCounter, region: string, by = 1): PNCounter => ({ ...c, p: gInc(c.p, region, by) });
export const pnDec = (c: PNCounter, region: string, by = 1): PNCounter => ({ ...c, n: gInc(c.n, region, by) });
export const pnValue = (c: PNCounter): number => gValue(c.p) - gValue(c.n);
export const pnMerge = (a: PNCounter, b: PNCounter): PNCounter => ({ p: gMerge(a.p, b.p), n: gMerge(a.n, b.n) });

// الـ OR-Set: كل add ليه tag فريد، والـ remove بيشيل الـ tags اللي شافها بس
export interface ORSet { adds: Record<string, string[]>; removes: string[] }
export const orEmpty = (): ORSet => ({ adds: {}, removes: [] });

export function orAdd(s: ORSet, element: string, tag: string): ORSet {
  return { ...s, adds: { ...s.adds, [element]: [...(s.adds[element] ?? []), tag] } };
}
export function orRemove(s: ORSet, element: string): ORSet {
  return { ...s, removes: [...new Set([...s.removes, ...(s.adds[element] ?? [])])] };
}
export function orHas(s: ORSet, element: string): boolean {
  return (s.adds[element] ?? []).some((t) => !s.removes.includes(t));
}
export function orValues(s: ORSet): string[] {
  return Object.keys(s.adds).filter((e) => orHas(s, e)).sort();
}
export function orMerge(a: ORSet, b: ORSet): ORSet {
  const adds: Record<string, string[]> = {};
  for (const src of [a.adds, b.adds]) {
    for (const [element, tags] of Object.entries(src)) {
      adds[element] = [...new Set([...(adds[element] ?? []), ...tags])].sort();
    }
  }
  return { adds, removes: [...new Set([...a.removes, ...b.removes])].sort() };
}

Interview question "Can a CRDT keep an account balance from going negative?" → No. A CRDT guarantees that replicas converge, not that any invariant holds across them: two regions can each approve a debit that is locally fine. An invariant like balance ≥ 0 needs a single owner, an escrow split between regions, or coordination.
"هل CRDT يقدر يمنع رصيد حساب إنه يبقى سالب؟" ← لأ. الـ CRDT بيضمن إن الـ replicas توصل لنفس الحالة، مش إن أي قيد يفضل صح بينها: region اتنين ممكن كل واحد يوافق على خصم صحيح عنده. قيد زي balance ≥ 0 محتاج صاحب واحد، أو escrow متقسم بين الـ regions، أو coordination.

Part 5 — Data residency 🔴 Advancedالجزء 5 — قوانين مكان الـ data

English

This part is engineering context, not legal advice. GDPR is the common reference: Chapter V (Articles 44–50) limits transfers of personal data out of the EU/EEA. It doesn't require the data to stay inside. A transfer needs a basis: an adequacy decision (Art. 45), appropriate safeguards such as standard contractual clauses (Art. 46), binding corporate rules (Art. 47), or a narrow derogation (Art. 49). The European Commission's adequacy list includes the UK, Japan, Switzerland and US companies in the Data Privacy Framework, and not Egypt or Saudi Arabia. Two details decide most designs. The EDPB says "remote access from a third country (for example in support situations)" also counts as a transfer, so a support engineer in Cairo opening an EU customer's record is a transfer. And many customer contracts ask for EU-only storage, which is stricter than the law.

Other countries have their own rules, and they change, so check the official text before quoting one. Egypt has Law 151 of 2020; its Executive Regulations were reported as issued in November 2025, with cross-border transfers needing a licence from the data protection centre. Saudi Arabia has the PDPL and a 2024 regulation on transfers outside the Kingdom. I could not read the official text of either: what I found is law-firm summaries, so treat those two sentences as pointers for your lawyer, not as facts to build on.

The design that follows is straightforward. Pin each tenant to a region. Split the control plane (tenants, feature flags, deploys: global and free of personal data) from the data plane (orders, invoices, customers: one region per tenant). Keep personal data out of global tables, and then remember the places people forget: backups, log pipelines, analytics exports and support tooling count too. Finally, make it mechanical: a rule in a wiki does nothing at 2 a.m. The router below throws ResidencyViolation before a write can leave the region, an unknown tenant fails closed, a table with no data class is rejected, a CI check fails the build if any store holding EU data sits elsewhere, and a database CHECK constraint is the last line if the router ever has a bug.

export type DataClass = "pii" | "operational";

export interface Tenant { id: string; residency: Region }

  override name = "ResidencyViolation";
}

// الجداول اللي فيها PII لازم تفضل في region الـ tenant
const TABLE_CLASS: Record<string, DataClass> = {
  orders: "pii",
  invoices: "pii",
  customers: "pii",
  feature_flags: "operational",
};

export class TenantRouter {
  private tenants: Map<string, Tenant>;
  constructor(tenants: Tenant[]) {
    this.tenants = new Map(tenants.map((t) => [t.id, t]));
  }

  regionFor(tenantId: string): Region {
    const tenant = this.tenants.get(tenantId);
    // لو الـ tenant مش معروف بنرفض، عمره ما يروح لـ region افتراضي
    if (!tenant) throw new ResidencyViolation(`unknown tenant ${tenantId}: refusing to route`);
    return tenant.residency;
  }

  assertWrite(tenantId: string, table: string, targetRegion: Region): void {
    const home = this.regionFor(tenantId);
    const dataClass = TABLE_CLASS[table];
    if (dataClass === undefined) throw new ResidencyViolation(`table ${table} has no data class: classify it first`);
    if (dataClass === "pii" && targetRegion !== home) {
      throw new ResidencyViolation(`tenant ${tenantId} is pinned to ${home}, refusing write to ${table} in ${targetRegion}`);
    }
  }
}

الجزء ده سياق هندسي مش استشارة قانونية. الـ GDPR هو المرجع المشهور: Chapter V (المواد 44–50) بيحدد نقل الـ personal data بره الـ EU/EEA، ومش بيطلب إن الـ data تفضل جوه. النقل محتاج أساس: adequacy decision (مادة 45)، أو safeguards زي standard contractual clauses (مادة 46)، أو binding corporate rules (مادة 47)، أو استثناء ضيق (مادة 49). قايمة الـ adequacy بتاعة المفوضية الأوروبية فيها UK و Japan و Switzerland والشركات الأمريكية المشتركة في Data Privacy Framework، ومصر والسعودية مش فيها. وفيه تفصيلتين بيحددوا أغلب التصميمات. الـ EDPB بيقول إن "remote access from a third country (for example in support situations)" بيتحسب نقل برضه، يعني مهندس support في القاهرة فتح سجل عميل أوروبي ده نقل. وكمان عقود كتير بتطلب تخزين جوه الـ EU بس، وده أشد من القانون.

الدول التانية ليها قوانينها، وبتتغير، فراجع النص الرسمي قبل ما تقتبس. مصر عندها قانون 151 لسنة 2020، ولائحته التنفيذية اتقال إنها صدرت في نوفمبر 2025، والنقل عبر الحدود محتاج ترخيص من مركز حماية البيانات. والسعودية عندها الـ PDPL ولائحة 2024 للنقل خارج المملكة. مقدرتش أقرا النص الرسمي للاتنين: اللي لقيته ملخصات مكاتب محاماة، فاعتبر الجملتين دول نقطة بداية للمحامي بتاعك، مش حقايق تبني عليها.

التصميم اللي بيطلع من ده واضح. ثبّت كل tenant في region. وافصل الـ control plane (الـ tenants والـ feature flags والـ deploys: global ومن غير personal data) عن الـ data plane (الـ orders والـ invoices والـ customers: region واحدة لكل tenant). خلّي الـ personal data بره الجداول العالمية، وافتكر الأماكن اللي الناس بتنساها: الـ backups، والـ log pipelines، وexports الـ analytics، وأدوات الـ support كلها بتتحسب. وأخيرًا خليها آلية: قاعدة في wiki مش هتعمل حاجة الساعة 2 بالليل. الراوتر تحت بيرمي ResidencyViolation قبل ما أي write يخرج من الـ region، والـ tenant المجهول بيعمل fail closed، والجدول اللي من غير data class مرفوض، والـ CI check بيوقّع الـ build لو أي مخزن فيه بيانات EU قاعد في مكان تاني، و CHECK constraint في الـ database آخر خط لو الراوتر فيه bug.

فين هستخدمه في شغلي؟ شركة SaaS مصرية بدأت تبيع لعميل ألماني والعقد فيه "البيانات تفضل في الاتحاد الأوروبي". هنا مش كفاية تعمل Postgres في Frankfurt. راجع: الـ backups بتروح فين؟ الـ logs بتتبعت لأي Sentry/Datadog وفي أنهي region؟ مين من الـ support بيقدر يفتح الـ data ومن أنهي بلد؟ وفي الكود: tenant_id إجباري في كل query و middleware بيرفض الـ region الغلط، زي الـ multitenancy في قسم 07.
Backups and logs count A correctly pinned primary with a backup bucket in another region, or logs shipped to a global SaaS with customer emails in them, is a residency failure the database never sees. Put every store in the map the CI check reads.
Primary متثبت صح مع backup bucket في region تانية، أو logs رايحة لـ SaaS عالمي وفيها إيميلات عملاء، ده فشل residency الـ database عمره ما هتشوفه. حط كل مخزن في الـ map اللي الـ CI check بيقراها.

Part 6 — Patterns 🔴 Advancedالجزء 6 — الأنماط وإمتى كل واحد

English

Most systems end up with one of four shapes. In single home per user, each user's rows live in one region, reads and writes go there, and writes never conflict. Cross-region queries get expensive. In read local, write home, replicas serve reads nearby while all writes go to one region: simple, with reads possibly stale. Active-active with conflict handling lets every region accept writes and resolves conflicts with LWW, merges or CRDTs: lowest write latency and the most moving parts. And consensus across regions gives strong consistency with a write latency of at least one inter-region round trip, which is what Spanner and CockroachDB's geo-partitioning are built around. Those two are named here and not run here.

The calculator below turns assumed inputs into a table, and every figure in it comes from those inputs, so replace them with your own. Two things are worth noticing: read-replica setups get cheap reads and leave writes where they were, and strong consensus buys an RPO of 0 with every write paying the inter-region trip. The cost column is a rough multiple of a single-region deployment, including the extra replication traffic and operational headcount that a price calculator tends to leave out.

The evolution order is the actual advice. Start in one region. Add read replicas when latency for far users or read load justifies it. Split users or tenants by home region when data volume, residency contracts or write latency require it. Active-active comes last, only when you have a specific reason to take writes in two places at once, and only for the data that can tolerate merging. Each step is cheap to do later and expensive to undo.

بالعامية

أغلب الأنظمة بتوصل لواحد من 4 أشكال. Single home per user: صفوف كل مستخدم في region واحدة، والقراية والكتابة هناك، ومفيش conflicts على الكتابة، بس الـ queries بين الـ regions غالية. Read local, write home: الـ replicas بتخدم القراية القريبة وكل الكتابات بتروح لـ region واحدة: بسيط، والقراية ممكن تبقى قديمة. Active-active مع conflict handling: كل region بتقبل كتابة وبنحل الـ conflicts بـ LWW أو merge أو CRDT: أقل latency للكتابة وأكتر تعقيد. و consensus بين الـ regions: strong consistency والكتابة بتدفع على الأقل رحلة واحدة بين الـ regions، وده اللي Spanner و geo-partitioning بتاع CockroachDB مبنيين عليه. الاتنين دول بنذكرهم بالاسم بس و not run here.

الآلة الحاسبة بتحوّل فرضيات لجدول، وكل رقم جاي من الفرضيات دي، فحط أرقامك. حاجتين مهمين: الـ read replicas بتدي قراية رخيصة والكتابة بتفضل زي ما هي، والـ consensus بيدي RPO صفر بس كل كتابة بتدفع الرحلة بين الـ regions. وعمود التكلفة تقدير تقريبي لمضاعفة region واحدة، ومعاها traffic الـ replication والناس اللي هتشغّل، اللي آلات حساب الأسعار بتنسى تحسبهم.

ترتيب التطور ده هو النصيحة الفعلية. ابدأ بـ region واحدة. ضيف read replicas لما الـ latency للمستخدمين البعيدين أو حمل القراية يبرر ده. قسّم المستخدمين أو الـ tenants بـ home region لما حجم الـ data أو عقود الـ residency أو latency الكتابة يطلبوا ده. والـ active-active في الآخر خالص، لما يبقى عندك سبب محدد تقبل كتابة في مكانين في نفس الوقت، وعلى الـ data اللي تستحمل الدمج بس. كل خطوة رخيصة لو عملتها بعدين، وغالية لو حبيت ترجع فيها.

فين هستخدمه في شغلي؟ لما الـ CTO يقول "لازم نبقى global". اسأله بالأرقام: كام في المية من الـ traffic بره region الـ database؟ كام ms بيخسروا؟ فيه عقد residency؟ لو 85% من المستخدمين في مصر والخليج، region قريبة ومعاها CDN أهم بكتير من active-active. واكتب القرار في ADR بالأرقام، زي project/adr/، عشان اللي يجي بعدك يعرف ليه وإمتى يعيد التفكير.
Keep the option cheap Put region on the user or tenant from day one, even with one region: it's a column and a default. Then splitting by region later is a data move and a router, instead of a schema migration across every table.
حط region على المستخدم أو الـ tenant من أول يوم، حتى لو عندك region واحدة: عمود وقيمة default. وساعتها التقسيم بعدين هيبقى نقل data وراوتر، بدل migration لكل جدول.

Solution · الحل 
import assert from "node:assert/strict";
import { test } from "node:test";
import fc from "fast-check";
import { orAdd, orEmpty, orMerge, orValues, pnEmpty, pnInc, pnMerge, pnValue, type ORSet, type PNCounter } from "./crdt.ts";

// عربة كاملة: OR-Set للأصناف و PN-Counter للكمية بتاعة كل صنف
interface Cart { items: ORSet; qty: Record<string, PNCounter> }
const empty = (): Cart => ({ items: orEmpty(), qty: {} });

function addLine(c: Cart, sku: string, region: string, tag: string, by: number): Cart {
  const current = c.qty[sku] ?? pnEmpty();
  return { items: orAdd(c.items, sku, tag), qty: { ...c.qty, [sku]: pnInc(current, region, by) } };
}

function mergeCart(a: Cart, b: Cart): Cart {
  const qty: Record<string, PNCounter> = { ...a.qty };
  for (const [sku, q] of Object.entries(b.qty)) qty[sku] = pnMerge(qty[sku] ?? pnEmpty(), q);
  return { items: orMerge(a.items, b.items), qty };
}

const view = (c: Cart) => orValues(c.items).map((sku) => [sku, pnValue(c.qty[sku] ?? pnEmpty())]);

let tag = 0;
const cart: fc.Arbitrary<Cart> = fc
  .array(fc.tuple(fc.constantFrom("sku-1", "sku-2"), fc.constantFrom("eu", "us"), fc.integer({ min: 1, max: 5 })), { maxLength: 10 })
  .map((ops) => ops.reduce((c, [sku, r, by]) => addLine(c, sku, r, `t${++tag}`, by), empty()));

test("cart merge is commutative", () => {
  fc.assert(fc.property(cart, cart, (a, b) => assert.deepEqual(view(mergeCart(a, b)), view(mergeCart(b, a)))), { numRuns: 300 });
});

test("two regions adding the same item keep both quantities", () => {
  const eu = addLine(empty(), "sku-1", "eu", "e1", 2);
  const us = addLine(empty(), "sku-1", "us", "u1", 3);
  assert.deepEqual(view(mergeCart(eu, us)), [["sku-1", 5]]);
});

Cheat sheet · الخلاصة

  • Latency is per round trip: never split the app from its data. 5 queries across a 90 ms link cost ≈493 ms, and one round trip ≈92 ms (measured through a delay proxy).
  • Give each user or tenant a home region; only a directory and the tenants table stay global, and a keyed email hash is still personal data.
  • Replication lag is at least the one-way delay plus apply time, and it grows with burst size and link limits (204 ms, then 1.8 s under a 1 MB/s cap).
  • Read-your-writes failed 40/40 from a far replica. Sticky reads or an LSN token fix it (0/40), and a token needs a timeout and a fallback.
  • LWW converges, and loses data: 71 lost updates at 100 ms lag, 1,593 at 5 s skew (simulation).
  • LWW is fine for replaceable snapshots. Use domain merges for anything a person expects to keep.
  • CRDTs converge through commutative, associative, idempotent merges. Test the laws with property tests.
  • CRDTs can't enforce invariants: a balance reached -50 after a merge. Metadata grows: 157,824 bytes for one element after 10,000 cycles.
  • GDPR restricts transfers, it doesn't demand local storage. Remote access from a third country counts as a transfer. Check other countries' official text.
  • Residency covers backups, logs, exports and support access. Enforce it with a router that throws, a CI check and a database constraint.
  • Evolution: one region → read replicas → home regions → active-active only where you can merge. Put a region column in from day one.
