Why this matters · ليه ده مهم

English

Booking is the cleanest test of whether you understand concurrency, because the bug is visible to a customer standing at a hotel desk with a confirmation for a room that does not exist. It has a small write volume and a huge read spike, which forces you to separate "what we show" from "what we promise". The same shape appears at work wherever stock is limited: coupons with a redemption cap, flash sales, appointment slots, the last unit of a product.

بالعامية

الـ booking هو أنضف اختبار لفهمك للـ concurrency، لأن الـ bug بيبان لعميل واقف قدام الريسبشن ومعاه تأكيد لغرفة مش موجودة. عدد الكتابات صغير وموجة القراية ضخمة، وده بيجبرك تفصل بين "اللي بنعرضه" و"اللي بنوعد بيه". ونفس الشكل هتلاقيه في شغلك في أي حاجة كميتها محدودة: كوبونات ليها حد استخدام، flash sales، مواعيد حجز، آخر قطعة من منتج.

English

Requirements with numbers. No double sale, ever. Hold a seat for 10 minutes while the user pays. Availability reads may be a few seconds stale; the booking decision may not. Target p95 under 300 ms for a hold, and keep the system up during the spike even if most users wait.

Read the spike correctly. 200,000 arrivals in a minute is about 3,300 per second on average, and several times that in the first seconds. Only 10,000 writes can ever succeed, about 5% of users. So the job is mostly saying no cheaply and letting a fixed rate through. The calculator also shows the limit of one hot counter row: at 3 ms per commit it takes 30 seconds to sell out through a single row, which is fine for correctness and the reason a queue in front is needed.

Inventory model, the first real decision. Numbered seats get one row per seat, so a primary key gives you a free uniqueness guarantee. General admission and hotels use counts: one row per room type per day. Counts are compact, and they make the multi-night booking an all-or-nothing update across several rows.

بالعامية

المتطلبات بالأرقام. مفيش كرسي يتباع مرتين، أبدًا. احجز الكرسي 10 دقايق واليوزر بيدفع. قراية المتاح ممكن تبقى قديمة بكام ثانية، بس قرار الحجز لأ. الهدف p95 أقل من 300ms للـ hold، والنظام يفضل شغال وقت الموجة حتى لو أغلب الناس مستنية.

افهم الموجة صح. 200,000 وصول في دقيقة يعني حوالي 3300 في الثانية متوسط، وأضعاف ده في أول ثواني. و10,000 كتابة بس هي اللي ممكن تنجح، يعني حوالي 5% من اليوزرز. فالشغل أغلبه إنك تقول لأ برخص وتدخّل معدل ثابت. والـ calculator بيوضح حدود صف العدّاد الواحد: بـ 3ms للـ commit، بيع الكل عن طريق صف واحد بياخد 30 ثانية، وده مقبول للصح وهو السبب إننا محتاجين طابور قدامه.

نموذج الـ inventory هو أول قرار حقيقي. الكراسي المرقمة صف لكل كرسي، فالـ primary key بيديك uniqueness ببلاش. الـ general admission والفنادق بالعدد: صف لكل نوع غرفة لكل يوم. العدد صغير الحجم، وبيخلي الحجز كذا ليلة update كله أو ولا حاجة على كذا صف.

فين هستخدمه في شغلي؟ لو البيزنس طلب "كوبون لأول 500 عميل"، ده نفس المسألة بالظبط بنموذج count. احسب الأول: كام طلب في الثانية وكام نجاح ممكن، وقول الـ ratio في الـ design review. لو 95% هيترفضوا، رفضهم لازم يبقى أرخص حاجة في النظام.

Part 2 — The bug 🔴 Advancedالجزء 2 — الـ bug

English

The naive flow reads the available count, checks it, inserts a booking and decrements. Under concurrency, many requests read the same number before any of them writes, so they all pass the check. This is the lost-update and check-then-act family from section 07 · 2.4.

Wrapping the same code in BEGIN/COMMIT does not fix it. Under Postgres's default Read Committed, a plain SELECT takes no lock and sees the latest committed value, so the check is still based on a number that can already be wrong. The transaction only makes the insert and the decrement atomic with each other.

The harness below is the double-booking test you keep for the rest of the lesson: same number of users, same seats, and it counts what actually got sold on real Postgres. Keep a test like this in your own suite, because this bug does not appear in a single-user test.

// الـ harness ده هو اختبار الـ double booking اللي هتفضل تستخدمه طول الدرس
import type pg from "pg";

export interface Outcome { ok: boolean; soldOut?: boolean; retries?: number; deadlocks?: number }
export type BookFn = (db: pg.Pool, eventId: number, userId: number) => Promise<Outcome>;

export const SCHEMA = `
  CREATE TABLE IF NOT EXISTS ticket_inventory (
    event_id  bigint PRIMARY KEY,
    total     int NOT NULL,
    available int NOT NULL,
    version   int NOT NULL DEFAULT 0
  );
  CREATE TABLE IF NOT EXISTS bookings (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_id bigint NOT NULL,
    user_id  bigint NOT NULL
  );
  CREATE INDEX IF NOT EXISTS bookings_event_idx ON bookings (event_id);
`;

let nextEvent = 1;

export async function runHarness(db: pg.Pool, name: string, book: BookFn, opts: { users: number; seats: number }) {
  const eventId = nextEvent++;
  await db.query(`INSERT INTO ticket_inventory (event_id, total, available) VALUES ($1, $2, $2)`, [eventId, opts.seats]);
  const lat: number[] = [];
  const started = performance.now();
  const results = await Promise.all(
    Array.from({ length: opts.users }, async (_, userId) => {
      const t = performance.now();
      const r = await book(db, eventId, userId);
      lat.push(performance.now() - t);
      return r;
    }),
  );
  const secs = (performance.now() - started) / 1000;
  lat.sort((a, b) => a - b);
  const row = (await db.query(`SELECT available FROM ticket_inventory WHERE event_id = $1`, [eventId])).rows[0];
  const sold = (await db.query(`SELECT count(*)::int AS n FROM bookings WHERE event_id = $1`, [eventId])).rows[0].n as number;
  return {
    name,
    sold,
    oversold: Math.max(0, sold - opts.seats),
    available: row.available as number,
    told_ok: results.filter((r) => r.ok).length,
    retries: results.reduce((s, r) => s + (r.retries ?? 0), 0),
    secs,
    tps: opts.users / secs,
    p50: lat[lat.length >> 1]!,
    p99: lat[Math.floor(lat.length * 0.99)]!,
  };
}

الـ flow الساذج بيقرا العدد المتاح، يتأكد، يعمل booking، وينقص. تحت الـ concurrency، طلبات كتير بتقرا نفس الرقم قبل ما حد فيهم يكتب، فكلهم بيعدوا الشرط. دي عيلة الـ lost update والـ check-then-act من قسم 07 · 2.4.

تغليف نفس الكود بـ BEGIN/COMMIT مبيحلّهوش. في الـ Read Committed الافتراضي بتاع Postgres، الـ SELECT العادي مبياخدش lock وبيشوف آخر قيمة اتعملها commit، فالشرط لسه مبني على رقم ممكن يكون غلط. الـ transaction بتخلي الـ insert والنقصان atomic مع بعض وبس.

الـ harness ده هو اختبار الـ double booking اللي هتفضل تستخدمه طول الدرس: نفس عدد اليوزرز ونفس الكراسي، وبيعدّ اللي اتباع فعلًا على Postgres حقيقي. خلي اختبار زي ده في الـ suite بتاعك، لأن الـ bug ده مبيظهرش في اختبار بيوزر واحد.

Part 3 — Three strategies, measured 🔴 Advancedالجزء 3 — 3 استراتيجيات بالقياس

English

Pessimistic: SELECT ... FOR UPDATE takes the row lock before reading, so the others queue behind it. Optimistic: read a version, then UPDATE ... WHERE version = $read and retry when zero rows change. Atomic: put the condition and the change in one statement, UPDATE ... WHERE available > 0, with the booking insert in a CTE. Details of each are in section 07 · 2.4; here they run on the same harness.

All three sold exactly the right number in every round, so correctness does not separate them. Contention does. The atomic statement needs one round trip while it holds the row lock. FOR UPDATE needs several round trips inside its transaction, so the lock is held longer. Optimistic has no lock to wait for, but under high contention nearly every attempt fails and is repeated. At 2,000 users it did 626,465 retries and the median request took about 56 seconds. That is the core lesson: optimistic locking suits low contention, such as two people editing a profile, and collapses when everyone wants the same row.

Deadlock risk appears when one booking locks several rows. Two users booking seats 5 and 6 in opposite orders produce a real 40P01; locking in a sorted order removes it. Hotel date ranges use a Postgres exclusion constraint: EXCLUDE USING gist (room_id WITH =, stay WITH &&) with btree_gist. Half-open ranges [) make the checkout day available for the next guest. Defence in depth: the constraint holds even when application code is wrong, and the run below proves it with deliberately buggy code.

// (1) الـ pessimistic: الـ lock بيتاخد قبل القراية
export const forUpdate: BookFn = async (db, eventId, userId) => {
  const c = await db.connect();
  try {
    await c.query("BEGIN");
    const { rows } = await c.query(`SELECT available FROM ticket_inventory WHERE event_id = $1 FOR UPDATE`, [eventId]);
    if (rows[0].available <= 0) { await c.query("ROLLBACK"); return { ok: false, soldOut: true }; }
    await c.query(`INSERT INTO bookings (event_id, user_id) VALUES ($1, $2)`, [eventId, userId]);
    await c.query(`UPDATE ticket_inventory SET available = available - 1 WHERE event_id = $1`, [eventId]);
    await c.query("COMMIT");
    return { ok: true };
  } finally {
    c.release();
  }
};

// (2) الـ optimistic: لو الـ version اتغير نعيد من الأول
export const optimistic: BookFn = async (db, eventId, userId) => {
  let retries = 0;
  for (;;) {
    const { rows } = await db.query(`SELECT available, version FROM ticket_inventory WHERE event_id = $1`, [eventId]);
    if (rows[0].available <= 0) return { ok: false, soldOut: true, retries };
    const c = await db.connect();
    try {
      await c.query("BEGIN");
      const moved = await c.query(
        `UPDATE ticket_inventory SET available = available - 1, version = version + 1 WHERE event_id = $1 AND version = $2`,
        [eventId, rows[0].version],
      );
      if (moved.rowCount === 1) {
        await c.query(`INSERT INTO bookings (event_id, user_id) VALUES ($1, $2)`, [eventId, userId]);
        await c.query("COMMIT");
        return { ok: true, retries };
      }
      await c.query("ROLLBACK");
    } finally {
      c.release();
    }
    retries++;
    // الـ jitter بيفرّق الناس عشان ميتصادموش تاني في نفس اللحظة
    await sleep(Math.random() * Math.min(50, 2 ** Math.min(retries, 6)));
  }
};

// (3) الذري: الشرط والتعديل والحجز في statement واحد
export const atomicUpdate: BookFn = async (db, eventId, userId) => {
  const r = await db.query(
    `WITH claimed AS (
       UPDATE ticket_inventory SET available = available - 1
        WHERE event_id = $1 AND available > 0 RETURNING event_id)
     INSERT INTO bookings (event_id, user_id) SELECT event_id, $2 FROM claimed`,
    [eventId, userId],
  );
  return r.rowCount === 1 ? { ok: true } : { ok: false, soldOut: true };
};

Pessimistic: SELECT ... FOR UPDATE بياخد الـ row lock قبل القراية، فالباقي بيقف طابور وراه. Optimistic: اقرا version، وبعدين UPDATE ... WHERE version = $read ولو 0 صفوف اتغيروا أعد تاني. Atomic: الشرط والتعديل في statement واحد، UPDATE ... WHERE available > 0، والـ insert بتاع الحجز في CTE. تفاصيل كل واحدة في قسم 07 · 2.4، وهنا بنشغّلهم على نفس الـ harness.

الـ 3 باعوا الرقم الصح بالظبط في كل جولة، فالصح مش هو اللي بيفرّق. الـ contention هو اللي بيفرّق. الـ statement الذري محتاج round trip واحد وهو ماسك الـ row lock. الـ FOR UPDATE محتاج كذا round trip جوه الـ transaction، فالـ lock بيتمسك أطول. الـ optimistic مفيهوش lock يستنى عليه، بس تحت contention عالي تقريبًا كل محاولة بتفشل وبتتعاد. عند 2000 يوزر عمل 626,465 retry والطلب الوسيط خد حوالي 56 ثانية. ده الدرس الأساسي: الـ optimistic locking مناسب للـ contention القليل، زي اتنين بيعدلوا profile، وبيقع لما الكل عايز نفس الصف.

خطر الـ deadlock بيظهر لما حجز واحد بيقفل كذا صف. اتنين بيحجزوا كرسي 5 و6 بترتيب عكسي عملوا 40P01 حقيقي، والقفل بترتيب ثابت بيشيله. مدى تواريخ الفندق بيستخدم exclusion constraint في Postgres: EXCLUDE USING gist (room_id WITH =, stay WITH &&) مع btree_gist. والـ ranges النص مفتوحة [) بتخلي يوم الخروج متاح للضيف اللي بعده. Defence in depth: القيد شغال حتى لو كود التطبيق غلط، والتشغيل فوق بيثبت ده بكود غلط عن قصد.

فين هستخدمه في شغلي؟ لو عندك خصم رصيد، أو مخزون منتج، أو حد استخدام كوبون: ابدأ بالـ atomic UPDATE ... WHERE الأول، لأنه الأبسط والأسرع. استخدم FOR UPDATE لو القرار محتاج أكتر من صف. ولو عندك مواعيد أو حجوزات بمدى زمني، حط exclusion constraint حتى لو الكود شايل الموضوع. والغلطة الشائعة: تختار optimistic locking لأنه "من غير locks" في مكان كله تصادم، فتاخد retries بالآلاف.

Part 4 — Holds with a TTL 🔴 Advancedالجزء 4 — الحجز المؤقت بـ TTL

English

A user needs minutes to pay, so the seat is held rather than sold. Check expiry at read time in the same statement that claims the seat: a seat counts as free when it is free or its hold has expired. Then correctness never depends on a background job running on time. The confirm statement also checks that the hold is still valid, so a late payer gets zero rows. A cleanup job still runs, but only to tidy rows and keep counts accurate.

A count-based model is different. If you decrement available when a hold is taken, stock returns only when the job adds it back, so a dead cleanup job silently leaks inventory. That is the argument for per-seat rows or for deriving availability from the holds table.

Redis as a pre-filter. A counter in Redis rejects the 95% who cannot win without touching Postgres. Postgres stays the truth: the gate only decides who is allowed to ask. Two traps: DECR on a missing key returns -1, so a lost key looks like "sold out" for everyone, and a request that dies after the gate leaves the counter too low. The script handles a missing key by passing through to the database, and a reconcile job resets the counter from Postgres.

Waiting room. Give each arrival an atomic ticket number with INCR and admit at a fixed rate by raising an admitted counter. A user's position is ticket - admitted, and admission hands out a signed token that the booking API requires. Rate limiting per user is in lesson 25.

اليوزر محتاج دقايق عشان يدفع، فالكرسي بيتحجز مؤقتًا مش بيتباع. افحص الـ expiry وقت القراية في نفس الـ statement اللي بياخد الكرسي: الكرسي يتحسب فاضي لو free أو الحجز بتاعه خلص. كده الصح مش معتمد على job شغال في ميعاده. والـ confirm كمان بيتأكد إن الحجز لسه شغال، فاللي بيدفع متأخر بياخد 0 صفوف. الـ job لسه موجود، بس عشان ينضف الصفوف ويظبط العدادات.

نموذج العدد مختلف. لو بتنقّص available وقت الـ hold، المخزون بيرجع بس لما الـ job يزوّده، فلو الـ job وقع المخزون بيضيع في صمت. وده السبب إننا بنفضّل صف لكل كرسي أو نحسب المتاح من جدول الـ holds.

Redis كـ pre-filter. عدّاد في Redis بيرفض الـ 95% اللي مش هيكسبوا من غير ما يلمس Postgres. Postgres تفضل هي الحقيقة، والـ gate بيحدد مين مسموح له يسأل بس. فخّين: DECR على مفتاح مش موجود بيرجع -1، فالمفتاح الضايع بيبان "sold out" للكل، والطلب اللي بيموت بعد الـ gate بيسيب العدّاد أقل من الحقيقة. الـ script بيعدّي الطلب للـ DB لو المفتاح مش موجود، والـ reconcile job بيرجّع العدّاد من Postgres.

غرفة الانتظار. كل واحد بياخد رقم تذكرة ذري بـ INCR، وبتدخّل الناس بمعدل ثابت بزيادة عدّاد admitted. مكان اليوزر هو ticket - admitted، والدخول بيدي token موقّع والـ booking API بيطلبه. الـ rate limiting لكل يوزر في درس 25.

فين هستخدمه في شغلي؟ أي "حجز مؤقت": cart بيحجز مخزون، حجز ميعاد لحد ما يتأكد، reservation في checkout. اسأل: لو الـ cron وقع ساعة، إيه اللي بيحصل؟ لو الإجابة "المخزون بيفضل محجوز"، يبقى الـ expiry لازم يتفحص وقت القراية. والغلطة الشائعة: تعتبر Redis هو مصدر الحقيقة في الـ stock، فلما يتعمله restart أو يفقد المفتاح تبيع غلط أو توقف البيع كله.
Trade-off: how long is a hold? Too short and honest users lose seats mid-payment. Too long and bots or abandoned carts keep inventory off the market. A common range is 5 to 15 minutes. Also tie it to the PSP: a payment page that can outlive the hold produces the late-payment case in Part 5.
لو قصير، الناس المحترمين هيخسروا الكرسي وهما بيدفعوا. لو طويل، الـ bots والـ carts المهجورة بتحبس المخزون. المدى الشائع من 5 لـ 15 دقيقة. وكمان اربطها بالـ PSP: صفحة دفع تعيش أطول من الحجز بتعمل حالة الدفع المتأخر اللي في الجزء 5.

Part 5 — Payment integration 🔴 Advancedالجزء 5 — ربط الدفع

English

A booking is a saga with three steps: hold, pay, confirm (lesson 34, code in section 08 · 3.3). The payment internals are the previous lesson. Each step has a compensation: a declined card releases the hold, and a hold that is no longer valid when the money arrives triggers a refund. The key decisions are the failure paths.

Idempotent booking. The same Idempotency-Key must return the same booking. A unique constraint with ON CONFLICT DO NOTHING makes the second request wait for the first, then find the row.

Timeouts on the PSP. A timeout after charging leaves an unknown outcome, so do not release the hold. Query the PSP first. Releasing it would give the seat to someone else while this customer's money may already have moved.

The late webhook. The payment succeeds after the hold expired and the seat was resold. Confirm returns zero rows, the booking moves to REFUND_PENDING in the same transaction, and a refund goes out with its own stable key. Recording the intent first means a crash cannot lose the refund, and a job finishes anything left. Prevent most of these by making the payment page expire before the hold. Check your PSP: Stripe Checkout's expires_at must be at least 30 minutes ahead, so with a 10-minute hold you call its expire endpoint when the hold ends, or you lengthen the hold.

async function pspPost<T>(path: string, body: unknown, key: string): Promise<T> {

interface Booking { id: string; status: string; seat_no: number; user_id: string; event_id: string }

export async function startBooking(key: string, userId: number, seat: number, ttl: string): Promise<Booking> {
  const c = await db.connect();
  try {
    await c.query("BEGIN");
    // نفس الـ key مرتين: التانية بتستنى الأولى تخلص وبعدين مبتعملش حاجة
    const ins = await c.query<Booking>(
      `INSERT INTO bookings (idempotency_key, event_id, seat_no, user_id) VALUES ($1, 1, $2, $3)
       ON CONFLICT (idempotency_key) DO NOTHING RETURNING *`,
      [key, seat, userId],
    );
    if (ins.rowCount === 0) {
      await c.query("COMMIT");
      return (await db.query<Booking>(`SELECT * FROM bookings WHERE idempotency_key = $1`, [key])).rows[0]!;
    }
    const held = await c.query(
      `UPDATE seats SET status = 'held', held_by = $2, hold_expires_at = now() + $3::interval
        WHERE event_id = 1 AND seat_no = $1 AND (status = 'free' OR (status = 'held' AND hold_expires_at < now()))`,
      [seat, userId, ttl],
    );
    if (held.rowCount === 0) await c.query(`UPDATE bookings SET status = 'REJECTED' WHERE id = $1`, [ins.rows[0]!.id]);
    await c.query("COMMIT");
    return { ...ins.rows[0]!, status: held.rowCount === 0 ? "REJECTED" : "HELD" };
  } finally {
    c.release();
  }
}

export async function onPaymentSucceeded(bookingId: string, pspRef: string, webhookId?: string): Promise<string> {
  const c = await db.connect();
  let refundNeeded = false;
  try {
    await c.query("BEGIN");
    if (webhookId) {
      const fresh = await c.query(`INSERT INTO processed_webhooks VALUES ($1) ON CONFLICT DO NOTHING`, [webhookId]);
      if (fresh.rowCount === 0) { await c.query("COMMIT"); return "duplicate-webhook"; }
    }
    const b = (await c.query<Booking>(`SELECT * FROM bookings WHERE id = $1 FOR UPDATE`, [bookingId])).rows[0]!;
    if (b.status !== "HELD") { await c.query("COMMIT"); return `already-${b.status}`; }
    // الـ confirm الذري: الكرسي لسه ماسكه نفس اليوزر والوقت لسه مخلصش
    const sold = await c.query(
      `UPDATE seats SET status = 'sold', hold_expires_at = NULL
        WHERE event_id = 1 AND seat_no = $1 AND held_by = $2 AND status = 'held' AND hold_expires_at > now()`,
      [b.seat_no, b.user_id],
    );
    if (sold.rowCount === 1) {
      await c.query(`UPDATE bookings SET status = 'CONFIRMED', psp_ref = $2 WHERE id = $1`, [bookingId, pspRef]);
    } else {
      // الفلوس اتخصمت بس الكرسي راح: نسجل النية قبل الـ refund عشان ميضيعش لو وقعنا
      await c.query(`UPDATE bookings SET status = 'REFUND_PENDING', psp_ref = $2 WHERE id = $1`, [bookingId, pspRef]);
      refundNeeded = true;
    }
    await c.query("COMMIT");
  } finally {
    c.release();
  }
  if (!refundNeeded) return "confirmed";
  await runRefunds();
  return "refund-path";
}

// بيتنادى بعد الـ commit وكمان كل دقيقة من job، فالـ crash هنا مبيضيّعش refund
export async function runRefunds(): Promise<void> {
  const { rows } = await db.query(`SELECT id, psp_ref FROM bookings WHERE status = 'REFUND_PENDING'`);
  for (const b of rows) {
    try {
      await pspPost("/refunds", { chargeRef: b.psp_ref }, `booking:${b.id}:refund`);
      await db.query(`UPDATE bookings SET status = 'REFUNDED' WHERE id = $1 AND status = 'REFUND_PENDING'`, [b.id]);
    } catch (err) {
      if (!(err instanceof Unknown)) throw err;
    }
  }
}

const reference = (id: string) => `booking-${id}`;
export async function chargeBooking(b: Booking): Promise<string> {
  try {
    const charge = await pspPost<Charge>("/charges", { reference: reference(b.id), amountMinor: 75_000 }, `booking:${b.id}:charge`);
    return await onPaymentSucceeded(b.id, charge.ref);
  } catch (err) {
    if (err instanceof Declined) {
      // خطوة التعويض في الـ saga: رجّع الكرسي وعلّم الحجز
      await db.query(`UPDATE bookings SET status = 'PAYMENT_FAILED' WHERE id = $1`, [b.id]);
      await releaseHold(b);
      return "declined-hold-released";
    }
    if (err instanceof Unknown) return "unknown-keep-hold";
    throw err;
  }
}

بالعامية

الحجز saga من 3 خطوات: hold، pay، confirm (درس 34، والكود في قسم 08 · 3.3). تفاصيل الدفع نفسها في الدرس اللي فات. كل خطوة ليها تعويض: الكارت المرفوض بيرجّع الكرسي، والحجز اللي مبقاش صالح لما الفلوس توصل بيعمل refund. القرارات المهمة كلها في مسارات الفشل.

الحجز idempotent. نفس الـ Idempotency-Key لازم يرجّع نفس الـ booking. unique constraint مع ON CONFLICT DO NOTHING بيخلي الطلب التاني يستنى الأول وبعدين يلاقي الصف.

الـ timeouts مع الـ PSP. الـ timeout بعد الخصم نتيجته مجهولة، فـمتعملش release للـ hold. اسأل الـ PSP الأول. لو رجّعته، الكرسي هيروح لحد تاني وفلوس العميل ده ممكن تكون اتحركت فعلًا.

الـ webhook المتأخر. الدفع نجح بعد ما الحجز خلص والكرسي اتباع. الـ confirm بيرجّع 0 صفوف، والـ booking بيروح REFUND_PENDING في نفس الـ transaction، والـ refund بيطلع بـ key ثابت خاص بيه. تسجيل النية الأول معناه إن الـ crash مش هيضيّع الـ refund، والـ job بيكمّل اللي فاضل. وتقدر تمنع أغلب الحالات دي بإن صفحة الدفع تنتهي قبل الحجز. راجع الـ PSP بتاعك: في Stripe Checkout الـ expires_at لازم يبقى بعد 30 دقيقة على الأقل، فمع hold 10 دقايق هتنادي الـ expire endpoint لما الحجز يخلص، أو تطوّل الحجز.

فين هستخدمه في شغلي؟ أي checkout بيحجز مخزون قبل الدفع: اكتب على ورقة جدول "لو X حصل بعد Y"، زي دفع بعد انتهاء الحجز، وفشل بعد الخصم. كل خلية محتاجة إجراء، وأهم خلية عند الماليات هي اللي فيها refund. والغلطة الشائعة: catch (timeout) { releaseSeat(); }، وده بيدي الكرسي لحد تاني والفلوس لسه ممكن تكون اتخصمت.
Interview question "The user paid, but the hold expired and the seat was sold to someone else. What happens?" → Confirm is a conditional update that affects zero rows, so the booking goes to refund pending in the same transaction and a refund is sent with its own key, retried by a job until it succeeds. The second buyer keeps the seat. Then shorten the payment window so this stays rare.
"اليوزر دفع، بس الحجز خلص والكرسي اتباع لحد تاني. إيه اللي بيحصل؟" ← الـ confirm هو update مشروط بيأثر على 0 صفوف، فالـ booking بيروح refund pending في نفس الـ transaction، والـ refund بيتبعت بـ key خاص بيه، وjob بيعيده لحد ما ينجح. المشتري التاني بيفضل معاه الكرسي. وبعدين قصّر وقت الدفع عشان الحالة دي تفضل نادرة.

Part 6 — Trade-offs and review 🔴 Advancedالجزء 6 — الـ trade-offs والمراجعة

English

Availability reads from a stale replica are fine, because the booking decision is not. Reading the seat map from a replica or a cache takes most of the read load off the primary. The run below uses a real standby with a 1.5-second apply delay: it reports 5 seats after the primary has sold them all, and the user's booking attempt still lands on the primary and is refused, with nothing oversold. The cost is an occasional "that seat just went" message, so design the UI for it. Replication itself is in lesson 12.

Fairness and bots. Pure first-come rewards whoever has the fastest script. In the labelled simulation, bots take 98.1% of the tickets with no per-user limit, 40% with a limit of 2, and 1.8% with a limit of 2 plus a randomized queue. Randomizing the waiting room at start time turns a speed contest into a lottery. Add account age, payment-card limits and CAPTCHA at the edge.

What breaks first at 10× (2M users in a minute, a burst near 167k arrivals per second): the waiting room's own front door, so serve it from a CDN or edge workers, then the booking API. Next is the Redis counter's hot key and, for general admission, the single inventory row, which you split into N bucket rows. The calculator shows 10 buckets giving about 3,300 writes a second. For hotels, search across 14.6 million rows moves to a read model.

let deadlocks = 0;
export async function bookSeats(userId: number, seats: number[]): Promise<boolean> {
  const c = await db.connect();
  try {
    await c.query("BEGIN");
    // الـ ORDER BY جوه الـ subquery بياخد الـ locks بترتيب ثابت
    const r = await c.query(
      `UPDATE seats SET status = 'sold', booked_by = $1
        WHERE event_id = 1 AND status = 'free' AND seat_no IN (
          SELECT seat_no FROM seats WHERE event_id = 1 AND seat_no = ANY($2::int[]) ORDER BY seat_no FOR UPDATE)`,
      [userId, seats],
    );
    // لو كرسي واحد ناقص نرجّع الباقي، فمفيش حجز نص نص
    if (r.rowCount !== seats.length) { await c.query("ROLLBACK"); return false; }
    await c.query("COMMIT");
    return true;
  } catch (err) {
    await c.query("ROLLBACK");
    if ((err as { code: string }).code !== "40P01") throw err;
    deadlocks++;
    return false;
  } finally {
    c.release();
  }
}

async function holdWithLimit(userId: number, seat: number): Promise<string> {
  const c = await db.connect();
  try {
    await c.query("BEGIN");
    // الـ lock ده بيتحرر لوحده مع نهاية الـ transaction
    await c.query(`SELECT pg_advisory_xact_lock(1, $1::int)`, [userId]);
    const { rows } = await c.query(`SELECT count(*)::int AS n FROM seats WHERE event_id = 1 AND held_by = $1`, [userId]);
    if (rows[0].n >= LIMIT) { await c.query("ROLLBACK"); return "over-limit"; }
    const r = await c.query(`UPDATE seats SET status = 'held', held_by = $1 WHERE event_id = 1 AND seat_no = $2 AND status = 'free'`, [userId, seat]);
    await c.query("COMMIT");
    return r.rowCount === 1 ? "held" : "taken";
  } finally {
    c.release();
  }
}

Cheat sheet · الخلاصة

  • Only 5% can win, so most of the design is rejecting cheaply and admitting at a fixed rate.
  • Inventory: per-seat rows for numbered seats, counts per type and day for hotels and general admission.
  • Read-then-write oversells, and BEGIN alone does not fix it.
  • Prefer the atomic UPDATE ... WHERE available > 0. Use FOR UPDATE when you must compute. Keep version for rare conflicts.
  • Lock several rows in a sorted order, or you will meet 40P01.
  • Hotel rooms: EXCLUDE USING gist with half-open ranges, correct even if the app is wrong.
  • Check hold expiry at read and at confirm. The cleanup job is tidying, not correctness.
  • Redis is a pre-filter. Handle a missing key, reconcile from Postgres, and never treat it as truth.
  • A PSP timeout keeps the hold. Query before releasing anything.
  • Late payment after expiry: conditional confirm returns 0 rows, then a refund with its own key.
  • Reads can be stale, the booking decision cannot. Keep decisions on the primary.
  • Per-user limits plus a randomized queue beat bots far better than speed does.
بالعامية
  • 5% بس هيكسبوا، فأغلب التصميم رفض رخيص ودخول بمعدل ثابت.
  • الـ inventory: صف لكل كرسي للكراسي المرقمة، وعدد لكل نوع ويوم للفنادق والـ general admission.
  • القراية وبعدين الكتابة بتبيع زيادة، وBEGIN لوحده مبيحلّهاش.
  • فضّل الـ atomic UPDATE ... WHERE available > 0، واستخدم FOR UPDATE لو لازم تحسب، وخلي الـ version للتصادم النادر.
  • اقفل الصفوف بترتيب ثابت، وإلا هتقابل 40P01.
  • غرف الفندق: EXCLUDE USING gist مع ranges نص مفتوحة، وده صح حتى لو التطبيق غلط.
  • افحص انتهاء الـ hold وقت القراية ووقت الـ confirm، والـ job للتنضيف مش للصح.
  • Redis فلتر قدام الـ DB. اتعامل مع المفتاح الضايع، واعمل reconcile من Postgres، ومتعتبرهوش الحقيقة.
  • الـ timeout من الـ PSP بيسيب الـ hold، واسأل قبل ما ترجّع أي حاجة.
