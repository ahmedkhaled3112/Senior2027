Why this matters · ليه ده مهم

English

Replication is how a database survives a dead machine and serves more reads than one server can. It also causes some of the most expensive incidents in production: a read that misses the write the user just made, a commit that hangs when a standby dies, a failover that quietly loses acknowledged orders, two primaries accepting writes at once. "It's replicated, so it's safe" is exactly the sentence that causes those.

Each of those failures runs below for real, on Postgres 18 with an actual primary and standbys. The multi-leader and leaderless models run as labelled simulations, because Postgres has neither. Streaming versus logical replication and connection pooling were covered in section 07 · replication & read replicas; this lesson is about what the system does when things go wrong.

بالعامية

الـ replication هي الطريقة اللي الـ database بتعيش بيها لو machine وقعت، وبتخدم بيها قراءات أكتر من اللي server واحد يقدر عليه. وهي كمان سبب في أغلى incidents بتحصل في production: قراية مش شايفة الكتابة اللي الـ user لسه عاملها، COMMIT بيتعلق لما standby يقع، failover بيضيّع orders اتأكدت للعميل من غير ما حد ياخد باله، واتنين primary بيقبلوا كتابة في نفس الوقت. جملة "ما هي متعملها replication، يبقى في أمان" هي بالظبط اللي بتسبب ده.

كل المشاكل دي بتتشغّل تحت بجد، على Postgres 18 و primary و standbys حقيقيين. الـ multi-leader والـ leaderless بيشتغلوا كـ simulations متعلّمة بوضوح، لأن Postgres مفيهوش الاتنين دول. الـ streaming مقابل logical والـ connection pooling اتشرحوا في قسم 07: الـ replication والـ read replicas، والدرس ده عن اللي النظام بيعمله لما الدنيا تبوظ.

How the numbers were taken Everything ran on one loaded Windows machine, on loopback. Replication "distance" is a TCP delay proxy, a stand-in for a real network: its real round trip is measured and printed next to each result. Latencies are ≈ medians. The simulations use a seeded PRNG and virtual time so their output repeats exactly.

Part 1 — Primary and replica 🟢 Basicالجزء 1 — الـ primary والـ replica

English

In single-leader replication one node, the primary, accepts all writes and streams its write-ahead log (WAL) to one or more standbys, which replay it. Standbys answer reads and refuse writes, so the read capacity grows with each one added. pg_stat_replication on the primary shows each standby's state and sync_state, and pg_wal_lsn_diff(sent_lsn, replay_lsn) gives the lag in bytes.

The experiment makes lag visible on purpose. pg_wal_replay_pause() stops the standby from applying WAL; it keeps receiving it. One INSERT on the primary gives the only result that matters here: the primary sees 1 row, the replica sees 0, with 424 bytes of lag between them. After resume the replica catches up. A replica is not the same data with a delay you can ignore: for that window it is a different database state.

Streaming versus logical replication, and how the application connects through a pool, are in section 07. In system-design terms, what you get is read scaling and a warm copy for failover. What you do not get is more write capacity: every standby still replays every write.

export function assertSafePort(port) {
  const n = Number(port);
  if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) throw new Error('refusing port ' + port);
  return n;
}

export async function createPrimary({ conf = '', fast = false } = {}) {
  const root = mkdtempSync(path.resolve('pgc-'));
  run(root, 'initdb', ['-D', 'primary', '-U', 'app', '-A', 'trust', '-E', 'UTF8', '--no-locale']);
  const port = assertSafePort(await freePort());
  const speed = fast ? 'fsync=off\nsynchronous_commit=off\nfull_page_writes=off\n' : '';
  writeFileSync(path.join(root, 'primary', 'postgresql.auto.conf'), `port=${port}\nlisten_addresses='127.0.0.1'\nmax_connections=60\n${speed}${conf}\n`);
  const c = { root, port, name: 'primary', nodes: ['primary'] };
  startNode(c, 'primary');
  return c;
}

export async function addStandby(c, { name = 's1', conf = '' } = {}) {
  assertSafePort(c.port);
  run(c.root, 'pg_basebackup', ['-h', '127.0.0.1', '-p', String(c.port), '-U', 'app', '-D', name, '-R', '-X', 'stream', '--no-sync']);
  const port = assertSafePort(await freePort());
  appendFileSync(path.join(c.root, name, 'postgresql.auto.conf'), `\nport=${port}\ncluster_name='${name}'\n${conf}\n`);
  startNode(c, name);
  c.nodes.push(name);
  return { name, port };
}

export async function stopAll(c) {
  for (const n of [...c.nodes].reverse()) {
    if (existsSync(path.join(c.root, n, 'postmaster.pid')) && !stopNode(c, n)) stopNode(c, n, 'immediate');
  }
  await new Promise((r) => setTimeout(r, 300));
  rmSync(c.root, { recursive: true, force: true, maxRetries: 5, retryDelay: 300 });
}

بالعامية

في الـ single-leader replication فيه node واحدة، الـ primary، بتقبل كل الكتابة وبتبعت الـ WAL بتاعها لواحد أو أكتر من الـ standbys اللي بتعمله replay. الـ standbys بتجاوب قراءات وبترفض كتابة، فسعة القراية بتزيد مع كل واحد بتضيفه. pg_stat_replication على الـ primary بيوريك state و sync_state لكل standby، وpg_wal_lsn_diff(sent_lsn, replay_lsn) بيدّيك الـ lag بالـ bytes.

التجربة بتخلي الـ lag ظاهر عن قصد. pg_wal_replay_pause() بتوقف الـ standby عن تطبيق الـ WAL، بس هو لسه بيستلمه. INSERT واحد على الـ primary بيطلّع النتيجة المهمة: الـ primary شايف صف، والـ replica شايفة صفر، وبينهم 424 byte lag. بعد الـ resume الـ replica بتلحق. الـ replica مش نفس الـ data بتأخير تقدر تتجاهله: طول الفترة دي هي database في حالة تانية خالص.

الـ streaming مقابل logical، وإزاي الـ app بيتوصل من خلال pool، موجودين في قسم 07. من ناحية الـ system design بتكسب read scaling ونسخة جاهزة للـ failover، بس مش بتكسب write capacity أكتر: كل standby لسه بيعيد كل كتابة.

فين هستخدمه في شغلي؟ صفحات القراية الكتير زي لستة الـ orders أو التقارير تروح على read replica، والكتابة والـ checkout على الـ primary. في Node ده معناه pool للـ primary و pool تاني للـ replica، وكل query بتختار. الغلطة الشائعة: تعتبر إن زيادة replicas بتحل مشكلة بطء الكتابة، وهي مش بتحلها: كل replica بتكتب نفس الكتابات.

Part 2 — Sync vs async 🟡 Intermediateالجزء 2 — الـ sync مقابل الـ async

English

The trade-off is durability versus latency. With asynchronous replication the primary confirms a commit once its own WAL is flushed, and the standby catches up later. With synchronous replication (set with synchronous_standby_names) the commit waits for a standby, and synchronous_commit chooses for what: off doesn't even wait for the local flush; local waits only for the local flush; on waits for the standby to flush WAL to disk; remote_write for the standby to write it; remote_apply for the standby to replay it, which is the only level where a read on that standby is guaranteed to see the commit.

On localhost those differences are invisible, so the standby is connected through a delay proxy. I asked for 5 ms one way; the measured round trip through it is 31.1 ms, because Windows timers round up. That is the distance stand-in. With async replication a commit took about 0.2 ms. With a synchronous standby, on took about 31 ms: one round trip, measured directly. synchronous_commit can be set per transaction, so a payment can pay for the round trip while an analytics event sets off and skips it.

The surprise is the availability cost. Stop the only synchronous standby and every commit waits, in wait event IPC/SyncRep, indefinitely. statement_timeout at 800 ms did not end it: after 3 seconds it was still waiting. pg_cancel_backend did end it, and then the client received a success result with a warning: canceling wait for synchronous replication, "already committed locally, but might not have been replicated". So the client saw success for a transaction whose durability guarantee was just waived, and the row is on the primary.

The fix for one standby being a single point of failure is a quorum: ANY 1 (s1, s2) commits as soon as any one of the two confirms, so losing either changes nothing. Twenty commits with s1 dead averaged about 1 ms. Lose both and it hangs again, by design: sync replication chooses to stop rather than lose the promise.

الـ client بيبعت COMMIT. الـ primary بيعمل flush للـ WAL محليًا ويبعته للـ standby. الـ standby بيعمل flush (لو on) أو يطبّق (لو remote_apply)، وبعدين يبعت ack. الـ primary مش بيرد على الـ client غير بعد الـ ack ده، فزمن الـ commit بيتضاف عليه round trip كامل. ده معنى "durability مقابل latency".

// بروكسي TCP بيأخر كل اتجاه: بديل عن المسافة بين الـ data centers، مش شبكة حقيقية
export function delayProxy(targetPort: number, oneWayMs: number) {
  assertSafePort(targetPort);
  const socks = new Set<net.Socket>();
  const srv = net.createServer((a) => {
    const b = net.connect(targetPort, "127.0.0.1");
    socks.add(a); socks.add(b);
    a.setNoDelay(true); b.setNoDelay(true);
    const pipe = (from: net.Socket, to: net.Socket) =>
      from.on("data", (d) => setTimeout(() => { if (!to.destroyed) to.write(d); }, oneWayMs));
    pipe(a, b); pipe(b, a);
    const kill = () => { a.destroy(); b.destroy(); };
    for (const s of [a, b]) { s.on("close", kill); s.on("error", kill); }
  });
  return new Promise<{ port: number; close: () => void }>((res) =>
    srv.listen(0, "127.0.0.1", () => {
      const { port } = srv.address() as net.AddressInfo;
      res({ port: assertSafePort(port), close: () => { socks.forEach((s) => s.destroy()); srv.close(); } });
    }));
}

// قياس الـ RTT الفعلي عبر البروكسي: Windows timers بتزوّد عن الرقم المطلوب
export async function measureProxyRtt(oneWayMs: number, samples = 30): Promise<number> {
  const echo = net.createServer((s) => s.on("data", (d) => s.write(d)));
  await new Promise<void>((r) => echo.listen(0, "127.0.0.1", () => r()));
  const echoPort = (echo.address() as net.AddressInfo).port;
  const proxy = await delayProxy(echoPort, oneWayMs);
  const c = net.connect(proxy.port, "127.0.0.1");
  c.setNoDelay(true);
  await new Promise<void>((r) => c.once("connect", () => r()));
  const xs: number[] = [];
  for (let i = 0; i < samples; i++) {
    const t0 = performance.now();
    c.write("x");
    await new Promise<void>((r) => c.once("data", () => r()));
    xs.push(performance.now() - t0);
  }
  c.destroy(); proxy.close(); echo.close();
  xs.sort((a, b) => a - b);
  return +xs[Math.floor(xs.length / 2)].toFixed(1);
}

Part 3 — Multi-leader 🟡 Intermediateالجزء 3 — الـ multi-leader

English

Multi-leader replication lets more than one node accept writes. The reasons are specific: several data centers where each region wants local write latency, and clients that must keep working offline. Calendars on phones and laptops behave this way, and collaborative editors do too. The price is write conflicts: two leaders can change the same record concurrently, and neither sees the other's change until later.

The simulation has two leaders change the same order while disconnected: support in Cairo changes the shipping address, and the warehouse in Frankfurt marks it shipped. Last-write-wins on the whole row keeps the newer version and silently loses the address change. LWW per field keeps both field updates but still loses one note. Application-level merge keeps everything: the status follows the state machine, the notes are a set union. And in the last line, a 10-tick clock skew makes LWW keep the Cairo version and lose the warehouse's shipped update entirely, with no error anywhere. A timestamp is not a causal order.

This simulation is deliberately small: it doesn't model replication topology, ordering across more than two leaders, or causality tracking. CRDTs and geo-replication are in Geo-Distribution. The trade-off to remember: you gain write availability in each region and pay for it with conflict handling in every feature that writes.

// (1) آخر كتابة تكسب: الـ row كله، يعني اللي عنده أكبر timestamp بياخد كل حاجة
function lwwWholeRow(a: Order, b: Order): Order {
  const newest = (o: Order) => Math.max(...Object.values(o.ts));
  return clone(newest(a) >= newest(b) ? a : b);
}

// (2) آخر كتابة تكسب لكل حقل لوحده: كده العنوان والحالة الاتنين بيعيشوا
function lwwPerField(a: Order, b: Order): Order {
  const out = clone(a);
  for (const f of ["status", "shippingAddress"] as const) {
    if (b.ts[f] > a.ts[f]) { out[f] = b[f]; out.ts[f] = b.ts[f]; }
  }
  return out;
}

// (3) حل application-level: دمج الـ notes كـ set، والحالة بترتيب الـ state machine
const statusRank: Record<string, number> = { pending: 0, paid: 1, shipped: 2, delivered: 3 };
function appMerge(a: Order, b: Order): Order {
  const out = lwwPerField(a, b);
  out.notes = [...new Set([...a.notes, ...b.notes])].sort();
  out.status = statusRank[a.status] >= statusRank[b.status] ? a.status : b.status;
  return out;
}

Part 4 — Leaderless quorums 🟡 Intermediateالجزء 4 — الـ leaderless quorums

English

In a Dynamo-style store there is no leader. The client (or a coordinator) writes to N replicas and waits for W acknowledgements, and reads from N replicas waiting for R responses, taking the newest version. If W + R > N, every read set overlaps every write set in at least one replica, so a read must include an up-to-date copy. That one line of arithmetic is what the name quorum means.

The simulation has N=3, 20,000 operations and a seeded PRNG. Without failures, W=1, R=1 reads something stale a third of the time (33.1%) and W=2, R=2 or W=3, R=1 never do. With each replica down 10% of the time the price shows up: W=3 fails 26.5% of writes, W=2 fails 2.9%, and W=1 fails 0.2% while still being stale 37.4% of the time. W=2, R=2 is the common balance for N=3, tolerating one replica down on both paths.

Read repair fixes old replicas as a read goes by. It only has something to compare when R > 1: with W=1, R=2 it took stale reads from 7.9% to 1.1%, while with R=1 it changed nothing, because a single response has nothing to disagree with.

W + R > N is not linearizability. Four cases are at the end of the output: a write in flight can be seen by one reader and missed by a later one; a write that failed at the client (too few acks) can still be visible; concurrent writes leave replicas that disagree, so the store must order or merge them; and a sloppy quorum writes to substitute nodes when the home nodes are down, so the write and the following strict read may not overlap at all. A runnable version with real processes is in the key-value store case.

function mulberry32(a: number) {
  return () => {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

interface Replica { version: number; down: boolean }
const N = 3;

// كل عملية: كتابة احتمالها writeProb، وبعدها قراية. نحسب كام قراية رجّعت قيمة أقدم من آخر ack
function run(W: number, R: number, opts: { downProb: number; readRepair: boolean; seed: number; ops: number; writeProb: number }) {
  const rnd = mulberry32(opts.seed);
  const replicas: Replica[] = Array.from({ length: N }, () => ({ version: 0, down: false }));
  let version = 0, acked = 0, stale = 0, reads = 0, writes = 0, failedWrites = 0;

  for (let op = 0; op < opts.ops; op++) {
    // احتمال إن كل replica تبقى down اللحظة دي
    for (const r of replicas) r.down = rnd() < opts.downProb;

    if (rnd() < opts.writeProb) {
      writes++;
      const order = replicas.map((r) => ({ r, k: rnd() })).sort((a, b) => a.k - b.k).map((x) => x.r);
      const alive = order.filter((r) => !r.down);
      if (alive.length >= W) {
        version++;
        // الـ W دول اتأكدوا. الباقيين الشغالين: نص الوقت الكتابة بتوصلهم، والنص لسه في الطريق
        alive.slice(0, W).forEach((r) => (r.version = version));
        alive.slice(W).forEach((r) => { if (rnd() < 0.5) r.version = version; });
        acked = version;
      } else {
        failedWrites++;
      }
    }

    // القراية: R replicas عشوائي شغالين، وبناخد أعلى version منهم
    const readSet = replicas.map((r) => ({ r, k: rnd() })).sort((a, b) => a.k - b.k).map((x) => x.r).filter((r) => !r.down).slice(0, R);
    if (readSet.length === R && acked > 0) {
      reads++;
      const seen = Math.max(...readSet.map((r) => r.version));
      if (seen < acked) stale++;
      if (opts.readRepair) readSet.forEach((r) => { r.version = Math.max(r.version, seen); });
    }
  }
  return { reads, staleRate: reads ? +(stale / reads * 100).toFixed(1) : 0, failedWritePct: writes ? +(failedWrites / writes * 100).toFixed(1) : 0 };
}

// ليه W+R>N مش ⁦linearizable (1)⁩: كتابة W=2 لسه في الطريق، ووصلت لـ replica واحدة
function writeInFlight() {
  const r = [0, 0, 0];
  r[0] = 1;
  const reader1 = Math.max(r[0], r[1]);
  const reader2 = Math.max(r[1], r[2]);
  return { reader1, reader2, laterReaderSawOlder: reader1 > reader2 };
}

// ليه W+R>N مش ⁦linearizable (2)⁩: كتابة فشلت عند العميل بس قيمتها فضلت على replica
function failedWriteStillVisible() {
  const r = [0, 0, 0];
  r[0] = 1;
  const clientGot = "error: only 1 of W=2 acks";
  return { clientGot, valueVisibleToAReader: Math.max(r[0], r[1]) === 1 };
}

// ليه W+R>N مش ⁦linearizable (3)⁩: كتابتين متزامنتين، وكل replica شافتهم بترتيب مختلف
function concurrentWrites() {
  const orderOnReplica = [["A", "B"], ["B", "A"], ["A", "B"]];
  const finalValue = orderOnReplica.map((seq) => seq[seq.length - 1]);
  return { finalValue, replicasDisagree: new Set(finalValue).size > 1 };
}

// الـ sloppy quorum: الكتابة اتحطت على nodes بره الـ home set، فالقراية الـ strict مش بتقاطعها
function sloppyQuorum() {
  const home = { a: 0, b: 0, c: 0 };
  const hint = { d: 0, e: 0 };
  hint.d = 1; hint.e = 1;
  const read = Math.max(home.a, home.b);
  return { writeAckedOn: "d,e (sloppy)", readFrom: "a,b", valueRead: read, sawTheWrite: read === 1 };
}

Interview question "N=3, W=2, R=2. Is that linearizable?" → No. The overlap guarantees the read reaches one fresh replica, but a write still in flight can be seen by one reader and missed by a later one. A failed write can remain on a replica. Concurrent writes need a version order or a merge. With a sloppy quorum the overlap isn't even guaranteed. For linearizable reads you need a consensus protocol or leases, as in the consensus lesson.
"N=3 و W=2 و R=2، ده linearizable؟" ← لأ. التقاطع بيضمن إن القراية هتوصل لنسخة واحدة جديدة، بس كتابة لسه في الطريق ممكن يشوفها قارئ ويفوتها قارئ بعده، وكتابة فشلت ممكن تفضل على replica، والكتابات المتزامنة محتاجة ترتيب versions أو merge، ومع الـ sloppy quorum التقاطع نفسه مش مضمون. عشان linearizable reads لازم consensus protocol أو leases، زي اللي في درس الـ consensus.

Part 5 — Failover and lost writes 🟡 Intermediateالجزء 5 — الـ failover والكتابات اللي بتضيع

English

Failover has three steps and each can go wrong. Detect that the primary is dead, usually a timeout, so a slow primary and a dead one look the same. Choose a new primary, ideally the standby with the most received WAL. Reconfigure clients to send writes there, through a virtual IP, a proxy or the driver.

With asynchronous replication failover can lose data that the client was told is safe. The experiment shows the mechanism in two variations. In variation A only replay is paused, and the primary then dies: the promoted standby still has the row, because replay is separate from receipt and the WAL had already arrived. In variation B the replication link is cut first, then the client gets a success for order 2, then the primary dies. After promotion the new primary doesn't have order 2, and the LSN comparison (0/302DA10 on the old primary vs 0/302D958 on the promoted node) shows exactly what was never received. That is RPO > 0 made visible: an acknowledged write gone.

Patroni is the common way to automate this. It keeps a leader key with a time limit in a distributed store such as etcd, Consul, ZooKeeper or Kubernetes; the node holding it is the primary, and a node that can't renew it demotes itself. Patroni also supports a watchdog to help fence a stuck node. Not run here: Patroni needs its store and processes that aren't part of this lab.

GitHub's October 2018 incident is the textbook case. A network partition between their US East Coast hub and data center lasted 43 seconds; Orchestrator moved the primaries to the US West Coast. The East Coast clusters held "several seconds of writes" not replicated west, and one of the busiest clusters had 954 writes in the affected window. Once writes landed on the West Coast, "the database clusters in both data centers now contained writes that were not present in the other data center", so they couldn't simply fail back. Degraded service lasted 24 hours and 11 minutes, and the sudden cross-country latency was a major contributor. Disaster-recovery planning continues in Redundancy & DR.

Part 6 — Split-brain 🟡 Intermediateالجزء 6 — الـ split-brain

English

Split-brain is two nodes that each believe they are the primary. It happens when the failure detector was wrong and the old primary is alive. The experiment promotes the standby with the old primary still running. Both report pg_is_in_recovery() = false, both accept writes, and they are now on different timelines (1 and 2). The order ids diverge as 2 and 34: the promoted node's sequence jumps ahead because Postgres logs sequences 32 values ahead in WAL, and a promoted standby resumes from the logged value. Nothing warns anyone. Clients get successes from both.

The fixes all answer "how does the old primary stop?": fencing or STONITH (shoot the other node in the head: cut its power or network, or revoke its storage access), leases (the primary may only act while it holds a time-limited lease, so an expired lease means stop), and a majority witness (a node can only be primary with agreement from a majority, so a minority side can't promote). Failure detection is in Fallacies & Detection and consensus in Consensus & Raft.

Rejoining the old primary needs pg_rewind. It rewinds the old node to the divergence point and copies what changed from the new primary. It requires data checksums or wal_log_hints, and data checksums are on by default since Postgres 18 (data_checksums on in the output). My first run failed: could not find previous WAL record, because pg_rewind needs the old primary's WAL from the last common checkpoint and it had been recycled. Keeping WAL with wal_keep_size, or an archive and restore_command, fixes that. After a successful rewind the old primary comes back as a standby, and written-to-old is gone: those writes were discarded, and that's the actual cost of split-brain.

Part 7 — Reads after writes in the app 🟡 Intermediateالجزء 7 — القراية بعد الكتابة في الـ app

English

The most common production symptom of replication lag is a user who saves something, the next page reloads, and the item is missing. The simple fix: after a user writes, send that user's reads to the primary for N seconds. N must be larger than the lag you are willing to tolerate. Reads from everyone else stay on replicas.

The experiment runs with replication paused, so the lag is real and fixed, and with two API instances, because that's what production looks like. A POST goes to instance A and the following GET to instance B, as a load balancer would do. With no routing: 404 from the replica. With an in-process Map marking recent writers: still 404, because A set the mark and B never saw it. With a mark in Redis (SET lastwrite:u PX 2000): 200 from the primary. Once the TTL expires and the replica has caught up, reads go back to the replica and the row is there.

Lag belongs on your dashboards. pg_stat_replication gives lag as bytes (pg_wal_lsn_diff) and as time (replay_lag). Alert when it exceeds the N you chose, because beyond that the sticky window no longer covers it. One trap in the docs: on a fully caught-up idle system the lag columns revert to NULL, so treat NULL as no measurement rather than as zero, and watch the byte difference as well. A stronger approach using LSN tokens is in Consistency & CAP, and the driver side is in section 07.

// كام ثانية بعد الكتابة نقرا فيها من الـ primary: لازم تبقى أكبر من الـ lag اللي بتستحمله
const STICKY_MS = 2000;

interface WriteMarks { mark(user: string): Promise<void>; recent(user: string): Promise<boolean> }

// في الذاكرة: كل instance من الـ API ليها Map لوحدها
class InProcessMarks implements WriteMarks {
  private until = new Map<string, number>();
  async mark(user: string) { this.until.set(user, Date.now() + STICKY_MS); }
  async recent(user: string) { return (this.until.get(user) ?? 0) > Date.now(); }
}

// في Redis: كل الـ instances بتشوف نفس الـ mark، والـ TTL بيمسحه لوحده
class RedisMarks implements WriteMarks {
  private redis: Redis;
  constructor(redis: Redis) { this.redis = redis; }
  async mark(user: string) { await this.redis.set(`lastwrite:${user}`, "1", "PX", STICKY_MS); }
  async recent(user: string) { return (await this.redis.exists(`lastwrite:${user}`)) === 1; }
}

function api(primary: pg.Client, replica: pg.Client, marks: WriteMarks | null) {
  const app = express();
  app.use(express.json());
  app.post("/orders", async (req, res) => {
    const user = String(req.headers["x-user"]);
    const { rows } = await primary.query(`insert into orders (user_id, status) values ($1, 'paid') returning id`, [user]);
    await marks?.mark(user);
    res.status(201).json(rows[0]);
  });
  app.get("/orders/:id", async (req, res) => {
    const user = String(req.headers["x-user"]);
    // الـ middleware كله في السطر ده: لو كتب من شوية يقرا من الـ primary
    const usePrimary = (await marks?.recent(user)) ?? false;
    const db = usePrimary ? primary : replica;
    const { rows } = await db.query(`select id, status from orders where id = $1`, [req.params.id]);
    res.set("x-read-from", usePrimary ? "primary" : "replica").status(rows[0] ? 200 : 404).json(rows[0] ?? { error: "not found" });
  });
  return new Promise<{ url: string; close: () => void }>((resolve) => {
    const s = app.listen(0, "127.0.0.1", () => resolve({ url: `http://127.0.0.1:${(s.address() as AddressInfo).port}`, close: () => s.close() }));
  });
}

  const b = await api(primary, replica, marks());
  const headers = { "content-type": "application/json", "x-user": "u-42" };

}

بالعامية

أشهر عرض لـ replication lag في production: الـ user يحفظ حاجة، الصفحة تعمل reload، والحاجة مش موجودة. الحل البسيط: بعد ما الـ user يكتب، ابعت قرايته للـ primary لمدة N ثانية. لازم N تبقى أكبر من الـ lag اللي بتستحمله. وقراية باقي الناس تفضل على الـ replicas.

التجربة شغالة والـ replication واقفة، فالـ lag حقيقي وثابت، ومعاها instance-ين من الـ API، لأن ده شكل الـ production. الـ POST بيروح لـ instance A والـ GET بعده لـ instance B، زي ما الـ load balancer بيعمل. من غير routing: 404 من الـ replica. بـ Map في الذاكرة بتعلّم اللي كتب: لسه 404، لأن A حطت الـ mark و B ما شافتهوش. بـ mark في Redis (SET lastwrite:u PX 2000): 200 من الـ primary. ولما الـ TTL يخلص والـ replica تلحق، القراية بترجع للـ replica والصف موجود.

الـ lag لازم يبقى على الـ dashboards بتاعتك. pg_stat_replication بيدّيك الـ lag بالـ bytes (pg_wal_lsn_diff) وبالوقت (replay_lag). اعمل alert لما يعدّي الـ N اللي اخترتها، لأن بعدها الـ sticky window مبقتش مغطية. وفيه فخ في الـ docs: على نظام idle لحق خالص، عواميد الـ lag بترجع NULL، فاعتبر NULL "مفيش قياس" مش "صفر"، وراقب فرق الـ bytes كمان. وفيه طريقة أقوى بـ LSN tokens في درس الـ Consistency و CAP، وجانب الـ driver في قسم 07.

فين هستخدمه في شغلي؟ بعد POST /orders أو حفظ الـ profile، middleware بيحط lastwrite:{userId} في Redis بـ TTL حوالي 5–10 ثواني، وأي GET بيعمل EXISTS قبل ما يختار الـ pool. لو عندك autoscaling لازم الـ mark يبقى shared. والـ alert: replica lag أكبر من الـ N لمدة 5 دقايق. الغلطة الشائعة: تحط الـ mark في memory الـ Node process وهو شغال كويس عند واحد dev، ويفضل stale في production لأن عندك 8 instances.
What breaks this pattern Lag longer than N: the sticky window closes and the reader lands on a replica that still doesn't have the row. Lag for one user's write that reaches a different service: the mark is per user, not per entity. And if Redis is down, the safe default is to read from the primary, not the replica, since that trades load for correctness.
إيه اللي بيكسر الـ pattern ده: lag أطول من N، فالـ sticky window تقفل والقارئ يقع على replica لسه ما عندهاش الصف. كتابة user توصل لـ service تانية: الـ mark لكل user مش لكل entity. ولو Redis واقع، الـ default الآمن تقرا من الـ primary مش الـ replica، عشان بتبدّل load بصحة البيانات.
Interview question "Users complain that after creating an order, the list sometimes doesn't show it. Why, and how do you fix it?" → Reads hit a replica that hasn't applied the write. Route that user's reads to the primary for N seconds after a write, with the mark in shared storage such as Redis, because the next request can land on another instance. Alert when lag exceeds N. For a stronger guarantee, pass the commit's LSN and wait for the replica to reach it.
"الناس بتشتكي إن بعد ما تعمل order اللستة أحيانًا مش بتظهره. ليه؟ وهتصلحها إزاي؟" ← القراية بتيجي من replica لسه ماطبّقتش الكتابة. أبعت قراية الـ user ده للـ primary لمدة N ثانية بعد الكتابة، والـ mark في storage مشترك زي Redis لأن الـ request الجاي ممكن يقع على instance تانية. وأعمل alert لما الـ lag يعدّي N. ولو عايز ضمان أقوى، أبعت LSN بتاع الـ commit وأستنى الـ replica توصل له.

    await db.query(`alter system set synchronous_standby_names = 'FIRST 1 (s1, s2)'`);
    await db.query(`select pg_reload_conf()`);
    await sleep(1000);
    const state = `select application_name, sync_state from pg_stat_replication order by 1`;
    report("before", (await db.query(state)).rows);
    stopNode(c, "s1");
    await sleep(1000);
    report("s1 dead", (await db.query(state)).rows);
    await db.query(`set statement_timeout = '5000ms'`);
    report("commit after s1 died", (await db.query(`insert into orders (status) values ('paid') returning id`)).rows[0]);
    await db.end();
  } finally {
    await stopAll(c);
  }
}

import { addStandby, connect, createPrimary, stopAll, stopNode } from "../pg-cluster.mjs";
import { report, sleep } from "./lab.ts";

// تمرين 3: fencing للـ primary القديم قبل الـ promote: كتابة جديدة لازم تترفض
{
  const c = await createPrimary();
  try {
    const s = await addStandby(c, { name: "s1" });
    const admin = await connect(c.port);
    const app = await connect(c.port);
    app.on("error", () => {});
    await admin.query(`create table orders (id serial primary key, status text)`);
    await sleep(400);

    await admin.query(`alter system set default_transaction_read_only = on`);
    await admin.query(`select pg_reload_conf()`);
    await sleep(300);
    const write = (db: typeof app) => db.query(`insert into orders (status) values ('after-fence')`).then(() => "accepted", (e: Error) => "refused: " + e.message);
    report("connection opened before the fence", await write(app));

    const standby = await connect(s.port);
    await standby.query(`select pg_promote(true, 20)`);
    report("standby promoted, in recovery?", (await standby.query(`select pg_is_in_recovery() r`)).rows[0].r);
    report("write on promoted node", (await standby.query(`insert into orders (status) values ('after-promote') returning id`)).rows[0]);
    report("rows on old primary", (await admin.query(`select count(*)::int n from orders`)).rows[0].n);
    await standby.end();
    await app.end().catch(() => {});
    await admin.end();
  } finally {
    await stopAll(c);
  }
}
process.exit(0);

Cheat sheet · الخلاصة

  • Replicas scale reads, not writes: every standby replays every write. A replica is a different state until it has applied the WAL.
  • Sync vs async is durability vs latency: a sync commit costs one round trip (≈31 ms with our proxy). synchronous_commit is per-transaction.
  • Only remote_apply guarantees a read on that standby sees the commit.
  • A dead sync standby hangs COMMIT in IPC/SyncRep. statement_timeout doesn't end it. ANY 1 (s1, s2) does.
  • Multi-leader buys local writes, and costs conflict handling in every writing feature. LWW silently loses updates, and clock skew makes it worse.
  • Quorum: W + R > N overlaps read and write sets. Stale rate for N=3 went 33.1% at (1,1) to 0% at (2,2), with 2.9% failed writes at 10% replica failure.
  • W + R > N is not linearizable: in-flight writes, failed writes, concurrent writes and sloppy quorums all break it.
  • Failover loses what was never received, not what wasn't applied. RPO > 0 is real with async replication: an acknowledged order disappeared.
  • Split-brain: two primaries, both accepting writes. Fence with STONITH, leases or a majority, and never promote without stopping the old one.
  • pg_rewind needs WAL from the last common checkpoint (wal_keep_size or an archive), and discards the old primary's divergent writes.
  • Read-your-writes: send a user to the primary for N seconds after writing, with the mark in shared storage, and alert when lag exceeds N.
بالعامية
  • الـ replicas بتزوّد القراية مش الكتابة: كل standby بيعيد كل كتابة. والـ replica حالتها مختلفة لحد ما تطبّق الـ WAL.
  • الـ sync مقابل الـ async هو durability مقابل latency: الـ sync commit بياخد round trip (≈31 ms مع الـ proxy بتاعنا). وsynchronous_commit per-transaction.
  • remote_apply بس هو اللي بيضمن إن القراية من الـ standby ده تشوف الـ commit.
  • الـ sync standby الميت بيعلّق الـ COMMIT في IPC/SyncRep. وstatement_timeout مش بينهيه. ANY 1 (s1, s2) هو الحل.
  • الـ multi-leader بيدّيك كتابة محلية، وتمنه conflict handling في كل feature بتكتب. الـ LWW بيضيّع تحديثات ساكت، والـ clock skew بيزوّدها.
  • الـ quorum: W + R > N بيخلي الـ read والـ write sets يتقاطعوا. نسبة الـ stale لـ N=3 من 33.1% عند (1,1) لـ 0% عند (2,2)، مع 2.9% كتابات فاشلة لو كل replica بتقع 10%.
  • W + R > N مش linearizable: الكتابات اللي في الطريق، الفاشلة، المتزامنة، والـ sloppy quorums كلهم بيكسروها.
  • الـ failover بيضيّع اللي ماتوصلش، مش اللي ماتطبقش. والـ RPO > 0 حقيقي مع الـ async: order اتأكد وضاع.
  • الـ split-brain: اتنين primary، الاتنين بيقبلوا كتابة. الحل fencing أو STONITH أو leases أو أغلبية، وعمرك ما تعمل promote من غير ما توقف القديم.
  • pg_rewind محتاج WAL من آخر checkpoint مشترك (wal_keep_size أو archive)، وبيرمي الكتابات المختلفة بتاعة الـ primary القديم.
  • الـ read-your-writes: ابعت الـ user للـ primary لمدة N ثانية بعد الكتابة، والـ mark في storage مشترك، واعمل alert لما الـ lag يعدّي N.
