Why this matters · ليه ده مهم

English

A distributed lock looks like a solved problem: SET NX PX, three lines, done. It's also one of the most reliable sources of silent data corruption in backend systems, because a lock that expires can't stop the process that thinks it still holds it. A double charge from a paused worker raises no exception and shows up as a support ticket weeks later.

This lesson reproduces that failure on real Redis and Postgres, then walks through what actually fixes it. "What's a fencing token?" is exit-test question 6 for this section, and "would you use Redlock for this?" is a standard senior interview follow-up. The honest answer usually starts with whether you need the lock at all.

Part 1 — Leases: efficiency vs correctness 🔴 Advancedالجزء 1 — الـ leases: كفاءة ولا صحة

English

The mechanics are already covered: 04 lesson 21 builds SET NX PX and the Lua release, and 07 lesson 35 adds DELEX and a first renewing lease. This lesson starts where those stop. A lease is a lock with an expiry: if the holder crashes, the lock frees itself. That's what makes it usable, and it's also the source of every problem below, since the lock can now end while the holder is still working.

Before writing any lock, ask what happens if two workers hold it at once. Martin Kleppmann's split is the most useful question in this topic. An efficiency lock only prevents duplicate work: if it fails, you pay some compute or send a second report. A correctness lock protects an invariant: if it fails, money moves twice or an invoice number repeats. A plain Redis lock is fine for the first kind. The second kind needs the storage itself to reject the late writer, which is Part 3.

Short leases recover quickly from a crash but expire by accident more often, so long jobs use a watchdog: a timer that extends the TTL every ttl / 3 while the job runs. In Node that timer lives on the same event loop as the job, so whatever blocks the job also blocks the renewer. In the run below a 300 ms lease survives 1200 ms of async work with 11 renewals and zero rival wins. Then a 900 ms stall: Redis has already dropped the key (PTTL is -2), yet lost() still says false on the first line after the stall. The holder learns the truth only after the next timer tick, 50 ms later in this run, and anything it did in between ran without a lock. A separate renewer thread narrows this for a JavaScript stall but not for a VM pause or CPU throttling, which stop every thread.

function checked(raw: string | undefined): number {
  const n = Number(raw);
  if (!/^\d+$/.test(String(raw)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {

  return n;
}

import type { Redis } from "ioredis";

// التجديد والـ release الاتنين compare-then-act: لازم atomic جوه Lua
const RENEW = `if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('pexpire', KEYS[1], ARGV[2]) end return 0`;
const RELEASE = `if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end return 0`;

export type Lease = { lost(): boolean; renewals(): number; release(): Promise<number> };

export async function acquireLease(r: Redis, key: string, ttlMs: number): Promise<Lease | null> {
  const token = randomUUID();
  if ((await r.set(key, token, "PX", ttlMs, "NX")) !== "OK") return null;

  let lost = false;
  let renewals = 0;
  // الـ watchdog ده timer عادي: عايش على نفس الـ event loop بتاع الشغل
  const watchdog = setInterval(async () => {
    const ok = await r.eval(RENEW, 1, key, token, ttlMs);
    if (ok === 1) renewals++;
    else {
      lost = true;
      clearInterval(watchdog);
    }
  }, ttlMs / 3);

  return {
    lost: () => lost,
    renewals: () => renewals,
    release: async () => {
      clearInterval(watchdog);
      return (await r.eval(RELEASE, 1, key, token)) as number;
    },
  };
}

بالعامية

الميكانيكا اتشرحت قبل كده: 04 lesson 21 فيه SET NX PX والـ Lua release، و07 lesson 35 فيه DELEX وأول lease بيتجدد. الدرس ده بيبدأ من حيث وقفوا. الـ lease هو lock ليه expiry: لو الـ holder وقع، الـ lock بيتفك لوحده. ده اللي مخليه ينفع، وهو برضه مصدر كل المشاكل الجاية، لأن الـ lock دلوقتي ممكن يخلص والـ holder لسه شغال.

قبل ما تكتب أي lock، اسأل: لو اتنين مسكوه مع بعض يحصل إيه؟ التقسيمة بتاعة Martin Kleppmann هي أهم سؤال في الموضوع. الـ efficiency lock بيمنع شغل متكرر بس: لو فشل، هتدفع شوية compute أو تبعت report مرتين. الـ correctness lock بيحمي invariant: لو فشل، فلوس بتتحرك مرتين أو رقم فاتورة بيتكرر. الـ Redis lock العادي تمام للنوع الأول. النوع التاني لازم الـ storage نفسه هو اللي يرفض الـ writer المتأخر، وده الجزء 3.

الـ lease القصير بيرجع بسرعة بعد crash بس بيخلص بالغلط أكتر، فالشغل الطويل بيستخدم watchdog: timer بيمد الـ TTL كل ttl / 3 طول ما الشغل ماشي. في Node الـ timer ده عايش على نفس الـ event loop بتاع الشغل، فأي حاجة بتوقف الشغل بتوقف اللي بيجدد كمان. في التشغيل فوق، lease مدته 300ms عدّى 1200ms شغل async بـ 11 تجديد ومفيش حد سبقه. بعدها stall مدته 900ms: Redis مسح الـ key خلاص (PTTL بقى -2)، ومع ذلك lost() لسه بيقول false في أول سطر بعد الـ stall. الـ holder بيعرف الحقيقة بعد ما الـ timer يشتغل تاني، بعد 50ms في التشغيل ده، وأي حاجة عملها في الوقت ده اتعملت من غير lock. لو حطيت الـ renewer في thread منفصل هيقلل المشكلة لو الـ JS هو اللي واقف، بس مش لو الـ VM نفسها وقفت أو الـ CPU اتعمله throttle، لأن ده بيوقف كل الـ threads.

فين هستخدمه في شغلي؟ عندك cron بيبعت إيميلات الـ invoices كل ليلة على 3 pods: lock على Redis كفاية، لو حصل وأتنين اشتغلوا، أسوأ حاجة إيميل زيادة. لكن لو الـ cron ده بيخصم من wallet، صنّفه correctness من الأول، وماتعتمدش على الـ lock لوحده. وفي الـ code review لو لقيت withLock(...) حوالين كتابة فلوس، اسأل: "لو الـ lease خلص في النص، إيه اللي بيمنع الكتابة؟".
Trade-off: picking the TTL A short TTL recovers fast after a crash, but costs more renewal traffic and expires by accident during any stall longer than the TTL. A long TTL tolerates stalls, but every crash blocks the work for the full TTL. A renewing lease gets you both, as long as the renewer keeps running.
الـ TTL القصير بيرجع بسرعة بعد الـ crash، بس بيزود traffic التجديد وبيخلص بالغلط في أي stall أطول منه. الـ TTL الطويل بيستحمل الـ stalls، بس أي crash بيوقف الشغل طول مدة الـ TTL كلها. الـ lease اللي بيتجدد بيجيب لك الميزتين، طول ما اللي بيجدد شغال.

Part 2 — The paused holder 🔴 Advancedالجزء 2 — الـ holder اللي وقف

English

Here's the failure for real, across two OS processes. Wallet 42 starts at 1000. Worker A takes a 500 ms lease, reads 1000, and intends to credit 100. Then it freezes for 1500 ms, with Atomics.wait standing in for a long GC pause. At about 500 ms the lease expires, so worker B acquires it, reads 1000, and writes 1050. A wakes up with its stale 1000 and writes 1100. The correct final balance is 1150, and Postgres holds 1100: B's credit is gone.

Neither worker did anything wrong by its own view, and no error appears anywhere. A's safe release returned 0, so the token check protected the lock from being deleted but did nothing for the data. Across the 6 paused runs in the output (1 printed and 5 counted), the update was lost every time, and it was lost 0 of 5 times without the pause. That shows that the pause, and nothing else, is what breaks it.

A pause longer than a lease isn't exotic. Large-heap GC, a slow synchronous JSON.parse, container CPU throttling, swap, or a VM live migration can all do it, and they get more common under load. Checking lease.lost() just before the write doesn't close the gap, because the pause can land between the check and the write. No client-side check can.

const KEY = "lock:wallet:42";
const RELEASE = `if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end return 0`;
type Job = { name: "A" | "B"; credit: number; pauseMs: number; t0: number };

const send = (m: object) => new Promise<void>((res) => process.send!(m, () => res()));

// كل worker ده process لوحده عشان الـ pause بتاع A مايوقفش B
async function worker({ name, credit, pauseMs, t0 }: Job) {
  const r = redis(redisPorts()[0]);
  const db = await pgClient();
  const token = randomUUID();
  const log = (m: string) => send({ log: `[${String(Date.now() - t0).padStart(5)} ms] ${name} ${m}` });

  while ((await r.set(KEY, token, "PX", 500, "NX")) !== "OK") await sleep(10);
  const { rows } = await db.query("SELECT balance FROM wallets WHERE user_id = 42");
  const balance = Number(rows[0].balance);
  await log(`got the 500 ms lease, read balance=${balance}`);
  await send({ locked: true });

  if (pauseMs) {
    freeze(pauseMs);
    await log(`woke up after a ${pauseMs} ms pause, no idea the lease expired`);
  }

  // هنا الكتابة العمياء: الـ lock هو الحماية الوحيدة
  await db.query("UPDATE wallets SET balance = $1 WHERE user_id = 42", [balance + credit]);
  await log(`wrote balance=${balance + credit}`);
  await log(`release returned ${await r.eval(RELEASE, 1, KEY, token)}`);
  await db.end();
  r.disconnect();
  process.exit(0);
}

function start(job: Job, onMsg: (m: any) => void): { child: ChildProcess; done: Promise<void> } {
  const child = fork(import.meta.filename, [JSON.stringify(job)]);
  child.on("message", onMsg);
  return { child, done: new Promise((res) => child.once("exit", () => res())) };
}

async function run(pauseMs: number, verbose: boolean): Promise<number> {
  const db = await pgClient();
  const r = redis(redisPorts()[0]);
  await db.query("UPDATE wallets SET balance = 1000 WHERE user_id = 42");
  await r.del(KEY);
  const t0 = Date.now();
  const print = (m: any) => m.log && verbose && console.log(m.log);
  let locked!: () => void;
  const aLocked = new Promise<void>((res) => (locked = res));
  const a = start({ name: "A", credit: 100, pauseMs, t0 }, (m) => (m.locked ? locked() : print(m)));
  await aLocked;
  const b = start({ name: "B", credit: 50, pauseMs: 0, t0 }, print);
  await Promise.all([a.done, b.done]);
  const { rows } = await db.query("SELECT balance FROM wallets WHERE user_id = 42");
  await db.end();
  r.disconnect();
  return Number(rows[0].balance);
}

ده الفشل بجد، على 2 processes منفصلين. الـ wallet 42 بتبدأ بـ 1000. الـ worker A بياخد lease مدته 500ms، يقرا 1000، وناوي يضيف 100. بعدها بيتجمد 1500ms، وAtomics.wait هنا بديل عن GC pause طويل. عند حوالي 500ms الـ lease بيخلص، فالـ worker B بياخده، يقرا 1000، ويكتب 1050. الـ A بيصحى بالـ 1000 القديمة ويكتب 1100. الرصيد الصح 1150، و Postgres فيه 1100: الـ credit بتاع B راح.

ولا worker عمل حاجة غلط من وجهة نظره، ومفيش error في أي مكان. الـ release الآمن بتاع A رجّع 0، يعني الـ token check منع مسح الـ lock بتاع غيره بس ماعملش حاجة للـ data. في الـ 6 runs اللي فيهم pause في الـ output (واحد متطبع و5 متعدّين) الـ update ضاع كل مرة، و0 من 5 من غير الـ pause. يعني الـ pause لوحده هو اللي بيكسرها.

والـ pause الأطول من الـ lease مش حاجة نادرة: GC على heap كبير، JSON.parse بطيء sync، CPU throttling في الـ container، swap، أو VM live migration، وكلهم بيزيدوا تحت الضغط. وتشيك lease.lost() قبل الكتابة مباشرة مش هيقفل الثغرة، لأن الـ pause ممكن ييجي بين التشيك والكتابة. مفيش check من ناحية الـ client يقدر يقفلها.

فين هستخدمه في شغلي؟ Incident شكله كده: "المستخدم عمل عمليتين، واحدة منهم اختفت من الرصيد". بتفتح الـ logs ومفيش error، بتلاقي pod كان واقف بسبب CPU throttling أو GC وقت العملية. أول سؤال في الـ postmortem: "الكتابة دي بتتحقق من أي حاجة وقت الكتابة؟" لو الإجابة "الـ lock بس"، ده السبب، وعلاجه الجزء الجاي.
What breaks at scale Under load, pauses get longer and more frequent, right when more workers are competing for the same lock. So the failure rate goes up exactly when traffic does, and a test at low load won't catch it.
تحت الضغط الـ pauses بتطول وبتتكرر، في نفس الوقت اللي workers أكتر بتتنافس فيه على نفس الـ lock. فنسبة الفشل بتزيد بالظبط لما الـ traffic يزيد، والتيست على load قليل مش هيكشفها.

Part 3 — Fencing tokens 🔴 Advancedالجزء 3 — الـ fencing tokens

English

The fix moves the decision to the place the write happens. Every acquisition receives a number that only goes up, the fencing token, and the storage rejects any write carrying a token it has already passed: UPDATE ... WHERE last_token < $2. Rerunning the same scenario, B writes with token 2. A wakes up and writes with token 1, Postgres returns rowCount=0, and A knows it lost. It then re-acquires the lock, reads the fresh 1050, and writes 1150 with token 3. All 6 runs ended at the correct total, and each one rejected exactly one stale write.

Three details decide whether this actually works. The token and the lock must come from one atomic step, which is why it's in a Lua script: if they were separate commands, A could acquire, pause, and then get a higher token than B. Take the token before reading the data, so a higher token always means a fresher read. And the token source has to be at least as durable as what it protects, because a Redis counter can move backwards after a failover (Part 4). When Postgres is the storage, a sequence is the obvious source, and it needs no Redis at all.

That's the catch: the resource must participate. A fence only works where something can compare the number at write time. A SQL row can, and S3 can do the equivalent with conditional writes. If-Match rejects the upload with HTTP 412 unless the object's ETag still matches what you read, so the first finisher wins. A third-party payment API or an email server has no such check, so there you use an idempotency key instead. As 07 lesson 35 showed, a fence orders writers but doesn't deduplicate them, so a unique key still has its own job.

Part 4 — Redis failover loses the lock 🔴 Advancedالجزء 4 — الـ failover في Redis بيضيّع الـ lock

English

Even without a pause, a single Redis with a replica can hand the same lock to two workers. Replication is asynchronous, so the primary answers OK before any replica has the write. This run uses three real instances with REPLICAOF set at runtime. To cut a replica off, it's pointed at a closed port, then the lock is taken on the old primary and the replica is promoted. SET NX returns OK on both, and worker-A and worker-B each hold the lock. Sentinel was not involved here: promotion is done by hand, which is the same end state.

The fence broke as well, and this is the detail people miss: INCR returned 8 on both sides. Two holders now have the same token, so a last_token < $2 check rejects whichever arrives second, even though that may be the legitimate one. Any counter kept in the failing system is only as good as that system's replication.

WAIT numreplicas timeout blocks until that many replicas acknowledge, and it returns how many actually did. In scenario 2 it returns 0, so the client gives the lock back and only one holder remains. That's a real improvement. It's not a guarantee, as scenario 3 shows: with two replicas, WAIT 1 returns 1 because replica1 has the write, but the failover promotes replica2, which doesn't. The Redis docs say the same thing directly: WAIT doesn't make Redis a strongly consistent store. An acknowledged write can still be lost on a failover, depending on which replica wins.

Part 5 — Redlock on five instances 🔴 Advancedالجزء 5 — Redlock على 5 instances

English

Redlock attacks the failover problem by removing replication: run N independent masters (5 in the Redis docs), and only count the lock as held if a majority granted it. The client records the start time, sends SET key value NX PX ttl to every instance, and computes validity = ttl - elapsed - drift. If it has at least 3 of 5 votes and validity > 0, it holds the lock for that long. Otherwise it releases everywhere, including the instances that seemed to fail, because a reply can be lost after the write succeeded. 07 lesson 35 ran this over 3 instances; here it's 5, with a real restart.

The run behaves as advertised: 5 of 5 votes with about 9.9 s of validity, a second client gets 0 votes and fails, 3 reachable instances still work, and 2 do not. For production, use a library rather than your own code. The redlock package's latest release is still a 2022 beta, so the run uses @sesamecare-oss/redlock 1.4, which is a named export and fails a blocked attempt with ExecutionError.

Now the limit. Client 1 reaches nodes 0, 1 and 2 only and gets 3 votes. Node 2 restarts with no persistence, so it has forgotten the lock. Client 2 reaches nodes 2, 3 and 4, and it also gets 3 votes. Both hold it. The restart is a real one: the helper stops the instance and starts a new empty one, which comes back on a different port here, unlike a real restart that would keep its address. The Redis docs cover this case: run with fsync=always, or keep a restarted node out of the pool for longer than the maximum TTL. That is an operational rule you have to enforce.

The public debate is worth reading in the original. Kleppmann argues that Redlock is too heavy for efficiency locks, where one Redis is enough, and not safe enough for correctness locks: it generates no monotonic fencing token, and its safety depends on timing assumptions about pauses, network delays and clocks. antirez replies that Redlock's random value can be used for compare-and-set on the resource, that if your store can compare tokens you barely need a strong lock anyway, that bounded clock error is a reasonable assumption if clocks are slewed rather than stepped, and that a pause during acquisition is caught by the second time check. They agree on the part that matters here: a pause after acquisition can defeat any lease. Since Redlock hands you no increasing token, don't use it where a double holder corrupts data.

const RELEASE = `if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end return 0`;
const QUORUM = 3;
const KEY = "lock:settlement:2026-11";

type Held = { value: string; votes: number; validityMs: number };

// الـ algorithm نفسه: اطلب من الكل، عدّ الأصوات، واحسب الوقت اللي فاضل
async function acquire(targets: Redis[], ttlMs: number): Promise<Held | null> {
  const value = randomUUID();
  const started = Date.now();
  const replies = await Promise.allSettled(targets.map((n) => n.set(KEY, value, "PX", ttlMs, "NX")));
  const votes = replies.filter((r) => r.status === "fulfilled" && r.value === "OK").length;
  const elapsed = Date.now() - started;
  // الـ drift ده هامش لاختلاف سرعة الساعات: 1% من الـ TTL زائد 2ms
  const validityMs = ttlMs - elapsed - (Math.ceil(ttlMs * 0.01) + 2);
  if (votes >= QUORUM && validityMs > 0) return { value, votes, validityMs };
  // فشلنا: لازم نرجّع اللي أخدناه، حتى من الـ instance اللي ماردتش
  await release(targets, value);
  console.log(`  acquire failed with ${votes}/5 votes`);
  return null;
}

async function release(targets: Redis[], value: string): Promise<void> {
  await Promise.allSettled(targets.map((n) => n.eval(RELEASE, 1, KEY, value)));
}

// ده بيوقف instance حقيقي ويرجّعه فاضي، زي restart من غير persistence
function restart(i: number): number {
  const dir = process.env.REDIS_DIRS!.split("|")[i];
  const helper = process.env.REDIS_HELPER!;
  execFileSync("node", [helper, "stop"], { cwd: dir, stdio: "ignore" });
  execFileSync("node", [helper, "start"], { cwd: dir, stdio: "ignore" });
  const port = Number(readFileSync(path.join(dir, "redis.port"), "utf8"));
  if (port < 1024 || [6379, 5432, 27017].includes(port)) throw new Error("refusing port " + port);
  return port;
}

دلوقتي الحد بتاعه. الـ client الأول واصل لـ nodes 0 و1 و2 بس فخد 3 أصوات. node 2 عملت restart من غير persistence فنسيت الـ lock. الـ client التاني واصل لـ 2 و3 و4 فخد 3 أصوات هو كمان. الاتنين ماسكين. الـ restart ده حقيقي: الـ helper بيوقف الـ instance ويشغّل واحد جديد فاضي، وبيرجع هنا على port تاني، عكس restart عادي بيحتفظ بالعنوان. الـ docs بتاعة Redis بتغطي الحالة دي: شغّل بـ fsync=always، أو سيب الـ node اللي عملت restart بره الـ pool مدة أطول من أكبر TTL. ودي قاعدة operational لازم إنت اللي تطبقها.

الخناقة المشهورة تستاهل تتقري من الأصل. Kleppmann بيقول إن Redlock تقيل على الـ efficiency locks، وRedis واحد كفاية هناك، ومش آمن كفاية للـ correctness locks: مابيطلّعش fencing token بيزيد، وأمانه معتمد على افتراضات timing عن الـ pauses والشبكة والساعات. antirez بيرد إن الـ random value بتاع Redlock ممكن يتستخدم في compare-and-set على الـ resource، وإن لو الـ store بتاعك يقدر يقارن tokens أصلًا مش محتاج lock قوي، وإن فرق الساعات المحدود افتراض معقول لو الساعات بتتظبط بالتدريج مش بقفزات، وإن الـ pause أثناء الـ acquisition بيتكشف بتشيك الوقت التاني. الاتنين متفقين على اللي يهمنا هنا: الـ pause بعد الـ acquisition بيهزم أي lease. وبما إن Redlock مابيدّيكش token بيزيد، ماتستخدمهوش في مكان لو فيه اتنين holders الـ data هتبوظ.

فين هستخدمه في شغلي؟ لو حد اقترح في design review "نستخدم Redlock على 5 Redis عشان تقفيل الفواتير يبقى آمن"، قوله إن ده 5 instances وقواعد restart وتشغيل، ومع ذلك مابيحلش الـ paused holder. البديل الأرخص: UPDATE بـ version أو unique constraint في Postgres اللي عندك أصلًا. وRedis واحد كفاية لو الـ lock ده efficiency.
Interview question "Should we use Redlock to protect payment settlement?" → No. It doesn't produce a fencing token, so it can't stop a paused holder from writing, and a restart without fsync can give two clients a majority. "نستخدم Redlock عشان نحمي تسوية المدفوعات؟" ← لأ. مابيطلّعش fencing token، فمش هيقدر يمنع holder واقف من الكتابة، وأي restart من غير fsync ممكن يدّي majority لـ اتنين clients. حط التحقق في الـ store نفسه: عمود version، أو unique constraint على الـ settlement id، أو fencing token بيتحقق منه Postgres. والـ lease استخدمه بس عشان تمنع شغل ضايع.

Part 6 — Alternatives, and dropping the lock 🔴 Advancedالجزء 6 — البدايل، وإلغاء الـ lock أصلًا

English

The first question isn't which lock to use, but whether you can drop it. In Part 2 the actual problem was a read-modify-write on a row. An optimistic version check solves that with no lock at all: UPDATE ... WHERE version = $2. Experiment 7 below reruns the paused-holder scenario with no Redis: B writes, A's stale write gets 0 rows, A rereads and succeeds, and the balance is 1150. Under real contention, 20 concurrent credits landed at the exact total with 123 retries (experiment 6). Retries are the price, so this suits low-to-moderate contention.

When you do need mutual exclusion, there's usually something closer than Redis. Advisory locks belong to a session, so there's no TTL. The lock ends when the connection dies, which is also a warning: in experiment 1, A's connection is killed, B gets the lock immediately, and A finds out only on its next query. They also break behind transaction-mode pooling (details in 07 lesson 22). Experiment 2 is a stand-in for that, since PgBouncer is not run here, with two server connections: request Y gets request X's lock because they share a connection, and X's unlock on the other connection returns false, leaving the lock held. pg_advisory_xact_lock avoids this, since it ends with the transaction.

SELECT ... FOR UPDATE is the straightforward row lock, with all credits correct. A unique constraint is a lock that can't expire: 20 instances race to insert today's cron run, and exactly one wins. FOR UPDATE SKIP LOCKED turns a table into a work queue: 4 workers claimed 40 distinct jobs. If you truly need a coordination service, etcd gives you a lease and a globally increasing revision that can serve as the fencing token. That's a linearizable alternative to Redlock, shown below as Not run here; see lesson 32 for why it's consistent.

Solution · الحل 
import { pgClient } from "./env.ts";

const db = await pgClient();
await db.query(`
  CREATE SEQUENCE wallet_fence;
  CREATE TABLE wallets (user_id int PRIMARY KEY, balance int NOT NULL, last_token bigint NOT NULL DEFAULT 0);
  INSERT INTO wallets VALUES (42, 1000, 0);
`);

const nextToken = async () => Number((await db.query("SELECT nextval('wallet_fence') AS t")).rows[0].t);
const write = (balance: number, token: number) =>
  db.query("UPDATE wallets SET balance = $1, last_token = $2 WHERE user_id = 42 AND last_token < $2", [balance, token]);

// الـ token لازم يتاخد قبل القراية، عشان ورا أي writer تاني يبقى رقمه أكبر
const tokenA = await nextToken();
const tokenB = await nextToken();
console.log("A token", tokenA, "| B token", tokenB);
console.log("B writes:", (await write(1050, tokenB)).rowCount);
console.log("A wakes, writes with the stale token:", (await write(1100, tokenA)).rowCount);
console.log("balance:", (await db.query("SELECT balance FROM wallets")).rows[0].balance);
await db.end();

balance: 1050
الـ sequence بيدّي token لكل acquisition من غير Redis، و B بياخد 2 وبيكتب، و A بـ 1 بياخد 0 صفوف. وخد بالك: nextval لازم ييجي قبل القراءة.

اكتب helper بياخد lock على الـ primary، ويعمل WAIT 1 200، ويرجّع الـ lock لو عدد الـ replicas أقل. بعدين أثبت بالسكريبت بتاع 3 instances إنه لسه بيفشل في السيناريو 3، واكتب فقرة عن هتعمل إيه.

Cheat sheet · الخلاصة

  • Ask first: if two workers hold this, what breaks? Duplicate work means efficiency lock; corrupt data means correctness lock.
  • A lease expires while the holder may still run. Watchdogs share its event loop, so they stall with it, and lost() can lie right after a stall.
  • Fencing token: a monotonically increasing number issued with the lock and checked by the storage at write time (WHERE last_token < $2).
  • Issue the token in the same atomic step as the lock, and take it before reading the data.
  • The resource must participate: SQL rows and S3 If-Match can; external APIs need idempotency keys.
  • Redis failover can create two holders and roll back the counter; WAIT reduces this but can't remove it.
  • Redlock needs 3 of 5 votes, a validity time, and fsync=always or a delayed restart. It gives no fencing token, so don't use it for correctness.
  • Session advisory locks break behind transaction-mode pooling. Use pg_advisory_xact_lock.
  • Often the best lock is none: version check, unique constraint or SKIP LOCKED.
بالعامية
  • اسأل الأول: لو اتنين مسكوه، إيه اللي هيبوظ؟ شغل متكرر يبقى efficiency lock، data بايظة يبقى correctness lock.
  • الـ lease بيخلص والـ holder ممكن يكون لسه شغال. الـ watchdog على نفس الـ event loop فبيقف معاه، و lost() ممكن يكدب بعد الـ stall على طول.
  • الـ fencing token: رقم بيزيد بس، بيطلع مع الـ lock والـ storage بيتحقق منه وقت الكتابة (WHERE last_token < $2).
  • طلّع الـ token في نفس الخطوة الـ atomic بتاعة الـ lock، وخده قبل ما تقرا الـ data.
  • الـ resource لازم يشارك: صفوف SQL و S3 If-Match يقدروا، والـ APIs اللي بره عايزة idempotency keys.
  • الـ failover في Redis ممكن يطلّع holders اتنين ويرجّع الـ counter لورا، و WAIT بيقلل ده بس مش بيلغيه.
  • Redlock محتاج 3 أصوات من 5، و validity time، و fsync=always أو delayed restart. ومابيطلّعش fencing token، فماينفعش للـ correctness.
  • الـ session advisory locks بتتكسر ورا transaction-mode pooling، استخدم pg_advisory_xact_lock.
  • وغالبًا أحسن lock هو إن مايبقاش فيه lock: version check أو unique constraint أو SKIP LOCKED.
