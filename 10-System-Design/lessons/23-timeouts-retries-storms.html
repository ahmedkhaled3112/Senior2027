Why this matters · ليه ده مهم

English

A timeout and a retry look like two lines of harmless code. At system level they are the two knobs that decide how a failure spreads. In this lesson's real runs, fixed timeouts let a payments service do 180 of 300 work units after the user had already left; three layers of "just retry three times" turned one user request into 27 calls at the bottom; and a server running at about 19% of its capacity stayed down after a 2-second outage, spending 98% of its time on requests nobody was waiting for. Interviewers ask about these because getting them wrong is how small incidents become long ones.

بالعامية

الـ timeout والـ retry شكلهم سطرين كود ملهمش أي ضرر. لكن على مستوى الـ system هما الزرارين اللي بيحددوا الفشل هينتشر إزاي. في الـ runs الحقيقية بتاعة الدرس ده: الـ timeouts الثابتة خلّت خدمة الـ payments تعمل 180 وحدة شغل من 300 بعد ما اليوزر مشي خلاص؛ وتلات طبقات كل واحدة بتعمل "retry تلات مرات" حوّلت request واحد من يوزر لـ 27 call تحت خالص؛ وسيرفر شغال على حوالي 19% من سعته فضل واقع بعد outage ثانيتين بس، وبيصرف 98% من وقته على requests محدش مستنيها. الـ interviewers بيسألوا في ده لأن الغلط فيه هو اللي بيحوّل incident صغير لـ incident طويل.

Part 1 — Timeouts from p99 🟡 Intermediateالجزء 1 — الـ timeout من الـ p99

English

Writing a timeout is the easy half, and it's covered in 04 Node, lesson 25 (Node's AbortSignal.timeout, Postgres timeouts) and 08 Design Patterns, lesson 22 (the wrappers). The harder question is what number to put in it. Every timeout value trades two costs against each other: false timeouts (healthy but slow requests you kill, and often retry) and hang time (how long a caller holds a socket, a concurrency slot and its memory when the downstream is genuinely dead). Little's Law turns hang time into a resource count: in-flight requests = arrival rate × time held. At 300 requests per second, a 1 s timeout during an outage means 300 requests stuck at once; a 100 ms timeout means 30.

So measure the downstream instead of guessing. Below, a real HTTP inventory service with a realistic shape (a tight body plus a 1.5% slow tail) is driven by autocannon, and every response time is recorded. On this Windows machine timers round up, so I measured that too: setTimeout(5) really sleeps ≈15.2 ms.

The table reads directly: 100 ms is below the p99 and kills about 2% of healthy calls; 1000 ms loses nothing but leaves 300 requests hanging at this rate; the suggested p99 × 1.25 (≈600 ms) loses about 0.7%. Why p99 and not the median? Because the median says nothing about the tail you're cutting off. Why a margin? Because latency isn't stable: the p99 you measured on a Tuesday is not the p99 during a deploy or a traffic spike. And if a user request fans out to 5 calls that each have 1% false timeouts, 1 − 0.99^5 ≈ 4.9% of user requests see at least one.

Distributions also move. The second run doubles the median, as a new release or a bigger table would: the 100 ms candidate jumps from about 2% false timeouts to about 33%, while the 250 ms candidate barely moves because the slow tail, not the body, sets its false-timeout rate. A timeout is therefore a value with a review date: alert on the timeout rate per dependency and re-check it after any deploy that changes the downstream's latency shape.

// مولد أرقام عشوائية بـ seed: نفس الـ seed بيدي نفس السلسلة في كل run
export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

export function percentile(values: number[], p: number): number {
  if (values.length === 0) return NaN;
  const sorted = [...values].sort((a, b) => a - b);
  const i = Math.min(sorted.length - 1, Math.ceil((p / 100) * sorted.length) - 1);
  return sorted[i]!;
}

export interface Served { url: string; close(): Promise<void> }

// سيرفر HTTP حقيقي على port 0: الـ OS هو اللي بيختار port فاضي
export async function serve(handler: http.RequestListener): Promise<Served> {
  const server = http.createServer(handler);
  await new Promise<void>((resolve) => server.listen(0, "127.0.0.1", resolve));
  const { port } = server.address() as AddressInfo;
  return {
    url: `http://127.0.0.1:${port}`,
    close: () =>
      new Promise((resolve) => {
        server.close(() => resolve());
        server.closeAllConnections();
      }),
  };
}

// الحمل open-loop: اليوزرز بيوصلوا بمعدل ثابت مهما السيرفر كان بطيء
export async function openLoop(rps: number, durationMs: number, fire: (i: number, elapsedMs: number) => void): Promise<void> {
  const start = performance.now();
  let sent = 0;
  for (;;) {
    const elapsed = performance.now() - start;
    if (elapsed >= durationMs) return;
    const due = Math.floor((elapsed * rps) / 1000);
    while (sent < due) fire(sent++, elapsed);
    await sleep(4);
  }
}

// حماية: أي port فاضي أو default بيوصّل لخدمة حقيقية، فبنرفضه قبل أي connection
export function privatePort(raw: string | number): number {
  const n = Number(raw);
  if (!/^\d+$/.test(String(raw)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port ${String(raw)}`);
  }
  return n;
}

// بنشغّل الخدمة في process لوحدها عشان الـ event loop بتاعها يتقاس صح من غير حمل الـ load generator
export async function forkService(file: string, args: string[]): Promise<{ url: string; child: ChildProcess; stop(): Promise<void> }> {
  const child = fork(file, args, { stdio: ["ignore", "inherit", "inherit", "ipc"] });
  const port = await new Promise<number>((resolve, reject) => {
    child.once("message", (m: { port: number }) => resolve(m.port));
    child.once("exit", (code) => reject(new Error(`child exited early: ${code}`)));
  });
  return {
    url: `http://127.0.0.1:${privatePort(port)}`,
    child,
    stop: () => new Promise((resolve) => { child.once("exit", () => resolve()); child.kill(); }),
  };
}

import autocannon from "autocannon";
import { mulberry32, percentile, serve, sleep } from "./lab.ts";

// الـ downstream: inventory service بجسم latency طبيعي وذيل بطيء 1.5%
function inventoryService(medianMs: number, seed: number) {
  const rng = mulberry32(seed);
  return serve(async (_req, res) => {
    const normal = Math.sqrt(-2 * Math.log(rng() || 1e-9)) * Math.cos(2 * Math.PI * rng());
    const slowTail = rng() < 0.015;
    const delay = slowTail ? 200 + rng() * 700 : medianMs * Math.exp(0.35 * normal);
    await sleep(delay);
    res.end(`{"sku":"A-100","available":7}`);
  });
}

// القياس: autocannon بيعمل الحمل وإحنا بنسجل latency كل response
async function measure(url: string, seconds: number): Promise<number[]> {
  const samples: number[] = [];
  await autocannon({
    url, connections: 40, duration: seconds,
    setupClient: (client) => { client.on("response", (_status: number, _bytes: number, ms: number) => samples.push(ms)); },
  });
  return samples;
}

function report(label: string, samples: number[], rps: number) {
  const p = (x: number) => percentile(samples, x).toFixed(0).padStart(5);
  console.log(`${label}: n=${samples.length}  p50=${p(50)}ms  p90=${p(90)}ms  p99=${p(99)}ms  p99.9=${p(99.9)}ms  max=${p(100)}ms`);
  console.log("  timeout | false timeouts | hang during outage | in-flight stuck at " + rps + " rps");

  }
}

بالعامية

كتابة الـ timeout نفسها سهلة وموجودة في درس 25 في Node ودرس 22 في الـ Design Patterns. السؤال الأصعب: تحط رقم إيه؟ كل قيمة timeout بتبدّل ضررين ببعض: false timeouts (طلبات سليمة بس بطيئة بتقتلها، وغالبًا بتعمل لها retry) وhang time (الـ caller هيفضل ماسك socket ومكان في الـ concurrency والـ memory قد إيه لو الـ downstream ميت فعلًا). وقانون Little بيحوّل الـ hang time لعدد resources: عدد الـ in-flight = معدل الوصول × الوقت. عند 300 request في الثانية، timeout ثانية وقت outage معناه 300 request واقفين في نفس اللحظة، و100ms معناها 30.

فقيس الـ downstream بدل ما تخمن. فوق: inventory service حقيقي على HTTP بشكل latency واقعي (جسم ضيق + ذيل بطيء 1.5%)، و autocannon بيحمّله، وبنسجل كل response. وعلى الجهاز ده الـ timers بتتقرّب لأعلى، فقستها كمان: setTimeout(5) بينام فعليًا ≈15.2ms.

الجدول بيتقري كده: 100ms أقل من الـ p99 وبتقتل حوالي 2% من الطلبات السليمة؛ 1000ms مبتخسرش حاجة بس بتسيب 300 request معلقين عند المعدل ده؛ والـ p99 × 1.25 (حوالي 600ms) بيخسر حوالي 0.7%. ليه p99 مش الـ median؟ لأن الـ median مبيقولش حاجة عن الذيل اللي إنت قاطعه. وليه margin؟ لأن الـ latency مش ثابتة، الـ p99 بتاع يوم التلات مش هو الـ p99 وقت deploy أو spike. ولو request واحد من اليوزر بيعمل fan-out لـ 5 calls كل واحدة فيها 1% false timeouts، 1 − 0.99^5 ≈ 4.9% من طلبات اليوزرز هتشوف واحد على الأقل.

والتوزيع بيتغير. الـ run التاني ضاعف الـ median زي ما release جديد أو table أكبر بيعمل: الـ 100ms قفزت من حوالي 2% لحوالي 33%، والـ 250ms بالكاد اتحركت لأن الذيل البطيء مش الجسم هو اللي بيحدد نسبة الـ false timeouts بتاعتها. فالـ timeout قيمة ليها معاد مراجعة: اعمل alert على نسبة الـ timeout لكل dependency، وراجعها بعد أي deploy بيغيّر شكل الـ latency.

فين هستخدمه في شغلي؟ عندك fetch لـ PSP أو لـ microservice تانية، وفي الكود timeout: 30000 من زمان ومحدش عارف ليه. افتح الـ APM أو الـ logs، طلّع p50 و p99 و p99.9 لآخر أسبوع، حط الـ timeout = p99 × 1.25، واعمل alert لو نسبة الـ timeouts زادت عن 1%. ولو عندك endpoint بيعمل fan-out لـ 5 خدمات، افتكر إن الـ 1% بتاعة كل خدمة بتبقى 4.9% على اليوزر. الغلطة الشائعة: رقم منقول من project تاني، أو 30000 "عشان نبقى في أمان"، وهو كده معلّق 30 ثانية من الـ concurrency وقت أول outage.
Trade-off: p99 or p99.9? Cutting at p99 means 1 in 100 healthy requests is sacrificed to save hang time. For a fan-out page, a p99.9-based timeout is often the better call: it costs longer hangs (here 875 ms vs ≈600 ms) but fewer user-visible failures. Check your own distribution: with a heavy tail, p99.9 can be many times the p99.
الاختيار بين p99 و p99.9: القطع عند p99 يعني طلب واحد سليم من كل 100 بيتضحى بيه عشان نوفر hang time. في صفحة فيها fan-out كتير، الـ p99.9 غالبًا أحسن: hang أطول (875ms بدل حوالي 600ms هنا) بس فشل أقل بيظهر لليوزر. وبص على التوزيع بتاعك: لو الذيل تقيل، الـ p99.9 ممكن يبقى أضعاف الـ p99.
Interview question: how do you pick a timeout value? Measure the downstream's p50, p99 and p99.9 under real load. Set the timeout just above the p99 (with a margin such as 1.25×), knowing the false-timeout rate at that point and how many in-flight requests a hang would hold at my traffic (Little's Law). Then alert on the timeout rate per dependency and review after deploys, because the latency distribution shifts.

Part 2 — Budgets across hops 🟡 Intermediateالجزء 2 — الميزانية عبر الـ hops

English

Pick good numbers for every hop and you still have a problem, because fixed timeouts ignore how much time is left. Take gateway → orders → payments. The gateway gives up after 1000 ms. Orders has its own 3000 ms timeout for payments, chosen on a different day by a different person. At t=1000 the user is gone, but orders keeps waiting and payments keeps computing for an answer nobody will read.

The fix is a single budget that travels with the request. The caller sends the time remaining (here in a x-timeout-ms header), each hop subtracts what it spent locally, and passes the rest as the next hop's timeout with AbortSignal.timeout(left). A hop that has no budget left doesn't start the call. gRPC has this built in: the deadline travels as the grpc-timeout header (see lesson 10), and @grpc/grpc-js carries it onward when the outgoing call is created with the incoming call as its parent. Send the remaining time rather than an absolute clock value, because two machines' clocks disagree (the same reason lesson 29 distrusts wall clocks across machines).

A budget alone doesn't cancel work already in progress, so each hop also ties its outgoing call to the incoming connection: if the caller closes, abort downstream too (AbortSignal.any over the timeout and res.on("close")). The run below counts payment "work units" in each case. With fixed timeouts all 300 units ran, and 180 of them after the user had left. With the budget propagated, only 160 ran and 20 of those after the user left (the step already in flight when cancel arrived). When orders itself was slow (1100 ms of local work), the fixed version still called payments for all 20 users and burned 300 units for no one, while the propagated version made zero calls.

One real trap, found while writing this: AbortSignal.timeout(797.3) throws RangeError: The value of "delay" is out of range. It must be an integer. (ERR_OUT_OF_RANGE). The remaining budget from performance.now() is almost never an integer, so Math.floor it, or a broad catch will quietly turn every call into a 504, which is exactly what my first version did.

import type { ServerResponse } from "node:http";
import { serve, sleep } from "./lab.ts";

// الـ header بيحمل الوقت الباقي: relative عشان نتجنب clock skew بين الأجهزة
const BUDGET_HEADER = "x-timeout-ms";
const USERS = 20;
const GATEWAY_BUDGET_MS = 1000;
const PAYMENT_STEPS = 15;
const PAYMENT_STEP_MS = 100;

let units = 0;
let unitsAfterClientGone = 0;
let paymentCalls = 0;
let clientGoneAt = Infinity;

function budgetOf(header: string | string[] | undefined): number | null {
  if (typeof header !== "string") return null;
  const ms = Number(header);
  return Number.isFinite(ms) && ms >= 0 ? ms : null;
}

// بيجمع نهاية الميزانية مع قفلة الـ connection من الـ caller في signal واحد
function requestSignal(res: ServerResponse, budgetMs: number | null): AbortSignal {
  const closed = new AbortController();
  res.on("close", () => { if (!res.writableEnded) closed.abort(); });
  if (budgetMs === null) return closed.signal;
  // لازم Math.floor: الـ AbortSignal.timeout بيرمي RangeError مع أي رقم فيه كسور
  return AbortSignal.any([closed.signal, AbortSignal.timeout(Math.max(1, Math.floor(budgetMs)))]);
}

async function run(propagate: boolean, ordersLocalMs: number, label: string) {
  units = 0; unitsAfterClientGone = 0; paymentCalls = 0; clientGoneAt = Infinity;

  const payments = await serve(async (req, res) => {
    paymentCalls++;
    const signal = requestSignal(res, propagate ? budgetOf(req.headers[BUDGET_HEADER]) : null);
    for (let step = 0; step < PAYMENT_STEPS; step++) {
      // الخدمة بتشوف الـ signal قبل كل خطوة عشان تقف بدري
      if (signal.aborted) break;
      await sleep(PAYMENT_STEP_MS);
      units++;
      if (performance.now() > clientGoneAt) unitsAfterClientGone++;
    }
    if (!res.destroyed) { res.statusCode = signal.aborted ? 504 : 200; res.end(); }
  });

  const orders = await serve(async (req, res) => {
    const started = performance.now();
    const budget = propagate ? budgetOf(req.headers[BUDGET_HEADER]) ?? 3000 : 3000;
    const signal = requestSignal(res, propagate ? budget : null);
    await sleep(ordersLocalMs);
    const left = budget - (performance.now() - started);
    // الميزانية خلصت؟ متبدأش call مش هتلحق تخلص
    if (propagate && (signal.aborted || left <= 0)) { if (!res.destroyed) { res.statusCode = 504; res.end(); } return; }
    const headers: Record<string, string> = propagate ? { [BUDGET_HEADER]: String(Math.floor(left)) } : {};
    try {
      // بدون propagation الـ orders عنده timeout ثابت 3 ثواني ومش عارف إن الـ gateway استسلم
      const combined = propagate ? signal : AbortSignal.timeout(3000);
      const upstream = await fetch(`${payments.url}/authorize`, { headers, signal: combined });
      res.statusCode = upstream.status;
    } catch { res.statusCode = 504; }
    if (!res.destroyed) res.end();
  });

  async function gatewayCall(): Promise<number> {
    try {
      const r = await fetch(`${orders.url}/orders`, {
        headers: { [BUDGET_HEADER]: String(GATEWAY_BUDGET_MS) },
        signal: AbortSignal.timeout(GATEWAY_BUDGET_MS),
      });
      return r.status;
    } catch { return 504; }
    finally { clientGoneAt = Math.min(clientGoneAt, performance.now()); }
  }

English

The jitter histogram and the retry helper are in 04 Node, lesson 25, Part 2, so I won't repeat them. The new question here is system-level: what happens to a server with limited capacity after a short outage, depending on how clients retry?

The server below has 8 workers of 40 ms and a FIFO queue, so its real capacity on this machine is ≈160 jobs/s. Clients arrive open-loop at 30 logical requests per second, about 19% of capacity, with a 250 ms attempt timeout and a 2 s give-up deadline. For two seconds the workers stop (the trigger), and then the server is completely healthy again. The first four runs differ only in the retry policy; the fifth breaks the loop while it's happening.

Look at "immediate retry". After the outage ends, recovery is never. Every attempt times out at 250 ms, so each logical request becomes up to about 8 attempts inside its 2 s deadline, and the 214 attempts/s offered exceed the 160/s the server can do. The queue keeps growing (1016 entries by the end), and 98% of the server's time goes to requests whose clients have already left. Nothing is broken any more. The server stays down purely because of the retries it is receiving. That is a metastable failure: the system has two stable states at the same load, healthy and overloaded, a trigger pushes it from one to the other, and a sustaining effect (here, retries) keeps it there after the trigger is gone. Restarting doesn't help, because the retries come straight back.

Backoff and jitter behave differently here than you might expect. Exponential backoff recovered in about 1 s, and it did so by reducing how many attempts fit inside the 2 s deadline (857 total against 3419), not by being clever. Full jitter recovered more slowly, in about 4 s, because shorter average waits fit more attempts into the same deadline (1310 attempts). Jitter's job is to break up synchronised waves, which is where it clearly wins in the Node lesson, where 100 clients started at the same instant. It does not reduce total load. These clients were already spread out by open-loop arrivals, so there was no synchrony for jitter to fix.

Then the fix. The last run is "immediate retry" again, but at t=10 s the server starts dropping work that can't finish before its deadline (the deadline from Part 2). Trigger gone since t=4, still down at t=9 with 608 requests queued, and within a second or two of breaking the loop the queue is empty. Requests that arrived from about t=8 onward were still retrying when the switch flipped, which is why the recovery line reads t=8.

const RUN_MS = 16_000, OUTAGE_FROM = 2_000, OUTAGE_TO = 4_000;

async function runOne(policy: Policy, breakLoopAtMs: number | null) {
  const rng = mulberry32(42);
  const queue: Array<{ res: import("node:http").ServerResponse; deadline: number }> = [];
  let busy = 0, blocked = false, dropDead = false, deadWork = 0, served = 0;
  let attempts = 0;
  const start = performance.now();
  const now = () => performance.now() - start;

  // الـ worker بياخد من الـ queue بالترتيب FIFO، ولو الـ client مشي الشغل بيتهدر
  const pump = () => {
    while (!blocked && busy < SLOTS && queue.length > 0) {
      const job = queue.shift()!;
      // ميت يعني الـ client مشي أو الشغل مش هيلحق يخلص قبل الـ deadline

      if (dead && dropDead) continue;
      busy++;
      void sleep(SERVICE_MS).then(() => {
        busy--; served++;
        if (dead) deadWork++;
        else if (!job.res.destroyed) job.res.end("ok");
        pump();
      });
    }
  };

  const orders = await serve((_req, res) => {
    queue.push({ res, deadline: now() + ATTEMPT_TIMEOUT_MS });
    pump();
  });

    attempts++;
    try {
      const r = await fetch(`${orders.url}/orders`, { signal: AbortSignal.timeout(ATTEMPT_TIMEOUT_MS) });
      await r.text();
      return r.ok;
    } catch { return false; }

    const at = now();

      if (await attempt()) { results.push({ at, ok: true }); return; }

      if (wait < 0 || now() + wait - at > GIVE_UP_MS) { results.push({ at, ok: false }); return; }
      if (wait > 0) await sleep(wait);

    const b = results.filter((r) => Math.floor(r.at / 1000) === s);
    return b.length ? b.filter((r) => r.ok).length / b.length : 1;
  };

      for (let j = s; j < secs; j++) if (okRate(j) < 0.9) { good = false; break; }

    }
    return -1;
  };

  const okAll = results.filter((r) => r.ok).length;
  const after = results.filter((r) => r.at > OUTAGE_TO);

function simulate(loadPct: number, delay: Delay, dropDead: boolean, useBudget: boolean): number | null {
  let tokens = 0;
  const rng = mulberry32(1234 + loadPct);
  const rps = (CAPACITY * loadPct) / 100;
  const agenda = new Map<number, Array<() => void>>();
  const at = (t: number, fn: () => void) => { const k = Math.ceil(t); (agenda.get(k) ?? agenda.set(k, []).get(k)!).push(fn); };
  type Job = { deadline: number; done: () => void; expired: () => boolean };
  const queue: Job[] = [];
  let free = SLOTS, clock = 0, head = 0;
  const results: Array<[number, boolean]> = [];
  const pump = () => {
    while (clock >= OUT_TO || clock < OUT_FROM) {
      if (free === 0 || head >= queue.length) return;
      const j = queue[head++]!;
      if (dropDead && j.expired()) continue;
      free--;
      at(clock + SERVICE_MS, () => { free++; j.done(); pump(); });
    }
  };
  const logical = () => {
    const born = clock;
    const attempt = (n: number) => {
      let finished = false;
      const fail = () => {
        if (finished) return;
        finished = true;
        const wait = delay ? delay(n, rng) : -1;
        const budgetOk = !useBudget || tokens >= 1;
        if (wait < 0 || !budgetOk || clock + wait - born > GIVE_UP_MS) results.push([born, false]);
        else { if (useBudget) tokens -= 1; at(clock + wait + (wait === 0 ? 1 : 0), () => attempt(n + 1)); }
      };
      const deadline = clock + ATTEMPT_MS;
      queue.push({ deadline, expired: () => clock + SERVICE_MS > deadline, done: () => { if (!finished && clock <= deadline) { finished = true; results.push([born, true]); } } });
      pump();
      at(deadline, fail);
    };
    tokens = Math.min(50, tokens + 0.1);
    attempt(0);
  };
  let next = 0;
  for (clock = 0; clock < RUN_MS; clock++) {
    for (const fn of agenda.get(clock) ?? []) fn();
    agenda.delete(clock);
    if (clock === OUT_TO) pump();
    while (next <= clock) { logical(); next += -Math.log(1 - rng()) * (1000 / rps); }
  }
  // آخر 3 ثواني من الـ run مش محسوبة: طلباتها لسه مخلصتش
  const lastGood = RUN_MS / 1000 - 3;
  for (let s = OUT_TO / 1000; s <= lastGood - 3; s++) {
    let good = true;
    for (let j = s; j <= lastGood && good; j++) {
      const b = results.filter(([t]) => t >= j * 1000 && t < (j + 1) * 1000);
      if (b.length && b.filter(([, ok]) => ok).length / b.length < 0.9) good = false;
    }
    if (good) return s - OUT_TO / 1000;
  }
  return null;
}

Part 4 — Amplification & budgets 🟡 Intermediateالجزء 4 — الـ amplification والـ budgets

English

Retries multiply across layers. Three services that each retry three times means 3 × 3 × 3 = 27 calls at the leaf for one user request, and the chain below counts it for real, over HTTP, with a leaf that always returns 503. Retrying at one layer takes it back to 3. Inner-layer retries are cheaper than outer-layer ones because a retry at the edge re-traverses every hop in between (400 internal calls for 40 users against 240). The usual choice is to retry once, at the layer closest to the dependency and with the most context about idempotency, and to send everything else straight up.

A retry budget caps the ratio instead of the attempts: each request deposits 0.1 tokens and each retry costs 1, so retries can't exceed about 10% of requests. It adapts by itself: when nothing fails it does nothing, and when everything fails the extra load is bounded at 10%. Across three hops it gave 1.3 leaf calls per user instead of 27. Real proxies offer this: Envoy has a retry_budget on its circuit breakers (budget_percent, min_retry_concurrency); Not run here, because Envoy is a downloaded executable.

Google SRE's client-side adaptive throttling goes one step further: each client tracks, over a window (two minutes in their setup), requests attempted and accepts from the backend, and rejects new requests locally with probability max(0, (requests − K × accepts) / (requests + 1)). Under normal conditions accepts ≈ requests, so this is 0. As the backend rejects more, clients shed load themselves before spending a network round trip. K sets how much over-the-limit traffic may still reach the backend (they generally prefer K = 2, and a smaller K is more aggressive).

The table compares policies under 50% failure, and it shows something worth understanding. Against a backend that randomly fails 50% (a bad replica, a flaky dependency), naive retries do help (88% success at 1.75× load), and a budget keeps load near 1.1×. But in that same case adaptive throttling with K = 2 collapses to 10.9% success, because 50% acceptance sits exactly on the K = 2 boundary, any noise tips it into rejecting locally, and those local rejections count in requests but not accepts, which pushes it further: a feedback loop. Against a backend that is actually capacity-limited at 50% of the offered load, the picture flips: 3 attempts gives no extra success at 2.06× load (pure waste), and adaptive K = 2 sits at 0.99×, while K = 1.1 cuts the load to 0.46× at 46% success. So adaptive throttling is a tool for overload rejections. If your "failures" are application errors, or the backend rejects randomly, count only explicit overload signals (429/503) as rejections, or the throttle will starve healthy traffic.

export class RetryBudget {
  private tokens = 0;
  private readonly ratio: number;
  private readonly cap: number;
  constructor(ratio = 0.1, cap = 50) {
    this.ratio = ratio;
    this.cap = cap;
  }
  onRequest() {
    this.tokens = Math.min(this.cap, this.tokens + this.ratio);
  }
  tryRetry() {
    if (this.tokens >= 1) {
      this.tokens -= 1;
      return true;
    }
    return false;
  }
}

// الـ adaptive throttling بتاع Google SRE: العميل بيرفض لوحده لما الـ accepts تقل
class AdaptiveThrottle {
  private readonly buckets: Array<{ requests: number; accepts: number }>;
  private cursor = 0;
  private readonly k: number;
  private readonly rng: () => number;
  // نافذة متحركة: 3 ثواني هنا، و Google بتستخدم دقيقتين في الإنتاج
  private readonly timer: NodeJS.Timeout;
  constructor(k: number, seed: number) {
    this.k = k;
    this.rng = mulberry32(seed);
    this.buckets = Array.from({ length: 30 }, () => ({ requests: 0, accepts: 0 }));
    this.timer = setInterval(() => {
      this.cursor = (this.cursor + 1) % this.buckets.length;
      this.buckets[this.cursor] = { requests: 0, accepts: 0 };
    }, 100);
  }
  stop() {
    clearInterval(this.timer);
  }
  rejectProbability() {
    const { requests, accepts } = this.buckets.reduce(
      (t, b) => ({ requests: t.requests + b.requests, accepts: t.accepts + b.accepts }),
      { requests: 0, accepts: 0 },
    );
    return Math.max(0, (requests - this.k * accepts) / (requests + 1));
  }
  allow() {
    this.buckets[this.cursor]!.requests++;
    return this.rng() >= this.rejectProbability();
  }
  accepted() {
    this.buckets[this.cursor]!.accepts++;
  }
}

async function run(name: string, kind: Backend, policy: { attempts: number; budget?: boolean; k?: number }) {
  const rng = mulberry32(99);
  let backendCalls = 0;
  let tokens = 0;
  let lastRefill = performance.now();
  const CAPACITY_PER_SEC = 100;
  const backend = await serve((_req, res) => {
    backendCalls++;
    let fail: boolean;
    if (kind === "capacity-50%") {
      // الـ backend ده بيستحمل 100 request في الثانية بس، والزيادة 503
      const t = performance.now();
      tokens = Math.min(CAPACITY_PER_SEC, tokens + ((t - lastRefill) / 1000) * CAPACITY_PER_SEC);
      lastRefill = t;
      fail = tokens < 1;
      if (!fail) tokens -= 1;
    } else {
      fail = rng() < (kind === "random-50%" ? 0.5 : 0.9);
    }
    res.statusCode = fail ? 503 : 200;
    res.end();
  });
  const throttle = policy.k ? new AdaptiveThrottle(policy.k, 1) : null;
  const budget = policy.budget ? new RetryBudget() : null;
  let ok = 0;
  let logical = 0;
  let localRejects = 0;
  const pending: Promise<void>[] = [];

  const one = async () => {
    logical++;
    budget?.onRequest();
    for (let attempt = 1; attempt <= policy.attempts; attempt++) {
      if (throttle && !throttle.allow()) {
        localRejects++;
        return;
      }
      const r = await fetch(backend.url).catch(() => null);
      await r?.text();
      if (r?.ok) {
        ok++;
        throttle?.accepted();
        return;
      }
      if (attempt < policy.attempts && budget && !budget.tryRetry()) return;
      if (attempt < policy.attempts) await sleep(5);
    }
  };

  await openLoop(200, 5000, () => {
    pending.push(one());
  });
  await Promise.all(pending);
  throttle?.stop();
  await backend.close();
  return { name, success: ((ok / logical) * 100).toFixed(1), load: (backendCalls / logical).toFixed(2), localRejects };
}

Retries multiply: 3 layers × 3 attempts = 27 calls at the leaf per request (counted in this lesson's chain), and when the failure is overload, those extra calls deepen it. Retry at one layer only, cap the retried share with a budget (about 10% of requests), and have clients throttle themselves on explicit overload signals (429 or 503).

Part 5 — When not to retry 🟡 Intermediateالجزء 5 — إمتى متعملش retry

English

Every retry is a bet that repeating the request is safe and might work this time. The fake PSP below records the charge first and then answers slowly, the way a real payment provider can. The client times out at 300 ms, retries, and the PSP has charged three times for one order. An Idempotency-Key makes the retry safe: same key, same charge, and the third attempt gets the original result with replay: true. The full design (storage, in-flight requests, expiry) is in lesson 30.

The decision depends on what actually happened, so make it a function with tests, not a retries: 3 setting. The rule underneath: a timeout means the outcome is unknown, so it is only retryable when repeating is harmless. A connect error is different: the request never reached the server, so even a POST is safe. 4xx means your request is wrong and will be wrong again. 429 and 503 usually carry Retry-After (seconds or an HTTP date, RFC 9110), which you should honour instead of your own backoff.

Finally, count time, not attempts. Three attempts at a 1000 ms timeout with 500 ms backoff against a hung server took about 4054 ms in this run, far past the 1500 ms the caller may have. A total deadline stopped at about 1509 ms with one attempt, and that deadline is the same budget from Part 2.

// كل نتيجة ممكنة لـ attempt: status، أو timeout بعد ما الطلب اتبعت، أو network قبل ما يوصل
export type Outcome =
  | { kind: "status"; status: number; retryAfter?: string | null }
  | { kind: "timeout" }
  | { kind: "connect-error" };

export interface RequestInfo {
  method: string;
  idempotencyKey?: string;
}

export interface Decision {
  retry: boolean;
  reason: string;
  waitMs?: number;
}

const IDEMPOTENT_METHODS = new Set(["GET", "HEAD", "PUT", "DELETE", "OPTIONS"]);

// الـ retry آمن بس لو تكرار الطلب مش هيعمل أثر تاني على الـ server
export function isIdempotent(req: RequestInfo): boolean {
  return IDEMPOTENT_METHODS.has(req.method.toUpperCase()) || Boolean(req.idempotencyKey);
}

// بيقبل الشكلين بتوع RFC 9110: عدد ثواني أو تاريخ HTTP
export function parseRetryAfter(value: string | null | undefined, nowMs: number): number | null {
  if (!value) return null;
  const v = value.trim();
  if (/^\d+$/.test(v)) return Number(v) * 1000;
  const date = Date.parse(v);
  return Number.isNaN(date) ? null : Math.max(0, date - nowMs);
}

export function isRetryable(outcome: Outcome, req: RequestInfo, nowMs = Date.now()): Decision {
  if (outcome.kind === "connect-error") return { retry: true, reason: "never reached the server" };
  if (outcome.kind === "timeout") {
    return isIdempotent(req)
      ? { retry: true, reason: "timeout on an idempotent request" }
      : { retry: false, reason: "timeout on non-idempotent: outcome unknown" };
  }
  const { status, retryAfter } = outcome;
  if (status < 400) return { retry: false, reason: "success" };
  if (status === 429 || status === 503) {
    const waitMs = parseRetryAfter(retryAfter, nowMs) ?? undefined;
    if (!isIdempotent(req)) return { retry: false, reason: "busy, but not idempotent" };
    return waitMs === undefined
      ? { retry: true, reason: "busy" }
      : { retry: true, reason: "busy, honour Retry-After", waitMs };
  }
  if (status === 408) {
    return isIdempotent(req)
      ? { retry: true, reason: "request timeout" }
      : { retry: false, reason: "408 on non-idempotent" };
  }
  if (status < 500) return { retry: false, reason: "client error: a retry repeats the same mistake" };
  if (status === 501 || status === 505) return { retry: false, reason: "server says never" };
  return isIdempotent(req)
    ? { retry: true, reason: "transient server error" }
    : { retry: false, reason: "5xx on non-idempotent: may have run" };
}

Cheat sheet · الخلاصة

  • A timeout trades false timeouts for hang time. In-flight during an outage = rate × timeout (Little's Law).
  • Measure p50/p99/p99.9; set the timeout at about p99 × 1.25; alert on the timeout rate; review after deploys.
  • Fan-out multiplies false timeouts: 1 − (1 − p)^n.
  • One deadline across hops: send the remaining time, subtract local work, don't start what can't finish; Math.floor before AbortSignal.timeout.
  • Metastable failure: the trigger is gone and the system stays down, because retries keep it overloaded. Breaking the loop, not restarting, is the way out.
  • Backoff reduces attempts in a time window. Jitter only desynchronises; it doesn't reduce load.
  • 3 layers × 3 attempts = 27 calls at the leaf. Retry at one layer, with a budget of about 10% of requests.
  • Adaptive throttling (max(0,(requests − K·accepts)/(requests+1))) works against capacity rejections. Count only overload signals (429/503), or it collapses on random errors.
  • Timeout on a non-idempotent call = unknown outcome: no retry without an idempotency key. 4xx: never. 429/503: honour Retry-After.
  • Count time, not attempts: a total deadline beats "3 attempts".
بالعامية
  • الـ timeout بيبدّل false timeouts بـ hang time. عدد الـ in-flight وقت الـ outage = المعدل × الـ timeout (قانون Little).
  • قيس p50 و p99 و p99.9، حط الـ timeout عند حوالي p99 × 1.25، واعمل alert على نسبة الـ timeouts، وراجع بعد الـ deploys.
  • الـ fan-out بيضرب الـ false timeouts: 1 − (1 − p)^n.
  • deadline واحد عبر الـ hops: ابعت الوقت الباقي، اطرح الشغل المحلي، متبدأش حاجة مش هتخلص، وMath.floor قبل AbortSignal.timeout.
  • الـ metastable failure: الـ trigger راح والنظام لسه واقع بسبب الـ retries. الحل كسر الـ loop مش الـ restart.
  • الـ backoff بيقلل عدد المحاولات في الوقت. والـ jitter بيفك التزامن بس، مش بيقلل الحمل.
  • 3 طبقات × 3 محاولات = 27 call تحت. الـ retry في طبقة واحدة، بـ budget حوالي 10% من الطلبات.
  • الـ adaptive throttling (max(0,(requests − K·accepts)/(requests+1))) شغال ضد رفض السعة. احسب إشارات الـ overload بس (429/503)، وإلا هينهار مع الـ errors العشوائية.
  • الـ timeout على call غير idempotent = نتيجة مش معروفة: مفيش retry من غير idempotency key. 4xx أبدًا. 429/503 التزم بـ Retry-After.
  • احسب وقت مش محاولات: deadline كلي أحسن من "3 محاولات".
