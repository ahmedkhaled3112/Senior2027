Why this matters · ليه ده مهم

English

A design doc that says "we'll autoscale" has not answered anything. How many instances at peak? What happens in the two minutes before new ones are ready? What does one request cost, and who pays for it? And the infrastructure choices (probes, CPU limits, discovery, config rollout) decide whether a healthy design survives a deploy. Interviewers ask for the numbers behind the boxes, and on-call rotations punish designs that never had any.

Part 1 — The capacity model 🟡 Intermediateالجزء 1 — موديل الـ capacity

English

Capacity is the highest load a service sustains while still meeting a latency target, not the highest RPS you ever saw on a graph. So you load test a real endpoint (a real Postgres, real serialization, durable commits) and step the concurrency up until p99 crosses the target. How to load test properly, including coordinated omission, is in 04 · Profiling & Load Testing. Here the output is a number you can design with.

Three steps. First check the load generator's own ceiling on an empty endpoint, or you end up measuring autocannon. Then find the knee: below it, more concurrency gives more throughput at roughly the same latency; after it, throughput goes flat and only the queue grows, which is Little's Law (L = λW, with λ capped, more L can only become more W). Finally convert to instances:

instances = ceil(peak × growth / (capacity_per_instance × headroom)) + spare

Headroom (commonly 0.6–0.7) keeps you off the knee and absorbs noise and a dependency slowing down. The + spare is N+1: lose one instance and the rest still carry the peak. If you run across zones, size it so that losing a whole zone still works.

Adding instances doesn't help forever. The Universal Scalability Law models it: X(N) = λN / (1 + σ(N−1) + κN(N−1)). σ is contention (the part that queues, such as locks and a shared DB) and κ is coherency (the cost of instances having to agree with each other). With κ > 0 throughput peaks at N* = √((1−σ)/κ) and then falls. Fit it on a handful of measured points and you learn where to stop buying instances and start fixing the shared bottleneck. In this run the API workers all share one Postgres on the same machine, and the fit peaks near 7 workers; the measured 12 and 16 are below 6 and 8.

import { readFileSync } from "node:fs";

type Point = { connections: number; rps: number; p99: number };
const data = JSON.parse(readFileSync(new URL("./capacity.json", import.meta.url), "utf8"));

// الـ ⁦capacity =⁩ أعلى rps لسه بيحقق الـ p99 المطلوب، مش أعلى rps والسلام
const capacityAt = (points: Point[], targetP99Ms: number) =>
  Math.max(...points.filter((p) => p.p99 <= targetP99Ms).map((p) => p.rps));

// عدد الـ instances: الـ peak بعد النمو، على الـ capacity بعد الـ headroom، زائد واحد احتياطي
function instancesFor(o: { peakRps: number; growth: number; capacityPerInstance: number; headroom: number; spare: number }) {
  const usable = o.capacityPerInstance * o.headroom;
  return Math.ceil((o.peakRps * o.growth) / usable) + o.spare;
}

// تركيب الـ USL: بنحوّلها لـ quadratic خطية ونحل least squares من غير intercept
function fitUSL(points: { n: number; x: number }[]) {
  const x1 = points.find((p) => p.n === 1)!.x;
  const rows = points.filter((p) => p.n > 1).map((p) => ({ a: p.n - 1, b: p.n * (p.n - 1), y: p.n / (p.x / x1) - 1 }));
  const s = (f: (r: (typeof rows)[number]) => number) => rows.reduce((t, r) => t + f(r), 0);
  const [aa, ab, bb, ay, by] = [s((r) => r.a * r.a), s((r) => r.a * r.b), s((r) => r.b * r.b), s((r) => r.a * r.y), s((r) => r.b * r.y)];
  const det = aa * bb - ab * ab;
  const sigma = (ay * bb - by * ab) / det;
  const kappa = (aa * by - ab * ay) / det;
  const predict = (n: number) => (x1 * n) / (1 + sigma * (n - 1) + kappa * n * (n - 1));
  return { x1, sigma, kappa, peakN: Math.sqrt((1 - sigma) / kappa), predict };
}

بالعامية

الـ capacity هي أعلى load الـ service بيستحمله وهو لسه ملتزم بالـ latency target، مش أعلى RPS شفته على graph. فبتعمل load test على endpoint حقيقي (Postgres حقيقي، serialization حقيقي، commits durable) وتزوّد الـ concurrency خطوة خطوة لحد ما الـ p99 يعدّي الـ target. إزاي تعمل load test صح، ومعاه موضوع الـ coordinated omission، موجود في درس الـ Profiling والـ Load Testing، وهنا المطلوب رقم تعرف تصمم بيه.

3 خطوات. الأول شوف سقف الـ load generator نفسه على endpoint فاضي، وإلا هتقيس autocannon مش الـ API. بعدين دوّر على الـ knee: قبله، أي concurrency زيادة بتجيب throughput زيادة بنفس الـ latency تقريبًا؛ بعده، الـ throughput بيبقى مسطح والطابور بس اللي بيكبر، ودي Little's Law (L = λW: لما الـ λ توصل سقفها، أي L زيادة لازم تبقى W زيادة). وأخيرًا حوّل لعدد instances بالمعادلة:

instances = ceil(peak × growth / (capacity_per_instance × headroom)) + spare

الـ headroom (غالبًا 0.6–0.7) بيخليك بعيد عن الـ knee وبيمتص الـ noise وأي dependency تبطّأ. والـ spare هو الـ N+1: لو instance وقع، الباقيين يشيلوا الـ peak. ولو شغال على zones، حسبها إن zone كاملة ممكن تقع والباقي يكفي.

زيادة الـ instances مش بتفيد للأبد. الـ Universal Scalability Law بتوصف ده: X(N) = λN / (1 + σ(N−1) + κN(N−1)). الـ σ هي الـ contention (الجزء اللي بيقف في طابور، زي الـ locks والـ DB المشتركة)، والـ κ هي الـ coherency (تكلفة إن الـ instances يتفقوا مع بعض). لو κ أكبر من صفر، الـ throughput بيوصل قمة عند N* = √((1−σ)/κ) وبعدها بينزل. تركّبها على كام نقطة مقاسة فتعرف إمتى توقف شراء instances وتبدأ تصلّح الـ bottleneck المشترك. في التجربة دي كل الـ workers على Postgres واحد وعلى نفس الجهاز، والـ fit قمته قريب من 7، والـ 12 و 16 المقاسين أقل من 6 و 8 فعلًا.

فين هستخدمه في شغلي؟ الـ PM قال "الحملة الجاية هتجيب 5× traffic". قبل ما تعمل أي تصعيد، شغّل الـ sweep ده على staging شبه الـ production على POST /orders الحقيقي، طلّع الـ capacity عند p99 = 300 ms، واحسب عدد الـ instances. ولو الـ USL قالتلك إن القمة عند 8 workers، يبقى الحل مش instances أكتر: الحل connection pooling (PgBouncer) أو read replica أو cache. ده اللي بيحوّل "هنعمل scale" لـ "محتاجين 14 instance والـ DB لازم تتغير قبل الحملة بأسبوعين".
Trade-off: headroom is paid idle capacity 0.5 headroom doubles the bill for quiet hours and buys you time when a dependency slows down. 0.8 is cheap and leaves about nothing for noise. Pick it per service: payment checkout gets more than a nightly report. Autoscaling (Part 2) is how you stop paying headroom at 4 am.
الـ headroom ده capacity فاضية بتدفع تمنها. 0.5 بتضاعف الفاتورة في الساعات الهادية وبتديك وقت لما dependency تبطّأ، و 0.8 رخيصة بس مبتسيبش حاجة للـ noise. اختار لكل service لوحده: الـ checkout بتاع الدفع ياخد أكتر من تقرير بالليل. والـ autoscaling (الجزء 2) هو اللي بيوقف دفع الـ headroom الساعة 4 الفجر.
Don't trust a fit outside the points you measured Eight noisy points on a shared machine: N=4 is visibly off the curve. Use the fit for its direction ("the shared Postgres caps us near 7") and measure again on production-shaped hardware before you sign a capacity number.
متثقش في الـ fit بره النقط اللي قستها. 8 نقط noisy على جهاز مشترك، والـ N=4 واضح إنها بعيدة عن المنحنى. استخدم النتيجة كاتجاه ("الـ Postgres المشترك سادد عند حوالين 7") وقيس تاني على hardware شبه الـ production قبل ما تمضي على رقم capacity.
Interview question "A load test reached 20,000 RPS. Can we plan the peak of 18,000 RPS on that instance count?" → No. 20,000 is the throughput ceiling, not capacity. I'd take the highest RPS that still meets the p99 target, apply 0.6–0.7 headroom, add N+1 (or a whole zone), and check the generator wasn't the limit and that the data volume and cache hit ratio match production.
"الـ load test وصل 20,000 RPS، ينفع نخطط للـ peak بتاع 18,000 بنفس عدد الـ instances؟" ← لأ. الـ 20,000 دي سقف الـ throughput مش الـ capacity. هاخد أعلى RPS لسه محقق الـ p99، وأطبق headroom 0.6–0.7، وأزود N+1 (أو zone كاملة)، وأتأكد إن الـ generator مكانش هو الحد وإن حجم الـ data ونسبة الـ cache hit زي الـ production.

Part 2 — Autoscaling 🟡 Intermediateالجزء 2 — الـ Autoscaling

English

Three families. Metrics-based (reactive) watches a metric and scales: Kubernetes' HPA runs desired = ceil(current × currentMetric / target) every 15 s by default, skips changes within a 10% tolerance, and applies a 5-minute stabilization window on scale-down. Scheduled scales on a calendar: you know the sale starts at 20:00. Predictive forecasts from history (AWS' predictive scaling looks for daily and weekly patterns) and launches capacity ahead of the forecast.

The enemy is startup delay: image pull, boot, warm-up and readiness can take 60–180 s, and traffic doesn't wait. The simulator below runs one service through a day with a flash sale: demand jumps by 3000 RPS in 60 s, while each new instance takes 60–180 s to become ready. Reading its table: CPU-based and queue-lag reactive policies both drop about 0.9–1%, because no reactive signal beats the boot time, and the scheduled policy drops 0 for about 22% more instance-hours. Cooldown fixes flapping (156 reversals without it, 50 with a 300 s cooldown, 16 with a 10% band on top). Startup delay moves drops more than the metric does: 30 s gives 0.39%, 180 s gives 1.15%. And predictive alone loses the most (2.71%), because a first-ever sale isn't in yesterday's history.

CPU is a poor metric once a service saturates: it pins at 100% and stops telling you how far behind you are. Better signals are queue depth or lag (for workers, KEDA scales on this), requests per instance, and event-loop lag. In practice you combine them: scheduled for what you know, reactive for what you don't, and a floor high enough for the spike you cannot predict. Scale out fast and in slowly: too late means dropped requests, too early means paying for idle machines.

function mulberry32(a: number) {
  return () => {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

const TICK = 10, DAY = 86400, CAP = 100, MIN = 4, MAX = 80, TARGET = 0.6, SALE = 20 * 3600;
const base = (t: number) => 250 + 450 * (0.5 - 0.5 * Math.cos((2 * Math.PI * (t - 4 * 3600)) / DAY));
// الـ flash sale: 3000 rps زيادة في دقيقة، وبعدين بتنزل بـ exp بـ tau = 12 دقيقة
const sale = (t: number) => (t < SALE ? 0 : Math.min(1, (t - SALE) / 60) * 3000 * Math.exp(-(t - SALE) / 720));

type View = { t: number; ready: number; cpu: number; backlog: number; servedRps: number };
type Policy = { name: string; cooldownIn: number; tolerance?: number; decide: (v: View) => number };

function run(p: Policy, startup: [number, number] = [60, 180], seed = 42) {
  const rnd = mulberry32(seed);
  let ready = MIN, pending: number[] = [], backlog = 0, dropped = 0, total = 0, instSec = 0, flaps = 0;
  let lastDir = 0, lastActionAt = -1e9, lastInAt = -1e9, maxLag = 0, actions = 0, served60 = 0, cap60 = 0;
  for (let t = 0; t < DAY; t += TICK) {
    pending = pending.filter((at) => (at <= t ? (ready++, false) : true));
    const arrivals = (base(t) + sale(t)) * (0.95 + rnd() * 0.1) * TICK;
    total += arrivals;
    const capacity = ready * CAP * TICK;
    const served = Math.min(backlog + arrivals, capacity);
    backlog += arrivals - served;
    // الطلب اللي هيستنى أكتر من 5 ثواني هيعمل timeout، فبنعدّه dropped
    const maxBacklog = ready * CAP * 5;
    if (backlog > maxBacklog) { dropped += backlog - maxBacklog; backlog = maxBacklog; }
    maxLag = Math.max(maxLag, backlog / (ready * CAP));
    served60 += served; cap60 += capacity; instSec += (ready + pending.length) * TICK;
    if (t % 60 === 0 && t > 0) {
      const v: View = { t, ready, cpu: served60 / cap60, backlog, servedRps: served60 / 60 };
      served60 = cap60 = 0;
      let desired = Math.min(MAX, Math.max(MIN, p.decide(v)));
      const have = ready + pending.length;
      // الـ tolerance: لو الفرق صغير متعملش حاجة، زي الـ 10% بتاعة HPA
      if (Math.abs(desired / have - 1) <= (p.tolerance ?? 0)) desired = have;
      const dir = Math.sign(desired - have);
      if (dir > 0) {
        for (let i = 0; i < desired - have; i++) pending.push(t + startup[0] + rnd() * (startup[1] - startup[0]));
      } else if (dir < 0 && t - lastInAt >= p.cooldownIn && t - lastActionAt >= p.cooldownIn) {
        ready = Math.max(MIN, ready - (have - desired));
        lastInAt = t;
      }
      const acted = dir > 0 || (dir < 0 && lastInAt === t);
      if (acted) {
        if (lastDir !== 0 && dir !== lastDir && t - lastActionAt < 600) flaps++;
        lastDir = dir; lastActionAt = t; actions++;
      }
    }
  }
  return { name: p.name, dropped: Math.round(dropped), pct: ((dropped / total) * 100).toFixed(2), instH: Math.round(instSec / 3600), flaps, actions, maxLag: maxLag.toFixed(1) };
}

const cpu = (cooldownIn: number, name: string, tolerance = 0): Policy => ({

Part 3 — Cost monitoring 🟡 Intermediateالجزء 3 — مراقبة التكلفة

English

A monthly bill can't tell you whether you're efficient. Cost per 1000 requests and per tenant can: it's a unit you can compare against revenue per tenant and against last month. To get it you need tags on every resource (team, service, env, and tenant where it's feasible), plus a metric for "share of spend with no owner", because untagged cost is cost nobody will reduce.

Then a simple anomaly check per tenant and service. Don't use mean + standard deviation: a spike inflates both and hides itself. Use a rolling median plus MAD (median absolute deviation, scaled by 1.4826 to be comparable with σ), and require a minimum ratio so that tiny absolute changes don't page anyone. The run below flags only the planted spike on day 26: a webhook retry loop inflating egress 40×, at $110.59 against a $3.52 baseline. Design-time estimates are the next step: see 44 · Cost & over-engineering.

function median(xs: number[]) {
  const s = [...xs].sort((a, b) => a - b), m = s.length >> 1;
  return s.length % 2 ? s[m] : (s[m - 1] + s[m]) / 2;
}
function anomalies(series: { date: string; usd: number }[], minDays = 7, k = 6, minRatio = 1.3) {
  const hits: string[] = [];
  series.forEach((p, i) => {
    const hist = series.slice(Math.max(0, i - 14), i).map((x) => x.usd);
    if (hist.length < minDays) return;
    const med = median(hist);
    const mad = median(hist.map((x) => Math.abs(x - med))) * 1.4826;
    // الشرطين مع بعض: بعيد إحصائيًا وكمان فرق فلوس يستاهل

  });
  return hits;
}

Part 4 — Containers & Kubernetes for designers 🟡 Intermediateالجزء 4 — الـ Containers و Kubernetes من منظور الـ designer

English

You don't need to operate a cluster to design for one (operating it is section 11, Testing, Security & DevOps; the image and the app side are in 04 · Config & Docker and 04 · Deployment). As a designer you need four facts.

  • Readiness ≠ liveness. Readiness answers "send me traffic?", and failing it takes the pod out of the endpoints. Liveness answers "am I wedged beyond repair?", and failing it restarts the container. Startup covers slow boots. Liveness must not check your dependencies: if it checks Postgres, a Postgres blip restarts every pod at once.
  • Requests vs limits. Requests reserve capacity for scheduling; limits are enforced at runtime. A CPU limit is a CFS quota: use your quota within the 100 ms period and all your threads stop until the next period, including GC helpers. The simulator below uses 0.42 cores on average, and a 1000m limit still produces a p99 of 66 ms where no limit gives 2 ms. Many teams set memory limits and leave CPU limit off. A memory limit is an OOM kill, not a slowdown.
  • Rolling updates are controlled by maxSurge and maxUnavailable, and they're only safe with a readiness probe and a graceful drain. Removing a pod from endpoints and sending it SIGTERM race each other, hence the common preStop sleep. The app must flip readiness, keep serving until the LB sees it, then stop accepting and finish in-flight requests. With a real Node server and a Node poller as the LB stand-in: 6 of 157 requests failed with an instant stop, 0 of 179 with the drain.
  • Getting traffic in. Community ingress-nginx was retired in March 2026, with no further releases or security fixes. Gateway API is the recommended path for new designs.

import http from "node:http";
import { once } from "node:events";
import { setTimeout as sleep } from "node:timers/promises";

type Replica = { name: string; port: number; drain: () => Promise<void>; crash: () => void };

async function startReplica(name: string): Promise<Replica> {
  let ready = true;
  const server = http.createServer(async (req, res) => {
    if (req.url === "/readyz") { res.statusCode = ready ? 200 : 503; return res.end(); }
    if (req.url === "/healthz") { res.statusCode = 200; return res.end(); }
    // طلب order بياخد 40 ms، يعني فيه طلبات شغالة وقت الـ shutdown
    await sleep(40);
    res.end(name);
  });
  server.keepAliveTimeout = 1000;
  server.listen(0, "127.0.0.1");
  await once(server, "listening");
  return {
    name,
    port: (server.address() as { port: number }).port,
    async drain() {
      // (1) الأول قول إنك مش ready، وإنت لسه بتخدم
      ready = false;
      // (2) استنى الـ LB يشوف ده: أكتر من فترة الـ poll
      await sleep(900);
      // (3) بعدين بطّل تقبل connections جديدة وخلّص اللي شغال
      server.close();
      server.closeIdleConnections();
      await once(server, "close");
    },
    crash() {
      server.close();
      server.closeAllConnections();
    },
  };
}

function simulate(limitMillicores: number) {
  const PERIOD = 100, quotaPerPeriod = (limitMillicores / 1000) * PERIOD;
  let quota = quotaPerPeriod, throttled = 0, periods = 0, wasThrottled = false, cpuUsed = 0;
  const q: { at: number; left: number }[] = [];
  const latencies: number[] = [];
  let gcLeft = 0;
  for (let t = 0; t < 30000; t++) {
    if (t % PERIOD === 0) {
      periods++; if (wasThrottled) throttled++;
      wasThrottled = false; quota = quotaPerPeriod;
    }
    // طلب كل 5 ms بياخد 1.5 ms CPU، يعني 0.3 core على الـ event loop
    if (t % 5 === 0) q.push({ at: t, left: 1.5 });
    // الـ GC: كل ثانية، 40 ms على 3 helper threads بياكلوا من نفس الـ quota
    if (t % 1000 === 0) gcLeft = 40;
    const wantsWork = q.length > 0 || gcLeft > 0;
    if (wantsWork && quota <= 0) { wasThrottled = true; continue; }
    if (gcLeft > 0) { gcLeft--; quota -= 3; cpuUsed += 3; }
    if (q.length > 0 && quota > 0) {
      const job = q[0], step = Math.min(1, job.left);
      job.left -= step; quota -= step; cpuUsed += step;
      if (job.left <= 0) { latencies.push(t + 1 - job.at); q.shift(); }
    }
  }
  latencies.sort((a, b) => a - b);
  const pct = (p: number) => latencies[Math.floor((latencies.length - 1) * p)];
  return { limit: limitMillicores, avgCores: (cpuUsed / 30000).toFixed(2), p50: pct(0.5), p99: pct(0.99), max: latencies.at(-1), throttled: `${((throttled / periods) * 100).toFixed(0)}%` };
}

Part 5 — Infrastructure as code 🟡 Intermediateالجزء 5 — الـ Infrastructure as Code

English

IaC means your infrastructure is described as desired state in version control. A tool computes a plan (the difference between desired and actual), a human reviews it, then apply makes the changes. Drift is when reality no longer matches the description because someone changed it in the console, or a process died.

That compare-and-converge idea is what Terraform and Kubernetes controllers share, and the difference is when it runs: Terraform on demand (usually in CI), a controller continuously. The tiny loop below is the whole idea: read desired JSON, compare with real running processes, print the plan first, apply it, and converge after you kill a process out of band.

Design consequences: plan must be a pure function so you can review it; the state must be locked and backed up (a remote state with locking, or two applies will fight); keep blast radius small by splitting state per service and environment; and prefer replacing machines over patching them, so that what you tested is what runs.

// فكرة Terraform و K8s controllers في ملف واحد: desired state، plan، apply، وتصليح الـ drift
import { fork, type ChildProcess } from "node:child_process";
import { setTimeout as sleep } from "node:timers/promises";

type Desired = Record<string, { replicas: number; version: string }>;
type Proc = { id: string; service: string; version: string; child: ChildProcess };
type Action = { op: "create" | "destroy"; service: string; version: string; proc?: Proc };

const worker = new URL("./replica.ts", import.meta.url);
const running = new Map<string, Proc>();
let seq = 0;

const desired: Desired = {
  "orders-api": { replicas: 2, version: "1.4.0" },
  "invoice-worker": { replicas: 1, version: "2.0.1" },
};

// الـ plan دالة نقية: بتقارن وبترجع actions، مبتلمسش حاجة
function plan(want: Desired, actual: Proc[]): Action[] {
  const actions: Action[] = [];
  for (const p of actual) {
    const spec = want[p.service];
    if (!spec || spec.version !== p.version) actions.push({ op: "destroy", service: p.service, version: p.version, proc: p });
  }
  for (const [service, spec] of Object.entries(want)) {
    const good = actual.filter((p) => p.service === service && p.version === spec.version).length;
    for (let i = good; i < spec.replicas; i++) actions.push({ op: "create", service, version: spec.version });
  }
  return actions;
}

function apply(actions: Action[]) {
  for (const a of actions) {
    if (a.op === "destroy") { a.proc!.child.kill(); running.delete(a.proc!.id); continue; }
    const id = `${a.service}-${++seq}`;
    const child = fork(worker, [a.service, a.version], { stdio: "ignore" });
    // لو الـ process مات لوحده بيتشال من الـ actual، والـ loop يلاحظ
    child.on("exit", () => running.delete(id));
    running.set(id, { id, service: a.service, version: a.version, child });
  }
}

function step(label: string) {
  const actions = plan(desired, [...running.values()]);
  const text = actions.map((a) => `${a.op === "create" ? "+" : "-"} ${a.service}@${a.version}`).join(", ") || "no changes";
  console.log(`[${label}] plan: ${text}`);
  apply(actions);
}

الـ IaC يعني الـ infrastructure بتاعتك مكتوبة كـ desired state في الـ version control. الأداة بتحسب plan (الفرق بين المطلوب والموجود)، والبني آدم يراجعه، وapply ينفذ. والـ drift لما الواقع ميبقاش زي الوصف: حد غيّر حاجة من الـ console، أو process وقع.

فين هستخدمه في شغلي؟ لو الـ RDS و الـ Redis و الـ S3 بتوع الـ staging اتعملوا بالإيد من الـ console، أول production incident هتكتشف إنهم مش زي الـ production (backup retention، parameter group). حط الـ .tf في الـ repo، وخلّي الـ PR يطلّع plan كـ comment، والـ apply من الـ CI بس بعد approval.

Part 6 — Discovery & config management 🟡 Intermediateالجزء 6 — الـ Discovery وإدارة الـ Config

English

Service discovery answers "where is orders-api right now?". DNS is the simplest: one name, a list of IPs and a TTL, and it works everywhere, but caches (resolvers, the JVM, HTTP clients) can hold a stale answer past the TTL; see 06 · DNS & global routing. A registry (Consul, etcd, Eureka, or the Kubernetes API) holds live instances with TTL heartbeats, so a dead instance disappears when its lease expires. Client-side discovery means each client fetches the list and picks an instance (fewer hops, smarter balancing, a library in every language). Server-side means the client hits one stable address and a load balancer picks (simpler clients, one more hop; a Kubernetes Service is this).

Whatever you choose, there is a stale window: from an instance's death until nobody routes to it. Its worst case is about TTL + client refresh. The stand-in below measures 725 ms against a worst case of 900 ms, and 1477 ms with slower settings. Requests that land in the window fail unless the client retries on another instance: 16 misrouted requests became 0 user-visible with one retry. That is why retries and discovery are designed together.

Config comes in two kinds: static, read at boot (env vars, needs a restart), and dynamic, pushed at runtime (feature flags, limits). Bad config is one of the top causes of large outages: Cloudflare's 18 November 2025 outage was a generated config file that doubled in size, exceeded a limit in the proxy software, and was propagated network-wide. So treat config like code: versioned, validated against a schema before applying, rolled out gradually with a canary, with one-step rollback and a last-known-good fallback. The run below rejects a wrong type, a typo and a cross-field violation, keeps the old version active, then catches a valid-but-harmful change at the canary. Note: Zod runs a .refine on the object only after the base shape passes, so a bad type hides a cross-field error until it's fixed.

// ده stand-in: registry في الـ memory بـ TTL heartbeats، بتايمرات حقيقية، مش Consul ولا etcd
import { setTimeout as sleep } from "node:timers/promises";

class Registry {
  private leases = new Map<string, number>();
  private ttlMs: number;
  constructor(ttlMs: number) { this.ttlMs = ttlMs; }
  heartbeat(id: string) { this.leases.set(id, performance.now() + this.ttlMs); }
  list() { const now = performance.now(); return [...this.leases].filter(([, exp]) => exp > now).map(([id]) => id); }
}

async function trial(ttlMs: number, heartbeatMs: number, clientRefreshMs: number, retry: boolean) {
  const reg = new Registry(ttlMs);
  const alive = new Set(["orders-1", "orders-2", "orders-3"]);
  const beats = [...alive].map((id) => setInterval(() => reg.heartbeat(id), heartbeatMs));
  for (const id of alive) reg.heartbeat(id);

  // الـ client-side discovery: كل client عنده نسخة من الليستة بيحدّثها كل فترة
  let cached = reg.list();
  const refresh = setInterval(() => { cached = reg.list(); }, clientRefreshMs);

  let i = 0, misrouted = 0, userVisible = 0, firstBad = 0, lastBad = 0, sent = 0;
  const victim = "orders-2";
  let deadAt = 0;
  const traffic = setInterval(() => {
    sent++;
    const target = cached[i++ % cached.length];
    if (alive.has(target)) return;
    misrouted++;
    if (!firstBad) firstBad = performance.now();
    lastBad = performance.now();
    // الـ retry على instance تاني بيخبّي الغلطة عن المستخدم
    if (!retry) userVisible++;
  }, 3);

  await sleep(500);
  // الموت: مفيش heartbeat تاني، والليستة لسه فيها الـ instance
  clearInterval(beats[1]);
  alive.delete(victim);
  deadAt = performance.now();
  await sleep(ttlMs + clientRefreshMs + 400);

  clearInterval(traffic); clearInterval(refresh); beats.forEach(clearInterval);
  return {
    ttlMs, heartbeatMs, clientRefreshMs, retry, sent, misrouted, userVisible,
    staleWindowMs: lastBad ? Math.round(lastBad - deadAt) : 0,
    worstCaseMs: ttlMs + clientRefreshMs,
  };
}

  apply(candidate: unknown): { ok: true; version: number } | { ok: false; error: string } {
    const r = AppConfig.safeParse(candidate);
    if (!r.success) return { ok: false, error: z.prettifyError(r.error) };
    if (r.data.version <= this.current.version) return { ok: false, error: `stale version ${r.data.version}` };
    this.history.push(this.current);
    this.current = r.data;
    return { ok: true, version: r.data.version };
  }
  rollback() { const prev = this.history.pop(); if (prev) this.current = prev; return this.current.version; }
}

const good = { version: 1, pool: { max: 10 }, requestTimeoutMs: 3000, dbTimeoutMs: 1500, payments: { provider: "stripe", rollout: 0.1 } };

بالعامية

الـ service discovery بتجاوب "orders-api فين دلوقتي؟". الـ DNS أبسط حاجة: اسم واحد، ليستة IPs و TTL، وشغال في كل حتة، بس الـ caches (الـ resolvers، الـ JVM، الـ HTTP clients) ممكن تحتفظ بإجابة قديمة بعد الـ TTL؛ شوف درس 06 · الـ DNS. الـ registry (Consul، etcd، Eureka، أو الـ Kubernetes API) بيخزن الـ instances الحية بـ TTL heartbeats، فالـ instance الميت بيختفي لما الـ lease تخلص. الـ client-side discovery يعني كل client بيجيب الليستة ويختار instance (hops أقل، balancing أذكى، library في كل لغة). الـ server-side يعني الـ client بيكلم عنوان ثابت والـ load balancer يختار (clients أبسط، hop زيادة، و Kubernetes Service كده).

أيًا كان اختيارك، فيه stale window: من لحظة موت الـ instance لحد ما محدش يبعتله. الـ worst case بتاعها حوالي TTL + client refresh. الـ stand-in هنا قاس 725 ms مقابل worst case 900 ms، و 1477 ms بإعدادات أبطأ. الطلبات اللي بتقع في الـ window بتفشل إلا لو الـ client عمل retry على instance تاني: الـ 16 طلب اللي راحوا غلط بقوا 0 ظاهر للمستخدم بـ retry واحد. وعشان كده الـ retries والـ discovery بيتصمموا مع بعض.

الـ config نوعين: static بيتقرا وقت الـ boot (env vars، ومحتاج restart)، و dynamic بيتدفع وقت التشغيل (feature flags، limits). والـ config الغلط من أكبر أسباب الـ outages الكبيرة: outage بتاع Cloudflare يوم 18 نوفمبر 2025 كان ملف config متولد حجمه اتضاعف، عدّى limit في الـ proxy software، واتنشر على الشبكة كلها. فعامل الـ config زي الكود: له version، بيتعمله validation بـ schema قبل ما يتطبق، بينتشر تدريجي بـ canary، وله rollback بخطوة واحدة و last-known-good. التشغيل هنا رفض نوع غلط و typo وعلاقة غلط بين حقلين، وفضّل الـ version القديم شغال، وبعدين مسك تغيير صح شكلًا بس مضر في الـ canary. ملحوظة: Zod بيشغّل .refine على الـ object بعد ما الـ shape الأساسي ينجح، فالنوع الغلط بيخبّي خطأ العلاقة لحد ما يتصلح.

فين هستخدمه في شغلي؟ الـ rate limits بتتغير من صفحة admin وتتخزن في Postgres. متخليش الـ API ياخدها مباشرة: اعمل Zod schema، ارفض الـ invalid في الـ endpoint نفسه، وخلي الـ API يحتفظ بـ last-known-good في الذاكرة. لو صفحة الـ admin دخّلت قيمة غلط، الـ service يكمل بالقديم بدل ما يقع. ونفس الفكرة للـ feature flags.
What breaks at scale Push the same bad config to every instance within seconds and you've built a global outage. Stagger it per zone, watch error rate for a bake period, and make rollback a config push, not a code deploy. See 27 · Deployment safety.
ادفع نفس الـ config الغلط لكل الـ instances في ثواني وأهلًا بالـ global outage. قسّمها على الـ zones، واتفرج على الـ error rate فترة bake، وخلّي الـ rollback عبارة عن config push مش code deploy. شوف درس 27 · أمان الـ deployment.
Interview question "A bad value in a config store took down all regions. How would you redesign the rollout?" → Schema validation at write time and at read time, versioned configs, a canary region with automatic comparison to baseline, staged rollout across zones with a bake time, and each instance keeping the last-known-good config so it can reject a bad update and stay up.
"قيمة غلط في الـ config store وقّعت كل الـ regions. هتعيد تصميم النشر إزاي؟" ← schema validation وقت الكتابة ووقت القراءة، و versioned configs، و canary region بمقارنة أوتوماتيك بالـ baseline، ونشر تدريجي على الـ zones مع bake time، وكل instance يحتفظ بـ last-known-good عشان يرفض الـ update الغلط ويكمل شغال.

Common mistakes · غلطات شائعة

❌ Capacity = the best RPS you saw 
// أعلى RPS شفته في الـ test، من غير p99 ولا headroom
const capacity = 19000;
const instances = Math.ceil((8000 * 1.5) / capacity);
// → 1
✅ RPS at the target p99, with headroom and N+1 
// الـ capacity عند p99 ≤ 10 ms، وبعدها headroom ومعاه واحد احتياطي
const capacity = capacityAt(points, 10);
const usable = capacity * 0.6;
const instances = Math.ceil((8000 * 1.5) / usable) + 1;
// → 3
بالعامية

❌ أعلى RPS شفته في الـ test رقم مش مربوط بأي p99، وده الـ throughput ceiling. لو خططت عليه هتشتغل طول الوقت عند الـ knee ومن غير أي spare، وأي instance يقع يبقى outage. ✅ خد الـ capacity عند الـ p99 المطلوب، وطبّق headroom، وزوّد N+1: عددك من 1 لـ 3 وإنت عارف ليه.

❌ Scaling queue workers on CPU 
// الـ workers مستنيين IO، فالـ CPU واطية والـ backlog بيكبر
const desired = Math.ceil(replicas * (cpu / 0.6));
✅ Scale on the work that is waiting 
// العدد من الشغل المتراكم، نهدف نخلّصه في 60 ثانية
const desired = Math.ceil((servedRps + backlog / 60) / (capacityPerWorker * 0.6));
بالعامية

❌ الـ worker اللي شغله كله IO (بيبعت email أو بيستنى API) هتلاقي الـ CPU بتاعته واطية والـ queue بيتراكم، فالـ HPA مش هيعمل حاجة. ✅ اعمل scale على الـ lag أو الـ waiting count: مقياس بيقول الشغل المتأخر قد إيه.

❌ Liveness checks a dependency 
// لو Postgres أخد blip كل الـ pods بتتعمل restart مرة واحدة
app.get("/healthz", async (_req, res) => {
  await pool.query("SELECT 1");
  res.sendStatus(200);
});
✅ Liveness = the process; readiness = the dependencies 
// الـ healthz بسيطة، والـ readyz هي اللي بتفحص Postgres
app.get("/healthz", (_req, res) => res.sendStatus(200));
app.get("/readyz", async (_req, res) => {
  const ok = await pool.query("SELECT 1").then(() => true, () => false);
  res.sendStatus(ok ? 200 : 503);
});
بالعامية

❌ لما الـ DB تقع، الـ liveness تفشل وكل الـ pods تتعمل restart مع بعض، فيجيلها connections من كل الـ pods مرة واحدة وتفضل واقعة. ✅ خلي الـ liveness تفحص الـ process بس، والـ readiness تفحص الـ DB فتطلّع الـ pod من الـ traffic من غير restart.

❌ A CPU limit near the average 
# الـ pod بيستخدم 0.42 core في المتوسط، فالـ limit ده شكله كويس
resources:
  limits: { cpu: "500m" }
# الـ GC burst هيعمل throttling والـ p99 هيبقى 181 ms
✅ Request the average, measure throttling 
# الـ request للـ scheduler، ومفيش CPU limit عن قصد
resources:
  requests: { cpu: "500m", memory: "512Mi" }
  limits: { memory: "512Mi" }
بالعامية

❌ الـ limit بيتحسب كل 100 ms مش كمتوسط. أي burst (GC، شغل sync) بيخلّص الـ quota والـ event loop كله بيقف لحد الـ period الجاية. ✅ حط الـ request قريب من الاستخدام، واترك الـ CPU limit أو خليه عالي جدًا، وراقب الـ throttling.

❌ Apply config, then find out 
// الـ config بيدخل من غير validation ومفيش طريق رجوع
const cfg = await fetchConfig();
applyConfig(cfg);
✅ Validate, keep last-known-good, canary 
// لو بايظ بنرفضه، والنسخة الشغالة بتفضل زي ما هي
const r = AppConfig.safeParse(await fetchConfig());
if (r.success) store.apply(r.data);
else log.error({ issues: r.error.issues }, "config rejected");
بالعامية

❌ config بيتنشر من غير فحص ده أقصر طريق لـ outage شامل، لأن كل الـ instances بتاخده في نفس اللحظة. ✅ افحصه بـ schema قبل ما يتطبق، واحتفظ بـ last-known-good، وانشره على canary الأول.

3. Validate a limits config 🟡 medium Write a Zod schema for a rate-limit config with version, perTenantRps and globalRps, where a tenant limit can never exceed the global limit. applyLimits must reject a bad version and keep the active one.

Solution · الحل 
import { z } from "zod";
const Limits = z.strictObject({
  version: z.number().int().positive(),
  perTenantRps: z.number().int().min(1),
  globalRps: z.number().int().min(1),
}).refine((c) => c.perTenantRps <= c.globalRps, { message: "perTenantRps must not exceed globalRps", path: ["perTenantRps"] });
type Limits = z.infer<typeof Limits>;

let active: Limits = Limits.parse({ version: 1, perTenantRps: 50, globalRps: 2000 });
function applyLimits(raw: unknown): string {
  const r = Limits.safeParse(raw);
  if (!r.success) return `rejected, keeping v${active.version}: ${r.error.issues[0].message}`;
  active = r.data;
  return `applied v${active.version}`;
}
console.log(applyLimits({ version: 2, perTenantRps: 5000, globalRps: 2000 }));
console.log(applyLimits({ version: 2, perTenantRps: 100, globalRps: 2000 }));
// → rejected, keeping v1: perTenantRps must not exceed globalRps
// → applied v2
الـ .refine بتحط القاعدة اللي بين الحقلين، و safeParse بترجع نتيجة بدل exception، فنقدر نحتفظ بالقيمة الشغالة لو الجديدة غلط. الـ output في آخر الكود من تشغيل حقيقي.

Cheat sheet · الخلاصة

  • Capacity = highest RPS meeting the target p99. Check the generator ceiling first.
  • instances = ceil(peak × growth / (capacity × headroom)) + spare; size for losing a zone if you span zones.
  • USL: σ contention, κ coherency, peak at √((1−σ)/κ). Past that, fix the bottleneck instead of adding instances.
  • Reactive autoscaling is always late by the boot time. Shorten boot, pre-scale for known events, use a floor.
  • CPU pins at 100%: prefer queue lag or RPS per instance. Scale out fast, in slowly (5 min stabilization is HPA's default).
  • Track $/1000 requests per tenant, tag everything, detect spikes with median + MAD.
  • Readiness = traffic, liveness = restart, and liveness never checks a dependency.
  • CPU limits are per-100 ms quotas: a GC burst can freeze the event loop while average CPU looks fine.
  • Flip readiness → wait for the LB → stop accepting → drain → exit.
  • IaC: desired state, plan, apply, drift; plan is pure, state is locked.
  • Stale window ≈ TTL + refresh; pair discovery with retry on another instance.
  • Config is code: version, validate before applying, canary, one-step rollback, last-known-good.
بالعامية
  • الـ capacity = أعلى RPS بيحقق الـ p99 المطلوب، وأول حاجة شوف سقف الـ generator.
  • instances = ceil(peak × growth / (capacity × headroom)) + spare، وحسبها على وقوع zone لو شغال على zones.
  • الـ USL: σ هي الـ contention و κ هي الـ coherency، والقمة عند √((1−σ)/κ)، وبعدها صلّح الـ bottleneck بدل ما تزود instances.
  • الـ reactive autoscaling دايمًا متأخر بوقت الـ boot: قصّر الـ boot، واعمل pre-scale للأحداث المعروفة، وحط floor.
  • الـ CPU بتلزق عند 100%: استخدم queue lag أو RPS لكل instance. Scale-out بسرعة و scale-in ببطء (الـ 5 دقايق stabilization هو default بتاع HPA).
  • تابع $/1000 طلب لكل tenant، وحط tags على كل حاجة، واكشف الـ spikes بـ median + MAD.
  • الـ readiness للـ traffic، والـ liveness للـ restart، والـ liveness متفحصش dependency أبدًا.
  • الـ CPU limits عبارة عن quota كل 100 ms: GC burst ممكن يقف الـ event loop والمتوسط شكله تمام.
  • اقلب الـ readiness، استنى الـ LB، بطّل تقبل، خلّص اللي شغال، واخرج.
  • الـ IaC: desired state و plan و apply و drift؛ الـ plan pure function، والـ state لازم locked.
  • الـ stale window ≈ الـ TTL + الـ refresh، واربط الـ discovery بـ retry على instance تاني.
  • الـ config كود: version، و validate قبل التطبيق، و canary، و rollback بخطوة، و last-known-good.
