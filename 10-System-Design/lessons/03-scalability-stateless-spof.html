Why this matters · ليه ده مهم

English

"How would you scale this?" is the question behind most system design rounds, and "what happens when X dies?" is the one that follows it. The honest answers depend on where the state lives, which component everything shares, and what your code does in the first second of an outage. In this lesson you measure all three on a real API, a real Postgres and a real Redis, so the words "stateless" and "SPOF" turn into numbers you have produced yourself.

بالعامية

"هتعمل scale للحاجة دي إزاي؟" هو السؤال اللي ورا أغلب جلسات الـ system design، وبعده على طول "إيه اللي هيحصل لو X وقع؟". الإجابة الصادقة بتعتمد على الـ state قاعدة فين، وإيه المكوّن اللي الكل بيشاركه، والكود بتاعك بيعمل إيه في أول ثانية من الـ outage. في الدرس ده هتقيس التلاتة على API حقيقي و Postgres حقيقي و Redis حقيقي، عشان كلمتي "stateless" و"SPOF" يبقوا أرقام إنت طلّعتها بإيدك.

Part 1 — Vertical vs horizontal, measured 🟢 Basicالجزء 1 — الـ vertical والـ horizontal بالقياس

English

Vertical scaling means a bigger machine: more CPU, more RAM, faster disk. No code changes, no distributed-systems problems, and a single Postgres on a big box goes a very long way. Its limits are a hard ceiling (the largest instance on sale), a price that climbs fastest near that ceiling, a restart to resize, and the fact that one machine is still one failure.

Horizontal scaling means more machines behind a load balancer. It has no practical ceiling for the stateless tier, and losing one machine loses a fraction of capacity instead of all of it. In exchange the service must be stateless (Part 2), you now operate a load balancer (Part 3), and it only multiplies the part you copied. Anything all the copies still share keeps its old limit.

The experiment below runs 1, 2, 4 and 8 Node processes behind a small stand-in load balancer. /cpu does real work with no shared dependency. /db does the same CPU work and then a durable transaction on one hot row in a single real Postgres, like the stock counter of a product on flash sale. The transaction holds that row's lock until COMMIT, so those transactions run one at a time no matter how many API processes send them.

English

Read the table in two steps. From 1 to 2 instances, /db rises because the API tier was the limit. From 2 to 8 it barely moves: one locked row is now the limit, and four times the instances bought about 13% more throughput. This is the shape to expect from any shared resource.

The 15 failures at 8 instances are a second, separate lesson. Each process has a pool of 8 connections, so the fleet can ask for 8 × 8 = 64, and this Postgres allows 60. Each failed request logged error: sorry, too many clients already. Scaling out the app multiplies connections to the shared database, which is why connection pooling becomes part of the design as soon as the instance count can change.

بالعامية

الـ vertical scaling معناه machine أكبر: CPU أكتر، RAM أكتر، disk أسرع. مفيش تغيير في الكود ومفيش مشاكل distributed systems، و Postgres واحدة على machine كبيرة بتمشي معاك مشوار طويل جدًا. حدوده: سقف صلب (أكبر instance متاح للبيع)، وسعر بيطلع أسرع قرب السقف ده، وrestart عشان تغيّر الحجم، وإن الـ machine الواحدة لسه failure واحدة.

الـ horizontal scaling معناه machines أكتر ورا load balancer. مفيش له سقف عملي للطبقة الـ stateless، ووقوع machine بيضيّع جزء من الـ capacity مش كلها. في المقابل الـ service لازم تبقى stateless (الجزء 2)، وبقى عندك load balancer تشغّله (الجزء 3)، وهو بيضاعف الجزء اللي نسخته بس. أي حاجة النسخ كلها لسه بتشاركها بتفضل عند حدها القديم.

التجربة بتشغّل 1 و2 و4 و8 processes ورا LB بسيط. الـ /cpu شغل حقيقي من غير أي dependency مشتركة. الـ /db نفس شغل الـ CPU وبعده transaction durable على صف واحد سخن في Postgres حقيقية واحدة، زي عدّاد الـ stock لمنتج عليه flash sale. الـ transaction ماسكة الـ lock بتاع الصف لحد الـ COMMIT، فالـ transactions دي بتمشي واحدة ورا التانية مهما كان عدد الـ processes اللي بتبعتها.

اقرا الجدول على مرحلتين. من 1 لـ 2 الـ /db طلع لأن طبقة الـ API كانت هي الحد. من 2 لـ 8 تقريبًا مبيتحركش: الصف الواحد المقفول بقى هو الحد، وأربع أضعاف النسخ جابت حوالي 13% زيادة بس. ده الشكل اللي تتوقعه من أي resource مشترك.

الـ 15 فشل عند 8 نسخ درس تاني منفصل: كل process عندها pool من 8 connections، فالـ fleet ممكن تطلب 8 × 8 = 64، والـ Postgres دي مسموح لها 60. الـ scale out للـ app بيضاعف الـ connections على الـ database المشتركة، وعشان كده الـ connection pooling بيبقى جزء من الـ design من أول ما عدد النسخ يبقى متغيّر.

فين هستخدمه في شغلي؟ الـ endpoint بتاع الـ checkout بطيء تحت الضغط، والـ manager قال "زوّد pods". قبل ما تزوّد، بص على pg_stat_activity: لو الـ connections كلها مستنية على Lock أو الـ DB CPU عند الحد، الـ pods الزيادة مش هتجيب حاجة وممكن تكسر الدنيا بـ too many clients. الحل هيبقى إعادة تصميم الصف السخن (reservation table أو counter مقسوم على shards)، أو Postgres أكبر (vertical) لو الـ CPU هو الحد فعلًا. والغلطة الشائعة: تضيف نسخ وإنت مش حاسب instances × pool قدام max_connections.
Trade-off: start vertical, keep the door open Vertical is the simplest thing that can work, until it isn't: resizing needs a restart and the machine is still one failure. The cheap move is to stay on one bigger database for as long as it holds, and keep the app tier stateless from day one, so adding instances stays a config change.
الـ vertical أبسط حل ممكن يشتغل، لحد ما يقف: تغيير الحجم محتاج restart والـ machine لسه failure واحدة. الحركة الرخيصة إنك تفضل على database واحدة أكبر طول ما هي شايلة، وتخلّي طبقة الـ app stateless من أول يوم، عشان زيادة النسخ تفضل مجرد تغيير config.

Part 2 — Stateless vs stateful 🟢 Basicالجزء 2 — الـ stateless والـ stateful

English

A service is stateless when any instance can serve any request, because everything that must outlive a request lives somewhere shared: a database, Redis, object storage. The instance keeps nothing that matters. A service is stateful when a request only works on the instance that holds some piece of data. The classic bad case is sessions in a Map inside the process.

The test below runs two instances behind the round-robin LB. Twenty users each log in and then call /me ten times. With the Map, a session exists only on the instance that handled the login, and every /me that lands on the other instance gets a real 401. Moving the store to Redis changes one line of wiring and the 401s disappear, with no other change to the handlers.

import http from "node:http";
import { randomUUID } from "node:crypto";
import type { AddressInfo } from "node:net";
import { Redis } from "ioredis";
import { safePort } from "./guard.ts";

type SessionStore = {
  save(token: string, userId: string): Promise<void>;
  find(token: string): Promise<string | null>;
};

// ❌ الـ state جوه الـ process: كل instance عندها نسخة مختلفة خالص
function memoryStore(): SessionStore {
  const sessions = new Map<string, string>();
  return {
    save: async (t, u) => void sessions.set(t, u),
    find: async (t) => sessions.get(t) ?? null,
  };
}

// ✅ الـ state بره: أي instance تقدر تخدم أي request
function redisStore(port: number): SessionStore {
  const redis = new Redis({ host: "127.0.0.1", port, maxRetriesPerRequest: 1 });
  return {
    save: async (t, u) => void (await redis.set(`sess:${t}`, u, "EX", 3600)),
    find: (t) => redis.get(`sess:${t}`),
  };
}

const store = process.env.STORE === "redis" ? redisStore(safePort(process.env.REDIS_PORT)) : memoryStore();

const server = http.createServer(async (req, res) => {
  if (req.url === "/health") return void res.writeHead(200).end("ok");
  if (req.url === "/login" && req.method === "POST") {
    const token = randomUUID();
    await store.save(token, "user-42");
    return void res.writeHead(200, { "content-type": "text/plain" }).end(token);
  }
  const token = req.headers.authorization?.replace("Bearer ", "") ?? "";
  const userId = await store.find(token);
  res.writeHead(userId ? 200 : 401).end(userId ?? "unauthorized");
});
server.listen(0, "127.0.0.1", () => process.send?.({ port: (server.address() as AddressInfo).port }));

English

Sticky sessions are the other way out: the LB pins each user to one instance. It hides the problem, and it keeps the other costs: load becomes uneven, a deploy or crash still logs those users out, and scaling down drops sessions. Use it as a stopgap or for something inherently connection-bound, not as the design.

Sessions are the obvious case. In code review, look for the less obvious ones: anything that behaves differently once there are two copies. The scanner below is a first pass that flags places to read by hand, and it is run here against a sample service file.

import { readdirSync, readFileSync, statSync } from "node:fs";
import path from "node:path";

// كل قاعدة: pattern بيدل على state جوه الـ process، والسؤال اللي تسأله في الـ code review
const rules: [RegExp, string][] = [
  [/^(?:export )?const \w+ = new (?:Map|Set)\b/, "module-level Map/Set: is this per-user state?"],
  [/multer\(\{\s*dest|writeFile(?:Sync)?\(/, "writes to local disk: does the next instance need this file?"],
  [/node-cron|cron\.schedule|^setInterval\(/, "in-process timer: runs once per instance, is that intended?"],
  [/new WebSocketServer|socket\.io/, "open sockets: how do messages reach users on another instance?"],
  [/rateLimit\(\{(?![^}]*store)/, "in-memory rate limit: the real limit becomes limit x instances"],
  [/new LRUCache|node-cache/, "local cache: what invalidates it on the other instances?"],
];

function* walk(dir: string): Generator<string> {
  for (const name of readdirSync(dir)) {
    if (name === "node_modules" || name.startsWith(".")) continue;
    const full = path.join(dir, name);
    if (statSync(full).isDirectory()) yield* walk(full);
    else if (/\.[cm]?[jt]sx?$/.test(name)) yield full;
  }
}

Part 3 — The load balancer as a concept 🟢 Basicالجزء 3 — الـ load balancer كمفهوم

English

Strip a load balancer to its concept and three jobs are left: distribute requests across instances, detect which instances are unhealthy, and stop sending to those. The code below is about 75 lines of Node doing exactly that. It is a stand-in for teaching: it has no TLS, no connection draining, no retries and no real timeout handling. The basics of proxies are in section 01, and algorithms, L4 vs L7 and draining are in Load Balancers in depth.

An active health check means the LB probes each instance on a timer, here every 500 ms. The detection window is the time between an instance dying and the next failed probe, so until then a share of real traffic still goes to a dead instance. The experiment kills one of three instances one second into a four-second run and counts every failed request.

import http from "node:http";

type Backend = { port: number; healthy: boolean; failures: number };
export type LbOptions = {
  healthCheck?: boolean;
  intervalMs?: number;
  unhealthyAfter?: number;
  onDown?: (port: number) => void;
};

export function startLb(ports: number[], opts: LbOptions = {}) {
  const { healthCheck = true, intervalMs = 500, unhealthyAfter = 1, onDown } = opts;
  const backends: Backend[] = ports.map((port) => ({ port, healthy: true, failures: 0 }));
  const agent = new http.Agent({ keepAlive: true, maxSockets: 256 });
  let cursor = 0;

  // (1) التوزيع: round robin على الـ instances السليمة بس
  const pick = () => {
    const up = backends.filter((b) => b.healthy);
    return up.length > 0 ? up[cursor++ % up.length] : undefined;
  };

  const server = http.createServer((req, res) => {
    const target = pick();
    if (!target) return void res.writeHead(503).end("no healthy backend");
    const options = { host: "127.0.0.1", port: target.port, path: req.url, method: req.method, headers: req.headers, agent };
    const upstream = http.request(options, (r) => {
      res.writeHead(r.statusCode ?? 502, r.headers);
      r.pipe(res);
    });
    // لو الـ instance وقعت والطلب ماشي: الـ client بياخد 502
    upstream.on("error", () => {
      if (res.headersSent) res.destroy();
      else res.writeHead(502).end("bad gateway");
    });
    req.pipe(upstream);
  });

  // (3) وقف الإرسال: بعد عدد فشل معيّن الـ instance تطلع من الـ pool
  const mark = (b: Backend, ok: boolean) => {
    if (ok) {
      b.failures = 0;
      b.healthy = true;
      return;
    }
    b.failures += 1;
    if (b.healthy && b.failures >= unhealthyAfter) {
      b.healthy = false;
      onDown?.(b.port);
    }
  };

  // (2) الاكتشاف: active health check كل intervalMs على كل instance
  const probe = (b: Backend) => {
    const r = http.get({ host: "127.0.0.1", port: b.port, path: "/health", timeout: 250, agent: false }, (res) => {
      res.resume();
      mark(b, res.statusCode === 200);
    });
    r.on("timeout", () => r.destroy());
    r.on("error", () => mark(b, false));
  };
  const timer = healthCheck ? setInterval(() => backends.forEach(probe), intervalMs) : undefined;

  return {
    server,
    backends,
    close() {
      clearInterval(timer);
      agent.destroy();
      server.close();
      server.closeAllConnections();
    },
  };
}

A single point of failure is a component whose loss stops the system. In a graph, that is an articulation point: a vertex whose removal disconnects the graph. Tarjan's algorithm finds them all in one depth-first search, O(V + E). Graph basics are in section 01.

There is a catch that decides whether this works at all. // كل node مكوّن وكل edge اعتماد، والـ graph هنا undirected
export type Graph = Map<string, Set<string>>;

export function graphOf(edges: [string, string][]): Graph {
  const g: Graph = new Map();
  const add = (a: string, b: string) => {
    if (!g.has(a)) g.set(a, new Set());
    g.get(a)!.add(b);
  };
  for (const [a, b] of edges) {
    add(a, b);
    add(b, a);
  }
  return g;
}

// الطبقات متسلسلة: كل node في طبقة موصولة بكل nodes الطبقة اللي بعدها
export function tiers(...layers: string[][]): Graph {
  const edges: [string, string][] = [];
  layers.slice(1).forEach((layer, i) => {
    for (const a of layers[i]) for (const b of layer) edges.push([a, b]);
  });
  return graphOf(edges);
}

// خوارزمية Tarjan للـ ⁦articulation points: O(V + E)⁩
export function findSpof(g: Graph): string[] {
  const disc = new Map<string, number>();
  const low = new Map<string, number>();
  const cut = new Set<string>();
  let clock = 0;

  const dfs = (u: string, parent: string | null): void => {
    disc.set(u, ++clock);
    low.set(u, clock);
    let children = 0;
    for (const v of g.get(u)!) {
      if (v === parent) continue;
      if (disc.has(v)) {
        low.set(u, Math.min(low.get(u)!, disc.get(v)!));
        continue;
      }
      children += 1;
      dfs(v, u);
      low.set(u, Math.min(low.get(u)!, low.get(v)!));
      // مفيش طريق من تحت v يوصل لفوق u: يبقى u نقطة قطع
      if (parent !== null && low.get(v)! >= disc.get(u)!) cut.add(u);
    }
    // الجذر نقطة قطع لو عنده أكتر من subtree
    if (parent === null && children > 1) cut.add(u);
  };

  for (const node of g.keys()) if (!disc.has(node)) dfs(node, null);
  return [...cut].sort();
}

// هل الطلب لسه يوصل من source لـ sink لو شيلنا كل دول مع بعض؟
export function survives(g: Graph, source: string, sink: string, down: string[]): boolean {
  const dead = new Set(down);
  if (dead.has(source) || dead.has(sink)) return false;
  const seen = new Set([source]);
  const stack = [source];
  while (stack.length > 0) {
    const u = stack.pop()!;
    if (u === sink) return true;
    for (const v of g.get(u) ?? []) {
      if (!seen.has(v) && !dead.has(v)) {
        seen.add(v);
        stack.push(v);
      }
    }
  }
  return false;
}

English

The redundant graph reports zero SPOFs and that is exactly when you get complacent. A graph sees boxes, and it cannot see what the boxes have in common. The function survives() handles this: list failure domains, the sets of things that die together, and check each set. These are the SPOFs no diagram shows:

  • One DNS provider: every LB is unreachable by name, however many there are.
  • One availability zone: two replicas in the same AZ are one failure.
  • One expiring certificate: a shared cert expires on all LBs at the same second.
  • One config push: a bad flag or deploy hits every instance, so redundancy gives you nothing.
  • One person who knows the deploy: the outage lasts until they answer the phone.

Fixes follow the same pattern: a second DNS provider or long TTLs, replicas across AZs, automated renewal with alerts on expiry, staged rollouts with a canary, and a written runbook that someone else has actually followed.

Part 5 — The kill test 🟢 Basicالجزء 5 — اختبار القتل

English

A SPOF on paper is a theory. A kill test turns it into a fact: send traffic, kill a dependency, and count what every endpoint does. The naive API below sends every request through Redis first and has no decision about failure. The fixed API writes one decision per endpoint and per dependency:

  • Fail open means serve anyway with less: the catalog falls through to Postgres when Redis is gone, or to a stale copy when Postgres is gone.
  • Fail closed means refuse: login and checkout return 503 with Retry-After. You can't create a session without its store, and an order must not be half-recorded.

A detail that matters as much as the policy: ioredis defaults to an offline queue and maxRetriesPerRequest: 20. From ioredis 6's default retry strategy (50 ms doubling, capped at 5 s) that adds up to about 71 seconds a command can wait. So the default doesn't fail fast, it hangs. The fix is enableOfflineQueue: false and a short commandTimeout.

async function naive(path: string, token: string): Promise<Reply> {
  await redis.incr("rate:global");
  if (path === "/catalog") {
    const cached = await redis.get("catalog");
    if (cached) return { status: 200, body: cached };
    const body = await readCatalog();
    await redis.set("catalog", body, "EX", 1);
    return { status: 200, body };
  }
  if (path === "/login") {
    await pool.query("SELECT 1 FROM users WHERE email = $1", ["a@shop.test"]);
    const t = randomUUID();
    await redis.set(`sess:${t}`, "user-42", "EX", 3600);
    return { status: 200, body: t };
  }
  const user = await redis.get(`sess:${token}`);
  if (!user) return unauthorized;
  if (path === "/checkout") await pool.query("INSERT INTO orders (user_id) VALUES ($1)", [user]);
  return { status: 200, body: user };
}

// ✅ لكل dependency وكل endpoint قرار مكتوب: fail open أو fail closed
async function resilient(path: string, token: string): Promise<Reply> {
  if (path === "/catalog") {
    const cached = await redis.get("catalog").catch(() => null);
    if (cached) return { status: 200, body: cached };
    try {
      const body = await readCatalog();
      await redis.set("catalog", body, "EX", 1).catch(() => {});
      await redis.set("catalog:stale", body, "EX", 3600).catch(() => {});
      return { status: 200, body, degraded: redis.status !== "ready" };
    } catch {
      // الـ DB واقعة: نسخة قديمة أحسن من error في صفحة قراءة
      const stale = await redis.get("catalog:stale").catch(() => null);
      return stale ? { status: 200, body: stale, degraded: true } : unavailable();
    }
  }
  try {
    if (path === "/login") {
      await pool.query("SELECT 1 FROM users WHERE email = $1", ["a@shop.test"]);
      const t = randomUUID();
      await redis.set(`sess:${t}`, "user-42", "EX", 3600);
      return { status: 200, body: t };
    }
    const user = await redis.get(`sess:${token}`);
    if (!user) return unauthorized;
    if (path === "/checkout") await pool.query("INSERT INTO orders (user_id) VALUES ($1)", [user]);
    return { status: 200, body: user };
  } catch {
    // مش 401: وقوع Redis مش معناه إن الـ user يتطرد من حسابه
    return unavailable();
  }
}

  const path = req.url ?? "/";
  const token = req.headers.authorization?.replace("Bearer ", "") ?? "";

    const reply = await (fixed ? resilient : naive)(path, token);
    const headers: Record<string, string> = reply.degraded ? { "x-degraded": "1" } : {};
    if (reply.status === 503) headers["retry-after"] = "5";
    res.writeHead(reply.status, headers).end(reply.body);
  } catch {
    res.writeHead(500).end("internal error");
  }
});

1. Connection budget 🟢 easy Write poolBudget(): given instances, surge pods during a rolling deploy, pool size, max_connections and connections reserved for admin, return the peak, whether it fits, and the largest safe pool size.

Solution · الحل 
// عدد الـ connections اللي الـ fleet كلها ممكن تفتحها وقت الذروة
function poolBudget(opts: { instances: number; surge: number; poolSize: number; maxConnections: number; reserved: number }) {
  const { instances, surge, poolSize, maxConnections, reserved } = opts;
  const peak = (instances + surge) * poolSize;
  const available = maxConnections - reserved;
  return { peak, available, ok: peak <= available, maxPoolSize: Math.floor(available / (instances + surge)) };
}

console.log(poolBudget({ instances: 8, surge: 2, poolSize: 5, maxConnections: 60, reserved: 5 }));

{ peak: 50, available: 55, ok: true, maxPoolSize: 5 }

2. Stop the flapping 🟡 medium Replace the health logic in lb.ts with a small pure function: an instance goes down after fall consecutive failures and comes back after rise consecutive passes. Test it with a sequence that flaps.

Solution · الحل 
// الـ state machine بتاعة الـ health: عدد فشل عشان تطلع، وعدد نجاح عشان ترجع
type Health = { healthy: boolean; fails: number; passes: number };

export function nextHealth(h: Health, ok: boolean, fall = 3, rise = 2): Health {
  if (ok) {
    const passes = h.passes + 1;
    return { healthy: h.healthy || passes >= rise, fails: 0, passes };
  }
  const fails = h.fails + 1;
  return { healthy: h.healthy && fails < fall, fails, passes: 0 };
}

// نفس السلسلة: instance بتهزّ، وبعدين بتقع، وبعدين بترجع
const probes = [true, false, true, false, false, false, true, false, true, true];
let state: Health = { healthy: true, fails: 0, passes: 0 };
const timeline = probes.map((ok) => {
  state = nextHealth(state, ok);
  return `${ok ? "pass" : "FAIL"}:${state.healthy ? "up" : "DOWN"}`;
});
console.log(timeline.join(" "));

import { tiers, survives } from "./find-spof.ts";

// النسختين في نفس الـ AZ: الـ graph شكله redundant بس الـ AZ لسه SPOF
const shop = tiers(["client"], ["lb1", "lb2"], ["api1", "api2"], ["pg-primary", "pg-standby"], ["psp"]);
const zoneOf: Record<string, string> = { lb1: "a", lb2: "b", api1: "a", api2: "b", "pg-primary": "a", "pg-standby": "a" };

function zoneSpofs(zones: Record<string, string>): string[] {
  const names = [...new Set(Object.values(zones))];
  return names.filter((z) => {
    const down = Object.keys(zones).filter((n) => zones[n] === z);
    return !survives(shop, "client", "psp", down);
  });
}

Cheat sheet · الخلاصة

  • Vertical: simple, has a ceiling, still one failure. Horizontal: needs stateless and an LB.
  • Scaling out multiplies only what you copied. A hot row stayed flat at about 900 rps from 2 to 8 instances.
  • Every instance multiplies connections: instances × pool must fit max_connections.
  • Stateless means any instance can serve any request. In-memory sessions gave 40–53% 401s, Redis gave 0.
  • Hidden state: local disk, in-process cron, in-memory limits, WebSockets, local caches.
  • An LB distributes, detects and stops sending. Detection window = interval × failures needed.
  • A drawing shows who talks to whom. Find SPOFs on what a request needs, in series.
  • Zero articulation points isn't zero SPOFs: list failure domains (DNS, AZ, cert, config push, people).
  • Decide per endpoint and per dependency: fail open or fail closed, and fail fast either way.
  • An outage is a 503, not a 401. Health checks must not depend on a shared dependency.
بالعامية
  • الـ vertical بسيط، ليه سقف، ولسه failure واحدة. الـ horizontal محتاج stateless و LB.
  • الـ scale out بيضاعف اللي نسخته بس. الصف السخن فضل ثابت عند حوالي 900 rps من 2 لـ 8 نسخ.
  • كل نسخة بتضاعف الـ connections: instances × pool لازم يدخل في max_connections.
  • الـ stateless يعني أي نسخة تخدم أي طلب. الـ sessions في الـ memory طلّعت 40–53% طلبات 401، و Redis صفر.
  • الـ state المستخبي: disk محلي، cron جوه الـ process، limits في الـ memory، WebSockets، caches محلية.
  • الـ LB بيوزّع ويكتشف ويبطّل يبعت. نافذة الاكتشاف = الـ interval × عدد مرات الفشل المطلوبة.
  • الرسمة بتبيّن مين بيكلّم مين. دوّر على الـ SPOF في اللي الطلب محتاجه، متسلسل.
  • صفر articulation points مش معناها صفر SPOF: اكتب الـ failure domains (DNS، AZ، cert، config push، الناس).
  • قرر لكل endpoint ولكل dependency: fail open أو fail closed، وفي الحالتين افشل بسرعة.
  • الـ outage يبقى 503 مش 401. والـ health checks مينفعش تعتمد على dependency مشتركة.
