Why this matters · ليه ده مهم

English

An event is a contract with consumers you may never meet, and it outlives the code that wrote it. Changing one field can stop a billing service three teams away, or worse, keep it running on wrong numbers. And once events exist, somebody asks for revenue per tenant, either from a nightly job or live on a dashboard, and the answer depends on which clock you use.

This lesson runs each piece: real Avro, Protobuf and JSON encoders, a real compatibility matrix, a small registry, a MapReduce on worker threads, and seeded simulations of windows and watermarks. Kafka, Flink, Spark and Confluent don't run here; wherever they appear they are labelled Not run here.

بالعامية

الـ event عبارة عن عقد مع consumers ممكن عمرك ما تقابلهم، وبيعيش أكتر من الكود اللي كتبه. تغيير field واحد ممكن يوقّف billing service عند فريق تاني خالص، أو الأوحش إنه يفضل شغال بأرقام غلط. ولما الـ events تبقى موجودة، حد هيسأل عن الـ revenue لكل tenant، يا إما من job بالليل يا إما live على dashboard، والإجابة بتتوقف على أنهي ساعة بتستخدمها.

Part 1 — Formats, measured 🟡 Intermediateالجزء 1 — الـ formats بالقياس

English

The same OrderPlaced event encoded four ways: plain JSON, JSON validated by JSON Schema (Ajv), Avro (avsc) and Protobuf (protobufjs). JSON carries its field names in every message. Avro carries no names and no field tags at all, only values in schema order, so a reader cannot decode a single byte without the writer's schema. Protobuf carries a small numeric tag per field, which is what lets an old reader skip fields it doesn't know.

The measured result: 119 bytes as JSON, 31 as Avro, 37 as Protobuf, so roughly 3 to 4 times smaller. But look at the gzip column for a batch of 1000 events: 20.6 KB against 17.6 KB. Compression removes the repeated field names, so the gap shrinks to about 1.2 times. Kafka compresses batches in practice, so that second number is usually the honest comparison. Speed is noise-heavy on this loaded machine, so read only the order of magnitude: every format is around a million operations a second or more, far faster than the network or database in front of it.

So the size argument alone is weak at most scales. At 1 billion events a day, uncompressed, JSON is 119 GB/day against 31 for Avro, about $8 a day in egress at a third-party list price of $0.09/GB. The real reason to adopt a schema format is the contract: a typed definition, generated code, and compatibility checks in CI. The cost is that the data is no longer readable with cat and every reader needs the schema.

function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

نفس الـ OrderPlaced اتعمل encode بـ 4 طرق: JSON عادي، JSON متحقق منه بـ JSON Schema عن طريق Ajv، و Avro بـ avsc، و Protobuf بـ protobufjs. الـ JSON بيشيل أسماء الحقول في كل رسالة. الـ Avro مفيهوش أسماء ولا tags خالص، قيم بس بترتيب الـ schema، فالـ reader مش هيعرف يفك byte واحد من غير schema الكاتب. الـ Protobuf بيشيل tag رقمي صغير لكل حقل، وده اللي بيخلي الـ reader القديم يعدّي الحقول اللي مش عارفها.

النتيجة المقاسة: 119 byte بـ JSON و 31 بـ Avro و 37 بـ Protobuf، يعني أصغر حوالي 3 لـ 4 مرات. بس بص على عمود الـ gzip لـ 1000 event: 20.6 KB مقابل 17.6 KB. الـ compression بيشيل أسماء الحقول المتكررة، فالفرق بيقل لحوالي 1.2 مرة. و Kafka بيضغط الـ batches في الواقع، فالرقم التاني غالبًا هو المقارنة الأمينة. السرعة فيها noise كتير على الجهاز ده، فخد منها الـ order of magnitude بس: كل format في حدود مليون عملية في الثانية أو أكتر، وده أسرع بكتير من الشبكة أو الـ database اللي قدامه.

يبقى حجة الحجم لوحدها ضعيفة في أغلب الأحجام. عند مليار event في اليوم من غير ضغط، الـ JSON حوالي 119 GB في اليوم مقابل 31 لـ Avro، يعني حوالي $8 في اليوم egress بسعر $0.09/GB من مصدر تالت. السبب الحقيقي لاستخدام format بـ schema هو العقد: تعريف typed، وكود متولّد، و compatibility checks في الـ CI. والتمن إن الـ data مبقتش تتقري بـ cat وكل reader محتاج الـ schema.

الغلطة الشائعة: تختار Avro عشان "أسرع وأصغر" من غير ما تقيس بعد الضغط، أو تستخدم JSON من غير أي validation على توبيك فيه 20 consumer.

فين هستخدمه في شغلي؟ لو عندك webhook عام أو events داخلية قليلة، JSON مع Zod كفاية. لو بدأت Kafka عليه أكتر من فريق، خد Avro مع registry عشان التغييرات تتفحص في الـ CI، مش عشان توفر كام GB.
Trade-off: readable vs schema required JSON lets you read a message during an incident with one command. Avro lets you reject a bad schema at build time. Most teams take the second and add a small tool that decodes a message from the registry, which is the same trick as jq with one more step.
الـ JSON بيخليك تقرا رسالة وقت الـ incident بأمر واحد. الـ Avro بيخليك ترفض schema بايظ وقت الـ build. معظم الفرق بتختار التاني وبتضيف أداة صغيرة بتفك الرسالة من الـ registry، وده نفس فكرة jq بخطوة زيادة.

Part 2 — Schema evolution 🟡 Intermediateالجزء 2 — تطور الـ schema

English

Backward compatible means new readers can read old data. Forward compatible means old readers can read new data. Full is both. In Avro the reader resolves the difference between its own schema and the writer's, so below each change actually runs in both directions instead of being looked up in a table.

Three results are worth memorizing. Adding a field with a default is FULL. Adding one without a default gives the exact error no matching field for default-less OrderPlaced.currency for backward reads, because the new reader has nothing to fill in. A rename without an alias is BREAKING in both directions, and an alias only fixes the new reader, so a rename is never FULL.

Protobuf works by field numbers, and its failures are quieter. Changing a number, or changing to an incompatible wire type, doesn't throw: the value just disappears. The worst case in the output is reusing number 2 for a field with the same wire type: total_cents = 5 becomes discount_cents = 5, with no error at all. Delete a field by marking its number reserved. JSON has no mechanism at all, so it relies on a tolerant reader that ignores unknown fields and defaults missing ones; a strict reader breaks on any additive change.

Deploy order follows from the definitions: for a backward-compatible change upgrade consumers first, for forward-compatible upgrade producers first, and for full, any order. Event-sourced systems have the further problem of events stored forever, handled by upcasting, in section 09 · 3.2.

// مهم: الـ reader هو اللي بيحل التعارض مع الـ writer schema
function reads(readerFields: object[], writerFields: object[], value: object): string {
  const reader = avro.Type.forSchema(record(readerFields));
  const writer = avro.Type.forSchema(record(writerFields));
  try {
    const resolver = reader.createResolver(writer);
    const decoded = reader.fromBuffer(writer.toBuffer(value), resolver);
    return `ok ${JSON.stringify(decoded)}`;
  } catch (err) {
    return `FAIL ${(err as Error).message}`;
  }
}

Part 3 — Schema registry 🟡 Intermediateالجزء 3 — الـ schema registry

English

Avro needs the writer's schema to decode, and you can't ship the schema inside every message. A schema registry stores schemas per subject, gives each an ID, and checks each new version against the compatibility mode before accepting it. Producers put the ID in front of each message, and consumers use it to fetch the writer's schema once and cache it.

The stand-in below is about 60 lines and shows the whole mechanism: register, reject incompatible versions, a 5-byte header of one magic byte plus a 4-byte big-endian ID, and resolution on read. That's the classic Confluent wire format, and per Confluent's docs a newer header-based format with a 16-byte GUID exists from Platform 8.1.1. The last step behaves like CI: a breaking change is rejected and the script exits non-zero, so the build fails before the bad schema reaches production. That is where most of the value is.

Versioning: in-place evolution keeps one topic and one stream of history, and it's the default for compatible changes. A truly breaking change gets a new topic such as orders.OrderPlaced.v2, with the producer writing both during the migration and consumers moving one by one. The cost is duplicated data and a window where two topics must agree. Publishing those events reliably is the outbox's job, in section 07 · 3.4.

import avro from "avsc";

// بديل صغير لـ schema registry، في الـ memory وعلى subject واحد في المرة
type Mode = "NONE" | "BACKWARD" | "FORWARD" | "FULL";
type Version = { id: number; schema: object };

export class Registry {
  private nextId = 1;
  private readonly byId = new Map<number, object>();
  private readonly subjects = new Map<string, Version[]>();

  // الـ reader لازم يقدر يحل الـ writer، وإلا avsc بيرمي error هنا
  private canRead(reader: object, writer: object): string | null {
    try {
      avro.Type.forSchema(reader as avro.Schema).createResolver(avro.Type.forSchema(writer as avro.Schema));
      return null;
    } catch (err) {
      return (err as Error).message;
    }
  }

  register(subject: string, schema: object, mode: Mode = "BACKWARD"): number {
    const versions = this.subjects.get(subject) ?? [];
    const latest = versions.at(-1);
    if (latest && mode !== "NONE") {
      const back = mode !== "FORWARD" ? this.canRead(schema, latest.schema) : null;
      const fwd = mode !== "BACKWARD" ? this.canRead(latest.schema, schema) : null;
      const problem = back ?? fwd;
      if (problem) throw new Error(`incompatible with v${versions.length} under ${mode}: ${problem}`);
    }
    const id = this.nextId++;
    this.byId.set(id, schema);
    versions.push({ id, schema });
    this.subjects.set(subject, versions);
    return id;
  }

  schemaById(id: number): object {
    const schema = this.byId.get(id);
    if (!schema) throw new Error(`unknown schema id ${id}`);
    return schema;
  }
}

// صيغة الرسالة: magic byte واحد، و schema id في 4 bytes، وبعدها الـ Avro
export function encode(registry: Registry, id: number, value: object): Buffer {
  const header = Buffer.alloc(5);
  header.writeUInt8(0, 0);
  header.writeUInt32BE(id, 1);
  return Buffer.concat([header, avro.Type.forSchema(registry.schemaById(id) as avro.Schema).toBuffer(value)]);
}

export function decode(registry: Registry, message: Buffer, readerSchema: object): unknown {
  if (message.readUInt8(0) !== 0) throw new Error("unknown magic byte");
  const writer = avro.Type.forSchema(registry.schemaById(message.readUInt32BE(1)) as avro.Schema);
  const reader = avro.Type.forSchema(readerSchema as avro.Schema);
  return reader.fromBuffer(message.subarray(5), reader.createResolver(writer));
}

Part 4 — Batch: MapReduce 🟡 Intermediateالجزء 4 — الـ Batch: MapReduce

English

Batch processing runs over a complete, bounded dataset. MapReduce is the shape behind it: map each input record to key-value pairs, shuffle so all values for a key meet, and reduce them to a result. Below, revenue per tenant from a generated 1M-line orders file, on real worker_threads, with shuffle going through files on disk.

Two details do the heavy lifting. A hash of the key picks the partition, so every value of a tenant reaches one reducer. And each mapper writes to a temporary file and renames it on success, so a failed task leaves nothing a reducer could read: re-running a task is therefore safe. That is why the framework can recover by re-execution. Here mapper 3 is made to crash once and the master re-runs it; the totals still match a straight single-threaded reference.

4 workers took about 323 ms against 1013 ms for 1, about 3.1 times faster, not 4: worker start-up, disk I/O and a loaded machine take the rest. Spark has the same shape but keeps intermediate data in memory and plans the job as a DAG of stages, which is what makes it fast for multi-step and iterative work; when a partition is lost it recomputes from the lineage (concept only, not run here). The original paper is listed in the reading map.

  let h = 0;
  for (let i = 0; i < key.length; i++) h = (h * 31 + key.charCodeAt(i)) | 0;
  return Math.abs(h) % n;

Part 5 — Stream: windows 🟡 Intermediateالجزء 5 — الـ Stream: الـ windows

English

A stream never ends, so "total revenue" has to become "revenue per window". Tumbling windows are fixed and don't overlap, so each event is counted once: revenue per minute. Sliding windows overlap, so an event falls in several: the last 60 s, updated every 30 s. Session windows are per key and close after a gap of inactivity: a user's shopping session.

Every window needs a clock. Processing time is when the event reached the system; event time is when it happened on the device. They differ because of networks and mobile clients. In this seeded simulation 527 of 2000 events arrived after a newer one, and the first minute shows 20,237 by processing time against the true 20,941, because 3% of its revenue landed in later windows. Even the session count changes, 49 against 45, since a late arrival makes a gap look longer. Revenue per minute on processing time means your numbers change whenever the network does, and a replay of yesterday's events would put everything in today's windows. Event time has its own trap: it comes from the device, so clamp impossible values (a phone whose clock is a year off), see Time & Clocks.

The real tools, by name: Apache Flink and Kafka Streams implement exactly these windows with durable state and checkpoints (not run here). What follows is a labelled model of the mechanism.

function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);

function sessions(time: (o: Order) => number, gap: number): { count: number; maxRevenue: number } {
  const byUser = new Map<string, Order[]>();
  for (const o of orders) (byUser.get(o.user) ?? byUser.set(o.user, []).get(o.user)!).push(o);
  let count = 0;
  let maxRevenue = 0;
  for (const list of byUser.values()) {
    list.sort((a, b) => time(a) - time(b));
    let revenue = list[0]!.amount;
    count++;
    for (let i = 1; i < list.length; i++) {
      if (time(list[i]!) - time(list[i - 1]!) > gap) {
        maxRevenue = Math.max(maxRevenue, revenue);
        revenue = 0;
        count++;
      }
      revenue += list[i]!.amount;
    }
    maxRevenue = Math.max(maxRevenue, revenue);
  }
  return { count, maxRevenue };
}

Part 6 — Watermarks & late events 🟡 Intermediateالجزء 6 — الـ watermarks والأحداث المتأخرة

English

With event time you can never be sure a window is complete, because an older event might still be on its way. A watermark is the system's claim that it no longer expects events older than some time. The usual form is watermark = max event time seen − allowed lateness. A window fires when the watermark passes its end. What happens to events behind the watermark is a policy choice: drop, send to a side output, or revise the window.

The seeded simulation has mobile events up to 30 s late (70% almost immediate, 20% up to 5 s, 10% up to 30 s). With lateness 0 s, 722 of 20,000 events are late, 3.71% of revenue if you drop them, and 19 of 20 windows need a revision, but results appear in 0.2 s. With 5 s it's 394 late. At 30 s nothing is late, and the results are 30 s old. Going to 60 s buys nothing but another 30 s of delay: with lateness above the true maximum delay, you pay for no benefit.

So lateness is set from your measured delay distribution, not guessed: pick the percentile you can live with. Above that, decide whether late events are revisions or a counter. Note the distinction in real engines: Flink has watermarks plus allowedLateness and side outputs, Kafka Streams has a grace period (by name, not run here). A watermark across partitions is the minimum of each partition's, so one idle partition stalls everyone; Exercise 3 runs that. Exactly-once in stream processing is in Transactions at Scale, and a full system built around this is in Ad Click Aggregation.

function run(events: Event[], latenessSec: number, size = 60) {
  const open = new Map<number, number>();
  const firedAt = new Map<number, number>();
  const firstResult = new Map<number, number>();
  const truth = new Map<number, number>();
  const revisedWindows = new Set<number>();
  let late = 0;
  let lateRevenue = 0;
  let maxEventTime = 0;
  let totalRevenue = 0;

  for (const e of events) {
    const w = Math.floor(e.eventTime / size) * size;
    truth.set(w, (truth.get(w) ?? 0) + e.amount);
    totalRevenue += e.amount;
    maxEventTime = Math.max(maxEventTime, e.eventTime);

    // العلامة: أقصى event time شوفناه ناقص الـ lateness المسموح
    const watermark = maxEventTime - latenessSec;

    if (firedAt.has(w)) {
      late++;
      lateRevenue += e.amount;
      revisedWindows.add(w);
    } else {
      open.set(w, (open.get(w) ?? 0) + e.amount);
    }

    for (const [start, sum] of open) {
      if (watermark >= start + size) {
        firedAt.set(start, e.arrival);
        firstResult.set(start, sum);
        open.delete(start);
      }
    }
  }
  for (const [start, sum] of open) {
    firedAt.set(start, Infinity);
    firstResult.set(start, sum);
  }

  const delays = [...firedAt.entries()].filter(([, at]) => at !== Infinity).map(([start, at]) => at - (start + size));
  const avg = delays.reduce((a, b) => a + b, 0) / delays.length;
  const worstError = Math.max(...[...truth].map(([w, t]) => (Math.abs(t - (firstResult.get(w) ?? 0)) / t) * 100));
  return { late, lateRevenuePct: (lateRevenue / totalRevenue) * 100, windows: firedAt.size, revised: revisedWindows.size, avgDelay: avg, worstError };
}

بالـ event time عمرك ما هتتأكد إن window اكتمل، لأن event أقدم ممكن يكون لسه في السكة. الـ watermark هو إعلان من السيستم إنه مبقاش مستني events أقدم من وقت معين. الشكل المعتاد watermark = أكبر event time شوفناه − الـ lateness المسموح. الـ window بيتحسب لما الـ watermark يعدّي نهايته. والـ events اللي ورا الـ watermark قرار: ترميها، تبعتها side output، أو تعدّل النتيجة.

الـ simulation بـ seed ثابت، events موبايل متأخرة لحد 30 ثانية (70% فورًا تقريبًا، 20% لحد 5 ثواني، 10% لحد 30 ثانية). عند lateness صفر، 722 من 20,000 event متأخرين، يعني 3.71% من الـ revenue لو رميتهم، و 19 من 20 window محتاجة revision، بس النتايج بتظهر في 0.2 ثانية. عند 5 ثواني 394 متأخر. عند 30 ثانية مفيش متأخر، والنتايج عمرها 30 ثانية. والـ 60 ثانية مش بتزود غير 30 ثانية تأخير كمان: لما الـ lateness يعدّي أقصى تأخير حقيقي، بتدفع من غير فايدة.

يبقى الـ lateness بيتحدد من توزيع التأخير المقاس عندك، مش بالتخمين: اختار الـ percentile اللي تقدر تتعايش معاه. وفوقيه قرر هل المتأخر revision ولا مجرد عداد. وخد بالك من الفرق في المحركات الحقيقية: Flink عنده watermarks وallowedLateness و side outputs، و Kafka Streams عنده grace period (بالاسم، not run here). والـ watermark عبر الـ partitions هو الـ minimum بتاعهم، فـ partition واحدة ساكتة بتوقّف الكل، والتمرين 3 بيشغّل ده. الـ exactly-once في الـ stream processing موجود في Transactions at Scale، ونظام كامل مبني على ده في Ad Click Aggregation.

فين هستخدمه في شغلي؟ تطبيق موبايل بيبعت orders متأخرة لما النت يرجع: قِس توزيع receivedAt - placedAt، خد الـ p99 كـ lateness للـ dashboard، واعتبر اللي بعده revisions. ولتقرير الفوترة شغّل batch ليلي على الـ data الكاملة، وده اللي يتحاسب عليه العميل مش رقم الـ stream.
Interview question "What's a watermark, and how do you choose the allowed lateness?" → It's a moving assertion that events older than a time are no longer expected, usually max event time minus a lateness bound. Measure the delay distribution and pick a percentile that trades freshness for correctness. Set a policy for what arrives after: drop with a counter, side output, or revise. Across partitions it's the minimum, so handle idle partitions.
"إيه الـ watermark، وتختار الـ lateness إزاي؟" ← إعلان متحرك إن الأحداث الأقدم من وقت معين مبقتش متوقعة، وعادةً أكبر event time ناقص حد للتأخير. قِس توزيع التأخير واختار percentile بيوازن بين الحداثة والصحة. وحدد سياسة للي بيوصل بعدها: رمي بعداد، أو side output، أو تعديل النتيجة. وعبر الـ partitions بتاخد الـ minimum، فلازم تتعامل مع الـ partitions الساكتة.

Common mistakes · غلطات شائعة

❌ Reuse a Protobuf number 
message OrderPlaced {
  string order_id = 1;
  // غلط: الرقم 2 كان total_cents قبل كده
  int64 discount_cents = 2;
}
✅ Reserve deleted numbers 
message OrderPlaced {
  reserved 2;
  reserved "total_cents";
  string order_id = 1;
  int64 discount_cents = 3;
}
بالعامية

❌ إعادة استخدام رقم بنفس الـ wire type: في التجربة total_cents = 5 اتقرت discount_cents = 5 من غير أي error. ✅ reserved للرقم وللاسم، والـ compiler هيمنع أي حد يستخدمهم تاني.

❌ New Avro field without a default 
{ "name": "currency", "type": "string" }
no matching field for default-less OrderPlaced.currency
✅ With a default 
{ "name": "currency", "type": "string", "default": "EGP" }
بالعامية

❌ حقل جديد من غير default بيكسر كل قراءة للـ data القديمة، بالـ error اللي فوق بالظبط. ✅ بالـ default التغيير بقى FULL، والـ data القديمة بتتقري بـ EGP.

❌ Strict consumer 
// النتيجة: أول حقل جديد بيوقّف الـ consumer
const Event = z.strictObject({
  orderId: z.string(),
  totalCents: z.number(),
});
✅ Tolerant reader 
// النتيجة: الحقول المجهولة بتتجاهل والناقص ليه default
const Event = z.object({
  orderId: z.string(),
  totalCents: z.number(),
  currency: z.string().default("EGP"),
});
بالعامية

❌ z.strictObject على event بيخلي أي إضافة في الـ producer تكسر الـ consumer (unrecognized_keys في التجربة). ✅ z.object بيتجاهل الزيادة، و default للحقول الجديدة. الـ strict مكانه الـ API inputs من بره، مش الـ events بين services.

❌ Window on arrival time 
// غلط: replay لأحداث امبارح كله هيقع في window النهارده
const windowStart = Math.floor(Date.now() / 60_000) * 60_000;
✅ Window on the event's own time 
// صح: الوقت جاي من جوه الـ event نفسه
const windowStart = Math.floor(event.placedAt / 60_000) * 60_000;
بالعامية

❌ Date.now() وقت الاستقبال معناه إن الأرقام بتتغير مع الشبكة وإن الـ replay بيبوّظ كل حاجة. ✅ الوقت من جوه الـ event نفسه، ومعاه watermark للي بيتأخر.

❌ Producer first on a backward-only change 
# غلط: الـ consumers القديمة مش هتعرف تقرا الـ data الجديدة
deploy orders-api@v2
deploy billing-consumer@v2
✅ Consumers first 
# صح: الـ consumer الجديد بيقرا القديم والجديد
deploy billing-consumer@v2
deploy orders-api@v2
بالعامية

❌ في تغيير BACKWARD بس (زي حذف حقل ملوش default)، لو الـ producer نزل الأول الـ consumers القديمة هتقع على الـ data الجديدة. ✅ ارفع الـ consumers الأول. ولو التغيير FORWARD بس يبقى العكس: الـ producers الأول.

BACKWARD بيفحص آخر إصدار بس. ضيف mode بيفحص كل الإصدارات القديمة، ولاقي تاريخ من 3 إصدارات بيعدي مع واحد ويفشل مع التاني.
Solution · الحل 
import avro from "avsc";

type Fields = object[];
const record = (fields: Fields) => ({ type: "record", name: "OrderPlaced", fields }) as unknown as avro.Schema;
const type = (fields: Fields) => avro.Type.forSchema(record(fields));

function canRead(reader: Fields, writer: Fields): string | null {
  try {
    type(reader).createResolver(type(writer));
    return null;
  } catch (err) {
    return (err as Error).message;
  }
}

class Subject {
  private readonly versions: Fields[] = [];

  // الحل: BACKWARD_TRANSITIVE يعني الجديد لازم يقرا كل الإصدارات القديمة، مش آخر واحد بس
  register(fields: Fields, transitive: boolean): void {
    const against = transitive ? this.versions : this.versions.slice(-1);
    for (const [i, old] of against.entries()) {
      const problem = canRead(fields, old);
      if (problem) throw new Error(`cannot read version ${i + 1 + (transitive ? 0 : this.versions.length - 1)}: ${problem}`);
    }
    this.versions.push(fields);
  }
}

const id = { name: "orderId", type: "string" };
const v1: Fields = [id, { name: "coupon", type: "string" }];
// ملحوظة: v2 شال coupon، و v3 رجّعه بنوع تاني وبـ default
const v2: Fields = [id];
const v3: Fields = [id, { name: "coupon", type: "long", default: 0 }];

for (const transitive of [false, true]) {
  const s = new Subject();
  s.register(v1, transitive);
  s.register(v2, transitive);
  try {
    s.register(v3, transitive);
    console.log(`${transitive ? "BACKWARD_TRANSITIVE" : "BACKWARD"}: v3 accepted`);
  } catch (err) {
    console.log(`${transitive ? "BACKWARD_TRANSITIVE" : "BACKWARD"}: v3 rejected, ${(err as Error).message}`);
  }
}
BACKWARD: v3 accepted
BACKWARD_TRANSITIVE: v3 rejected, cannot read version 1: cannot read "string" as "long"
حقل coupon اتشال في v2 ورجع في v3 بنوع تاني وبـ default. BACKWARD بيقارن بـ v2 بس فبيقبل، وBACKWARD_TRANSITIVE بيقارن بـ v1 كمان فبيرفض، لأن v3 هيتعامل مع coupon القديم كـ long وهو string. ده بيحصل فعلًا لو عندك data قديمة في replay.
3. Idle partitions 🔴 hard Two partitions, one stops sending at t=20 s. Show that the watermark (the minimum across partitions) stalls and no window fires, then fix it by ignoring partitions idle for over 10 s.
عندك partitions اتنين، واحدة بتسكت عند t=20 ثانية. وريني إن الـ watermark (الـ minimum بينهم) بيقف ومفيش window بيتحسب، وبعدين صلحها بتجاهل الـ partitions الساكتة أكتر من 10 ثواني.
Hint · تلميح Track the last arrival per partition, and take the minimum only over the partitions that sent something recently.
احتفظ بآخر وصول لكل partition، وخد الـ minimum على الـ partitions اللي بعتت حاجة قريب بس.
Solution · الحل 
console.log("SIMULATION: virtual time, two partitions, one goes idle after t=20s.");

type Arrival = { partition: number; eventTime: number; at: number };
const events: Arrival[] = [];
for (let t = 0; t <= 120; t += 2) {
  events.push({ partition: 0, eventTime: t, at: t });
  if (t <= 20) events.push({ partition: 1, eventTime: t, at: t });
}
const LATENESS = 5;

function run(idleTimeoutSec: number | null): string {
  const maxByPartition = new Map<number, number>([[0, -Infinity], [1, -Infinity]]);
  const lastSeen = new Map<number, number>([[0, 0], [1, 0]]);
  const fires: string[] = [];
  let windowStart = 0;
  for (const e of events) {
    maxByPartition.set(e.partition, Math.max(maxByPartition.get(e.partition)!, e.eventTime));
    lastSeen.set(e.partition, e.at);
    // الحل: الـ watermark هو الـ min على الـ partitions النشطة بس
    const active = [...maxByPartition.keys()].filter(
      (p) => idleTimeoutSec === null || e.at - lastSeen.get(p)! <= idleTimeoutSec,
    );
    const watermark = Math.min(...active.map((p) => maxByPartition.get(p)!)) - LATENESS;
    while (watermark >= windowStart + 30) {
      fires.push(`[${windowStart}-${windowStart + 30}) fired at t=${e.at}`);
      windowStart += 30;
    }
  }
  return fires.join(", ") || "no window fired in 120s";
}

console.log(`no idle handling: ${run(null)}`);
console.log(`idle after 10s:   ${run(10)}`);
SIMULATION: virtual time, two partitions, one goes idle after t=20s.
no idle handling: no window fired in 120s
idle after 10s:   [0-30) fired at t=36, [30-60) fired at t=66, [60-90) fired at t=96
من غير معالجة الـ idle مفيش ولا window اتحسب في 120 ثانية، لأن الـ minimum واقف عند الـ partition الساكتة. مع تجاهلها بعد 10 ثواني الـ windows بدأت تتحسب. وتمن الحل إن الـ partition لو رجعت بأحداث قديمة هتيجي متأخرة.

Cheat sheet · الخلاصة

  • JSON is 3–4× larger than Avro/Protobuf raw, but only about 1.2× after batch gzip. Adopt schemas for the contract, not the bytes.
  • Backward: new reads old. Forward: old reads new. Full: both.
  • Add with a default is FULL. Add without one is forward-only. A rename is never FULL.
  • Protobuf: never reuse a field number, mark deleted ones reserved; wrong numbers fail silently.
  • JSON events need tolerant readers, so z.object, not z.strictObject.
  • Deploy consumers first for backward, producers first for forward.
  • Registry: register, check, and put a magic byte + 4-byte ID before each message. Fail the build on breaking changes, and disable auto-registration in production.
  • Compatible change in place; breaking change gets a new topic with dual writes.
  • MapReduce: map, shuffle by key hash, reduce. Atomic task output makes re-execution safe. Spark is the same shape in memory with a DAG.
  • Windows: tumbling, sliding, session. Always window on event time for money and reporting.
  • watermark = max event time − allowed lateness; choose lateness from measured delay, and decide what late events do. Lateness above the real maximum only adds delay.
بالعامية
  • الـ JSON أكبر 3 لـ 4 مرات من Avro و Protobuf من غير ضغط، بس حوالي 1.2 مرة بعد gzip للـ batch. استخدم schemas عشان العقد مش عشان الـ bytes.
  • الـ Backward: الجديد يقرا القديم. الـ Forward: القديم يقرا الجديد. الـ Full: الاتنين.
  • إضافة بـ default تبقى FULL، ومن غير default تبقى forward بس، والـ rename عمره ما يبقى FULL.
  • الـ Protobuf: متعيدش استخدام رقم حقل أبدًا وعلّم المحذوف reserved، والأرقام الغلط بتفشل في صمت.
  • الـ JSON events محتاجة tolerant readers، يعني z.object مش z.strictObject.
  • ارفع الـ consumers الأول لو backward، والـ producers الأول لو forward.
  • الـ registry: سجّل وافحص وحط magic byte و ID من 4 bytes قدام كل رسالة، وقع الـ build على التغييرات اللي بتكسر، واقفل الـ auto-registration في production.
  • التغيير المتوافق في نفس المكان، والتغيير اللي بيكسر ياخد topic جديد مع كتابة مزدوجة.
  • الـ MapReduce: map، shuffle بـ hash الـ key، reduce. ناتج الـ task الذري بيخلي إعادة التنفيذ آمنة. و Spark نفس الشكل في الـ memory ومعاه DAG.
  • الـ Windows: tumbling و sliding و session. ودايمًا اعمل window بالـ event time لأي حاجة فيها فلوس أو تقارير.
  • watermark = أكبر event time − الـ lateness المسموح، اختار الـ lateness من التأخير المقاس، وقرر تعمل إيه في المتأخر. والـ lateness اللي أكبر من أقصى تأخير حقيقي بيزود التأخير وبس.
