Why this matters · ليه ده مهم

English

Availability, durability, throughput and latency are the four numbers every design discussion ends up negotiating. People mix them up constantly: a service can be available while quietly losing data, and an average can look perfect while one user in fifty waits a full second. Here you compute the math, then break real Redis and Postgres to see which writes survive, and measure the tail on real servers. In interviews and SLO meetings, these are the numbers you will be asked to defend.

بالعامية

الـ availability والـ durability والـ throughput والـ latency هم الأربع أرقام اللي أي مناقشة design بتنتهي بتفاوض عليهم. الناس بتخلط بينهم طول الوقت: service ممكن تكون available وهي بتضيّع data في صمت، و average ممكن يبقى شكله ممتاز وuser من كل خمسين مستني ثانية كاملة. هنا هتحسب الرياضة، وبعدين هتكسر Redis و Postgres حقيقيين وتشوف أنهي writes عاشت، وهتقيس الـ tail على servers حقيقية. في الـ interviews واجتماعات الـ SLO، دي الأرقام اللي هيتطلب منك تدافع عنها.

Part 1 — Nines 🟢 Basicالجزء 1 — الـ nines

English

Availability is the fraction of time the system answers correctly. Each extra nine divides the allowed downtime by ten, and the budget is smaller than it sounds: 99.99% allows 4.32 minutes a month, which is less than one engineer logging in. Two formulas do most of the work.

Serial composition: a request that needs all of its dependencies is up only when every one of them is up, so availabilities multiply: a^n. Checkout on five services at 99.9% gives about 99.5%, which is five times the downtime of any single one. Parallel redundancy: if a request succeeds when any one of n copies is up, then 1 - (1 - a)^n. Two copies at 99% give 99.99%. That formula assumes independent failures, and real failures are often shared: same deploy, same AZ, same bad config.

// حاسبة الـ nines: كام دقيقة downtime مسموح بيها في السنة والشهر
const MINUTES_YEAR = 365 * 24 * 60;
const MINUTES_MONTH = 30 * 24 * 60;

function budget(availability: number) {
  const down = 1 - availability;
  return { perYearMin: down * MINUTES_YEAR, perMonthMin: down * MINUTES_MONTH };
}

// مولّد PRNG بـ seed ثابت عشان الناتج يتكرر بالظبط
function mulberry32(seed: number): () => number {
  let s = seed | 0;
  return () => {
    s = (s + 0x6d2b79f5) | 0;
    let t = Math.imul(s ^ (s >>> 15), 1 | s);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

const rand = mulberry32(42);
const TRIALS = 2_000_000;

// كل trial دقيقة افتراضية: هل الـ checkout المتسلسل شغال؟
function simSerial(a: number, n: number): number {
  let up = 0;
  for (let t = 0; t < TRIALS; t++) {
    let allUp = true;
    for (let i = 0; i < n; i++) if (rand() >= a) allUp = false;
    if (allUp) up += 1;
  }
  return up / TRIALS;
}

// الـ redundancy: commonCause هو نصيب الفشل اللي بيوقّع النسختين مع بعض
function simParallel(a: number, n: number, commonCause: number): number {
  const shared = (1 - a) * commonCause;
  const own = (1 - a) * (1 - commonCause);
  let up = 0;
  for (let t = 0; t < TRIALS; t++) {
    if (rand() < shared) continue;
    let anyUp = false;
    for (let i = 0; i < n; i++) if (rand() >= own) anyUp = true;
    if (anyUp) up += 1;
  }
  return up / TRIALS;
}

English

The last line is the point of the simulation. Shift only 5% of failures into a shared cause and the pair falls from 99.99% to 99.94%, six times the downtime, while every box in the diagram is still redundant. The simulation treats each minute independently and has no repair times, no outage bursts and no human response, so it confirms the arithmetic and nothing more.

بالعامية

الـ availability هي نسبة الوقت اللي النظام بيرد فيه صح. كل 9 زيادة بتقسم الـ downtime المسموح على 10، والـ budget أصغر مما تتخيل: 99.99% بتدّيك 4.32 دقيقة في الشهر، أقل من الوقت اللي مهندس بياخده عشان يعمل login. فيه معادلتين بيعملوا أغلب الشغل.

التسلسل (serial): الطلب اللي محتاج كل الـ dependencies بتاعته شغال بس لما كلهم شغالين، فالنِسَب بتتضرب: a^n. الـ checkout على 5 خدمات 99.9% بيدّي حوالي 99.5%، يعني 5 أضعاف downtime الخدمة الواحدة. التوازي (parallel redundancy): لو الطلب بينجح لما أي نسخة من n تكون شغالة، يبقى 1 - (1 - a)^n. نسختين 99% بيدّوا 99.99%. المعادلة دي بتفترض إن الأعطال مستقلة، والأعطال الحقيقية كتير منها مشتركة: نفس الـ deploy، نفس الـ AZ، نفس الـ config الغلط.

آخر سطر هو هدف الـ simulation. انقل 5% بس من الأعطال لسبب مشترك، والنسختين ينزلوا من 99.99% لـ 99.94%، يعني 6 أضعاف الـ downtime، وكل صندوق في الرسمة لسه redundant. الـ simulation بتعامل كل دقيقة لوحدها، ومفيهاش وقت إصلاح ولا outages متجمعة ولا رد فعل بشر، فهي بتأكد الحساب وبس.

كل 9 بتكلّف أضعاف لأنها بتشيل اختيارات، مش بسبب الـ hardware. الجدول اللي فوق بيبيّن كل سطر بيمنع إيه.

فين هستخدمه في شغلي؟ الـ product قال "عايزين 99.99%". اسأل: الـ checkout بيعتمد على كام خدمة؟ لو على 5 كل واحدة 99.9%، السقف الحسابي 99.5%، يعني الوعد مستحيل من غير ما تغيّر الـ architecture أو تشيل dependencies من المسار. وترجمها لدقايق في الاجتماع: "99.99 معناها 4.3 دقيقة في الشهر، ومعندناش automated failover". والغلطة الشائعة: تجمع الـ redundancy على الورق وتنسى إن النسختين بيتعمل لهم deploy في نفس اللحظة. الـ SLOs والـ error budgets بالتفصيل في درس الـ SLOs.
Interview question: "Your payment provider promises 99.9%. Can checkout be 99.99%?" Not while the provider is a hard dependency in the request path, because serial availability can't exceed its weakest link. You either add a second provider in parallel, or take the provider out of the synchronous path by accepting the order and charging through a queue, with an honest "pending" state.
السؤال: "الـ payment provider بيوعد بـ 99.9%. ينفع الـ checkout يبقى 99.99%؟" الإجابة: مينفعش طول ما الـ provider dependency أساسية في مسار الطلب، لأن الـ availability المتسلسلة مبتعدّيش أضعف حلقة. يا تضيف provider تاني بالتوازي، يا تشيل الـ provider من المسار الـ synchronous: تقبل الـ order وتحاسب عبر queue، وتعرض حالة "pending" بصراحة.

Part 2 — Reliability, durability, fault tolerance 🟢 Basicالجزء 2 — الـ reliability والـ durability والـ fault tolerance

English

Four words that people use as synonyms mean four different things. Availability: can I get an answer now? Reliability: does it keep doing the right thing over time (fewer failures, longer between them)? Durability: once you acknowledged my write, is it still there later? Fault tolerance: does the system keep working while a component is broken? They separate in real failures, so we can measure them.

First, Redis with no persistence: it is highly available and has no durability at all. The script writes keys in a loop, counting only writes that got OK, crashes the server with DEBUG SEGFAULT, and restarts it in the same folder with three settings. DEBUG is off by default and enabled here only on this private instance.

import { execFileSync } from "node:child_process";
import { mkdirSync, readFileSync, rmSync } from "node:fs";
import path from "node:path";
import { Redis } from "ioredis";
import { safePort } from "./guard.ts";

const helper = String(process.env.REDIS_HELPER);

// تشغيل Redis خاص على port حر، بالـ flags المطلوبة
function start(dir: string, flags: string[]): number {
  execFileSync(process.execPath, [helper, "start", ...flags], { cwd: dir, stdio: "ignore" });
  return safePort(readFileSync(path.join(dir, "redis.port"), "utf8").trim());
}

async function connect(port: number): Promise<Redis> {
  const redis = new Redis({ host: "127.0.0.1", port: safePort(port), maxRetriesPerRequest: 0, enableOfflineQueue: false, retryStrategy: () => null });
  redis.on("error", () => {});
  await new Promise((ok) => redis.once("ready", ok));
  return redis;
}

async function trial(label: string, flags: string[]) {
  const dir = path.resolve("runs", `r-${label.split(" ").join("-").replace(/[^a-zA-Z-]/g, "")}`);
  rmSync(dir, { recursive: true, force: true });
  mkdirSync(dir, { recursive: true });

  const allFlags = ["--enable-debug-command", "yes", ...flags];
  const port = start(dir, allFlags);
  const redis = await connect(port);
  const killer = await connect(port);

  // اكتب لحد ما الـ process يموت، والعدّاد بيزيد بعد الـ OK بس
  let acked = 0;
  const started = performance.now();
  let crashed = false;
  const writer = (async () => {
    try {
      while (!crashed) {
        await redis.set(`order:${acked}`, "paid");
        acked += 1;
      }
    } catch {
      crashed = true;
    }
  })();

  await new Promise((r) => setTimeout(r, 1500));
  // الأمر DEBUG SEGFAULT بيوقّع الـ process نفسها: أقرب حاجة لـ crash حقيقي
  await killer.call("DEBUG", "SEGFAULT").catch(() => {});
  crashed = true;
  await writer;
  const elapsed = (performance.now() - started) / 1000;
  redis.disconnect();
  killer.disconnect();

  // نفس الفولدر: لو فيه AOF هيتحمّل، ولو مفيش تبدأ فاضية
  const after = await connect(start(dir, allFlags));
  const survived = await after.dbsize();
  after.disconnect();
  execFileSync(process.execPath, [helper, "stop"], { cwd: dir, stdio: "ignore" });

  return { persistence: label, writes_per_s: Math.round(acked / elapsed), acked, survived, lost: acked - survived };
}

English

Why did everysec lose nothing? Because only the process died. The data had already been handed to the operating system with write(), and the OS kept it. Its documented risk is about one second of writes on a machine crash or power cut, which this experiment can't produce: Not run here. A process crash is the milder failure, so don't read this zero as proof for a power cut.

Now Postgres, where the same distinction shows up inside one setting. synchronous_commit=on waits for the WAL to reach disk before acknowledging. off acknowledges right after the commit is recorded in memory, and the WAL writer flushes it shortly after, at most three times wal_writer_delay later according to the docs. The script writes in a loop, stops the server with pg_ctl stop -m immediate, restarts it, and counts acknowledged rows that are gone.

import { createPrimary, connect, stopNode, startNode, stopAll } from "../pg-cluster.mjs";
import { safePort } from "./guard.ts";

const cluster = await createPrimary();
const port = safePort(cluster.port);
type Mode = "on" | "off";

async function crashRun(mode: Mode): Promise<{ acked: number; lost: number }> {
  const admin = await connect(port);
  await admin.query("DROP TABLE IF EXISTS payments; CREATE TABLE payments (id int PRIMARY KEY)");
  await admin.end();

  const writer = await connect(port);
  await writer.query(`SET synchronous_commit = ${mode}`);
  let next = 1;
  let acked = 0;
  // الـ insert بيتحسب acked بس لما الـ query ترجع من غير error
  const loop = (async () => {
    try {
      for (;;) {
        await writer.query("INSERT INTO payments (id) VALUES ($1)", [next]);
        acked = next;
        next += 1;
      }
    } catch {
      // الـ server مات: ده المتوقع هنا
    }
  })();

  await new Promise((r) => setTimeout(r, 700));
  // وقف فوري من غير checkpoint: أقرب حاجة لوقوع الـ process
  stopNode(cluster, "primary", "immediate");
  await loop;
  await writer.end().catch(() => {});

  startNode(cluster, "primary");
  const check = await connect(port);
  const { rows } = await check.query("SELECT count(*)::int AS n FROM payments WHERE id <= $1", [acked]);
  await check.end();
  return { acked, lost: acked - rows[0].n };
}

try {
  const table: Record<string, string | number>[] = [];
  for (const mode of ["on", "off"] as const) {
    for (let run = 1; run <= 5; run++) {
      const r = await crashRun(mode);
      table.push({ synchronous_commit: mode, run, acked: r.acked, acked_rows_lost: r.lost });
    }
  }
  console.table(table);
} finally {
  await stopAll(cluster);
}

English

So an acknowledgment means different things. off doubled the write rate here, and in all five runs acknowledged rows disappeared. The database itself stayed consistent after recovery, and the docs state that: a crash loses some recent commits, it does not corrupt anything. So off is a legitimate choice for high-volume analytics events and a wrong one for payments.

Copies multiply durability, on paper. With an annual failure rate per disk and a repair window, data is lost only if every other copy fails before the first one is repaired:

// حساب تقريبي: احتمال ضياع الـ data في سنة بعدد نسخ N
// بفرض إن الأعطال مستقلة، وده أكبر افتراض في الحسبة كلها
const AFR = 0.02;
const repairHours = 24;

function lossProbability(copies: number): number {
  const windowFraction = repairHours / (365 * 24);
  const failDuringRepair = AFR * windowFraction;
  return copies * AFR * failDuringRepair ** (copies - 1);
}

for (const copies of [1, 2, 3, 4]) {
  const p = lossProbability(copies);
  const nines = -Math.log10(p);
  console.log(`copies=${copies}  P(loss per year) = ${p.toExponential(2)}  durability = ${nines.toFixed(1)} nines`);
}

Part 3 — Latency vs throughput 🟢 Basicالجزء 3 — الـ latency والـ throughput

English

Latency is how long one request takes. Throughput is how many complete per second. They are separate dials, and Little's law connects them: L = λW. The average number of requests in the system equals the arrival rate times the average time each one spends inside. It holds for any stable system, with no assumption about distributions. For the basics of these terms, see section 01, part 7. What's new here is applying the law to your own measurements.

The endpoint below waits a fixed 50 ms, with no CPU work, like an API waiting on another service. Raising the number of connections tells you whether throughput and latency move together.

// (2) الـ batcher بيجمّع الطلبات ويكتبها في commit واحد
function createBatcher(flushEveryMs: number) {
  let waiting: { kind: string; done: () => void }[] = [];
  const flush = async () => {
    const batch = waiting;
    waiting = [];
    if (batch.length === 0) return;
    await db.query("INSERT INTO events (kind) SELECT * FROM unnest($1::text[])", [batch.map((b) => b.kind)]);
    batch.forEach((b) => b.done());
  };
  const timer = setInterval(() => void flush(), flushEveryMs);
  return {
    write: (kind: string) => new Promise<void>((done) => waiting.push({ kind, done })),
    stop: () => clearInterval(timer),
  };
}

async function load(write: (kind: string) => Promise<void>, clients: number) {
  const latencies: number[] = [];
  const end = performance.now() + 2000;
  const client = async () => {
    while (performance.now() < end) {
      const t0 = performance.now();
      await write("order.placed");
      latencies.push(performance.now() - t0);
    }
  };
  await Promise.all(Array.from({ length: clients }, client));
  return { rps: Math.round(latencies.length / 2), avgMs: +avg(latencies).toFixed(1) };
}

English

Batching does not simply trade latency for throughput, and Little's law shows why. A batched write waits about one window, roughly 31 ms here, so the throughput is clients / 0.031: 1 / 0.0306 = 33 rows/s, 64 / 0.0309 = 2,071, 1000 / 0.0318 = 31,447. All three match the table. At low concurrency the window is pure added latency. At high concurrency, the single-commit path saturates (3,869 rows/s, 270 ms) and batching wins on both dials, because it does less work per row.

A cache goes the other way: the latency of a hit is tiny, and throughput rises as a side effect, because each request does less work. Note what that doesn't change: the first request after expiry still pays the full 42 ms, and the cold-cache case is what cache failure modes covers.

بالعامية

الـ latency هي الطلب الواحد بياخد قد إيه. الـ throughput هو كام طلب بيخلص في الثانية. دول مؤشرين منفصلين، وقانون Little بيربطهم: L = λW. متوسط عدد الطلبات جوه النظام = معدل الوصول × متوسط الوقت اللي كل طلب بيقضيه جوه. بينطبق على أي نظام مستقر، من غير أي افتراض عن الـ distributions. أساسيات المصطلحات في القسم 01، الجزء 7، والجديد هنا تطبيق القانون على قياساتك إنت.

ده اللي الـ README يقصده: تقدر تزوّد الـ throughput من غير ما تقلل الـ latency. الزيادة 100 ضعف هنا جت من الـ concurrency بس، وكل طلب أخد نفس الوقت. والقانون بيشتغل بالعكس كمان كأداة capacity: لو عارف الـ traffic وقت الذروة والـ latency، تقدر تحسب كام طلب in-flight، وده بيدّيك أحجام الـ pools وعدد الـ instances.

Trade-off: batching windows A longer window packs more rows per commit and adds that window to every write's latency. Flush on size or time, whichever comes first, so a quiet minute doesn't make a single write wait a full window.

Part 4 — Why the average lies 🟡 Intermediateالجزء 4 — ليه الـ average بيكذب

English

Latency is rarely a bell curve. Most requests are fast and a small group is very slow, because of lock waits, GC pauses or a cold cache. An average merges those two groups into one number that describes neither. Percentiles answer a better question: "the slowest X% of requests took at least this long". The server below makes a fixed share of requests take one second. Node's perf_hooks.createHistogram records the distribution.

import type { AddressInfo } from "node:net";

  served += 1;

  else res.writeHead(200).end("fast");

  const api = await spawnInstance("src/api-slow-one-percent.ts", { SLOW_EVERY: String(slowEvery) });

  // الـ histogram بيخزن microseconds، وبنعرضه بالـ ms
  const hist = createHistogram({ lowest: 1, highest: 60_000_000, figures: 3 });

  const call = () =>
    new Promise<void>((resolve, reject) => {
      const t0 = performance.now();
      http
        .get({ host: "127.0.0.1", port: api.port, path: "/orders", agent }, (res) => {
          res.resume();
          res.on("end", () => {
            hist.record(Math.max(1, Math.round((performance.now() - t0) * 1000)));
            resolve();
          });
        })
        .on("error", reject);
    });

  // عشرين client، كل واحد 500 طلب ورا بعض

    Array.from({ length: 20 }, async () => {
      for (let i = 0; i < 500; i++) await call();
    }),
  );
  agent.destroy();
  stopAll([api]);

  const ms = (us: number) => +(us / 1000).toFixed(1);
  return {
    slow_share: label,
    requests: hist.count,
    avg_ms: ms(hist.mean),
    p50_ms: ms(hist.percentile(50)),
    p95_ms: ms(hist.percentile(95)),
    p99_ms: ms(hist.percentile(99)),

Averages hide problems. So does a common way of load testing. A closed-loop generator such as autocannon or a simple loop sends the next request only after the previous one returns. During a server stall it goes quiet, so it records one bad sample where real users would have been arriving and queueing the whole time. This is coordinated omission: the tool politely stops sending at the exact moment the system is at its worst. An open-loop generator sticks to a schedule and measures from the intended send time.

// ❌ الحمل closed loop: مبيبعتش الطلب الجاي غير لما اللي قبله يرجع
async function closedLoop(port: number) {
  const hist = newHist();
  const agent = new http.Agent({ keepAlive: true, maxSockets: 1 });
  const end = performance.now() + DURATION;
  while (performance.now() < end) {
    const t0 = performance.now();
    await request(port, agent);
    record(hist, performance.now() - t0);
  }
  agent.destroy();
  return hist;
}

// ✅ الحمل open loop: جدول ثابت، والـ latency محسوبة من وقت الإرسال المقصود
async function openLoop(port: number, ratePerSec: number) {
  const hist = newHist();
  const agent = new http.Agent({ keepAlive: true, maxSockets: 2000 });
  const gap = 1000 / ratePerSec;
  const start = performance.now();
  const total = Math.floor((DURATION / 1000) * ratePerSec);
  const pending: Promise<void>[] = [];
  for (let i = 0; i < total; i++) {
    const intended = start + i * gap;
    const wait = intended - performance.now();
    if (wait > 0) await sleep(wait);
    pending.push(request(port, agent).then(() => record(hist, performance.now() - intended)));
  }
  await Promise.all(pending);
  agent.destroy();
  return hist;
}

One Node process stands in for the 100 backends, so read the shape of the result rather than the exact millisecond values. // بعد afterMs من غير رد ابعت نسخة تانية، وخد اللي يرجع الأول، وألغي الباقي
async function hedged(afterMs: number): Promise<void> {
  const first = new AbortController();
  const second = new AbortController();
  let timer: NodeJS.Timeout | undefined;
  const backup = new Promise<void>((resolve, reject) => {
    timer = setTimeout(() => callBackend(second.signal).then(resolve, reject), afterMs);
  });
  await Promise.race([callBackend(first.signal), backup]);
  clearTimeout(timer);
  first.abort();
  second.abort();
}

  const pages: number[] = [];
  let started = 0;
  const worker = async () => {
    while (started < PAGES) {
      started += 1;
      const t0 = performance.now();
      await Promise.all(Array.from({ length: FANOUT }, () => callOne().catch(() => {})));

A warning from a first attempt. Part 6 — Queueing near saturation 🟡 Intermediateالجزء 6 — الـ queueing قرب التشبّع

English

Latency doesn't grow in a straight line with load. Queues form as utilization ρ approaches 1. For the classic M/M/1 model, one server with random arrivals and service times, mean time in system is S / (1 - ρ). At 50% utilization a request takes 2 service times, at 80% it takes 5, at 95% it takes 20, and past 100% there is no steady state: the queue grows for as long as the overload lasts.

The experiment uses a real server with a concurrency limit of one: Node's event loop serves one request at a time, with real CPU work of an exponential duration. The load is open-loop with Poisson arrivals and is measured from the intended time, so coordinated omission can't flatter it. Each level ran three times, and the table shows the median, because this machine is shared with other work. A second table repeats the idea with a pool of 8 slots and a constant service time.

    return Promise.resolve();

  const next = queue.shift();

}

function mulberry32(seed: number): () => number {
  let s = seed | 0;
  return () => {
    s = (s + 0x6d2b79f5) | 0;
    let t = Math.imul(s ^ (s >>> 15), 1 | s);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// الـ setTimeout على Windows خشن: setImmediate بيدّي دقة أحسن ومن غير ما يوقف الـ I/O
async function waitUntil(t: number): Promise<void> {
  while (performance.now() < t) await new Promise((r) => setImmediate(r));
}

  const stats = async () => (await (await fetch(`http://127.0.0.1:${api.port}/stats`)).json()) as { meanServiceMs: number; limit: number };

  const send = () =>
    new Promise<void>((resolve, reject) => {
      http
        .get({ host: "127.0.0.1", port: api.port, path: "/orders", agent }, (res) => {
          res.resume();
          res.on("end", () => resolve());
        })
        .on("error", reject);

  // حمل open loop بوصول Poisson، والـ latency من وقت الوصول المقصود
  async function drive(rate: number, seconds: number, seed: number): Promise<{ sorted: number[]; failed: number }> {
    const rand = mulberry32(seed);
    const latencies: number[] = [];
    const pending: Promise<void>[] = [];
    const start = performance.now();
    let failed = 0;
    let at = 0;
    for (;;) {
      at += -Math.log(1 - rand()) * (1000 / rate);
      if (at >= seconds * 1000) break;
      const intended = start + at;
      await waitUntil(intended);
      // الـ overload بيظهر كمان كـ connection resets، فلازم يتعدّوا
      pending.push(send().then(() => void latencies.push(performance.now() - intended), () => void (failed += 1)));
    }
    await Promise.all(pending);
    return { sorted: latencies.sort((a, b) => a - b), failed };
  }

  const { meanServiceMs, limit } = await stats();

  console.log(`${file}: service ${meanServiceMs.toFixed(1)} ms, limit ${limit}, capacity about ${capacity.toFixed(0)} rps`);

  const rows = [];
  for (const rho of [0.5, 0.8, 0.95, 1.1]) {
    const runs: { p50: number; p99: number; failed: number }[] = [];
    for (let i = 0; i < repeats; i++) {
      const { sorted: s, failed } = await drive(capacity * rho, SECONDS, Math.round(rho * 100) + i);
      runs.push({ p50: pct(s, 50), p99: pct(s, 99), failed });
      // الطابور لازم يفضى بين التشغيلات
      await stats();
    }
    // الجهاز عليه حمل تاني: الـ median بتاع التشغيلات أثبت من تشغيلة واحدة
    const median = (xs: number[]) => [...xs].sort((a, b) => a - b)[Math.floor(xs.length / 2)];
    const row: Record<string, string | number> = {
      utilization: `${Math.round(rho * 100)}%`,
      rate_rps: Math.round(capacity * rho),
      p50_ms: Math.round(median(runs.map((r) => r.p50))),
      p99_ms: Math.round(median(runs.map((r) => r.p99))),
      conn_errors: runs.reduce((sum, r) => sum + r.failed, 0),
    };
    if (withModel) {

      row.mm1_p99_ms = rho < 1 ? Math.round(Math.log(100) * meanT) : "unbounded";
    }
    rows.push(row);
  }
  console.table(rows);
  agent.destroy();
  stopAll([api]);
}

Compare the first table against the model columns. At 50% and 80%, the measured values are in the same range and the p50 is off by at most a factor of two: the shape is right. At 95% the measured p50 is 234 ms against 50 predicted. The likely reason, which was not measured separately, is that capacity was computed from CPU time alone (3.6 ms). That ignores the HTTP parsing and event-loop work each request also needs, so the true utilization at that step was probably higher than the 95% written in the table. Near the knee, a small error in ρ moves latency a lot, and that is precisely the point. At 110% there is no steady state: the numbers depend on how long the test ran, and connections started failing.

The pool of 8 stays much flatter: 45 to 48 ms from 50% to 95%. Multiple servers sharing one queue absorb random bursts, and its service time here is constant. That is why M/M/1 is a pessimistic shape for a real service with many workers. But the cliff is the same: above 100%, requests pile up without limit. The practical conclusion is to plan for 70–80% utilization at peak, so a lost instance or a burst doesn't put you past the knee. Sizing and autoscaling follow in Capacity & Infrastructure.

3. Plan capacity with Little's law 🟡 medium Peak 2,000 rps at 120 ms, each instance safely handles 50 concurrent requests, and the target utilization is 75%. Compute in-flight requests and the instance count, with one spare.
الذروة 2000 rps بـ latency 120ms، وكل instance بتستحمل 50 طلب concurrent بأمان، والـ utilization المطلوبة 75%. احسب الطلبات in-flight وعدد الـ instances بنسخة spare.
Solution · الحل 
// تخطيط الـ capacity بقانون Little وحد الـ utilization
function plan(opts: { peakRps: number; latencyMs: number; concurrencyPerInstance: number; targetUtilization: number }) {
  const { peakRps, latencyMs, concurrencyPerInstance, targetUtilization } = opts;
  const inFlight = peakRps * (latencyMs / 1000);
  const instances = Math.ceil(inFlight / (concurrencyPerInstance * targetUtilization));
  return { inFlight, instances, withOneSpare: instances + 1 };
}

console.log(plan({ peakRps: 2000, latencyMs: 120, concurrencyPerInstance: 50, targetUtilization: 0.75 }));
{ inFlight: 240, instances: 7, withOneSpare: 8 }
قانون Little بيدّي 2000 × 0.12 = 240 طلب in-flight. على 50 × 0.75 = 37.5 طلب لكل نسخة يبقى 7 نسخ، وبالـ spare تبقى 8.

Cheat sheet · الخلاصة

  • 99.9% = 8.76 h/year = 43.2 min/month. 99.99% = 52.6 min/year = 4.32 min/month.
  • Serial: a^n (5 × 99.9% = 99.5%). Parallel: 1 - (1-a)^n, only if failures are independent. 5% shared failures: 99.99% → 99.94%.
  • Each nine removes an option: 52 min a year rules out manual failover.
  • Available ≠ durable. Redis with no persistence lost 9,068 of 9,068 acknowledged writes. S3: 11 nines durability, 4 nines availability (design).
  • synchronous_commit=off lost 89–3,746 acknowledged rows per crash; on lost 0. Kill -9 is milder than a power cut.
  • Replicas protect against machines, not against DELETE. Backups and PITR protect against people.
  • Little's law: L = λW. Throughput can grow with latency unchanged (16 → 1575 rps, 62 ms flat).
  • Batching adds a window of latency and wins under high concurrency. A cache cuts latency and raises throughput.
  • The average hides the tail. A percentile hides whatever is just past it: watch p99 and p99.9.
  • Closed-loop load tools hide stalls (p99 0.3 ms vs 974 ms). Measure from the intended send time.
  • Fan-out: 1 - 0.99^n, so 63.4% at 100 calls, 99% near 460. Hedge idempotent reads after about p95.
  • Plan for 70–80% utilization. Past 100% latency grows with no limit.
