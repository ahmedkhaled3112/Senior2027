Why this matters · ليه ده مهم

English

Chat is the case where HTTP's habits stop working. The server has to push, every connection is long-lived state pinned to one machine, and a phone can vanish without saying goodbye. The same four problems show up in any real-time feature you'll ship: order-status updates, live support, collaborative editing, trading screens. Interviewers pick it because a stateless-only mental model fails at the first question: "user A is on server 1 and user B is on server 2, now what?"

بالعامية

الـ chat هو الـ case اللي عادات الـ HTTP بتقف عندها. السيرفر لازم يبعت من نفسه، وكل connection عبارة عن state طويل العمر مربوط بجهاز واحد، والموبايل ممكن يختفي من غير ما يقول سلام. ونفس الأربع مشاكل دول هتقابلك في أي feature real-time: تحديث حالة الأوردر، الـ live support، الـ collaborative editing، شاشات الـ trading. والـ interviewer بيختاره لأن اللي دماغه stateless بس بيقع من أول سؤال: "المستخدم A على سيرفر 1 والمستخدم B على سيرفر 2، هتعمل إيه؟"

English

Model answer, numbers first. 50M × 40 = 2B messages/day ≈ 23k/s on average, ≈69k/s at a 3× peak. Concurrent sockets depend on how long sessions last: I assume 10% of daily users are connected at any moment, so 5M sockets. At 100k sockets per server that's 50 servers; with a 1.5× margin so one zone can die, 75. At 200 bytes per message including metadata: 400 GB/day, 146 TB/year raw, 438 TB/year with 3 replicas. Say every assumption out loud, because the 10% and the 200 bytes are the numbers the interviewer will push on.

The shape. Split the system by what holds state. Connection servers are stateful: they hold sockets and nothing else, so they can be numerous and dumb, and a deploy costs a reconnect wave. Chat services are stateless: they validate, assign an order, persist and fan out, so they scale like any API. Redis holds the routing table (user → connection server) and the presence keys. The message store holds the truth. Anything slow, like push notifications and search indexing, goes through a queue.

API. Sends go over the socket with a client-generated id, and history goes over HTTP so it can be cached, paged and retried like any other read. The data model is three tables: conversations, conversation_members with a cursor per device, and messages keyed by (conversation_id, seq).

  const peakFactor = 3;
  // افتراض: 10% من الـ DAU فاتحين في نفس اللحظة، وقيس ده من شغلك

    concurrentSockets: concurrent,
    connectionServers: servers,
    rawTBPerYear: Math.round(rawPerYear / TB),
    replicatedTBPerYear: Math.round((rawPerYear * replicationFactor) / TB),
  };
}

بالعامية

الإجابة النموذجية، الأرقام الأول. 50 مليون × 40 = 2 مليار رسالة في اليوم، يعني حوالي 23 ألف في الثانية في المتوسط وحوالي 69 ألف في الـ peak لو الـ peak 3 أضعاف. الـ sockets المفتوحة في نفس الوقت بتعتمد على طول الـ sessions: أنا هفترض إن 10% من مستخدمي اليوم متوصلين في أي لحظة، يعني 5 مليون socket. بـ 100k socket للسيرفر يبقوا 50 سيرفر، وبهامش 1.5 عشان zone كاملة تقدر تقع يبقوا 75. لو الرسالة 200 byte شاملة الـ metadata يبقى 400 GB في اليوم، و 146 TB في السنة raw، و 438 TB بالـ 3 replicas. قول كل افتراض بصوت عالي، لأن الـ 10% والـ 200 byte هما اللي الـ interviewer هيضغط عليهم.

الشكل العام. قسّم النظام حسب مين شايل state. الـ connection servers stateful: ماسكة sockets وبس، فتقدر تكتّرها وتخليها غبية، والـ deploy تمنه موجة reconnect. الـ chat services stateless: بتعمل validate وتحدد الترتيب وتخزن وتوزّع، فبتكبر زي أي API. Redis فيه جدول الـ routing (المستخدم على أنهي connection server) ومفاتيح الـ presence. والـ message store هو مصدر الحقيقة. وأي حاجة بطيئة زي الـ push notifications والـ search indexing بتمشي في queue.

الـ API. الإرسال بيمشي على الـ socket ومعاه id من الـ client، والـ history بيمشي على HTTP عشان يتعمله cache و paging و retry زي أي read. والـ data model تلات جداول: conversations، و conversation_members فيه cursor لكل جهاز، و messages والـ key بتاعه (conversation_id, seq).

فين هستخدمه في شغلي؟ لو عندك dashboard بيعرض تحديثات الأوردرات live، نفس التقسيم ينطبق: gateway صغير ماسك الـ sockets وبيعمل subscribe على Redis، والـ API العادي stateless هو اللي بيكتب في Postgres وبيعمل publish. كده الـ deploy للـ API مبيقطعش اتصال حد، والـ gateway بيتعمله deploy على مراحل.

Part 2 — WebSockets across servers 🔴 Advancedالجزء 2 — الـ WebSockets بين السيرفرات

English

The handshake, the upgrade, and the adapter pattern are in 04 · Real-time at scale. Here's the routing that the design needs. Two real ws processes run below, with Redis as the only thing they share. Each server keeps a local Map of the sockets it owns and writes route:user → serverId to Redis with a TTL. To deliver, a server looks up the route: if the user is local it writes to the socket, if the user is elsewhere it publishes to that server's own channel, and if there's no route the user is offline and the message goes down the offline path.

Publishing per server rather than per user is deliberate. With a channel per user, every connection adds a subscription, so 5M users would mean 5M subscriptions spread over the fleet. With one channel per server, the subscription count equals the server count, which is 75 here. Each server then receives only the traffic addressed to its own users, which is exactly what you want. To keep the demo short, the send logic that belongs to the chat service runs inside the connection server here.

Two details decide whether this survives production. The route must be released with compare-and-delete: a user who reconnects to server B while the old close event on A is still in flight must not have A delete B's route. The demo below shows the route surviving that race. Memory per socket sets how many sockets a box can hold, so measure it. And when a server dies its 100k clients all reconnect at once, so reconnects need full jitter, otherwise the survivors get a thundering herd.

To run these examples Node 22+, "type": "module" in package.json, and npm i ws ioredis pg. Start a throwaway Redis on a non-default port and write that port into a redis.port file one folder up. The small guard below refuses an empty or default port, so an example with FLUSHALL in it can never reach a real Redis. Parts 5 and 6 import pg-cluster.mjs, a helper that starts a throwaway Postgres on a free port. Use your own disposable instance instead, and never a database you care about.

import { readFileSync } from "node:fs";

// الدالة دي بترفض أي port فاضي أو default، عشان متوصلش بالـ Redis الحقيقي بالغلط
export function redisPort(): number {
  const raw = readFileSync(new URL("../redis.port", import.meta.url), "utf8").trim();
  const n = Number(raw);
  if (!/^\d+$/.test(raw) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error("refusing port " + raw);
  }
  return n;
}

// لازم connection تاني للـ subscribe، لأن الـ connection بتاعته مش بتعرف تنفذ commands عادية
const sub = new Redis({ host: "127.0.0.1", port });

const local = new Map<string, WebSocket>();

await sub.subscribe(`server:${serverId}`);
sub.on("message", (_channel, raw) => {
  const envelope = JSON.parse(raw) as { to: string };
  local.get(envelope.to)?.send(raw);

const releaseRoute = `if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end return 0`;

const wss = new WebSocketServer({ port: 0, host: "127.0.0.1" });
wss.on("listening", () => {
  const address = wss.address();
  if (typeof address === "object" && address !== null) process.send?.({ port: address.port });
});

wss.on("connection", (ws, req) => {
  const userId = new URL(req.url!, "ws://stand-in").searchParams.get("user")!;
  local.set(userId, ws);
  void redis.set(`route:${userId}`, serverId, "EX", 60);

  ws.on("message", async (data) => {
    const msg = JSON.parse(String(data)) as { to: string; text: string; clientMsgId: string };
    const envelope = JSON.stringify({ ...msg, from: userId, via: serverId });
    const target = await redis.get(`route:${msg.to}`);
    if (target === null) {
      // المستخدم offline، فالرسالة تتخزن ويتبعت push notification
      ws.send(JSON.stringify({ ack: msg.clientMsgId, status: "stored-offline" }));
      return;
    }
    if (target === serverId) local.get(msg.to)?.send(envelope);
    else await redis.publish(`server:${target}`, envelope);
    ws.send(JSON.stringify({ ack: msg.clientMsgId, status: "sent", target }));
  });

  ws.on("close", () => {
    if (local.get(userId) === ws) local.delete(userId);
    void redis.eval(releaseRoute, 1, `route:${userId}`, serverId);
  });
});

process.on("message", (m) => {
  if (m === "stop") process.exit(0);
});

// دي simulation بـ seed ثابت و virtual time، مش clients حقيقيين
console.log("SIMULATION: 100k clients of a dead server, one survivor takes 5k handshakes/s");

function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

function run(jitter: boolean) {
  const rand = mulberry32(42);
  const CLIENTS = 100_000;
  const CAPACITY_PER_SEC = 5_000;
  const backoffSec = (attempt: number) => Math.min(60, 5 * 2 ** attempt);
  // كل عنصر في الـ schedule هو ثانية محاولة العميل
  const nextAt = (attempt: number) => (jitter ? rand() * backoffSec(attempt) : backoffSec(attempt));
  let pending = Array.from({ length: CLIENTS }, () => ({ at: nextAt(0), attempt: 0 }));
  let second = 0, peak = 0, attempts = 0;
  while (pending.length > 0) {
    const due = pending.filter((c) => c.at < second + 1);
    const later = pending.filter((c) => c.at >= second + 1);
    peak = Math.max(peak, due.length);
    attempts += due.length;
    // الـ capacity بتتستهلك والباقي بيتعمله reject ويعيد المحاولة
    const rejected = due.slice(CAPACITY_PER_SEC);
    for (const c of rejected) { c.attempt++; c.at = second + 1 + nextAt(c.attempt); }
    pending = [...later, ...rejected];
    second++;
  }
  return { jitter, secondsToDrain: second, peakAttemptsPerSec: peak, totalAttempts: attempts };
}

Part 3 — Presence 🔴 Advancedالجزء 3 — الـ Presence

English

A TCP close is not reliable: a phone going into a tunnel sends nothing. So presence is defined by heartbeats, not by connections. Each device writes a timestamp with a TTL every few seconds, and "online" means at least one device's TTL hasn't expired. In Redis 8 this fits one hash per user with a per-field TTL through HEXPIRE, so one dead phone expires while the laptop keeps the user online. The run below kills the phone and then the laptop, and the keyspace events show each one disappearing about 2 s after its last heartbeat. Keyspace notifications are fire-and-forget pub/sub, so treat them as a hint and let the TTL be the truth.

The cost is in the fan-out, not the writes. With 200 friends and 10 status changes a day, telling all friends is 1.16M events/s, 50× the message rate itself. That's why presence is pull-then-subscribe: when a client opens a screen it asks for the status of the users visible on that screen and subscribes only to those. At about 5 watchers per user the same traffic drops to 29k events/s. Mobile networks also flap, so a dropped connection for 3 seconds shouldn't broadcast "offline" and then "online". A grace period (only report offline after N seconds of silence) removes most of that noise.

Part 4 — Ordering & receipts 🔴 Advancedالجزء 4 — الترتيب والـ receipts

English

You don't need a global order, and paying for one is a mistake. Users only compare messages inside one conversation, so a per-conversation sequence from one INCR gives a total order exactly where it's visible, and different conversations scale apart. Timestamps can't do this job: two servers' clocks disagree and two messages can share a millisecond.

Retries need an idempotency key from the client. The client generates clientMsgId before the first send, the server runs dedupe and INCR in one Lua script, and a retry returns the original seq. The hash tag {c:42} keeps all three keys in one slot, or the script would fail on Redis Cluster.

The client is the other half of the protocol. It drops anything at or below its last rendered seq, buffers anything ahead of it, and treats a persistent hole as a loss and refetches only that range from the log. The run below replays the real log through a simulated bad network. Note two things in the output. A gap threshold smaller than the reorder window wastes work: 221 refetches and 712 duplicates against 47 and 77. And a lost tail is invisible, because no later message arrives to reveal the gap, so the client must periodically compare its last seq with the server's. Receipts follow the same idea: store one high-water mark per member per conversation instead of a row per message, and only ever move it forward. Sent means the server acked, delivered means the recipient's device acked, read means the recipient reported it.

// (2) العميل بيعمل dedupe وبيكتشف الـ gap وبيجيب اللي ناقص من الـ log الحقيقي
class ConversationClient {
  lastRendered = 0;
  rendered: number[] = [];
  buffer = new Map<number, string>();
  duplicates = 0;
  refetches = 0;
  gapThreshold: number;
  constructor(gapThreshold: number) { this.gapThreshold = gapThreshold; }
  async receive(seq: number, payload: string) {
    if (seq <= this.lastRendered || this.buffer.has(seq)) { this.duplicates++; return; }
    this.buffer.set(seq, payload);
    this.drain();
    // لو عدد المستنيين وصل الـ threshold بنعتبر الناقص ضاع مش اتأخر
    if (this.buffer.size >= this.gapThreshold) await this.refetch();
  }
  drain() {
    while (this.buffer.has(this.lastRendered + 1)) {
      this.lastRendered++;
      this.rendered.push(this.lastRendered);
      this.buffer.delete(this.lastRendered);
    }
  }
  // الـ refetch بيجيب الـ gap بس، مش الـ log كله
  async refetch(until = Math.min(...this.buffer.keys()) - 1) {
    this.refetches++;
    const missing = await redis.zrangebyscore(k("42")[2], this.lastRendered + 1, until, "WITHSCORES");
    for (let i = 0; i < missing.length; i += 2) {
      const seq = Number(missing[i + 1]);
      if (seq > this.lastRendered && !this.buffer.has(seq)) this.buffer.set(seq, missing[i]!);
    }
    this.drain();
  }
}

الـ retries محتاجة idempotency key من الـ client. الـ client بيولّد clientMsgId قبل أول إرسال، والسيرفر بيعمل الـ dedupe والـ INCR في Lua script واحد، والـ retry بيرجع نفس الـ seq الأصلي. الـ hash tag {c:42} بيخلي التلات keys في slot واحد، وإلا السكريبت يقع على Redis Cluster.

الـ client هو النص التاني من البروتوكول. بيتجاهل أي حاجة عند أو تحت آخر seq عرضها، وبيخزن المؤقت أي حاجة قدّامه، ولو الـ gap فضل بيعتبره ضاع ويجيب المدى ده بس من الـ log. التشغيل فوق بيعيد الـ log الحقيقي على شبكة وحشة متسيمولة. لاحظ حاجتين: threshold أصغر من الـ reorder window بيضيع شغل (221 refetch و 712 تكرار مقابل 47 و 77). والـ tail الضايع مش باين، لأن مفيش رسالة بعده تكشف الـ gap، فالـ client لازم يقارن آخر seq عنده بتاع السيرفر كل فترة. الـ receipts بنفس الفكرة: مؤشر واحد لكل عضو في كل محادثة بدل صف لكل رسالة، وبيتحرك لقدام بس. sent يعني السيرفر عمل ack، و delivered يعني جهاز المستلم عمل ack، و read يعني المستلم بلّغ إنه قرا.

Interview question "How do you guarantee ordering in a group chat with 3 chat servers?" → Don't order by server clock. One atomic per-conversation counter (Redis INCR, or a row with UPDATE ... RETURNING) gives each message a seq, so order is total inside a conversation and absent across conversations. If the counter store is down, that conversation stops accepting sends rather than producing an ambiguous order.
"إزاي تضمن الترتيب في جروب و 3 chat servers؟" ← متبنيش الترتيب على ساعة السيرفر. عدّاد atomic لكل محادثة (INCR في Redis، أو صف بـ UPDATE ... RETURNING) بيدّي كل رسالة seq، فالترتيب كامل جوه المحادثة ومش موجود بين المحادثات. ولو مكان العدّاد وقع، المحادثة دي بتقف عن الإرسال بدل ما تطلع ترتيب ملخبط.

Part 5 — Storage 🔴 Advancedالجزء 5 — الـ Storage

English

The access pattern is narrow: append to a conversation and read a recent range of it, by a key you always know. That's a wide-column store's best case: partition key picks the node, clustering key keeps the rows sorted on disk. Two messages in one conversation sit next to each other, and "latest 50" is one seek. The schema below is CQL and is not run here, since Cassandra is not available on this machine.

A partition must be bounded, because a single channel can grow for years. Discord's published design used ((channel_id, bucket), message_id), with a bucket of about 10 days so a partition stayed under about 100 MB. The cost shows up on quiet conversations, where reading the last 50 messages walks many empty buckets, and the calculation below prints that. Their 2023 write-up describes the failure mode at scale: a hot partition on quorum reads makes every query served by that node slower, so they added data services with request coalescing in front of the database, and separately moved from 177 Cassandra nodes to 72 ScyllaDB nodes. The cost angle of that migration is in 44 · Cost & evolution.

What runs here is the same access pattern on real Postgres: hash partitions by conversation, primary key (conversation_id, seq). The plan touches one partition and 7 buffers for the last 50 messages, even in the giant channel. But the skew is real: one conversation put 34.4% of the rows into a partition whose fair share was 6.25%. Hashing distributes conversations, not messages.

فين هستخدمه في شغلي؟ لو عندك جدول audit_logs أو order_events بيكبر، ابدأ بـ Postgres partitions و (tenant_id, seq) قبل ما تفكر في Cassandra. وراقب الـ tenant الكبير: لو عميل واحد بقى 30% من الصفوف، الـ partition بتاعته هي اللي هتسخن، وهتحتاج تقسّمه بالوقت جوه.
Trade-off: wide-column vs Postgres Postgres gives you one system, transactions and joins, and it's fine for this pattern up to billions of rows with partitions. A wide-column store gives you linear write scaling and cheap multi-node replication, and it takes away joins, secondary indexes and ad-hoc queries. At 438 TB/year you'll likely want it. At 4 TB/year you almost certainly don't.
Postgres بيدّيك نظام واحد و transactions و joins، وكويس للنمط ده لحد مليارات الصفوف بالـ partitions. الـ wide-column بيدّيك write scaling خطي و replication رخيص على nodes كتير، وبياخد منك الـ joins والـ secondary indexes والـ ad-hoc queries. عند 438 TB في السنة غالبًا هتحتاجه، وعند 4 TB في السنة غالبًا لأ.

Part 6 — Groups & offline sync 🔴 Advancedالجزء 6 — الجروبات والـ offline sync

English

A group message can be stored two ways. Per-recipient inbox writes one row per member, which makes the "what's new for me" query trivial but multiplies writes by group size. Shared log with a read cursor writes the message once and keeps a last_seq per member. With my assumptions in the calculator below, inbox writes pass the shared log's fixed cost at around 8 members and reach 100B writes/day at 500. So small groups can use either, and big groups must use the cursor. Fan-out to online members still happens per recipient, but that's a socket write, not a durable row.

Offline sync follows directly. Each device keeps its own last_seq per conversation, because a phone and a laptop catch up independently. On reconnect, the client asks which conversations have last_seq greater than its cursor, then pages through each one in seq order and saves the cursor after every page, so a dropped connection resumes where it stopped. In the run below a phone gets 574 missed messages across 4 conversations, in order, then a second sync returns nothing.

The online path and the sync path deliver the same messages, so the client's dedupe by seq from Part 4 is what makes "both happened" harmless. For a device with no socket at all, the queue triggers a push notification, as built in 49 · Notification system. The push is only a wake-up call; the app then syncs over the normal path.

الـ offline sync نتيجة طبيعية لده. كل جهاز ماسك last_seq بتاعه لكل محادثة، لأن الموبايل واللاب توب بيلحقوا بشكل مستقل. عند الـ reconnect الـ client بيسأل أنهي محادثات last_seq بتاعها أكبر من الـ cursor بتاعه، وبعدين يعمل paging على كل واحدة بترتيب الـ seq، ويحفظ الـ cursor بعد كل صفحة، فلو النت قطع يكمل من مكانه. في التشغيل فوق الموبايل جاله 574 رسالة فايتة في 4 محادثات، بالترتيب، و sync تاني مرجّعش حاجة.

طريق الـ online وطريق الـ sync بيوصّلوا نفس الرسايل، فالـ dedupe بالـ seq من Part 4 هو اللي بيخلي الاتنين مع بعض مش مشكلة. ولو الجهاز مفيهوش socket خالص، الـ queue بيشغّل push notification زي اللي اتبنى في 49 · Notification system. الـ push مجرد إيقاظ، والـ app بعدها بيعمل sync عادي.

فين هستخدمه في شغلي؟ الـ notifications center في أي SaaS: صف لكل notification لكل مستخدم بيتفجر مع tenant فيه 50 ألف مستخدم. بدل كده اكتب الإعلان مرة واحدة في جدول، وخلي لكل مستخدم last_seen_seq، والعدّاد بتاع الـ unread يبقى max_seq - last_seen_seq. وبرضه الـ mobile app بعد ما يرجع من الـ background يبعت الـ cursors ويجيب الجديد بس.

Part 7 — Trade-offs & review 🔴 Advancedالجزء 7 — الـ trade-offs والمراجعة

English

WhatsApp and Slack want different things. WhatsApp treats the server as a mailbox: small groups, messages deleted after delivery in the classic model, and end-to-end encryption, so search and history live on the phone. Slack treats the server as the product: channels with thousands of members, searchable history and integrations, so the server must be able to read the content. The two sets of requirements point at different storage budgets and different fan-out strategies, which is why you ask before you design.

End-to-end encryption changes the back end. The server can't search or moderate content, and a new device can't fetch history unless the keys are shared. Group cost also changes: pairwise encryption means one ciphertext per member, 38,000 bytes for one message to 500 people in the run below, while a sender key, the approach used for groups in Signal-protocol messaging, means one 76-byte ciphertext. The price of sender keys is key distribution, and a re-key whenever someone leaves.

What breaks first at 10×. 500M daily users means 694k messages/s at peak. Socket count scales fine, since you just add boxes, up to 750 servers. The first thing to break is the shared backbone: one Redis carried ≈180–220k publishes/s here, so a peak of 347% of that doesn't fit, and you need sharded pub/sub (SPUBLISH) or per-cell Redis. Next is the reconnect wave of a large deploy, then storage at 4.4 PB/year.

import { createCipheriv, randomBytes } from "node:crypto";

// الديمو ده بيقارن تشفير رسالة جروب: لكل عضو لوحده مقابل sender key واحد
function encrypt(key: Buffer, text: string): Buffer {
  const iv = randomBytes(12);
  const cipher = createCipheriv("aes-256-gcm", key, iv);
  const body = Buffer.concat([cipher.update(text, "utf8"), cipher.final()]);
  return Buffer.concat([iv, cipher.getAuthTag(), body]);
}

import { WebSocket, WebSocketServer } from "ws";
import { once } from "node:events";

// الدالة دي بتعيد الاتصال بـ full jitter، والـ delay بيتصفّر بعد نجاح الاتصال
function connectForever(url: string, onConnected: (attempts: number) => void) {
  let attempt = 0, stopped = false, socket: WebSocket | undefined;
  const tryConnect = () => {
    if (stopped) return;
    attempt++;
    socket = new WebSocket(url);
    socket.on("open", () => { onConnected(attempt); attempt = 0; });
    socket.on("error", () => {});
    socket.on("close", () => {
      if (stopped) return;
      const cap = Math.min(2000, 50 * 2 ** attempt);
      setTimeout(tryConnect, Math.random() * cap);
    });
  };
  tryConnect();
  return () => { stopped = true; socket?.terminate(); };
}

Cheat sheet · الخلاصة

  • Numbers: 50M × 40 = 2B/day ≈ 23k/s avg, ≈69k/s peak; 10% online = 5M sockets; 75 servers; 146 TB/year raw, 438 TB with 3 replicas.
  • Split by state: connection servers hold sockets, chat services are stateless, Redis holds routes and presence.
  • One pub/sub channel per server, with a route lookup per message. Release routes with compare-and-delete.
  • Measure memory per socket (≈8.5 KB RSS here, idle) and treat it as a floor. Reconnect with full jitter.
  • Presence = heartbeat + TTL, per device with HEXPIRE. Send it only to who's looking (50× vs 1.25× the message rate), with a grace period for flapping.
  • Order per conversation with one atomic INCR; no global order. clientMsgId makes resends idempotent.
  • Client: dedupe by seq, buffer ahead, refetch only the gap, threshold above the reorder window, and periodic tail sync.
  • Receipts are high-water marks per member that only move forward. Read by all = min across members.
  • Storage: partition by (conversation, bucket), clustered by seq. Buckets bound partitions; quiet conversations pay in extra reads.
  • Small groups: inbox or log. Large groups: shared log + cursors. Device-level cursors drive offline sync; push is only a wake-up.
  • E2EE moves search and history to the device. Sender keys beat pairwise on bytes and cost re-keying.
  • First to break at 10×: the shared pub/sub backbone, then deploy reconnect waves, then storage cost.

  • pub/sub channel واحدة لكل سيرفر مع route lookup لكل رسالة، والـ route يتمسح بـ compare-and-delete.
  • قيس الـ memory لكل socket (حوالي 8.5 KB RSS هنا وهي فاضية) واعتبرها أرضية، و reconnect بـ full jitter.
  • الـ presence = heartbeat و TTL لكل جهاز بـ HEXPIRE، وتتبعت للي بيتفرج بس (50 ضعف مقابل 1.25 ضعف معدل الرسايل)، مع grace period للـ flapping.
  • الترتيب لكل محادثة بـ INCR واحد atomic من غير ترتيب global، و clientMsgId بيخلي إعادة الإرسال idempotent.
  • الـ client: dedupe بالـ seq، و buffer للي قدّام، و refetch للـ gap بس، و threshold أكبر من الـ reorder window، و tail sync كل فترة.
  • الـ receipts مؤشرات high-water لكل عضو بتتحرك لقدام بس، و read by all = أقل قيمة بين الأعضاء.
  • الـ storage: partition بالمحادثة والـ bucket، و clustering بالـ seq. الـ buckets بتحدد حجم الـ partition، والمحادثات الهادية بتدفع قرايات زيادة.
  • الجروبات الصغيرة inbox أو log، والكبيرة log مشترك و cursors، و cursors الأجهزة هي اللي بتشغّل الـ offline sync، والـ push مجرد إيقاظ.
  • الـ E2EE بينقل البحث والـ history للجهاز، والـ sender keys أوفر في الـ bytes وتمنها الـ re-keying.
  • أول حاجة بتقع عند 10×: الـ pub/sub المشترك، بعدها موجات الـ reconnect في الـ deploy، وبعدها تكلفة الـ storage.
