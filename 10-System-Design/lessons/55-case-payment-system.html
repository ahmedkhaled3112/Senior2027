Why this matters · ليه ده مهم

English

A payment system is the one design where a rare bug is a refund queue, a regulator's question, or a customer charged twice. The traffic is usually small and the correctness bar is absolute, which inverts the instincts every other case trains. In an interview this question separates people who say "use a transaction" from people who ask "what do we do when the PSP times out and we don't know whether the money moved?". The same mechanisms apply at work to anything that calls an external system with side effects: invoicing, SMS credits, shipping labels, payouts.

بالعامية

الـ payment system هو التصميم الوحيد اللي فيه bug نادر معناه طابور refunds، أو سؤال من جهة رقابية، أو عميل اتخصم منه مرتين. الـ traffic غالبًا صغير والصح لازم يبقى 100%، وده عكس اللي بتتعوّد عليه في باقي الـ cases. في الـ interview السؤال ده بيفرّق بين اللي بيقول "استخدم transaction" واللي بيسأل "هنعمل إيه لما الـ PSP يعمل timeout ومش عارفين الفلوس اتحركت ولا لأ؟". ونفس الآليات دي هتستخدمها في شغلك في أي حاجة بتكلم نظام خارجي وليها أثر: الفواتير، رصيد الـ SMS، بوالص الشحن، الـ payouts.

English

Requirements with numbers. Functional: authorize, capture, refund, webhook intake, daily reconciliation, merchant balances. Non-functional: zero double charges and zero lost charges as a hard invariant, API p95 under 2 s (dominated by the PSP), 99.95% availability for the write path, and audit data kept for seven years (a common retention assumption; confirm it with your regulator or auditor).

Say the scale out loud, because it changes the design. One million a day is only about 12 TPS on average and about 35 at peak. A single Postgres primary handles that with room to spare. So correctness beats scale: no sharding, no Kafka on the first whiteboard, and every minute goes into idempotency, unknown outcomes, the ledger and reconciliation. The number that actually drives the design is the bottom line of the calculator below: thousands of unknown outcomes every day.

Part 2 — No double charge 🔴 Advancedالجزء 2 — مفيش double charge

English

The API side is the idempotent endpoint from lesson 30, which this lesson does not re-teach. The new problem is the outbound call. A timeout from the PSP has three possible meanings: the request never arrived, the PSP processed it and the response was lost, or the PSP is still processing it. From the caller these are indistinguishable (lesson 28), so a timeout means unknown, never failed.

Three retry strategies against a labelled local PSP stub show what that costs. The stub can drop the connection before processing (drop-before), drop it after charging (drop-after), or finish charging after the client has given up (slow). Querying before retrying fixes drop-after but not slow, because the charge does not exist yet at query time. Only a stable idempotency key sent to the PSP closes both.

The flow in pay.ts has four steps: reserve the key, write the intent, query if a previous attempt may have reached the PSP, then call with the same key. On an unknown outcome the row stays in_doubt and the client gets 202. A retry with the same key or the sweeper finishes the job.

The test kills a real child process with process.exit(137) at each of five points, combined with each PSP behaviour and both recovery paths. The invariant is exactly one charge per key, and the first draft of this code failed it: an unguarded UPDATE ... SET in_doubt = true WHERE id = $1 raced the sweeper and left two finished rows marked as doubtful. The fix is the state in the WHERE clause, which is the theme of Part 3.

// ده STUB محلي مش PSP حقيقي، بيقلّد الأعطال اللي بتحصل في الشبكة بين السيرفر والـ PSP
import http from "node:http";
import type { AddressInfo } from "node:net";
import { setTimeout as sleep } from "node:timers/promises";

export type Behaviour = "ok" | "drop-before" | "drop-after" | "slow" | "declined";
export interface Charge { ref: string; reference: string; key: string | null; amountMinor: number }

export async function startPspStub(opts: { slowMs?: number } = {}) {
  const slowMs = opts.slowMs ?? 400;
  const charges: Charge[] = [];
  const byKey = new Map<string, Charge>();
  const scripts = new Map<string, Behaviour[]>();
  let requests = 0;
  let seq = 0;

  // التسجيل هنا هو الفلوس الفعلية: لو الـ key اتكرر بيرجّع نفس الـ charge
  const record = (reference: string, key: string | null, amountMinor: number): Charge => {
    if (key && byKey.has(key)) return byKey.get(key)!;
    const charge: Charge = { ref: `psp_${++seq}`, reference, key, amountMinor };
    charges.push(charge);
    if (key) byKey.set(key, charge);
    return charge;
  };

  const server = http.createServer((req, res) => {
    const url = new URL(req.url ?? "/", "http://stub");
    const send = (code: number, body: unknown) => {
      res.writeHead(code, { "content-type": "application/json" });
      res.end(JSON.stringify(body));
    };
    if (req.method === "GET" && url.pathname === "/charges") {
      const found = charges.find((c) => c.reference === url.searchParams.get("reference"));
      return found ? send(200, found) : send(404, { error: "not_found" });
    }
    let raw = "";
    req.on("data", (d) => (raw += d));
    req.on("end", async () => {
      requests++;
      const body = JSON.parse(raw) as { reference: string; amountMinor: number };
      const key = (req.headers["idempotency-key"] as string | undefined) ?? null;
      const behaviour = scripts.get(body.reference)?.shift() ?? "ok";
      if (behaviour === "drop-before") return void req.socket.destroy();
      if (behaviour === "drop-after") {
        record(body.reference, key, body.amountMinor);
        return void req.socket.destroy();
      }
      if (behaviour === "declined") return send(402, { error: "card_declined" });
      // الحالة الأصعب: الـ PSP بيخلّص بعد ما العميل يكون زهق ومشي
      if (behaviour === "slow") await sleep(slowMs);
      const charge = record(body.reference, key, body.amountMinor);
      if (!res.destroyed) send(200, charge);
    });
  });
  await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));
  const { port } = server.address() as AddressInfo;

  return {
    url: `http://127.0.0.1:${port}`,
    slowMs,
    script: (reference: string, list: Behaviour[]) => void scripts.set(reference, list),
    chargesFor: (reference: string) => charges.filter((c) => c.reference === reference),
    allCharges: () => charges,
    requestCount: () => requests,
    close: () => new Promise((r) => { server.closeAllConnections(); server.close(r); }),
  };
}

// الخطأ ده معناه: مش عارفين الفلوس اتسحبت ولا لأ
export class PspUnknownOutcome extends Error {}
export class PspDeclined extends Error {}

export function pspClient(baseUrl: string, timeoutMs = 120) {
  return {
    async authorize(reference: string, amountMinor: number, idempotencyKey: string | null): Promise<Charge> {
      const headers: Record<string, string> = { "content-type": "application/json" };
      if (idempotencyKey) headers["idempotency-key"] = idempotencyKey;
      let res: Response;
      try {
        res = await fetch(`${baseUrl}/authorize`, {
          method: "POST",
          headers,
          body: JSON.stringify({ reference, amountMinor }),
          signal: AbortSignal.timeout(timeoutMs),
        });
      } catch (err) {
        // أي timeout أو قطع اتصال هنا معناه "مش عارفين"، مش "فشلت"
        throw new PspUnknownOutcome((err as Error).name);
      }
      if (res.status === 402) throw new PspDeclined("card_declined");
      if (!res.ok) throw new PspUnknownOutcome(`status ${res.status}`);
      return (await res.json()) as Charge;
    },
    async lookup(reference: string): Promise<Charge | null> {
      const res = await fetch(`${baseUrl}/charges?reference=${encodeURIComponent(reference)}`, {
        signal: AbortSignal.timeout(timeoutMs * 4),
      });
      return res.status === 404 ? null : ((await res.json()) as Charge);
    },
  };
}

type Strategy = (reference: string) => Promise<void>;

// (1) بيعيد على طول من غير key
const blindRetry: Strategy = async (reference) => {
  for (let attempt = 0; attempt < 3; attempt++) {
    try { await client.authorize(reference, 1000, null); return; }
    catch (err) { if (!(err instanceof PspUnknownOutcome)) throw err; }
  }
};
// (2) بيسأل الأول، ولو ملقاش حاجة يعيد من غير key
const queryThenRetry: Strategy = async (reference) => {
  for (let attempt = 0; attempt < 3; attempt++) {
    try { await client.authorize(reference, 1000, null); return; }
    catch (err) {
      if (!(err instanceof PspUnknownOutcome)) throw err;
      if (await client.lookup(reference)) return;
    }
  }
};
// (3) نفس الـ key في كل محاولة، والسؤال قبل الإعادة
const sameKey: Strategy = async (reference) => {
  const key = `pay_${reference}`;
  for (let attempt = 0; attempt < 3; attempt++) {
    try { await client.authorize(reference, 1000, key); return; }
    catch (err) {
      if (!(err instanceof PspUnknownOutcome)) throw err;
      if (await client.lookup(reference)) return;
    }
  }
};

const strategies: [string, Strategy][] = [
  ["blind retry, no key", blindRetry],
  ["query then retry, no key", queryThenRetry],
  ["same key + query", sameKey],
];
for (const [name, run] of strategies) {
  const refs: string[] = [];

export const CRASH_POINTS = ["after-insert", "after-intent", "before-psp", "after-psp", "after-commit"] as const;
export type PayResult = { status: string };
interface Row { id: string; order_id: string; idempotency_key: string; amount_minor: string; attempts: number; state: string }

// الدالة دي ممكن تتنادى كام مرة بنفس الـ key، والنتيجة charge واحدة
export async function pay(db: pg.Pool, psp: PspClient, req: PayRequest, crash: Crash): Promise<PayResult> {
  // (1) احجز الـ key، ولو موجود الـ insert مبيعملش حاجة
  await db.query(
    `INSERT INTO payments (idempotency_key, order_id, amount_minor, currency)
     VALUES ($1, $2, $3, $4) ON CONFLICT (idempotency_key) DO NOTHING`,
    [req.key, req.orderId, req.amountMinor, req.currency],
  );
  crash("after-insert");
  const { rows } = await db.query<Row>(`SELECT * FROM payments WHERE idempotency_key = $1`, [req.key]);
  const row = rows[0]!;
  if (row.state !== "CREATED") return { status: row.state };

  // (2) اكتب النية قبل ما تكلم الـ PSP، عشان لو وقعت حد يعرف إن في call ممكن تكون راحت
  // الـ state في الـ WHERE ضروري: من غيره الـ sweeper ممكن يكون خلّص الصف وإحنا نرجّعه in_doubt
  const intent = await db.query(
    `UPDATE payments SET in_doubt = true, attempts = attempts + 1, updated_at = now() WHERE id = $1 AND state = 'CREATED'`,
    [row.id],
  );
  if (intent.rowCount === 0) {
    // حد تاني خلّص الصف قبلنا، فرجّع حالته الحقيقية
    const latest = await db.query<Row>(`SELECT * FROM payments WHERE id = $1`, [row.id]);
    return { status: latest.rows[0]!.state };
  }
  crash("after-intent");
  return settle(db, psp, row, crash);
}

export async function settle(db: pg.Pool, psp: PspClient, row: Row, crash: Crash): Promise<PayResult> {
  try {
    // (3) لو دي مش أول محاولة النتيجة القديمة مجهولة، فاسأل الأول
    let charge = row.attempts > 0 ? await psp.lookup(row.order_id) : null;
    crash("before-psp");
    // (4) لو ملقيناش حاجة ابعت بنفس الـ key، والـ PSP هيرجّع نفس الـ charge لو الأولانية وصلت متأخر
    charge ??= await psp.authorize(row.order_id, Number(row.amount_minor), row.idempotency_key);
    crash("after-psp");
    await db.query(
      `UPDATE payments SET state = 'AUTHORIZED', psp_ref = $2, in_doubt = false, updated_at = now()
       WHERE id = $1 AND state = 'CREATED'`,
      [row.id, charge.ref],
    );
    crash("after-commit");
    return { status: "AUTHORIZED" };
  } catch (err) {
    // نتيجة مجهولة: سيب الصف in_doubt وارجّع PENDING للعميل، ومتعيدش هنا
    if (err instanceof PspUnknownOutcome) return { status: "PENDING" };
    throw err;
  }
}

// الـ sweeper بيخلّص أي صف فضل معلّق بعد crash أو timeout
export async function recover(db: pg.Pool, psp: PspClient): Promise<number> {
  const { rows } = await db.query<Row>(`SELECT * FROM payments WHERE state = 'CREATED'`);
  for (const row of rows) {
    const intent = await db.query(
      `UPDATE payments SET in_doubt = true, attempts = attempts + 1, updated_at = now() WHERE id = $1 AND state = 'CREATED'`,
      [row.id],
    );
    if (intent.rowCount === 0) continue;
    await settle(db, psp, { ...row, attempts: row.attempts + 1 }, () => {});
  }
  return rows.length;
}

Part 3 — The state machine 🔴 Advancedالجزء 3 — الـ state machine

English

A payment's life is CREATED → AUTHORIZED → CAPTURED → REFUNDED, with FAILED reachable before capture. Enforce the transitions in the database, because several actors write this row: the API, webhooks, the sweeper and reconciliation. UPDATE ... WHERE id = $1 AND state = $expected is a compare-and-swap: an invalid transition affects 0 rows, and two concurrent captures produce exactly one winner. A single statement both moves the state and writes the history row, so a transition can never exist without its audit record.

A trigger backed by a legal_transitions table is the second line of defence, for code that forgets the guard or for a human in psql.

PSP webhooks arrive out of order and more than once. Stripe's docs state plainly that event order is not guaranteed. So dedupe on the event id, lock the payment row, and apply an event only if it moves the payment forward. A late payment.authorized after payment.captured is stale, gets recorded and changes nothing. Allowing a jump from CREATED to CAPTURED is correct here, because the PSP is the source of truth for what already happened.

CREATE TABLE legal_transitions (
  from_state payment_state NOT NULL,
  to_state   payment_state NOT NULL,
  PRIMARY KEY (from_state, to_state)
);
INSERT INTO legal_transitions VALUES
  ('CREATED', 'AUTHORIZED'), ('CREATED', 'FAILED'),
  ('AUTHORIZED', 'CAPTURED'), ('AUTHORIZED', 'FAILED'),
  ('CAPTURED', 'REFUNDED'),
  -- الـ webhooks ممكن توصل بالعكس، فالقفز لقدام مسموح
  ('CREATED', 'CAPTURED'), ('CREATED', 'REFUNDED'), ('AUTHORIZED', 'REFUNDED');

-- خط الدفاع التاني: حتى لو كود غلط عمل UPDATE مباشر، الـ DB بترفض
CREATE FUNCTION enforce_legal_transition() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.state IS DISTINCT FROM OLD.state AND NOT EXISTS (
    SELECT 1 FROM legal_transitions WHERE from_state = OLD.state AND to_state = NEW.state
  ) THEN
    RAISE EXCEPTION 'illegal payment transition % -> %', OLD.state, NEW.state USING ERRCODE = '23514';
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER payments_legal BEFORE UPDATE OF state ON payments
  FOR EACH ROW EXECUTE FUNCTION enforce_legal_transition();

export async function transition(q: pg.Pool | pg.PoolClient, id: string, from: State, to: State, source: string, eventId: string | null = null): Promise<boolean> {
  const r = await q.query(
    `WITH moved AS (
       UPDATE payments SET state = $3::payment_state, updated_at = now()
       WHERE id = $1 AND state = $2::payment_state RETURNING id)
     INSERT INTO payment_transitions (payment_id, from_state, to_state, source, event_id)
     SELECT id, $2::payment_state, $3::payment_state, $4, $5 FROM moved`,
    [id, from, to, source, eventId],
  );
  return r.rowCount === 1;
}

const RANK: Record<State, number> = { CREATED: 0, AUTHORIZED: 1, CAPTURED: 2, REFUNDED: 3, FAILED: 3 };
const TARGET: Record<string, State> = { "payment.authorized": "AUTHORIZED", "payment.captured": "CAPTURED", "payment.refunded": "REFUNDED", "payment.failed": "FAILED" };
interface Webhook { eventId: string; pspRef: string; type: string }

async function handleWebhook(ev: Webhook): Promise<string> {
  const c = await db.connect();
  try {
    await c.query("BEGIN");
    // الـ event اللي اتنفذ قبل كده بيرجع 200 من غير أي تأثير
    const fresh = await c.query(`INSERT INTO webhook_events (event_id, psp_ref, type) VALUES ($1, $2, $3) ON CONFLICT DO NOTHING`, [ev.eventId, ev.pspRef, ev.type]);
    if (fresh.rowCount === 0) { await c.query("COMMIT"); return "duplicate"; }
    // الـ lock هنا بيخلي الـ events بتاعة نفس الـ payment تتنفذ واحد ورا التاني
    const { rows } = await c.query(`SELECT id, state FROM payments WHERE psp_ref = $1 FOR UPDATE`, [ev.pspRef]);
    const current = rows[0].state as State;
    const target = TARGET[ev.type]!;
    let outcome: string;
    if (RANK[target] <= RANK[current]) outcome = "stale";
    else if (await transition(c, rows[0].id, current, target, "webhook", ev.eventId)) outcome = "applied";
    else outcome = "conflict";
    await c.query(`UPDATE webhook_events SET outcome = $2 WHERE event_id = $1`, [ev.eventId, outcome]);
    await c.query("COMMIT");
    return outcome;
  } catch (err) {
    await c.query("ROLLBACK");
    throw err;
  } finally {
    c.release();
  }
}

Part 4 — The double-entry ledger 🔴 Advancedالجزء 4 — الـ double-entry ledger

English

Every money movement is a transaction made of at least two entries whose debits equal their credits. Money is never created or lost inside the system, so an imbalance is a bug you can detect with one query. Entries are immutable: a mistake is corrected with a new reversing transaction, which is exactly what an auditor wants to see. Amounts are integers in minor units (section 07 · 3.7).

The balance check is a DEFERRABLE INITIALLY DEFERRED constraint trigger. Entries are inserted one by one, so after the first insert the transaction is legitimately unbalanced. A deferred trigger runs at COMMIT, when all entries exist. BEFORE UPDATE OR DELETE and BEFORE TRUNCATE triggers forbid rewriting history. UNIQUE (payment_ref, kind) stops the same capture being posted twice. Balances are derived with a SUM, so there is no balance column that can drift.

A capture of 10,000 with a 3% fee has three legs: debit psp_clearing 10,000, credit the merchant 9,700, and credit fee_revenue 300. The fee uses integer division so no fractions appear. A refund reverses those three legs in a new transaction.

-- بيتشغل عند الـ COMMIT مش عند كل insert، عشان الصفوف بتتكتب واحد ورا التاني
CREATE FUNCTION assert_balanced() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE bad record;
BEGIN
  SELECT currency,
         sum(amount_minor) FILTER (WHERE direction = 'D') AS debits,
         sum(amount_minor) FILTER (WHERE direction = 'C') AS credits
    INTO bad
    FROM ledger_entries WHERE tx_id = NEW.tx_id
   GROUP BY currency
  HAVING coalesce(sum(amount_minor) FILTER (WHERE direction = 'D'), 0)
      <> coalesce(sum(amount_minor) FILTER (WHERE direction = 'C'), 0)
   LIMIT 1;
  IF FOUND THEN
    RAISE EXCEPTION 'unbalanced ledger tx %: debits % credits % %', NEW.tx_id, bad.debits, bad.credits, bad.currency
      USING ERRCODE = '23514';
  END IF;
  RETURN NULL;
END $$;
CREATE CONSTRAINT TRIGGER ledger_balanced AFTER INSERT ON ledger_entries
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION assert_balanced();

-- الـ ledger append-only: التصحيح بيبقى transaction جديدة مش تعديل
CREATE FUNCTION forbid_ledger_change() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'ledger is append-only: % on % is forbidden', TG_OP, TG_TABLE_NAME USING ERRCODE = '23514';
END $$;
CREATE TRIGGER entries_immutable BEFORE UPDATE OR DELETE ON ledger_entries
  FOR EACH ROW EXECUTE FUNCTION forbid_ledger_change();
CREATE TRIGGER entries_no_truncate BEFORE TRUNCATE ON ledger_entries
  FOR EACH STATEMENT EXECUTE FUNCTION forbid_ledger_change();
CREATE TRIGGER tx_immutable BEFORE UPDATE OR DELETE ON ledger_transactions
  FOR EACH ROW EXECUTE FUNCTION forbid_ledger_change();

-- الـ balance محسوب من الـ entries، مفيش عمود balance يتلخبط
CREATE VIEW account_balances AS
SELECT a.id, a.kind, a.currency,
       coalesce(sum(CASE e.direction WHEN 'D' THEN e.amount_minor ELSE -e.amount_minor END), 0)::bigint AS debit_minus_credit
  FROM accounts a LEFT JOIN ledger_entries e ON e.account_id = a.id
 GROUP BY a.id, a.kind, a.currency;
import type pg from "pg";

export interface Entry { account: string; direction: "D" | "C"; amountMinor: number }

// الـ header والـ entries في transaction واحدة، والـ deferred trigger بيفحص عند الـ COMMIT
export async function postTx(c: pg.PoolClient, paymentRef: string, kind: string, entries: Entry[], opts: { currency?: string; at?: string } = {}): Promise<string> {
  const currency = opts.currency ?? "EGP";
  // الوقت بييجي من الحدث المالي نفسه لو معروف، زي وقت الـ capture في ملف الـ PSP
  const { rows } = await c.query(
    `INSERT INTO ledger_transactions (payment_ref, kind, created_at) VALUES ($1, $2, coalesce($3::timestamptz, now())) RETURNING id`,
    [paymentRef, kind, opts.at ?? null],
  );
  const txId = rows[0].id as string;
  for (const e of entries) {
    await c.query(
      `INSERT INTO ledger_entries (tx_id, account_id, direction, amount_minor, currency) VALUES ($1, $2, $3, $4, $5)`,
      [txId, e.account, e.direction, e.amountMinor, currency],
    );
  }
  return txId;
}

}

كل حركة فلوس هي transaction فيها entries على الأقل اتنين، والـ debits بتساوي الـ credits. الفلوس مبتتخلقش ومبتضيعش جوه النظام، فأي عدم توازن ده bug تقدر تكشفه بـ query واحدة. الـ entries immutable: الغلطة بتتصلح بـ transaction عكسية جديدة، وده بالظبط اللي المراجع عايز يشوفه. والمبالغ integers بالـ minor units (قسم 07 · 3.7).

فحص التوازن constraint trigger بـ DEFERRABLE INITIALLY DEFERRED. الـ entries بتتكتب واحد ورا التاني، فبعد أول insert الـ transaction طبيعي تبقى مش متوازنة. الـ deferred trigger بيشتغل عند الـ COMMIT، لما كل الـ entries تبقى موجودة. وتريجرز BEFORE UPDATE OR DELETE وBEFORE TRUNCATE بتمنع تعديل التاريخ. وUNIQUE (payment_ref, kind) بيمنع نفس الـ capture يتسجل مرتين. والأرصدة محسوبة بـ SUM، فمفيش عمود balance يتلخبط.

الـ capture بتاع 10,000 بعمولة 3% ليه 3 أرجل: debit لـ psp_clearing بـ 10,000، وcredit للتاجر بـ 9,700، وcredit لـ fee_revenue بـ 300. العمولة بالقسمة الصحيحة فمفيش كسور. والـ refund بيعكس الـ 3 أرجل في transaction جديدة.

فين هستخدمه في شغلي؟ أي wallet أو نظام نقط أو رصيد تاجر: لو عندك عمود users.balance بتعمله UPDATE، ومفيش سجل يقولك ليه الرقم ده، أول خلاف مع عميل هيبقى مستحيل تحله. اعمل الـ ledger الأول والـ balance يبقى query أو snapshot. والغلطة الشائعة: تحسب العمولة بـ float، فبعد مليون عملية الماليات تلاقي فرق جنيهات مش عارفة تفسره.
Interview question "Why double-entry, and why not just a balance column?" → A balance column tells you the current number and nothing else. With double-entry every number is explained by rows, an imbalance is one SUM away, corrections are visible instead of overwritten, and concurrent writers append rather than fight over one row.
"ليه double-entry ومش مجرد عمود balance؟" ← عمود الـ balance بيقولك الرقم الحالي وبس. في الـ double-entry كل رقم ليه صفوف بتشرحه، وعدم التوازن بتلاقيه بـ SUM واحدة، والتصحيحات بتبان بدل ما تتكتب فوق القديم، والـ writers المتزامنين بيضيفوا صفوف بدل ما يتخانقوا على صف واحد.

Part 5 — Reconciliation 🔴 Advancedالجزء 5 — الـ reconciliation

English

Everything so far guards against bugs you imagined. Reconciliation catches the ones you did not: a webhook the PSP never sent, a manual refund in the PSP dashboard, a settlement error on their side. Once a day, load the PSP's settlement file and compare it with the ledger using a FULL JOIN, so that rows missing from either side still appear.

The script below writes 1,000 captures to the real ledger, generates a CSV with planted anomalies, and must find all of them. The classes are: matched; timing (captured just before the cutoff, expected in tomorrow's file); missing_at_psp; amount_mismatch; duplicate (the PSP settled the same reference twice); unknown_at_ledger (the PSP has money we have no record of); and lost_capture (the payment exists but its webhook never arrived).

Only two classes are fixed automatically. timing is carried to the next run, and lost_capture is repaired because both sides agree on what happened. Everything else goes to a human queue, because guessing about money is worse than waiting. The job runs daily, is safe to re-run, and alerts whenever a row needs a person.

Part 6 — Retries and PCI scope 🔴 Advancedالجزء 6 — الـ retries والـ PCI scope

English

Retry policy. Write it as one function, because the decision depends on what the outcome means. The backoff and retry wrappers live in section 08 · 3.2. Network errors and 5xx responses are unknown, so query first and reuse the same key. A 402 decline is final, and retrying a card the bank refused only earns you more declines and possibly a flag. Other 4xx responses are bugs: stop and alert. Note that Stripe's docs for its v1 API say a retry with the same key replays the saved response, including 500 errors, so with such a PSP the retry does not re-attempt the charge and only the query tells you what happened.

Outbox toward the PSP. The state change and the intent to call the PSP commit in one transaction (section 07 · 3.4, section 08 · 3.3). The worker claims rows with a lease and SKIP LOCKED, then makes the HTTP call outside any transaction, because holding a row lock and a connection across a slow PSP is how a PSP incident becomes a database incident. A worker that dies mid-flight simply lets the lease expire, and the same key makes the re-send harmless.

PCI scope. Tokenization means the card number goes straight from the browser to the PSP's hosted fields, and your servers only ever see a token. That moves most of the PCI DSS burden to the PSP. Secondary sources describe PCI DSS v4.0.1 as the active version; this lesson could not confirm that on PCI SSC's own site, so check their document library before you quote it. Enforce the boundary with a test: scan logs for numbers that pass a Luhn check. Luhn matters because a long order number usually fails it, so the scanner stays quiet on normal IDs.

3-D Secure in one line: the issuing bank challenges the cardholder, which cuts fraud and usually shifts chargeback liability away from the merchant, at the cost of some checkout drop-off.

// الـ policy في مكان واحد: كل نتيجة ليها قرار، والمحاولات ليها سقف
export type Outcome =
  | { kind: "timeout" } | { kind: "connection-reset" }
  | { kind: "http"; status: number; retryAfterMs?: number };
export type Decision = "done" | "query-then-retry-same-key" | "wait-retry-same-key" | "final-no-retry" | "bug-stop-and-alert";

export function decide(o: Outcome): Decision {
  if (o.kind !== "http") return "query-then-retry-same-key";
  if (o.status >= 200 && o.status < 300) return "done";
  if (o.status === 429) return "wait-retry-same-key";
  // الـ 5xx ممكن يكون الـ PSP خلّص الشغل والرد هو اللي وقع، فمش عارفين
  if (o.status >= 500) return "query-then-retry-same-key";
  if (o.status === 402) return "final-no-retry";
  return "bug-stop-and-alert";
}

}

// الـ Luhn بيفلتر الأرقام الطويلة العادية عن أرقام الكروت الحقيقية
export function luhnValid(digits: string): boolean {
  let sum = 0;
  let double = false;
  for (let i = digits.length - 1; i >= 0; i--) {
    let d = digits.charCodeAt(i) - 48;
    if (double) { d *= 2; if (d > 9) d -= 9; }
    sum += d;
    double = !double;
  }
  return digits.length >= 13 && digits.length <= 19 && sum % 10 === 0;
}

// بنقبل مسافات أو شرط بين الأرقام، وده اللي بييجي من الـ forms غالبًا
const CANDIDATE = /\b\d(?:[ -]?\d){12,18}\b/g;

export function findPans(text: string): string[] {
  return [...text.matchAll(CANDIDATE)].map((m) => m[0]).filter((m) => luhnValid(m.replace(/\D/g, "")));
}

export function maskPans(text: string): string {
  return text.replace(CANDIDATE, (m) => {
    const digits = m.replace(/\D/g, "");
    return luhnValid(digits) ? `[PAN-REDACTED ****${digits.slice(-4)}]` : m;
  });
}

الـ outbox ناحية الـ PSP. تغيير الحالة ونية مكالمة الـ PSP بيتعملوا commit في transaction واحدة (قسم 07 · 3.4 وقسم 08 · 3.3). الـ worker بياخد الصفوف بـ lease وSKIP LOCKED، وبعدين الـ HTTP call بتتعمل بره أي transaction، لأن مسك row lock وconnection طول فترة PSP بطيء هو اللي بيحوّل incident عند الـ PSP لـ incident عند الـ DB. والـ worker اللي بيموت في النص، الـ lease بتاعه بينتهي، ونفس الـ key بيخلي إعادة الإرسال من غير ضرر.

الـ PCI scope. الـ tokenization معناها إن رقم الكارت بيروح من المتصفح لـ hosted fields بتوع الـ PSP على طول، والسيرفرات بتاعتك مبتشوفش غير token. وده بينقل أغلب حِمل PCI DSS على الـ PSP. مصادر ثانوية بتقول إن PCI DSS v4.0.1 هي النسخة الشغالة، والدرس ده معرفش يأكد ده من موقع PCI SSC نفسه، فاتأكد من مكتبة المستندات بتاعتهم قبل ما تقتبسها. وافرض الحدود دي باختبار: دوّر في الـ logs على أرقام بتعدي Luhn check. الـ Luhn مهم لأن رقم الأوردر الطويل غالبًا بيفشل فيه، فالـ scanner مش هيزعّقلك على IDs عادية.

3-D Secure في سطر: البنك المُصدِر بيطلب من صاحب الكارت يثبت هويته، وده بيقلل الـ fraud وغالبًا بينقل مسؤولية الـ chargeback بعيد عن التاجر، بس بتخسر شوية عملاء في الـ checkout.

فين هستخدمه في شغلي؟ حط findPans في test بيعدي على الـ logs بتاعة الـ integration tests، وفي الـ logger نفسه كـ redaction. وأول سطر تدوّر عليه في الـ code review: logger.info(req.body) على أي route فيه بيانات دفع. والغلطة الشائعة: تعمل HTTP call للـ PSP جوه BEGIN ... COMMIT، فلما الـ PSP يبطأ الـ connections كلها تتحجز والـ API كله يقع.
Trade-off: Luhn scanner false positives About 1 in 10 random long digit strings passes Luhn, so a busy log will flag some order numbers. Tighten it with known card prefixes or by ignoring fields you control, but keep the failure loud. Part 7 — Trade-offs and review 🔴 Advancedالجزء 7 — الـ trade-offs والمراجعة

English

PSP failover is the risky one. Adding a second PSP sounds like pure availability, but if you fail over on an unknown outcome you may charge the customer at both providers. The labelled simulation below assumes 1.5% unknown outcomes, 40% of which really charged. The rule that follows: fail over only fresh payments that have never been sent. An in-doubt payment stays with its PSP until that PSP answers.

What actually changes at 10× (10M a day, 116 TPS average, 347 peak): not the TPS, which Postgres still handles. What breaks first is the single-row balance if you added one. Every capture for a big merchant queues on that row lock, so the ceiling is one divided by your commit latency. Measured below on this machine, the extra row cost roughly a factor of 2 to 4 in throughput once warmed up, and commit here is well under a millisecond. On a cloud disk at 3 ms the same row tops out near 330 writes a second. Next come 22 billion ledger rows a year (partition by month, archive to object storage), a reconciliation job that outgrows its window (partition by day, process per-merchant batches), PSP rate limits (a token bucket in front of the outbox), and webhook bursts (acknowledge fast, process from a queue).

const PAYMENTS = 100_000;
const UNKNOWN_RATE = 0.015;
const ACTUALLY_CHARGED = 0.4;

let s = 2026;
const rand = () => ((s = (s * 1664525 + 1013904223) >>> 0) / 4294967296);

function simulate(policy: "failover-on-any-error" | "failover-only-fresh") {
  let doubles = 0, charged = 0, held = 0;
  for (let i = 0; i < PAYMENTS; i++) {
    const unknown = rand() < UNKNOWN_RATE;
    if (!unknown) { charged++; continue; }
    const chargedAtA = rand() < ACTUALLY_CHARGED;
    if (policy === "failover-on-any-error") {
      charged++;
      if (chargedAtA) doubles++;
    } else {
      // السياسة الآمنة: الدفعة المجهولة بتفضل مكانها لحد ما A يرد
      held++;
      if (chargedAtA) charged++;
    }
  }
  return { policy, doubles, charged, held, doubleChargedEGP: doubles * 500 };
}

بالعامية

الـ PSP failover هو الخطر. إضافة PSP تاني شكلها availability صافية، بس لو عملت failover على نتيجة مجهولة ممكن تخصم من العميل عند الاتنين. المحاكاة المتعلّم عليها فوق بتفترض 1.5% نتايج مجهولة، و40% منها اتخصمت فعلًا. القاعدة: اعمل failover للدفعات الجديدة اللي عمرها ما اتبعتت بس. الدفعة الـ in-doubt تفضل مع الـ PSP بتاعها لحد ما يرد.

إيه اللي بيتغير فعلًا عند 10 أضعاف (10 مليون في اليوم، 116 TPS متوسط و347 peak): مش الـ TPS، Postgres لسه يشيله. أول حاجة بتكسر هي صف الـ balance الواحد لو ضفته: كل capture لتاجر كبير بيقف في طابور على الـ row lock ده، فالسقف هو واحد على الـ commit latency. على الجهاز ده الصف الزيادة كلّف من 2 لـ 4 أضعاف في الـ throughput بعد التسخين، والـ commit هنا أقل من millisecond. على cloud disk بـ 3ms نفس الصف بيقف عند حوالي 330 write في الثانية. بعدها: 22 مليار صف ledger في السنة (partition بالشهر والأرشيف على object storage)، وjob الـ reconciliation يكبر عن وقته (partition باليوم وbatches لكل تاجر)، والـ rate limits بتاعة الـ PSP (token bucket قدام الـ outbox)، وموجات الـ webhooks (رد بسرعة ونفّذ من queue).

الـ interviewer بيدوّر على: الـ idempotency في الطبقتين (الـ API والـ PSP)، التعامل مع النتيجة المجهولة، ledger immutable، reconciliation، وstate machine متفروض في الـ DB. الـ red flags: "نعملها distributed transaction" (الـ PSP مبيدخلش في 2PC، راجع درس 34)، "نعمل retry 3 مرات" من غير key، فلوس بـ float، تخزين رقم الكارت، أو كلمة exactly-once من غير آلية.

الروتين بتاع الـ README: اكتب design doc صفحة واحدة بـ project/design-docs/0000-template.md، قارنه بالحل المرجعي (فصل الـ Payment System في Alex Xu vol. 2)، واكتب اللي فاتك. دي نفس طريقة درس 45.

فين هستخدمه في شغلي؟ لما حد في الفريق يقترح "نضيف PSP تاني عشان الـ availability"، اسأله: "الدفعات اللي نتيجتها مجهولة وقت العطل هنعمل فيها إيه؟". لو الإجابة مش واضحة، المقترح لسه مش جاهز. والغلطة الشائعة: تحسب الـ 10× على الـ TPS بس وتنسى الـ row lock على التاجر الكبير وحجم الـ ledger.
What the interviewer looks for Idempotency at both layers, a clear answer for unknown outcomes, an immutable ledger with an invariant you can query, reconciliation as a named component, and a state machine enforced in the database. Red flags: "we'll use a distributed transaction" (a PSP does not join your 2PC, see lesson 34), "retry three times" with no key, float money, storing card numbers, or saying exactly-once without naming the mechanism.

Cheat sheet · الخلاصة

  • 1M/day is about 12 TPS. Say it, then spend the time on correctness, not scale.
  • A timeout means unknown, never failed. Answer 202, keep the row in doubt.
  • Reserve the key, write the intent, call with the same key. Query before re-sending.
  • Querying alone misses a slow PSP. Only a key closes that window.
  • State changes are compare-and-swap: WHERE state = $expected, check the row count.
  • Webhooks: dedupe on event id, lock the row, apply only forward moves.
  • Ledger: append only, debits equal credits per currency, deferred trigger at COMMIT.
  • Reconcile daily with a FULL JOIN. Auto-fix only when both sides agree.
  • Outbox toward the PSP, HTTP outside the transaction, lease plus same key.
  • Tokenize so card numbers never reach you, and fail CI if a Luhn-valid number shows up in logs.
  • Fail over only fresh payments. In-doubt ones stay with their PSP.
  • At 10×: hot balance row, ledger size, recon window, PSP limits. Not raw TPS.
بالعامية
  • مليون في اليوم يعني حوالي 12 TPS. قولها وحط وقتك في الصح مش في الـ scale.
  • الـ timeout معناه مجهول مش فشل. رد 202 وسيب الصف in doubt.
  • احجز الـ key، اكتب النية، ابعت بنفس الـ key، واسأل قبل ما تعيد الإرسال.
  • السؤال لوحده مبيغطيش PSP بطيء، الـ key بس هو اللي بيقفل الفجوة دي.
  • تغيير الحالة compare-and-swap: WHERE state = $expected وبص على عدد الصفوف.
  • الـ webhooks: dedupe بالـ event id، اقفل الصف، ونفّذ الحركة لقدام بس.
  • الـ ledger: append only، والـ debits بتساوي الـ credits لكل عملة، وdeferred trigger عند الـ COMMIT.
  • اعمل reconcile كل يوم بـ FULL JOIN، والإصلاح الأوتوماتيك بس لما الطرفين متفقين.
  • outbox ناحية الـ PSP، والـ HTTP بره الـ transaction، بـ lease ونفس الـ key.
  • tokenization عشان أرقام الكروت متوصلكش، وخلّي الـ CI يفشل لو رقم بيعدي Luhn ظهر في الـ logs.
  • الـ failover للدفعات الجديدة بس، والـ in-doubt تفضل مع الـ PSP بتاعها.
  • عند 10 أضعاف: صف الـ balance، حجم الـ ledger، وقت الـ recon، وحدود الـ PSP، مش الـ TPS نفسه.
