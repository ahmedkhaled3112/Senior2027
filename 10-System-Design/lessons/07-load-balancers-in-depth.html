Why this matters · ليه ده مهم

English

The load balancer decides which backend does the work, so its mistakes are multiplied by every request. A wrong algorithm turned one slow instance into a 4× throughput loss in the runs below. A health check that queries the database turned a 3-second lock into a full outage. A rolling deploy without draining failed 43 of 1000 requests, and with draining it failed none. Interviewers ask about these because they separate people who have run production traffic from people who have only drawn a box labelled "LB".

The basics (what an LB is, the algorithms in a simulation, the keep-alive 502) are in section 01 · Load Balancers, Proxies & CDN. This lesson uses real Node backends and counts what breaks. Every LB here is a Node stand-in, labelled as such: the behaviour is the point, not the speed.

بالعامية

الـ load balancer هو اللي بيقرر مين يشتغل، فأي غلطة فيه بتتضرب في كل request. في التجارب تحت: algorithm غلط خلّى instance واحد بطيء يضيّع 4 أضعاف الـ throughput. و health check بيكلم الـ DB خلّى lock مدته 3 ثواني يبقى outage كامل. و rolling deploy من غير draining وقّع 43 من 1000 request، وبالـ draining صفر. الـ interviewers بيسألوا في الحاجات دي عشان هي اللي بتفرّق بين حد شغّل traffic حقيقي وحد رسم مربع مكتوب عليه "LB" وخلاص.

الأساسيات (يعني إيه LB، الـ algorithms في simulation، و 502 بتاعة الـ keep-alive) موجودة في درس section 01. هنا هنشغّل backends حقيقية بـ Node ونعدّ إيه اللي بيقع. وكل LB في الدرس ده stand-in مكتوب بـ Node ومتعلّم عليه كده: اللي يهمنا هو السلوك، مش السرعة.

Part 1 — L4 vs L7, measured 🟡 Intermediateالجزء 1 — الفرق بين L4 و L7 بالأرقام

English

Section 01, part 1 explains the idea. Here is the consequence people miss. An L4 balancer makes one decision per TCP connection and then moves bytes. It can see the 5-tuple and nothing else. An L7 balancer terminates the protocol, reads every request, and makes one decision per request, so it can route by path, header, cookie or method, terminate TLS, and retry.

That difference becomes an outage with long-lived multiplexed connections. HTTP/2 and gRPC put thousands of requests on one TCP connection. Through L4, every one of them lands on the backend chosen when the connection opened. The test below sends 1000 requests over a single HTTP/2 connection through both stand-ins: L4 sent all 1000 to one backend, and L7 split them 334/333/333.

The price of L7 is work per request: parsing, and usually TLS. In this run L7 took about 133 ms against about 102 ms for L4 (Node stand-ins on a loaded Windows machine, so read the ratio only). Real L4 can also be much cheaper than this, since it can run in the kernel or on a NIC, which a Node process can't show.

// تجربة: عميل HTTP/2 واحد بيبعت 1000 request، ومرة بيعدّي على L4 ومرة على L7.
// الاتنين هنا stand-ins مكتوبين بـ Node، مش HAProxy ولا ALB.
import http2 from "node:http2";
import net from "node:net";

type Backend = { name: string; port: number; hits: number; close(): void };

async function startBackend(name: string): Promise<Backend> {
  const b: Backend = { name, port: 0, hits: 0, close() {} };
  const server = http2.createServer((req, res) => {
    b.hits++;
    res.end(JSON.stringify({ servedBy: name, path: req.url }));
  });
  await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));
  b.port = (server.address() as net.AddressInfo).port;
  b.close = () => server.close();
  return b;
}

// الـ L4: بيختار backend مرة واحدة لكل TCP connection، وبعدها بينقل bytes وبس
function startL4(backends: Backend[]) {
  let next = 0;
  const seen = { connections: 0, firstBytes: "" };
  const server = net.createServer((client) => {
    seen.connections++;
    const target = backends[next++ % backends.length]!;
    const upstream = net.connect(target.port, "127.0.0.1");
    client.once("data", (d) => (seen.firstBytes = (d as Buffer).subarray(0, 14).toString("latin1")));
    client.pipe(upstream).pipe(client);
    client.on("error", () => upstream.destroy());
    upstream.on("error", () => client.destroy());
  });
  return { server, seen };
}

// الـ L7: بيفك الـ HTTP/2 ويقرأ كل stream، فبيختار backend لكل request لوحده
function startL7(pools: { orders: Backend[]; payments: Backend[]; canary: Backend[] }) {
  let next = 0;
  const sessions = new Map<Backend, http2.ClientHttp2Session>();
  const sessionFor = (b: Backend) => {
    if (!sessions.has(b)) sessions.set(b, http2.connect(`http://127.0.0.1:${b.port}`));
    return sessions.get(b)!;
  };
  const server = http2.createServer((req, res) => {
    // القرار ده مستحيل على L4: الـ path والـ header جوه الـ bytes
    const pool = req.url.startsWith("/payments/") ? pools.payments
      : req.headers["x-canary"] === "1" ? pools.canary
      : pools.orders;
    const target = pool[next++ % pool.length]!;
    const up = sessionFor(target).request({ ":method": req.method, ":path": req.url });
    up.on("response", (h) => res.writeHead(Number(h[":status"])));
    up.pipe(res);
    up.on("error", () => res.destroy());
  });
  const close = () => { for (const s of sessions.values()) s.close(); server.close(); };
  return { server, close };
}

const listen = (s: net.Server) =>
  new Promise<number>((r) => s.listen(0, "127.0.0.1", () => r((s.address() as net.AddressInfo).port)));

// بنبعت كل الـ requests على HTTP/2 connection واحدة (multiplexing)
async function sendAll(port: number, n: number, path = (i: number) => `/orders/${i}`, headers = {}) {
  const session = http2.connect(`http://127.0.0.1:${port}`);
  const one = (i: number) => new Promise<void>((resolve, reject) => {
    const r = session.request({ ":path": path(i), ...headers });
    r.on("error", reject);
    r.resume();
    r.on("end", resolve);
    r.end();
  });
  const t0 = performance.now();
  for (let i = 0; i < n; i += 50) {
    await Promise.all(Array.from({ length: Math.min(50, n - i) }, (_, k) => one(i + k)));
  }
  session.close();
  return Math.round(performance.now() - t0);
}

بالعامية

الـ L4 بياخد قرار واحد لما الـ TCP connection تتفتح، وبعدها بينقل bytes وخلاص، وكل اللي يعرفه الـ 5-tuple. الـ L7 بيفك الـ protocol ويقرا كل request ويقرر لكل واحد لوحده، فيقدر يوجّه بالـ path أو الـ header أو الـ cookie أو الـ method، ويفك الـ TLS، ويعمل retry.

الفرق ده بيبقى outage مع الـ connections الطويلة: HTTP/2 و gRPC بيحطوا آلاف الـ requests على TCP connection واحدة. على L4 كلهم بيروحوا للـ backend اللي اتحدد وقت فتح الـ connection. في التجربة: 1000 request على connection واحدة، الـ L4 بعتهم كلهم لـ backend واحد، والـ L7 قسمهم 334/333/333.

تمن الـ L7 إنه بيشتغل على كل request: parsing وغالبًا TLS. هنا أخد ≈133ms مقابل ≈102ms للـ L4، وده Node على Windows عليه ضغط، فبص على النسبة بس. والـ L4 الحقيقي ممكن يبقى أرخص بكتير لأنه ممكن يشتغل في الـ kernel أو على الـ NIC، وده Node مايقدرش يوريه.

فين هستخدمه في شغلي؟ لو عندك خدمة بتنادي خدمة تانية بـ gRPC من ورا NLB (يعني L4)، هتلاقي pod واحد واكل الحمل كله وباقي الـ pods فاضيين، حتى لو الـ dashboard بيقول "4 instances". الحل: L7 proxy قدّام الـ gRPC، أو client-side balancing، أو maxConnectionAge عشان الـ connections تتجدد. نفس المشكلة في Postgres من ورا NLB: الـ connections الجديدة بس هي اللي بتتوزع.
Interview question "We scaled our gRPC service from 3 to 6 pods behind an NLB and load didn't drop on the old pods. Why?" → gRPC multiplexes on long-lived connections, and an L4 balancer chooses per connection. Existing connections stay where they are. Fix with an L7 proxy, client-side balancing, or a maximum connection age so clients reconnect.
السؤال: "كبّرنا خدمة gRPC من 3 لـ 6 pods ورا NLB والحمل على القديمة مانزلش. ليه؟" ← الإجابة: الـ gRPC بيعمل multiplexing على connections طويلة، والـ L4 بيختار لكل connection، فالـ connections القديمة بتفضل مكانها. الحل L7 proxy، أو client-side balancing، أو حد أقصى لعمر الـ connection عشان العملاء يعملوا reconnect.

Part 2 — Algorithms under a slow backend 🟡 Intermediateالجزء 2 — الـ algorithms مع backend بطيء

English

The simulation is in section 01, part 2. Here the backends are real: four Node servers, one of them 10× slower (requested 20 ms and 200 ms, and setTimeout on Windows really gave ≈28 ms and ≈206 ms). Each has 8 slots, like a small connection pool, so excess work queues. The load is 40 keep-alive connections from autocannon.

  • Round robin gave the slow backend the same share. Under a closed loop every connection eventually waits on it (peak in-flight 39 of 40), so the whole fleet runs at the speed of the slowest node: ≈180 rps against ≈800 for the adaptive algorithms.
  • Weighted had the best p99 (≈217 ms), but only because I told it the truth (10:10:10:1). A backend that becomes slow unexpectedly doesn't update its weight.
  • Least connections needs no configuration. The slow node holds its requests longer, so its count stays high and it naturally receives fewer: ≈806 rps.
  • Least response time, taken literally, is the trap. Every new request goes to the backend with the lowest moving average, so all 40 land on one backend until its average rises, and then all 40 move to the next. That is the herd effect: peak in-flight 40 on each fast backend, p50 ≈124 ms, ≈350 rps, and the slow node got 0 requests, so its bad average never changes.
  • Power of two choices samples two backends at random and takes the less loaded. It nearly matched least connections (≈803 rps, peak in-flight 12) with no global scan. The randomness is what breaks the herd: two balancers with stale counts won't all choose the same "best" backend. Envoy's LEAST_REQUEST uses this (P2C) when host weights are equal.
// الـ stand-in بتاع الـ L7 load balancer: مكتوب بـ Node وبيتغيّر فيه الـ picker بس.
import http from "node:http";
import type { AddressInfo } from "node:net";

export type Backend = {
  id: string; port: number; weight: number;
  inflight: number; peak: number; count: number; ewma: number;
};
export type Picker = (bs: Backend[]) => Backend;

const random = (n: number) => Math.floor(Math.random() * n);
const lowestBy = (bs: Backend[], f: (b: Backend) => number) => {
  let best = [bs[0]!];
  for (const b of bs.slice(1)) {
    if (f(b) < f(best[0]!)) best = [b];
    else if (f(b) === f(best[0]!)) best.push(b);
  }
  // لو فيه تعادل بنختار عشوائي، عشان مفيش backend يتظلم بسبب ترتيبه
  return best[random(best.length)]!;
};

export const roundRobin = (): Picker => { let i = 0; return (bs) => bs[i++ % bs.length]!; };

// ده الـ smooth weighted round robin بتاع nginx: بيوزّع الـ weights من غير دفعات متتالية
export const weightedRoundRobin = (): Picker => {
  const current = new Map<string, number>();
  return (bs) => {
    const total = bs.reduce((s, b) => s + b.weight, 0);
    let best = bs[0]!;
    for (const b of bs) {
      const c = (current.get(b.id) ?? 0) + b.weight;
      current.set(b.id, c);
      if (c > (current.get(best.id) ?? 0)) best = b;
    }
    current.set(best.id, current.get(best.id)! - total);
    return best;
  };
};

export const leastConnections = (): Picker => (bs) => lowestBy(bs, (b) => b.inflight);

// أقل response time بس: مبيبصش على الـ inflight، وده سبب الـ herd
export const leastResponseTime = (): Picker => (bs) => lowestBy(bs, (b) => b.ewma);

// اختيار عشوائي لاتنين، وبعدين الأقل inflight منهم (ده LEAST_REQUEST في Envoy)
export const powerOfTwo = (): Picker => (bs) => {
  const a = random(bs.length);
  let b = random(bs.length - 1);
  if (b >= a) b++;
  return bs[a]!.inflight <= bs[b]!.inflight ? bs[a]! : bs[b]!;
};

export function startLb(backends: Backend[], pick: Picker) {
  const agent = new http.Agent({ keepAlive: true });
  const server = http.createServer((req, res) => {
    const b = pick(backends);
    b.count++;
    b.inflight++;
    b.peak = Math.max(b.peak, b.inflight);
    const t0 = performance.now();
    const up = http.request(
      { port: b.port, host: "127.0.0.1", path: req.url, method: req.method, agent },
      (r) => {
        res.writeHead(r.statusCode ?? 502, r.headers);
        r.pipe(res);
        r.on("end", () => {
          b.inflight--;
          const rtt = performance.now() - t0;
          b.ewma = b.ewma === 0 ? rtt : 0.2 * rtt + 0.8 * b.ewma;
        });
      },
    );
    up.on("error", () => { b.inflight--; res.statusCode = 502; res.end("bad gateway"); });
    req.pipe(up);
  });
  return new Promise<{ port: number; close(): void }>((resolve) => {
    server.listen(0, "127.0.0.1", () =>
      resolve({
        port: (server.address() as AddressInfo).port,
        close() { agent.destroy(); server.close(); server.closeAllConnections(); },
      }));
  });
}

import http from "node:http";
import type { AddressInfo } from "node:net";
import autocannon from "autocannon";
import {
  type Backend, type Picker, startLb, roundRobin, weightedRoundRobin,
  leastConnections, leastResponseTime, powerOfTwo,
} from "./lb.ts";

const SLOTS = 8;
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

async function startBackend(id: string, delayMs: number, weight: number) {
  let busy = 0;
  const waiters: Array<() => void> = [];
  const samples: number[] = [];
  const server = http.createServer(async (_req, res) => {
    if (busy >= SLOTS) await new Promise<void>((r) => waiters.push(r));
    busy++;
    const t0 = performance.now();
    await sleep(delayMs);
    samples.push(performance.now() - t0);
    busy--;
    waiters.shift()?.();
    res.end(JSON.stringify({ id }));
  });
  await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));
  const b: Backend = {
    id, port: (server.address() as AddressInfo).port, weight,
    inflight: 0, peak: 0, count: 0, ewma: 0,
  };
  const realDelay = () => samples.reduce((s, x) => s + x, 0) / (samples.length || 1);
  return { b, server, realDelay };
}

const nodes = await Promise.all([
  startBackend("a", 20, 10), startBackend("b", 20, 10),
  startBackend("c", 20, 10), startBackend("slow", 200, 1),
]);

  const t0 = performance.now();
  await (await fetch(`http://127.0.0.1:${port}/probe`)).text();
  return performance.now() - t0;

English

IP hash and consistent hashing serve a different goal: affinity, keeping a client on the same backend (a local cache, a per-tenant shard). Plain hash(ip) % N reshuffles almost everyone when N changes: going from 4 to 5 backends moved 80.1% of 100,000 clients. A consistent hash ring moves only the share that belongs to the new node, about 1/5. With 150 virtual nodes per backend it moved 18.2% and the load stayed within 18–21% per backend. With 1 virtual node per backend it moved 34.1% and the load ranged from 11.6% to 34.1%, which is why vnodes exist. The mechanism in depth comes in lesson 13.

// حاسبة: لو زودنا backend خامس، كام client هيروح لـ backend تاني؟
import { createHash } from "node:crypto";

const hash = (s: string) => createHash("md5").update(s).digest().readUInt32BE(0);
const clients = Array.from({ length: 100_000 }, (_, i) => `10.${(i >> 16) & 255}.${(i >> 8) & 255}.${i & 255}`);

function ipHash(nodes: string[]) {
  return (client: string) => nodes[hash(client) % nodes.length]!;
}

function consistentRing(nodes: string[], vnodes: number) {
  const ring = nodes
    .flatMap((n) => Array.from({ length: vnodes }, (_, i) => ({ at: hash(`${n}#${i}`), n })))
    .sort((x, y) => x.at - y.at);
  return (client: string) => {
    const h = hash(client);
    let lo = 0, hi = ring.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (ring[mid]!.at < h) lo = mid + 1; else hi = mid;
    }
    return ring[lo % ring.length]!.n;
  };
}

function report(name: string, before: (c: string) => string, after: (c: string) => string) {
  let moved = 0;
  const load = new Map<string, number>();
  for (const c of clients) {
    const a = after(c);
    if (before(c) !== a) moved++;
    load.set(a, (load.get(a) ?? 0) + 1);
  }
  const shares = [...load.values()].map((v) => (v / 1000).toFixed(1) + "%").join(" ");
  console.log(`${name.padEnd(26)} moved ${(moved / 1000).toFixed(1)}% | load after: ${shares}`);
}

  • Round robin: البطيء بياخد نفس النصيب، وفي closed loop كل الـ connections في الآخر بتستناه (peak 39 من 40)، فالـ fleet كله بيمشي بسرعة أبطأ node: ≈180 rps مقابل ≈800 للـ algorithms اللي بتتكيف.
  • Weighted: أحسن p99 (≈217ms)، بس عشان إحنا قلنا له الحقيقة (10:10:10:1). لو backend بقى بطيء فجأة، الـ weight مش هيتغير لوحده.
  • Least connections: من غير أي config. البطيء ماسك الـ requests وقت أطول، فعدده بيفضل عالي وبياخد أقل لوحده: ≈806 rps.
  • Least response time لو طبقته حرفيًا هو الفخ: كل request جديد بيروح لأقل متوسط، فالـ 40 كلهم بيروحوا لواحد لحد ما متوسطه يعلى، وبعدين الـ 40 ينقلوا للي بعده. ده الـ herd effect: peak 40 على كل backend سريع، و p50 ≈124ms، و ≈350 rps. والبطيء ماخدش ولا request، فالمتوسط بتاعه عمره ما هيتغير.
  • Power of two choices: بياخد اتنين عشوائي ويختار الأقل حملًا. قرب جدًا من least connections (≈803 rps و peak 12) من غير ما يلف على كل الـ backends. العشوائية هي اللي بتكسر الـ herd: لو عندك كذا LB بأرقام قديمة، مش هيختاروا كلهم نفس "الأحسن". الـ LEAST_REQUEST في Envoy بيستخدم ده (P2C) لما الـ weights متساوية.

IP hash و consistent hashing هدفهم حاجة تانية: الـ affinity، يعني client يفضل على نفس الـ backend (cache محلي أو shard لكل tenant). الـ hash(ip) % N بيبعتر تقريبًا الكل لما N يتغير: من 4 لـ 5 حرك 80.1% من 100 ألف client. الـ ring بيحرك نصيب الـ node الجديد بس، حوالي الخُمس: بـ 150 vnode حرك 18.2% والحمل بين 18% و 21%، وبـ vnode واحد حرك 34.1% والحمل من 11.6% لـ 34.1%، وده سبب وجود الـ vnodes. التفاصيل في درس 13.

فين هستخدمه في شغلي؟ API عندك فيه endpoint تقيل (report بياخد 2 ثانية) و endpoints خفيفة. على ALB الـ default هو round robin، فالـ instance اللي مسك reports كتير بيبقى زحمة والباقي فاضي. غيّر الـ algorithm لـ least_outstanding_requests. ولو بتعمل cache محلي لكل tenant، استخدم consistent hashing عشان الـ deploy أو الـ scale-out مايمسحش الـ cache كله. والغلطة الشائعة: hash % N مع in-memory cache، فأول scale-out الـ DB تاخد الضربة كلها.
Trade-off: least connections vs power of two Least connections needs a current count for every backend, which is easy in a single balancer and hard across a fleet of balancers. Power of two needs only two samples, so it scales out, and it's almost as good. Don't reach for least response time unless the implementation combines latency with in-flight count and keeps probing nodes it has stopped using.
الـ least connections محتاج عدد محدّث لكل backend، وده سهل في LB واحد وصعب في fleet من الـ LBs. الـ power of two محتاج عينتين بس، فبيكبر بسهولة وقريب جدًا في الجودة. ماتستخدمش least response time إلا لو الـ implementation بيجمع الـ latency مع الـ inflight وبيفضل يجرّب الـ nodes اللي بطّل يبعتلها.

Part 3 — Health checks that cause outages 🟡 Intermediateالجزء 3 — الـ health checks اللي بتعمل outage

English

Active checks probe each backend on a timer. Passive checks (outlier detection) watch real responses. Detection time is interval × failure threshold, plus up to one timeout. Recovery is interval × success threshold. On AWS ALB the documented defaults are 30 s and 2, so about 60 s to eject, and 30 s and 5, so about 150 s to return.

The dangerous pattern is a deep /health that queries the database. One dependency is now tied to the liveness of every backend, so one blip fails them all at the same moment. The run below is real: 4 backends, a throwaway Postgres 18, and a migration-style LOCK TABLE orders IN ACCESS EXCLUSIVE MODE held for 3 seconds. 80% of traffic is catalog reads from memory that never touch the database.

  • A) Deep check: the LB ejected all 4 at t=2.8 s and brought the first back at t=5.5 s. 462 of 1440 requests failed (435 were 503 "no healthy upstream"), including the catalog reads that had nothing to do with Postgres.
  • B) Deep check plus a panic threshold: same ejections, but below 50% healthy the LB ignores health and keeps routing. Only 78 failed, all of them requests that really needed the database.
  • C) Shallow check: /health doesn't touch the database, so no backend was ejected. 74 failed, again only the requests that needed it.

Passive detection solves the opposite problem: a backend whose process is alive and passes a shallow check but fails every real request. In run D one of four returned 500s for the whole test, and 120 of 480 requests failed (25%). With passive ejection (5 consecutive 5xx, the Envoy default, and a cap so at most half the pool is ejected) only 5 failed.

Real products agree on the safeguards. Envoy's panic threshold defaults to 50%, and its outlier detection defaults to 5 consecutive 5xx, 30 s base ejection and a 10% max ejection. AWS ALB fails open: if every target is unhealthy it routes to all of them anyway. Don't let that make you comfortable, though: a deep check that fails on only some backends still ejects those and piles their load on the rest.

// لازم نتأكد إن الـ port بتاع الـ Postgres المؤقت مش الـ default قبل أي connection
function safePort(port: unknown): number {
  const n = Number(port);
  if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port ${String(port)}`);
  }
  return n;
}

function startBackend(dbPort: number, mode: Mode, broken = false) {
  const pool = new pg.Pool({
    host: "127.0.0.1", port: safePort(dbPort), user: "app", database: "postgres",
    max: 4, connectionTimeoutMillis: 300, statement_timeout: 800,
  });
  pool.on("error", () => {});
  const server = http.createServer(async (req, res) => {
    if (req.url === "/health") {
      if (mode === "shallow") return void res.end("ok");
      // الغلطة: الـ liveness بتاع الـ LB بقى معتمد على الـ DB
      try { await pool.query("select 1 from orders limit 1"); res.end("ok"); }
      catch { res.statusCode = 503; res.end("db down"); }
      return;
    }
    if (broken) { res.statusCode = 500; return void res.end("broken"); }
    // الـ catalog من memory: مش محتاج الـ DB خالص
    if (req.url?.startsWith("/catalog/")) return void res.end('{"sku":"A1","price":999}');
    try { await pool.query("select id from orders where id = $1", [1]); res.end("ok"); }
    catch { res.statusCode = 504; res.end("db timeout"); }
  });
  return new Promise<{ port: number; stop(): Promise<void> }>((resolve) => {
    server.listen(0, "127.0.0.1", () => resolve({
      port: (server.address() as AddressInfo).port,
      async stop() { server.closeAllConnections(); server.close(); await pool.end(); },

}

type Opts = { panic?: boolean; passive?: boolean };
type Node = { port: number; healthy: boolean; fails: number; oks: number; bad5xx: number; ejectedUntil: number };

function startLb(backends: { port: number }[], opts: Opts, log: string[]) {
  const nodes: Node[] = backends.map((b) => ({ port: b.port, healthy: true, fails: 0, oks: 0, bad5xx: 0, ejectedUntil: 0 }));
  const t0 = performance.now();
  const stamp = () => ((performance.now() - t0) / 1000).toFixed(1);
  const check = async (n: Node) => {
    const ok = await fetch(`http://127.0.0.1:${n.port}/health`, { signal: AbortSignal.timeout(400) })
      .then((r) => r.ok, () => false);
    const before = nodes.some((x) => x.healthy);
    if (ok) { n.fails = 0; if (++n.oks >= 2) n.healthy = true; }
    else { n.oks = 0; if (++n.fails >= 2) n.healthy = false; }
    const after = nodes.some((x) => x.healthy);
    if (before && !after) log.push(`all backends ejected at t=${stamp()}s`);
    if (!before && after) log.push(`first backend back at t=${stamp()}s`);
  };
  // كل 500ms، و 2 فشل يشيله و 2 نجاح يرجّعه: وقت الاكتشاف ⁦≈ 500 × 2⁩
  const timer = setInterval(() => nodes.forEach((n) => void check(n)), 500);
  let rr = 0;
  const agent = new http.Agent({ keepAlive: true });
  const server = http.createServer((req, res) => {
    const now = performance.now();
    let pool = nodes.filter((n) => n.healthy);
    // الـ panic: لو أقل من 50% healthy، تجاهل الـ checks وابعت للكل
    if (opts.panic && pool.length / nodes.length < 0.5) pool = nodes;
    if (opts.passive) {
      const live = pool.filter((n) => n.ejectedUntil <= now);
      // حد أقصى للـ ejection: مانشيلش أكتر من نص الـ pool
      if (live.length >= nodes.length / 2) pool = live;
    }
    if (pool.length === 0) { res.statusCode = 503; return void res.end("no healthy upstream"); }
    const n = pool[rr++ % pool.length]!;
    const up = http.request({ port: n.port, host: "127.0.0.1", path: req.url, agent }, (r) => {
      if (r.statusCode === 500) {
        if (++n.bad5xx >= 5) { n.ejectedUntil = performance.now() + 30_000; n.bad5xx = 0; }
      } else n.bad5xx = 0;
      res.writeHead(r.statusCode ?? 502);
      r.pipe(res);
    });
    up.on("error", () => { res.statusCode = 502; res.end(); });
    up.end();
  });
  return new Promise<{ port: number; stop(): void }>((resolve) => {
    server.listen(0, "127.0.0.1", () => resolve({
      port: (server.address() as AddressInfo).port,
      stop() { clearInterval(timer); agent.destroy(); server.closeAllConnections(); server.close(); },
    }));
  });
}

// حمل open-loop: حوالي 200 request في الثانية، 80% catalog و 20% orders
async function drive(port: number, seconds: number, catalogOnly = false) {
  const perSecond: Record<string, number>[] = Array.from({ length: seconds + 2 }, () => ({}));
  const t0 = performance.now();
  const pending: Promise<void>[] = [];
  while (performance.now() - t0 < seconds * 1000) {
    for (let i = 0; i < 5; i++) {
      const url = catalogOnly || i > 0 ? "/catalog/1" : "/orders/1";
      pending.push(fetch(`http://127.0.0.1:${port}${url}`, { signal: AbortSignal.timeout(2000) })
        .then(async (r) => { await r.arrayBuffer(); return String(r.status); }, () => "timeout")
        .then((s) => {
          const b = perSecond[Math.floor((performance.now() - t0) / 1000)]!;
          b[s] = (b[s] ?? 0) + 1;
        }));
    }
    await sleep(25);
  }
  await Promise.all(pending);
  return perSecond;
}

function summarize(name: string, perSecond: Record<string, number>[], log: string[]) {
  const total: Record<string, number> = {};
  for (const b of perSecond) for (const [k, v] of Object.entries(b)) total[k] = (total[k] ?? 0) + v;
  const failsPerSec = perSecond.slice(0, -1).map((b) =>
    Object.entries(b).filter(([k]) => k !== "200").reduce((s, [, v]) => s + v, 0));
  console.log(`${name}\n  totals ${JSON.stringify(total)}\n  failed per second ${failsPerSec.join(" ")}`);
  if (log.length) console.log(`  ${log.join(", ")}`);
}

Part 4 — Connection draining 🟡 Intermediateالجزء 4 — الـ connection draining

English

The keep-alive 502 is covered in section 01, part 3, and the full shutdown sequence in Node lesson 24. This part measures the deploy. A rolling restart of 3 backends under 1000 requests, with real child processes:

  • Without draining the process exits while the LB still routes to it. 43 requests failed: 18 ECONNRESET (in flight when it died) and 25 ECONNREFUSED (routed to a port with nobody listening).
  • With draining: start the replacement first, stop routing to the old one, wait for its in-flight count to reach zero, then server.close() plus closeIdleConnections(). 0 of 1000 failed, and the run took about the same time.

Windows note: a child's SIGTERM ends it immediately with no handler, so these runs trigger shutdown over IPC with child.send("shutdown"). On Linux the same code would run from a SIGTERM handler. The trade-off is drain time against deploy speed. With 40 instances and one at a time, a 30 s drain makes a deploy about 27 minutes, a 5 s drain about 10 minutes, and batches of 4 with a 30 s drain about 7 minutes. The batch costs capacity: while 4 of 40 restart you have 90% of your capacity, so it must survive that. On ALB the deregistration delay defaults to 300 s. It ends early once a target has no in-flight requests and no active connections, so treat it as a ceiling and set it just above your longest request.

    |
  stop       LB marks old as draining (no new requests)

async function spawnBackend(): Promise<Slot> {

function startLb(slots: Slot[]) {
  let rr = 0;
  const errors: Record<string, number> = {};
  const agent = new http.Agent({ keepAlive: true });
  const server = http.createServer((req, res) => {
    const live = slots.filter((s) => !s.draining);
    const s = live[rr++ % live.length]!;
    s.inflight++;
    const fail = (e: NodeJS.ErrnoException) => {
      s.inflight--;
      errors[e.code ?? "ERR"] = (errors[e.code ?? "ERR"] ?? 0) + 1;
      if (!res.headersSent) res.statusCode = 502;
      res.end("bad gateway");
    };
    const up = http.request({ port: s.port, host: "127.0.0.1", path: req.url, agent }, (r) => {
      res.writeHead(r.statusCode ?? 502);
      r.pipe(res);
      r.on("end", () => s.inflight--);
    });
    up.on("error", fail);
    up.end();
  });
  return { server, errors, agent };
}

async function drive(port: number, total: number) {
  let sent = 0, ok = 0, failed = 0;
  const worker = async () => {
    while (sent < total) {
      sent++;
      const status = await fetch(`http://127.0.0.1:${port}/orders/${sent}`)
        .then(async (r) => { await r.arrayBuffer(); return r.status; }, () => 0);
      if (status === 200) ok++; else failed++;
    }
  };
  await Promise.all(Array.from({ length: 10 }, worker));
  return { ok, failed };
}

async function rollingRestart(slots: Slot[], drain: boolean) {
  for (let i = 0; i < slots.length; i++) {
    await sleep(800);
    const old = slots[i]!;
    if (drain) {
      // (1) شغّل البديل الأول (maxSurge = 1)، (2) وقّف التوجيه للقديم، (3) استنى، (4) اقفله
      const fresh = await spawnBackend();
      slots.push(fresh);
      old.draining = true;
      const deadline = performance.now() + 5000;
      while (old.inflight > 0 && performance.now() < deadline) await sleep(5);
      old.child.send("shutdown");
      await once(old.child, "exit");
      slots.splice(slots.indexOf(old), 1, fresh);
      slots.pop();
    } else {
      // من غير draining: الـ LB لسه شايف الـ backend ده والـ process بيموت فجأة
      old.child.send("die-now");
      await once(old.child, "exit");
      const fresh = await spawnBackend();
      slots[i] = fresh;
    }
  }
}

Part 5 — Sticky sessions 🟡 Intermediateالجزء 5 — الـ sticky sessions

English

Sticky sessions keep a client on one backend, usually with a cookie set by the balancer. They exist because a backend holds state in memory. Two costs follow, and both are measured here with 3 backends, 90 users and one heavy tenant making 1800 requests:

  • Lost sessions: when b2 died, its 30 users of 90 got 401 on the next request, because their sessions lived in that process.
  • Imbalance: the load balancer can't move a pinned client, so the heavy tenant's backend took 2130 requests against 330 and 330 (max/mean 2.29).

With sessions in Redis and no stickiness, the same run split 930/930/930 (max/mean 1.00) and lost 0 of 90 when b2 died. Every backend can now serve every user, so scale-out and deploys become non-events.

When there's no alternative: WebSockets. The connection itself pins the client, and on AWS ALB WebSocket connections are inherently sticky. Keep your session state external anyway, so a reconnect can land anywhere. See Node lesson 37, part 7 for balancing and adapters. The new problem is reconnection: a simulated rolling deploy with 100,000 sockets on 20 instances (assuming 2 ms of CPU per reconnect, so 10,000 per second in total). If they all reconnect at once with no jitter, 450,000 handshakes are rejected. Exponential backoff without jitter doesn't help: the retries stay synchronized and the last client is back only after 303 s. Spreading the first attempt over 30 s plus full jitter gave a peak of 3420 per second, zero rejections, and everyone back in 30 s. During a rolling restart, sockets that reconnect anywhere get moved 1.70 times on average, because they land on instances about to restart. Steering reconnects to instances that have already restarted brought that down to 1.05.

// مولّد أرقام بـ seed ثابت عشان الأرقام تطلع زي بعضها كل مرة
function rng(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

type Policy = { name: string; first(r: () => number): number; retry(attempt: number, r: () => number): number };

function simulate(p: Policy) {
  const r = rng(42);
  const arrivals = new Map<number, number[]>();
  const add = (t: number, attempt: number) => {
    const s = Math.floor(t);
    (arrivals.get(s) ?? arrivals.set(s, []).get(s)!).push(attempt);
  };
  for (let i = 0; i < SOCKETS; i++) add(p.first(r), 1);
  let connected = 0, rejected = 0, peak = 0, last = 0;
  for (let t = 0; connected < SOCKETS && t < 3600; t++) {
    const now = arrivals.get(t) ?? [];
    peak = Math.max(peak, now.length);
    const admitted = Math.min(now.length, CAPACITY);
    connected += admitted;
    if (admitted > 0) last = t;
    for (const attempt of now.slice(admitted)) {
      rejected++;
      add(t + Math.max(1, p.retry(attempt, r)), attempt + 1);
    }
    arrivals.delete(t);
  }
  console.log(`${p.name.padEnd(36)} peak/s=${String(peak).padStart(6)} rejected=${String(rejected).padStart(7)} all back after ${last + 1}s`);
}

function rollingBounces(smart: boolean) {
  const r = rng(7);
  const home = Int32Array.from({ length: SOCKETS }, () => Math.floor(r() * INSTANCES));
  let moves = 0;
  for (let restarting = 0; restarting < INSTANCES; restarting++) {
    for (let s = 0; s < SOCKETS; s++) {
      if (home[s] !== restarting) continue;
      moves++;
      if (smart && restarting + 1 < INSTANCES) {
        // بنوجّه الـ reconnect لـ instance اتعملها restart خلاص، لو فيه
        home[s] = restarting === 0 ? 1 + Math.floor(r() * (INSTANCES - 1)) : Math.floor(r() * restarting);
      } else {
        let n = Math.floor(r() * (INSTANCES - 1));
        if (n >= restarting) n++;
        home[s] = n;
      }
    }
  }
  console.log(`rolling deploy, ${smart ? "reconnect to restarted instances" : "reconnect anywhere"}: ${moves} reconnects, ${(moves / SOCKETS).toFixed(2)} per socket`);
}

Part 6 — The LB as a failure point 🟡 Intermediateالجزء 6 — الـ LB نفسه ممكن يقع

English

A load balancer that removes single points of failure can be one. The three standard patterns for making it redundant:

  • Active-passive with a virtual IP (VIP): two LBs share an IP through VRRP (keepalived). The passive one takes the IP if heartbeats stop. Failover takes seconds, existing connections usually break unless state is synced, and half your hardware sits idle.
  • ECMP: the routers spread flows over several active LBs by hashing the 5-tuple. All capacity is used. But if plain modulo hashing is in use, losing 1 of 4 LBs moves 75.1% of flows (calculated below), and those connections break. Resilient hashing moves only the 25.0% that were on the dead LB.
  • Managed LB (ALB, NLB, GCLB): the provider runs the redundancy. You still own the configuration, and there are limits you need to know.

Three limits show up in production. Ephemeral ports: an LB connecting to one backend IP and port can use one source port per connection on each of its source IPs. Linux's default range of 32768–60999 is 28,232 ports, and the side that closes first holds the pair in TIME_WAIT for 60 s on Linux. If that side is the LB, you get about 470 new connections per second per backend, or about 1075 even if you widened the range to the 64,512-port maximum. Without keep-alive every request costs a port: the run below used 2000 distinct source ports for 2000 requests, and with keep-alive only 20. Max connections: server.maxConnections = 2 dropped 3 of 5 clients at once, and every LB has an equivalent limit. Idle timeouts: Node's keepAliveTimeout defaults to 5 s and ALB's idle timeout to 60 s. AWS recommends making the application's idle timeout larger than the LB's, because otherwise the LB can send a request on a connection the application just closed and return a 502. Set keepAliveTimeout above the LB's value, and keep headersTimeout above that as a common safe default.

الـ LB اللي بيشيل الـ single points of failure ممكن يبقى هو نفسه واحد. فيه 3 طرق معروفة للـ redundancy:

  • Active-passive بـ virtual IP (VIP): اتنين LB بيتشاركوا IP عن طريق VRRP (keepalived)، والـ passive بياخد الـ IP لو الـ heartbeats وقفت. الـ failover بياخد ثواني، والـ connections الموجودة غالبًا بتقع إلا لو الـ state متزامن، ونص الـ hardware قاعد فاضي.
  • ECMP: الـ routers بتوزع الـ flows على كذا LB شغالين بالـ hash على الـ 5-tuple، فكل الـ capacity مستخدمة. بس مع modulo عادي، لو واحد من 4 وقع، 75.1% من الـ flows بتتحرك (محسوبة تحت) والـ connections دي بتقع. الـ resilient hashing بيحرك الـ 25.0% اللي كانوا على الـ LB الميت بس.
  • Managed LB (ALB و NLB و GCLB): الـ provider بيشغّل الـ redundancy، وإنت لسه مسؤول عن الـ config، وفيه حدود لازم تعرفها.

3 حدود بتظهر في الـ production. الـ ephemeral ports: الـ LB لما يكلم backend على IP و port معين، بيستخدم source port واحد لكل connection على كل source IP عنده. الـ default في Linux من 32768 لـ 60999، يعني 28,232 port، والطرف اللي بيقفل الأول بيمسك الـ pair في TIME_WAIT لمدة 60s على Linux. لو الطرف ده هو الـ LB، هتاخد حوالي 470 connection جديدة في الثانية لكل backend، أو حوالي 1075 حتى لو وسّعت الـ range لأقصى 64,512 port. ومن غير keep-alive كل request بياخد port: التجربة استهلكت 2000 source port مختلف لـ 2000 request، وبالـ keep-alive 20 بس. الـ max connections: server.maxConnections = 2 قفل 3 من 5 عملاء فورًا، وكل LB عنده حد زي ده. الـ idle timeouts: الـ keepAliveTimeout في Node الـ default بتاعه 5s، والـ idle timeout في ALB الـ default بتاعه 60s. و AWS بتنصح إن الـ idle timeout بتاع الـ application يكون أكبر من بتاع الـ LB، لأن غير كده الـ LB ممكن يبعت request على connection الـ app لسه قافلها ويرجع 502. خلي keepAliveTimeout أكبر من قيمة الـ LB، وخلي headersTimeout أكبر منه كـ default آمن شائع.

فين هستخدمه في شغلي؟ لو شفت في الـ logs EADDRNOTAVAIL أو 502 متفرقة تحت الضغط، أول حاجة تتأكد إن الـ keep-alive شغال بين الـ LB والـ backends (في nginx لازم keepalive و proxy_http_version 1.1). وفي كل service Node ورا ALB حط server.keepAliveTimeout = 65_000 و server.headersTimeout = 66_000. والغلطة الشائعة: تسيب الـ default 5s ورا ALB فتشوف 502 متفرقة مالهاش سبب واضح.

Solution · الحل 
// الفكرة: احسب وزن تدريجي من عمر الـ backend وطبّقه قبل الاختيار
const weightOf = (joinedAt: number, now: number, windowMs = 5000) =>
  Math.min(1, Math.max(0.1, (now - joinedAt) / windowMs));
// ✅ جرّبها: عند العمر 0 الوزن 0.1، وبعد 5 ثواني الوزن 1
console.log(weightOf(0, 0), weightOf(0, 2500), weightOf(0, 5000));
// → 0.1 0.5 1
اضرب الـ inflight أو الـ cost في عكس الوزن وقت الاختيار، أو اختار الـ backend الجديد باحتمال الوزن بتاعه. مش كل الـ LBs بتدعم ده مع كل algorithm: في ALB الـ slow start مش متاح مع least_outstanding_requests.

Cheat sheet · الخلاصة

  • L4 decides per connection, L7 per request. HTTP/2 or gRPC through L4 pins everything to one backend (1000/0/0 vs 334/333/333).
  • Round robin runs the fleet at the speed of its slowest node. Prefer least connections or power of two; weights only help if they are true.
  • Pure least response time herds. Power of two avoids it with two random samples.
  • Affinity: hash % N moved 80.1% when adding a node, a ring with vnodes moved 18.2%.
  • Never make the LB's check depend on the DB. Shallow liveness + passive ejection + panic threshold or fail-open.
  • Detection = interval × failure threshold. Recovery = interval × success threshold. ALB defaults: ~60 s and ~150 s.
  • Draining: surge, stop routing, wait for in-flight 0, close() + closeIdleConnections(). 43 errors became 0.
  • Sessions in Redis instead of stickiness. WebSockets pin by nature, so add jitter to reconnects.
  • Exponential backoff without jitter stays synchronized: full jitter is what spreads the herd.
  • LB limits: ephemeral ports (~470 new conn/s per backend without keep-alive), max connections, and keepAliveTimeout > LB idle timeout.
بالعامية
  • الـ L4 بيقرر لكل connection والـ L7 لكل request. HTTP/2 أو gRPC على L4 بيثبّت كله على backend واحد (1000/0/0 مقابل 334/333/333).
  • الـ round robin بيمشّي الـ fleet كله بسرعة أبطأ node. استخدم least connections أو power of two، والـ weights بتفيد لو حقيقية بس.
  • الـ least response time الصافي بيعمل herd، والـ power of two بيتجنبه بعينتين عشوائيتين.
  • الـ affinity: hash % N حرّك 80.1% لما زودنا node، والـ ring بالـ vnodes حرّك 18.2%.
  • أوعى تخلي check الـ LB معتمد على الـ DB. استخدم shallow liveness مع passive ejection مع panic threshold أو fail-open.
  • الاكتشاف = interval × failure threshold، والرجوع = interval × success threshold. defaults الـ ALB حوالي 60 ثانية و 150 ثانية.
  • الـ draining: surge، وقف التوجيه، استنى inflight صفر، close() مع closeIdleConnections(). الـ 43 error بقوا 0.
  • الـ sessions في Redis بدل الـ stickiness. الـ WebSockets بتتثبت بطبيعتها، فحط jitter للـ reconnects.
  • الـ exponential backoff من غير jitter بيفضل متزامن: الـ full jitter هو اللي بيبعتر الـ herd.
  • حدود الـ LB: الـ ephemeral ports (حوالي 470 connection جديدة في الثانية لكل backend من غير keep-alive)، والـ max connections، و keepAliveTimeout لازم أكبر من الـ idle timeout بتاع الـ LB.
