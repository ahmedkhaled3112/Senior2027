Why this matters · ليه ده مهم

English

One service with one log file is easy to debug. Twenty services, each with thirty instances, are not: a single checkout touches many processes, and each of them writes its own log. At that size the three pillars stop being a setup task and become a design problem with a budget. What can you still join together? What do you keep? What does it cost per month?

This lesson stays on the system-level questions. Lesson 04 · 30 and 04 · 31 taught the instrumentation inside one service; here we cross service boundaries, read real traces, count what sampling loses, price logs, predict metric series and watch a real pool saturate. Interviewers ask exactly this: "how would you find which service made checkout slow?"

Part 1 — Correlation IDs across boundaries 🟡 Intermediateالجزء 1 — الـ correlation IDs عبر حدود الـ services

English

A correlation ID is one value that travels with one business request through every hop. AsyncLocalStorage carries it inside a process, as 04 · 30 showed. It does nothing across a process boundary, so each boundary needs an explicit step: read the ID on the way in, write it on the way out.

There are three kinds of boundary. An incoming HTTP call reads the header, or creates an ID if this is the first hop. An outgoing HTTP call copies the ID into a header. A queue message has no headers of its own in a Redis list, so the ID goes in an envelope around the payload; the consumer takes it out and opens a new context around the handler. Forget any one of them and the chain silently breaks at that hop.

The run below uses real separate processes: api, orders, payments, plus a notifier worker reading a real Redis list. Five checkouts run at the same time and one card is declined. Without IDs, the payments log has no field that also appears in the API log, so you can't say which user was declined. With IDs, one grep gives the whole path.

import { AsyncLocalStorage } from "node:async_hooks";
import { randomUUID } from "node:crypto";
import { appendFileSync } from "node:fs";
import type { IncomingMessage, ServerResponse } from "node:http";

type Ctx = { correlationId: string };
// الـ store ده بيمشي مع الـ async context جوه الـ process بس، مش بيعدّي الشبكة لوحده
export const als = new AsyncLocalStorage<Ctx>();
const SERVICE = process.env.SERVICE!;
const WITH_IDS = process.env.MODE === "ids";

export function log(msg: string, fields: Record<string, unknown> = {}) {
  const correlationId = WITH_IDS ? als.getStore()?.correlationId : undefined;
  const line = { ts: Date.now(), svc: SERVICE, correlationId, msg, ...fields };
  appendFileSync(`logs/${SERVICE}.jsonl`, JSON.stringify(line) + "\n");
}

// (1) دخول الـ request: خد الـ id من الـ header أو ولّد واحد لو إحنا أول hop
export function withCorrelation(req: IncomingMessage, res: ServerResponse, next: () => void) {
  const incoming = req.headers["x-correlation-id"];
  const correlationId = typeof incoming === "string" && incoming ? incoming : randomUUID();
  res.setHeader("x-correlation-id", correlationId);
  als.run({ correlationId }, next);
}

// (2) خروج الـ HTTP call: حط الـ id في الـ header
export function callService(url: string, body: unknown) {
  const headers: Record<string, string> = { "content-type": "application/json" };
  const id = als.getStore()?.correlationId;
  if (WITH_IDS && id) headers["x-correlation-id"] = id;
  return fetch(url, { method: "POST", headers, body: JSON.stringify(body) });
}

// (3) خروج رسالة الـ queue: الـ id جوه الـ envelope مش في الـ payload
export function envelope<T>(payload: T) {
  return JSON.stringify({ correlationId: WITH_IDS ? als.getStore()?.correlationId : undefined, payload });
}

function serve(routes: Record<string, Handler>) {

    withCorrelation(req, res, async () => {
      const chunks: Buffer[] = [];
      for await (const c of req) chunks.push(c as Buffer);
      const body = chunks.length ? JSON.parse(Buffer.concat(chunks).toString()) : {};
      const route = routes[`${req.method} ${req.url}`];

    });
  });
  server.listen(0, "127.0.0.1", () => {
    const { port } = server.address() as { port: number };
    process.send?.({ port });
  });

بالعامية

الـ correlation ID قيمة واحدة بتمشي مع الـ business request الواحد في كل hop. الـ AsyncLocalStorage بيشيلها جوه الـ process بس، زي ما شفنا في 04 · 30. لكن بره الـ process ملوش أي تأثير، فكل حد لازم تعدّيه بإيدك: تقرا الـ id وإنت داخل وتكتبه وإنت خارج.

عندنا 3 أنواع حدود. HTTP داخل: اقرا الـ header، ولو إنت أول hop ولّد id. HTTP خارج: انسخ الـ id في الـ header. رسالة queue: الـ Redis list ملهاش headers، فالـ id بيتحط في envelope حوالين الـ payload، والـ consumer بيطلّعه ويفتح context جديد حوالين الـ handler. لو نسيت حد واحد من التلاتة، السلسلة بتتقطع عند الـ hop ده من غير أي error.

الـ run فوق processes حقيقية منفصلة: api وorders وpayments، ومعاهم worker اسمه notifier بيقرا من Redis list حقيقية. خمس checkouts في نفس الوقت، وبطاقة واحدة بتترفض. من غير IDs، مفيش حقل مشترك بين الـ payments log والـ api log، فمش هتعرف مين اترفض. بالـ IDs، grep واحد بيجيب المسار كله.

الغلطة الشائعة: تحط الـ id في الـ HTTP بس وتنسى الـ queue. الـ worker ساعتها بيطبع logs ملهاش صاحب، وده بالظبط الجزء اللي الناس بتدوّر فيه لما email متبعتش.

فين هستخدمه في شغلي؟ عميل بيقول "دفعت وملقتش الـ order". بدل ما تدوّر بالوقت في 3 dashboards، بتاخد الـ x-correlation-id من الـ response بتاع الـ client (أو من الـ error page) وتعمل بيه بحث واحد في الـ logs. وفي الـ BullMQ أو أي queue عندك، حط الـ id في بيانات الـ job وافتح als.run في أول الـ processor.

HTTP headers don't exist there, so the producer must put the ID in the message and the consumer must restore it before running the handler.

Part 2 — Traces and the critical path 🟡 Intermediateالجزء 2 — الـ traces والـ critical path

English

A correlation ID tells you what happened; a trace also tells you when and for how long. OpenTelemetry propagates context with the W3C traceparent header: 00-<32 hex trace id>-<16 hex parent span id>-<2 hex flags>. Every hop creates child spans under the same trace ID. Setup is in 04 · 31, so we only added the bootstrap to the same three services from Part 1 and a tiny exporter that writes each span as a JSON line.

Two real things happened on the way. First, our services are ESM, and with a plain --require bootstrap only the client spans appeared and every fetch became its own trace, with no error at all: the server side was never patched. Adding the import hook fixed it, which is the ESM trap from 04 · 31. Second, this install resolved to SDK 0.301, where the package is @opentelemetry/sdk-trace and SimpleSpanProcessor takes an options object, new SimpleSpanProcessor({ exporter }). Passing the exporter directly gave Cannot read properties of undefined (reading 'export').

The new tool here is a script that reads the exported spans and answers the question a waterfall only hints at: which spans actually determine the total time? The critical path walks backwards from the end of the root span, always picking the child that finished last. A child that overlaps the chosen one ran in parallel, so it isn't on the path. Speeding up something off the critical path doesn't change the total at all.

The script also lists sibling spans that ran back to back. Those are candidates for parallel calls, but it can't know about dependencies. Here /risk and /limits are independent, while /charge needs both results. A human makes that call.

import fs from "node:fs";
import { NodeSDK } from "@opentelemetry/sdk-node";
import { SimpleSpanProcessor } from "@opentelemetry/sdk-trace";
import { HttpInstrumentation } from "@opentelemetry/instrumentation-http";
import { UndiciInstrumentation } from "@opentelemetry/instrumentation-undici";

const service = process.env.SERVICE;
const toMs = ([s, ns]) => s * 1e3 + ns / 1e6;

// الـ exporter ده بيكتب كل span كسطر JSON في ملف الـ service، بدل collector حقيقي
class FileSpanExporter {
  export(spans, done) {
    for (const s of spans) {
      const ctx = s.spanContext();
      const line = {
        traceId: ctx.traceId, spanId: ctx.spanId, parentId: s.parentSpanContext?.spanId,
        service, name: s.name, kind: s.kind, startMs: toMs(s.startTime), endMs: toMs(s.endTime),
        status: s.status.code, path: s.attributes["url.path"] ?? s.attributes["http.target"],
        rawBytes: Buffer.byteLength(JSON.stringify({ ctx, parent: s.parentSpanContext, name: s.name, attrs: s.attributes, resource: s.resource.attributes })),
      };
      fs.appendFileSync(`spans/${service}.jsonl`, JSON.stringify(line) + "\n");
    }
    done({ code: 0 });
  }
  shutdown() { return Promise.resolve(); }
}

type Span = { traceId: string; spanId: string; parentId?: string; service: string; kind: number; startMs: number; endMs: number; path?: string; rawBytes: number };
type Seg = { label: string; ms: number };

const spans: Span[] = readdirSync("spans").flatMap((f) =>
  readFileSync(`spans/${f}`, "utf8").trim().split("\n").map((l) => JSON.parse(l)));

// جمّع الـ spans بالـ trace، وخد الـ trace الوسطاني عشان منتخدعش بواحد شاذ
const byTrace = Map.groupBy(spans, (s) => s.traceId);
const rootOf = (t: Span[]) => t.find((s) => !s.parentId || !t.some((p) => p.spanId === s.parentId))!;
const traces = [...byTrace.values()].sort((a, b) => dur(rootOf(a)) - dur(rootOf(b)));
function dur(s: Span) { return s.endMs - s.startMs; }
const trace = traces[Math.floor(traces.length / 2)]!;
const root = rootOf(trace);
const total = dur(root);
const kids = (p: Span) => trace.filter((s) => s.parentId === p.spanId).sort((a, b) => a.startMs - b.startMs);
const label = (s: Span) => `${s.service} ${s.kind === 1 ? "SERVER" : "CLIENT"} ${s.path}`;

console.log(`trace ${root.traceId.slice(0, 8)}…  spans=${trace.length}  total=${total.toFixed(0)} ms  (median of ${traces.length} traces)`);
const WIDTH = 40;
function waterfall(s: Span, depth: number) {
  const left = Math.round(((s.startMs - root.startMs) / total) * WIDTH);
  const len = Math.max(1, Math.round((dur(s) / total) * WIDTH));
  const bar = " ".repeat(left) + "█".repeat(len);
  console.log(`${bar.padEnd(WIDTH + 1)} ${String(dur(s).toFixed(0)).padStart(4)} ms  ${"  ".repeat(depth)}${label(s)}`);
  kids(s).forEach((k) => waterfall(k, depth + 1));
}
waterfall(root, 0);

// الـ critical path: امشي بالعكس من نهاية الأب، وخد الابن اللي خلص آخر واحد قبل المؤشر
function criticalPath(s: Span): Seg[] {
  const out: Seg[] = [];
  let cursor = s.endMs;
  for (const k of kids(s).sort((a, b) => b.endMs - a.endMs)) {
    // ابن بيخلص بعد المؤشر يبقى شغال بالتوازي مع اللي اخترناه، فمش على الـ critical path
    if (k.endMs > cursor + 0.5) continue;
    if (cursor > k.endMs) out.push({ label: label(s) + " (self)", ms: cursor - k.endMs });
    out.push(...criticalPath(k));

Part 3 — Head vs tail sampling 🟡 Intermediateالجزء 3 — الـ head مقابل الـ tail sampling

English

Keeping every trace at scale is usually too expensive, so you sample. Head sampling decides when the trace starts, usually from a hash of the trace ID so every service reaches the same answer. It's cheap and stateless, but it decides before anyone knows the outcome. Tail sampling decides after the trace finishes, so it can keep every error and every slow request. The price is that something has to hold all the spans in memory until the decision.

The run below generates 100,000 traces with 0.5% errors. Head sampling at 1% uses the real TraceIdRatioBasedSampler. It kept 3 of 518 error traces. The tail policy (all errors, all slow requests, 1% of the rest) kept all 518 at about 2% of the storage. That's the whole argument for tail sampling: you pay for roughly twice as many spans as head sampling and keep 170 times as many of the traces you'd actually open.

The cost moves into the collector. Memory held is traces/s × spans per trace × bytes per span × decision window. We use 1,628 bytes per span, measured from the real spans in Part 2 as JSON; a collector stores them differently, so treat it as an order of magnitude. There's also a hard topology rule: all spans of a trace must reach the same collector instance, so tail sampling at scale needs two layers, one with the load-balancing exporter routing by trace ID and one doing the sampling.

Part 4 — Logs at scale 🟡 Intermediateالجزء 4 — الـ logs على scale

English

The log bill is arithmetic: QPS × lines per request × bytes per line × seconds, then a price for ingesting and a price for storing. Line size is something you can measure instead of guessing. With real pino output, a plain info line was about 106 bytes, the trace context pushed it to 234, and an error with a stack was about 1,075.

Run the calculator at 2,000 QPS and 12 lines per request and you get about 601 GB a day. Ingest was 94% of the "keep everything" bill, and that's why moving old data to a cheaper tier didn't help here: the tiered plan cost more, because it added 90 days of cold storage while ingest stayed the same. The prices are assumptions to replace with your vendor's. The lever that actually works is writing less. Sample info logs and keep every warning and error. That took the bill from about $9,561 to about $831 a month.

Sampling has two rules. Decide by a hash of the trace ID, so all the lines of one request stay or go together; a request with half its lines missing is worse than none. And make it changeable at runtime: when a customer reports a problem, raise that tenant to 100% with a config flag, with no deploy. Retention tiers then answer a separate question: hot and searchable for a week, cold in object storage for audits.

Finally, cardinality is the difference between logs and metrics. Adding userId and tenantId to a log line cost 44 bytes. That's all. The same fields as metric labels are a different story, which Part 5 measures.

Part 5 — Metrics and cardinality 🟡 Intermediateالجزء 5 — الـ metrics والـ cardinality

English

Each unique combination of label values is its own time series, and the bill is counted in series. For one histogram, series = routes × statuses × instances × (buckets + 3): one line per bucket, plus +Inf, _sum and _count. You can check this before shipping. Our estimate of 416 per instance matched a real @prometheus-io/client registry exactly (prom-client is deprecated). The raw-URL-as-label bug is in 04 · 31 part 4; here we size the general case.

Then add user_id. Even at the kindest possible assumption, one route and one status per user, 10,000 users made 130,000 series on one instance, a 12.6 MB scrape body and about 17.5 MB of extra heap in the app. registry.metrics() took about 117 ms, and that runs on the event loop. Multiply by 20 instances and Prometheus gets 2.6 million series from one metric. We measured the client side; the server's cost per series wasn't run here.

The second trap is aggregation. You can't average percentiles. Two instances, one fast with 9,000 requests and one slow with 1,000: the average of their p99s said 1,267 ms, while the true p99 across all requests was 2,140 ms. Histograms can be merged because you add bucket counts, and the merged estimate was 2,349 ms, limited only by bucket width. That's why you store histograms and compute the quantile last, across the fleet.

type B = { le: number; count: number };
async function bucketsOf(r: Registry): Promise<B[]> {
  const m = (await r.getMetricsAsJSON())[0]!;
  return (m.values as any[])
    .filter((v) => v.metricName?.endsWith("_bucket"))
    .map((v) => ({ le: v.labels.le === "+Inf" ? Infinity : Number(v.labels.le), count: v.value }));
}

// نفس فكرة histogram_quantile بتاع Prometheus: interpolation خطية جوه الـ bucket
function quantile(q: number, b: B[]) {
  const total = b[b.length - 1]!.count;
  const rank = q * total;
  let prevCount = 0, prevLe = 0;
  for (const x of b) {
    if (x.count >= rank) {
      if (x.le === Infinity) return prevLe;
      return prevLe + ((x.le - prevLe) * (rank - prevCount)) / (x.count - prevCount);
    }
    prevCount = x.count; prevLe = x.le;
  }
  return NaN;
}

Part 6 — RED and USE on a real run 🟡 Intermediateالجزء 6 — الـ RED و الـ USE على run حقيقي

English

Two checklists stop you staring at random graphs. RED is for services, seen from the caller: Rate, Errors, Duration. USE is for resources: Utilization, Saturation, Errors. For a Node service the resources are the connection pool (busy connections over max, and waitingCount as saturation), queue depth, and event loop delay. RED tells you that users are hurting; USE tells you what's running out.

We ran two real HTTP services, api calling orders, with a real Postgres behind a pool of 5 and a Redis queue drained at about 150 jobs a second. The load is open loop: requests leave at a fixed rate whether or not the server keeps up, as real users do. Each query holds a connection for about 31 ms on this machine (pg_sleep(0.02), plus Windows timer rounding), so the pool tops out near 162 requests a second.

Read the table from the top. From 40 to 150 rps, p50 stays at 32 ms, so RED looks perfectly healthy, while pool utilization climbs from 27% to 89% and the queue starts to grow at 150. Then at 170 rps utilization is 98%, 12 requests are waiting on average, and p50 jumps to 110 ms. At 190 it's 293 ms. Saturation signals moved one full step before latency did. Event loop delay stayed flat at about 16 ms, which is the Windows timer floor here: the event loop wasn't the bottleneck, the pool was. Which of these deserve an alert is the subject of Lesson 40.

async function pacedLoad(url: string, rate: number, seconds: number) {
  const inflight: Promise<unknown>[] = [];
  const t0 = performance.now();
  let sent = 0;
  await new Promise<void>((done) => {
    const tick = setInterval(() => {
      const elapsed = (performance.now() - t0) / 1000;
      if (elapsed >= seconds) { clearInterval(tick); return done(); }
      const due = Math.floor(elapsed * rate);
      while (sent < due) { sent++; inflight.push(fetch(url).then((r) => r.text()).catch(() => {})); }
    }, 5);
  });
  return inflight;
}

Common mistakes · غلطات شائعة

❌ The ID stops at the queue 
// الـ id راح مع الـ HTTP بس
await redis.lpush("q:notify", JSON.stringify({ userId }));
✅ The message carries the context 
// الـ id في الـ envelope والـ consumer بيرجّعه
await redis.lpush("q:notify", envelope({ userId }));
als.run({ correlationId }, () => handle(payload));
بالعامية

❌ الـ HTTP hops متربطة كويس، بس أول ما الشغل يدخل queue الـ id بيضيع، فأي مشكلة في الـ worker ملهاش صاحب. ✅ الرسالة نفسها بتشيل الـ id في envelope، والـ consumer بيرجّعه بـ als.run قبل الـ handler، فالسلسلة بتكمل لحد آخر الشغل.

❌ Head sampling for rare failures 
// بيقرر قبل ما يعرف النتيجة: 3 errors من 518
new TraceIdRatioBasedSampler(0.01);
✅ Decide after the outcome is known

بالعامية

❌ الـ head بنسبة 1% خلّى 3 traces بس من 518 error في المحاكاة، فلما تيجي تدوّر على عطل هتلاقي مفيش. ✅ القرار بعد ما الـ trace يخلص بيحتفظ بكل الـ errors والبطيء بحوالي 2% تخزين، والتمن memory في الـ collector.

❌ Unbounded label 
// كل مستخدم بقى series: 130,000 مع 10,000 مستخدم
h.observe({ route, status, user_id: user.id }, s);
✅ Bounded labels, details in logs 
// الـ labels ليها حد أقصى، والـ user في الـ log
h.observe({ route, status }, s);
logger.info({ userId: user.id, route }, "served");
بالعامية

❌ user_id كـ label خلّى عدد الـ series يتضرب في عدد المستخدمين، 130,000 series على instance واحد مع 10,000 مستخدم. ✅ الـ labels تفضل بقيم محدودة، والتفاصيل عالية الـ cardinality تروح الـ logs، وتكلفتها هناك 44 byte في السطر.

Cheat sheet · الخلاصة

  • Correlation ID: read on entry, write on HTTP exit, put in the envelope for queues. ALS only works inside one process.
  • W3C traceparent: 00-traceId-spanId-flags. ESM apps need the import hook or server spans vanish silently.
  • Critical path: walk back from the root's end, take the last-finishing child. Off-path work doesn't change the total.
  • Sequential siblings are candidates for parallel; only independent reads qualify.
  • Head 1% kept 3 of 518 errors; tail kept all 518 at about 2% storage.
  • Collector memory = traces/s × spans × bytes × decision window. All spans of a trace must reach one collector.
  • Log bill = QPS × lines × bytes × price. Ingest dominated; sampling info cut it from about $9,561 to $831.
  • Sample by trace ID hash, keep all errors, raise per tenant at runtime.
  • High cardinality: 44 bytes in a log line, 130,000 series as a metric label.
  • Series = routes × statuses × instances × (buckets + 3). Never average percentiles; merge histograms.
  • RED for services, USE for resources. Pool utilization and queue depth moved before p50 did.
  • Check how your load generator actually sends requests before trusting it.
بالعامية
  • الـ correlation ID: اقراه وإنت داخل، اكتبه في الـ HTTP الخارج، وحطه في envelope للـ queues. الـ ALS شغال جوه process واحد بس.
  • الـ traceparent بتاع W3C شكله 00-traceId-spanId-flags. تطبيقات ESM محتاجة الـ import hook وإلا الـ server spans بتختفي من غير error.
  • الـ critical path: ارجع من نهاية الـ root وخد الابن اللي خلص آخر واحد. أي شغل بره الـ path مش بيغيّر الوقت الكلي.
  • الـ siblings المتتابعين مرشحين للـ parallel، بس الـ reads المستقلة هي اللي تنفع.
  • الـ head بنسبة 1% خلّى 3 من 518 error، والـ tail خلّى الـ 518 كلهم بحوالي 2% تخزين.
  • الـ collector memory = traces/s × spans × bytes × decision window، وكل spans الـ trace لازم توصل لـ collector واحد.
  • فاتورة الـ logs = QPS × سطور × bytes × سعر. الـ ingest هو الأكبر، والـ sampling للـ info نزّلها من حوالي 9,561 لـ 831 دولار.
  • اعمل sampling بـ hash الـ trace ID، سيب كل الـ errors، وارفع النسبة لـ tenant معين وقت التشغيل.
  • الـ high cardinality: 44 byte في سطر log، و130,000 series كـ metric label.
  • الـ series = routes × statuses × instances × (buckets + 3). متعملش متوسط لـ percentiles، اجمع الـ histograms.
  • الـ RED للـ services والـ USE للـ resources. الـ pool utilization وطول الـ queue اتحركوا قبل الـ p50.
  • اتأكد الـ load generator بيبعت الطلبات إزاي قبل ما تثق في نتيجته.
