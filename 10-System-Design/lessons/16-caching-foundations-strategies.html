Why this matters · ليه ده مهم

English

Caching is the first tool anyone reaches for and the one most often applied without numbers. Put simply, a cache buys two different things, lower latency and lower load on the database, and on a healthy primary-key query the first one can be almost nothing while the second is huge. Choosing well means knowing which level holds the data, what hit ratio you actually have per data type, what gets evicted under memory pressure, and what happens to a write when one of the two stores fails.

This lesson measures each of those on real Redis and Postgres. It deliberately stops at the foundations: invalidation is the next lesson, and stampede and hot keys are in the one after.

بالعامية

الـ caching هو أول أداة أي حد بيمسكها، وأكتر أداة بتتحط من غير أرقام. الـ cache بيشتريلك حاجتين مختلفين: latency أقل، و load أقل على الداتابيز. وعلى query بالـ primary key على داتابيز سليمة، الأولى ممكن تبقى ولا حاجة تقريبًا والتانية ضخمة. الاختيار الصح معناه تعرف أنهي level شايل الداتا، والـ hit ratio الحقيقي لكل نوع داتا، وإيه اللي بيتشال لما الـ memory تضغط، وإيه اللي بيحصل للـ write لو واحد من المكانين وقع.

الدرس ده بيقيس كل ده على Redis و Postgres حقيقيين، وبيقف عند الأساسيات عن قصد: الـ invalidation في الدرس الجاي، والـ stampede والـ hot keys في اللي بعده.

Part 1 — Why cache, measured 🟢 Basicالجزء 1 — ليه الـ cache بالقياس

English

Two separate benefits. Latency: the hit is cheaper than the query. Load: every hit is a query the database never ran. Measure both, because they aren't the same size. In the run below a primary-key lookup on local Postgres was about as fast as a Redis GET (a 1.6× difference), so caching it buys almost no latency. A product-page join and aggregate over about 2,000 reviews was about 12× slower than the GET, which is where latency improves.

The load result is the one that pays. Under 40 connections for 6 seconds the API did about 3,768 req/s going straight to the database and about 29,300 req/s with a warmed Redis, with zero database queries. Notice the middle line of the load output: the cold cache sent 7,063 queries in that run, because 40 connections asked for the same key at once before anyone had filled it. That is a stampede, the subject of lesson 18.

The formula. Effective latency = h × cache + (1 − h) × (cache + db). A miss pays for the cache lookup too, which is why a cache with a poor hit ratio makes things slower than having none. Plugging in the measured means shows the shape: 2.1 ms at 0%, 0.35 ms at 90%, 0.18 ms at 99%.

async function time(label: string, n: number, f: () => Promise<unknown>) {
  const xs: number[] = [];
  for (let i = 0; i < n; i++) {
    const t0 = performance.now();
    await f();
    xs.push(performance.now() - t0);
  }
  const { mean, p50, p99 } = stats(xs);
  console.log(label.padEnd(30), `mean≈${mean.toFixed(3)} ms  p50≈${p50.toFixed(3)} ms  p99≈${p99.toFixed(3)} ms`);
  return mean;
}
const pk = await time("Postgres PK lookup", 2000, () => db.query(`select * from products where id=$1`, [7]));
const agg = await time("Postgres product page (join)", 2000, () => db.query(PAGE_SQL, [7]));
const cache = await time("Redis GET (same page JSON)", 2000, () => redis.get("product:1"));

// الـ ⁦formula: h×cache + (1−h)×(cache+db) —⁩ الـ miss بيدفع رحلة الـ cache برضه
for (const h of [0, 0.5, 0.8, 0.9, 0.95, 0.99]) {
  const effective = h * cache + (1 - h) * (cache + agg);
  console.log(`hit ratio ${String(h * 100).padStart(3)}%: effective ≈ ${effective.toFixed(3)} ms, DB gets ${((1 - h) * 100).toFixed(0)}% of reads`);
}
console.log(`ratio page/redis ≈ ${(agg / cache).toFixed(1)}x, ratio PK/redis ≈ ${(pk / cache).toFixed(1)}x`);

async function load(mode: "db" | "cache", warm: boolean) {
  await redis.flushall();
  const child = fork(new URL("./p1-server.ts", import.meta.url), {
    env: { ...process.env, MODE: mode, PG_PORT: String(cluster.port), REDIS_PORT: String(redis.options.port) },
  });
  const [{ port }] = (await once(child, "message")) as [{ port: number }];
  const base = `http://127.0.0.1:${port}`;
  const stat = async () => (await (await fetch(`${base}/stats`)).json()) as { dbQueries: number };
  // الـ warm-up: كل منتج مرة واحدة قبل الضغط، فالـ cache مليان من الأول
  if (warm) for (let i = 1; i <= 200; i++) await (await fetch(`${base}/products/${i}`)).text();
  const before = (await stat()).dbQueries;
  const requests = Array.from({ length: 200 }, (_, i) => ({ path: `/products/${i + 1}` }));
  const r = await autocannon({ url: base, connections: 40, duration: 6, requests });
  const queries = (await stat()).dbQueries - before;
  child.kill();
  console.log(`${mode}${warm ? " warm" : " cold"}`.padEnd(11), `req/s≈${Math.round(r.requests.average)}  p50≈${r.latency.p50} ms  p99≈${r.latency.p99} ms  errors=${r.errors + r.non2xx}  DB queries=${queries}  (${(queries / 6).toFixed(0)}/s)`);
}
await load("db", false);
await load("cache", false);
await load("cache", true);

await db.end();
await redis.quit();
await stopAll(cluster);
process.exit(0);

import http from "node:http";
import type { AddressInfo } from "node:net";
import { newPool, newRedis } from "./lab.ts";

const mode = process.env.MODE as "db" | "cache";
const pool = newPool(process.env.PG_PORT!);
const redis = newRedis();
const counters = { dbQueries: 0, requests: 0 };

const PAGE_SQL = `
  select p.id, p.name, p.price_cents, count(r.id)::int reviews, round(avg(r.rating), 2) rating
  from products p left join reviews r on r.product_id = p.id
  where p.id = $1 group by p.id`;

async function loadProduct(id: number) {
  counters.dbQueries++;
  return (await pool.query(PAGE_SQL, [id])).rows[0];
}

async function getProduct(id: number) {
  if (mode === "db") return loadProduct(id);
  const key = `product:${id}`;
  const hit = await redis.get(key);
  if (hit !== null) return JSON.parse(hit);
  const row = await loadProduct(id);
  await redis.set(key, JSON.stringify(row), "EX", 120);
  return row;
}

const server = http.createServer(async (req, res) => {
  if (req.url === "/stats") return res.end(JSON.stringify(counters));
  counters.requests++;
  const id = Number(req.url!.split("/")[2]);
  res.setHeader("content-type", "application/json");
  res.end(JSON.stringify(await getProduct(id)));
});
server.listen(0, "127.0.0.1", () => process.send!({ port: (server.address() as AddressInfo).port }));

بالعامية

فايدتين منفصلين. الـ latency: الـ hit أرخص من الـ query. والـ load: كل hit هو query الداتابيز معملتهاش. قيس الاتنين لأنهم مش نفس الحجم. في التشغيل فوق، الـ primary-key lookup على Postgres محلي كان تقريبًا زي Redis GET (فرق 1.6 مرة)، فالـ cache عليه مش بيشتريلك latency تقريبًا. أما صفحة المنتج بـ join و aggregate على حوالي 2000 review كانت أبطأ حوالي 12 مرة، وهنا الـ latency بيتحسن فعلًا.

نتيجة الـ load هي اللي بتفرق. تحت 40 connection لمدة 6 ثواني، الـ API عمل حوالي 3,768 طلب في الثانية وهو نازل على الداتابيز مباشرة، وحوالي 29,300 طلب في الثانية مع Redis مليان ومن غير ولا query. بص على السطر اللي في النص: الـ cache الفاضي بعت 7,063 query في الـ run ده، لأن 40 connection طلبوا نفس الـ key في نفس الوقت قبل ما حد يملاه. ده الـ stampede، وموضوع درس 18.

المعادلة: الـ latency الفعلي = h × cache + (1 − h) × (cache + db). الـ miss بيدفع رحلة الـ cache برضه، وعشان كده cache بـ hit ratio وحش ممكن يخلّي الدنيا أبطأ من مفيش cache خالص. لما حطينا الأرقام المتقاسة طلع: 2.1 ms عند 0%، و0.35 ms عند 90%، و0.18 ms عند 99%.

فين هستخدمه في شغلي؟ قبل ما تضيف Redis لـ endpoint، قيس. لو الـ query بتاعتك PK بسيط والداتابيز مرتاحة، الـ cache مش هيحسن الـ latency وهيزود كود invalidation. لو الـ endpoint صفحة منتج بـ joins و aggregates بتتطلب 3000 مرة في الثانية، الـ cache هينقذ الـ primary من ضغط حقيقي حتى لو الـ latency مش هو المشكلة. والـ PR بتاعك يقول الرقمين.
Trade-off: a cache is a second copy of the truth Every cache adds a staleness window, an invalidation path and a new failure mode. If the database is comfortable and the query is cheap, an index or a read replica may solve the problem with fewer moving parts. Add the cache when the numbers say the database is the constraint.
كل cache بيضيف فترة stale، ومسار invalidation، وطريقة فشل جديدة. لو الداتابيز مرتاحة والـ query رخيصة، ممكن index أو read replica يحلوا المشكلة بأجزاء أقل. ضيف الـ cache لما الأرقام تقول إن الداتابيز هي القيد.
Interview question "Would you put Redis in front of a primary-key lookup?" → Measure first. On a healthy database it often buys little latency, so I'd add it for load: if that query is a large share of primary CPU, a cache lets me shrink the database or survive a traffic spike. Then I'd state the hit ratio I expect and the staleness I'm accepting.
"هتحط Redis قدام primary-key lookup؟" ← أقيس الأول. على داتابيز سليمة غالبًا مش بيوفر latency كتير، فهضيفه عشان الـ load: لو الـ query دي جزء كبير من الـ CPU بتاع الـ primary، الـ cache بيخليني أصغّر الداتابيز أو أستحمل traffic spike. وبعدها أقول الـ hit ratio المتوقع والـ staleness اللي قابله.

Part 2 — Cache levels 🟢 Basicالجزء 2 — مستويات الـ cache

English

A product request can be answered at four levels: the browser (no network at all), the CDN edge (tens of milliseconds, near the user), application memory with lru-cache (sub-microsecond, per process) and Redis (a network hop, shared by all pods). Behind them sits the database. HTTP cache headers, CDN behaviour and in-process LRU are covered in Next caching, the CDN lesson and the Redis patterns lesson, so this part only adds the cost comparison.

The rule: the closer to the user, the faster and the harder to invalidate. One DEL clears Redis. Twenty pods each hold their own memory, so they need an event or a short TTL. A CDN needs a purge API call that takes seconds. A browser can't be reached at all: you wait for max-age, or you change the URL.

Read the trace carefully. Once a request has crossed the internet to your origin, the hops inside your data center are rounding errors: the L1 hit, the Redis hit and even the database query all show about 80 ms in the table below. In this run the browser and CDN hops are assumed numbers (not run here), while L1, Redis and Postgres are measured. Inner levels are about protecting your origin, and outer levels are about the user.

   Browser        CDN edge        App pod (L1)      Redis (L2)     Postgres
   max-age        s-maxage        lru-cache         shared         truth
   0 ms           ~20 ms *        +60 ms * + <1 us  +~0.1 ms       +~0.1-2 ms
     |              |                |                 |              |
   hard to invalidate  <------------------------------>  easy to invalidate
   (one user only)                                       (one DEL)

   * assumed, not measured here
من الشمال لليمين: كل ما تقرّب من الـ database التكلفة في الـ network بتزيد والـ invalidate بيبقى أسهل. الـ browser ببلاش بس مش تقدر توصله، بعده الـ CDN (حوالي 20 ms افتراضي)، بعده الـ app memory، بعده Redis، وآخر حاجة Postgres. الأرقام اللي عليها علامة (*) افتراض مش قياس. واللي تحت: الـ browser أصعب حاجة تعمله invalidate، و Redis أسهل حاجة (DEL واحدة).

بالعامية

طلب المنتج ممكن يتجاوب من 4 مستويات: الـ browser (مفيش network خالص)، و CDN edge (عشرات الـ milliseconds وقريب من المستخدم)، و app memory بـ lru-cache (أقل من microsecond ولكل process لوحده)، و Redis (network hop ومشترك بين كل الـ pods). ووراهم الداتابيز. الـ HTTP headers والـ CDN والـ LRU جوه الـ process متغطيين في درس Next caching ودرس الـ CDN ودرس Redis patterns، فالجزء ده بيضيف مقارنة التكلفة بس.

القاعدة: كل ما تقرّب من المستخدم، بيبقى أسرع وأصعب في الـ invalidate. DEL واحدة بتمسح Redis. عشرين pod كل واحد عنده memory لوحده، فمحتاجين event أو TTL قصير. الـ CDN محتاج purge API بياخد ثواني. والـ browser مفيش طريقة توصله: يا تستنى الـ max-age يا تغيّر الـ URL.

اقرا الـ trace كويس. بعد ما الطلب عدّى الإنترنت ووصل الـ origin، المسافات جوه الـ data center بقت أرقام مهملة: L1 و Redis وحتى الداتابيز كلهم حوالي 80 ms في الجدول اللي فوق. والـ browser والـ CDN هنا أرقام مفترضة (مشغلناهمش هنا)، أما L1 و Redis و Postgres فمتقاسين. المستويات الداخلية هدفها تحمي الـ origin، والخارجية هدفها المستخدم.

Part 3 — Cache-aside & hit ratio 🟢 Basicالجزء 3 — الـ cache-aside والـ hit ratio

English

Cache-aside is read the cache, on a miss read the database, then write the cache with a TTL. The full helper with its fail-open behaviour is in the Node Redis lesson, part 1; the Redis-side details are in the Databases lesson. What's new here is measuring it. The helper below only adds a counter per namespace.

The global number lies. INFO stats gives keyspace_hits and keyspace_misses for the whole instance. In the run it said 82.1%, which looks acceptable, while the cart namespace was at 0.5%: every cart read went to the database and also paid a useless Redis write. Only per-namespace counters show that.

Small hit ratio changes are large load changes. What matters to the database is the miss rate. Going from 90% to 99% cuts misses from 10% to 1%, a tenfold difference. At 10,000 reads per second that's 1,000 versus 100 database reads per second. Measured with real pg_stat_statements counts on 20,000 requests: 2,009 queries against 185, about 10.9×.

Cold start. After a deploy that flushes the cache, or a Redis restart, the hit ratio starts at zero and climbs. In the run it was 48% in the first thousand requests and took about 9,000 requests to level off near 80%, while the database took about 2.6 times the steady-state queries in the first bucket. Plan warm-up or capacity for it.

// نفس الـ helper بتاع درس 04، زائد counters لكل namespace
import type { Redis } from "ioredis";

export type NsStats = { hits: number; misses: number; errors: number };

export function createCache(redis: Redis) {
  const byNs = new Map<string, NsStats>();
  const statsFor = (ns: string) => {
    let s = byNs.get(ns);
    if (!s) byNs.set(ns, (s = { hits: 0, misses: 0, errors: 0 }));
    return s;
  };

  async function getOrSet<T>(ns: string, id: string | number, ttlSeconds: number, loader: () => Promise<T>): Promise<T> {
    const s = statsFor(ns);
    const key = `${ns}:${id}`;
    let cached: string | null = null;
    try {
      cached = await redis.get(key);
    } catch {
      // لو Redis وقع نكمل على الـ DB: الـ cache مش لازم يوقّع الـ request
      s.errors++;
      return loader();
    }
    if (cached !== null) {
      s.hits++;
      return JSON.parse(cached) as T;
    }
    s.misses++;
    const value = await loader();
    await redis.set(key, JSON.stringify(value), "EX", ttlSeconds).catch(() => { s.errors++; });
    return value;
  }
  return { getOrSet, byNs };
}

export const hitRatio = (s: NsStats) => ((100 * s.hits) / (s.hits + s.misses)).toFixed(1) + "%";

Part 4 — Eviction policies 🟡 Intermediateالجزء 4 — سياسات الـ eviction

English

Eviction decides what leaves when memory is full; TTL decides what leaves when it's old. They're different mechanisms and you usually want both. How LRU is built is covered in the hash tables and LRU lesson, and Redis's own options in Running Redis. This part compares policies on the same traces.

The simulator replays three seeded traces at the same capacity of 1,000 entries:

  • Plain Zipf: LFU wins (51.4%) because it keeps genuinely popular keys, ahead of LRU (42.3%), TTL-only (40.1%) and FIFO (38.4%).
  • Zipf plus a nightly scan: a reporting job reads 20,000 unrelated keys once. In the first 500 user requests after each scan, LRU falls to 26.5% because the scan flushed it, and LFU holds at 52.5%. FIFO and TTL-only behave like LRU here.
  • Zipf where popularity shifts each day: LFU drops to 27.6% because yesterday's favourites keep high counts and block new ones. LRU stays at 42.2%. Adding decay, which halves the counters periodically, brings LFU to 47.0%, and that is why Redis's LFU has lfu-decay-time.

TTL-only has no memory bound. With a 2,000-tick TTL it peaked at 2,000 entries during the scan, double the capacity the others were limited to, so its row is not directly comparable. Memory is roughly the rate of new keys times the TTL, which is why a TTL alone doesn't protect you.

On real Redis at 5 MB, the same order showed up: allkeys-lfu at 75.8%, allkeys-lru at 70.3%, and volatile-ttl at 58.3%, because it evicts by time-to-live, whatever the popularity. And a volatile-* policy with no TTLs set has nothing to evict, so writes fail with an OOM error. This Redis build also accepts allkeys-lrm and volatile-lrm, which the Redis docs describe as least recently modified; we only confirmed the setting is accepted, not how it behaves.

// المحاكي: نفس الـ trace على LRU و LFU و FIFO و TTL-only و LFU بالـ decay
import { mulberry32, zipf } from "./lab.ts";

console.log("Not modelled: object sizes, Redis sampling, memory overhead, concurrency, the real cost of a miss.");

type Policy = { name: string; get(k: number, now: number): boolean; put(k: number, now: number): void; size(): number };

function lru(cap: number): Policy {
  const m = new Map<number, true>();
  return {
    name: "LRU",
    get: (k) => { if (!m.has(k)) return false; m.delete(k); m.set(k, true); return true; },
    put: (k) => { m.set(k, true); if (m.size > cap) m.delete(m.keys().next().value!); },
    size: () => m.size,
  };
}
function fifo(cap: number): Policy {
  const m = new Map<number, true>();
  return {
    name: "FIFO",
    get: (k) => m.has(k),
    put: (k) => { m.set(k, true); if (m.size > cap) m.delete(m.keys().next().value!); },
    size: () => m.size,
  };
}
function lfu(cap: number, decayEvery = 0): Policy {
  const freq = new Map<number, number>();
  let buckets = new Map<number, Set<number>>();
  let minF = 1, ops = 0;
  const addTo = (f: number, k: number) => { if (!buckets.has(f)) buckets.set(f, new Set()); buckets.get(f)!.add(k); };
  const bump = (k: number) => {
    const f = freq.get(k)!;
    const b = buckets.get(f)!;
    b.delete(k);
    if (b.size === 0) { buckets.delete(f); if (minF === f) minF = f + 1; }
    freq.set(k, f + 1);
    addTo(f + 1, k);
  };
  const evict = () => {
    while (!buckets.has(minF)) minF++;
    const b = buckets.get(minF)!;
    const victim = b.values().next().value!;
    b.delete(victim);
    if (b.size === 0) buckets.delete(minF);
    freq.delete(victim);
  };
  // الـ decay بيقسم الـ counters على 2: اللي كان نجم زمان لازم يفضل يتطلب عشان يفضل
  const decay = () => {
    buckets = new Map();
    minF = Infinity;
    for (const [k, f] of freq) { const nf = Math.max(1, f >> 1); freq.set(k, nf); addTo(nf, k); minF = Math.min(minF, nf); }
    if (minF === Infinity) minF = 1;
  };
  return {
    name: decayEvery ? "LFU+decay" : "LFU",
    get: (k) => {
      if (decayEvery && ++ops % decayEvery === 0) decay();
      if (!freq.has(k)) return false;
      bump(k);
      return true;
    },
    put: (k) => { if (freq.size >= cap) evict(); freq.set(k, 1); addTo(1, k); minF = 1; },
    size: () => freq.size,
  };
}
function ttlOnly(ttl: number): Policy & { peak(): number } {
  const m = new Map<number, number>();
  let peak = 0;
  const purge = (now: number) => { for (const [k, exp] of m) { if (exp > now) break; m.delete(k); } };
  return {
    name: `TTL-only(${ttl})`,
    get: (k, now) => { purge(now); const e = m.get(k); return e !== undefined && e > now; },
    put: (k, now) => { m.delete(k); m.set(k, now + ttl); peak = Math.max(peak, m.size); },
    size: () => m.size,
    peak: () => peak,
  };
}

type Req = { key: number; user: boolean };
function buildTrace(kind: "zipf" | "scan" | "shift"): Req[] {
  const rand = mulberry32(2026);
  const pick = zipf(100_000, 0.95, rand);
  const out: Req[] = [];
  for (let day = 0; day < 4; day++) {
    // الـ shift: الترتيب بيتحرك كل يوم فالمنتجات النجوم بتتغير
    const offset = kind === "shift" ? day * 37_000 : 0;
    for (let i = 0; i < 100_000; i++) out.push({ key: ((pick() - 1 + offset) % 100_000) + 1, user: true });
    // الـ nightly scan: reporting job بيقرا 20 ألف منتج مرة واحدة ومحدش هيطلبهم تاني
    if (kind === "scan") for (let i = 0; i < 20_000; i++) out.push({ key: 200_000 + day * 20_000 + i, user: false });
  }
  return out;
}

function run(trace: Req[], p: Policy) {
  let hits = 0, reqs = 0, afterHits = 0, afterReqs = 0, sinceScan = Infinity;
  trace.forEach((r, t) => {
    const hit = p.get(r.key, t);
    if (!hit) p.put(r.key, t);
    if (!r.user) { sinceScan = 0; return; }
    reqs++;
    if (hit) hits++;
    if (sinceScan < 500) { afterReqs++; if (hit) afterHits++; sinceScan++; }
  });
  return { ratio: (100 * hits) / reqs, after: afterReqs ? (100 * afterHits) / afterReqs : NaN };
}

const CAP = 1000;
const factories: Array<() => Policy & { peak?: () => number }> = [
  () => lru(CAP), () => lfu(CAP), () => lfu(CAP, 25_000), () => fifo(CAP), () => ttlOnly(2000),
];
for (const kind of ["zipf", "scan", "shift"] as const) {
  const trace = buildTrace(kind);
  console.log(`--- trace ${kind}: ${trace.length} requests ---`);
  for (const f of factories) {
    const p = f();

    const peak = p.peak ? ` peak entries ${p.peak()}` : "";
    const a = Number.isNaN(after) ? "" : ` first 500 after each scan ${after.toFixed(1).padStart(5)}%`;
    console.log(p.name.padEnd(16), `hit ratio ${ratio.toFixed(1).padStart(5)}%${a}${peak}`);
  }
}
process.exit(0);

Part 5 — Read-through & write-through 🟡 Intermediateالجزء 5 — الـ read-through والـ write-through

English

Read-through moves the loader inside the cache layer: callers ask the cache and never touch the database. The logic is the same as cache-aside, but the ownership differs, so one class controls keys, TTLs and metrics, and callers can't forget to populate. The cost is coupling: the cache layer now knows how to load the data.

Write-through writes both stores synchronously on every write. Reads after a write are fresh, and the price is added write latency: in the run about 0.63 ms instead of 0.33 ms mean, because the request now waits for Postgres and Redis.

Order is the whole game. With the cache first, if the database then rejects the write (a check constraint here) the cache holds a value that never existed in your system: the run shows the cache returning -500 while the database says 1000. Every reader sees it until the TTL. Write the database first, because the database is where the rules live, then update the cache.

The cache write can still fail after a successful commit. In the last line of the run, Redis was down during the write: the database has the new price, the old value is still cached. Handle it by trying a DEL, counting the error and keeping a TTL as the safety net. The remaining races between concurrent writers are the next lesson's subject.

// الـ read-through: الـ class ده بيملك الـ loader، والكود اللي بيستخدمه مش عارف فيه DB أصلًا
class ReadThroughCache<T> {
  hits = 0;
  misses = 0;
  private readonly redis: Redis;
  private readonly ns: string;
  private readonly ttl: number;
  private readonly loader: (id: number) => Promise<T | null>;
  constructor(redis: Redis, ns: string, ttl: number, loader: (id: number) => Promise<T | null>) {
    this.redis = redis;
    this.ns = ns;
    this.ttl = ttl;
    this.loader = loader;
  }
  key(id: number) { return `${this.ns}:${id}`; }
  async get(id: number): Promise<T | null> {
    const hit = await this.redis.get(this.key(id));
    if (hit !== null) { this.hits++; return JSON.parse(hit) as T; }
    this.misses++;
    const value = await this.loader(id);
    if (value !== null) await this.redis.set(this.key(id), JSON.stringify(value), "EX", this.ttl);
    return value;
  }
}

الـ read-through بينقل الـ loader جوه طبقة الـ cache: اللي بيستخدمها بيسأل الـ cache بس وعمره ما بيلمس الداتابيز. المنطق هو هو الـ cache-aside، بس الملكية مختلفة، فـ class واحد بيتحكم في الـ keys والـ TTLs والـ metrics، ومحدش ينسى يملا الـ cache. التكلفة coupling: طبقة الـ cache بقت عارفة إزاي تجيب الداتا.

الـ write-through بيكتب في المكانين في نفس الوقت مع كل write. القراءة بعد الكتابة بتبقى طازة، والثمن latency زيادة: في التشغيل حوالي 0.63 ms بدل 0.33 ms في المتوسط، لأن الطلب بقى بيستنى Postgres و Redis.

الترتيب هو الموضوع كله. لو كتبت في الـ cache الأول والداتابيز رفضت (check constraint هنا)، الـ cache هيبقى فيه قيمة عمرها ما كانت موجودة في النظام: التشغيل بيوريك الـ cache بيرجّع -500 والداتابيز بتقول 1000. وكل اللي بيقرا هيشوفها لحد الـ TTL. اكتب في الداتابيز الأول لأن القواعد هناك، وبعدين حدّث الـ cache.

كتابة الـ cache ممكن تفشل برضه بعد commit ناجح. في آخر سطر من التشغيل، Redis كان واقع وقت الـ write: الداتابيز فيها السعر الجديد والقديم لسه في الـ cache. الحل: جرّب DEL، وعدّ الـ error، وسيب TTL كحزام أمان. والـ races بين كذا writer مع بعض هي موضوع الدرس الجاي.

فين هستخدمه في شغلي؟ تعديل سعر المنتج من لوحة التحكم: setPrice بيعمل UPDATE ... RETURNING في transaction، وبعدين SET بالصف الراجع من الداتابيز (مش من الـ input). كده الـ client مبيشوفش قيمة مرفوضة أبدًا، ولو Redis وقع السعر في الداتابيز صح والـ TTL القصير بينضّف الباقي.

Deleting the key on write is simpler and pays one miss afterwards. For most CRUD data, delete-on-write is the safer default; write-through earns its place when reads right after writes are common.

Part 6 — Write-behind & refresh-ahead 🟡 Intermediateالجزء 6 — الـ write-behind والـ refresh-ahead

English

Write-behind (write-back) acknowledges first and writes to the database later, in batches. The gain is dramatic for high-frequency, low-value updates: 5,000 article views took 5,000 database writes write-through and 10 batched upserts write-behind, and about 24 times less total time. The price is in the third line of the run: the process died by SIGKILL after acknowledging 3,737 views, and only 3,500 reached the database. 237 acknowledged increments were lost, and every one of those requests had already received a success response.

For view counters that's an acceptable error, and you'd say so in writing. For money, inventory or anything a customer was told succeeded, it is not. Moving the buffer to Redis with HINCRBY survives an app crash but not a Redis loss, and the helper Redis here runs with no persistence. If the increments must survive, you want a durable log, that is the outbox from the outbox lesson, and then you've left caching behind.

Refresh-ahead reloads a key in the background when a read finds it past some fraction of its TTL, so popular keys never expire under a user. In the virtual-time simulation at 80% of TTL, the hot-catalog p99 dropped from 54.5 ms to 1 ms with no wasted refreshes. On the long-tail catalog it barely moved, 94.8 to 92.6 ms, and 412 of 3,184 refreshes were never read. Refresh-ahead only helps keys that are read often enough to be read again, and it spends database capacity on predictions. It does not fix cold misses.

async function flush() {
  if (pending.size === 0) return;
  const ids = [...pending.keys()];
  const deltas = [...pending.values()];
  pending.clear();
  dbWrites++;
  await pool.query(
    `insert into article_views (article_id, views)
     select * from unnest($1::bigint[], $2::bigint[])
     on conflict (article_id) do update set views = article_views.views + excluded.views`,
    [ids, deltas]);
}

async function recordView(articleId: number) {
  if (mode === "write-through") {
    dbWrites++;
    await pool.query(
      `insert into article_views values ($1, 1)
       on conflict (article_id) do update set views = article_views.views + 1`, [articleId]);
  } else {
    pending.set(articleId, (pending.get(articleId) ?? 0) + 1);
    if (acked % 500 === 499) await flush();
  }
  // من اللحظة دي المستخدم خد 200 OK: الـ view اتحسبت من وجهة نظره
  acked++;
  if (killAt && acked === killAt) {
    writeFileSync("acked.txt", String(acked));
    // موت مفاجئ زي OOM kill أو crash: مفيش flush ومفيش shutdown hook
    process.kill(process.pid, "SIGKILL");
  }
}

type Entry = { storedAt: number; readsSince: number; fromRefresh: boolean; refreshingUntil: number };
const TTL = 30_000;

function run(refreshAt: number | null, keys: number, s: number) {
  const rand = mulberry32(4242);
  const pick = zipf(keys, s, rand);
  const latency = () => 30 + 20 * -Math.log(1 - rand());
  const cache = new Map<number, Entry>();
  const lat: number[] = [];
  let misses = 0, refreshes = 0, wasted = 0, now = 0;

  for (let i = 0; i < 60_000; i++) {
    now += 5;
    const k = pick();
    let e = cache.get(k);
    if (e && e.refreshingUntil > 0 && now >= e.refreshingUntil) {
      if (e.fromRefresh && e.readsSince === 0) wasted++;
      e = { storedAt: e.refreshingUntil, readsSince: 0, fromRefresh: true, refreshingUntil: 0 };
      cache.set(k, e);
    }
    if (e && now - e.storedAt < TTL) {
      e.readsSince++;
      lat.push(1);
      const trigger = refreshAt !== null && now - e.storedAt >= refreshAt * TTL;
      if (trigger && e.refreshingUntil === 0) {
        refreshes++;
        e.refreshingUntil = now + latency();
      }
      continue;
    }
    if (e && e.fromRefresh && e.readsSince === 0) wasted++;
    misses++;
    const l = latency();
    lat.push(1 + l);
    cache.set(k, { storedAt: now + l, readsSince: 0, fromRefresh: false, refreshingUntil: 0 });
  }
  for (const e of cache.values()) if (e.fromRefresh && e.readsSince === 0) wasted++;
  const r = stats(lat);
  return { mean: r.mean.toFixed(2), p50: r.p50.toFixed(1), p99: r.p99.toFixed(1), misses, refreshes, wasted };
}

بالعامية

الـ write-behind (write-back) بيرد الأول ويكتب في الداتابيز بعدين في batches. المكسب ضخم للـ updates الكتيرة قليلة القيمة: 5,000 view خدوا 5,000 كتابة DB في الـ write-through و10 batched upserts في الـ write-behind، ووقت إجمالي أقل بحوالي 24 مرة. الثمن في السطر التالت من التشغيل: الـ process مات بـ SIGKILL بعد ما رد على 3,737 view، و3,500 بس وصلوا الداتابيز. 237 increment ضاعوا، وكل الطلبات دي كانت خدت success.

في عدّاد المشاهدات ده error مقبول، وتكتبه صراحةً. أما الفلوس أو المخزون أو أي حاجة قولت للعميل إنها نجحت فلأ. لو نقلت الـ buffer لـ Redis بـ HINCRBY هينجو من crash الـ app بس مش من ضياع Redis، و Redis عندنا هنا من غير persistence أصلًا. لو الـ increments لازم تعيش، إنت محتاج durable log، يعني الـ outbox في درس الـ outbox، وساعتها إنت خرجت من موضوع الـ caching.

الـ refresh-ahead بيعيد تحميل الـ key في الخلفية لما قراءة تلاقيه عدّى نسبة من الـ TTL، فالمفاتيح الشعبية عمرها ما بتخلص قدام المستخدم. في الـ simulation بوقت افتراضي عند 80% من الـ TTL، الـ p99 للكتالوج السخن نزل من 54.5 ms لـ 1 ms من غير أي refresh ضايع. في الكتالوج اللي ذيله طويل بالكاد اتحرك، 94.8 لـ 92.6 ms، و412 من 3,184 refresh محدش قراهم. يعني الـ refresh-ahead بيفيد المفاتيح اللي بتتقرا كفاية بس، وبيصرف capacity من الداتابيز على توقعات، ومش بيحل الـ cold misses.

الاختيار: الجدول فوق. الـ cache-aside هو الـ default، والباقي إجابات لمشكلة محددة متقاسة.

فين هستخدمه في شغلي؟ زراير "إعجاب" و"عدد مشاهدات" الفيديو على موقع ضغطه عالي: write-behind كل ثانية أو كل 500 حدث، وقول للـ PM "ممكن نفقد ثواني من العدّ لو حصل crash". أما الرصيد والمخزون: أبدًا. والـ refresh-ahead يبقى في صفحة الـ top sellers اللي بتتقرا آلاف المرات في الدقيقة وحسابها غالي، ومتستخدمهوش على كتالوج 5 مليون منتج.
What breaks: write-behind without an accounting of loss The dangerous form isn't the batching, it's a team that doesn't know how much it can lose. Write down the maximum loss as "N events or T seconds", flush on SIGTERM, and accept that SIGKILL and power loss skip the handler entirely, as the run shows.
الخطر مش في الـ batching، الخطر في فريق مش عارف ممكن يخسر قد إيه. اكتب أقصى خسارة بصيغة "N حدث أو T ثانية"، واعمل flush على SIGTERM، واعرف إن SIGKILL وانقطاع الكهربا بيتخطوا الـ handler خالص، زي ما التشغيل بيوريك.
Interview question "Would you use write-behind for a shopping cart total or a payment?" → Not for a payment: a success response has to mean the money is recorded, and write-behind can lose acknowledged writes. For a cart I'd still usually write through, or store it in Redis as the primary with its durability limits understood. Write-behind fits counters and analytics, where a small loss is agreed in advance.
"هتستخدم write-behind في مجموع السلة أو في عملية دفع؟" ← الدفع لأ: رد الـ success لازم يعني إن الفلوس اتسجلت، والـ write-behind ممكن يضيّع كتابات اتقال إنها نجحت. السلة برضه غالبًا write-through، أو تخزّنها في Redis كمكان أساسي وإنت فاهم حدود الـ durability. الـ write-behind مناسب للعدّادات والـ analytics لما يكون الفقد الصغير متفق عليه مقدمًا.

// حل التمرين: أقل hit ratio يوصلني لمتوسط latency معين
export function requiredHitRatio(targetMs: number, cacheMs: number, dbMs: number): number {
  // من المعادلة: target = cache + (1 - h) * db
  if (targetMs < cacheMs) throw new Error("target is below the cache latency itself");
  const h = 1 - (targetMs - cacheMs) / dbMs;
  return Math.min(1, Math.max(0, h));
}

// حل التمرين: تنبيه لكل namespace واطي، بشرط يكون عنده طلبات كفاية عشان الرقم يتصدق
type Ns = { hits: number; misses: number };

export function lowHitRatio(byNs: Record<string, Ns>, minRatio: number, minReads: number) {
  return Object.entries(byNs).flatMap(([ns, s]) => {
    const reads = s.hits + s.misses;
    const ratio = reads === 0 ? 0 : s.hits / reads;
    return reads >= minReads && ratio < minRatio ? [{ ns, reads, ratio: Number((ratio * 100).toFixed(1)) }] : [];
  });
}

Cheat sheet · الخلاصة

  • A cache buys latency and load. Measure both: a primary-key lookup may gain almost no latency, while load falls hard.
  • Effective latency = h × cache + (1 − h) × (cache + db). A miss pays for both.
  • Levels: browser, CDN, app memory, Redis. Closer to the user is faster and harder to invalidate.
  • Read the miss rate: 90% to 99% is 10× fewer DB reads (measured 10.9×).
  • Track hit ratio per namespace: the global 82% hid a 0.5% cart.
  • Plan for cold start: hit ratio takes thousands of requests to recover.
  • Eviction: start with allkeys-lru; LFU beats it on stable popularity and scans, but needs decay when trends shift. TTL-only has no memory bound.
  • volatile-* without TTLs, or noeviction, means writes fail with OOM.
  • Write-through: database first, then cache from the returned row, then DEL and TTL on failure.
  • Write-behind loses acknowledged writes on a crash (237 here). Fine for views, never for money.
  • Refresh-ahead helps hot keys only; on long tails it mostly wastes refreshes.
بالعامية
  • الـ cache بيشتري latency و load. قيس الاتنين: الـ primary-key lookup ممكن مايكسبش latency تقريبًا، بس الـ load بيقع جامد.
  • الـ latency الفعلي = h × cache + (1 − h) × (cache + db). الـ miss بيدفع الاتنين.
  • المستويات: browser و CDN و app memory و Redis. كل ما تقرّب من المستخدم أسرع وأصعب في الـ invalidate.
  • بص على الـ miss rate: من 90% لـ 99% يعني 10 أضعاف أقل قراءات DB (اتقاس 10.9 مرة).
  • تابع الـ hit ratio لكل namespace: الـ 82% العام كان مخبّي cart عند 0.5%.
  • خطّط للـ cold start: الـ hit ratio بياخد آلاف الطلبات عشان يرجع.
  • الـ eviction: ابدأ بـ allkeys-lru. الـ LFU أحسن مع الشعبية الثابتة والـ scans، بس محتاج decay لما الشعبية تتغير. والـ TTL-only مالوش حد memory.
  • volatile-* من غير TTLs أو noeviction معناها الكتابة بتفشل بـ OOM.
  • الـ write-through: الداتابيز الأول، وبعدين الـ cache بالصف الراجع، ولو فشل DEL و TTL.
  • الـ write-behind بيضيّع كتابات اتقال إنها نجحت لو حصل crash (237 هنا). ينفع للـ views، وأبدًا للفلوس.
  • الـ refresh-ahead بيفيد المفاتيح السخنة بس، وعلى الذيل الطويل بيضيّع refreshes.
