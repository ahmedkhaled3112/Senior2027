Why this matters · ليه ده مهم

English

Both cases look like "store bytes and serve them", and both are really about one idea: separate the small, strongly consistent metadata from the huge, immutable blobs. File sync adds the hard question of what happens when two devices disagree. Video adds a long asynchronous pipeline and a bill where bandwidth dwarfs everything else. You will reuse these moves whenever a product has attachments, invoice PDFs, exports or media.

بالعامية

الحالتين شكلهم "خزّن bytes ورجّعها"، بس الفكرة الحقيقية في الاتنين واحدة: تفصل الـ metadata الصغيرة اللي لازم تبقى consistent عن الـ blobs الضخمة اللي مبتتغيرش. الـ sync بيزود سؤال صعب: لما جهازين يختلفوا، إيه اللي يحصل؟ والفيديو بيزود pipeline طويل asynchronous، وفاتورة الـ bandwidth فيها بتاكل أي حاجة تانية. هتستخدم نفس الحركات دي في أي product فيه attachments أو invoice PDFs أو exports أو media.

English

Model answer. Functional: upload, download, sync changes to every device, keep old versions, share folders, handle offline edits. Non-functional: durability first (losing a file is the unforgivable bug), sync visible on other devices in a few seconds, read-after-write for your own changes, and tolerate clients that are offline for days.

The estimate below shows the shape of the problem. Blobs are 420 PB, metadata is about 105 TB before indexes, which is 0.025% of the blob size. They need different stores: object storage for blobs, a sharded relational database for metadata, because metadata needs transactions and conditional updates. The commit rate is modest (about 3,500/s peak) and the file count is what hurts: 250 billion rows force sharding by owner or namespace.

The upload path uses presigned URLs so bytes never cross your API (taught in lesson 15, part 2): the client asks which chunks are missing, uploads only those directly to the store, then commits a new version in the metadata DB.

الإجابة النموذجية. الـ functional: upload، download، sync على كل الأجهزة، حفظ الإصدارات القديمة، مشاركة فولدرات، والتعديل وإنت offline. الـ non-functional: الـ durability أول حاجة (ضياع ملف ذنب ميتغفرش)، التغيير يوصل للأجهزة التانية في ثواني، read-after-write لتعديلاتك إنت، وتستحمل جهاز يفضل offline أيام.

الـ estimate بيوضح شكل المشكلة: الـ blobs حجمها 420 PB والـ metadata حوالي 105 TB قبل الـ indexes، يعني 0.025% من حجم الـ blobs. يبقى لازم تخزينين مختلفين: object storage للـ blobs، و relational DB متقسّم للـ metadata، لأن الـ metadata محتاجة transactions و conditional updates. الـ commits قليلة (حوالي 3,500 في الثانية في الـ peak)، بس عدد الملفات هو اللي بيوجع: 250 مليار صف بيجبرك تعمل sharding بالـ owner أو الـ namespace.

Part 2 — Chunking & dedup, real 🔴 Advancedالجزء 2 — الـ chunking والـ dedup على الحقيقي

English

Fixed-size chunking cuts a file every N bytes. Insert one byte at the start and every boundary shifts, so every chunk's hash changes and the whole file re-uploads. Content-defined chunking (CDC) picks boundaries from the bytes themselves: slide a rolling hash and cut where the hash matches a pattern. After an insert, boundaries realign within a chunk or two.

The implementation below is FastCDC-style: a Gear rolling hash (fp = (fp << 1) + gear[byte]), a skip over the minimum size so we never cut tiny chunks, and normalized chunking: a harder mask before the average size and an easier one after, which pulls sizes toward the average instead of the long tail plain CDC produces. We tested a 10 MiB file with a 64 KiB average. That size suits a small test file; the estimate in part 1 assumes 4 MB chunks, because metadata rows grow as chunks shrink.

Chunks are stored under their SHA-256, so the same content has one key and duplicates cost nothing. That gives dedup within a file, across versions and across users. It also creates a security duty: a client can upload wrong bytes under someone else's hash unless the server verifies them.

// الملف ده فيه fixed-size chunking و content-defined chunking بأسلوب FastCDC.
import { createHash } from "node:crypto";

export interface Chunk {
  offset: number;
  length: number;
  hash: string;
}

export function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// الجدول ده 256 رقم عشوائي ثابت، كل byte ليه قيمة بتدخل في الـ fingerprint.
const rand = mulberry32(42);
const GEAR = Uint32Array.from({ length: 256 }, () => (rand() * 2 ** 32) >>> 0);

export const sha256 = (bytes: Uint8Array): string => createHash("sha256").update(bytes).digest("hex");

function makeChunk(data: Buffer, offset: number, length: number): Chunk {
  return { offset, length, hash: sha256(data.subarray(offset, offset + length)) };
}

export function fixedChunks(data: Buffer, size: number): Chunk[] {
  const chunks: Chunk[] = [];
  for (let offset = 0; offset < data.length; offset += size) {
    chunks.push(makeChunk(data, offset, Math.min(size, data.length - offset)));
  }
  return chunks;
}

// الدالة دي بترجع الـ mask اللي بيبص على أعلى n bits، ودي اللي بتعتمد على آخر 32 byte.
const topBits = (n: number): number => ((2 ** n - 1) * 2 ** (32 - n)) >>> 0;

export function cdcChunks(data: Buffer, avg = 64 * 1024): Chunk[] {
  const min = avg / 4;
  const max = avg * 4;
  const bits = Math.round(Math.log2(avg));
  // قبل الـ avg الشرط أصعب وبعده أسهل، وده اللي بيقرّب الأحجام من المتوسط (normalized chunking).
  const hardMask = topBits(bits + 2);
  const easyMask = topBits(bits - 2);

  const chunks: Chunk[] = [];
  let start = 0;
  while (start < data.length) {
    const remaining = data.length - start;
    let cut = remaining;
    if (remaining > min) {
      const limit = Math.min(remaining, max);
      const normal = Math.min(avg, limit);
      let fp = 0;
      let i = min;
      let found = false;
      for (; i < normal; i++) {
        fp = ((fp << 1) + GEAR[data[start + i]!]!) >>> 0;
        if ((fp & hardMask) === 0) { found = true; break; }
      }
      if (!found) {
        for (; i < limit; i++) {
          fp = ((fp << 1) + GEAR[data[start + i]!]!) >>> 0;
          if ((fp & easyMask) === 0) { found = true; break; }
        }
      }
      cut = found ? i + 1 : limit;
    }
    chunks.push(makeChunk(data, start, cut));
    start += cut;
  }
  return chunks;
}

export function seededBytes(size: number, seed: number): Buffer {
  const next = mulberry32(seed);
  const out = Buffer.allocUnsafe(size);
  for (let i = 0; i < size; i += 4) {
    const word = (next() * 2 ** 32) >>> 0;
    // الـ loop بيكتب 4 bytes في المرة، والأخيرة ممكن تقع بره الحجم.
    for (let k = 0; k < 4 && i + k < size; k++) out[i + k] = (word >>> (8 * k)) & 0xff;
  }
  return out;
}

    return true;
  } catch {

// الدالة دي الـ API: بترجع presigned URL للـ chunks الناقصة بس.
async function planUpload(hashes: string[]) {
  const unique = [...new Set(hashes)];
  const missing: { hash: string; url: string }[] = [];
  for (const hash of unique) {
    if (await exists(hash)) continue;
    const url = await getSignedUrl(s3, new PutObjectCommand({ Bucket, Key: keyOf(hash) }), { expiresIn: 300 });
    missing.push({ hash, url });
  }
  return { unique: unique.length, missing };
}

// الدالة دي الـ client: بيرفع اللي الـ API طلبه ويرجّع عدد الـ bytes.
async function uploadFile(file: Buffer, chunks: Chunk[]) {
  const byHash = new Map(chunks.map((c) => [c.hash, c]));
  const plan = await planUpload(chunks.map((c) => c.hash));
  let bytes = 0;
  for (const { hash, url } of plan.missing) {
    const c = byHash.get(hash)!;
    const body = file.subarray(c.offset, c.offset + c.length);
    const res = await fetch(url, { method: "PUT", body: Uint8Array.from(body) });
    if (res.status !== 200) throw new Error(`upload failed: ${res.status}`);
    bytes += c.length;
  }
  return { total: chunks.length, unique: plan.unique, uploaded: plan.missing.length, kib: Math.round(bytes / 1024) };
}

async function download(hash: string): Promise<Buffer> {
  const res = await s3.send(new GetObjectCommand({ Bucket, Key: keyOf(hash) }));
  return Buffer.from(await res.Body!.transformToByteArray());
}

Part 3 — Sync & conflicts 🔴 Advancedالجزء 3 — الـ sync والـ conflicts

English

Every commit is a compare-and-set on the row's version: UPDATE files SET version = version + 1 ... WHERE id = $1 AND version = $base. Zero rows updated means someone got there first. Dropbox-style policy: don't merge, keep both, by creating a conflicted copy beside the original so a human decides. Merging arbitrary binaries isn't possible; merging text silently is how people lose work.

Each owner has its own sequence, bumped inside the same transaction as the commit. A global identity column would be wrong here: two transactions can take ids 5 and 6, commit in the order 6 then 5, and a device that read up to 6 would never see 5. A per-namespace counter is serialized by the row lock on the namespace, so the cursor order equals the commit order.

Notifications only say "something changed, pull". They go after the commit over Redis pub/sub, which is at-most-once: a device that is offline misses it, and that is fine, because the source of truth is changes plus the device's cursor. The run below shows a device that subscribes late and still receives everything by pulling. Delta sync is the chunk list: the device diffs the new list against what it has, and downloads only what's missing.

Run it with your own throwaway servers: PG_PORT=5544 REDIS_PORT=6380 node sync-conflict.ts. The guard refuses default ports on purpose, so a lab script never touches a real database.

// العداد ده per-namespace وبيتزود جوه نفس الـ transaction، فالترتيب هو ترتيب الـ commit.
async function nextSeq(tx: Tx, owner: number): Promise<number> {
  const r = await tx.query(`update namespaces set last_seq = last_seq + 1 where owner_id = $1 returning last_seq`, [owner]);
  return Number(r.rows[0].last_seq);
}

interface Edit { owner: number; fileId: number; path: string; baseVersion: number; chunks: string[]; device: string }
type Result = { kind: "updated" | "conflicted"; fileId: number; version: number; path: string; seq: number };

async function commit(e: Edit): Promise<Result> {
  const tx = await db.connect();
  try {
    await tx.query("begin");
    // الشرط هنا هو الـ compare-and-set كله: مين جاي على آخر version بس اللي بيكسب.
    const up = await tx.query(
      `update files set version = version + 1, chunk_hashes = $1, updated_by = $2
       where id = $3 and version = $4 returning version`,
      [e.chunks, e.device, e.fileId, e.baseVersion],
    );
    let result: Result;
    if (up.rowCount === 1) {
      const seq = await nextSeq(tx, e.owner);
      const version = up.rows[0].version as number;
      await tx.query(`insert into changes values ($1, $2, $3, $4)`, [e.owner, seq, e.fileId, version]);
      result = { kind: "updated", fileId: e.fileId, version, path: e.path, seq };
    } else {
      // السلوك ده زي Dropbox: مفيش merge، ملف جديد بجانب الأصلي والإنسان يقرر.
      const seq = await nextSeq(tx, e.owner);
      const copyPath = e.path.replace(/(\.\w+)$/, ` (conflicted copy from ${e.device} #${seq})$1`);
      const ins = await tx.query(
        `insert into files (owner_id, path, chunk_hashes, updated_by) values ($1, $2, $3, $4) returning id, version`,
        [e.owner, copyPath, e.chunks, e.device],
      );
      await tx.query(`insert into changes values ($1, $2, $3, $4)`, [e.owner, seq, ins.rows[0].id, 1]);
      result = { kind: "conflicted", fileId: Number(ins.rows[0].id), version: 1, path: copyPath, seq };
    }
    await tx.query("commit");
    // الـ notification بييجي بعد الـ commit، وبيقول "اسحب" بس، مش بيشيل الـ data.
    await pub.publish(`sync:${e.owner}`, String(result.seq));
    return result;
  } catch (err) {
    await tx.query("rollback");
    throw err;
  } finally {
    tx.release();
  }
}

Part 5 — Transcoding DAG 🔴 Advancedالجزء 5 — الـ transcoding DAG

English

A transcoding pipeline is a DAG: probe the source, then renditions in parallel, package them, then publish. Topological sort is taught in CS lesson 07, part 4; here the interesting part is failure. Three properties matter: tasks run in parallel when their dependencies are done, a failed task doesn't redo the finished ones, and a crashed orchestrator resumes from saved state.

The executor below writes state after every task (temp file then rename, so a crash can't leave half-written JSON). The run has three chapters: a hard crash just after t720 finishes, then a resume where t480 fails transiently twice and t360 fails permanently, then a resume after fixing the 360p settings. Tasks here are stand-ins that sleep and log, no real video is processed, and the real ffmpeg command below is labelled Not run here.

Look at the final counts. t720 ran once, and t1080 ran twice: it was in flight when the process died, so its work was lost. That is at-least-once execution. Real tasks must be idempotent, writing to a deterministic key like output/video-42/720p/seg_0001.ts, so a rerun overwrites instead of duplicating.

// الملف ده DAG executor صغير: ترتيب، توازي، retries، واستكمال بعد crash.
import { existsSync, readFileSync, renameSync, writeFileSync } from "node:fs";

export interface Task {
  id: string;
  deps: string[];
  retries: number;
  run: (attempt: number) => Promise<void>;
}

type Status = "done" | "failed";
type State = Record<string, { status: Status; attempts: number }>;

// الـ Kahn بيرمي error لو فيه cycle، بدل ما الـ pipeline يتعلق للأبد.
export function topoOrder(tasks: Task[]): string[] {
  const indegree = new Map(tasks.map((t) => [t.id, t.deps.length]));
  const dependents = new Map<string, string[]>();
  for (const t of tasks) {
    for (const d of t.deps) dependents.set(d, [...(dependents.get(d) ?? []), t.id]);
  }
  const queue = tasks.filter((t) => t.deps.length === 0).map((t) => t.id);
  const order: string[] = [];
  while (queue.length > 0) {
    const id = queue.shift()!;
    order.push(id);
    for (const next of dependents.get(id) ?? []) {
      const left = indegree.get(next)! - 1;
      indegree.set(next, left);
      if (left === 0) queue.push(next);
    }
  }
  if (order.length !== tasks.length) throw new Error("cycle in DAG");
  return order;
}

// الكتابة في ملف مؤقت وبعدين rename عشان crash في النص ميسيبش state نصه مكتوب.
function saveState(path: string, state: State): void {
  writeFileSync(`${path}.tmp`, JSON.stringify(state));
  renameSync(`${path}.tmp`, path);
}

export interface RunOptions {
  statePath: string;
  concurrency: number;
  retryDelayMs: number;
  onDone?: (id: string) => void;
}

export async function runDag(tasks: Task[], opts: RunOptions) {
  topoOrder(tasks);
  const loaded: State = existsSync(opts.statePath) ? JSON.parse(readFileSync(opts.statePath, "utf8")) : {};
  // الـ tasks اللي فشلت قبل كده بترجع للـ pending وتاخد فرصة تانية في الـ run ده.
  const state: State = Object.fromEntries(Object.entries(loaded).filter(([, v]) => v.status === "done"));
  const skipped = Object.keys(state);
  const running = new Map<string, Promise<void>>();

  async function execute(task: Task): Promise<void> {
    let attempt = 0;
    while (true) {
      attempt++;
      try {
        await task.run(attempt);
        state[task.id] = { status: "done", attempts: attempt };
        break;
      } catch {
        if (attempt > task.retries) {
          state[task.id] = { status: "failed", attempts: attempt };
          break;
        }
        // الـ backoff هنا exponential، والـ transient failure بيتحل من غير ما يبوظ الـ pipeline.
        await new Promise((r) => setTimeout(r, opts.retryDelayMs * 2 ** (attempt - 1)));
      }
    }
    saveState(opts.statePath, state);
    opts.onDone?.(task.id);
  }

  while (true) {
    const ready = tasks.filter(
      (t) => !state[t.id] && !running.has(t.id) && t.deps.every((d) => state[d]?.status === "done"),
    );
    for (const task of ready) {
      if (running.size >= opts.concurrency) break;
      const p = execute(task).finally(() => running.delete(task.id));
      running.set(task.id, p);
    }
    if (running.size === 0) break;
    await Promise.race(running.values());
  }

  const blocked = tasks.filter((t) => !state[t.id]).map((t) => t.id);
  return { state, skipped, blocked };
}

export function masterPlaylist(renditions: Rendition[]): string {
  const lines = ["#EXTM3U", "#EXT-X-VERSION:6", "#EXT-X-INDEPENDENT-SEGMENTS"];

      `${r.name}/index.m3u8`,
    );

}

export function mediaPlaylist(durations: number[]): string {
  const target = Math.ceil(Math.max(...durations));
  const lines = ["#EXTM3U", "#EXT-X-VERSION:6", `#EXT-X-TARGETDURATION:${target}`, "#EXT-X-MEDIA-SEQUENCE:0", "#EXT-X-PLAYLIST-TYPE:VOD"];
  durations.forEach((d, i) => lines.push(`#EXTINF:${d.toFixed(3)},`, `seg_${String(i).padStart(4, "0")}.ts`));
  lines.push("#EXT-X-ENDLIST");
  return lines.join("\n") + "\n";
}

export function checkMedia(text: string): { ok: boolean; segments: number } {
  const target = Number(/#EXT-X-TARGETDURATION:(\d+)/.exec(text)?.[1]);
  const durations = [...text.matchAll(/#EXTINF:([\d.]+),/g)].map((m) => Number(m[1]));
  return { ok: durations.every((d) => Math.round(d) <= target), segments: durations.length };
}

Part 6 — Adaptive bitrate 🔴 Advancedالجزء 6 — الـ adaptive bitrate

English

The server doesn't choose quality; the player does. It downloads a segment, measures throughput, and picks the next rendition. HLS (Apple, RFC 8216) and DASH (MPEG standard) are the same idea with different manifest formats, and CMAF lets one set of segments serve both. HTTP segments mean any CDN can serve them with no special protocol.

The simulation runs 200 seeded sessions over a bandwidth trace with sudden dips. A fixed 1080p stream stalls badly (44 rebuffers per session), because the network often can't sustain 5 Mbps. Fixed 480p barely stalls but stays at 1 Mbps. Throughput-based selection stays around 2 Mbps with 0.13 rebuffers per session. Adding a buffer guard cuts rebuffers a little more and costs some extra quality switches. The cost of playing it safe here is switches, and users notice those too, which is why real players add hysteresis.

The second calculator answers "which videos go on the CDN?". A video earns its edge slot only if the bandwidth it saves is worth more than storing it at every site. With these assumptions that point is about 69 views per month, reached around rank 1.35 million. Below that, serve from origin or pull through on demand. Total cost is lowest at 1M videos on the edge, and the 5M and 20M rows show that storing the long tail costs more than it saves.

function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

const LADDER = [0.3, 0.6, 1, 2.5, 5];
const SEGMENT_SECONDS = 4;
const SEGMENTS = 75;
const MAX_BUFFER = 30;

// الـ trace ده per-second، بيتحرك واحدة واحدة وفيه هبوط زي نفق أو زحمة.
function bandwidthTrace(seed: number, seconds: number): number[] {
  const rand = mulberry32(seed);
  const trace: number[] = [];
  let mbps = 3 + rand() * 3;
  let dip = 0;
  for (let i = 0; i < seconds; i++) {
    mbps = Math.max(0.5, Math.min(10, mbps * (0.92 + rand() * 0.16)));
    if (dip === 0 && rand() < 0.012) dip = 8 + Math.floor(rand() * 15);
    trace.push(dip > 0 ? Math.max(0.25, mbps * 0.12) : mbps);
    if (dip > 0) dip--;
  }
  return trace;
}

type Choose = (history: number[], buffer: number) => number;

function play(trace: number[], choose: Choose) {
  let time = 0;
  let buffer = 0;
  let started = false;
  let stalled = false;
  let rebufferEvents = 0;
  let rebufferSeconds = 0;
  let switches = 0;
  let last = -1;
  let totalBitrate = 0;
  const history: number[] = [];

  for (let seg = 0; seg < SEGMENTS; seg++) {
    const level = choose(history, buffer);
    if (last >= 0 && level !== last) switches++;
    last = level;
    let megabits = LADDER[level]! * SEGMENT_SECONDS;
    const startedAt = time;
    // الحد 1e-9 ده عشان أخطاء الـ floating point متعلقش الـ loop للأبد.
    while (megabits > 1e-9) {
      const sec = Math.floor(time);
      const rate = trace[Math.min(sec, trace.length - 1)]!;
      const slice = Math.max(1e-6, Math.min(sec + 1 - time, megabits / rate));
      megabits -= rate * slice;
      time += slice;
      if (started) {
        const played = Math.min(buffer, slice);
        buffer -= played;
        if (played < slice) {
          if (!stalled) { stalled = true; rebufferEvents++; }
          rebufferSeconds += slice - played;
        }
      }
    }
    history.push((LADDER[level]! * SEGMENT_SECONDS) / (time - startedAt));
    buffer += SEGMENT_SECONDS;
    stalled = false;
    if (seg === 1) started = true;
    totalBitrate += LADDER[level]!;
    // لو الـ buffer عدّى السقف، اللاعب بيستنى لحد ما ينزل قبل ما ينزّل تاني.
    if (buffer > MAX_BUFFER) {
      const wait = buffer - MAX_BUFFER;
      time += wait;
      buffer -= wait;
    }
  }
  return { avgMbps: totalBitrate / SEGMENTS, rebufferEvents, rebufferSeconds, switches };
}

const fixed = (level: number): Choose => () => level;

// الأسلوب ده بياخد الـ harmonic mean لآخر 5 segments ويضرب في 0.8 كـ safety.
const throughputBased: Choose = (history) => {
  if (history.length === 0) return 1;
  const recent = history.slice(-5);
  const harmonic = recent.length / recent.reduce((s, x) => s + 1 / x, 0);
  const budget = harmonic * 0.8;
  let level = 0;
  LADDER.forEach((mbps, i) => { if (mbps <= budget) level = i; });
  return level;
};

// الإضافة دي بتنزّل الجودة خطوة لو الـ buffer قليل، حتى لو الشبكة باين عليها كويسة.
const throughputWithBuffer: Choose = (history, buffer) => {
  const base = throughputBased(history, buffer);
  return buffer < 8 ? Math.max(0, base - 1) : base;
};

Part 7 — View counting & review 🔴 Advancedالجزء 7 — عدّ المشاهدات والمراجعة

English

A view counter doesn't need exact numbers, it needs cheap ones. HyperLogLog (explained in CS lesson 10, part 6) counts distinct viewers in about 12 KB no matter how many there are. We loaded 1,000,000 real users: the estimate was off by 0.03% in this run (Redis documents a standard error of 0.81%, so don't expect this luck), and it used 12,341 bytes against 37,277,585 bytes for a real set, about 3,000×.

Counters go through a stream. Writing one INCR per view would mean the hot video's key gets millions of writes. A consumer reads batches, aggregates per video, and writes one increment per video per batch. The trap is the crash window: if the worker dies after HINCRBY and before XACK, the batch is redelivered and counted twice, shown below. Wrapping both in MULTI makes them one atomic step.

Fraud is the other half: without a filter, a script inflates a counter. A short-lived SET ... NX EX per viewer and video drops repeats. Real systems add device and account signals and review anomalies offline, and they keep two numbers: a fast approximate one shown publicly, and an audited one used for monetization.

عدّاد المشاهدات مش محتاج رقم مظبوط، محتاج رقم رخيص. الـ HyperLogLog (متشرح في الدرس 10 من CS، الجزء 6) بيعد الـ distinct viewers في حوالي 12 KB مهما كان العدد. حطينا مليون user حقيقي: التقدير طلع غلطان بـ 0.03% في الـ run ده (الـ standard error الموثق في Redis هو 0.81%، فمتتوقعش الحظ ده على طول)، وأخد 12,341 byte مقابل 37,277,585 byte لـ set حقيقي، يعني حوالي 3,000 ضعف.

الـ counters بتعدّي على stream. INCR لكل مشاهدة يعني key الفيديو الـ hot هياخد ملايين الكتابات. الـ consumer يقرا batches، يجمّع لكل فيديو، ويكتب increment واحد لكل فيديو في الـ batch. الفخ هو نافذة الـ crash: لو الـ worker مات بعد HINCRBY وقبل XACK، الـ batch بترجع وتتحسب مرتين، زي ما التشغيل بيوريك. وMULTI بيخلي الاتنين خطوة atomic واحدة.

النص التاني هو الـ fraud: من غير فلتر، أي script بيضخّم العداد. SET ... NX EX قصير لكل viewer وفيديو بيرمي التكرار. الأنظمة الحقيقية بتضيف إشارات عن الجهاز والحساب وبتراجع الشاذ offline، وبتفضّل رقمين: رقم سريع تقريبي بيتعرض للناس، ورقم مراجَع يستخدم في الفلوس.

فين هستخدمه في شغلي؟ صفحة dashboard عايزة "عدد الـ users الفريدين اللي عملوا checkout النهارده": PFADD checkout:2026-11-09 userId بدل SELECT COUNT(DISTINCT) على جدول ضخم. ولو بتعد events كتير، بدل UPDATE counters SET n = n + 1 لكل event (row lock وسط الزحمة)، جمّعهم في stream أو queue وحدّث كل batch في transaction واحد.

Common mistakes · غلطات شائعة

❌ Fixed-size chunks for a sync product 
// الغلط: أي byte زيادة في الأول بيزحزح كل الحدود
const chunks = fixedChunks(file, 64 * 1024);
// → 161/161 chunks changed after inserting 1 byte
✅ Content-defined boundaries 
// الحل: الحدود من المحتوى فبترجع تتظبط بعد التعديل
const chunks = cdcChunks(file, 64 * 1024);
// → 1/146 chunks changed after inserting 1 byte
بالعامية

❌ الـ fixed-size بيبان إنه شغال في الاختبار اللي بيعدّل في آخر الملف، وبيقع مع أي insert في الأول: 161 من 161 chunk اتغيروا، يعني الملف كله اترفع تاني. ✅ الـ CDC بيحط الحدود من المحتوى، فبعد نفس التعديل chunk واحدة بس اتغيرت من 146.

❌ Last write wins on commit 
-- الغلط: الجهاز التاني بيمسح شغل الأول من غير ما حد يعرف
UPDATE files SET chunk_hashes = $1 WHERE id = $2;
✅ Compare-and-set, then a conflicted copy 
-- الحل: صفر صفوف معناها حد سبقك، فاعمل نسخة conflicted
UPDATE files SET chunk_hashes = $1, version = version + 1
WHERE id = $2 AND version = $3;
بالعامية

❌ الـ update من غير شرط بيخلي جهاز يمسح شغل جهاز تاني وهو ساكت. ✅ WHERE version = $3 بيحوّل الـ commit لـ compare-and-set: صفر صفوف معناها حد سبقك، فتعمل conflicted copy وتسيب الإنسان يقرر. في تجربتنا 12 جهاز من نفس الـ base، واحد بس كسب.

❌ Trusting the client's hash 
// الغلط: أي client يقدر يرفع bytes غلط تحت hash مش بتاعه
if (await exists(hash)) return;
await store.put(hash, clientBytes);
✅ Verify before the commit 
// الحل: الـ commit بيعيد الحساب، أو الـ PUT بيتوقّع بـ checksum
const stored = await download(hash);
if (sha256(stored) !== hash) throw new Error("hash mismatch");
بالعامية

❌ لو صدّقت الـ hash اللي الـ client بيبعته من غير تحقق، حد ممكن يرفع bytes مسمومة تحت hash ملف ناس تانية (الـ stand-in عندنا قبلها بـ 200). ✅ أعد حساب الـ hash وقت الـ commit قبل ما الـ chunk تبقى متاحة، أو خلي الـ PUT يتوقّع بـ checksum زي ما AWS بتوفر.

❌ Transcoding inside the request 
// الغلط: request بيفضل مفتوح ساعات والـ crash بيبدأ من الأول
app.post("/videos/:id/complete", async (req, res) => {
  await transcodeEverything(req.params.id);
  res.json({ status: "ready" });
});
✅ Accept, enqueue, resume 
// الحل: الـ API يرد 202 والـ DAG يكمّل من الـ state بتاعه
app.post("/videos/:id/complete", async (req, res) => {
  await queue.add("transcode", { videoId: req.params.id });
  res.status(202).json({ status: "processing" });
});
بالعامية

❌ لو عملت transcode جوه الـ request، الـ HTTP connection هتفضل مفتوحة ساعات، وأي restart هيبدأ من الأول. ✅ الـ API يسجّل الشغل ويرد 202، والـ DAG orchestrator يكمّل من الـ state، زي تجربة الـ crash في الجزء 5.

3. Stuck workers 🔴 hard A worker hangs on a broken segment. Add a per-task deadline so a task that exceeds it counts as a failed attempt, without changing the executor.

Solution · الحل 
// الحل ده بيلف أي task بمهلة: لو عدّت، الـ task بتعتبر فشلت وتدخل في الـ retries.
import { rmSync } from "node:fs";
import { runDag, type Task } from "./dag.ts";

function withTimeout(task: Task, limitMs: number): Task {
  return {
    ...task,
    run: async (attempt) => {
      let timer: NodeJS.Timeout | undefined;
      const deadline = new Promise<never>((_, reject) => {
        timer = setTimeout(() => reject(new Error(`timeout after ${limitMs} ms`)), limitMs);
      });
      try {
        await Promise.race([task.run(attempt), deadline]);
      } finally {
        clearTimeout(timer);
      }
    },
  };
}

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
const statePath = "ex-timeout.state.json";
rmSync(statePath, { force: true });

// الـ task دي بتعلق أول مرة بس، زي worker ماسك على segment بايظة.
const hang: Task = {
  id: "t720",
  deps: [],
  retries: 2,
  run: async (attempt) => {
    await sleep(attempt === 1 ? 2000 : 10);
  },
};

const { state } = await runDag([withTimeout(hang, 100)], { statePath, concurrency: 1, retryDelayMs: 10 });
console.log(state);
rmSync(statePath, { force: true });
process.exit(0);

Cheat sheet · الخلاصة

  • Separate metadata (small, strongly consistent, sharded by owner) from blobs (huge, immutable, object store).
  • Fixed chunks re-upload everything after an insert (161 of 161); CDC changes about one chunk (1 of 146).
  • Content-addressed chunks dedup within files, across versions and across users; always verify the hash server-side.
  • Commit is compare-and-set on version; a loser becomes a conflicted copy, never a silent overwrite.
  • Sequence per namespace in the same transaction, so cursor order equals commit order.
  • Notifications are hints (at-most-once is fine); the change log plus cursor is the truth.
  • Global dedup leaks existence across tenants; dedup per tenant or decouple it from the response.
  • Video: egress dominates storage (48× here); the CDN is the product.
  • Transcoding is a DAG: parallel tasks, per-task state, deterministic output keys, at-least-once execution.
  • Align keyframes across renditions, or switching between them breaks.
  • The player chooses quality; a throughput estimate plus a buffer guard beats any fixed bitrate.
  • HLL for distinct viewers (12 KB, 0.81% standard error); batch counters and MULTI the ack.
بالعامية
  • افصل الـ metadata (صغيرة، consistent، متقسمة بالـ owner) عن الـ blobs (ضخمة، immutable، في object store).
  • الـ fixed chunks بترفع كل حاجة تاني بعد insert (161 من 161)؛ الـ CDC بيغير chunk تقريبًا واحدة (1 من 146).
  • الـ chunks بالـ hash بتعمل dedup جوه الملف وبين الإصدارات والـ users؛ ودايمًا اتأكد من الـ hash على الـ server.
  • الـ commit هو compare-and-set على version؛ اللي خسر بيبقى conflicted copy، مش overwrite ساكت.
  • sequence لكل namespace في نفس الـ transaction، فترتيب الـ cursor هو ترتيب الـ commit.
  • الـ notifications مجرد إشارات (at-most-once عادي)؛ الـ change log مع الـ cursor هو الحقيقة.
  • الـ global dedup بيكشف وجود ملف بين الـ tenants؛ اعمل dedup لكل tenant أو افصله عن الرد.
  • الفيديو: الـ egress أكبر من التخزين (48 ضعف هنا)؛ الـ CDN هو المنتج.
  • الـ transcoding هو DAG: tasks بالتوازي، state لكل task، keys ثابتة للناتج، و at-least-once.
  • نظبط الـ keyframes بين الـ renditions، وإلا التنقل بينهم بيتكسر.
  • الـ player هو اللي بيختار الجودة؛ تقدير الـ throughput مع buffer guard أحسن من أي bitrate ثابت.
  • الـ HLL للـ distinct viewers (12 KB و 0.81% standard error)؛ جمّع الـ counters وخلي الـ ack في MULTI.
