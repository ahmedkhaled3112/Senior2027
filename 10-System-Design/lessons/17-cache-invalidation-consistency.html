Why this matters · ليه ده مهم

English

A cache is a second copy of your data with no shared transaction with the first copy, so the two will disagree. The only design question is how long they disagree and who can see it. Most "the price is wrong on the site" incidents come from one of the failures in this lesson: a missed event, a delete in the wrong order, a refill from a lagging replica, or a value that should never have been cached. In a system design interview, "and how do you keep the cache consistent?" is the follow-up that separates people who have drawn a Redis box from people who have run one.

بالعامية

الـ cache نسخة تانية من الـ data، ومفيش transaction مشترك بينها وبين الـ DB، فالاتنين هيختلفوا أكيد. السؤال الوحيد في التصميم: هيختلفوا قد إيه ومين هيشوف الاختلاف؟ أغلب حوادث "السعر غلط على الموقع" جاية من حاجة من اللي في الدرس ده: event ضاع، delete في الترتيب الغلط، refill من replica متأخرة، أو قيمة مكانش المفروض تتعمل لها cache أصلًا. وفي الـ system design interview، سؤال "وهتخلي الـ cache consistent إزاي؟" هو اللي بيفرّق بين اللي رسم مربع Redis وبين اللي شغّله بجد.

Part 1 — TTL vs events 🟡 Intermediateالجزء 1 — الـ TTL قصاد الـ events

English

TTL only. A product price changes in Postgres and nobody tells the cache. Each key stays wrong for whatever TTL it has left, so across keys filled at different times the staleness is spread between 0 and the TTL: mean about TTL/2, worst case the full TTL. Below, 40 real keys with a 3 s TTL (scaled so the run takes seconds, not minutes) measured a mean of ≈1.42 s and a max of ≈2.94 s. At a 60 s TTL those same ratios mean ≈28 s on average and ≈59 s at worst. You can state that number to the product team, and that is TTL's strength.

Events. When one shared Redis is the only cache, the writer can just DEL the key. Events matter once there are copies you can't reach with one DEL: an in-process L1 in every app instance, or a cache owned by another service. Redis Pub/Sub is fire-and-forget: messages go only to subscribers connected at that moment, with no replay and no error for anyone who missed one. Below, instance B's connection blips, PUBLISH reaches 1 subscriber of 2, B reconnects, and B keeps serving the old price with no signal that anything happened.

The reliable path is a log. Put the change in a durable stream and let every instance track its own position. With Redis Streams each instance needs its own consumer group, because a group delivers each entry to only one of its consumers. Below, instance B is offline, comes back and reads the entry it missed. The same run shows the trap: with one shared group, A gets the entry and B gets nothing, so B stays stale. The event must also come from the database's commit, not from application code that can crash just after it: that is the outbox or CDC, taught in section 07 · 3.4. The Redis side of event-based deletes is in section 07 · 3.5, part 5.

Keep the TTL anyway, always. Streams get trimmed (MAXLEN), consumers have bugs, a deploy can skip a range. Events make staleness short in the normal case, and the TTL is the upper bound for every abnormal case. An event-driven cache with no TTL turns one lost message into a permanently wrong price.

export function requirePort(name: string): number {
  const raw = process.env[name] ?? "";
  const n = Number(raw);
  if (!/^\d+$/.test(raw) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing ${name}='${raw}'`);
  }
  return n;
}

export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

export const percentile = (xs: number[], p: number): number => {
  const s = [...xs].sort((a, b) => a - b);
  return s[Math.min(s.length - 1, Math.floor((p / 100) * s.length))] ?? 0;
};

async function readPrice(id: number): Promise<number> {
  const key = `product:${id}:price`;
  const hit = await redis.get(key);
  if (hit !== null) return Number(hit);
  const { rows } = await db.query<{ price: number }>("SELECT price FROM products WHERE id = $1", [id]);
  await redis.set(key, String(rows[0]!.price), "PX", TTL_MS);
  return rows[0]!.price;
}

// كل app instance عنده L1 في الـ memory، والـ Map دي بتتمسح لما يوصله event
class AppInstance {
  readonly l1 = new Map<string, number>();
  readonly name: string;
  constructor(name: string) {
    this.name = name;
  }
  drop(key: string) {
    this.l1.delete(key);

async function drain(app: AppInstance, group: string): Promise<number> {
  const res = (await redis.xreadgroup("GROUP", group, app.name, "COUNT", 100, "STREAMS", stream, ">")) as Entries;
  const entries = res?.[0]?.[1] ?? [];
  for (const [id, fields] of entries) {
    app.drop(fields[1]!);
    await redis.xack(stream, group, id);
  }
  return entries.length;
}

بالعامية

الـ TTL لوحده. السعر اتغيّر في Postgres ومحدش قال للـ cache. كل key هيفضل غلط على قد الـ TTL اللي فاضل له، ولأن الـ keys اتملت في أوقات مختلفة، الـ staleness بتتوزع من صفر للـ TTL كله: المتوسط حوالي TTL/2 والأسوأ TTL كامل. فوق، 40 key حقيقيين بـ TTL 3 ثواني (مصغّر عشان التجربة تخلص في ثواني مش دقايق) طلّعوا متوسط ≈1.42 ثانية وأقصى ≈2.94. عند TTL 60 ثانية نفس النسب معناها متوسط ≈28 ثانية وأسوأ حالة ≈59. الرقم ده تقدر تقوله للـ product team، ودي قوة الـ TTL.

الـ events. لو عندك Redis واحد مشترك وهو الـ cache الوحيد، الكاتب يعمل DEL وخلاص. الـ events بتفرق لما يبقى فيه نسخ DEL واحد مش هيوصلها: L1 جوه الـ memory في كل app instance، أو cache بتاع service تانية. الـ Redis Pub/Sub بتاع fire-and-forget: الرسالة بتروح للي متوصل في اللحظة دي بس، مفيش replay ومفيش error للي فاته. فوق، الـ connection بتاع B قطع لحظة، الـ PUBLISH وصل لواحد من اتنين، B رجع، وفضل يرجّع السعر القديم من غير أي إشارة إن حاجة حصلت.

الطريق المضمون هو log. حط التغيير في stream محفوظ وخلي كل instance يتابع مكانه هو. في Redis Streams كل instance لازم يبقى له consumer group لوحده، لأن الـ group بيدي كل entry لـ consumer واحد بس من جواه. فوق الـ B كان offline، رجع وقرا اللي فاته. ونفس التجربة بتوريك الفخ: group واحد مشترك، الـ A خد الـ entry والـ B مخدش حاجة، فالـ B فضل stale. والـ event كمان لازم يطلع من الـ commit بتاع الـ DB، مش من كود ممكن يقع بعده بلحظة: ده الـ outbox أو CDC في section 07 · 3.4. وزاوية Redis بتاعة الـ delete بالـ events في section 07 · 3.5، الجزء 5.

سيب الـ TTL دايمًا. الـ streams بتتقص (MAXLEN)، والـ consumers فيهم bugs، والـ deploy ممكن يفوّت حتة. الـ events بتخلي الـ staleness قصيرة في الحالة العادية، والـ TTL هو السقف لأي حالة مش عادية. وcache بالـ events من غير TTL بيحوّل رسالة واحدة ضايعة لسعر غلط على طول.

فين هستخدمه في شغلي؟ API بتاع products عليه L1 بـ lru-cache في 8 instances وRedis وراهم. لما الـ admin يغيّر سعر: الـ write يكتب في Postgres وoutbox في نفس الـ transaction، relay ينزّل الـ event في stream، وكل instance عنده consumer group باسمه (app-${hostname}) يمسح الـ key من الـ L1. وتسيب TTL 60 ثانية على الـ L1 و10 دقايق على Redis، عشان لو event ضاع، الغلط يبقى له آخر. وخد بالك: مفيش حد يستخدم group واحد لكل الـ instances، دي الغلطة الشائعة هنا.
Trade-off: how long should the TTL be? A short TTL lowers the worst-case staleness but raises the DB load: halving the TTL roughly doubles the refills for keys that stay popular. Pick the TTL from the business cost of being wrong (a banner: minutes; a price: under a minute; stock at checkout: don't cache the decision, see part 5), then let events bring the common case down to milliseconds.
الـ TTL القصير بيقلل أسوأ staleness بس بيزوّد الحمل على الـ DB: لو قسمت الـ TTL على 2 الـ refills بتتضاعف تقريبًا للـ keys المشهورة. اختار الـ TTL من تمن الغلط في البيزنس (banner: دقايق، سعر: أقل من دقيقة، الـ stock وقت الـ checkout: متعملش cache للقرار نفسه، شوف الجزء 5)، وسيب الـ events تنزّل الحالة العادية لـ milliseconds.

Part 2 — Versioned keys & tags 🟡 Intermediateالجزء 2 — الـ versioned keys والـ tags

English

Versioned keys move invalidation from "find and delete" to "change the name". A key like product:123:v5 embeds the row's version, so after an update readers build v6 and never see the old entry. At group level, a namespace version does the same for a whole tenant: tenant:7:v3:product:123, where v3 comes from one counter. INCR tenant:7:ver invalidates everything for that tenant in O(1), however many keys exist.

Measured on real Redis with 200,000 keys, 10,000 of them for tenant 7: SCAN + UNLINK took 200 round trips and ≈149 ms, because SCAN has to walk the whole keyspace to find the 10,000 that match. The version bump was 1 round trip and ≈0.14 ms. Purge time depends on total keys for SCAN and on nothing for the bump.

The two costs. First, an extra read to get the current version on every request: measured ≈0.083 ms for a direct GET against ≈0.162 ms for version + GET, one more round trip, which on a real network is a full RTT. Caching the version in process for a second or so removes most of it and brings back a second of staleness. Second, memory: the bump freed nothing (59.8 MB before and after), because the old keys are only unreachable. They leave by TTL or eviction, so every versioned key needs a TTL and the instance needs room for the overlap.

Tags answer a different question: "purge everything that used product 123", when a page depends on many products and a product appears on many pages. Each cached page registers itself in a set tag:product:123; a purge reads the set and unlinks its members. One version counter can't express that many-to-many relation. Below, a tag purge removed 3 pages plus the tag itself (4 keys). The tag set is a cache entry too: give it a TTL, and remember members of expired keys pile up in it. Section 07 · 3.5, part 5 showed the non-atomic purge race; exercise 2 here fixes it with Lua.

import { mean, newRedis } from "./lib.ts";

const redis = newRedis();
await redis.flushall();
const VALUE = "x".repeat(200);
const TTL_S = 3600;
const usedMemory = async () => Number(/used_memory:(\d+)/.exec(await redis.info("memory"))![1]);

async function load(keyOf: (i: number) => string, n: number) {
  for (let i = 0; i < n; i += 2000) {
    const p = redis.pipeline();
    for (let j = i; j < Math.min(i + 2000, n); j++) p.set(keyOf(j), VALUE, "EX", TTL_S);
    await p.exec();
  }
}

Part 3 — The race, a thousand times 🟡 Intermediateالجزء 3 — الـ race، ألف مرة

English

The writer has two steps, the database and the cache, and they can't be one transaction. A reader doing cache-aside has steps too: GET miss, SELECT, SET. Between any two steps something else can run. The experiment below uses real Postgres and real Redis, with 1000 iterations per strategy, one writer and one racing reader per product, and injected delays: 5–25 ms between the writer's two steps, and 20% of readers paused between SELECT and SET (15% for 60 ms, 5% for 250 ms, standing in for GC or a slow network). 30% of keys start cold. These rates show the mechanism and the relative order of the strategies, not your production rate, which depends on how often a reader lands in the window.

Delete-then-write (the wrong order): the writer deletes, then updates. A reader in that gap misses, reads the old committed row, and refills it. Then the write commits and the cache holds the old value for a full TTL. Stale in 471 of 1000.

Write-then-delete (the right order) closes that window, and only a narrower one remains: a reader that read before the commit and sets after the delete. It needs a cold key (a warm key is a hit, so the reader never goes to the DB) and a pause longer than the commit plus delete. 15 of 1000 here: rarer, not gone.

Three fixes, each run. A delayed second delete (120 ms later) catches readers slower than that gap but not the 250 ms ones: 6 stale, at the cost of a second delete and extra misses. Set-if-newer stores the row version in the value and uses a Lua compare-and-set, with the writer writing the new versioned value instead of deleting it: 0 stale, and DB reads drop to 281 because the writer warms the cache. It needs the writer to have the whole value, and a delete breaks it: the "set-if-newer + DEL" row shows 15 stale, the same as write-then-delete, because once the key is gone there's nothing to compare against. Leases, from Facebook's memcache paper: a miss takes a token, the fill is accepted only while the token is still valid, and the writer's delete also removes the token. 0 stale, at more Redis work per read.

Whatever you pick, a crash between commit and the cache step still leaves the key stale until TTL. That window is the reason for the outbox or CDC (section 07 · 3.4) and for keeping a TTL.

  | "set-if-newer + DEL (bug)"

interface Stats {
  stale: number;
  dbReads: number;
  redisOps: number;
  readerWait: number[];
}

async function run(name: Name): Promise<Stats> {
  const stats: Stats = { stale: 0, dbReads: 0, redisOps: 0, readerWait: [] };
  const rand = mulberry32(42);
  await redis.flushall();
  await db.query("UPDATE products SET price = 100, version = 1");

  const usesLua = name === "set-if-newer" || name === "set-if-newer + DEL (bug)";
  const readRow = async (id: number) => {
    stats.dbReads++;
    const { rows } = await db.query<{ price: number; version: number }>(
      "SELECT price, version FROM products WHERE id = $1", [id]);
    return rows[0]!;
  };

  // الـ reader: GET، لو miss يقرا من الـ DB ويستنى (GC أو network بطيء) وبعدين يملا
  async function reader(id: number, pause: number, leased: boolean): Promise<void> {
    stats.redisOps++;
    if ((await redis.get(KEY(id))) !== null) return;
    let token: string | null = null;
    if (leased) {
      token = `${id}-${pause}-${Math.random()}`;
      stats.redisOps++;
      const got = await redis.set(LEASE(id), token, "PX", 5000, "NX");
      if (got !== "OK") token = null;
    }
    const row = await readRow(id);
    if (pause > 0) await sleep(pause);
    stats.redisOps++;
    if (usesLua) {
      await redis.eval(SET_IF_NEWER, 1, KEY(id), row.version, row.price, TTL_MS);
    } else if (leased) {
      if (token) await redis.eval(FILL_IF_LEASED, 2, KEY(id), LEASE(id), token, `${row.version}|${row.price}`, TTL_MS);
    } else {
      await redis.set(KEY(id), `${row.version}|${row.price}`, "PX", TTL_MS);
    }
  }

  async function writer(id: number, gap: number): Promise<void> {
    const update = () =>
      db.query<{ version: number }>(
        "UPDATE products SET price = 200, version = version + 1 WHERE id = $1 RETURNING version", [id]);
    if (name === "delete-then-write") {
      stats.redisOps++;
      await redis.del(KEY(id));
      await sleep(gap);
      await update();
      return;
    }
    const { rows } = await update();
    await sleep(gap);
    if (name === "set-if-newer") {
      stats.redisOps++;
      await redis.eval(SET_IF_NEWER, 1, KEY(id), rows[0]!.version, 200, TTL_MS);
      return;
    }
    if (name === "lease") {
      stats.redisOps++;
      await redis.del(KEY(id), LEASE(id));
      return;
    }
    stats.redisOps++;
    await redis.del(KEY(id));
    if (name === "delayed-double-delete") {
      await sleep(120);
      stats.redisOps++;
      await redis.del(KEY(id));
    }
  }

  const leased = name === "lease";
  const iterate = async (id: number) => {
    const cold = rand() < 0.3;
    if (!cold) {
      stats.redisOps++;
      await redis.set(KEY(id), `1|100`, "PX", TTL_MS);
    }
    // الاتنين بيبدأوا في لحظات عشوائية جوه نفس الـ 30 ms
    const readerAt = rand() * 30;
    const writerAt = rand() * 30;
    // نسب الـ pause: حوالي 80% من غير تأخير و15% متوسط و5% أطول من الـ delete التاني
    const p = rand();
    const pause = p < 0.8 ? 0 : p < 0.95 ? 60 : 250;
    const gap = 5 + rand() * 20;
    await Promise.all([
      (async () => { await sleep(writerAt); await writer(id, gap); })(),
      (async () => { await sleep(readerAt); await reader(id, pause, leased); })(),
    ]);
    // بعد ما كله يهدى: قارن اللي في الـ cache باللي في الـ DB
    stats.redisOps++;
    const cached = await redis.get(KEY(id));
    if (cached !== null) {
      const { rows } = await db.query<{ price: number }>("SELECT price FROM products WHERE id = $1", [id]);
      if (Number(cached.split("|")[1]) !== rows[0]!.price) stats.stale++;
    } else {
      // الـ follow-up reader بيعمل miss ويملا: ده الحمل الزيادة بعد الـ delete
      await reader(id, 0, leased);
    }
  };

  for (let i = 1; i <= ITERATIONS; i += PARALLEL) {
    await Promise.all(Array.from({ length: Math.min(PARALLEL, ITERATIONS - i + 1) }, (_, j) => iterate(i + j)));
  }
  return stats;
}

Interview question: "Is write-then-delete enough?" It closes the common race, but a slow reader that read before the commit can still set after the delete, which needs a cold key and a long pause. If that matters, the writer sets a versioned value with compare-and-set, or use leases as Facebook did. A crash between commit and delete still needs a TTL and ideally CDC or an outbox.

Part 4 — Replicas poison caches 🟡 Intermediateالجزء 4 — الـ replicas بتسمّم الـ cache

English

You read from a replica to spare the primary. The writer does everything correctly, commit then delete, and the next reader misses and refills from a replica that hasn't replayed the update yet. Now the old value is back in the cache with a brand-new TTL. Replica lag was milliseconds, and the wrong value lives for minutes. Below, with real streaming replication and replay paused: primary 150, replica 100, the reader cached 100, the replica caught up, and the cache still says 100 with 60 s left. Replication lag and its failure modes are in lesson 12.

Fix 1: read from the primary when repopulating right after a write. The writer sets a short marker (recent-write:product:2, a few seconds, longer than your lag) and a miss that sees the marker reads the primary. Fix 2: carry a version. The writer records the minimum version the cache may hold, and the reader rejects a replica row that's older and goes to the primary. Fix 1 is simpler and adds some primary reads after every write; fix 2 only touches the primary when the replica is actually behind, at the cost of another key per entity. Both cost nothing when there's no replica lag to speak of.

Part 5 — What not to cache 🟡 Intermediateالجزء 5 — إيه اللي متعملوش cache

English

A cache hit is cheaper than the database, but a miss pays for both trips plus the write back. So there's a break-even hit ratio: mean latency with cache = tGet + (1 − h)(tDb + tSet), which equals tDb at h = (tGet + tSet) / (tDb + tSet). Below that, the cache makes reads slower while using memory and adding a failure path.

Measured here on loopback: a primary-key lookup costs ≈0.27 ms against ≈0.18 ms for GET and SET, so the formula gives ≈81%, and the sweep (mean latency at each hit ratio, against plain database reads in the same rounds) crossed between 90% and 99%. In other words, on this machine a PK lookup is about as cheap as a Redis round trip and a cache barely pays. Add a 0.5 ms network RTT to each call and the break-even is ≈94%. An aggregate over 200,000 rows costing ≈7.2 ms breaks even at ≈5.4%. Cache expensive queries, not cheap ones, unless the goal is protecting the database from load, which is a different reason with its own numbers.

The usual suspects. Per-user dashboards: 3 views a day with a 5-minute TTL gives a hit ratio of about 1.1% (seeded calculator), far under any break-even, and you keep 100,000 keys in memory to get it. Data that changes every second, like live counts: the TTL would have to be shorter than the change rate, so you're just running a slower database. Cheap queries, as above. Permissions: a revoked admin keeps access until the TTL, so cache only with a very short TTL and an event that really is delivered, and never let the cached value be the final authorization on a sensitive action.

Never make a money decision from a cached value. Three concurrent checkouts of 400 against a cached balance of 1000 all passed, leaving −200. The same three against UPDATE ... WHERE balance >= $1 approved 2 of 3 and left 200. Show the cached balance on the page if you like; the decision belongs in the transaction that changes it.

async function measure(sql: string, n: number) {
  const db_ms: number[] = [];
  const get_ms: number[] = [];
  const set_ms: number[] = [];
  const rand = mulberry32(7);
  for (let i = 0; i < n; i++) {
    const id = 1 + Math.floor(rand() * 5000);
    db_ms.push(await time(() => db.query(sql, [id])));
    get_ms.push(await time(() => redis.get(`m:${id}`)));
    set_ms.push(await time(() => redis.set(`m:${id}`, "x".repeat(200), "EX", 60)));

  return { tDb: mean(db_ms), tGet: mean(get_ms), tSet: mean(set_ms) };
}

Part 6 — Sizing from an access log 🟡 Intermediateالجزء 6 — الـ sizing من access log

English

A cache size is a decision about hit ratio, so measure it from your own traffic instead of guessing. Take one hour of keys from your access log and replay them through a simulated LRU at many capacities. That gives a miss ratio curve. Below, a seeded log of 3 million requests over a catalog of 1M keys with Zipf skew 0.9 (a simulation, labelled in its output; it doesn't model varying value sizes, TTL expiry or Redis's sampled eviction).

Working set first. Distinct keys requested: 29,124 in a minute, 188,198 in 10 minutes, 584,925 in the hour. The cold-miss floor is 19.5%: every key's first request must miss, so no cache size beats 80.5% in this hour. Then the curve: hit ratio climbs steeply and flattens as it nears the floor. Read the column "gain per extra 100k keys": 15.7 points from 50k to 100k, 2.8 at 400k, 0.2 past 500k. The knee here is 400,000 keys (≈78.7% hit ratio): beyond it more memory barely helps.

Convert to bytes with the real overhead. A 796-byte product JSON costs 843 bytes in MEMORY USAGE; a batch of 20,000 keys grew used_memory by 913 bytes per key once the hash table is counted. So 400,000 keys ≈ 0.34 GB, or 0.48 GB with 1.4× headroom for fragmentation and growth.

Compare with the estimation rule. The 80/20 rule from lesson 02 caches 20% of daily reads: 14.4M objects, ≈12.2 GB. It's a sound first number on a whiteboard, but it counts requests, and repeated requests for the same key take no extra memory. Here the access-log method gives a size about 25× smaller for a similar hit ratio. Use the rule to set the order of magnitude in an interview, then use the curve for the actual purchase.

import { mulberry32, newRedis } from "./lib.ts";

console.log("[simulation] seeded access log, LRU simulated in memory. Not captured: value sizes that vary, TTL expiry, eviction sampling inside Redis.");

// (1) نولّد log لمدة ساعة بتوزيع Zipf زي أغلب الـ catalogs
const CATALOG = 1_000_000;
const REQUESTS = 3_000_000;
const S = 0.9;
const rand = mulberry32(2026);

// حساب الـ CDF مرة واحدة، وبعدين binary search لكل request
const cdf = new Float64Array(CATALOG);
let sum = 0;
for (let i = 0; i < CATALOG; i++) {
  sum += 1 / Math.pow(i + 1, S);
  cdf[i] = sum;
}
for (let i = 0; i < CATALOG; i++) cdf[i]! /= sum;

function pick(): number {
  const u = rand();
  let lo = 0;
  let hi = CATALOG - 1;
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (cdf[mid]! < u) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}

const log = new Int32Array(REQUESTS);
for (let i = 0; i < REQUESTS; i++) log[i] = pick();

// (2) الـ distinct keys: كام key اتطلب فعلاً في الساعة، وفي دقيقة، وفي 10 دقايق
const distinct = (from: number, to: number) => {
  const seen = new Set<number>();
  for (let i = from; i < to; i++) seen.add(log[i]!);
  return seen.size;
};
const perMin = Math.floor(REQUESTS / 60);
console.log(`requests/hour=${REQUESTS.toLocaleString("en-US")} (${Math.round(REQUESTS / 3600)} rps)`);
console.log(`distinct keys: 1 min=${distinct(0, perMin).toLocaleString("en-US")}  10 min=${distinct(0, perMin * 10).toLocaleString("en-US")}  1 hour=${distinct(0, REQUESTS).toLocaleString("en-US")}`);

// (3) الـ miss ratio curve: LRU بأحجام مختلفة على نفس الـ log
// ملحوظة: Linked list في typed arrays، لأن ⁦map.keys().next()⁩ بعد deletes كتير بقى بطيء جدًا هنا
function simulateLru(capacity: number): number {
  const prev = new Int32Array(CATALOG).fill(-1);
  const next = new Int32Array(CATALOG).fill(-1);
  const inCache = new Uint8Array(CATALOG);
  let head = -1;
  let tail = -1;
  let size = 0;
  let misses = 0;
  const unlink = (k: number) => {
    const p = prev[k]!;
    const n = next[k]!;
    if (p !== -1) next[p] = n;
    else head = n;
    if (n !== -1) prev[n] = p;
    else tail = p;
  };
  const pushFront = (k: number) => {
    prev[k] = -1;
    next[k] = head;
    if (head !== -1) prev[head] = k;
    head = k;
    if (tail === -1) tail = k;
  };
  for (let i = 0; i < REQUESTS; i++) {
    const k = log[i]!;
    if (inCache[k]) {
      unlink(k);
      pushFront(k);
      continue;
    }
    misses++;
    inCache[k] = 1;
    pushFront(k);
    if (++size > capacity) {
      const victim = tail;
      unlink(victim);
      inCache[victim] = 0;
      size--;
    }
  }
  return misses / REQUESTS;
}

const sizes = [1_000, 5_000, 20_000, 50_000, 100_000, 200_000, 300_000, 400_000, 500_000, 700_000];
const curve = sizes.map((c) => ({ capacity: c, miss: simulateLru(c) }));

// الـ cold misses: أول مرة كل key يتطلب. ده الحد الأدنى مهما كبّرت الـ cache
const coldFloor = distinct(0, REQUESTS) / REQUESTS;
console.log(`\ncold-miss floor (first touch of each key) = ${(coldFloor * 100).toFixed(1)}%`);
console.log("LRU capacity (keys)  miss ratio  hit ratio  gain per extra 100k keys");
curve.forEach(({ capacity, miss }, i) => {
  const before = curve[i - 1];
  const gain = before ? ((before.miss - miss) * 100) / ((capacity - before.capacity) / 100_000) : NaN;
  console.log(`${capacity.toLocaleString("en-US").padStart(18)}    ${(miss * 100).toFixed(1).padStart(6)}%    ${((1 - miss) * 100).toFixed(1).padStart(6)}%    ${Number.isNaN(gain) ? "" : gain.toFixed(1).padStart(6) + " pts"}`);
});

// (5) الـ knee: أول حجم بعده الزيادة بتجيب أقل من نقطتين لكل 100 ألف key
const knee = curve.find((c, i) => {

const gb = (n: number, bytes: number, headroom: number) => (n * bytes * headroom) / 1024 ** 3;
console.log(`\nknee at ${knee.capacity.toLocaleString("en-US")} keys -> hit ratio ${((1 - knee.miss) * 100).toFixed(1)}% -> ${gb(knee.capacity, perKey, 1.0).toFixed(2)} GB raw, ${gb(knee.capacity, perKey, 1.4).toFixed(2)} GB with 1.4x headroom`);

// (6) قارن بقاعدة الـ 80/20 اللي بتحسب على عدد الـ requests في اليوم
const dailyReads = (REQUESTS / 3600) * 86400;
const rule8020 = 0.2 * dailyReads;

حجم الـ cache هو قرار على الـ hit ratio، فقيسه من الـ traffic بتاعك بدل التخمين. خد ساعة keys من الـ access log وعدّيهم على LRU متشبّه بأحجام كتير. ده بيطلّع miss ratio curve. فوق، log بـ seed فيه 3 مليون request على catalog مليون key بتوزيع Zipf 0.9 (simulation ومكتوب كده في الـ output، ومش بيغطي الأحجام المختلفة للقيم ولا الـ TTL ولا الـ sampled eviction بتاع Redis).

قارنها بقاعدة التقدير. قاعدة 80/20 من الدرس 02 بتعمل cache لـ 20% من قراءات اليوم: 14.4 مليون object، ≈12.2 GB. دي بداية كويسة على السبورة، بس بتحسب requests، والطلبات المكررة لنفس الـ key مش بتاخد memory زيادة. هنا طريقة الـ access log طلّعت حجم أصغر بحوالي 25 مرة لـ hit ratio قريب. استخدم القاعدة في الـ interview عشان الـ order of magnitude، والـ curve لما تيجي تدفع فلوس.

What breaks at scale Sizing to the knee assumes tomorrow looks like today. A flash sale widens the working set, and a nightly scan pushes the hot set out of LRU. Re-measure after traffic changes and leave the headroom; with noeviction, a full instance returns errors instead of evicting (section 07 · 3.5).
الـ sizing عند الـ knee بيفترض إن بكرة زي النهارده. الـ flash sale بيوسّع الـ working set، والـ scan الليلي بيطرد الـ hot set من الـ LRU. قيس تاني لما الـ traffic يتغير وسيب headroom. ولو سايب noeviction، الـ instance لما يتملي بيرد errors بدل ما يعمل evict (section 07 · 3.5).

Common mistakes · غلطات شائعة

❌ Delete before the write 
await redis.del(key);
// القارئ ممكن يملا القديم في اللحظة دي
await db.query(updateSql, params);
✅ Commit first, then delete 
await db.query(updateSql, params);
// بعد الـ commit: القارئ الجديد هيشوف الجديد
await redis.del(key);

❌ المسح قبل الكتابة بيفتح window واسعة: 471 من 1000 في التجربة. ✅ الـ commit الأول وبعدين الـ delete نزّلها لـ 15، وخلي الـ delete بره الـ transaction callback عشان تضمن إن الـ commit حصل فعلًا.

❌ Event-driven, no TTL

Solution · الحل 
import { newPool, newRedis, sleep } from "./lib.ts";

const db = newPool(10);
const redis = newRedis();
await redis.flushall();
await db.query(`DROP TABLE IF EXISTS products;
  CREATE TABLE products (id int PRIMARY KEY, price int NOT NULL);
  INSERT INTO products SELECT g, 100 FROM generate_series(1, 300) g;`);

const verKey = (id: number) => `product:${id}:ver`;
const dataKey = (id: number, v: string) => `product:${id}:v${v}`;

// الحل: الـ reader بياخد رقم الجيل الأول، فالكتابة المتأخرة بتروح لجيل محدش هيقراه
async function slowFill(id: number) {
  const v = (await redis.get(verKey(id))) ?? "0";
  const { rows } = await db.query("SELECT price FROM products WHERE id = $1", [id]);
  await sleep(60);
  await redis.set(dataKey(id, v), String(rows[0].price), "EX", 600);
}

async function write(id: number) {
  await db.query("UPDATE products SET price = 200 WHERE id = $1", [id]);
  await redis.incr(verKey(id));
}

let stale = 0;
for (let id = 1; id <= 300; id += 30) {
  await Promise.all(
    Array.from({ length: 30 }, async (_, j) => {
      const pid = id + j;
      await Promise.all([slowFill(pid), sleep(10).then(() => write(pid))]);
      const v = (await redis.get(verKey(pid))) ?? "0";
      const cached = await redis.get(dataKey(pid, v));
      if (cached !== null && cached !== "200") stale++;
    }),
  );
}
console.log(`300 slow readers racing a writer: stale=${stale}`);
await db.end();
redis.disconnect();

Cheat sheet · الخلاصة

  • TTL only: staleness ≈ TTL/2 on average, TTL at worst (measured ≈1.4 s / ≈2.9 s for 3 s).
  • Pub/Sub loses messages while a subscriber is offline; a stream with one consumer group per instance doesn't.
  • Always keep a TTL: it bounds every failure you didn't think of.
  • Namespace version = O(1) purge (≈0.14 ms vs ≈149 ms for SCAN + UNLINK of 10k keys), but one more round trip and memory until old keys expire.
  • Tags: many-to-many "everything that used product X"; TTL on the tag set too.
  • Delete-then-write is wrong (471/1000). Write-then-delete is the right order, but a slow reader on a cold key remains (15/1000).
  • Set-if-newer with the writer writing the value: 0 stale; with a DEL it's useless. Leases: 0 stale, more Redis work.
  • Filling from a lagging replica re-poisons the cache: read the primary right after a write, or check a version.
  • Break-even hit ratio = (tGet + tSet) / (tDb + tSet): cheap queries ≈80–90%+, expensive ones a few percent.
  • Never decide money or stock from a cached value; put the check in the transaction.
  • Size from an access log: distinct keys, cold-miss floor, miss ratio curve, knee, then real MEMORY USAGE + headroom.
بالعامية
  • الـ TTL لوحده: الـ staleness حوالي TTL/2 متوسط والـ TTL كله في الأسوأ (قست ≈1.4 ثانية و≈2.9 ثانية لـ TTL 3 ثواني).
  • الـ Pub/Sub بيضيّع الرسايل لما الـ subscriber يكون فاصل، والـ stream بـ consumer group لكل instance مش بيضيّعها.
  • سيب TTL دايمًا: هو السقف لكل مشكلة محسبتش حسابها.
  • الـ namespace version معناه purge في O(1) (≈0.14 ms قصاد ≈149 ms لـ SCAN + UNLINK لـ 10 آلاف key)، بتمن round trip زيادة وmemory لحد ما القديم ينتهي.
  • الـ tags لعلاقة many-to-many "كل حاجة استخدمت المنتج X"، وحط TTL على الـ tag set كمان.
  • الـ delete-then-write غلط (471 من 1000). الـ write-then-delete هو الترتيب الصح، بس reader بطيء على key فاضي لسه ممكن (15 من 1000).
  • الـ set-if-newer والكاتب بيكتب القيمة: 0 stale، ومع DEL ملوش فايدة. الـ leases: 0 stale بشغل أكتر على Redis.
  • الملا من replica متأخرة بيسمّم الـ cache تاني: اقرا من الـ primary بعد الكتابة أو اتأكد من الـ version.
  • الـ break-even hit ratio = (tGet + tSet) / (tDb + tSet): الـ queries الرخيصة ≈80–90% فأكتر، والغالية كام في المية.
  • متاخدش قرار فلوس أو stock من قيمة cached، خلي الفحص جوه الـ transaction.
  • الحجم من access log: distinct keys، الـ cold-miss floor، الـ miss ratio curve، الـ knee، وبعدين MEMORY USAGE الحقيقي + headroom.
