Why this matters · ليه ده مهم

English

A design nobody understood is a design nobody will approve, build or defend. At Senior level, most of your technical influence goes through documents, diagrams and review meetings, not code. In a system design interview the same skill is what's being scored: the interviewer can only rate what you say and draw, in 45 minutes. This lesson turns communication into things you can check: a lint for diagrams, a lint for design docs, a clock for the session, a drill for pushback, a score sheet for transcripts and a status script for RFCs.

بالعامية

تصميم محدش فهمه هو تصميم محدش هيوافق عليه ولا يبنيه ولا يدافع عنه. في مستوى الـ Senior، أغلب تأثيرك التقني بيعدّي من documents و diagrams و review meetings، مش من الكود. وفي الـ system design interview نفس المهارة دي هي اللي بتتقيّم: الـ interviewer مش بيقيّم غير اللي بتقوله وبترسمه في 45 دقيقة. الدرس ده بيحوّل التواصل لحاجات تقدر تتأكد منها: lint للـ diagrams، lint للـ design docs، ساعة للجلسة، drill للـ pushback، ورقة تقييم للـ transcripts، وscript بيطبع حالة الـ RFCs.

Part 1 — Diagrams that answer one question 🔴 Advancedالجزء 1 — diagrams كل واحدة بتجاوب سؤال واحد

English

A diagram is an answer, so it has to start from a question. Four cover almost every design review: a context diagram (who uses this, what does it depend on outside), a container diagram (what do we deploy, what talks to what), a data flow diagram (where does this data travel and rest) and a sequence diagram (what happens in what order, especially on failure). C4 levels and diagrams as code are taught in section 09 · 3.4. Here the concern is using them in a review, where each picture gets about 30 seconds of attention.

Two rules make a diagram readable. One question per diagram, written next to it, so the reader knows what was left out on purpose. And a node limit: past about nine boxes people stop following arrows and start guessing. Both rules can be checked, so lintDiagram below fails a diagram whose question is missing or too broad, or that has too many nodes. The limits (9 nodes, 5 participants, 10 messages) are our choice, not a standard. Change them, but keep a number.

The test is the overloaded diagram: 16 nodes and the question "how does the whole system work?". It fails both rules. Split into "which hops does a request cross?" and "what happens after the order commits?", each passes and neither loses anything the reader needed. Every diagram was also rendered in real Chrome with Mermaid 12.3, and the rendered node count matches what the lint counted.

const LIMITS = { nodes: 9, participants: 5, messages: 10 };

type Count = { kind: "flowchart"; nodes: number } | { kind: "sequence"; participants: number; messages: number };

export function count(src: string): Count {
  const lines = src.split("\n").map((l) => l.trim());
  if (lines[0].startsWith("sequenceDiagram")) {
    return {
      kind: "sequence",
      participants: lines.filter((l) => l.startsWith("participant ")).length,
      messages: lines.filter((l) => /-+[>x)]/.test(l) && l.includes(":")).length,
    };
  }
  const ids = new Set<string>();
  for (const line of lines.slice(1)) {
    // تنضيف: بنشيل الـ labels اللي على الأسهم عشان يفضل الـ id بس
    const bare = line.replace(/-- "[^"]*" -->/g, "-->").replace(/-\. "[^"]*" \.->/g, "-->").replace(/-\.->/g, "-->");
    for (const chunk of bare.split("-->")) {
      const id = chunk.trim().match(/^[A-Za-z_]\w*/)?.[0];
      if (id) ids.add(id);
    }
  }
  return { kind: "flowchart", nodes: ids.size };
}

export function lintDiagram(d: Diagram): string[] {
  const problems: string[] = [];
  const marks = d.question.match(/\?/g)?.length ?? 0;
  if (marks !== 1 || !d.question.trim().endsWith("?")) problems.push("needs exactly one question, ending in ?");
  // السؤال العام مبيحددش إنت هترسم إيه وهتسيب إيه
  if (/\b(whole|entire|everything|overview|architecture)\b/i.test(d.question)) problems.push("question is too broad to choose what to leave out");
  const c = count(d.src);
  if (c.kind === "flowchart" && c.nodes > LIMITS.nodes) problems.push(`${c.nodes} nodes, limit is ${LIMITS.nodes}`);
  if (c.kind === "sequence" && c.participants > LIMITS.participants) problems.push(`${c.participants} participants, limit is ${LIMITS.participants}`);
  if (c.kind === "sequence" && c.messages > LIMITS.messages) problems.push(`${c.messages} messages, limit is ${LIMITS.messages}`);
  return problems;
}

بالعامية

الـ diagram إجابة، فلازم تبدأ من سؤال. فيه 4 أنواع بيغطوا أغلب الـ design reviews: context (مين بيستخدم النظام وبيعتمد على إيه بره)، container (بنعمل deploy لإيه ومين بيكلم مين)، data flow (الـ data دي بتتحرك فين وبتقعد فين)، وsequence (إيه اللي بيحصل بالترتيب، خصوصًا وقت الفشل). مستويات الـ C4 و diagrams as code متشرحين في section 09 · 3.4، وهنا بنتكلم عن إزاي تستخدمهم في review، لأن كل صورة بتاخد حوالي 30 ثانية انتباه.

فيه قاعدتين بيخلوا الـ diagram تتقري: سؤال واحد لكل diagram مكتوب جنبها، عشان اللي بيقرا يعرف إيه اللي اتساب بقصد. وحد لعدد الـ nodes: بعد حوالي 9 boxes الناس بتبطل تتبع الأسهم وبتبدأ تخمّن. القاعدتين دول ينفع يتفحصوا بكود، فـ lintDiagram بيفشّل أي diagram سؤالها ناقص أو واسع، أو فيها nodes كتير. الحدود (9 nodes، و5 participants، و10 messages) اختيارنا إحنا مش standard: غيّرها براحتك، بس سيب رقم.

الاختبار الحقيقي هو الـ diagram الكبيرة: 16 node وسؤال "النظام كله بيشتغل إزاي؟". بتفشل في الاتنين. لما بنقسمها لـ "الـ request بيعدّي على إيه؟" و"إيه اللي بيحصل بعد الـ commit؟"، الاتنين بيعدّوا ومفيش معلومة كان القارئ محتاجها ضاعت. وكل الـ diagrams اترسموا في Chrome حقيقي بـ Mermaid 12.3، وعدد الـ nodes في الـ SVG طابق اللي الـ lint عدّه.

الغلطة الشائعة: تعمل صورة واحدة "للنظام كله" وتفتكر إنها أشمل، بس هي مبتجاوبش على حاجة محددة.

فين هستخدمه في شغلي؟ لما تعمل PR فيه feature جديدة أو تكتب ADR: حط container diagram واحدة وsequence للمسار الحرج (مثلًا الدفع أو رفع ملف). ولو الـ reviewer سألك "طب والـ cache؟"، متزودهاش في نفس الصورة: اعمل diagram تانية بسؤال تاني. ولو عايز الـ lint يبقى جزء من الـ repo، خليه يشتغل على ملفات .mmd في الـ CI ويفشّل الـ PR لو الـ diagram مفيهاش سؤال.
Interview question "Draw the architecture of this system." What do you draw first, and how much? Say which question you're answering first ("I'll start with the deployed parts and how they talk"), draw at most about nine boxes, and offer the next view ("I can show the payment failure as a sequence if useful") instead of cramming it all into one picture.

Part 2 — The one-page design doc 🔴 Advancedالجزء 2 — الـ design doc في صفحة أو اتنين

English

The repo's template, project/design-docs/0000-template.md, has 14 numbered sections. For a real doc you keep the numbers and trim what doesn't apply, so the structure stays recognizable. For a one- or two-page doc the sections that matter are: TL;DR, Problem (1), Requirements with numbers (3), Options with trade-offs (5), Proposed design with a diagram, data model and API (6), Failure modes (7), Rollout (11) and Open questions (13). ADRs record the single decision that comes out of this; they are taught in section 09 · 3.4.

lintDoc below turns those into checks. It finds sections by template number, so both the Arabic template and an English doc parse. A Non-functional line needs at least three numbers. Options need at least two described and one marked as the decision. Failure modes need at least two complete rows. Rollout needs a filled Rollback: line, because a plan with no way back isn't a plan. Open questions need at least one item, because a doc with none usually hasn't been thought through.

Run on a bad and a good doc for an invoice export feature, the bad one passes only the length check, and the good one passes all eight. The untouched template passes only two, which is right: it has the structure, but every number is still blank. A linter proves the doc is complete. It can't prove the design is good, so it replaces nothing in the review, it just stops reviewers spending their time asking for missing numbers.

export type Finding = { check: string; ok: boolean; why: string };

// السكاشن بنلاقيها برقمها في الـ template، فأي لغة للعناوين شغالة
function sections(md: string): Map<number, string> {
  const out = new Map<number, string>();
  let cur: number | null = null;
  for (const line of md.split(/\r?\n/)) {
    const m = line.match(/^##\s+(\d+)\./);
    if (m) { cur = Number(m[1]); out.set(cur, ""); continue; }
    if (/^##\s/.test(line)) { cur = null; continue; }

## TL;DR
Tenants export up to 12 months of invoices as a CSV in S3. It runs as a Postgres-backed job, one export per tenant at a time. The key decision is a queued job over a streaming HTTP response, because large exports outlive a request.

## 1. Problem and context
Finance teams need invoices for audits. Today support runs a SQL query by hand, 25 times a month, and it takes a day.

## 2. Goals and non-goals
**Goals:** self-service CSV export. **Non-goals:** PDF bundles, scheduled exports.

## 3. Requirements
**Functional:** request an export, see its status, download once it is ready.

**Non-functional:** enqueue p95 under 200 ms · 90% of exports done in 2 minutes · largest tenant 2,000,000 invoices · 99.9% for the enqueue API · files kept 7 days.

## 4. Estimation
300 exports a day, peak 5 running at once. Largest file about 400 MB at 200 bytes per row. 300 × 40 MB × 7 days ≈ 84 GB stored.

## 5. Options
| | A: Stream over HTTP | B: Job plus S3 | C: Read replica plus job |
| --- | --- | --- | --- |
| Summary | `GET` streams rows from a cursor | Row in `export_jobs`, worker writes to S3 | Same as B, reads from a replica |
| Complexity | Low | Medium | Medium, plus replica lag handling |
| Performance | Holds a connection for minutes | Request returns in ms | Same as B, protects the primary |
| Cost | None extra | About $2 a month of S3 | One more DB instance |
| Risk | Dies on a deploy, no resume | Worker crash needs a retry | Lag means missing fresh invoices |
| **Decision** | | ✅ | |

Why B: exports outlive deploys and proxy timeouts, and we are nowhere near needing a replica. Move to C if export queries push primary CPU above 60%.

English

The README's split is 5 minutes of requirements, 5 of estimation, 10 of high-level design, 15 of deep dive and 10 of trade-offs and bottlenecks. The method's eight steps are in lesson 01, which has a simple phase timer. What matters here is what you do when you're behind, because you will be. Requirements usually overrun, because they're comfortable.

So the clock below has a checkpoint at 80% of each phase, an over-budget warning, and a replan that takes minutes from the remaining phases in a fixed order: estimation first, then high-level, then trade-offs, and deep dive last, each only down to a floor. Estimation drops to two minutes: one or two numbers said aloud. The high-level loses polish, not boxes. Trade-offs never go below four minutes, because that's where seniority shows. It runs in compressed time: --speed=600 makes a minute 100 ms, so a whole session takes about 4.5 s of real time.

The other decision is which part to deep dive on. Pick the part where the design could actually fail, not the part you know best. Rank components by likelihood times blast radius and discount the commodity parts whose solutions are well known. In checkout, retrying a payment without a double charge beats tuning a load balancer every time. If the interviewer points somewhere else, follow them, but offer your pick first.

export type Phase = { name: string; budget: number; floor: number };

// الـ floor هو أقل وقت ينفع المرحلة تتعمل فيه من غير ما تبقى شكلية
export const PLAN: Phase[] = [
  { name: "requirements", budget: 5, floor: 3 },
  { name: "estimation", budget: 5, floor: 2 },
  { name: "high-level", budget: 10, floor: 6 },
  { name: "deep dive", budget: 15, floor: 10 },
  { name: "trade-offs", budget: 10, floor: 4 },
];

// الترتيب ده هو اللي بنقص منه الأول لما نتأخر
const CUT_ORDER = ["estimation", "high-level", "trade-offs", "deep dive"];

export function replan(remaining: Phase[], minutesLeft: number): { plan: Phase[]; dropped: string[] } {
  const plan = remaining.map((p) => ({ ...p }));
  let over = plan.reduce((a, p) => a + p.budget, 0) - minutesLeft;
  for (const name of CUT_ORDER) {
    if (over <= 0) break;
    const p = plan.find((x) => x.name === name);
    if (!p) continue;
    const cut = Math.min(over, p.budget - p.floor);
    p.budget -= cut;
    over -= cut;
  }
  // لو لسه فوق الوقت حتى بعد الـ floors، لازم تقول بصوت عالي إيه اللي هتسيبه
  const dropped = over > 0 ? [`say aloud what you are skipping: ${over} min does not fit`] : [];
  return { plan, dropped };
}

What breaks: a plan with no floor If you only "save time" by shrinking everything equally, the deep dive ends up too short to say anything and the trade-offs vanish. A floor per phase means that past a point you must say out loud what you're skipping, which is itself a good signal.

"Why not Kafka?" is rarely an attack. It's a test of whether you know what you gave up. Defending ("Kafka is overkill") fails it. A good answer has the same shape every time: what is true about X, the constraint that decides it with a number, what you give up, and the condition under which you'd switch. Lesson 43 has the trade-off sentence and lesson 44 the full cost model. Here they meet the challenge in real time.

The code below carries a small version of that model: the store decision comes from decide() in lesson 11, and egress is priced with the constant from lesson 44 (about $0.09 per GB after 100 GB free, from third-party sources, so check AWS before quoting it). Five habits separate a Senior answer from a recited one. Ask before you assume, because the constraints change the design. Say your assumptions aloud so they can be corrected. Start simple and add complexity only when a number or the interviewer calls for it. Go deep when asked, with a mechanism, not a slogan. And don't recite memorized solutions: a memorized answer sounds right until the interviewer changes one constraint and it doesn't bend.

The score sheet below applies those seven dimensions to a transcript, on top of review() from the self-review script in lesson 01. It's a rough heuristic over text, and it says so: it counts questions, stated assumptions, numbers, how heavy the first design is, and how much substance follows "go deeper". Red flags worth learning by heart: no clarifying questions; naming tools before any number; claiming "exactly-once" with no mechanism; spending a third of the session on one easy component; and arguing with the interviewer instead of asking what they're worried about. Part 6 — RFCs in a team 🔴 Advancedالجزء 6 — الـ RFC في الفريق

English

An RFC is a design doc with a process around it: it moves through draft, in review and closed. The doc itself is the template from Part 2. Five things make the process work. An owner who decides, usually the author's tech lead. Named reviewers, chosen by what the change touches: the service owner, whoever is on call for it, security when PII or payments are involved. A deadline for feedback, written in the file, so silence can't block forever. A way to close: the owner decides by the deadline, and disagreement is recorded rather than negotiated indefinitely. And a recorded outcome: an ADR, as taught in section 09 · 3.4, so a year later someone can see what was decided and why.

Hold a meeting only when writing has stopped working: more than two rounds of comments going in circles, or one blocking disagreement. Then 30 minutes, with a written agenda, and a decision or a named next step at the end. Otherwise async review is cheaper and leaves a record.

Because status lives in front matter, it can be checked with a script. rfc-status.ts reads the samples and prints overdue reviews, open decisions and accepted RFCs with no ADR. On the sample data it finds one RFC four days overdue, waiting on two reviewers, with four rounds of comments, so it suggests a meeting. It also finds one accepted RFC that nobody recorded as an ADR. The human side of this, running these discussions and disagreeing well, belongs to section 13 (Senior Skills).

import { readdirSync, readFileSync } from "node:fs";
import { join } from "node:path";

type Rfc = {
  id: string; title: string; status: string; author: string; reviewBy: Date;
  reviewers: { name: string; state: string }[]; decision: string; rounds: number; adr: string;
};

// قراءة بسيطة للـ front matter: سطور key: value بين خطين ⁦---⁩
function parse(md: string): Rfc {
  const block = md.split(/\r?\n/);
  if (block[0] !== "---") throw new Error("missing front matter");
  const end = block.indexOf("---", 1);
  const kv = Object.fromEntries(block.slice(1, end).map((l) => {
    const i = l.indexOf(":");
    return [l.slice(0, i).trim(), l.slice(i + 1).trim()];
  }));
  return {
    id: kv.id, title: kv.title, status: kv.status, author: kv.author,
    reviewBy: new Date(kv.review_by + "T00:00:00Z"),
    reviewers: kv.reviewers.split(",").map((r) => {
      const [name, state] = r.trim().split("=");
      return { name, state };
    }),
    decision: kv.decision, rounds: Number(kv.comment_rounds), adr: kv.adr,
  };
}

}

Cheat sheet · الخلاصة

  • A diagram is an answer: one question per diagram, written next to it, and at most about 9 boxes.
  • Four views: context, container, data flow, sequence for the risky path. C4 detail is in section 09.
  • One-page doc: TL;DR, problem, requirements with numbers, options, design, failure modes, rollout with rollback, open questions.
  • A lint can prove a doc is complete. It can't prove the design is right.
  • 45 minutes: 5, 5, 10, 15, 10. Replan when behind, cutting estimation first, with a floor for each phase.
  • Deep dive where the design could fail, not where you are comfortable.
  • Pushback shape: what is true about X, the deciding constraint with a number, what you give up, when you would switch.
  • Ask, state assumptions, start simple, go deep when asked, don't recite. Claiming exactly-once with no mechanism is a red flag.
  • RFC: owner who decides, named reviewers, a deadline in the file, meeting only when comments loop, ADR at the end.
بالعامية
  • الـ diagram إجابة: سؤال واحد لكل diagram مكتوب جنبها، وحوالي 9 boxes بالكتير.
  • 4 views: context و container و data flow و sequence للمسار الخطر. وتفاصيل الـ C4 في section 09.
  • الـ doc في صفحة: TL;DR، المشكلة، requirements بأرقام، options، التصميم، failure modes، rollout و rollback، و open questions.
  • الـ lint يقدر يثبت إن الـ doc كامل، لكنه ميقدرش يثبت إن التصميم صح.
  • الـ 45 دقيقة: 5، 5، 10، 15، 10. لما تتأخر اعمل replan، قصّر الـ estimation الأول، وكل مرحلة ليها floor.
  • اعمل deep dive في الجزء اللي التصميم ممكن يقع فيه، مش الجزء اللي مريحك.
  • شكل الرد على الـ pushback: إيه الصح في X، القيد اللي بيحسم برقم، بتتنازل عن إيه، وإمتى هتغيّر رأيك.
  • اسأل، قول الافتراضات، ابدأ بسيط، ادخل عمق لما يتطلب، ومتحفظش. وادعاء exactly-once من غير mechanism red flag.
  • الـ RFC: owner بيقرر، reviewers بأسماء، deadline في الملف، meeting بس لما التعليقات تلف، و ADR في الآخر.
