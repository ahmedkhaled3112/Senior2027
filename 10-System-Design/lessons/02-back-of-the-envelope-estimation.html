Why this matters · ليه ده مهم

English

An estimate decides whether you need one database or twenty before anyone writes code. It's also the step in a design interview where a candidate shows they can reason about real machines. The goal is the right order of magnitude with assumptions you can defend, so the arithmetic is deliberately rough.

You'll build one small calculator and reuse it through this section. Every rule of thumb here is then checked against something real: a generated day of traffic, real Postgres row sizes, real Redis memory and real latencies from this machine. Some of the rules hold and some don't.

بالعامية

التقدير هو اللي بيقرر محتاج database واحدة ولا عشرين قبل ما حد يكتب كود. وهو كمان الخطوة في الـ design interview اللي بتبيّن إنك بتفكر في machines حقيقية. الهدف إنك تجيب رتبة الرقم صح بافتراضات تقدر تدافع عنها، فالحساب تقريبي عن قصد.

هتبني calculator صغير وتستخدمه طول القسم. وكل قاعدة هنا هنراجعها على حاجة حقيقية: يوم traffic متولّد، وأحجام صفوف Postgres حقيقية، وذاكرة Redis حقيقية، و latencies حقيقية من الجهاز ده. فيه قواعد هتطلع صح، وفيه قواعد لأ.

Part 1 — QPS & peak 🟢 Basicالجزء 1 — الـ QPS والـ peak

English

Average QPS = users per day × actions per user ÷ 86,400. The shortcut is to divide by 100,000 instead. For 1M users with 10 requests each, that's 115.7 QPS exactly, or 100 with the shortcut. Peak is the average times a factor: 2–3× gives 231–347 QPS.

A correction to the README. Its rule of thumb says "1M users/day ≈ 12 QPS average and ~100 QPS peak". The 12 only holds if each user does exactly one action. And 100 is 8.6× the average, while the same README line says peak is 2–3×. Both can't be the default. Always say which you assume: 2–3× for a steady SaaS, 8–10× or worse for flash sales. At 2–3×, those 12 QPS peak at 23–35.

You don't have to guess the factor. The second script generates a whole day, second by second, using a seeded random generator: a quiet night and an evening peak, then the same day with a five-minute sale at 10× traffic. It reports the peak factor from the trace itself. A normal day peaks at 2.7× measured over one second, so 2–3× is fair. The sale day peaks at 7.4×, and a fleet sized for 3× is over capacity for all 300 seconds of the sale, which is exactly when the money is.

// الملف ده الـ calculator اللي هتستخدمه طول القسم، كل دالة بترجع أرقام مش نص
export const SECONDS_PER_DAY = 86_400;
export const KB = 1_000;
export const MB = 1_000_000;
export const GB = 1_000_000_000;
export const TB = 1_000_000_000_000;

export function qps(input: { dau: number; actionsPerUser: number; peakFactor: number }) {
  const avg = (input.dau * input.actionsPerUser) / SECONDS_PER_DAY;
  return { avg, peak: avg * input.peakFactor };
}

export function storageBytes(input: {
  itemsPerDay: number;
  bytesPerItem: number;
  years: number;
  // ده مضاعف الـ tuple header والـ indexes، قيسه ومتخمّنوش
  overheadFactor?: number;
  replicas?: number;
}) {
  const days = input.years * 365;
  const raw = input.itemsPerDay * input.bytesPerItem * days;
  return { raw, total: raw * (input.overheadFactor ?? 1) * (input.replicas ?? 1) };
}

export function bandwidth(input: { qps: number; bytesPerRequest: number; compressionRatio?: number }) {
  const bytesPerSec = (input.qps * input.bytesPerRequest) / (input.compressionRatio ?? 1);
  // الشبكة بتتباع بالـ bits، والملفات بتتحسب بالـ bytes
  return { bytesPerSec, megabitsPerSec: (bytesPerSec * 8) / MB };
}

export function monthlyEgressBytes(bytesPerSec: number) {
  return bytesPerSec * SECONDS_PER_DAY * 30;
}

export function cacheBytes(input: { readsPerDay: number; valueBytes: number; hotShare?: number; overheadPerKey?: number }) {
  const hotKeys = input.readsPerDay * (input.hotShare ?? 0.2);
  return { hotKeys, bytes: hotKeys * (input.valueBytes + (input.overheadPerKey ?? 0)) };
}

export function human(bytes: number): string {
  if (bytes >= TB) return `${(bytes / TB).toFixed(2)} TB`;
  if (bytes >= GB) return `${(bytes / GB).toFixed(2)} GB`;
  if (bytes >= MB) return `${(bytes / MB).toFixed(2)} MB`;
  return `${(bytes / KB).toFixed(1)} KB`;
}

// المولّد ده بـ seed ثابت عشان نفس الأرقام تطلع كل مرة
export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// للتشغيل: node traffic-trace.ts
import { mulberry32, SECONDS_PER_DAY } from "./estimate.ts";

const DAILY_REQUESTS = 10_000_000;

// المنحنى ده بيعمل هدوء بالليل وذروة حوالين الساعة 9 مساءً
function diurnalWeight(sec: number): number {
  const hours = sec / 3600;
  return 0.35 + Math.max(0, Math.sin(((hours - 9) / 24) * 2 * Math.PI)) ** 2;
}

// العرض ده بيبدأ الساعة 8 مساءً ويطلع 10 أضعاف لمدة 5 دقايق
const SALE_START = 20 * 3600;
const SALE_LEN = 300;
function saleMultiplier(sec: number): number {
  return sec >= SALE_START && sec < SALE_START + SALE_LEN ? 10 : 1;
}

function trace(withSale: boolean, seed: number): Int32Array {
  const rand = mulberry32(seed);
  const weights = new Float64Array(SECONDS_PER_DAY);
  let sum = 0;
  for (let s = 0; s < SECONDS_PER_DAY; s++) {
    weights[s] = diurnalWeight(s) * (withSale ? saleMultiplier(s) : 1);
    sum += weights[s]!;
  }
  const counts = new Int32Array(SECONDS_PER_DAY);
  for (let s = 0; s < SECONDS_PER_DAY; s++) {
    const lambda = (weights[s]! / sum) * DAILY_REQUESTS;
    // تقريب Poisson بالتوزيع الطبيعي، وده كفاية لمعدلات فوق 30 في الثانية
    const u = Math.max(1e-12, rand());
    const z = Math.sqrt(-2 * Math.log(u)) * Math.cos(2 * Math.PI * rand());
    counts[s] = Math.max(0, Math.round(lambda + Math.sqrt(lambda) * z));
  }
  return counts;
}

function analyse(name: string, counts: Int32Array): void {
  const total = counts.reduce((a, b) => a + b, 0);
  const avg = total / SECONDS_PER_DAY;
  const peak1s = counts.reduce((a, b) => Math.max(a, b), 0);
  let peak1m = 0;
  let window = 0;
  for (let s = 0; s < SECONDS_PER_DAY; s++) {
    window += counts[s]!;
    if (s >= 60) window -= counts[s - 60]!;
    if (s >= 59) peak1m = Math.max(peak1m, window / 60);
  }
  // لو حجمت السيرفرات على 3 أضعاف المتوسط، كام ثانية هتبقى فوق الطاقة؟
  const capacity = avg * 3;
  const overload = counts.reduce((n, c) => n + (c > capacity ? 1 : 0), 0);
  console.log(`${name}: avg ${avg.toFixed(1)}/s, seconds over 3x capacity: ${overload}`);
  console.log(`  peak over 1 s: ${peak1s}/s = ${(peak1s / avg).toFixed(1)}x, over 1 min: ${peak1m.toFixed(0)}/s = ${(peak1m / avg).toFixed(1)}x`);
}

بالعامية

متوسط الـ QPS = users في اليوم × actions لكل user ÷ 86400. والاختصار إنك تقسم على 100 ألف. يعني مليون يوزر بـ 10 requests لكل واحد: 115.7 QPS بالظبط، أو 100 بالاختصار. والـ peak هو المتوسط في معامل: من 2 لـ 3 ضعف يطلع من 231 لـ 347 QPS.

تصحيح للـ README. القاعدة بتقول "1M users/day ≈ 12 QPS متوسط و ~100 QPS peak". الـ 12 دي صح بس لو كل يوزر بيعمل action واحد. والـ 100 دي 8.6 ضعف المتوسط، في حين إن نفس الـ README بيقول الـ peak من 2 لـ 3 ضعف. الاتنين مينفعوش يبقوا الـ default. قول دايمًا إنت فارض إيه: 2–3 ضعف لـ SaaS ثابت، و 8–10 ضعف أو أكتر للـ flash sales. وعلى 2–3 ضعف، الـ 12 QPS دول ذروتهم من 23 لـ 35.

ومش لازم تخمّن المعامل. السكريبت التاني بيولّد يوم كامل ثانية بثانية بـ random generator ليه seed: ليل هادي وذروة بالليل، وبعدين نفس اليوم بعرض مدته 5 دقايق بـ 10 أضعاف الـ traffic. وبيطلّع الـ peak factor من الـ trace نفسه. اليوم العادي ذروته 2.7 ضعف مقاسة على ثانية، فالـ 2–3 ضعف معقولة. يوم العرض ذروته 7.4 ضعف، والسيرفرات المحسوبة على 3 أضعاف بتبقى فوق طاقتها الـ 300 ثانية بتوع العرض كلهم، وده بالظبط الوقت اللي الفلوس بتيجي فيه.

فين هستخدمه في شغلي؟ الـ marketing جاي يقولك "هنعمل عرض الجمعة الساعة 8". لو عندك access logs، احسب الـ peak factor من يوم عرض قديم بنفس طريقة السكريبت ده: requests/second لكل ثانية وخد الأعلى على المتوسط. وبعدين حدد عدد الـ instances على الرقم ده، مش على المتوسط، وخلي الـ autoscaling يجهز قبلها لأن الـ spike أسرع منه.

Part 2 — Storage 🟢 Basicالجزء 2 — الـ storage

English

Storage = items per day × bytes per item × days, then multiply by overhead and by copies. The exit question, 10M requests a day at 1 KB for 5 years, is 18.25 TB raw. That number is the start of the estimate.

I inserted 100,000 orders into real Postgres 18 twice, with small rows and with rows near 1 KB, each with a UUID primary key and two secondary indexes. Then I compared the sum of the column widths with pg_total_relation_size. Small rows of 146 bytes actually take 274 (1.88×). Rows of 1,010 bytes take 1,252 (1.24×). So the overhead is not a fixed percentage:

  • Each row carries a tuple header of about 24 bytes and a 4-byte pointer in its page.
  • The three indexes cost about 80 bytes per row in both tables, whatever the row width. The index size depends on the indexed columns.
  • The 1 KB rows lose space to page fit: 8,192 ÷ 1,171 is almost exactly 7 rows per page, and the leftover in each page is wasted.

Then add copies. A primary and two replicas is 3×. The exit answer becomes 18.25 × 1.24 × 3 ≈ 68 TB, nearly four times the naive figure, and that's before WAL, backups and bloat. Use the factor measured on rows that look like yours. This is fast: true Postgres, since durability doesn't affect sizes.

// للتشغيل: PG_PORT=54329 node storage-check.ts
import pg from "pg";
import { human, storageBytes, TB } from "./estimate.ts";
import { throwawayPort } from "./db-guard.ts";

const c = new pg.Client({ host: "127.0.0.1", port: throwawayPort(process.env.PG_PORT), user: "app", database: "postgres" });
await c.connect();
try {
  const exit = storageBytes({ itemsPerDay: 10_000_000, bytesPerItem: 1_000, years: 5 });
  console.log(`exit Q1: 10M/day x 1 KB x 5 years = ${human(exit.raw)}`);

  async function measure(table: string, noteRepeats: number): Promise<{ naive: number; total: number }> {
    await c.query(`CREATE TABLE ${table} (
      id uuid PRIMARY KEY DEFAULT uuidv7(),
      user_id bigint NOT NULL,
      status text NOT NULL,
      total_cents bigint NOT NULL,
      currency char(3) NOT NULL,
      created_at timestamptz NOT NULL DEFAULT now(),
      shipping_note text NOT NULL)`);
    await c.query(`CREATE INDEX ON ${table} (user_id, created_at DESC)`);
    await c.query(`CREATE INDEX ON ${table} (status, created_at)`);
    await c.query(`INSERT INTO ${table} (user_id, status, total_cents, currency, shipping_note)
      SELECT (random() * 500000)::bigint,
             (ARRAY[$$pending$$,$$paid$$,$$shipped$$,$$delivered$$])[1 + floor(random() * 4)::int],
             (random() * 200000)::bigint, $$EGP$$,
             repeat(md5(g::text), ${noteRepeats})
      FROM generate_series(1, 100000) g`);
    await c.query(`ANALYZE ${table}`);
    const { rows } = await c.query<Record<string, string>>(`SELECT
      count(*) AS n,
      avg(16 + 8 + octet_length(status) + 8 + 3 + 8 + octet_length(shipping_note)) AS naive,
      pg_table_size($$${table}$$) AS heap,
      pg_indexes_size($$${table}$$) AS indexes,
      pg_total_relation_size($$${table}$$) AS total
      FROM ${table}`);
    const r = rows[0]!;
    const n = Number(r.n);
    const naive = Number(r.naive);
    const total = Number(r.total) / n;
    console.log(`${table}: naive ${naive.toFixed(0)} B/row, heap ${(Number(r.heap) / n).toFixed(0)}, 3 indexes ${(Number(r.indexes) / n).toFixed(0)}`);
    console.log(`  total ${total.toFixed(0)} B/row => ${(total / naive).toFixed(2)}x, +${(total - naive).toFixed(0)} B/row`);
    return { naive, total };
  }

  await measure("orders_small", 3);
  const wide = await measure("orders_1kb", 30);

  // المعامل بيتغير مع حجم الصف، فاستخدم القياس اللي شبه صفوفك إنت
  const factor = wide.total / wide.naive;
  const real = storageBytes({ itemsPerDay: 10_000_000, bytesPerItem: 1_000, years: 5, overheadFactor: factor, replicas: 3 });
  console.log(`exit Q1 with the 1 KB factor and 3 copies: ${(real.total / TB).toFixed(1)} TB`);
} finally {
  await c.end();
}

بالعامية

الـ storage = العناصر في اليوم × حجم العنصر بالـ bytes × عدد الأيام، وبعدين تضرب في الـ overhead وعدد النسخ. سؤال الـ exit، 10 مليون request في اليوم بـ 1 KB لمدة 5 سنين، يطلع 18.25 TB raw. والرقم ده بداية التقدير بس.

دخّلت 100 ألف order في Postgres 18 حقيقية مرتين، مرة بصفوف صغيرة ومرة بصفوف قريبة من 1 KB، وكل مرة بـ UUID primary key و2 secondary indexes. وبعدين قارنت مجموع عرض الأعمدة بـ pg_total_relation_size. الصفوف الصغيرة 146 byte بقت 274 (1.88 ضعف). والصفوف 1010 byte بقت 1252 (1.24 ضعف). يعني الـ overhead مش نسبة ثابتة:

  • كل صف معاه tuple header حوالي 24 byte، و pointer بـ 4 bytes في الصفحة بتاعته.

وبعدين النسخ. primary واتنين replicas يعني 3 أضعاف. إجابة الـ exit بتبقى 18.25 × 1.24 × 3 ≈ 68 TB، حوالي 4 أضعاف الحساب البسيط، وده قبل الـ WAL والـ backups والـ bloat. استخدم المعامل المقاس على صفوف شبه صفوفك إنت. والتجربة دي على Postgres بـ fast: true، لأن الـ durability مش بتأثر على الأحجام.

الغلطة الشائعة: تنسى الـ 3 أضعاف بتوع الـ replicas وحجم الـ indexes، وتقدّم 18 TB لما الرقم الحقيقي قريب من 70.

What breaks if you skip this Plan for 18 TB, get 68 TB, and the disk fills up in about a quarter of the time you promised. On a full disk Postgres can't write WAL, so writes stop. That's an outage from a multiplication you skipped.

Part 3 — Bandwidth 🟢 Basicالجزء 3 — الـ bandwidth

English

Bandwidth = QPS × bytes per request. The exit question at 2 KB gives about 231 KB/s, which is 1.85 Mbit/s. Those two figures differ by a factor of 8, and that factor is the classic unit bug. Networks are sold in bits per second, files are measured in bytes. A 1 Gbps link carries at most 125 MB/s, so a 50 GB backup takes 400 seconds at line rate, not 50, and in practice longer because protocols have overhead.

Compression changes the answer, by an amount that depends on size. Real node:zlib gzip on an orders JSON gave only 1.07× for one order (203 bytes; the gzip header is a large part of a small payload), 3.54× for ten orders (about 2 KB), and 5.40× for 500 orders. Repeated keys are what compress. So use the ratio measured at your typical response size.

Monthly egress is the number that turns into money: bytes per second × 86,400 × 30. At 115.7 QPS × 2 KB that's about 600 GB raw and 169 GB with gzip. Lesson 44 takes this number and prices it.

Part 4 — Cache memory & the 80/20 rule 🟡 Intermediateالجزء 4 — ذاكرة الـ cache وقاعدة 80/20

English

The rule of thumb is to cache 20% of daily reads, on the assumption that 20% of the keys get 80% of the traffic. The formula counts reads, while what you actually store are distinct keys, so it can overestimate when the same keys are read many times.

The 80/20 part is an assumption about skew, so I tested it. A seeded Zipf generator over 1M keys, 2M warm-up requests and 2M measured, simulated against an LRU of 1%, 5% and 20% of the keys, for three skews:

  • s = 0 (flat): the hit ratio simply equals the cache size. Twenty percent of the keys buys 20% of the traffic.
  • s = 0.8: the top 20% of keys get 70.8% of traffic, so "80/20" isn't even true here. A 20% cache hits 60.7%, below that 70.8% because LRU also holds keys that won't be read again soon.
  • s = 1.2: the top 20% get 97.7%, and a 1% cache already hits 87.5%.

So the skew is the whole answer: a 1% cache on skewed traffic beats a 20% cache on flat traffic. Measure your real access pattern if you can. Flat patterns, like users each reading their own private data, need far more memory.

The other assumption is that N keys of 1 KB take N KB. Real Redis says no. MEMORY USAGE reports about 44 extra bytes on a single key, and a bulk test of 50,000 keys with TTLs costs 1,101 bytes per key, about 10% over the value size. Small values suffer most: a 64-byte value takes 106 bytes.

// الملف ده بيختبر قاعدة 80/20 بـ Zipf و LRU حقيقي.
// للتشغيل: node lru-zipf.ts
import { mulberry32 } from "./estimate.ts";

const KEYS = 1_000_000;
const WARMUP = 2_000_000;
const MEASURED = 2_000_000;

// جدول تراكمي بنعمل عليه binary search عشان نختار key بسرعة
function zipfCdf(s: number): Float64Array {
  const cdf = new Float64Array(KEYS);
  let sum = 0;
  for (let k = 0; k < KEYS; k++) {
    sum += 1 / (k + 1) ** s;
    cdf[k] = sum;
  }
  for (let k = 0; k < KEYS; k++) cdf[k]! /= sum;
  return cdf;
}

function sample(cdf: Float64Array, u: number): number {
  let lo = 0;
  let hi = KEYS - 1;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (cdf[mid]! < u) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}

// الـ keys أرقام، فبنعمل الـ linked list بتاعة الـ LRU بـ arrays وكل عملية ⁦O(1)⁩
function hitRatio(trace: Int32Array, capacity: number): number {
  const HEAD = KEYS;
  const next = new Int32Array(KEYS + 1);
  const prev = new Int32Array(KEYS + 1);
  const cached = new Uint8Array(KEYS);
  next[HEAD] = HEAD;
  prev[HEAD] = HEAD;
  const unlink = (k: number) => {
    next[prev[k]!] = next[k]!;
    prev[next[k]!] = prev[k]!;
  };
  const toFront = (k: number) => {
    next[k] = next[HEAD]!;
    prev[k] = HEAD;
    prev[next[HEAD]!] = k;
    next[HEAD] = k;
  };
  let size = 0;
  let hits = 0;
  for (let i = 0; i < trace.length; i++) {
    const key = trace[i]!;
    if (cached[key]) {
      if (i >= WARMUP) hits++;
      unlink(key);
    } else {
      if (size === capacity) {
        // آخر عنصر قبل الـ HEAD هو الأقدم استخدامًا، فبيتطرد
        const oldest = prev[HEAD]!;
        unlink(oldest);
        cached[oldest] = 0;
      } else {
        size++;
      }
      cached[key] = 1;
    }
    toFront(key);
  }
  return hits / MEASURED;
}

English

The reference table and what each number means is in CS Fundamentals lesson 16, part 7, and why constants matter is in lesson 02. The four to carry into a design are RAM about 100 ns, SSD about 100 µs, a datacenter round trip about 0.5 ms and a cross-continent round trip about 150 ms. Here I measured them on this machine, a loaded Windows box, so read the ratios.

  • Random memory hops through 128 MB cost about 113 ns, close to the reference. Sequential access was 0.8 ns per element, about 140× cheaper.
  • A 4 KB read that the OS cache answers takes about 4 µs. The same read with the OS cache bypassed (FILE_FLAG_NO_BUFFERING) took 272 µs in the run below and 56–117 µs in the others, depending on what else the disk was doing. A quick file-read benchmark usually measures the cache.
  • fsync took about 0.8 ms at the median. A durable Postgres single-row INSERT took about 0.2 ms, using open_datasync on an already allocated WAL file, and 0.1–0.4 ms across runs. I didn't determine why it beats a plain fsync here. Consumer SSDs can acknowledge writes from their own cache, so don't carry that figure to a production volume.
  • On loopback an HTTP round trip took about 75 µs, a Postgres primary-key read about 141 µs and a Redis GET about 103 µs. Across six runs of this script those three ranged over 67–113, 79–253 and 80–229 µs, so every median here moves by 2–3× with the load on this machine, and Redis and Postgres stayed within about 1.5× of each other. No network is involved, the row was in Postgres's buffer cache, and the cost is the client, the socket and the event loop.

That last one contradicts a common belief. Redis is not 100× faster than a Postgres primary-key lookup that's already in memory. Caching pays off when the query is expensive or the database is loaded. The two real network rows can't be measured here, and the table says so.

Now use the numbers. Budget a 200 ms checkout: load balancer, app work, four database round trips, and one cross-region call to a tax service. The sum of medians is 174 ms, which looks like it fits. A simulation with long-tailed latencies shows a p99 of 259 ms, and 25% of requests over budget, with warm connections. A cold connection adds two more round trips (TCP plus TLS 1.3, 300 ms) and a retry after a 250 ms timeout blows it too. Moving the tax call out of the request brings p99 down to 69 ms. These step latencies are assumptions from the table, not measurements.

function memoryLatency(): { seqNs: number; randNs: number } {
  const size = 1 << 25;
  const next = new Int32Array(size);
  for (let i = 0; i < size; i++) next[i] = i;
  // خوارزمية Sattolo بتعمل دايرة واحدة كبيرة، فكل قفزة بتروح لمكان عشوائي
  const rand = mulberry32(7);
  for (let i = size - 1; i > 0; i--) {
    const j = Math.floor(rand() * i);
    const tmp = next[i]!;
    next[i] = next[j]!;
    next[j] = tmp;
  }
  const hops = 8_000_000;
  let p = 0;
  let t = performance.now();
  for (let i = 0; i < hops; i++) p = next[p]!;
  const randNs = ((performance.now() - t) * 1e6) / hops;
  let sum = 0;
  t = performance.now();
  for (let i = 0; i < size; i++) sum += next[i]!;
  const seqNs = ((performance.now() - t) * 1e6) / size;
  if (p < 0 || sum < 0) throw new Error("unreachable");
  return { seqNs, randNs };
}

  closeSync(f);

}

// الـ lognormal شكلها قريب من الـ latency الحقيقية: ديل طويل على اليمين
function sampler(step: Step, rand: () => number): () => number {
  const mu = Math.log(step.p50);
  const sigma = (Math.log(step.p99) - mu) / 2.326;
  return () => {
    const u = Math.max(1e-12, rand());
    const z = Math.sqrt(-2 * Math.log(u)) * Math.cos(2 * Math.PI * rand());
    return Math.exp(mu + sigma * z);
  };
}

النقطة الأخيرة عكس اعتقاد شائع. Redis مش أسرع 100 مرة من primary-key lookup في Postgres لو الصف أصلًا في الذاكرة. الـ caching بيكسب لما الـ query تقيلة أو الـ DB مضغوطة. وسطرين الشبكة الحقيقية ماينفعش يتقاسوا هنا، والجدول بيقول كده.

وبعدين استخدم الأرقام. وزّع ميزانية 200 ms على checkout: load balancer، شغل الـ app، 4 database round trips، ونداء cross-region لخدمة ضرايب. مجموع الـ medians 174 ms، وشكله داخل. لكن simulation بـ latencies ليها ديل طويل بتدي p99 بـ 259 ms، و25% من الـ requests فوق الميزانية، مع connections جاهزة. والـ connection الجديدة بتزود رحلتين (TCP و TLS 1.3، يعني 300 ms)، و retry بعد timeout بـ 250 ms بيكسرها برضه. ولما نشيل نداء الضرايب من الـ request الـ p99 بينزل لـ 69 ms. أرقام الخطوات دي افتراضات من الجدول، مش قياس.

فين هستخدمه في شغلي؟ لو الـ endpoint عندك بطيء، اكتب ميزانية زي دي: كل نداء والـ p50 والـ p99 بتوعه من الـ traces. غالبًا هتلاقي نداء واحد واكل الميزانية، زي خدمة ضرايب أو payment في region تانية. الحل مش "نسرّع الكود": تخلي النداء async، أو تعمل cache للنتيجة، أو تحرك الخدمة لنفس الـ region.
What a laptop can't tell you Loopback hides the network, so a local Postgres read looks as cheap as Redis. A real datacenter round trip adds about 0.5 ms, so four sequential queries cost at least 2 ms in the network alone, and N+1 queries turn that into your whole budget. Your measurements are good for ratios and bad for absolute production numbers.
الـ loopback بيخبّي الشبكة، فقراية Postgres المحلية تبان رخيصة زي Redis. الـ round trip الحقيقي في الـ datacenter بيزود حوالي 0.5 ms، فـ 4 queries ورا بعض بياخدوا على الأقل 2 ms في الشبكة لوحدها، و N+1 queries بتحوّل ده للميزانية كلها. القياسات بتاعتك كويسة للنسب، ووحشة للأرقام المطلقة في production.

English

An orders platform with 5M daily users. Every assumption is at the top of the file and said out loud: 20 requests per user, a 3× peak, 5% writes, 1M orders a day at 300 bytes, overhead 1.5× (the +128 bytes per row measured in Part 2 works out to about 1.4× at this size, rounded up for bloat), 3 copies, 2 KB responses compressing 3.5× (Part 3), and about 100 bytes of Redis overhead per key (Part 4).

The result: 1,157 QPS on average and 3,472 at peak, of which only 174 are writes; about 493 GB of storage a year including indexes and copies; 19M hot keys in about 21 GB of Redis; 15.9 Mbit/s of egress at peak; and 1.7 TB of egress a month. Read that as a design conclusion: storage and bandwidth are small, and the interesting number is the read peak.

For a sanity check I ran one real Postgres on this machine for 5 seconds: 16 connections, a 95/5 read/write mix, durable commits. It did about 14,900 QPS with a p99 of about 3 ms, and an earlier run of the same script did about 29,900, a 2× swing from other jobs on the box. That is well above the 3,472 peak, with big caveats: the data was 300,000 rows that fit in memory, there was no network, no replication and no long queries. It tells you one well-run database is not obviously out of range. It doesn't tell you it's enough.

How to say it in an interview: round aggressively, state each assumption, and sanity-check the result against something you know. // الحل ده بيحط cache قدام النداء البعيد ويقيس تأثير الـ hit ratio.
// للتشغيل: node ex3-budget.ts
import { mulberry32 } from "./estimate.ts";

const rand = mulberry32(5);
const BUDGET = 200;

function lognormal(p50: number, p99: number): () => number {
  const mu = Math.log(p50);
  const sigma = (Math.log(p99) - mu) / 2.326;
  return () => {
    const u = Math.max(1e-12, rand());
    const z = Math.sqrt(-2 * Math.log(u)) * Math.cos(2 * Math.PI * rand());
    return Math.exp(mu + sigma * z);
  };
}

const local = [lognormal(2, 8), lognormal(10, 25), lognormal(3, 25), lognormal(3, 25), lognormal(3, 25), lognormal(3, 25)];
const remote = lognormal(150, 220);
const cacheHit = lognormal(0.5, 3);

for (const hitRatio of [0, 0.5, 0.9, 0.99]) {
  const n = 200_000;
  let over = 0;
  const totals: number[] = [];
  for (let i = 0; i < n; i++) {
    let t = rand() < hitRatio ? cacheHit() : remote();
    for (const step of local) t += step();
    totals.push(t);
    if (t > BUDGET) over++;
  }
  totals.sort((a, b) => a - b);
  console.log(`hit ratio ${String(hitRatio * 100).padStart(3)}%: p50 ${totals[n >> 1]!.toFixed(0).padStart(3)} ms, p99 ${totals[Math.floor(n * 0.99)]!.toFixed(0).padStart(3)} ms, over budget ${((over / n) * 100).toFixed(1)}%`);
}

Cheat sheet · الخلاصة

  • QPS = users × actions ÷ 86,400, or ÷ 100K for speed (13.6% low, fine).
  • Peak: 2–3× for steady SaaS, 8–10× or worse for flash sales. Say which. Measure it from a trace if you have one.
  • README's "12 QPS, ~100 peak" assumes 1 action per user, and 100 is 8.6×.
  • Storage = items × bytes × days × overhead × copies. Measured overhead: 1.88× at 146-byte rows, 1.24× at 1 KB.
  • Exit Q1: 115.7 QPS, 231–347 peak, 231 KB/s, 18.25 TB raw (about 68 TB real).
  • Bandwidth is bits on the wire, bytes in files: 1 Gbps = 125 MB/s.
  • gzip ratio grows with payload size: 1.07× for one order, 3.54× at 2 KB.
  • 80/20 is a skew assumption. Flat traffic: hit ratio equals cache size. s = 1.2: a 1% cache hits 87.5%.
  • Redis costs about 100 bytes per key beyond the value at 1 KB, relatively more for small values.
  • RAM 100 ns, SSD 100 µs, datacenter 0.5 ms, cross-continent 150 ms. One cross-region call eats a 200 ms budget.
  • On loopback, Redis and an in-memory Postgres PK read stayed within about 1.5×. Local medians move 2–3× between runs, so trust ratios only.
  • Round, state every assumption, sanity-check against something you know.
