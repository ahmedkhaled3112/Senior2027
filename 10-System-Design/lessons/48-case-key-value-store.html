Why this matters · ليه ده مهم

English

This case packs half of distributed systems into one question: partitioning, replication, quorums, conflicts, repair. You'll rarely build one, but you will use systems built this way, like Cassandra, Riak and ScyllaDB, and you'll be asked why a write that succeeded can't be read. Here you'll run a small store made of real Node processes. It's a teaching toy, labelled that way throughout: every behaviour below is real, but nothing here should hold production data.

بالعامية

الـ case ده بيجمع نص الـ distributed systems في سؤال واحد: partitioning، و replication، و quorums، و conflicts، و repair. نادرًا هتبني واحد، بس هتستخدم أنظمة مبنية بالشكل ده زي Cassandra و Riak و ScyllaDB، وهتتسأل ليه write نجحت ومش قادر تقراها. هنا هتشغّل store صغير من Node processes حقيقية. ده teaching toy ومكتوب كده في كل مكان: كل سلوك هتشوفه حقيقي، بس مفيش حاجة هنا تنفع تشيل data في production.

English

Requirements. Functional: put(key, value, context) and get(key) returning values and a context. Non-functional: 10 TB, 100k QPS, a single-key value of at most about 1 MB, availability over consistency for writes, and consistency chosen per request. Non-goals: multi-key transactions, range scans, secondary indexes. Saying those out loud is part of the answer.

Estimates. From the calculator: 10 TB × N=3 = 30 TB raw. With 2 TB disks at 70% full, that's 22 nodes for storage. 80k reads and 20k writes per second become 300k replica operations per second, because the coordinator sends every request to all N replicas. At a planning figure of 25k ops per node that's 12 nodes, so storage decides, and with one-third headroom for losing a zone we get 30 nodes.

API with context. get returns { values, context }. put takes that context back. The context is an opaque version vector, and that's the whole trick: the server can tell whether your write has seen the versions it's replacing. Data model per node: a map from key to a list of versions, a hint store for writes held for other nodes, and a Merkle tree per key range.

Part 2 — Partitioning & replication 🔴 Advancedالجزء 2 — الـ partitioning والـ replication

English

Each key is hashed onto a ring built from virtual nodes, and the first N distinct physical nodes clockwise form the preference list. N = 3 here. Lesson 13 taught the ring and measured key movement, so what's new is how the ring is used: the preference list is computed from the key alone, so any node can act as coordinator without a lookup. A node that isn't one of the replicas still coordinates: it computes the list, writes to all three, and answers.

The real run below uses five real Node processes on real HTTP. With one vnode per node the busiest node holds 3.8 times the keys of the quietest. With 64 vnodes that falls to a spread of 17,067 to 22,371 around an ideal 20,000 per node. The put went through n4, which holds no copy, and the data landed exactly on n2, n1, n3.

// الـ ring ده تطبيق بسيط للـ consistent hashing اللي اتشرح في درس 13
import { createHash } from "node:crypto";

export const hash32 = (s: string) => createHash("md5").update(s).digest().readUInt32BE(0);

export class Ring {
  private tokens: { t: number; node: string }[] = [];
  private nodeCount: number;

  constructor(nodes: string[], vnodes = 64) {
    this.nodeCount = nodes.length;
    for (const node of nodes) {
      for (let v = 0; v < vnodes; v++) this.tokens.push({ t: hash32(`${node}#${v}`), node });
    }
    this.tokens.sort((a, b) => a.t - b.t);
  }

  // بنمشي مع عقارب الساعة من مكان الـ key، وناخد كل node مرة واحدة بس
  walk(key: string): string[] {
    const h = hash32(key);
    let lo = 0;
    let hi = this.tokens.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (this.tokens[mid].t < h) lo = mid + 1;
      else hi = mid;
    }
    const out: string[] = [];
    for (let i = 0; i < this.tokens.length && out.length < this.nodeCount; i++) {
      const n = this.tokens[(lo + i) % this.tokens.length].node;
      if (!out.includes(n)) out.push(n);
    }
    return out;
  }

  preference(key: string, n: number): string[] {
    return this.walk(key).slice(0, n);
  }
}
// الـ coordinator: أي node ينفع، وبيبعت لكل الـ N وبيستنى W بس
async function coordPut(key: string, value: unknown, ctx: Clock, w: number, sloppy: boolean) {
  const pref = ring.preference(key, N);
  const extras = ring.walk(key).slice(N);
  seq++;
  const version: Version = { value, dot: [id, seq], ctx, ts: Date.now() };
  return await new Promise<{ ok: boolean; acks: number; ackedBy: string[]; hinted: string[] }>((resolve) => {
    let acks = 0;
    let settled = 0;
    const ackedBy: string[] = [];
    const hinted: string[] = [];
    const finish = () => {
      if (acks >= w || settled === pref.length) resolve({ ok: acks >= w, acks, ackedBy, hinted });
    };
    for (const target of pref) {
      void (async () => {
        if (await replicaPut(target, key, [version])) {
          acks++;
          ackedBy.push(target);
        } else if (sloppy) {
          // الـ node ده واقع: بنمشي للي بعده على الـ ring ونسيب hint
          while (extras.length) {
            const alt = extras.shift()!;
            if (await replicaPut(alt, key, [version], target)) {
              acks++;
              ackedBy.push(alt);
              hinted.push(`${alt}(for ${target})`);
              break;
            }
          }
        }
        settled++;
        finish();
      })();
    }
  });
}

// الـ PRNG بـ seed ثابت لكل node عشان الـ delay يتكرر
let prngState = hash32(id);
function rand() {
  prngState = (prngState + 0x6d2b79f5) >>> 0;
  let t = prngState;
  t = Math.imul(t ^ (t >>> 15), t | 1);
  t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
}
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
const delay = async () => {
  if (config.delayMax > 0) await sleep(config.delayMin + rand() * (config.delayMax - config.delayMin));
};

function persist(rec: object) {
  appendFileSync(dataFile, JSON.stringify(rec) + "\n");
}

function replay() {
  if (!existsSync(dataFile)) return;
  for (const line of readFileSync(dataFile, "utf8").split("\n")) {
    if (!line) continue;
    const r = JSON.parse(line);
    if (r.t === "put") store.set(r.key, r.versions);
    if (r.t === "hint") hints.push({ target: r.target, key: r.key, versions: r.versions });
    if (r.t === "clear") hints = hints.filter((h) => !(h.target === r.target && h.key === r.key));
    if (r.versions) for (const v of r.versions as Version[]) if (v.dot[0] === id) seq = Math.max(seq, v.dot[1]);
  }
}

function merge(list: Version[]) {
  return config.mode === "lww" ? lww(list) : reconcile(list);
}

function apply(key: string, incoming: Version[], durable = true) {
  const merged = merge([...(store.get(key) ?? []), ...incoming]);
  store.set(key, merged);
  tree = null;
  if (durable) persist({ t: "put", key, versions: merged });
}

async function replicaPut(target: string, key: string, versions: Version[], hint?: string): Promise<boolean> {
  if (target === id) {
    await delay();
    if (config.rejectWrites) return false;
    if (hint) {
      hints.push({ target: hint, key, versions });
      metrics.hintsStored++;
      persist({ t: "hint", target: hint, key, versions });
    } else apply(key, versions);
    return true;
  }
  if (Date.now() < (downUntil.get(target) ?? 0)) return false;
  try {
    const r = await fetch(`http://127.0.0.1:${peers[target]}/r/put`, {
      method: "POST",
      body: JSON.stringify({ key, versions, hint }),
      signal: AbortSignal.timeout(config.timeoutMs),
    });
    await r.arrayBuffer();
    if (r.status === 200) return true;
    return false;
  } catch {
    downUntil.set(target, Date.now() + 500);
    return false;
  }
}

async function replicaGet(target: string, key: string): Promise<Version[] | null> {
  if (target === id) {
    await delay();
    return store.get(key) ?? [];
  }
  if (Date.now() < (downUntil.get(target) ?? 0)) return null;
  try {
    const r = await fetch(`http://127.0.0.1:${peers[target]}/r/get?key=${encodeURIComponent(key)}`, { signal: AbortSignal.timeout(config.timeoutMs) });
    return ((await r.json()) as { versions: Version[] }).versions;
  } catch {
    downUntil.set(target, Date.now() + 500);
    return null;
  }
}

function digest(versions: Version[]) {
  return createHash("sha1").update(JSON.stringify(versions.map((v) => v.dot.join(":")).sort())).digest("hex").slice(0, 16);
}

async function coordGet(key: string, r: number) {
  const pref = ring.preference(key, N);
  const replies: { target: string; versions: Version[] }[] = [];
  return await new Promise<{ ok: boolean; versions: Version[]; answered: number }>((resolve) => {
    let settled = 0;
    let answered = false;
    for (const target of pref) {
      void (async () => {
        const v = await replicaGet(target, key);
        if (v) replies.push({ target, versions: v });
        settled++;
        if (!answered && replies.length >= r) {
          answered = true;
          resolve({ ok: true, versions: merge(replies.flatMap((x) => x.versions)), answered: replies.length });
        }
        if (settled === pref.length) {
          if (!answered) {
            answered = true;
            resolve({ ok: false, versions: [], answered: replies.length });
          }
          // الـ read repair: اللي عنده نسخة قديمة ياخد الدمج
          const all = merge(replies.flatMap((x) => x.versions));
          const want = digest(all);
          for (const x of replies) {
            if (digest(x.versions) !== want) {
              metrics.readRepairs++;
              void replicaPut(x.target, key, all);
            }
          }
        }
      })();
    }
  });
}

function leafOf(key: string) {
  return hash32(key) >>> (32 - DEPTH);
}

function buildTree(): string[][] {
  if (tree) return tree;
  const buckets: string[][] = Array.from({ length: 1 << DEPTH }, () => []);
  leafIndex = new Map();
  for (const [key, versions] of store) {
    const leaf = leafOf(key);
    const d = digest(versions);
    buckets[leaf].push(`${key}=${d}`);
    leafIndex.set(leaf, [...(leafIndex.get(leaf) ?? []), [key, d]]);
  }
  const sha = (s: string) => createHash("sha1").update(s).digest("hex").slice(0, 16);
  const levels: string[][] = [buckets.map((b) => sha(b.sort().join("|")))];
  while (levels[0].length > 1) {
    const prev = levels[0];
    const up: string[] = [];
    for (let i = 0; i < prev.length; i += 2) up.push(sha(prev[i] + prev[i + 1]));
    levels.unshift(up);
  }
  tree = levels;
  return levels;
}

function leafEntries(leaf: number) {
  buildTree();
  return leafIndex.get(leaf) ?? [];
}

// الـ anti-entropy: بنبدّل الـ hashes من فوق لتحت وننزل بس في الفروع المختلفة
async function merkleSync(peer: string, push: boolean) {
  let bytes = 0;
  const call = async (path: string, init?: RequestInit) => {
    const r = await fetch(`http://127.0.0.1:${peers[peer]}${path}`, init);
    const text = await r.text();
    bytes += path.length + (init?.body ? String(init.body).length : 0) + text.length;
    return JSON.parse(text);
  };
  const mine = buildTree();
  let frontier = [0];
  let nodesExamined = 0;
  for (let level = 0; level <= DEPTH; level++) {
    if (!frontier.length) break;
    nodesExamined += frontier.length;
    const remote = (await call(`/m/nodes`, { method: "POST", body: JSON.stringify({ level, idx: frontier }) })).hashes as string[];
    const differing = frontier.filter((idx, i) => mine[level][idx] !== remote[i]);
    if (level === DEPTH) {
      frontier = differing;
      break;
    }
    frontier = differing.flatMap((i) => [2 * i, 2 * i + 1]);
  }
  const leaves = frontier;
  const keysToFix = new Set<string>();
  for (const leaf of leaves) {
    const theirs = new Map((await call(`/m/leaf?idx=${leaf}`)).entries as [string, string][]);
    const ours = new Map(leafEntries(leaf));
    for (const k of new Set([...theirs.keys(), ...ours.keys()])) {
      if (theirs.get(k) !== ours.get(k)) keysToFix.add(k);
    }
  }
  let keysSynced = 0;
  if (keysToFix.size && push) {
    const items = [...keysToFix].map((k) => ({ key: k, versions: store.get(k) ?? [] }));
    const body = JSON.stringify({ items });
    const pulled = await call(`/m/merge`, { method: "POST", body });
    for (const it of pulled.items as { key: string; versions: Version[] }[]) apply(it.key, it.versions, false);
    keysSynced = keysToFix.size;
  }
  return { bytes, nodesExamined, leavesDiffering: leaves.length, keysDiffering: keysToFix.size, keysSynced };
}

  }

    const all = { ...peers, ...this.downPorts };

  }

    delete this.downPorts[id];
    await this.spawn(id);
    this.broadcast();

  }

English

The coordinator sends to all N replicas and answers after W acks for a write or R replies for a read. If R + W > N, the read set and the write set must overlap on at least one node, as long as they're drawn from the same set of N. Lesson 12 covers replication theory; here you measure the dial. W and R are chosen per request.

The run below injects 1–40 ms of delay per replica, seeded and labelled, kills one process halfway through, and writes then reads through a different coordinator. (1,1) is fastest and returned 38 stale reads out of 200. (2,2) had no stale reads and survived the kill. (3,1) also had no stale reads while healthy, but every write touching the dead node failed: 90 failed puts. In the (1,1) and (2,2) runs the 1–2 failed puts are requests in flight through the coordinator that was killed.

A failed write isn't rolled back. The W=3 write below returns 503 with 2 acks, yet the two live replicas keep the version and a read returns it. "Failed" means the system couldn't confirm the write, not that it didn't happen. Clients should retry with the same value or read the value back, and never treat 503 as "nothing changed".

async function coordGet(key: string, r: number) {
  const pref = ring.preference(key, N);
  const replies: { target: string; versions: Version[] }[] = [];
  return await new Promise<{ ok: boolean; versions: Version[]; answered: number }>((resolve) => {
    let settled = 0;
    let answered = false;
    for (const target of pref) {
      void (async () => {
        const v = await replicaGet(target, key);
        if (v) replies.push({ target, versions: v });
        settled++;
        if (!answered && replies.length >= r) {
          answered = true;
          resolve({ ok: true, versions: merge(replies.flatMap((x) => x.versions)), answered: replies.length });
        }
        if (settled === pref.length) {
          if (!answered) {
            answered = true;
            resolve({ ok: false, versions: [], answered: replies.length });
          }
          // الـ read repair: اللي عنده نسخة قديمة ياخد الدمج
          const all = merge(replies.flatMap((x) => x.versions));
          const want = digest(all);
          for (const x of replies) {
            if (digest(x.versions) !== want) {
              metrics.readRepairs++;
              void replicaPut(x.target, key, all);
            }
          }
        }
      })();
    }
  });
}

فين هستخدمه في شغلي؟ لو بتشتغل مع Cassandra، LOCAL_QUORUM هو (2,2) على RF=3. ولو الـ endpoint بتاع "user settings" مكتوب ONE، توقّع إن اليوزر يكتب ويعمل refresh ويلاقي القيمة القديمة. والأهم: في أي write بيرجع 503، اعمل الكود بتاعك على أساس إن الكتابة ممكن تكون حصلت، استخدم idempotency key، ومتفترضش rollback.

والغلطة الشائعة هنا إن R + W > N يعني strong consistency. دي overlap بس، ومع failed partial writes أو sloppy quorum ممكن تقرا حاجة غير اللي متوقعها.

Interview question: you set N=3, W=2, R=2. Can a read still be stale? Yes. The overlap holds only when both quorums come from the same three nodes. A sloppy quorum writes to a fallback node, a failed write leaves a partial version behind, and concurrent writes need conflict handling. R+W>N is a read-your-write guarantee on a fixed set, not linearizability.
السؤال: ظبطت N=3 و W=2 و R=2. هل القراءة لسه ممكن تبقى stale؟ أيوه. الـ overlap بيتحقق بس لو الـ quorumين من نفس التلات nodes. الـ sloppy quorum بيكتب على node بديل، والـ write الفاشل بيسيب partial version، والـ writes المتوازية محتاجة conflict handling. يعني R+W>N ده read-your-write على مجموعة ثابتة، مش linearizability.

Part 4 — Versions & siblings 🔴 Advancedالجزء 4 — الـ versions والـ siblings

English

Each write carries a vector clock built from the client's context plus a new event at the coordinator. Lesson 29 teaches vector clocks; here they sit on values. If neither clock dominates the other, the versions are concurrent and the store keeps both as siblings, returning both on the next read. Nothing is lost, and nothing is decided yet. The client merges and writes back with the combined context.

In the run, two clients read the same context and each added one item to the cart. The store returned 2 siblings with concurrent clocks. The client took the union and wrote back, and the next read returned one version with all three items. The same run with last-write-wins returned one version with one item gone, and no error appeared anywhere. That's the trade-off: application complexity against silent data loss. A union merge has its own failure: a removed item can come back, as the run shows with case. The Dynamo paper mentions this anomaly, and proper fixes are CRDTs or an operation log.

A real trap. Two writes through the same coordinator with the same empty context would produce {n1:1} and {n1:2}, and a plain vector clock says the first is before the second, so one write silently vanishes. This toy uses a dot, the coordinator's own event per write, kept apart from the context, and a version is dropped only if another version's context has seen its dot. That's the idea behind Dotted Version Vectors (paper in the sources).

// كل version معاه ⁦context (⁩اللي شافه الـ client قبل الكتابة) و ⁦dot (⁩الكتابة نفسها)
export type Clock = Record<string, number>;
export type Dot = [string, number];

export interface Version {
  value: unknown;
  dot: Dot;
  ctx: Clock;
  ts: number;
}

export const covers = (ctx: Clock, dot: Dot) => (ctx[dot[0]] ?? 0) >= dot[1];

// بنحذف أي version الـ context بتاع version تانية شافها، والباقي siblings
export function reconcile(list: Version[]): Version[] {
  const byDot = new Map<string, Version>();
  for (const v of list) byDot.set(v.dot.join(":"), v);
  const all = [...byDot.values()];
  return all.filter((v) => !all.some((u) => u !== v && covers(u.ctx, v.dot)));
}

// ده الـ last-write-wins: الأحدث بالـ ts يكسب والتاني بيضيع
export function lww(list: Version[]): Version[] {
  return [...list].sort((a, b) => b.ts - a.ts || b.dot[0].localeCompare(a.dot[0])).slice(0, 1);
}

// الـ context اللي بيرجع للـ client: كل اللي الـ versions دي شايفاه
export function contextOf(list: Version[]): Clock {
  const c: Clock = {};
  for (const v of list) {
    for (const [n, s] of Object.entries(v.ctx)) c[n] = Math.max(c[n] ?? 0, s);
    c[v.dot[0]] = Math.max(c[v.dot[0]] ?? 0, v.dot[1]);
  }
  return c;
}

// ده الـ vector clock العادي، وبنستخدمه عشان نوري العلاقة بين نسختين
export function compare(a: Clock, b: Clock): "before" | "after" | "equal" | "concurrent" {
  let less = false;
  let more = false;
  for (const n of new Set([...Object.keys(a), ...Object.keys(b)])) {
    if ((a[n] ?? 0) < (b[n] ?? 0)) less = true;
    if ((a[n] ?? 0) > (b[n] ?? 0)) more = true;
  }
  return less && more ? "concurrent" : less ? "before" : more ? "after" : "equal";
}

Part 5 — Hinted handoff & read repair 🔴 Advancedالجزء 5 — الـ hinted handoff والـ read repair

English

When a replica is down, a strict quorum fails and the store stops being writable. A sloppy quorum instead writes to the next healthy node on the ring with a hint naming the intended owner. In the run, node n4 is dead and a W=3 write still returns 200: the ack came from n1 holding a hint for n4. The holder keeps the hint in a separate table, retries periodically, and deletes it once delivered. The counts printed go from one hint stored and held to one replayed and zero held.

The cost is the guarantee from Part 3. With two of the three owners dead, the write went to a fallback, and once those owners came back before the hints were replayed, with the third owner now dead, a read with R=2 from the owners returned nothing even though R + W = 4 > N = 3. After the hints replayed the value appeared. Availability was bought with the possibility of a miss, which is why read-your-write needs care on a sloppy system.

Read repair is the other half. A replica that missed a write (one rejected it here) is found out on the next read: the coordinator notices a replica's digest differs from the merged result and writes the merged version back. It fixes data that gets read, but data nobody reads needs the Merkle trees of Part 6.

لو replica واقع، الـ quorum الصارم بيفشل والـ store بيبطل يقبل writes. الـ sloppy quorum بدل كده بيكتب على الـ node السليم اللي بعده على الـ ring ومعاه hint باسم صاحب النسخة الأصلي. في التجربة n4 ميت وكتابة W=3 برضه رجعت 200: الـ ack جه من n1 شايل hint لـ n4. اللي شايل الـ hint بيحطها في جدول لوحده، ويعيد المحاولة كل شوية، ويمسحها بعد التسليم. الأرقام المطبوعة راحت من hint واحد متخزن ومتشال، لـ واحد اتبعت وصفر متشال.

التمن هو الضمان اللي في Part 3. مع موت 2 من التلات owners، الكتابة راحت لـ fallback، ولما الـ owners رجعوا قبل ما الـ hints تتبعت والـ owner التالت مات، قراءة R=2 منهم رجعت فاضية رغم إن R + W = 4 > N = 3. وبعد الـ replay القيمة ظهرت. يعني اشترينا الـ availability بإمكانية الـ miss، وعشان كده read-your-write محتاج حرص على sloppy systems.

الـ read repair هو النص التاني. الـ replica اللي فاتها write (هنا replica رفضت) بتتكشف في القراءة الجاية: الـ coordinator بيلاحظ إن digest بتاع replica مختلف عن النتيجة المدموجة وبيكتب النسخة المدموجة ليها. ده بيصلّح الـ data اللي بتتقري، إنما الـ data اللي محدش بيقراها محتاجة Merkle trees بتاعة Part 6.

فين هستخدمه في شغلي؟ Cassandra فيها hinted handoff و read repair بالظبط، بس الـ hints ليها وقت محدد، وأي node غايب أكتر من كده بيحتاج nodetool repair. لما تلاقي "البيانات رجعت قديمة بعد ما node رجع"، ده اللي بيحصل. وفي أي نظام sloppy، لو عايز read-your-write للجلسة نفسها، خليها sticky على نفس الـ replica set أو ارفع R.

Part 6 — Merkle trees 🔴 Advancedالجزء 6 — الـ Merkle trees

English

Read repair only touches keys someone reads, and hints have a limited life. Anti-entropy compares replicas in the background, and a Merkle tree makes that cheap: leaves hash key ranges, each parent hashes its children, and two replicas compare from the root down, descending only where hashes differ. In this toy the leaves are 4,096 buckets over the hash space. The real thing keeps one tree per key range, which is why ring changes are expensive: the Dynamo paper moved to fixed-size partitions partly for this reason.

Run on two real processes with 20,000 keys: with 10 keys different, Merkle exchanged about 8 KB against 673 KB for comparing every key's digest, and found exactly those 10 keys. The Merkle number also includes shipping the changed values while the compare-all number is only the digests, so the comparison favours compare-all. With 100 keys different it cost about 65 KB (about 10%). With half the keys different it cost about 2.7 MB, about four times more than comparing everything, because it walks nearly the whole tree and then still ships the data.

So Merkle trees are for the normal case of a small divergence. Membership in a real store comes from a gossip protocol (lesson 28), and the toy just uses a static list. Storage underneath is usually an LSM tree (lesson 35); the toy uses an in-memory map plus a JSON log.

function leafOf(key: string) {
  return hash32(key) >>> (32 - DEPTH);
}

function buildTree(): string[][] {
  if (tree) return tree;
  const buckets: string[][] = Array.from({ length: 1 << DEPTH }, () => []);
  leafIndex = new Map();
  for (const [key, versions] of store) {
    const leaf = leafOf(key);
    const d = digest(versions);
    buckets[leaf].push(`${key}=${d}`);
    leafIndex.set(leaf, [...(leafIndex.get(leaf) ?? []), [key, d]]);
  }
  const sha = (s: string) => createHash("sha1").update(s).digest("hex").slice(0, 16);
  const levels: string[][] = [buckets.map((b) => sha(b.sort().join("|")))];
  while (levels[0].length > 1) {
    const prev = levels[0];
    const up: string[] = [];
    for (let i = 0; i < prev.length; i += 2) up.push(sha(prev[i] + prev[i + 1]));
    levels.unshift(up);
  }
  tree = levels;
  return levels;
}

function leafEntries(leaf: number) {
  buildTree();
  return leafIndex.get(leaf) ?? [];
}

// الـ anti-entropy: بنبدّل الـ hashes من فوق لتحت وننزل بس في الفروع المختلفة
async function merkleSync(peer: string, push: boolean) {
  let bytes = 0;
  const call = async (path: string, init?: RequestInit) => {
    const r = await fetch(`http://127.0.0.1:${peers[peer]}${path}`, init);
    const text = await r.text();
    bytes += path.length + (init?.body ? String(init.body).length : 0) + text.length;
    return JSON.parse(text);
  };
  const mine = buildTree();
  let frontier = [0];
  let nodesExamined = 0;
  for (let level = 0; level <= DEPTH; level++) {
    if (!frontier.length) break;
    nodesExamined += frontier.length;
    const remote = (await call(`/m/nodes`, { method: "POST", body: JSON.stringify({ level, idx: frontier }) })).hashes as string[];
    const differing = frontier.filter((idx, i) => mine[level][idx] !== remote[i]);
    if (level === DEPTH) {
      frontier = differing;
      break;
    }
    frontier = differing.flatMap((i) => [2 * i, 2 * i + 1]);
  }
  const leaves = frontier;
  const keysToFix = new Set<string>();
  for (const leaf of leaves) {
    const theirs = new Map((await call(`/m/leaf?idx=${leaf}`)).entries as [string, string][]);
    const ours = new Map(leafEntries(leaf));
    for (const k of new Set([...theirs.keys(), ...ours.keys()])) {
      if (theirs.get(k) !== ours.get(k)) keysToFix.add(k);
    }
  }
  let keysSynced = 0;
  if (keysToFix.size && push) {
    const items = [...keysToFix].map((k) => ({ key: k, versions: store.get(k) ?? [] }));
    const body = JSON.stringify({ items });
    const pulled = await call(`/m/merge`, { method: "POST", body });
    for (const it of pulled.items as { key: string; versions: Version[] }[]) apply(it.key, it.versions, false);
    keysSynced = keysToFix.size;
  }
  return { bytes, nodesExamined, leavesDiffering: leaves.length, keysDiffering: keysToFix.size, keysSynced };
}

بالعامية

الـ read repair بيلمس الـ keys اللي حد بيقراها بس، والـ hints ليها عمر محدود. فالـ anti-entropy بيقارن الـ replicas في الخلفية، وشجرة Merkle بتخليه رخيص: الأوراق بتعمل hash لـ key ranges، وكل parent بيعمل hash لأولاده، والـ replicaتين بيقارنوا من الـ root لتحت، وبينزلوا بس في المكان اللي الـ hash مختلف فيه. في الـ toy الأوراق 4,096 bucket على hash space. الحقيقي بيحتفظ بشجرة لكل key range، وعشان كده تغييرات الـ ring غالية: ورقة Dynamo نقلت لـ fixed-size partitions لسبب زي ده.

على 2 processes حقيقيين بـ 20,000 key: لما 10 keys مختلفين، Merkle بدّل حوالي 8 KB مقابل 673 KB لمقارنة digest كل الـ keys، ولقى الـ 10 بالظبط. ورقم Merkle كمان فيه شحن القيم المتغيرة، ورقم compare-all الـ digests بس، فالمقارنة ظالمة لـ Merkle. مع 100 key مختلفين كلّف حوالي 65 KB، يعني حوالي 10%. مع نص الـ keys مختلفين كلّف حوالي 2.7 MB، يعني أربع مرات مقارنة الكل، لأنه بيمشي الشجرة كلها تقريبًا وبعدين يشحن الـ data.

فالـ Merkle trees للحالة العادية بتاعة divergence صغير. الـ membership في store حقيقي من gossip protocol (درس 28)، والـ toy بيستخدم قايمة ثابتة بس. والـ storage تحت عادة LSM tree (درس 35)، والـ toy عنده map في الـ memory و JSON log.

فين هستخدمه في شغلي؟ لما تعمل sync بين 2 systems، زي catalog بين Postgres و Elasticsearch، أو بين region وregion: متفترضش إن compare-all رخيص. فكرة الشجرة ممكن تتطبق بسهولة: اعمل hash لكل range من الـ IDs وقارن الـ ranges، ولو فيه اختلاف انزل جوه الـ range ده. وبعدين nodetool repair في Cassandra بيبني نفس الشجرة دي.

والغلطة الشائعة هنا إنك تكمّل بالشجرة حتى لما node غايب من مدة طويلة؛ ساعتها الفرق كبير والأرخص تعمل نسخ كامل أو streaming للـ range كله.

Part 7 — Trade-offs & review 🔴 Advancedالجزء 7 — الموازنات والمراجعة

English

Everything you just ran maps to a section of the 2007 Dynamo paper. One correction is essential. Amazon DynamoDB the service is not the 2007 Dynamo design. The USENIX ATC 2022 paper says that DynamoDB's replication group "uses Multi-Paxos for leader election and consensus", that "only the leader replica can serve write and strongly consistent read requests", and that a write is acknowledged once a quorum of peers persists the log record. That's leader-based replication, without siblings or client-side reconciliation, which is much closer to Spanner and Raft-based stores than to this toy. Saying "DynamoDB uses vector clocks" in an interview is a red flag.

What breaks at 10×. Vector clocks grow with one entry per coordinator, as the output below shows: the paper truncates at a threshold it gives as "say 10", accepting that truncation can cause false conflicts. Anti-entropy gets heavy once trees are rebuilt for ring changes, membership state grows with node count, and hot keys hit a single partition regardless of the total. The 10× numbers below are arithmetic.

Interviewer looks for: consistent hashing with vnodes, quorum math including what it doesn't guarantee, conflict handling, failure handling. Red flag: saying "use DynamoDB" as a design, or claiming R+W>N is linearizable. Routine: a one-page design doc using project/design-docs/0000-template.md, compare it with the key-value store chapter of Alex Xu's System Design Interview volume 1, and write down what you missed.

كل اللي شغّلته ليه مكان في ورقة Dynamo بتاعة 2007. وفيه تصحيح مهم جدًا: Amazon DynamoDB الخدمة مش هي تصميم Dynamo بتاع 2007. ورقة USENIX ATC 2022 بتقول إن replication group بتاع DynamoDB "uses Multi-Paxos for leader election and consensus"، و"only the leader replica can serve write and strongly consistent read requests"، وإن الـ write بيتأكد لما quorum من الـ peers يخزّنوا log record. ده replication بـ leader، من غير siblings ولا reconciliation عند الـ client، وأقرب بكتير لـ Spanner والأنظمة اللي شغالة بـ Raft من الـ toy ده. لو قلت في interview "DynamoDB بيستخدم vector clocks" فده red flag.

Interview question: is DynamoDB built on the Dynamo paper? The name is shared, the design isn't. The ATC 2022 paper describes Multi-Paxos replication groups with a leader for each partition, write-ahead logs replicated to a quorum of peers, and strongly consistent reads from the leader. The paper describes no sloppy quorums and no vector clocks with client reconciliation.
السؤال: هل DynamoDB مبني على ورقة Dynamo؟ الاسم مشترك، التصميم لأ. ورقة ATC 2022 بتوصف replication groups بـ Multi-Paxos وليها leader لكل partition، و write-ahead logs بتتنسخ لـ quorum من الـ peers، و strongly consistent reads من الـ leader. والورقة مش بتوصف sloppy quorums ولا vector clocks مع reconciliation عند الـ client.

Common mistakes · غلطات شائعة

❌ Quorum means strong consistency 
// الكلام ده مش صح: R+W أكبر من N مش linearizable

await put(key, value, opts);
// لو الـ fallback هو اللي استلم، القراءة ممكن تفوّتها
const v = await get(key, { r: 2 });
✅ Say exactly what you get 
// لو عايز overlap مضمون على نفس الـ N استخدم strict quorum
const opts = { w: 2, sloppy: false };
const res = await put(key, value, opts);
// لو الـ 503 رجع، الكتابة ممكن تكون حصلت، فكرر بـ idempotency key
if (res.status === 503) await retryWithSameKey(key, value);
بالعامية

❌ الـ R+W>N مع sloppy quorum زي ما شفت في Part 5 ممكن القراءة تفوّت الكتابة، فمش strong consistency. ✅ قول بالظبط إيه اللي عندك: strict quorum عشان overlap مضمون، أو sloppy عشان availability، وفي الحالتين الـ 503 معناه إن الكتابة ممكن تكون حصلت.

❌ Last-write-wins for a cart

await store.set(`cart:${id}`, nextCart);
✅ Merge concurrent versions

const { values, context } = await get(key);
await put(key, union(values), { context });
بالعامية

❌ last-write-wins ضيّع item من الـ cart في التجربة من غير ولا error. ✅ الـ siblings معناها إن الـ client بيشوف الاتنين ويدمج، والـ context بيقول للـ store إن الكتابة دي شافت اللي قبلها، فيشيل الـ siblings.

❌ Writing without the context

await put(key, { items: ["phone"] }, {});
✅ Read, then write with the context 
// الـ context اللي رجع من الـ read هو دليل إن الكتابة شافت اللي قبلها
const { values, context } = await get(key);
await put(key, addItem(values, "phone"), { context });
بالعامية

❌ كتابة من غير context بتتعامل على إنها concurrent مع كل اللي قبلها: 3 كتابات طلعوا 3 siblings في التجربة. ✅ اقرا الأول وابعت الـ context، فالـ store يعرف إن كتابتك فعلًا جديدة ويسيب الـ siblings القديمة.

3. A counter that merges itself 🔴 hard Siblings of a counter are annoying to merge by hand. Write a G-counter: one slot per node, increment your own slot, merge with max per slot. Show that merging is commutative and idempotent.
الـ siblings بتاعة counter صعب دمجها بإيدك. اكتب G-counter: خانة لكل node، زوّد خانتك إنت بس، والدمج max لكل خانة. وبيّن إن الدمج commutative و idempotent.
Solution · الحل 
// الحل: counter بينضم لوحده، كل node ليه خانة بتاعته، والدمج max لكل خانة
type GCounter = Record<string, number>;

const increment = (c: GCounter, node: string, by = 1): GCounter => ({ ...c, [node]: (c[node] ?? 0) + by });

function merge(a: GCounter, b: GCounter): GCounter {
  const out: GCounter = { ...a };
  for (const [n, v] of Object.entries(b)) out[n] = Math.max(out[n] ?? 0, v);
  return out;
}

const total = (c: GCounter) => Object.values(c).reduce((s, v) => s + v, 0);

// تحديثين متوازيين على replica مختلفة، من نفس النقطة
const base: GCounter = { n1: 2 };
const a = increment(base, "n2", 3);
const b = increment(base, "n4", 5);
const merged = merge(a, b);
console.log(`a=${JSON.stringify(a)} b=${JSON.stringify(b)} merged=${JSON.stringify(merged)} total=${total(merged)}`);
console.log(`merge is commutative: ${total(merge(a, b)) === total(merge(b, a))}, idempotent: ${total(merge(merged, merged)) === total(merged)}`);
a={"n1":2,"n2":3} b={"n1":2,"n4":5} merged={"n1":2,"n2":3,"n4":5} total=10
merge is commutative: true, idempotent: true

Cheat sheet · الخلاصة

  • Size by the larger of storage and replica ops: 10 TB × 3 ÷ 1.4 TB ≈ 22 nodes, 300k replica ops/s, 30 with headroom.
  • Preference list = first N distinct nodes clockwise. Any node can coordinate. Vnodes flatten the load.
  • W acks, R replies, R+W>N for overlap on a fixed set. It's not linearizability.
  • Measured: (1,1) fast with 38/200 stale, (2,2) 0 stale and survives a kill, (3,1) 0 stale and 90 failed writes.
  • A failed write isn't rolled back: a 503 can leave the value on replicas, so retry idempotently.
  • Vector clock = context + a new event. Concurrent versions become siblings; the client merges and writes back the context.
  • Last-write-wins silently drops a write. Union merges can resurrect deletes. CRDTs avoid both for the right data types.
  • Use a dot per write, or two writes through one coordinator with the same context look ordered and one is lost.
  • Sloppy quorum + hints keeps writes alive but breaks the R+W>N overlap until hints replay.
  • Read repair fixes what's read. Merkle trees fix what's not, cheaply when divergence is small: about 1% of compare-all for 10 keys, about 400% at 50%.
  • DynamoDB (2022) is leader-based Multi-Paxos per partition, not the 2007 Dynamo design.
بالعامية
  • احسب الأكبر بين الـ storage والـ replica ops: 10 TB في 3 على 1.4 TB حوالي 22 node، و300 ألف replica op في الثانية، و30 مع headroom.
  • الـ preference list أول N nodes مختلفين مع عقارب الساعة، وأي node ينفع coordinator، والـ vnodes بتساوي الـ load.
  • W acks و R رد، و R+W>N يدوك overlap على مجموعة ثابتة، وده مش linearizability.
  • المقاس: (1,1) سريع وفيه 38/200 stale، و(2,2) صفر stale وعدّى موت node، و(3,1) صفر stale و90 write فشل.
  • الـ write الفاشل مش بيترجّع: 503 ممكن يسيب القيمة على replicas، فكرر بـ idempotency.
  • الـ vector clock هو الـ context زائد event جديد، والـ versions المتوازية بتبقى siblings والـ client يدمج ويكتب بالـ context.
  • الـ last-write-wins بيضيّع write من غير صوت، والـ union ممكن يرجّع المحذوف، والـ CRDTs بتحل الاتنين للأنواع المناسبة.
  • استخدم dot لكل write، وإلا كتابتين على نفس الـ coordinator بنفس الـ context هيبانوا مرتبين وواحدة تضيع.
  • الـ sloppy quorum والـ hints بيخلوا الـ writes شغالة، بس بيكسروا overlap الـ R+W>N لحد الـ replay.
  • الـ read repair بيصلّح اللي بيتقري، والـ Merkle trees بتصلح الباقي، وبرخص لما الفرق صغير: حوالي 1% لـ 10 keys، وحوالي 400% عند 50%.
  • DynamoDB (2022) leader-based بـ Multi-Paxos لكل partition، مش تصميم Dynamo بتاع 2007.
