Why this matters · ليه ده مهم

English

These two cases teach opposite instincts. Autocomplete moves the work to before the request: answers are computed offline so a read costs almost nothing, and the design question becomes how stale you can afford to be. A crawler is about restraint: you could fetch much faster than you should, and the design question is how to go fast overall while staying slow against each site. Product search boxes, sitemap and link checkers, price scrapers and data imports from partner sites all reuse one of these two shapes.

بالعامية

الـ cases دول بيعلموا غريزتين عكس بعض. الـ autocomplete بينقل الشغل لقبل الـ request: الإجابات بتتحسب offline فالقراية تكلفتها شبه صفر، والسؤال بيبقى قد إيه تستحمل الداتا تبقى قديمة. والـ crawler موضوعه ضبط النفس: تقدر تجيب صفحات أسرع بكتير من اللي المفروض، والسؤال بيبقى إزاي تبقى سريع في المجموع وبطيء مع كل موقع. مربع البحث في أي منتج، و sitemap و link checkers، و scrapers الأسعار، و imports الداتا من مواقع الشركاء، كلهم بيستخدموا شكل من الاتنين دول.

Part 1 — Autocomplete: the exercise 🟡 Intermediateالجزء 1 — الـ autocomplete: التمرين

⏱ Stop. Set a 45-minute timer, talk out loud, design on paper, and only then read on.

Prompt: design search autocomplete. 10M daily users, 10 searches a day each, 20 characters per search. Return the 5 most popular completions for what's typed so far, in under 100 ms. English only, lowercase, no personalization. Suggestions must be safe, and new popular terms should appear within a week.

Produce: QPS (say whether you assume debounce), storage, the API, and a diagram that separates the query path from the data pipeline.

وقّف هنا. شغّل تايمر 45 دقيقة، واتكلم بصوت عالي، وارسم على ورقة، وبعد كده بس كمّل قراية.

المطلوب: صمّم search autocomplete. 10 مليون مستخدم في اليوم، كل واحد بيعمل 10 عمليات بحث، وكل بحث 20 حرف. رجّع أشهر 5 إكمالات للي مكتوب لحد دلوقتي في أقل من 100 ms. إنجليزي بس، lowercase، من غير personalization. الاقتراحات لازم تبقى آمنة، والكلمات الجديدة المشهورة تظهر خلال أسبوع.

طلّع: الـ QPS (وقول إنت مفترض debounce ولا لأ)، والـ storage، والـ API، و diagram بيفصل الـ query path عن الـ data pipeline.

English

Model answer. 10M × 10 × 20 = 2B requests/day ≈ 23k QPS with one request per character, and ≈46k at a 2× peak. Reference solutions usually round this up to ≈24k. Debounce changes the number a lot, so state which you assume: the simulation below gives 15 requests per search at 150 ms and 9.4 at 250 ms, for 17k and 11k QPS. The raw query log is about 2 GB/day. If 20% of queries are new, about 0.4 GB/day of new text reaches the index.

The shape. Two separate paths that meet at one artifact. The query path is read-only and must be very fast: browser cache, CDN, then a suggestion service reading a precomputed structure. The data pipeline is slow and offline: logs, aggregation, build, validate, swap. Nothing on the query path computes a ranking, and nothing in the pipeline serves a user.

API and data model. One endpoint, GET /v1/suggest?q=ca&limit=5. The data model is query_counts(query, week, count) as pipeline output, and a versioned prefix → top-5 structure as the serving artifact.

Part 2 — Top-k per prefix, real 🟡 Intermediateالجزء 2 — أعلى k لكل prefix، على الحقيقي

English

Tries and top-k are taught in 01 · Heaps & tries (parts 4, 6 and 7). What's new here is the design move: store the answer at each node. Sort queries by count descending and insert in that order, and the first 5 queries to reach a node are its top 5 by construction. A lookup then walks the prefix and returns a stored list, so its cost depends on the prefix length and not on how many queries match it.

The test data is a generated 1M-query log: real English words from a word list, with popularity drawn from a seeded Zipf distribution, so it's a stand-in for a real log. The table compares three ways of serving it. The trie answers in well under a microsecond in-process but costs ≈149 MB of JavaScript heap, because a Map per node is expensive. A Redis sorted set per prefix holding only the top 5 costs ≈34 MB for 377k keys and answers in ≈0.11 ms over loopback. Postgres with pg_trgm computes the answer at query time.

Postgres looks fine in this table, and that's the honest result at 120k distinct queries. Read the plan though: for c% it fetches every matching row and sorts them. The work grows with the number of matches, which is why the 1-character prefix is 7× slower than the 5-character one. Multiply by traffic: 23k QPS at ≈2.1 ms is about 48 seconds of database time every second if all requests were short prefixes. Precomputing makes the expensive prefixes exactly as cheap as the rare ones.

To run these examples Node 22+, "type": "module" in package.json, and npm i ioredis pg an-array-of-english-words. Run trie-top5.ts with --expose-gc. Start a throwaway Redis on a non-default port and write that port into a redis.port file one folder up. The guard below refuses an empty or default port, so an example with FLUSHALL in it can never reach a real Redis. compare-stores.ts imports pg-cluster.mjs, a helper that starts a throwaway Postgres on a free port. Use your own disposable instance instead, and never a database you care about.

import { readFileSync } from "node:fs";

// الدالة دي بترفض أي port فاضي أو default، عشان متوصلش بالـ Redis الحقيقي بالغلط
export function redisPort(): number {
  const raw = readFileSync(new URL("../redis.port", import.meta.url), "utf8").trim();
  const n = Number(raw);
  if (!/^\d+$/.test(raw) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error("refusing port " + raw);
  }
  return n;
}

import { createRequire } from "node:module";

const require = createRequire(import.meta.url);
const words: string[] = require("an-array-of-english-words");

export function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// الـ log ده متولّد: كلمات إنجليزي حقيقية و popularity بتوزيع Zipf بـ seed ثابت
export function generateQueryLog(total = 1_000_000, distinct = 200_000) {
  const rand = mulberry32(2026);
  const pool = words.filter((w) => w.length >= 3 && w.length <= 20);
  // خلط الكلمات عشان الـ popularity ميبقاش ماشي مع الترتيب الأبجدي
  for (let i = pool.length - 1; i > 0; i--) {
    const j = Math.floor(rand() * (i + 1));
    [pool[i], pool[j]] = [pool[j]!, pool[i]!];
  }
  const queries = pool.slice(0, distinct);
  const s = 1.0;
  const cdf = new Float64Array(distinct);
  let sum = 0;
  for (let i = 0; i < distinct; i++) { sum += 1 / (i + 1) ** s; cdf[i] = sum; }
  const counts = new Map<string, number>();
  for (let n = 0; n < total; n++) {
    const target = rand() * sum;
    let lo = 0, hi = distinct - 1;
    while (lo < hi) { const m = (lo + hi) >> 1; if (cdf[m]! < target) lo = m + 1; else hi = m; }
    const q = queries[lo]!;
    counts.set(q, (counts.get(q) ?? 0) + 1);
  }
  return counts;
}

import { generateQueryLog } from "./querylog.ts";

class TrieNode {
  children = new Map<string, TrieNode>();
  // الـ top فيها أرقام الاستعلامات مش النص، عشان الذاكرة
  top: number[] = [];
}

export function buildTrie(counts: Map<string, number>) {
  // الترتيب تنازلي بالـ count، فأول 5 يوصلوا لأي node هما الـ top 5 بتوعها
  const sorted = [...counts.entries()].sort((a, b) => b[1] - a[1]);
  const names = sorted.map(([q]) => q);
  const root = new TrieNode();
  let nodes = 1;
  sorted.forEach(([query], id) => {
    let node = root;
    for (const ch of query) {
      let next = node.children.get(ch);
      if (!next) { next = new TrieNode(); node.children.set(ch, next); nodes++; }
      node = next;
      if (node.top.length < 5) node.top.push(id);
    }
  });
  return { root, names, nodes };
}

export function suggest(t: ReturnType<typeof buildTrie>, prefix: string): string[] {
  let node = t.root;
  for (const ch of prefix) {
    const next = node.children.get(ch);
    if (!next) return [];
    node = next;
  }
  return node.top.map((id) => t.names[id]!);
}

Part 3 — Autocomplete: pipeline & review 🟡 Intermediateالجزء 3 — الـ autocomplete: الـ pipeline والمراجعة

English

Pipeline. Logs go through a weekly aggregation, the small MapReduce from 22 · Batch vs stream with a map, a shuffle by hash and a reduce. Then the build produces a complete new version under its own namespace, and one atomic write flips an active pointer to it. The run below compares that with updating keys in place: while a user types two characters in a row, an in-place update returned a mix of old and new data in 44 of 238 reads, and the pointer swap in 0 of 238. Keep the old version for a while, since rollback is the same one-key write.

Filtering. Remove blocked terms before computing the top 5, or you'll return 4 suggestions when a banned term ranks first, as the output shows. Keep a small serving-time blocklist as well, because a takedown can't wait for next week's build.

Sharding. Splitting the alphabet into even ranges is the wrong partition because traffic isn't even across letters. In this log, equal ranges give shards with 34%, 17%, 35% and 14% of the traffic, and a greedy routing table built from the measured distribution gives 25% each. The log comes from a dictionary, so u is inflated by the many "un-" words, but s and c are still near the top. Build the table from your real traffic and split a hot letter by its second character when one letter alone is too big for a shard.

Caching and 10×. Each layer removes load from the next, as in the response header in Part 1. Short prefixes are the most cacheable because there are few of them, and an hour of staleness is invisible for a weekly build. At 10× (≈231k QPS) reads scale with replicas and the CDN, so reads aren't what breaks first. The build window breaks first, since 10× the logs must still finish inside the cycle, followed by skew on the hottest shards. Trending terms also expose the staleness of a weekly build, which needs a small real-time layer merged at read time.

function mapReduce(log: string[], reducers = 4) {
  const shards = Array.from({ length: reducers }, () => new Map<string, number>());
  for (const q of log) {
    const q2 = q.trim().toLowerCase();
    if (!q2) continue;
    const h = [...q2].reduce((acc, c) => (acc * 31 + c.charCodeAt(0)) >>> 0, 7);
    const shard = shards[h % reducers]!;
    shard.set(q2, (shard.get(q2) ?? 0) + 1);
  }
  return new Map(shards.flatMap((s) => [...s]));
}

English

Model answer. 1B pages/month ≈ 386 pages/s, say ≈400, and ≈800 at a 2× peak. At 500 KB that's about 1.5 Gbps on average and 500 TB/month raw, or 30 PB over 5 years before compression, and roughly a fifth of that if HTML compresses 5×. Those are all easy numbers. The constraint that shapes the design is politeness: at one request per second per host, 386 pages/s requires pages to be spread across at least several hundred busy hosts at all times, and a million hosts leaves plenty of headroom.

Requirements. Politeness: at most one in-flight request per host, a minimum delay between requests, robots.txt honoured. Freshness: recrawl according to how often a page changes. Robustness: bad HTML, timeouts, infinite URL spaces. Extensibility: new content types later.

Components and data model. BFS on a graph is the base algorithm, and the URL frontier is what turns it into something safe to run at scale. Seeds go to the frontier, fetchers pull from it, parsers extract links, and the dedup stage decides what goes back in. Data model: url_state(url_hash, host, depth, last_fetched_at, next_fetch_at, content_hash), hosts(host, robots_fetched_at, delay_ms), and page bodies in object storage keyed by content hash. The operator API is small: POST /seeds, GET /crawl/status, POST /hosts/{host}/block.

Part 5 — Frontier & politeness, real 🟡 Intermediateالجزء 5 — الـ Frontier والـ politeness، على الحقيقي

English

The frontier has two layers. Front queues are ordered by priority and answer "what matters most". Back queues hold one FIFO per host and answer "what is allowed now". A selector takes the next URL from a host that is ready, with no request in flight, and whose delay has passed. The delay starts when the previous response finishes, so a slow site automatically gets crawled more slowly. That is the classic Mercator layout, reduced to about 50 lines below.

The stand-ins are four real local HTTP servers, one port per host, each logging every request it sees. Trust the server's log rather than the crawler's intentions. Without politeness, each site saw up to 8 concurrent requests and a minimum gap of 0 ms, and every /private page was fetched. With politeness, each host saw 1 concurrent request and a minimum gap of ≈136 ms against a configured 120 ms, the site asking for Crawl-delay: 0.5 saw ≈514 ms, and 4 pages were blocked by robots.txt.

On robots.txt, the standard is RFC 9309, and this parser is deliberately small. A real one needs Allow, the longest-match rule, and status handling: a 4xx means "unavailable" so the crawler may proceed, and a 5xx or network error means "unreachable" so it must assume complete disallow. Caches shouldn't be used for more than 24 hours. Crawl-delay isn't in the RFC at all, it's a common extension, so treat it as a request you choose to honour. Priority beats plain BFS for the same reason it does in a job queue: BFS reached the hub pages at positions 13–15 of 22, and priority reached them at positions 1–3.

// الـ URL frontier: priority queues قدّام، وطابور لكل host ورا، و delay أدنى لكل host
type Item = { url: string; depth: number };
type Back = { queue: Item[]; readyAt: number; busy: boolean; delayMs: number };

export class Frontier {
  front: Item[][] = [[], [], []];
  back = new Map<string, Back>();
  defaultDelayMs: number;
  onePerHost: boolean;
  constructor(defaultDelayMs: number, onePerHost: boolean) {
    this.defaultDelayMs = defaultDelayMs;
    this.onePerHost = onePerHost;
  }

  add(url: string, depth: number, priority: number) {
    this.front[priority]!.push({ url, depth });
  }
  setDelay(host: string, delayMs: number) {
    this.hostQueue(host).delayMs = delayMs;
  }
  hostQueue(host: string): Back {
    let b = this.back.get(host);
    if (!b) { b = { queue: [], readyAt: 0, busy: false, delayMs: this.defaultDelayMs }; this.back.set(host, b); }
    return b;
  }
  // الخطوة دي بتنقل من الأولويات العالية الأول لطوابير الـ hosts
  private refill() {
    for (const q of this.front) {
      while (q.length > 0) {
        const item = q.shift()!;
        this.hostQueue(new URL(item.url).host).queue.push(item);
      }
    }
  }
  // الدالة دي بتدّي URL من host جاهز ومفيش عليه طلب شغال، وإلا بترجع null
  take(now: number) {
    this.refill();
    let best: Back | null = null;
    for (const b of this.back.values()) {
      if (b.queue.length === 0 || b.busy || b.readyAt > now) continue;
      if (!best || b.readyAt < best.readyAt) best = b;
    }
    if (!best) return null;
    best.busy = this.onePerHost;
    return { ...best.queue.shift()!, back: best };
  }
  // الـ delay بيتحسب من وقت انتهاء الطلب، فالموقع البطيء بياخد راحته
  release(back: Back, now: number) {
    back.busy = false;
    back.readyAt = now + back.delayMs;
  }
  pending() {
    return this.front.some((q) => q.length > 0) || [...this.back.values()].some((b) => b.queue.length > 0 || b.busy);
  }
}

export function parseRobots(text: string) {
  const disallow: string[] = [];
  let crawlDelaySec: number | null = null;
  let applies = false;
  for (const raw of text.split("\n")) {
    const [field, ...rest] = raw.split(":");
    const name = field!.trim().toLowerCase();
    const value = rest.join(":").trim();
    if (name === "user-agent") applies = value === "*";
    else if (applies && name === "disallow" && value) disallow.push(value);
    else if (applies && name === "crawl-delay") crawlDelaySec = Number(value);
  }
  return { disallow, crawlDelaySec };
}

export type CrawlOptions = {
  seeds: string[];
  workers: number;
  delayMs: number;
  polite: boolean;
  maxPages: number;
  priority?: (url: string) => number;
  maxDepth?: number;
  maxUrlLength?: number;
};

export async function crawl(o: CrawlOptions) {
  const frontier = new Frontier(o.polite ? o.delayMs : 0, o.polite);
  const seen = new Set<string>();
  const robots = new Map<string, ReturnType<typeof parseRobots>>();
  const order: string[] = [];
  let fetched = 0, rejectedByLimit = 0, blockedByRobots = 0, inFlight = 0;

  const enqueue = (url: string, depth: number) => {
    if (seen.has(url)) return;
    seen.add(url);
    frontier.add(url, depth, o.priority?.(url) ?? 1);
  };
  o.seeds.forEach((s) => enqueue(s, 0));

  async function allowed(url: URL) {
    if (!o.polite) return true;
    let rules = robots.get(url.host);
    if (!rules) {
      const res = await fetch(`${url.origin}/robots.txt`);
      rules = parseRobots(await res.text());
      robots.set(url.host, rules);
      if (rules.crawlDelaySec !== null) frontier.setDelay(url.host, rules.crawlDelaySec * 1000);
    }
    return !rules.disallow.some((d) => url.pathname.startsWith(d));
  }

  async function worker() {
    for (;;) {
      if (fetched >= o.maxPages) return;
      const item = frontier.take(performance.now());
      if (!item) {
        if (!frontier.pending() && inFlight === 0) return;
        await new Promise((r) => setTimeout(r, 2));
        continue;
      }
      inFlight++;
      try {
        const url = new URL(item.url);
        if (await allowed(url)) {
          const res = await fetch(url);
          const html = await res.text();
          fetched++;
          order.push(url.pathname);
          for (const m of html.matchAll(/href="([^"]+)"/g)) {
            const next = new URL(m[1]!, url).href;
            const nextDepth = item.depth + 1;
            // حدود الـ traps: العمق وطول الـ URL
            if ((o.maxDepth !== undefined && nextDepth > o.maxDepth) || (o.maxUrlLength !== undefined && next.length > o.maxUrlLength)) {
              rejectedByLimit++;
              continue;
            }
            enqueue(next, nextDepth);
          }
        } else blockedByRobots++;
      } finally {
        inFlight--;
        frontier.release(item.back, performance.now());
      }
    }
  }
  await Promise.all(Array.from({ length: o.workers }, worker));
  return { fetched, rejectedByLimit, blockedByRobots, order };
}

}

Interview question "You have 100 fetcher threads and one huge site. How do you stop them from hammering it?" → Politeness can't live in the fetchers, because they don't know about each other. Part 6 — Dedup & traps 🟡 Intermediateالجزء 6 — الـ Dedup والـ traps

English

URL dedup. Normalize first, or the same page counts as four. After that, a Bloom filter tests "seen before" with a fixed memory budget, and the mechanics are in 01 · Data structures for system design (part 2). The important part for a crawler is which way it fails. A false positive says "already seen" about a new URL, so that page is never crawled and nothing reports it. At 10 bits per URL, 813 of 100,000 new pages were lost (0.81%). At 4 bits, 14,602 were (14.6%). Those lost pages have no error, no log and no retry, so size the filter for the loss you can accept and keep the real URL state in durable storage for pages that matter.

Content dedup. Different URLs can serve the same bytes: mirrors, print views, tracking variants. A SHA-256 of the body catches exact copies, 2 of 5 here. Near-duplicates need a similarity hash like SimHash, which this lesson doesn't build.

DNS caching. Resolution is a blocking step per URL unless you cache it. Counted at a local stand-in DNS server: 500 URLs on 20 hosts made 500 queries without a cache, and 20 with a TTL-respecting cache, then 20 more after the TTL expired. Traps. A calendar with a "next month" link is an infinite URL space. With no limits, the crawl kept going until a safety cap of 300 stopped it. With a depth limit of 8 and a URL length limit of 120, it stopped after 9 fetches. Add a per-host budget as the backstop.

// (1) الـ Bloom filter: كل false positive صفحة هتتعلم "اتزارت" وهي عمرها ما اتزارت
class Bloom {
  bits: Uint8Array;
  m: number;
  k: number;
  constructor(m: number, k: number) { this.m = m; this.k = k; this.bits = new Uint8Array(Math.ceil(m / 8)); }
  private indexes(s: string) {
    const d = createHash("sha256").update(s).digest();
    const h1 = d.readUInt32LE(0), h2 = d.readUInt32LE(4);
    return Array.from({ length: this.k }, (_, i) => (h1 + i * h2) % this.m);
  }
  add(s: string) { for (const i of this.indexes(s)) this.bits[i >> 3]! |= 1 << (i & 7); }
  has(s: string) { return this.indexes(s).every((i) => (this.bits[i >> 3]! & (1 << (i & 7))) !== 0); }
}

الـ URL dedup. اعمل normalize الأول، وإلا نفس الصفحة هتتحسب 4. بعدها Bloom filter بيختبر "اتشاف قبل كده" بميزانية memory ثابتة، والتفاصيل في 01 · Data structures for system design (الجزء 2). المهم للـ crawler هو بيغلط في أنهي اتجاه. الـ false positive بيقول "اتشاف" عن URL جديد، فالصفحة دي عمرها ما هتتزار ومفيش حاجة هتبلّغ عنها. بـ 10 bits للـ URL ضاع 813 من 100 ألف صفحة جديدة (0.81%)، وبـ 4 bits ضاع 14,602 (14.6%). الصفحات دي ملهاش error ولا log ولا retry، فحدد حجم الـ filter حسب الخسارة اللي تقبلها، وخلي حالة الـ URL الحقيقية في storage دايم للصفحات المهمة.

فين هستخدمه في شغلي؟ الـ Bloom filter ينفع قدّام DB لمنع الاستعلامات عن حاجات مش موجودة، زي "الـ email ده اتسجل قبل كده؟" في signup كبير. بس خد بالك من الاتجاه: لو false positive معناه رفض حقيقي للمستخدم، لازم تأكد من الـ DB. ونفس فكرة الحدود ضرورية في أي pagination خارجي: حط max pages و max depth، عشان API شريك فيه bug ميخليش الـ job يلف للأبد.
Trade-off: Bloom filter vs a real URL table A Bloom filter costs about 1.25 bytes per URL at 10 bits and silently loses about 1% of new URLs. A real table of hashes costs tens of bytes per URL, never loses one, and also stores crawl state. Large crawlers commonly combine them, using the filter to skip most lookups and the table as the truth.

Part 7 — Crawler: trade-offs & review 🟡 Intermediateالجزء 7 — الـ crawler: الـ trade-offs والمراجعة

English

Distribute by host, not by URL. Hash the host to pick a crawler worker and every URL of that site lands on one machine, which enforces the delay with local state. Hashing the URL spreads one host over all 16 workers, and politeness then needs a distributed lock on every fetch. Host hashing isn't perfectly balanced: with Zipf-sized sites the biggest worker got 12.2% against an ideal 6.3%, since one giant host can't be split. Consistent hashing, from 13 · Partitioning, limits the movement when workers come and go.

Recrawl and rendering. A fixed recrawl interval wastes fetches on pages that never change and misses the ones that do. Schedule from an estimate of each page's change rate, capped at some maximum so old pages are still checked. Conditional requests with If-None-Match make an unchanged page nearly free. JavaScript rendering is the expensive option: with assumed costs of 50 ms for a fetch and 2 s for a render, rendering every page needs ≈772 busy cores against ≈19 for none, so render only the pages that need it.

Storage and 10×. Compressed bodies go in object storage, keyed by content hash, with metadata in a database. See 15 · Object storage. At 10× (≈3,900 pages/s), bandwidth and storage cost grow linearly and are mostly a budget problem. What breaks first is the single-machine state: the frontier and the seen-URL set no longer fit on a box, so both must be partitioned by host, which is another reason to choose host hashing early. DNS becomes a bottleneck next, and politeness turns into a real ceiling for large sites, because a big site still takes one page per second no matter how many machines you add.

import assert from "node:assert/strict";

// النسخة دي بتشيل الـ default port و index.html و الـ tracking params
function normalize(raw: string): string {
  const u = new URL(raw);
  u.hash = "";
  u.hostname = u.hostname.toLowerCase();
  for (const key of [...u.searchParams.keys()]) {
    if (key.startsWith("utm_") || key === "sid" || key === "fbclid") u.searchParams.delete(key);
  }
  u.searchParams.sort();
  u.pathname = u.pathname.replace(/\/index\.html?$/i, "/").replace(/(.)\/$/, "$1");
  return u.href;
}

Solution · الحل 
import assert from "node:assert/strict";

type Row = [query: string, score: number];

// الدمج بياخد الـ batch الأسبوعي ومعاه عدّاد الساعة الأخيرة، والـ trending ليه وزن أعلى
export function mergeTop5(weekly: Row[], lastHour: Row[], hourWeight = 168): string[] {
  const scores = new Map<string, number>();
  // القسمة على 168 بتحوّل عدّاد الأسبوع لمتوسط في الساعة
  for (const [q, n] of weekly) scores.set(q, (scores.get(q) ?? 0) + n / 168);
  for (const [q, n] of lastHour) scores.set(q, (scores.get(q) ?? 0) + n * (hourWeight / 168));
  return [...scores].sort((a, b) => b[1] - a[1]).slice(0, 5).map(([q]) => q);
}

const lastHour: Row[] = [["iphone 18 launch", 500]];
const merged = mergeTop5(weekly, lastHour);
console.log(merged);

Cheat sheet · الخلاصة

  • Autocomplete numbers: 10M × 10 × 20 = 2B/day ≈ 23k QPS, ≈46k peak; debounce at 150 ms ≈ 17k. Always state the assumption.
  • Two paths: an offline pipeline that builds, and a read-only query path that serves. They meet at one versioned artifact.
  • Precompute the top 5 at every prefix: insert queries sorted by count and the first 5 to reach a node are its answer.
  • Short prefixes are the most expensive to compute and the most requested, so they gain the most from precomputing and caching.
  • Pipeline: aggregate, filter before top-k, build a full new version, swap one pointer. Rollback is one write.
  • Shard by measured traffic with a routing table, not by even alphabet ranges.
  • Crawler numbers: 1B/month ≈ 386 pages/s, 500 TB/month raw at 500 KB, 30 PB in 5 years.
  • Frontier = priority queues in front, one queue per host behind, one in-flight request per host, delay after each response. Audit it from server logs.
  • robots.txt per RFC 9309: 4xx may proceed, 5xx must disallow, cache at most 24 h. Crawl-delay isn't in the RFC.
  • Bloom false positives silently lose pages (0.81% at 10 bits per URL, 14.6% at 4). Normalize URLs first. Hash content for mirrors.
  • Cache DNS with the TTL. Stop traps with depth, URL length and per-host budget limits.
  • Distribute by host hash so politeness stays local. At 10×, partition the frontier and URL set by host; a large site stays capped by politeness regardless.
