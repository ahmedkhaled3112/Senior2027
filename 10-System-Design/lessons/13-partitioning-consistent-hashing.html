Why this matters · ليه ده مهم

English

Sharding is the step you can't quietly undo. Pick the wrong key and every query fans out, one shard melts while the others idle, and moving data later means a live migration under traffic. In interviews, "how would you shard this?" is rarely about the word hash: it's about which queries stay cheap, what happens to the biggest tenant, and how you add a node without losing writes. This lesson measures each of those on real databases, so you can quote numbers instead of slogans.

بالعامية

الـ sharding هي الخطوة اللي مش بترجع منها بسهولة. لو اخترت key غلط، كل query هتبقى fan-out، وshard واحد هيولّع والباقي قاعد فاضي، ونقل الـ data بعد كده هيبقى live migration تحت الـ traffic. وفي الـ interviews، سؤال "هتعمل sharding إزاي؟" نادرًا ما بيبقى عن كلمة hash: بيبقى عن أنهي queries هتفضل رخيصة، والـ tenant الكبير هيحصل له إيه، وإزاي تضيف node من غير ما تضيّع writes. الدرس ده بيقيس كل ده على databases حقيقية، عشان تتكلم بأرقام مش شعارات.

Part 1 — Range vs hash, on real databases 🟡 Intermediateالجزء 1 — الـ range مقابل الـ hash على databases حقيقية

English

A shard key decides two things at once: where writes land and which queries can be answered by one shard. Range sharding keeps neighbouring keys together, so range scans are cheap, but any key that grows with time sends every new write to the last shard. Hash sharding scatters keys evenly, but a range over the original key now touches every shard.

The experiment routes 300,000 orders across three real Postgres databases, twice: by created_at range (30 days each) and by a hash of user_id. These are three databases inside one local cluster, so they share CPU and disk: the row counts and shards touched are the result, not the milliseconds. Orders arrive in time order over 90 days, as they do in production.

Watch the totals. Under range sharding each shard ends with exactly 100,000 rows, so a dashboard of row counts looks perfectly balanced, while in every 30-day window one shard took 100% of the writes. Balance of stored data and balance of write load are different questions. Query cost flips with the key: one day of orders is 1 shard under range and 3 under hash; one user's orders is 3 shards under range and 1 under hash.

Before you shard at all, read when sharding is worth it and how to choose the shard key, and partitioning inside one Postgres, which solves many of these problems without a second server.

// الـ PRNG ده seeded عشان الـ output يتكرر بالظبط ونقدر نقتبسه في الدرس
export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

    const b = buckets[i]!;
    if (!b.length) return;
    await pools[i]!.query(
      `INSERT INTO orders SELECT * FROM unnest($1::bigint[], $2::int[], $3::timestamptz[], $4::int[])`,
      [b.map((o) => o.id), b.map((o) => o.userId), b.map((o) => new Date(o.createdAt).toISOString()), b.map((o) => o.totalCents)],
    );
    buckets[i] = [];

  for (const o of orders) {
    const i = route(o);
    buckets[i]!.push(o);
    if (buckets[i]!.length === 5000) await flush(i);
  }
  await Promise.all(SHARDS.map((_, i) => flush(i)));

Part 2 — Consistent hashing, measured 🟡 Intermediateالجزء 2 — الـ consistent hashing بالقياس

English

The ring itself is built step by step in the data structures lesson, parts 3 and 4: don't rebuild it from zero. What's new here are the measurements, on 200,000 keys.

Adding a fifth node to hash % N moves 80.2% of keys, and that's arithmetic: a key stays only if its remainder happens to match in both, so N/(N+1) move. A ring moves only what the new node takes over. With 100 virtual nodes that was 16.2%, not the textbook 20%, because the moved fraction is the new node's real share and its 100 points landed unevenly. At 1,000 virtual nodes it's 19.9%. So "consistent hashing moves 1/(N+1) of keys" is true on average, and the number of vnodes decides how close you get.

Virtual nodes buy balance with memory and rebalancing work. Standard deviation of load falls from 48% with one point per node to 2.25% with 1,000, while the ring grows from 24 bytes to 24 KB. Lookup time barely changes (≈1.3 µs, mostly the MD5 of the key; binary search over 4,000 entries is cheap). Each tenfold increase cut the deviation by about 2.5 to 3.1 times, close to the ideal √10 ≈ 3.2. In exchange, more vnodes means more distinct ranges to stream when a node joins, and Cassandra's docs add another cost: "the more tokens you have", the higher the probability of an outage.

Rendezvous hashing (highest random weight) drops the ring entirely: for each key, score every node with hash(node, key) and take the winner. On the same keys it moved exactly 20.0%, balanced to 0.54% deviation, and used no memory. The price is a lookup that hashes once per node: ≈6.3 µs here for 4 nodes, and it grows linearly with the node count, which is fine for tens of nodes and poor for thousands.

const KEYS = Array.from({ length: 200_000 }, (_, i) => `order:${i}`);

// الـ ring في typed arrays: الـ memory هنا رقم مظبوط مش تقدير
class Ring {
  readonly positions: Uint32Array;
  readonly owners: Uint16Array;
  constructor(nodes: string[], vnodes: number) {
    const points: Array<[number, number]> = [];
    nodes.forEach((node, idx) => {
      for (let v = 0; v < vnodes; v++) points.push([hash32(`${node}#${v}`), idx]);
    });
    points.sort((a, b) => a[0] - b[0]);
    this.positions = Uint32Array.from(points, (p) => p[0]);
    this.owners = Uint16Array.from(points, (p) => p[1]);
  }
  get bytes(): number {
    return this.positions.byteLength + this.owners.byteLength;
  }
  // البحث binary search: أول نقطة بعد الـ hash، ولو عدّينا الآخر نلف لأول الـ ring
  ownerIndex(h: number): number {
    let lo = 0;
    let hi = this.positions.length;
    while (lo < hi) {
      const mid = (lo + hi) >>> 1;
      if (this.positions[mid]! < h) lo = mid + 1;
      else hi = mid;
    }
    return this.owners[lo === this.positions.length ? 0 : lo]!;
  }
}

// الـ rendezvous: كل مفتاح بيحسب score مع كل node، وأعلى score هو المالك
function rendezvousOwner(key: string, nodes: string[]): number {
  let best = -1;
  let winner = 0;
  nodes.forEach((node, idx) => {
    const score = hash32(`${node}|${key}`);
    if (score > best) {
      best = score;
      winner = idx;
    }
  });
  return winner;
}

const assign = (fn: (i: number) => number) => Int32Array.from(KEYS, (_, i) => fn(i));

const stats = (owners: Int32Array, n: number) => {
  const load = new Array<number>(n).fill(0);
  for (const o of owners) load[o]!++;
  const mean = owners.length / n;
  const sd = Math.sqrt(load.reduce((a, x) => a + (x - mean) ** 2, 0) / n);
  return { sdPct: (sd / mean) * 100, maxOverMean: Math.max(...load) / mean };
};

const movedPct = (a: Int32Array, b: Int32Array) => {
  let moved = 0;
  for (let i = 0; i < a.length; i++) if (a[i] !== b[i]) moved++;
  return ((moved / a.length) * 100).toFixed(1) + "%";
};

Interview question (exit test Q2): explain consistent hashing and why virtual nodes. Place nodes and keys on the same hash ring; a key belongs to the next node clockwise. When a node joins, only keys in its new arcs move, about 1/(N+1), versus N/(N+1) with mod N (measured 16-20% vs 80%). One point per node gives very uneven arcs (48% load deviation here), so each physical node gets many virtual points; more points improve balance (2.25% at 1,000) at the cost of ring memory and more ranges to move on membership changes.

Part 3 — Hot spots and salting 🟡 Intermediateالجزء 3 — الـ hot spots والـ salting

English

A perfect hash still can't split one key: if one tenant is 16% of your traffic, all 16% lands on one shard. Real tenant traffic is close to Zipf. In this simulation of 1,000,000 orders over 5,000 tenants (labelled in the output, seeded so it repeats), the biggest tenant, id 7, is 15.8% of all orders, and the table of shard load tells a less obvious story: the hottest shard isn't the whale's own shard, because the second and third tenants landed somewhere too.

Key salting splits one logical key into several physical ones, tenant:7#0 to tenant:7#9, so its writes spread. The measured result is surprising: salting only the whale made the hottest shard worse, 1.47× the mean against 1.28× with no salting. Ten buckets hashed onto four shards landed 3, 4, 0 and 3, and shard 3, already the hottest, took another 30% of the whale. Salting works when applied to the top tenants together: salting the top 20 reached 1.10×. Check the load table after salting, because the assumption that "it spreads" isn't a measurement.

The cost is on the read side, measured on real Postgres. One shard answers "latest 50 orders of the whale" with one query and 50 rows (p50 ≈0.38 ms). Salted and gathered naively, it's 10 queries and 500 rows (≈1.26 ms). Grouping buckets by shard brings it to 3 queries and 150 rows (≈0.50 ms). This depends on the right index: earlier runs with an index that didn't match the query took ≈10 ms for the single-shard read, and the grouped query took ≈5.3 ms until ANALYZE ran after the bulk load. Choose the salt from the order id, not at random, or finding one order by id becomes a fan-out over all buckets.

The operational alternative is a dedicated shard for the whale, kept in a small override table the router checks first. It doesn't improve balance by itself (1.60× here, because the other shards keep their old load and the average now includes a shard holding only the whale), and it does give isolation: a separate blast radius, its own capacity plan and maintenance window, and reads that stay single-shard. For a paying enterprise tenant, that's often the better trade.

// توزيع Zipf: أول tenant في الترتيب بياخد أكبر نصيب والباقي بيقل بسرعة
function zipfSampler(n: number, s: number, rand: () => number) {
  const cdf = new Float64Array(n);
  let sum = 0;
  for (let k = 1; k <= n; k++) {
    sum += 1 / k ** s;
    cdf[k - 1] = sum;
  }
  return () => {
    const u = rand() * sum;
    let lo = 0;
    let hi = n - 1;
    while (lo < hi) {
      const m = (lo + hi) >>> 1;
      if (cdf[m]! < u) lo = m + 1;
      else hi = m;
    }
    return lo + 1;
  };
}

Part 4 — Rebalancing and a live move 🟡 Intermediateالجزء 4 — الـ rebalancing والنقل وهو شغال

English

Three families of strategy, with real numbers for adding a fifth node to 400 GB over 4 nodes:

  • Fixed slots. Many more slots than nodes, decided up front: Redis Cluster uses 16,384 and moves whole slots between nodes. Adding a node moves 3,276 slots, 80 GB. Keys with the same {hashtag} share a slot, as {tenant:7}:orders and {tenant:7}:users do below (both slot 2624, from cluster-key-slot, which uses Redis's CRC16). The output shows real slot numbers only: this is client-side routing standing in for a cluster. Real Redis Cluster commands are not run here, because the private Redis in this lab runs without cluster mode.
  • Dynamic splitting. A partition splits at a size limit, as in HBase regions or MongoDB chunks. Here 63 splits produce 64 partitions of 6.25 GB; a fifth node takes about 13, 81 GB. It adapts to data size, but a brand-new table starts with one partition, so all early writes hit one node unless you pre-split.
  • Per-node proportional. Each node holds a fixed number of partitions, as with Cassandra's tokens. 16 per node gives 64 partitions; a new node splits 16 and takes half of each, about 50 GB at the average partition size. Random picks are uneven, which is why Cassandra 3.x and later added a token allocator.

Moving data is the dangerous part. The experiment moves one slot between two real databases while 4 workers write and read. The bad version copies a snapshot, flips the routing table, and deletes the source: 4,464 of 10,016 acknowledged writes were lost and 1,275 reads missed rows, with zero errors raised. Nothing in the logs says anything went wrong. The versioned version adds an epoch on every shard and a double-write window: it copied, fenced the source, then flipped. Result: 0 lost, 0 misrouted, 8 stale-route retries, a worst write pause of ≈37 ms, at the cost of a move that took ≈951 ms instead of ≈353 ms.

The fence is the part to copy. A write carries the epoch it read from the routing table, and the shard checks it with SELECT … FOR SHARE on the slot_state row inside the write's own statement. The flip's UPDATE slot_state waits for in-flight writers holding that row lock, so after it commits, no write with the old epoch can succeed. Stale clients get a rejected write, refresh, and retry instead of silently writing to a shard that's about to be emptied. Production systems usually replace double-write with CDC or logical replication for catch-up, because a double-write can land on one side and fail on the other: that code lives with logical replication in section 07.

async function loadRoute(meta: pg.Pool): Promise<Route> {
  const { rows } = await meta.query(`SELECT shard, epoch, dual FROM slot_map WHERE slot = $1`, [SLOT]);

// الكتابة المحمية: الـ FOR SHARE بيقفل صف الـ epoch، فالـ flip لازم يستنى الكتابات اللي شغالة
const FENCED_UPSERT = `
  WITH fence AS (SELECT 1 FROM slot_state WHERE slot = $2 AND epoch = $4 AND accepting FOR SHARE)
  INSERT INTO orders (id, slot, total_cents) SELECT $1, $2, $3 FROM fence
  ON CONFLICT (id) DO UPDATE SET total_cents = EXCLUDED.total_cents`;
const FENCED_READ = `
  SELECT o.id FROM slot_state s LEFT JOIN orders o ON o.id = $1
  WHERE s.slot = $2 AND s.epoch = $3 AND s.accepting`;

class StaleRoute extends Error {}

function client(pools: Record<ShardName, pg.Pool>, meta: pg.Pool, c: Counters, fenced: boolean) {
  let cached: Route | null = null;
  let fetchedAt = 0;
  const route = async (force = false) => {
    if (force || !cached || performance.now() - fetchedAt > CACHE_TTL_MS) {
      cached = await loadRoute(meta);
      fetchedAt = performance.now();
    }
    return cached;
  };

  async function withRetry<T>(fn: (r: Route) => Promise<T>): Promise<T> {
    const t0 = performance.now();
    for (let attempt = 0; attempt < 40; attempt++) {
      try {
        const out = await fn(await route(attempt > 0));
        if (attempt > 0) c.maxPauseMs = Math.max(c.maxPauseMs, performance.now() - t0);
        return out;
      } catch (e) {
        if (!(e instanceof StaleRoute)) throw e;
        c.staleRetries++;
        await sleep(2);
      }
    }
    throw new Error("route never settled");
  }

  return {
    write: (id: number) =>
      withRetry(async (r) => {
        if (!fenced) {
          await pools[r.shard].query(`INSERT INTO orders VALUES ($1, $2, 2000) ON CONFLICT (id) DO UPDATE SET total_cents = 2000`, [id, SLOT]);
          return;
        }
        // الترتيب: المصدر الأول وبعدين الوجهة، والـ ack بس لو الاتنين نجحوا
        for (const shard of r.dual ? [r.shard, r.dual] : [r.shard]) {
          const res = await pools[shard].query(FENCED_UPSERT, [id, SLOT, 2000, r.epoch]);
          if (res.rowCount === 0) throw new StaleRoute();
        }
      }),
    read: (id: number) =>
      withRetry(async (r) => {
        if (!fenced) return (await pools[r.shard].query(`SELECT id FROM orders WHERE id = $1`, [id])).rowCount! > 0;
        const res = await pools[r.shard].query(FENCED_READ, [id, SLOT, r.epoch]);
        if (res.rowCount === 0) throw new StaleRoute();
        return res.rows[0].id !== null;
      }),
  };
}

async function badMove(pools: Record<ShardName, pg.Pool>, meta: pg.Pool) {

// ✅ النقل بالـ version: double-write، نسخ، تأكيد، flip محمي بالـ epoch
async function versionedMove(pools: Record<ShardName, pg.Pool>, meta: pg.Pool) {
  // (1) فتح الـ double-write: الـ epoch بيزيد فكل client قديم بيترفض ويعرف الـ route الجديد
  await pools.b.query(`UPDATE slot_state SET epoch = 2, accepting = true WHERE slot = $1`, [SLOT]);
  await pools.a.query(`UPDATE slot_state SET epoch = 2 WHERE slot = $1`, [SLOT]);
  await meta.query(`UPDATE slot_map SET epoch = 2, dual = 'b' WHERE slot = $1`, [SLOT]);

  // (2) النسخ بـ batches بالـ id: الـ DO NOTHING بيسيب الصف الأحدث اللي الـ double-write كتبه
  let lastId = 0;
  for (;;) {
    const { rows } = await pools.a.query(`SELECT id, slot, total_cents FROM orders WHERE slot = $1 AND id > $2 ORDER BY id LIMIT 500`, [SLOT, lastId]);
    if (!rows.length) break;
    await pools.b.query(`INSERT INTO orders SELECT * FROM unnest($1::bigint[], $2::int[], $3::int[]) ON CONFLICT DO NOTHING`,
      [rows.map((r) => r.id), rows.map((r) => r.slot), rows.map((r) => r.total_cents)]);
    lastId = Number(rows.at(-1).id);
    await sleep(5);
  }

  // (3) الـ flip: نقفل المصدر الأول (بيستنى الكتابات الشغالة)، وبعدها الوجهة، وبعدها الـ routing table
  await pools.a.query(`UPDATE slot_state SET epoch = 3, accepting = false WHERE slot = $1`, [SLOT]);
  await pools.b.query(`UPDATE slot_state SET epoch = 3 WHERE slot = $1`, [SLOT]);
  await meta.query(`UPDATE slot_map SET shard = 'b', epoch = 3, dual = NULL WHERE slot = $1`, [SLOT]);

  // (4) المسح بييجي بعد الـ flip، ولو اتأخر مفيش مشكلة لأن المصدر بيرفض
  await pools.a.query(`DELETE FROM orders WHERE slot = $1`, [SLOT]);
}

  • Per-node proportional: كل node شايل عدد ثابت من الـ partitions، زي الـ tokens في Cassandra. 16 لكل node يعني 64 partition، والـ node الجديد بيقسم 16 ويأخد نص كل واحدة، حوالي 50 GB بحساب متوسط الحجم. الاختيار العشوائي بيطلع مش متساوي، وعشان كده Cassandra 3.x وبعدها ضافت token allocator.

نقل الـ data هو الجزء الخطر. التجربة بتنقل slot واحد بين 2 databases حقيقيين و4 workers بيكتبوا ويقروا. النسخة السيئة بتاخد snapshot، وتقلب الـ routing table، وتمسح المصدر: 4,464 من 10,016 كتابة اتأكدت ضاعوا، و1,275 قراية ملقتش صفوف، ومن غير ولا error. مفيش حاجة في الـ logs بتقول إن فيه مشكلة. النسخة بالـ version بتزود epoch على كل shard وفترة double-write: نسخت، وقفلت المصدر، وبعدين قلبت. النتيجة: 0 ضياع، 0 misrouted، و8 retries بسبب route قديم، وأسوأ توقف كتابة ≈37 ms، والتمن إن النقل خد ≈951 ms بدل ≈353 ms.

الـ fence هو الجزء اللي لازم تنقله. كل كتابة معاها الـ epoch اللي قرتها من الـ routing table، والـ shard بيتأكد منه بـ SELECT … FOR SHARE على صف slot_state جوه نفس الـ statement. والـ UPDATE slot_state بتاع الـ flip بيستنى الكتابات اللي ماسكة الـ row lock ده، فبعد ما يعمل commit مفيش كتابة بالـ epoch القديم تعدي. الـ client القديم بيترفض ويحدّث ويعيد المحاولة، بدل ما يكتب في صمت على shard هيتفضّى. في الـ production غالبًا الـ CDC أو الـ logical replication بيحلوا محل الـ double-write في الـ catch-up، لأن الكتابة الدبل ممكن تنجح على ناحية وتفشل على التانية: الكود ده مع الـ logical replication في قسم 07.

فين هستخدمه في شغلي؟ بتعمل migration لجدول invoices لـ shards جديدة. الـ plan الـ junior: "نعمل dump، ننقل، نقلب الـ config، نمسح القديم في الليل". في الـ design review اسأل: الكتابات اللي بتحصل بعد الـ dump هتروح فين؟ الـ clients اللي معاهم config قديم بيعملوا إيه؟ الجواب الناضج: double-write أو CDC للـ catch-up، epoch على كل كتابة، verification بالـ count/checksum قبل الـ flip، والمسح آخر خطوة وبعد فترة مراقبة.
What breaks at scale Double-write has no atomic commit: if the write to the source succeeds and the destination fails, they diverge, and neither side knows. Treat any failure on the second write as a failed request and retry idempotently, verify with count and checksum before the flip, and prefer CDC for tables with heavy traffic.
الـ double-write مفيهوش atomic commit: لو الكتابة على المصدر نجحت وعلى الوجهة فشلت، هيبقوا مختلفين ومحدش عارف. اعتبر أي فشل في الكتابة التانية request فشل وأعد المحاولة بشكل idempotent، واتأكد بـ count وchecksum قبل الـ flip، وفضّل CDC للجداول اللي عليها traffic تقيل.

Part 5 — Cross-shard queries 🟡 Intermediateالجزء 5 — الـ queries اللي بتلف على كذا shard

English

A query with no shard key has to ask everyone: scatter-gather. For "latest 20 orders", each shard returns its own sorted top 20, and merging them gives the true global top 20, because the global top 20 can't contain a row outside some shard's top 20. In the run that's 60 rows fetched to answer from 50,000. The merging itself is the k-way merge from the heaps lesson; with 3 lists a sort is fine, and with hundreds of shards use the heap.

Latency is where it hurts. Promise.all waits for the slowest shard, so the p99 of the fan-out tracks the p99 of the worst shard. Here shard 2 sleeps 80 ms on 5% of its queries (a stand-in for a checkpoint or a noisy neighbour): the healthy shard's p99 stays ≈0.8 ms, the sick shard's p99 is ≈93 ms, and the fan-out p99 is also ≈93 ms. The chance a fan-out hits at least one slow shard is 1 - (1 - p)^n. At p = 1% and 100 shards that's 63.4%, so a problem affecting 1% of requests on one shard becomes the common case for fan-out queries. Hedged requests, per-shard timeouts with partial results, and avoiding fan-out on hot paths are the real responses.

Offset pagination is wrong across shards. Each shard's OFFSET 20 skips that shard's first 20 rows, but the global page 2 may need rows from inside those first 20 on an emptier shard. With orders uneven across shards, 20 out of 20 rows were wrong on every page from 2 onward. The correct offset version asks every shard for offset + limit rows and merges them in the app, so its cost grows with depth: 40,020 rows fetched to return page 1,001. A cursor (keyset) stays at 60 rows per page and was correct on all 5 pages, because each shard resumes strictly after the last row the client saw. Transactions that span shards are a different problem: see distributed transactions.

Part 6 — Secondary indexes 🟡 Intermediateالجزء 6 — الـ secondary indexes

English

You sharded by user_id, and now support asks for "all orders containing SKU-123". The shard key can't help. There are two designs.

A local index lives on each shard and indexes that shard's rows. Writes stay in one place and one transaction, so the index is always consistent with its rows: 150 out of 150 new orders were visible at once. Reads must scatter across every shard, 3 queries here, 64 on a 64-shard system.

A global index is a separate table partitioned by the indexed value (orders_by_sku, shard chosen by hash(sku)). A read goes to one index shard. Writes now touch two shards, so the index is updated asynchronously; here that's an outbox row in the same transaction as the order and a poller that writes it across. That gap is real: only 2 of 150 new orders were visible at once, with lag p50 ≈46 ms and p99 ≈62 ms at a 40 ms poll, and with the updater down for 800 ms the lag reached ≈839 ms while the writes kept succeeding. The system looks healthy while the index quietly freezes, so monitor the outbox depth and the lag.

One thing the numbers correct: a global index isn't automatically fewer queries. Fetching the full orders back took 1 index query plus 3 shard fetches, 4 queries against the local index's 3, because this SKU's orders are spread across all shards. The win appears when the index covers the read (the fields you need are stored in the index, 1 query), or when the shard count is much larger than the number of shards a value's rows live on. Cloud databases expose this exact choice as attribute projection.

From the docs: DynamoDB global secondary indexes are global and eventually consistent, and strongly consistent reads are "only supported on tables and local secondary indexes". Cassandra's Storage-Attached Indexes are written per SSTable on each node, so they're local, and a read that spans the cluster goes through token ranges across many nodes.

الـ global index جدول منفصل متقسم بالقيمة المتعمل لها index (orders_by_sku، والـ shard بيتحدد بـ hash(sku)). القراية بتروح لـ index shard واحد. الكتابات بقت بتلمس 2 shards، فالـ index بيتحدث async؛ هنا عن طريق صف outbox في نفس transaction الـ order، وpoller بينقله. الفجوة دي حقيقية: 2 بس من 150 order بانوا فورًا، واللاج p50 ≈46 ms وp99 ≈62 ms مع poll كل 40 ms، ولما الـ updater وقف 800 ms اللاج وصل ≈839 ms والكتابات شغالة عادي. النظام شكله سليم والـ index متجمّد في صمت، فلازم تراقب حجم الـ outbox والـ lag.

حاجة الأرقام صلّحتها: الـ global index مش أوتوماتيك معناه queries أقل. لما رجعنا نجيب الـ orders كاملة، احتجنا index query واحدة + 3 shard fetches، يعني 4 مقابل 3 بتاعة الـ local، لأن orders الـ SKU ده متفرقة على كل الـ shards. المكسب بيظهر لما الـ index يغطي القراية (الحقول اللي محتاجها متخزنة في الـ index، query واحدة)، أو لما عدد الـ shards يبقى أكبر بكتير من عدد الـ shards اللي صفوف القيمة دي موجودة عليها. والـ cloud databases بتعرض الاختيار ده بالظبط تحت اسم attribute projection.

من الـ docs: الـ global secondary indexes في DynamoDB هي global وeventually consistent، والـ strongly consistent reads مدعومة بس على الـ tables والـ local secondary indexes. والـ Storage-Attached Indexes في Cassandra بتتكتب لكل SSTable على كل node فهي local، والقراية اللي بتعدي على الـ cluster كله بتلف على token ranges في nodes كتير.

فين هستخدمه في شغلي؟ شاشة support بتدور بـ email، والـ users متقسمين بـ hash على الـ id. لو الـ endpoint بيتطلب 1000 مرة في الثانية، الـ local index معناه 16 query لكل طلب على 16 shard: اعمل جدول global صغير users_by_email بيخزن الـ shard والـ id. ولو العميل بيغيّر الإيميل وبيدخل فورًا، اختبر الـ stale window: بعد الـ update الـ login الجديد ممكن يفشل لثواني، فاقرا من مصدر الحقيقة في الـ flow ده أو اعمل الكتابة sync في الحالة دي بالذات.

Common mistakes · غلطات شائعة

❌ Shard key that grows with time 
// كل order جديد بيروح لآخر shard
const shard = monthIndex(order.createdAt);
✅ Hash the entity that owns the row 
// الكتابات بتتوزع، وأوامر كل مستخدم في shard واحد
const shard = hash32(`user:${order.userId}`) % shardCount;
بالعامية

❌ لو الـ shard key بيزيد مع الوقت (created_at، id متسلسل)، كل الكتابات الجديدة بتنزل على آخر shard، وعدد الصفوف النهائي بيفضل شكله متوازن فبيخدعك. ✅ اعمل hash للكيان اللي بيملك الصف، زي الـ user أو الـ tenant، عشان الكتابات تتوزع وقراية بيانات الكيان ده تفضل على shard واحد.

❌ Trusting the modulus in code 
// لو عدد الـ shards اتغير، 80% من المفاتيح مكانها بيتغير
const shard = hash32(key) % shards.length;
✅ Slots + a routing table 
// مفيش حساب بيتغير: الـ slot ثابت، والجدول اللي بيتغير
const slot = hash32(key) % 16384;
const shard = routing.lookup(slot);
بالعامية

❌ الـ hash % length بينقل 80% من المفاتيح لو N زاد واحد. ✅ عدد slots ثابت وكبير، والـ routing table بيقول كل slot فين، فإضافة node معناها نقل slots بس وتعديل الجدول، والمعادلة نفسها ماتتغيرش.

❌ OFFSET pushed to each shard 
// كل shard بيتخطى أول صفوفه هو، فالصفحة بتطلع غلط
await Promise.all(shards.map(s => s.query(
  `... ORDER BY created_at DESC LIMIT 20 OFFSET 20`)));
✅ Cursor on (created_at, id) 
// كل shard بيكمّل بالظبط بعد آخر صف العميل شافه
await Promise.all(shards.map(s => s.query(
  `... WHERE (created_at, id) < ($1, $2)
   ORDER BY created_at DESC, id DESC LIMIT 20`, cursor)));
بالعامية

❌ الـ OFFSET لوحده على كل shard طلّع 20 من 20 صف غلط في التجربة، لأنه بيتخطى صفوف الـ shard ده بس. ✅ الـ cursor على (created_at, id) بياخد الصفحة صح وبتكلفة ثابتة؛ والـ id لازم يكون موجود عشان الـ ties (في التمرين 3 هتشوف الـ cursor بالوقت لوحده بيضيّع صفوف).

❌ Random salt per write 
// مفيش طريقة تعرف الـ order ده في أنهي bucket
const bucket = Math.floor(Math.random() * 10);
const key = `tenant:7#${bucket}`;
✅ Salt derived from the row 
// الـ bucket معروف من الـ id، والقراية بالـ id بتروح لمكان واحد
const bucket = hash32(orderId) % 10;
const key = `tenant:7#${bucket}`;
بالعامية

❌ الـ salt العشوائي بيخلي قراية order واحد بالـ id تبقى fan-out على كل الـ buckets. ✅ لو الـ bucket طالع من الـ order id نفسه، تقدر تحسبه وقت القراية وتروح لـ bucket واحد؛ والتوزيع برضه متساوي طالما الـ hash كويس.

❌ Flip the routing table and hope 
// الـ snapshot قبل الـ flip، وأي كتابة بعدها بتضيع
await copyRows(a, b, slot);
await updateRouting(slot, "b");
await deleteRows(a, slot);
✅ Epoch fence + double write 
// كل كتابة بتتأكد من الـ epoch جوه نفس الـ statement
await openDoubleWrite(slot);
await backfill(a, b, slot);
await fenceAndFlip(slot);
بالعامية

❌ الـ flip من غير حماية ضيّع 4,464 كتابة متأكدة ومن غير ولا error. ✅ كل كتابة معاها epoch بيتراجع على الـ shard نفسه، والـ double-write بيغطي الوقت اللي النسخ شغال فيه، فالـ client القديم بيترفض ويحدّث بدل ما يضيّع كتابته في صمت.

Solution · الحل 
import { createHash } from "node:crypto";

const hash32 = (key: string) => createHash("md5").update(key).digest().readUInt32BE(0);

// كل bucket بيروح لـ shard واحد، فبنجمّعهم عشان query واحدة لكل shard
export function bucketsByShard(tenant: number, buckets: number, shards: number): Map<number, number[]> {
  const out = new Map<number, number[]>();
  for (let b = 0; b < buckets; b++) {
    const s = hash32(`tenant:${tenant}#${b}`) % shards;
    out.set(s, [...(out.get(s) ?? []), b]);
  }
  return out;
}

type Order = { id: number; createdAt: number };

// كل الـ orders ليها نفس الوقت أحيانًا: الـ tie-break على الـ id هو اللي بيفرق
const shards: Order[][] = [
  [{ id: 9, createdAt: 100 }, { id: 8, createdAt: 100 }, { id: 3, createdAt: 90 }],
  [{ id: 7, createdAt: 100 }, { id: 5, createdAt: 95 }, { id: 2, createdAt: 90 }],
  [{ id: 6, createdAt: 100 }, { id: 4, createdAt: 95 }, { id: 1, createdAt: 90 }],
];
const newestFirst = (a: Order, b: Order) => b.createdAt - a.createdAt || b.id - a.id;
const truth = shards.flat().sort(newestFirst);

function page(cursor: Order | null, size: number, withTieBreak: boolean): Order[] {
  const after = (o: Order) =>
    cursor === null ||
    (withTieBreak
      ? o.createdAt < cursor.createdAt || (o.createdAt === cursor.createdAt && o.id < cursor.id)
      : o.createdAt < cursor.createdAt);
  return shards.flatMap((s) => s.filter(after).sort(newestFirst).slice(0, size)).sort(newestFirst).slice(0, size);
}

function walk(withTieBreak: boolean): number[] {
  const seen: number[] = [];
  let cursor: Order | null = null;
  for (;;) {
    const rows = page(cursor, 2, withTieBreak);
    if (!rows.length) return seen;
    seen.push(...rows.map((r) => r.id));
    cursor = rows.at(-1)!;
  }
}
const missing = (ids: number[]) => truth.filter((o) => !ids.includes(o.id)).map((o) => o.id);

Cheat sheet · الخلاصة

  • Range: cheap scans, sequential keys send 100% of writes to the last shard. Hash: even writes, range queries hit every shard.
  • Row-count balance isn't write balance: all three shards ended at 100,000 rows while each took 100% of one window.
  • Adding a node: % N moves N/(N+1) (80.2%); a ring moves the new node's real share (16.2% at 100 vnodes, 19.9% at 1,000).
  • Vnodes trade memory and rebalancing work for balance: deviation 48% → 2.25%. Rendezvous: no ring, 0.54%, lookup O(N).
  • Salting spreads writes and multiplies reads. Hash placement on few shards can make the hottest shard worse (1.28× → 1.47×); salt the top tenants together and re-measure.
  • Group salted buckets by shard (3 queries, not 10) and pick the salt from the row id, not at random.
  • Rebalancing: fixed slots, dynamic split, or per-node proportional. A live move needs double-write or CDC, a verified copy, and an epoch fence on each write.
  • A bad flip loses acknowledged writes with zero errors (4,464 of 10,016). A fenced flip: 0 lost, 8 retries, ≈37 ms pause.
  • Scatter-gather latency is the slowest shard; 1-(1-p)^n is your tail exposure. Per-shard OFFSET is wrong: use a cursor on (created_at, id).
  • Local index: consistent, read scatters. Global index: one-place read, async write, stale window. It wins when it covers the read.
بالعامية
  • الـ range: الـ scans رخيصة، والمفاتيح المتسلسلة بتبعت 100% من الكتابات لآخر shard. الـ hash: كتابات متوزعة، والـ range queries بتلمس كل الـ shards.
  • توازن عدد الصفوف مش توازن الكتابة: الـ 3 shards خلصوا 100,000 صف، وكل واحد شال 100% من نافذة كاملة.
  • إضافة node: % N بينقل N/(N+1) (80.2%)، والـ ring بينقل نصيب الـ node الجديد الحقيقي (16.2% عند 100 vnode و19.9% عند 1000).
  • الـ vnodes بتبدّل memory وشغل rebalancing بتوازن: الانحراف من 48% لـ 2.25%. والـ Rendezvous: من غير ring، 0.54%، بس الـ lookup O(N).
  • الـ salting بيوزع الكتابات ويضاعف القرايات. الـ hash على shards قليلة ممكن يخلي أسخن shard أسوأ (من 1.28× لـ 1.47×)؛ طبّقه على أكبر tenants مع بعض وقيس تاني.
  • جمّع الـ salted buckets حسب الـ shard (3 queries مش 10)، واختار الـ salt من الـ row id مش عشوائي.
  • الـ Rebalancing: fixed slots، أو dynamic split، أو per-node proportional. والنقل وهو شغال محتاج double-write أو CDC، ونسخة متأكد منها، وepoch fence على كل كتابة.
  • الـ flip السيء بيضيّع كتابات متأكدة ومن غير errors (4,464 من 10,016). والـ flip بالـ fence: 0 ضياع، 8 retries، وتوقف ≈37 ms.
  • latency الـ scatter-gather هو أبطأ shard، و1-(1-p)^n هو تعرّضك للذيل. الـ OFFSET لكل shard غلط: استخدم cursor على (created_at, id).
  • الـ local index: متسق، والقراية بتنتشر. الـ global index: القراية من مكان واحد، الكتابة async، وفيه stale window. بيكسب لما يغطي القراية.
