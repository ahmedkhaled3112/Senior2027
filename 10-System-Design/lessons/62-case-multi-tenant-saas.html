Why this matters · ليه ده مهم

English

This is the case closest to your own platform. Almost every B2B product is multi-tenant, and the failures are not exotic: one customer's bulk import makes every other customer slow, a migration half-applies across thousands of schemas, a bill is wrong because a retry counted twice, or a deleted customer's data is still in the backups. Interviewers use this question because the answer shows whether you can reason about fairness and blast radius, not just tables.

بالعامية

دي أقرب حالة لمنصتك. تقريبًا كل منتج B2B هو multi-tenant، والفشل مش غريب: import كبير من عميل واحد يبطّأ الكل، migration تتطبق نصها على آلاف الـ schemas، فاتورة غلط عشان retry اتحسب مرتين، أو بيانات عميل اتمسح لسه موجودة في الـ backups. الـ interviewers بيسألوا السؤال ده لأن الإجابة بتبين إذا كنت بتفكر في الـ fairness والـ blast radius، مش بس في الجداول.

Part 2 — Isolation models, measured 🔴 Advancedالجزء 2 — نماذج الـ isolation بالقياس

English

Three models: shared (one table, a tenant_id column), schema per tenant (same tables repeated in every schema), database per tenant. The trade-off is isolation against operating cost, and the cost is concrete. On a real Postgres 18 with 1,000 tenants (helper pg-cluster.mjs starts a throwaway instance on a random port, never the default one):

The migration took about 13 ms on the shared table and 3,650 ms across 1,000 schemas, and it partially failed: one schema already had the column, so 999 migrated and one did not. Schema-per-tenant is a fleet of migrations, so you need per-schema migration state, retry, and a way to tell which tenants are on which version. The catalog grew from 8 MB and 281 relations to 38 MB and 11,269 relations. Every backend that touches all tenants caches metadata for each table it opens: 23.1 MB per backend, against 0.1 MB for shared. Multiply by 200 connections and the catalog becomes a memory cost, not a disk cost.

Database-per-tenant gives the strongest isolation and is the most expensive: about 8 MB and 223 ms per empty database, and each database needs its own connections, so the pool cannot be shared. Here 60 max_connections was exhausted with 57 connections across only 5 databases, and it failed with 53300. And the classic bug of schema-per-tenant: SET search_path on a pooled connection leaks to the next request. Use set_config(..., true), which is scoped to the transaction.

The practical answer is hybrid: shared tables for free and pro, dedicated databases or cells for the enterprise tenants who pay for it. The table below shows the shape.

import { readFileSync } from "node:fs";

// حماية: أي port فاضي أو default معناه إننا هنكلم الـ service الحقيقي، فبنقف فورًا
export function safePort(p: unknown): number {
  const n = Number(p);
  if (!/^\d+$/.test(String(p)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error("refusing port " + String(p));
  }
  return n;
}

async function catalog(db: pg.Client) {
  const { rows } = await db.query(`
    select pg_size_pretty(sum(pg_total_relation_size(c.oid))) as size,
           (select count(*) from pg_class where relkind in ('r','i','t')) as relations
    from pg_class c join pg_namespace n on n.oid = c.relnamespace
    where n.nspname = 'pg_catalog' and c.relkind = 'r'`);
  return rows[0] as { size: string; relations: string };
}

Part 3 — Noisy neighbour 🔴 Advancedالجزء 3 — الـ Noisy neighbour

English

A noisy neighbour is one tenant taking the whole shared resource. On the real stack below (an HTTP server, a Postgres pool of 10, and queries that hold a connection for 10 ms), five normal tenants send requests open-loop while one tenant runs 80 flat-out clients. Without protection the victims' p99 goes from about 51 ms to 157 ms and their p50 is nine times worse, because they queue behind the flood for the pool.

Three fixes, all run. Per-tenant rate limit: a Redis token bucket per tenant (rate limiting teaches the algorithm); the flood gets 429s fast and never reaches the pool, and the victims' p99 is 36 ms. Per-tenant concurrency limit: cap in-flight work per tenant, the fix that matches a resource like a pool, and p99 is 33 ms; a concurrency cap protects even when requests are slow and few, which a rate limit does not. Fair queueing for background jobs: a FIFO queue serves whoever arrived first, so 600 jobs from one tenant make everyone else wait 2.4 seconds; a per-tenant round-robin brings the victims' wait down to about 76 ms, and the noisy tenant finishes at nearly the same time because the total work is unchanged.

Rate limits and concurrency limits at the edge protect the shared resource; fair queueing protects the backlog. Shuffle sharding shrinks the blast radius of whatever gets through: give each tenant a random subset of workers. With plain shards of 10, a noisy tenant takes down its whole group, about 10% of tenants. With 5 random workers out of 100, the chance another tenant shares all five is 1 / C(100,5), about one in 75 million, and 23% share at least one worker. A tenant that shares one worker is degraded, not down, as long as clients retry on the other four.

interface Job { tenant: string; enqueuedAt: number; }

// الـ FIFO العادي: طابور واحد، واللي وصل الأول بياخد العمال كلهم
class Fifo {
  private q: Job[] = [];
  push(j: Job) { this.q.push(j); }
  next() { return this.q.shift(); }
}

// الـ fair queue: طابور لكل tenant، والعامل بياخد من كل واحد بالدور
class FairQueue {
  private queues = new Map<string, Job[]>();
  private order: string[] = [];
  private cursor = 0;
  push(j: Job) {
    let q = this.queues.get(j.tenant);
    if (!q) { q = []; this.queues.set(j.tenant, q); this.order.push(j.tenant); }
    q.push(j);
  }
  next(): Job | undefined {
    for (let i = 0; i < this.order.length; i++) {
      const tenant = this.order[this.cursor % this.order.length]!;
      this.cursor++;
      const q = this.queues.get(tenant)!;
      if (q.length) return q.shift();
    }
    return undefined;
  }
}

const WORKERS = 100, TENANTS = 10_000, RUNS = 200;

function trial(shardSize: number, seed: number, plain: boolean) {
  const rand = mulberry32(seed);
  const pick = () => {
    if (plain) {
      // الـ sharding العادي: كل tenant في مجموعة ثابتة من shardSize عامل
      const g = Math.floor(rand() * Math.floor(WORKERS / shardSize));
      return Array.from({ length: shardSize }, (_, i) => g * shardSize + i);
    }
    const set = new Set<number>();
    while (set.size < shardSize) set.add(Math.floor(rand() * WORKERS));
    return [...set];
  };
  const noisy = pick();
  const bad = new Set(noisy);
  let fullyDown = 0, partial = 0;
  for (let t = 1; t < TENANTS; t++) {
    const shard = pick();
    const hit = shard.filter((w) => bad.has(w)).length;
    if (hit === shard.length) fullyDown++;
    else if (hit > 0) partial++;
  }
  return { fullyDown, partial };
}

Part 4 — Tenant-aware routing 🔴 Advancedالجزء 4 — الـ Routing بالـ tenant

English

A cell is a complete, independent copy of the stack: app servers, database, cache, queue. Tenants are assigned to cells, so a bad deploy or a bad tenant takes down one cell, not the product, which is the blast-radius idea from sharding applied to the whole stack. Routing is a table, tenant → cell, read by every API instance through a cache with a TTL: the subdomain (or API key) resolves to a tenant, and the tenant resolves to a cell. Unlike consistent hashing, this lookup lets you move one tenant on purpose, which you do for capacity and for compliance.

Moving a tenant live is the hard part, and it was run between two real Postgres databases with writers running throughout. The sequence is: freeze writes for that tenant only (clients get 503 with Retry-After), wait out the cache TTL so no API instance still believes the old route, copy, verify row counts and a checksum, flip the route, and delete from the old cell later.

The TTL wait is the step everyone skips. In the buggy run the copy finished while stale routers kept writing to the old cell: 1,165 acknowledged writes ended up stranded on A, and the verify step alone did not save them, because rows also landed after it ran. With the freeze and the wait, zero writes were lost and clients saw only a brief run of 503s. For extra safety, make the old cell refuse writes for a moved tenant, so a stale router fails loudly instead of writing into a hole.

type Route = { cell: string; state: "active" | "frozen"; version: number };

// الـ router: كل app instance عندها cache خاص بيها، وده اللي بيعمل كل المشكلة
class Router {
  private cache = new Map<string, { route: Route; expires: number }>();
  private control: pg.Pool;
  constructor(control: pg.Pool) { this.control = control; }
  async route(tenant: string): Promise<Route> {
    const hit = this.cache.get(tenant);
    if (hit && hit.expires > Date.now()) return hit.route;
    const { rows } = await this.control.query("select cell, state, version from tenant_cell where tenant = $1", [tenant]);
    const route = rows[0] as Route;
    this.cache.set(tenant, { route, expires: Date.now() + TTL_MS });
    return route;
  }
}

فين هستخدمه في شغلي؟ أول مرة عميل enterprise يطلب region تاني أو database لوحده، ده بالظبط الـ runbook: freeze → انتظار الـ TTL → copy → verify → flip. لازم تكون الخطوات دي script متجرب على staging، مش خطوات يدوية يوم الجمعة بالليل. والـ TTL نفسه رقم في الـ runbook.
Trade-off: the router cache TTL A short TTL means more load on the control plane and faster moves; a long TTL protects the control plane and makes every move wait longer. Whatever you choose, the freeze must wait at least one TTL, and the control plane must be highly available and cached, or it becomes the outage that takes down every cell at once.
الـ TTL الصغير معناه حمل أكتر على الـ control plane وحركة أسرع، والكبير بيحمي الـ control plane وبيخلي كل نقلة تستنى أكتر. أيًا كان اختيارك، الـ freeze لازم يستنى TTL واحد على الأقل، والـ control plane لازم يكون highly available ومتكيش، وإلا هو نفسه هيبقى الـ outage اللي يوقع كل الـ cells مع بعض.

English

Usage flows as events with a stable id: API → Redis stream → aggregator → Postgres upsert into usage_monthly. Delivery is at-least-once, so the aggregator must be idempotent: inside one transaction it inserts the event id into usage_seen with ON CONFLICT DO NOTHING, and only if that inserted a row does it add to the monthly total. The commit and the XACK are separate, so a crash between them re-delivers the batch, and the id check makes the re-delivery a no-op. This is the idempotency pattern from idempotency keys, applied to money.

The run below kills the consumer twice with a real SIGKILL immediately after the commit and before the ack, on a stream that also contains 309 producer duplicates. Totals match exactly. A naive counter on the same deliveries over-bills by 1,529 units, and that is a real invoice.

Month-end cut-off: events are billed by when they happened, not when they arrived, and a month stays open for a grace period (here until the 3rd). A late event for a closed month becomes an adjustment on the next invoice, because a sent invoice is never edited. Quota enforcement reads the aggregate, which lags the stream by a batch: that is fine for a soft limit, while a hard limit needs a real-time counter in Redis as well. The invoice uses integer cents and the plan's included units.

Part 6 — Tenant lifecycle 🔴 Advancedالجزء 6 — دورة حياة الـ tenant

English

Per-tenant config and flags: effective config is the plan's defaults overlaid by tenant overrides, resolved in one function so no code path reads a raw flag. Onboarding is a list of idempotent steps recorded in a table. A step that fails throws, the next run skips what is done and continues, and a retry cannot create a second key or send a second welcome email, as the run shows.

Data export must stream. The worker walks the tenant's rows with keyset pagination, writes NDJSON through gzip, and uploads with multipart: memory stayed flat (about 17 MB of growth for 30,000 rows), then the tenant gets a time-limited presigned GET link. S3 is played by s3rver, a labelled stand-in: it accepted a tampered signature in our testing and has no lifecycle rules, so don't treat it as proof of S3's security or expiry behaviour; see object storage. Real S3 also requires a known length for a plain PUT, which is why a stream goes through multipart (@aws-sdk/lib-storage).

Offboarding is a hard delete plus crypto-shredding: each tenant's personal data is encrypted under its own data key, and that key is itself wrapped by a master key. Deleting the wrapped key makes the ciphertext unreadable everywhere, including backups you cannot edit (see secrets and encryption). Crucially, that only works if the key is not in those same backups, so keys live in a KMS or in a table with short-lived backups. Prove deletion with a test that walks every table with a tenant_id column from information_schema, so a table added next year cannot be forgotten: zero rows remain and the other tenant is untouched.

Part 7 — Trade-offs & review 🔴 Advancedالجزء 7 — الـ Trade-offs والمراجعة

English

Compliance tier: region-pinned tenants are the strongest argument for cells, because a cell can live in one region and the router sends only that tenant there (see geo-distribution and residency). Enterprise demands arrive as a list: SSO, audit logs, a dedicated cluster, customer-managed keys, a named support contact. Price them; don't absorb them. Per-tenant cost visibility means you can answer "what does this customer cost us?" from metered usage plus allocated infrastructure, which is what tells you when a tenant deserves its own cell, and when a plan is unprofitable.

Breaks first at 10× (100,000 tenants), from the measured numbers: schema-per-tenant becomes painful: migrations take about six minutes sequentially, each backend holds about 2.3 GB of catalog cache, and you must add cells. Database-per-tenant needs about 200,000 idle connections, so without a pooler it was already over at 10,000. Shared tables reach 60 billion rows and must be partitioned or split across cells. In every case, the control plane becomes the single point of failure unless it is replicated and cached.

The AWS SaaS Lens is the reference to compare against, since Xu has no chapter on this: it uses the silo, bridge and pool vocabulary for the same three models. And compare it with your own platform: what do you actually do today for noisy neighbours and offboarding?

import assert from "node:assert/strict";

// الـ limiter ده بيحط طابور صغير لكل tenant، ولما الطابور يتملى بيرد فورًا
class TenantLimiter {
  private max: number;
  private maxQueued: number;
  private state = new Map<string, { running: number; queue: (() => void)[] }>();
  constructor(max: number, maxQueued: number) { this.max = max; this.maxQueued = maxQueued; }
  async run<T>(tenant: string, fn: () => Promise<T>): Promise<T> {
    let s = this.state.get(tenant);
    if (!s) { s = { running: 0, queue: [] }; this.state.set(tenant, s); }
    if (s.running >= this.max) {
      if (s.queue.length >= this.maxQueued) throw new Error("429");
      await new Promise<void>((resolve) => s!.queue.push(resolve));
    } else {
      s.running++;
    }
    try {
      return await fn();
    } finally {
      const next = s.queue.shift();
      // الدور بيتنقل للي واقف، فالعدّاد ما بيتغيرش لو فيه حد في الطابور
      if (next) next(); else s.running--;
      if (s.running === 0 && s.queue.length === 0) this.state.delete(tenant);
    }
  }
}

3. Late events bucket 🔴 hard Write bucket(eventAt, receivedAt, periods) returning the billing month and whether the event counts as "current" or "adjustment". Cover: an event on the last day received during grace, the same event received after close, and a next-month event received late.
اكتب bucket(eventAt, receivedAt, periods) ترجع شهر الفوترة وإذا كان الـ event "current" ولا "adjustment". غطي: event في آخر يوم وصل في الـ grace، ونفس الـ event وصل بعد القفل، و event لشهر جديد وصل متأخر.
Solution · الحل 
import assert from "node:assert/strict";

interface Period { month: string; closesAt: Date; }

// الحدث بيتحسب على الشهر بتاع وقت حدوثه، ولو الشهر اتقفل بيروح adjustment
function bucket(eventAt: Date, receivedAt: Date, periods: Period[]) {
  const month = eventAt.toISOString().slice(0, 7);
  const p = periods.find((x) => x.month === month);
  if (!p || receivedAt < p.closesAt) return { month, kind: "current" as const };
  return { month, kind: "adjustment" as const };
}

const periods: Period[] = [{ month: "2026-10", closesAt: new Date("2026-11-03T00:00:00Z") }];

assert.deepEqual(bucket(new Date("2026-10-31T23:00:00Z"), new Date("2026-11-04T01:00:00Z"), periods), { month: "2026-10", kind: "adjustment" });
assert.deepEqual(bucket(new Date("2026-11-02T10:00:00Z"), new Date("2026-11-04T01:00:00Z"), periods), { month: "2026-11", kind: "current" });

Cheat sheet · الخلاصة

  • Load is by tier, not average: top 1% holds most of the data; let the numbers pick the model.
  • Shared / schema / database per tenant: isolation against operating cost. Hybrid is the common end state.
  • Schema per tenant means a fleet of migrations with partial failures; track migration state per schema.
  • Catalog cost is memory per backend too (≈23 MB per backend per 1,000 schemas here), not just disk.
  • SET search_path leaks through a pool; use set_config(..., true) inside a transaction.
  • Noisy neighbours: per-tenant rate limit, per-tenant concurrency cap, fair queueing; shuffle sharding for blast radius.
  • Cell = full stack copy; routing is a table with a cached TTL; moving a tenant is freeze, wait TTL, copy, verify, flip.
  • Metering is at-least-once: dedupe by event id in the same transaction as the upsert.
  • Month-end: bill by event time, close after a grace window, late events become adjustments.
  • Offboarding: crypto-shred the key plus hard delete; test by walking information_schema; keys must not live in the same backups.
  • Breaks at 10×: the catalog and migration fleet, connections per database, and an uncached control plane.
بالعامية
  • الحمل بالـ tier مش بالمتوسط: أكبر 1% عندهم معظم الداتا، وخلي الأرقام هي اللي تختار النموذج.
  • shared / schema / database لكل tenant: isolation مقابل تكلفة تشغيل، والـ hybrid هو النهاية الشائعة.
  • الـ schema per tenant يعني fleet من الـ migrations بفشل جزئي، فلازم تتبع حالة كل schema.
  • تكلفة الـ catalog كمان memory لكل backend (≈23 MB لكل backend لكل 1,000 schema هنا)، مش disk بس.
  • SET search_path بيعدي من الـ pool، واستخدم set_config(..., true) جوه transaction.
  • الـ noisy neighbours: rate limit لكل tenant، concurrency cap لكل tenant، و fair queueing، و shuffle sharding للـ blast radius.
  • الـ cell = نسخة stack كاملة؛ الـ routing جدول بـ cache و TTL؛ ونقل tenant = freeze، انتظار TTL، copy، verify، flip.
  • الـ metering at-least-once: dedupe بالـ event id في نفس transaction الـ upsert.
  • آخر الشهر: احسب بوقت الحدوث، اقفل بعد grace، والمتأخر يبقى adjustment.
  • الـ offboarding: crypto-shred للمفتاح + hard delete؛ والـ test بيلف على information_schema؛ والمفاتيح مينفعش تكون في نفس الـ backups.
  • اللي بيقع عند 10×: الـ catalog و fleet الـ migrations، الـ connections لكل database، و control plane من غير cache.
