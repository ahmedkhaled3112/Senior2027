Why this matters · ليه ده مهم

English

Most data breaches are not clever cryptography attacks. A password sits in an old log line, a backup was restored somewhere it shouldn't be, or "encrypted" meant the disk was encrypted while the attacker came in through SQL. This lesson is about matching each protection to the threat it actually stops, and then running the operations people skip: expiring a credential, rotating a key, deleting one user's data from a backup you can't edit. The privacy half is engineering too: a test that fails when someone adds an unclassified column is worth more than a policy document. Nothing here is legal advice; the GDPR parts are engineering practice, so check your actual obligations with someone qualified.

بالعامية

أغلب تسريبات البيانات مش هجمات cryptography ذكية. باسورد قاعد في log line قديمة، أو backup اترجع في مكان مكانش المفروض، أو "متشفر" كان معناها الـ disk متشفر والمهاجم دخل من SQL. الدرس ده عن إنك تربط كل حماية بالتهديد اللي بتمنعه فعلًا، وبعدين تشغّل العمليات اللي الناس بتفوتها: انتهاء credential، تغيير key، ومسح بيانات يوزر واحد من backup مقدرش تعدّله. ونص الـ privacy هندسة برضه: test بيقع لما حد يضيف column من غير تصنيف أحسن من ورقة policy. ومفيش حاجة هنا استشارة قانونية؛ أجزاء الـ GDPR ممارسات هندسية، فراجع التزاماتك الفعلية مع حد متخصص.

Part 1 — Secrets management 🟡 Intermediateالجزء 1 — إدارة الـ secrets

English

The basics are in section 04, secrets rotation and config validation. Start with the two leaks that keep happening: a secret committed to the repo, and a startup log that prints the environment. The first run below shows a single JSON.stringify(process.env) putting a database password and a live payment key into your log pipeline, where it is retained, replicated and readable by far more people than the production database. The fix is an allow-list of what may be logged, plus a scanner in CI (a real one such as gitleaks is not run here).

A secrets manager changes the shape of the problem from "protect a long-lived password" to "issue short-lived ones". The idea of Vault's dynamic secrets, on real Postgres: the app asks for a credential, gets a new role that expires soon, and renews while it's alive. The stand-in below creates a role with VALID UNTIL. It needs password auth, since trust ignores expiry. The result worth remembering: after expiry a new connection fails with password authentication failed, but an existing connection keeps working, because the expiry is checked only at login. So revocation means terminating sessions, not just waiting.

Rotating a credential without a restart means owning the pool: open a new pool with the new role, test it, swap the pointer, drain the old one. Draining matters more than it looks. Calling pool.end() on pg's pool right after the swap left queued queries unresolved forever: all workers were stuck when we measured it. Wait for waitingCount to reach zero, then end(), and 41,151 queries ran across three rotations with zero failures.

Tool status matters here. HashiCorp Vault moved to the Business Source License (BUSL 1.1) from version 1.15, with a change date four years after each release, and it is now part of IBM. OpenBao is the community fork under the Linux Foundation's OpenSSF, with an OSI-approved license per its site; check its repo for the exact terms. For a cloud-hosted service a managed KMS plus the cloud's secrets manager is often enough, and running Vault is its own operational commitment.

const poolFor = (c: { user: string; password: string }) =>
  new pg.Pool({ host: "127.0.0.1", port, user: c.user, password: c.password, database: "postgres", max: 4 });

// الفكرة: pointer واحد على الـ pool الحالي، وبنبدله من غير ما الـ app يقف
class RotatingPool {
  private current: pg.Pool;
  private drainFirst: boolean;
  constructor(initial: pg.Pool, drainFirst: boolean) { this.current = initial; this.drainFirst = drainFirst; }
  query(text: string) { return this.current.query(text); }
  async swap(next: pg.Pool) {
    // اختبر الجديد الأول، ولو فشل الـ pool القديم يفضل شغال
    await next.query("select 1");
    const old = this.current;
    this.current = next;
    // من غير الـ drain ده، الـ queries اللي مستنية connection بتفضل معلقة للأبد
    while (this.drainFirst && old.waitingCount > 0) await sleep(5);
    await old.end();
  }
}

async function trial(name: string, drainFirst: boolean) {
  const pool = new RotatingPool(poolFor(await newRole()), drainFirst);
  let ok = 0, failed = 0, stop = false;
  const worker = async () => {
    while (!stop) {
      try { await pool.query("select count(*) from rotation_probe"); ok++; }
      catch { failed++; }
    }
  };
  const workers = Array.from({ length: 8 }, worker);
  for (let i = 0; i < 3; i++) {
    await sleep(300);
    await pool.swap(poolFor(await newRole()));
  }
  await sleep(300);
  stop = true;
  const verdict = await Promise.race([
    Promise.all(workers).then(() => "all workers finished"),
    sleep(2000).then(() => "STUCK: queued queries never settled"),
  ]);
  console.log(`${name}: ${ok} ok, ${failed} failed, ${verdict}`);
}

await trial("end() right after the swap ", false);
await trial("drain the queue, then end()", true);

بالعامية

الأساسيات في القسم 04، الـ secrets rotation والـ config validation. نبدأ بالتسريبين اللي بيتكرروا: secret اتعمله commit في الـ repo، و startup log بيطبع الـ environment. التجربة الأولى بتوري JSON.stringify(process.env) واحدة بتحط باسورد الـ database و payment key حقيقي في الـ log pipeline، اللي بيتخزن ويتعمله replication، ويقدر يقراه ناس أكتر بكتير من اللي يقدروا يوصلوا الـ production DB. الحل allow-list باللي مسموح يتطبع، و scanner في الـ CI (الـ scanner الحقيقي زي gitleaks مش متشغّل هنا).

الـ secrets manager بيغيّر شكل المشكلة من "احمي باسورد عمره طويل" لـ "طلّع باسوردات عمرها قصير". فكرة الـ dynamic secrets بتاعة Vault على Postgres حقيقي: الـ app بيطلب credential، بياخد role جديد بينتهي قريب، وبيجدده طول ما هو شغال. الـ stand-in تحت بيعمل role بـ VALID UNTIL، ولازم password auth، لأن trust بيتجاهل الـ expiry. النتيجة اللي لازم تفتكرها: بعد الـ expiry الـ connection الجديد بيفشل بـ password authentication failed، لكن الـ connection القديم بيفضل شغال، لأن الـ expiry بيتفحص وقت الـ login بس. يعني الـ revocation معناها تقتل الـ sessions، مش تستنى وخلاص.

تغيير الـ credential من غير restart معناه إنك تملك الـ pool: تفتح pool جديد بالـ role الجديد، تختبره، تبدل الـ pointer، وتفضي القديم. والتفضية مهمة أكتر من ما تبان. pool.end() بتاع pg على طول بعد الـ swap ساب الـ queries اللي في الـ queue معلقة للأبد: كل الـ workers علقوا لما قسناها. استنى waitingCount يوصل صفر، وبعدين end()، و41,151 query عدّوا على 3 rotations من غير ولا failure.

HashiCorp Vault نقل لـ Business Source License (BUSL 1.1) من الإصدار 1.15، وبتتحول لـ open بعد 4 سنين من كل إصدار، وهو دلوقتي تبع IBM. و OpenBao هو الـ fork المجتمعي تحت OpenSSF بتاعة Linux Foundation، بـ license معتمد من OSI حسب موقعهم؛ راجع الـ repo للتفاصيل. لخدمة على cloud، الـ KMS المدار مع secrets manager بتاع الـ cloud غالبًا كفاية، وتشغيل Vault التزام تشغيلي لوحده.

Trade-off: dynamic credentials vs a static password Dynamic credentials shrink the damage of a leak to minutes or hours and give you per-instance audit, but you now depend on the issuer at startup and at renewal. If it's down when a credential expires, new connections fail. Static passwords are simple and don't depend on anything, and are valid until someone remembers to change them.
الـ trade-off: الـ dynamic credentials بتصغّر ضرر التسريب لدقايق أو ساعات، وبتديك audit لكل instance، بس بقيت معتمد على الـ issuer وقت الـ startup والتجديد. لو وقع والـ credential خلص، الـ connections الجديدة بتفشل. الـ static password بسيط ومعتمدش على حاجة، لكنه صالح لحد ما حد يفتكر يغيره.

Part 2 — In transit & at rest 🟡 Intermediateالجزء 2 — التشفير أثناء النقل وعند التخزين

English

"Is it encrypted?" isn't a useful question. "Encrypted against whom?" is. Each layer below stops a different attacker, and none of them is a replacement for another. The most common confusion: encryption at rest on a cloud disk protects against someone stealing the physical disk or a snapshot, and does nothing against SQL injection or a stolen database credential, because the database decrypts for anyone who is logged in.

Application-level encryption is the strongest here because the database only ever holds ciphertext, so a dump or a curious DBA reads nothing. The price is real: as the run shows, sorting by the column sorts ciphertext bytes, so the order is effectively random, LIKE 'sara%' matches nothing, and range queries are gone.

Exact-match search is recoverable with a blind index: store an HMAC of the normalized value, keyed separately from the encryption key, in an indexed column. email_bidx = HMAC(email) gave an index scan and found SARA@example.com after normalization. But a blind index leaks equality: it reveals which rows share a value, so never use it on low-cardinality columns. In the run the country_bidx groups (1634, 271, 100) matched the real country distribution exactly, and anyone can guess which group is Egypt.

import { createCipheriv, createDecipheriv, randomBytes } from "node:crypto";

// الشكل المخزن: ⁦[version 1 byte][nonce 12][tag 16][ciphertext]⁩، والـ version بيقول أنهي key اتستخدم
export function seal(key: Buffer, plaintext: string, version = 1): Buffer {
  const nonce = randomBytes(12);
  const c = createCipheriv("aes-256-gcm", key, nonce);
  const ct = Buffer.concat([c.update(plaintext, "utf8"), c.final()]);
  return Buffer.concat([Buffer.from([version]), nonce, c.getAuthTag(), ct]);
}

export function open(key: Buffer, blob: Buffer): string {
  const nonce = blob.subarray(1, 13);
  const tag = blob.subarray(13, 29);
  const d = createDecipheriv("aes-256-gcm", key, nonce);
  d.setAuthTag(tag);
  return Buffer.concat([d.update(blob.subarray(29)), d.final()]).toString("utf8");
}

Part 3 — Envelope encryption 🟡 Intermediateالجزء 3 — الـ envelope encryption

English

Calling a KMS for every row is slow and expensive, and a master key used directly for everything is a single point of disaster. Envelope encryption solves both. A KEK (key encryption key) stays inside the KMS and only ever wraps other keys. A DEK (data encryption key) encrypts your data; the app stores the DEK encrypted by the KEK next to the data, and unwraps it once.

The FakeKms class below is a labeled stand-in, because a real KMS keeps the KEK inside an HSM and exposes only wrap and unwrap calls. Encrypting 100,000 invoices with one KMS call per row makes 100,000 calls. With a DEK per tenant, cached after first use, it makes 100 calls, and a restart costs another 100 unwraps, one per tenant, not one per row.

Calculated at a published price of about $0.03 per 10,000 requests and an assumed 10 ms per call (verify current pricing for your region; AWS lists KMS keys at $1 a month, and the request price appeared in its pricing example): 100M rows a month costs about $300 and adds 10 ms to every write, against under a cent with cached DEKs. A DEK per tenant also gives you a real isolation property: using tenant A's DEK on tenant B's row fails with Unsupported state or unable to authenticate data, because GCM's authentication tag catches it.

The trade-off is that a cached DEK sits in the app's memory. Cap how long it stays cached (minutes, or a bounded number of uses) so a memory dump or a compromised process doesn't get a key forever, and never log it.

// ده STAND-IN لـ KMS: الـ KEK جوه الـ process هنا، في KMS حقيقي عمره ما بيخرج من الـ HSM
export class FakeKms {
  calls = { generateDataKey: 0, decrypt: 0, reEncrypt: 0 };
  private keks = new Map<number, Buffer>();
  currentVersion = 0;

  constructor() { this.rotate(); }

  rotate() {
    this.currentVersion++;
    this.keks.set(this.currentVersion, randomBytes(32));
    return this.currentVersion;
  }

  generateDataKey() {
    this.calls.generateDataKey++;
    const dek = randomBytes(32);
    return { dek, wrapped: seal(this.keks.get(this.currentVersion)!, dek.toString("base64"), this.currentVersion) };
  }

  decrypt(wrapped: Buffer) {
    this.calls.decrypt++;
    return this.unwrap(wrapped);
  }

  // نفس فكرة ReEncrypt: الـ DEK بيتلف بالـ KEK الجديد من غير ما يخرج plaintext للتطبيق
  reEncrypt(wrapped: Buffer) {
    this.calls.reEncrypt++;
    return seal(this.keks.get(this.currentVersion)!, this.unwrap(wrapped).toString("base64"), this.currentVersion);
  }

  private unwrap(wrapped: Buffer) {
    return Buffer.from(open(this.keks.get(wrapped[0]!)!, wrapped), "base64");
  }
}

Part 4 — Key rotation 🟡 Intermediateالجزء 4 — تغيير الـ keys

English

There are two rotations and they cost very different amounts. Rotating the KEK means re-wrapping the DEKs: 100 DEKs took about 34 ms and touched zero data rows. Rotating a DEK means decrypting and re-encrypting every row: 100,000 rows took about 3.3 s here, about 97× more, and that ratio grows with your data, not your tenant count. So routine rotation should be KEK rotation, and DEK rotation is reserved for suspected compromise of the DEK itself.

Rotation can't be atomic across a real dataset, so old and new must coexist. The stored ciphertext carries a version byte naming the key that encrypted it, so reads use the right key and a migration can run in the background at its own pace. After rotation, the row re-encrypted at version 2 and an archived row still at version 1 both decrypted correctly. Keep old keys available for decryption until the last row using them is gone, and stop encrypting with them immediately.

AES-GCM has one rule you cannot break: never reuse a nonce with the same key. The demo below uses a fixed nonce, which is what a counter that resets on restart gives you. XOR of the two ciphertexts equals XOR of the two plaintexts exactly, so knowing one message reveals the other without the key, and the attacker recovered invoice:INV-1002:card:4242. Nonce reuse also lets an attacker forge authentication tags. The fix is a fresh 96-bit random nonce per encryption, which is what seal() does.

Random nonces have a limit too. NIST's guidance for GCM with random IVs is at most 2^32 encryptions per key, keeping the collision probability around 2^-33. At 5,000 encryptions a second, one key reaches that in about 9.9 days. This is another reason for per-tenant DEKs: the budget is per key, and a key that encrypts one tenant's rows may never get close.

فيه نوعين من الـ rotation وتكلفتهم مختلفة جدًا. تغيير الـ KEK معناه إعادة لف الـ DEKs: 100 DEK خدوا حوالي 34ms ومالمسوش ولا صف بيانات. تغيير DEK معناه فك وتشفير كل صف تاني: 100 ألف صف خدوا حوالي 3.3 ثانية هنا، أكتر بحوالي 97 ضعف، والنسبة دي بتكبر مع الـ data مش مع عدد الـ tenants. يعني الـ rotation الروتيني يبقى للـ KEK، وتغيير الـ DEK يتساب للاشتباه في اختراق الـ DEK نفسه.

الـ rotation مينفعش يبقى atomic على data حقيقية، فالقديم والجديد لازم يعيشوا مع بعض. الـ ciphertext المتخزن فيه version byte بيقول أنهي key شفره، فالقراءة بتستخدم الـ key الصح، والـ migration يشتغل في الخلفية على مهله. بعد الـ rotation الصف اللي اتشفر بـ version 2 والصف الأرشيف اللي لسه version 1 اتفكوا صح الاتنين. خلي الـ keys القديمة متاحة للفك لحد ما آخر صف بيستخدمها يتشال، وبطّل تشفر بيها فورًا.

الـ AES-GCM ليه قاعدة واحدة متتكسرش: أبدًا ماتكررش nonce مع نفس الـ key. الـ demo بيستخدم nonce ثابت، وده اللي بيحصل مع counter بيتصفر بعد restart. الـ XOR بتاع الـ ciphertexts بيساوي الـ XOR بتاع الـ plaintexts بالظبط، فمعرفة رسالة واحدة بتكشف التانية من غير الـ key، والمهاجم طلّع invoice:INV-1002:card:4242. وتكرار الـ nonce كمان بيخلي المهاجم يقدر يزوّر الـ authentication tags. الحل nonce عشوائي 96 bit لكل عملية تشفير، وده اللي seal() بتعمله.

والـ nonces العشوائية ليها حد كمان. إرشادات NIST للـ GCM بـ IVs عشوائية هي 2^32 عملية تشفير على الأكتر لكل key، عشان احتمال التكرار يفضل حوالي 2^-33. عند 5000 عملية في الثانية، key واحد بيوصل ده في حوالي 9.9 يوم. وده سبب تاني للـ DEK لكل tenant: الحد لكل key، و key بيشفر صفوف tenant واحد يمكن ميقربش منه أبدًا.

فين هستخدمه في شغلي؟ لو عندك خدمة بتشفر رسايل بـ AES-GCM: دوّر في الكود على createCipheriv وتأكد إن الـ nonce من randomBytes(12) كل مرة، مش counter ولا قيمة ثابتة. واعمل column key_version أو byte في الـ ciphertext من أول يوم، عشان الـ rotation يبقى background job مش downtime. ولو security طلبت rotation سنوي، قولها rotation للـ KEK بياخد ثواني.
Interview question "What's the difference between rotating the KEK and rotating the DEK?" → KEK rotation only re-wraps DEKs, so it's cheap and can run on a schedule. DEK rotation re-encrypts data, so it scales with data volume. Use a key version stored with each ciphertext so old and new coexist during migration.
"إيه الفرق بين تغيير الـ KEK وتغيير الـ DEK؟" ← تغيير الـ KEK بيعيد لف الـ DEKs بس، فهو رخيص وممكن يبقى دوري. تغيير الـ DEK بيعيد تشفير البيانات، فبيكبر مع حجم الـ data. واستخدم key version متخزن مع كل ciphertext عشان القديم والجديد يعيشوا مع بعض أثناء الـ migration.

Part 5 — PII & minimization 🟡 Intermediateالجزء 5 — الـ PII وتقليل البيانات

English

You can't protect data you haven't located. Classify every column in a map kept in the repo, using a small set of labels: none, pii, sensitive, secret. Then make it enforceable: a test reads information_schema and fails when a column has no classification, so a migration that adds users.phone fails CI with unclassified columns: users.phone. The review conversation then happens at the moment the column is added, which is the only moment anyone remembers why it exists.

Logs are where PII escapes most often. pino's redact removes known paths before the line is written: user.email, card.number and headers.authorization come out as [REDACTED]. Its limit is that it works on paths, not on text: the message payment failed for sara@example.com went through untouched. So don't interpolate user data into message strings, keep structured fields, and treat redaction as the safety net rather than the plan.

The best protection is not having the data. Data minimization means collecting only what a feature needs, with a retention period set up front: if you only need age verification, store a boolean, not a birth date. For analytics, pseudonymize with a keyed HMAC of the user id. It is stable, so funnels still work, and it can't be reversed without the key, unlike a plain hash of an email, which a list of emails will crack. Note the legal distinction: pseudonymized data is generally still personal data under GDPR, because re-identification remains possible.

Part 6 — GDPR & audit 🟡 Intermediateالجزء 6 — الـ GDPR والـ audit

English

This is engineering practice, not legal advice. The right to erasure means a user's data must go from every place it lives: the database, cache, search index, data warehouse, logs and backups. Backups are the hard one, because you can't surgically edit a backup. Section 07, GDPR deletion covers the deletion flow, and section 09 covers immutable event logs. Data residency, where the data physically sits, is in geo-distribution.

Crypto-shredding solves the backup problem: encrypt each user's data under that user's own DEK, and to erase the user delete the key. In the run, after deleting the key the live data read ciphertext only: no key, unreadable, another user was unaffected, and a backup restored afterwards was unreadable too. The trap is where the keys live. A second backup that included the key table restored fine and Sara's data came straight back. If the key table is in the same backup as the data, you erased nothing. Keep keys in a separate store with its own short retention, so an old backup of data is not paired with an old backup of keys.

Audit logs prove who did what, and they only help if they're trustworthy. Section 07, audit logging compares three approaches. Here is the tamper-evidence layer: an append-only table where a trigger blocks UPDATE and DELETE and each row stores a hash chained to the previous one.

Building it taught a real concurrency lesson. The first version used an identity column for ordering, and six concurrent writers broke the chain immediately (chain BROKEN at seq 4), because the identity value is assigned before the trigger takes its lock, so rows can get the chain position out of order. The fix assigns the sequence inside the advisory lock. Then 300 concurrent inserts verified clean, a superuser who disabled triggers and edited row 10 was caught (row content was modified), and an attacker deleting the newest rows was caught only by comparing with a head hash stored elsewhere. Triggers stop mistakes; only an external anchor stops someone with superuser. Publish the head hash somewhere the database admin can't write, on a schedule.

begin

await Promise.all(writers.map(async (c, w) => {
  for (let i = 0; i < 50; i++) await write(c, `admin_${w}`, "user.view", `user_${i}`);
}));
await Promise.all(writers.map((c) => c.end()));

type Row = { seq: string; actor: string; action: string; target: string; at: string; prev_hash: Buffer; hash: Buffer };
async function verify(): Promise<string> {
  const { rows } = await db.query<Row>("select seq, actor, action, target, at::text as at, prev_hash, hash from audit_log order by seq");
  let prev: Buffer = Buffer.from([0x00]);
  for (const r of rows) {
    const expected = createHash("sha256").update(Buffer.concat([prev, Buffer.from(`${r.actor}|${r.action}|${r.target}|${r.at}`)])).digest();
    if (!r.prev_hash.equals(prev)) return `chain BROKEN at seq ${r.seq}: prev_hash does not match`;
    if (!r.hash.equals(expected)) return `chain BROKEN at seq ${r.seq}: row content was modified`;
    prev = r.hash;
  }
  return `chain OK, ${rows.length} rows, head ${prev.toString("hex").slice(0, 16)}`;
}

بالعامية

دي ممارسات هندسية مش استشارة قانونية. الـ right to erasure معناه إن بيانات اليوزر لازم تروح من كل مكان موجودة فيه: الـ database، الـ cache، الـ search index، الـ data warehouse، الـ logs، والـ backups. والـ backups هي الصعبة، لأنك مقدرش تعدل backup بالمشرط. القسم 07، الـ GDPR deletion بيغطي الـ flow، والقسم 09 بيغطي الـ immutable event logs. والـ data residency، يعني البيانات قاعدة فين فعليًا، في الـ geo-distribution.

الـ crypto-shredding بيحل مشكلة الـ backups: شفّر بيانات كل يوزر بـ DEK بتاعه، ولما تمسح اليوزر امسح الـ key. في التجربة بعد مسح الـ key، الـ data الحية قرت ciphertext only: no key, unreadable، ويوزر تاني ماتأثرش، و backup اترجع بعدها طلع مش مقروء برضه. الفخ هو مكان الـ keys. backup تاني كان فيه جدول الـ keys اترجع عادي وبيانات Sara رجعت على طول. لو جدول الـ keys في نفس الـ backup مع الـ data، إنت مامسحتش حاجة. خلي الـ keys في store منفصل وبـ retention قصير، عشان backup قديم للـ data ميتجمعش مع backup قديم للـ keys.

الـ audit logs بتثبت مين عمل إيه، ومفيدة بس لو موثوقة. القسم 07، الـ audit logging بيقارن 3 طرق. هنا طبقة كشف التلاعب: جدول append-only فيه trigger بيمنع UPDATE وDELETE، وكل صف بيخزن hash مربوط بالصف اللي قبله.

والبناء علّمنا درس concurrency حقيقي. أول نسخة استخدمت identity column للترتيب، و6 writers متوازيين كسروا السلسلة على طول (chain BROKEN at seq 4)، لأن قيمة الـ identity بتتحدد قبل ما الـ trigger ياخد القفل، فالصفوف ممكن تاخد مكانها في السلسلة بالعكس. الحل: الـ sequence بيتحدد جوه الـ advisory lock. بعدها 300 insert متوازية طلعوا سليمين، و superuser وقف الـ triggers وعدّل الصف 10 اتمسك (row content was modified)، ومهاجم مسح آخر الصفوف اتمسك بس بالمقارنة مع head hash متخزن بره. الـ triggers بتمنع الغلطات؛ والـ anchor الخارجي بس هو اللي يوقف حد معاه superuser. انشر الـ head hash في مكان الـ DB admin مايقدرش يكتب فيه، بشكل دوري.

فين هستخدمه في شغلي؟ لو عندك endpoint "احذف حسابي": اكتب checklist بكل مكان البيانات فيه (Postgres، Redis، search، analytics، logs، backups)، وخلي الـ erasure job بيسجل على كل مكان خلص. ولأي action إداري حساس زي refund أو تعديل صلاحيات، اكتب audit row من نفس الـ transaction، وفي الـ cron اليومي ابعت الـ head hash لـ S3 بـ object lock أو لنظام تاني مايقدرش الـ DBA يكتب فيه.
Trade-off: crypto-shredding costs a key per user A DEK per user means more wrapped keys and a lookup on every read, and losing the key table loses everything, so the key store needs its own backups with short retention. It is worth it when backups are immutable, as with event logs, or when the amount of data makes per-row erasure impractical. If you only have a live database with short backups, a normal delete may be enough.
الـ trade-off: الـ crypto-shredding بيكلف key لكل يوزر. يعني wrapped keys أكتر و lookup على كل read، ولو ضاع جدول الـ keys كله ضاع، فلازم الـ key store يبقى ليه backups بـ retention قصير. يستاهل لما الـ backups ماتتغيرش زي الـ event logs، أو لما كمية البيانات تخلي المسح صف بصف صعب. لو عندك DB حي و backups قصيرة، delete عادي يمكن يكفي.

Common mistakes · غلطات شائعة

❌ Logging the whole config at startup 
// ❌ كل الأسرار طلعت في الـ log pipeline
logger.info({ config: process.env }, "starting");
✅ Log an allow-list only 
// ✅ الـ keys المسموحة بس هي اللي بتتطبع
const safe = pick(process.env, ["NODE_ENV", "LOG_LEVEL"]);
logger.info({ config: safe }, "starting");
بالعامية

❌ الـ process.env فيه كل الأسرار، وبمجرد ما يدخل الـ log pipeline بقى عند ناس كتير وبيتخزن شهور. ✅ allow-list بأسامي الـ keys اللي ينفع تتطبع، وأي حاجة تانية مش بتطلع أصلًا.

❌ A fixed or counter-based GCM nonce 
// ❌ كل restart بيرجع يكرر نفس الـ nonces
const nonce = Buffer.alloc(12, counter++);
createCipheriv("aes-256-gcm", key, nonce);
✅ A fresh random nonce per encryption 
// ✅ لكل عملية تشفير nonce عشوائي جديد
const nonce = randomBytes(12);
createCipheriv("aes-256-gcm", key, nonce);
بالعامية

❌ الـ counter بيتصفر بعد restart، فنفس الـ key والـ nonce بيتكرروا، و XOR الـ ciphertexts بيكشف الرسايل، وكمان بيتزوّر الـ authentication tag. ✅ randomBytes(12) لكل عملية، وخلي بالك من حد 2^32 لكل key.

❌ Saying "encrypted at rest" answers a database breach 
-- ❌ الـ disk متشفر، بس أي login بيقرا كل حاجة
select email from customers;
-- النتيجة: كل الإيميلات plaintext لأي حد عنده credential
✅ App-level encryption for the columns that matter 
-- ✅ الـ DB بتشوف ciphertext، والـ app هو اللي بيفك
select email_enc from customers;
-- النتيجة: bytes مش مقروءة من غير الـ key بتاع الـ app
بالعامية

❌ تشفير الـ disk بيحمي من سرقة الـ disk بس، وأي حد معاه DB login بيقرا كله عادي. ✅ التشفير في الـ app للـ columns الحساسة بيخلي الـ dump نفسه مش مقروء، بس بتدفع تمن search و sort.

❌ Keeping the key table in the same backup 
# ❌ النسخة الكاملة فيها جدول الـ keys مع البيانات
pg_dump -f full.sql app
✅ Back keys up separately, with short retention 
# ✅ النسخة بتاعة البيانات من غير محتوى جدول الـ keys
pg_dump --exclude-table-data=user_keys -f data.sql app
بالعامية

❌ جدول الـ keys في نفس الـ backup معناه إن أي restore بيرجّع كل اللي الـ crypto-shredding مسحه، وده اللي شوفناه بعينينا مع Sara. ✅ الـ keys ليها backup منفصل و retention قصير، والـ --exclude-table-data بيسيب تعريف الجدول ويشيل الصفوف.

Cheat sheet · الخلاصة

  • Never log process.env; allow-list what is logged and scan in CI.
  • VALID UNTIL is checked at login only: existing connections survive, so revocation means terminating sessions.
  • Rotating a pool: test the new one, swap, drain waitingCount to zero, then end().
  • Vault is BUSL 1.1 from 1.15; OpenBao is the OpenSSF fork; a cloud KMS is often enough.
  • Ask "encrypted against whom?": TLS, disk, column and app-level encryption each stop different attackers.
  • App-level encryption loses search and sort; a blind index restores equality only, and leaks low-cardinality distributions.
  • Envelope: KEK stays in KMS, DEK per tenant, cached briefly: 100 KMS calls instead of 100,000.
  • KEK rotation re-wraps keys (ms); DEK rotation re-encrypts data (about 97× here, growing with rows).
  • GCM: never reuse a nonce; random 96-bit nonces, at most 2^32 per key.
  • PII: a classification map enforced by a test on information_schema; redact covers paths, not message text.
  • Minimize first; pseudonymize with a keyed HMAC, which is still personal data.
  • Crypto-shredding needs keys outside the data backup; audit chains need the sequence set inside the lock and an external head anchor.
بالعامية
  • متعملش log لـ process.env أبدًا؛ allow-list للي بيتطبع و scan في الـ CI.
  • الـ VALID UNTIL بيتفحص وقت الـ login بس: الـ connections القديمة بتعيش، فالـ revocation معناها تقتل الـ sessions.
  • تغيير الـ pool: اختبر الجديد، بدّل، استنى waitingCount يبقى صفر، وبعدين end().
  • الـ Vault بقى BUSL 1.1 من 1.15؛ والـ OpenBao هو الـ fork تحت OpenSSF؛ والـ KMS بتاع الـ cloud غالبًا كفاية.
  • اسأل "متشفر ضد مين؟": الـ TLS والـ disk والـ column والـ app-level كل واحد بيوقف مهاجم مختلف.
  • التشفير في الـ app بيخسر search و sort؛ الـ blind index بيرجّع التساوي بس، وبيكشف توزيع القيم القليلة.
  • الـ envelope: الـ KEK في الـ KMS، و DEK لكل tenant متكاش فترة قصيرة: 100 call بدل 100 ألف.
  • تغيير الـ KEK بيعيد لف الـ keys (ms)، وتغيير الـ DEK بيعيد تشفير الـ data (حوالي 97 ضعف هنا، وبيكبر مع الصفوف).
  • الـ GCM: ماتكررش nonce أبدًا؛ nonces عشوائية 96 bit، وعلى الأكتر 2^32 لكل key.
  • الـ PII: خريطة تصنيف بيفرضها test على information_schema؛ والـ redact بيغطي الـ paths مش نص الرسالة.
  • قلّل البيانات الأول؛ والـ pseudonymize بـ HMAC بمفتاح، ولسه personal data.
  • الـ crypto-shredding محتاج الـ keys بره backup البيانات؛ وسلسلة الـ audit محتاجة الـ sequence جوه القفل و head anchor خارجي.
