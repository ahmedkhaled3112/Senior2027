Why this matters · ليه ده مهم

English

Every real product ends up storing files: invoice PDFs, exports, avatars, database backups. Object storage is the cheap, durable place for them, but it behaves nothing like a filesystem or a database, and the differences decide your design: no partial updates, uploads that should skip your API, parts that bill you forever when abandoned, and archive tiers that take hours to read.

Retention and backups are where a system design answer turns into a production answer. "We have backups" means nothing until you can state the RPO, the RTO and the date of your last restore test. Interviewers ask this, and incidents test it.

بالعامية

أي منتج حقيقي في الآخر بيخزّن ملفات: فواتير PDF، exports، صور، backups بتاعة الداتابيز. الـ object storage هو المكان الرخيص والـ durable ليها، بس هو مش زي الـ filesystem ولا زي الداتابيز، والفروق دي هي اللي بتحدد الـ design بتاعك: مفيش partial update، الـ uploads المفروض متعديش على الـ API بتاعك، الـ parts اللي بتتساب بتتحاسب عليها للأبد، والـ archive tiers القراية منها بتاخد ساعات.

والـ retention والـ backups هما المكان اللي إجابة الـ system design بتتحول فيه لإجابة production. جملة "عندنا backups" ملهاش معنى لحد ما تقول الـ RPO كام، والـ RTO كام، وآخر مرة جرّبت فيها restore كانت إمتى. ده اللي الـ interviewer بيسأل عليه، وده اللي الـ incidents بتختبره.

Part 1 — Object storage semantics 🟡 Intermediateالجزء 1 — الـ semantics بتاعة الـ object storage

English

The model is a flat map from key to blob. A key like tenants/t-42/invoices/2026/INV-1001.json is one string: the slashes are ordinary characters. "Folders" are computed at read time from Prefix plus Delimiter, so renaming a "folder" means copying and deleting every object under it.

Objects are immutable. There is no partial update: changing one field means writing the whole object again. Partial reads do exist through Range. Listing is paginated, up to 1,000 keys per page on AWS, so any "list everything" code needs a ContinuationToken loop.

Consistency. Since December 1, 2020, S3 gives strong read-after-write for GET, PUT and LIST, in every region, at no extra cost. So the README's "eventual → strong" is history you may still see in old blog posts. Strong does not mean transactional: there are no multi-key transactions, and two concurrent writers to one key end with last-writer-wins unless you use a condition.

Conditional writes are the fix for that race. If-None-Match: * means "create only if the key does not exist", and If-Match: <etag> means "replace only if it is still the version I read". They work on PutObject, CompleteMultipartUpload and CopyObject. Among concurrent writers the first to finish wins and the others get 412 Precondition Failed; a concurrent delete can produce 409 Conflict instead.

Current limits (AWS docs): 48.8 TiB maximum object, 10,000 parts maximum, parts from 5 MiB to 5 GiB with no minimum on the last part, and multipart worth considering from 100 MB. Note that the largest object is simply 10,000 × 5 GiB, while minimum-size parts only reach 48.8 GiB, so part size must be chosen from the file size.

بالعامية

الـ object storage ببساطة map مسطّحة من key لـ blob. المفتاح زي tenants/t-42/invoices/2026/INV-1001.json ده نص واحد، والـ "/" حرف عادي. الـ "فولدرات" بتتحسب وقت القراية بـ Prefix وDelimiter، فلو عايز تعمل rename لفولدر، لازم تعمل copy و delete لكل object جواه.

الـ objects immutable: مفيش partial update. لو هتغيّر حقل واحد هتكتب الـ object كله من أول وجديد. القراية الجزئية موجودة بـ Range، بس الكتابة الجزئية لأ. والـ list بصفحات، على AWS لحد 1000 key في الصفحة، فأي كود بيقول "هات كل حاجة" لازم يلف بـ ContinuationToken.

الـ consistency: من 1 ديسمبر 2020 الـ S3 بيدي strong read-after-write لـ GET و PUT و LIST في كل الـ regions ومن غير فلوس زيادة. يعني "eventual → strong" اللي في الـ README ده تاريخ لسه هتلاقيه في blog posts قديمة. بس strong مش معناها transactions: مفيش transaction على أكتر من key، واتنين بيكتبوا على نفس الـ key في نفس الوقت، اللي يخلص الأخير هو اللي يكسب، إلا لو استخدمت شرط.

الكتابة المشروطة هي الحل للـ race ده. If-None-Match: * معناها "اكتب بس لو الـ key مش موجود"، وIf-Match: <etag> معناها "بدّل بس لو لسه نفس النسخة اللي قريتها". شغالين على PutObject و CompleteMultipartUpload و CopyObject. لو في كذا حد بيكتب مع بعض، أول واحد يخلص يكسب والباقي ياخدوا 412 Precondition Failed، ولو حصل delete في نفس الوقت ممكن تاخد 409 Conflict.

الحدود الحالية من الـ docs: أكبر object 48.8 TiB، أقصى عدد parts هو 10,000، حجم الـ part من 5 MiB لـ 5 GiB والـ part الأخير ملوش حد أدنى، وفكّر في الـ multipart من 100 MB. لاحظ إن أكبر object هو ببساطة 10,000 × 5 GiB، بينما أصغر parts بتوصّلك لـ 48.8 GiB بس، يعني حجم الـ part لازم يتحسب من حجم الملف.

إحنا بنشغل الأمثلة على s3rver، ده stand-in محلي مش AWS. الجدول فوق بيقولك بالظبط إيه اللي موديله وإيه لأ.

فين هستخدمه في شغلي؟ فواتير SaaS: خلّي الـ key tenants/{tenantId}/invoices/{yyyy}/{uuid}.pdf. الـ tenant في أول المفتاح بيدّيك IAM policy بالـ prefix وتكلفة لكل عميل وexport سهل. والـ cron اللي بيبني تقرير شهري من أكتر من worker: اكتبه بـ If-None-Match: *، أول worker يكسب والباقي ياخدوا 412 ويتجاهلوها، بدل ما تعمل distributed lock عشان ملف.
Trade-off: the key is your only index The only query S3 answers quickly is "keys starting with this prefix, in lexical order". Listing is paged at 1,000 keys per request, so finding "all invoices over $500" means a metadata table in Postgres, not S3. Keep bytes in S3 and facts in the database, and link them with the key.
الـ key هو الـ index الوحيد عندك. السؤال الوحيد اللي S3 بيجاوبه بسرعة هو "المفاتيح اللي بتبدأ بالـ prefix ده بالترتيب الأبجدي". والـ list بصفحات كل واحدة 1000 key، فسؤال زي "كل الفواتير فوق 500 دولار" محتاج جدول metadata في Postgres مش S3. خلّي الـ bytes في S3 والمعلومات في الداتابيز، واربط بينهم بالـ key.
Interview question "S3 is strongly consistent now. Can two workers still overwrite each other's output?" → Yes. Strong consistency only guarantees that a read sees the latest finished write. Two PUTs to one key are still last-writer-wins. Use If-None-Match: * for create-once or If-Match with the ETag for compare-and-swap, and treat 412 as "someone else won".
"الـ S3 بقى strongly consistent. ممكن لسه اتنين workers يكتبوا فوق بعض؟" ← أيوه. الـ strong consistency بتضمن بس إن القراية تشوف آخر كتابة خلصت. اتنين PUT على نفس الـ key برضه آخر واحد يكسب. استخدم If-None-Match: * للإنشاء مرة واحدة، أو If-Match مع الـ ETag لـ compare-and-swap، وتعامل مع الـ 412 على إنها "حد تاني سبقني".

Part 2 — Presigned URLs: invoice uploads that skip your API 🟡 Intermediateالجزء 2 — الـ presigned URLs: رفع الفواتير من غير ما يعدّي على الـ API

English

Proxying uploads through Node is the expensive default. Eight concurrent 20 MiB invoice uploads, measured on the API process alone: buffering peaked at about 416 MB RSS, and streaming still moved all 160 MiB through the process while holding one connection per upload. With presigning the API moved 0 bytes: it signs a URL and returns a small JSON. Memory and connection slots are what fall over first under real load, so the difference matters most when uploads are slow, because a slow mobile client holds a proxy connection for minutes.

A presigned URL is a normal S3 URL with an expiry and a signature computed from your credentials. Whoever holds it can do exactly that one operation on that one key until it expires, and no AWS credentials ever reach the browser. One detail bites people: the AWS SDK v3 presigner does not sign Content-Type by default (its source adds it to unsignableHeaders), so a URL you meant for PDFs would accept any type. Pass signableHeaders: new Set(["content-type"]), and the client must then send exactly that header. Line (9) of the run prints both signed-header lists. Our stand-in doesn't verify signatures, so the enforcement itself comes from AWS's signing rules, not from this run.

You cannot trust the client about what it uploaded. A plain presigned PUT doesn't give you a size range, so use a POST policy with content-length-range when you need a hard limit. Either way, record a pending row before signing, then confirm: on completion read the real size with HeadObject and only then mark it uploaded. Generate the key yourself, never from the user's filename, and let a reaper expire rows whose upload never arrived. Completion can come from the client or, more reliably, from an S3 event notification into a queue (not run here).

الـ Browser بيطلب رفع من الـ API، فالـ API يسجّل صف pending في Postgres ويمضي URL من غير ما يكلم S3 أصلًا، ويرجّع الـ id والـ URL. بعدين الـ Browser يرفع الملف على S3 مباشرة، والـ bytes مبتعديش على الـ API خالص. لما يخلص يكلّم complete، فالـ API يسأل S3 بـ HeadObject عن الحجم الحقيقي، ولو تمام يحوّل الصف لـ uploaded.

import http from "node:http";
import type { AddressInfo } from "node:net";
import { Transform } from "node:stream";
import { PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";
import { s3Client } from "./lab.ts";

const Bucket = "invoices";
const s3 = s3Client(process.env.S3_ENDPOINT!);
const stats = { bytesThroughApi: 0, peakRssMb: 0 };
setInterval(() => {
  stats.peakRssMb = Math.max(stats.peakRssMb, Math.round(process.memoryUsage().rss / 2 ** 20));
}, 10).unref();

const server = http.createServer(async (req, res) => {
  const url = new URL(req.url!, "http://x");
  const Key = `tenants/t-42/invoices/${url.searchParams.get("name")}`;
  const ContentLength = Number(req.headers["content-length"] ?? 0);
  const count = (c: Buffer) => { stats.bytesThroughApi += c.length; };

  if (url.pathname === "/proxy-buffer") {
    // ❌ الأوحش: الملف كله في الـ heap قبل ما يتبعت لـ S3
    const chunks: Buffer[] = [];
    for await (const c of req) { count(c as Buffer); chunks.push(c as Buffer); }
    await s3.send(new PutObjectCommand({ Bucket, Key, Body: Buffer.concat(chunks), ContentType: "application/pdf" }));
    res.end("ok");
  } else if (url.pathname === "/proxy-stream") {
    // ❌ أحسن في الـ memory: بس الـ API لسه ماسك الـ connection وعدّى عليه كل byte
    const counted = req.pipe(new Transform({ transform(c, _e, cb) { count(c); cb(null, c); } }));
    await s3.send(new PutObjectCommand({ Bucket, Key, Body: counted, ContentLength, ContentType: "application/pdf" }));
    res.end("ok");
  } else if (url.pathname === "/presign") {
    // ✅ الـ API بيعمل توقيع بس: JSON صغير والـ client بيرفع لـ S3 مباشرة
    const signed = await getSignedUrl(s3, new PutObjectCommand({ Bucket, Key, ContentType: "application/pdf" }), { expiresIn: 300 });
    res.setHeader("content-type", "application/json");
    res.end(JSON.stringify({ url: signed }));
  } else if (url.pathname === "/stats") {
    res.end(JSON.stringify(stats));
  } else { res.statusCode = 404; res.end(); }
});
server.listen(0, "127.0.0.1", () => {
  process.send!({ port: (server.address() as AddressInfo).port });
});

async function completeUpload(id: string) {
  const { rows: [row] } = await db.query(`select * from invoice_uploads where id=$1`, [id]);
  // لو اتأكد قبل كده: رد عادي من غير ما نعمل حاجة تاني (idempotent)
  if (row.status !== "pending") return { http: 200, status: row.status, repeated: true };
  let size: number;
  try {
    const head = await s3.send(new HeadObjectCommand({ Bucket, Key: row.s3_key }));
    size = head.ContentLength!;
  } catch {
    return { http: 409, reason: "object not uploaded yet" };
  }
  // إحنا اللي بنتحقق: الـ client ممكن يقول أي حاجة، الحجم الفعلي من S3
  if (size !== Number(row.expected_bytes)) {
    await db.query(`update invoice_uploads set status='rejected' where id=$1`, [id]);
    await s3.send(new DeleteObjectCommand({ Bucket, Key: row.s3_key }));
    return { http: 422, reason: `size ${size} != expected ${row.expected_bytes}` };
  }
  const r = await db.query(
    `update invoice_uploads set status='uploaded', confirmed_at=now() where id=$1 and status='pending'`, [id]);
  return { http: 200, status: "uploaded", rows: r.rowCount };
}

الـ presigned URL هو URL عادي لـ S3 فيه expiry و signature محسوبة من الـ credentials بتاعتك. اللي معاه اللينك يقدر يعمل العملية دي بالظبط على الـ key ده بس لحد ما ينتهي، والـ AWS credentials عمرها ما بتوصل للـ browser. في تفصيلة بتوقّع ناس كتير: الـ presigner بتاع AWS SDK v3 مش بيمضي الـ Content-Type بشكل افتراضي (الكود بتاعه بيحطه في unsignableHeaders)، فاللينك اللي إنت عامله للـ PDF هيقبل أي نوع. مرّر signableHeaders: new Set(["content-type"])، وساعتها الـ client لازم يبعت الـ header ده بالظبط. سطر (9) في التشغيل بيطبع الـ signed headers في الحالتين. والـ stand-in مش بيتحقق من التوقيع، فالإلزام نفسه جاي من قواعد التوقيع بتاعة AWS، مش من التشغيل ده.

متصدّقش الـ client في اللي رفعه. الـ presigned PUT العادي مش بيدّيك حد للحجم، فلو عايز حد أقصى استخدم POST policy بـ content-length-range. وفي الحالتين: سجّل صف pending قبل التوقيع، ولما يخلص اقرا الحجم الحقيقي بـ HeadObject وبعدها بس علّمه uploaded. اعمل الـ key بنفسك، عمره ما يبقى من اسم ملف المستخدم، وخلّي reaper يحوّل الصفوف اللي الرفع بتاعها موصلش لـ expired. إشارة الانتهاء ممكن تيجي من الـ client، أو الأضمن من S3 event notification على queue (ده مشغلناهوش هنا).

الغلطة الشائعة: تعمل req.on("data") عشان تعدّ الـ bytes وبعدين تدّي الـ req للـ SDK. أنا نفسي وقعت فيها وأنا بكتب المثال ده: الـ listener بيشغّل الـ stream في flowing mode، فالـ SDK مش بيلاقي data والـ request بيعلّق للأبد. الحل Transform بيعدّ ويعدّي، زي اللي في الكود.

فين هستخدمه في شغلي؟ شاشة "ارفع فاتورة المورّد" في SaaS: endpoint POST /invoices/uploads يعمل authz ويسجل pending ويرجّع URL صالح 5 دقايق. الـ Next client يرفع على S3 بـ fetch مع progress، وبعدين يكلّم /complete. الـ worker يبدأ يعمل virus scan و OCR بعد التأكيد بس. وcron كل ساعة يحوّل الـ pending القديمة لـ expired ويمسح أي object يتيم.
What breaks: a presigned URL is a bearer token Anyone with the link can use it until it expires, so a URL logged in your access log or pasted into chat is a leak. Keep expiry short (minutes), never log the query string, and sign one key per upload. Revoking a single URL before expiry isn't a feature: the signature is checked against the credentials, so rotating them is the blunt instrument.
الـ presigned URL زي الـ bearer token: اللي معاه اللينك يستخدمه لحد ما ينتهي، فأي لينك اتسجل في الـ access log أو اتبعت في شات يبقى تسريب. خلّي الـ expiry قصير (دقايق)، متسجلش الـ query string في الـ logs، وامضي key واحد لكل upload. مفيش حاجة اسمها تلغي URL واحد قبل ما ينتهي: التوقيع مربوط بالـ credentials، فتغييرها هو الحل الوحيد وهو حل تقيل.

Part 3 — Multipart uploads 🟡 Intermediateالجزء 3 — الـ multipart upload

English

Multipart splits an object into numbered parts of at least 5 MiB (only the last may be smaller), uploaded independently and in parallel. A flaky network costs you one part instead of the whole file, and throughput grows with concurrency. Three calls: CreateMultipartUpload returns an upload id, UploadPart returns one ETag per part, and CompleteMultipartUpload stitches them in part-number order.

Resume needs state. Save each part's ETag as it succeeds, in a file, a database row or browser storage. After a crash, send only the missing parts. On real S3, ListParts can rebuild that state; our stand-in doesn't implement it, so the example persists a JSON file. For server-side streams, Upload from @aws-sdk/lib-storage handles chunking and concurrency for you (not run here), but it does not resume across process restarts.

The ETag of a multipart object is not the MD5 of the file. AWS's docs say so; the commonly observed form is the MD5 of the concatenated part MD5s, followed by -N, and that's an observation rather than a contract. Our stand-in returned the plain file MD5, which is a stand-in quirk, so the script prints the value AWS would produce next to it. If you need end-to-end integrity, send a checksum (x-amz-checksum-sha256) and compare that, rather than parsing ETags.

Abandoned uploads cost money forever. Parts of an upload that is never completed or aborted stay billed and don't appear in a normal list. The fix is one lifecycle rule, AbortIncompleteMultipartUpload, shown in Part 4.

// الـ multipart بإيدنا: parts بالتوازي، فشل في part 3، و resume من غير إعادة اللي خلص
import { createHash } from "node:crypto";
import { writeFileSync, readFileSync, rmSync } from "node:fs";
import {
  CreateMultipartUploadCommand, UploadPartCommand, CompleteMultipartUploadCommand, HeadObjectCommand,
} from "@aws-sdk/client-s3";
import { startS3 } from "./lab.ts";

console.log("STAND-IN: s3rver. The failure on part 3 is injected by this script.");
const { s3, bucket: Bucket, close } = await startS3();
const MiB = 2 ** 20;
const PART_SIZE = 5 * MiB;
const Key = "exports/2026-10-invoices.tar";

// ملف 26 MiB بمحتوى ثابت عشان الـ ETag يطلع هو هو كل مرة
const file = Buffer.alloc(26 * MiB);
for (let i = 0; i < file.length; i++) file[i] = i % 251;

const parts = Array.from({ length: Math.ceil(file.length / PART_SIZE) }, (_, i) => ({
  PartNumber: i + 1, body: file.subarray(i * PART_SIZE, (i + 1) * PART_SIZE),
}));
console.log("parts:", parts.map((p) => `${p.PartNumber}:${p.body.length / MiB}MiB`).join(" "));

const { UploadId } = await s3.send(new CreateMultipartUploadCommand({ Bucket, Key }));

type State = { uploadId: string; done: Record<number, string> };
const STATE = "upload-state.json";
const state: State = { uploadId: UploadId!, done: {} };
const save = () => writeFileSync(STATE, JSON.stringify(state));

let bytesSent = 0;
let failOnce = true;
async function uploadPart(p: (typeof parts)[number]) {
  if (p.PartNumber === 3 && failOnce) {
    failOnce = false;
    throw new Error("ECONNRESET while sending part 3");
  }
  const r = await s3.send(new UploadPartCommand({ Bucket, Key, UploadId: state.uploadId, PartNumber: p.PartNumber, Body: p.body }));
  bytesSent += p.body.length;
  // بنسجّل الـ ETag بعد كل part ناجح: ده اللي بيخلّي الـ resume ممكن
  state.done[p.PartNumber] = r.ETag!;
  save();
}

// تشغيل بحد أقصى 3 في نفس الوقت، والـ errors بتتجمع بدل ما توقّف الباقي
async function runPool(todo: typeof parts, limit: number) {
  const q = [...todo];
  const errors: string[] = [];
  await Promise.all(Array.from({ length: limit }, async () => {
    while (q.length) {
      const p = q.shift()!;
      await uploadPart(p).catch((e: Error) => errors.push(`part ${p.PartNumber}: ${e.message}`));
    }
  }));
  return errors;
}

const errors = await runPool(parts, 3);
console.log("first pass errors:", errors, "| uploaded", Object.keys(state.done).length, "of", parts.length, "| bytes", bytesSent / MiB, "MiB");

// الـ resume: نقرا الـ state من الـ disk زي ما يكون الـ process اتقفل
const saved = JSON.parse(readFileSync(STATE, "utf8")) as State;
Object.assign(state, saved);
const missing = parts.filter((p) => !state.done[p.PartNumber]);
const before = bytesSent;
await runPool(missing, 3);
console.log("resume uploaded parts:", missing.map((p) => p.PartNumber), "| bytes this pass", (bytesSent - before) / MiB, "MiB");

const done = await s3.send(new CompleteMultipartUploadCommand({
  Bucket, Key, UploadId: state.uploadId,
  MultipartUpload: { Parts: parts.map((p) => ({ PartNumber: p.PartNumber, ETag: state.done[p.PartNumber]! })) },
}));
const head = await s3.send(new HeadObjectCommand({ Bucket, Key }));
console.log("complete: size", head.ContentLength, "etag", done.ETag);

// الـ ETag مش MD5 الملف: ده MD5 لسلسلة الـ MD5 بتاعة الـ parts وبعدها عددهم
const md5 = (b: Buffer) => createHash("md5").update(b).digest();
const fileMd5 = md5(file).toString("hex");
const perPart = md5(Buffer.concat(parts.map((p) => md5(p.body)))).toString("hex") + `-${parts.length}`;
console.log("md5(file)        ", fileMd5);
console.log("md5(md5s)-count  ", perPart);
const etag = done.ETag!.replaceAll('"', "");
console.log("ETag == md5(file)?", etag === fileMd5);
console.log("ETag == computed? ", etag === perPart);

rmSync(STATE, { force: true });
await close();
process.exit(0);

بالعامية

الـ multipart بيقسم الـ object لـ parts مترقمة، كل واحد على الأقل 5 MiB (الأخير بس ممكن يبقى أصغر)، وبيترفعوا لوحدهم وبالتوازي. شبكة بايظة بتكلفك part واحد مش الملف كله، والسرعة بتزيد مع الـ concurrency. 3 calls: CreateMultipartUpload بيرجّع upload id، وUploadPart بيرجّع ETag لكل part، وCompleteMultipartUpload بيجمّعهم بترتيب الأرقام.

الـ resume محتاج state. احفظ الـ ETag بتاع كل part أول ما ينجح، في ملف أو صف في الداتابيز أو browser storage. لو الـ process وقع، ابعت الناقص بس. على S3 الحقيقي ListParts يقدر يرجّعلك الـ state ده، بس الـ stand-in بتاعنا مش عامله، فالمثال بيحفظ ملف JSON. ولو بترفع stream من السيرفر، Upload من @aws-sdk/lib-storage بيعمل التقسيم والـ concurrency لوحده (مشغلناهوش هنا)، بس مش بيعمل resume لو الـ process اتقفل.

الـ ETag بتاع الـ multipart مش الـ MD5 بتاع الملف. الـ docs بتقول كده، والشكل المعروف إنه MD5 لسلسلة الـ MD5 بتاعة الـ parts وبعدها -N، وده ملاحظة الناس مش contract مضمون. الـ stand-in عندنا رجّع MD5 الملف عادي وده غلط منه، فالسكريبت بيطبع القيمة اللي AWS كان هيطلّعها جنبها. لو عايز تتأكد إن الملف وصل سليم، ابعت checksum (x-amz-checksum-sha256) وقارنه، ومتحللش الـ ETag.

الـ uploads المتسابة بتتحاسب عليها للأبد. الـ parts بتاعة upload متعملوش complete ولا abort بتفضل متحاسب عليها ومبتظهرش في الـ list العادي. الحل lifecycle rule واحدة، AbortIncompleteMultipartUpload، هتشوفها في الجزء 4.

فين هستخدمه في شغلي؟ export شهري لكل فواتير عميل كبير، tar حجمه 12 GB من worker. لو الشبكة قطعت عند 90% والـ worker اتعمله restart، احفظ {uploadId, etags} في Postgres ويكمّل من الناقص بدل ما يرفع 12 GB تاني. ومن الناحية التانية، أول ما تفتح S3 في مشروع جديد حط الـ abort rule في الـ Terraform في نفس الـ PR، عشان متكتشفش بعد سنتين إنك بتدفع على داتا محدش شايفها.

Add an abort-incomplete lifecycle rule and a pending row so abandoned uploads get cleaned up.

Part 4 — Lifecycle & cost 🟡 Intermediateالجزء 4 — الـ lifecycle والتكلفة

English

Lifecycle rules move data down in temperature as it ages: hot, then cold, then archive. Each step lowers the price per GB and raises the cost and time of reading. The traps are fixed fees: a minimum storage duration, a retrieval fee per GB and a transition fee per object. S3 won't transition objects under 128 KB by default (since September 2024), and Flexible and Deep Archive add 40 KB of metadata per object.

The calculator below runs 100 TB arriving evenly over 5 years. Prices are us-east-1 and were checked in November 2026 from third-party pages only, because the AWS price tables did not come through when fetched. The per-GB retrieval rates in particular could not be confirmed from any page reached, so treat them as assumptions and verify everything on the AWS page before deciding. Retrieval is a small share of these totals, so the conclusions don't hinge on it.

Versioning protects against overwrites and deletes, and it is a classic cost surprise. Every overwrite keeps the old copy, billed as a normal object. A delete only adds a delete marker: the data stays and the bill doesn't move. Always pair versioning with a NoncurrentVersionExpiration rule.

type Cls = "STANDARD" | "IA" | "GLACIER_IR" | "GLACIER" | "DEEP";
const PRICE: Record<Cls, { gbMonth: number; retrievalGb: number; transitionPer1k: number }> = {
  STANDARD: { gbMonth: 0.023, retrievalGb: 0, transitionPer1k: 0 },
  IA: { gbMonth: 0.0125, retrievalGb: 0.01, transitionPer1k: 0.01 },
  GLACIER_IR: { gbMonth: 0.004, retrievalGb: 0.03, transitionPer1k: 0.02 },
  GLACIER: { gbMonth: 0.0036, retrievalGb: 0.01, transitionPer1k: 0.03 },
  DEEP: { gbMonth: 0.00099, retrievalGb: 0.02, transitionPer1k: 0.05 },
};
const TB = 1024; // بالـ GB
const MONTHS = 60;
const TOTAL_GB = 100 * TB;
const COHORT_GB = TOTAL_GB / MONTHS;

// الـ Standard بسعرين: أول 50 TB بسعر، وبعد كده الجزء اللي فاضل أرخص
const standardCost = (gb: number) => Math.min(gb, 50 * TB) * 0.023 + Math.max(gb - 50 * TB, 0) * 0.022;

type Plan = Array<{ cls: Cls; untilAgeMonths: number }>;
const classAt = (plan: Plan, age: number) => plan.find((p) => age < p.untilAgeMonths)!.cls;

function simulate(name: string, plan: Plan, avgObjectKb: number) {
  const objectsPerCohort = (COHORT_GB * 1024 * 1024) / avgObjectKb;
  let storage = 0, transitions = 0, retrieval = 0, overheadGb = 0;
  for (let m = 0; m < MONTHS; m++) {
    const gbByClass: Record<Cls, number> = { STANDARD: 0, IA: 0, GLACIER_IR: 0, GLACIER: 0, DEEP: 0 };
    for (let c = 0; c <= m; c++) gbByClass[classAt(plan, m - c)] += COHORT_GB;
    // الـ Glacier Flexible و Deep بيزودوا 40 KB metadata لكل object
    const archivedObjects = (gbByClass.GLACIER + gbByClass.DEEP) / COHORT_GB * objectsPerCohort;
    const extraGb = (archivedObjects * 40) / (1024 * 1024);
    overheadGb = Math.max(overheadGb, extraGb);
    storage += standardCost(gbByClass.STANDARD) + gbByClass.IA * PRICE.IA.gbMonth
      + gbByClass.GLACIER_IR * PRICE.GLACIER_IR.gbMonth + gbByClass.GLACIER * PRICE.GLACIER.gbMonth
      + gbByClass.DEEP * PRICE.DEEP.gbMonth + extraGb * PRICE.DEEP.gbMonth;
    // كل شهر cohort بيتنقل لـ class جديدة: رسوم transition لكل object
    for (let c = 0; c < m; c++) {
      const [from, to] = [classAt(plan, m - c - 1), classAt(plan, m - c)];
      if (from !== to) transitions += (objectsPerCohort / 1000) * PRICE[to].transitionPer1k;
    }
    // افتراض: كل سنة 2% من الداتا اللي عمرها أكتر من سنة بترجع للتدقيق
    if (m % 12 === 11) {
      for (let c = 0; c <= m - 12; c++) retrieval += COHORT_GB * 0.02 * PRICE[classAt(plan, m - c)].retrievalGb;
    }
  }
  const total = storage + transitions + retrieval;
  const usd = (n: number) => "$" + Math.round(n).toLocaleString("en-US").padStart(8);
  console.log(name.padEnd(30), "storage", usd(storage), "| transitions", usd(transitions), "| retrieval", usd(retrieval), "| total", usd(total), "| overhead", (overheadGb / TB).toFixed(1), "TB");
}

بالعامية

الـ lifecycle rules بتنزّل الداتا في الحرارة كل ما تكبر: hot وبعدين cold وبعدين archive. كل خطوة بتقلل السعر للـ GB وبتزوّد تكلفة ووقت القراية. والفخاخ في الرسوم الثابتة: minimum storage duration وretrieval fee لكل GB وtransition fee لكل object. الـ S3 مش بينقل objects أصغر من 128 KB بشكل افتراضي (من سبتمبر 2024)، و Flexible و Deep Archive بيزودوا 40 KB metadata على كل object.

الحاسبة فوق بتشغّل 100 TB داخلين بالتساوي على 5 سنين. الأسعار us-east-1 واتراجعت في نوفمبر 2026 من مواقع طرف تالت بس، لأن جداول أسعار AWS مطلعتش لما حاولت أجيب الصفحة. وأسعار الـ retrieval لكل GB بالذات مقدرتش أأكدها من أي صفحة، فاعتبرها افتراضات وراجع كل حاجة على صفحة AWS قبل ما تقرر. الـ retrieval جزء صغير من الإجمالي، فالاستنتاجات مش واقفة عليه.

الـ versioning بيحميك من الـ overwrite والـ delete، وبرضه مفاجأة تكلفة مشهورة. كل overwrite بيحتفظ بالنسخة القديمة ومتحاسب عليها كـ object عادي. والـ delete بيضيف delete marker بس: الداتا بتفضل والفاتورة مبتتحركش. دايمًا حط مع الـ versioning قاعدة NoncurrentVersionExpiration.

الغلطة الشائعة: تعمل lifecycle على bucket فيه ملايين الـ objects الصغيرة من غير ما تحسب رسوم الـ transition. زي ما شايف، لما متوسط الحجم بقى 200 KB الرسوم بقت أكبر من التخزين نفسه. الحل تجمّع الملفات الصغيرة في tar أو تستخدم size filter.

فين هستخدمه في شغلي؟ فواتير عمرها أكتر من سنة محدش بيفتحها إلا في مراجعة ضرايب: Deep Archive يوفر جدًا، بس لازم تقول للـ product إن القراية بتاخد ساعات، وتعمل شاشة "اطلب الفاتورة وهنبعتها لك". أما صور المنتجات اللي بتتقرا كل يوم فتفضل Standard ورا CDN، ومتنقلهاش. وأول حاجة تعملها لما تفتح فاتورة AWS: شوف الـ noncurrent versions والـ incomplete multipart.
Trade-off: Glacier Instant vs Deep Archive Instant keeps millisecond reads at about 4× the Deep Archive storage price, and costs more per GB to read. If a user-facing screen might ever need the file synchronously, Deep Archive isn't an option without a "we'll email it to you" flow. Decide by who is waiting, not only by the price per GB.

Part 5 — Retention & archival 🟡 Intermediateالجزء 5 — الـ retention والـ archival

English

Retention is a policy per data type, written down, not a TTL someone picked. Each type needs an owner, a reason and a deletion mechanism. The numbers below are illustrative: actual periods come from your legal and finance people, and tax rules differ by country.

Delete by dropping, not by DELETE. In the run below, deleting one month from a flat table took about 116 ms, generated 5.4 MB of WAL and left the table at exactly 131.2 MB even after VACUUM, because the freed space is reusable inside the table and is not returned to the OS. Dropping the equivalent partition took about 11 ms in total (detach plus drop), wrote almost no WAL and returned 21.2 MB. These numbers are at 100,000 rows: DELETE grows with the row count, while the drop stays roughly constant. That's why time-based data should be partitioned from day one (see partitioning).

Archive, verify, then delete. Export the partition with COPY, compress, upload, read it back and compare the row count before anything is dropped. Skipping the read-back means your first proof of a corrupted archive arrives when you need it.

Legal hold beats right to deletion, and both beat your cron job. A legal hold means certain records must not be deleted; a GDPR-style erasure request means certain records must be. Your deletion job has to check for holds, and PII inside immutable archives and backups needs a plan, commonly crypto-shredding: encrypt per user and delete the key. Details are in soft delete, audit and GDPR and secrets, encryption and privacy. S3 Object Lock gives a server-enforced hold (not run here).

What breaks: the job that deletes without a guard Retention jobs are the code most able to destroy data, and they run unattended. Require a verified archive, a maximum number of partitions per run, a dry-run mode, a legal-hold check and an alert when the job does nothing for too long.

Part 6 — Backups, RPO & RTO 🟡 Intermediateالجزء 6 — الـ backups والـ RPO والـ RTO

English

RPO (recovery point objective) is how much data you can lose, measured in time. RTO (recovery time objective) is how long you can be down. They come from the business, cost money to tighten, and only mean something if you've measured them. A backup you never restored isn't a backup.

Physical backup plus WAL archive gives point-in-time recovery. The base backup is a copy of the data directory and the archive holds every WAL segment since. To undo a bad DELETE, restore the base and replay WAL until just before it. Our run restored 51,000 rows after a DELETE had left 10. The RTO was about 1.5 seconds, which is meaningless at this size: it's mostly startup time on a tiny dataset.

RPO is not zero with WAL archiving. A segment is archived when it's full or switched, so writes in the open segment are lost with the primary. The run shows it: 500 rows written after the last archived segment disappeared. Set archive_timeout to bound the loss, or stream WAL continuously with pg_receivewal or a synchronous standby (not run here).

Incremental backups exist natively since Postgres 17: enable summarize_wal, take a full backup, then pg_basebackup --incremental=<manifest>, and reconstruct with pg_combinebackup. In our run the incremental was 26.6 MB against a 91.4 MB full, of which 16 MB was just the WAL segment, and the combined backup started and had every changed row. On a larger database the ratio improves, because the WAL part is fixed. Restores get more complex though: lose one link and everything after it is gone.

Extrapolating RTO. The tiny run can't be scaled directly, so use throughput: time to download and lay down the base, plus time to replay the WAL. A 5 TB base plus 200 GB of WAL comes to roughly 3.5 to 18 hours under the assumptions printed below. That is the number to bring to the business. Strategy across regions is in redundancy, failover and disaster recovery; the operational details are in backups, PITR and upgrades.

                 base backup
   time ---------[B]---------------[target]--[bad DELETE]---[crash]--->
                  |                    ^           ^           ^
   WAL archive:   |== seg ==|== seg ==|== seg ==|== seg ==|. open .|
                                                           ^^^^^^^^
                                       never archived: this is your RPO
   restore  = copy [B], then replay WAL up to [target]
   RTO      = copy time + replay time + checks

async function restore(name: string, target?: string) {
  const dir = path.join(cluster.root, name);
  const recovery = target ? `recovery_target_time='${target}'\nrecovery_target_action='promote'\n` : "";
  appendFileSync(path.join(dir, "postgresql.auto.conf"),
    `\nrestore_command='copy "..\\\\wal\\\\%f" "%p"'\n${recovery}archive_mode=off\n`);
  writeFileSync(path.join(dir, "recovery.signal"), "");
  cluster.nodes.push(name);
  const start = performance.now();
  startNode(cluster, name);
  const r = await connect(cluster.port);
  for (let i = 0; i < 80; i++) {
    if (!(await r.query(`select pg_is_in_recovery() x`)).rows[0].x) break;

  await r.end();
  stopNode(cluster, name);
  return { rows: n, rto };
}

بالعامية

الـ RPO هو قد إيه داتا ممكن تخسرها، بالوقت. الـ RTO هو قد إيه ممكن تفضل واقف. الاتنين بييجوا من الـ business، وتضييقهم بيكلّف فلوس، وملهمش معنى لو مقستهمش. الـ backup اللي عمرك ما عملت منه restore مش backup.

الـ physical backup مع WAL archive بيدّوك point-in-time recovery. الـ base backup نسخة من الـ data directory والأرشيف فيه كل WAL segment بعدها. عشان تلغي DELETE غلط، ترجّع الـ base وتعيد الـ WAL لحد قبله بالظبط. في التشغيل رجّعنا 51,000 صف بعد ما الـ DELETE ساب 10 بس. الـ RTO كان حوالي 1.5 ثانية، وده ملوش معنى عند الحجم ده: معظمه وقت startup على داتا صغيرة.

الـ RPO مش صفر مع الـ WAL archiving. الـ segment بيتأرشف لما يتملي أو يتعمله switch، فالكتابات اللي في الـ segment المفتوح بتروح مع الـ primary. التشغيل بيوريك ده: 500 صف اتكتبوا بعد آخر segment اتأرشف واختفوا. استخدم archive_timeout عشان تحدد الخسارة، أو ابعت الـ WAL باستمرار بـ pg_receivewal أو synchronous standby (مشغلناهمش هنا).

الـ incremental backups موجودة natively من Postgres 17: شغّل summarize_wal، خد full backup، وبعدين pg_basebackup --incremental=<manifest>، ورجّعها بـ pg_combinebackup. في التشغيل عندنا الـ incremental كان 26.6 MB مقابل full 91.4 MB، ومنهم 16 MB مجرد WAL segment، والـ combined اشتغل وفيه كل الصفوف المتعدلة. على داتابيز أكبر النسبة بتتحسن لأن جزء الـ WAL ثابت. بس الـ restore بيبقى أعقد: لو حلقة واحدة ضاعت، كل اللي بعدها راح.

تقدير الـ RTO. التشغيل الصغير ميتكبرش مباشرة، فاستخدم الـ throughput: وقت تحميل ووضع الـ base زائد وقت إعادة الـ WAL. 5 TB base مع 200 GB WAL بتطلع تقريبًا من 3.5 لـ 18 ساعة بالافتراضات المطبوعة فوق. ده الرقم اللي تروح بيه للـ business. الاستراتيجية بين الـ regions في درس الـ redundancy والـ failover والـ DR، والتفاصيل التشغيلية في درس الـ backups والـ PITR والـ upgrades.

الغلطة الشائعة: recovery_target_time بقيمة من toISOString(). لما جربناها، ALTER SYSTEM SET قبلها، بس لما الـ server قام من الـ config رفضها بـ invalid value والـ restore مكملش. استخدم القيمة من now()::text بتاع Postgres نفسه.

فين هستخدمه في شغلي؟ لما الـ CTO يسأل "لو الـ primary راح دلوقتي بنخسر قد إيه وبنرجع إمتى؟" الإجابة تبقى: "RPO 60 ثانية بسبب archive_timeout، RTO متقاس آخر مرة من 3 أسابيع 4 ساعات و20 دقيقة على داتا الـ production". وحط job شهري يعمل restore على instance مؤقتة، يعد الصفوف، ويبعت الرقم على Slack. لو الـ job ده فشل يبقى عندك incident حتى لو مفيش حاجة واقعة.

Walk me through recovery." → A replica won't help, since the mistake replicated too, unless you keep a delayed standby. await s3.send(new PutObjectCommand({ Bucket, Key, Body: counted, ContentLength }));

// حل التمرين: أصغر part size يخلّي الملف يدخل في 10,000 part
const MiB = 2 ** 20;
const MIN_PART = 5 * MiB;
const MAX_PART = 5 * 1024 * MiB;
const MAX_PARTS = 10_000;

export function partSizeFor(fileBytes: number): { partSize: number; parts: number } {
  if (fileBytes <= 0) throw new Error("empty file");
  // الحد الأدنى اللي يكفي عشان عدد الـ parts ميعديش 10,000
  const needed = Math.ceil(fileBytes / MAX_PARTS);
  const partSize = Math.max(MIN_PART, Math.ceil(needed / MiB) * MiB);
  if (partSize > MAX_PART) throw new Error("object too large for S3");
  return { partSize, parts: Math.ceil(fileBytes / partSize) };
}

Solution · الحل 
// حل التمرين: خطة الـ retention بتطلّع اللي يتأرشف من غير ما تمسح حاجة بنفسها
export function retentionPlan(partitions: string[], keepMonths: number, today: Date): string[] {
  const y = today.getUTCFullYear();
  const m = today.getUTCMonth() + 1;
  const toIndex = (year: number, month: number) => year * 12 + (month - 1);
  const cutoff = toIndex(y, m) - keepMonths;
  return partitions
    .map((name) => {
      const match = /_(\d{4})_(\d{2})$/.exec(name);
      if (!match) throw new Error(`bad partition name: ${name}`);
      return { name, idx: toIndex(Number(match[1]), Number(match[2])) };
    })
    .filter((p) => p.idx < cutoff)
    .sort((a, b) => a.idx - b.idx)
    .map((p) => p.name);
}

Cheat sheet · الخلاصة

  • S3 = flat keys, immutable objects, no partial update; Range reads only. Strong read-after-write since Dec 2020, but no transactions.
  • Concurrent writers: If-None-Match: * or If-Match; the first finisher wins, others get 412.
  • Limits: 48.8 TiB, 10,000 parts, 5 MiB to 5 GiB per part. Pick part size from file size.
  • Uploads: pending row → presign → client PUT → HeadObject → confirm. Never trust the client's claim, and treat the URL as a bearer token.
  • Multipart: save part ETags, retry only failed parts, and add AbortIncompleteMultipartUpload on day one. The multipart ETag is not the file MD5.
  • Lifecycle saves about 80% at 100 TB, and per-object fees can erase it for small objects. Aggregate them or filter by size.
  • Versioning needs NoncurrentVersionExpiration; a delete marker frees nothing.
  • Retention is a written policy per data type. Drop partitions rather than DELETE, and archive and verify first.
  • RPO is measured data loss, RTO is measured downtime. WAL archiving leaves the open segment at risk.
  • Use now()::text for recovery_target_time, restore on a schedule, and estimate RTO by throughput.
بالعامية
  • الـ S3 مفاتيح مسطّحة و objects immutable ومفيش partial update، والقراية الجزئية بـ Range بس. الـ read-after-write strong من ديسمبر 2020، بس مفيش transactions.
  • لو في كذا حد بيكتب مع بعض: If-None-Match: * أو If-Match، وأول واحد يخلص يكسب والباقي ياخدوا 412.
  • الحدود: 48.8 TiB و10,000 part وكل part من 5 MiB لـ 5 GiB. احسب حجم الـ part من حجم الملف.
  • الـ uploads: صف pending ثم presign ثم PUT من الـ client ثم HeadObject ثم تأكيد. متصدقش كلام الـ client، وتعامل مع الـ URL كـ bearer token.
  • الـ multipart: احفظ الـ ETags بتاعة الـ parts، وأعد الفاشل بس، وحط AbortIncompleteMultipartUpload من أول يوم. والـ ETag بتاع الـ multipart مش MD5 الملف.
  • الـ lifecycle بيوفر حوالي 80% عند 100 TB، ورسوم كل object ممكن تضيّع ده مع الملفات الصغيرة. جمّعها أو فلتر بالحجم.
  • الـ versioning لازم معاه NoncurrentVersionExpiration، والـ delete marker مش بيوفّر حاجة.
  • الـ retention سياسة مكتوبة لكل نوع داتا. اعمل drop للـ partitions بدل DELETE، وأرشف واتأكد الأول.
  • الـ RPO هو الداتا اللي ممكن تضيع متقاسة، والـ RTO هو وقت التوقف متقاس. الـ WAL archiving بيسيب الـ segment المفتوح في خطر.
  • استخدم now()::text لـ recovery_target_time، واعمل restore بجدول ثابت، وقدّر الـ RTO بالـ throughput.
