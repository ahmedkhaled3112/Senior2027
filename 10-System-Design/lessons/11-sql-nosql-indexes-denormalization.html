Why this matters · ليه ده مهم

English

"Which database?" is usually the first question in a design discussion and usually asked too early. The answer is a consequence of something you can write down: the exact queries the product runs, how often, and which of them need transactions. Interviewers listen for that order. So do production incidents: most data-layer pain comes from a missing index, a wrong column order, or a denormalized copy nobody owns, and very little of it from the brand of the store.

This lesson runs the same order system on real Postgres and real MongoDB, tests a decision framework with unit tests, then measures what each index and each copied column costs on one million rows.

بالعامية

سؤال "نستخدم أنهي database؟" بييجي غالبًا أول حاجة في الـ design، وبييجي بدري قوي. الإجابة نتيجة لحاجة تقدر تكتبها: الـ queries اللي الـ product بيعملها بالظبط، بتتكرر قد إيه، وأنهي منها محتاج transaction. الـ interviewer بيسمع الترتيب ده بالذات. والـ incidents كمان: معظم وجع الـ data layer جاي من index ناقص، أو ترتيب أعمدة غلط، أو نسخة denormalized محدش مسؤول عنها، وقليل جدًا منه جاي من اسم الـ store.

الدرس ده بيشغّل نفس نظام الـ orders على Postgres و MongoDB حقيقيين، بيختبر decision framework بـ unit tests، وبعدين بيقيس كل index وكل عمود متنسخ بيتكلف قد إيه على مليون صف.

Part 1 — Access patterns first 🟢 Basicالجزء 1 — الـ access patterns الأول

English

An access pattern is one concrete question the application asks of its data: the filter, the sort, the columns it needs, how often it runs and how fast it must be. Write the list before naming a store. For an orders system there are four obvious ones: fetch one order with its lines by id, a user's latest 20 orders, a tenant's orders in a date range, and monthly revenue per tenant. A fifth is the one that catches people out: revenue per SKU, which cuts across every order's lines.

The two natural shapes are a relational pair of tables (orders and order_lines, joined at read time) and a document with the lines embedded inside the order. The script below loads the same 200,000 orders and 600,000 lines into both, adds one index per pattern on each side, and runs each pattern in the way that is natural for that store.

Three things are visible in the output. First, the point reads and lists are under a millisecond on both sides and even the aggregates are single-digit milliseconds, because every pattern has an index built for it; that is the index doing the work, not the store. Second, the shapes differ: the embedded read touched exactly one key and one document, while the join walked two indexes and 13 buffers. On a cold cache that shape is the difference between one random read and several. Third, the embedded model still answers the cross-cutting SKU question, but only by unwinding every array; a pattern like "which orders contain SKU-42" or "fix a typo in a product name inside old orders" now means touching many documents. Modelling details are in section 07 · NoSQL map & MongoDB modeling.

The conclusion is not that one store won. It is that the pattern list decides. Embedded lines fit when an order is nearly always read and written as a whole and no invariant spans orders. Separate tables fit when you also need ad-hoc reporting and invariants across rows, such as stock or balances.

export function labPort(name = "LAB_PG_PORT"): number {
  const raw = process.env[name] ?? "";
  const n = Number(raw);
  if (!/^\d+$/.test(raw) || n < 1024 || n > 65535 || [5432, 27017, 6379].includes(n)) {
    throw new Error(`refusing port '${raw}'`);
  }
  return n;
}

// الـ median أثبت من الـ average على جهاز عليه حمل تاني
export function median(xs: number[]): number {
  const s = [...xs].sort((a, b) => a - b);
  return s[Math.floor(s.length / 2)];
}

export async function medianMs(runs: number, fn: (i: number) => Promise<unknown>): Promise<number> {
  const xs: number[] = [];
  for (let i = 0; i < runs; i++) {
    const t0 = performance.now();
    await fn(i);
    xs.push(performance.now() - t0);
  }
  return +median(xs).toFixed(2);
}

// مولّد أرقام بـ ⁦seed (mulberry32)⁩ عشان نفس الـ ids تتكرر في كل run
export function prng(seed: number): () => number {
  let a = seed;
  return () => {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

بالعامية

الـ access pattern هو سؤال واحد محدد الـ app بيسأله للـ data: الـ filter، الـ sort، الأعمدة اللي محتاجها، بيتكرر قد إيه، ولازم يخلص في قد إيه. اكتب القايمة دي قبل ما تسمّي أي store. في نظام orders عندك 4 واضحين: هات order بالـ id ومعاه الـ lines، آخر 20 order لـ user، orders بتاعة tenant في مدة معينة، والإيراد الشهري لكل tenant. والخامس هو اللي بيوقّع الناس: الإيراد لكل SKU، وده بيقطع في الـ lines بتاعة كل order.

الشكلين الطبيعيين هما جدولين relational (orders و order_lines وتعمل join وقت القراية)، أو document والـ lines جواه. السكريبت فوق بيحط نفس الـ 200 ألف order و600 ألف line في الاتنين، ويعمل index لكل pattern في كل ناحية، ويشغّل كل pattern بالطريقة الطبيعية للـ store بتاعه.

الـ output بيوريك 3 حاجات. الأولى: القراية بالـ id واللستات أقل من ملي ثانية في الناحيتين، وحتى الـ aggregates كام ملي ثانية بس، لأن كل pattern ليه index معمول عشانه، يعني الـ index هو اللي بيشتغل مش اسم الـ store. التانية: الشكل مختلف: القراية الـ embedded لمست key واحد و document واحد، والـ join مشي على indexين و13 buffer، ولو الـ cache بارد الفرق ده هو الفرق بين random read واحدة وكذا واحدة. التالتة: الموديل الـ embedded لسه بيجاوب سؤال الـ SKU بس لازم يفك كل array، وأي pattern زي "أنهي orders فيها SKU-42" أو "صلّح اسم منتج غلط جوه orders قديمة" بقى معناه تلمس documents كتير. تفاصيل الـ modelling في قسم 07: الـ NoSQL و MongoDB modeling.

الخلاصة مش إن store كسب. الخلاصة إن قايمة الـ patterns هي اللي بتقرر. الـ lines جوه الـ document تنفع لما الـ order بيتقرا ويتكتب ككتلة واحدة تقريبًا دايمًا ومفيش invariant بين orders وبعض. الجداول المنفصلة تنفع لما كمان محتاج reporting متغير و invariants عبر صفوف، زي المخزون أو الأرصدة.

فين هستخدمه في شغلي؟ قبل ما تكتب أي ADR فيه "هنستخدم Mongo" أو "هنستخدم Postgres"، حط في أول الـ design doc جدول فيه: الـ pattern، الـ filter والـ sort، الـ rate المتوقع، الـ p99، ومحتاج transaction ولا لأ. في code review لو حد ضاف feature بـ query جديدة شكلها مختلف، ارجع للجدول وشوف: هل الـ store والـ indexes لسه بيخدموها؟ الغلطة الشائعة: تختار الـ store الأول وبعدين تكتشف إن الـ reporting محتاج $unwind على كل حاجة.
Interview question "Why not just use MongoDB for orders, since an order is naturally a document?" → Because the document shape only helps the patterns that read one order whole. Orders also need invariants across rows (stock, payments) and reporting across lines. I would write the access patterns first: if ad-hoc analytics and multi-row transactions are on the list, relational is the default and JSONB covers the flexible part. If the list is really "get order by id" and "list orders by user", embedded lines are a good fit.
"ليه ما نستخدمش MongoDB للـ orders طالما الـ order بطبيعته document؟" ← لأن شكل الـ document بيفيد بس الـ patterns اللي بتقرا order كامل. الـ orders كمان محتاجة invariants عبر صفوف (مخزون، مدفوعات) و reporting عبر الـ lines. أكتب الـ access patterns الأول: لو الـ analytics المتغير والـ multi-row transactions في القايمة، يبقى relational هو الاختيار الأساسي و JSONB بيغطي الجزء المرن. ولو القايمة فعلًا "هات order بالـ id" و"لستة orders لـ user"، الـ lines جوه الـ document مناسبة.

Part 2 — A decision framework you can test 🟡 Intermediateالجزء 2 — decision framework تقدر تختبره

English

The framework is a fixed order of questions: access patterns → consistency needs → read or write heavy → schema flexibility → team. The order matters. A multi-row invariant ends the discussion at step 2 no matter how the writes scale. Scale comes third and acts mostly as a tie-breaker. Team familiarity comes last, but it can legitimately flip a tie, because someone has to operate the thing at 3 a.m.

"NoSQL for scale" is a myth at most sizes. To put a number on it, the second script measures durable writes per second on one real Postgres (fsync=on, synchronous_commit=on) and compares them with SaaS estimates built the way lesson 02 taught. About 33,000 durable single-row commits per second beat the flash-sale estimate of about 1,157 writes per second by roughly 28× here. Watch the batching line too: batching 100 rows per commit moved roughly 281,000 rows per second, because one fsync now covers 100 rows.

The caveats are real and belong in the design doc. This is a local SSD and a table with one small index, not a cloud network volume, and Windows uses wal_sync_method=open_datasync. Group commit is why 32 connections beat 1 connection seven times over: many transactions share one WAL flush. Long before raw write throughput, a single node usually hits data volume, autovacuum on huge tables, or connection counts.

JSONB is the middle ground when part of your data has no fixed shape. A catalog where shirts have a size and phones have RAM fits one table with a jsonb column and a GIN index. You keep transactions, joins and one backup story. The price is that JSONB has no per-key statistics, so the planner guesses selectivity for @> and a bad guess gives a bad plan, and keys are not typed or constrained unless you add checks.

// الـ framework: access patterns ← consistency ← read/write heavy ← schema ← team
export type Pattern =
  | "lookup-by-key"          // هات قيمة بالـ key بس
  | "relational"             // فيه joins و reporting و filters متغيرة
  | "partition-time-range"   // كل القراية جوه partition واحد مترتب بالوقت
  | "attribute-filter"       // فلترة على attributes بتختلف من صف لصف
  | "aggregate-over-time";   // تجميع sum/count على ملايين الصفوف

export interface Workload {
  name: string;
  pattern: Pattern;
  // فيه invariant لازم يتحقق عبر أكتر من صف في نفس الـ transaction؟
  multiRowInvariant: boolean;
  writesPerSecPeak: number;
  dataTb: number;
  schemaVaries: boolean;
  teamKnowsPostgres: boolean;
}

export interface Decision { store: string; because: string }

// الحد ده افتراض تكتبه وتراجعه: قيس على hardware بتاعك، متنسخهوش
const SINGLE_NODE_WRITES_PER_SEC = 20_000;
const SINGLE_NODE_DATA_TB = 10;

export function decide(w: Workload): Decision {
  // (1) الـ consistency الأول: أي invariant عبر صفوف بيقفل النقاش
  if (w.multiRowInvariant) {
    return { store: "relational (Postgres)", because: "multi-row invariant needs ACID transactions" };
  }
  const outgrowsOneNode = w.writesPerSecPeak > SINGLE_NODE_WRITES_PER_SEC || w.dataTb > SINGLE_NODE_DATA_TB;

  // (2) الـ pattern بيختار، والـ scale بيكسر التعادل بس
  switch (w.pattern) {
    case "lookup-by-key":
      return { store: "key-value (Redis / DynamoDB)", because: "only ever read by key, no query shape to serve" };
    case "partition-time-range":
      return outgrowsOneNode
        ? { store: "wide-column (Cassandra / ScyllaDB)", because: "partitioned, append-mostly, exceeds one node" }
        : { store: "relational (Postgres, time-partitioned)", because: "same pattern fits one node; no second system to operate" };
    case "aggregate-over-time":
      return { store: "columnar / time-series (ClickHouse / TimescaleDB)", because: "scans few columns over many rows" };
    case "attribute-filter":
      return w.teamKnowsPostgres
        ? { store: "JSONB on Postgres", because: "flexible attributes, team and backups already exist" }
        : { store: "document (MongoDB)", because: "flexible attributes and no relational base to reuse" };
    case "relational":
      return { store: "relational (Postgres)", because: "ad-hoc joins and reporting" };
  }
}

الـ framework ترتيب ثابت للأسئلة: access patterns ← consistency ← read أو write heavy ← schema flexibility ← team. والترتيب مهم. أي invariant عبر أكتر من صف بيقفل النقاش عند الخطوة التانية، مهما كان حجم الكتابة. الـ scale بييجي تالت وغالبًا بيكسر التعادل بس. الـ team آخر حاجة، بس ممكن تقلب تعادل بجد، لأن حد لازم يشغّل الحاجة دي الساعة 3 الفجر.

فكرة "NoSQL عشان الـ scale" خرافة في معظم الأحجام. عشان نحط رقم: السكريبت التاني بيقيس الكتابة الـ durable في الثانية على Postgres واحد حقيقي (fsync=on و synchronous_commit=on)، وبيقارنها بـ estimates لـ SaaS بنفس طريقة الدرس 02. حوالي 33 ألف commit durable في الثانية عدّت estimate الـ flash sale (حوالي 1,157 write في الثانية) بحوالي 28 مرة هنا. وبص كمان على سطر الـ batching: 100 صف في الـ commit الواحد حرّك حوالي 281 ألف صف في الثانية، لأن fsync واحد بقى بيغطي 100 صف.

الـ caveats حقيقية ولازم تتكتب في الـ design doc. ده SSD محلي وجدول فيه index صغير واحد، مش cloud network volume، و Windows بيستخدم wal_sync_method=open_datasync. الـ group commit هو السبب إن 32 connection أسرع 7 مرات من connection واحدة: transactions كتير بتشارك في WAL flush واحد. وقبل ما توصل لحد الكتابة الخام، الـ node الواحدة غالبًا بتخبط في حجم الـ data، أو autovacuum على جداول ضخمة، أو عدد الـ connections.

الـ JSONB هو الحل الوسط لما جزء من الـ data ملوش شكل ثابت. كتالوج القمصان فيه size والموبايلات فيها RAM يتحط في جدول واحد بعمود jsonb و GIN index، وتفضل عندك transactions و joins وخطة backup واحدة. التمن: الـ JSONB معندوش statistics لكل key، فالـ planner بيخمن الـ selectivity بتاعة @> والتخمين الغلط بيطلّع plan وحش، والـ keys مش typed ولا عليها constraints إلا لو ضفت checks بإيدك.

فين هستخدمه في شغلي؟ لما حد في الفريق يقول "المنتج هيكبر، نستخدم Cassandra من دلوقتي"، ادخل بالأرقام: DAU × writes في اليوم ÷ 86400 × peak factor، وقارنها بـ pgbench على نفس الـ instance type بتاعك. لو الـ peak 400 write/s، الـ Postgres معاه هامش ضخم، والـ Cassandra معناها cluster تشغّله وتراقبه وتتعلمه من الصفر. والـ attrs jsonb هو الإجابة المعتادة لـ "كل tenant عايز custom fields". الغلطة الشائعة: تعتمد على رقم قستُه على laptop كأنه رقم الـ production.
Trade-off: where the framework can be wrong The threshold constants in decide() (20,000 writes/s, 10 TB) are assumptions, not facts. Replace them with what you measured on your own instance type. A framework that hides its thresholds is an opinion. A framework that states them can be tested and overruled.

Part 3 — Queries decide indexes 🟢 Basicالجزء 3 — الـ queries هي اللي بتحدد الـ indexes

English

You derive indexes from the pattern list in the same order you wrote it. The rule for a composite index: columns compared with equality go first, then the column you sort or range over. "A user's latest 20" is an equality on customer_id and a sort on created_at, so the index is (customer_id, created_at DESC). B-tree mechanics are in section 01, Database Theory part 8 and section 07 · composite and partial indexes; here the question is what the design buys.

The experiment runs the same query on one million orders in three states. With no helpful index, Postgres parallel-scans the table and touches 9,422 buffers. With the columns in the wrong order, the index is sorted by date and the customer's rows are scattered across it, so it walks 1,833 buffers to find 20 rows. With equality first it needs 23 buffers. Postgres 18 added B-tree skip scan, which can use a later column when the leading column has few distinct values; created_at has millions, so Index Searches: 1 shows no skipping happened.

Indexes are not free. Every index is a second structure each insert must update, in the same transaction and the same WAL. On a table that had already been warmed to 200,000 rows, adding two secondary indexes cut batched inserts from about 420,000 to about 160,000 rows per second, and six indexes cut them to about 50,000, so 8.4× slower, with the indexes taking 85 MB against a 26 MB table. Single-row commits are dominated by the fsync, so expect a smaller ratio there. The cost is highest on random keys, because each insert lands on a different leaf page.

Part 4 — Indexes at scale 🟡 Intermediateالجزء 4 — الـ indexes على scale

English

Indexes cost memory because the pages they use must sit in RAM to be fast. Measure one million rows and multiply. The primary key here is 21.4 MB per million rows and each composite index is 30.1 MB, so at 100 million rows three indexes need about 7.9 GB. A freshly built index is the best case: an index grown by random inserts sits near 65% leaf density instead of about 90%, about 1.4× larger; the numbers are in Unique IDs. On a 16 GB instance with shared_buffers around a quarter of RAM, those indexes no longer fit, and the question becomes which part of each index is hot. A time-ordered index keeps only its recent right-hand edge hot. A random-key index keeps every page hot.

Partial indexes are the first tool. A job queue only ever reads the 1% of rows with status = 'pending'. A full index on (status, created_at) is 38.7 MB, and the partial one is 0.2 MB for practically the same buffers (53 vs 52) and the same latency. Nothing got faster; the gain is memory, plus 99% of writes not touching that index at all.

Covering indexes with INCLUDE avoid the table entirely. Adding status and total_cents grew the index from 30.1 to 47.3 MB and took the query from 22 buffers to 4 with an index-only scan. Latency on this fully cached run is within noise, so count pages, not milliseconds. The fine print is the visibility map: after an update there were 39 heap fetches, because Postgres has to check those pages. After VACUUM there were 0 in the final run, though one earlier run still showed 10. So a covering index depends on vacuum keeping up.

Put tenant_id first in a multi-tenant table: every query is scoped to one tenant, and each tenant's rows stay adjacent. On a 30-day range the two column orders were close (773 vs 930 buffers). On 365 days, (tenant_id, created_at) needed 6,055 buffers and about 4.7 ms, while (created_at, tenant_id) made the planner give up and scan the whole table for 9,365 buffers and about 33 ms. Building any of these on a live table must use CREATE INDEX CONCURRENTLY, since a plain CREATE INDEX blocks writes; see section 07 · safe migrations.

Part 5 — Denormalization on purpose 🟡 Intermediateالجزء 5 — الـ denormalization المقصودة

English

Denormalization means storing a value somewhere else so a read does not have to compute or join it. It trades a cheaper read for a more expensive write and a new way to be wrong. "On purpose" means you can name the read it speeds up, the write that pays for it, and the job that repairs it. Modelling options are in section 07 · denormalization & read models; this part measures the trade.

The first result is the one people skip. Showing the latest 20 orders with the customer name by join takes about 0.42 ms, against about 0.11 ms with a copied column. That saves a third of a millisecond, on a read that is about to spend more than that on the network. A 20-row join on a primary key is not a reason to denormalize. The copy earns its place when the filter and sort live on different tables, so no single index can serve both: sorting by customer name went from about 6.96 ms to about 0.17 ms, roughly 40×. A counter cache is similar: count(*) on the whale customer's 50,000 orders takes about 2.3 ms, and reading orders_count about 0.07 ms.

Writes pay. Updating a counter in the same transaction cost about 26% of throughput with the load spread across customers. When all eight connections hit one customer, the row becomes a queue, and throughput falls 74%, from about 18,600 to about 4,800 transactions per second. Hot counters are a write-contention problem first and a read optimization second.

Then the anomaly, reproduced. Rename the customer and 50,000 copies now disagree with the source. A batched repair job fixed them in about 1.6 seconds and wrote about 26 MB of WAL. Where should the update live? A trigger is synchronous and can't be forgotten, but the rename now pays for every copy: about 2 ms for a small customer, about 433 ms holding 50,000 row locks for the whale. An application write is visible in code, and every code path must remember it. An outbox event (section 07 · outbox) decouples the slow fan-out from the rename, at the cost of a window where old and new names coexist.

الـ denormalization إنك تخزن قيمة في مكان تاني عشان القراية متحسبهاش أو تعمل join. بتبدّل قراية أرخص بكتابة أغلى وطريقة جديدة للغلط. أول نتيجة هي اللي الناس بتعدّيها. عرض آخر 20 order مع اسم الـ customer بالـ join بياخد حوالي 0.42 ms، وبالعمود المنسوخ حوالي 0.11 ms. يعني وفرت تلت ملي ثانية على قراية هتصرف أكتر من كده على الشبكة. الـ join بتاع 20 صف على primary key مش سبب للـ denormalization. النسخة بتستاهل لما الـ filter والـ sort يبقوا على جدولين مختلفين، فمفيش index واحد يخدم الاتنين: الـ sort باسم الـ customer نزل من حوالي 6.96 ms لحوالي 0.17 ms، حوالي 40 مرة. والـ counter cache نفس الفكرة: count(*) على الـ 50 ألف order بتاعة الـ whale بياخد حوالي 2.3 ms، وقراية orders_count حوالي 0.07 ms.

الكتابة هي اللي بتدفع. تحديث العداد في نفس الـ transaction كلّف حوالي 26% من الـ throughput لما الـ load متوزع على customers كتير. ولما الـ 8 connections يضربوا customer واحد، الصف بيبقى طابور، والـ throughput بيقع 74%، من حوالي 18,600 لحوالي 4,800 transaction في الثانية. الـ counters الـ hot هي مشكلة write contention الأول وتحسين قراية بعد كده.

Part 6 — Materialized views 🟡 Intermediateالجزء 6 — الـ materialized views

English

A materialized view stores a query's result as a table and leaves it stale until you refresh it. It is denormalization with the repair job built in, as long as you can accept the staleness. A live aggregate across all tenants took about 253 ms on one million orders. The view holds 1,250 rows in 136 kB and answers one tenant in about 0.15 ms. The reference is section 07 · read models.

Refreshing has a catch you should see once. Plain REFRESH MATERIALIZED VIEW takes an ACCESS EXCLUSIVE lock, so every reader waits. With a reader looping throughout, only 5 reads finished during a ≈250 ms refresh and the worst read waited ≈249 ms, the whole refresh. REFRESH ... CONCURRENTLY took a little longer (≈279 ms) and the reader finished 1,351 queries with a worst case of ≈2 ms. It needs a unique index on the view; without one you get the real error below. CONCURRENTLY works by diffing the new result against the old rows, so it is the wrong choice when most rows change on each refresh.

The staleness budget is a product decision with a price tag: how old may the number be, and what does one refresh cost? At ≈264 ms per refresh, a one-minute budget uses about 0.44% of one core and a 15-minute budget about 0.03%. That is cheap at this size. On a billion rows the refresh takes tens of minutes and overlaps itself, which is when you need something incremental.

The alternative is a summary table updated per event. Each order inserts into orders and upserts one row into revenue_summary in the same transaction, so the number is never stale and reads take about 0.1 ms. Writes pay as usual: ≈13,700 tx/s drops to ≈10,600 with tenants spread and to ≈2,950 when one tenant takes everything. And a code path that forgets the upsert causes drift. In this run, the "insert only" path caused exactly that in 8 tenants' rows, and a reconcile job recomputed from the source of truth and fixed them.

CONCURRENTLY خد شوية أكتر (≈279 ms) والـ reader خلّص 1,351 query وأسوأها ≈2 ms. بس محتاج unique index على الـ view، ومن غيره بييجيلك الخطأ الحقيقي اللي فوق. والـ CONCURRENTLY شغله إنه يقارن النتيجة الجديدة بالصفوف القديمة، فمش اختيار كويس لو معظم الصفوف بتتغير في كل refresh.

الـ staleness budget قرار product وليه تمن: الرقم ينفع يبقى قديم قد إيه، و refresh واحد بيتكلف كام؟ عند ≈264 ms للـ refresh، ميزانية دقيقة واحدة بتاخد حوالي 0.44% من core واحدة، و15 دقيقة حوالي 0.03%. رخيص عند الحجم ده. على مليار صف الـ refresh بياخد عشرات الدقايق وبيتداخل مع نفسه، وساعتها محتاج حاجة incremental.

البديل summary table بتتحدث مع كل event. كل order بيعمل insert في orders و upsert لصف واحد في revenue_summary في نفس الـ transaction، فالرقم عمره ما يبقى قديم والقراية حوالي 0.1 ms. والكتابة بتدفع زي العادة: ≈13,700 tx/s بتنزل لـ ≈10,600 والـ tenants متوزعين، ولـ ≈2,950 لما tenant واحد ياخد كله. وأي code path ينسى الـ upsert بيعمل drift. في الـ run ده، مسار الـ "insert only" عمل كده بالظبط في صفوف 8 tenants، و reconcile job حسب من مصدر الحقيقة وصلّحهم.

فين هستخدمه في شغلي؟ dashboard الإيراد الشهري لكل tenant في SaaS: REFRESH ... CONCURRENTLY كل 5 دقايق من worker، وعليه alert لو الـ refresh فشل أو بقى أطول من الـ period. ولو الـ finance عايز الرقم لحظي، يبقى summary table بـ upsert، مع reconcile job ليلي بيقارنها بالـ orders ويصلّح الفرق. الغلطة الشائعة: REFRESH من غير CONCURRENTLY على جدول بيقرا منه dashboard شغال، فكل request بيقف طول الـ refresh، زي ما قسنا.
Trade-off: view vs summary table Materialized view: no changes to write paths, stale by your budget, cost grows with the whole dataset per refresh. Summary table: always current, every write path must maintain it, and one hot tenant's row costs real throughput (≈-78% in this run, 13,700 → 2,950 tx/s). Start with the view. Move to a summary table when a refresh no longer fits inside the budget or the number has to be current.
الـ trade-off بين الـ view والـ summary table: الـ materialized view مش بتغيّر مسارات الكتابة، قديمة بقد الـ budget بتاعك، وتمنها بيكبر مع حجم الـ data كله في كل refresh. الـ summary table دايمًا محدّثة، بس كل مسار كتابة لازم يحدّثها، وصف الـ tenant الـ hot بيكلّف throughput حقيقي (حوالي -78% في الـ run ده، من 13,700 لـ 2,950 tx/s). ابدأ بالـ view، وانقل لـ summary table لما الـ refresh ميدخلش في الـ budget أو الرقم لازم يبقى لحظي.
Interview question "How do you serve a dashboard of monthly revenue per tenant over a billion orders?" → Not a live aggregate. For staleness of minutes, a materialized view or a rollup table refreshed by a job, with CONCURRENTLY so readers don't block. At this size a full recompute won't fit the window, so incremental: upsert into a summary keyed by tenant and month, or a stream rollup, with a periodic reconcile against the source of truth to catch drift.
"إزاي تخدم dashboard للإيراد الشهري لكل tenant على مليار order؟" ← مش aggregate live. لو الـ staleness بالدقايق ينفع، materialized view أو rollup table بيتحدث بـ job، مع CONCURRENTLY عشان الـ readers ميقفوش. عند الحجم ده إعادة الحساب الكاملة مش هتدخل في الوقت، فنروح incremental: upsert في summary مفتاحها tenant و month، أو stream rollup، ومعاه reconcile دوري ضد مصدر الحقيقة عشان يمسك الـ drift.

Common mistakes · غلطات شائعة

❌ Choosing the store from its marketing 
// القرار جه قبل أي query اتكتبت
const db = "cassandra"; // عشان الـ scale وخلاص
// النتيجة: مفيش joins للـ reports
// ومفيش transactions للـ stock
✅ Decide from written patterns 
// الـ decision طالعة من الـ patterns والأرقام
const choice = decide({
  name: "orders",
  pattern: "relational",
  multiRowInvariant: true,
  writesPerSecPeak: 400,
  dataTb: 1,
  schemaVaries: false,
  teamKnowsPostgres: true,
});
بالعامية

❌ لو اخترت الـ store قبل ما تكتب ولا query، بتكتشف بعد كده إن الـ reporting والـ stock محتاجين joins و transactions مش موجودين. ✅ اكتب الـ patterns الأول، وخلي الـ decision ينتج من القايمة والأرقام: بـ 400 write/s و invariant عبر صفوف، Postgres هو الإجابة ومعاه هامش كبير.

❌ Composite index in the wrong order 
-- القراية: customer_id = ? ORDER BY created_at DESC
CREATE INDEX ON orders (created_at DESC, customer_id);
-- بيقرا 1,833 buffer عشان 20 صف
✅ Equality first, sort after 
-- عمود الـ equality الأول وبعده الـ sort
CREATE INDEX ON orders (customer_id, created_at DESC);
-- بيقرا 23 buffer عشان نفس الـ 20 صف
بالعامية

❌ الـ index بتاع created_at الأول بيفرّق صفوف الـ customer في كل مكان، فبيمشي على 1,833 buffer. ✅ لما الـ equality ييجي الأول، صفوف الـ customer كلها جنب بعض، 23 buffer بس، يعني حوالي 80 مرة أقل، على نفس الجدول ونفس الـ query.

❌ Counter updated after the commit 
// لو الـ process وقع بين السطرين العداد غلط للأبد
await db.query("insert into orders ...");
await db.query("update customers set orders_count = orders_count + 1 where id = $1", [id]);
✅ Same transaction, plus a reconcile job 
// الاتنين في نفس الـ transaction، و reconcile ليلي للـ bugs
await db.query("begin");
await db.query("insert into orders ...");
await db.query("update customers set orders_count = orders_count + 1 where id = $1", [id]);
await db.query("commit");
بالعامية

❌ لو الـ insert حصل والـ process وقع قبل الـ update، العداد غلط للأبد ومحدش هيعرف. ✅ الاتنين في نفس الـ transaction يا إما الاتنين يتموا يا إما لا. وكمان reconcile job ليلي، لأن أي مسار كتابة تاني (bulk import مثلًا) ممكن يعدّي من غير ما يحدّث العداد.

❌ Plain REFRESH on a live dashboard 
-- كل الـ readers واقفين طول الـ refresh
REFRESH MATERIALIZED VIEW monthly_revenue;
-- أسوأ قراية ⁦≈249 ms⁩ على مليون صف بس
✅ CONCURRENTLY with a unique index 
-- محتاج unique index مرة واحدة
CREATE UNIQUE INDEX ON monthly_revenue (tenant_id, month);
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_revenue;
-- أسوأ قراية ⁦≈2 ms⁩ في نفس التجربة
بالعامية

❌ الـ REFRESH العادي بيقفل الـ view كلها بـ ACCESS EXCLUSIVE، فكل قراية بتستنى لحد ما يخلص، وعلى داتا أكبر ده بيبقى دقايق. ✅ بـ CONCURRENTLY والـ unique index، الـ reader مكمل شغله والأسوأ ≈2 ms، مقابل refresh أبطأ سنة.

// تمرين 3: عداد بـ trigger، بيتحدث في نفس الـ transaction بتاعة الـ insert
await db.query(`
  create function bump_orders_count() returns trigger language plpgsql as $$
  begin
    update customers set orders_count = orders_count + 1 where id = new.customer_id;
    return new;
  end $$;
  create trigger orders_count_bump after insert on orders
    for each row execute function bump_orders_count();
`);
const count = async () => (await db.query(`select orders_count n from customers where id = 777`)).rows[0].n as number;
const before = await count();
await db.query(`insert into orders values (2000001, 1, 777, 'pending', 1000, now())`);
console.log("after insert through the normal path:", (await count()) - before, "added");

// الـ bug اللي بنحاكيه: bulk import بيعدّي من غير الـ trigger، زي COPY بعد disable trigger
await db.query(`alter table orders disable trigger orders_count_bump`);
await db.query(`insert into orders select 2000001 + g, 1, 777, 'pending', 1000, now() from generate_series(1, 5) g`);
await db.query(`alter table orders enable trigger orders_count_bump`);

const reconcile = `
  update customers c set orders_count = x.n
  from (select customer_id, count(*)::int n from orders group by 1) x
  where x.customer_id = c.id and c.orders_count <> x.n
  returning c.id`;
const fixed = await db.query(reconcile);
console.log("reconcile fixed customers:", fixed.rows.map((r) => Number(r.id)), "| second run fixes:", (await db.query(reconcile)).rowCount);
await db.end();

reconcile fixed customers: [ 777 ] | second run fixes: 0

Cheat sheet · الخلاصة

  • Write the access patterns first: filter, sort, rate, p99, transaction or not. The store comes after.
  • Framework order: patterns → consistency → read/write → schema → team. A multi-row invariant ends it at step 2.
  • "NoSQL for scale" is a myth at most sizes: one durable Postgres did ≈33,000 commits/s here against a ≈1,200/s flash-sale estimate.
  • JSONB is the middle ground for per-item attributes. @> with a GIN index took ≈37 ms down to ≈4.6 ms.
  • Composite index: equality columns first, then sort or range. Wrong order cost 1,833 buffers vs 23.
  • Six indexes made batched inserts 8.4× slower. Every index needs a query that justifies it.
  • Index RAM: measure 1M rows, multiply, add about 1.4× for random-insert bloat, count what is really hot.
  • Partial indexes save memory (38.7 MB → 0.2 MB). Covering indexes save pages (22 → 4) if vacuum keeps up. tenant_id goes first.
  • Denormalize when filter and sort are on different tables (≈40×), not for a 20-row PK join (≈0.3 ms).
  • Every copy needs a named update path and a repair job. Hot counters are write contention: -74% on one row.
  • Materialized view: use CONCURRENTLY and a unique index, or readers stall for the whole refresh.
  • Summary table when the view no longer fits the staleness budget, with a reconcile job against the source of truth.
بالعامية
  • اكتب الـ access patterns الأول: الـ filter، الـ sort، الـ rate، الـ p99، و transaction ولا لأ. الـ store بييجي بعد كده.
  • ترتيب الـ framework: patterns ← consistency ← read/write ← schema ← team. أي invariant عبر صفوف بيقفل النقاش عند الخطوة التانية.
  • "NoSQL عشان الـ scale" خرافة في معظم الأحجام: Postgres واحد durable عمل ≈33,000 commit في الثانية هنا مقابل estimate لـ flash sale حوالي 1,200.
  • الـ JSONB حل وسط للـ attributes اللي بتختلف من عنصر لعنصر. @> مع GIN index نزلت من ≈37 ms لـ ≈4.6 ms.
  • الـ composite index: أعمدة الـ equality الأول، وبعدها الـ sort أو الـ range. الترتيب الغلط كلّف 1,833 buffer مقابل 23.
  • 6 indexes خلّوا الـ insert بالـ batches أبطأ 8.4 مرة. كل index لازم query تبرره.
  • الـ RAM بتاع الـ indexes: قيس على مليون صف، اضرب، زوّد حوالي 1.4× لـ bloat الـ random inserts، واحسب اللي hot بجد.
  • الـ partial بيوفر memory (38.7 MB لـ 0.2 MB). الـ covering بيوفر صفحات (22 لـ 4) لو الـ vacuum ملاحق. والـ tenant_id أول عمود.
  • اعمل denormalize لما الـ filter والـ sort يبقوا على جدولين (≈40×)، مش عشان join بتاع 20 صف على PK (≈0.3 ms).
  • كل نسخة ليها طريقة تحديث متسمية و repair job. الـ counters الـ hot معناها write contention: -74% على صف واحد.
  • الـ materialized view: استخدم CONCURRENTLY مع unique index، وإلا الـ readers واقفين طول الـ refresh.
  • الـ summary table لما الـ view ميبقاش داخل في الـ staleness budget، ومعاها reconcile job ضد مصدر الحقيقة.
