Why this matters · ليه ده مهم

English

Most production systems keep slow or fragile work out of the request path: confirmation e-mails, invoice PDFs, webhook delivery, video transcoding. Interviews ask the same thing in one sentence: "queue, stream or pub/sub, and what happens when the consumer is down?" Getting it wrong shows up as lost events, a checkout that fails because an e-mail provider had a bad minute, or a user told "order placed" whose card is declined 30 seconds later. Every number in this lesson comes from real runs on Redis 8 and Postgres 18; the e-mail and PDF calls are labelled stand-ins.

بالعامية

أغلب الأنظمة في production بتطلّع الشغل البطيء أو اللي بيقع بسهولة بره الـ request: إيميل تأكيد، PDF فاتورة، webhook، تحويل فيديو. وفي الـ interview السؤال بييجي في جملة واحدة: "queue ولا stream ولا pub/sub، وإيه اللي بيحصل لو الـ consumer واقع؟". لو اخترت غلط، النتيجة بتبان: events بتضيع، أو checkout بيفشل عشان provider الإيميل وقع دقيقة، أو مستخدم قلتله "الطلب اتعمل" وبعد 30 ثانية الكارت يترفض. كل الأرقام في الدرس ده من runs حقيقية على Redis 8 و Postgres 18، وأي call لإيميل أو PDF مكتوب عليه إنه محاكاة.

Part 1 — Producer → queue → consumer 🟢 Basicالجزء 1 — الـ producer والـ queue والـ consumer

English

Three roles. A producer appends a message and carries on. A queue holds it durably. A consumer pulls it whenever it has capacity. The producer never calls the consumer, so the two are decoupled in time (the consumer needn't be running when the order is placed) and decoupled in failure (the e-mail provider being down no longer fails checkout). A queue doesn't make work faster. It moves work out of the request and lets it wait.

The experiment runs one checkout route two ways under autocannon (20 connections, 400 requests). /checkout-inline awaits the e-mail call. /checkout-queued does a BullMQ add on real Redis and returns. BullMQ's API is taught in Node.js lesson 22; here we only care about the system behaviour. Then the consumer stops and the provider goes down, and we watch what each design does.

What breaks: if Redis itself is down, add throws, so decide up front whether to fail the request or write to an outbox (see the mistakes below). And an unbounded queue hides a growing backlog until someone checks it (lesson 21).

// السكريبتات دي بتعمل FLUSHDB، فأي port فاضي أو default هيمسح الـ Redis بتاعك الحقيقي
export function redisPort(): number {
  const raw = process.env.REDIS_PORT ?? readFileSync("redis.port", "utf8").trim();
  const n = Number(raw);
  if (!/^\d+$/.test(raw) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) throw new Error("refusing port " + raw);
  return n;
}

export function percentile(values: number[], p: number): number {
  const s = [...values].sort((a, b) => a - b);
  return s[Math.min(s.length - 1, Math.floor((p / 100) * s.length))];
}

async function load(path: string, amount: number) {
  const times: number[] = [];
  const statuses: Record<number, number> = {};
  await new Promise<void>((resolve) => {
    const run = autocannon({ url: `http://127.0.0.1:${port}${path}`, method: "POST", connections: 20, amount }, () => resolve());
    run.on("response", (_c, status, _b, ms) => {
      times.push(ms);
      statuses[status] = (statuses[status] ?? 0) + 1;
    });
  });
  return { p50: percentile(times, 50), p95: percentile(times, 95), statuses };
}

بالعامية

عندك 3 أدوار. الـ producer بيحط رسالة ويكمّل طريقه. الـ queue بتشيلها في مكان آمن. والـ consumer بيسحبها لما يبقى عنده وقت. الـ producer عمره ما بينادي الـ consumer مباشرة، فالاتنين بقوا منفصلين في الوقت (الـ consumer مش لازم يكون شغال وقت ما الطلب يتعمل) ومنفصلين في الفشل (لو provider الإيميل وقع، الـ checkout مش هيقع معاه). والـ queue مش بتخلي الشغل أسرع: هي بس بتطلّعه بره الـ request وتخليه يستنى.

التجربة بتشغّل نفس الـ checkout بطريقتين تحت autocannon، 20 connection و400 request. /checkout-inline بيستنى الإيميل، و/checkout-queued بيعمل add في BullMQ على Redis حقيقي ويرد. الـ API بتاع BullMQ اتشرح في درس 22 في Node.js، وهنا اللي يهمنا سلوك النظام. بعد كده بنوقف الـ consumer ونوقّع الـ provider ونشوف كل واحد عمل إيه.

لاحظ إن الـ p95 نزل من ≈ 345ms لـ ≈ 21ms، بس الإيميل نفسه لسه بياخد 300ms. اللي اتغير إن المستخدم مش بيستناه. والفرق الأكبر مش في الـ latency: الـ inline فشل 100 مرة لما SMTP وقع، والـ queued منجح 100 طلب وحط الشغل يستنى، ولما رجع خلّص الـ 100 لوحده.

إيه اللي هيكسر؟ الـ Redis نفسه لو وقع، add بيفشل: وقتها لازم تقرر (تفشّل الطلب، أو outbox في الـ DB، وهنشوفها في الغلطات تحت). والـ queue اللي مش محدودة بتخبّي مشكلة: الـ backlog يكبر من غير ما حد ياخد باله، وده موضوع الدرس 21.

فين هستخدمه في شغلي؟ API بتاع checkout في Node: بدل await mailer.send() جوه الـ route، حط job في BullMQ وخلّي process تانية تبعته. لو الـ SendGrid وقع ساعة الصبح، الطلبات تفضل تنجح والإيميلات تتأخر شوية بدل ما الموقع كله يبقى بيرجع 500. وأي code review فيه await على provider خارجي جوه request handler، ده أول سؤال تسأله.
Trade-off: you buy resilience and pay in complexity A queue adds a broker to run and monitor, a second deployment (the worker), eventual consistency (the user sees "sent" before it is sent), and new failure modes (duplicates, poison messages). For a 2 ms local operation, it only adds risk.
الـ queue بتشتري بيها resilience بس بتدفع تعقيد: broker لازم يتشغّل ويتراقب، deployment تاني للـ worker، و eventual consistency (المستخدم يشوف "اتبعت" قبل ما يتبعت فعلًا)، ومشاكل جديدة زي التكرار والـ poison messages. لو الشغلانة 2ms على DB محلية، الـ queue هتزوّد خطر بس.

Part 2 — When to go async 🟢 Basicالجزء 2 — إمتى تعمل حاجة async

English

Start from the request budget: the latency target for the endpoint minus what the request already spends. If the task's p99 doesn't fit, it can't be synchronous. But budget is only half the question. The other half is: does the user's next step depend on the answer? Payment authorization often takes a few seconds, way over a tight budget, and it stays synchronous because the user can't move on without knowing. An e-mail fits the budget (300 ms) and still goes async because a provider outage mustn't fail the order.

A second lesson from the numbers: enqueue latency is not job latency. Below, 40 PDF jobs at 400 ms each on 4 workers: the enqueue costs ≈ 0.3 ms, but the last job finishes after ≈ 4 s, because 40 × 400 / 4 = 4000 ms. That wait still exists. It has moved from the HTTP connection to a status endpoint, so the API returns 202 Accepted with a Location header and the client polls GET /jobs/:id.

export type Task = {
  name: string;
  p99Ms: number;
  // المستخدم هيغيّر قراره دلوقتي حسب النتيجة؟
  userNeedsOutcomeNow: boolean;
  dependsOnThirdParty: boolean;
};
export type Decision = { mode: "sync" | "async"; reason: string };

// الـ budget هو اللي فاضل من الـ SLO بتاع الـ request بعد باقي الشغل
export function shouldBeAsync(task: Task, remainingBudgetMs: number): Decision {
  if (task.userNeedsOutcomeNow) return { mode: "sync", reason: "the user's next step depends on the answer" };
  if (task.p99Ms > remainingBudgetMs) return { mode: "async", reason: `p99 ${task.p99Ms}ms exceeds budget ${remainingBudgetMs}ms` };
  if (task.dependsOnThirdParty) return { mode: "async", reason: "a third-party outage must not fail the request" };
  return { mode: "sync", reason: "fast, local and cheap: a queue would only add failure modes" };
}

بالعامية

ابدأ بالـ request budget: هدف الـ latency بتاع الـ endpoint ناقص اللي الـ request صرفه أصلًا. لو الـ p99 بتاع الشغلانة ميدخلش، مينفعش تبقى sync. بس الـ budget نص السؤال بس. النص التاني: الخطوة الجاية بتاعة المستخدم متوقفة على الإجابة؟ الدفع غالبًا بياخد كام ثانية، أكبر من أي budget ضيق، ومع كده بيفضل sync لأن المستخدم مش هيعرف يكمل من غير ما يعرف. والإيميل بيدخل في الـ budget (300ms)، ومع كده بيبقى async عشان وقوع الـ provider ميوقّعش الطلب.

Part 3 — Retries & dead-letter queues 🟢 Basicالجزء 3 — الـ retries والـ dead-letter queue

English

Consumers fail. Two kinds of failure need two answers. A transient failure (a 503 during a deploy) passes if you wait, so retry with exponential backoff, leaving the service room to recover. A persistent failure (a bad URL, a malformed payload) never passes, so after a fixed number of attempts the message moves aside into a dead-letter queue (DLQ), where it no longer burns workers and a person can look at it. The DLQ is also why retries can be finite: without one, giving up means losing the message.

The run below sends 50 webhooks at a flaky merchant: 33 succeed immediately, 14 fail twice and then pass, and 3 always fail until the merchant fixes its URL. The attempt count is predictable, which is how you sanity-check a retry policy: 33×1 + 14×3 + 3×4 = 87. A replay script then moves the DLQ back to the main queue after the fix.

This is the concept and the minimum code. Poison detection, TTL, retry storms and replay safety are in lesson 21, and BullMQ's failed-set-versus-DLQ detail is in Node.js lesson 22, part 6.

function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

Part 4 — Three models on real Redis 🟡 Intermediateالجزء 4 — التلات نماذج على Redis حقيقي

English

The same five OrderPlaced events, three delivery models. A queue (Redis LIST with BLPOP) distributes work: each message goes to exactly one consumer and is then gone. A log (Redis STREAM) keeps the messages and lets each consumer group read them independently, so two groups each get all five and a group created afterwards can still replay from the beginning. Pub/sub (PUBLISH) is live fan-out: every currently connected subscriber gets the message and nothing is stored, so a late subscriber sees nothing.

That single property, what happens to a message after delivery, decides the rest. RabbitMQ and SQS behave like the list (RabbitMQ's fan-out exchanges and SQS with SNS add fan-out). Kafka is a log with partitions, Redis Streams a smaller log, and Redis pub/sub and SNS are fan-out. Queues and logs are compared on products in section 07, lesson 39, and message channels as patterns in section 08, lesson 25.

async function readGroup(group: string, consumer: string): Promise<string[]> {
  const r = newRedis();
  await r.xgroup("CREATE", "orders:stream", group, "0");

      got.push(fields[1]);
      await r.xack("orders:stream", group, id);
    }
  }
  await r.quit();
  return got;
}

Part 5 — Choosing one 🟡 Intermediateالجزء 5 — تختار إزاي

English

Work through the requirements, not the logos. Is loss acceptable (cache invalidation, presence)? Then pub/sub. Do you need replay or independent consumers? Then a log. Otherwise you need work distribution with per-message ack, which means a queue. Ordering and retention matter: a queue can't replay last week, and a plain queue with several workers won't preserve order (measured in lesson 20).

Add the option everyone forgets, a Postgres table with FOR UPDATE SKIP LOCKED. If you already run Postgres, the job row can be written in the same transaction as the order, so the "row saved but job lost" problem disappears: the run below rolls back both together. It also shows the real cost. With one job per transaction and durable commits, 4 workers did ≈ 5.8k jobs/s here; batching 20 per transaction gave ≈ 62k. Both numbers only mark rows done: no real work runs, the numbers are from this machine's disk under load, and at that volume dead tuples need vacuuming. Whether you need Kafka at all is the subject of lesson 44.

Treat chooseMessaging() below as a starting point, not a rule: it eliminates first (is loss acceptable? replay?) and then picks the simplest option that satisfies the rest, and any new case should get a scenario test first. p5-skip-locked.mjs imports a small helper that starts a throwaway Postgres on a free port; any disposable Postgres works.

export type Needs = {
  replay: boolean;
  independentConsumers: number;
  perKeyOrdering: boolean;
  // فشل message واحدة لازم ميوقفش اللي بعدها
  perMessageAck: boolean;
  retentionDays: number;
  msgsPerSecond: number;
  // ضياع الـ message مقبول (زي presence أو invalidation)
  lossAcceptable: boolean;
  // الـ message لازم تتكتب مع الـ business row في نفس الـ transaction
  sameTxAsBusinessData: boolean;
};

export type Choice = "pub/sub" | "postgres skip-locked" | "queue (BullMQ, SQS, RabbitMQ)" | "log (Kafka, Redis Streams)";

// الترتيب مهم: الأول الحاجات اللي بتستبعد خيارات، وبعدين الأبسط اللي يكفي
export function chooseMessaging(n: Needs): Choice {
  if (n.lossAcceptable && !n.replay) return "pub/sub";
  if (n.replay || n.independentConsumers > 1 || n.retentionDays > 14) return "log (Kafka, Redis Streams)";
  if (n.sameTxAsBusinessData && n.msgsPerSecond < 1_000) return "postgres skip-locked";
  return "queue (BullMQ, SQS, RabbitMQ)";
}

  async function worker(batch, seen) {
    const c = await connect(port);
    for (;;) {
      await c.query("BEGIN");
      const { rows } = await c.query(
        `SELECT id FROM jobs WHERE state = 'ready' ORDER BY id LIMIT $1 FOR UPDATE SKIP LOCKED`,
        [batch],
      );
      if (rows.length === 0) { await c.query("COMMIT"); break; }
      for (const r of rows) seen.set(r.id, (seen.get(r.id) ?? 0) + 1);
      await c.query(`UPDATE jobs SET state='done', attempts=attempts+1, done_at=now() WHERE id = ANY($1::bigint[])`, [rows.map((r) => r.id)]);
      await c.query("COMMIT");
    }
    await c.end();
  }

    await admin.query("TRUNCATE jobs");
    await admin.query(`INSERT INTO jobs(kind, payload) SELECT 'email', '{}'::jsonb FROM generate_series(1, $1::int)`, [n]);

امشي على المتطلبات مش على الأسامي. الضياع مقبول (cache invalidation، presence)؟ يبقى pub/sub. محتاج replay أو consumers مستقلين؟ يبقى log. غير كده إنت محتاج توزّع شغل مع ack لكل رسالة، يبقى queue. والـ ordering والـ retention مهمين: الـ queue مش هتعمل replay لشغل الأسبوع اللي فات، والـ queue العادية مع كذا worker مش بتحافظ على الترتيب (قسناها في الدرس 20).

وضيف الخيار اللي الناس بتنساه: جدول Postgres مع FOR UPDATE SKIP LOCKED. لو عندك Postgres أصلًا، الـ job row بيتكتب في نفس الـ transaction مع الطلب، فمشكلة "الصف اتحفظ والـ job ضاعت" بتختفي: التجربة عملت ROLLBACK للاتنين مع بعض. وكمان بتبين التكلفة: job واحدة في كل transaction مع durable commits، 4 workers عملوا ≈ 5.8k job/s، والـ batch من 20 عمل ≈ 62k. الرقمين دول بيعلّموا rows done بس، مفيش شغل حقيقي، على disk الجهاز ده وهو عليه ضغط، وعلى volume زي ده الـ dead tuples محتاجة vacuum. وهل محتاج Kafka أصلًا؟ ده الدرس 44.

والـ chooseMessaging() اللي فوق نقطة بداية مش قانون: الترتيب فيها إنها تستبعد الأول (ضياع مقبول؟ replay؟) وبعدين تختار الأبسط اللي يكفي. وأي خيار جديد ضيفله سيناريو test الأول. والـ p5-skip-locked.mjs بيستورد helper صغير بيشغّل Postgres مؤقت على port فاضي، وأي Postgres مؤقت هيعمل نفس الشغل.

فين هستخدمه في شغلي؟ مشروع صغير بـ Postgres بس وعايز "ابعت فاتورة بعد الطلب": جدول jobs في نفس الـ transaction ووorker بـ SKIP LOCKED هيعيش لحد مئات الـ jobs في الثانية من غير أي infrastructure جديدة. لما يبان إن فيه billing و analytics و fraud كلهم عايزين نفس الـ event ويرجعوا له، وقتها تفكر في stream زي Kafka.

Interview: "Why not use Kafka for everything?" Kafka is a log: it gives replay and many independent consumers, but it also adds partitions to plan, a cluster to run, and rebalance pauses. A job queue with a handful of workers is better served by a simpler queue, or by the Postgres you already have. Reach for a log when you need its properties, not for its name.
السؤال: "ليه منستخدمش Kafka في كل حاجة؟" الإجابة: Kafka عبارة عن log بيديك replay و consumers كتير مستقلين، بس بيزوّد partitions لازم تخطط لها، وcluster لازم تشغّله، وrebalance pauses. للـ jobs القليلة، queue أبسط أو الـ Postgres اللي عندك أحسن. استخدم log لما تحتاج خصايصه، مش عشان اسمه.

import { Queue } from "bullmq";
import { connection, flush } from "./lib.ts";

await flush();
const main = new Queue("webhooks", { connection });
const dlq = new Queue("webhooks-dlq", { connection });

// الـ DLQ فيها 3 رسايل: اتنين سليمين وواحدة poison من غير url
await dlq.add("deliver", { original: { webhookId: "wh-1", url: "https://merchant.example/hook" }, reason: "503" });
await dlq.add("deliver", { original: { webhookId: "wh-2", url: "https://merchant.example/hook" }, reason: "503" });
await dlq.add("deliver", { original: { webhookId: "wh-3" }, reason: "payload missing url" });

const isValid = (p: { url?: unknown }) => typeof p.url === "string" && p.url.startsWith("https://");

let replayed = 0;
let kept = 0;
for (const dead of await dlq.getJobs(["waiting"])) {
  if (!isValid(dead.data.original)) {
    // الـ poison بيفضل في الـ DLQ عشان إنسان يبص عليه، ومتتعملوش replay
    kept++;
    continue;

  await main.add(dead.name, dead.data.original, { jobId: `replay-${dead.data.original.webhookId}`, attempts: 4 });
  await dead.remove();
  replayed++;
}

await dlq.close();

Cheat sheet · الخلاصة

  • A queue decouples time and failure. It doesn't make work faster.
  • Two questions: does the p99 fit the remaining budget, and does the user's next step depend on the answer?
  • Payment authorization: sync with a timeout. Capture, invoice, e-mail: async.
  • Enqueue ≈ 0.3 ms, job latency = backlog ÷ throughput. Report both.
  • Long jobs: 202 + Location + status endpoint; keep the status long enough for the client to read it.
  • Retries for transient errors with backoff, finite attempts, then a DLQ and a replay path.
  • What happens after delivery decides the model: queue (removed), log (retained), pub/sub (not stored).
  • Pub/sub only when losing a message is acceptable.
  • Postgres SKIP LOCKED commits the job with the business row, ≈ 5.8k jobs/s here marking rows only.
  • Kafka when you need replay and many independent consumers, not by default.
بالعامية
  • الـ queue بتفصل الوقت والفشل، ومش بتخلي الشغل أسرع.
  • سؤالين: الـ p99 يدخل في الـ budget الباقي؟ والخطوة الجاية بتاعة المستخدم متوقفة على الإجابة؟
  • الدفع (authorization): sync مع timeout. الـ capture والفاتورة والإيميل: async.
  • الـ enqueue ≈ 0.3ms، ووقت الـ job = الـ backlog ÷ الـ throughput. قيس الاتنين.
  • الـ jobs الطويلة: 202 وLocation و status endpoint، وخلّي الـ status موجود كفاية عشان الـ client يقراه.
  • الـ retries للأخطاء المؤقتة مع backoff وعدد محدود، وبعدها DLQ وطريقة replay.
  • اللي بيحصل بعد التسليم هو اللي بيحدد النوع: queue (بتتشال)، log (بتفضل)، pub/sub (مبتتخزنش).
  • الـ pub/sub بس لما ضياع الرسالة يبقى مقبول.
  • الـ Postgres SKIP LOCKED بيعمل commit للـ job مع الـ business row، وهنا ≈ 5.8k job/s بيعلّم rows بس.
  • الـ Kafka لما تحتاج replay و consumers كتير مستقلين، مش افتراضيًا.
