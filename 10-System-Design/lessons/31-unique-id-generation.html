Why this matters · ليه ده مهم

English

An ID looks like a detail until the table holds a billion rows and appears in every foreign key, index, URL, log line and event. The choice decides whether two shards can both create orders, how much your primary key index and WAL cost, whether a competitor can read your sales volume from a URL, and whether a JavaScript client silently corrupts the number. It is also a very common interview question, usually asked as "design a unique ID generator".

بالعامية

الـ ID شكله تفصيلة صغيرة لحد ما الـ table يوصل مليار صف ويبقى موجود في كل foreign key وindex وURL وlog وevent. الاختيار ده هو اللي بيحدد هل shard-ين يقدروا يعملوا orders مع بعض، الـ primary key index والـ WAL هيكلفوك قد إيه، منافسك يقدر يعرف حجم مبيعاتك من URL ولا لأ، وهل الـ client في JavaScript هيبوّظ الرقم من غير ما يقول. وكمان سؤال interview مشهور جدًا، غالبًا بصيغة "صمّم unique ID generator".

Part 1 — Auto-increment and where it stops 🟡 Intermediateالجزء 1 — الـ auto-increment وبيقف فين

English

On one database a sequence is close to perfect: 8 bytes, strictly increasing per generator, ordered inserts, and nothing to deploy. The trouble starts when two databases generate IDs independently. A sequence only knows its own database, so two shards hand out the same numbers, and the collision appears later, when you merge data, build a global search index, or move a tenant between shards.

The classic hack is offset and step: shard A takes odd numbers, shard B even. It works, but the shard count is baked into every sequence. A third shard does not fit without changing the step everywhere, and a naive "start 3, step 3" collides with both, as the run below shows. Plan for it up front by choosing a large step (say 1024) and you waste nothing real, but you are still hand-assigning ranges in a config that must never be wrong.

Sequential IDs also leak. Place two orders a day apart and subtract: that is your competitor's daily order volume. And sequential IDs in a URL make enumeration trivial: /invoices/1042 invites /invoices/1043. Authorization has to stop that anyway (see OWASP Top 10 in Node), but an ID that can't be guessed removes the easy version of the attack.

It is still the right answer for a single database, for internal IDs that never leave the API, and for small lookup tables. If you shard later, the usual fix is a new ID scheme for new rows, not a rewrite.

import pg from "pg";

// تحذير: السكريبت بيعمل tables، فشغّله على Postgres للتجربة بس
const [urlA, urlB] = [process.env.PG_A_URL, process.env.PG_B_URL];
if (!urlA || !urlB) throw new Error("set PG_A_URL and PG_B_URL to two throwaway databases");
const shardA = new pg.Client({ connectionString: urlA });
const shardB = new pg.Client({ connectionString: urlB });
await shardA.connect();
await shardB.connect();

const insertOrder = async (db: pg.Client, table: string, userId: number) => {
  const r = await db.query<{ id: string }>(`INSERT INTO ${table} (user_id) VALUES ($1) RETURNING id`, [userId]);
  return r.rows[0].id;
};

// (1) كل shard عنده sequence لوحده ومايعرفش حاجة عن التاني
for (const db of [shardA, shardB]) {
  await db.query(`CREATE TABLE orders (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, user_id int NOT NULL)`);
}
const a = [await insertOrder(shardA, "orders", 7), await insertOrder(shardA, "orders", 8), await insertOrder(shardA, "orders", 9)];
const b = [await insertOrder(shardB, "orders", 20), await insertOrder(shardB, "orders", 21), await insertOrder(shardB, "orders", 22)];
console.log("shard A order ids:", a);
console.log("shard B order ids:", b);
console.log("same id, two different orders:", a.filter((id) => b.includes(id)));

// (2) حيلة الـ offset والـ step: الأرقام الفردية لـ A والزوجية لـ B
await shardA.query(`CREATE TABLE orders2 (id bigint GENERATED ALWAYS AS IDENTITY (START WITH 1 INCREMENT BY 2) PRIMARY KEY, user_id int)`);
await shardB.query(`CREATE TABLE orders2 (id bigint GENERATED ALWAYS AS IDENTITY (START WITH 2 INCREMENT BY 2) PRIMARY KEY, user_id int)`);
const a2: string[] = [];
const b2: string[] = [];
for (let i = 0; i < 4; i++) {
  a2.push(await insertOrder(shardA, "orders2", 1));
  b2.push(await insertOrder(shardB, "orders2", 1));
}
console.log("step 2, A:", a2, "B:", b2, "collisions:", a2.filter((id) => b2.includes(id)).length);

// (3) دلوقتي عايز shard تالت: مفيش مكان ليه من غير ما تغيّر الـ step عند الكل
await shardA.query(`CREATE SEQUENCE third_shard START WITH 3 INCREMENT BY 3`);
const c: string[] = [];
for (let i = 0; i < 4; i++) c.push((await shardA.query<{ v: string }>(`SELECT nextval('third_shard') AS v`)).rows[0].v);
console.log("naive third shard:", c, "hits A:", c.filter((id) => a2.includes(id)), "hits B:", c.filter((id) => b2.includes(id)));

await shardA.end();
await shardB.end();

بالعامية

على database واحدة الـ sequence قريب من الكمال: 8 bytes، بيزيد باستمرار جوه الـ generator، الـ inserts مرتبة، ومفيش حاجة تتعمل deploy. المشكلة بتبدأ لما اتنين databases يولّدوا IDs لوحدهم. الـ sequence عارف الـ database بتاعته بس، فالاتنين بيدّوا نفس الأرقام، والتعارض بيظهر بعدين: لما تجمع الـ data، أو تعمل global search index، أو تنقل tenant بين shards.

الحل القديم هو الـ offset والـ step: shard A ياخد الفردي وshard B ياخد الزوجي. شغال، بس عدد الـ shards بقى محفور في كل sequence. الـ shard التالت مش هيدخل من غير ما تغيّر الـ step عند الكل، ولو عملت "start 3, step 3" ببساطة هيخبط في الاتنين زي ما الناتج فوق بيوضح. ممكن تخطط من الأول بـ step كبير زي 1024 وماتخسرش حاجة حقيقية، بس برضه بتوزّع ranges بإيدك في config لازم مايغلطش أبدًا.

الـ IDs المتتالية كمان بتسرّب معلومات. اعمل طلبين بينهم يوم واطرح الرقمين: ده حجم طلبات منافسك في اليوم. وكمان في الـ URL بتسهّل الـ enumeration: /invoices/1042 بتعزم عليك بـ /invoices/1043. الـ authorization لازم يوقف ده في كل الأحوال (شوف OWASP Top 10 في Node)، بس الـ ID اللي مايتخمّنش بيشيل النسخة السهلة من الهجوم.

ولسه هو الاختيار الصح مع database واحدة، ومع IDs داخلية مابتطلعش برا الـ API، ومع الـ lookup tables الصغيرة. ولو عملت sharding بعدين، الحل المعتاد هو scheme جديد للصفوف الجديدة مش إعادة كتابة كل حاجة.

أمثلة الـ TypeScript بتشتغل بـ node file.ts على Node 22 (type stripping)، من فولدر الـ package.json بتاعه فيه "type": "module"، ومتسطب فيه pg وuuid 14 وulid 3.

فين هستخدمه في شغلي؟ API لمتجر فيه Postgres واحدة وعمود orders.id داخلي، بتستخدمه في الـ joins بس، وفي الـ URL بتعرض public_id تاني مش متتالي. الغلطة الشائعة: تعرض orders.id في /orders/1042 فأي user يقدر يعرف عدد طلباتك ويجرّب أرقام غيره.

Part 2 — UUID v4 and the index it damages 🟡 Intermediateالجزء 2 — الـ UUID v4 والضرر اللي بيعمله في الـ index

English

UUID v4 has 122 random bits. Collisions are not a practical worry, and any machine can generate one with no coordination, which is why it became the default. The cost lands on the B-tree: every insert goes to a random leaf page. Pages split wherever they happen to be, so they settle around two-thirds full instead of packed, the whole index stays "hot" instead of just its right edge, and after each checkpoint the first change to every page writes a full-page image to the WAL.

I measured this on real Postgres 18.4 with 32 MB of shared_buffers, durable settings, inserts in batches of 10,000, and idx_blks_read from pg_statio_user_indexes for buffer misses. Size and density are stable and repeat in every run. Insert time needs care: at 200k and 1M rows the gap moved between runs, from about 1.3× to 2.2×, on a loaded Windows machine with v4 going first, so I wouldn't conclude much from those. At 5M rows the index is about 6× larger than the buffer pool, and that is where the difference becomes real: I reran 5M with v7 going first and got the same picture, 74 s vs 23 s and 2.74M vs 17.7k misses (storage engines explains the page mechanics).

  UUID v4: every insert picks a random leaf
    [leaf 1 ...w..] [leaf 2 .w...] [leaf 3 ..w..] [leaf 4 w....]
     all pages dirty, splits everywhere, about 69% full

  UUID v7: inserts go to the rightmost leaf
    [leaf 1 full] [leaf 2 full] [leaf 3 full] [leaf 4 ...w ->]
     only the right edge is hot, about 90% full
فوق: الـ v4 بيكتب في leaf عشوائية كل مرة، فكل الصفحات بتبقى dirty، والـ splits في كل حتة، والصفحات مليانة حوالي 69% بس. تحت: الـ v7 بيكتب دايمًا في آخر leaf على اليمين، فالصفحات القديمة بتتملى وتسكت، والجزء الساخن هو الطرف اليمين بس، ومليانة حوالي 90%.
import pg from "pg";

// تحذير: شغّله على Postgres 18 للتجربة، وابدأه بـ shared_buffers=32MB عشان الـ cache يبقى أصغر من الـ index
const url = process.env.PG_URL;
if (!url) throw new Error("set PG_URL to a throwaway Postgres 18");
const ROWS = Number(process.env.ROWS ?? 1_000_000);
const BATCH = 10_000;
const db = new pg.Client({ connectionString: url });
await db.connect();
await db.query("CREATE EXTENSION IF NOT EXISTS pgstattuple");

const indexIo = async (idx: string) => {
  // ملحوظة: الـ stats بتتكتب متأخر، فبنجبرها تتسجل قبل ما نقرا
  await db.query("SELECT pg_stat_force_next_flush()");
  const r = await db.query<{ read: string; hit: string }>(
    "SELECT idx_blks_read AS read, idx_blks_hit AS hit FROM pg_statio_user_indexes WHERE indexrelname = $1",
    [idx],
  );
  return r.rows[0];
};

for (const [table, fn] of [["orders_v4", "gen_random_uuid()"], ["orders_v7", "uuidv7()"]] as const) {
  await db.query(`CREATE TABLE ${table} (id uuid PRIMARY KEY, user_id int NOT NULL, total_cents int NOT NULL)`);
  const before = (await db.query<{ l: string }>("SELECT pg_current_wal_lsn() AS l")).rows[0].l;
  const t0 = performance.now();
  // ملحوظة: دفعات صغيرة بتشبه الـ traffic الحقيقي أكتر من INSERT واحد ضخم
  for (let i = 0; i < ROWS / BATCH; i++) {
    await db.query(`INSERT INTO ${table} SELECT ${fn}, (random()*1e5)::int, (random()*1e5)::int FROM generate_series(1, ${BATCH})`);
  }
  const ms = Math.round(performance.now() - t0);
  const wal = (await db.query<{ b: string }>("SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), $1::pg_lsn)::bigint AS b", [before])).rows[0].b;
  const s = (await db.query(`SELECT pg_size_pretty(pg_relation_size('${table}_pkey')) AS size, avg_leaf_density AS density, leaf_pages FROM pgstatindex('${table}_pkey')`)).rows[0];
  console.log(table, { rows: ROWS, ms, walMB: Math.round(Number(wal) / 1048576), ...s, ...(await indexIo(`${table}_pkey`)) });
}

// القراية الواقعية: آخر 1% اتكتب هو اللي بيتقرا أكتر (طلبات النهارده، مش بتوع 2019)
for (const table of ["orders_v4", "orders_v7"]) {
  const recent = (await db.query<{ id: string }>(`SELECT id FROM ${table} ORDER BY ctid DESC LIMIT ${Math.floor(ROWS / 100)}`)).rows;
  await db.query("SELECT pg_stat_reset()");
  const t0 = performance.now();
  for (let i = 0; i < 20_000; i++) {
    await db.query(`SELECT total_cents FROM ${table} WHERE id = $1`, [recent[(i * 7919) % recent.length].id]);
  }
  const ms = Math.round(performance.now() - t0);
  console.log("recent reads", table, { lookups: 20_000, ms, ...(await indexIo(`${table}_pkey`)) });
}
await db.end();

بالعامية

الـ UUID v4 فيه 122 bit عشوائيين. الـ collision مش مشكلة عملية، وأي machine تولّده من غير تنسيق، وعشان كده بقى الـ default. التكلفة بتيجي على الـ B-tree: كل insert بيروح لـ leaf page عشوائية. الصفحات بتتقسم في أي مكان فبتستقر على حوالي الثلثين مليانة بدل ما تبقى متروسة، والـ index كله بيفضل "سخن" بدل طرفه اليمين بس، وبعد كل checkpoint أول تعديل على كل صفحة بيكتب full-page image في الـ WAL.

قست ده على Postgres 18.4 حقيقي بـ shared_buffers قدها 32 MB، إعدادات durable، inserts في دفعات 10,000، وidx_blks_read من pg_statio_user_indexes عشان الـ buffer misses. الحجم والكثافة ثابتين في كل تشغيل. الـ insert time محتاج حرص: عند 200 ألف ومليون الفرق بيتغير من تشغيل للتاني (من حوالي 1.3 لـ 2.2 مرة) على Windows عليه ضغط والـ v4 اتشغل الأول، فماتستنتجش منهم كتير. عند 5 مليون الـ index أكبر من الـ buffer pool حوالي 6 مرات، وهنا الفرق بقى حقيقي: شغّلت الـ 5 مليون تاني والـ v7 الأول وطلعت نفس الصورة، 74 ثانية مقابل 23 ثانية، و2.74 مليون miss مقابل 17.7 ألف (storage engines بيشرح ميكانيكا الصفحات).

فين هستخدمه في شغلي؟ جدول events أو orders بيكتب كتير والـ PK فيه v4: الأعراض في production هتبقى WAL كبير، replication lag، و cache hit ratio نازل مع إن الـ traffic ثابت. قبل ما تكبّر الـ instance، بص على pgstatindex وidx_blks_read. الغلطة الشائعة إنك تختبر بـ 10 آلاف صف، تلاقي مفيش فرق، وتقرر إن الموضوع مبالغ فيه: الفرق مابيظهرش غير لما الـ index يبقى أكبر من الـ cache.
Interview question "Your UUID v4 primary key is hurting a write-heavy table. Explain why, and what would you change?" → Random inserts touch random leaf pages, so the index is about 69% full, the working set is the whole index, and checkpoints produce many full-page images. "الـ primary key الـ UUID v4 بيأذي جدول كتابته كتيرة. اشرح ليه وهتغيّر إيه؟" ← الـ inserts العشوائية بتلمس leaf pages عشوائية، فالـ index مليان حوالي 69% بس، والـ working set هو الـ index كله، والـ checkpoints بتطلّع full-page images كتير. استخدم ID مرتب بالوقت (v7) للصفوف الجديدة. تغيير الصفوف القديمة نادرًا ما يستاهل، لإن الصفوف الجديدة بتبدأ تتجمع على طول.

Part 3 — UUID v7, the new default 🟡 Intermediateالجزء 3 — الـ UUID v7 الـ default الجديد

English

UUID v7 (RFC 9562) keeps the 128-bit shape and the uuid column type but puts a 48-bit Unix millisecond timestamp first, then version and variant bits, then random. Sorting by value now means sorting by time, so the B-tree behaves like auto-increment while any machine can still generate IDs on its own.

Postgres 18 has uuidv7() built in, plus uuid_extract_version() and uuid_extract_timestamp(). The docs say the timestamp uses millisecond precision plus a sub-millisecond part. An optional shift interval moves the embedded time. In Node, the uuid package's v7() gives the same layout, and generating in the app means you know the ID before the insert, which helps with outbox rows and idempotent retries.

Two limits matter. Ordering is only monotonic inside one generator: across servers the order is only as good as their clocks, so a server 5 seconds behind writes IDs that sort before older ones. Never use v7 to decide "which event happened first" for anything that matters (see time and clocks). And the creation time is printed on the ID: anyone holding it can read when the row was made. That is usually fine for orders. It is not fine when the creation time is itself sensitive, such as a medical record or a user's signup date in a public profile: keep v7 as the private key and expose a separate random token.

For new tables, UUID v7 is the default choice unless you specifically need 64 bits.

  UUID v7 (128 bits)
  +----------------------------+------+----------+----+----------------+
  | unix_ts_ms (48)            | ver  | rand_a   | var| rand_b (62)    |
  |                            | (4)  | (12)     |(2) |                |
  +----------------------------+------+----------+----+----------------+
   sorts by time first          always 7           random tail
أول 48 bit هي الوقت بالـ millisecond، وبعدها 4 bits للـ version (دايمًا 7)، و12 bit في rand_a، و2 bits للـ variant، و62 bit عشوائيين في rand_b. ولإن الوقت في الأول، الترتيب بالقيمة هو نفسه الترتيب بالوقت.
import pg from "pg";
import { v4, v7, version } from "uuid";

const url = process.env.PG_URL;
if (!url) throw new Error("set PG_URL to a throwaway Postgres 18");
const db = new pg.Client({ connectionString: url });
await db.connect();

// (1) من جوه Postgres: الـ id نفسه شايل الوقت
const id = (await db.query<{ id: string }>("SELECT uuidv7() AS id")).rows[0].id;
const info = (await db.query("SELECT uuid_extract_version($1::uuid) AS version, uuid_extract_timestamp($1::uuid) AS created_at", [id])).rows[0];
console.log({ id, version: info.version, createdAt: info.created_at.toISOString() });

// (2) من جوه Node: نفس الـ layout من الـ npm package
const appId = v7();

Part 4 — ULID, size, and the JavaScript trap 🟡 Intermediateالجزء 4 — الـ ULID والحجم وفخ الـ JavaScript

English

ULID came before UUID v7 and solved the same problem: 48 bits of millisecond time and 80 bits of randomness, the same 128 bits, written as 26 characters of Crockford base32 (no I, L, O or U, to avoid reading mistakes). It sorts lexicographically as a string. monotonicFactory() increments the random part inside the same millisecond to keep order. Compared to v7 it is shorter and nicer in URLs and logs, but it is not an RFC standard and databases have no native type for it. In Postgres, store it in a uuid column as binary and only render it as text at the edge.

Width is the real decision. 128 bits vs 64 bits sounds small, but the ID is copied into the PK index, every foreign key column, and every index on those columns. The calculator below counts 8 copies per order across a billion rows. Storing it as text is the worst choice: pg_column_size says 40 bytes for a UUID as text against 16 for the uuid type, a real measurement on Postgres 18.

The JavaScript trap: JSON.parse turns numbers into doubles, and anything above 253−1 silently loses precision. A 64-bit Snowflake from a real system is well past that today. It breaks on the client, not the server, so it usually gets noticed as "the wrong order opened". The fix is to send 64-bit IDs as strings. node-pg already does this for you: a bigint column comes back as a string (real output: { id: '9007199254740993' } string).

Part 5 — Snowflake in BigInt 🟡 Intermediateالجزء 5 — Snowflake بالـ BigInt

English

Twitter's Snowflake packs an ID into 64 bits: 41 bits of milliseconds since a custom epoch, 10 bits of machine ID, and 12 bits of sequence, with the top bit left as zero so it fits a signed bigint. It sorts by time, generates without any network call, and is half the width of a UUID.

The ceiling is 4,096 IDs per millisecond per worker, because the sequence is 12 bits. After that the generator has to wait for the next millisecond. A single Node thread doing BigInt arithmetic reaches that ceiling in this run, and the counter shows how many milliseconds were exhausted. The 41-bit clock lasts 241 ms ≈ 69.7 years from your epoch, which is why you pick a recent epoch rather than 1970.

What you pay is operations. Every worker needs a unique machine ID, and a duplicated one produces duplicate IDs silently. And the clock is now part of correctness: if time goes backwards the generator must refuse, wait, or switch. The full treatment of clock rollback and multiple datacenters is in the ID generator case study. Here the code just refuses.

// الـ layout: bit للإشارة (صفر⁦) + 41⁩ وقت ⁦+ 10 machine + 12 sequence = 64⁩
// البداية بتاعتنا: أول يناير 2025، وده بيطوّل عمر الـ 41 bit
const EPOCH = 1_735_689_600_000n;
const MACHINE_BITS = 10n;
const SEQUENCE_BITS = 12n;
const MAX_MACHINE = (1n << MACHINE_BITS) - 1n;
const MAX_SEQUENCE = (1n << SEQUENCE_BITS) - 1n;

export class Snowflake {
  private lastMs = -1n;
  private sequence = 0n;
  exhausted = 0;
  private readonly machineId: bigint;
  private readonly now: () => bigint;

  constructor(machineId: bigint, now: () => bigint = () => BigInt(Date.now())) {
    if (machineId < 0n || machineId > MAX_MACHINE) throw new RangeError(`machineId must be 0..${MAX_MACHINE}`);
    this.machineId = machineId;
    this.now = now;
  }

  next(): bigint {
    let ms = this.now();
    // ملحوظة: الساعة رجعت لورا، فالأأمن نرفض بدل ما نكرر ⁦id (⁩الحلول الكاملة في درس الـ case)
    if (ms < this.lastMs) throw new Error(`clock moved backwards by ${this.lastMs - ms} ms`);
    if (ms === this.lastMs) {
      this.sequence = (this.sequence + 1n) & MAX_SEQUENCE;
      // لو الـ 4096 خلصوا في نفس الـ ms لازم نستنى الـ ms اللي بعدها
      if (this.sequence === 0n) {
        this.exhausted++;
        while (ms <= this.lastMs) ms = this.now();
      }
    } else {
      this.sequence = 0n;
    }
    this.lastMs = ms;
    return ((ms - EPOCH) << (MACHINE_BITS + SEQUENCE_BITS)) | (this.machineId << SEQUENCE_BITS) | this.sequence;
  }
}

export const decode = (id: bigint) => ({
  createdAt: new Date(Number((id >> (MACHINE_BITS + SEQUENCE_BITS)) + EPOCH)).toISOString(),
  machine: (id >> SEQUENCE_BITS) & MAX_MACHINE,
  sequence: id & MAX_SEQUENCE,
});

Part 6 — Ticket servers, blocks, and the final table 🟡 Intermediateالجزء 6 — الـ ticket servers والـ blocks والجدول النهائي

English

Flickr's "ticket server" is a dedicated database whose only job is issuing numbers: a table with one row and a REPLACE INTO that bumps auto_increment. They ran two of them, one odd and one even, so one could die without stopping the site. It's simple, the IDs fit 64 bits and sort roughly by time, but every ID now needs a network round trip to a central service.

The fix for the round trip is blocks (also called hi/lo): take 1,000 IDs at once and hand them out from memory. In my run that was 20 round trips instead of 20,000, about 160× more IDs per second. The price is gaps: a worker that crashes holding a block loses what it hadn't used, 863 values in the run below. Gaps are not duplicates. They are harmless for primary keys, and only a problem if the number has a legal meaning, such as an invoice sequence that must have no holes. A Postgres sequence has gaps anyway, because nextval never rolls back and the WAL logs ahead by 32 values.

Single point of failure analysis: one ticket server is a SPOF for all writes. Two servers with odd and even give availability at the cost of order, since one can pull ahead while the other is down. Blocks soften an outage too: workers keep running on what they already hold.

import pg from "pg";

// تحذير: شغّله على Postgres للتجربة بس
const url = process.env.PG_URL;
if (!url) throw new Error("set PG_URL to a throwaway Postgres");
const db = new pg.Client({ connectionString: url });
await db.connect();

await db.query("CREATE SEQUENCE order_ids");
await db.query("CREATE SEQUENCE order_id_blocks INCREMENT BY 1000 START WITH 1000");

// الـ hi/lo: روح مرة للـ DB تجيب نهاية block، والـ 1000 id بتوعه بتوزعهم من الـ memory
class BlockAllocator {
  private next = 0n;
  private end = 0n;
  roundTrips = 0;
  private readonly client: pg.Client;
  private readonly sequence: string;

  constructor(client: pg.Client, sequence: string) {
    this.client = client;
    this.sequence = sequence;
  }

  async id(): Promise<bigint> {
    if (this.next === this.end) {
      this.roundTrips++;
      const r = await this.client.query<{ v: string }>("SELECT nextval($1) AS v", [this.sequence]);
      const hi = BigInt(r.rows[0].v);
      this.next = hi - 999n;
      this.end = hi + 1n;
    }
    return this.next++;
  }
}

بالعامية

الـ "ticket server" بتاع Flickr هو database مخصصة شغلها الوحيد توزيع أرقام: جدول فيه صف واحد وREPLACE INTO بيزوّد الـ auto_increment. شغّلوا اتنين، واحد فردي وواحد زوجي، عشان لو واحد وقع الموقع يكمّل. بسيط، والـ IDs بتدخل في 64 bit ومترتبة تقريبًا بالوقت، بس كل ID بقى محتاج network round trip لخدمة مركزية.

الحل لموضوع الـ round trip هو الـ blocks (بيتقال لها hi/lo): خد 1,000 ID مرة واحدة ووزّعهم من الـ memory. في التجربة بقوا 20 round trip بدل 20,000، وعدد الـ IDs في الثانية زاد حوالي 160 مرة. التمن هو الـ gaps: worker مات وهو ماسك block بيضيّع اللي ماستخدمهوش، 863 رقم في التجربة. الـ gaps مش تكرار. مش مشكلة في الـ primary keys، بس مشكلة لو الرقم له معنى قانوني، زي تسلسل الفواتير اللي لازم يبقى من غير فجوات. وPostgres sequence عنده gaps أصلًا، لإن nextval مابيرجعش مع الـ rollback، والـ WAL بيسجل قدّام 32 قيمة.

تحليل الـ SPOF: ticket server واحد هو SPOF لكل الكتابة. اتنين بفردي وزوجي بيدّوك availability على حساب الترتيب، لإن واحد ممكن يسبق وهو التاني واقع. والـ blocks كمان بتخفف الـ outage: الـ workers بتكمّل على اللي في إيدها.

فين هستخدمه في شغلي؟ لو بتعمل bulk import لملايين products من Node: استخدم block allocator فوق nextval بدل round trip لكل صف. أما invoice_number اللي مصلحة الضرايب بتطلبه متتالي من غير فجوات، فلازم عدّاد في جدول بيتحدّث جوه نفس الـ transaction، لإن الـ sequence هيسيب فجوات. الغلطة الشائعة: استخدام sequence عادي لرقم الفاتورة القانوني.

Common mistakes · غلطات شائعة

❌ UUID stored as text

  id varchar(36) PRIMARY KEY
);
-- حجم القيمة 40 byte بالقياس
✅ The native type 
CREATE TABLE orders (
  id uuid PRIMARY KEY DEFAULT uuidv7()
);
-- حجم القيمة 16 byte بالقياس
بالعامية

❌ الـ varchar(36) بياخد 40 byte لكل نسخة، وده بيتكرر في الـ PK والـ foreign keys وكل index، وعلى مليار صف بـ 8 نسخ بيبقى 298 GiB بدل 119. ✅ نوع uuid بياخد 16 byte، وكمان المقارنة بتبقى أسرع، وDEFAULT uuidv7() بيدّيك ترتيب بالوقت على Postgres 18.

❌ الـ URL بالـ id المتتالي بيسرّب عدد الفواتير ويسهّل تجربة أرقام غيرك. ✅ الـ token الغامض بيشيل التخمين، بس لسه لازم تتأكد إن الفاتورة بتاعة الـ user نفسه: الـ ID الصعب مش بديل عن الـ authorization. وبنرجّع 404 مش 403 عشان ماتأكدش وجود الفاتورة أصلًا.

3. Fix the block allocator race 🔴 hard The BlockAllocator from Part 6 has a concurrency bug: under Promise.all with 5,000 calls, every call sees an empty block and fetches its own. Measure the round trips, then fix it so only one refill runs at a time.

Hint · تلميح Keep the in-flight refill as a shared promise, and re-check in a while loop after awaiting it.

Solution · الحل 
// تسلسل وهمي في الـ memory بدل Postgres، مع تأخير 1ms زي round trip
let hi = 0;
let trips = 0;
const nextBlock = async () => {
  trips++;
  await new Promise((r) => setTimeout(r, 1));
  hi += 1000;
  return BigInt(hi);
};

class Buggy {
  private next = 0n;
  private end = 0n;
  async id() {
    if (this.next === this.end) {
      const h = await nextBlock();
      this.next = h - 999n;
      this.end = h + 1n;
    }
    return this.next++;
  }
}

class Fixed {
  private next = 0n;
  private end = 0n;
  private refill: Promise<void> | null = null;
  async id() {
    while (this.next === this.end) {
      // الحل: refill واحد بس شغال، والباقي يستنوه
      this.refill ??= nextBlock()
        .then((h) => {
          this.next = h - 999n;
          this.end = h + 1n;
        })
        .finally(() => {
          this.refill = null;
        });
      await this.refill;
    }
    return this.next++;
  }
}

for (const [name, Alloc] of [["buggy", Buggy], ["fixed", Fixed]] as const) {
  hi = 0;
  trips = 0;
  const a = new Alloc();
  const ids = await Promise.all(Array.from({ length: 5000 }, () => a.id()));
  console.log(name, { ids: new Set(ids).size, roundTrips: trips });
}
buggy { ids: 5000, roundTrips: 5000 }
fixed { ids: 5000, roundTrips: 5 }

Cheat sheet · الخلاصة

  • Auto-increment is ideal on one database. Two databases collide, and the offset-and-step hack doesn't age well.
  • Sequential IDs leak volume and invite enumeration. Keep them internal.
  • UUID v4: random leaf inserts. Measured at 5M rows on Postgres 18: 196 vs 150 MB, 69% vs 90% density, about 3× slower inserts.
  • The difference shows up when the index is bigger than the cache. Test with real sizes.
  • UUID v7 is the default for new tables: time-ordered, generated anywhere, native uuid type, uuidv7() in Postgres 18.
  • v7 exposes creation time and is only monotonic inside one generator.
  • ULID: same 128 bits, 26 chars, Crockford base32. Store as binary.
  • 128 vs 64 bits: multiply by every copy in FKs and indexes. Never store as text.
  • JS: 64-bit IDs go in JSON as strings, or they silently change.
  • Snowflake: 41 + 10 + 12 bits, 4,096/ms per worker, about 69.7 years, needs unique machine IDs and a sane clock.
  • Blocks (hi/lo) trade gaps for far fewer round trips. Gaps are fine for keys, not for legal numbering.
بالعامية
  • الـ auto-increment ممتاز على database واحدة. مع اتنين بيخبطوا، وحيلة الـ offset والـ step مابتعيشش كتير.
  • الـ IDs المتتالية بتسرّب الحجم وبتسهّل الـ enumeration. خليها داخلية.
  • الـ UUID v4: inserts في leaves عشوائية. القياس عند 5 مليون صف على Postgres 18: 196 مقابل 150 MB، وكثافة 69% مقابل 90%، وinserts أبطأ حوالي 3 مرات.
  • الفرق بيظهر لما الـ index يبقى أكبر من الـ cache. اختبر بأحجام حقيقية.
  • الـ UUID v7 هو الـ default للجداول الجديدة: مرتب بالوقت، بيتولّد في أي مكان، نوع uuid الأصلي، وuuidv7() في Postgres 18.
  • الـ v7 بيكشف وقت الإنشاء، وترتيبه monotonic جوه generator واحد بس.
  • الـ ULID: نفس الـ 128 bit، 26 حرف، Crockford base32. خزّنه binary.
  • 128 مقابل 64 bit: اضرب في كل نسخة في الـ FKs والـ indexes. وماتخزّنش نص أبدًا.
  • في JS: الـ IDs الـ 64-bit تتبعت في الـ JSON كـ strings، وإلا هتتغير من غير ما تحس.
  • Snowflake: 41 + 10 + 12 bit، 4,096 في الـ ms لكل worker، حوالي 69.7 سنة، ومحتاج machine IDs مختلفة وساعة سليمة.
  • الـ blocks (hi/lo) بتبدّل الـ gaps بعدد round trips أقل بكتير. الـ gaps عادي للمفاتيح، مش للترقيم القانوني.
