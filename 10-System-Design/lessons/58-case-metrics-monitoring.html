Why this matters · ليه ده مهم

English

Every production system you run depends on a metrics pipeline, and during an incident it's often the only thing you trust. It's also an odd workload: almost pure writes, immutable data, reads that scan time ranges, and a cost driven by how many distinct series you create, not by how many points you store. That's why a general-purpose database is a poor fit and why one careless label can take the monitoring down. Lesson 39 covers the three pillars and lesson 40 covers SLOs and alert design. Here you design the system underneath them, and build its compression.

بالعامية

أي نظام بتشغّله في production معتمد على metrics pipeline، ووقت الـ incident غالبًا هي الحاجة الوحيدة اللي بتثق فيها. وهو كمان شغل غريب: كتابة تقريبًا كلها، data مابتتغيرش، قراية بتمسح فترات زمنية، والتكلفة بتيجي من عدد الـ series المختلفة مش من عدد النقاط. عشان كده الـ DB العادية مش مناسبة، وعشان كده label واحد غلط ممكن يوقّع الـ monitoring كله. درس 39 بيغطي الـ three pillars ودرس 40 بيغطي الـ SLOs وتصميم الـ alerts. هنا هتصمّم النظام اللي تحتهم، وتبني الـ compression بتاعه بإيدك.

English

Requirements with numbers. Functional: ingest samples, query a range with a step, evaluate alert rules, send notifications. Non-functional: 10k hosts × 1,000 series every 10 s means 10M active series and 1M points per second. Ingest must keep up continuously. Recent dashboards in under about 1 second. Alerting must survive partial failures of the system it watches. Retention: 15 days raw, 90 days at 1 minute, 2 years at 1 hour.

Estimates. A point is a timestamp and a float, 16 bytes. 1M points/s is 16 MB/s, or 1.38 TB/day raw. With the 1.84 bytes per point measured in Part 2 it's 159 GB/day. Prometheus's docs give "1-2 bytes per sample" for its own engine, so the estimate is in the right range. Disk write speed isn't the problem. The problem is 10M active series, each of which needs an in-memory head, an index entry and a slot in every query.

The shape of the workload. Writes are almost all appends to the present. Reads are ranges over time and are recent-heavy. Data never changes. That points to an append-optimized store partitioned by time, in the same family as the LSM engines in lesson 35, with a Gorilla-style encoding per series.

API and data model. A series is a metric name plus a label set, and any new label value is a new series. An inverted index maps a label pair to the series that have it, the way a search index does. Samples go into 2-hour chunks. A range query takes an expression, a start, an end and a step.

const SECONDS_PER_DAY = 86_400;

function metrics(i: { hosts: number; seriesPerHost: number; intervalSec: number; bytesRaw: number; bytesCompressed: number }) {
  const series = i.hosts * i.seriesPerHost;
  const pointsPerSec = series / i.intervalSec;
  const perDay = pointsPerSec * SECONDS_PER_DAY;
  return {
    series,
    pointsPerSec,
    pointsPerDay: perDay,
    rawTBPerDay: (perDay * i.bytesRaw) / 1e12,
    compressedTBPerDay: (perDay * i.bytesCompressed) / 1e12,
  };
}

المتطلبات بالأرقام. Functional: تستقبل samples، تعمل query على range بـ step، تقيّم alert rules، وتبعت notifications. Non-functional: 10 آلاف host × 1,000 series كل 10 ثواني يعني 10 مليون active series ومليون نقطة في الثانية. الـ ingest لازم يفضل ملاحق طول الوقت. الـ dashboards الحديثة في أقل من حوالي ثانية. الـ alerting لازم يعيش لو جزء من النظام اللي بيراقبه وقع. الـ retention: ‏15 يوم raw، 90 يوم بدقة دقيقة، وسنتين بدقة ساعة.

الحسابات. النقطة timestamp و float يعني 16 byte. مليون نقطة في الثانية يعني 16 MB/s أو 1.38 TB في اليوم خام. بالـ 1.84 byte للنقطة اللي قيسناها في الجزء 2 تبقى 159 GB في اليوم. docs بتاعة Prometheus بتقول "1-2 bytes per sample" لمحركها، فالتقدير في المدى الصح. سرعة الكتابة على الـ disk مش المشكلة. المشكلة هي الـ 10 مليون active series، كل واحدة محتاجة head في الـ memory و entry في الـ index ومكان في كل query.

شكل الشغل. الكتابة تقريبًا كلها append على الوقت الحالي. القراية ranges زمنية ومعظمها حديث. والـ data مابتتغيرش. ده بيودّيك لتخزين append-optimized متقسم بالوقت، من نفس عيلة محركات الـ LSM في درس 35، مع encoding على طريقة Gorilla لكل series.

الـ API والـ data model. الـ series هي اسم الـ metric مع مجموعة labels، وأي قيمة label جديدة تبقى series جديدة. فيه inverted index بيربط كل زوج label بالـ series اللي فيها، زي search index بالظبط. الـ samples بتتحط في chunks بتاعة ساعتين. والـ range query بياخد expression و start و end و step.

فين هستخدمه في شغلي؟ قبل ما تضيف metric جديدة في service عندك، احسب: عدد القيم المختلفة لكل label مضروب في بعض، مضروب في عدد الـ pods. histogram بـ 12 bucket و 20 route و 3 methods على 50 pod يبقى 36,000 series من metric واحدة. الرقم ده بيتحسب في دقيقة قبل الـ merge، وبيوفر incident.
Interview question "Why not just store this in Postgres?" Model answer: measure it. Rows cost 83.8 bytes per point with an index against 1.84 with time-series encoding, about 45× more here. Add per-row writes, vacuum and an index that grows with every point. A time-partitioned, append-only store avoids all of that.

Part 2 — Compression, real 🔴 Advancedالجزء 2 — الضغط، على حقيقي

English

Timestamps. Samples arrive on a schedule, so the delta between timestamps is nearly constant. Gorilla stores the delta of deltas: 0 when the interval didn't change, and that costs a single bit. The buckets from the VLDB 2015 paper are: 0 for no change, 10 and 7 bits for −63..64, 110 and 9 bits for −255..256, 1110 and 12 bits for −2047..2048, else 1111 and 32 bits.

Values. Neighbouring floats usually share sign, exponent and top mantissa bits, so XOR with the previous value gives mostly zeros. An identical value costs one bit. Otherwise a control bit says whether the meaningful bits fit inside the previous window, or whether a new window is written with 5 bits of leading-zero count and 6 bits of length.

Verified against the paper. It reports 1.37 bytes per point, a 12× reduction from 16 bytes, on two-hour blocks of Facebook's production data, with about 96% of timestamps in one bit, and 51% / 30% / 19% of values in the three control cases. The encoder below round-trips every point exactly. Measured on generated series:

  • A constant series like up: 0.33 bytes per point.
  • A counter: 2.05. An integer gauge in 4 KB pages: 1.31.
  • A CPU ratio rounded to 2 decimals: 5.36.
  • A noisy float such as a latency gauge: 7.20, only 2.2× better than raw.

A blended mix of 40% constant, 30% counters, 15% integer gauges, 10% CPU and 5% noisy floats gives 1.84. That mix is my assumption, and the paper's 1.37 depends on real data where half of values repeat. The lesson is that the compression ratio depends on your data. Noisy high-precision gauges barely compress, so don't publish extra decimals. Prometheus's chunks use the same delta-of-delta and XOR family, per its chunk format docs.

Against Postgres. On a real Postgres 18, 500,000 points take 52.2 bytes each in the heap and 83.8 with a B-tree on (series_id, ts). Against the paper's 1.37 that's 61×. Against this lesson's own 1.84 it's about 45×. Row headers, alignment and the index are the cost, and they exist for random updates you'll never do.

// الملف ده تنفيذ حقيقي لضغط Gorilla: delta-of-delta للوقت و XOR للقيم
export class BitWriter {
  private readonly bytes: number[] = [];
  private cur = 0;
  private used = 0;
  bitLength = 0;

  write(value: bigint, bits: number): void {
    for (let i = bits - 1; i >= 0; i--) {
      const bit = Number((value >> BigInt(i)) & 1n);
      this.cur = (this.cur << 1) | bit;
      this.bitLength++;
      if (++this.used === 8) {
        this.bytes.push(this.cur);
        this.cur = 0;
        this.used = 0;
      }
    }
  }

  finish(): Uint8Array {
    const out = [...this.bytes];
    if (this.used > 0) out.push(this.cur << (8 - this.used));
    return Uint8Array.from(out);
  }
}

export class BitReader {
  private pos = 0;
  private readonly data: Uint8Array;
  constructor(data: Uint8Array) { this.data = data; }

  read(bits: number): bigint {
    let v = 0n;
    for (let i = 0; i < bits; i++, this.pos++) {
      const byte = this.data[this.pos >> 3] ?? 0;
      v = (v << 1n) | BigInt((byte >> (7 - (this.pos & 7))) & 1);
    }
    return v;
  }
}

const buf = new DataView(new ArrayBuffer(8));
const floatToBits = (f: number): bigint => { buf.setFloat64(0, f); return buf.getBigUint64(0); };
const bitsToFloat = (b: bigint): number => { buf.setBigUint64(0, b); return buf.getFloat64(0); };

function leadingZeros(x: bigint): number {
  let n = 0;
  for (let mask = 1n << 63n; mask > 0n && (x & mask) === 0n; mask >>= 1n) n++;
  return n;
}
function trailingZeros(x: bigint): number {
  let n = 0;
  while (n < 64 && ((x >> BigInt(n)) & 1n) === 0n) n++;
  return n;
}

export type Stats = { tsOneBit: number; valSame: number; valReuse: number; valNew: number; points: number };
export const newStats = (): Stats => ({ tsOneBit: 0, valSame: 0, valReuse: 0, valNew: 0, points: 0 });

export class Encoder {
  private readonly w = new BitWriter();
  private readonly header: number;
  private prevT = 0;
  private prevDelta = 0;
  private prevBits = 0n;
  private prevLead = -1;
  private prevTrail = 0;
  private first = true;
  private readonly stats: Stats;

  constructor(blockStart: number, stats: Stats = newStats()) {
    this.header = blockStart;
    this.stats = stats;
  }

  add(ts: number, value: number): void {
    const w = this.w;
    this.stats.points++;
    const bits = floatToBits(value);
    if (this.first) {
      // أول نقطة: 14 bit للوقت من بداية الـ block، و 64 bit للقيمة من غير ضغط
      w.write(BigInt(ts - this.header), 14);
      w.write(bits, 64);
      this.first = false;
      this.prevDelta = ts - this.header;
      this.prevT = ts;
      this.prevBits = bits;
      return;
    }
    const delta = ts - this.prevT;
    const dod = delta - this.prevDelta;
    if (dod === 0) { w.write(0n, 1); this.stats.tsOneBit++; }
    else if (dod >= -63 && dod <= 64) { w.write(0b10n, 2); w.write(BigInt(dod + 63), 7); }
    else if (dod >= -255 && dod <= 256) { w.write(0b110n, 3); w.write(BigInt(dod + 255), 9); }
    else if (dod >= -2047 && dod <= 2048) { w.write(0b1110n, 4); w.write(BigInt(dod + 2047), 12); }
    else { w.write(0b1111n, 4); w.write(BigInt.asUintN(32, BigInt(dod)), 32); }
    this.prevDelta = delta;
    this.prevT = ts;

    const xor = bits ^ this.prevBits;
    this.prevBits = bits;
    if (xor === 0n) { w.write(0n, 1); this.stats.valSame++; return; }
    w.write(1n, 1);
    const lead = Math.min(leadingZeros(xor), 31);
    const trail = trailingZeros(xor);
    if (this.prevLead >= 0 && lead >= this.prevLead && trail >= this.prevTrail) {
      // نفس نافذة الـ bits اللي فاتت تكفي، فمش هنكتب طولها تاني
      const len = 64 - this.prevLead - this.prevTrail;
      w.write(0n, 1);
      w.write(xor >> BigInt(this.prevTrail), len);
      this.stats.valReuse++;
    } else {
      const len = 64 - lead - trail;
      w.write(1n, 1);
      w.write(BigInt(lead), 5);
      // الطول 64 مش بيتساع في 6 bits، فبيتكتب صفر
      w.write(BigInt(len === 64 ? 0 : len), 6);
      w.write(xor >> BigInt(trail), len);
      this.prevLead = lead;
      this.prevTrail = trail;
      this.stats.valNew++;
    }
  }

  get bitLength() { return this.w.bitLength; }
  finish() { return this.w.finish(); }
}

export function decode(data: Uint8Array, blockStart: number, count: number): { ts: number; value: number }[] {
  const r = new BitReader(data);
  const out: { ts: number; value: number }[] = [];
  let delta = Number(r.read(14));
  let t = blockStart + delta;
  let bits = r.read(64);
  out.push({ ts: t, value: bitsToFloat(bits) });
  let lead = 0;
  let trail = 0;
  while (out.length < count) {
    let dod = 0;
    if (r.read(1) === 1n) {
      if (r.read(1) === 0n) dod = Number(r.read(7)) - 63;
      else if (r.read(1) === 0n) dod = Number(r.read(9)) - 255;
      else if (r.read(1) === 0n) dod = Number(r.read(12)) - 2047;
      else dod = Number(BigInt.asIntN(32, r.read(32)));
    }
    delta += dod;
    t += delta;
    if (r.read(1) === 1n) {
      if (r.read(1) === 1n) {
        lead = Number(r.read(5));
        let len = Number(r.read(6));
        if (len === 0) len = 64;
        trail = 64 - lead - len;
      }
      const len = 64 - lead - trail;
      bits ^= r.read(len) << BigInt(trail);
    }
    out.push({ ts: t, value: bitsToFloat(bits) });
  }
  return out;
}

export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

function compress(gen: () => (i: number) => number, stats: Stats, jitter: boolean) {
  const f = gen();

  const points: { ts: number; value: number }[] = [];

    const ts = t + (jitter && rnd() < 0.02 ? 1 : 0);

    enc.add(ts, value);

بالعامية

الوقت. الـ samples بتيجي على جدول، فالفرق بين الـ timestamps تقريبًا ثابت. Gorilla بتخزن فرق الفرق (delta of deltas): صفر لو الفترة ماتغيرتش، وده بياخد bit واحد. الـ buckets من paper بتاع VLDB 2015: 0 لو مفيش تغيير، 10 و7 bits لـ −63..64، 110 و9 bits لـ −255..256، 1110 و12 bits لـ −2047..2048، وغير كده 1111 و32 bit.

القيم. الأرقام الجنب بعض غالبًا نفس الـ sign والـ exponent وأول bits من الـ mantissa، فالـ XOR مع القيمة اللي قبلها بيطلع أصفار كتير. القيمة المتكررة بتاخد bit واحد. غير كده فيه control bit بيقول هل الـ bits المهمة جوه النافذة اللي فاتت، ولا هنكتب نافذة جديدة بـ 5 bits لعدد الأصفار و6 bits للطول.

اتأكدنا من الـ paper. بيقول 1.37 byte للنقطة، يعني 12× أقل من 16 byte، على blocks بتاعة ساعتين من data حقيقية عند Facebook، وحوالي 96% من الـ timestamps في bit واحد، و51% / 30% / 19% من القيم في حالات الـ control التلاتة. الـ encoder هنا بيرجّع كل نقطة زي ما هي بالظبط. على series مولّدة طلع:

  • series ثابتة زي up: ‏0.33 byte للنقطة.
  • counter: ‏2.05. و int gauge بوحدات 4 KB: ‏1.31.
  • CPU ratio مقرّب لرقمين عشريين: 5.36.
  • float عشوائي زي latency gauge: ‏7.20، يعني أحسن من الخام بـ 2.2× بس.

الـ mix بتاع 40% ثابت و30% counters و15% int gauges و10% CPU و5% float عشوائي طلّع 1.84. الـ mix ده افتراض مني، ورقم الـ 1.37 معتمد على data حقيقية نصها متكرر. الدرس هنا: نسبة الضغط بتعتمد على الـ data بتاعتك. الـ gauges العشوائية بدقة عالية تقريبًا مش بتتضغط، فماتبعتش كسور زيادة مش محتاجها. الـ chunks في Prometheus بتستخدم نفس عيلة delta-of-delta و XOR، حسب docs شكل الـ chunks.

مقارنة بـ Postgres. على Postgres 18 حقيقي، 500,000 نقطة بتاخد 52.2 byte للنقطة في الـ heap و83.8 مع B-tree على (series_id, ts). مقارنة بـ 1.37 بتاعة الـ paper ده 61×، ومقارنة بالـ 1.84 بتاعتنا حوالي 45×. الـ row headers والـ alignment والـ index هم التكلفة، وموجودين عشان random updates إنت عمرك ما هتعملها.

فين هستخدمه في شغلي؟ لو بتبعت metric زي order_value_egp بكسور كتير، قرّبها: قيمة مقرّبة بتتضغط أحسن بكتير، وفي الـ dashboard مفيش حد محتاج 15 رقم عشري. والغلطة الشائعة: تحفظ metrics في جدول Postgres عادي "عشان بسيط"، وبعد شهور الجدول يبقى 90% من حجم الـ DB والـ vacuum يوقّع الـ API.
Trade-off: block length and decode cost Longer blocks compress better, but a read has to decode from the start of the block. The paper found that blocks beyond two hours give diminishing returns. That's the same trade-off as a sparse index: storage against read work.
الـ blocks الأطول بتتضغط أحسن، بس القراية لازم تفك من أول الـ block. الـ paper لقى إن أكتر من ساعتين الفايدة بتقل. ده نفس trade-off بتاع الـ sparse index: تخزين مقابل شغل وقت القراية.

Part 3 — Downsampling 🔴 Advancedالجزء 3 — الـ downsampling

English

Keeping 10 s data for 2 years is wasteful, because a chart over a year can't show it anyway. Downsampling replaces raw points with rollups, 10 s to 1 m to 1 h, and each rollup stores min, max, sum and count, not an average. The average is sum/count, which merges correctly across windows. In the run, the average and the max rebuilt from the 1 h tier were identical to the raw values. Build 1 h from 1 m, not from raw. Averaging averages is wrong when counts differ: (10 + 90) / 2 = 50 against a true 10.8.

Percentiles are worse: you cannot average them. A p99 isn't additive. I built 100 hosts with one slow host and compared the true fleet p99 with the average of per-host p99s and with a merged histogram:

  • When the slow host gets 0.1% of traffic: true 56.3 ms, average of p99s 78.0, histogram 70.7.
  • When the slow host gets 50% of traffic: true 1,862 ms, average of p99s 76.8, histogram 2,311. The average is 24× too low and would keep you asleep during an outage.

The fix is to keep the histogram buckets in the rollup. Bucket counts are additive across hosts and time. The cost is resolution: a bucket's width bounds the error, as the 24% overshoot in that wide bucket shows, so put bucket edges around your SLO. Prometheus's docs make the same point: you can't aggregate quantiles.

Route queries by range. A query layer picks the coarsest tier with enough points for the chart, as long as the data's age is within that tier's retention. Storage per tier, using the same encoder on the same mix (replication not included): raw at 10 s costs 17.6 KB per series per day, 1 m costs 10.0 KB, and 1 h costs 235 bytes. So 1-minute rollups save less than you'd expect, because four fields per point are a lot of fields, while 1-hour rollups are about 75× cheaper than raw. Storing everything raw for 2 years is 129 TB and about $10,300/month on SSD, and the three tiers together are 13.3 TB and about $460/month. The prices are assumptions (about $0.08/GB-month SSD, $0.023 S3 from secondary sources) and exclude requests and egress.

type Bucket = { min: number; max: number; sum: number; count: number };
const newBucket = (): Bucket => ({ min: Infinity, max: -Infinity, sum: 0, count: 0 });
const add = (b: Bucket, v: number) => { b.min = Math.min(b.min, v); b.max = Math.max(b.max, v); b.sum += v; b.count++; };
const merge = (a: Bucket, b: Bucket) => { a.min = Math.min(a.min, b.min); a.max = Math.max(a.max, b.max); a.sum += b.sum; a.count += b.count; };

const rnd = mulberry32(99);
// يوم واحد من series بـ 10 ثواني: 8640 نقطة

for (let i = 0; i < 8640; i++) raw.push({ ts: i * 10, v: 20 + rnd() * 30 + (i % 360 === 0 ? 400 : 0) });

function rollup(points: { ts: number; v: number }[], step: number): Map<number, Bucket> {
  const out = new Map<number, Bucket>();
  for (const p of points) {
    const k = p.ts - (p.ts % step);
    if (!out.has(k)) out.set(k, newBucket());
    add(out.get(k)!, p.v);
  }
  return out;
}

Interview question "How do you keep percentiles after downsampling?" Model answer: you don't keep the percentile value, you keep the distribution. Store histogram bucket counts in each tier, since counts add across hosts and windows. The price is bucket-width error, so choose buckets around the SLO.
"إزاي تحتفظ بالـ percentiles بعد الـ downsampling؟" الإجابة النموذجية: مابتحتفظش بقيمة الـ percentile، بتحتفظ بالتوزيع. خزّن عدد كل histogram bucket في كل طبقة، لأن الأعداد بتتجمع عبر الـ hosts والفترات. التمن هو خطأ عرض الـ bucket، فاختار الـ buckets حوالين الـ SLO.

Part 4 — Pull vs push 🔴 Advancedالجزء 4 — الـ pull مقابل الـ push

English

Pull is what Prometheus does: the monitoring system scrapes /metrics from each target. The important side effect is that a failed scrape records up=0, so the system knows the difference between "no data" and "dead target". In the run, a real @prometheus-io/client endpoint was scraped three times and the counter moved 5, 7, 9. Stopping the service gave up=0 straight away. The text format averages 64 bytes per sample here, so 1M samples/s is about 64 MB/s on the wire, far more than the 1.84 MB/s stored after compression.

Push suits things that can't be scraped. A job alive for 80 ms with a 1-second scrape interval is visible at best 8% of the time, and the batch job's result would be lost. Pushing on exit works: the receiver got 1200 from the Monday job. But the crashed Tuesday job sent nothing, and that looks exactly like a job that didn't run. And the receiver keeps the last value forever: Prometheus's docs warn that the Pushgateway never forgets series and is a single point of failure, and recommend it only for service-level batch jobs.

Where to aggregate. Summing 10,000 series over 360 steps at query time read 3.6M points in ≈10 ms in this in-memory model. Reading a pre-aggregated series read 360. Aggregating at ingest (recording rules) makes dashboards cheap, at the cost of per-host drill-down unless you keep the raw series too. Aggregate at ingest for the expensive dashboards and alert rules you know you'll need, and keep raw for the unknown incident.

Part 5 — Cardinality & alerts 🔴 Advancedالجزء 5 — الـ cardinality والـ alerts

English

Cardinality explosion is the failure that takes monitoring systems down. A series is the name plus the label values, so someone adding user_id as a label turns one metric into one series per user. Series cost memory, index and query time forever, and points are nearly free. Ingest therefore needs a hard per-tenant limit on new series. The run floods one tenant with 200,000 unique user_id values. Without a limit it creates 200,050 series and uses ≈261 MB in the model. With a limit of 1,000 it rejects 199,050 new series and uses ≈1 MB. Existing series keep working, and another tenant isn't affected. Rejecting new series and keeping the old ones matters, because the dashboards people depend on stay alive.

The alert evaluator. A rule runs on a schedule. Its state machine is inactive, then pending when the condition first holds, then firing once it has held for the whole for duration, then resolved when it clears. That for is what makes a 2-minute blip harmless. In the virtual-time run, the blip at minutes 2 to 4 reached pending and went back silently, while the real problem at minute 10 became firing at minute 15 and resolved at 18. Lesson 40 explains why burn-rate alerts are better than fixed thresholds.

After the rule fires, a separate component does the routing. Two Prometheus replicas send identical alerts for high availability, so the same alert arrives twice and dedup by fingerprint removes the copies: 80 became 40. A network switch dying takes 40 hosts with it, so grouping by alert name and cluster turns 40 pages into one notification. That is what Alertmanager does, along with silences and inhibition. It's not run here, so its config below is labelled.

Monitoring the monitor. If the alerting pipeline is down, nothing tells you. A dead man's switch is an alert that always fires, sent to an external service that pages if the signal stops. In the simulation a monitor dying at 600 s is paged at 750 s, 150 s later. That delay is the timeout you chose.

// الملف ده بيوقف فيضان labels: كل tenant ليه حد أقصى من الـ series
// لازم تشغّله بـ node --expose-gc، والسيناريو التاني بـ node --expose-gc p5-cardinality.ts limit
type Labels = Record<string, string>;
const seriesKey = (name: string, labels: Labels) =>
  name + "{" + Object.keys(labels).sort().map((k) => `${k}="${labels[k]}"`).join(",") + "}";

class Ingest {
  private readonly tenants = new Map<string, Map<string, Float64Array>>();
  accepted = 0;
  rejected = 0;
  private readonly limit: number;
  constructor(limit: number) { this.limit = limit; }

  push(tenant: string, name: string, labels: Labels, value: number): boolean {
    let series = this.tenants.get(tenant);
    if (!series) { series = new Map(); this.tenants.set(tenant, series); }
    const key = seriesKey(name, labels);
    let buf = series.get(key);
    if (!buf) {
      // ده الفحص الوحيد المهم: series جديدة بعد الحد مترفوضة، والموجودة تفضل شغالة
      if (series.size >= this.limit) { this.rejected++; return false; }
      buf = new Float64Array(120);
      series.set(key, buf);
    }
    buf[0] = value;
    this.accepted++;
    return true;
  }
  seriesOf(tenant: string) { return this.tenants.get(tenant)?.size ?? 0; }
}

  (globalThis as any).gc?.();
  const m = process.memoryUsage();
  return Math.round((m.heapUsed + m.arrayBuffers) / 1e6);
};

// الملف ده alert evaluator بوقت افتراضي: pending ثم firing ثم resolved، و dedup و grouping
// تنبيه: دي simulation بوقت افتراضي، مش Prometheus ولا Alertmanager
type State = "inactive" | "pending" | "firing";
type Alert = { name: string; labels: Record<string, string> };
type Rule = { name: string; forSec: number; condition: (value: number) => boolean };

class Evaluator {
  private readonly state = new Map<string, { s: State; since: number }>();
  private readonly rule: Rule;
  constructor(rule: Rule) { this.rule = rule; }

  // كل evaluation بترجع التغييرات بس، مش الحالة كلها
  evaluate(t: number, series: Map<string, number>): { key: string; to: State | "resolved" }[] {
    const out: { key: string; to: State | "resolved" }[] = [];
    for (const [key, v] of series) {
      const cur = this.state.get(key) ?? { s: "inactive" as State, since: t };
      if (this.rule.condition(v)) {
        if (cur.s === "inactive") { this.state.set(key, { s: "pending", since: t }); out.push({ key, to: "pending" }); }
        else if (cur.s === "pending" && t - cur.since >= this.rule.forSec) { this.state.set(key, { s: "firing", since: t }); out.push({ key, to: "firing" }); }
      } else if (cur.s === "firing") {
        this.state.set(key, { s: "inactive", since: t });
        out.push({ key, to: "resolved" });
      } else if (cur.s === "pending") {
        // الـ blip الأقصر من for بيرجع inactive من غير ما يبعت حاجة
        this.state.set(key, { s: "inactive", since: t });
      }
    }
    return out;
  }
}

بالعامية

انفجار الـ cardinality هو العطل اللي بيوقّع أنظمة الـ monitoring. الـ series هي الاسم مع قيم الـ labels، فلو حد ضاف user_id كـ label، الـ metric الواحدة بقت series لكل مستخدم. الـ series بتكلف memory و index ووقت query على طول، والنقط نفسها تقريبًا ببلاش. عشان كده الـ ingest لازم يبقى عنده حد صارم لكل tenant على الـ series الجديدة. التجربة غرّقت tenant بـ 200,000 قيمة user_id مختلفة. من غير حد بيعمل 200,050 series وبياكل ≈261 MB في الـ model. بحد 1,000 بيرفض 199,050 series جديدة وبياكل ≈1 MB. الـ series الموجودة بتفضل شغالة، والـ tenant التاني مابيتأثرش. وده مهم: ترفض الجديد وتخلي القديم عشان الـ dashboards اللي الناس معتمدة عليها تفضل عايشة.

الـ alert evaluator. الـ rule بتشتغل على جدول. حالتها: inactive، بعدين pending لما الشرط يتحقق أول مرة، بعدين firing لما يفضل متحقق طول مدة الـ for، بعدين resolved لما يخلص. الـ for ده اللي بيخلي الـ blip بتاع دقيقتين مش بيعمل مشكلة. في الـ run بوقت افتراضي، الـ blip من دقيقة 2 لـ 4 وصل pending ورجع من غير صوت، والمشكلة الحقيقية عند دقيقة 10 بقت firing عند دقيقة 15 و resolved عند 18. درس 40 بيشرح ليه الـ burn-rate alerts أحسن من الحدود الثابتة.

بعد ما الـ rule تشتغل فيه component تاني بيعمل الـ routing. نسختين Prometheus بيبعتوا نفس الـ alerts عشان الـ availability، فالـ alert بيوصل مرتين، والـ dedup بالـ fingerprint بيشيل التكرار: 80 بقوا 40. switch واحد يموت بياخد معاه 40 host، فالـ grouping حسب اسم الـ alert والـ cluster بيحوّل 40 page لـ notification واحدة. ده اللي Alertmanager بيعمله، ومعاه الـ silences والـ inhibition. هو مش متشغّل هنا، فالـ config اللي تحت متعلّم عليه.

مراقبة الـ monitor نفسه. لو pipeline الـ alerting واقع، محدش هيقولك. الـ dead man's switch هو alert شغال دايمًا، بيروح لـ service خارجية بتعمل page لو الإشارة وقفت. في الـ simulation، monitor مات عند 600 ثانية وجه الـ page عند 750، يعني بعد 150 ثانية. التأخير ده هو الـ timeout اللي إنت اخترته.

فين هستخدمه في شغلي؟ في code review لأي labels: { user: req.user.id } أو path: req.url: ارفضها فورًا، واستخدم route pattern زي /orders/:id. ولو عندك multi-tenant، حط limit لكل tenant في الـ ingest عشان tenant واحد غلطان مايوقّعش الباقيين. والغلطة الشائعة: alert على رقم من غير for، فالـ on-call بيتصحى على كل spike لمدة دقيقة واحدة.

Part 6 — Trade-offs & review 🔴 Advancedالجزء 6 — الموازنات والمراجعة

English

One Prometheus or a distributed system. A single Prometheus keeps local data for 15 days by default and handles a lot before it needs help. Start there, with a pair of identical replicas for availability. When you outgrow one box or need retention beyond local disk, the usual choices, none of them run here, are Thanos (a sidecar that ships blocks to object storage and a global query layer) and Grafana Mimir (a horizontally scalable, multi-tenant backend that receives data over remote write). Long-term storage lives in an object store because compressed blocks are immutable, which suits it, as covered in lesson 15.

What breaks first at 10×. Disk is fine: 1.6 TB per day compressed. The first failure is active series in memory. My JS model of a head block costs ≈735 bytes per series, so 100M series is ≈74 GB before any index. A real engine differs, so measure yours, but the law holds: memory scales with active series, not with points. Next comes the 50 shards and the queries that fan out to them. Then the churn from pods with new names creating new series on every deploy, because series that stop reporting still occupy the index until the block is compacted away. Finally the scrape wire volume, about 640 MB/s of text at 10×.

What the interviewer looks for. Write-heavy reasoning from numbers, a time-partitioned store with compression, downsampling that keeps distributions, cardinality as the first-class risk, and an alerting pipeline that can survive failure. Red flags: storing raw rows in a general-purpose DB, averaging percentiles, unlimited labels, and no plan for when the monitoring itself is down.

2. A reset-aware counter increase 🟡 medium A counter drops to 0 when its process restarts. Given scrapes [100, 130, 170, 5, 40, 90], the naive last - first gives −10. Write increase(values) that detects the reset and returns the true increase. Then explain why a downsampled counter needs this too.

Solution · الحل 
// الحل ده بيحسب increase صح لـ counter حتى لو الـ process عمل restart والقيمة صفّرت
export function increase(values: number[]): number {
  let total = 0;
  for (let i = 1; i < values.length; i++) {
    const delta = values[i] - values[i - 1];
    // لو القيمة نزلت يبقى فيه reset، فالقيمة الجديدة كلها زيادة
    total += delta >= 0 ? delta : values[i];
  }
  return total;
}

const scrapes = [100, 130, 170, 5, 40, 90];
console.log("naive last - first:", scrapes.at(-1)! - scrapes[0]);
console.log("reset-aware increase:", increase(scrapes));
naive last - first: -10
reset-aware increase: 160
الزيادات: 30 + 40 + (الـ reset، القيمة الجديدة 5) + 35 + 50 = 160. عند الـ downsampling، أي rollup بيحسب sum عادي للـ counter بيبقى رقم مالوش معنى، فلازم نخزن الزيادة المحسوبة مع مراعاة الـ resets، وده اللي أنظمة زي Thanos بتعمله في طبقاتها.

Solution · الحل 
// الحل ده بيطلّع أنهي label هو سبب انفجار الـ cardinality
type Labels = Record<string, string>;

export function offenders(series: Labels[], top = 3): [string, number][] {
  const distinct = new Map<string, Set<string>>();
  for (const s of series) {
    for (const [k, v] of Object.entries(s)) {
      if (!distinct.has(k)) distinct.set(k, new Set());
      distinct.get(k)!.add(v);
    }
  }
  return [...distinct.entries()].map(([k, set]) => [k, set.size] as [string, number]).sort((a, b) => b[1] - a[1]).slice(0, top);
}

const series: Labels[] = [];
for (let i = 0; i < 20_000; i++) series.push({ route: `/r${i % 40}`, status: String(200 + (i % 5)), user_id: `u-${i}` });
console.log(offenders(series));
[ [ 'user_id', 20000 ], [ 'route', 40 ], [ 'status', 5 ] ]
user_id عنده 20,000 قيمة مقابل 40 و 5، فهو السبب. الـ ingest ممكن يعمل drop للـ label ده تلقائيًا (زي relabeling) أو يرفض الـ series الجديدة ويبلّغ صاحب الـ service بالاسم، بدل ما الـ limit يبقى رقم غامض.

Cheat sheet · الخلاصة

  • 10k hosts × 1,000 series / 10 s = 10M series, 1M points/s, 1.38 TB/day raw, about 159 GB/day compressed.
  • Time-series data is write-heavy, immutable and recent-heavy: partition by time, append only.
  • Gorilla: delta-of-delta timestamps (one bit when regular), XOR values (one bit when unchanged). Paper: 1.37 B/point. Measured here: 0.33 constant, 7.20 noisy float, 1.84 on an assumed mix. Your data decides.
  • Postgres rows: 83.8 B/point with an index, about 45× this lesson's encoded size.
  • Rollups keep min, max, sum, count plus histogram buckets. Never store an average of averages or an average of percentiles (24× wrong in the run).
  • Route queries to the coarsest tier with enough points. Tiers saved about 22× in storage cost here against keeping raw for 2 years.
  • Pull gives up=0 and simple debugging. Push suits short jobs, and silence on push looks like idle. Pushgateway never forgets.
  • Aggregate at ingest for known expensive queries, keep raw for the unknown incident.
  • Cardinality is the top risk: per-tenant limit on new series, reject new and keep existing, route patterns instead of raw URLs.
  • Alert states: inactive → pending → firing → resolved. for filters blips. Then dedup, group, route.
  • Monitor the monitor with a dead man's switch. At 10×, active-series memory breaks first, disk last.
  • Start with Prometheus + replica. Thanos or Mimir when you outgrow it, with blocks on object storage.

  • الـ time-series كتابة تقريبًا كلها، ومابتتغيرش، والقراية على الحديث: قسّم بالوقت و append بس.
