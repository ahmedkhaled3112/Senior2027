Why this matters · ليه ده مهم

English

Most of what people see of your work, they see in writing, and usually they weren't in the room. A PR description, a commit message, a decision summary or a chat message gets read more often than it gets written, sometimes by you six months later trying to work out why a timeout is 11 seconds. Weak writing costs other people time every time it's read. It also comes up in interviews, in questions like "How do you make your PRs easy to review?"

Nothing in this lesson needs talent. Each part is a fixed shape you can fill in.

About the examples. The Orders team from lesson 01 is back: Mona (product manager), Hany (engineering manager), Karim (mid-level engineer), Salma (junior engineer), Nour (infra engineer) and Yasmin (support lead). The team, names and numbers in the scenarios are invented for teaching, and the Mid-versus-Senior contrasts are teaching patterns, not measurements of real people.

بالعامية

معظم اللي الناس بتشوفه من شغلك بتشوفه مكتوب، وغالبًا مكانوش موجودين وقتها. الـ PR description والـ commit message وملخص القرار ورسالة الـ chat بيتقروا أكتر ما بيتكتبوا، وساعات اللي بيقرا هو إنت بعد 6 شهور وبتحاول تفهم ليه الـ timeout ده 11 ثانية. والكتابة الضعيفة بتاخد من وقت الناس كل مرة تتقرا فيها. وبتيجي كمان في الـ interviews، في أسئلة زي «إزاي بتخلي الـ PRs بتاعتك سهلة في الـ review؟».

مفيش حاجة في الدرس ده محتاجة موهبة. كل جزء شكل ثابت تملاه.

عن الأمثلة. فريق الـ Orders بتاع الدرس 01 راجع تاني: منى (product manager)، هاني (engineering manager)، كريم (mid-level engineer)، سلمى (junior engineer)، نور (infra engineer)، وياسمين (support lead). الفريق والأسامي والأرقام في المواقف دي متألفة عشان الشرح، ومقارنات الـ Mid والـ Senior أنماط للتعليم، مش قياس لناس حقيقيين.

Part 1 — The PR description 🟢 Basicالجزء 1 — الـ PR description

English

The situation. A 480-line PR titled "fix webhook" lands in the review queue. It stops duplicate payment webhooks from creating duplicate rows, but the description is empty.

What a mid-level engineer does. Leaves it empty. The reviewer reverse-engineers the purpose from the diff, asks in comments, and can't test it without asking how.

What a senior does. Writes five things: what changed, why, how to test it, the evidence it works, and what's deliberately not in this PR. The title says what the change does: "Dedupe payment webhooks by provider event id".

Why the second works. The description is read by the reviewer now and by someone running git blame later. Google's published guidance calls "Fix bug" an inadequate description and says one should explain what is changing and why. GitHub's guidance says not to assume familiarity with the history and to be explicit about what feedback you want. "Not in this PR" stops a reviewer from spending comments on something you've already split out. GitHub picks up a template from .github/pull_request_template.md, so the shape is there every time.

<!-- Keep it short. Delete what doesn't apply: a typo fix needs one line. -->

## What
<!-- What changes, in a sentence or two. Where should the reviewer start? -->

## Why
<!-- The problem and ticket link. Don't assume readers know the history. -->

## How to test
<!-- Steps a reviewer can run, and what they should see. -->

## Evidence
<!-- Logs, screenshots, query output, numbers. -->

## Not in this PR
<!-- Related work left out on purpose, so nobody reviews for it. -->
# Dedupe payment webhooks by provider event id

## What
`payment-webhook` now inserts with `ON CONFLICT (provider_event_id) DO NOTHING`, so a repeated delivery changes nothing and still answers 200. A migration moves the 61 existing duplicate rows to `payments_duplicates` and adds a unique index on `payments.provider_event_id`.

Start with `src/payments/webhook.ts`. Most of the 480 lines are the migration, its test and fixtures. I mainly want eyes on the conflict handling.

## Why
The provider resends a webhook when our 200 arrives late. Each resend created another `payments` row and a second invoice email. 37 customers got double emails last week (ORD-1482).

## How to test
1. `npm run db:migrate`
2. Run this twice: `npm run webhook:replay -- fixtures/payment-succeeded.json`
3. Expect a 200 both times, and this query to return 1:
   `SELECT count(*) FROM payments WHERE provider_event_id = 'evt_test_1';`

## Evidence
    14:02:11 info payment-webhook event=evt_test_1 result=inserted status=200
    14:02:13 info payment-webhook event=evt_test_1 result=duplicate status=200

## Not in this PR
- Retry policy for the `invoice-pdf` queue: separate PR.
- Apology to the 37 customers: Mona and Yasmin have it (ORD-1490).

 WITH a description (illustrative)

 Mon 10:00  PR with what, why, how to test, evidence, not in this PR
 Mon 16:00  reviewer follows the steps, leaves one comment
 Tue 10:00  fixed, approved and merged
 6 months   git blame -> the PR -> the reason is written there
نفس الـ PR مرتين، والمواعيد للتوضيح بس. من غير description: اتفتح الاتنين الصبح، والـ reviewer مش فاهم بيصلّح إيه فسابه، وسأل التلات، والرد جه بعدها بأربع ساعات، والأربع جرّبه غلط، واتعمله merge الأربع بعد الضهر. وبعد 6 شهور الـ git blame بيوصّلك لـ "fix webhook" ومحدش فاكر ليه. بالـ description: اتفتح الاتنين، والـ reviewer مشي على الخطوات وساب comment واحد، واتعمله merge التلات الصبح. وبعد 6 شهور الـ git blame بيوصّلك للـ PR والسبب مكتوب فيه.
بالعامية

الموقف. PR فيه 480 سطر وعنوانه "fix webhook" نزل في الـ review queue. هو بيمنع الـ payment webhooks المتكررة من إنها تعمل صفوف متكررة، بس الـ description فاضي.

الـ Mid بيعمل إيه. بيسيبه فاضي. الـ reviewer بيحاول يفهم الهدف من الـ diff، ويسأل في الـ comments، ومش عارف يختبره من غير ما يسأل إزاي.

الـ Senior بيعمل إيه. بيكتب 5 حاجات: إيه اللي اتغير، وليه، وإزاي تختبره، والدليل إنه شغال، وإيه اللي مش في الـ PR ده عن قصد. والعنوان بيقول التغيير بيعمل إيه: "Dedupe payment webhooks by provider event id".

ليه التانية بتنجح. الـ description بيقراه الـ reviewer دلوقتي وحد بيعمل git blame بعدين. الإرشادات اللي Google ناشراها بتقول إن "Fix bug" وصف مش كفاية، وإن الوصف لازم يشرح إيه اللي بيتغير وليه. وإرشادات GitHub بتقول متفترضش إن القارئ عارف التاريخ، وقول صراحة إنت عايز feedback على إيه. و«مش في الـ PR ده» بتمنع الـ reviewer يضيّع comments على حاجة إنت فصلتها خلاص. وGitHub بياخد الـ template من .github/pull_request_template.md، فالشكل بيبقى موجود كل مرة.

الـ template بالعامية: كل قسم فيه تعليق بيقول تكتب إيه: «إيه» (التغيير في جملة أو اتنين والـ reviewer يبدأ منين)، «ليه» (المشكلة ولينك الـ ticket)، «إزاي تختبره» (خطوات يقدر يشغّلها وهيشوف إيه)، «الدليل» (logs أو screenshots أو أرقام)، و«مش في الـ PR ده» (اللي سبته عن قصد). واللي مش محتاجه امسحه: تصليح typo سطر واحد كفاية.

الـ PR زي ما هتوصفه لزميلك:

  • إيه: «الـ payment-webhook بقى بيعمل insert بـ ON CONFLICT (provider_event_id) DO NOTHING، فلو نفس الـ event اتبعت تاني مفيش حاجة بتتغير والرد برضه 200. وفيه migration بينقل الـ 61 صف المتكررين لـ payments_duplicates ويضيف unique index على payments.provider_event_id. ابدأ من src/payments/webhook.ts، ومعظم الـ 480 سطر migration وtest وfixtures. أنا عايز عينك أساسًا على الـ conflict handling.»
  • ليه: «الـ provider بيبعت الـ webhook تاني لما الـ 200 بتاعنا بيتأخر. كل مرة كانت بتعمل صف جديد في payments وinvoice email تاني. 37 customer جالهم إيميلين الأسبوع اللي فات (ORD-1482).»
  • إزاي تختبره: «شغّل npm run db:migrate، وبعدين npm run webhook:replay -- fixtures/payment-succeeded.json مرتين. المفروض 200 في المرتين، وcount(*) على evt_test_1 يرجع 1.»
  • الدليل: سطرين log: الأول result=inserted status=200، والتاني بعده بثانيتين result=duplicate status=200.
  • مش في الـ PR ده: الـ retry policy بتاعة queue الـ invoice-pdf ليها PR لوحدها، والاعتذار للـ 37 customer مع منى وياسمين (ORD-1490).
فين هستخدمه في شغلي؟ الـ PR الجاي اللي بيغيّر سلوك API أو webhook أو queue. لو الـ repo مفيهوش template، جرّب الشكل ده في الـ PR بتاعك الأول، ولو الناس حسّوا بفرق اقترح تضيفوه في .github/.
Trade-off: the template shouldn't be a tax A typo fix gets a one-line description. If people fill in empty headings to satisfy a form, the template has become noise, so let authors delete what doesn't apply.
الـ trade-off: الـ template متبقاش ضريبة. تصليح typo ياخد سطر واحد. لو الناس بتملا عناوين فاضية عشان خاطر الشكل، الـ template بقت دوشة، فسيب الـ author يمسح اللي مش محتاجه.
Interview: "How do you make your PRs easy to review?" Model answer, told from the invented Orders team: "I keep them to one purpose and let the description do the work: what, why, how to test, evidence, and what's not included. On our webhook dedupe, the PR said to replay the same event twice and expect one payments row and a 200 both times, and it said retry policy was a separate PR so nobody reviewed for it. I also tell the reviewer where to start and what I want them to look at." A good answer names the reader's problem. A weak one only says "I write small PRs."
سؤال الـ interview: «إزاي بتخلي الـ PRs بتاعتك سهلة في الـ review؟». إجابة نموذجية من فريق الـ Orders المتألف: «بخلي كل PR ليه هدف واحد، والـ description بيعمل الشغل: إيه، ليه، إزاي تختبره، الدليل، وإيه اللي مش فيه. في الـ webhook dedupe، الـ PR قال اعمل replay لنفس الـ event مرتين وتوقع صف واحد في payments و200 في المرتين، وقال إن الـ retry policy في PR لوحده عشان محدش يعمل review عليها. وكمان بقول للـ reviewer يبدأ منين وعايزه يركز على إيه.» الإجابة الكويسة بتسمّي مشكلة القارئ، والضعيفة بتقول «بعمل PRs صغيرة» وبس.

Part 2 — Commits 🟢 Basicالجزء 2 — الـ commits

English

The situation. Salma's branch reads wip, fix, fix2, final, and she asks you if it's ready to merge.

What a mid-level engineer does. Squashes it and hopes the squash message says something.

What a senior does. Sits with Salma and reshapes the branch into small logical commits using Conventional Commits, each with a body that says why: fix(payments): dedupe webhook by provider event id. When a contract changes, the commit says so with a BREAKING CHANGE: footer or a ! after the type.

Why the second works. git bisect lands on one small commit instead of a 480-line lump, git revert can remove one bad step, and changelog tools can read the types. The spec itself gives special meaning only to feat, fix and breaking changes, and allows other types. commitlint's config-conventional narrows the list to build, chore, ci, docs, feat, fix, perf, refactor, revert, style and test, a convention inherited from Angular's. So if someone says chore isn't in the spec, they're right, and it's your tooling that requires it.

بالعامية

الموقف. الـ branch بتاع سلمى فيه wip وfix وfix2 وfinal، وبتسألك ينفع يتعمله merge ولا لأ.

الـ Mid بيعمل إيه. بيعمل squash ويتمنى رسالة الـ squash تقول حاجة.

الـ Senior بيعمل إيه. بيقعد مع سلمى ويعيدوا تشكيل الـ branch لـ commits صغيرة ومنطقية بـ Conventional Commits، وكل واحد فيه body بيقول ليه: fix(payments): dedupe webhook by provider event id. ولما contract يتغير، الـ commit بيقولها بـ footer اسمه BREAKING CHANGE: أو ! بعد الـ type.

ليه التانية بتنجح. git bisect بيقف على commit صغير بدل كتلة 480 سطر، وgit revert يقدر يشيل خطوة واحدة غلط، وأدوات الـ changelog تقدر تقرا الـ types. الـ spec نفسها بتدي معنى خاص لـ feat وfix والـ breaking changes بس، وبتسمح بأي types تانية. والـ config-conventional بتاع commitlint بيحدد الـ list في build وchore وci وdocs وfeat وfix وperf وrefactor وrevert وstyle وtest، وده عرف جاي من Angular. فلو حد قال إن chore مش في الـ spec، عنده حق، واللي بيطلبها هو الـ tooling بتاعك.

تقول لسلمى إيه: «الشغل كويس، بس الـ history مش بيحكي حاجة. تعالي نقسّمه 3 خطوات: الـ index، وبعدين الـ fix، وبعدين الـ test. وفي الـ fix اكتبي في الـ body ليه: الـ provider بيعيد الإرسال لما الـ 200 يتأخر، وده اللي كان بيعمل الصفوف المتكررة.» وتوريها git rebase -i مرة واحدة وهي اللي تعمله بإيدها.

فين هستخدمه في شغلي؟ لما تجهّز branch للـ review، أو لما تساعد junior قبل ما يفتح PR. وأول ما bug يظهر في production وتعمل git bisect هتحس بالفرق. ولو عندكم generated changelog أو semantic release، الـ type بيحدد إيه اللي بيتكتب.
Trade-off: squash-merge teams care about the PR title If your team squash-merges, main gets one commit per PR, so the PR title and squash message are what must be clear, and tidy branch commits mainly help the reviewer. On a team that rebases or keeps merge commits, every commit lands on main. Find out which yours is before spending time on either.
الـ trade-off: الفرق اللي بتعمل squash-merge بيهمها عنوان الـ PR. لو الفريق بيعمل squash-merge، main بياخد commit واحد لكل PR، فعنوان الـ PR ورسالة الـ squash هما اللي لازم يبقوا واضحين، والـ commits المترتبة في الـ branch بتفيد الـ reviewer أساسًا. ولو الفريق بيعمل rebase أو بيسيب merge commits، كل commit بيوصل main. اعرف فريقك أنهي نوع قبل ما تصرف وقت على أي واحدة.

Part 3 — Write before you talk 🟢 Basicالجزء 3 — تكتب قبل ما تتكلم

English

The situation. You want to change the retry policy on the invoice-pdf queue. It affects infra, product and support.

What a mid-level engineer does. Books 30 minutes with six people. Half of them don't know why they're there, and the meeting opens with someone explaining the problem.

What a senior does. Sends half a page first: the current policy, what breaks, the proposal and its cost, what they need from each person, and by when. A meeting happens only if writing can't settle it, and then only with the people who disagree.

Why the second works. Writing forces you to find the holes before six people do. Each reader can answer on their own schedule, and each one knows exactly what's being asked of them. A date plus a stated default keeps the proposal from sitting open forever. Bigger decisions grow into an RFC, and this message is the small version of that habit.

Proposal: change the retry policy on the `invoice-pdf` queue. Replies by Wed 18:00.

Now: 3 attempts with a fixed 5s delay. After that the job sits in `failed` and nobody looks.

What breaks: if the PDF service is down for more than about 10 seconds, the attempts run out and the invoice never goes out. Last month: 212 failed jobs across two slow periods, each retried by hand.

Proposal: 6 attempts with exponential backoff starting at 30s (30s, 1m, 2m, 4m, 8m), about 15 minutes of cover. Jobs that still fail alert the Orders channel.

Cost: during an outage an invoice can arrive up to 15 minutes late, instead of never.

What I need:
- Nour: any problem with that many extra delayed jobs in Redis?
- Mona: is a 15-minute delay acceptable for invoice emails?
- Karim: is the PDF job safe to run twice for the same order?
- Yasmin: nothing to do, just so support knows.

If nobody objects by Wed 18:00, I'll open the PR on Thursday. If this needs a call, say so and I'll book 15 minutes with only the people who disagree.

بالعامية

الموقف. عايز تغيّر الـ retry policy بتاعة queue الـ invoice-pdf، وده بيأثر على الـ infra والـ product والـ support.

الـ Mid بيعمل إيه. بيحجز 30 دقيقة مع 6 أشخاص. نصهم مش عارف جاي ليه، والـ meeting بيبدأ بحد بيشرح المشكلة.

الـ Senior بيعمل إيه. بيبعت نص صفحة الأول: الـ policy الحالية، إيه اللي بيكسر، الاقتراح وتمنه، محتاج إيه من كل واحد، ولحد إمتى. والـ meeting بيحصل بس لو الكتابة محسمتش، وساعتها مع المختلفين بس.

ليه التانية بتنجح. الكتابة بتجبرك تلاقي الثغرات قبل ما 6 أشخاص يلاقوها. وكل واحد يقدر يرد في الوقت اللي يناسبه، وعارف بالظبط المطلوب منه إيه. وميعاد ومعاه default بيمنعوا الاقتراح يفضل مفتوح للأبد. والقرارات الأكبر بتكبر لـ RFC، والرسالة دي النسخة الصغيرة من نفس العادة.

الرسالة زي ما هتتبعت:

  • «عايز أغيّر الـ retry policy بتاعة الـ invoice-pdf queue، ومحتاج ردودكم قبل الأربع 6 بالليل.»
  • دلوقتي: 3 attempts بـ delay ثابت 5 ثواني، وبعدها الـ job بتقعد في failed ومحدش بيبص عليها.
  • إيه اللي بيكسر: لو خدمة الـ PDF وقعت أكتر من حوالي 10 ثواني، الـ attempts بتخلص والفاتورة مبتتبعتش. الشهر اللي فات 212 job فشلت في فترتين بطء، وكلهم اتعمل لهم retry بالإيد.

Part 6 — Documenting the why 🟢 Basicالجزء 6 — توثّق الـ "ليه"

English

The situation. A new teammate asks, "Why is this timeout 11 seconds?" The person who set it has left.

What a mid-level engineer does. Wrote // set timeout to 11s. That repeats the code and answers nothing, so the next person rounds it to 15.

What a senior does. Writes down the reason the code can't show: the provider's gateway cuts the connection at 12 seconds, so our error has to come first. The same habit applies at three sizes: a comment for one line, a README section for one module, and a runbook for one failure.

Why the second works. Code shows what happens, and only a note can say why, what would break if you changed it, and when the reason stops applying. A runbook is written for someone tired and new to the problem, so it's ordered symptom, check, fix, escalate, and each step is something they can do. Designing the alerts that point to runbooks is covered in the alert design part. Here it's only about the writing.

Owner: Orders team. Last checked: 2 Nov 2026.

## Symptom
Customers report missing invoices, or the `invoice-pdf` waiting count grows for 10+ minutes while the active count stays at 0.

- Workers down: restart them. They pick up waiting jobs on their own.

- Customers have waited over an hour: tell Mona and Yasmin.

❌ «خلّي الـ timeout 11 ثانية» بتقول اللي السطر اللي تحتها قايله. واللي جاي بعدك هيغيّرها من غير ما يعرف إيه اللي هيكسر.

Try it yourself · جرّب بنفسك

1. Rewrite your last PR description 🟢 easyأعد كتابة آخر PR description Open the last PR you authored and rewrite its description by hand, without AI, in the five-part shape: what, why, how to test, evidence, not in this PR. Update the real PR if it's still open. If you can't do this at work, use a PR in your side project.
افتح آخر PR كتبته وأعد كتابة الـ description بإيدك ومن غير AI بالشكل ده: إيه، ليه، إزاي تختبره، الدليل، ومش في الـ PR ده. ولو الـ PR لسه مفتوح حدّثه فعلًا. ولو مينفعش تعمل ده في الشغل، استخدم PR في مشروعك الجانبي.
Hint · تلميح Start with "Why". If you can't write it in two sentences, ask yourself whether the reviewer could have known it.
ابدأ بـ «ليه». لو مش عارف تكتبها في جملتين، اسأل نفسك الـ reviewer كان هيعرفها إزاي.
Solution · الحل Worked example from the invented team: Salma's PR said "update coupon logic". Rewritten: "What: a coupon now counts as used only after payment succeeds. Why: failed payments were using up single-use coupons, 14 support tickets in October. Test: pay with the failing test card and the coupon stays usable. Evidence: test run output. Not here: refunding coupons on cancelled orders."
مثال من الفريق المتألف: الـ PR بتاع سلمى كان مكتوب فيه "update coupon logic". بعد إعادة الكتابة: «إيه: الـ coupon بيتحسب مستخدم بعد نجاح الدفع بس. ليه: الدفع الفاشل كان بيحرق coupons بتتستخدم مرة واحدة، و14 support ticket في أكتوبر. الاختبار: ادفع بالـ test card الفاشلة والـ coupon يفضل صالح. الدليل: نتيجة الـ test run. مش هنا: رجوع الـ coupons في الأوردرات الملغية».
2. Your next 5 questions, complete 🟡 mediumأسئلتك الـ 5 الجاية كاملة For your next five questions at work, write the complete form yourself: context, question, what you tried, what you need, by when. Keep the greeting. Write down how many got answered in the first reply. If you can't do this at work, write one complete issue on an open-source project for a problem you've actually hit, with no company data in it.
في الـ 5 أسئلة الجايين في الشغل، اكتب الشكل الكامل بنفسك: السياق، والسؤال، واللي جرّبته، ومحتاج إيه، ولحد إمتى. وخلّي التحية. واكتب كام واحد اتجاوب من أول رد. ولو مينفعش في الشغل، اكتب issue كاملة في مشروع open-source عن مشكلة قابلتك فعلًا، ومن غير أي data من شركتك.
Solution · الحل Worked example from the invented team: Karim sent five. Four were answered in the first reply, and one he solved himself while listing what he'd tried, so he never sent it. The count tells you whether your context is enough. If a reply asks for something you could have included, add it to your shape.
مثال من الفريق المتألف: كريم بعت 5. 4 اتجاوبوا من أول رد، وواحد حله بنفسه وهو بيكتب اللي جرّبه فمبعتوش خالص. العدد بيقولك السياق بتاعك كفاية ولا لأ. ولو الرد طلب حاجة كان ممكن تكتبها، ضيفها للشكل بتاعك.
3. At work: a decision summary and a why 🔴 hardفي الشغل: ملخص قرار و"ليه" مكتوبة Within an hour of your next meeting, post a decision summary yourself: decided, not decided, next, owner. This week, add one runbook or one why-comment to a service you own. Don't put customer data or secrets in either. If you can't do this at work, write docs/runbook-*.md in your side project for a failure it can actually have.
في خلال ساعة من الـ meeting الجاي، انشر ملخص القرار بنفسك: اتقرر إيه، ماتقررش إيه، الخطوة الجاية، والمسؤول. والأسبوع ده، ضيف runbook واحد أو why-comment واحد في service إنت مسؤول عنها. ومتحطش data بتاعة customers أو secrets في أي واحد منهم. ولو مينفعش في الشغل، اكتب docs/runbook-*.md في مشروعك الجانبي لعطل ممكن يحصل فيه فعلًا.
Hint · تلميح For the summary, write "Not decided" even if it's "nothing open". For the runbook, start from the last time something broke and write the steps you actually took.
في الملخص، اكتب «ماتقررش» حتى لو هتكتب «مفيش حاجة مفتوحة». وفي الـ runbook، ابدأ من آخر مرة حاجة وقعت واكتب الخطوات اللي عملتها فعلًا.
Solution · الحل Worked example from the invented team: after a 25-minute call about coupon limits, Salma posted within the hour: "Decided: one coupon per order. Not decided: stacking with gift cards, Mona will check. Next: validation in POST /orders, Karim, PR by Thursday." Her why-comment in the coupon service read: "Rounded down so the discount can never exceed the order total in EGP."
مثال من الفريق المتألف: بعد call 25 دقيقة عن حدود الـ coupons، سلمى نشرت في خلال ساعة: «اتقرر: coupon واحد لكل أوردر. ماتقررش: تجميعها مع الـ gift cards، ومنى هتتأكد. الخطوة الجاية: validation في POST /orders على كريم، PR لحد الخميس». والـ why-comment بتاعها في الـ coupon service: «بنقرّب لتحت عشان الخصم عمره ما يعدي إجمالي الأوردر بالجنيه».

Cheat sheet · الخلاصة

  • PR description: what, why, how to test, evidence, not in this PR. A typo gets one line.
  • The title says what the change does. "fix webhook" says nothing.
  • Commits: small and logical, type(scope): subject, and a body that says why.
  • Breaking change: ! after the type or a BREAKING CHANGE: footer. The spec singles out feat and fix; the longer list comes from your tooling.
  • On a squash-merge team, the PR title is what lands on main.
  • Write first: now, what breaks, proposal, cost, what you need from each person, by when, and a default.
  • Thread, doc or call depends on reversibility, how many people, and whether there's conflict. Conflict goes to a call.
  • Decision summary within the hour: Decided, Not decided, Next, Owner. Never minutes.
  • Complete message: greeting, context, question, tried, need, by when, all in one message.
  • Comments explain why. Runbooks go symptom, check, fix, escalate. Docs live near the code with an owner and a last-checked date.
بالعامية
  • الـ PR description: إيه، ليه، إزاي تختبره، الدليل، ومش في الـ PR ده. والـ typo سطر واحد.
  • العنوان بيقول التغيير بيعمل إيه. "fix webhook" مبتقولش حاجة.
  • الـ commits: صغيرة ومنطقية، بشكل type(scope): subject، وbody بيقول ليه.
  • الـ breaking change: ! بعد الـ type أو footer اسمه BREAKING CHANGE:. الـ spec بتميّز feat وfix، والـ list الأطول جاية من الـ tooling بتاعك.
  • في فريق squash-merge، عنوان الـ PR هو اللي بيوصل main.
  • اكتب الأول: الوضع الحالي، إيه اللي بيكسر، الاقتراح، التمن، محتاج إيه من كل واحد، لحد إمتى، وdefault.
  • thread ولا doc ولا call بيعتمد على: ينفع نرجع فيها ولا لأ، كام واحد، وفيه خلاف ولا لأ. والخلاف مكانه call.
  • ملخص القرار في خلال ساعة: اتقرر، ماتقررش، الخطوة الجاية، المسؤول. ومش minutes أبدًا.
  • الرسالة الكاملة: تحية، سياق، سؤال، اللي جرّبته، محتاج إيه، لحد إمتى، وكله في رسالة واحدة.
  • الـ comments بتشرح ليه. والـ runbook ترتيبه symptom ثم check ثم fix ثم escalate. والـ docs جنب الكود ومعاها owner وتاريخ آخر مراجعة.

README items to tick · بنود الـ README تعلّمها

Tick only with evidence The README's own rule: an item gets ticked when evidence exists (an RFC written, a postmortem led, a colleague saying you helped), not when you've understood it.
قاعدة الـ README نفسه: البند بيتعلّم لما يكون فيه دليل (RFC اتكتب، postmortem اتقاد، زميل قال إنك ساعدته)، مش لما تفهمه.
