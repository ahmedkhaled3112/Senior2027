Why this matters · ليه ده مهم

English

Double-entry is a 500-year-old data integrity technique, and it's the data model under every ERP, bank and payment system. Once you read it as an invariant, the vocabulary stops being scary and money bugs stop being silent. You need it to design a wallet, a refund flow or a billing ledger, and to talk with the accountant who will sign off your integration. This lesson is engineering literacy, not accounting advice: for how a real company should book something, ask an accountant.

بالعامية

الـ double-entry تقنية data integrity عمرها 500 سنة، وهي الـ data model اللي تحت أي ERP وبنك ونظام دفع. أول ما تقراها كـ invariant، المصطلحات بتبطل تخوّف، وباجات الفلوس بتبطل تعدّي في السكوت. هتحتاجها عشان تصمم wallet أو refund flow أو billing ledger، وعشان تتكلم مع المحاسب اللي هيوافق على الـ integration بتاعتك. الدرس ده ثقافة هندسية مش نصيحة محاسبية: لو عايز تعرف شركة حقيقية تسجل حاجة إزاي، اسأل محاسب.

Part 1 — Why two sides 🟢 Basicالجزء 1 — ليه جهتين

English

Single-entry bookkeeping is a balance column: you change a number and the previous number is gone. Double-entry records every movement as at least two lines, debits on one side and credits on the other, and they must sum to the same amount. Money doesn't appear or vanish: it moves from somewhere to somewhere, and both ends are written down.

Read it the way you'd read any invariant: sum(debit) == sum(credit) per entry. If code forgets one side, the invariant fails at write time, and the bug shows up as an imbalance instead of as silent drift.

The first program is the bad version on real Postgres. A refund should take 100 from the merchant and give it to the customer. The customer's email arrives with a capital letter, the lookup finds no row, the if skips the second update, and no error is raised. The total falls by 100 and nothing records where it went. The second program has the identical bug in double-entry form: the second line never gets added, and assertBalanced throws. Then a property-style loop runs 10,000 random entries, checks that all balanced ones pass, and checks that changing any one line by one piastre is caught.

Amounts are integer piastres throughout. Lesson 04 covers money in code in detail. To run the SQL programs, use the throwaway Postgres from lesson 01, part 4, and set "type": "module" in your package.json.

// مولّد أرقام بـ seed عشان النتيجة تتكرر بالظبط كل مرة
export function mulberry32(seed: number): () => number {
  let a = seed;
  return () => {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

import { mulberry32 } from "./rng.ts";

type Line = { account: string; debit: number; credit: number };
type Entry = { memo: string; lines: Line[] };

function assertBalanced(entry: Entry): void {
  if (entry.lines.length === 0) throw new Error(`${entry.memo}: empty entry`);
  let debit = 0;
  let credit = 0;
  for (const l of entry.lines) {
    if (!Number.isSafeInteger(l.debit) || !Number.isSafeInteger(l.credit)) throw new Error(`${entry.memo}: not integer piastres`);
    if (l.debit < 0 || l.credit < 0) throw new Error(`${entry.memo}: negative amount on ${l.account}`);
    // السطر لازم يكون في جهة واحدة بس: يا مدين يا دائن
    if ((l.debit === 0) === (l.credit === 0)) throw new Error(`${entry.memo}: line must be one-sided on ${l.account}`);
    debit += l.debit;
    credit += l.credit;
  }
  if (debit !== credit) throw new Error(`${entry.memo}: unbalanced ${debit} <> ${credit}`);
}

// نفس باج الريفند بالظبط: الإيميل غلط، والسطر التاني مش بيتضاف
function refundEntry(customerAccount: string | undefined, amount: number): Entry {
  const lines: Line[] = [{ account: "merchant", debit: amount, credit: 0 }];
  if (customerAccount) lines.push({ account: customerAccount, debit: 0, credit: amount });
  return { memo: "refund", lines };
}

function randomEntry(rand: () => number, i: number): Entry {
  const n = 1 + Math.floor(rand() * 5);
  const lines: Line[] = [];
  let total = 0;
  for (let k = 0; k < n; k++) {
    const amount = 1 + Math.floor(rand() * 1_000_000);
    total += amount;
    lines.push({ account: `acct-${k}`, debit: amount, credit: 0 });
  }
  lines.push({ account: "offset", debit: 0, credit: total });
  return { memo: `entry-${i}`, lines };
}

بالعامية

الـ single-entry هو عمود balance: بتغيّر الرقم والقديم بيروح. الـ double-entry بيسجل كل حركة في سطرين على الأقل، مدين في جهة ودائن في جهة، ولازم مجموعهم يبقى نفس الرقم. الفلوس مش بتظهر من العدم ولا بتختفي: بتنتقل من حتة لحتة، والطرفين مكتوبين.

اقراها زي أي invariant: sum(debit) == sum(credit) لكل قيد. لو الكود نسي جهة، الـ invariant بيفشل وقت الكتابة، والباج بيظهر كـ imbalance بدل ما يبقى drift ساكت.

أول برنامج هو النسخة الوحشة على Postgres حقيقي. الريفند المفروض ياخد 100 من التاجر ويديهم للعميل. إيميل العميل جاي بحرف كبير، الـ lookup مش بيلاقي row، الـ if بيعدّي التعديل التاني، ومفيش error. الإجمالي بينزل 100 ومفيش حاجة بتسجل راحوا فين. البرنامج التاني فيه نفس الباج بالظبط بشكل double-entry: السطر التاني مش بيتضاف، وassertBalanced بيرمي error. وبعدين loop بأسلوب الـ property tests: 10,000 قيد عشوائي، نتأكد إن المتوازن كله بيعدّي، وإن تغيير أي سطر بقرش واحد بيتمسك.

الأرقام كلها قروش integer. درس 04 بيشرح الفلوس في الكود بالتفصيل. عشان تشغّل برامج الـ SQL، استخدم الـ Postgres المؤقت من درس 01، الجزء 4، وحط "type": "module" في package.json.

فين هستخدمه في شغلي؟ لو عندك جدول users.credit_balance في Node API وبتعمل عليه UPDATE في الريفند والكوبونات والـ cashback، يبقى كل bug بيغيّر الرقم من غير أثر. لما الدعم يسأل "العميل ده رصيده نقص ليه؟" مفيش إجابة. الحل: جدول سطور append-only، والرصيد يتحسب منه أو يبقى cache فوقه. الغلطة الشائعة: عمود balance لوحده هو مصدر الحقيقة.
Trade-off: lines versus a balance column A ledger costs more rows and a sum to read a balance. At scale you keep a cached balance updated in the same transaction as the lines, and treat the lines as the truth. The balance can always be rebuilt; lost history can't.
الـ ledger بياخد rows أكتر و sum عشان تقرا الرصيد. على scale بتحتفظ برصيد cached بيتعدل في نفس الـ transaction مع السطور، وتعتبر السطور هي الحقيقة. الرصيد ممكن يتبني تاني في أي وقت، إنما التاريخ اللي ضاع مش بيرجع.

Part 2 — The five account types 🟢 Basicالجزء 2 — أنواع الحسابات الخمسة

English

Every account is one of five types. Each has a normal side, the side that increases it. The whole rule fits in one line: debit increases assets and expenses; credit increases liabilities, equity and income.

TypeWhat it isIncreases onExample
AssetsWhat the company owns or is owedDebitBank, laptops, receivables
LiabilitiesWhat it owes othersCreditVAT payable, accrued salaries
EquityWhat belongs to the ownersCreditShare capital
IncomeWhat it earnedCreditSales
ExpensesWhat it consumed to earn itDebitRent, salaries
  • Assets: اللي الشركة مالكاه أو ليها عند حد. بيزيد بالمدين. زي البنك، اللابتوبات، والعملاء المديونين.
  • Liabilities: اللي عليها لغيرها. بيزيد بالدائن. زي الضريبة المستحقة والمرتبات المستحقة.
  • Equity: اللي يخص أصحاب الشركة. بيزيد بالدائن. زي رأس المال.
  • Income: اللي كسبته. بيزيد بالدائن. زي المبيعات.
  • Expenses: اللي صرفته عشان تكسب. بيزيد بالمدين. زي الإيجار والمرتبات.

The biggest trap for a programmer: debit doesn't mean "minus" and credit doesn't mean "plus". Debit means the left column and credit means the right column. Your bank statement seems to say the opposite because it's written from the bank's side: your deposit is the bank's liability, so it credits you.

The accounting equation ties the types together: Assets = Liabilities + Equity + (Income − Expenses). It holds after every balanced entry. The program works 8 transactions for a Cairo SaaS company and prints the equation after each one. Watch transaction 6: VAT collected from a customer is a liability, because that money belongs to the tax authority, so it never touches income. Transaction 8, the owner taking money out, debits equity, using 604000 Dividends paid, the closest account in this chart. بالعامية

كل حساب واحد من خمس أنواع، وكل نوع ليه normal side: الجهة اللي بتزوّده. القاعدة كلها في سطر: المدين بيزوّد الأصول والمصروفات، والدائن بيزوّد الالتزامات وحقوق الملكية والإيرادات.

أكبر فخ للمبرمج: debit مش معناها "ناقص"، و credit مش معناها "زايد". الـ debit معناها العمود الشمال، والـ credit العمود اليمين. كشف حساب البنك بتاعك شكله بيقول العكس لأنه مكتوب من ناحية البنك: الفلوس اللي حطيتها التزام على البنك، فبيعملك credit.

معادلة المحاسبة بتربط الأنواع ببعض: Assets = Liabilities + Equity + (Income − Expenses)، وبتفضل صح بعد أي قيد متوازن. البرنامج بيشتغل على 8 حركات لشركة SaaS في القاهرة ويطبع المعادلة بعد كل واحدة. بص على الحركة 6: الضريبة اللي خدتها من العميل التزام، لأن الفلوس دي بتاعة مصلحة الضرايب، فعمرها ما بتلمس الإيراد. والحركة 8، صاحب الشركة بياخد فلوس، بتعمل debit لحقوق الملكية على 604000 Dividends paid، أقرب حساب في الشجرة دي. أكواد الحسابات من شجرة حسابات مصر في Odoo، عشان الجزء 5 يقارن النظامين.

فين هستخدمه في شغلي؟ بتعمل marketplace وبتحصّل 1000 جنيه من المشتري، منهم 900 للتاجر و100 عمولتك. لو سجلت الألف كلها revenue، الـ dashboard هيكذب: الـ 900 دول liability عليك للتاجر، والـ income بتاعك 100 بس. القيد: Dr Bank 1000، Cr Merchant Payable 900، Cr Commission Income 100. الغلطة الشائعة: تعتبر أي فلوس دخلت إيراد.
Interview question "A customer deposits 500 in your wallet product. Is that revenue?" → No. You owe it back, so it's a liability: debit Bank 500, credit Customer Wallets 500. Revenue appears only when you earn a fee.
"عميل حط 500 في الـ wallet بتاع الـ product. ده revenue؟" ← لأ. إنت مديون له بيها، فهي liability: مدين البنك 500، دائن محافظ العملاء 500. الـ revenue بيظهر بس لما تكسب رسوم.

Part 3 — The chart of accounts 🟢 Basicالجزء 3 — شجرة الحسابات

English

The chart of accounts (CoA) is the list of accounts a company posts to: think of it as an enum that every journal line references. A good design has a hierarchy, stable code ranges and enough detail to produce the reports you owe, and no more. The rule of thumb: an account answers "what kind of money is this?". Who it relates to, which project or which branch are dimensions on the line: partners and analytic accounts in Odoo.

Here's the real one: Odoo's Egyptian chart has 215 active accounts. Odoo keeps the five types but refines them into a finer account_type, such as asset_receivable or expense_direct_cost, and derives the five-way internal_group from it. Codes follow ranges in this chart (1 assets, 2 liabilities, 4 expenses, 5 income, 6 equity), but ranges are only a convention: the output shows an expense account at 210803, inside the liability range. Write reports against the type, never against a code prefix.

A change in Odoo 20: the account.group model is gone, and hierarchy now lives on the account itself through parent_id. Odoo ships an upgrade script for it, 19.3-00-account-groups.py. In this chart all 20 parent accounts are stored with active = False, so they don't appear in normal lists, and posting to one fails with The account Receivables (150000) is archived. Account codes are also optional now; the script creates an account without one.

The common mistake is an account per customer. The second program simulates 5,000 customers with accounts named AR-…, where 37 were opened by someone who typed Customer … instead. The report that sums accounts by name prefix misses them silently. One receivable account with the customer as a dimension on the line can't have that bug.

English

Two words that sound alike. A journal entry is one balanced document: a date, a reference and two or more lines. A journal is a book that groups entries by source: sales, purchases, bank, cash, miscellaneous. The journal gives each entry its numbering sequence, and it tells you where a number came from when an auditor asks.

In Odoo an entry is an account.move and its lines are account.move.line. Invoices are moves too: move_type says which kind, and 'entry' means a plain journal entry with no invoice behind it. An entry starts as draft with no number, and gets its number when posted.

Part 5 — From entries to the general ledger 🟢 Basicالجزء 5 — من القيود لدفتر الأستاذ

English

The general ledger (GL) is all posted lines grouped by account, each with a running balance. It isn't new data: it's a GROUP BY over the journal lines. That's the important part. Everything downstream, trial balance and financial statements included, is derived from these same lines.

We compute it twice. First in SQL over the TypeScript ledger, with a window function for the running balance (see section 09 · window functions). Then in Odoo with _read_group on account.move.line, filtered to posted lines, after posting the same 8 transactions.

Odoo Community has no General Ledger screen. The financial reports engine, account_reports, is Enterprise and isn't in this source tree. So here you compute it yourself, which is also how you check any report you're handed. All 10 accounts match to the piastre. Odoo's balance is debit minus credit, so credit-normal accounts show as negative. The script also gets one customer's receivable by grouping on partner_id, the dimension from Part 3, with no account of their own.

// تشغيل: DATABASE_URL=postgres://ledger@127.0.0.1:55433/ledger node gl-sql.ts
import { writeFileSync } from "node:fs";
import { connect } from "./db.ts";
import { accounts, transactions } from "./transactions.ts";

const db = connect();
await db.connect();
await db.query("DROP TABLE IF EXISTS journal_line");
await db.query("DROP TABLE IF EXISTS journal_entry");
await db.query(`CREATE TABLE journal_entry (id int PRIMARY KEY, memo text NOT NULL, posted_on date NOT NULL)`);
await db.query(`CREATE TABLE journal_line (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  entry_id int NOT NULL REFERENCES journal_entry(id),
  account text NOT NULL,
  debit numeric(18,2) NOT NULL DEFAULT 0 CHECK (debit >= 0),
  credit numeric(18,2) NOT NULL DEFAULT 0 CHECK (credit >= 0))`);

// كل قيد بسطوره في transaction واحدة: يا كله يتسجل يا ولا حاجة
await db.query("BEGIN");
for (const [i, tx] of transactions.entries()) {
  const day = String(i + 1).padStart(2, "0");
  await db.query("INSERT INTO journal_entry VALUES ($1, $2, $3)", [i + 1, tx.memo, `2026-11-${day}`]);
  for (const [code, debit, credit] of tx.lines) {
    await db.query("INSERT INTO journal_line (entry_id, account, debit, credit) VALUES ($1, $2, $3, $4)", [i + 1, code, debit, credit]);
  }
}
await db.query("COMMIT");

// دفتر حساب واحد برصيد متراكم: الـ window function بتجمع لحد السطر الحالي
const bank = await db.query<{ posted_on: string; memo: string; debit: string; credit: string; running: string }>(`
  SELECT to_char(e.posted_on, 'YYYY-MM-DD') AS posted_on, e.memo, l.debit, l.credit,
         sum(l.debit - l.credit) OVER (PARTITION BY l.account ORDER BY e.posted_on, l.id) AS running
  FROM journal_line l JOIN journal_entry e ON e.id = l.entry_id
  WHERE l.account = '160100'
  ORDER BY e.posted_on, l.id`);
console.log("ledger for 160100 Bank");
for (const r of bank.rows) {
  console.log(`${r.posted_on} ${r.memo.padEnd(15)} ${r.debit.padStart(11)} ${r.credit.padStart(11)} ${r.running.padStart(11)}`);
}

// الملخص: سطر لكل حساب، زي اللي Odoo بيطلّعه بـ ⁦_read_group⁩
const summary = await db.query<{ account: string; debit: string; credit: string; balance: string }>(`
  SELECT account, sum(debit) AS debit, sum(credit) AS credit, sum(debit - credit) AS balance
  FROM journal_line GROUP BY account ORDER BY account`);
console.log("\ngeneral ledger summary");
for (const r of summary.rows) {
  console.log(`${r.account} ${accounts[r.account]!.name.padEnd(22)} ${r.debit.padStart(11)} ${r.credit.padStart(11)} ${r.balance.padStart(11)}`);
}
writeFileSync("gl-sql.json", JSON.stringify(summary.rows));
await db.end();

Part 6 — What breaks 🟢 Basicالجزء 6 — إيه اللي بيكسر

English

The invariant catches only what it can see. Four failures to know:

  • Wrong sign. A debit of −100 against a credit of −100 balances. A naive sum check passes, so amounts must be validated as non-negative and each line one-sided.
  • Wrong account type. Rent booked to an asset balances perfectly and overstates profit by 12,000. No invariant in the code can catch this: only a review of account choice can.
  • Entry split across two transactions. If each line insert auto-commits and the process dies between them, an imbalance stays in the database.
  • Floats. Ten thousand lines of 0.10 don't sum to exactly 1,000 in binary floating point, so a strict equality check fails on correct data.

The crash demo kills a child process between the two inserts, first with auto-commit and then inside BEGIN. With auto-commit, entry 101 stays unbalanced. Inside a transaction, Postgres discards the uncommitted work when the connection dies and entry 102 never exists. On Windows the killed child reports exit status 1 and no signal. A transaction fixes the crash, but it still relies on every caller using one correctly. Lesson 05 makes the database itself refuse an imbalance with a deferred constraint trigger.

Interview question "Explain double-entry to a programmer in two minutes." → It's an append-only log of transfers with an invariant. Each entry has lines that move value between accounts, and debits must equal credits per entry. Debit means left, credit means right; which one increases an account depends on its type. A bug shows as an imbalance instead of as silent drift, as long as the entry is written atomically.

// تشغيل: node ex-reverse.ts
type Line = { account: string; debit: number; credit: number };
type Entry = { memo: string; lines: Line[] };

// عكس القيد: نبدّل الجهتين، والقيد الأصلي يفضل زي ما هو
function reverseEntry(entry: Entry): Entry {
  return {
    memo: `Reversal of ${entry.memo}`,
    lines: entry.lines.map((l) => ({ account: l.account, debit: l.credit, credit: l.debit })),
  };
}

const net = (entries: Entry[]) => {
  const balances = new Map<string, number>();
  for (const e of entries) {
    for (const l of e.lines) balances.set(l.account, (balances.get(l.account) ?? 0) + l.debit - l.credit);
  }
  return balances;
};

  `WITH opening AS (
     SELECT coalesce(sum(l.debit - l.credit), 0) AS amount
     FROM journal_line l JOIN journal_entry e ON e.id = l.entry_id
     WHERE l.account = $1 AND e.posted_on < $2
   )

          (SELECT amount FROM opening)
            + sum(l.debit - l.credit) OVER (ORDER BY e.posted_on, l.id) AS running
   FROM journal_line l JOIN journal_entry e ON e.id = l.entry_id
   WHERE l.account = $1 AND e.posted_on >= $2
   ORDER BY e.posted_on, l.id`,

Cheat sheet · الخلاصة

  • Invariant: sum(debit) == sum(credit) per entry; also validate non-negative, one-sided lines.
  • Debit = left, credit = right. Debit increases assets and expenses; credit increases liabilities, equity and income.
  • Assets = Liabilities + Equity + (Income − Expenses), after every entry.
  • Customer money you hold and VAT you collected are liabilities, not income.
  • An account answers "what kind of money?". Customers, projects and branches are dimensions on the line.
  • Code ranges are a convention; report on the account type.
  • Odoo 20: no account.group, hierarchy through parent_id, codes optional.
  • Entry = one balanced document (account.move). Journal = a book grouping entries by source.
  • General ledger = posted lines grouped by account. Community has no GL screen (account_reports is Enterprise).
  • One transaction per entry, integer piastres or numeric. An unbalanced entry in Odoo gives "The entry is not balanced."
بالعامية
  • الـ invariant: sum(debit) == sum(credit) لكل قيد؛ وكمان اتأكد إن السطور مش سالبة وفي جهة واحدة.
  • الـ debit شمال والـ credit يمين. المدين بيزوّد الأصول والمصروفات، والدائن بيزوّد الالتزامات وحقوق الملكية والإيرادات.
  • Assets = Liabilities + Equity + (Income − Expenses)، بعد كل قيد.
  • فلوس العملاء اللي عندك والضريبة اللي حصّلتها التزامات، مش إيراد.
  • الحساب بيجاوب "الفلوس دي نوعها إيه؟". العملاء والمشاريع والفروع dimensions على السطر.
  • الـ code ranges عرف؛ التقارير تتبني على نوع الحساب.
  • Odoo 20: مفيش account.group، والـ hierarchy بـ parent_id، والأكواد اختيارية.
  • القيد document واحد متوازن (account.move). الـ journal دفتر بيجمّع القيود حسب المصدر.
  • الـ general ledger هو السطور الـ posted متجمعة بالحساب. Community مفيهوش شاشة GL (account_reports في Enterprise).
  • Transaction واحدة لكل قيد، وقروش integer أو numeric. والقيد غير المتوازن في Odoo بيدي "The entry is not balanced."
