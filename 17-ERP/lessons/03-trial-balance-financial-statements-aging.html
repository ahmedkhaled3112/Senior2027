Why this matters · ليه ده مهم

English

Sooner or later a finance person will tell you "the report doesn't match". The reports are nothing more than queries over the ledger from lesson 02, so a backend engineer who can read them can find the bug. This lesson builds the four views a business runs on: the trial balance, the income statement, the balance sheet and the cash flow statement. Then it adds the two ideas behind most reporting arguments: accrual timing and receivables aging.

Two notes, said once. Odoo Community has no financial reports screen, because account_reports is an Enterprise module, so every statement here is computed by this lesson's own SQL or _read_group. And this is engineering literacy, not accounting advice: the real treatment of a transaction in your company is an accountant's call.

بالعامية

عاجلًا أو آجلًا هييجي لك حد من الماليات ويقولك "التقرير مش مظبوط". التقارير دي في الآخر مجرد queries فوق الـ ledger بتاع درس 02، فالـ backend engineer اللي يعرف يقراها يقدر يلاقي الـ bug. الدرس ده بيبني الأربع حاجات اللي أي شركة ماشية عليهم: الـ trial balance، والـ income statement، والـ balance sheet، والـ cash flow statement. وبعدين بيضيف الفكرتين اللي وراء أغلب الخناقات على التقارير: توقيت الـ accrual، والـ aging بتاع الـ receivables.

Part 1 — Trial balance 🟢 Basicالجزء 1 — الـ trial balance وليه بيتوازن

English

A trial balance is one row per account with its total debits and total credits. Total debits equal total credits, and there is nothing magical about it. Every entry balances, and the trial balance adds up exactly the same numbers in a different grouping. Addition doesn't care about grouping, so if the sum of each entry's debits minus credits is zero, the sum across all accounts is zero too.

That makes the trial balance a cheap integrity check: if it doesn't balance, something bypassed the posting path, such as a bad import or a hand-edited row. The important limit runs the other way. A trial balance that balances doesn't prove the books are right. A sale posted to the wrong account, an entry that was never posted, and an entry posted twice all still balance. It detects one-sided errors only.

type Line = { account: string; debit: number; credit: number };
type Entry = { memo: string; lines: Line[] };

// المبالغ كلها قروش integer، عشان الجمع يبقى exact
const dr = (account: string, egp: number): Line => ({ account, debit: egp * 100, credit: 0 });
const cr = (account: string, egp: number): Line => ({ account, debit: 0, credit: egp * 100 });

function assertBalanced(entry: Entry): void {
  const d = entry.lines.reduce((s, l) => s + l.debit, 0);
  const c = entry.lines.reduce((s, l) => s + l.credit, 0);
  if (d !== c) throw new Error(`${entry.memo}: ${d} <> ${c}`);
}

function trialBalance(entries: Entry[]) {
  const rows = new Map<string, { debit: number; credit: number }>();
  for (const entry of entries) {
    assertBalanced(entry);
    for (const l of entry.lines) {
      const row = rows.get(l.account) ?? { debit: 0, credit: 0 };
      row.debit += l.debit;
      row.credit += l.credit;
      rows.set(l.account, row);
    }
  }
  const totalDebit = [...rows.values()].reduce((s, r) => s + r.debit, 0);
  const totalCredit = [...rows.values()].reduce((s, r) => s + r.credit, 0);
  return { rows, totalDebit, totalCredit, balanced: totalDebit === totalCredit };
}

بالعامية

الـ trial balance هو صف لكل حساب، فيه مجموع الـ debit ومجموع الـ credit بتوعه. المجموعين بيطلعوا متساويين، ومفيش سحر في الموضوع: كل قيد متوازن، والميزان بيجمع نفس الأرقام بالظبط بس بتجميعة مختلفة. والجمع مبيفرقش معاه الترتيب، فلو الفرق في كل قيد صفر، يبقى الفرق على كل الحسابات صفر.

ده بيخلي الميزان فحص سلامة رخيص: لو مش متوازن، يبقى فيه حاجة عدّت من ورا مسار الـ posting، زي import بايظ أو row حد عدّله بإيده. بس الحد المهم في الناحية التانية: الميزان المتوازن مش دليل إن الدفاتر صح. بيع على حساب غلط، وقيد ماتسجلش أصلًا، وقيد اتسجل مرتين، التلاتة متوازنين. هو بيكشف الغلطات اللي في ناحية واحدة بس.

وفي Odoo نفس الحسبة: سطور account.move.line المرحّلة متجمعة بالحساب عن طريق _read_group. الفلتر parent_state = 'posted' مهم، لأن القيود الـ draft ليها سطور هي كمان. السكريبت بيشتغل جوه odoo-bin shell عن طريق driver صغير، وبيعمل rollback في الآخر.

فين هستخدمه في شغلي؟ عملت migration لفواتير قديمة من نظام تاني لـ Postgres. بعد الـ import شغّل query الميزان: لو الفرق مش صفر يبقى فيه rows ناقصة أو نص قيد اتنقل، ووقف قبل ما حد يبني عليها. ولو الفرق صفر متفرحش: قارن كمان إجمالي كل حساب بالنظام القديم، لأن الحساب الغلط مش هيبان في الميزان.
Interview question "The trial balance balances. Can you tell finance the books are correct?" → No. It proves every entry has equal sides. It can't see a wrong account, a missing entry or a duplicate. For those you need reconciliation against an outside source, such as the bank statement or the source documents.
"الـ trial balance متوازن، تقدر تقول للماليات إن الدفاتر صح؟" ← لأ. هو بيثبت إن كل قيد ناحيتيه متساويين بس. مبيشوفش الحساب الغلط ولا القيد الناقص ولا المتكرر. دول محتاجين reconciliation مع مصدر برّه، زي كشف البنك أو المستندات الأصلية.

Part 2 — Income statement 🟢 Basicالجزء 2 — الـ income statement (الـ P&L)

English

The income statement, or P&L, is income minus expenses over a period. For an e-commerce seller it has three levels, and each answers a different question. Gross profit is revenue minus cost of goods sold (COGS): is the product itself worth selling? Operating profit subtracts running costs such as shipping, salaries and marketing: does the business work? Net profit subtracts interest and income tax: what is left for the owners?

COGS is the purchase cost of the units that were sold, not of the units that were bought. Stock you bought and still hold is an asset. It becomes an expense only when it sells, which is why buying 150,000 of stock below produces only 108,000 of COGS. From here on the lesson uses one ledger in its own fresh database. It keeps lesson 02's journal_entry and journal_line idea, names the date entry_date, adds an account table holding each account's type and report line, and adds partner, doc, doc_date and due_date columns for Part 6. The VAT on these sales is left out on purpose until lesson 04.

-- الدالة دي بتسجّل قيد كامل، وبترفضه لو مش متوازن
create or replace function post(d date, m text, lines jsonb) returns bigint language plpgsql as $$
declare eid bigint; td numeric; tc numeric;
begin
  select coalesce(sum((l->>'debit')::numeric),0), coalesce(sum((l->>'credit')::numeric),0)
    into td, tc from jsonb_array_elements(lines) l;
  if td <> tc or td = 0 then raise exception 'unbalanced: % <> %', td, tc; end if;
  insert into journal_entry(entry_date, memo) values (d, m) returning id into eid;
  insert into journal_line(entry_id, account, debit, credit, partner, doc, doc_date, due_date)
  select eid, l->>'account', coalesce((l->>'debit')::numeric,0), coalesce((l->>'credit')::numeric,0),
         l->>'partner', l->>'doc', (l->>'doc_date')::date, (l->>'due_date')::date
    from jsonb_array_elements(lines) l;
  return eid;
end $$;

export function guardPort(raw: string): number {
  const port = Number(raw);
  if (!/^\d+$/.test(raw) || port < 1024 || port > 65535 || [5432, 27017, 6379].includes(port)) {
    throw new Error(`refusing port '${raw}'`);
  }
  return port;
}

// التحويل: الـ pg بيرجّع numeric كـ string، فبنحوّله لقروش BigInt من غير float خالص
export function toMinor(value: string): bigint {
  const [whole, frac = ""] = value.split(".");
  const sign = whole!.startsWith("-") ? -1n : 1n;
  const digits = BigInt(whole!.replace("-", "")) * 100n + BigInt(frac.padEnd(2, "0").slice(0, 2));
  return sign * digits;
}

export function fmt(minor: bigint): string {
  const sign = minor < 0n ? "-" : "";
  const abs = minor < 0n ? -minor : minor;
  const whole = (abs / 100n).toString().replace(/\B(?=(\d{3})+(?!\d))/g, ",");
  return `${sign}${whole}.${(abs % 100n).toString().padStart(2, "0")}`;
}

Part 3 — Balance sheet 🟢 Basicالجزء 3 — الـ balance sheet

English

The balance sheet is a snapshot at one moment: what the company has (assets), what it owes (liabilities), and what belongs to the owners (equity). The equation Assets = Liabilities + Equity holds for the same mechanical reason as the trial balance.

The piece that trips programmers is how profit reaches equity. During the year, profit lives in income and expense accounts. So a balance sheet that selects only asset, liability and equity accounts will not balance mid-year. It must add the current period's net profit to equity. At year-end the closing entry moves that profit into retained earnings, which lesson 04 writes by hand. Assert the equation in code, because a failure tells you more than you'd expect: the amount it's off by equals the total of whatever you left out.

const db = await connect();
try {
  const asOf = "2026-03-31";

      from journal_line l

      join account a on a.code = l.account
     where e.entry_date <= $1
     group by a.type`, [asOf]);

  const debitNet = (t: AccountType) => toMinor(rows.find((r) => r.type === t)?.net ?? "0");

  function balanceSheet(omit?: AccountType) {
    const pick = (t: AccountType) => (t === omit ? 0n : debitNet(t));
    const assets = pick("asset");
    const liabilities = -pick("liability");
    const contributed = -pick("equity");
    // النقطة المهمة: ربح الفترة لسه قاعد في حسابات الدخل والمصروفات، فلازم يتضاف للـ equity
    const currentProfit = -pick("income") - pick("expense");
    return { assets, liabilities, contributed, currentProfit, equity: contributed + currentProfit };
  }

  function assertEquation(label: string, omit?: AccountType): void {
    const b = balanceSheet(omit);
    const right = b.liabilities + b.equity;
    process.stdout.write(`${label.padEnd(18)}A=${fmt(b.assets).padEnd(11)} L=${fmt(b.liabilities).padEnd(11)} E=${fmt(b.equity).padEnd(11)} `);
    if (b.assets !== right) throw new Error(`off by ${fmt(b.assets - right)}`);
    console.log("OK");
  }

  const full = balanceSheet();
  console.log(`equity = capital ${fmt(full.contributed)} + current profit ${fmt(full.currentProfit)}`);
  assertEquation("complete");
  for (const omit of ["expense", "liability"] as const) {
    try {
      assertEquation(`without ${omit}`, omit);
    } catch (err) {
      console.log(`FAILED ${(err as Error).message}`);
    }
  }
} finally {
  await db.end();
}

Part 4 — Cash flow statement 🟢 Basicالجزء 4 — الـ cash flow statement

English

Profit is an opinion about a period; cash is a fact in the bank. The cash flow statement explains the gap, in three sections: operating, investing and financing. The indirect method starts from net profit and adjusts for everything that was profit without being cash. An increase in receivables means you earned money you haven't collected, so subtract it. An increase in inventory means cash became stock, so subtract it. An increase in payables means you haven't paid yet, so add it. (The direct method lists actual receipts and payments instead.)

On the ledger above, Q1 shows a net profit of 28,000 and cash from operations of −47,000. There is no investing activity here, and financing brought in 300,000. The statement has a built-in test: its net change must equal the movement of the cash account.

Now the classic trap, as a model. A B2B seller gives 90-day terms, makes a healthy 40% gross margin, pays for stock a month before selling it, and triples its sales in six months. type Scenario = { label: string; sales: number[]; termsMonths: number; openingCash: number };

const COGS_RATE = 0.6;
const OPEX = 25_000;
const MONTHS = 12;

function run({ label, sales, termsMonths, openingCash }: Scenario, print: boolean) {
  // الماضي: قبل أول شهر كانت المبيعات ثابتة على أول رقم
  const at = (m: number) => sales[Math.min(Math.max(m, 1), sales.length) - 1]!;
  let cash = openingCash;
  let totalProfit = 0;
  let lowest = { month: 0, cash: openingCash };
  if (print) console.log(`${label}\nmonth     sales    profit collected  paid-out      cash`);
  for (let m = 1; m <= MONTHS; m++) {
    const profit = at(m) * (1 - COGS_RATE) - OPEX;
    const collected = at(m - termsMonths);
    // المخزون: بيتشترى ويتدفع قبل البيع بشهر
    const paidOut = at(m + 1) * COGS_RATE + OPEX;

    totalProfit += profit;
    if (cash < lowest.cash) lowest = { month: m, cash };

  }
  return { label, totalProfit, lowest, closing: cash };
}

Part 5 — Accrual, cash and revenue recognition 🟢 Basicالجزء 5 — الـ accrual والـ cash والـ revenue recognition

English

Under the cash basis you record income and expenses when money moves. Under the accrual basis you record them when they're earned or incurred, whenever the money moves. Everything so far has been accrual: the invoice is revenue on its date, even though the customer pays months later.

Revenue recognition is the rule for when revenue counts as earned. The clearest case for a programmer is a subscription. A customer pays EGP 12,000 upfront for 12 months starting 1 October. On day one you have the cash but you haven't delivered anything, so you owe the customer a year of service. That is a liability called deferred revenue. Each month you deliver one twelfth, and 1,000 moves from the liability into revenue. That's 13 entries: one when billing, twelve releases.

This is the concept only. The real standard is IFRS 15, and it has rules on performance obligations, discounts, bundles and contract changes that this lesson doesn't teach. For a real contract, ask an accountant.

Part 6 — Receivables, payables and aging 🟡 Intermediateالجزء 6 — الـ receivables والـ payables والـ aging

English

Accounts receivable (AR) is what customers owe you; accounts payable (AP) is what you owe suppliers. The general ledger holds one control account for each, and a sub-ledger holds the detail per partner and per document. The rule that keeps them honest: the sum of the sub-ledger must equal the control account.

Aging sorts open items into buckets by how late they are: 0–30, 31–60, 61–90 and 90+ days past due, plus a "not due" column for what isn't late yet. Two things make it correct. Age from the due date, because a 90-day invoice issued 100 days ago is only 10 days late. And use the open amount, because a partly paid invoice only exposes you for what's left. It's one query: compute open items, then bucket with CASE.

       |                  |                      |
  -----+------------------+----------------------+-----> time
       |<-- not late ---->|<-- days past due --->|
       |<---------- days since invoice --------->|

  aging counts ONLY "days past due"
الخط ده الزمن. من تاريخ الفاتورة لتاريخ الاستحقاق العميل مش متأخر. ومن تاريخ الاستحقاق لتاريخ التقرير دي أيام التأخير الحقيقية. الـ aging بيعدّ أيام التأخير بس، مش كل الأيام من تاريخ الفاتورة.
import { connect } from "./db.ts";
import { fmt, toMinor } from "./money.ts";

const ASOF = "2026-09-30";

// الـ query: الـ open items الأول، وبعدين توزيعهم على الـ buckets بـ CASE
const agingSql = (dateColumn: "due_date" | "doc_date", amountColumn: "residual" | "original") => `
  with items as (
    select l.partner, l.doc,
           max(l.doc_date) as doc_date,
           max(l.due_date) as due_date,
           sum(case when $3::int = 1 then l.debit else l.credit end) as original,
           $3::int * sum(l.debit - l.credit) as residual
      from journal_line l
      join journal_entry e on e.id = l.entry_id
     where l.account = $2 and e.entry_date <= $1::date
     group by l.partner, l.doc
    having sum(l.debit - l.credit) <> 0
  ), aged as (
    select *, $1::date - ${dateColumn} as days from items
  )
  select coalesce(partner, 'TOTAL') as partner,
         sum(case when days < 0               then ${amountColumn} else 0 end) as not_due,
         sum(case when days between 0  and 30 then ${amountColumn} else 0 end) as d0_30,
         sum(case when days between 31 and 60 then ${amountColumn} else 0 end) as d31_60,
         sum(case when days between 61 and 90 then ${amountColumn} else 0 end) as d61_90,
         sum(case when days > 90              then ${amountColumn} else 0 end) as d90_plus,
         sum(${amountColumn}) as total
    from aged
   group by rollup (partner)
   order by partner nulls last`;

type Row = { partner: string; not_due: string; d0_30: string; d31_60: string; d61_90: string; d90_plus: string; total: string };
const cols = ["not_due", "d0_30", "d31_60", "d61_90", "d90_plus", "total"] as const;
const print = (r: Row) => console.log(r.partner.padEnd(12), ...cols.map((c) => fmt(toMinor(r[c])).padStart(10)));

try {

  header();

    select sum(l.debit - l.credit) as net from journal_line l
      join journal_entry e on e.id = l.entry_id
     where l.account = '1100' and e.entry_date <= $1`, [ASOF]);
  const subledger = toMinor(ar.rows.at(-1)!.total);
  const control = toMinor(gl.rows[0]!.net);

  header();
  for (const [label, d, a] of [["right", "due_date", "residual"], ["by inv date", "doc_date", "residual"], ["full amount", "due_date", "original"]] as const) {
    const { rows } = await db.query<Row>(agingSql(d, a), [ASOF, "1100", 1]);

فين هستخدمه في شغلي؟ منصة B2B فيها زرار "ابعت reminder" أو قاعدة "وقّف الطلبات للعميل المتأخر". لو حسبت بتاريخ الفاتورة، هتوقّف عميل شروطه 90 يوم وهو ملتزم، والـ sales هيزعل. ولو حسبت بالمبلغ الكامل، هتبعت reminder بمبلغ العميل دفع نصه. الغلطتين دول بالظبط اللي الجدول فوق بيبيّنهم بالأرقام.
Trade-off: compute the open amount, or store it? Deriving the open amount from lines, as above, can't go stale, but it scans the lines on every report. Storing it, as Odoo does with amount_residual, makes reports cheap, but then every payment, refund and reversal has to keep it correct. Start derived. Store it when you've measured a reason, and keep the derived query as the check.
حساب المبلغ المفتوح من السطور زي فوق مستحيل يبقى قديم، بس بيعمل scan للسطور في كل تقرير. تخزينه زي amount_residual في Odoo بيخلي التقارير رخيصة، بس ساعتها كل payment وrefund وreversal لازم يحافظ عليه صح. ابدأ بالحساب، وخزّن لما تقيس سبب حقيقي، وخلي الـ query المحسوبة هي الفحص.

Common mistakes · غلطات شائعة

❌ Balance sheet without current profit 
-- الغلط: مفيش ربح الفترة، فالمعادلة مش هتتوازن
select type, sum(debit - credit)
  from v_lines
 where type in ('asset','liability','equity')
 group by type;
✅ Add income and expenses into equity 
-- الصح: الخمس أنواع، وربح الفترة بيتضاف للـ equity
select case when type in ('income','expense')
            then 'equity' else type end as section,
       sum(debit - credit)
  from v_lines
 group by 1;
بالعامية

❌ لو اخترت الـ asset والـ liability والـ equity بس، ربح الفترة هيفضل برّه، والمعادلة هتطلع بفرق بيساوي الربح بالظبط. ✅ الصح تدخّل الدخل والمصروفات جوه الـ equity لحد ما قيد الإقفال ينقلهم.

❌ Aging by invoice date

  from items;
✅ Aging by due date 
-- الصح: التأخير بيبدأ من تاريخ الاستحقاق

  from items;
بالعامية

❌ الحساب من تاريخ الفاتورة طلّع الـ 90+ بـ 134,000 بدل 90,000 في مثالنا، وبيعاقب العميل اللي واخد شروط طويلة. ✅ الحساب من تاريخ الاستحقاق هو اللي بيقيس التأخير الحقيقي.

❌ Counting a partly paid invoice in full

select doc, sum(debit) as exposure
  from journal_line
 where account = '1100'
 group by doc
having sum(debit - credit) <> 0;

having sum(debit - credit) <> 0;

❌ جمع الـ debit بس بيتجاهل الدفعات الجزئية: في مثالنا طلع 204,000 بدل 164,000، مع إن الفواتير المقفولة مستبعدة. ✅ الصح تجمع الـ debit ناقص الـ credit لكل مستند، وتشيل اللي باقيه صفر.

await post(today, [
  dr("1000 Cash", 12_000),

// الحل: القسمة بالقروش، والباقي بيتوزع قرش قرش على أول الشهور
export function recognitionSchedule(totalMinor: bigint, months: number): bigint[] {
  if (months <= 0) throw new Error("months must be positive");
  const n = BigInt(months);
  const base = totalMinor / n;
  const remainder = Number(totalMinor % n);
  return Array.from({ length: months }, (_, i) => base + (i < remainder ? 1n : 0n));
}

for (const [total, months] of [[1_200_000n, 12], [100_000n, 3], [99_999n, 7]] as const) {
  const schedule = recognitionSchedule(total, months);
  const sum = schedule.reduce((s, v) => s + v, 0n);
  console.log(`${total} over ${months}:`, schedule.join(" "), "| sum matches:", sum === total);
}

Cheat sheet · الخلاصة

  • Trial balance: one row per account. It balances because every entry balances.
  • Balanced doesn't mean correct: a wrong account, a missing entry and a duplicate all balance.
  • Income statement covers a period: revenue − COGS = gross; − opex = operating; − interest and tax = net.
  • COGS is the cost of what was sold. Unsold stock is an asset.
  • Balance sheet is a moment: A = L + E, and mid-year E must include current profit.
  • When the equation fails, the difference equals the total of what you left out.
  • Cash flow (indirect): net profit, minus increases in AR and stock, plus increases in AP. It must tie to the cash account.
  • Fast growth with long customer terms can bankrupt a profitable company.
  • Prepayment = deferred revenue (a liability), released as the service is delivered.
  • Aging: bucket the open amount by days past the due date. The sub-ledger must equal the control account.
بالعامية
  • الـ trial balance: صف لكل حساب، وبيتوازن لأن كل قيد متوازن.
  • متوازن مش معناها صح: الحساب الغلط والقيد الناقص والمتكرر كلهم متوازنين.
  • الـ income statement عن فترة: المبيعات ناقص COGS = gross، ناقص مصاريف التشغيل = operating، ناقص الفوايد والضريبة = net.
  • الـ COGS تكلفة اللي اتباع، والبضاعة اللي لسه عندك asset.
  • الـ balance sheet لحظة: A = L + E، وفي نص السنة الـ E لازم يشمل ربح الفترة.
  • لو المعادلة وقعت، الفرق بيساوي إجمالي اللي نسيته.
  • الـ cash flow بالـ indirect: صافي الربح، ناقص زيادة الـ AR والمخزون، زائد زيادة الـ AP، ولازم يطابق حساب الـ cash.
  • النمو السريع مع شروط دفع طويلة ممكن يفلّس شركة كسبانة.
  • الدفع المقدم = deferred revenue (التزام)، وبيتحول مع تقديم الخدمة.
  • الـ aging: وزّع المبلغ المفتوح بأيام التأخير بعد تاريخ الاستحقاق، ومجموع الـ sub-ledger لازم يساوي الـ control account.
