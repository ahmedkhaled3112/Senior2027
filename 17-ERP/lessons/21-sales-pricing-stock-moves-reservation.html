Why this matters · ليه ده مهم

English

Every checkout you have written has a line like if (stock >= qty). In an ERP that single number becomes five different numbers, and picking the wrong one oversells. The price on a line is the output of a rule engine, the tax on it depends on who is buying, and a physical box moving across a warehouse is recorded as double-entry between locations. This lesson runs each of those on real Odoo 20, then races two real database transactions over the last two units. Integration work and interviews both go straight to these questions: which stock number do you trust, and what happens when two people buy the last one?

بالعامية

أي checkout كتبته قبل كده فيه سطر زي if (stock >= qty). في الـ ERP الرقم ده بيبقى خمس أرقام مختلفة، ولو اخترت الغلط هتبيع حاجة مش عندك. السعر اللي على السطر طالع من rule engine، والضريبة عليه بتعتمد على مين اللي بيشتري، والكرتونة لما تتحرك في المخزن بتتسجل double-entry بين locations. الدرس ده بيشغّل كل ده على Odoo 20 حقيقي، وبعدين بيخلي transactions حقيقية تتسابق على آخر وحدتين. شغل الـ integration والـ interviews الاتنين بيروحوا للسؤالين دول على طول: تثق في أنهي رقم stock؟ وإيه اللي بيحصل لو اتنين اشتروا آخر قطعة؟

Part 1 — Pricelists and discounts 🟡 Intermediateالجزء 1 — الـ pricelists والخصومات

English

A product.pricelist holds product.pricelist.item rules. Each rule has a scope (applied_on: variant, product, category or all products), a min_quantity, optional dates, and a compute_price. In Odoo 20 that field takes discount, markup or fixed, with the percentage in price_discount. Older tutorials use percentage and percent_price: the first raises Wrong value and the second Invalid field. Rules are ordered by applied_on, min_quantity desc, categ_id desc, id desc, so the most specific scope and the highest quantity threshold are tried first.

A pricelist discount can reach the customer in two ways. With the "Discounts" setting off (sale.group_discount_per_so_line), the line simply shows a lower unit price: 900, discount 0. With it on, the same rule shows the list price and a visible discount: 1000 at 10%. The subtotal is 9000 either way. The difference is presentation, and it matters to sales people who want the customer to see what they saved.

The books see neither. A 5% manual discount on 10 units at 900 gives a subtotal of 8550, and income is credited 8550. There is no separate "discounts given" journal line, so if finance wants that figure it has to come from the sales lines or be modelled deliberately.

def mkprod(method='fifo', name='Router', valuation='real_time', **kw):
    cat = e['product.category'].create({'name': f'{name} {method}'})
    cat.property_cost_method = method
    cat.property_valuation = valuation
    return e['product.product'].create({'name': name, 'is_storable': True, 'categ_id': cat.id, 'list_price': 1000, 'standard_price': 600, **kw})


def receive(prod, qty, cost):
    po = e['purchase.order'].create({'partner_id': vendor.id, 'picking_type_id': wh.in_type_id.id, 'order_line': [Command.create({'product_id': prod.id, 'product_qty': qty, 'price_unit': cost})]})
    po.button_confirm()
    picking = po.picking_ids
    picking.move_ids.quantity = qty
    picking.move_ids.picked = True
    picking.button_validate()
    return po, picking


def bill(po):
    po.action_create_invoice()
    move = po.invoice_ids
    move.invoice_date = fields.Date.today()
    move.action_post()
    return move


def sell(prod, qty, partner=None, **line):
    so = e['sale.order'].create({'partner_id': (partner or customer).id, 'warehouse_id': wh.id, 'order_line': [Command.create({'product_id': prod.id, 'product_uom_qty': qty, **line})]})
    so.action_confirm()
    return so, so.picking_ids


def ship(picking):
    picking.move_ids.picked = True
    picking.button_validate()


def adjust(prod, location, qty, lot=None):
    # الـ inventory_mode هو اللي بيسمح بتعديل الجرد
    vals = {'product_id': prod.id, 'location_id': location.id, 'inventory_quantity': qty}
    if lot:
        vals['lot_id'] = lot.id
    e['stock.quant'].with_context(inventory_mode=True).create(vals).action_apply_inventory()


def show(move):
    print(move.move_type)
    for l in move.line_ids.sorted(lambda x: -x.debit):
        print(f'  {l.account_id.code} {l.account_id.account_type:18} D {l.debit:>9.2f}  C {l.credit:>9.2f}')


def quants(prod):
    return e['stock.quant'].sudo().search([('product_id', '=', prod.id)], order='location_id, id')


def print_quants(prod):
    for q in quants(prod):
        print(f'  {q.location_id.complete_name:22} {q.location_id.usage:9} qty {q.quantity:>6} reserved {q.reserved_quantity:>4} {q.lot_id.name or ""}')
    print('  sum of all quants =', sum(quants(prod).mapped('quantity')))

بالعامية

الـ product.pricelist جواها قواعد product.pricelist.item. كل قاعدة ليها نطاق (applied_on: variant، منتج، category، أو كل المنتجات)، وmin_quantity، وتواريخ لو عايز، وcompute_price. في Odoo 20 الحقل ده قيمه discount أو markup أو fixed، والنسبة في price_discount. الـ tutorials القديمة بتستخدم percentage وpercent_price: الأولانية بتدي Wrong value والتانية Invalid field. القواعد مترتبة بـ applied_on, min_quantity desc, categ_id desc, id desc، يعني النطاق الأضيق وأعلى حد كمية بيتجربوا الأول.

خصم الـ pricelist ممكن يوصل للعميل بطريقتين. لو إعداد "Discounts" مقفول (sale.group_discount_per_so_line)، السطر بيظهر سعر أقل وخلاص: 900 وخصم صفر. لو مفتوح، نفس القاعدة بتظهر سعر القائمة وخصم واضح: 1000 بخصم 10%. الـ subtotal 9000 في الحالتين. الفرق في العرض بس، وده مهم لفريق المبيعات اللي عايز العميل يشوف هو وفّر قد إيه.

الدفاتر مش شايفة الاتنين. خصم يدوي 5% على 10 وحدات بـ 900 بيدي subtotal 8550، والـ income بيتقيد 8550. مفيش سطر قيد منفصل اسمه "خصومات"، فلو المالية عايزة الرقم ده لازم يطلع من سطور البيع أو تعمله modeling مخصوص.

كل Python script في الدرس بيتشغل بعد lab_helpers.py اللي فوق.

Trade-off: lower price or visible discount? A visible discount tells the customer what they saved and lets you report on it from the lines. A lower price is simpler and hides your list price from wholesale customers. Choose per business, and remember that neither one creates a separate accounting line.

Part 2 — Taxes on the line 🟡 Intermediateالجزء 2 — الضرايب على السطر

English

tax_ids on sale.order.line is computed in two steps. First Odoo takes the product's taxes_id and keeps the ones for the line's company: a product shared between companies carries a tax per company, and our router holds four. Then the order's fiscal position runs map_tax on them. The fiscal position comes from the partner, so the same product can be 14% for a Cairo retailer and 0% for a Dubai importer.

In Odoo 20 the mapping is declared on the replacement tax itself, with fiscal_position_ids and original_tax_ids, and compiled into a tax_map on the fiscal position. map_tax has one rule worth reading: a tax that is not in the map stays only if it has no fiscal positions of its own, or lists this one.

The invoice copies the line's tax. The line is a snapshot: changing the product's taxes later does not touch orders that already exist. Lesson 23 opens the tax engine itself (price-included taxes, groups, rounding).

Part 3 — Moves, move lines, quants 🟡 Intermediateالجزء 3 — الـ moves والـ move lines والـ quants

English

Three models answer three different questions. stock.move is the intent: "3 routers should go from Stock to Customers". stock.move.line is what physically moved or is reserved to move, with the exact location, lot and package; one move can have several. stock.quant is the current balance per product, location, lot, package and owner, with quantity and reserved_quantity.

Inventory is double-entry too. Every move goes from one location to another, and virtual locations exist so that the other side always has somewhere to land: supplier, customer, inventory (adjustments and scrap), production, transit. When 10 units arrive, the Stock quant is +10 and the Vendors quant is −10. The sum across all locations stays zero, which gives you an invariant you can assert. It is the same idea as the ledger in lesson 5, with units instead of money.

  sale.order.line  --creates-->  stock.move  (intent: demand 3)
                                    |
                                    | 1..n
                                    v
                             stock.move.line (reality: qty 3, lot, package)
                                    |
                     on done: -3    |    +3
                                    v
        stock.quant[Stock]  ------------------>  stock.quant[Customers]
        qty 10 -> 7                              qty 0 -> 3

        sum of quantity over ALL locations is always 0
السطر في الأوردر بيولّد stock.move وده النية (مطلوب 3). الـ move ليه واحد أو أكتر stock.move.line وده الواقع بالـ lot والـ package. لما الحركة تخلص، الـ quant في Stock بينزل 3 والـ quant في Customers بيطلع 3، ومجموع كل الـ quants في كل الـ locations بيفضل صفر.

عندك 3 models بيجاوبوا على 3 أسئلة مختلفة. stock.move هو النية: "3 routers المفروض يروحوا من Stock لـ Customers". stock.move.line هو اللي اتحرك فعلًا أو محجوز يتحرك، بالـ location والـ lot والـ package بالظبط، والـ move الواحد ممكن يبقى ليه كذا واحد. stock.quant هو الرصيد الحالي لكل منتج وlocation وlot وpackage وowner، وفيه quantity وreserved_quantity.

فين هستخدمه في شغلي؟ لو بتبني inventory service في Postgres، متعملش عمود products.stock وتعمله UPDATE. اعمل جدول حركات (from، to، qty) وجدول رصيد مشتق منها. لما عميل يشتكي إن الرقم غلط، هتقدر ترجع لكل حركة. والغلطة الشائعة: تفتكر إن reserved_quantity بينقص quantity، وهو مش بينقصها غير عند التسليم.
Interview question "Why does an ERP record a stock move between two locations instead of decrementing a counter?" → Because it preserves the source of every unit: the move history can rebuild any balance, the sum across locations is a checkable invariant, and shrinkage or a vendor return has a real place to land instead of a mystery adjustment.
"ليه الـ ERP بيسجل حركة بين location والتاني بدل ما ينقص عدّاد؟" ← عشان بيحفظ مصدر كل وحدة: تاريخ الحركات يقدر يبني أي رصيد من الأول، ومجموع الـ locations invariant تقدر تتأكد منه، والهالك أو المرتجع للمورد بيلاقي مكان حقيقي يروح له بدل تعديل مجهول.

Part 5 — Reservation and races 🔴 Advancedالجزء 5 — الحجز والـ races

English

Reserving means writing reserved_quantity on the quant and creating a move line. No goods move. With 2 units and two orders for 2, the first is assigned with quantity 2 and the second stays confirmed with 0. Partial availability is a real state, partially_available, and one move can reserve from several shelves through several move lines. That is why this is harder than a counter: many sellers, many locations, partial answers.

The core is _update_available_quantity in stock_quant.py, which _update_reserved_quantity delegates to. It calls try_lock_for_update(allow_referencing=True, limit=1), which runs FOR NO KEY UPDATE SKIP LOCKED. If another transaction holds the row, Odoo doesn't wait. It creates a second quant row for the same product and location, and _merge_quants folds the duplicates together later. Its docstring states the reason: "we'll create a new quant in order for these transactions to not rollback."

Cursors run at REPEATABLE READ, so each transaction checks availability against its own snapshot. The race below uses two real cursors and the real _action_assign, and it has three outcomes depending on timing.

So a reservation in Odoo is a strong hint and not a guarantee. Timing A produces an over-reservation with no error at all. Timing B raises a serialization failure, and the HTTP layer's retrying runs the request again up to 5 times, which turns it into timing C. The final check is physical: when a shipment is validated, _free_reservation takes away reservations that can no longer be honoured. Odoo chose to keep warehouse staff working and repair afterwards.

A flash sale wants the opposite trade. Here are four strategies racing 50 buyers over 10 units, on a throwaway Postgres and a private Redis. The patterns come from section 09: locks, isolation and retries and Redis atomicity.

// تشغيل: ⁦node src/flash-sale.ts <pgPort> <redisPort>⁩
import pg from "pg";
import { Redis } from "ioredis";

function guard(port: string | undefined): number {
  const n = Number(port);
  // ممنوع البورت الفاضي أو الـ default: كده هتوصل لقاعدة بيانات حقيقية
  if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error("refusing port " + port);
  }
  return n;
}

const STOCK = 10;
const BUYERS = 50;
const pool = new pg.Pool({ host: "127.0.0.1", port: guard(process.argv[2]), user: "ledger", database: "postgres", max: 20 });
const redis = new Redis({ host: "127.0.0.1", port: guard(process.argv[3]) });

const reset = async () => {
  await pool.query("DROP TABLE IF EXISTS stock");
  await pool.query("CREATE TABLE stock (sku text PRIMARY KEY, qty int NOT NULL)");
  await pool.query("INSERT INTO stock VALUES ('router', $1)", [STOCK]);
};

const pause = () => new Promise((r) => setTimeout(r, 2));

// ❌ بيقرا وبعدين يكتب: كل الـ buyers بيشوفوا نفس الرقم
async function readThenWrite(): Promise<boolean> {
  const { rows } = await pool.query("SELECT qty FROM stock WHERE sku='router'");
  if (rows[0].qty < 1) return false;
  await pause();
  await pool.query("UPDATE stock SET qty = $1 WHERE sku='router'", [rows[0].qty - 1]);
  return true;
}

// ✅ الـ row lock بيخلي الـ buyers يقفوا في طابور
async function selectForUpdate(): Promise<boolean> {
  const c = await pool.connect();
  try {
    await c.query("BEGIN");
    const { rows } = await c.query("SELECT qty FROM stock WHERE sku='router' FOR UPDATE");
    if (rows[0].qty < 1) { await c.query("ROLLBACK"); return false; }
    await pause();
    await c.query("UPDATE stock SET qty = qty - 1 WHERE sku='router'");
    await c.query("COMMIT");
    return true;
  } finally { c.release(); }
}

// ✅ الشرط والخصم في statement واحد
async function conditionalUpdate(): Promise<boolean> {
  const r = await pool.query("UPDATE stock SET qty = qty - 1 WHERE sku='router' AND qty >= 1");
  return r.rowCount === 1;
}

// ✅ سريع جدًا، بس العدّاد برّه الـ transaction بتاعة الأوردر
async function redisDecr(): Promise<boolean> {
  const left = await redis.decrby("stock:router", 1);
  if (left >= 0) return true;
  await redis.incrby("stock:router", 1);
  return false;
}

async function race(name: string, buy: () => Promise<boolean>, left: () => Promise<number | string | null>) {
  const started = performance.now();
  const results = await Promise.all(Array.from({ length: BUYERS }, buy));
  const ms = performance.now() - started;
  console.log(name.padEnd(20), "sold", String(results.filter(Boolean).length).padStart(2), "left", String(await left()).padStart(3), `≈${ms.toFixed(0)} ms`);
}

try {
  await reset();
  await race("read-then-write", readThenWrite, remaining);
  await reset();
  await race("SELECT FOR UPDATE", selectForUpdate, remaining);
  await reset();
  await race("conditional UPDATE", conditionalUpdate, remaining);
  await redis.set("stock:router", STOCK);
  await race("Redis DECRBY", redisDecr, () => redis.get("stock:router"));

  // الـ process بيقع بعد الخصم وقبل ما الأوردر يتكتب في الـ DB لـ 3 buyers
  await redis.set("stock:router", STOCK);
  await pool.query("DROP TABLE IF EXISTS orders");
  await pool.query("CREATE TABLE orders (id serial PRIMARY KEY)");
  let n = 0;
  await Promise.all(Array.from({ length: BUYERS }, async () => {
    if (!(await redisDecr())) return;
    n += 1;
    if (n <= 3) return;
    await pool.query("INSERT INTO orders DEFAULT VALUES");
  }));
  const orders = (await pool.query("SELECT count(*)::int AS n FROM orders")).rows[0].n as number;
  console.log("after crash: redis left", await redis.get("stock:router"), "orders in DB", orders, "units lost", STOCK - orders);
} finally {
  await pool.end();
  redis.disconnect();
}

Walk me through the options." → Pessimistic row lock (exact, serialises), conditional update (exact, cheapest, single counter), atomic counter in Redis (fast, needs compensation and reconciliation), or accept over-reservation and repair at fulfilment, which is what Odoo does. Part 6 — Lots and serials 🟡 Intermediateالجزء 6 — الـ lots والـ serial numbers

English

tracking on the product is lot (a batch shares a number), serial (one number per unit), or unset for no tracking. The value none from older tutorials raises Wrong value for product.template.tracking. Numbers live in stock.lot, and the name must be unique per product within a company. Inventory adjustments go through stock.quant with inventory_mode=True, inventory_quantity and action_apply_inventory.

Once a product is tracked, quants split by lot and reservation picks lots for you, oldest first with the default removal strategy. One order can get several lots: below, Mansoura gets one unit from each. Validating a tracked move without a lot is refused.

The payoff is a recall. A sale order doesn't know which lot it received, because the lot is on the move line. So "who got the bad batch?" is one query on stock.move.line filtered by lot, state done and destination usage customer. A correct recall also subtracts what came back, by querying the opposite direction.

Part 7 — What breaks 🔴 Advancedالجزء 7 — إيه اللي بيكسر

English

Negative quants. Reservation is advisory for a person at the warehouse. If someone types 5 on a move with 2 in stock and validates, Odoo accepts it: Stock goes to −3 and total_value to −300. It is usually a receipt that wasn't entered yet, and it will distort costing until it is.

Forgotten reservations. Cancelling releases the reservation: free_qty went from 0 back to 2. A confirmed order nobody cancels holds the stock for ever, so abandoned orders need a job that cancels them. Direct SQL is worse, because reserved_quantity then disagrees with the move lines. _clean_reservations recomputes it from the move lines and repaired the drift below.

The wrong number on a website. Each stock figure answers a different question: qty_available is on hand, free_qty is on hand minus reserved, and virtual_available is on hand plus incoming minus outgoing. Here 10 on hand, 3 reserved and 20 on order give 10, 7 and 27. Show 27 and you promise goods that are still on a truck; show 10 and you sell the 3 already promised. Odoo's own website_sale_stock reads free_qty. A draft quote changes none of them. These are also computed on read from quants and moves, so a busy storefront caches them, and a cached number is stale by definition.

def stock_numbers(product):
    product.invalidate_recordset()
    numbers = {f: product[f] for f in ['qty_available', 'free_qty', 'incoming_qty', 'outgoing_qty', 'virtual_available']}
    # الـ virtual بيتحسب من الأربعة دول
    assert numbers['virtual_available'] == numbers['qty_available'] + numbers['incoming_qty'] - numbers['outgoing_qty']
    return numbers

from collections import defaultdict


def recall(lot):
    # الصافي عند كل عميل = اللي اتشحن ناقص اللي رجع
    net = defaultdict(float)
    lines = e['stock.move.line'].search([('lot_id', '=', lot.id), ('state', '=', 'done')])
    for ml in lines:
        if ml.location_dest_id.usage == 'customer':
            net[ml.picking_partner_id.name] += ml.quantity
        elif ml.location_id.usage == 'customer':
            net[ml.picking_partner_id.name] -= ml.quantity
    return {name: qty for name, qty in net.items() if qty > 0}

Solution · الحل 
// تشغيل: node src/ex-storefront.ts
type Snapshot = { freeQty: number; fetchedAt: number };
type Badge = { label: string; canAdd: boolean; verifyAtCheckout: boolean };

const MAX_AGE_MS = 30_000;
const SAFETY = 2;

function badge(s: Snapshot, now: number): Badge {
  // الرقم القديم مش حقيقة: بنسمح بالإضافة ونتأكد عند الدفع
  if (now - s.fetchedAt > MAX_AGE_MS) return { label: "check at checkout", canAdd: true, verifyAtCheckout: true };
  const sellable = s.freeQty - SAFETY;
  if (sellable <= 0) return { label: "out of stock", canAdd: false, verifyAtCheckout: false };
  if (sellable <= 5) return { label: `only ${sellable} left`, canAdd: true, verifyAtCheckout: true };
  return { label: "in stock", canAdd: true, verifyAtCheckout: false };
}

Cheat sheet · الخلاصة

  • compute_price is discount, markup or fixed; rules sort by scope, then highest min_quantity.
  • A discount shown or a lower price: same subtotal, and the books record the net only.
  • Line tax = product taxes for the company, then fiscal_position.map_tax. The line is a snapshot.
  • stock.move intent, stock.move.line reality, stock.quant balance.
  • Quants sum to zero across all locations, virtual ones included.
  • pull asks where goods come from; push says where they go next. In 2-step, the Delivery appears after the Pick.
  • Reservation writes reserved_quantity; goods move only at validation.
  • SKIP LOCKED plus a new quant can over-reserve with no error; _free_reservation settles it at shipping.
  • Exact counters: conditional UPDATE first, FOR UPDATE when logic needs the row, Redis only with reconciliation.
  • tracking is lot, serial or unset; recalls query stock.move.line.
  • Sell from free_qty, plan from virtual_available, count with qty_available.
بالعامية
  • compute_price قيمه discount أو markup أو fixed، والقواعد بتترتب بالنطاق وبعدين أعلى min_quantity.
  • خصم ظاهر أو سعر أقل: نفس الـ subtotal، والدفاتر بتسجل الصافي بس.
  • ضريبة السطر = ضرايب المنتج للشركة، وبعدين fiscal_position.map_tax. والسطر snapshot.
  • stock.move النية، وstock.move.line الواقع، وstock.quant الرصيد.
  • مجموع الـ quants صفر في كل الـ locations، بالوهمية كمان.
  • pull بتسأل البضاعة جاية منين، وpush بتقول رايحة فين بعد كده. وفي الخطوتين الـ Delivery بيظهر بعد الـ Pick.
  • الحجز بيكتب reserved_quantity، والبضاعة بتتحرك بس عند الـ validation.
  • SKIP LOCKED مع quant جديد ممكن يعمل حجز زيادة من غير error، و_free_reservation بتحسمها عند الشحن.
  • للعدّاد الدقيق: UPDATE بشرط الأول، وFOR UPDATE لو الـ logic محتاج الصف، وRedis بس مع reconciliation.
  • tracking يا lot يا serial يا فاضي، والـ recall بيقرا stock.move.line.
  • بيع من free_qty، وخطط من virtual_available، واعرف اللي في الإيد بـ qty_available.
