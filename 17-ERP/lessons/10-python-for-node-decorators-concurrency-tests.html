Why this matters · ليه ده مهم

English

Lesson 09 gave you the language. This one gives you the idioms that Odoo's code is built from: @api.depends is a decorator, with self.env.cr.savepoint(): is a context manager, raise UserError(...) is what your user reads on screen. And it answers the question every Node developer asks in week one: why is this framework not async?

Money and time deserve special attention in an ERP. Odoo stores money in exact numeric columns and then hands it to you as a binary float. You need to know why that works, and where it stops working.

Part 1 — Decorators 🟢 Basicالجزء 1 — الـ decorators

English

A decorator is a function that takes a function and returns a function. The @ line is only syntax: @retry(times=2) above def post_invoice means post_invoice = retry(times=2)(post_invoice), and it runs once, when the module is imported. A decorator that takes arguments therefore has three layers: the factory (retry), the decorator (decorate), and the wrapper that runs on every call. Stacked decorators apply from the bottom up. functools.wraps copies the original's name, docstring and __dict__ onto the wrapper.

import functools
import time


# الـ decorator البسيط: function بتاخد function وترجّع function
def timed(function):
    @functools.wraps(function)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return function(*args, **kwargs)
        finally:
            elapsed_ms = (time.perf_counter() - start) * 1000
            print(f"{function.__name__} took about {round(elapsed_ms, -1):.0f} ms")

    return wrapper


# الـ decorator بـ arguments: طبقة زيادة، retry(times=3) هي اللي بترجّع الـ decorator
def retry(times: int, delay: float = 0.0, on: tuple[type[Exception], ...] = (ConnectionError,)):
    def decorate(function):
        @functools.wraps(function)
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return function(*args, **kwargs)
                except on as error:
                    print(f"attempt {attempt}/{times} failed: {error}")
                    if attempt == times:
                        raise
                    time.sleep(delay)

        return wrapper

    return decorate


calls = {"count": 0}


# الترتيب من تحت لفوق: retry بيلف الأصلية، و timed بيلف نتيجة retry
@timed
@retry(times=3, delay=0.05)
def fetch_exchange_rate(currency: str) -> str:
    """Read today's rate from the bank."""
    calls["count"] += 1
    if calls["count"] < 3:
        raise ConnectionError("bank API timeout")
    return f"{currency}=48.25"

In TypeScript you get the same effect with a higher-order function, which works on any function. TypeScript's @decorator syntax is narrower: it applies only to classes and class members, and a plain function can't be decorated. Node 22 can't run it directly either: type stripping leaves @logged in place and it fails with SyntaxError: Invalid or unexpected token, so it has to go through tsc (compiled and run here with TypeScript 7.0.2).

// نفس الفكرة في TypeScript بـ higher-order function، وبتشتغل على أي function
function withRetry<A extends unknown[], R>(fn: (...args: A) => R, times: number) {
  return (...args: A): R => {
    for (let attempt = 1; ; attempt++) {
      try {
        return fn(...args);
      } catch (error) {
        console.log(`attempt ${attempt}/${times} failed: ${(error as Error).message}`);
        if (attempt === times) throw error;
      }
    }
  };
}

let calls = 0;
const fetchExchangeRate = withRetry((currency: string): string => {
  calls += 1;
  if (calls < 3) throw new Error("bank API timeout");
  return `${currency}=48.25`;
}, 3);

console.log(fetchExchangeRate("USD"));

Now read Odoo's decorators in odoo/orm/decorators.py. You might expect wrappers that intercept calls. Mostly they aren't: @api.depends, @api.constrains, @api.onchange and @api.ondelete are all built on a four-line helper called attrsetter, which sets an attribute on the function and returns the same function. @api.model does the same with _api_model = True, except on create, where it delegates to model_create_multi. The framework reads that metadata when the registry loads. Here is the mechanism, in miniature.

import functools


# الدالة دي منسوخة زي ما هي من odoo/orm/decorators.py
def attrsetter(attr, value):
    """ Return a function that sets ``attr`` on its argument and returns it. """
    def setter(method):
        setattr(method, attr, value)
        return method

    return setter


def depends(*fields):
    return attrsetter("_depends", fields)


def constrains(*fields):
    return attrsetter("_constrains", fields)


class Invoice:
    # ملحوظة: مفيش wrapper هنا، الـ function الأصلية هي اللي فضلت
    @depends("line_ids.subtotal", "currency_id")
    def compute_total(self) -> None: ...

    @constrains("total")
    def check_total(self) -> None: ...

    def plain_helper(self) -> None: ...


# ده اللي الـ framework بيعمله وقت التحميل: بيقرا الـ metadata ويبني الخريطة
for name, member in vars(Invoice).items():
    if hasattr(member, "_depends"):
        print(name, "recomputes when", member._depends)
    if hasattr(member, "_constrains"):
        print(name, "runs when", member._constrains, "changes")
# → compute_total recomputes when ('line_ids.subtotal', 'currency_id')
# → check_total runs when ('total',) changes


# ❌ لو لفيت الـ method من غير wraps الـ metadata بتضيع
def careless(function):
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs)

    return wrapper


# ✅ الـ wraps بتنسخ __dict__ كمان، فـ _depends بتفضل موجودة
def careful(function):
    @functools.wraps(function)
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs)

    return wrapper


print(hasattr(careless(Invoice.compute_total), "_depends"))
# → False
print(careful(Invoice.compute_total)._depends)
# → ('line_ids.subtotal', 'currency_id')

الـ decorator هو function بتاخد function وترجّع function. سطر الـ @ مجرد syntax: @retry(times=2) فوق def post_invoice معناها post_invoice = retry(times=2)(post_invoice)، وبيتنفذ مرة واحدة وقت الـ import. فالـ decorator اللي بياخد arguments فيه 3 طبقات: الـ factory (retry)، والـ decorator (decorate)، والـ wrapper اللي بيشتغل مع كل call. ولو أكتر من decorator بيتطبقوا من تحت لفوق. و functools.wraps بتنسخ اسم الأصلية والـ docstring والـ __dict__ على الـ wrapper.

في TypeScript بتوصل لنفس النتيجة بـ higher-order function، وبتشتغل على أي function. أما syntax الـ @decorator في TS فأضيق: على classes وأعضائها بس، وأي function عادية متتحطش عليها. و Node 22 مش بيعرف يشغّله مباشرةً: الـ type stripping بيسيب @logged زي ما هو ويقع بـ SyntaxError: Invalid or unexpected token، فلازم يعدّي على tsc (اتعمله compile وشغّلناه هنا بـ TypeScript 7.0.2).

دلوقتي اقرا decorators بتوع Odoo في odoo/orm/decorators.py. ممكن تتوقع wrappers بتعترض الـ calls. أغلبها لأ: @api.depends و @api.constrains و @api.onchange و @api.ondelete كلهم مبنيين على helper من 4 سطور اسمه attrsetter، بيحط attribute على الـ function وبيرجّع نفس الـ function. و @api.model بيعمل نفس الحكاية بـ _api_model = True، ما عدا مع create بيحوّلها على model_create_multi. والـ framework بيقرا الـ metadata دي وقت تحميل الـ registry، وده اللي عملناه في المثال المصغر. لاحظ في آخر سطر من الـ shell: _compute_amount اتعمله override في point_of_sale من غير decorator، فالنسخة العليا مفيهاش _depends، و Odoo بيعدّي على كل النسخ في الـ MRO بـ resolve_mro جوه Field.get_depends ويجمع منهم. ولو لفيت method بـ wrapper من غير wraps، الـ metadata بتضيع زي ما شفت في careless.

فين هستخدمه في شغلي؟ لما تكتب @api.depends('line_ids.price_subtotal') هتعرف إن السطر ده مش بينفذ حاجة وقت الـ call: هو بيسجّل dependency، وعشان كده لو نسيت field فيها الحقل مش هيتحسب من غير أي error (الدرس 15). وفي الـ integration هتكتب @retry حوالين نداء لـ API بنك، زي الـ middleware في Express. والغلطة الشائعة: @retry على عملية مش idempotent زي "اخصم من الكارت" فتخصم 3 مرات.
What breaks A retry is only safe on idempotent work (see idempotency keys), and time.sleep inside a request holds that worker the whole time. Odoo's own retry, retrying() in odoo/http/retrying.py, rolls back the transaction between tries, tries at most 5 times, and retries only concurrency failures: an integrity error is turned into a ValidationError instead.
الـ retry آمن على الشغل الـ idempotent بس (شوف idempotency keys)، و time.sleep جوه request بيمسك الـ worker طول الوقت. والـ retry بتاع Odoo نفسه، retrying() في odoo/http/retrying.py، بيعمل rollback للـ transaction بين المحاولات، وبيجرّب 5 مرات بالكتير، وبيعيد في أخطاء الـ concurrency بس: أما الـ integrity error فبيتحول لـ ValidationError.

Part 2 — Context managers 🟢 Basicالجزء 2 — الـ context managers

English

with X as y: calls X.__enter__(), runs the block, then always calls X.__exit__(exc_type, exc, traceback). It's a reusable try/finally. __exit__ receives the exception, so it can decide what to do based on success or failure, and if it returns True the exception is swallowed. @contextlib.contextmanager lets you write the same thing as a generator with exactly one yield: code before the yield is the enter, code after is the exit, and an exception in the block is re-raised at the yield.

A savepoint is the perfect example, because what you do at the end depends on whether the block failed. The example uses sqlite3 from the standard library, so that it runs anywhere.

import sqlite3
from collections.abc import Iterator
from contextlib import contextmanager

connection = sqlite3.connect(":memory:", isolation_level=None)
connection.execute("CREATE TABLE payments (ref TEXT PRIMARY KEY, amount INTEGER)")


# النسخة الأولى: class فيها __enter__ و __exit__
class Savepoint:
    def __init__(self, db: sqlite3.Connection, name: str) -> None:
        self.db = db
        self.name = name

    def __enter__(self) -> "Savepoint":
        self.db.execute(f"SAVEPOINT {self.name}")
        return self

    # الـ exit بياخد الـ exception نفسه، وده الفرق الكبير عن dispose في JS
    def __exit__(self, exc_type, exc, traceback) -> bool:
        if exc_type is not None:
            self.db.execute(f"ROLLBACK TO {self.name}")
        self.db.execute(f"RELEASE {self.name}")
        # القيمة False معناها سيب الـ exception يكمّل طريقه
        return False


# النسخة التانية: generator فيه yield واحد، وقبله enter وبعده exit
@contextmanager
def savepoint(db: sqlite3.Connection, name: str) -> Iterator[None]:
    db.execute(f"SAVEPOINT {name}")
    try:
        yield
    except BaseException:
        db.execute(f"ROLLBACK TO {name}")
        raise
    finally:
        db.execute(f"RELEASE {name}")


def refs() -> list[str]:
    return [row[0] for row in connection.execute("SELECT ref FROM payments ORDER BY ref")]


connection.execute("BEGIN")
connection.execute("INSERT INTO payments VALUES ('PAY-1', 100)")

# الدفعة دي بتفشل، فبيترجع اللي جوه الـ savepoint بس
try:
    with Savepoint(connection, "class_style"):
        connection.execute("INSERT INTO payments VALUES ('PAY-2', 200)")
        connection.execute("INSERT INTO payments VALUES ('PAY-1', 999)")
except sqlite3.IntegrityError as error:
    print("class style:", error)
    # → class style: UNIQUE constraint failed: payments.ref
print(refs())
# → ['PAY-1']

try:
    with savepoint(connection, "generator_style"):
        connection.execute("INSERT INTO payments VALUES ('PAY-3', 300)")
        raise ValueError("amount mismatch")
except ValueError as error:
    print("generator style:", error)
    # → generator style: amount mismatch
print(refs())
# → ['PAY-1']

# الدفعة الناجحة بتفضل، والـ transaction الكبيرة لسه عايشة
with savepoint(connection, "ok"):
    connection.execute("INSERT INTO payments VALUES ('PAY-4', 400)")
connection.execute("COMMIT")
print(refs())
# → ['PAY-1', 'PAY-4']
English

JavaScript's closest feature is using with [Symbol.dispose](). There's one important difference: dispose takes no arguments, so it can't know whether the block threw. A savepoint or transaction needs that information, so in TypeScript you still write try/catch, or a callback wrapper such as Prisma's $transaction(async (tx) => ...). Node 22 also can't parse using yet (SyntaxError: Unexpected identifier 'x' on V8 12.4), so this sample was compiled with TypeScript 7.0.2 first.

class Savepoint implements Disposable {

    console.log(`SAVEPOINT ${name}`);

  [Symbol.dispose](): void {
    console.log(`release ${this.name}, knows about the error: no`);
  }
}

function postPayment(): void {

  throw new Error(`gateway refused inside ${savepoint.name}`);
}

try {
  postPayment();
} catch (error) {
  console.log("caught:", (error as Error).message);

Odoo's real one is env.cr.savepoint() in odoo/sql_db.py, and its __exit__ is one line: self.close(rollback=exc_type is not None). The run below happened in odoo-bin shell on the lab database. The failed insert violates a unique constraint. Inside a savepoint, only the savepoint is lost and the outer transaction carries on. Without one, PostgreSQL marks the whole transaction as aborted and refuses every further statement until a rollback. Odoo uses this pattern everywhere: account_move.py alone has 8 @contextmanager functions, and an ExitStack that enters several of them together.

بالعامية

with X as y: بتنادي X.__enter__()، تنفذ الـ block، وبعدين دايمًا بتنادي X.__exit__(exc_type, exc, traceback). يعني try/finally بتتعاد استخدامها. __exit__ بياخد الـ exception نفسه، فيقدر يقرر على أساس النجاح أو الفشل، ولو رجّع True الـ exception بيتبلع. و @contextlib.contextmanager بتخليك تكتب نفس الحاجة كـ generator فيه yield واحد بالظبط: اللي قبله enter واللي بعده exit، والـ exception اللي في الـ block بيترمي عند الـ yield. الـ savepoint مثال ممتاز لأن اللي بتعمله في الآخر مربوط بفشل الـ block، والمثال مستخدم sqlite3 من الـ standard library عشان يشتغل في أي مكان.

أقرب حاجة في JS هي using مع [Symbol.dispose](). فرق مهم: dispose مش بياخد arguments، فمش هيعرف الـ block رمى ولا لأ. والـ savepoint أو الـ transaction محتاجين المعلومة دي، فبتفضل تكتب try/catch أو callback wrapper زي $transaction(async (tx) => ...) بتاعة Prisma. وكمان Node 22 لسه مش بيعرف يعمل parse لـ using (SyntaxError: Unexpected identifier 'x' على V8 12.4)، فالمثال اتعمله compile بـ TypeScript 7.0.2 الأول.

بتاع Odoo الحقيقي هو env.cr.savepoint() في odoo/sql_db.py، و __exit__ بتاعه سطر واحد: self.close(rollback=exc_type is not None). التشغيل اللي فوق حصل في odoo-bin shell على قاعدة الـ lab. الـ insert الغلط بيكسر unique constraint. جوه savepoint، اللي بيضيع هو الـ savepoint بس والـ transaction بتكمّل. من غيره، PostgreSQL بيعلّم الـ transaction كلها إنها aborted وبيرفض أي statement لحد الـ rollback. وفي account_move.py نفسه هتلاقي @contextmanager مستخدمة 8 مرات و ExitStack بيركّب كذا context manager مع بعض.

فين هستخدمه في شغلي؟ job بيعمل import لـ 5000 عميل: لو صف واحد غلط من غير savepoint الـ transaction كلها بتموت. حط كل صف في with env.cr.savepoint(): وسجّل الفاشل وكمّل (التمرين 4). ونفس الفكرة لو عملت BEGIN في pg من Node و query وقعت: أي query بعدها هترجع current transaction is aborted (قسم الـ databases). والغلطة الشائعة: تعمل except وتكمّل على نفس الـ cursor من غير savepoint.
Trade-off A savepoint isn't free. _FlushingSavepoint flushes pending ORM writes on entry and snapshots the transaction state, so one per row in a huge loop costs real time. Group rows into batches and fall back to per-row savepoints only for a batch that failed. Also, a method that commits, like _commit_progress, can't run inside one (Pending savepoints not released).

English

Python's form is try / except / else / finally. else runs only if try raised nothing, which keeps the risky line alone inside try. You catch by class, so a hierarchy lets a caller catch one case or a whole family. raise NewError(...) from error stores the original in __cause__, and the traceback prints both, the same idea as new Error(msg, { cause }) in JS (error handling). except Exception doesn't catch KeyboardInterrupt or SystemExit, which derive from BaseException.

import json

class BillingError(Exception):
    pass


class PaymentDeclined(BillingError):
    def __init__(self, reference: str, reason: str) -> None:
        super().__init__(f"{reference} declined: {reason}")
        self.reference = reference
        self.reason = reason


class GatewayResponseError(BillingError):
    pass


def parse_gateway(reference: str, raw: str) -> dict:
    try:
        body = json.loads(raw)

        raise GatewayResponseError(f"{reference}: invalid gateway body") from error

        if body["status"] == "declined":
            raise PaymentDeclined(reference, body["reason"])
        return body
    finally:
        # الـ finally بتشتغل في كل الحالات
        print(f"  finished parsing {reference}")

You know Node's model from the event loop lesson: one thread runs your JavaScript, concurrency comes from never blocking it, and CPU work freezes everyone. Standard Python has real OS threads, but the GIL (Global Interpreter Lock) lets only one of them run Python bytecode at a time. So threads don't speed up CPU-bound work, but they do help I/O-bound work, because blocking calls release the GIL. Separate processes each have their own GIL and really run in parallel, at the cost of memory and start-up time. English

Why Odoo isn't async. Python has asyncio, and the run above shows it works. Odoo doesn't use it: apart from one test file, no Python file under odoo/ or addons/ contains async def. The reasons are structural:

  1. One request, one transaction. odoo/http/router.py runs the whole request through retrying(serve_func, env=request.env): one cursor, committed at the end, or rolled back and the entire function run again.
  2. The environment and its cache are bound to that transaction. Environment.__new__ takes its transaction from the cursor.
  3. Reading an attribute can run SQL. On a real run, after clearing the cache, partner.name cost 1 query; the second read cost 0. You can't await inside an attribute read, so going async would mean rewriting every line that touches a field, in every module.
  4. The driver is blocking. Odoo uses psycopg2.

So concurrency comes from running several requests side by side, each one synchronous. With workers = 0, ThreadedServer handles each request in a thread, and that's the mode on this Windows machine. With workers > 0, PreforkServer uses processes (not run here; see lesson 34). The exception is the websocket worker: GeventServer uses gevent's green threads with gevent.monkey.patch_all(), cooperative concurrency without async syntax. gevent isn't installed on Windows, so that's "not run here" too.

Node: one thread, requests interleave at each await
  event loop:  A start | B start | A resumes | B resumes | A done | B done

Odoo, workers = 0: one thread per request
  thread 1:  request A -> cursor A -> SQL, SQL, SQL -> commit
  thread 2:  request B -> cursor B -> SQL, SQL      -> commit

Odoo, workers > 0: one process handles one request at a time
  worker 1:  request A -> cursor A -> ... -> commit -> request C -> ...
  worker 2:  request B -> cursor B -> ... -> commit -> request D -> ...
فوق Node: thread واحد والـ requests بتتداخل عند كل await. في النص Odoo بـ workers = 0: thread لكل request، وكل request ليه cursor خاص بيه من أوله لآخره. تحت Odoo بـ workers > 0: كل process بيخلّص request قبل ما ياخد اللي بعده. يعني عدد الـ requests اللي بتتنفذ في نفس اللحظة محدود بعدد الـ workers.
بالعامية

إنت عارف Node من درس الـ event loop: thread واحد بيشغّل الـ JS، والـ concurrency جاية من إنك متقفلوش، وشغل الـ CPU بيجمّد الكل. Python العادية فيها OS threads حقيقية، بس الـ GIL (Global Interpreter Lock) بيسمح لواحد بس منهم يشغّل Python bytecode في المرة. فالـ threads مش بتسرّع شغل الـ CPU، بس بتفيد في شغل الـ I/O، لأن الـ calls اللي بتستنى بتسيب الـ GIL. والـ processes كل واحد ليه GIL خاص وبيشتغلوا بالتوازي فعلًا، بتكلفة memory ووقت تشغيل. وعلى Windows الـ process الجديد بيعيد import للملف، فلازم if __name__ == "__main__":. فيه builds من غير GIL (PEP 703)، بس ده مش منهم: sys._is_gil_enabled() بترجّع True.

ليه Odoo مش async. Python فيها asyncio، والتشغيل فوق بيثبت إنها شغالة. Odoo مش بيستخدمها: ما عدا ملف test واحد، مفيش ملف Python في odoo/ ولا addons/ فيه async def. الأسباب في البنية نفسها:

  1. request واحد = transaction واحدة. odoo/http/router.py بيشغّل الـ request كله عن طريق retrying(serve_func, env=request.env): cursor واحد، يا commit في الآخر، يا rollback والـ function كلها تتعاد.
  2. الـ environment والـ cache بتاعه مربوطين بالـ transaction دي. Environment.__new__ بياخد transaction من الـ cursor.
  3. قراءة attribute ممكن تشغّل SQL. في تشغيل حقيقي، بعد مسح الـ cache، partner.name كلفت query واحدة، والقراءة التانية صفر. ومتقدرش تعمل await جوه قراءة attribute، فالتحويل لـ async معناه إعادة كتابة كل سطر بيلمس field في كل module.
  4. الـ driver بيبلوك. Odoo بيستخدم psycopg2.

فالـ concurrency جاية من تشغيل كذا request جنب بعض، وكل واحد sync. مع workers = 0 الـ ThreadedServer بيخدم كل request في thread، وده الوضع على Windows هنا. مع workers > 0 الـ PreforkServer بيستخدم processes (ده متشغلش هنا، شوف الدرس 34). والاستثناء هو الـ websocket worker: GeventServer بيستخدم green threads بتاعة gevent مع gevent.monkey.patch_all()، concurrency تعاونية من غير syntax الـ async. و gevent مش متثبت على Windows، فده برضو "not run here".

فين هستخدمه في شغلي؟ لو في Node كنت بتنادي API بطيء جوه handler، الـ event loop بيخدم غيره عادي. في Odoo نفس النداء بيمسك worker كامل و transaction مفتوحة طول المدة، و 4 workers مع 4 نداءات بطيئة معناها السيستم واقف. فأي نداء خارجي تقيل حطه في cron أو queue بره الـ request (الدرس 28)، ومتحطش requests.get من غير timeout. والغلطة الشائعة إنك تفتح thread جوه method وتستخدم نفس self.env: الـ cursor والـ cache مربوطين بالـ request ومش معمولين يتشاركوا بين threads.
Interview question "You have a CPU-heavy report in Python. Do threads help?" → No, the GIL serializes bytecode: 4 threads took about as long as serial. Use processes, or push the work into SQL or a C extension that releases the GIL. Threads are for waiting, not computing.
"عندك تقرير CPU تقيل في Python، الـ threads هتفيد؟" ← لأ، الـ GIL بيخلّي الـ bytecode واحد ورا التاني: 4 threads أخدوا وقت قريب من التسلسلي. استخدم processes، أو انقل الشغل لـ SQL أو C extension بيسيب الـ GIL. الـ threads للانتظار مش للحساب.

❌ Swallowing everything

1. Split an invoice into installments 🟢 easy Write installments(total: str, count: int) -> list[Decimal]. The parts must add up to the total exactly, and any leftover cent goes on the last one: installments("100.00", 3) gives 33.33, 33.33, 33.34.
اكتب installments(total: str, count: int) -> list[Decimal]. الأقساط لازم مجموعها يساوي الإجمالي بالظبط، وأي قرش فاضل يروح على آخر قسط: installments("100.00", 3) تطلع 33.33 و 33.33 و 33.34.
Solution · الحل 
from decimal import ROUND_DOWN, Decimal

CENT = Decimal("0.01")


def installments(total: str, count: int) -> list[Decimal]:
    amount = Decimal(total)
    # الحل: كل قسط بيتقرّب لتحت، والفرق كله بيروح آخر قسط
    share = (amount / count).quantize(CENT, rounding=ROUND_DOWN)
    return [share] * (count - 1) + [amount - share * (count - 1)]


parts = installments("100.00", 3)
print(parts, sum(parts))
# → [Decimal('33.33'), Decimal('33.33'), Decimal('33.34')] 100.00
2. Retry with backoff, tested 🟡 medium Extend @retry so the wait doubles on each attempt, and only the listed exceptions are retried. Test it with unittest, without really sleeping: prove the delays are 0.1 then 0.2, and that a ValueError isn't retried.
طوّر @retry بحيث الانتظار يتضاعف مع كل محاولة، والـ exceptions المحددة بس هي اللي تتعاد. اختبره بـ unittest من غير ما يستنى فعلًا: أثبت إن الانتظارات 0.1 وبعدين 0.2، وإن ValueError مش بيتعاد.
Hint · تلميح mock.patch("time.sleep") replaces the wait, and mock.Mock(side_effect=[...]) fails on demand.
mock.patch("time.sleep") بيبدّل الانتظار، و mock.Mock(side_effect=[...]) بيفشل زي ما إنت عايز.
Solution · الحل 
import functools
import time
import unittest
from unittest import mock


def retry(times: int, base_delay: float = 0.1, on: tuple[type[Exception], ...] = (ConnectionError,)):
    def decorate(function):
        @functools.wraps(function)
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return function(*args, **kwargs)
                except on:
                    if attempt == times:
                        raise
                    # الانتظار بيتضاعف مع كل محاولة
                    time.sleep(base_delay * 2 ** (attempt - 1))

        return wrapper

    return decorate


class RetryTest(unittest.TestCase):
    # الـ patch بيبدّل time.sleep عشان الـ test ميستناش فعلًا
    @mock.patch("time.sleep")
    def test_backoff_doubles(self, sleep: mock.Mock) -> None:
        target = mock.Mock(side_effect=[ConnectionError(), ConnectionError(), "ok"])
        target.__name__ = "target"
        self.assertEqual(retry(times=3)(target)(), "ok")
        self.assertEqual([call.args[0] for call in sleep.call_args_list], [0.1, 0.2])

    @mock.patch("time.sleep")
    def test_other_errors_pass_through(self, sleep: mock.Mock) -> None:
        target = mock.Mock(side_effect=ValueError("bad amount"))
        target.__name__ = "target"
        with self.assertRaises(ValueError):
            retry(times=3)(target)()
        self.assertEqual(target.call_count, 1)
        sleep.assert_not_called()


if __name__ == "__main__":
    unittest.main(verbosity=1)

Cheat sheet · الخلاصة

  • @d(x) over def f means f = d(x)(f), once at import. Always functools.wraps.
  • Odoo's @api.depends and friends set an attribute and return the same function. The registry reads it.
  • with = reusable try/finally, and __exit__ knows about the exception. dispose in JS doesn't.
  • An SQL error without a savepoint aborts the whole transaction. with env.cr.savepoint(): limits the damage.
  • raise New from old keeps the cause. except Exception: pass leaves invalid data in Odoo.
  • UserError and children reach the user; anything else is a server error.
  • Decimal("2.675"), never Decimal(2.675). Say the rounding mode. The default is half-even.
  • Aware datetimes: datetime.now(UTC), zoneinfo (needs tzdata on Windows). Odoo fields are naive UTC.
  • Odoo money: numeric in the DB, float in Python. Use currency.round, is_zero, compare_amounts. Never ==.
  • GIL: threads for waiting, processes for computing. Odoo: one request, one transaction, synchronous, because attribute reads run SQL.
  • Type hints aren't enforced at runtime. pyright is your tsc --noEmit.
  • Odoo tests are unittest plus a savepoint per test. Always check the test count isn't 0.
