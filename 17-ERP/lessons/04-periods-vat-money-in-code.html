Why this matters · ليه ده مهم

English

Accounting software has rules a typical CRUD app never meets: last month's numbers must stop changing, a piastre of difference can fail a tax document, and the same invoice can legitimately have two different totals. These rules decide how you design a billing system, how you import data and how you integrate with an ERP. They also come up directly in fintech and e-commerce interviews. As in lesson 03, this is engineering literacy and not tax advice: rates and treatments change, so confirm them with an accountant.

بالعامية

برامج المحاسبة ليها قواعد أي CRUD app عادي عمره ما قابلها: أرقام الشهر اللي فات لازم تبطل تتغير، وفرق قرش واحد ممكن يوقّع مستند ضريبي، ونفس الفاتورة ممكن يبقى ليها إجماليين مختلفين وكلهم صح. القواعد دي بتحدد إزاي تصمم نظام billing، وإزاي تعمل import للـ data، وإزاي تتكامل مع ERP. وكمان بتيجي مباشرة في interviews الـ fintech والـ e-commerce. وزي درس 03، ده ثقافة هندسية مش استشارة ضريبية: النسب والمعاملات بتتغير، فأكّدها مع محاسب.

Part 1 — Fiscal periods and closing 🟢 Basicالجزء 1 — الفترات المالية والإقفال

English

A fiscal year is the 12-month reporting period, which doesn't have to match the calendar year. It is usually closed in steps: a monthly close reconciles and reviews each month, and a year-end close resets income and expenses to zero and moves the result into retained earnings. Income and expense accounts measure one period; assets, liabilities and equity carry forward.

A closed period must not change, because other people have already used its numbers. The tax return was filed from them and the auditor signed them. The script below shows the problem directly: one back-dated expense changes a quarter that was already reported. It then writes the closing entry and proves that Income and Expenses are zero afterwards.

Closing creates a trap of its own. Once the closing entry exists, a naive P&L for that year returns zero, so reports must exclude it. That's why the entry carries an is_closing flag. A partial unique index makes a second close impossible. Odoo takes a different route: its docs say the closing entry doesn't need to be made right after year-end, and it shows the prior result as a dynamic line. The template's chart has an equity_unaffected account for this (999999, Undistributed Profits/Losses).

// الدالة: رصيد كل نوع حساب لحد آخر السنة، بقيد الإقفال أو من غيره
async function byType(includeClosing: boolean) {
  const { rows } = await db.query<{ type: string; net: string }>(`
    select a.type, sum(l.debit - l.credit) as net
      from journal_line l
      join journal_entry e on e.id = l.entry_id
      join account a on a.code = l.account
     where e.entry_date <= $1 and ($2 or not e.is_closing)
     group by a.type order by a.type`, [YEAR_END, includeClosing]);
  return Object.fromEntries(rows.map((r) => [r.type, toMinor(r.net)]));
}

async function netProfit(from: string, to: string): Promise<bigint> {
  const { rows } = await db.query<{ net: string }>(`
    select coalesce(sum(l.credit - l.debit), 0) as net
      from journal_line l
      join journal_entry e on e.id = l.entry_id
      join account a on a.code = l.account
     where a.type in ('income', 'expense')
       and e.entry_date between $1 and $2 and not e.is_closing`, [from, to]);
  return toMinor(rows[0]!.net);
}

// الإقفال: كل حساب دخل ومصروف بيتصفّر، والفرق بيروح Retained Earnings
async function closeYear(): Promise<number> {
  const { rows } = await db.query<{ account: string; net: string }>(`
    select l.account, sum(l.debit - l.credit) as net
      from journal_line l
      join journal_entry e on e.id = l.entry_id
      join account a on a.code = l.account
     where a.type in ('income', 'expense')
       and e.entry_date between $1 and $2 and not e.is_closing
     group by l.account having sum(l.debit - l.credit) <> 0
     order by l.account`, [YEAR_START, YEAR_END]);

  const entry = await db.query<{ id: string }>(
    `insert into journal_entry(entry_date, memo, is_closing) values ($1, 'Year-end close 2026', true) returning id`, [YEAR_END]);
  const id = entry.rows[0]!.id;
  let toRetained = 0n;
  for (const r of rows) {
    const net = toMinor(r.net);
    toRetained += net;
    // العكس: رصيد مدين بيتقفل بـ credit، ورصيد دائن بيتقفل بـ debit
    await db.query(`insert into journal_line(entry_id, account, debit, credit) values ($1, $2, $3, $4)`,
      [id, r.account, net < 0n ? r.net.replace("-", "") : "0", net > 0n ? r.net : "0"]);
    console.log(`  ${r.account}  ${net < 0n ? "debit " : "credit"} ${fmt(net < 0n ? -net : net).padStart(12)}`);
  }
  const amount = fmt(toRetained < 0n ? -toRetained : toRetained).replaceAll(",", "");
  await db.query(`insert into journal_line(entry_id, account, debit, credit) values ($1, '3100', $2, $3)`,
    [id, toRetained > 0n ? amount : "0", toRetained < 0n ? amount : "0"]);
  console.log(`  3100  ${toRetained < 0n ? "credit" : "debit "} ${fmt(toRetained < 0n ? -toRetained : toRetained).padStart(12)}  (Retained Earnings)`);
  return rows.length + 1;
}

بالعامية

الـ fiscal year هي فترة التقارير الـ 12 شهر، ومش لازم تطابق السنة الميلادية. وعادةً بتتقفل على خطوات: الـ monthly close بيطابق ويراجع كل شهر، والـ year-end close بيصفّر الدخل والمصروفات وينقل النتيجة لـ retained earnings. حسابات الدخل والمصروفات بتقيس فترة واحدة، أما الـ assets والـ liabilities والـ equity فبتكمّل.

الفترة المقفولة ممنوع تتغير، لأن ناس تانية استخدمت أرقامها خلاص: الإقرار الضريبي اتقدم بيها والمراجع مضى عليها. السكريبت بيبيّن المشكلة مباشرة: مصروف واحد بتاريخ قديم غيّر ربع اتبلّغ عنه خلاص. وبعدين بيكتب قيد الإقفال ويثبت إن الدخل والمصروفات بقوا صفر.

والإقفال نفسه ليه فخ: بعد قيد الإقفال، أي P&L ساذج للسنة دي هيرجّع صفر، فالتقارير لازم تستبعده. عشان كده القيد عليه flag اسمه is_closing. وفيه partial unique index بيمنع إقفال تاني. وOdoo ماشي بطريقة تانية: الـ docs بتقول إن قيد الإقفال مش لازم يتعمل على طول بعد نهاية السنة، وبيعرض نتيجة السنة اللي فاتت كسطر dynamic. والـ chart بتاع الـ template فيه حساب equity_unaffected للغرض ده (999999، Undistributed Profits/Losses).

فين هستخدمه في شغلي؟ عندك job بيعيد حساب commissions أو بيعمل backfill لفواتير قديمة. من غير ما تفكر في الفترات، الـ job هيكتب بتواريخ قديمة ويغيّر أرقام اتقدمت للضرايب. الصح: أي تصحيح لفترة مقفولة يتسجل بتاريخ في فترة مفتوحة. والغلطة الشائعة: تنسى تستبعد قيد الإقفال من تقرير الـ P&L فيطلع صفر. ودرس 06 هيبني قفل الفترة في Postgres تحت الـ concurrency.

Part 2 — Lock dates in practice 🟡 Intermediateالجزء 2 — الـ lock dates عمليًا

English

Odoo implements closing as dates on res.company. There are five, and the script below tries each one against five kinds of document dated inside the locked period. The result surprises most developers: posting doesn't fail. Odoo keeps invoice_date and moves the accounting date forward.

It moves to the end of the first open period, not its first day. The docstring of _get_accounting_date says it takes "the last day of the period, depending on the sequence format", and the run confirms it: invoices here number per year, so they land on 2025-12-31, while bills number per month and land on 2025-01-31. The date is also capped at today, so when the first open period is the current year the document lands on the day you run it (2026-11-11 in this run).

Three more behaviours from the same run. A soft lock can be removed, but removing a hard_lock_date raises UserError, and so does moving it backwards. An entry already posted inside a locked period can't be reset to draft or deleted, but it can be reversed, and the reversal lands in the open period. And a fiscalyear_lock_date or hard_lock_date past unreconciled bank lines raises RedirectWarning, while a tax_lock_date doesn't. Lesson 24 covers the internals and audited exceptions.

بالعامية

Part 3 — VAT mechanics 🟢 Basicالجزء 3 — آلية الـ VAT

English

VAT passes through the business. Output tax is what you charge on sales, and it's a liability because you collected it on the government's behalf. Input tax is what you paid on purchases, and it's an asset because you can claim it back. The periodic return settles the difference. Neither is income or an expense in the normal case.

The standard rates are 14% in Egypt, 15% in Saudi Arabia and 5% in the UAE (PwC Worldwide Tax Summaries, pages reviewed 17 August, 29 July and 9 September 2026). A worked month at 14%: sales of 100,000 give output tax of 14,000; purchases of 40,000 give input tax of 5,600; the net payable is 8,400.

Two zero-VAT treatments look identical on the invoice and differ in cost. Zero-rated sales charge 0% but keep the right to reclaim input tax. Exempt sales charge nothing and lose that right, so the input tax becomes a cost. Which goods fall where is a legal question this lesson doesn't answer.

Part 4 — Decimal, not float 🟢 Basicالجزء 4 — decimal مش float

English

The storage side is already covered in section 11 · 2.8 and section 09 · 3.7. Here the question is what the tax authority sees. The usual warning, "float loses money on every invoice", isn't what the measurement shows, and the truth is more dangerous.

On a seeded 1,000-line invoice at 14%, float rounded per line got every line's tax right; the total drifted by about 5×10⁻¹⁰, invisible at two decimals. Run the same code at 15% and 15 lines are wrong, for a loss of 0.15. The damage concentrates on amounts whose tax lands exactly on half a piastre. An exhaustive test over every amount up to 100,000.00 shows it: at 14%, Math.round is wrong 0 times out of 200,000 boundary cases, yet at 15% it's wrong 119,903 times out of 500,000. So code can pass every test in Egypt and then misreport in Saudi Arabia. toFixed is worse at all three rates.

Postgres shows the same split. Summing one million fees of 0.10 gives exactly 100000.00 as numeric and 100000.00000133288 as double precision, and the equality check fails. Note that pg returns numeric as a string, deliberately. Odoo is a useful counter-example: its columns are numeric, but the ORM holds them as Python float (confirmed in the lab) and rounds to the currency at each step. That can work with strict discipline. In new code, exact decimals are the cheaper way to be right.

// المولّد: seed ثابت عشان الرقم يطلع هو هو كل مرة
function makeLines(count: number) {
  let seed = 20261111;
  const rnd = (n: number) => {
    seed = (Math.imul(seed, 1103515245) + 12345) & 0x7fffffff;
    return (seed >>> 8) % n;
  };
  return Array.from({ length: count }, () => ({ priceMinor: 1 + rnd(99_999), qty: 1 + rnd(9) }));
}

function invoice(ratePercent: number) {
  const lines = makeLines(1000);
  const rate = ratePercent / 100;
  let floatTotal = 0;
  let intTotal = 0;
  let decTotal = new Decimal(0);
  let onHalf = 0;
  let wrongLines = 0;
  let errorPiastres = 0;

  for (const { priceMinor, qty } of lines) {
    // الطريقة الأولى: float زي ما أغلب الكود بيتكتب
    const netF = (priceMinor / 100) * qty;
    const taxF = Math.round(netF * rate * 100) / 100;
    floatTotal += netF + taxF;

    // الطريقة التانية: قروش integer، والتقريب half-up بعمليات exact
    const netI = priceMinor * qty;
    const taxI = Math.floor((netI * ratePercent + 50) / 100);
    intTotal += netI + taxI;

    // الطريقة التالتة: decimal.js
    const netD = new Decimal(priceMinor).div(100).mul(qty);
    const taxD = netD.mul(ratePercent).div(100).toDecimalPlaces(2, Decimal.ROUND_HALF_UP);
    decTotal = decTotal.add(netD).add(taxD);

    if ((netI * ratePercent) % 100 === 50) onHalf++;
    const taxFMinor = Math.round(taxF * 100);
    if (taxFMinor !== taxI) {
      wrongLines++;
      errorPiastres += taxFMinor - taxI;
    }
  }

  console.log(`\nrate ${ratePercent}%: 1000 lines, ${onHalf} land exactly on half a piastre`);
  console.log("  float total  :", floatTotal);
  console.log("  integer total:", (intTotal / 100).toFixed(2));
  console.log("  decimal.js   :", decTotal.toFixed(2));
  console.log("  float drift  :", floatTotal - intTotal / 100);
  console.log("  wrong lines  :", wrongLines, " error in piastres:", errorPiastres);
}

// الاختبار: كل مبلغ من قرش لحد 100,000 جنيه ضريبته بتقع بالظبط على نص قرش
const MAX_MINOR = 10_000_000;

function measure(ratePercent: number) {
  const rate = ratePercent / 100;
  let boundary = 0;
  let wrongRound = 0;
  let wrongFixed = 0;
  let firstWrong: string | undefined;
  for (let net = 1; net <= MAX_MINOR; net++) {
    if ((net * ratePercent) % 100 !== 50) continue;
    boundary++;
    // الصح: half-up بعمليات integer
    const exact = Math.floor((net * ratePercent + 50) / 100);
    const netFloat = net / 100;
    const viaRound = Math.round(netFloat * rate * 100);
    const viaFixed = Math.round(Number((netFloat * rate).toFixed(2)) * 100);
    if (viaRound !== exact) {
      wrongRound++;
      firstWrong ??= `${netFloat.toFixed(2)} * ${rate} = ${netFloat * rate}, Math.round gives ${(viaRound / 100).toFixed(2)}, exact ${(exact / 100).toFixed(2)}`;
    }
    if (viaFixed !== exact) wrongFixed++;
  }
  return { ratePercent, boundary, wrongRound, wrongFixed, firstWrong };
}

Part 5 — Rounding per line versus per document 🟡 Intermediateالجزء 5 — التقريب لكل سطر ولا للمستند كله

English

The same invoice can have two correct totals. Take 3 lines of 33.33 at 14%. Rounding per line gives 4.67 three times, so tax is 14.01 and the total 114.00. Rounding per document computes 14% of 99.99 = 13.9986, so tax is 14.00 and the total 113.99. Neither is a bug. They're different rules.

Odoo exposes the choice as tax_calculation_rounding_method, and flipping it on a real invoice produces exactly those numbers. Its localizations pick different defaults: l10n_eg sets round_per_line and l10n_sa sets round_globally. Which one applies isn't a preference. It's a contract you read in the tax authority's specification.

Here is why it matters, from Odoo's real ETA code. _generate_l10n_eg_edi_json builds the document and rounds to 5 decimals through _l10n_eg_edi_round. Under round_per_line everything agrees. Under round_globally, Odoo spreads the tax across lines as 4.66, 4.67, 4.67, but each line's total stays 38.0, so the lines sum to 114.00 while the header says 113.99. ETA's published rule is TotalAmount = sum of all Invoiceline.Total – Extra discount amount. The stand-in below applies that equation with zero tolerance and rejects the document. It's a local stand-in. Nothing was sent to ETA, the published page states no tolerance, and how the real service treats this document wasn't tested. Lesson 31 covers the integration.

Part 6 — Multi-currency 🟡 Intermediateالجزء 6 — العملات المتعددة

English

Every foreign document has two amounts: the transaction currency (what the invoice says) and the company currency (what the books report), linked by the rate on the document date. When the rate changes before payment, a difference appears that belongs to neither the sale nor the customer.

A realised gain or loss is locked in by an actual settlement. An unrealised one is a month-end estimate on an item that's still open, and it's commonly reversed the next day so it doesn't double count. Worked example: a USD 100 invoice at 50 books 5,000 EGP. At month-end the rate is 52, an unrealised gain of 200. The customer pays at 54, so the bank receives 5,400 against a receivable of 5,000, and 400 is a realised gain. The entries are written by hand here; lesson 24 shows Odoo generating them.

The classic mistake is storing only the converted amount. The bank statement says USD 100.00, your row says 5,000 EGP, and you can no longer match them or compute the gain. Store the original amount, the currency, the rate and the company amount.

  10 Mar: invoice      31 Mar: month-end       20 Apr: paid
  USD 100 @ 50         USD 100 @ 52            USD 100 @ 54
  books 5,000          unrealised +200         bank 5,400
       |               (reversed 1 Apr)        realised +400
  -----+--------------------+--------------------+-----> time

الربح أو الخسارة الـ realised بيتثبت بتسوية فعلية. الـ unrealised تقدير آخر الشهر على بند لسه مفتوح، وغالبًا بيتعكس تاني يوم عشان مايتحسبش مرتين. مثال: فاتورة 100 دولار بسعر 50 بتتسجل 5,000 جنيه. آخر الشهر السعر 52، مكسب غير محقق 200. العميل بيدفع بسعر 54، فالبنك بيستلم 5,400 قصاد receivable بـ 5,000، و400 مكسب محقق. القيود هنا مكتوبة بالإيد، ودرس 24 بيبيّن Odoo وهو بيولّدها.

الغلطة المشهورة إنك تخزن المبلغ المحوّل بس. كشف البنك بيقول 100.00 دولار، والـ row بتاعك بيقول 5,000 جنيه، ومابقتش تقدر تطابقهم ولا تحسب الفرق. خزّن المبلغ الأصلي، والعملة، والسعر، ومبلغ عملة الشركة.

فين هستخدمه في شغلي؟ بتاخد مدفوعات بالدولار عن طريق Stripe وبتقرر بالجنيه. جدول payments لازم يبقى فيه amount وcurrency وfx_rate وamount_company، وسعر الصرف يتسجل وقت العملية مش يتجاب بعدين. لو جبته بعدين، الـ reconciliation job مش هيطابق كشف الـ provider أبدًا.
Trade-off: which rate? Using the rate on the document date is auditable and stable, but it needs a stored rate table and a rule for weekends and missing days. Fetching a live rate is simpler and can't be reproduced later. For anything that reaches the books, store the rate you used on the row.
سعر تاريخ المستند قابل للمراجعة وثابت، بس محتاج جدول أسعار متخزن وقاعدة للإجازات والأيام الناقصة. جلب سعر لحظي أبسط، بس مستحيل تعيد حسابه بعدين. وأي حاجة بتوصل للدفاتر، خزّن السعر اللي استخدمته على نفس الـ row.

Common mistakes · غلطات شائعة

❌ Rounding money with float 
// الغلط: بيطلّع 0.22
const tax = Math.round(1.5 * 0.15 * 100) / 100;
✅ Exact decimal, explicit rule 
// الصح: بيطلّع 0.23
const tax = new Decimal("1.50").mul("0.15")
  .toDecimalPlaces(2, Decimal.ROUND_HALF_UP);
بالعامية

❌ 1.50 في 0.15 بالـ float بتطلع 0.22499999999999998، فالتقريب بينزل لـ 0.22. ✅ الـ decimal بيحسبها 0.225 بالظبط، وقاعدة ROUND_HALF_UP المكتوبة بتطلعها 0.23.

❌ Editing a closed period 
-- الغلط: بيغيّر رقم اتقدم للضرايب
update journal_line set debit = 5000
 where entry_id = 42;
✅ New entry in an open period 
-- الصح: التصحيح قيد جديد وظاهر
select post('2026-11-11', 'Correct entry 42',
  '[{"account":"6000","debit":5000},
    {"account":"1000","credit":5000}]');
بالعامية

❌ التعديل بيغيّر رقم ناس استخدمته خلاص، ومن غير أثر. ✅ قيد جديد بتاريخ في فترة مفتوحة بيصلح الرصيد، والتصحيح يفضل ظاهر ومراجَع.

❌ Header and lines computed separately 
// الغلط: كل واحد بقاعدة، فممكن يختلفوا بقرش
const header = round(sum(nets) * rate);
const lines = nets.map((n) => round(n * rate));
✅ Header derived from the lines 
// الصح: الـ header مجموع السطور النهائية
const lines = allocateTax(nets, rate);
const header = sum(lines.map((l) => l.total));
بالعامية

❌ حساب الـ header والسطور كل واحد لوحده هو اللي بيعمل فرق القرش اللي شفناه في Odoo. ✅ احسب السطور النهائية الأول، وخلي الـ header مجموعهم، فمستحيل يختلفوا.

❌ Only the converted amount 
-- الغلط: العملة والسعر ضاعوا للأبد
create table payment (
  id bigint primary key,
  amount_egp numeric(18,2) not null
);
✅ Original, currency, rate, converted 
-- الصح: تقدر تطابق البنك وتحسب الفرق
create table payment (
  id bigint primary key,
  amount numeric(18,2) not null,
  currency char(3) not null,
  fx_rate numeric(18,6) not null,
  amount_company numeric(18,2) not null
);
بالعامية

❌ لو خزنت الجنيه بس، مش هتعرف تطابق سطر بنك بالدولار ولا تحسب مكسب فرق العملة. ✅ خزّن الأربعة: المبلغ الأصلي، والعملة، والسعر، والمبلغ المحوّل.

3. Allocate without losing a piastre 🟡 medium Write allocateTax(nets, rate): round the document tax once, spread it across lines by largest remainder, and compute each line's total after the spread, so the lines always sum to the header. Test it with 3 lines of 33.33 at 14%.

Solution · الحل 
import { Decimal } from "decimal.js";

type Allocated = { net: string; tax: string; total: string };

// الحل: نقرّب ضريبة المستند مرة واحدة، وبعدين نوزعها بأكبر باقي
function allocateTax(nets: string[], ratePercent: string): { lines: Allocated[]; tax: string; total: string } {
  const rate = new Decimal(ratePercent).div(100);
  const exact = nets.map((n) => new Decimal(n).mul(rate));
  const documentTax = exact.reduce((s, t) => s.add(t), new Decimal(0)).toDecimalPlaces(2, Decimal.ROUND_HALF_UP);
  const floors = exact.map((t) => t.toDecimalPlaces(2, Decimal.ROUND_DOWN));
  let left = documentTax.sub(floors.reduce((s, t) => s.add(t), new Decimal(0))).mul(100).toNumber();
  const order = exact.map((t, i) => ({ i, rest: t.sub(floors[i]!) })).sort((a, b) => b.rest.cmp(a.rest) || a.i - b.i);
  const taxes = [...floors];
  for (const { i } of order) {
    if (left <= 0) break;
    taxes[i] = taxes[i]!.add("0.01");
    left--;
  }
  // المهم: total السطر بيتحسب من الضريبة بعد التوزيع، مش قبله
  const lines = nets.map((n, i) => ({ net: new Decimal(n).toFixed(2), tax: taxes[i]!.toFixed(2), total: new Decimal(n).add(taxes[i]!).toFixed(2) }));
  const total = lines.reduce((s, l) => s.add(l.total), new Decimal(0));
  return { lines, tax: documentTax.toFixed(2), total: total.toFixed(2) };
}

Solution · الحل 
import { Decimal } from "decimal.js";

type Invoice = { amount: string; currency: string; rate: string; amountCompany: string };
type Settlement = { cashCompany: string; gain: string; loss: string };

// الحل: بنحتفظ بالمبلغ الأصلي والعملة والسعر، والفرق بيتحسب وقت التحصيل
function settle(invoice: Invoice, paymentRate: string): Settlement {
  const cash = new Decimal(invoice.amount).mul(paymentRate).toDecimalPlaces(2, Decimal.ROUND_HALF_UP);
  const diff = cash.sub(invoice.amountCompany);
  return { cashCompany: cash.toFixed(2), gain: diff.gt(0) ? diff.toFixed(2) : "0.00", loss: diff.lt(0) ? diff.abs().toFixed(2) : "0.00" };
}

const invoice: Invoice = { amount: "100.00", currency: "USD", rate: "50", amountCompany: "5000.00" };

console.log("paid at 48:", settle(invoice, "48"));
console.log("paid at 50:", settle(invoice, "50"));

Cheat sheet · الخلاصة

  • Year-end close zeroes income and expenses into retained earnings. Reports must then exclude the closing entry.
  • A closed period doesn't change: correct it with a new entry in an open period.
  • Odoo doesn't refuse a late document: it moves date to the end of the first open period, capped at today, and keeps invoice_date.
  • tax_lock_date affects taxed documents only; sale and purchase locks follow the journal type; hard_lock_date can't be removed.
  • Output VAT is a liability, input VAT an asset, and the return settles the difference. 14% Egypt, 15% Saudi Arabia, 5% UAE.
  • Zero-rated keeps input recovery; exempt loses it.
  • Float fails at half-unit boundaries, and how often depends on the rate: 0 of 200,000 at 14%, 119,903 of 500,000 at 15%.
  • Use integer minor units or decimals, numeric in Postgres, and an explicit rounding rule.
  • Per line and per document give different correct totals. The authority's specification decides.
  • Foreign documents store amount, currency, rate and company amount. Realised is settled; unrealised is a reversible estimate.
بالعامية
  • الـ year-end close بيصفّر الدخل والمصروفات في retained earnings، وبعدها التقارير لازم تستبعد قيد الإقفال.
  • الفترة المقفولة مبتتغيرش: صلّحها بقيد جديد في فترة مفتوحة.
  • Odoo مبيرفضش المستند المتأخر: بيحرّك date لآخر أول فترة مفتوحة، بسقف النهاردة، وبيسيب invoice_date.
  • الـ tax_lock_date على اللي فيه ضريبة بس، وlocks البيع والشراء حسب نوع الـ journal، والـ hard_lock_date ماينفعش يتشال.
  • الـ output VAT التزام، والـ input VAT أصل، والإقرار بيسوّي الفرق. 14% مصر، 15% السعودية، 5% الإمارات.
  • الـ zero-rated بيحتفظ باسترداد الـ input، والـ exempt بيخسره.
  • الـ float بيغلط عند نص الوحدة، وعدد المرات حسب النسبة: 0 من 200,000 عند 14%، و119,903 من 500,000 عند 15%.
  • استخدم integer minor units أو decimals، وnumeric في Postgres، وقاعدة تقريب صريحة.
  • التقريب لكل سطر وللمستند بيدّوا إجماليين مختلفين وكلهم صح، ومواصفات الجهة هي اللي بتحدد.
  • المستندات الأجنبية بتخزن المبلغ والعملة والسعر ومبلغ عملة الشركة. الـ realised متسوّي، والـ unrealised تقدير بيتعكس.
