Why this matters · ليه ده مهم

English

In lesson 14 a model was a table and a recordset was a set of ids. This lesson adds behaviour: values that derive from other values, rules that refuse bad data, and code that runs on create, write and delete. Most Odoo bugs that reach production live here. A total that stops updating, a field that is filled in the form and empty through the API, a duplicate that a Python check let through: each one looks fine in a demo and costs real money on a real ledger.

For a Node developer the surprise is where this logic runs. Odoo's ORM decides when a compute fires, and it does so in batches, on records you never asked for. Every example below ran on real Odoo 20 in a private lab. Timings come from a loaded Windows machine with fsync off, so read them as ratios; query and row counts are exact.

بالعامية

في الدرس 14 الـ model كان جدول، والـ recordset كان مجموعة ids. الدرس ده بيضيف السلوك: قيم بتطلع من قيم تانية، قواعد بترفض الـ data الغلط، وكود بيشتغل مع الـ create والـ write والـ delete. معظم الـ bugs بتاعة Odoo اللي بتوصل production بتبقى هنا: total وقف يتحدّث، حقل بيتملا في الـ form وفاضي من الـ API، أو duplicate عدّى من check مكتوب بـ Python. كل واحدة فيهم شكلها تمام في الـ demo، وبتكلّف فلوس بجد على ledger حقيقي.

المفاجأة لمبرمج Node هي الـ logic ده بيشتغل فين. الـ ORM بتاع Odoo هو اللي بيقرر الـ compute يشتغل إمتى، وبيشغّله batches، وعلى records إنت ماطلبتهاش أصلًا. كل مثال تحت اتشغّل على Odoo 20 حقيقي في lab خاص. الأوقات جاية من جهاز Windows عليه ضغط وfsync مقفول، فبص عليها كنِسَب؛ أما عدد الـ queries والصفوف فمظبوط.

Part 1 — Computed fields 🟡 Intermediateالجزء 1 — الـ computed fields

English

A computed field declares compute='_method' and a list of dependencies with @api.depends. The method receives self as a recordset that may hold thousands of records, so it loops, and it must assign the field on every record in every branch. Without store=True the value exists only in the cache and is computed on read. With store=True it is a real column, recomputed when a dependency changes and written at the next flush.

The dependency list is a contract with the ORM, and the ORM trusts it completely. It never inspects your method to discover what you read. Write @api.depends('line_ids') while the code reads amount, and adding or removing a line triggers a recompute while editing a line's amount does not. The stored value is silently wrong from that moment on.

Use fields.Monetary for money, not fields.Float. In the lab Monetary produced a numeric column and Float without digits produced double precision. In Python both are floats, and Monetary rounds to the currency's precision when it stores the value (lesson 04 covers why).

بالعامية

الـ computed field بتكتب فيه compute='_method' وبتحدد الـ dependencies بـ @api.depends. الـ method بتستلم self كـ recordset ممكن يبقى فيه آلاف الـ records، فلازم تعمل loop، ولازم تكتب قيمة للحقل على كل record في كل فرع. من غير store=True القيمة موجودة في الـ cache بس وبتتحسب وقت القراءة. مع store=True بتبقى عمود حقيقي، بيتحسب تاني لما dependency تتغير وبيتكتب في الـ flush الجاي.

قايمة الـ dependencies دي عقد بينك وبين الـ ORM، والـ ORM بيصدّقها تمامًا. عمره ما بيبص جوه الـ method يشوف إنت بتقرا إيه. لو كتبت @api.depends('line_ids') والكود بيقرا amount، إضافة أو مسح line هيعمل recompute، لكن تعديل amount بتاع line مش هيعمل. والقيمة المتخزنة تبقى غلط من اللحظة دي من غير ما حد يحس.

الفلوس تبقى fields.Monetary مش fields.Float. في الـ lab الـ Monetary طلّع عمود numeric، والـ Float من غير digits طلّع double precision. في Python الاتنين float، والـ Monetary بيقرّب على دقة العملة وقت التخزين (الدرس 04 بيشرح ليه).

ثلاث غلطات شوفناهم بالتشغيل. الأولى: dependency ناقصة، والقيمة بتبقى قديمة في صمت. التانية: فرع مش بيكتب القيمة، ورد الفعل بيختلف: حقل readonly ومش stored بيدي ValueError، أما الحقل الـ stored فبياخد False من غير أي صوت. التالتة: كود من غير loop بيشتغل لما تجرّب record واحد في الـ shell، ويقع في list view، لأن الـ ORM بينادي الـ compute على كل الـ records اللي معاه في نفس الـ recordset.

فين هستخدمه في شغلي؟ أي رقم مشتق في module بتكتبه: amount_total في order، عدد الـ lines، حالة الدفع. سؤال الـ exit test رقم 4 بيبدأ هنا: model فيه computed stored field. وفي الـ code review، أول حاجة تبص عليها: كل حقل بيتقرا جوه الـ compute موجود في الـ @api.depends بالـ path كامل؟ وهل فيه for rec in self؟ وكل فرع بيكتب القيمة؟
What breaks at scale A compute that runs a search per record is an N+1 that fires every time a list view opens. The batch you receive is your chance to query once for all of self. Lesson 16 measures this.

Part 2 — Stored versus non-stored, measured 🟡 Intermediateالجزء 2 — stored ولا non-stored بالأرقام

English

The choice is a read/write trade. A stored field costs a column and a write whenever a dependency changes, and reading it is a plain SELECT. A non-stored field costs nothing to write and runs the method on every read in a fresh transaction. Only a stored field exists for SQL, so searching a non-stored field needs a search= method that translates the condition into a domain, and aggregating it in _read_group is impossible.

The test data is 10,000 refunds with 20,000 lines, all for one partner. Stored total reads in one query. Non-stored total_live runs the same arithmetic through the ORM and takes five queries and roughly twenty times as long.

The cost of storing appears on the write side. fee depends on partner_id.refund_fee_pct, so one write to one partner row rewrites every refund of that partner: 10,000 rows from a single field change. On a busy table that is a long transaction holding row locks, plus 10,000 dead tuples for vacuum (section 09 · MVCC).

precompute=True attacks a different cost. Normally a stored compute on a new record means INSERT then UPDATE, twice the writes. With precompute=True the value is computed before the INSERT. The source documents two limits: a default value or an explicit value disables it, and it can hurt when records are created one at a time, since each compute then runs alone and loses batching.

def _search_total_live(self, operator, value):
    if operator not in ('>', '>=', '<', '<=', '='):
        return NotImplemented
    rows = self.env['erp_lab.refund.line']._read_group(
        [], ['refund_id'], having=[('amount:sum', operator, value)],
    )
    return [('id', 'in', [refund.id for (refund,) in rows])]

القرار ده مبادلة بين القراءة والكتابة. الـ stored بيكلّفك عمود وكتابة كل ما dependency تتغير، وقراءته SELECT عادي. الـ non-stored كتابته ببلاش، وبيشغّل الـ method كل قراءة في transaction جديدة. والـ SQL مبيشوفش غير الـ stored، فالـ search على non-stored محتاج search= method تحوّل الشرط لـ domain، والتجميع عليه في _read_group مستحيل.

الـ data بتاعة التجربة: 10,000 refund و20,000 line لعميل واحد. الـ total الـ stored اتقرا في query واحدة. الـ total_live الـ non-stored بيعمل نفس الحساب عن طريق الـ ORM، وخد 5 queries وحوالي 20 ضعف الوقت.

تكلفة التخزين بتظهر في الكتابة. الـ fee معتمد على partner_id.refund_fee_pct، فكتابة واحدة على صف partner واحد بتعيد كتابة كل الـ refunds بتاعته: 10,000 صف من تغيير حقل واحد. على جدول عليه شغل ده معناه transaction طويلة ماسكة row locks، و10,000 dead tuple للـ vacuum (القسم 09 · MVCC).

الـ precompute=True بيعالج تكلفة تانية. العادي إن stored compute على record جديد معناه INSERT وبعده UPDATE، يعني ضعف الكتابة. مع precompute=True القيمة بتتحسب قبل الـ INSERT. الـ source كاتب حدّين: أي default أو قيمة صريحة بتلغيه، وممكن يضر لو الـ records بتتعمل واحد واحد، لأن كل compute هيشتغل لوحده ويخسر الـ batching.

فين هستخدمه في شغلي؟ شاشة "refunds أكبر من 1000 مرتبة بالقيمة" محتاجة stored، لأنها search وsort. لكن "الرصيد المتاح للمستخدم الحالي" non-stored. وقبل ما تعمل store=True على حقل معتمد على partner_id.something، اسأل: كام record ممكن يبقى تحت أكبر partner؟ لو عميل عنده مليون order، تعديل حقل واحد في بيانات العميل ممكن يقف الـ worker دقايق.
Interview question "When do you store a computed field in Odoo?" → When you need to search, sort or aggregate it in SQL, or when reads far outnumber changes to its dependencies. Check the fan-out first: a dependency through a Many2one means one parent write rewrites all its children. Don't store anything that depends on the user or context.
"إمتى تعمل store لـ computed field في Odoo؟" ← لما تحتاج search أو sort أو aggregation في SQL، أو لما القراءات أكتر بكتير من تغييرات الـ dependencies. افحص الـ fan-out الأول: dependency عن طريق Many2one معناها إن كتابة واحدة على الأب بتعيد كتابة كل الأبناء. ومتعملش store لأي حاجة بتعتمد على المستخدم أو الـ context.

Part 3 — Related fields and onchange 🟡 Intermediateالجزء 3 — الـ related fields والـ onchange

English

related='partner_id.city' is a computed field the framework writes for you. By default it is read-only and not stored, and in the lab it could still be searched and grouped, because the ORM follows the path with a join. Store it (store=True) when the query is hot enough to need its own column and index, and accept the same fan-out as Part 2. Be careful with readonly=False: writing the field on a refund writes the partner's city, which changes every other document for that partner.

@api.onchange belongs to the form. The web client calls it while the user edits, on a virtual record whose id is a NewId, and sends the assigned values back to the screen. Nothing calls it from create or write, so it never runs through JSON-2, XML-RPC, a cron or a script.

This is the most common integration surprise in Odoo. A consultant fills a field with an onchange, it looks right on every screen, and then the e-commerce sync creates records with that field empty. The fix is a stored compute with readonly=False. It runs on any path, it still updates live in the form, and the user can still type over it. One limit: an editable compute is recomputed when its dependency changes, so a typed value is lost if the partner changes later.

Part 4 — Constraints 🟡 Intermediateالجزء 4 — الـ constraints

English

Odoo has two kinds. @api.constrains('field') runs Python after a create or write that touches a named field, and raises ValidationError. It can express anything, including rules across records, but it has limits: dotted names such as partner_id.city aren't supported, and it only runs when a named field is in the values, so a create that leaves the field out skips the check. On a stored compute it runs with the recompute, at flush.

models.Constraint('unique (name, company_id)', 'message') becomes a real Postgres constraint. models.Index and models.UniqueIndex create indexes, and the unique form accepts a WHERE clause for partial uniqueness. The old _sql_constraints list is no longer supported in Odoo 20: the framework logs a warning at load and creates nothing, which means code ported from an older version loses its uniqueness guarantee while still installing.

The deciding difference is who enforces the rule. Raw SQL skips a Python constraint entirely. Concurrency defeats it too: two transactions each insert a row and each count only what they can see, so both checks pass and both commit. Only the database sees uncommitted rows of other transactions at the index level. The second insert waits on the first and fails when it commits. Any rule that must hold under concurrency, uniqueness above all, goes in the database. See section 09 · isolation.

Part 5 — Overriding create, write, unlink 🟡 Intermediateالجزء 5 — الـ override لـ create و write و unlink

English

CRUD methods are overridden like any Python method, with three rules. Decorate create with @api.model_create_multi, which guarantees a list even when the caller passes one dict. Always call super(), because other installed modules sit in the same chain (lesson 16 prints it). Keep batches working: one super() call for the whole list, and write must treat self as many records.

Two bad versions, both run for real. def create(self, vals) without the decorator works for a single dict and crashes with AttributeError as soon as anything passes a list, and load, imports and other modules do. Calling rec.write(...) inside write re-enters the same method and ends in RecursionError.

To forbid deletion, use @api.ondelete(at_uninstall=False), not an unlink override. The ORM runs it inside unlink and skips it when the module that defines it is being uninstalled. In the lab, a module whose unlink override refused to delete its own data record finished uninstalling, and left that partner and its external ID behind. The same rule written with @api.ondelete removed both. One more limit: an SQL ondelete='cascade' removes child rows in Postgres, so a child's unlink override never runs.

@api.model_create_multi
def create(self, vals_list):
    # الـ vals_list دايمًا list، حتى لو اللي نادى بعت dict واحد
    prepared = []
    for vals in vals_list:
        # نسخة عشان منبوظش الـ dict بتاع اللي نادى
        vals = dict(vals)
        if vals.get('name', '/') == '/':
            vals['name'] = self.env['ir.sequence'].next_by_code('erp_lab.refund')
        prepared.append(vals)
    # نداء واحد لـ super بالـ list كلها، فالـ batch يفضل batch
    return super().create(prepared)

def write(self, vals):
    # الـ self ممكن يبقى كذا record، فالفحص على الكل مرة واحدة
    if 'partner_id' in vals and any(rec.state == 'posted' for rec in self):

نسختين غلط اتشغلوا فعلًا. def create(self, vals) من غير الـ decorator بيشتغل مع dict واحد، ويقع بـ AttributeError أول ما حد يبعت list، والـ load والـ imports وmodules تانية بيبعتوا list. ونداء rec.write(...) جوه write بيدخل نفس الـ method تاني ويخلص بـ RecursionError.

عشان تمنع المسح استخدم @api.ondelete(at_uninstall=False) مش override لـ unlink. الـ ORM بيشغّله جوه unlink وبيتخطّاه لو الـ module اللي معرّفاه بتتشال. في الـ lab، module الـ unlink override بتاعها رفض يمسح الـ data record بتاعها خلصت الـ uninstall، وسابت الـ partner والـ external ID بتاعه وراها. ونفس القاعدة بـ @api.ondelete شالت الاتنين. وحد تاني: ondelete='cascade' بتاع SQL بيمسح صفوف الأبناء جوه Postgres، فالـ unlink override بتاع الـ child عمره ما بيشتغل.

فين هستخدمه في شغلي؟ ترقيم مستند وقت الإنشاء، أو منع مسح refund اترحّل للمحاسبة، أو منع تغيير العميل بعد الـ posting. نفس فكرة الـ reversal بدل update في الـ ledger بتاعك (الدرس 05). ولو الـ cleanup لازم يحصل مع مسح الأب، متحطوش في unlink بتاع الـ child؛ حطه في unlink بتاع الأب قبل الـ super(). والـ sequence ده مش gap-free؛ الترقيم المحاسبي في الدرس 20.
Trade-off: override or compute? Prefer the declarative tool. A value derived from others is a compute, a rule is a constraint, a delete block is @api.ondelete. Override create or write only for side effects that have no declarative form: assigning a sequence, or starting an external job. Each override is more code on the path of every other module, and more to re-check at upgrade time.
فضّل الأداة الـ declarative. قيمة مشتقة يبقى compute، قاعدة يبقى constraint، منع مسح يبقى @api.ondelete. اعمل override لـ create أو write بس للـ side effects اللي ملهاش شكل declarative: زي تعيين sequence أو تشغيل job خارجي. كل override كود زيادة في طريق كل module تانية، وحاجة زيادة تتراجع وقت الـ upgrade.

Common mistakes · غلطات شائعة

❌ Dependency stops at the relation 
# الـ total هيفضل قديم لما amount يتغير
@api.depends('line_ids')
def _compute_total(self):
    for rec in self:
        rec.total = sum(rec.line_ids.mapped('amount'))
✅ Full path to what you read 
# كل حقل بتقراه لازم يبقى في الـ path
@api.depends('line_ids.amount')
def _compute_total(self):
    for rec in self:
        rec.total = sum(rec.line_ids.mapped('amount'))
بالعامية

❌ الـ @api.depends('line_ids') بيشتغل لما line تتضاف أو تتمسح بس، فتعديل amount بيسيب الـ total قديم من غير error (قسناها: 15 والحقيقي 105). ✅ 'line_ids.amount' بيقول للـ ORM على الحقل اللي الكود بيقراه فعلًا.

❌ Business value in onchange 
# بيشتغل في الـ form بس، والـ API هيسيبه فاضي

    self.delivery_city = self.partner_id.city
✅ Editable stored compute

    compute='_compute_delivery_city',
    store=True, readonly=False)

        rec.delivery_city = rec.partner_id.city
بالعامية

❌ الـ onchange مابيتناداش من create، فأي record جاي من JSON-2 أو cron بيدخل والحقل False. ✅ الـ compute بـ store=True, readonly=False بيتملا في كل الطرق وبيفضل قابل للتعديل، بس بيتحسب تاني لو الـ partner اتغير.

❌ Uniqueness in Python, or the old attribute

    'unique (provider_ref)',

بالعامية

❌ الـ search_count بيخسر قدام اتنين transactions في نفس اللحظة (طلعوا صفين في التجربة)، و_sql_constraints في Odoo 20 بيطلّع warning وخلاص (صفر constraints). ✅ models.Constraint Postgres هي اللي بتنفذه، والتاني بيستنى وبعدين بياخد UniqueViolation.

❌ create for one dict, write that recurses 
# بيقع مع list
def create(self, vals):
    vals['name'] = vals['name'].upper()
    return super().create(vals)

# بيدخل نفسه لحد RecursionError
def write(self, vals):
    for rec in self:
        rec.write({'touched': True})
    return super().write(vals)
✅ Batch-safe overrides 
@api.model_create_multi
def create(self, vals_list):
    # نسخة عشان متغيّرش dict بتاع حد تاني
    vals_list = [dict(v) for v in vals_list]
    for vals in vals_list:
        vals['name'] = vals['name'].upper()
    return super().create(vals_list)

def write(self, vals):
    # الحقل الزيادة بيتضاف لنفس النداء
    return super().write({**vals, 'touched': True})
بالعامية

❌ create(self, vals) بيفترض dict، فأول ما حد يبعت list يقع بـ AttributeError. وrec.write جوه write بيدخل نفس الـ method لحد RecursionError. ✅ @api.model_create_multi بيضمن list، ونداء super() واحد بيحافظ على الـ batch، والقيمة الزيادة في write بتتضاف لنفس الـ vals.

Cheat sheet · الخلاصة

  • @api.depends needs the full path to every field you read. The ORM trusts the list.
  • Compute: for rec in self, assign in every branch. A stored field silently gets False otherwise.
  • Stored: searchable, groupable, cheap to read, and one parent write can rewrite thousands of rows.
  • Non-stored: free to write, recomputed on read, needs search=, can't be aggregated in SQL.
  • precompute=True turns INSERT + UPDATE into one INSERT; a default disables it.
  • A non-stored related can be searched; readonly=False writes through to the source record.
  • @api.onchange runs only in the form. Business values belong in a stored compute with readonly=False.
  • @api.constrains: simple names only, skipped when the field is absent, beaten by raw SQL and races.
  • models.Constraint, models.Index, models.UniqueIndex replace _sql_constraints, which now only warns.
  • @api.model_create_multi, one super(), never rec.write inside write.
  • Block deletes with @api.ondelete(at_uninstall=False). SQL cascade skips child unlink.
  • Tests: flush inside assertRaises for computed constraints, and check the test count isn't 0.
بالعامية
  • @api.depends محتاج الـ path كامل لكل حقل بتقراه، والـ ORM بيصدّق القايمة.
  • الـ compute: for rec in self، واكتب القيمة في كل فرع، وإلا الحقل الـ stored بياخد False في صمت.
  • الـ stored: بيتعمل عليه search و group، قراءته رخيصة، وكتابة واحدة على الأب ممكن تعيد كتابة آلاف الصفوف.
  • الـ non-stored: كتابته ببلاش، بيتحسب وقت القراءة، محتاج search=، ومفيش aggregation عليه في SQL.
  • precompute=True بيحوّل INSERT وUPDATE لـ INSERT واحد، وأي default بيلغيه.
  • الـ related الـ non-stored ينفع عليه search، وreadonly=False بيكتب في الـ record الأصلي.
  • @api.onchange بيشتغل في الـ form بس، وقيم البيزنس مكانها stored compute بـ readonly=False.
  • @api.constrains: أسماء بسيطة بس، بيتخطّى لو الحقل مش موجود، والـ raw SQL والسباقات بيهزموه.
  • models.Constraint وmodels.Index وmodels.UniqueIndex بدل _sql_constraints اللي بقى warning وخلاص.
  • @api.model_create_multi، وsuper() واحدة، ومتعملش rec.write جوه write أبدًا.
  • منع المسح بـ @api.ondelete(at_uninstall=False)، والـ cascade بتاع SQL بيتخطّى unlink بتاع الـ child.
  • الـ tests: اعمل flush جوه assertRaises للـ constraints على computed، واتأكد إن عدد الـ tests مش صفر.
