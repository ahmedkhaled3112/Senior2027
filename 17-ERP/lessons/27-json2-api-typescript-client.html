Why this matters · ليه ده مهم

English

This is the point where a Node backend meets the ERP. Your shop, your mobile API or your billing service will need to read customers from Odoo and push orders and payments into it. Odoo 20 gives you one modern door for that, the JSON-2 API, and it's closing the two old ones. The HTTP call is the easy part. The hard part is that each call is its own database transaction, that empty values come back as false, that the fields differ from one customer's database to the next, and that a lost response tells you nothing about whether the write happened. Interviewers for integration roles probe exactly those four points.

بالعامية

هنا بالظبط الـ Node backend بتاعك بيقابل الـ ERP. المتجر، أو الـ mobile API، أو خدمة الفواتير، هيحتاجوا يقروا العملاء من Odoo ويبعتوله orders ومدفوعات. Odoo 20 بيديك باب حديث واحد للموضوع ده، وهو الـ JSON-2 API، وبيقفل البابين القدام. الـ HTTP call نفسه هو الجزء السهل. الصعب إن كل call بيبقى database transaction لوحده، وإن القيم الفاضية بترجع false، وإن الـ fields بتختلف من database عميل للتاني، وإن الرد اللي ضاع مش بيقولك الـ write حصل ولا لأ. الـ interviewers في وظايف الـ integration بيسألوا في الأربع نقط دول بالذات.

Part 1 — JSON-2 basics 🟡 Intermediateالجزء 1 — أساسيات الـ JSON-2

English

Every call is POST /json/2/<model>/<method> with Authorization: bearer <key> and a JSON body. The body is a flat object of the method's named arguments, plus two reserved keys: ids, the records the method runs on, and context, for values such as {"lang": "en_US"}. There's no positional args array and no login step: the key identifies the user on every request.

X-Odoo-Database is optional. It's needed when one server hosts several databases and dbfilter doesn't pick one from the Host header. On success you get a 200 with the method's return value as JSON, and if the method returned a recordset, the controller converts it to a list of ids (addons/rpc/controllers/json2.py). Only public methods can be called: names starting with _ are refused.

Plan limits. Per the Odoo 20 docs, on Odoo Online the external API is available only on the Custom plan, not on One App Free or Standard. A self-hosted Community instance, like the one on your machine, has no such plan check. Find out which plan a customer is on before you promise an integration.

                                          (access rules apply)
                                       5. COMMIT, or ROLLBACK on error

Odoo بيعمل 6 حاجات: (1) يعرف الـ user من الـ key، (2) يدور على الـ method ويتأكد إنها public، (3) يفتح transaction، (4) ينفذ الـ method بصلاحيات الـ user ده، (5) يعمل commit لو نجحت أو rollback لو فشلت، (6) لو الناتج recordset يحوله لـ list of ids ويرجعه JSON مع 200.

async function json2(model: string, method: string, body: object) {
  const res = await fetch(`${url}/json/2/${model}/${method}`, {
    method: "POST",
    headers: {
      Authorization: `bearer ${key}`,
      "Content-Type": "application/json; charset=utf-8",
      // الـ header ده لازم بس لو السيرفر عليه أكتر من database
      "X-Odoo-Database": "odoo",
      "User-Agent": "shop-sync/1.0",
    },
    body: JSON.stringify(body),
  });
  return { status: res.status, body: await res.json() };
}

بالعامية

كل call هو POST /json/2/<model>/<method> ومعاه Authorization: bearer <key> و JSON body. الـ body عبارة عن object مسطح فيه الـ arguments بتاعة الـ method بالاسم، وزيادة عليهم مفتاحين محجوزين: ids وده الـ records اللي الـ method هتشتغل عليها، وcontext لقيم زي {"lang": "en_US"}. مفيش args بالترتيب ومفيش خطوة login: الـ key بيعرّف الـ user في كل request.

الـ X-Odoo-Database اختياري. بتحتاجه لما سيرفر واحد يبقى عليه كذا database والـ dbfilter مش بيختار واحدة من الـ Host header. لو نجح بيرجعلك 200 وقيمة الـ method كـ JSON، ولو الـ method رجّعت recordset الـ controller بيحوله لـ list of ids (في addons/rpc/controllers/json2.py). مينفعش تنادي غير الـ public methods: أي اسم بيبدأ بـ _ بيترفض.

حدود الخطط. حسب docs بتاعة Odoo 20، على Odoo Online الـ external API موجود في خطة Custom بس، مش في One App Free ولا Standard. أما Community اللي مستضيفها بنفسك، زي اللي على جهازك، فمفيهاش الفحص ده. اعرف العميل على أنهي خطة قبل ما توعده بـ integration.

فين هستخدمه في شغلي؟ Endpoint في الـ Node API بتاعك GET /customers/:id/credit بيقرا رصيد العميل من Odoo عشان يقرر يسمحله بالدفع الآجل ولا لأ. بتعمل search_read بـ fields وlimit محددين، وتحط الـ key في secret manager. ولو العميل عنده Odoo Online على Standard، الـ endpoint ده مش هيشتغل أصلًا، ولازم يترقى لـ Custom. الغلطة الشائعة إنك تبعت args زي XML-RPC: هيرجعلك 422 عشان الـ arguments لازم تبقى بالاسم.
Interview question "What's different about Odoo's JSON-2 API compared with XML-RPC?" → Named arguments instead of positional ones, a bearer API key on every request instead of a uid and password, real HTTP status codes instead of a 200 carrying a fault, and one URL per model and method, so proxies and logs can see what's being called.
"إيه الفرق بين JSON-2 و XML-RPC في Odoo؟" ← الـ arguments بالاسم مش بالترتيب، و bearer API key في كل request بدل uid و password، و HTTP status codes حقيقية بدل 200 جواه fault، و URL لكل model و method، فالـ proxies والـ logs يقدروا يشوفوا إيه اللي بيتنادى.

Part 2 — API keys and a least-privilege user 🟡 Intermediateالجزء 2 — الـ API keys و user بأقل صلاحيات

English

You create a key from Preferences → Account Security → New API Key, or programmatically with res.users.apikeys.generate. The value is shown once: the database stores a hash and an 8-character index, so nobody can read it back. An expiry is required, and the docs cap it at three months. The source shows how: _check_expiration_date takes the largest api_key_duration across the user's groups, which is 90 days here. In the lab, a regular user asking for no expiry or for 100 days was refused. The same function returns early for system users and sudo, so an admin can still create a key that never expires. Don't: that's the worst key to leak.

Rotation has a fixed order: create, deploy, verify, revoke. Programmatic generate and revoke are open to administrators by default, others need the base.enable_programmatic_api_keys parameter, and the default limit is 10 keys per user. Watch out for remove: it's decorated with @check_identity, so over JSON-2 it returns a 200 carrying an "enter your password" window action and deletes nothing. Use revoke.

Never run an integration as admin. The key inherits every access rule of its user (lesson 19), so a dedicated bot user limits the damage of a leak and gives you honest audit logs. Never print a key, and keep it out of Git: it belongs in a secret manager or in environment variables.

const url = process.env.ODOO_URL!;
const adminKey = process.env.ODOO_KEY!;
const botKey = process.env.ODOO_BOT_KEY!;

async function call(key: string, model: string, method: string, body: object) {
  const res = await fetch(`${url}/json/2/${model}/${method}`, {
    method: "POST",
    headers: { Authorization: `bearer ${key}`, "Content-Type": "application/json" },
    body: JSON.stringify({ ...body, context: { lang: "en_US" } }),
  });
  return { status: res.status, body: await res.json() as any };
}

// (1) نفس الـ call بـ user عنده كل الصلاحيات، وبـ user محدود
const count = { domain: [] };
for (const [model, method, body] of [
  ["res.partner", "search_count", count],
  ["account.move", "search_count", count],
  ["ir.config_parameter", "search_count", count],
  ["product.product", "create", { vals_list: [{ name: "Bot Product" }] }],
] as const) {
  const admin = await call(adminKey, model, method, body);
  const bot = await call(botKey, model, method, body);
  console.log(`${model}.${method}: admin ${admin.status} | bot ${bot.status}`, admin.status === 200 ? admin.body : "", bot.status === 200 ? bot.body : "");
}

// (2) الـ rotation: اعمل الجديد، ووزّعه، واتأكد إنه شغال، وبعدين الغي القديم
const oldKey = process.env.ODOO_ROTATE_KEY!;
const expiry = new Date(Date.now() + 30 * 86_400_000).toISOString().slice(0, 10);
const made = await call(oldKey, "res.users.apikeys", "generate", {
  key: oldKey,
  scope: "rpc",
  name: "shop-sync-rotation",
  expiration_date: expiry,
});
const newKey = made.body as string;
console.log("generate", made.status, "new key received:", typeof newKey === "string");

const verify = await call(newKey, "res.partner", "search_count", count);
console.log("new key works", verify.status);

const revoked = await call(newKey, "res.users.apikeys", "revoke", { key: oldKey });
console.log("revoke old key", revoked.status);

const after = await call(oldKey, "res.partner", "search_count", count);
console.log("old key now", after.status, after.body.message);

// (3) الفخ: remove بيرجع 200 بس مبيمسحش، لأنه مستني password في شاشة
const rows = await call(newKey, "res.users.apikeys", "search_read", {
  domain: [["name", "=", "shop-sync-rotation"]],
  fields: ["name"],
});
const trap = await call(newKey, "res.users.apikeys", "remove", { ids: [rows.body[0].id] });
console.log("remove", trap.status, trap.body.res_model);
console.log("key after remove", (await call(newKey, "res.partner", "search_count", count)).status);

بالعامية

الـ key بتعمله من Preferences ← Account Security ← New API Key، أو بالكود بـ res.users.apikeys.generate. القيمة بتظهر مرة واحدة: الـ database بتخزن hash و index من 8 حروف، فمحدش يقدر يرجّعها تاني. لازم يبقى ليه تاريخ انتهاء، والـ docs بتقول 3 شهور بالكتير. والـ source بيوضح إزاي: _check_expiration_date بتاخد أكبر api_key_duration في groups الـ user، وهنا 90 يوم. في الـ lab، user عادي طلب من غير expiry أو طلب 100 يوم واترفض. نفس الـ function بترجع بدري لو الـ user system أو في sudo، فالـ admin لسه يقدر يعمل key مبيخلصش. متعملش كده: ده أسوأ key ممكن يتسرب.

الـ rotation ليها ترتيب ثابت: اعمل الجديد، وزّعه، اتأكد إنه شغال، الغي القديم. الـ generate وrevoke بالكود مفتوحين للـ administrators بس by default، والباقيين محتاجين الـ parameter اسمه base.enable_programmatic_api_keys، والحد الافتراضي 10 keys لكل user. وخد بالك من remove: عليها @check_identity، فعلى JSON-2 بترجع 200 ومعاها window بتطلب password، ومبتمسحش حاجة. استخدم revoke.

عمرك ما تشغّل integration بـ admin. الـ key بيورث كل صلاحيات الـ user بتاعه (الدرس 19)، فالـ bot user المخصوص بيقلل الضرر لو الـ key اتسرب، وبيخلي الـ audit logs صادقة. وعمرك ما تطبع الـ key أو تحطه في Git: مكانه secret manager أو environment variables.

فين هستخدمه في شغلي؟ في الـ deploy pipeline: cron كل 60 يوم بيعمل key جديد لـ integration.bot، يحطه في الـ secret manager، يعمل rolling restart للـ workers، يتأكد إن call واحد نجح بالجديد، وبعدين يعمل revoke للقديم بالجديد. ولو عندك dashboard بيعرض الأوردرات بس، اعمله user تاني صلاحياته read فقط. الغلطة الشائعة إن الـ key يتحط في .env ويتعمله commit، أو إن الـ remove يرجع 200 فتفتكر إنك لغيته.
A 200 isn't proof remove returned 200 and left the key working. When a call is security-relevant, verify the effect: after revoking, call with the old key and expect a 401.
الـ remove رجّع 200 وساب الـ key شغال. لما الـ call يبقى ليه علاقة بالأمان، اتأكد من النتيجة نفسها: بعد الـ revoke نادي بالـ key القديم ولازم يرجع 401.

Part 3 — What's deprecated, and when it goes 🟡 Intermediateالجزء 3 — إيه اللي deprecated وهيتشال إمتى

English

/xmlrpc, /xmlrpc/2 and /jsonrpc are all deprecated. Both protocols expose the same three services: common, db and object. The db service is already gone in Odoo 20 (fall 2026) and Online 19.1. The common and object services are scheduled for removal in Odoo 22 (fall 2028) and Online 21.1 (winter 2027). Older articles say "removed in Odoo 20": that's wrong, as the real run below shows. Note that Online gets there first, so a customer on Odoo Online has much less time than one on-premise.

Each legacy call also writes a WARNING to the server log with the removal notice, which is an easy way to find out who's still calling. Controllers declared with @route(type='jsonrpc') are not part of this deprecation: that's the web client's own transport. type='json' is just its deprecated alias.

const url = process.env.ODOO_URL!;

const xml = (method: string) =>
  `<?xml version="1.0"?><methodCall><methodName>${method}</methodName><params/></methodCall>`;

async function xmlrpc(service: string, method: string): Promise<string> {
  const res = await fetch(`${url}/xmlrpc/2/${service}`, {
    method: "POST",
    headers: { "Content-Type": "text/xml" },
    body: xml(method),
  });
  const text = await res.text();
  // الـ fault بيرجع بـ HTTP 200، فلازم تقرا الـ body عشان تعرف
  const fault = text.includes("<fault>");
  const lastLine = text.split("\n").filter((l) => l.includes("Error")).at(-1) ?? "";
  const version = /<string>(\d+\.\d+)<\/string>/.exec(text)?.[1];
  return `HTTP ${res.status} fault=${fault} ${fault ? lastLine.trim().slice(0, 80) : `version=${version}`}`;
}

بالعامية

/xmlrpc و/xmlrpc/2 و/jsonrpc كلهم deprecated. البروتوكولين بيقدموا نفس التلات services: common وdb وobject. خدمة db اتشالت خلاص في Odoo 20 (خريف 2026) وفي Online 19.1. أما common وobject فمتحدد ليهم الشيل في Odoo 22 (خريف 2028) وOnline 21.1 (شتا 2027). المقالات القديمة بتقول "هيتشالوا في Odoo 20" وده غلط، والتجربة فوق بتثبته. وخد بالك إن Online بيوصل الأول، فالعميل اللي على Odoo Online قدامه وقت أقل بكتير من اللي on-premise.

كل legacy call كمان بيكتب WARNING في الـ server log فيه تنبيه الشيل، وده طريقة سهلة تعرف بيها مين لسه بينادي. الـ controllers المعمولة بـ @route(type='jsonrpc') مش داخلة في الـ deprecation ده: دي طريقة الـ web client نفسه. وtype='json' مجرد alias قديم ليها.

فين هستخدمه في شغلي؟ ورثت sync قديم بيستخدم xmlrpc.client أو مكتبة npm قديمة؟ ابدأ بـ grep في الـ server log على رسالة الـ deprecation عشان تعرف مين بينادي. بعدين انقل call ورا call بالجدول، وسيب الـ legacy شغال لحد ما الـ logs تفضى. الغلطة الشائعة إنك تأجل الموضوع لـ 2028 وإنت عميلك على Online، والميعاد بتاعه شتا 2027.
Interview question "A customer's integration uses XML-RPC on Odoo 20. Is it urgent?" → It depends on hosting. It still works, except for the db service. Self-hosted, the removal is Odoo 22 in fall 2028. On Odoo Online, it's 21.1 in winter 2027, and the external API also needs the Custom plan. I'd check the logs for callers and plan the migration now, since the move is mechanical.
"integration عند عميل شغالة XML-RPC على Odoo 20. الموضوع مستعجل؟" ← حسب الاستضافة. هي لسه شغالة ما عدا خدمة db. لو self-hosted الشيل في Odoo 22 خريف 2028. لو Odoo Online فهو 21.1 شتا 2027، وكمان الـ external API محتاج خطة Custom. هبص في الـ logs على مين بينادي وأخطط للنقل دلوقتي، لأن النقل شغل ميكانيكي.

Part 4 — A typed client 🟡 Intermediateالجزء 4 — client بـ types

English

This is Artifact 3 from the README. One generic method, call<T>(model, method, body, schema), does the work, with Zod 4 validating every response at the boundary (section 02 · runtime validation). A compile-time type alone would be a guess: nothing stops a module from changing what a field returns.

Four decisions matter:

  • A typed error per real response: 401 no key, 403 private method or access, 404 unknown model or method, 422 validation, and 5xx for the rest. Callers branch on the class, not on a string.
  • Strip debug. Every error body carries a full Python traceback, 1–5 KB with server paths in it. The client keeps name and message only, so it can't reach your logs or your API's clients.
  • A timeout through AbortSignal.timeout, wrapping both fetch and the body read. A timeout becomes OdooUnknownOutcomeError, because the server may have committed. So there's no automatic retry in here: lesson 28 covers how to retry safely.
  • Model Odoo's value shapes. A many2one is [id, name] or false. An empty char is false, not null or "". Two small schemas, many2one and odooText, normalize those once.

export class OdooClient {
  readonly #baseUrl: string;
  readonly #headers: Record<string, string>;
  readonly #timeoutMs: number;
  readonly #lang: string;

  constructor(opts: OdooClientOptions) {
    this.#baseUrl = opts.baseUrl;
    this.#timeoutMs = opts.timeoutMs ?? 10_000;
    this.#lang = opts.lang ?? "en_US";
    this.#headers = {
      Authorization: `bearer ${opts.apiKey}`,
      "Content-Type": "application/json; charset=utf-8",
      "User-Agent": "shop-sync/1.0",
      ...(opts.database ? { "X-Odoo-Database": opts.database } : {}),
    };
  }

  async call<T>(model: string, method: string, body: CallBody, schema: z.ZodType<T>): Promise<T> {
    const where = `${model}.${method}`;
    const payload = { ...body, context: { lang: this.#lang, ...body.context } };
    let res: Response;
    let text: string;
    try {
      res = await fetch(`${this.#baseUrl}/json/2/${model}/${method}`, {
        method: "POST",
        headers: this.#headers,
        body: JSON.stringify(payload),
        signal: AbortSignal.timeout(this.#timeoutMs),
      });
      text = await res.text();
    } catch (cause) {
      // الطلب ممكن يكون وصل واتعمل commit قبل ما الرد يضيع
      throw new OdooUnknownOutcomeError(`${where}: no response`, 0, undefined, { cause });
    }
    if (!res.ok) throw toOdooError(res.status, text, where);

    const parsed = schema.safeParse(JSON.parse(text));
    if (!parsed.success) {
      throw new OdooSchemaError(`${where}: ${z.prettifyError(parsed.error)}`, res.status);
    }
    return parsed.data;
  }
}

function toOdooError(status: number, text: string, where: string): OdooError {
  // بناخد الـ name والـ message بس، والـ debug traceback منسيبوش يوصل للـ logs
  const parsed = OdooErrorBody.safeParse(safeJson(text));
  const odooName = parsed.success ? parsed.data.name : undefined;
  const message = `${where}: ${parsed.success ? parsed.data.message : `HTTP ${status}`}`;
  if (status === 401) return new OdooAuthError(message, status, odooName);
  if (status === 403) return new OdooForbiddenError(message, status, odooName);
  if (status === 404) return new OdooNotFoundError(message, status, odooName);
  if (status === 422) return new OdooValidationError(message, status, odooName);
  return new OdooServerError(message, status, odooName);
}

function safeJson(text: string): unknown {
  try {
    return JSON.parse(text);
  } catch {
    return undefined;
  }
}

Part 5 — Generating types from the database 🟡 Intermediateالجزء 5 — توليد الـ types من الـ database

English

Writing an interface by hand for a model with 200 fields is a waste of time and wrong within a month. fields_get describes every field in the database you're talking to: type, selection values and relation. A small generator turns that into TypeScript interfaces and Zod schemas from one mapping, so the two can't disagree.

Three things to know before trusting the output. It describes one database as seen by one user: the admin and the bot get different field lists, because fields with groups= are hidden. A field added by a module on one customer's database is invisible on another's, and asking for a field that doesn't exist isn't a clean 4xx: it's a 500 ValueError. And the mapping isn't perfect: against 40 real invoices, 1 of the 267 fields didn't match, because invoice_pdf_report_file is declared binary yet came back as an object with filename and content. That's what validating against real rows is for. For the same reason the generator ignores required and keeps | false on every text field.

So generate against the oldest supported database, commit the generated file, and add a missingFields check at startup: the integration stops with a readable message at deploy time rather than failing at night.

const FieldMeta = z.object({
  type: z.string(),
  string: z.string(),
  required: z.boolean().optional(),
  selection: z.array(z.tuple([z.string(), z.string()])).optional(),
  relation: z.string().optional(),

const FieldsGet = z.record(z.string(), FieldMeta);

// بنرجع الـ TS type والـ Zod expression مع بعض عشان ميختلفوش
function mapField(meta: FieldMeta): { ts: string; zod: string } {
  const orFalse = (ts: string, zod: string) => ({
    ts: `${ts} | false`,
    zod: `z.union([${zod}, z.literal(false)])`,
  });
  switch (meta.type) {
    case "integer":
    case "float":
    case "monetary":
      return { ts: "number", zod: "z.number()" };
    case "boolean":
      return { ts: "boolean", zod: "z.boolean()" };
    case "many2one":
      return orFalse("[number, string]", "z.tuple([z.number(), z.string()])");
    case "one2many":
    case "many2many":
      return { ts: "number[]", zod: "z.array(z.number())" };
    case "selection": {
      const values = (meta.selection ?? []).map(([key]) => JSON.stringify(key));
      if (values.length === 0) return orFalse("string", "z.string()");
      return orFalse(values.join(" | "), `z.enum([${values.join(", ")}])`);
    }
    case "char":
    case "text":
    case "html":
    case "date":
    case "datetime":
    case "binary":
    case "reference":
      return orFalse("string", "z.string()");
    default:
      return { ts: "unknown", zod: "z.unknown()" };
  }
}

const pascal = (model: string) =>
  model.split(".").map((s) => s[0]!.toUpperCase() + s.slice(1)).join("");

export async function generate(client: OdooClient, model: string): Promise<string> {
  const fields = await client.call(
    model,
    "fields_get",
    { attributes: ["type", "string", "required", "selection", "relation"] },
    FieldsGet,
  );
  const name = pascal(model);
  const names = Object.keys(fields).sort();
  const tsLines = names.map((f) => `  ${JSON.stringify(f)}: ${mapField(fields[f]!).ts};`);
  const zodLines = names.map((f) => `  ${JSON.stringify(f)}: ${mapField(fields[f]!).zod},`);
  return [
    `export interface ${name} {`,
    ...tsLines,
    `}`,
    `export const ${name}Schema = z.object({`,
    ...zodLines,
    `});`,
    ``,
  ].join("\n");
}

export async function writeModels(client: OdooClient, models: string[], file: string) {
  const parts = await Promise.all(models.map((m) => generate(client, m)));
  writeFileSync(file, `import { z } from "zod";\n\n${parts.join("\n")}`);
}

export async function missingFields(client: OdooClient, model: string, needed: string[]): Promise<string[]> {
  const fields = await client.call(model, "fields_get", { attributes: ["type"] }, z.record(z.string(), z.unknown()));
  return needed.filter((name) => !(name in fields));
}

Part 6 — One transaction per call 🔴 Advancedالجزء 6 — transaction واحد لكل call

English

From the docs: "All calls to the JSON-2 endpoint run in their own SQL transaction." It's committed on success and discarded on error, and it's not possible to chain multiple calls inside a single transaction. That has two sides, and the run below proves both: one create with two records, where the second is invalid, leaves 0 records. Two separate calls with the same data leave 1, already committed, and nothing you do can undo it.

You have three ways to get atomicity across several operations:

  1. One server-side method. Put the steps in a public method in a small module, so they share one transaction. This is what the docs recommend, and it's the default choice when all the work is inside Odoo. Note that _create_invoices is private (a 403 over the API), which is another reason you need your own method.
  2. Idempotent steps with compensation. Each call can be repeated safely and the worker resumes where it stopped. You accept in-between states, and on a dead end you run the opposite action, such as a credit note. Lesson 28 builds this.
  3. A saga, for when the steps span several systems, such as Odoo plus a payment gateway plus your shop (section 11 · sagas).

The transaction also has a cost, since each call pays for authentication, a cursor and a commit. Measured here on a loaded Windows machine over loopback: 20 sequential calls took ≈358 ms in the run below (≈18 ms each), and ≈1.0–1.2 s in an earlier run when the machine was busier.

def action_create_invoice_from_order(self):
    # (1) كل الخطوات دي في transaction واحد: يا كلها يا ولا حاجة
    self.ensure_one()
    if self.state == 'draft':
        self.action_confirm()
    # (2) لو الفاتورة موجودة من محاولة قبل كده منعملش واحدة تانية
    invoice = self.invoice_ids.filtered(lambda move: move.state != 'cancel')[:1]
    if not invoice:
        invoice = self._create_invoices()
    if invoice.state == 'draft':
        invoice.action_post()
    # (3) فشل متعمد للـ lab عشان نثبت الـ rollback
    if self.env.context.get('lab_fail_after_post'):
        raise UserError('simulated failure after posting')
    return {
        'invoice_id': invoice.id,
        'name': invoice.name,
        'amount_total': invoice.amount_total,
        'state': invoice.state,
    }

بالعامية

من الـ docs: "All calls to the JSON-2 endpoint run in their own SQL transaction." يعني كل call ليه transaction لوحده، بيتعمله commit لو نجح وبيترمي لو فشل، ومينفعش تربط أكتر من call في transaction واحد. وده ليه وشين، والتجربة فوق بتثبت الاتنين: create واحد فيه سجلين والتاني غلط بيسيب 0 records. وcallين منفصلين بنفس الـ data بيسيبوا 1، متسيف خلاص ومفيش حاجة ترجّعه.

عندك 3 طرق تضمن بيهم الـ atomicity على كذا عملية:

  1. Method واحدة على السيرفر. حط الخطوات في public method في module صغير، فيبقوا في transaction واحد. ده اللي الـ docs بتنصح بيه، وهو الاختيار الافتراضي لما الشغل كله جوه Odoo. ولاحظ إن _create_invoices خاصة (403 على الـ API)، وده سبب زيادة تعمل method بتاعتك.
  2. خطوات idempotent مع compensation. كل call ينفع يتكرر بأمان والـ worker بيكمل من مكان ما وقف. إنت بتقبل حالات وسطانية، ولو وصلت لطريق مسدود بتعمل العملية العكسية زي credit note. الدرس 28 بيبني ده.
  3. Saga، لما الخطوات تعدي كذا نظام، زي Odoo و payment gateway والمتجر بتاعك (قسم 11 · sagas).

والـ transaction ليه تمن كمان، لأن كل call بيدفع authentication و cursor و commit. المقاس هنا على جهاز Windows عليه ضغط وعلى loopback: 20 call ورا بعض خدوا ≈358 ms في التجربة اللي تحت (≈18 ms للـ call)، و≈1.0–1.2 ثانية في تجربة قبلها لما الجهاز كان عليه ضغط أكتر.

فين هستخدمه في شغلي؟ الـ checkout بيحتاج: أوردر، confirm، فاتورة. لو عملتهم 3 calls من Node والـ process وقع بعد التاني، هيفضل عندك أوردر متأكد ومحجوز ليه مخزون ومن غير فاتورة، والمحاسب هيكتشفه آخر الشهر. الحل تكتب action_create_invoice_from_order في module وتناديها مرة واحدة. الغلطة الشائعة إنك تفتكر إن Promise.all أو try/catch في Node بيعمل transaction: Odoo عمل commit خلاص.

If it's all Odoo work, I add a public server-side method and call it once. If other systems are involved, I make each step idempotent with a stable key, persist progress so it can resume, and define a compensating action for dead ends.

Part 7 — What breaks 🔴 Advancedالجزء 7 — إيه اللي بيكسر

English

Five failures that all pass in development, each measured below (timings are ≈, from a loaded Windows machine):

  • Offset pagination on a moving dataset. New rows at the front push old ones onto the next page, so you read them twice, and deletes pull rows back so you skip some. Use a keyset cursor: ["id", ">", last] with order: "id asc".
  • No limit, no fields. search_read without fields returns every column, images included. There's no default page size.
  • A company the user isn't allowed. allowed_company_ids in the context with a wrong id is a 403. In a multi-company database, pass it deliberately rather than relying on the user's default.
  • N+1 calls. A loop of read pays the per-call cost each time. read and create take lists.
  • Concurrent writes on one record. Odoo runs in REPEATABLE READ and retries serialization failures on the server, up to 5 tries, waiting a random time up to 2^n seconds. That retry has a budget. 8 parallel writes on one record took ≈17–21 s, and across three runs the result varied: all 8 returned 200 once, 7 did once, and in the run below 6 did and 2 got a 500. So a concurrent write can fail even though the server retried it.

5 حاجات بتعدي في الـ development، وكل واحدة متقاسة فوق (الأوقات تقريبية ومن جهاز Windows عليه ضغط):

  • الـ offset pagination على data بتتغير. الصفوف الجديدة قدام بتزق القديمة للصفحة اللي بعدها فبتقراها مرتين، والحذف بيسحب الصفوف لورا فبتفوّت منها. استخدم keyset cursor: ["id", ">", last] مع order: "id asc".

  • شركة الـ user مش مسموحله بيها. allowed_company_ids في الـ context بـ id غلط بيرجع 403. في database فيها كذا شركة ابعتها بقصد، ومتعتمدش على الـ default بتاع الـ user.
  • الـ N+1 calls. Loop من read بيدفع تمن الـ call كل مرة. وread وcreate بياخدوا lists.
  • Writes متوازيين على نفس الـ record. What breaks at scale Every one of these calls runs on the same workers that serve your users' screens. A sync with no concurrency limit competes with the accountant closing the month. Cap your concurrency and run heavy jobs off-hours.
كل الـ calls دي بتشتغل على نفس الـ workers اللي بيخدموا شاشات المستخدمين. Sync من غير حد للـ concurrency بينافس المحاسب وهو بيقفل الشهر. حط حد للـ concurrency وشغّل الـ jobs التقيلة بره مواعيد الشغل.

import { z } from "zod";
import { OdooClient } from "./odoo-client.ts";

// الحل: keyset pagination كـ async generator، الذاكرة ثابتة مهما كان العدد
export async function* iterateAll<T extends { id: number }>(
  client: OdooClient,
  model: string,
  domain: unknown[],
  fields: string[],
  schema: z.ZodType<T>,
  pageSize = 200,
): AsyncGenerator<T> {
  for (let last = 0; ;) {
    const rows = await client.call(model, "search_read", {
      domain: [...domain, ["id", ">", last]],
      fields,
      order: "id asc",
      limit: pageSize,
    }, z.array(schema));
    if (rows.length === 0) return;
    yield* rows;
    last = rows.at(-1)!.id;
  }
}

}

Cheat sheet · الخلاصة

  • POST /json/2/<model>/<method>, Authorization: bearer <key>, named arguments plus ids and context.
  • Odoo Online needs the Custom plan for the external API. Self-hosted Community has no such check.
  • Keys need an expiry (90 days here), are shown once and are stored hashed. Rotate: create, deploy, verify, revoke.
  • Use revoke, not remove: remove returns 200 and deletes nothing over the API.
  • A dedicated bot user with least privilege. Never admin, never a key in Git.
  • db service is gone. common and object go in Odoo 22 (fall 2028) and Online 21.1 (winter 2027).
  • Statuses: 401 key, 403 private or access, 404 unknown, 422 validation, 500 for an unknown field. Strip debug.
  • Many2one is [id, name] or false; an empty char is false.
  • fields_get depends on the user and the installed modules. Commit generated types and check missingFields at startup.
  • One transaction per call. For atomicity: one server-side method, idempotent steps, or a saga.
  • Use a keyset cursor, always set limit and fields, and batch instead of looping.
  • A timeout means unknown outcome: never retry a non-idempotent write blindly.
بالعامية
  • POST /json/2/<model>/<method> و Authorization: bearer <key>، والـ arguments بالاسم ومعاهم ids وcontext.
  • Odoo Online محتاج خطة Custom عشان الـ external API. و Community المستضافة عندك مفيهاش الفحص ده.
  • الـ keys لازم ليها expiry (هنا 90 يوم)، بتظهر مرة واحدة ومتخزنة hash. الـ rotation: اعمل، وزّع، اتأكد، الغي.
  • استخدم revoke مش remove: الـ remove بيرجع 200 ومبيمسحش حاجة على الـ API.
  • Bot user مخصوص بأقل صلاحيات. عمره ما يبقى admin، وعمر الـ key ما يدخل Git.
  • خدمة db اتشالت. وcommon وobject هيتشالوا في Odoo 22 (خريف 2028) و Online 21.1 (شتا 2027).
  • الـ statuses: 401 الـ key، 403 خاصة أو صلاحيات، 404 مش موجود، 422 validation، و 500 لـ field مش موجود. شيل الـ debug.
  • الـ many2one بيبقى [id, name] أو false، والـ char الفاضي بيبقى false.
  • fields_get بيتغير حسب الـ user والـ modules المتسطبة. اعمل commit للـ types المولّدة وافحص missingFields عند الـ startup.
  • Transaction واحد لكل call. وللـ atomicity: method واحدة على السيرفر، أو خطوات idempotent، أو saga.
  • استخدم keyset cursor، وحط limit وfields دايمًا، واعمل batching بدل الـ loops.
  • الـ timeout معناه النتيجة مش معروفة: عمرك ما تعيد write مش idempotent على العمياني.
