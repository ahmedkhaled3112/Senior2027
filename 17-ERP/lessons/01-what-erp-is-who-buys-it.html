Why this matters · ليه ده مهم

English

An ERP is the system a company's money and stock pass through. You will meet one as a backend engineer even if you never join an ERP vendor: your first large customer asks whether your product can post to their ERP, or your company outgrows Stripe plus spreadsheets and someone has to decide what replaces them. Knowing what an ERP guarantees, what it costs and who does the work lets you make that call with numbers. It also separates you in fintech and B2B interviews, where "how do you keep the money correct across systems?" is the real question.

بالعامية

الـ ERP هو النظام اللي فلوس الشركة ومخزونها بيعدّوا منه. هتقابله كـ backend engineer حتى لو عمرك ما اشتغلت عند vendor: أول عميل كبير هيسألك "الـ product بتاعك يقدر يبعت للـ ERP بتاعنا؟"، أو شركتك هتكبر على Stripe والـ Excel وحد لازم يقرر إيه اللي هيحل محلهم. لما تعرف الـ ERP بيضمن إيه، وبيكلف كام، ومين اللي بيشتغل فيه، هتاخد القرار ده بأرقام. وده كمان بيفرق معاك في interviews الـ fintech والـ B2B، لأن السؤال الحقيقي هناك هو "إزاي تضمن إن الفلوس صح عبر الأنظمة؟".

Part 1 — One data model versus glued SaaS 🟢 Basicالجزء 1 — data model واحد قصاد SaaS متلزّق ببعضه

English

An ERP (Enterprise Resource Planning system) is a set of integrated business modules that share one data model, usually one database. The consequence that matters to an engineer: when an operational document is posted, the accounting rows are written by the same code, in the same database transaction, and joined to that document by foreign keys. There is nothing in between that can get lost.

Now take the common startup stack: Stripe for payments, Shopify for orders, a CRM for customers, an accounting tool for the books, all joined by webhooks. Each vendor has its own database, and no transaction spans two vendors. A webhook is at-least-once delivery at best, and only while the receiver is up and its handler is correct. Retries shrink the gap but can't close it, because a handler can return 200 and then crash. So you end up owning deduplication and a reconciliation job.

The first program below is a stand-in (no vendor is called): 1,000 orders, 5% of webhooks lost, seeded so it repeats exactly. The second runs the same sale through real Odoo 20 and prints the journal lines. The third proves atomicity from a separate database connection: the same sale raises an exception before commit, and nothing persists.

One accuracy note. In the Odoo UI, confirm, deliver and invoice are separate clicks, so separate transactions. The script runs them in one transaction only to make the rollback visible. The guarantee you get in normal use is per step: each step writes its own rows and the rows it owes other modules atomically. Also, in Odoo 20 a delivery alone creates no journal entry, even under real_time valuation; the cost of goods sold lands on the customer invoice, which is why the invoice below has five lines. Lesson 22 covers valuation.

// مولّد أرقام بـ seed عشان النتيجة تتكرر بالظبط كل مرة
export function mulberry32(seed: number): () => number {
  let a = seed;
  return () => {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

function webhook(target: Map<number, Order>, order: Order): void {
  if (rand() < DROP_RATE) return;
  target.set(order.id, order);
}

// حماية: الـ port الفاضي أو الـ default بيوصلك بالـ database الحقيقية بتاعتك
export function connect(): pg.Client {
  const url = new URL(process.env.DATABASE_URL ?? "");
  const n = Number(url.port);
  if (!/^\d+$/.test(url.port) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port '${url.port}'`);
  }
  return new pg.Client({ connectionString: url.href });
}

بالعامية

الـ ERP هو مجموعة modules متكاملة (حسابات، مبيعات، مشتريات، مخزون، تصنيع، HR، وغيرهم) فوق data model واحد، وغالبًا database واحدة. اللي يهمك كمهندس: لما document تشغيلي يتسجل، القيود المحاسبية بتتكتب من نفس الكود، في نفس الـ database transaction، ومربوطة بالـ document ده بـ foreign keys. مفيش حاجة في النص ممكن تضيع.

قارن ده بالـ stack المعتاد في أي startup: Stripe للدفع، Shopify للطلبات، CRM للعملاء، وأداة حسابات، وكله متوصل بـ webhooks. كل vendor ليه database لوحده، ومفيش transaction بتعدّي بين اتنين vendors. الـ webhook أحسن حاجة فيه at-least-once، وده طول ما الـ receiver شغال والـ handler سليم. الـ retries بتقلل الفجوة بس مش بتقفلها، لأن الـ handler ممكن يرد 200 وبعدين يقع. فبتلاقي نفسك شايل الـ deduplication و reconciliation job.

أول برنامج stand-in (مفيش vendor بيتنادى عليه): 1000 طلب و5% من الـ webhooks بتضيع، بـ seed عشان النتيجة تتكرر. التاني بيعمل نفس البيعة في Odoo 20 الحقيقي ويطبع سطور القيد. التالت بيثبت الـ atomicity من connection منفصلة: نفس البيعة بتعمل exception قبل الـ commit ومفيش حاجة بتتحفظ.

ملحوظة دقة: في شاشات Odoo، الـ confirm والـ deliver والـ invoice كليكات منفصلة، يعني transactions منفصلة. السكريبت حطهم في transaction واحدة عشان الـ rollback يبان بس. الضمان اللي بتاخده في الاستخدام العادي لكل خطوة: كل خطوة بتكتب الـ rows بتاعتها والـ rows اللي عليها لباقي الـ modules مع بعض. وكمان في Odoo 20 التسليم لوحده مش بيعمل قيد، حتى مع real_time valuation؛ تكلفة البضاعة بتنزل على فاتورة العميل، وعشان كده الفاتورة فوق ليها 5 سطور. درس 22 بيشرح الـ valuation.

فين هستخدمه في شغلي؟ عندك checkout في Node بيعمل charge في Stripe وبيبعت event لـ service الفواتير. لو الـ service دي وقعت ساعة deploy، هتلاقي آخر الشهر إن المحصّل في Stripe أكبر من الإيراد عندك، ومحدش عارف الفرق جاي منين. أول خطوة تعملها: job يومية تقارن charges بالفواتير وتطلّع الفرق بالـ id. دي نفس الـ reconciliation اللي الـ ERP بيوفرها عليك جوه modules بتاعته. الغلطة الشائعة إنك تفتكر الـ retries كفاية.
Trade-off: one schema One schema means no reconciliation between modules. It also means one blast radius (a bad migration or a locked table hurts sales and accounting together) and one upgrade (you can't upgrade inventory alone). And "one database" isn't absolute: two-tier and "postmodern" ERP are loosely coupled on purpose, a core plus specialist systems, and they accept the integration work in exchange. Part 7 builds one.
الـ schema الواحد معناه مفيش reconciliation بين الـ modules. وبرضه معناه blast radius واحد (migration بايظة أو table مقفول بيوجع المبيعات والحسابات مع بعض) و upgrade واحد (متقدرش ترقّي المخزون لوحده). و"database واحدة" مش قاعدة مطلقة: الـ two-tier و الـ "postmodern" ERP loosely coupled بالقصد، core ومعاه أنظمة متخصصة، وبيقبلوا شغل الـ integration في المقابل. الجزء 7 بيبني واحد.
Interview question "Stripe retries webhooks. Why isn't that as good as an ERP's single transaction?" → Retries give at-least-once delivery to a receiver that may have bugs. They don't give atomicity across two databases, so you still need idempotent handlers and a reconciliation job. A single transaction removes that class of failure, at the cost of one blast radius.
"Stripe بيعمل retry للـ webhooks. ليه ده مش زي الـ transaction الواحدة بتاعة الـ ERP؟" ← الـ retries بتديك at-least-once لـ receiver ممكن يكون فيه bugs. مش بتديك atomicity بين two databases، فلسه محتاج handlers تكون idempotent و reconciliation job. الـ transaction الواحدة بتشيل النوع ده من الأعطال كله، والتمن blast radius واحد.

Part 3 — ERP vs accounting software vs CRM 🟢 Basicالجزء 3 — الـ ERP والـ accounting software والـ CRM

English

Each tool answers a different question. Accounting software answers "what do we own and owe, and did we make a profit?". A CRM answers "who might buy, and how likely?". An ERP answers "when something physically or commercially happens, how does every department's record stay in step?". You can see the difference in the data model. A crm.lead has a probability and an expected revenue but no journal. An account.move has a journal and lines but no stock location. Where the two do connect, the link lives in a bridge module (sale_crm, stock_account), so the CRM on its own never learns accounting.

The decision function below is a teaching heuristic: the rules are my judgment, not a published standard. Notice which signal drives it: stock that has to tie to the books. The bad decision to avoid is the first profile, a 6-person service company with no stock. An ERP gives it nothing that an accounting package doesn't, and it would pay for configuration, training and upgrades it doesn't need.

type Profile = {
  name: string;
  employees: number;
  branches: number;
  holdsStock: boolean;
  manufactures: boolean;
  needsAuditTrail: boolean;
  salesPipeline: boolean;
};

type Answer = "accounting package" | "CRM plus accounting" | "ERP";

function decide(p: Profile): { answer: Answer; why: string } {
  // الإشارة الأقوى: حركة بضاعة لازم تطلّع قيد محاسبي من غير نقل يدوي
  if (p.manufactures) return { answer: "ERP", why: "bill of materials must drive stock and cost" };

  if (p.salesPipeline) return { answer: "CRM plus accounting", why: "pipeline plus invoices, no stock to tie" };
  return { answer: "accounting package", why: "one site, no audit, no pipeline: books are enough" };
}

Part 4 — Who buys and why 🟢 Basicالجزء 4 — مين بيشتري وليه

English

Companies rarely buy an ERP because it's a good idea. They buy because something broke. Four triggers come up repeatedly: Excel stops being trustworthy, a second branch opens, stock becomes valuable enough to count, and an auditor, bank or tax authority asks for a trail. Published surveys on buying reasons use different categories and don't agree with each other, so this lesson names the triggers without percentages.

The Excel failure is a concurrency bug, and you already know the fix. Two branches work from the same stock sheet, copied or emailed each morning, so neither sees the other's sales until the day ends. With the last 3 units, the first program below measures how often they oversell across 1,000 simulated days.

The second program does it on real Postgres with two concurrent connections. Read-then-write without a lock reproduces the Excel number almost exactly. SELECT ... FOR UPDATE on the single stock row makes the second branch wait and then read the updated quantity, and overselling drops to 0. See section 09 · locks. An ERP is, among other things, a product that has this row and this lock already in place.

// البيعة: اقرا الكمية، احسب المتاح، اكتب الباقي، وكله جوه transaction
async function sell(db: Client, demand: number, lock: boolean): Promise<number> {
  await db.query("BEGIN");
  const res = await db.query<{ qty: number }>(
    `SELECT qty FROM stock WHERE sku = 'CHAIR-1' ${lock ? "FOR UPDATE" : ""}`,
  );
  const qty = res.rows[0]!.qty;
  const sold = Math.min(demand, qty);
  await db.query("UPDATE stock SET qty = $1 WHERE sku = 'CHAIR-1'", [qty - sold]);
  await db.query("COMMIT");
  return sold;
}

async function simulate(lock: boolean): Promise<void> {
  const rand = mulberry32(7);
  let daysOversold = 0;
  let unitsOversold = 0;
  for (let day = 0; day < DAYS; day++) {
    await branchA.query("DELETE FROM stock");
    await branchA.query("INSERT INTO stock (sku, qty) VALUES ('CHAIR-1', 3)");
    const demandA = Math.floor(rand() * 4);
    const demandB = Math.floor(rand() * 4);
    const [soldA, soldB] = await Promise.all([sell(branchA, demandA, lock), sell(branchB, demandB, lock)]);
    const over = Math.max(0, soldA + soldB - 3);
    if (over > 0) daysOversold++;
    unitsOversold += over;
  }
  console.log(`${lock ? "FOR UPDATE" : "no lock   "} days oversold: ${daysOversold}, units oversold: ${unitsOversold}`);
}

فين هستخدمه في شغلي؟ أول عميل B2B في مشروعك الجانبي بيقولك: "تقدر تبعت للـ ERP بتاعنا؟". الإجابة الصح مش "أيوه" على طول. اسأله: أنهي ERP وأنهي version؟ أنهي events (فاتورة، دفعة، مرتجع)؟ مين الـ system of record للأسعار وللعملاء؟ بتستحملوا duplicates ولا لازم idempotency key؟ ده اللي هنبنيه في درس 28. الغلطة الشائعة: read ثم write من غير lock في أي endpoint بيحجز مخزون أو رصيد.
Trade-off: FOR UPDATE on one hot row One row and one lock is correct, and it serializes every sale of that product. For a normal catalogue that's fine. For a flash sale on one SKU the row becomes a bottleneck. UPDATE stock SET qty = qty - $1 WHERE sku = $2 AND qty >= $1 holds the lock for a shorter time and needs one round trip.

English

An ERP bill has two very different halves: the license, and the people who make it work. ERP Research puts the integrator's share at 40–70% of the implementation budget, depending on project size. Treat that carefully: it's a lead-generation site with no published method. For 51–250 users, the same page says 45–60% and a budget of $150,000–$750,000, and those figures describe companies well above a typical Egyptian SMB.

The calculator models an 80-user company over 3 years, labels every input as a dated source or an assumption, and runs both ends of each range. Odoo's price lists vary a lot by country: $16.40 per user per month on a low-cost list and $61.00 on the US list, a factor of about 3.7, and the page fetched showed no region.

Read how the conclusion moves. At the low-cost price, services exceed the license in all four cases, by 1.84x up to 16.12x. At the US price on a small budget, it flips: services are only 0.50x–0.87x of the license. Services are 25–74% of three-year spend. So "services cost more than the software" is usually right but depends on your inputs.

That money is also why most ERP practitioners work at implementation partners: if services are the larger share of the budget, the jobs follow the services. This is an inference from the budget split, because no source counts ERP jobs by employer type. Lesson 41 covers it with the partner numbers.

Part 7 — Deployment models and two-tier ERP 🟢 Basicالجزء 7 — طرق التشغيل والـ two-tier ERP

English

There are four shapes. Cloud (SaaS): the vendor runs it. On-premise: you run it on your own or rented servers. Hybrid: some modules in the cloud, some on your servers. Two-tier: a heavy ERP at headquarters and a lighter one in subsidiaries, with data exchanged between them. Two-tier trades the single-transaction guarantee from Part 1 for local speed and lower cost, so it reintroduces integration work, and consolidation has to be idempotent.

The stand-in below models it on loopback: a subsidiary posts locally and a nightly job sends the day's total to HQ. The scheduler runs the job twice, as happens after a timeout retry or when a cron is configured on two servers. Without an idempotency key, HQ's total doubles. With a key derived from what the batch means (subsidiary plus day), the second call is ignored. The full treatment of keys is in section 12 · idempotency keys. No real ERP is involved in this program.

// تشغيل: node two-tier.ts
// الـ HQ هنا stand-in على loopback، مش SAP ولا ERP حقيقي
import http from "node:http";
import type { AddressInfo } from "node:net";

type Batch = { subsidiary: string; day: string; revenuePiastres: number };

function startHq(useIdempotency: boolean) {
  const seen = new Set<string>();
  const state = { consolidatedPiastres: 0, duplicatesIgnored: 0 };
  const server = http.createServer((req, res) => {
    let body = "";
    req.on("data", (c) => (body += c));
    req.on("end", () => {
      const batch = JSON.parse(body) as Batch;
      const key = req.headers["idempotency-key"];
      // لازم نشوف المفتاح قبل ما الرقم يتجمع، مش بعده
      if (useIdempotency && typeof key === "string") {
        if (seen.has(key)) {
          state.duplicatesIgnored++;
          res.writeHead(200).end("duplicate");
          return;
        }
        seen.add(key);
      }
      state.consolidatedPiastres += batch.revenuePiastres;
      res.writeHead(201).end("ok");
    });
  });
  return { server, state };
}

async function nightlyJob(url: string, batch: Batch, withKey: boolean): Promise<number> {
  const headers: Record<string, string> = { "content-type": "application/json" };
  // المفتاح مبني من معنى الدفعة (فرع ويوم)، مش uuid جديد كل تشغيلة
  if (withKey) headers["idempotency-key"] = `${batch.subsidiary}:${batch.day}`;
  const res = await fetch(url, { method: "POST", headers, body: JSON.stringify(batch) });
  await res.text();
  return res.status;
}

Two-tier: ERP تقيل في الـ HQ وواحد أخف في الفروع، والبيانات بتتبادل بينهم. الـ Two-tier بيبدّل ضمان الـ transaction الواحدة بتاع الجزء 1 بسرعة محلية وتكلفة أقل، فبيرجّع شغل الـ integration، والـ consolidation لازم يبقى idempotent.

الـ stand-in ده على loopback: فرع بيسجل محليًا و job كل ليلة بيبعت إجمالي اليوم للـ HQ. الـ scheduler بيشغّل الـ job مرتين، زي ما بيحصل بعد retry على timeout أو لما cron يتظبط على two servers. من غير idempotency key، إجمالي الـ HQ بيتضاعف. ومع مفتاح مبني من معنى الدفعة (الفرع واليوم)، التانية بتتجاهل. شرح الـ keys كامل في قسم 12 · idempotency keys. مفيش ERP حقيقي في البرنامج ده.

فين هستخدمه في شغلي؟ أي job بتجمّع أرقام وتبعتها لنظام تاني: عمولات آخر الشهر، settlement لتجار، sync يومي لفروع. اسأل "لو الـ job دي اشتغلت مرتين؟". لو الإجابة "الرقم هيتضاعف"، ضيف مفتاح مبني من اليوم والجهة. الغلطة الشائعة: crypto.randomUUID() جوه الـ job نفسها، فكل تشغيلة بتطلع مفتاح جديد والحماية بتبقى شكل بس.
What breaks at scale The Set of seen keys here is in memory, so a restart of HQ forgets them. In production the key goes in a table with a unique constraint, written in the same transaction as the total. Otherwise a crash between the two writes either loses the batch or counts it twice.
الـ Set بتاع المفاتيح هنا في الـ memory، فلو الـ HQ عمل restart هينساهم. في production المفتاح بيتحط في table بـ unique constraint، ويتكتب في نفس الـ transaction مع الإجمالي. وإلا الـ crash بين الكتابتين يا هيضيّع الدفعة يا هيعدّها مرتين.

❌ Trusting the webhook alone

بالعامية

❌ الرد بـ 200 قبل الحفظ معناه Stripe مش هيعيد المحاولة، ولو الـ process وقع بعدها الإيراد ضاع للأبد. ✅ خزّن الـ event الأول بـ unique id (فالـ duplicates بتتجاهل)، رد بعدها، واعمل job يومية تقارن charges بالإيراد عشان تمسك اللي عدّى. شوف قسم 09 · outbox.

❌ Read, then write, no lock

-- الفرع التاني قرا نفس الرقم في اللحظة دي
UPDATE stock SET qty = 0 WHERE sku = 'CHAIR-1';
✅ Lock the row, or update conditionally 
UPDATE stock SET qty = qty - 3
WHERE sku = 'CHAIR-1' AND qty >= 3;
-- لو rowCount طلع 0 يبقى مفيش كمية كفاية
بالعامية

❌ الـ read ثم write بيخلي الفرعين يبيعوا نفس القطع: ده اللي طلّع ≈ 592 قطعة oversold. ✅ يا تعمل FOR UPDATE، يا تخلي الـ UPDATE نفسه بشرط qty >= 3 وتبص على rowCount.

❌ A share as a bare constant

const sapShare = 0.23;
✅ Value with source and denominator 
const sapShare = [
  { source: "ERP Research", value: 0.23, denominator: "core ERP" },
  { source: "Apps Run the World", value: 0.066, denominator: "broad" },
];
بالعامية

❌ رقم واحد في slide بيبان حقيقة وهو في الأصل اختيار denominator. ✅ حط المصادر جنب بعض وقول الفرق بينهم 3.5 مرة، وخلّي القارئ يشوف إن الرقم مش ثابت.

❌ A fresh key on every run

  crypto.randomUUID();
✅ A key derived from the batch

بالعامية

❌ الـ UUID الجديد كل تشغيلة معناه الـ HQ شايف كل مرة طلب جديد، والإجمالي بيتضاعف رغم إن الكود فيه header اسمه idempotency. ✅ المفتاح لازم يتحسب من معنى الدفعة، عشان التشغيلة التانية تطلّع نفس المفتاح.

// تشغيل: node ex-reconcile.ts
import { mulberry32 } from "./rng.ts";

function run(dropRate: number): void {
  const rand = mulberry32(2026);
  const source = new Set<number>();
  const crm = new Set<number>();
  for (let id = 1; id <= 1_000; id++) {
    source.add(id);
    if (rand() >= dropRate) crm.add(id);
  }
  // الـ job بتطلّع الفرق بين المصدر والـ CRM وتضيفه، وتشغيلها مرتين مش بيغيّر حاجة
  const reconcile = () => {
    let added = 0;
    for (const id of source) {
      if (!crm.has(id)) {
        crm.add(id);
        added++;
      }
    }
    return added;
  };
  console.log(`drop ${dropRate}: first pass added ${reconcile()}, second pass added ${reconcile()}, crm now ${crm.size}`);
}

run(0.05);
run(0.2);

Solution · الحل 
// تشغيل: node ex-lost-response.ts
import http from "node:http";
import type { AddressInfo } from "node:net";

const seen = new Set<string>();
let consolidated = 0;
let dropNextResponse = true;

const server = http.createServer((req, res) => {
  req.resume();
  req.on("end", () => {
    const key = String(req.headers["idempotency-key"]);
    if (!seen.has(key)) {
      seen.add(key);
      consolidated += 12_500_000;
    }
    // الـ HQ سجّل الدفعة فعلًا، وبعدين الرد ضاع في الشبكة
    if (dropNextResponse) {
      dropNextResponse = false;
      req.socket.destroy();
      return;
    }
    res.writeHead(200).end("ok");
  });
});
await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));
const url = `http://127.0.0.1:${(server.address() as AddressInfo).port}/consolidate`;

async function postWithRetry(attempts: number): Promise<number> {
  for (let i = 1; i <= attempts; i++) {
    try {
      const res = await fetch(url, { method: "POST", headers: { "idempotency-key": "alex-branch:2026-11-10" }, body: "{}" });
      await res.text();
      console.log(`attempt ${i}: status ${res.status}`);
      return res.status;
    } catch (e) {
      console.log(`attempt ${i}: network error, retrying`);
    }
  }
  throw new Error("gave up");
}

await postWithRetry(3);
console.log("HQ consolidated:", (consolidated / 100).toFixed(2));
server.closeAllConnections();
await new Promise((r) => server.close(r));

Cheat sheet · الخلاصة

  • ERP = integrated modules on one data model. Each posting step writes all its rows in one transaction.
  • Webhooks between SaaS tools are at-least-once with no shared transaction: you own dedupe and reconciliation.
  • In Odoo the chain is real foreign keys: sale_order_line, stock_move, account_move_line.
  • One schema means no cross-module reconciliation, one blast radius and one upgrade.
  • Payroll (hr.payslip) is Enterprise only.
  • Buying triggers: Excel breaks, a second branch, valuable stock, an audit. A service company with no stock usually doesn't need an ERP.
  • Segments are inference; mid-market ranges from 500 to 5,000 employees; market sizes differ 3.3x; SAP's share is 6.6% or 23% by denominator.
  • Integrator share is 40–70% from a source with no method. Services were 25–74% of 3-year spend in the model.
  • Two-tier gives up the single transaction, so consolidation needs a key derived from the batch's meaning.
بالعامية
  • الـ ERP = modules متكاملة على data model واحد. كل خطوة post بتكتب كل الـ rows بتاعتها في transaction واحدة.
  • الـ webhooks بين أدوات الـ SaaS at-least-once ومفيش transaction مشتركة: الـ dedupe والـ reconciliation عليك.
  • في Odoo السلسلة foreign keys حقيقية: sale_order_line، stock_move، account_move_line.
  • الـ schema الواحد معناه مفيش reconciliation بين الـ modules، و blast radius واحد، و upgrade واحد.
  • الـ Payroll (hr.payslip) في Enterprise بس.
  • أسباب الشراء: الـ Excel يقع، فرع تاني، مخزون قيمته كبيرة، audit. شركة خدمات من غير مخزون غالبًا مش محتاجة ERP.
  • الشرايح استنتاج؛ الـ mid-market من 500 لـ 5,000 موظف؛ حجم السوق بيختلف 3.3 مرة؛ حصة SAP يا 6.6% يا 23% حسب الـ denominator.
  • نصيب الـ integrator 40–70% من مصدر من غير method. الخدمات كانت 25–74% من التلات سنين في الموديل.
  • الـ Two-tier بيتنازل عن الـ transaction الواحدة، فالـ consolidation محتاج مفتاح مبني من معنى الدفعة.
