Why this matters · ليه ده مهم

English

Almost every line of Odoo code goes through the ORM, and it doesn't think like Prisma or TypeORM. The schema comes from your Python classes and changes when you upgrade, without a migration file. self is a set of records, not one. Fields load lazily but in batches. Filters are Polish-notation lists. Get the mental model right and a report takes one query; get it wrong and it takes a thousand, as Part 6 measures. And one change that looks harmless, renaming a field, deletes a column with its data.

بالعامية

تقريبًا كل سطر كود في Odoo بيعدّي على الـ ORM، وهو مش بيفكر زي Prisma أو TypeORM. الـ schema جاية من الـ Python classes بتاعتك وبتتغيّر لما تعمل upgrade من غير migration file. self مجموعة records مش record واحد. الـ fields بتتحمّل lazy بس في batches. والـ filters لستات بالـ Polish notation. لو الـ mental model صح الـ report بياخد query واحدة، ولو غلط بياخد ألف، زي ما الجزء 6 بيقيس. وفيه تغيير شكله بريء، إنك تعمل rename لـ field، بيمسح عمود بالـ data اللي فيه.

Part 1 — Models and fields 🟡 Intermediateالجزء 1 — الـ models والـ fields

English

A class extending models.Model with a _name becomes a table: dots turn into underscores, so erp_lab.refund is erp_lab_refund. Each stored field becomes a column. Odoo adds id, create_uid, create_date, write_uid and write_date for free, so every table has a basic audit trail. Field objects also carry behaviour: required=True becomes NOT NULL, index=True creates an index, and default is applied by the ORM, not by the column.

Empty values surprise JavaScript developers: an unset Date, Char or Many2one reads as False or an empty recordset, not None. A Float with digits and a Monetary are numeric columns, a plain Float is double precision, and Python sees a float in every case (lesson 10 covers why). Datetime is stored as naive UTC. Html is sanitized by default: in the run below a <script> tag was removed on write.

At -u, Odoo compares the classes with the database and applies the difference. Additive changes are safe and need no migration file. Others aren't. A rename is not a rename: Odoo sees one field disappear and another appear, so it creates a new empty column and, at the end of the upgrade, deletes the old field's ir.model.fields record, which runs ALTER TABLE … DROP COLUMN … CASCADE. The data is gone, the exit code is 0, and the only trace is an INFO line. Older tutorials say the old column stays; on Odoo 20 it doesn't. To rename safely, rename the column in a pre-migrate script.

بالعامية

أي class بتورث models.Model وليها _name بتبقى table: النقط بتبقى underscores، فـ erp_lab.refund تبقى erp_lab_refund. كل field stored بيبقى عمود. وOdoo بيضيف id وcreate_uid وcreate_date وwrite_uid وwrite_date ببلاش، فكل table عندها audit trail بسيط. والـ fields كمان ليها سلوك: required=True بتبقى NOT NULL، وindex=True بتعمل index، وdefault بيطبّقه الـ ORM مش العمود.

القيم الفاضية بتفاجئ مطوري JavaScript: Date أو Char أو Many2one فاضيين بيرجعوا False أو recordset فاضي، مش None. Float بـ digits وMonetary أعمدة numeric، وFloat العادي double precision، وPython بيشوف float في كل الحالات (درس 10 بيشرح ليه). Datetime بتتخزن UTC من غير timezone. وHtml بيتعمله sanitize by default: في التجربة تاج <script> اتشال وقت الكتابة.

في الـ -u، Odoo بيقارن الـ classes بالـ database ويطبّق الفرق. الإضافات آمنة ومش محتاجة migration file. الباقي لأ. الـ rename مش rename: Odoo بيشوف field اختفى وfield ظهر، فبيعمل عمود جديد فاضي، وفي آخر الـ upgrade بيمسح record الـ ir.model.fields بتاع القديم، وده بيشغّل ALTER TABLE … DROP COLUMN … CASCADE. الـ data راحت، والـ exit code 0، والأثر الوحيد سطر INFO. Tutorials قديمة بتقول العمود القديم بيفضل، بس في Odoo 20 مش بيفضل. عشان تعمل rename بأمان غيّر اسم العمود في سكريبت pre-migrate.

المقارنة بـ Prisma (من الـ docs، ومشغّلتوش هنا): بتغيّر الـ schema وبتطلع ملف SQL بتراجعه قبل ما يشتغل، وrename عنده برضه بيتفهم drop وadd بس بتشوفه وتعدّله. في Odoo مفيش خطوة review دي، فإنت اللي لازم تعملها. وعندك درس الـ safe migrations والـ expand-contract.

فين هستخدمه في شغلي؟ في الـ code review لأي PR بتاع Odoo: لو شفت field اسمه اتغيّر في الـ diff، ده مش refactor، ده حذف عمود في production. اطلب pre-migrate ورفع version، واختبر على نسخة من الـ data. ولو عندك API في Node بيقرا من Odoo، متعاملش false كأنها قيمة boolean حقيقية في تاريخ أو نص: اعمل normalize لـ null على الحدود.
What breaks: a green upgrade that lost data Both the rename and the failed NOT NULL exit 0. Don't judge an upgrade by its exit code: search the log for Deleting and odoo.schema, and rehearse on a copy of production.

Part 2 — Relational fields 🟡 Intermediateالجزء 2 — الـ relational fields

English

Many2one is a real column with a foreign key; ondelete becomes the FK action. On ordinary models the default is set null, or restrict when the field is required. One2many has no column: it's the reverse view of a Many2one on the other model, which is why it names the inverse field. Many2many creates a relation table with two foreign keys, both ON DELETE CASCADE, a composite primary key and a reverse index.

Odoo doesn't index a Many2one by itself. In the run below refund_id, the inverse of line_ids, had no index until index=True was added, so at scale every read of line_ids is a sequential scan. Add index=True to inverse fields.

You write x2many fields with commands. Command.create, update, delete, unlink, link, clear and set build the old triples such as (0, 0, vals). Use the names in Python; over RPC you must send the raw triples. The difference to remember: delete removes the row, and unlink only breaks the link. Except that on a One2many whose inverse is required with ondelete='cascade', breaking the link deletes the row too, as measured below.

class Refund(models.Model):
    _name = 'erp_lab.refund'
    _description = 'Refund request'

    # عمود حقيقي عليه foreign key
    partner_id = fields.Many2one('res.partner', required=True, ondelete='restrict')
    # مفيش عمود: ده الاتجاه العكسي
    line_ids = fields.One2many('erp_lab.refund.line', 'refund_id')
    # بيعمل table وسيطة
    tag_ids = fields.Many2many('erp_lab.refund.tag')


class RefundLine(models.Model):
    _name = 'erp_lab.refund.line'
    _description = 'Refund line'

    # ده الـ inverse بتاع line_ids
    refund_id = fields.Many2one('erp_lab.refund', required=True, ondelete='cascade', index=True)
    description = fields.Char()

بالعامية

Many2one عمود حقيقي عليه foreign key، وondelete بيبقى الـ FK action. في الـ models العادية الـ default set null، أو restrict لو الـ field required. One2many ملوش عمود: ده الاتجاه العكسي لـ Many2one في الـ model التانية، وعشان كده بتكتب اسم الـ inverse field. Many2many بتعمل table وسيطة فيها foreign keys الاتنين ON DELETE CASCADE، وprimary key مركب، وindex بالعكس.

Odoo مش بيعمل index للـ Many2one لوحده. في التجربة refund_id، الـ inverse بتاع line_ids، مكانش عليه index لحد ما ضفنا index=True، فعلى حجم كبير كل قراية لـ line_ids بتبقى sequential scan. ضيف index=True على الـ inverse fields (وعندك درس الـ B-tree indexes).

الكتابة على x2many بتبقى بالـ commands. Command.create وupdate وdelete وunlink وlink وclear وset بيبنوا الـ triples القديمة زي (0, 0, vals). استخدم الأسماء في Python، وفي الـ RPC لازم تبعت الـ triples نفسها. الفرق اللي تفتكره: delete بيمسح الصف وunlink بيفك الربط بس. ماعدا على One2many الـ inverse بتاعها required وondelete='cascade': فك الربط بيمسح الصف برضه، زي ما قسنا فوق.

فين هستخدمه في شغلي؟ الـ Node service بتاعك بيبعت order فيها lines لـ Odoo عن طريق JSON-2 (درس 27): الـ payload هيبقى "line_ids": [[0, 0, {...}], [0, 0, {...}]] لأن Command موجودة في Python بس. ولو عايز تستبدل الـ lines كلها في update ابعت [[5, 0, 0], [0, 0, {...}]]. وفي الـ review: أي Many2one بيتعمل عليها One2many على table هتكبر لازم عليها index=True.

Part 3 — Recordsets, self, env 🟡 Intermediateالجزء 3 — الـ recordsets و self و env

English

A recordset is an ordered collection of ids plus an environment. One record is a recordset of length 1, and "no record" is a recordset of length 0, so there's no null to check. self in a model method is a recordset of any size. That's why methods start with for rec in self, and why reading a field on two records raises ValueError: Expected singleton. Use ensure_one() when a method really needs exactly one.

env holds the cursor (env.cr), the user (env.uid, env.user), the context (env.context), the company (env.company) and the superuser flag (env.su). env['model'] gives an empty recordset of that model. The recordset helpers are mapped, filtered, sorted and grouped, and the set operators | (union), & (intersection), - (difference) and + (concatenation, keeps duplicates) are dunder methods, as in lesson 09.

The shift from Node ORMs is that Odoo is lazy and batch-first. browse runs no query. The first field access loads that field for every record in the set, so a loop over one recordset costs a constant number of queries. In TypeORM you say up front which relations you want, and if you forget, the property is undefined. In Odoo you just walk the relation. Writes are also delayed: assignments in a loop are flushed together, so in this run the loop and the batch version both took 3 queries.

class Refund(models.Model):
    _name = 'erp_lab.refund'
    _description = 'Refund request'

    def action_approve_wrong(self):
        # الغلط: بيتعامل مع self كأنها record واحد
        if self.state == 'draft':
            self.state = 'approved'

    def action_approve(self):
        # الصح: self ممكن تبقى أي عدد
        for refund in self:
            if refund.state == 'draft':
                refund.state = 'approved'
        return True

    def action_approve_batch(self):
        # نفس الفكرة بأسلوب الـ recordset
        self.filtered(lambda refund: refund.state == 'draft').write({'state': 'approved'})

Part 4 — Domains and search 🟡 Intermediateالجزء 4 — الـ domains والـ search

English

A domain is a list of conditions (field, operator, value) in Polish (prefix) notation. Adjacent conditions are ANDed implicitly. '|' and '&' each take the next two expressions, and '!' takes the next one. So three alternatives need two '|'. One '|' in front of three conditions means (A or B) and C.

The left side can be a dotted path such as partner_id.country_id.code. For a Many2one path Odoo generates a LEFT JOIN; for a One2many path, an EXISTS subquery, the same SQL as the explicit any operator. child_of and parent_of walk a hierarchy: without a stored parent_path that's one query per level, as the log below shows. Odoo also adds active IS TRUE automatically on models with an active field; active_test=False in the context turns that off.

For composing domains in code, use the Domain class from odoo.fields: &, | and ~ build the tree, so you never count prefix operators by hand. search returns a recordset and takes offset, limit and order; search_count counts; search_read returns dicts, which is what APIs want.

الـ domain لستة شروط (field, operator, value) بالـ Polish (prefix) notation. الشروط اللي جنب بعض بينهم AND ضمني. '|' و'&' كل واحد بياخد التعبيرين اللي بعده، و'!' بياخد واحد. فتلات اختيارات محتاجين '|' مرتين. و'|' واحد قدام 3 شروط معناه (A or B) and C.

Part 5 — Aggregates 🟡 Intermediateالجزء 5 — الـ aggregates

English

Grouping runs in SQL, and Odoo 20 has three APIs for it, all with the signature (domain, groupby, aggregates, having, offset, limit, order). _read_group is the internal one, for server-side code: it returns tuples, with relational groups as recordsets. read_group is public and returns the same tuples, with records replaced by ids. formatted_read_group, defined in the web addon, returns the dicts the web client uses, including __extra_domain.

Aggregates are strings like 'balance:sum', plus '__count'. Besides PostgreSQL aggregates there are count_distinct and recordset. Date groups take a granularity, such as 'date:month'. having is a domain over the aggregates.

This is a breaking change for code ported from version 17 or earlier: the old read_group(domain, fields, groupby, lazy=…) returned dicts. Called the old way it now fails, and if only the result handling is old it fails with a TypeError on the first group['partner_id'].

فين هستخدمه في شغلي؟ Dashboard في Next.js عايز إجمالي المستحق لكل عميل. بدل ما تسحب كل الـ lines لـ Node وتجمّعهم، نادي read_group عن طريق JSON-2 وخد صف لكل عميل. ولو بتعمل port لـ module من Odoo 17، اعمل grep على read_group( كأول خطوة (درس 36 بيكمّل الموضوع).
Interview question "A module ported from Odoo 17 crashes with tuple indices must be integers or slices, not str on a report. What changed, and what's the fix?" → read_group now returns tuples and has a new signature. Inside the server, move to _read_group and unpack the tuples; if the code really needs dicts, use formatted_read_group.

Part 6 — Bad query, better query 🟡 Intermediateالجزء 6 — query وحشة وquery أحسن

English

Revenue per customer, three ways. The first runs search inside a loop, so one query per partner plus the reads. The second runs one search and groups in Python with grouped: few queries, but every row travels to Python. The third is one _read_group: the database does the work and returns one row per group.

The tool is env.cr.sql_log_count, a counter on the cursor that is always on. Call env.flush_all() and env.invalidate_all() first so a warm cache doesn't flatter the result. The demo data is small, so the run also adds 10,000 refunds across 500 customers inside a transaction that is rolled back. Query counts are stable; timings are from a loaded Windows machine, so read them as ratios.

All three return the same totals; the script asserts it. The shell runs as superuser, so company rules don't filter anything, which is why the domain names the company explicitly.

import time

Move = env['account.move']
Partner = env['res.partner']
company = env.ref('base.main_company')
domain = [('move_type', '=', 'out_invoice'), ('state', '=', 'posted'), ('company_id', '=', company.id)]


def measure(label, fn):
    # نفضّي الـ cache عشان القياس يبقى عادل
    env.flush_all()
    env.invalidate_all()
    c0 = env.cr.sql_log_count
    t0 = time.perf_counter()
    result = fn()
    ms = (time.perf_counter() - t0) * 1000
    print(f'{label:30} queries={env.cr.sql_log_count - c0:<6} time≈{ms:8.1f} ms groups={len(result)} total={round(sum(result.values()), 2)}')
    return result


def loop_demo():
    # الغلط: search لكل عميل
    out = {}
    for partner in Partner.search([]):
        moves = Move.search(domain + [('partner_id', '=', partner.id)])
        if moves:
            out[partner.id] = sum(moves.mapped('amount_untaxed_signed'))
    return out


def grouped_demo():
    # أحسن: search واحدة والتجميع في Python
    out = {}
    for partner, moves in Move.search(domain).grouped('partner_id').items():
        out[partner.id] = sum(moves.mapped('amount_untaxed_signed'))
    return out


def read_group_demo():
    # الأحسن: الـ database هي اللي بتجمّع
    return {partner.id: total for partner, total in Move._read_group(domain, ['partner_id'], ['amount_untaxed_signed:sum'])}


a = measure('demo: search in a loop', loop_demo)
b = measure('demo: one search + grouped', grouped_demo)
c = measure('demo: _read_group', read_group_demo)
print('same answer:', a.keys() == b.keys() == c.keys(), all(abs(a[k] - c[k]) < 0.01 for k in a))

بالعامية

الإيراد لكل عميل بتلات طرق. الأولى search جوه loop، يعني query لكل عميل غير القراية. التانية search واحدة والتجميع في Python بـ grouped: queries قليلة بس كل الصفوف بتروح لـ Python. التالتة _read_group واحدة: الـ database هي اللي بتشتغل وبترجع صف لكل group.

الأداة env.cr.sql_log_count، counter على الـ cursor شغال دايمًا. نادي env.flush_all() وenv.invalidate_all() الأول عشان الـ cache الدافي ميجمّلش النتيجة. الـ demo data صغيرة، فالتجربة كمان ضافت 10,000 refund على 500 عميل جوه transaction اترجّعت في الآخر. عدد الـ queries ثابت، والأوقات من جهاز Windows عليه ضغط، فاقرأها كنسب.

التلاتة بيرجعوا نفس الإجماليات والسكريبت بيتأكد. والـ shell شغال كـ superuser فقواعد الشركات مش بتفلتر حاجة، وعشان كده الـ domain بيحدد الشركة صراحةً.

فين هستخدمه في شغلي؟ Report بياخد 40 ثانية على production وعلى staging بياخد ثانية. قبل ما تزوّد workers، عدّ الـ queries بـ sql_log_count حوالين الـ function. لو الرقم بيكبر مع عدد الصفوف يبقى عندك N+1، ونفس فكرة الـ N+1 في Prisma بالظبط. الحل _read_group لو عايز أرقام، أو search واحدة بره الـ loop لو عايز records. وتقدر تثبّت ده بـ assertQueryCount (في درس 16).
Trade-off: grouped against _read_group _read_group only sees stored fields and SQL aggregates. If the number depends on a non-stored compute or on Python logic, use one search plus grouped: still a constant number of queries, at the cost of loading the rows. For very large sets, process in batches.
_read_group بتشوف الـ stored fields والـ SQL aggregates بس. لو الرقم معتمد على compute مش stored أو logic في Python، استخدم search واحدة مع grouped: برضه عدد ثابت من الـ queries، بس بتمن تحميل الصفوف. وللمجموعات الكبيرة جدًا اشتغل بـ batches.

Common mistakes · غلطات شائعة

❌ Renaming a field in the class

✅ Rename the column first

بالعامية

❌ Odoo شايف field اتشال وfield جديد، فبيعمل DROP COLUMN والـ data بتروح بـ exit 0. ✅ غيّر اسم العمود في pre-migrate وارفع الـ version في الـ manifest عشان السكريبت يشتغل.

❌ Treating self as one record

    # بيقع لو اتبعت أكتر من record
    if self.state == 'draft':
        self.state = 'approved'
✅ Loop, or filter and write

    # بيشتغل مع أي عدد
    self.filtered(lambda r: r.state == 'draft').write({'state': 'approved'})

❌ بيعدّي مع record واحد ويرمي Expected singleton أول ما حد يختار كذا صف. ✅ loop أو filtered مع write، والاتنين بيشتغلوا مع أي عدد.

❌ One '|' for three conditions

['|', A, B, C]
✅ One fewer than the conditions, or in

['|', '|', A, B, C]

❌ مفيش error، بس النتيجة 0 لأن الشرط التالت دخل بـ AND. ✅ لـ N اختيار محتاج N−1 من '|'، أو in لو نفس الـ field، أو الـ Domain class.

Cheat sheet · الخلاصة

  • _name → table, field → column, plus 5 free audit columns. default lives in the ORM.
  • Empty reads as False or an empty recordset, not None.
  • Renaming a field drops the old column with its data: use pre-migrate and bump the version.
  • A new required on existing rows logs ERROR, exits 0 and stays nullable.
  • Many2one = column + FK, not indexed by default. One2many = no column. Many2many = relation table.
  • Command.create/update/delete/unlink/link/clear/set; raw triples over RPC.
  • self is a recordset of any size: for rec in self, or ensure_one().
  • env = cursor, user, context, company, superuser flag.
  • Lazy and batch-first: one recordset costs a constant number of queries.
  • Domains are prefix notation: N alternatives need N−1 '|', or use Domain.
  • Tuples from _read_group and read_group; dicts only from formatted_read_group.
  • Count with env.cr.sql_log_count; see SQL with --log-sql.
بالعامية
  • _name بتبقى table، والـ field عمود، ومعاهم 5 أعمدة audit ببلاش. وdefault في الـ ORM مش في العمود.
  • الفاضي بيرجع False أو recordset فاضي، مش None.
  • الـ rename بيمسح العمود القديم بالـ data: استخدم pre-migrate وارفع الـ version.
  • required جديد على صفوف موجودة: ERROR في الـ log، وexit 0، والعمود بيفضل nullable.
  • Many2one عمود وFK ومن غير index by default. One2many ملوش عمود. Many2many table وسيطة.
  • Command.create/update/delete/unlink/link/clear/set، والـ triples نفسها في الـ RPC.
