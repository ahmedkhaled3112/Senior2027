Why this matters · ليه ده مهم

English

Saudi e-invoicing adds something Egypt's system does not have: every invoice carries the hash of the invoice before it, so your invoices form a chain, per device. That turns an ordinary concurrency bug or a careless retry into a compliance problem. Odoo's handling of a timeout here is some of the best failure-handling code in the whole product, and it is worth reading closely.

All of this runs against real Odoo 20 code and a local stand-in. Nothing in this lesson contacts ZATCA, its sandbox, or Fatoora. Keys and certificates are generated at runtime and thrown away.

بالعامية

الـ e-invoicing في السعودية بيزوّد حاجة مش موجودة في مصر: كل فاتورة شايلة الـ hash بتاع الفاتورة اللي قبلها، فالفواتير بتعمل سلسلة لكل جهاز. وده بيخلي أي concurrency bug عادي أو retry مش محسوب مشكلة compliance. والطريقة اللي Odoo بيتعامل بيها مع الـ timeout هنا من أحسن كود failure handling في المنتج كله، ويستاهل تقراه بتركيز.

كل ده شغال على كود Odoo 20 الحقيقي وعلى stand-in محلي. مفيش حاجة في الدرس بتكلّم ZATCA ولا الـ sandbox بتاعها ولا Fatoora. والمفاتيح والشهادات بتتولد وقت التشغيل وبترمى بعدها.

Part 1 — Clearance and reporting 🔴 Advancedالجزء 1 — الـ clearance والـ reporting

English

There are two flows. A standard tax invoice (B2B or B2G) goes through clearance: ZATCA validates and stamps it, and only the cleared version may reach the buyer. A simplified tax invoice (B2C) goes through reporting: you give it to the customer immediately and report it within 24 hours. Odoo picks the type from the customer: a company gets tax, an individual gets simplified.

The architectural consequence is the part to remember. Clearance puts the authority in your synchronous path. If ZATCA is slow, your invoice is slow; if it is down, you cannot issue a B2B invoice at all. Odoo's call uses a 30 second timeout. Reporting is the opposite: the sale never waits, but you now own a queue with a legal deadline, and something has to watch it.

Odoo's API paths live in account_journal.py. Notice that compliance and compliance/invoices are separate endpoints used only during onboarding (Part 7).

 CLEARANCE (standard, B2B)              REPORTING (simplified, B2C)

 ERP --invoice--> ZATCA                 ERP --invoice--> Customer   (now)
 ERP <--stamped-- ZATCA                  |
  |                                      +--report--> ZATCA   (within 24 h)
  +--stamped invoice--> Customer

 ZATCA down: cannot issue               ZATCA down: issue, queue the report
الرسمة بتقارن المسارين. على الشمال الـ clearance: الـ ERP بيبعت لـ ZATCA، ياخد الفاتورة مختومة، وبعدين بس يديها للعميل، فلو ZATCA واقعة مينفعش تطلّع الفاتورة. على اليمين الـ reporting: العميل بياخد الفاتورة دلوقتي، والبلاغ بيروح خلال 24 ساعة، فلو ZATCA واقعة بتطلّع الفاتورة وتحط البلاغ في طابور.

// فاتورة B2B لازم تتعمل لها clearance قبل ما تتسلم، و B2C تتسلم وبعدين تتبلغ
type Standard = { kind: "standard"; id: string };
type Simplified = { kind: "simplified"; id: string; issuedAt: number };
type Invoice = Standard | Simplified;

type Result =
  | { status: "issued"; id: string; note: string }
  | { status: "blocked"; id: string; note: string }
  | { status: "issued-pending-report"; id: string; reportBy: number };

const DAY = 86_400_000;

export function issue(invoice: Invoice, authorityUp: boolean): Result {
  switch (invoice.kind) {
    case "standard":
      // الـ authority في الـ synchronous path: مفيش رد يعني مفيش فاتورة
      return authorityUp
        ? { status: "issued", id: invoice.id, note: "cleared, customer gets the stamped XML" }
        : { status: "blocked", id: invoice.id, note: "cannot be issued until cleared" };
    case "simplified":
      // العميل بياخد الفاتورة دلوقتي، والبلاغ ليه مهلة 24 ساعة
      return authorityUp
        ? { status: "issued", id: invoice.id, note: "issued, reported immediately" }
        : { status: "issued-pending-report", id: invoice.id, reportBy: invoice.issuedAt + DAY };
  }
}

export function overdue(pending: { id: string; reportBy: number }[], now: number) {
  return pending.filter((p) => p.reportBy < now).map((p) => p.id);
}

بالعامية

فيه مسارين. الفاتورة الضريبية standard (B2B أو B2G) بتعدي على clearance: ZATCA بتراجعها وتختمها، والنسخة المختومة بس هي اللي توصل للمشتري. والفاتورة المبسطة simplified (B2C) بتعدي على reporting: بتديها للعميل على طول وتبلّغ عنها خلال 24 ساعة. و Odoo بيحدد النوع من العميل: الشركة tax، والفرد simplified.

النتيجة المعمارية هي أهم حاجة تفتكرها. الـ clearance بيحط الـ authority في الـ synchronous path بتاعك. لو ZATCA بطيئة فاتورتك بطيئة، ولو واقعة مينفعش تطلّع فاتورة B2B خالص. والـ call في Odoo بـ timeout قدره 30 ثانية. الـ reporting عكس كده: البيع عمره ما بيستنى، بس بقى عندك queue ليه deadline قانوني، ولازم حاجة تراقبه.

المسارات موجودة في account_journal.py. لاحظ إن compliance وcompliance/invoices endpoints منفصلة بتتستخدم في الـ onboarding بس (الجزء 7).

فين هستخدمه في شغلي؟ لو بتبني checkout لعميل B2B في السعودية، متخليش زرار "تأكيد الطلب" يستنى ZATCA 30 ثانية جوه الـ HTTP request. خد الطلب، حط الفاتورة في queue بحالة "في انتظار الختم"، وابعت الفاتورة للعميل لما تتختم. وللـ POS اعمل alert لو أي بلاغ قرّب من الـ 24 ساعة.

الغلطة الشائعة: تعامل الاتنين نفس المعاملة. لو بعت فاتورة B2B للعميل قبل الـ clearance، بعت مستند لسه مش صالح.

Interview question "A government API sits in your invoice flow and has no SLA you control. How do you design around it?" → Separate taking the order from issuing the document. Persist first, send through a queue, show a pending state, set a timeout and a budget, and alert on the age of the oldest pending document, since that is what maps to the legal deadline.
"API حكومي في مسار الفاتورة ومفيش SLA تتحكم فيه. هتصمم حواليه إزاي؟" ← افصل استلام الطلب عن إصدار المستند. احفظ الأول، ابعت عن طريق queue، اعرض حالة pending، حط timeout وbudget، واعمل alert على عمر أقدم مستند pending، لأن ده اللي بيقابل الـ deadline القانوني.

Part 2 — Waves 🔴 Advancedالجزء 2 — الموجات

English

Phase 1 (generation) has applied since 4 December 2021. Phase 2 (integration) started on 1 January 2023 and rolls out in waves by revenue. The threshold keeps falling, so more small businesses are pulled in with each wave.

The latest one, as of November 2026, is Wave 25: ZATCA's announcement of 24 July 2026 covers taxpayers whose VAT-subject revenues exceeded SAR 187,500 in any of 2022, 2023, 2024 or 2025, integrating by 1 February 2027. Vendor pages that call Wave 24 the last one are out of date. ZATCA says it notifies each group at least six months ahead, so a public list is not the only signal.

The rule says "exceeded", so exactly SAR 187,500 is not in. Thresholds are data with a date and a source, never if statements. The table below marks which rows are primary and which came from secondary sources.

// الموجات بتتحدث بقرار رسمي، فبنحطها data بتاريخ ومصدر مش if في الكود
type Wave = { wave: number; thresholdSar: number; years: number[]; deadline: string; source: string };

export const WAVES: Wave[] = [
  { wave: 22, thresholdSar: 1_000_000, years: [2022, 2023, 2024], deadline: "2025-12-31", source: "secondary: Cygnet, read 2026-11-11" },
  { wave: 23, thresholdSar: 750_000, years: [2022, 2023, 2024], deadline: "2026-03-31", source: "secondary: EY alert, read 2026-11-11" },
  { wave: 24, thresholdSar: 375_000, years: [2022, 2023, 2024], deadline: "2026-06-30", source: "secondary: EY alert, read 2026-11-11" },
  { wave: 25, thresholdSar: 187_500, years: [2022, 2023, 2024, 2025], deadline: "2027-02-01", source: "ZATCA news, 2026-07-24" },
];

export function firstWave(revenueByYear: Record<number, number>): Wave | null {
  // الشرط "تعدّى" يعني أكبر بس، مش أكبر أو يساوي
  for (const wave of [...WAVES].sort((a, b) => b.thresholdSar - a.thresholdSar)) {
    if (wave.years.some((year) => (revenueByYear[year] ?? 0) > wave.thresholdSar)) return wave;
  }
  return null;
}

export function status(revenueByYear: Record<number, number>, today: string) {
  const wave = firstWave(revenueByYear);
  if (!wave) return "not in any wave listed here: watch for a new announcement";
  const days = Math.round((Date.parse(wave.deadline) - Date.parse(today)) / 86_400_000);
  return `wave ${wave.wave}, deadline ${wave.deadline} (${days >= 0 ? `${days} days left` : `${-days} days overdue`})`;
}

Part 3 — UBL 2.1 XML 🔴 Advancedالجزء 3 — الـ UBL 2.1 XML

English

Where Egypt uses JSON, ZATCA uses UBL 2.1 XML. The XML below came from a real invoice posted in the lab's Saudi company through _l10n_sa_generate_zatca_template, which uses account.edi.xml.ubl_21.zatca.

The fields worth knowing: cbc:ProfileID is reporting:1.0. cbc:InvoiceTypeCode is 388 for an invoice, 381 for a credit note, 383 for a debit note and 386 for a prepayment. Its name attribute is a 7-character code: the first two digits are 01 for standard or 02 for simplified, followed by five flags for third party, nominal, export, summary and self-billed.

AdditionalDocumentReference holds the chain: ICV (Invoice Counter Value) and PIH (Previous Invoice Hash). ICV shows 0 here only because this XML was generated before submission. There are two cac:TaxTotal elements: one with the per-category breakdown and one with only the amount.

An XPath checklist catches structural mistakes early. It does not replace ZATCA's validator, which runs business rules such as BR-KSA-39 and BR-KSA-40 on the VAT number's first and last digit.

type Check = { name: string; expr: string; test: (value: string) => boolean };

// قايمة فحص بسيطة للهيكل، مش بديل عن الـ validator بتاع ZATCA
export const checks: Check[] = [
  { name: "ProfileID", expr: "string(/inv:Invoice/cbc:ProfileID)", test: (v) => v === "reporting:1.0" },
  { name: "UUID", expr: "string(/inv:Invoice/cbc:UUID)", test: (v) => /^[0-9a-f-]{36}$/.test(v) },
  { name: "InvoiceTypeCode", expr: "string(/inv:Invoice/cbc:InvoiceTypeCode)", test: (v) => ["388", "381", "383", "386"].includes(v) },
  { name: "InvoiceTypeCode@name", expr: "string(/inv:Invoice/cbc:InvoiceTypeCode/@name)", test: (v) => /^0[12][01]{5}$/.test(v) },
  { name: "ICV", expr: "string(//cac:AdditionalDocumentReference[cbc:ID='ICV']/cbc:UUID)", test: (v) => /^\d+$/.test(v) },
  { name: "PIH", expr: "string(//cac:AdditionalDocumentReference[cbc:ID='PIH']/cac:Attachment/cbc:EmbeddedDocumentBinaryObject)", test: (v) => v.length > 40 },
  { name: "Seller VAT", expr: "string(//cac:AccountingSupplierParty//cac:PartyTaxScheme/cbc:CompanyID)", test: (v) => /^3\d{13}3$/.test(v) },
  { name: "TaxTotal[1]", expr: "string((//cac:TaxTotal)[1]/cbc:TaxAmount)", test: (v) => Number(v) >= 0 && v !== "" },
  { name: "TaxTotal[2]", expr: "string((/inv:Invoice/cac:TaxTotal)[2]/cbc:TaxAmount)", test: (v) => v !== "" },
  { name: "PayableAmount", expr: "string(//cac:LegalMonetaryTotal/cbc:PayableAmount)", test: (v) => Number(v) > 0 },
  { name: "Line count", expr: "string(count(/inv:Invoice/cac:InvoiceLine))", test: (v) => Number(v) >= 1 },
];

export function runChecks(xml: string) {
  const doc = new DOMParser().parseFromString(xml, "text/xml") as unknown as Node;
  return checks.map(({ name, expr, test }) => {
    const value = select(expr, doc, true) as unknown as string;
    return { name, value: String(value), ok: test(String(value)) };
  });
}

Part 4 — The hash chain 🔴 Advancedالجزء 4 — الـ hash chain

English

Every invoice from a device has a counter (ICV) and the hash of the previous invoice (PIH). It is the same idea as the tamper-evident chain in lesson 06: change one old invoice and every later hash stops matching.

The hash has a precise recipe in _l10n_sa_generate_invoice_xml_hash. Apply pre-hash_invoice.xsl, which removes UBLExtensions, the QR reference and cac:Signature. Canonicalize with inclusive C14N. Take SHA-256. The port below reproduces Odoo's hash on four different files, and the details are where people lose days:

  • Whitespace counts. The same invoice pretty-printed produced a different hash in the lab. Removing a node must leave the whitespace around it.
  • Two encodings exist. Odoo's DigestValue is base64 of the raw 32 bytes. Its PIH is base64 of the 64-character hex string. They are not interchangeable.
  • The first invoice has a defined PIH: base64 of the hex SHA-256 of the string "0".

Why order matters. Two writers that read the same last hash produce two invoices claiming the same parent, and the chain forks. Odoo prevents this by locking: lock_for_update fails fast with LockError, shown to the user as "This document is being processed already."

export function stripForHash(xml: string): Node {
  const doc = new DOMParser().parseFromString(xml, "text/xml") as unknown as Document;
  const select = (expr: string) => xpath.select(expr, doc as unknown as Node) as Element[];
  const targets = [
    ...select("//*[local-name()='Invoice']//*[local-name()='UBLExtensions']"),
    ...select("//*[local-name()='AdditionalDocumentReference']").filter((node) => {
      const id = Array.from(node.childNodes).find((c) => (c as Element).localName === "ID" && (c as Element).namespaceURI === CBC);
      return id?.textContent?.trim() === "QR";
    }),
    ...select("//*[local-name()='Invoice']//*[local-name()='Signature']"),
  ];

  for (const node of targets) node.parentNode?.removeChild(node);
  return doc.documentElement;
}

Part 5 — The unknown state 🔴 Advancedالجزء 5 — حالة الـ unknown

English

Read _l10n_sa_post_zatca_edi and _l10n_sa_handle_submission_error. On a timeout the document goes to unknown, the exact signed XML is saved as an attachment, and the journal's latest hash is committed. The next attempt resends those same bytes with no new ICV. The Odoo comment states why: for ZATCA, one chain index must correspond to one invoice.

There are three failure outcomes, and each treats the chain differently (see the table). A local error never reached ZATCA, so the chain does not move. A rejection did reach it, so the hash still advances. A timeout may or may not have reached it, so Odoo keeps everything frozen until it knows.

On the retry, a 409 counts as success ("already reported"), because it proves the first attempt arrived. And _l10n_sa_handle_submission_success skips updating the journal's hash when retrying from unknown, because that hash was committed at the time of the timeout.

One detail the lab exposed: ICVs can be burned. A rejected invoice used ICV 7, a local error used 8 without ever sending, and the retry got 9. The sequence is no_gap, but a gap still appeared in what the authority sees.

export class Device {
  readonly docs = new Map<string, Doc>();
  icv = 0;
  lastHash = FIRST_PIH;
  private tail: Promise<unknown> = Promise.resolve();
  private readonly baseUrl: string;
  private readonly authHeader: string;
  private readonly onRejectedHash: (hash: string) => void;

  constructor(baseUrl: string, authHeader: string, onRejectedHash: (hash: string) => void) {
    this.baseUrl = baseUrl;
    this.authHeader = authHeader;
    this.onRejectedHash = onRejectedHash;
  }

  add(id: string, kind: Doc["kind"]) {
    if (!this.docs.has(id)) this.docs.set(id, { id, kind, uuid: randomUUID(), state: "to_send", icv: null, bytes: null, pih: null, sends: 0 });
    return this.docs.get(id)!;
  }

  private async transmit(doc: Doc): Promise<Outcome> {
    doc.sends++;
    const path = doc.kind === "standard" ? "/invoices/clearance/single" : "/invoices/reporting/single";
    try {
      const response = await fetch(this.baseUrl + path, {
        method: "POST",
        headers: { "content-type": "application/json", authorization: this.authHeader },
        body: JSON.stringify({ uuid: doc.uuid, icv: doc.icv, pih: doc.pih, invoice: doc.bytes }),
        signal: AbortSignal.timeout(150),
      });
      const body = (await response.json()) as { validationResults?: { errorMessages: { code: string }[] } };
      if (response.ok) return { kind: "ok" };
      if (response.status === 409) return { kind: "already" };
      if (response.status === 400) return { kind: "rejected", code: body.validationResults?.errorMessages[0]?.code ?? "unknown" };
      // أي 401 أو 5xx: الطلب ملوش نتيجة نهائية، فنحتفظ بنفس الـ ICV
      return { kind: "excepted", why: `HTTP ${response.status}` };
    } catch (error) {
      return { kind: "excepted", why: (error as Error).name };
    }
  }

  // نفس ترتيب ⁦_l10n_sa_post_zatca_edi⁩: لو unknown نبعت نفس الـ bytes، غير كده ICV جديد
  private async post(id: string, localError?: Error) {
    const doc = this.docs.get(id)!;
    if (doc.state === "accepted") return doc;
    if (doc.state !== "unknown") {
      // مفيش فاتورة جديدة تتبني فوق واحدة نتيجتها لسه مش معروفة
      const blocked = [...this.docs.values()].find((d) => d.state === "unknown");
      if (blocked) throw new Error(`chain blocked: ${blocked.id} (ICV ${blocked.icv}) is still unknown`);
      doc.icv = ++this.icv;
      doc.pih = this.lastHash;
      if (localError) {
        doc.state = "to_send";
        doc.icv = null;
        doc.pih = null;
        return doc;
      }
      doc.bytes = `<Invoice id="${doc.id}" icv="${doc.icv}" pih="${doc.pih}"/>`;
    }

    const wasUnknown = doc.state === "unknown";
    const outcome = await this.transmit(doc);
    const hash = hashOf(doc.bytes!);
    if (outcome.kind === "ok" || outcome.kind === "already") {
      doc.state = "accepted";
      if (!wasUnknown) this.lastHash = hash;
    } else if (outcome.kind === "rejected") {
      doc.state = "rejected";
      doc.icv = null;
      this.lastHash = hash;
      this.onRejectedHash(hash);
    } else {
      doc.state = "unknown";
      if (!wasUnknown) this.lastHash = hash;
    }
    return doc;
  }

  // طابور لكل جهاز: طلب واحد بس في المرة، زي الـ lock في Odoo
  submit(id: string, localError?: Error): Promise<Doc> {
    const run = this.tail.then(() => this.post(id, localError));
    this.tail = run.catch(() => undefined);
    return run;
  }

  // الغلط: من غير طابور، طلبين بيقروا نفس lastHash في نفس الوقت
  submitUnsafe(id: string): Promise<Doc> {
    return this.post(id);
  }
}

export async function startZatcaStandIn(options: { productionDays?: number } = {}) {
  const ca = await crypto.subtle.generateKey(EC, false, ["sign", "verify"]);
  const accepted: Accepted[] = [];
  const faults: Fault[] = [];
  const otps = new Set<string>();
  const credentials = new Map<string, Credential>();
  const complianceChecks = new Map<string, number>();
  const hanging = new Set<ServerResponse>();
  const log: string[] = [];
  let productionDays = options.productionDays ?? 365;
  let requestId = 1000;
  let lastHash: string | null = null;

  const send = (res: ServerResponse, status: number, body: unknown) => {
    res.writeHead(status, { "content-type": "application/json", "x-stand-in": "not-the-real-ZATCA" });
    res.end(JSON.stringify(body));
  };
  const issue = async (csrB64: string, days: number, kind: Credential["kind"]) => {
    const csr = new x509.Pkcs10CertificateRequest(Buffer.from(csrB64, "base64").toString("utf8"));
    const notAfter = Date.now() + days * 86_400_000;
    const certificate = await x509.X509CertificateGenerator.create({
      serialNumber: String(++requestId), subject: csr.subject, issuer: "CN=STAND-IN CA, not ZATCA",
      notBefore: new Date(Date.now() - 30 * 86_400_000), notAfter: new Date(notAfter),
      signingAlgorithm: EC, publicKey: csr.publicKey, signingKey: ca.privateKey,
    });
    const token = Buffer.from(Buffer.from(certificate.rawData).toString("base64")).toString("base64");
    const secret = `fake-secret-${requestId}`;
    credentials.set(token, { secret, kind, notAfter });
    return { requestID: requestId, dispositionMessage: "ISSUED", binarySecurityToken: token, secret };
  };
  const auth = (header: string | undefined) => {
    if (!header?.startsWith("Basic ")) return null;
    const [token, secret] = Buffer.from(header.slice(6), "base64").toString().split(":");
    const found = credentials.get(token!);
    return found && found.secret === secret ? { token: token!, ...found } : null;
  };

  const server = createServer(async (req, res) => {
    const chunks: Buffer[] = [];
    for await (const chunk of req) chunks.push(chunk as Buffer);
    const body = chunks.length ? JSON.parse(Buffer.concat(chunks).toString()) : {};
    const path = req.url!;
    log.push(`${req.method} ${path}`);

    if (path === "/compliance" && req.method === "POST") {
      const otp = String(req.headers.otp ?? "");
      if (!otps.delete(otp)) return send(res, 400, { errors: [{ code: "Invalid-OTP", message: "OTP is invalid or already used" }] });
      return send(res, 200, await issue(body.csr, 365, "compliance"));
    }
    if (path === "/compliance/invoices" && req.method === "POST") {
      const who = auth(req.headers.authorization);
      if (who?.kind !== "compliance") return send(res, 401, { error: "compliance credential required" });
      complianceChecks.set(who.token, (complianceChecks.get(who.token) ?? 0) + 1);
      return send(res, 200, { validationResults: { status: "PASS", warningMessages: [], errorMessages: [] } });
    }
    if (path === "/production/csids" && req.method === "POST") {
      const who = auth(req.headers.authorization);
      if (who?.kind !== "compliance") return send(res, 401, { error: "compliance credential required" });
      if ((complianceChecks.get(who.token) ?? 0) < 6) return send(res, 400, { errors: [{ code: "Checks-Incomplete", message: "6 compliance samples are required" }] });
      return send(res, 200, await issue(body.csr, productionDays, "production"));
    }
    if (path === "/production/csids" && req.method === "PATCH") {
      const otp = String(req.headers.otp ?? "");
      if (!otps.delete(otp)) return send(res, 400, { errors: [{ code: "Invalid-OTP", message: "OTP is invalid or already used" }] });
      return send(res, 200, await issue(body.csr, productionDays, "production"));
    }

    const mode = path === "/invoices/clearance/single" ? "clearance" : path === "/invoices/reporting/single" ? "reporting" : null;
    if (mode && req.method === "POST") {
      const who = auth(req.headers.authorization);
      if (who?.kind !== "production") return send(res, 401, { error: "production credential required" });
      if (who.notAfter < Date.now()) return send(res, 401, { error: "certificate expired" });
      const fault = faults.shift();
      if (fault === "down") { res.destroy(); return; }
      if (fault === "timeout-before-accept") { hanging.add(res); return; }
      if (fault === "reject") return send(res, 400, { validationResults: { status: "ERROR", warningMessages: [], errorMessages: [{ code: "BR-KSA-37", message: "stand-in rejection" }] } });

      const { uuid, icv, pih, invoice } = body as { uuid: string; icv: number; pih: string; invoice: string };
      const hash = createHash("sha256").update(invoice).digest("hex");
      const already = accepted.find((a) => a.uuid === uuid);
      if (already) {
        if (already.hash !== hash) return send(res, 400, { validationResults: { status: "ERROR", warningMessages: [], errorMessages: [{ code: "duplicate-uuid", message: "same UUID, different bytes" }] } });
        return send(res, 409, { validationResults: { status: "ERROR", warningMessages: [], errorMessages: [{ code: "already-submitted", message: "already received" }] } });
      }
      // الـ stand-in أشد من اللازم عن قصد: أي سلسلة مكسورة بترفض عشان الاختبار يفشل بصوت عالي
      if (lastHash !== null && pih !== lastHash) return send(res, 400, { validationResults: { status: "ERROR", warningMessages: [], errorMessages: [{ code: "chain-broken", message: `PIH does not match the previous invoice (ICV ${icv})` }] } });
      accepted.push({ uuid, icv, pih, hash, mode });
      lastHash = hash;
      if (fault === "timeout-after-accept") { hanging.add(res); return; }
      return send(res, 200, mode === "clearance" ? { clearanceStatus: "CLEARED", clearedInvoice: invoice } : { reportingStatus: "REPORTED" });
    }
    return send(res, 404, { error: "not found in stand-in" });
  });

  await new Promise<void>((resolve) => server.listen(0, "127.0.0.1", resolve));
  const { port } = server.address() as AddressInfo;
  return {
    url: `http://127.0.0.1:${port}`,
    accepted, log,
    issueOtp: (otp: string) => otps.add(otp),
    injectFault: (fault: Fault) => faults.push(fault),
    setProductionDays: (days: number) => { productionDays = days; },
    // الـ rejected بيدخل السلسلة زي ما Odoo بيعمل، فالـ hash بيتحدث من بره
    noteRejectedHash: (hash: string) => { lastHash = hash; },
    async stop() {
      for (const res of hanging) res.destroy();
      server.closeAllConnections();
      await new Promise<void>((resolve) => server.close(() => resolve()));
    },
  };
}

Part 6 — QR and signature 🔴 Advancedالجزء 6 — الـ QR والتوقيع

English

The Phase 2 QR is a Base64 string of TLV records: one byte tag, one byte length, then the value. There are nine fields: seller, VAT number, timestamp, total, VAT, invoice hash, signature, public key, and the signature of the certificate. Tags 1 to 7 are text, 8 and 9 are raw bytes.

The length is one byte, so a field holds at most 255 bytes, not 255 characters. Arabic text is usually 2 bytes per letter. In Odoo a longer field raises OverflowError.

Who builds the QR depends on the flow. For a simplified invoice your system builds it, since the customer gets the invoice before ZATCA sees it. For a standard invoice Odoo reads the QR out of the cleared XML that ZATCA returned.

The signature is ECDSA with SHA-256, using the device's private key, generated in the lab only. The decoder below read Odoo's QR from a real invoice, and the TypeScript encoder rebuilt it byte for byte from the XML and certificate.

export type Tlv = { tag: number; value: Buffer };

// طول الحقل byte واحد، يعني الحد 255 byte مش 255 حرف
export function encodeTlv(fields: Tlv[]): Buffer {
  return Buffer.concat(fields.map(({ tag, value }) => {
    if (value.length > 255) throw new RangeError(`tag ${tag}: ${value.length} bytes does not fit in one length byte`);
    return Buffer.concat([Buffer.from([tag, value.length]), value]);
  }));
}

export function decodeTlv(data: Buffer): Tlv[] {
  const out: Tlv[] = [];
  for (let i = 0; i < data.length; ) {
    const tag = data[i]!;
    const length = data[i + 1]!;
    out.push({ tag, value: data.subarray(i + 2, i + 2 + length) });
    i += 2 + length;
  }
  return out;
}

Part 7 — Onboarding and certificates 🔴 Advancedالجزء 7 — الـ Onboarding والشهادات

English

Before a device can submit anything it must be onboarded, and in Odoo a "device" is a journal. _l10n_sa_api_onboard_journal runs three steps. First, a person gets an OTP from the Fatoora portal, and Odoo generates a key and a CSR, then exchanges them for a Compliance CSID (compliance). Second, it runs compliance checks on 6 sample invoices: invoice, credit and debit for both standard and simplified (compliance/invoices). Third, it requests a Production CSID (production/csids).

A CSID comes back as a double-Base64 X.509 certificate plus a secret, and API calls authenticate with Basic auth over those two. The CSR carries the serial as 1-Odoo|2-20|3-<journal id>, and each field is limited to 64 bytes.

Renewal has a trap. The expiry is l10n_sa_production_csid_validity. After it passes, _l10n_sa_api_get_pcsid refuses to submit: "The Journal is not valid anymore. Please Renew it." But Odoo also refuses to renew early: the journal "can only be renewed upon expiry". Renewal needs a new OTP from a person and uses PATCH production/csids. So there is a window where a device cannot submit, and an alert before expiry is how you get a person and an OTP ready for that moment.

Secrets belong in a vault, not in a config file: see secrets and rotation. If onboarding fails, Odoo resets the certificates, because the same CSR cannot be used twice.

const crypto = webcrypto as unknown as Crypto;
x509.cryptoProvider.set(crypto);
const EC = { name: "ECDSA", namedCurve: "P-256", hash: "SHA-256" };

type Csid = { requestID: number; binarySecurityToken: string; secret: string };

export const certOf = (c: Csid) => new x509.X509Certificate(Buffer.from(Buffer.from(c.binarySecurityToken, "base64").toString(), "base64"));
const basic = (c: Csid) => "Basic " + Buffer.from(`${c.binarySecurityToken}:${c.secret}`).toString("base64");

// تنبيه قبل الانتهاء بفترة كافية، لأن التجديد محتاج OTP من شخص
export function renewalAlert(notAfter: Date, now: Date, warnDays = 30) {
  const daysLeft = Math.floor((notAfter.getTime() - now.getTime()) / 86_400_000);
  if (daysLeft < 0) return { level: "expired", daysLeft } as const;
  return { level: daysLeft <= warnDays ? "warn" : "ok", daysLeft } as const;
}

async function call(url: string, method: string, path: string, body: object, headers: Record<string, string>) {
  const response = await fetch(url + path, { method, headers: { "content-type": "application/json", ...headers }, body: JSON.stringify(body) });
  return { status: response.status, body: (await response.json()) as any };
}

الـ secrets مكانها vault مش config file: شوف درس الـ secrets والـ rotation. ولو الـ onboarding فشل، Odoo بيمسح الشهادات، لأن نفس الـ CSR مينفعش يتستخدم مرتين.

Common mistakes · غلطات شائعة

❌ New ICV on retry 
async function retry(doc) {
  // غلط: رقم جديد لنفس الفاتورة
  doc.icv = ++device.icv;
  await send(build(doc));
}
✅ Resend the saved bytes 
async function retry(doc) {
  // نفس الـ ICV ونفس الـ bytes
  await send(doc.bytes);
}
بالعامية

❌ لو الفاتورة وصلت فعلًا قبل الـ timeout، رقم ICV جديد بيخلي عندك فاتورة واحدة برقمين والسلسلة تبوظ. ✅ لما الحالة unknown ابعت نفس الـ bytes المتخزنة بالظبط.

❌ Hash a reformatted XML 
const pretty = format(xml);
// المسافات اتغيرت فالـ hash اتغير
const hash = sha256(c14n(pretty));
✅ Hash what you will send 
// نفس الـ bytes اللي هتتبعت
const hash = invoiceSha256(xml);
await send(xml);
بالعامية

❌ الـ C14N مبيشيلش المسافات بين العناصر، فأي pretty-print بيطلّع hash تاني، وده اتثبت في الـ lab. ✅ احسب الـ hash على نفس الـ bytes اللي هتبعتها.

❌ Mix up the two encodings 
// غلط: الـ PIH مش base64 للـ bytes الخام
const pih = sha.digest("base64");
✅ Base64 of the hex string 
// شكل الـ PIH زي ما Odoo بيعمله
const pih = Buffer.from(sha.digest("hex")).toString("base64");
بالعامية

❌ الـ base64 للـ bytes الخام طوله 44 حرف، وده شكل الـ DigestValue مش الـ PIH. ✅ الـ PIH في Odoo هو base64 لنص الـ hex وطوله 88 حرف.

❌ String length in TLV 
// غلط: عدد الحروف مش عدد الـ bytes
const length = seller.length;
✅ Byte length 
// العربي غالبًا 2 byte للحرف
const length = Buffer.byteLength(seller);
بالعامية

❌ .length بيعدّ الحروف، فمع العربي الطول المكتوب بيبقى أصغر من الحقيقي والـ QR بيتقرا غلط. ✅ Buffer.byteLength بيرجّع عدد الـ bytes الصح.

Cheat sheet · الخلاصة

  • Standard (B2B): cleared before it reaches the buyer. Simplified (B2C): issued, then reported within 24 hours.
  • Clearance puts the authority in your synchronous path. Reporting gives you a queue with a legal deadline.
  • Wave 25: revenue above SAR 187,500 in any of 2022–2025, integrate by 1 February 2027. Keep waves as dated data.
  • UBL: ProfileID is reporting:1.0; type codes 388, 381, 383, 386; name is 7 characters.
  • ICV is the counter and PIH is the previous hash. One chain per device (a journal in Odoo).
  • Hash: strip extensions, QR and signature, then inclusive C14N, then SHA-256. Whitespace counts.
  • DigestValue is base64 of raw bytes; PIH is base64 of the hex string. First PIH comes from "0".
  • Serialize per chain: a lock or a single consumer per device.
  • Timeout goes to unknown: keep the ICV and resend the same bytes. Rejection clears the index. Local error goes to to_send.
  • QR is TLV with a one-byte length: 255 bytes, not characters.
  • Onboarding: OTP, CSR, Compliance CSID, 6 checks, Production CSID, per device.
  • Odoo renews only on expiry and needs a new OTP, so alert early and name an owner.
بالعامية
  • الـ standard (B2B) بيتعمله clearance قبل ما يوصل للمشتري. والـ simplified (B2C) بيتسلم وبعدين يتبلّغ خلال 24 ساعة.
  • الـ clearance بيحط الـ authority في الـ synchronous path. والـ reporting بيديك queue ليه deadline قانوني.
  • الموجة 25: إيراد أكتر من 187,500 ريال في أي سنة من 2022 لـ 2025، والربط بحد أقصى 1 فبراير 2027. خلي الموجات data بتاريخ.
  • الـ UBL: ProfileID قيمته reporting:1.0، وأكواد النوع 388 و381 و383 و386، وname من 7 حروف.
  • الـ ICV عداد والـ PIH هو الـ hash السابق. سلسلة واحدة لكل جهاز (journal في Odoo).
  • الـ hash: شيل الـ extensions والـ QR والتوقيع، وبعدين inclusive C14N، وبعدين SHA-256. والمسافات بتتحسب.
  • DigestValue هو base64 للـ bytes الخام، وPIH هو base64 لنص الـ hex. وأول PIH جاي من "0".
  • اعمل serialize لكل سلسلة: lock أو consumer واحد لكل جهاز.
  • الـ timeout بيروح unknown: حافظ على الـ ICV وابعت نفس الـ bytes. والرفض بيمسح الـ index. والخطأ المحلي بيروح to_send.
  • الـ QR هو TLV بطول byte واحد: 255 byte مش حرف.
  • الـ Onboarding: OTP، و CSR، و Compliance CSID، و6 فحوصات، و Production CSID، لكل جهاز.
  • Odoo بيجدد بعد الانتهاء بس ومحتاج OTP جديد، فنبّه بدري وحدد owner.
