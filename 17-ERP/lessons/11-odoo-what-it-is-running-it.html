Why this matters · ليه ده مهم

English

Until now the section has been domain: double-entry, documents, projects. From here on the domain runs on a real system. Before you write one line for an Odoo customer you need three answers: which edition, which hosting, and which version, because those decide whether your code is even allowed to run. Then you need a mental model of the machine: a Python monolith whose schema, screens and permissions are rows in Postgres, and whose every HTTP request is one transaction that may run more than once. A Node developer who misses that last point writes integrations that charge a card twice.

بالعامية

لحد دلوقتي القسم كان domain: الـ double-entry والمستندات والمشاريع. من هنا الـ domain هيشتغل على نظام حقيقي. قبل ما تكتب سطر واحد لعميل على Odoo لازم تعرف 3 إجابات: أنهي edition، أنهي hosting، وأنهي version، لأن دول اللي بيحددوا الكود بتاعك مسموحله يشتغل أصلًا ولا لأ. وبعدين لازم تبني صورة في دماغك للماكينة نفسها: Python monolith الـ schema والشاشات والصلاحيات بتاعته كلها rows في Postgres، وكل HTTP request فيه هو transaction واحدة ممكن تتنفذ أكتر من مرة. مبرمج Node اللي النقطة الأخيرة دي تفوته بيكتب integration بيخصم من الكارت مرتين.

Part 1 — Community and Enterprise 🟢 Basicالجزء 1 — Community و Enterprise

English

Odoo comes in two editions that share one core. Community is the open part: odoo/release.py says license = 'LGPL-3', and all 173 modules installed in this lab report LGPL-3. Enterprise is not a separate product. It is a second set of proprietary modules placed on the same addons path, on top of Community, under the Odoo Enterprise Edition License v1.0: it may only be run with a valid subscription for the correct number of users, and copies may not be published or resold. (The 20.0 docs page still heads these sections "Odoo 19"; the LICENSE file in the 20.0 source says LGPLv3.)

Don't trust a feature matrix when you can ask the system. A model either exists in the registry or it doesn't. The check below ran against real Community 20: hr.employee exists but hr.payslip doesn't, so HR is there and Payroll isn't. ai.agent and account.asset are missing too, and so are the addons account_reports, account_accountant, hr_payroll and ai.

The subtle one is account.report. It is registered, with 8 rows, including the Egyptian and Saudi tax reports. Community holds the report definitions as data. The engine that renders them (get_report_information) lives in the Enterprise addon account_reports, along with the bank-reconciliation widget in account_accountant. So Community has a complete ledger but no balance-sheet screen, which is why lesson 12 builds a trial balance by hand. Licences in depth come in lesson 37.

Part 2 — Hosting 🟢 Basicالجزء 2 — الـ Hosting

English

There are three places an Odoo database can live. Odoo Online is Odoo's SaaS. The pricing page describes it as "our cloud infrastructure to host databases without custom modules", and the hosting docs say it "is not compatible with non-standard apps". Online databases also run intermediary versions (the docs' example is 16.3), which Odoo.sh and on-premise don't support: you wait for the next major version before you can move out. Odoo.sh is Odoo's platform for custom code: Git branches for development, staging and production. On-premise means you run it, with Community or with a licensed Enterprise, and you own backups, upgrades and security. Odoo.sh was not run here.

The plan matters as much as the host. The pricing page lists External API only under the Custom plan, along with Studio and multi-company. It defines external API as other software calling in through JSON-RPC or XML-RPC; calls that Odoo itself initiates, such as a payment provider, are not counted.

Put the two together: Python modules need Odoo.sh or on-premise, and inbound API calls need the Custom plan. Inference, not Odoo's wording: a customer on Online Standard has no developer work for you, because neither of the two ways in is open. Migration, process design or moving them to another plan is still possible, but that is a different job.

type Hosting = "Online Standard" | "Online Custom" | "Odoo.sh" | "On-premise";

interface Customer {
  name: string;
  needsCustomModules: boolean;
  needsExternalApi: boolean;
  mustHostOwnData: boolean;
}

// القرار بالترتيب: القيود اللي ملهاش بديل تتفحص الأول
function chooseHosting(c: Customer): { hosting: Hosting; devWork: string } {
  if (c.mustHostOwnData) {
    return { hosting: "On-premise", devWork: "modules, API, and all the ops: backups, upgrades, security" };
  }
  if (c.needsCustomModules) {
    return { hosting: "Odoo.sh", devWork: "Python modules on Git branches, API" };
  }
  if (c.needsExternalApi) {
    return { hosting: "Online Custom", devWork: "API integration from your own service, Studio" };
  }
  return { hosting: "Online Standard", devWork: "none (inference)" };
}

const customers: Customer[] = [
  { name: "12-person shop", needsCustomModules: false, needsExternalApi: false, mustHostOwnData: false },
  { name: "Distributor + Node storefront", needsCustomModules: false, needsExternalApi: true, mustHostOwnData: false },
  { name: "Factory with custom costing", needsCustomModules: true, needsExternalApi: true, mustHostOwnData: false },
  { name: "Regulated lender", needsCustomModules: true, needsExternalApi: true, mustHostOwnData: true },
];

for (const c of customers) {
  const { hosting, devWork } = chooseHosting(c);
  console.log(`${c.name.padEnd(30)} ${hosting.padEnd(16)} ${devWork}`);
}

بالعامية

فيه 3 أماكن الـ database ممكن تعيش فيها. Odoo Online هو الـ SaaS بتاع Odoo. صفحة الأسعار بتوصفه بإنه "البنية السحابية بتاعتنا لاستضافة databases من غير custom modules"، والـ docs بتقول إنه "مش متوافق مع الـ non-standard apps". وكمان Online بيشغّل intermediary versions (مثال الـ docs هو 16.3)، ودي Odoo.sh والـ on-premise مش بيدعموها: لازم تستنى الـ major version الجاي قبل ما تقدر تخرج. Odoo.sh هي منصة Odoo للكود الـ custom: Git branches للـ development والـ staging والـ production. On-premise معناها إنت اللي بتشغّل، بـ Community أو بـ Enterprise مرخص، والـ backups والـ upgrades والـ security عليك. Odoo.sh ماتجربش هنا.

الـ plan مهم زي الـ host بالظبط. صفحة الأسعار حاطة External API تحت plan الـ Custom بس، ومعاه Studio والـ multi-company. وبتعرّف الـ external API بإنه software تاني بينادي على Odoo عن طريق JSON-RPC أو XML-RPC. أما الـ calls اللي Odoo نفسه بيبدأها، زي payment provider، فمش محسوبة.

حط الاتنين جنب بعض: الـ Python modules محتاجة Odoo.sh أو on-premise، والـ API calls اللي داخلة محتاجة plan الـ Custom. ده استنتاج مننا، مش كلام Odoo: عميل على Online Standard مفيش عنده شغل developer ليك، لأن الطريقين الاتنين مقفولين. لسه ممكن migration أو تصميم عمليات أو تنقله لـ plan تاني، بس ده شغل مختلف.

فين هستخدمه في شغلي؟ شركة عندها Next.js storefront وعايزة الأوردرات تدخل Odoo. قبل ما تكتب أي fetch، اطلب منهم يبعتولك الـ plan. لو Standard، الـ integration مش هينفع لحد ما يطلعوا Custom، وده تمن شهري على كل مستخدم لازم يبقى في الـ proposal. الغلطة الشائعة إنك تكتشف ده بعد ما تكون بنيت الـ sync.

Part 3 — Running Odoo 20 🟢 Basicالجزء 3 — تشغيل Odoo 20

English

Odoo is one Python program, odoo-bin, pointed at a config file and a database. odoo/release.py states the requirements: Python 3.12 to 3.14 and PostgreSQL 16 or newer. The helper D:/tools/odoo/odoo.mjs hides no magic. For a lab it copies a ready-made Postgres data folder, starts Postgres on a free port, writes a config, and runs python odoo-bin -c <conf> -d odoo --http-port <free port>. For your practice instance it runs python odoo-bin -c <conf> -d odoo --dev=xml,reload, with Postgres on 55469 and HTTP on 8069.

Start yours with node D:/tools/odoo/odoo.mjs start, open http://127.0.0.1:8069, and log in as admin / admin. Your modules go in D:/tools/odoo/custom-addons. This database has Arabic as the admin's language and English isn't even active, so the screens come up in Arabic. To match the English labels in this lesson, run use_english.py below once in the shell and log in again.

/web/health is the endpoint for load balancers: it needs no login and answers {"status": "pass"}. According to addons/web/controllers/home.py, adding ?db_server_status=1 also tests a Postgres connection and returns 500 if that fails. Logging in from code goes to /web/session/authenticate, the same route the web client uses. For integrations you'll use API keys instead (lesson 27).

Part 5 — The architecture 🟢 Basicالجزء 5 — الـ Architecture

English

Odoo is a modular monolith in Python on PostgreSQL. A module (addon) is a folder on the addons path. Installing one records it in the database. At startup Odoo builds a registry per database: it reads which modules are installed in that database and composes the model classes from them. That composition is the unusual part. sale.order here is one Python class with 65 classes in its MRO, contributed by 38 modules through extensions and mixins. No single file describes it.

Each request gets a cursor (one Postgres connection and transaction, at REPEATABLE READ, which is the isolation 2 below) and an Environment: that cursor, the user, the context, and the superuser flag. Registry load took ≈1–5 s across runs on this loaded Windows machine, read from the log line Registry loaded in 1.396s.

odoo/service/server.py picks the server. With workers = 0, as on Windows and in this lab, you get ThreadedServer: one process, a thread per request. On Linux with workers > 0 you get PreforkServer: a master that forks WorkerHTTP and WorkerCron processes and spawns a gevent process for websockets on port 8072. Prefork uses os.fork, so it was not run here. Defaults from config.py: limit_time_cpu 60 s, limit_time_real 120 s, limit_memory_soft 2 GiB, limit_memory_hard 2.5 GiB, db_maxconn 64. Odoo عبارة عن modular monolith بـ Python فوق PostgreSQL. الـ module (أو addon) فولدر على الـ addons path. لما تسطبه بيتسجل في الـ database. وفي الـ startup Odoo بيبني registry لكل database: بيشوف أنهي modules متسطبة في الـ database دي ويركّب الكلاسات منها. التركيبة دي هي الحتة الغريبة. sale.order هنا كلاس Python واحد فيه 65 كلاس في الـ MRO، جايين من 38 module عن طريق extensions و mixins. مفيش ملف واحد بيوصفه كله.

كل request بياخد cursor (اتصال Postgres واحد و transaction واحدة، على REPEATABLE READ، وده معنى isolation 2) وEnvironment: الـ cursor ده والمستخدم والـ context وعلامة الـ superuser. تحميل الـ registry خد ≈1–5 ثواني في التشغيلات المختلفة على جهاز Windows المحمّل ده، ومقرية من سطر الـ log Registry loaded in 1.396s.

odoo/service/server.py هو اللي بيختار السيرفر. مع workers = 0، زي Windows والـ lab، بتاخد ThreadedServer: process واحدة و thread لكل request. على Linux و workers > 0 بتاخد PreforkServer: master بيعمل fork لـ processes من نوع WorkerHTTP و WorkerCron وبيشغّل process بـ gevent للـ websockets على port 8072. الـ Prefork بيستخدم os.fork فماتجربش هنا. الـ defaults من config.py: limit_time_cpu 60 ثانية، limit_time_real 120 ثانية، limit_memory_soft 2 GiB، limit_memory_hard 2.5 GiB، db_maxconn 64. حسابات الـ production في درس 34.

فين هستخدمه في شغلي؟ لو Node service بيبعت 200 request متوازي على Odoo فيه 4 workers: في Node كان ده عادي، بس هنا 4 بس اللي شغالين والباقي مستني في الطابور، وكل واحد ماسك Postgres connection. عشان كده الـ integration يتعمل بـ concurrency صغير وbatches (درس 28)، مش Promise.all على 200 أوردر. الغلطة الشائعة إنك تفكر في Odoo بعقلية الـ event loop.
Interview question "Why does a module installed through one Odoo worker show up in the others?" → Each process holds its own registry in memory. The installing process inserts a row into orm_signaling_registry in Postgres, and every request first reads max(id) from those signalling tables (the first query in Part 6); a process that sees a newer value rebuilds its registry. Postgres is the coordination channel.
"ليه module اتسطب من worker واحد بيظهر في الباقيين؟" ← كل process ماسكة registry في الـ memory بتاعتها. اللي سطّب بيضيف row في orm_signaling_registry في Postgres، وكل request بيقرا الأول max(id) من جداول الـ signaling دي (أول query في الجزء 6)، واللي يلاقي رقم أحدث بيبني الـ registry من جديد. يعني Postgres هو قناة التنسيق.

Part 6 — One request, traced 🟡 Intermediateالجزء 6 — request واحد من أوله لآخره

English

Follow one JSON-2 call through the real source. odoo/http/router.py receives it in Application.__call__ and hands it to serve_db, which gets the registry and a cursor, builds an Environment, matches the route with ir.http._match, and calls the handler inside retrying. The handler, serve_ir_http, runs ir.http._authenticate (here _auth_method_bearer, which looks up the API key), _pre_dispatch, then the dispatcher, which calls the controller web_json_2_rpc in addons/rpc/controllers/json2.py. That resolves the model and a public method (private _methods get 403) and calls the ORM. Back in retrying, the changes are flushed and the transaction committed.

The run below used --log-sql. A warm search_read is 7 queries: 2 registry and cache signalling checks, the API-key lookup, 3 reads to load the user, their partner and company, and finally the real query. Notice the real query contains a company_id IN (...) clause you never wrote: that is ir.access applied by the ORM. The last field of the log line, rw, is the cursor mode; search_read is marked read-only, but there is no replica here so it uses the primary.

Now the part that matters most. retrying catches serialization failures, deadlocks and lock timeouts, rolls back, waits a random time (uniform(0, 2**try) seconds), and runs your whole handler again, up to 5 tries. Two concurrent requests changing one row made that happen for real: 2 HTTP requests, 2 success responses, but 3 executions. The database is fine, because the first attempt was rolled back. A Python list isn't in the transaction, and neither is a card charge or an email.

The fix is env.cr.postcommit.add(fn): callbacks run only after a successful commit, and rollback() clears them. It ran exactly once per request even though both retried. It still isn't exactly-once: a crash right after the commit loses the callback. For money, use an outbox and an idempotency key. Why Postgres raises this is in the isolation lesson; the production side is lesson 35.

بالعامية

تعالى نمشي مع JSON-2 call واحد في الكود الحقيقي. odoo/http/router.py بيستلمه في Application.__call__ ويديه لـ serve_db، اللي بيجيب الـ registry و cursor، ويبني Environment، ويلاقي الـ route بـ ir.http._match، وينادي الـ handler جوه retrying. الـ handler، serve_ir_http، بيشغّل ir.http._authenticate (هنا _auth_method_bearer اللي بيدور على الـ API key)، وبعدها _pre_dispatch، وبعدها الـ dispatcher اللي بينادي الـ controller web_json_2_rpc في addons/rpc/controllers/json2.py. ده بيلاقي الـ model والـ public method (الـ _methods الـ private بترجع 403) وينادي الـ ORM. ولما يرجع لـ retrying التعديلات بتتعمل flush والـ transaction تتعمل commit.

التشغيل استخدم --log-sql. search_read بعد ما الـ caches تسخن عبارة عن 7 queries: 2 فحص signaling للـ registry والـ caches، وواحدة للـ API key، و3 قراية للمستخدم والـ partner بتاعه والشركة، وفي الآخر الـ query الحقيقية. لاحظ إن الـ query الحقيقية فيها company_id IN (...) إنت ماكتبتهاش: ده ir.access الـ ORM طبّقه. وآخر حتة في سطر الـ log، rw، هي نوع الـ cursor. search_read متعلّم read-only، بس مفيش replica هنا فبيستخدم الـ primary.

الجزء الأهم بقى. retrying بيمسك الـ serialization failures والـ deadlocks والـ lock timeouts، يعمل rollback، يستنى وقت عشوائي (uniform(0, 2**try) ثانية)، ويشغّل الـ handler بتاعك كله تاني، لحد 5 محاولات. طلبين متوازيين بيعدلوا نفس الـ row خلوا ده يحصل بجد: 2 HTTP requests و 2 ردود ناجحة، بس 3 مرات تنفيذ. الـ database سليمة لأن المحاولة الأولى اترجعت بالـ rollback. بس الـ Python list مش جوه الـ transaction، ولا خصم الكارت ولا الإيميل.

الحل env.cr.postcommit.add(fn): الـ callbacks بتشتغل بعد commit ناجح بس، وrollback() بيمسحها. اشتغلت مرة واحدة لكل request رغم إن الاتنين حصل عليهم retry. ومع ذلك ده مش exactly-once: لو الـ process وقعت بعد الـ commit على طول الـ callback بتضيع. في الفلوس استخدم outbox وidempotency key. ليه Postgres بيرمي الـ error ده في درس الـ isolation، وجانب الـ production في درس 35.

فين هستخدمه في شغلي؟ Custom module بينادي Stripe أو ETA جوه action_post. في الضغط، لما محاسبين اتنين يعدلوا نفس العميل، الـ request بيتعاد والخصم يتكرر، والـ log مفيهوش غير SERIALIZATION_FAILURE, 4 tries left بـ level INFO. الغلطة الشائعة تدوّر على الـ bug في الـ Node client، مع إن الـ client بعت مرة واحدة. الحل: الـ call الخارجي يطلع برا الـ transaction.
Interview question "Your Odoo controller sends one webhook, and the receiver sometimes gets it twice, though the client called once. Why?" → Odoo re-runs the whole handler on a serialization failure at REPEATABLE READ. Move the call to env.cr.postcommit or, better, an outbox row written in the same transaction, and send an idempotency key.

Solution · الحل 
import pg from "pg";
import { setTimeout as sleep } from "node:timers/promises";

const raw = process.argv[2] ?? "";
const port = Number(raw);
if (!/^\d+$/.test(raw) || port < 1024 || port > 65535 || [27017, 5432, 6379].includes(port)) {
  throw new Error(`refusing port ${raw}`);
}
const pool = new pg.Pool({ host: "127.0.0.1", port, user: "odoo_lab", database: "odoo", max: 4 });

let attempts = 0;
let emails = 0;

// نفس فكرة retrying في Odoo: أعد الشغل كله، بس الـ side effect بعد الـ commit
async function withRetry<T>(
  work: (client: pg.PoolClient) => Promise<T>,
  afterCommit: (result: T) => Promise<void>,
  maxTries = 5,
): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    const client = await pool.connect();
    try {
      await client.query("BEGIN ISOLATION LEVEL REPEATABLE READ");
      const result = await work(client);
      await client.query("COMMIT");
      await afterCommit(result);
      return result;
    } catch (err) {
      await client.query("ROLLBACK").catch(() => undefined);
      // بس 40001 هو اللي ينفع يتعاد، أي error تاني يطلع زي ما هو
      if ((err as { code?: string }).code !== "40001" || attempt >= maxTries) throw err;
      await sleep(Math.random() * 2 ** attempt * 50);
    } finally {
      client.release();
    }
  }
}

const addToOrder = (amount: number) =>
  withRetry(
    async (client) => {
      attempts++;
      const { rows } = await client.query("SELECT total FROM lab_orders WHERE id = 1");
      await sleep(300);
      await client.query("UPDATE lab_orders SET total = $1 WHERE id = 1", [Number(rows[0].total) + amount]);
      return amount;
    },
    async () => {
      emails++;
    },
  );

try {
  await pool.query("CREATE TABLE IF NOT EXISTS lab_orders (id int PRIMARY KEY, total numeric NOT NULL)");
  await pool.query("INSERT INTO lab_orders VALUES (1, 0) ON CONFLICT (id) DO UPDATE SET total = 0");
  await Promise.all([addToOrder(100), addToOrder(50)]);
  const { rows } = await pool.query("SELECT total FROM lab_orders WHERE id = 1");
  console.log({ total: rows[0].total, attempts, emails });
  await pool.query("DROP TABLE lab_orders");
} finally {
  await pool.end();
}
{ total: '150', attempts: 3, emails: 2 }
الـ total طلع 150 يعني مفيش update ضاع، و3 محاولات لطلبين يعني واحد اتعاد، والإيميلات 2 بالظبط. ده نفس تصميم retrying وpostcommit في Odoo.

Cheat sheet · الخلاصة

  • Community is LGPLv3. Enterprise is proprietary modules on top and needs a subscription.
  • Ask the registry: 'hr.payslip' in env. account.report exists in Community as data only.
  • Online has no custom modules; the external API needs the Custom plan; Odoo.sh and on-premise run your Python.
  • odoo-bin -c conf -d db. Python 3.12–3.14, PostgreSQL 16+. Practice: http://127.0.0.1:8069, Postgres 55469.
  • ?debug=1 is stored in the session and unlocks Settings → Technical; ?debug=assets unminifies JS.
  • The technical menu is a database browser: ir.model, ir.model.fields, ir.ui.view, ir.actions.*, ir.access, ir.cron, ir.sequence. Read with SQL, never write.
  • Registry per database, composed from installed modules. sale.order here: MRO of 65 from 38 modules.
  • workers = 0 → ThreadedServer; Linux workers > 0 → PreforkServer with HTTP, cron and gevent processes.
  • One request = one cursor = one transaction at REPEATABLE READ.
  • retrying re-runs the whole handler up to 5 tries. Side effects go in env.cr.postcommit or an outbox.
