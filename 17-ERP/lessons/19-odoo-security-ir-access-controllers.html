Why this matters · ليه ده مهم

English

An ERP holds salaries, bank details and every customer's balance, so its access model decides who can move money. A custom Odoo module runs inside that model, and one careless sudo() can expose another company's invoices to any logged-in user. Odoo 20 also replaced the two security tables that every older tutorial describes with a single model, ir.access, so a lot of what you'll find online is now wrong. In code review and interviews the senior question stays the same: what happens if this user calls this method directly, with a record that isn't theirs?

بالعامية

الـ ERP شايل المرتبات وبيانات البنوك ورصيد كل عميل، فالـ access model هو اللي بيحدد مين يقدر يحرّك فلوس. أي custom module في Odoo بيشتغل جوه الـ model ده، وsudo() واحدة من غير تفكير ممكن تفتح فواتير شركة تانية لأي user عامل login. وكمان Odoo 20 شال الجدولين بتوع الـ security اللي أي tutorial قديم بيشرحهم وحط مكانهم model واحد اسمه ir.access، فكتير من اللي هتلاقيه على النت بقى غلط. في الـ code review والـ interviews السؤال بتاع الـ senior ثابت: إيه اللي هيحصل لو الـ user ده نادى الـ method دي مباشرة، على سجل مش بتاعه؟

Part 1 — Groups and default deny 🟡 Intermediateالجزء 1 — الـ groups والمنع كأصل

English

A res.groups record is a named role. Users join groups, and permissions attach to groups, never directly to a user. implied_ids builds inheritance: Refund Manager implies Refund User, which implies base.group_user, the internal user role.

On res.users there are two fields, and mixing them up is a real bug. group_ids holds only what was assigned explicitly. all_group_ids is the computed closure that includes everything implied. A manager's group_ids doesn't contain Refund User at all, so check with user.has_group('module.xmlid') or all_group_ids.

res.groups.privilege is presentation. It bundles the groups of one application into a single choice on the user form, and it grants nothing by itself. What grants access is ir.access, and the model is default deny: if no row matches an operation on a model for a user, that user has no access. A new model with no rows is reachable only by the superuser.

بالعامية

الـ res.groups ده role ليه اسم. الـ users بيدخلوا groups، والصلاحيات بتتعلق على الـ groups، عمرها ما بتتعلق على user مباشرة. الـ implied_ids بتعمل الوراثة: Refund Manager بيـ imply الـ Refund User، واللي بيـ imply الـ base.group_user (الـ internal user).

على res.users فيه حقلين، والخلط بينهم bug حقيقي. الـ group_ids فيها اللي اتدّى صراحةً بس. الـ all_group_ids محسوبة وفيها كل حاجة implied. يعني الـ group_ids بتاعة المدير مفيهاش Refund User أصلًا، فاتشيك بـ user.has_group('module.xmlid') أو بـ all_group_ids.

الـ res.groups.privilege شكل بس: بيجمّع groups الـ app الواحد في اختيار واحد في فورم الـ user، ومبيدّيش أي صلاحية لوحده. اللي بيدّي صلاحية هو ir.access، والـ model default deny: لو مفيش row مطابق لعملية على model لـ user معين، الـ user ده ملوش access. يعني model جديد من غير rows محدش يوصله غير الـ superuser.

فين هستخدمه في شغلي؟ في Node API عندك middleware زي requireRole('manager') (شوف درس الـ authorization). في Odoo الـ role ده group، والـ role hierarchy هي implied_ids. لو جالك ticket "المدير مش شايف زرار الموظف"، أول حاجة تبص عليها إن حد كاتب شرط على group_ids بدل has_group.

Part 2 — ir.access: one model for permissions and restrictions 🔴 Advancedالجزء 2 — ir.access: model واحد للصلاحيات والقيود

English

Up to Odoo 19 you wrote two things: ir.model.access.csv for model-level CRUD and ir.rule records for row-level domains. In Odoo 20 both models are gone. On the lab database 'ir.rule' in env and 'ir.model.access' in env are both False, and the template holds 1,267 ir.access rows. A module ships security/ir.access.csv with the columns id,name,model_id,group_id/id,operation,domain, where model_id holds the model name.

operation is a subsequence of the string crud: r, cru, ud and so on, in that order. The row's kind follows from one column. A row with a group is a permission, and permissions add up across all of a user's groups. A row without a group is a restriction that applies to every user, and restrictions intersect.

So an operation on a record is allowed when at least one permission for that operation has a group the user belongs to and a domain the record satisfies, and the record satisfies every restriction for that operation. A restriction can therefore block something a group was granted. The docs warn that several restrictions can produce non-overlapping sets and remove all access.

def allowed(self, operation):
    try:
        with self.env.cr.savepoint():
            operation()
            self.env.flush_all()

بالعامية

لحد Odoo 19 كنت بتكتب حاجتين: ir.model.access.csv للـ CRUD على مستوى الـ model، وir.rule للـ domains على مستوى الصف. في Odoo 20 الاتنين اتشالوا. على داتابيز الـ lab الـ 'ir.rule' in env والـ 'ir.model.access' in env الاتنين False، والـ template فيه 1,267 row في ir.access. الـ module بيشحن security/ir.access.csv بالأعمدة id,name,model_id,group_id/id,operation,domain، والـ model_id فيه اسم الـ model.

الـ operation جزء من كلمة crud بنفس الترتيب: r أو cru أو ud وهكذا. ونوع الـ row بيتحدد من عمود واحد: row فيه group يبقى permission، والـ permissions بتتجمع عبر كل groups الـ user. Row من غير group يبقى restriction على كل الناس، والـ restrictions بتتقاطع.

يعني العملية على السجل مسموحة لو فيه permission واحدة على الأقل لنفس العملية، الـ group بتاعها عند الـ user والسجل جوه الـ domain بتاعها، وكمان السجل عدّى كل restriction للعملية دي. عشان كده restriction ممكن تمنع حاجة الـ group ادّاها. والـ docs بتحذر إن كذا restriction ممكن يطلعوا مجموعات مش متقاطعة ويشيلوا الـ access خالص.

فين هستخدمه في شغلي؟ قاعدة زي "الـ refund المدفوع ميتعدلش" لو كتبتها في Node هتبقى if في كل endpoint، وهتنساها في endpoint واحد. هنا هي row واحد في CSV بيتطبق على الـ UI والـ API والـ cron بتاع أي user عادي. نفس فكرة الـ RLS في Postgres: القاعدة قريبة من الـ data، مش متوزعة في الـ handlers.

الغلطة الشائعة: تضيف restriction وإنت فاكرها هتزوّد access. الـ row من غير group عمره ما يزوّد، ده بيضيّق بس.

What breaks Copying an old tutorial's ir.model.access.csv into an Odoo 20 module, or forgetting the group column and turning a permission into a restriction. A row with an empty group doesn't grant access to everyone: it narrows access for everyone.

Part 3 — Multi-company isolation 🔴 Advancedالجزء 3 — عزل الشركات

English

Odoo's multi-company is tenant isolation inside one database, and it needs two independent controls. The first is the restriction you saw: [('company_id', 'in', company_ids)]. The domain can use four variables: time, user, company_id (the current company's id) and company_ids (the ids of the companies active right now).

"Active right now" is the part people miss. company_ids comes from env.companies, which is the company switcher's selection, filtered by what the user may access. A user who belongs to two companies but has only one selected doesn't see the other's records. (The docs describe company_ids as all of the user's companies; the source comment and the test below both show it's the active selection.) Also, with_company(x) makes x the current company without removing the others from env.companies, so it doesn't narrow anything.

The second control protects links between records. check_company=True on a relational field together with _check_company_auto = True on the model makes create and write call _check_company, which refuses a record of company A pointing at a partner that belongs only to company B. Records meant to be shared set company_id to empty, and their restriction then needs ['|', ('company_id', '=', False), ('company_id', 'in', company_ids)].

Reading an out-of-scope record raises AccessError, but searching silently excludes it. A count that looks low may be the access model working correctly. The general idea, and the failure modes, are in section 13 · tenant isolation.

بالعامية

الـ multi-company في Odoo هو tenant isolation جوه داتابيز واحدة، ومحتاج control-ين مستقلين. الأول الـ restriction اللي شفناه: [('company_id', 'in', company_ids)]. الـ domain يقدر يستخدم 4 متغيرات: time، وuser، وcompany_id (id الشركة الحالية)، وcompany_ids (ids الشركات النشطة دلوقتي).

"النشطة دلوقتي" دي اللي الناس بتغفل عنها. الـ company_ids جاية من env.companies، يعني اختيار الـ company switcher بعد ما يتفلتر باللي الـ user مسموح له. فـ user في شركتين ومختار واحدة بس مش هيشوف سجلات التانية. (الـ docs بتوصف company_ids إنها كل شركات الـ user، بس الـ comment في الـ source والـ test اللي تحت الاتنين بيبيّنوا إنها الشركات المختارة.) وكمان with_company(x) بتخلي x الشركة الحالية من غير ما تشيل الباقي من env.companies، فهي مبتضيّقش حاجة.

English

sudo() returns the same records in an environment that skips access checks, so ir.access, including the company restriction, stops applying. It's a legitimate tool: a clerk can't write to the audit table, yet submitting a refund must leave an audit row. The rule is narrow first with the user's own permissions, then elevate for one specific write.

Any method whose name doesn't start with _ is callable over RPC, by any authenticated user, on any record ids, with any arguments. The official guide says it directly: the record and the parameters can't be trusted, and access is only verified during CRUD operations. So a public method that calls self.sudo().write(...) has no protection at all unless it checks first. A _private method can't be called remotely (real response below), but it's only as safe as the public methods that call it.

The same guide lists the APIs to prefer. Build domains with Domain(...) & Domain(...) instead of concatenating lists, because a list that comes from outside can change how an appended condition binds. Write SQL through the SQL wrapper, and remember raw SQL skips ir.access, so filters are your job. Build HTML with Markup, which escapes what you format into it, and render with t-out, not t-raw. Parse data with ast.literal_eval or json.loads, never eval. Read a dynamic field with record[name] behind an allow-list, never getattr on user input.

Part 5 — Controllers: auth, CSRF, validation, ownership 🔴 Advancedالجزء 5 — الـ controllers: الـ auth والـ CSRF والـ validation والملكية

English

A controller is an HTTP entry point and the ORM doesn't protect its arguments. @http.route takes the decisions that matter. type is http (form and query parameters, you return a response), jsonrpc (the JSON-RPC envelope) or json2 (plain JSON body and response). type='json' still works, but it has been a deprecated alias of jsonrpc since 19.

CSRF protection is on by default for type='http' requests that aren't safe methods, and it's off for jsonrpc. A POST with no token gets a 400. Setting csrf=False on a session-authenticated route removes a real control, so embed the token instead. It makes sense only where the caller authenticates with something a browser doesn't attach by itself, such as a bearer key or a signed webhook.

Inside the handler, do three things in order: validate input by type and range, load the record with the caller's permissions, and return a generic error. A wrong owner should get the same 404 as a record that doesn't exist, so the response doesn't confirm the id is real. <int:refund_id> in the route validates only the shape. In Python bool is a subclass of int, so isinstance(True, int) is true and booleans need rejecting explicitly.

Part 6 — API keys and external users 🔴 Advancedالجزء 6 — الـ API keys والمستخدمين الخارجيين

English

A key lives in res.users.apikeys. The database stores a PBKDF2 hash and an 8-character index, so the plain value is shown once and can't be recovered. A key acts as its user, with exactly that user's access, so never run an integration as admin. Create a dedicated user with the narrowest groups that work.

Keys have a scope. The generic rpc scope covers auth='bearer' routes declared with bearer_scope='rpc'. In the lab a key generated for another scope got a 401 on those routes. They also expire. The docs say keys can't last more than three months, and in the source that limit is the api_key_duration field on groups, 90 days for regular users. Note the exception: _check_expiration_date returns early for system administrators, and in the lab admin created a 200-day key. That's one more reason not to issue keys from an admin account.

Rotate in four steps: create the new key, deploy it, verify traffic works with it, then revoke the old one. Both keys are valid during the overlap, so nothing goes down. Programmatic revoke needs a system user, or the base.enable_programmatic_api_keys parameter.

External people are a different case. A portal user (base.group_portal) is an external login with share=True, created through the Grant Portal Access wizard, and it has no access to your models unless a row grants it. On Odoo's paid plans internal users are the billed seats, and they see the back office. Give customers a portal login or a token link rather than an internal account. Portal users only see API key management when portal.allow_api_keys is on, and it's off by default.

Finally, every JSON-2 error body includes a debug field with a full Python traceback. That's useful to you and it shouldn't reach your end users. If a Node service sits in front of Odoo, log it internally and return a generic error with a correlation id.

export function createRefundProxy(config: ProxyConfig): Server {
  const callOdoo = async (method: string, payload: unknown): Promise<Response> =>
    fetch(`${config.odooUrl}/json/2/erp_refund.refund/${method}`, {
      method: "POST",
      headers: {
        "content-type": "application/json",
        authorization: `bearer ${config.apiKey}`,
        "x-odoo-database": config.database,
      },
      body: JSON.stringify(payload),
    });

  return createServer(async (req, res) => {
    const match = /^\/refunds\/(\d{1,12})(\/approve)?$/.exec(req.url ?? "");
    if (!match) return sendJson(res, 404, { error: "not_found" });
    const id = Number(match[1]);

    try {
      const upstream = match[2]
        ? await callOdoo("action_approve", { ids: [id] })
        : await callOdoo("search_read", { domain: [["id", "=", id]], fields: ["name", "state"] });
      const text = await upstream.text();

      if (!upstream.ok) {
        const correlationId = randomUUID();
        // النص الكامل للـ logs، والعميل بياخد الـ correlationId بس
        config.onUpstreamError({ correlationId, status: upstream.status, body: text });
        return sendJson(res, publicStatus(upstream.status), { error: "upstream_error", correlationId });
      }

      const data: unknown = JSON.parse(text);
      if (Array.isArray(data) && data.length === 0) return sendJson(res, 404, { error: "not_found" });
      return sendJson(res, 200, Array.isArray(data) ? data[0] : { ok: true });
    } catch {
      return sendJson(res, 502, { error: "upstream_unavailable" });
    }
  });
}

Cheat sheet · الخلاصة

  • Groups are roles. implied_ids is inheritance. Check has_group, not group_ids.
  • Default deny: no matching ir.access row means no access.
  • Odoo 20: ir.rule and ir.model.access are gone. Ship security/ir.access.csv.
  • Row with a group = permission, they add up. Row without a group = restriction, they intersect.
  • company_ids means the active companies. with_company doesn't narrow them.
  • check_company=True + _check_company_auto protect links between records.
  • Reads raise AccessError, searches silently exclude.
  • sudo() skips ir.access: narrow first, elevate for one write.
  • Public methods take any ids and arguments over RPC. Check inside them.
  • Prefer Domain, SQL, Markup, t-out, literal_eval, record[name] with an allow-list.
  • Controllers: validate, load with the caller's rights, return a generic 400 or 404. Keep CSRF on for session routes.
  • Keys: dedicated narrow user, 90-day limit, rotate create → deploy → verify → revoke, and strip debug before the end user.
