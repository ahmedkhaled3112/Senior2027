Why this matters · ليه ده مهم

English

Almost nothing you write in Odoo starts from an empty model. You extend res.partner, sale.order or account.move, and your code runs inside a chain built from every installed module. You switch user and company to do work on someone's behalf, and each switch can open or close a security boundary. A report that is fast on demo data and takes minutes on real data is almost always a query-count problem.

This lesson shows how those mechanics work and measures them. Query counts below are exact. Timings come from a loaded Windows machine running Postgres with fsync off, so treat them as ratios and expect real disks to widen the gap on writes.

بالعامية

تقريبًا مفيش حاجة بتكتبها في Odoo بتبدأ من model فاضي. إنت بتوسّع res.partner أو sale.order أو account.move، والكود بتاعك بيشتغل جوه سلسلة متبنية من كل module متسطبة. وبتبدّل المستخدم والشركة عشان تشتغل بالنيابة عن حد، وكل تبديل ممكن يفتح أو يقفل حد أمني. والـ report اللي سريع على الـ demo data وبياخد دقايق على الـ data الحقيقية، مشكلته تقريبًا دايمًا عدد الـ queries.

الدرس ده بيوريك الحاجات دي بتشتغل إزاي وبيقيسها. عدد الـ queries تحت مظبوط. الأوقات جاية من جهاز Windows عليه ضغط وPostgres شغالة بـ fsync مقفول، فبص عليها كنِسَب، ومع disks حقيقية الفرق في الكتابة هيكبر.

Part 1 — Extension 🟡 Intermediateالجزء 1 — الـ extension

English

_inherit = 'res.partner' without a _name means "modify that model". A new field becomes a new column in the same res_partner table, and a method you define joins the chain for that model. There is no subclass that callers must opt into: every env['res.partner'] in the database now has your field and your method.

Odoo builds this at registry load. Each module's class becomes a base of one final class, and Python's MRO orders them by module dependency. super() follows that MRO, exactly as lesson 09 showed. So super() means "the next module in the chain", and the next module can change with what's installed. In this lab res.partner has 93 classes in its MRO and eleven of them define write.

The consequence for your override: always call super(), pass the arguments through, and return what it returned. A method that forgets super() silently cuts off every module behind it in the chain, including ones installed next year.

class ResPartnerLoyalty(models.Model):
    # من غير _name: ده تعديل على نفس الموديل ونفس الجدول
    _inherit = 'res.partner'

    loyalty_tier = fields.Selection([('silver', 'Silver'), ('gold', 'Gold')], default='silver')

    def write(self, vals):
        # الـ super هنا بيمشي في الـ MRO لكل الـ modules المتسطبة، مش لـ parent واحد
        if vals.get('loyalty_tier') == 'gold':
            _logger.info('Promoted to gold: %s', self.ids)
        return super().write(vals)

بالعامية

_inherit = 'res.partner' من غير _name معناها "عدّل الموديل ده". الحقل الجديد بيبقى عمود جديد في نفس جدول res_partner، والـ method اللي بتكتبها بتدخل في سلسلة الموديل. مفيش subclass اللي بينادي لازم يختاره: كل env['res.partner'] في الـ database بقى فيه الحقل والـ method بتوعك.

Odoo بيبني ده وقت تحميل الـ registry. الـ class بتاع كل module بيبقى base لـ class نهائي واحد، والـ MRO بتاع Python بيرتبهم حسب dependencies الـ modules. وsuper() بيمشي على الـ MRO ده، زي ما الدرس 09 وراك. يعني super() معناها "الـ module اللي بعدي في السلسلة"، واللي بعدك ممكن يتغير حسب اللي متسطب. في الـ lab ده res.partner الـ MRO بتاعه 93 class، و11 منهم بيعرّفوا write.

النتيجة على الـ override بتاعك: نادي super() دايمًا، عدّي الـ arguments، ورجّع اللي رجع منها. الـ method اللي تنسى super() بتقطع في صمت كل الـ modules اللي وراها في السلسلة، حتى اللي هيتسطبوا السنة الجاية.

فين هستخدمه في شغلي؟ عميل عايز "tier" على الـ customer أو حقل زيادة على الفاتورة: _inherit من غير _name في module بتاعك، ومتلمسش كود Odoo نفسه، عشان الـ upgrade يفضل ممكن (الدرس 37). ولما سلوك يبقى غريب وتشك إن module تانية بتغيّره، اطبع الـ __mro__ من الـ shell، هيقولك مين بيعرّف الـ method وبأي ترتيب.
Interview question "How does super() behave in an Odoo model compared with a normal class hierarchy?" → Odoo assembles one class per model from every installed module, ordered by dependency. super() follows that MRO, so the next method depends on what's installed, and skipping it cuts off the rest of the chain.
"super() بيتصرف إزاي في Odoo model مقارنة بـ class hierarchy عادية؟" ← Odoo بيجمّع class واحد لكل model من كل الـ modules المتسطبة بترتيب الـ dependencies. super() بيمشي على الـ MRO ده، فالـ method اللي بعدك بتعتمد على اللي متسطب، ولو سبته بتقطع باقي السلسلة.

Part 2 — Prototype and delegation 🟡 Intermediateالجزء 2 — الـ prototype والـ delegation

English

Prototype: _inherit together with a new _name copies the definition of the source model into a new model with its own table. The two share code and share nothing at runtime: rows in one aren't rows in the other. It's mainly useful with abstract mixins. A model with its own _name and _inherit = ['mail.thread'] is this form, and it's how a model gets a chatter.

Delegation: _inherits = {'res.partner': 'partner_id'} keeps the parent's fields in the parent's table. Creating a vendor creates two rows, and vendor.name reads and writes res_partner.name through partner_id. Odoo uses this for res.users over res.partner, and product.product over product.template. It's composition with generated accessors.

Two runtime behaviours to know. Deleting the vendor left the partner in place, while deleting the partner removed the vendor through the cascade. And a prototype of a model that has a One2many breaks: the copied line_ids still points at lines whose refund_id references the original table. In the lab, installing that copy succeeded and creating a record with lines raised MissingError.

الـ Prototype: _inherit مع _name جديد بينسخ تعريف الموديل الأصلي في موديل جديد بجدول خاص بيه. الاتنين مشتركين في الكود ومفيش بينهم حاجة وقت التشغيل: صفوف ده مش صفوف ده. فايدته الأساسية مع الـ abstract mixins. موديل عنده _name خاص بيه و_inherit = ['mail.thread'] هو الشكل ده، وهي الطريقة اللي الموديل بياخد بيها chatter.

سلوكين تعرفهم وقت التشغيل. مسح الـ vendor ساب الـ partner مكانه، ومسح الـ partner شال الـ vendor بالـ cascade. وprototype لموديل فيه One2many بيبوظ: الـ line_ids المنسوخ لسه بيشاور على lines الـ refund_id بتاعها راجع للجدول الأصلي. في الـ lab النسخة اتسطبت عادي، وإنشاء record بـ lines رمى MissingError.

المقارنة في TypeScript في الكود فوق: class Customer extends Partner شبه الـ prototype، كل object شايل data بتاعته. وVendor اللي جواه partner شبه الـ delegation، وinstanceof Partner بترجع false لأنه مش Partner، هو شايل واحد. الفرق إن Odoo بيولّد الـ getters والـ setters لوحده مع _inherits.

فين هستخدمه في شغلي؟ "Driver" في نظام توصيل هو contact بيتبعتله فواتير وإيميلات، وعنده license وvehicle: ده delegation فوق res.partner، فاسمه وتليفونه مصدرهم واحد. ولو عايز كل موديلاتك يبقى ليها audit log: abstract mixin، وكل موديل يعمله _inherit. ولو حد في الـ review عمل prototype لـ sale.order عشان "نسخة شبهه"، وقفه: الـ lines هتبوظ.

Part 3 — Environment switches 🔴 Advancedالجزء 3 — تبديل الـ environment

English

Each switch returns the same records under a new Environment, sharing the cursor and transaction. sudo() bypasses access checks and keeps env.user, so create_uid still records the real user. with_user() changes the user and leaves superuser mode. with_context() changes the context, and with_company() puts a company first in allowed_company_ids.

A company_dependent=True field gives one value per company. In Odoo 20 it's stored as one jsonb column keyed by company id, not in a separate properties table, so property_cost_method on a single category reads differently under two companies, and a search respects the current company.

A claim you'll find in older advice is that with_context inside a loop kills prefetching. Measured on Odoo 20, it doesn't for ordinary fields: with_env keeps the same prefetch ids, and field values live in a per-transaction cache that only context-dependent fields split by key. A loop with with_context, sudo or with_company per record still took 2 queries for 50 records. Three things do hurt. browse(id) starts a new prefetch set, giving 100 queries. A field with @api.depends_context gets a new cache slot per context value: the compute ran 50 times over all 50 records, 2,500 record computations instead of 50. And each new context value builds a new Environment, roughly eight times the Python cost of reusing one.

Part 4 — Prefetching and N+1 🔴 Advancedالجزء 4 — الـ prefetching والـ N+1

English

A recordset carries a prefetch set: the ids it was born with. Reading one field on one record loads that field and the other prefetchable columns for every id in the set, in one SELECT. So a plain loop over a recordset is already batched, and a Node developer's instinct to rewrite it with an explicit join is usually wasted work. Records reached through a relation inherit a prefetch set too, which is why r.partner_id.name in a loop costs one more query in total, not one per row.

You lose this in two main ways: building a fresh recordset per id with browse(id), whose prefetch set contains only that id, and running a query per row with search or search_count. On 50 records the plain loop took 2 queries, browse per id took 100 (a row and its partner each time), and search_count in a loop took 51. On 3,000 records the plain iteration was still a single query.

Query counts are stable across runs, which makes them a far better regression test than timing. assertQueryCount fails the test when the number grows. Lock in the count for any hot path, and the next person to add a query in a loop gets a red build.

Part 5 — Batch operations 🔴 Advancedالجزء 5 — الـ batch operations

English

Writes batch through two mechanisms. create with a list inserts in multi-row statements, and write on a recordset groups rows into a few UPDATEs. Separately, the ORM delays writes: assigning a field costs zero queries, and the value sits in the cache marked dirty until a flush.

A flush happens automatically before a search on the affected fields and at commit, and on demand with env.flush_all() or record.flush_recordset(). Invalidation is the opposite direction: invalidate_recordset() and env.invalidate_all() drop cached values so the next read returns to the database. Reach for both rarely and on purpose. A flush_all() inside a loop destroys the batching you just got, as the second row below shows.

Exit test question 5 starts here: "a report is slow, how do you find why?" The first move is to count queries before you read any code. Then read the SQL, run EXPLAIN, fix it, and lock the count. Lesson 26 continues it with the profiler.

Part 6 — Raw SQL 🔴 Advancedالجزء 6 — الـ Raw SQL

English

Use raw SQL for reporting queries the ORM can't express (window functions, CTEs), set-based bulk updates, and data migrations. Everything else stays in the ORM, because raw SQL steps outside it. It skips access checks: a demo user saw 0 rows through the ORM and 1 through raw SQL. It skips the cache in both directions: an UPDATE leaves the record showing the old value until you invalidate, and a SELECT can't see a pending ORM write until you flush. It also skips recompute: after a raw update to a line, the stored total stayed wrong and write_date didn't move, so anything polling write_date misses the change (lesson 28).

A correct raw update has three steps: flush the columns you touch, run the statement, then invalidate and call modified() so stored computes follow. env.execute_query(SQL(...)) flushes for you when the SQL declares its fields through to_flush.

Always build queries with SQL('... %s', value) from odoo.tools and SQL.identifier() for names, so values travel as parameters. Nothing stops an f-string at runtime: SQL(f"...") constructed without error in the lab, since the protection is a LiteralString type hint and a lint rule. Keep user input out of the format string (section 13 · injection). And measure before you drop to raw: a 10,000-row update took ≈0.55 s through the ORM and ≈0.31 s raw, less than a factor of two, which rarely pays for losing everything above.

الـ raw update الصح ليه تلات خطوات: flush للأعمدة اللي هتلمسها، تشغّل الـ statement، وبعدين invalidate ونادي modified() عشان الـ stored computes تتحدّث. وenv.execute_query(SQL(...)) بيعمل flush لوحده لما الـ SQL يعلن عن حقوله بـ to_flush.

ابني الـ queries دايمًا بـ SQL('... %s', value) من odoo.tools وSQL.identifier() للأسماء، عشان القيم تروح كـ parameters. ومفيش حاجة بتوقف f-string وقت التشغيل: SQL(f"...") اتبنى من غير error في الـ lab، لأن الحماية type hint اسمه LiteralString وقاعدة lint. خلّي input المستخدم بره الـ format string (القسم 13 · injection). وقيس قبل ما تنزل للـ raw: update على 10,000 صف خد حوالي 0.55 ثانية بالـ ORM وحوالي 0.31 بالـ raw، أقل من الضعف، وده نادرًا ما يستاهل تخسر كل اللي فوق.

فين هستخدمه في شغلي؟ Aging report بـ window functions على مليون move line: raw SQL بـ SQL()، بس الأول حدد الشركات بإيدك في الـ WHERE لأن الـ access rules مش هتشتغل، ومن غير الشرط ده هتسرّب بيانات شركة لشركة. وفي migration بيصلّح عمود على 5 مليون صف: raw في batches، وبعدها modified أو recompute مقصود للحقول المعتمدة عليه.
Trade-off: raw SQL or _read_group? For sums and counts by a key, _read_group gives you one query with access rules applied. Reach for raw SQL when you need window functions, recursive CTEs or joins the domain language can't state, and accept that you now own security, flush and invalidation.
للـ sums والـ counts حسب مفتاح، _read_group بيديك query واحدة والـ access rules مطبقة. انزل للـ raw SQL لما تحتاج window functions أو recursive CTEs أو joins الـ domain مش بيعرف يقولها، واعرف إنك بقيت مسؤول عن الأمان والـ flush والـ invalidation.

Common mistakes · غلطات شائعة

❌ browse inside the loop 
# كل browse بيبدأ prefetch set جديد: 100 query
names = [Refund.browse(i).partner_id.name for i in ids]
✅ One recordset 
# الـ recordset الواحد بيتقرا في batches: 2 query
names = [r.partner_id.name for r in Refund.browse(ids)]
بالعامية

❌ browse(i) جوه الـ loop بيعمل recordset فيه id واحد، فالـ prefetching بيجيب صف صف: 100 query لـ 50 record. ✅ browse(ids) مرة واحدة بره الـ loop: 2 query.

❌ Unscoped sudo 
# بيرجع refunds من كل الشركات: [1, 4]
found = model.sudo().search([('id', 'in', ids)])
✅ Scope it yourself 
# الشرط بيرجّع اللي كان الـ access rule بيعمله: [1]
found = model.sudo().search([
    ('id', 'in', ids),
    ('company_id', 'in', model.env.companies.ids),
])
بالعامية

❌ الـ sudo() بيشيل قيود الشركات، فالمستخدم يشوف data شركة تانية (طلع [1, 4] لمستخدم مسموحله بالشركة 1 بس). ✅ لو محتاج الـ sudo، حط شرط الشركة بإيدك في الـ domain (طلع [1]).

❌ Raw update, then carry on 
# الـ cache قديم، والـ total مش هيتحسب
cr.execute(SQL('UPDATE erp_lab_refund_line SET amount = %s WHERE id = %s', 77, line.id))
print(line.refund_id.total)
✅ Flush, execute, invalidate, notify 
line.flush_recordset(['amount'])
cr.execute(SQL('UPDATE erp_lab_refund_line SET amount = %s WHERE id = %s', 77, line.id))
line.invalidate_recordset(['amount'])
# الـ modified بتعلّم الحقول المعتمدة عشان تتحسب تاني
line.modified(['amount'])
بالعامية

❌ بعد الـ UPDATE الـ ORM لسه فاكر القيمة القديمة، والـ total الـ stored فضل 10 والـ line 77. ✅ flush_recordset الأول، وبعد الـ statement invalidate_recordset وmodified، فالـ total بقى 77.

❌ Values in the format string 
# القيمة بقت جزء من نص الـ SQL
cr.execute(f"SELECT id FROM erp_lab_refund WHERE name = '{name}'")
✅ Parameters through SQL 
# القيمة بتروح لوحدها كـ parameter
cr.execute(SQL('SELECT id FROM erp_lab_refund WHERE name = %s', name))
بالعامية

❌ الـ f-string بيخلّي القيمة جزء من نص الـ query، وأي اسم فيه apostrophe زي O'Brien هيكسرها، وده نفس باب الـ SQL injection. ✅ SQL('... %s', name) بيبعت القيمة منفصلة عن الكود.

❌ A new context value per record 
# الـ compute بيتنادى لكل record على الكل: 2,500 حساب
for rec in records:
    rec.with_context(display_currency=f'C{rec.id}').label_in_context
✅ Switch once, outside the loop 
# الـ context واحد: نداء واحد على 50 record
in_egp = records.with_context(display_currency='EGP')
for rec in in_egp:
    rec.label_in_context
بالعامية

❌ على حقل depends_context، كل قيمة context خانة cache جديدة، فالـ compute بيشتغل 50 مرة على الـ 50 record: 2,500 حساب. ✅ بدّل الـ context مرة واحدة بره الـ loop: نداء واحد و50 حساب.

def line_counts_slow(self):

Solution · الحل 
def line_counts_fast(self):
    # صح: query واحدة بتجمّع في Postgres
    groups = self.env['erp_lab.refund.line']._read_group(
        [('refund_id', 'in', self.ids)], ['refund_id'], ['__count'],
    )
    counts = {refund.id: count for refund, count in groups}
    return {rec_id: counts.get(rec_id, 0) for rec_id in self.ids}

def test_line_counts_is_one_query(self):
    refunds = self.env['erp_lab.refund'].create([
        {'partner_id': self.partner.id, 'line_ids': [Command.create({'amount': 1})]}
        for _ in range(30)
    ])
    self.env.flush_all()
    self.env.invalidate_all()
    with self.assertQueryCount(1):
        counts = refunds.line_counts_fast()
    self.assertEqual(set(counts.values()), {1})

line_counts_fast: queries 1 {2}

3. A correct bulk update 🔴 hard Write bulk_set_amount(amount) on erp_lab.refund.line using one raw UPDATE. After it runs, amount, the parent's stored total and write_date must all be correct. Prove it with a test.

Hint · تلميح Three things are skipped by raw SQL here: the cache, the recompute and the audit columns.

Solution · الحل 
def bulk_set_amount(self, amount):
    # (1) أي كتابة معلّقة على العمود لازم توصل الـ database الأول
    self.flush_recordset(['amount'])
    self.env.cr.execute(SQL(
        """UPDATE erp_lab_refund_line
              SET amount = %s, write_uid = %s, write_date = %s
            WHERE id = ANY(%s)""",
        amount, self.env.uid, self.env.cr.now(), self.ids,
    ))
    # (2) الـ cache عنده القيم القديمة، فنشيلها
    self.invalidate_recordset(['amount', 'write_uid', 'write_date'])
    # (3) بنقول للـ ORM إن amount اتغير عشان total يتحسب تاني
    self.modified(['amount'])

Cheat sheet · الخلاصة

  • _inherit alone edits the model in place. super() walks a chain built from every installed module.
  • _inherit + new _name copies the definition into a new table. Fine for abstract mixins; a copied One2many breaks.
  • _inherits delegates storage: two rows, shared fields, used by res.users and product.product.
  • sudo() keeps env.user and crosses company limits, so scope the records yourself.
  • company_dependent is one jsonb column keyed by company id; read it under with_company.
  • Switching env in a loop keeps prefetching for normal fields. browse(id) and depends_context are what hurt.
  • A recordset batches reads: 2 queries for 50 records, against 100 with browse per id and 51 with search per row.
  • Lock hot paths with assertQueryCount: counts are stable, timings aren't.
  • create(list) and write on a recordset. Never flush inside a loop.
  • Raw SQL skips access, cache, recompute and write_date: flush, execute, invalidate, modified().
  • SQL('... %s', value) always. An f-string isn't refused at runtime.
  • Slow report: reproduce, count queries, read SQL, EXPLAIN, fix, lock.
بالعامية
  • _inherit لوحده بيعدّل الموديل في مكانه، وsuper() بيمشي في سلسلة متبنية من كل الـ modules المتسطبة.
  • _inherit مع _name جديد بينسخ التعريف في جدول جديد. كويس للـ abstract mixins، والـ One2many المنسوخ بيبوظ.
  • _inherits بيفوّض التخزين: صفين وحقول مشتركة، وبيستخدمه res.users وproduct.product.
  • sudo() بيسيب env.user وبيعدّي حدود الشركات، فحدد الـ records بإيدك.
  • company_dependent عمود jsonb واحد بمفتاح الـ company id، واقراه تحت with_company.
  • تبديل الـ env في loop بيحافظ على الـ prefetching للحقول العادية. اللي بيضر browse(id) وdepends_context.
  • الـ recordset بيجمّع القراءة: 2 queries لـ 50 record، قصاد 100 بـ browse لكل id، و51 بـ search لكل صف.
  • ثبّت الـ hot paths بـ assertQueryCount: العدد ثابت، والوقت لأ.
  • create(list) وwrite على recordset. ومتعملش flush جوه loop أبدًا.
  • الـ raw SQL بيتخطّى الـ access والـ cache والـ recompute وwrite_date: flush، تنفيذ، invalidate، modified().
  • SQL('... %s', value) دايمًا. الـ f-string مش بيترفض وقت التشغيل.
  • report بطيء: reproduce، عد الـ queries، اقرا الـ SQL، EXPLAIN، صلّح، ثبّت.
