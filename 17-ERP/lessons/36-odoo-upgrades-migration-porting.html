Why this matters · ليه ده مهم

English

Every customization you ship is a debt collected at the next major version, and Odoo ships one every fall. In this lesson a field rename with no script silently destroyed 1,000 values, and Odoo reported success. A failed upgrade left one module upgraded and the other not, while /web/health still said pass. Upgrades are where a Senior earns the title: knowing what can't be undone, proving the money didn't move, and being able to say "no-go" with evidence.

بالعامية

كل customization بتسلّمه دين هيتحصّل في الـ major version الجاية، و Odoo بينزّل واحدة كل خريف. في الدرس ده rename لحقل من غير script مسح 1,000 قيمة في صمت و Odoo قال نجاح. و upgrade فاشل ساب module متحدّث والتاني لأ، و /web/health لسه بيقول pass. الـ upgrades هي المكان اللي الـ Senior بيستاهل فيه اللقب: يعرف إيه اللي مبيرجعش، ويثبت إن الفلوس متحركتش، ويقدر يقول "no-go" بدليل.

Part 1 — The cycle 🔴 Advancedالجزء 1 — دورة الإصدارات والدعم

English

Odoo releases a major version each fall; 20.0 came out on 24 September 2026. Per the official support page, every major version gets three years of standard support, on Online, Odoo.sh and on-premise. Extended support follows for an additional fee: on Odoo.sh for a limited number of versions, on-premise for any version. Security updates exist only during standard support; extended support includes helpdesk and bug fixes "where technically feasible". SaaS versions such as 19.4 appear every two to three months on Online only.

You can upgrade from any version to any major version still under standard support, or one whose standard support ended less than six months ago. That six-month rule is about the target, not your source. How forced you are depends on hosting: Online majors must upgrade every two years; on Odoo.sh you get two more years after the three; on-premise can stay indefinitely, which is allowed and is usually how the security debt builds.

Today (November 2026) a customer on 17.0 is already outside standard support: it ended in September 2026. They get no more security fixes unless they move. And cost isn't uniform: configuration travels with the database and only needs testing, customization is code you port at every version, and integration is a contract with something outside Odoo that can be retired under you (/xmlrpc and /jsonrpc are scheduled for removal in Odoo 22).

function monthsBetween(from: string, to: string): number {
  const [fy = 0, fm = 0] = from.split("-").map(Number);
  const [ty = 0, tm = 0] = to.split("-").map(Number);
  return (ty - fy) * 12 + (tm - fm);
}

export function status(v: Version, today: string): string {
  const left = monthsBetween(today, v.standardEnd);
  if (left >= 0) return `standard support, ${left} months left, valid upgrade target`;
  const past = -left;
  // الهدف: ينفع تطلع لـ version خلص دعمها من أقل من 6 شهور بس
  const target = past < 6 ? "still a valid upgrade target" : "no longer a valid upgrade target";
  return `extended only (paid, no security updates), ended ${past} months ago, ${target}`;
}

بالعامية

Odoo بينزّل major version كل خريف، و 20.0 نزلت 24 سبتمبر 2026. حسب صفحة الدعم الرسمية، كل major version ليها 3 سنين standard support على Online و Odoo.sh و on-premise. بعدها extended support بفلوس زيادة: على Odoo.sh لعدد محدود من الـ versions، وعلى on-premise لأي version. الـ security updates موجودة في الـ standard بس، والـ extended فيه helpdesk و bug fixes "لو ينفع تقنيًا". والـ SaaS versions زي 19.4 بتنزل كل شهرين تلاتة على Online بس.

تقدر تعمل upgrade من أي version لأي major version لسه في الـ standard support، أو خلص دعمها من أقل من 6 شهور. قاعدة الـ 6 شهور دي عن الهدف مش عن اللي إنت عليه. ومدى الإجبار حسب الاستضافة: Online الـ major لازم يتعمله upgrade كل سنتين، Odoo.sh بياخد سنتين زيادة بعد التلاتة، و on-premise ينفع يفضل للأبد، وده مسموح وعادةً ده اللي بيراكم الدين الأمني.

النهارده (نوفمبر 2026) العميل اللي على 17.0 بره الـ standard support خلاص، خلصت في سبتمبر 2026، ومفيش security fixes غير لو اتحرك. والتكلفة مش واحدة: configuration بيتنقل مع الـ database ومحتاج اختبار بس، customization كود بتنقله كل version، و integration عقد مع حاجة بره Odoo ممكن تتشال من تحتك (/xmlrpc و /jsonrpc مجدولين للإزالة في Odoo 22).

فين هستخدمه في شغلي؟ لما تكتب proposal لعميل عايز customization، حط سطر تكلفة سنوية للـ upgrade مش تكلفة البناء بس. مثال: عميل على 17.0 on-premise بيقولك "شغال ومش عايز نلمسه": ورّيه إنه من سبتمبر مفيش security patches، وخطة 17 → 19 أو 20 بجدول. الغلطة الشائعة: تحسب تكلفة الـ module مرة واحدة وتنسى إنها بتتكرر.
Interview question (exit test 3) "What's the difference between configuration, customization and integration, and what does each cost at upgrade?" → Configuration is data and travels with the database, so you only test it. Customization is your code, which you port and retest at every major version, and it's the expensive one because the cost recurs. Integration is a contract with an outside system: cheap while the API is stable, and a project of its own when the API is retired. So prefer them in that order.
"إيه الفرق بين configuration و customization و integration، وكل واحد بيكلف إيه عند الـ upgrade؟" ← الـ configuration بيانات بتتنقل مع الـ database، فبتختبرها بس. الـ customization كودك، بتنقله وتختبره كل major version، وده الغالي لأن التكلفة بتتكرر. الـ integration عقد مع نظام بره: رخيص طول ما الـ API ثابت، ومشروع لوحده لما الـ API يتشال. فالأفضلية بنفس الترتيب ده.

Part 2 — Upgrade service against OpenUpgrade 🔴 Advancedالجزء 2 — خدمة Odoo قصاد OpenUpgrade

English

Neither route is run here: this machine has one Odoo version, no Enterprise and no upgrade platform access. What follows comes from the docs and from reading the OpenUpgrade repository on 2026-11-11.

Odoo's upgrade service. You request an upgraded test database, test it, report problems, and repeat; then you request production. With Enterprise it's free, including support for discrepancies in standard apps. Test databases are neutralized. On Online, once a production upgrade completes "it is impossible to revert". On Odoo.sh a failure is reverted automatically and a backup is taken. Custom modules are the maintainer's job, and the docs are blunt: a database with custom modules "cannot be upgraded until a version of your custom modules is available for the target version".

OpenUpgrade. The OCA's community route, AGPL-3, for databases the Odoo service won't take, typically Community. It migrates one version at a time, so 17 to 20 is three runs. A 20.0 branch exists with openupgrade_scripts at 20.0.1.0.0, and that sounds finished. It isn't: on the date we checked, the branch has no per-module scripts at all, and tracking issue #6044 still lists base, mail, the analysis tooling and the framework as open. The 19.0 branch has scripts for 332 modules. So read per-module coverage before promising anything, and check it again when you actually plan the work.

// الفكرة: قبل ما توعد عميل بـ OpenUpgrade، اقرا الـ coverage الفعلي للـ modules بتاعته
const BRANCH_FILE = "https://raw.githubusercontent.com/OCA/OpenUpgrade/19.0/docsource/modules180-190.rst";
const MY_MODULES = ["account", "sale", "stock", "purchase", "mrp", "point_of_sale", "l10n_eg", "l10n_sa"];

interface Row {
  module: string;
  status: string;
}

export function parse(rst: string): Row[] {
  const rows: Row[] = [];
  let current: Row | null = null;
  for (const line of rst.split("\n")) {
    if (!line.startsWith("|")) {
      current = null;
      continue;
    }
    const [, first = "", second = ""] = line.split("|");
    const module = first.trim();
    const status = second.trim();
    if (module && !module.startsWith("Module")) {
      current = { module: module.replace(/\\/g, ""), status };
      rows.push(current);
    } else if (current && status) {
      current.status = `${current.status} ${status}`.trim();
    }
  }
  return rows;
}

Part 3 — Migration scripts 🔴 Advancedالجزء 3 — سكريبتات pre و post و end

English

A script is a Python file at migrations/<version>/{pre,post,end}-*.py (or under upgrades/) that exposes def migrate(cr, version), where version is the installed one. pre runs before the module loads, so the new schema doesn't exist yet. post runs after the module and its dependencies are updated. end runs after all modules. Within a phase, files run in lexical order. A script only runs if its folder's version is higher than the installed version and no higher than the new one, so no version bump means no script (real: a second -u ran nothing). A 0.0.0 folder runs on any version change.

Renaming a field shows why this matters. Odoo has no idea a rename happened. It sees one field disappear and another appear, so it creates an empty column, then at the end of the update it deletes the old field and drops its column. We renamed carrier_ref to tracking_ref on 1,000 rows with no script. Exit status 0. Result: 0 of 1,000 filled, and the old column gone. That data is only in your backup.

The fix is a pre script that renames the column before Odoo looks, plus the two metadata rows so that the field keeps its identity. It must be pre: by post the empty column already exists. On a live system that can't take a maintenance window, the expand/contract pattern from section 09 is the alternative: add, backfill, switch, drop later.

_logger = logging.getLogger(__name__)


def migrate(cr, version):
    # العمود: قبل ما Odoo يشوف الموديل، عشان ميعملش عمود فاضي
    cr.execute('ALTER TABLE ship_good_parcel RENAME COLUMN carrier_ref TO tracking_ref')

بالعامية

الـ script ملف Python في migrations/<version>/{pre,post,end}-*.py (أو تحت upgrades/) وفيه def migrate(cr, version)، و version هي المتسطبة حاليًا. pre بيشتغل قبل تحميل الموديول، فالـ schema الجديد لسه مش موجود. post بعد ما الموديول واللي معتمد عليهم يتحدثوا. end بعد كل الموديولات. وجوه المرحلة الواحدة الملفات بتشتغل بالترتيب الأبجدي. الـ script بيشتغل بس لو version الفولدر أعلى من المتسطبة ومش أعلى من الجديدة، يعني من غير version bump مفيش script (جربناها: -u تاني مشغّلش حاجة). وفولدر 0.0.0 بيشتغل مع أي تغيير version.

الـ rename بيوضح ليه ده مهم: Odoo مش عارف إن فيه rename. هو شايف حقل اختفى وحقل ظهر، فبيعمل عمود فاضي، وفي آخر الـ update بيمسح الحقل القديم ويعمل DROP لعموده. غيّرنا carrier_ref لـ tracking_ref على 1,000 صف من غير script. الـ exit status صفر. والنتيجة: 0 من 1,000 متعبيين والعمود القديم راح. الداتا دي بقت في الـ backup بس.

Part 5 — Strategy 🔴 Advancedالجزء 5 — الاستراتيجية: test database و diff

English

The sequence is: copy production, neutralize, upgrade, run the test suite, diff the schema, diff the data, then let real users test. Neutralizing comes first because a copy of production will otherwise email your customers and post to live APIs. odoo-bin neutralize -c conf -d db did it for real: active crons went from 39 to 1 (only autovacuum survives), mail servers were disabled with their credentials dropped, and a dummy one was inserted so that no fallback server is used. --stdout prints the SQL for review.

Diff schema and data, not screens. The script below snapshots information_schema, row counts, invoice totals, and a per-account trial balance, then compares. Schema changes are expected; any change to money or row counts is blocking. On a clean upgrade it reported 1 schema change and 0 blocking differences. Then we shipped a plausible bug, a migration that "cleans up" tax lines by rounding them, with exit status 0. The diff found 7 blocking differences. Note the first version of this script keyed on account code, which is stored per company, so nulls collided and it raised false alarms. Test your safety net too.

Rehearse at least twice: the docs recommend repeating close to go-live because both the upgrade scripts and your data keep moving. Then time the run, since that time is your maintenance window.

// الأمان: لازم الـ port يبقى صريح، ومفيش رجوع للـ default بتاع Postgres
function guardPort(raw: string | undefined): number {
  const n = Number(raw);
  if (!/^\d+$/.test(String(raw)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port ${raw}`);
  }
  return n;
}

type Row = Record<string, string>;
interface Snapshot {
  columns: string[];
  counts: Record<string, number>;
  invoices: Row[];
  trialBalance: Row[];
}

const COUNTED = ["res_partner", "account_move", "account_move_line", "product_template", "stock_move", "ir_attachment", "mail_message"];

export async function snapshot(port: number, database: string): Promise<Snapshot> {
  const client = new pg.Client({ host: "127.0.0.1", port: guardPort(String(port)), user: "odoo_lab", database });
  await client.connect();
  try {
    const columns = await client.query<{ c: string }>(`
      SELECT table_name || '.' || column_name || ':' || data_type AS c
      FROM information_schema.columns
      WHERE table_schema = 'public'
      ORDER BY 1`);
    const counts: Record<string, number> = {};
    for (const table of COUNTED) {
      const r = await client.query<{ n: string }>(`SELECT count(*) AS n FROM ${table}`);
      counts[table] = Number(r.rows[0]?.n);
    }
    const invoices = await client.query<Row>(`
      SELECT company_id::text, move_type, state, count(*)::text AS n,
             sum(amount_total_signed)::numeric(16, 2)::text AS total
      FROM account_move
      GROUP BY 1, 2, 3
      ORDER BY 1, 2, 3`);
    // ليه: account_id مش code، لأن الكود متخزن لكل شركة وممكن يطلع NULL فالـ keys تتصادم
    const trialBalance = await client.query<Row>(`
      SELECT company_id::text, account_id::text,
             sum(debit)::numeric(16, 2)::text AS debit,
             sum(credit)::numeric(16, 2)::text AS credit
      FROM account_move_line
      WHERE parent_state = 'posted'
      GROUP BY 1, 2
      ORDER BY 1, 2`);
    return { columns: columns.rows.map((r) => r.c), counts, invoices: invoices.rows, trialBalance: trialBalance.rows };
  } finally {
    await client.end();
  }
}

// المنطق: تغيير الـ schema متوقع بعد upgrade، أما أي تغيير في الفلوس أو عدد الصفوف فبيوقف الـ go-live
export function diff(before: Snapshot, after: Snapshot): { expected: string[]; blocking: string[] } {
  const expected: string[] = [];
  const blocking: string[] = [];
  const a = new Set(before.columns);
  const b = new Set(after.columns);
  for (const c of a) if (!b.has(c)) expected.push(`- column ${c}`);
  for (const c of b) if (!a.has(c)) expected.push(`+ column ${c}`);
  for (const [table, n] of Object.entries(before.counts)) {
    if (after.counts[table] !== n) blocking.push(`rows ${table}: ${n} -> ${after.counts[table]}`);
  }
  const key = (r: Row, fields: string[]) => fields.map((f) => r[f]).join("|");
  const compare = (name: string, xs: Row[], ys: Row[], fields: string[]) => {
    const map = new Map(ys.map((r) => [key(r, fields), r]));
    for (const x of xs) {
      const y = map.get(key(x, fields));
      map.delete(key(x, fields));
      if (!y) blocking.push(`${name} ${key(x, fields)}: missing after upgrade`);
      else if (JSON.stringify(x) !== JSON.stringify(y)) blocking.push(`${name} ${key(x, fields)}: ${JSON.stringify(x)} -> ${JSON.stringify(y)}`);
    }
    for (const k of map.keys()) blocking.push(`${name} ${k}: new after upgrade`);
  };
  compare("invoices", before.invoices, after.invoices, ["company_id", "move_type", "state"]);
  compare("trial balance", before.trialBalance, after.trialBalance, ["company_id", "account_id"]);
  return { expected, blocking };
}

Part 6 — Rollback 🔴 Advancedالجزء 6 — الـ rollback الحقيقي

English

There is no downgrade. Rollback means restoring the pre-upgrade backup, database and filestore together. Once users work on the new version, restoring discards their work, so the real decision point is before you reopen. See section 09 · backups and lesson 34.

We rehearsed it: dump, upgrade two modules where the second fails in post, restore, verify. A failed -u is not atomic across modules. Odoo commits after each module, so roll_a stayed upgraded to 20.0.1.1.0 with its new column, while roll_b rolled back to 20.0.1.0.0, including its pre rename and the 100 rows its post had updated. The log says Failed to load registry, and the process exits non-zero.

Worse, the database is now out of step with the code on disk, and the server still starts. /web/health answered pass, db_server_status was true, /web/login returned 200, and an ORM read of the model raised UndefinedColumn. A load balancer would have put that node in rotation. So never reopen after a failed upgrade without restoring. In our run the dump took ≈13.7 s and the restore ≈13.8 s for 22 MB; on your data, measure it, because that number decides whether a rollback fits inside the window.

بالعامية

مفيش downgrade. الـ rollback يعني ترجّع الـ backup اللي قبل الـ upgrade، الـ database والـ filestore مع بعض. ولما المستخدمين يشتغلوا على الـ version الجديدة، الـ restore بيضيّع شغلهم، فنقطة القرار الحقيقية قبل ما تفتح النظام. راجع section 09 · backups و الدرس 34.

عملنا rehearsal: dump، upgrade لموديولين التاني بيقع في post، restore، تحقق. الـ -u الفاشل مش atomic عبر الموديولات. Odoo بيعمل commit بعد كل module، فـ roll_a فضل متحدّث على 20.0.1.1.0 بعموده الجديد، و roll_b رجع لـ 20.0.1.0.0، ومعاه الـ rename بتاع pre والـ 100 صف اللي post عدّلهم. الـ log بيقول Failed to load registry والـ process بيخرج بـ status مش صفر.

والأسوأ إن الـ database بقت مش متوافقة مع الكود اللي على الديسك، و السيرفر لسه بيقوم. /web/health رد pass، و db_server_status كانت true، و /web/login رجّع 200، وقراية الموديل من الـ ORM وقعت بـ UndefinedColumn. يعني load balancer كان هيدخّل الـ node دي في الخدمة. فمتفتحش أبدًا بعد upgrade فاشل من غير restore. عندنا الـ dump أخد ≈13.7 ثانية والـ restore ≈13.8 لـ 22MB. على داتاك قيس بنفسك، لأن الرقم ده بيحدد الـ rollback هيدخل في الـ window ولا لأ.

فين هستخدمه في شغلي؟ ليلة go-live: معاك جدول go/no-go مطبوع، و dump متعمله restore الصبح، و runbook فيه وقت نهائي: "لو الساعة 3 الفجر ومخلصناش، هنرجّع". وبعد الـ restore تشغّل نفس الـ diff عشان تثبت إنك رجعت للنقطة الصح. الغلطة الشائعة: تعتمد على /web/health كدليل نجاح، وهو بيقول pass على database نص متحدّثة.
What breaks: partial upgrade plus reopen If someone reopens after a failed -u and users work for an hour, you now have new data on a half-upgraded schema, and no backup contains it. Restoring loses the hour, and keeping it means hand repair. Block access first: stop the service or the proxy before the upgrade starts, and don't lift the block until the diff passes.
لو حد فتح النظام بعد -u فاشل والمستخدمين اشتغلوا ساعة، بقى عندك داتا جديدة على schema نص متحدّث، ومفيش backup فيه الداتا دي. الـ restore بيضيّع الساعة، والاحتفاظ بيها معناه تصليح يدوي. اقفل الوصول الأول: وقّف الخدمة أو الـ proxy قبل ما الـ upgrade يبدأ، ومتفتحش غير لما الـ diff ينجح.

Solution · الحل 
type TrialRow = { company_id: string; debit: string; credit: string };

// الـ invariant: لكل شركة، مجموع المدين لازم يساوي مجموع الدائن بالقرش
export function unbalanced(rows: TrialRow[]): string[] {
  const cents = (s: string) => Math.round(Number(s) * 100);
  const byCompany = new Map<string, number>();
  for (const r of rows) {
    byCompany.set(r.company_id, (byCompany.get(r.company_id) ?? 0) + cents(r.debit) - cents(r.credit));
  }
  return [...byCompany].filter(([, diff]) => diff !== 0).map(([id, diff]) => `company ${id} off by ${diff / 100}`);
}

  { company_id: "2", debit: "50.01", credit: "50.00" },
]));
// → [ 'company 2 off by 0.01' ]

Cheat sheet · الخلاصة

  • Major version each fall; 3 years standard; then paid extended with no security updates. 17.0 left standard support in September 2026.
  • Valid upgrade target: under standard support, or ended less than 6 months ago.
  • Upgrade cost: configuration < integration (while the API lives) < customization.
  • Odoo's service: Enterprise, test then production, no revert on Online. OpenUpgrade: one version per run, and check per-module coverage; its 20.0 branch had no module scripts on 2026-11-11.
  • pre old schema, post new schema, end after all modules. No version bump, no script.
  • Rename without pre: new empty column, old column dropped, exit status 0.
  • Porting: upgrade_code --script on a git copy, one at a time. Exit 1 means files changed. Windows: PYTHONUTF8=1, watch CRLF.
  • By hand: set_param → set_str, groups_id → group_ids, read_group → formatted_read_group, static props → useProps.
  • Strategy: copy, neutralize, upgrade, tests with a count, diff schema and money, users, go/no-go.
  • No downgrade. Rollback is a restore of database and filestore together, and users' later work is lost.
  • A failed -u commits module by module, the server still starts, and /web/health says pass. Block access until the diff passes.
بالعامية
  • Major version كل خريف، 3 سنين standard، وبعدها extended بفلوس ومن غير security updates. الـ 17.0 خرجت من الـ standard في سبتمبر 2026.
