Why this matters · ليه ده مهم

English

In Odoo you rarely write a page. You describe one in XML, store that description as a database row, and let a generic web client turn it into a screen. Almost every customization a client pays for ends up here: a new column, a hidden field, a button that only appears on drafts, a bulk action on 500 selected invoices.

A Node developer's instinct gets two things wrong in this layer. First, a readonly or groups attribute in a view looks like a rule, but it only shapes the screen, so an API call walks straight past it. Second, a view can pass install and still crash in the browser. This lesson runs both against real Odoo 20, using the erp_lab.refund model from the ORM lessons.

بالعامية

في Odoo إنت نادرًا ما بتكتب صفحة. إنت بتوصفها في XML، الوصف ده بيتخزن كـ row في الـ database، و web client عام بيحوّله لشاشة. أغلب الـ customization اللي العميل بيدفع فيها بتيجي هنا: column جديد، field مخفي، زرار بيظهر على الـ drafts بس، أو bulk action على 500 فاتورة متعلّمين.

غريزة الـ Node developer بتغلط في حاجتين في الطبقة دي. الأولى: readonly أو groups في الـ view شكلهم قاعدة، بس هما بيشكّلوا الشاشة بس، فأي API call بيعدّي من جنبهم عادي. التانية: الـ view ممكن يعدّي الـ install وبرضه يقع في المتصفح. الدرس ده بيجرّب الاتنين على Odoo 20 حقيقي، على الـ model بتاع erp_lab.refund اللي من دروس الـ ORM.

Part 1 — The seven views 🟡 Intermediateالجزء 1 — الـ views السبعة

English

A view is data. Each one is a row in ir.ui.view with a type, a model and an XML arch. When the web client opens a screen it asks the server for the views it needs, and the server returns each arch after applying inheritance and access rights. Models and fields are covered in lesson 14; here is the slice of erp_lab.refund the views below rely on.

class RefundRequest(models.Model):
    _name = 'erp_lab.refund'
    _description = 'Refund request'
    _inherit = ['mail.thread']
    _order = 'id desc'

    name = fields.Char(required=True, tracking=True)
    partner_id = fields.Many2one('res.partner', required=True)
    company_id = fields.Many2one('res.company', required=True, default=lambda self: self.env.company)
    currency_id = fields.Many2one(related='company_id.currency_id')
    request_date = fields.Date(required=True, default=fields.Date.context_today)
    state = fields.Selection(
        [('draft', 'Draft'), ('approved', 'Approved'), ('rejected', 'Rejected')],
        default='draft', required=True, tracking=True,
    )
    reason = fields.Char()
    tag_ids = fields.Many2many('erp_lab.refund.tag')
    line_ids = fields.One2many('erp_lab.refund.line', 'refund_id')
    # الـ aggregator بتاع Float هو sum، و store=True بيخليه يتجمع في SQL
    total = fields.Float(compute='_compute_total', store=True)
    # من غير store مفيش column، فمفيش aggregator
    total_live = fields.Float(compute='_compute_total_live')
    # مخفي من الـ view بس: الـ API لسه بيرجّعه
    internal_note = fields.Char()
    # محمي على الـ model نفسه: الـ ORM بيرفض يقراه
    risk_score = fields.Float(groups='base.group_system')
English

The root tag must match the view type. The table lists each root element as it appears in the 20.0 source, what it requires, and what it is for. <list> replaced <tree>, and kanban cards now live in a template named card. Pivot and graph measures need a field with an aggregator: numeric fields default to sum, but only when the value is stored in a column or has SQL behind it, because the aggregation runs in Postgres.

English

Because a view is a row, you can inspect it. Reading arch gives you the XML as one module wrote it. Calling get_view gives you the resolved view, with every inheriting view applied, which is what the browser really receives. When a screen looks wrong, compare those two before you read any JavaScript. Here is the real output after install: the extension's field appears in the resolved partner form and not in the base row.

بالعامية

الـ view هو data. كل واحد row في ir.ui.view فيه type وmodel وarch بالـ XML. لما الـ web client يفتح شاشة بيطلب الـ views اللي محتاجها، والـ server بيرجّع كل arch بعد ما يطبّق الـ inheritance والـ access rights.

الـ root tag لازم يطابق نوع الـ view. <list> حلّ محل <tree>، وكروت الـ kanban بقت في template اسمه card. الـ measures في الـ pivot والـ graph محتاجة field ليه aggregator: الـ fields الرقمية الافتراضي بتاعها sum، بس بشرط تكون القيمة stored في column أو ليها SQL، لأن التجميع بيحصل جوه Postgres.

وعشان الـ view هو row، تقدر تفتّشه. arch بيديك الـ XML زي ما الـ module كتبه. وget_view بيديك النسخة النهائية بعد كل الـ inheritance، ودي اللي المتصفح بيستلمها فعلًا. لو شاشة شكلها غلط، قارن الاتنين دول قبل ما تقرا أي JavaScript.

فين هستخدمه في شغلي؟ المحاسب بيقولك "الـ column بتاع الـ VAT اختفى من شاشة الفواتير بعد ما نزّلنا module جديد". بدل ما تدوّر في 10 modules، افتح odoo-bin shell واطبع get_view للـ view ده وقارنه بالـ arch الأصلي: هتعرف في ثانية مين شال الـ field. ولو طلب منك الـ finance تقرير شهري، <pivot> بـ 3 أسطر XML بيغنيك عن endpoint و chart library كاملين، بشرط الـ field يكون store=True.
Interview question "A stakeholder wants a monthly refund total in a pivot, but the field is computed. What do you check?" → Whether it is stored. Aggregation happens in SQL, so a non-stored compute has aggregator: False and nothing to sum. Add store=True with correct @api.depends, and plan the backfill on large tables.
"حد عايز إجمالي الـ refunds الشهري في pivot، بس الـ field computed. بتشيّك على إيه؟" ← هل هو stored. التجميع بيحصل في SQL، فالـ compute اللي مش stored الـ aggregator بتاعه False ومفيش حاجة تتجمع. ضيف store=True مع @api.depends صح، وخطط للـ backfill لو الجدول كبير.

Part 2 — XPath inheritance 🟡 Intermediateالجزء 2 — الـ inheritance بالـ XPath

English

You never edit another module's view. You create a new row with inherit_id, whose arch holds instructions: find a node with an XPath expression, then apply a position. This is the view-layer version of _inherit from lesson 16. On upgrade the base view gets replaced and your instructions are simply re-applied.

  • after / before: insert a sibling.
  • inside: append as the last child.
  • attributes: change attributes on the node and leave it in place.
  • replace: swap the node for your content, or delete it if your content is empty.
<odoo>
  <record id="partner_form_tier" model="ir.ui.view">
    <field name="name">res.partner.form.erp_lab_tier</field>
    <field name="model">res.partner</field>
    <field name="inherit_id" ref="base.view_partner_form"/>
    <field name="arch" type="xml">
      <!-- ضيف الـ field بعد الـ VAT من غير ما تلمس الـ view الأصلي -->
      <xpath expr="//field[@name='vat']" position="after">
        <field name="erp_lab_tier"/>
      </xpath>
    </field>
  </record>
</odoo>
<data>
  <xpath expr="//field[@name='name']" position="before"><field name="partner_id"/></xpath>
  <xpath expr="//field[@name='name']" position="after"><field name="request_date"/></xpath>
  <xpath expr="//group[@name='g']" position="inside"><field name="tag_ids"/></xpath>
  <xpath expr="//field[@name='state']" position="attributes"><attribute name="readonly">True</attribute></xpath>
  <xpath expr="//field[@name='reason']" position="replace"><field name="company_id"/></xpath>
</data>
English

Applied to <form><field name="name"/><field name="state"/><group name="g"><field name="reason"/></group></form>, those five instructions resolved to this (attributes added by the server are trimmed):

<form>
  <field name="partner_id"/>
  <field name="name"/>
  <field name="request_date"/>
  <field name="state" readonly="True"/>
  <group name="g">
    <field name="company_id"/>
    <field name="tag_ids"/>
  </group>
</form>
النتيجة: partner_id اتحط قبل name (before)، وrequest_date بعده (after)، وstate بقى عليه readonly (attributes)، وreason اتبدّل بـ company_id (replace)، وtag_ids اتضاف في آخر الـ group (inside).
English

replace is the fragile one. It removes a node other modules may be targeting. Module A deletes reason from the form and installs fine; module B then targets reason and its install aborts. Neither module is wrong on its own, and the failure shows up only when a customer installs both. This is the real failure:

    <field name="arch" type="xml">
      <!-- شيل reason من الـ form خالص -->
      <xpath expr="//field[@name='reason']" position="replace"/>
    </field>
    <field name="arch" type="xml">
      <!-- module تاني عايز يضيف placeholder على نفس الـ field -->
      <xpath expr="//field[@name='reason']" position="attributes">
        <attribute name="placeholder">Why is this refund needed?</attribute>
      </xpath>
    </field>
odoo.tools.convert.ParseError: while parsing file:/.../v.xml:2
Error while parsing or validating view:

Element '<xpath expr="//field[@name=&#39;reason&#39;]">' cannot be located in parent view
الـ error بيقول إن الـ xpath بتاع module التاني ملقاش الـ node في الـ view الأب، لأن module الأول شاله. والـ install بيقف كله.
English

The fix is to hide rather than remove. With position="attributes" the node stays in the tree, so other modules can still find it, and the user does not see it. Remember to clear any required at the same time, or the form demands a value for a field the user cannot reach. After this change both modules installed with exit status 0.

    <field name="arch" type="xml">
      <!-- الحل: الـ node يفضل موجود، بس المستخدم مبيشوفوش -->
      <xpath expr="//field[@name='reason']" position="attributes">
        <attribute name="invisible">True</attribute>
        <attribute name="required">False</attribute>
      </xpath>
    </field>
بالعامية

إنت عمرك ما بتعدّل view بتاع module تاني. بتعمل row جديد بـ inherit_id، والـ arch بتاعه فيه تعليمات: دوّر على node بـ XPath وطبّق position. ده نفس فكرة _inherit بس على مستوى الـ view. وقت الـ upgrade الـ view الأساسي بيتبدّل وتعليماتك بتتطبق تاني.

  • after وbefore: حط sibling بعد أو قبل الـ node.
  • inside: ضيف كآخر child جوه الـ node.
  • attributes: غيّر attributes والـ node يفضل مكانه.
  • replace: بدّل الـ node باللي عندك، أو امسحه لو الـ content فاضي.

replace هو الهش. بيشيل node ممكن modules تانية بتدوّر عليه. module أ بيمسح reason ويتنزّل عادي، module ب بيدوّر على reason والـ install بتاعه يقع. ولا واحد فيهم غلط لوحده، والمشكلة بتظهر بس لما العميل ينزّل الاتنين.

الحل إنك تخبّي بدل ما تشيل. بـ position="attributes" الـ node بيفضل في الشجرة، فالـ modules التانية تلاقيه، والمستخدم مبيشوفوش. افتكر تلغي أي required معاه، وإلا الـ form هيطلب قيمة لـ field المستخدم مش شايفه. بعد التعديل ده الاتنين اتنزّلوا بـ exit status 0.

فين هستخدمه في شغلي؟ العميل عايز يشيل "Payment Terms" من شاشة الـ sales order. لو عملت replace، أول ما حد ينزّل localization أو module بيعدّل نفس الـ field، الـ upgrade هيقع بالليل وقت الـ deploy. اعمل attributes وinvisible. وفي الـ code review، أي position="replace" على view مش بتاعك اسأل عنه. وخلّي الـ XPath بالاسم //field[@name='vat'] مش بالترتيب //group[2]/field[3]، لأن الترتيب بيتغير بين الـ versions.
Trade-off A hidden field is still loaded and sent to the browser, so invisible is not a way to keep data secret (see Part 4). And replace is fine in one case: on a view your own module owns, where you control who depends on it.
الـ field المخفي لسه بيتحمّل وبيتبعت للمتصفح، فـ invisible مش طريقة تخبّي بيها data سرية (بص الجزء 4). وreplace مقبول في حالة واحدة: على view الـ module بتاعك هو اللي مالكه، وإنت عارف مين معتمد عليه.

Part 3 — Actions and menus 🟡 Intermediateالجزء 3 — الـ actions والـ menus

English

A view does nothing until an action opens it. ir.actions.act_window says which model to show, which view types to offer (view_mode, first one is the default), a domain that always applies, a context for defaults and pre-enabled filters such as search_default_draft, and in recent versions a path that gives a readable URL like /odoo/refunds. A <menuitem> is a row in ir.ui.menu pointing at an action; one with no parent becomes a top-level app.

ir.actions.server runs server-side logic instead of showing a screen. With state="code" it evaluates Python in a restricted sandbox where env, model, record, records, log and UserError are available. Setting binding_model_id puts it in the Action menu of that model, and binding_view_types chooses list, form or both. Keep the body to one line that calls a model method: logic in a database string has no tests, no review and no stack trace pointing at a file.

Part 4 — Widgets, conditional attributes, groups 🟡 Intermediateالجزء 4 — الـ widgets والـ conditional attributes والـ groups

English

A widget overrides how one field renders. monetary formats a number with a currency (it supports monetary, float and integer fields and needs a currency field in the view), many2many_tags shows relations as colored pills, and statusbar turns a selection into the header pipeline. An unknown widget name does not fail: the view installs, the client logs a warning, and the field falls back to its default rendering.

Since Odoo 17 there is no attrs and no states. invisible, required, readonly and column_invisible take Python-like expressions directly, such as invisible="total == 0". The web client evaluates them in the browser against the current record, so they change as the user types. The old syntax now fails at install with Since 17.0, the "attrs" and "states" attributes are no longer used. A field named in an expression must exist on the model but does not have to be in the view: the server adds it for you, as <field name="state" invisible="True" readonly="True" data-used-by="…"/> in the resolved arch.

All of these are presentation. groups makes the difference clear because it can sit in two places. On a node in a view, the server strips the node from the arch for users outside the group, and the data stays readable. On a field definition in Python, the ORM itself refuses access. The experiment below uses a clerk with only base.group_user, calling the JSON-2 API with his own key.

Part 5 — Wizards 🟡 Intermediateالجزء 5 — الـ wizards

English

A wizard is a modal form backed by a models.TransientModel: a real Postgres table whose rows are temporary. A wizard row exists so that defaults, onchange and validation work like any form while the user fills it in, and then it is garbage. Auto-vacuum deletes rows older than transient_age_limit, 1 hour by default, and osv_memory_count_limit can cap the count (0 means unlimited). Rows touched in the last 5 minutes are never removed. Transient models still need an access entry, and a normal model cannot hold a Many2one to a transient one.

The flow: an action with target="new" opens the form in a dialog. When started from a list, the client puts active_model and active_ids in the context, and a field default reads them. The button calls a method that does the work on the real records and returns ir.actions.act_window_close.

from odoo import api, fields, models
from odoo.exceptions import UserError


class BulkApproveRefunds(models.TransientModel):
    _name = 'erp_lab.bulk.approve'
    _description = 'Bulk approve refunds'

    # الـ default بيقرا الـ selection من الـ context اللي الـ list باعته
    refund_ids = fields.Many2many('erp_lab.refund', default=lambda self: self._default_refund_ids())
    note = fields.Char(required=True)
    draft_count = fields.Integer(compute='_compute_draft_count')

    def _default_refund_ids(self):
        if self.env.context.get('active_model') != 'erp_lab.refund':
            return self.env['erp_lab.refund']
        return self.env['erp_lab.refund'].browse(self.env.context.get('active_ids', []))

    @api.depends('refund_ids.state')
    def _compute_draft_count(self):
        for wizard in self:
            wizard.draft_count = len(wizard.refund_ids.filtered(lambda refund: refund.state == 'draft'))

    def action_approve(self):
        self.ensure_one()
        drafts = self.refund_ids.filtered(lambda refund: refund.state == 'draft')
        if not drafts:
            raise UserError('Nothing to approve: the selection has no draft refund.')
        drafts.action_approve()
        for refund in drafts:
            refund.message_post(body=self.note)
        return {'type': 'ir.actions.act_window_close'}

فين هستخدمه في شغلي؟ "اعتمد كل الفواتير المعلّمة واكتب سبب واحد": ده wizard، مش صفحة ومش API. ولأن الـ row بيتمسح لوحده، متخزنش فيه أي حاجة محتاج ترجعلها: الـ audit لازم يروح في الـ chatter أو model عادي، زي ما عملنا بـ message_post. لو لسه بتفكر بعقلية Node: الـ wizard زي draft بيتخزن في Redis بـ TTL ساعة، بس الـ framework بيديلك الـ form والـ validation ببلاش.
What breaks at scale "Select all" across pages caps active_ids at web.active_ids_limit, 20,000 by default, and also sends active_domain. Everything in action_approve runs in one transaction, so 20,000 message_post calls hold row locks for the whole request and can hit the HTTP worker timeout. For big selections, have the wizard enqueue the work and process batches in a cron with _commit_progress (lesson 20).

Common mistakes · غلطات شائعة

❌ Old syntax from a pre-17 tutorial 
<tree>
  <field name="name"
    attrs="{'invisible': [('state','=','draft')]}"/>
</tree>
✅ What Odoo 20 accepts 
<list>
  <field name="name"
    invisible="state == 'draft'"/>
</list>
بالعامية

❌ أغلب الـ tutorials لسه بتكتب <tree> وattrs. الاتنين بيوقّعوا الـ install دلوقتي: الـ root لازم يبقى <list>، وattrs اتشال من 17.0. ✅ اكتب <list> والـ expression على طول في invisible.

❌ Trusting the view as a lock 
<!-- كده الـ API لسه يقدر يعدّل -->
<field name="name"
  readonly="state != 'draft'"/>
✅ Lock in the model too 
def write(self, vals):
    # القفل الحقيقي بيبقى هنا
    if 'name' in vals and any(r.state != 'draft' for r in self):
        raise UserError('Approved refunds are locked.')
    return super().write(vals)
بالعامية

❌ readonly في الـ view مش قفل: جرّبناها والـ API غيّر الاسم على refund معتمد. ✅ سيب الـ readonly عشان المستخدم، وحط القاعدة الحقيقية في write، عشان أي مسار (API، cron، import) يقف عندها.

❌ Removing a node you don't own 
<xpath expr="//field[@name='reason']"
       position="replace"/>
✅ Hide it and keep the node 
<xpath expr="//field[@name='reason']"
       position="attributes">
  <attribute name="invisible">True</attribute>
  <attribute name="required">False</attribute>
</xpath>
بالعامية

❌ replace فاضي بيمسح الـ node، وأي module تاني بيدوّر عليه الـ install بتاعه يقع. ✅ attributes بيخبّيه والـ node يفضل موجود. ومتنساش تلغي required.

❌ A measure with no column 
total_live = fields.Float(compute='_compute_total_live')
✅ Stored, so SQL can sum it 
total = fields.Float(compute='_compute_total', store=True)
بالعامية

❌ الـ field من غير store مالوش column، والـ aggregator بتاعه False. لما استخدمناه كـ measure، الـ client بعت total_live:false والـ server وقع، والمستخدم رجع لـ Discuss من غير رسالة. ✅ store=True بيدي الـ field column، والـ aggregator بيبقى sum.

❌ State that must survive, kept in a wizard 
class ApprovalLog(models.TransientModel):
    _name = 'erp_lab.approval.log'
    # هيتمسح بعد ساعة
    note = fields.Char()
✅ Wizard collects, real record keeps

❌ أي حاجة في TransientModel بتتمسح بعد ساعة، فـ audit log فيه يعني audit log بيختفي. ✅ الـ wizard بيجمّع المدخلات بس، والنتيجة الدايمة تروح في الـ chatter أو model عادي.

Cheat sheet · الخلاصة

  • A view is a row in ir.ui.view; arch is one module's XML and get_view is the resolved result.
  • Roots: list, form, kanban (t-name="card"), search, pivot, graph, calendar. <tree> and attrs fail at install.
  • Pivot and graph measures need an aggregator, so the field must be stored.
  • XPath positions: after, before, inside, attributes, replace. Prefer attributes plus invisible to removing nodes you don't own.
  • act_window opens views; domain is a filter and not security; path gives a stable URL.
  • ir.actions.server with binding_model_id lands in the Action menu. Keep the code to one method call.
  • invisible, required, readonly are browser hints evaluated on the client.
  • groups in a view hides the node; groups on the field makes the ORM refuse.
  • Wizards are TransientModel rows: 1 hour by default, need access entries, read active_ids, open with target="new".
  • Test wizards with Form, and always read the test count.
  • Install passing does not prove the screen works: check it in a browser and watch console errors.
  • Arabic RTL needs rtlcss on the server's PATH; without it Odoo serves the left-to-right CSS.

  • الـ view هو row في ir.ui.view؛ arch هو XML بتاع module واحد، وget_view هو النتيجة النهائية.
  • الـ roots: list وform وkanban (t-name="card") وsearch وpivot وgraph وcalendar. و<tree> وattrs بيوقّعوا الـ install.
  • الـ measures في الـ pivot والـ graph محتاجة aggregator، فالـ field لازم يبقى stored.
  • مواضع الـ XPath: after وbefore وinside وattributes وreplace. فضّل attributes مع invisible عن إنك تشيل nodes مش بتاعتك.
