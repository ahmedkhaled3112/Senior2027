Why this matters · ليه ده مهم

English

A duplicated row in a blog is a nuisance. A duplicated invoice is a wrong tax return, and a missed payment is a customer chased for money they've paid. Integrations between a shop and an ERP fail in exactly the places demos skip: the response that never arrives, the webhook sent while the receiver was restarting, the row committed late. This lesson reproduces each one against a real Odoo and fixes it, ending with a sync service that survives being killed at every step. It also answers exit test question 6: "a JSON-2 call failed after the write succeeded: how do you guarantee no duplicate?"

بالعامية

صف متكرر في blog حاجة بسيطة. إنما فاتورة متكررة يعني إقرار ضريبي غلط، ودفعة ضايعة يعني عميل بيتطالب بفلوس دفعها. الـ integrations بين المتجر والـ ERP بتقع في نفس الأماكن اللي الـ demos بتعديها: الرد اللي مبيوصلش، والـ webhook اللي اتبعت والـ receiver بيعمل restart، والصف اللي اتعمله commit متأخر. الدرس ده بيطلّع كل مشكلة منهم قدامك على Odoo حقيقي ويصلحها، وبيخلص بـ sync service يستحمل إنه يتقتل عند كل خطوة. وبيجاوب كمان سؤال 6 في اختبار الخروج: "JSON-2 call فشل بعد ما الـ write نجح: تضمن عدم التكرار إزاي؟"

Part 1 — The unknown outcome 🔴 Advancedالجزء 1 — النتيجة المجهولة

English

When a call ends in a socket error or a timeout, three different things may have happened: the request never arrived, it arrived and failed, or it arrived, committed, and only the response was lost. From the client's side these look identical. So a retry is only safe if repeating the operation can't change the result, and a plain create doesn't have that property.

HTTP APIs usually solve this with an Idempotency-Key header (section 12 · idempotency keys), but JSON-2 has no such header, and the transaction closes before the response is sent. You have to bring the key yourself, as data. To see the problem, here's a small loopback proxy that forwards the whole request to Odoo, waits for the commit, and then drops the connection.

  Node client           Proxy              Odoo
  -----------           -----              ----
  POST create  ------>  forward  ------>   BEGIN, INSERT, COMMIT
                                           (the row exists now)
  socket error  x-----  drop     <------   200 [78]

  POST create  ------>  forward  ------>   BEGIN, INSERT, COMMIT
                                           (a second row)
  200 [79]     <------  forward  <------   200 [79]
الرسمة فيها محاولتين. في الأولى الـ client بعت create، الـ proxy وصّله، و Odoo عمل commit والصف بقى موجود، بس الـ proxy قفل الاتصال فالـ client شاف socket error. في التانية الـ client عمل retry بنفس الطلب، فـ Odoo عمل صف تاني ورجّع 200. الـ client فاكر إنه نجح مرة واحدة، والـ database فيها اتنين.
import http from "node:http";
import type { AddressInfo } from "node:net";

// بروكسي بيوصّل الطلب لـ Odoo كامل، وبعدين يقفل الـ socket قبل ما الرد يرجع
export async function startDropProxy(target: string, dropFirst: number) {
  let seen = 0;
  const server = http.createServer((req, res) => {
    const chunks: Buffer[] = [];
    req.on("data", (c: Buffer) => chunks.push(c));
    req.on("end", async () => {
      seen += 1;
      const upstream = await fetch(target + req.url, {
        method: req.method ?? "POST",
        headers: {
          authorization: req.headers.authorization ?? "",
          "content-type": "application/json",
          "x-odoo-database": String(req.headers["x-odoo-database"] ?? "odoo"),
        },
        body: Buffer.concat(chunks),
      });
      const text = await upstream.text();
      // هنا Odoo عمل commit خلاص، والعميل هيشوف socket hang up
      if (seen <= dropFirst) return req.socket.destroy();
      res.writeHead(upstream.status, { "content-type": "application/json" });
      res.end(text);
    });
  });
  await new Promise<void>((ok) => server.listen(0, "127.0.0.1", ok));
  const { port } = server.address() as AddressInfo;
  return { url: `http://127.0.0.1:${port}`, stop: () => server.close() };
}

بالعامية

لما الـ call يخلص بـ socket error أو timeout، فيه 3 حاجات ممكن يكونوا حصلوا: الطلب موصلش أصلًا، أو وصل وفشل، أو وصل واتعمله commit والرد بس هو اللي ضاع. من ناحية الـ client التلاتة شكلهم واحد. فالـ retry يبقى آمن بس لو تكرار العملية مش هيغير النتيجة، وcreate العادي مش كده.

الـ HTTP APIs عادة بتحل ده بـ header اسمه Idempotency-Key (قسم 12 · idempotency keys)، بس JSON-2 مفيهوش header زي ده، والـ transaction بيتقفل قبل ما الرد يتبعت. فلازم إنت تجيب المفتاح بنفسك كجزء من الـ data. وعشان نشوف المشكلة، ده proxy صغير على loopback بيوصّل الطلب كله لـ Odoo، ويستنى الـ commit، وبعدين يقطع الاتصال.

فين هستخدمه في شغلي؟ الـ Node worker بيعمل فاتورة في Odoo، والـ load balancer قفل الاتصال بعد 30 ثانية و Odoo لسه شغال. الـ worker بيعمل retry بـ attempts: 5 بتاعة BullMQ، فالعميل ياخد 2 فواتير والمحاسب يكتشفها آخر الشهر. الغلطة الشائعة إن الـ retry policy تتحط على كل الـ errors من غير ما تفرق: الـ 422 مش هيتصلح لوحده، والـ timeout نتيجته مجهولة ومحتاج مفتاح.
Interview question (exit test 6) "A JSON-2 call failed after the write succeeded. How do you guarantee no duplicate?" → I can't know if it committed, so the write must be repeatable. I give every record a stable business key, an external ID through load or a unique column with a server-side upsert. Then a retry lands on the same record. I record each finished step so the worker resumes, and a reconciliation report catches anything left.
"JSON-2 call فشل بعد ما الـ write نجح. تضمن عدم التكرار إزاي؟" ← مقدرش أعرف الـ commit حصل ولا لأ، فلازم الـ write يبقى قابل للتكرار. بدي كل record مفتاح business ثابت: external ID عن طريق load، أو column عليه unique مع upsert على السيرفر. كده الـ retry بييجي على نفس الـ record. وبسجل كل خطوة خلصت عشان الـ worker يكمل، وreconciliation report بيمسك أي حاجة فضلت.

Part 2 — External IDs as the key 🔴 Advancedالجزء 2 — الـ external IDs كمفتاح

English

Odoo already has a mechanism for stable keys: external IDs, the same XML IDs that data files use, stored in ir.model.data. The public load method upserts by them. Name id as a column, give a value such as lab_sync.partner_1, and the first call creates while later calls update the same record. The response is {ids, messages, nextrow}.

load comes from the import feature, so failure isn't an HTTP error. A bad row returns 200 with ids: false and the reason in messages, and the whole batch is rolled back: a good row next to a bad one wasn't saved. A client that only checks the status believes it succeeded, so loadRows treats ids === false or any error message as a failure. A column name that doesn't exist is different and ends in a raw 500.

The alternative is your own column: x_external_ref with a models.Constraint unique, plus a server-side upsert. It has one subtlety. Odoo runs in REPEATABLE READ, so after losing the race on the unique index your snapshot still can't see the winner's row, and searching again finds nothing. The fix is to raise ConcurrencyError, which makes Odoo retry the whole call in a new transaction. And write only what changed, otherwise every retry locks the row and competes with the others.

Under a burst of identical retries neither path ever produced a duplicate, but they fail differently. load catches the serialization error per row and reports it in messages with a 200, so Odoo's automatic retry never runs and your client has to retry. sync_upsert lets the error reach the server's retry loop, so the client just sees success.

import { z } from "zod";
import { OdooError, type OdooClient } from "./odoo-client.ts";

const LoadResult = z.object({
  ids: z.union([z.array(z.number().int()), z.literal(false)]),
  messages: z.array(z.object({ type: z.string(), message: z.string() }).loose()),
});

export class OdooImportError extends OdooError {}

// الـ load بيرجع HTTP 200 حتى لو فشل، فلازم نقرا ids و messages بنفسنا
export async function loadRows(
  client: OdooClient,
  model: string,
  fields: string[],
  data: string[][],
): Promise<number[]> {
  const result = await client.call(model, "load", { fields, data }, LoadResult);
  const errors = result.messages.filter((m) => m.type === "error");
  if (result.ids === false || errors.length > 0) {
    throw new OdooImportError(`${model}.load: ${errors.map((e) => e.message).join("; ")}`, 200);
  }
  return result.ids;
}
@api.model
def sync_upsert(self, ref, vals):
    partner = self.search([('x_external_ref', '=', ref)], limit=1)
    if partner:
        # الـ retry غالبًا بيبعت نفس القيم، فمنعملش write يقفل الصف من غير داعي
        changed = {key: value for key, value in vals.items() if partner[key] != value}
        if changed:
            partner.write(changed)
        return partner.id
    try:
        with self.env.cr.savepoint():
            return self.create({**vals, 'x_external_ref': ref}).id
    except IntegrityError as exc:
        # الـ transaction التاني سبقنا، والـ snapshot بتاعنا مش هيشوفه أبدًا
        # فبنطلب من Odoo يعيد الـ call كله في transaction جديد
        raise ConcurrencyError(f'lost the race on {ref}') from exc

type Outcome = "ok" | "reported_failure" | `http_${number}` | "no_response";

async function runLimited(total: number, limit: number, task: (i: number) => Promise<Outcome>) {
  const tally: Record<string, number> = {};
  let next = 0;
  await Promise.all(Array.from({ length: limit }, async () => {
    while (next < total) {
      const i = next;
      next += 1;
      const outcome = await task(i);
      tally[outcome] = (tally[outcome] ?? 0) + 1;
    }
  }));
  return tally;
}

const failures = new Set<string>();
const classify = async (run: () => Promise<unknown>): Promise<Outcome> => {
  try {
    await run();
    return "ok";
  } catch (err) {
    if (err instanceof OdooImportError) {
      failures.add(err.message.slice(0, 110));
      return "reported_failure";
    }
    if (err instanceof OdooUnknownOutcomeError) return "no_response";
    if (err instanceof OdooError) return `http_${err.status}`;
    throw err;
  }
};

بالعامية

Odoo عنده أصلًا طريقة للمفاتيح الثابتة: الـ external IDs، نفس الـ XML IDs اللي الـ data files بتستخدمها، ومتخزنة في ir.model.data. والـ public method اسمها load بتعمل upsert بيها. سمّي column باسم id وادّيه قيمة زي lab_sync.partner_1، فأول call بيعمل create والـ calls اللي بعده بيعدلوا نفس الـ record. الرد شكله {ids, messages, nextrow}.

الـ load جاية من الـ import feature، فـالفشل مش HTTP error. الصف الغلط بيرجع 200 ومعاه ids: false والسبب في messages، والـ batch كله بيترجع: صف سليم جنب صف غلط متسيفش. والـ client اللي بيبص على الـ status بس هيفتكر إنه نجح، فـ loadRows بتعتبر ids === false أو أي error message فشل. أما اسم column مش موجود فده مختلف وبيخلص بـ 500 خام.

البديل column بتاعك: x_external_ref عليه models.Constraint unique، ومعاه upsert على السيرفر. وفيه نقطة دقيقة. Odoo شغال بـ REPEATABLE READ، فبعد ما تخسر السباق على الـ unique index الـ snapshot بتاعك لسه مش شايف صف اللي كسب، ولو عملت search تاني مش هتلاقي حاجة. الحل ترمي ConcurrencyError، فـ Odoo يعيد الـ call كله في transaction جديد. واكتب اللي اتغير بس، وإلا كل retry هيقفل الصف وينافس الباقيين.

وتحت زحمة retries متطابقة، الطريقتين عمرهم ما عملوا duplicate، بس طريقة الفشل مختلفة. load بتمسك الـ serialization error لكل صف وتكتبه في messages مع 200، فالـ retry الأوتوماتيك بتاع Odoo مبيشتغلش، والـ client بتاعك هو اللي لازم يعيد. أما sync_upsert فبتسيب الـ error يوصل لـ retry loop بتاع السيرفر، فالـ client بيشوف نجاح وخلاص.

فين هستخدمه في شغلي؟ المتجر عنده customers.id = 512، فالـ external ID يبقى shop_sync.customer_512. أي retry، أو replay من الـ queue، أو تشغيل الـ sync من الأول، بيقع على نفس الـ partner. ولو العميل على Odoo Online ومينفعش تركب module، load هو طريقك. الغلطة الشائعة إنك تستخدم الاسم أو الإيميل كمفتاح: اتنين بنفس الاسم هيتدمجوا، وعميل غيّر إيميله هيتكرر.

Part 3 — Webhooks 🟡 Intermediateالجزء 3 — الـ webhooks

English

Both directions go through base_automation, which isn't in the lab template, so install it first with -i base_automation.

Inbound is an automation with trigger='on_webhook' and a record_getter expression. Odoo serves it at POST /web/hook/<uuid> with auth='public', so the UUID is the only secret: there's no signature check. Treat the URL as a password and rotate it with action_rotate_webhook_uuid if it leaks. A repeated delivery runs the action again, so the action has to be idempotent itself.

Outbound is a server action with state='webhook'. The source (_run_action_webhook) tells you exactly what you get: it registers a postcommit hook, so a rolled-back transaction sends nothing. Then it makes one requests.post with a 1-second timeout and no retry: "send and forget". That has four consequences, all reproduced below:

  • If the receiver is down, Odoo logs a warning, the write still returns 200, and the event is gone.
  • The call runs in the request's thread after the commit, so each dead or slow receiver delays the user's write by up to a second per webhook.
  • A timeout doesn't mean failure: a slow receiver got the event while Odoo logged "may or may not have failed". Expect duplicates.
  • Without trigger_field_ids the automation fires on every internal write, so one create can send many webhooks.

The action can't set custom headers, so a shared secret has to go in the URL, and Odoo logs that URL at INFO level. That's a real limit: use a long random token only for this hook, keep those logs private, and rotate. Your receiver must verify the token in constant time (section 13 · webhooks), answer fast, and treat the body as a hint: take the id, read the current state through JSON-2, and apply it only if the version changed. Then duplicates and reordering stop mattering, and only lost events remain. Polling handles those.

  Odoo write        postcommit            Node receiver
  ----------        ----------            -------------
  COMMIT  ------->  POST, timeout=1s ---> check token
                    no retry              add id to a set
                    no signature          reply 204 at once
                                               |
                                               v
  JSON-2 read  <----------------------  drain: read current state
                                        apply if version changed
  If the receiver is down: logged, lost. Only polling finds it.

import { createHash, timingSafeEqual } from "node:crypto";
import type { AddressInfo } from "node:net";

export interface PartnerHint {
  _model: string;
  _id: number;
}

const digest = (s: string) => createHash("sha256").update(s).digest();

// بنقارن الـ hash مش النص نفسه عشان الطولين يبقوا زي بعض
const sameSecret = (a: string, b: string) => timingSafeEqual(digest(a), digest(b));

export async function startReceiver(opts: {
  port?: number;
  secret: string;
  delayMs?: number;
  onHint: (hint: PartnerHint) => void;
}) {
  const server = http.createServer((req, res) => {
    const url = new URL(req.url ?? "/", "http://receiver.local");
    if (req.method !== "POST" || url.pathname !== "/odoo/events") {
      res.writeHead(404).end();
      return;
    }
    if (!sameSecret(url.searchParams.get("token") ?? "", opts.secret)) {
      res.writeHead(401).end();
      return;
    }
    const chunks: Buffer[] = [];
    req.on("data", (c: Buffer) => chunks.push(c));
    req.on("end", () => {
      // الـ webhook مجرد إشارة: خد الـ id وارجع اقرا الحالة الحقيقية من Odoo
      const body = JSON.parse(Buffer.concat(chunks).toString("utf8")) as PartnerHint;
      opts.onHint(body);
      // لازم ترد بسرعة: Odoo مستني ثانية واحدة بس
      setTimeout(() => res.writeHead(204).end(), opts.delayMs ?? 0);
    });
  });
  await new Promise<void>((ok) => server.listen(opts.port ?? 0, "127.0.0.1", ok));
  const { port } = server.address() as AddressInfo;
  return {
    port,
    stop: () => new Promise<void>((ok) => {
      server.close(() => ok());
      server.closeAllConnections();
    }),
  };
}

Part 4 — Polling on write_date 🔴 Advancedالجزء 4 — الـ polling على write_date

English

Polling looks trivial: remember the latest write_date, ask for anything newer. The trap is in odoo/sql_db.py: cr.now() runs SELECT now(), and Postgres's now() is the transaction's start time, not the commit time. So a long transaction that starts at 10:00:00 and commits at 10:00:06 stamps its rows 10:00:00. A short one that commits at 10:00:03 stamps 10:00:03, your cursor moves there, and when the long one finally becomes visible its rows are older than your cursor. They're skipped forever, with no error.

Precision makes it worse. The column has microseconds, but the API returns whole seconds, and the domain layer compares whole seconds too (odoo/orm/domains.py turns > x into >= x + 1s). So a second change inside the same second as your cursor is also skipped.

The fix is an overlap window: query from cursor − overlap, where the overlap is longer than your longest transaction, and drop what you've already applied by (id, write_date). Re-reading the same rows is cheap; a lost invoice isn't. Keyset order is write_date, id, and the sink must be idempotent anyway. For true commit-order change capture you need logical decoding, which lesson 30 covers.

  time     0s      1s      2s      3s      4s      5s      6s
           |-------|-------|-------|-------|-------|-------|
  Tx A     BEGIN (write_date = 0s) ..................... COMMIT
  Tx B                     BEGIN+COMMIT (write_date = 2s)
  Poller                                 poll -> sees B
                                         cursor = 2s
  After A commits: A's write_date is 0s, older than the cursor.
  write_date > 2s            -> A is never seen
  write_date >= 2s - overlap -> A is seen, B is dropped as a duplicate

export class NaivePoller {
  #cursor: string;
  #client: OdooClient;
  #domain: Domain;
  constructor(start: string, client: OdooClient, domain: Domain) {
    this.#cursor = start;
    this.#client = client;
    this.#domain = domain;
  }
  async poll(): Promise<Row[]> {
    const rows = await fetchSince(this.#client, this.#domain, ">", this.#cursor);
    if (rows.length) this.#cursor = rows.at(-1)!.write_date;
    return rows;
  }
}

export class OverlapPoller {
  #cursor: Date;
  #client: OdooClient;
  #domain: Domain;
  #overlapMs: number;
  readonly #seen = new Map<number, string>();
  constructor(start: string, client: OdooClient, domain: Domain, overlapMs: number) {
    this.#cursor = toDate(start);
    this.#client = client;
    this.#domain = domain;
    this.#overlapMs = overlapMs;
  }
  async poll(): Promise<Row[]> {
    const from = new Date(this.#cursor.getTime() - this.#overlapMs);
    const rows = await fetchSince(this.#client, this.#domain, ">=", toOdoo(from));
    const fresh = rows.filter((r) => this.#seen.get(r.id) !== r.write_date);
    for (const r of fresh) this.#seen.set(r.id, r.write_date);
    const newest = rows.at(-1)?.write_date;
    if (newest && toDate(newest) > this.#cursor) this.#cursor = toDate(newest);
    return fresh;
  }
}

والدقة بتزود المشكلة. الـ column فيه microseconds، بس الـ API بيرجع ثواني كاملة، وطبقة الـ domain كمان بتقارن بالثانية (odoo/orm/domains.py بتحول > x لـ >= x + 1s). فأي تغيير تاني جوه نفس ثانية الـ cursor بيتفوت برضه.

الحل overlap window: اسأل من cursor − overlap، والـ overlap أكبر من أطول transaction عندك، وشيل اللي طبقته قبل كده بـ (id, write_date). إنك تقرا نفس الصفوف تاني رخيص؛ إنما فاتورة ضايعة مش رخيصة. الترتيب write_date, id، والمكان اللي بتكتب فيه لازم يبقى idempotent في كل الأحوال. ولو عايز change capture بترتيب الـ commit الحقيقي محتاج logical decoding، والدرس 30 بيغطيه.

فين هستخدمه في شغلي؟ Worker كل 5 دقايق بيجيب تعديلات الـ res.partner وproduct.product للمتجر. الـ cron بتاع إقفال الشهر عند المحاسب بيفتح transaction بياخد 4 دقايق، فالـ overlap لازم يبقى مثلًا 15 دقيقة. وراقب أطول transaction من pg_stat_activity عشان تعرف الرقم الحقيقي. الغلطة الشائعة إن الـ overlap يتحسب من الـ request timeout بتاع الويب وينسى الـ crons.
Trade-off: the size of the overlap Bigger is safer but re-reads more rows and needs a bigger dedupe memory. Size it from the longest transaction you've measured, and persist the cursor and the seen set in Postgres so a restart doesn't replay or forget.
الأكبر أأمن بس بيعيد قراية صفوف أكتر ومحتاج memory أكبر للـ dedupe. حدده من أطول transaction قسته، واحفظ الـ cursor والـ seen set في Postgres عشان الـ restart ميعيدش كل حاجة وميفوتش حاجة.

English

This is Artifact 4: the side project's orders reach Odoo through a Postgres outbox and a BullMQ worker (section 09 · outbox, section 06 · BullMQ). The order and its outbox row are written in one local transaction, a relay moves pending rows into the queue with a fixed jobId, and the worker runs six steps: partner, sale order, confirm, invoice, charge, payment.

Each step has a stable key, so repeating it lands on the same thing: shop_sync.customer_N, shop-order-N, the order's own invoice, an Idempotency-Key at the gateway, and the gateway's charge id on the payment. Each finished step is recorded in sync_steps, so a restart resumes where it stopped.

Note the gap: the crash point in the test is after the remote call succeeded and before recording it, the worst possible moment. sync_steps alone can't protect that window, because the row was never written. The stable key is what protects it. The two work together: the table saves work, the key prevents duplicates.

The test kills the worker with SIGKILL once at each of the six steps, on six different orders. BullMQ's lock expires, the stalled-job check puts the job back, and a new worker continues. The gateway here is a labelled stand-in on loopback: no real provider is called. At the end a reconciliation report compares the shop, the gateway and Odoo, because no retry logic can catch a change someone makes by hand. To prove the report can see drift, order 3 was edited in the shop after syncing and order 8 never entered the outbox. export async function relayOnce(pool: Pool, queue: Queue, limit = 50): Promise<number> {
  const db = await pool.connect();
  try {
    await db.query("begin");
    const { rows } = await db.query<{ id: string; order_id: string }>(
      `select id, order_id from outbox
        where published_at is null
        order by id
        for update skip locked
        limit $1`,
      [limit],
    );
    for (const row of rows) {
      await queue.add("sync-order", { orderId: Number(row.order_id) }, {
        jobId: `order-${row.order_id}`,
        attempts: 5,
        backoff: { type: "exponential", delay: 500 },
      });
    }
    await db.query("update outbox set published_at = now() where id = any($1::bigint[])", [
      rows.map((r) => r.id),
    ]);
    await db.query("commit");
    return rows.length;
  } catch (err) {
    await db.query("rollback");
    throw err;
  } finally {
    db.release();
  }
}

// الخطوة بتتنفذ مرة واحدة: لو متسجلة بنرجّع نتيجتها، ولو لأ بننفذ ونسجل
async function step<T>(
  ctx: StepContext,
  orderId: number,
  name: string,
  run: () => Promise<T>,
): Promise<T> {
  const done = await ctx.pool.query<{ result: T }>(
    "select result from sync_steps where order_id = $1 and step = $2",
    [orderId, name],
  );
  if (done.rowCount) return done.rows[0]!.result;
  const result = await run();
  ctx.afterCall(orderId, name);
  await ctx.pool.query(
    `insert into sync_steps (order_id, step, result) values ($1, $2, $3)
     on conflict (order_id, step) do nothing`,
    [orderId, name, JSON.stringify(result)],
  );
  return result;
}

          price_unit: amount / order.quantity,

  );

English

OCA's queue_job has a 20.0 branch (manifest 20.0.1.0.0, depends on mail, base_sparse_field and web). It isn't installed here, so its code is labelled "not run here": what follows comes from reading its source on GitHub. You call record.with_delay().method(), which stores a row in the queue_job table. Channels cap concurrency (root:2). A job runner, loaded with server_wide_modules = web,queue_job, listens through Postgres NOTIFY and runs each job through an HTTP call back into Odoo. Retries are triggered by raising RetryableJobError, the default is 5, and dead jobs are re-queued.

The key difference is where the job lives. In queue_job it's a row written in your business transaction, so it's a built-in outbox: if the order rolls back, the job never existed. BullMQ lives in Redis, outside that transaction, which is why Part 5 needed an outbox table to get the same guarantee.

The rule of thumb: if the work is 90% ORM (recompute, generate invoices, post moves), let queue_job own it, inside Odoo, and don't drag records across HTTP. If the work is mostly outside Odoo (your shop, gateways, emails), let your Node stack own it with BullMQ, and treat Odoo as one more remote API.

Cheat sheet · الخلاصة

  • A lost response means unknown outcome. Retry only an operation that's safe to repeat.
  • JSON-2 has no idempotency header. Bring a stable business key as data.
  • load upserts by external ID, and it returns 200 on failure: check ids and messages.
  • Server-side upsert: models.Constraint unique, raise ConcurrencyError on the race, write only what changed.
  • Send X-Odoo-Database and cap client concurrency.
  • Inbound webhook: the UUID is the only secret, duplicates run twice, rotate with action_rotate_webhook_uuid.
  • Outbound webhook: postcommit, one POST, 1-second timeout, no retry, no custom headers. At most once.
  • Receiver: verify the secret, reply fast, treat the body as a hint and re-read the state.
  • write_date is the transaction's start, in whole seconds over the API. Poll with overlap and dedupe.
  • Sync: outbox, fixed jobId, a key per step, recorded progress, then reconcile.
  • queue_job: the job is in your transaction, best for ORM work. BullMQ: needs an outbox, best for work outside Odoo.
بالعامية
  • الرد الضايع معناه النتيجة مجهولة. اعمل retry بس للعملية اللي تكرارها آمن.
  • JSON-2 مفيهوش idempotency header. هات مفتاح business ثابت كجزء من الـ data.
  • load بيعمل upsert بالـ external ID، وبيرجع 200 حتى لو فشل: افحص ids وmessages.
  • الـ upsert على السيرفر: models.Constraint unique، وارمي ConcurrencyError لو خسرت السباق، واكتب اللي اتغير بس.
  • ابعت X-Odoo-Database وحط حد للـ concurrency عند الـ client.
  • الـ inbound webhook: الـ UUID هو السر الوحيد، والتكرار بيتنفذ مرتين، وغيّره بـ action_rotate_webhook_uuid.
  • الـ outbound webhook: postcommit، و POST واحد، و timeout ثانية، من غير retry ومن غير headers خاصة. يعني at most once.
  • الـ receiver: افحص الـ secret، ورد بسرعة، واعتبر الـ body إشارة واقرا الحالة من جديد.
  • write_date هو بداية الـ transaction، وبالثواني الكاملة على الـ API. اعمل polling بـ overlap و dedupe.
