Why this matters · ليه ده مهم

English

An ERP fails differently from a stateless API. Nobody is scrolling a feed: forty accountants are posting invoices on the last day of the month, a cron is reconciling bank lines, and every one of those writes touches the same few rows. In this lesson we ran real Odoo 20 against a private Postgres 18 copy and watched what actually breaks. Six orders produced 20 payment-provider calls. A 16-client load on one gap-free sequence failed 12 of 32 requests while the Odoo process used 2% of a CPU. Those two numbers are the lesson: under load, Odoo's problem is usually contention and replays, and adding servers doesn't fix either.

بالعامية

الـ ERP بيقع بطريقة غير الـ API العادي. مفيش حد بيقلّب في feed: عندك 40 محاسب بيرحّلوا فواتير آخر يوم في الشهر، وcron بيعمل reconciliation لحركات البنك، وكل الكتابات دي بتخبط في نفس الكام row. في الدرس ده شغّلنا Odoo 20 حقيقي على نسخة Postgres 18 خاصة وشفنا إيه اللي بيكسر فعلًا. 6 orders عملوا 20 مكالمة لـ payment provider. وضغط 16 client على sequence واحد من غير فجوات فشّل 12 طلب من 32، والـ process بتاع Odoo مستخدم 2% بس من CPU. الرقمين دول هما الدرس كله: تحت الضغط، مشكلة Odoo غالبًا contention و replays، وزيادة السيرفرات مش هتحل ولا واحدة فيهم.

Part 1 — Postgres for Odoo 🔴 Advancedالجزء 1 — Postgres مظبوط لـ Odoo

English

Workload shape. Odoo opens every cursor at REPEATABLE READ (real: SHOW transaction_isolation on an ORM cursor returned repeatable read), and runs many small ORM-generated queries per request. A handful of tables grow with the business: mail_message (every chatter entry), account_move_line (the ledger), ir_attachment (the rows; the bytes live in the filestore) and stock_move. The demo template only has 2,867 / 330 / 1,624 / 208 rows in those four, so we seeded 400,000 rows into a lab table to get a plan worth reading.

Measure first. pg_stat_statements needs shared_preload_libraries and a server restart, so it has to run on a cluster you own. Run a representative workload, sort by total_exec_time (not mean: a 2 ms query called a million times beats a 5 s report), read the plan with EXPLAIN (ANALYZE, BUFFERS), then fix it in the module with models.Index so that the index exists in every environment and survives a rebuild. A hand-made index is invisible to code review, and it won't exist in staging or in any freshly built database.

The catch. models.Index runs a plain CREATE INDEX during -u (there is no CONCURRENTLY anywhere in the ORM), which blocks writes to that table while it builds. On a big table, build it first with CREATE INDEX CONCURRENTLY under the exact name Odoo will use, <table><attribute name>. apply_to_database keeps an index that has no comment, and we confirmed it: the OID was unchanged after -u.

Connection maths. Each Odoo process has its own pool capped at db_maxconn (default 64). The worst case is (workers + max_cron_threads) × db_maxconn + db_maxconn_gevent, plus whatever your backups and monitoring use, and it must stay below max_connections. Odoo also depends on session state: LISTEN cron_trigger, listen imbus and a session-level advisory lock on registry_loading. Those are the things PgBouncer's transaction mode breaks, so see section 09 · pooling before you put one in front.

interface Deployment {
  workers: number;
  cronThreads: number;
  dbMaxconn: number;
  dbMaxconnGevent: number;
  reservedForOps: number;
  maxConnections: number;
}

// الحد الأقصى النظري: كل process عنده pool مستقل بسقف db_maxconn
export function worstCase(d: Deployment): number {
  return (d.workers + d.cronThreads) * d.dbMaxconn + d.dbMaxconnGevent + d.reservedForOps;
}

function report(name: string, d: Deployment): void {
  const need = worstCase(d);
  const verdict = need <= d.maxConnections ? "fits" : `over by ${need - d.maxConnections}`;
  console.log(`${name}: worst case ${need} of ${d.maxConnections} -> ${verdict}`);
}

بالعامية

شكل الشغل: Odoo بيفتح كل cursor بـ REPEATABLE READ (جربناها: SHOW transaction_isolation طلعت repeatable read)، وبيبعت queries صغيرة كتير من الـ ORM في كل طلب. والجداول اللي بتكبر مع البيزنس: mail_message (كل chatter)، account_move_line (الـ ledger)، ir_attachment (الصفوف بس، الملفات نفسها في الـ filestore)، و stock_move. الـ demo فيه 2,867 و330 و1,624 و208 صف بس، فعملنا seed لـ 400 ألف صف في جدول lab عشان نشوف خطة تستاهل.

قيس الأول: pg_stat_statements محتاج shared_preload_libraries و restart، يعني لازم cluster بتاعك. شغّل workload حقيقي، رتّب بـ total_exec_time مش المتوسط (query بـ 2ms متنادية مليون مرة أخطر من report بـ 5 ثواني)، اقرا الخطة بـ EXPLAIN (ANALYZE, BUFFERS)، وصلّح جوه الـ module بـ models.Index عشان يبقى موجود في كل environment. الـ index اليدوي محدش بيشوفه في الـ code review، ومش هيبقى موجود في الـ staging ولا في أي database جديدة.

الفخ: models.Index بيعمل CREATE INDEX عادي وقت -u (مفيش CONCURRENTLY في الـ ORM كله)، وده بيقفل الكتابة على الجدول طول ما بيتبني. على جدول كبير، ابنيه الأول بـ CREATE INDEX CONCURRENTLY بنفس الاسم اللي Odoo هيستخدمه، <table><اسم الـ attribute>. الـ apply_to_database بيسيب الـ index اللي مفيهوش comment، وأكدناها: الـ OID فضل زي ما هو بعد -u.

حساب الـ connections: كل process عنده pool مستقل سقفه db_maxconn (الـ default 64). أسوأ حالة (workers + max_cron_threads) × db_maxconn + db_maxconn_gevent، زائد الـ backups والـ monitoring، ولازم تفضل أقل من max_connections. كمان Odoo بيعتمد على session: LISTEN cron_trigger و listen imbus و advisory lock على مستوى الـ session اسمه registry_loading. ودول بالظبط اللي الـ transaction mode بتاع PgBouncer بيكسرهم، فاقرا section 09 · pooling قبل ما تحطه قدامه.

فين هستخدمه في شغلي؟ عميل بيشتكي إن شاشة الفواتير بطيئة آخر الشهر. بدل ما تخمّن: فعّل pg_stat_statements على نسخة، رتّب بالوقت الكلي، خد أول query، EXPLAIN، حط models.Index في الـ module بتاعك، وافتح PR فيه الخطة قبل وبعد. ولو الجدول 40 مليون صف، ابني الـ index بـ CONCURRENTLY قبل الـ deploy بنفس الاسم. الغلطة الشائعة: تعمل CREATE INDEX بإيدك في production وتنسى، والـ staging يفضل بطيء ومحدش عارف ليه.

Part 2 — Monitoring 🔴 Advancedالجزء 2 — الـ monitoring والـ logs

English

Health. /web/health answers {"status": "pass"} without touching Postgres, so it only proves the HTTP thread is alive. Add ?db_server_status=1 and it opens a real cursor. Neither checks that your code and your schema agree: lesson 36 shows it answering pass on a half-upgraded database.

The access line is a free profiler. In Odoo 20 the logger is odoo.http.server, and its format ends in three performance columns: query_count, query_time, and remaining_time (total minus SQL), then the cursor mode. Our N+1 endpoint logged 206 queries against 6 for the batched one. A retried request shows a huge remaining_time with a tiny query_time: those 24 seconds are time.sleep in the retry backoff, not CPU.

Log routing. --log-handler module:LEVEL is repeatable; --log-sql is a shortcut for odoo.sql_db:DEBUG; --log-config takes a JSON or TOML dictConfig if you want structured output. log_db copies records at or above log_db_level into the ir_logging table (real row below). Each record opens its own cursor, so keep it at warning. And be careful: odoo.http.server:WARNING silenced 5 of 5 access lines in our run, and any exporter reading them goes blind without an error.

The exporter. Odoo has no built-in Prometheus endpoint, so a small Node process tails the log and exposes metrics. Prometheus and Grafana themselves are not run here; the exporter and the numbers below are real. For how to scrape and graph it, see section 13 · Prometheus.

const LINE = /^\S+ \S+ \d+ (\w+) \S+ (\S+): (.*)$/;

const ACCESS = /"(\w+) ([^ "]+) HTTP\/[\d.]+" (\d{3}) \S+ (\d+) ([\d.]+) ([\d.]+)/;

// ليه: لو حطيت الـ URL زي ما هو في label، كل id هيعمل time series جديدة
export function normalizeRoute(url: string): string {
  const [path = "/"] = url.split("?");
  return path.replace(/\/\d+(?=\/|$)/g, "/:id").replace(/\/assets\/.*/, "/assets/*").slice(0, 80);
}

export function consume(line: string): void {
  const m = LINE.exec(line);
  if (!m) return;
  const [, level = "", logger, message = ""] = m;
  levels.inc({ level });
  if (MEMORY.test(message)) memoryKills.inc();
  if (logger === "odoo.http.server") {
    const a = ACCESS.exec(message);
    if (!a) return;
    const route = normalizeRoute(a[2] ?? "/");
    const queries = Number(a[4]);
    const queryTime = Number(a[5]);
    const otherTime = Number(a[6]);
    requests.inc({ route, status: a[3] ?? "0" });
    duration.observe({ route }, queryTime + otherTime);
    sqlCount.inc({ route }, queries);
    sqlSeconds.inc({ route }, queryTime);
    return;
  }
  if (logger === "odoo.http") {
    const r = RETRY.exec(message);
    if (r) retries.inc({ error: r[1] ?? "unknown" });
    const g = GAVE_UP.exec(message);
    if (g) gaveUp.inc({ error: g[1] ?? "unknown" });
  }
}

async function poll(): Promise<void> {
  const { size } = await stat(logPath);
  // الـ logrotate: لو الملف صغر يبقى اتلف، نبدأ من الأول
  if (size < offset) {
    offset = 0;
    partial = "";
  }
  if (size === offset) return;
  const file = await open(logPath, "r");
  try {
    const buffer = Buffer.alloc(size - offset);
    await file.read(buffer, 0, buffer.length, offset);
    offset = size;
    // السطر الأخير ممكن يكون لسه بيتكتب، فبنسيبه للمرة الجاية
    const lines = (partial + buffer.toString("utf8")).split("\n");

Part 3 — Alerts 🔴 Advancedالجزء 3 — الـ alerts: تنبّه على إيه

English

An alert is only worth having if someone must act on it. For Odoo, split them into three families: availability (error-budget burn), workload (memory kills, cron lag, retries, mail queue) and business (reconciliation drift, certificate expiry, filestore disk). The last family is what separates an ERP from a web app: the site can be up while the books are wrong.

Most of the workload and business signals aren't in the log. They live in tables, so a probe reads them with SQL: ir_cron.nextcall and failure_count, mail_mail.state, certificate_certificate.date_end, and open receivables compared against your billing system's total. Prometheus rules follow; the SLO maths behind burn rate is in section 13 · SLOs.

For a 99.9% SLO the budget is 0.1%. A burn rate of 14.4 sustained for an hour consumes 2% of a 30-day budget, which is why it pages. A burn of 6 over six hours opens a ticket. The rules are not run here (no Prometheus on this machine): we parsed the YAML and computed the burn-rate logic in Node.

// الأمان: Port فاضي معناه الـ default، وده ممكن يوصّلك لـ database حقيقية
function guardPort(raw: string | undefined): number {
  const n = Number(raw);
  if (!/^\d+$/.test(String(raw)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port ${raw}`);
  }
  return n;
}

export async function collect(client: pg.Client, filestore: string, billingTotal: number): Promise<Sample[]> {
  const samples: Sample[] = [];

  // التأخير: nextcall متخزن UTC من غير timezone، فلازم نقارنه بـ UTC
  const cron = await client.query<{ overdue: string; failing: string }>(`
    SELECT coalesce(max(extract(epoch FROM (now() AT TIME ZONE 'utc') - nextcall))
                    FILTER (WHERE nextcall < (now() AT TIME ZONE 'utc')), 0)::int AS overdue,
           count(*) FILTER (WHERE failure_count > 0) AS failing
    FROM ir_cron WHERE active`);
  samples.push({ metric: "odoo_cron_overdue_seconds", value: Number(cron.rows[0]?.overdue) });
  samples.push({ metric: "odoo_cron_failing", value: Number(cron.rows[0]?.failing) });

  const mail = await client.query<{ state: string; n: string }>("SELECT state, count(*) AS n FROM mail_mail GROUP BY state");
  for (const state of ["outgoing", "exception"]) {
    const row = mail.rows.find((r) => r.state === state);
    samples.push({ metric: "odoo_mail_queue", labels: { state }, value: Number(row?.n ?? 0) });
  }

  // الشهادات: أقرب واحدة هتخلص هي اللي تهمّ
  const cert = await client.query<{ not_after: string | null }>(
    "SELECT extract(epoch FROM min(date_end))::bigint AS not_after FROM certificate_certificate WHERE active AND date_end IS NOT NULL");
  if (cert.rows[0]?.not_after) samples.push({ metric: "odoo_certificate_not_after_seconds", value: Number(cert.rows[0].not_after) });

  // الفلوس: الرصيد المفتوح في Odoo قصاد الرقم اللي جاي من الـ billing
  const open = await client.query<{ residual: string }>(`
    SELECT coalesce(sum(aml.amount_residual), 0)::numeric(16, 2) AS residual
    FROM account_move_line aml
    JOIN account_account aa ON aa.id = aml.account_id
    WHERE aa.account_type = 'asset_receivable' AND aml.parent_state = 'posted' AND NOT aml.reconciled`);
  const residual = Number(open.rows[0]?.residual);
  samples.push({ metric: "odoo_receivable_open", value: residual });
  samples.push({ metric: "odoo_reconciliation_drift_egp", value: Number((residual - billingTotal).toFixed(2)) });

  const disk = await statfs(filestore);
  samples.push({ metric: "odoo_filestore_free_bytes", value: disk.bavail * disk.bsize });
  return samples;
}

      return `${s.metric}${labels} ${s.value}`;
    })
    .join("\n");
}

export function burnRate(errors: number, total: number, slo: number): number {
  if (total === 0) return 0;
  const allowed = 1 - slo;
  return errors / total / allowed;
}

export function hoursToExhaust(rate: number, windowDays = 30): number {
  return rate === 0 ? Infinity : (windowDays * 24) / rate;
}

Part 5 — Cron locks and long transactions 🔴 Advancedالجزء 5 — الـ cron locks والـ transactions الطويلة

English

Odoo claims a cron job with FOR NO KEY UPDATE SKIP LOCKED on the ir_cron row. We proved it: with one cursor holding the claim, a second _acquire_one_job returned nothing. That protects the claim: two workers won't run the same job. It does nothing for the rows the job writes. If the job updates 200 deliveries in one transaction, it holds 200 row locks until it commits, and any user touching one of them waits.

A long transaction also holds a snapshot. While it's open, its backend_xmin stops vacuum from removing any row version newer than that snapshot, in every table. We held one cursor, updated 50,000 rows elsewhere, and vacuum reported all 50,000 "dead but not yet removable". After the cursor closed, the same vacuum removed them. MVCC itself is covered in section 09 · MVCC.

The fix is batches with _commit_progress. Each batch commits, releases its locks and takes a new snapshot; the framework records progress in ir_cron_progress, reschedules unfinished work, and enforces a time budget. Commits mean a batch has to be restartable: pick the next rows from their state, never from an in-memory list. Note that _commit_progress can't run inside env.cr.savepoint(). For claiming rows, try_lock_for_update() gives you the ORM's own SKIP LOCKED.

    @api.model
    def _cron_settle_monolith(self):
        todo = self.search([('state', '=', 'pending'), ('name', '=like', 'CRON-%')], order='id')
        for delivery in todo:
            delivery.state = 'sent'
            self.env.flush_all()
            time.sleep(0.01)

    # الصح: كل batch بيعمل commit، ويبلّغ التقدم، ويقف لو الوقت خلص
    @api.model
    def _cron_settle_batched(self, batch=20):
        domain = [('state', '=', 'pending'), ('name', '=like', 'CRON-%')]
        ir_cron = self.env['ir.cron']
        ir_cron._commit_progress(remaining=self.search_count(domain))
        while True:
            # القراية: من الـ state كل مرة، عشان لو الـ job وقع يكمّل من مكانه
            todo = self.search(domain, order='id', limit=batch)
            if not todo:
                return
            for delivery in todo:
                delivery.state = 'sent'
                self.env.flush_all()
                time.sleep(0.01)
            left = ir_cron._commit_progress(len(todo))
            if not left:
                return

بالعامية

Odoo بيحجز الـ cron بـ FOR NO KEY UPDATE SKIP LOCKED على صف ir_cron. وأثبتناها: cursor ماسك الحجز، فـ _acquire_one_job التاني مرجعش حاجة. ده بيحمي الحجز: اتنين workers مش هيشغّلوا نفس الـ job. بس ملوش دعوة بـ الصفوف اللي الـ job بيكتب فيها. لو الـ job بيعدّل 200 delivery في transaction واحدة، هيمسك 200 row lock لحد الـ commit، وأي user يلمس واحد منهم هيستنى.

الـ transaction الطويلة كمان ماسكة snapshot. طول ما هي مفتوحة، الـ backend_xmin بتاعها بيمنع الـ vacuum يشيل أي نسخة صف أحدث منه، في كل الجداول. مسكنا cursor واحد وعدّلنا 50 ألف صف من مكان تاني، والـ vacuum قال الـ 50 ألف "dead but not yet removable". بعد ما الـ cursor اتقفل نفس الـ vacuum شالهم. شرح الـ MVCC في section 09 · MVCC.

الحل batches بـ _commit_progress: كل batch بيعمل commit، فيفك الـ locks وياخد snapshot جديد، والـ framework بيسجل التقدم في ir_cron_progress، ويعيد جدولة اللي لسه، ويطبّق ميزانية وقت. الـ commits معناها إن الـ batch لازم يتعاد عادي: هات الصفوف الجاية من الـ state بتاعها، مش من list في الـ memory. و _commit_progress مينفعش جوه env.cr.savepoint(). ولحجز صفوف، try_lock_for_update() بيديك SKIP LOCKED من الـ ORM.

فين هستخدمه في شغلي؟ cron بيبعت 50 ألف فاتورة لمصلحة الضرايب بالليل. لو عملته loop واحد، أي محاسب يعدّل فاتورة هيقف، والجدول هيتنفخ لأن الـ vacuum واقف، ولو الـ job وقع عند رقم 49,999 كله يترجع. بـ batches: كل 100 فاتورة commit، ولو وقع يكمّل. الغلطة الشائعة: تحط self.env.cr.commit() بإيدك في نص write عادي، فتكسر الـ atomicity بتاعة الطلب.
Interview question "SKIP LOCKED is on the job queue. Why can a cron still block users?" → It only protects the claim on the job row. The job's own writes take ordinary row locks that last until commit. Batch with commits, so each lock's lifetime is one batch, and make every batch restartable.
"الـ SKIP LOCKED موجود على طابور الـ jobs. ليه الـ cron ممكن لسه يعطّل المستخدمين؟" ← لأنه بيحمي الحجز على صف الـ job بس. الكتابات بتاعة الـ job نفسه بتاخد row locks عادية بتفضل لحد الـ commit. قسّم batches بـ commits عشان عمر الـ lock يبقى batch واحد، وخلي كل batch ينفع يتعاد.

Part 6 — Serialization failures 🔴 Advancedالجزء 6 — الـ serialization failures والـ retries

English

At REPEATABLE READ, a transaction that updates a row someone else committed after its snapshot gets SerializationFailure 40001 could not serialize access due to concurrent update (real output below). Odoo's answer lives in odoo/http/retrying.py: it rolls back and calls your whole request again, up to MAX_TRIES_ON_CONCURRENCY_FAILURE (5) tries, sleeping random.uniform(0, 2**try) between them. It retries SerializationFailure, DeadlockDetected, LockNotAvailable and ConcurrencyError.

The database work is rolled back cleanly. Everything else isn't. An HTTP call to a payment provider inside the request fires again on each replay. We ran 6 concurrent requests against a loopback stand-in: 20 charges. One customer got a 500 and was charged 5 times. That is the trap, and it's specific to frameworks that replay.

The fix: move the side effect after the commit with env.cr.postcommit.add(fn). Rollback clears those callbacks, so only the attempt that committed fires: 6 requests, 6 charges. Postcommit is at-most-once: a crash between commit and call loses it. For money, use an outbox row written in the same transaction and dispatched by a cron with an idempotency key, as in section 09 · outbox and lesson 28. Isolation theory is in section 09 · isolation.

            sleep uniform(0, 2) ----------------------------<---+

import functools
import time

import requests

from odoo import http
from odoo.http import request


def _charge(url, ref):
    requests.post(url, json={'order': ref}, timeout=5)


class ProdLab(http.Controller):

    def _provider(self):
        return request.env['ir.config_parameter'].sudo().get_str('prod_lab.provider_url')

    def _hot(self):
        return request.env.ref('base.main_partner').sudo()

    # الغلط: المكالمة جوه الطلب، فكل retry بيعمل charge جديد
    @http.route('/prod_lab/charge_bad', type='http', auth='public', methods=['POST'], csrf=False)
    def charge_bad(self, ref='x'):
        _charge(self._provider(), ref)
        partner = self._hot()
        partner.comment = f'charged {ref}'
        request.env.flush_all()
        time.sleep(0.05)
        return 'ok'

    # الصح: المكالمة بعد الـ commit، والـ rollback بيمسح الـ callback
    @http.route('/prod_lab/charge_good', type='http', auth='public', methods=['POST'], csrf=False)
    def charge_good(self, ref='x'):
        url = self._provider()
        partner = self._hot()
        partner.comment = f'charged {ref}'
        request.env.flush_all()
        time.sleep(0.05)
        request.env.cr.postcommit.add(functools.partial(_charge, url, ref))
        return 'ok'

English

Honest scope. k6 is not run here, so a small Node generator hits a threaded lab with workers = 0, the only mode on Windows. That is not production: one Python process, one GIL, a loaded machine. Absolute numbers mean nothing; the comparison between two runs on the same setup does. Load-testing method is in section 13 · load tests.

The experiment. One endpoint takes a number from an ir.sequence, sleeps 30 ms to stand in for the rest of an invoice, and creates a row. The only difference between the two series is the sequence's implementation: standard uses a Postgres sequence, with no row lock. no_gap does SELECT ... FOR UPDATE NOWAIT and then UPDATE on one row. 32 requests per level, closed loop.

The result. standard scales to ≈22 req/s and never retries. no_gap drops from ≈5 req/s to ≈1, and at 16 clients it fails 12 of 32 requests, with a p95 of ≈24 s, while the Odoo process uses 2% of a CPU. The bottleneck is lock contention, not CPU. More workers would make it worse: more concurrent transactions colliding on the same row.

What didn't help. We expected taking the number last, to shorten the lock, to fix it. It didn't: same 4 and 10 failures, same 27 and 57 retries. At REPEATABLE READ the conflict window is the whole transaction, because the snapshot starts at the first query, so any commit on that row since then fails you, however briefly you hold it. What works: use no_gap only where law demands it, assign numbers in one place (a single cron over committed drafts), and shorten the whole transaction. Odoo's own invoice numbering is a different mechanism (_locked_increment in sequence_mixin.py), which this benchmark did not measure.

التجربة اللي فشلت: توقعنا إن أخد الرقم في آخر الطلب هيقصّر الـ lock ويحل المشكلة. النتيجة نفس الفشل ونفس الـ retries بالظبط. السبب إن الـ snapshot بيبدأ مع أول query، فأي commit على الصف من ساعتها بيوقعك مهما كان مسكك قصير.
بالعامية

حدود التجربة بصراحة: k6 مش متشغّل هنا، فـ generator صغير بـ Node بيضرب lab بـ workers = 0، وده الوضع الوحيد على Windows. ده مش production: process واحد و GIL واحد وجهاز عليه ضغط. الأرقام المطلقة ملهاش معنى، بس المقارنة بين run ورن على نفس الإعداد ليها. طريقة الـ load test في section 13 · load tests.

التجربة: endpoint بياخد رقم من ir.sequence، وينام 30ms كبديل لباقي شغل الفاتورة، ويعمل صف. الفرق الوحيد بين الخطين هو implementation: الـ standard بيستخدم Postgres sequence من غير row lock، و no_gap بيعمل SELECT ... FOR UPDATE NOWAIT وبعدين UPDATE على صف واحد. 32 طلب لكل مستوى، closed loop.

النتيجة: standard وصل ≈22 طلب في الثانية ومعملش ولا retry. no_gap نزل من ≈5 لـ ≈1، وعند 16 client فشل 12 من 32 طلب، بـ p95 ≈24 ثانية، والـ process مستخدم 2% من CPU. عنق الزجاجة lock contention مش CPU. وزيادة الـ workers هتزوّدها: transactions أكتر بتخبط في نفس الصف.

اللي مانفعش: توقعنا إن أخد الرقم في الآخر يقصّر الـ lock ويحلها. مانفعتش: نفس الـ 4 و 10 فشل، ونفس الـ 27 و 57 retry. في REPEATABLE READ نافذة التعارض هي الـ transaction كلها، لأن الـ snapshot بيبدأ مع أول query، فأي commit على الصف من ساعتها بيوقعك مهما مسكته قليل. اللي بينفع: استخدم no_gap بس لو القانون طالبه، ووزّع الأرقام من مكان واحد (cron واحد على drafts متعمل لها commit)، وقصّر الـ transaction كلها. والترقيم بتاع فواتير Odoo نفسها آلية تانية (_locked_increment في sequence_mixin.py) والـ benchmark ده مقاسهاش.

فين هستخدمه في شغلي؟ قبل go-live لعميل عنده 40 محاسب: ابني سيناريو بأكتر عملية متنافسة عنده (مثلًا صنف واحد عليه كل الطلبات، أو journal واحد كل الفواتير بتعدّي عليه)، وزوّد الـ concurrency تدريجيًا، وارسم الـ retries مش الـ CPU. لو الـ retries طلعت والإنتاجية نزلت، إنت قدام hot row. الغلطة الشائعة: تطلب سيرفر أكبر، والسيرفر الحالي فاضي 98%.
What breaks at scale Retries multiply load exactly when you can least afford it. With 5 tries and backoff up to 24 seconds, a worker can sit on a failing request for ≈24 s (we measured 24.028 s of remaining_time). With 8 workers, eight such requests occupy every worker, and healthy requests queue behind them. Contention on one row becomes an outage of the whole site.
الـ retries بتضاعف الضغط في أسوأ وقت. بـ 5 محاولات و backoff لحد 24 ثانية، الـ worker ممكن يفضل ماسك طلب فاشل ≈24 ثانية (قسنا 24.028 ثانية في remaining_time). ومع 8 workers، 8 طلبات زي دول بيمسكوا كل الـ workers، والطلبات السليمة تقف وراهم. يعني التنافس على صف واحد بيتحول لوقوع الموقع كله.

Common mistakes · غلطات شائعة

❌ Side effect inside the request 
# الغلط: كل retry بيعمل charge جديد
_charge(url, ref)
partner.comment = f'charged {ref}'
✅ After the commit 
# الصح: بينفذ مرة واحدة بعد commit ناجح
partner.comment = f'charged {ref}'
env.cr.postcommit.add(functools.partial(_charge, url, ref))
بالعامية

❌ المكالمة جوه الطلب: Odoo بيعيد الطلب كله لحد 5 مرات لو حصل 40001، والمكالمة بتتكرر معاه، وعندنا 6 طلبات عملوا 20 charge. ✅ postcommit بيتنفذ بعد الـ commit بس، والـ rollback بيمسحه، فبقوا 6. ولو الفلوس مهمة استخدم outbox.

❌ One transaction for a whole cron 
# الغلط: كل الـ locks ماسكة لحد الآخر
for delivery in self.search(domain):
    delivery.state = 'sent'
✅ Batches that can restart 
# الصح: Commit لكل batch، والقراية من الـ state
while todo := self.search(domain, limit=100):
    todo.write({'state': 'sent'})
    if not self.env['ir.cron']._commit_progress(len(todo)):
        return
بالعامية

❌ الـ transaction الواحدة بتعطّل المستخدمين (≈1770ms عندنا) وبتوقف الـ vacuum، ولو وقعت عند آخر صف كله يترجع. ✅ كل batch بيعمل commit وبيفك الـ locks، ولو الـ job وقع يكمّل من الـ state. وخد بالك إن _commit_progress بيرجع الوقت الباقي، فلو صفر لازم تقف.

❌ Index by hand in production 
-- الغلط: موجود في production بس، ومحدش عارف
CREATE INDEX my_idx ON prod_lab_delivery (partner_id);
✅ In the module, pre-built if big 
-- الصح: بنفس اسم models.Index، قبل الـ deploy
CREATE INDEX CONCURRENTLY prod_lab_delivery_partner_state_idx
  ON prod_lab_delivery (partner_id, scheduled_at DESC)
  WHERE state = 'pending';
بالعامية

❌ الـ index اليدوي مش في الكود، فالـ staging وأي database جديدة مش هيبقى فيهم. ✅ عرّفه بـ models.Index في الـ module. ولو الجدول كبير، ابنيه CONCURRENTLY قبل -u بنفس الاسم بالظبط، و Odoo هيسيبه زي ما هو بدل ما يقفل الكتابة.

❌ Health check that sees nothing 
# الغلط: بيثبت إن الـ thread عايش وخلاص
test: ["CMD", "curl", "-f", "http://127.0.0.1:8069/web/health"]
✅ Touch the database, probe the business 
# الصح: يفتح cursor، والـ probes تغطي الباقي
test: ["CMD", "curl", "-fsS", "http://127.0.0.1:8069/web/health?db_server_status=1"]
بالعامية

❌ /web/health لوحده بيرد pass حتى لو Postgres واقع. ✅ ?db_server_status=1 بيفتح cursor حقيقي. وده برضه مش كفاية: الـ cron ممكن يبقى واقف والدفاتر غلط، فالـ probes اللي في Part 3 هي اللي بتكمّل الصورة.

❌ Secret in the environment 
# الغلط: بيبان في docker inspect وبيتعمله commit
environment:
  PASSWORD: CHANGE_ME_NOT_A_REAL_PASSWORD
✅ Config file as a secret 
# الصح: الـ entrypoint بيلاقي db_password في الملف فمبيبعتهوش
environment:
  ODOO_RC: /run/secrets/odoo_conf
secrets:
  - odoo_conf
بالعامية

❌ الباسورد في environment بيبان في docker inspect، وحتى PASSWORD_FILE بيوصل لـ --db_password على الـ command line. ✅ حط db_password جوه ملف config واعمله mount كـ secret، و check_config في الـ entrypoint هيلاقيه فمش هيبعته كـ argument.

Solution · الحل 
import requests

from odoo import api, fields, models


class Outbox(models.Model):
    _name = 'prod_lab.outbox'
    _description = 'Provider call waiting to be sent'

    ref = fields.Char(required=True)
    state = fields.Selection([('pending', 'Pending'), ('sent', 'Sent')], default='pending', required=True)

    # الضمان: ref واحد بس، حتى لو الطلب اتعاد
    _ref_unique = models.UniqueIndex('(ref)')
    _pending_idx = models.Index("(id) WHERE state = 'pending'")

    @api.model
    def _cron_dispatch(self, batch=50):
        ir_cron = self.env['ir.cron']
        url = self.env['ir.config_parameter'].sudo().get_str('prod_lab.provider_url')
        domain = [('state', '=', 'pending')]
        ir_cron._commit_progress(remaining=self.search_count(domain))
        while todo := self.search(domain, order='id', limit=batch):
            for row in todo:
                # المفتاح: لو الـ commit فشل بعد المكالمة، الـ provider يعرف إنها مكررة
                requests.post(url, json={'order': row.ref}, headers={'Idempotency-Key': row.ref}, timeout=5)
                row.state = 'sent'
            if not ir_cron._commit_progress(len(todo)):
                return

run 200 ok   calls after cron 6   per order 1 each   distinct keys 6   rows sent: 6
rerun 200 ok   calls 6
ناتج حقيقي: بعد الطلبات الستة صفر مكالمات و 6 صفوف pending، رغم الـ retries، لأن الـ rollback بيشيل الصف مع المحاولة الفاشلة. بعد الـ cron: 6 مكالمات، واحدة لكل order. التشغيل التاني مبعتش حاجة. ولما الـ provider علّق في تجربة سابقة، الـ job وقع بـ ReadTimeout والصفوف فضلت pending ومضاعتش.

Cheat sheet · الخلاصة

  • Odoo runs REPEATABLE READ. Tables that grow: mail_message, account_move_line, ir_attachment, stock_move.
  • Tune by measurement: pg_stat_statements sorted by total time, EXPLAIN (ANALYZE, BUFFERS), then models.Index. Big table: CONCURRENTLY first, same name.
  • Connections: (workers + max_cron_threads) × db_maxconn + db_maxconn_gevent + ops < max_connections. Odoo uses LISTEN and session advisory locks.
  • Access line ends in query_count query_time remaining_time cursor_mode. Big remaining_time with low query_time on a failure means retry sleeps.
  • /web/health alone doesn't touch Postgres. Add ?db_server_status=1, and probe cron lag, mail, drift, certificates, disk.
  • Page on burn 14.4 over 1 h and 5 min; ticket on burn 6 over 6 h.
  • Docker: pin a dated tag, mount the config as a secret, postgres:18 volume at /var/lib/postgresql.
  • SKIP LOCKED protects the job claim, not the rows it writes. Batch with _commit_progress, restart from state.
  • A long transaction blocks vacuum everywhere: watch idle in transaction and age(backend_xmin).
  • retrying() replays the whole request up to 5 times. External calls go in postcommit or an outbox.
  • Under contention, retries climb, throughput falls and CPU stays flat. Shortening the lock doesn't help at REPEATABLE READ; shrink the transaction or serialize the work.
بالعامية
  • Odoo شغال بـ REPEATABLE READ. الجداول اللي بتكبر: mail_message و account_move_line و ir_attachment و stock_move.
  • الظبط بالقياس: pg_stat_statements مترتب بالوقت الكلي، و EXPLAIN (ANALYZE, BUFFERS)، وبعدين models.Index. جدول كبير: CONCURRENTLY الأول بنفس الاسم.
  • الـ connections: (workers + max_cron_threads) × db_maxconn + db_maxconn_gevent + ops لازم أقل من max_connections. و Odoo بيستخدم LISTEN و session advisory locks.
  • سطر الـ access بيخلص بـ query_count query_time remaining_time cursor_mode. remaining_time كبير و query_time صغير على طلب فاشل معناه نوم الـ retries.
  • /web/health لوحده مش بيلمس Postgres. ضيف ?db_server_status=1، واعمل probes لتأخير الـ cron والإيميل وفرق الفلوس والشهادات والديسك.
  • نادي حد عند حرق 14.4 على ساعة و5 دقايق، وافتح تذكرة عند حرق 6 على 6 ساعات.
  • Docker: ثبّت tag بتاريخ، اعمل mount للـ config كـ secret، و volume بتاع postgres:18 على /var/lib/postgresql.
  • SKIP LOCKED بيحمي حجز الـ job مش الصفوف اللي بيكتبها. قسّم بـ _commit_progress وكمّل من الـ state.
  • الـ transaction الطويلة بتوقف الـ vacuum في كل مكان: راقب idle in transaction و age(backend_xmin).
  • retrying() بيعيد الطلب كله لحد 5 مرات. المكالمات الخارجية مكانها postcommit أو outbox.
  • تحت الـ contention، الـ retries بتطلع والإنتاجية بتنزل والـ CPU ثابت. تقصير الـ lock مش بيفيد في REPEATABLE READ؛ قصّر الـ transaction أو وحّد الشغل في مكان واحد.
