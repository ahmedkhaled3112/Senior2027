Why this matters · ليه ده مهم

English

You've seen the document flow and double-entry on paper. This lesson connects them on a running system: which click creates which row, and, just as important, which click creates no accounting at all. Every integration you'll build pushes data into the middle of these flows. If you don't know that a delivery posts nothing while an invoice posts three lines, you can't tell whether a sync bug lost money or just hasn't reached the step that records it.

بالعامية

إنت شفت مسار المستندات والـ double-entry على الورق. الدرس ده بيوصلهم ببعض على نظام شغال: أنهي click بتعمل أنهي row، والأهم، أنهي click مبتعملش أي محاسبة خالص. كل integration هتبنيه بيدخل data في نص المسارات دي. لو مش عارف إن الـ delivery مبيعملش قيد وإن الفاتورة بتعمل 3 سطور، مش هتقدر تفرّق بين sync bug ضيّع فلوس وبين خطوة لسه موصلتش للمرحلة اللي بتسجلها.

Part 1 — A company from scratch 🟢 Basicالجزء 1 — شركة من الصفر

English

A company in Odoo is a res.company row with a country and a currency, and at first it has no books at all: 0 accounts. env['account.chart.template'].try_loading('eg', company, install_demo=False) loads the Egyptian template and creates 215 accounts, 11 taxes and 9 journals. In the UI the same thing is Settings → Users & Companies → Companies → New, then Invoicing → Configuration → Settings → Fiscal Localization.

Then a surprise from the lab: this company has no warehouse. stock's res.company.create does make the locations, sequences and picking types, but it only creates a warehouse under test (if modules.module.current_test:). So anything that needs an operation type fails. Creating a purchase order dies at the database with NotNullViolation on purchase_order.picking_type_id. The fix is one record: env['stock.warehouse'].create({'name': ..., 'code': ..., 'company_id': co.id}), or Inventory → Configuration → Warehouse Management → Warehouses → New. That one record builds the stock location and the Receipts and Delivery Orders operation types.

All the snippets in this lesson form one script, run in order inside odoo-bin shell. Without env.cr.commit() the shell rolls everything back at the end, so you can run it repeatedly. The database has Arabic loaded, so p0_common.py forces lang='en_US'; in your own screens journal and document names may show in Arabic, like الفاتورة/2026/00010.

Part 2 — Localizations 🟢 Basicالجزء 2 — الـ Localizations

English

A fiscal localization is a module that supplies a country's accounting content. l10n_eg and l10n_sa each ship a chart of accounts, taxes, tax groups and fiscal positions as CSV files in data/template/, plus tax reports as XML. They contain no accounting logic; the engine is account. Their manifests declare 'countries': ['eg'] and 'auto_install': ['account']. E-invoicing is separate: l10n_eg_edi_eta and l10n_sa_edi (lessons 31 and 32).

A fiscal position is a mapping rule: for a customer it swaps the default tax or account for another. Both charts ship two, domestic and foreign. The template database already has both companies, so you can compare them directly. The first accounts are identical, but the chart sizes differ (215 and 225), the standard rate differs (14% in Egypt, 15% in Saudi Arabia), and each has its own tax return.

The Egyptian company here has 12 taxes against Nile Traders' 11. The last line of the output shows why: 2% WTH is a withholding tax with the external ID account.4_withholding_demo_tax, so it comes from the template's demo data. It's a useful habit: when two "identical" setups differ, diff them instead of guessing.

Part 3 — Users and multi-company context 🟢 Basicالجزء 3 — الـ Users وسياق الشركات

English

Three fields on res.users decide what a person can do. group_ids (renamed from groups_id) holds roles. company_ids is the set of companies they may ever access, and company_id is the default. On top of that, each request carries allowed_company_ids in the context: the companies currently ticked in the switcher at the top right. The first id is the active company, which is where new records go.

The run below creates an accountant (account.group_account_manager) and a salesperson (sales_team.group_sale_salesman). with_user drops superuser mode, so access is really checked. Mona sees both quotations and all 27 journal entries. Omar sees only his 1 quotation, because the ir.access rule named Personal Orders filters on user_id, and only 3 customer invoices, from a similar rule. He can't read account.payment or create account.move.

The context can narrow what you see but can't widen it: asking for a company you don't belong to raises AccessError. The full security model is lesson 19.

def make_user(name, login, group_xmlid):
    groups = [env.ref('base.group_user').id, env.ref(group_xmlid).id]
    return env['res.users'].with_context(no_reset_password=True).create({
        'name': name, 'login': login, 'company_id': eg_co.id,
        'company_ids': [Command.set([eg_co.id])], 'group_ids': [Command.set(groups)],
    })

    # الـ with_user بيشيل الـ sudo فالـ access بيتفحص بجد
    records = e[model].with_user(user).with_context(allowed_company_ids=[eg_co.id])
    try:
        records.check_access(operation)
        return f'yes ({records.search_count([])} rows)'
    except AccessError:
        return 'NO'

بالعامية

3 fields على res.users بيحددوا الشخص يقدر يعمل إيه. group_ids (كان اسمه groups_id) فيه الأدوار. company_ids الشركات اللي مسموحله يدخلها أصلًا، وcompany_id الافتراضية. وفوق ده كل request شايل allowed_company_ids في الـ context: الشركات المتعلّم عليها دلوقتي في الـ switcher فوق على اليمين. أول id هي الشركة الشغالة، وهي اللي الـ records الجديدة بتروحلها.

الكود بيعمل محاسبة (account.group_account_manager) وبائع (sales_team.group_sale_salesman). with_user بيشيل الـ superuser mode فالصلاحيات بتتفحص بجد. منى شايفة عرضين السعر وكل الـ 27 قيد. عمر شايف عرضه الواحد بس، لأن قاعدة ir.access اسمها Personal Orders بتفلتر على user_id، و3 فواتير عملاء بس من قاعدة شبهها. ومايقدرش يقرا account.payment ولا يعمل account.move.

الـ context يقدر يضيّق اللي بتشوفه بس مايقدرش يوسّعه: لو طلبت شركة مش تبعك هيرمي AccessError. الـ security كله في درس 19.

فين هستخدمه في شغلي؟ Node integration بـ API key بتاع admin بيشوف كل الشركات، فأوردر تبع السعودية يدخل بالغلط في شركة مصر. الصح: user مخصوص للـ integration، company_ids بتاعه الشركات المطلوبة بس، وصلاحياته أقل حاجة ممكنة، وتبعت allowed_company_ids في الـ context في كل call. زي الـ tenant isolation بالظبط، بس الفحص جوه الـ ORM.
Interview question "Same user, same record, different result between two API calls. Where do you look in Odoo?" → The context. allowed_company_ids changes which rows pass the company rule and where new records land. Then the user's groups, then the ir.access domains for that model.
"نفس الـ user ونفس الـ record ونتيجة مختلفة بين API calls. تدور فين في Odoo؟" ← الـ context. allowed_company_ids بيغيّر أنهي rows تعدي من قاعدة الشركات وفين الـ records الجديدة بتتحط. بعدها الـ groups بتاعة الـ user، وبعدها الـ domains بتاعة ir.access للـ model ده.

English

The UI path on your practice instance, with EG Company selected in the switcher and a warehouse created for it:

  1. Sales → Orders → Quotations → New: pick a customer, add a product with Track Inventory on, then Confirm.
  2. Click the Delivery smart button, then Validate.
  3. Back on the order: Create Invoice → Create Draft, then Confirm on the invoice.

The same flow in code shows what each step really does. action_confirm moves the order to sale, creates the delivery and reserves stock: on hand stays 20 while reserved becomes 3. button_validate moves the goods: on hand 17, reserved 0, and still no journal entry. _create_invoices makes a draft with no number (name is False), and action_post turns it into three lines. The default invoice_policy is order, which is why it could be invoiced even before delivery.

Payment is a second entry. The wizard behind the Pay button, account.payment.register, debits Outstanding Receipts, not the bank account, and credits Receivable, then reconciles against the invoice. The cash reaches the Bank account only when a bank statement line is matched (lesson 24).

English

The UI path: Purchase → Orders → Requests for Quotation → New, pick a vendor and product, Confirm Order. Click Receive (or the Receipt smart button) and Validate. Part 6 — Periodic versus perpetual, first look 🟡 Intermediateالجزء 6 — Periodic قصاد Perpetual، أول نظرة

English

If you've read older Odoo material, expect a surprise. res.company.inventory_valuation defaults to periodic, and real_time is labelled Perpetual (at invoicing). In both modes a receipt and a delivery created 0 account.move records in this run. The difference shows up on the documents.

Periodic: the vendor bill debits an expense account, as if the goods were consumed when bought. The customer invoice has only revenue and VAT. Stock value reaches the books at closing. Perpetual: the bill debits the stock account (an asset), and the customer invoice adds two lines: Dr COGS 1,800 (3 units × 600) and Cr Inventory 1,800. The mode is set per product category through property_valuation.

Note which account took the cost: 424800 Other Expenses, because that's the default expense account in the Egyptian chart. A real setup gives the category a proper cost-of-sales account; ask the accountant. Lesson 22 explains valuation fully.

بالعامية

لو قريت حاجات قديمة عن Odoo استعد لمفاجأة. res.company.inventory_valuation الافتراضي بتاعه periodic، وreal_time اسمه Perpetual (at invoicing). وفي الاتنين الاستلام والتسليم عملوا 0 account.move في التشغيل ده. الفرق بيبان على المستندات.

Periodic: فاتورة المورد بتعمل debit لحساب مصروف، كأن البضاعة اتصرفت لحظة ما اتشرت. فاتورة العميل فيها إيراد وضريبة بس. وقيمة المخزون بتوصل الدفاتر وقت الإقفال. Perpetual: فاتورة المورد بتعمل debit لحساب المخزون (أصل)، وفاتورة العميل بتزيد سطرين: مدين COGS بـ 1,800 (3 وحدات × 600) ودائن Inventory بـ 1,800. الـ mode بيتحدد على مستوى الـ product category بـ property_valuation.

لاحظ أنهي حساب شال التكلفة: 424800 Other Expenses، لأن ده حساب المصروف الافتراضي في الـ chart المصري. الإعداد الحقيقي بيدي الـ category حساب تكلفة مبيعات صح، واسأل المحاسب. درس 22 بيشرح الـ valuation كله.

فين هستخدمه في شغلي؟ Dashboard للـ gross margin بتبنيه من account_move_line. لو الشركة periodic، COGS مش هيظهر في فواتير العملاء أصلًا، والـ margin هيطلع مبالغ فيه طول الشهر وبعدين يقع وقت الإقفال. اسأل عن الـ valuation mode قبل ما تكتب الـ query. الغلطة الشائعة إنك تفترض إن كل بيعة بتعمل COGS.
Trade-off Periodic is simpler and needs less configuration, but margins are only right after closing. Perpetual gives margin per invoice, but needs correct stock and cost accounts on every category, and a wrong cost flows straight into the ledger.
Periodic أبسط ومحتاج إعدادات أقل، بس الـ margins مبتبقاش صح غير بعد الإقفال. Perpetual بيديك margin لكل فاتورة، بس محتاج حسابات مخزون وتكلفة صح على كل category، وأي تكلفة غلط بتنزل في الـ ledger على طول.

English

The script prints two views: only the entries created in this lesson, so each number can be traced, and the whole EG Company including its demo data. Both must balance. That's the invariant from lesson 2, now asserted against a real system.

// الفلوس بالقروش عشان نبعد عن float، زي ما اتشرح في درس 04
type Cents = number;
interface Line { account: string; debit: Cents; credit: Cents }
interface Entry { memo: string; lines: Line[] }

function assertBalanced(entry: Entry): Entry {
  const debit = entry.lines.reduce((sum, l) => sum + l.debit, 0);
  const credit = entry.lines.reduce((sum, l) => sum + l.credit, 0);
  if (debit !== credit) throw new Error(`${entry.memo} unbalanced: ${debit} <> ${credit}`);
  return entry;
}

// الفاتورة: مديونية على العميل قصاد إيراد وضريبة
function invoiceEntry(net: Cents, vatRate: number): Entry {
  const vat = Math.round(net * vatRate);
  return assertBalanced({
    memo: "customer invoice",
    lines: [
      { account: "Accounts Receivable", debit: net + vat, credit: 0 },
      { account: "VAT Output", debit: 0, credit: vat },
      { account: "Sales", debit: 0, credit: net },
    ],
  });
}

// الدفع: المديونية بتتقفل والفلوس لسه في حساب وسيط لحد كشف البنك
function paymentEntry(amount: Cents): Entry {
  return assertBalanced({
    memo: "customer payment",
    lines: [
      { account: "Outstanding Receipts", debit: amount, credit: 0 },
      { account: "Accounts Receivable", debit: 0, credit: amount },
    ],
  });
}

const invoice = invoiceEntry(300_000, 0.14);
const payment = paymentEntry(342_000);
const balances = new Map<string, Cents>();
for (const line of [...invoice.lines, ...payment.lines]) {

}
console.log(Object.fromEntries(balances));

Cheat sheet · الخلاصة

  • Setup order: res.company → try_loading('eg', co) → stock.warehouse → users. No warehouse is made for you outside tests.

  • P2P: button_confirm → button_validate → action_create_invoice → set invoice_date → action_post → pay.

  • Default is periodic. real_time = Perpetual (at invoicing): bill debits stock, invoice adds COGS.
  • Trial balance in Community: _read_group on posted lines. Debits must equal credits.
