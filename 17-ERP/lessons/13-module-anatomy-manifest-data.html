Why this matters · ليه ده مهم

English

In Odoo the module is the unit of deployment. Tables, views, permissions, seed data and upgrade scripts all travel in one folder, and -i and -u are your release pipeline. In Node those jobs are spread over package.json, a migration tool and a seed script. Here one convention does all of it, and the failures are quiet: during this lesson's runs a module from the wrong series "installed" with exit code 0 and created nothing, an upgrade restarted a customer's invoice numbering at 1, and a missing depends passed today and took the whole database down at the next restart. Every one of those is a question you get asked on an Odoo project.

بالعامية

في Odoo الـ module هو وحدة الـ deployment. الـ tables والـ views والصلاحيات والـ seed data وسكريبتات الـ upgrade كلهم ماشيين في فولدر واحد، و-i و-u هما الـ release pipeline بتاعك. في Node الشغل ده متقسم بين package.json وأداة migrations وسكريبت seed. هنا convention واحدة بتعمل كل ده، والأعطال بتحصل في صمت: في التجارب بتاعة الدرس ده module من series غلط "اتسطّب" بـ exit code 0 ومعملش حاجة، وupgrade رجّع ترقيم فواتير العميل لـ 1، وdepends ناقصة عدّت النهارده ووقّعت الـ database كلها في الـ restart اللي بعده. كل واحدة من دول سؤال هيتسأل لك في أي مشروع Odoo.

Part 1 — The manifest 🟡 Intermediateالجزء 1 — الـ manifest

English

__manifest__.py marks a folder as a module. It looks like Python but it's a single dict literal: Odoo reads it with ast.literal_eval, so an import, a variable or a function call in it fails. That's the first difference from a JavaScript config file, which can run code.

The keys that matter: depends is the load order and the dependency graph (an empty list is replaced with ['base']); data lists files loaded on every install and upgrade, in the order written; demo lists files loaded only on demo databases; assets adds JS, CSS and templates to named bundles; version drives migration scripts. A missing author or license only logs a warning, and the license defaults to LGPL-3.

The version must belong to the running series. adapt_version prefixes short versions with the series, and check_version rejects any full version from another one. A rejected module doesn't raise anything: it is marked uninstallable, Odoo logs a warning, and the command exits 0.

مقارنة بالـ package.json صف بصف:

  • name وsummary زي name وdescription: نص بيظهر في شاشة الـ Apps، والاسم التقني الحقيقي هو اسم الفولدر.
  • version بتتسجّل في latest_version، وهي اللي بتحدد أنهي migration scripts تشتغل.
  • depends زي dependencies بس معاها ترتيب التحميل وبتسطّب الأهالي تلقائي، ومفيهاش version ranges.
  • external_dependencies بتتأكد من Python packages والبرامج قبل الـ install.
  • data زي الـ migrations مع الـ seed: records بتتحمّل في الـ install وفي كل upgrade.
  • demo زي seed للـ dev بس: للـ databases اللي فيها demo.
  • assets زي entry points الـ bundler: بتضيف ملفات لـ bundles زي web.assets_backend.
  • license وauthor لو ناقصين بييجي warning بس، والتراخيص هنشرحها في درس 37.

بالعامية

__manifest__.py هو اللي بيخلي الفولدر module. شكله Python بس هو dict literal واحد: Odoo بيقراه بـ ast.literal_eval، فأي import أو variable أو function call جواه هيفشل. ودي أول حاجة مختلفة عن config بتاع JavaScript اللي ممكن يشغّل كود.

المفاتيح المهمة: depends هي ترتيب التحميل والـ dependency graph (لو سبتها فاضية بتتبدّل بـ ['base']). data ملفات بتتحمّل في كل install وupgrade بالترتيب اللي كتبته. demo ملفات للـ databases اللي فيها demo بس. assets بتضيف JS وCSS وtemplates لـ bundles بالاسم. version هي اللي بتشغّل الـ migration scripts. لو author أو license ناقصين بييجي warning بس، والـ license بتبقى LGPL-3 by default.

الـ version لازم تكون من الـ series الشغالة. adapt_version بتحط الـ series قدام الـ versions القصيرة، وcheck_version بترفض أي version كاملة من series تانية. والـ module المرفوضة مش بترمي error: بتتعلّم uninstallable، وOdoo بيكتب warning، والأمر بيخلص بـ exit 0.

فين هستخدمه في شغلي؟ بتعمل port لـ module من Odoo 19 وبتشغّل CI بيعمل -i ويبص على الـ exit code. الـ pipeline هتبقى خضرا والـ module مش متسطّبة أصلًا. عشان كده خطوة الـ CI لازم تسأل الـ database عن state = 'installed' وlatest_version بعد الأمر، زي ما بتعمل smoke test بعد deploy لـ API بدل ما تثق في exit code الـ deploy script.
Interview question "Your CI runs odoo-bin -i my_module --stop-after-init and it passes, but the module isn't there. How is that possible?" → The exit code doesn't prove the install. A version from another series marks it uninstallable, and a mistyped name logs invalid module names, ignored; both exit 0. Assert state and latest_version in ir_module_module.
"الـ CI بيشغّل odoo-bin -i my_module --stop-after-init وبيعدّي، بس الـ module مش موجودة. إزاي؟" ← الـ exit code مش دليل على الـ install. version من series تانية بتعلّمها uninstallable، واسم غلط بيطلّع invalid module names, ignored، والاتنين بيخلصوا بـ exit 0. لازم تعمل assert على state وlatest_version في ir_module_module.

Part 2 — Folder layout and a first module 🟡 Intermediateالجزء 2 — هيكل الفولدرات وأول module

English

Only two files are mandatory: __manifest__.py and __init__.py. Odoo's addons-path check looks for exactly that pair. Everything else is convention, but a strong one: reviewers and tools expect it. odoo-bin scaffold generates a skeleton to start from.

Two things to know about the scaffold in this 20.0 checkout. It omits license, so every run warns. And it still writes security/ir.model.access.csv, a format that no longer exists: the line is commented out in the manifest, and uncommenting it fails with KeyError: 'ir.model.access'. Access rules in Odoo 20 live in security/ir.access.csv (lesson 19 goes deep).

Python files must be imported to exist. The manifest lists data files, not code; a model is only registered if the __init__.py chain imports it.

فيه ملفين بس إجباريين: __manifest__.py و__init__.py، وده بالظبط اللي الـ addons-path check بيدور عليه. الباقي convention بس قوية: الـ reviewers والأدوات متوقعينها. odoo-bin scaffold بيعملك skeleton تبدأ منه.

حاجتين تعرفهم عن الـ scaffold في نسخة 20.0 دي: مش بيحط license فكل تشغيل بييجي warning. ولسه بيكتب security/ir.model.access.csv، وده format مبقاش موجود: السطر بتاعه commented في الـ manifest، ولو شلت الـ comment هتاخد KeyError: 'ir.model.access'. الصلاحيات في Odoo 20 مكانها security/ir.access.csv (درس 19 بيدخل فيها بالتفصيل).

ملفات الـ Python لازم يتعملها import عشان تبقى موجودة. الـ manifest بيعدّ ملفات الـ data مش الكود، والـ model مش بتتسجّل غير لو سلسلة __init__.py وصلتلها.

فين هستخدمه في شغلي؟ لو المتجر بتاعك مبني بـ Node وعايز المرتجعات تتسجّل في Odoo، الـ refund_request دي هي المكان اللي بيعيش فيه الـ domain ده جوه الـ ERP: الـ model والصلاحيات والشاشة. وفي الـ code review أول حاجة تبص عليها: هل كل model جديدة ليها سطر في ir.access.csv، وهل متعملها import. زي ما بتتأكد إن route جديد في Express اتسجّل في الـ router.

Part 3 — Install and upgrade 🟡 Intermediateالجزء 3 — الـ install والـ upgrade

English

--addons-path is a comma-separated list of folders that contain modules. Reading tools/config.py: a path that doesn't exist, or that holds no module, logs a warning and is skipped, so a typo there shows up later as "module not found". -i installs modules that are uninstalled; on an installed module it does nothing. -u upgrades installed modules: it reloads Python, updates the schema, reloads data files and runs migrations. --stop-after-init exits when loading ends, which is what you want in scripts and CI.

A pure Python method change needs only a restart. A new field, a changed field or any XML or CSV change needs -u. Each module's work runs in the database transaction and is committed when that module finishes, so a failure rolls back the module in progress only. In a real -u refund_request,refund_no_id run, the second module failed and the first one's changes stayed.

depends decides load order: modules load sorted by phase, depth and name. A missing dependency can pass by luck. When the parent is already installed, the new module installs afterwards in a later phase and succeeds. At the next plain start everything is in one phase, the module's depth is small, it loads before its real parent, and the registry fails.

odoo-bin -u refund_request            per module, inside load_module_graph()

  pre-migrate scripts          (upgrade only)
        |
  import Python, register models
        |
  init_models: CREATE TABLE / ALTER TABLE
        |
  load 'data' files in manifest order   (mode: init or update)
        |
  load 'demo' files            (only if this database has demo)
        |
  post-migrate scripts         (upgrade only)
        |
  post_init_hook               (install only)
        |
  state = installed, latest_version = X, COMMIT
        |
  after all modules: end-migrate scripts, then delete records
  whose External ID was not loaded this time (_process_end)
الترتيب لكل module جوه load_module_graph: الأول سكريبتات pre-migrate (في الـ upgrade بس)، بعدها الـ Python يتعمله import والـ models تتسجّل، بعدها init_models تعمل CREATE TABLE أو ALTER TABLE، بعدها ملفات data بترتيب الـ manifest، بعدها demo لو الـ database فيها demo، بعدها post-migrate، بعدها post_init_hook (في الـ install بس)، وفي الآخر الـ state تبقى installed وتتسجّل الـ version ويحصل COMMIT. وبعد ما كل الـ modules تخلص: سكريبتات end-migrate، وبعدها _process_end بتمسح أي record الـ External ID بتاعه متحمّلش المرة دي.

  • module upgrade --outdated all: بيعمل upgrade بس للي عندها version أحدث على الـ disk. ده من الـ --help ومشغّلتوش هنا.
بالعامية

--addons-path لستة فولدرات مفصولة بفاصلة، كل فولدر جواه modules. من قراءة tools/config.py: الـ path اللي مش موجود أو مفيهوش module بياخد warning ويتساب، فغلطة كتابة هناك بتظهر بعدين كـ "module مش موجودة". -i بيسطّب الـ modules اللي حالتها uninstalled، ولو متسطّبة مبيعملش حاجة. -u بيعمل upgrade للمتسطّبة: بيعيد تحميل الـ Python، ويحدّث الـ schema، ويعيد تحميل ملفات الـ data، ويشغّل الـ migrations. --stop-after-init بيخرج لما التحميل يخلص، وده اللي عايزه في السكريبتات والـ CI.

لو غيّرت method في الـ Python بس، restart كفاية. لو field جديد أو field اتغيّر أو أي XML أو CSV، لازم -u. شغل كل module بيحصل في الـ transaction وبيتعمله commit لما الـ module دي تخلص، فالفشل بيرجّع الـ module اللي شغالة دلوقتي بس. في تشغيل حقيقي لـ -u refund_request,refund_no_id التانية فشلت وتغييرات الأولى فضلت. يعني الـ upgrade لكذا module مش atomic.

depends هي اللي بتحدد ترتيب التحميل: الـ modules بتتحمّل مترتبة بالـ phase والـ depth والاسم. الـ dependency الناقصة ممكن تعدّي بالحظ: لو الأب متسطّب أصلًا، الـ module الجديدة بتتسطّب بعده في phase متأخرة وتنجح. بس في الـ start العادي اللي بعده كله في phase واحدة، والـ depth بتاعها صغير، فبتتحمّل قبل الأب الحقيقي والـ registry بيقع. والغلطة الشائعة هنا إنك تقول "اتسطّبت عندي يبقى تمام".

وفي المقارنة بـ Node: -u هو npm install مع prisma migrate deploy مع الـ seed في أمر واحد.

فين هستخدمه في شغلي؟ الـ deploy بتاع Odoo على production: -u للـ modules اللي اتغيّرت، بعد backup، في maintenance window. وفي الـ CI لازم يبقى فيه job بيعمل install على database فاضية، لأن الـ depends الناقصة مش هتظهر على نسخة staging اللي كل حاجة متسطّبة فيها. ده نفس سبب إنك بتشغّل الـ migrations بتاعة Postgres من الصفر في CI مش بس على آخر نسخة.
Trade-off: Odoo's upgrade against a migration tool Odoo derives the schema from the Python classes, so there are no migration files to write for additive changes. The price is less review: you don't see the SQL in a pull request, and destructive changes happen without a prompt (lesson 14 shows a rename deleting a column). With a tool such as Prisma Migrate the SQL is a reviewed file. Link: section 09 · safe migrations.
Odoo بيستنتج الـ schema من الـ Python classes، فمفيش migration files تكتبها للإضافات. التمن إن الـ review أقل: مش بتشوف الـ SQL في الـ pull request، والتغييرات المدمرة بتحصل من غير ما يسألك (درس 14 بيوريك rename بيمسح عمود). في أداة زي Prisma Migrate الـ SQL ملف بيتراجع. وعندك درس الـ safe migrations في قسم 09.

Part 4 — Data files and External IDs 🟡 Intermediateالجزء 4 — ملفات الـ data والـ External IDs

English

A data file is a declarative list of records, in XML or CSV. In XML each <record> has an id and a model. In CSV the model comes from the file name (refund.reason.csv) and the id column holds the identifier.

Each id becomes a row in ir.model.data: (module, name) → (model, res_id), unique on (module, name). The full name is module.xml_id. So an External ID is a stable name for a row whose database id differs on every installation. Inside a file, ref="..." resolves one to its database id, and eval="..." runs a restricted Python expression with ref, Command, datetime, relativedelta and a few others. In code it's env.ref('module.xml_id').

This is why loading is idempotent. On each load Odoo looks up the External ID: found means update, not found means create. It is the idempotency key of Odoo's data layer, the same idea as INSERT … ON CONFLICT on a natural key. Two consequences follow, both measured below. A record with no id has no key: it's created on install and fails the upgrade. And a record you remove from a file is deleted from the database on the next upgrade, because Odoo treats the file as the desired state.

        <field name="code">DMG</field>
        <!-- القيمة دي expression بيتحسب: 14 -->
        <field name="max_days" eval="7 * 2"/>

بالعامية

ملف الـ data هو لستة declarative بالـ records، XML أو CSV. في الـ XML كل <record> ليه id وmodel. في الـ CSV الـ model جاي من اسم الملف (refund.reason.csv) وعمود id فيه الـ identifier.

كل id بيبقى صف في ir.model.data: (module, name) بيشاور على (model, res_id)، و(module, name) unique. الاسم الكامل module.xml_id. يعني الـ External ID اسم ثابت لصف الـ database id بتاعه بيختلف من تسطيبة للتانية. جوه الملف ref="..." بيحوّله لـ database id، وeval="..." بيشغّل Python expression محدود فيه ref وCommand وdatetime وrelativedelta وحاجات قليلة تانية. وفي الكود env.ref('module.xml_id').

وده سبب إن التحميل idempotent. في كل load، Odoo بيدور على الـ External ID: لو لقاه يعمل update، لو ملقاهوش يعمل create. يعني ده الـ idempotency key بتاع data layer الـ Odoo، نفس فكرة INSERT … ON CONFLICT على natural key (وعندك درس الـ idempotency keys). والنتيجة حاجتين جربناهم: record من غير id ملوش key، فبيتعمل في الـ install وبيوقّع الـ upgrade. وrecord تشيله من الملف بيتمسح من الـ database في الـ upgrade الجاي، لأن Odoo بيعتبر الملف هو الـ desired state. الفكرة دي هنرجعلها في درس 28 (الـ sync) ودرس 29 (الـ data migration).

فين هستخدمه في شغلي؟ بتعمل sync للعملاء من المتجر بتاعك لـ Odoo. لو كل retry عمل create هتلاقي العميل متكرر. لو استخدمت External ID زي shop_sync.customer_8841 مبني على الـ id بتاعك، نفس الـ request يتبعت 5 مرات والنتيجة record واحد. وفي الـ code review: لو حد شال <record> من ملف data عشان "مبقاش محتاجه"، اسأله: عارف إن ده هيمسح الصف من database العميل؟
Interview question "Why does Odoo need External IDs if every row already has a primary key?" → The primary key is assigned per database, so the same record has different ids on staging and production. The External ID is a stable, module-scoped name, which is what lets a data file be loaded repeatedly as an upsert, and lets other modules reference the record.
"ليه Odoo محتاج External IDs طالما كل صف ليه primary key؟" ← الـ primary key بيتحدد لكل database لوحدها، فنفس الـ record ليه ids مختلفة على staging وproduction. الـ External ID اسم ثابت ومربوط بالـ module، وده اللي بيخلي ملف الـ data يتحمّل كذا مرة كـ upsert، وبيخلي modules تانية تشاور على الـ record.

Part 5 — noupdate 🟡 Intermediateالجزء 5 — الـ noupdate

English

By default -u rewrites every field listed in the file, on every upgrade. That's right for views, and wrong for anything the customer is meant to change. <odoo noupdate="1"> means: create these records once, then leave them alone. The flag is stored per record in ir_model_data.noupdate.

Details the run below confirms. Only fields written in the XML are reset; a field the file doesn't mention keeps the customer's value. A deleted noupdate record comes back on upgrade unless it has forcecreate="0". The database flag wins over the file: removing noupdate="1" from the file does not release records already created, so to change one in a release, clear ir_model_data.noupdate or write the change in a migration script. And --reinit ignores the protection entirely.

The expensive mistake: a sequence with number_next in a file without noupdate. Every upgrade restarts the numbering, and the next refund gets a number already issued.

<?xml version="1.0" encoding="utf-8"?>
<!-- الفلاج ده معناه: اعمل الـ records مرة واحدة وسيبها للعميل -->

    <record id="reason_late" model="refund.reason">
        <field name="name">Late delivery</field>

بالعامية

تفاصيل التجربة أكدتها: الـ fields المكتوبة في الـ XML بس هي اللي بترجع، والـ field اللي الملف مش جايب سيرته بيفضل بقيمة العميل. الـ record بتاع noupdate لو اتمسح بيرجع في الـ upgrade إلا لو عليه forcecreate="0". فلاج الـ database بيكسب الملف: لو شلت noupdate="1" من الملف، الـ records اللي اتعملت قبل كده مش بتتحرر، فعشان تغيّر واحد في release لازم تصفّر ir_model_data.noupdate أو تكتب التغيير في migration script. و--reinit بيتجاهل الحماية خالص.

الغلطة الغالية: sequence فيها number_next في ملف من غير noupdate. كل upgrade بيرجّع الترقيم، والـ refund الجاي ياخد رقم اتصرف قبل كده.

فين هستخدمه في شغلي؟ العميل غيّر قالب إيميل المرتجعات بعد مراجعة الـ legal، وبعد شهر نزلت أنت bugfix وعملت -u. لو القالب مش noupdate صياغته راحت من غير أي error، وهتعرف من شكوى. القاعدة في الـ review: أي حاجة العميل ممكن يعدّلها (sequences، mail templates، default settings، reasons) تروح في ملف noupdate="1". والـ views والـ actions والـ menus تفضل من غيره عشان تتحدّث.
What breaks: duplicate document numbers A restarted sequence doesn't fail at the moment it happens. It fails later, when two refunds or invoices carry the same number. On a legal document that's an audit problem, and it needs a data fix, not a redeploy.
الـ sequence اللي رجعت من الأول مش بتقع وقتها. بتقع بعدين لما يبقى فيه اتنين refund أو فاتورتين بنفس الرقم. وفي مستند قانوني دي مشكلة audit، وعلاجها data fix مش redeploy.

Part 6 — Demo data and hooks 🟡 Intermediateالجزء 6 — الـ demo data والـ hooks

English

data is for records the module needs to work; demo is for examples. --with-demo applies when a database is created. After that, a module's demo files load only if all its dependencies have demo enabled (demo_installable). Demo records are loaded with noupdate on, as the demo_refund_1 row in Part 4 shows. Never put a record the module depends on in demo: production databases don't have it.

Hooks are plain functions in the module's __init__.py, named in the manifest, and they receive env. pre_init_hook runs before the module's tables exist, post_init_hook after its data is loaded, uninstall_hook during uninstall. The first two run on install only, never on upgrade; for upgrades you need a migration script.

A real trap when copying older tutorials: ir.config_parameter.set_param is gone in Odoo 20. A hook calling it raises AttributeError, the registry fails to load, and the install rolls back. Use set_str, set_int, set_bool, set_float, and the matching get_*.

{
    'name': 'Refund hooks',
    'version': '20.0.1.0.0',
    'author': 'Senior2027 Shop',
    'license': 'LGPL-3',
    'depends': ['base'],
    # الأسماء دي functions في __init__.py بتاع الـ module
    'pre_init_hook': 'pre_init',
    'post_init_hook': 'post_init',
    'uninstall_hook': 'uninstall',
}

import logging

_logger = logging.getLogger(__name__)


def pre_init(env):
    # بيشتغل قبل ما tables الـ module تتعمل
    env.cr.execute("SELECT to_regclass('ir_module_module')")
    _logger.info('HOOK pre_init sees table %s', env.cr.fetchone()[0])


def post_init(env):
    # الغلط من tutorial قديم: params.set_param('refund_hooks.max_days', '14')
    params = env['ir.config_parameter'].sudo()
    params.set_int('refund_hooks.max_days', 14)
    _logger.info('HOOK post_init max_days=%s', params.get_int('refund_hooks.max_days'))


def uninstall(env):
    # نضّف اللي الـ module سابته وراها
    env['ir.config_parameter'].sudo().search([('key', '=like', 'refund_hooks.%')]).unlink()
    _logger.info('HOOK uninstall done')

  • عايز تجهّز table كبيرة قبل عمود جديد: pre_init_hook، بيشتغل قبل خطوة الـ schema.
  • عايز تغيّر data في تسطيبة موجودة: migration script، لأن الـ hooks مش بتشتغل في الـ upgrade.
  • عايز تنضّف حاجة مش مربوطة بـ record: uninstall_hook، والـ records اللي ليها External IDs بتتمسح لوحدها.
بالعامية

data للـ records اللي الـ module محتاجاها عشان تشتغل، وdemo للأمثلة. --with-demo بيأثر وقت إنشاء الـ database. بعد كده ملفات الـ demo بتاعة أي module بتتحمّل بس لو كل الـ dependencies بتاعتها فيها demo (demo_installable). وrecords الـ demo بتتحمّل وnoupdate شغال، زي صف demo_refund_1 في الجزء 4. وأوعى تحط record الـ module معتمدة عليه في demo: الـ production مفيهوش.

الـ hooks functions عادية في __init__.py بتاع الـ module، أسماءها في الـ manifest، وبتاخد env. pre_init_hook قبل ما tables الـ module تتعمل، post_init_hook بعد تحميل الـ data، uninstall_hook وقت الـ uninstall. أول اتنين بيشتغلوا في الـ install بس ومش في الـ upgrade، وللـ upgrade محتاج migration script.

فخ حقيقي لما تنقل من tutorials قديمة: ir.config_parameter.set_param اتشالت في Odoo 20. الـ hook اللي بينادي عليها بترمي AttributeError، والـ registry بيقع، والـ install بيترجّع. استخدم set_str وset_int وset_bool وset_float، وget_* المقابلة ليهم.

فين هستخدمه في شغلي؟ بتضيف module لعميل عنده 200 ألف order وعايز تملا field جديد للصفوف القديمة مرة واحدة: post_init_hook في أول تسطيبة. ولو الـ module متسطّبة أصلًا والـ field نازل في version جديدة، الـ hook مش هتشتغل ولازم migration script (درس 36). نفس الفرق في Node بين seed بيشتغل على database جديدة وmigration بتشتغل على الموجودة.
Interview question "You added a post_init_hook to backfill a field and shipped it as an upgrade. Nothing was backfilled. Why?" → post_init_hook runs only on install. On an already-installed module, -u skips it. The backfill belongs in migrations/<version>/post-*.py, with the manifest version bumped so the script runs.
"ضفت post_init_hook يملا field ونزّلته كـ upgrade، ومفيش حاجة اتملت. ليه؟" ← post_init_hook بيشتغل في الـ install بس، والـ -u على module متسطّبة بيعدّيه. الـ backfill مكانه migrations/<version>/post-*.py، ولازم ترفع الـ version في الـ manifest عشان السكريبت يشتغل.

Common mistakes · غلطات شائعة

❌ Trusting "it installed on my database" 
# الكود بيعمل _inherit لـ sale.order بس الـ depends ناقصة
'depends': ['base'],
✅ Declare every module the code touches 
# كده الترتيب مضمون على أي database
'depends': ['sale'],
بالعامية

❌ الـ install عدّى لأن sale كانت متسطّبة، وفي الـ restart اللي بعده الـ registry وقع بـ TypeError: Model 'sale.order' does not exist in registry. والـ server كله مش هيقوم. ✅ اكتب كل module الكود بيلمسها، واختبر الـ install على database فاضية في الـ CI.

❌ A record with no id 
<!-- بيعدّي في الـ install ويوقّع الـ upgrade -->
<record model="refund.reason">
    <field name="name">Other</field>
    <field name="code">OTHER</field>
</record>
✅ Always give it an External ID 
<!-- كده الـ load بقى upsert -->
<record id="reason_other" model="refund.reason">
    <field name="name">Other</field>
    <field name="code">OTHER</field>
</record>
بالعامية

❌ من غير id الـ -i بينجح، والـ -u بيفشل بـ ParseError لأن Odoo ملوش طريقة يعرف بيها أنهي صف يحدّثه، فالمشكلة بتظهر في أول release. ✅ كل <record> ليه id.

❌ Customer-owned record without noupdate 
<!-- كل upgrade بيرجّع الترقيم لـ 1 -->
<odoo>
    <record id="seq_refund" model="ir.sequence">
        <field name="code">refund.request</field>
        <field name="number_next">1</field>
    </record>
</odoo>
✅ Create once, then hands off 
<!-- بيتعمل مرة واحدة والعميل يملكه -->
<odoo noupdate="1">
    <record id="seq_refund" model="ir.sequence">
        <field name="code">refund.request</field>
        <field name="number_next">1</field>
    </record>
</odoo>
بالعامية

❌ الـ sequence رجعت RF/00001 بعد ما كان اتصرف 3 أرقام، يعني أرقام متكررة على مستندات. ✅ مع noupdate="1" كمّلت ACME-RF/00004. نفس الكلام للـ mail templates.

❌ Wrong order in data 
# الـ menu بيشاور على action لسه ما اتحمّلش
'data': ['views/menu.xml', 'views/action.xml'],
✅ Referenced files first 
# الـ action الأول وبعده اللي بيشاور عليه
'data': ['views/action.xml', 'views/menu.xml'],
بالعامية

❌ الملفات بتتحمّل بالترتيب، فالتحميل وقع بـ External ID not found in the system: refund_order_bug.action_refund_report. ✅ حط الملف اللي فيه الـ record قبل اللي بيعمله ref، وبنفس السبب security بييجي بدري.

❌ Hook copied from an old tutorial 
def post_init(env):
    # اتشالت في Odoo 20
    env['ir.config_parameter'].sudo().set_param('refund.days', '14')
✅ The typed API 
def post_init(env):
    # القيمة بترجع int من get_int
    env['ir.config_parameter'].sudo().set_int('refund.days', 14)
بالعامية

❌ set_param بترمي AttributeError وتوقّع الـ install كله. ✅ استخدم الـ API الجديدة: set_str وset_int وset_bool وset_float. وأي كود من tutorial قبل Odoo 20 اقرأه قصاد الـ source الأول.

Try it yourself · جرّب بنفسك

1. Read a scaffold 🟢 easy Run node D:/tools/odoo/odoo.mjs start once so D:/tools/odoo/custom-addons exists, then scaffold a module there. Add license, change the version to 20.0.1.0.0, delete security/ir.model.access.csv, and install it from Apps after "Update Apps List".
شغّل node D:/tools/odoo/odoo.mjs start مرة عشان D:/tools/odoo/custom-addons يتعمل، وبعدين اعمل scaffold لـ module هناك. ضيف license، وغيّر الـ version لـ 20.0.1.0.0، وامسح security/ir.model.access.csv، وسطّبها من Apps بعد "Update Apps List".
Hint · تلميح Turn on developer mode with ?debug=1, or "Update Apps List" won't appear. Remove the "Apps" filter when searching for the module.
شغّل developer mode بـ ?debug=1 وإلا "Update Apps List" مش هتظهر. وشيل فلتر "Apps" وإنت بتدور على الـ module.
2. Prove noupdate 🟡 medium Add two refund.reason records to refund_request, one in a plain file and one in a noupdate="1" file. Edit both in the UI, run -u, and predict which edit survives before you look.
ضيف اتنين refund.reason لـ refund_request، واحد في ملف عادي وواحد في ملف noupdate="1". عدّل الاتنين من الـ UI، شغّل -u، وتوقّع أنهي تعديل هيفضل قبل ما تبص.
Solution · الحل 
-- الاستعلام ده بيوريك الفلاج لكل record
SELECT name, noupdate FROM ir_model_data
WHERE module = 'refund_request' AND model = 'refund.reason'
ORDER BY name;
The edit in the plain file is reset for the fields written in the XML; the one in the noupdate file stays.
تعديل الملف العادي بيرجع للـ fields المكتوبة في الـ XML، وتعديل ملف noupdate بيفضل. شغّل الـ SQL بـ psql و-p 55469 صريحة.
3. Break it and read the log 🔴 hard Make three separate breakages on your practice instance, one at a time: swap the order of two files in data, remove the id from a record and upgrade, and add an _inherit = 'purchase.order' without the dependency, then restart. For each, write down the exit code, the first useful log line, and the state of the module afterwards.
اعمل 3 أعطال منفصلة على الـ practice instance، واحد واحد: بدّل ترتيب ملفين في data، وشيل الـ id من record واعمل upgrade، وضيف _inherit = 'purchase.order' من غير الـ dependency وبعدين restart. لكل واحد اكتب الـ exit code، وأول سطر مفيد في الـ log، وحالة الـ module بعدها.
Hint · تلميح Undo each breakage before the next one. The third can stop the server from starting at all: fix the manifest, then start again.
ارجع عن كل عطل قبل اللي بعده. التالت ممكن يمنع الـ server إنه يقوم خالص: صلّح الـ manifest وابدأ تاني.
4. In your project 🔴 project Build refund_request in D:/tools/odoo/custom-addons for your side project's shop. Add a shop_order_ref field, a noupdate sequence, and a post_init_hook that stores a default refund window with set_int. Add a CI step that installs it on an empty database and asserts state = 'installed'.
ابني refund_request في D:/tools/odoo/custom-addons لمتجر مشروعك الجانبي. ضيف field اسمه shop_order_ref، وsequence بـ noupdate، وpost_init_hook بيخزن مدة المرتجعات الافتراضية بـ set_int. وضيف خطوة CI بتسطّبها على database فاضية وتعمل assert إن state = 'installed'.

Cheat sheet · الخلاصة

  • The manifest is a dict literal. data order matters; depends must list everything the code touches.
  • Version must be 20.0.x.y.z; another series means uninstallable with exit 0.
  • Exit 0 doesn't prove an install: assert state and latest_version.
  • Access rules are security/ir.access.csv; the scaffold's ir.model.access.csv is stale.
  • Python change: restart. Field, XML or CSV change: -u. Always pass -c.
  • Each module commits when it finishes: a multi-module upgrade isn't atomic.
  • External ID = module.name in ir.model.data: the upsert key for data files.
  • No id fails the upgrade; removing a record from a file deletes it.
  • noupdate="1" for anything the customer owns. The flag lives in the database and beats the file; --reinit ignores it.
  • demo never holds required records. Hooks run on install, not upgrade.
  • set_param is gone: set_str, set_int, set_bool, set_float.
بالعامية
  • الـ manifest هو dict literal. ترتيب data مهم، وdepends لازم فيها كل حاجة الكود بيلمسها.
  • الـ version لازم 20.0.x.y.z، وseries تانية معناها uninstallable مع exit 0.
  • الـ exit 0 مش دليل على الـ install: اعمل assert على state وlatest_version.
  • الصلاحيات في security/ir.access.csv، وir.model.access.csv بتاع الـ scaffold قديم.
  • تغيير Python: restart. تغيير field أو XML أو CSV: -u. وحط -c دايمًا.
  • كل module بتعمل commit لما تخلص، فالـ upgrade لكذا module مش atomic.
  • الـ External ID هو module.name في ir.model.data، وده الـ upsert key لملفات الـ data.
  • من غير id الـ upgrade بيفشل، ولو شلت record من الملف بيتمسح.
  • noupdate="1" لأي حاجة العميل بيملكها. الفلاج في الـ database وبيكسب الملف، و--reinit بيتجاهله.
  • demo عمرها ما تشيل records مطلوبة. والـ hooks بتشتغل في الـ install مش الـ upgrade.
  • set_param اتشالت: set_str وset_int وset_bool وset_float.
