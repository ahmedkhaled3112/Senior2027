Why this matters · ليه ده مهم

English

Migration is the part of an ERP project where a bug becomes a wrong balance sheet. The code is ordinary ETL, but the acceptance test is not "the import finished": it is "finance signs that every account, customer, vendor and stock location agrees with the old system". This lesson builds that whole path against a real Odoo 20: a dirty Excel file, an idempotent import, an opening entry, open invoices, opening stock, a reconciliation script with an exit code, and a cutover plan that was run twice. All data here is invented.

بالعامية

الـ migration هو الجزء من مشروع الـ ERP اللي الـ bug فيه بيتحول لميزانية غلط. الكود نفسه ETL عادي، بس الـ acceptance test مش "الـ import خلص": هو إن الماليات تمضي إن كل حساب وكل عميل وكل مورد وكل location في المخزن مطابق للنظام القديم. في الدرس ده هنبني الطريق كله على Odoo 20 حقيقي: ملف Excel مبهدل، import ينفع يتعاد، قيد افتتاحي، فواتير مفتوحة، مخزون افتتاحي، reconciliation script ليه exit code، وخطة cutover اتشغلت مرتين. كل البيانات هنا متألفة.

Part 1 — Mapping and cleaning 🟡 Intermediateالجزء 1 — الـ mapping وتنضيف البيانات

English

Legacy data is rarely wrong in one way. The seeded workbook here has what real ones have: the same customer twice with different Arabic spelling (شركة and شركه), one date column holding five formats including Excel serial numbers and Arabic-Indic digits, negative stock, invoices paid above their total, and a chart of accounts with a different shape: one account per customer plus header rows that carry subtotals.

The pipeline has three rules. Normalize for comparison, not for storage: nameKey folds أ/إ/آ, ة, ى, diacritics and spacing, but the stored name stays as written. Deduplicate on a strong key: the tax number, never the name, and keep a mergeMap from every old code to the surviving one, because invoices still point at the duplicate. Reject with a reason: a row that fails goes to a rejects file a person can act on; it is never silently dropped or silently fixed.

Dates need a declared convention. 05/06/2024 is May or June depending on who typed it, so the source is declared D/M/Y and anything else is rejected. JavaScript also rolls 31/02 over to 3 March, so the parser builds the date and checks that the month and day survived.

// المصدر معلن إنه D/M/Y: من غير القرار ده 05/06 ممكن تبقى مايو أو يونيو
export function parseDate(v: unknown): string | null {
  if (v instanceof Date) return v.toISOString().slice(0, 10);
  if (typeof v === "number") return new Date(Math.round((v - 25569) * 86400000)).toISOString().slice(0, 10);
  if (typeof v !== "string") return null;
  const s = fromArabicDigits(v).trim();
  let y: number, m: number, d: number;
  const iso = s.match(/^(\d{4})-(\d{2})-(\d{2})$/);
  const dmy = s.match(/^(\d{1,2})\/(\d{1,2})\/(\d{4})$/);
  if (iso) [y, m, d] = [+iso[1]!, +iso[2]!, +iso[3]!];
  else if (dmy) [d, m, y] = [+dmy[1]!, +dmy[2]!, +dmy[3]!];
  else return null;
  const date = new Date(Date.UTC(y, m - 1, d));
  // التحقق بالرجوع: 31/02 بتتحول لـ 3 مارس في JS فلازم نقارن
  if (date.getUTCMonth() !== m - 1 || date.getUTCDate() !== d) return null;
  return date.toISOString().slice(0, 10);
}

  });

    counts.Customers.rejected++;
    continue;
  }
  const c = parsed.data;
  const first = survivors.get(c.tax);
  if (first) {
    mergeMap.set(c.code, first.code);
    counts.Customers.merged++;
    if (nameKey(first.name).slice(0, 8) !== nameKey(c.name).slice(0, 8)) reject("Customers", c.code, `same tax as ${first.code}, names differ: review`);

  }
  survivors.set(c.tax, c);
  mergeMap.set(c.code, c.code);
}

function rng(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// الفلوس integer cents من أول سطر: راجع درس الفلوس في القسم
export function cents(v: unknown): number {
  if (v === null || v === undefined || v === "") return 0;
  const s = fromArabicDigits(String(v)).replace(/,/g, "").trim();
  if (!/^-?\d+(\.\d{1,2})?$/.test(s)) throw new Error(`bad money ${JSON.stringify(v)}`);
  const neg = s.startsWith("-");
  const [whole, frac = ""] = s.replace("-", "").split(".");
  const n = Number(whole) * 100 + Number(frac.padEnd(2, "0"));
  return neg ? -n : n;
}

Part 2 — CSV import and external IDs 🟡 Intermediateالجزء 2 — الـ CSV import والـ external IDs

English

Odoo's import format is a table whose id column is an external ID, a stable name such as legacy_mig.customer_C0001 stored in ir.model.data. Load a row whose ID exists and Odoo updates that record; load a new ID and it creates one. A relation is a column with a /id suffix, such as parent_id/id, holding the other record's external ID (/.id takes a database ID). That is what makes a migration re-runnable. Lesson 28 used the same property for live sync.

Two entry points share this format. base_import.import is what the UI uses and has execute_import(..., dryrun=True), which validates and rolls back. load is a public model method, so it can be called through JSON-2 from Node.

Three behaviours, all observed below. Order matters: a child row before its parent fails, so load parents first. A batch is all-or-nothing: one bad row returned ids: false and left no rows from that batch, so batch size is also blast radius. Errors come back as HTTP 200: the failure is in messages, and a client that checks only the status reports success.

export async function loadRows(call: Call, model: string, fields: string[], rows: string[][], batch: number, context: object): Promise<number> {
  let done = 0;
  for (const part of chunk(rows, batch)) {
    const r = await call<LoadResult>(model, "load", { fields, data: part, ...context });
    if (!r.ids || r.messages.some((m) => m.type === "error")) throw new Error(`load failed: ${JSON.stringify(r.messages).slice(0, 300)}`);
    done += r.ids.length;
  }
  return done;
}

Part 3 — Opening balances 🟡 Intermediateالجزء 3 — الأرصدة الافتتاحية

English

The opening balance is one account.move, dated the day before go-live, that recreates the closing trial balance of the old system. In Odoo, res.company.account_opening_date is the go-live date, _get_default_opening_move_values dates the entry one day earlier, and account_opening_move_id points at it. With go-live on 2026-01-01 the entry is dated 2025-12-31.

Receivables and payables do not go in this entry as balances. They will arrive as individual documents in Part 4, so the entry posts those amounts to a dedicated clearing account (399901 here), and the documents post the opposite side. When the migration is complete the clearing account must be exactly zero, which is itself a check.

A trap in Odoo's own helper: importing the opening_balance column or calling _update_opening_move adds an Automatic Balancing Line on the unaffected-earnings account (999999). If your source is off by 100, Odoo does not complain: it invents a 100 line. Convenient for a small company typing in a few balances; dangerous in a migration, because it turns an error into a balanced entry. Build the entry yourself, or assert that 999999 is zero afterwards.

Then prove it: total debits equal total credits, and every account's balance in Odoo equals the legacy trial balance. A balanced entry only shows the two sides agree with each other, not with the old books.

export async function loadRows(call: Call, model: string, fields: string[], rows: string[][], batch: number, context: object): Promise<number> {
  let done = 0;
  for (const part of chunk(rows, batch)) {

    ...inventory,
  });
  await call("stock.quant", "action_apply_inventory", { ids, ...inventory });
  return ids.length;
}

Part 4 — Open invoices and opening stock 🟡 Intermediateالجزء 4 — الفواتير المفتوحة والمخزون الافتتاحي

English

Each unpaid invoice is imported as its own document with its residual as the amount and its original due date. Three dates do different jobs: invoice_date is the legacy date, invoice_date_due drives aging, and date (the accounting date) is the opening date, so nothing lands in the new year. The line uses the clearing account and no taxes, because the revenue and VAT were recorded in the old system. A dedicated journal (OPNS, OPNP) keeps these out of the real numbering sequence, and keeps them away from e-invoicing: these invoices were already issued once.

Opening stock goes through the same mechanism as a physical count: create stock.quant rows with inventory_mode=True and an inventory_quantity, then call action_apply_inventory. The product's standard_price must be set first, because it becomes the value.

Where the value lands in the ledger is the trap, and the run below shows what Odoo 20 actually does. With real_time valuation and the default configuration the adjustment location has no valuation_account_id, so _should_create_account_move is false: stock value becomes 1,000 while the GL stays 0. The opening entry must post it. If someone sets a valuation account on that location, the adjustment does post, and an opening entry on top doubles the GL to 2,000 against a stock value of 1,000. Pick one route. See lesson 22 for valuation itself.

Part 5 — Reconciliation by script 🟡 Intermediateالجزء 5 — الـ reconciliation بـ script

English

Reconciliation is a program, not a person with two spreadsheets, because it runs on every rehearsal and must give the same verdict each time. It compares five things: the trial balance per account, AR per customer, AP per vendor, stock quantity per product and location, and stock value against the GL. Money uses a tolerance of one cent per key; quantities use zero. It prints a diff report and sets the exit code, so a cutover runner can stop on it. Same idea as lesson 06, across two systems.

Granularity is the point. Each of the three errors seeded below passes a coarser check. Error 1 moves 1,000 between two bank accounts, so the trial balance still sums to zero. Error 2 moves an invoice to the wrong customer, so total AR is unchanged. Error 3 changes one location's count. Only a per-key comparison sees them.

One real bug from building this: account.account.code depends on the company, so reading it through JSON-2 without allowed_company_ids returned no usable codes, and 11 accounts all showed a false difference. The check failed loudly, which is the good way to fail; a comparison that silently skipped unknown keys would have passed.

function compare(name: string, unit: Check["unit"], legacy: Map<string, number>, odoo: Map<string, number>, tolerance: number): Check {
  const keys = new Set([...legacy.keys(), ...odoo.keys()]);
  const diffs: Diff[] = [];
  for (const key of keys) {
    const a = legacy.get(key) ?? 0, b = odoo.get(key) ?? 0;
    if (Math.abs(a - b) > tolerance) diffs.push({ key, legacy: a, odoo: b });
  }
  return { name, compared: keys.size, diffs, unit };
}

async function byCode<T extends string>(call: Call, s: Setup, model: string, field: T, m: Map<number, number>): Promise<Map<string, number>> {
  if (!m.size) return new Map();
  const context = { allowed_company_ids: [s.companyId], lang: "en_US" };
  const rows = await call<({ id: number } & Record<T, string>)[]>(model, "read", { ids: [...m.keys()], fields: [field], context });
  return new Map(rows.map((r) => [r[field], m.get(r.id)!]));
}

export function printReport(checks: Check[]): boolean {

  for (const c of checks) {

English

A cutover plan is data: tasks with an owner, an estimate, dependencies, go/no-go gates and a rollback point. As data it can be executed, timed and revised. Lesson 08 covers the project side; this part runs one. The runner blocks any task whose dependency failed, and the gate is the reconciliation script from Part 5.

The rehearsal cycle uses Odoo's CLI: odoo-bin db dump makes a zip with the database and filestore, the import runs, reconciliation decides, then odoo-bin db load -f restores. For test copies, db load -n or odoo-bin neutralize disables outgoing mail, crons (except autovacuum) and webhooks, so a copy cannot email real customers.

Rehearsal paid for itself here. The first restore failed: on Windows, filestore files are read-only and shutil.rmtree refused them, after Odoo had already dropped the database. So the rollback command destroyed the database and then crashed. That is specific to Windows, but the lesson is general: a rollback you have never run is a hope.

The rule that decides everything: rollback is only clean until the first real transaction in the new system. After that, restoring the dump erases real invoices and payments, so rollback has become a data-loss decision that the business must own, usually replaced by fixing forward.

export type Action = () => Promise<string>;

// بينفذ بالترتيب: أي task قبلها فشلت يبقى اللي بعدها ميبدأش
export async function runPlan(plan: Task[], actions: Record<string, Action>): Promise<{ rows: Row[]; go: boolean }> {
  const rows: Row[] = [];
  const done = new Set<string>();
  for (const t of plan) {
    const missing = t.dependsOn.filter((d) => !done.has(d));
    if (missing.length) {
      rows.push({ ...t, actualSec: 0, ok: false, note: `blocked by ${missing.join(",")}` });
      continue;
    }
    const start = performance.now();
    try {
      const note = await actions[t.id]!();
      rows.push({ ...t, actualSec: (performance.now() - start) / 1000, ok: true, note });
      done.add(t.id);
    } catch (e) {
      rows.push({ ...t, actualSec: (performance.now() - start) / 1000, ok: false, note: (e as Error).message.slice(0, 80) });
    }
  }
  return { rows, go: rows.every((r) => r.ok) };
}

export function printRun(label: string, rows: Row[], go: boolean): void {
  console.log(`== ${label} ==`);
  console.log("id  owner      est(s)  actual(s)  status  note");
  for (const r of rows) {
    console.log(`${r.id.padEnd(3)} ${r.owner.padEnd(10)} ${String(r.estimateSec).padStart(6)} ${r.actualSec.toFixed(1).padStart(10)}  ${(r.ok ? "ok" : "FAIL").padEnd(6)}  ${r.note}`);
  }
  const est = rows.reduce((a, r) => a + r.estimateSec, 0);
  const act = rows.reduce((a, r) => a + r.actualSec, 0);
  console.log(`total est=${est}s actual=${act.toFixed(1)}s decision=${go ? "GO" : "NO-GO"}`);
}

خطة الـ cutover هي data: tasks ليها owner وتقدير و dependencies و go/no-go gates و rollback point. ولأنها data تقدر تشغلها وتقيسها وتعدلها. درس 08 بيغطي ناحية المشروع، والجزء ده بيشغّل واحدة فعلًا. الـ runner بيوقف أي task الـ dependency بتاعها فشل، والـ gate هو الـ reconciliation script بتاع الجزء 5.

دورة الـ rehearsal بتستخدم CLI بتاع Odoo: odoo-bin db dump بيعمل zip فيه الـ database والـ filestore، الـ import بيشتغل، الـ reconciliation بيقرر، وبعدين odoo-bin db load -f بيرجّع. ولنسخ التجربة، db load -n أو odoo-bin neutralize بيقفلوا الإيميلات الخارجة والـ crons (ماعدا الـ autovacuum) والـ webhooks، عشان النسخة متبعتش إيميل لعميل حقيقي.

الـ rehearsal جاب تمنه هنا. أول restore فشل: على Windows ملفات الـ filestore read-only وshutil.rmtree رفضها، بعد ما Odoo كان مسح الـ database خلاص. يعني أمر الرجوع نفسه مسح الـ database وبعدين وقع. ده خاص بـ Windows، بس الدرس عام: الـ rollback اللي عمرك ما شغلته مجرد أمل.

القاعدة اللي بتحكم كل حاجة: الـ rollback نضيف بس لحد أول transaction حقيقية في النظام الجديد. بعدها الـ restore بيمسح فواتير ومدفوعات حقيقية، فالـ rollback بقى قرار data-loss البيزنس هو اللي يتحمله، وغالبًا بيتبدل بإنك تصلّح وإنت ماشي (fix forward).

فين هستخدمه في شغلي؟ أي نقل كبير في production: تغيير payment provider أو نقل database. اكتب الخطة كـ array في الـ repo، شغلها على staging مرتين، وحط الـ reconcile كـ gate. وخد بالك إن "الـ restore اتجرب" معناها إنك شغلته فعلًا وعدّيت الـ rows بعده. الغلطة الشائعة: backup موجود بس محدش جرب يرجعه، وأول مرة بتتجرب بتبقى في نص الأزمة.

Do you roll back?" → No: two days of real invoices and payments are in the new system, and restoring erases them. 3. Catch a wrong due date 🔴 hard The reconciliation misses an invoice with the right customer and amount but the wrong due date. Add a check comparing each invoice's aging bucket, and show it failing for one seeded invoice.
الـ reconciliation مش بيشوف فاتورة عميلها ومبلغها صح وتاريخ استحقاقها غلط. ضيف check بيقارن الـ aging bucket لكل فاتورة، ووريه بيفشل على فاتورة واحدة زرعت فيها الغلطة.
Solution · الحل Compare buckets, not raw dates: a one-day difference inside the same bucket doesn't change any report.

export type OpenItem = { no: string; due: string; residualCents: number };
export function bucket(due: string, asOf: string): string {
  const days = Math.floor((Date.parse(asOf) - Date.parse(due)) / 86_400_000);
  return days <= 0 ? "not due" : days <= 30 ? "1-30" : days <= 60 ? "31-60" : days <= 90 ? "61-90" : "90+";
}
export function agingDiffs(legacy: OpenItem[], odoo: OpenItem[], asOf: string): string[] {
  const target = new Map(odoo.map((i) => [i.no, i]));
  const out: string[] = [];
  for (const l of legacy) {
    const o = target.get(l.no);
    if (!o) out.push(`${l.no}: missing`);
    else if (bucket(l.due, asOf) !== bucket(o.due, asOf)) out.push(`${l.no}: ${bucket(l.due, asOf)} -> ${bucket(o.due, asOf)}`);
  }
  return out;
}

Cheat sheet · الخلاصة

  • Normalize for comparison, store as written; dedupe on a strong key and keep a mergeMap.
  • Every rejected row has a reason; in = out + merged + rejected.
  • External IDs make imports re-runnable; load parents before children.
  • load returns 200 on failure: read ids and messages. A batch is all-or-nothing.
  • Opening entry: one account.move, dated the day before go-live.
  • _update_opening_move auto-balances to 999999: assert it's zero.
  • AR and AP arrive as individual documents against a clearing account that ends at zero.
  • Keep invoice_date and invoice_date_due original; set date to the opening date.
  • Odoo 20 default: an inventory adjustment posts no GL entry. Post stock value exactly once.
  • Reconcile per key and return an exit code; totals hide offsetting errors.
  • The plan is data; rehearse it, including the restore.
  • After the first real transaction, rollback is a data-loss decision.
