Why this matters · ليه ده مهم

English

Sooner or later a product needs to answer "how much do we owe, and to whom?": wallets, marketplace payouts, refunds, subscriptions. Teams usually start with a balance column and discover, during an incident, that nothing explains how the number got there. In lesson 02 you learned the accounting rule. Here you make the database enforce it, so that a bug in any service, script or migration gets refused at COMMIT instead of becoming a wrong number in a report.

This is also README exit-test question 7, "design a ledger that refuses an unbalanced entry at the database level", and the first half of README artifact 1. Building one by hand is the fastest way to understand what Odoo's account.move is really doing.

بالعامية

عاجلًا أو آجلًا الـ product هيحتاج يجاوب على سؤال "إحنا مديونين بكام ولمين؟": wallets، payouts لتجار marketplace، refunds، subscriptions. الفرق عادةً بتبدأ بعمود balance، وبعدين تكتشف وقت incident إن مفيش حاجة بتشرح الرقم ده جه منين. في الدرس 02 اتعلمت القاعدة المحاسبية. هنا هتخلي الـ database نفسها هي اللي تفرضها، فأي bug في أي service أو script أو migration يترفض عند الـ COMMIT بدل ما يبقى رقم غلط في تقرير.

ده كمان سؤال 7 في اختبار الخروج بتاع الـ README: "صمّم ledger بيمنع قيد غير متوازن على مستوى الـ database"، وهو النص الأول من artifact 1. وإنك تبنيه بإيدك هو أسرع طريقة تفهم بيها الـ account.move بتاع Odoo بيعمل إيه فعلًا.

Part 1 — The schema 🟡 Intermediateالجزء 1 — الـ schema

English

Three tables carry the whole idea. accounts is the chart of accounts. journal_entry is the document header: one business fact, one date, one currency. journal_line holds the debit and credit lines. Constraints are taught in section 09, so here is only what's specific to a ledger:

  • numeric(18,2) stores exact decimals; lesson 04 shows what float does to a tax total. Two decimals fit EGP, SAR and AED. A currency with three (KWD) needs a wider scale.
  • CHECK (debit >= 0), CHECK (credit >= 0) and CHECK ((debit = 0) <> (credit = 0)) make every line exactly one-sided. The last one forbids both "both filled" and "both empty".
  • currency sits on the entry, so summing an entry's lines is always meaningful. Multi-currency entries, with a transaction amount beside the company amount, are in lesson 24.
  • tenant_id is part of the foreign keys, not just a column. FOREIGN KEY (tenant_id, account_code) means a line of tenant 1 can't point at an account of tenant 2, even if the application has a bug.
  • entry_date is copied onto the line so the ledger query can be answered from one index. A copy can drift, so the composite foreign key (tenant_id, entry_id, entry_date) makes a mismatch impossible.

-- الشركات: كل tenant ليه base currency بتاعته
CREATE TABLE tenants (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name          text    NOT NULL,
  base_currency char(3) NOT NULL
);

-- دليل الحسابات: الـ code فريد جوه الـ tenant بس، مش على مستوى الـ database كلها
CREATE TABLE accounts (
  tenant_id bigint NOT NULL REFERENCES tenants(id),
  code      text   NOT NULL,
  name      text   NOT NULL,
  type      text   NOT NULL
            CHECK (type IN ('asset','liability','equity','income','expense')),
  PRIMARY KEY (tenant_id, code)
);

-- رأس القيد: مستند واحد متوازن
CREATE TABLE journal_entry (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id       bigint  NOT NULL REFERENCES tenants(id),
  journal         text    NOT NULL,
  entry_date      date    NOT NULL,
  currency        char(3) NOT NULL,
  memo            text    NOT NULL,
  idempotency_key text    NOT NULL,
  payload_hash    text    NOT NULL,
  reversal_of     bigint  REFERENCES journal_entry(id),
  -- رقم العملية عند الـ payment provider، هنقابل بيه في الدرس الجاي
  external_ref    text,
  -- رقم الـ transaction اللي عمل القيد: هنحتاجه في الجزء 5 عشان نقفل القيد بعد الـ commit
  created_xid     xid8    NOT NULL DEFAULT pg_current_xact_id(),
  posted_at       timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, idempotency_key),
  -- هدف الـ composite foreign key اللي تحت
  UNIQUE (tenant_id, id, entry_date)
);

CREATE TABLE journal_line (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id    bigint NOT NULL,
  entry_id     bigint NOT NULL,
  -- نسخة من تاريخ القيد عشان الـ index يغطي الـ ledger query، والـ FK بيمنعها تختلف عن الأصل
  entry_date   date   NOT NULL,
  account_code text   NOT NULL,
  debit        numeric(18,2) NOT NULL DEFAULT 0,
  credit       numeric(18,2) NOT NULL DEFAULT 0,
  FOREIGN KEY (tenant_id, entry_id, entry_date)
    REFERENCES journal_entry (tenant_id, id, entry_date),
  -- الـ FK المركب ده بيمنع سطر tenant 1 يشاور على حساب tenant 2
  FOREIGN KEY (tenant_id, account_code) REFERENCES accounts (tenant_id, code),
  CONSTRAINT debit_not_negative  CHECK (debit  >= 0),
  CONSTRAINT credit_not_negative CHECK (credit >= 0),
  -- بالظبط ناحية واحدة فيها رقم: مش الاتنين ومش ولا واحدة
  CONSTRAINT exactly_one_side    CHECK ((debit = 0) <> (credit = 0))
);
بالعامية

تلات جداول شايلين الفكرة كلها: accounts هو دليل الحسابات، journal_entry هو رأس المستند (حدث واحد، تاريخ واحد، عملة واحدة)، وjournal_line فيه سطور المدين والدائن. الـ constraints متشرحة في section 09، فهنا اللي يخص الـ ledger بس:

  • numeric(18,2) بيخزن decimals بالظبط، والدرس 04 بيوريك الـ float بيعمل إيه في إجمالي الضريبة. رقمين عشريين كفاية للجنيه والريال والدرهم. عملة بتلات أرقام زي الدينار الكويتي محتاجة scale أكبر.
  • CHECK (debit >= 0) وCHECK (credit >= 0) وCHECK ((debit = 0) <> (credit = 0)) بيخلوا كل سطر ناحية واحدة بالظبط. آخر واحد بيمنع "الاتنين مليانين" و"الاتنين فاضيين".
  • currency على القيد نفسه، فجمع سطور القيد دايمًا ليه معنى. القيود متعددة العملات، اللي فيها مبلغ العملية جنب مبلغ الشركة، في الدرس 24.
  • tenant_id جزء من الـ foreign keys، مش مجرد عمود. FOREIGN KEY (tenant_id, account_code) معناه إن سطر بتاع tenant 1 مش ممكن يشاور على حساب tenant 2، حتى لو الـ application فيها bug.
  • entry_date متنسخ على السطر عشان الـ ledger query تتجاوب من index واحد. والنسخة ممكن تختلف عن الأصل، فالـ composite foreign key (tenant_id, entry_id, entry_date) بيخلي الاختلاف مستحيل.

الأول Postgres خاص بيك. ابعت الـ port صريح دايمًا: port فاضي معناه الـ default، والـ default هو الـ database الحقيقية اللي على جهازك.

فين هستخدمه في شغلي؟ عندك SaaS فيه wallets لكل tenant، وحصل bug في background job كتب سطر بـ tenant_id غلط. لو الـ FK على account_code لوحده، السطر هيتكتب والفلوس هتبان عند عميل تاني. بالـ composite FK الـ INSERT بيقع فورًا والـ job بيفشل بصوت عالي، وده أرخص بكتير من تحقيق بعد شهر.

Part 2 — The balanced invariant in the database 🟡 Intermediateالجزء 2 — قاعدة التوازن جوه الـ database

English

"Debits equal credits" is a rule across several rows, and that's where the normal tools stop. A CHECK sees one row only, and Postgres refuses a subquery in it outright:

-- محاولة ساذجة: CHECK بيبص على سطور تانية
ALTER TABLE journal_line ADD CONSTRAINT entry_balanced_try CHECK (
  (SELECT sum(debit) - sum(credit) FROM journal_line l WHERE l.entry_id = entry_id) = 0
);
psql:sql/02-check-cannot-span.sql:4: ERROR:  cannot use subquery in check constraint
الـ CHECK بيشوف سطر واحد بس، و Postgres بيرفض أي subquery جواه من الأساس. فمفيش طريقة نعبّر بيه عن قاعدة بين أكتر من سطر.
English

A normal AFTER INSERT trigger can run a query, but it fires after each statement's row, while the entry is still half-written. A perfectly good entry fails on its first line:

-- غلط مقصود: trigger عادي بيشتغل بعد كل سطر، مش عند الـ COMMIT
CREATE FUNCTION check_now() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE d numeric; c numeric;
BEGIN
  SELECT sum(debit), sum(credit) INTO d, c FROM journal_line WHERE entry_id = NEW.entry_id;
  IF d <> c THEN RAISE EXCEPTION 'entry % unbalanced: % <> %', NEW.entry_id, d, c; END IF;
  RETURN NULL;
END $$;
CREATE TRIGGER balanced_now AFTER INSERT ON journal_line
  FOR EACH ROW EXECUTE FUNCTION check_now();

القيد ده سليم، بس الـ trigger العادي اشتغل بعد أول سطر، ووقتها كان فيه مدين 100 ودائن ولا حاجة، فرفضه. يعني الـ trigger العادي بيرفض كل القيود، السليمة قبل الغلط.
English

What we need is a check that waits until the transaction is finished. That's a CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED: it's queued per row and executed at COMMIT, when every line is in place. If it raises, the whole transaction rolls back. Postgres only allows constraint triggers as AFTER ... FOR EACH ROW, which is why there's no way to fire it once per statement.

 BEGIN
   INSERT journal_entry          immediate trigger | deferred trigger
   INSERT line  debit  100  ---> runs: 100 <> 0    | queued
                                 FAILS             |
   INSERT line  credit 100                         | queued
 COMMIT  --------------------------------------->  | runs: 100 = 100, OK
الـ trigger العادي (الشمال) بيشتغل مع أول سطر ويلاقي 100 قصاد صفر فيرفض. الـ deferred (اليمين) بيتحط في طابور مع كل سطر، ومبيشتغلش غير عند الـ COMMIT، ساعتها السطرين موجودين والمجموع 100 = 100.
CREATE FUNCTION assert_entry_balanced(p_entry bigint) RETURNS void
LANGUAGE plpgsql AS $$
DECLARE d numeric; c numeric;
BEGIN
  SELECT coalesce(sum(debit), 0), coalesce(sum(credit), 0) INTO d, c
  FROM journal_line WHERE entry_id = p_entry;
  IF d <> c THEN
    -- الكود 23514 هو check_violation، فالـ Node يقدر يفرّق الغلطة دي عن غيرها
    RAISE EXCEPTION 'entry % unbalanced: % <> %', p_entry, d, c USING ERRCODE = '23514';
  END IF;
END $$;

CREATE FUNCTION line_trigger_balanced() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  PERFORM assert_entry_balanced(NEW.entry_id);
  RETURN NULL;
END $$;

-- التأجيل هو كل الحكاية: الفحص بيشتغل عند الـ COMMIT بعد ما كل السطور تدخل
CREATE CONSTRAINT TRIGGER line_keeps_entry_balanced
  AFTER INSERT OR UPDATE ON journal_line
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION line_trigger_balanced();

  IF NOT EXISTS (SELECT 1 FROM journal_line WHERE entry_id = NEW.id) THEN

The refactor is functional core, imperative shell. The core has one pure function per event: postOrderShipped, postInvoice, postPayment. Each takes the event and a list of posting rules and returns a draft entry, with no database and no clock. The shell loads the rules, calls the core, and writes the result in one transaction.

Which account a component goes to is data, in a posting_rule table: when finance moves fees to a new account, nobody deploys. Money in the core is bigint piastres, so no float can enter. The three events make up order-to-cash: shipping moves cost from inventory to cost of goods sold; the invoice creates the receivable, revenue and VAT; the payment clears the receivable into a provider clearing account, net of the fee. Clearing means "the provider owes us this until it settles", which is exactly what lesson 06 reconciles.

export function canonicalEvent(event: DomainEvent): string {
  const entries = Object.entries(event)
    .map(([k, v]) => [k, typeof v === "bigint" ? v.toString() : v] as const)
    .sort(([a], [b]) => (a < b ? -1 : 1));
  return JSON.stringify(Object.fromEntries(entries));
}

export const hashEvent = (event: DomainEvent): string =>
  createHash("sha256").update(canonicalEvent(event)).digest("hex");

function linesFrom(
  rules: readonly PostingRule[],
  eventType: DomainEvent["type"],
  components: Record<string, Minor>,
): LineDraft[] {
  return Object.entries(components)
    // السطر الصفر ممنوع بالـ CHECK، فالـ component اللي قيمته صفر مبيطلعش سطر
    .filter(([, amount]) => amount !== 0n)
    .map(([component, amount]) => {
      const rule = rules.find((r) => r.eventType === eventType && r.component === component);
      if (!rule) throw new Error(`no posting rule for ${eventType}/${component}`);
      return rule.side === "debit"
        ? { accountCode: rule.accountCode, debit: amount, credit: 0n }
        : { accountCode: rule.accountCode, debit: 0n, credit: amount };
    });
}

export const toNumeric = (m: Minor): string => {
  const sign = m < 0n ? "-" : "";
  const abs = m < 0n ? -m : m;
  return `${sign}${abs / 100n}.${String(abs % 100n).padStart(2, "0")}`;
};

export const toMinor = (s: string): Minor => {
  const [whole, frac = ""] = s.replace("-", "").split(".");
  const v = BigInt(whole) * 100n + BigInt(frac.padEnd(2, "0").slice(0, 2));
  return s.startsWith("-") ? -v : v;

export interface PostResult { entryId: string; created: boolean }

export async function post(pool: pg.Pool, tenantId: string, d: EntryDraft): Promise<PostResult> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const inserted = await client.query<{ id: string }>(
      `INSERT INTO journal_entry
         (tenant_id, journal, entry_date, currency, memo, idempotency_key, payload_hash, reversal_of, external_ref)
       VALUES ($1,$2,$3,$4,$5,$6,$7,$8,$9)
       ON CONFLICT (tenant_id, idempotency_key) DO NOTHING
       RETURNING id`,
      [tenantId, d.journal, d.date, d.currency, d.memo, d.idempotencyKey, d.payloadHash, d.reversalOf ?? null, d.externalRef ?? null],
    );
    if (inserted.rowCount === 0) {
      // الحدث جه قبل كده: مفيش كتابة، نرجّع القيد الأصلي
      await client.query("ROLLBACK");
      const { rows } = await client.query<{ id: string; payload_hash: string }>(
        "SELECT id, payload_hash FROM journal_entry WHERE tenant_id = $1 AND idempotency_key = $2",
        [tenantId, d.idempotencyKey],
      );
      // نفس الـ key بمحتوى مختلف ده bug عند اللي بعت، مش duplicate عادي
      if (rows[0].payload_hash !== d.payloadHash) {
        throw new IdempotencyConflict(`key ${d.idempotencyKey} reused with a different payload`);
      }
      return { entryId: rows[0].id, created: false };
    }
    const entryId = inserted.rows[0].id;
    await client.query(
      `INSERT INTO journal_line (tenant_id, entry_id, entry_date, account_code, debit, credit)
       SELECT $1, $2, $3, a, d, c
       FROM unnest($4::text[], $5::numeric[], $6::numeric[]) AS t(a, d, c)`,
      [tenantId, entryId, d.date,
       d.lines.map((l) => l.accountCode), d.lines.map((l) => toNumeric(l.debit)), d.lines.map((l) => toNumeric(l.credit))],
    );
    // الترتيب بالـ account code بيمنع الـ deadlock بين قيدين بيلمسوا نفس الحسابات
    const sorted = [...d.lines].sort((a, b) => (a.accountCode < b.accountCode ? -1 : 1));
    for (const l of sorted) {
      await client.query(
        `INSERT INTO account_balance (tenant_id, account_code, debit, credit)
         VALUES ($1,$2,$3,$4)
         ON CONFLICT (tenant_id, account_code) DO UPDATE
           SET debit = account_balance.debit + EXCLUDED.debit,
               credit = account_balance.credit + EXCLUDED.credit`,
        [tenantId, l.accountCode, toNumeric(l.debit), toNumeric(l.credit)],
      );
    }
    await client.query("COMMIT");
    return { entryId, created: true };
  } catch (err) {
    await client.query("ROLLBACK").catch(() => {});
    // الـ partial unique index هو اللي بيقول إن القيد اتعكس قبل كده
    if ((err as { constraint?: string }).constraint === "one_reversal_per_entry") {
      throw new AlreadyReversed(`entry ${d.reversalOf} is already reversed`);
    }
    throw err;
  } finally {
    client.release();
  }
}

Part 4 — Idempotent posting 🟡 Intermediateالجزء 4 — الـ idempotent posting

English

Queues and webhooks deliver at least once, so the same event will arrive twice. Section 12 covers idempotency keys in general. The ledger-specific rule: the key is derived from the business event (order:123:shipped), never from the delivery. Anything that varies per attempt, such as a timestamp, a queue message ID or a random UUID made by the consumer, defeats it.

The mechanism is UNIQUE (tenant_id, idempotency_key) plus INSERT ... ON CONFLICT DO NOTHING, already in post(). Concurrency is handled by Postgres: if two transactions insert the same key, the second waits for the first. If the first commits, the second does nothing and returns zero rows. If the first rolls back, the second inserts. No SELECT first, so no window.

Also store a hash of the event. The same key with a different amount isn't a duplicate: it's a bug in the sender, and swallowing it hides that the two systems disagree. Hash the event and not the draft, so a rule change doesn't make an honest replay look like a conflict.

Part 5 — Reversal instead of update 🟡 Intermediateالجزء 5 — القيد العكسي بدل الـ update

English

A posted entry is a historical fact: a tax return or an audit may already rely on it. A correction is therefore a new entry that mirrors the old one, with reversal_of pointing back, dated in the current open period. Afterwards the old entry, its reversal and the reason are all visible, and the net effect is zero.

Three things have to be enforced. Row triggers refuse UPDATE and DELETE on both tables. A partial unique index allows only one reversal per entry. And a less obvious one: an append-only rule that only stops UPDATE still lets someone INSERT a balanced pair of new lines into an entry posted last year. So created_xid records which transaction created the entry, and a trigger refuses lines from any other. pg_current_xact_id() returns the top-level transaction ID, so savepoints don't break it (tested).

CREATE FUNCTION refuse_change() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'ledger is append-only' USING ERRCODE = '23001';
END $$;

-- الـ row trigger بيوقف UPDATE و DELETE، على الرأس والسطور
CREATE TRIGGER journal_line_immutable BEFORE UPDATE OR DELETE ON journal_line
  FOR EACH ROW EXECUTE FUNCTION refuse_change();
CREATE TRIGGER journal_entry_immutable BEFORE UPDATE OR DELETE ON journal_entry
  FOR EACH ROW EXECUTE FUNCTION refuse_change();

-- القيد يتعكس مرة واحدة بس، والـ index ده بيحكم حتى لو جالك طلبين مع بعض
CREATE UNIQUE INDEX one_reversal_per_entry
  ON journal_entry (reversal_of) WHERE reversal_of IS NOT NULL;

-- السطور تدخل بس في نفس الـ transaction اللي عمل القيد
CREATE FUNCTION refuse_late_line() RETURNS trigger
LANGUAGE plpgsql AS $$
DECLARE creator xid8;
BEGIN
  SELECT created_xid INTO creator FROM journal_entry WHERE id = NEW.entry_id;
  IF creator IS DISTINCT FROM pg_current_xact_id() THEN
    RAISE EXCEPTION 'entry % is already posted', NEW.entry_id USING ERRCODE = '23001';
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER journal_line_only_at_creation BEFORE INSERT ON journal_line
  FOR EACH ROW EXECUTE FUNCTION refuse_late_line();

القيد اللي اترحّل حقيقة تاريخية: ممكن إقرار ضريبي أو audit يكون معتمد عليه. فالتصحيح قيد جديد مراية للقديم، وreversal_of بيشاور عليه، وتاريخه في الفترة المفتوحة دلوقتي. بعدها القيد القديم والعكسي والسبب كلهم ظاهرين، والتأثير الصافي صفر.

لازم نفرض تلات حاجات. الـ row triggers بترفض UPDATE وDELETE على الجدولين. والـ partial unique index بيسمح بقيد عكسي واحد لكل قيد. والتالتة مش واضحة: قاعدة append-only بتمنع UPDATE بس لسه بتسمح لحد يعمل INSERT لسطرين متوازنين جوه قيد اترحّل السنة اللي فاتت. فـ created_xid بيسجل الـ transaction اللي عمل القيد، وفيه trigger بيرفض السطور من أي transaction تاني. وpg_current_xact_id() بترجّع رقم الـ transaction الأساسي، فالـ savepoints مش بتبوّظها (جرّبناها).

وفي السباق: عشرين موظف داسوا "Reverse" مع بعض، كل واحد بـ request key مختلف، فالـ idempotency مش هتنقذنا، والـ partial unique index لوحده هو اللي منع القيد العكسي التاني.

وثغرة أخيرة: الـ row trigger مبيشتغلش مع TRUNCATE. الحل على مستويين: statement-level trigger بـ BEFORE TRUNCATE بيوقف حتى الـ owner، و role للـ app مش owner ومعندوش غير SELECT وINSERT. النتيجة فوق: الـ owner اترفض بالـ trigger؛ والـ ledger_app اترفض بـ permission denied في TRUNCATE وUPDATE، وmust be owner لما حاول يقفل الـ trigger، وpermission denied لما حاول يزوّر created_xid، لأن الـ GRANT INSERT على أعمدة محددة مش شاملاه. وجربنا post() كامل بالـ role ده وشغال.

فين هستخدمه في شغلي؟ عميل طلب refund لفاتورة اتقفل شهرها. الغلط: UPDATE invoices SET total = 0، فالأرقام اللي اتبعتت للضرايب ماعدتش تطابق الـ database. الصح: POST /entries/:id/reverse بيعمل قيد عكسي بتاريخ النهارده. وفي الـ deploy بتاعك: الـ DATABASE_URL بتاع الـ API يبقى role محدود، والـ migrations بس تستخدم الـ owner. الغلطة الشائعة: الـ app والـ migrations بنفس الـ user، فأي SQL injection أو script غلط يقدر يقفل الـ triggers.
What these controls don't stop A superuser, or the table owner, can still disable triggers or edit rows. The triggers stop mistakes and limit the application; they aren't proof against someone with full database access. Lesson 06 adds a hash chain that makes such an edit detectable.

Part 6 — Tests on the invariants 🟡 Intermediateالجزء 6 — tests على الـ invariants

English

Example-based tests check the cases you thought of. A ledger is better tested by stating what must always be true and letting a generator look for counterexamples (property tests), against a real Postgres (integration tests), because the triggers and the unique index are part of what's under test.

Each of 500 seeded sequences mixes shipments, invoices, payments, duplicate deliveries and reversals in a fresh tenant, then asserts four properties:

  1. Every entry balances, and total debits equal total credits.
  2. Each account's stored balance equals the sum of its lines.
  3. Each account's balance equals what an independent oracle computes from the events.
  4. Replaying every event changes nothing.

Property 3 is the one that matters most, and the oracle must not read the posting rules. If it did, a wrong rule would agree with itself. A failure prints the seed, so the exact sequence can be replayed. This is README artifact 1.

import { afterAll, describe, expect, it } from "vitest";

// بنزرع bug في القواعد بالـ environment عشان نثبت إن الـ test بيمسكه
function rulesUnderTest(): readonly PostingRule[] {
  const patch = (match: (r: PostingRule) => boolean, change: Partial<PostingRule>) =>
    RULES.map((r) => (match(r) ? { ...r, ...change } : r));
  switch (process.env.SEED_BUG) {
    case "wrong-account":
      return patch((r) => r.eventType === "payment.received" && r.component === "receivable", { accountCode: "4000" });
    case "wrong-side":
      return patch((r) => r.eventType === "payment.received" && r.component === "fee", { side: "credit" });
    default:
      return RULES;
  }
}

// مولد عشوائي بـ seed: أي فشل يتعاد بالظبط بنفس الرقم
function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

type Step = { kind: "event"; event: DomainEvent } | { kind: "reverse"; target: number };
type Invoice = Extract<DomainEvent, { type: "invoice.issued" }>;

function randomSteps(seed: number): Step[] {
  const rand = mulberry32(seed);
  const int = (lo: number, hi: number) => lo + Math.floor(rand() * (hi - lo + 1));
  const date = "2026-11-02", currency = "EGP";
  const steps: Step[] = [];
  const events: DomainEvent[] = [];
  const invoices: Invoice[] = [];
  const count = int(3, 15);
  for (let n = 0; n < count; n++) {
    const dice = rand();
    let event: DomainEvent | undefined;
    if (dice < 0.3) {
      event = { type: "order.shipped", orderId: `O${n}`, date, currency, costMinor: BigInt(int(100, 900_000)) };
    } else if (dice < 0.6 || invoices.length === 0) {
      const net = int(100, 900_000);
      const invoice: Invoice = { type: "invoice.issued", invoiceId: `I${n}`, date, currency, netMinor: BigInt(net), vatMinor: BigInt(Math.round(net * 0.14)) };
      invoices.push(invoice);
      event = invoice;
    } else if (dice < 0.85) {
      const inv = invoices[int(0, invoices.length - 1)];
      const amountMinor = inv.netMinor + inv.vatMinor;
      event = { type: "payment.received", paymentId: `P${n}`, invoiceId: inv.invoiceId, date, currency, amountMinor, feeMinor: BigInt(int(0, Number(amountMinor) / 30)) };
    } else if (dice < 0.95 && events.length > 0) {
      // توصيلة مكررة (duplicate delivery) لحدث قديم
      steps.push({ kind: "event", event: events[int(0, events.length - 1)] });
      continue;
    } else if (events.length > 0) {
      steps.push({ kind: "reverse", target: int(0, events.length - 1) });
      continue;
    }
    if (event) { events.push(event); steps.push({ kind: "event", event }); }
  }
  return steps;
}

// الـ oracle مكتوب من غير ما يبص على جدول القواعد، وده اللي بيخليه يمسك bug فيه
function applyToOracle(book: Map<string, Minor>, e: DomainEvent, sign: Minor) {
  const add = (code: string, debitMinusCredit: Minor) =>
    book.set(code, (book.get(code) ?? 0n) + sign * debitMinusCredit);
  if (e.type === "order.shipped") { add("5000", e.costMinor); add("1200", -e.costMinor); }
  if (e.type === "invoice.issued") { add("1100", e.netMinor + e.vatMinor); add("4000", -e.netMinor); add("2100", -e.vatMinor); }
  if (e.type === "payment.received") { add("1010", e.amountMinor - e.feeMinor); add("6100", e.feeMinor); add("1100", -e.amountMinor); }
}

const keyOf = (e: DomainEvent) =>
  e.type === "order.shipped" ? `o:${e.orderId}` : e.type === "invoice.issued" ? `i:${e.invoiceId}` : `p:${e.paymentId}`;

async function runSequence(seed: number): Promise<void> {
  const rules = rulesUnderTest();
  const tenant = await createTenant(pool, `prop-${process.pid}-${seed}`, rules);
  const oracle = new Map<string, Minor>();
  const posted = new Map<string, { event: DomainEvent; entryId: string; reversed: boolean }>();
  const order: string[] = [];

  for (const step of randomSteps(seed)) {
    if (step.kind === "event") {
      const key = keyOf(step.event);
      const r = await post(pool, tenant, draftFor(step.event, rules));
      if (r.created) {
        applyToOracle(oracle, step.event, 1n);
        posted.set(key, { event: step.event, entryId: r.entryId, reversed: false });
        order.push(key);
      }
    } else {
      const item = posted.get(order[Math.min(step.target, order.length - 1)]);
      if (!item || item.reversed) continue;
      const original = await loadEntry(pool, tenant, item.entryId);
      await post(pool, tenant, buildReversal(original, "2026-11-20", `reversal:${item.entryId}`));
      item.reversed = true;
      applyToOracle(oracle, item.event, -1n);
    }
  }

  // (1) كل قيد متوازن، والمجموع الكلي مدين = دائن
  const broken = await pool.query(
    "SELECT entry_id FROM journal_line WHERE tenant_id = $1 GROUP BY entry_id HAVING sum(debit) <> sum(credit)", [tenant],
  );
  expect(broken.rows, `seed ${seed}: unbalanced entries`).toEqual([]);
  const totals = await pool.query(
    "SELECT coalesce(sum(debit),0) AS d, coalesce(sum(credit),0) AS c FROM journal_line WHERE tenant_id = $1", [tenant],
  );
  expect(totals.rows[0].d, `seed ${seed}: total debit vs credit`).toBe(totals.rows[0].c);

  // (2) الرصيد المتخزن لكل حساب = مجموع سطوره
  const fromLines = await pool.query(
    "SELECT account_code, sum(debit) - sum(credit) AS balance FROM journal_line WHERE tenant_id = $1 GROUP BY 1 ORDER BY 1", [tenant],
  );
  const stored = await pool.query(
    "SELECT account_code, debit - credit AS balance FROM account_balance WHERE tenant_id = $1 ORDER BY 1", [tenant],
  );
  expect(stored.rows, `seed ${seed}: stored balance vs lines`).toEqual(fromLines.rows);

  // (3) الأرصدة = اللي الـ oracle حسبه من الأحداث
  const actual = Object.fromEntries(fromLines.rows.filter((r) => Number(r.balance) !== 0).map((r) => [r.account_code, r.balance]));
  const expected = Object.fromEntries([...oracle].filter(([, v]) => v !== 0n).sort(([a], [b]) => (a < b ? -1 : 1)).map(([k, v]) => [k, toNumeric(v)]));
  expect(actual, `seed ${seed}: balances vs oracle`).toEqual(expected);

  const before = await pool.query("SELECT count(*) AS n FROM journal_entry WHERE tenant_id = $1", [tenant]);
  // (4) إعادة كل الأحداث مبتغيرش حاجة
  for (const { event } of posted.values()) {
    const r = await post(pool, tenant, draftFor(event, rules));
    expect(r.created, `seed ${seed}: replay created an entry`).toBe(false);
  }
  const after = await pool.query("SELECT count(*) AS n FROM journal_entry WHERE tenant_id = $1", [tenant]);
  expect(after.rows[0].n, `seed ${seed}: entry count after replay`).toBe(before.rows[0].n);
  const storedAfter = await pool.query(
    "SELECT account_code, debit - credit AS balance FROM account_balance WHERE tenant_id = $1 ORDER BY 1", [tenant],
  );
  expect(storedAfter.rows, `seed ${seed}: balances after replay`).toEqual(stored.rows);
}

describe("ledger invariants", () => {
  it("holds for 500 random event sequences", async () => {
    let next = 1;
    const worker = async () => { while (next <= 500) await runSequence(next++); };
    await Promise.all(Array.from({ length: 8 }, worker));
  }, 280_000);
});

الـ tests اللي بالأمثلة بتفحص الحالات اللي خطرت على بالك. الـ ledger الأحسن تختبره إنك تقول إيه اللي لازم يبقى صح دايمًا وتسيب generator يدور على مثال يكسره (property tests)، وعلى Postgres حقيقية (integration tests)، لأن الـ triggers والـ unique index جزء من اللي بنختبره.

كل sequence من الـ 500، وكل واحدة ليها seed، بتخلط شحنات وفواتير ومدفوعات وتوصيلات مكررة وقيود عكسية في tenant جديد، وبعدين بتتأكد من 4 حاجات:

  1. كل قيد متوازن، وإجمالي المدين = إجمالي الدائن.
  2. الرصيد المتخزن لكل حساب = مجموع سطوره.
  3. رصيد كل حساب = اللي oracle مستقل بيحسبه من الأحداث.
  4. إعادة كل الأحداث مبتغيرش حاجة.

رقم 3 هو الأهم، والـ oracle ممنوع يقرا الـ posting rules؛ لو قراها، القاعدة الغلط هتوافق نفسها. والفشل بيطبع الـ seed فتقدر تعيد نفس الـ sequence بالظبط. ده artifact 1 في الـ README.

Cheat sheet · الخلاصة

  • Header + lines. numeric(18,2), non-negative, exactly one side per line, tenant inside the composite foreign keys.
  • A CHECK can't span rows; an immediate trigger fires on a half-written entry; a deferred constraint trigger runs at COMMIT.
  • Line-level triggers miss zero-line entries: add one on the header.
  • A foreign key creates no index. Add (tenant_id, account_code, entry_date, id) INCLUDE (debit, credit) for the ledger query.
  • Pure core + thin shell. Which account a component goes to is data, in posting_rule.
  • The idempotency key comes from the business event, never the delivery. ON CONFLICT DO NOTHING, never check-then-insert.
  • Same key with a different payload is a bug: store a hash of the event and raise.
  • Correct by a mirror entry with reversal_of; a partial unique index allows one reversal.
  • Block UPDATE, DELETE, TRUNCATE and late lines. Run the app under a role that isn't the owner.
  • Test with a seeded generator and an independent oracle: a wrong account still balances.
بالعامية
  • رأس وسطور. numeric(18,2)، مفيش سالب، ناحية واحدة بالظبط لكل سطر، والـ tenant جوه الـ composite foreign keys.
  • الـ CHECK ميشوفش أكتر من سطر؛ الـ trigger العادي بيشتغل والقيد نص مكتوب؛ الـ deferred constraint trigger بيشتغل عند الـ COMMIT.
  • الـ triggers اللي على السطور مبتشوفش القيد اللي من غير سطور: ضيف واحد على الرأس.
  • الـ foreign key مبيعملش index. ضيف (tenant_id, account_code, entry_date, id) INCLUDE (debit, credit) للـ ledger query.
  • Core pure وshell رفيع. الحساب اللي كل component بيروحله data في posting_rule.
  • الـ idempotency key طالع من الحدث التجاري، مش مرة التوصيل. ON CONFLICT DO NOTHING، ومفيش check وبعدين insert.
  • نفس الـ key بمحتوى مختلف يبقى bug: خزّن hash للحدث وارمي error.
  • التصحيح بقيد مراية بـ reversal_of؛ والـ partial unique index بيسمح بقيد عكسي واحد.
  • امنع UPDATE وDELETE وTRUNCATE والسطور المتأخرة. وشغّل الـ app بـ role مش owner.
  • اختبر بـ generator ليه seed وoracle مستقل: الحساب الغلط لسه بيتوازن.
