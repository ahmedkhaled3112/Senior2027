Why this matters · ليه ده مهم

English

Lesson 28 made one sync reliable. This one is about the system those syncs add up to: a shop, a payment provider and an ERP that must agree about money while each can be down, slow or wrong. The senior questions are who owns each field, how a change travels, how to keep one vendor's data shape from spreading through your code, when to buy instead of build, and how you find out they disagree. Everything that could run here ran against real Odoo, real Postgres and real Redis.

بالعامية

درس 28 خلّى sync واحد يعتمد عليه. الدرس ده عن النظام اللي الـ syncs دي بتكوّنه: متجر و payment provider و ERP لازم يتفقوا على الفلوس، وكل واحد فيهم ممكن يقع أو يبطأ أو يغلط. أسئلة السنيور هنا: مين بيملك كل field، التغيير بيتنقل إزاي، إزاي تمنع شكل data بتاع vendor واحد إنه ينتشر في كودك، إمتى تشتري بدل ما تبني، وهتعرف إزاي إنهم مختلفين. كل اللي ينفع يشتغل هنا اشتغل على Odoo و Postgres و Redis حقيقيين.

Part 1 — System of record 🔴 Advancedالجزء 1 — الـ system of record

English

"The ERP is the system of record" is too coarse to implement. Ownership is decided per entity and per field. For a customer, the legal name, tax ID and credit limit belong to the ERP, because they appear on legal documents. Email and marketing preferences belong to the product, because that is where the user changes them and where consent is recorded. An invoice number comes only from the ERP, since numbering is a legal sequence. A contract price belongs to the ERP; a promotional price can belong to the shop.

Write the matrix as data and enforce it in the sync path. A source can write only the fields it owns; a field nobody listed is refused, because an unlisted field means nobody has decided. Each field also has a conflict rule: owner-wins drops the other side's value and, for a value that must never diverge silently, manual-review sends it to a person.

This removes the worst integration bug: two systems both writing a field and overwriting each other forever. Record the decision in a design doc, using project/design-docs/0000-template.md: that is README artifact 9.

// مصفوفة الملكية كـ data: كل field ليه مالك واحد، وأي write من غير المالك بيترفض
export type System = "erp" | "shop" | "crm";
export type Entity = "customer" | "invoice" | "price";

type Rule = { owner: System; onConflict: "owner-wins" | "manual-review" };

export const OWNERSHIP: Record<Entity, Record<string, Rule>> = {
  customer: {
    legalName: { owner: "erp", onConflict: "owner-wins" },
    taxId: { owner: "erp", onConflict: "manual-review" },
    creditLimit: { owner: "erp", onConflict: "owner-wins" },
    email: { owner: "shop", onConflict: "owner-wins" },
    marketingOptIn: { owner: "shop", onConflict: "owner-wins" },
    salesStage: { owner: "crm", onConflict: "owner-wins" },
  },
  invoice: {
    number: { owner: "erp", onConflict: "manual-review" },
    total: { owner: "erp", onConflict: "manual-review" },
    paymentState: { owner: "erp", onConflict: "owner-wins" },
    shopOrderRef: { owner: "shop", onConflict: "owner-wins" },
  },
  price: {
    contractPrice: { owner: "erp", onConflict: "owner-wins" },
    promoPrice: { owner: "shop", onConflict: "owner-wins" },
  },
};

export type Decision = {
  accepted: Record<string, unknown>;
  refused: { field: string; owner: System | "unknown"; onConflict: Rule["onConflict"] | "reject-unknown" }[];
};

// الـ default هو الرفض: field مش في المصفوفة معناه إن محدش قرر مين صاحبه
export function filterWrite(entity: Entity, source: System, patch: Record<string, unknown>): Decision {
  const accepted: Record<string, unknown> = {};
  const refused: Decision["refused"] = [];
  for (const [field, value] of Object.entries(patch)) {
    const rule = OWNERSHIP[entity][field];
    if (!rule) refused.push({ field, owner: "unknown", onConflict: "reject-unknown" });
    else if (rule.owner !== source) refused.push({ field, owner: rule.owner, onConflict: rule.onConflict });
    else accepted[field] = value;
  }
  return { accepted, refused };
}
test("shop cannot rename the legal customer", () => {
  const d = filterWrite("customer", "shop", { legalName: "Typo Trading", email: "buyer@example.test" });
  assert.deepEqual(d.accepted, { email: "buyer@example.test" });
  assert.deepEqual(d.refused, [{ field: "legalName", owner: "erp", onConflict: "owner-wins" }]);
});

test("erp cannot flip a marketing preference", () => {
  const d = filterWrite("customer", "erp", { marketingOptIn: true });
  assert.deepEqual(d.accepted, {});
  assert.equal(d.refused[0]?.owner, "shop");

  const d = filterWrite("customer", "erp", { x_studio_field: 1 });
  assert.deepEqual(d.refused, [{ field: "x_studio_field", owner: "unknown", onConflict: "reject-unknown" }]);

بالعامية

جملة "الـ ERP هو الـ system of record" عامة أوي ومتتنفذش. الملكية بتتقرر لكل entity ولكل field. في العميل: الاسم القانوني والرقم الضريبي وحد الائتمان ملك الـ ERP لأنهم بيظهروا في مستندات قانونية. الإيميل وتفضيلات التسويق ملك المنتج، لأن المستخدم بيغيرهم هناك والموافقة بتتسجل هناك. رقم الفاتورة من الـ ERP بس، لأن الترقيم تسلسل قانوني. سعر التعاقد ملك الـ ERP، وسعر العرض ممكن يبقى ملك المتجر.

اكتب المصفوفة كـ data وطبّقها في مسار الـ sync. المصدر يكتب الـ fields اللي يملكها بس، والـ field اللي محدش كتبه بيترفض، لأن عدم وجوده معناه إن محدش قرر. وكل field ليه قاعدة تعارض: owner-wins بتشيل قيمة الطرف التاني، وmanual-review بتبعتها لبني آدم لو القيمة ممنوع تختلف في السر.

ده بيشيل أسوأ bug في الـ integration: نظامين بيكتبوا نفس الـ field وكل واحد بيمسح التاني للأبد. سجل القرار في design doc باستخدام project/design-docs/0000-template.md: ده artifact 9 في الـ README.

فين هستخدمه في شغلي؟ المتجر بتاعك بيعمل sync للعملاء مع Odoo، وموظف صلّح اسم الشركة في Odoo، وبعدها بساعة المستخدم حدّث البروفايل والـ sync رجّع الاسم الغلط. بالمصفوفة، الـ patch اللي جاي من المتجر بيعدي فيه الإيميل بس والاسم بيترفض. الغلطة الشائعة: "last write wins" على كل الـ fields، وده معناه إن آخر حد ضغط save هو اللي بيقرر الـ data القانونية.

Part 2 — Outbox and CDC around an ERP 🔴 Advancedالجزء 2 — الـ outbox والـ CDC حوالين الـ ERP

English

The mechanics are in section 09 · Outbox, CDC & Idempotent Consumers. The ERP angle is an asymmetry. Inside your Node service you own the schema, so an outbox row committed with the business row is the right tool: the event is a contract you designed. Around Odoo you do not own the schema, so reading its tables through CDC couples you to an internal that changes between versions.

The run below uses logical decoding with test_decoding on a throwaway Postgres with wal_level=logical. It shows why CDC is attractive: a rolled-back transaction never appears, and changes arrive in commit order, so the transaction that started first and committed last comes last. That is exactly what defeated the write_date cursor in lesson 28.

It also shows the two costs. A column rename, the sort of thing a major version does, makes the parser return null with no error. And a slot nobody reads holds WAL on the primary: retained bytes grew by about 23 MB per batch here and would continue until the disk fills, which on an ERP database means the whole company stops. Debezium and Kafka are the production form of this; they are not run here.

بالعامية

التفاصيل نفسها في قسم 09 · Outbox و CDC. زاوية الـ ERP هي عدم التماثل. جوه الـ Node service بتاعك إنت مالك الـ schema، فصف outbox بيتعمله commit مع صف البيزنس هو الأداة الصح: الـ event عقد إنت اللي صممته. حوالين Odoo إنت مش مالك الـ schema، فقراية جداوله بالـ CDC بتربطك بتفاصيل داخلية بتتغير بين النسخ.

التجربة فوق بتستخدم logical decoding بـ test_decoding على Postgres مؤقتة بـ wal_level=logical. بتوري ليه الـ CDC جذاب: الـ transaction اللي اتعمل لها rollback مبتظهرش، والتغييرات بتيجي بترتيب الـ commit، فالـ transaction اللي بدأت الأول وعملت commit في الآخر بتيجي في الآخر. وده بالظبط اللي كسر الـ write_date cursor في درس 28.

وبتوري التكلفتين كمان. rename لعمود، زي اللي بيحصل في major version، بيخلي الـ parser يرجع null من غير أي error. والـ slot اللي محدش بيقراه بيمسك WAL على الـ primary: الحجم زاد حوالي 23 MB كل batch هنا، وهيفضل يزيد لحد ما الديسك يتملي، وده على database الـ ERP معناه إن الشركة كلها تقف. Debezium و Kafka هما الشكل الـ production للكلام ده، ومتشغلوش هنا (not run here).

فين هستخدمه في شغلي؟ المتجر بتاعك (Node و Postgres): outbox. لما order يتأكد، صف الـ order وصف الـ outbox في transaction واحدة، و worker ينقله لـ BullMQ. ناحية Odoo: webhook للسرعة و polling بـ overlap كشبكة أمان، ومتعملش CDC على جداوله غير لو إنت اللي ماسك الـ upgrades ومعاك monitoring على الـ slot. الغلطة الشائعة: slot اتعمل في تجربة واتنسى، وبعد أسبوعين الديسك يتملي.
Interview question "Would you use Debezium on the customer's Odoo database?" → Usually not. It reads a private schema, needs replication access, and an abandoned slot can fill the disk of a system the whole company depends on. I'd use the public API with webhooks plus an overlapping write_date poll. I would reconsider if we run the database ourselves, own the upgrades, and the volume makes polling impractical.
"هتستخدم Debezium على database الـ Odoo بتاعة العميل؟" ← غالبًا لأ. بيقرا schema خاص، ومحتاج صلاحية replication، و slot متساب ممكن يملا ديسك نظام الشركة كلها معتمدة عليه. هستخدم الـ API العام بـ webhooks و write_date poll فيه overlap. وأعيد التفكير لو إحنا اللي ماسكين الـ database والـ upgrades والحجم مخلي الـ polling مش عملي.

Part 3 — Canonical model and ACL 🔴 Advancedالجزء 3 — الـ canonical model والـ ACL

English

A canonical model is one shape your code uses for a business concept, independent of any vendor. An anti-corruption layer is the code at the boundary that translates to and from it; the pattern is in section 11 · ACL. Odoo's JSON has real quirks to contain, all visible in the payload below: a many2one is [id, name] or false; any empty field is false, even a date; amounts are floats; section rows sit among the invoice lines with display_type: "line_section"; taxes are IDs that need a second read.

The adapter validates with Zod, then maps: tuples to objects, false to null, floats to integer minor units using the currency's digits (not always 100), and Odoo's two status fields to one enum. A tax type the code doesn't understand throws instead of guessing. The NetSuite adapter here is a stand-in with an invented shape in the style of its records (US dates, nested references); it calls nothing.

The test of the design: the same invoice from both sources yields equal money and equal lines, and the domain function never changes. Keep the model small: a canonical model holding every field of every system becomes a second ERP schema. Include only what your domain uses.

  Odoo JSON-2  ---> fromOdoo()     --+
  [id, name], false, floats          |
                                     +--> Invoice --> domain code
  NetSuite     ---> fromNetSuite() --+    (canonical)   (no vendor names)
  (stand-in)
  M/D/YYYY, nested refs

  vendor shapes stop at the adapters
كل مصدر ليه adapter: fromOdoo بياخد الـ tuples والـ false والـ floats، وfromNetSuite (stand-in) بياخد التواريخ الأمريكي والـ references المتداخلة. الاتنين بيطلّعوا نفس Invoice، والـ domain code مبيشوفش أي اسم vendor. أشكال الـ vendors بتقف عند الـ adapters.
// الـ canonical model: شكل واحد بتاعنا، ومفيش فيه أي اسم field من Odoo أو NetSuite
import { z } from "zod";

export const Money = z.object({ minor: z.number().int(), currency: z.string().length(3) });
export const TaxLine = z.object({ code: z.string(), ratePercent: z.number() });
export const InvoiceLine = z.object({
  description: z.string(),
  quantity: z.number(),
  unitPrice: Money,
  net: Money,
  taxes: z.array(TaxLine),
});
export const Invoice = z.object({
  source: z.enum(["odoo", "netsuite"]),
  externalId: z.string(),
  number: z.string(),
  customer: z.object({ externalId: z.string(), name: z.string() }),
  issuedOn: z.iso.date(),
  dueOn: z.iso.date().nullable(),
  status: z.enum(["draft", "open", "paid", "cancelled"]),
  net: Money,
  tax: Money,
  total: Money,
  lines: z.array(InvoiceLine).min(1),
});
export type Invoice = z.infer<typeof Invoice>;

// عدد الخانات بييجي من العملة: JPY صفر و KWD تلاتة، مش دايمًا 100
const MINOR_DIGITS: Record<string, number> = { EGP: 2, SAR: 2, USD: 2, JPY: 0, KWD: 3 };
export function toMoney(amount: number, currency: string): z.infer<typeof Money> {
  const digits = MINOR_DIGITS[currency];
  if (digits === undefined) throw new Error(`unknown currency ${currency}`);
  return { minor: Math.round(amount * 10 ** digits), currency };
}

Part 4 — iPaaS versus custom 🟡 Intermediateالجزء 4 — الـ iPaaS قصاد الـ custom

English

An iPaaS (Make, n8n, Boomi, Workato, MuleSoft) gives you connectors, a visual flow and hosted retries. It fits when volume is modest, the flow is a straight line, the people who change it aren't developers, and a lost run is annoying rather than a financial error. It fits poorly when you need idempotency across steps, a per-entity version check, code review and tests on the mapping, or when per-task pricing scales with volume.

The pricing units differ, so the comparison must be per unit. As read on 2026-11-11: n8n counts one execution per workflow run regardless of steps (Starter EUR 20 for 2.5K, Pro EUR 50 for 10K, Business EUR 667 for 40K, annual billing). Make counts credits per action, and its page didn't show paid prices in what I could read. Workato publishes no list price. Boomi lists pay-as-you-go at USD 99 a month plus usage. MuleSoft shows "USD 2K per month to get started". Nothing here calls these services.

The model below labels every assumption. Note the batching effect: n8n's unit is the run, so 100 documents per run cuts the bill by 100, but one run now succeeds or fails for 100 documents, which gives up per-document retry. That is the idempotency trade-off appearing as a pricing decision. Self-hosted n8n removes the execution bill and adds operations work, and any real comparison needs a vendor quote.

Part 5 — Reconciliation as a feature 🔴 Advancedالجزء 5 — الـ reconciliation كـ feature

English

Lesson 06 reconciled a ledger with a provider, and lesson 29 did a one-time check. In a running integration, reconciliation is a permanent feature: a scheduled three-way compare of the shop, the payment provider and Odoo. Retries and idempotency reduce disagreements; only reconciliation tells you one happened.

A mismatch is not a log line; it is a record with a lifecycle: a state (open, investigating, accepted, resolved), an owner derived from its kind, and a first_seen_at that later runs never reset, so age is honest. When a run stops seeing an item it resolves automatically; if it reappears it reopens. accepted is a human decision that a difference is legitimate, and it leaves the age count.

That gives you a metric with a meaning: unreconciled value older than 24 hours. It measures money rather than rows, because one EGP 1,000,000 mismatch outweighs a hundred rounding differences. Set an objective on it, as in section 12 · SLOs, and alert on the breach. In the run, Odoo is real and the provider is a labelled in-memory stand-in.

// مقارنة تلات مصادر، وكل فرق بيبقى item ليه state و owner وعمر
import type pg from "pg";

export type Doc = { ref: string; minor: number };
export type Kind = "missing_in_shop" | "missing_in_provider" | "missing_in_odoo" | "amount_mismatch";
export type Mismatch = { ref: string; kind: Kind; valueMinor: number; detail: string };

const OWNER: Record<Kind, string> = {
  missing_in_shop: "backend-oncall",
  missing_in_provider: "payments-ops",
  missing_in_odoo: "integration-team",
  amount_mismatch: "finance",
};

export function compareThree(shop: Doc[], provider: Doc[], odoo: Doc[]): Mismatch[] {
  const index = (xs: Doc[]) => new Map(xs.map((x) => [x.ref, x.minor]));
  const s = index(shop), p = index(provider), o = index(odoo);
  const out: Mismatch[] = [];
  for (const ref of new Set([...s.keys(), ...p.keys(), ...o.keys()])) {
    const a = s.get(ref), b = p.get(ref), c = o.get(ref);
    const value = Math.max(a ?? 0, b ?? 0, c ?? 0);
    if (a === undefined) out.push({ ref, kind: "missing_in_shop", valueMinor: value, detail: `provider=${b} odoo=${c ?? "-"}` });
    else if (b === undefined) out.push({ ref, kind: "missing_in_provider", valueMinor: value, detail: `shop=${a} odoo=${c ?? "-"}` });
    else if (c === undefined) out.push({ ref, kind: "missing_in_odoo", valueMinor: value, detail: `shop=${a} provider=${b}` });
    else if (a !== b || b !== c) out.push({ ref, kind: "amount_mismatch", valueMinor: Math.max(Math.abs(a - b), Math.abs(b - c), Math.abs(a - c)), detail: `shop=${a} provider=${b} odoo=${c}` });
  }
  return out;
}

export const SCHEMA = `
  create table if not exists recon_item(
    ref text not null, kind text not null,
    value_minor bigint not null, detail text not null, owner text not null,
    state text not null default 'open' check (state in ('open','investigating','accepted','resolved')),

  await db.query("begin");
  try {
    let opened = 0;
    for (const m of found) {
      const r = await db.query<{ inserted: boolean }>(
        `insert into recon_item(ref, kind, value_minor, detail, owner, first_seen_at, last_seen_at)
         values ($1,$2,$3,$4,$5,$6,$6)
         on conflict (ref, kind) do update
           set value_minor = excluded.value_minor, detail = excluded.detail, last_seen_at = excluded.last_seen_at,
               state = case when recon_item.state = 'resolved' then 'open' else recon_item.state end,
               resolved_at = null
         returning (xmax = 0) as inserted`,
        [m.ref, m.kind, m.valueMinor, m.detail, OWNER[m.kind], now],
      );
      if (r.rows[0]!.inserted) opened++;
    }
    const resolved = await db.query(
      `update recon_item set state = 'resolved', resolved_at = $1
       where state in ('open','investigating') and last_seen_at < $1`,
      [now],
    );
    await db.query("commit");
    return { opened, autoResolved: resolved.rowCount ?? 0 };
  } catch (e) {
    await db.query("rollback");
    throw e;
  }
}

English

Three drills, run for real: BullMQ on real Redis, into real Odoo through JSON-2. The delivery theory is in section 12 · delivery and ordering. The receiving side is a small module with one public method, sync_apply(ref, version, vals). It locks the row, compares versions and writes in the same transaction. A check in Node before the call would leave a gap between the check and the write.

Drill 1, ERP down: the Odoo server is stopped mid-sync. Jobs fail, back off and wait; on restart the queue drains with nothing lost or duplicated. Backoff needs a cap and jitter: plain exponential retries double without limit, and without jitter they arrive in synchronized waves on a system that has only just recovered. The cap here is 3 s to keep the drill short; in production it would be minutes, with enough attempts to outlast your longest expected outage.

Drill 2, duplicates: the same 150 events are replayed, and every one reports duplicate. Drill 3, out of order: 25 entities with 5 versions each, shuffled, six at a time. A plain upsert leaves most entities on a stale version; the version check leaves none.

Drill 3 also caught a bug in my first attempt. I had classed every 4xx as permanent, so a job would not retry. But two concurrent first events race to create the row, and the loser's unique-index violation comes back as HTTP 422. Those events were dropped and 2 entities ended on old versions. The fix is an explicit contract: the method catches the violation and returns retry. Odoo runs at REPEATABLE READ, so the loser cannot simply re-read the row in the same transaction; a new attempt gets a new snapshot.

export type PartnerEvent = { ref: string; version: number; vals: { name: string; city: string } };
type Outcome = "created" | "applied" | "duplicate" | "stale";
export type Stats = Record<Outcome, number> & { failedAttempts: number; reasons: Record<string, number> };
export const emptyStats = (): Stats => ({ created: 0, applied: 0, duplicate: 0, stale: 0, failedAttempts: 0, reasons: {} });

type Target = { url: () => string; key: string };

async function applyToOdoo(t: Target, e: PartnerEvent): Promise<Outcome> {
  const res = await fetch(`${t.url()}/json/2/res.partner/sync_apply`, {
    method: "POST",
    headers: { "Content-Type": "application/json", Authorization: `bearer ${t.key}`, "X-Odoo-Database": "odoo" },
    body: JSON.stringify(e),
    signal: AbortSignal.timeout(15_000),
  });
  // الطلب نفسه غلط: إعادته 30 مرة مش هتصلحه
  if (res.status >= 400 && res.status < 500 && res.status !== 429) throw new UnrecoverableError(`odoo rejected: ${res.status}`);
  if (!res.ok) throw new Error(`odoo ${res.status}`);
  const { status } = (await res.json()) as { status: Outcome | "retry" };
  // خسر سباق الـ create: الـ retry هيلاقي الصف ويقارن الـ version
  if (status === "retry") throw new Error("lost the create race");
  return status;
}

export const backoff = (attempt: number, capMs = 3000): number => Math.min(200 * 2 ** attempt, capMs) * (0.5 + Math.random() / 2);

export function startSync(name: string, connection: { host: string; port: number }, target: Target, concurrency: number) {
  const queue = new Queue<PartnerEvent>(name, {
    connection,
    defaultJobOptions: { attempts: 30, backoff: { type: "custom" }, removeOnComplete: true, removeOnFail: false },
  });
  const stats = emptyStats();
  const worker = new Worker<PartnerEvent>(
    name,
    async (job: Job<PartnerEvent>) => {
      stats[await applyToOdoo(target, job.data)]++;
    },
    { connection, concurrency, settings: { backoffStrategy: (attempts: number) => backoff(attempts) } },
  );
  worker.on("failed", (_job, err) => {
    stats.failedAttempts++;
    const reason = err.message.slice(0, 40);
    stats.reasons[reason] = (stats.reasons[reason] ?? 0) + 1;
  });
  worker.on("error", () => {});
  return { queue, worker, stats };
}

Drill 1، الـ ERP وقع: وقفنا Odoo في نص الـ sync. الـ jobs بتفشل وتستنى، ولما يرجع الـ queue بتخلص من غير ما حاجة تضيع أو تتكرر. الـ backoff محتاج cap و jitter: الـ exponential العادي بيضاعف من غير حد، ومن غير jitter الـ retries بتيجي موجات ورا بعض على نظام لسه قايم. الـ cap هنا 3 ثواني عشان التجربة تخلص بسرعة، وفي production هيبقى دقايق، بعدد محاولات يعدي أطول وقوع متوقع.

Drill 2، التكرار: نفس الـ 150 event اتعادوا، وكلهم رجعوا duplicate. Drill 3، الترتيب الغلط: 25 entity كل واحد 5 نسخ، متلخبطين، 6 في نفس الوقت. الـ upsert العادي بيسيب معظمهم على نسخة قديمة، والـ version check مبيسيبش ولا واحد.

و Drill 3 مسك bug في أول محاولة ليا. كنت معتبر كل 4xx فشل نهائي فالـ job متتعادش. بس أول اتنين events بيتسابقوا يعملوا الصف، واللي بيخسر بياخد unique-index violation بترجع HTTP 422. الـ events دي ضاعت و 2 entities فضلوا على نسخ قديمة. الحل عقد صريح: الـ method بتمسك الـ violation وترجع retry. و Odoo شغال بـ REPEATABLE READ، فاللي خسر ميقدرش يقرا الصف تاني في نفس الـ transaction، والمحاولة الجديدة بتاخد snapshot جديد.

فين هستخدمه في شغلي؟ قبل ما تقول "الـ integration جاهز"، شغل التلات تجارب دول على staging: اقفل الـ ERP، أعد الـ events، ولخبط ترتيبها، واطبع الحالة النهائية. وأي event ليه version من المصدر: updated_at مش كفاية لو ساعات السيرفرات مختلفة، فاستخدم عداد بيزيد لكل entity. الغلطة الشائعة: تصنيف الأخطاء بالـ status code لوحده من غير ما تعرف الـ API بيرجع إيه في سباق حقيقي.
What breaks: a public method on a shared model sync_apply is callable by any user whose API key can reach it. It runs with the caller's rights (no sudo), and it writes only an allowlist of fields. Keep both properties; give the integration its own user with only the access it needs (lesson 19).
إيه اللي بيكسر: method عامة على model مشترك. sync_apply ينفع يناديها أي مستخدم الـ API key بتاعه يوصلها. بتشتغل بصلاحيات اللي نادى (من غير sudo)، وبتكتب allowlist من الـ fields بس. حافظ على الخاصيتين دول، وخلي للـ integration مستخدم لوحده بالصلاحيات اللي محتاجها بس (درس 19).

❌ Odoo field names inside the domain

  return `${move.partner_id[1]}: ${move.amount_total}`;
}
✅ The domain only sees the canonical type 
function customerLabel(invoice: Invoice) {
  const total = (invoice.total.minor / 100).toFixed(2);
  return `${invoice.customer.name}: ${total}`;
}
بالعامية

❌ الكود عارف إن partner_id tuple وإن المبلغ float: طبع undefined لما الـ partner فاضي، ووقع مع ERP تاني. ✅ الـ domain بيشوف Invoice بس، وتفاصيل Odoo محبوسة في الـ adapter.

❌ Every 4xx is permanent 
if (res.status >= 400 && res.status < 500)
  throw new UnrecoverableError("rejected");
// خسارة سباق الـ create كانت 422 فالـ event ضاع

const { status } = await res.json();

if (status === "retry") throw new Error("lost the create race");

❌ الـ 422 هنا كان سباق مؤقت مش طلب غلط، فاعتباره نهائي ضيّع events وساب 2 entities على نسخ قديمة. ✅ خلي الـ API يرجع حالة صريحة للحاجات اللي تتعاد، وسيب الـ 4xx للطلبات الغلط بجد.

if (event.version > current) {

  await odooWrite(ref, event.vals);
}

    'SELECT id, x_sync_version FROM res_partner '

بالعامية

❌ الفحص في Node والكتابة في Odoo عمليتين منفصلتين، و event أقدم ممكن يعدي الفحص ويكتب بعد واحد أحدث. ✅ FOR UPDATE والمقارنة والكتابة جوه transaction واحدة في المكان اللي الـ data عايشة فيه.

❌ Backoff with no cap and no jitter

// بعد 20 محاولة الانتظار بقى أيام
✅ A cap, and jitter 
const backoff = (attempt: number, capMs = 3000) =>
  Math.min(200 * 2 ** attempt, capMs) * (0.5 + Math.random() / 2);
بالعامية

❌ الـ exponential من غير حد بيوصل لأيام: الـ ERP رجع من بدري والـ job لسه نايمة، ومن غير jitter كله بيرجع في نفس اللحظة. ✅ الـ cap بيحدد أقصى انتظار، والـ jitter بيفرق الـ retries.

Cheat sheet · الخلاصة

  • Ownership is per field, written as data; an unlisted field is refused.
  • Every field has a conflict rule: owner-wins or manual-review.
  • Your service: outbox. Someone else's ERP: public API, webhooks and an overlapping poll.
  • CDC gives commit order and no rolled-back rows, but couples you to a private schema.
  • An unread replication slot retains WAL until the disk fills.
  • Adapters absorb [id, name], false, floats and section lines; the domain sees one type.
  • Keep the canonical model small; throw on values you don't understand.
  • Compare iPaaS per pricing unit; batching cuts cost and gives up per-document retry.
  • A mismatch is a record with state, owner and an age that survives runs.
  • Put an SLO on unreconciled value older than 24 h.
  • Check the version and write in the same transaction, where the data lives.
  • Backoff needs a cap and jitter; know which errors are really permanent.
بالعامية
  • الملكية لكل field ومكتوبة كـ data، والـ field اللي مش مكتوب بيترفض.
  • كل field ليه قاعدة تعارض: owner-wins أو manual-review.
  • الـ service بتاعك: outbox. الـ ERP بتاع حد تاني: API عام و webhooks و poll فيه overlap.
  • الـ CDC بيديك ترتيب الـ commit ومفيش صفوف rollback، بس بيربطك بـ schema خاص.
  • الـ replication slot اللي محدش بيقراه بيمسك WAL لحد ما الديسك يتملي.
  • الـ adapters بتمتص [id, name] وfalse والـ floats وأسطر الـ section، والـ domain بيشوف type واحد.
  • خلي الـ canonical model صغير، واعمل throw على القيم اللي مش فاهمها.
  • قارن الـ iPaaS بوحدة التسعير؛ الـ batching بيقلل التكلفة وبتتنازل عن الـ retry لكل document.
  • الفرق record ليه state و owner وعمر بيعيش عبر الـ runs.
  • حط SLO على الفلوس غير المتطابقة الأقدم من 24 ساعة.
  • افحص الـ version واكتب في نفس الـ transaction، في المكان اللي الـ data عايشة فيه.
  • الـ backoff محتاج cap و jitter، واعرف أنهي أخطاء نهائية فعلًا.
