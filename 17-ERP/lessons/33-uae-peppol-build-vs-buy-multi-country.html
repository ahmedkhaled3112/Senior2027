Why this matters · ليه ده مهم

English

Lessons 31 and 32 connected you directly to one authority each. The UAE works differently: you never talk to the authority, you go through an accredited provider on a network. Once a company sells in Egypt, Saudi Arabia and the UAE, it runs three different legal models at the same time, and the expensive mistake is writing if (country === "SA") through the billing code.

This lesson answers the two questions that decide a project's budget: what do you buy, and how do you shape what you build so a fourth country is a new file instead of a rewrite. No tax authority, Peppol access point or service provider is called anywhere here. Every counterpart is a labelled stand-in on loopback.

بالعامية

في الدرسين 31 و 32 اتوصلت مباشرة بجهة واحدة في كل مرة. الإمارات شغلها مختلف: إنت عمرك ما بتكلم الجهة نفسها، بتعدّي عن طريق provider معتمد على network. ولما شركة تبيع في مصر والسعودية والإمارات، بتبقى شغّالة بـ 3 موديلات قانونية مختلفة في نفس الوقت، والغلطة الغالية إنك تكتب if (country === "SA") في كل حتة في كود الفواتير.

الدرس ده بيجاوب على السؤالين اللي بيحددوا ميزانية أي مشروع: هتشتري إيه، وهتبني الباقي إزاي بحيث الدولة الرابعة تبقى ملف جديد مش إعادة كتابة. مفيش أي call لأي tax authority أو Peppol access point أو service provider في الدرس كله. كل طرف تاني هنا stand-in متعلّم عليه وشغال على loopback.

Part 1 — Peppol and the five corners 🔴 Advancedالجزء 1 — Peppol والخمس أركان

English

Peppol is a network for exchanging business documents. Its classic model has four corners: C1 the seller's system, C2 the seller's access point, C3 the buyer's access point, C4 the buyer's system. The seller only has to connect to one access point to reach every buyer on the network, the same way an email user only needs one mail provider. Corner five adds the tax authority: tax data is reported to C5 alongside the exchange.

PINT AE is the UAE's specification under Peppol International (PINT). It defines the document, identified by the specification identifier urn:peppol:pint:billing-1@ae-1. In the UAE, the corners C2 and C3 are Accredited Service Providers (ASPs), and every issuer and recipient must appoint one. As secondary sources describe it, the sender's ASP validates the invoice and sends it both to the receiver's ASP and to the Federal Tax Authority, whose system acts as a repository. PINT AE also defines cases where a document is only reported: "the document need not be exchanged with C3; instead, it should only be reported to C5", such as deemed supply.

The engineering point is where each failure lands. A validation error stops at C2 and comes back to you synchronously. A buyer's system being down is not your failure at all: C3 stores and forwards. The dangerous case is the lost acknowledgement, where C3 received the invoice but C2 never heard back, so C2 resends. Only deduplication on the invoice's unique identifier keeps the buyer from receiving it twice. The simulation below runs all five corners as real HTTP servers on loopback, labelled as a stand-in.

// تنبيه: ⁦[STAND-IN, not a real Peppol network]⁩ كل الأركان http servers على loopback
import http from "node:http";
import type { AddressInfo } from "node:net";

type Invoice = { uuid: string; number: string; sellerTin: string; buyerTin: string; totalAed: number };
type Fault = "none" | "c2-rejects" | "c3-down" | "c3-ack-lost" | "c4-down" | "c5-down";
type Handler = (body: Invoice, res: http.ServerResponse) => void | Promise<void>;

const reply = (res: http.ServerResponse, status: number, body: object) => {
  res.writeHead(status, { "content-type": "application/json" });
  res.end(JSON.stringify(body));
};

async function corner(handler: Handler) {
  const server = http.createServer(async (req, res) => {
    let raw = "";
    for await (const chunk of req) raw += chunk;
    await handler(JSON.parse(raw) as Invoice, res);
  });
  await new Promise<void>((ok) => server.listen(0, "127.0.0.1", ok));
  const { port } = server.address() as AddressInfo;
  return { url: `http://127.0.0.1:${port}/`, close: () => { server.closeAllConnections(); server.close(); } };
}

const post = async (url: string, doc: Invoice) => {
  try {
    const res = await fetch(url, { method: "POST", body: JSON.stringify(doc), signal: AbortSignal.timeout(2000) });
    return res.status;
  } catch {
    // مفيش رد خالص: ده الـ unknown، ممكن يكون وصل وممكن لأ
    return 0;
  }
};

async function run(fault: Fault) {
  const buyerInbox = new Map<string, number>();
  const taxRepository = new Map<string, number>();
  const seenByC3 = new Set<string>();
  const c3Pending: Invoice[] = [];
  const count = { c3Calls: 0, c4Fails: fault === "c4-down" ? 1 : 0, c5Fails: fault === "c5-down" ? 4 : 0, c3Fails: fault === "c3-down" ? 2 : 0, ackLost: fault === "c3-ack-lost" ? 1 : 0 };

  // الركن الخامس: الـ tax authority، بيخزّن بس ومبيعملش validation
  const c5 = await corner((doc, res) => {
    if (count.c5Fails-- > 0) return reply(res, 503, { error: "repository unavailable" });
    taxRepository.set(doc.uuid, (taxRepository.get(doc.uuid) ?? 0) + 1);
    reply(res, 200, { stored: true });
  });

  // الركن الرابع: الـ ERP بتاع المشتري
  const c4 = await corner((doc, res) => {
    if (count.c4Fails-- > 0) return reply(res, 503, { error: "buyer ERP down" });
    buyerInbox.set(doc.uuid, (buyerInbox.get(doc.uuid) ?? 0) + 1);
    reply(res, 200, { received: true });
  });

  // الركن التالت: الـ ASP بتاع المشتري، store and forward وبيعمل dedupe بالـ uuid
  const c3 = await corner(async (doc, res) => {
    count.c3Calls++;
    if (count.c3Fails-- > 0) return reply(res, 503, { error: "receiver ASP down" });
    if (!seenByC3.has(doc.uuid)) {
      seenByC3.add(doc.uuid);
      const status = await post(c4.url, doc);
      if (status !== 200) c3Pending.push(doc);
    }
    if (count.ackLost-- > 0) { res.destroy(); return; }
    reply(res, 202, { accepted: true });
  });

  const reportPending: Invoice[] = [];
  // الركن التاني: الـ ASP بتاع البايع، بيعمل validate وبعدين deliver و report
  const c2 = await corner(async (doc, res) => {
    if (!/^\d{10}$/.test(doc.sellerTin)) return reply(res, 422, { error: "IBR-148-AE: seller TIN must be 10 digits" });
    let delivered = false;
    for (let attempt = 1; attempt <= 3 && !delivered; attempt++) delivered = (await post(c3.url, doc)) === 202;
    if ((await post(c5.url, doc)) !== 200) reportPending.push(doc);
    reply(res, delivered ? 202 : 502, { delivered });
  });

  const doc: Invoice = { uuid: "7f0c1a52-lab", number: "INV-1001", sellerTin: fault === "c2-rejects" ? "12345" : "1000000001", buyerTin: "1000000002", totalAed: 1050 };
  const c1Saw = await post(c2.url, doc);

  // الـ drain: بعد ما الخدمة ترجع، الركن اللي شايل الـ pending هو اللي يعيد
  const before = { c3Pending: c3Pending.length, reportPending: reportPending.length };
  for (const pending of c3Pending.splice(0)) await post(c4.url, pending);
  for (const pending of reportPending.splice(0)) {
    let status = 0;
    for (let attempt = 1; attempt <= 5 && status !== 200; attempt++) status = await post(c5.url, pending);
  }

  for (const c of [c2, c3, c4, c5]) c.close();
  return { fault, c1Saw, c3Calls: count.c3Calls, ...before, buyerCopies: buyerInbox.get(doc.uuid) ?? 0, taxCopies: taxRepository.get(doc.uuid) ?? 0 };
}

console.log("[STAND-IN, not a real Peppol network]");
const faults: Fault[] = ["none", "c2-rejects", "c3-down", "c3-ack-lost", "c4-down", "c5-down"];
console.log("fault        C1   C3calls c3Pending reportPending buyer tax");
for (const fault of faults) {
  const r = await run(fault);
  console.log(`${r.fault.padEnd(12)} ${r.c1Saw}  ${String(r.c3Calls).padEnd(7)} ${String(r.c3Pending).padEnd(9)} ${String(r.reportPending).padEnd(13)} ${r.buyerCopies}     ${r.taxCopies}`);
}

بالعامية

Peppol network لتبادل المستندات التجارية. الموديل الكلاسيكي 4 أركان: C1 نظام البايع، C2 الـ access point بتاع البايع، C3 الـ access point بتاع المشتري، C4 نظام المشتري. البايع بيتوصل بـ access point واحد ويوصل لكل المشترين على الـ network، زي ما إنت محتاج mail provider واحد عشان تبعت لأي حد. والركن الخامس بيضيف الجهة الضريبية: بيانات الضريبة بتتبلّغ لـ C5 جنب التبادل.

PINT AE هي مواصفة الإمارات تحت Peppol International (PINT). بتعرّف شكل المستند، و specification identifier بتاعها urn:peppol:pint:billing-1@ae-1. وفي الإمارات C2 و C3 هم Accredited Service Providers (ASPs)، وكل مُصدر ومستلم لازم يعيّن واحد. وزي ما مصادر ثانوية بتوصفه، الـ ASP بتاع البايع بيعمل validate للفاتورة ويبعتها للـ ASP بتاع المستلم وللـ Federal Tax Authority، والنظام بتاعها بيشتغل كـ repository. و PINT AE كمان بتعرّف حالات المستند فيها بيتبلّغ بس: مش لازم يتبادل مع C3 ويتبلّغ لـ C5 لوحده، زي الـ deemed supply.

النقطة الهندسية هي كل failure بيقع فين. الـ validation error بيقف عند C2 وبيرجعلك على طول. نظام المشتري لو واقع مش مشكلتك أصلًا: C3 بيخزّن ويبعت بعدين. الحالة الخطر هي الـ lost acknowledgement: C3 استلم الفاتورة و C2 مسمعش رد، فبيعيد الإرسال. والـ dedupe على الـ unique identifier بتاع الفاتورة هو الوحيد اللي بيمنع المشتري يستلمها مرتين. الـ simulation اللي فوق بتشغّل الخمس أركان كـ HTTP servers حقيقية على loopback، ومتعلّم عليها إنها stand-in.

فين هستخدمه في شغلي؟ لو بتبني integration بين Node API و ASP، الـ uuid بتاع الفاتورة لازم يتولّد مرة واحدة ويتخزن قبل أول إرسال، زي الـ idempotency key بالظبط. لو ولّدته جوه الـ retry، كل محاولة تبقى فاتورة جديدة. الغلطة الشائعة إنك تعتبر 202 من الـ ASP معناه "المشتري استلم": ده معناه "الـ ASP استلم" بس، والحالة النهائية بتيجي بعدين.
Interview question "In a five-corner network your provider times out on submit. What do you do?" → Treat it as unknown, not failed. Resend the same document with the same unique identifier, and rely on deduplication downstream. Never generate a new number or identifier for the retry, because then a delivered invoice and its retry become two legal documents.
"في network بخمس أركان، الـ provider عمل timeout على الـ submit. تعمل إيه؟" ← اعتبرها unknown مش failed. ابعت نفس المستند بنفس الـ unique identifier، واعتمد على الـ dedupe اللي بعدك. أوعى تولّد رقم أو identifier جديد للـ retry، لأن ساعتها فاتورة اتسلّمت والـ retry بتاعها يبقوا مستندين قانونيين.

Part 2 — UAE deadlines 🔴 Advancedالجزء 2 — مواعيد الإمارات

English

The primary source for the first phase is Ministerial Decision 66 of 2026, Article One: a person "whose Revenue is equal to or exceeds AED 50,000,000 shall appoint an Accredited Service Provider by 30 October 2026 and shall implement the Electronic Invoicing System by 1 January 2027." Today is 11 November 2026, so that appointment deadline has already passed and go-live is 51 days away.

The next phases, as reported by KPMG on 22 July 2026: companies below AED 50,000,000 appoint an ASP by 31 March 2027 and go live on 1 July 2027; in-scope government entities appoint by 31 March 2027 and go live on 1 October 2027. A warning about sources: you will see 31 March 2027 quoted as "the deadline" for smaller companies, and that looks like a conflict with 1 July. In KPMG's table they are two milestones of the same phase: 31 March is for appointing the ASP, 1 July is for going live. When a page gives one date without naming the milestone, read the Ministry's text before you plan around it.

The rules keep moving. Sovos reports that Ministerial Decision 197 of 2026, effective 1 October 2026, amends Decision 243 of 2025: invoices must be transmitted within 14 business days, and the requirement to store data inside the UAE is removed. ClearTax limits the 14-day rule to issuers not registered for VAT, so read the text before relying on either summary. So keep these dates in data with their source and confidence attached. Don't scatter them through code.

// المواعيد data مش if متفرقة في الكود، وكل سطر معاه مصدره ودرجة الثقة فيه
type Phase = {
  id: string;
  applies: (c: Company) => boolean;
  appointAspBy: string;
  goLive: string;
  source: "primary: MoF Decision 66/2026" | "secondary: KPMG 2026-07-22";
};
type Company = { name: string; revenueAed: number; government: boolean };

const PHASES: Phase[] = [
  { id: "phase-1", applies: (c) => !c.government && c.revenueAed >= 50_000_000, appointAspBy: "2026-10-30", goLive: "2027-01-01", source: "primary: MoF Decision 66/2026" },
  { id: "phase-2", applies: (c) => !c.government && c.revenueAed < 50_000_000, appointAspBy: "2027-03-31", goLive: "2027-07-01", source: "secondary: KPMG 2026-07-22" },
  { id: "phase-3", applies: (c) => c.government, appointAspBy: "2027-03-31", goLive: "2027-10-01", source: "secondary: KPMG 2026-07-22" },
];

const days = (from: string, to: string) => Math.round((Date.parse(to) - Date.parse(from)) / 86_400_000);

export function check(company: Company, today: string) {
  const phase = PHASES.find((p) => p.applies(company));
  if (!phase) throw new Error(`no phase for ${company.name}`);
  const aspDays = days(today, phase.appointAspBy);
  const liveDays = days(today, phase.goLive);
  const state = liveDays <= 0 ? "LIVE: must be issuing" : aspDays < 0 ? "ASP deadline passed" : "appoint an ASP";
  return { company: company.name, phase: phase.id, aspDays, liveDays, state, source: phase.source };
}

بالعامية

المصدر الأساسي للمرحلة الأولى هو Ministerial Decision 66 of 2026، المادة الأولى: أي شخص الـ Revenue بتاعه يساوي أو يعدّي AED 50,000,000 لازم يعيّن Accredited Service Provider قبل 30 أكتوبر 2026 ويطبّق النظام قبل 1 يناير 2027. النهارده 11 نوفمبر 2026، يعني ميعاد التعيين عدّى والـ go-live بعد 51 يوم.

المراحل اللي بعدها زي ما KPMG نشرت في 22 يوليو 2026: الشركات الأقل من AED 50,000,000 تعيّن ASP قبل 31 مارس 2027 و go-live في 1 يوليو 2027؛ والجهات الحكومية المشمولة تعيّن قبل 31 مارس 2027 و go-live في 1 أكتوبر 2027. تحذير عن المصادر: هتلاقي 31 مارس 2027 مكتوب إنه "الـ deadline" للشركات الأصغر، وده شكله متعارض مع 1 يوليو. في جدول KPMG هما milestone اتنين في نفس المرحلة: 31 مارس لتعيين الـ ASP، و1 يوليو للـ go-live. لما صفحة تديك تاريخ واحد من غير ما تقول بتاع إيه، اقرا نص الوزارة قبل ما تخطط عليه.

والقواعد لسه بتتغير. Sovos بتقول إن Ministerial Decision 197 of 2026، الساري من 1 أكتوبر 2026، بيعدّل Decision 243 of 2025: الفواتير لازم تتبعت خلال 14 business day، واتشال شرط تخزين البيانات جوه الإمارات. و ClearTax بتقول إن قاعدة الـ 14 يوم للمُصدرين غير المسجلين في الـ VAT بس، فاقرا النص قبل ما تعتمد على أي ملخص منهم. فخلي المواعيد دي data ومعاها المصدر ودرجة الثقة، ومتفرّقهاش في الكود.

Part 4 — Build versus buy 🔴 Advancedالجزء 4 — تبني ولا تشتري

English

A useful decision model separates hard gates from costs. Gates remove options outright: does a connector exist for your ERP at all, and does the country require an accredited provider? Costs compare what survives, over a fixed horizon. The inputs that matter are documents per month, number of countries, certification and accreditation, who carries each regulatory change, signing operations, and exit cost.

Packaged connectors exist. The Odoo Apps store lists Suntech's account_tca_peppol for Odoo 19, at $1,786.40 when read, which generates PINT AE and submits to that vendor's access point. For ERPNext, ECOSIRE advertises a build-to-order PINT AE app that sends through an ASP (seen in a search result; I did not open the page). Those are vendor claims, I tested neither, and I found no listing for Odoo 20. The inference I draw, and it is an inference, is that basic connectivity is a commodity: getting an XML to an endpoint is what you can buy for under two thousand dollars. The differentiated engineering is what the connector doesn't know about your business: reconciling what the authority accepted against your ledger, handling the failures from Part 1, and operating signing keys.

Every number in the model below is an assumption made up for illustration. Replace them. The value is in the shape of the calculation and in seeing which input flips the answer.

  name: string;

const ASSUME = {
  engineerDayUsd: 300,
  buildDaysPerCountry: 90,
  daysPerRegChange: 6,
  signingAndCertUsdPerYear: 9_000,
  onCallDaysPerYear: 25,
  connectorLicenseUsd: 1_800,
  connectorIntegrationDays: 15,
  providerMinUsdPerMonth: 150,
  reconcileDaysPerCountry: 12,
  vendorChangeDaysPerFlow: 25,
  ownFlowDays: 6,

  years: 3,

// الـ provider بيسعّر بالشرايح: كل ما الحجم يزيد سعر المستند بينزل
const usdPerDoc = (docs: number) => (docs > 100_000 ? 0.012 : docs > 10_000 ? 0.04 : 0.08);

export function model(p: Profile, a = ASSUME) {
  const providerPerYear = Math.max(p.docsPerMonth * usdPerDoc(p.docsPerMonth), a.providerMinUsdPerMonth * p.countries) * 12;
  const reconcile = p.countries * a.reconcileDaysPerCountry * a.engineerDayUsd;
  const regChange = p.regulatoryChangesPerYear * p.countries * a.daysPerRegChange * a.engineerDayUsd * a.years;
  const onCall = a.onCallDaysPerYear * a.engineerDayUsd * a.years;

  // (1) اشتري: connector جوه الـ ERP والـ vendor شايل الـ regulatory change
  const buy =
    p.countries * (a.connectorLicenseUsd + a.connectorIntegrationDays * a.engineerDayUsd) +
    reconcile + providerPerYear * a.years + p.customFlows * a.vendorChangeDaysPerFlow * a.engineerDayUsd;

  // (2) الـ core بتاعك والنقل من provider: نص الـ regulatory change بس بيبقى عليك
  const hybrid =
    (40 + p.countries * 30) * a.engineerDayUsd +
    reconcile + providerPerYear * a.years + regChange * 0.5 + onCall + p.customFlows * a.ownFlowDays * a.engineerDayUsd;

  // (3) ابني كله: الـ signing والـ regulatory change والـ on-call كلهم عليك
  const build =
    p.countries * a.buildDaysPerCountry * a.engineerDayUsd +
    reconcile + regChange + onCall + p.customFlows * a.ownFlowDays * a.engineerDayUsd +
    (p.needsOwnSigning ? a.signingAndCertUsdPerYear * p.countries * a.years : 0);

  const options = [
    // الـ gate الأولاني: الـ connector الجاهز بيتباع لـ ERP معروف، مش لنظامك الخاص
    { option: "buy connector", usd: Math.round(buy), allowed: p.connectorExists },
    { option: "own core + provider", usd: Math.round(hybrid), allowed: true },
    // الشرط ده hard gate: لو الدولة بتلزمك بـ provider معتمد، الـ build الكامل مش مسموح أصلًا
    { option: "build everything", usd: Math.round(build), allowed: !p.mustUseAccreditedProvider },
  ];
  const winner = options.filter((o) => o.allowed).sort((x, y) => x.usd - y.usd)[0]!;
  return { name: p.name, options, winner: winner.option, exitCostUsd: p.countries * a.exitDaysPerCountry * a.engineerDayUsd };
}

Part 5 — A multi-country architecture 🔴 Advancedالجزء 5 — Architecture لأكتر من دولة

English

This is ports and adapters applied to compliance. The port EInvoicingProvider has five verbs: prepare, sign, submit, status, cancel. Everything country-specific sits behind it: numbering, rounding, tax rules, transport, signature. The core owns only what is the same everywhere: the document's lifecycle.

The key design choice is one shared state machine (section 11 · state machines) that handles both synchronous clearance and asynchronous reporting. They look different but reduce to the same result type: submit returns accepted (Saudi clearance), pending (Egypt, the UAE), rejected, or unknown. The core doesn't know which country produced it.

Two invariants carry over from lessons 31 and 32. The signed bytes are persisted before the first send, so a retry after unknown resends exactly those bytes. And a rejection is terminal for that document. The proof of the design is test 8: a fourth, entirely fake country is defined inside the test file, works end to end, and an assertion reads core.ts to confirm it contains no country name.

// الـ core: مفيهوش اسم دولة واحد، كل اللي يخص الدولة ورا الـ port
export type Invoice = { id: string; country: string; buyerTaxId: string; netMinor: bigint; vatRateBp: number };
export type Prepared = { invoiceId: string; number: string; payload: string };
export type Signed = Prepared & { signature: string };
export type Submit =
  | { kind: "accepted"; ref: string }
  | { kind: "pending"; ref: string }
  | { kind: "rejected"; errors: string[] }
  | { kind: "unknown" };
export type Status = { kind: "accepted" | "pending" } | { kind: "rejected"; errors: string[] };

export interface EInvoicingProvider {
  readonly country: string;
  prepare(invoice: Invoice, sequence: number): Prepared;
  sign(prepared: Prepared): Promise<Signed>;
  submit(signed: Signed): Promise<Submit>;
  status(ref: string): Promise<Status>;
  cancel(ref: string, reason: string): Promise<boolean>;
}

export type State = "draft" | "signed" | "pending" | "accepted" | "rejected" | "unknown" | "cancelled";
type Event = "signed" | "accepted" | "pending" | "rejected" | "unknown" | "cancelled";

// الـ state machine واحدة: الـ clearance المتزامن والـ reporting الغير متزامن بيعدّوا منها الاتنين
const TRANSITIONS: Record<State, Partial<Record<Event, State>>> = {
  draft: { signed: "signed" },
  signed: { accepted: "accepted", pending: "pending", rejected: "rejected", unknown: "unknown" },
  unknown: { accepted: "accepted", pending: "pending", rejected: "rejected", unknown: "unknown" },
  pending: { accepted: "accepted", rejected: "rejected", pending: "pending" },
  accepted: { cancelled: "cancelled" },
  rejected: {},
  cancelled: {},
};

export type Record_ = { invoice: Invoice; state: State; signed?: Signed; ref?: string; errors?: string[]; sends: number };

export class Engine {
  readonly records = new Map<string, Record_>();
  private readonly sequences = new Map<string, number>();
  private readonly providers = new Map<string, EInvoicingProvider>();

  register(provider: EInvoicingProvider) { this.providers.set(provider.country, provider); }

  private providerFor(country: string) {
    const provider = this.providers.get(country);
    if (!provider) throw new Error(`no provider registered for ${country}`);
    return provider;
  }

  private move(record: Record_, event: Event) {
    const next = TRANSITIONS[record.state][event];
    if (!next) throw new Error(`illegal transition ${record.state} --${event}`);
    record.state = next;
  }

  private apply(record: Record_, result: Submit) {
    if (result.kind === "rejected") record.errors = result.errors;
    if (result.kind === "accepted" || result.kind === "pending") record.ref = result.ref;
    this.move(record, result.kind);
  }

  async issue(invoice: Invoice) {
    const provider = this.providerFor(invoice.country);
    const sequence = (this.sequences.get(invoice.country) ?? 0) + 1;
    this.sequences.set(invoice.country, sequence);
    const record: Record_ = { invoice, state: "draft", sends: 0 };
    this.records.set(invoice.id, record);
    // الـ bytes الموقّعة بتتحفظ قبل أول إرسال، عشان الـ retry يبعت نفس الـ bytes
    record.signed = await provider.sign(provider.prepare(invoice, sequence));
    this.move(record, "signed");
    record.sends++;
    this.apply(record, await provider.submit(record.signed));
    return record;
  }

  async retryUnknown(id: string) {
    const record = this.records.get(id);
    if (!record || record.state !== "unknown" || !record.signed) throw new Error(`nothing to retry for ${id}`);
    record.sends++;
    this.apply(record, await this.providerFor(record.invoice.country).submit(record.signed));
    return record;
  }

  async poll(id: string) {
    const record = this.records.get(id);
    if (!record || record.state !== "pending" || !record.ref) throw new Error(`nothing to poll for ${id}`);
    const status = await this.providerFor(record.invoice.country).status(record.ref);
    if (status.kind === "rejected") record.errors = status.errors;
    this.move(record, status.kind);
    return record;
  }

  async cancel(id: string, reason: string) {
    const record = this.records.get(id);
    if (!record?.ref) throw new Error(`nothing to cancel for ${id}`);
    if (await this.providerFor(record.invoice.country).cancel(record.ref, reason)) this.move(record, "cancelled");
    return record;
  }
}

export function vat(netMinor: bigint, rateBp: number) {
  const raw = netMinor * BigInt(rateBp);
  return (raw + 5_000n) / 10_000n;
}

export const fake = (payload: string) => createHash("sha256").update(`lab-only:${payload}`).digest("hex").slice(0, 16);

const call = async (url: string, body: object): Promise<{ status: number; json: Record<string, unknown> }> => {
  const res = await fetch(url, { method: "POST", body: JSON.stringify(body), signal: AbortSignal.timeout(2000) });
  return { status: res.status, json: (await res.json()) as Record<string, unknown> };
};

abstract class HttpAdapter implements EInvoicingProvider {
  abstract readonly country: string;
  protected abstract readonly path: string;
  protected readonly baseUrl: string;
  constructor(baseUrl: string) { this.baseUrl = baseUrl; }
  abstract prepare(invoice: Invoice, sequence: number): Prepared;

  async sign(prepared: Prepared): Promise<Signed> { return { ...prepared, signature: fake(prepared.payload) }; }

  async submit(signed: Signed): Promise<Submit> {
    try {
      const { status, json } = await call(`${this.baseUrl}/${this.path}/submit`, signed);
      if (status === 422) return { kind: "rejected", errors: json.errors as string[] };
      if (status === 202) return { kind: "pending", ref: json.ref as string };
      if (status === 200) return { kind: "accepted", ref: json.ref as string };
      return { kind: "unknown" };
    } catch {
      // مفيش رد: مش عارفين وصل ولا لأ، فمينفعش نقول rejected ولا نولّد رقم جديد
      return { kind: "unknown" };
    }
  }

  async status(ref: string): Promise<Status> {
    const { json } = await call(`${this.baseUrl}/${this.path}/status`, { ref });
    return json as unknown as Status;
  }

  async cancel(ref: string, reason: string) {
    return (await call(`${this.baseUrl}/${this.path}/cancel`, { ref, reason })).status === 200;
  }
}

import http from "node:http";

type Doc = { number: string; payload: string; signature: string };

export async function startStandIn() {
  const seen = new Map<string, string>();
  const statuses = new Map<string, string>();
  const received: string[] = [];
  const faults = { dropAckOnce: false };

  const server = http.createServer(async (req, res) => {
    let raw = "";
    for await (const chunk of req) raw += chunk;
    const body = JSON.parse(raw) as Doc & { ref: string };
    const [, country, action] = (req.url ?? "").split("/");
    const send = (code: number, json: object) => { res.writeHead(code, { "content-type": "application/json" }); res.end(JSON.stringify(json)); };

    if (action === "status") return send(200, { kind: statuses.get(body.ref) ?? "accepted" });
    if (action === "cancel") return send(200, { cancelled: true });

    received.push(body.payload);
    if (body.payload.includes('"net":"0"')) return send(422, { errors: [`${country}: net amount must be positive`] });
    // الـ dedupe هنا بالـ bytes: نفس الـ payload مبيتحسبش فاتورة جديدة
    const ref = seen.get(body.payload) ?? `${country}-ref-${seen.size + 1}`;
    seen.set(body.payload, ref);
    if (faults.dropAckOnce) { faults.dropAckOnce = false; res.destroy(); return; }
    if (country === "sa") return send(200, { ref });
    statuses.set(ref, "accepted");
    return send(202, { ref });
  });
  await new Promise<void>((ok) => server.listen(0, "127.0.0.1", ok));
  const { port } = server.address() as AddressInfo;
  return { url: `http://127.0.0.1:${port}`, received, faults, uniqueDocs: () => seen.size, close: () => { server.closeAllConnections(); server.close(); } };
}

ده ports and adapters متطبق على الـ compliance. الـ port اللي اسمه EInvoicingProvider فيه 5 أفعال: prepare و sign و submit و status و cancel. وكل حاجة خاصة بدولة ورا الـ port: الترقيم، التقريب، قواعد الضريبة، النقل، والتوقيع. والـ core شايل بس اللي واحد في كل حتة: دورة حياة المستند.

القرار الأساسي هو state machine واحدة مشتركة (القسم 11 · state machines) بتشيل الـ clearance المتزامن والـ reporting الغير متزامن. شكلهم مختلف بس بيتحولوا لنفس نوع النتيجة: submit بترجّع accepted (الـ clearance السعودي) أو pending (مصر والإمارات) أو rejected أو unknown. والـ core ميعرفش أنهي دولة طلّعت النتيجة.

فيه invariant اتنين جايين من الدرسين 31 و 32. الـ bytes الموقّعة بتتحفظ قبل أول إرسال، عشان الـ retry بعد unknown يبعت نفس الـ bytes بالظبط. والـ rejection نهائي للمستند ده. وإثبات التصميم هو الـ test التامن: دولة رابعة وهمية بالكامل معرّفة جوه ملف التست، شغالة من أولها لآخرها، و assertion بيقرا core.ts ويتأكد إن مفيهوش أي اسم دولة.

فين هستخدمه في شغلي؟ الشركة قررت تدخل الكويت السنة الجاية. لو الكود فيه switch (country) في 40 مكان، ده مشروع 3 شهور ومخاطرة على الدول الشغالة. لو عندك port، ده adapter جديد وملف config. نفس فكرة PaymentGateway interface لما تضيف Stripe جنب Paymob. الغلطة الشائعة إن الـ core يبدأ يعرف "لو الدولة كذا استنى": أول if بيخلّي التاني أسهل.

Part 6 — Operating it 🔴 Advancedالجزء 6 — تشغيله

English

Compliance systems fail in a specific way: nothing in your code changes, and the rules around it do. So four things become operational data. A compliance calendar holds every dated obligation, with an owner and a source. Schema versions per country record which version a document was issued under, since an archived invoice must be read against the rules of its day. Per-country dashboards need different thresholds, because a pending document for 9 minutes is alarming under synchronous clearance and normal on an asynchronous network.

The archive has legally required retention, and you should check each period with an accountant. From the sources I could read, which are secondary: Egypt requires 5 years from filing the return (EY on Law 206 of 2020; I did not check whether Law 7 of 2025 changed this); Saudi Arabia 6 years, and up to 11 for real estate, with records available inside the Kingdom (Qoyod); the UAE 5 years, and 7 for real estate (ClearTax), with the in-country storage requirement removed by Decision 197 of 2026 (Sovos). Keep the signed bytes and the authority's response, not just a rendered PDF.

What breaks: an authority changes a validation rule at midnight. Your code is unchanged, your tests are green, and at 00:01 every invoice is rejected. A canary catches it: a scheduled contract test that sends saved samples to the provider's validation endpoint and alerts on the first difference. The example runs against a labelled stand-in. Against a real provider, use only a sandbox your contract permits.

Common mistakes · غلطات شائعة

❌ Generating the identifier inside the retry 
// كل محاولة بتطلع فاتورة جديدة
async function send(invoice: Invoice) {
  const doc = { ...invoice, uuid: randomUUID() };
  return retry(() => provider.submit(doc));
}
✅ Generate once, persist, then send 
// الـ uuid بيتخزن مرة واحدة قبل أول إرسال
const doc = await store.getOrCreate(invoice.id, () =>
  ({ ...invoice, uuid: randomUUID() }));
await retry(() => provider.submit(doc));
بالعامية

❌ لو الـ uuid بيتولّد جوه الـ function اللي بتتعاد، الـ dedupe عند C3 مش هيشتغل، والمشتري يستلم فاتورتين قانونيتين. ✅ ولّده مرة واحدة وخزّنه قبل أول إرسال، وكل retry يبعت نفس القيمة.

❌ Country logic in the core 
// كل دولة جديدة بتعدّل الكود الشغال
if (invoice.country === "SA") await clear(doc);
else if (invoice.country === "AE") await viaAsp(doc);
else await submitAndPoll(doc);
✅ One port, one result type 
// الـ core ميعرفش الدولة، بيعرف النتيجة بس
const result = await providerFor(invoice.country).submit(signed);
apply(record, result);
بالعامية

❌ كل if على الدولة في الـ core معناها إن إضافة دولة بتلمس كود شغال في دول تانية، ومخاطرة على فواتير حقيقية. ✅ الـ core بيتعامل مع نوع نتيجة واحد، والدولة بتتحدد مرة واحدة عند اختيار الـ adapter.

❌ Treating a timeout as rejected 
// الجهة ممكن تكون قبلت، وإنت هتصدر رقم جديد
try { await submit(doc); }
catch { markRejected(doc); issueNewNumber(doc); }
✅ A timeout is unknown 
// نفس الـ bytes بتتبعت تاني لحد ما نعرف
try { await submit(doc); }
catch { markUnknown(doc); scheduleResend(doc.signedBytes); }
بالعامية

❌ الـ timeout مش rejection: ممكن الجهة تكون قبلت والرد ضاع. لو أصدرت رقم جديد يبقى عندك مستندين لنفس البيعة. ✅ unknown حالة مستقلة، والـ retry بيبعت نفس الـ bytes، زي ما شفت في الدرس 32.

❌ One date, no milestone, no source 
// تاريخ من غير معنى ولا مصدر
const UAE_DEADLINE = "2027-03-31";
✅ Milestones as data, with a source 
// كل تاريخ معاه معناه ومصدره
{ id: "phase-2", appointAspBy: "2027-03-31",
  goLive: "2027-07-01", source: "secondary: KPMG 2026-07-22" }
بالعامية

❌ تاريخ واحد من غير ما تقول بتاع إيه هو نفس اللبس اللي بيخلّي الناس تفتكر إن 31 مارس هو الـ go-live. ✅ كل milestone ليه اسم ومصدر، ولما القرار يتعدّل تغيّر سطر data وتعرف كان جاي منين.

Cheat sheet · الخلاصة

  • Corners: C1 seller, C2 seller's provider, C3 buyer's provider, C4 buyer, C5 tax authority.
  • PINT AE identifier: urn:peppol:pint:billing-1@ae-1; TIN scheme 0235; flags in cbc:ProfileExecutionID; cbc:UUID required.
  • In the UAE you must appoint an accredited ASP; a direct connection isn't the model.
  • Revenue ≥ AED 50M: appoint by 30 Oct 2026, live 1 Jan 2027 (Decision 66 of 2026).
  • Below that: appoint by 31 Mar 2027, live 1 Jul 2027. Government: 31 Mar and 1 Oct 2027 (KPMG). 31 March is the appointment, not go-live.
  • This Odoo 20 checkout has no PINT AE module; Enterprise status is unknown.
  • Build versus buy: hard gates first, then multi-year cost including recurring regulatory change.
  • Connectivity is a commodity (inference); reconciliation, failure handling and signing are the real engineering.
  • One port with five verbs; one state machine; results accepted, pending, rejected, unknown.
  • Persist signed bytes before the first send; unknown resends the same bytes.
  • Operate from data: calendar, schema versions, per-country thresholds, per-country retention.
  • A scheduled canary on saved samples catches a rule change before customers do.
