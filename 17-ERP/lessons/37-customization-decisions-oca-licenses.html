Why this matters · ليه ده مهم

English

An ERP outlives the people who customized it. Every line you add is paid for again at each upgrade, by someone who may never have met you. Developers are rewarded for saying yes, so the senior skill here is deciding what not to build, and building the rest so the next release can still land. This lesson gives you a decision ladder, a real demonstration of why an override beats a fork, a dependency check you can put in CI, a way to judge community modules, and enough licence literacy to avoid an expensive surprise. Exit test question 10 is answered in Part 1.

بالعامية

الـ ERP بيعيش أطول من الناس اللي عملوله customization. كل سطر بتضيفه بيتدفع تمنه تاني مع كل upgrade، وممكن اللي يدفعه واحد عمره ما قابلك. المبرمج بياخد تقدير لما يقول "حاضر"، فالمهارة السنيور هنا إنك تقرر إيه اللي مش هيتبني، وتبني الباقي بطريقة تخلي الإصدار الجاي يعرف ينزل. الدرس ده بيديك سلم قرار، وتجربة حقيقية توضح ليه الـ override أحسن من الـ fork، وفحص dependencies تحطه في CI، وطريقة تقيّم بيها الـ community modules، وفهم كفاية للرخص عشان متتفاجئش بمصيبة غالية. سؤال 10 في اختبار الخروج إجابته في الجزء 1.

Part 1 — When to say no 🔴 Advancedالجزء 1 — إمتى تقول لأ

English

Exit test question 10 asks: a client wants a big customization, when do you say no, and how? "No" is rarely the first answer. The first answer is a question: what is the lowest rung on this ladder that meets the real need? The rungs run from cheapest to most expensive at upgrade time:

  1. Change the process. The company adapts to the standard flow. No software change.
  2. Configure. A setting that already exists. Odoo's po_double_validation on res.company already gives a second approval above an amount.
  3. Use an existing module. Something in core or OCA already does it.
  4. Extend. A custom module using _inherit, inheriting views, adding fields.
  5. Integrate. Build it outside and talk through the JSON-2 API. The upgrade only touches the contract.
  6. Modify. Edit or replace core behaviour. Effectively a fork.

Then put numbers on it. Four inputs matter: request size (build days), upgrade exposure (rework days per upgrade, set by the rung), business value, and frequency. Build cost is the part everyone counts, and the upgrade tax is the part that decides. The function below compares five years of value with five years of cost. A legal requirement always proceeds, on the lowest rung that satisfies it, and a modification is refused whatever its ratio, because the ratio can't price the risk of owning core behaviour. The day rate, rework days and minutes are illustrative: replace them with your own.

// السلم: كل درجة أغلى من اللي قبلها عند الـ upgrade
const LADDER = ["process", "configure", "existing-module", "extend", "integrate", "modify"] as const;
type Rung = (typeof LADDER)[number];

// الأرقام دي افتراضية: يوم شغل بالجنيه، وأيام إعادة الشغل في كل upgrade
const DAY_RATE_EGP = 6_000;
const UPGRADES_IN_5_YEARS = 4;
const REWORK_DAYS_PER_UPGRADE: Record<Rung, number> = {
  process: 0, configure: 0.25, "existing-module": 1, extend: 3, integrate: 2, modify: 15,
};

interface ChangeRequest {
  title: string;
  lowestRung: Rung;
  buildDays: number;
  timesPerMonth: number;
  minutesSavedEach: number;
  // قيمة تانية غير الوقت: غرامة أو خسارة بتتمنع في السنة
  otherValueEgpPerYear: number;
  legalRequirement?: boolean;
}

const COST_PER_MINUTE_EGP = 2.5;

function assess(r: ChangeRequest) {
  const yearlyTime = r.timesPerMonth * 12 * r.minutesSavedEach * COST_PER_MINUTE_EGP;
  const value5y = (yearlyTime + r.otherValueEgpPerYear) * 5;
  const build = r.buildDays * DAY_RATE_EGP;
  const upgradeTax = REWORK_DAYS_PER_UPGRADE[r.lowestRung] * UPGRADES_IN_5_YEARS * DAY_RATE_EGP;
  const cost5y = build + upgradeTax;
  const ratio = cost5y === 0 ? Infinity : value5y / cost5y;

  // القرار: الإلزام القانوني بيتعمل، بس برضه على أرخص درجة ممكنة
  let verdict: "do it" | "push back" | "say no";
  if (r.legalRequirement) verdict = "do it";
  else if (r.lowestRung === "modify") verdict = "say no";
  else if (ratio >= 2) verdict = "do it";
  else if (ratio >= 1) verdict = "push back";
  else verdict = "say no";
  return { title: r.title, rung: r.lowestRung, value5y, cost5y, ratio, verdict };
}

const requests: ChangeRequest[] = [
  { title: "Skip delivery step for services", lowestRung: "process", buildDays: 0.5, timesPerMonth: 300, minutesSavedEach: 1, otherValueEgpPerYear: 0 },
  { title: "CFO approves POs over EGP 500k", lowestRung: "configure", buildDays: 0.5, timesPerMonth: 20, minutesSavedEach: 5, otherValueEgpPerYear: 60_000 },
  { title: "Delivery-note column on invoice PDF", lowestRung: "extend", buildDays: 2, timesPerMonth: 400, minutesSavedEach: 0.5, otherValueEgpPerYear: 12_000 },
  { title: "Courier labels from carrier API", lowestRung: "integrate", buildDays: 10, timesPerMonth: 4_000, minutesSavedEach: 2, otherValueEgpPerYear: 0 },
  { title: "Rewrite stock reservation in core", lowestRung: "modify", buildDays: 30, timesPerMonth: 2_000, minutesSavedEach: 1, otherValueEgpPerYear: 100_000 },
];

for (const a of requests.map(assess)) {
  const ratio = a.ratio === Infinity ? "inf" : a.ratio.toFixed(1);
  console.log(`${a.verdict.padEnd(9)} ${a.rung.padEnd(10)} value=${String(a.value5y).padStart(9)} cost=${String(a.cost5y).padStart(7)} x${ratio.padStart(5)}  ${a.title}`);
}

بالعامية

سؤال 10 في اختبار الخروج: عميل طالب customization كبيرة، تقول لأ إمتى وإزاي؟ "لأ" نادرًا ما بتبقى أول رد. أول رد سؤال: إيه أقل درجة في السلم تحل الاحتياج الحقيقي؟ الدرجات من الأرخص للأغلى عند الـ upgrade:

  1. غيّر الـ process. الشركة تمشي على الـ flow القياسي، ومفيش تغيير في السوفتوير.
  2. Configure. setting موجود أصلًا. po_double_validation على res.company في Odoo بيدّيك موافقة تانية فوق مبلغ معين.
  3. استخدم module موجود. حاجة في الـ core أو OCA بتعمل المطلوب.
  4. Extend. custom module بـ _inherit و view inheritance و fields جديدة.
  5. Integrate. ابنيها برّه واتكلم عن طريق الـ JSON-2 API. الـ upgrade بيلمس الـ contract بس.
  6. Modify. تعدّل أو تستبدل سلوك الـ core، وده عمليًا fork.

وبعدين حط أرقام. 4 مدخلات: حجم الطلب (أيام الـ build)، الـ upgrade exposure (أيام إعادة الشغل في كل upgrade وبتتحدد بالدرجة)، القيمة للـ business، والتكرار. تكلفة الـ build الكل بيحسبها، لكن الـ upgrade tax هو اللي بيحسم. الـ function بتقارن قيمة 5 سنين بتكلفة 5 سنين. الإلزام القانوني بيتعمل دايمًا بس على أقل درجة تكفي، والـ modify مرفوض مهما كانت النسبة، لأن النسبة مش بتحسب خطر إنك تبقى مالك سلوك الـ core. سعر اليوم وأيام إعادة الشغل والدقايق كلها أرقام للتوضيح: حط أرقامك إنت.

فين هستخدمه في شغلي؟ الـ product manager قالك "عايزين نعيد كتابة الـ checkout عشان عميل واحد طلب". نفس السلم شغال في أي codebase: feature flag موجود؟ config؟ library؟ plugin؟ service برّه؟ ولا تعديل في قلب الـ payment flow؟ احسب الـ build + تكلفة صيانته كل release، وحطها في الـ ticket قبل الـ sprint planning. الغلطة الشائعة إنك تحسب أيام الـ build بس.

Part 2 — Extension against modification 🔴 Advancedالجزء 2 — الـ extension قصاد الـ modification

English

Extension leaves the vendor's code alone and adds to it through a supported mechanism. In Odoo that's _inherit and super(), taught in lesson 16. Modification edits the vendor's code or a copy of it. The question is what happens at the next release, so I ran it on real Odoo 20.

The setup: lab_core is a small stand-in for a core module, with margin arithmetic modelled on the real sale_margin. It's a separate module because the real source stays untouched, and get_module_path returns the first match on addons_path, where core comes first in this lab. lab_core_vip adds a handling fee through _inherit. lab_core_fork is an edited copy holding the same fee inline. Then a simulated next release of lab_core makes two changes: _line_cost gains a currency_rate argument, and a bug is fixed so the discount finally counts.

The result is the point of the lesson. The extension fails loudly: a TypeError with a stack trace naming the method, fixed in two lines, and after that it inherits the bug fix for free. The fork fails silently: its test stays green and it reports a margin overstated by EGP 100 on one line, for as long as nobody compares it with upstream. To be fair to the fork, it does go loud on any path where a newly upgraded caller uses the new signature. But that only shows up on that path, in production, while the wrong number needs no caller at all.

Clean core is SAP's name for the same discipline. SAP's FAQ defines it as "a system or a landscape of systems that is as close to standard as possible, while running cloud-compliant extensions and integrations", and ABAP Cloud enforces it by allowing only released objects and public APIs. Odoo has no such contract. _line_cost here is private, and _inherit will happily let you depend on it. So an Odoo override is safer than a fork, not safe: prefer public hooks, keep overrides thin, and always call super().

from odoo import api, fields, models


class MarginLine(models.Model):

    _description = 'Margin line'

from odoo import models

HANDLING_FEE = 5.0


class MarginLine(models.Model):
    _inherit = 'lab.margin.line'

    # الإضافة: بنزوّد الـ fee فوق حساب الـ core ومبنلمسش ملف الـ core
    def _line_cost(self):
        return super()._line_cost() + HANDLING_FEE

    def _line_cost(self):
        self.ensure_one()
        # التعديل جوه نسخة الـ core نفسها: الـ fee اتكتب هنا على طول
        return self.unit_cost * self.qty + 5.0

    @api.depends('qty', 'price_unit', 'discount', 'unit_cost')
    def _compute_margin(self):
        for line in self:
            line.margin = line.qty * line.price_unit - line._line_cost()

    # التغيير 1 في الإصدار الجديد: الـ signature بقت بتاخد currency_rate
    def _line_cost(self, currency_rate):
        self.ensure_one()
        return self.unit_cost * self.qty * currency_rate

    @api.depends('qty', 'price_unit', 'discount', 'unit_cost')
    def _compute_margin(self):
        for line in self:
            # التغيير 2: الـ bug اتصلح والـ discount بقى داخل في الحساب
            subtotal = line.qty * line.price_unit * (1 - line.discount / 100)
            line.margin = subtotal - line._line_cost(1.0)

    # التصليح كله سطرين: الـ signature الجديدة وتمرير الـ argument لـ super
    def _line_cost(self, currency_rate):
        return super()._line_cost(currency_rate) + HANDLING_FEE

بالعامية

الـ extension بيسيب كود الـ vendor في حاله ويضيف عليه بطريقة مدعومة، وفي Odoo ده _inherit وsuper() اللي اتشرحوا في الدرس 16. الـ modification بيعدّل كود الـ vendor أو نسخة منه. السؤال هو إيه اللي بيحصل في الإصدار الجاي، فشغّلتها فعلًا على Odoo 20.

التجهيز: lab_core module صغير بيلعب دور الـ core، وحسبة الـ margin فيه مأخوذة من sale_margin الحقيقي. عملته module منفصل عشان الـ source الأصلي ميتلمسش، ولأن get_module_path بيرجّع أول match في addons_path والـ core جاي الأول في الـ lab. lab_core_vip بيضيف handling fee بـ _inherit. lab_core_fork نسخة متعدلة فيها نفس الـ fee جوه الكود. وبعدين إصدار جديد متخيَّل من lab_core عمل تغييرين: _line_cost بقت بتاخد currency_rate، وbug اتصلح فالـ discount بقى محسوب.

النتيجة هي زبدة الدرس. الـ extension وقع بصوت عالي: TypeError وstack trace فيه اسم الـ method، اتصلح في سطرين، وبعدها أخد تصليح الـ bug ببلاش. الـ fork وقع في صمت: الـ test بتاعه فضل أخضر وطلّع margin زيادة 100 جنيه في السطر الواحد، ولحد ما حد يقارنه بالأصل. وعشان نبقى منصفين، الـ fork بيعلّي صوته برضه في أي مسار فيه caller متحدّث بينادي الـ signature الجديدة. بس ده بيظهر على المسار ده بس، في production، بينما الرقم الغلط مش محتاج أي caller.

الـ clean core هو اسم SAP لنفس الانضباط. الـ FAQ بتاع SAP بيعرّفه كده: "a system or a landscape of systems that is as close to standard as possible, while running cloud-compliant extensions and integrations"، يعني نظام قريب من الـ standard على قد ما يقدر وشغال بـ extensions و integrations مناسبة للـ cloud. و ABAP Cloud بيفرضه بإنه مش بيسمح غير بالـ released objects والـ public APIs. Odoo معندوش عقد زي ده: _line_cost هنا private و_inherit هيسيبك تعتمد عليها عادي. فالـ override في Odoo أأمن من الـ fork، مش آمن: فضّل الـ public hooks، وخلّي الـ overrides رفيعة، ونادي super() دايمًا.

فين هستخدمه في شغلي؟ نفس الحكاية مع npm: patch-package أو نسخة متعدلة من library في الـ repo ده fork. الـ wrapper حوالين الـ library ده extension. لو الـ library غيرت signature، الـ wrapper هيقع في tsc أو الـ CI. الـ fork هيفضل شغال وناقصه security patch ومحدش واخد باله. في الـ code review اسأل: "لو الـ dependency دي طلعت major بكرة، هنعرف إزاي؟" والغلطة الشائعة override من غير super()، وده fork متنكر.
Trade-off A loud failure costs you a broken build on upgrade day, and that's the feature. Sometimes modification really is the only option, such as an urgent security patch before upstream ships it. Then keep it as a small patch file with a link to the upstream issue and a removal condition, never as a silent edit.
الوقوع بصوت عالي تمنه build مكسور يوم الـ upgrade، وده بالظبط المطلوب. أحيانًا الـ modification بيبقى الحل الوحيد فعلًا، زي security patch مستعجل قبل ما الـ upstream ينزله. ساعتها خليه patch file صغير فيه لينك للـ issue في الـ upstream وشرط إزالته، ومتعملوش تعديل صامت أبدًا.

Part 3 — Boundaries and dependency direction 🔴 Advancedالجزء 3 — الـ boundaries واتجاه الـ dependencies

English

Three rules keep a custom addons folder upgradable. One module per business capability, so you can remove or replace one without surgery. depends points toward more stable modules, the same idea as who depends on whom in section 11. And when two capabilities have to meet, a thin bridge module joins them so neither one knows about the other.

Odoo's own source does this. sale doesn't depend on stock, and stock doesn't depend on sale. sale_stock depends on ['sale', 'stock_account'] with auto_install: True, so it appears only when both sides are present. The script below reads every __manifest__.py, builds the graph, counts fan-in, and exits non-zero on a cycle or a forbidden edge. This is a fitness function, as taught in section 11, aimed at Odoo manifests.

Run on the real source it reports 663 modules and 1,385 edges, no cycles, and account at the top with a fan-in of 158. Fan-in is a warning label: 158 modules break if account changes, so it has to be stable and you should hesitate before overriding its internals. The regex parser is a shortcut, since Odoo itself reads manifests with ast.literal_eval. I checked it against ast.literal_eval on all 663 manifests and found no differences.

function parseDepends(source: string): string[] {
  const noComments = source.replace(/^\s*#.*$/gm, "");
  const match = noComments.match(/['"]depends['"]\s*:\s*\[([\s\S]*?)\]/);
  if (!match) return [];
  return [...match[1].matchAll(/['"]([\w.-]+)['"]/g)].map((m) => m[1]);
}

for (const deps of graph.values()) for (const d of deps) fanIn.set(d, (fanIn.get(d) ?? 0) + 1);

// الـ cycle: DFS بثلاث ألوان، والرمادي معناه لسه جوه الـ stack
function findCycles(): string[][] {
  const color = new Map<string, "grey" | "black">();
  const cycles: string[][] = [];
  const visit = (node: string, stack: string[]) => {
    color.set(node, "grey");
    for (const next of graph.get(node) ?? []) {
      if (color.get(next) === "grey") cycles.push([...stack.slice(stack.indexOf(next)), node, next]);
      else if (!color.has(next)) visit(next, [...stack, node]);
    }
    color.set(node, "black");
  };
  for (const node of graph.keys()) if (!color.has(node)) visit(node, []);
  return cycles;
}

Part 4 — Evaluating OCA 🔴 Advancedالجزء 4 — إزاي تقيّم OCA

English

The Odoo Community Association maintains hundreds of modules on GitHub, organized by repository (OCA/queue, OCA/account-invoicing) with one branch per Odoo version. Rung 3 of the ladder usually means OCA. Treat a module as a dependency you'll inherit, and check: a release branch for your exact version, development_status, maintainers, tests, CI, open issues, and the licence.

Worked example: queue_job, read on GitHub on 2026-11-11 and not installed. It needs --workers greater than 1, which can't run on this Windows machine anyway. The 20.0 branch exists and its manifest says version 20.0.1.0.0, "development_status": "Mature", "maintainers": ["guewen", "sbidoul"], "license": "LGPL-3", and external Python dependencies requests and openupgradelib. There are 12 test files, the latest tests and pre-commit workflow runs on the branch succeeded, and the repo has 18 open issues and 49 open pull requests.

Three details only show up if you read closely. The repository's GitHub badge says AGPL-3.0 while this module says LGPL-3: OCA licences are per module, so the manifest is what counts. The most recent commit is a Weblate translation; the last real merge was PR #999 on 2026-10-29, so look at merges, not bot commits. }

interface Mod { license: string; depends: string[]; }

function field(source: string, key: string): string | undefined {

Part 6 — The customization register 🟡 Intermediateالجزء 6 — سجل الـ customizations

English

A customization register is a living document with one row per customization: what it is, its owner, the reason, its upgrade risk, and its retirement condition ("remove when core supports cost per lot"). The last column is the valuable one, because customizations are easy to add and nobody ever schedules their removal. It feeds the upgrade assessment from lesson 36.

Don't write the first version by hand. This script uses Python's ast to walk a module's classes, finds _inherit targets, lists fields and methods, checks whether each method calls super(), and reads inherited views. Risk comes from the code: a new field is low, a super() override or view inheritance is medium, an xpath with replace is high. A method without super() is labelled new-or-high, since static analysis can't tell a brand-new helper from an override that swallows core. A human checks those. The merge step keeps what people typed, so running it again doesn't wipe your work.

import ast
import json
import sys
import xml.etree.ElementTree as ET
from pathlib import Path

# الاستخدام: python customization_register.py module_dir register.json
module_dir, register_path = Path(sys.argv[1]), Path(sys.argv[2])
module = module_dir.name
HUMAN_FIELDS = ('owner', 'reason', 'retire_when')


def class_inherit(node):
    # القراءة: بنطلّع قيمة _inherit لو الـ class بيعدّل model موجود
    names = {}
    for stmt in node.body:
        if isinstance(stmt, ast.Assign) and isinstance(stmt.targets[0], ast.Name):
            if stmt.targets[0].id in ('_inherit', '_name'):
                names[stmt.targets[0].id] = ast.literal_eval(stmt.value)
    inherit = names.get('_inherit')
    if isinstance(inherit, list):
        inherit = inherit[0] if len(inherit) == 1 else None
    return inherit if inherit and names.get('_name', inherit) == inherit else None


def calls_super(fn):
    for sub in ast.walk(fn):
        if isinstance(sub, ast.Call) and isinstance(sub.func, ast.Name) and sub.func.id == 'super':
            return True
    return False


def is_field(stmt):
    return (
        isinstance(stmt, ast.Assign)
        and isinstance(stmt.value, ast.Call)
        and isinstance(stmt.value.func, ast.Attribute)
        and isinstance(stmt.value.func.value, ast.Name)
        and stmt.value.func.value.id == 'fields'
    )


rows = []
for py in sorted((module_dir / 'models').glob('*.py')):
    tree = ast.parse(py.read_text(encoding='utf-8'))
    for node in [n for n in tree.body if isinstance(n, ast.ClassDef)]:
        target = class_inherit(node)
        if not target:
            continue
        for stmt in node.body:
            if is_field(stmt):
                rows.append({'key': f'field:{target}.{stmt.targets[0].id}', 'risk': 'low'})
            elif isinstance(stmt, ast.FunctionDef):
                # الخطر: override من غير super بيبلع منطق الـ core كله
                risk = 'medium' if calls_super(stmt) else 'new-or-high'
                rows.append({'key': f'method:{target}.{stmt.name}', 'risk': risk})

for xml in sorted((module_dir / 'views').glob('*.xml')) if (module_dir / 'views').exists() else []:
    for record in ET.parse(xml).getroot().iter('record'):
        inherit = record.find("field[@name='inherit_id']")
        if inherit is None:
            continue
        positions = [x.get('position', 'inside') for x in record.iter('xpath')]
        risk = 'high' if 'replace' in positions else 'medium'
        rows.append({'key': f"view:{inherit.get('ref')}<-{record.get('id')}", 'risk': risk})

# الدمج: الحقول اللي البني آدم كتبها متتمسحش لما السكريبت يشتغل تاني
old = {}
if register_path.exists():
    old = {r['key']: r for r in json.loads(register_path.read_text(encoding='utf-8'))}
for row in rows:
    row['module'] = module
    for name in HUMAN_FIELDS:
        row[name] = old.get(row['key'], {}).get(name, 'TODO')
gone = sorted(set(old) - {r['key'] for r in rows})
register_path.write_text(json.dumps(rows, indent=1), encoding='utf-8')

todo = sum(1 for r in rows if 'TODO' in (r['owner'], r['reason'], r['retire_when']))
print(f'{module}: {len(rows)} customizations, {todo} still TODO, {len(gone)} gone since last run')
for r in rows:
    print(f"  {r['risk']:<12} {r['owner']:<10} {r['key']}")

بالعامية

سجل الـ customizations مستند حي، فيه سطر لكل customization: هو إيه، مين المسؤول، السبب، خطره عند الـ upgrade، وشرط إزالته ("اشيله لما الـ core يدعم cost لكل lot"). العمود الأخير هو الأهم، لأن إضافة الـ customizations سهلة ومحدش بيحدد ميعاد لشيلها. وده بيغذي تقييم الـ upgrade من الدرس 36.

متكتبش أول نسخة بإيدك. السكريبت بيستخدم ast بتاع Python يلف على classes الـ module، يلاقي الـ _inherit، يطلّع الـ fields والـ methods، يشوف كل method بتنادي super() ولا لأ، ويقرا الـ views الموروثة. الخطر طالع من الكود: field جديد low، و override بـ super() أو view inheritance medium، و xpath فيه replace high. الـ method من غير super() بتتعلّم new-or-high، لأن التحليل الساكن مش هيعرف يفرّق بين helper جديدة و override بيبلع الـ core، فبني آدم يبص عليها. وخطوة الـ merge بتحافظ على اللي الناس كتبته، فالتشغيل التاني مش بيمسح شغلك.

فين هستخدمه في شغلي؟ في Node، نفس الفكرة لـ patch-package والـ forks والـ feature flags القديمة: ملف فيه كل flag ومين صاحبه وشرط شيله، وCI بيفشل لو flag عدّى تاريخه. الغلطة الشائعة register مكتوب بإيد مرة واحدة ومحدش بيحدّثه؛ توليده من الكود هو اللي بيخليه صادق.
Trade-off It's bureaucracy until the first upgrade. Filling owner, reason and retirement condition costs maybe ten minutes a row and pays nothing for a year or two. Then the upgrade comes, and it's the difference between "this field has an owner who says delete it" and three days of archaeology. Keep it generated and small, or it dies.
ده بيروقراطية لحد أول upgrade. ملء الـ owner والسبب وشرط الإزالة بياخد يمكن 10 دقايق للسطر ومبيرجعش بفايدة سنة أو اتنين. وبعدين الـ upgrade بييجي، ويبقى الفرق بين "الـ field ده ليه صاحب بيقول امسحه" و3 أيام تنقيب في الكود. خليه متولّد وصغير، وإلا هيموت.

Solution · الحل 
import { existsSync, readdirSync, readFileSync } from "node:fs";
import { join } from "node:path";

// الاستخدام: ⁦node bridges.ts folder1 folder2 ⁩...
const bridges: string[] = [];
for (const root of process.argv.slice(2)) {
  for (const name of readdirSync(root)) {
    const file = join(root, name, "__manifest__.py");
    if (!existsSync(file)) continue;
    const source = readFileSync(file, "utf8").replace(/^\s*#.*$/gm, "");
    // الانتباه: القيمة ممكن تبقى True أو list فيها أسماء modules
    const autoInstall = /['"]auto_install['"]\s*:\s*(True|\[\s*['"])/.test(source);
    const body = source.match(/['"]depends['"]\s*:\s*\[([\s\S]*?)\]/)?.[1] ?? "";
    const depends = [...body.matchAll(/['"]([\w.-]+)['"]/g)].map((m) => m[1]);
    // الجسر: بيتنزل لوحده وبيربط موديولين أو أكتر
    if (autoInstall && depends.length >= 2) bridges.push(`${name} <- ${depends.join(" + ")}`);
  }
}
console.log(`bridges: ${bridges.length}`);

Cheat sheet · الخلاصة

  • Ladder: process → configure → existing module → extend → integrate → modify. Stop at the first rung that meets the need.
  • Cost = build + rework per upgrade × upgrades. The upgrade tax usually decides.
  • Say no to the implementation, not the problem: number, recommendation, options, success measure, decision date.
  • An override fails loudly and fixably; a fork fails silently.
  • Odoo overrides are safer than forks, not safe: private methods have no stability promise. Always call super().
  • Clean core: as close to standard as possible, extending only through released interfaces.
  • One module per capability; depends points to the more stable; thin auto_install bridges.
  • Check manifests in CI: fail on cycles and forbidden edges.
  • OCA: right branch, status, maintainers, tests, CI, issues. Licence per module, from the manifest.
  • LGPL: duties come with conveying. OEEL: subscription needed. OPL: no copying or redistribution. AGPL: remote users get the source of your modified version.
  • Register: owner, reason, risk, retirement condition; generated from code, human fields preserved.
بالعامية
  • السلم: process ← configure ← module موجود ← extend ← integrate ← modify. اقف عند أول درجة تحل الاحتياج.
  • التكلفة = الـ build + إعادة الشغل في كل upgrade × عدد الـ upgrades. والـ upgrade tax غالبًا هو اللي بيحسم.
  • قول لأ للتنفيذ مش للمشكلة: رقم، توصية، بدايل، معيار نجاح، وتاريخ قرار.
  • الـ override بيقع بصوت عالي وبيتصلح، والـ fork بيقع في صمت.
  • الـ overrides في Odoo أأمن من الـ forks مش آمنة: الـ private methods مفيهاش وعد بالثبات. ونادي super() دايمًا.
  • الـ clean core: قريب من الـ standard على قد ما تقدر، والـ extension عن طريق الـ released interfaces بس.
  • module لكل capability، وdepends ناحية الأكتر استقرارًا، وجسور رفيعة بـ auto_install.
  • افحص الـ manifests في الـ CI: افشل عند الـ cycles والـ edges الممنوعة.
  • OCA: الـ branch الصح، الـ status، الـ maintainers، الـ tests، الـ CI، الـ issues. والرخصة لكل module من الـ manifest.
  • LGPL: الالتزامات مع الـ conveying. OEEL: لازم subscription. OPL: ممنوع النسخ وإعادة التوزيع. AGPL: المستخدمين عن بعد ليهم source نسختك المعدلة.
  • الـ register: owner وسبب وخطر وشرط إزالة، متولّد من الكود والحقول البشرية محفوظة.
