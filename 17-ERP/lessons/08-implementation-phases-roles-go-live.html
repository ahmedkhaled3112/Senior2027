Why this matters · ليه ده مهم

English

An ERP implementation is not a software release. It is a change to how a company runs, with a date after which the old system stops. Most of the money goes to services and most of the risk sits in decisions and data rather than in code. As a developer you will be handed a spec by someone with a job title you don't know yet, asked to estimate something that should have been a setting, and woken up on a cutover weekend. This lesson gives you the vocabulary, the cost logic behind "just customize it", and a cutover you have rehearsed by hand.

بالعامية

تنفيذ ERP مش release عادي. ده تغيير في طريقة شغل شركة كاملة، وليه تاريخ السيستم القديم بيقف بعده. أغلب الفلوس بتروح services وأغلب المخاطرة في القرارات والـ data مش في الكود. وإنت كـ developer هيجيلك spec من حد بـ job title لسه متعرفوش، وهيتطلب منك تقدّر حاجة كان المفروض تبقى setting، وهتصحى في weekend الـ cutover. الدرس ده بيديك المصطلحات، ومنطق التكلفة ورا جملة "اعملها customization وخلاص"، وcutover عملت له rehearsal بإيدك.

Part 1 — The phases and their gates 🟢 Basicالجزء 1 — المراحل والبوابات بتاعتها

English

Every vendor names them differently, but the arc is the same: discovery (what is the business and what is in scope), fit-gap (compare each requirement to the standard product), configuration (set up the standard), customization (build the gaps worth building), data migration (map, clean, load, reconcile), UAT (user acceptance testing, by the people who will use it), go-live (the cutover), and hypercare (a period of heightened support before handing over to normal support).

What makes these phases rather than a to-do list is that each one ends in a written output someone signed. A signed fit-gap matrix is what stops a request in month 7 from being "obviously in scope". Treat each phase as a gate, like a required CI check: no artifact, no advance, and the signature has to come from the right role. Changing an early decision invalidates what was built on it, so re-opening a phase clears later sign-offs.

A note on numbers: how long hypercare usually lasts was not found in any reliable source. SAP and Microsoft name the concept without giving a duration, so agree it per project instead of quoting a norm. For overall duration, Panorama's 2026 survey reports a median of 9 months, but its sample has a median revenue of about $200M and we only have it second-hand, so it says little about a 30-person distributor in Cairo.

type Role = "sponsor" | "pm" | "functional" | "developer" | "key_user";
type Artifact = { name: string; approver: Role };
type Phase = { name: string; exit: Artifact[] };

// كل phase ليها مخرجات مكتوبة، ومين اللي لازم يوقّع عليها
const PHASES: Phase[] = [
  { name: "discovery", exit: [{ name: "scope-document", approver: "sponsor" }] },
  { name: "fit-gap", exit: [{ name: "fit-gap-matrix", approver: "key_user" }] },
  { name: "configuration", exit: [{ name: "configuration-workbook", approver: "functional" }] },
  { name: "customization", exit: [{ name: "technical-design", approver: "developer" }, { name: "customization-register", approver: "pm" }] },
  { name: "data-migration", exit: [{ name: "reconciliation-report", approver: "key_user" }] },
  { name: "uat", exit: [{ name: "uat-sign-off", approver: "key_user" }] },
  { name: "go-live", exit: [{ name: "go-no-go-minutes", approver: "sponsor" }] },
  { name: "hypercare", exit: [{ name: "handover-to-support", approver: "pm" }] },
];

class GateRefused extends Error {
  override name = "GateRefused";
}

class Project {
  private index = 0;
  private signed = new Map<string, Role>();

  get phase(): string {
    return PHASES[this.index]!.name;
  }

  sign(artifact: string, by: Role): void {
    this.signed.set(artifact, by);
  }

  // البوابة: مفيش مرحلة جديدة من غير المخرج، والتوقيع لازم يكون من الدور الصح
  advance(): void {
    const missing = PHASES[this.index]!.exit.filter((a) => this.signed.get(a.name) !== a.approver);
    if (missing.length > 0) {
      const list = missing.map((a) => `${a.name} (needs ${a.approver})`).join(", ");
      throw new GateRefused(`${this.phase}: missing ${list}`);
    }
    this.index += 1;
  }

  // تغيير الـ scope بيرجّعك لورا وبيلغي التوقيعات اللي اتبنت عليه
  reopen(phase: string, reason: string): void {
    const target = PHASES.findIndex((p) => p.name === phase);
    for (const p of PHASES.slice(target)) for (const a of p.exit) this.signed.delete(a.name);
    this.index = target;
    console.log(`reopened at ${phase}: ${reason}`);
  }
}

const attempt = () => {

    console.log(`advanced to ${p.phase}`);
  } catch (e) {
    console.log(`${(e as Error).name}: ${(e as Error).message}`);
  }
};

بالعامية

كل vendor بيسميهم بشكل مختلف بس الشكل واحد: discovery (الشركة بتعمل إيه وإيه اللي جوه الـ scope)، fit-gap (كل requirement قصاد المنتج الـ standard)، configuration (تظبيط الـ standard)، customization (بناء الفجوات اللي تستاهل)، data migration (mapping وتنضيف وتحميل وreconcile)، UAT (اختبار بإيد الناس اللي هتستخدمه)، go-live (الـ cutover)، وhypercare (فترة دعم مكثف قبل التسليم للدعم العادي).

اللي بيخليهم مراحل مش to-do list إن كل واحدة بتخلص بـ مخرج مكتوب حد وقّع عليه. الـ fit-gap matrix الموقعة هي اللي بتوقف طلب في الشهر السابع من إنه يبقى "أكيد جوه الـ scope". اتعامل مع كل مرحلة كبوابة، زي required check في الـ CI: مفيش مخرج يبقى مفيش تقدم، والتوقيع لازم من الدور الصح. وتغيير قرار بدري بيلغي اللي اتبنى عليه، فلما تفتح مرحلة قديمة التوقيعات اللي بعدها بتتمسح.

ملاحظة على الأرقام: مدة الـ hypercare المعتادة ملقيناهاش في أي مصدر موثوق. SAP وMicrosoft بيذكروا الفكرة من غير مدة، فاتفق عليها في كل مشروع ومتقولش رقم كأنه معيار. وعن مدة المشروع كله، استبيان Panorama 2026 بيقول median 9 شهور، بس العينة median الإيراد بتاعها حوالي 200 مليون دولار والرقم وصلنا من مصدر تاني مش من التقرير نفسه، فمش بيقول حاجة كتير عن موزع في القاهرة عنده 30 موظف.

فين هستخدمه في شغلي؟ لو بتشتغل مع عميل على feature كبيرة في SaaS وكل أسبوع الـ requirements بتتغير: اعمل نسخة صغيرة من ده. وثيقة scope موقعة، وكل تغيير بعدها change request يرجّعك لبوابة ويعيد التقدير. الغلطة الشائعة إنك تكمل بناء فوق قرار اتغير، وتكتشف في الـ UAT إن نص الشغل مبني على افتراض قديم.

Part 2 — Configuration, customization, integration 🟢 Basicالجزء 2 — الـ configuration والـ customization والـ integration

English

In developer terms: configuration is a feature flag the vendor carries across upgrades. An extension is a plugin on a public API: your code, in your module, calling through super(). A modification is a patch inside node_modules that you reapply on every version. Integration is your service talking to theirs over a versioned contract, with retries, monitoring and reconciliation to run forever.

Why is that the cost order? Because cost is dominated by what recurs. Configuration is stored as data and the vendor owns its compatibility. Custom code is yours: Odoo's docs state that a database with custom modules cannot be upgraded until a version of those modules exists for the target version, and that customers maintaining their own modules must upgrade that source themselves. An integration is cheaper to upgrade than it looks if the API is stable, but it has a running cost every month even when nothing changes.

The demo below answers one business request two ways in real Odoo. "Quotations should expire after 7 days" is a setting. "Government customers get 60 days" has no setting, so it needs a new field and an override of a method whose name is an internal detail of the sale module.

An honest note on the order. The README's sequence (configuration, customization, integration) holds when customization means a clean extension. A core modification is not a step on that ladder at all: in the model below it reaches 27 days, about two and a half times the extension. No rigorous measurement of upgrade cost per customization was found, so these figures are reasoning rather than data. The Odoo 14 docs claim 60% of initial development requests are dropped after a few weeks of real use, but that is an unsourced vendor claim. A real Cairo job posting asks for the ability to tell five things apart: standard Odoo, configuration, third-party apps, integration and custom development.

// كل الأرقام هنا افتراضات بتاعتي أنا عشان نشوف الشكل، مش بيانات من مصدر
type Option = {
  name: string;
  buildDays: number;
  retestDaysPerUpgrade: number;
  breakProbability: number;
  fixDaysIfBroken: number;
  runDaysPerYear: number;
};

const ASSUMPTIONS: Option[] = [
  { name: "configuration", buildDays: 0.5, retestDaysPerUpgrade: 0.25, breakProbability: 0.02, fixDaysIfBroken: 0.5, runDaysPerYear: 0 },
  { name: "extension (_inherit)", buildDays: 4, retestDaysPerUpgrade: 1, breakProbability: 0.35, fixDaysIfBroken: 2, runDaysPerYear: 0.5 },
  { name: "integration", buildDays: 15, retestDaysPerUpgrade: 2, breakProbability: 0.2, fixDaysIfBroken: 4, runDaysPerYear: 6 },
  { name: "core modification", buildDays: 3, retestDaysPerUpgrade: 3, breakProbability: 0.8, fixDaysIfBroken: 5, runDaysPerYear: 1 },
];

// تكلفة متوقعة: بناء مرة واحدة، وبعدين كل ⁦upgrade (⁩سنة تقريبًا) فيه retest واحتمال كسر
function cumulative(o: Option, upgrades: number): number {
  const perUpgrade = o.retestDaysPerUpgrade + o.breakProbability * o.fixDaysIfBroken + o.runDaysPerYear;
  return o.buildDays + upgrades * perUpgrade;
}

function table(options: Option[]): void {
  console.log("option                 build   +1 upg   +2 upg   +3 upg");
  for (const o of options) {
    const cells = [0, 1, 2, 3].map((u) => cumulative(o, u).toFixed(1).padStart(6));
    console.log(`${o.name.padEnd(22)} ${cells.join("   ")}`);
  }
}

بالعامية

بلغة المبرمجين: الـ configuration هي feature flag الـ vendor بيشيلها معاك في الـ upgrades. الـ extension هي plugin على public API: كودك في الـ module بتاعك وبيعدي على super(). الـ modification هي patch جوه node_modules بتعيد تطبيقها كل version. والـ integration هي الـ service بتاعك بيكلم بتاعهم بـ contract له version، ومعاه retries وmonitoring وreconciliation هتفضل تشغّلهم على طول.

ليه ده ترتيب التكلفة؟ لأن التكلفة بيسيطر عليها اللي بيتكرر. الـ configuration متخزنة كـ data والـ vendor مسؤول عن توافقها. الكود الـ custom بتاعك إنت: docs بتاعة Odoo بتقول إن database فيها custom modules متتعملهاش upgrade لحد ما يبقى فيه version من الـ modules دي للـ version الجديدة، وإن اللي ماسك الـ modules بتاعته مسؤول يعمل لها upgrade بنفسه. والـ integration ممكن تبقى أرخص في الـ upgrade من ما هي باينة لو الـ API ثابت، بس ليها تكلفة تشغيل كل شهر حتى لو مفيش حاجة اتغيرت.

الـ demo بيرد على طلب بطريقتين في Odoo الحقيقي. "الـ quotations تنتهي بعد 7 أيام" دي setting. "العملاء الحكوميين ليهم 60 يوم" مفيش ليها setting، فمحتاجة field جديد وoverride لـ method اسمها تفصيلة داخلية في الـ sale module.

أمانة في الترتيب: ترتيب الـ README (configuration ثم customization ثم integration) صح لو الـ customization معناها extension نضيفة. لكن تعديل الـ core مش درجة على السلم ده أصلًا: في الموديل بتاعي بيوصل 27 يوم، يعني حوالي مرتين ونص الـ extension. ومفيش قياس جاد لتكلفة الـ upgrade لكل customization لقيناه، فالأرقام دي تفكير مش بيانات. وOdoo 14 docs بتقول إن 60% من طلبات التطوير الأولية بتتلغي بعد كام أسبوع استخدام، بس ده ادعاء vendor من غير مصدر. وإعلان وظيفة حقيقي في القاهرة طالب صراحةً القدرة على التفرقة بين خمسة: standard وconfiguration وthird-party apps وintegration وcustom development.

فين هستخدمه في شغلي؟ لما الـ product يطلب "حالة خاصة لعميل واحد" في SaaS بتاعك: الاختيارات هي نفسها. feature flag أو setting لكل tenant (configuration)، plugin على hook رسمي (extension)، أو if (tenant === "acme") جوه الـ core (modification). التالتة أرخص النهارده وأغلى كل release. الغلطة الشائعة إنك تقدّر تكلفة البناء بس وتنسى تكلفة الـ upgrades.
Interview question (exit test 3) "What is the difference between configuration, customization and integration, and what does each cost at upgrade?" → Configuration is supported settings stored as data: the vendor carries it, and you only retest. Customization is code you own: it must be ported and retested each version, and it blocks the database upgrade until it is. If it edits core rather than extending, you also re-apply it by hand. Integration is a separate system on a contract: upgrades cost little if the API is stable, a migration if it is removed, and it costs monitoring and reconciliation every month regardless.
"إيه الفرق بين الـ configuration والـ customization والـ integration، وتكلفة كل واحد عند الـ upgrade؟" ← الـ configuration إعدادات مدعومة متخزنة كـ data: الـ vendor بيشيلها وإنت بتعيد تختبر بس. الـ customization كود بتاعك: لازم يتنقل ويتختبر كل version، وبيوقّف الـ upgrade لحد ما يخلص، ولو بيعدل في الـ core بدل ما يعمل extend هتعيد تطبيقه بإيدك كمان. الـ integration نظام منفصل على contract: الـ upgrade تكلفته قليلة لو الـ API ثابت، وmigration لو الـ API اتشال، وليها تكلفة monitoring وreconciliation كل شهر في كل الأحوال.

Part 4 — Methodologies side by side 🟢 Basicالجزء 4 — الـ methodologies جنب بعض

English

SAP Activate has six phases: Discover, Prepare, Explore, Realize, Deploy, Run. Its signature is the fit-to-standard workshop in Explore: instead of collecting requirements on a blank page, you demonstrate SAP's Best Practices and log only the deltas into a backlog, which Realize then delivers in sprints.

Microsoft Success by Design names five "methodology-agnostic" phases: Discover, Initiate, Implement, Prepare, Operate. It is explicitly an adjunct to whatever methodology the team chose, built around reviews: the Solution Blueprint Review and Go-live Readiness Review are mandatory. Microsoft recommends a hybrid: sequential at the ends, iterative in the middle.

Odoo's approach needs a caveat. Its current official methodology document could not be read during research. What we do have is the Odoo 14 documentation describing the Success Pack: phased releases, GAP analysis, an 80-20 rule, "Replace, without replicate", and standard first. A third-party write-up lists five phases and calls itself the official methodology, but that claim is unconfirmed. The Odoo column below rests on those two sources, and the whole mapping is my synthesis rather than any vendor's.

Part 5 — Why projects fail, and why no rate is reliable 🟡 Intermediateالجزء 5 — المشاريع بتفشل ليه، وليه مفيش نسبة موثوقة

English

There is no reliable ERP failure rate, because the commonly quoted numbers don't measure the same thing. Gartner's "more than 70% ... by 2027" is a forecast about initiatives that won't fully meet their original business case (we have it through TechTarget). Bain's 80% "miss their goals" has no published method (through CIO.com). Panorama's 2026 survey says more than a quarter ran over budget and almost a quarter over schedule, and Panorama sells ERP consulting (through a Rework guide). A 2018 Mint Jutras survey of 315 manufacturers and distributors found 67% rating their projects successful: self-rated, commissioned by a consultancy, and seen by us only in a search excerpt.

Run every definition over one portfolio and the point makes itself. The portfolio below is entirely invented; only the spread is the lesson.

The documented causes are mostly organisational or about readiness, and two are very familiar to engineers. National Grid (SAP, go-live November 2012, reported cost $585M, about two years of clean-up) tested only the happy path and went live as Hurricane Sandy approached. PG&E (Oracle, 2016, nearly $3M fine) had a vendor copy live data to its own network during testing, exposing it for about 70 days. Both are as reported by TechTarget. Panorama's most common cause of budget overruns was an unplanned need for extra technology, usually a fit gap found late, and its most common schedule cause was organisational resistance.

function mulberry32(seed: number): () => number {
  let a = seed;
  return () => {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

Part 6 — Go-live as a rehearsed cutover 🟡 Intermediateالجزء 6 — الـ go-live كـ cutover متدرب عليه

English

A cutover is the switch from the old system to the new one. Microsoft's implementation guide says it is often called the "cutover weekend" because it is "usually less than 48 hours", and that neither system can be used during it. That is the big difference from the deployments you know: there was no canary or gradual rollout in the materials we read. It is closer to a timed data-centre migration.

The same guide says each task needs an order, timing, an owner and a backup owner, instructions, verification and sign-off; that the plan needs a rollback; that you should avoid financial close periods and peak seasons; and that the mock cutover runs "several times" with the same data, tools, people and timing. Someone named decides go/no-go against criteria written in advance.

The rehearsal below runs for real on a throwaway Postgres: dump a rollback point, freeze the legacy database, export, transform, load, reconcile, gate, roll back. It ran three times. The first failure was planted: a date parser that silently skips another format. The second failure was not planted. On Windows, COPY TO a server file ends lines with \r\n, my split("\n") left a \r on the last column, and every status became "open\r". Row count and grand total both matched exactly. Only the per-customer open balance caught it. That is why you rehearse and why you reconcile on more than one dimension.

Each rehearsal also feeds the plan. Only volume-dependent steps scale up; people's time doesn't. And the go/no-go deadline is worked backwards from the end of the window: it has to leave enough time to roll back. The figures multiply by 250, assuming production holds ten million invoices and that growth is linear, which is an assumption rather than a measurement; the timings come from a loaded Windows machine and vary between runs. Lesson 29 runs this against Odoo.

Two cautions. default_transaction_read_only is a guardrail rather than a lock, since any session can override it for itself; a real freeze also stops the applications and closes their connections. And a dump only counts once you have restored it, as section 09 · backups explains.

    |                                                                      |
    v                                                                      v
  dump --> freeze --> export --> transform --> load --> reconcile --> GO/NO-GO --> open new
    ^                                                                  |
    |                                                                NO-GO
    |                                                                  v
    +------------------- restore dump, unfreeze legacy <---------------+

// الـ parser الساذج: أي تاريخ بشكل تاني بيتساب في صمت، وده اللي بيحصل في أول rehearsal
const parseNaive = (s: string) => {
  const m = /^(\d{2})\/(\d{2})\/(\d{4})$/.exec(s);
  return m ? `${m[3]}-${m[2]}-${m[1]}` : null;
};
const parseFixed = (s: string) => parseNaive(s) ?? (/^\d{4}-\d{2}-\d{2}$/.test(s) ? s : null);

type Plan = { n: number; parse: (s: string) => string | null; lineBreak: string | RegExp; loader: "row-by-row" | "copy" };
type Step = { name: string; seconds: number };

async function rehearse(plan: Plan): Promise<{ passed: boolean; steps: Step[] }> {
  const steps: Step[] = [];
  const timed = async <T>(name: string, fn: () => Promise<T>): Promise<T> => {
    const t0 = performance.now();
    const result = await fn();
    steps.push({ name, seconds: (performance.now() - t0) / 1000 });
    return result;
  };
  console.log(`\n=== rehearsal ${plan.n}: loader=${plan.loader}, dates=${plan.parse === parseFixed ? "fixed" : "naive"}, split=${plan.lineBreak === "\n" ? "LF" : "CRLF-safe"}`);

  // (1) نقطة الرجوع قبل ما نلمس أي حاجة
  const dump = `rollback-${plan.n}.dump`;
  await timed("rollback point (pg_dump)", async () => pgTool("pg_dump", ["-Fc", "-f", dump, "new_erp"]));

  // (2) التجميد: السيستم القديم read-only وأي session مفتوحة بتتقفل
  await timed("freeze legacy", async () => {
    const admin = await connect("postgres");
    await admin.query("alter database legacy_erp set default_transaction_read_only = on");
    await admin.query("select pg_terminate_backend(pid) from pg_stat_activity where datname = 'legacy_erp'");
    await admin.end();
  });
  const probe = await connect("legacy_erp");
  const refused = await probe.query("update customer set name = name where code = 'C1'").catch((e: Error) => e.message);
  console.log(`  write during freeze: ${typeof refused === "string" ? refused : "ALLOWED"}`);
  await probe.end();

  // (3) التصدير من القديم لملفات
  const legacy = await connect("legacy_erp");
  const exported = `export-${plan.n}.csv`;
  await timed("export", () => legacy.query(`copy (select id, customer_code, issued, amount_piastres, status from invoice order by id) to '${sqlPath(exported)}' with (format csv)`));

  // (4) التحويل: كل حاجة بتترفض بتتعد، مفيش سطر بيختفي
  let rejected = 0;
  const rows = await timed("transform", async () => {
    const out: string[][] = [];
    for (const line of readFileSync(exported, "utf8").split(plan.lineBreak)) {
      if (!line) continue;
      const [id, code, issued, piastres, status] = line.split(",") as [string, string, string, string, string];
      const date = plan.parse(issued);
      if (!date) {
        rejected += 1;
        continue;
      }
      out.push([id, code, date, (Number(piastres) / 100).toFixed(2), status]);
    }
    return out;
  });

  // (5) التحميل في السيستم الجديد
  const target = await connect("new_erp");
  await timed("load", async () => {
    await target.query("begin");
    const customers = await legacy.query("select code, name from customer");
    await target.query("insert into partner select * from unnest($1::text[], $2::text[])", [customers.rows.map((r) => r.code), customers.rows.map((r) => r.name)]);
    if (plan.loader === "row-by-row") {
      for (const r of rows) await target.query("insert into invoice values ($1, $2, $3, $4, $5)", r);
    } else {
      // بنشيل الـ index ونبنيه بعد التحميل مرة واحدة بدل ما يتحدث 40 ألف مرة
      await target.query("drop index invoice_partner");
      const file = `load-${plan.n}.csv`;
      writeFileSync(file, rows.map((r) => r.join(",")).join("\n") + "\n");
      await target.query(`copy invoice from '${sqlPath(file)}' with (format csv)`);
      await target.query("create index invoice_partner on invoice(partner_code)");
    }
    await target.query("commit");
  });

  // (6) المطابقة: عدد، إجمالي، ورصيد مفتوح لكل عميل
  const diffs = await timed("reconcile", async () => {
    const a = (await legacy.query("select count(*)::int n, sum(amount_piastres)::text total from invoice")).rows[0];
    const b = (await target.query("select count(*)::int n, (sum(amount) * 100)::bigint::text total from invoice")).rows[0];
    const arOld = await legacy.query("select customer_code c, sum(amount_piastres)::text v from invoice where status = 'open' group by 1");
    const arNew = await target.query("select partner_code c, (sum(amount) * 100)::bigint::text v from invoice where status = 'open' group by 1");
    const newMap = new Map(arNew.rows.map((r) => [r.c as string, r.v as string]));
    const customersOff = arOld.rows.filter((r) => newMap.get(r.c) !== r.v).length;
    const statuses = (await target.query("select distinct status s from invoice order by 1")).rows.map((r) => r.s);
    console.log(`  status values in new_erp: ${JSON.stringify(statuses)}`);
    console.log(`  reconcile: legacy ${a.n} rows / ${a.total}, new ${b.n} rows / ${b.total}, customers off ${customersOff}, rejected ${rejected}`);
    return { rows: a.n - b.n, total: BigInt(a.total) - BigInt(b.total), customersOff, rejected };
  });
  await legacy.end();
  await target.end();

  // (7) البوابة: معيار مكتوب قبل التجربة، مش إحساس في نص الليل
  const passed = diffs.rows === 0 && diffs.total === 0n && diffs.customersOff === 0 && diffs.rejected === 0;
  console.log(`  gate: ${passed ? "GO" : "NO-GO"}`);

  // (8) الرجوع: في الفشل إجباري، وفي الـ rehearsal بنعمله دايمًا عشان نقيس وقته
  await timed("rollback (pg_restore + unfreeze)", async () => {
    pgTool("pg_restore", ["--clean", "--if-exists", "-d", "new_erp", dump]);
    const admin = await connect("postgres");
    await admin.query("alter database legacy_erp reset default_transaction_read_only");
    await admin.end();
  });
  const check = await connect("new_erp");
  const after = await check.query("select (select count(*)::int from invoice) invoices, (select count(*)::int from setting) settings");
  await check.end();
  const open = await connect("legacy_erp");
  const write = await open.query("update customer set name = name where code = 'C1'");
  await open.end();
  console.log(`  after rollback: new_erp invoices ${after.rows[0].invoices}, settings ${after.rows[0].settings}, legacy write ok ${write.rowCount === 1}`);
  for (const s of steps) console.log(`    ${s.name.padEnd(34)} ≈${s.seconds.toFixed(2)} s`);
  return { passed, steps };
}

بالعامية

الـ cutover هو التحويل من السيستم القديم للجديد. دليل Microsoft بيقول إنه غالبًا بيتسمى "cutover weekend" لأنه "usually less than 48 hours"، وإن السيستمين الاتنين مينفعش يتستخدموا أثناءه. ده الفرق الكبير عن الـ deployments اللي تعرفها: مفيش canary ولا gradual rollout في المصادر اللي قريناها. هو أقرب لنقل data center بجدول زمني.

نفس الدليل بيقول كل task محتاجة ترتيب، ووقت، ومسؤول ومسؤول احتياطي، وتعليمات، وتحقق، وتوقيع. والخطة لازم فيها rollback. وابعد عن فترات الإقفال المالي ومواسم الذروة. والـ mock cutover يتعمل "several times" بنفس الـ data والأدوات والناس والتوقيت. وشخص باسمه بيقرر go/no-go على معايير مكتوبة من قبلها.

الـ rehearsal هنا حقيقي على Postgres مؤقت: dump لنقطة الرجوع، freeze للقديم، export، تحويل، تحميل، reconcile، gate، rollback، واتشغل 3 مرات. أول فشل أنا زارعه: parser للتواريخ بيسيب أي شكل تاني في صمت. تاني فشل مكنتش زارعه. على Windows، الـ COPY TO لملف على السيرفر بينهي السطور بـ \r\n، والـ split("\n") بتاعي ساب \r في آخر عمود، فكل status بقت "open\r". عدد الصفوف والإجمالي الاتنين كانوا مظبوطين تمامًا، واللي مسكها هو الرصيد المفتوح لكل عميل بس. وده السبب إنك تعمل rehearsal، وإنك تطابق على أكتر من بُعد.

كل rehearsal كمان بيغذي الخطة. الخطوات اللي بتعتمد على الحجم بس هي اللي بتكبر، ووقت الناس لأ. وآخر وقت للـ go/no-go بيتحسب بالعكس من آخر الـ window: لازم يسيب وقت كفاية للرجوع. الأرقام هنا: مضروبة في 250 على افتراض إن production عشرة مليون فاتورة وإن الزيادة خطية، وده افتراض مش قياس. والدرس 29 بيعمل ده على Odoo.

وحاجة تانية عن الـ freeze: default_transaction_read_only حاجز مش قفل أمان، أي session تقدر تلغيه لنفسها. في الحقيقة كمان بتوقف الـ apps وتقفل الـ connections. وعن الـ dump: شوف قسم 09 · backups، ودايمًا جرّب الـ restore مش الـ dump بس.

فين هستخدمه في شغلي؟ لو هتنقل جدول orders لـ schema جديد أو تغيّر payment provider: اكتب الخطوات كـ script بـ timing لكل خطوة، وشغله على نسخة من الـ production بعد masking مرتين أو تلاتة. قيس، واحسب آخر وقت تقدر تقول فيه "نرجع". الغلطة الشائعة إن الـ reconcile يبقى count(*) بس، وزي ما شفت العدد والإجمالي طلعوا مظبوطين والـ data بايظة.
Interview question "You're at hour 30 of a 48-hour cutover and reconciliation is off by 0.3%. What do you do?" → Compare the elapsed time against the written go/no-go deadline, which was worked back from how long rollback took in rehearsal. Check whether 0.3% is inside the written tolerance. If it isn't and it can't be explained and fixed before the deadline, the named decision-maker calls no-go and we restore. Nobody negotiates the criteria at 3 a.m.
"إنت في الساعة 30 من cutover مدته 48 ساعة، والـ reconciliation فيها فرق 0.3%. هتعمل إيه؟" ← أقارن الوقت بآخر موعد مكتوب للـ go/no-go، اللي اتحسب بالعكس من وقت الـ rollback في الـ rehearsal. أشوف الـ 0.3% جوه الـ tolerance المكتوبة ولا لأ. لو برّاها ومش هقدر أفسرها وأصلحها قبل الموعد، صاحب القرار بالاسم يقول no-go ونرجّع. ومحدش يتفاوض على المعايير الساعة 3 الفجر.

Solution · الحل 
type Defect = { id: string; severity: 1 | 2 | 3; open: boolean };

// الشرط: توقيع الـ key user مش كفاية لو فيه defect خطير لسه مفتوح
function uatGate(signed: boolean, defects: Defect[], maxOpenSev2 = 3): string[] {
  const open = defects.filter((d) => d.open);
  const reasons: string[] = [];
  if (!signed) reasons.push("uat-sign-off missing");
  const sev1 = open.filter((d) => d.severity === 1).map((d) => d.id);
  if (sev1.length > 0) reasons.push(`open severity 1: ${sev1.join(", ")}`);
  const sev2 = open.filter((d) => d.severity === 2).length;
  if (sev2 > maxOpenSev2) reasons.push(`${sev2} open severity 2, limit ${maxOpenSev2}`);
  return reasons;
}

];

Cheat sheet · الخلاصة

  • Phases: discovery, fit-gap, configuration, customization, data migration, UAT, go-live, hypercare. Each ends in a signed artifact.
  • Typical hypercare length: no reliable source. Agree it per project.
  • Configuration is data the vendor carries. Extension is your code on a public seam. Core modification is a patch you reapply. Integration has a monthly running cost.
  • Custom modules block an Odoo database upgrade until they are ported.
  • "Implementer" in Odoo shops usually means functional.
  • RACI: exactly one A per row, at least one R.
  • SAP Activate: 6 phases, fit-to-standard. Success by Design: 5 phases, an adjunct. Odoo's current official method: not confirmed.
  • Never write "ERP failure rate is X". Ask what "fail" means and who measured it.
  • Cutover: usually under 48 hours, both systems frozen, mock it several times.
  • Reconcile on business dimensions: count and total passed while the data was wrong.
  • Work the go/no-go deadline backwards from the time rollback needs.
بالعامية
  • المراحل: discovery وfit-gap وconfiguration وcustomization وdata migration وUAT وgo-live وhypercare. كل واحدة بتخلص بمخرج موقّع.
  • مدة الـ hypercare المعتادة: مفيش مصدر موثوق. اتفق عليها في كل مشروع.
  • الـ configuration data الـ vendor بيشيلها. الـ extension كودك على نقطة رسمية. تعديل الـ core patch بتعيد تطبيقه. والـ integration ليها تكلفة تشغيل كل شهر.
  • الـ custom modules بتوقف upgrade الـ database في Odoo لحد ما تتنقل.
  • "Implementer" في شركات Odoo غالبًا معناها functional.
  • الـ RACI: A واحد بالظبط في كل سطر، وR واحد على الأقل.
  • SAP Activate: 6 مراحل وfit-to-standard. Success by Design: 5 مراحل وإضافة فوق methodology تانية. طريقة Odoo الرسمية الحالية: مش متأكدين منها.
  • متكتبش أبدًا "ERP failure rate is X". اسأل "فشل" معناها إيه ومين قاس.
  • الـ Cutover: غالبًا أقل من 48 ساعة، السيستمين متجمدين، واعمله mock كذا مرة.
