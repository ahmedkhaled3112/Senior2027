Why this matters · ليه ده مهم

English

Odoo runs fine on a laptop with the defaults, and those same defaults are wrong for a company whose invoices live in it. Production adds four questions: how many processes fit on this host, how requests reach them through a proxy without losing the client's identity, whether a backup really contains the PDFs, and which database a hostname opens. Each one has a failure that stays silent until a bad day: chat that stops updating, audit logs full of 127.0.0.1, a restored database with empty attachments, or a login page that lists every client you host.

This lesson runs what can run here against real Odoo 20. This machine is Windows, so multi-worker mode is not run here, and nginx is not run here either: a labelled Node proxy shows the mechanism in front of a real server.

بالعامية

Odoo بيشتغل كويس على اللابتوب بالـ defaults، بس نفس الـ defaults دي غلط لشركة فواتيرها كلها جواه. الـ production بيضيف 4 أسئلة: كام process يستحملهم السيرفر ده، الـ requests هتوصلهم إزاي عن طريق proxy من غير ما هوية الـ client تضيع، الـ backup فيه الـ PDFs فعلًا ولا لأ، وأنهي database هتفتح مع أنهي hostname. كل سؤال منهم ليه failure ساكت لحد يوم وحش: chat وقف يتحدّث، audit logs مليانة 127.0.0.1، database رجعت من backup والـ attachments فاضية، أو صفحة login بتعرض أسماء كل عملائك.

الدرس بيشغّل اللي ينفع يتشغّل هنا على Odoo 20 حقيقي. الجهاز Windows، فالـ multi-worker mode not run here، و nginx كمان not run here: بدله Node proxy متعلّم عليه إنه stand-in عشان يوضّح الآلية قدام server حقيقي.

Part 1 — Workers and limits 🔴 Advancedالجزء 1 — الـ workers والـ limits

English

Odoo has three server classes in odoo/service/server.py. ThreadedServer is used when workers = 0: one process, one thread per request. PreforkServer is used when workers > 0: a master forks HTTP workers, cron workers and a gevent process. GeventServer is that gevent process. Prefork relies on fork, fcntl and POSIX signals, so it does not exist on Windows. In config.py, workers, limit_memory_hard, limit_time_cpu and limit_request are PosixOnlyOptions: on Windows they stay at their defaults and are hidden from --help. Setting them is silently ignored: on this machine both --workers 2 and workers = 2 in the config file exited 0 and left config['workers'] at 0.

The limits, read from odoo/tools/config.py:

  • limit_memory_soft, 2048 MiB: past it, the worker finishes the current request and is recycled.
  • limit_memory_hard, 2560 MiB: past it, any allocation fails. On Linux it is set through RLIMIT_AS.
  • limit_time_cpu, 60 s of CPU per request, and limit_time_real, 120 s of wall clock. A query waiting on a lock burns real time without burning CPU, which is why both exist.
  • limit_request, 65536: a worker is recycled after that many requests, which bounds slow leaks.
  • max_cron_threads, 2: cron workers, which also compete for CPU.

One detail catches people: the memory limits measure virtual memory. odoo/tools/osutil.py returns pmem.vms everywhere except macOS, so a dashboard showing RSS will not line up with when workers get recycled. For sizing, Odoo's deployment guide gives rules of thumb: (CPUs × 2) + 1 as the worker ceiling, about 6 concurrent users per worker, and memory of workers × (0.8 × 150 MB + 0.2 × 1 GB).

// الأرقام دي من دليل Odoo الرسمي، وهي نقطة بداية مش نتيجة: قيس على الـ workload بتاعك
const USERS_PER_WORKER = 6;
const LIGHT_MB = 150;
const HEAVY_MB = 1024;
const HEAVY_SHARE = 0.2;

type Host = { users: number; cpus: number; ramGb: number; cronWorkers: number };

export function size({ users, cpus, ramGb, cronWorkers }: Host) {
  const wanted = Math.ceil(users / USERS_PER_WORKER);
  const cpuCap = cpus * 2 + 1;
  // الـ cron بياخد من نفس الـ CPU، فبيتخصم من السقف
  const httpCap = cpuCap - cronWorkers;
  const workers = Math.min(wanted, httpCap);
  const perWorkerMb = (1 - HEAVY_SHARE) * LIGHT_MB + HEAVY_SHARE * HEAVY_MB;
  const processes = workers + cronWorkers;
  const expectedGb = (processes * perWorkerMb) / 1024;
  // أسوأ حالة: كل process وصل الـ hard limit الافتراضي في نفس اللحظة
  const worstCaseGb = processes * 2.5;
  return {
    users, cpus, wanted, cpuCap, workers,
    servesUsers: workers * USERS_PER_WORKER,
    enough: workers >= wanted,
    expectedGb: +expectedGb.toFixed(1),
    worstCaseGb,
    fitsExpected: expectedGb <= ramGb * 0.75,
    fitsWorstCase: worstCaseGb <= ramGb,
  };
}

for (const host of [{ cpus: 4, ramGb: 16 }, { cpus: 8, ramGb: 16 }, { cpus: 8, ramGb: 48 }]) {
  const r = size({ users: 80, cronWorkers: 2, ...host });
  console.log(`cpus=${r.cpus} ram=${host.ramGb}GB wanted=${r.wanted} cap=${r.cpuCap} workers=${r.workers} serves=${r.servesUsers} enough=${r.enough}`);
  console.log(`  expected=${r.expectedGb}GB worst=${r.worstCaseGb}GB fitsWorst=${r.fitsWorstCase}`);
}

بالعامية

Odoo عنده 3 server classes في odoo/service/server.py. ThreadedServer لما workers = 0: process واحد و thread لكل request. PreforkServer لما workers > 0: master بيعمل fork لـ HTTP workers و cron workers و process للـ gevent. وGeventServer هو الـ process ده. الـ prefork معتمد على fork و fcntl و POSIX signals، فمالوش وجود على Windows. وفي config.py الخيارات workers و limit_memory_hard و limit_time_cpu و limit_request نوعها PosixOnlyOption: على Windows بتفضل على الـ default ومستخبية من --help. ولو حطيتها بتتجاهل من غير ولا كلمة: على الجهاز ده --workers 2 وworkers = 2 في ملف الـ config الاتنين خلصوا بـ exit 0 وconfig['workers'] فضل 0.

الـ limits زي ما هي في odoo/tools/config.py:

  • limit_memory_soft بـ 2048 MiB: لو عدّاها الـ worker بيخلّص الـ request الحالي وبعدين يتعمله recycle.
  • limit_memory_hard بـ 2560 MiB: لو عدّاها أي allocation بيفشل، وعلى Linux بتتطبق عن طريق RLIMIT_AS.
  • limit_time_cpu بـ 60 ثانية CPU لكل request، وlimit_time_real بـ 120 ثانية وقت حقيقي. الـ query اللي مستنية lock بتاكل وقت حقيقي من غير CPU، وعشان كده الاتنين موجودين.
  • limit_request بـ 65536: الـ worker بيتعمله recycle بعد العدد ده من الـ requests، وده بيحدّ أي leak بطيء.
  • max_cron_threads بـ 2: الـ cron workers، وهم كمان بينافسوا على الـ CPU.

تفصيلة بتوقّع ناس كتير: الـ memory limits بتقيس الـ virtual memory. odoo/tools/osutil.py بيرجّع pmem.vms في كل الأنظمة ما عدا macOS، فلو الـ dashboard بتاعك بيعرض RSS مش هيطابق توقيت الـ recycle. وللـ sizing دليل Odoo بيدي قواعد تقريبية: (CPUs × 2) + 1 سقف الـ workers، حوالي 6 users متزامنين لكل worker، والذاكرة workers × (0.8 × 150 MB + 0.2 × 1 GB).

فين هستخدمه في شغلي؟ عميل عنده 80 موظف بيشتكي إن Odoo "بيهنّج الساعة 9 الصبح" على سيرفر 4 CPU. بدل ما تزوّد workers = 30، تحسب: السقف 9، فالـ requests بتقف في الطابور عشان مفيش CPU مش عشان مفيش workers. نفس منطق تظبيط PM2 cluster في Node: عدد الـ processes مربوط بالـ CPU، والزيادة بتجيب context switching مش throughput. الغلطة الشائعة إنك تضاعف الـ workers وتسيب الـ limits على الـ default، فأسوأ حالة الذاكرة تعدّي الـ RAM والـ OOM killer يقتل Postgres.
Trade-off: soft limit size A low limit_memory_soft recycles workers often, costing a registry reload per new process but capping leaks. A high one avoids churn but lets a few heavy reports eat the host. Start from the defaults, watch recycles in the log, then lower the limits until the worst case fits the RAM.
لو limit_memory_soft قليل، الـ workers بيتعملهم recycle كتير وكل process جديد بيدفع تمن تحميل الـ registry، بس الـ leaks محدودة. ولو عالي، الـ churn بيقل بس كام report تقيل ممكن ياكلوا السيرفر. ابدأ بالـ defaults، راقب الـ recycles في الـ log، ونزّل الـ limits لحد ما أسوأ حالة تدخل في الـ RAM.
Interview question "Why does Odoo have both limit_time_cpu and limit_time_real?" → CPU time catches a computation stuck in a loop. Real time catches a request that burns no CPU because it is blocked, usually on a Postgres lock or an external HTTP call. A worker blocked on a lock would never hit a CPU limit.
"ليه Odoo عنده limit_time_cpu و limit_time_real الاتنين؟" ← الـ CPU time بيمسك computation واقفة في loop. والـ real time بيمسك request مش بياكل CPU عشان واقف مستني، غالبًا على Postgres lock أو HTTP call خارجي. worker واقف على lock عمره ما هيوصل لـ CPU limit.

Part 2 — Gevent and websockets 🔴 Advancedالجزء 2 — الـ gevent والـ websockets

English

A prefork HTTP worker handles one request at a time. A websocket stays open for hours, so one open browser tab would pin a whole worker. Odoo therefore runs long-lived bus connections in a separate gevent process on gevent_port (8072), where each connection is a cheap greenlet. It has its own knobs: limit_memory_soft_gevent, limit_memory_hard_gevent and db_maxconn_gevent, all defaulting to the regular values. The model is close to a Node websocket server, one process multiplexing many sockets, and section 06 · real-time covers the general design.

The source shows why routing matters. In odoo/http/server.py, the raw socket is exposed only in threaded or evented mode, with the comment "cannot use websocket in prefork HTTP workers". If /websocket reaches a prefork worker on 8069, the lookup fails and addons/bus/websocket.py raises Couldn't bind the websocket. Is the connection opened on the evented port (8072)?

The user sees almost nothing. The page loads, forms save, because those are ordinary RPCs. Only live updates stop: Discuss messages, notifications, presence. The browser's worker keeps retrying with a delay of up to 120 s plus up to 30 s of jitter (websocket_worker.js). Prefork and the gevent process are not run here: gevent is excluded on Windows in requirements.txt. Threaded mode serves websockets on the main port, so a real handshake can still prove what a proxy must do.

// بيجرّب الـ websocket handshake مباشر وورا proxy غلط وورا proxy صح
import crypto from "node:crypto";
import http from "node:http";
import { startProxy } from "./proxy-standin.ts";

process.env.PYTHONUTF8 = "1";
type Lab = { server(): Promise<{ httpPort: number; stop(): void }>; stop(): Promise<void> };
const LAB_URL: string = "file:///D:/tools/odoo/odoo.mjs";
const { startLab } = (await import(LAB_URL)) as { startLab(o: { dir: string; addons: string[] }): Promise<Lab> };

const handshake = (port: number) =>
  new Promise<string>((done) => {
    const key = crypto.randomBytes(16).toString("base64");
    const request = http.request({
      host: "127.0.0.1", port, path: "/websocket?version=saas-19.5-1",
      headers: { Connection: "Upgrade", Upgrade: "websocket", "Sec-WebSocket-Version": "13", "Sec-WebSocket-Key": key, Origin: "http://127.0.0.1" },
    });
    request.on("upgrade", (res, socket) => { socket.destroy(); done(`${res.statusCode} upgraded`); });
    request.on("response", (res) => { res.resume(); done(`${res.statusCode} not upgraded`); });
    request.on("error", (e) => done(`error ${e.message}`));
    request.end();
  });

const lab = await startLab({ dir: process.cwd().replace(/\\/g, "/"), addons: [] });
try {
  const server = await lab.server();
  const naive = await startProxy(server.httpPort, { forwardedHost: true, relayUpgrade: false });
  const correct = await startProxy(server.httpPort, { forwardedHost: true, relayUpgrade: true });
  console.log("direct to Odoo :", await handshake(server.httpPort));
  console.log("naive proxy    :", await handshake(naive.port));
  console.log("upgrade relayed:", await handshake(correct.port));
  naive.close();
  correct.close();
  server.stop();
} finally {
  await lab.stop();
}
process.exit(0);

Part 3 — Reverse proxy, proxy_mode and TLS 🔴 Advancedالجزء 3 — الـ reverse proxy و proxy_mode و TLS

English

Odoo's built-in server speaks plain HTTP, so TLS terminates at a proxy in front of it. The general pattern is in section 12 · reverse proxy; this part covers what Odoo adds. The config below follows Odoo's deployment guide and is labelled not run here because nginx is not on this machine. Note the header inheritance rule: nginx inherits proxy_set_header from the outer level only if the current location defines none, so location /websocket has to repeat them.

proxy_mode = True tells Odoo to trust forwarded headers. In odoo/http/server.py the check is if config['proxy_mode'] and environ.get('HTTP_X_FORWARDED_HOST'), then werkzeug's ProxyFix with x_for=1, x_proto=1, x_host=1. Two consequences follow. The headers are applied only when X-Forwarded-Host is present, so a proxy that omits it silently turns the feature off. And x_for=1 takes the last entry of X-Forwarded-For, the one your own proxy appended, so a value the client sent earlier in the list is ignored. In a real run, a client-supplied value passing through the proxy was ignored, while a request reaching Odoo directly with those headers was believed. That is why the port has to be firewalled.

Why this matters beyond logs: hr.url_root feeds generated links, and an admin login stores it as web.base.url unless web.base.url.freeze is set. With the wrong scheme, password-reset and portal links come out as http://.

// تنبيه: ⁦[STAND-IN for nginx] Node proxy⁩ بيوضّح الآلية بس، مش بديل لـ production
import http from "node:http";
import type { AddressInfo } from "node:net";

const HOP_BY_HOP = new Set(["connection", "upgrade", "keep-alive", "proxy-connection", "te", "trailer", "transfer-encoding"]);
export type ProxyOptions = { forwardedHost: boolean; relayUpgrade: boolean };

export function startProxy(target: number, options: ProxyOptions) {
  const forwardHeaders = (req: http.IncomingMessage) => {
    const headers: http.OutgoingHttpHeaders = {};
    for (const [key, value] of Object.entries(req.headers)) if (!HOP_BY_HOP.has(key)) headers[key] = value;
    const peer = (req.socket.remoteAddress ?? "").replace("::ffff:", "");
    // زي proxy_add_x_forwarded_for: الـ IP الحقيقي بيتضاف في آخر القايمة
    const previous = req.headers["x-forwarded-for"];
    headers["x-forwarded-for"] = previous ? `${previous}, ${peer}` : peer;
    headers["x-forwarded-proto"] = "https";
    if (options.forwardedHost) headers["x-forwarded-host"] = req.headers.host;
    else delete headers["x-forwarded-host"];
    return headers;
  };

  const server = http.createServer((req, res) => {
    const upstream = http.request({ host: "127.0.0.1", port: target, path: req.url, method: req.method, headers: forwardHeaders(req) }, (r) => {
      res.writeHead(r.statusCode ?? 502, r.headers);
      r.pipe(res);
    });
    upstream.on("error", (e) => { res.writeHead(502); res.end(String(e)); });
    req.pipe(upstream);
  });

  if (options.relayUpgrade) {
    // ده المقابل لـ location /websocket في nginx: Upgrade لازم يتبعت صريح
    server.on("upgrade", (req, socket, head) => {
      const headers = { ...forwardHeaders(req), connection: "Upgrade", upgrade: req.headers.upgrade };
      const upstream = http.request({ host: "127.0.0.1", port: target, path: req.url, method: req.method, headers });
      upstream.on("upgrade", (r, upstreamSocket, upstreamHead) => {
        const lines = Object.entries(r.headers).map(([k, v]) => `${k}: ${String(v)}`).join("\r\n");
        socket.write(`HTTP/1.1 101 Switching Protocols\r\n${lines}\r\n\r\n`);
        if (upstreamHead.length) socket.write(upstreamHead);
        if (head.length) upstreamSocket.write(head);
        upstreamSocket.pipe(socket);
        socket.pipe(upstreamSocket);
        upstreamSocket.on("error", () => socket.destroy());
        socket.on("error", () => upstreamSocket.destroy());
      });
      upstream.on("response", (r) => socket.end(`HTTP/1.1 ${r.statusCode} upstream\r\n\r\n`));
      upstream.on("error", () => socket.destroy());
      upstream.end();
    });
  }

  return new Promise<{ port: number; close: () => void }>((ready) =>
    server.listen(0, "127.0.0.1", () =>
      ready({ port: (server.address() as AddressInfo).port, close: () => { server.closeAllConnections(); server.close(); } }),
    ),
  );
}

Part 4 — Filestore and backups 🔴 Advancedالجزء 4 — الـ filestore والـ backups

English

Binary attachments do not live in Postgres by default. ir_attachment stores a path in store_fname, and the bytes live at data_dir/filestore/<db>/<first 2 hex>/<sha1>. The name is the content's SHA-1, so storage is content-addressed: two attachments with the same bytes share one file. Deleting a row therefore cannot delete the file straight away. _mark_for_gc adds the name to a checklist folder, and _gc_file_store (an autovacuum job) later removes files no row references, after a grace period of at least 30 minutes.

The consequence is the point of this part: a database backup without the filestore loses every PDF, and nothing complains at backup time. The rows survive and still claim a size, while the bytes are gone. There are two backup shapes. odoo-bin db dump writes a zip with dump.sql, manifest.json and filestore/. pg_dump plus a file copy is the same data in two pieces, and it scales better because the zip path copies the filestore to a temp folder first.

If you take the two pieces separately, dump the database first and copy files after. A file with no row is harmless. A row with no file is a lost invoice.

بالعامية

الـ attachments مش في Postgres بالـ default. ir_attachment بيخزّن مسار في store_fname، والـ bytes نفسها في data_dir/filestore/<db>/<أول حرفين hex>/<sha1>. اسم الملف هو الـ SHA-1 بتاع محتواه، يعني content-addressed: اتنين attachments بنفس الـ bytes بيشتركوا في ملف واحد. وعشان كده مسح row مينفعش يمسح الملف على طول. _mark_for_gc بيحط الاسم في فولدر checklist، و_gc_file_store (autovacuum job) بعدين بيشيل الملفات اللي مفيش row بيشاور عليها، بعد grace period 30 دقيقة على الأقل.

النتيجة هي أهم نقطة في الجزء: backup للـ database من غير filestore بيضيّع كل الـ PDFs، ومفيش حاجة بتشتكي وقت الـ backup. الـ rows بتفضل وبتقول إن ليها حجم، والـ bytes راحت. عندك شكلين للـ backup: odoo-bin db dump بيطلّع zip فيه dump.sql وmanifest.json وfilestore/. أو pg_dump مع نسخ الملفات، نفس الـ data على قطعتين، وده بيكبر أحسن لأن طريقة الـ zip بتنسخ الـ filestore لفولدر مؤقت الأول.

لو أخدت القطعتين منفصلين، اعمل dump للـ database الأول وانسخ الملفات بعدها. ملف من غير row مش مشكلة. لكن row من غير ملف يعني فاتورة ضايعة.

فين هستخدمه في شغلي؟ الـ DevOps عامل cron بيعمل pg_dump كل ليلة وبيقول "عندنا backups". يوم ما السيرفر يقع، الأرقام ترجع والـ PDFs وصور المنتجات والمستندات الموقّعة تبقى فاضية. ده نفس فخ إنك تعمل backup لـ Postgres وتنسى الـ S3 bucket بتاع الـ uploads في تطبيق Node. الغلطة الشائعة إنك تثق في exit code 0 بتاع الـ backup من غير ما تعد الملفات.
Trade-off: zip versus pg_dump plus files The zip is one atomic artifact and restores with one command, which suits small databases. It copies the whole filestore on every run and needs that disk space in a temp folder. For a large filestore, use pg_dump -Fc plus an incremental file sync, and accept that you now have to keep two pieces consistent.
الـ zip ملف واحد وبيرجع بأمر واحد، ومناسب للـ databases الصغيرة، بس بينسخ الـ filestore كله كل مرة ومحتاج مساحته في فولدر مؤقت. لو الـ filestore كبير، استخدم pg_dump -Fc مع file sync تزايدي، وساعتها بقى عليك إنك تحافظ على توافق القطعتين.

Part 5 — The restore test 🔴 Advancedالجزء 5 — اختبار الـ restore

English

A backup is a hypothesis until it has been restored. The drill below loads the backup into a second database, neutralizes it, starts a server, and asserts on record counts, attachment reads and a real login. The general theory of RPO, RTO and PITR is in section 09 · backups; here the Odoo-specific parts matter.

Neutralize is not optional on a copy of production. db load -n runs every installed module's data/neutralize.sql. The base script deactivates mail servers and clears their credentials, inserts a dummy mail server, disables crons except autovacuum, and sets database.is_neutralized. Without it, a restored copy would email real customers and run real integrations on its first cron tick. db load also generates a new database UUID unless you pass --move, so a copy cannot pose as the original to services keyed on it.

Time the drill, because the elapsed time from restore to first login is your measured RTO. Then automate it as a scheduled job that fails loudly, and prove the check can fail by damaging the restore on purpose. A check that has never failed has not been tested.

Part 6 — Multi-database and dbfilter 🔴 Advancedالجزء 6 — الـ multi-database و dbfilter

English

One Odoo server can host many databases. _set_session_and_dbname in odoo/http/router.py picks one per request from the session cookie, the X-Odoo-Database header, or, if exactly one database is visible, that one ("monodb"). All three pass through db_filter. dbfilter is a regex with two placeholders: %h for the full host and %d for its first label after removing www.. So dbfilter = ^%d$ maps cairo.erp.test to the database cairo.

The related options: db_name (-d) limits exposed databases when no dbfilter is set. list_db = False disables the selector and the database manager. Each database that receives traffic gets its own registry in the process, and every worker pays that separately. The registries sit in an LRU: on POSIX its size comes from limit_memory_soft at 15 MB per registry (136 at the default), and elsewhere it stays at the class default of 42; ODOO_REGISTRY_LRU_SIZE overrides both. In the real run below, RSS rose by about 13 MB per extra registry on an idle database, close to the 10 MB average that Odoo's source comment estimates. A busy one with warm caches will cost more, so measure yours.

The risk is a wide filter. dbfilter = .* with list_db = True shows every client's database name to anyone who opens the selector, and lets a request pick any of them by header. A hardening checklist: an anchored dbfilter; list_db = False; a long random admin_passwd (its default is literally admin, and it can only be set in the config file); a firewall so that 5432, 8069 and 8072 are unreachable from outside.

بالعامية

سيرفر Odoo واحد يقدر يشيل databases كتير. _set_session_and_dbname في odoo/http/router.py بيختار واحدة لكل request من الـ session cookie، أو الـ header X-Odoo-Database، أو لو ظاهر database واحدة بس بياخدها ("monodb"). التلاتة بيعدّوا على db_filter. وdbfilter regex فيها placeholders: %h للـ host كله و%d لأول جزء منه بعد شيل www.. يعني dbfilter = ^%d$ بيربط cairo.erp.test بـ database اسمها cairo.

الخيارات المرتبطة: db_name (-d) بيحدد الـ databases الظاهرة لو مفيش dbfilter. list_db = False بيقفل الـ selector والـ database manager. وكل database بيجيلها traffic بيبقى ليها registry جوه الـ process، وكل worker بيدفع ده لوحده. الـ registries محفوظين في LRU: على POSIX حجمه بيتحسب من limit_memory_soft بواقع 15MB لكل registry (يعني 136 بالـ default)، وفي الأنظمة التانية بيفضل 42؛ وODOO_REGISTRY_LRU_SIZE بيغطي على الاتنين. في التشغيل الحقيقي الـ RSS زاد حوالي 13MB لكل registry على database هادية، قريب من متوسط الـ 10MB اللي مكتوب في comment جوه source بتاع Odoo. والـ database المشغولة بالـ caches بتاعتها هتكلّف أكتر، فقيس عندك.

الخطر هو الفلتر الواسع. dbfilter = .* مع list_db = True بيعرض أسماء databases كل عملائك لأي حد يفتح الـ selector، وبيخلّي أي request يختار أي واحدة بالـ header. الـ hardening checklist: dbfilter مقفول بـ ^ و $؛ list_db = False؛ admin_passwd طويل وعشوائي (الـ default بتاعه حرفيًا admin، وبيتحط في ملف الـ config بس)؛ و firewall بحيث 5432 و 8069 و 8072 ميتوصلوش من بره.

فين هستخدمه في شغلي؟ شركة بتعمل hosting لـ 30 عميل صغير على Odoo. ^%d$ بيخلّي كل subdomain يفتح الـ database بتاعته، زي tenant routing في Next.js middleware. بس لازم تحسب: 30 registry في كل worker بيضربوا في عدد الـ workers، والـ upgrade بقى 30 مرة. الغلطة الشائعة إنك تسيب dbfilter فاضي عشان "لسه شغالين"، فأول عميل يشوف قايمة باقي العملاء.
What breaks at scale With more active databases than the registry LRU holds, every request can evict and rebuild a registry, which takes seconds. Lowering limit_memory_soft also shrinks the LRU on POSIX, so tuning memory can change this. Size ODOO_REGISTRY_LRU_SIZE and the RAM for your real tenant count, or split tenants across servers.
لو عدد الـ databases النشطة أكبر من حجم الـ registry LRU، كل request ممكن يطرد registry ويبني واحدة جديدة، وده بياخد ثواني. وتقليل limit_memory_soft بيصغّر الـ LRU كمان على POSIX، فظبط الذاكرة ممكن يأثر على ده. ظبّط ODOO_REGISTRY_LRU_SIZE والـ RAM على عدد الـ tenants الحقيقي، أو قسّم الـ tenants على سيرفرات.

Common mistakes · غلطات شائعة

❌ proxy_mode without X-Forwarded-Host 
# الـ proxy_mode هنا مش هيعمل حاجة خالص
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
✅ Send all three headers 
# الشرط في الكود بيبص على الـ Host ده بالذات
proxy_set_header X-Forwarded-Host $http_host;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
بالعامية

❌ من غير X-Forwarded-Host، الشرط في odoo/http/server.py مبيتحققش، فـ Odoo بيفضل شايف الـ proxy وhttp ومن غير أي warning، حتى لو proxy_mode = True. ✅ ابعت التلاتة، وراجع النتيجة بـ endpoint زي /lab/whoami بدل ما تفترض.

❌ /websocket falls through to 8069 
# الـ websocket هيروح لـ prefork worker ويفشل
location / {
  proxy_pass http://odoo;
}
✅ A dedicated location to 8072 
# الـ Upgrade لازم يتبعت صريح للـ gevent
location /websocket {
  proxy_pass http://odoochat;
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection $connection_upgrade;
}
بالعامية

❌ لو /websocket وقع في location /، بيروح 8069 والـ prefork worker مش عنده socket، فالتحديث اللحظي بيقف والصفحة شغالة عادي. ✅ location مخصوص رايح 8072 ومعاه Upgrade وConnection. ومتنساش تكرر الـ forwarded headers جواه عشان الوراثة بتقف.

❌ Backing up only Postgres 
# بيرجّع exit 0 والـ PDFs مش جواه
pg_dump -Fc -p "$PG_PORT" odoo > odoo.dump
✅ Database first, then files, then verify 
# الترتيب مهم: ملف زيادة أهون من row من غير ملف
pg_dump -Fc -p "$PG_PORT" odoo > odoo.dump
rsync -a "$DATA_DIR/filestore/odoo/" backup/filestore/
# الفحص الحقيقي هو الـ restore drill
node restore-drill.ts
بالعامية

❌ pg_dump لوحده بيرجّع نجاح والـ attachments مش جواه، وهتكتشف ده يوم الكارثة. ✅ الـ database الأول وبعدها الملفات، وبعدين restore drill يتأكد إن كل ملف موجود. rsync هنا مثال ومتشغّلش على الجهاز ده.

❌ Restoring production without neutralize 
# النسخة دي هتبعت إيميلات حقيقية مع أول cron
odoo-bin db -c odoo.conf load staging prod.zip
✅ Always neutralize copies 
# الـ crons والـ mail servers بيتقفلوا قبل أول تشغيل
odoo-bin db -c odoo.conf load -n staging prod.zip
بالعامية

❌ من غير -n، الـ staging معاه mail servers و crons و webhooks بتوع production، فأول cron يبعت تذكير دفع لعملاء حقيقيين. ✅ -n بيشغّل الـ neutralize، وفي التشغيل الحقيقي الـ crons نزلت من 39 لـ 1.

❌ A wide filter on a shared server 
; أي حد يشوف أسماء كل الـ databases
dbfilter = .*
list_db = True
✅ Anchored, no listing 
; كل hostname بيفتح database واحدة بس
dbfilter = ^%d$
list_db = False
بالعامية

❌ .* مع list_db = True عرض الخمس databases كلهم لـ hostname غريب في التشغيل الحقيقي. ✅ فلتر مقفول بـ ^ و $، وlist_db = False. ومن غير ^ و $ الـ regex ممكن تطابق أكتر من database.

Cheat sheet · الخلاصة

  • workers = 0 is threaded; workers > 0 is prefork and POSIX only.
  • Sizing: ceiling CPUs × 2 + 1, about 6 users per worker, cron counts against CPU.
  • Defaults: soft 2048 MiB, hard 2560 MiB, CPU 60 s, real 120 s, 65536 requests. Memory limits measure virtual memory.
  • /websocket must go to 8072 with Upgrade. If it doesn't, only live updates die, silently.
  • proxy_mode applies only if X-Forwarded-Host is present.
  • Enable proxy_mode only behind a proxy, and firewall Odoo's ports.
  • Attachments are files named by SHA-1, deduplicated, and removed by GC.
  • A database backup without the filestore loses every PDF and still exits 0.
  • Separate pieces: database first, files after.
  • Restore on a schedule with load -n, assert on content, time it for RTO, and prove the check fails.
  • dbfilter = ^%d$, list_db = False, random admin_passwd, firewall 5432.
  • Each active database is a registry in every worker: count it in RAM.
