Why this matters · ليه ده مهم

English

An Odoo module runs inside the same process and transaction as the code that posts invoices, so a bug here can misstate money. Odoo's test runner has its own rules, and one of them is dangerous: a run can select nothing, report success and exit 0. This lesson builds a small refund module, then tests it, debugs it, profiles it and gates it in CI.

All of it ran on a private Odoo 20 lab on Windows under load, so timings carry a ≈ and the counts are what you should trust.

بالعامية

الـ module في Odoo شغال جوه نفس الـ process والـ transaction بتوع الكود اللي بيرحّل الفواتير، فأي bug هنا ممكن يبوّظ أرقام فلوس. والـ test runner بتاع Odoo ليه قواعده، وواحدة منهم خطر: ممكن الـ run ميختارش أي test، ويقول نجحت، ويخرج بـ exit 0. في الدرس ده هنبني module صغير للـ refunds، ونعمله test و debug و profile، ونحطه ورا CI.

Part 1 — TransactionCase and Form 🟡 Intermediateالجزء 1 — الـ TransactionCase والـ Form

English

TransactionCase runs all of a class's tests in one transaction that is never committed, and each test method in a savepoint. It's the same isolation trick as the transaction-rollback tests in section 13, built into the framework. Calling commit() inside a test raises an error for that reason.

setUpClass runs once per class and suits expensive shared data. setUp runs before every test. Anything a test writes, including changes to records from setUpClass, is rolled back at the end of that test. The run confirms it: test A renamed the shared partner and created a refund, and test B saw the original name and no refund. By then setUpClass had run once and setUp twice.

create() and Form test different things. create() talks to the ORM: it enforces model constraints and ignores the view. Form loads the real view and simulates a user: it runs @api.onchange methods and enforces the view's required, readonly and invisible rules. Below, reason is optional on the model and required="1" in the view, so the same missing value passes with create and fails with Form.

بالعامية

TransactionCase بيشغّل كل tests الكلاس في transaction واحد عمره ما بيتعمله commit، وكل test method جوه savepoint. دي نفس فكرة عزل الـ tests بالـ rollback في قسم 13، بس جاهزة في الـ framework. وعشان كده لو ناديت commit() جوه test هترمي error.

setUpClass بتشتغل مرة لكل كلاس ومناسبة للبيانات المشتركة الغالية. setUp بتشتغل قبل كل test. وأي حاجة الـ test يكتبها، حتى لو تعديل على records من setUpClass، بترجع في آخر الـ test. التشغيل بيأكد ده: test A غيّر اسم الـ partner المشترك وعمل refund، و test B شاف الاسم الأصلي ومفيش refund. ولحد اللحظة دي setUpClass اشتغلت مرة وsetUp مرتين.

create() وForm بيختبروا حاجات مختلفة. create() بيكلم الـ ORM: بيطبق constraints الـ model وبيتجاهل الـ view. Form بيحمّل الـ view الحقيقية وبيمثل دور اليوزر: بيشغّل @api.onchange وبيطبق required وreadonly وinvisible بتوع الـ view. هنا reason اختياري في الـ model وrequired="1" في الـ view، فنفس القيمة الناقصة بتعدي مع create وبتفشل مع Form.

فين هستخدمه في شغلي؟ لو الـ integration بتاعك في Node بيكتب عن طريق JSON-2، فهو ماشي في طريق create: مفيش onchange ومفيش قواعد view. يعني الـ record اللي بيتعمل من الـ API ممكن يبقى ناقص حقول اليوزر مجبر يملاها. اكتب test بـ create يمثل الـ API و test بـ Form يمثل الموظف، ولو القاعدة لازم تتطبق على الاتنين حطها constraint في الـ model مش في الـ view.

Part 2 — Tags and how tests get selected 🟡 Intermediateالجزء 2 — الـ tags وإزاي الـ tests بتتختار

English

Tests run only with --test-enable. --test-tags then filters them with the grammar [-][tag][/module][:class][.method], comma-separated. @tagged adds tags to a class, and a leading minus removes one.

A test runs in one of two phases. at_install runs right after that module loads, while later modules aren't loaded yet. post_install runs once the whole registry is ready, and that's what you want for most business tests, because another module may override your flow. In the run below the at_install test started before the log line Starting post tests, and the post_install test started after it. HttpCase belongs in post_install: Odoo logs a warning otherwise.

Now the trap. Selecting nothing isn't an error. A typo in a method name, a module that isn't installed, or a manifest Odoo refuses all end the same way: exit status 0 and 0 failed, 0 error(s) of 0 tests, logged at WARNING level. A CI job that only checks the exit code goes green having tested nothing. A hard install failure is different: a missing data file aborted with Failed to load registry and a non-zero status. So the exit code catches some failures and misses the worst one. Always parse the count and fail when it's 0.

بالعامية

الـ tests مبتشتغلش غير بـ --test-enable. و--test-tags بيفلترها بالصيغة [-][tag][/module][:class][.method]، مفصولة بـ commas. @tagged بيضيف tags للكلاس، والسالب قدام الـ tag بيشيله.

الـ test بيشتغل في مرحلة من اتنين. at_install بيشتغل بعد ما الـ module يتحمل على طول، والـ modules اللي بعده لسه متحملتش. post_install بيشتغل بعد ما الـ registry كله يجهز، وده اللي عايزه لمعظم tests الـ business، لأن module تاني ممكن يعمل override للـ flow بتاعك. في التشغيل، test الـ at_install بدأ قبل سطر Starting post tests، وtest الـ post_install بدأ بعده. وHttpCase مكانه post_install، وإلا Odoo بيكتب warning.

دلوقتي الفخ. إن مفيش test اتختار مش error. typo في اسم method، أو module مش متنزل، أو manifest Odoo رفضه، كلهم بيخلصوا نفس النهاية: exit status 0 و0 failed, 0 error(s) of 0 tests، ومكتوبة بمستوى WARNING. CI بيبص على الـ exit code بس هينوّر أخضر ومفيش حاجة اتختبرت. فشل الـ install الصريح مختلف: ملف data ناقص وقّف كل حاجة بـ Failed to load registry و status مش صفر. يعني الـ exit code بيمسك شوية حالات وبيفوّت أخطرها. لازم دايمًا تقرا الـ count وتفشّل الـ job لو صفر.

فين هستخدمه في شغلي؟ زي vitest --passWithNoTests بالظبط، بس هنا السلوك ده هو الـ default ومفيش flag يقفله. لو حد غيّر اسم test class في PR، والـ pipeline بيختار بالاسم، الـ job هيفضل أخضر. في الـ code review أي تغيير في --test-tags أو في اسم كلاس بيتشغل بالاسم لازم يتراجع، والـ CI لازم يتأكد إن عدد الـ tests أكبر من صفر.

Part 3 — HttpCase and tours 🟡 Intermediateالجزء 3 — الـ HttpCase والـ tours

English

HttpCase starts a real test server. url_open makes an HTTP request against it, so controllers, routing and auth are all exercised. That part works here: /erp_lab/ping passed.

A tour is a scripted UI walk: a JS file registers steps with a trigger selector and a run action, and start_tour drives it in headless Chrome. On this machine Odoo's runner can't start. Chrome exists, but browser_js needs the Python package websocket-client to talk to it, and that package isn't in the venv, so the test is skipped. A skipped test counts as passed in the summary, so the run printed 0 failed, 0 error(s) of 1 tests without executing a single step. That's the Part 2 trap with a different costume. start_tour through Odoo's runner is not run here.

As a labelled stand-in, playwright-core drove the same steps in real Chrome and saved a refund with 0 page errors. It also loaded the page with ?debug=assets,tests and called odoo.startTour directly. The real tour file ran inside the page and logged TOUR erp_lab_refund_tour SUCCEEDED, and both records were in the database afterwards. What this skips is Odoo's Python-side harness, such as its log checking and failure reporting.

Part 4 — shell, logging and --dev 🟡 Intermediateالجزء 4 — الـ shell والـ logging و --dev

English

odoo-bin shell opens Python with env ready. It's the Odoo equivalent of a Node REPL with your models loaded, and it's the fastest way to ask the database a question. Nothing persists unless you call env.cr.commit(): a record created in one session wasn't there in the next, and a committed one was.

Logging is standard Python logging. Declare _logger = logging.getLogger(__name__) and the logger's name becomes odoo.addons.erp_lab.models.refund. --log-level sets a global preset, --log-handler=odoo.addons.erp_lab:DEBUG turns up one module only, and --log-sql is shorthand for --log-handler=odoo.sql_db:DEBUG, printing every query with its time. Prefer the narrow handler: a global debug level buries you.

--dev takes a comma-separated list. xml reads views from the source file instead of the database, so a view edit needs no -u. qweb logs the compiled template with QWeb errors. reload restarts the server when source changes, but it needs the watchdog package (or inotify on Linux). That package isn't installed here, so Odoo logged 'watchdog' module not installed. Code autoreload feature is disabled. On this machine, restart Odoo after editing Python, even though the practice launcher passes --dev=xml,reload. xml has its own sharp edge: a view written with its root element on the same line as <field name="arch" type="xml"> crashed with TypeError, because Odoo concatenates that element's .text, which is None without whitespace. Put the root element on its own line.

One Windows detail: printing Arabic through the shell raises UnicodeEncodeError under the cp1252 console encoding until PYTHONUTF8=1 is set.

Part 5 — Profiler and reading ORM SQL 🔴 Advancedالجزء 5 — الـ Profiler وقراءة الـ SQL بتاع الـ ORM

English

odoo.tools.profiler.Profiler is a context manager. collectors=['sql'] records every query with its time and stack, and db=None keeps the result in memory. Give it a database name instead and it stores an ir.profile row, which is what the web client's debug menu does: enable profiling there and each request is recorded, with sql_count and a speedscope view. Enabling it writes an expiry to the base.profiling_enabled_until parameter, so it switches itself off.

The ORM prefetches well on its own, so an N+1 usually comes from calling search inside a loop, where prefetching can't help. The compute below does exactly that on 2,000 records. The profiler counted 2,001 queries against 2 after the fix, and the top query appeared 2,000 times, which is the signature: one normalized SQL shape repeated once per record.

The fix is to query once for the whole recordset. _read_group pushes the sum into a single GROUP BY. A stored computed field is the other option: it moves the cost to write time and makes the value searchable, but every refund change must then recompute the partner's total. Choose by how often it's read compared with written. The checksum matched in both versions, so the result didn't change. Note what EXPLAIN says about the repeated query: an index scan touching 22 buffers, which looks perfectly healthy. Looking at one query would have told you nothing, which is why you count first. Finally, lock the win in with assertQueryCount, so the next person who adds a loop gets a red test.

# الغلط: search جوه loop، يعني query لكل record
def _compute_partner_total_slow(self):
    for rec in self:
        siblings = self.search([('partner_id', '=', rec.partner_id.id)])
        rec.partner_total_slow = sum(siblings.mapped('total'))

# الصح: query واحدة لكل الـ recordset
def _compute_partner_total_fast(self):
    groups = self._read_group(
        [('partner_id', 'in', self.partner_id.ids)],
        groupby=['partner_id'],
        aggregates=['total:sum'],
    )
    totals = {partner.id: total for partner, total in groups}
    for rec in self:
        rec.partner_total_fast = totals.get(rec.partner_id.id, 0.0)

    sql = re.sub(r"'[^']*'", '?', sql)
    sql = re.sub(r'\b\d+\b', '?', sql)
    sql = re.sub(r'(\?,\s*)+\?', '?', sql)

odoo.tools.profiler.Profiler هو context manager. collectors=['sql'] بيسجل كل query بوقتها والـ stack بتاعها، وdb=None بيخلي النتيجة في الـ memory. لو اديته اسم database بيخزن صف في ir.profile، وده اللي الـ debug menu في الـ web client بيعمله: فعّل الـ profiling من هناك وكل request بيتسجل، ومعاه sql_count وعرض speedscope. والتفعيل بيكتب وقت انتهاء في parameter اسمه base.profiling_enabled_until، فبيقفل لوحده.

الـ ORM بيعمل prefetch كويس لوحده، فالـ N+1 غالبًا بييجي من search جوه loop، والـ prefetch ملوش حل هناك. الـ compute اللي فوق بيعمل كده بالظبط على 2,000 record. الـ profiler عدّ 2,001 query مقابل 2 بعد التصليح، وأعلى query اتكررت 2,000 مرة، ودي العلامة: شكل SQL واحد بيتكرر مرة لكل record.

الحل إنك تسأل مرة واحدة للـ recordset كله. _read_group بتنزّل الجمع لـ GROUP BY واحد. والـ stored computed field هو الاختيار التاني: بينقل التكلفة لوقت الكتابة وبيخلي القيمة searchable، بس كل تغيير في refund لازم يعيد حساب إجمالي العميل. اختار حسب عدد مرات القراءة مقابل الكتابة. والـ checksum طلع نفس الرقم في النسختين، فالنتيجة متغيرتش. وبص EXPLAIN قال إيه عن الـ query المتكررة: index scan بيلمس 22 buffer، وده شكله سليم جدًا. لو بصيت على query واحدة مكنتش هتعرف حاجة، وعشان كده بتعد الأول. وفي الآخر ثبّت المكسب بـ assertQueryCount، عشان اللي يضيف loop بعدك ياخد test أحمر.

فين هستخدمه في شغلي؟ نفس N+1 اللي بتقابله في Prisma أو TypeORM (قسم 09)، ونفس قراءة الـ plan (EXPLAIN). لما المحاسب يقول "تقرير نهاية الشهر بياخد 4 دقايق": متبدأش بإضافة index. اعمل reproduce بحجم بيانات الشهر، عدّ الـ queries، ولو لقيت رقم قريب من عدد الصفوف يبقى المشكلة في الكود مش في الـ database.

English

Odoo can't be tested against a mock database: the ORM generates Postgres-specific SQL, so CI needs a real server. The GitHub Actions workflow below uses a postgres:18 service. It is not run here; for the CI basics see section 13.

The same steps did run for real through a Node script against startLab: install, test, parse the log, and exit non-zero on failures or on 0 tests. The first test run is slow because Odoo builds its asset bundles when an HttpCase is in the suite. Here the test step took ≈84 s for 7 tests in the CI script and ≈151 s in an earlier, busier run, while a run with no HttpCase took ≈6 s. type Verdict = "pass" | `fail: ${string}`;

export function verdict(log: string, minTests: number): Verdict {
  const lines = [...log.matchAll(/(\d+) failed, (\d+) error\(s\) of (\d+) tests/g)];
  const last = lines.at(-1);
  if (!last) return "fail: no summary line";
  const [failed, errors, total] = [Number(last[1]), Number(last[2]), Number(last[3])];
  if (total === 0) return "fail: 0 tests ran";
  if (failed + errors > 0) return `fail: ${failed} failed, ${errors} errors`;
  // الـ suite لو صغرت يبقى غالبًا ملف test اتمسح أو اتغير اسمه
  if (total < minTests) return `fail: only ${total} tests, expected at least ${minTests}`;
  return "pass";
}

Cheat sheet · الخلاصة

  • TransactionCase: one uncommitted transaction per class, a savepoint per test. Shared data in setUpClass.
  • create tests the model. Form tests the view: onchange and required rules.
  • --test-tags [-][tag][/module][:class][.method] needs --test-enable.
  • at_install runs during loading. post_install runs with the full registry; use it by default.
  • 0 tests selected means exit 0. Parse of N tests and fail when N is 0.
  • A skipped test counts as passed. Tours skip here because websocket-client is missing.
  • odoo-bin shell: nothing persists without env.cr.commit(), and it runs as superuser.
  • --log-handler=odoo.addons.x:DEBUG for one module, --log-sql for every query.
  • --dev=xml reads views from files. reload needs watchdog.
  • Windows: PYTHONUTF8=1 or Arabic output raises UnicodeEncodeError.
  • Slow report: reproduce, count, read SQL, EXPLAIN, fix, assertQueryCount.
  • CI needs real Postgres. Check the exit code and the summary line together.
