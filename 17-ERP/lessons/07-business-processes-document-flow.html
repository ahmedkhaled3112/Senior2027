Why this matters · ليه ده مهم

English

An ERP is organised around a few end-to-end processes, not around screens. Sell something and you walk Order-to-Cash; buy something and you walk Procure-to-Pay; finish a month and you walk Record-to-Report. Every integration you will write plugs into one of these chains at a specific document, and the question that decides whether your code is correct is always the same: which document exists now, and which accounting entries did it produce? Consultants speak in these process names, and exit-test question 2 of this section is exactly this lesson.

بالعامية

الـ ERP متقسّم حوالين كام process من أولها لآخرها، مش حوالين شاشات. لو بتبيع تبقى ماشي في Order-to-Cash، لو بتشتري تبقى في Procure-to-Pay، ولو بتقفل الشهر تبقى في Record-to-Report. أي integration هتكتبه بيدخل على السلسلة دي عند document معين، والسؤال اللي بيحدد كودك صح ولا غلط دايمًا واحد: إيه الـ document الموجود دلوقتي، وطلّع قيود إيه؟ الـ consultants بيتكلموا بأسامي الـ processes دي، وسؤال 2 في اختبار الخروج بتاع القسم هو الدرس ده بالظبط.

Part 1 — Order-to-Cash as a state machine 🟢 Basicالجزء 1 — الـ Order-to-Cash كـ state machine

English

Order-to-Cash (O2C) is the chain quotation → sales order → delivery → invoice → payment. The first two documents are commitments: a quotation is an offer and a sales order is a promise, and neither has moved value, so neither produces a journal entry. Value moves at the other three: goods leave (delivery), a legal claim appears (invoice), cash arrives (payment).

The order of delivery and invoice is not fixed, and that is where developers get surprised. Under accrual accounting, revenue belongs to the period in which control of the goods passes to the customer (the principle in IFRS 15), not the period of the invoice or the cash. So the same DELIVER event needs a different entry depending on where it came from: deliver first, and revenue is earned against Unbilled AR, an asset; invoice first, and the invoice credits Deferred Revenue, a liability, which delivery later releases.

That makes a state machine the natural model, as taught in section 11 · state machines. The transition table lists what is legal, anything else throws, and each transition updates the document and posts its entry in one database transaction against the lesson 05 ledger. The UPDATE ... WHERE state = $old guard settles races between two workers.

                        DELIVER
                   +-------------> delivered ------ INVOICE ------+
                   |                                              v
quotation -CONFIRM-> sales_order                         delivered_invoiced --PAY--> paid
    |              |                                              ^                   ^
  CANCEL           +-------------> invoiced ------ DELIVER -------+                   |
    v                   INVOICE       |                                               |
cancelled                             +--PAY--> paid_undelivered ------ DELIVER ------+
الـ quotation بيتأكد فيبقى sales order، أو بيتلغي. من الـ sales order فيه طريقين: تسلّم الأول فتبقى delivered، أو تعمل فاتورة الأول فتبقى invoiced. الطريقين بيتقابلوا عند delivered_invoiced وبعدها الدفع يوصلك لـ paid. والخط اللي تحت: العميل دفع قبل ما يستلم (paid_undelivered)، والتسليم بعدها يقفل الـ order.

// حماية: لو الـ port فاضي الـ driver بيرجع لـ 5432 ويوصل للـ database الحقيقية بتاعتك
export function guardedPort(raw: string | undefined): number {
  const n = Number(raw);
  if (!/^\d+$/.test(String(raw)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port ${raw}`);
  }
  return n;
}

export async function connect(database = "postgres"): Promise<pg.Client> {
  const client = new pg.Client({
    host: "127.0.0.1",
    port: guardedPort(process.env.LEDGER_PORT),
    user: "ledger",
    database,
  });
  await client.connect();
  return client;
}

// نفس الـ schema بتاع الدرس 5 باختصار: الـ trigger بيتأكد إن القيد متوازن وقت الـ COMMIT
export async function createLedger(db: pg.Client): Promise<void> {
  await db.query(`
    create table account(code text primary key, kind text not null);
    create table journal_entry(
      id bigint generated always as identity primary key,
      entry_date date not null, memo text not null,
      idempotency_key text not null unique);
    create table journal_line(
      id bigint generated always as identity primary key,
      entry_id bigint not null references journal_entry(id),
      account text not null references account(code),
      debit numeric(18,2) not null default 0 check (debit >= 0),
      credit numeric(18,2) not null default 0 check (credit >= 0),
      ref text,
      check ((debit = 0) <> (credit = 0)));
    create function check_balanced() returns trigger language plpgsql as $$
    declare d numeric; c numeric; begin
      select coalesce(sum(debit),0), coalesce(sum(credit),0) into d, c
        from journal_line where entry_id = new.entry_id;
      if d <> c then
        raise exception 'entry % unbalanced: % <> %', new.entry_id, d, c using errcode = '23514';
      end if;
      return null;
    end $$;
    create constraint trigger balanced after insert or update on journal_line
      deferrable initially deferred for each row execute function check_balanced();`);
  for (const [code, kind] of ACCOUNTS) {
    await db.query("insert into account values ($1, $2)", [code, kind]);
  }
}

// لازم تتنادى جوه transaction: الـ document والقيد يتكتبوا مع بعض أو ميتكتبوش خالص
export async function post(db: pg.Client, e: Entry): Promise<number | null> {
  if (e.lines.length === 0) return null;
  const inserted = await db.query(
    `insert into journal_entry(entry_date, memo, idempotency_key) values ($1, $2, $3)
     on conflict (idempotency_key) do nothing returning id`,
    [e.date, e.memo, e.key],
  );
  if (inserted.rowCount === 0) return null;
  const id = Number(inserted.rows[0].id);
  for (const l of e.lines) {
    await db.query(
      `insert into journal_line(entry_id, account, debit, credit, ref)
       values ($1, $2, $3::numeric / 100, $4::numeric / 100, $5)`,
      [id, l.account, l.dr ?? 0, l.cr ?? 0, l.ref ?? null],
    );
  }
  return id;
}

export async function postTx(db: pg.Client, e: Entry): Promise<number | null> {
  await db.query("begin");
  try {
    const id = await post(db, e);
    await db.query("commit");
    return id;
  } catch (err) {
    await db.query("rollback");
    throw err;
  }
}

export function show(e: Entry): void {
  if (e.lines.length === 0) {
    console.log(`  ${e.date}  ${e.memo}: no entry`);
    return;
  }
  console.log(`  ${e.date}  ${e.memo}`);
  for (const l of e.lines) {
    const side = l.dr ? `Dr ${(l.dr / 100).toFixed(2).padStart(9)}` : `Cr ${(l.cr! / 100).toFixed(2).padStart(9)}`;
    console.log(`      ${l.account.padEnd(18)} ${side}`);
  }
}

// رصيد كل account لحد تاريخ معين، موجب = مدين وسالب = دائن
export async function balances(db: pg.Client, upTo = "9999-12-31"): Promise<Map<string, number>> {
  const r = await db.query(
    `select l.account, sum(l.debit - l.credit) as bal
       from journal_line l join journal_entry e on e.id = l.entry_id
      where e.entry_date <= $1 group by l.account order by l.account`,
    [upTo],
  );
  return new Map(r.rows.map((x) => [x.account as string, Number(x.bal)]));
}

export function printBalances(title: string, b: Map<string, number>): void {
  console.log(title);
  for (const [account, bal] of b) {
    if (bal !== 0) console.log(`      ${account.padEnd(18)} ${bal.toFixed(2).padStart(10)}`);
  }
}
import type pg from "pg";
import { connect, freshDb } from "./db.ts";
import { balances, createLedger, egp, type Entry, type Line, post, postTx, printBalances, show } from "./ledger.ts";

type State =
  | "quotation" | "sales_order" | "delivered" | "invoiced"
  | "delivered_invoiced" | "paid_undelivered" | "paid" | "cancelled";
type Event = "CONFIRM" | "DELIVER" | "INVOICE" | "PAY" | "CANCEL";

// جدول الـ transitions هو الحقيقة الوحيدة: اللي مش فيه يبقى ممنوع
const TRANSITIONS: Record<State, Partial<Record<Event, State>>> = {
  quotation: { CONFIRM: "sales_order", CANCEL: "cancelled" },
  sales_order: { DELIVER: "delivered", INVOICE: "invoiced", CANCEL: "cancelled" },
  delivered: { INVOICE: "delivered_invoiced" },
  invoiced: { DELIVER: "delivered_invoiced", PAY: "paid_undelivered" },
  delivered_invoiced: { PAY: "paid" },
  paid_undelivered: { DELIVER: "paid" },
  paid: {},
  cancelled: {},
};

type Order = { id: number; qty: number; unitPrice: number; unitCost: number; vatBps: number };

// قواعد القيود دالة pure: بتاخد الـ state اللي جاي منه عشان نفس الـ event ليه قيد مختلف
function postingLines(from: State, event: Event, o: Order): Line[] {
  const net = o.qty * o.unitPrice;
  const vat = Math.round((net * o.vatBps) / 10_000);
  const cost = o.qty * o.unitCost;
  switch (event) {
    case "DELIVER": {
      const earnedFrom = from === "sales_order" ? "Unbilled AR" : "Deferred Revenue";
      return [
        { account: "COGS", dr: cost },
        { account: "Inventory", cr: cost },
        { account: earnedFrom, dr: net },
        { account: "Revenue", cr: net },
      ];
    }
    case "INVOICE": {
      const creditTo = from === "delivered" ? "Unbilled AR" : "Deferred Revenue";
      return [
        { account: "AR", dr: net + vat },
        { account: creditTo, cr: net },
        { account: "VAT Output", cr: vat },
      ];
    }
    case "PAY":
      return [{ account: "Bank", dr: net + vat }, { account: "AR", cr: net + vat }];
    default:
      // ملاحظة: الـ quotation والـ sales order التزام مش حركة مالية، فمفيش قيد
      return [];
  }
}

class IllegalTransition extends Error {
  override name = "IllegalTransition";
}

async function apply(db: pg.Client, o: Order, event: Event, date: string): Promise<Entry> {
  await db.query("begin");
  try {
    const row = await db.query("select state from sales_order where id = $1", [o.id]);
    const from = row.rows[0].state as State;
    const to = TRANSITIONS[from][event];
    if (!to) throw new IllegalTransition(`order ${o.id}: cannot ${event} from ${from}`);
    // الشرط على الـ state القديم هو اللي بيحسم الـ race لو requestين جم مع بعض
    const moved = await db.query(
      "update sales_order set state = $1 where id = $2 and state = $3",
      [to, o.id, from],
    );
    if (moved.rowCount !== 1) throw new IllegalTransition(`order ${o.id}: lost the race on ${event}`);
    const entry: Entry = {
      key: `order:${o.id}:${event}`,
      date,
      memo: `${event} order ${o.id} (${from} -> ${to})`,
      lines: postingLines(from, event, o),
    };
    await post(db, entry);
    await db.query("commit");
    return entry;
  } catch (err) {
    await db.query("rollback");
    throw err;
  }
}

بالعامية

الـ O2C هو السلسلة quotation ← sales order ← delivery ← invoice ← payment. أول اتنين مجرد التزام: الـ quotation عرض والـ sales order وعد، ومفيش قيمة اتحركت، فمفيش قيد. القيمة بتتحرك عند التلاتة التانيين: البضاعة خرجت (delivery)، حق قانوني ظهر (invoice)، الفلوس وصلت (payment).

ترتيب الـ delivery والـ invoice مش ثابت، وهنا المبرمجين بيتفاجئوا. في الـ accrual accounting، الإيراد بيتحسب في الفترة اللي السيطرة على البضاعة انتقلت فيها للعميل (ده المبدأ في IFRS 15)، مش فترة الفاتورة ولا فترة الفلوس. فنفس الـ event DELIVER محتاج قيد مختلف حسب جاي منين: لو سلّمت الأول، الإيراد بيتسجل قصاد Unbilled AR وده asset. لو عملت الفاتورة الأول، الفاتورة بتعمل credit لـ Deferred Revenue وده liability، والتسليم بعدين بيفكّه.

عشان كده الـ state machine هو الشكل الطبيعي (شرحناه في قسم 11): جدول الـ transitions بيقول المسموح، وأي حاجة تانية بترمي error، وكل transition بيعدّل الـ document ويكتب القيد في transaction واحدة على الـ ledger بتاع الدرس 5. وشرط UPDATE ... WHERE state = $old هو اللي بيحسم الـ race بين اتنين workers.

Part 2 — Procure-to-Pay and 3-way matching 🟢 Basicالجزء 2 — الـ Procure-to-Pay والـ 3-way matching

English

Procure-to-Pay (P2P) is the mirror image: RFQ → purchase order → receipt → vendor bill → payment. An RFQ (request for quotation) and a PO are commitments again. The control that matters here is 3-way matching: before paying, compare what you ordered (PO quantity and price), what you received (receipt quantity), and what you are billed (bill quantity and price). It exists because the vendor writes the bill, so the bill alone proves nothing.

Real matching needs a tolerance, otherwise a rounding difference of one piastre blocks a payment. Use a percentage together with an absolute cap, because 2% of a ten-million-pound order is a lot of money. A failed match puts the bill on hold for a person to decide; it is never silently adjusted.

Goods and bills arrive independently, so textbook ledgers use a clearing account called GR/IR (goods received / invoice received). Receipt: Dr Inventory, Cr GR/IR. Bill: Dr GR/IR, Dr VAT Input, Cr AP. A line that has both events nets to zero, and whatever stays open is an unmatched event. If you know Kafka, this is a stream-stream join of a receipts topic and a bills topic on the PO line key: GR/IR is the state store, and aged open items are events that outlived the join window and now need a human.

In Odoo Community 20, purchase_method (the Control Policy) decides which quantity a bill proposes. The 3-way matching switch itself, module_account_3way_match, is marked widget="upgrade_boolean" in the settings view and the module is absent from this checkout, so it is Enterprise. The run below also shows that real-time valuation in 20.0 uses no GR/IR: the bill debits the stock account directly.

type Piastres = number;

type MatchInput = {
  po: { qty: number; unitPrice: Piastres };
  receivedQty: number;
  bill: { qty: number; unitPrice: Piastres };
};

// الـ tolerance نسبة ومعاها سقف مطلق: 2% من طلبية بعشرة مليون لوحدها مبلغ كبير
type Tolerance = { priceBps: number; priceCapPerUnit: Piastres; qtyBps: number };

type Reason =
  | "BILLED_MORE_THAN_RECEIVED" | "RECEIVED_MORE_THAN_ORDERED"
  | "PRICE_ABOVE_PO" | "NOT_RECEIVED_YET";

type MatchResult = {
  status: "match" | "within_tolerance" | "hold";
  reasons: Reason[];
  payable: Piastres;
  priceVariance: Piastres;
  openPoQty: number;
};

export function threeWayMatch({ po, receivedQty, bill }: MatchInput, t: Tolerance): MatchResult {
  const reasons: Reason[] = [];
  // ضرب في basis points بدل قسمة float، فالمقارنة integer بالكامل
  const qtyLimit = (q: number) => (q * (10_000 + t.qtyBps)) / 10_000;
  if (receivedQty === 0) reasons.push("NOT_RECEIVED_YET");
  else if (bill.qty > qtyLimit(receivedQty)) reasons.push("BILLED_MORE_THAN_RECEIVED");
  if (receivedQty > qtyLimit(po.qty)) reasons.push("RECEIVED_MORE_THAN_ORDERED");

  const allowedRise = Math.min(Math.floor((po.unitPrice * t.priceBps) / 10_000), t.priceCapPerUnit);
  if (bill.unitPrice > po.unitPrice + allowedRise) reasons.push("PRICE_ABOVE_PO");

  const priceVariance = (bill.unitPrice - po.unitPrice) * bill.qty;
  const exact = bill.qty === receivedQty && bill.unitPrice === po.unitPrice;
  const status = reasons.length > 0 ? "hold" : exact ? "match" : "within_tolerance";
  return {
    status,
    reasons,
    // المبلغ المتعلق ميتدفعش: الـ hold معناه صفر لحد ما بني آدم يقرر
    payable: status === "hold" ? 0 : bill.qty * bill.unitPrice,
    priceVariance,
    openPoQty: Math.max(po.qty - receivedQty, 0),
  };
}

function billReceived(ref: string, date: string, poValue: number, billed: number, vatBps = 1400): Entry {
  const vat = Math.round((billed * vatBps) / 10_000);

الـ P2P هو المرايا بتاعة الـ O2C: RFQ ← purchase order ← receipt ← vendor bill ← payment. الـ RFQ (طلب عرض سعر) والـ PO التزامات برضه. الرقابة المهمة هنا هي 3-way matching: قبل ما تدفع، قارن اللي طلبته (كمية وسعر الـ PO)، واللي استلمته (كمية الاستلام)، واللي اتفوتر عليك (كمية وسعر الفاتورة). السبب إن المورد هو اللي كاتب الفاتورة، فالفاتورة لوحدها مش دليل على حاجة.

الـ matching الحقيقي محتاج tolerance، وإلا فرق قرش واحد في التقريب يوقّف الدفع. استخدم نسبة ومعاها سقف مطلق، لأن 2% من طلبية بعشرة مليون جنيه مبلغ كبير. لو الـ match فشل الفاتورة بتتحط hold وبني آدم يقرر، ومتتعدلش في صمت أبدًا.

البضاعة والفاتورة بيوصلوا كل واحد لوحده، فالدفاتر في الكتب بتستخدم حساب وسيط اسمه GR/IR (goods received / invoice received). الاستلام: Dr Inventory وCr GR/IR. الفاتورة: Dr GR/IR وDr VAT Input وCr AP. السطر اللي حصل له الحدثين بيقفل صفر، واللي يفضل مفتوح يبقى event مالقاش نصه التاني. لو تعرف Kafka: ده stream-stream join بين topic اسمه receipts وtopic اسمه bills على key سطر الـ PO، والـ GR/IR هو الـ state store، والـ open items القديمة هي events عدّت الـ join window ومحتاجة بني آدم.

Part 3 — Record-to-Report: closing the month 🟢 Basicالجزء 3 — الـ Record-to-Report: قفل الشهر

English

Record-to-Report (R2R) turns transactions into statements. Sub-ledgers hold the detail (each open customer invoice, each vendor bill), and one control account in the general ledger holds the total, so the first check of any close is that they agree. Then come adjustments that no operational document produced: an accrual records an expense you have incurred but not been billed for, such as October's electricity, and depreciation spreads an asset's cost across months.

Reconciliation proves the books against an outside source; the bank statement is the classic one. Only then do you close the period so nothing can post into it, and report: P&L, balance sheet, the checks from lesson 03.

For an engineer, a close is a pipeline of idempotent steps with blocking gates. Idempotent, because finance will rerun it; blocking, because a report built on unreconciled cash is worse than a late report. Odoo enforces the same rule: res.company._validate_locks refuses a hard lock date while unreconciled bank statement lines exist in the period. The locking mechanics and their race conditions are in lesson 06.

A real mistake from writing this example: I first summed the balances as floats, the equation came out as -0.00, and A = L + E printed false for books that balanced. The fix is to add in integer piastres, as lesson 04 teaches.

الـ Record-to-Report (R2R) بيحوّل الحركات لقوايم مالية. الـ sub-ledgers فيها التفاصيل (كل فاتورة عميل مفتوحة، كل فاتورة مورد)، وcontrol account واحد في الـ general ledger فيه الإجمالي، فأول check في أي close إن الاتنين يتفقوا. بعدين adjustments مفيش document عملها: الـ accrual بيسجل مصروف حصل ولسه الفاتورة بتاعته مجتش، زي كهربا أكتوبر، والإهلاك بيوزّع تكلفة الأصل على الشهور.

الـ reconciliation بتثبت الدفاتر قصاد مصدر خارجي، وكشف البنك هو المثال المشهور. بعدها بس تقفل الفترة عشان محدش يكتب فيها، وتطلّع التقارير: P&L وbalance sheet والـ checks بتوع الدرس 3.

بالنسبة لمهندس، الـ close هو pipeline من steps كلها idempotent وفيها gates بتوقف. Idempotent لأن المحاسبة هتعيد تشغيله أكيد، وبتوقف لأن تقرير مبني على فلوس مش متطابقة أوحش من تقرير متأخر. Odoo بيطبق نفس القاعدة: res.company._validate_locks بيرفض الـ hard lock date طول ما فيه bank statement lines مش متسوية في الفترة. تفاصيل الـ lock والـ race بتاعه في الدرس 6.

لاحظ كمان الغلطة اللي وقعت فيها وأنا بكتب الكود ده: جمعت الأرصدة كـ float، فالمعادلة طلعت -0.00 وA = L + E طلعت false وهي صح. الحل تجمع بالقروش integer، زي ما شرحنا في الدرس 4.

فين هستخدمه في شغلي؟ أي SaaS بيعمل billing شهري عنده close من غير ما يسميه كده: job بيقفل usage الشهر، يطلع الفواتير، يطابق مع Stripe، ويبعت تقرير. اكتبه كـ steps ليها idempotency key زي accrual:2026-10:electricity، عشان لما الـ job يقع في النص وتشغله تاني ميفوترش العملاء مرتين.

Part 4 — Hire-to-Retire and Plan-to-Produce 🟢 Basicالجزء 4 — الـ Hire-to-Retire والـ Plan-to-Produce

English

Two more chains, as a map only; lesson 25 goes further. Hire-to-Retire follows a person: recruit → onboard → payroll → exit. Payroll is what connects it to accounting, and it is hard because the rules change by law, by country and by date. In Odoo, hr.employee is in Community, while Payroll (hr.payslip) is Enterprise.

Plan-to-Produce follows a product: forecast → BoM → MRP → work order → finished goods. A BoM (bill of materials) is a recipe, and because components can have their own BoMs it is a tree. MRP (material requirements planning) walks that tree and answers one question: what must I make, and what must I buy? Stock on hand has to be netted level by level: 30 finished boards on the shelf also save you 30 SoCs and 360 capacitors you no longer need.

  Hire-to-Retire:    recruit --> onboard --> payroll --> exit

  Plan-to-Produce:   forecast --> BoM --> MRP --> work order --> finished goods

// بيخصم المخزون مستوى بمستوى: Sub-assembly جاهزة بتوفّر كل القطع اللي تحتها
export function explode(root: string, qty: number, bom: Bom, onHand: Map<string, number>): Plan {
  const stock = new Map(onHand);
  const plan: Plan = { purchase: new Map(), make: new Map() };

  const visit = (sku: string, needed: number, path: string[]): void => {
    if (path.includes(sku)) throw new Error(`BoM cycle: ${[...path, sku].join(" -> ")}`);
    const available = stock.get(sku) ?? 0;
    const used = Math.min(available, needed);
    stock.set(sku, available - used);
    const net = needed - used;
    if (net === 0) return;
    const children = bom.get(sku);
    if (!children) {
      plan.purchase.set(sku, (plan.purchase.get(sku) ?? 0) + net);
      return;
    }
    plan.make.set(sku, (plan.make.get(sku) ?? 0) + net);
    for (const c of children) visit(c.sku, c.qty * net, [...path, sku]);
  };

  visit(root, qty, []);
  return plan;
}

Part 5 — Master data versus transactional data 🟢 Basicالجزء 5 — الـ master data قصاد الـ transactional data

English

Master data describes the things the business deals with and changes slowly: customers, vendors, products, the chart of accounts. Transactional data records events and is written constantly: orders, invoices, stock moves, payments. Every transaction points at master records and inherits from them: the product decides the income account, the customer decides payment terms and tax treatment.

That inheritance is why master-data quality decides an ERP project. A wrong product category posts every future sale to the wrong account; a customer split across three records has three credit limits, three aging reports and a revenue figure nobody can trust. Bad master data is a bug multiplied by every transaction that follows.

Deduplicating needs more than GROUP BY name. Normalise first (case, punctuation, legal suffixes, Arabic letter variants), use the strongest key available (tax ID), then fuzzy-match names with pg_trgm inside a block such as the same city (see section 09 · search). Two records with different tax IDs are never merged automatically, however similar the names are.

A trap found while testing this: in a database created with --locale=C, pg_trgm ignores Arabic letters completely, so similarity is 0.000 and there is no error. With Arabic names, create the database with a Unicode-aware provider such as --locale-provider=builtin --builtin-locale=C.UTF-8, and test before you trust the number.

  let a = seed;

Part 6 — Document flow in real Odoo 🟡 Intermediateالجزء 6 — الـ document flow في Odoo الحقيقي

English

In an ERP each document is generated from the previous one and links back to it. That linkage is the feature: from a payment you can walk to the invoice, the delivery and the order, and an auditor does exactly that. In Odoo the graph for one sale is sale.order → stock.picking → account.move → account.payment, with account.partial.reconcile joining the receivable line of the invoice to the receivable line of the payment.

The script below runs in a throwaway lab, walks one sale, and prints IDs and entries. Read section 5 of the output carefully, because Odoo 20 differs from Part 1. With the valuation labelled Perpetual (at invoicing), delivery posts no journal entry at all: the stock move only records a value of −1800. Cost of goods and revenue are posted together on the customer invoice. Section 9 shows the consequence: with the invoicing policy on ordered quantities, an invoice issued before delivery still posts revenue and COGS while qty_delivered is 0, and the later delivery posts nothing. There is no automatic deferred revenue; cut-off is the accountant's job.

So the textbook model and the product differ, and only reading the entries tells you which one you are on. Company default valuation is periodic, where the vendor bill debits an expense instead. Lesson 22 covers valuation and lesson 23 the entries.

Common mistakes · غلطات شائعة

❌ Revenue at invoice, always 
// الإيراد بيتسجل مع الفاتورة مهما كان التسليم
case "INVOICE":
  return [
    { account: "AR", dr: net + vat },
    { account: "Revenue", cr: net },
    { account: "VAT Output", cr: vat },
  ];
✅ The source state decides 
// الفاتورة قبل التسليم بتروح التزام مش إيراد
case "INVOICE": {
  const creditTo = from === "delivered"
    ? "Unbilled AR" : "Deferred Revenue";
  return [
    { account: "AR", dr: net + vat },
    { account: creditTo, cr: net },
    { account: "VAT Output", cr: vat },
  ];
}
بالعامية

❌ لو الإيراد بيتسجل مع الفاتورة دايمًا، سيناريو B هيطلّع إيراد 3000 في أكتوبر والبضاعة لسه في المخزن، وده cut-off غلط. ✅ الحالة اللي جاي منها هي اللي بتحدد: قبل التسليم يبقى Deferred Revenue، وبعده يبقى بيقفل الـ Unbilled AR. ولو شغال على Odoo، اعرف إن الـ default بيعمل الأول، فالمحاسب لازم يعالجها.

❌ Document and entry in two transactions 
await db.query("update sales_order set state = 'invoiced' where id = $1", [id]);
// لو الـ process وقع هنا: الـ order فاتورته اتعملت ومفيش قيد
await postTx(db, entry);
✅ One transaction, guarded 
await db.query("begin");
const moved = await db.query(
  "update sales_order set state = $1 where id = $2 and state = $3",
  [to, id, from],
);
if (moved.rowCount !== 1) throw new IllegalTransition("lost the race");
await post(db, entry);
await db.query("commit");
بالعامية

❌ لو الاتنين في transactions منفصلة، crash في النص يسيبك بـ document من غير قيد، والمحاسبة تكتشفه آخر الشهر. ✅ transaction واحدة، وشرط state = $3 هو اللي بيمنع اتنين workers يعملوا نفس الـ transition. ولو القيد لازم يروح نظام تاني، استخدم الـ outbox.

❌ Two-way match 
// بيقارن الفاتورة بالـ PO بس، واللي وصل فعلًا مش في الصورة
const ok = bill.qty <= po.qty
  && bill.unitPrice <= po.unitPrice;
if (ok) await pay(bill);
✅ Three sources, hold on doubt 
const r = threeWayMatch({ po, receivedQty, bill }, tolerance);
// الـ hold بيروح لبني آدم، والمبلغ المسموح بيتدفع
if (r.status === "hold") await queueForReview(bill, r.reasons);
else await pay(bill, r.payable);
بالعامية

❌ المقارنة بالـ PO بس بتدفع 100 وحدة حتى لو وصل 80، زي الحالة 5 في الجزء 2. ✅ التلات مصادر مع بعض، والشك بيروح لمراجعة بني آدم بالأسباب.

❌ Merge on similar names 
-- بيدمج أي اسمين قريبين حتى لو الـ tax ID مختلف
select a.id, b.id from customer a join customer b
  on a.id < b.id and similarity(a.name, b.name) > 0.6;
✅ Normalise, block, respect the tax ID 
-- الاسم بعد الـ normalize، ونفس المدينة، وواحد مالوش tax ID
select a.id, b.id from customer a join customer b
  on a.id < b.id and a.city = b.city and a.norm % b.norm
where a.tax_id is null or b.tax_id is null;
بالعامية

❌ عند 0.6، Cairo Retail وCairo Retailers (similarity 0.706) هيتدمجوا وهما شركتين مختلفين، ومن غير block الـ query هيقارن كل الأسماء ببعض. ✅ normalize الأول، block على المدينة، وأي اتنين بـ tax ID مختلف ميتدمجوش، والنتيجة تروح قايمة مراجعة.

Cheat sheet · الخلاصة

  • O2C: quotation → sales order → delivery → invoice → payment. Quotation and order post nothing.
  • Delivery and invoice can swap. Deliver first: Unbilled AR. Invoice first: Deferred Revenue. Same lifetime profit, different month.
  • P2P: RFQ → PO → receipt → bill → payment. 3-way match compares ordered, received, billed, with a percentage tolerance and an absolute cap.
  • GR/IR is a correlation account. Read its open items, not its balance: +7,500 and −4,000 hide inside 3,500.
  • R2R: sub-ledgers → GL → adjustments → reconcile → close → report. Steps are idempotent, gates block.
  • Master data is inherited by every transaction, so an error in it multiplies.
  • Dedupe: normalise, tax ID first, trigrams inside a block, never auto-merge different tax IDs. pg_trgm under locale C ignores Arabic.
  • Document flow: every document links back. account.partial.reconcile ties invoice and payment lines.
  • Odoo 20 perpetual-at-invoicing: no entry at receipt or delivery; COGS and revenue post on the invoice.
  • In Odoo Community the 3-way matching switch is Enterprise; purchase_method only controls the proposed bill quantity.
بالعامية
  • الـ O2C: quotation ← sales order ← delivery ← invoice ← payment. الـ quotation والـ order مفيهمش قيود.
  • التسليم والفاتورة ممكن يتبدلوا. التسليم الأول: Unbilled AR. الفاتورة الأول: Deferred Revenue. نفس الربح الكلي بس الشهر مختلف.
  • الـ P2P: RFQ ← PO ← receipt ← bill ← payment. الـ 3-way match بيقارن المطلوب والمستلم والمفوتر، بـ tolerance نسبة وسقف مطلق.
  • الـ GR/IR حساب ربط. اقرا الـ open items مش الرصيد: 7500+ و4000− بيستخبوا جوه 3500.
  • الـ R2R: sub-ledgers ← GL ← adjustments ← reconcile ← close ← report. الـ steps idempotent والـ gates بتوقف.
  • الـ master data كل حركة بتورث منها، فالغلطة فيها بتتضرب.
  • إزالة التكرار: normalize، الـ tax ID الأول، trigrams جوه block، ومتدمجش tax IDs مختلفة أوتوماتيك. والـ pg_trgm مع locale C بيتجاهل العربي.
  • الـ document flow: كل document بيشاور على اللي قبله. وaccount.partial.reconcile بيربط سطور الفاتورة والدفعة.
  • Odoo 20 مع perpetual-at-invoicing: مفيش قيد عند الاستلام أو التسليم، والتكلفة والإيراد بيتسجلوا على الفاتورة.
  • في Odoo Community زرار الـ 3-way matching في الـ Enterprise، والـ purchase_method بيتحكم بس في كمية الفاتورة المقترحة.
